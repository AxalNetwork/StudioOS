### Newsletter lists Worker contract (D810, #2256)

Worker routes in `routes/newsletter.ts`, backed by `services/newsletter.ts` and migration 515. D813's pages call them; the client is `lib/api/newsletter.js`. The public routes need no sign-in: a signed token in the query is the authority. Subscribe, confirm and preferences share the `newsletter_public` rate-limit bucket (10 a minute per IP, fails closed); unsubscribe is outside it, because one-click POSTs come from the mailbox provider's servers. Each address gets at most one signup email every ten minutes. Each public route answers 503 `newsletter_unconfigured` in production until `NEWSLETTER_TOKEN_KEY` is set.

| Route | Who | What it answers |
| --- | --- | --- |
| `POST /api/newsletter/subscribe` | anyone (Turnstile) | Takes `{ email, topics[], turnstileToken, hp }`. A new, pending or unsubscribed address becomes `pending`, with a single-use confirm token (only its hash is stored, 48 hours) and the Confirm subscription email. A confirmed address gets a "manage your topics" email and nothing changes. A bounced, paced or honeypot request sends nothing. Every case answers the same 200 `{ ok, message }`. Bad address 400 `invalid_email`; failed challenge 403 `turnstile_failed`. |
| `GET /api/newsletter/confirm?token=` | the mailbox's holder | **Changes nothing** (S1's review: a mail scanner opens every link). A browser gets a page whose one button POSTs; JSON is `{ ok, status: 'pending' }`. Same 410s as the POST. |
| `POST /api/newsletter/confirm?token=` | the mailbox's holder | CSRF-exempt: the single-use token authorises it. Confirms the row, records the consent (`consent_text_version`, `consented_at`), lifts an earlier unsubscribe suppression, raises `token_version` if the row had been unsubscribed, and sends Welcome with `List-Unsubscribe`. A used or unknown token is 410 `token_invalid`; an expired one 410 `token_expired`. A browser gets a short page; JSON otherwise, `{ ok, status: 'confirmed', topics }` with the labels now on (D813). The confirmation email links the SPA's `/newsletter/confirm?token=` (D813), which checks with the GET and posts here on a press. |
| `GET /api/newsletter/preferences?token=` | the token's holder | `{ email (masked), status, topics: { key: bool } }`. The partner letter is listed only for an investor's row. A forged or retired token is 403 `token_invalid`, here and on the three below. |
| `PUT /api/newsletter/preferences?token=` | the token's holder | Takes `{ topics: { key: bool } }`. The partner letter is dropped unless the row is an investor's. Turning a topic on for an unsubscribed row confirms it again. Sends Preferences saved (paced). |
| `GET /api/newsletter/unsubscribe?token=[&topic=]` | the token's holder | Changes nothing. A browser gets a page with one Unsubscribe button that POSTs. |
| `POST /api/newsletter/unsubscribe?token=[&topic=]` | the token's holder, or the mailbox provider (RFC 8058 one-click) | One topic off, or every topic off when `topic` is absent: then the row is `unsubscribed` and the address gets an `unsubscribe` suppression. Sends Unsubscribed (paced). CSRF-exempt (`middleware/csrf.ts`). An unknown topic is 400 `invalid_topic`. |
| `GET /api/me/newsletters` | signed in | `{ email, status, topics: [{ key, label, description, audience, enabled }] }` on the account email; the partner letter only for an investor. |
| `PUT /api/me/newsletters` | signed in | Takes `{ topics: { key: bool } }`. No confirmation email: the account email is verified. The row is `account`-sourced and confirmed when a topic is turned on. The partner letter from anyone but an investor is 403 `topic_not_allowed`. `insights` is written to `insight_subscriptions` too. |

The old `GET /api/insights/newsletter` and `POST /api/insights/newsletter/{subscribe,unsubscribe}` keep answering: the toggle writes the `insights` topic as well, and the GET reads the topic once the member has a subscriber row (D813 retires them).
