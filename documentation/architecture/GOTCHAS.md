# Persistent gotchas

This doc holds the persistent, non-obvious operational gotchas that previously
lived inline in `replit.md`. They were split out so the README stays a
scannable overview of live invariants while the detailed gotchas remain easy to
find. Content below is preserved verbatim from the original `replit.md`
"Persistent gotchas" section.

### Migrations & schema
- **Migrations auto-apply on deploy** (Task #9). `npm run deploy`'s `predeploy` hook runs `node scripts/migrate-d1.mjs --remote`: a forward-only runner that applies only the *pending* `cloudflare-worker/sql/migrations/*.sql` (sorted by numeric prefix, with a filename tiebreak so the duplicate prefixes `011_`/`068_`/`118_` are deterministic) and records each in the `schema_migrations` ledger (`filename` PK, `checksum`, `applied_at`). A failed migration aborts the deploy non-zero and names the file; files applied before it stay recorded. No-new-migrations re-deploy = fast no-op. Pure planning/audit/apply-loop logic lives in `scripts/lib/migrationPlan.mjs` (tested against `node:sqlite` in `cloudflare-worker/test/migrate_d1_plan.test.ts`); the CLI only binds wrangler to it. Still needs Node 22+ (`export PATH=/nix/store/51gywl5jn4nna7al9waj142pw4vfhy0k-nodejs-22.19.0/bin:$PATH`).
  - **One-time baseline (CRITICAL — do before the first auto-deploy).** Prod was migrated by hand with no ledger, so the runner's safety guard *aborts* a plain `--remote` run on an existing DB and tells you to run `npm run d1:baseline` once. The migration set is **NOT self-contained** (base tables live in `sql/schema.sql`; many `ALTER ... ADD COLUMN` files add columns `schema.sql` already declares), so blindly replaying everything would fail with `duplicate column`. `--baseline` therefore **applies the pending *idempotent* files** (real apply for the genuinely-pending `IF NOT EXISTS`/`INSERT OR IGNORE` ones, harmless no-op for the rest) and **records the *non-idempotent* files (57 of 124 — every `ALTER`/bare-`INSERT`, surfaced by `npm run d1:audit`) WITHOUT executing them**, printing each so you can verify it is truly present. Run it once per environment (`--preview`/`--local` analogues), then deploys auto-apply only new migrations. Audit-only: `npm run d1:audit`; plan preview: `node scripts/migrate-d1.mjs --remote --dry-run`.
- Manual single-file apply is still available when needed: `wrangler d1 execute studioos-db --remote --env production --file=cloudflare-worker/sql/migrations/<file>.sql` (then it shows as already-present/no-op to the runner; record it in the ledger if you want the runner to skip it).
- **Never put SQL `BEGIN;`/`COMMIT;` in a migration file** — D1 rejects transaction statements outright (`use state.storage.transaction()...`), so the file can NEVER apply remotely. `141_watchlist_journal_contract.sql` originally had them (mirroring 039) and failed mid-deploy 2026-07-08; they were stripped (the wrangler `d1 execute --file` batch is applied atomically by D1 anyway). `039_project_cascade.sql` still contains them — it is ledger-recorded so leave it (editing an applied file triggers checksum-drift warnings on every run), but its FK-cascade rebuild section will fail on any fresh local/preview DB. **`200_service_offerings_shape.sql` did it again on 2026-09-03** (deploy run 33738772717, the statement right after 199 applied): stripped the same day, `PRAGMA foreign_keys=OFF/ON` replaced by `PRAGMA defer_foreign_keys = TRUE` — inside the batch's implicit transaction SQLite ignores `PRAGMA foreign_keys`, so that bracket never did anything; `util/usersRoleRebuild.ts` is the in-repo precedent — and `frontend/test/migration_column_shapes.test.mjs` now fails any migration carrying a transaction statement or a `foreign_keys` toggle. Wrangler adds a check of its own before D1 sees anything (`src/d1/trimmer.ts`): it reads the RAW file, comments included, strips one `BEGIN TRANSACTION;`/`COMMIT;` pair and refuses the file if the long form still appears — so a header comment that spells it out stops the deploy too; the guard checks the raw text for that as well. **And a rebuild under deferred foreign keys must drop the table and recreate it under its OWN name, then copy back** — SQLite's deferred-violation counter is decremented only by INSERTs into the table the constraint names, made after the drop; a scratch table filled first and renamed into place never clears it, and the batch dies at its end with `FOREIGN KEY constraint failed` (200's first rewrite did exactly that in the local reproduction; `util/usersRoleRebuild.ts` records the same lesson from production). Reproduce a file against a local D1 before it reaches production: `npx wrangler d1 execute studioos-db --config ../wrangler.toml --local --persist-to <scratch> --file=…` from `cloudflare-worker/` runs the same workerd D1 and returns the same errors.
- **`109_events_core.sql` throws a permanent, harmless checksum-drift warning — known, and not to be "fixed."** PR #352 edited the `type` column's trailing comment after this file had already applied to production: a hardcoded 7-value list became a pointer at `eventTypes.ts` (the real source of truth, now grown to 12 values — the hardcoded list was already stale when it was replaced). The DDL is byte-identical; only a SQL comment changed, so production's schema is unaffected either way. But `migrate-d1.mjs` hashes the whole file, so the ledger's recorded checksum will never match disk again, and every future `--dry-run` or apply against this file will print the checksum-drift warning forever. **Do not edit the file to "restore" the old comment** — that reintroduces the stale hardcoded list and is itself a second edit to an applied migration, the exact thing this rule exists to prevent. Confirmed 2026-08-30 during the first production deploy since #352 landed: `npm run deploy` reported the warning, non-blocking, alongside 193/193 applied and 0 pending.
- **Verify the baseline actually matches reality.** The 2026-07-08 prod baseline marked `139–145` as applied WITHOUT executing them, but their effects were *absent* (they postdate the last hand-apply). Fix pattern: PRAGMA-check each marked file's indicator column/table, `DELETE FROM schema_migrations WHERE filename IN (...)` for the truly-missing ones, then re-run `node scripts/migrate-d1.mjs --remote` to real-apply. Editing a *pending* file is safe (checksums are only compared for already-applied files). **That fix pattern is now `npm run d1:verify-marked`** (`--verify-marked`): it reads each ledgered file's `CREATE TABLE` / `ADD COLUMN` effects, checks them against the live schema, and un-marks the absent ones; INSERT-only files are reported as unverifiable rather than guessed at.
- **A `schema_migrations` of the WRONG shape was seen on 2026-09-03 — and the runner did not meet it.** A read-only query through the Cloudflare connection that morning showed `studioos-db` (`16a23acd…`, the id in both `wrangler.toml` tables) with a `schema_migrations(name, applied_at)` of four rows dated April–May 2026 — `score_anti_cheat_v1`, `queue_jobs_lifecycle_columns`, `lp_investors_seal_v1`, `activity_logs_observability_columns` — that nothing in this repository writes. That read was the basis for the runner's foreign-ledger refusal (`ledgerShapeProblem`, `npm run d1:adopt-legacy-ledger`, DEPLOY.md §4(d)). **At 08:44 the same day the first CI migration step (`cloudflare-worker-deploy.yml`, Actions run 33734906029) read the runner's OWN ledger through wrangler against the same binding: `(filename, checksum, applied_at)`, 200 rows, 001–198 applied, 199–207 pending.** The two reads cannot describe one database at one moment and the discrepancy is unexplained — the connection may have reached another database. Wrangler's read is the one that matters, it agrees with the 2026-08-30 "193/193" note above, and the refusal has never fired. It stays as a guard; do not run `adopt-legacy-ledger` unless a `dry-run` from CI names the foreign shape.
- New migrations: additive-only, `IF NOT EXISTS` (so they are safe to re-run and the runner/baseline treats them as real-applies). If an ALTER is needed, also add a lazy PRAGMA-check in the consuming route (`ensureAdvisorWeekColumn()` / `ensureMarketIntelSchema()` are the reference patterns) — an `ALTER` file is flagged non-idempotent by the audit and will be *recorded-without-running* on a baseline, so the lazy bootstrap is what guarantees the column exists on a DB that was baselined before the ALTER landed.
- **`users` table has hit D1's ALTER-rewrite column limit** — `ALTER TABLE users ADD COLUMN` now fails with `too many columns on sqlite_altertab_users`. New user-attached fields must use a side table keyed by `user_id PRIMARY KEY` (see `user_google_links` from migration 065 for the canonical pattern). **Migration 199 did exactly this on 2026-09-03**: the first deploy that ran migrations before shipping (#413) failed at `199_super_admin.sql`'s `ALTER TABLE users ADD COLUMN is_super_admin` with that error, the worker did not ship, and 200–207 (every advisor store from #394) stayed pending behind it. 199 was rewritten — before it had applied anywhere that matters — as the `super_admins` side table, `auth.ts getCurrentUser` hydrates `user.is_super_admin` from it the way it hydrates `mi_pro_subscriptions` (one keyed lookup; D1 also refuses a result set wider than 100 columns, so a JOIN into `SELECT *` is not an option either), and `frontend/test/migration_column_shapes.test.mjs` now fails any migration numbered above 198 that adds a column to `users`.
- **Pending / partial migrations** (historical notes — once the one-time `npm run d1:baseline` has run, the `schema_migrations` ledger is the source of truth for what is applied; `npm run d1:audit` shows which files are non-idempotent and were *recorded-without-running* by the baseline and therefore still warrant a manual verify): `039_project_cascade.sql` partial (deleted_at + index applied; FK-cascade rebuilds blocked by D1's BEGIN/COMMIT rejection); `034_unmounted_routes.sql` unapplied (missing `owner_user_id`); `056_customer_chat_threads.sql` unapplied; `057_data_imports.sql` applied 2026-05-22 (fixes `/api/imports/quota` 500s); `060_auth_recovery.sql` **partial** (`auth_recovery_tickets` + `auth_trusted_contacts` tables + indexes applied 2026-05-22; the two `users` ALTERs for `recovery_cooling_off_until`/`recovery_step_up_due_at` blocked by the column-limit — move to a side table when needed; `user_sessions.assurance_level` ALTER still pending); `061_google_sub.sql` **superseded by 065** (don't re-apply); `062`/`063`/`064` unapplied; `066_team_members.sql` unapplied (Task #10 LD; worker carries `ensureTeamMembersSchema()` lazy bootstrap so the public /team endpoint works regardless — applying the migration also seeds the Guillaume Lauzier row); `115_axal_fit.sql` **applied 2026-06-20** (fixed the Best-Fit Console 500 — `admin_consultation_bookings` + `axal_values`/`axal_fit_scores`/`axal_fit_reports` were missing in prod; worker now also carries `services/axalFitSchema.ts::ensureAxalFitSchema()` lazy bootstrap, wired into the consultations / best-fit / self-best-fit routes, so these self-heal on a cold D1).
- **`workflow_tasks`: the live shape is still unverified, and the whole feature is inert anyway (Task #185).** The 2026-08-29 Replit deploy hit a shape conflict on `workflow_tasks` and reconciled it live against production with no migration file, so the repo does not record what the live table looks like. That question is still open and cannot be settled from this repository or from a CI container: it needs `npx wrangler d1 execute studioos-db --remote --command="PRAGMA table_info('workflow_tasks')"` run by someone holding `CLOUDFLARE_API_TOKEN`. Migration `177_workflow_shared_services.sql` and `services/workflowSchema.ts` agree with each other on the canonical shape (`assignee_user_id INTEGER REFERENCES users(id)`), and both are `CREATE TABLE IF NOT EXISTS` — so if the live table predates them with a different shape, **both are silent no-ops** and the repo's definition never applies.
  - **Before spending effort on that, know that it changes nothing today.** The column is written by **nothing**. All three creation sites — `legalcap.ts:687` (spin-out checklist), `networkfx.ts:397` (marketplace intro), `pipeline.ts:431` (decision-gate review) — insert `(workflow_id, title, description, status, priority, ai_assisted, metadata)` and omit the assignee; no `UPDATE` anywhere sets it. It is read by exactly one query, `dashboard.ts:145` `myTasks`, whose `WHERE t.assignee_user_id = ?` therefore matches no row on any database, correctly migrated or not. That query sits inside `safeQuery(...)` with a `[]` fallback, so a schema mismatch and an empty result are indistinguishable from the outside. Its result becomes `operator_workspace.assigned_tasks`, whose only consumer is `Dashboard.jsx:149` — and that computes `isOperator`, which the file never uses. Writer, reader, response field and consumer: **inert end to end.** Tasks are created for humans to act on and no surface in the SPA displays them.
  - **Do not "fix" this by assigning tasks at creation.** There is no UI that would show them, and the assignment rule is a product decision, not a gap to fill: `networkfx.ts` sets the intro workflow's `owner_user_id` to whoever first requested an intro, while its own comment says the task is "for an admin to handle" — so assigning to the workflow owner would put every future intro request on one arbitrary user's dashboard, which is worse than empty. Finishing this means deciding who owns a workflow task and building the surface; it is a feature, not a repair.
  - **A "column read by a predicate but written by nothing" guard was measured and rejected.** It would have to work off `check-sqlite-columns.mjs`'s predicate harvest, and `singleTablePredicate()` returns null for any query containing a `JOIN` — which excludes `myTasks`, the case that motivated it. Run over the worker anyway it yields 1816 candidates, mostly SQL keywords and `id` (AUTOINCREMENT, so never in an INSERT list); adjudicating the remainder against migrations, backfills and the FastAPI would make it a baseline exercise, not a check. Same reasoning as declining to extend the column guard to the 286 raw-interpolated queries: a heuristic with a large baseline is not a guard.

### Skills & values taxonomy (Task #10)
- **Canonical reference data, not per-user data.** Migration `089_skills_values_taxonomy.sql` (schema) + `090_seed_skills_values_taxonomy.sql` (seed) create `skill_categories`, `skills`, `value_dimensions` — the single source of truth every downstream feature (skill profiles, radar graph, co-founder/partner/investor matching, deck spider) reads from. Both additive + idempotent (`CREATE TABLE IF NOT EXISTS` / `INSERT OR IGNORE` on UNIQUE `slug`), so re-applying is a clean no-op — meaning the deploy migration runner (Task #9) applies them as real-applies on baseline/deploy (no manual wrangler step needed).
- **Lazy bootstrap** `services/skillsTaxonomySchema.ts::ensureSkillsTaxonomySchema()` mirrors `ensureNetworkProfilesSchema()` — creates the SHAPE only on a cold D1 (it deliberately does NOT seed; bulk-inserting 128 rows on a hot path is the seed migration's job). On a cold D1 the tables exist but are empty until 090 is applied; code needing the 8 axes regardless of seed state reads the exported `RADAR_AXES` constant. No route consumes it yet (downstream tasks wire it in) — it's typechecked via `tsconfig` `include: src/**/*.ts`.
- **The 8 canonical radar axes** (`skill_categories.is_radar_axis=1`, equal default `radar_weight=1.0`): `product`, `engineering`, `design`, `gtm_sales`, `marketing_brand`, `finance_ops`, `legal_compliance`, `capital_network`. Chosen to cleanly absorb the legacy 12-axis free-text `SKILL_CATALOG` (in `networkProfilesSchema.ts` + `AdminNetworkProfiles.jsx`): engineering←Engineering+Technical DD, gtm_sales←GTM+Sales, finance_ops←Finance+Operations, capital_network←Fundraising+Recruiting; the rest map 1:1. Reconciling/retiring the legacy catalog is a later task. **Never rename a category/skill slug** — they are stable join keys (`skills.category_slug`, `RADAR_AXES`, downstream radar code).
- **Seniority ladder** is the canonical 5-rung `["aware","working","proficient","advanced","expert"]` (array index 0..4 == rank 1..5), the `skills.seniority_levels_json` default and the `SENIORITY_LEVELS` constant. Per-user proficiency lives in downstream per-user tables, never here.
- **Value dimensions**: `family='schwartz'` = 10 unipolar Schwartz basic values; `family='founder'` = 5 bipolar founder spectrums (`pole_low`↔`pole_high`): Mission-vs-Profit, Speed-vs-Quality, Risk-Appetite, Growth-vs-Sustainability, Autonomy-vs-Structure.

### Backend / Worker
- **The role-schema bootstrap blocks the request path, and that exemption list is load-bearing.** `index.ts` runs `ensureInvestorSchema` / `ensureAdvisorSchema` / `ensureExploringSchema` **before** `app.fetch` on any `/api/*` request that `requiresBlockingRoleSchemaBootstrap()` returns true for — which is the default; only `/api/health`, `/api/track`, `/api/client-error` and safe anonymous GET reads are exempt. The three helpers share one promise per isolate so concurrent cold requests don't issue overlapping rebuilds, but a cold isolate still waits on D1 before serving. **It adds sequential D1 round-trips to a cold isolate's first request**, which is why the exemptions exist — the comment at the call site says the exempt routes "must stay responsive during cold starts and D1 contention". Adding work to the blocking branch, or removing a route from the allowlist, puts that endpoint behind a D1 round-trip on every cold start. **Sizing it honestly (corrected 2026-08-30, after first overstating this entry as "a 504 generator"):** the expensive-looking part — `rebuildUsersRoleCheckForInvestor` — is guarded. It reads `sqlite_master`, and returns `{rebuilt:false}` immediately when the CHECK already accepts the role, so a healthy prod DB pays one cheap query, not a table rebuild. What is *not* guarded is the promote block: three writes (`UPDATE users … role='investor'`, `INSERT INTO investors … WHERE NOT EXISTS`, `UPDATE users SET investor_id=…`) that run on every cold isolate whether or not there is anything to promote, and whose join predicate (`lp.user_id = u.id OR lower(lp.email) = lower(u.email)`) cannot use an index. Across the three helpers that is on the order of 15–20 sequential D1 round-trips before the first response — seconds of added cold-start latency, and a real hazard as the user table grows. It is **not** a plausible cause of a ~100s gateway timeout against 23 production users. So this is a latent scaling hazard and a correctness smell (a data migration living permanently in the request path instead of in `sql/migrations/`), not the explanation for the 2026-08-30 census of 254 504s. That cause is still open — see the apex entry below.
- **The apex 5xx baseline is ~15%, not ~0%.** Measured 2026-08-29→30: 1,044 5xx in 6,729 requests before the bootstrap deploy, 254 in 2,446 after. Any gate, alert or runbook that treats a raw 5xx count as an abort signal will fire constantly and mean nothing. Compare against the baseline. `documentation/architecture/CLOUDFLARE-CUTOVER.md` gate item 2 carries the table and had to be rewritten for exactly this reason.
- **Admin role changes** — direct SQL only, no UI.
- **Referrer-Policy is two-tier (NICE-SEC-01)** — the authenticated app/API surface (`middleware/securityHeaders.ts` on the Worker + dev `backend/app/main.py`) emits `no-referrer` (canonical; never leak IDs/query-params); the public static frontend (`frontend/public/_worker.js` — see the 2026-09-03 correction for where that actually runs) keeps `strict-origin-when-cross-origin` (no sensitive URLs, wants referral attribution). The split is deliberate — don't "unify" them. **Corrected 2026-08-31:** this bullet used to name `github.toml` and `cloudflare.toml` as the files enforcing the laxer value. Both were dead — written in Netlify's TOML dialect (`[[headers]]`, `[context.production]`), which neither GitHub Pages nor Cloudflare Pages has ever read, referenced by nothing in the repo but prose, and added in one unrelated bulk commit (`5d2705e8`, "Add pasted advisor workspace sections reference document"). ### Stripe Tax + payment debugging (Task #12)
- **`automatic_tax` is FLAG-GATED and OFF by default** — every Subscription / Checkout Session / Invoice create only sets `automatic_tax[enabled]=true` when `STRIPE_TAX_ENABLED` is a truthy env value (`1`/`true`/`yes`/`on`). The single source of truth is `cloudflare-worker/src/util/stripeTax.ts` (`stripeTaxEnabled(env)` + `automaticTaxParams(enabled, {checkout, hasExistingCustomer})`); callers spread its result so the disabled path is a no-op (`{}`). **Do NOT hardcode `automatic_tax[enabled]` anywhere** — route it through the helper so the flag stays a single switch.
- **Why the flag exists (don't flip it blind)** — Stripe **rejects** `automatic_tax[enabled]=true` with a hard error until **Stripe Tax is activated in the dashboard** (Settings → Tax) AND an origin address + tax registrations are configured. With the flag off, every create call carries no tax param and behaves exactly as before. Flipping `STRIPE_TAX_ENABLED=1` before the dashboard is ready makes **every** checkout/subscription/invoice create 502 — see ops item (k).
- **`customer_update[address]=auto` is Checkout-only AND requires an existing `customer`** — the helper only adds it when `checkout:true` AND `hasExistingCustomer:true`. On the `customer_email` path (no `customer` yet) Checkout creates + addresses the customer itself, and passing `customer_update` then is an API error. Tax can only be computed once the customer has a determinable address — Checkout collects it; for the incorporation **Invoice** path the customer must already carry an address or finalize fails.
- **Raw PaymentIntents do NOT support `automatic_tax`** — `routes/payments.ts::createPaymentIntent` (à la carte / charges) and `routes/bookings.ts` mint PaymentIntents directly, and Stripe's PI API has **no** `automatic_tax` param (it 400s). Tax on those one-time flows needs the **Stripe Tax Calculation API** (`POST /tax/calculations` → add the computed tax as a line / `amount`), which is a larger change — deliberately deferred (follow-up). Don't "add `automatic_tax` to the PI" — it will fail.
- **Debugging a checkout that suddenly 502s after a tax change** — first check `STRIPE_TAX_ENABLED`: if it's on, confirm Stripe Tax is active in the dashboard and the customer/session has an address. The worker surfaces the Stripe error verbatim in the `checkout_failed`/`subscribe_failed` detail — read it; "You cannot use automatic_tax… without an origin address" or "Tax is not active" means the dashboard side isn't ready, not a code bug. Flip the flag off to restore service while the dashboard is fixed.
- **Webhook idempotency is already enforced at the DB layer** — fulfilment writes are idempotent on UNIQUE keys (`feature_unlocks.source_payment_intent_id`, `promo_redemptions.payment_intent_id`, commission `UNIQUE(user_id,source_type,source_id)`, `invoice_email_log` ids), so a re-delivered/replayed Stripe event no-ops rather than double-fulfilling. There is no separate event-dedup table by design — the per-effect UNIQUE constraints are the dedup. A test-clock subscription-lifecycle run + a webhook-replay integration test both need live Stripe **test keys** (not available in CI here) — tracked as a follow-up; the unit test `cloudflare-worker/test/stripeTax.test.ts` covers the pure flag/param contract.

### Static analysis / code scanning
- **`# nosemgrep` works, but the SARIF still ships the finding.** Semgrep's console output drops suppressed results (`Ran 517 rules on 1656 files: 44 findings`) while its `--sarif` output *keeps* them, tagged `"suppressions": [{"kind": "inSource"}]`. GitHub code scanning opens an alert for those anyway, so every deliberately-annotated line came back as an open "Error" alert — e.g. alert #4581 on `backend/app/models/migrations.py:2793`, whose reported snippet visibly ends in the very `# nosemgrep:` comment meant to silence it. `.github/workflows/semgrep.yml` therefore runs `scripts/strip-suppressed-sarif.py` between the scan and the upload so the payload matches the count semgrep reported. **Don't remove that step to "see everything"** — you'll re-open ~119 alerts that each already carry a written justification in the source. Note the SARIF spec subtlety the script encodes: an *empty* `suppressions: []` array means "known NOT suppressed" and must be kept; only a non-empty array is a real suppression.

- **The job is green even when findings exist.** The scan step is `continue-on-error: true`, so `--error`'s exit 1 never fails the job — a green Semgrep check means "the scan ran", not "nothing was found". Read the step log line (`Ran N rules on M files: K findings`) or the Security tab for the real answer.
