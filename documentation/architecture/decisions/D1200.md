### 1. The tester pool (`services/productTesters.ts` `listTesters`, `GET /api/admin/product-testers`)

**Two new fields on each row:**
- **`decided_by_name`** is who approved, declined, paused or removed the tester, read by name from `users`. It is null when there was no decision. `readTester` carries it too, so one tester's detail reads it as well.
  - `decided_by` stays as the id, for Approvals (D1042).
- **`programmes: { applied, picked }`** counts the tester's `testing_applications` over all time:
  - `applied` is every application not withdrawn, whether applied, picked or declined;
  - `picked` is every application picked.

**Three new filters,** each off when it is not sent:
- **`role`** is `users.role`. A value that is not a role word is 400 `unknown_role`.
- **`availability_given`** is `yes` or `no`. Availability that is blank or only spaces is not given.
- **`in_programme`** is `yes` or `no`. A tester is in a programme while they hold a picked place in a programme that has not closed or been rejected (D1132's open place, picked only).
- Any other value for `availability_given` or `in_programme` is 400 `bad_filter`.

**`matching`** counts what all the filters keep. With only `status`, it is the status total, as before. `totals` stay the whole pool, per status.

**The query is fixed, bound SQL.** Each filter is a `(? = '' OR …)` clause, so no SQL text is assembled from input. The WHERE is written out in both the list query and the count query.

**The email is unchanged.** `member.email` stays on the row for Approvals, as the issue asks. The Product testing page never draws it.

### 2. The Tester badge on applicants (`services/testing.ts` `applicants`)

The owner's applicant list (D812: a partner's programme, and HQ's own through the admin route) now gives each row **`tester`**.

- **True** when the member is in the tester pool with status `active` or `paused`. A paused tester keeps the badge.
- **False** when the member is applied, declined, removed or not in the pool.
- **Null when the pool could not be read** (`testerIds` catches the read). The answer then also carries `tester_pool_readable: false`, so a row never shows a badge, or no badge, that nobody read.
  - The applicants themselves still read.

The list reads `user_id` to match the pool, but does not return it. No email or account id is added to an applicant row.

**Mail's applicant read is unchanged** (`mailApplicants`, D812). It is Mail's own and not this page's.

**"Part 2's reads".** The issue also names part 2's applicant reads, which are not on `main`. When they land, they take `tester` from `testerIds` in the same way.
