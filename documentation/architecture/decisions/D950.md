### 1. The Invitations list is the Worker's

- **Search, filters, sort and page** go to `GET /api/admin/partners/invitations` (D926): `q`, `stage` (Lapsed included, computed on each read), `deal_type`, `invited_by` (a user id), `sent_within`, `sort`, `limit` 25 and `offset`. The page's sort words map to the Worker's (`oldest-open` is `oldest_open`, `expires` is `expires_soonest`).
- **The total is exact,** so Guard L is gone from this tab: no "200+", no "within the newest 200". The tab's count is exact too, from R1's own `total`.
- **One request per filter change.** A change waits 300 ms; another change in that time replaces it. A reply for options that are no longer the page's is dropped, even when it lands after a newer one. The first read, a reload after a write, and Try again go at once.
- **Invited by** offers the admins who sent an invitation the page has read (R1 and the page shown), by user id. A row with no `invited_by_user_id` is left out of the choices.
- **Guard I is not applied here.** Since D924 a resend keeps the stored stage, so the stored stage is the stage reached. `stageOf` takes `repair: false` for the list and the record; the other tabs keep the repair until their parts.

### 2. The Email column

Part 1's latest send (D924):

- **Sent** when `last_send_ok` is true. Sent means the mail service accepted it, never Delivered.
- **Not sent** when it is false, with the reason on hover and to a screen reader: the address is suppressed, email is not set up, the mail service refused it, or the send failed.
- **Not recorded** when it is null: a row from before migration 547, whose result was never stored.

The record says the same as a line, with the number of sends. The reason words are the Overview's (D929's `SEND_REASONS`, #2851). Once both are on `main`, one list should serve both.

### 3. Export CSV

- **The current view,** every page of it: the same filters and sort, read 100 at a time until the Worker's total.
- **Never the invitation link or its token.** The columns are name, email, offered, stage, latest send, send reason, sends, invited by, first sent, opened, expires and deal.
- **Spreadsheet-safe:** every cell is quoted, and a cell that starts with `=`, `+`, `-` or `@` is prefixed with `'`.
- **A page that fails makes no file.** The page says so, with Try again in the button. A file from part of the view would read as the whole.

### 4. One invitation

`GET /api/admin/partners/invitations/:id` (D927 §3). A 404 says there is no such invitation. Any other failure says it could not be read, with Try again. A failed refresh keeps the record under "Could not refresh".

- **The message** the admin wrote, or "No message was written for this invitation."
- **The seven step dates.** A date with no row reads "Not recorded" once the stage shows the step was reached, and "Not reached" past it. A closed invitation keeps no stage, so a missing row there is only "Not recorded"; a revoked one was never signed. Offer chosen shows the first and, when it differs, the latest choice.
- **What we offered:** the types, and the offers the invitee saw. Until they asked for offers, the record says none were made.
- **The chosen deal,** with its offer.
- **The agreement's refusals,** each "Could not be sent [date]", now that an attempt is recorded.
- **The history,** oldest first: who did what and when, with the send result, merged with the signing-link renewals from the envelope's trail. A resend from before part 4 says nothing about the signing link.

Each block answers alone: a failed block shows the Worker's own reason, and the rest stand. The read carries no token, so the link to copy comes from a list row: the one the page holds, or the row read for this address.

### 5. New invitation

- **The five cards show part 4's offer preview** (D927 §4): the Worker's text over a neutral profile, with a line for each part the invitee's answers fill. The preview offers three types per ask, so the cards are read in two asks, once, as the dialog opens.
  - A card whose preview could not be read says so.
  - The invitation can still be sent.
- **The two warnings are one read of part 3's lookup** (D926 §5). An open invitation to the address warns, with Open it; it never refuses (O-DUP). A member is named by role.
  - The member sentence is "Signing keeps their role and adds the partner deal": since part 2 (D925), activation no longer lowers a paid plan.
- **Open invitation, after the send,** opens the record by the id the reply named. The record reads its own row, so no list is read first.
- **Adjust terms** stays out until O-TERMS.

### 6. Resend's result

It reads the reply's `signing_link` (D927 §5):

| `signing_link` | `email_sent` | Result |
|---|---|---|
| `'renewed'` | true | "Sent. The agreement's signing link was renewed and the email carries it." |
| `'not_renewed'` | false | "Not sent. Renewing the signing link failed, so the link already in their inbox still stands." |
| `null` | true | "Sent. No signature was pending, so the onboarding email went instead." |
| `null` | false | "Not sent. Copy the link instead.", with the link to copy. |

A reply with no `signing_link` key (before part 4) says only "Sent." or the not-sent line. The line before the write is D924's, from R7, as before.
