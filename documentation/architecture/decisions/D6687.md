## D6687 — Company-subject orders: an incorporation order for a company, not only a venture (#6687)

- **Status:** built by S11 for #6687, 2026-11-16. Part of #6680 (plan key E7, Phase 1).
- **Depends on:** #6683 (E3), #6685 (E5) and #6686 (E6), all merged.
- **Migration:** `cloudflare-worker/sql/migrations/202611161616_6687_incorporations_company_subject.sql`. This is the plan's one table rebuild; no other migration on `incorporations` lands beside it.

### 1. Why

An order needed a project. The owner wants a company with no legal record to be incorporated directly.

`incorporations.company_id` already means "the company the filing linked or created" (685, D1415), and is null until then. It keeps that meaning, so the company an order is *for* needs a column of its own.

### 2. The table

`incorporations` is rebuilt:

| Column | Change |
|---|---|
| `project_id` | Now nullable. An order for a company has no venture. |
| `subject_company_id` | New, nullable, `→ company_profiles(id)`: the company the order is for, set when it is placed. |
| `CHECK (project_id IS NOT NULL OR subject_company_id IS NOT NULL)` | New. An order with neither is refused. |

**What is kept.** Every other column, default, foreign key and the `UNIQUE` on `stripe_session_id` are as the baseline, 411 and 685 left them. Every row is copied with its id.

**Indexes.** `idx_incorporations_user_status` is recreated. A partial index on `subject_company_id` is added.

**Dependencies.**
- No table references `incorporations` by foreign key. `formation_case_orders.incorporation_id` is a plain integer (D6686).
- No trigger is defined on `incorporations`.

**The copy is checked before the old table is dropped.** The row count, the sum of `amount_cents` and the set of `stripe_session_id` must be equal in both tables. Otherwise the `CHECK` on a scratch table aborts the batch and nothing changes.

**The runtime mirror.** `ensureIncorporationsSchema` declares the same shape. It adds `subject_company_id` through `runSchemaBootstrap` for a database the runner has not reached (D235, D5343).

### 3. The order routes

Both `POST /api/legal/incorporation/order` and `POST /api/legal/incorporate/checkout` accept `company_uid` in place of `project_id`.

- **Who may order.** The caller must be able to edit that company as its Admin (`companyAccess.canEdit`: an Owner, Admin or Founder link, or the primary admin; HQ admins pass as they do everywhere).
- **What is refused:**

  | Request | Answer |
  |---|---|
  | A member who is not an Admin | 403 |
  | No such company, or an archived one | 404 |
  | Both `company_uid` and `project_id` | 400 |

  Each refusal comes before any write.
- **What is stored.** The order is stored with `project_id` NULL and `subject_company_id` set. Pricing, payment and the dev fallback are unchanged.
- **A venture's order** (`project_id`) is exactly as before. "A new company" keeps D1414: the project is created first.

### 4. The reads

- **`GET /api/legal/incorporate/status`** keeps `company_uid` from `company_id` only, so it is null until filed. It adds `subject_company_uid`.
- **`GET /api/legal/incorporate/orders`** adds `subject_company_uid` to each order.
- **The frontend adapter's `orderCompany`** reads `company_uid` as before.

### 5. The filing

`markFiled` reads the order's `subject_company_id` (`incorporationFiling.ts`'s order facts).

For a company-subject order, `filingCompanyStatements` takes the subject company:
- it fills only the company's NULL legal fields and the registered location, as for a venture already in a company;
- it sets `company_id = subject_company_id`;
- it moves no project.

The existing guards (`WHERE status = 'filed' AND company_id IS NULL`) stay on every statement. A subject company that is gone creates nothing in its place.

### 6. "In formation"

The joins now read `COALESCE(company_id, subject_company_id, p.company_id)`:
- the account's companies list (`account_companies.ts`'s formation orders);
- `formationState`'s company and venture order reads.

So a company with a paid company-subject order reads `in_formation`, and reads `incorporated` once its record is filled.

### 7. Not here

- The frontend door (#6688, F1).
- Project-keyed orders, which are unchanged.
- **The legacy formation case.** `ensureCaseForOrder` (D6686) still opens a `convert_project` case with no project for a company-subject order. Naming it `incorporate_company` belongs to `formationCase.ts`, which this issue does not own.
- **The Lab milestone.** It is keyed by the order's user, so it already tolerates a NULL project.

### 8. Tests

`cloudflare-worker/test/incorporations_company_subject_6687.test.ts`, 3 tests:

1. **The rebuild.** It is applied to the schema as it stood before it. Every row, column and id is kept, and the scratch table is gone. `project_id` is now nullable. An order with neither subject is refused by the CHECK. The `UNIQUE` and the index hold.
2. **The routes.** A non-Admin member is refused, and so are an archived company, an unknown company and both subjects, each before any write. An Admin's order stores the subject. The status read's `company_uid` stays null until filed, and `subject_company_uid` is set. A venture's order is as before.
3. **Formation and filing.** A paid company order reads `in_formation`. Filing it fills only the company's empty legal fields, keeps its recorded name, sets `company_id`, creates no company, and the company then reads `incorporated`.

Every existing order, filing and formation test passes unchanged.
