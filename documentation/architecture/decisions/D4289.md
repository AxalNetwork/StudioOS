### 1. What the canvas settles

The canvas follows the prompt in #4289. Where it is more specific, the canvas wins:

1. **The duration is counted in invoices, not months.** Every surface reads "12 invoices per member" and the ledger's invoice column reads "3 of 12". P3 counts a member's first 12 paid invoices on the attributed subscription. It does not count 12 calendar months from the first invoice, so a paused or annual plan doesn't lose or gain commission against the label.
2. **A moved handle redirects for 12 months** (in7s). After that, the old handle reads as unknown and can be taken again. P2 keeps `slug_history` rows for handles 12 months.
3. **Apply again after 90 days** (in9r). A declined application dates its retry. P1 refuses a new application before `decided_at + 90 days` and returns that date.
4. **The handle changes once every 30 days**, and Links says when ("Change in 18 days", in2). P2's read returns `next_change_at`.
5. **The Overview's Eadwyn line restates figures with their date** ("From your link records, as of …"). It is built from P6's read and never from a model call, so it cannot promise anything.
6. **A small group reads "Fewer than 5"** everywhere, in the cohort grid as `<5`. A value nothing stores reads "Not recorded", with the date the store starts when there is one ("EUR revenue is stored from …"). A failed read reads "could not be read. That is not the same as having none." with Try again.
7. **The rates on `/influencers` and in Settings are data, not copy.** The public tier table and Admin's tier defaults read the same settings P1 stores (D1050). The canvas's 20% · 25% · 30% are P1's seed, and the page never types them.
8. **Admin money columns** read "HQ reads" for an admin and the amounts for the Super Admin (in11b, in11d), each currency on its own line.

### 4. P1 (#4290): the program and the membership

Built by S12 (slot S25, taken at the owner's request), 2026-11-03. The migration is `202611031502_influencer_program.sql`. The routes are in the route map (`1000-influencer-program-membership-d4289.md`).

**The registry row and its lists.**
- `influencer` is the tenth program: "Influencers", "Network and referrals", "By application", `partly_built`, position 10.
- How it runs has seven sections (purpose, who, join, rewards, terms, measure, What you do), published as version 1 with a draft copy, as migration 560 seeded the nine.
- The key is in every program list:
  - `programRegistry.PROGRAM_KEYS` (registry order, last);
  - `programGrants.PROGRAMS` and `frontend/src/lib/programGrants.js`, after Refer & Earn, so the studio grid's "Network and referrals" span stays one block;
  - `escalationRequests.REQUESTABLE_PROGRAMS` and `frontend/src/lib/studioProgramTerms.js`, which their tests hold equal to the grid;
  - `programActivity` (HQ's eight Influencer actions);
  - the catalogue card: active influencers, and applications waiting on HQ as Needs you.
- Influencers runs at HQ (`readiness: 'hq'`, grant defaults off), so a branch's members apply at HQ, and a branch refuses `POST /api/influencer/apply`.

**The CHECKs.**
- `referral_partners` and `referral_partner_terms` are rebuilt under their own names. Both segment CHECKs gain `influencers`, and every row, id and AUTOINCREMENT high-water mark is kept.
- `program_grant_defaults` is rebuilt too, because its key CHECK held the nine (553:68-72). This is the CHECK #4290 meant.
- `program_grants` itself needed nothing: migration 562 had already widened its key CHECK to any registry slug.

**The membership.**
- Apply:
  - one open application per member (a partial unique index);
  - an application HQ asked more of is answered by applying again;
  - a declined member may apply again 90 days after the decision.
- Admit makes:
  - the `influencers` row. It carries P1's `handle` column, which P2 writes; S21's hand-out puts the column in P1;
  - a `referral_partners` row in the `influencers` segment, unless the member is already a partner, who keeps their row and segment;
  - draft terms from the tier's defaults. The trigger `influencer_subscription_invoice_paid` is at the tier's `percentage_bps`. Strategic Partner's rate is negotiated, so its draft has no trigger until HQ writes one. The terms check accepts that trigger, so HQ can edit the draft before P3 fires it.
- A re-admitted member reuses their one membership row.

**The tier defaults.**
- `influencer_tier_defaults` holds the rate, the number of paid invoices that earn, the offer budget and the currency for each tier. The seed is the owner's table: 20%, 25%, 30%, and negotiated (null).
- The Super Admin changes them, behind the write bar.
- New terms copy them; terms already drafted keep theirs.
- The public `/api/influencer/tiers` reads the same rows (§1.7).
- Terms have no duration column. P3 reads `duration_invoices` from the defaults, or adds a terms column.

**The benefit (D-l).**
- An active influencer holds Investor Pro through the granted-tier columns (`investor_tier = 'professional'`, status `influencer_grant`).
- It is set only over no investor plan of the member's own. A member who pays keeps their subscription, and `influencers.investor_grant` stays 0.
- Pausing or ending takes back only what this program gave (status `influencer_ended`, tier free), and resuming gives it again.

**Decided once.** Every decision and change is one guarded UPDATE first. Of two admins deciding at once, one decides and the other gets 409. An admission whose rest does not land puts the application back to HQ undecided.
