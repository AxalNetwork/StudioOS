### 1. What the integration builds

Five connector tasks put parts on the same Build modules as GitHub's (D782), and on Validate's experiment record:
- #2948 adds Lovable's;
- #2962, #2963 and #2964 add Vercel's.

Until now `CycleRoute.jsx` held one part per module in one `toFnMap` block, so every one of those tasks would have rewritten the same lines.

- **`pages/cycles/buildParts.jsx`** holds Build's parts. For each module it lists `[connector, render]` entries in the canvases' order. A part not built yet is `null` on its own line, with the task, decision and component that fill it. Each task replaces its own line and no other.
- **The order** is the canvases':

  | Module | Parts, top to bottom | Board |
  |---|---|---|
  | Operating systems | Tools history (with GitHub's Code system), Vercel's Hosting | VC1 |
  | Solution design | From GitHub, Vercel's Runs on | VC4a |
  | Prototype / MVP | From GitHub, Vercel's Live strip, From Lovable | VC2, LV7 |
  | Product roadmap | **Vercel's Deploys strip, then** GitHub's Releases | VC3: "The Deploys strip sits above GitHub's Releases strip" |
  | Founding team | From GitHub | — |
  | Company creation | From GitHub, Vercel's Where production runs | VC4b |

- **One part failing never blanks the module.** Each part renders in `PartBoundary`. One that throws reads "This part could not be read. The rest of this page is current." with Retry; the parts beside it stay drawn (VC5: "A failed read blanks nothing else on the page").
- **Anchors:** each new part takes `#from-vercel` or `#from-lovable`, as GitHub's take `#from-github`.
- **`CycleRoute.jsx`** takes `build.parts` from `buildPartsMap()` and imports none of the part components itself. Five tests that pinned the old lines now read `buildParts.jsx`.
- **Validate's experiment record** (LV1–LV6) is drawn by `HypothesesSection` and the record page, not by `build.parts`. #2947 and #2948 own it.
