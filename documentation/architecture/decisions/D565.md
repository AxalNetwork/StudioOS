## D565 — Advisor Program: the design for its stores, approval flow and money handling

**The owner brought the Advisor Program into scope on #975 ("B", 2026-10-05).
This is the design #975 asked for first. It adds no route, migration or
screen.** Slot S08, issue #1169, 2026-10-05.

**What the program is.** The canvas,
`design/canvases/backlog/Advisor Studio.dc.html` (moved here from
`out-of-scope/`), says it in its own words. "This is not an open advisor
network. You are applying to advise founders inside a specific 28-day cohort.
Every application is reviewed by the fund team; matching is admin-governed."
The lifecycle it draws is:

1. apply;
2. review by the fund team;
3. assessment and a signed agreement;
4. admin-governed cohort matching;
5. engagements, with "advisory economics" (equity grants on signature).

The draft terms (`templates/legal/advisor_program_terms_v1.md`) add paid
sessions under a platform take rate. This design covers both halves. Where they
need an owner call, it asks (section 6).

## 1. What already exists, and is reused rather than rebuilt

- **Advisor identity and profile.** `advisors`, one row per user (`user_id
  UNIQUE`). `POST /api/advisors/me` creates or updates it for any signed-in
  user (`routes/advisors.ts`).
- **Being an advisor.** The `advisor` role is set by an admin through the
  role change in `routes/admin.ts` (D249), usually out of the Exploring lane.
  Nothing records an application or a decision beyond that role change. This
  is the gap the program fills.
- **Sessions and pricing.**
  - `advisor_session_types` (migration 240): `price_cents`, where NULL is
    unpriced and not free, plus `is_free_intro` and `once_per_client`.
  - `advisor_office_hour_slots.payment_state`: `not_applicable`,
    `held_unpaid`, `authorized`, `charged` or `refunded`.
  - `advisor_bookings.amount_cents`, with `platform_cut_cents` and
    `take_rate_bps` stamped per line (migration 241).
- **The take rate.**
  - `platform_settings.advisor_take_rate_bps` is seeded at 1500 (15%) by
    migration 241.
  - It is read by `services/advisorMoney.ts::takeRate()`, which falls back to
    the default and says so. It is clamped to at most 5000 bps.
  - A Super Admin sets it, audited, through `PUT
    /api/admin/platform/take-rate` (`routes/admin_platform.ts`). D75.
- **Charging.** `services/advisorConnect.ts::chargeSession`, a Stripe Connect
  destination charge with `application_fee_amount`. It is the same shape the
  wellbeing directory runs. It is **off**: `settlementMode()` answers `none`
  unless `ADVISOR_CHARGING_ENABLED` is `1` and a Stripe key is present, and no
  environment sets the flag.
- **Payout accounts and payouts.** `advisor_payout_accounts` (one per advisor;
  `pending`, `verified` or `blocked`) and `advisor_payouts` (`scheduled`,
  `paid`, `failed` or `reversed`, with `provider_payout_id`), both from
  migration 241.
- **The generic `payouts` table is not the program's.** It holds user
  withdrawal requests with a free-text `payout_method`. An advisory payout is
  money settling from a client's card to an advisor's connected account, and
  migration 241 built `advisor_payouts` for exactly that.
- **E-sign.** `esign_envelopes` and `esign_recipients`. Completion runs
  hooks in `routes/esign.ts`: the three-way NDA, partner-deal activation and
  the obligation satisfier. The program adds one more hook of that kind.
- **Cohort access.** `advisor_cohort_assignments`: an admin assigns an advisor
  to a `cohort_cycles` row. `services/approvalSources.ts` lists "Advisor cohort
  access" in `NOT_LANED`, because nobody can request it. That stays true: the
  program's application is a new lane (section 2.4), and assignment stays an
  admin act.
- **Client access.** `advisor_client_grants`, opened by the founder, plus
  `advisor_client_access_log`. These are unchanged.
- **Equity documents.** `venture_share_agreement_fast_v1.md` (the FAST-style
  VSA) and `cap_table_vesting` (a founder's own cap table). Terms §4 says
  equity-for-advice is "between the Advisor and the Client", and that "the
  Company is not a party".

## 2. The stores

Each table below is new. Every write row names its actor in the row itself
(`actor_user_id` and `actor_kind`). Writes do **not** go through
`logActivity`: D553 found that it never sets `activity_logs.action`, which is
NOT NULL, so it records nothing on a database built from the migrations.

### 2.1 `advisor_program_applications`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | INTEGER PK | |
| `uid` | TEXT UNIQUE | Used in URLs, never the id. |
| `user_id` | INTEGER NOT NULL → `users.id` | **Personal data** (the applicant). |
| `cohort_cycle_id` | INTEGER → `cohort_cycles.id`, nullable | The cohort applied for. NULL means "the next one". |
| `primary_role` | TEXT NOT NULL | A closed set, from the canvas's role picker. |
| `expertise_json` | TEXT NOT NULL DEFAULT `'[]'` | The functional expertise scored against founders' Profiling gaps. |
| `value_add` | TEXT NOT NULL | The "value-add statement", up to 2,000 characters. **Personal data** (free text). |
| `hours_band` | TEXT NOT NULL | CHECK in `2_3`, `4_6` or `8_plus` hours a month. |
| `compensation_pref` | TEXT NOT NULL | CHECK in `equity_fast`, `stipend_equity` or `pro_bono`: the canvas's three. A preference, not a term (section 3). |
| `spinout_experience` | INTEGER NOT NULL DEFAULT 0 | University spin-out, IP licensing or tech-transfer experience. |
| `status` | TEXT NOT NULL DEFAULT `'submitted'` | CHECK in `submitted`, `under_review`, `approved`, `refused` or `withdrawn`. Moved only by the routes in section 2.5. |
| `submitted_at`, `updated_at` | TEXT NOT NULL | |

- Keys: a partial unique index on `(user_id)` WHERE `status IN ('submitted',
  'under_review')`. That gives one open application per person; a refused
  applicant can apply again for a later cohort.
- Index: `(status, submitted_at)` for the lane.

| --- | --- | --- |

| `application_id` | INTEGER NOT NULL → applications | |

- **Append-only.** The application's `status` is set in the same batch as the

### 2.4 The approvals lane

- `advisor_program_applications` becomes the twelfth lane in
  `services/approvalSources.ts`. Pending means `status IN ('submitted',
  'under_review')`, and the age is measured from `submitted_at`. The console
  is the admin decisioning page.
- This **changes `branch_approvals_s16_d215` deliberately**, as #975 required:
  - `APPROVAL_SOURCES.length` goes from 11 to 12;
  - the empty-database run gains the table;
  - the seeded run gains one application.
- D555's HQ glance and `HeldApprovals.jsx` pick the lane up through
  `laneCounts` and `LANE_CONSOLES`.
- "Advisor cohort access" stays in `NOT_LANED`. It is a different act.

### 2.5 Money stores

- **No new store for pricing.** A session's price is
  `advisor_session_types.price_cents`, and the program's take rate is the
  platform's `advisor_take_rate_bps`. Each booking stamps the rate it was
  charged at (`take_rate_bps`) and the cut (`platform_cut_cents`), so a later
  rate change never moves a past quarter.
- **The cancel window is a setting:** `platform_settings` key
  `advisor_cancel_window_hours`. It fills the terms'
  `{{advisor_program.cancel_window}}`, so the terms and the refund rule cannot
  disagree. That is the same one-source rule D75 set for the take rate.
- **`advisor_session_refunds` (new).** Nothing refunds an advisory session
  today; `payment_state = 'refunded'` has no writer. Its columns:

  | Column | Type | Notes |
  | --- | --- | --- |
  | `id` | INTEGER PK | |
  | `uid` | TEXT UNIQUE | |
  | `booking_id` | INTEGER NOT NULL UNIQUE → `advisor_bookings.id` | One refund per booking. A partial refund is not offered. |
  | `amount_cents` | INTEGER NOT NULL | |
  | `reason` | TEXT NOT NULL | CHECK in `advisor_cancelled`, `client_cancelled_in_window`, `no_show_policy` or `admin`. |
  | `state` | TEXT NOT NULL | CHECK in `requested`, `refunded` or `failed`. |
  | `provider_refund_id` | TEXT | |
  | `failure_reason` | TEXT | |
  | `actor_user_id` | INTEGER | |
  | `actor_kind` | TEXT NOT NULL | |
  | `created_at`, `updated_at` | TEXT NOT NULL | |

- **Payouts.** `advisor_payouts` (migration 241), not `payouts`.

### 2.6 Equity grants, only if they are in the first build (question C)

`advisor_equity_grants` would hold:
- `membership_id` and `project_id`;
- `instrument` (CHECK `fast_vsa`);
- `equity_bps` or `shares`, never both;
- `vesting_months` and `cliff_months` (FAST defaults: 24 and 3);
- `start_date`;
- `envelope_id`, the signed VSA;
- `state`: `proposed`, `signed` or `cancelled`;
- the actor columns.

"On signature it propagates automatically" (the canvas) would be one more
completion hook, writing `signed`. It would **not** write the founder's
`cap_table_vesting`: that is the founder's own record, and terms §4 keeps the
company out of the agreement. Personal data: the grant ties a named person to
an equity stake in a named company.

## 3. The flow

| From | To | Who | Condition |
| --- | --- | --- | --- |
| — | application `submitted` | the applicant (any signed-in, non-staff account) | No open application of theirs. Not already an `active` member. |
| `submitted` | `under_review` | an admin of the deployment | Opening the application records `opened`. This is optional; deciding from `submitted` is allowed. |
| `submitted`, `under_review` | `approved` | an admin | Creates the membership in `awaiting_terms` and sends the terms through e-sign (`esign_envelopes`, `document_type = 'advisor_program_terms'`) to the applicant's email. |
| `submitted`, `under_review` | `refused` | an admin | A reason is required. It is shown to the applicant. |
| `submitted`, `under_review` | `withdrawn` | the applicant | |
| membership `awaiting_terms` | `active` | **system** | The e-sign completion hook for that envelope. The event's `source_ref` is `esign:<uuid>`. Sets the role to `advisor` if it is not already, and `advisors.is_active = 1`. |
| `awaiting_terms` | `ended` | an admin, or the advisor | Terms never signed. A reason is required from an admin. |
| `active` | `suspended` | an admin | A reason is required. Paid session types are hidden, as in `PAYOUT_GATE.blocked`. Booked sessions stand. |
| `suspended` | `active` | an admin | A reason is required. |
| `active`, `suspended` | `ended` | an admin (reason required), or the advisor | Exit (section 5). Booked sessions must be completed or refunded (terms §8). |

- **Matching stays admin-governed.** An admin can assign
  (`advisor_cohort_assignments`) only an `active` member. That is the
  canvas's "approval unlocks matching only when … the signed agreement" is in
  place.
- **The canvas's assessment gate** (skills and values archetype) has no
  advisor variant in `routes/assessment.ts`. Question D asks whether it gates
  matching in the first build.
- **The preference is not a term.** `compensation_pref` records what the
  applicant asked for. Whatever is agreed with a founder is a document (the
  VSA) or, if question C is in, a grant row.

## 4. The money

- **Where the take rate is held and who sets it.**
  `platform_settings.advisor_take_rate_bps`, set only by a Super Admin through
  `PUT /api/admin/platform/take-rate`, which already records the actor and the
  old and new values. There is no per-advisor or per-programme rate. A second
  source is exactly what D75 removed.
- **How sessions are charged.** Through the existing
  `advisorConnect.ts::chargeSession`: a destination charge to the advisor's
  connected account, with `application_fee_amount` = `cutCents(gross,
  take_rate_bps)`. It is charged at booking (terms §3.2), and only when
  `advisor_payout_accounts.state = 'verified'`; otherwise the slot is
  `held_unpaid`, as today. **Charging stays off** until question B is
  answered.
- **Payouts.** Stripe Connect pays the connected account on its own
  schedule. `advisor_payouts` records each payout the provider reports, and
  `provider_payout_id` reconciles it. The platform never initiates a payout
  by hand, and never writes `paid` without a provider id.
- **Refunds in the cancel window.**
  - An advisor cancels: always a full refund (terms §3.4).
  - A client cancels with at least `advisor_cancel_window_hours` notice: a
    full refund.
  - A client cancels inside the window, or does not show: the session type's
    stated policy. The first build offers no partial refund, so it is a full
    charge or a full refund.
  - The refund is a Stripe refund with `reverse_transfer` and
    `refund_application_fee`, so the advisor's share and the platform fee
    both return.
  - The `advisor_session_refunds` row is written as `requested` before the
    provider call and moved on its answer, so a failed call is a visible row
    and not a silent gap. The slot's `payment_state` goes to `refunded`.
- **The actor on every write.**
  - Applications, decisions, memberships and events carry `actor_user_id` and
    `actor_kind`.
  - The take rate carries `updated_by`.
  - Refunds carry the actor columns.
  - A charge records the booking's founder as the payer and `system` as the
    actor for the provider call.
  - Nothing money-related goes through `logActivity` (section 2).

## 5. Personal data

- **Who sees what.**
  - The **applicant** sees their own applications, every decision on them,
    and the reason for a refusal. They see no admin's name, only "the fund
    team".
  - **Admins of the deployment** see the lane and every application on it,
    including `value_add`.
  - On a subsidiary, its own D1 holds its own applications. The tenancy wall
    is physical (D106), so HQ sees none of them, and D555's HQ figures count
    HQ's own lane only.
  - **Founders** see only an `active` member's public `advisors` profile, as
    today. They never see an application, a value statement, a decision or a
    membership state.
  - **Other advisors** see nothing of another's application or membership.
- **Retention.** The privacy policy (`privacy_v1.md` §4) keeps account data
  "for as long as your account is active". Within that:
  - a refused or withdrawn application is kept as the record of the decision;
  - money rows (bookings with their cut, refunds, payouts) are kept for the
    tax period the terms imply (§7, Form 1099). Question E asks how long.
- **Deletion on exit.**
  - **Ending membership** is not deleting the account. On `ended`:
    - `advisors.is_active = 0`;
    - every `advisor_session_types` row goes inactive;
    - open `advisor_client_grants` are revoked;
    - active `advisor_cohort_assignments` are unassigned, with
      `unassigned_at` and a note.
  - The application, decisions, events and money rows stay, as the record of
    what happened.
  - **Account deletion** is today a request with no automation (`POST
    /api/settings/account/delete-request`). When it is carried out:
    - the application's free text (`value_add`, `expertise_json`) is
      cleared, and so are the decision reasons;
    - the outcome rows, their dates and actors stay;
    - money rows stay for the tax period, then the person's link is removed.

## 6. Questions for the owner

Reply on #1169 with one letter per question. S08's pick is first.

**A. Who decides an application?**
- **A1. Any admin of the deployment, with a reason on refusal (S08's
  pick).** It matches every other lane on the board, and on a subsidiary the
  subsidiary's own admins decide.
- **A2. A Super Admin only.** HQ-only, and a subsidiary could not run a
  program.

**B. Paid sessions in the first build?**
- **B1. No (S08's pick).** The program ships with applications, review,
  signed terms, membership and matching. `ADVISOR_CHARGING_ENABLED` stays
  unset, and paid sessions stay as today: priced, `held_unpaid` when charged,
  nothing moved.
- **B2. Yes.** Switch charging on with the program. That needs the refund
  path (B7 below), a production Stripe Connect review, and counsel's sign-off
  on terms §3.

**C. Advisor equity grants in the first build?**
- **C1. Out (S08's pick).** Equity stays a signed VSA between advisor and
  founder, through the existing template and e-sign. Terms §4 keeps the
  company out of it.
- **C2. In.** Build `advisor_equity_grants` (section 2.6) with its signature
  hook.

**D. Does the assessment gate matching in the first build?**
- **D1. No (S08's pick).** Approval plus signed terms unlock matching. The
  skills and values assessment is a later task, because `assessment.ts` has
  no advisor variant.
- **D2. Yes.** Build the advisor assessment first. Matching waits on it.

**E. How long are money rows kept after an account is deleted?**
- **E1. Seven years (S08's pick).** It covers the US information-return
  period the terms' §7 implies. Counsel should confirm.
- **E2. Counsel sets it before B2 ships.**

**F. Which terms are sent on approval?**
The draft is marked DORMANT in `LEGAL_REVIEW.md`, because §3 describes
charging the platform does not do.
- **F1. A v2 for counsel without the paid-session sections (S08's pick).**
  §3.2 to §3.3 would come back when charging ships. Approval sends v2.
- **F2. Send v1 as it stands** once counsel clears it, with charging still
  off.
- **F3. Hold the program's terms step until charging ships.** Memberships
  then wait in `awaiting_terms`.
