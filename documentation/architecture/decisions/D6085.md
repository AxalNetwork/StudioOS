## D6085 — Use of funds names the cap-table scenario that pays for it (#6085)

- **Status:** built 2026-11-15 on the Raise v2 Cap Table and Use of Funds canvas (D6088, boards RA-32 to RA-34; `design/incoming/Raise v2 Cap Table and Use of Funds · Boards.dc.html`). Builds on D1176 (the plan's stores and reads), D5069 (revisions) and UF13d (the "Raise differs" line, not redrawn).
- **Before:** each plan scenario said "No cap-table scenario linked" (`scenariosForecastModel.js`), the plan read the latest cap-table model with `link_state: 'not_recorded'` (`services/useOfFunds/read.ts`), and migration 606 stored no link.

### The link

- **Stored on the plan scenario.** Migration `202611152337_6085_uof_captable_link.sql` adds `uof_scenarios.cap_table_scenario_uid` (nullable), with `cap_table_linked_at` and `cap_table_linked_by`, and an index on `(project_id, cap_table_scenario_uid)`. It is a plain uid, not a foreign key, so a deleted cap-table scenario leaves a broken link that the plan can name, rather than a link that vanishes. Existing rows read Not linked.
- **Same project only.** A link is written only to a `cap_table_scenarios` row of the plan's own project: the route checks first, and the `UPDATE` repeats the check inside the batch, so a scenario deleted or moved between the two links nothing (404 `cap_table_scenario_not_found`). It is read back the same way. A linked scenario that is no longer in the project reads `deleted` ("Link broken"), never an error, and never another venture's figures.
- **One write, three outcomes.** `PUT /api/cycles/raise/use-of-funds/scenarios/:id/cap-table` takes `{ cap_table_scenario_uid: <uid> | null, expected_revision }` and nothing else. It goes through the plan router's existing gate (the venture founder or an admin; a support session cannot write). It bumps the scenario's revision (D5069), so a stale read gets 409 `changed_since_open`. It writes one audit row into the plan's history: `uof_captable_linked`, `uof_captable_changed` or `uof_captable_unlinked`, written only when the link was. Linking changes neither the plan's figures nor the cap-table scenario's.
- **The picker's list.** `GET /api/cycles/raise/use-of-funds/cap-table-scenarios[?scenario_id=]` lists the venture's cap-table scenarios: the model first, then the newest, at most 50. Each comes with its first round's investment, its date and whether it differs from the plan scenario's raise. `matching_uid` names the first one whose investment equals the plan's raise. The list sits behind the plan router's gate rather than the cap-table router's, whose admin refusal (`scoped_cap_table_required`) would stop an admin from reading the list for a plan they can already edit. It reads the same `cap_table_scenarios` table the plan already reads for its ties, never another project's rows.

### What the plan reads

- **Each scenario's read carries `cap_table_link`.** This applies to `GET /scenarios`, `/scenarios/:id`, `/compare` and the plan's base. The states are:
  - `not_linked`: no query is made.
  - `linked`: the scenario's name and date, its first round, `raise: { plan_cents, scenario_cents, differs }` and `founders`.
  - `deleted`.
  - `unreadable`: the read failed or the stored JSON did not parse; the plan around it still reads.
- **The plan's ties read the linked scenario.** `ties.cap_table` reads the linked scenario when there is one, with `link_state: 'linked'`. Without a link, it reads the latest model, shown unlinked (`not_recorded`). With a broken link, it also reads the latest model, and says so (`deleted`). The round's candidates and their disagreement read the same scenario, so "Raise differs" (UF13d) compares the plan with the scenario it names.
- **Founders after the round is Modelled.** For each founder in the linked scenario's `founder_dilution`, it gives the Founding share and the share after the first modelled round, with the change in points, and the founders together. A scenario with no founders reads Not recorded ("Not 0%"). These are the scenario's founders, not recorded holders, so no Recorded figure sits in this card.
- **The first round is the one compared.** When a scenario models several rounds, the first is the round this plan raises. The raise and Founders after the round both read it.
- **The raise is compared, never fixed.** A mismatch names both amounts, each tagged ("Raise differs: [scenario] invests X; the plan raises Y. Linking changes neither."). Choose the round size (UF13d) stays the only way to change the plan's raise.

### The pages

- **Home (RA-32 A, RA-33).** The header row reads "Paid for by". It shows the linked scenario (◇ Modelled) with Change. Otherwise it gives its state:
  - Not linked, with the latest model shown unlinked and Link a scenario.
  - None, with Model a round in Cap table.
  - Link broken, with Pick another.
  - Unavailable, with Try again.

  Founders after the round sits under where the money goes once a scenario is linked: a table with a caption, or stacked cards on a phone (RA-34 D). Open in Cap table goes to `/raise/cap-table/scenarios/:uid`.
- **The picker (RA-32 B, RA-34 E).** The shared `Sheet` is a bottom sheet on a phone. It lists each scenario with its investment, date and Raise differs. The one whose investment matches the plan's raise is suggested ("Eadwyn suggests …"); that suggestion is an exact match on the stored figures, not a model call, and it sets nothing until Pick it and Link scenario. It also has Unlink, Cancel, the refusal's sentence, Review latest after a stale write, a failed read (never an empty list), and an empty venture.
- **Scenarios (UF9) and Compare (UF10).** Each card's Cap table line names its own link, with Link, Change or Pick another. Compare's "Founders after the round" row gives the founders together after the round with the change, tagged Modelled, or Not recorded with why. "Committed so far" still waits on a read of the round's commitments (D1177 §9).
- **The cap table's scenario page.** `GET /api/captable/scenarios/:uid` adds `used_by_plans`, the same venture's plan scenarios that name it. The page then says "Use of funds: Base plan (base) is paid for by this scenario." with Open Use of funds. When nothing names it, or the read fails (`used_by_plans: null`), the page says nothing.

### Not in this change

- **The owner's questions.** D6088's four questions (Q1 to Q4) are about grants, the pool, Archive and check size, not this link; nothing here waits on them.
- **No new page and no new route in the SPA.** The `/raise/cap-table/proposal/:proposal` page, the grant sheet and the investor facts (#6086, #6087) are their own tasks.
- **Data and admin.** No backfill: every existing plan reads Not linked until someone links it. An admin linking on a founder's plan is recorded with "Studio admin:" in the history, as every other plan write is.
