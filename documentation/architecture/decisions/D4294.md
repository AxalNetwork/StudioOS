## D4294 — Influencer payout readiness: identity, a tax form, the current terms, $50 and once a month (#4294)

- **Status:** D4289 P5, by S17, 2026-11-03. Part of #4289.
- **The owner's answers** (#4289): KYC plus a tax form (W-9 or W-8BEN); a $50 minimum; monthly; payouts stay manual. An influencer requests, and the Super Admin pays through the D572 queue.
- **Migration:** `202611031530_influencer_payout_readiness.sql`.

### 1. Who is an influencer

An admitted influencer has a `referral_partners` row in the `influencers` segment (D-b). P1 (#4290) writes that row on admission and rebuilds the segment CHECK to allow it. Until P1 is on `main` nobody is in the segment, so nobody is gated and every payout request behaves exactly as before. This part reads no P1 table: the guards fail a query on a table no migration creates.

### 2. The gate

`POST /api/network/payout/request` refuses an influencer's request with a named reason, never a bare 403. It checks in this order, and the readiness read lists the same items:

| Order | Item | Refusal |
|---|---|---|
| 1 | Identity: `users.kyc_status` is `approved` | 403 `kyc_required` |
| 2 | Tax form: the newest form is `accepted` | 403 `tax_form_required` |
| 3 | Terms: the current `INFLUENCER_TERMS_VERSION` is accepted | 403 `terms_acceptance_required` |
| 4 | Minimum: at least $50 payable in the terms' currency | 400 `below_payout_minimum` |
| 5 | Monthly: no request yet this calendar month (UTC) | 403 `payout_already_requested_this_month`, with the date the next one opens |
| 6 | The request: in the terms' currency, and at least the minimum | 400 `payout_currency_not_terms`, `below_payout_minimum` |

- **Payable** is the member's `accrued` commissions in the terms' currency. A commission P3 holds as pending is not accrued, so it never counts.
- **The terms' currency** comes from the newest signed (or active) `referral_partner_terms` record, and is USD when there is none.
- **A failed payout** returned its commissions, so it does not use up the month. Any other request does.
- **The payout method** is listed but never blocks: the request names its destination (D572 part 3b), and the readiness item shows the last one used.

### 3. The tax form

- **Upload:** `POST /api/influencer/me/tax-form` takes a W-9 or W-8BEN as a PDF, JPEG or PNG of at most 5 MB.
- **Storage:** the private `FILES` bucket, under `taxforms/<user_id>/`. Each upload is a new `influencer_tax_forms` row; the newest row is the status, and no row reads `missing`. A rejected form stays as the record of what was reviewed.
- **Review:** only the Super Admin accepts or rejects (`POST /api/admin/influencers/:uid/tax-form/decision`). A rejection needs a reason, which the influencer reads. Any other admin gets 403 `super_admin_only`. Each decision goes through `logAdminAction`.
- **Reading the file:** only the Super Admin streams it (`GET /api/admin/influencers/:uid/tax-form/file`), with `no-store` and as an attachment, and each read is logged. No reply carries the file's key or a URL to it. The reader (`r2.getTaxForm`) refuses any key outside `taxforms/`.
- **After acceptance:** a new upload is refused with 409 `tax_form_already_accepted`. A change of details goes through HQ.

### 4. Terms acceptance

`influencer_terms_acceptances` records which version each influencer accepted. `POST /api/influencer/me/terms/accept` accepts only the current version. A new version, set by changing `INFLUENCER_TERMS_VERSION`, gates the next payout until it is accepted.

P1's application stores the version accepted when applying (`consent_version`). When P1 lands, admission should also write that acceptance here, so that a newly admitted influencer is not asked twice.

### 5. Owner action

Legal review of the Influencer terms text and of the tax form handling before launch.
