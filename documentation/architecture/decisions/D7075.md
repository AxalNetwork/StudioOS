## D7075 — Recruits: a plan that names a role with no agent asks the team to add it (#7075)

Part of #7072. Owner decision D on #7072 is in force at its default, **D1**: a
manager of the team approves a recruit and becomes its sponsor.

### Problem

`acceptPlan` (`services/agents/planner.ts`) assigns an item whose role has no
agent on the team to nobody. The plan then stalls until a person notices and
adds the agent by hand, and the tasks are never handed to it.

### Decision

1. **A request, filed with the plan.** When a plan is accepted, each role it
   names that has no agent on the team (none at all: a paused agent of the role
   still counts, since the add path would refuse a second one) becomes a row of
   `agent_recruit_requests`. The row holds the scope, the role, the plan, the
   agent that drafted it (`ai_rail_proposals.agent_id`, null when Eadwyn
   planned) and who accepted it. `agent_recruit_tasks` holds the tasks waiting
   on it. The statements join the accept's own batch and are gated on its
   private claim marker, so a losing or failed accept files nothing.
2. **One open request per scope and role.** A partial unique index enforces it,
   and a later plan that needs the same role adds its tasks to the open request
   (`INSERT OR IGNORE`, then the link by scope and role).
3. **A person decides.** `/api/team-recruits` (`routes/agent_recruits.ts`):
   - `GET /:scope/:id` lists the requests (read);
   - `POST /:uid/approve` and `POST /:uid/decline` decide one (manage: the gate
     that adding an agent uses).

   A person who cannot read the team gets 404, so the request is not revealed.
   A member who can read it but not manage it gets 403.
4. **Approval goes through the add path.** The `POST /:scope/:id/agents` handler
   moved, unchanged, into `addAgentAs` in `team_agents.ts`. The route and the
   approval both call it, so an approval makes every check an add makes, in the
   same order:
   - the manager gate;
   - the paid plan;
   - HQ's persona roster and maximum cap;
   - the model offer;
   - the allowlists;
   - one agent per role and persona.

   The approver is the sponsor. An approval sends the model, the cap and
   optionally a persona and a name. It never sends tool grants or skills:
   the sponsor adds those on the agent's page. The recruit's rule book is
   whatever is in force for the role on the team, which is the role's default
   unless the team saved a version.
5. **The tasks follow.** Once the agent exists, the request closes once
   (`WHERE status = 'open'`). Each waiting task that is still open and
   unassigned, and whose module the new agent's rule book lists (`agentFits`),
   is assigned to it, with an `assigned` event on its timeline. Any other task
   stays as it is.

   With `AGENT_AUTONOMY=self_start` and the engine on, the scope's object is
   asked to admit the first assigned task that has a rail option. Plan tasks
   carry no option today, so in practice a person presses Start, as for any
   plan task. A refused admission is reported and changes nothing.
6. **Decline.** The tasks stay unassigned. Each gets an `updated` event with
   `recruit_declined` and the reason (at most 500 characters). A later plan
   that needs the role files a new request.
7. **No agent adds an agent.** A request is data. Nothing is created, granted
   or charged until a person approves it.

### Edges

- If an approval and a decline race after the add path has created the agent,
  the request answers 409 `recruit_decided` and the agent stays. A person
  approved its addition, and it can be removed from the team page.
- If someone adds the role by hand while a request is open, approving answers
  409 `role_taken`, and the request stays open for a manager to decline.

### Out of scope

The screen (it joins the canvas of #7078), custom roles a plan invents, and
recruiting across scopes.

### Migration

`202611170937_7075_agent_recruits.sql`: two new tables, additive. Nothing
reads them until a plan is accepted with a missing role.
