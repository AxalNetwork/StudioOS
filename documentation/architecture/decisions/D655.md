## D655 — The GitHub connector, and "now fed by" counts for every connector

**Issue:** #1467, part of #1461 (D649). **Slot:** S03 (moved from S18 at the owner's request). **Migration:** 445 (provisional; see below).
**Canvas:** `design/incoming/Cycle Action.dc.html`, `action=connect`, views `sync` and `success`.

### What was true

`routes/github.ts` is the ticket mirror's incoming webhook. There was no member GitHub connection, and no connector recorded what it delivered to which module.

### A GitHub App, because an OAuth App cannot be read-only

An OAuth App's only scope for private repositories, `repo`, also grants write. A GitHub App's permissions are fine-grained, so the connector is a GitHub App's **user authorization**, and the App is registered with four permissions, all `read`:
- `issues:read`;
- `pull_requests:read`;
- `contents:read` (releases);
- `metadata:read`.

Those four are the registry's `oauth_scopes`. GitHub takes no `scope` in an App's authorize URL, because the permissions are fixed on the App. So the grant is **read back, never assumed**: `grantedPermissions` lists each installation's `permissions` as `name:level`. That list is checked against the registry with the same `hasScopeOverreach` check D650 uses, twice:
- **at the callback**, where an overreach is refused and the grant revoked (also on disconnect; `DELETE /applications/:client_id/grant`);
- **whenever repositories are chosen** (`PUT /:uid/repositories`), because an installation's permissions can be widened in GitHub after the connection is made. A grant with any permission outside the four requested reads, including another read, is refused with 403 `write_scope_refused`. Nothing is saved, and the overreach is logged.

The client is `GITHUB_APP_CLIENT_ID` and `GITHUB_APP_CLIENT_SECRET`, a managed provider key (env first, then Admin → Integration Keys).

### Choosing repositories

- `GET /:uid/repositories` lists the repositories the installations reach, and what is chosen.
- `PUT /:uid/repositories {repositories, project_id}` accepts only repositories in that list, at most 50, and a project in a company the connection is enabled for (`projectEnabled`).
- The route also requires the active company to be enabled for the connection (`companyEnabled`). This is the same check D650's sync and push use. #1464's follow-up moves it into a shared helper; these routes should call that helper once it lands.
- A `PATCH /:uid/config` cannot set `repositories` around the grant check.

### The first sync, and where the data lands

`POST /:uid/sync` is D650's route. `github` now counts as a project-writing provider (`writesProjectData`), so the route's company check applies. Inside the sync, the chosen project is checked again with `projectEnabled`, and GitHub is not read if that check fails.
- **Issues** become Product roadmap items (`roadmap_okrs`):
  - a new one goes to `next`, or to `done` if it is closed;
  - a re-sync updates the title and closes the item, and leaves the founder's lane alone.
  - The issues endpoint also lists pull requests, and those are skipped.
- **Pull requests** become Prototype / MVP must-haves (`mvp_features`):
  - merged → `Done`;
  - closed unmerged → `Blocked`;
  - draft → `In Progress`;
  - open → `Review`.
- **Releases** have no store in the founder workspace. Each is recorded as arrived, with no local row, and the fed count says so. No store is invented for them.

`GET /:uid/sync-status` returns `{state, pct, reading}` while the sync runs, for example `38` and "Pull requests in acme/app". Before any sync it returns `idle` with `pct: null`. The progress lives in KV for an hour. It is a convenience, and the sync does not depend on it.

### The ledger, migration 445

`connector_fed_items` has one row per external item delivered: its module, its kind, and the local row it became (`local_table`, `local_id`, NULL when there is no store). It is unique on `(integration_id, external_id)`. That makes it two things:
- **the link**, so a re-sync updates instead of duplicating (`roadmap_okrs` and `mvp_features` have no external-id column);
- **the ledger**, which "now fed by" counts.

The number is **provisional**. I asked S1 for one on #1467 because the issue said no migration was expected; 436 to 444 were taken on main or in open PRs.

### "Now fed by", for every connector

`GET /:uid/fed` returns each module the connector feeds, from the registry's `feeds`:
- `count`: items delivered;
- `linked`: how many landed on a row;
- `unlanded`: how many arrived with no store;
- `reason`.

A connector that writes the ledger (GitHub, today) gets measured counts, including a measured 0. **Every other connector gets `count: null` and "Not recorded", never 0.** Nobody measured what Stripe or HubSpot delivered per module, and 0 would claim that nothing arrived. When a provider starts writing the ledger, it joins `FED_LEDGER_PROVIDERS`.

### Follow-up (#1883): the user token is renewed, and disconnecting revokes the sign-in

The connector stores `expires_at` and `refresh_token_expires_at` from the durations
GitHub returns, without assuming either duration. A legacy blob derives expiry
from its numeric `issued_at` and `expires_in`. A token with no expiry is returned
as before. Expiring tokens renew 60 seconds early, at most once per call.

Renewal uses `github:refresh:<uid>` in RATE_LIMITS, a random holder, a read-back
and the minimum 60-second TTL. A loser polls D1 six times at 500 ms and never
renews; it returns the new token, the final refusal, or `github_refresh_busy`.
KV remains an advisory hint. Before spending the refresh token, every caller
must additionally claim an exclusive lease in the encrypted credential blob by
D1 compare-and-swap. Losers poll and never spend the token, even when KV fails.
The D1 lease lasts 60 seconds; the GitHub refresh request has a 15-second deadline.
A stale lease can be reclaimed after its holder dies. Failure restores the exact
original ciphertext only if the caller's lease still stands. Success/refusal
remove the lease, and reconnects remain protected by CAS.

This strengthens the issue's KV-only plan after the different-vendor review
found that an early duplicate refusal could otherwise discard a winner's new
pair before it was stored. The new regression holds back the winner's response
while KV is unavailable and proves that a second token request never happens.
No migration or new binding is needed.

Only `bad_refresh_token`, a missing refresh token, or its local expiry is final.
The guarded write removes the refresh token, sets `reauth_required`, marks the
row `error` and records `github_sign_in_expired: Sign in to GitHub again.`.
Further calls do not renew or rewrite this state until reconnect replaces it.
Other endpoint errors use an allowlisted code in `github_refresh_failed`; HTTP,
JSON and network failures give `github_refresh_unavailable`. Neither changes the
credentials. No token, secret, Basic header or provider description is logged or
included in those messages. An API 401 is not retried.

Disconnect renews first if needed and revokes the grant with Basic client auth.
Revocation is best effort: a failure still allows the route to remove the local
connection. Revocation ends the sign-in, but the App stays installed on the
member's repositories until they uninstall it on GitHub. No route, binding or
schema changes; `accessToken(env, row)` keeps its signature.

Checked against [GitHub's App refresh documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)
and the [token endpoint's documented bad_refresh_token refusal](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#refreshing-an-access-token-with-a-refresh-token).
No live account was used. #1885 remains responsible for setup/runbook wording;
the owner enables expiry after this PR merges. The existing non-expiring grants
are not made expiring by changing the App setting (GitHub's refresh docs).

### Verified

`cloudflare-worker/test/github_connector_d655.test.ts` has 7 tests, on SQLite with migrations 001, 153, 435 and 445 and a fake GitHub. They cover:
- the requested list is read-only, and a write is overreach against that same list;
- a write grant refuses the repository choice, saves nothing and logs it;
- the choice is limited to repositories the installation reaches, an enabled company and its project, and the owner;
- a config patch cannot bypass the choice;
- sync lands issues and pull requests once, and a re-sync updates;
- progress goes from `idle` to `done`;
- the fed counts, including the release with no store;
- sync into a project outside the enabled companies writes and reads nothing;
- fed for a non-ledger connector is Not recorded, never 0;
- the choice limits and the pull request states.

**Mutation checks.** 16 mutants on those rules were tried and all were caught.
