## D7905 part 7 — Hosted execution seams for the trusted readers (#7905, #8345)

S39 owns the three hosted readers (#8345). This part fixes the executor side they
plug into. It adds no reader and no hosted boundary job, so every hosted admission
and run still refuses. It raises no timeout, cap or lease.

- **Child and control revisions.** The coordinator dispatches the child workflow at
  `childWorkflowSha ?? executorSha`. Dispatch, transport and admission already used
  that value, but the hosted verifier compared the job, run and OIDC SHAs to
  `executorSha`, so a pinned child was refused.
  - The verifier now binds `claims.workflow_sha`, `claims.sha`, `run.head_sha`,
    `job.head_sha` and `context.childWorkflowSha` to the child revision.
  - `executorSha` stays the control revision. It is bound to the context, and
    admission alone proves it is on `main`.
  - A reader's `binding` must carry the same `childWorkflowSha` as the receipt.
- **Admission and execution ports.** Every executor caller passes phase `execute`,
  so the phase cannot separate pre-checkout admission from the live check. What
  separates them is which port the executor calls, as for `linux-x64`.
  - **`verifyAdmission`** runs before checkout, when no instance exists. It checks
    provenance, included eligibility and a `readBoundaryReadiness` document
    (`trusted-native-readiness`). That document carries a policy digest and must
    not name an instance. The live boundary is never read here.
  - **`verifyExecution`** is called by the run step before install and again before
    test. It reads the live `readBoundary` document. The executor passes the
    trusted job's own `{instanceId, policyDigest}`, and a missing value refuses
    (`hosted_boundary_instance_unbound`). A different instance or policy also
    refuses (`hosted_boundary_instance_changed`).
  - **`inspect` and `verifyIsolation`**, the accepted #8007 port, are unchanged.
- **Composition.** `hostedExecutorDependencies` takes the profile from
  `isolationFor`, and passes the trusted job to the readers factory so a reader
  can inspect that exact instance.
  - It composes an execution port only for a `JobContainer` serving that same
    profile, so a `github-8` job never stands in for `hosted`, or the reverse.
  - `hostedBoundaryJob()` returns `null`, so the port is never composed today.
- **Run step.** `runInContainer` accepts `hosted` and `github-8` only with a trusted
  `JobContainer` whose profile matches. `linux-x64` is unchanged.
- **`JobContainer`.**
  - Each container serves one profile (`linux-x64` by default). Receipts for any
    other profile are refused at create, verification and cleanup.
  - `boundaryIdentity()` now includes the policy digest.
  - **`inspectBoundary`** is read-only. It returns the live document only after
    `verifyIsolation` passes, and its denials come from that inspection: two
    read-only input mounts, the fixed environment, uid 10001, `cap-drop ALL` and
    no devices.
  - **`inspectReadiness`** is one bounded `version` call, and never names an
    instance.
  - Both report `deniesHostControl: false`, because the bridge network still
    reaches the host's metadata and platform endpoints. The verifier therefore
    refuses them.

**Still missing, and refusing until supplied:**
1. A trusted hosted container policy and a digest-pinned image acquired from the
   control checkout. A hosted runner has neither, and `--pull=never` applies.
2. A verified egress rule that blocks the host metadata and platform endpoints.
3. A native hosted canary showing that candidate code cannot read the OIDC token,
   the job token, the runner agent's credentials or host metadata.

Tests: `frontend/test/runner_hosted_ports_8345.test.mjs`. All results are synthetic
and interface-only.
