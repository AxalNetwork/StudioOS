## D944 — Spin-Out Lab overview and paged applications reads

Issue #2749, part 2 of #2374, stacked on D937's integration PR #2742 while it
is open. The canvas is `design/incoming/Spin-Out Lab Admin Page.dc.html`, SL1
rows 2–5, SL2, SL5 and SL6. This part supplies reads and their clients; drawing
those blocks belongs to #2752/#2753. No rendered route changes, no migration,
no new index, no schema bootstrap and no production data access.

### Mount, permission and client

`routes/admin_lab.ts` is mounted at `/` by `admin_cohort.ts`, which is mounted
at `/api/admin/cohort` by `index.ts`. Both new GETs call `requireAdmin` before
any reads. They do not gate reads on licence suspension. The existing cohort
read/write handlers are unchanged. `frontend/src/lib/api/adminLab.js` exports
`adminLabApi`, re-exported once by api.js's alphabetical block (D527).

### GET /api/admin/cohort/overview?cohort=YYYY-MM

The optional cohort selects the funnel; default is the most recent started
cohort, otherwise the earliest future cohort. Invalid month syntax is 400.
All stored cohorts are included, rather than silently clipping to the older
read's twelve cycles. Top-level fields: `as_of` (UTC ISO), `timezone`
(`America/New_York`), `definitions` and `blocks`:

- `cohorts`: `{available:true,items:[...]}`, with calendar metadata and the
  metrics below for each cohort. If its read fails it is
  `{available:false,reason}`; the submissions chart still answers.
- `applications_per_week`: `{available:true,items:[{start,end,partial,applied}]}`.
  Twelve Monday-based ET civil weeks, including the current partial week.
  `start`/`end` are UTC ISO instants; end is exclusive. DST weeks can be 167 or
  169 hours. Zone-less D1 times are UTC. Future submissions after `as_of` are
  excluded. Counts use application submissions once, not carried assignments
  or drafts. An empty successfully read week is a real zero.
- `funnel`: `{available:true,cohort,interview_is_optional:true,steps:{...}}`.
  Steps: `applied`, `interviewed`, `approved`, `started_week_1`,
  `passed_week_4`, `incorporated`, `certificate_issued`. Each is its own metric
  state. A valid but absent selected cohort is unavailable, not a zero funnel.
  Interviews are optional and sit beside the conversion steps in the canvas.

Waiting and Interview set are counted in the same SQL read, so concurrent pool
changes cannot create a negative waiting count by subtracting separate snapshots.

Each cohort metric is `{available:true,value:number}`, a failed source is
`{available:false,reason}`, or an unrecorded fact is `{recorded:false,reason}`.
A failed source carries no numeric value. These source queries answer
independently; failure of interviews, outcomes, week windows, milestones,
starts, certificates or weekly submissions never blanks the other figures.

| Metric | Recorded source / exact meaning |
|---|---|
| applied | Cohort pool assignments, including carried-in rows; no 200-row cap |
| approved | Pool status approved **or activated**, matching SL1's “Approved or started” legend and the funnel's admission step |
| undecided | All pending assignments, including scheduled interviews; use for the chart's undecided/waiting band |
| waiting | Pending assignments with no latest scheduled interview, matching SL2's separate Waiting and Interview set chips |
| interview_set | Pending assignments whose latest interview row is scheduled; older cancelled rows never duplicate the pool |
| interviewed | **Not recorded**: the interview store has scheduled/cancelled states and no attendance/completion event. A past appointment is not proof of attendance |
| waitlisted / declined / withdrawn | Pool status waitlisted / rejected / withdrawn |
| carried_forward / carried_in | Outward rolled_forward status / arrival with rolled_from_cycle_id. They are different counts |
| started | Distinct members from the union of activated pool assignments and recorded users.spinout_lab_started_at within the cohort window. Includes graduates, legacy admits without applications, and retained historical activations; overlap is counted once |
| in_grace | Distinct members with a stored grace outcome, not the sum of week rows. Expired grace stays grace until the scheduler decides it |
| incorporated | incorporation_completed milestone on/after the recorded start (or cohort start for a historical activation), attributed through the same start/activation candidates; **not** the application's self-declaration or global incorporated flag. If a graduate has start/activation candidates in multiple cohorts, its milestone cannot be attributed and that cohort metric is Not recorded, with the reason |
| certificates_issued | Distinct currently issued certificate holders whose frozen public_cohort is the canonical “Month Year Cohort” or YYYY-MM. Revoked and legacy/unattributed labels are excluded |

`weeks` is `{available:true,items:[{week_number,unlock_at,deadline_at,state,
passed,failed,in_grace,pending,reached}]}`, from recorded week windows and
per-week outcomes. `state` is `not_started` before unlock, otherwise `opened`.
`reached` is **Not recorded**: window unlock does not write a per-founder
reached-week ledger, and an outcome-row count is not that denominator. The
passed/failed/grace/pending counts remain usable independently. Failed outcomes
or windows make this block unavailable; no fabricated four-week rows appear.

These counts describe recorded current states, not reconstructed event history:
a rolled-forward row does not retain an earlier approval, milestones have no
cohort foreign key, and a certificate's unrecognised legacy label is not guessed
from a free-text string. The response includes these definitions for consumers.

### GET /api/admin/cohort/applications/list

Returns `{available:true,items,total,limit,offset,sort,filters,definitions}`.
One SQL statement returns one bounded application row at a time plus a total
metadata row, avoiding D1’s 2 MiB per-row limit for large pages. It filters, orders and pages the pool and counts the entire
filtered relation, so a page beyond the last row is `items:[]` with its true
nonzero total. It is not a capped browser-filtered page. A failed read returns
`{available:false,reason,items:null,total:null,limit,offset}` with HTTP 200;
unknown totals are never called zero.

| Query | Values / semantics |
|---|---|
| cohort | YYYY-MM; omitted means all cohorts |
| status | waiting, interview_set, approved, waitlisted, declined, withdrawn, carried_forward, started; uses derived display_status, while the row retains its original status |
| origin | university, corporate, independent, unknown |
| tech_transfer | not_disclosed, disclosed, negotiating, signed, not_applicable, unknown |
| stage | Exact recorded stage, up to 80 characters |
| incorporated | yes, no, unknown; this filters the application self-declaration |
| interview | scheduled, cancelled, none; latest scheduling row only, never inferred completion |
| carried_forward | yes/no; carried-in rows with/without rolled_from_cycle_id |
| q | Up to 200 characters; literal case-insensitive company, founder name/email, institution or idea search. Quotes, %, and _ have no SQL wildcard meaning |
| sort | waiting_longest (default), newest, company, team_size |
| limit / offset | Default 25/0, limit clamped 1–100; nonnegative integer offset. Invalid filters, syntax or unsafe offsets return 400 |

Waiting sorts pending/waitlisted rows first by `COALESCE(decided_at,
pool_created_at)` ascending, then ID descending. This clock resets on carry-in
and uses the last recorded pool decision, not an invented interview-completion
clock. Newest sorts submission time descending, Company case-insensitively
ascending with unknowns last, Team size by recorded integer descending with
unknowns last. Every sort has an ID tie-breaker.

Rows include the pool and application IDs, cohort key, original and display
status, company/idea, founder identity/role, stage/jurisdiction/incorporation
self-declaration, normalised origin/transfer/team fields, answers and the latest
interview scheduling fields. Null/legacy answers are `not_recorded`, malformed
answers are `unreadable`, and neither becomes an independent founder or a zero
team. The client preserves these states and supports zero offset. Unknown
query keys are not forwarded. Every SQL request value, including sort, limit,
offset and search, is bound; no request is interpolated into SQL.

### Verification

Real SQLite fixtures use the production baseline and lifecycle/interview
migrations. Tests exercise both routes through the mounted cohort router,
every source failing independently, empty and absent states, all filters and
sorts, uncapped totals beyond 200, empty offset pages, rollover deduplication,
ET midnight and both DST transitions, ambiguous attribution, literal SQL-like
search and admin/anonymous refusals. Client tests stub fetch and exercise the
actual exports; no new screen or React props are introduced in this part.
Key assertions are mutation-checked, followed by root build and full drift.

The table-existence guard also now recognises chained CTE aliases and explicit
CTE column lists. Its previous comma-boundary expression mistook these aliases
for missing physical tables. Regression tests execute valid CTE SQL and prove
that an actual missing store inside the CTE is still reported. No baseline or
scanner ignore is added.
