## D4605 — Ask reads whole passages, says when it could not search, and the document row decides eligibility (#4605)

#4605 (Research audit 1/5, slot S05, taken at the owner's request).

### Whole passages

Each research-document vector now stores the chunk's whole text as `metadata.passage` (byte-capped at `PASSAGE_MAX_BYTES`, 8000, inside Vectorize's 10 KiB metadata limit; `chunkMarkdown` caps a chunk at 4000 characters), beside the 280-character `snippet` that stays the display preview. The reranker reads up to `RANK_CONTEXT_CHARS` (2000) of each passage and the answer model reads the passages whole, best first, within `ASK_CONTEXT_BUDGET` (16,000 characters; the first passage always fits). The text still lives only in the vector and the R2 object, as migration 213 intended; no D1 copy is added.

A citation names the document uid, the index run (`revision`), the chunk and its page when the converter knows it.

### A search that could not run

`searchSemanticOutcome` reports `unavailable` (no index binding), `embedding_failed` or `query_failed`. `searchSemantic` keeps its old contract (an empty list) for the directory callers. Ask records such a question as `retrieval_unavailable`: stored like every outcome, counted apart in the totals, returned with `retryable: true`, charged nothing, and shown on Ask, the founder desk and the investor workspace as "could not be searched", never as an evidence gap. A search that ran and found nothing is still `no_source`. Diagnostics name the operation and never the question or a passage.

### The document row decides

A hit is eligible only while its document is the caller's, its `index_state` is `indexed` or `partial`, and the hit's `revision` is the document's `indexed_at`. So a removed document (vector deletion is best-effort), one being re-indexed (`pending`) and a vector an earlier run left contribute nothing. A vector written before revisions has none and reads its preview; it gains its whole passage on its next re-index.

### Indexing runs

Each run takes a revision (`indexRevision()`, `datetime('now')`'s shape with milliseconds), stamps every vector with it, and writes it to `indexed_at` only when the run finishes. The span of vector ids the run may write is recorded in `chunk_count` before the first write, so an interrupted run leaves every id nameable for the next re-index or a delete; the document stays `pending`, which the hourly sweep retries. Vector ids are stable, so a retry overwrites rather than duplicates. Every chunk written is `indexed`; some is `partial`, with a note saying how many; none is `failed`.
