## D1133 — Checkout gaps: renewal preparation, payment history and Pricing’s held-plan read

Issue #3013, part of #2451. Slot S25, implemented by Codex s28 at the owner’s
request. Basis: main `114d347fa0`, D1048’s Checkout canvas, PAYX10a and the
existing checkout sheet. No migration.

### What was built

`POST /api/billing/alerts/:id/pay` prepares the existing failed renewal’s
PaymentIntent for the in-page Payment Element. It creates no subscription or
invoice and confirms no charge. `POST /api/billing/alerts/:id/update-card`
prepares a card-only, off-session SetupIntent. Its `scope` identifies the
existing Billing default-card endpoint to use after Stripe.js confirms setup. Investor scope follows the recorded investor subscription id, not a customer-id coincidence; normal/founder scope serves account plans too, as the existing endpoint does.
The default is not changed just by opening the form.

Both actions require Billing’s existing TOTP factor and recent step-up. The
alert must be the caller’s own open `payment_failed` alert, its subscription
must still belong to that caller, and Stripe’s invoice must name that same
subscription and one of the caller’s recorded customers. Only an open, unpaid
invoice is actionable. Pay also checks the expanded intent’s customer and
status. Customer, subscription and intent ids are checked before reaching a
provider URL. A paid/ended payment returns a safe refusal; provider failures
return Unreadable with retry and no raw error. Responses are private/no-store.
No card or client secret is stored or audited. Refusal classification must read Stripe’s invoice because subscription-created PaymentIntents do not reliably carry plan metadata. A classification failure retries the webhook instead of silently dropping its required history. Other payment fulfilment is not deferred: auto-reload runs first and skips this audit entirely.

The three missing `activity_logs` actions now come from verified webhooks:

- `payment_refused`: the caller-bound first-payment invoice’s failed PaymentIntent,
  with only `reason_family` (`declined`, `authentication`, `payment_failed`).
  A first refusal can arrive before subscription.created: the trusted Stripe
  subscription metadata must also match the member’s recorded customer.
  Only subscription_create invoices qualify, so renewals are not double-counted. Event redeliveries share an opaque hash key; raw errors never enter history. Auto-reload failure handling runs first and its events skip checkout audit reads entirely.
- `renewal_failed`: each recorded failed renewal attempt, with empty details.
  The alert and history row commit together; an audit failure retries both.
- `renewal_recovered`: a failed renewal closed by invoice.paid or an active/
  trialing subscription, once per failed alert. The history and close commit
  together. Ending a subscription never counts as recovering its payment.

Pricing now passes D1049’s `planRead` into both `heldCard` and the sheet. An
Advisor or Operating Partner opening it during a read sees Reading; a failed
read says Unreadable and has Try again. Payment cannot start until that read
answers. A paying member sees the existing change-on-Billing mode rather than
an offer to start another subscription.
