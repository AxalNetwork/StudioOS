## D571 — Advisor practice tools from the Ops canvas: deliverables by client, session types, booking links, the access log, and the profile a client sees

**The Ops canvas (`design/incoming/Ops Page.dc.html`, D566) draws five
advisor screens over stores that already exist: A1 deliverables, A2 session
types, A3 booking links, A4 the client data access log, and A5 the profile a
client sees. Six of the client methods behind them had no screen. They have
one now, built into the Practice zones that already read each store, and every
part of the canvas that no route serves reads "Not recorded" with its reason.**
Issue #1174, slot S01 (Session 1), 2026-10-06. No migration, no Worker change,
no new client method.

**What was true on main.**
- `updateMyAdvisorDeliverable`, `createMyAdvisorSessionType`,
  `updateMyAdvisorSessionType`, `createMyAdvisorBookingLink`,
  `advisorClientAccessLog` and `getAdvisor` were in `api.js` and called by
  nothing.
- Practice · Sessions listed session types and booking links read-only. A
  failed read, or one still in flight, printed "Nothing is offered yet", which
  is a claim the page had not read.
- Practice · Delivery's "By client" chip sorted rows by client name and
  nothing more. No work product could be edited after it was created.
- No page showed one advisor's profile. `/advisors` is the directory.

**Where each screen lives.** The Practice bucket's five zones are pinned to
their own canvas (`advisor_shell_canvas.test.mjs`,
`advisor_expertise_zones.test.mjs`). Each Ops screen answers a question one of
those zones already reads the store for, so each is a section of that zone,
and the canvas's address redirects to it (`App.jsx`, guarded
`['admin', 'advisor']` like the zones, because every `/me/*` store answers
only a caller with an advisor row):

| Screen | Address | Lands on | Reads | Writes |
| --- | --- | --- | --- | --- |
| A1 Deliverables | `/practice/deliverables` | `/practice/delivery?view=by_client` | `listMyAdvisorDeliverables`, `listMyAdvisorEngagements` (the editor's picker) | `updateMyAdvisorDeliverable`; `addMyAdvisorDeliverableVersion` to attach a link; `sendMyAdvisorDeliverableVersion` (already there) |
| A2 Session types | `/practice/session-types` | `/practice/sessions#session-types` | `listMyAdvisorSessionTypes` | `createMyAdvisorSessionType`, `updateMyAdvisorSessionType` |
| A3 Booking links | `/practice/booking-links` | `/practice/sessions#booking-links` | `listMyAdvisorBookingLinks`, the session types | `createMyAdvisorBookingLink` |
| A4 Access log, advisor side | `/practice/access-log` | `/practice/engagements#access-log` | `advisorClientsSharedWithMe` | nothing |
| A4 Access log, client company side | none | the founder's data room page, under Advisors | `advisorClientAccessLog` | nothing |
| A5 Profile | `/advisors/:uid` | its own page | `getAdvisor` | nothing |

`/advisors/:uid` admits the directory's roles (`labRoles([...five])`),
because `GET /api/advisors/:uid` answers any signed-in caller. A founder is
not redirected to the team tab here: the founder is the client the page is
drawn for. The advisor's own Expertise · Profile zone links to it ("See it as
a client does").

**What each screen does.**
- **A1.** "By client" now groups: one card per client, with the canvas's
  deliverable, due, status and attachment columns and an Edit per row. The
  status flow reads Not started → Sent → Opened → Accepted. Edit changes the
  title and the engagement or client. A blank title is refused in the form,
  because the route silently keeps the old one. Moving a work product that has
  been sent asks for a second click, since the founder's received list is read
  through the engagement and the move is seen on both sides. A row with no link
  offers Attach, which records the next version, not sent, carrying the link.
  The flat list gained Edit too. Every write now says what it did.
- **A2.** A table of name, length, price, bookable and bookings, and an
  editor for a new or stored type. The canvas's rule holds: a type with no
  price reads "Not recorded" and cannot be switched on. The create route stores
  every new type switched on, so an unpriced type is created and then switched
  off in a second write. If that write fails, the page says the type is stored
  as bookable. A stored type that is on with no price is flagged, and the only
  move offered is off.
- **A3.** One card per link under its session type: the address, Copy, the
  stored on/off state, the audience and payout note. A type with no link offers
  Create link, with a slug suggested from the type's name and checked against
  the Worker's own slug rule before the round trip. A 409 ("That link is
  already taken") is shown under the form.
- **A4.** The rows are read-only: no row carries a control, and the canvas's
  line "Rows cannot be edited or removed by anyone" is under every table. They
  filter by client, by who and by a day window. The route's stamps are SQLite
  `CURRENT_TIMESTAMP` (UTC, no zone marker) and are read as UTC.
- **A5.** Name, positioning · sectors · country, expertise, the bio, the
  advisor's details and published hourly rate, and the year the profile was
  created, on one column on a phone and two on a desktop.

**Departures from the canvas.**
1. The four practice screens are sections of zones, not pages or zones, for
   the reason above. The Ops canvas's search, sort and pagination toolbars are
   not drawn: each zone keeps the chip row its own canvas pins.
2. The status flow is the store's derived state. Planned and In progress are
   one state, Not started; Delivered is Sent; Opened (the client's receipt) is
   added; Accepted is the latest version's `signed_off_at`. There is no status
   dropdown: the one status change an advisor makes is Send.
3. "Included" is stored as a price of zero, the only no-charge value the store
   holds besides a free intro. "A price" must be above zero.
4. The booking link's on/off switch is drawn disabled with its reason. The
   "Bookings received" table is not drawn: no booking is attributed to a link.
   The card links to Opportunities, which lists every request received.
5. The access log's advisor view reads "Not recorded" and lists the clients
   whose records are open to the advisor. The client company's view is mounted
   on the founder's grant panel, where the route answers.
6. The profile's address is the advisor's `uid` (the canvas says `[handle]`),
   it shows the country (the canvas says city), and it has no Book buttons and
   no session list, which a client cannot read. It adds the stored stages,
   languages, timezone, availability note, LinkedIn and hourly rate.
7. Rails. The Practice zones keep their Worker rail. It gains one line saying
   Eadwyn drafts nothing on Delivery or Sessions, where the canvas draws three
   proposals. The access log section sits under Engagements' rail, although
   the canvas draws none for it. The profile has none, as drawn.
8. On Sessions, the session types card is full width, and rules and links share
   a row. The editor opens under its row rather than beside the table.

**GAPS: what the screens need that no route serves.** Each reads "Not
recorded" with its reason.
1. **A deliverable's due date.** `advisor_deliverables` (migration 239) has no
   due column, and `PATCH /api/advisors/me/deliverables/:id` takes only
   `title`, `engagement_id` and `client_name`.
2. **A deliverable status set by hand** (Planned vs In progress). There is no
   status column. `GET /api/advisors/me/deliverables` derives `state` from
   `sent_at` and `opened_at`.
3. **Accepted.** `advisor_deliverable_versions.signed_off_at` has no writer.
   It wants a client-side route beside
   `POST /api/advisors/received/deliverables/:uid/open`.
4. **"Included in an engagement".** `advisor_session_types` (migration 240)
   has no column for it, and it is stored as `price_cents = 0`.
5. **Bookings per session type.** `advisor_bookings` has no
   `session_type_id`, and `GET /api/advisors/me/session-types` returns no
   count.
6. **What "bookable" changes.** No booking path reads
   `advisor_session_types.is_active`: `POST /api/advisors/slots/:id/book`
   books a slot, not a type.
7. **Switching a link on or off.** There is no
   `PATCH /api/advisors/me/booking-links/:id`.
8. **Opening a link.** No Worker route reads `advisor_booking_links` by
   `slug`, and no SPA route answers `/b/:slug`. A copied link reaches
   page-not-found, and the card says so.
9. **Opens and bookings per link.** Nothing counts an open, and
   `advisor_bookings` has no link id.
10. **The advisor's own access log.**
    `GET /api/advisor-grants/:projectUid/access-log` answers the owning founder
    only (`ownedProject` → `projectOwnerScope`, no rows for any other role) and
    admin. It wants a reader such as `GET /api/advisor-grants/shared/access-log`
    scoped to `advisor_user_id`.
11. **"Downloaded".** `advisor_client_access_log.action` records opens only,
    and `open_document` has no writer.
12. **Session types and links on the public profile.**
    `GET /api/advisors/me/session-types` and `/me/booking-links` are the
    owner's. There is no `GET /api/advisors/:uid/session-types`.
13. **The profile's engagement count and response time.** Engagements are
    private (`/me/engagements`), and nothing stores a response commitment.
14. **An advisor handle and a city.** `advisors` has neither column.
15. **Eadwyn's three proposals** (status update, session description,
    follow-up). `routes/research.ts` registers no `practice/delivery` or
    `practice/sessions` draft surface.

**Sidebar (left to #1164).** No new row is needed: every Practice address
lands in a zone the Practice row already matches, and the Expertise row
already matches `/advisors` for an advisor. For a founder, `/advisors/:uid`
lights Grow through its `/advisors` match, while the canvas puts the profile
under Network.

**Found on the way, outside this issue.**
- Expertise · Profile's save sends no `hourly_rate_usd`, and `POST
  /api/advisors/me` writes that column as a full replace. So every profile save
  clears a rate set elsewhere, such as by the Studio interview bank in
  `lib/advisor/banks/advisor.js`, and the profile's "Hourly rate" mostly reads
  Not recorded.
- `AdvisorsPage.jsx` (the directory) reads `name`, `hourly_rate`,
  `specialties` and `accepting_bookings`, which the Worker's `advisorDto` does
  not send. Its cards show no name, show every advisor as "Free", and say each
  is not accepting bookings.
