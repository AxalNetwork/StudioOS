### The route and its gate

`POST /api/network/directory/admin/organisation-apply`: `requireSuperAdminWriteBar` (a TOTP session, a recent
step-up, then Super Admin), then a support session is refused with `support_session_refused`. A member, a plain
admin and a lapsed step-up are refused before the body is read. A declared `Content-Length` over 4 MiB is refused
(`413` `body_too_large`) before a byte is read; a body without one is read as a stream with a running count and
cancelled at the ceiling.

**Audit.** Every call that ran a write statement (`wrote: true` in the answer or the refusal) writes one
`admin_audit_log` row with the run id, status and counts only: a call that commits batches, one that then fails or
does not reconcile, and a retry that applies no record batch but runs the review or completion batch. A replay that
writes nothing writes no row. The apply is already committed when the audit runs, so **a failed audit write is
logged and the call still answers what happened**; it never turns a committed apply into an error (and
`logAdminAction` itself never throws). No source value reaches a response, a refusal, a log line or an audit row.

### The upload contract (`network-directory-organisation-apply-v1`)

```json
{
  "contract": "network-directory-organisation-apply-v1",
  "target_environment": "<the Worker's ENVIRONMENT>",
  "schema": "202611191414_7672_network_directory",
  "planner_version": "network-directory-7672-v1",
  "snapshot": { "record_count": 0, "records_sha256": "<sha-256 of canonical(records)>" },
  "plan": { "run_uid": "<summary.run_uid>", "review_manifest_hash": "<summary.review_manifest_hash>" },
  "manifest": { "version": 1, "rows": [], "duplicate_channel_groups": [] },
  "records": [],
  "max_batches": 100
}
```

The operator copies three things from the summary the offline planner (`scripts/plan-network-directory.mjs`)
prints, or writes with `--report`, for the reviewed inputs: its `snapshot` object as the upload's `snapshot`
verbatim (`record_count` and `records_sha256`, computed by `recordsDigest` in `scripts/lib/networkDirectoryDigest.mjs`,
the same function the Worker runs: SHA-256 of the planner's `canonical` JSON of the record array), and its `run_uid`
and `review_manifest_hash` as `plan`. The manifest's optional `source_snapshot_sha256` hashes file bytes and is a
different value; it is not the upload's digest. The body is at most 4 MiB and 5,000 records; a call applies
1 to 200 batches (default 100). Any other top-level field is refused (`upload_field_unknown`), and an upload carrying
`batches`, `statements`, `sql` or `params`, at the top or in `plan`, is refused with `submitted_sql_refused`: the
server builds every statement it runs.

**Checks, in order, each writing nothing when it refuses:** contract (`contract_unknown`); `target_environment`
equal to the Worker's `ENVIRONMENT` (`wrong_target_environment`); production held (`production_apply_held`, below);
schema identity (`schema_version_mismatch`) and, once planned, the eight #7672 tables present (`schema_not_ready`);
mapping version equal to the planner's `VERSION` (`mapping_version_mismatch`); shapes (`snapshot_invalid`,
`plan_invalid`, `records_invalid`, `manifest_invalid`, `max_batches_invalid`); then the organisation-only rules; then
the snapshot count and digest (`snapshot_mismatch`); then the server's re-plan, whose `run_uid` and
`review_manifest_hash` must equal the reviewed ones (`plan_stale`). A planner exception becomes `manifest_invalid`
with our sentence, because its text can quote a source value.

**Organisation only (#7739 Q3 B).** Every manifest row must be `entity_kind: "organization"` and carry no person-only
key (`affiliation_disposition`, `title`, `title_disposition`), else `people_records_refused`; every record needs a
reviewed row (`record_unreviewed`) and every row a record. `manifest.organizations` (Folk's derived organisations,
which exist only through person rows) is refused (`derived_organizations_refused`). A source must have an
organisation mapping in `ORGANISATION_FIELDS`: today only `airtable_angels`, with exactly D7672's organisation
columns (`Name`, `Type`, `Headquarters`, `Sector Focus`, `Investment Stage`, `Currently investing?`,
`Previous Investments`, `LinkedIn`); Folk is refused (`source_not_organisation_mapped`). A column whose name reads as
a contact channel, an email address anywhere in a record or the manifest, or an email channel review is
`contact_field_refused`; a `linkedin.com/in/` link anywhere is `personal_profile_refused`; any other column is
`field_not_permitted`. The re-planned summary must hold zero people, zero affiliations and zero derived
organisations, as a second check.

### Source-review dispositions and protected records

The plan applies the manifest's `accept|review|skip` exactly as #7672 does. Before writing, the latest stored
observation of each uploaded source row is read: if the directory already holds a **newer** observation than the
upload carries, the upload's review is stale and the call is refused (`manifest_stale`, with a count). So an older
acceptance cannot land behind a later hold (the 2026-11-19T14:27Z note), and a newer hold is applied as a new
observation that `readiness()` (D7674) then reports as `latest_observation_not_accepted` and `open_review`. A planned
organisation uid that already exists as a person is refused before any batch (`entity_kind_conflict`).

Protected entries are those published, suppressed or archived, not `unverified_source_claim`, or account- or
company-linked. The planner's entry upsert already leaves them untouched; this service also fingerprints them
before and after each call and reports a difference as a mismatch. New entries are `staged`; the apply never
publishes, and publication stays the reviewed D7674 action.

### Idempotent, resumable batches from durable state

The plan's batches run in order, each in one `DB.batch()` (atomic). Progress is read from the database, not kept
in the request: `prepare` is done when the run row exists, a record batch when its `network_directory_import_rows`
checkpoint exists. A call applies only missing batches, up to `max_batches` and the statement budget below, and
answers `202` `in_progress` with the counts applied and pending. A batch that throws rolls back alone; the call
answers `503` `apply_batch_failed` with the progress, and sending the same upload again resumes. Any failure after
the first batch is committed (the protected re-read, the review batch, the read-back, the completion) is a `503`
`apply_step_failed` refusal carrying `run_uid`, `applied_batches`, `pending_batches` and `wrote`, never a bare 500.

**Statement budget.** D1 allows 1,000 queries per Worker invocation on the paid plan, and each statement inside a
`batch()` counts as one (Cloudflare's D1 limits; `services/labMilestoneCredits.ts` sizes its backfill by the same
1,000; no shared constant exists in the repo, so the service names it `D1_QUERIES_PER_INVOCATION`). Every read and
write the service runs goes through a counting wrapper, and a call stops before the next batch would take its own
statements past `STATEMENT_BUDGET` (400) while keeping back what the end of the run needs (the protected re-read,
the review and completion batches, the four read-back counts, the run read). The rest of the cap covers the gate,
the audit write and headroom; in the tests a 150-organisation plan (753 statements) ran as two calls of 410 and 394
queries in all, each within 400 of its own. Each answer reports `statements_run` and `statement_budget`. A plan whose
next batch cannot fit at all is refused with `plan_exceeds_call_budget`, writing nothing. Replaying a completed run applies nothing and answers
`200` with `replayed: true`.

### Read-back before completion

When no record batch is pending, the duplicate-review batch runs, then the run is read back and held to the plan:
checkpoints, accepted, review and skipped rows, private-source rows (counted, never selected), organisation entries,
zero people, zero affiliations, and a review item for every held record. Only when every count reconciles and no
protected entry changed is the planner's `complete` statement run, and the answer is `complete` only if the run row
then reads `complete`. Otherwise the answer is `409` `read_back_mismatch` naming the differing counts, the run stays
`planned`, and a retry reports the same mismatch rather than papering over it.

### Production

`PRODUCTION_APPLY_HELD` in the service refuses any apply when the Worker's `ENVIRONMENT` is `production`
(`production_apply_held`), whatever the request says. Lifting it is a reviewed one-line change once #8232 closes
and the owner has supplied an authorised organisation manifest; a real apply also needs the normal release gates.
No real production apply or count is recorded here.

### Rollback

Revert the PR. Nothing in the schema changed. A run applied in a non-production environment leaves staged entries
and immutable observations, which no member reads until an operator publishes one.
