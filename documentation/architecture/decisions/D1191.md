## D1191 — Capital relationships membership, staff summaries and support reads

2026-10-26 · #3125 · S29, claimed at the owner's request after S18's boundary
question returned to ready. Part of #2457; no migration or new binding.

### Identity and permissions

The recorded answer on #3125 is A: this Worker's D1 binding is the studio
boundary. No company selection, geographic field or HQ licence guesses a studio
association. No remote database or service binding is read. A project absent
from the local binding is not accessible here. A future shared deployment needs
its own decision/schema task.

Owners and active Lab owners retain their pipeline access. An accepted
`project_members` editor role (`owner` or `cofounder`) grants pipeline reads and
writes, including the shared capital record sections/actions. Advisor
memberships, removed/pending memberships and investor profiles do not grant
pipeline access. This does not widen the global project or other Raise-tool
permission helpers. Explicit editor membership does not compare the member's
unrelated company with the venture's company; existing company filtering of
the original owner's legacy Contacts scope remains.

Round changes, close/pro-rata changes and sending legacy updates remain the
venture owner's operations. Staff cannot edit/import/promote investors or
change round data. There is no investor-removal endpoint on current main;
this access task adds no physical deletion act. Co-founders gain no deletion
path. Existing promotion's internal compare-and-swap cleanup is preserved.

### Staff read surface

Admin and Super Admin follow the same rule: counts for this deployment's
ventures, without investor names, emails, notes or amounts. Summary SQL selects
only stage/count data and local venture metadata. Each failed count block stays
Unreadable, with null totals. Venture lists and private support snapshots are
paged (25 rows plus one overflow probe).

The owner confirmed during review that the wider Raise home keeps the other
tools' existing cards. Only the capital card becomes a count summary, and its
committed/conversation figures are omitted without reading them. The existing
data-room summary stays in place; readiness and runway figures are preserved.
The capital module uses the existing records-table contract for non-linkable
stage/count rows, titled Pipeline counts. It does not invent an unsupported
table state or claim that withheld investor records do not exist. Unreasoned
commitments/match/detail/round reads are refused.
The shared staff scope explicitly allows only the capital module summary GET
and support POST; all other capital paths are refused by default, including
future private GETs. The separate studio summary route authenticates staff itself.
The legacy Contacts pipeline routes and capital record/form/action routes also
enforce the boundary. Generic Contacts lists and details exclude investor or
pipeline-linked contacts for staff, so the hub is not a detail bypass. A support
session impersonating a founder cannot use these surfaces to bypass the audit.

### A fresh reason for each support response

`POST /api/cycles/raise/capital-relationships/support-read?project=` takes a
trimmed reason of 1–500 characters. It resolves exactly one active founder/Lab
owner, then writes `capital_relationships_support_read` into `activity_logs`
with that founder as `user_id`, the staff actor, reason, page, optional prospect
ID and read-only marker. The reason history exposes those request targets too.
A selected prospect is checked using only its project-bound existence before
the audit; a foreign/missing ID records no opened read and reads no private row.
Success and exactly one inserted row are required before any private pipeline
SQL. A missing/ambiguous owner, failed write or ineffective write refuses the
read. A secondary `admin_audit_log` copy supports staff governance and is
best-effort after the mandatory founder row succeeds. Its failure does not
refuse the already-audited response or log a raw database exception.

The response is a paged, read-only pipeline/round snapshot, optionally one
prospect; it carries no action and creates no access grant. Another read needs
another reason. Ordinary GETs and writes remain closed afterward. The venture's
editors can read the paged reason history through `GET .../support-reads` and
the founder can see the original activity row. Reader names are used, never
email fallbacks. Reasons stay in the intended founder-visible audit, never in
console output or refusal text.

Legacy prospect form/import/edit/promotion now enter the prospect writer module
and record the actor. Their implementation is the narrow
`raiseProspectWriters.ts` leaf, re-exported by `raiseWriters.ts`; Contacts imports
the leaf directly to preserve D752's admin/cron/member-bank import boundary.
Legacy create/import now batch each prospect insert with
its actor audit, so a failed audit rolls back that row. An import interrupted
by this storage failure reports the actual prior created count and marks the
remaining row numbers unsaved through its existing skipped-row contract.
Fixed write refusals say that saving failed, without raw database details.
The legacy edit retains its batched write/audit. Its
validation, status handling, project-bound close check and promotion's loser
cleanup are retained. Successful promotion also retains the Contacts history
entry, with fixed words and no investor email/name, once only and never for a
concurrent loser. This task changes no money/commitment arithmetic.
