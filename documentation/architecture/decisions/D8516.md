## D8516 — A durable record and a replay for e-sign effects, part 1: the staged next stage (#8516)

- **Status:** S30, 2026-11-25. Part 1 of #8516 (tracker #8509, row D2). Migration `202611250101_8516_esign_effects.sql`. Parts 2 onward are not built.
- **Basis:** the Contracts and eSignature CI audit of 2026-11-25, "fix first" 2. `routes/esign.ts` committed a signature and then ran each dependent effect in a try block that only logged. A failure left no trace and nobody could replay it without asking the signer again.

### 1. The record

`esign_effects`: one row per (envelope, effect kind), unique on the pair. Columns: `state` (`pending`, `done`, `failed`), `attempts` (every run, the first included), `last_error_class`, `last_attempt_at`, `done_at`, `created_at`, `updated_at`.

- `last_error_class` is a code (a refusal code such as `send_failed`, or an exception's name, lower-cased, at most 64 characters). It never holds message text, a token or an address.
- The row is written in the same D1 batch as the envelope's completion (`recordRequiredEffects`, `INSERT OR IGNORE`), so it exists whenever the envelope is `completed`. A completion whose record cannot be written (the batch fails as a whole) falls back to the completion alone and logs `effect_record_unwritten`; the signer's completion is never lost to the record.
- `effect_kind` has no CHECK: each later part adds a kind in code without a table rebuild.

### 2. The required-effects table

`REQUIRED_EFFECTS` in `services/esignEffects.ts` states which effects each document type requires (`'*'` is every type). Part 1 lists only `staged_next_stage`. The staged effect writes its row only for an envelope that is a stage of a staged envelope. The other effects stay in `routes/esign.ts` as they were, to move one at a time.

### 3. The staged next stage

`runStagedNextStage` (`services/stagedSigning.ts`) replaces `onStagedEnvelopeCompleted`. It stamps the stage signed once, then sends the next stage unless Axal's. It throws on failure, so the record can say so. It is idempotent: a next stage that already carries an envelope returns `already_sent` and sends nothing, so a replay invites the next signer exactly once and asks nobody to sign again.

### 4. The replay

- **The tick** (`services/esignEffects.ts` `sweepEffects`, every minute, every deployment): pending and failed records under `MAX_EFFECT_ATTEMPTS` (5) last touched at least 2 minutes ago, oldest first, 20 per tick. A record at the cap stays `failed` and the tick leaves it alone.
- **By hand:** `POST /api/legal/esign/effects/:id/retry`, a Super Admin (`requireSuperAdmin`, the gate the staged countersign uses; no narrower admin gate exists in the e-sign routes). It runs one attempt, past the cap. A `done` record changes nothing and answers `ran: false`. A missing record is 404 `effect_not_found`. Client: `esignEffectsApi.retry` in `frontend/src/lib/api/esignEffects.js`.
- The attempt is claimed by one UPDATE (`state IN ('pending','failed')` and under the cap, unless forced), so a `done` record is never run.

### 5. For the owner

- **Known gap, unchanged:** if a send succeeds but the write that links the next stage to its envelope does not, the replay finds the envelope through the sender's `already_pending` answer and records the effect `done` without the link. This was already the case; the record now makes the window visible, not closed.
- **Retry cadence:** 5 attempts at 2-minute spacing is about 8 minutes of automatic retry. Change `MAX_EFFECT_ATTEMPTS` or `RETRY_AFTER_MINUTES` if a longer window is wanted.
- **Tests that build the staged schema** (`staged_signing_d1216`, `esign_signer_resend_6197`, `closing_paper_audit_4811`) now load this migration too, since a stage's next send runs from the record.
