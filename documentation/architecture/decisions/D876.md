## D876 — Live meeting transcription: Zoom RTMS later, Meet Media API deferred, no media access from an SFU alone

- **Status:** study and recommendation for owner review, 2026-10-22; #2523, part of #2516. S14 · Codex. No live implementation is authorized by this document.
- **Basis:** `origin/main` at `f2511b82b2`. Repository observations below refer to that commit. All external sources were read **2026-10-22**; product eligibility and prices must be checked again before a build or purchase.
- **Migration/configuration/runtime changes:** none. This PR owns this file only.
- **Evidence vocabulary:** **verified** means a cited source says it or the cited repository code does it; **inference** is a technical conclusion from those facts; **proposal** is future Axal behavior; **UNVERIFIED** means no confirmed entitlement, price, compatibility test or legal conclusion. A recommendation is not a provider approval.

### 1. Recommendation and prerequisites

**Zoom — LATER: technically feasible, first candidate after post-call works.** Prefer the native RTMS transcript stream; consider audio → Workers AI only when necessary. RTMS requires a user-managed General app and relevant scopes [Z1]; external distribution requires Zoom review [Z2]. A Durable Object is a plausible WebSocket receiver, not a proven deployment (§3). The current RTMS bill is not fully verified (§6). Do not turn it on or request wider scopes in this study.

**Google Meet — LATER / no production commitment now.** The current overview and setup pages say Developer Preview is **closed to new signups** [G1, G2]. Existing Axal enrollment is **UNVERIFIED**. Restricted scopes, a full WebRTC client and participant controls add work even if Google grants access. Do not promise that adding the current transcript-import scope enables live media.

**Cloudflare Realtime SFU/TURN — NO as the source of Zoom/Meet media; OPTIONAL later as transport.** These products route application media or relay WebRTC [C1]; they do not grant a Google/Zoom meeting connection. **Inference:** an authorized provider receiver must acquire the media first. Zoom's direct WebSocket path does not need an extra SFU. A future Meet receiver might publish an authorized track to the SFU, but the provider connection remains necessary.

**Owner order:** keep native post-call transcripts first, then the authorized Whisper fallback. #2517 (M1) was still `in-progress` when read. #2520 (M4) has a merged first part (#2532), but its latest comment says part 2 is blocked on #2502/#2504; its closed issue state does not establish full readiness. **Proposal:** S1 confirms M1 and all M4 acceptance steps working before filing/enabling any live pilot. Completing this study does not clear that gate.

The webhook currently accepts `meeting.ended` and `recording.transcript_completed`, not RTMS events. The existing six-scope connector is not a live-media grant.
- [`googleMeet.ts`](../../../cloudflare-worker/src/services/channels/googleMeet.ts): existing Calendar token store; `meetings.space.readonly` for generated transcript entries; scheduled-slot matching, pagination and participant labels with `Speaker ?` fallback. This is a post-call REST reader, not a WebRTC receiver.
- [`meetings.ts`](../../../cloudflare-worker/src/services/channels/meetings.ts): `interview_channel_refs` owns the user/interview/session mapping. `destinationSession` rechecks writable ownership and preserves a recorder session; import writes final segments. Under D765 the importer runs **no model automatically**: the founder presses Summarise or Structure. The older D757/runbook automatic-handoff wording must not be copied as current behavior.
- [`liveTranscription.ts`](../../../cloudflare-worker/src/services/liveTranscription.ts): the recorder already relays PCM to Workers AI, stores draft `live` segments, holds four-minute budget blocks and settles a receipt. The route in [`founder_validate_sessions.ts`](../../../cloudflare-worker/src/routes/founder_validate_sessions.ts) checks recording state and consent before opening it. This relay consumes recorder audio; it does not capture a Zoom/Meet call or prove provider-to-Worker compatibility.

The owner setup and distribution work in [`ZOOM_AND_MEET_TRANSCRIPTS.md`](../../operations/ZOOM_AND_MEET_TRANSCRIPTS.md) still needs an account-level check. **UNVERIFIED:** actual production secrets, verified OAuth applications, account entitlements and successful real calls; none were inspected in this study.

### 3. Zoom RTMS: access, stream and Worker feasibility

**Verified product contract.** A new or existing **General, user-managed** app can add RTMS. Subscribe to `meeting.rtms_started` and `meeting.rtms_stopped`; request `meeting:read:meeting_transcript` for text or `meeting:read:meeting_audio` for audio, not video/chat/screen scopes. RTMS scopes cannot be optional [Z1]. **Proposal:** request transcript only for the first pilot; any widening of Axal's strict callback scope list and existing-user reauthorization belongs in a reviewed follow-up.

Zoom requires App Review before use outside the developer's own account [Z2]. The setup guide requires an active Developer Pack [Z3]; the troubleshooting page says Basic accounts are unsupported and paid plans still need Developer Pack [Z4]. **UNVERIFIED:** Axal's approved app, subscription, test entitlement and exact external distribution terms. Owner steps: confirm those, add minimal scopes/events, complete review and arrange consenting test hosts before promising availability.

**Verified transport.** The official WebSocket quickstart uses a start webhook, an outbound signaling WebSocket, an HMAC handshake, a second media WebSocket and keep-alive/client-ready messages [Z5]. Media documentation specifies:

- default audio is mono 16 kHz L16 PCM, with base64 audio data and participant/timestamp metadata; per-participant or merged audio is available;
- transcript packets carry attributed text, language and timing; native real-time text needs final asset reconciliation [Z6].

**Inference: Worker/DO candidate, not a successful integration.** Workers and Durable Objects support client/server WebSockets [C2]. Native RTMS transcript JSON, or decoded PCM with the appropriate framing, could be consumed using web APIs without a Node-only RTMS SDK. Prefer one DO per authorized meeting instance to coordinate signaling, lifecycle, bounded buffers, cursor/dedupe and revocation. An outbound provider socket cannot hibernate [C2]; cost it as active. A short webhook request plus `waitUntil` is not a durable meeting supervisor.

**UNVERIFIED until a bounded spike:** Zoom TLS/handshake compatibility on workerd, allowed media endpoint hosts, protocol changes, failover behavior, frame/CPU/memory limits, end-to-end latency and recovery completeness. Do not copy example logging of signatures, handshake contents or transcript text, or examples that disable TLS verification [Z5]. Proposed receivers validate the signed event and mapped ref **before** using any URL; constrain provider destinations and redirect behavior; never turn a provider-supplied URL into an arbitrary authenticated fetch.

**Speaker and completion proposal:** preserve provider attribution per instance; a name is a display label, not proof of member identity. Use neutral distinct speaker labels when unknown, never classify a colleague as the customer. Keep live segments provisional. Reconcile once with the preferred post-call transcript, retaining provenance and explicit gaps, so reconnects/imports do not duplicate evidence or AI charges. The live feed alone is not a completeness guarantee.

### 4. Google Meet Media API: preview, grants, WebRTC and notice

**Verified current availability:** both canonical developer pages explicitly say no new preview signups [G1, G2]. Older indexed setup content under `?authuser=3` still says the Cloud project, OAuth principal and every participant must be enrolled [G3]. **UNVERIFIED:** whether that older per-participant enrollment rule still applies to existing tenants. The canonical notice is the basis for deferral; an admin setting is not proof of API admission or general availability. Owner must obtain Google's written confirmation of project/principal/participant eligibility and enrollment before a spike.

**Verified permissions/Workspace controls:** audio-only scope is `https://www.googleapis.com/auth/meetings.conference.media.audio.readonly` (restricted); the setup page also requires `https://www.googleapis.com/auth/meetings.space.read` (sensitive). Server storage/transmission of restricted data requires the verification/security-assessment process described there [G2]. These are different from Axal's existing `meetings.space.readonly`. Workspace admins can enable Media API and restrict who may consent. The admin feature supports Business Starter/Standard/Plus, Enterprise Standard/Plus and other listed editions; this does **not** establish Axal API eligibility [G4]. **UNVERIFIED:** an approved Axal project, assessment cost and any additional license terms.

**Verified transport:** media uses WebRTC, SDP negotiation, RTP and resource DataChannels; CSRC identifies the participant behind a virtual stream, so a track cannot be treated as one permanent speaker [G1]. The setup guide requires codecs/header extensions and periodic client metrics [G2]. Google's reference implementations are TypeScript and C++ [G5]. **Inference:** start from a supported WebRTC receiver on a suitable runtime if enrollment becomes possible. A standard Worker/DO WebSocket endpoint is not that receiver. **UNVERIFIED:** direct workerd compatibility or a supported direct Meet-to-Cloudflare SFU connection; do not promise either.

**Verified participant experience:** an eligible in-meeting consenter is required. The overview describes the initial dialog for host/co-host or eligible same-organization participants, and says anyone can stop Media API [G1]. The admin guide states participants are informed and **each participant can turn it off** [G4]. This is not a record of affirmative consent from every party. **UNVERIFIED:** exact indicator/modal visibility for all desktop/mobile/phone/late-join cases; owner test must establish it. The conservative Axal proposal in §7 is an additional gate.

**Cost:** no confirmed per-minute Meet Media API tariff was obtained from these sources; it is **NULL/UNVERIFIED, not free**. Budget approved receiver compute/network, Google license/assessment costs and Workers AI separately. Stay with native post-call import and the authorized recorder/upload paths while live admission is unavailable.

### 5. Cloudflare transport and streaming speech-to-text

**Verified SFU/TURN role:** SFU routes tracks/DataChannels; TURN supplies connectivity through NAT/firewalls [C1]. The generally available SFU WebSocket adapter can send an existing Opus publication to a service as protobuf-framed **48 kHz stereo signed 16-bit PCM**, and can ingest PCM as an SFU publication [C3]. **Inference:** it could bridge a future authorized receiver's publication to an Axal processing service. It does not join Zoom/Meet. Its PCM/framing differs from the current recorder's 16 kHz mono relay; conversion, identity mapping and budget accounting need a measured spike. Do not place it in the Zoom-native-transcript path without a demonstrated need.

**Verified streaming STT:** Cloudflare lists `@cf/deepgram/nova-3` as real-time and batch, with interim/endpointing options and diarization [C4]. The official Gateway guide also describes Workers AI Deepgram WebSockets [C5]. **Repository:** `services/ai/catalog.ts` and `aiRouter.ts` already distinguish its WebSocket price from HTTP; the recorder relay has the hold/settle precedent. **Proposal:** reuse/refactor that shared metering path; do not add direct unmetered `env.AI.run` calls in a provider adapter. Names inferred by diarization are not verified participant identities. Latency, accuracy, language switching and overlapping-speaker quality in Axal calls are **UNVERIFIED**, not promised.

### 6. Cost model: USD supplier estimates, not a new member currency

Rates below are the cited public rates on 2026-10-22, before tax, contract discounts and any plan minimum. Calculations are **estimates**, not measured bills. Member-facing usage remains **AI tokens** through the existing reserve/settle ledger; provider pack terminology is not Axal product copy.

- **Nova-3 streaming:** **$0.0092/audio minute**, versus HTTP **$0.0052/audio minute** [C4, C6]. One continuously fed 60-minute stream: **$0.552** streaming; two independent 60-minute streams: **$1.104**. Whisper Large v3 Turbo batch is **$0.0005/audio minute**, hence **$0.03/hour** [C6]. These exclude translation, summaries, proposals, provider transport and infrastructure. Do not use the batch tariff to price live audio. Streams, reconnect overlap, silence and supplier rounding need billing validation; Axal's current relay rounds elapsed minutes upward (`billedMinutes`).
- **Zoom:** a Zoom staff reply dated 2026-06-15 cites **$0.01/meeting streaming minute without transcription** [Z7]. Indicative only: **$0.60/hour** RTMS audio + **$0.552/hour** one Nova stream = **$1.152/hour**, before infrastructure. **UNVERIFIED:** current pack minimum, unused-pack liability, billable-minute definition, concurrency/stream charging and the **with-transcription** tariff. The current pricing page confirms Developer Pack but its extracted content supplies no numeric rate [Z8]. A native transcript is not assumed to cost $0.01 or to be free. Owner obtains and records current rates for text-only and audio separately before approval.
- **Meet:** supplier access/license tariff is **UNVERIFIED/NULL**. If admitted, one full-hour Nova stream adds **$0.552**, plus WebRTC receiver compute, network and verification costs. Per-speaker sockets scale with the sum of fed stream minutes, not merely meeting duration. No total price is supportable yet.
- **Optional SFU/TURN:** **$0.05/GB egress**, first **1,000 GB/month shared** between SFU/TURN; ingress is free; other services billed separately [C7]. Example assumption: one 256 kbit/s mono PCM egress for an hour is 0.1152 decimal GB, about **$0.00576** above the allowance. The adapter's 48 kHz stereo PCM is 1.536 Mbit/s, or 0.6912 GB/hour and **$0.03456** for one such egress, excluding framing. Count actual billable paths; neither is an all-in meeting rate.
- **DO supervisor:** outgoing sockets cannot hibernate [C2]. Paid overage is **$12.50/million GB-s** and **$0.15/million requests**, with included monthly allocations [C8]. An always-active hour at the documentation's 0.128 GB accounting is 460.8 GB-s, or **$0.00576** duration before allowances; messages/alarms/storage/Workers are extra. This is an arithmetic illustration, not a measured receiver resource quote.

**Proposed budget rule:** hold bounded time blocks before live STT, renew before expiry, stop audio on refusal/withdrawal and settle once for actual usage, including failures. Stable execution/stream identities must prevent retry charging. Reuse `reserveAiBudget`, `settleAiReservation`, `aiRouter` and D844 `meteredCall` where appropriate; no second balance or conversion. **Owner decision needed:** who pays Zoom pack/receiver overhead and whether any part is passed through as AI tokens; do not silently charge an unverified tariff or charge a second STT run when native text suffices.

### 7. Consent, notice and privacy

**Verified legal example, not a worldwide clearance:** Washington RCW 9.73.030 generally requires consent of all participants to private conversations/communications, subject to statutory exceptions. Its announcement provision requires an effective announcement to all parties, and recording that announcement if the conversation is recorded [L1]. Laws differ by jurisdiction and circumstances; cross-border applicability and any other region's requirements are **UNVERIFIED here**. **Proposal:** owner/counsel approves launch jurisdictions, lawful basis, notice wording, processing agreements and retention before a live build is enabled. Do not treat the absence of an audio file as an exemption from live interception/transmission rules.

**Verified provider notice:** Zoom documents RTMS disclosures and App Activity Notifications identifying content shared with apps [Z9]. Meet documents participant notice and each participant's stop control [G4]. These provider permissions/disclosures do not by themselves prove Axal's all-party consent record.

**Proposed conservative live gate:**

1. Founder explicitly selects one scheduled/verified-attached meeting and interview. Resolve user/company/session from its stored ref; verify current member grant/ownership. No automatic capture of all meetings or arbitrary links.
2. Explain live audio/text processing, recipients, purpose, retention and stopping, with `/privacy/interviews` available. Record all-party agreement before provider capture/STT, in addition to provider permissions. An upload attestation remains a different post-call path. No silent, auto-start pilot.
3. On a late join or unknown consent, pause capture until notice and agreement are recorded for that party; refusal, provider stop, withdrawal, revocation or deletion closes the stream and settles/releases holds. **UNVERIFIED:** provider controls can implement this without a pre-consent buffer. The spike must prove that no earlier buffered media is processed or stored; otherwise do not ship.
4. Raw media stays transient unless an expressly approved session retention policy needs it. Keep transcript/translation/provenance under the session; reuse M8 retention/deletion and remove live buffers/state on purge. Recheck consent before every asynchronous write; late frames cannot recreate deleted data.
5. Never log media, text, names, identifiers, OAuth material, signatures or signed URLs. Logs contain coarse counts/states only. Render text as escaped data, never HTML or instructions; tool access still requires its own current scopes/consent/export rules.

These are proposed acceptance gates, **not implemented controls**. Existing consent fields and recorder checks are useful primitives, not evidence that all-party live notice and withdrawal already work.

1. **Readiness/owner evidence:** confirm M1 and complete M4; record actual Zoom app distribution, scope grants, text/audio tariff and pack terms; ask Google about existing admission/new-signup closure. 2. **Consent/lifecycle design:** approve jurisdictions/notice and per-party/late-join behavior; define ref-to-live-session identity, withdrawal, budget and M8 deletion races. Acceptance: agreed contract and explicit no-capture behavior when any gate is unknown.
3. **Zoom transcript-only spike:** signed events → restricted destinations → DO signaling/media protocol → bounded draft segments, with no automatic summaries or provider audio retention. Acceptance: restart/reconnect, duplicate events, long call, consent withdrawal, revoked grant, deleted session and kill-switch cases; measured costs/latency/gaps. Mark compatibility claims verified only after this.
4. **Zoom production pilot:** approved scopes/distribution, recovery supervisor, final native transcript reconciliation, receipts/idempotency, role/tenant isolation and founder-only review. Add translation/analytics/proposals through the shared services, on the required press; no automatic module writes or live MCP prompt execution.
5. **Optional audio spike:** only if native RTMS text is inadequate; select merged versus participant streams, verify Nova encoding/speaker mapping and block metering, compare accuracy and total bill. SFU/TURN only if a measured transport requirement justifies it.
6. **Meet feasibility revisit:** only after Google admits Axal. Use a supported WebRTC reference client, verify all participant notice/stop cases, identity across virtual-stream changes, eligible editions and costs. A closed preview has no implementation delivery date.
