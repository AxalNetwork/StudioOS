## D9026 — Licensed-program agreements: the readers of `program_grants.schedule_contract_uid` read the canonical agreement rows (#9026)

D5048 §5 kept `program_grants.schedule_contract_uid` as the read-through for a grant's schedule envelope "until its callers move", and D5051 §6.3 named the five files that still read it: `routes/admin_program_grants.ts`, `services/programGrants.ts`, `services/programSchedule.ts`, `services/licencePrograms.ts` and `services/programAgreements.ts`. This moves them to the grant's current `program_schedule` version in `licence_program_agreements`. The column is not dropped (§4).

### 1. One definition: `program_grant_schedule_envelopes`

Migration `202611272239_9026_program_grant_schedule_envelopes.sql` adds a view, `(grant_id, envelope_uuid, source)`, so the rule is written once and the read and the completion guard cannot disagree.

A grant's schedule envelope is its newest `program_schedule` version (by id) when that version is still the grant's:

| Newest version | Envelope |
| --- | --- |
| `sent`, `partially_signed`, `executed` | its envelope |
| `voided` | its envelope, unless the D4805 schedule row for that envelope was superseded by a terms change |
| `superseded` | none |

That is what the column holds on every path that writes both in one batch:

- **Send and resend.** `scheduleAgreementSentStatements` voids or supersedes the version in flight and inserts the new one, which is the newest.
- **Completion.** The version becomes `executed` and stays the newest.
- **Terms change and re-grant.** `scheduleAgreementsSupersededStatements` supersedes every live version of the grant in the batch that clears the column.
- **Legacy grants.** D5048's backfill gave each envelope a version, in schedule order, with the column's envelope last.

A voided envelope that was never sent again stays named, as the column kept it (the send then allows a resend, as before). The D4805 check on `voided` covers a legacy grant whose envelope was voided and whose terms then changed: the backfill marks it `voided`, and the column was cleared.

**Legacy fallback.** A grant with no schedule version at all reads the column (`source = 'legacy_column'`). After D5048's backfill no production grant should be in that state. A row written outside the send path is, though, and `licence_agreement_policies_d5052.test.ts` test 12 inserts such a grant and expects its envelope. This fallback is the one place left that reads the column.

### 2. The readers

- **`services/programAgreements.ts`.** `scheduleEnvelopes(env, grantIds)` reads the view. `withScheduleEnvelopes(env, rows)` adds `schedule_envelope_uuid` to grant rows. The header no longer calls the column the read-through.
- **`services/programGrants.ts`.** `presentGrant` takes the schedule's `contract_uid` and its status from `schedule_envelope_uuid`, and `readGrid` reads it for every grant. `scheduleStatus` is unchanged: it takes the presented envelope as its argument, and `presentGrant` hands it the agreement row's envelope.
  - A row read without `withScheduleEnvelopes` presents no envelope. Every caller that answers a `schedule` reads it first: the grid, the licence read, the grant writes' answers and the branch copy. The others use only `in_force` and `waiting_on`, which the envelope does not touch: `programEnforcement`, `programGrantStates`, `agreementPolicies` and `admin_licence_agreements`.
- **`routes/admin_program_grants.ts`.**
  - `grantRow` and the licence read go through `withScheduleEnvelopes`.
  - The send's `already_sent` refusal reads the agreement row's envelope and its e-sign status.
  - The history line's `before` is that envelope. The history key stays `schedule_contract_uid`, so old and new lines read alike.
  - Terms change and re-grant are unchanged: they already supersede the agreement rows in their batch.
- **`services/programSchedule.ts`.** The completion guard matches the envelope against the view (`? = (SELECT v.envelope_uuid FROM program_grant_schedule_envelopes v WHERE v.grant_id = program_grants.id)`), before the batch executes the version. Before, it matched `schedule_contract_uid = ?`.
- **`services/licencePrograms.ts` (the branch copy).** HQ fills the copy's `schedule_contract_uid` from the agreement row's envelope, not from the column. The copy keeps that field name, because a branch holds the last copy pushed to it. A copy pushed before this change carries the same field, and `studioPrograms` presents a branch's copy from it. Branches run the same Worker, so the field stays until the drop (§4). Renaming it then needs the fallback `studioPrograms` already has.

### 3. Writes are unchanged

The send still sets the column (`RECORD_SCHEDULE`), and terms change and re-grant still clear it, in the same batches as before. The Worker one version back reads the column, so a rollback finds it true.

`program_grant_schedule_readers_9026.test.ts` test 3 fails on any new mention of the column in `cloudflare-worker/src`. Allowed are the three writes, the history key, `scheduleStatus`'s argument and the branch copy's field. It also fails on an allowlist entry that no longer matches.

### 4. Is the drop safe now? Not in one step

- The view's legacy fallback reads the column. D5052's test 12 pins that read for a grant with no agreement row.
- The three writes keep the column true for a rollback.

A drop is safe in two deploys, each its own PR:

1. **Stop writing.** A migration re-runs D5048's column-only backfill, so no grant depends on the fallback. It replaces the view without the fallback, and the Worker stops writing the column. This needs test 12 restated as a backfilled grant.
2. **Drop.** One deploy later, so that no running Worker writes the column, drop it.

D5048 §7 question 2 is still open on #5047, and no owner answer to Q17 was found. Option A (drop after the move) is S1's built default, so the drop waits on that answer. Per the issue, the drop is not filed under #5047, because it is not safe yet.

### 5. Proof

`cloudflare-worker/test/program_grant_schedule_readers_9026.test.ts`, real node:sqlite:

1. **Every write path.** The run goes through grant, send, resend refused, an envelope voided, resend, the replaced envelope completing, the current one completing, a terms change, the amendment sent, a completion for superseded terms, end, re-grant, and a new schedule signed. After each step, for every grant, each reader is checked against the column read by the code as it was before:
   - the presented status and contract uid;
   - the completion guard, for every envelope on file and one from elsewhere;
   - the licence read;
   - the branch copy, and a branch presenting from it.
2. **Eight legacy grants.** The grants are inserted below the D5048 migration (sent, signed, voided, voided then changed, signed then amended, sent then changed, an envelope only the column names, never sent). The test records what the column answers, applies D5048's backfill and this view, and checks that each reader answers the same. It then empties the column, as the drop will, and the answers do not change.
3. **A backfilled legacy grant (`origin = 'backfill_d5048'`).** With its column emptied, it reads as sent on the licence read and the branch copy. A resend is refused, and its completion signs the grant through the guard.
4. **The guard** described in §3.

The existing tests pass unchanged: the four program grant files, `licence_agreement_policies_d5052` (test 12 included), `licence_programs_d984` and the rest that name these files.
