## D6474 — The branch keeper merges main into conflicted PR branches on a runner, without a model (#6474)

- **Status:** built. The hosted proof waits on the owner's landing bot App and `landing-bot` environment. Part
  of #5600 (plan key C3).
- **Why:** GitHub ignores `README.md merge=union`, so a PR whose only conflicts are README rows shows as
  conflicted although `git merge` merges it. That was 3 of the 6 dirty PRs on 2026-11-14. A conflicted PR also
  gets no `pull_request` CI. In the landing simulation, a runner merge took knock-outs from 27 to 22 and
  conflicting pairs from 42 to 28.
- **What it does:** `.github/workflows/landing-bot-keeper.yml` with `scripts/landing-bot/keeper*.mjs`; the
  rules are in `scripts/landing-bot/README.md`, "The branch keeper". In order:
  1. It reads all open PRs in one GraphQL call per 100.
  2. It keeps only PRs that are conflicting, not queued, quiet, not handed back since their last push, and that
     pass `eligible()`, `attempts()` and `budget()`. It takes them in `order()`, up to the per-sweep cap.
  3. It reserves today's pushes in an artifact before any push.
  4. It merges main with hooks, filters and LFS off. Merge rules come from main only, through
     `$GIT_DIR/info/attributes`.
  5. It checks that only `README.md` files needed the union rule, and that each passes `readmeUnion.mjs`.
  6. It pushes a normal merge commit, never forced.
- **Named `landing-bot-keeper.yml`, not `branch-keeper.yml`** as the issue had it. #6467's shared rules already
  name each bot kind's workflow `landing-bot-<kind>.yml`, and the guard helper reads that list.
- **Conflicts.** A real conflict is labelled `conflict` and listed in the sticky comment. A separate job asks the
  resolver (`landing-bot-conflict.yml`, #6475) with `GITHUB_TOKEN` and only `actions: write`. Until #6475 lands,
  that job notes in the summary that the resolver is not on main. A conflict in a file `pathGuard()` refuses
  goes to `giveUp()`, with `needs-session`.
- **Workflow-file pushes.** If GitHub refuses the push because the merge carries main's workflow-file changes,
  the keeper tries the update-branch API with the expected head SHA. If that fails too, it hands the PR back.
  Each run's summary records how often this happens; the hosted proof answers the question with a run link.
- **AGENTS.md:** one sentence: fetch and merge your own branch before you push, because the bot may have added
  a merge commit.
- **Guard:** `frontend/test/landing_bot_keeper_6474.test.mjs`.
  - Real git fixtures:
    - a README-only conflict is merged as one normal merge;
    - a duplicate README row is refused;
    - a code conflict is reported, never committed;
    - a PR adding `*.ts merge=union` cannot merge a code conflict.
  - The plan does nothing for a queued PR, a recently pushed PR, a fork, `bot:off`, an unset mode, an open
    breaker, a third attempt, an only-behind PR, a handed-back PR or an unreadable diff.
  - The workflow has no PR trigger, no expression in a run script, and no App token in the dispatch job;
    `assertWorkflow` passes.
  - Mutation-checked: honouring in-tree attributes, dropping the README check, and touching queued PRs each fail
    it.
