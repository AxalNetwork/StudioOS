### What was found, on main `a2677f7615`

Part 1 deferred executions to #4667 for "a reliable run status". #4667 was about evidence binding, so the run records were read again here to see what each one says:

- **Completed runs name their skill.** `agentRun` tags the run's usage row and its guard rows with `skill_id` and `skill_version` (`tagUsage`) after the model answers, on the manual and the scheduled path. Its `run` event carries `skill: { uid, version }`.
- **Refused and failed runs do not.** `refused()` logs `{ code, module, option }`, and `tagUsage` is not reached. That includes `skill_not_ready`, `skill_suspended`, `tool_not_in_skill`, a gateway or model failure after the hold, and `proposal_not_saved`.
- **A scheduled run's row has no skill.** `agent_task_runs` keeps the status and refusal code. Its skill is reachable only through the task's session, whose `agent_duties.skill_version` a re-pin rewrites in place. So that join would name the current pin, not the version that ran.
- **Evaluation runs are untagged.** The published board, the draft board and the rubric never call `tagUsage`, so they do not count as executions.
- **Account path.** A run that answered on a later account attempt tags only the answering attempt's row. Its `run` event records `accounts_tried`.
- **Timing.** No run records the whole run's start and end. `ai_usage_logs.latency_ms` is the model call's latency. A scheduled run's `ended_at` includes the person's decision.

### What is decided

1. **A run is a completed run.** The block counts skill-tagged parent usage rows (`guard_for IS NULL`) and says so (`counts: 'completed_runs'`). It is the only record that names the skill, the executed version and the model, all written at run time.
2. **Tokens and charge are the run's rows.** Each covers the parent and its guard rows, the same rows `chargedFor` sums, in integer micro-USD as stored.
   - A run with any row's charge NULL is `runs_unrecorded`.
   - A run whose event names an earlier account attempt is `runs_incomplete`.
   - Neither is summed. `cost_per_completed_microusd` divides over the fully recorded runs only, else it is `{ available: false }`. The total is never an estimate, and the estimate (`tokens_per_run`) stays labelled as one.
3. **Latency is the model call, by nearest rank.** `model_latency_ms` reads p50 and p95 of `latency_ms` (> 0) per executed version and in total. Only the rows at those two ranks leave SQL. `run_latency` is `{ available: false }`.
4. **The path is the engine's own row.** A run is scheduled when an `agent_task_runs` row names its usage row, else manual. The check is keyed by the run's agent (`idx_agent_task_runs_agent`), as is the account-attempt check (`idx_team_agent_events_agent`). Neither scans a table once per run.
5. **The window.** It is on the usage row's `created_at`: the `from`/`to` filter (at most 366 days), else the last 30 UTC days with today included. `window.source` says which. The read never runs over the whole history.
6. **Filters.** The skill terms keep HQ skills by their current published version, as coverage does. `version` is the exception: it keeps that **executed** version. Model and window are bound in SQL. `by_scope.company` is a count under the window and model, and `{ available: false }` under any skill term.
7. **Adoption is not usage.** `published_without_completed_runs` names the published HQ skills, after the same filters, that completed no run in the window, whatever their pins. It is not "unused": a skill whose every run was refused is in it, and the block says why.
8. **Company skills are counted, never named.** Their runs appear in `by_scope.company` only. No company uid, slug, role or tag is selected into the response (the D4161 boundary).
9. **Unreadable is said.** If the run history cannot be read, the block is `{ available: false, reason, window }`. If only the latency read fails, each `model_latency_ms` says so. Neither is served as zeros.
10. **#3851 is not read.** No query names a proposal table. The test checks both SQL texts.
11. **`coverage.executions` stays unavailable** and points here. Coverage is the catalogue now, and usage is its own block with its own window.
12. **Refusals name their skill from now on** (owner answer A, 2026-11-21, asked on #4536). `refusalDetail` writes it into every `refused` event:
    - the requested skill uid;
    - its version, null until `skillForRun` reads the pin, else the session's saved version;
    - the HTTP `status`;
    - `outcome_v: 1`;
    - `engine: true` on a scheduled run.

    Every `run` event carries `outcome_v: 1` too. A scheduled skill-evidence refusal (`skill_not_ready` in `runStep`) ends before `agentRun`, so the loop writes its `refused` event. That is the one new event a member can see: the agent's activity now lists that refusal as it lists every other one. There is no migration (it is the events' JSON detail). The proposal is unchanged.
13. **Rates count marked events only.** `outcomes` reads `run` and `refused` events with `outcome_v = 1`, joined to HQ skills by uid, so a company skill is never joined. An event from before the change never enters a denominator, and `attributed_since` names the earliest one read.
    - A refusal is **failed** when the run reached the model path and did not finish (`FAILED_CODES`).
    - It is **retryable**, and no outcome, when the step is tried again (`step_in_flight`, or another status of 500 or above). It is counted apart.
    - Otherwise it is **refused**.

    The rates divide by `ended` (completed + refused + failed). A model filter makes `outcomes` unavailable, because an event has no model. Refusals that end a scheduled run before its skill is read (the `load` and `context` steps) name no skill and are not in the rates.
14. **The events read scans the window's events.** `team_agent_events` has no index on `created_at`, and adding one would be a migration this answer did not ask for. The read groups in SQL and returns one row per skill, kind, code and version. If its cost shows, a partial index on `(kind, created_at)` is the follow-up.
