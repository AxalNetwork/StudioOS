## D8754 — Scheduled backups and monitoring leave the reviewed production-ops environment, and an alert says when they do not run (#8754)

**Context.** `production-ops` has a required reviewer. It holds the broad Cloudflare token for recovery drills,
branch provisioning and agent keys, and it was also the environment of every scheduled backup and monitoring job. So
every scheduled run waited for a person. From 2026-11-22 the daily D1 backup (`backup-d1.yml`) waited four days in a
row (runs 45008680536, 45158038475, 45392739036, 45601802222). The last success was run 44890546972 on 2026-11-21,
against a 24-hour recovery-point objective. The magic-link probe and the weekly admin drift waited the same way.
Nothing said so: the Worker reads `heartbeat-d1.json` only for the admin page. D8069 had seen the cause for one job
and kept `github-alerts.yml/file-backup` out of `production-ops` for exactly this reason, leaving its home to the owner.

**Decision.**

1. **An alert on GitHub's own run records (this change).** `github-alerts.yml` gains an hourly `ops-schedules` job
   (`scripts/lib/opsScheduleHealth.mjs`) that reads only the watched workflows' `main` runs with `actions: read`. It
   has no environment and no production credential. It opens one `[alert] scheduled production operations not
   running` issue and posts once when any of these holds:
   - `approval_pending`: a run has waited on an environment approval for over an hour;
   - `backup_stale`: no successful D1 backup started in the last 26 hours (the objective plus its schedule's slack);
   - `schedule_missed`: no run of a watched workflow was created within its window (backup 26 h, probe 9 h, admin
     drift 8 days);
   - `credentials_missing`: the newest finished run failed at the workflow's own secret guard step.

   Unreadable evidence is no observation: an open alert stays open until a read proves every watched job healthy.
   Only the named reasons and workflow file names reach the issue and Slack.
2. **Two environments for the scheduled jobs (the follow-up PR, after the admin slot creates them).**
   - `production-backup` holds `backup-d1.yml`, with a Cloudflare token scoped to D1 read and export of
     `studioos-db` and R2 objects on `studioos-backups` only.
   - `production-monitoring` holds `magic-link-insert-probe.yml`, `admin-drift.yml`,
     `github-alerts.yml/file-backup` and the hourly `pr-overlap.yml` (the owner's answer, 2026-11-26: its only
     secret is the application-only WorkGraph ingest token), with a D1 read-only token and their existing
     secrets. `SLACK_GITHUB_WEBHOOK_URL` stays a repository secret (also the owner's answer).

   Both allow deployments from `main` only and need no reviewer. `production-ops` keeps its reviewer and its broad
   token for every destructive recovery, restore and sensitive mutation: `dr-drill.yml`, `schema-rehearsal.yml`,
   `branch-provision.yml`, the agent workflows and `file-recovery.yml`.
   No pull-request workflow can reach any of the three.

**Rollback.** The alert is one job and one mode; deleting them removes it. The environment move is one revert that
points the four jobs back at `production-ops`, and the two new tokens are then revoked.

**Verified.** `scripts/lib/opsScheduleHealth.test.mjs`, 9 tests:
- the 22–25 November record itself is `approval_pending` and `backup_stale`, 119 hours old;
- approval grace, staleness, missed schedules, the per-workflow credential guard, and branch and event filtering;
- the episode opens once, stays open through unreadable checks, and closes on a healthy read;
- the facts allowlist;
- the job holds no environment and no secret but the Slack webhook.

Mutation check: 13 mutations, 13 caught. A read-only run of the rule over the live run records on 2026-11-26 found
the backup (four runs waiting, 119 hours since the last success), the probe and admin drift all `approval_pending`.
