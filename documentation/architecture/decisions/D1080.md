### 1. The routes (`cloudflare-worker/src/routes/connector_mcp_oauth.ts`)

They are mounted at `/api/integrations/mcp`, after Mercury's sign-in and ahead of the integrations router.

- **`GET /:key/start`** answers `{ ok, authorize_url }` and sets the CSRF cookie `__Host-axal_mcp_oauth` (ten minutes). The SPA then sends the browser to the address, as Mercury's start does. The redirect is the browser's, not a 302 from the Worker, because the start is a signed-in `fetch`.
- **`GET /:key/callback`** answers a redirect to the connector's page: `/account/connectors/<key>`, or the start's `return_to`. It carries `oauth=ok|error`, `provider` and one reason word (`CALLBACK_REASONS`), never anything else.
- **`GET /:key/client.json`** is the client ID metadata document (§4). It is public.

**`:key` is looked up, never interpolated.** `genericMcpProvider` reads it from the frozen records with `Object.hasOwn`, so a key such as `__proto__` is unknown. The record must name itself and call back to `/api/integrations/mcp/<key>/callback`. An unknown key is 404, and so is Mercury, whose callback is its own.

**The router is built by `createMcpOauthRouter(deps)`.** Tests pass a record, a descriptor, the fake's `fetch`, a pre-registered loader and a provider check. The default export uses `MCP_PROVIDERS`, the registry, the global `fetch` and HQ › Integration keys.

### 2. Who starts, in this order

Nothing below writes a state row or reaches the provider when it refuses.

1. Signed in.
2. The descriptor is visible to the caller (`audienceFor`, D757); otherwise 404.
3. Not a support session: 403 `support_session_refused`.
4. An active company when the provider writes project data (`writesProjectData`): 400 `active_company_required`.
5. Not coming soon: 503 `coming_soon`.
6. The plan the descriptor names: 402.
7. D751's readiness (`mcpReadiness`):
   - a record that registers by DCR, or by a client ID metadata document served here, is ready, because the server's own metadata decides at start;
   - a record that can only use a pre-registered client is ready when HQ holds it. Otherwise it is 503 `oauth_unconfigured`, or 503 `oauth_setup_unreadable` when the key store could not be read.

A start that cannot discover or register is 503 `mcp_sign_in_unavailable`, with the client's error code as `reason`.

**The state** is #1's signed, single-use, ten-minute token, bound to the user and the record's `state_provider`. Its row holds:
- the PKCE verifier;
- the SHA-256 of the CSRF cookie;
- the client's key;
- the issuer and resource discovered at start;
- the active company;
- the return path. That is a path on this site of at most 200 characters, never `//…`, a scheme, a backslash or whitespace; anything else becomes the connector's page.

### 3. The callback, in this order

1. **The state** is consumed first, so it can never be replayed. A state issued to another user, forged or replayed reads `invalid_state`.
2. **The cookie** must be the one given at start: `csrf_mismatch`.
3. **`iss` (RFC 9207).** The server is discovered again for the stored resource and must name the issuer recorded at start. `iss` is required when the server says it sends one, and when present must equal that issuer byte for byte (`issuerAccepted`). On a mismatch nothing is acted on, the provider's own `error` included: `issuer_mismatch`. A server that cannot be discovered again reads `discovery_failed`.
4. **The provider's answer:** `error` reads `access_denied` and a missing code `missing_code`. Then the start's refusals are checked again (`not_allowed`), the company excepted: the state carries it.
5. **The exchange.** It uses the client the state names, found again (`resolveMcpClient`), and this host's callback. A grant reporting any scope off `accepted_scopes` is revoked and refused inside `exchangeMcpCode`: `scope_refused`. Any other failure is `token_exchange_failed`.
6. **The provider's own check**, when its issue gives one (`verifySignIn`, by key; none today). A check that fails or throws revokes the grant (`revokeMcpTokens`): `sign_in_refused`. A passing check may name the account, which labels the connection.
7. **One row.** The `integrations` row is keyed by member and provider, with `auth_type = 'oauth_mcp'`.
   - Its tokens are encrypted against its uid. The blob is version 2, with `v` and `resource`.
   - `config_json` is `{ via: 'oauth_mcp', resource }`, and `scopes_json` holds the granted scopes.
   - A second sign-in updates the same row.
   - The company the state names is enabled when the member still belongs to it.
   - One `integration_logs` row and one `activity_logs` row record it.
   - A write that fails revokes the grant: `callback_failed`.

Every failure from step 3 on writes one `activity_logs` row, `integration_oauth_failed`, holding its reason word.

**Nothing credential-shaped is logged, stored in a log row or put in a redirect.** That covers tokens, the code, the verifier and the cookie. `mcp_client_oauth.test.ts` §10 checks all four sinks.

### 4. The client ID metadata document

`GET /api/integrations/mcp/<key>/client.json` serves only a record that registers by `cimd` and whose `cimd_url` is exactly `https://axal.vc/api/integrations/mcp/<key>/client.json` (`mcpCimdUrl`). Any other record gets 404. The document holds:
- `client_id`: its own URL;
- `client_name`: "Axal VC";
- `client_uri`;
- the record's callback on both hosts (`redirect_uris`);
- `authorization_code` and `refresh_token`, `code`, and `token_endpoint_auth_method: none`;
- the record's scopes.

There is no secret in it. It is cached for an hour, and it has its own rate-limit bucket, `mcp_client_metadata`: 60 a minute per IP, fail-open like the other public reads (`middleware/rateLimit.ts`, `MCP_CLIENT_METADATA`).

The client (`mcpClientFor`) already offers a CIMD client only when the server says it takes one and the URL is on axal.vc. This route is what makes that URL answer.

### 5. Pre-registered clients: the `MANAGED_PROVIDERS` and `CALLBACK_URL` hooks

A record whose `registration` names `preregistered` reads its client ID and secret from HQ › Integration keys (`mcpPreregisteredFor`, through `loadOauthCreds`, env first). So:

- its key must be a `MANAGED_PROVIDERS` key. `mcp_providers.test.ts` §3 fails a record that is not.
- `CALLBACK_URL` in `routes/admin_integration_keys.ts` is exhaustive over that union, so `tsc` then requires its entry. The entry is `mcpCallbackUrl('<key>')`, which gives `<callbackBase>/api/integrations/mcp/<key>/callback`.

No record is pre-registered today, so neither list changes here. The provider issue that first needs one adds its key to both, with its `PROVIDER_ENV_VARS` names.

The redirect URI sent to the provider is the host the sign-in started on, as Mercury's is, because the `__Host-` cookie lives there. So a pre-registered client must register both `https://axal.vc/…/callback` and `https://app.axal.vc/…/callback`. The console shows the first. A DCR client is registered once per redirect URI (D847).

### 6. Disconnect

`DELETE /api/connectors/:uid` (`routes/integrations.ts`) calls a provider's own `disconnect` when it has one, as before; Mercury does. Otherwise it calls `mcpDisconnect`:
- for an `oauth_mcp` row of a record the generic routes serve, that is `revokeMcpConnection`: the provider's revocation endpoint, best effort, then the stored tokens deleted;
- for any other row it does nothing.

The row is deleted after, as before.

### 7. The `mcp` kind in the SPA

The kind is read by `isMcpSignIn(p)` in `frontend/src/pages/account/connectorsModel.js`: a connector whose registry row says `auth_type: 'oauth_mcp'`, or whose directory entry says `sign_in.kind: 'mcp'`, and which is not Mercury. Mercury keeps D840's words and route.

- **The label.** The band's one action (`pageAction`) and Details' Sign-in row say "Sign in with <Provider>". The `aria-label` is "Sign in with <Provider> to connect it to Axal VC". There is no token choice beside it.
- **Manage.** It holds Sync now, **Sign in again** and Disconnect.
- **The tooltip.** It reads "Opens <Provider>’s own sign-in page. Axal VC never sees your password there." It is on the band's button (`ConnectorPage.jsx`) and on the Discover card's "+" (`AccountConnectors.jsx`).
- **The start.** `useConnectFlow`'s `startOauth` calls `mcpOauthApi.start(key)` (`frontend/src/lib/api/mcpOauth.js`, one line in `api.js`, D527), then sends the browser to `authorize_url`. A refusal draws the page's notice and assigns nothing. The client sends `return_to` only for a path on this site.
- **The return** is read by the existing `oauthReturn`: `ok` draws Connected, and a reason word draws the refusal.

"Add a custom connector" stays disabled (owner decision 11 on #2415), and its tooltip is unchanged.

### 8. Tests

**`cloudflare-worker/test/mcp_client_oauth.test.ts`** has 10 cases, against `_mcp_fake.mjs` ("notes" on `notes.example`):
1. Sign in end to end: one DCR registration per redirect URI, the encrypted v2 blob, one row on a second sign-in, and the return path.
2. Discovery through the start. The well-known order; a 401's `resource_metadata` first, and never off the hosts. A changed issuer, no S256, an endpoint off the hosts, another resource and a 3xx are each refused.
3. Registration order: pre-registered, then CIMD, then DCR. A pre-registered client also signs in end to end, its secret never stored.
4. The start's refusals. Signed out; a support session; no company; an unknown key and `__proto__`; Mercury; a provider the caller cannot see; the plan; no client held, or none readable. None leaves a state row or reaches the fake.
5. The callback's refusals. Another user's state, a forged one, no cookie, a wrong cookie, the provider's error, a replay, and the start's refusals checked again. None exchanges a code.
6. `iss`:
   - absent with no `iss` support, accepted;
   - wrong with no `iss` support, refused;
   - absent with `iss` support, refused;
   - a near miss, refused;
   - an `error` under a mismatch, refused;
   - right, accepted;
   - a server that now answers as another issuer, refused.
7. An overreaching grant, and a `verifySignIn` that fails or throws, each revoked with nothing stored. A passing check labels the row.
8. The client ID metadata document, its three 404s, and its rate-limit bucket.
9. Disconnect revokes and deletes the tokens. The integrations router runs it before its `DELETE`.
10. No token, code, verifier or cookie in a log line, a log row or a redirect.
