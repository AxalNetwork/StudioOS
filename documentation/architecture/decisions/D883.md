### 3. The guard: `scripts/check-mercury-member-surfaces.mjs`

It runs in `npm run test:guards`. It fails when:

1. **A member page names them.** Any JS or JSX file under `frontend/src/pages/account/` names an Axal entity or the entity accounts or connections, `mercury_entity_connections`, the admin Mercury API (`adminMercury`, `/api/admin/mercury`), the entity sheet (`MercuryEntity…`), or its helpers (`entityRows`, `isEntityRow`, `ENTITY_SOURCE`).
2. **The registry row brings back entity roles.** The `mercury` provider row in `integrations/registry.ts` carries `entity_roles`, or its description names the entity accounts.
3. **The metadata names them.** `CONNECTOR_METADATA.mercury` names the entity accounts.
4. **The registry routes a connector to their table.** `integrations/registry.ts` routes a connector to `mercury_entity_connections` (the old `connection_source`).
5. **The connector pages get an entity variant.** `integrations/connectorPages.ts` gives Mercury an `entity` variant, or `mercuryPage` names the entity accounts.
6. **A member connect route refuses with the entity answer.** `routes/integrations.ts` or `routes/mercury_personal.ts` answers `entity_connection_only`, or names the entity accounts.

**How it reads:**
- **Code only.** A small scanner that knows strings blanks the comments and keeps every line, so a comment explaining the move is never a finding, a string such as `'/api/*'` never opens a comment, and every finding names the file's own line.
- **Prose is not swept.** READMEs are prose, and they say where the accounts went.
- **HQ's own files are never read** (`pages/admin/**`, `routes/admin_mercury.ts`, `services/mercury/**`): that is where the accounts belong.
- **A missing file is a finding.** A file the guard reads that is missing, or a registry without its `mercury` row, fails rather than passing unread.

So the guard checks the result their owners land, whichever way they resolve the conflicts. If a resolution kept C3's `entity` page beside C1's removal, the guard would fail on it.

### 4. Tests

`frontend/test/mercury_member_surfaces_d883.test.mjs` uses synthetic fixture files, never the real pages.

1. **A clean tree passes,** with comments, an HQ file and a glob string in it.
2. **A member page fails** on each of the five kinds of name, at its line.
3. **The registry fails** on `entity_roles` on the row, an entity description, entity metadata, and a routing to the entity table. A commented-out role is not one.
4. **The connector pages fail** on an `entity` variant or an entity tagline. **Both member routes fail** on the entity refusal.
5. **A missing file**, or a registry with no `mercury` row, is a finding.
6. **`codeOnly`** blanks comments and keeps strings and every line.
7. **The repository itself has no findings.** This case is red on `main` until C1–C3 merge, which is the acceptance criterion: it passes after them, and fails when an entity line is put back.
