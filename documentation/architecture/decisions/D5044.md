- **Builds on:** D133 (one holder, enforced), D138 (the Team read), D153 (view-as), D165 (sign out one account), D221 (the transfer's reason; the rail reads what the table read), D259, D262, D530, D4801 (Security v2's result classification), D5040 to D5043.
- **No migration.** One new Worker read; no write bar changed.

### Built (2026-11-09)

**1. The transfer picker has its own read.** `GET /api/admin/super-admins/candidates` (Super Admin, `routes/admin_super_admins.ts`) answers `{ candidates: [{ id, name, email }] }`: administrators who are active and do not hold the elevation, filtered in the query by the rules the transfer route enforces (`not_active`, already a holder), with no LIMIT (D138's reason). `SuperAdminHolders.jsx` reads it through `superAdminCandidatesApi` (`frontend/src/lib/api/superAdminCandidates.js`) and no longer calls `api.hqAdmins()`. The HQ Team page's first load now makes **one** `GET /api/admin/hq/admins`; a frontend test mounts the whole page over a recording `fetch` and counts it.

**2. Holder truth does not wait on the picker.** The holders and the candidates are two independent reads, never one `Promise.all`. A failed candidates read leaves the holders on screen and draws Unreadable beside the picker ("not a claim that there is nobody to hand it to"); a failed holders read is said on its own.

**3. Revoke is not a normal action.** In the one-holder state no Revoke is drawn (the route refuses the last holder and your own row; handing it on is the transfer), and the console says so. With more than one holder (only a database that predates D133) the console says **Invariant broken**, how many hold it, and offers **Remove elevation…** on each holder other than the viewer, as a repair: review with an acknowledgement, then the request, then the server's answer. The page passes `viewerId` so the viewer's own row is never offered.

**4. HqTeamTable is split** into `frontend/src/pages/hq/team/` (its README lists each file). `HqTeamTable.jsx` composes and re-exports the names others import (`MoveHit`, `branchHitStates`, `supportNoticeOutcome`, `SupportNoticeOutcome`).

| File | Holds |
| --- | --- |
| `useHqTeamRoster.js` | The page's one supervision read, with D5042's debounce and generation guard |
| `HqAdminRoster.jsx` | The HQ-held table, its rows and `rosterRows` (complete list, narrowed, worst first) |
| `BranchAccountSearch.jsx` | The branch groups and `MoveHit`, one action panel open at a time |
| `SignOutAccountAction.jsx`, `SupportSessionAction.jsx`, `MoveAccountAction.jsx`, `UnbindAdminAction.jsx` | One destructive action each |
| `governedAction.js`, `ActionNotice.jsx` | The shared state model and how a refusal or an unknown outcome is drawn |
| `teamInvalidation.js` | Which reads each act invalidates |

**5. One state model for every destructive action** (`useGovernedAction`): idle, open (review), submitting, confirmed, refused, unknown. Sign out, Support, Move, Unbind, the holder transfer and the holder repair all use it. Success is drawn only from the server's answer. A thrown request is classified by Security v2's `resultOfError` (`pages/hq/security/accessModel.js`, D4801), reused rather than restated: an answer with a 4xx is **refused** (the route's sentence, via `actionRefusal`); no HTTP status, a 5xx, or no answer within `ACTION_TIMEOUT_MS` (120 s, long enough for the step-up prompt `request()` raises mid-call) is **unknown**, drawn as "Outcome unknown. … Check the account before trying again." and never as done or refused. A request cannot be sent twice while one is in flight, and the send button stays disabled after an unknown outcome.

**6. Explicit invalidation, no page reload.** `teamInvalidation.js` names what each act changes: a holder change → roster and directory; a directory change (role, active state, access) → roster; a branch move or unbind → roster; a sign-out → nothing either list reads. `AccountsPage.jsx` holds one key per read and passes `keys.roster` to the Team table and `keys.directory` to `UsersConsole`, which now takes `reloadKey` and `onChanged` (it re-reads on the page's key and reports its own changes). The handed-over card's `window.location.reload()` button is gone: `leaveHq` (D5040) already takes HQ's screens away.

Authorization and write bars are unchanged: every route keeps its gates, and nothing in the browser decides who may act.

### Departures and limits
- **The Security v2 dialog shell (`security/ActionDialog.jsx`) is not reused.** Its Scope → Review → Result modal is built for Security's bulk acts; HQ Team's acts are inline forms on a row. What is reused is the outcome classification (`resultOfError`), so the two pages say refused and unknown by the same rule.
- **A 502 from a branch route is "unknown".** Security's rule treats every 5xx as unproven. The branch routes' 502 says the branch could not be reached and nothing was done there; the form shows "Outcome unknown" with the rule's sentence, followed by what the server said, rather than trusting that one route's wording.
- **Moves to finish is not invalidated by a move** (D5043): the move's outcome is on its own hit, and relisting it would draw one move twice.
