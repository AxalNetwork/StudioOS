## D7905 part 1 — Executor wiring for the Linux container (#7905)

The trusted executor now runs a `linux-x64` shard inside the per-run container
from D7905 and nowhere else. `runner-execution.mjs` creates the container from
the admitted receipt identity, admits the run again with the adapter that
inspects the live container (`containerIsolationAdapter`), runs the fixed
install and shard driver through `runCandidate`, and removes the exact
container ID in `finally`. The workflow's two host `npm ci` steps skip
`linux-x64`, so no candidate install script runs as the listener account.

Admission runs before checkout, when no container exists to inspect. Its port
(`executor-isolation.mjs`) therefore proves only that the boundary is
available: the reviewed root-owned policy loads, the engine answers, and the
target is `linux-x64` on this repository. That is readiness, not isolation. A
run is authorised by the second, live admission and by `runCandidate`'s own
verification, both before any candidate byte executes.

Mac, hosted and `github-8` get no implementation and keep refusing. The
durable receipt transport (#7887) is still absent, so both CLIs still refuse
at `receipt_authority_unconfigured`; keep that refusal. Still required before
enablement: the reviewed pinned image, and the live credential-denial canary
on the actual node. Test traces written inside the container are not copied
out, so the trace upload step finds nothing for `linux-x64` until a reviewed
export exists.
