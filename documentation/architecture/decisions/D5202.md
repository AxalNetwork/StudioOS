## D5202 — Connected is the credential; whether its events loaded is its own state (#5202)

Part 2 of 7 of the 2026-11-09 Calendar audit (of #3723). P1. No migration.

**What was seen.** The authenticated production Calendar reported **26 of 28 sources answered**, with the Google
and Outlook event reads both failed, while the Connected calendars rail showed both providers **Connected**. D1
inspection had already shown the Google grants carried calendar-readable scopes, so "the scope was never
granted" does not explain it.

**Why the page could say that.** `providerState` promoted an external source failure to the provider's row for
one code only, `reconnect`. A connected provider whose events came back `rate_limited` or `unreadable`
therefore kept its green Connected pill while its events were missing from the agenda — the page had no way to
say "the credential is fine and the events did not load", because it had one dimension where it needed two.

**The two dimensions.**

| | What it answers | Values |
| --- | --- | --- |
| **Connection** (`STATES`, unchanged) | does the credential work? | `reading`, `unconfigured`, `off`, `connected`, `failed` (last copy), `reconnect` |
| **Read health** (`READ_HEALTH`, new) | did the last read of its events answer? | `reading`, `healthy`, `rate_limited`, `unavailable`, `truncated`, `not_read` |

`reconnect` stays with the connection: a withdrawn credential is not a read problem, and counting it in both
places would say the same thing twice. `readHealth(sources, provider)` maps that code to `not_read` for exactly
that reason. A provider with no source row was never asked, which is not a failure.

A connected provider whose read is degraded now renders both — "Google Calendar · Connected · Events
temporarily unavailable" — with the read's own sentence and a retry of its own.

**The retry is scoped.** `reloadProvider(provider)` in `CalendarPage.jsx` asks
`GET /calendar/events?kinds=external_google` (or `external_microsoft`) and replaces that provider's events and
that provider's source row, touching no other source. A rate-limited Google read is not a reason to ask
twenty-seven other sources again, and the member is waiting on this one. The route already took `kinds`, so no
new endpoint exists for this.

**Safe source health, emitted not persisted.** `CalendarSourceStatus` carries, per source: `reason`,
`latency_ms`, `items`, `at`, and the `truncated` flag it already had. `ExternalReadError` gains a `reason`, one
fixed word, so support can tell a provider-wide outage from one account's problem:

| reason | what happened |
| --- | --- |
| `scope_missing` | the stored grant names no calendar scope (refused before any request) |
| `refresh_refused` | the saved refresh token would not exchange |
| `rate_limited` | 429 |
| `http_4xx` | the provider refused the request (401 and 403 are `reconnect`) |
| `http_5xx` | the provider itself failed |
| `timeout` | no answer inside the read's own deadline (`READ_TIMEOUT_MS`, per page) |
| `network` | the request did not complete |
| `bad_body` | the answer was not the JSON object the reader expects |
| `schema_missing` / `threw` | this deployment's own fault, not the provider's |

`readEvidence()` is the page-side reader of that, and it copies only those named fields, so a row that somehow
carried private text cannot leak it onward. Nothing is stored: the issue allows "persist **or** emit", and
emitting needs no migration. "Last successful read" is therefore not available across page loads; that would
need a store of its own and is left out.

**Nothing private travels.** A reason is a fixed word. The failure log is `{ kind, outcome, reason, latency_ms }`
and the source row adds only numbers and a timestamp: no title, attendee, address, join link, token or provider
body. A test asserts that of both the log and the rows, with a provider body and an attendee planted in the
answer.

**What this does NOT do: the live production failure is not repaired here.** This session cannot reach
production, and the repository's rules put production D1 at read-only schema and aggregates. So the live Google
and Outlook reads were not reproduced or fixed. What this delivers is the other half of the audit's first
criterion — the failure is now *exact and visible*: its code, its reason, its latency and its item count, next
to a Connected credential, with a scoped retry. Once production is read with this in place, the `reason` says
which of the nine shapes it is, which is what the repair will need. This is called out on the issue.

**Tests.**
- `cloudflare-worker/test/calendar_read_health_5202.test.ts` (7): a healthy read's count, latency and time;
  each failure shape mapped to its code and reason (429, 5xx, 4xx, bad body, timeout, dead network, 401, 403); a
  scope-less grant refused before any request, and a refused refresh; a disconnected provider having no source
  row at all; one provider failing hiding neither the other provider's events nor Axal's own; a scoped read
  asking one provider only; and no row or log line carrying a title, attendee, address, join link or body.
- `frontend/test/calendar_read_health_5202.test.mjs` (5): the health mapping, the two dimensions rendered
  together, the scoped retry action, the connection states keeping their own wording, and the evidence reader.
- `frontend/tests/visual/calendar_degraded_5202.spec.mjs` (2, desktop and phone): the browser journey the audit
  asked for. A failed Google read with a good credential: the agenda still carries Axal's and Outlook's events,
  the rail says Connected and "Events temporarily unavailable", Retry asks for `external_google` only, and the
  degraded wording clears in place.

Mutations caught: a failed read reading as healthy (the audit's own bug); the scoped retry removed; the evidence
reader passing the whole row through; a 5xx reported as a 4xx; a timeout indistinguishable from a dead network.

**Not in this slice.** All-day semantics, truncation disclosure and server-derived coverage (#5204); the live
production repair, as above; persistence of source health over time.

**One shape grew.** `CalendarSourceStatus` now carries four more fields, so three existing tests that compared a
whole source row with `deepEqual` (`calendar_bot_calls_d1486`, `calendar_compliance_d1384`, `calendar_d1206`)
compare the fields they are about instead. They would have been flaky against `latency_ms` and `at` in any case.
