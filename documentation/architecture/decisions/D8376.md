## D8376 — Reconcile an exhausted capacity publication (#8376)

The capacity owner can recover an existing check after both creation attempts lost their acknowledgements. The request store and result journal remain the authorities for execution, cleanup and reservations. Only the publication intent changes.

### Stop, inspect and drain

Under separate operating authorization, stop intake, engage the capacity kill switch and preserve the service, its result channel and the existing journals while draining. Confirm the explicit kill readback. Record outstanding children, independent termination evidence, reservations and pending negative results. Escalate missing evidence to the operator responsible for the child. An orphan or mode conflict stays retained.

Both the Worker and the Durable Object authenticate these routes with the capacity owner credential. Use the private operator channel. Keep bearer material out of URLs, worksheets and logs.

1. Read `GET /capacity/publications` and repeat with the returned `after` cursor until `next` is null. Sum the counts by reason. Each page covers up to 32 distinct request identities. A request can contribute to more than one reason. Counts describe the observed records over the traversal. Concurrent changes may require another pass. Missing or incomplete intents can include newly arrived work. An unreadable result association contributes to pending negative authority and prevents adoption.
2. For one known retained request, read the same endpoint with `requestId`. Record the publication key, parent attempt, source revision, reasons and fingerprint. An `adoptable: true` response means the local intent is eligible to try. Only the subsequent GitHub read can establish a unique match. If both creates landed and both checks are visible, adoption refuses and the intent stays exhausted. For a full request with one matching visible check, the next publication alarm discovers and adopts it automatically. A compact record with an exhausted intent needs owner reconciliation. Find the proposed check independently. Adoption requires the original mode, two consumed attempts, no known check, and matching retained authority. Zero candidates, multiple matches, incomplete GitHub results, an unknown identity or a changed mode require escalation. Keep the retained evidence and counters.
3. With the explicit kill engaged, submit `POST /capacity/reconcile` with `requestId`, `mode`, `checkId` and the observed `fingerprint`. The service reads the exact parent attempt and verifies the repository name and numeric id, run identity and source revision. It reads the complete source-check list within the existing page bound and requires exactly one match on App id, check name, source and external id. The proposed numeric check id must equal that match. The transaction rechecks the fingerprint before adopting the check. A stale, conflicting or incomplete observation requires fresh inspection.
4. Record the adoption receipt, prior fingerprint, check identity and time in the private audit record. The transaction retains the fingerprint and observation time on the publication intent. Normal publication resumes from its known check id on the prearmed alarm. Verify actual check delivery separately and reconcile each outstanding result, cleanup and reservation before declaring drain complete. Preserve the journal and escalate any unresolved evidence. Destructive retirement requires a separate decision.

Review evidence includes a 37-day retained request, zero, duplicate and mismatched checks, a stale observation during discovery, restart, independently pending cleanup and a successful authenticated adoption. Provider responses and time are simulated. Independent authority and retention review and operating qualification remain pre-enable gates.
