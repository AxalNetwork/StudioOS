### 1. What the file holds

The base scenario, as of the day of the export, in four tables:

- **Plan:** the scenario's name, currency, raise, when it arrives, opening
  cash, plan start, target runway, the runway after the raise, and planned
  spend.
- **Split:** each section's share and amount.
- **Milestones:** each milestone's section, due date, cost and whether it is
  funded.
- **Hires:** each planned hire's role, section, start and annual cost.

Every figure the planning model computes (a section's amount, a milestone's
funded state, planned spend, the runway after the raise) carries `Modelled`
in its source column. A typed figure keeps its own source (`Typed`,
`Recorded`, and so on). A missing value is an empty cell in the CSV and
`Not recorded` in the PDF, never 0. A recorded zero stays a zero. The CSV and
the PDF are drawn from one table model (`planTables`), so they cannot
disagree. CSV cells use the cap table's formula-safe escaper (D1020).

### 2. No Mercury, no measured cash

The issue says Mercury actuals stay out unless the caller is the founder who
owns them. The file leaves out runway today, and every measured or connector
figure, for every caller. It holds only the plan and its modelled runway
after the raise. A file is made to be handed to an investor, so the stricter
rule is the safe one, and the founder's own bank figures never travel in it.

### 3. Who may export, and when not

The router's gate is unchanged: the venture's founder or an admin. A support
session may download, because a GET is a read, but cannot file to the data
room, because the middleware refuses every non-GET. A plan that cannot be
read, including when its hires cannot be read, is refused with 503
`plan_unreadable`. Nothing is half-exported, and no audit row is written for
it.

The plan read now returns `viewer.capabilities: { export, add_to_data_room }`,
in the capability names #5074 lists. `export` is false while the base, its
model or its hires are not readable. `add_to_data_room` is also false for a
support session. The page draws Export only when `export` is true, and the
data-room item only when `add_to_data_room` is true. The Worker still checks
both.

### 4. Audit, and the data room

Each download writes `uof_plan_exported` to `activity_logs` under
`raise.use-of-funds` before the file is answered. That puts it in the plan's
own History (D1177): no audit, no file. "Add to the data room" files
`Use of funds as of <date>.pdf` the way the cap table's snapshot is filed:
under NDA, `access_tier = 'nobody'`, `source_ref = 'use_of_funds'`. The file
row and its audit row (`uof_plan_snapshot_filed`) are one batch, and a failure
removes the stored object. The page then says where the file went.
