## D1381 — Eadwyn AI waits for a founder who has not joined the Zoom call yet, and a refused Zoom pass says why

- **Status:** a fix, found live on 2026-10-29 by the owner. Built by S21.
- **Builds on:**
  - D886 (#2582): the Zoom notetaker's OBF ("on behalf of") token, and waiting for the founder;
  - D1368: a failed run records where it stopped.
- **Migration:** none.

### What happened

The owner pressed Start Call on a Zoom call before joining it, signed in to the Zoom account connected to Axal. Eadwyn AI never appeared.

The run (session 45) failed after 25 s as `platform_blocked@runtime_start`. At start, the bot asks the Worker for its Zoom credentials, and the Worker refused. Every refusal of that request had the same code, `bot_zoom_unavailable`. The bot then reported every failure to start as the same `platform_blocked@runtime_start`. Nothing said which check had failed.

The likeliest cause is one line in `mintObfToken`. Zoom mints the OBF token only while the founder is in the meeting, and the code read every 403 from Zoom as "the grant lacks `user:read:token`" (`zoom_obf_scope_missing`). That refusal is final. A Zoom 403 for "not in the meeting" therefore ended the run at once, instead of waiting for the founder as D886 intended.

### What changed

- **`mintObfToken`** (`services/channels/zoom.ts`) reads Zoom's 403 body. Only Zoom's scope error (code 4711, or a message naming scopes) is `zoom_obf_scope_missing`. Any other 403 is `zoom_waiting_for_host`: the bot waits for the founder, retrying every few seconds for up to six minutes, as for any refusal while the founder is absent.
- **The Worker names each credential refusal** (`meetingBotZoom.ts`, and the run's own check in `MeetingBotRun`). The codes:
  - `zoom_bot_unconfigured`;
  - `zoom_run_inactive`;
  - `zoom_meeting_unread`;
  - `zoom_not_connected`;
  - the provider's code (`zoom_reconnect`, `zoom_obf_scope_missing`, `zoom_unreachable`, …);
  - else `zoom_obf_failed`.
- **The bot carries that code as the failure's detail** (`AdapterFailure.detail`, lowercase codes only). The run then records `obf_unavailable@zoom_not_connected`, for example, through D1368's checked `failure_detail`, never a message. A Zoom join that fails for another reason records:
  - `sdk_refused`, when the Zoom SDK refuses the join;
  - `join_failed`, for any other join error;
  - `host_never_joined`, when the founder never joins within the six minutes;
  - `join_timed_out`, when the join stops at its time limit.
- **Unchanged:** an adapter that fails to start for a reason it does not name still reports `platform_blocked@runtime_start`.

### Verified

- **Worker test** (`zoom_obf_d886`):
  - a 403 naming no scope, or an empty 403, waits;
  - a 403 with code 4711, or a message naming scopes, is still `zoom_obf_scope_missing`.
- **Mutation check:** reading every 403 as scope-missing again fails the new test.
- **Bot tests:**
  - a refused credential request carries only the Worker's code (a code with other characters is dropped, and no message reaches the detail);
  - the runtime reports a named start failure as itself, and an unnamed one as `runtime_start`.
- **Totals:** 130 of 130 meeting-bot tests pass on real Chromium. 91 of 91 Zoom, bot-control, privacy and capture Worker tests pass. `tsc` reports no errors.
- **Deploying:** the bot change needs the meeting-bot image to be redeployed (`meeting-bot-deploy.yml`). The Worker half deploys with the Worker.
