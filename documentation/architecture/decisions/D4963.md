### Optimistic concurrency

`profile_version` is a monotonic revision of the General profile: the fields `PATCH /api/company/:uid` writes, plus the logo. Existing rows start at 1. Every company detail carries it.

- **`expected_version`.** It is optional on `PATCH /company/:uid`, and on `POST`/`DELETE /company/:uid/logo` as `?expected_version=`. When it is stale the write is refused with **409 `version_conflict`**. The body carries `current_version` and the current `company`, and nothing is written. An invalid value is a 400 `invalid_expected_version`.
- **Every write is compare-and-swap.** This holds with or without `expected_version`. The update runs `WHERE profile_version = <the version this request read>` and increments it in the same statement. If no row matched, another write landed between this request's read and its update, and the answer is the same 409. A legacy caller that sends no version still cannot overwrite a write it never saw.
- **Only changed fields are written.** A body that changes nothing writes nothing and keeps the version.

**The General form** sends the version it loaded with every save. It saves the logo first, then sends the fields at the version the logo returned, so a save never trips over its own logo.

On a 409 the form is rebuilt on the conflict's company (`rebaseOnConflict`):

- every value the other editor committed is kept;
- this editor's edits to fields nobody else changed are re-applied;
- an edit to a field both changed is replaced by the committed value and named in the save bar.

The editor reviews the result and saves again.

### One archived rule

**An archived company is read-only until it is restored.**

`companyAccess.archivedRefusal` is the one refusal: 409, with `error` and `code` both `archived`, and one sentence. Every company write uses it:

- **General and logo:** `PATCH /company/:uid` and the logo `POST`/`DELETE`.
- **Team:**
  - member role change and removal;
  - leave;
  - invitations: create, resend and revoke;
  - team people, coverage and plan.
- **Legal:** legal, tax id, officers, locations and slug.
- **Documents:** upload.
- **Compliance:** every non-GET route, through a router guard.
- **Transfer.**
- **Venture moves:** a move into the company, and now also a move out of it.

`POST /company/:uid/restore` is the one write an archived company takes. Reads still answer, so its members see what they are restoring. A non-member is never told the company is archived: the guard answers only for a member, and the handler's own 404 or 403 answers everyone else.

### The audit

Every committed General change writes one `profile_update` event in the same batch:

- **What it holds:**
  - the actor, the company and the time;
  - `after_json.fields`, the changed field **names**;
  - `profile_version` before and after.
- **What it never holds:** no field value is stored.
- **Alongside it:** a rename (`rename`) and a currency change (`currency_change`) keep their own events. The logo keeps its single `logo_change` event (kind of logo before and after); a test pins one event per logo action.
- **Conditioning:** each event in the batch is conditioned on this request's update having matched. That means the new version *and* this request's own `updated_at` stamp. The version alone is not enough: a concurrent writer that won the race leaves the same next version behind. The race test caught that in the first draft.

### Not changed, and why

- **`PATCH /company/me`** already answers 404 on main. `PATCH /company/:uid` is declared first and takes `uid = me`, so the alias never reaches its handler. This change does not touch it.
- **The FastAPI dev backend** is not mirrored, per CLAUDE.md.
- **Project-owned writes** (EIN, receiving accounts) are the venture's, not the company's settings, and are unchanged.
