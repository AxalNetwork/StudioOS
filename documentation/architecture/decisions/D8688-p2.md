## D8688 part 2 — The 390 px browser pass for the role qualification, and the LP applications console that never loaded (#8688)

Part of #8688. Part 1 is `D8688.md` (the local isolated API run, the test territory and the matrix).

**Context.** Part 1 left the matrix's 390 px column at "not run": its session could not fetch a Chromium, and the
visual suite had no server for a branch. The issue asks each scenario for a 390 px check of the starting state,
the saved draft, the return after reload and the next action.

**Decision.**

1. **A separate browser suite, `frontend/tests/qualification/`, not a spec in `frontend/tests/visual/`.** Part 1's
   guard refuses a database that holds any account outside `qualification.invalid`. The visual server's database
   holds other suites' accounts. Seeding the qualification there would mean weakening the guard. The new
   `server.ts` serves the built SPA with the real Worker twice:
   - HQ, over part 1's `hqWorld()`;
   - branch `qa8688a`, over `branchWorld()`, holding HQ's pushed copy of the draft `XQ` licence.

   Both use part 1's own fixture. `provisionTerritory` was lifted out of the Admin scenario so the API run and the
   server provision the territory with the same code. The branch Worker sees its own host, as `assertBranchAppUrl`
   requires. The browser talks only to 127.0.0.1. Every outside request the Worker attempts is refused and counted,
   and a row that causes one fails.
2. **One row per role, signed in as the role itself, at 390 × 844.** Each row checks:
   - start: the seeded starting state is shown;
   - draft: the saved draft is shown;
   - reload: the draft is still shown after a full reload;
   - next action: the control is visible, enabled and inside the 390 px width, and the row taps it where the tap
     is a local record change;
   - every screen: nothing scrolls sideways.

   The Operating Partner's proposal draft is written and saved in the browser. The opportunity sheet has the form.
   The other drafts use the role's own session and the API run's request, because their screens need multi-step
   forms for drafting. The browser then checks what the role sees. The partner's hand-off has no Leads control
   (bidding moved to Proposals, #2338), so the API run's requests make it. After that, Complete is tapped on
   Delivery · Health.
3. **The result is the matrix's `--phone` file.** Each row writes `{ result, evidence }` as it ends, because a
   failed row restarts Playwright's worker. The config clears the file once per run. A failure names the step and
   check that stopped it, never a selector message. `isPublishable` screens every sentence.
4. **The LP applications console is fixed.** `AdminLpApplications.jsx` called `api.adminLpApplications` and
   `api.adminLpApplicationReview`. Both live on `spinoutLab`. Every load therefore threw a TypeError before any
   request was sent, and the console showed "Could not load the queue" on HQ and on every branch. The Admin's next
   action, Request follow-up, is decided in that console. The page now imports `spinoutLab`.
   `founder_journey_entry.test.mjs` had pinned the wrong object; its regex now names `spinoutLab`.
   `admin_lp_applications_reads_8688.test.mjs` checks that each `lib/api` object the page calls has the method it
   calls.

**Not built, and why.**
- **A hosted isolated environment (#7147, #7149).** It still does not exist. The pass runs locally, against the
  same fixtures.
- **CI wiring.** The suite needs `docs/` and a Chromium. Running it on every PR needs a job in
  `.github/workflows/ci.yml`, which this slot may not change (owner T2). The proposed step, beside the `visual`
  job in the same pinned Playwright image:
  `npx --no-install playwright test -c tests/qualification/playwright.config.mjs` from `frontend/`, after
  `npm run build`, with `PW_CHROMIUM_PATH` set as for `visual`. It would then upload
  `frontend/tests/qualification/test-results/role-phone-390.json`.
- **The owner questions from part 1 still stand:**
  - whether a territory Admin should ever be appointed on HQ;
  - whether outside delivery firms keep the studio-wide Build read (D757).
- **The production sign-in release (#8680).** Verified separately.
