## D4133 — The worker test schema is built once per run (#4133)

**Context.** About 180 worker test files each built a SQLite database from
`cloudflare-worker/sql/schema_baseline.sql` and every migration above
`BASELINE_CUTOFF` (413 files today). One build takes 4–10 s on CI and 10–70 s
on a loaded development box, and it was the bulk of the worker suite's time
(D4130 has the profile). Every one of those builds produced the same schema.

**Decision.**

1. **One helper builds it once.** `cloudflare-worker/test/_schema_once.mjs`:
   - `schemaKey(opts)` hashes this file's build version, the baseline, and
     each selected migration's name and bytes. Any change to any of them is
     a new key, and so a fresh build. A cached file is never served stale.
   - `schemaPath(opts)` builds `<tmpdir>/studioos-schema-<key>.sqlite` once
     per run, across every test process:
     - The first process to create `<file>.lock` (O_EXCL) builds into a
       private temp file and renames it into place. The rename is atomic, so
       a reader sees no file or a complete one.
     - The others wait for the file.
     - A lock older than 10 minutes is taken over. A process that waits past
       that builds its own copy instead of failing.
   - `loadSchema(db, opts)` fills a test's own empty handle from that file,
     in this order:
     1. every table, in creation order;
     2. their rows;
     3. indexes, views and triggers, after the rows, so the copy fires no
        trigger;
     4. `sqlite_sequence`, exactly as the build left it.

     The test keeps its own handle, options and copy, so a test that changes
     its schema afterwards changes only its copy.
   - `loadSchema(db, { below: N })` is the schema as it stood before
     migration N. Each bound is its own key and file.
   - `copySchemaTo(dest)` is the file form, for tests that copy a seed per
     case.
2. **153 test files and two shared fixtures moved onto it**
   (`_posthog_cycle_fixture.ts`, `_storage_schema.ts`). The move was
   mechanical: `<handle>.exec(<baseline>)` plus the loop that ran each
   migration on that handle became `loadSchema(<handle>)`, with the loop's
   `< N` bound carried as `{ below: N }`. Every converted file's bound was
   checked against its original. Builds that replayed statement by statement
   and ignored errors now get whole-file builds. The full build runs every
   file whole without an error, so the result is the same.
3. **These tests keep their own build**, because their schema is not the
   shared one:
   - **Leave out named migrations:** `event_badges_restored_d257`,
     `licence_kind_d196`, `sub_cutoff_restores_d190` and
     `user_column_cap_d189` (skip lists), and the three cap-table suites
     (`cap_table_import_d1026`, `cap_table_record_d1017`,
     `captable_scenarios_d1018`, built without `RECORD`).
   - **Stop at a migration chosen at call time:** `grow_writes_d691`,
     `job_comp_public_2181`, `legal_library_coded_d758`,
     `legal_notice_kinds_d716`, `linkedin_connector_d1350` and
     `program_grant_drafts_d956`.
   - **Leave out the learning migrations from 388:** `learning_plan_3959`.
   - **Insert rows partway through the build:** `approval_decisions_d1043`
     and `deck_image_sweep_d1508`.
   - **Test the build itself:** `migrations_fresh_build`.
   - **Read the baseline as text:** `runtime_schema_declared_d235`.
   - **Do not match the pattern:** eight more (`data_room_nda_choice_d1102`,
     `deck_share_null_limit_d895`, `fund_lp_comms_d553`, `kyb_d1231`,
     `learning_video_d561`, `onboarding_checklist_detectors_d184`,
     `onboarding_checklist_repairs_d186`,
     `partner_profiles_single_shape_d187`).

   Any of them can move later by calling the helper the same way.

**What checks it.** `cloudflare-worker/test/schema_once_d4133.test.ts`:
- **Schema:** a database filled by `loadSchema` has the same `sqlite_schema`
  rows as a fresh build.
- **Rows:** every row, `sqlite_sequence` included, matches the cached file it
  was copied from. Each table's row count matches a fresh build. Two builds
  never write identical rows, because migrations stamp `created_at` and draw
  random uids, so rows are not compared against a fresh build directly.
- **Options and isolation:** the handle keeps its own options, and one test's
  change is not seen by another's copy.
- **Keys:** an edited migration, an added migration and a different bound each
  change the key.
- **Race:** two processes racing the first build both get the same complete
  file (`integrity_check` ok), and no lock or temp file is left behind.

The mutations named in the test's comments were each caught.
