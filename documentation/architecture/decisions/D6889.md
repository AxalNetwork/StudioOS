## D6889 — Closing records: actor names, a phone verifier, and the line-to-position link (#6889)

The closing workspace (#6866, canvas D6158) draws three things no read served.
This decision adds them on the Worker. The workspace shows them once #6866's
page (PR #6892) is on main; that wiring is a later part of #6889.

### 1. The actor's name on closing events

`readClosing` (`services/closings.ts`) now joins `users` and returns
`actor_name` beside `actor_user_id` on each event.

- **Who reads it.** The events' own rule, unchanged: an admin and the
  venture's founder (reach `all`) read events; an investor reading through a
  line of their own (reach `own`) reads no events, so no names.
- **No name.** An actor whose account is gone, or has no name, reads `null`.
  The page says "Not recorded", never another name.
- **Stored events are unchanged.** `closing_events` still carries no name;
  the name is joined when the closing is read.

### 2. A phone verifier apart from the recorder

Migration `202611161150_6889_deal_transfer_phone_verifier.sql` adds
`deal_transfers.phone_verified_by INTEGER REFERENCES users(id)`, nullable,
with no backfill.

- **Existing rows.** They keep `NULL`. The verifier was never recorded for
  them, and nothing is guessed from `recorded_by`.
- **The write.** `POST /api/deals/:id/transfers` takes an optional
  `phone_verified_by`, an Admin's user id (a JSON integer). The gate is
  unchanged: an Admin records, under `closing.evidence`. The write refuses
  with 400, writing nothing:
  - `phone_verifier_without_verification` when `phone_verified` is not `true`;
  - `phone_verifier_invalid` when the id is not an integer, or names no
    Admin (an Operating Partner, an investor, an unknown id).

  Phone-verified with no verifier named is still recorded, and the verifier
  reads `null` (Not recorded), as before this change. The verifier may be
  the recorder; nothing requires a second person (see Open question).
  The deal-room audit row for the transfer carries `phone_verified_by`.
- **The reads.** `GET /api/deals/:id/transfers`, `GET /api/deals/transfers`
  and the write's own answer return `phone_verified_by` and
  `phone_verified_by_name`. Those reads already return the recorder's name
  to the same readers, so the verifier's name reaches no one new.
- **The client.** `frontend/src/lib/api.js`'s `dealTransferRecord` passes
  its body through, so it needs no change. No transfers module exists under
  `frontend/src/lib/api/`. The Record transfer dialog field comes with the
  workspace part.

### 3. A closing line's Portfolio position

The only reliable key is `portfolio_positions.closing_line_uid` (migration
612). `POST /api/positions` writes it when the Admin names the line, and
checks that the line belongs to a closing of that venture. `readClosing`
reads the first position (by id) that names each line.

- **What each reader gets.**
  - An admin: `in_portfolio` (true or false) and `portfolio_position_uid`
    (the position's uid, or `null`).
  - The founder: `in_portfolio` only. Positions are a fund's record (D1057),
    and `/api/positions` is not the founder's read.
  - An investor: neither field.
- **No guessed link.** A position recorded without naming the line does not
  link, even on the same venture and round. Matching by venture, round name
  or amount would guess, and a fund's position need not be one investor's
  line. Positions recorded before 612, or without a line, therefore read
  `in_portfolio: false`.
- **Closing creates no position.** The canvas's Record position action is
  still `POST /api/positions` with `closing_line_uid`.

### Tests

`cloudflare-worker/test/closing_records_6889.test.ts` (5 tests) covers:

- the actor's name for an admin and the founder, `null` for a missing
  account, and no events for an investor;
- the migration's column, foreign key and missing backfill;
- the verifier written and returned by all three transfer reads, and the
  verifier left out;
- both refusals, with nothing written;
- the Portfolio link for each reader, including that a position naming no
  line links nothing.

The hand-written `deal_transfers` schemas in `deal_closing_money`,
`deal_preparation_5454`, `deal_rooms_d630` and `deal_transfer_firm_d467`
gain the column or run the migration.

### Open question

Should the phone verifier be required to differ from the recorder (a second
person on every phone-verified wire)? This change records who verified, and
does not require a second person.
