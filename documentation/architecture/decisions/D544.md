## D544 — The Super Admin's review queue for feature requests and suggested tasks

**A support ticket of type Feature waits for the Super Admin to approve or
decline it before anything is built. A ticket of type Task is a suggestion
that, once approved for an audience, is published to the community task list
and pays its suggester. Every decision is recorded once, with a typed reason,
whatever GitHub answers.** Issue #1107, slot S08, part of #1101. Migration
383. This entry covers the store and the API; the HQ page waits on its design
(`needs-design`).

**What was true on main.**
- `POST /api/tickets` (`routes/tickets.ts`) filed a ticket with a type and
  mirrored it to GitHub with a `bug`, `feature` or `task` label.
- Nothing acted on the type.

**What changed.**
- **Migration 383.**
  - **`community_tasks`** holds `id`, `ticket_id` (unique), `title`, `body`,
    `audience`, `status` (`pending`, `approved` or `declined`), `decided_by`,
    `decided_at`, `decline_reason` and `created_at`.
  - **Two triggers write a ticket's pending row.** One fires when a ticket is
    inserted as a task; the other when one is re-typed to a task (the GitHub
    label sync can change `type`). The ticket form (#1022's) is untouched.
    Tickets filed before the migration get no row, so the queue starts empty
    rather than holding every ticket that ever defaulted to `task`.
  - **`feature_request_reviews`** holds the decision on a feature request:
    `status`, `decided_by`, `decided_at`, `decline_reason` and
    `label_status`. It is stored here, not only as a label on the mirrored
    issue, because the label is a GitHub call that can fail or be
    unconfigured.
- **`routes/admin_ticket_reviews.ts`**, at `/api/admin/ticket-reviews`, all
  behind `requireSuperAdmin`:
  - **`GET /features` and `GET /tasks`** list what is undecided. Each item
    carries its text, who asked (the account's id, name and email), the
    priority, the date, and the mirrored issue's link.
  - **Approving a feature** records the decision and adds the
    `feature:approved` label to the mirrored issue. Session 1 then files the
    build task. The label goes through a new `addLabels` in
    `services/githubSync.ts`, which POSTs so the issue's type and priority
    labels stay (`setLabels` PUTs, which replaces them all). The user is told
    it is approved, "not a promise of a date".
  - **Declining a feature** adds `feature:declined` and sends the user the
    reason. `label_status` records `added`, `no_issue`, `not_configured` or
    `failed`, and the response says it.
  - **Approving a suggested task** needs an audience: `all` or one persona,
    `founder`, `investor`, `advisor`, `partner` or `explorer` (the chat's
    `Persona`, less admin and unknown). It publishes the task for #1108 to
    list, and pays the suggester `task_approved` through D540's
    `grantCredits`, with the Super Admin as actor. The grant is keyed
    `task:<id>`, so it is paid once. A staff suggester's task is published
    and pays nothing.
  - **Declining a suggested task** records the reason and sends it.
  - **Every decision:**
    - takes a reason of at least ten characters;
    - is logged through `logAdminAction`;
    - happens once. A second decision on the same request is a 409, with no
      second label, payment or notice.

**Noted, not changed.** `Task` is also the ticket type the general Tickets page
(`TicketsPage.jsx`) defaults to, and the type `validateTicketCreate` assumes
when none is sent. So ordinary support requests filed there as `task` will
enter this queue too, for the Super Admin to decline. That form is #1022's.

**Not built here.** The HQ "Review queue" page (Features and Suggested tasks
tabs) waits on the owner's approval of the canvas whose prompt is on #1107.

**Verified.**
- `cloudflare-worker/test/ticket_reviews_d544.test.ts` (10 tests) runs the
  real router over migration 383 (its triggers included) and D540's rules,
  with GitHub stubbed. It covers:
  - which tickets make a pending row, once;
  - the Super Admin gate on all six routes, with no GitHub call and no change;
  - the queue's contents;
  - each approve and decline path;
  - the label as an added label, not a replacement, and its state when GitHub
    fails, is unset or has no issue;
  - the reason floor;
  - the audience;
  - the task reward paid exactly once, with the Super Admin as actor;
  - a staff suggester paid nothing;
  - a decided request refusing a second decision.
