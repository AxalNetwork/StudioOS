## D7885 — Verified runner bootstrap and capability profiles (#7885)

This is the bootstrap stage of #7884. It does not activate production routing.
#7882 was initially inspected at ec9eb07ced2ea69b31dd6f025a3a465d21313c84
and subsequently landed as 595b2d26145c35806ef9483393836a4098e360f4 while

useful groundwork, not proof of extra hosted-slot capacity.

The schema v1 profile file defines linux-x64, macos-arm64 and a separate hosted profile targeting
ubuntu-latest. Self-hosted selection is the AND of default actual OS/
architecture labels and studioos-worker-v1 in one restricted group. A proposed
StudioOS Worker Pool group needs administrator confirmation; no group is created,
renamed or broadened here. Names are random stable inventory identifiers, never
hostnames or runs-on labels. One registered listener process per machine is the
initial limit. More processes do not create hardware capacity.

Pins: Actions runner 2.338.2, Node 22.23.3 and CPython 3.11.18 from `python-build-standalone` release 20261110. Per-platform SHA256 digests come from the linked
upstream release metadata/Node SHASUMS in profiles.json. Downloads are verified
before extraction/execution; paths, links and special archive members are checked.
Git 2.39 through 2.x is supported. The small bootstrap controller uses the OS's
root-owned /usr/bin/python3 (3.9+); job Python is the separately pinned binary.
The current organization's available runner version is unverified (403), so an
operator confirms the pin against its Runners download instructions before use.

A separate non-root listener owns registration/OAuth files, protected from the
separate job account. This is a preparation boundary, not a claim that a normal
host job changes Unix identity automatically. #7886 must enforce and prove that
candidate code runs as the job identity, has only its owned job workspace/cache,
and leaves no surviving processes. Same-UID native host execution can read the
listener's credentials and is not acceptable. No executor, sudo broker, container
policy or caller is added by this issue. The main-published executor and isolation
proof are mandatory operator prerequisites before registration/start.

Registration accepts short-lived material only through FD >=3. It is passed only
in the private configuration process environment, never argv, stdout, public
logs, service environment or state JSON. Child configuration output is suppressed.
The listener's runtime OAuth files are required by GitHub but stay private to that
identity. Operator/provider/App credentials are not installed into the listener or
job environment. Unknown CLI/receipt input is refused without echoing values.

The operator receipt is root-owned mode 0600, at most 15 minutes old, bound to the
stable identity, exact organization/repository/group and directly defining main
workflow, with an immutable executor revision/content digest. Main ancestry and
file content are independently read from public GitHub metadata. A repository-only
registration, incomplete registration or wrong group is refused, never repaired
by weakening selection. Existing valid registration is observed without making
another; this local observation does not assert remote eligibility.

Install resumes completed verified artifacts; unmarked partial destinations fail
closed for operator recovery. Service files are root-owned; start is idempotent,
restart needs a fresh drained receipt, and a bounded supervisor stops the pilot
at its approved deadline (at most 24 hours). Linux approval also confirms provider
teardown was scheduled privately: stopping a service does not stop VM billing.
Removal requires drain/stop; revoked-enrollment cleanup needs an explicit private
operator receipt. Job data/caches and accounts are retained for deliberate operator
handling, rather than deleted through an unchecked path.
