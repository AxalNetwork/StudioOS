### 1. The run

`POST /api/cycles/build/plan/word?project=&scope=`:
- one `rail_write` run through D765's `run()`, under the page `Founder · Build` and the option `draft:build/plan`;
- metered (D640) and recorded on the surface `/build/plan` (`AI_SURFACE.buildPlan`);
- the venture's founders only. An admin and anyone else is 404 `not_this_project`, as D1065's preparation is.

**It runs only on the press.** Nothing scheduled, prepared or accepted calls it; a test pins that the prompt is built in one route handler. In Manual mode `run()` refuses it, so it answers 403 `assist_off` and nothing is run. An empty purse is 402, and the other refusals follow `refuseRun`.

| Answer | When |
|---|---|
| 409 `no_plan` | no plan is prepared |
| 409 `plan_paused` | the plan is paused |
| 422 `nothing_to_word` | no item is pending |
| 422 `nothing_kept` | every worded field was screened out (§3); nothing is stored |
| 503 `ai_unavailable` | the model could not be reached; nothing was charged |

### 2. What Eadwyn reads, and what it may word

**Eadwyn words; the rules decide (#2426 owner question 2, A).** The model gets the pending items the rules proposed, each under a short ref (`i1`, `i2`…), never a uid. It answers wording for those refs only. A ref it invents is dropped, so it never adds, removes, merges or reorders an item. A door to connect a tool is never sent.

| Kind | Worded |
|---|---|
| feature | title, description |
| must-have, prototype test, risk, roadmap, formation step | title |
| the brief | a summary |
| the plan | the Lovable prompt |

**Labels and counts only.** Each item is sent as its kind, its module, the rule's title (already `planLabel`ed by D1065) and its evidence. The evidence goes as kinds with counts and their labels, `planLabel`ed again, which strips quotes, contacts, links, dates and amounts. A decision and a commitment are counted and never worded. The brief goes as its audience, problem, positioning and replaces labels. No transcript, quote, interviewee name, decision reasoning or date reaches the model; the test checks for each.

**The prompt forbids:**
- numbers, dates, prices and amounts;
- names and quotes;
- saying whether to proceed, pivot or stop;
- equity, shares or ownership.

### 3. What leaves

`screenWording` drops any worded field that holds a digit, a currency sign, `%`, `@` or a link, and the answer says how many it dropped (`removed`). A field the kind does not take is ignored, and each field is cut at its limit on a whole word:

| Field | Limit (characters) |
|---|---|
| title | 200 |
| description | 600 |
| summary | 600 |
| prompt | 4,000 |

### 4. The wording row

The run stores one `ai_rail_proposals` row:

| Column | Value |
|---|---|
| `kind` | `draft` |
| `rail_page` | `Founder.Build.Plan` |
| `rail_option` | `draft:build/plan` |
| `record_ref` | `build_plan:<plan uid>` |
| `payload_json` | the screened wording, by item uid |
| `model`, `usage_log_id` | the run |
| `decided_payload_json` | `{ kept, discarded }` |

A newer press withdraws the founder's pending wording on the plan, so wordings do not stack. **Nothing else is written:** the items' proposals, Build and `fill_provenance` are unchanged until the founder keeps something. `GET /word` reads the latest wording back, without the targets already kept or discarded.

### 5. Keep wording and Discard wording

| Target | Keep wording | Discard wording |
|---|---|---|
| an item | **its Save:** `PATCH /items/:uid { wording: <wording uid> }`. `POST /word/:uid/keep` refuses an item (400). | `POST /word/:uid/discard { target: <item uid> }`. The rule's title stands and the item is untouched. |
| the brief or the Lovable prompt | `POST /word/:uid/keep { target }` records it on the wording row | `POST /word/:uid/discard { target }` |

**Keeping an item's wording.** D1066's PATCH, extended:
- It takes the wording's words for that item as the edit, with the founder's own `payload` keys over them.
- It checks the edit against D1066's editable fields, as any edit is.
- It saves the result with `wording: { uid, usage_log_id }` on the payload.
- The item stays proposed, and no Build row is written.
- The wording row records the keep and becomes `accepted`.
- A wording that is not on the item's own plan, or not the founder's, is 400 `invalid_edit`.

**The founder's own words win.** A later edit that changes a title or a description drops `wording` from the payload: the run no longer wrote those words.

**Accept names the run (D777).** When the saved payload carries `wording`, each `fill_provenance` row for a worded column (`title`, `objective` and `description`) gets:
- `ai_usage_log_id`, the run;
- `wording: { proposal_uid, usage_log_id }` in `citation_json`.

The other columns name no run. A feature's `description` is now one of the fields Accept carries, so it gets a provenance row when it has a value. **Where the kept brief and prompt go:** part 5 reads the kept prompt from the wording row when it sends to Lovable. Nothing here sends to a tool.

### 6. VB5 on the plan page

`PlanWording` is a standalone panel on `/build/plan`, under the plan's wait line. Part 6 (#2939) can fold it into its item cards.

**What it draws:**

**Each pending item** shows its module and the rule's plain title. When there is wording, it is drawn in lavender:

**The brief and the Lovable prompt** get the same lavender card. Manual mode and an empty purse each say so, the second with a top-up link.
