## D8692 — The merge-queue provenance range is bound to the candidate it reports on (#8692)

**Context.** D8068's `provenance` job runs on `merge_group` as well as on `pull_request`. On a
queue run it did not know which pull request head the candidate was built from. It read the
pull request's current head from the API twice, fetched `refs/pull/<n>/head` and compared the
two. That only proved the head had not moved between two reads a moment apart. If the head
changed after the queue built the candidate, the job checked commits that are not in the
candidate and reported the verdict on the candidate's commit.

How the queue builds candidates (main's ruleset, read 2026-11-25): `merge_method: SQUASH`,
`max_entries_to_build: 5`, `grouping_strategy: ALLGREEN`. A candidate is one squash commit on
`merge_group.base_sha`. That base is main, or the candidate ahead of it when entries stack: in
the 25 squash commits at the top of main on 2026-11-25, several bases were another candidate
(#8657's base was #8658's candidate, #8651's was #8657's). In all 25, the candidate had one
parent, its base, and its tree was
`git merge-tree --write-tree <base> <pull request head>`.

**Decision.** On `merge_group` the head is the fetched `refs/pull/<n>/head`, and the job proves
it is the one the candidate (`merge_group.head_sha`) was built from before it checks anything:

- the candidate's only parent is `merge_group.base_sha`, as given, so the proof works for a
  candidate stacked behind another and does not depend on what main is at that moment; and
- `git merge-tree --write-tree <base> <head>` exits 0 and writes exactly the candidate's tree.

If either fails, the job fails and names the head, the candidate and the base. It never falls
back to checking the current head. A head that conflicts with the base is refused.

The proof is `node scripts/ci/agent-provenance.mjs --bind --base <sha> --head <sha> --candidate
<sha>`. The workflow runs the base copy of the script when that copy accepts `--bind`, as it
does for `--pr-merges` (D8606). Until main carries this change, the candidate's own copy runs
it. The API is now read once, for the branch name only (`.head.ref`). The current head is never
read from the API.

**Why this proof.** Nothing else ties the candidate to a pull request head. The `merge_group`
event names the candidate, its base and the queue branch. The queue branch carries the base
sha, not the head. The API reports only the current head. The tree is what the squash keeps,
so a matching tree is the strongest binding git can give. A head that is not the one queued
but merges to exactly the same tree would still pass. Such a head merges exactly the content
the candidate holds. GitHub also removes a pull request from the queue when its head moves.
Checking the parent as well as the tree means a candidate cannot be paired with the wrong
base: a candidate that is not one commit on the given base is refused, even if its tree matches.

**Unchanged.** The `pull_request` path still takes the event's head and refuses a moved one.
`continue-on-error: true` stays; making `provenance` required is the owner's ruleset change
(D8068). The #8606 exemption keeps working: the range is still `base..head`, the pull-request
merges in it are listed from the API as before, and the trailer rules are untouched.
