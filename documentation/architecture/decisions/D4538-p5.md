## D4538 part 5 — Explicit rebase choices create an extension draft on a newer Axal base (#4538, #5965)

### Contract recorded before implementation

SK-20 in the approved D5963 Extension Compare canvas offers Keep mine, Take Axal
and Edit by hand per conflicting part. It compares the company's latest published
version (its draft only when never published), not unpublished edits. Rebase is
`POST /api/teams/skills/:uid/rebase`, where uid is the company extension.

Body: `{ version, expected_draft_hash, resolutions }`. `version` is the exact
newest published Axal version shown in the comparison; a newer publish requires
reloading rather than applying unreviewed changes. `expected_draft_hash` is the
64-character hash from the company editor's skill card and is required here:
creating the new draft replaces existing draft edits. `resolutions` is an object
keyed by conflicting part (`name`, `purpose`, `steps`, `tools`, `output_kind`,
`tags`, `roles`). Each value is `{ choice: 'mine' }`, `{ choice: 'axal' }` or
`{ choice: 'edit', value: <that part's normal draft value> }`. Every conflict
must be chosen; missing choices return `conflict_unresolved` with `part`.
Unknown parts, invalid choices or choices for non-conflicting parts are refused.

A part changed only by Axal comes from the new base; one changed by the company
stays the company's; identical changes stay identical. A manual value is checked
with the same `checkDraft` validation as a normal draft. Tools must be a subset
of the new base, even for Keep mine or Edit by hand (`tool_not_in_base`). There
is no line merge or silent conflict resolution. The response is `{ skill,
base: { uid, version } }`; the skill is the normal editor card with its new draft.

### Storage, history and permissions

No migration is needed. `agent_skills` already stores the mutable draft and its
`based_on_version`, while each immutable `agent_skill_versions` row preserves
its own `based_on_version`. Rebase changes the draft fields and the skill row's
base pointer together. Publish already copies that pointer into the new version.
Until publish, `based_on` names the draft's base; historical versions retain their
original bases and agents retain their exact pins. The original fork reason is
preserved. No published version, pin, Axal row, or Axal draft is written.

Only the extension company's own editors may call it; HQ is explicitly refused,
even if it has a company seat. A different company gets 404. A standalone skill
cannot be rebased; retired extensions/bases, no newer version, suspended targets
and unreadable old/new base versions are refused. Archived companies are read-only.
The route reuses `threeWay`, `baseOf`, `versionParts`, `checkDraft`, `draftGuard`
and `auditDraft`. A transactional guard also protects the lineage, published
comparison version and Axal target from changes between read and write. A stale
draft answers `draft_conflict` as PATCH does; stale comparison/base state requires
reload. The audit records actor, before/after hashes, old/new base and choices,
including a base-only change whose definition hash stays identical.

`teamAgentsApi.rebaseSkill(uid, body)` ships with this route. Comparison UI and
base/extend methods remain #5964's. This task adds no screen, Help flow, live
skill update, model call or deployment.

### Validation

The dedicated SQLite route suite covers all seven conflict parts, all three
choices, non-conflicting/equal changes, draft-only operation and later publish
lineage, immutable Axal/company history and pins, tools, permissions, unreadable
base/history, retired/suspended/no-update states, mandatory/stale hashes, and
concurrent draft/comparison changes with rollback. A frontend fetch fixture
checks the mounted route, encoded uid, POST and exact body. Mutation checks
exercise permission, conflict, merge, tool, history, audit and concurrency
regressions. All records and keys are synthetic local fixtures.
