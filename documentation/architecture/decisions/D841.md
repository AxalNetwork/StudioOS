## D841 — Member API keys for axal.vc/mcp: a hashed, scoped, revocable second credential beside OAuth

- **Status:** filed by S21 for S1 as #2464, part of #2463. This is the first task of the MCP platform plan (`documentation/architecture/MCP_API_PLATFORM.md`).
- **Basis:** `origin/main` at `56c2498983`. Worker paths are relative to `cloudflare-worker/src/`.
- **Stacks on:** D665 and D666 (the MCP server and its OAuth grants), D784 (`/mcp` is its own address), and D527 (one API module per domain).

### 1. The decision

The owner, 2026-10-21, asked for "a production-grade API key system so users and authorized workspaces can generate keys to access Axal's MCP endpoint and supported Axal APIs". Until now `/mcp` accepted only OAuth tokens from assistants that sign in. Settings returned `api_keys_enabled: false` with an empty list (T20).

A member key is a **second credential for the same principal**, not a second permission system:
- it reaches only ventures the member owns (`grantableCompanies`, as OAuth consent does);
- it carries only scopes the MCP server defines (`SCOPES`, today `validate:read` and `validate:write`);
- it is re-checked on every use, as a grant is.

This task builds the keys and their management. #2470 (D842) makes `/mcp` accept them.

### 2. What was built

- **Migration 523:** `member_api_keys`. The table holds:
  - `key_id` (public, unique, 12 characters) and `secret_sha256` (never the secret);
  - name, scopes, companies and an optional per-key monthly AI token cap in micro-USD;
  - the per-minute rate, expiry and the revocation fields.
- **`services/apiKeys.ts`:**
  - **Format.** A key is `axk_<key_id>_<secret>`: a 12-character id from `[a-z0-9]` drawn by rejection sampling, and 32 random bytes as base64url.
  - **Verification.** It parses the bearer and reads by `key_id`. It always hashes the presented secret, so a miss and a mismatch cost the same, then compares in constant time.
  - **Answers.** Any failure before the secret matches answers `invalid_key`. Only the holder of the right secret learns `revoked_key` or `expired_key`.
  - **The account behind the key.** The account must be active, with no deletion request. A "sign out everywhere" (`jwt_min_iat`) after the key was made ends it, as it ends grants.
  - **Last use** is written at most once a minute.
- **`routes/developer_keys.ts`,** at `/api/developer/keys`: list, create, revoke and rotate, as plan §3 states.
  - Session only: an `axk_` bearer gets `401 session_required`, so a key can never manage keys.
  - A support session cannot change keys.
  - At most 25 live keys per member.
  - Every write logs `api_key_created`, `api_key_revoked` or `api_key_rotated` with the key's uid only.
- **Rotation** revokes the old key and inserts the new one in one batch. The insert is conditional on the revoke, so a racing revoke or rotate leaves no orphan. The new key keeps the name, scopes, limit and remaining expiry, and keeps only the companies the member still owns.
- **The flag `API_KEYS_ENABLED`,** set to "false" in every environment of `wrangler.toml`. While it is off, every route answers 404.
- **The client** `frontend/src/lib/api/developerKeys.js` (`developerKeysApi`). There is no page yet: the UI is #2463's Saturday work.

### 3. Why SHA-256 and not a password hash

The secret is 256 random bits, not a human choice: no dictionary or brute force reaches it, so a slow hash (bcrypt, scrypt, PBKDF2) adds per-call cost and no security. GitHub, Stripe and others hash high-entropy tokens the same way.
