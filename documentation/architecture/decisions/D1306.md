### 1. The drawer's tabs (ACC4–ACC6)

The drawer keeps D1299's address, `/admin/accounts/all/:id`. Its tabs come from `DRAWER_TABS`, in this order: Profile, Sub-accounts, Identity, Agreements, Registration, Onboarding, Conversations, Activity, Notes.

- **Profile:** the account's profile name and ID, and one line for its onboarding profile (D989): its verdict and date (D991, migration 557) and a link to Partner profiles.
  - The line comes from the profile read's new `onboarding_profile`. The read looks first for the account's own row (`user_id`), then for a row from before the account existed, matched on the address in any case.
  - `null` means there is none. `{available:false}` means the store could not be read, and the rest of the record still loads.
  - No address reaches the answer.
- **Sub-accounts (ACC5):** D1302's `GET /api/admin/sub-accounts/accounts/:userId`, read-only as D1302 §6 says. Each decision is a link:
  - the Product tester record links to Approvals › Product testers;
  - the LP status links to LP applications.
  - A failed read says so with Try again. It is never drawn as "none".
- **Identity:** the identity check, provider, email verification, two-step and ID document, plus the limited-access line.
  - Resend verification is drawn only while the address is unverified, and it opens a dialog.
  - Identity is decided in KYC & KYB, which the tab links to.
- **Activity:** says "Showing the latest 100." The read is capped at 100.
- **Notes (ACC6):** labelled "Notes only admins see". It carries a "Last saved on … by …" line from D1303's `notes_saved`; until D1303 is on the database the line reads Not recorded and says why.

### 2. Every change is an in-page dialog (ACC7)

`window.confirm`, `window.prompt` and `alert` are gone from the console and from `accounts/`. The D1306 test greps both for them. Every change now opens `AccountDialog`, which shows what the change does and who is told, with a reason where the Worker wants one (at least ten characters):

| Change | Reason | Sends |
|---|---|---|
| Profile (role) | — | `PATCH /admin/users/:id/role` (a move to `exploring` opens its override dialog, `setRoleOverride`, instead) |
| Grant full access without an identity check | required | `PATCH /kyc/admin/:id/approve` with `{reason}` (D1303) |
| Grant / revoke limited access | — | `adminSetAccessLevel` |
| Deactivate | required for an administrator (D247), optional otherwise | `adminToggleActive(id, reason)` |
| Reactivate | required for an administrator | `adminToggleActive` |
| Resend verification | — | the existing resend |

A refusal stays inside the dialog as one sentence. The dialog stays open and nothing is assumed to have changed. The dialog closes, and the list reloads, only when the change has answered. The support session and role-override dialogs keep their own errors inline the same way.

Another administrator's account draws no Disable for a plain Admin (`drawsAccountControls`, D221). So there is no "refused" dialog to open; a 403 that still comes back is shown as "Only a Super Admin can change another administrator’s account."

**Support session.** The scope reads "Read and write, as this account". The length row reads "30 minutes. You can extend it, up to 120 minutes in all." Its two constants are tested against `auth.ts`'s `IMPERSONATION_EXPIRY_MINUTES` and `IMPERSONATION_CEILING_MINUTES`.

### 4. ACC13

- **ACC13a.** An administrator's record is the Super Admin's: the profile read answers 403 `super_admin_required` (D133). The drawer shows one panel that says so and names the account as an administrator, and draws no controls. Any other failed read says Unreadable with Try again.
- **ACC13b**, a viewer who is not a studio admin, was already met by D940's `AdminOnlyNotice`. Nothing is added for it.
