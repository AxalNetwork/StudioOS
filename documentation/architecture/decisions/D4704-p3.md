## D4704 part 3 — Practice domain services and bounded detail (#4704)

Build on the merged #5114 route split and #5194 money-report definition.
#4692's actor/time work has landed, so the booking lifecycle can now move too.
The independent frontend sections and their state wording still wait for
#4829's committed canvas; part 2's explicit cleanup is the permitted exception.

The Worker domain services take the environment and plain values. Routes keep
authentication, their existing narrow ownership gates, parsing, response status
and execution-context calendar scheduling. `PracticeRefusal` carries a domain
refusal as data; only a route creates an HTTP response from it.
Booking routes preserve the original success order: change and audit the row,
defer calendar work, then read the response. Unexpected failures still reach
the application's existing global error handler.

| Service | Authority |
| --- | --- |
| `advisorAvailability.ts` | List eligibility uses the existing pure `advisorBookingRules.ts` engine; occupancy and recorded price kinds use one grouped read per slot list. |
| `advisorBookingLifecycle.ts` | Booking policy, conditional status update, recorded decision, cancellation side and actor/time audit; calendars remain deferred at the route. |
| `advisorEngagements.ts` | Descriptive corrections, lane graph, signing, per-term renewal decisions/replays, history and full-population reporting. |
| `advisorDistribution.ts` | Derived work-product state, send-time recipient identity, client-only first-open/sign-off receipts, owner/recipient lists and complete metrics. |
| `advisorBilling.ts` | Included sessions, explicit repricing, immutable settled snapshots and guarded price-event writes. Existing `advisorMoney`, `advisorConnect` and `practiceReporting` remain the arithmetic, provider and reporting authorities. |

No duplicate ledger or rule engine is introduced. Reservation INSERT guards,
booking compare-and-swap, renewal uniqueness/replay, price-event batches,
write-once recipients/receipt actors and the advisor/client DTO boundary are
preserved. Existing route-module exports remain available to their importers.

Engagement detail is selected with SQL limit/offset; small grouped counts
compute totals over every engagement. Deliverable detail selects only the
requested page and batches its versions; database aggregates cover every work
product. Opening time still uses the first opened version by version number;
rounding the SQL time difference to milliseconds preserves the existing
JavaScript rounding at a half-tenth of an hour. Recipient lists batch versions,
paginate and report totals over all versions actually sent to that recipient,
including after an engagement is relinked. Renewal events and term corrections
form one paginated chronological history instead of two silent 200-row caps.
Its default is 400 combined rows, preserving the previous maximum response
size; callers can request a smaller page and follow `page.next_offset`.

Existing list fields and totals retain their meaning. Additive `population`
metadata explicitly names the complete engagement, owner-deliverable and
recipient-deliverable definitions. `page` supplies total and next offset for
recipient lists and combined history. Detail pages may change between requests
when records change; this does not promise a cross-request snapshot.

Eight new mounted SQLite fixtures cover first use and literal-route precedence,
501-slot batching/privacy, 401-row engagement/work-product pages, recipient
relink/draft isolation, history beyond both former caps, and median rounding.
Existing fixtures cover reservation races, stale transitions, renewal replay,
corrections, receipts, recorded billing and shared report definitions. A new
negative participant fixture also proves that the wrong party cannot transition
a booking or leave an actor record. Source
guards follow the imported domain services so moving a rule does not remove
its assertions. Thirty-one behavioral mutants were caught by assertions,
with passing controls and restored sources, including the booking participant
gate, stale writes, audit records, renewal replay and settled-price lock.
Failed writes schedule nothing; a successful change still schedules its calendar
work when the final response read fails. Mutants cover both ordering errors and
accidental remapping of unexpected failures.
Full-run results and the mutation logs accompany the review package.
