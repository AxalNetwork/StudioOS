## D680 — Contact, the three legal pages and cookie preferences, built to the owner's website canvas

Issue: #1554. Part of #1546 (D673). Source: `design/canvases/integrated/Axal VC Website.dc.html`, views CONTACT, LEGAL PAGES and COOKIE PREFERENCES, with `INTENTS`, `contactRoutes`, `LEGAL` and `cookieRows` from its logic script.

### What was built

- **`/contact` (`ContactPage.jsx`)** follows CONTACT, inside `SitePage`:
  - "Get in touch", "Tell us what you are building.", the lede;
  - the three ways in, with the canvas's addresses: founders@axal.vc, guillaume.lauzier@axal.vc and network@axal.vc, each a mail link;
  - the form card: "Application enquiry", the intent pills (Spin-Out Lab, Investing / LP, Advising), the five fields with the canvas's placeholders, and "Send enquiry →";
  - "Everything you send is confidential. We do not share applications outside the fund team." under the button, which is true now that submissions stay off GitHub (below);
  - the sent state: the tick, "Received." and the canvas's reply line, then the stored submission's reference and "Send another enquiry". The old "Reference: tracking link" pointed at a public GitHub issue and is gone.
- **The form posts to the existing `POST /api/contact`** through `request('/contact')`. Turnstile, the honeypot, the global per-IP limit and the validation are unchanged. `contact.ts` gained these fields:
  - `intent`, from `CONTACT_INTENTS` (lab, invest, advise, licence). Any other value gets 400 `invalid_intent`.
  - `company`, up to 200 characters.
  - `link`, which is optional. When given, it must be an http(s) URL of at most 500 characters, or the route answers 400 `invalid_link`. A link that is too long is refused rather than cut short.
  - When an intent is given, `subject` may be left out. It becomes "<intent> — <company or name>".
  - A request in the old shape (a subject and no intent) is still accepted.
- **A submission is stored in D1 and emailed; it is no longer filed to GitHub.** See "Where a submission goes" below.
- **`/terms`, `/privacy` and `/risk-disclosures`** render through `pages/site/LegalDocument.jsx`, the canvas's legal layout:
  - the "Legal" eyebrow, the h1 and "Last updated <date>" in mono;
  - the intro, then numbered sections, each a number and a heading followed by the body;
  - the questions box.
- **The cookie preferences dialog** (`CookiePreferencesDialog` in `components/CookieConsent.jsx`, styled in `components/cookieConsent.css`) follows COOKIE PREFERENCES:
  - the title, the intro, rows with switches, "Save preferences", "Accept all" and the "Preferences saved." note;
  - the footer's "Cookie preferences" and the banner's "More choices" both open it.
- **Shared CSS for this group** is in `pages/site/contact.css`.

### Where a submission goes

- **Before D680** the route filed each submission as a GitHub issue on `GITHUB_REPO_OWNER/GITHUB_REPO_NAME`. That is AxalNetwork/StudioOS in both `[vars]` and `[env.production.vars]`, and the repository is public (checked through the GitHub API on 2026-10-12). Each issue would have held the sender's name, email, message, company, link, IP and user agent. AGENTS.md ("The repository is public") forbids personal data on GitHub. No submission was ever filed: the `contact-form` label does not exist on the repository.
- **Now** the route makes no GitHub call and reads no GitHub setting:
  1. It stores the submission in `contact_submissions` (migration 448): uid, created_at, kind, intent, name, email, company, link, subject, message, `ip_hash`, user_agent (cut to 200 characters) and `notified_at`.
  2. `ip_hash` is a SHA-256 of the UTC day, the worker's `JWT_SECRET` and the IP. The IP itself is never stored. The hash can show one source sending many in a day, but cannot name it or follow it across days.
  3. It then emails the submission, with every field and the row's reference, through `sendNotificationEmail` to the canvas's mailbox for the intent:
     - Spin-Out Lab → founders@axal.vc;
     - Investing / LP → guillaume.lauzier@axal.vc;
     - Advising and Licence → network@axal.vc;
     - no intent, or a support request → founders@axal.vc.
     
     The firm's own inbox may hold personal data.
  4. A sent email stamps `notified_at`.
- **When email is not configured, or the send fails,** the row is still stored and the route still answers 200 `{ ok, reference }`. `notified_at` stays NULL, so unsent rows can be found, and a warning naming only the reference and the intent is logged.
- **A row that cannot be written** is answered 500 `store_failed`, and nothing is emailed.
- The 503 `github_token_missing` path is gone. `GITHUB_ISSUES_TOKEN` is now read by nothing; its declaration is removed from `types.ts`, and the Worker secret, if one is set, can be deleted.
- **The `/demo` form did the same.** `POST /api/public/demo-request` opened an issue with the lead's name, email, company and message on `GITHUB_REPO` whenever `GITHUB_TOKEN` was set. No `demo-request` issue exists on the repository, so none was filed. The route now stores the request in `demo_requests` as before, emails the lead the confirmation as before, and emails the team instead of filing to GitHub. `DEMO_MAILBOX` sends each topic to the contact form's mailbox for it: product → founders@axal.vc, investor brief → the investing mailbox, partnership → network@axal.vc. An unsent team email logs only the request number. `github_issue_url` stays in the table, unused.

### The decisions

- **The Licence pill is shown only when `?topic=licence` is present.** The Administrators page's "Request a licence" (D677) links there, and the pill arrives pressed. Without the topic the form shows the canvas's three intents. Any other topic falls back to Spin-Out Lab, including the `?topic=circle` that `CirclesPage` already sends.
- **Legal text: option A.** Each page keeps the words it had before D680, laid out the canvas's way:
  - its own headings become the sections, in sentence case (only the case changes, not the wording);
  - its own numbers are zero-padded. Privacy keeps its "00", and the Terms' unnumbered "Acknowledgment" stays unnumbered;
  - the Terms' "Effective Date: July 8, 2026" and the other two pages' "March 31, 2026" become "Last updated";
  - the Terms' operator lines, the Privacy controller line and opening paragraph, and the Risk warning and opening paragraph become the intros;
  - the questions box names the address each page already printed: legal@axal.vc on the Terms and privacy@axal.vc on Privacy. Risk printed none, so it uses the canvas's legal@axal.vc.
  - A word-for-word diff of the rendered text before and after shows no change beyond the eyebrow, the number format, the date label and the questions line.
  - The "Back to Axal VC" link is gone, because the nav carries the home link.
- **The cookie dialog has a row only where turning it off stops something.** Each category was read against the code (2026-10-12):
  - **Analytics.** `lib/funnel.js` checks `hasConsent('analytics')` before it creates its random ID, before it persists anything and before it sends an event. When consent is revoked it erases its four storage keys. This row has a switch and is off by default.
  - **Functional and advertising.** No code calls `hasConsent()` for either. The canvas's Preferences and Marketing rows are dropped, because a switch for them would do nothing.
  - The stored record keeps all four categories and `CONSENT_VERSION` 1, so a saved choice is stored as before.
  - `COOKIE_ROWS` in `lib/cookieConsent.js` is the list the dialog draws.
- **What was set without asking is disclosed under Essential.** Workspace settings (view mode, sidebar state and the like) are kept whatever the visitor chooses. So is `axal_ref`, which `App.jsx` sets for 30 days from any `?ref=` link and was already set without asking before D680. Without a mention, the canvas intro's "Everything else is optional and off by default" would be false. Essential keeps the canvas's text and adds one sentence: "This also keeps the settings you choose, and for 30 days the code of any referral link you arrived through."
- **The Analytics line is rewritten to match the code.** The canvas's line, "Aggregated usage of the public site so we know which pages are read", describes the cookieless page counter in `lib/seo.js` (`/api/public/analytics/pageview`). That counter writes nothing to the browser and is not gated, so turning the switch off would not stop it. The row's line now describes what the switch does control: which sign-up steps are reached and which link brought the visitor, kept under a random ID in the browser and sent only to Axal.
- **Saving keeps the dialog open** and shows "Preferences saved.", as the canvas does. Closing it with ×, Esc or the backdrop records an essential-only choice for a visitor who had not chosen yet, which is the banner's existing rule. The banner itself is unchanged except for one sentence: it now names only "analytics purposes" and no longer "functional, analytics, and advertising".
- **The cohort is the Lab's own rule.** The canvas's "Cohort 5" appears in the founders route ("Cohort N applications") and in the sent state. Both take N from `openCohortCopy()`, as the front page does. When no cohort is open they read "Cohort applications" and "the open cohort". The held-for-a-cohort sentence is shown only after a Spin-Out Lab enquiry, because it is about Lab applications.
- **The named General Partner stays.** "Guillaume Lauzier, General Partner" and his address are real. `lib/fundBriefViewModel.js` already prints both. He is not one of the canvas's sample people.
- **The Turnstile widget uses the light theme**, matching the site. The widget is otherwise unchanged.

### What was dropped, and why

- **The "Kind" select (General enquiry / Support request).** The canvas form has none. Support has its own way in: `/support` redirects to the Help Center. The route still accepts `kind`.
- **The canvas's legal text** waits on the owner and counsel (option B on #1554).
- **The Preferences and Marketing cookie rows.** Nothing is gated behind either (see above).
- **A page to read submissions.** None is built. Until one is, the team reads them in its mailboxes, and any unsent row (`notified_at IS NULL`) in `contact_submissions`.

### Guards

`cloudflare-worker/test/contact.test.ts` (ten tests) runs the route on a SQLite D1 built from migration 448 itself, with fetch stubbed and recorded. It pins:
- the honeypot answering ok, storing and sending nothing;
- missing fields refused;
- a submission that cannot be stored being refused with 500, not dropped;
- the intent set;
- an unknown intent refused before anything is stored;
- the link rule: http(s) only, at most 500 characters, normalised and never cut;
- a valid submission stored with every field, the derived subject, a 200-character user agent and a salted SHA-256 `ip_hash`, with the raw IP in no column;
- each intent, the no-intent case and support emailed to the right mailbox, with the fields in the body and `notified_at` stamped;
- no request to github.com (every request is to Google's OAuth or Gmail), and no `api.github.com` or `GITHUB_` setting in the route;
- with email off: a 200, a stored row with `notified_at` NULL, no request, and a warning naming no one. A failed Gmail send behaves the same way.

`cloudflare-worker/test/demo_request_d680.test.ts` (three tests) runs `/demo-request` with `GITHUB_TOKEN` and `GITHUB_REPO` set and every waitUntil awaited. It pins the row stored, no request to github.com, the lead's confirmation and the team email both sent, each topic reaching its mailbox only, and, with email off, the row still stored and a warning naming no one. Five mutants were killed: a GitHub call put back, the team email removed, the investor topic sent to the wrong mailbox, the lead's name in the warning, and the row not stored.
