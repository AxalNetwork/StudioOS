## D1057 — Reporting part 1: the fixes for #2427's five open findings

- **Status:** filed by S21 as #2927, part 1 of Reporting to investors (#2427), from S21's integration (D1056). Built by S28. No migration.
- **The map:** `documentation/audits/REPORTING_MAP_2026-10-25.md` §1, on D1056's branch. Findings 1 and 2 were fixed by D889 (#2438), and finding 5 by `cleanMetrics`. This decision fixes 3, 4, 6, 7 and 8.
- **Worker only,** bound SQL only.

### 1. Finding 3: quarterly compliance reads Grow's monthly periods

`GET /api/positions/kpi-compliance` compared an update's stored `period` with the due period as strings. Share an update stores the month its period starts in (`YYYY-MM`, `portfolio_updates.ts`), and the quarterly due period is `YYYY-Qn`, so every Grow update read "Not reported".

`periodCounts(cadence, due, stored)` (`services/portfolioMetrics.ts`) decides instead:
- **Quarterly:** `YYYY-Qn` counts for that quarter, and a month inside the quarter counts for it (August counts for Q3; June does not).
- **Monthly:** months are compared. A quarter does not count for a month, because it does not say which month it reports.
- **Anything else** counts for nothing: blank, free text such as "Q3 2026", an impossible month.

Only submitted updates count, as before.

### 2. Finding 4: the investor's update rows read `metrics_json`

`GET /api/portfolio-updates` and `GET /api/portfolio-updates/:uid` built each row from `kpis_json` alone, so a Share an update row read "No KPI values recorded". `updateFigures` (`routes/portfolio_updates.ts`) now gives each row:
- **`figures`:** the row's `metrics_json` figures, each with its `value`, `unit`, `source`, `as_of` and, when not recorded, its `reason`.
  - They are keyed by Share an update's `METRIC_KEYS` (mrr, growth, customers, burn, runway). Part 3's `REPORT_FIGURES` keys report figures the same way.
  - They are read as stored: the save already checked each figure against the period's snapshots (`cleanMetrics`). Running it again here, with no snapshots to check against, would relabel every source "typed".
  - A recorded figure with no source is dropped (D654's rule), and an unknown key is dropped.
  - A figure nothing recorded stays null with its reason, never 0.
- **`kpis`:** the flat map the pages already read. It now holds the recorded figures' values. A value the older KPI form stored in `kpis_json` wins for its own key, and a KPI-form row reads exactly as before.

Until D1056 merges, `/grow/reporting` resolves as an unknown Grow module, so the two should land together or D1056 first.

### 4. Finding 7: `raise_investor_updates` folds into `portfolio_updates`

An investor update posted from the Raise pipeline (`POST /api/contacts/raise-updates`) was a row in a second table that nothing else read and nothing emailed. Now:
- **The write.** The post is a `portfolio_updates` row with status `pipeline`:
  - author = the poster;
  - title = the subject; body = the text;
  - no period; `audience_json` null; never `sent_at`.
- **Its recipients.** Each active prospect (not passed) is an `update_recipients` row:
  - audience `investor`, no account;
  - its email lower-cased; its name as the label;
  - no delivery, with `not_delivered_reason` "Recorded on the Raise pipeline; not emailed".

  This is how Share an update records a pipeline investor it cannot send to.
- **The contact timelines** are logged as before.
- **Nothing is sent, as before:**
  - `pipeline` is not `submitted`, so no investor inbox, compliance read, deck count or focus count takes it for a report;
  - its audience grants nobody, so D889's rule shows it to its founder and admins only.
- **The read.** `GET /api/contacts/raise-updates` reads the `pipeline` rows from `portfolio_updates`, with their recipient counts, as `source: 'pipeline'`. Grow's sent updates stay in `shared_updates`, unchanged.
- **The response** keeps the fields the Raise page and the Spin-Out Lab Capital page draw: `subject`, `body`, `recipients_count`, `created_at`. It drops `round_id`, which no page read. `portfolio_updates` has no round column, and adding one would be a migration this part does not have.
- **The old rows.** `raise_investor_updates` takes no new rows. The rows already there stay where they are and are read with the new ones, newest first, marked `source: 'pipeline_legacy'`, so no posted update disappears.
  - They are never written again.
  - A later migration can copy them into `portfolio_updates` as `pipeline` rows, with their counts as unrecorded recipients, and drop the table; this part keeps them where they are.
  - `contacts.ts`'s bootstrap still creates the table, so the legacy read works on a database built through it.

### 5. Finding 8: Portfolio lists only held positions

`/api/positions` scoped an investor by `investorProjectIds`: any company reached through a dealroom, an introduction or a converted watchlist item. That is a relationship, not a position.

**The rule taken until #2424's `closing_lines` exist:** a confirmed commitment.
- `investorHeldProjectIds` (`routes/_investorProjectScope.ts`) is the relationship set narrowed to companies where the seat's investor holds a `commitments` row with `status = 'confirmed'`, on a deal of that company, in the active company or with no company recorded.
- Pending and withdrawn commitments are not holdings.
- A confirmed commitment outside the relationship set widens nothing.

**The reads that take it:** all five positions reads (`/`, `/marks`, `/analytics`, `/kpi-compliance`, `/:projectUid`). Admins and operators stay unscoped.

**`GET /api/positions` says which rule it used:**
- an investor's reply carries `scope: { rule: 'confirmed_commitment', text }`. The text says the amounts are the positions the studio recorded in those companies, and that how the investor holds each one is not recorded yet;
- an admin's carries `rule: 'all_positions'`.

`portfolio_updates`' investor scope (D889) and the chase are unchanged: an investor still reads and chases the companies they have a relationship with.
