## D6481 part 2 — The Ready flow: the feeder's own switch, a fresh policy report on Ready, and a reason for every wait (#6481)

- **Status:** built by S34 on 2026-11-27 for the owner's request on #6481 (2026-11-21, "Ready for review → full checks → automatic native queue entry"). Rebuilt from main after the earlier S34 session's local work (head `5a6ed96e`) was never published. Default off: nothing changes until the owner sets `LANDING_BOT_FEEDER_ENABLED`.
- **Builds on:** D6481, D5605 row 6, D8076. Conflict recovery and the `conflict` badge stay with #6476 (S21).

**The flow the owner asked for.** Click Ready for review. CI's full suite runs, and so does a fresh `landing policy` report for the same head. The next feeder sweep then admits the PR to the native merge queue once, at that head, with `expectedHeadOid`. If the PR later conflicts and leaves the queue, a return is #6476's, not the feeder's: the feeder still refuses any PR with queue history.

| What | Before | Now |
| --- | --- | --- |
| Feeder switch | `LANDING_BOT_ENABLED`, shared with the keeper, refresh, repair and recovery | `LANDING_BOT_FEEDER_ENABLED`, read by the feeder only (`rules.mjs` `SWITCHES`, `switchFor`). Unset is off. `LANDING_BOT_ENABLED` no longer reaches the feeder, and the new variable reaches nothing else |
| Scheduled sweeps | Allowed whenever the switch was `true` | `true` also needs #6480 (the landing rules) closed as completed. An unread or other state holds. A named dispatch (the one-T0 rehearsal) does not wait for it, as #6481's safety rules allow `dispatch` before #6480 |
| Policy report on Ready | `landing-policy.yml` ran on the default `pull_request` types, so a report from a draft or from before `LANDING_AUTO` changed stayed the latest one for that head | `types: [opened, synchronize, reopened, ready_for_review]`. The trusted base checkout and everything else in the workflow are unchanged |
| Full-suite proof | `test:drift (full suite)` succeeded in a `pull_request` run of `ci.yml` for this PR and head | The same, and the PR must not edit `.github/workflows/ci.yml`. A `pull_request` run executes the PR's own copy of that file, so its job names prove nothing when the PR changes it |
| Bot login | `LANDING_BOT_LOGIN` was set on the plan step only, so the recheck before each write could classify a keeper merge as unattributed and drop a planned PR | Set once for the whole job: the plan and the recheck read the same login |
| A PR that waits | Skipped without a word (only #8076's holds were written) | One `waiting` line per listed PR in the run summary, named by kind: `checks` (draft, no full suite on this head, head moved), `policy` (the failing `landPr` gate and its detail), `conflict` (`mergeable` false, or not yet computed), `hold` (owner labels, breakers, #6480), `owner review` (T2, model-repaired), `queue` (already queued, queue history) or `capacity` (no free build slot, daily cap spent) |

**What does not change.** T0/T1 only, through `landPr.decide()`. The owner lands T2 and model-changed PRs. `bot:off`, `bot:resolved` and `main-repair` hold a PR. Main's required checks and their source apps, queue build slots, the per-sweep and daily caps, the failure-share breaker and #8076's holds all still apply. `mergeable` must be `true`: null or an unread value never admits. The ruleset requires zero native approvals; no review policy changes, and an advisory review is not an approval. The enqueue credential is still the landing-bot App's installation token in the `landing-bot` environment. There is no new workflow, no `pull_request` trigger on the feeder and no second auto-merge path. The sweep's concurrency group, `alreadyQueued` and `expectedHeadOid` keep a duplicate sweep or a stale event from adding a second entry.

**Not in this part.** The hosted proof (one named T0 PR queued by the bot, then a green merge-group run) and the one-week share of feeder-queued merges (#6479). Both wait for the owner's #5500, the #5605 settings and the landing-bot App. The conflict → resolve → green → return path and the PR-list `conflict` badge are #6476's.

**Rollout.** Set `LANDING_AUTO=true`, `LANDING_BOT_FEED_PER_SWEEP=1`, `LANDING_BOT_DAILY_FEEDS=1` and `LANDING_BOT_QUEUE_FAIL_BREAKER`, then `LANDING_BOT_FEEDER_ENABLED=dispatch`, and dispatch `landing-feeder.yml` with one named T0 PR. Set `true` only after that proof and after #6480 closes. Unset `LANDING_BOT_FEEDER_ENABLED` to stop admission without touching the other landing bots.

Tests: `frontend/test/landing_feeder_ready_6481.test.mjs` (the switch both ways, the Ready sequence to exactly one entry, each stop and its line, a moved head, #6480, the workflows), plus the ci.yml and #6480 reads in `landing_feeder_github_6481.test.mjs`.
