## D5676 — Independent archive receipts, retry and canary verification (#5676)

**Status:** local implementation for review. No observer resource, live binding, production write, synthetic producer request, Slack send, retention or deletion change occurred. The queue hold #5657 closed before draft publication. Provider-originated canary/receipt/fallback acceptance awaits the shared sender, approved resources and owner rollout.

### Why the receiver is separate

A telemetry request to studioos would itself enter the tail input and generate another telemetry request. The candidate receiver therefore runs as a separate disabled Worker, with a separate metadata database and no tail consumer. Its code never calls the producer. The tail's optional private service binding targets that receiver only, with no global-fetch fallback. Writer, owned producer and external reader have separate signing keys and strict bounded metadata contracts. None grants a notification caller an object download, D1 customer store or Slack send.

The root application exposes an HQ write-bar synthetic producer. It first persists a random marker expectation in the independent receiver, then logs only that marker through the existing input path. A quiet parent with no expected input is idle; a stopped consumer or missed expected marker is a different state. This route is off and unconfigured. The observer never invokes it, preventing a self-generating monitor loop. A real recurring producer and missed-process fallback require an owner-approved external cadence through #5668, not a new CI job per notification.

### Write identity and bounded recovery

The writer canonicalizes each incoming batch before adding the received timestamp. Content identity and source-event hour produce a stable object key across delayed/repeated delivery; malformed timestamps have an explicit undated prefix. If-None-Match creates the object once. While the object is retained, a lost acknowledgement retries the same key/write identity and verifies metadata when the conditional put reports an existing object. The first object is not overwritten with a new received time. This deduplicates a retried batch, not arbitrary regrouping of the same events into different batches.

At most three put attempts, short bounded backoff and independent received/retry/confirmed/exhausted notices occur. Timed-out puts remain accounted for through waitUntil; they may still commit. Exhaustion is unconfirmed delivery, not a fabricated definite-loss count. Serialization placeholders are separately counted as loss. The independent store deduplicates notices, preserves the first observation and never lets an older attempt erase a confirmed outcome. Oversize/unrecognized input has closed native error/count telemetry, not raw content or a silent claimed archive success.

Replay is bounded to the handler's retained body. This patch adds no raw-event dead-letter store or retention policy. After that window, restoration needs an owner-authorized replay from a retained upstream source if available; otherwise the gap remains explicitly unverifiable/potentially unrecoverable. Metadata survives to diagnose it. Confirmed service restoration does not claim lost archive data was reconstructed.

### Independent checks and source episodes

The observer checks at most 100 batches and 100 marker expectations per call, reading only HEAD metadata for known private keys. Batch ID/count and the exact owned marker must match; newest-object time or the writer's confirmation alone is insufficient. Old unverified expectations remain eligible beyond the rolling window. A capped or unreadable inventory is unknown, not zero. Sustained unconfirmed writes after grace, a missed marker or recorded serialization loss fires one studioos-tail/archive cause. A fresh independently verified write can supply recovery evidence to the trusted existing episode owner. A public read-role request cannot select a recovery timestamp. Unknown query/receiver state never clears an episode.

D5673's redacted source contract carries only counts/window/closed category/owner and the stable labels `[cf][prod][studioos-tail][archive][firing]`. Exact keys, markers, payloads, diagnostic exceptions and customer data stay out of receipts/Slack/public issues. #5665 owns one thread and repeats/recovery; activity counts use its digest. The external checker targets only the independent observer and emits a typed unknown receipt when it cannot reach it. #5668 must watch that process/heartbeat and provide a fallback outside the Cloudflare account/Slack failure domain before activation; no such live fallback receipt is claimed here.

The check window also includes older unresolved expectations, and its reported start expands accordingly. Authenticated read checks have a five-second cooldown. Current proposed recent check window is ten minutes, write grace one minute and owned marker deadline two minutes; these are fixture defaults requiring measured ingress/clock-delay/owner review, not approved production SLOs. One batch has at most three conditional puts and four metadata notices; each notice is below 2 KB. One bounded metadata check has at most 200 known-key reads (currently fewer because markers share batch HEADs), and stops on metadata outage. The proposed external cadence, daily cost and retention must be budgeted from actual ingress. Receiver canary creation is rate-limited to one per five minutes; default deployment is disabled. Sampling/native log loss remains a coverage limit, so canary evidence is not proof every normal event arrived.
