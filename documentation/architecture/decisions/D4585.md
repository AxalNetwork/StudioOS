## D4585 — Validate's evidence contract: named populations, the PostHog metric read, and failed reads refused (#4585)

- **Status:** built 2026-11-07 by S26 for #4585 (parent #4584, phase 2 · P1).
- **Migration:** none.
- **Builds on:** D690 (claim records, evidence links), D704 (the read records verdict history), D1605 (PostHog metrics as evidence), D4629 (bounded history coverage).
- **Leaves alone:** the claim-status scoring policy. A claim's status is still computed from interviews reached through its pain-theme links only. This decision labels that population; it does not widen it.

### The shared contract

A claim's evidence has two populations, and every surface says which one it shows.

| Population | What it holds | Where it is read |
|---|---|---|
| **Interview support** | Interviews that name a theme the claim is linked to (`hypothesis_pain_links`) | The claim's status, the Experiments list's *Interview support* column and `interview_support`, the record header's *Interview support* fact, the board, the summary CSV, the overview's status bars and its weekly bars |
| **Linked evidence** | Rows in `hypothesis_evidence_links`: a direct interview, a demand signal (`signal-`, `revenue-`, `waitlist-`), a KPI, a PostHog metric (`posthog-<uid>`), an experiment | The record's Evidence section (`evidenceFor`), and the Experiments list's `linked_evidence` counts by kind |

Each item that `evidenceFor` returns carries its source identity (`link`, `kind`, `ref_id`), its claim (`hypothesis_id`), its direction, its value inside the label, and its observation date.

- **The Experiments list.** The column `Evidence` is now `Interview support`. Its cell reads `2 interviews · Pattern`. When the claim has other linked evidence, the cell adds `· 3 other linked, not in status`. A claim with nothing reads *Not recorded*, never `0`. The row carries `linked_evidence: { interview, signal, metric, experiment }`, and the list's stats carry `status_basis: 'interviews'`.
- **The record header.** The fact `Evidence` (`n for · m against`) is now `Interview support`.
- **The overview card.** Its caption read "evidence added per week" over bars that count only pain-theme links. It now reads "interview-theme links added per week".

### A PostHog metric that is accepted is read

`addEvidence` has accepted a `posthog-<uid>` metric once PostHog has given it a value (D1605). Before this decision, `evidenceFor` skipped every metric outside `KPI_KEYS`, so an accepted link vanished on reload.

It now resolves the link through the connector's own stores:

- `posthog_tracked_metrics` supplies the name (the insight's name, or else its role) followed by "(PostHog)".
- `posthog_metric_facts` supplies the latest valued fact: its value (with a `%` for a percentage unit) and its `as_of` date, which is the observation date.

There are two edge cases:

- If the metric is still tracked but has no value now, it reads *Not recorded*, never 0.
- If the metric is no longer tracked, it is left out, the same as any missing record.

Add evidence's choices also list valued PostHog metrics. They are the same population `addEvidence` accepts, so the form and the writer agree. No connector code changed (#3731).

### Failed reads are refused, never empty

The board (`buildBoard`) and the interview CSV used to catch a failed read and continue with an empty result. Three reads are now required:

- the claims (`hypotheses`);
- their pain links (`hypothesis_pain_links`);
- the interviews (`discovery_interviews`).

A failure throws `EvidenceUnreadable` naming its source. The board, the summary CSV and the interview CSV answer `503 { error: 'evidence_unreadable', source, detail }`, and the detail says that nothing was changed.

- **No false transition.** The throw happens before any verdict is derived, so `recordVerdictChanges` never sees an incomplete board. No history row is written.
- **No manufactured recovery.** Because a failure writes nothing, the next healthy read finds no false transition to "recover" from. It records the claim's real state once.
- **Empty is not failure.** A venture with no claims and no interviews reads an empty board and exports its CSVs with status 200.
- **The cycle read is already safe.** The Experiments list's history writer (`experimentRecords`) gets its claims, links and interviews from `Promise.all` with no catch, so a failure there rejects before `recordVerdictChanges` runs.

### Tests

- `cloudflare-worker/test/validate_evidence_reliability_4585.test.ts`:
  - **Fault injection, one required query at a time.** Each failure is checked on the board and on the summary CSV: the response is a 503 naming its source, the verdict history is unchanged, and a later healthy read writes exactly one observation, with nothing written on a second read.
  - **CSV and empty-venture cases.** A failed interview read refuses the interview CSV. An empty venture's board and CSVs succeed.
  - **Every evidence kind.** A direct interview, a pain-derived interview, a demand signal, a pre-sale, an ordinary KPI, a PostHog metric and an experiment are each written through `addEvidence` and read back through `evidenceFor`, checking source, direction and date.
  - **Labels and counts.** The list's *Interview support* column, `linked_evidence` and `status_basis`, the record header's label, and the PostHog choice in Add evidence.
  - **Link removal.** Unlinking updates the list and the record, and leaves the tracked metric and its fact in place.
  - **Missing PostHog values.** A valueless PostHog metric reads "Not recorded", and an untracked one is left out.
- `frontend/test/validate_support_cell_4585.test.mjs`: the *Interview support* cell, including the null case.
- **Mutations, each caught by the new tests:**
  - each of the three required reads put back to catch-to-empty;
  - the interview CSV allowed to export empty on a failed read;
  - the PostHog branch removed;
  - "Not recorded" replaced by 0;
  - the header label put back to *Evidence*;
  - `linkedCounts` emptied.

### Remaining methodology dependency

Some questions here belong to the methodology work package in #4584, not to this decision:

- whether directly linked interviews, demand signals, metrics or experiment results should count toward a claim's status;
- with what weight they would count;
- how direction and strength combine across kinds.

Until that policy is decided, every surface keeps the two populations apart and names them. If that work changes the policy, `status_basis` is where the change is announced.

Two related areas are left to their own issues:

- temporal coverage of the verdict history (#4629);
- retry-safe proposal writes (#4627).
