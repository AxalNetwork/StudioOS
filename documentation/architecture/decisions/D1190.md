### 1. Migration 607: money in cents, with a currency

- **The columns:**

  | Table | Gains |
  |---|---|
  | `raise_prospects` | `amount_cents`, `currency` |
  | `raise_rounds` | `target_cents`, `currency` |
  | `raise_pro_rata` | `taking_cents`, `currency` |
  | `raise_closes` | `currency` |
  | `raise_prospect_events` | `starts_at`, `calendar_item_uid` (unique where set) |

  A close records no amount of its own (its money is its prospects'), so it gains only the currency.
- **The currency** is three capital letters (a CHECK) and USD for every existing row, because every amount was typed as dollars, as D1149 decided for deals. One currency per venture: the active round's.
- **The copy** runs once: `CAST(ROUND(dollars * 100) AS INTEGER)`, only for an amount from 0 to ten trillion. A missing amount stays NULL, never 0. A negative or out-of-range one stays NULL too, because no cents value would be true.
- **Kept in step by triggers.** Every writer still writes dollars: `contacts.ts`, `raiseWriters.ts`, the Mercury credit (D752) and D653's round-call response, about twenty statements. Instead of changing them, one trigger per table recomputes the cents on every insert and every change of the dollars, by the same rule. The triggers write only the cents column, so D752's trigger on `amount` and `stage` never fires from them.
- **A database without 607's triggers** is one `contacts.ts` healed at runtime (its runtime definitions now declare the columns, as `check-schema-pair-drift` requires). There the commitments read falls back to the dollars, by the same rule, when the cents are NULL.

### 2. The commitments read: `GET /api/cycles/raise/capital-relationships/commitments?project=`

The module's own gate applies: the venture's founder or an admin (`scope`, D663). The read covers four stores, each as it stands:

| Source | Store | Status words | Counts |
|---|---|---|---|
| Typed | a prospect at Committed (`raise_prospects`) | Signed, Wired, Soft, Status not recorded | Signed and Wired |
| Recorded | an answered round call that named an amount (D653) | Indicated through a call | never |
| Recorded | a deal-room commitment (`commitments`), pending or confirmed | Pending, Confirmed | both |
| Connector · Mercury | a Mercury credit the founder matched (D752), **the founder alone** | Received | yes |

- **Closings** (CAPITAL, #2424) are recorded nowhere yet. The read says so in `sources.closings`.
- **What counts:** Received, Signed, Wired, Confirmed and Pending, as the canvas's "Committed against the target" draws them. A soft commitment, an indication through a call, and a commitment with no status never count (#2457 owner question 4). Each carries `why_not_counted`.
- **One line per investor in the totals.** One investor reaches several stores:
  - a round-call response also writes its prospect as Soft (D653);
  - a matched Mercury credit marks its prospect Wired (D752);
  - a deal investor is often a prospect too.

  Summing every line would count that money twice. So each investor's lines are grouped, by the prospect or the same person's email, and only the strongest line counts toward the totals. The order is Received, Signed, Wired, Confirmed, Pending, Indicated, Soft, Status not recorded. Every line is still listed under its investor.
- **A missing amount** is listed with `cents: null` and never summed as 0. The totals count it (`amount_not_recorded`, `counted_amount_not_recorded`).
- **One currency.** A line in another currency than the round's (a EUR deal) is listed, not counted, and never added; `other_currency` counts them.
- **Totals:** `counted_cents`, `not_counted_cents`, `by_status` (cents and investors), and `percent_of_target` against the round's `target_cents`. With no active round there is no target, and the read says why.
- **Mercury for an admin:** `sources.mercury` is `founder_only`, and no Mercury line is read. The prospect's typed Wired still counts the same money once.
- **One failed block never blanks the read.** A store that cannot be read is `unreadable` with its reason, the others answer, and `totals.partial` is true. No raw error text reaches the answer.
- **Names:** a prospect is the venture's own record. A round-call respondent is named, as Calls already names everyone who answered. A deal investor is named, never by email.

### 3. Meetings with a start, and the Calendar item

- **The writer.** `logProspectEvent` (and the record's Log action) takes `starts_at` for a meeting or a call: an ISO instant with its zone (`Z` or `±hh:mm`), stored as UTC.
  - A time with no zone is refused, never read as UTC.
  - A start on another kind is refused.
  - An `on` for a different day is refused.
  - The step's day is the start's day. The step gets `calendar_item_uid` (`investor-meeting-<the step's uid>`), the id its Calendar item keeps.
- **The kind.** `investor_meeting` is the ninth `CalendarEvent` kind (`services/calendar/investorMeetings.ts`):
  - **whose calendar:** the venture's founder (`users.founder_id = projects.founder_id`), and nobody else, admins included (#2420's "Mine");
  - **its title:** "Investor meeting · [the firm]" or "Investor call · …", with the note in its notes;
  - **its times:** the end is the start, because the step records no end (no invented hour);
  - **no attendees and no organiser:** a Google or Outlook copy is private and mails no investor.
- **Where it reaches:** `/calendar`, the `.ics` file and the Google and Outlook sync, as every kind does.
- **`/calendar`'s kind table** draws it as "Investor meeting", source `raise_prospect_events`. Its mark is a leaf (round but for its top right) in emerald, the Meetings family's colour in #2420's canvas. The page guard requires a chip for every kind the Worker emits.
- **Not pushable one at a time.** `PUSHABLE_KINDS` is unchanged; "Sync now" carries it.

### 4. The match read: `GET /api/cycles/raise/capital-relationships/match?project=&q=&hq_country=&focus=&size_band=&fit=&warm=1&sort=&limit=&offset=`

- **The funds** are the fund directory's answer (D535, read only through `SERVED_FUNDS`, D597): its search, filters, facets, sort and paging. Each fund adds:
  - `fit`: `fundFit` against the venture's sector through the Research crosswalk, never a substring. It carries the fund's focus and the venture's sector;
  - `warm_paths`: the people in the **caller's own** network (`network_connections`) whose company is the fund's name, case aside. Another member's network is never read;
  - `in_pipeline`: the prospect that already tracks the fund (`research_fund_uid`), or null;
  - `stage: null` with its reason. The directory records no stage, so a `stage` filter is 400, as the directory refuses it.
- **The two filters it adds:**
  - `fit=fits|outside|unclear`. SQL cannot run the crosswalk, so the read computes which of the directory's distinct focus strings have that Fit. The query then filters on them, with a fund that records no focus counting as Unclear. Paging and `total` stay the directory's.
  - `warm=1`: only the funds someone in the caller's network works at.

  A bad value is 400 with its field.
- **Verified investors are a count, never names** (owner question 10). The count is investors on Axal:
  - verified: active and KYC approved;
  - whose published sectors fit the venture's, by the same crosswalk;
  - whose anti-thesis does not name the venture's sector.

  With no sector recorded, the count is null with its reason, and every Fit reads Unclear.
- **"Not for us"** (CRL7's hide) and "Sort: Fits first" are not built. The Fit filter gives the first; the hide has no store and belongs to part 5.
