## D6425 — A Deal flow pass answers the viewer's own invitation (#6425)

- **Status:** built 2026-11-14 by S12.
- **Owner's call:** option A, decided on #6425 the same day. Found while building #6152 (D6152).
- **No migration.**

### The gap

Deal flow's Pass dialog said "The studio that invited you is told you passed." for a deal reached by invitation. The pass (`POST /api/deals/flow/:dealId/pass`, `services/dealFlow.ts` `passDeal`) wrote only `deal_flow_entries`:
- the invitation stayed `invited`;
- the studio was never told.

Only `POST /api/deals/:id/invitations/respond` answered an invitation.

### 1. The pass answers the invitation

`passDeal` reads the viewer's own invitation to the deal (`deal_invitations`, unique per deal and investor). Any pass on that deal answers it, whether from New for you or from the flow table:
- **an open invitation** (`invited`, or `interested`, which `/invitations/respond` also lets an investor change) is set to `passed` with `responded_at`;
- **one already `passed`** is left alone, with no second notice.

**Land together or not at all.** The answer is one more statement in the pass's own `DB.batch`. Its `UPDATE` is guarded by `EXISTS (… deal_flow_entries … uid = ? AND stage = 'passed')`, because a D1 batch runs every statement: a flow write that lost its D4632 guard (409, nothing saved) must not let the invitation change. `status <> 'passed'` in the same `UPDATE` keeps a race from answering twice.

**Whose invitation.** It is always the viewer's (`investor_user_id` = the caller). A colleague passing the firm's shared row never answers someone else's invitation.

### 2. The studio is told, by the same notice

`services/dealInvitationAnswer.ts` `notifyInvitationAnswer` is the one `deal_invitation_response` notice. `/invitations/respond` now calls it too, so the two cannot drift.
- `passDeal` sends it only when the `UPDATE` changed the row.
- It is best effort: a notice that cannot be sent leaves the pass and the answer in place, as `/invitations/respond` already treated its notice.

The pass's response adds `invitation_answered: true | false`.

### 3. The dialog says so only when it is true

- **Flow rows** carry `my_invitation`, the viewer's own invitation status or null (a `LEFT JOIN` on the caller in `ROW_SELECT`).
- **The flow table's Pass dialog** shows the studio line when `passAnswersInvitation(row)`, meaning the viewer's invitation is `invited` or `interested`. It used to show it for `entered_via === 'invited'`, which a colleague's invitation also matches.
- **New for you** keeps `source === 'invitation'`: its invitation items are exactly the viewer's own, still `invited`.

### Not changed

- The old `InvestorDealsWorkspace` queue (D6152).
- The deal room's "I'm interested".
- `/invitations/respond`'s own rule: any answer, re-answerable, with the notice.
