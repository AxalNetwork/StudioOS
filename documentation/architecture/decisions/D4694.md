## D4694 — Licence terms and licence-fee invoices are written against the revision the editor read (#4694)

This is package 4 of 7 of the `/admin/licences` audit. It covers lost updates
in HQ's terms and invoice writes. The remaining packages are not touched here.

### The failure

- The Terms editor sent all seven fields on every save, from the values it
  first showed. Renew the licence while it was open, edit only the fee, and
  the renewal date went back to the old one.
- `PUT /terms` (the schedule) read the row, merged the body onto that
  snapshot, and replaced the row. Two administrators editing unrelated terms
  lost one of the two edits without a word.
- An invoice payment or void read the invoice, checked it, then ran a
  conditional UPDATE and returned success without looking at how many rows it
  changed. A void racing a payment could answer 200 and write an audit row for
  a void that never happened. Two payment totals could replace each other.
- The legacy `PATCH /terms` clamped a share to 0..10000, cut a currency to
  three characters, and accepted any string as a date.

### The rule

Every write that starts from a snapshot names the **revision** it read
(`expected_revision`), and applies only if the row is still at that revision.

| Write | Revision | Bumped by |
| --- | --- | --- |
| `PATCH /api/admin/licences/:uid/terms` (fee, term, shares, dates) | `territory_licences.terms_revision` | that PATCH and `POST .../renew` |
| `PUT /api/admin/licences/:uid/terms` (the schedule) | `licence_terms.revision` | each save; no row reads as 0 |
| `PATCH /api/admin/licences/:uid/fee-invoices/:uid` (payment, void) | `licence_fee_invoices.revision` | each payment or void |

Migration `202611071531_licence_revisions.sql` adds the three columns, `NOT
NULL DEFAULT 0`. Nothing is backfilled.

- **A missing, non-integer or negative `expected_revision` is a 400
  `revision_required`**, never read as 0. Revision 0 is a real value: a licence
  with no schedule yet.
- **The UPDATE names the revision, and the route reads the affected-row
  count.** Zero rows is a 409, so a competing write that lands between the
  route's check and its UPDATE still loses. The cheap early check only saves a
  round trip; the UPDATE is what decides.
- **A first schedule save is `INSERT ... ON CONFLICT DO NOTHING`.** If another
  administrator inserted first, the save is a 409 rather than an overwrite.
- **No event and no audit row for a write that did not commit.** The
  `terms_changed` event and the `licence_fee_invoice_*` audit rows are written
  after the row count is checked.
- **A 409 carries what to reload.** `terms_conflict` returns
  `current_revision` and `current`; `invoice_changed` returns
  `current_revision`, `current_status` and `current_paid_cents`.
- **Renewing bumps `terms_revision`.** A stale Terms form is refused after a
  renewal; the editor reloads, and the next save carries the new revision.

### What each side sends

- **Core terms:** only the keys named. `null` clears one; a key left out keeps
  its value. An unknown key is refused. The PATCH takes the schedule's bar
  (TOTP session, fresh step-up, Super Admin elevation) and a required reason;
  before this change it needed only a Super Admin.
- **The editor** keeps the values it was last synced to. A save sends the
  fields that differ, the reason, and the revision. When the licence refreshes,
  every untouched field takes the server's value and every edited field keeps
  what was typed. If an edited field also changed on the server, the form says
  so before the save replaces it.
- **The schedule form** already sent only changed terms; it now sends the
  revision it loaded. On a 409 the typed edits stay, and a "Load the current
  terms" button replaces them on purpose.
- **The invoice panel** sends the invoice's `revision`. On `invoice_changed` it
  shows the server's sentence and reads the list again.

### Validation: refused, not coerced

`validateCoreTermsBody` (`services/licenceTerms.ts`):

| Term | Accepted |
| --- | --- |
| `term_years` | whole number 1..50 |
| `annual_fee_cents` | whole cents 0..10^12 |
| `revenue_share_bps`, `token_split_bps` | whole basis points 0..10000 |
| `currency` | three letters (case is normalised to upper) |
| `starts_on`, `renews_on` | a real calendar day as `YYYY-MM-DD` |

A value must be a JSON number where a number is meant (`"3500"` is refused).
`null` clears a nullable term; a currency cannot be cleared. The schedule's
`normaliseTerm` was already strict and is unchanged.

### Decisions and what is not done

- **A revision counter, not `updated_at`.** Two writes in one millisecond would
  share a timestamp.
- **Explicit 409, not an automatic merge**, for two administrators editing
  unrelated terms. The issue allows either; a conflict is what an audited
  money record should do, and the reload is one click.
- **No payment ledger.** The issue offers an append-only ledger "if that is
  the cleaner invariant". The revision check closes the lost update on the
  running total and keeps HQ's existing "total received so far" model and the
  licensee's invoice view. A ledger would change both and needs the owner's
  call; it is not started here.
- **Other writers of `territory_licences`** (status transitions, seats,
  territories) touch columns outside the terms and do not bump
  `terms_revision`.
- **Not verified here:** an authenticated run against production data. The
  tests use synthetic licences.
