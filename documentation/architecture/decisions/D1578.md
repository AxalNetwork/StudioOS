### 1. The PDF is tagged, and checked for PDF/UA

The print page is printed by Chrome with `tagged: true` (D1575). That gives:
- a structure tree in the DOM's order, which is the card's reading order;
- each picture as a `Figure` carrying its alt text. An image whose alt text is empty becomes an artifact, not a Figure, and the print page always writes an `alt`.

**`finishTaggedPdf` adds what the page cannot say:**
- the deck's title, shown as the window title (`DisplayDocTitle`);
- the deck's language: the theme's `lang` (D1571), else `en`;
- `MarkInfo /Marked true`;
- the document XMP, with PDF/UA-1's identifier (`pdfuaid:part="1"`), the title and the language.

The structure tree and the pages stay as Chrome wrote them.

**`checkDeckPdf` adds, under `ua`, one code for each thing PDF/UA asks that this export can answer for:**

| Code | Refused when |
| --- | --- |
| `not_tagged` | there is no structure tree, or MarkInfo is not `/Marked true` |
| `no_language` | there is no `/Lang` |
| `no_title` | there is no title, or it is not shown as the window title |
| `no_pdfua_id` | the XMP has no PDF/UA-1 identifier |
| `figure_without_alt` | a Figure has neither `/Alt` nor `/ActualText` |
| `ai_unmarked` | the deck holds AI-drawn pictures and the XMP does not say so |

A PDF that fails is refused as D1575's other failures are (502 `pdf_fidelity_failed`, codes only), and the finished file, never the browser's, is the one handed out.

**Why the CI check is ours.** veraPDF cannot run in this repo's CI. So "the PDF/UA check passes in CI" means:
- this check, run on a real Chromium tagged print (the fixture, base64 so no line-ending rule can touch it) after `finishTaggedPdf`;
- every rule refusing its absence, each one mutation-checked.

It covers the machine-checkable part of PDF/UA for this document: tagging, language, title, identifier and figure alt text. It does not judge whether the alt text is meaningful; that is the author's.

### 2. PowerPoint reading order

D1574's writer already writes each card's areas in reading order: top to bottom, then start to end, keeping the card's own order where areas overlap. A screen reader takes shapes in that order.

**This change:**
- **Decorative shapes.** Decor (native shapes, icons and textures drawn as SVG) and a filter's colour wash are marked decorative with Office's `adec:decorative` extension. A screen reader then reads the areas and nothing that only decorates.
- **Alt text.** Pictures keep their alt text in `descr`, as before.
- **Title and language.** The file now carries them in `docProps/core.xml`, for the download and for Google Slides.

### 3. AI marking survives every export

**Which images are AI-drawn.** `aiImagesOf` reads the venture's own `deck_images` rows with `source = 'generated'`, by each image block's and each card background's `image_id`. An upload is never marked. A store that cannot be read marks nothing new, and logs an outcome only.

**Per format:**

| Format | Where the mark is |
| --- | --- |
| PowerPoint, .odp, HTML, Google Slides | in the image file itself |
| PDF | in the document XMP |

- **In the file (`markImages`).** These exports embed the image's bytes. D1505 already writes the XMP packet (`Iptc4xmpExt:DigitalSourceType` = `trainedAlgorithmicMedia`, `xmp:CreatorTool` = the model id) into every image it draws. `markImages` writes the same packet into an AI image that lacks it, for example one stored before D1505. A file already marked is left as it is, and a kind the writer cannot walk (GIF) is left unchanged. Every embedding route reads its images through `markedImages`.
- **In the PDF's XMP.** Chrome re-encodes pictures into the PDF, so a file's own XMP does not survive there. The document XMP therefore says `compositeWithTrainedAlgorithmicMedia` and lists each AI picture's model and card (1-based). No prompt, name or figure is written.
