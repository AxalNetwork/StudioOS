### How the records were collected

- **Listing.** Every page of `repos/AxalNetwork/StudioOS/actions/artifacts`
  was read through REST, down to 2026-11-09. Nothing older can hold a record,
  because the job first ran on #5635 itself. There are **3,733
  `selection-shadow-*` artifacts and none has expired**. They run from
  2026-11-11 22:21 UTC to 2026-11-25 23:23 UTC and come from **3,657 distinct
  PR runs**. The other 76 artifacts are earlier attempts of rerun runs.
- **Reading.** The session's egress proxy reaches only one of the 23 Azure blob
  accounts that serve artifact zips (`productionresultssa31`). That allowed
  just **16 records** to be downloaded whole. The other 3,641 runs were read
  from the `selection (shadow)` job log of each run's latest attempt. The CLI
  prints its record summary there (`mode`, `reason`, `scoring`, `misses`,
  `selected`, `total`). For all 16 downloaded records, the summary matched the
  full record field for field. That gives **3,652 runs read**. The 5 runs not
  read are 2 cancelled jobs, 1 log with no summary line, 1 run whose latest
  attempt has no shadow job and 1 jobs-listing error.
- **Report.** The summaries were written back as `kind: selection-shadow`
  records and passed to the unchanged `node scripts/select-tests.mjs --report
  <dir>`. The 16 whole records were also reported on their own.

### Backtest

`node scripts/select-tests.mjs --backtest` prints **unscored for all 27
episodes**: none passes and none misses. The fixture has failing files for 25
of them. Two, `565a9f5df0` and `5f36014c93`, are guard- or setup-only and have
no test-file identity. The deciding fact is that no `test-deps-<sha>` artifact
exists for any of the 27 first-red commits. The episodes run from 2026-11-04 to
2026-11-11, and the producer started on 2026-11-16. Those traces can never be
recorded after the fact. So the backtest half of the gate cannot be met from
this fixture. It needs either a new episode set drawn from red mains after
2026-11-16, while their `test-deps-*` artifacts are still within the 30-day
retention, or `--evidence` files built from such traces.

### Why nothing is scored

1. **No `pr_failure` evidence exists when the shadow job reads it.** Only the
   `ci-failures-classified-*` record has a `verdict`. That record is written by
   `why CI failed (D5398)`, which needs eleven jobs and runs only on failure.
   The shadow job needs only `suite`, so it usually downloads before the
   classified record exists. Of the 46 runs where both artifacts were visible,
   the shadow's upload came first in 31. The per-part
   `ci-failures-<part>-attempt-*` records were downloaded in 820 runs, but they
   have no `verdict`, so the CLI correctly ignores them.
2. **Classified records that the shadow did receive were not `pr_failure`.**
   In 13 runs (reruns and races) the shadow did download a classified record,
   and every one still produced an unscored record. All 11 classified records
   this session could open say `main_health_unknown`, with only `unknown`
   failures. 8 of the 11 carry the warning "No completed main run exists for the
   tested base SHA". The others list failures as `step` / "Not recorded". The
   #5502 classifier needs base-run evidence before anything can count.
3. **Drafts no longer run the suite (#6460).** A draft PR's shadow record
   cannot carry a suite failure, so scored cases can come only from ready-PR
   runs. That slows the 300-run count even after 1 and 2 are fixed.

### Why the trace is often missing or refused

- **`missing-or-invalid-trace` after 2026-11-16 (877 runs).** The lookup reads
  only the newest 100 artifacts in the repository. That is about one to two
  hours of artifacts, out of about 1,400 a day. Whenever no main or queue
  `test-deps-*` artifact is in that window, no trace is found.
- **`shadow-evidence-unavailable` (842 runs).** The lookup takes the *newest*
  trace on main. The CLI then requires that trace's SHA to be an ancestor of
  the PR's base and throws if it is not. Four sampled runs (44109339110,
  44335404908, 44639551582, 45042121624) each picked a trace 1 to 3 commits
  *newer* than the PR's base. The ancestry check is conservative and correct,
  but in practice the chosen trace is seldom usable. Picking the newest trace
  at or before the base needs the base SHA in the lookup step. That is a change
  to the shared CI step and is left for the owner.

### Limits of this evidence

- 3,636 of the 3,652 runs were read from job-log summaries, not from the
  records themselves. The `files` and `failing` lists were not seen for them.
  For 16 runs the summary and the record were checked to be equal.
- The report counts records, not runs. Folding in the 76 earlier-attempt
  artifacts would change no total that matters here, but a future report over
  raw artifacts should deduplicate by run.
- `score()` marks a whole run unscored if any reported failure is not a
  `*.test.mjs` / `*.test.ts` file, for example a guard script. A real
  `pr_failure` that mixes a guard failure with a test failure will therefore not
  count toward 300.
- The ci-failures records have a 3-day retention, so the classified verdicts
  before 2026-11-22 can no longer be read.
