### 2. The exact-SHA reuse lookup is a script with fixtures

On a push to main, CI's `verified` job looks for a successful `merge_group` run
of `ci.yml` on the same commit; only when it finds one are the suite parts
skipped, and `test:drift (full suite)` and `landing gate` pass on that run's
evidence. The lookup was inline shell in `ci.yml` with no executable test. It
is now `scripts/ci/queue-run-lookup.mjs`, with the same query (`head_sha`,
`event=merge_group`, `status=success`, `per_page=1`), the same check on the
newest run (same SHA, `merge_group`, `success`), the same four lookups twenty
seconds apart, and the same output `run`. A failed or unreadable call still
counts as no run, and no run still means the full suite runs.

The job was named `already verified in the merge queue`, which read as a pass
on every push, including the ones that ran the full suite. It is now
`merge-queue run lookup`; its id stays `verified`, so no `needs:` changes. It
is not a required check, and no workflow, script or deploy proof reads its name.
It also writes a second output, `outcome`, and a step-summary line:

- `reused`: the queue run's URL; the suite parts are skipped on the push.
- `miss`: every lookup answered and none matched; the full suite runs.
- `unavailable`: a lookup could not be read and none matched; the full suite runs.

`frontend/test/queue_run_lookup_5500.test.mjs` runs it on fixtures: exact
match, delayed success, a success after the fourth lookup, wrong SHA, wrong
event, failed, cancelled, skipped and in-progress runs, an empty or malformed
answer, API unavailable on every lookup and on some, missing inputs, and the
command line through a stand-in `gh`. It also runs both gates' own shell on the
outcomes: a skipped or cancelled suite without a queue run fails both, and a
queue run is trusted only on a push.

The job now checks out `scripts/ci` (sparse, no persisted credentials) and sets
up Node, so its permissions are `contents: read` and `actions: read`.
