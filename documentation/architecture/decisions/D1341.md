### 1. The task, the charge and the estimate

`mail_draft` is a Workers AI task:
- its model is `MID_LLAMA`;
- its fallback is `SMALL_LLAMA`;
- its priced alternates are those two and `llama-3.2-3b-instruct`;
- its label is "Draft an email";
- its surface is `/email`, listed in D552.

**The charge.** A draft is one `run()`. The router holds and settles it in AI tokens through `aiCredits`, like every rail run, on the rail page `Email` with option `draft:email`. The record is the person's ref. The route writes no charge of its own.
- The draft stores `ai_usage_logs.charged_microusd` for its run. When that row cannot be read, it stores null, never 0.
- A short balance is 402 in `budgetRefusalMessage`'s words, through `refuseRun`, and nothing is stored.

**The estimate.** `estimate: true` is `quoteRun` over the same options: the same messages, model choice, multiplier and guard. It runs nothing, holds nothing and stores nothing. It answers the most the run can charge, with the sources and blocks it would carry.

### 2. Intents, one table

`services/mail/intents.ts` has no imports, so the composer (#3552) can import it as the SPA imports `redirectRoutes.ts`. It holds:
- the intents per relationship (#3547 EM3);
- `RELATIONSHIP_OF`, each ref kind to its relationship;
- `TONES` and `LENGTHS`.

| Relationship | Intents |
| --- | --- |
| customer | Thank and follow up; ask for a second interview; share what we built from your feedback |
| investor | Send an update; ask for a meeting; answer due-diligence questions |
| advisor (and operating partner, and growth partner) | Ask for advice; book a session; share progress |
| cofounder | Weekly sync summary |
| network | Introduce myself |

The Worker refuses an intent that is not its relationship's: 400 `intent_invalid`. The issue's "recruiting pipeline row" is not a kind of its own. It is the interview's own stage, so an interviewee's pack carries it (§3).

### 3. The context pack: each record through its module's own read

A person is a ref, `kind:id`. Each kind is read as its module reads it, never from a raw table.

**Module records** go through `readableRecord`, the record page's own path:
- the spec's read gate (`allowed`);
- the id proven in its store for the venture (`ownedRow`);
- `spec.record`;
- each section that its own gate and `when` admit.

A fixed statement finds the venture from the row; nothing in a request names a table.

| Kind | Module | Link |
| --- | --- | --- |
| `interviewee:<id>` | Validate › Customer research (`discovery_interviews`) | `/validate/customer-research/<id>?project=` |
| `prospect:<id>` | Raise › Capital relationships (`raise_prospects`) | `/raise/capital-relationships/<id>?project_id=` |
| `cofounder:h-<id>` | Build › Founding team (`cap_table_holders` with a founder role) | `/build/founding-team/h-<id>?project=` |
| `growth_partner:<uid>` | Grow › Partner network (`growth_partners`) | `/grow/partner-network/<uid>?project_id=` |

- **What goes into the text.** An interviewee's text adds its pains and its recruiting stage, from the row the gate already admitted. It leaves out the raw transcript, the run's cost and the session's plumbing; its kept summary carries the quotes, under the summary's own consent rule.
- **A fact with no value** is said in its own reason, never as 0.

**Engagements have no record spec.** They are read by the founder's own rule, the one their pages use:
- `advisor:<id>` is an `advisor_engagements` row whose `founder_user_id` is the member. Its last session is the latest `advisor_bookings` row of that advisor and member whose slot has started, and that is not cancelled. It has no venture.
- `partner:<id>` is an `engagements` row whose `founder_id` is the member's. Its last session is read the same way from `partner_bookings`. Its venture is the engagement's.

**`member:<id>`** is part 3's (#3550) and answers 404 until then.

**Refusals look like absence.** A ref that is malformed, does not exist, or that the member cannot read is the same 404: `{ error: 'not_found', detail: 'Record not found.' }`. That is the record route's own sentence.

**The pack.** `GET /api/mail/context?person=[&project=]` answers `{ person, intents, items }`.
- **The person's own record** comes first, `selected: true`.
- **The company's items** follow, never selected: the one-liner (`one_liner:<project>`) and the KPI board (`kpis:<project>`). Each is offered only when its block (§4) has something to say. Their venture is the person's; `project` names it only when the person has none (an advisor), and never overrides the person's own.
- **Each item** has a ref, a one-line label, an `as_of` day (the row's last change, or the block's), a link, and its text.

A support session is refused on every route (403 `support_session_refused`): an email is the member's own words.

### 4. Live update blocks

`POST /api/mail/blocks` takes `{ kind, ref?, project? }`. Each block is computed when asked, under the module's own gate:

| Kind | Read | Gate |
| --- | --- | --- |
| `kpis` | Revenue and traction's `kpiRows`: only rows with a value, each with its `as_of` | Grow's record gate (`canAccessProject`) |
| `raise_status` | Capital relationships' `commitmentsRead`, never Mercury (founder user id is null) | `capitalCanWork` |
| `project_progress` | Product roadmap's OKRs by column (`done`, `now`, `next`, `later`) and up to three Now objectives | Build's record gate |
| `interview_insights` | Customer research's card (`customerResearchCard`): held, booked or held, pain confirmed, solution-fit | Validate's record gate |
| `one_liner` | The Investor narrative's core one-liner (`readPositioning`) | the venture's own writer. An admin reads the narrative only with a reason on its page (D914), never through a draft. |

**When a block is null.** A block is `{ block: null }` when:
- the member cannot read it;
- its module has nothing recorded;
- its read fails (logged by kind only).

**Never a guessed figure.** A KPI with no value is left out. Commitments whose amount is not recorded say "Committed amount: not recorded", never $0.

### 5. Drafts

**`POST /api/mail/drafts`** takes `{ person, intent, tone, length, refs[], blocks[], project?, estimate? }`.
- The pack is read again at the press.
- A ref outside it is 404 "Record not found.".
- The asked blocks are computed now.

**The prompt carries only what was ticked.**
- It holds the ticked items' text and the blocks that have something to say.
- Of an unticked record it carries only the recipient's name (the record's title), which the greeting needs.
- The system prompt forbids inventing a figure, name, date, promise or quote.
- The model answers JSON `{subject, body}`. An answer without both is 503 `draft_unreadable` and is not stored; the run may still be charged, and the sentence says so.

**The stored row.** One `mail_drafts` row holds:
- the person ref, intent, tone and length;
- the sources (ref, label, `as_of`, link);
- the blocks (kind, `as_of`, link);
- subject and body;
- model, tokens and charge.

The draft lists its sources.

**`POST /api/mail/drafts/:uid/revise`** takes `{ instruction }`: `shorter`, `warmer`, or the member's own words, up to 500 characters.
- It reads the parent's person, refs and blocks again, through the same reads, so a record the member can no longer read is refused.
- It sends the current draft with the instruction.
- It writes a new row whose `parent_uid` is the parent. Every version stays.

**`GET /api/mail/drafts[?person=]`, `GET /:uid` and `DELETE /:uid`** answer the member's own rows only. Another member's draft is 404 "Draft not found." Deleting a parent leaves its revisions with the parent's uid.
