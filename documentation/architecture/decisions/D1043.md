## D1043 — Approval notices, co-marketing paging and the expert decision record

Issue #2891, Approvals part 5 of #2390. Depends on D1039 (#2887), now on main.
Migration **577** is additive; no existing migration is edited.

### Co-marketing

`GET /api/comarketing/admin/queue` remains an Admin read. It accepts `status`
(proposed by default, or approved/rejected/published/withdrawn/all), `limit`
(1–200) and nonnegative `offset`. Supplying either paging parameter opts into
pages, with a default limit of 25. Existing callers that send only a status
keep their complete list (`limit: null`), so older consoles lose no pitches.
Rows are oldest first by SQLite
datetime, then id for ties. `total` counts the full matching queue, independent
of its page. Invalid filters are coded 400 refusals. Failed reads return 503
`queue_unreadable`, carrying no invented empty queue.
The row query joins partners, and one grouped attribution query covers the
whole page. Query count does not grow with the number of pitches returned.
Decision response counts are read before the conditional write; afterward the
response uses the confirmed transition values, so a response-only database
read failure cannot present a saved decision as failed.

Each row retains its lifetime `attribution` and adds `attribution_30d` counts
for visits, signups, leads and conversions. The response's `attribution_30d`
is over the **entire status-filtered queue**, not the current page; use
`status=all` for the total across all pitches. The window starts 30 days before
the read (`attribution_since`) and excludes future timestamps.

Approve, decline and publish use the existing `requireAdmin` routes and
transition rules. A conditional update prevents two simultaneous decisions
from both succeeding or sending notices. The actor is recorded in the pitch
and activity log. Each successful decision calls the existing notification
publisher for **inbox and email** to the submitting partner account. Declines
include the stored reason; publishing includes the published link. Replays
and refused decisions send nothing. Publishing requires a complete HTTPS URL,
without embedded credentials, at most 500 characters after URL parsing.

### Wellbeing expert review

Migration 577 adds `decision_state` (pending/verified/declined), `decided_by`,
`decided_at`, `decline_reason`, licence number/issuer/expiry, and a review
version to `experts`. Existing verified experts remain verified, with NULL
decision actor/time because those facts were not recorded. No date is invented.
`expert_review_decisions` records each verify, remove-verification, decline,
hide and restore in the same D1 batch as its state change. The decision token
ties the history insert to the successful conditional update. A failure rolls
both back; a competing update returns 409 and sends no notice.

The standing verify/hide paths remain in `routes/wellbeing.ts`. Verification
requires `verified: true`, `credentials_checked: true` and `expected_version`
matching the reviewed record. This is the admin's explicit credentials-check
attestation; the platform does not claim it has checked an external issuer.
A recorded expiry in the past refuses verification. Credential fields may be
NULL when Not recorded; an absent licence is not fabricated. Verifying and
restoring visibility retain the branch-suspension gate. Removing verification,
hiding and declining remain available as takedowns. HQ's Admin freeze still
applies to decisions. Declines need a trimmed reason of 10–4000 characters.
An ordinary admin may read their own expert record but cannot verify, decline
or restore it; those decisions require Super Admin. Self-takedowns stay open. Removing verification requires an actually verified
record; it cannot clear a decline or put it back into the waiting queue.
Visibility-only changes retain the current review actor/time and put their own
actor/time in the decision trail.

`routes/wellbeing_expert_review.ts`, mounted by the existing Wellbeing router,
adds:

- `GET /api/wellbeing/admin/experts`: oldest-first paged review read, with
  complete total, `state=all|pending|verified|declined`, limit up to 200 and
  offset. Includes inactive/unverified records for review, not just directory
  matches; it is not capped at 50. Known development samples are excluded from
  both rows and totals. An ordinary admin cannot see another admin's
  credential record; Super Admin can. The older Admin directory read also
  now includes each expert's actual `created_at`. Private file metadata is
  loaded in one batch for the page, without a query per expert.
- `GET /api/wellbeing/admin/experts/:uid/review`: that record and its decision
  trail, with the same permission check.
- `POST /api/wellbeing/admin/experts/:uid/decline`: records the decision and
  reason and tells the expert. Verify/hide notices use the same existing inbox
  and email publisher. Legacy profiles with no linked account cannot be
  verified or declined as though they could be notified; they may still be
  taken down, with no invented recipient.
- `GET/PATCH /api/wellbeing/experts/me/credentials`: the caller's own licence
  metadata, record and private-file metadata. PATCH accepts `licence_number`,
  `issuer`, `expires_on`; expiry is a real YYYY-MM-DD date or NULL. Credential
  changes reset verification/current decision and advance the version; the
  prior decision trail remains. A stale review cannot approve changed evidence.
- `PUT /api/wellbeing/experts/me/credentials/files`: raw PDF/PNG/JPEG bytes,
  Content-Type, matching Content-Length and optional X-File-Name. Bytes are
  streamed with a 10 MB bound and checked against the declared type. At most
  ten files per expert. R2 uses fresh generated keys under a private prefix.
  Database failure removes the new object; the upload cannot attach to a
  different expert. Uploading resets verification/version atomically with
  its metadata insert.
- `GET /api/wellbeing/experts/credentials/files/:fileUid`: private download
  for the owner or permitted reviewer. Others get 404; another admin's file
  needs Super Admin. No bucket URL/key is returned. Downloads are attachments,
  private/no-store, nosniff and sandboxed.
- `DELETE /api/wellbeing/experts/me/credentials/files/:fileUid`: owner-only
  removal, also resetting verification/version. R2 is deleted first; a storage
  failure keeps the metadata/key for retry and changes no review version.
  If the later database batch fails, its metadata row is retained and the
  same deletion can retry R2's idempotent delete. No lost cleanup reference.

Saving normalized credentials unchanged (including an empty patch) preserves
the verification/decline, reason, actor/time and review version. Only a real
credential change invalidates the review.

The expert's own credential reads/edits omit the deciding admin's internal
user id; Admin review reads and the decision trail retain the actor.
Public expert DTOs never include these credential fields or files. New reads
and failed D1 batches return a coded 5xx, never fake zeros or empty evidence.
Approvals' waiting-expert count and rows now exclude declined records, the
predicate D1041 explicitly deferred to this part. Co-marketing and Wellbeing
lane captions name the partner/expert they now notify instead of Nobody yet.
All expert decisions use the same Wellbeing audit record; Community's
privacy-safe activity feed includes declines without a name or decline reason.
The existing notification publisher honours preferences and handles provider
delivery failures under its standing best-effort policy; no email-delivered
claim is returned by these APIs.

### Strategic access

The existing D957 `POST /api/refer-earn/admin/strategic-access/:userId/decision`
remains the only decision route. It passes its existing `note` to the service;
a decline requires a trimmed reason of 10–4000 characters. The member gets
an inbox/email notice for each successful grant or decline, with that reason
on a decline. The member's request note stays unchanged; the standing Admin
audit records the decision's note and actor. Admin, HQ-freeze, branch-suspension
and D985 program-grant guards remain in place.

The service checks the existing request before the conditional update and
returns the confirmed status/time after a win. Competing or repeated decisions
send no second notice. No successful decision depends on a post-commit response
read. The route records the actor before attempting delivery. The read/save
refusal covers only the decision stage; audit and notification failures after
a confirmed write keep its success response and are logged separately.
No second route or additional migration is introduced.

### Verification

New route tests start from the schema baseline and **every post-cutoff
migration**, then drive real Hono handlers and SQLite, including migration
backfill, paging and attribution windows, inbox/Gmail delivery, races and
replays, credential invalidation, privacy, role/branch/HQ gates and transaction
rollback. R2 and Gmail transports use synthetic fixtures; no live member
content, production database or email provider is accessed. Mutation and full
suite results are recorded in the PR.
