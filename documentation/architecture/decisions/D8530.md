## D8530 — VentureSpace data lifecycle: one inventory of every store and what each event does to it, checked in CI (#8530)

- **Status:** built by S26, 2026-11-25 (#8530; tracker #8509 row E6). First PR: every store is listed; answers nobody has decided are `unspecified` and put to the owner below.
- **Migration:** none. No production code path changes; this records and tests what the code does.
- **Why:** `services/projectTrash.ts` and `project_deck_hard_delete_3747.test.ts` show a good lifecycle for deck assets, and `documentation/operations/PROCESSING_AND_RETENTION_5510.md` describes retention in prose, but nothing tied a new table or R2 prefix holding a venture's data to an answer for move, archive, restore, hard delete or account erasure. A closed data-subject request was the only evidence of erasure.

### 1. The inventory is code

`cloudflare-worker/src/services/ventureSpaceDataInventory.ts` (`VENTURE_SPACE_STORES`) is the single source: 381 stores. 368 D1 tables (every table with a `project_id` or `company_id` column, `projects` itself included), 8 R2 key templates in `studioos-files` under a venture's or a company's id, and 5 other stores (the two Vectorize indexes, the agent scope object, the two queues). No KV namespace keys a venture.

Each store answers each event with one of **follows**, **removed** (`by` names the code path), **kept** (with the reason), **not applicable** (with the reason), or **unspecified** (with `today`, what the code does now, and the question below). The events are the real paths:

| Event | Code path |
|---|---|
| move | `POST /api/projects/:id/move` (`services/projectMove.ts`, `afterMove`) |
| archive | `DELETE /api/projects/:id`: the venture goes to Trash (`deleted_at`, D1135) |
| restore | `POST /api/projects/:id/restore` |
| hard delete | `hardDeleteProject`: HQ's `DELETE /api/admin/projects/:id/hard-delete` and the 30-day trash sweep. The project route's `?hard=true` refuses HQ on a company's venture (#5366), so the test uses the admin route |
| account erasure | `eraseAccountAgents` (D1530), the only erasure code there is; the rest is manual (D168) |

What the code does today, in numbers: move, archive and restore leave every row and object where it is, so every venture-keyed store **follows** (move: 289 stores, archive and restore: 324) and every company-keyed one is **not applicable** (52). Hard delete **removes** 164 stores (25 by name in `hardDeleteProject` or `eraseAgentData`, 136 by `ON DELETE CASCADE`, `deck-images/`, the search vectors through the `embed_delete` job, and the venture row) and **keeps** 2 with a reason (`activity_logs`, the audit trail; `capital_calls` with receipts, financial records). Account erasure removes one store's rows (`agent_memory_notes`).

### 2. CI

- `cloudflare-worker/test/venturespace_data_inventory_8530.test.ts` fails when a table with a `project_id` or `company_id` column is not listed (or a listed one no longer exists), when Worker source builds an R2 key `` `<prefix>/${<project, venture, company or pid>}` `` under an unlisted prefix (`refused/` is a key name only, `NOT_STORES`), when a KV write names a venture, when an answer is malformed, and when an unspecified answer's question, or the store it lists, is missing from this file.
- `cloudflare-worker/test/venturespace_data_lifecycle_8530.test.ts` (with `_venture_stores_8530.ts`) builds the real migrated schema once, writes a row for the venture and one for a control venture in every D1 store (every column that references `users` names that venture's owner; every other reference is made real), puts an object under every R2 prefix, runs each event through its route or service in a rolled-back savepoint and reads every store. A **removed** row must be gone, a **follows** or **not applicable** row byte-identical, a **kept** row still there, an **unspecified** row what `today` says, and the control venture untouched. Each of the 54 stores marked `refuses` is proved one at a time: with its row the hard delete answers 409 and nothing is removed. A **removed** answer must name a path that names the table, or a real `ON DELETE CASCADE`. Erasure is checked against the stores, never a request record.

Mutation check (both test files): 19 mutations, 19 caught, 0 equivalent. Among them, a migration that adds `CREATE TABLE synthetic_8530_probe (id INTEGER PRIMARY KEY, project_id INTEGER)` fails the coverage test.

### 3. Questions for the owner

### Q1 What erasing the venture owner's account does to the venture's data

Every store except `agent_memory_notes` (removed) is unspecified for account erasure (380 answers). The platform performs no account erasure (D168); `eraseAccountAgents` removes the agent memory of agents the account sponsors and cancels their open tasks (`scope_tasks`, today `changed`). Everything else stays.
**A** (my pick): an account erasure leaves a venture that has other members to them, and treats a venture whose only owner is erased as a hard delete, with the same answers; a follow-up issue writes that erasure path and flips these answers to what it does.
**B**: erasure removes every row the account wrote (columns naming the user), whatever venture it is in.
**C**: leave erasure manual (D168) and keep these answers unspecified.

### 4. Limits

- The coverage rule is the issue's: a `project_id` or `company_id` column, or a key template under a venture's or a company's id. A store reached only through a parent (`deck_share_views` through `deck_id`) is covered by its parent's answer and is not listed; a template whose interpolation is not named after a project, venture or company (or `pid`) is not found.
- Generic rows cannot reach every condition a code path looks for. Where the test needed one, `_venture_stores_8530.ts` says so (`OVERRIDES`, `linkAgents`).
- The test runs on the canonical schema. `projectTrash.ts` records that production D1 once differed from the migrations; the D1 drift guards own that.
