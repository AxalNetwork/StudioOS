## D7151 — The release records, before any write, whether it could be rolled back automatically (#7151)

**Decided.** Every production release classes itself `auto`, `auto-additive` or `manual` before it writes anything, and records the class, the reasons and the Worker version a rollback would return to. It is report-only: nothing in the release reads the class. #7152 is the task that acts on it, and under the owner's decision E1 on #7144 it may roll back by itself only a release classed `auto` or `auto-additive`, and only after a report-only period.

**Why these three classes.** A Worker rollback reverts code, never D1 (`documentation/operations/DEPLOY.md` §3), so after a rollback the previous Worker runs on the schema this release migrated. Cloudflare also refuses a rollback across a Durable Object migration, and to a version whose bound resource no longer exists. So:

- **`auto`.** No pending D1 migration, no Durable Object migration tag after the live one, no non-variable binding of the live version missing from this release, and exactly one live version to return to. The previous Worker would run on exactly the schema and bindings it ran on before.
- **`auto-additive`.** As `auto`, except that every pending statement only adds something the previous Worker never names: a table (`CREATE [VIRTUAL] TABLE`), a view, a non-unique index, a column that is nullable or has a default and whose `CHECK` names only itself or columns this same release adds, or anything (rows, a unique index, a trigger, an `UPDATE`/`DELETE`) confined to a table this same release creates. Old code ignores columns it does not select and never reads tables it does not know.
- **`manual`.** Anything else, each with its reason, file and line:
  - a drop (`DROP TABLE|INDEX|VIEW|TRIGGER`, `ALTER TABLE … DROP`) or a rename: the previous Worker still uses the old object;
  - a `NOT NULL` column with no default: the previous Worker inserts rows without it;
  - a new column whose `CHECK` names an existing column, or whose foreign key has a non-NULL default: it can refuse the previous Worker's writes to the other column (762's `close_reason` reads `board_column`);
  - an `UPDATE` or `DELETE` on an existing table, or rows inserted into one: the previous Worker reads rows it never wrote or does not know;
  - a `UNIQUE` index or a trigger on an existing table: they act on the previous Worker's writes;
  - a statement the classifier does not recognise (`PRAGMA`, `WITH …`, `SELECT`), an unreadable file, or an unreadable plan;
  - a pending Durable Object migration tag, a live tag not in this release's list, or a live tag that could not be read;
  - a removed binding (a variable, JSON value or secret is not one: those live in the version itself), or live bindings that could not be read;
  - no single live version (none recorded, or traffic split across versions).

**Unknown means manual.** The classifier only names what is safe; everything else, including anything it cannot read, is `manual`. A table rebuild is caught by its drop and rename. One known gap, recorded rather than closed: `CREATE TABLE IF NOT EXISTS` of a table that already exists in production is read as a new table, so rows inserted into it after would read as additive. Migrations do not do that today.

**Where it runs.** `scripts/lib/rollbackClass.mjs` is the pure classifier; `scripts/release-rollback-class.mjs` is the step "Record the release rollback class" in `cloudflare-worker-deploy.yml`, after "Record migration plan and previous Worker version" (D5501's preflight) and before the final admission check, the D1 migrations and the publish. Its inputs:

- the pending D1 files: the `apply` lines of `migrate-d1.mjs --remote --dry-run`, which reads the `schema_migrations` ledger, read from `migration-plan.log`;
- the rollback target: the live version in `previous-deployments.json` (`wrangler deployments list --json`, newest deployment, one version at 100%), which the release already recorded;
- the live bindings and Durable Object tag: `wrangler versions view <id> --json` with the release's existing Cloudflare token. When the version does not report its migration tag, the step reads `wrangler.toml` at the commit the live version was deployed from (its `WORKER_DEPLOY_VERSION`) with the job's read-only GitHub token. No new credential.

The step is `continue-on-error`, the script catches its own faults as `manual` (`classifier-error`) and exits 0, and no step reads its outcome. It writes `rollback-class.json` and `rollback-class.md` into the release evidence artifact and the same Markdown into the job summary. The evidence keeps binding names and types only, never a variable's value or the version's author.

**Not built.** Performing the rollback (#7152). Reverting D1. Changing how migrations are written. A later task may let a migration declare its own class in a header comment (for example a `rollback: additive` line the classifier checks against what it reads); that is recorded here as an option and not built. Whether the version API reports `migration_tag` is unconfirmed until the first release run shows it; either way the fallback or `manual` applies.

**Verified.** `scripts/lib/rollbackClass.test.mjs` runs real migrations from `cloudflare-worker/sql/migrations/` for each class and each manual reason, a mixed release, and the release step's place and report-only shape in the workflow; every rule was mutation-checked with `scripts/mutation-check.mjs`.
