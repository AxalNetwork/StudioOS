## D9205 — The cron queue lease and the fail-closed rate-limit counters are atomic in AiGovernor (#9205)

### What was wrong

Both were a KV `get` followed by a KV `put`. KV is eventually consistent (a read can be served from cache for about
60 seconds) and takes about one write per second per key.

- `scheduled()` took `cron:queue:lease` that way, so two ticks could both take it, and a tick could still read a
  released lease and skip its minute.
- `bumpCounter` (middleware/rateLimit.ts) counted every request that way, so concurrent requests could read the same
  count and all pass a fail-closed bucket, and a failed write on one became a 503.

### What changed

Both now live in the existing `AiGovernor` Durable Object (`AI_GOVERNOR`), which applies its calls one at a time over
its own storage. `services/atomicLease.ts` holds the rules and the clients.

- **The cron lease** is one object, `cron-lease:cron:queue:lease`. `take` sets it only when it is free or expired
  (90 seconds, as before) and otherwise returns the holder; `release` clears it only for the holder that took it. The
  value is still the D201 lease-holder value, so a tick that finds it held records `deduped` or `skipped` as before.
  It stays ONE lease shared by every trigger (D201): one queue drain at a time. The trigger is part of the holder
  value, not of the object's name. On a failed take the tick runs, as it did on a failed KV read.
- **Every `failClosed` bucket's counter** (ai, register, promo_validate, admin_catalog_writes and the others marked
  `failClosed: true`) is one object per bucket and scope (`rate-counter:rl:<scope>:<bucket>`), holding its window and
  count; an alarm clears it after the window ends. A failed or stalled call keeps the bucket's policy: 503
  `rate_limit_unavailable`, under the same 2-second deadline.
- **Fail-open buckets stay on KV.** Their worst case is a small over-allowance, which they accept by design, and
  moving them would put every `/api/*` request (the `global` and `ip` buckets) on a Durable Object call.
- With no `AI_GOVERNOR` binding (unit tests, local dev without Durable Objects) both use the KV path they used before.

### Why AiGovernor and not a new class

`AiGovernor` already holds durable, serialised leases under named objects (D5338's `upstream-lease:<slug>`), and is
bound in all three `wrangler.toml` tables. `WorkGraphLease` is bound to one tenant, company and asset per object and
is refused while `WORK_GRAPH_LEASES` is off, so it does not fit. Reusing `AiGovernor` adds no class, no binding, no
migration tag and no `index.ts` export (D5615); `scheduled()` reaches the client by a dynamic import (HUBS.md).

### Deploy

Nothing for the owner beyond a normal deploy: no wrangler binding or migration changes. During the rollout an old
isolate (KV lease) and a new one (Durable Object lease) do not see each other's lease, so one minute may run twice,
as it could before. `queue-consumer.ts`'s `reserveAiBudget` is out of scope (#9172).
