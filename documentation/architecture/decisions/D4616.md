### 1. One validity rule, scoped to the owner

A session is active when it is not revoked, is inside its token's lifetime, and was minted after the account's
sign-out floor (`jwt_min_iat`). That is `services/sessionStatus.ts` (D4691), which HQ · Security already uses.

- **The list** (`GET /api/settings/sessions`) keeps history: every row the member has, newest first, each with the
  `status` that rule gives it (`active`, `revoked`, `expired`, `signed_out`, `unknown`), and `active_count`.
- **The count** on `/api/settings/security` (`active_sessions`) is the same statement as `active_count`. It used to be
  `revoked_at IS NULL` alone, so expired tokens and sessions ended by "Sign out everywhere" were counted as in use.
- **The owner filter is in the statement.** Both reads bind `s.user_id = ?` to the caller, and there is no unscoped
  variant in the member's path. The revoke still passes `ownerId` to `revokeUserSession`, so another member's row is
  a 404.
- **The session key is no longer returned.** The list used to send each row's `jti`; nothing on the page read it.

### 2. "This device" follows authentication's token choice

`currentJtiFromRequest` now asks `selectJwt`, the function `getCurrentUser` uses. It applies the same rules for a
cookie, a Bearer token, or both. It used to read the Bearer header only, so a browser signed in by cookie (the normal
case) had no "This device" row, no warning before revoking itself, and no sign-out after. Only an `active` row can be
the current one.

The card's behaviour is unchanged: it warns before revoking the current session and signs out afterwards. Rows that no
longer open a door say why ("Revoked", "Expired", "Signed out") instead of offering Revoke.

### 3. Display name is `display_name`

The Profile card's field labelled Display name wrote the account name (`users.name`) through the root PATCH. The
public profile and article bylines show `display_name` first, so an edit there could leave the preview and the public
page showing different names.

- **The field now reads and writes `display_name`** through the identity contract, `PUT
  /api/settings/profile/identity`. A blank value clears it.
- **The account's full name stays its own field.** It is edited under Account · Profile, and the hint says so.
- **One rule for the name other members see:** `effectiveDisplayName` is the display name when one is set, else the
  account name. The public profile serves it, and `GET /api/settings` returns it as `public_name`, with
  `display_name` as stored. The card's preview uses the same rule (`lib/displayName.js`).
- **Article bylines agree.** They read `COALESCE(u.display_name, u.name)`, which matches because `trimOrNull` stores
  a blank display name as NULL.

### Not changed

- What makes a token stop working (`getCurrentUser`, the revoke routes).
- HQ · Security's list and counts.
- The card layouts. The Account redesign (#4955) and the account-menu work (#3704, #4472, #4473) own them.
