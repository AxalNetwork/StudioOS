### 1. Spec Docs → Solution design proposals

A Doc chosen for Solution design is read with `documents.get`.
- **What is kept:** its title and its headings (Heading 1 to 3, at most 40). A paragraph is never stored.
- **The proposal:** one per Doc, in `google_workspace_proposals` (module `solution_design`, kind `design_note`, `source_key` = the file id).
- **The fingerprint** is the SHA-256 of the title and headings:
  - the same text proposes nothing new, whatever the status, so a dismissed proposal stays dismissed;
  - changed text puts it back to pending.
- **Accept** (`POST /proposals/:id/accept`) writes one `solution_design_notes` row:
  - the Doc's title, and the headings as an outline;
  - `source_url` is the Doc, and `source_path` is `google_docs/<file id>`;
  - the ledger links it (`<file id>:design_note`, module `solution_design`).
- **A later Accept of the same Doc** updates that note, never a second one. If the founder deleted the note, a later Accept is their decision and writes it again.
- **Dismiss** (`POST /proposals/:id/dismiss`) works once.
- **Concurrency:** both decisions are conditional on the proposal still being pending, so a race decides it once (409 otherwise).

**Why `google_workspace_proposals` and not `solution_design_proposals`** (the issue asked which):
- The latter's `repository` and `path` columns are GitHub's shape.
- Disconnect and Stop using clear `google_workspace_proposals` (D1091), and would leave Google proposals behind in the GitHub table.
- The note itself goes in the one notes store, so Solution design reads a single list.

### 2. A roadmap Sheet → Product roadmap

A Sheet chosen for Product roadmap lands nothing until it is mapped (GW4). An unmapped Sheet is not even read.

**The mapping** is part 2's draft (`PUT /api/connectors/google-workspace/files/:uid/mapping`), validated here before any write:
- `{ header_row (0–10, default 1), columns: { objective, quarter, status, key_result?, progress? } }`;
- each column a letter A–Z, the three named fields required, and no column used twice;
- anything else and the Sheet lands nothing (`needs_mapping`).

**Rows:**
- Each row with an objective is one fact. Its ledger key is `<file id>:row:<hash of the objective>`, so it follows its row when rows move.
- A blank objective, or one repeated in the Sheet, is counted and not landed.
- Rows are read from `A1:Z501`: up to 500 after the header.

**The one-owner rule (`fedOwnership.ts`):**
- **A new row** creates a `roadmap_okrs` item: objective, quarter, a lane from the status, and the key result with its progress.
- **A row the ledger holds** updates its own item only, and only while this connection is that item's one owner.
  - An item another connection also claims is held, not written (`held`).
  - A GitHub-linked, Notion-linked or hand-entered row is never written; the test diffs them field by field.
- **A row whose item the founder deleted** stays deleted and is unlinked (`deleted_kept`), on every later sync.

**Values:**
- **Status words → lanes:**
  - Done or Shipped → Done;
  - In progress or At risk → Now;
  - Planned or To do → Next;
  - Backlog → Later.
  - An unknown word moves nothing: a new item starts in Next, and an existing one keeps the founder's lane.
- **Progress** is a percentage — "40%", "40", or "0.25" read as 25% — or nothing. It is never a guess and never 0 for a blank cell.
- **Key results** are stored as `[{ text, current, target: 100, unit: '%' }]` only when the Sheet has a key result or a progress. None is invented.

### 3. The routes (`/api/cycles/build/google`)

| Route | What |
| --- | --- |
| `GET /?project=` | From Google (GW3): the files with when each was last read and whether a Sheet is mapped, the pending proposals, and the roadmap items this connection owns, as they stand now |
| `POST /sync` `{ project }` | Reads the venture's chosen Docs and mapped Sheets now. Per-file outcomes and totals: proposed, changed, unchanged, created, updated, held, deleted_kept, blank, repeated, needs_mapping, unreadable |
| `POST /proposals/:id/accept` `{ project }` | §1 |
| `POST /proposals/:id/dismiss` `{ project }` | §1 |

**The scope check is part 2's:** a member with write access to the venture, the company enabled for this connection, and never a support session.
- **One unreadable file** is marked `unreadable` with its error code, and the next file still syncs.
- **Errors are codes.** No cell, heading or title is logged.
- **Accept and Dismiss** are recorded in the Build cycle's activity, as GitHub's are.
