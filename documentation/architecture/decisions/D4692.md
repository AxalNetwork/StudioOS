## D4692 — Practice: one bookability rule, two lifecycle graphs, conditional writes (#4692)

- **Status:** Built for #4692 (Practice audit 2/6), 2026-11-07. It covers the Worker, `Sessions` and `Engagements`.
- **Builds on:** migration 240 (availability rules, `blocked_reason`), migration 238 (engagements), D573 (booking links), D976 (paused advisors), D4703 (the `AND status = ?` guard on a booking transition).
- **Migration:** `202611072048_advisor_lifecycle_events.sql`. One new append-only table, `advisor_lifecycle_events`. No existing table is rebuilt and no applied migration is touched.

### What the audit found, and what still reproduced on `main`

1. A blocked slot was listed and booked: it reproduced. `GET /:uid/slots` filtered only `is_cancelled`, and the booking handler never read `blocked_reason`.
2. The saved rules (paid cap, notice, buffer, blackouts) were consulted by nothing that sold an hour: it reproduced.
3. A delayed confirmation overwriting a completion: it did **not** reproduce. D4703 had already made the booking UPDATE conditional on the status it read, with the row count checked. What was missing was a graph in one place, the engagement writes (still `WHERE id = ?`) and any record of who decided.
4. `signed → proposed → ended` bypassing the outcome: it reproduced. The refusal looked at the current lane, and `/advance` allowed any lane from any lane.

### The eligibility rule (`services/advisorBookability.ts`)

`slotRefusal(slot, context, { paid, now })` is the only place the rules live. The slot list calls it for every slot; the booking handler calls it before writing. The first rule that fails is the answer.

| # | Rule | Refusal |
|---|---|---|
| 1 | Advisor is active and not paused (D976) | 404 `advisor_inactive`, 409 `advisor_paused` |
| 2 | Slot is not cancelled | 404 `slot_cancelled` |
| 3 | Slot is not blocked (the reason is private and never sent; reads as "Slot not available") | 404 `slot_blocked` |
| 4 | Slot has not started | 400 `slot_past` |
| 5 | pending + confirmed + completed bookings are under capacity | 409 `slot_full` |
| 6 | It starts at least `min_notice_hours` from now (NULL = no rule) | 409 `inside_notice` |
| 7 | It overlaps no blackout window, read in the rules' zone, else the advisor's, else UTC | 409 `blackout` |
| 8 | No other booked slot of this advisor is within `buffer_minutes` of it | 409 `buffer` |
| 9 | A PAID type: that Monday-to-Monday week (advisor's zone) holds fewer paid bookings than `weekly_paid_cap`. A cap of 0 refuses every paid session; NULL is no cap | 409 `weekly_cap` |

"Paid" means the type has `price_cents > 0` and is neither included nor a free intro. A booking with no type is not paid. The booking-link rules (audience, active type, `requires_payout_account`) stay in `usableBookingLink`, which the booking handler already ran; they are link-scoped, so the plain list has no link to apply them to.

**The list.** `GET /api/advisors/:uid/slots` returns only slots that pass. `?session_type_id=` asks for a type (a paid type meets the cap). `upcoming_only=false` (history) is the advisor's and an admin's only; anyone else gets the bookable list. A full slot is no longer listed.

**The write.** The booking INSERT is one `INSERT … SELECT … FROM advisor_office_hour_slots s WHERE …` that re-asserts every rule another request can change between the read and the write: not cancelled, not blocked, notice, capacity (counted inside the statement), advisor standing, buffer, weekly cap, and the D573 type, link and once-per-client switches. A statement that inserts nothing is re-evaluated by the shared function to name the rule, so the loser of a race is refused (`slot_full` for the capacity race) and only the winner holds the hour. The old "insert, count, cancel the loser as `capacity_race`" step is gone; rows written under that reason stay withdrawn. Blackouts depend only on the slot and the saved rules and are checked before the write, not inside it.

### Blocking and cancelling

- Blocking a range **never touches an existing booking.** A slot holding a pending, confirmed or completed booking is skipped and counted in `skipped_booked`; the advisor cancels such a booking (or the slot) as a separate act, because that tells the client.
- The block is one conditional UPDATE (`… AND NOT EXISTS (live booking)`), and the booking INSERT refuses a blocked slot. Whichever statement the database runs first wins, so a blocked slot never carries a booking.
- Cancelling a slot is one batch: the slot, one decision row per open booking (actor: the advisor), and the cancel of its `pending`/`confirmed` bookings.

### The booking graph (`BOOKING_TRANSITIONS`)

| From | To |
|---|---|
| `pending` | `confirmed`, `cancelled`, `completed`, `no_show` |
| `confirmed` | `cancelled`, `completed`, `no_show` |
| `completed`, `cancelled`, `no_show` | (final) |

Every transition route reads this table (`bookingMoveAllowed`); the slot-delete batch cancels from `bookingSourcesOf('cancelled')`. Who may press which verb is unchanged (advisor: confirm, complete, no-show; either party: cancel).

### The engagement graph (`ENGAGEMENT_ADVANCE`) and "ever signed"

| From | `/advance` may move it to |
|---|---|
| `drafting` | `proposed`, `signed`, `ended` |
| `proposed` | `drafting`, `signed`, `ended` |
| `signed` | `renewal_due` |
| `renewal_due` | `signed` |
| `ended` | (final) |

These are exactly the moves the board offers. A signed or renewal-due engagement ends only through `/renewal` with decision `ended`.

**Whether an engagement was ever signed is read from its history, not its lane:** `cycles > 0` (signing starts the first term; `cycles` never goes down) or a `started_at`. The outcome requirement follows that fact (`advanceRefusal`): `/advance` to `ended` is refused with 409 `outcome_required` for any ever-signed row, and `/renewal` accepts `ended` for an ever-signed row in any unfinished lane (a renewal still needs it under contract). `signed → proposed` is no longer a move at all, and a row that reached an earlier lane some other way is held to the same rule. The engagement DTO carries `ever_signed` so the page does not offer the lane move. No column was added for it.

### Conflict semantics

Every booking and engagement state change is `UPDATE … WHERE id = ? AND status = ?` (engagements: `AND lane = ? AND cycles = ? AND outcome IS ?`), the affected-row count is checked, and a stale write is **409 `changed_while_looking`**: "This record changed while you were looking at it. Reload it and try again." It names nothing about the record or the other party. Concurrent confirm/complete and confirm/cancel therefore leave one valid final state and the loser changes nothing.

A booking that is not the caller's reads as the same 404 "Booking not found" as one that does not exist, for every verb (it was a 403 for a stranger). A party who may not press that verb still gets 403.

### Who decided, and when

`advisor_lifecycle_events` holds one row per decision: subject (booking or engagement), advisor, from and to state, the renewal `decision` when there is one, `actor_user_id`, `actor_role` (advisor, founder or admin), an optional reason, and the time. It is written in the same batch as the UPDATE and only if that UPDATE changed a row (`WHERE changes() > 0`), so a stale write leaves no event and a winner cannot lack one. It records: booking confirm, complete, cancel and no-show (and each cancel a slot cancellation makes); engagement lane moves including signing, and renewal decisions.

### The pages

`EngagementsZone` shows the Worker's refusal as written, offers "Reload the engagements" on a 409 conflict, leaves the typed decision as it was, offers no `Ended` move for an ever-signed row, and its decision form offers only `Ended` for a row that is not under contract. `SessionsZone` shows the Block refusal as written and offers a reload on a conflict, keeping the dates in the form.
