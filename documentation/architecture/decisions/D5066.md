### 1. Next action: every actionable source, not formation steps alone

`company()`'s card combined three sources into one list (`combined`: Lab incorporation milestones, formation
steps, entity obligations — decision 8 of #1693), but its next action only ever inspected
`steps.find(s => s.state !== 'done')`, a plain, unordered scan of formation steps. An overdue obligation or an
unfinished Lab step could sit at the top of the card's own table with nothing in the next-action slot naming it,
while an unrelated formation step with no due date at all could win just by being first in `formation_steps`'
sort order.

**Fix:** the next action is read from `combined` itself, after it is built — the same rows the Due and State
columns already draw, so the priority used here can never disagree with what the table shows next to it.

```ts
const FILING_RANK: Record<string, number> = { overdue: 0, due_soon: 1, upcoming: 2 };
const openFilings = combined.filter(r => r.keys!.state !== 'filed');
const nextFiling = openFilings.length ? openFilings.slice().sort((a, b) => {
  const byRank = FILING_RANK[a.keys!.state as string] - FILING_RANK[b.keys!.state as string];
  if (byRank !== 0) return byRank;
  const ad = a.keys!.due as string | null, bd = b.keys!.due as string | null;
  return ad == null && bd == null ? 0 : ad == null ? 1 : bd == null ? -1 : ad.localeCompare(bd);
})[0] : null;
```

**Priority order chosen: overdue, then due soon, then any other open item** (upcoming — a general open step or
obligation with no imminent date, or an unfinished Lab milestone, which never carries a deadline of its own;
see item 2). Ties keep `combined`'s own order (Lab, then step, then obligation — unchanged from decision 8) and
then the earliest due date. This was the only ordering the issue's acceptance criteria pinned down explicitly
("preferring overdue/due-soon work before general open steps"; the mixed-state test requires the overdue
obligation to win over an open Lab step), so no owner call was needed — the only choice left open (the
tie-break among same-priority items) follows the list's own existing, already-tested order rather than
inventing a second one.

The next action's own link is unchanged: `next()` always points at the module page
(`/build/company-creation?project=<id>`), never at one record — true for every one of the six Build cards
before this PR, so Company Creation keeps the same contract as Founding team, Product roadmap and the rest. The
text (`Complete <title>`) now names whichever record is the true highest-priority item, across all three
sources, instead of only ever naming a formation step.

Boundary tests (`cycle_records_build_d690.test.ts`, test 17): an unfinished Lab step alone produces the next
action; an overdue obligation inserted alongside it wins instead (the mixed-state case the acceptance criteria
calls out by name); a due-soon obligation then outranks both a general open step with no due date and the open
Lab step.

### 2. No open obligation is silently capped at three

`company()` read open entity obligations with `ORDER BY o.due_date, o.id LIMIT 3` and fed those rows straight
into `combined`, the module's authoritative `rows`. **Chosen: remove the cap — real pagination, not a new
preview pattern.** This is not the same shape as #5067's "Feedback it answers" fix (item 2 of the issue invites
following that pattern, but it does not fit here): #5067's fix was for a **record section**
(`SectionSpec.read(ctx, id, record)`), which has no page parameter in its contract at all, so a trailing
"Showing the latest N of TOTAL" row with a link elsewhere was the only option. Company Creation's obligations
are not a section — they are rows in the **module's own list**, and every Build module's list already has a
complete, generic pagination mechanism: the route (`app.get('/modules/:slug')`, `cycle_build.ts`) runs every
module's `rows` through `pageBuildRows` (`services/buildCycleRecords.ts`, D690/#1693) unless a module sets its
own `paged` (as Solution design does for SQL-level paging past hundreds of features). Company Creation never
set `paged`, so once the `LIMIT 3` is gone, `pageBuildRows` already gives the list a real `total`, `page` and
`page_size`, the same filters (`state`, `due_window`) and the same sort the table already exposes for every
other row — the frontend's shared module table (`CycleModulePage.jsx`) already renders search, filters, sort
and pages generically from exactly that envelope, so no frontend change was needed. A silent cap inside one
module's own query, below a pagination layer that already existed for the whole list, was the bug; matching
#5067's trailing-row shape here would have built a second, narrower pagination story next to one that already
worked for every row in this exact list.

```diff
- WHERE o.entity_id = ? AND o.status = 'open' ORDER BY o.due_date, o.id LIMIT 3
+ WHERE o.entity_id = ? AND o.status = 'open' ORDER BY o.due_date, o.id
```

Boundary test (`cycle_records_build_d690.test.ts`, test 16): five open obligations (recorded()'s own plus four
more, past the old cap of 3) all reach `records.rows`, and `records.total` accounts for every row (13: 3 Lab
milestones + 5 formation steps + 5 obligations), proving the list's own total — never a silent cap — is what a
caller reads.

### 4. Proof: four explicit states, never the ambiguous dash

Two places built the filing's Proof text, and both collapsed "not yet due" and a genuinely missing proof into
the same shape:

- The list (`proofText`, `cycle_build.ts`): `'—'` for an upcoming filing with no proof key, `'Missing'` for a
  filed/overdue/due-soon one. A reader could not tell "nothing to chase yet" from "proof is actually
  outstanding" by looking at the character alone — and `'—'` is a plain string **cell**, not a `null` cell, so
  it never went through the generic cell renderer's own "Not recorded" treatment
  (`frontend/src/pages/cycles/cycleModel.js`'s `cellView`, which already turns a `null` cell into
  `{ text: 'Not recorded', nr: true }`); it displayed as a bare dash with no further meaning attached.
- The single record's Proof fact (`companyCreation.record()`, `services/records/build.ts`): `null` with the
  reason `'Not filed yet'`, for every step/obligation with no proof key regardless of whether it was overdue,
  due soon or not due for months — the same ambiguity, expressed as a generic reason string instead of a dash.

**Fix — the same four states in both places:**

| State | Meaning |
|---|---|
| `Stored` | A proof uploaded under `build-proof/` (unchanged — #1695/#461's own convention). |
| `Unreadable` | A key is recorded but it is not one `build-proof/` can open — a key typed before #461. Renamed from the previous `'Key recorded'`, which said nothing about whether it could be opened. |
| `Not expected yet` | No key, and the filing is not yet due or overdue (`upcoming`) — nothing to chase. Replaces the ambiguous `'—'`. |
| `Missing` | No key, and the filing is filed, overdue or due within 30 days — a real, actionable gap. Unchanged in meaning, now reached by every state that is not `upcoming`. |

```ts
// cycle_build.ts — the list's proofText
function proofText(key: unknown, state: string): string {
  if (typeof key === 'string' && key) return key.startsWith('build-proof/') ? 'Stored' : 'Unreadable';
  return state === 'upcoming' ? 'Not expected yet' : 'Missing';
}
```

```ts
// services/records/build.ts — the single record's Proof fact
const proof = f.source === 'lab' ? null
  : typeof f.proofKey === 'string' && f.proofKey ? (proofStored(f.proofKey) ? 'Stored' : 'Unreadable')
  : state === 'upcoming' ? 'Not expected yet' : 'Missing';
```

A lab- row keeps `proof: null` in both places, unchanged: the Lab's own incorporation order is that
milestone's record, not an uploadable proof, so "not applicable, tracked elsewhere" is a fifth, genuinely
different concept from the four states above, and was never ambiguous (the record's reason already said so
explicitly: "The Lab keeps this filing's record."; the list's cell was already `null`, which the frontend's
`cellView` already renders as "Not recorded" — distinct from the bare `'—'` this PR removes).

**#4600's pattern is preserved, unchanged.** This PR touches no upload or open-proof code path:
`uploadProof`/`openProof` (`services/records/build.ts`) are untouched, the "Open proof" action still appears
only for a key under this venture's own `build-proof/<project>/` prefix (so a renamed-to-`Unreadable` key still
gets no open action — the permission boundary did not move, only its label), and the file-type/size validation
in `uploadProof` is untouched. #4600's own partial-success retry (`FormLightbox`'s `memory`/`partial` handling
on the frontend, D4600) is a different code path entirely (the Add-filing form's own submit error handling) and
is not touched by this PR.

Boundary tests (`cycle_records_build_d690.test.ts`): test 11's "cells read the canvas's words" now expects
`'Unreadable'` for step-3 (a typed, pre-461 key) and `'Not expected yet'` for step-4 (no key, no due date) in
the list; test 2 now expects `{ label: 'Proof', value: 'Not expected yet' }` (no `reason` — `fact()` drops it
once the value is non-null) for step-4's single-record read, and `'Unreadable'` for step-3's. Between them, the
existing fixture already exercises all four states on one list read (step-1 `Missing`, step-3 `Unreadable`,
obligation-1 `Missing`, step-2 `Missing`, step-5 `Stored`, step-4 `Not expected yet`), so no new fixture was
needed for this item.
