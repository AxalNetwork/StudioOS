## D4643 — Learning completion and exam attempts are authoritative (#4643)

- **Status:** built 2026-11-06 by S09 for #4643 (Learning audit, work package 1 of 5). Parent #3726.
- **Migration:** `202611062214_learning_attempt_policy.sql`. It adds three nullable columns to `learning_exam_attempts` and one partial index. It applies ahead of the Worker safely.
- **Builds on:** D557 (progress), D558 (programs), D559 (exercises and exams, and its #1249 follow-up `services/learningCompletion.ts`).

### 1. Completion, by content type

| Content | Completes when | Who can say so |
|---|---|---|
| Reading or video lesson, standalone reading or video | the member presses "Mark complete" | the member (unchanged) |
| Webinar lesson | the member's own mark, as before; program views read attendance (D1124) | unchanged |
| **Exercise lesson** | a reviewer **accepts** a submission | the Worker, on acceptance (`completeAssessmentLessons`) |
| **Exam lesson** | one of the member's attempts **passes** | the Worker, on a passing submit |
| **Course** | every **required** lesson is complete (completed required over required, rounded; none required means no percent and never complete) | **the Worker only** (`refreshCourses`) |
| Program | each content's own status (D558), the course cell reading the course row or its lessons | unchanged |

- **What changes in `POST /api/learning/progress`:**
  - A lesson of kind `exercise` or `exam` posted as `completed` is refused: 409 `completed_by_result`, with the sentence saying what completes it. `started` is still the member's.
  - A course posted with any status or percent is not stored as sent. The server writes the course's derived row (`refreshCourses`) and answers it.
  - The frontend's "Mark complete" (`learningReads.js` `markLessonComplete`) keeps working unchanged. Its course post now returns the derived row.
- **Every completed lesson moves its course's row.** The member's own "Mark complete", a passing attempt and an acceptance all go through `refreshCourses`, so the course row, the course page's measure and program views agree.
- **Unchanged:**
  - An optional lesson never moves the course.
  - The member's UI never offered "Mark complete" on an exercise or exam lesson (the button is wired only to video and reading items), so no screen changes.
  - The no-downgrade rule (`PROGRESS_UPSERT`) still applies.

### 2. Exam attempts

- **One open attempt per member and exam.**
  - Start is one conditional `INSERT … WHERE NOT EXISTS (an open attempt) AND (no limit OR attempts used < limit)`, then a read of the open attempt.
  - Simultaneous starts (two tabs, a retried request), repeated starts and a resume all answer the same attempt. They use one allowance; only the start that inserted answers 201.
  - The partial index `idx_learning_attempts_open` serves the check and the resume read.
- **An attempt keeps the rules it started under.**
  - The pass mark, the time limit and the reveal policy are copied onto the attempt at start.
  - The deadline (start, resume, expiry), the grade (submit) and what a submitted attempt reveals are read from the attempt.
  - An author's edit applies to new attempts. A historical result keeps its own reading.
- **Attempts from before D4643** store none of the three (null). They are read with the exam's current rules, which is how they were always read; no row is rewritten.

### 3. Historical records: scope for review, no correction made

Before D4643, a member's own request could store a completed exam or exercise lesson, or a completed course row, that no result supports. D4643 stops new ones and changes no existing row. The queries below **count** the rows that disagree. They read only: run them with `wrangler d1 execute studioos-db --remote --command "…"` (owner-approved), and review the counts before deciding on any correction. A correction would be its own reviewed change, preserving valid results.

```sql
-- Exam lessons marked completed with no passing attempt by that member.
SELECT COUNT(*) FROM learning_progress p
  JOIN learning_lessons l ON p.subject_kind = 'lesson' AND l.uid = p.subject_uid AND l.kind = 'exam'
 WHERE p.status = 'completed' AND NOT EXISTS (
   SELECT 1 FROM learning_exam_attempts a JOIN learning_exams e ON e.id = a.exam_id
    WHERE e.uid = l.ref_uid AND a.user_id = p.user_id AND a.passed = 1);
-- Exercise lessons marked completed with no accepted submission by that member.
SELECT COUNT(*) FROM learning_progress p
  JOIN learning_lessons l ON p.subject_kind = 'lesson' AND l.uid = p.subject_uid AND l.kind = 'exercise'
 WHERE p.status = 'completed' AND NOT EXISTS (
   SELECT 1 FROM learning_exercise_submissions s JOIN learning_exercises x ON x.id = s.exercise_id
    WHERE x.uid = l.ref_uid AND s.user_id = p.user_id AND s.status = 'accepted');
-- Courses marked completed whose required lessons are not all complete.
SELECT COUNT(*) FROM learning_progress p JOIN learning_courses c ON p.subject_kind = 'course' AND c.uid = p.subject_uid
 WHERE p.status = 'completed' AND EXISTS (
   SELECT 1 FROM learning_course_modules m JOIN learning_lessons l ON l.module_id = m.id AND l.required = 1
    WHERE m.course_id = c.id AND NOT EXISTS (
      SELECT 1 FROM learning_progress q WHERE q.user_id = p.user_id AND q.subject_kind = 'lesson' AND q.subject_uid = l.uid AND q.status = 'completed'));
```

These counts were **not run** from this session: production data is outside it.
