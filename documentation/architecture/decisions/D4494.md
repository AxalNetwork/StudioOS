## D4494 — Distribution Inbox and the manual reply boundary (#4494)

The Inbox groups the selected venture's customer contacts by UID, combining their recorded contact replies with mail_sent rows belonging to the current member and addressed to that contact. Mailbox messages are read only from that member's active can_read accounts, and only from conversations resolved from an email Axal sent. Another venture's UID is not found; another member's mailbox is never joined. Support sessions cannot enter this Inbox. The project read gate is the existing Grow canAccessProject rule. Accepted readers may mark their own messages read; that changes no contact or venture data.

The existing contact log records neither channel nor personal unread state. The additive migration adds grow_inbox_reads keyed by user, contact and message digest. Current rows have no channel column and remain Contact log, never an invented Email or WhatsApp reply. The reader accepts optional recorded channel metadata if the contact store later supplies it; no unused channel column or second channel store is added here. A receipt marks exactly the inbound keys the viewer loaded, so an arrival during reading remains unread. The write is attributed to the caller. A single bound JSON snapshot inserts all receipts alongside its audit in one atomic D1 batch; an audit failure rolls back the whole snapshot, including long threads. Mail receipt keys are digests, not copied addresses or message bodies. No second contact, campaign or messaging store is introduced.

Every unread source must finish successfully before a count is returned. Source failures, malformed responses and bounded/truncated reads yield null, never an invented zero. Reads are bounded to 500 contacts, 5,000 contact messages, 1,000 sent rows, 50,000 personal receipts, 30 mailbox threads and 10 pages per mailbox thread; a hit limit is unreadable rather than an empty Inbox. The tab badge and Overview's Replies row consume the same successful count. Channel rows without a recorded contact reply or readable connector say Not connected. Inbox and thread reads have skeletons; a successful empty read says No replies yet, while failures say Unreadable.

Outlook's existing listThread path expected a conversation ID, although mail_sent stores the sent message's internetMessageId or Graph ID. Resolve that saved message under /me before reading its conversation. Retain the previously granted Mail.Read scope on the read refresh and seal rotated credentials through the existing accounts service. Keep the complete Graph nextLink URL, validating its host, mailbox path, conversation filter, selected fields and page size before following it. No credentials or provider error text reach a response. The paging contract follows [Microsoft Graph's messages documentation](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0).

mail_sent does not retain the actual sent body, and a saved draft may differ from what was sent. The Inbox therefore shows Message body: Not recorded for a sent-log-only bubble, and labels actual mailbox bodyPreview values as previews. It never substitutes a draft for the sent email. People are named on cards; the recipient address is exposed only in the selected prospect detail for the existing mail composer boundary.

Accept or Edit puts reply text in the local composer. Only Send followed by Send reply obtains the existing /api/mail/send/confirm nonce and calls /api/mail/send; a synchronous in-flight guard prevents duplicate presses. The Inbox Worker router imports no send helper and cannot send. Book a demo opens the existing Calendar new-event URL; it does not qualify a contact or write a booking on its own.

The DS8 layout reuses #4484's Distribution shell, tokens and shared proposal presentation. The supplied artifact URLs could not be fetched, so the issue's explicit DS8/MK8 screen contract defines the two-column layout and phone stacking. The branch merges the pending shell dependency rather than copying it. Prospects continues to own its data/UI contract in #4492. Thread-scoped suggested drafting remains dependent on #4488's contact/thread contract: the Inbox exposes a DraftIntent slot and accepts its decided reply payload, but does not invent a second AI task or claim that an unscoped draft read this thread. Manual replies remain available while that integration waits.
