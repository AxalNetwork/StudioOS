## D7720 — Study questions, evidence and decision history (#7720)

A study stores its questions and the evidence for and against them. Answering or setting aside a question changes its status, never its links. The question list supplies stored SQL counts for the context rail and Overview; there are no screens in this change.

### Store and scope

The additive migration creates questions, decisions and links below `research_studies`. A project with no study returns `recorded: false`, `counts: null`. An existing study with no questions returns recorded zeros. Counts include answered, total, open, set aside, open questions with at least one contradicting link (counted once), and all finding links whose finding has been removed. Read failures propagate as failures, never zeros.

A question has no separate owner column. Until #7728 introduces reviewers, the project has one owner, checked by `checkProjectOwner`; a column with no independent writer would imply ownership that does not exist. All handlers authenticate and check that owner, including reads. Foreign projects return 404, support-session writes return 403, and archived writes return 409. Write SQL checks owner and active project again.

Topics, statuses and evidence directions are bounded enums. Target kinds are checked in the Worker: this issue accepts only `finding`. There is deliberately no database CHECK enumerating target kinds, and finding snapshot columns allow NULL for future non-finding targets, so #7721 can add another target without rebuilding this table. The current Worker always writes all finding snapshot columns.

### Evidence and concurrency

A link snapshots the finding's uid, kind and updated_at. The finding must belong to the same project and cannot be a discarded interpretation. Later finding edits do not rewrite the snapshot. Deleting the finding sets only its foreign key to NULL; the read returns `finding_removed: true`, `target_label: "finding removed"`, retaining direction, note and snapshot. This rule also applies to decision links. A status change never removes evidence. Removing a question removes its dependent links; removing a project cascades its whole study. Only the question-link removal route can remove an individual link; it cannot address a decision link.

Questions start at version 1. Full-field edits, removal and link changes require that question's current version. Adding/removing a link advances it. Reorder accepts the complete list as `questions: [{uid, version}]` and validates the entire set inside a single SQL UPDATE before changing positions or versions. Stale or changed records return 409 `study_changed` with no partial write. Question creation appends the next position in SQL.

Decision POST requires the `study_version` returned by either list as `version`. In one `DB.batch`, the study version is advanced, the decision is inserted only if that write succeeded, and its links are inserted only under that new decision uid. A missing or discarded finding at write time makes the link's required target kind NULL and violates its NOT NULL constraint, rolling back the entire batch, including the version change and any earlier links. This uses [D1's documented transactional batch behavior](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). Unexpected database failures propagate rather than claiming a successful save.

The append-only decision UPDATE trigger rejects all updates. There is no DELETE trigger so a project cascade works. The API has no decision edit/delete route, nor any later mutation of its links. Listing returns every decision newest first by monotonic row id (also deterministic for equal timestamps), with its own evidence, rationale, reversing assumptions, actor and timestamp. `current` is the newest row, or null.

### Limits, routes and receipts

Exported limits: 100 questions and 1000 links per study, with insert triggers enforcing both under concurrent requests; question text 1000, answer 4000, gap note and next action 2000, link note 2000, decision rationale and reversing assumptions 4000 characters. A decision's initial links have an additional exported limit of 20 per save. Empty optional text is NULL. Questions and decisions are full-field writes. Receipts carry identifiers, field names and counts, never member-entered text or finding content.

Both routers self-mount at `/api/research/projects`. Questions: GET/POST `/:uid/study/questions`, PUT/DELETE `/:uid/study/questions/:questionUid`, POST `/:uid/study/questions/reorder`, POST `/:uid/study/questions/:questionUid/links`, DELETE `/:uid/study/questions/:questionUid/links/:linkUid`. Decisions: GET/POST `/:uid/study/decisions`. The new client module covers these mounted routes. No auth-inventory ledger exception is added.
