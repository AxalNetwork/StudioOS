## D6173 — Deals v2: the change since the last visit, and the investment case read (#6173)

D4815 said everything on the Deals v2 canvas mapped to existing routes. Two things on the deal page boards did not:
- DX5's Change column, with DX4's "Changed: Market ▲4 since your last visit";
- DX4's Investment case.

This adds a read for each. Both consumers are the DX4 and DX5 builds (#5904, #5905).

### 1. The change since the last visit

`GET /api/venture-scores/deal/:dealId` adds `change` to each scope, and `change_since` to the response. **Only after the NDA**: before it, no scope carries `change` and the response has no `change_since`.

**What a change is.** It is a difference between two stored versions of one scope in `venture_scorecards`, and none is invented:
- the latest version;
- the latest version stored at or before the investor's last visit.

```
{ state: 'recorded', delta, from, to, from_computed_at, since }   a difference; 0 when unchanged
{ state: 'not_recorded', reason }                                 no difference to report, and why
{ state: 'unreadable', reason }                                   the earlier version did not verify, or the read failed
```

**When there is no change, the reason says why** (`CHANGE_REASONS`):
- a first visit;
- no score now;
- only one version stored;
- no version stored before the visit;
- no score at the visit;
- a different scoring model then. Scores from two models are not compared, as the trajectory keeps model versions apart (D1258).

**Verification.** The earlier row is verified the way `storedScorecard` verifies the latest. PMF's rows are verified by their own store (D1144).

**The last visit.** By default it is this firm's `deal_seen.last_seen_at` for the deal, the firm chosen as `deal_context` chooses it.

The deal page's What's new read advances that watermark as the page opens. So the page passes the `since` that What's new returned as `?since=`. That value is used only if it is a well-formed UTC stamp no later than the stored watermark, so the comparison is never against a visit that has not happened.

With no firm chosen, every change reads Not recorded and asks the investor to choose one.

### 2. The investment case

**`GET /api/deals/:id/case`** (`routes/deal_case.ts`, mounted ahead of `deal_context`). It has the same gate as the deal's private notes:
- the investor licence;
- the firm chosen;
- an invitation or a commitment on the deal;
- no support session;
- `no-store`.

There is no staff bypass: the case is the firm's.

**Where each line comes from:**

| Block | Source | Not recorded when |
|---|---|---|
| `thesis_fit` | The thesis-fit read's own computation (`computeThesisFit`, `GET /api/deals/fit`) for this deal | No thesis is recorded, or too little about the venture is recorded |
| `main_evidence` | The investor evidence read's coverage (`investorEvidenceCoverage`, the `GET /api/deals/:id/evidence` rules). Counts by area, kind and source, top five, never an item. | The founder shares no evidence with this investor yet |
| `open_questions` | This firm's own `deal_notes` tagged Question or Risk (any case), newest first, at most 20 | The firm has no such note |
| `missing` | Scorecard scopes that are `not_enough`, or scored with coverage below 0.5 (`LOW_COVERAGE`) | The founder's switch is off, or before the NDA |

**Rules:**
- Each block carries `state`: `recorded`, `not_recorded` (with its reason) or `unreadable`. One block's failure never fails the others.
- The case returns nothing another firm wrote, and no other investor's own note.
- It returns nothing the NDA or the founder's sharing holds back.
- The coverage read is not logged as an evidence open, since no item is opened; the Evidence block's own read still logs `open_evidence`.

**Eadwyn.** Anything Eadwyn drafts for the case is a proposal the investor saves as a note (tagged Question or Risk, so it then appears here). It is never stored as a fact. This read serves no Eadwyn draft.
