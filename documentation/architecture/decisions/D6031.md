### 1. The Test cell

The `tests` cell is gone. It showed the must-have's hypothesis claim under "Tests", as if the claim were a test. The hypothesis is still the Hypothesis filter's key.

`test` names the must-have's latest session in `mvp_test_sessions`: the newest dated session first, then undated ones by id. With no session it says what Tested says (§2).

### 2. Built and Tested, two marks

Each is its own cell, and neither reads the other's source.

- **Tested** comes from the must-have's own sessions and findings: `Tested` once a done session has recorded at least one finding.
- **Built** comes from GitHub's pull-request state for the must-have:
  - `built` (merged): `Built`, plus "in production since <day>" when Vercel recorded a production deploy carrying the merge commit;
  - `in_progress` / `in_review`: GitHub's own label.
- **Built for a must-have GitHub has not fed** comes from its delivery status: `Done` is `Built`, as the board's footnote says.

Neither mark having its proof:
- before Done (not started, in progress) reads **Not expected yet**;
- after Done (and for a blocked or unknown state) is **Not recorded**.

**Unavailable:**
- a GitHub part that could not be read makes Built Unavailable on every row. Test and Tested keep their state;
- a sessions read that failed makes Test and Tested Unavailable. Built and the module stay readable.

### 3. What it reads

**Built reads nothing new.** It uses the module page's own `parts.github` and `parts.vercel`, now read before the rows.

**Tested and Test are one statement** for the rows being returned:
- the SQL page's 25;
- or, on the in-memory path (a search, a column sort), every must-have, which that path reads anyway.

The statement takes the ids as bound placeholders, 90 per statement under D1's 100-parameter limit. `json_each` was tried first: D1 counts each of its rows as a row read, which added 25 rows to every page. The placeholder string is the only interpolation, recorded in `scripts/baselines/sql-prepare/`.

The overview reads no rows, so it runs neither read.

### 4. The summary line and the dominant action

**Facts** gain `blocked`, counted from the grouped scan the card already runs. The module page also gets `can_set_target` (`canWrite`), so a reader who may not write, such as a partner, is not offered Set.

**The summary** sits above the table on desktop and phone: "N of M must-haves complete · target <date> · N blocked", with the progress bar.
- A missing date reads "target Not recorded".
- A writer gets Set, which saves through `PATCH /project/target` and re-reads the module.
- A read that sent no counts draws no line, never zeros.

**The card's next action** (the page's dominant action) is:
- the next blocked must-have, as "Unblock <title>";
- else the next one due, the earliest due date not done, as "Complete <title>";
- else the first not done in read order.

It is three `LIMIT 1` subqueries, so each stops at its first match:
- the blocked one on `idx_mvp_features_must_groups`;
- the due one on the new `idx_mvp_features_must_due (project_id, is_must_have, due_date, sort_order)`.

One sorted scan of every open must-have went over #4603's overview budget by 99 rows.
