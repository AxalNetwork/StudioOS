### 1. A run carries one skill (the owner, 2026-11-03)

The issue first pictured every skill an agent has joining every run, so that more skills meant a dearer run and specialists were cheaper. #3954, merged while this was built, made runs work otherwise:
- a run names at most one of the agent's skills;
- only that skill's prompt (`skillPrompt` in `skillEval.ts`: its purpose, numbered steps and allow-list) joins the system prompt.

Asked which model the meter should follow, the owner chose **"Follow #3954's runs"**:
- a skill costs its tokens on each run that uses it;
- having more skills never makes one run dearer;
- an agent's cost per run is a range, from its cheapest skill's run to its dearest.

So:
- the "more skills cost more" hint became a breadth hint (§3);
- SK6, the generalist-versus-specialists explainer, was dropped, because its sum no longer holds.

### 2. What a skill adds, and what a run costs

**`context_tokens`** is a version's prompt as `agentRun.ts` joins it (`\n\n` + `skillPrompt(version)`), by the AI budget's own estimate (`estTokens`: one token per four characters, rounded up).
- **Where it is kept:** `agent_skill_version_costs`, keyed by skill and version, written by `skillPublish.ts` in the same batch as the version.
- **Why a sibling table:** a published version is immutable (`trg_agent_skill_versions_immutable` refuses every UPDATE).
- **Older versions:** they have no row. The reader (`runCost.ts` `pinTokens`) works the same figure out from the version, so nothing is back-filled: the prompt is built in code.

**Per run**, for the agent's own model:
- **Baseline:** the run's own system prompt (`agentRun.ts`'s `systemPrompt`, now exported, for the agent's first module), plus a typical request (400 tokens) in, and a typical proposal (800 tokens) out.
- **A run with a skill:** the baseline plus that skill's `context_tokens`.
- **`tokens_per_run` / `est_usd_per_run`:** the dearest run (with its largest skill), or the baseline for an agent with none.
- **`cheapest`, `baseline`, `runs`:** the cheapest run, a run with no skill, and a run with each skill (by uid).
- **`monthly_at_cap`:** how many of the dearest runs the monthly cap pays for (null for an agent not yet added).
- **`delta`:** the dearest run's change, so adding a smaller skill moves it by 0.
- **Pricing:** the catalogue's price at what the sponsor pays (`memberChargeMultiplier`): `billedMicro` for Workers AI, `usdRatesBilledMicro` for provider models.

When the price or a skill cannot be read, the answer is **`{ available: false, reason }`**, never 0. The page reads "Not recorded" and never shows "$0.00" for a price nobody read; a real fraction of a cent reads "< $0.01".

The typical request and output sizes are estimates. When runs record real counts per skill (`ai_usage_logs.skill_id`, #3954), they can be measured instead.

### 3. The threshold and the hint

`RUN_COST_CONFIG` in `services/agents/runCost.ts` holds `requestTokens` 400, `outputTokens` 800 and `specialistMaxSkills` 6.

Past 6 skills, the hint names:
- the area most of them fall in (by their taxonomy tags, ties in the radar's order);
- how many areas they span;
- an offered persona not already on the team whose natural fit includes that area, in catalogue order, or none.

Hidden and retired personas (D4158) are never suggested. The words are about focus, not price ("a specialist keeps each agent focused"), because more skills do not cost more per run. The issue's second trigger, "above 2× the baseline", was dropped with the old model.
