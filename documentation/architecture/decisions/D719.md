## D719 — A connector webhook is processed only when it can be checked: an active connection with a signing key, or a handler that checks its own signature

Issue: none; S1 hotfix, 2026-10-17. S1 prepared it with two other server-side checks, and both reached `main` first, so neither is part of this decision: #1790 (D707, Build step 4) makes a payment intent need a catalog price, and #1793 (D712, decision 6) scopes LP report writes to the fund's GP of record.

### Why

- **Connector webhooks.** A delivery is processed only when it can be checked, which takes a signing key on the connection or a provider whose handler checks its own signature.

### What was decided

#### Connector webhooks (`routes/integrations.ts`, `integrations/providers/calendly.ts`, `integrations/providers/stripe.ts`)

- `POST /api/integrations/webhook/:provider/:uid` and `POST /api/connectors/webhook/:provider/:uid` run one handler. It answers 404 `{error: 'not_found'}`, the answer for an unknown uid, when:
  - no row matches the uid and provider;
  - the row's status is not `active`;
  - the provider has no `webhook` handler;
  - the row has no `webhook_secret_enc` and the provider is not in `VERIFIED_IN_HANDLER`, which holds only `hubspot`. HubSpot's handler checks the v3 signature against the app's client secret before it reads the body.
- These checks run right after the row lookup and before the body is read, so no handler runs, no fetch is made and no `integration_logs` row is written.
- An active row with a key and a handler gets the same signature check as before (401 `missing_signature` or `invalid_signature`, 500 `webhook_secret_unreadable`), then the sync-frequency and company gate, then the handler.
- The 200 `{ok: true, accepted: true}` that stored the payload for a provider with no handler is removed.
- Calendly:
  - `clFetch` takes only an absolute path, which it sends to `api.calendly.com`. Anything else throws `calendly_path_invalid`.
  - `scheduledEventPath` accepts an event URI only when it parses to origin `https://api.calendly.com` and the path `/scheduled_events/<id>`, and it returns that path alone.
  - The webhook handler skips any other URI without a fetch, and `fetchInviteeForEvent` returns null for one.
  - The `calendar_events` upsert's conflict update has `WHERE calendar_events.user_id = excluded.user_id`, so a row another member holds for the same Calendly URI is left as it is.
- Stripe: only the comment on `verifyWebhook` changed. It says that a key is stored only by a `POST /connect` body that carries `webhook_secret`, that the OAuth callback stores none, and that nothing falls back to `STRIPE_WEBHOOK_SECRET`.
- This narrows D232 point 3. `POST /api/integrations/webhook/stripe/:uid` delivers a connection's own events only when that connection holds a key.

No migration, no new dependency and no `wrangler.toml` change.

### Who is affected

Connector webhooks:

- **Stripe.** The OAuth callback stores no key, so an OAuth-connected Stripe row takes no deliveries. Its numbers update on the first sync after connect, on Sync (`POST /:uid/sync`) and on the Stripe import. There is no scheduled Stripe reconcile (D232). A way to store a Stripe endpoint's key is still open.
- **Calendly.** A row with no key takes no deliveries. A row is in that state between connect and `postConnect`'s subscription, or when Calendly declined the subscription (a plan without webhooks). Calendly delivers only to a subscription that `ensureWebhookSubscription` created, and that stores the key in the same update. The 15-minute reconcile still runs.
- **DocuSign.** Only a row with no key is refused, which means a Connect configuration set up by hand in DocuSign before the integration stored one. The key is stored with the Connect configuration `postConnect` provisions, or at the first send, before any delivery. The 30-minute reconcile still runs.
- **Providers with no handler** (Salesforce, Carta, Affinity, Crunchbase, Slack, GitHub, Zoom and others) get 404 instead of 200, and no "received (no handler yet)" line appears in the connector log. Nothing processed those events. Their scheduled polls are unchanged.
- **Rows whose status is not `active`** (`error`, `paused`, `disconnected`) are refused until they are active again. `POST /:uid/sync` sets `error` on any failure, and the scheduled reconciles read only active rows, so such a row is updated again after a successful Sync or a reconnect.
- **HubSpot** is unchanged.
- **Shared Calendly events.** When two members host the same Calendly event, the second member's sync or webhook leaves the row the first member holds as it is. Neither gets a second row, because of `UNIQUE(source, external_uri)`.

### Guards

- `cloudflare-worker/test/connector_webhook_keys.test.ts`, 9 tests, with each route test run on both mounts:
  - a Calendly, Stripe or DocuSign row with no key, an inactive row with a key and a correct signature, and a provider with no handler all get the unknown-uid answer, with no handler call, no fetch and no log row;
  - a correctly signed Calendly delivery to an active row with a key is fetched from `api.calendly.com` and stored, and an unsigned one still gets 401;
  - an event URI that is not an `api.calendly.com` scheduled event (13 forms) is skipped with no fetch, and the invitee fetch and the next-page fetch never leave `api.calendly.com`;
  - an upsert naming another member's Calendly URI leaves that member's row unchanged, and the owner's own row still updates;
  - HubSpot with no stored key still reaches its handler, which refuses an unsigned delivery and takes a v3-signed one.
- Mutants, each applied alone to a copy and each killed by its test:
  - the no-key, status, no-handler and HubSpot conditions each removed;
  - the Calendly origin check, path pattern, `clFetch` path check and upsert `WHERE` each removed.

  Against the code on main, every test of a new check fails, and the tests of the paths that stay open pass.
