## D8962 — Merge-queue Worker shards on the larger runner group, behind one variable, ubuntu-latest otherwise (#8962)

**Status.** Proposed; the owner lands the workflow part (T2). This change carries the record, the measurements,
the helper that holds the expression and measures the shards (`scripts/ci/queue-larger-runners.mjs`) and its test
(`frontend/test/ci_queue_larger_runners_8962.test.mjs`). It edits no file under `.github/workflows/`. The diff at
the end is the rest, verbatim, and it must land as one change.

**Context.** #8961 sets the merge queue to 20 entries building at once. Every CI job asks for `ubuntu-latest`. The
six `worker-*` parts of the `suite` matrix are the largest share of a queue entry's runner time. The group "StudioOS
Included Compute" (group 6, label `studioos-bench-linux-8`, the catalog's `github-8` profile, D7907) has so far been
named only by the benchmark, canary and executor workflows.

### Decision

`ci.yml`'s `suite` job takes the same `fromJSON(<condition> && '<target>' || '"ubuntu-latest"')` form that
`included-compute-canary.yml` uses (`matrix.lane == 'github-8'`), with the target JSON built from the catalog
(`executionTarget(resolveCatalogProfile('github-8'))`). The condition is all of:

1. `github.event_name == 'merge_group'`: pull requests and pushes never use the group.
2. `startsWith(matrix.part, 'worker-')`: the `frontend-*` parts and `rest` stay hosted.
3. `vars.CI_QUEUE_LARGE_RUNNERS == 'true'`: the one switch. Unset or any other value means `ubuntu-latest`.
4. `needs.capacity-route.outputs.accepted != 'true'`: a part that #7909's coordinator accepted stays hosted.
5. `!(matrix.part == 'worker-1-of-6' && vars.MACBOOK_WORKER_ENABLED == 'true')`: the part the Mac may take
   (D7881) keeps its standard hosted fallback, as D7881's guard test requires. D7907 already gives the Mac
   `worker-1-of-6`.

`runs-on` may read `needs`, and `suite` already needs `capacity-route` (D8626). When that job is skipped, which is
every run while queue routing is off, its output is empty, so condition 4 holds.

**The routes never claim the same shard.** A shard is claimed by:

- *capacity-route* (#7909, D8626) when `CAPACITY_ROUTED` is true: `merge_group`, a `worker-` part and `accepted ==
  'true'`. The coordinator then runs every routed Worker part, and the hosted job only reports where it ran.
- *the Mac* (D7881) when the `macbook` step's guard holds and the part is `worker-1-of-6`.
- *the larger group* (this decision) when the condition above holds.

Condition 4 takes the larger group out whenever capacity-route claims the shard, and condition 5 whenever the Mac
may. Capacity-route and the Mac already exclude each other: `capacity-submission.mjs` refuses a queue submission while
`MACBOOK_WORKER_ENABLED` is `'true'` (`macbook_worker_enabled`), so `accepted` is never `'true'` with the Mac on. The
test evaluates the real `CAPACITY_ROUTED` and `macbook` expressions from `ci.yml`, with the proposed `runs-on`, over
every event, part and switch value (1,296 cases, 36 of them unreachable for the reason above). It finds at most
one claimant in every case, and finds each route reachable. It also writes the larger-group rule out
independently of the expression and checks the two agree. The capacity-route/Mac overlap was found by this test
before the refusal was taken into account.

**No automatic fallback.** A job queued on a larger-runner label never moves to `ubuntu-latest` by itself (D7907).
`runs-on` is read when the job is created, so turning the variable off moves every *later* entry back to hosted. An
entry already waiting for group 6 waits until the queue's 90-minute check timeout, or until someone cancels it.
Setting `CI_QUEUE_LARGE_RUNNERS` to anything but `true` is the one place to switch it off.

**Pool contract.** `scripts/ci/pool-contract.mjs` (D8072) cannot read an expression `runs-on`, and `suite` runs on
pull requests too. The diff adds one dated exception for `ci.yml` › `suite` (`runs-on-unreadable`, owner #8962,
expires 2027-01-31, like the others). The exception is sound because the expression is evaluated for every event by
the test, and both targets are GitHub-hosted ephemeral machines: group 6 is `pool: github-hosted-included`, never
the self-hosted pool. An exception that matches nothing fails the check, so it cannot land before the workflow line.
D8072 already lists `ci.yml` › `suite`.

**Why the guard is a proposal.** A test that pins the expression in `ci.yml` fails on main until the line is there.
So what landed tolerates both states. It requires `suite`'s `runs-on` to be `ubuntu-latest` or exactly
`SUITE_RUNS_ON`, and it runs the disjointness proof against `SUITE_RUNS_ON`. The diff tightens it to equality and
evaluates `ci.yml`'s own value.

### Proposed change (the owner applies it as one change)

Measured against main `25819e877`. With it applied, every test that reads `ci.yml` (76 files, plus this one) gives
the same results as on main. Each of six mutations of the new `ci.yml` line is caught by
`ci_queue_larger_runners_8962` and by `ci_suite_parts_4130`: back to `ubuntu-latest`, no capacity exclusion, no Mac
exclusion, pull requests too, wrong label, and switch on by default. `macbook_workflow_7881` catches the dropped Mac
exclusion.


### What the owner does, in order

1. **Runner group 6 access.** D7907 limits group 6 to `included-compute-canary.yml@refs/heads/main` (and, for
   routing later, `runner-executor.yml@refs/heads/main`). A `merge_group` run of `ci.yml` runs from a
   `gh-readonly-queue/main/...` ref, so the group must also admit `ci.yml` there. Check the exact form the
   selected-workflows list accepts for that ref in the console. That is admin-slot work, recorded in
   `GITHUB_ADMIN_BASELINE.md`. Also check that the group's maximum concurrency covers six shards per building entry:
   60 at 10 entries, 120 at 20.
2. **Spending.** D7907 authorized group 6 on included compute only, with no overage. At the medians above, one
   queue entry is about 6 × 16 = 96 eight-core minutes, and a day had 55 to 288 queue runs, though cancelled entries
   use less. Confirm that this fits, or set a cap, before the variable goes on.
3. **Apply the diff** in one change, with the checks green.
4. **Set `CI_QUEUE_LARGE_RUNNERS=true`** as a repository variable. Leave it unset to keep today's behaviour.
5. **Measure after** 10 queue runs: `node scripts/ci/queue-larger-runners.mjs --runs 10`. Compare its `larger`
   rows with the table above, and record them on #8962.
6. **Switch off** by setting the variable to anything but `true`. Cancel any entry that is still waiting on group 6.
