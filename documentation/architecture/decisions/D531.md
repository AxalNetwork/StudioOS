## D531 — research_company_directory's 24 hand-added columns are declared by migration 375

**Migration 375 declares the 24 columns production's `research_company_directory`
holds and no repo file did. A fresh build now has them, and so does each branch
database once 375 runs there. Production already has them, so before the deploy
that carries 375, its ledger records the file as applied (one owner step,
below).** GitHub issue 1073, slot S02. Migration 375. No route, no `api.js`
change, and `frontend/src` is unchanged.

**What was true on main (`27af83d6d`).** D359 (#1068) made
`check-baseline-drift` compare columns as well as names. Its first run, deploy
run 37197266231 (2026-10-04 11:02 UTC), failed "repo can still rebuild
production's schema" on 24 columns of `research_company_directory` that neither
`schema_baseline.sql` nor any migration declares. The Worker deployed and the
database is fine. What broke is that a database built from the repo comes up
with migration 228's thirteen columns and not production's thirty-seven.

**Where they came from.** By hand, on production, without a migration.
- No commit has ever declared them. `git log -S` and `git grep` over all 44
  branches find none of the 24 names on this table. The one hit,
  `valuation_currency`, is `company_funding_rounds`' own column in migration
  370. A PR search finds none of them either.
- Migration 228 created the table on 2026-09-29 (`b9557713c`, 22:54 UTC) with
  the thirteen columns it still declares, so the 24 arrived later. The
  name-only check could not see a column, so they went unreported until D359,
  on 2026-10-04.
- They are the same data family as the four `company_*` tables created by hand
  on 2026-09-30 (D520, migration 370): funding, valuation, revenue, employees,
  market share, and the evidence and confidence behind them. That points to
  the same out-of-band session, but production keeps no timestamp for a
  column, so the exact moment is not recorded.

**What 375 declares.** Each statement is the column exactly as run
37197266231 printed it. `check-baseline-drift` reads `pragma_table_info` and
prints the type, plus NOT NULL and DEFAULT whenever production has them, so a
bare type means production's column is nullable with no default. Nothing is
re-chosen. With 13 + 24 = 37 columns, the table is well under D1's 100-column
cap. Nothing is rewritten or dropped.

**Why a migration, and not a re-dump of the baseline.** The drift check's
invariant is `schema_baseline.sql` + every migration above `BASELINE_CUTOFF`
(219) == production. A re-dump taken today would already contain 220 to 374,
so it only works if the cutoff moves to 374, and bootstrap then marks every
file up to 374 as applied without running it. Several of those files carry
data, not just schema: 228's own company rows, 229's markets, 365's
EuroTech fund directory. A schema-only dump drops all of it, so a fresh database would come up
with empty directories. A re-dump also needs production credentials, which
this environment does not have. The repo's rules call for a re-dump when the
snapshot is refreshed, not when one table is missing columns.

**Why plain ALTERs, and the one step production needs.** The issue pointed at
migration 278 as precedent for declaring a column production already had, but
278's `partners.accepting_intros` was measured absent from production, so a
plain ALTER was right there. The closer precedent is 370 (D520), whose
statements are `CREATE TABLE IF NOT EXISTS`, a no-op on production. Columns
have no such form:
- SQLite has no `ADD COLUMN IF NOT EXISTS`, and `migrate-d1` executes a pending
  file whole.
- Rebuilding the table under a new shape would select the 24 columns, which a
  fresh database lacks. It would also rewrite production's rows.

So 375 is plain `ALTER TABLE … ADD COLUMN`, which applies as written on a fresh
database and on every branch database, all built from the repo. On production
the effect is already present, and the runner's own recovery for "effect
present, ledger row absent" (`applyPlan` in `scripts/lib/migrationPlan.mjs`)
is to record the row and re-run. Production writes are the owner's, so this
is the owner's step, taken **before** merging:

```sh
cd cloudflare-worker   # the target and flags migrate-d1 itself uses for production
npx wrangler d1 execute studioos-db --config ../wrangler.toml --remote \
  --command "INSERT INTO schema_migrations (filename, checksum) VALUES ('375_research_company_directory_columns.sql', 'aa0374fda68a81bf232bdbbed23d1572d4f83ebb67d5bcc84b9cb227574400e9');"
cd .. && node scripts/migrate-d1.mjs --remote --verify-marked   # read-only; 375 should be verified
```

- The checksum is `sha256` of the file as merged.
  `research_directory_columns_d531.test.mjs` fails if the file and this
  command disagree.
- `--verify-marked` probes every ledgered file's columns on production, so it
  confirms all 24 exist.
- If the deploy runs first, the first ALTER fails with "duplicate column" and
  nothing changes. The workflow stops before the Worker ships, and recording
  the row and re-running the workflow recovers it.

**Money.** Four of the columns are REAL currency amounts: `funding_total`,
`last_funding_amount`, `revenue` and `valuation`. As with D520, they are
recorded in `scripts/money-cents-baseline.json` as created out-of-band and
declared verbatim, to be converted to `<col>_cents`. The money classifier did
not recognise `funding_total`, so it learns it, pinned in
`schema_guards.test.mjs`. `employee_growth_pct` and `market_share_pct` are
rates, and the classifier already reads them as not money. These two files
are outside the issue's list. The money gate fails without them, and D520
set the pattern.

**Readers, and "Not recorded".** No code reads these columns. The two
directory routes (`GET /api/research/company-directory` and `/:uid`) select
migration 228's columns only, and their `source_boundary` says the directory
makes "no funding, valuation, revenue, market-size, or diligence claims". So
no screen can show a zero for an absent value today. The first reader is the
Research companies rebuild (GitHub issue 1079, D534). It must render an absent
value as "Not recorded". The test pins that nothing reads the columns yet, so
that rebuild has to re-aim the pin deliberately.

**Not measured.** Production's row values are user-adjacent content and out
of bounds, and this environment has no Cloudflare credentials. So how many
rows hold a value in each column is not recorded here. An aggregate count is
allowed, and S1 can take it when the D534 reader is built.

**Guard.** `cloudflare-worker/test/research_directory_columns_d531.test.mjs`:
- The repo's schema story (baseline + every migration above the cutoff, in
  `node:sqlite`, through `check-baseline-drift`'s own builder) gives this table
  exactly production's 37 columns and types. Without 375 it lacks exactly the
  24.
- 375 holds only `ALTER TABLE research_company_directory ADD COLUMN`
  statements, one per production column, so recording it on production is
  equivalent to running it there.
- Running 375 on a table that already has the columns fails with "duplicate
  column" and leaves the table unchanged.
- With the row recorded, the planner skips 375, and `verifyMarked` reports it
  verified against production's shape and missing against a table without the
  columns.
- The command above cites 375's current checksum.
- No Worker or frontend source names any of the 24 columns yet.

**Mutations: 11 run, 11 caught.** Each counted only with a non-zero exit and
a `not ok` line, and every file was restored from a sha256-checked snapshot.
The mutations:
- 375 drops a column, retypes one, adds NOT NULL DEFAULT, carries an extra
  statement, alters another table, or adds a column production lacks;
- D531 cites a stale checksum, or drops the `--verify-marked` command;
- a directory route reads `revenue` from the table;
- the classifier forgets `funding_total`;
- the money ledger loses `valuation`.
