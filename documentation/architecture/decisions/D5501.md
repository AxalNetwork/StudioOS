## D5501 — Admit the exact verified main candidate before production writes (#5501)

A production publish previously ran in parallel with the tests for the commit it was shipping. The release now resolves all six required contexts from the Actions jobs of their expected workflows: `ci.yml`, `migration-immutability.yml` and `gitleaks.yml`. It verifies the producer path, repository, push event, main ref, exact commit, run attempt and successful job result. It uses the latest matching run. PR results or merge-queue results on a different SHA cannot satisfy admission. The existing CI push gate can reuse its own same-SHA merge-queue proof. Coordinate changes to the six contexts with #5500.

Admission waits up to 95 minutes without production credentials or the production write lock. Under the lock, the workflow rechecks the main ref and candidate results before building and immediately before any write. Production D1 maintenance shares that lock, including verification that can unmark ledger rows. Read-only D1 planning has its own path. [GitHub's multi-pending concurrency queue](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) keeps waiting releases and manual jobs from cancelling one another. A queued or retried old candidate fails the main tip check. A release that already began mutating finishes under the lock before any newer release can mutate. Repeating an eligible candidate uses the existing migration ledger to skip applied files.

Queue verification and the packaged startup check from #5549 and #5552 are mandatory before D1 writes or Worker publication. The preflight archive contains the exact candidate, six check identities, production queue result, SHA-256 of the locally profiled artifact, startup profile and health timings, D1 plan, previous deployment and recorded release outcome. The release publishes using the same checked-out SHA, config and built SPA with the candidate set as `WORKER_DEPLOY_VERSION`. Wrangler rebuilds the Worker upload during publication. A dry-run using `--no-bundle` with the emitted module directory omitted required imports on Wrangler 4.156.1, so the prepared artifact's digest identifies the check input rather than an assertion of byte equality with the later upload. Keep any startup profile emitted during a remote rejection.

A failed preflight prevents migration and publication. After migration starts, publication failure leaves the migration ledger and schema in place. Use the recorded compatible Worker version or a fix-forward candidate under the [operator recovery procedure](../../operations/DEPLOY.md#3-capture-a-rollback-point-first). Production mutation and resulting version are reported separately from live smoke, schema parity (#4591) and branch rollout. Branch rollout and branch manual D1 writes use a different shared lock and branch-specific targets. The owner-enabled private meeting bot verifies its own exact main candidate before publishing and does not use the StudioOS bundle. If a watched bot push is superseded by unrelated main changes, dispatch the bot workflow on the current verified main.

Operator deploy and production D1 npm scripts dispatch the main workflows. Release publication already dispatches the same production workflow. Limit production credential use to trusted release contexts; privileged direct Cloudflare access remains an owner recovery capability. The 800 ms startup check is local and still needs release-runner calibration, and real 10021 diagnosis needs an authoritative isolated Cloudflare rehearsal (#5532, #4566). The fixture validates ordering and refusal decisions with synthetic inputs. Hosted staging, compatible rollback against a migrated schema, and the first routine production release evidence remain follow-up acceptance work.
