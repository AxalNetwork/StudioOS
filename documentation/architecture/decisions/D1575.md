## D1575 — The PDF that matches the screen: the deck's aspect, and a check before it is handed out (#3822)

- **Status:** built 2026-11-03 by S09 for #3822, part of #3716 (deck builder v2, Phase E, task E2). It serves pd8b's PDF card, "Matches the screen".
- **Migration:** none. **Charge:** none. No model runs.
- **Builds on:** D901 (the PDF through Browser Rendering), #3655 (`renderUrl` and its code-only refusal), D1499 (4:3 and the print page at the slide's own size), D1500 (rich text runs and their https links), D1545 (link, button, audio and video blocks), D1574 (the editable PowerPoint, the sibling export).

### 1. Why

The PDF route rendered every deck on a fixed 1920 × 1080 viewport and `@page`. Since D1499 the print page lays a 4:3 studio deck out on 1440 × 1080, so a 4:3 deck printed onto a 16:9 sheet with a white band. Nothing checked what came back: a PDF with a font missing, words flattened into a picture or a dead link would be handed out as "the deck".

### 2. The page

`services/decks/pdfExport.ts` `printPageOf` picks the page the print page itself uses (`PitchDeckPrintPage.jsx`'s `pageW`): a studio deck (no template method, at least one card on The Grid) prints at its aspect, 1920 × 1080 at 16:9 and 1440 × 1080 at 4:3; a template deck stays 1920 × 1080. `pdfRenderOptions` writes the viewport, the `@page` size and `pdfOptions` width and height from that one page, so they can never disagree. `tagged: true` asks Chrome for a tagged PDF.

### 3. The check

`checkDeckPdf` reads the bytes Browser Rendering answered (pdf-lib) before anything is recorded:

| Code | When |
| --- | --- |
| `unreadable` | pdf-lib cannot read it, or it has no page tree |
| `no_pages` | it has no page |
| `page_size` | a page is not the deck's size, ±1 pt (Chrome prints a CSS pixel at 0.75 pt) |
| `font_not_embedded` | a font has no `FontFile`, `FontFile2` or `FontFile3` (a Type0 font is read through its descendant; a Type3 font draws its own glyphs) |
| `text_flattened` | the deck has words (`hasWords`) and the PDF has no font at all |
| `links_missing` | a link the cards draw live (`expectedLinks`) is not a URI link annotation |

`expectedLinks` names exactly the anchors `BlockView` draws with `live`: a link, button, audio or provider video block's URL (an uploaded mp4 plays in place, so it is no link), and the https href of a run with words in a text block with words (`runsOf` drops any other href).

A PDF that fails is refused `502 pdf_fidelity_failed` with `diagnostic: { reason: 'pdf_fidelity', checks: [codes], pages }`. No URL and no text from the deck is in it. Nothing is written to `deck_exports` and no `deck_exported` audit row is written, as for a failed render (#3655).

### 4. Not in this

- The PPTX is D1574's. The client is unchanged: `ExportDialog`'s PDF card already calls `api.deckExport` and shows a refusal's message.
- Screen-reader structure past `tagged: true` (reading order, alt text in the tag tree) is not checked here.
