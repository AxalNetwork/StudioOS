## D8069 — Deploy and ops workflows name their environment, grant permissions per job, and hold `id-token` only beside an OIDC login (#8069)

**Decision date:** 2026-11-22. **Scope:** the deploy and ops workflows, one guard test, the preview environment name and
two runbooks. No application, database or production change. Consumes the environment contract of #8063 and the
credential contract of #8064. Builds on D7145 (credential inventory) and D7146 (the preview's trusted half).

### What changes

- **Every cloud credential is read inside an environment.** A job that reads a Cloudflare API token, an S3-style
  access key, or an AWS or Azure credential names the GitHub environment that holds it. Two jobs that read the
  outside copy's keys without one now enter `production-ops`, like every other DR and recovery job:
  `dr-drill.yml › independent-file-drill` and `file-recovery.yml › synthetic-proof`. The first runs in the same
  scheduled run as `drill`, which already waits for that environment's approval. The second is dispatch-only.
- **The preview enters `preview`.** `pr-preview-deploy.yml` looked up and entered `pr-preview`, an environment that
  was never created (#7424 records the 404 on every run). It now uses `preview`, which #8063 created with a main-only
  branch policy and no reviewer. `resolve` checks that same name before deploy or delete enters it.
  `scripts/ci/pool-contract.mjs` lists `preview` in place of `pr-preview` among the deploy environments, so #8072's
  trigger and runner rules keep applying to it.
- **The preview keeps its dedicated token name.** It reads `PR_PREVIEW_CLOUDFLARE_API_TOKEN`, not
  `CLOUDFLARE_API_TOKEN`. A missing environment secret falls back to a repository secret of the same name, and the
  repository still holds the production-capable `CLOUDFLARE_API_TOKEN` (#8063's inventory). The guard refuses the
  generic name in `preview` until that copy is deleted.
- **Permissions per job.** These workflows now set `permissions: {}` at the top and declare the same grants on each
  job, so a job added later starts with nothing:
  - `cloudflare-worker-deploy.yml`, `merge-control-deploy.yml`, `meeting-bot-deploy.yml`, `archive-observer-deploy.yml`;
  - `post-deploy-smoke.yml`, `backup-d1.yml`, `dr-drill.yml`, `file-recovery.yml`;
  - `pr-preview-deploy.yml`, which already did so.

  The effective grants are unchanged.
- **`id-token: write` only beside an OIDC login.** A job that holds it, directly or from the top of its workflow,
  must contain a step that exchanges the token, or call a local reusable workflow whose job does. The steps that
  count:
  - Claude Code's workload identity federation (D5530): the action, or `vars.ANTHROPIC_FEDERATION_RULE_ID`;
  - a script that requests the token itself;
  - `aws-actions/configure-aws-credentials`, `azure/login`, or `actions/attest-build-provenance` (#8073).

  Every current holder passes.
- **No long-lived AWS or Azure key.** No workflow may read `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`,
  `AWS_SESSION_TOKEN`, `AZURE_CLIENT_SECRET` or `AZURE_CREDENTIALS`, even inside an environment. None does today.
- **The guard.** `frontend/test/workflow_environments_8069.test.mjs` parses every workflow with `yaml` and checks the
  rules above, with invented fixtures showing each rule fail on its own. One job is excepted by name with its reason:
  `github-alerts.yml › file-backup`.
- **Unchanged.** The deploy's admission and rollback contract (`documentation/operations/DEPLOY.md` §1.1, §3).
  #8073's provenance lines (proposed on this issue, not yet applied). `ci.yml` and the landing workflows (#8072).

### Owner gates

1. **Preview token.** Add `PR_PREVIEW_CLOUDFLARE_API_TOKEN` (Workers Scripts edit only, D7146) to the `preview`
   environment. Until then the preview's deploy job stops with the message `PR_PREVIEW_CLOUDFLARE_API_TOKEN is not set
   in the preview environment`, in place of today's 404 on `pr-preview`. #7424 closes on the first passing run.
2. **AWS and Azure OIDC steps.** No workflow holds an AWS or Azure credential today, so there is no static key to
   replace. The OIDC login actions are not on the repository's Allowed actions list (an explicit SHA list since
   2026-11-21), and #8064's roles are not yet created. When a workflow first needs AWS or Azure, the owner adds the
   pinned SHA of `aws-actions/configure-aws-credentials` or `azure/login` to Allowed actions. The job then names its
   environment, holds `id-token: write` and assumes the #8064 role. The guard already accepts exactly that shape.
3. **`github-alerts.yml › file-backup`.** It reads the `FILE_RECOVERY_HEALTH_*` keys on a schedule to check backup
   health. `production-ops` would hold every alert run for the owner's approval. The owner chooses its home: an
   environment without a reviewer that admits `main` only (`staging` exists), or a read-only key in the repository
   as today. It stays excepted by name until then.
4. **Execution evidence.** After the owner lands this, one release from `main` under `production` succeeds and is
   recorded on #8069. A pull-request run shows no deploy credential (no job of a PR-triggered workflow enters these
   environments; #8063 records the check).

### Rollback

Revert the PR. The workflows return to `pr-preview` and their top-level permission blocks. The two drill jobs then
read their keys without an environment again. No setting, secret or deployment is changed by this PR or by its
revert.
