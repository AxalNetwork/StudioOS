## D9187 — A pipeline vote is one upsert, and a vote for a missing deal is refused (#9187)

- **Status:** built by S06 on #9187, 2026-11-28.
- **Scope:** `cloudflare-worker/src/routes/votes.ts`, `POST /api/pipeline/vote/:deal_id` (and its `/votes/` alias). No schema change; the runtime DDL is untouched.

### The problem

- The cast read the caller's row and then wrote an `INSERT` when there was none. Two near-simultaneous first votes (a double-click) both found no row. The second `INSERT` hit `UNIQUE(deal_id, user_id)` and answered 500 `vote_failed`, although the vote had been saved.
- The cast checked only that `deal_id` parsed as an integer. A vote for an id with no deal answered 200 and stored an orphan row.

### What was decided

- **A deal is a `projects` row.** The pipeline board (`GET /api/pipeline/active`) lists `projects`, and the board's vote widget keys every vote by that id. The cast reads it with `pipelineProject` (`services/pipelineAccess.ts`). An id with no row answers 404 `deal_not_found` before anything is written. A closed venture (rejected, archived, spun out) still exists, so it still takes a vote, as every per-deal pipeline route still reads it.
- **Existence only, not the board's `read` rule.** D4676 held the board's list, detail and writes to the venture, and it left the vote audience (admin, partner, investor) as it was. The tally GET answers any signed-in account, and `_user_weight` gives an investor weight 3. Refusing a vote to an account the board would not list it to narrows who may vote. That is a separate decision, so it is not made here.
- **One statement.** The write is `INSERT … ON CONFLICT(deal_id, user_id) DO UPDATE`, setting the vote type, weight, comment, anonymity and `updated_at`. The constraint decides, so every parallel cast answers 200 and one row remains, holding the last value written.
- The tally GET still makes no existence check. A read cannot leave an orphan, and the board fans it out across every deal.

### Tests

`cloudflare-worker/test/votes_upsert_9187.test.ts` runs on the migrated schema. Its parallel cases run the requests in lockstep at every `pipeline_votes` statement, as real D1's network round trips do; without the lockstep, in-process SQLite serialises them and the old read-then-write passes. The cases:

- four parallel first votes by one caller: four 200s and one row;
- four parallel first votes by four callers: four rows;
- a changed vote: the one row takes the new type and comment;
- a vote for a missing deal: 404 `deal_not_found` and no row.

`pipeline_votes_tally.test.ts` and `pipeline_retrieval_4701.test.ts` now seed the deal they vote on.

Mutation check (`votes_upsert_9187.test.ts`): 7 mutations, 7 caught, 0 equivalent. The mutations were: the deal check dropped; the wrong refusal code; a plain `INSERT`; `DO NOTHING`; the update leaving out the vote type; the update leaving out the comment; and the original select-then-insert put back.
