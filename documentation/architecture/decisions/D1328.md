**Classes and sources:**
- Every text field is a `composition` from Eadwyn.
- The must-have's hypothesis is a `restatement`. It picks one of the venture's own unretired hypotheses (D46's match-back), as Add feature's does.

**What is left out, and why:**
- **The founder's own judgements:** a theme's severity, a segment's urgency and its score window, a hypothesis's direction, and a must-have's state.
- **People:** owners and deadlines.
- **Fields that are not one column on the form's table:**
  - a theme's quotes and its hypothesis (`pain_group_aliases`, `hypothesis_pain_links`);
  - a hypothesis's pain themes;
  - a must-have's links.

  `POST /api/fills/record` re-reads the row the Save wrote, so a field must be one of its columns.

**Forms with no entry yet:**
- **New competitor:** its rows are `competitor_candidates` under an analysis, with no `project_id` to scope a literal read.
- **Record a signal:** it is a kind, a person, an amount, a date and a status, so nothing in it is Eadwyn's to write.

### 3. What each table gained

- **`ROW_READS`** (`routes/fills.ts`): one literal, venture-scoped read each for `pain_groups`, `customer_segments` and `hypotheses`. `mvp_features` already had one.
- **`ROW_REQUIRED`** (`routes/rail_run.ts`): a row is proposed only with a theme's title, a segment's name or a hypothesis's claim.
- **`EXISTING_READS`** (`services/fills/formRun.ts`):
  - One literal statement per table for what is already on file, so a proposed row does not repeat one.
  - It replaces part 3's `mvp_features`-only branch, with the same statement.
- **Accept all's writers** (`services/fills/keep.ts`). Each is the form's own route's writer:
  - **`pain_groups` uses `writeTheme`,** with the title only.
  - **`customer_segments` uses `writeSegment`.** An existing name answers `duplicate`, and the row waits again.
  - **`hypotheses` uses `createHypothesis`:** the claim and its two bars.
  - **A refusal is reported, not hidden.** A `WriterError` becomes `invalid`, or `unmatched` for a 404.
- **`FORM_ROW_WRITERS`,** new beside `ROW_WRITERS`:
  - **Why it is needed:** Add must-have writes `mvp_features`, as Add feature does. A writer keyed by table alone would create a must-have as a feature.
  - **The key** is `<page> / <form>` (`FILL_FORMS`' words), and it is checked first.
  - **Add must-have's writer** runs `POST /must-haves`' own `mustHaveCreateStatements`: Backlog, no owner, no due date, no links. It accepts a hypothesis only if it is this venture's and unretired.
- **`UNDO_WRITES`:**
  - `pain_groups.title` and `hypotheses.claim` (required, so an undo to blank is refused);
  - a segment's `who_they_are`, `job_to_be_done` and `value_promised`;
  - a hypothesis's `success_bar` and `disproof`.
  - **A segment's name has no undo.** Its writer keeps `name_norm` beside it, which a literal one-column statement cannot. Its undo answers 404 `fill_not_found`, as any column without a write does.

Each form's entries sit in their own block in both copies of FILL_FIELDS, so part 6 (#3490), which adds to the same arrays, can merge beside them.

**AF3: the triggers** (`pages/cycles/FormLightbox.jsx`, prop `fill`):
- The form reads `GET /api/fills/sheet` once.
- "Fill [field] with Eadwyn" is drawn beside a field's label only when two things hold:
  - the read gives the field a trigger (`field.trigger`: never a typed, never-fill or decision field, never a reader);
  - the field's box is still blank.
- The form's "Fill" is drawn while any such field is blank. With AI off, both read "…from your sources".
- An unreadable read says so, with Try again, and draws no trigger.

**AF7: placed, then saved:**
- Accept in the sheet places the values in the open form. Each is marked "Not saved", and a line says "N values placed. Nothing is saved until you press [the form's button]."
- A placed value the member types over loses its mark.
- Nothing is written before Save. The form's own route writes, and then `POST /api/fills/record` runs with the saved row's id and every placed proposal.
  - The Worker keeps only the fields that still equal the proposal (D1326 §2). A typed-over value is never filed as Eadwyn's.
  - A failed Save records nothing.
  - A Save reply with no row id records nothing.
  - A failed record never undoes the Save.

**AF1: the module trigger** (`pages/cycles/FillRowsPanel.jsx`, `FillModule`, in the module header's `more` slot):
- It reads "Fill with Eadwyn" with "N waiting".
- N counts the member's own row proposals for the module's Add form, on this venture only. Field proposals are not rows, and another venture's rows do not count.
- An unreadable read draws no count, never "0 waiting".
- The count is read again when the page re-reads.

**AF16: the panel** (D1317's `Sheet` at 520px):
- **Each proposal:** "Add feature [title]?", its other text fields, and "Eadwyn · proposed". A restatement's id is never drawn.
- **Accept:** `POST /api/fills/rows/accept` for that one row.
- **Accept all (N):** at most 50, through the same route. The panel then says "Added 1 of 2.", with each refusal's reason in words beside its row, never a bare code.
- **Edit:** opens the Add form with the row's values, each "Not saved". Its Save writes through the form's route, then decides the proposal `edit` with what was saved.
- **Discard:** the proposal's own decision. Discard all decides each one in turn, after an in-page dialog.
- **Ask Eadwyn for up to 5:**
  - It runs the form's handler with `input.rows` (D1326).
  - It is offered only while AI is on, and says it uses AI tokens.
  - A refusal is `refusalView`'s sentence.
- **"Nothing is waiting for [module]."** when nothing is.
