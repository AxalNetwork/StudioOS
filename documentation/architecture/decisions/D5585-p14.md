### 1. The rule

Each `ComponentState` in an evaluation carries `attestations`, oldest first by `created_at`, then `id`. These are the
attestations recorded for the pinned revision at its pinned digest, in the manifest's own tenant and company. They are
exactly the rows that decide `missingAttestations`, so the two never disagree.

An attestation of the same revision at another digest is not listed and does not count. Neither does one recorded under
another tenant or company.

Each entry is `{ id, requirement, evidenceRef, authority, actorKind, userId, agentRunId, at }`:

- `userId` is the person who attested. When an agent run attested (a CI check), it is the person the run acted for,
  which is the `actor_user_id` the row already holds. The run is `agentRunId`.
- `evidenceRef` is returned as recorded. It is ids only (a PR and commit, a CI run, a rights record), and
  `attestComponent` bounds it to 200 characters.

Every attestation at the pinned digest is listed, including a second one for a requirement that is already met. A page
that shows evidence should show all of it.

### 2. Who sees it

Only the Super Admin reads return an evaluation: `GET …/manifests/:manifest`, and the publication pointer of
`GET …/lines/:line`. Both now name attesters in `people`, by `effectiveDisplayName` and never by email (D5585-p11 §2).

The reviewer read (`/api/work-graph/releases/pending`) returns pending items, not evaluations, so it is unchanged. The
public site record (D5585-p9) and every delivery read their own columns, never `ComponentState`, so no evidence ref or
user id reaches a public answer.

### 3. Cost

The cost is unchanged: still one statement per evaluation. That statement now returns each attestation row instead of
distinct requirements. A manifest holds at most `WORK_GRAPH_RELEASE_LIMITS.maxComponents` (32) pieces, and the rows per piece are as many as were recorded
at its digest.

Revert this commit. The field disappears, and nothing else depends on it.
