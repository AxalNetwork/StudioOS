### 1. Capital relationships: Add or Link, never a duplicate

**What waits.** Each row of the founder's mapped investor CRM waits as a `prospect` proposal (D1086). How it reads comes from the acceptor's `describe`, at sync time:

- **"Link to [existing]"** when the row names an investor already tracked:
  - by email, when the founder mapped the Email property (case-insensitive);
  - else by firm (case-insensitive).
  - A name alone never matches.
- **"Add [Firm or Name] at [stage]?"** otherwise, with the stage in the pipeline's own words.

**Accept.**
- **A row that matches** is linked to that investor. Nothing is written but an audit row of ids, so there is never a duplicate.
- **Any other row** goes through `addProspect`, the pipeline's own Add investor: the name, the firm, the mapped stage and the notes. An email is passed only when the founder mapped one.

**Once linked, the stage is a fact.** Each later sync finds the row's ledger link (`notion:<project>:capital_relationships:<row>`) and calls the module's linked updater (`registerLinkedUpdater`), not a new proposal.
- The updater moves the stage through `updateProspect`'s stage writer, which logs "Contacted → Diligence".
- The same stage writes nothing.
- Only the stage follows Notion: notes and names stay as the founder keeps them in Raise.
- An investor deleted in Raise is neither brought back nor proposed again.

### 2. Data room: a snapshot, NDA by default

**What waits.** Each picked page waits as a `data_room_snapshot` proposal: "Add a snapshot of “[page]”?". Nothing reaches the room, storage or an investor before Accept.

**Add a snapshot.** Accept opens a dialog with the gate: "Investors who signed the NDA" (chosen) or "Every investor with access". Accept then:
1. reads the page whole, as of now, held to what was proposed (409 `changed_in_notion` until it is synced again);
2. refuses an empty page;
3. stores the Markdown through `storeDataRoomFile`, the upload's own storage step.

That step does what every upload does:
- applies the storage guard (D1170), counting the file to the venture's owner;
- derives the key, `data-room/<venture uid>/<uid>`;
- writes the `data_room_files` row (`text/markdown`), its log line and the storage notice.

A gate other than `nda` or `open` is 400 `invalid_visibility`.

**Update the snapshot.** When the page changes after a snapshot, the sync re-proposes it as "Update the snapshot of “[page]”", marked Changed in Notion.
- Its Accept adds a version through Replace (`replaceDataRoomFile`): the earlier object stays as version 1, and the file keeps its gate.
- No version is added before Accept.
- The dialog says so and asks nothing more.

**One way into the room.** `storeDataRoomFile` is the upload route's storage tail, factored out unchanged. The route calls it, so D1170's storage-guard census now names it, with a note.

### 3. The engine, extended

- **`Acceptor.describe(env, ctx, { module, key, title, payload })`** sets how a proposal reads at sync time. The fingerprint is unchanged by it.
- **`registerLinkedUpdater(module, fn)`.** In a database proposal module, a row an earlier Accept linked lands as a fact through the module's updater, counted as `updated` when it changed something.
