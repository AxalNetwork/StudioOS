## D7108 — Queue CI does each check once per candidate: worker parts skip the SPA build, fast skips what required jobs repeat (#7108)

Amends D5606 (fast's typecheck and build "follow" on every event) and records a narrowing of D4130/D6461 (every suite part builds the SPA). The six required contexts in ruleset 25309597 on `main` — `test:drift (full suite)`, `worker (typecheck)`, `frontend (build)`, `api ↔ worker drift`, `applied migrations unchanged`, `scan` — keep their names, jobs, `if`, `needs` and `runs-on`. The queue verifies the same set of checks and runs the same test files on every candidate as before.

### Why

On 2026-11-17 the merge queue stalled (#7108). Measured on 2026-11-16: 43% of `merge_group` CI runs failed; passing runs took p50 31 min and p90 66 min; about a third of a passing queue run's wall time was spent waiting for a runner, because pull-request CI and queue CI share one runner pool (a 2-second verdict job waited 12 minutes). Build concurrency is now 5. The root cause is runner contention. This change trims work that runs twice on the same candidate. It does not remove a runner acquisition, so it cannot fix contention alone (see "Deferred").

### What changed

1. **Worker suite parts skip the frontend install and the root SPA build.** In `ci.yml`'s `suite` job, 'Install frontend deps' and 'Build the SPA' carry `if: ${{ !startsWith(matrix.part, 'worker') }}`. `runner-benchmark.yml`'s `benchmark` job carries the same lines, so the D5611 step parity holds. A `worker-N-of-6` part runs only `test:worker`. None of those tests reads the root `docs/` or `frontend/node_modules`. They import frontend *source*, and its packages (react, lucide-react, jspdf) resolve from the root `node_modules`. The root build needs vite from `frontend/node_modules`, so the two steps are skipped together. Every test that opens `docs/` (apex_truth_doc, pptx_image_size_not_bundled, repo_layout, assetsIgnore, check-docs-assets-closure, check-bundle-budget) is in `test:frontend` or `rest`, and those parts still install everything and build. The worker and root installs, both `queue-ref-alive.sh` steps, the tracer and the upload are unchanged. Saving: about 11–14 s on each of the six worker parts, roughly 1.1–1.4 runner-min per candidate.
2. **`ci / fast` skips its six duplicated steps under `merge_group`.** `install_scanner`, `scan`, `worker_install`, `worker_typecheck`, `frontend_install` and `frontend_build` carry `if: ${{ !cancelled() && github.event_name != 'merge_group' }}`. In the queue, the required `scan` (gitleaks.yml: the same gitleaks 8.21.2, the same `.gitleaks.toml`, the same `base_sha..head_sha` range), `worker (typecheck)` (`npm ci`, build-generated, `tsc --noEmit`) and `frontend (build)` (`npm ci`, `npm run build`) run the same commands on the same candidate. Fast still runs its queue-only work: the migration and drift checkers loaded from the trusted base. The verdict accepts `skipped` for those six outcomes only when `EVENT == merge_group`. On every event, checkout, setup-node, range, trusted, migrations and drift must succeed. A `failure` or `cancelled` outcome is a fail everywhere. On `pull_request` and `push`, fast behaves exactly as before. Fast keeps no job-level `if`, and `landing gate` is unchanged.

   **During the shadow phase, the queue's `ci / fast` and `landing gate` no longer reflect typecheck, build or secret-scan results.** In the queue they go green on a candidate whose `tsc`, SPA build or gitleaks would fail. Only the required `worker (typecheck)`, `frontend (build)` and `scan` jobs check those there. So the D5606 shadow comparison on `merge_group` runs covers the migration, drift and suite verdicts only; a queue candidate where `worker (typecheck)` or `frontend (build)` is red while `landing gate` is green is expected under D7108 and is not a shadow mismatch. Compare those three checks on `pull_request` and `push` runs, where fast runs every step. Saving: about 0.4–0.5 runner-min per candidate, and one fewer GitHub-release download in the queue.

### Evidence

- On `origin/main` (ebc86b3d6b), the 192 worker test files that import from `frontend/`, lucide or jspdf passed with `frontend/node_modules` removed and no `docs/` present: 2,077 tests, 2,076 passed, 1 skipped, 0 failed. This PR's own `pull_request` run gives the hosted proof: the full matrix runs all six worker parts under the new steps.
- `frontend/test/ci_worker_parts_7108.test.mjs` pins both conditions in both workflows and the unconditional worker and root installs. It also checks statically that no worker test names the root `docs/` or `frontend/node_modules`, so a soft `existsSync(docs)` skip cannot pass a worker part silently. `generated_before_build_5612` now requires the suite's one build step to skip only the worker parts. `landing_gate_5606` pins which fast steps skip in the queue, fails if `ci / fast` or `landing gate` becomes required (or a duplicate job is removed) while those skips remain, and executes the verdict for queue skips, queue failures, a skipped migration check, a missing drift or scan result, and skips on `pull_request` and `push`. Each new assertion has a mutation case that fails.

### Audit claims, checked

(1) Every shard runs three `npm ci` and a full SPA build: true before this change; the worker parts now run two installs and no build. (2) Fast duplicates the build and typecheck in the queue: true; the duplicated steps are now skipped there (item 2). (3) Verdict jobs need their own runners: true, deferred. (4) Fast downloads gitleaks on every run: true; no longer in the queue. (5) `plan` adds a runner hop: true, deferred. (6) `queue-ref-alive.sh` runs twice per shard: true by design (D5601, under 1 s). (7) `test-deps` competes with later candidates: true, deferred (D5608). (8) `verified` polls: it runs on push only, never in the queue.

### Not done, and why

- Building `docs/` once and sharing it as an artifact: a ~60 MB, ~1,300-file transfer costs about what it saves, adds a serial `needs` edge in front of the matrix, and leaves the source of the downloaded `docs/` unverifiable.
- A job-level skip of fast in the queue: D5606 pins that fast has no job-level `if`, and `landing` would have to ignore a trusted-base failure.
- Trimming the worker or root installs, or the first `queue-ref-alive.sh`: tests need those installs, and D5601 pins the ref check.

### Deferred to the owner

- **Remove the `plan` hop in the queue** (largest lever: 3.5–17 min of critical-path wall time and one runner per candidate). This needs a static matrix with a pinned timing source and changes to D5609 and the required gate's logic. It needs its own issue, PR and decision, reviewed by whoever signs off on the required gate.
- **Move the small control jobs (gate, landing, test-deps, plan, verified) to `ubuntu-slim`.** Benchmark this first with runner-benchmark.yml. Moving a required-context job to a new runner label needs owner sign-off (D5611/D6724).
- **Give merge-group CI its own runner pool** (larger, paid or self-hosted runners). This is the root cause the measurements point at: roughly a third to a half of queue wall time is runner wait. It needs an owner decision on billing or infrastructure. Jobs that read secrets stay on GitHub-hosted runners.
- **Cut the required contexts over to `ci / fast` + `landing gate`** (D5606 PR 2), then delete the duplicate queue jobs. This needs an owner edit of ruleset 25309597. **Precondition: first revert this decision's item 2** — drop `&& github.event_name != 'merge_group'` from the six fast steps (`install_scanner`, `scan`, `worker_install`, `worker_typecheck`, `frontend_install`, `frontend_build`) and the verdict's `merge_group` skip branch, in a PR that lands before the ruleset edit. Otherwise a candidate with a typecheck error, a broken build or a leaked secret passes the new required contexts and merges. `frontend/test/landing_gate_5606.test.mjs` ("the queue skips stay covered by the required jobs until they are reverted") fails while any of the six skips is present and `ci / fast` or `landing gate` is in `scripts/lib/requiredChecks.mjs`, or `worker (typecheck)`, `frontend (build)` or `scan` has left it, or the `frontend`, `worker` or gitleaks `scan` job has been removed, renamed or given a job-level `if`.
- **Take `test-deps` off the per-candidate path** while keeping timings flowing (amends D5608).
- **Skip push re-runs of non-required jobs on a commit the queue already verified.** This needs a review against `verify-production-candidate.mjs` admission.
- **Cache the gitleaks tarball in the required `scan` job.** This is a reliability fix, for a separate small PR.
