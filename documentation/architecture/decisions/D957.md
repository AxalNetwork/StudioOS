## D957 — Programs' referral and perk admin contracts

Issue #2790, part 4 of Programs #2371. Worker-first; no migration, no new UI.
Existing parameter-free list calls retain their response shapes. Item 15's
cross-member balance summary waits for OD8's account-population decision and
is not implemented or exposed by this partial delivery.

### Refer & Earn

- `GET /api/refer-earn/admin/strategic-access` defaults to requested; also
  accepts granted, declined or all, limit (maximum 200) and offset. It returns
  `{items,total}`, oldest first, without emails. `listStrategicAccess` is
  exported from `referralSubmissions.ts` for the program catalogue to reuse.
- `POST /admin/strategic-access/:userId/decision` accepts granted or declined,
  guards the UPDATE on requested, preserves the member's note and sets the
  decision time. Admin and branch gates precede it. `logAdminAction` records
  `referral_strategic_access.granted` or `.declined`, target and admin note.
  No request is 404; an already decided request is 409; invalid decision 400.
- `GET /admin/submissions` still returns an array without offset. Supplying
  offset opts into `{items,total}`. Filters accept comma-separated statuses
  through a single bound JSON value, and category. Limit stays at most 200;
  newest (default) and oldest use time then id for stable paging. Admin rows
  add `referrer_user_id`; member `toWire` does not change.
- `GET /admin/submissions/:uid` returns the admin row and its existing history;
  missing is 404. `GET /admin/submissions/weekly?weeks=4|12|52` returns
  `{from,items:[{week,startup,customer,strategic}]}` with UTC Monday buckets,
  including empty weeks and the current partial week. Failed reads propagate.

Referral moves (`reviewSubmission`, one table beside STATUSES):

| From | Allowed destinations |
|---|---|
| draft | submitted, rejected, closed |
| submitted | under_review, more_info_needed, qualified, rejected, closed |
| under_review | more_info_needed, qualified, rejected, closed |
| more_info_needed | under_review, qualified, rejected, closed |
| qualified | in_conversation, rejected, closed |
| in_conversation | converted, rejected, closed |
| converted | reward_eligible, closed |
| reward_eligible | reward_issued, closed |
| reward_issued, rejected, closed | none |

Nothing enters draft. Same-status saves are annotations, including on terminal
rows: other fields save without another status event; a supplied note creates
an Updated event with null status. Status update and timeline insert share a
D1 batch. The UPDATE guards the observed state; the conditional insert runs
only if it changed a row. A competing decision returns 409 bad_transition and
adds no event. The member's own context-update behavior is unchanged.

### Perks

`POST /api/perks/admin/:uid/review` checks Admin, then branch suspension.
The state and observed updated_at are guarded in the UPDATE.

| Action | From | Result |
|---|---|---|
| approve | in_review, draft, paused | live |
| approve | live | feature/editorial edit only; review note and reviewer metadata kept |
| reject | in_review, draft | rejected; own reason required |
| pause | live | paused |

Other moves refuse with 409 not_reviewable; rejected stays final. Invalid
act, missing listing and missing rejection note use bad_action, not_found and
note_required through refuse. Explicit `featured:false` clears the flag;
omission keeps it. Missing/blank approve or pause notes keep the prior note.
Decisions audit perk.approved, perk.rejected or perk.paused; live edits audit
perk.feature_updated, with uid, before/after status, feature-change flag and
partner target when present.

`GET /api/perks/admin/listings` returns `{items,total}`, all five states or
one state, newest/oldest by updated time, limit at most 100 and offset. Rows
retain the queue's fields and add all-time claims/redemptions. The existing
queue shape and draft/in_review membership stay unchanged.

`GET /api/perks/admin/claims?weeks=1..52` (default 12) returns from,
by_listing (ranked claims and redeemed), by_week (Monday/kind_at_claim with
claims and redeemed, including zero buckets), and totals. Exported
`perkClaimsCounts` in `services/perkClaims.ts` is the catalogue's shared read.
All counts cover the same window, from Monday of the first week through now.
Redemptions count claims made in that window which are redeemed now. ISO and
SQLite timestamps normalize through datetime; no credit-spend sum is exposed.
A database failure is an error, not a fabricated empty chart.

### Integration and validation

Existing API client families gain the new reads and strategic decision.
The branch suspension summary also names Perks in its frozen Programs writes.
The partner alias contract inspects GET /partner rather than counting admin
queries that happen to share its alias.
Program Activity action lists belong to #2787 and do not exist on this base;
that part must include the six audit action names recorded above. New literals
precede parameter routes. No member eligibility, referral credit reward,
reapplication after decline or rejected-listing resubmission changes here.

Tests dispatch Hono with signed JWTs against migration-based node:sqlite,
exercise every referral pair and perk action/state, same-state updates, exact
pagination past 200, timelines, both strategic decisions and conflicts, audit
rows, un-feature, kept notes, empty weeks, failed reads, authorization and
suspended writes. Clients are checked through stubbed fetch; key regressions
are mutation checked. Build/full-suite results are recorded in the draft PR.
