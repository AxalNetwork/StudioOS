## D4611 — Records past a page are reachable, counts name their scope, and a failed read is not a zero (#4611)

#4611 (Network audit 4 of 5, slot S11, taken at the owner's request). Carries
findings 7 to 11.

### The project filter runs before the page (finding 8)

`GET /api/contacts` answered one bounded page — `LIMIT 500`, no cursor — and
built `counts` by walking it. `FounderNetworkRelationships` then discarded
every row whose `project_id` was not the selected startup. So a founder with
more than 500 contacts across their startups opened one startup's book and saw
whichever of its contacts happened to survive a cut made across all of them:
600 on startup A and 40 on startup B could render B as **empty**, with "In the
book 0" above it.

`project_id` is a server filter now, applied inside the authorized scope and
before `LIMIT`; an id outside the scope is `project_not_authorized` in the same
words whether it is somebody else's or nobody's. `counts` and `total` come from
their own aggregate over the whole filtered set and do not move when the page
does. Continuation is #4701's own `util/keyset.ts` — `listLimit`, `decodeCursor`
(a malformed cursor is a 400, never a silent restart), `trimPage` — on
`(COALESCE(last_activity_at, created_at) DESC, id DESC)`. `id DESC` is new and
is what makes that order **total**: the sort key alone is not unique, and a
non-total order has no keyset cursor.

The 500 was never a page size; it was the cap standing in for paging.

### The introduction log is a page, and its counts are not the page's (finding 8)

`introRequests` read `LIMIT 100` across **sent and received together** and then
split the one page into two lists. A busy introducer's own asks were crowded out
by rows they had been asked; a pending request older than the newest hundred was
in no list and so could not be answered, which is the log's whole purpose; and a
notification could name a request the log would not show. None of it was
visible to the reader.

Keyset pagination on `(created_at, id)` through the same cursor format, and
`totals` — `sent`, `received`, `sent_pending`, `received_pending` — from one
aggregate over the whole filtered log. `relationshipSummary` already computed
the two pending counts and nothing read them. An unreadable aggregate throws
rather than returning four zeroes under a populated list.

`followUpsDueList` (`GET /relationships/intro-requests/follow-ups-due`) is the
navigable list behind a positive `follow_ups_due`: the count was unbounded while
the rows beside it were capped, so the desk could say "7 follow-ups due" over a
page holding none of them, with nowhere to go. Same predicate as the count, so
the two cannot disagree.

### The cold clock (finding 9)

`contacts.filter(isCold)` is well-formed JavaScript calling a well-formed
function, and `Array.prototype.filter` invokes its callback as
`(element, index, array)` — so `isCold`'s second parameter, `now`, received the
**row index**. `daysSince` clamps at `Math.max(0, …)`, so against a clock of
0, 1, 2 every contact measured zero days old and **no row was ever cold**. The
summary read "Going cold: 0" and "Coldest: Unavailable" beside a chip filter
(`(row) => isCold(row)`, an arrow, correctly defaulted) and a per-row cell that
both flagged the same records. Three readers of one definition; one of them
silently measuring against 1970.

`coldView` existed and could not be used: it reads `last_interaction_at`, the
investor and advisor tie column. `coldBookView` and `coldestBookDays` are its
founder twins on `last_activity_at`, and they take `now` **once** for the whole
list, so a summary cannot straddle a midnight boundary either. Passing `isCold`
bare to `filter` is now a mistake with an alternative rather than a workaround.

### Unreadable is not empty (finding 10)

`FounderNetworkRelationships`'s state machine was `chosen ? 'ready' : …`, so a
**rejected** contacts read with a resolved project was `'ready'`: a full, zeroed
book, with a table whose empty state says "No matching project-linked contacts
are recorded" — a statement of fact about the store — and a thin amber banner
above it. Zero presented as a figure somebody read. `'unreadable'` is its own
state now, it draws no counts, and `contacts` is `null` until a read succeeds,
never `[]`, because an empty array renders exactly as an unread list does.

`RecordCompose` branched on `account`'s truthiness alone, so a null from a
**failed** mailbox lookup and a null from a member with no mailbox rendered the
same sentence — telling someone whose mailbox is connected to go and connect it,
and hiding an outage behind a setup prompt. `mailboxes` makes the caller say
which it is (`connected` / `none` / `unreadable`); both callers already held the
distinction and neither passed it on. Only `none` gets setup guidance, and it
gets a route to follow rather than an instruction with nowhere to go.

### Complete navigation and explicit scopes (finding 7)

`InvestorNetworkWorkspace` applied `slice(0, 4)` on **both** surfaces — the
`/network` overview, where four cards is right, and the dedicated
`/network/introductions` zone, which is the only place a member can act on a
proposition. The fifth and later propositions were unreachable by any
navigation; accepted and declined records fell off the same edge. The heading
beside the four cards read `${propositionRows.length} shown` — "30 shown" above
four — and the export carried the four while the heading claimed thirty, the
one zone on the page that did not export its full array. Organizations had the
same shape at six rows.

The cap is now what its name says: a preview on the overview, which links to the
zone; the zone pages. Three numbers mean three things and the heading says which
is which. The export is the whole filtered collection.

### The note the decline form promised (finding 11)

The form's label is "A note they will read (optional)". The note is stored on
`relationship_interactions.decision_note`, `interactionView` has always returned
it to **both** people on a request, and `grep decision_note frontend/src`
returned nothing. The teammate typed an explanation, the product said the asker
would read it, the Worker served it, and the asker's log had no column for it;
the notification said only "There is a note for you", pointing at a page that
would not show it.

`decisionLine` pairs the note with the verdict and its date — "Declined on
2026-11-04" — because a bare note is a sentence with no subject. An acceptance
note is shown too: same column, same writer, same reader. A request answered
without a note draws nothing, because an absent note is not "no reason given".
Only the two people on a request can read it, which was already true at the API.
The textarea's `maxLength` was 500 against the Worker's 1,000, so a 600-character
note was clipped by the browser before it was ever sent.
