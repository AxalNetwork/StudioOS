## D543 — Support-ticket triage: Session 1's protocol, and the bounty and feature labels it runs on

**Issue #1106, slot S01, part of #1101 (the support-ticket epic),
2026-10-06.** No migration, no Worker change and no new route. This declares
the labels, and writes down who applies them and when.

### What was true on main

- The Worker already acts on eight labels that GitHub did not have:
  - `services/bugBounties.ts` (D542, #1105) reads the six `bounty:` labels;
  - `routes/admin_ticket_reviews.ts` (D544, #1107) adds `feature:approved`
    or `feature:declined` to a feature request's issue.
- `.github/labels.yml` declared none of them, so `labels-sync.yml` never
  created them (D503). The repository's only ticket labels were the ones the
  GitHub sync creates on first use, such as `support-ticket`, with no
  description.
- AGENTS.md said nothing about tickets, so no agent knew that only Session 1
  applies these labels.

### The labels

They are declared in `.github/labels.yml`, and `labels-sync.yml` creates them
when this merges.

| Label | Who adds it | What the platform does |
|---|---|---|
| `bounty:confirmed` | Session 1 | nothing yet: the ticket reads "being fixed" (D542) |
| `bounty:not-a-bug` | Session 1, with the reason | closes the ticket and its issue |
| `bounty:duplicate` | Session 1, with a link to the original | closes the ticket and its issue |
| `bounty:verified-high`, `-medium`, `-low` | Session 1, once the fix is checked in production | grants `bug_high`, `bug_medium` or `bug_low` (#1105) |
| `feature:approved` | the platform, when the Super Admin approves | Session 1 files the build task |
| `feature:declined` | the platform, when the Super Admin declines | the member is sent the reason |

**Only Session 1 adds a bounty label, and the platform enforces it.** D542's
`BOUNTY_GRANTERS` allowlist holds only the owner account, which Session 1
writes as. A bounty label from any other sender is refused and logged, and
grants and closes nothing. A collaborator, a bot or an outsider cannot pay
themselves.

### The protocol

AGENTS.md has a "Support-ticket triage" section in the task protocol, so
every agent knows the flow and that only Session 1 applies these labels:

1. **Check.** For each new `support-ticket` issue labelled `bug`, Session 1
   reproduces the bug from the code and the report, and searches for
   duplicates.
2. **Label the outcome,** with a short reason comment: `bounty:not-a-bug`,
   `bounty:duplicate` with a link to the original, or `bounty:confirmed`. For
   a confirmed bug, Session 1 files a slot task that links the ticket.
3. **Verify.** After the fix merges and deploys, Session 1 checks in
   production, read-only, that the bug is gone.
4. **Grade.** Session 1 rates the value of the fix High, Medium or Low, and
   adds the matching `bounty:verified-` label. The platform grants the reward.

A feature request is never built until the Super Admin approves it (#1107).
The approval adds `feature:approved`, and Session 1 then files the build
task.

### The hourly check

From the day #1105 merges, Session 1 runs this check every hour:
- triage new `support-ticket` issues labelled `bug` that carry no bounty
  label;
- verify and grade the confirmed tickets whose fix has deployed;
- file the build task for each newly approved feature.

**It has not started.** #1105's grant is still in progress, and D542 records
that Session 1 applies these labels only from the day it merges. So #1106
stays open for this step.

### Claims from outside

On 2026-10-04 an account outside the project forked the repository. It opened
#1115, a pull request that edited AGENTS.md as a "fix" for #1106 and ended
with `/claim #1106`. That is the command bounty platforms use to claim an
issue's reward. Its author closed it, unmerged, 12 minutes later.

- It had no access to the repository.
- Its workflow runs got no secrets: no workflow here runs a fork's pull
  request with `pull_request_target` or `workflow_run`.
- It is the only issue or pull request in the repository's history opened by
  anyone but the owner or a bot.

These bounties are not GitHub bounties. They are platform credits granted to
the member who filed the ticket. The AGENTS.md section says so:
- nothing on GitHub claims one;
- a pull request from outside the project is closed without being merged.

The repository-level defences are the owner's settings, not this change:
- blocking an account at the organization;
- limiting interactions to collaborators;
- requiring approval for fork pull request workflows.
