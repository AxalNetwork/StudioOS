## D4628 — Session setup distinguishes "the row exists" from "setup finished", and resumes instead of faking success (#4628)

- **Status:** Built for #4628, 2026-11-07. Covers both `founder_validate_sessions.ts` setup
  endpoints: `POST /sessions` (new-person/per-interview-pick setup) and
  `POST /interviews/:id/sessions` (per-interview Start).
- **Builds on:** D685 §5.1/§5.1.1 (the one-call setup and its `client_key`
  replay/race handling), migration 452 (`client_key` and its unique index),
  #4584 (parent: reliable evidence processing through failures).
- **Migration:** `cloudflare-worker/sql/migrations/202611071550_session_setup_complete.sql`
  — adds `interview_sessions.setup_complete_at`, backfilled non-null on every
  existing row.

### Problem

`openOn` inserted the session row, then ran further writes (talking points,
the output preference, the interview's channel and quote consent, the audit
row, and — for an upload or a pasted chat — the held-stage move and the
content itself) as separate, later calls. The setup routes caught any
exception from that whole sequence, looked the session up again by
`client_key`, and returned it as a successful duplicate-start replay merely
because a row with that key existed. A failure in any of the later writes —
most visibly a failed pasted-transcript write — left a session whose
submitted content never landed, while the response reported success. A
repeat of the same `client_key` then returned that same false "success"
forever, because the replay check asked only "does a row exist", never
"did its setup finish".

### Decision

1. **`openOn` now does only the insert.** It creates the interview (when the
   setup call is making one) and the session row in one D1 batch — unchanged
   from before — and returns with `setup_complete_at` left `NULL`. Nothing
   past this point is assumed to have happened just because the row exists.
2. **A new function, `finishSetup`, does everything else, as one D1 batch
   whose last statement stamps `setup_complete_at`.** The output preference,
   the talking points, the interview's channel/quote-consent updates and the
   audit row land together or not at all (D1 runs a batch as one
   transaction — the same guarantee `openOn`'s own insert already relied on
   for the interview/session pair). An upload's held-stage move and a pasted
   chat's content (`markInterviewHeld`, `replaceWithFinal`) run first, ahead
   of that batch, because each is already independently safe to repeat:
   `markInterviewHeld` is documented best-effort and idempotent, and
   `replaceWithFinal` deletes-then-inserts its segments in its own atomic
   batch, so running it again after a failed attempt lands the same content,
   never a second copy. `setup_complete_at` is therefore the single fact
   that says "every one of these writes has landed", stamped only once they
   all have.
3. **A session found by `client_key` is only answered as a completed replay
   when `setup_complete_at` is set.** Found incomplete, the route calls
   `finishSetup` with the *current* request's own `plan`/`body` — the same
   content a legitimate retry resubmits — and answers success once that
   lands, or an explicit `{ detail: 'setup_incomplete' }` (202) if it fails
   again. Nothing is silently reported as having worked when it has not.
4. **Only a confirmed `client_key` unique-index violation is treated as the
   duplicate-start race.** `isClientKeyRace` checks the D1/SQLite error text
   for `interview_sessions.client_key` specifically (the codebase's existing
   convention for reading `UNIQUE constraint failed`, e.g.
   `capTableWrites.ts`, `programRegistry.ts`). Any other exception from
   `openOn` is no longer swallowed into a false success — it is rethrown,
   uncaught, so the failure is visible on that request; the row it may have
   already inserted is picked up and finished by the next request carrying
   the same `client_key`.
5. **Both setup endpoints share the same `openOn` → `finishSetup` →
   `resumeOrReplay` path**, so a new-person setup, a picked-interview setup
   and a per-interview Start all behave the same way under a late failure.

### Why not a fully single-batch `openOn`

An earlier draft considered folding every write (including the held-stage
move and the pasted content) into one D1 batch with `openOn`'s own insert,
using the session's already-known `uid` to avoid needing its numeric id
ahead of time. That would remove the two-phase gap entirely, but the
`interview_session_created` audit row's JSON needs the newly created
interview's numeric id as a literal value, which is not known until the
insert has actually run; forcing it through a subquery (or dropping it from
the JSON) would change an existing audit shape other code may read. Two
batches — the insert, then `finishSetup` — keeps that shape, keeps each
batch itself atomic (removing the previous bug entirely for everything
inside `finishSetup`), and uses `setup_complete_at` only to cover the one
remaining gap: the interval between the two round trips.

### What stays the same

- A genuinely completed replay (`setup_complete_at` set) returns the same
  committed result immediately — `finishSetup` never runs twice.
- Two Start clicks racing the unique index still produce exactly one
  session; the loser now also finishes the winner's setup if it had not
  landed yet, rather than only echoing a possibly-unfinished row.
- Every column's semantics are unchanged: points are still a plain INSERT
  (never re-run once `setup_complete_at` is set, since resume only runs when
  it is `NULL`, and `finishSetup`'s own batch is all-or-nothing on a single
  attempt), the channel/quote-consent updates are still idempotent
  `COALESCE`/flag writes, and the held-stage move is still "best-effort,
  idempotent, never fails the caller that triggered it".

### Tests

`cloudflare-worker/test/interview_sessions_d657.test.ts` adds:
- a fault-injection case per setup endpoint (`/sessions` with talking
  points; `/interviews/:id/sessions` with a pasted chat) that forces a
  later write to throw, asserts the response is not a false success, that
  the session exists but is not marked complete, and that the content that
  write was supposed to store did not land; then retries the same
  `client_key`/body and asserts the session completes exactly once with the
  originally submitted content, no duplicate interview and no duplicate
  audit row — and a third identical retry proves a genuinely completed
  replay never re-runs `finishSetup`;
- a concurrent-Start race case for `/interviews/:id/sessions` (the existing
  one covered only `/sessions`), and an added assertion on the existing
  `/sessions` race test that the resolved session is actually marked
  complete, not merely present.

Every fixture across the suite that applies migration 452 now also applies
this migration (mechanical, since `setup_complete_at` is additive); one
fixture (`call_outputs_4412.test.ts`) builds its `interview_sessions`
columns by hand rather than from the migration file and got the column
added to that same list.
