## D7146 — PR previews deploy from a trusted job on `main`; pull-request runs hold no Cloudflare credential (#7146)

Part of #7144 (issue 2 of 8). Owner decision A on #7144: **A1**, a trusted job on `main` deploys the artifact a credential-free pull-request job built, in the same Cloudflare account. Amends D4130 (where the deploy runs, not when) and the `login-e2e` arrangement of D722 and D753 (what the specs run against). Coordinates with #7145, which moves the production credentials into the `production` and `production-ops` environments and deletes the repository-level `CLOUDFLARE_API_TOKEN` once this has landed too.

### Why

`pr-preview.yml` ran on `pull_request` and read `CLOUDFLARE_API_TOKEN` in the same workflow that built and tested the branch. A same-repository branch writes that workflow file, so every branch could read the token. Scoping the token does not help here: each preview is a new Worker (`studioos-pr-<number>`), and a token that may create a Worker that does not exist yet needs account-wide Workers edit. That token must never reach a run that executes a branch's code.

### The trust boundary

- **Untrusted side: `pr-preview.yml` (`pull_request`).** Runs the branch's code. Reads no secret at all, has a read-only `GITHUB_TOKEN` (`contents: read`; the merged-branch cleanup job keeps its own `contents: write`, and runs only from the merged base). Its `build` job builds the SPA and uploads `docs/` as the `pr-preview-docs` artifact, leaving out `_headers`, `.assetsignore`, `.asset-retention.json` and `.build-source`. Its `login-e2e` job runs the D722 and D753 specs (check name `/login Google window (Playwright)`, unchanged).
- **Trusted side: `pr-preview-deploy.yml` (`workflow_run` on `PR preview` completed).** GitHub reads a `workflow_run` workflow's file from the default branch, so this is always `main`'s code. Top-level `permissions: {}`; each job asks for what it needs:
  - `resolve` (`actions: read`, `contents: read`, `pull-requests: read`, no secret, no checkout) takes the PR number and head commit **from the event payload** and checks them against the API: a `pull_request` run of `.github/workflows/pr-preview.yml`, from this repository (forks get no preview, as before), not Dependabot, the pull request on this run's branch, not a draft (D4130), and the head commit still the PR's head. A closed PR's run carries no number in the payload, so then the PR is the one whose head is this run's branch and commit. It decides `deploy`, `delete` or nothing, finds the run's one `pr-preview-docs` artifact (size under the zip cap), and before `deploy` or `delete` confirms that the `pr-preview` environment admits exactly `main`. A run for an older commit deploys nothing; the run for the newer commit deploys. Nothing is ever read from the artifact to make these choices.
  - `deploy` (`environment: pr-preview`, `actions: read`, `contents: read`, `pull-requests: write`) checks out `main`'s own commit without persisting credentials, sets up Node without a dependency cache, fetches the artifact zip through the REST API into the runner's temp directory, checks and unpacks it, adds `main`'s `frontend/public/_headers`, deploys with `main`'s `wrangler.pr-preview.toml` and `scripts/pr-preview-worker.mjs` (no bindings), waits for `/login` to answer, and keeps the one sticky `<!-- pr-preview -->` comment.
  - `delete` (`environment: pr-preview`, no token permissions) deletes `studioos-pr-<number>` when the PR closes, with the retry rules of #5527 unchanged.
- **Only `deploy` and `delete` can read `PR_PREVIEW_CLOUDFLARE_API_TOKEN`,** and only because they name the `pr-preview` environment, which admits jobs on `main` only. A branch that adds its own workflow cannot enter it.

### The artifact is data

`scripts/check-preview-artifact.mjs`, with its rules in `scripts/lib/previewArtifact.mjs`, reads the zip's central directory itself and accepts the archive all or nothing:

- at most 5,000 files, 25 MiB per file (Cloudflare's own asset limit), 200 MB uncompressed in all, a 200 MB zip; each entry must inflate to exactly its declared size with a matching CRC, so a size lie or a compression bomb is refused;
- regular files and directories only: a symlink, device or other mode is refused, as are encrypted entries, ZIP64 and multi-disk archives;
- names: no absolute path, backslash, `.` or `..` segment, empty segment, character outside `[A-Za-z0-9._@+~-]`, leading dot (except the top-level `.well-known/`), or a name that differs from another only by case;
- extensions from a fixed static list (html, js, mjs, css, map, json, webmanifest, txt, xml, md, png, jpg, jpeg, gif, webp, avif, svg, ico, woff, woff2, ttf, otf);
- no configuration: `_headers`, `_redirects`, `_routes.json`, `_worker.js` and `.assetsignore` are refused at any depth; `_headers` comes from `main`;
- an `index.html` at the root.

The unpacker writes only into an empty `docs/` and refuses to write anything if one problem is found. The trusted job runs no script from the artifact, installs no lockfile and reads no config from it; `wrangler` comes from the registry at the pinned version, as before.

### The browser tests

The deploy only starts once the pull-request run has completed, so a job in that run cannot wait for it, and running the branch's specs on the trusted side would put branch code in `main`'s cache scope and hide the result from the PR's checks. So `login-e2e` stays in `pr-preview.yml` and runs both specs against the same artifact, served by `wrangler dev` from the same `wrangler.pr-preview.toml` and preview script the deployed Worker runs (no Cloudflare account needed). The trusted deploy then checks the deployed Worker answers `/login` before it posts the link. All 13 tests passed locally against `wrangler dev` serving this branch's build.

### Guards

- `frontend/test/workflow_security_4571.test.mjs` **WF-7**: no workflow triggered by `pull_request`, and no `pull_request_target` workflow that checks out the branch, references a Cloudflare credential (`secrets.*CLOUDFLARE*`, `*WRANGLER*`, `CF_API*`, `CF_ACCOUNT*`), `secrets[...]`, `toJSON(secrets)` or `secrets: inherit`. **WF-4** now admits `workflow_run` only for the files in `TRUSTED_WORKFLOW_RUN`, each with a decision file, `workflow_run` on completion as its only trigger, no `ref:` checkout, no `actions/download-artifact`, the `pull_request` and same-repository checks, and `permissions: {}`. **WF-5** adds the `workflow_run` fields a branch author writes (`head_branch`, `display_title`, `head_commit`, `pull_requests`).
- `frontend/test/pr_preview.test.mjs` pins both halves, the token in exactly the two environment jobs, the fetch → check → `_headers` → deploy order, and runs the `resolve` script against a simulated API (deploy, every refusal, closed-PR lookup, the environment rule).
- `scripts/lib/previewArtifact.test.mjs` builds hostile zips by hand: symlink, traversal, absolute path, control files, script extensions, size lie, bomb, CRC mismatch, encryption, caps.
- When #7145's credential guard lands, its `pr-preview.yml` exception is dropped: after this change `pr-preview.yml` reads no secret, and the preview token lives only in the `pr-preview` environment.

### Owner setup (before merge)

1. Create the GitHub environment **`pr-preview`**. Deployment branches: **selected branches**, with exactly one rule, the branch **`main`**. No required reviewer, no wait timer (a reviewer would add a click per preview). `resolve` refuses to deploy or delete while the environment is missing or admits anything else.
2. Create a Cloudflare API token with **Workers Scripts edit on the account only** (no D1, KV, R2, queue, route or DNS permission), and add it to the `pr-preview` environment as the secret **`PR_PREVIEW_CLOUDFLARE_API_TOKEN`**. `CLOUDFLARE_ACCOUNT_ID` stays readable as today.
3. **`agent-compute-preview.yml`** already names its `agent-compute-preview` environment and reads `secrets.CLOUDFLARE_API_TOKEN`. An environment secret takes precedence over a repository secret of the same name, so its token moves with no file change: add `CLOUDFLARE_API_TOKEN` (a token scoped to what that workflow deploys) as a secret of the `agent-compute-preview` environment before the repository-level one is deleted.
4. Keep the repository-level `CLOUDFLARE_API_TOKEN`: production still reads it until #7145 lands. Its deletion and revocation is #7145's step 4, once both have landed.

### Follow-up, not done

- **A2: a separate Cloudflare account for previews.** The stronger isolation: the account-wide Workers token then cannot touch a production Worker at all. Recorded as the follow-up the owner may choose; out of scope here.
- Previews for PRs whose run is cancelled by a newer push are skipped on purpose; the newer run deploys.
