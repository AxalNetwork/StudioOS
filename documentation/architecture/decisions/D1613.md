### 1. What a session is

An **AI agent session** is one run of one agent, on one of its role's skills:
- optionally on one record (a meeting, deal, deck, module or document), with a short instruction;
- at a time (`once`) or on a repeat (daily, weekly, monthly).

Its work comes back as **proposals in Approvals**, and nothing is applied until a named person accepts it. Before the run, a hold is shown, within the agent's monthly cap, paid from the sponsor's AI tokens.

A session is skipped, with its reason and **without a charge**, in four cases:
- the agent is paused;
- the sponsor is out of tokens;
- a tool the skill reads is disconnected;
- the skill was retired.

These are #3957's terms on #3849's `agent_duties`, not a second scheduler.

### 6. #3957, the Worker: sessions on E5's duties

Built 2026-11-02 by the S06 slot, on D1530's E5 duties. No second scheduler is added.

- **Number.** #3957 names no decision, so its Worker half is this section of the Calendar decision its screen side already uses. Its issue's STATUS says so.
- **A session is a duty row.** `agent_duties` has `kind = 'session'`. Migration `202611022045_agent_duty_sessions.sql` rebuilds the table the way 762 rebuilt `scope_task_events`, keeping every row, every id and the AUTOINCREMENT mark:
  - `cadence` also takes `once`, with `run_at`;
  - `minute_utc`, `zone` and `local_time` hold the time;
  - `skill_id` and `skill_version` hold the skill;
  - `target_kind` and `target_id` hold the record;
  - `instruction` holds at most 1,000 characters;
  - `status` also takes `done`, for a once session after its claim;
  - `template_key` becomes a duty's only, and E5's one-live-duty-per-template index now covers duties alone.
  - CHECKs keep the shapes honest: a session always has a skill and never a template; a duty is never once; a target has both its kind and its id.
- **The skill.** It is one **assigned** to the agent (S1's decision of 2026-11-02 on #3957: agents no longer have roles), at its pinned version.
  - Otherwise the answer is 422 `skill_not_in_role`, "That skill is not assigned to this agent." The code is kept so the screen's mapping holds.
  - A skill retired after scheduling skips the claim: `skipped:skill_retired`.
- **The record.** Two kinds are accepted today, because their read gate can be checked here:
  - a **module** in the agent's rule book;
  - a **project deck** in the agent's scope.

  For either, the sponsor must still read the team. `meeting`, `deal` and `document` are refused 422 `target_not_readable` until a gate for each exists. They are not quietly accepted.
- **Where the work lands.** A run needs a module and an option. A session takes the target module when there is one, else the first `works_in` module of the agent's book that offers one of its `may_propose` options (`placeOf`). `agentFits` still checks the pair at run time, so a session never reaches past the agent's rule book.
  - The skill's own steps ride with the run as data (below). The skill picking its own option is #3954's run path.
- **Time.** `once` is an instant (UTC). A repeat is a local time in the member's IANA zone (`zonedNext`), so 08:00 Lisbon stays 08:00 across the clock change.
  - The next slot is always strictly after the claim's own time, so a missed slot runs once (E5's rule), to the minute, within the sweep's 5-minute tick.
  - The screen names days `Monday`…`Sunday`; the row keeps E5's 0 = Sunday.
- **The claim.** It is E5's `claimDuty`, unchanged for duties.
  - A once session is claimed by flipping it to `done`, guarded by `next_due_at` and `status = 'active'`. Two sweeps make one task between them.
  - A repeat moves to its next zoned slot.
  - A claim is skipped and records why when the agent is paused (`skipped:agent_paused`), the skill is retired, or the sponsor has no tokens (`skipped:no_tokens`, which the read calls `out_of_tokens`).
  - The task is E5's `kind = 'duty'`, with `source_ref` set to the session's uid. With `AGENT_AUTONOMY = manual`, nothing runs until a person presses Start or Run now.
- **The instruction is untrusted.** `buildContext` adds one `<agent_data source="session" trust="data">` block, marked `untrusted: true`, holding the pinned version's name and steps, the target and the instruction. The instruction appears nowhere else in the prompt and is never logged.
- **The cap.** Save is refused 422 `over_cap` in two cases:
  - this session's runs left this month, plus the agent's other live sessions, exceed what its cap has left;
  - the agent is already at its cap. Then no quote is even asked for, because a quote at the cap pauses the agent and an estimate must change nothing.

  An estimate that cannot be read refuses nothing; the run's own cap check still holds.
- **Routes** (`agent_engine.ts`, behind the engine's flag):
  - `GET /api/teams/sessions/agents`: the agents of the teams the member manages.
  - `POST /api/teams/agents/:uid/sessions/estimate` returns cents, null when unread, never 0.
  - `POST /api/teams/agents/:uid/duties` with a `skill_id` makes a session.
  - `GET`, `PATCH` and `DELETE /api/teams/sessions/:uid`.
  - `POST /api/teams/sessions/:uid/run` makes one task, admitted through the runtime like a person's Start, so its hold, cap and single flight apply.
  - A manager of the team, or the agent's sponsor, changes a session; any reader of the team sees it, and its instruction only if they may change it. People appear by name only.
- **The read's `state`:**
  - `cancelled` (removed);
  - `running`, or `waiting` with `proposals_waiting` (from the latest run of its tasks);
  - `skipped` (the last claim's reason);
  - `paused`, `done` or `scheduled`.
- **The calendar.**
  - `agent_session` is a kind of the new "AI agents" family (teal: `#0f766e` light, `#2dd4bf` dark).
  - It is page only, and in `PERSONAL_ONLY_KINDS`: a team's members read it, never a staff scope.
  - Its reader gives each live session's slots in the range (at most 40), plus the runs it made, all `read_only`.
