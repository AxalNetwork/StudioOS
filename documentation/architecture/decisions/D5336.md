### 1. A case's identity

There is one helper, `skillCaseIdentity.caseIdentity`. The CI gate's manifest, the store manifest
(`storedCaseIdentity`), the reconciliation and the seed's skip rule all call it. #4531's `caseSha` lives in the same
module, so the hashing cannot drift. `skillLifecycle.ts` re-exports `caseSha`, so its callers are unchanged.

| Case | Identity | Key |
| --- | --- | --- |
| A scenario (`skills/scenarios/<slug>.json`) | its `case_id` and integer `revision` | `<case_id>:r<revision>` |
| A v1 golden case (`skills/cases/<slug>.json`) | unchanged from D4532 | `<slug>#<first 12 hex of sha256({input, expect})>` |

Every identity also carries `sha256`, the content hash of what `checkCase` keeps.

**The v1 identities are unchanged, with one fix.** D4532 §2 says the hash is of what `checkCase` keeps, but the source
side hashed the raw file. For the one file that carries `refuse_when` (`customer-interview-summary`), that gave a hash
its own seeded row could never have, so the reconciliation read it as `case_drift`. Both sides now hash the checked
case. The other 181 golden identities are byte-for-byte what they were, and the test checks every one.

### 2. Generator, store and seed

**Generator.** `build-skill-library.mjs` embeds a skill's scenarios after its golden case, one case each. Each carries
`skill`, `case_id`, `revision`, `name`, `note` (the scenario's `covers`), `input` and `expect`; `outputs` and `staged`
stay in the pack. The module was rebuilt with the script. The library now has 182 skills, 234 cases and 52 scenarios.
No test pins these totals.

**Store (the change from D4588 §3).** A text cannot give back a `case_id` and `revision`, so the seed writes them to
`agent_skill_cases.source_case_id` and `source_revision`. For a golden case it writes `<slug>#<sha12>` with no
revision. A row with neither is identified by its content, exactly like a v1 golden case: that covers rows from an
older seed and cases an HQ admin added. The migration adds:

- a partial unique index, so two live cases of one skill cannot share a source identity;
- a trigger that makes the two columns as immutable as the rest of the row.

**Seed.**

- Each scenario is stored under its own `name`. A golden case keeps `"<slug>: golden case"`.
- **The skip rule:** a draft gains a case only when no live case has its identity. Nothing is edited or replaced,
  whether live or removed.
- **A changed revision is a new case.** It is added beside the old one, which stays live until an HQ admin removes it
  through the reviewed `PUT /:uid/cases`. The draft's evidence changes, so it needs a fresh review and fresh evals
  before any publish (D4533).
- **A changed golden case** is also a new identity now, so it is added the same way. Before, the name rule skipped it.
- A published or retired skill gains nothing, as before.
- Seeding stays idempotent and writes no audit row when it adds nothing. It never publishes.
- Two source cases with one identity are refused (`case_identity_duplicate`).

### 3. The CI gate

`check-skill-library.mjs` now reads `skills/scenarios/` too. It runs #4588's suite rules on every pack, through
`skillScenarios.checkScenarioPacks`. Each rule below is an error:

| Rule | Fails when |
| --- | --- |
| `scenario_malformed` | the pack is not JSON, or has no `skill` and `scenarios` |
| `scenario_orphan` | the pack names another skill, or its skill has no definition |
| `scenario_case_id_invalid` | the `case_id` is not `<slug>-<scenario>` |
| `scenario_case_id_duplicate` | a `case_id` is used twice |
| `scenario_revision_invalid` | the revision is not an integer of 1 or more |
| `scenario_name_duplicate` | a name is used twice, or is a golden case's name |
| `scenario_has_email` | there is an email address anywhere in the scenario, outputs included |
| `scenario_correct_fails` | the known-correct output fails `judge()` |
| `scenario_incorrect_not_caught` | an incorrect output passes, or fails on another assertion than the one it names |
| `scenario_incorrect_invalid` | an incorrect output's edit is not found exactly once |
| `scenario_assertion_uncaught` | an assertion has no incorrect output that fails on it |

The packed cases then go through the existing per-case rules, like every library case:

- `checkCase` itself;
- `record_key_unknown` and `record_key_outside_tools`, so a case uses declared reads only;
- the skill and output-kind checks.

Two rules are new beside them. `case_identity_duplicate` fails two cases of one skill with one identity. `cases_max`
fails a skill with more cases than the cap; it is `checkLibrary`'s own refusal, reported like every runtime code.

**Coverage is reported apart from executions.** The summary gains `scenario_coverage`: for each skill, its cases,
scenarios, assertions, incorrect outputs and staged expectations. It also gains `executions: { status: 'not_run', runs:
0 }`, beside the unchanged `model_evaluation: not_run`. The command prints one coverage line per skill.

### 4. The case cap

`CASES_MAX` stays 20 live cases per skill (`skillLifecycle.ts`). The golden case plus up to 10 scenarios is 11, so it
fits. The gate fails a skill whose sources exceed 20, which is the golden case plus 19 scenarios. The seed refuses
such a skill (`cases_max`). It also refuses to add cases to a draft when its live cases plus the new ones would pass
20, for example when an admin has added cases of their own.

### 5. What the 9-of-10 bar means now

The bar counts runs, not cases. A draft needs `pass × 10 ≥ total × 9`, where `total` is its live cases times its
required models, and every run must have a result. So a draft may fail at most `floor(total / 10)` runs:

| Live cases | 1 model | 2 models | 3 models | 4 models | 5 models |
| --- | --- | --- | --- | --- | --- |
| 6 | 0 | 1 | 1 | 2 | 3 |
| 7 | 0 | 1 | 2 | 2 | 3 |
| 11 | 1 | 2 | 3 | 4 | 5 |

So with one required model, a skill with 6 to 9 cases must pass every run. That is no stricter than one case on one
model was. But each case it gains is one more run that must pass. From 10 cases on, one failure in ten is allowed.
The rule itself is unchanged.

**Seeding never un-publishes.** The seed adds nothing to a published or retired skill. Cases added to a published
skill another way (HQ's reviewed `PUT /:uid/cases`) do not change it either:

- its `status` stays `published`;
- its live version, the version's release manifest and its pinned agents are untouched;
- only the next publish is held to the new suite, which needs every case evaluated on every required model and a
  review on the new evidence.

### 6. Owner question

The issue asks for one owner choice. Should the seed also add the scenarios to an already-published library skill?

- **A.** No. The seed leaves published and retired skills alone, as it does today. Scenarios reach a published skill
  only through HQ's reviewed `PUT /:uid/cases`. *(Built; my pick.)*
- **B.** Yes. The seed adds missing cases to a published skill too. It stays published (§5), but its current evidence
  changes, so its next publish needs fresh evals and a fresh review.
- **C.** Yes, but only to a published skill that has no open review.

Whether any of the ten skills is published in production is not known here: no production read was made.

### 7. Tests

`skill_case_identity_5336.test.ts` runs on a local sqlite D1 with the real migrations.

- **The identity helper.** Scenario and golden keys; a new revision or id gives a new key. A stored row agrees with
  its source. Every committed golden case keeps its D4532 identity.
- **The generator.** The committed module equals the script's output. The golden case comes first, as committed. Each
  scenario follows, packed the same way by the generator and by the gate.
- **A fresh store.** A golden case and five scenarios seed six live cases, each with its own name and identity. A
  second run changes no row.
- **A store seeded before this change.** The old seed is replayed, then the migration, then the new seed. Every
  earlier row is unchanged, by row hash; this includes `customer-interview-summary`'s golden case. Only the scenarios
  are added. The reconciliation is then all `exact`, and a further run adds nothing.
- **Coverage.** `board-meeting-brief-missing-burn` is followed from its file to the module to its row, with key
  `board-meeting-brief-missing-burn:r1`. Every scenario in `skills/scenarios/` is checked present in the source, the
  module and the store. No two scenarios of one skill share an identity. The store refuses a second live row for one
  identity, and refuses an edit to a row's identity.
- **The gate.** Each new rule fails its own targeted fixture, and the unmutated pack is clean. A golden case claiming a
  scenario's identity fails, in the gate and in the reconciliation. A scenario edited without a rebuild makes the
  generated module stale. Golden plus 10 passes and golden plus 20 fails, and the seed refuses both over-cap cases.
- **The summary.** Coverage for each scenario skill; `executions` and `model_evaluation` are `not_run`.
- **Reconciliation with multi-case sources.** `exact`. `case_drift` for a removed scenario: the seed re-adds it and
  the removed row stays as it was. `case_drift` for a changed revision: the seed adds it beside the old one and
  changes no row. `case_drift` for a revision bumped over the same text, which is identity, not content alone.
  `missing_case`. A published skill gains nothing and stays published.

The existing suites were updated where the shape changed:

- `skill_library_seed_d4225` and `skill_library_ci_4532` load the new migration. The #4532 manifest check no longer
  assumes one case per skill.
- `skill_scenarios_4588` imports `incorrectText` and `assertionItems` from `skillScenarios.ts`, so the suite and the
  gate cannot differ.
- `skill_judge_assertions_4531_s2`'s "version 2 results are unchanged" check now runs over the v1 golden cases only.
  The scenarios use judge version 3's assertions, which that check exists to exclude.

**Mutation checks.** Each was applied, seen failing in this suite, and restored:

- the identity key without its revision;
- a stored row's recorded id ignored;
- the content hash's key order changed;
- the seed's skip rule made always-add, and made the old by-name rule;
- both cap checks removed;
- each scenario rule switched off in turn;
- `case_identity_duplicate` switched off;
- the scenarios left out of the gate's packing;
- the reconciliation's presence check by content only;
- the reconciliation's duplicate-identity check switched off;
- the generator without the scenarios.
