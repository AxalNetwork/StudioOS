### 1. The four mentor routes are `requireAdmin`, and the writes take the branch gate

`GET /api/advisors/admin/cohort-assignments/assignable`, `GET …/cohort-assignments`, `POST …/cohort-assignments` and `DELETE …/cohort-assignments/:id`. The same router answers `/api/mentors/…`.

- **Each calls `requireAdmin`** in place of `requireAuth` plus `isAdmin`. `requireAdmin` compares the role exactly, and it already guards every other admin route.
- **The two reads stay open to a frozen admin.** The freeze never gates a read.
- **POST and DELETE then call `requireBranchNotSuspended`,** as the Lab's decide route does.
- **Refusals,** through `mapError`:
  - a frozen admin's write answers 423 `admin_frozen`;
  - a write on a suspended branch answers 423 `branch_suspended`;
  - a non-admin keeps its 403, `{ detail: 'Admin required' }`.
- **The guard test.** `routes/advisors.ts` joins `branch_suspended_freeze.test.ts`'s file list, so each gate is checked to sit after its admin gate.
- **The new history read** (§3) is `requireAdmin` too.

### 2. Each holder's account state

One rule: an account is active when `users.is_active` is 1, which is what `getCurrentUser` lets through on every request. A deactivated holder was counted, offered and accepted, and could read nothing (map F1).

- **The picker** (`…/assignable`) leaves out deactivated accounts.
- **The list** carries `advisor_is_active` on each row. It is null when the user row is gone.
- **The POST** refuses a deactivated account with 400 `account_inactive`, by the picker's rule.
- **Part 1** (#2787) is not on main, so its catalogue's Mentor block takes this rule when it lands.

### 3. A grant and end history (migration 565)

`advisor_cohort_assignment_events` has one row per grant (`assigned`) or end (`ended`). Its columns are `assignment_id`, `advisor_user_id`, `cohort_cycle_id`, `kind`, `admin_user_id` (NULL when not recorded), `note` and `created_at`. It is indexed on `(assignment_id, created_at)` and `(cohort_cycle_id, created_at)`. Nothing updates or deletes a row.

- **Writes.**
  - The POST writes an `assigned` row when it opens access, and the DELETE writes an `ended` row.
  - Each history row is written in the same batch as the change, and only when that change happened.
- **A re-post of an open pair** answers 409 `already_assigned` and writes nothing: no note change, no history row and no notice.
  - The upsert now updates only an ended row.
  - Before, the re-post started a new episode. Founders got a fresh "can see you", then an "access has ended" that was not true (map M-W1).
- **A DELETE on an ended row** answers 409 `already_ended` and changes nothing. Before, it moved the end date to now (map M-W2).
- **The read:** `GET /api/advisors/admin/cohort-assignments/history`.
  - Filters: `assignment_id` and `cohort_cycle_id`. `limit` is 1–200, default 50; there is also `offset`.
  - Answers `{ items, total, limit, offset }`, newest first.
  - Each item carries `kind`, `created_at`, `assignment_id`, `advisor_user_id`, `cohort_cycle_id` and `by_admin`.
  - `by_admin` says whether an admin was recorded. No read returns the admin's name or id (map Part B §4.1).
  - The client is `api.adminAdvisorCohortHistory(params)`.
- **The backfill.**
  - One `assigned` row per assignment, from `assigned_at` and `assigned_by_admin_id`.
  - One `ended` row per `unassigned_at`, with no admin: 206 never stored who ended one.
  - One `assigned` row, with no admin, for each earlier episode a re-assign overwrote that survives as a `started` notice's `episode_at` (map F5).
- **What cannot be recovered.** An overwritten episode in which no founder was told is stored nowhere. Neither is the end of any overwritten episode. Neither is invented.
- **Dev databases.** `ensureAdvisorStoresSchema` creates the same table and indexes, and `advisor_stores_bootstrap.test.ts` checks it matches 565. The backfill stays in the migration; the bootstrap runs on every request.

### 4. The audit rows

The POST and the DELETE call `logAdminAction` with `advisor_cohort.assigned` and `advisor_cohort.ended`. The details are `target_user_id` (the advisor), `assignment_id` and `cohort_cycle_id`. A refused write logs nothing. Part 1's activity read adds the two names to Mentor's list when it lands.

### 5. Hidden-founder counts

- **`founders_hidden`, on each list row.** These are founders with an opt-out in force against that advisor (367, `withdrawn_at IS NULL`). They must be in that row's cycle as the mentor's own reads count them (`company_week_status`). An ended row keeps its count.
- **`founders_hidden_total`, for PG4's tile.** These are distinct founders hidden from at least one active holder: an open row whose advisor has the advisor role and an active account. A founder hidden from two mentors counts once.
- **Counts only:** no founder is named.
- **Unreadable is null.** When the opt-outs or the membership cannot be read, both are null, never 0, and the list still answers.

### 7. The Lab's two reads answer a failure truthfully (map N1, N2)

- **`GET /api/admin/spinout-applications`.**
  - A failure answers 503 `lab_applications_unreadable` through `refuse`. Before, every error answered `{ applications: [] }`, which reads as nobody applying.
  - It also answers `counts` by status, all-time and uncapped, as `GET /api/admin/lab-hosts` does. The list stays at 200.
- **`GET /api/admin/spinout-participants`.**
  - A failure of its list answers 503 `lab_participants_unreadable`.
  - Its two inner reads say so instead of reading as none, with `milestones_unreadable: true` and `applications_unreadable: true`.
  - When the milestones are unread, a participant who is not active gets `status: null` and `milestones: null`. Graduated and admitted differ only by a milestone, and a failed read had turned graduates into "admitted".
  - It answers `truncated: true` when its 400-row limit comes back full. That limit counts user-and-project rows before the de-dup, so a full page means some participants may be missing.
- **The Lab console** already shows Unreadable when a request throws (`AdminSpinoutLab.jsx`). The console is #2374's.

### 9. Refusal codes

The new refusals go through `refuse`, which puts the code in the body's `error` field, beside `message`:
- `account_inactive` (400);
- `already_assigned` (409);
- `already_ended` (409);
- `lab_applications_unreadable` (503);
- `lab_participants_unreadable` (503).

The two auth refusals keep `adminFrozenBody` and `branchSuspendedBody`, which carry `code`. Today's `{ detail }` refusals keep their shape.
