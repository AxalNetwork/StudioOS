## D4860 — HQ › Platform v2: one health state, a ranked attention queue, and freshness on every block (#4860)

- **Status:** canvas landed 2026-11-07 (`design/incoming/Platform v2 Page.dc.html`, `design/incoming/Platform v2 · Boards.dc.html`, boards PL01 to PL12). Not built. The build is a separate task.

- **Migration:** none expected.

### The question

`/admin/platform` is technically honest ("unknown is not zero"), but important status is buried in long explanatory sections. The operator cannot tell in seconds whether the platform is healthy, what is broken, what needs attention and where to fix it.

### What the canvas decides

**One overall health state:** Healthy · Degraded · Unknown · Critical. It is not derived from cron alone; unknown or unavailable telemetry lowers confidence and says why in one line under the state.

**Needs attention** is a severity-ranked queue (Critical, High, Medium, Low, Info). Each item has a description, state, how long, last observed and one remediation action. When nothing readable is wrong but signals are Unknown, it says so instead of showing an all-clear.

**Four compact core-system blocks** (Infrastructure, Payments, AI, Integrations). Each shows status, a key metric, a few key/value rows, freshness (observed time with fresh, stale or unknown) and a console link.

**Fixed status vocabulary:** Healthy, Degraded, Critical, Unknown, Disabled, Not configured, Stale, Partial, Available. It is always a symbol plus words. Switches are named by business meaning ("Session charging: Disabled — no member is charged per session"), never "X off: off".

**Webhook health** has eight fields: health, last delivery, last success, last failure, consecutive failures, silence threshold, expected activity and endpoint. Zero deliveries against expected activity reads as Stale.

**Incidents:** detected incidents and published status incidents are separate. "0 published" is worded as manual-only, never a green KPI.

**Integration keys** show metadata only (requirement, configured, rotated, expiry, last good and failed use, verification freshness, rotation due), never secret material.

**Broadcast** distinguishes Verified recently from merely Configured.

**Flags and switches** split into Active overrides, Deployment configuration and Runtime safety systems, each row with scope, current user impact and last changed.

**Navigation:** consoles grouped by domain. Features that do not do what they advertise (Event syndication: "Not built yet: nothing posts") sit in Preview / Planned.

**Palette:** emerald and neutral system palette with ink primary buttons, and a strong dark mode. **Eadwyn** stays collapsed unless asked, pinned, or carrying an actionable insight (PL12).

### Data

- Integrations, scheduled jobs (`triggerState`, `STALE_GRACE_MINUTES`), monitoring, broadcast and switches come from `GET /api/admin/platform/summary` and `/switches`. Capacity comes from `/capacity` (D4559). Topology comes from `/topology`.
- The overall health rule is new logic over those reads. Proposal: Critical if a user-facing capability is failing; Degraded if any block errors or telemetry is unavailable; Unknown if core blocks cannot be read; Healthy only when every core block was read within its freshness threshold.
- Webhook "expected activity" needs a baseline (drawn as ≥ 1/day from the 30-day checkout volume); confirm the source.

### What the canvas does not decide

The sample content follows the live-state examples in the brief. Which 4 providers are connected, which 5 keys are unset, and the broadcast counts are assumptions to confirm.
