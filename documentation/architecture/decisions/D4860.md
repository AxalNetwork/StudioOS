## D4860 — HQ › Platform v2: one health state, a ranked attention queue, and freshness on every block (#4860)

- **Status:** canvas landed 2026-11-07 (`design/incoming/Platform v2 Page.dc.html`, `design/incoming/Platform v2 · Boards.dc.html`, boards PL01 to PL12). Not built. The build is a separate task.
- **Builds on:** D203 (switches), D209 (topology), D1170 (storage), D4559 (capacity); `admin_platform.ts`'s per-block states.
- **Migration:** none expected.

### The question

`/admin/platform` is technically honest ("unknown is not zero"), but important status is buried in long explanatory sections. The operator cannot tell in seconds whether the platform is healthy, what is broken, what needs attention and where to fix it.

### What the canvas decides

**One overall health state:** Healthy · Degraded · Unknown · Critical. It is not derived from cron alone; unknown or unavailable telemetry lowers confidence and says why in one line under the state.

**Needs attention** is a severity-ranked queue (Critical, High, Medium, Low, Info). Each item has a description, state, how long, last observed and one remediation action. When nothing readable is wrong but signals are Unknown, it says so instead of showing an all-clear.

**Four compact core-system blocks** (Infrastructure, Payments, AI, Integrations). Each shows status, a key metric, a few key/value rows, freshness (observed time with fresh, stale or unknown) and a console link.

**Fixed status vocabulary:** Healthy, Degraded, Critical, Unknown, Disabled, Not configured, Stale, Partial, Available. It is always a symbol plus words. Switches are named by business meaning ("Session charging: Disabled — no member is charged per session"), never "X off: off".

**Webhook health** has eight fields: health, last delivery, last success, last failure, consecutive failures, silence threshold, expected activity and endpoint. Zero deliveries against expected activity reads as Stale.

**Incidents:** detected incidents and published status incidents are separate. "0 published" is worded as manual-only, never a green KPI.

**Integration keys** show metadata only (requirement, configured, rotated, expiry, last good and failed use, verification freshness, rotation due), never secret material.

**Broadcast** distinguishes Verified recently from merely Configured.

**Flags and switches** split into Active overrides, Deployment configuration and Runtime safety systems, each row with scope, current user impact and last changed.

**Navigation:** consoles grouped by domain. Features that do not do what they advertise (Event syndication: "Not built yet: nothing posts") sit in Preview / Planned.

**Palette:** emerald and neutral system palette with ink primary buttons, and a strong dark mode. **Eadwyn** stays collapsed unless asked, pinned, or carrying an actionable insight (PL12).

### Data

- Integrations, scheduled jobs (`triggerState`, `STALE_GRACE_MINUTES`), monitoring, broadcast and switches come from `GET /api/admin/platform/summary` and `/switches`. Capacity comes from `/capacity` (D4559). Topology comes from `/topology`.
- The overall health rule is new logic over those reads. Proposal: Critical if a user-facing capability is failing; Degraded if any block errors or telemetry is unavailable; Unknown if core blocks cannot be read; Healthy only when every core block was read within its freshness threshold.
- Webhook "expected activity" needs a baseline (drawn as ≥ 1/day from the 30-day checkout volume); confirm the source.

### What the canvas does not decide

The sample content follows the live-state examples in the brief. Which 4 providers are connected, which 5 keys are unset, and the broadcast counts are assumptions to confirm.

**Health rule, as built.** Each read becomes a signal (`signals`). The core signals are telemetry (traffic by branch, the Analytics Engine read), scheduled jobs, dead letters, integrations and the Stripe webhook.
- **Critical** when a known capability is failing: a branch that does not answer or whose database fails, a webhook refused `WEBHOOK_CRITICAL_RUN` (3) times in a row with no success since, a dead-letter backlog of `DLQ_CRITICAL` (100) or more, or the AI budget tripped.
- **Unknown** when the summary cannot be read, or when both scheduled jobs and the dead-letter queue cannot be read.
- **Degraded** when anything else is wrong, or when a core signal is unknown. An unread signal lowers confidence and is named in the line under the state. It never counts as zero.
- **Healthy** only when every core signal was read on this visit and is healthy.
- Configuration items (an unset recommended key, an unbound channel, X not provisioned, a partly inactive catalogue, the ticket mirror off) appear in Needs attention as Low or Info. On their own they never lower health.

**Needs attention** ranks Critical, High, Medium, Low and Info, keeping read order within a severity. Each item has a severity, description, state, "since" where a stored stamp gives one, when it was observed, and one link to its console. On a phone, Low and Info items are collapsed under "N more · Low and Info" (PL-08 A). When the queue is empty but some signals are Unknown, it says this is not an all-clear and names those signals (PL-02 C).

**Webhook health** (finding 5). `services/stripeWebhookDeliveries.ts` now also returns `last_success`, `last_failure` and `consecutive_failures`: the failures after the newest 2xx, counted up to `CONSECUTIVE_FAILURE_CAP` (1000), with `consecutive_failures_capped` set when the count reaches the cap. A delivery with no recorded status counts as neither a success nor a failure. The webhook's states:
- **Healthy** only when the newest delivery was 2xx and came within the 24 h silence threshold.
- **Stale** when no delivery came within the window. "0 not 2xx" never makes it healthy.
- **Unknown** when no delivery was ever recorded.
- **Degraded** when the newest delivery failed.
- **Critical** on a run of 3 or more failures.

### Emergency control plane (needs the owner's call, question A)

The one operator kill switch is Eadwyn's (`eadwyn_off`), and it lives in D1 (`platform_switches`, migration 283). During a D1 incident:
- A **read** keeps the last good reading per isolate. With none, it fails **open**, so Eadwyn keeps answering.
- A **throw** cannot be written.
- The break-glass is the deploy var `ADVISOR_DISABLED`. It is read first, with no database, but changing it needs a deploy.

So the switch is not available in the failure domain it would most likely be thrown in.

- **A. Keep D1, and document it.** This is the status quo, plus this note and a line on Switches saying a D1 incident needs the deploy var.
- **B. Mirror operator switches into the KV namespace that is already bound.** On a throw, write KV first and D1 second, for the audit trail. The gate reads KV before D1. No new binding is needed and `wrangler.toml` is untouched. The cost is KV's eventual consistency, up to about 60 s across locations, which is about the existing per-isolate TTL.
- **C. A dedicated control-plane binding.** A new KV namespace or Durable Object, scoped to emergency switches only. It needs a `wrangler.toml` change and an owner-created resource.

**Pick: B.** It removes the D1 dependency from both the throw and the read, at no new infrastructure, and D1 keeps the audit row. This PR builds none of the three. It is `Part of #4860`, and the issue stays open for this call.

### Key lifecycle

The platform records, per managed key, where it lives (Worker secret, database, unset or unknown) and when the console last saved it (`last_set_at` with its basis). That is all the overview shows. Last rotated beyond that save, expiry, last successful and failed use, verification freshness and rotation due are **not recorded** anywhere, so the overview draws none of them and never reads a key's value. Warning before a provider expiry needs a store for the provider-reported expiry. That waits on the owner (question D).

### Built (part 3), 2026-11-09: the KV mirror of the operator switches (question A = B)

Part of #4860. No migration and no new binding: the mirror lives in the `TOKENS` KV namespace, which every deployment already binds. `wrangler.toml` is untouched.

- **`services/emergencySwitches.ts` (new).** One KV key per switch, `operator_switch:<key>`, holding `{ thrown, revision, set_at }`. It holds no reason, actor or figure, because `platform_switches` (migration 283) stays the record and the audit trail.
  - Readings travel as the D1 store's do (D203): one read per switch, held for 30 s per isolate, keyed on the binding. The writing isolate clears its own reading. A failed read keeps the last good reading and is retried after the TTL, never latched.
  - KV itself is eventually consistent, so other locations follow within about a minute.
  - A deployment with no `TOKENS` binding has no mirror and behaves exactly as before.
- **A throw writes the mirror first** (`setOperatorSwitch`), then D1 with its audit row in one batch (D4703).
  - If D1 refuses the write, the kill still holds through the mirror. The route answers **202 `thrown_unrecorded`**, with no audit row, and says to throw again once the database answers, which records it and aligns the mirror's revision.
  - On success the mirror is rewritten with the revision D1 recorded, the one a release must name.
- **A release runs on D1 first**, with its audit row, and clears the mirror only once D1 no longer holds the throw.
  - With D1 down nothing is released, so an emergency kill fails safe.
  - If the mirror cannot be cleared, the route answers **202 `release_incomplete`**: Eadwyn stays off, and releasing again clears it.
  - A throw D1 never recorded is released by the revision the page read (0 while no row exists), with its own audit row marked `store: 'emergency'`. If that audit row cannot be written, the clear is undone and the route answers 503.
  - A stale tab still conflicts (D4703).
- **The gate reads the mirror before D1** (`advisorKillState`). A thrown mirror decides with no D1 read at all. The operator half is thrown when either says so, and neither can release the other.
  - An unreadable mirror is not a throw: D1 still decides.
  - A new isolate whose D1 read fails, with a thrown mirror, now refuses. Before, it failed open.
- **The console** (`readOperatorSwitchEntries`) adds an `emergency` half (`bound`, `readable`, `thrown`, `recorded`). It says when the mirror holds a throw the database never recorded, and when the database holds one the mirror does not.

**What this does not cover.** HQ's own throw route still needs D1 to authenticate the operator, so a **full** D1 outage still blocks a throw from the console. The deploy variable `ADVISOR_DISABLED` stays the break-glass for that. What the mirror adds: a kill thrown before or during a partial outage holds at every isolate, a throw lands while D1 refuses writes, and the gate no longer fails open on a thrown switch when D1 cannot be read.

**Tests:** `operator_switches_d203.test.ts` gains 8 D4860 tests, against a KV fake whose reads and writes can fail:

### Built (question D), 2026-11-10: expiry and last use for the managed keys (#5304)

Question D = (b). Migration `202611100933_provider_key_expiry_last_use.sql` adds nullable `expires_at` and `last_used_at` to `provider_oauth_keys`. It is additive, and both columns also sit in the runtime `CREATE TABLE` in `services/providerOauthKeys.ts`. No new binding, and `wrangler.toml` is untouched. Key levels (B = a) and the webhook's Not recorded baseline (C = a) stay as built. Nothing rotates and nothing is sent automatically.

**Which providers report an expiry.** None of the fourteen returns an expiry for the managed key to any call the Worker makes:
- **OAuth clients** (Slack, HubSpot, Salesforce, DocuSign, LinkedIn, Calendly, Carta, GitHub, Vercel, and Stripe Connect's client id). The `client_id`/`client_secret` pair is pasted into the console. The only responses that carry `expires_in` are the token responses from code exchange and refresh. That `expires_in` belongs to the member's access token, which is already kept in `integrations.credentials_enc` (for example HubSpot's `expires_at`), not to Axal's client secret. The console's probes (`services/providerOauthTest.ts`) send an invalid code on purpose and get no token at all.
- **API keys and tokens.** Stripe's secret key (probe: `GET /v1/account`), Crunchbase's user key, Affinity's key (`/auth/whoami`), Telegram's bot token (`getMe`) and Identity Platform's API key (`accounts:sendVerificationCode`). None of these responses carries an expiry for the key itself.
- **What a provider's console shows.** A provider whose dashboard shows an expiry for a key (for example a Stripe key rolled with an expiry) is relayed by the Super Admin, never fetched.

**Expiry.** The Integration keys dialog has an optional **Expires on** date: "Only if the provider's console shows an expiry for this key". `PUT /:provider` and `POST /:provider/rotate` take it as `expires_at` (a date or an ISO date-time). Blank records none, and anything else is refused with 400 `expires_at_invalid` before Cloudflare is called. The audit row carries the date when one was given. A save or rotate deletes the old key's row, so a new key starts with no expiry and no last use. A database-held rotate resets them on its own row (`resetKeyStamps`).

**Where a Worker-secret key's stamps live.** The console promotes every key to Worker secrets and deletes its row, so most keys have no row at all. Their stamps go on a **stamps-only row**, where `client_id` and `client_secret_enc` are both `''`, with no key material. Every reader of a held key now requires `client_secret_enc <> ''`: the status list, the rotate fallback and the "removed keys" count. `loadOauthCreds` already treated an empty pair as unconfigured. So a stamps row never reads as "In the database", and Remove deletes it after the key.

**Last use** (`markProviderKeyUsed`) is stamped after a call that authenticated with the managed key succeeded:
- the OAuth code exchange in `routes/integrations.ts` (`POST /connect` with an `oauth_code`, and the OAuth callback), which covers every registry OAuth provider;
- HubSpot's, Salesforce's and DocuSign's refresh-token exchange, which is the hot path;
- LinkedIn's callback exchange;
- Crunchbase's diligence search.

It is not stamped for GCIP SMS sends, Telegram broadcast, Affinity, the Vercel webhook signature check or the console's own probe. Those read as Not recorded until they are wired.

**The throttle.** The stamp is written at most once an hour per key:
- An isolate that wrote skips the statement for an hour.
- The statement itself is an upsert whose `DO UPDATE … WHERE last_used_at IS NULL OR datetime(last_used_at) <= datetime(now − 1 h)`, so a stamp another isolate wrote within the hour is left alone. An isolate that finds such a stamp asks again in ten minutes.

All binds are bound parameters. The stamp is best effort: it never throws into its caller, and it logs only the provider and the error message, never a key.

**Reads.** `readProviderKeyStatus` reads the two stamps in their own query (`readProviderKeyStamps`). A database without the columns reports `stamps_readable: false`, and every other field stands.
- The console's `GET /api/admin/integration-keys` returns each provider's `expires_at` and `last_used_at`, plus `stamps_readable`.
- HQ › Platform's summary returns both on each key in place. A provider with no key carries neither. It also returns `stamps_available` and `stamps_reason`. No key value is returned or logged.

**The page.**
- **Key rows** (System detail › Integration keys). Each held key draws `Expiry 1 Mar 2027 · in 110 d`, `Expiry 1 Nov 2026 · expired 9 d ago`, or `Expiry Not recorded`, plus `Last used 2026-11-10 11:42` or `Last used Not recorded`. Unread columns read `Unreadable`. A value the platform has not recorded is never a date and never 0 days. Dates follow the canvas's `3 Dec 2026 · in 26 d`.
- **Integrations core block.** It gains a **Key expiry** line: expired, within 30 d, and how many of the keys in place have none recorded.
- **Needs attention.** An expired key is **High** ("Hubspot key expired"), and one within `KEY_EXPIRY_WARN_DAYS` (30) is **Medium**. Each links to Integration keys. Like every key item, they are configuration and never lower health on their own. An unrecorded expiry raises nothing, because unknown is not soon. `Expired` and `Expiring` join the status vocabulary.

**Known limits.**
- A key replaced at deploy (`wrangler secret put`), not from the console, keeps the stamps of the key before it. `stamps_reason` says so.
- Last failed use, verification freshness and rotation due are still not recorded.
