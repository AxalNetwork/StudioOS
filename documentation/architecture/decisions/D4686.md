### The queued push row from #4805 (follow-up)

#4805 queues a `licence_push_pending` row in the same batch as a program-grant change (`queuePushStatement`, reason "queued with the change", picked up at the next tick). A push that then fails before it learns its branch (the licence reread or the deployment lookup) used to overwrite that row with an empty code. It now leaves an existing row as it is, raising only the revision it stands for, and writes its own row only when none exists, so the intent is never lost (`recordPushOutcome` in `services/licencePush.ts`; `program_grant_revisions_d4805.test.ts` 7b).

### What was decided

- **A revision is allocated per push attempt, not per edit.** The ~20 routes that change the copy already call one function, so numbering there keeps every caller correct with no edit. Allocating before the read means a higher revision always carries content read no later than a lower one. A pull numbers its copy the same way.
- **An equal revision is applied again; a lower one never is.** A retry allocates a new revision, so the equal case is a re-delivery of the same message.
- **A branch answering "stale" is not success.** If the branch holds a later revision than HQ's counter (HQ's store restored from a backup), HQ raises its counter to the branch's, so the next attempt is accepted instead of refused for ever. If HQ has already acknowledged that later revision, the late refusal records nothing.
- **A resume can be manual or scheduled.** `POST /:uid/terminate` and the HQ scheduled handler claim the same five-minute lease. Only the holder runs incomplete consequences; neither path writes another terminal event or repeats a completed notification.
- **No pre-D4686 termination needed a synthetic ledger.** The required read-only production query on 2026-11-10 found zero `territory_licences.status = 'terminated'` rows without `licence_termination_ops` (zero rows read or written). The repeat-request backfill branch was therefore not added; a no-ledger terminated licence keeps the conservative 409.
- **Terminate keeps its inline guarded batch instead of calling `transition()`.** The terminal move must atomically include territory release, the single terminal event, sync revision, pending push and termination ledger. `transition()` deliberately owns only the status compare-and-swap and queued push for ordinary moves; routing termination through it would either split this larger invariant or give the generic helper termination-only knowledge.
- **A holder of the Super Admin elevation does not hold the operation open.** HQ deprovisioning skips them with a reason (D145); that is a manual act, so the step is `done` with the skip in the response.
- **Failure codes, not error text, are stored and shown.** The ledger and the pending row keep short codes; the licence page maps them to sentences.

### What changes for branches

A branch deployment on an older build ignores the extra `hq_revision` key and answers `{ applied: true }`; HQ then records that revision as acknowledged, so "branch revision" is HQ's belief for such a branch, not the branch's own statement. A branch on the new build must have applied the migration (`branch_licence.hq_revision`, `copy_state`, `copy_failed_sections`); until it has, a numbered push throws on the branch, HQ records it pending, and the hourly retry delivers it after the migration. The answer shapes `stale` and `partial` are new and only sent in response to a numbered push.

### Follow-up completed by D5361 (#5361)

- The scheduled handler resumes incomplete termination ledgers past their lease, using the same claim as a person.
- Each administrator demotion batch writes a `licence_termination_reseeds` row before deleting the binding. A failed strict re-seed stays failed and is retried by either resume path; a completed row is never repeated.
- `starts_on`, `renews_on` and the other edits are not versioned separately; the revision orders pushes, it is not a history of edits.
