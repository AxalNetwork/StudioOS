## D8605 — The Network-to-Research bridge holds plain Research uids, and fund re-imports carry its links (#8605)

**Context.** Migration `202611191414_7672_network_directory.sql` (D7672, PR #7687) declared
`network_directory_research_links.company_directory_uid` as `REFERENCES research_company_directory(uid)` and
`.fund_directory_uid` as `REFERENCES research_fund_directory(uid)`. A fund list is re-imported by deleting that list's
rows and inserting them again (`scripts/import-research-funds.py`; migrations `429_research_fund_directory_shai_list.sql`
and `202611180052_7166_research_fund_directory_vehicles.sql`), and D1 enforces foreign keys statement by statement
(D1096, D6115). So the first reviewed link to a fund would have made the next re-import of its list fail at the deploy's
migration step, and a uid move (`10d` to `10d-i` in D7166) would have left a link on a uid that no longer exists. The
table was empty and nothing on main wrote to it when this landed.

**Decision.**

- **Plain references** (migration `202611251148_8605_network_research_links_soft_refs.sql`). The table is rebuilt with
  both Research uids as plain `TEXT`, the way the other references to catalogue uids are kept
  (`research_funds.catalogue_uid`, `raise_prospects.research_fund_uid`, `research_project_subjects.directory_uid`).
  Everything else is as D7672 declared it: the foreign keys to `network_directory_entries`,
  `network_directory_source_records` and `users`, the exactly-one-target and target-kind CHECKs, and both partial
  unique indexes under their names. The rebuild follows GOTCHAS (`PRAGMA defer_foreign_keys`, the table recreated
  under its own name, every row copied back) and replays to the same rows. D7672's "exactly one existing Research row"
  becomes "exactly one Research uid": existence is the importer's and the reader's to check, not the database's.
- **`needs_review`.** The status CHECK adds `needs_review` beside `reviewed` and `withdrawn`. Only `reviewed` is a link
  to any reader (#7824, #7847 and every later one). A link whose uid moved or whose record left the catalogue is
  `needs_review` until a reviewer confirms it or withdraws it.
- **Fund re-imports** (`bridge_statements` in `scripts/import-research-funds.py`). After a list's rows are re-inserted
  and the saved references have moved:
  - with moves (the EuroTech writer): a link whose fund uid is gone and has a recorded move is carried to the new uid
    and set to `needs_review`, never re-pointed silently, because a move can turn a manager key into a vehicle row. It
    is carried only when the new uid is listed, holds no link yet, and no other link on a gone uid moves onto it, so
    the unique index never fails the migration; a link that cannot be carried stays on its old uid. A withdrawn link
    stays withdrawn.
  - every list: a `reviewed` link whose fund is not in the catalogue is set to `needs_review`.
  Both statements are correct on an empty bridge and on a replay. `eurotech_vehicle_migration(..., bridge=False)`
  reproduces the applied 7166 file, which was written before the bridge existed.
- **The importer names only files that run after this one.** The statements need this table's shape, so a file
  carrying them must sort after `202611251148_8605`. `shai-migration` took a three- or four-digit number, and a
  numbered file sorts before every stamped one, so it would have run before the bridge existed and broken every fresh
  schema build. Both `shai-migration` and `eurotech-migration` now take a D4106 stem stamped after
  `BRIDGE_READY_STAMP` (`is_bridge_ready_stem`) and write `<stem>.sql`; a number, or a stem at or before that minute,
  is refused. `shai_directory` builds the third list's directory for the command and the tests alike.
- **Company side.** Nothing on main deletes or moves a company record. Any later migration or route that does sets
  the bridge row to `needs_review` the same way (#7825 item 10 asks the same of uid-moving migrations).

**Not here.** Any writer of bridge rows (#7681 is the first planned one, and waits for this), any reader, any review
screen. The 7672 test still recreates the bridge from its own migration file, so it pins that applied file's shape.

**Tests.** `cloudflare-worker/test/network_research_links_8605.test.mjs` on the fresh schema with foreign keys on:
- the same re-import fails with `FOREIGN KEY` on the 7672 shape and succeeds on this one, and a deleted company leaves
  its link;
- the rebuild copies every row and column of a populated 7672 table back and replays to the same rows;
- every other rule still refuses what it refused;
- the rebuilt table's SQL is the 7672 table's with exactly the two references removed and `needs_review` added;
- the importer's own statements (read from the script) carry a moved link for review, leave on its old uid for review
  a link whose target is taken, shared by a twin or not listed, carry a gone link that shares a target only with a
  still-listed one, keep a withdrawn link withdrawn, mark a link to a dropped fund, touch no company link, and change
  nothing on a replay or on an empty bridge;
- both writers' real output (EuroTech and the third list), applied to the fresh schema with foreign keys on, carries a
  moved EuroTech link for review, marks a link to a dropped row of either list, keeps a link to a listed row, and
  replays to the same rows; the command refuses a number or an early stem and names its files after this migration.

`scripts/test_import_research_funds.py` (not run by CI; the Worker test above covers the same paths in CI) pins that a
new EuroTech import adds exactly the two header lines and the two statements after the saved references, that the
third list's import marks a link to a row it removed, and the command's stems.
