## D5048 — Package and program agreements get their own canonical store, beside the master licence agreement (#5048)

- **Status:** built by S23, 2026-11-08 (#5048, part 1 of #5047). PR: see the issue.
- **Number:** D5048 is this issue's number (D4106). Migration: `202611082025_licence_program_agreements.sql`.
- **Files:** the migration; `cloudflare-worker/src/services/programAgreements.ts`;
  `cloudflare-worker/src/routes/admin_licence_agreements.ts` (reads, `/api/admin/licence-agreements`);
  the schedule's send, terms change and completion in `routes/admin_program_grants.ts` and
  `services/programSchedule.ts`; `cloudflare-worker/test/licence_program_agreements_d5048.test.ts`.

### 1. Why not `licence_contracts`

`licence_contracts` is the territory licence's master agreement, and since D4671 it holds exactly one current
row per licence (`idx_licence_contracts_one_current`). A program schedule or a package agreement written there
would supersede the master agreement, which is why D1120 never wrote schedules there. So the agreements this
epic adds have their own table, `licence_program_agreements`, and nothing that writes it touches
`licence_contracts` (test 4 counts its rows).

### 2. `licence_uid` holds the territory licence's uid until #5057

#5047's combined order puts #5057 (a shared licence identity for operator and user licence families) before
this issue. On the owner's request this issue was built first, so `licence_uid` holds `territory_licences.uid`.
It is a plain column with **no foreign key**, so #5057 can repoint it at the shared identity's uid with one
`UPDATE` (or a mapping), with no table rebuild. The read route says so in its answer
(`licence_identity: 'territory_licence'`). User licences (Founder, Investor, Operating Partner, Advisor) get
agreements here once #5057 gives them a uid; nothing in the table is territory-specific.

### 3. One slot, one version in flight, one executed version

- **The slot** is what an agreement is for on its licence, derived from the kind and its scope and held to that
  by a CHECK (`slotKeyOf` mirrors it): `program_licence:<program>`, `program_schedule:<program>`,
  `program_addendum:<program>:<addendum>`, `package_master`, `package_addendum:<addendum>`. Program kinds need a
  `program_key`; package kinds need a `package_key`; addendum kinds need an `addendum_key`. Package scope adds
  `package_offer_uid` and `package_version`, free columns until #5021's package store exists.
- **Two partial unique indexes**, not one: at most one version **in flight** (draft, ready, sent, partially
  signed) and at most one **executed** version per slot. So an amendment can be drafted and sent while the signed
  version stays in force; the executed version is superseded only in the batch that executes its replacement
  (`agreementSignedStatements`). Superseded and voided versions are history; any number of them coexist.
- **One envelope is one version** (a unique index on `envelope_uuid`).

### 4. Frozen at the database, revision-safe, audited

- A trigger refuses, on any update: changing the template, its version, the body hash or the package version
  once the version left draft/ready; changing a linked envelope; changing a recorded signature time or signed
  document hash; moving a version to another licence, slot or scope; reopening a superseded or voided version;
  moving an executed version anywhere but superseded; moving a sent version back to draft; and any update that
  does not move `revision` by exactly one. A second trigger refuses every delete.
- A person's status change names the revision and status it read (`transitionStatements`), runs through
  `runDecision` with the D4805 guard, and loses whole when stale. A person cannot mark a version executed: only a
  signature does.
- `licence_agreement_events` is append-only (two triggers, as migration 269 seals `licence_events`): one line per
  write, in the write's own batch, naming the status left, the status reached and the revision made.

### 5. The schedule backfill, and `schedule_contract_uid`

- Every schedule envelope already sent gets one canonical version (`origin = 'backfill_d5048'`): each
  `program_grant_schedules` row (D4805), plus any `program_grants.schedule_contract_uid` that table does not
  name. Status comes from the envelope and the schedule row: signed → executed, or superseded when a newer
  revision replaced it; envelope void/rejected → voided; otherwise sent/partially signed, or superseded when
  replaced. Only the newest row per grant of each kind stays current, so both indexes hold. The body hash is the
  envelope's (never invented when the envelope row is missing); the signed document hash is the newest signed
  copy in `legal_document_files`. Each insert skips an envelope already on file, so the file applies twice
  (test 1).
- **`program_grants.schedule_contract_uid` is kept unchanged** as the read-through: the grant routes, the branch
  copy and the completion hook still read it. From now on the schedule send, a terms change or re-grant, and the
  completion hook also write the canonical version **in the same batches** they write the grant, so the two never
  disagree. A later issue moves the callers and can then retire the column.

### 6. The five states

`programLegalState` reads, for each grant: the grant exists (granted or paused), an agreement is required (the
signed-schedule rule), one was sent, one was executed, and the program is legally in force (the grant in force by
`presentGrant` **and** an executed agreement when one is required). `program_grants.state` holds only the first.
`GET /api/admin/licence-agreements/licences/:uid` answers all five per program, beside every version and each
slot's executed and in-flight version. Surfacing them in Licences and Program access is #5051.
