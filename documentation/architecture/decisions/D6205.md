## D6205 — Positions: an investor asks HQ for a mark, a correction or a follow-on round (#6205)

- **Status:** part 1 built 2026-11-14: the store, the Worker route and the investor's side. The admin position sheet's open requests wait on open PR #5854 (PF-07), which rewrites `PortfolioPositionsPage.jsx`.
- **Builds on:** D4817 (Portfolio v2; "a request-a-mark flow" is listed there as backend required), D1057 / D4636 (who holds a company), `positions.ts`'s admin-only mark write.

### The problem

Marks are an HQ admin write (`POST /api/positions/:projectUid/marks`). An investor who saw a stale, missing or wrong mark had no action. The Positions toolbar drew `Add follow-on`, which records a round (an admin write too), so on the investor's book it could never be enabled.

### What is built

**Store.** Migration `202611141523_6205_portfolio_mark_requests.sql`, table `portfolio_mark_requests`:
- company, requester and reason;
- `kind`: `mark`, `correction` or `follow_on`;
- `state`: `open`, `resolved` or `declined`;
- `resolved_by`, `resolved_at`, `resolved_mark_uid` and `resolution_note`.

A partial unique index holds the one-open-request-per-company-per-investor rule, so two submits at once keep one. CHECKs keep an open request free of an answer, and let only a resolved one link a mark.

**Worker.** `routes/mark_requests.ts`, mounted at `/api/mark-requests` through the route registry.

| Method | Who | Rule |
| --- | --- | --- |
| `POST /` | an investor, not an admin | The company must be held through a confirmed commitment (`investorHeldProjectIds`, the Positions read's held scope). Not held and not found answer alike (403 `not_held`), so a request does not confirm that a company exists. A second open request is 409 `request_open`, with the open one. Every active admin gets an in-app notice (`portfolio_mark_requested`). |
| `GET /` | an investor's own requests; an admin reads all, with who asked | Optional `?state=`. No licence: 403. |
| `PATCH /:uid` | admin | `resolved` links the mark recorded, which must be a mark of the same company. A follow-on, or a decline, takes a note instead. An answered request is not reopened (409). The investor is notified (`portfolio_mark_request_answered`). |

A request never writes a mark. Recording one stays the admin write it was.

**Investor page.** On `InvestorPortfolioPositions.jsx`, there are two entry points:
- **Ask HQ** in the mark-history Sheet (`MarkRequestPanel.jsx`);
- **Request…** beside a Stale chip, or beside a mark that is missing or unusable. It opens the Sheet on the form.

The form names the company, takes what is asked for and a reason, and sends. Afterwards the panel and the register read the request's state:
- **Requested · date**: no second request is offered.
- **Resolved · date** or **Declined · date**, with HQ's note. A new request may follow.

The requests are a read of their own. While it is unreadable, the panel offers Retry and no form, and the register shows no chip. Whether a request is already open is unknown then, so the page never reads that as "none sent". A refusal is read by its `code` (`markRequestModel.js`); a Worker `detail` never reaches the page.

**Toolbar.** `Add follow-on` is gone from `investorZoneActions('portfolio/positions')`. The investor's follow-on act is a `follow_on` request.

### Departures from the canvas, recorded

- **Placement of Request.** The Portfolio v2 canvas draws "Request…" once, inside a list item tagged "request flow: backend required". It draws it on neither the Positions register nor the mark-history Sheet, and no board draws the admin side. This build places Request in the Sheet and beside the register's Stale chip. That is a departure from the canvas, to confirm when the canvas is redrawn.
- **`Add follow-on` withheld.** The investor Portfolio artboard (`Pages · Investor Portfolio`) still lists `Export · Mark history · Add follow-on`. `profile_zone_actions.test.mjs` now carries `withheld: { 'portfolio/positions': ['Add follow-on'] }`: an artboard op the table deliberately does not carry. The test fails if the canvas drops it, or if the table brings it back.

### Not built here

- **The admin side.** The admin position sheet showing a company's open requests, with Resolve (pick the mark just recorded) and Decline. `PortfolioPositionsPage.jsx` is rewritten by open PR #5854 (PF-07), so this follows it; the issue stays open (`Part of #6205`). Until then HQ is told in-app and answers through `PATCH /api/mark-requests/:uid`.
