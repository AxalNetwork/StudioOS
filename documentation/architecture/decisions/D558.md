## D558 — Learning programs: regional cohorts, assigned admins, enrolment and a read-only learner view (migration 389)

**A program gathers Learning content for a region or cohort. The Super Admin
builds it, assigns admins to follow it, and enrols members. Enrolled members
can open its `program` content, and its assigned admins can read their
learners' progress without changing anything.** Slot S07, issue #1159,
2026-10-06, on #1158's tables (D557) and #1160's (D559). The canvas is
`design/incoming/Learning.dc.html` (D566); Session 1 builds the screens (#1163).

### Migration 389

| Table | What it holds |
| --- | --- |
| `learning_programs` | `uid`, `name`, `region` (free text, such as "Nordics" or a branch code), `description`, `enrolment` (`invite` or `open`, default `invite`), `status` (`draft`, `published` or `archived`, default `draft`), `created_by` and timestamps. |
| `learning_program_contents` | The program's ordered list: `subject_kind` (`course`, `item`, `exam`, `exercise` or `webinar`), `subject_uid`, `position`. Unique on (`program_id`, `subject_kind`, `subject_uid`). |
| `learning_program_admins` | `program_id`, `user_id`, `assigned_by`, `assigned_at`. Unique. |
| `learning_enrollments` | `program_id`, `user_id`, `enrolled_by`, `enrolled_at`, `status` (`active` or `removed`). Unique. |

Every closed set is a CHECK.

**Unenrolling marks the row `removed` and keeps it.** Who was enrolled, by
whom and when stays on file. `enrolled_by` is the member's own id on a
self-enrolment.

**A webinar is reserved, not yet accepted.** The column allows it for D560
(#1161). There is no webinar store to check a uid against yet, so the
contents route refuses one with `webinar_not_built` rather than store it
unchecked.

### Who sees program content: `canSeeLearning`

D557 kept `program` content for the Super Admin. It now opens to a member
**actively enrolled in a published program that holds it**. A program holds a
subject in one of two ways:
- directly, as a row in its contents;
- through a course it holds, as the target of one of that course's lessons.
  So a program that holds a course opens the readings, videos, exercises and
  exams the course's lessons point at.

It stays one synchronous check. Every member read selects
`enrolledSql(kind, uid)` as `enrolled` beside the row, and `canSeeLearning`
reads that column:
- the catalog, in both its rows and its totals;
- a course, an item, and a progress write;
- an exercise and an exam (D559's routes).

A draft or archived program opens nothing. A removed member loses access on
the next read.

### Routes

**Super Admin** (`routes/admin_learning_programs.ts`, at `/api/admin/learning`).
Every write is recorded with `logAdminAction` as `learning.program.*`:
- `GET` and `POST /programs`; `GET` and `PATCH /programs/:uid` (name, region,
  description, enrolment, status).
- `PUT /programs/:uid/contents`: the full ordered list. Each subject must
  exist, and none may appear twice.
- `POST /programs/:uid/admins` and `DELETE …/admins/:userUid`. The target must
  be an admin.
- `POST /programs/:uid/enrollments` and `DELETE …/enrollments/:userUid`.

**Members** (`routes/learning_programs.ts`, at `/api/learning`):
- `GET /programs`: published programs open to self-enrolment, and whether the
  caller is in each.
- `GET /programs/enrolled`: the caller's own programs, each with its `contents` and `my_completion` (addendum below).
- `POST /programs/:uid/enrol`: self-enrolment, only into a published open
  program. An invite-only program answers 403 `invite_only`. A member the
  Super Admin removed answers 403 `removed` and cannot enrol themselves back.
- `GET /programs/:uid`: the program and its contents, with the caller's own
  completion when enrolled. A program the caller is not in, not assigned to
  and cannot enrol into is 404.

**Assigned admins, read-only** (same file):
- `GET /programs/mine`: the programs assigned to the caller. The Super Admin
  sees every program; a member gets 403.
- `GET /programs/:uid/learners` and `GET …/learners/:userUid`: each enrolled
  learner's completion of each content item. An admin not assigned to the
  program gets 403.

D559's review routes (`/review/exercises/:uid/submissions` and
`/review/exams/:uid/attempts`) now admit an assigned admin too. They show work
only by learners actively enrolled in a program that holds the subject.

### What a learner's completion says

| Content | Read from | Says |
| --- | --- | --- |
| Course | `learning_progress` (the course's required lessons, and the course row) | `completed`, `in_progress` or `not_started`; `completed` of `required` lessons, and a percent (null when the course has no required lesson). |
| Item | `learning_progress` | `completed`, `in_progress` or `not_started`, and the percent. |
| Exercise | the latest submission (D559) | `accepted`, `needs_work`, `submitted` or `not_submitted`. |
| Exam | the submitted attempts (D559) | `passed`, `not_passed` or `not_attempted`; the best score, and the number of attempts. |

**Nothing started is not zero.** An exam with no attempt has no best score
(null), never 0%.

**A learner is a name and a uid.** No program query selects an email, and the
test reads every response it makes for one.

### Addendum (#1251, 2026-10-06): "My programs" in one read

**`GET /api/learning/programs/enrolled` answers each program with its
`contents` and the caller's `my_completion`.** These are the same fields, built
by the same helpers (`describeContents`, `completionFor`), that
`GET /programs/:uid` gives an enrolled member. A screen that lists the
member's programs therefore reads once, not 1 + N times.

**One round of queries, however many programs:**

| Read | Queries |
| --- | --- |
| The programs | 1 |
| Their contents (`enrolledContents`, each row carrying its `program_id`) | 1 |
| Titles and statuses | 1 per kind of content |
| Completion | 4 |

To make that possible, both helpers now take their rows as bound JSON lists
(`IN (SELECT value FROM json_each(?))`), never one query per item or per
program:
- `describeContents` reads each kind of content in one query; it used to make
  one query per item. The detail and learner reads gain this too.
- `completionFor` is scoped by the learners' ids and the contents' courses,
  where it used to be scoped by one program's enrolment, so its `programId`
  argument is gone.

**A failure stays on its own row:**
- A content item whose store row is gone says `missing` on its own line, and
  the rest still draws.
- If the contents round fails, the list is still answered. Each program
  carries `contents: null`, `my_completion: null` and
  `contents_error: 'unavailable'`, so each row can say it could not load its
  contents.

**Tests:** two in `learning_programs_d558.test.ts`, both failing on the code
before this change. They pin:
- each program's contents and completion are equal to the detail read's;
- the caller sees only their own completion, never another learner's;
- programs the caller is not in are left out;
- a missing item is shown on its own row;
- one program and four programs take the same number of queries;
- a failed contents round blanks no program.

Ten mutations were made and eight were caught. The two that survive are
equivalent, so no test can tell them apart from the real code:
- dropping the `published` filter from `enrolledContents`: the route already
  discards contents of a program it does not list;
- unscoping the submissions read: each completion cell is keyed by its
  learner.

The frontend half (`readMyPrograms` making one call) is in
`frontend/src/pages/learning/programReads.js`. That file is not on main
(D562 stage 3, #1163), so it is changed when that file lands.
