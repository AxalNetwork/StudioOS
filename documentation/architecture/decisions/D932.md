## D932 — Admin · Community's Recent activity: one paged read over five sources, with no member named

- **Status:** decided by S1 for the owner, 2026-10-24 (#2716; part 2 of #2367). Built by S08.
- **Basis:** `origin/main` at `6c48aa50d0`. Paths are relative to `cloudflare-worker/` unless they say otherwise.
- **Migration:** none.
- **Canvas:** "Community", boards CM1 (row 7, Recent activity) and CM6 (its lightbox). S1's map, `documentation/audits/COMMUNITY_OVERVIEW_MAP_2026-10-24.md` §2–§3, is in draft PR #2714 (D930, the page).
- **Part 1 (#2715)** adds the overview read to the same router, `src/routes/admin_community.ts`. It was not on `main` when this was built, so this PR creates the file.

### 1. The read

`GET /api/admin/community/activity?kind=&from=&to=&q=&limit=&offset=`

- **Gate:** `requireAdmin`. Any admin; a member gets 403.
- **Query:**
  - `kind`: `events`, `jobs`, `circles`, `wellbeing` or `admin` (admin actions in every source);
  - `from` and `to`: UTC days, `YYYY-MM-DD`, inclusive at both ends;
  - `q`: a case-insensitive title search; `%` and `_` match themselves;
  - `limit`: 1–50, default 10, as CM1 draws;
  - `offset`, with `offset + limit` at most 1000.
  - Anything else is a 400 (`bad_kind`, `bad_date`, `bad_limit`, `bad_offset`), never a quietly wider answer.
- **Answer:** `{ rows, total, limit, offset, filters, sources, unreadable, definition }`.
  - Each row is `{ kind, actor, icon, sentence, title, href, at }`, plus `count` on a registration row and `dated_by: 'last_change'` on a row dated by its item's last change.
  - `actor` is `admin` or `member`, never which one.
  - `href` is the item's console: `/admin/events`, `/admin/jobs`, `/admin/circles`, or `/admin?tab=wellbeing` until #2375.
- **Paging:** newest first. Each source is asked for its first `offset + limit` rows and its own count, and the rows are merged. So the pages are disjoint and add up to the whole, and `total` is the sum of the sources that answered.

### 2. What each row is, and where it comes from

| Source | Rows | Store | Sentence |
|---|---|---|---|
| `events` | An admin published, sent back, unpublished, featured, stopped featuring, or cancelled an event | `admin_audit_log`, `report_type = 'events'`, written by `routes/admin_events.ts`; the title from `events` | "An admin published “Demo Night”." |
| `events` | An event submitted for review | `admin_audit_log`, `action = 'event_submitted'`, written by `logAdminAction` in `routes/events.ts` | "“Pitch Night” was submitted for review.", or "An admin submitted …" when the submitter is an admin |
| `jobs` | An admin published, sent back or unpublished a posting | `admin_audit_log`, `report_type = 'jobs'`, written by `routes/admin_jobs.ts` | "An admin published “Founding CTO”." |
| `jobs` | A posting waiting for review, or closed | `job_postings` with status `pending_review` or `closed`, dated by its own `updated_at` (`dated_by: 'last_change'`) | "“Product Designer” was submitted for review.", "“Ops Lead” was closed." |
| `circles` | An admin created, published, unpublished, featured or stopped featuring a circle | `admin_audit_log`, `report_type = 'circles'`, written by `routes/admin_circles.ts` | "An admin featured “Climate Founders”." |
| `event_registrations` | The registrations made for one event on one UTC day, counted, whatever their status now | `event_registrations.registered_at` | "12 registrations for “Demo Night” on 2026-10-24." |
| `wellbeing` | An admin verified, unverified, hid or restored a wellbeing expert | `admin_audit_log`, `report_type = 'wellbeing'`, written by `routes/wellbeing.ts` from this decision on | "An admin verified a wellbeing expert." |

**Why some rows are dated the way they are.**
- **Events** keep only `created_at` and `updated_at`, and `updated_at` moves on every edit. So an event's changes are dated by the audit rows, never by the row.
- **Submitting and closing a job posting** are a host's acts and write no audit row. The posting's last change is the only date there is, and the row says so. Writing members' acts into `admin_audit_log` would put them on HQ's governance feed (H7), which reads that table unfiltered, so this decision does not.
- **Wellbeing** verify and hide wrote no audit row before D932. Each now writes one, `{ expert_uid }`, and only when a row changed. An unknown uid writes nothing.

**Not activity:** event and job drafts; edits; capacity overrides; agenda changes; registration approvals; a circle's deletion (the circle is gone, so there is no title to show); and every other audit row.

### 3. Members are never named

- An admin's act reads "An admin …". No admin's name, email, id or hashed actor travels.
- A member's act reads as the item ("… was submitted for review") or as a count ("12 registrations for …").
- A registration is never one row per person. It is one row per event per day, counted.
- A wellbeing expert is not named: an expert's name is a person's details. The row's `title` is null.
- No row carries an account id, an audit row id or an item id. Item titles appear, as the canvas draws them.

### 4. Each source answers alone

A source whose store failed is listed in `unreadable` as `{ source, reason }`. Its rows are absent and its count is not in `total`; the other sources answer. `sources` lists the ones that answered.

### 5. The client

`communityApi.activity(params)` in `frontend/src/lib/api/community.js`, re-exported by one line in `api.js` (D527). Part 1's client joins the same module.

### 6. Tests

`test/community_activity_d932.test.ts` (new, 9), on `node:sqlite` behind the real route. The audit rows are seeded the way the consoles write them, and the wellbeing rows come from the real verify and hide routes:

1. Every source answers, newest first, with its sentence, console link and total. A day's registrations are one counted row.
2. An admin is "An admin"; a member's act never says so.
3. A failed source (`job_postings`, `event_registrations`, `admin_audit_log`) is listed in `unreadable`, adds no row and nothing to `total`, and the others answer.
4. Paging: pages are disjoint, in order and add up to the whole; `total` does not move; ten by default.
5. Every kind: events with their registrations, jobs, circles, wellbeing, and admin actions across sources.
6. The date range is inclusive at both ends.
7. The title search is case-insensitive and literal for `%` and `_`, drops untitled rows, and combines with the kind.
8. Each bad filter is a 400, and a member is refused.
9. Verify and hide write their audit rows, and an unknown expert writes none.

Every response is walked: no key names a person or a record, no string is an email, and no seeded name, email or expert uid appears.

`frontend/test/community_client_d932.test.mjs` (new, 2): the query carries only what is set, and the module is one alphabetical line calling its one route.

**Mutation check.** 14 mutations were tried; all 14 were caught:

- one row per registrant;
- a registrant's name in the title;
- a failed source failing the read;
- the merge left unsorted;
- the admin filter off;
- `to` made exclusive;
- the search unescaped;
- an audit row for an unchanged hide;
- an audit row for an unknown verify;
- a member's submission shown as an admin's;
- drafts as activity;
- unlisted event acts let in;
- the featured flag inverted;
- events without their registrations.

### Rollback

Revert the PR. Nothing is migrated. The wellbeing audit rows already written stay in `admin_audit_log`, which is sealed against UPDATE and DELETE (D156); HQ's governance feed lists them as the admin actions they are.
