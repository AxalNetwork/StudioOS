### 1. Sign-in: a Vercel Integration, Read only

- **The start** (`GET /api/connectors/oauth/vercel/start`) writes the signed state and sends the member to `https://vercel.com/integrations/<VERCEL_INTEGRATION_SLUG>/new?state=…`. The member picks a personal account or a team, and all or chosen projects, on Vercel's own screen.
- **The callback** is the shared one. `connect` exchanges the code (`exchangeVercelCode`), reads the installation, and returns its `scopes`. The route holds them to the registry's three (`read:project`, `read:deployment`, `read:domain`). Anything wider is refused (`scope_overreach`), and `revokeGranted` uninstalls the installation (`DELETE /v1/integrations/configuration/{id}`).
- **The credentials** `{ access_token, configuration_id, team_id }` are encrypted against the row's uid. The token has no refresh. A 401 or 403 from Vercel reads as "Reconnect Vercel".
- **Set up means three things:** the client pair (`VERCEL_CLIENT_ID`, `VERCEL_CLIENT_SECRET`, env or HQ → Integration keys) **and** a valid `VERCEL_INTEGRATION_SLUG`. Without all three, `ready` is false, and the start is refused before any state row is written (D751). The slug is a wrangler var in both blocks, committed empty until the owner registers the Integration (#2408 decision 1).
- HQ's Test sends a code that cannot exist to Vercel's token endpoint and reads the answer (`testVercel`).

### 2. Choose projects

- **One venture per connection,** like GitHub's repositories. `vercel` joins `writesProjectData`: connecting and syncing need an active company, and `project_id` must be a venture in a company the connection is enabled for (`PATCH /:uid/config`'s existing check).
- **The list.** `GET /api/connectors/:uid/action/projects` lists what the installation reaches: its chosen projects when the member picked some at install, else every project, at most five pages of 100. It records their ids as `known_projects`, the only ids `validateConfig` accepts.
- **The choice.** `projects` is a list of at most 50 of those ids; a repeat is dropped. Every other config field is refused (`read_only_field`).
- **The page.** Vercel's connector page draws Projects under Your connection (`VercelProjectsSection.jsx`). It shows the venture, the list (or why it is empty), and Save and sync. Save opens an in-page dialog that says what changes ("Axal VC will read 2 projects for Acme Health and sync them now. Nothing changes on Vercel."). A failed read is Unreadable with Try again.

### 3. The sync and the directory

- **What it records:**
  - the installation in `vercel_installations` (the webhook's lookup), on every sync and projects read, and after connect (`postConnect`);
  - per chosen project, `vercel_projects`: name, framework, Node version, production branch, linked repository (`owner/repo`), production domain, plan, `live_state` (`live`, `failing`, `building`, `not_deployed`) and `live_since`.
- **The production domain** is the first verified custom domain, else the first verified one, and never an unverified one. `live_state` comes from the project's current production deployment.
- **What it reads:** the installation, the project and its domains only. No deployment list, log, runtime log or analytics: parts 2 and 3 add their own reads.
- **Pruning.** A project no longer chosen, or a venture the connection no longer feeds, leaves the directory.
- **Rate limits.** A 429 stops the sync "Partly synced" and prunes nothing. The next Sync starts over and only updates. A project Vercel no longer answers for (404), or one outside a "selected" installation, is counted `not_reachable` and left out.
- **Nothing personal is stored:** no creator, no commit message and no log line.
- **Clearing rows.** `clearVercelRows` deletes a connection's Vercel rows. Parts 2-4 add the tables they own. The rows also cascade with the connection (`ON DELETE CASCADE`).
- **What the page claims.** `vercelFeeds.ts` lists each landing, its module and the part that builds it. A landing is claimed on the connector page only once its part sets a store, and the registry's `pulls` and `feeds` are read from it. Part 1 claims only the connection on Operating systems (`VERCEL_READ_BY`), where Tools lists Vercel under its new category, Hosting.

### 4. The webhook receiver

`POST /api/connectors/webhook/vercel` (`routes/vercel_webhook.ts`) is mounted ahead of the connector router.

1. **The signature.** `x-vercel-signature` must be the HMAC-SHA1 hex of the raw body with the client secret, compared in constant time. Missing, wrong, oversized (more than 256 KB) or unparseable answers 404, before any lookup or log.
2. **The lookup.** The connection is found by the event's configuration id in `vercel_installations`. An unknown one answers 404.
3. **A nudge.** The body is a nudge, never a fact. The connection syncs again, which re-reads Vercel, and nothing in the body is stored. A 60-second KV key per connection and object (deployment, project, domain or event type) drops repeats.
4. **Removal.** `integration-configuration.removed` marks the connection `error` ("Removed in Vercel"), deletes its Vercel rows, and later deliveries for it answer 404.

Logs hold the event type and an outcome or a code, never a body, a name, a domain or a token.

### 5. Disconnect

`DELETE /api/connectors/:uid` deletes the Vercel rows, uninstalls on Vercel (best effort; a failure is logged and never blocks), and deletes the connection. Part 1 writes no `connector_fed_items` rows, so there is no ledger to unlink.
