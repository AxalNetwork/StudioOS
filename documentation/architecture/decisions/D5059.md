### 1. Four things, kept apart

| Question | Where it lives |
| --- | --- |
| Is this licence type eligible for the program? | `program_licence_rules`: one versioned rule per program and licence type |
| Has HQ actually granted the program to the account? | `user_program_grants`: one row per account and program (granted, paused, ended) |
| Is it legally ready? | the rule's `agreement_required`, answered by an executed `program_licence:<program>` agreement on the source licence (D5048's `licence_program_agreements`) |
| Is the licence suspended or ended? | the licence's own status (D5058); nothing is copied |

A held licence is a **source** of a program when the in-force rule for its type is eligible and its status holds
access (`active`, `renewal_pending`: D5058's `ACCESS_STATUSES`). A program is **in force** when it has a source, a
grant in state `granted`, and at least one source that is legally ready. Each program carries its `blockers`, each
in a sentence: `not_granted`, `grant_paused`, `grant_ended`, `licence_<status>` (no other valid source),
`no_eligible_licence`, `agreement_missing`, `agreement_not_sent`, `agreement_awaiting_signature`,
`agreement_not_recorded`, `agreement_unreadable`.

### 2. The union, and ending one licence

Every licence the account holds is evaluated. A program appears once, listing every licence that sources it, and
`in_force_via` names the first ready one: that is how Program access says which licence caused an entitlement.

The grant names no licence. Sources are derived on every read, so ending or suspending one licence removes the
entitlement only when no other valid licence still sources it. The grant row is not rewritten by a licence
change: a granted program that loses its last source reads "Not in force" with the licence's status as the
blocker, and comes back if the licence is resumed. A grant (or resume) is refused (409 `not_eligible`) when no
valid source exists at the time; the event records the sources then (`sources_json`), as history only.

One grant row per account and program (UNIQUE), so a multi-licence account can never hold a duplicate.

### 3. Rules are data, versioned

- Append-only (triggers). A change is the next version of its (program, licence type) pair, with
  `effective_from`, a reason and who. `eligible = 0` is a version that withdraws eligibility.
- The version in force on a day is the highest version whose `effective_from` has come; a later-dated one is
  scheduled. A version may not take effect before the one it follows (409).
- **The seed** is the issue's examples, as version 1 rows (`origin = 'seed_d5059'`, effective 2026-11-12), on the
  Programs catalogue's keys. The evaluation holds no program or licence type name (a test evaluates with no rules
  and gets nothing). Judgement calls, which HQ may version:
  - Founder: Spin-Out Lab, AI-native Venture, Learning, Perks, Refer & Earn.
  - Investor: Investor cohort access, Referral partners (the "investor/network features"), Learning, Perks.
  - Advisor: Mentor cohort access, Learning.
  - Operating Partner: Spin-Out Lab, AI-native Venture, Mentor cohort access, Learning.
  - `agreement_required` on Spin-Out Lab and AI-native Venture (both types) and Investor cohort access, after
    #5047's "Venture Building → stronger program-specific agreements". Everything else requires none.

### 4. Honesty and role strings

- `users.role` is never read. An account whose role says `investor` but which holds no `licences` row has no
  entitlement; an `admin` holding an Investor licence has the Investor programs. The primary licence counts through
  its D5058 backfilled row.
- The agreement store missing reads Not recorded; a failed read, Unreadable. Either blocks an agreement-required
  program and never reads as signed; a program that needs no agreement is not held by it.
- D5052's agreement policies and holdings are frozen on operator licences at a territory grant; they are not
  consulted here. For a user licence the requirement is the rule's.

### 5. Territory Program Grants

`program_grants` (D982) is untouched: nothing here reads or writes it, its routes and pages are unchanged, and a
test shows the territory read identical before and after user grant writes, and that a territory grant makes no
member eligible. Program access by licence gains a **User licences** tab beside Grid, Requests, Default terms and
History.

### 6. Routes

HQ reads are `requireSuperAdmin`, as the registry and Program access are; writes are `requireSuperAdminWriteBar`
with a reason of at least 10 characters, audited (`program_licence_rule_versioned`, `user_program_grant_changed`).

- `GET /api/admin/program-entitlements` — Program access by user licence (`licence_type`, `holder=user:<id>`,
  `program`, `q`, `limit`); an unknown filter value is a 400.
- `GET|POST /api/admin/program-entitlements/rules`.
- `GET /api/admin/program-entitlements/accounts/:id`; `POST .../accounts/:id/programs/:program`
  `{ action: grant|pause|resume|end, expected_revision, reason }` (0 when there is no grant; stale is 409).
- `GET /api/admin/program-entitlements/licences/:uid` — one user licence's programs.

### 8. Grant reconciliation

HQ can read `GET /api/admin/program-entitlements/reconciliation?program=learning&limit=100`.
Use the returned `next_after` as the next request's `after` until it is null. The response is private and
uncacheable. It contains account IDs, source licence IDs, grant state and revision, and blocker codes.
Each report uses the current UTC day. Run all pages for one program within the same day and recheck
individual accounts before applying any change. No report row writes a grant.

1. Read each mapped program. Active assignments, enrolments, terms, and pool memberships identify
   candidates for review. A past claim or submission identifies activity for review only. Empty pages
   describe that evidence source. They do not cover new participants or show a complete list of members
   who could be affected. Use the Program access holder view to review those cases.
2. Leave `in_force` and `preserve_grant_decision` rows alone. Investigate `review_licence` and
   `review_agreement` against the source licence and its required agreement. A cohort NDA or terms record
   is a separate requirement and does not satisfy the program licence agreement.
3. Confirm scope, existing access and the intended grant for each `review_grant` and `review_activity`
   row. A human records approved changes through the HQ grant action with its current revision and an
   audit reason. Re-run the report to confirm those grants and identify exceptions. Keep enforcement off
   while the rollout scope, exceptions and existing grants are being reviewed.

### Member program access

`GET /api/member/program-entitlements` uses the authenticated account and the same evaluator as the HQ read.
It returns the member's licences, each program's eligibility, grant and legal status, its sources and blockers.
The response is private and non-cacheable. The member projection omits account records, audit history,
rule metadata, agreement identifiers and grant revisions. The Account profile has a Program access card that
shows each program's status, source licences and blockers.

HQ can manage a holder's grant from the user licence Programs card. Writes carry the revision and reason
through the existing write bar. Program access › User licences also offers versioning of eligibility rules.
The D5060 detail read uses the same entitlement service for its Programs section.

The opt-in `PROGRAM_ENTITLEMENT_ENFORCEMENT=true` checks those HQ entry points. Territory Workers retain their existing programme rules. It leaves the Lab application and exit flows available. Rollout requires reconciling existing
member grants, since the seed records eligibility rules only.
