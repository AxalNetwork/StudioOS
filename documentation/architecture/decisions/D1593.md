## D1593 — The company's registered agent and one open mailing address

- **Status:** built by S17, 2026-10-31 (#3861). The issue was filed for S18; the owner moved it to S17.
- **Canvas:** the Portfolio canvas (#3696): PF8a and PF8b, the legal facts sheet, and PF2's Legal card.
- **Builds on:** D1415 (#3697 part 1, migration 685): a company as a legal entity, its locations and `routes/company_legal.ts`.
- **Migration:** `749_company_registered_agent_and_mailing.sql`.
- **Basis:** `origin/main` at `ce9e885b33`. Worker paths are relative to `cloudflare-worker/`.

### 1. What the sheet needs that D1415 does not store

- **The registered agent's name.** Incorporate already collects it with every order (`incorporations.registered_agent_name` and `registered_agent_address`, migration 086). The company had no field for it.
- **A mailing address.** `company_locations.kind` allowed `registered`, `headquarters`, `office` and `other`.

### 2. The migration (749)

- `company_profiles.registered_agent_name TEXT`. Nothing is backfilled. #3855 (D1415 Part 3) copies the order's agent onto the company at filing, filling it only when it is NULL.
- `company_locations.kind` gains `mailing`.
  - SQLite cannot widen a CHECK in place, so the table is rebuilt, as 644 rebuilt `notion_proposals`: a new table with the same columns, defaults and keys and the wider CHECK; every row copied with its `id`; the old table dropped; the new one renamed.
  - `idx_company_locations_one_registered` is created again.
  - `idx_company_locations_one_mailing` is added: at most one open mailing address per company, as there is one open registered address.
  - Nothing references `company_locations` and no trigger sits on it (only 685 creates it, and `routes/company_legal.ts` is its only reader).
- No BEGIN or COMMIT. `scripts/migrate-d1.mjs` hands the file whole to `wrangler d1 execute --file`, as it did 644's rebuild.

### 3. The routes (`routes/company_legal.ts`; the gates are unchanged)

| Route | Change |
|---|---|
| `GET /api/company/:uid/legal` | It gains `registered_agent_name` (null when not recorded) and `mailing_address`, a block holding the open `mailing` row or null, beside `registered_address`. A failed locations read makes both unavailable, never null. |
| `PUT /api/company/:uid/legal` | It accepts `registered_agent_name`: text of at most 200 characters, trimmed, where `null` clears it (400 `text_too_long` above 200). It is written in the same fixed statement as the other legal fields. |
| `POST /api/company/:uid/locations`, `PATCH …/:locUid` | They accept `kind: 'mailing'`. A second open mailing address is 409 `mailing_exists`, "This company already has a mailing address. Close it before you add another." The pre-check answers first; when two writes race past it, the index decides and the answer names the kind that clashed. `kind_invalid` lists mailing. |
| `POST …/locations/:locUid/close` | Unchanged: it closes a mailing address as any other, which frees the slot. |

Nothing is deleted, and an archived company takes no write (409 `archived`), as D1415 set.

### 4. Screens

S1 integrates. PR #3853's `companyLegalApi` already covers it, with no new client method:
- `legal(uid)` reads `registered_agent_name` and `mailing_address`;
- `saveLegal(uid, { registered_agent_name })` writes the agent;
- `addLocation(uid, { kind: 'mailing', … })` and `closeLocation` handle the mailing address.

### 5. Verified

`cloudflare-worker/test/company_legal_mailing_d1593.test.ts` has 3 tests, on the baseline plus 597, 685 and 749:
1. The migration keeps every location row, id and column. The registered index still refuses a second open registered address, `mailing` is accepted and a second open mailing address is refused. The kind is still checked, nothing is backfilled, and new ids continue after the copied ones.
2. The agent: an editor sets it (trimmed) and clears it with null. A member reads it, another field's write leaves it as it was, 201 characters is 400 `text_too_long`, a member who is not an editor gets 403, and an archived company gets 409.
3. The mailing address: null inside an available block when none is open. `kind_invalid` names mailing. A mailing address does not take the registered slot. A second one, by POST or by PATCH, is 409 `mailing_exists`. Closing frees the slot and nothing is deleted. A failed locations read makes both addresses unavailable.

`company_legal_d1415.test.ts` now applies 749 as well and stays green.

10 mutations were run and 8 caught: the mailing index left out; rows copied without their ids (either side); the registered index dropped in the rebuild; `mailing_address: null` on a failed read; the agent left out of the write or of the fields; and `kind_invalid` without mailing.

The 2 survivors are the mailing pre-checks in POST and PATCH. Without them, the unique index refuses the write and `clashOf` answers the same 409 `mailing_exists`, so the response is unchanged. They are equivalent by design, as D1415's registered pre-check is.

The issue's fifth mutation ("overwrite a set agent at filing") belongs to the filing fill, which is #3855's (D1415 Part 3).
