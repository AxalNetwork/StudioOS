## D9067 — Introduction requests: a Super Admin's named operator grant and a Network reviewer entitlement in place of every HQ admin (#9067)

- **Status:** built by S02, 2026-11-27 (#9067, under #7673). Implements the owner's answer A of 2026-11-27 on #7673 for D7678 ("operator entitlement is a named grant by a Super Admin") and D7677 Q3 ("reviewers are HQ Admins with a Network reviewer entitlement").
- **Migration:** `cloudflare-worker/sql/migrations/202611272227_9067_network_intro_grants.sql`, additive: one table, `network_intro_staff_grants`.
- **Why:** every operator and readiness route of `routes/intro_requests.ts` called `requireHqAdmin`, so any HQ admin could read every request, assign it, contact the target and approve a requester's readiness. The owner chose a named grant instead.

### What changed

- **The grant.** A row of `network_intro_staff_grants` names one HQ admin and one kind, `operator` or `reviewer`, with who granted it, when and why. At most one grant per person and kind is in force (a partial unique index on rows not revoked). A revoke keeps the row and records who revoked it, when and why. There is no validity period: no column holds one, and a grant holds until a Super Admin revokes it. `network_intro_policies.validity_days` stays NULL.
- **The gates.** Each operator-side route asks, in order: an HQ admin (`requireHqAdmin`, unchanged: a branch admin is still refused), not a support session if the route writes, then the grant.

  | Route | Operator grant | Reviewer entitlement |
  |---|---|---|
  | `GET /operator/queue`, `GET /operator/requests/:uid`, `GET /operator/provisional-targets` | yes | yes (read only) |
  | `POST /operator/requests/:uid/assign`, `/move`, `/recipient`, `/contact-attempts`, `POST /operator/contact-attempts/:attemptUid/reconcile` | yes | no |
  | `GET /operator/readiness`, `POST /operator/readiness/:userId/:key` | no | yes |

  Refusals: `network_staff_required` (a read with neither), `operator_grant_required`, `reviewer_entitlement_required`, `support_session_read_only` (403 each).
- **Granting and revoking.** `GET /api/intro-requests/operator/grants` (Super Admin) lists the grants in force. `POST /api/intro-requests/operator/grants/:userId` with `{ kind, reason }` grants; `DELETE /api/intro-requests/operator/grants/:userId/:kind` with `{ reason }` revokes. Both writes pass `requireSuperAdminWriteBar` (a TOTP-minted session, a step-up within 15 minutes, then the elevation), the bar the other Super Admin writes use. The grantee must be an active HQ admin. The change and its `admin_audit_log` row (`network_intro_grant`, `network_intro_revoke`, with the grantee, kind, grant uid and reason) are one batch, so neither lands without the other. A repeated grant or revoke changes nothing, records nothing and answers `already: true`.
- **Private notes.** Unchanged and now pinned by this issue's test as well: the operator projection never carries the requester's `private_notes`.

### Choices made here

- **A Super Admin is not an operator by being one.** The answer names a grant; a Super Admin who works the queue grants it to themselves, which leaves a receipt like any other grant.
- **The reviewer reads the operator side, read only.** A readiness decision is about a requester whose request is waiting, so the reviewer may read the queue, a case (the operator projection, without private notes) and the provisional targets. Every request write needs the operator grant. The operator does not read the readiness queue or decide readiness: those are the reviewer's.
- **A support session reads, never writes,** on every operator and reviewer route, as it already could not on the requester's.
- **A grant needs a reason,** up to 500 characters, kept with the row and in its audit receipt, as the Super Admin elevation's transfer does.
- **No client method.** No page calls these routes yet; the HQ screen that will is not drawn. The member-side request flow (#9068) is untouched.

### Questions for the owner

- **Q1. May a reviewer read requests?** **A** (built): read only, as above. **B**: readiness only; the request queue and cases are the operator's.
- **Q2. Does granting need the Super Admin write bar (TOTP and a recent step-up)?** **A** (built): yes, as for every other Super Admin write. **B**: the elevation alone.

### Tests

`cloudflare-worker/test/intro_operator_grants_9067.test.ts` (real migrated schema, synthetic people): the table's guards and no validity period; an HQ admin, and a Super Admin, without a grant refused on every operator and reviewer route with nothing written; a granted operator works a request end to end and cannot decide readiness; a reviewer decides readiness and reads the operator side but every request write is refused and nothing changes; a support session with both grants reads and is refused every write; only a Super Admin past the write bar grants or revokes, each change leaves exactly one audit row, a repeat leaves none, and a revoked grant closes the queue at once. `intro_requests_7673.test.ts` keeps every assertion; its fixture now grants its two operators (and the first the reviewer entitlement), since an HQ admin alone no longer opens those routes.
