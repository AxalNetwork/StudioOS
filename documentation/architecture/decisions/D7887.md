## D7887 — Durable CI capacity coordination (#7887)

### Delivery boundary

This first draft delivers an **inactive coordinator core**, pure policy, and
SQLite recovery tests. It is part of #7887. It is not a routing cutover.
`CiCapacity` has no production constructor call, public route, alarm handler,
GitHub adapter, check publisher, planner caller, or executor credentials.
The existing hosted CI path, required checks, and App permissions are unchanged.

On 2026-11-20 the connected Cloudflare account's Workers inventory did not
contain `studioos-merge-control`. This observation is limited to that account.
Deployment, recovery, webhook subscriptions and permission review must be
proved before relying on Merge Control. A passing local simulation is not a
live canary or a hosted-slot capacity measurement.

### Ownership and dependencies

Caller/gate ownership was requested on #6677 and PR #7882 before any caller
edits. Their paths remain untouched pending agreement. #7885 owns bootstrap
and the shared profile contract. #7886 owns the trusted executor, candidate
provenance/plan checks and execution contract. Proposed receipt fields and
OIDC transport were posted on #7887 for agreement with #7886. The interfaces
here remain draft integration contracts.

The future executor must authenticate to the configured control plane using
GitHub OIDC. `requestId` and `logicalShard` are lookup keys only. An adapter
must verify issuer, audience, signature, expiry, repository and exact child
run/attempt plus trusted workflow revision against GitHub metadata. It must
resolve the currently owned receipt twice, before candidate checkout and
immediately before tests. No caller receipt JSON or webhook payload is proof.
Unconfigured or unreadable authority denies execution. No owner token may be
passed to an Actions job to substitute for child identity.

### Durable ownership

`SqlCapacityStore` uses its own `ci_capacity_requests` table and SQL transaction
boundary, with a unique repository/parent run/attempt identity. Issue claims,
queue cancellation, application D1 and their kill switch are separate.
One object per repository must hold one `CiCapacity` instance, serializing
admission and effects. Request acceptance durably records the complete expected
shard and prerequisite sets before remote execution. Acceptance never means
that tests passed. Equivalent duplicate requests are idempotent; conflicting
identities are rejected. A later parent attempt fences older children even
if a process stops before the cached superseded flag is written.

Each attempt binds repository, original event/workflow/run/attempt, candidate
SHA, original merge-group queue-base SHA (null otherwise), plan digest and artifact ID, executor SHA, logical shard, pool, generation,
child run/attempt and immutable deadlines. Parent and child IDs are positive
integers; SHAs are full revisions. Main push plans require the authenticated
parent artifact ID. Merge groups use the trusted deterministic plan digest.
The original merge-group base is bound from authenticated event metadata and must remain in the complete source ancestry; it is never replaced with current main. The future provenance adapter must independently derive these values. Merely
copying the submission into `CiProvenance` is invalid outside tests.

A reservation and `dispatching` intent commit before the dispatch call. The
returned child run ID commits before observation. GitHub's current dispatch
API returns this ID under API version `2026-03-10`; the existing repository
client uses `2022-11-28` and needs an intentional scoped extension. A network
error or interrupted intent becomes `dispatch_unknown`. Reconciliation may
bind one verified owned child, but must never redispatch an ambiguous intent.
Duplicate run IDs cannot own two shards. Cancellation is also fenced and
persisted before the API call. Only owned bound children can be cancelled.

### Pool and fallback policy

Inventory is an authenticated, complete, fresh snapshot of one approved
organization group, with shared capability profiles and actual OS/architecture
validation supplied by #7885's adapter. No repository/default-group discovery,
paid larger labels, per-host dispatch selectors or hostname lists are used.
Runner IDs deduplicate inventory and are never dispatch targets. New compatible
machines contribute when the approved inventory refreshes.

Profiles are `hosted`, `linux-x64`, `macos-arm64`. Only trusted push/merge-group
Worker work can delegate; PR and non-Worker work stays in the existing ci.yml; untrusted admitted work remains hosted. Mac compatibility
initially covers `worker-1-of-6`. At most two Worker shards delegate. The policy
requires at least one hosted Worker shard and normally retains four of six;
non-Worker work remains hosted. Inventory errors, incompleteness, wrong groups,
staleness, busy/offline/draining runners, or exhausted durable reservations
choose hosted before delegation. Reservations subtract only reserved, dispatching, dispatch_unknown and queued
attempts across accepted requests; running attempts are already represented by busy inventory (D7903). A snapshot never grants atomic ownership of a machine.

| Budget | Default |
| --- | ---: |
| External pickup | 90 seconds |
| External execution | 25 minutes |
| Cancellation confirmation | 2 minutes |
| Hosted pickup | 10 minutes |
| Complete hosted execution | 40 minutes |
| Control margin | 5 minutes |
| Overall queue deadline | 90 minutes |
| Inventory maximum age | 30 seconds |
| Reconciliation wake interval | 15 seconds |

The configured path totals 83.5 minutes and is rejected if it exceeds the queue
budget. The external pickup budget is configurable. Execution deadlines include
the startup allowance and cannot be extended by repeated events. Hosted fallback
is allowed once, from an external generation with verified terminal outcome and
no confirmed test failure, preserving the candidate and plan. Cancellation API
success alone does not confirm termination. Node loss or unreadable test truth
stays pending with `cancellation_unknown`, then fails at the overall deadline.
Ambiguous dispatch also stays unresolved until metadata recovery or failure.
A verified failure is sticky across retries, duplicate events and older
attempts. Late success cannot satisfy a newer generation. Contradictory late
verified test failure changes the shadow authority to failure.

### Aggregate and cutover audit

The core exposes a shadow aggregate only. It requires each expected logical
shard's current generation and every prerequisite to have verified success.
Unknown job, test step, workflow, runner profile, child attempt, altered receipt
or incomplete prerequisite evidence cannot clear it. A completed success is
durably stable after the deadline; contradictory verified failure still wins.
The future observer must check the exact workflow file, one owned job, actual
runner profile, successful candidate-test step and full run conclusion. These
injected port obligations are not implemented GitHub verification yet.

The following source audit identifies the coordinated consumer work remaining.
No entry below has been changed or certified for the new authority.

Proposed aggregate context is `ci-capacity/full-suite` from the dedicated Merge
Control App, on the exact admitted candidate SHA. That distinct name avoids two
identically named producers during shadow testing. App ID and source binding
must be reviewed in the actual required-check ruleset before activation. The
aggregate must have one idempotent producer keyed by request, with publication
outbox/reconciliation and the full prerequisite set. This draft has no producer
or publication outbox and is not eligible to replace existing required checks.

| Capability | Current request | Proposed addition before activation |

| Repository Contents | read | Retain for source, trusted executor and plan provenance. |
| Repository Checks | absent | write for the one reviewed aggregate, never broad status fabrication. |
| Repository Metadata | implicit read | Retain installation/repository identity verification. |
| Organization Self-hosted runners | absent | read for the configured approved group and complete paginated inventory. |
| Webhooks | Existing ingress | Subscribe to `workflow_job` and `workflow_run`, retain typed run/job/attempt identity, verify HMAC and re-read metadata. |

Use a separate scoped organization installation client for group inventory;
the existing repository-only URL allowlist must not become arbitrary URL
access. Bound pagination, response bodies, request counts and request timeouts.
Registration/removal privileges belong to the separately reviewed operator
lifecycle, never candidate jobs. No permissions, subscriptions, deployment
settings or repository rules were changed by this part.

### Remaining integration and operational proof

1. Agree and import #7885 profiles and #7886 receipt schema; reserve exclusive
   caller/gate ownership with #6677/#7882.
2. Implement authenticated planner submission and receipt routes, typed webhook
   hints, bounded GitHub provenance/inventory/dispatch/observation adapters,
   independent enable/kill switch, durable alarm and append-only CI audit.
   `CapacityPorts.parent` must revalidate exact source, event, parent attempt
   and liveness, not only the existence of a run. All I/O must time out.
3. Add publication outbox and reviewed App-owned aggregate/prerequisite adapter;
   then update all consumers and actual required-check source restrictions as
   one coordinated cutover. Do not rename or waive existing checks early.
4. Review App scope and deploy Merge Control independently. Prove recovery with
   webhook loss, alarms, queued ingress and process restart. The inactive core
   bounds active requests at eight. The original implementation threw only when
   reading the 1,001st receipt, after accepting it. D7903 now refuses new
   admissions before 1,000 retained receipts can be exceeded, retains settled
   receipts for seven days, and preserves compact identity fences after pruning.
   Terminal-observation reconciliation and operational retention still need
   review before enabling a long-lived service.
5. Run an isolated same-source end-to-end canary showing real hosted and external
   work, one current outcome per shard, correct-child cancellation, both
   admission checks, hosted fallback and zero hosted controller wait. The local
   SQLite simulation does not satisfy this acceptance item.
6. Enable only after review. During service outage no immediate fallback can be
   promised. Keep the aggregate pending/failed until recovery. A reviewed rollback
   fences/reconciles all external children, restores the intact hosted planner,
   matrix and original check producer/source settings, and proves the hosted
   full suite on the same candidate. Never waive required contexts to recover.

### Validation

`merge-control/test/ci_capacity.test.ts` exercises routing, bounds, exact
provenance, real SQLite restart, durable intent/reservations, timeout and
cancellation uncertainty, fallback identity, sticky failures, out-of-order and
late results, supersession and full-set/prerequisite authority. The existing
Merge Control suite and TypeScript checks are run alongside it. Mutation
experiments remove individual authority/fencing conditions and must be rejected
by the deterministic tests. No live dispatch, hosted occupancy proof, new App
permission grant or production activation is claimed.
