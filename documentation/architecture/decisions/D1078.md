## D1078 — Your trust: member requirements, details, agreements and data

Issue #2970, slot S18. Part 6 of #2425. No migration or new API route.

### What ships

- `/trust/me` draws TRU7–TRU10 from the caller’s authoritative `/api/trust/me`
  role and obligation rows. The overview says **Requirements met: n of m**;
  only required rows count and satisfied/waived rows are met. No trust score,
  verdict, demo figure or invented prior count is drawn. Other consumers of
  the shared trust-score library are unchanged.
- TRU11’s lightbox has its own address, `/trust/me?requirement=<key>`.
  It resolves only a key in the caller’s matrix. Unknown keys and member-id
  parameters show the scoped unavailable state without another member read.
  It explains what the item is, why it is asked, its actual state, dates and
  evidence source. In-review and completed rows do not offer signing. Open
  issued role envelopes reuse the actual signing URL flow; other actions
  open existing legal, identity, Account or Help pages. No generic Start
  write returns. Accreditation does not offer an upload with no endpoint.
- Agreements (TRU12) retain real role-envelope signing and recipient-scoped
  history. Signing eligibility is shared between the list and detail, including
  the required/status checks. Refreshes preserve mounted dialogs and their
  signing messages instead of blanking the page. Pairwise reads include an admin’s own pairs, now safe after D1074;
  platform-wide administration stays in Contracts. Search, state filter and
  date sorting operate on the returned rows only. Pairwise and other-contract
  failures are independent, named Unreadable and retryable; history can retry.
- Your data (TRU13) reads deletion state and matching consent independently.
  Download, request deletion and cancel each explain their action in a dialog
  and call existing Settings routes. A request is never described as completed
  erasure. The after-state re-reads the server timestamp; no local date is
  fabricated. The previous DSR outcome uses the existing notice component.
  An omitted deletion field is Not recorded, not a claim of no open request.
- Founder company KYB keeps its own read and failure state. Identity detail
  remains investor-only, even if a non-investor has a stale KYC row. A failed
  identity read keeps the matrix’s separate requirement state visible.
- Admin tools remain links, with no sanctions or platform list fetched. HQ’s
  Super Admin links to the existing `/admin/security/trust-center` editor.
- The same responsive cards serve desktop and phone. The shared Lightbox
  supplies focus containment, Escape, focus restoration and the full-screen
  phone frame, with the requirement action at the foot (TRU19b/c).

### Deliberate canvas departures

The API records historical **scores**, not historical required/met counts.
Those percentages cannot be converted into an honest previous count when the
requirements change, so the summary states that count is Not recorded.
Completion dates are not returned separately from update dates and are not
invented. Reviewer names, requested document details, company names on
pairwise rows and total counts beyond the returned page are not fabricated.

`#2418` remains planning-only and `/account/developer` still admits admins
only. Every profile therefore has the actual Connectors door for connected
assistants; only admins also get Developer. This task does not publish that
separate Developer redesign. The identity view log has no member read here
and is labelled unavailable. The existing auth guard still sends a signed-out
visit to sign-in; an expired-session read also draws the TRU18 sign-in door.

Older phone/score presentation pins are updated to the new member count
contract; shared score-library, signing, status vocabulary, privacy and
identity-masking checks remain. New mounted tests and counterfactual mutations
cover the replacement behavior; no test is disabled or newly skipped.

### Verification boundary

Local validation uses synthetic responses and existing clients, never live
personal data. UNVERIFIED until the owner’s deployed check: real envelope
signing and return, provider KYC/KYB updates, real download and deletion review,
branch/HQ role context, and the final all-profile Developer integration from
#2418. No production store is read or written, no CHANGELOG or built docs is
committed, and the draft is left for the owner to merge.
