## D6651 — Record files are write-once: one writer, one delete path, and a guard (#6651)

R2 keeps no previous versions (#6428, D5581-p3). A backup limits the loss from an
overwrite or a delete; it does not prevent one. For every prefix that the D6650
registry (`documentation/operations/R2_INVENTORY.json`) classes `record`, the Worker
now never replaces an object and never deletes one from request code.

**The writer.** `cloudflare-worker/src/services/recordStore.ts` holds the only puts
to a record prefix. `putRecord` writes with R2's conditional put
(`onlyIf: { etagDoesNotMatch: '*' }`), which commits only while the key is absent.
When an object is already stored R2 writes nothing and answers `null`; the helper
returns the typed refusal `{ ok: false, refusal: 'record_exists' }`, and the first
object keeps its bytes. `putRecordOrThrow` is the same refusal as a
`RecordExistsError`. There is one entry point per bucket (`putRecord` for FILES,
`putPublicationRecord`, `putBackupRecord`), each with its own conditional put, so the
D6650 inventory resolves each write's bucket and prefix from its callers. The
helper has no delete.

**Content-addressed blobs.** A `wg/v1/` key names the SHA-256 of the only bytes it
may hold, and the put carries that digest, so R2 refuses any other body. D5581-p3
repairs a torn or corrupt object, or rewrites a preview marker, by putting the same
bytes again. `putContentAddressedRecord` keeps that repair: it refuses a key that
does not end in its digest, and the store can only ever hold the bytes the key
names. The record does not change.

**Replacing a record.** A replacement writes a new key and the row points at the
newest key. The replaced object is kept, unlike a rollback's: a row named it. This changes D690 (a Build proof),
`validateWriters` (demand evidence), the Raise Google Drive copy and a KYC
resubmission: each deleted the old object after repointing. Data room versions,
interview recordings and governance versions already wrote new keys.

**Rollbacks.** When a row write fails, conflicts or hits a limit after its file was
stored, the request erases that file through the delete path below with the reason
`unreferenced`. Such an object is not a record being deleted: the same request (or
call) created it under a fresh key with a write-once put that succeeded, no row ever
named it, and nothing served it. Keeping it would leave personal data (a failed KYC
submit's identity documents, a credential, a filed statement) with no row to find it by,
which is the data-minimisation gap the old code closed. Each site keeps its old error
handling: a cleanup failure is swallowed and never masks the original error. The
rollbacks are a governance version, a cap-table or use-of-funds snapshot, a KYB document
(a conflict or a failed write), mark-request evidence, a report statement (a failed
insert or a report already sent), wellbeing credential evidence (the ten-file limit or a
failed write), a KYC submit (the documents of a failed list upload or a failed write), a
Raise Drive copy, Grow minutes, a fund notice that lost its race, a Mercury statement in
the data room, a Build proof and an advisor deliverable version. A site where a later
statement can fail after a row already names the key erases only while no row does:
the KYC case and its listed documents, the Raise copy's data room row, the Mercury
statement's data room row (kept when its row could not be removed), and an advisor
version (checked before erasing). A Mercury investor statement is keyed by its proposal,
so it is erased only when this call's put stored it and the decided proposal does not
name it; a copy that was already there is kept. A work-graph blob is content
addressed and may be shared by another row of the same company, so its limit-refused
put is not erased; reconciliation collects it when nothing names it. D4557's compute
completions (cancelled, revoked or losing) leave the same way, as `unreferenced`.
A governance version and a contract's execution evidence take a fresh suffix under
the same prefix, so a concurrent upload can never erase another's file; the row insert
still decides which upload wins. A call-audio chunk stays keyed by its sequence number:
a second put is refused and the stored copy stands.

**The one delete path.** Deletion that the law or a stated retention promise
requires still happens: a member removing their own file, the 30-day call-audio
sweep (PROCESSING_AND_RETENTION_5510), compute-artifact expiry and erasure, a Trash
purge, a rejected KYC or KYB case's purge, and work-graph retention. #6652 (owner's
answer A) routes these through one audited Worker path, and #6654 builds its
suppression ledger. `services/recordErasure.ts` is that path's single door.
`eraseRecordObjects(bucket, keys, reason)` takes a closed list of reasons
(`owner_removed`, `retention_expired`, `purge`, `erasure_request`, `unreferenced`). It logs the
reason and a count, never a key. #6654 adds the ledger row in the same operation
there, so no caller changes. This file adds no new deletion: every caller deleted
the same objects before, the rollbacks included. Until #6654 lands it writes no suppression row, and
because no class has a locked copy (`locked_copy: no` throughout) a restore cannot
yet bring an erased object back.

**The guard.** `scripts/check-record-writes.mjs` runs in `test:guards`. It uses the
D6650 typed scan and fails on any mutation of a record class outside
`recordStore.ts` (writes) or `recordErasure.ts` (deletes), naming file, line,
operation and key. Its baseline, `scripts/record-writes-baseline.json`, started
empty. A baseline entry whose site no longer exists also fails. Replaceable media
and logs are out of scope: routes may still overwrite and delete them. The
inventory now records one reviewed provenance entry for the erasure site, listing
the writers of each stored key its callers pass. Twenty superseded per-site entries
were removed.

Tests use an in-memory bucket that honours `onlyIf` and `sha256`. A second put is
refused with the first bytes unchanged. A Build proof replace writes a new key and
keeps the first proof. A Build proof, cap-table snapshot, KYB document or
mark-request upload whose row write fails leaves no object. The guard fails on a synthetic route that deletes or puts a
record key directly, and passes when the route uses the helpers. No live object,
member key or credential is involved.

**Open for the owner.** Rollback cleanup is built (above). Two questions remain: what
the delete door records before #6654's ledger lands (today a log line with the reason
and a count), and whether #6654 should also sweep replaced files, which this decision
keeps with no row naming them.
