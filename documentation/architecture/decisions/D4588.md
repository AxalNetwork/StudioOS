Each pack covers the issue's required checks for its skill. Across the packs that means:

- complete evidence;
- a missing required input, named field by field;
- stale or contradictory records;
- one task-specific edge case, such as zero or negative burn, two currencies, a missing snapshot date, a conditional
  conversion, or consent not given;
- an instruction embedded in the evidence, which must stay data.

The records are realistic and made up. They carry stable ids, document versions, dates, periods, units and currencies.
No answer is planted in an `evidence` array. Every required phrase comes from a record the output has to read.

### 2. How a scenario proves its assertions

Each scenario is checked with the production code, judge version 3:

1. **The case is valid.** `checkCase` accepts its name, input and expect.
2. **The known-correct output passes** `judge()`.
3. **Each incorrect output fails on the assertion it names.** An incorrect output is the correct one with one targeted
   edit, so it differs only where the assertion looks. It must fail, and the failure detail must name its `targets`:
   the phrase, field, metric, section, citation, refusal subject or claim at fault.
4. **No assertion is decorative.** Every assertion in `expect` has at least one incorrect output that fails on it.

The assertion types used are `must_include`, the per-field `must_say_not_recorded` (#4982), `numbers` with value,
unit and tolerance, `must_not_include`, and judge version 3's `structure`, `evidence`, `refusal` and `claims`.
`output_schema` is not used: none of the ten skills produces a typed artifact.

**The board-meeting regression is pinned.** A brief that says "Churn: Not recorded" and gives runway a figure satisfied
judge version 1, which accepted "Not recorded" anywhere. It fails now. The case is `board-meeting-brief-missing-burn`,
and the test has a dedicated check for it.

### 3. Packaging: a separate folder, not imported yet

**The existing convention is unchanged.** `cases/<slug>.json` is still the one golden case per skill. The generator and
the seed read only that file, so the generated module and the store are unchanged.

**Why a separate folder.** The issue forbids silently replacing that convention, and forbids giving several cases the
same importer identity. The seed names every library case `<slug>: golden case` and dedupes by name, so ten scenarios
fed to it unchanged would collapse into one. The scenarios therefore live in `scenarios/` with their own identities:

- `case_id` is unique and prefixed with the slug;
- `revision` is an integer, bumped when a case's text changes;
- `name` is unique, and differs from the golden case's name.

**Proposal for #4531 and #4532** (needs their agreement; not built here):

- The generator embeds each scenario as a case named by its `name`, so each keeps its own identity.
- `check-skill-library.mjs` runs this suite's rules.
- The live-case cap (`CASES_MAX`, 20 per skill) allows the golden case plus 10 scenarios.

Until that is agreed, these scenarios are local, deterministic evidence. They are not stored cases.

### 5. Findings for #4529 and #4667

The cases use only reads each skill declares, as the issue requires. Two skills' declared reads do not cover what
#4667's input matrix says they need:

- **`safe-convertible-instrument-review`** declares `raise.read` and `cap_table.read`. #4667 lists the instrument text
  under `data_room.index`, which this skill does not declare. These cases supply the terms as a typed `raise.records`
  instrument, with document and version identity. Either the skill should add `data_room.read`, or the matrix should
  move the instrument to `raise.records`. That decision belongs to #4529 and #4667.
- **`contract-risk-issue-spotting`** needs an organization review policy. #4667 names it `manual:review_policy`, which
  is not a catalogue read. These cases put the policy in `company.profile.review_policy`, the only declared read that can
  hold it. Whether the policy is a company-profile field or a manual input belongs to #4667.

`customer-interview-summary`'s historical `refuse_when` stays in its golden case, which is untouched. The scenarios
assert refusal with `refusal`. Consent given, consent not given and no consent record are three separate cases.

### 6. Staged expectations

- **board-meeting-brief:** a runway statement should name burn as the reason it is missing. No assertion relates two
  fields in one statement.
- **safe-convertible-instrument-review:** a calculation should be required to stay conditional. The number and claim
  checks skip conditional statements, but nothing requires a statement to be conditional.

Both are listed in their scenario's `staged` field and are not counted as enforced.
