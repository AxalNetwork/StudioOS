## D8932 — Release admission accepts a verified recent main commit (#8932, #8933)

**Decision (owner answer B on #8932, 2026-11-27).** Production admission no
longer requires the candidate to be the exact `main` tip. This changes the
exact-tip rule of [D5501](D5501.md). A candidate is admitted when it is the
tip, or when it is a verified ancestor of the tip within a bound and not older
than the Worker production serves. Built in #8933.

**Why.** D5501 checks the candidate twice: in *Verify the exact main
candidate*, and again in *Recheck candidate under the production lock* once a
runner picks up the deploy job. With about 40 sessions merging and a congested
runner pool, the gap between those two checks was often longer than the gap
between merges. On 2026-11-27 every deploy was refused as `superseded` until
the owner froze the queue by hand (#8317, #8932). The owner chose B over a
deploy hold (A), which needs every queueing path to honour a switch, and over
re-targeting at deploy time (C), which would ship a commit other than the one
approved. Under B the approved SHA is still the SHA that ships, and the later
commits ship with the next deploy.

**What admission checks** (`scripts/verify-production-candidate.mjs`,
`verifyCandidate()`):

1. **The tip** is admitted as before. Its deployed-version read is evidence
   only: the tip cannot be older than a `main` commit already served.
2. **Ancestry.** Any other candidate is compared with
   `GET /repos/AxalNetwork/StudioOS/compare/{main}...{candidate}`. Only
   `behind` (the candidate is an ancestor of the tip, `ahead_by` 0, merge base
   the candidate) or `identical` is admitted. `diverged` or `ahead` returns
   `untrusted`. A failed or malformed read throws, which the CLI reports as
   `unreadable`. It never admits.
3. **Bound.** More than `MAX_BEHIND_COMMITS` (30) commits behind the tip, or a
   committer time more than `MAX_BEHIND_MS` (6 hours) older than the tip's,
   returns `superseded`, as a newer `main` did before.
4. **Never backwards.** The deployed version is the `sha` that
   `GET https://axal.vc/api/public/version` serves ([D8073](D8073.md)): the
   `WORKER_DEPLOY_VERSION` the release stamps, which the post-deploy smoke
   also reads. The candidate must equal it, or `compare/{deployed}...{candidate}`
   must be `ahead` or `identical`; otherwise it is `stale`. A version that
   cannot be read (HTTP error, timeout, a `null` or malformed `sha`) refuses a
   non-tip candidate with `unreadable`. It fails closed.
5. **The six D5501 checks are unchanged.** They run on the candidate's own
   `push` runs on `main`, as before, after the steps above admit it.

The result JSON carries `main`, `behind_by` and `deployed`, so the release
evidence (`admission.json`, `final-admission.json`) records them. In the
initial decision job, `stale` is a skip like `superseded` (`decision=stale`,
the summary names the deployed SHA); under the production lock it refuses.

**Why the tip does not fail closed.** The issue asks for a refusal when the
deployed version cannot be read. That holds for every non-tip candidate. At
the tip it would add a new way to block a release that D5501 admits today:
production serving no `/api/public/version` (the endpoint arrived with D8073
and was not live on 2026-11-27), or production being down, would refuse the
very deploy that fixes it. So the tip keeps D5501's rule and records the
deployed version, or `null`, as evidence.

**No workflow change.** The script reads the deployed version itself, with no
new input. `.github/workflows/*` is untouched (T2). Migrations stay safe: they
are append-only, and an ancestor's ledger is a prefix of `main`'s. The
D5501 check contexts are untouched (coordinate any change with #5500).

**Tests.** `scripts/lib/productionAdmission.test.mjs` has one fixture per
outcome: the tip, an ancestor inside the bound, more than 30 behind, more
than 6 hours behind, diverged or ahead, older than deployed, deployed version
unreadable, a compare read failure, and each of the six checks still failing.
