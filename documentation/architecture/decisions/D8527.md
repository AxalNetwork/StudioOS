## D8527 — A VentureSpace's settings follow the member's access while open: the browser test and the client fix (#8527)

- **Status:** built by S17, 2026-11-25 (#8527, row E3 of #8509).
- **Migration:** none.
- **Why:** the Worker re-checks access on every request (D8526), but nothing showed what a person *sees* when their access changes while the page is open. `ProjectSettingsPage` read the project once, on mount. A revoked member kept the settings they last saw until they reloaded, and a read that left before the change could arrive after it and paint the old view.

### 1. The client fix (`frontend/src/pages/team/ProjectSettingsPage.jsx`)

- **The next read.** The page reads again when the tab comes back, on `focus` or `visibilitychange` to visible. A member whose seat was revoked sees "You do not have access to it" (`data-testid="project-settings-no-access"`) with a link back to Portfolio, and the settings are gone.
- **A read carries the scope it was asked for:** its number, and the company selected when it left. Only the latest read, answering for the company still selected, is drawn. A late answer, an answer for a page that has unmounted, or one asked under another selection is dropped. So a response that left before a revocation, an archive, a move or an account switch never repaints the old view.
- **404 reads as no access.** D8526 answers someone with no relation to a venture as if it did not exist, so 403 and 404 both read as no access here, with no "Try again".

### 2. The browser test

`frontend/tests/visual/venturespace_stale_access_8527.spec.mjs` runs on the visual suite's local Worker (`server.ts`: the built SPA and the real Worker on SQLite), at 1440 and 390 px. `frontend/tests/e2e/` has no local Worker: its specs answer `/api/*` with fixtures, so a revocation could not be real there.

**The seed.** `_venturespace_seed.ts` seeds an isolated copy of three accounts for each scenario and width:

- A owns Northwind and Southwind and the venture;
- B is a Member of Northwind with a co-founder seat, and one data-room file;
- C has no access.

A acts through the real routes, in A's own browser context.

**The scenarios:**

| Scenario | What happens | What must hold |
|---|---|---|
| revoke | A removes B's seat | B's next read shows no access and the settings are gone. A write (a cap table proposal) and the data-room download B had open, both sent from B's open page with B's session and selection, are refused. |
| late | one of B's reads is answered before the revoke and held | B's next read shows no access. When the held answer is released, the old view does not come back. |
| archive | A archives Northwind | B's next read shows what the Worker now grants on the settings read, whatever company B selected. A revoke after it is shown on the next read. |
| move | A moves the venture to Southwind | the same |
| switch | in one context B signs out and C signs in | C sees no access and none of B's data. The selected company is cleared and the stored user is C. B's read still in flight is released into C's view and lands nowhere. |
| back | B opens Work, A removes the seat, B presses Back | the cached settings are not shown |

**Constraints:**

- Fixtures only: no production account, no email, and every request off 127.0.0.1 aborted.
- The spec is in the visual suite, which the `visual` job of `ci.yml` already runs. No new required check.

### 3. Where the issue's steps differ

- **The write and the download.** The settings page offers a co-founder no write and no download. For a company venture, `can_manage` comes from company authority, and B is a Member. So the write and the download are sent from B's open page, as the app sends them, and checked by their answers, not by text on the page.
- **Sign-out.** The switch scenario signs B out the way `App.jsx`'s `logout` does: it removes the same keys, the selected company included. It does not click the account menu, whose trigger differs between the desktop and phone shells.

### 4. Proof

- **The spec:** 6 pass at 1440 and 6 pass at 390, locally on the visual harness. The run used the session's pre-installed Chromium, not CI's pinned build.
- **Mutation check:** 2 client mutations, both caught.
  - Without the stale-answer guard, the late scenario fails: the old view comes back.
  - Without the focus re-read, revoke and late fail: the next read never happens.
- **Unit tests:** the page's existing unit tests pass (`team_page_d1497`, `settings_simplified_d4152`, `work_d1614`: 72).

### 5. After the first CI run

The visual job's first run on this PR failed the **back** scenario at 1440. Locally it then failed at both widths. The cause was the spec: Work is a lazy route, and React keeps the settings on screen while Work's chunk loads, with the URL already at `/work`. A Back pressed before Work is drawn therefore returns to a settings page that never left. The spec now waits for the Work page to be drawn before the revocation.

Two client changes came out of the same investigation. Neither was the cause of that failure:

- **An answer for a changed selection asks again.** The desktop header's `CompanySwitcher` sets the selected company after its own read, which can be after a settings read has left. Dropping that answer without asking again could leave the page on "Reading…". It now asks again under the selection held.
- **A page restored from the back-forward cache reads again** (`pageshow` with `persisted`). Back can restore a page whole, without a remount or a focus event.
