### 1. A policy is versioned configuration

`licence_agreement_policies` holds one row per **version** of a package's or program's policy. Two triggers make it append-only. A row holds:

- **`strategy`**: `per_program`, `package_master` or `none`. `package_master` is only for a package. `none` forces the gate to `optional`.
- **`legal_gate`**: `optional`, `required_before_grant` or `required_before_in_force`. The default is `required_before_in_force`, the issue's recommendation: a commercial grant may exist before signature, but it is in force only once executed.
- **For a package:** `programs_json`, the programs it includes. Under a master, also `required_schedules_json`: the included programs that need their own schedule (`package_addendum:<program>`) besides the master.

`POST /api/admin/licence-agreement-policies/:program|package/:key` writes version n+1. The version and its history line go in one batch, and a concurrent save that would take the same number loses whole (`UNIQUE (scope_kind, scope_key, version)`).

### 2. The version is frozen per licence

`licence_agreement_policy_holdings` records which version a licence holds:

- **A program** freezes its latest version in the grant's own batch, on a grant or a re-grant.
- **A package** freezes its latest version on `POST /licences/:uid/package-acceptances`. That endpoint stands in for #5021's offer acceptance until the package store exists, and #5021 calls the same statements.

A later policy version reaches **no** existing holder. The licence read answers `behind_latest` for each holding, so HQ can see who is behind without anything changing for them. A frozen holding cannot be edited (trigger). Its one write is being superseded, once, by a new acceptance. A licence holds at most one package (D5048, owner answer A).

Accepting the same package at the same version and offer again writes nothing. Accepting another package supersedes the old holding and records `replacement_required` for the old master (test 11).

### 3. What a program needs, and its legal status

`requirementFor` reads the licence's **frozen** holdings, never the current policy:

| Holding | Documents a program needs |
| --- | --- |
| The held package includes the program, `package_master` | `package_master`, executed **for that package**, plus `package_addendum:<program>` when the package lists it among its required schedules |
| `per_program` (the package's or the program's own) | `program_licence:<program>` |
| `none` | none |
| No holding | **not recorded**: nothing is inferred, and the D1120/D4805 schedule rule applies as before (test 12) |

On top of any strategy, the program schedule is still required whenever the grant's signed-schedule rule is on. It is read from `schedule_signed_at` (legacy and backfilled schedules included).

`programLegalStatus` answers one of these states:

- Not granted
- Draft
- Granted — agreement required
- Awaiting signature
- Granted — not in force yet (dates or licence)
- In force
- Paused
- Ended

The status also carries each required document: whether it gates, its executed and in-flight versions, and what is missing.

A required document that is not executed can never read as in force:

- `required_before_in_force` holds the program.
- `required_before_grant` also refuses the grant (409 `agreement_required_before_grant`, naming the missing documents). The schedule is not one of those documents, because it is built from the grant's terms.
- `optional` records the documents without gating.

### 4. Enforcement everywhere `in_force` is read

`presentGrant` gains one more thing a grant can wait on, `agreement_executed`. It applies when a row carries `legal_waiting = 1`. HQ computes that value (`legalWaitingByProgram`) and sets it in three places:

- **the branch copy:** `programCopy`, through the new copy column `legal_waiting`;
- **HQ's licence read:** `GET /api/admin/program-grants/licences/:uid`;
- **HQ's grid:** `GET /api/admin/program-grants`, including the in-force tile.

When an agreement executes, the completion hook records the gate's new answer and pushes the licence to its branch, so the branch's copy releases the program. A push that does not land is retried (D272).

### 5. Replacement, never mutation

`replacementsRequired` names two kinds of executed agreement, on read:

- an agreement drafted against grant terms revision R (`merge_values_json`'s `grant.revision`, D5049) when the grant has moved past R;
- a package master or addendum for a package the licence no longer holds.

The terms change and the package move each also record `replacement_required` in their own batch. This happens once per agreement and terms revision (a partial unique index), with the actor and the reason.

The executed row is **not** voided, superseded or edited for it (tests 8 and 9 compare its status, hashes and revision before and after). The replacement is a new draft of the same slot, which D5048 allows while the executed version stands. Drafting it records `replacement_prepared`. A person sends it, and it supersedes the old version only when it is executed. Nothing sends automatically.

**Unchanged on purpose:** the program **schedule** (D4805). A terms change still marks its executed schedule superseded, because the schedule *is* the terms. Its document, body hash and signed hash stay frozen (D5048's trigger), and the grant waits on an amendment, exactly as before.

### 6. History

`licence_legal_events` is append-only (two triggers). Its actions:

- `policy_versioned`
- `policy_frozen`
- `replacement_required`
- `replacement_prepared`
- `gate_satisfied`
- `gate_unsatisfied`

Each line carries the actor, the policy uid and version, the agreement uid and revision, the package or program, and the reason.

Gate lines are written only when the gate's answer changes, so a repeated sync adds nothing (test 13). They follow every grant write, an acceptance and both completion hooks. They are best effort: the write they follow has already committed.

The agreement lifecycle (prepared, sent, signed, voided, superseded) stays in `licence_agreement_events` (D5048). `GET /licences/:uid/history` merges both stores into one list, oldest first, each line with its agreement kind, slot, package or program, and template.
