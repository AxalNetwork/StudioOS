### What is decided

- **A reader whose audience is already the deal's audience reads in `transactional` mode.** D5454 §3 keeps an unlisted (withdrawn or archived) release for deal staff, the venture's owner and investors already related to it, and hides a private or unknown preparation from everyone. Each of these readers already narrows to that audience, so each drops `hiddenDealIds(env, 'transactional')`, bound as `d.id NOT IN (SELECT CAST(value AS INTEGER) FROM json_each(?))` before any `LIMIT`, and keeps the unlisted releases:
  - **Calendar deal picker.** Every row then passes `userMayReadDeal`: staff by licence, the venture's founder, or an invited or committed investor.
  - **Eadwyn CRM context.** The rows are the run company's own ventures' deals (`p.company_id = ?`, after `companyEnabled`), so the company reads them as the venture's owner. AI context is a discovery reader, and the owner is the one audience §3 lets see an unlisted release there.
  - **`scoreAccess`.** `mayReadProjectDeal` opens a venture to an investor only through a deal `userMayReadDeal` admits. `counterpartiesOf` pairs people on the same open deal. A private deal no longer opens a venture or makes a counterparty. A withdrawn release still does, between the parties already on it.
- **`private-data` reads like the deal list.** The same rule as `routes/deals.ts`'s `listMode`: staff by licence (`isDealStaff`) read `transactional`, and anyone else reads `discovery`, which also drops the unlisted releases. That covers a partner's own deals by `partner_id`, which an investor account linked to a partner record also reaches, and the admin totals.
- **What is kept.** Legacy deals with no preparation (owner answer Q1=A), an unreleased `legacy_attach` and a published release are unchanged in all four.
- **Failure.** A database that has not applied the migration hides nothing, which is the guard's own rule (`isMissingPreparationTable`). Any other guard failure, including the `HIDDEN_SET_MAX` bound, fails the reader closed:
  - the picker and `private-data` answer 500, with no list or total;
  - an Eadwyn reader throws, and `readForRun` drops that connector's lines;
  - `scoreAccess` throws, so no score is read.

  None of them falls back to an unfiltered read.
- **Cost.** One indexed statement per request. A trust-score batch is two statements in all, never one per id.
