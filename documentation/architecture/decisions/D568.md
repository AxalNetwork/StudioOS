## D568 — The Account center: the canvas's six sections on `/account`, each read from the route that serves it

**`/account` follows the Account center canvas (`ac-*` in
`design/incoming/Ops Page.dc.html`, rows in `ops-data.js`): a section list on
the left of the content, and Profile and identity, Notifications, Sign-in and
security, Billing and orders, Following, and Developer for the one role its
routes answer.** Issue #1174, Session 1. No route, client method or migration
was added; every section reads a method `frontend/src/lib/api.js` already had,
checked against its Worker route.

**The page was extended, not rebuilt.** `/account` and `/account/:section`
are still `pages/SettingsPage.jsx`. The canvas's zones are new components in
`pages/account/`, built on the `ui/` kit and the axal tokens the sidebar pages
use, and mounted at the top of the matching pane. What the old page held and
the canvas does not draw stays below them or under "More".

### What each section reads

- **Section list** (`AccountCenter.jsx`, `AccountSectionNav`). The canvas's six
  names in its order. The section ids did not change, so every deep link still
  lands (`/account/notifications` from the bell, `/settings/*` from mail). The
  four sections the canvas does not draw (Onboarding, Integrations,
  Appearance, Activity Log) follow under "More". Below `lg` the list is the
  canvas's phone row of chips, scrolling sideways; the old dropdown is gone.
  New aliases: `/account/following`, `/account/developer`, `/account/sign-in`,
  `/account/orders`. `/account/activity` now survives a reload.
- **Profile and identity** (`AccountProfile.jsx`). Five cards, five reads:
  - Personal details: the account name (root `GET /settings`, written with
    `updateSettings`), username and language (`getIdentitySettings` /
    `updateIdentitySettings`), phone and location (`getProfileDetails` /
    `updateProfileDetails`; the phone is write-only, the route serves its last
    four digits). A display name that differs from the account name is said.
  - Identity, "Used by Trust Center": legal name, date of birth and
    nationality from the identity route; tax residence from the details route.
  - Company profile: `getCorporateProfile` / `updateCorporateProfile`, four of
    the corporate profile's fields, with the canvas's empty state when the
    route holds no row.
  - Public archetype: the newest profile snapshot for the role's persona
    (`profileHistory`, label from `assessmentMeta`, confidence as a
    percentage), and the publish switch (`archetypePublished` /
    `setArchetypePublished`).
  - Change history: one line per snapshot (`profileHistory`) and "Ask me
    again" (`profileReask`), which lists the answers due again and links to
    Studio, where they are asked. The route is a read-only peek; nothing is
    marked asked from this page, and the card says so.

  Each editable card opens a form, sends only the changed fields to the route
  that owns each one, and shows the route's refusal on the field it names. The
  editors below the cards (Personal / Corporate / Verification and the rest)
  stay. They edit some of the same fields, so a save on either side tells the
  other (`axal:profile_saved`, and the editors remount after a card saves).
- **Notifications.** The type × channel matrix is the page's existing one,
  extended in place. It now reads and writes its own route
  (`getNotificationPrefs` / `putNotificationPrefs`) instead of the copy in the
  root payload. Its columns are the canvas's: In-app, Email, Push, plus Slack
  once Slack is connected. Presets, the D333 locks and the partner block are
  unchanged. Below it, Devices registered for push (`AccountDevices.jsx`,
  `pushSubscriptions`).
- **Sign-in and security.** The canvas's factor rows are the existing
  `SignInFactorsCard`, now with the SMS row. That row reads
  `getSecuritySettings`, the pane's one read, passed down so the card still
  fetches nothing. Each row has a button that scrolls to its flow. Order:
  factors, authenticator setup, SMS number, then the new Sessions and alerts
  card (active session count from `getSecuritySettings`, and "Sign out
  everywhere" through `signOutEverywhere`, confirmed in place). Google
  sign-in, recovery codes, passkeys, trusted contacts, the recovery log and the
  per-device session list follow, kept. The privacy cards stay on this pane
  under a "Privacy" label: the Worker's cohort-access notice links
  `/account/security-privacy` to one of them.
- **Billing and orders** (`AccountBilling.jsx`). The plan line reads the
  role's own status route (`tierStatus`, `investorBillingStatus` or
  `planStatus`). It shows the tier, the seats for an investor, the renewal, and
  the subscribed tier when it differs from the one that applies. "Manage
  billing" opens the URL `tierPortal` or `investorPortal` returns; with no
  billing account it is disabled and says why. Orders: `myOrders`, with search,
  Status and Year chips, newest or oldest first, and an invoice on a paid
  order. The plan is read once and handed to the role's panel below, whose own
  "Current plan" card the line replaces.
- **Following** (`AccountFollowing.jsx`). `followsMine`, people and startups
  linked to their public profiles. Unfollow is `unfollow` (DELETE
  `/follows`). An unfollowed row stays with Undo (`follow`), so no
  confirmation box is needed for a step this easy to take back.
- **Developer** (`AccountDeveloper.jsx`). Admin only. `GET/PUT
  /settings/developer` and the re-sync route answer 403 to every other role,
  and no per-account developer-mode flag exists, so the admin role is the
  switch. The section is listed for admins, `/account/developer` is guarded
  `['admin']` in `App.jsx`, and a 403 hides the section. It holds the stored
  feature flags (`updateDeveloperSettings`), the account row the route serves,
  and "Re-sync search indexes" (`resyncDeveloperIndices`), showing the route's
  message and the time this page sent the request.

**The Worker AI rail** is mounted beside the page as on Send for signature: a
`--fwr-track` column, `role="founder"` as a literal (the canvas draws the page
in violet for every role). Its coverage lines are counts and states, never the
email address.

### Where this departs from the canvas, and why

- **The brief's SMS and authenticator methods are the sign-in page's, not this
  page's.** `smsStartChallenge` / `smsVerifyChallenge` are the unauthenticated
  login challenge, and verify-challenge mints a new session over the current
  one. `setupTotp` needs the one-shot email verification token; without it the
  route refuses ("Invalid setup token."). `verifyTotp` only checks a code. The
  page keeps the signed-in enrolment it already had:
  - `TotpEnrollment` (`/settings/totp/enrol/*`): scan, a 6-digit code, then
    recovery codes shown once, which are the canvas's three steps.
  - `SmsPanel` (`/auth/sms/{start,confirm}-enrollment`).
  - `authFactors` is the login page's email-keyed discovery, rate-limited per
    IP. The factor rows read `getSecuritySettings`, which holds the same facts
    for the session's own account.
- **One "Sign out everywhere".** The Active sessions card's revoke-all button
  (`revokeAllSessions`, behind `window.confirm`) moved into the canvas's card
  as `signOutEverywhere`. It is the same `jwt_min_iat` bump.
- **An unset notification switch is drawn on.** `resolveChannels` in
  `services/notify.ts` delivers a channel unless the stored value is exactly
  `false`, so the old `!!prefs[type][channel]` showed a new account every
  switch off while every notification was sent. `channelOn` is the Worker's
  rule. D333's test pins the new line.
- **Push is not a switch.** notify.ts pushes to registered devices whenever it
  writes the in-app row. There is no push channel in `notification_prefs`, so
  the Push column says, per type, whether the in-app row (and so the push) is
  on. The reserved "SMS · Coming soon" column is gone: notify.ts has no SMS
  channel.
- **A device is removed only from itself.** `GET /push/subscriptions` returns
  ids, and the route's remove (`POST /push/unsubscribe`) takes the endpoint,
  which only the subscribed browser knows. So "Remove" (confirmed) is offered
  for this browser through `disablePush()`, and the card says how another
  device is removed. "Turn on push here" uses `enablePush()`. "Last seen" is
  drawn as "last push delivered", the date the store keeps.
- **"Recent" sort on Following is by name.** The route returns no follow dates
  and re-reads the rows by id, so their order is not the follow order.
- **Two-column zones follow the pane, not the window.** The canvas's 2-column
  grids are container queries (`@2xl`), so they open when the pane is wide
  enough (a wide window, or the rail collapsed). Below that the cards stack, as
  the canvas's phone rule stacks them. The orders table and the notification
  matrix collapse to two-up rows the same way.
- **Sections are path segments, not the canvas's `#anchors`.** The bell and
  mail already link `/account/<section>`.
- **Fixes on the same pane**, because the new cards would otherwise contradict
  them:
  - The profile-slug hint said "Becomes /u/<slug>" and allowed 2–40
    characters. `/u/:handle` reads the account id, and the Worker takes 3 to 32.
  - `/account#security-recovery-codes`, where account recovery sends the
    reader, named no element. It now opens the sign-in pane at that card.
  - The founder billing panel fell back to `subscription_*` fields the root
    payload does not carry, so a failed read drew the Free ladder. A failed
    plan read now says so once, on the plan line.

### GAPS — drawn "Not recorded" with a reason, and the route that should serve each

| Canvas field | Why it is not drawn | Route that should return it |
| --- | --- | --- |
| Bio draft (rail proposal) | nothing drafts a bio | a `DRAFT_SURFACES` entry over role, company and sectors |
| Username as the public address | `profile_slug` is stored and resolved by nothing | `GET /public/u/:handle` resolving a slug |
| "[n] questions" in a history line | a snapshot does not record its answer count | `GET /profile/history` carrying the count per snapshot |
| Device "last seen" | only `last_sent_at` is stored | `GET /notifications/push/subscriptions` with a last-seen stamp |
| Remove another device | the list has no endpoint and remove takes one | `DELETE /notifications/push/subscriptions/:id` |
| Push per type | push follows in-app; no push key in prefs | `notification_prefs[type].push`, honoured in notify.ts |
| Session length | one platform length, nothing per account | `GET /settings/security` (and a writer) |
| New-device alerts | no setting; `auth_signin_new_device` is never sent | `GET /settings/security` plus a sender |
| Refunded order | `OrderStatus` is pending, paid or failed | `GET /orders/mine` with a refund state |
| Follow date ("since") | selected by the route, not returned | `GET /follows/mine` returning `created_at` |
| API key, webhook URL, rate limit | no key store (D433, T20), no per-account webhook or limit | `GET /settings/developer` |
| Search indexes "last run" | the re-sync route logs a request and returns no run | `GET /settings/developer` returning the last run |

And one read that cannot fail honestly: `GET /notifications/prefs` answers
`{ prefs: {} }` when its query throws, which this page must read as "every
switch on". The route should answer 503.

### How it was verified

- `frontend/test/account_center_d568.test.mjs`, 38 tests:
  - Each card renders in its loading, empty, "Not recorded" and unreadable
    states, from fixtures in the routes' own shapes.
  - The model functions are tested directly.
  - The page and the route wiring are pinned, with each fixture field checked
    against the Worker source.
  - Every client method is checked against its path and verb with a stubbed
    `fetch`.
  - The file runs in `America/Los_Angeles`, where a date of birth formatted as
    an instant would read a day early.
- Every new assertion was mutation-checked: 66 source mutations, each turning
  the file red, then restored. The matrix sits in `SettingsPage.jsx`, which
  cannot be imported under node (`lib/stripe.js` reads `import.meta.env` at
  load), so its states are pinned in its source.
- Re-pointed: `account_d433` (the page now ends at `function Card(`),
  `company_settings_members` (the grid and presets share `savePrefs`) and
  `settings_notification_locks_d333` (the default-on line). Each was checked
  with mutations of its own.
- The built SPA was served against fixture routes and driven in headless
  Chromium at 1440px and 390px, with no horizontal overflow. The checked
  writes:
  - a city edit sends only `PUT /settings/profile/details {"city":"Bern"}`;
  - a switch sends the whole prefs object, keeping the stored opt-out;
  - "Sign out everywhere" asks before it posts;
  - Unfollow sends `DELETE /follows` and leaves Undo.
