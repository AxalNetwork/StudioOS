### 1. O-CRD: what pays, and when

The owner answered O-CRD with **A** on #2798 (2026-10-26), the canvas's figures:

| Rule | Category | Credits | Paid on the move to |
| --- | --- | --- | --- |
| `referral:startup_accepted` | Startup / founder | 100 | Converted ("on acceptance") |
| `referral:startup_formed` | Startup / founder | 400 | Reward issued ("on formation") |
| `referral:customer_onboarded` | Platform user | 50 | Reward issued ("once onboarded") |

- **Strategic introductions** are agreed case by case and have no rule.
- **Partner referrers** are not paid perk credits. Their referrals still move, and the save says no credits were paid.
- **The value:** one credit is US$1 (`usd_value_cents` = credits × 100).
- **Where the amounts live:** in `credit_reward_rules`. The Super Admin edits each one in Credit rules, with a reason, like every other rule. The code names only the rule, its category and the status that pays it (`REFERRAL_REWARD_RULES` in `services/referralSubmissions.ts`).
- **The key prefix:** every key starts `referral:`. `ruleKind` reads each as a `reward`.
- **Reward issued is final** (D957's allowed moves), so no later move takes a paid reward back. A revoke stays the Super Admin's (`POST /api/admin/credit-rules/grants/:id/revoke`).
- **A referral that was already at Converted before 566** was not paid on acceptance. It is paid on formation only. Nothing back-pays it.

### 2. The review pays the reward

`reviewSubmission` runs in this order:
1. D957's allowed-move check.
2. `payReferralReward`.
3. The move.

`payReferralReward` calls `grantCredits` for the referrer, with:
- **the rule:** the one the category pays at the new status;
- **the source:** `referral:<uid>:<rule key>`, so each submission pays each rule once;
- **the actor:** the reviewing admin. The grant writes its own audit row and sends the referrer's inbox notice. `ruleReason` gives each rule a sentence, and the ledger names a `referral:` source "Referral reward".

A retry after a failed move reads `already_granted` and pays nothing twice.

**What each result does:**

| `grantCredits` answers | The move | The PATCH's `reward` |
| --- | --- | --- |
| `granted`, or `already_granted` | goes ahead | `{ rule_key, paid: true, credits, ledger_id }` |
| `rule_inactive`: HQ switched the reward off | goes ahead, unpaid | `{ rule_key, paid: false, code: 'rule_inactive' }` |
| `not_eligible`: a partner or admin referrer (O-CRD A) | goes ahead, unpaid | `{ rule_key, paid: false, code: 'not_eligible' }` |
| anything else (`rule_unknown`, `user_not_found`, …) | refused: 409 `reward_not_paid`, carrying the code. Nothing is written. | — |
| the move pays no rule | goes ahead | `null` |

**A departure from #2798's text.** The issue had a partner's referral refused at its paying status, unless O-CRD paid partners. O-CRD A keeps partners unpaid and lets their referrals move, so `not_eligible` is the second refusal that lets a move through.

`reward_label` stays the reviewer's free text.

### 3. The reads

- **`GET /api/refer-earn/admin/rewards`** (`requireAdmin`):
  - **`rules`:** each rule's key, category, `pays_at`, `when`, `credits` and `active`. A rule with no row reads `credits: null`, off. Every admin gets this, because the member page states the same amounts.
  - **`paid`:** `{ grants, credits, by_rule }` over `referral:` grants that were not later revoked, by `CAP_USED_SQL`'s revoke test. Only a Super Admin gets it, since it is a cross-member credit figure (D953 §2, O-MONEY); an Admin gets `null`.
  - **Failures:** the rule test is `substr(key, 1, 9) = 'referral:'`, never LIKE. A D1 failure is a 5xx, never zeros.
- **`GET /api/refer-earn/overview`:**
  - Each category carries `rewards`: one entry per rule that is on, with `rule_key`, `credits`, `pays_at` and `when`. A category with every rule off, or none, serves an empty list.
  - `reward` is built from those rules ("100 perk credits on acceptance, and 400 perk credits on formation."), or reads "No perk credits are paid for this kind of referral now."
  - If the rules cannot be read, `rewards` is `null`, and the line says the reward could not be read rather than promising one.

### 4. The pages

- **Rewards issued tile** (`ReferRewards.jsx`, mounted by Refer & Earn's Overview):
  - **The count:** referrals at Reward issued, from part 4's exact paged total.
  - **Credits paid:** shown to a Super Admin. An Admin reads "Credits paid: Not read here yet. HQ reads these figures."
  - **A line under both:** the count includes rewards settled off the platform, so the two figures are not read as one.
  - Perk credits and introduction credits are never summed.
- **Rewards card:**
  - **Each category's rules:** "[n] credits on acceptance", "Off on formation" with "HQ has switched this reward off.", "Not recorded" for a rule with no row, and "Agreed case by case" for strategic.
  - **Open Perks** for everyone.
  - **For an Admin:** the lock and the foot "Credits are spent on Perks. HQ sets the rewards."
  - **For a Super Admin:** Edit in Credit rules (`/admin/credit-rules`).
  - Both doors are literal `to`s, credited to `ReferAndEarn.jsx` in the reachability test's `COMPOSED`.
  - Each block draws its own Reading…, Unreadable with Try again, and figure.
- **The Queue's save** shows what the move paid, under the result line:
  - "100 credits paid to the referrer.";
  - "No credits paid: HQ has switched this reward off.";
  - "No credits paid: partner and admin accounts do not earn perk credits.";
  - `reward_not_paid` reads "The referrer's reward could not be paid, so the referral did not move. Nothing was saved."
- **The credit sentences:**
  - **Refer & Earn's How it runs (Rewards)** says what pays and when, with no amount: HQ can change the amounts, and the Rewards card shows them. It names the partner rule and keeps the introduction credit named as such.
  - **The catalogue card's purpose** says members earn perk credits.
  - **Migration 566** writes the same words into the registry and both playbook versions (the draft and the seeded version 1), only where each still holds part 1's seed word for word, so an HQ edit is never overwritten.
  - **The catalogue's Credits in and out** shows a Referrals source once a `referral:` rule exists (D961). It needs no change here.
- **The member page (`/referrals`):**
  - The reward matrix and each category's reward line come from the overview's rules. A category with no rule on reads "No perk credits now", and an unread overview promises nothing.
  - The hard-coded "Milestone-based" and "Platform credit" rows are gone.
  - The FAQ says what pays without an amount.
