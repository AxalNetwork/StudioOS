## D9204 — Batch cohort reads and portfolio chase requests (#9204)

The cohort timeline prepares its three child queries once and submits one D1
batch for the selected cycles. Review batches participant reads, deduplicates
their user IDs and batches milestone reads. Applications batches each kind of
read across the selected cycles, preserving the pending-first order and the
200-applicant limit for each cycle. Optional lifecycle, interview and Week 1
plan reads remain independent so missing optional tables do not hide applicants.

Portfolio chase fetches all visible target projects and recent chases in two
bound bulk queries. Eligibility uses prepared templates in three read batches,
preserving caller-book scoping, cadence, submitted-period matching, due-day
normalization by SQLite and fail-closed refusals. New chase records commit in
one write batch; only then are founders notified, with failures still best-effort.
Input ordering, the 100-target cap and the one-hour repeat response are retained.
Notification delivery remains per recipient; its own work is not counted as
chase preparation in the synthetic no-recipient query-count fixture.

The SQLite D1 test adapter now returns batched SELECT results and keeps bound
statements independent, as D1 does. Counting tests compare one versus twelve
cycles and one versus twenty targets, exercise review and application batches,
check optional-read degradation and prove an insert refusal rolls back all
chases before any notification. Existing route assertions are retained; the
decision-race harness attaches its barrier to the bound statement to follow
the adapter's immutable binding behavior.

No schema, binding, public API shape, authorization or deployment change is
required. Rollback is the route/helper revert; there is no data migration.
