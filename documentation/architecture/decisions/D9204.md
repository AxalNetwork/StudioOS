## D9204 — Bulk cohort reads and portfolio chase requests (#9204)

The cohort timeline loads windows, participant counts and status counts with
one bound bulk query per kind. Review loads participants for the current
cycles, then reads milestones for their distinct user IDs. Applications loads
each kind across the selected cycles and groups locally; a partitioned row
number preserves the pending-first order and 200-applicant limit per cycle.
Lifecycle, interview and Week 1 plan reads retain independent optional-table
fallbacks. Internal cycle/rank keys are removed from response child rows.

Portfolio chase bulk-loads visible target projects and eligible targets' recent
chases. Eligibility bulk reads preserve caller-book scoping, cadence,
submitted-period matching, SQLite due-day normalization and fail-closed
refusals. Targets already known not to be held keep their no-obligation reason
if a later read fails. Ineligible targets never need to read the chase log.
New records use one bound JSON-backed INSERT submitted through one D1 write
batch; only then are founders notified, with failures still best-effort.
Input order, the 100-target cap and the one-hour repeat response are retained.
Notification delivery remains per recipient; its own work is not counted as
chase preparation in the synthetic no-recipient query-count fixture.

Counting SQLite-backed D1 tests compare one versus twelve cycles and one versus
twenty targets, exercise review and per-cycle application isolation/limits,
check optional-read degradation and prove an insert refusal rolls back all
chases before notifications. Existing route tests and the D1 adapter are
unchanged. Coverage is recorded here because #8875 owns the test catalog.

No schema, binding, public API shape, authorization or deployment change is
required. Rollback is the route/helper revert; there is no data migration.
