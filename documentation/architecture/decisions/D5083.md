## D5083 — HQ › Revenue: Receivables apart from Billing exceptions, no Draw while D514 holds it, one-line empty states (#5083)

- **Status:** built 2026-11-12 (#5083, parent #5039). Frontend only. No route, no migration.
- **Number:** D5083 is the issue's number (D4106).
- **Builds on:** D5039 parts 1 and 2 (#5111: the cockpit, Receivables and the statement drawer, Billing exceptions as RV08; #5166: the drawer's governed Record a payment, Mark issued and Void), D514 (statement drawing held), D5037 (the refund is looked up and reviewed before money moves).

### What was already on `main`

Most of #5083 had landed with #5039's slices, so this change starts from a check of each acceptance box against `main`:

- **Receivables and Billing exceptions are separate sections.** #5111 replaced "Statements and Stripe" with `revenue/Receivables.jsx` (RV05) and `revenue/BillingExceptions.jsx` (RV08).
- **The governed edits live in the row's drawer.** #5166 added `POST /api/admin/statements/:uid/issue`, `/payments` and `/void` in `routes/admin_statements.ts`, with a reason, `expected_revision`, an idempotency key, the step-up for payment and void, and audit rows; plus the drawer flows in `revenue/StatementActionFlow.jsx`. No route was missing, so none was added here.
- **No Draw action.** The page offers none. `StatementDrawHeld` is the canvas's compact policy state ("Statement creation · policy decision required", then one sentence), with no button, link or form.
- **LTV and token margin per branch** left Billing exceptions in #5111. Customer lifetime value is on HQ › Revenue › Billing (`BillingConsole`). The per-branch AI margin is not measured (U1), and Subsidiaries says so in one line.
- **Complete, floor, estimated and void** keep D514's meaning in `revenueModel.js` and `statementActionModel.js`. This change does not touch them.
- **Refund execution** is `RefundReviewFlow` (D5037), folded inside Billing exceptions. This change does not touch it.

### What this change does

- **The empty states are one operator line.** The fuller explanation is in the counts' temporal labels and the Data coverage drawer.
  - Receivables with no statement: "No statements yet" (it used to say "No statement has been drawn.").
  - Streams for a period with no statement: "No Q4 2026 statements yet" (it used to say "None drawn for Q4 2026").
  - Billing exceptions with both reads answered and nothing open: "No billing exceptions". It used to be a sentence naming the refund window and Stripe; both still show on the counts above it ("Open disputes · Live · Zero", "Refunds through HQ · Last 30 days · Zero").
- **A status chip with no rows says so.** Choosing a filter with no statements behind it (for example Void 0) used to leave the section blank under the chips. It now says "No void statements".
- **The page no longer scrolls sideways on a phone.** At 390px it was 851px wide. Each table's visually hidden state words (`sr-only`, `position: absolute`) escaped their scroll wrapper, because no wrapper was positioned. Each `overflow-x-auto` wrapper in `pages/hq/revenue/` is now `relative`, and the tables still scroll inside their cards. The browser check found this, and a source test now holds it.
- **The interaction tests run on the whole mounted page.** `frontend/test/hq_revenue_receivables_5083.test.mjs` mounts `RevenuePage` with `fetch` answered per address. It holds:
  - the two sections apart;
  - no Draw control anywhere, before and after a statement is opened;
  - one Open control per row, and no edit until the drawer opens;
  - each governed edit sending one request to its mounted route, with a deferred reply;
  - the in-flight state: Authenticate for a payment and a void, a disabled "Sending…" for Mark issued, and the drawer held open;
  - a refusal drawn as a refusal with no re-read;
  - a 503 drawn as Outcome unknown, never as success;
  - the empty-state lines.

### Departures, each on purpose

- **The policy state keeps the canvas wording.** RV05 heads it "Statement creation · policy decision required", and #5039's tests pin that wording. The issue's "Statement creation disabled" is an alternative, not a requirement.
- **Billing exceptions still has no incomplete-subscription, failed-reconciliation or policy-override row.** The issue lists these as kinds of exception. None of them has a read today. The only incomplete-subscription source is a reconciliation POST (D5039 part 1), and refund policy overrides live on the Billing tab. A row needs a read first, and that work is Worker-first.
- **`RefundForm` is still exported from `BillingExceptions.jsx`,** although nothing mounts it. Removing it is item 1 of #5039's remaining list (S25), so it is left alone here.
