## D6281 — Evidence Library: search, drop-to-upload, filters kept in the URL (#6281)

- **Status:** built (frontend only). Part of #3701.
- **Canvas:** `design/incoming/Research v2 Page.dc.html` and `Research v2 · Boards.dc.html`, board RS-06 (Evidence Library) and RS-10C (phone).
- **Builds on:** D3701 part 1 (the two state columns), D549 (collections), D4612 (indexing).
- **Worker:** no change. Every filter narrows the list `GET /api/research/documents` already returned. There is no new route, no migration and no API method.

D3701 part 1 recorded the rest of RS-06 as departures, with no follow-up. This builds four of them.

### What is built

1. **Search documents.** This comes from board RS-06, not D3701, whose departure list does not mention it.
   - It narrows by title, ignoring case.
   - A search or filter that leaves nothing shows **No document matches**, with **Clear**. It never shows an empty table, which would read like an empty library.
   - When the chosen collection could not be read, the card says so, rather than claiming nothing matches.
2. **The four filters**, each a query parameter. From D3701's "filters stay the zone's existing chips" departure.
   - **Type** (`type`): the file type, from the stored `content_type`. It is PDF, Word, PowerPoint, Text, Markdown or CSV. A document with no type recorded is Not recorded, never PDF. This is not the document's kind, which keeps its own column (D3701 "Library columns").
   - **Index state** (`index`): the indexer's word, from `researchStates.js`'s `INDEX_STATE`.
   - **Answerable in Ask** (`answerable`): read from `answerabilityOf`, so it uses the Worker's `in_ask`. A client's indexed document therefore filters as Not answerable, as its column reads.
   - **Collection** (`collection`): the D549 collection. The same parameter drives the collection manager's own selector, so the two always agree.
   - Only types and states that some document carries are offered.
3. **Kept in the URL.**
   - The search, the four filters and the profile's chip view (`view`) are query parameters. A reload or Back therefore lands on the same list.
   - They are written in place (`replace`), so typing a search does not add a history entry per letter.
   - Other parameters in the URL are kept.
4. **Drop to upload.** From board RS-06's "Drop files here".
   - A dropped file goes through the same `sendFile` as the form, with the kind and title chosen there.
   - Before anything is sent, `uploadRefusal` applies the Worker's own two rules (`routes/research.ts` `ALLOWED_MIME` and `MAX_BYTES`) and says why it refuses: the type cannot be read, or the file is over 20 MB.
   - A file whose type the browser could not name is refused too, because the Worker reads only the type.
   - Dropping several files at once adds none and says so.
5. **Upload document is the header's primary action.** From D3701's header departure. It opens the same file picker as the upload card, so there is still one upload path.

The phone cards (RS-10C) are unchanged. At 390px the filters stack in one column, and the header button and Clear are 44px.

### Departures

- **The collection filter is labelled "In collection".** The collection manager below already has a selector labelled "Collection", and two controls with one name confuse a screen reader. Both read and write the same `collection` parameter.
- **The profile chips stay.** Every licence keeps its artboard's view chips (`*ZoneFilters.js`), now kept in the URL as `view`. The dropdowns sit beside them. They do not replace them.
- **The toolbar's Upload and Add document stay.** These are the profile artboards' ops (`*ZoneActions.js`). They call the same picker as the header button, so no table changed.
- **Ask Eadwyn in the header** is still not built. It is not part of #6281.
- **Excel** appears in the canvas's drop line but is not accepted. The Worker refuses it, so the drop line lists the types it accepts.
