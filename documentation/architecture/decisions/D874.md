## D874 — The call tools on Axal's MCP server: list_meetings, get_meeting_transcript, summarize_meeting

- **Status:** S13, 2026-10-22 (#2521, part of #2516). The owner moved the task from S10 to S13. **PR 1 of 2.** No migration.
  - **PR 1 (this one):** `list_meetings`, `get_meeting_transcript` and `summarize_meeting`.
  - **PR 2:** `extract_action_items`. It runs M4's extraction (#2520 PR 2), which follows D859 (#2504). Until both land, it is not registered.
- **Basis:**
  - `origin/main` at `b29e50bd`;
  - D684's call import (`services/channels/zoom.ts`, `googleMeet.ts`, `meetings.ts`), D757's engine, D846's registry and `callTool`, D844's metering, and D864's channel tools (the module pattern, #2527);
  - the owner's ruling on #2510 (Q1 B), which #2521 follows for call transcripts.

### 1. What was decided

1. **Three tools in `mcp/tools/meetings.ts`**, registered beside D864's:

| Tool | Scope | What it returns |
| --- | --- | --- |
| `list_meetings` | `validate:read`, read-only | The member's calls: state, `source`, provider, times, company, interview, and the session the transcript is in. Filters by provider and state; limit 1–200. |
| `get_meeting_transcript` | `validate:read`, read-only | The call's stored transcript, in pages. |
| `summarize_meeting` | `validate:write` | The engine's summary of the call, read or run. |

2. **Tenancy comes from the ref.** `interview_channel_refs` fixes a call's member, interview and session when the call is scheduled or attached; nothing a provider sends changes them.
   - A call is read only when the ref is the member's, on an interview in a company the grant still reaches.
   - `list_meetings` filters in SQL, so its limit counts only what the call may see.
   - Any other call is `404 meeting_not_found`, the same answer as for a call that does not exist.
3. **Where the transcript lives.**
   - A scheduled call's transcript is in the session opened with the provider.
   - A call attached to a recording has its own session beside the recording (`meeting:<ref uid>`, as `meetings.ts` opens it). `session_id` names that session, never the recording's.
   - `source` is `attached` when the ref has no `ends_at`, which is how the attach route writes it, and `scheduled` otherwise.
4. **The transcript follows the owner's ruling B on #2510.**
   - It returns the stored **final** segments of an imported call whose session consent is `given`, with speaker labels, times, and D857's translation beside the original when one is stored.
   - Each translation is decrypted with the per-column cipher, bound to its segment; one that is absent or unreadable is `null`, never ciphertext.
   - The ref's state and the session's consent are checked again inside the segment query, so a withdrawal or cancellation during the read exports nothing.
   - A call that is not imported, or not consented, returns `transcript: null` with the reason in Axal's words.
   - Pages hold up to 200 segments (100 by default), with `next_after_id` and `complete`. A cursor from another call is `400 invalid_transcript_cursor`.
5. **Nothing identifying leaves.** A join URL, meeting id, Meet code, passcode or provider token is never a field. In the transcript text and in the summary, these are removed:
   - links;
   - phone numbers (seven digits or more);
   - credential-shaped values and passcodes;
   - the call's own meeting id and Meet code.

   Instructions in the text stay as data in the result; they never reach a description.
6. **The summary.**
   - `summarize_meeting` returns the stored draft (`summaryOf` and `sessionDigest`, the session page's own view).
   - When none is stored, or `rerun` is true, it runs `digestSession` with `trigger: 'manual', stages: ['summarise'], force: true`, exactly as the Summarise button does. The engine checks consent; a declined call is refused and records nothing.
   - The ledger's refusals reach the client as D844's metering refusal, so the usage row's category is `insufficient_tokens`. Other refusals keep the engine's own sentence.
7. **Metering.**
   - The three tools are priced 0 in `METERING_POLICY`. The two reads use no AI.
   - The summary's model run holds and settles its own AI tokens through `aiRouter` (D640). By D844's composite rule, a tool fee on top would charge the same call twice.
   - The test pins this: one summary is one hold, settled; a second read runs nothing and holds nothing.

### 2. Where it differs from the issue's text

- **The transcript is the full stored text.** The issue's scope, written before the ruling, says "the structured transcript view, not the full text". The owner's later ruling on #2510, relayed on #2521, governs.
- **The redaction lives in this module** (`exportText`). #2534 (D864's ruling-B follow-up) has the same rule for chats, in `channels.ts`, which that open PR owns. The two can share one helper once both are on `main`.

### 3. Not built here

- **`extract_action_items`.** PR 2 adds it once M4's extraction exists: `decision` and `action_item` proposals, through D859's extraction. Like the summary, it will hold AI tokens through `aiRouter` and return the proposals it created, never accepted items.
- **Uploaded calls (M3, #2519).** They are sessions with no ref, so `list_meetings` does not list them. Reaching them through MCP is a later decision.

### 4. Verified

- **`test/meeting_mcp_tools_d874.test.ts`** (10 tests) drives the real `callTool` on D684's channel world, with calls imported through `importMeetingRef`. It covers:
  - the scope gates and the listing per scope;
  - only the member's own calls, in the grant's companies, and the filters;
  - another member's call, or another company's, answering 404;
  - the transcript's final-only, consented, imported gate, and withdrawal or cancellation mid-read;
  - pages and cursors;
  - redaction, including a Meet code, and the stored translation;
  - the summary held and settled once, a second read running nothing, and `rerun`;
  - the ledger's refusal leaving no hold;
  - usage rows.
- **Mutation check:** every mutation of the module (36) is caught by the tests.
- **Pinned lists:** the tool lists pinned in `mcp_server_d666`, `mcp_authorization_d669` and `mcp_registry_d846` name the three tools.
