### Prepared experiment

`runner-benchmark.yml` runs only on a push to `bench/runners-**`, with
`contents: read`, no secret references and no PR/dispatch trigger. The matrix
uses the merged suite's nine derived parts, its exact steps and 40-minute
part limit. A 27-job matrix limit lets all three nine-part lanes become
eligible together, avoiding a nine-job workflow throttle that would queue one
lane behind another. This is not an account-cap reading. It does not change `ci.yml`, shard counts or required checks.
`#5609` remains a pending suite-planner dependency: reconcile the copied steps
when it merges; the parity test refuses a silent difference.

The free lane is the only default. Paid lanes require the owner to verify a
spending cap and set `RUNNER_BENCHMARK_SPENDING_CAP_VERIFIED=true`, plus the
relevant `RUNNER_BENCHMARK_GITHUB8_READY` or
`RUNNER_BENCHMARK_EPHEMERAL_READY` to exactly `true`. Readiness means all owner
steps are complete, including repository-only app access, public runner-group
access, the selected runner and an account-level spend cap. These flags attest
to billing controls; they do not implement a billing cap themselves. The 8-core
runner must have the owner-created label `studioos-bench-linux-8`.
GitHub larger runners were not selected by the current owner answer, so leave
that flag off. No app, runner, plan, billing or repository setting was changed.

Run the same candidate three times on uniquely named benchmark branches only
after the owner posts the actual plan/cap and no queue backpressure alert is open. Retain run links, SHA, attempt and the report from
`node scripts/runner-benchmark-report.mjs <run id>` from that tested candidate
checkout: part coverage is compared with its part definition. Compare only successful,
complete part sets (`comparable: true`); failures retain their incurred cost and are not successes.
The report uses #5603's `runnerWait`, rounds each measured job's duration up
to a whole minute for cost, and exposes missing timing/price as unavailable.
Lane wall includes wait from earliest suite-job creation to last completion;
the free planning job is excluded. Historical prices do not prove invoice totals.

### Verify-first evidence, checked 12 November 2026

- [GitHub push events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push)
  use the pushed ref and commit; a push workflow can live on the benchmark
  branch. This is documented support, not a hosted rehearsal in this session.
- [GitHub runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing):
  Linux x64 8-core **$0.022/min**, 4-core $0.012/min; larger runners require
  Team/Enterprise Cloud and are billed even on public repositories. The public
  standard lane is [free](https://docs.github.com/en/billing/concepts/product-billing/github-actions).
- [WarpBuild cloud runners](https://www.warpbuild.com/docs/ci/cloud-runners):
  `warp-ubuntu-latest-x64-4x`, Ubuntu 24.04, 4 vCPU/16GB, **$0.008/min**.
  Per-job VMs are allocated fresh and destroyed afterward; GA Linux/Windows
  advertise unlimited concurrency. This is a vendor statement, not a measured
  account entitlement or reserved-capacity guarantee. The issue's earlier
  $0.002–0.004 estimate is not used.
- [WarpBuild public-repo setup](https://www.warpbuild.com/docs/ci/public-repos)
  registers in the organization's Default runner group and requires enabling
  public-repository access. Install on this repository only; no fork-PR jobs.
  Cold-start latency is **Not recorded**: no actual provider job was run, and
  no startup SLA was established by the retrieved docs.
