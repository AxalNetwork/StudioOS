## D8467 — A Worker test file may replay the migration chain twice at most (#8467)

Every Worker test process now counts the whole migration files it executes. Two chains' worth is allowed: one
build of the schema, and as much again for cuts of it or for re-running a migration to test that it replays
safely. Each one past that throws and names the helper that builds the schema once. The rule is
`cloudflare-worker/test/_schema_budget.mjs`, loaded by `_ts-loader.mjs`.

This is the part of #8437 (make the heaviest Worker test files cheaper) that the per-file tasks do not cover:
it stops the cost from coming back.

### 1. What was measured

Measured on 2026-11-24, on `main` at `d4e7a3245b`.

| Fact | Figure |
| --- | --- |
| Migrations above the cutoff (`BASELINE_CUTOFF` is 219) | 768 |
| One full build on this session's machine | 52 s |
| Of that, one data migration (`202611181350_7325_verified_global_fund_managers.sql`) | 16 s |
| One full build on CI, from the test durations of files that build once per test | about 35 s |
| Top-level test seconds in five of six Worker shards of one merge-queue run | 14,939 s |

That data migration is 556 inserts, and each one scans `research_fund_directory` to look for an existing manager.
An applied migration cannot be edited, so every build pays for it. The shared build pays once per run.

**The census.** Every Worker test file that names the baseline, the migrations directory or a fixture that reads
them was run in report mode: 615 of the 2,142 files.

| Group | Files |
| --- | --- |
| Execute no whole migration file | 195 |
| Up to one chain (one build, or cuts of it) | 350 |
| More than one chain, up to two (a build plus re-running some migrations) | 19 |

Ten candidate files executed no SQL at all. One, `partner_invitation_fixes_d924`, was still running after 35

The 41 files over budget are listed in `scripts/test-schema-replays.txt`, each with its count and, where #8437 filed

### 2. The rule

- **What is counted.** A call to `DatabaseSync.prototype.exec` whose SQL is exactly the text of a migration file
  above the cutoff. The count is per test process, which is per test file.
- **The budget.** Twice as many as there are migrations above the cutoff (`CHAINS = 2`). A first version allowed
  one chain; the verification run stopped files that build once and then re-run some migrations on purpose
  (`channels_meetings_d684`, `cycle_raise_d663`, `interview_sessions_d657`), which is a legitimate test of a
  migration, not a rebuild. The census puts nineteen files between one and two chains: twelve at 1.0 to 1.1, and
  seven from 1.6 to exactly 2.0. A file that rebuilds per test sits above two, from 2.1 up to 20.5.
- **Past the budget.** The call throws before it runs. The message names the file, the count, the size of one
  build, the helper to use (`freshSchema()`, `loadSchema(db)`, `openSchema()`, `{ below: N }`) and the list. If a
  fixture swallows the error, the process still exits non-zero with the same message.
- **Not counted.** A build made by `_schema_once.mjs`, recognised by its caller. Otherwise the test file that
  happens to build the cache first would be charged for it, and the result would depend on scheduling.
- **Deterministic.** The count is of files, never of seconds, so a file is over budget on every machine or on
  none.

It is installed only in a process whose command line names a file `cloudflare-worker/test/<name>.test.ts` or
`.test.mjs`. `npm run bench:d1` and the guards, which use the same loader, are untouched.

### 3. The list

`scripts/test-schema-replays.txt` holds the files that were over budget when the rule arrived.

- A listed file is not stopped.
- A listed file that has been fixed stays valid. So the PRs for #8440 to #8463 do not edit the list and cannot
  conflict on it.
- An entry must name an existing Worker test file, and the list is sorted with no duplicates
  (`schema_replay_budget_8467.test.mjs`).
- A new entry is for a file about the build itself, with the reason after `#`.

The list is not yet forced to shrink. Once round one of #8437 has landed, running the suite with
`SCHEMA_REPLAY_REPORT=<file>` gives each file's count, and the entries at or under one chain can be removed.

### 4. What it does not see

A file that applies the chain statement by statement, or through `prepare`, executes no whole migration file
and is not counted. These builders are few and deliberate (`sub_cutoff_restores_d190`, `user_column_cap_d189`,
`event_badges_restored_d257`, `licence_kind_d196`, `partner_profiles_single_shape_d187`), and #8437 ranks them on
their own. The pattern that spread by copying is `db.exec(readFileSync(...))`
in a loop over the directory, and that is what the rule stops.

### 5. Cost

- Reading the migrations directory: 17 ms, once per test process that executes any SQL.
- Per `exec` call: about 110 ns.
- Per whole migration file: the file is read once and compared; 110 ms for a full chain, against a build of 35 s
  or more.

### 6. What was considered and not done

- **A check that reads the source.** A file that both reads the baseline and lists the migrations directory does
  not always build: on the first 123 files of the census, that rule flagged 67 and 32 of them never ran a full
  build. A rule that wrong half the time would be switched off.
- **Counting bytes of SQL executed.** `loadSchema` itself executes every `CREATE` statement per copy, so a file
  with a hundred tests would pass any byte limit that still caught a rebuild.
- **Moving the baseline cutoff forward.** A baseline taken after migration 7325 would make every build cheap, in
  the shared helper and outside it. `BASELINE_CUTOFF` also tells the production runner which files to mark as
  already applied, and tests build "the schema before migration N" for many N above 219. It is a larger change
  with a production side, and it is the owner's to decide; it is not started here.
- **Editing `_schema_once.mjs`.** Not needed, and S01 asked that no task in the round touch it.

### 7. Validation

- `schema_replay_budget_8467.test.mjs`: 17 of 17, on a three-migration chain in a temporary directory, plus the
  real chain's count against `schemaInputs()` and the real list.
- Mutation check: 38 changes to `_schema_budget.mjs` and the loader line, 38 caught.
- The census: 615 candidate files run in report mode on `main` at `d4e7a3245b`, 2026-11-24. Every file over two
  chains is listed.
- The budget enforced on the eight unlisted files nearest the limit (1.6 to 2.0 chains): none is stopped.
