## D6277 — Benchmark history: keep each restatement of a benchmark (#6277)

- **Status:** built 2026-11-27. Canvas: `design/incoming/Investor Research v2 Benchmarking and Library Page.dc.html`, board RS-14, card "Restatement history" (D6273; the owner's answers in D6273-p2, option A throughout).
- **Problem:** `PATCH /api/research/benchmarks/:uid` overwrote the row, so an investor tracking a figure quarter by quarter lost the earlier value, the earlier peer figure and the earlier reading.

### What is decided

- **One row per change, holding the row as it was.** Migration `202611270437_6277_research_benchmark_history.sql` adds `research_benchmark_history`: `benchmark_id`, `owner_user_id`, the six fields (`metric`, `our_value`, `peer_value`, `peer_source`, `peer_sample_size`, `peer_as_of`) and `reading` as they were before the change, and `changed_at`, the moment they were replaced (the same instant as the row's new `updated_at`). Values stay text, as in migration 217.
- **Only a change is kept.** `PATCH` compares the merged row with the stored one on those seven columns (blank and missing are the same value) and writes a history row only when one differs. A save that changes nothing writes nothing.
- **The snapshot and the update are one batch.** The history row is an `INSERT … SELECT` of the stored row, batched ahead of the `UPDATE`; D1 runs a batch as one transaction, so neither lands without the other.
- **Using a fund's figure is a restatement too.** `POST /benchmarks/:uid/ours-from-fund` (D6278) replaces "Ours", so it keeps the earlier row the same way when the figure changes. The issue named only PATCH; leaving this writer out would have lost exactly the values the issue is about.
- **Owner-scoped everywhere.** The read, the write and the delete each bind `benchmark_id` and `owner_user_id`. A history row under another owner is never shown or removed by this caller.
- **History goes with the benchmark.** `DELETE /benchmarks/:uid` removes the benchmark's history, owner-scoped, after its constituents and before the row (D1 does not run the foreign key's cascade inside a batch).
- **Read with the detail.** `GET /benchmarks/:uid` (and every write that answers with the detail) returns `history`: the earlier versions, newest first, at most 200. If the history cannot be read it is `null`, never `[]`, and the rest of the detail still answers.

### The page

- `BenchmarkDetail.jsx` draws the RS-14 "Restatement history" card after Peer constituents: Field · Earlier value · Replaced, newest first. `benchmarkRead.js` `historyRows` turns the stored versions into one line per field each save changed, by comparing each version with the one that replaced it (the current row for the newest). This is the canvas's table; the issue's list (date, ours, peer, n, as-of, reading) is the same information, shown per field.
- Values are text with their unit, and no chart is drawn. A blank earlier value reads Not recorded.
- An empty history reads "No earlier version is recorded." A history the Worker could not read says Unavailable, with the sentence that it is not an empty history, and every other card still loads.

### Not done

- Values a PATCH overwrote before this migration cannot be reconstructed; every existing benchmark starts with an empty history, and the card says so.
- Changes to named constituents are not part of a benchmark's history; they are their own rows (migration 303).
