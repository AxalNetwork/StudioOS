### 1. `website_cdn`: a site record in the existing `FILES` bucket

The Worker has no website or CDN publish integration (D5585-p3 §2: Vercel is read-only by D1096, and the Cloudflare
token cannot purge a cache). What it has is the `FILES` R2 bucket. So the adapter writes the release's **site record**
there. The website reads it, and serving it at the edge is the route part's job.

| Step | What it does |
|---|---|
| Key | `release-sites/t<tenant>/c<company>/<site>/<manifest>.json`. The effect's ref is the site, a DNS label (`campaign-site`). The tenant and company are the effect's own. Part 2's handler has already checked that the manifest is theirs. |
| Body | Ids only: the release key, line, manifest uid and digest, audience, and each pinned piece's asset, revision, digest and role. No content and no source locator. |
| Metadata | The effect's key, the manifest, the digest, the tenant and the company, as R2 custom metadata. `lookup` is one `head`. |
| Publish | One `put` per (site, manifest), written once. A later release is a new object, so a late effect of an older release can never overwrite a newer one. Which record a site shows is still the line's publication pointer (`servedRelease`). |
| Retract | Deletes that one object. Another release's record on the same site is not touched. |

**Rules.**

- **Public only.** A website is a public surface. A non-`public` audience is refused `audience_forbidden` before any
  request. Part 1 already refuses a `website_cdn` effect on a non-public line at publication.
- **Never overwritten.** If a record of this manifest exists under another key or digest, the adapter refuses
  `digest_conflict`. It neither takes that record as delivered nor replaces it. A record whose metadata names another
  tenant or company is refused `wrong_tenant`.
- **Unknown outcomes.** A thrown R2 call, or a `put` that returns nothing, is `provider_unavailable`. The next attempt's
  `head` finds a write that landed, so the record is written once.
- **No bucket.** Without `FILES` the adapter refuses `target_not_configured` and makes no request.

**Why `release-sites/` and not `wg/v1/`.** The D6650 inventory classes `wg/v1/` as `record`. D6651 makes those objects
write-once, and only `recordErasure.ts` may delete one, for a fixed list of reasons. A takedown is not on that list. A
site record is not evidence either: the manifest, its decisions and its delivery rows in D1 are the evidence, and the
record can be rebuilt from them. So it has its own prefix, classed `replaceable` (`files-release-sites`).
`check-record-writes` and `build-r2-inventory --check` both pass. The prefix is also outside `wg/v1/…/sha256/`, which
#5581's reconcile lists for orphan blobs.

**Not done here.** The record is private, like everything in `FILES`. Serving it publicly, with cache headers and a
purge, needs a route and the owner's approval. If the website should be served from a public bucket or a CDN with its
own token, that needs a new binding or secret, and so belongs to that later part. The adapter keeps the same contract
either way.

### 2. `external_distribution`: an adapter over injected channels

The Worker has no outside channel a drain may send to on its own. D5585-p3 §2 gives the two candidates and why
neither fits. Founder publishing (`publishCore.ts`) sends only on the founder's confirm. Event syndication
(`services/eventSyndication/`) lists events, and its one provider is switched off. A new channel needs an account, a
secret and the owner's approval. None of that is in this part.

So the adapter is built against a `ReleaseDistributionChannel` interface (`find`, `post`, `withdraw`, `owns`,
`audiences`), keyed by the ref's channel (`<channel>:<destination>`, e.g. `ir_list:acme-investors`).
`RELEASE_DISTRIBUTION_CHANNELS`, the registry on main, is **empty**. In production every effect therefore refuses
`target_not_configured`, calls nothing and dead-letters, exactly as before. Tests pass a fake channel through
`drainReleaseEffects(env, { distributionChannels })`.

The adapter enforces the rules, so a channel cannot weaken them:

- **Ref and scope, before any request.** A ref not of the shape is `malformed_ref`. An unregistered channel is
  `target_not_configured`. A destination the effect's tenant and company do not own (`owns`, a configuration read) is
  `ref_out_of_scope`. An audience the channel does not carry is `audience_forbidden`.
- **Lookup.** `find` by the effect's key must read everything (`complete`), or the answer is `lookup_incomplete` and
  nothing is posted. A record of another tenant or company is `wrong_tenant`. A record under the key with another
  manifest or digest, or more than one record, is `digest_conflict`.
- **Errors.** A `ChannelError` with 401 or 403 is `provider_unauthorized`. A 5xx, a 429, no status or any other throw
  is `provider_unavailable`, which the next lookup settles. Any other 4xx is `provider_rejected`. A `post` answer that
  does not name the key and an id is `provider_malformed`.
- **Retraction.** Withdraws every record of the manifest at that destination (a 404 is already gone). It is done once
  `find` by manifest returns nothing.
- **Ids only.** The posted record carries the same ids as the site record, plus the tenant and company.

**Adding a channel later** is a row in `RELEASE_DISTRIBUTION_CHANNELS`, in its own task, with its account, its secret
through `integrations/secrets.ts`, and the owner's approval. It changes nothing here.

### 3. What both adapters share with the others

- Part 2's handler still runs every check before either adapter is called: the manifest exists in the effect's tenant
  and company and on its line, the digest is the effect's, the pointer still names the manifest, the audience is the
  line's, and nothing is taken down or tombstoned. The tests check each one for these two targets, with no request.
- Every R2 operation and channel request counts once in the drain's `ProviderMeter`, under its target. Part 2's
  delivery rows still carry each delivery's D1 statements and adapter calls.
- Every refusal is part 2's `DeliveryRetry`. The outbox records it as an `effect_retry` or `effect_dead` integrity
  event with its code, backs off, and dead-letters after its attempts. The tests read those audit rows.
- **The request now carries `tenantId` and `companyId`.** They are the effect's own scope, which the handler has
  already matched to the manifest. The site key needs them, and so does a channel's ownership check. The other adapters
  ignore them.

### 5. Rollback

Point `website_cdn` and `external_distribution` back at `unconfiguredAdapter()` in `releaseAdapters`, and delete the
new service and the `files-release-sites` inventory entry. Nothing else calls them. Leaving
`WORK_GRAPH_RELEASE_DELIVERY` unset keeps the drain off without a revert. Site records written while it was on can be
deleted under `release-sites/` with nothing else affected.
