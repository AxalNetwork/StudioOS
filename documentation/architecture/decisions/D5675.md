The canary uses the existing studioos-meeting-bot-preview script, its own MEETING_BOT_CONTAINER namespace/application and one canary-prefixed control DO identity. Production still returns HTTP 404. Preview exposes only authenticated canary traffic when its explicit audience and enable flags are set; the committed enable flag is off and recipient origin empty. The origin must be the exact preview bot script's HTTPS workers.dev host, not the UI preview or either production application hostname. Existing APP_URL and the real B1 customer callback path are not repurposed.

A separately provisioned MEETING_BOT_PREVIEW_SECRET derives distinct run, callback and receipt keys per synthetic ID, nonce and exact revision. Signature validation covers exact bytes/path/timestamp, environment, script and role before namespace allocation and again inside the host. A callback is accepted only for the current challenge. One operator request replays its receipt without starting another container. A new probe ID cannot bypass an earlier unknown cleanup; the shared control object admits another probe only after confirmed stop, retaining a bounded short-lived replay history. Production secrets, D1, R2 and Slack credentials never enter the fixture container. The actual image boots its normal provider-free health process; no start/join/invite/record command is sent. Readiness must echo the exact deployed revision. The guest's canary script reuses the existing callback signer and refuses production targets and redirects.

A signed callback plus acknowledgement and durable receiver marker are all required. Cleanup acknowledgement is required for promotion. Failed image start/readiness/callback and uncertain stop produce closed stage evidence, not a success. Alarm cleanup remains available if admission is off or the caller disappears. Only the canary's matching synthetic lease/receipt is deleted after ten minutes; unknown cleanup is retried and stays ineligible. This is not a claim that an unavailable provider acknowledged termination.

The normal deploy workflow is preview publish → deployed callback verification → production publish. No continue-on-error or automatic bypass exists. The CLI requires owner verification of the private preview route, validates the server-signed receipt, exact revision, stage and stopped instance, and retains only sanitized revision/stage/elapsed/digest/cleanup evidence. #5673/#5667 consume release phases; the canary result is not a production recording-success receipt. #5665/#5671 must turn failing/repeated/recovered preview evidence into one preview thread.
