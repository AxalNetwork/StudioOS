## D5022 — The versioned package catalogue: `program_packages`, its composition, and what is frozen when (#5022)

- **Status:** built by S04, 2026-11-09 (#5022, part 1 of #5021). PR: see the issue.
- **Number:** D5022 is this issue's number (D4106). Migration: `202611091023_program_packages.sql`.
- **Files:** the migration; `cloudflare-worker/src/services/licencePackagesStore.ts`;
  `cloudflare-worker/src/routes/admin_licence_packages.ts` (`/api/admin/licence-packages`);
  `cloudflare-worker/test/licence_packages_d5022.test.ts`.

### 1. What this issue builds, and what it deliberately does not

#5021's delivery order puts "package schema + versioning" first, before pricing, acceptance, lifecycle rules or
HQ's UI. This issue is that first part only: a durable, versioned definition of what a package IS — its key,
its commercial defaults, and the programs it bundles — with nothing yet pointing a licence at one.

So, on purpose, this migration adds no country-pricing logic (#5023), no package OFFER or ACCEPTANCE and no
program-grant orchestration (#5024), no upgrade/downgrade/renewal/proration rule (#5025), and no HQ UI
(#5026). "Retiring a package does not alter licences that already hold it" (the issue's acceptance criterion)
is true today for the plain reason that **no table yet links a licence to a package version** —
`territory_licences` carries no package column, and `licence_agreement_policy_holdings` (D5052, migration
202611090840) freezes a *legal policy* version, not a *commercial* package version, and already says package
acceptance is deferred until this store exists. #5024 is where that link is built, and it is specified to hold
a frozen `package_key` + `version` pair, read-through, never a live join to this catalogue's current row — so
the same fact stays true once a licence actually can hold one.

### 2. The four keys, and where they came from

The issue names the four packages by display name only ("Core Network", "Talent & Learning", "Venture
Building", "Full Axal VC operating system") and says explicitly: no package uses a display label as its
foreign key. Two files already needed stable keys for these exact four packages, written one day before this
issue by #5047/#5049's part 2 (`services/agreementTemplates.ts`, D5049), which names each package agreement
template with a `package_key` and says in its own comment: *"The four Axal VC packages a package agreement can
name (#5021 builds their store; until then, these keys)."* Those keys are:

| Display name | `package_key` |
|---|---|
| Core Network | `core_network` |
| Talent & Learning | `talent_learning` |
| Venture Building | `venture_building` |
| Full Axal VC operating system | `full_axal_vc` |

This migration uses exactly those keys, not a fresh set, so `licence_program_agreements.package_key`
(migration 202611082025, D5048 — already live, already accepting these values with its own CHECK) and
`agreementTemplates.ts`'s `catalogRefusal` need no change to agree with the catalogue this issue builds.
**A later issue should repoint `agreementTemplates.PACKAGES` to read its name from this table** rather than
keep its own hard-coded array; until then the two must be kept in sync by convention, as `agreementTemplates.ts`
already flagged. A diff in that file's four-row array, without a matching migration here, is the signal that
sync broke.

### 3. The Full Axal VC program list: pinned, sourced, and from where

The issue requires the Full Axal VC program list to be a **literal, frozen list in the seed data**, never a
dynamic "every program" query — so a program added to the registry after this migration runs reaches no
existing package version, Full Axal VC included.

The source for "every currently grantable Axal VC program" is `PROGRAM_KEYS` in
`services/programRegistry.ts` (D954/#2787, extended by D4289's Influencers addition) — the registry HQ's own
Programs page reads, and the same ten keys `agreementTemplates.ts` (D5049) already licenses one program
licence/addendum template at a time. As of this migration, in registry order:

`spinout-lab`, `ai-native-venture`, `mentor-cohorts`, `investor-cohorts`, `referral-partners`,
`refer-and-earn`, `perks`, `learning`, `product-testing`, `influencer`.

These ten are written as a literal `INSERT` list in the migration (never a `SELECT key FROM programs`), so the
seed is immune to the registry growing later. Core Network, Talent & Learning and Venture Building's program
lists come straight from the issue's own text, matched to the same registry keys.

### 4. The lifecycle, and why a trigger (not only the route layer) enforces it

The issue asks the route layer to refuse writing to an active version's composition or commercial fields, but
also asks me to weigh whether a database trigger is warranted given house style. It is: `pricing_models`
(D5014, migration 202611081906, one day before this issue) is the same shape of problem — a versioned,
draft→active→retired commercial catalogue whose active and retired rows must stay byte-for-byte reproducible
— and it freezes itself with a `BEFORE UPDATE`/`BEFORE DELETE` trigger pair, never relying on the route alone.
This migration follows that exact pattern for `program_packages`:

- **`trg_program_packages_frozen`** refuses any `UPDATE` once a row has left `draft`, for every column except
  `status` itself — and even `status` only along the one real transition a route can still make
  (`active → retired`; `retired → draft` is also refused, since nothing may un-retire a version). Retiring may
  set `effective_to` freely; it is not in the frozen list.
- **`trg_program_packages_no_delete`** refuses deleting any row once it has left `draft`: an active or retired
  version is history, kept forever, exactly as `pricing_models` keeps retired models.
- **`program_package_items` is frozen the same way, read through its parent.** Three triggers
  (`BEFORE INSERT`/`UPDATE`/`DELETE`) each check `(SELECT status FROM program_packages WHERE uid = …)` and
  refuse unless that package row is still a draft (a missing parent reads as draft via `COALESCE`, which only
  matters for the seed's own insert-before-parent-exists ordering, below — nothing else can produce a
  parentless item row). So a package's **composition** is exactly as immutable as its **commercial fields**: an
  active or retired version's `program_package_items` rows can never gain, lose or reorder a program.

The route layer (`licencePackagesStore.ts`) still checks `status === 'draft'` **before** every write, so the
person gets a named refusal (`package_version_immutable`, 409) rather than a raw SQLite trigger message; the
trigger is the backstop for whoever else ever writes this table, not the only gate.

**The seed exercises this same lifecycle rather than bypassing it.** Each of the four v1 rows is inserted as
`draft`, its `program_package_items` rows inserted while it is still a draft (the items-lock trigger would
otherwise refuse an insert against an already-active parent), and only then flipped to `active` by an `UPDATE`
— the same `draft → active` transition the write bar's publish route performs. An insert straight into an
`active` row, items included, would have had its items blocked by its own trigger before the migration
finished, which is exactly the regression this ordering is proof against.

### 5. Reads, writes and who may do each

Reads (`GET /api/admin/licence-packages*`) are `requireSuperAdmin`. Every write — create, draft a next
version, edit a draft, publish, retire, delete a draft — is `requireSuperAdminWriteBar` (TOTP-minted session,
recent step-up, then the elevation), the same gate `admin_licence_pricing.ts` uses for its own versioned,
draft→active→retired commercial catalogue (`pricing_models`) one day earlier. That file is the closest existing
precedent for this exact shape of problem, so this issue reuses its pattern rather than the plainer
`requireSuperAdmin` some other HQ-only writes use (e.g. `admin_programs.ts`'s registry edits) — those are
metadata edits to an existing program, not a new version of a commercial product with a price attached.
`publish` and `retire` additionally require a `reason` (3–500 characters), as `pricing_models`' `activate` and
`retire` do; `create` and the draft `PUT` do not, matching that file too. Every write calls `logAdminAction`.

### 6. Composition validation

`program_package_items.program_key` is checked against the live `programs` table (`unknownProgramKeys`) at
every write that sets composition, so a typo'd key is refused with its own 400 before it can ever be frozen —
never silently accepted and then unreadable. This is the same shape as `programRegistry.ts`'s `checkTemplates`
checking a playbook section's `template_keys` against the contracts library. It is a write-time check only:
a program later removed from the registry does not retroactively invalidate a package version that already
named it, because the version is frozen and the registry's own rows are never deleted either.

### 7. Owner question

None. Every schema field, every lifecycle rule and every seed value is specified in the issue; the one real
choice — which existing "Super Admin write bar" to reuse — is answered by precedent (§5), not by invention, so
there is nothing here that needs the owner's call.
