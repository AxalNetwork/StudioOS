## D982 — Program grants part 1: the grant store, default terms per program, HQ's reads and its step-up writes (#2773)

- **Status:** built by S15, 2026-10-24 (#2773, part 1 of #2376, under D981).
- **Migration:** 553 (`cloudflare-worker/sql/migrations/553_program_grants.sql`).
- **Canvas:** "Program grants", GR1, GR3, GR4, GR6 and GR10 (`design/incoming/Program Grants Page.dc.html`).
- **Why:** D981 drew HQ's grid with every cell "Not recorded", because nothing stored a grant. This part is that store, and HQ's reads and writes over it. The pages that use it are part 6 (HQ) and part 7 (the studio).

### 1. The store

- **`program_grants`:** one row per licence and program key, `UNIQUE (licence_id, program_key)`. A row holds:
  - its state (`granted`, `paused`, `ended`);
  - the grant terms;
  - the program schedule (`schedule_contract_uid`, `schedule_signed_at`);
  - HQ's note to the studio;
  - `paused_at` and `ended_at`;
  - who set it and when.
- **Program keys:** the canvas's nine, on D953's strings, as `frontend/src/lib/programGrants.js` (D981) keeps them. The migration's CHECK and `services/programGrants.ts` repeat the list, and `program_grants_d982.test.ts` holds all three equal.
- **Every term is nullable,** and a term nobody set reads `null`, so the page shows "Not recorded" (D797's rule).
- **The terms are the canvas's** (GR4, GR6, GR8):
  - the period: `starts_on`, `ends_on`, `ends_with_licence`;
  - capacity: `capacity_cap`, `capacity_uncapped`;
  - `cohorts_per_year` and `credits_per_quarter`;
  - money: `fee_cents`, `currency`, `hq_share_bps`;
  - HQ approval: `hq_approves_each_cohort`, `hq_approval_above_cents`;
  - `playbook`, `brand` and `reporting`;
  - `requires_signed_schedule`.
- **Each program carries only the terms the canvas gives it.** For example, credits belong to Refer & Earn and Perks, and cohorts to the Lab and Mentor cohorts. `TERM_FIELDS` in the service is that table, and a write naming a term that doesn't apply is refused (`… does not apply to Spin-Out Lab`).
- **Capacity is two columns,** because the canvas's "No cap" is a decision and an empty cell is not:
  - `capacity_cap = N` reads "Up to N";
  - `capacity_uncapped = 1` reads "No cap";
  - both null reads "Not recorded";
  - both set at once is refused.

### 2. Default terms per program

- **`program_grant_defaults`** has one row per program: the "can be granted" flag and the defaultable terms. The period is not a default; it belongs to each grant.
- **The seed sets only two things.** Each program's flag, and `requires_signed_schedule = 1` (D981 §5, decision 3: on by default). Every money and capacity default is HQ's to enter, so it starts "Not recorded". The canvas's bracketed figures are samples, never data.
- **Product testing, Investor cohort access and AI-native Venture ship off,** and switching one on is refused (`not_grantable`). Product testing stays at HQ, and the other two are not ready (D981 §3).
- **A new grant starts from its program's defaults,** and what HQ names wins. Grants in force keep their own terms until HQ changes them (GR6's line).

### 3. HQ's reads and writes (`routes/admin_program_grants.ts`, at `/api/admin/program-grants`)

**Reads** use `requireSuperAdmin`, as the ledger's do. A D1 failure is a 5xx through `mapError`, never an empty list.

- **The grid** (`GET /`). Licences that are not drafts and not terminated (D981 §2), each with its grants by program. Also:
  - **the tiles:** in force; granted; paused; ending in 90 days; program fees a year, by currency, plus how many grants have no fee recorded; and requests waiting;
  - **the series:** studios holding each program (granted and paused), and requests by month.
  - Requests waiting and requests by month are `null` with a reason naming #2774, because requests are part 2. They are never 0.
- **One licence** (`GET /licences/:uid`): its grants and its program history.
- **The history** (`GET /licences/:uid/history[?program=]`).
- **The defaults** (`GET /defaults`).

**Writes** use `requireSuperAdminWriteBar` (a TOTP session, a fresh step-up, the elevation), as a terms save does. Each needs a reason of at least 10 characters.

| Write | From | Refused when |
|---|---|---|
| Grant (`POST /licences/:uid/:program`) | no row, or `ended` (a re-grant on the same row, with fresh terms and schedule) | the program is locked or switched off (422); the licence is suspended, terminated or a draft (409); it is already granted or paused (409) |
| Change terms (`PATCH`) | `granted`, `paused` | the licence is suspended or terminated; nothing would change |
| Pause | `granted` | — (open on a suspended licence) |
| Resume | `paused` | the licence is suspended or terminated |
| End | `granted`, `paused` | — (open on a suspended licence) |
| Defaults (`PUT /defaults/:program`) | — | a locked program switched on; a term only a grant carries |

- **A pending licence may be granted.** The grant waits for activation: it is not in force until the licence is active (GR1's row note).
- **Each state change is guarded on the state it leaves** (`WHERE … AND state = ?`). A write that lost a race says so and changes nothing.

### 4. In force

A grant is in force only when all of these hold:
- it is `granted`;
- its licence is `active`;
- its start date has come;
- its end has not passed (`ends_on`, or the licence's `renews_on` when it ends with the licence);
- its schedule is signed, unless HQ recorded the rule as off.

**A rule nobody recorded counts as on.** The default is on, and a grant must not run on an unsigned schedule because a term was blank. Each grant says what it waits on in `waiting_on`: `licence_active`, `schedule_signed`, `start_date` or `ended_by_date`.

**`schedule_signed_at` has no writer yet.** Sending and signing the schedule is part 6's "Send schedule" (GR3). Until then no grant whose rule is on can be in force, and the tile says 0 in force, not a guess.

**The program fee is stored, not billed.** Where it is billed is still the owner's (D981 §5, decision 2).

### 5. History: one generic `licence_events` kind, `program_changed`

**The choice (#2773 asked for it to be recorded here).** Every grant write appends one `licence_events` row:
- `event = 'program_changed'`;
- `note` = the reason;
- `detail_json = { action, program_key, changed: [{key, before, after}], reason }`;
- `action` is one of `granted`, `regranted`, `terms_changed`, `paused`, `resumed`, `ended`.

**Why one generic kind, not six.** Both options need a rebuild, because SQLite cannot widen a CHECK in place. One kind means one rebuild now, and parts 2 to 5 can add actions (a request answered, a schedule sent) with no further rebuild of a sealed table. The licence's history still reads in one place, and each action keeps its own name in the detail.

**A defaults change is not one licence's,** so it goes to the admin audit log (`logAdminAction`, `program_grant_defaults_changed`).

**Found while building: the seal was gone, and 553 restores it.**
- Migration 269 sealed `licence_events` append-only with two triggers. It warned that any rebuild must re-run them, because `DROP TABLE` drops a table's triggers.
- Migration 331 rebuilt the table to admit `contract_sent` and did not re-run them. So on the full migration chain, `licence_events` has accepted UPDATE and DELETE since 331.
- `audit_immutability_d156.test.ts` didn't catch it, because it applies 269 to the baseline alone, never the full chain.
- 553's rebuild ends with 269's two triggers, verbatim. `program_grants_d982.test.ts` asserts them on the full chain, refuses an UPDATE and a DELETE, and checks that the rebuild keeps every existing event.
