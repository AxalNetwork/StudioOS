## D4533 — A skill release is published on its evidence: the definition, the cases, the evaluator and the required models (#4533, step 3 of #4528)

- **Status:** built by S25, 2026-11-08: part A (the lifecycle matrix) and step 3 (release evidence), PR #5086. Second slice, 2026-11-09: step 5 (recovery), §10, and finding F1 fixed. Part B's release notes and draft history, and part E's timeline, wait on the owner (§11).
- **Migration:** `202611081919_skill_release_evidence.sql`. Additive, with no backfill. Its reasons are in §3. The step 5 slice adds none.
- **Production:** nothing was published, retired, re-pinned or approved. The 110 HQ drafts and the 70 definitions in #4526 stay drafts.

### 1. The defect

At `d85951ca` an approval and an eval result were bound to `draftHash()`, which hashes the definition only (name, purpose, steps, tools, output kind, tags, roles). Three things could change after an approval without making it stale:

- **The case suite.** `PUT /:uid/cases` adds and removes cases (each keeps an immutable uid), but the hash stayed the same. Removing a failing case raised the pass rate with no new review.
- **The evaluator.** No result recorded the judge version it was judged under (#4531's `JUDGE_VERSION`).
- **The models.** `evalSummary()` took its models from the results it found. A draft run on one model was measured on one model. A model nobody ran did not appear in the matrix, so it could not fail.

This finding is about the completeness of the release evidence. It is not an authorization bypass. The second-admin rule was enforced throughout.

### 2. The release evidence

**Identity (`evidenceOf`, `services/agents/skillLifecycle.ts`).** A draft's evidence has four parts, and `evidence_hash` names all four:

| Part | Source | Stored where |
| --- | --- | --- |
| `definition_hash` | `draftHash()`, unchanged. `skillCatalogue.ts` still uses it to compare drafts with the library files | `draft_hash` columns, as before |
| `suite` | The live cases, oldest first. `revision` = SHA-256 of their uids. Each case also gets a `sha256` of its stored text, for the record | Derived. Nothing new is stored, because the uids already exist and are now immutable in D1 |
| `evaluator_version` | `EVALUATOR.version`, which is #4531's `JUDGE_VERSION`, read through the import (the object is a seam for tests) | Derived |
| `models` | `{ required, source }`. `declared`: the draft's `agent_skills.required_models_json`, set by `PUT /:uid/models`. `default`: the first five models agents may run on (`defaultModels`), the same five that Re-run evals with no choice has always run. It is sorted, and it is never read from the results | The declared set is stored. The default is derived |

`evidence_hash` = SHA-256 of `[definition_hash, suite.revision, evaluator_version, required models]`.

**Binding.** A review request stores `evidence_hash` and `evidence_json` (all the parts). An eval result stores `evidence_hash`. `approvalFor` matches on `evidence_hash`. `evalSummary` reads results under `evidence_hash`, and only on the required models.

**The manifest (manifest 1).** It is written in the same INSERT as the HQ version row, into `agent_skill_versions.evidence_json`, so a version and its manifest cannot be separated. It holds:

- `version`, `definition_hash`, `evidence_hash`;
- `suite` (each case's uid, name and text hash, and the revision);
- `evaluator_version`;
- `models` (`required` and `source`);
- `results`: one row for every live case on every required model, with `case_uid`, `model`, `result` and the eval result's `result_id`;
- `bar`: `{ pass, total, pass_bar }`;
- `review`: `{ review_id, requested_by, reviewer_id, decided_at }`.

GET `/:uid` shows it as `versions[].evidence`, with the people as `{ uid, name }` and no email address.

### 3. Why a migration

The suite revision is derived, as the task prefers. Three facts cannot be derived later:

1. The declared required model set is a choice, not a fact recorded in any row.
2. The evidence a review or result was given on. Without it, a later evaluator or model-set change cannot be told apart.
3. What a version was released on.

So the migration adds five nullable columns:

- `agent_skills.required_models_json`;
- `agent_skill_reviews.evidence_hash` and `evidence_json`;
- `agent_skill_eval_results.evidence_hash`;
- `agent_skill_versions.evidence_json`.

It also adds one index and the triggers below. It creates no new table and no second lifecycle or status model. A version's manifest lives in the version row, because that row is already immutable.

**Triggers: nothing in the history is rewritten.**

| Table | Rule |
| --- | --- |
| `agent_skill_versions` | Already never updated (759). It is now never deleted either (`trg_agent_skill_versions_kept`) |
| `agent_skill_cases` | A case is never edited. Its one permitted change is `removed_at`, from NULL, once. It is never deleted |
| `agent_skill_eval_results` | Never updated and never deleted |
| `agent_skill_reviews` | Already never deleted. A review now keeps what it was asked on (skill, hashes, people, `requested_at`, evidence). A decided review is final |

The application already wrote this way. The triggers make the database refuse anything else.

### 4. The freshness decision

`releaseDecision(env, skill, parts)` is computed once, on the server:

```
{ ready, blocking: ['needs_approval' | 'evaluation_incomplete' | 'golden_cases_failing'],
  evidence,
  review: { approved, changes: { definition, cases, evaluator, models } | null, released_version },   (released_version: §10.1)
  evaluation: { pass, total, not_evaluated, meets_bar, pass_bar } }
```

- `publishRefusalOf(decision)` is the gate. `publishDraft` calls it for an HQ skill. The first blocking reason answers, and every refusal carries the decision as `freshness`.
- The success reply of `POST /api/teams/skills/:uid/publish` is `{ skill, freshness }`. `freshness` is the decision publish was let through on, and null for a company skill.
- GET `/:uid` answers the same object as `freshness`. The test holds the refusal's `freshness`, the direct call and GET `/:uid` equal at every step. The decision carries no timestamps, so the same evidence always gives the same decision. #4537's screen should read `freshness` rather than re-derive it.
- `review.changes` compares the latest approval of the skill with the current evidence. On a review from before D4533 it reads `cases`, `evaluator` and `models` as null, because they were never recorded.

**Invalidation rules.** Each row is tested.

| Change | Review | Evaluation |
| --- | --- | --- |
| Definition (any `draftHash` field) | stale (`needs_approval`; an open review is `review_stale`) | stale: every cell not evaluated |
| A case added, removed or changed (a changed case is a new uid) | stale | stale |
| Evaluator version (#4531 bumps `JUDGE_VERSION`) | stale | stale |
| A model added to, or removed from, the required set | stale | stale |

**Not evaluated.** The matrix is every live case on every required model, built from the evidence. A cell with no result under the current evidence reads `not_evaluated`. It is listed, it is never left out, and it is never a pass. While any cell is `not_evaluated`, publishing is refused with `409 evaluation_incomplete { not_evaluated, total, freshness }`, even when the cells that do have results would meet the bar (the test uses 19 of 20). `not_run` (the model refused) stays a result that is not a pass, as before. The 9-of-10 bar (`PASS_BAR`, `meetsBar`) is unchanged.

**Reviewers.** Reviewers see case-suite and model changes beside the definition in two places:

- Each review in GET `/:uid` carries `changes`. A stale approval answers `review_stale { changes }`.
- `GET /:uid/diff` adds `evidence`, next to `frontmatter` and `steps`:

```
{ recorded: { from, to },
  cases: { from, to, added, removed } | null,
  models: { from, to, added, removed } | null,
  evaluator: { from, to } }
```

A version side reads its manifest. The draft side reads the live evidence.

**The library (GET `/`).** The list computes each row's evidence from the same reads, in a fixed number of queries. `golden` adds `not_evaluated`, and `meets_bar` is false while any required cell is not evaluated, so a row never reads ready when the detail would refuse.

**Running the evals.** `POST /:uid/evals` with no `models` runs the required set. Bulk evals with no `models` runs each skill's own required set. A run with `models` may include a model outside the set; its results are recorded but do not count. Each eval audit row records the evidence it ran on (hash, suite revision, case uids, evaluator version, required models), so every result can be attributed to its evidence even before any release.

### 5. Historical releases and rows (backward compatibility)

- **A version published before D4533** has `evidence_json` NULL. It stays published, its pins and runs are untouched, and it reads `evidence: null` ("Not recorded", never "passed"). The diff against it reads `recorded.from: false`, and its `cases` and `models` read null. Nothing is backfilled, because nothing was recorded.
- **A review or result from before D4533** (`evidence_hash` NULL) is kept as written and stays attributable by its draft hash, case, model, person and time. It never counts towards a publish. So an HQ draft that was approved and passing under D4160 needs a new review and a new run before it publishes. This is deliberate: its suite, evaluator and models were never recorded. An open review from before D4533 reads stale, and asking again withdraws it.
- **A company version** has no manifest, because no HQ gate applies to it (§6).

The PUT models route does not act on company skills: HQ's routes answer 404 for a non-HQ uid. Company editors cannot reach them (403).

**Atomicity: no pointer without its version.** `publishDraft` writes the pointer and the version row in one `DB.batch`, which D1 runs as a single transaction (the test fixture does the same, D370). The pointer update is guarded on `current_version`. If two presses race, the second batch's INSERT of the same number fails on `UNIQUE (skill_id, version)`, the whole batch rolls back, and the route answers `publish_conflict`. If the version INSERT fails for any other reason, the pointer update rolls back with it. The manifest is a column of that same row, so it cannot be missing on its own. The tests cover:

- a simultaneous publish (one 200, one 409, one row);
- a forced INSERT failure (the pointer stays at 0, `draft`);
- an invariant query: no skill has `current_version > 0` without that version's row.

The audit row is written after the batch. If it fails, a version exists without its audit row, but never a pointer without its version.

### 7. Findings

- **F1 (fixed in the step 5 slice).** Creating or editing a draft (HQ or company) wrote no admin audit row. Each now writes one with the definition hash before and after (`*_draft_created`, `*_draft_saved`); a save that changes nothing writes none. The draft is still mutable and is still not a history: the audit row says who saved which hash, not the text (§11 B2).
- **F2 (open).** Setting cases or models does not make the setter the draft's author (`updated_by`), as before D4533. Any change still makes the evidence new, so it needs a fresh review by someone who is neither the asker nor the last definition author.

- **F3 (open, not changed here).** Re-pinning a company's agent goes through `canManage` → `companyAccess.canEdit`, whose admin pass lets a platform admin re-pin a company's agent too. It is explicit and audited (`skills_changed`, D4534), so no pin moves silently, but it is wider than "the team's managers". The gate is `services/agents/teams.ts`'s, shared with every team-agent write, so changing it is its own task (§11 C).
- **F4 (fixed in the step 5 slice).** An approval was never spent. After a publish, the same approval still matched the unchanged draft's evidence, so a second press published an identical vN+1 with no new review, and a draft restored to an old version's evidence would have counted that version's old approval. §10.1.

### 10. Step 5 — recovery without rewriting history (second slice, 2026-11-09)

**10.1 An approval releases one version.** `approvalFor` now skips an approval that a version's manifest already names (`json_extract(evidence_json, '$.review.review_id')`). So:

- publishing the same draft twice needs a second review, and
- a restored definition needs a new review, even when its evidence is byte-for-byte the evidence an old version was approved on.

The decision says so: `freshness.review.released_version` is the version the matching approval released (null when none did), and the `needs_approval` message names it. A version from before D4533 has no manifest, so its approval was never bound to evidence and never matches anyway (§5). No migration: the manifest already records the review id. A failed publish writes no version row, so it spends nothing (tested).

**10.2 Restore is a proposal, not a rollback.** `POST /:uid/restore { from_version, reason, discard_draft? }` (`services/agents/skillRecovery.ts`) copies vK's definition (name, purpose, steps, tools, output kind, tags, roles) into the draft, checked by today's `checkDraft`. It never:

- writes, changes or deletes a version row (the triggers would refuse it anyway, §3);
- moves `current_version` or `status`;
- touches `agent_skill_links`.

The restorer becomes `updated_by`, so they can neither review nor approve it. It reaches agents only as the **next** integer version, through the same gate as any draft: a new approval on the current evidence (10.1), every required cell evaluated, and 9 of 10. Results already recorded under the identical evidence (vK's, if nothing else changed) still count as results; whether a recovery must re-run them is §11 A.

- `draft_has_changes` (409): the draft holds edits that were never published. They are replaced only with `discard_draft: true`, and then the audit row keeps the discarded draft in full, because the draft table is not a history.
- `already_restored` (409): the draft already holds vK's definition.
- An open review is withdrawn in the same batch: it was asked about the replaced draft.
- A retired skill is not restored (409 `retired`); its replacement carries on.
- The reply carries `freshness`, the same decision GET `/:uid` and the publish gate use.

**10.3 The cases.**

| Case | What happens | Tested |
| --- | --- | --- |
| Bad release (vN is wrong) | Restore vK (or edit), new review, evals, publish vN+1. vK and vN stay as written; no agent moves until its team re-pins | yes |
| Bad evaluation (a flaky or wrong result) | A result is immutable (§3). The latest result per case and model under the evidence counts, so a new run supersedes it and the old row stays. An evaluator fault is fixed by a new `JUDGE_VERSION`, which makes every draft's evidence new | yes (a failing run blocks, a new run clears it, the failing row is kept) |
| Failed promotion (the version row cannot be written) | The batch rolls back: no pointer, no version, the approval unspent. The next press publishes | yes |
| Partly completed publish (the version landed, its audit row did not) | The audit row is written after the batch, best-effort (§6). GET `/:uid`'s `versions[].publish_audited` reads false for such a version, and null when the audit log cannot be read, never "audited". It is a signal, not a repair | yes |
| Concurrent publish | One version; the loser is refused by the pointer guard, or by the gate once the winner spent the approval. A stale press that passes the gate on an approval of its own is still refused `publish_conflict` | yes |

**10.4 The pins.** `GET /:uid/pins` (Super Admin, read-only) answers each published version with its live agents (`current` marks the pointer), and each agent with its name, role, team (company and project names), `pinned_version` and `update_available`. A retired skill offers no update: its agents keep their pin. The list stops at 500 agents; `agents_total` is always the whole count. Re-pinning stays the explicit act it already was, `PUT /api/teams/agents/:uid/skills { skills: [{ uid, version }] }`, audited as `skills_changed` with each skill's version before and after (D4534); this slice adds no second re-pin path (§11 C, F3).

**10.5 Signals for #4536, without a second ledger.** Everything above is read from rows that already exist:

- the restore audit row (`agent_skill_restore_proposed`);
- `publish_audited` on each version;
- `freshness.review.released_version`;

Every run already carries `skill_id` and `skill_version` on its usage rows (D1612 part D); a run after a recovery, a new version or a retirement still reads the agent's pinned version (tested).

### 11. Owner decisions this slice raises (not decided here)

- **A. Must a recovery re-run its evals when the evidence is identical to an old version's?** Today (as built) results under identical evidence still count; only the approval is spent.
