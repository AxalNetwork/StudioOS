## D6466 — Fail a change that appends a section to an existing decision file (#6466)

- **Status:** built. Part of #5600 (plan key B3).
- **Why:** D5615 says a later part of a multi-part issue writes its own file,
  `decisions/D<n>-p<k>.md`, and `scripts/check-decision-ids.mjs` accepts that
  name and heading, but nothing read the diff. Open PRs #6445, #6444, #6409
  and #6303 each add a "Built, PPnn" section to `D4838.md` (six latent
  conflicting pairs), and `D4811.md` (652 lines) was edited by 16 of the last
  396 commits. Decision-file appends and README rows were 20 of 42 conflicting
  pairs in the 2026-11-14 landing plan.

### The rule

`scripts/check-decision-appends.mjs` runs in `npm run test:guards`, after
`check-decision-ids.mjs`. A file under `documentation/architecture/decisions/`
named `D<n>.md` or `D<n>-p<k>.md` that is on the base fails when the change

- adds a `##` or `###` heading (more of them than the base has, fenced code
  not read, so a renamed heading is not a new one), or
- grows it by more than 10 lines (lines now minus lines on the base).

The failure names the file, the new headings and the growth, and says to put
the text in `D<n>-p<k>.md` headed `## D<n> part <k> — <title> (#<n>)`, listing
the part numbers already taken and the next free one, with the `git diff`
that shows what to take out. Below D4000 part files are refused by
`check-decision-ids.mjs`, so the message there says to write the author's own
`D<issue>.md` citing the old decision. A file the change creates is not on the
base and passes whatever its size. `D4811.md` and `D4838.md` are not split.

**Why 10 lines.** On main from 2026-09-01 there were 822 edits to a decision
file that already existed: 140 grew it by 1-3 lines (one added a heading), 82
by 4-10 (32 added a heading, which the heading rule fails anyway) and 114 by
11-20, of which 91 added a heading and the rest appended an unheaded addendum
(`33f5c363b7`: eleven lines of later behaviour at the end of `D5207.md`). Ten
keeps a corrected sentence or an added bullet and refuses a paragraph of new
record.

**Part files too.** An existing `D<n>-p<k>.md` is one landed part's record,
and the next part writes the next file. Leaving part files open would move the
appends from `D<n>.md` to `D<n>-p2.md` and keep the conflict.

### The base

`test:guards` runs in CI's `suite` job, whose checkout is depth 1, so there is
no merge base to compute. On a pull request the checkout is GitHub's merge
commit, whose first parent is the base tip it merged into; the raw commit
names that parent even when shallow, so the guard reads it with `git cat-file`,
fetches that one commit at depth 1 if it is missing, and compares trees, which
needs no history. In the merge queue it uses `merge_group.base_sha` from the
event payload. Elsewhere (a local run, a checkout of the PR head) it takes the
merge base of HEAD with `DECISION_APPEND_BASE` or `origin/<GITHUB_BASE_REF or
main>`. It compares the base with the working tree, so a local run sees
uncommitted edits.

A base it cannot resolve, fetch, or find history to, and a base holding no
decision file, exit 2 with a "could not check" line, as
`migration-immutability-gate.mjs` and `changelog-gate.mjs` do: never a pass. On
a push (`GITHUB_EVENT_NAME=push`) there is no pull request to hold to a base,
so it prints "skipped, not checked" and exits 0, as `check-test-clock.mjs`
skips its base check on a push to main; the change was checked as a pull
request before it merged.

### Verification

`frontend/test/decision_appends_6466.test.mjs` builds git repositories under
the OS temp directory (no network) and runs the real script: an appended
`###` or `##` section, an unheaded addendum of 11 lines, a section added to an
existing part file and to a decision below D4000 fail with their instruction;
10 lines, a same-length rewrite, typo and link fixes, a renamed heading, a
heading in a fence, a new `D<n>.md`, a new `D<n>-p<k>.md`, and base-branch
edits made after branching pass; an uncommitted append fails; an unresolvable
base and a base with no decisions exit 2; a push skips with its line; a depth-1
clone of a PR merge commit run as a `pull_request` fetches the first parent and
both fails an append and passes a part file; this branch passes; and the guard
is in `test:guards` and `scripts/README.md`.

Mutation-checked with `scripts/mutation-check.mjs`, 19 of 19 caught: the
heading rule removed, the threshold one higher, gross instead of net growth, a
renamed heading counted as new, fences read, created files treated as
existing, part files unread, the wrong next part number, part files offered
below D4000, the merge's second parent, no fetch of the first parent, the
merge-commit path off, "could not check" as a pass, an empty base as a pass,
pushes not skipped, HEAD instead of the working tree, the base tip instead of
the merge base, the guard taken out of `test:guards`, and its README row
removed.
