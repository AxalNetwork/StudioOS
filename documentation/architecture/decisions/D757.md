### 1. What the owner asked for, and what main already has

**The ask, in the owner's words (2026-10-18, about 14:15Z):** "Telegram, WhatsApp, Google Call, Zoom and summaries … record into interview module, and distribute the information of the customer across modules: Problem discovery, Customer research, Ideal customer profile, Market intelligence, Demand and urgency signals, Experiments and evidence, Verdict. Create the engine to be able to populate these modules, including In-Person recording, voice-to text, then summarize into interviews." The connectors are for founders, who connect their own accounts to Validate. The owner had pressed **+** on the Zoom card and got "Zoom refused access … This integration is not yet configured on the server."

**What main already has.**

**Zoom is built end to end.** It came from D684 (#1577, PR #1581), D685 (#1585, PR #1612) and #1601 (PR #1614):
- per-member OAuth with PKCE and six granular scopes (`integrations/registry.ts:401-421`);
- token refresh under a lease (`services/channels/zoom.ts:282-372`);
- scheduling from an interview, with consent required (`routes/founder_validate_meetings.ts:221-310`, `:239-250`);
- attaching a pasted link to a live recording (`:140-219`);

- the VTT download with the member's own token, parsed into speaker- and time-stamped segments in the recorder's own table (`services/channels/meetings.ts:263-296`);
- a daily sweep, and 43 Worker tests.

**The owner's error means only that the Zoom app's secrets are unset.** `clientCreds` throws `zoom_oauth_unconfigured` (`zoom.ts:82-88`). The route turns that into a 503 (`routes/integrations.ts:1300-1301`). The page then calls every non-402 failure "refused" (`frontend/src/pages/account/connectorsModel.js:616-622`). D751 fixes that wording for every OAuth connector, and D757 does not repeat it.

**The in-app recorder** covers in person, video and phone. It runs voice-to-text, a cited five-sentence summary and Structure as one job (`services/interviewProcessing.ts:300-366`). Live transcription runs while recording.

**Google Meet** ("Google Call" in the owner's words; no other Google call product exists in code):
- Scheduling works on the Calendar connection.
- The transcript import is coded (`services/channels/googleMeet.ts`).
- The consent route exists: `POST /api/calendar/google/meet-transcripts/connect` (`routes/calendar.ts:812`).
- But no frontend calls that route, and the consent screen lacks the scope. So every Meet call settles as `meet_transcripts_unavailable` (`meetings.ts:72`).

**WhatsApp and Telegram text threads** land as `text` sessions when assigned to an interview (`services/channels/threads.ts:619-628`).

**D658's Structure** proposes seven kinds of finding, each tied to a cited span (`services/interviewStructuring.ts:90-166`). The founder accepts each one through that module's own writer (`routes/founder_validate_structure.ts:147-267`).

**What is missing, and D757 closes:**
- **Only recordings are summarised.** Zoom, Meet, chats, the pasted text chat and assistant submissions get findings but no summary. The import hands straight to Structure (`meetings.ts:344`); only `interviewProcessing.ts:350-355` summarises.
- **An accepted pain never reaches Problem discovery.** Accept writes only `interview_pain_severities` (`founder_validate_structure.ts:163-166`), while themes read `pains_json` (`services/cycleValidate.ts:202`).

- **Long calls are refused:** the limits are 100 KB of text and 12 model calls (`interviewStructuring.ts:183-184`).
- **Server-triggered runs ignore** the member's Manual mode and model pick.
- **No module page shows its pending suggestions,** and the Verdict hears nothing new.
- **Zoom is visible to every role,** and the OAuth start route checks no audience (`routes/integrations.ts:1240-1252`, unlike `/connect` at `:438`).

### 2. Decisions

#### 2.1 Zoom is switched on, not rebuilt
The adapter on main is the Zoom connector. D757 adds five things:
- the owner's app steps (§10);
- an honest distribution state;
- the founder-only audience (§2.11);
- the engine hand-off, which needs no change at `meetings.ts:344` (§2.2);
- the docs and a live check.

**The Zoom app is a General app, user-managed**, so each founder connects their own Zoom with no admin. It has:
- **Redirect:** `https://app.axal.vc/api/integrations/oauth/zoom/callback`.
- **Scopes, exactly these six:** `meeting:write:meeting`, `meeting:delete:meeting`, `cloud_recording:read:list_recording_files`, `meeting:read:meeting`, `meeting:read:list_past_instances`, `user:read:user`. The callback refuses any wider grant (`routes/integrations.ts:1364-1371`).
- **Event endpoint:** `https://axal.vc/api/channels/zoom/webhook`.
- **Events:** `meeting.ended`, `recording.transcript_completed` and `app_deauthorized`.

**Distribution is the real external gate.** An unpublished Zoom app can be authorized only by users in the developer's own Zoom account. Founders outside it need Zoom's beta share (up to 100 users, 4 weeks plus two 4-week extensions) or Marketplace publication. Until Zoom approves one of these, the Zoom page says so in plain words (§2.12). A non-secret var `ZOOM_APP_AUDIENCE` carries the state: `own_account`, the default, then `beta` or `public`.

**Consent stays two-layered:**
- the founder confirms that the interviewee agreed before Axal schedules a call (`founder_validate_meetings.ts:239-250`), and cloud recording happens only when the founder ticks it (`zoom.ts:417`);
- Zoom shows its own recording notice.

Zoom's notice is never treated as Axal's consent record.

**A transcript requires the member's plan:** Pro or higher, cloud recording on, and "Create audio transcript" turned on before the call. The UI says so. **There is no audio fallback in v1** (§2.14). A founder without Zoom transcripts can record in Axal during the call, using the attach-by-link path that exists (D685).

#### 2.2 One engine, one entry
A new file, `services/validateEngine.ts`, is the only code that runs a summary or findings model over a conversation:

```ts
digestSession(env, { sessionId, userId, trigger, stages?: ('summarise' | 'structure')[], force?: boolean }): Promise<DigestOutcome>
enqueueDigest(env, sessionId, userId, trigger)   // job type stays `session_structure` (models/jobs.ts:44)
```

It calls the two existing steps in order:
1. `summariseSession` (`interviewProcessing.ts:152-171`), widened to the digest (§2.5);
2. `structureSession` (`services/sessionAutoStructure.ts:65-106`), with the widened kinds (§2.6).

No source calls a model itself.

**Its callers:**
- **`runSessionStructureJob`** (`sessionAutoStructure.ts:116-124`) delegates to `digestSession`. So the existing hand-offs need no change:
  - `call_imported`, from Zoom and Meet (`meetings.ts:344`);
  - `chat_assigned` (`threads.ts:628`);
  - `chat_quiet` (`sessionAutoStructure.ts:131-144`).
- **The recorder's `interview_process`:** its `summarising` and `placing` stages call `digestSession` with one stage each (`interviewProcessing.ts:350-366`). The stage machine, resumption and sentences are kept.
- **The manual buttons:** `POST /sessions/:id/summarise` (`routes/founder_validate_sessions.ts:609`) and `POST /sessions/:id/structure` call it with `force: true`.
- **New triggers:**
  - `consent_given`, from `PATCH /sessions/:id/consent` (`:419`) when consent becomes `given` on a session that is already transcribed;
  - `chat_pasted`, from the pasted text chat (`openOn`, `:243-247`);
  - `assistant_submitted`, from `submit_interview` (`services/assistantInterviews.ts:298`). This one runs the summary only, because the assistant proposes its own placements;
  - `voice_note_added`, reserved for D754 W3 and D756.

The job type, `index.ts`, `queueWorker.ts` and `models/jobs.ts` are unchanged, so no S01 shared file moves.

#### 2.3 The ingestion contract every source meets
A source does exactly two things:

**1. It stores final segments on a session of an interview it already scoped to the member.** The entry points are the existing intake functions:
- `interviewIntake.appendSegments` for threads;
- `importTranscript` for meetings;
- `replaceWithFinal` for the recorder, the pasted chat and the assistant;
- D754 W3's voice-note mode for chat audio.

Each segment is:
```ts
{ id, start_ms, end_ms, speaker_label, speaker_raw, text }   // interview_transcript_segments, source = 'final'
```
- **A transcript** (recorder, Zoom, Meet, a call) has ms offsets and the provider's speaker name: Zoom's `Name:` or "Unknown Speaker", Meet's participant name or "Speaker ?".
- **A thread** (WhatsApp or Telegram text, including voice notes once transcribed) has one segment per message. Its time is the message time relative to the thread's first message. Its speaker is `Me` for the founder, or the interviewee (`threads.ts:113-117`).

**2. It calls `enqueueDigest(trigger)`, or reaches `interview_process`'s summarising stage.**

The engine derives the rest from the session:
- `source`, from `submitted_via` or `channel`: `recorder`, `zoom`, `google_meet`, `whatsapp`, `telegram`, `text_chat` or `assistant`;
- `kind`, which is `thread` when `channel = 'text'` and `transcript` otherwise.

The interview id always comes from the caller's scoped row, never from a payload (`interviewIntake.ts:1-19`).

#### 2.4 What the engine does, in order
1. **Re-scope.** `writableSession` (`interviewIntake.ts:147-155`). On failure the outcome is `not_writable`.
2. **Consent** (§2.10). An audio or video session without `given` consent stops with `consent_not_recorded` (`interviewSessions.ts:55`).
3. **Mode and model.**
   - The member's `validate` section in `ai_rail_preferences` (migration 465) gives the mode and the per-task model.
   - The recorder's per-session auto flag (`processing_auto`) wins for its own session.
   - **Manual mode stops after the transcript** and leaves Summarise and "Find suggestions" to the buttons.
4. **Segments.** If there are none, the outcome is `no_final_transcript`.
5. **Idempotency per transcript.**
   - `hash = sha256` over every final segment's `start_ms | end_ms | speaker_label | text`.
   - If the hash equals `interview_sessions.digest_hash` and the last run was `ok`, the run is a no-op (`unchanged`), unless `force` is set.
   - So a duplicate Zoom event, a re-import of the same VTT or a re-sweep never bills twice.
6. **Limits.**
   - The text cap rises from 100 KB to 400 KB, about eight hours of talk. It is still split on segment boundaries and never truncated.
   - At most three model calls per part.
   - Over the cap, the outcome is `too_long`, with a plain sentence and no charge.
7. **Summarise:** the digest (§2.5).
8. **Structure:** the typed findings (§2.6), stored as pending `validate_proposals` with `run_id`, `session_id`, `cite_from`, `cite_to` and `citation_json`, as today (`founder_validate_structure.ts:99-123`).
   - **On automatic triggers,** a finding whose kind and key were already proposed on this interview, in any status, is skipped. A discarded suggestion is never proposed again (migration 214's intent).
   - **Manual re-structure** keeps every finding, for Compare.
9. **State.**
   - `digest_status` is `queued`, `running`, `done`, `refused` or `skipped`, with the Worker's sentence in `digest_note`.
   - The session moves from `transcribed` to `structured` as today (`sessionAutoStructure.ts:102-104`).

**Re-runs are bounded.** A growing chat re-runs only when its hash changed, no more than once per `MIN_HOURS_BETWEEN` (6 h). The count includes summary receipts as well as structure receipts. The quiet sweep covers every `MESSAGING_PROVIDERS` value (`services/channels/types.ts`) instead of the literal list at `sessionAutoStructure.ts:136`.

#### 2.5 The digest: an Otter-like summary, the same for every source
**One model call per part,** using the existing `summarise_interview` task and receipt step. Its output is one JSON object, stored in `interview_sessions.digest_json`:

```json
{ "v": 1, "source": "zoom", "kind": "transcript", "hash": "…", "model": "@cf/meta/llama-3.3-70b-instruct-fp8-fast",
  "written_at": "…", "parts": 1, "run_id": "<the structure run>",
  "overview":   [{ "text": "…", "cite": { "from": 0, "to": 61000 } }],
  "key_quotes": [{ "quote": "…", "speaker": "Dana", "start_ms": 754000, "segment_id": 123 }],
  "decisions":  [{ "text": "…", "cite": { … } }],
  "next_steps": [{ "text": "…", "who": "me" | "them" | null, "cite": { … } }] }
```

**The rules:**
- **Speaker, time and segment id are computed from the stored segments** through `quoteSpan` (`interviewStructuring.ts:194-212`). They are never taken from the model.
- A quote that is not verbatim is dropped. So is a sentence with no citation (`:616-634`).
- **The typed sections come from the same run's suggestions, not from a second model output.** These are pain points, jobs to be done, objections, willingness to pay and budget, competitors and alternatives, and next steps. So the summary and the suggestions cannot disagree, and nothing is billed twice.
- `summary` and `summary_citations_json` stay as they are, for `SessionSummary.jsx` and `summaryOf` (`interviewProcessing.ts:174-179`).
- **Thread mode** frames a chat as interview notes over days, citing messages.
- **Per part:** summarise each part, then merge, keeping at most 5 overview sentences per part and 12 in total.

**The digest is a draft until the founder keeps it.**
- It reads "Draft · written by <model>", and only venture writers see it.
- **Keep** or **Edit** makes it the interview's summary. Edit changes the overview and next steps, and can remove a quote but never rewrite one. It is then shown on the Customer research record to everyone allowed to read that interview.
- Quotes stay behind the quote gate: `QUOTE_WITHHELD` unless `quote_consent = 1` (`services/records/validate.ts:250`).

This is "Eadwyn drafts; you send." Nothing the model writes is final without the founder's action.

#### 2.7 The founder accepts every suggestion
- **No AI output reaches a module without the founder's Accept.** There is no auto-accept setting in v1.
- **Accept, Edit or Discard** run the existing claim:
  - the claim is `WHERE id = ? AND status = 'pending'`;
  - an edit is validated as strictly as the model's payload;
  - the write goes through the module's own writer;
  - a failure returns the suggestion to pending (`founder_validate_structure.ts:217-280`).
- **Where the founder decides:**
  - **The session page.** All seven modules, grouped by module, with "Accept all for <module>". That is a new `POST /api/founder/validate/sessions/:id/placements/accept`, which runs each suggestion's own claim and writer and reports each outcome.
  - **Each module page,** in a "From your interviews" panel (`parts.suggestions`).
  - **The Customer research record,** in "Eadwyn's suggestions" and "What it fed", counted per module.
- **Every suggestion links to its source:** "Heard in <interviewee> · 00:12:31 · <speaker>" (for a thread, the message's date and time) → `/validate/session/:id?project=…#seg-<segment id>`.
- Only venture writers see pending suggestions.

#### 2.10 Consent
- **Any audio or video, from any source, is processed only with `given` consent.** That is today's rule (`interviewSessions.ts:55`).
  - **Zoom and Meet:** the founder confirms at scheduling.
  - **Recorder:** at start.
  - **Voice notes:** the contact's in-chat reply, or the founder's attestation (D754 W2).
- **Text threads and pasted chats keep D684's rule:** the founder is responsible, and there is no gate. This answers `D684.md:336` with "no". The assignment dialog reminds the founder.
  - A voice note inside a chat is gated at **transcription**, never at the engine. The engine sees only final segments.
- **Quotes shown to non-writers** follow `quote_consent`.
- **Withdrawal** (a session's consent becomes `declined`, or D754 W2 `withdrawn`):
  - no new run;
  - the digest is cleared;
  - pending suggestions from that session are deleted;
  - accepted module rows stay, without their quotes.

#### 2.11 Communication connectors are founder-facing, under Validate

  - the OAuth **start** and **callback** routes;
  - `/available`, and D753's `/directory/:key`;

  Existing connections keep Disconnect.
- **Where they show:**

**Where the build departs from the issue text, and why.**
- *The unchanged check reads the hash alone, not the hash and `digest_status = 'done'`.*
  `enqueueDigest` marks the row `queued` before its job runs, so the status is never `done` when the
  job reads it; only a completed automatic run writes the hash, so the hash alone says "digested".
  An unchanged run puts a `queued` row back to `done`, and a re-imported `transcribed` session back
  to `structured`.
- *The claim also requires, for an automatic run, that the stored hash differs from its own.* Without
  it, a second job that passed the hash check just before the first one finished could still claim
  and bill again. The new test caught it. A failed claim whose hash now matches is `unchanged`, not
  `busy`.
- *A stored model pick applies only to automatic runs.* A button's request carries the pick the rail
  shows, or none for the default, as it always has.
- *A consent refusal on a withdrawn session keeps the withdrawal's sentence*, which says more.
- *Errors thrown inside a stage release the claim* (written `refused` with the generic sentence) and
  rethrow, so a retry is never told it is busy.
