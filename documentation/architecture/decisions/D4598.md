## D4598 — Pitch: the check before sending reads the version that is sent, and a viewer's events land on their own link (#4598)

- **Status:** Part 1 built 2026-11-07 (the preflight gate and the attribution of view, timing, click and reaction events). Part 2 built 2026-11-09: the check moves into the Share and Export dialogs themselves, reading each dialog's own effective content, closing the issue.
- **Builds on:** D1370 (#3661, the preflight and its gate), D1573 (#3820, per-card analytics), D1500 (card uids), D1545 (hidden cards and button clicks), D902 (the share dialog).
- **No migration. Part 2 adds one route**, `POST /api/decks/:id/preflight/link-cards` (`deck_preflight.ts`).

### What was decided

1. **The gate before Share and Export checks the saved version (`PitchEditor.jsx`).**
   - Share and Export send the saved version. Before, the gate checked the working deck, so unsaved edits that fixed a defect cleared a saved version that still had it ("Checked with your unsaved edits. The link and the export carry the saved version until you save one.").
   - With no unsaved edits, the working deck is the saved one, and the one check serves both, as before.
   - With unsaved edits, the gate runs a second `usePreflight` on the saved version's own cards and theme. The panel ("Check before you send") keeps checking what is on screen. The second run borrows the first's dismissed set (`dismissedFrom`), so one version has one set and is read once.
   - The gate says which version it read: "v3 · the saved version that will be sent". With edits it adds: "You have unsaved edits. This check read the saved version, not your edits: the link and the export carry the saved version. Save a new version to send your edits, then check again."
   - With edits, the gate offers **Save a new version…** (it closes the gate and opens the save dialog) and drops Show me, because a finding's card place belongs to the saved version, not to the cards on screen. Saving is the founder's own step. The next Share or Export then checks the new version.
   - The check is bound to the version it read: a result for another state reads "Out of date" and runs again, as the hook already did (`currentResult`).
2. **Export's version picker (`ExportDialog.jsx`), part 1's behaviour.** The gate hands the dialog the version it read. If the founder picks another version, the dialog says "v2 was not checked. The check before you export read v3." It does not block: the picker is the founder's choice, and the sentence is the visible difference. **Superseded by part 2 below**, which checks the picked version instead of only flagging it.
3. **A viewer's events name only their own link's visit (`deck_share_actions.ts`, `decks.ts`).**
   - A view id sent with a heartbeat, a click, a feedback form, a sign-up, an NDA signing or the deal pack is accepted only if that view belongs to this link and this deck (`ownView`; the heartbeat checks the same).
   - A view id from another link or deck changes nothing of that view: no read seconds, no seconds per card, no signals. The event itself is kept on this link, under no view.
   - A heartbeat that names another link's view answers `{ ok: false }` and writes nothing.
4. **A reaction is filed on the card the link sent at that place (`/share/:token/feedback`).** The place is read against `linkSentCards`, the list the reader and the click route already use: the link's variant order, less hidden cards and what the link leaves out. Before, it indexed the version's stored cards, so a reaction on a tailored link, or on a deck with a hidden card, landed on another card.
5. **Time per slide still holds.** A link with it off stores the visit count only, as before.

### Part 2 — the dialogs check their own effective content (2026-11-09)

S1's 2026-11-08 guidance on issue #4598 answered the three questions part 1 left open without
needing the owner: move the final check into the dialogs; block, don't warn, on a picked
combination that was not checked; and the remaining tests. This part builds exactly that.

6. **The effective content a dialog is about to send, not the saved version as a whole.**
   - **Export** (`ExportDialog.jsx`) reads the picked version's own cards (`api.deckGet`), less
     any hidden one (`exportableCards`, mirroring the Worker's `visibleCards`: a hidden card is
     in no export). The two "include" options (speaker notes, the Sources appendix) add text
     elsewhere; they never drop a card, so they are not part of the checked combination.
   - **Share** (`ShareDialog.jsx`) reads the version's cards in the picked variant's order, less
     what "What is included" leaves out — through the new `POST /api/decks/:id/preflight/link-cards`
     (`deck_preflight.ts`), because that filtering (hidden cards, the Sources appendix, figures,
     bands, cap-table totals, team photos) is the same regex- and gate-aware logic `shareSlides`
     already carries, and duplicating it client-side was the drift risk the issue named. The route
     calls `decks.ts`'s new `effectiveSlidesFor`, which `linkSentCards` (part 1) now also calls
     through a shared `variantOrderOf` helper (by the variant's row id for a persisted link, by its
     uid for a proposed one) — one computation, so the check a dialog runs and the card a reaction
     later attributes to can never drift apart.
   - Both dialogs run this through the SAME hook, `useSendCheck.js`: it builds a `usePreflight`
     deck from the effective content, auto-runs the check whenever that content's `deckKey` hash
     (`preflightModel.js`) is not current, and exposes `gate` (`gateOf`), `blocked` and `confirm`.
   - `GateBody` (`PreflightPanel.jsx`) is `PreflightGate`'s Sheet body pulled out so the dialogs can
     draw the same fix/look groups inline, without a Sheet and without `onShow` (there is no slide
     to jump to from inside a dialog that may be open without an editor).
7. **Re-check on change, and block until clean or confirmed.** `usePreflight`'s result key is a
   hash of the checked content, so picking another version (Export), variant or "What is included"
   (Share) makes `current` false and the hook re-runs on its own. Export and Share's own actions
   are disabled (`send.blocked`) until that fresh check is clean, or its warnings are confirmed
   through **Export/Send anyway** — `useSendCheck`'s own `confirm()`, the SAME confirmation
   `PreflightGate`'s "anyway" already used in part 1, not a second one. The confirmation is keyed to
   the result it was given for (`confirmedKey === resultKey`): a run that lands back on content
   identical to something confirmed before switching away still asks again, because `confirmedKey`
   is cleared the moment a new run starts. "Anyway" only unblocks the action; the founder still
   presses Export/Create link, so confirming never sends by itself and a second press never sends
   twice. A content read that fails (network, not a finding) blocks too, with a plain "could not be
   read" line and **Try again** — never a silent pass.
   - The editor's own first-look gate (part 1, unchanged) still runs before either dialog opens,
     against the saved version with no variant or include choice yet: a fast early signal. It no
     longer hands the dialog a "checked version" (`checked`/`cleared` removed from `PitchEditor.jsx`)
     because the dialog now checks its own combination from scratch regardless of how it was opened
     — including the page-level "Share ▾" path that opens a dialog with no editor mounted at all,
     which part 1's gate never covered.
   - Export's old flag-only sentence ("v2 was not checked…", `notCheckedLine`) is retired along with
     the `checked` prop: a picked version is now actually checked, not just flagged.
