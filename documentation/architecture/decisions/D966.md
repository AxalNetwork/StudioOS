## D966 — Mercury SAFEs accepted before #2629 take `post_money`, through the owner's dry-run-first repair

- **Status:** decided by S1 on #2630 (2026-10-26, from S1's block) and built by S1 at the owner's request. Running it against production is the owner's act.
- **Basis:** `origin/main` at `f593052`.
- **Migration:** none.
- **Why:** before #2629 (`d15d97bd2f`), `acceptRaiseProposal` called `addHolder` without a basis, and `safeEntry` never stored one.
  - So every Mercury SAFE accepted before #2629 sits in its venture's `cap_table_scenarios.inputs_json` with no `basis`.
  - `simulate` reads such an entry as the legacy pre-money SAFE, but Mercury's SAFE requests carry a post-money cap.
  - #2629 fixed every later Accept and deliberately repaired no data. The number of affected production scenarios is not known.

### 1. What is repaired

**The candidates.** `services/mercury/safeBasisRepair.ts` reads one page at a time:

```sql
SELECT id, project_id, local_id, target, payload_json FROM mercury_raise_proposals
 WHERE id > ? AND kind = 'safe' AND status = 'accepted' AND local_table = 'cap_table_scenarios'
 ORDER BY id LIMIT ?
```

- **Why these columns.** This is exactly where the pre-#2629 Accept landed:
  - `kind` is the proposal's own column (migration 520: `fund_mapping`, `statement`, `safe` or `investor_credit`);
  - `local_id` is the venture's canonical scenario at the time;
  - `target` is the entry key (`e-<n>`) that `addHolder` returned;
  - `payload_json` holds the terms the Accept passed to `addHolder`.
- **Not candidates.** Accepts since D1017 land on `cap_table_issuances`. Between #2629 and D1017, Accepts landed here with a basis, so they report `has_basis`. A founder who disconnected Mercury has no rows here at all (§6).

**The repair.** A candidate is repaired only when all of these hold:

- `local_id` still names a canonical (`is_variant = 0`) `cap_table_scenarios` row of the proposal's own venture;
- no other accepted SAFE proposal names the same scenario and key;
- the recorded key names exactly one entry in the three keyed lists (`founders`, `safes`, `rounds`, which share one key sequence);
- that entry is a SAFE: a `safes[]` entry whose `instrument` is absent or `safe`;
- its `basis` is absent or null, the two spellings `safeEntry` and `validateInputs` both read as none;
- its `amount`, `cap` and `discount` are exactly what the Accept stored from `payload_json` (§2);
- the venture's cap table is still its model. `readCapTable(env, projectId).source !== 'record'` is the check `acceptSafe` makes before writing the model (`raiseFeeds.ts`);
- the inputs with the basis added pass `validateInputs`.

Then that one entry gains `basis: 'post_money'`, and the results are recomputed.

### 2. What is never touched

- **No entry is matched by investor name.** Only the key the proposal recorded is used. A manual SAFE under the same investor name, or a deleted entry's namesake under a new key, is left alone.
- **Only the entry the Accept wrote.** The key alone does not prove it:
  - a client that posts no keys (`SpinoutLabCapTablePage`'s `normalizeInputs`: name, amount, cap and discount) sends the same body for "edit the Mercury row" and "delete it and type a namesake";
  - `withEntryKeys` gives a keyless posted entry the key of a stored entry of the same name, so the recorded key can by then name a hand-typed SAFE.

  So the repair writes only an entry that still carries the exact terms the Accept wrote: `amount`, `cap` and `discount` equal to what `safeEntry` stored from the payload's `amount_cents`, `cap_cents` and `discount_pct`. The conversion is `safeEntry`'s own (`safeTerms`, exported from `capTableWrites.ts`); absent and null are one value. Any other entry, and a payload that cannot be read, is `entry_changed`, left for the owner and listed by proposal id and key. A founder's own edit of the terms is left too: that entry is then theirs.
- **No entry but the target.** The rest of `inputs_json` is written back as it was read: other entries, keys, `entry_key_seq`, rounds and exits. Only that entry's `basis` is added. This holds byte for byte, so the write does not go through `saveScenario`:
  - its `withEntryKeys` and `keepOwnHolders` can change an entry other than the target;
  - and its write is unconditional.
  The repair recomputes with `simulate`, the engine every save runs, and writes the same columns.
- **No inputs the engine refuses.** `simulate` answers `{ errors }` rather than throwing when `validateInputs` fails, so inputs that fail it (an older save can leave such a value elsewhere in the table) are `inputs_invalid` and never written.
- **A stated basis,** `pre_money` included, is kept (`has_basis`).
- **Manual instruments.** A SAFE no proposal names is never read for a write.
- **Draft variants are never written,** even one holding an entry under the same key. A key in a copy proves nothing about where the entry came from (#2630). Each row lists, by id, the venture's variants that hold a SAFE with no basis under its key (`variants_untouched`). Repairing them is a separate decision.
- **Provenance:** the proposal row, its `connector_fed_items` ledger row and the scenario's uid, owner, venture, name and `created_at` are not written. Only `computed_at` and `updated_at` move.
- **Record ventures,** whose cap table is read from the record (D1017, D1018).

### 3. The outcomes

Each candidate gets one outcome, decided in this order:

| Outcome | When | Written |
|---|---|---|
| `scenario_missing` | `local_id` is null, names no row, or names a draft variant | no |
| `scenario_other_venture` | the row belongs to another venture, or to none | no |
| `ambiguous` | another accepted SAFE proposal names the same scenario and key, or the key names more than one entry | no |
| `entry_missing` | the key names no entry (deleted, or replaced under a new key), the target is not a key, or the inputs cannot be read | no |
| `entry_not_safe` | the key names a founder, a round or a note | no |
| `has_basis` | the SAFE states a basis | no |
| `entry_changed` | the SAFE's amount, cap or discount is not what the Accept stored from the payload, or the payload cannot be read | no |
| `record_venture` | the SAFE needs the repair, but the venture reads from the record | no |
| `inputs_invalid` | the inputs with the basis added fail `validateInputs` | no |
| `would_repair` | a dry run: it would be written | no |
| `repaired` | written | yes |
| `conflict` | the scenario changed after it was read | no |
| `failed` | a read or the write threw; the walk went on | no |

A dry run never answers `repaired` or `conflict`, and answers `inputs_invalid` as a write would.

### 4. The write

The write is one D1 batch of two statements under one guard: this row is still that venture's canonical scenario, with the `inputs_json` that was read.

1. **The rollback record:** an `admin_audit_log` row, action `mercury_safe_basis_repaired`, inserted only `WHERE EXISTS` the guarded row. It holds:
   - `admin_user_id`, the operator;
   - the reason;
   - the proposal, venture, scenario id and uid, the key, the list and index;
   - `prior_entry`, the entry exactly as it was.
2. **The scenario:** `UPDATE cap_table_scenarios SET inputs_json, result_json, computed_at, updated_at … WHERE id = ? AND project_id = ? AND COALESCE(is_variant, 0) = 0 AND inputs_json = ?`. `result_json` is `simulate` on inputs `validateInputs` has passed.

- **Both land or neither does.** If the guard no longer holds, neither statement matches: the outcome is `conflict` and nothing is written.
- **A batch that throws rolls back whole.** That is `failed`, and neither statement is written.
- **After a write,** D632's `captable_scenario_updated` row goes into `activity_logs` with the venture, best effort and by ids only: `{ scenario_uid, is_variant: 0, repair: 'D966', entry_key }`. The founder's History › Changes then says who changed the scenario.
- **Run twice, the second run writes nothing.** A repaired entry has a basis, so it reports `has_basis`.

No existing history table holds a scenario's prior inputs, so the rollback record is the audit log's own row per repaired entry. `admin_audit_log` is sealed against UPDATE and DELETE (D156). Unlike the run's audit, this row holds the investor's name and amounts, because it is the entry as it was.

### 5. The route

`POST /api/admin/mercury/safe-basis-repair` (`routes/admin_mercury_safe_basis.ts`), mounted beside D710's `admin_mercury.ts`. It reads none of Axal VC's entity accounts. It copies D892 §6's reconciliation:

- **Body:** `{ dry_run?: boolean, reason?: string, after?: number, limit?: 1..100 }`.
- **Answer:** `{ dry_run, checked, counts, written, rows: [{ proposal_id, project_id, scenario_id, entry_key, outcome, variants_untouched }], next_after }`. `counts` has every outcome, zeros included.
- **A dry run unless `"dry_run": false`.** A dry run reads and writes nothing, and needs a Super Admin (`requireSuperAdmin`, which also refuses a branch).
- **Writing** takes the write bar (`requireSuperAdminWriteBar`: a TOTP session, a recent step-up, the holder). It also takes a `reason` of 1 to 500 characters, or it answers 400 `reason_required`.
- **The recovery cool-off pauses it,** dry runs included: 423 `recovery_cool_off_active`. The route is on `index.ts`'s `COOL_OFF_ROUTES` (D248), because it writes founders' cap tables, the money-adjacent class D892's reconciliation is paused under (`/api/admin/billing`). It is the exact route, never `/api/admin/mercury` as a prefix, so D710's entity reads stay open.
- **Paging:** `after` is a proposal id (default 0). `limit` defaults to 25 and is clamped to 1..100. `next_after` is the last id of a full page, and null once the walk has read every candidate.
- **A run that fails part-way says what it wrote.** A row whose read or write throws is `failed`, and the walk goes on. The answer is 200, with `written` and every row's outcome. Only a page that cannot be read answers 503 `repair_unavailable`, "Nothing was written", and then no row has been touched.
- **Every run is audited,** dry or written, failed part-way or not. That is one `logAdminAction`, as `mercury_safe_basis_repair_dry_run` or `mercury_safe_basis_repair`, holding:
  - the page asked for (`after`, `limit` as clamped), `checked`, the counts, `written`, `next_after` and the reason;
  - each row's ids, key, outcome and untouched variants.

  A run whose page could not be read carries `failed: "page_unreadable"`. The rows are keyed by `proposal_id`, `project_id` and `scenario_id`, never `user_id` (D159). The audit insert stays best-effort, as D159 has it. The per-row rollback record (§4) is not best-effort: it lands with its change.
- **No answer and no run's audit carries a name, an email or an amount.** A target that is not a key is answered as `entry_key: null`, never echoed.

### 6. How the owner runs it

The owner runs it against production; no deploy, cron or agent session runs it. There is no HQ button: POST from a Super Admin's own session, outside a recovery cool-off, as D892 §6's reconciliation is run.

1. **Dry run first:** `{}`, then `{ "after": <next_after> }` until `next_after` is null. Read the counts and every row: this is the answer to "how many scenarios are affected", for ventures still connected to Mercury.
2. **Write:** `{ "dry_run": false, "reason": "<why>" }` with a fresh step-up. Repeat with `"after": <next_after>` until `next_after` is null.
3. **Re-run** any page that reported `failed` or `conflict`. A repaired row then reports `has_basis`. A `conflict` whose founder changed the SAFE's terms in between then reports `entry_changed`.
4. **Decide the rest yourself:** `record_venture`, `ambiguous`, `entry_changed`, `inputs_invalid` and any `variants_untouched` are reported for you and changed by nothing here.

**Disconnected ventures are out of the repair's sight.** `mercury_raise_proposals.integration_id` is `REFERENCES integrations(id) ON DELETE CASCADE` (migration 520), and disconnecting deletes the `integrations` row (`DELETE /api/integrations/:uid`). So a founder who disconnected Mercury lost every proposal row, and the repair cannot see the SAFEs they accepted before #2629. Nothing matches them by name and nothing writes them: each is the owner's to look at by hand.

The pre-#2629 Accept also wrote one activity row (`log` in `raiseFeeds.ts` → `logCycleWrite`): `activity_logs` with `entity_type = 'raise.cap-table'`, `entity_id` the entry key and `action = 'mercury_safe_accepted'`. That row stays when the connection goes. This read-only query counts those Accepts with no surviving accepted proposal for the same venture and key, and how many of them still sit on the venture's canonical cap table as a SAFE with no basis. Today's Accepts log a record uid, never an `e-<n>` key, so they are not counted:

```sql
SELECT COUNT(*) AS accepts,
       COUNT(DISTINCT a.project_id) AS ventures,
       COALESCE(SUM(EXISTS (
         SELECT 1
           FROM cap_table_scenarios s,
                json_each(CASE WHEN json_valid(s.inputs_json) THEN s.inputs_json ELSE '{}' END, '$.safes') e
          WHERE s.project_id = a.project_id AND COALESCE(s.is_variant, 0) = 0
            AND json_extract(s.inputs_json, e.fullkey || '.key') = a.entity_id
            AND COALESCE(json_extract(s.inputs_json, e.fullkey || '.instrument'), 'safe') = 'safe'
            AND json_extract(s.inputs_json, e.fullkey || '.basis') IS NULL
       )), 0) AS without_basis
  FROM activity_logs a
 WHERE a.entity_type = 'raise.cap-table' AND a.entity_id GLOB 'e-[1-9]*' AND a.action = 'mercury_safe_accepted'
   AND NOT EXISTS (
     SELECT 1 FROM mercury_raise_proposals p
      WHERE p.project_id = a.project_id AND p.kind = 'safe' AND p.status = 'accepted'
        AND p.local_table = 'cap_table_scenarios' AND p.target = a.entity_id
   );
```

Its filter leads with `entity_type` and an `entity_id` prefix, the columns of `idx_al_entity`, and it answers one row. To see which ventures, select `a.project_id, a.entity_id` in place of the counts and add `LIMIT 100`. Between #2629 and D1017 an Accept wrote a basis, so `without_basis` is the number that matters; `accepts` includes those.

### 7. Rollback

Each repaired entry has its `mercury_safe_basis_repaired` row. To undo one:

- read its `scenario_id`, `list`, `index`, `entry_key` and `prior_entry`;
- check the scenario's entry at `list[index]` still has that key and equals `prior_entry` plus `basis: "post_money"`. If it does not, the founder has changed it since, and it is theirs;
- put `prior_entry` back at `list[index]`;
- recompute `result_json` with `simulate`, under the same `inputs_json = ?` guard.

The tests prove the record restores the inputs byte for byte, with the SAFE last of its list and first of three. No rollback route is built; the record is what makes one possible.

### 8. The proof

`cloudflare-worker/test/mercury_safe_basis_repair_d966.test.ts` runs on node:sqlite. It uses the baseline tables and migrations through `_mercury_raise_fixture.ts`, the real route behind the real guards, the real writers (`addHolder`, `saveScenario`, `updateHolder`) and the real engine. Nothing on the write path is stubbed. The pre-#2629 Accept is replayed as `d15d97bd2f~1` had it: the claim, `addHolder` with no basis, the landing on the canonical scenario, its ledger row and its activity row. All data is synthetic.

1. **A pre-#2629 Accept leaves a SAFE with no basis.**
   - The dry run reports it and writes nothing.
   - The write adds `post_money` to that entry alone. The inputs equal the old ones plus that basis, byte for byte.
   - It recomputes: `post_money_check` goes from 0 to 0.005, and the SAFE converts post-money in the round.
   - It keeps keys, variants, the proposal, the ledger and the namesake and manual SAFEs.
   - It writes the rollback record (which restores the inputs byte for byte) and D632's row.
   - A second run, dry or written, reports `has_basis` and writes nothing.
2. **A SAFE accepted today lands on the record** with its basis, and is no candidate.
3. **Every skip is reported and left byte-identical,** written or not:
   - a stated basis;
   - a deleted entry;
   - a namesake under a new key;
   - an entry made a note;
   - a key re-used by a founder;
   - a target that is no key;
   - a deleted scenario, and a proposal with no `local_id`;
   - a scenario moved to another venture, and a proposal naming another venture's;
   - a `local_id` naming a draft variant;
   - unreadable inputs;
   - a record venture;
   - a key under two entries, and two proposals claiming one key.

   Another kind, a dismissed SAFE and a SAFE landed on the record are never candidates. In the same run, a SAFE stored with `basis: null` and one stored with `instrument: 'safe'` spelled out are repaired, and the manual SAFE beside them is not.
4. **A founder's save between the read and the write** is `conflict`: no basis, no rollback record. On the next run, the SAFE whose amount the founder edited (`updateHolder`) is `entry_changed` and written nothing; the one whose table changed elsewhere (an exit, through `saveScenario`) is repaired.
5. **A write that throws on the second of three rows:**
   - the first and third rows are written, and the second is `failed`, with no rollback record;
   - the answer is 200, `written: 2`, and never says "nothing was written";
   - the run is audited, and the next run repairs the failed row.

   A page that cannot be read answers 503 and is audited with `page_unreadable`.
6. **Refused:** no session (401); a founder or a plain Admin (403, dry or written); a write without a recent step-up (403); a write without a reason, or with a blank, 501-character or non-string one (400). A refused request writes nothing and is no run.
7. **Paging:** `limit: 1` and `limit: 2` walk each candidate once, past a pending proposal, with `next_after` null at the end. A written walk repairs each candidate once. The default page is 25, a page is at most 100, and below 1 reads 1. Each run's audit holds the `after`, the clamped `limit`, `checked` and `next_after` of its page.
8. **The terms check,** on the real writers. `entry_changed`, its table byte-identical:
   - one `saveScenario` deletes the Mercury entry and adds a keyless namesake on other terms, which takes the Mercury key;
   - the Mercury SAFE and a manual namesake on other terms, then a keyless save without the Mercury row in `normalizeInputs`' shape, which hands the manual SAFE the Mercury key. The manual SAFE gets no basis;
   - the cap alone, and the discount alone, edited through `updateHolder`;
   - a payload that is not JSON, and one whose amount `safeEntry` refuses.

   The founder's keyless re-save of the Mercury SAFE itself, posting `cap: null` where none was stored, is repaired: absent and null are one value. An edited amount with a stated basis is `has_basis`.
9. **Inputs that fail validation** (an option pool of 95%) are `inputs_invalid` in a dry run and a write. Nothing is written, and no errors are stored as results.
10. **A read that throws** on the second of three rows (its variants, its scenario, the claimants, or `readCapTable`) makes that row `failed` alone. The walk goes on, the third row is written, and the run is audited.
11. **`variants_untouched`** lists only the venture's own drafts that hold a SAFE with no basis under the key (`instrument: 'safe'` spelled out included). Another venture's draft under the same key is not listed, and neither are a founder, a note or a stated basis under it.
12. **The rollback record of a SAFE first of three** names index 0 and restores the inputs byte for byte.
13. **The write guard's venture and canonical flag:** a scenario made a draft, or moved to another venture, between the read and the batch is `conflict`. Nothing is written and there is no rollback record.
14. **A disconnected founder:** deleting the connection row takes its proposals (`ON DELETE CASCADE`, real SQLite foreign keys), and the repair sees only the still-connected venture. §6's query, read from this file, counts four Accepts in two ventures, two without a basis. It does not count today's Accept, a surviving proposal, a key repeated in another venture, a stated basis, a note or a draft.
15. **The cool-off:** the route is on `COOL_OFF_ROUTES` as the route itself, and `/api/admin/mercury` is no cool-off prefix. `impersonation_d248.test.ts`, on the bundled worker, shows the 423 for a dry run and a write, while D710's Mercury read under the same mount is not paused.

Every answer, and every run's audit, is checked for the invented names, emails and amounts.

**Mutation-checked on 2026-10-26.** The first build: 53 single mutants, 53 killed. Two were equivalent and not counted:

### 9. UNVERIFIED until the owner's run

- **How many production proposals are candidates,** and how they split by outcome: the dry run answers this.
- **How many disconnected ventures hold such a SAFE:** §6's query answers this, read-only. The repair cannot see them.
- **How many entries the founders changed after the Accept** (`entry_changed`), and whether any production table fails validation (`inputs_invalid`): the dry run answers both.
- **Whether production holds the shapes the tests build by hand:**
  - two entries under one key;
  - two accepted proposals naming one key, which a lost-update race between two Accepts could leave;
  - a `local_id` naming a variant.
- **That D1 reports `meta.changes` per statement of a batch** for the guarded UPDATE, as the node:sqlite fixture does. D892 §6's repair relies on the same.
- **That a scenario's `inputs_json`, bound twice in one batch, stays inside D1's statement limits** for the largest production scenario.
