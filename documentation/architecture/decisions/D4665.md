## D4665 — A send is an operation with a recorded outcome (#4665)

Package 1 of 6 of the Email audit (findings 1, 2 and 12). Migration `202611071530_mail_send_operations`.

**The problem.** `POST /api/mail/send` did the provider call, the credential update and the sent-log write in one `try`. A failure after the provider accepted the email was logged as a failed send and answered as an error, and the composer's next press fetched a fresh nonce and sent again. Outlook's draft-then-send route needed `Mail.ReadWrite`, which the send-only consent does not grant. The 20-an-hour check was a count taken before the send, so concurrent sends could all pass it.

**The model.** One `mail_send_ops` row per logical email, written before any provider I/O (`services/mail/sendOps.ts`).

| State | Meaning | Holds a place in the 20 an hour |
| --- | --- | --- |
| `pending` | admitted; the provider has not answered | yes |
| `accepted` | the provider took it | yes |
| `uncertain` | the provider may or may not have it | yes |
| `refused` | the provider definitely did not take it | no (released) |

- **Identity.** The composer sends `operation_key` (kept across retries of one composition; a server-made one when a caller sends none, so the Distribution and inbox callers are unchanged). The row stores a fingerprint of mailbox, recipient, subject, body, draft and introduction. The same key with the same fingerprint is a replay; the same key with a changed message is `409 operation_changed`.
- **Replay never reaches the provider.** It is read before the nonce is spent, so a repeat needs no new confirmation and cannot send twice. `accepted` is re-reconciled (sent-log row, sequence step, introduction record: each already idempotent) and answered `200 { recovered: true }`; `uncertain` and `pending` answer `202` with the state.
- **Acceptance is written first.** The moment the adapter returns, the row becomes `accepted`; the credential update, the sent-log insert (`ON CONFLICT(uid) DO NOTHING`, with the operation's uid) and the introduction record each fail alone and are retried on replay.
- **Reservation.** Admission is one `INSERT … SELECT … WHERE (count of the member's non-refused rows in the last hour) < 20`, so two concurrent sends cannot both take the last place. Recovery reuses the same row. A wrong nonce deletes the row it briefly held. `refused` releases; `pending`, `accepted` and `uncertain` hold. A pending row whose Worker died (no update for 120 s) becomes `uncertain`, never `refused`. There is one send entry point (`POST /send`); every composer, the sequences and the inbox go through it.
- **Uncertain is explicit.** `GET /send/operations/:uid` reads the state; `POST /send/operations/:uid/resolve { outcome: arrived | not_arrived }` is the member's word after looking in their Sent folder. `arrived` makes it `accepted`; `not_arrived` makes it `refused` and frees the place. The composers show "Not confirmed" with both buttons and hold Send until the member answers. A request that got no answer from the Worker says the outcome is unknown, never "Nothing was sent".

**Adapters.**
- **SMTP.** Once the payload is written, a lost answer is `uncertain`; a 4xx/5xx after DATA is a refusal; `250` is acceptance, and QUIT is best effort (RFC 5321 §6.1: final DATA acceptance transfers responsibility).
- **Outlook.** `POST /me/sendMail` with `Mail.Send`, the only mail permission asked for. No draft is created. `sendMail` returns no message id, so `provider_message_id` is null for new Outlook sends; reading a thread back still needs the optional `Mail.Read` grant and says so itself (D4494). A `403` is the new `consent` code: the mailbox turns `expired` with "Reconnect the mailbox and allow sending", not "could not be reached". A network failure or 5xx after the request left is `uncertain`.
- **Gmail.** Same classification: `403` consent, network failure or 5xx `uncertain`.
- **Product messages** are written here; no provider text is returned.

**Tests.** `mail_accounts_d1340`: QUIT failure after `250`, refusal after DATA, accepted-then-bookkeeping-failure with a recovered replay (the server saw one DATA), a changed message under the same key, a lost answer kept uncertain across a repeat and resolved, a dead pending row, 30 concurrent admissions admitting exactly 20, a replay taking no second place, a refused place released, a wrong nonce freeing its place, and Outlook fixtures that enforce Microsoft's documented permissions (`sendMail` needs `Mail.Send`, Create message needs `Mail.ReadWrite`). `email_send_operation_4665` (frontend): key stability, outcome reading, the unknown-outcome line, and both composers' wiring. Existing fixtures that mocked the draft route now mock `sendMail`.

**Not done here; stays in #4665 or its neighbours.**
- An authorized provider acceptance check against a real Outlook mailbox. The audit's own caveat stands: nothing here sent real email.
- Introduction sending stays on #4604's lifecycle. This package only makes its post-send record safe to retry; it does not change that lifecycle.
- Sent-log presentation of `uncertain` rows (the history package, #4662) and account-update persistence (the mailbox-lifecycle package, #4654). An `uncertain` send is already written to `mail_sent` with `sent_at` null and an error sentence.
- MCP-mailbox sends keep their current classification: the adapter maps the custom tool's errors, and an error it cannot classify is `uncertain`.
- Detailed quota-race evidence belongs in the private security report, not here.
