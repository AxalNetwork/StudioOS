## D4599 — Pitch Overview: the first-use import, and the reads it stopped making (#4599)

Pitch audit 5/5 (#4599). This PR does two of the issue's three parts: the
import entry on the no-deck Overview, and the Overview's request baseline with
the duplicate and nonessential reads removed. The third part, the recorded
walkthrough UI (pd36 Record, pd35's Walkthrough column), is not in it, so the PR
says "Part of #4599".

### 1. The first-use import

The no-deck Overview (ps2) offered two ways in: from your records, and from a
template. The Pitch Studio v2 canvas (`design/incoming/Pitch Studio v2 Page.dc.html`,
`homeFirst`) draws a third, "Import a deck or document", and its words:
"A .pptx becomes editable cards. A PDF, DOCX or pasted text becomes an outline
you approve card by card." That is what the import does
(`routes/deck_imports.ts`, D1563). A PDF is never described as an editable
copy of its slides.

- It is `NO_DECK_ITEMS`' third item (`pitchOverviewModel.js`, `IMPORT_LINE`).
  `PitchOverview`'s `NoDeck` opens the Decks tile's own sheet,
  `DocumentImport.jsx` (#3810), in place. It is not a second import flow, and
  nothing is sent until the founder drops a file or presses Import.
- It is gated on `availability('importDocument')`, the same gate the Decks
  tile's Start from uses. When the import is switched off on this Worker, the
  card is drawn greyed with "Coming later" and opens nothing.
- A reader (an admin) gets no ways in, as before.
- The grid is one column on a phone and three from `md`, so the entry is on the
  first screen at both widths. The Sheet is already a phone sheet.

The rest of the canvas's first-use page (the price card, "What your data can
fill") is not in this PR. This PR adds the import door and nothing else.

### 2. The Overview's loading contract

**How it was measured.** `frontend/test/pitch_overview_reads_4599.test.mjs`
mounts the whole studio (`PitchStudio tab="overview"`, with its rail and Ask)
on a stubbed `fetch`. It uses one synthetic venture and records every request
the real clients send. The baseline was taken on `main` 8656c52e5f with the
same harness.

| | Before | After |
|---|---|---|
| Requests, venture with a deck | 43 | 35 |
| Requests, venture with no deck | 16 | 10 |
| `GET /decks/null/usage` (a read for a deck not known yet; 404) | 3 + 3 | 0 |
| `GET /decks/:id/usage` | 3 | 1 |
| `GET /decks/:id/model-presets` | 2 | 1 |
| `GET /cycles/raise/modules/pitch-deck` on the Overview | 1 | 0 |
| `GET /decks/checks` with no deck | 1 | 0 |
| Serial depth to the deck card | 3 (ventures → versions → deck) | 3 |

**Not recorded:** bytes transferred and time to useful content. Both need a
real browser against a real Worker with an authorized test account. A
stubbed `fetch` measures neither, and nothing here estimates them.

**What changed.**

- **The rail read usage for a null deck.** `deckRail(null)` ran before the
  versions read answered, and each of its three usage rows asked
  `/decks/null/usage`. A deck that is not known now answers "unavailable"
  without a request (`deckRailGroups.js`), and those rows are hidden as before
  (`hideUnavailable`).
- **Three rows, one read.** The rail's Estimated, Spent and plain-units rows
  read the same `/usage` reply at the same moment, and the presets and HQ's
  locks read the same `/model-presets` reply. Both clients now go through
  `sharedRead` (#4622). It shares only a read already in flight. Once that read
  settles nothing is kept, so a later read, or a read after a preset is picked,
  is fresh.
- **The module read waits for the tab that draws it.** Only Decks
  (`StudioHome`) and Share & analytics draw `reads.module`. The Overview,
  Script, Review and Notes (`NO_MODULE_TABS`, `PitchStudio.jsx`) leave it
  idle, and a tab not on that list reads it as before. A finished read for the
  same venture is kept, and its tab reads again on arrival.
- **No deck, no check pills.** The version checks are drawn on the deck card
  only. With no current version, `useDeckChecks` is not called with a venture.

**Kept, and why.**

- **Ventures → versions → deck stays serial.** Each read needs the id the one
  before it returns. Removing a step means a Worker read that answers the
  current version with the venture, and that is not part of this PR.
- **The four per-deck status reads** (rehearsals, comments, notes, investor
  links) are what the four status cards and the activity list draw. They run
  in parallel after the versions read.
- **The sources read** runs alongside the versions read rather than after it,
  so the deck card does not wait an extra round trip. With no deck it is spent,
  but holding it back would slow every venture that has one.
- **The Ask's eleven proposal reads**, one per deck option
  (`DeckAsk.readEdits`), feed the Ask button's waiting count. The Worker's
  `GET /ai/rail/proposals` takes one `option` (or a rail `page`) per read.
  Folding them into one read is a Worker change on a shared route, so it is
  left to its own issue.
- **`/ai-budget/me` and `/ai-budget/holds`, twice each,** come from the shared
  AI rail and are read on every page that mounts it, not only Pitch. They are
  outside this PR.

### 3. Not in this PR: the recorded walkthrough

The Worker routes and client exist (`routes/deck_recordings.ts`,
`lib/api/deckRecordings.js`, D1590). The retention decision #3837 refers to is
settled: owner decision **W = A** (2026-11-02, D1590). A take is kept until its
maker deletes it, or until its deck or account goes. The walkthrough is behind
the `deck:walkthrough` feature flag, and `deckV2Adapter.walkthrough` is still
`off(...)`. Connecting the pd36 Record screen and pd35's Walkthrough column to
those routes is the remaining part of #4599. Wiring the UI does not turn the
flag on.
