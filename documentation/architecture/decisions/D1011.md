## D1011 — Payments part 3, the Worker: the change log read, failed syncs recorded, and webhook deliveries per hour

- **Status:** built by S26 for #2830 (part 3 of Payments, #2386), 2026-10-24. Migration: none.
- **Basis:** `origin/main` at `f08de28b7a`. S21's page (D1008) is not on `main` yet, so this part is the Worker and its client only; the page draws them when it lands. Worker paths are relative to `cloudflare-worker/src/`.
- **Canvas:** `design/incoming/Payments Page.dc.html`: PAY5 (deliveries per hour), PAY6 C (sync failed) and PAY7 (the change log).

### 1. The change log (PAY7): `services/paymentsChangeLog.ts`

- **One reader for both writers.** The catalogue's writes (`routes/catalog.ts`, `writeAdminAudit`) and the Stripe settings' writes (`routes/admin_stripe.ts`, `logAdminAction`) already land in `admin_audit_log`. `CHANGE_ACTIONS` names those fifteen actions and what each changed: `product`, `price`, `sync`, `token_pack`, `webhook` or `key`. Nothing new is written for a change.
- **A test holds the list to the code.** It reads both route files and asserts that the actions they write are exactly `CHANGE_ACTIONS`, so a new write cannot be missing from the log.
- **What a row says:** its time, what changed, the action, who did it (account id and name, never an email), and the product and price it names. A row that names only a price is filed under its product through the catalogue mirror (`stripe_products.prices_json`), so filtering by a product finds its prices' changes. A price the mirror no longer holds keeps its row, with no product.
- **Filters:** `what`, `who` (an account id), `product` (`prod_…`), `from` and `to` (`YYYY-MM-DD`, inclusive, UTC). A filter that cannot be read is a 400 that names it.
- **Pages:** `limit` (50 by default, at most 200) and `offset`, with the `total` the filters match.
- **A read creates nothing** (D204's rule for GETs). A database that does not answer is a 503 with a sentence, never an empty list.
- **Money:** a row's details are returned as written. Amounts stay in the currency's smallest unit, and no two rows' amounts are added.

### 2. The export

- `GET /api/admin/payments/change-log.csv?…&reason=` gives the same filtered rows as a CSV (`services/csv.ts`), at most 5,000. `X-Export-Rows` gives the count, and `X-Export-Capped` says whether it stopped at the cap.
- **The reason is required:** 10 to 500 characters.
- **It is recorded before the file leaves,** as `payments_change_log_export` in `admin_audit_log`, with the reason, the filters and the row count. The write **fails closed**: if it cannot be recorded, the export is a 503 and no file is sent. (`logAdminAction` never fails the act it records; that is right for a change already made, not for a file that has not left yet.)
- An export is not a change, so it is not in the log. It shows on HQ's governance feed like every `admin_audit_log` row.

### 3. A failed sync is recorded (PAY6 C)

- Before D1011, "a sync that fails leaves no record". Now `POST /api/admin/catalog/sync` writes `catalog_sync_failed` when it fails, with the admin who started it.
- **What it records:** `{ failure: 'stripe', stripe_status, stripe_code }` when Stripe refused, otherwise `{ failure: 'other' }`. Stripe's text is never kept, so nothing the call carried (a key's tail in an "expired key" message, say) can reach the log. The refusal the admin sees is unchanged.

### 4. Webhook deliveries per hour (PAY5): `services/stripeWebhookDeliveries.ts`

- **One reader for both pages.** HQ · Platform's P3 block (D213) moved here unchanged and gained `hours`. `routes/admin_platform.ts` calls it; `STRIPE_WEBHOOK_PATH` and `WEBHOOK_WINDOW_HOURS` are still exported from there.
- **`hours`:** 24 buckets, oldest first, ending with the hour the read is made in (the current hour is partial). Each is `{ hour, deliveries, not_2xx }` from `activity_logs`.
- **An hour with no log is null, never 0.** An hour in which the request log (rows with an `endpoint`) wrote nothing at all is `null`: the log was silent, so how many deliveries came is unknown. An hour the log wrote in, with no delivery, is `0`. Admin action rows (no `endpoint`) are not the request log and do not count.
- **Refusals:** as in the totals, only a status that was written and is outside 2xx counts as not-2xx. A row with no status is a delivery, not a refusal.
- **Unreadable is its own state:** `available: false` with the reason, on Platform. On the Payments route it is a 503 with that sentence.

### 5. The routes: `routes/admin_payments.ts`

Mounted at `/api/admin/payments`, before the catch-all `/api/admin`. **Super Admin only** (`requireSuperAdmin`): a plain admin is 403, and so is a branch deployment.

| Route | What |
| --- | --- |
| `GET /change-log` | `{ entries, total, limit, offset, filters, kinds }` |
| `GET /change-log.csv` | the CSV, with `reason`, recorded first |
| `GET /webhook-deliveries` | `{ available, window_hours, last, deliveries, not_2xx, hours, basis, hours_basis }` |

The client is `frontend/src/lib/api/payments.js` (`paymentsApi.changeLog`, `changeLogCsv`, `webhookDeliveries`), one line in `api.js`'s block (D527).

### 6. What this does not change

- The catalogue and Stripe write routes keep their guards (`requireAdmin`, with token packs and webhook `register` on HQ's bar). Moving them to `requireSuperAdmin` is not this part's.
- No migration: every row read here already exists.
