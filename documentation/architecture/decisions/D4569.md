## D4569 — Conditional D1 partitioning and financial consistency (#4569)

**Status: proposed.** Nothing here is authorised to be built. This decision
records how StudioOS would split its one D1 database *if* measurements show it
must, and the financial rules any split has to keep. It changes no schema, no
binding, no route and no data. It becomes an implementation issue only when
all of these exist: the #4567 baseline and benchmark report, the #4568
optimisation result, a cost and operability comparison, and the owner's
sign-off on §9's thresholds. Until then the answer is **option A: one
database, optimised, no partition** ("not yet needed", §5).

Parent #4554. Coordinates with #4559 (capacity signals, PR #4730), #4567,
#4568 and the existing backup/restore programme (#1007, #1008, #4558).

`ai_usage_logs`.

**Two facts that decide the shard key.**

1. *Money is keyed by the member, work by the scope.* An agent belongs to one
   company or one project (`712_team_agents.sql:21-54`), but its runs are held
   and charged from its **sponsor's** balance (`sponsor_user_id`,
   `712_team_agents.sql:36`; `services/agents/agentRun.ts:5`, `:234`). A
   member can sponsor agents in several companies, and can be a member of
   several. No single tenant key puts a member's balance and every scope that
   spends it in one place.
2. *Settlement and usage are already two writes.* The hold, the allowance and
   balance debits and the ledger rows are one atomic `db.batch()` plus
   triggers (`aiBudget.ts:451`, `:214`; `486:110-131`). The usage row is a
   separate later `INSERT` (`aiRouter.ts:2506` settles, `recordUsage` then
   writes), and `recordUsage` returns `null` when it cannot write
   (`aiRouter.ts:1430-1433`). So today a settled charge can exist without its
   usage row. The money is never wrong in that case (the reservation and the
   ledger carry it), but attribution can be missing. This is an existing gap
   to *measure* in #4567/#4568 (settled reservations with a non-zero charge and
   no `ai_usage_logs.reservation_uid`), not something this decision fixes.

**Erasure and backup.** No code deletes a user or anonymises usage
(`services/dsrRequests.ts:15-27`). The D1 backup is one daily
`wrangler d1 export` of one database (`.github/workflows/backup-d1.yml:21-22`,
`:103`); `services/backup.ts` covers KV only.

### 2. Cloudflare limits this rests on

Read 2026-11-06 with the Cloudflare documentation search. Each line names the
page.

- **D1 · Platform · Limits** (`/d1/platform/limits/`): maximum database size
  10 GB on Workers Paid, "cannot be further increased"; 1 TB storage per
  account (raisable on request); databases per account on Workers Paid
  1,000,000, the first 100,000 included; "each individual D1 database is
  inherently single-threaded, and processes queries one at a time", so
  throughput is about `1 / query duration` (1 ms → at most 1,000 queries/s,
  100 ms → 10), less per-request overhead; an overloaded database queues, then
  returns an "overloaded" error; each database is backed by one Durable Object
  and each read replica is a separate one; about 5,000 D1 bindings per Worker
  script; six simultaneous D1 connections per invocation; 30 s maximum query
  duration; a `db.batch()` counts as one query against the per-invocation
  limit; 50 MB maximum query result size (from 2026-11-04); Time Travel 30 days
  on Workers Paid, 10 restores per 10 minutes per database. The page also says
  D1 "is designed for horizontal scale out across multiple, smaller (10 GB)
  databases, such as per-user, per-tenant or per-entity databases".
- **D1 · Worker API · D1 Database** (`/d1/worker-api/d1-database/`): `batch()`
  statements "are SQL transactions"; a failing statement "aborts or rolls back
  the entire sequence". There is no transaction across two databases.
- **D1 · Pricing** (`/d1/platform/pricing/`): Workers Paid includes 25 billion
  rows read and 50 million rows written a month, then $0.001 per million read
  and $1.00 per million written; 5 GB storage included, then $0.75 per GB-month;
  $0.10 per database per month above 100,000, "even when it is empty".
- **D1 · Read replication** (`/d1/best-practices/read-replication/`):
  replicas serve reads only through the Sessions API (`withSession`); writes
  always go to the primary; replicas exist in ENAM, WNAM, WEUR, EEUR, APAC, OC.
- **D1 · Configuration · Data location** (`/d1/configuration/data-location/`):
  a jurisdiction (`eu`, `fedramp`, `us`) can only be set when a database is
  created; a location hint is a preference, not a guarantee.
- **D1 · Observability · Debug D1** (`/d1/observability/debug-d1/`): "a
  disruption to one database does not affect other databases on the account";
  read-only queries are retried up to twice by D1, writes are never retried
  automatically, and need idempotent application retries.
- **D1 · Observability · Find slow and expensive queries**
  (`/d1/observability/find-expensive-queries/`): the `events.d1Queries` dataset
  is sampled, with weights applied by the SQL API; `wrangler d1 insights` gives
  top queries for up to 31 days. This is where #4567's evidence comes from.
- **Changelog, 2026-10-23**: undelete of a deleted D1 database only within
  7 days.

The 10 GB figure is written "GB" on the limits page and the page does not
say decimal or binary; PR #4730 uses the smaller, decimal reading
(10,000,000,000 bytes), and this decision does the same.

### 3. Authority boundaries — who owns what

"Owner" means the one store whose row is the truth. Every other copy is a
cache, an export or a projection and can be rebuilt from the owner.

| Entity | Owner store | Rule |
| --- | --- | --- |
| Member identity, sessions, licences, permissions, company and project membership | core D1 (`users`, membership tables) | Never partitioned. Every shard decision reads it. |
| Agent registry and scope (`team_agents`, rule books, duties), tasks (`scope_tasks`) | core D1 | Scope moves are rows here. |
| **Balance home**: `ai_topup_accounts`, `ai_included_spend`, `member_ai_spend_limits`, `ai_budget_reservations`, `ai_credit_ledger`, `ai_topup_purchases`, `ai_topup_ledger` | one D1 per member (today: core D1) | Every check-and-debit for one member happens in **one batch in one database**. Never split by company, project or agent. |
| Immutable usage attribution (`ai_usage_logs`) | D1, same database as the balance home in A, B and C; in D, the payer's balance home | Append-only by convention (no trigger enforces it today). It is the charge's explanation, used by refunds, disputes, HQ usage and run cost. Analytics Engine is not a substitute. |
| Agent run state (`agent_task_runs`, `steps_json`) | core D1 in A, B and D; the run-state D1 in C | Single flight (`idx_agent_task_runs_live`) must stay in the database that admits runs. |
| Proposals (`ai_rail_proposals`) | core D1 | Referenced by product tables (`build_plans`, raise evidence); stays with them. |
| Analytics and read models (AE `studioos_metrics`, `system_metrics`, HQ aggregates, KV spend buckets in `aiRouter.ts:2513-2523`) | none: projections | Never authorise spend. A missing value is unknown, never zero. |
| Backups (R2 `BACKUPS`) | export of an owner | A backup is not a second ledger and is never written to. |

The KV day/month/org spend buckets (`aiRouter.ts:2513-2523`) are a
best-effort guard on cost, not money; they stay as they are in every option.

### 4. The alternatives

Each is judged on the same eleven points. "Trigger" is the measured condition
that would justify moving to it; the numbers are set in §9 by the owner, not
here.

#### A — one D1, optimised, no partition (the current choice)

- **Trigger:** none; this is the default while §9's gates are green.
- **Expected relief:** whatever #4568 measures: query shape, pagination,
  index changes, avoiding full-history `SUM`s, batching statements to cut
  per-request overhead (limits page), and moving `markRun`'s per-step
  `json_insert` writes (`engine.ts:205-219`) into fewer statements. Size
  relief from an approved retention tier only (#4568 §6; nothing is deleted
  before counsel/owner approval).
- **DB count / limits:** 1 of 100,000 included; 10 GB per database; one
  single-threaded primary.
- **Binding / routing:** unchanged (`DB`).
- **Query / reporting:** unchanged; every join in §1 keeps working.
- **Backup / restore:** unchanged; one export, one Time Travel window.
- **Regional:** one primary location; a jurisdiction cannot be added later.
- **Privacy:** unchanged; one erasure surface.
- **Operating cost:** lowest; only rows and storage above the included amounts.
- **Outage / recovery:** one database is one failure domain: if it is
  unavailable, everything that writes is.
- **Rollback:** each #4568 change carries its own migration rollback.

#### B — append-only analytics to Analytics Engine / R2; atomic money stays in D1

- **Trigger:** #4567 shows the top read cost or latency is *reporting*
  (dashboards, HQ usage, evaluation scans over `ai_usage_logs`), not the
  hold/settle path; or size growth is dominated by closed-period history.
- **Expected relief:** read load and, after an approved retention policy,
  size. **No write relief** on the money path: every `ai_usage_logs` row is
  still written to D1 because it is the charge's attribution.
- **DB count / limits:** still 1 D1. Uses the existing `ANALYTICS` binding
  (dataset `studioos_metrics`) and an existing R2 bucket; no new database.
- **Binding / routing:** none new; one more `writeDataPoint` after
  `recordUsage`.
- **Query / reporting:** dashboards read AE (sampled, so labelled as
  estimates); anything that decides money, a refund, a dispute, an export or
  an HQ statement reads D1. Closed periods exported to R2 as immutable,
  versioned files with a checksum manifest.
- **Backup / restore:** D1 export unchanged; R2 period files are themselves a
  recoverable copy; AE is never restored and is rebuilt from D1 if needed.
- **Regional:** AE and R2 locations must be checked against any data
  residency commitment before personal data is written there; AE gets no
  member id, prompt, model output or company name (low cardinality, #4559
  rule).
- **Privacy:** a second place holds usage history (R2), which erasure and
  export must cover; AE holds only aggregates without identifiers.
- **Operating cost:** AE writes and R2 storage; small next to D1 rows read by
  repeated scans.
- **Outage / recovery:** an AE or R2 outage affects dashboards only; money is
  untouched.
- **Rollback:** stop writing AE points and point the reads back at D1; the D1
  rows were never removed.

#### C — separate operational run state into its own D1

- **Trigger:** #4567 shows the core primary is saturated by run-state writes
  (`markRun` per step, admission, DLQ/cancel updates) and not by the money
  path, after A's batching is done.
- **Expected relief:** write load of `agent_task_runs` and its step timeline
  leaves the core primary. The hold/settle path does not move.
- **DB count / limits:** 2 D1 databases; the second has its own 10 GB.
- **Binding / routing:** one new binding (for example `RUNS_DB`), static in
  `wrangler.toml`; every run-state query switches to it.
- **Query / reporting:** the three joins in §1 that pair runs with usage
  (`workRuns.ts:36`, `evaluation.ts:77`, `:179`) become two reads and an
  application join; `agent_task_runs.usage_log_id` and the FK cascades to
  `team_agents`/`scope_tasks` (`728:36-37`) can no longer be enforced and need
  an application cascade and a nightly orphan check; admission still reads
  `projects.company_id` from core (`engine.ts:155-156`).
- **Backup / restore:** two exports and two Time Travel windows; a restore
  must pick one point in time for both, or reconcile the gap (§7).
- **Regional, privacy:** same location policy as core; run summaries already
  hold no prompt or output (`728:44-46`).
- **Operating cost:** about the same rows; one more database (included).
- **Outage / recovery:** runs can fail while money and the rest of the
  product keep working; a run that cannot be marked ends through the
  existing hold expiry (`aiBudget.ts:289-294`) and the DLQ path.
- **Rollback:** dual-write runs to both databases during cutover; roll back by
  pointing reads at core again; core keeps the rows until verification ends.
- **Not this:** the existing AgentScope Durable Object storage (D1528, built
  but not activated) is a possible home for *transient* step state, but this
  decision does not add a scheduler, a second runtime or a second run table.

#### D — per-scope or per-member D1 partitions with an authoritative directory

- **Trigger:** A, B and C are done and #4567/#4568 still show either the core
  primary saturated on the **money path itself**, or size projected past the
  critical policy level within the agreed horizon even after B's retention.
- **Expected relief:** money-path writes spread across N primaries; each
  partition has its own 10 GB.
- **DB count / limits:** **shard groups, not one database per tenant.** A
  Worker reaches a D1 database through a binding declared in configuration,
  and a script has about 5,000 of them (limits page). A database per member
  or company does not fit that at a million agents and would need the account
  REST API on the request path, which this decision rejects. So: N fixed
  partitions (for example 16 or 64), each member assigned to one by the
  directory, N bindings in `wrangler.toml`. Hot members move to their own
  partition (§6.2).
- **Binding / routing:** a directory row in core D1 (`member → partition`,
  with a version) is the truth; a Worker may cache it in memory for one
  request only, never in KV without a version check, because a stale entry
  would send a debit to the wrong balance.
- **Query / reporting:** any HQ or company report that spans members fans
  out to N partitions and merges; per-company reports become fan-outs because
  a company's agents may have sponsors in different partitions. That is the
  main cost of D.
- **Backup / restore:** N + 1 exports; restores per partition; a
  cross-partition consistent point in time does not exist, so recovery
  relies on §7's reconciliation.
- **Regional:** the only option that can place members in a jurisdiction
  (`eu`, `us`), because the jurisdiction is chosen at creation (data location
  page). This is a reason to choose D only if a legal requirement appears.
- **Privacy:** erasure and export must visit the member's partition and core;
  the directory itself is personal data.
- **Operating cost:** N databases (included up to 100,000), N migrations per
  deploy, N backups, N sets of capacity metrics.
- **Outage / recovery:** one partition's outage stops only its members'
  spending ("a disruption to one database does not affect other databases",
  debug page); the directory in core is a single point and must stay small and
  cached per request.
- **Rollback:** the directory can point a member back at core while core
  still holds the member's rows (§7, no dual authority).

#### Managed alternative

Evaluated only if every D1 option fails measured requirements, as #4554
already decides. Not evaluated now.

### 5. "Not yet needed"

Option A is the decision until §9's scorecard fails. Size is at about 3.2% of
the limit; there is no measured contention, no measured query latency and no
D1 query telemetry in production yet (PR #4730, owner item 1). Partitioning
now would add N failure domains, break the joins and FKs in §1 and give up
single-batch money atomicity for a problem nobody has observed.

### 6. Shard-key evaluation (for D, and the part of C that matters)

#### 6.1 Candidates

| Key | Money atomicity | Run/proposal locality | Reports | Verdict |
| --- | --- | --- | --- | --- |
| member (`user_id`, the payer) | kept: every balance table is keyed by it | runs and proposals of one agent go with its sponsor, so one company's agents can sit in several partitions | per-member reads local; per-company reads fan out | **only acceptable key for the balance home** |
| company / project (scope) | **broken**: one member's balance would be spent from several partitions | local | per-company local | rejected for money; possible for run state only (C) |
| agent | broken, as above | local | fans out per member and per company | rejected |
| workload (money vs runs vs analytics) | kept | runs separate from money | joins across workloads become application joins | this is C and B, not D |

So any partition of money is **by payer**. Runs could be placed by scope in C,
but then their usage link crosses databases; placing runs with the sponsor
(by payer) keeps `agent_task_runs.usage_log_id` local and is preferred.

#### 6.2 Hot member

A member whose holds and settles dominate one partition gets a partition of
their own through the directory move in §7. One member's writes are still
serialised by one primary, and that is the floor: the balance check needs it.
If one member alone saturates a primary, the answer is batching their
statements and bounding their concurrency (the existing hold refusal and
single-flight index), not splitting their balance.

#### 6.3 Directory

`member → partition, version, moved_at`, in core D1. Read once per request,
together with the member's session; never cached across requests outside a
versioned check. A write that finds the version changed is refused and
retried from the start, so a stale directory can never debit the old home
after a move.

#### 6.4 Binding growth

N is fixed in `wrangler.toml` and sized well under the ~5,000-binding cap;
adding partitions is a deploy, never a request-time action.

#### 6.5 Scope moves and cross-company access

A scope move (an agent's project changing company, `scope_moved` in
`728:39-41`) changes no partition under the payer key, because the sponsor
does not change. A sponsor change (`202611040924_team_agent_sponsor_changes.sql`)
changes the payer for *future* runs only; past usage stays with the old payer's
partition. A member working across several companies is one directory entry.

#### 6.6 Analytics aggregation

Cross-partition totals come from B's projections (AE, period files), labelled
as estimates where sampled, never from a live fan-out on an HQ page load.
Money statements per member stay single-partition reads.

#### 6.7 Erasure, export, retention

There is no erasure code today (`dsrRequests.ts:15-27`). Any split multiplies
the places an erasure or export must visit: core, the member's partition, R2
period files. Financial records will likely have a legal retention that
outranks erasure; that is counsel's decision (#4568 §1), recorded before any
archive or delete.

### 7. Financial invariants and the protocol any split must keep

**Invariants** (already true today; any design must keep them and #4567's
automated checks test them):

1. **No double charge.** One hold per idempotency key per member
   (`525:18-19`, `aiBudget.ts:362`, `:440`, `:464`); one settlement per hold
   (`settlement_uid` CAS, `aiBudget.ts:186-216`); one ledger row per
   `(kind, source_ref)` (`486:86`); one proposal per run key (`727:129`).
2. **No overdraw.** The hold's insert computes the split from the counters
   inside the same write and refuses when the allowance plus balance or the
   member's monthly limit cannot cover it (`aiBudget.ts:386-414`); the balance
   never goes below zero (shortfall recorded instead, `486:81-83`).
3. **No charge above the hold.** A cost above the hold goes to review, not to
   the balance (`aiBudget.ts:224-229`).
4. **Append-only money history.** `ai_credit_ledger` refuses update and
   delete (`486:97-107`); corrections are new rows (`refund`, `release`,
   `adjustment`, `dispute_won`).
5. **Unknown is not zero.** A missing usage row, unreadable balance or absent
   metric is reported as unavailable (`chargedFor`, `agentRun.ts:270-276`).

**The protocol** for any design where usage attribution or run state lives in
a different database from the balance home (C, or D's fan-in):

- **Rule 1 — one home per debit.** Hold, settle, refund and review write only
  the balance home, in one `db.batch()`. No debit is ever split across two
  databases. There is no dual-authoritative balance at any time, including
  during a move.
- **Rule 2 — outbox in the same batch.** The settle batch also inserts an
  outbox row in the balance home (`reservation_uid`, target, payload without
  prompt or output). This is a new table *only if* C or D is authorised.
- **Rule 3 — idempotent follower write.** A relay (the existing job queue,
  not a new scheduler) writes the follower row in the other database with
  `INSERT … ON CONFLICT DO NOTHING` keyed by `reservation_uid` (or the run
  uid), then marks the outbox row delivered. Replays are harmless.
- **Rule 4 — compensation is a new row.** A failed run after settlement is
  refunded by a new `refund` ledger row through the existing reversal path,
  never by editing or deleting the settlement.
- **Rule 5 — reconcile.** A scheduled check compares, per day: settled
  reservations with a non-zero charge vs usage rows with that
  `reservation_uid`; runs with `usage_log_id` vs usage rows; outbox rows older
  than a bound. Each mismatch is a count with a link, never auto-repaired with
  money.

**Failure cases the PoC must show** (synthetic only):

| Case | Expected result |
| --- | --- |
| Balance home fails mid-settlement | the batch rolls back whole (D1 Database page); the hold stays pending; retry settles once (CAS); expiry releases it if the run never answers |
| Follower database down after settlement | money final; outbox row waits; relay retries; reconciliation shows it as pending, not as zero |
| Retry of the same run with the same key, concurrently | one hold (`ON CONFLICT DO NOTHING` + `heldUnder`), one proposal (`run_key`), one charge |
| Stale directory during a move | version check refuses the write; the request restarts against the new home |
| Partition outage | only that partition's members are refused (`budget unreadable`), others unaffected; nothing is reported as zero |
| Duplicate relay delivery | follower insert is a no-op |

**Moving a member between homes** (D only, on paper): freeze the member
(refuse new holds, which the existing refusal path supports), wait for pending
holds to settle or expire, copy their rows with a checksum (row count and a
hash over `uid, delta, created_at` ordered by `uid`), verify, flip the
directory version, unfreeze. Core keeps the copied rows read-only until
verification ends; rollback is flipping the directory back while the member is
frozen.

### 8. Gradual migration — on paper only

For whichever option §9 selects, in order, each step reversible:

1. **Snapshot and checksum** of the source tables in a throwaway copy
   (#4566's isolated preview), never production.
2. **Shadow read**: the new store is filled from the snapshot plus replayed
   events; reads run against both and compare; differences are counted. The
   old store stays authoritative throughout.
3. **Idempotent replay** of everything after the snapshot, keyed as in §7.
4. **Consistency proof**: §7's reconciliation returns zero mismatches for an
   agreed window; the #4567 invariant suite passes on the new layout.
5. **Cutover** of one member cohort (or, for C, run state only) behind a
   flag; **rollback** is the flag, while the old store still holds the rows.
6. **Backup and independent restore** of every new database rehearsed through
   the #1007/#1008/#4558 drill before the flag reaches everyone.
