## D693 — Verdict: decisions are kept for the venture or one hypothesis, withheld below the evidence bar, and never overwritten

Issues #1702, #1703 and #1704, part of D689 (#1654). Task S06, run in slot S12. The owner: "Verdict has a new page in the artifact." The canvases (`design/canvases/integrated/Cycle Overview.dc.html`, CO; `Cycle Modules · Boards.dc.html`, BOARDS) arrived with #1653. Verdict becomes Validate's seventh module (board MV7), with a card, a Decisions table, one record per decision, and a Record a decision lightbox. D693 also closes the gap #1440's blueprint comparison named: "No loop carries a hypothesis through a sprint to evidence, a decision and a next commitment", and "a Proceed / Pivot / Stop verdict for the venture, which nothing else reads." Session 1 settled every open point on the issues. #1702 starts this file and #1704 finishes it.

It ships as three PRs:

| --- | --- |

| 3 (#1704) | The module, its card and Decisions table, Record a decision, the memo, Export summary's button, and `/validate/verdict`'s swap |

### What was there

- `validation_decisions` (migration 211) kept `decision`, `reasoning`, `decided_at`, `decided_by` and `superseded_at`. It had no scope, no evidence, no withheld state, no pointer to what a decision superseded, and no commitments.
- `POST /api/founder/validate/decision/:pid` superseded every current decision of the venture, then inserted, in two statements outside a batch. So a venture may hold two current rows.
- The decision GET turned a failed read into an empty history, and the summary CSV turned one into "not recorded". Both took "the current decision" to be any row with `superseded_at IS NULL`.

### Decisions

**1. A decision is For the venture or for one hypothesis, and supersedes only its own scope.**

- `hypothesis_id` NULL is the venture.
- A given decision supersedes the current given decision of its own scope, and `supersedes_id` points at it. Both are written in one `DB.batch`. The pointer is chosen inside the batch (`INSERT … SELECT`), never read before it, so two decisions recorded at once leave exactly one current and a correct chain.
- The same batch supersedes every earlier current given decision of the scope, so a venture that holds two from the old route holds one after its next decision. The pointer names the newest of them.
- A decision on H2 never retires the venture's verdict, and the venture's never retires H2's.
- **No unique index on the current decision.** A venture may already hold two current rows, and such an index would fail the migration on deploy. The reader takes the newest.
- **No `ON DELETE` action on `hypothesis_id`.** This departs from the plan, which wrote `ON DELETE SET NULL`. That would turn a decision on one claim into a decision on the venture. Hypotheses are retired, never deleted, and a project's delete still cascades through both tables in one statement (`services/projectTrash.ts`).

**2. The bar is its own constant, and it counts what the founder checks.**

- `DECISION_EVIDENCE_BAR = 5` lives in `services/verdict.ts`, citing CO:335. `VALIDATION_BAR` keeps its own meaning: supporting ICP interviews behind one claim.
- The bar counts the checked items, contradicting ones included.
- The items are the venture's own `evidenceFor` items (#1692's `services/validateEvidence.ts`). Each item's key is `evidenceFor`'s `id`, which names the link the item came through, so an interview behind two claims is two items.
- The writer accepts only keys that the evidence reader returns for this venture. Any other key answers 404 "Evidence not found." and nothing is written.
- Each item's label, strength, direction and date are copied into `validation_decision_evidence`, so the record does not change when the evidence is edited later.
- **Until #1703**, `services/verdict.ts`'s `evidenceFor` is a stub that returns no items, so every decision recorded through the new route is withheld. Tests pass their own source through `recordDecision`'s options.

**3. Below the bar, a decision is kept as Withheld.** It is never current and supersedes nothing. It has its own row in the table, its own record, and a hollow step on the card's timeline. A Withheld Pivot still starts its new hypothesis (#1703).

**4. A decision is never edited or deleted.** There is no PATCH and no DELETE. This departs from D-e's "every Add form has an Edit". A founder who changes their mind records a new decision, and the old one stays.

**5. Old rows are read as they are.** An existing row reads as a given decision for the venture (`state` defaults to `'given'`, `hypothesis_id` is NULL). Nothing is backfilled. A given decision with no evidence rows can only come from the old route, since every other given decision rests on at least five. Its Evidence fact is Not recorded, with the reason "Recorded on the earlier verdict page, which kept no evidence." (`NO_EVIDENCE_REASON`).

**6. One module touches the three tables.**

- Only `services/verdict.ts` reads or writes `validation_decisions`, `validation_decision_evidence` and `validation_decision_commitments`. The one exception is `services/records/owned.ts`'s two ownership entries (D-u), which only test that an id is the venture's. A test greps `cloudflare-worker/src` for it.
- Every reader of the current decision calls `currentDecision(env, projectId, scope)`: the old GET, the summary CSV, and #1701's Verdict index row.
- `currentDecision`, `decisionsFor` and `decisionById` each bind the venture in their query and throw on a failed read. A read that fails answers 503 or draws its card as unreadable, never an empty history.

**7. Decisions never reach anyone `canReadDecision` refuses.**

| Viewer | Overview | Verdict module read | Record, activity, form-options, actions, `POST`, summary CSV | Another venture's decision id |
|---|---|---|---|---|
| The venture's founder, or an admitted Lab member on their own venture | the card; `can_read_decisions: true` | yes | yes | 404 |
| Admin | the card; `true` | yes | yes | 404 |
| Partner | no card, no index row; `can_read_decisions: false` | 403 "Partners do not see decisions." | 403 | 403 |
| Advisor, investor, or another venture's founder | 403, as today | 403 | 403 | 403 |

- Decision activity is logged only under `entity_type 'validate.verdict'`, never against the hypothesis, so a hypothesis record, which partners read, never shows one.
- No activity summary carries the reasoning or a commitment's text. Each says the decision and its scope: "Recorded Pivot for H2", "Recorded Stop for the venture, withheld", "Superseded by Proceed". The new decision's row has action `validation_decision_recorded`. The row on the decision it superseded has `validation_decision_superseded`, and a withheld decision writes none.
- The new decision's id is read back inside the batch as `MAX(id)` for the venture, since `validation_decisions` has no `uid`. PR 1 writes these rows through a local helper in `services/verdict.ts`, because #1690's `logCycleWrite` is not on `main` yet. #1703 replaces it and adds `validation_decisions` to that helper's read-back list in `services/cycleActivity.ts`, the one other place the table's name may appear.
- `POST /api/activity/sync-github` (`routes/activity.ts`) mirrors a member's own activity rows to their GitHub repo when they ask. A decision's rows carry only the decision and its scope, never the reasoning, so that route stays as it is.

**12. `/validate/verdict` stays a static route; its element changes, and the old decision routes answer through the new writer.**

- `App.jsx`'s `/validate/verdict` line stays, with its guard, and #1704 makes it render `<CycleRoute cycle="validate" slug="verdict" />`. `route_role_zone_contract.test.mjs` then needs no change.
- Until #1704 swaps that line, `VerdictPanel` is reachable and sends no evidence. So `POST /api/founder/validate/decision/:pid` calls `recordDecision` with `bar: 0`: a given venture decision that supersedes only the venture's current given one. It still answers `{ id, decision }` with 201. #1704 drops that argument when it swaps the line, so the two pages never disagree.
- The old GET's `current` is `currentDecision(venture)`, and its `history` is the venture's own rows, each with `state`. Both answer 503 when the read fails.
- The summary CSV reads `currentDecision(venture)` and answers 503 "The decision could not be read." on a failure, instead of exporting no decision.

**`POST /api/cycles/validate/decisions?project=N`** (`routes/cycle_verdict.ts`), gated by `canWrite`. It takes `{ decision, for: 'venture' | 'h-<id>', reasoning?, evidence?: string[], pivot_claim? }` and answers 201 `{ id, state, supersedes_id, pivot_hypothesis_id }`. It refuses, in order:

1. 401.
2. 400 for a bad `project`.
3. 404 "Project not found".
4. 403.
5. 400 "decision must be proceed, pivot or stop".
6. 400 for a malformed `for`, more than 50 evidence keys, reasoning over 4,000 characters, or a `pivot_claim` without Pivot ("Only a Pivot starts a new hypothesis.").
7. 404 "Hypothesis not found." for another venture's hypothesis.
8. 404 "Evidence not found." for a key that is not this venture's.

Until #1703, a `pivot_claim` on a Pivot answers 400 "A Pivot cannot start a hypothesis yet."

### PR 2a (#1703, first PR) — the record, its commitments and Record a decision's options

**Logging.** `recordDecision` logs through `services/cycleActivity.ts`'s statement form, in the decision's batch. `Readback` gains `{ table: 'validation_decisions', by: 'max' | 'supersedes' }`:

The local helpers `logRecorded` and `logSuperseded` are gone. The rows, actions and summaries are unchanged.

**The record** is `services/records/verdict.ts`'s `verdictSpec()`, a `ModuleSpec` with `read: canReadDecision`, `write: canWrite`, store `validation_decisions` and activity type `validate.verdict`. The copy:

| Part | Content |
|---|---|
| title | "\<Decision\> · the venture", or "\<Decision\> · \<claim\>" |
| sub | "Recorded \<d Mon\> by \<Name\> · rests on \<n\> pieces of evidence" ("1 piece of evidence"). No name without `decided_by`. No evidence clause on an old-route decision (a given one with no evidence rows) |
| pills | Proceed `ok`, Pivot `warn`, Stop `bad`; then Current `v1`, Superseded `grey` or Withheld `grey` |
| facts | Decision; For ("The venture" or "\<code\> · \<claim\>"); Evidence ("\<n\> items", "1 item", or Not recorded with decision 5's reason); Supersedes ("\<Decision\> · \<d Mon\>", "Nothing, withheld", "Nothing, the first for the venture" or "for H\<n\>", or Not recorded with "Recorded before decisions named what they replaced.") |

| next | Record a new decision: it is the first action, and no main row is open |

**Commitments** (decision 8) are written by `services/verdict.ts`'s `addCommitment` and `completeCommitment`, each in one batch with its activity row on the decision (`validation_commitment_added`, `validation_commitment_done`, summaries without the text).

- A writer's refusal is thrown as a `Response`, which the entry point's `withThrownResponses` answers.

### PR 3a (#1704, Worker part) — the card and the Decisions table

`services/verdict.ts` gains `verdictCard(ctx)` and `decisionRecords(ctx, rq)`, read directly by `verdict_d693.test.ts`. Neither is in `cycleValidate.ts`'s `MODULES`, `CARD_FOR` or `RECORDS_FOR` yet: the Worker's list and the page's land together with `/validate/verdict`'s swap, in #1704's closing PR.

**9. The card is the venture's verdict** (CO:542, CO:584). `safeCard` with slug `verdict`, range "All time", caption "Every decision, oldest to newest, never overwritten." and source "Decisions", so it carries the same eight keys as the other six.

| State | When | Body |
|---|---|---|
| `empty` | the venture has no decision in any scope | "No decision yet. Decisions appear here once evidence is in.", with "Record a decision" → `/validate/verdict/new?project=N` |
| `too_little` | decisions exist, but no current given decision for the venture | "No verdict for the venture yet. Withheld decisions and decisions on one hypothesis are in the table.", with the same action |
| `ok` | the venture has a current given decision | `series: { decisions: [{ decision, state, date }], current: { decision, date, evidence }, next }` |
| `unreadable` | a read throws | `safeCard`'s: "Decisions could not be read" |

- The timeline is the venture's own decisions, the six newest (`TIMELINE_CAP`), oldest first. A Withheld one keeps its `state`, so the page draws it hollow. A decision on one hypothesis is not on it.
- `current.evidence` is the count it rests on, or null for an old-route decision (decision 5), so the page drops the evidence clause.
- `series.next` and the card's `next` are null in this part. The sprint's date is `hypotheses.deadline`, #1692's migration 460, and the closing PR fills both.

**The Decisions table** (CO:610):
- Columns Decision / For / Reasoning / Evidence / Date · by.
- The Decision filter is Proceed, Pivot, Stop and Withheld. The For filter is The venture, then each of the venture's hypotheses that has a decision, as "\<code\> · \<claim\>" with value `h-<id>`.
- Sorts are Newest (the default) and Oldest.
- Search covers the reasoning and the claim the decision is For.
- Filtering, search and paging run in SQL, and every value is bound.

Each row is `{ id, decision, state, hypothesis_id, for, reasoning, evidence, date, by }`, and its id is the decision's id.
- A Withheld row's `reasoning` is "\<n\> of 5 pieces of evidence".
- A Pivot that started a hypothesis reads "Starts \<code\> · \<claim\>", through `pivot_hypothesis_id`.
- Any other row reads the first non-blank line of its reasoning, or null.
- `for` is "The venture" or "\<code\> · \<claim\>".
- `evidence` is null for an old-route row.

**`decisionsFor` gains two things:**
- A bound `q`, where `%` and `_` match as themselves.
- A Decision filter that counts given decisions only. A Withheld Proceed is under Withheld, not under Proceed, because the table names it Withheld. Its two callers, the old GET and #1702's test, pass no kind filter, so neither changes.
