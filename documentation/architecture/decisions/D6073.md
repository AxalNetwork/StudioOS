### 1. A column, not a second table

`data_room_files` gains `removed_at`, `removed_by_user_id` and `removed_folder_name`. Remove stamps them; Restore clears them. Moving the row to another table would have taken its `data_room_file_versions` (ON DELETE CASCADE), its access-log links (SET NULL), its search passages and its deck values with it, and Restore could not have brought them back. The row keeps its folder, gate (visibility, tier, end date), checklist and request match and versions untouched while it waits.

`removed_folder_name` is the folder's name at the Remove, so Trash can say "returns to Top level" when the folder was deleted while the file waited.

### 2. Hidden from every investor read and count at once

Every read of `data_room_files` an investor, an advisor, a count or a founder's summary makes carries `liveFiles(db, alias)` (`AND <alias>.removed_at IS NULL`), and `tierAdmits` refuses a row whose `removed_at` is set, for the readers that select the whole row. The investor reads: `GET /data-room/shared` (the count), `GET /shared/:p` (the listing and the NDA-withheld count), `POST /shared/:p/search`, `POST /shared/:p/files/:uid/download`, the founder's `GET /:p/preview`, `GET /shared/:p/evidence` (`raiseEvidence.fileAdmits`), `readableRoomFiles`, `admittedCounts` (Research's held-room counts and the advisor brief), `roomGatesAskNda`, `research.ts`'s `/diligence/:grant`, `/diligence/:grant/files/:uid` and the room memo, `dd.ts`'s request files, their names and their download link, the deck proof link (`deck_proof.ts`, through `tierAdmits`) and the deck values a deck reads (`decks/sources.ts`). The founder's reads and counts leave it out too: the room read, the admin summary, Checklist, the diligence matches on Requests, search and indexing, Eadwyn's room facts and proposals, the Raise card and record list, the mock-diligence section, a prospect's Materials, the round-call room count, venture scoring's data-room inputs, a cap-table document reference and a Notion snapshot's earlier file. A file in Trash is not the venture's record (`records/owned.ts`), so its record, Replace and Remove answer 404 until it is restored, and so do the founder's download, versions, Make current, rename and move.

`cloudflare-worker/test/data_room_trash_6073.test.ts` enumerates the investor reads and counts against one file before and after Remove and after Restore, and its source guard fails on any statement over `data_room_files` that neither leaves Trash out nor is listed with its reason. Left as they are, with the reason in that list: storage usage (a file in Trash still holds its bytes until it is purged, so it counts), the access and activity logs (they keep naming what was opened), the activity history's creator, "nothing recorded yet" checks, inserts, and writes reached only after a live-only lookup.

`liveFiles` returns '' only when the column does not exist (a database before this migration, where nothing can be in Trash); any other failure throws, so an unreadable store never drops the filter.

### 3. Restore, and its fallback

The owner and an accepted co-founder restore (`restore` capability, D6071 owner question 4 option A, as #6073's acceptance states). The file returns to its folder when that folder still exists in the venture; otherwise to the top level, and the answer says so (`returned_to_top_level`), as RAD28 draws ("returns to Top level"). Its gate, matches and versions are as they were. A second Restore, or one racing the purge, changes one row at most (guarded on the stamp).

### 4. Delete now and the purge

Only the owner deletes now (`delete`, unchanged from D1103: only the owner deletes a file); Remove stays the owner's too. The purge deletes the stored objects first (the current one and every version, inside `data-room/<project uid>/` only), then the passages and vectors, then the rows (versions, deck values, the file) in one batch. A failed object delete keeps the row in Trash (Delete now answers 503 `delete_incomplete`; the sweep counts it as failed and retries the next day). Deleting an object twice is a no-op, so a purge interrupted anywhere is safe to run again.

The sweep is the existing 04:30 UTC daily branch in `index.ts`, beside the venture trash (`sweepTrashedProjects`); no cron is added. It purges files whose `removed_at` is 30 days old or more, oldest first, 200 a run.

### 5. Connector copies (D1094)

A purge keeps the file's `connector_fed_items` row with `local_id` NULL, so a Google Drive or Mercury re-sync never copies it again. While a Drive copy is in Trash its ledger still names it and `syncRaiseGoogle` leaves it alone (`kept_deleted`), even when Google's file changes; From Google's list does not show it. After Restore it is a linked copy again and the next change in Google replaces it in place, as before; no second copy is made. From Google's own Delete of a copy is unchanged (it deletes at once).

### 6. The page

Files has Trash as the tree's last row, with the room read's `trash_count`, for those with `restore`; choosing it puts the Trash list where the table was: file, folder (and "returns to Top level"), removed on and by, days left of 30, Restore, and Delete now when the read says `can_delete_now`. Delete now is a Scope dialog, then a Review dialog, then a result line. Loading, Unreadable ("Trash could not be read. Files still work. Nothing in Trash was changed.") and empty are each said. At phone width each file is a card with 44px buttons. The Remove dialog (Files' bulk bar and the file lightbox) says the files move to Trash for 30 days, names the folder and the day they can be restored until, and its button reads Move to Trash.

**Departs from the canvas:** the Remove dialog does not name the checklist item the file answers ("it will read Missing"): the room read carries no checklist match per file. Eadwyn's proposal to restore a file that answered a checklist item (RAD28's rail) is not built.
