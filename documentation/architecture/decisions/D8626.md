## D8626 — The merge queue can route its Worker parts through the capacity coordinator, behind its own flag (#8626)

**Context.** The capacity coordinator (`merge-control/`, D7909) already accepts a `merge_group` submission. It proves
the queue chain, each entry's pull request and the base before it accepts, and #8628 gave it cross-candidate Linux
pickup. But `ci.yml` submitted only on a push to main, so a queue candidate's six Worker parts always ran on hosted
runners. In the queue the required check is `test:drift (full suite)`, and it passes when every `suite` part passes.
A Worker part the coordinator runs must not also run here, or each shard runs twice. But if it does not run here, that
check no longer proves the Worker result.

**Decision.** A queue candidate is routed only when all of these hold. Otherwise nothing changes, and every part runs
hosted as before.

1. `vars.CI_CAPACITY_QUEUE_ROUTING` is `'true'`, as well as `vars.CI_CAPACITY_ENABLED`. It is switched on only in the
   same change that makes main's ruleset require `ci-capacity/full-suite` (S39's consumer cutover, #7909).
2. `scripts/ci/capacity-submission.mjs` reads main's live rules and finds `ci-capacity/full-suite` required *from an
   App*: an entry with an `integration_id`, and the App in `vars.CI_CAPACITY_FULL_SUITE_APP_ID` when that is set. A
   context with no App could be posted as a commit status by any token. Before that, it prepares nothing.
3. `vars.MACBOOK_WORKER_ENABLED` is not `'true'`: D7881's Mac handoff would run a routed part a second time.
4. The trusted planner (`capacity-planner.yml`, at its reviewed main pin) submitted, and the coordinator answered
   `accepted` for *this* request id. Only then does the planner write `accepted=true`. A refusal, an outage, another
   id or any earlier error leaves it unset, and the planner's queue step is `continue-on-error`, so a refusal never
   turns a candidate red.

The submission is the queue entry's own: its ref, its event's head and base, and its run must agree. It carries the
equal-weight plan of its checkout (D7108 part 2), the same bytes the planner rebuilds, and no plan artifact.

**The suite and the gate.**

- `suite` needs `capacity-route`, so a routed candidate's nine parts start one job later. With routing off that job is
  skipped before it starts.
- The routed Worker parts keep every step. `runner-benchmark.yml` mirrors them (D5611), so the steps are unchanged.
  A job-level `CAPACITY_ROUTED` tells `test-drift-parts.mjs` to say where the part runs instead of running it, and only
  for a planned `test:worker` part of a `merge_group` run with a well-formed request id.
- `gate` (`test:drift (full suite)`) reads `capacity-route`'s `accepted`. For a routed candidate it reads main's rules
  again and fails unless `ci-capacity/full-suite` is still required from an App. The rules can change after the route
  job read them, and a submission alone must never be what lets a candidate land. It adds no way to pass.

**Rollout.** The planner pin is a main commit (D8335), so this change cannot pin its own planner. Both callers keep
`cb63d3997d`, whose planner submits on main pushes only. Until a later PR moves both pins to the commit that lands this
planner, a routed candidate's `accepted` stays unset and it runs fully hosted. The live ruleset stays at five
candidates; nothing here deploys, activates or enrols a runner.
