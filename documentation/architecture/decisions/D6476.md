## D6476 — The queue ejection handler restores only an entry a person made, on content no model changed (#6476)

- **Status:** built. The live proof waits on the owner's landing bot App. Part of #5600 (plan key C5). The
  branch is stacked on #6474's: it reuses the keeper's GitHub client and asks the keeper to fix conflicts.
- **Why:** in 7 days, 397 queue runs served 118 PRs. Only 32 of 106 merged PRs got through on their first
  run. Of 177 failed queue runs:

  | Cause | Runs |
  | --- | --- |
  | Cascades from an entry ahead | 60 |
  | One infrastructure step | 58 |
  | A test failing | about 38 |
  | Red main | 19 |

  The owner had to notice each ejection and re-queue by hand.
- **Owner's answers (2026-11-16):** the bot may restore an entry the owner queued and no model touched:
  - only after a conflict, cascade, flake or infrastructure ejection;
  - with every required check green on the current head;
  - at most 2 times per PR per 24 hours;
  - never while `[alert] merge queue stalled` is open.

  A bot-queued entry is not consent, and a model commit voids it. A timeout is therefore labelled, not
  re-queued, which narrows the issue's list.
- **Built:**
  - `scripts/landing-bot/ejection-rules.mjs`, pure: `consent()`, `classify()`, `decide()`;
  - `scripts/landing-bot/ejection.mjs`, the sweep;
  - `.github/workflows/landing-bot-ejection.yml`, named for #6467's shared rules (`landing-bot-<kind>.yml`)
    rather than the issue's `queue-ejection.yml`.
- **No `workflow_run` trigger.** The #4571 guard (WF-4) forbids it repo-wide, so the handler sweeps every
  10 minutes, plus dispatch with one PR. The issue's minutes-from-ejection measure is in each run's summary.
- **Consent** is the newest of two signals: an added-to-queue event by a non-bot actor, or an auto-merge
  request enabled by one. It stays valid while every later commit is a no-model merge of main: the keeper's
  `Landing-Bot-Kind: keeper` merge commit, or GitHub's update-branch merge. Any other commit, or a person's
  removal from the queue, voids it.
- **Known limits:**
  - Agents and the owner share one GitHub login today, so "a person queued it" cannot tell the owner from an
    agent until the separate agent identity (#5605 row 2) exists.
  - Failed test names are not read from logs yet, so the flaky-list rule (#6464) applies only when a caller
    passes them. A flake is otherwise recognised by its own head run and main both being green.
  - #5973's queue record is used when one is passed in.
  - Whether GitHub clears an auto-merge request on ejection is undocumented. Each summary line records
    whether auto-merge was still set.
- **Guard:** `frontend/test/landing_bot_ejection_6476.test.mjs` covers:
  - every class;
  - the consent rules: a bot-queued entry, a model commit, a manual removal, and auto-merge as a signal;
  - every refusal: no consent, a third re-queue, the repo-wide cap, the failure-share breaker, red main, a
    stalled queue, a head changed since green, and red checks;
  - that a flake gets a re-queue and no repair;
  - the workflow text.

  Mutation-checked: accepting any actor as consent, keeping consent across a model commit, dropping the
  per-PR cap, and re-queueing a manual removal each fail it.
