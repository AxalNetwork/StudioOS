## D1279 — main's CI finishes for every commit, README.md merges by union, and check-folder-docs refuses what union gets wrong

- **Status:** decided and built by S21, 2026-10-26, on the owner's asks: "README.md is always creating conflicting files issues in PRs, can we find a better solution" and "Failed checks seem to continue in PRs, resolve problem, and tell me what it is".
- **Why:** rule 3 of `scripts/check-folder-docs.mjs` makes every PR that adds a file add its row to the folder's README. Many open PRs append at the same spot of the same README, so each merge of `main` stopped on a conflict that only needed both sides kept. On 2026-10-26, #3303, #3296 and #3182 conflicted on `frontend/src/pages/README.md` and nothing else.

### 1. What changes

- **`.gitattributes`:** `README.md merge=union`. Git's built-in union driver keeps both sides' lines instead of stopping. That is right for appends, so a README conflict no longer stops a local `git merge origin/main`.
- **Rule 4, ONE VERSION, in `scripts/check-folder-docs.mjs`:** every tracked `README.md` is read by `scripts/lib/readmeUnion.mjs`. It fails on:
  - a conflict marker;
  - a table row whose first cell is a backticked name that the same table already lists (one file, two descriptions);
  - the same line of 40 or more characters twice within eight lines (union's two copies sit side by side).
- **Tables keyed by something else may repeat their key.** For example, `design/incoming/README.md`'s build tables have one row per issue under one decision.
- **`AGENTS.md`:** one row per new file at the end of its table, never a rewrite of another feature's row, a feature's notes in its decision file.

### 2. What it does not do

- GitHub's own conflict badge and its web merge do not run custom merge attributes. A PR may still show a README conflict until someone merges `main` into it locally. That merge then completes on its own.
- Union cannot tell which of two rewritten lines is right. Rule 4 makes the duplicate fail the build, so a person picks one.

### 3. Cleanup

Rule 4's first run found five rows that earlier hand merges had already kept twice on `main`:
- `cloudflare-worker/src/services/README.md`: `hqApprovalSources.ts`, `ai/` and `scoring/`;
- `documentation/architecture/README.md`: `PROFILING_V2.md`;
- `frontend/src/lib/README.md`: `railOptions/`.

Each now has one row: the newer one, or the two merged for `ai/`.

### 4. Why the checks kept failing: main's CI never finished

- **What happened.** At 12:13Z #3165 added a sentence to `frontend/src/pages/README.md` naming `CapTablePage.jsx`. #3236, merged a minute later, deleted that file. Neither PR saw the other, so `check-folder-docs` failed on `main` from then until `1024f6356d` (13:11Z).
- **Why nobody saw it.** `ci.yml` had one concurrency group per ref with `cancel-in-progress: true`. On `main` every merge cancelled the run before it. The full suite takes about 25 minutes and merges came faster than that, so every CI run on `main` that day ended "cancelled". No run on `main` ever reported red.
- **What it cost.** Every PR that merged `main` in that hour failed `test:drift` on the same line: #3210, #3269, #3284, #3293 and #3295. Each session then wrote its own fix to the same sentence (#3275, and ports in #3182, #3273, #3294, #3296 and #3303), and those fixes conflicted with each other in the README.
- **The fix.** `ci.yml` now uses `migration-immutability.yml`'s rule:
  - one group per commit for a push to `main`, never cancelled;
  - a pull request's run is still cancelled by its next push.

  Every `main` commit gets a finished verdict, and a red one names the merge that broke it. It costs one full run per merge.

### 5. Tests

- `scripts/lib/readmeUnion.test.mjs` (`npm run test:retention`) holds:
  - the row, repeat, rule and marker checks;
  - the decision-keyed table;
  - the `.gitattributes` line.
- `frontend/test/ci_main_completes_d1279.test.mjs` holds `ci.yml`'s concurrency: per-commit and never cancelled on `main`, cancellable on a PR.
