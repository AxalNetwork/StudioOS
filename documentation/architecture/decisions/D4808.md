## D4808 — Custom programs get a generic page, and a proposal is reviewed before it is decided (#4808)

- **Status:** built 2026-11-07 (work package 5 of 7 of the Programs audit).
- **Builds on:** D953 (the program pages), D954 (the registry and playbooks), D955 (proposals and New program), D956 (grants).
- **Migration:** `202611072010_program_approved_specs.sql`.

### The problem

The registry accepts any valid program key, but the frontend resolved pages from the fixed set. A custom program had a catalogue row and no destination; creating one closed the dialog without refreshing the catalogue; HQ's read of a branch dropped any key outside the nine; and an approval kept only purpose, who and join, so a program could not say what had been approved. Sent proposals led straight to Decide, and the catalogue repeated the whole proposal list that has its own address.

### What changed

- **A generic page, `/admin/programs/:key`** (with `/how-it-runs` and `/activity`), for any key the registry holds, with one shell: About, Availability, Declared capabilities, the Approved proposal and the operating screen where one exists. Capability-specific screens are optional modules: where the frontend knows one for the key it links to it, otherwise the page says none exists yet. Create → open → edit → publish → revisit needs no new route for the key.
- **New program** refreshes the catalogue and offers Open program; every registry row's card has an Open door; a branch read keeps every valid registry key (`isRegistryKey`) instead of only the nine.
- **An immutable record of the approval.** `program_approved_specs` holds, per program, the proposal's uid and a frozen copy of every material field as approved. It is written in the approval's own batch and is append-only (triggers refuse UPDATE and DELETE). `GET /api/admin/programs/:key` returns it as `approved_proposal`.
- **Nothing material is lost.** The playbook draft gains Eligibility and What HQ receives. Eligibility, rewards, contracts and templates, tools and HQ obligations are carried into the spec and **explicitly marked not operational** ("Recorded as approved. Nothing enforces it yet."), as is each declared capability (`capabilities`), so a page never reads as if the program enforced them.
- **Review before Decide.** `/admin/programs/proposals/:uid` shows every submitted field, what is not operational, and Decide. The queue's rows lead to Review.
- **The catalogue** shows a compact proposal line with Open proposals for a Super Admin; search, filters and review live at `/admin/programs/proposals`. An Admin's own proposals list stays on the catalogue: it is their only address for it.

### Not done here

The remaining work packages of the audit. Making any of the "not operational" fields operate is each its own decision; this change only stops them being silent.
