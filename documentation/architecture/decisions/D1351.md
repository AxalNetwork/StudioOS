### 1. What LinkedIn gives

Every member can export their own connections today, with no LinkedIn approval: LinkedIn → Settings → Data privacy → Get a copy of your data → Connections.

The file, `Connections.csv`:
- opens with a "Notes:" preamble;
- then has the header: First Name, Last Name, URL, Email Address, Company, Position, Connected On;
- leaves Email Address empty unless the connection allowed it.

### 2. The parser, on the server

`parseConnectionsCsv` ports `frontend/src/lib/linkedinCsv.js`:
- **A BOM is dropped.**
- **The header** is the first of the first ten records that names First Name and Last Name. The preamble above it is skipped.
- **Quoted fields** keep their commas, `""` and newlines.
- **Each row keeps the line it starts on,** so the preview can name it.

A file with no such header is not LinkedIn's: 422 `not_linkedin_csv`. The browser parser looked for "Email Address" instead, but an export is LinkedIn's whether or not its emails are present.

**Caps:**
- **5 MB:** 413 `file_too_large`, checked on the declared length and again on the file;
- **20,000 rows:** the preview says `truncated`.

### 3. Normalising into the member's own book

The book is `network_connections`, with `user_id` the member. Migration 652 adds `linkedin_url` and `connected_on` to it, with an index on each of `(user_id, linkedin_url)` and `(user_id, email)`.

- **Name:** First and Last joined. A row with neither is an error.
- **Email:** lowercased, and kept only when it has the shape of an address.
- **Company and title:** Company and Position, trimmed.
- **Profile URL:** one form, `https://www.linkedin.com/in/<slug>`, lowercased, with no query or trailing slash. A regional host (`uk.linkedin.com`) is LinkedIn too. Anything else, a company page included, is no profile.
- **`connected_on`:** LinkedIn's "12 Mar 2024" as `2024-03-12`.
- **`source = 'linkedin_csv'`**, with one `contact_sources` row each (D1350).

### 4. Conservative matching, against the member's own records only

**The records** (`ownRecords`). Every statement binds the member:

| Record | Read as theirs by |
|---|---|
| Their book | `network_connections.user_id` |
| Their raise pipeline | `raise_prospects` on ventures whose `founder_id` is theirs |
| Their recruiting | `job_applications` to a posting they host, or on their ventures |
| Their interviews | `discovery_interviews` on their ventures |
| A partner's book | `partner_book_contacts.owner_user_id` |

Nothing is matched across members; that is part 7.

**The order** (`planRows`):
1. The exact profile URL.
2. The exact email, lowercased.
3. Otherwise, name plus company: folded to lower case with single spaces, and only when both are there.

**What each outcome does:**

| Outcome | What happens |
|---|---|
| **Matched**: an exact URL or email match on a row of the book | That row. The import fills only its blanks (URL, date, email, company, title) and never overwrites a value the member typed. Its source is recorded with `created_row = 0`. |
| **Suggestion**: a name-and-company match, or any match on a record outside the book | **Never merged on its own.** The row is added, and one `contact_match_reviews` row is written for the member to decide. |
| **Skipped**: the same URL or email as a row above it in the file | Nothing written. |
| **Error**: no name | Nothing written. |
| **New**: none of the above | The row is added. |

**Preview** (`?preview=1`): the counts (rows, new, duplicates, suggestions, skipped, errors) and the first twenty rows with their outcome. **Nothing is written,** and no email is echoed.

**Commit:**
- **One `contact_import_jobs` row** (D1350's `startImportJob` and `finishImportJob`), audited by count, never by email.
- **Writes go in D1 batches of 50,** so a 20,000-row export stays inside an invocation's query budget.

A support session may preview but not commit (403 `support_session`).

### 5. Suggestions: Merge, Keep both, Dismiss (`contact_match_reviews`, migration 652)

Each review row holds:
- the imported row of the book;
- the member's record it may be: its table and id;
- why: `url`, `email` or `name_company`;
- `pending`, `merged`, `kept_both` or `dismissed`.

`GET /import/reviews` lists the member's pending ones with both names and companies, and never an email.

- **Merge** is offered only between two rows of the book (`can_merge`). A raise prospect or an applicant is a different kind of record, so it is 409 `cannot_merge`. The imported row folds into the one already there:
  - blanks are filled and nothing is overwritten;
  - **its sources move across with `created_row = 0`, so both provenance rows stay.** The row they now describe was there first, so D1350's `delete_imported` never deletes it;
  - its notes and tasks move too;
  - its other pending suggestions are dismissed;
  - then the imported row is deleted.
  - If either row is gone, Merge answers 404.
- **Keep both** and **Dismiss** change no contact.
- **A suggestion is decided once.** A second decision is 409 `decided`.

### 6. Notes and follow-ups (migration 652)

`contact_tasks` (127) hangs off `contacts`, the founder's inbound CRM, and its only owner is `created_by`. It cannot hold a task on a row of the book. So the book gets two owner-scoped tables:
- **`network_contact_notes`:** a body of 1 to 4,000 characters.
- **`network_contact_tasks`:** a title of up to 300 characters, `due_on` as `YYYY-MM-DD`, and `done_at`.

**The routes:** `GET` and `POST /book/:id/notes`, `GET` and `POST /book/:id/tasks`, and `PATCH /book/:id/tasks/:uid` `{ done }`.
- **Every write is `INSERT … SELECT` from the member's own book row,** so another member's contact is 404.
- **A task is found only on its own contact.**

### 7. Verified

**`cloudflare-worker/test/linkedin_csv_import_d1351.test.ts`** (12 tests), on the migrated schema with synthetic people. It covers:

- **Merge keeps both sources:**
  - the merged LinkedIn source as `created_row = 0`;
  - blanks filled, the note moved;
  - it survives D1350's `deleteLinkedinOnly`, while a LinkedIn-only row goes;
