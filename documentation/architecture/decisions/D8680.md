## D8680 — A member's email link lands signed in, on the review screen, or on a reason: never a bare Sign in (#8680)

- **Status:** built 2026-11-27 (S14). Related #8536, #8537 (D8537).
- **Builds on:** D8537 (`magic=ok` starts the session probe; the local Worker and outbox in `frontend/tests/e2e/_helpers.js`), Task #9 and Auth v2 A2/A3d (`exploring` accounts, the licence picker at `/onboarding`, the review screen at `/exploring`).
- **No migration, no Worker route, no client method, no role or access-policy change, no new dependency, no workflow edit.**

### What was served when the retests ran

The four sign-up links, the returning Founder's link and the onboarding-chat control (25 and 26 November) all opened `/api/auth/magic/verify`, were sent to `/dashboard?magic=ok` or `/onboarding/chat?magic=ok` with only the httpOnly cookie set, and settled on `/login`. That is the bug D8537's Fix 1 names, and the served build did not have the fix:

- The last production deploy is run 44861456167 (2026-11-21 03:31Z), for main `086a2461c`. Every `cloudflare-worker-deploy.yml` run after it skipped its deploy job; run 45913216756 (main `d26a93a25`) waits for the `production` environment approval.
- PR #8579 (#8537) merged on 2026-11-25 as `ef1bea659`, which `086a2461c` does not contain.
- The bundle served on `axal.vc` and `app.axal.vc` on 2026-11-27 (`index-BrjndlSl.js`) reads the marker as `e.has('google')||e.has('google_signup')`, with no `magic`, and its `pendingNext` chunk marks the redirect with no history key. Both are the code before #8579.

So the live failure is a missing deployment, not a new regression. On main, with #8579, the same links reach the signed-in destination in a browser (below).

### What main still lacked, built here

When the session probe after the email link fails, the guard fell through to a bare `/login`: the link was spent and the person read only "Sign in". Now:

- `useAuthSync` keeps the email link's marker apart from Google's. When its forced `/me` probe fails, it records why with `linkBootstrapFailureFor` (`lib/pendingNext.js`): `session` when the server answered 401 (the browser did not keep the cookie), `unreachable` for anything else. It drops any cached account at the same time, because an identity the probe could not confirm, perhaps another person's from an earlier session, must not be drawn instead.
- `RequireAuth` carries the reason on its redirect, `withLinkFailure(loginRedirectFor(location), …)`, as `?magic_error=session|unreachable` after any kept `?next=`. Only those two codes are written.
- `LoginPage` words both in `MAGIC_ERROR_COPY` and opens on its send-a-new-link step, as it already does for `expired`, `invalid`, `rate`, `limiter`, `inactive` and `error` from the Worker. The address loses the code once read. The reason is spent when `/login` is reached, so a later signed-out visit to a protected page reads the plain sign-in page.

A member who is pending review already has an intelligible landing on main: an `exploring` account that has chosen its licence is sent from `/studio` to `/exploring` ("Welcome, …", "Founder · under review", "Membership under review — you can keep working"), and one that has not is sent to the licence picker at `/onboarding` ("Choose your adventure"). Nothing about who may see what changes.

### The browser regression

`frontend/tests/e2e/public_journey.spec.js` gains a "member sign-up links (#8680)" block at 1440 px, run by the `visual` job's existing step:

1. For each lane (founder, investor, partner, advisor): `/register?lane=…` → the sign-up link from the outbox → `/dashboard?magic=ok` → signed in on the licence picker; a reload keeps it. The account is `exploring` with that lane as its suggested role (none for advisor, as `LANE_ROLE` sends).
2. A returning member pending review, opening their link in a browser signed in as another account → `/exploring` under review as themselves; a reload keeps it.
3. An address with no account, through the ordinary email sign-in → `/onboarding/chat?magic=ok` → the licence picker; a reload keeps it.
4. A link used twice → "That sign-in link has expired or was already used. Send a new one." on the new-link step → a new link → signed in.
5. A link whose session probe answers 503, and one that answers 401 → the matching reason on the new-link step, nothing cached → a new link → signed in; a later signed-out visit reads the plain page.

The harness's register now keeps the lane as `suggested_role`, which `/me` returns, as `routes/auth.ts` does through `upsertSuggestedRole`.
