## D6935 part 2 — Model fallback, PR matching and reopened trackers for scan remediation (#6935)

- **Status:** built 2026-11-17 by S21 on S06's branch (#6939), from the owner's code-scanning audit of the same day.
- **Builds on:** D6935, D6473 (the landing bot's model runner), D6473-p2 (its account order).

### 1. The Claude/Codex fallback

Before this change, an alert with no usable Autofix got a `state:ready` tracker and nothing else. That covered
every Semgrep alert, and CodeQL alerts whose suggestion fails. Now:

1. **Offer.** The sweep offers such an alert to the fallback when its tracker is actionable and unclaimed, no PR
   carries its fix, and no `alert-fix-<n>` or `alert-autofix-<n>` branch holds work.
2. **Dispatch.** A separate job holding only `actions: write` starts one `scan-remediation-model.yml` run per
   alert.
3. **Plan** (read-only). It refuses:
   - a file that is not JavaScript or TypeScript;
   - a path that `pathGuard` protects or `merge-policy.mjs` rates T2;
   - an alert whose branch already exists.

   It builds a task with:
   - one allowed file;
   - the finding as untrusted data, never as instructions;
   - two rounds;
   - verification by `scripts/scan-remediation/syntax.mjs`, which parses the file with Node's TypeScript stripping
     and acorn and runs nothing.
4. **Run.** The landing bot's model runner tries primary Claude, then Claude 2, Claude 3 and Codex. The keys stay in
   the `repair` environment.
5. **Apply.** This job holds no model key. It:
   - re-checks the patch with main's `checkPatch` against the file at the patch's base;
   - makes one commit on a new `alert-fix-<n>` branch, with trailers `Landing-Bot-Kind: scan-fix` and
     `Model-Provider: <account>`, and never overwrites an existing branch;
   - opens a draft PR into main labelled `security-scan` and `model-edited`.

   If PR creation is refused, it leaves the compare link on the tracker instead.

The fallback is **off** until `SCAN_REMEDIATION_MODEL_PER_SWEEP` is set (at most 5). `SCAN_REMEDIATION_MODEL_PER_DAY`
caps runs per UTC day (default 2, at most 10). The owner reviews every model-edited PR and submits it to the merge
queue, as with the landing bot. A rerun reuses the same work: the plan skips an alert whose branch exists, and the
sweep links the open PR.

### 2. PR matching

- Only a PR into `main` counts. A PR into `staging` fixed nothing on main but used to end the attempt.
- A closed, unmerged PR no longer blocks a replacement. The tracker, not an old PR, records a person's decision.
- An open PR wins. A merged one is `merged_pr`: its tracker stays linked and nothing is generated until the next
  scan decides.

### 3. Trackers a person closed

A tracker closed as **completed** is reopened, once, with a comment naming the scan, when:
- the newest default-branch analysis by the alert's tool is later than the closure;
- that analysis still reports the alert open;
- the tracker is unclaimed.

A tracker closed as **not planned** stays closed: that is a decision, and the comment tells people to use it, or to
dismiss the alert in Code Scanning.

This covers #5589–#5595, closed as completed on 2026-11-13. The audit found six of their alerts still open on main.
The account that closed them is shared with agent sessions, so who closed them is not known; the scan is the
evidence.
