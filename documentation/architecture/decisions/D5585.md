### 1. No second ledger

The issue asks to extend the existing registries. So a release is made of #5581's own records:

| Release concept | Where it lives |
|---|---|
| Release line (one audience) | a `composite` asset in `work_graph_assets` under `human_publication`, plus one fixed row in `work_graph_release_lines` for its audience |
| Manifest | one immutable revision of that asset in `work_graph_revisions`. Its digest is SHA-256 of the canonical manifest body; its parent is the manifest published when it was cut |
| What the manifest pins | the revision's `component` edges in `work_graph_edges`, each to an exact component revision |
| Publication pointer | the line's head, moved only by `advanceHead`'s compare-and-swap |
| Publication audit | the `advance_head` / `advance_refused` rows in `work_graph_events` (refusals before the swap are recorded there too, with the release code) |
| Outbox effects | `work_graph_effects` rows (`release_<target>`) and their `effect_enqueued` audit in `work_graph_integrity_events` |

The four new tables hold only what those cannot: the line's audience, the manifest body (ids, digests, roles,
profiles and source refs), component attestations, and reviewers' decisions. All four are append-only by trigger. A
withdrawn approval is a later `withdraw` row.

### 2. Manifests pin exact versions

`cutManifest` takes each component as asset, revision and digest. It refuses:

- a digest that is not the revision's (`unpinned_component`);
- a revision that is not its asset's accepted head, which means a draft (`composite_incompatible`);
- another tenant's or company's piece (`wrong_tenant`);
- a piece the line's audience may not see (`audience_forbidden`). The rules: `public` takes only `public` pieces,
  `partners` adds `internal`, `investors` adds `confidential`, `internal` takes all four classes;
- a profile the kind does not allow (`policy_profile`);
- a full (non-partial) package that drops an asset the published manifest has (`incomplete_package`). A partial
  package may leave pieces out.

A manifest never contains a "latest" pointer. Its body records each piece's kind, role, access class, profiles and
`SourceRef` (Git commit, D1 row, Stream id, R2 key). So `publishedRelease` traces every displayed piece to the
version that was released, even after the piece is edited.

### 3. Domain policy profiles

`POLICY_PROFILES` sets four things per profile: the attestations each component needs at its exact digest, the
authorities that may approve publication, what an approval must carry, and what a change owes.

| Profile | Attestations | Approver authority | Approval carries | Superseded | Input changed |
|---|---|---|---|---|---|
| `code` | `pr_validated`, `ci_passed` (an agent run may attest) | `maintainer` | — | rebuild | rebuild |
| `marketing` | `brand_rights`, `claims_review` | `brand_owner`, `marketing_lead` | rights, disclosure | re-approve | rebuild |
| `investor_pitch` | `evidence_review` | `founder`, `partner` | citations, disclosure | re-approve | re-approve |
| `contract` | `counsel_review`, `signing_authority` | `counsel`, `authorized_signatory` | — | re-approve | re-approve |
| `protected_data` | `residency_review`, `security_review` | `security_officer` | — | re-approve | re-approve |

- **Profiles per kind.** Each kind allows certain profiles (`KIND_PROFILES`). `document` may be marketing, pitch or
  contract.
- **Protected data.** `protected_data` is added automatically to any `restricted` component, or any component with a
  residency.
- **Person attestations.** Every attestation except PR and CI is a person's, under an authority the caller resolved
  for them (`REQUIREMENT_AUTHORITY`).
- **Who resolves authority.** The service takes each person's authorities in `ReleaseContext.authorities`. The route
  that later exposes this resolves them from real roles.

### 4. Staleness, read and never stored

`releaseStatus` reads each pinned component against the registry now:

- **`superseded`.** The asset has a newer head. The component owes what its profile's `onSuperseded` says.
- **`input_changed`.** A `read`, `write` or `derived` dependency it was built from has a newer head. The component
  owes its profile's `onInputChanged`. For example, captions derived from a glossary owe a rebuild under marketing.
- **Manifest status.** The worst of its components: `reapproval_required` over `rebuild_required` over `current`.

Publication is refused with that code. A publish approval is bound to the manifest digest, so any change means a new
manifest and a new approval in any case. The per-component status says what work is owed before that.

The CAS also re-checks every component edge at the instant it runs (#5581), so an edit that lands between the checks
and the write still refuses (`composite_incompatible`).

### 5. Decisions bound to the digest (D5458)

`decideRelease` records one reviewer's decision (`approve`, `reject`, `request_changes`, `withdraw`) on one manifest.
Each decision is bound to:

- the manifest digest;
- the audience;
- the profile;
- the purpose: `publish`, or `render`, which is the separate approval for expensive renders and never authorizes
  publication;
- the reviewer and their authority;
- the time;
- citations (revision uids in the company);
- a disclosure ref and a rights ref;
- the approval-inbox item it came from (`approval_ref`). The Approvals inbox stays the place a decision is asked
  for (D5579 §1). This table is the digest binding, not a second inbox.

The service refuses:

| Code | Cause |
|---|---|
| `agent_review` | an agent as reviewer |
| `revoked_author` | a revoked reviewer |
| `stale_approval` | another digest |
| `audience_forbidden` | another audience |
| `no_authority` | an authority the profile does not accept or the person does not hold |
| `self_approval` | the manifest's author approving |
| `approval_incomplete` | an approval missing the citations, rights or disclosure its profile needs |

At publication the live decision of each reviewer is their latest row. Revocation and authority are re-read then,
not trusted from the decision.

### 6. Publication

`publishRelease` refuses unless all of these hold:

- every component is current (§4);
- every attestation exists at the pinned digest;
- every profile in the manifest has a live publish approval;
- no reviewer's latest decision is reject or request changes (`changes_requested`);
- D5579's release check passes: each pinned component's bytes were approved by a person when they became its head
  (`unapproved_release`).

Then it calls `advanceHead` on the line from `expectedManifestUid`.

The new `hooks.afterSwap` puts the effect rows in the CAS batch. Each row is guarded on this batch's
`advance_head` event (its idempotency key and request hash). So the pointer and its effects commit together or not
at all. A concurrent duplicate's guard finds the winner's event and its inserts do nothing (`ON CONFLICT DO
NOTHING`).

Effect targets:

| Target | Condition |
|---|---|
| `github_pr` | needs a `code` piece |
| `signed_document` | needs a `contract` piece |
| `website_cdn` | needs a `public` line |
| `stream` | none |
| `external_distribution` | none |

The tenant's outbox room is checked before the batch (`queue_full`). The check is not inside the insert, so a
publication can overshoot the cap by at most `maxEffects` (8).

**Replay.** A retry with the same key returns the first result and writes nothing. That covers a lost callback, a
redelivered webhook and two deliveries at once. The same key for another manifest, base or effect set is
`idempotency_conflict`. A late webhook with a fresh key cannot roll the pointer back:

- naming an older expected manifest is `stale_revision`;
- naming a manifest that was not built on the current one is `not_descendant`.

### 7. Cost telemetry

Every result carries `cost: { d1Statements, d1Batches }`, including the statements its `createRevision` or
`advanceHead` call issued.

### 8. Left for later parts

- **Delivery.** Handlers for the five `release_*` effects (GitHub PR, Stream, signed document, website/CDN, external
  distribution). Also reconciliation of an ambiguous delivery through the effect's idempotency key, with provider
  acceptance and confirmed delivery as separate outcomes (D5458). Until then the effects stay `pending`, and no drain
  is scheduled.
- **Revocation and takedown.** Withdraw a published release with a reason and the current release identity. Stop
  serving disallowed content while keeping the manifest, decisions and audit (retention). Re-point the line to a
  prior manifest. #5581's head only walks forward, so this needs a new revision that re-pins the older components,
  which `cutManifest` refuses today because they are not heads.
- **Render approvals.** Tie render approvals to #5586's budgets.
- **The route.** Super-Admin-only, behind a flag that defaults off. It resolves scope and authorities, and turns an
  Approvals-inbox decision into `decideRelease`.

### 9. Rollback

Every function is unreachable without a route.

- **Undo the code.** Revert `workGraphReleases.ts` and the `hooks` argument. `advanceHead` without hooks behaves
  exactly as before.
- **Drop the tables.** Dropping the four `work_graph_release_*` tables loses only the release metadata. The composite
  assets, revisions, edges, events and queued effects stay #5581's. A queued `release_*` effect has no handler, so
  dropping these tables delivers nothing.
