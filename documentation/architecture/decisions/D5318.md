### H10

**The finding.** Every anonymous page asks for `GET /api/settings/appearance`, `GET /api/settings/explainers` and `GET /api/public/plans-and-packs` on load (baseline §3).

**How each read is personalised, read from the code before any header was chosen.**
- `settings/appearance` and `settings/explainers` are **one member's own choices**: `requireAuth`, then `user_settings WHERE user_id = ?` (`routes/settings.ts`). They are not admin-wide settings, so no admin change has to reach anyone through them. To a visitor both can only answer 401. `SettingsProvider` (`frontend/src/contexts/SettingsContext.jsx`) sent both on every load of every page anyway, and swallowed the 401.
- `public/plans-and-packs` is built from the D1 catalogue mirror, the token packs and the Worker's Stripe mode only (`plansAndPacks(env)`, `services/aiCredits.ts`); it never reads the caller, and a signed-in read answers the same bytes as an anonymous one (held by the test below).
- No middleware sets `no-store` on `/api/*`, and the frontend's `request()` sends no `cache` option and no cache-busting parameter, so nothing overrode a route's own header. No change was needed there.

**What changed.**
1. **The anonymous page no longer sends the two member reads.** `lib/sessionHint.js` decides whether the browser may hold a session from what every sign-in leaves behind: a `token` or `user` in localStorage, or this host's JS-readable CSRF cookie, which `setAuthCookies` sets beside the httpOnly auth cookie with the same lifetime. With none of the three, `SettingsProvider` skips both reads and keeps its cached theme. Any one of them means "ask", so the error is on the side of one wasted 401, never of hiding a member's theme.
2. **The member reads are `Cache-Control: private, no-cache` with an ETag.** `private`: no shared cache may keep one member's settings. `no-cache`: the browser revalidates on every use, so a save in another tab or device shows on the next load with no window at all; an unchanged value answers 304 with no body.
3. **The plans read is `public, max-age=60, s-maxage=60, stale-while-revalidate=60` with an ETag.** It is a price, so the window is short. A price or plan change shows on any load within 60 s, and at worst 120 s for the one load that is served the stale copy while it revalidates. That supersedes D816's five minutes (`max-age=300`), which predated a freshness requirement for prices; the 60 s is what it was before D816. A revalidation whose ETag still matches answers 304 instead of the whole catalogue.
4. The ETag is `util/httpCache.ts`'s `jsonWithEtag`: SHA-256 of the exact body, first 128 bits. The route still builds the body to compare, so **a 304 saves the bytes, not the D1 reads**; nothing in-isolate is cached, so no server-side staleness is added to the windows above.

**Before and after, on the #4573 fixture** (`main` at `d16c59081c`, synthetic accounts, statements by category auth / telemetry / route).

| Read | Before | After |
| --- | --- | --- |
| Anonymous page load, the two member reads | 2 requests, both 401, 4 D1 telemetry writes | 0 requests |
| `settings/appearance`, `settings/explainers` signed in | 200, 4 / 2 / 1, no `Cache-Control`, no ETag | the same 200; a revalidation answers 304, 0 B, the same 7 statements |
| `public/plans-and-packs` | 200, 18,892 B, 0 / 2 / 3 anonymous (4 / 2 / 3 signed in), `max-age=300`, no ETag: every refetch is the whole body | the same 200 and statements, `max-age=60` + 60 s stale-while-revalidate; a revalidation answers 304, 0 B |

**What CI holds.** The three reads have no row in `perf_budgets_4573.test.ts`, and a header lowers no server-side count, so `cloudflare-worker/test/public_config_cache_5318.test.ts` holds: each read's statement budget by category, the two policies, the same bytes and ETag for anonymous and signed-in plan reads, 304 with no body and no more statements than the 200, and a saved change moving the ETag. `frontend/test/settings_context_anonymous_5318.test.mjs` holds the session hint and that both member reads come after it. The harness now returns each response's headers and body size and takes request headers (`_perf_harness.ts`).

**Not done.** The plans read is still fetched by several components on a page that need it (`planPrices.js` shares one read; `RegistrationPlan`, `TokenPacksSection`, `StoragePage` and `PricingPhone` call it themselves); within 60 s the browser cache answers those. No edge cache (Cache API) is added: the Worker answers every request that reaches it, and no production traffic was read to size one.
