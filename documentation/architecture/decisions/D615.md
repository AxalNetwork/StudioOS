## D615 — A draft save on a published contract type does not change the live type

**Saving a draft for a published contract document type writes a pending copy. The live title, layer, party roles, required fields and status stay until publish.** Issue #1313. Migration 416.

**What was wrong.** `upsertDraft` inserted with `ON CONFLICT(doc_type) DO UPDATE` and, when the row was already published, kept `status = 'published'` while replacing the live columns. A draft save changed the type the hub shows, with no reason, no step-up and no audit.

**The pending copy.** Migration 416 adds `draft_title`, `draft_layer`, `draft_party_roles_json`, `draft_required_fields_json`, `draft_updated_at` and `draft_updated_by` on `contract_doc_type_registry`. They are empty until a save. Nothing is backfilled.

**Saving.** A type that is only a draft still updates the live columns, and clears any pending columns, as it did before. A published type leaves those live columns and `status` untouched and writes the save into the pending columns. The live row's `updated_at` does not move.

**Publishing.** `POST /api/admin/contracts/registry/:doc_type/publish` is still the Super Admin write bar (TOTP session, step-up, a reason of at least 10 characters) and is still audited as `registry.type.publish`. It copies any pending columns onto the live columns, sets `status` to `published`, then clears the pending columns. A draft-only row has nothing pending, so publish promotes the values already on the row.

**Reads.** `GET /api/admin/contracts/registry` and `GET /api/admin/contracts/registry/doc-types` return the live values and `pending_draft` (null when there is none). Overlap and the draft-type count still use the live row: a pending revision is not a second type and is not a draft-status row. The Contracts page does not describe the old overwrite, so its copy is unchanged.

The review window that would show the pending draft next to the live type is not this change. The reads carry both so that page can.
