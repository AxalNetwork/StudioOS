## D4602 — An accepted item's own address, one Progress filter model, and native radios (#4602)

Build audit 3/4 (#4602), findings 5, 7 and 8 — the three that need no new
layout. The audit's other findings (the phone Build overview's Plan entry, the
compact phone filter arrangement, and evidence-chip drilldown) are built to the
approved Build V2 boards (#4846), whose export is not on `main` yet, so they
are not here.

### Finding 5 — Open goes to the row, not the module

An accepted plan item records the row it landed in: `build_plan_items.landed_table`
and `landed_id`, written by `buildPlanAccept.ts`'s `LANDED` statements. The
done row's Open went to `/build/<module>` and left the founder to find the row
by eye, although the plan had held its id since the accept.

`landedHref(item, module, search)` in `buildPlanModel.js` resolves it. **It
answers the row only where the module's own record route reads that table**,
and the table of which routes do is read off `services/records/build.ts`, one
entry per `record()` reader that file actually has:

| `landed_table` | Module whose `record()` reads it | Address |
| --- | --- | --- |
| `mvp_features` | `solution-design`, `prototype-mvp` (both `featureRow`) | `/build/<module>/<id>` |
| `roadmap_okrs` | `product-roadmap` (`roadmapRow`) | `/build/product-roadmap/<id>` |
| `formation_steps` | `company-creation` (`filingOf`) | `/build/company-creation/step-<id>` |
| `venture_risks` | none | the module |
| `hypothesis_experiments` | none | the module |

Three things this gets right and a simpler version would not:

- **The ids are typed where the record reader types them.** `filingOf` reads
  `step-<id>` for a formation step, `obligation-<id>` for an obligation and
  `lab-<id>-<n>` for a Lab order, and `services/records/build.ts` writes
  `recordHref('company-creation', `step-${id}`, …)` itself. The prefix is that
  file's convention, not a guess here.
- **A module that cannot address the table keeps the module link.** Two tables
  have no record reader at all. A link built from the id anyway would open
  *another table's row with the same number* — a worse answer than the module,
  because it would look right.
- **Nothing but a positive integer reaches a URL.** `landedId` takes
  `^[1-9]\d{0,17}$` and nothing else, so a null, a `0`, a `../x` or anything
  with a separator in it falls back to the module rather than building a path
  out of it.

The link's own words say which it is — "Open the record" or "Open the module",
with a `title` naming the destination — so the founder knows what it opens
before pressing it. `search` carries the venture either way.

### Finding 7 — one filter model, both widths

Desktop Progress had search, Module, Stage, Tool, a sort and pages of 25,
held in `ItemsTable`'s own `useState`. The phone branch called
`filterRows(rows)` **with the defaults** and offered Show more, so a founder
with a long accepted list had to page through every card five at a time.

The state is the page's now — `useProgressFilter()` in
`BuildPlanProgress.jsx` — and both branches read `filterRows(rows, f, sort)`
from it, so the same inputs select the same items at either width. That is the
audit's "equivalent desktop/phone filter inputs select the same underlying
items": one function, one state, two renderers.

The controls above the phone's cards are `ProgressControls`, **the desktop
controls themselves**, reused and wrapping at a phone's width with 44px
targets. They are not a new arrangement: the compact one belongs to the Build
V2 boards, and when that export lands it restyles this row and changes nothing
underneath. The phone's Show more window resets to five whenever the filters
change, so it never leaves a founder reading the eleventh card of a two-card
result, and an empty result says so rather than showing nothing.

### Finding 8 — the edit dialog's choices are native radios

Impact, Effort, Severity and Lane were `<button role="radio">`s inside a
`role="radiogroup"` with no key handling: every option was a tab stop, the
arrow keys did nothing, and `aria-checked` was the only thing that moved. The
WAI-ARIA radio pattern asks for one tab stop, arrows that move **and** select,
and a group label.

`ChoiceField` draws native `<input type="radio">` inputs that share a `name`,
so the browser gives all of that — one tab stop on the checked input, arrows
that move and select, Tab out to the next field — and **there is no keyboard
code here to get wrong**. The chip look is the label's, drawn from the input it
follows with `peer-checked` and `peer-focus-visible`; the input stays in the
accessible tree (`sr-only`, never `display: none`, which would take the
keyboard pattern with it). A `<fieldset>`/`<legend>` is the group's accessible
name, replacing the `aria-labelledby` span. Each field gets its own `name`, so
Impact and Effort are separate groups rather than one.

### What this does not do

No Worker change, no store, no migration, no new route: `/build/:slug/:id` is
`App.jsx`'s existing record route, answered by readers that already exist. No
authorization changes — the record route is guarded as it was, and this only
decides which URL a link points at.

## Step 2 — phone Plan entry, compact phone Progress, evidence drilldown (2026-11-14)

Built to the Build v2 boards now on `main` from #5858 (`design/incoming/Build v2 · Boards.dc.html`,
`Build v2 Page.dc.html`, D4846): BD2 and BD14m B (the phone overview and the plan's phone
pages), BD14m A and BD5 (phone Progress), BD4 (the evidence sheet) and BD16 (radio chips).

**The phone Plan entry (BD2, BD14m B).** `BuildPhoneNav.jsx` draws Build's phone tabs,
Overview · Plan · Progress: literal links with `aria-current="page"`, 44px tall, each carrying
`?project_id=` (and a one-claim plan's `scope` on Plan and Progress, through `planHref`).
`PhoneCycleRoot` draws them above every state of Build's phone root (loading, refused,
unreadable, ready), so the plan is one tap away even while the overview fails, and opens
"Everything else in Build" with a Build Plan row to `/build/plan`. The plan's own phone pages
draw the same tabs in place of the Plan · Progress strip; an Operating Partner keeps
Progress only. **Not drawn: BD2's Tools tab and the row's counts.** Build › Tools is #6029's
entry (BD23), which waits on #5078; and the overview read carries no plan counts, so the row
says what the plan is rather than inventing "12 accepted".

**Compact phone Progress (BD14m A, BD5).** `PhoneProgressControls`: Search, then Filters (N)
and Sort, each a bottom sheet (`Sheet phone="sheet"`). Filters are Module, Stage and Tool as
native radio chips on a draft; Show N items applies them, and N is `filterRows` over the
draft, the same function and the same page state the desk's table reads, so equivalent inputs
select the same items at either width. Sort applies as it is picked. The desk keeps its
selects.

**Evidence drilldown (BD4).** A proposal's "Because" chips are buttons that open the evidence
sheet: one row per reference (a signal per row, where the chip counts them), with its kind,
label and source word, and Open record where a module's own `record()` reader reads that
reference's row by that id — `evidenceHref`:

| Reference | Opens | Reader |
| --- | --- | --- |
| `pain_group` | `/validate/problem-discovery/<id>` | `pain_groups` |
| `hypothesis` | `/validate/experiments/<id>` | `hypotheses` |
| `signal` | `/validate/demand-signals/signal-<id>` | `demand_signals` (typed id) |
| `decision` | `/validate/verdict/<id>` | `validation_decisions` |
| `feature` | `/build/solution-design/<id>` | `mvp_features` |
| `experiment`, `finding`, `commitment` | nothing: kind only | no reader keyed by that id |

Only a positive integer reaches a URL. Permissions: the link exists only where a record page
reads the source, and that record route applies its own access check when opened, as every
record link does; the sheet never claims a reader may open what the Worker would refuse.
**Return to the same proposal:** the open sheet is the plan address's `?evidence=<uid>`,
written with `replace`, so Back from a record lands on the plan with the same proposal's sheet
open, venture and scope kept; an address naming an item no longer on the plan opens nothing.
The sheet's heading takes focus on open and focus returns to the chip on close (`Sheet`).
**Dates:** BD4 draws a date per node "only where recorded"; a plan reference stores none, so
the sheet shows none and says the dates are on each record, rather than "Date not recorded"
beside every row.

**Radio chips (BD16).** Step 1's native radios gain a check mark beside the weight on the
selected chip (never colour alone) and 44px on a phone; Progress's filter sheet reuses the
same `ChoiceField`.

Tests: `frontend/test/build_plan_step2_4602.test.mjs`; `build_plan_4602.test.mjs` and
`phone_cycle_roots_d703.test.mjs` updated for the sheet and the Build Plan row.
