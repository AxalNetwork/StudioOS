### The decision

- **A module read says what it is for** (`ReadOpts`):
  - `FULL` for a module page;
  - `OVERVIEW` for the overview.
- **With `OVERVIEW`, no reader builds its integration `parts`**, and every read used only inside them is skipped:
  - GitHub (proposals, notes, releases, contributors, company facts);
  - Vercel (runtime, hosting, proposals);
  - Lovable (app links, the last opened);
  - in Operating systems, the Code and Hosting systems.
- **Why that is safe.** The overview answers cards, figures and the phone's focus, meter and index. Those read each module's `card`, `facts` and `rows` only (`services/cycleFocus.ts`), and its response never carried `parts`.
- **What stays.** The module rows stay (the phone index reads Solution design's and Company creation's), and so does every fact.
- **Unchanged.** Authorization (`context()` and `canReadBoard`), each module's own failure isolation (`safeRead`), and the unreadable, not-recorded and zero distinctions.

### Tests

`cloudflare-worker/test/build_read_amplification_4603.test.ts`, each assertion mutation-checked:

- the overview stays within 29 statements at 10 and at 1,000 records, and none of them touches an integration store;
- each overview card equals its module page's card;
- every module page still answers its parts;
- another venture's founder is refused the overview and every module;
- the remaining limit below is pinned, so part 2 lowers it on purpose.

### What is left (part 2)

- **Rows still grow with the venture.** The overview's cards and the phone's index aggregate every module row in memory. Each module page reads every record, then filters, sorts and pages 25 in memory (`pageBuildRows`).
- **Bounding that needs two things:**
  - each card's chart and facts as SQL aggregates (counts by state, by severity, by month);
  - the list's search, filters, its ordinal sorts (for example impact high → low, filing state overdue first) and its pages in SQL, with a deterministic tie-break on id.
- **One module per PR.** That keeps the semantics (totals, empty pages, filters on computed keys such as "Links to nothing" and the due window) testable one module at a time. Solution design is first (part 2a, below).
- **Not changed here.** The caller is still resolved twice per Build request (`context()`, then `requireAuth`). #4573's H1 fixes that across every route.

### Part 2a — Solution design pages its features in SQL (2026-11-07)

Measured with `_build_reads.ts` against main at the time (`805f58221b`). Rows *returned* to the Worker; statement counts in brackets.

| Records per list | Overview before | Overview after | Solution design page before | Solution design page after |
|---:|---:|---:|---:|---:|
| 10 | 56 (29) | 40 (29) | 23 (14) | 17 (15) |
| 100 | 529 (29) | 333 (29) | 203 (14) | 32 (15) |
| 1,000 | 5,254 (29) | **3,258** (29) | 2,003 (14) | **32** (15) |

- **The card reads aggregates.** It reads the feature count, the linked count (a stored pain theme) and the risks by severity, and no feature row. The overview passes `rows: false` (`ReadOpts`), so it reads no feature row and no risk row at all.
- **The phone index reads `facts.features` and `facts.linked`.** `services/cycleFocus.ts` falls back to the rows when a read gives no counts. `linked` is a new, additive fact.
- **The module page's list is paged in SQL** when every part of the query maps exactly onto stored values:
  - the default sort, and Impact or Effort either way;
  - the Linked, Impact and Effort filters.

  Each key is the same mapping the row's `keys` use (`IMPACT_KEY`, `EFFORT_KEY`). An unknown value sorts last either way, and ties keep read order (`sort_order`, then `id`), as `pageBuildRows` keeps them. The total is a `COUNT(*)` with the same predicates.
- **The rest stays in memory, on purpose.** A search, a sort on a text column, or a filter on any other key reads every feature and pages in memory, exactly as before. The reason: `toLocaleLowerCase` and `localeCompare` are not SQLite's `LOWER` and binary order, so moving those into SQL would change results for accented and some punctuated text.
- **Proven equal.** `build_bounded_reads_4603.test.ts` compares the SQL page with `pageBuildRows` over every feature, for more than 300 queries on features that cover every mapped value. Every new assertion is mutation-checked.
- **`facts.risks` is dropped (owner decision, 2026-11-07).** The module page answered the full risks list in its facts from D662 on. No screen read it, and it grew with the venture. Risks are now counted by severity for the card and never listed. `cycle_build_d662.test.ts` checks the stored risk and that the list is gone. The Solution design page is now bounded: 32 rows at any size, of which 25 are the page.

**Left for part 2b onwards:** Prototype & MVP, Product roadmap, Founding team, Company creation and Operating systems, one module per PR. The phone index still reads Company creation's rows for the next filing date.

### Part 2b, module 1 — Prototype / MVP pages its must-haves in SQL (2026-11-09)

Measured with `_build_reads.ts` against main at the time (`6ac1f0a8af`), at the sizes part 2a used. Rows *returned* to the Worker; statement counts in brackets. Main's overview had already fallen from 29 to 26 statements since part 2a, through changes outside this package.

| Records per list | Overview before | Overview after | Prototype / MVP page before | after | Page with a search, before | after |
|---:|---:|---:|---:|---:|---:|---:|
| 10 | 39 (26) | 30 (27) | 13 (13) | 10 (16) | 13 (13) | 9 (15) |
| 100 | 332 (26) | 233 (27) | 103 (13) | 30 (16) | 103 (13) | 54 (15) |
| 1,000 | 3,257 (26) | **2,258** (27) | 1,003 (13) | **30** (16) | 1,003 (13) | 504 (15) |

The harness marks every other seeded feature a must-have, so 1,000 records are 500 must-haves.

- **The card and facts read aggregates.** One row gives the must-have count, the done count and the first must-have not done (in read order, `sort_order` then `id`: the card's "Complete <title>"). The burn-up reads done must-haves per month of completion, one row per month. The overview passes `rows: false`, so it reads no must-have row. It costs one statement more than before (the per-month read) and returns one row per month instead of one per feature.
- **The phone needs nothing more.** Its focus, meter and Prototype index row read the `must_haves_done` and `days_to_mvp` figures, which are built from `facts` and the card, never from Prototype's rows (`services/cycleFocus.ts`).
- **The module page's list is paged in SQL** when every part of the query maps exactly onto stored values: the default sort (State) either way, and the State and Hypothesis filters. The keys are `MUST_KEY`'s mapping, and a hypothesis counts only when its claim joins (another venture's hypothesis reads "none", as the row says). An unknown state sorts last either way, ties keep read order, and the total is a `COUNT(*)` with the same predicates. The Hypothesis filter still offers every must-have's hypothesis, from one row per distinct hypothesis, not from the page.
- **One helper for every module.** Part 2a's `featurePageSql` is now `listPageSql(list, query)` with a `ListSql` per module (its keys, ordinal sorts, default sort and read order), and `sqlPage` runs the count and the page. Solution design's behaviour is unchanged. The later modules declare a `ListSql` and reuse both.
- **The rest stays in memory, on purpose,** for part 2a's reason: a search, a sort on a text column, or a filter on another key. That path now reads must-haves only (`is_must_have = 1`, exactly the rows the reader kept before), so it reads half as many rows on the harness venture.
- **Proven equal.** `build_prototype_reads_4603.test.ts` compares the SQL page with `pageBuildRows` over every must-have for more than 300 queries, and the card and facts with the old full-read algorithm, kept in the test as the reference. A counted zero stays `[0, n]`, no must-haves stays Not recorded, and a failed Prototype read is Unreadable alone while the other cards read. Every new assertion is mutation-checked.
- **#5067 is not folded in.** Its measured-zero finding is the must-have *record* page's Tests run fact (`services/records/build.ts`), and its 20-row feedback limit and 200-item dependency cap are Product roadmap's. None of them is on this reader's path, and this change alters none of them.

**What is still not bounded.** D1's rows *read* (scanned) still grow with the venture: the aggregates and the ordinal sort scan the venture's features through `idx_mvp_features_project_order`. No index would help the ordinal sort, which ranks a mapped value. The harness cannot measure rows read; Cloudflare's D1 analytics can. The in-process times are not production latency, and no production speed-up is claimed.

**Left for part 2b's later PRs:** Product roadmap, Founding team, Company creation (including the phone index's next-filing date) and Operating systems.
