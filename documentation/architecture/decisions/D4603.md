### The decision

- **A module read says what it is for** (`ReadOpts`):
  - `FULL` for a module page;
  - `OVERVIEW` for the overview.
- **With `OVERVIEW`, no reader builds its integration `parts`**, and every read used only inside them is skipped:
  - GitHub (proposals, notes, releases, contributors, company facts);
  - Vercel (runtime, hosting, proposals);
  - Lovable (app links, the last opened);
  - in Operating systems, the Code and Hosting systems.
- **Why that is safe.** The overview answers cards, figures and the phone's focus, meter and index. Those read each module's `card`, `facts` and `rows` only (`services/cycleFocus.ts`), and its response never carried `parts`.
- **What stays.** The module rows stay (the phone index reads Solution design's and Company creation's), and so does every fact.
- **Unchanged.** Authorization (`context()` and `canReadBoard`), each module's own failure isolation (`safeRead`), and the unreadable, not-recorded and zero distinctions.

### What is left (part 2)

- **Rows still grow with the venture.** The overview's cards and the phone's index aggregate every module row in memory. Each module page reads every record, then filters, sorts and pages 25 in memory (`pageBuildRows`).
- **Bounding that needs two things:**
  - each card's chart and facts as SQL aggregates (counts by state, by severity, by month);
  - the list's search, filters, its ordinal sorts (for example impact high → low, filing state overdue first) and its pages in SQL, with a deterministic tie-break on id.
- **Its own PR.** That keeps the semantics (totals, empty pages, filters on computed keys such as "Links to nothing" and the due window) testable one module at a time.
- **Not changed here.** The caller is still resolved twice per Build request (`context()`, then `requireAuth`). #4573's H1 fixes that across every route.
