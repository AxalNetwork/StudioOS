## D4647 — a reporting period is the last completed one, and a total counts the whole ledger (#4647)

Issue: [#4647](https://github.com/AxalNetwork/StudioOS/issues/4647), Portfolio
audit package 5 of 5. This decision covers the parts of that package that could
start without waiting on the #4817 canvas or on another package's files; the
rest stays open on the issue.

### 1. Which quarter a default means

The quarter-end export's default `as_of` was

```js
const quarterEndMonth = Math.floor((now.getMonth() - 1) / 3) * 3;
const end = new Date(now.getFullYear(), quarterEndMonth, 0);
return end.toISOString().slice(0, 10);
```

which is wrong twice.

`getMonth()` is zero-based, so in the first month of any quarter — January,
April, July, October — `(0 - 1) / 3` floors to `-1` and the default landed a
**whole quarter early**: in April it exported 31 December rather than 31 March.
And `new Date(y, m, 0)` is local midnight, which `toISOString()` then converts
to UTC, so for every reader east of UTC the exported date was the **day before**
the quarter end. Neither error shows on the sheet: the figures are simply a
different quarter's, under a date nobody checks.

**The rule is the last completed quarter, on a civil date.** A quarter still
running has no end to report. `frontend/src/lib/reportingPeriod.js` holds it —
`civilToday`, `quarterPeriod`, `lastCompletedQuarter`, `lastCompletedQuarterEnd`,
`isCompleted` — and works on a calendar day resolved in the reader's own IANA
zone through `Intl`, never on an instant converted to UTC.

This is the same rule the Worker already applies when it builds a fund's
quarterly pack (`services/fundReportBuild.ts`'s `lastClosedQuarter`). Rather
than a second definition,
`cloudflare-worker/test/portfolio_reporting_period_d4647.test.ts` pins the two
to each other for every month of three years, so they cannot drift.

### 2. A total counts the ledger, not the page

`GET /api/portfolio-support` read the ledger with a bare `LIMIT 400` and then
accumulated everything it reports — `totals`, the per-company rollup and
`untouched` — from those rows in JavaScript. There was no `COUNT(*)` anywhere
in the file. On a book with more than 400 entries every one of those figures
silently understated the work, on the one desk whose stated purpose is to make
that work auditable; and the page beside them printed `entries.length` as "N
recorded entries", which was the page's length rather than the ledger's.

**The page narrows what is listed, never what is counted.** The totals and the
per-company rollup are now grouped in SQL over the whole authorized population,
and ignore both the cursor and the state filter. `totals.entries_total` is the
ledger's own count, and the page's copy reads it. An entry with no hours is
still counted and never summed as zero — that rule moves into the SQL rather
than out of it.

### 3. Every record stays reachable

The order was `created_at DESC` alone. `created_at` is a second-resolution
stamp, so entries written in one request tie and the order is not total: a
reader paging back could miss a row or see one twice. The order is now
`created_at DESC, s.id DESC`, and the cursor is an entry's own `id`
(`?before=`), never an offset, because an offset page shifts under every write.
`limit + 1` is read so `has_more` is answered without a second count, and the
response carries `page: { limit, state, returned, has_more, next_before }`.

`?state=` narrows the listing in SQL. Without it an outstanding promise older
than the newest page could not be reached at all — which is, in effect, the
same defect as the "status written once and never updated, so every row reads
outstanding forever" that this route's own header says it exists to end. The
Value-add desk's Delivered and Outstanding chips now ask the Worker for that
state instead of filtering one page in the browser. An unknown state is a 400,
not a silently ignored parameter.

### What the ledger's Export writes

The Value-add desk's Export is the shared zone builder's `kind: 'export'`,
whose label is `Export · this view` and whose documented contract is that it
writes the rows the view is showing. That stays: the fix is that the view now
says what it is. The line beside the ledger reads the whole ledger's count
from `totals.entries_total` and adds "the newest N shown" whenever
`page.has_more`, so a reader pressing Export knows which rows they are about
to get. Making that control walk the cursor to the end would change a builder
shared by every investor zone, which is not this package's file.

### What is not in this decision

The per-company latest-update read (the issue's fifth criterion) needs
`routes/portfolio_updates.ts`, which #4636 owns and has in review, so it is
asked for on the issue rather than taken here. The summary labels, the units
and the overview presentation wait on the #4817 canvas, per S1's note on the
issue. The authoritative valuation-mark rule and the return formulas belong to
#4644, and the source-availability states to #4645; neither is touched, and no
gate or scope moved.

### Where the contract is written down

`routes/portfolio_support.ts`'s own header carries it, which is where #4104
puts a route's description: the services and routes READMEs generate their file
lists from each file's header comment and take no new hand-written entries.

### Where it is held

- `cloudflare-worker/test/portfolio_reporting_period_d4647.test.ts` — the
  period rule, pinned to the Worker's, month by month across a leap year and
  two year boundaries, plus the zone behaviour.
- `cloudflare-worker/test/portfolio_support_totals_d4647.test.ts` — the totals
  and the paging, driven with **more entries than one page**, because that is
  the only shape in which the old code was wrong.

Every assertion in both is checked both ways.
