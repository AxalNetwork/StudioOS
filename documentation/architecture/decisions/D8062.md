### The allowlist

The first save normalised the cache and CodeQL sub-actions to their parent
paths (14 entries). GitHub matches a pattern against the whole `uses:` string,
so every job using `actions/cache/restore`, `actions/cache/save` or a
`github/codeql-action/*` sub-action failed at "Prepare all required actions"
(reported by S21 on #8062). The correction, saved by 19:17 UTC and checked
after a reload and on real PR and `main` jobs, lists those five sub-actions on
their own: 17 full references across 14 repository revisions, 16 used directly
and `oven-sh/setup-bun`, which the pinned `anthropics/claude-code-action` calls
from its own `action.yml`. That corrected list is what the baseline holds.

**Re-checked on 2026-11-27** against every `uses:` of
`.github/workflows/*.yml` on main `d26a93a25`: every reference in use is
listed, and every listed reference is in use (`oven-sh/setup-bun` through the
pinned action's `action.yml`, read at that pin). No workflow has bumped a pin
since 2026-11-21. The references not on the list are this repository's own
reusable workflows: `./.github/workflows/landing-bot-model.yml` and
`landing-bot-model-round.yml`, and
`AxalNetwork/StudioOS/.github/workflows/capacity-planner.yml` pinned at a
`main` commit (added on 2026-11-23 by #8234, re-pinned by #8658). The
`selected` policy allows the owner's own workflows, and CI on main has parsed
`ci.yml` with that call since, so none is missing. A pin bump or a new action
needs the admin slot to add the reference before the workflow change lands,
and the baseline row to change with it; a parent-path entry never stands in
for a sub-action.

### Not applied, and why

1. **The organisation-wide allowed-actions policy.** Other organisation
   repositories use version-tag references the StudioOS list would refuse,
   and two of the organisation's repositories were not inventoried.
2. **Public repository creation.** The checkbox is checked and locked in the
   console; GitHub documents that restriction under Enterprise Cloud. No plan
   change was made.

The coordinator asked the owner on #8062 (2026-11-27) to choose between
accepting the repository-level allowlist as the StudioOS boundary (A),
migrating the other repositories first (B) and Enterprise Cloud (C). Until the
answer, `org.members_can_create_public_repositories` stays to be recorded, and
the baseline has no row for the organisation allowlist.

### Rollback

Never back to the 14-entry list. If an action is refused, add its exact full
reference, pinned, in a reviewed change. Allowing all actions or dropping the
SHA requirement is not a recovery step; reversing 2FA or fork approval is an
owner decision.
