## D5624 — A team's Landing settings, off behind TEAM_LANDING (#5624)

Part of #5600. A team (a company, or a standalone project) records how its
agents' code lands: which repository, which risk tiers land without a person,
who signs T2, how far repair may go, who owns which paths, how many changes
run at once per repository, a compute budget and the executors it allows.
This decision is the contract and the store. Nothing enforces the settings
yet: admission and quotas are #5570's, reservations and the conflict graph
(which read `path_owners`) are #5580's.

### Contract

`merge-control/contract/landingPolicy.ts` imports nothing. It holds the types,
`LANDING_DEFAULTS`, the HQ caps and `validateLandingPolicy(body, caps)`.

| Field | Shape | Rule |
| --- | --- | --- |
| `repository` | `venture_git_installations.uid` (D5569) | The team's own current record: same company (or project), not revoked, project not deleted, company not archived. A reference, never proof of GitHub access. |
| `landing` | `{ auto_tiers, t2_signers }` | `auto_tiers` holds T0 and T1 only: T2 never lands by itself. `t2_signers` are `{ kind: 'person', uid }` on the team's seats; an agent is refused by the contract and again by the user lookup. |
| `repair` | `{ max_attempts, max_spend_microusd, pushers }` | Within HQ caps; pushers are people on the team or the team's live agents. |
| `path_owners` | `[{ path, owners }]` | A relative pattern of letters, digits and `. _ - / *` (no `..`, `.`, `.git`, empty segment), one entry per path, at least one owner, owners are people. |
| `max_parallel_per_repo` | 1..cap | Separate from the engine's `max_parallel_runs` (#3742), which stays. |
| `compute_budget_microusd` | 0..cap | Compute, separate from the inference budget. |
| `executors` | provider ids | A subset of D5565's `PROVIDERS`. |

Lists are deduplicated and sorted. A PUT names only the fields it changes;
`null` resets one; an empty body or an unknown key is refused. A field that is
`null` reads as `null`, as in D4422. `LANDING_DEFAULTS` is what the enforcer
will apply to an unset field, and it lands, repairs and runs nothing a manager
has not chosen: T0 alone lands by itself, nobody signs T2, repair is off, one
change at a time, no compute, no executor.

### HQ caps

Verified on `main` (7ca13d975b): HQ's AI policy (`ai_agent_policy`, D4162)
holds inference caps only, and no store holds landing caps. Until an HQ
settings task adds one, the caps are constants in the contract:
`repair_max_attempts` 2 (internal Merge Control's own `MAX_ATTEMPTS`,
D5622), `max_parallel_per_repo` 5 (the engine's 1 to 5),
`repair_max_spend_microusd` 50,000,000 and `compute_budget_microusd`
1,000,000,000 (the last two confirmed by the owner, 2026-11-14). The executor list is D5565's
`PROVIDERS`; whether a provider is switched on remains D5565's fail-closed
capability check, not this list.

### Routes and store

`GET`/`PUT /api/teams/:scope/:id/landing` (`routes/team_landing.ts`) mounts
itself before `agent_engine.ts`, so before `team_agents.ts`, whose `*`
middleware would otherwise answer `team_agents_off`. Both answer 404
`team_landing_off` unless `TEAM_LANDING` is `true` and `agentEngineEnabled`.
Gates are the `/engine` pair's: a reader may GET, a manager may PUT (403
`not_manager`), and a caller who cannot read the team gets 404. A refusal is
400 `invalid_landing` with `field`.

Migration `202611132316_5624_agent_landing_settings.sql` adds
`agent_landing_settings` (one row per scope, NULL columns are unset) and
`agent_landing_setting_changes` (actor, version, before and after), which two
triggers keep insert-only. A save is compare-and-swap on `version`: the
settings write and the log row go in one batch, and the log row is written only
when the write changed a row, so a save that lost a race (or sent a stale
`version`) is 409 `landing_changed` and stores nothing.

### The one-month condition

The route ships off. `TEAM_LANDING` is set in production only after internal
Merge Control (D5618, D5620, D5622) has run on this repository for a month,
and only by the owner. The screen (a Landing section in Team › Agents) waits
for a canvas: the issue carries `needs-design`.

### Checks and rollback

`team_landing_5624.test.ts` runs the routes on SQLite: the flag, the gates,
every refusal storing nothing, null reads, one log row per save, a stale
version and a lost race, the insert-only log, and the migration applied twice.
Rollback is leaving the flag off or removing the route; the additive tables
stay once applied.
