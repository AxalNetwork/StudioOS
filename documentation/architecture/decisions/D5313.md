## D5313 — Perks runs in the generic program shell, the pattern for the other eight (#5313)

- **Status:** built 2026-11-11 (#5313). Frontend only: no migration, no new Worker route, no new client method.
- **Number:** D5313 is the issue's number (D4106).
- **Builds on:** D4873 part 4 (the generic shell, PG03, `GenericProgramPage.jsx`, `genericProgramModel.js`, `MODULE_PATHS`), D4808 (the registry-backed page), D953 and D962 (Perks' Overview, How it runs, Queue and Activity), D4873 part 2 (`programs.member_access`, `programs.modules`).
- **Answers:** the owner's option A on #4873 (2026-11-09): the nine built-in program pages move into the generic shell, one task per page. D4873 part 4 kept them bespoke; this is the first move.
- **Canvas:** PG03a on the Programs v2 canvas (`design/incoming/Programs v2 · Boards.dc.html`, drawn from `Programs v2 Page.dc.html` board `PG03`).

### What changed

`/admin/programs/perks` now draws the shell's six core sections, with Perks' own screens where it has them:

| Tab | Address | What it draws |
| --- | --- | --- |
| Overview | `/admin/programs/perks` | Perks' tiles, Top perks, Claims per week and Grant or deduct credits (D962), then the shell's Capability modules |
| Playbook | `/how-it-runs` | the playbook editor (D962), unchanged |
| Availability & grants | `/availability` | the shell's section: the grant badge, whether it can be offered, Manage grants |
| Participation | `/participation` | Claims in the last 12 weeks, from the claims read Overview already makes; Members taking part: "Not recorded" |
| Perk queue (module) | `/queue` | the review queue (D962), unchanged, at `MODULE_PATHS.perks.perk_queue`; the tab carries the count in review |
| History | `/activity` | the activity read (D962), unchanged |
| Settings | `/settings` | the shell's member-access editor (Super Admin) or its value (Admin) |

- **Every address is kept.** The four D953 and D962 gave Perks keep their paths and their `App.jsx` lines. The three new ones are literal routes in `frontend/src/routes/adminProgramsPerks.jsx`, onto the same `ProgramPage`. Until now they fell through to `/admin/programs/:key/…` and drew the registry-backed page; a literal route ranks above `:key`, so every Perks address is one page with one strip.
- **The shell's sections are shared.** Capability modules, Availability & grants, Participation and Settings moved unchanged from `GenericProgramPage.jsx` into `ProgramShellSections.jsx`. The registry-backed page imports them from there, and so does Perks. `OnRegistry` wraps a section that needs the registry read: it draws "Reading…", or "This program could not be read" with Try again, never the section on no data.
- **The registry read is the frame's.** `useProgramDetail('perks')` feeds the header (status, grant, member access), Modules, Availability and Settings, as on the shell. A failed read marks only those sections; Perks' own reads still draw. Modules on a failed read say "Could not be read", never "None yet" (`shellModules`).
- **The header's status is the registry's,** as on the shell, so a paused Perks reads Paused. Before, it was the frontend constant's.
- **Participation is never a 0 that was not measured.** The claims read counts claims and redemptions, so the Claims tile shows them, and a measured zero is "0 · 0 redeemed". It carries no member, so "Members taking part" is "Not recorded" with its reason, whatever the claims say (`perkParticipationTiles`).
- **The strip.** `PAGES.perks.tabs` and `ProgramTabs.jsx`'s `PerksTabs` list the seven tabs in PG03's order and words, each a literal `<Tab to="…">`, so the reachability walk and D953's strip test still read them as doors. The module tab carries `module: 'perk_queue'`; the test holds its path equal to `moduleRows('perks', …)`'s.

### Departures from the canvas

- **Overview keeps Perks' own figures.** PG03a draws a three-row Perk queue preview and an Availability card on Overview. Overview keeps D962's tiles, charts and credits, and adds Capability modules. The queue is one tab away (the tab carries its count, and the header's "Review perk queue" opens it), and Availability is its own section, as D4873 part 4 did for the shell.
- **The header actions.** PG03a draws Export and "Review perk queue". Review perk queue is added (hidden on the queue itself). Export stays D1124's Download (CSV) in the ⋯ menu.
- **No "+ Offers" chip.** PG03a draws "+ Offers" beside "✓ Perk queue". A module arrives with its screen, so nothing here switches one on (D4873 part 4).
- **Participation.** The canvas draws no Participation for Perks. The section shows the claims Overview already reads, and "Not recorded" for members, because no read counts the members who claimed.
- **No five-dimension strip of its own.** The header already draws the five dimensions (D4807), from the registry read.

### Pattern for the other eight

Each of Learning, Referral partners, Investor cohort access, AI-native Venture, Influencers, Mentor cohort access, Refer & Earn and Spin-Out Lab moves the same way, as its own task:

1. **The strip.** In `programsModel.js`, give the program's `PAGES` entry the shell's tabs in PG03's order and words: Overview, Playbook (`/how-it-runs`), Availability & grants (`/availability`), Participation (`/participation`), its module tabs, History (`/activity`), Settings (`/settings`). Keep every path it has today. A tab that is a module carries `module: '<key>'`, and its path must equal `MODULE_PATHS[key][module]`. Write the same tabs as literal `<Tab to="…">` lines in its `ProgramTabs.jsx` strip (D953's test holds the two equal).
2. **The routes.** Leave the routes already in `App.jsx` alone. Register each new core address as a literal route onto the program's own page, in one module under `frontend/src/routes/` (as `adminProgramsPerks.jsx`). Where `MODULE_PATHS` maps a module to `''` (Investor cohorts, Influencer), that module is Overview's content, not a tab.
3. **The sections.** Draw Availability & grants and Settings from `ProgramShellSections.jsx` inside `OnRegistry`, and Capability modules on Overview with `shellModules(key, detail.read)`. Where the page draws in `ProgramFrame`, pass it `status={registryStatus(detail)}` and the page's own `detail`. Refer & Earn and Spin-Out Lab already have a `/settings` of their own: the shell's member-access editor joins that page rather than replacing it.
4. **Participation.** Use the program's own recorded figure where one exists, and say "Not recorded" with its reason for what is not. Never a 0 that was not measured. With no store at all, use the shell's `Participation`.
5. **Its screens.** Its existing screens become Overview content or module tabs, at their existing addresses and with their existing test ids, so the existing tests keep passing. Only the assertions that pin the old strip change.
6. **The tests.** Copy `programs_perks_shell_5313.test.mjs`: the route table, every address and its deep links, the failed registry read, and a mutant for each assertion.
7. **The docs.** Write a decision file, add a sentence to the Admin · Programs canvas row, and list the departures from PG03.
