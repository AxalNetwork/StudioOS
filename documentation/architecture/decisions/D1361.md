## D1361 — The connector API: Axal VC as a Lovable custom connector

- **Status:** built by S21 for S1, 2026-10-28, at the owner's request. The owner chose OAuth in Lovable's form ("I'm using OAuth for now").
- **Migration:** none.
- **Builds on:**
  - D666 and D784: Axal VC's OAuth server and `/mcp`;
  - D841 and D842: member API keys;
  - D846: the read tools and their scopes;
  - D849: limits.
- **Separate from:** #2398 and D1313, the Axal VC → Lovable connection (From Lovable). This is the other direction.

### 1. What it is

A Lovable workspace adds Axal VC as a **custom connector**. Lovable's gateway then calls `https://axal.vc/api/connector/v1/*` with each member's own credential. The API is a small, read-only REST surface over tools Axal VC already serves on `/mcp`, implemented in `cloudflare-worker/src/routes/connector_api.ts`.

| Route | Tool | Scope |
|---|---|---|
| `GET /me` | none: the connection test | any valid credential |
| `GET /companies` | `list_companies` | `validate:read` |
| `GET /companies/:id/validate-context` | `get_validate_context` | `validate:read` |
| `GET /companies/:id/interview-guide?hypothesis=` | `get_interview_guide` | `validate:read` |
| `GET /companies/:id/build-progress` | `get_build_progress` | `build:read`, plus the member's GitHub connection |

- **No second set of rules.** Each data route runs the tool through `callTool`. So the scope, the companies on the grant or key, the member's live ownership of each company, the plan check, the per-grant and per-member limits, the 20-second timeout, metering and the call log all apply exactly as on `/mcp`.
- **An allow-list, not a proxy.** Any other path or method answers `404 not_found`.
- **Read-only.** There is no write, no Raise or investor data, and no admin route.
- **Errors.** Each is `{ error, message, detail }`: `400` for a bad id or filter, `401`, `402` from the AI token ledger, `403` `insufficient_scope` or `refused`, `404`, `429`, `503`, `504`. A null figure means "not recorded", never zero.

The contract is `documentation/operations/AXAL_CONNECTOR_API.openapi.json`.

### 2. Credentials

Two kinds are accepted, both the member's own, and both already used by `/mcp`. A session cookie never authenticates here.

1. **OAuth: the owner's choice for Lovable.**
   - **Tokens** come from Axal VC's own authorization server: `/api/oauth/authorize` and `/api/oauth/token`.
   - **PKCE (S256) is required**, so Lovable's "Use PKCE" must be on.
   - **The consent page** (`/connect/assistant`) is the one Claude and ChatGPT already use. On it the member ticks the companies and approves the scopes.
   - **The connector checks each token** with `unwrapToken`: it must exist, be unexpired, and have a grant that still stands. If the token carries an audience, it must be Axal VC's `/mcp` resource.
   - **The grant's props** are the principal `/mcp` serves.
   - **A refused token** answers `401 invalid_token`.
   - **Needs `MCP_SERVER_ENABLED`**, which is already on in production.
2. **Member API key** (`Authorization: Bearer axk_…`).
   - `authenticateKey`, extracted from D842's `serveWithKey`, now serves both `/mcp` and this API.
   - It covers the flag, the per-IP failure throttle, the hashed secret, revoked and expired keys, "sign out everywhere" and the key's own rate.
   - **Needs `API_KEYS_ENABLED`**, still `"false"` in production. With OAuth chosen, this is optional.

An OAuth grant made for an assistant on `/mcp` can also call this API. That is the same member, the same companies and the same scopes, through a different transport.

### 3. The Lovable OAuth client

Lovable's form says: "Each workspace enters its own OAuth app's client ID and secret when connecting." Its redirect URL is fixed: `https://api.lovable.dev/workspaces/connectors/standard/oauth/callback`.

**Dynamic registration does not fit.** Clients registered through `/api/oauth/register` expire after seven days.

**So a Super Admin mints one non-expiring client** in HQ › Integration keys › Lovable connector, through `routes/admin_connector_clients.ts`:
- `GET /api/admin/connector-clients/lovable` returns the client id and the form's values, never the secret;
- `POST /api/admin/connector-clients/lovable` creates the client and returns the secret once. A second POST replaces the client, and the old one stops working.

The client's only redirect is Lovable's callback.

**The client alone reads nothing.** Every member still signs in, consents and can revoke the grant. That is why the route is behind `requireSuperAdmin` and not the secret-write bar's step-up. The current client's id is kept in `OAUTH_KV` under `connector_client:lovable`.

### 4. Not built, and not claimed

- **No write operation.** A use case and its safeguards come first.
- **No team-shared data.** Lovable's "Shared team data" stays off: a connection is one member's.
- **Not listed in Lovable's public catalogue.** This is a custom connector for one workspace. What Lovable requires for public listing is not documented.
- **No live Lovable connection has been run from this change.** The OAuth flow is tested in-process, end to end.
