## D4833 part 3 — Practice Delivery: a version's summary and stored file (#4833)

- **Status:** built for #5961, 2026-11-15. Part 3 of #4833 (Practice UX 5/6); part 1 is D4833, part 2 is D4833-p2.
- **Canvas:** `design/incoming/Practice v2 Page.dc.html`, PX-06 C: "Change note · required", "Document or URL · required", "Summary · optional"; PX-06 B draws the latest version's document as a file ("📄 Q4-strategy-memo-v3.pdf").
- **Builds on:** D5959 (`version_summary`, apart from the change note `summary`) and D5960 (a version's document is an https link or a stored file; `document` and `file` on each version; the two downloads).
- **Migration:** none. **Worker:** unchanged.

### What the advisor sees

- **Add version** has the canvas's three fields, in its order. The document is a file ("Choose a file", a PDF, JPEG or PNG of at most 10 MB) or an https link, one of the two. The summary is optional and is sent only when written.
- **The rules are the Worker's, said before a byte is sent** (`versionDraft`, `fileRefusal` in `deliveryTrail.js`):
  - no change note, or no document: refused as before (D4712);
  - a link and a file together: refused, as the Worker's 422 `two_documents`;
  - a file over 10 MB, empty, or declared as another type: refused in the Worker's own sentence.
- **A file the Worker still refuses** (its bytes are not a PDF, JPEG or PNG; the plan is full; storage failed) comes back as the Worker's sentence in the dialog. The dialog stays open, and nothing is saved or read back.
- **New work product** takes the same two fields for v1: a file beside the link, and the optional summary.
- **One picker.** Both forms use `FileChoice` (`VersionFile.jsx`). It runs no model, so it is not an AI-rail upload, and `railOptions/advisor.js` does not list it. That list holds only the controls that run a model (D773).
- **The latest version card** shows the summary under the change note when one was recorded, and **nothing** when none was. An optional field the advisor left empty is not "Not recorded". A file shows its name, its size ("2.4 MB") and **Download**.
- **The history** shows each version's summary and file the same way. Its one control is Download; nothing edits a stored summary or file, because a version is never edited (D4712, and D5959's trigger).
- **Send** names a file by its file name: the preview reads "Sends v2 — “note” · file memo-v2.pdf" and the confirmation's Document row "Q4 Strategy Memo v2 · file memo-v2.pdf". The confirmation also shows the summary when there is one. Mark ready accepts a file version.
- **Copy:** "There is no file upload yet. A version’s document is a web link." became "A version’s document is a web link or a stored file, a PDF, JPEG or PNG of at most 10 MB." The Ready half had already changed in part 2.

### What the client sees

The received list (`raise/AdvisorGrantSection.jsx`, `listReceivedDeliverables`) shows a sent version's summary when there is one, and a file version as its name, size and Download, from `GET /api/advisors/received/deliverables/:uid/file`. A download records nothing: opening stays the client's own Mark open.

### Downloads

- **Fetched as a blob** with exactly the headers `request()` sends (`rawRequestHeaders`, D717), then handed to the browser through an object URL.
- **Saved only when** the response is `ok` and the body is not empty. A refusal (the Worker's 502 `file_unreadable`, a 404) or an empty body is an alert with **Retry**, and no file is saved. On the Raise surface the alert's sentence goes through `userFacingRaiseError` (#5070).

### Where the client methods went

`frontend/src/lib/api.js` is a frozen hub (D5615): it takes no new names. The advisor deliverable methods all live there, so the file half is a new module, `frontend/src/lib/api/advisorDeliverableFiles.js` (`advisorDeliverableFilesApi`):

| Method | Route |
|---|---|
| `createWithFile(body, file)` | `POST /api/advisors/me/deliverables`, multipart |
| `addVersionWithFile(id, body, file)` | `POST /api/advisors/me/deliverables/:id/versions`, multipart |
| `downloadVersionFile(id, version)` | `GET /api/advisors/me/deliverables/:id/versions/:version/file` |
| `downloadReceivedFile(uid)` | `GET /api/advisors/received/deliverables/:uid/file` |

A version with a link still goes through the existing JSON methods (`api.createMyAdvisorDeliverable`, `api.addMyAdvisorDeliverableVersion`). They pass `version_summary` like any other field, so `api.js` is not edited.

`scripts/check-api-drift.mjs` reads the two `request()` writes. The two downloads use `fetch` (a binary answer), as `companyDocuments.js` does, so the drift check does not see them; the new test asserts their paths against the Worker's routes.
