## D5569 part 3 — Privileged draft publisher execution and publication receipts (#5569)

This part adds an unmounted executor on top of D5569 part 2's planner. It
can execute a planned branch and draft PR through a broker-owned GitHub
installation token. The platform has no route, consumer, secret binding or
configuration flag wired to this entry point. Production activation still
requires the owner's installation and the #5500/#5501 gates.

### Broker boundary

`executeAgentPublication` receives an already authorized platform scope,
an intent, a staged candidate commit SHA, the enable value and privileged
ports. Only the exact value `on` permits execution. The platform must supply
the current authorization and preflight readers, the separate write App's
signer, a clock and transport. Workspace data cannot provide these ports.

The preflight reader must load current WorkGraph and GitHub evidence.
The WorkIntent must bind tenant, company, project, repository, task, agent,
run, base and changed paths and have an unexpired active state. Its candidate
SHA binds the supplied required-check observations to the exact commit.
The installation comes from the existing scoped D1 lookup and overrides
the identity and approval fields in the supplied observation. Empty allowed
paths continue to permit nothing.

The privileged signer can use `publisherAppJwt`, which signs an RS256 JWT
with a non-extractable SHA-256 private key. The installation API request
names one repository ID and requests only Contents/Pull requests write and
Metadata/Checks read. Tokens stay local to the invocation. The executor
uses a fixed GitHub API origin, rejects redirects, limits each response to
2 MiB and each request to 15 seconds, and returns fixed failure codes.

### Candidate and write checks

Before any repository write the executor reads the live App installation,
checks its App ID and suspension state, and confirms the repository's
numeric identity. The candidate must already exist as a Git object in that
repository, have exactly one parent equal to the approved base, and contain
exactly the declared changed files and operations. Renames and copies
require a new supported contract. The digest of GitHub's immutable
base-to-candidate diff must equal the workspace patch digest.

The executor re-reads the installation and preflight immediately before
writing and independently checks the live base ref. A successful plan can
create only `agent/<task>/<attempt>` with GitHub's create-ref operation,
then a draft PR. It never updates an existing ref. A returned branch or PR
with a different ref, candidate SHA or canonical URL becomes an uncertain
outcome for reconciliation.

The planner now requires `success` for every required candidate check.
Pending, skipped and neutral conclusions cannot authorize a publication.

### Reservation, retries and receipts

Migration `202611190937_5569_agent_publish_requests.sql` adds a metadata-only
publication reservation and audit table. Its uniqueness constraints cover
both logical task and idempotency key within installation and platform
scope. A conditional insert bounds pending/unknown requests to 100 per
tenant. Concurrent deliveries of one task obtain one reservation.

A published receipt records stable agent ID, task and run UUID,
installation, repository and target/head refs, exact base/candidate SHAs,
intent/patch digests, WorkIntent UID, the recorded human approvals and PR
number/URL. The deploy SHA remains null until a subsequent verified release
adapter records it. Credentials, patch bytes and log excerpts are absent.

A replay of the same published intent returns its receipt. A changed
intent or candidate for that task refuses. Read failures can retry after
bounded exponential backoff, at most five total attempts. A 403 permission
refusal requires review. A 429 or secondary-limit 403 carries the provider's
retry time or the existing planner's backoff.

Once a write begins, a timeout, rate limit or lost response leaves
`unknown`. Automatic replay stops, including after a successful PR creation
whose response was lost. A person or later reconciliation adapter must
compare the GitHub ref and PR against the recorded hashes before resolving
that state. An orphaned branch is retained as evidence.

### Integration still required

- A privileged candidate-staging adapter must produce the Git object and
  patch digest without giving the workspace write credentials.
- The server preflight must load authenticated WorkGraph WorkIntents,
  current PR/collision evidence, reviewer/dependency decisions and required
  checks on that exact combined candidate. This part provides the consuming
  interface and validates its binding.
- Register delivery through the existing AgentTaskWorkflow/Queue or
  WorkGraph effect outbox, with scheduling fairness, per-installation
  dispatch rate limits and reconciliation of abandoned reservations.
  The reservation table holds publication receipts. The existing engines
  continue to own task delivery and AI usage.
- Supply owner-approved persisted allowed paths. The registration table
  still has no such column. Choose the activation flag's Env binding and
  whether people or an approved policy mark drafts ready.
- Verify post-publish review, protected merge queue and exact-SHA release
  before reporting an approval or deploy SHA.

### Owner installation and rollback

Create the separate least-permission write App and install it only on
approved venture repositories. Keep it out of ruleset bypass lists.
Register its numeric IDs and canonical repository name through an
owner-authorized path and retain its signing key in the privileged broker.
Test on an isolated repository with recorded allowed paths and a protected
base. Validate duplicate and uncertain-write reconciliation before wiring a
production consumer. The read-only connector retains its own credentials.

Until those dependencies are reviewed, keep the executor unmounted. To
roll back an integrated preview, disable its consumer before removing the
module and retain the receipt rows for reconciliation. Any later activation
must record the chosen flag, path-policy source, reviewed head and owner
approval in a new decision part.

### Verification

The synthetic GitHub transport and real SQLite tests cover draft-only
writes, repository-scoped tokens, credential-free receipts, concurrent
duplicates, changed candidate paths/parents/diff bytes, base movement,
installation revocation, expired/revoked WorkIntents, failed checks,
403/429 and secondary limits, retry bounds, capacity, redirects, oversized
responses and lost writes. The migration applies twice in the fixture.
The App JWT test verifies its RS256 signature, App ID and validity window.
All 33 focused publisher/installation tests pass with zero skips. Mutation
verification caught 19 of 19 injected regressions, including removal of the
task uniqueness constraint and the required-success check.

Provider interfaces were checked against GitHub's
[installation-token API](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app),
[reference creation](https://docs.github.com/en/rest/git/refs#create-a-reference)
and [draft PR creation](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request).

No live App token was minted and no venture ref or PR was created during
these tests.
