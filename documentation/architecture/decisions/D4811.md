### The question

HQ › Contracts mixes eight peer tabs (Agreements, NDAs, Partner deals, Templates, Corporate Governance, Forms, Document types, Closings). Templates, generated agreements and governance records share status styling, so an approved template can read like a signed contract. Rows flag "No signature date" on agreements that are simply awaiting signature. Governance shows "None recorded" where the system knows which record belongs.

### What the canvas decides

The full specification is on the canvas's spec boards. **CT90** has problem → design → benefit for each recommendation. **CT91** has the state system and component inventory. **CT92** has the interaction specifications. **CT93** has the accessibility notes and what must be tested. **CT94** has the implementation notes mapped to `frontend/src/ui/`, with the data fields and permissions. In summary:

**Four workflow tabs:** Agreements · Templates · Corporate Governance · Closings. NDAs and Partner deals become category views inside Agreements; Forms and Document types move to a Library menu.

**Three lifecycles**, each with its own vocabulary and glyphs:
- Templates: Draft → Under legal review → Approved for use → Superseded / Archived.
- Agreements: Prepared → Ready for signature → Sent → Executed / Voided.
- Governance: Draft → Reviewed → Approved → Executed → Archived.

Only executed instruments carry the filled "● Executed" seal. "Approved for use" is a dashed pill, never filled. Restricted and Incomplete are overlays beside the state; while either applies, Generate, Use template and Publish are not rendered, and the API refuses them.

**Rows show semantic state** ("Sent 12 May 2026 · Awaiting signature"). Real linkage gaps get a dashed repair action. Amber warning is reserved for contradictions (marked signed with no execution evidence).

**Corporate Governance:** a group header (Holdings → 100% Management, 100% GP) with linked counts, and per-entity expected records. The six record states are Current, Review required, Missing — expected, Not recorded — add if applicable, Restricted and Incomplete. There is no health score; beneficial-owner detail sits behind a Super Admin control.

**Document workspace:** Overview · Document · Versions · Legal Review · Activity · Related. Legal review is a first-class record bound to a version hash. AI research and counsel approval never share a style.

**Execution evidence** is an explicit choice between a completed StudioOS envelope and an externally signed upload, always bound to an approved immutable version. A draft is rejected inline.

**Related-document warnings** are non-destructive ("4 related documents may require review"); nothing is rewritten automatically.

**Search:** cross-object search across templates, agreements, governance records and reviews, current versions by default. **Cross-border fields** do not default governing law to Delaware. **High-risk actions** are permission-gated, need a reason and typed confirmation, and are audited.

### Data

### Built (part 1)

Part of #4811: the P0s and the agreements-row cleanup (implementation order items 1, 2 and 4). No migration, and no stored value changes.

1. **Restricted and Incomplete, from the data the platform already holds.**
   - Restricted: the template's slug is in `COUNSEL_REVIEW_SLUGS` (`services/templateFormat.ts`, D803), the set of templates with a body counsel has not reviewed. Today that is `subsidiary_licence_agreement`. A slug leaves the set when counsel signs it off.
   - Incomplete: the library row is a stub (`is_stub = 1`) or its body is blank after trimming, the rule the publication SQL, the esign send and the licence instantiation already applied.
   - One predicate, `services/templateSafety.ts` (`templateSafety`, `templateUseRefusal`), answers both. Restricted is checked first. The template reads (`GET /templates/store`, `GET /templates/store/:slug`, `GET /published-templates`, the licence picker) carry its result as `safety`.
2. **The API refuses, with 409.** The code is `template_restricted`, or `template_has_no_body` for Incomplete (the code these routes already answered). Each route:
   - `POST /api/admin/contracts/published-templates/:slug/publish`;
   - `POST /api/admin/contracts/published-templates/publish` (the library publish), which skips a restricted template and removes its earlier publication, as it does a stub's;
   - `POST /api/admin/contracts/published-templates/push`, which withholds a restricted publication from the branches and names it in `withheld`;
   - `POST /api/admin/contracts/envelopes/preview` and `/envelopes/send`, through `preparePublishedContract`, even for a publication recorded before the restriction;
   - `createAndSendEnvelope` (`routes/esign.ts`), for a body it looks up and for one its caller rendered. This covers every envelope send, including `POST /api/esign/send` and the licence contract send;
   - `POST /api/admin/licences/:uid/contract` (instantiate). Nothing is written or superseded.

   Reading, editing, previewing, exporting and withdrawing are not refused, because a template has to be read and edited to be completed or reviewed.
3. **The page does not render what the API refuses.** While either overlay applies, the template editor renders no Publish (Withdraw stays), and New envelope draws a restricted or incomplete publication as a note, not a choice. A banner says "Restricted — Legal review required" with the reason, or "Template incomplete — This document has not yet been completed and cannot be used to generate an agreement."
4. **One lifecycle vocabulary.** `frontend/src/lib/contractLifecycle.js` maps the stored values, drawn by `LifecycleBadge.jsx` on the template cards, the editor, the agreements table and panel, and the governance tab.
   - Templates: archived (`is_active = 0`), Superseded (a version older than the publication), Under legal review (restricted), Approved for use (published, with no overlay), otherwise Draft.
   - Agreements: draft → Prepared, generated → Ready for signature, sent → Sent, signed → Executed, void → Voided.
   - Governance: review reads "In review", not the canvas's "Reviewed": D4563 lets a record in `review` return to draft, so the stored state is a review in progress.

   Only Executed is the filled seal. Approved for use is a dashed outline. Every badge is a glyph (hidden from screen readers) and words.
5. **Agreements rows.**
   - An awaiting row reads "Sent 12 May 2026 · Awaiting signature". A missing signature date is not flagged. A send that was never recorded stays a neutral "Not recorded".
   - A row with no company link reads "Unlinked recipient". There is no repair action, because no agreement-to-company link flow exists yet.
   - The one amber flag is "Marked signed · no execution evidence": signed, with no signature date, signed file, linked envelope or completed esign envelope.

### Built (part 4) — 2026-11-09

Part of #4811: cross-object legal search (board CT-13, interactions CT-92 "Search"). It is read-only. The new route is `GET /api/admin/contracts/search?q=&historical=true` (`cloudflare-worker/src/services/contractSearch.ts`). There is no migration.

1. **One ranked list over three stores:**
   - templates: the library rows, with their history rows as earlier versions;
   - agreements: the Contracts union. A match is checked against the title, recipient, company, template, type and the licence fields;
   - governance records: a record at its latest file, with its earlier files as earlier versions.

   Each result names its object type, its context (category, company or entity), its lifecycle state in its own vocabulary, Restricted and Incomplete for a template, and its version.
2. **Current versions by default.** Earlier versions are counted ("6 historical versions hidden"), and listed only with "Include historical versions", tagged Historical. A superseded template reads Superseded.
3. **Ranking:**
   - an exact title, then a title that starts with the query, then a word that starts with it, then anywhere in the title, then another field;
   - current before historical, then the most recently updated, then title, then the newer version.

   At most 50 results are listed; the total is always stated.
4. **Who:**
   - Governance is HQ's (D4563); a branch Worker searches none of it, and says so.
   - A confidential governance record is filtered in SQL for anyone but the Super Admin, so it is never listed and never counted, not even as a hidden version.
   - A store that fails to read is named in `unreadable` ("Governance records could not be read"), never shown as no match.
5. **The box** (`frontend/src/pages/admin/contracts/ContractSearch.jsx`, rules in `contractSearchModel.js`) sits above the strip on the Contracts desk, so it is reachable from every tab and from Corporate Governance.
   - "/" focuses it, and results follow 250 ms after typing stops. It needs 2 to 200 characters.
   - It is a combobox over a listbox: ↑/↓ move, Enter opens the highlighted or top result, Escape clears. The count and what was left out are read out in a polite live region.
   - A template opens in its editor (`?tab=templates&open=<slug>`, a new `openSlug` on `AdminTemplates`). An agreement opens in the desk's panel; a licence agreement, or one found from the governance address, is found in the list instead. A governance record opens its entity (`?entity=<key>`, part 2).

**Where this departs from the canvas:**
- The canvas's filter row (entity, document type, category, jurisdiction, lifecycle status, review state, version, updated) is not built. Search is by text, with the version toggle. Jurisdiction waits on question A, and review state on question C.
- Legal-review records are not searched; there is no store yet (question C).
- A governance result opens its entity, not the record's panel, because the panel has no address yet.
