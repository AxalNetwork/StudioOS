## D4811 — HQ › Contracts v2: a legal-operations workspace with three lifecycles and safety overlays (#4811)

- **Status:** canvas landed 2026-11-07 (`design/incoming/Contracts v2 Page.dc.html`, `design/incoming/Contracts v2 · Boards.dc.html`, boards CT01 to CT16 and spec boards CT90 to CT94). Not built. The build is a separate task.
- **Builds on:** D480 (the registry hub), D4563 (Corporate Governance, migration 202611062154), the live Contracts tabs.
- **Migration:** possibly, for the expected-record configuration and the legal-review record. See "Open questions".

### The question

HQ › Contracts mixes eight peer tabs (Agreements, NDAs, Partner deals, Templates, Corporate Governance, Forms, Document types, Closings). Templates, generated agreements and governance records share status styling, so an approved template can read like a signed contract. Rows flag "No signature date" on agreements that are simply awaiting signature. Governance shows "None recorded" where the system knows which record belongs.

### What the canvas decides

The full specification is on the canvas's spec boards. **CT90** has problem → design → benefit for each recommendation. **CT91** has the state system and component inventory. **CT92** has the interaction specifications. **CT93** has the accessibility notes and what must be tested. **CT94** has the implementation notes mapped to `frontend/src/ui/`, with the data fields and permissions. In summary:

**Four workflow tabs:** Agreements · Templates · Corporate Governance · Closings. NDAs and Partner deals become category views inside Agreements; Forms and Document types move to a Library menu.

**Three lifecycles**, each with its own vocabulary and glyphs:
- Templates: Draft → Under legal review → Approved for use → Superseded / Archived.
- Agreements: Prepared → Ready for signature → Sent → Executed / Voided.
- Governance: Draft → Reviewed → Approved → Executed → Archived.

Only executed instruments carry the filled "● Executed" seal. "Approved for use" is a dashed pill, never filled. Restricted and Incomplete are overlays beside the state; while either applies, Generate, Use template and Publish are not rendered, and the API refuses them.

**Rows show semantic state** ("Sent 12 May 2026 · Awaiting signature"). Real linkage gaps get a dashed repair action. Amber warning is reserved for contradictions (marked signed with no execution evidence).

**Corporate Governance:** a group header (Holdings → 100% Management, 100% GP) with linked counts, and per-entity expected records. The six record states are Current, Review required, Missing — expected, Not recorded — add if applicable, Restricted and Incomplete. There is no health score; beneficial-owner detail sits behind a Super Admin control.

**Document workspace:** Overview · Document · Versions · Legal Review · Activity · Related. Legal review is a first-class record bound to a version hash. AI research and counsel approval never share a style.

**Execution evidence** is an explicit choice between a completed StudioOS envelope and an externally signed upload, always bound to an approved immutable version. A draft is rejected inline.

**Related-document warnings** are non-destructive ("4 related documents may require review"); nothing is rewritten automatically.

**Search:** cross-object search across templates, agreements, governance records and reviews, current versions by default. **Cross-border fields** do not default governing law to Delaware. **High-risk actions** are permission-gated, need a reason and typed confirmation, and are audited.

### Data

- Governance entities, categories, statuses, confidential flags, versions, envelopes and ownership come from `admin_governance.ts` (D4563). Templates and the registry come from `admin_contracts.ts` and `admin_contract_doc_registry.ts`.
- The expected-record set per entity is new configuration: a map from entity to record type, with a conditional flag.
- The legal-review record (reviewer, type, jurisdiction, version hash, findings, required changes, sources, next review, decision, decided-by role) has no store today.

### Built (part 1)

Part of #4811: the P0s and the agreements-row cleanup (implementation order items 1, 2 and 4). No migration, and no stored value changes.

1. **Restricted and Incomplete, from the data the platform already holds.**
   - Restricted: the template's slug is in `COUNSEL_REVIEW_SLUGS` (`services/templateFormat.ts`, D803), the set of templates with a body counsel has not reviewed. Today that is `subsidiary_licence_agreement`. A slug leaves the set when counsel signs it off.
   - Incomplete: the library row is a stub (`is_stub = 1`) or its body is blank after trimming, the rule the publication SQL, the esign send and the licence instantiation already applied.
   - One predicate, `services/templateSafety.ts` (`templateSafety`, `templateUseRefusal`), answers both. Restricted is checked first. The template reads (`GET /templates/store`, `GET /templates/store/:slug`, `GET /published-templates`, the licence picker) carry its result as `safety`.
2. **The API refuses, with 409.** The code is `template_restricted`, or `template_has_no_body` for Incomplete (the code these routes already answered). Each route:
   - `POST /api/admin/contracts/published-templates/:slug/publish`;
   - `POST /api/admin/contracts/published-templates/publish` (the library publish), which skips a restricted template and removes its earlier publication, as it does a stub's;
   - `POST /api/admin/contracts/published-templates/push`, which withholds a restricted publication from the branches and names it in `withheld`;
   - `POST /api/admin/contracts/envelopes/preview` and `/envelopes/send`, through `preparePublishedContract`, even for a publication recorded before the restriction;
   - `createAndSendEnvelope` (`routes/esign.ts`), for a body it looks up and for one its caller rendered. This covers every envelope send, including `POST /api/esign/send` and the licence contract send;
   - `POST /api/admin/licences/:uid/contract` (instantiate). Nothing is written or superseded.

   Reading, editing, previewing, exporting and withdrawing are not refused, because a template has to be read and edited to be completed or reviewed.
3. **The page does not render what the API refuses.** While either overlay applies, the template editor renders no Publish (Withdraw stays), and New envelope draws a restricted or incomplete publication as a note, not a choice. A banner says "Restricted — Legal review required" with the reason, or "Template incomplete — This document has not yet been completed and cannot be used to generate an agreement."
4. **One lifecycle vocabulary.** `frontend/src/lib/contractLifecycle.js` maps the stored values, drawn by `LifecycleBadge.jsx` on the template cards, the editor, the agreements table and panel, and the governance tab.
   - Templates: archived (`is_active = 0`), Superseded (a version older than the publication), Under legal review (restricted), Approved for use (published, with no overlay), otherwise Draft.
   - Agreements: draft → Prepared, generated → Ready for signature, sent → Sent, signed → Executed, void → Voided.
   - Governance: review reads "In review", not the canvas's "Reviewed": D4563 lets a record in `review` return to draft, so the stored state is a review in progress.

   Only Executed is the filled seal. Approved for use is a dashed outline. Every badge is a glyph (hidden from screen readers) and words.
5. **Agreements rows.**
   - An awaiting row reads "Sent 12 May 2026 · Awaiting signature". A missing signature date is not flagged. A send that was never recorded stays a neutral "Not recorded".
   - A row with no company link reads "Unlinked recipient". There is no repair action, because no agreement-to-company link flow exists yet.
   - The one amber flag is "Marked signed · no execution evidence": signed, with no signature date, signed file, linked envelope or completed esign envelope.

### Built (part 2) — 2026-11-08

Part of #4811: the Corporate Governance attention view (implementation order item 3; boards CT-03 to CT-06, phone rows after CT-14). Read-only apart from the existing D4563 writes. No migration and no new route: `GET /api/admin/governance` gains `attention` per entity and `group`, so no frontend API method is added.

1. **Expected records** (`cloudflare-worker/src/services/governanceAttention.ts`, `EXPECTED_RECORDS`). Each entity expects one record per D4563 category, under its own name:
   - Holdings: Operating Agreement, Certificate of Formation, Member Register, Written Consents, Signing authority.
   - Management: Sole-Member Operating Agreement, Certificate of Formation, Member Register (conditional), Sole-Member Consents, Delegation of Authority.
   - GP: GP LLC Operating Agreement, Certificate of Formation, Member Register (conditional), Parent Member Consent and GP resolutions, Authorized signatories.

   The member register is conditional for the two single-member LLCs, so its absence reads "Not recorded — add if applicable"; every other absence reads "Missing — expected".
2. **Record states, computed on the server** from the category's documents that are not archived: none → Missing / Not recorded; none this viewer may open → Restricted; one in review, or a draft with a file → Review required; one with no file → Incomplete; otherwise one approved or executed → Current. The record names the document that needs attention, so "Open review" opens the draft or review, not the executed copy beside it.
3. **Facts per entity:** latest executed (or "None recorded as executed", or "None you can open" when confidential documents exist), last review, outstanding issue (the first missing record, else the first incomplete one), next required action (add, upload or finish the review). **Last review is "Not recorded"** with its reason: there is no legal-review store yet (question C). No score anywhere.
4. **Drillable counts.** The group header's cells (Legal entities, Need legal review, Missing — expected, Restricted, and Incomplete when any) link to `/admin/contracts/governance?records=<state>`, which lists the records behind the count across the entities. An entity's page is `?entity=<key>`, with the breadcrumb, the four facts, the expected-records table and that entity's existing document collection. Query parameters, not new paths, so the route map's shell routes are unchanged.
5. **The group structure is not hard-coded.** It is read from the Super Admin's ownership rows (`governance_entity_profiles`, D4563) whose holder is another Axal entity's legal name, compared trimmed and case-insensitively. Only those intercompany links (parent, child, percent) are returned; a row naming any other holder never leaves the Worker. A percent not entered reads "percent not recorded", never 100% or 0%. With no such row, the chart says Not recorded and how it gets recorded.
6. **Existing flows stay.** The three entity collections, the document panel, the new-document panel (now pre-filled with the entity and the record's category when opened from a record) and the ownership panel are unchanged. An empty category in a collection now says what the system knows ("Missing — expected.", "Not recorded — add if applicable.", "Restricted: only the Super Admin can open it.") instead of "None recorded.". The ownership button reads "🔒 View restricted ownership details", as the canvas words it, and the chart refreshes when its panel closes.
7. **Phones.** Below `md` the entities and expected-records tables are lists of structured rows with 44px controls, never a sideways scroll.

**Where this departs from the canvas, and why:**
- **Seven record types per entity on the canvas, five here.** IP ownership documents, ownership records, manager appointments, compliance records, intercompany agreements, fund-formation approvals and fund-governance records have no D4563 category. Adding one rebuilds the `category` CHECK of `governance_documents`, a schema change kept for a later part. The canvas's "Ownership records" row is the Super Admin's ownership panel, reached from the header.
- **"Request legal review" is not rendered.** It needs the legal-review record (question C). A record's own review still moves through the D4563 statuses in its panel.
- **"View restricted ownership details" opens the existing ownership panel** without a re-authentication step; the Worker already refuses it to anyone but the Super Admin. Re-authentication belongs with the high-risk dialog (CT-16), a later part.
- **Formation jurisdiction and dates** in the entity subtitle are not drawn: they are question A, and the platform records neither.
- **Two widenings of D4563, confirmed by the owner on 2026-11-09 (both kept):** (a) an admin who is not the Super Admin now learns *which category* holds a confidential record (it reads Restricted), where D4563 told them only how many confidential documents an entity has. Nothing else of the record is returned: no title, date, version or count. Without this, a confidential record would read "Missing — expected", which is false. (b) The intercompany ownership links, which D4563 kept Super Admin only, are shown to HQ admins; beneficial owners are not. The issue asks for the Holdings → 100% structure in the general view.

**Tests:** `cloudflare-worker/test/governance_attention_4811.test.ts` (6) and `frontend/test/governance_attention_4811.test.mjs` (6); one line of `governance_tab_d4563.test.mjs` follows the ownership button's new words. Fourteen mutations of the new code were each caught.

**Still not done:** the legal-review record and counsel role (C), jurisdictions and cross-border fields (A), the four-tab IA and Closings (B), the new governance categories, the document workspace, execution evidence, search, the Agreements metric strip, the quick panel, the high-risk dialog and the "Unlinked recipient" repair action.

### Built (part 3) — 2026-11-09

Part of #4811: the Agreements metric strip (board CT-01, implementation order "metrics"). It is read-only. There is no migration and no new route: `GET /api/admin/contracts/stats` gains `attention`, and `GET /api/admin/contracts` gains `?attention=`.

1. **Six cells, in the canvas's order** (`frontend/src/pages/admin/contracts/MetricStrip.jsx`, rules in `contractMetrics.js`). They replace the desk's five counters (Total, Awaiting signature, Signed, Average days to sign, Signed in the last 30 days); the canvas's strip has no total and no average.
   - **Awaiting signature:** sent or generated. Opens `status=awaiting_signature`.
   - **Executed:** signed, with this year and this month by the recorded signature date. A signed row with no date counts in the total and is named ("2 with no signature date"), never put in a period. Opens `status=signed`.
   - **Stalled / overdue:** awaiting, with a recorded send more than 30 days ago. A send that was never recorded is not judged either way, and the cell says how many there are. Opens `attention=stalled`.
   - **Legal review required:** the restricted templates (counsel has not reviewed them, D803) plus the governance records in review.
   - **Restricted:** the same restricted templates plus the confidential governance records that are not archived. A restricted template is in both cells, because it is both under review and blocked.

     Both of these cells open the Templates tab, and their governance part links to `/admin/contracts/governance?records=…` (part 2's drill-down).
   - **Data repair required:** a row marked signed with no execution evidence (part 1's contradiction rule, now also in the Worker), or a live row whose recipient is not linked to a company. Opens `attention=repair`.
2. **One rule for the count and the list** (`cloudflare-worker/src/services/contractAttention.ts`). The strip counts the rows the page lists (`recorded=true`) with the same predicate `?attention=` filters by. A test checks that every count equals the total of the list it opens. An unknown filter value is refused (400), never ignored.
3. **Unknown is not zero.**
   - Governance is HQ's (D4563). On a branch Worker its part reads "governance is kept at HQ" and is not added in.
   - A failed governance or template read is `unreadable` and draws "Unreadable", never 0.
   - A stats answer without `attention` draws a sentence that says so, not six zeros.
4. **The list names its filter.** "Showing: Stalled: sent over 30 days ago", with "Show all agreements" to clear it.

**Where this departs from the canvas:**
- The canvas's three list cards under the strip (Stalled and awaiting signature, Data repair required, Legal review required) and the governance summary line are not built. Each cell opens the full list instead.
- The repair cell has no repair action yet: there is still no link-recipient or bind-to-version flow.
- The canvas reserves "Signed" vs "Executed" for the open part 1 question. The strip says Executed; the list's status chip still says Signed.

In `contracts_desk_d647.test.mjs`, the count-click test now presses strip cells, and the missing-average assertion became the strip's own "not returned" sentence. ### Built (part 4) — 2026-11-09

Part of #4811: cross-object legal search (board CT-13, interactions CT-92 "Search"). It is read-only. The new route is `GET /api/admin/contracts/search?q=&historical=true` (`cloudflare-worker/src/services/contractSearch.ts`). There is no migration.

1. **One ranked list over three stores:**
   - templates: the library rows, with their history rows as earlier versions;
   - agreements: the Contracts union. A match is checked against the title, recipient, company, template, type and the licence fields;
   - governance records: a record at its latest file, with its earlier files as earlier versions.

   Each result names its object type, its context (category, company or entity), its lifecycle state in its own vocabulary, Restricted and Incomplete for a template, and its version.
2. **Current versions by default.** Earlier versions are counted ("6 historical versions hidden"), and listed only with "Include historical versions", tagged Historical. A superseded template reads Superseded.
3. **Ranking:**
   - an exact title, then a title that starts with the query, then a word that starts with it, then anywhere in the title, then another field;
   - current before historical, then the most recently updated, then title, then the newer version.

   At most 50 results are listed; the total is always stated.
4. **Who:**
   - Governance is HQ's (D4563); a branch Worker searches none of it, and says so.
   - A confidential governance record is filtered in SQL for anyone but the Super Admin, so it is never listed and never counted, not even as a hidden version.
   - A store that fails to read is named in `unreadable` ("Governance records could not be read"), never shown as no match.
5. **The box** (`frontend/src/pages/admin/contracts/ContractSearch.jsx`, rules in `contractSearchModel.js`) sits above the strip on the Contracts desk, so it is reachable from every tab and from Corporate Governance.
   - "/" focuses it, and results follow 250 ms after typing stops. It needs 2 to 200 characters.
   - It is a combobox over a listbox: ↑/↓ move, Enter opens the highlighted or top result, Escape clears. The count and what was left out are read out in a polite live region.
   - A template opens in its editor (`?tab=templates&open=<slug>`, a new `openSlug` on `AdminTemplates`). An agreement opens in the desk's panel; a licence agreement, or one found from the governance address, is found in the list instead. A governance record opens its entity (`?entity=<key>`, part 2).

**Where this departs from the canvas:**
- The canvas's filter row (entity, document type, category, jurisdiction, lifecycle status, review state, version, updated) is not built. Search is by text, with the version toggle. Jurisdiction waits on question A, and review state on question C.
- Legal-review records are not searched; there is no store yet (question C).
- A governance result opens its entity, not the record's panel, because the panel has no address yet.

**Tests:** `cloudflare-worker/test/contracts_search_4811.test.ts` (5) and `frontend/test/contracts_search_4811.test.mjs` (3). Sixteen mutations were checked. Two survived at first: the current-before-historical order, and the 250 ms pause. Each got its own assertion, and both are now caught.
