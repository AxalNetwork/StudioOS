### 1. Renewals (KYC9), at `/admin/kyc/renewals`

The tab reads `GET /api/kyc/admin/renewals` and draws:

- **Four tiles:**
  - expiring in 30 days, with the next date;
  - expired;
  - re-checks asked and not done, with the oldest ask;
  - screened over 12 months ago, with those never screened counted apart.
  - **A count the read did not return** is "Not recorded" with the read's own reason (`recorded: false`), never 0. A 0 the Worker counted is drawn as 0.
- **The month chart:** checks expiring per month over the next 12 months, people and businesses stacked. Its lead names the busiest month or months and how many checks fall this month; a year with none says so. A screen-reader table carries the same numbers.
- **The chips:** Expire in 30 days, Expired and All, each with its count. **All is the default**, which reads "expired first, then the soonest", the Worker's order. The canvas's "Re-checks asked" chip is not drawn: the read has no filter for it, so it is a tile only.
- **Search** by name.
- **The table:** who, kind, what expires, the date and how far off, the member warnings sent at 30, 14 and 7 days, and the status.
  - A warning not sent is drawn dashed.
  - A person's name opens their case. A business has no case link until part 6.
  - A business reads Approved or Expired from its obligation. A person reads their KYC status in the canvas's words, with "Re-check asked" when one is open.
- **The pager.**

**A failed read** is "The renewals could not be read. This is not a sign that there are none.", with Try again. The periods card is its own read and still draws: one failed block never blanks the page.

### 2. How long a check lasts (KYC17c)

The card beside the chart reads `GET /api/kyc/admin/periods`.

- **Each row:** the check's period, and whether it is the default or who set it and when. Accreditation adds the Worker's sentence that its period is kept and not used yet.
- **Who can change them:** only when the Worker answers `can_change` (a Super Admin at HQ) does the card offer Change…. It then turns into whole-month fields (1 to 120), and Save… opens the dialog.
  - **The dialog** lists each change ("Accreditation evidence: 12 months → 18 months.") and says, as the canvas does: "New periods apply to checks approved from today. Existing dates do not move."
  - **Only changed values are sent** (`PUT /api/kyc/admin/periods`). The Worker asks for the authenticator code when the last check has lapsed, and the dialog says so beforehand.
  - **Anyone else** reads "HQ sets these periods."
- **The canvas's sentence "Every studio uses these periods" is not drawn**, because D1232 §1 says a branch keeps the defaults until HQ's setting reaches it. The dialog says that instead.
- **The canvas's fourth row**, sanctions screening every 12 months, is D1230's and is not in this read, so it is not drawn.

### 3. Audit (KYC10), at `/admin/kyc/audit`

The tab reads `GET /api/kyc/admin/audit`.

- **The window:** the last 7 or 30 days (30 is the default), the last 90 days or the last 12 months, each ending today.
- **The chart:** looks and decisions per day. A window over two months is drawn a week per column, so a year is not 365 slivers. Every day the Worker returns was counted, so a 0 there is a measured 0. Its lead gives the window's totals and today's so far. Assignments and notes are listed but counted as neither, and the chart says so.
- **Filters:**
  - by action, one option per audited action. The two actions that share "Opened a case" are told apart as "the record" and "its history".
  - by admin;
  - by case, chosen from a row's "Only this case" and cleared from its chip.
- **Search,** and a table of when, admin, action, case (opening the person's case) and detail, newest first, with the pager and "HQ can see this record too." (D1232 §5's feed).
- **Names and actions only:** the page draws what the Worker returns, which never holds a reason's text or a shown value.
- **A failed read** is Unreadable with Try again, never an empty record.

### 4. The export is HQ's (KYC17d, KYC14b)

- **Who sees Export…:** a Super Admin at HQ (`is_super_admin` from `/me`, and not a branch). The Worker's `requireSuperAdmin` is still what decides.
- **Anyone else** reads "Only a Super Admin can export the audit record.", never a disabled button.
- **The dialog** takes From and To (the current window by default) and a required reason of 10 to 500 characters. It says "This deployment's record only. Format: CSV." and "The file holds names and actions, never documents or shown values. The export is recorded."
- **The Worker records the export before it makes the file.** The page hands the CSV it returns to the browser as a blob, never a new tab.
- **If the browser does not take the file,** the bar says the export is recorded and the file was not taken. It is never reported as a refused export.
- **A refusal** (for example "could not be recorded, so it was not made") is said in the dialog, which stays open.
- **The canvas's "Every studio / One studio" choice is not drawn.** The Worker exports this deployment's record only (D1232 §4).
