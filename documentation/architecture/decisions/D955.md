## D955 — Programs part 2: program proposals, HQ's decision on each, and New program (migration 561)

- **Status:** built by S12 for #2788 (part 2 of #2371), 2026-10-24. The owner moved the task to S12 from S11.
- **Basis:** `origin/main` at `fd02f60e59`, which carries part 1 (D954, #2840).
- **Canvas:** PG14, PG15a, PG19b, and PG1's and PG2's proposal lists, from the owner's "Programs" canvas (`design/incoming/Programs Page.dc.html`).
- **Map:** `documentation/audits/PROGRAMS_MAP_2026-10-24.md` §1.4 and §4.
- **Scope:** Worker only. Part 11 (#2797) draws it and adds the clients.

Worker paths are relative to `cloudflare-worker/src/`.

### 1. The store: migration 561

- **`program_proposals`:** one row per proposal.
  - Its sender's studio, `licence_uid`, read from `licence_admins` as `routes/licence_requests.ts` reads it. It is NULL ("HQ-held") for an admin bound to no licence.
  - Its status: `draft`, `sent`, `approved`, `sent_back` or `declined` (dc:325).
  - PG14's four steps.
  - The decision.

  In a draft every field may be NULL, which reads "Not set".
- **List fields are JSON:** `who` (the canvas's six audience words), `rewards` (None, Credits, Cash, Equity; None stands alone), `template_keys`, and `tools` (the seven switches, stored as declarations; nothing attaches a tool to a program yet).
- **`programs.licence_uid`** is NULL for a program every studio sees. It holds a licence's uid for one approved for that studio only.

A proposal's status and a program's stay apart. An approval writes a registry row whose status is `proposed`, HQ's draft (map §3).

### 2. Routes: `routes/admin_program_proposals.ts`, at `/api/admin/programs/proposals`

The router is mounted before `/api/admin/programs`, whose `/:key` would otherwise answer `proposals`.

| Route | Who | What |
| --- | --- | --- |
| `POST /` | `requireAdmin` | starts a draft for the caller's studio |
| `PATCH /:uid` | `requireAdmin` | saves any fields; answers `updated_at` ("Draft saved") |
| `POST /:uid/send` | `requireAdmin` | Send to HQ (§3) |
| `GET /mine?q=&status=&sort=&page=` | `requireAdmin` | Your proposals: name, `sent_at`, status, HQ's note, an exact `total` |
| `GET /?q=&status=&licence=&sort=&page=` | `requireSuperAdmin` | HQ's queue: every studio's proposals but drafts, oldest first, with the studio and `counts` by status (`counts.sent` is the tab's count) |
| `GET /:uid` | `requireAdmin` | one proposal: the studio's own, or for a Super Admin any that is not a draft |
| `POST /:uid/decision` | `requireSuperAdmin` | `{ outcome, note }` (§4) |

**A proposal belongs to its studio.**
- The licence's admins share it. An admin with no licence reads only their own.
- Anyone else gets 404 `unknown_proposal`. That includes a Super Admin asking for a draft.

**The rules on every write:**
- Only a `draft` or `sent_back` proposal changes; any other is 409 `not_editable`.
- A value outside its list, or over its length, is 400 `bad_<field>`.
- A template slug that is not an active contracts-library template is 400 `unknown_template`, the check part 1's playbook uses.

**Searches** match the name with `%`, `_` and `\` taken literally (`ESCAPE '\'`). Every query is fixed text with bound values: no SQL is interpolated.

### 3. Send to HQ, and OD-PROP

**What Send needs:** a name, a purpose, who, a group and a join method. Otherwise it is 400 `incomplete`, with `missing`.

**Who may send waits on OD-PROP** (D953 §5: who may send a proposal while no studio is deployed).
- `sendPolicy` in `services/programProposals.ts` is the one place that answers it.
- **Until the owner answers, nobody may send.** Send answers 403 `proposals_closed` with "HQ has not opened program proposals yet, so this proposal cannot be sent. It stays saved as a draft."
- Drafts save as usual. HQ's side is tested with seeded `sent` rows, and the send itself with the policy opened in the test.

A send that lands moves the proposal to `sent`, sets `sent_at`, and is audited as `program.proposal.send`.

### 4. The Super Admin's decision (PG15a)

Only a `sent` proposal is decided; any other is 409 `not_waiting`. The decision's UPDATE is guarded on `sent`, so a second decision racing the first changes nothing.

**The note:**
- Required for Send back and Decline: 400 `note_required`.
- At most 2,000 characters: 400 `note_too_long`.
- The studio reads it under Your proposals.

**The four outcomes:**
- **Approve for the catalogue** writes a registry row from the proposal, with status `proposed` and every studio reading it:
  - its key comes from the name (`keyFromName`), and a taken key is 409 `program_key_taken`;
  - its group, purpose, who ("Founders, operating partners") and join method;
  - an unpublished playbook draft of PG14's Review sections (Purpose, Who it is for, How people join, Rewards, Tools; dc:467). The proposal's contract templates sit on Rewards.

  Its grant state is part 3's (#2789).
- **Approve for this studio only** writes the same row with the studio's `licence_uid`.
  - Only that studio and HQ read it. Part 1's catalogue, `/:key` and `/:key/activity` reads are filtered (`ProgramReader`), and to another studio the key is 404 `unknown_program`.
  - A proposal with no studio is 409 `no_studio`.
  - The draft grant PG15a's foot names is part 3's.
- **Send back** returns it as `sent_back`, editable and sendable again.
- **Decline** is final.

**The audit and the activity.** Each decision is audited as `program.proposal.decide` with its outcome, note and program key. The decision and New program's `program.registry.create` are in `services/programActivity.ts`'s registry list, so a program's Activity lists them. A send back or decline names no program and is read in the admin audit.

### 5. New program (PG2's header)

`POST /api/admin/programs`, `requireSuperAdmin`, takes Basics and How it runs. Terms and Tools are a proposal's, and are 400 `bad_field`.
- **The row:** status `proposed`, for every studio, at the end of the catalogue.
- **The draft:** the same five sections, unpublished.
  - "How people join" comes from How it runs.
  - "Who it is for" comes from who and eligibility.
  - The rest are unset.

  Part 1's playbook routes edit and publish it.
- **The key:** `proposals` and `propose` are refused for any program, from an approval too, because they are sub-paths (D953 §1). So is a taken key: 409 `program_key_taken`.
- **The audit:** `program.registry.create`.

### 6. Changes to part 1 (D954)

- **Any key.** A key is any lower-case slug (`PROGRAM_KEY_RE`), not only the nine, and `programByKey` reads it from the registry.
- **A fallback in the activity read.** A program with no actions of its own reads an empty list rather than failing.
- **D954's test** applies 561 after 560, as the deploy does, because every registry read now selects `licence_uid`.
