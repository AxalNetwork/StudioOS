**What the audit found:**

1. **No feed works only on the token path.** D713's and D752's uses read either way, through `bankReaderFor`. Grow and Raise read only through the sign-in: they need invoices, customers, treasury, statements, SAFEs and the cashflow summary, which a token cannot read. But **nothing tested the D713 and D752 uses on a sign-in**: every one of their tests used a token.
2. **Disconnected and token states were silent:**
   - Raise showed **no Mercury part at all** to a founder with no connection.
   - With a token, Raise said "Nothing from Mercury yet. Sync to read it", and the Sync then refused.
   - Grow said "the founder has not synced" in every case.
   - Neither linked to `/account/connectors/mercury`.
3. **No member path reads an Axal entity's Mercury.** No Grow or Raise file names D710's tables (`mercury_entity_connections`, `mercury_accounts`, `mercury_transactions`, `mercury_balance_snapshots`, `mercury_matches`, `mercury_sync_runs`). None imports `store.ts`, `sync.ts`, `match.ts`, `notOurs.ts` or `access.ts`. `namesAxalEntity` compares a counterparty with the entities' names, which are constants: a wire from an Axal entity reads as financing, never as income.

   The only member-side read of an entity table is D713's decision 3, in `integrations/providers/mercury.ts`, at connect time. It looks up the new connection's account ids in `mercury_accounts` only to refuse an Axal organization, and returns nothing. That is the connect path, which belongs to C1 and C3.
4. **Raise's landings were not held to the declaration.** Grow's were: `mercury_grow_d840.test.ts` checks that each Grow module lands only the kinds `GROW_FEED_KINDS` lists. Nothing held each feed's declared tools to the tools its sync calls.

### 2. The fixes

- **`services/mercury/memberConnection.ts`** (new) gives the founder's connection state from their one `integrations` row. No credential is decrypted and no Mercury request is made:
  - `connected`: signed in through MCP;
  - `sign_in_required`: an active pasted token;
  - `reconnect`: a sign-in Mercury rejected, `status = 'error'`;
  - `not_connected`.

  Every state but `connected` carries "Connect Mercury", `/account/connectors/mercury` and one sentence.
- **Grow** (`growFromMercury`). The part carries the venture founder's `connection`.
  - With nothing recorded and no usable sign-in, the part is that state: its sentence, with no figure.
  - Figures already landed stay, with the connection beside them.
  - Only the founder gets the link and Sync. A teammate is told it is the founder's move (`FOUNDER_MERCURY_SENTENCES`), because the bank account is not theirs.
  - Someone outside the company still reads only `team_only`.
- **Raise** (`routes/cycle_raise.ts`). The founder's module read always carries a Mercury part:
  - with no connection, the connection's state and sentence;
  - with a token, the stored facts and proposals with the connection beside them.

  The owner checks (`mercuryFounderOnly`: the founder, in their own company, outside a support session) are split from the connection lookup. Every route still refuses as before.
- **The screens.** `GrowFromMercury.jsx` and `MercuryRaiseFeed.jsx` draw `ConnectMercury.jsx`: the sentence and a link that opens only a `/account/connectors/` path. Raise offers no Sync without a usable sign-in.
- **Unknown is NULL.** A connect part carries no figure key at all, never a zero.

### 3. One declaration

`mercury_grow_raise_mcp_d882.test.ts` holds the declaration to the code. Raise's and Grow's landings are read from real syncs against the fake MCP server; it does not read constants:

- A full Raise sync, with every Accept, lands exactly in the `raise_*` modules, and the sync calls exactly their tools. `RAISE_PART_FOR` names the same modules.
- A Grow sync calls exactly the `grow_*` tools. `GROW_FEED_SLUGS` and `GROW_FEED_KINDS` name the `grow_*` modules.
- **A founder's connector page** declares `PERSONAL_MERCURY.founder.feeds`, which `connectorFeeds('mercury', 'founder')` returns. It equals the modules the Grow and Raise syncs land in, plus Revenue and traction for D713's import. A module declared but not fed, or fed but not declared, fails the test.

**The catalogue row.** `CONNECTOR_METADATA.mercury.feeds` and `used_by` are C1's (D879), which removes the entity variant. When it names the Grow and Raise modules, it should be derived from, or asserted against, `mercuryFedModules('founder')`, the same list this test holds. This task does not edit that row, so the two PRs do not collide.
