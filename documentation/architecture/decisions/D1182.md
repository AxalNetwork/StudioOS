## D1182 — Bank-account history read and recorder names

- Issue #3111, S20, s31; part 1 of #2389. Based on main `826ed19703`.
- No migration, new write endpoint, Mercury provider call, credential/store import,
  production D1 access or deployment. The existing registry and audit stores suffice.

`GET /api/admin/bank-accounts/history` uses the existing HQ `requireSuperAdmin`
gate. It writes `bank_accounts_history_read` before reading either history store;
failed or zero-row auditing returns 503. This read action is outside the
`bank_account_` source prefix, so reads do not pollute their own history.

The read unions every reveal ledger row (including an LP's capital-call-line
reveal) with the `bank_account_*` and three Mercury connection actions. Audit
mirrors of an admin reveal remain separate audit records: the `source` field
identifies `reveal_ledger` versus `admin_audit`, with unique prefixed ids. There
is no inferred deduplication, invented change detail or claim of provider activity
beyond the stored audit action. Mercury is never contacted. A literal-prefix
`GLOB` uses the existing `idx_admin_audit_action_ts` index alongside exact
Mercury actions, avoiding unrelated platform audit rows without a migration.

History selects only registry uid, label, entity and last four; actor names;
recorded timestamps; and the ledger context/reference. It never selects bank
ciphertext, decrypts, returns raw audit JSON, addresses, routing numbers, tokens
or arbitrary JSON fields. Free text redacts four-or-more digits, including
separator-formatted numbers. A capital-call-line reference is an explicitly
typed positive numeric id and is preserved. Account numbers are only `••••4821`.
Digit redaction is intentionally conservative, including years in labels/names;
search still matches the stored metadata. Unknown names/accounts stay null. Names and mutable account labels are resolved
at read time; the stores do not hold historical display-name snapshots.

Filters: `kind=reveal|bank_account|mercury`, the four `entity` keys, numeric
`actor` or `actor:<id>`, and literal `q` using D1 case folding over actor/account labels,
last four, entity, action and context. It never searches raw audit JSON or reveal
reasons. `range=all|7d|30d|90d` or `from`/`to` UTC calendar dates; the end date is
inclusive. Invalid filters are 400. Unreadable audit details retain the stored
action, actor and time with null account/entity details and `detail_unreadable: true`.
Missing metadata stays null with the flag false. Failed source reads are 503
with fixed error text, never successful empty history.

Pages default to 25, at most 100, with positive `page`. Returned `snapshot`
pins the two append-only source id ceilings and relative-range clock; reuse it on subsequent pages to
exclude later inserts, even backdated ones. Count and page share one filtered
SQL read and timestamp ordering includes milliseconds, then source/id ties.
This is insertion stability, not a frozen version of mutable names/labels.
A genuinely empty history returns recorded total 0 and an empty array.

Every registry account returned by the Super Admin console list, writes and
admin reveal includes nullable `recorded_by_name`, resolved through the stored
recorder relationship. It never returns `recorded_by`, substitutes an id/email,
or guesses a deleted user's name. Shared masked readers, LP payment instructions
and frozen fund notices keep their original projection without recorder names.
The existing reveal gate and 30-second UI
policy are unchanged. The existing client module gains the GET method; D527's
existing re-export remains. The BNK5 screen belongs to the later UI part.
