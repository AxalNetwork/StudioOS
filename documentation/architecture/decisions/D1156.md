## D1156 — Dated program figures from each studio to HQ

#3061, part of #2376. Migration 601 adds `program_usage_reports`, one latest
row per licence and program, with count columns, the UTC month (`period`),
branch assertion time (`reported_at`) and HQ receipt time (`received_at`). No
member name, address, id, referral text, redemption code or payment figure is
sent or stored in this report. The existing source ledgers remain canonical.

### Report and identity

The branch's `pushProgramUsage` assembles aggregates from its own D1. It runs
at 05:15 UTC daily, on branches only, and on demand through
`POST /api/licence/mine/programs/report`. That route requires a signed-in
branch Admin, takes no caller-supplied figures and records the Admin's action.
The on-demand helper uses the existing RATE_LIMITS binding, fails closed when
that store cannot be read/written, and limits sends to one per five minutes.
There is no new binding, secret, external provider or AI call.

`BranchEntrypoint.reportProgramUsage(code, secret, period, reportedAt, figures)`
is a thin delegation to the tested service. HQ authenticates the branch's own
RPC secret using `authenticateBranch` before any report write. Its deployment
record supplies the licence uid: the caller cannot select another studio.
Only currently granted or paused programs in that licence are accepted.
Missing keys, extra fields, duplicate programs, invalid/negative/fractional or
unsafe counts, invalid periods/stamps and stamps over five minutes ahead of
HQ are refused. Errors and scheduled logs contain fixed outcomes and counts,
never payloads or exception text. HQ has five seconds to acknowledge a push;
a missing or negative acknowledgement is a failed send.

The entire batch validates before writing and uses one D1 batch transaction.
The UPSERT replaces a row only when the branch's assertion time is strictly
newer. Retries, delayed sends and racing identical reports cannot overwrite
newer evidence. An equal timestamp is idempotent. This is a latest-reading
store, not a participation history or a billing input.

### Count definitions

`period` is the UTC calendar month of `reported_at`. Events are in the
half-open interval from its first day to the report time. People are distinct
accounts within each program; they are not summed across programs.

- Spin-Out Lab: non-postponed cohorts overlapping that month to date, and
  distinct activated applicants in those cohorts. Pending or approved-only
  applications are not participants.
- Mentor cohorts: distinct assignment holders and distinct assigned cohorts
  for assignments active at any time in the month to date. These count the
  assignment ledger's history; they do not claim the holders' current role.
- Learning: distinct enrolled accounts in published Learning programs, with
  enrolments active at any time in the month to date. A learner in two
  Learning programs is counted once. Learning programs are not relabelled
  as Lab cohorts.
- Refer & Earn: non-draft referral submissions made in the month, and their
  distinct referrers.
- Referral partners: referral-kind redemptions in the month, and distinct
  redeemers. Deal-sourcing redemptions are excluded.
- Perks: claims made in the month and distinct claimants, including historical
  claims that subsequently expired or were revoked. No code or claim detail
  leaves the branch.

A metric without a defined local source is null. AI-native venture, investor
cohorts, product testing and custom programs have no invented figures.
Unsupported combinations (for example Learning cohorts or Lab claims) stay
null as well. A failing source query sets that metric's unreadable bit and
keeps its count null; other metrics/programs still report. The wire has only
program keys, nullable integer counts and that bounded bit mask alongside
the period/time. It carries no free-text reasons from a source record.

### HQ read

`GET /api/admin/program-grants/licences/:uid/in-use` is HQ Super Admin only.
It returns that studio's granted/paused programs, independently of the rest
of GR3. A program with no report has `state: not_reported`, null counts and
timestamps, and exactly "This studio has not reported program figures yet."
A reported row keeps its period and assertion time. Counts distinguish
`recorded`, `not_recorded` and `unreadable`, with fixed absence/retry reasons;
a recorded zero remains zero.
Reports older than 48 hours are marked stale and retain the original date
and age. Storage failure is a fixed, retryable 503, never an empty result or
zero. The API client exposes `inUse(uid)` and `sendProgramReport()`; neither
accepts a figure body. GR3's layout remains owned by D987/#2778.
