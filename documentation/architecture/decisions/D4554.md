## D4554 — Cloudflare-centred hybrid platform and bounded agent compute (#4554)

**Status:** Proposed for owner architecture review; created through #5298 on **2026-11-11**. This is a repository-verification decision record, **not** approval to deploy or activate infrastructure.

**Parent:** #4554. **Unblocks after acceptance/merge:** #4557's host implementation. **Technical truth:** [CLAUDE.md](../../../CLAUDE.md) and [wrangler.toml](../../../wrangler.toml) on `main`, inspected 2026-11-11. No live Cloudflare account settings, D1 user records or production runtime metrics were read for this ADR. "Configured in repo" is **not** a claim that a service is active.

### 1. Decision and alternatives

Retain **one Cloudflare Worker/Hono control plane**, one D1 authority for transactional records and authorization, R2 for binary and generated artifacts, Vectorize for semantic retrieval, Durable Objects for scoped state, Queues and Workflows for durable work, and the **existing** Axal AI router, budget holds/settlement and member usage ledger. Cloudflare Containers are a **separate, default-off, constrained compute plane** for tasks that cannot safely or economically execute inside a Worker, such as Python, document rendering and isolated code execution. Agent Skills integration is a loader/adapter under D1 policy and pinned versions, never a second entitlement system (D4555).

Do **not** introduce a wholesale PostgreSQL, Temporal, Kubernetes, AWS or GCP migration now. Each introduces a second identity/permission plane, operational control plane or transactional boundary without an established, measured constraint that warrants it. Reassess only after measured, owner-reviewed reliability, throughput, regulatory/residency, cost or capability evidence; never assume a hypothetical swarm QPS is observed load. D4569 adopted **one optimized D1 database, no partition** on 2026-11-10; use its scorecard and transactional invariants before considering a split.

**Alternatives evaluated:** (A) extend existing Worker/Hono + D1 + R2 + DO/Queues/Workflows with a bounded Container compute adjunct **chosen**; (B) direct external-model-only architecture **not chosen** because gateway and D851 adapter are alternatives behind one AI accounting path; (C) replace core with Postgres/Temporal/Kubernetes **deferred**, because it adds consistency, operating and migration risks before a verified bottleneck. A future alternative requires a separately reviewed design, testable rollback and an independent financial/tenant-consistency proof.

### 3. Component and trust-boundary diagram

```text
Browser / connected assistant / external integration
       |
       v
+---------------------------------------------------+
| StudioOS Cloudflare Worker / Hono                 |
| AuthN / role + tenant + company + fund authZ      |
| plan + approval + AI policy + rate/cost limits    |
| scoped input manifests, grants and audit ledger   |
+---------------------+-----------------------------+
          | privileged binding / scoped Worker call
    +-----+------+--------------+------------------+
    |            |              |                  |
    v            v              v                  v
   D1           R2         Vectorize        DO + Queue/Workflow
  records     artifacts       index          per-scope lifecycle
  & ledger                                    durable retries
    ^                                             |
    | result metadata + verified grant            | authorized dispatch
    +------------------- Worker broker ------------+
                             |
                             | narrowly scoped, authenticated call
                             v
            Separate general compute host Worker
                             |
                    Container-owning DO
                             |
            Isolated Container; no D1 or provider key
            no network egress; bounded CPU/RAM/time
                             |
             uploaded/signed R2 artifact reference
                             |
                   Worker validates result
                             |
          proposal → explicit human approval → action
```

A Container does not connect directly to D1, R2 credentials, model-provider secrets or unrestricted outbound network. Signed resource handoffs originate from the broker, are scope-bound, short-lived, single-use and never authorize a different tenant or run. The Worker verifies and records any callback, rejects late/cancelled results, and produces a proposal (not a self-executing business decision). External inference, if allowed, is **Worker-brokered** through the same AI router and holds/settlement authority; untrusted document content is data, never higher-priority instructions.

### 4. Resource responsibilities and approval boundaries

| Component | Owns | Must not own / trigger |
|---|---|---|
| D1 | users/licences, member and company scope, consent, run identities, financial reservations, canonical usage and immutable review decisions | large binary content, an unapproved second ledger or blind cross-tenant joins |
| R2 | stored documents, generated media and compute artifacts, using scoped keys and access-controlled delivery | permission policy, legal retention decisions or direct, unrestricted public reads |
| Vectorize | retrieval index and embeddings with provenance; authorized post-filtering on Worker reads | user identity/role grant or authoritative product facts without source verification |
| Durable Objects | isolation/coordination per named run, room or stateful session | cross-tenant global authority or unbounded job execution |
| Queues + Workflows | retryable execution and persisted step coordination, with explicit failure and idempotency | a second unsupervised agent lifecycle or charge-on-retry without settlement |
| Workers AI / AI Gateway / approved external adapters | model transport and provider-specific capability | tenant policy, final spending authority, direct privileged access to D1, broad payload logging |
| Containers | narrow CPU/OS workloads, bounded generated result and artifact metadata | model key, DB connection, production deploy, final approval, free Internet egress |
| Human reviewer | approvals of releases, irreversible writes, provider enablement and compliance gates | arbitrary UI-only trust or silent delegation to an agent |

**Security and privacy:** treat source documents, tool outputs, URLs, prompts and archive contents as untrusted. Validate size/type/entry count before and inside the Container; enforce per-job CPU, RSS, wall-clock, size and spending limits with hard termination on cancel/timeout. Store raw output in private, access-controlled R2; keep logs restricted and redact personal/financial/prompt content. Require origin authentication, replay-protected grants, actor and tenant attribution, approval gating, and separate security review for any new egress, filesystem or tool capability.

### 5. Container compute boundary agreed on #4557 — and the current Cloudflare caveat

Owner decisions recorded on #4557 (2026-11-07): **Q1=B** builds the pre-host grants as a separate, off-by-default slice (already merged); **Q2=A** makes the host a **separate Worker** (own Wrangler file, cross-script binding, owner-gated deployment); **Q3=A** asks for the **Durable Object Container API, default scheduling and `enableInternet: false`**; **Q4=A** requires a **proposal referencing an R2 artifact** at `agent-compute/<scope_kind>/<scope_id>/<run_uid>/`, human decision retained. No main Worker binding, no host deployment and no automation enablement is authorized here.

**New upstream warning (verified 2026-11-11):** Cloudflare's [Scheduling Policies](https://developers.cloudflare.com/containers/configuration/scheduling-policy/) page, last updated **2026-11-04**, now says **default scheduling is deprecated** and recommends the `durable_object` policy (public beta). The scheduling policy is immutable after application creation. The [Durable Object Container API](https://developers.cloudflare.com/containers/api/durable-object-container/) supports `enableInternet: false`; the 2026-09-30 [changelog](https://developers.cloudflare.com/changelog/post/2026-09-30-durable-object-scheduling-policy/) details the new alternative.

**Decision gate, not a silent override:** preserve the owner's Q3=A as the recorded choice; **before creating the Container application**, have the owner explicitly reaffirm default scheduling with a deprecation/migration plan, or separately approve the newer `durable_object` policy. Do not change the issued instruction merely because upstream recommends a new policy. This is a dated, blocking activation question, not permission to deploy a different policy. Isolated preview tests must cover the chosen policy, network isolation, image pin/SBOM, cancellation, quota enforcement, artifact validation, grant replay, rollback and independent review.

### 6. AI provider path: one router, two transports

D4556 compares **AI Gateway Unified Billing** (using the existing Workers AI binding where supported) against **D851 direct-provider adapters**. Either route is beneath the Worker AI policy gate and the same metering, allowance, tenant and usage ledger. A gateway model alias may choose *transport*, but cannot silently choose tenant entitlement, tool authority, billable user, budget or approval state.

Until approved, any new model/provider stays off. The evaluation must demonstrate capabilities, data locality, retention/zero-retention declarations, privacy classifications, untrusted input controls, payload logging disabled or explicitly approved, upstream and member-cost reconciliation, loss-of-usage semantics, fallback/rollback, timeout and rate-limit behavior. Upstream fees are not substitute member receipts.

### 7. Measured review and scale triggers

Use the existing [D4559 platform capacity dictionary](../../operations/PLATFORM_OBSERVABILITY.md) and [D4569 D1 scale decision](D4569.md). Its current *policy* review triggers are **5 GB D1** (capacity review) and **7.5 GB** (migration assessment), against a 10 GB per-database paid limit; these are **not** claims that a migration is necessary or that Axal has reached the threshold. Compare actual D1 size, p95/p99 query latency, busy responses, queue wait, Workflow retries, failed holds, restore RPO/RTO, egress, CPU time, cost per successful task and isolation failures on equivalent workloads.

Reopen the architecture only on:
1. Persistent, independently reproduced D1 contention/limit/availability evidence after query/index, backpressure and retention optimization (D4567–D4569), with a proof preserving financial atomicity and tenant scope.
2. Workloads that cannot run within Worker/Container limits even after bounded chunking, or a measured material cost/reliability advantage from another compute engine.
3. Documented legal or customer residency/transfer requirements not achievable with approved Cloudflare deployment controls.
4. Approved independent backup recovery objectives that cannot be met within the current failure domain.
5. Demonstrated product demand and accepted total operating cost that justify a second platform.

No hypothetical million-agent write-rate, unit-cost estimate or cloud-brand comparison substitutes for a reproducible measurement.
