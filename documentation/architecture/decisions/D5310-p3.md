## D5310 part 3 — One introduction request as its record: NW3.2 and NW3.4 (#5310)

Part 3 of #5310, after parts 1 (`D5310.md`, NW1, NW1.2, NW5) and 2 (`D5310-p2.md`, NW2, NW2.1). It builds boards NW3.2 and NW3.4 of the approved Network workspace canvas (`design/incoming/network-workspace/NW3-Intro-detail.dc.html`, D4799): one introduction request, accepted and not yet made; and the variant whose send is recorded while Made is not. No new route: an **Open record** action on each row of the Introductions log (`IntroductionsDesk`) opens the record in the shared detail `Sheet`.

### The new Worker read

`GET /api/relationships/intro-requests/:uid` returns `{ request }` in the log's own shape (`interactionView`).
- It is built on `requestOf(…, 'either')` and `viewOf`, the lookup every request action already uses, so only the asker and the teammate read it.
- Anyone else, or a uid that is not a request, gets the same 404 "Not found." as a request that does not exist. Nothing is read before that check.
- The asker never reads the introducer's send (`mail_sent_uid`, `delivery`), exactly as on the log.

Client: `relationshipsApi.introRequest(uid)`.

### What the record draws

| Board part | From | Rule |
|---|---|---|
| Title and line | `requester`, `teammate`, `person`, `created_at` | From the reader's side: "You → Priya, via Tom" for the asker, "Maya → Priya, via you" for the introducer. |
| Lifecycle | `created_at`, `decided_at`, `accepted_at`, `made_at`, `outcome` | Only recorded steps are done. Declined and Withdrawn end the steps after them, never drawn as waiting. Accepting is not making. |
| Timeline | the same fields, `note`, `decision_note`, `delivery` | Each entry is Recorded or Not recorded, with its time. The introduction email is the introducer's (D4604). The asker reads only that Made is recorded when the introducer sends it or records it. |
| Banner (NW3.2) | `status`, `made_at` | Accepted and not made. To the asker: the introducer's yes is not an introduction, and nothing is sent for them. |
| Reconciliation (NW3.4) | `delivery.state = record_pending` (D4604) | To the introducer only: the mail server took the send and the record is not updated. **Update the record** calls `POST …/delivery/reconcile`. It sends nothing, and there is no Resend. |
| People | the same | Target, Introducer and Requester, from the reader's side. |
| Next step | `status`, side | Each action is one the Worker allows that side: Withdraw (the asker, while pending), Update the record (the introducer, `record_pending`), Record the outcome (either side, once made), and the reader's own follow-up date. |
| Credits | — | "Team introductions spend no intro credits. Curated matches do." |

D4799 listed the reconciliation state as **Backend required (#4604)**. D4604 has since built it: `delivery.state`, `record_pending`, and the reconcile route. This part draws it and needs no new backend.
