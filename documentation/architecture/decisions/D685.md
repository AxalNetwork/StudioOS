### 1. Context

The owner's goal: **"transcribe from calls and then the worker AI defines the pain points, and populates the other modules in Validate"**.

The redesign is the founder's half of that chain:

1. **Setup.** "Record a session" opens a centred setup modal at `/validate/record`, over the page the founder is on. It has five sections:
   - Who;
   - How: In person | Video call | Audio call | Text chat;
   - Talking points;
   - Transcript;
   - Consent.
2. **Recording.** Start opens the full-screen Recording View at `/validate/record/live`.

### 4. The pipeline and the Worker AI step

The pipeline's last step, **"Placing findings", calls `structureSession(env, { sessionId, userId, trigger: 'recording_processed' })`.** It does not re-implement structuring.

`structureSession` already does the following:
- re-checks the member and the venture (`writableSession`);
- re-checks consent (`consentBlocks`);
- reads the final segments;
- picks `structured` or `re_structured`;
- reserves and settles the budget;
- writes the receipt lines and stores the placements;
- moves the session from `transcribed` to `structured`.

Three rules hold, as in D684:
- **Placements stay proposals** (D658). The founder accepts, edits or discards each one, and nothing reaches a module on its own.
- **#1470's consent rule.** An audio or video session without consent `given` is never structured.
- **The D640 budget.** Every AI step (transcribe, summarise, place) reserves and settles the member's budget and leaves receipt lines. A refused step is recorded and shown in the Worker's own words.

#### 5.1 session-setup-api: S03 issue A

**Asks:** S2, S3, S5, S7, S9, S10, S11; R2, R3, R9; A2.

**Now:**

**Build (Worker):**

1. **`POST /api/founder/validate/sessions`.** The body:

   - `interview_id`, or `interviewee: { name, company? }`, where name is required and at most 120 characters;

   - stage `'booked'` with `booked_at`.

   A picked interview must be on the same project and in stage `lead`, `invited` or `booked`. The session opens in the same D1 batch, and the route answers 201 `{ session, interview }`.

   Three more rules:
   - **Idempotent.** A repeated `client_key` from the same user answers 200 with the same pair. A double click on Start creates one interview, not two.
   - **One live session per member.** If the caller already has a session in `recording` or `paused` (not a channel or assistant session), it answers 409 `session_active` with that session's id. `POST /sessions/:id/start` applies the same check.
   - **Old callers.** `POST /interviews/:id/sessions` accepts the same new fields. `'manual'` stays accepted there for old callers but is no longer offered.

2. **`call_provider` and `meeting_url` on `interview_sessions`** (migration 450). Valid pairs are checked in the Worker:

   | channel | `call_provider` |
   | --- | --- |
   | `in_person` | NULL only |
   | `video` | `zoom`, `google_meet`, `teams`, `whatsapp`, `telegram` |
   | `phone` | `phone_speaker`, `whatsapp`, `telegram`, `signal` |
   | `text` | `whatsapp`, `telegram`, `paste` |

   - **`meeting_url`** is accepted only on video. It must be HTTPS, and its host must match the provider: `zoom.us` or `*.zoom.us`; `meet.google.com`; `teams.microsoft.com` or `teams.live.com`. A link for WhatsApp or Telegram video is refused with a sentence, because those calls have no meeting link to check.
   - **The canonical link.** `meeting_url` holds only a pasted link. `GET /sessions/:id` falls back to the `interview_channel_refs.join_url` of a scheduled D684 call.
   - **The label is derived, never stored.** The Worker returns `call_label` ("Video call · Zoom", "Audio call · WhatsApp call"; null for in person) from one map, so the frontend does not re-derive it.
   - **D684's `openSession` (`services/interviewIntake.ts`) also sets `call_provider`** (`zoom`, `google_meet`, `telegram`, `whatsapp`). That file is S01's under D684 §16, so S01 makes this change or reviews S03's.
   - **`submitted_via` is not touched.** It means "imported from elsewhere", and `channelOf` in `assistantSession.js` hides the recorder when it is set.

3. **Language.** `language` is optional, and NULL means Detect.
   - **Allowlist.** It is the ISO-639-1 codes accepted by both `@cf/openai/whisper-large-v3-turbo` and `@cf/deepgram/nova-3`, served as `languages: [{ code, name }]` in `GET /sessions/models`.
   - **Storage.** The language is stored at create.
   - **Plumbing.** It is passed through `RunOptions` in `services/aiRouter.ts` (`callWorkersAI` calls `audioInputFor` at about :842), through `sttFormats.audioInputFor`, through the transcribe route's `WHISPER_TURBO` fallback, and through the live relay (`liveTranscription.ts`).
   - **Per model:**
     - Whisper v1 (`@cf/openai/whisper`) gets no language.
     - A Nova-3 batch run drops `detect_language: true` when a language is set.
     - Flux, the live model, is English-only. Flux with a language other than `en` is refused with a sentence, and a Flux session on Detect stores `en` at start.
   - **Detect while recording.** The language line stays hidden until the final transcript's detection fills it, unless S03 confirms from the Workers AI docs that Nova-3 live events carry a detected language, in which case the relay stores it.
   - Detection still fills `language` when it is NULL.

4. **Text chat quote consent.** When a consent method is picked on a text session, set `discovery_interviews.quote_consent = 1`. This is quote consent, not recording consent. Not picked leaves it NULL.

5. **The interview on reads.** `GET /sessions/:id` and `GET /interviews/:id/sessions` return:
   - `interview: { id, interviewee_name, interviewee_company, project_id, stage }`;
   - `call_label` and `meeting_url` (§5.1.2);
   - `points` (§5.2).

   - when a text session first reaches `transcribed`, which happens at create and in `interviewIntake.appendSegments`;

   Optional: a backfill in 450 copies each interview's latest session channel into rows where `channel IS NULL`.

   **Call (S01):** the row is created at Start as `booked`, because a session needs an interview, and `booked` is true at that moment. It moves to `done` at stop. "Interviews this month" counts only held interviews (stage NULL or `done`), so a booked row does not inflate it. §5.6's sweeper deletes a draft that was never started, and the interview this route created for it.

7. **The recruiting picker.** `researchRecords`' stage filter accepts `'pipeline'` (stage in `lead`, `invited`, `booked`), with a "booked first" order beside Newest, Oldest and Name. It is read through `GET /api/cycles/validate/modules/customer-research`.

#### 5.9 processing-pipeline: S03 issue B, then S02 issue C

**Asks:** R14, R15; A1, A2.

**Now:**
- Stop is two synchronous calls the client drives: `POST /stop`, then `POST /transcribe`, which runs every chunk inside the request (`founder_validate_sessions.ts:313`).
- A Worker that dies mid-run leaves the session in `transcribing` for good, and DELETE refuses it (`:464`).
- A chunk that arrives after transcribe starts gets 409 and is left out.
- The frontend sets the stage itself (0, then 1). Summarising and Placing findings read "· Not recorded".

**Build (Worker, S03 B):**

1. **Migration 451 on `interview_sessions`:**
   - `processing_stage`: `uploading | transcribing | summarising | placing | done | failed`;
   - `processing_done`, `processing_total`;
   - `processing_error`, a sentence;
   - `processing_updated_at`;
   - `expected_last_seq`.

   Plus a staging table, `interview_chunk_transcripts (session_id, seq, model, segments_json, transcribed_at, PRIMARY KEY (session_id, seq))`, ON DELETE CASCADE. It holds one row per transcribed chunk, so a retry never bills a chunk twice. `deleteSession` deletes it explicitly.

2. **`POST /sessions/:id/finish { last_seq, auto }`,** called after stop.
   - It stores `expected_last_seq` and sets the stage to `uploading`, with `done` = the chunks stored at or below `last_seq`.
   - Once every chunk is stored, it enqueues an `interview_process` job.
   - A chunk PUT re-checks and enqueues when the last chunk arrives.
   - `auto: false`, sent in the rail's Manual mode (`useAssistMode('Validate')` off), stops the job after Transcribing. The review then offers Summarise and Structure buttons.

3. **The `interview_process` job.**
   - **Bounded.** It handles a bounded batch of chunks per message, up to `MAX_CHUNKS` = 2000 of 5MB, and re-enqueues itself.
   - **Transcribing.** Per chunk it transcribes under today's budget hold, writes the staged row, and moves `processing_done` forward. The transcription logic is extracted from the route into a service that both use. When every chunk is done, it assembles the staged segments and calls `replaceWithFinal` once (status `transcribed`, language detection).
   - **Summarising.** It calls the summary (§5.10). A refusal is recorded as a receipt line, and the job moves on.
   - **Placing findings.** It calls `structureSession(env, { sessionId, userId, trigger: 'recording_processed' })` (§4). A refusal leaves the session `transcribed` with the refusal in `processing_error`, so the review shows Structure.
   - **Done.** Stage `done`.
   - **Idempotent.** It resumes from the stage reached and is retried by the queue. A failure stores a sentence and stage `failed`.
   - **Retry.** `POST /sessions/:id/process` retries with a fresh idempotency key: `queue-consumer` claims each key in `job_idempotency` and acks a repeat.
   - **Stale rows.** A stage other than `done` or `failed`, with `processing_updated_at` older than 15 minutes, is stale. The sweeper (§5.6) and `/process` recover it, including today's stuck `transcribing` rows.

4. **Queue wiring.**
   - Enqueue through `services/queue.ts` `enqueueJob`; `USE_CF_QUEUE` is `"true"` everywhere.
   - Add `interview_process` to `AI_JOB_TYPES` in `services/queueWorker.ts`, to its mirror in `src/queue-consumer.ts`, and to `models/jobs.ts`. These are shared files that S01 edits (D684 §16).

5. **`GET /sessions/:id`** returns `processing: { stage, done, total, error }`.

6. **Keep `POST /transcribe` and `POST /structure`** for re-runs.
   - Widen `/transcribe`'s admitted statuses (`:318` admits only `stopped` and `transcribed`) to include `structured` and `reviewed`.
   - Refuse both while `processing_stage` is not `done`, `failed` or NULL, so two writers never run at once.
   - Let DELETE through for failed or stale rows.

**Build (frontend, S02 C):**

1. **"Stop and process"** runs:
   - `POST /stop`;
   - the capture's stop and flush. With no live capture, it flushes the IndexedDB queue directly, because `capture.current?.stop()` (`:308`) is then a no-op;

### 7. Honesty rules

These come from `CLAUDE.md` and `design/README.md`.

- **A canvas is a proposal, not a specification.** Every bracketed value in it is a placeholder, never data.
- **A figure with no stored fact behind it says so.**
  - The processing ring shows a percentage only where a count exists (§5.9). Summarising and Placing findings show none.
  - The meter shows "No target set" until a target is stored.
  - The language line is hidden until a language is known.
  - A missing company reads "Not recorded".
- **Prices come from the Worker.** They come from `GET /sessions/models` and the router's tables, never from the canvas. The canvas's $0.29 for Flux is not the price.
- **Refusals are printed in the Worker's own words:** consent, budget, `session_active`, a reused link.
- **Proposals stay proposals** (D658), and consent gates audio (#1470).
