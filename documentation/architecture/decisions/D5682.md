## D5682 — Section reporting coverage and canary boundaries (#5682)

The route coverage table records the current source declarations, their
diagnostic sections, and where a section cannot safely be assigned. Each row
names the declaring source. These files identify the code to check when a
family changes. On-call owners and notification exceptions are still pending
the rollout work.

The table is build output and is never committed (D5612). A committed copy
went stale whenever another branch landed a route first, which failed the
merge queue for a change that touched no route. From the repository root,
`node scripts/build-section-coverage.mjs` prints it and `--write` saves it to
the gitignored `documentation/architecture/SECTION_COVERAGE.md`. `--check`
fails if two renders differ or if a copy is tracked again; the frontend suite
runs the same check and asserts that every declared family, Worker family and
menu source has a row. Signatures make changes visible even when a path,
guard, menu restriction, alias, or handler changes within a family and the
family totals stay the same: to review a routing change, render the table
before and after it and compare the affected rows.

- **Frontend declarations.** Parse `App.jsx` and the registered route module
  directory as JSX. Group literal and nested templates by route family and
  account for aliases, wildcards and dynamic expressions. Known credential-bearing
  templates and declarations without a recognizable auth wrapper are excluded.
  An auth wrapper is static evidence only. The table does not determine a
  session's actual rights, including tier, venture or tenant membership.
- **Menus and generated catalogue.** Read the desktop and phone Account menus,
  persona and multi-licence sidebar data, and company settings tabs. Compare
  these sources and the same route-map fragments used by Profile Routing and
  Page Inventory to the declared route families. A navigation reference or a
  proposed canvas address may lack a declared route. This inventory does not
  resolve all computed destinations or infer mounted paths from menu copy.
- **Diagnostic sections.** Probe guarded templates with synthetic parameter
  values and the existing Worker classifier. A result names a section that
  the hint can return in a supplied context. Different profiles, menu origin,
  resource action and multi-licence ownership can change the answer. A
  guarded route with no hint is a private-fallback gap. It has no section
  dispatch from this inventory.
- **Worker handlers and jobs.** Reuse the authorization inventory's method,
  path, gate and file data. Do not assign a delivery destination or treat
  authorization as verified from a URL match. The staged HQ database-capacity
  producer is tracked separately from the anonymous intake and Slack receipt
  preview. Other jobs need an explicit verified producer before rollout.

The remaining #5682 work depends on #5679, #5681 and the owner's Slack setup.
The persona smoke journeys, cross-tenant and expired-session negatives,
failure and replay drills, and destination rollout have no live evidence from
this work. Production delivery is unverified. Keep workspace membership,
channel identifiers and receipts in the private operational record.
