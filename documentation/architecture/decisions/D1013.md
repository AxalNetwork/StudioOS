### 1. New product (PAY3)

- **Two steps.** Step 1 asks what is being sold: Plan, One-time service, Add-on or Session. Token packs are made on AI allowances.
- **A plan's family and level come from `/pricing`'s own cards** (`lib/sitePricing.js` `PLAN_CARDS`). Each level carries the metadata `aiCredits.planOf` reads:

  | Level | Metadata |
  |---|---|
  | Validate + Build | `tier=growth` |
  | Raise + Grow | `tier=studio` |
  | Investor Pro | `investor_tier=professional` |
  | Institutional | `investor_tier=institutional` |
  | Advisor Pro | `plan_group=advisor` |
  | Operating Partner Pro | `plan_group=partner` |
  | Market Intelligence Pro | `plan=mi_pro` |

  A test holds every one of them to what `validateProductMetadata` accepts.
- **Investor Plus** is a `/pricing` card that no checkout sells: no `investor_tier` names it, and D1009 adds none. The dialog says "/pricing shows this card, but no checkout sells this level yet", and Create stays disabled. It does not create a product whose metadata nothing reads.
- **Institutional** says that `/pricing` shows it as Contact Sales.
- **Market Intelligence** has no `/pricing` tab, and the preview says so.
- **The preview** is the `/pricing` card as a member will see it: the name as it is typed, the description or the card's tagline, "No price yet", and the card's button, drawn inert.
- **The clash (PAY3b).** If another active product already makes the same plan, the dialog names it and says to archive it first. It reads part 2's `plan.key` when present, and otherwise the same `planOf` rule. Two founder tiers are not a clash. As on the canvas, this is a warning, not a block.
- **The other kinds.**
  - An add-on asks for the feature it unlocks and its days, which must be a whole number above zero.
  - A one-time service and a session take a name and a description.
  - Every kind can set its audience.
- **Codes such as `tier=growth`** appear only under Technical details.

### 2. The price dialogs (PAY4)

- **Add a price.** The dialog takes an amount, a currency (USD, EUR, GBP or CAD) and the billing: Monthly, Yearly or One-time.
  - **The preview** is the canvas's line. For example: "$204.00 / year · AI allowance $4.25 a month · saves 15% against monthly."
  - **The allowance** is D783's: 25% of a USD monthly price, or a yearly price ÷ 12, rounded down. A price in another currency gives no allowance, and the line says so.
  - **The saving** is computed only against the product's live monthly price in the same currency, and only when there is a saving. Nothing is added across currencies.
- **Change a price** uses part 2's `POST /api/admin/catalog/prices/:priceId/change`.
  - **The canvas's "Also archive the old price" checkbox is not drawn.** The route always archives the old price, and rolls the new one back if it cannot, so the dialog says that instead.
  - **The reason** must be at least 10 characters, D1010's rule.
  - **The idempotency key** is made once per dialog, so pressing again after a refusal makes one change, not two.
- **Members on a price.** Change, archive a price and archive a product each count the members on it from part 2's `GET /api/admin/catalog/members`. If that read fails, the dialog says the members could not be counted, never "0 members".
- **Edit details and Archive a price.** These keep what the retired editor could do.
  - Edit details sends the product's full metadata with the new audience, so the plan it is read from is kept.
  - The catalogue mirror holds no description, so an empty description is never sent: it would wipe the one Stripe holds. The field says so.

### 3. The Stripe dialogs and the step-up (PAY6)

- **Replace key.** The key is checked as it is typed.
  - **A secret or restricted key** (`sk_`, `rk_`) is refused before anything is sent: "That is a secret key. Never paste it here."
  - **A key in a different mode from the account** is said as the canvas says it, and is not sent.
  - **If the account's mode was not read,** the dialog says the key was not compared.
  - **After a replace,** only the new mode is said, never the key.
- **Register a new endpoint** and **Add the missing events** send the Worker's own `register` and `update` actions.
  - Register writes `STRIPE_WEBHOOK_SECRET`, so its door sits inside `SecretWriteGate` (D223); `secret_consoles_d223.test.mjs` now reads it there.
  - If the signing secret could not be stored, the refusal is shown, never "registered".
- **Sync from Stripe** sits on the mirror card.
  - **What changed** comes from the catalogue read just before and just after the sync, by product ID. If either read fails, the dialog says what changed could not be listed, rather than calling every product new.
  - **A failed sync** says "Stripe did not answer. Nothing changed. This failure is recorded." (D1011 records it) and offers Try again.
- **The step-up (PAY6 D)** is the platform's own.
  - A write the Worker answers with 403 `step_up_required` raises `studioos:step_up_required`. `StepUpModal` collects the authenticator code, and `request()` sends the same write once more.
  - Cancelling surfaces the refusal as "The authenticator code was not entered, so nothing was changed."
  - The dialogs say "Next you enter your authenticator code" before the press, because it is asked for only when the session's step-up is stale.
  - **No second step-up dialog is drawn.** A page-level copy of the prompt would be a second place where the code is typed.
- **Reasons.** Every product, price and key write sends `reason`, as D1009 requires. `adminCatalogArchiveProduct`, `adminCatalogArchivePrice` and `adminStripeSetConfig` now take it, and the other writes carry it in their bodies.
  - Sync, Register and Add the missing events take no reason, because the Worker records none for them. The dialogs say each is recorded and ask for nothing that would not be kept.

### 4. Who is drawn a change

- Every Payments write is the Super Admin's (D1009's write bar).
- The page draws a change only for the holder of that elevation (`isSuperAdminUser`, `payUi.useCanWrite`).
- Anyone else reads "Only the Super Admin can change payments, after a fresh authenticator code." (D134: never a control the server can only refuse.)
- A token pack offers no change here; it is managed on AI allowances.

### 5. Retired

- **`PaymentsPanel`** (`pages/admin/consoles/PaymentsConsole.jsx`) is deleted, with its `confirm()` calls and the "Make a change" section that mounted it. It had stopped working anyway: since D1009 its archive and key writes sent no reason and were refused.
- **Tests and lists updated:**
  - the console lists (`_adminConsoles.mjs`, the reachability walk);
  - its D648 rows;
  - its toast-render check;
  - the rail's file list for H29.
- **The storefront's "Add Product"** on `/pricing/products` no longer creates anything.
  - It used to be drawn for any admin and sent no reason, so every press was refused.
  - It is now drawn only for the Super Admin, as a link to `/admin/platform/payments?new=product`, which opens New product.

### 6. Where the dialogs open from

- **Catalogue:** a New product button. Each product's name opens its sheet (on a phone, its card), and the sheet holds that product's actions. The dialog itself opens at page level, so a sheet never holds a dialog inside it.
- **Stripe connection:** the three doors part 6 drew, plus Sync from Stripe.
- **Part 4:** its lightbox (PAY2) can open the same dialogs through the same `{ type, product, price }` shape.
- **On a phone,** every dialog is a bottom sheet (D1014's `PayDialog`).
