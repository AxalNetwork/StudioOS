## D4673 — Status reports: one access policy, the founder profile as the client, and a draft that saves only where it was composed (#4673)

- **Status:** built by S13, 2026-11-06 (#4673, Delivery audit 1/6, P1).
- **Scope:** this records the rules and the fix. Reproduction detail stays in the private security-reporting process, as the issue asks.

### 1. One access policy

`services/statusReportAccess.ts` decides who may read and write an engagement status report, and every surface asks it.

| Who | Access |
| --- | --- |
| The partner on the engagement | Reads every report of it; writes one until it is sent (a sent report is a record of what the client received) |
| The engagement's client founder | Reads a report only once it is sent; never writes |
| Anyone else | Nothing |

- **Fill with Eadwyn** (`services/fills/scopes.ts`, `engagement_status_reports`) now reads through this policy. Its client branch matched the founder and never looked at the report's state, so an unsent draft's marks were readable from the client side. A client asking for an unsent report's sheet now gets 403.
- **The Delivery save** (`PUT …/status-reports/:period`) asks the same policy for the "a sent report is frozen" rule.
- **Partner-firm ownership is unchanged.** Every Delivery route still resolves the engagement through `requireOwnEngagement`, so another firm's caller is 404. Support-session restrictions are unchanged: Fill still gives a support session marks and no trigger, and refuses its keep and undo (`routes/fills.ts`).

The derivative reads already filtered `state = 'sent'` and are unchanged: the mail profile records (`services/mail/profileRecords.ts`) and the people list (`services/mail/people.ts`).

### 2. The client is the founder profile

`engagements.founder_id` and `founder_needs.founder_id` are `founders.id`, copied from `projects.founder_id`. An account belongs to a founder through `users.founder_id`. Delivery and Pipeline joined `users` on `founder_id`, which treats a founder id as a user id. When the two ids differ, the client's name was whichever account happened to have that number, or nothing.

All eleven of those joins now read `founders` by `founders.id`. That covers six in `routes/partner_delivery.ts` and five in `routes/partner_pipeline.ts`.

- **A founder with no account, or with several,** resolves to its own name.
- **A user whose id equals the founder's id** is never mistaken for the founder.
- **Response contracts** keep `founder_id`, a founder id, and never put a user id in its place.
- **A guard test** fails if either file joins `users` on a `founder_id` again.

**Not done here.** The same join appears 11 more times outside Delivery and Pipeline: nine in `routes/research.ts` and two in `routes/partner_offers.ts`. They are left for their own work package so this one stays the issue's size.

### 3. A draft saves only where it was composed

- **The composition names its target.** `GET …/report-draft/:period` returns `engagement_id` with `period`.
- **The page ignores stale responses.** `pages/partner/delivery/statusReportDraft.js` holds the rule. The composer keeps the latest request only: a change of engagement or period retires any composition in flight, so a late response is dropped rather than shown under the new selection.
- **The save uses the draft's own identity.** Save writes into the draft's own engagement and period, and sends both in the body.
- **The Worker checks it.** `PUT` refuses a body whose `engagement_id` and `period` do not match its URL with 409 `draft_mismatch`, and writes nothing. A body that names no draft is refused the same way.
