## D6315 — Grow proposal destinations and safe undo (#6315)

Mercury acceptance now uses the existing Calendar confirmation pattern: it
names the partner destination before creating anything. After acceptance,
Mercury, Calendar and Grow's PostHog feedback show a persistent destination
link and Undo beside their existing source sections. The links use the existing
scoped Grow record routes. The Beehiiv accept API also returns its channel
receipt; no unapproved new Beehiiv screen is introduced.

A content-free receipt records the source proposal, destination, accepting
member and whether acceptance created a record or linked an existing one.
Each source has its own undo route. Undo is private to that member, requires the existing venture writer gate,
refuses support sessions, and retains Mercury's founder gate. It changes no
external connector account. Existing records are retained; only this source's
link is cleared. Newly created records are removed only if unchanged and
without added child business records. Source proposals return to pending.

Four additive revision columns and update triggers count every target edit,
including a same-second edit back. An idempotent PostHog retry that reuses feedback is treated as an existing link,
including records predating revision tracking. New records require revision zero, avoiding
a race in which an edit before receipt creation becomes an undo baseline.
A D1 batch conditionally claims the receipt, checks its source link, clears
only that source link, deletes only a record this acceptance created, writes
`grow_proposal_undone` under the existing Grow activity/actor convention, and
marks the receipt undone. Refused and replayed undos cannot produce success
audit rows. Historical Calendar/PostHog acceptances retain destination links
but explicitly lack undo creation provenance. Historical Mercury links come
from their existing proposal read. We never infer delete permission for them.

The migration is additive; no old rows are backfilled as newly created.
Rolling back route and frontend code leaves these columns and tables harmless.
No production writes or external messages are part of validation. The owner
retains deployment and landing control.
