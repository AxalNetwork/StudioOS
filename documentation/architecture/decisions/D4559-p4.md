## D4559 part 4 — Settled AI charges without a usage row, as a capacity signal (#4559)

- **Status:** built. One signal, `ai.settlement.without_usage_row`, in the capacity read, its daily snapshot and its alert episodes; one matching benchmark invariant. Production rows are not repaired.
- **Context:** D4569 §1 fact 2 found that a run settles its hold in one write (`settleAiReservation`, an atomic batch with its ledger rows) and writes its `ai_usage_logs` row in a later one (`recordUsage`, which returns null when it cannot write). A settled charge can then exist with no usage row: the money is right, the attribution is missing. D4569 left the measurement to #4567 and #4568; neither made it (`missing_charge` in `_d1_bench.ts` checks a proposal whose usage row has no charge, a different fault). The owner's 2026-11-09 scope keeps #4559 as the backend readiness signals, with no panel.
- **Decision:**
  17. The signal counts holds with `status = 'settled'`, a non-zero `actual_included_microusd + actual_topup_microusd` and `surface = 'ai'` that no `ai_usage_logs` row names by `reservation_uid`. One parent hold with several usage rows (a deck run) is attributed. It is read by one statement, `SETTLED_WITHOUT_USAGE_SQL` in `services/platformCapacitySignals.ts`, which returns only a `COUNT`.
  18. Only `surface = 'ai'` holds are counted, because those are the paths (`aiRouter.run`, deck batches) that write a usage row under the hold. MCP and flow holds record their use in `api_usage_events`; holds that name no surface (meeting bots, image draws, live transcription, every hold from before migration 632) are not covered, and the read's `sampling` says so. Counting them would make a permanent warning out of rows that never owed a usage row.
  19. The window is holds taken in the last 24 hours, by `created_at`, settled (`updated_at`) at least 5 minutes before the read, so a run between its settle and its insert is not counted. `idx_ai_reservations_review_created (status, created_at)` (migration 430) bounds the outer rows and `idx_ai_usage_logs_reservation_ref (reservation_uid, record_ref)` (migration 202611070806) answers each `NOT EXISTS`; the test pins the plan with no `SCAN`. No migration is added.
  20. The signal is deployment-scoped, with `source`, `window`, `sampling`, unit `count` and `last_success_at` (the read itself). A read that throws, times out, answers without a count, or meets a schema without the columns is `unavailable` with `value: null`, never 0. It names no member, company, agent or hold.
  21. Threshold (proposed, owner item 6 in `PLATFORM_OBSERVABILITY.md` §7): any non-zero count is a warning, hysteresis 0. No critical level is proposed; `critical` is `Number.MAX_SAFE_INTEGER` so `levelFor` never reaches it. A measured 0 clears the episode; an outage holds it, and opens a freshness gap only when a count was measured in the last 48 hours.
  22. `_d1_bench.ts` counts the same statement, over every hold with no window and no grace, as its `settled_without_usage` invariant, and `d1_benchmark_4567.test.ts` breaks it on purpose (the usage rows of a settled, charged AI hold lose their `reservation_uid`). The benchmark's "every invariant 0" now covers this fault.
- **Consequences:** HQ gets a count of missing attribution with no new table, index or vendor. A non-zero count in production is reported on #4559 and repaired as its own task, never here. Holds that name no surface stay unmeasured until their callers name one.
