## D684 — Interview channels: business Telegram, business WhatsApp, Zoom and Google Meet feed Validate through one intake

Issue: #1575. Slots:
- **S19:** Telegram and WhatsApp.
- **S18:** Zoom and Google Meet.
- **S02:** the Validate UI and Account › Connectors.
- **S01:** the contract, integration and review.

Number assigned by S1, 2026-10-13.

### 1. Problem and objectives

The owner, 2026-10-13:
- Telegram and WhatsApp are connectors for all users. Each user connects their **business** Telegram or WhatsApp account in Account › Connectors (/account/connectors), and can also connect from an interview, "so then the data can be transmitted across different modules in Validate".
- The same intake should cover audio and video calls: Zoom, Google Meet, WhatsApp calls and Telegram calls.

Objectives:
- Customer conversations from those channels reach an interview.
- From there they reach the existing Structure → proposals → review flow, which places them across the Validate modules.
- Security, tenancy and idempotency are built in.
- Only infrastructure already in production is used.
- Each provider is held to what its official API actually allows.

### 2. Verified findings

Checked in the code at the cited paths, and read-only in production D1, on 2026-10-13.

**Text chat is not a live chat.**
- The founder pastes a finished conversation (`RecordSessionSheet`, "Name: words").
- `POST /api/founder/validate/interviews/:id/sessions` stores it once through `replaceWithFinal` (`services/interviewSessions.ts:173`): segments are written and the session is set to `transcribed`.
- Nothing can be appended afterwards, and no AI replies inside a chat.

**AI runs after capture.**
- `POST /sessions/:id/structure` (`structureTranscript`) writes **pending `validate_proposals` across the Validate modules**. The founder accepts or rejects them. This is how data moves "across different modules in Validate".
- `POST /sessions/:id/ask` answers questions about the transcript, with citations.
- Both run on `aiRouter.run` under the D629 allowance and tokens.

**Precedent for an outside source.**
- The AI-assistant connector (`services/assistantInterviews.ts`, D666/D669) creates an interview and a session, and sets `interview_sessions.submitted_via` (migration 447).
- It re-checks `canWrite(project, user)` on every write.

**Ownership.**
- The chain is `discovery_interviews.project_id` → `projects.founder_id`, checked with `canWrite` / `ownsVenture` (`routes/_founder_validate_helpers.ts`).
- `users` is at D1's 100-column limit.

**Connectors (D649/D651).**
- `integrations` holds one row per member and provider (`UNIQUE(user_id, provider_key)`).
- It carries optional credentials encrypted with `columnCipher` under `KEK_PII`, plus `external_account_id`/`_name` and `config_json`.
- Account › Connectors reads `/api/connectors`, and the registry already has a `Messaging` category.

**Webhooks.**
- The generic receiver assumes one URL per member connection.
- Telegram (one bot), Meta (one app) and Zoom (one app) each post to one URL, so tenancy must be resolved from the payload.
- The model to copy is the GitHub receiver: HMAC, `INSERT OR IGNORE` on an event key, then claim and release.
- `constantTimeEqual` is in `rpc/secret.ts`.

**Async.**
- `JOB_QUEUE`, with `job_idempotency`, retries and a DLQ.
- A per-minute cron with reconcile sweeps.
- `waitUntil`.

**Existing Telegram code.**
- `TELEGRAM_BOT_TOKEN` is the outbound-only news bot (`services/telegramClient.ts`). It has no inbound path.

**Google.**
- The first-party Google Calendar connection already holds `calendar.events`, which creates events with a Meet link.

**Production.**
- `interview_sessions` has one row, in person.
- No text session has ever been created.

### 4. Options considered

- **A. Direct per provider.** Each provider writes into interviews its own way.
- **B. Shared connector framework.** A generic plugin interface for every channel kind.
- **C. Event-driven everything.** Every webhook goes straight to a queue, and a consumer does all the work.
- **D. Hybrid (chosen).**
  - Thin provider adapters (verify, normalise, send or fetch).
  - One intake service that writes into the existing session model.
  - Connections on the existing `integrations` rows.
  - Shared tables for event dedupe, customer threads and meeting refs.
  - The existing queue only for slow work (voice transcription, transcript downloads, sends), and the existing cron only for Meet, which has no push.

- **A** repeats tenancy, dedupe and ownership four times, and those are the security-critical parts.
- **B** builds a plugin system for four known providers.
- **C** puts customer message text in queue payloads (and in `queue_jobs` on the D1 fallback). It also delays the step that must happen before acknowledging: persisting the message.
- **D** persists before acknowledging, keeps text only where transcripts already live (plus an encrypted, time-limited pending inbox), and queues only work that can outrun a webhook deadline.

### 6. Selected architecture

```
Telegram webhook (one Axal bot)   WhatsApp webhook (one Axal Meta app)   Zoom webhook   Meet sweep (cron)
 verify secret_token               verify X-Hub-Signature-256             verify HMAC    poll after ends_at
 business_* updates                tenant = metadata.phone_number_id      host → member  ref → member
 tenant = business_connection_id   → integrations row (member)
 → linked member                          │                                  │             │
            └─────────────── dedupe: channel_events ─────────────────────────┘─────────────┘
                                   │
               channel_threads: one per customer chat
               ├─ pending → channel_thread_messages (encrypted, ≤ 30 days) → member assigns in Axal
               └─ assigned → services/interviewIntake.ts (S01) → interview_sessions (channel 'text' |
                             'video', submitted_via = provider) + interview_transcript_segments (existing)
                                   │
       existing Structure / Ask (aiRouter, D629 budget) → validate_proposals → founder review → Validate modules
```

**Business Telegram.**
1. In Account › Connectors the member presses **Link Telegram**. Axal issues a one-time code, stored only as a SHA-256 hash, valid 10 minutes, usable once.
2. The member opens `t.me/<AxalBot>?start=<code>`. The private `/start` records its claiming Telegram account; its first/last name and @username are encrypted on the claim and shown only to the signed-in Axal member. The bot names the masked Axal account and asks that same Telegram account for `/confirm`. **Both** that confirmation and the member's Confirm in Axal are required within the original ten-minute code lifetime. Either can arrive first. Only then does one guarded D1 batch create/update the active `integrations` row and attach business connections; replacing an old account forgets its threads in that same batch. A uniqueness race rolls everything back. A new code or disconnect cancels earlier pending claims; expired, cancelled and unreadable claims refuse with a sentence. Existing active connections are unchanged until both sides agree (#1602, migration 458).
3. In Telegram › Settings › Telegram Business › Chatbots, the member connects the Axal bot and chooses its chats. The `business_connection` update is stored in `telegram_business_connections` and joined to the member through their Telegram user id.
   - If they connected before linking, the bot messages them a link prompt and stores nothing from the connection until they link.
4. Each `business_message` lands in the thread for its chat. Text is stored. A voice note on a chat not yet in an interview is kept as a placeholder (its duration, its file reference encrypted) and transcribed only once the member adds the chat to an interview, so a stranger's voice notes never spend the member's AI budget. Then it is transcribed with the existing Whisper route under that budget, within a per-connection cap of 50 a day held in D1 (failing closed), and only the text is kept.
   - `edited_business_message` updates a pending message.
   - `deleted_business_messages` deletes pending copies.
5. The member's replies from Axal go out through `sendMessage` with `business_connection_id`, only when `rights` allow replying.

**Provider deadlines (#1602).** Telegram Bot API and WhatsApp Graph calls have a 10-second deadline covering both headers and JSON, using `util/deadline.ts` and an abort signal. A lost send response (deadline, network loss, or malformed acceptance) is `send_unknown`: its outbound row stays `pending`, the reply answers `ok: null`, and a repeat of the same client key sends nothing. A known provider refusal still records `failed`. The composer retains its key on an unknown response too; another press checks the same attempt and never offers a duplicate send. Telegram's member-only claim read/confirm routes and D1 attempt store ship in migration 458; S02 enables the matching Account › Connectors control only after these routes merge.

**Business WhatsApp.**
1. In Account › Connectors the member presses **Connect WhatsApp Business**. Meta's Embedded Signup v4 opens in coexistence mode, so they keep their WhatsApp Business app.
2. The Worker exchanges the returned code for a business token (stored encrypted in `integrations.credentials_enc`). It records `waba_id` and `phone_number_id`, and subscribes the Axal app to that WABA's webhooks.
3. Webhook events find the member by `metadata.phone_number_id`.
   - `messages` from a customer become the customer's side of the thread.
   - `smb_message_echoes` (what the member sent from the app) become "Me", so the thread holds both sides of the conversation.
   - `statuses` advance `channel_outbound`.
4. Replies from Axal go out only inside a 24-hour window (`CHANNEL_LIMITS.replyWindowMs`). On WhatsApp it runs from the customer's last message; outside it the composer says templates are a later step and sends nothing. Telegram Business lets a bot act only in chats active in the last 24 hours, so the same rule applies there.

**From an interview.** The interview's Connect panel does two things:
- It lists the member's pending threads. Choosing one **assigns** it: pending messages move into a new capture session (channel `text`, `submitted_via` = provider) and later messages append to it. "Create interview from this chat" is a separate action; nothing is created on its own.
- It links or connects the provider in place if the member has not yet, through the same flows as Account › Connectors.

**Meetings (Zoom, Google Meet).**
- `POST /api/founder/validate/interviews/:id/meetings` creates the call and a session (channel `video`, `submitted_via` = provider), plus an `interview_channel_refs` row.
- **Zoom.** It connects per member through the Connectors registry (OAuth). `recording.transcript_completed` is verified and deduped, then a queue job imports normalized final VTT segments after `writableSession` rechecks ownership, keeping timestamps and speakers. A call that was ended and restarted is several Zoom instances: the first takes the call's session, and each later one is imported into a session of its own on the same interview.
- **Google Meet.** It uses the member's Google connection to schedule the call. Reading its transcript needs `meetings.space.readonly`, which no Google sign-in in Axal asks for yet (#1585 adds that consent), so until then a reconnect cannot help: the call is scheduled, and the ref says plainly that its transcript will not be imported and that the recorder or a pasted conversation will do instead (`meet_transcripts_unavailable`). The sweep code, which imports the transcript entries of a call whose `ends_at` has passed, is ready for when that scope is granted.
- **Which conference is the call.** A Zoom instance or a Meet conference record belongs to the interview only if it started within the call's slot: up to 30 minutes before its start, or an hour after its end (`withinCallSlot`, `services/channels/meetings.ts`). A restart or rejoin during the call is kept; another use of the same link later that day is someone else's conversation and is never imported.
- **No recording or transcript.** If the plan or setting doesn't provide one, the ref says why in plain words. The founder can still use the in-app recorder or paste the conversation.

**Reliability follow-ups (#1601).** A later Zoom instance's lookup failure is stored on that instance's ref, including non-retryable and exhausted-queue outcomes, so the first imported part cannot hide it. A retry or sweep lists past instances with `meeting:read:list_past_instances` and imports only starts inside `withinCallSlot`; recently completed calls are checked for seven days, with the existing idle backoff. Token headers and JSON share a ten-second deadline, below the thirty-second rotation lease, and a timeout releases the lease. Import-now failures offer a manual retry without promising an automatic one. Confirmed and unconfirmed provider cancellation outcomes are kept in the ref's notice/error sentence and returned after reload. The interview transcript mirror aggregates each provider session once, in session order; a recorded transcript remains authoritative and is never replaced by this mirror. The per-session final segments remain the import source of truth.

**From the transcript to Validate, without a button** (`services/sessionAutoStructure.ts`). The owner's goal is the whole chain: a call or chat is transcribed, the Worker AI finds the pain points, and the other Validate modules fill in. D658's Structure already proposes seven kinds of placement: pain severity (Problem discovery), ICP fit, segment, demand signal, evidence, competitor mention and market fact. Until now only the founder's button ran it. It now runs by itself as a queued `session_structure` job:
- when a Zoom or Meet transcript is imported (`call_imported`);
- when a customer chat is assigned to an interview (`chat_assigned`);
- when an assigned chat gains messages and then stays quiet for 30 minutes (`chat_quiet`). This is the five-minute sweep, and it runs at most once every six hours per session, refused runs included, so a chatty customer cannot spend the member's budget.

Three rules do not change:
- Placements stay **proposals**: the founder accepts, edits or discards each one, and nothing reaches a module on its own.
- **#1470's consent rule** still applies. A call is scheduled only with the interviewee's consent recorded, saying how it was given (`POST …/meetings` takes `consent: { status: 'given', method }`), and a video session without consent is never structured.
- Every run reserves and settles the **D640 budget** and leaves receipt lines. A refused run is recorded, and the founder can still press Structure.

Record a session's processing pipeline (#1575's Record a session redesign, S03: upload → transcribe → summarise → place findings) calls the same `structureSession` for its last step.

**Calls through Telegram and WhatsApp.**
- **Telegram:** there is no call API. Voice notes are captured as above. A Telegram call can be recorded with the existing in-app recorder (channel `phone`).
- **WhatsApp Calling** is available to a member's own number once it is eligible (messaging limit ≥ 2,000). Media needs a WebRTC endpoint.
  - The phase 2 design: the member's **browser** answers a customer's WhatsApp call (Graph API SDP pre-accept/accept from the `calls` webhook), and records it through the existing chunk recorder and transcription.
  - It is not built in this phase. The Connectors card shows "Calls: not yet".

### 7. Rejected alternatives

- **One Axal number or bot that founders message, personal capture only.** Superseded by the owner: members connect their **business** accounts, so their customer conversations arrive directly.
- **Each member creates their own Telegram bot.** Telegram Business lets one Axal bot serve every member, with each member choosing their chats.
- **Reusing the news bot.** A bot that receives customer conversations must be revocable on its own.
- **Auto-creating an interview for each new chat.** Rejected: an unknown sender must never create or change interview records. The pending inbox is the explicit association step.
- **A queue in front of every webhook.** Rejected for text, as in C.
- **A live chatbot loop or Durable Objects.** Rejected because no live AI conversation exists to extend, and auto-replying to a member's customers is a consequential action this phase does not take.
- **Meet push through Workspace Events.** Rejected because it adds a GCP Pub/Sub dependency.
- **Building WhatsApp Calling now.** Rejected because of eligibility, plus the WebRTC endpoint it needs.

### 10. Security

- **Fail closed:** every webhook returns 503 when its secret is unset.
  - Telegram: `X-Telegram-Bot-Api-Secret-Token`.
  - WhatsApp GET: `hub.verify_token`.
  - WhatsApp POST: `X-Hub-Signature-256` over the raw body with the Axal app secret. The GET challenge never stands in for it.
  - Zoom: `x-zm-signature` over `v0:{ts}:{body}`, with a 5-minute window and the url_validation challenge.
  - All comparisons use `rpc/secret.ts` `constantTimeEqual`.
- **Two-sided Telegram consent (#1602).** A code alone and either owner's confirmation alone activate nothing. The claim stores encrypted provider name/username; only its issuing member may read/confirm it. Expiry is the code's original ten minutes, new codes/disconnects cancel pending consent, and the guarded activation batch makes claim consumption, connection replacement and old-thread deletion atomic. Migration 458 invalidates legacy pending codes, leaving active integrations intact.
- **Tenancy comes only from the verified connection.** The interview comes from the member's own assignment, never from a payload.
  - Telegram: `business_connection_id` → a connection whose `user_id` is linked.
  - WhatsApp: `phone_number_id` → an active `integrations` row.
  - Zoom: account and host → a connected member.
  - Meet: ref → member.
  - `canWrite` is re-checked on assignment and on every append, along with the member's active and deletion state.
- **Privacy.**
  - Pending text and contact names are encrypted. Pending threads are purged after 30 days, and pending copies are deleted on assignment.
  - Logs and events carry ids, never text or phone numbers. WhatsApp numbers are shown masked.
  - Business tokens are encrypted; platform secrets stay in Worker secrets and never reach D1, a response or a log.
- **Abuse limits.** Raw body ≤ 256 KB, counted as it arrives, so a body without Content-Length is never buffered whole. Text ≤ 8,000 characters per message. A per-connection limit of 120 events a minute, held in D1 (`channel_counters`): a KV counter could not trip, because KV accepts one write per key per second. Link-code issuance and redemption/confirmation attempts are counted atomically in D1 (`channel_link_attempts`, migration 458): 20/hour per hashed IP for issuance and 10/hour per hashed Telegram account for bot-side attempts. Hashes are domain-separated HMACs; rows contain no raw IP/identity and are purged after two days. Counter failures refuse linking, so a KV 429 cannot leave attempts uncounted.
- **Ambiguous outbound sends (#1602).** A provider that does not answer within ten seconds cannot hold the reply request. Timeout/network loss keeps the outbound claim `pending` with `send_unknown`, never `failed`, and never automatically retries it. The member is told to check the provider chat; no local transcript claims an unconfirmed send happened. The frontend retains the original key on unknown sends and tells the member to inspect the provider chat; another press checks that same attempt.
- **Inbound text is data.** It is never instructions: it reaches AI only through the existing citation-bound Structure and Ask, and no message triggers an action.

### 11. Reliability and idempotency

- **Persist, then acknowledge.**
  1. Verify.
  2. `INSERT OR IGNORE` into `channel_events`; a duplicate gets 200 and nothing else happens.
  3. Store the pending message or the segment.
  4. Enqueue slow work.
  5. Return 200.
- **Failure before the store** releases the event row and returns 5xx, so the provider retries (the GitHub pattern).
- **Jobs** (`channel_followup`, `meeting_import`) carry `provider:event` idempotency keys. Each adapter registers its handler with `services/channels/jobs.ts` at module load, and `queueWorker.ts` dispatches by job type and the payload's `provider`. A provider that registered none fails loudly. A provider that must poll (Meet) registers a sweep, which the cron runs every five minutes.
- **Sends** are guarded by `channel_outbound.client_key`.
- **Delivery.** WhatsApp statuses advance delivery; Telegram reports acceptance only, so "delivered" is never claimed there.
- **AI failures** never lose a stored message.

- **No new bindings.** The work reuses `DB`, `JOB_QUEUE`, `RATE_LIMITS`, `AI`, the cron and `KEK_PII`.
- **New Worker secrets** (PRODUCTION.md §4):

  - WhatsApp (Axal's Meta app as Tech Provider): `WHATSAPP_APP_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_EMBEDDED_SIGNUP_CONFIG_ID`.
  - Zoom: `ZOOM_CLIENT_ID`, `ZOOM_CLIENT_SECRET`, `ZOOM_WEBHOOK_SECRET_TOKEN`.

The page accepts the signup's `message` event only from a `facebook.com` origin.
