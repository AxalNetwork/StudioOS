## D8693 — A push uses one plan: the equal-weight plan, in every consumer (#8693)

**Context.** On a push to `main`, one run of `ci.yml` built two plans under the same part names. The `plan` job ran
`test-drift-parts.mjs --plan test-timings.json` (weighted by main's newest timing artifact) and uploaded it as
`suite-plan`. That artifact is what the capacity pilot submits (`planDigest`), what the trusted planner checks, and what
a delegated Worker shard runs (the executor and D7881's Mac handoff read the parent's artifact). The hosted `suite`
parts each wrote `--plan --equal-weights` (D8435). Each plan covers every file once on its own. A delegated
`worker-N-of-6` standing in for the hosted part of the same name, from the other plan, would leave some files run twice
and others not at all. D8435 left the choice to S39. The merge queue already had one plan (D8626).

**Decision.** A push uses the equal-weight plan everywhere, as the queue and every hosted part already do.

1. `ci.yml`'s `plan` job writes `--plan --equal-weights` and no longer downloads main's timing artifact. Its
   `suite-plan` artifact is therefore the same bytes each `suite` part writes for itself. The runner benchmark's
   `plan` job carries the same steps, because `runner_lanes_5611` holds the two equal.
2. `capacity-submission.mjs` is unchanged in behaviour. It still digests the uploaded artifact, which is now that plan.
3. `capacity-planner.mjs` rebuilds the equal-weight plan from the candidate's checkout on both events. On a push it
   refuses (`planner_plan_not_equal_weight`) an artifact that is not those bytes exactly, even one whose digest
   matches the submission. So a weighted plan cannot reach the coordinator, whatever wrote the artifact.
4. The executor (`runner-execution.mjs`) is unchanged. It runs the bytes the submission's digest names, so its
   shards now match the hosted parts.

**Why equal weights.** D8435 measured both packings over the same 37 hours: 105 weighted pull-request runs against
169 equal-weight queue runs. The slowest Worker shard took 40.0 / 48.2 minutes (p50 / p95) weighted and 40.4 / 49.3
equal. The weights bought nothing measurable. An equal-weight plan is a pure function of the commit, needs no API
call or artifact, and is already what the hosted parts and the queue use. So making the plan job match them is a
one-line change, and the other way round would have changed every part on every event. #5609 is measuring part
*counts* (6, 8, 12) on the landed planner. This decision changes no count and records no benchmark result, so it
neither depends on that work nor contradicts it. If #5609 later shows a packing that beats equal weights, every
consumer has to change together, and `ci_push_one_plan_8693` fails until they do.

**Held equal by a test.** `frontend/test/ci_push_one_plan_8693.test.mjs` runs the planner command each of the two
jobs carries in `ci.yml` on this commit, in a scratch checkout. It feeds the `plan` job's bytes through
`capacitySubmission`, `plannerSubmission` and the executor's `verifiedPlan` (push and queue). Then it asserts that each
delegated `worker-N-of-6` has the files and commands of the hosted part of the same name. It also asserts that every
file of the sharded suites is planned exactly once, and that `rest` carries every other step of `test:drift`. A second
case shows the planner refusing a valid, exact-once timing-weighted plan with a matching digest.

**What does not change.** No test file is dropped and no part name changes. No required check changes, and the
matrix, the gate and every job but `plan` are byte-for-byte the same (`BASE_JOB_DIGESTS` excludes `plan`, so no entry
moves under D8434). Nothing enables the pilot, deploys, or changes a repository variable or the ruleset.
`github-alerts.yml`'s future-clock plan still reads timings. It is a separate workflow and no capacity consumer reads it.

**Rollout.** `capacity-submit` and `capacity-route` run the planner from their pinned main commit (D8335), so the
planner's new check takes effect only when the pin moves to the commit that lands this change. That move is its own
follow-up PR. Until then the pinned planner reads the artifact as before, and that artifact is already the
equal-weight plan from step 1.
