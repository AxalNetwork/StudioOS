## D5023 — A package version is priced from the licence's country index, with its bundle economics shown and frozen (#5023)

- **Status:** built 2026-11-09 by S26 for #5023 (packages 2/5, parent #5021). Builds on D5017 (licence pricing basis and
  snapshot), D5018 (program reference prices and `recommendProgramFee`) and D5022 (the versioned package catalogue).
- **Number:** D5023 is this issue's number (D4106). Migration:
  `cloudflare-worker/sql/migrations/202611092252_package_pricing_recommendations.sql`.
- **Code:** `cloudflare-worker/src/services/packagePricing.ts`, `cloudflare-worker/src/routes/admin_package_pricing.ts`.
- **Tests:** `cloudflare-worker/test/package_pricing_5023.test.ts`.

### 1. The calculation

`recommendPackage` is pure and works in exact integer micro-cents:

1. recommended = the package version's base annual fee × the licence's country index;
2. clamped to [base × floor, base × ceiling] when the version sets them (`clamped` in the trace says which);
3. rounded half up to the pricing model's commercial increment (a package version has no increment of its own);
4. the unrounded and clamped values are kept in the trace;
5. the guidance range (`guidance_min_cents`, `guidance_max_cents`) is moved by the same index and rounded the same way.
   It is never clamped, because it is guidance and not a price.

### 2. The index is the licence's own

- The index comes from the licence's latest country recommendation (D5017's `licence_pricing_snapshots` row):
  - for one country, that country's index;
  - for a basket, the weighted index under the recorded basis and weights (`indexOfSnapshot`, as D5018 uses it).
- So a package is priced from the same snapshot and basket as the licence.
- HQ may name an older snapshot of the same licence only with a `snapshot_reason`. The record keeps
  `snapshot_is_latest = 0` and the reason.
- A snapshot from another licence is refused.

### 3. Bundle economics

- The standalone comparison prices every program the version includes by default (`included_by_default`). Each is
  priced with D5018's `recommendProgramFee`, from the same index, and in the version's own item order.
- The included programs come from the version's frozen `program_package_items`, never the live registry. So a program
  added since does not change a version's price or its comparison.
- For each recommendation the answer gives:
  - the package price;
  - each program's standalone price, with the reference-price version it used;
  - their sum;
  - the absolute saving;
  - the discount in basis points (`saving × 10000 / sum`, rounded half up).
- **No global discount is configured.** The discount is derived from the version's own base, as the issue allows.
- **Price above the standalone sum.** When the package costs more than its programs bought one by one, the answer sets
  `bundle_value_warning` and `bundle_premium_cents`. The saving and discount are then null, so it is never presented
  as a discount.
- **No fake zero.** A program with no reference price makes the standalone sum unknown, not smaller. The sum, saving
  and discount are null, and a `missing_program_price` warning names the programs. A program whose price cannot be
  worked out (for example a currency mismatch) gets `program_price_unavailable`.
- **Provisional market data.** When the snapshot's countries used provisional inputs, a `provisional_market_data`
  warning lists them, taken from the snapshot's own trace.

### 4. Frozen, and deterministic

- `package_pricing_recommendations` is append-only; triggers refuse every update and delete.
- Each row records:
  - the package version and the licence snapshot;
  - the model version, index and currency;
  - the base, recommended and guidance figures;
  - each program's standalone price and reference-price version;
  - the sum, saving, discount and warning flag;
  - the warnings and the trace;
  - the actor.
- `inputs_key` is a SHA-256 of every input: the licence, the snapshot, the package version and each program's
  reference-price uid. It is unique.
  - Asking again with the same inputs returns the row already made (`200`, `created: false`), and the audit records
    only the first.
  - So the same package version and country snapshot always answer the same recommendation.
- A country-data update reaches only recommendations made from a newer snapshot. A new package version or a new
  program reference price is a new input, so it makes a new row and leaves the old rows as they were.
- A draft package version is refused (`package_not_published`), because it can still change. A retired version can
  still be priced.

### 5. Routes

All are Super Admin, HQ only, ahead of the licence ledger's `/:uid` catch-all:

- `GET /api/admin/licences/:uid/package-pricing` is a preview and writes nothing. It prices every active package, or
  `?package=` and `?version=`, from the latest snapshot, or from `?snapshot=`.
- `POST /api/admin/licences/:uid/package-pricing/recommendations` freezes one. It needs the write bar and is audited
  as `package_pricing_recommended`.
- `GET /api/admin/licences/:uid/package-pricing/recommendations` lists the frozen ones, newest first, with an optional
  `?package=`.

### 6. Considered and not built

- **Writing the price onto the licence or an invoice.** #5024 is where a licence accepts a package version and its
  price; this decision stops at the recommendation.
- **A frontend panel.** The issue asks for the calculation and its provenance. The HQ package screens come with the
  offer flow (#5024), which reads these routes. No client method is added until a screen uses it.
- **A configured target discount per package.** The issue allows deriving the effective discount from the configured
  base, and doing so keeps one source for the price.
