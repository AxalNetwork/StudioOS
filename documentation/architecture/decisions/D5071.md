## D5071 — Fundraising readiness: exact fix routes, scores that mean what they say, freshness from input hashes (#5071)

- **Status:** Built, 2026-11-09 (Worker, one migration, a small frontend change).
- **Migration:** `202611091000_readiness_input_hash.sql` adds `readiness_scores.input_hash`.
- **Builds on:** D691 (the six computed checks), D891 (typed traction is stated), D1607 (PostHog is shown, never scored), D1610 (next steps).

### What was wrong

1. A readiness gap's step (the card's `next`, the checklist's Missing line) opened the generic Fundraising readiness page, so "Save an investor narrative version" did not open Narrative.
2. Three checks were existence checks: Pitch scored 10 from a deck row (an empty deck counted), Cap table from a scenario row (a scenario with no shares counted), Traction 10 from any one signal, including a typed number.
3. "Has this score gone stale" was inferred from each table's newest timestamp. A deleted row, a typed `projects` field and a 90-day window leave no newer row, so those checks had to re-score on every run, and a score could not be proved current.

### Fix routes

`readinessFix(ctx, key, score)` in `raiseCycle.ts` is the one table. The destination comes from the item key and what its score says is missing, never from the page the item is listed on.

| Item | Opens |
| --- | --- |
| Investor narrative | `/raise/investor-narrative/new` with no saved version; `/check` when the check found a difference or compared nothing; the module otherwise |
| Pitch deck | the Pitch Studio |
| Data room | the Checklist tab |
| Cap table | the cap table |
| Use of funds | Use of funds |
| Traction | Metrics |
| Team | the founding team |
| Product-market fit | Product-market fit |

The card's `next`, `nextSteps`, and each Readiness-items row (`cells.fix_href`) all use it. The raise-kit gap list on the Product-market-fit page links to `cells.fix_href` (only if it is an address inside the app).

### What each score means now

- **Pitch deck:** 10 only when the *current* saved version holds at least one card. A deck row with no current version, or an empty one, is 3. None is 0. The deck's preflight findings are computed per request and not stored, so they are not part of this score.
- **Cap table:** 10 for a recorded ownership (holders with shares in the issuance record); 6 for a saved model with founders and shares but no recorded holders (evidence Stated); 3 for a scenario with no shares in it; 0 for none. A read that fails is `Unavailable` (no score, no hash), never 0.
- **Traction (threshold and evidence quality):** 10 measured (connector-verified revenue from Stripe or Mercury, or a fresh measured MRR or paying-accounts figure); 8 documented (revenue backed by a proof document or a Mercury receipt; evidence Pattern); 5 stated (a typed figure or an unverified entry; evidence Stated); 0 nothing recorded. A stated figure can be recorded but not scored as proof. PostHog figures are shown beside the score and never count (D1607).
- Unchanged: Use of funds (raise target and a 100% allocation), Data room (checklist items with a downloadable file), Narrative (the consistency check), Team and Product-market fit (a person; the PMF engine).
- **Not recorded, Unavailable, zero and unscored stay four things.** A score of 0 is a real zero (no deck). A narrative with no version is not scored (no row), not 0. A check that cannot run is Unavailable. An item with no stored hash is "Not recorded".

### Freshness

Each computed check returns `input_hash`: SHA-256 of the canonical JSON (keys sorted at every depth) of the exact rows and fields it read. The deck hashes every deck row and its card list; Use of funds, the typed `projects` fields; Cap table, the ownership read; Traction, the proof fields, the revenue and metric rows including their freshness flag; Data room, the downloadable files with their checklist item and folder; Narrative, the newest version's figures and the metrics compared. `rescoreReadiness` stores the hash with the score.

- `since: 'last'` now re-scores an item only when it has no score, its score kept no hash, a fresh run reads other inputs (a different hash), or the check finds something other than the stored score. The two checks that read `projects` fields no longer re-score every time.
- The Readiness-items table has a Freshness column: **Current**, **Stale · its inputs changed**, **Not recorded** (no stored hash) or **Unavailable** (the check could not run). Not scored and person-scored items have none.

### Not covered

- A rescore is still run by a person (Re-score) or the existing triggers; freshness is shown on read, it does not re-score by itself.
- Pitch readiness does not read the preflight findings (not stored); the comment in `computeReadiness` says so.
- Existing stored scores have no hash and read "Not recorded" until their next re-score.
