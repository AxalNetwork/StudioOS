## D777 — The auto-fill foundation: a never-fill registry in the SPA and the Worker, refused at propose, accept and provenance

- **Status:** decided by S1, 2026-10-19 (#2102; task `X0` of D720's plan, #1874 §9, "Eadwyn drafts; you send"). Built in three PRs, per S1's comment on #2102. **Part 1 (this file's §1) is the never-fill registry.** Parts 2 (provenance naming its `ai_usage_logs` row and proposal) and 3 (fill into the open form only; placements accepted one by one) add their own sections.
- **Basis:** `origin/main` at `a0309f6`. Worker paths are relative to `cloudflare-worker/src/`.

### 1. The never-fill registry (part 1)

1. **One registry, two copies.** `frontend/src/lib/neverFill.js` and `services/fills/neverFill.ts` hold the same `NEVER_FILL_RULES` and the same matcher. `test/never_fill.test.ts` compares the rules value for value and the two matchers' answers field by field, so neither copy can change alone.
2. **Four kinds of field**, each a rule:

   | Category | Label | Examples |
   | --- | --- | --- |
   | `signature_consent` | Signatures and consents | `signature`, `signed_at`, `marketing_consent`, every column of `channel_consents` |
   | `payment_amount` | Money amounts on a payment | `refund_amount`, `amount_cents`, every column of `fund_capital_calls`, `fund_distributions`, `payouts`, `entity_bank_accounts` |
   | `identity_number` | Identity numbers | `ssn`, `tax_id`, `passport`, `iban`, `routing_number`, every column of `kyc_partner_imports` |
   | `legal_attestation` | Legal attestations | `attestation`, `accredited`, `sworn`, every column of `capital_attestations` |

3. **How a field is named and matched.** A field is `table.column` (what a fill kind's `target()` and `fill_provenance` record) or a bare form-field name; names fold to snake_case. A rule refuses every column of the tables it lists, and any column whose name contains one of its tokens **as whole words**, so `sin` never refuses `business` and `consent` never refuses `consentient`.
4. **Where it is enforced.**
   - **Propose** (`POST /api/founder/validate/propose/:projectId`): a proposal whose target is listed is not stored, and is counted in `refused` as "a field Eadwyn never fills".
   - **Accept** (`POST /api/founder/validate/proposals/:id/accept`): checked before `apply`, so nothing is written. A listed proposal, stored before its field was listed, is set to `discarded` and answered `422 { refusal: 'never_fill' }` with the registry's sentence. It is not put back to pending, because it can never become acceptable.
   - **Provenance** (`recordFill`): refuses a listed target before it touches D1. Every fill path ends there, so a path added later that forgets the first two still cannot record Eadwyn as the author of such a field. `recordCompositionFills` (brand Save) skips that row and keeps the member's own save.
   - **The band** (`FillProposals.jsx`): the proposals list now names each proposal's `field`, and the band holds back one the SPA's registry lists, with the registry's sentence, instead of drawing Accept. Its accept refuses one too.
5. **Nothing filled today is refused.** The test runs every current kind's target and every `landing_pages` column (read from the migrations) through the registry, and each passes.
6. **No migration.** Part 1 adds no columns.

### 2. Provenance names its run (part 2)

1. **The run is the `ai_usage_logs` row it was recorded under.** `aiRun` (`services/aiRouter.ts`) returns `usageLogId`: the id of the row its answered run wrote, on the uncached path and on both cache-hit paths. The guard's own rows name that row in `guard_for` (D763). The id is null when the row could not be written. It is absent on a refusal, and on a stream, which records its row when the stream ends.
2. **The proposal keeps it.** Migration 503 adds `validate_proposals.ai_usage_log_id`. The propose route (`POST /api/founder/validate/propose/:projectId`) stores the run's `usageLogId` on every proposal it stores from that run.
3. **The accepted value keeps it, with its row.** Migration 503 adds two columns to `fill_provenance`, and the accept route copies both from the proposal:
   - `ai_usage_log_id`, the proposal's run;
   - `target_row_ref`, the proposal's `target_ref`. This names the row where `target_row_id` cannot, such as a competitor row recorded as row 0.

   `recordFill` takes `usageLogId` and `targetRowRef`. A path that passes neither, like brand Save's `recordCompositionFills`, writes both as NULL.
4. **The read answers the run.** `fillsForRow` returns each newest fill with `run`. It is `{ usage_log_id, rail_page, rail_option, charged_microusd, est_cost_usd }`, read from that usage row (D762's columns), or `null`.
   - `null` covers a fill with no run, a row that has gone, and a usage log that cannot be read. All three read as "Not recorded", never as a zero cost.
   - The run's page and option are the ones the propose route passed (`fill:<kind>`, D765).
5. **A database from before 503 heals at runtime.** `ensureFillProvenanceSchema` and `ensureProposalRunColumn` add the columns once per binding, with migration 503's exact DDL (D235: the migration is the declaration).
6. **Not yet: `ai_proposal_id`.** D720's pointer at `ai_rail_proposals` lands with #2105, which builds that table. Part 3 (fill into the open form only; placements one by one) adds its own section.
