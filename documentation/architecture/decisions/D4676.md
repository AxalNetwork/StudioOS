## D4676 — One Pipeline access policy for every door, and an open socket that ends with its session (#4676)

- **Status:** Built, 2026-11-10. Pipeline audit 1 of 6 (P1). Production behaviour is **unverified**: nothing here was checked against the live deployment.
- **Builds on:** D889 (#2438, partners are outside members; `services/projectAccess.ts`), D4472 (licences held independently of one scalar role), D4669 (the realtime upgrade asks `sessionStanding`), D4673 and #4768 (client names read through `founders`).
- **Followed by:** #4705 (Pipeline audit 6 of 6) waits on this.

### What was wrong, on current `main`

- **List and detail disagreed.** `GET /api/pipeline/active` returned every project to any signed-in account that was not a founder, with each card's latest metrics, decision-gate recommendation and task counts. `GET /projects/:id/detail` refused the same accounts.
- **Writes were not held to their venture.** Advance, MVP tasks, metrics snapshots, the gate review and the gate decision checked a scalar role (`admin` or `partner`) and never the project. A task was changed by its id alone.
- **The realtime room was wider than both.** The per-deal door admitted any partner or investor to any deal, and the board events on the shared channel went to every partner and investor socket.
- **An open socket outlived its session.** The upgrade asked `sessionStanding` (D4669), but once open a socket received events until the browser let go, whatever happened to the account or its session.

### The policy (`services/pipelineAccess.ts`)

One function answers four named capabilities on one project, from the project rule D889 already defined:

| Capability | Who |
|---|---|
| `read` (list, enrichment, detail, the per-deal room, every board event) | an admin; the founder who owns it; an accepted project member (owner, co-founder or advisor). An account holding only the investor licence reads nothing here; its view of a venture stays the masked, NDA-gated one on the project routes. |
| `edit` (MVP tasks, metrics snapshots) | an admin, or a partner-licence holder who is an accepted owner or co-founder member of this venture |
| `review` (opening a gate review, advancing the stage) | the same |
| `spinout` (deciding the gate, whose `passed` moves the venture to spin-out) | the same |

The three operator capabilities are named apart because they are different acts; today one rule answers all three. It is the rule the route always had (admins and partners), now held to the target project.

**Nothing here widens a write.** A partner used to write to every venture and now writes only where they are a member; a founder wrote to none and still writes to none. Reads follow the project rule, so a member reads their venture's pipeline as they already read the venture.

**Licences, not one role.** Every check reads the licences an account holds. An account that is a founder and a partner keeps both: its own ventures to read, and the ventures it is a member of to read and, as a partner, operate. It does not operate a venture it only owns.

**Creating a project** has no target yet, so it keeps the operator rule (an admin or a partner-licence holder), read from licences rather than the scalar role. In the product a partner's `/pipeline` is their own business pipeline, not this board, so no screen depends on it.

### Applied to every door (`routes/pipeline.ts`, `routes/realtime.ts`)

- The list is drawn from exactly the readable set (the founder profile owned through, still narrowed to the active company, united with accepted memberships), so its page, its `total` and its enrichment all come from the set the detail admits. A test checks, for every principal and every venture, that a venture is on the list if and only if its detail opens.
- A per-project act goes through one door (`projectFor`): 404 when the venture does not exist; for a read the account may not make, 404 too, so the read does not confirm it exists; for a write, 403 `pipeline_forbidden` naming the capability.
- A task is changed through its own venture's rule, and the `UPDATE` is bound to that venture.
- The gate review checks the venture before it spends the caller's AI quota or a model run.
- The per-deal realtime door admits by `read` on that deal, and answers 404 otherwise.

### An open socket (`services/pipelineRoomAudience.ts`, `durable-objects/pipeline-room.ts`)

The upgrade now forwards the token's session facts (issue time, session row, support-session record, operator; identifiers only) to the room, which keeps them on the socket. At every event, for every socket:

1. the account must still be active and its session must still stand, by the same `sessionStanding` the HTTP path and the upgrade use. A socket that fails is **closed** (4401), not merely skipped. A socket opened before this change carries no facts; it is closed once and the client reconnects with them, and a reconnect whose session no longer stands is refused at the upgrade;
2. a personal notification goes to its recipient only, as before;
3. a vote tally goes where it always went (admin, partner, investor): `GET /votes/:deal_id` already answers it to any signed-in account;
4. every other board event names a deal and goes only to a socket whose account may `read` that deal; an event that names no deal goes to admins only.

Each account is read once per event, so a busy room costs one standing check per viewer.

### Client identity

D4673 and #4768 already moved every client-name join in Delivery, Pipeline, Research and Offers from `users` to `founders` (`founder_needs.founder_id` and `engagements.founder_id` are `founders.id`). Re-checked on current `main`: no Worker file joins `users` on a `founder_id`, including the files that build AI context. This adds a **Worker-wide** guard so the next file cannot reintroduce it, where the earlier guards each covered named files.

Pipeline's own ownership check compares `users.founder_id` with `projects.founder_id`. The fixtures include an account whose user id equals another founder's profile id, and it owns, lists, opens and receives nothing by that coincidence.

### Not changed here

- Who may create a pipeline project (above).
- The vote tally's audience (above).
- The frontend. A detail read that is refused now answers 404 rather than 403; both callers (`PipelinePage.jsx`, `FounderBuildBoard.jsx`) catch any refusal and show their own "did not load" sentence, so nothing on screen depends on which status it was.
