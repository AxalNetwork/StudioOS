## D1102 — Data-room owner access, audited support reads and NDA uploads

Part of #2982 and #2456. The owner chose to include the shared cycle-record
access gate in #2982; #2983 retains the file-versioning work.

The founder-side data-room routes now require the venture's founder, retaining
company scope and the deleted-project check. Admin status is not ownership.
The data-room record module uses the same owner-only rule for reads, activity,
form options and actions. Other Raise modules keep their existing rules.
Legacy investor grants do not give admins an alternative route to room details
or download tokens.

An admin's ordinary room read returns scoped aggregate file, folder, checklist
coverage and grant counts. It contains no file/folder names, investor identities,
access rows or storage keys. Coverage means recorded checklist tags, not proof
that an investor can open the files. A failed aggregate is unavailable on its
own, and the existing files tool displays “Unreadable” with Try again rather
than inventing a count or showing owner controls.

`POST /api/data-room/:projectUid/support-read` requires an admin and a trimmed
reason of 1–500 characters. Before reading private details it must record an
activity row under the uniquely identified founder's user ID, with the admin
as actor and the reason in details. The founder can read that row through the
existing activity API. Missing/ambiguous owners and failed audit writes refuse
support access. `logAdminAction` also records the support read for HQ. The
response is read-only and grants no persistent capability; founder-side room
mutations and shared record writes remain refused after a support read. The dedicated support UI is outside this
part and is not claimed as shipped.

Both upload doors start with NDA on: the files tool's checked default now
matches the module form, and an omitted gate on the Worker upload defaults to
`nda`. A founder can still intentionally choose `open`.

## Part 2 (#2982): the deck's explicit NDA choice and the Raise data-room paths

### Migration 608: the founder's NDA choice

`projects.data_room_nda_required` is `NOT NULL DEFAULT 0`, so an untouched 0
cannot be told from a No. SQLite cannot drop NOT NULL in place. `projects`
cannot be rebuilt the way migration 558 rebuilt a leaf table: dozens of tables
reference it, many `ON DELETE CASCADE`, and no migration in the repo drops a
column. So `608_data_room_nda_choice.sql` adds the house pattern's nullable
column, `projects.data_room_nda_choice INTEGER CHECK (IN (0, 1))`: NULL is not
chosen, 1 is Yes, 0 is No. It applies to a fresh build (the baseline, then every
migration above the cutoff) and to the live shape (608 after 609).

The backfill is S1's legacy rule: a stored 1 stays 1, and a stored 0 becomes
NULL. Both run in the protective direction. No deck loses an NDA it showed, and
no untouched default hides one the room requires.

Nothing reads the old column for the choice. The two writers mirror each
explicit choice into it, so a Worker rolled back to before 608 still reads every
choice made since. A choice a rolled-back Worker records lands only in the old
column, and is not read after the roll-forward.

**The read.** The deck (`services/decks/axalSpinoutDemoDay.ts`) asks
`services/dataRoomNda.ts`:

- the founder's choice, when there is one;
- else true when any file an investor can be admitted to is gated `nda`.
  "Admitted to" is `tierAdmits()` asked for the most an investor can hold
  (committed, every folder): a tier of `invited` or `committed`, inside its
  access window. A file shared with nobody, or whose window has closed, asks
  no one for an NDA;
- else null when the room's files cannot be read. `spinoutDeckData.ts` then
  shows "Unreadable", never "Not required".

The incorporation-step fallback is gone. `readableRoomFiles()` is not used for
this: it counts an `nda` file only once a granted investor has signed, so it
would answer No for exactly the room that needs an NDA. Project detail reads
`data_room_nda_choice`.

**The writes.** Every explicit choice is stored, Yes and No.

- `PUT /api/projects/:id` takes `data_room_nda_choice` as `true`/`false` (or
  1/0). Anything else is 400 `invalid_nda_choice`, with nothing written. The
  old `data_room_nda_required` key is no longer taken: an open tab on an
  earlier build re-sends it unchanged on every save of the section, which
  would store an untouched default as a No.
- `PUT /api/decks/:id` stores the deck's NDA flag only when it differs from
  the saved version's. Every save carries the flag the deck was built with,
  and that echo is not a choice. Keeping a "Fill from project" proposal writes
  a version without a choice.

**The page.** Project detail's Data room section shows Yes and No radios in
place of the checkbox. While unset, neither is selected, and the section says
"Not chosen yet. Until you choose, the deck asks for an NDA when any file you
share with investors is NDA-gated." A save sends the choice only when the
founder picked one that differs from the stored one, so saving the URL alone
never records a No.

**No clear back to unset.** The owner's answer names none, so neither the route
nor the page offers one. A founder who has chosen can change Yes to No, but
cannot return to the derived default. If the owner wants that, it is a small
follow-up: a third option on the page, and `null` accepted by the route.

`PUT /api/projects/:id` keeps its existing editors, admins included, so a choice
an admin sets there is stored as the venture's choice. That route's access rule
is outside D1102.

### `cycle_raise.ts`: the data room's paths answer its owner

The data-room module, overview and checklist paths use D1102's
`dataRoomOwner()`, as `routes/data_room.ts` and the shared record module do.
`scope()`'s `canWrite` admits an admin, so without this an admin was treated as
the owner. Every other path in the file keeps its rule.

- **`GET /overview`.** The owner gets the owner's card. Anyone else the
  overview admits gets the room's summary as the data-room card: an admin, and
  also an admitted Lab member on their own venture whose account role is not
  `founder`. The summary is `data_room.ts`'s `roomSummary`, with four rows:
  Files, Files gated by NDA, Checklist items with a tagged file ("n of 12") and
  Active grants. A block that cannot be read says "Unreadable" on its row, and
  all of them failing makes an unreadable card. It proposes no action. The
  owner's card query, which names who opened the room, never runs for a
  non-owner. The other six cards and the figures are unchanged.
- **`GET /modules/data-room`.** An admin gets 403 `support_read_required`, the
  code D1102 gives `/shared`. Anyone else who is not the owner gets 403. Both
  are refused before any data-room table is read. CycleRoute draws a 403 as
  the Worker's sentence, with no Retry.
- **`PUT /data-room/files/:id/checklist`.** Anyone but the owner gets 403
  `Forbidden`, as the shared record door refuses a write. Nothing is written
  or logged.

One limit: Try again on an unreadable summary card re-reads that card through
the module read, which refuses an admin. For an admin it does nothing; the
overview's own retry still works.
