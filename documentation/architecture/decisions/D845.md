## D845 — A member's own usage reports over `api_usage_events`: groups, history, tenant checks

- **Status:** decided by S1 for the owner, 2026-10-21 (#2471; part of #2463). Built by S09.
- **Basis:** #2489's branch (D843, migration 524) on `origin/main` at `56c2498983`. Paths are relative to `cloudflare-worker/` unless they say otherwise.
- **Migration:** none.

### What is built

1. **`GET /api/developer/usage`** (`src/routes/developer_usage.ts`, `src/services/apiUsageReport.ts`) takes `?from&to&group&by&key&cursor` and returns:

   ```
   { recorded, recorded_since, range: { from, to }, group, by, key,
     totals: Stats, groups: [ { key, label, by_key?, by_label?, ...Stats } ], next_cursor }
   Stats = { calls, ok, errors, refused, rate_limited, insufficient_tokens, error,
             charged_microusd|null, refunded_microusd|null, metered_calls, p50_ms|null }
   ```

   - `group` is `day` (the default), `key`, `provider`, `connector`, `tool` (the operation) or `model`.
   - `by` is `key`, `provider`, `connector` or `tool`, and only with `group=day`. Each group is then one cell, a day and a second key.
   - `errors` is every call that did not succeed: `refused + rate_limited + insufficient_tokens + error`. A call whose `error_category` is `insufficient_tokens` counts there and nowhere else, whatever its outcome.
   - `totals` cover the whole range, not the page, and equal the sum of every group's counts and known amounts.
   - Groups are 100 a page, days in order and every other grouping by calls, most first. `next_cursor` is `g<offset>`.
   - `recorded` is whether the member has any row at all. `recorded_since` is the first day the table holds any row, anyone's: recording started then for everyone, so a chart can say "Not recorded before [date]". It is a date, nothing else.
   - A `key` group's `label`, and a `by=key` cell's `by_label`, is the key's name from the member's own `member_api_keys` (D841). The calls made without a key form one group whose key and label are NULL. The other groups' label is their key.
2. **`GET /api/developer/usage/events`** takes `?from&to&key&outcome&surface&operation&provider&connector&company&cursor` and returns `{ range, events, next_cursor }`, newest first, 100 a page.
   - Each event: `execution_id, created_at, surface, operation, outcome, error_category, duration_ms, api_key_uid, grant_id, client, company_id, model, provider, connector, reservation_uid, reserved_microusd, charged_microusd, refunded_microusd`. Never an argument or a result: the table has none (D843).
   - `outcome` filters and reads with `insufficient_tokens` as above, so the five words split the calls with no overlap.
   - The cursor is an opaque `(created_at, id)` pair. `id` breaks ties within a second, so paging never repeats or skips a row.
3. **Ranges** are UTC days, both ends included: at most 92, and the last 30 up to today when none is given. A malformed day, a range that ends before it starts, or one over 92 days is a 400 with the sentence the page prints.
4. **`GET /api/developer/usage/keys`** (scope 3) takes `?month=YYYY-MM`, this UTC month by default, and returns `{ month, near_limit_percent: 80, keys: [ … ] }`. It lists every one of the member's keys, live or not, newest first. Each key carries:
   - `uid, name, key_id, live, expires_at, revoked_at`. There is never a hash or a secret.
   - `monthly_limit_microusd`: the member's own cap for the key (D841). NULL means no per-key cap.
   - `calls`, `charged_microusd` and `metered_calls` for the key's calls that month. The charge is worked out as in the reports, so it is NULL when nothing was metered.
   - `used_percent`: the whole percent of the cap used, rounded down.
   - `alert`: `at_limit` at 100% or more, `near_limit` at 80% or more, else NULL.

   Both `used_percent` and `alert` are NULL with no cap or no metered charge. A key with an unknown charge is never shown as 0% used. The comparison is in integers (`BigInt`), so it is exact for any two safe amounts; float arithmetic would round one micro-USD under 80% of the largest cap up to 80%.

   This read reports only. Enforcing the cap, and the alerts' store, route and notification, are #2472's (D849).
5. **`frontend/src/lib/api/developerUsage.js`** (`developerUsageApi.report`, `.events`, `.keys`), its own module beside #2464's `developerKeys.js` (D527).

### Tenant checks

- **Every statement is `WHERE e.user_id = ?`** with the session's user. No parameter can widen it.
- **A hold is joined only when it is the same user's** (`r.user_id = e.user_id`). A row naming someone else's hold reads as unmetered.
- **A `key=` is re-checked before it narrows anything.** `ownsKey` reads `member_api_keys` with the session's user (`ownKey`, D841). A key that is not the member's answers `404 unknown_key`, with the same body as a key that does not exist, so another member's key cannot be confirmed. A key of theirs with no calls yet, or a revoked one, reads normally.
- **The month read** lists `member_api_keys` rows `WHERE k.user_id = ?`. It counts only the same user's events and holds, so a row of another member's naming one of these keys' uids is never added to it.
- **Sessions only.** `requireAuth`. The reads change nothing, so a support session may read them.

### Money

- **A row's charge** is its settled hold's (`actual_included_microusd + actual_topup_microusd`, status `settled` or `refunded`) when it names one. A hold still `pending` or in `review` has charged nothing yet, so the charge is NULL. A row with no hold keeps its own `charged_microusd`: NULL until metering (#2466) writes it, or a known 0 for a free tool (D844).
- **Refunded** is the hold minus the charge, from a settled hold only; NULL otherwise.
- **Sums** are SQL `SUM`, which skips NULLs and is NULL when every row is. `metered_calls` says how many calls the sum covers, so a page can say "3 of 5 calls metered" rather than show a partial sum as the whole.
- **`provider_cost_microusd` is never in a member response.** It is HQ's (#2481); this table does not carry it, and the test asserts no response mentions it.

### Static SQL

The grouping is a bound `CASE ?1 WHEN 'day' THEN … END`, not a spliced column name, so every statement is one literal with bound parameters. The totals are the same statement with the group bound NULL, which makes one group of every row. No raw interpolation is added, so `schema_guards` stays under its limit.

### p50

The issue asks for an ordered `LIMIT`/`OFFSET` subquery per group. SQLite does not let a correlated subquery's `OFFSET` read the outer group's count, so the median is a window instead: `ROW_NUMBER() OVER (PARTITION BY g1, g2 ORDER BY duration_ms)` and the group's count, taking row `(n + 1) / 2`. That is the same value, the lower median for an even count, in one pass. A group of fewer than 5 calls has a NULL p50.
