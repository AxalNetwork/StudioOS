### 1. The one handoff store (migration 582)

`build_handoffs` is StudioOS's record of the founder's own press of Send to…. It is never a claim that the tool built anything.

| Column | What it holds |
| --- | --- |
| `uid`, `project_id`, `provider` | `lovable`, `github`, `notion` or `vercel` |
| `module`, `record_table`, `record_id` | The module when every item shares one; the landed row when the press sent one item |
| `plan_item_uids` | A JSON list. Empty for #2398's launch from a module page |
| `target` | The repository, `lovable.dev`, or null for a copy |
| `prompt_text`, `prompt_chars`, `text_hash` | The text as sent, its length and its SHA-256. All three are null for a Vercel import, which carries no text: unknown, never 0 |
| `marker` | The markers planted, space-separated |
| `opened_by`, `opened_at` | Who pressed, and when |

- **#2398's Lovable launch link writes here** with `provider = 'lovable'`, and has no table of its own (D1063's cross-check).
- **The text is the venture's team's only.** `GET /handoffs` returns it to the venture's founders. Admins and partners read the row without it.
- **Logs keep ids and codes, never text.** The one log line is `[build-handoff] recorded` with the provider and two counts.

### 2. `POST /api/cycles/build/plan/handoffs?project=&scope=`

The body is `{ provider, items, repository? }`. Only the venture's founders may press it, through D1065's `context(c, true)`.

- **What may be sent:**
  - 1 to 50 items from the venture's current plan, each accepted (or edited and accepted) and landed;
  - not a Connect door, which is opened, never sent;
  - and not while the plan is paused.
- **The text is built on the server.** It uses only what the plan holds:
  - each item's accepted payload: title, description, a test's target and method, a risk's mitigation;
  - its evidence labels with their source words;
  - the brief: audience, problem, promise, what makes it different, what it replaces;
  - for Lovable, the founder's kept Eadwyn wording (D1071).
- **What the text never holds:**
  - a transcript, a quote, a pending proposal or a name typed by anyone else;
  - the decision, which only the founders read (D693): its evidence line is left out.
- **Per tool:**

  | Tool | Out | Recorded |
  | --- | --- | --- |
  | Lovable | One prompt for the items: the opening (or the kept wording), the brief, "Build:" with each item, then one marker line per item. Returned as `text` and as Lovable's prompt link, `https://lovable.dev/?autosubmit=true#prompt=…`. The prompt rides in the fragment, which reaches no server. Over 4,000 characters (VB6's counter) is refused as `too_long`, with the count. | One row, `target = 'lovable.dev'` |
  | GitHub | One issue per item: its title, its body (detail, then "Why this is on the plan (from Validate):" and the evidence lines, then the marker line), and `https://github.com/<repo>/issues/new?title=…&body=…`. Also every issue as Markdown ("Copy all as Markdown"). With no repository, `url` is null and only the Markdown is given. | One row per item, its own marker |
  | Notion | One Markdown page per item (`# title`, then the issue body), and all of them joined. | One row, `target` null |
  | Vercel | Vercel's import page for the repository, `https://vercel.com/new/import?s=…`. No text, so no marker: a deploy is read back through the linked must-have. | One row, no text |

- **The repository.** It must be one the founder picked on their GitHub connection for this venture (`integrations.config_json`: `repositories` and `project_id`). Otherwise it is refused as `repository_not_picked` (403). Vercel needs one (`invalid_handoff`).
- **The privacy check.** Every text runs through `lintForSend` (`services/telegramRedactCheck.ts`), the check HQ's X posting and Telegram use, with #2411's fix (PR #2625), so a member's full legal name matches as well as an email.
  - It runs as `public`, because the text leaves StudioOS. Any member it finds, consented or not, is a finding.
  - **The markers are masked before the scan.** Each is scanned as a same-length placeholder, because 32 hex digits read as a phone or card number. Without this, a send would have been refused at random.
  - A finding refuses the send with `pii_found` (422) and `findings: [{ kind, in }]`. `in` is the item's uid, or `prompt`.
  - The matched words are never returned or logged. The founder edits the item and sends again.
- **Nothing is written on a refusal.** Every check runs first. Then the rows and one activity line ("2 plan items sent to GitHub", `build_plan_handoff`, under the first item's module) are one batch.
- **Nothing is sent by StudioOS.** The response is a link the founder opens or text they copy. No AI sends.

### 3. The marker

- **Each plan item already has its marker** (`build_plan_items.marker`, D1065, unique per venture). It is `VB-` followed by 32 hex digits.
- **Every text plants "Axal VC plan item VB-…"** for each item it carries (`MARKER_LINE`).
- **The full marker is used, not the canvas's four-character sample** ("VB-7K2Q"). It cannot collide within a venture, and it is the stored value D1065 made.

### 4. Back in: D782's feed reads the marker

- **Where.** `syncGithub` reads the bodies of the new issues and pull requests on each page (`markerLinks`), those not already in the `connector_fed_items` ledger.
  - It costs one read when a body names a marker and two when one is known. A page with no marker costs nothing.
- **When a marker is known** (its item is on this venture, accepted and landed), `issueStatements` and `pullStatements` write no roadmap item and no must-have. Instead they write:
  - the ledger row, unlinked (`local_id` null), so no later sync makes a second row;
  - a link proposal: an `ai_rail_proposals` row with `rail_option = 'link:build/plan'`, `source_kind = 'connector'`, `source_ref` the fed item (`issue:owner/repo#n`) and `source_label` "Connector".
    - It is filed for the connection's owner, the founder.
    - Its payload is the plan item, the marker, the fed kind and its GitHub title.
- **Never twice.** One proposal per fed item, guarded in the INSERT. The sync reports `link_proposals`.
- **An unknown marker, or none,** lands as before.
- **`GET /links`** lists link proposals and links. A partner sees links only, never a pending proposal (D1063 §4).
- **Link** (`POST /links/:uid/accept`).
  - The proposal is accepted, with one activity line (`build_plan_linked`).
  - The fed item's ledger row is pointed at the plan's row **only when the tables agree**: an issue to a roadmap item (`roadmap_okrs`), a pull request to a must-have or feature (`mvp_features`).
    - `github.ts` and `github/mvp.ts` write their table by the ledger's `local_id` alone. A ledger row pointed at another table would make GitHub update an unrelated row with the same id.
    - So an issue linked to a feature is recorded as a link, and GitHub's state is not followed into the feature.
  - A pull request linked to its must-have follows it from then on: Planned, In progress, Built (D782).
  - If the plan item is no longer accepted and landed, it is refused as `marker_unknown` (409), and the proposal stays open.
- **Not this one** (`POST /links/:uid/dismiss`).
  - The proposal is discarded and the unlinked ledger row removed, so the next sync lands the item as its own row.
  - A discarded link is never proposed again.
- **A link by hand** (`POST /items/:uid/link`, `{ fed }`) links a fed item with no marker to an accepted item, recorded as an accepted link (`by: 'hand'`).
  - The ledger is re-pointed only while the fed item is unlinked. A row the feed already made stays as it is, and the founder deletes it if it was a duplicate.
  - `already_linked` (409) when that item is linked or waiting.
  - A fed item that has not arrived on the venture is a 404.
- **Who.** Every decision is the venture's founders', as Accept is (D1066).

- **Refusals and readers:**
  - an item not accepted;
  - a bad provider or item list;
  - another founder, an admin, a partner or no session;
  - a paused plan;
  - the text returned to the founder and never to an admin or partner.
- **Back in.**
  - Marked issues and a marked pull request become three link proposals, and unmarked or unknown-marker items land.
  - A second sync adds nothing.
  - Link on an issue points the ledger at the roadmap row; on a pull request, at the must-have. An issue linked to a feature leaves the ledger unlinked.
  - GitHub's next sync updates the linked row.
  - The partner's list shows links only.
- **Not this one** lands the item on the next sync and never proposes it again. A plan item no longer landed is `marker_unknown`, with the proposal still open.
- **A link by hand:**
  - refused for an item not accepted, a malformed or unknown fed item, and another founder;
  - recorded once, then `already_linked`;
  - the feed's own row keeps its ledger.
