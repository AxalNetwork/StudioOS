### 2. A record scope beside the venture's

`GET /api/fills/sheet`, `POST /api/fills/record`, `POST /api/fills/rows/accept`, `POST /api/fills/:id/undo` and the `form` handler of `POST /api/ai/rail/run` all required a venture. The other profiles' records do not sit on one. `services/fills/scopes.ts` adds RECORD_SCOPES beside it. Each entry is one literal read and its own route's write check:

| Table | Who fills it | Who reads its marks | The route whose check it keeps |
|---|---|---|---|
| `advisor_services` | the advisor, on their own service | the same advisor | `routes/advisors.ts` (`requireMyAdvisor`) |
| `engagement_status_reports` | the partner on the engagement, until the report is sent | that partner, and the client founder it is sent to | `routes/partner_delivery.ts` (`requireOwnEngagement`; a sent report is frozen) |
| `events` | `canManage`: an admin, or the event's host | the same | `routes/events.ts` |
| `event_agenda_items` | `canManage` on its event | the same | `routes/events.ts` |
| `admin_publications` | an admin | an admin | `routes/admin_publications.ts` (`requireAdmin`) |
| `ic_decisions` | its author, while it is not decided | a voter, the firm's members, an admin (`icDecisionScope`'s predicate as one literal statement) | `routes/ic.ts` (`PUT /:uid`) |

**The requests.**
- A scoped request names `record` (an id). For an Add form, it names `parent` instead: an engagement for a new report, an event for a new session.
- **The advisor's own profile is never named.** A new service is filed under the caller's own profile, looked up as `myAdvisor` does.
- **`project` is not sent.** The reply carries `project: null` and `scope`, which is the record (`<table>:<id>`) or the parent (`<kind>:<id>`).
- **The venture's requests, replies and tests are unchanged,** because S22 builds `FillSheet` on them. The sheet's body is shared through `sheetReply`, a pure extraction. The D1325 and D1326 suites pass as they were.

**Proposals are filed under the scope** (`payload.scope`), not a venture:
- `POST /api/fills/record` keeps a proposal only when its scope is this record, or the parent the saved row now hangs under. That is how an Add form's Save is recognised.
- Accept all takes only the rows filed under the parent it names.

**Writes, reads and undo for these tables:**
- **Accept all for an agenda session** goes through `SCOPED_ROW_WRITERS`. It is `POST /api/events/:id/agenda`'s insert: a title, what happens, and the next place in the running order. Times, speakers and places are the host's.
- **Each scoped table's read** sits in `ROW_READS` (`SCOPED_READS`), bound on the id alone. It is reached only through the scoped branch, after the scope is checked.
- **Each column's undo** is `scoped`: it is bound on the row and the fill, after the route has checked the record's scope.

**Who gets what:**
- **A reader** gets marks and no trigger. They undo nothing: an undo answers 404, as a fill they cannot see.
- **A support session** gets no trigger, and is refused a keep, a run and an undo.
- **An Explorer** is refused `no_profile`, "Fill opens once you hold a venture or a profile." (AF22).

**No admin trigger on a decision or a member's record** (#2431 question 5, A):
- An admin fills events and publications, which are content they write.
- An IC memo is another member's decision record. An admin reads it with no trigger.
- An approval has no form Eadwyn fills. Approvals › Events' review answers 404 `unknown_form`.
- No member's table (`users`, `founders`, `advisors`, `partners`, `investors`) is listed.
