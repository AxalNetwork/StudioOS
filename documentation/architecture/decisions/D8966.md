## D8966 — Agent publisher part 5: reconcile unknown and abandoned publication reservations, unmounted (#8966)

- **Status:** built on `agent/claude/8966-publisher-reconcile`. It is the fifth slice of #5569 and follows
  `D5569.md` and `D5569-p2.md` to `D5569-p4.md`. The record is filed under this issue's own number (D4106).
  Nothing calls the code: there is no route, cron, queue consumer, Env binding or token minting.
- **Code:** `cloudflare-worker/src/services/agents/agentPublisherReconcile.ts`, with the test
  `cloudflare-worker/test/agent_publisher_reconcile_5569.test.ts`.
- **Migration:** `cloudflare-worker/sql/migrations/202611271849_8966_agent_publish_reconcile.sql` adds two nullable
  columns to `agent_publish_requests`: `reconcile_evidence_json` and `reconciled_at_ms`.
- **Not done here:** the owner's 2026-11-27 answers to D5569-p3 (the allowed-paths column, the Env flag and
  person-only ready). Those are separate slices.

### Why

D5569-p3 leaves a publication `unknown` once a write has begun and then timed out, hit a rate limit or lost its
response. The broker never replays such a row. A row can also stay `reserved` when the invocation that held it
died. Until a person or an adapter compares GitHub with the record, these rows stay unresolved. They also count
against the tenant's cap of 100 pending rows (`reserved` plus `unknown`), which the broker checks on insert and
retry. D5569-p3 requires this comparison before any production consumer is wired.

### What it does

`reconcileAgentPublications(env, ports, { limit })` reads at most `limit` rows (default 25, at most 100), oldest
first. A row is eligible when:

- it is `unknown`, or it is `reserved` and abandoned; and
- **`RECONCILE_AFTER_MS`** (30 minutes) have passed since `last_outcome_at_ms`, or since `created_at_ms` when no
  outcome was recorded. When the row has a recorded `retry_at_ms`, that time is used instead.

The broker makes at most about a dozen 15-second requests per invocation, so a live invocation has ended well
before the deadline.

A `reserved` row that already has an outcome was re-opened by the broker's retry. The broker does not record when
that retry started. On first sight the reconciler therefore stamps `retry_at_ms = now + RECONCILE_AFTER_MS` and
reads nothing (`deferred`). It reconciles the row only after that time.

For each row, the platform's `transportFor` port returns a read-only transport scoped to that repository. It
follows the style of part 4: a fixed origin, `/repos/<owner>/<name>`, no redirects, bounded time and size, and a
throw when no response arrives. The reconciler keeps only the transport's `get`. It reads two things:

1. `GET /git/ref/heads/<head_ref>`. A 404 means the branch is absent. An answer for another ref name, or one
   without a 40-hex SHA, counts as unreadable.
2. `GET /pulls?head=<owner>:<head_ref>&state=all&per_page=100`. A listed PR whose head ref or head repository
   differs is ignored. A full page counts as more than one PR.

| GitHub holds | Row becomes | `retry_at_ms` |
| --- | --- | --- |
| A ref at the recorded candidate SHA, plus exactly one PR whose head SHA is the candidate, whose base is the row's target and whose `html_url` is `https://github.com/<repo>/pull/<number>` for this repository and number | `published`, with `pr_number` and `pr_url` | null |
| No ref and no PR | `refused`, evidence `absent` | `now` while `attempts < 5`, else null |
| Anything else: the ref is at another SHA, the ref is missing while a PR exists, there is no PR, there are several PRs, or the PR has another head, base or URL | `refused`, evidence `mismatch` with reason codes | null (a person decides) |
| No answer, a 5xx, a 401, a 404 on the PR list, a malformed body, or a transport for another repository | unchanged | +5 minutes |
| A 429, or a 403 that is a rate limit | unchanged | the time that part 2's `classifyGithubResponse` gives |
| A plain 403 | unchanged | +1 hour |

Every resolution stores `reconcile_evidence_json` (version 1) with the following fields:

- the outcome, the prior state and the check time;
- the ref name and SHA, and the recorded candidate SHA;
- the PR count, plus up to ten PRs, each with its number, canonical URL (empty when the URL is not canonical),
  head SHA, whether its base matches, open or closed, merged and draft;
- the reason codes: `ref_missing`, `ref_sha_differs`, `pr_missing`, `pr_multiple`, `pr_head_differs`,
  `pr_base_differs`, `pr_url_differs`.

The evidence never holds a title, a body, a credential or patch bytes. The branch is never deleted, and no PR is
created, closed or edited.

Every write is a compare-and-set on the row as it was read: id, state, attempts, `retry_at_ms` and
`last_outcome_at_ms`. If the broker moves the row in between, the reconciler writes nothing and reports `raced`.

### Review points

- **Absent means the broker may try again.** When nothing reached GitHub, the row becomes `refused` with
  `retry_at_ms = now`. The broker's existing bounded retry (at most five attempts) can then re-run the whole
  publication. That retry re-verifies the installation, the WorkIntent, the checks, the candidate and the base.
  It creates `agent/<task>/<attempt>` only if the ref does not exist; if the ref exists, GitHub answers 422 and the
  row returns to `unknown`. The reconciler itself never writes. Without this rule, a task whose publication never
  reached GitHub could not be published again, because the table allows one row per task.
- **A merged PR whose branch was deleted is refused** (`ref_missing`), even though its PR is real. The rule is
  strict on purpose: all four values must match. The evidence records `merged: true`, so a person can see what
  happened.
- **A PR that a person has marked ready or has closed still counts as published** when every recorded value
  matches. Draft state is recorded but not required, because only a person marks a draft ready (owner, 2026-11-27).
- **The reconciler takes no enable flag.** After a rollback turns the publisher off, the rows it left behind still
  need resolving (D5569-p3, "retain the receipt rows for reconciliation").

### Later gates

The consumer and its schedule, and a concrete read transport built on the broker's installation token, belong to
the slice that wires the publisher. That slice also brings the owner's answers and the write App (#8061).

**Rollback:** nothing calls the module, so removing the module and its test changes no data. The two columns are
nullable and additive, and nothing else reads them.

### Verification

The test uses real SQLite with the three publisher migrations, part 8071's budget migration and one synthetic
GitHub that the broker writes to and the reconciler reads from. It covers the following:

- A lost PR-creation response from the real broker is reconciled to `published`. The broker's replay then returns
  the receipt, makes no request and opens no second PR.
- Ten mismatch shapes are refused with evidence. The ref is kept and no retry is set.
- An absent row resolves with no write, both with retry left and with retries spent.
- Thirteen read failures (no response, 5xx, 429, secondary and primary limits, plain 403, 401, a 404 on the PR
  list, malformed bodies) leave the row unchanged, record the retry time, and are read again at that time.
- An unreadable installation and a transport for another repository are treated as unreadable.
- `reserved` rows: a fresh row before and after the deadline, and a re-opened row that is deferred first.
- A broker that moves the row during the read wins the race.
- 100 `unknown` rows fill the tenant's capacity; once reconciled, the broker can reserve and publish a new task.
- A listed PR for another head or repository is ignored, and a full page of 100 is never read as one PR.
- The batch is bounded and runs oldest first.

The synthetic transport also exposes `post`, `patch` and `delete`. The tests that reach GitHub assert that the
reconciler called none of them.

All 11 reconcile tests and the 51 existing publisher, broker, staging and installation tests pass with zero
skips. A mutation run over the module caught 35 of 35 injected regressions. Three of them add a write call:
creating the ref, deleting a mismatched ref and re-creating the PR. Seven accept a missing or mismatched ref,
or a PR with another head, base, URL, URL number or URL repository. The rest cover reading a 5xx as absent,
dropping the deadline or the compare-and-set, and leaving a mismatch retryable.
