## D666 — The StudioOS MCP server: OAuth for AI assistants, per-company grants, the read tools

**Issue:** #1496, part of #1495 (D665). **Slot:** S19, claimed by the S02 session at the owner's request. **Migration:** none: the grants live in KV.

StudioOS answers as a remote MCP server at `https://axal.vc/api/mcp`. ChatGPT, Claude, Gemini, Grok or any MCP client adds it by URL and signs in with OAuth 2.1. A founder approves each assistant for the companies they tick, sees every grant on Connectors, and can revoke it. Everything is behind `MCP_SERVER_ENABLED`, `"false"` in all three environments, and behind the `OAUTH_KV` binding, which is not bound yet.

### Where it differs from #1495, and why
- **No `agents` package.** #1495 named `createMcpHandler` from Cloudflare's `agents`. Every published `agents` release (to 0.28.0) pins `@modelcontextprotocol/sdk` 1.30.0, inside GHSA-6qxp-vccf-f47h (affects <1.31.0), so the worker's `npm audit` would go red, which the issue forbids. `createMcpHandler` is the SDK's web-standard Streamable HTTP transport in stateless mode, so this uses that transport directly from the patched SDK (1.32.1). The audit stays at 0, and `agents`' dependency tree (esbuild among it) is not shipped.
- **The validator is `@cfworker/json-schema`.** The SDK's default validator (ajv) compiles code with `new Function`, which Workers refuse.
- **The OAuth endpoints are `/api/oauth/*`, not `/authorize`, `/token`, `/register`.** They sit under `/api/*`, which `run_worker_first` already sends to the Worker, so no new pattern is needed for them. They sit outside `/api/mcp` because the provider treats every path under its `apiRoute` as a resource needing a token, and a founder reaching the authorize endpoint has none.
- **`[env.preview]` has no `[assets]` block,** so the two `/.well-known` patterns join `run_worker_first` in the two blocks that have one.
- **"Changing the password" is "signing out everywhere".** StudioOS has no password: sign-in is TOTP, passkeys and magic links. Every grant is revoked wherever the session floor is raised (`bumpJwtMinIat`: sign out everywhere, force re-auth, TOTP re-pairing, an email-change revoke), after the post-recovery re-enrolment, and on an account deletion request.

### The flag and the binding
- `MCP_SERVER_ENABLED = "false"` in the top-level, production and preview vars.
- `OAUTH_KV` is declared in all three blocks **commented out**, marked `OAUTH_KV-PENDING`, because the owner has not given the namespace id (#1495 asks). A binding without an id would break the deploy. The Worker treats a missing `OAUTH_KV` as off, whatever the flag says.
- **With either missing,** `/api/mcp`, `/api/oauth/*`, both `/.well-known/oauth-*` paths, the consent routes and the grants routes all answer 404, and the provider is never built.
- **To turn it on:** `npx wrangler kv namespace create OAUTH_KV`, paste the id into the three blocks and uncomment them, then set the flag to `"true"` after S1's review.
- `MCP_PUBLIC_ORIGIN` (optional) names the resource's origin, `https://axal.vc` by default, so a preview Worker can be connected from the MCP Inspector.

### The provider (`cloudflare-worker/src/mcp/oauth.ts`)
- `@cloudflare/workers-oauth-provider` 1.2.3: dynamic client registration, PKCE, RFC 8414 and RFC 9728 metadata.
- **PKCE is required, S256 only.** The provider refuses `plain`, and demands PKCE of public clients; the authorize endpoint also refuses a confidential client without it.
- Access tokens last 1 hour. Refresh tokens last 30 days and expire after 30 days idle (`refreshTokenIdleTTL`).
- The Worker's `fetch` sends these paths to the provider before anything else; every other path goes on exactly as before.

### Consent through the SPA
The SPA signs requests with a bearer token, not a cookie, so the Worker cannot see who is signed in on a redirect (`GOTCHAS.md`).
1. The authorize endpoint parses and checks the request, parks it in `OAUTH_KV` for 10 minutes under a random id, and redirects to `/connect/assistant?request=<id>`.
2. `GET /api/mcp/consent/:id` (signed in) returns the client's registered name, **its redirect host**, the scopes and the companies the caller may grant.
3. `POST …/approve` with `{ companies }` checks each company again, completes the authorization with props `{ userId, companies, clientName, redirectHost, grantedAt }`, and returns `{ redirectTo }`.
4. `POST …/deny` returns the `access_denied` redirect.
5. **A request id is single-use:** approve or deny deletes it and leaves a tombstone, so a second use is 409 and an unknown or lapsed id 410. KV has no compare-and-set; two answers racing inside KV's propagation window would both be the same signed-in user's.

**Nothing is auto-approved, ever.**

**"Companies" are projects the person owns or co-founds.** Validate is per project. Admins and partners pass `canAccessProject` for every project, so listing through it would offer staff every company; consent lists only owned and co-founded projects, and approve refuses anything else.

### Grants
- `GET /api/connectors/assistants`: client name, redirect host, companies, connected, last used ("last used" is the provider-less part: each successful tool call stamps `mcp_used:<grantId>` in `OAUTH_KV`). No token is ever returned.
- `DELETE /api/connectors/assistants/:grantId`: only the caller's own grant; it takes effect within about a minute across edges (KV propagation).

### The server and the tools
- **Stateless:** one `McpServer` per request on `WebStandardStreamableHTTPServerTransport` with JSON responses. No Durable Object.
- **The registry:** `registerMcpTools` in `server.ts`. #1497 adds the interview tools there.
- **Every call**, before the tool runs:
  - re-reads the user: a deactivated account, a deletion request, or a session floor raised after the grant refuses the call (a backstop if a revoke failed);
  - for a tool that takes a company, checks it is in the grant and still writable by the user;
  - counts against the grant's limit, 60 calls a minute, failing closed;
  - writes one `activity_logs` row (`mcp_tool_call`) with the tool, company, client and outcome. **Never the arguments or the result.**
- **The read tools** (`tools/context.ts`):
  - `list_companies`: the granted companies the user can still write to;
  - `get_validate_context({ company })`: hypotheses and status, pain themes and severity, ICP segments, open questions (untested, testing or inconclusive hypotheses), and interview counts. It reads Validate's own module records; customer research's records are not used, because they carry interviewees' names. **No interviewee name or contact is returned.**
  - `get_interview_guide({ company, hypothesis? })`: questions built by code from the open hypotheses and the strongest pain themes. The same input gives the same guide.
- **A result is data,** never an instruction. A refusal is a plain sentence, never an exception's text.

### The cost
The production bundle grows from 2.17 MB to 2.40 MB gzipped (the SDK, zod, the provider and the validator).

### Verified
`cloudflare-worker/test/mcp_server_d666.test.ts`, 12 tests, running the whole flow against the real provider over an in-memory KV (`test/_mem_kv.mjs`) and SQLite D1. The test loader gains a `cloudflare:workers` stub (empty base classes), which the provider imports.
- With the flag off, or with no `OAUTH_KV`, every path answers 404.
- An unauthenticated call gets 401, with `WWW-Authenticate` naming the protected-resource metadata.
- Discovery names `https://axal.vc/api/mcp` and S256 only.
- Consent refuses a company the caller cannot write to, a used request id and an expired one; staff are offered no company; deny carries `access_denied`.
- A revoked grant's token gets 401 on its next call. Signing out everywhere ends every grant, and a raised floor refuses a grant even when no revoke ran.
- A tool for a company outside the grant is refused, and so is one for a company the user has since lost.
- `get_validate_context` never returns the seeded interviewee's name anywhere in the response.
- The `activity_logs` row holds no argument text.
- The toml's two `run_worker_first` additions, the flag `"false"` three times, `OAUTH_KV` pending in all three blocks, `main` unchanged and no route.

**Mutations: 27 run, 27 caught.** Two escaped at first. Removing the PKCE check went unnoticed, because the provider demands PKCE of public clients; a confidential-client case now catches it. One mutation was a helper with no effect of its own and was dropped.
