## D767 — Pitch decks: "Fill from project" proposes a version the founder keeps or discards, and the deck's model calls run through the router

- **Status:** decided by S1 for the owner, 2026-10-19 (#2096; task `A8` of D720's plan, #1874 §9). PR 1 (`Part of #2096`) builds §1; PR 2 (`Closes #2096`) builds §2.
- **Basis:** `origin/main` at `4f7816e`. Worker paths are relative to `cloudflare-worker/src/`.
- **Rule it applies:** D720 §9: "Every AI output is a proposal or a draft. Nothing is sent, published, saved as final or written to a record until the member acts." D720 named the deck's fill as the breach: `POST /api/decks/:id/autofill` overwrote the open version's slides in place.

### 1. "Fill from project" proposes; the founder keeps or discards (PR 1)

1. **A fill writes a proposal, never a version.** `POST /api/decks/:id/autofill` builds the slides exactly as before (the Spin-Out demo-day branch and the template branch) and stores them as one `pitch_deck_proposals` row (migration 498). It changes no `pitch_decks` row: the `UPDATE pitch_decks SET slides = ?` the route ran twice is gone. The answer is `{ proposal, method_id, coverage_pct, slide_confidence, coverage? }`; it carries no `deck`, because none was written.
2. **Proposals live apart from the versions.** A proposal is never a `pitch_decks` row, so nothing that reads `pitch_decks` sees one: not the version list, share links, round calls, Raise records, the cycle's activity, or skill evidence. *Why a table and not a flag on `pitch_decks`:* a dozen reads of `pitch_decks` take "the latest version" or count versions, and each would have needed to learn to skip a proposal.
3. **One unkept proposal per project.** A new fill replaces the project's earlier unkept proposal; it was never a version, so nothing the founder chose is lost. `GET /api/decks/by-project/:pid` answers `{ versions, proposal }`, so the editor shows an unkept proposal again after a reload.
4. **Keep** (`POST /api/decks/proposals/:id/keep`) writes the proposal as the project's new current version through `insertVersion`, the same insert every save uses, then deletes the proposal. Earlier versions are left as they were (only `is_current` moves, as on every save).
5. **Discard** (`DELETE /api/decks/proposals/:id`) deletes that proposal and nothing else.
6. **Who may.** Keep and Discard check the proposal's project with the same `projectOwned` every deck route uses: another member gets 403 and nothing changes; an unknown or already kept proposal is 404.
7. **The editor** (`PitchDeckPage.jsx`) shows the proposal beside the current version, slide by slide (`components/DeckProposalPanel.jsx`, words and pairing in `lib/deckProposal.js`): "Filled from project · not kept yet", "Your current version is unchanged.", how many slides change, and Keep as new version / Discard. A fill no longer replaces the editor's deck.

**Tests (PR 1).**
- `cloudflare-worker/test/deck_fill_proposal_d767.test.ts` (5): the real router over node:sqlite tables from `schema_baseline.sql` plus migration 498, with no network.
  - a fill leaves every `pitch_decks` row byte-identical and stores one proposal;
  - Keep makes version 2 current with the proposal's slides and leaves v1 identical but for `is_current`;
  - Discard deletes only that proposal, not an older version and not another project's proposal;
  - a second fill replaces the unkept proposal, and another member's Keep and Discard are 403;
  - a source pin that the fill route has no `UPDATE pitch_decks` and no `insertVersion`.
- `frontend/test/deck_fill_proposal_d767.test.mjs` (3): the pairing, the panel, and the editor's wiring (a fill sets the proposal and never the deck).
- Mutations, each caught: the fill still overwriting (either branch), no replacement of an earlier proposal, Keep leaving the proposal, Discard deleting other rows, no ownership check, every slide marked changed, and a fill that still sets the editor's deck.

**Rollback.** Revert the PR. Migration 498's table is additive and stays; unkept proposals in it are never read.

### 2. The deck's model calls run through the router (PR 2)

1. **Both calls run through `run()`.** The deck draft (`aiSlides`, `routes/decks.ts`) and the slide fill (`aiBatchFill`, `services/decks/autofill.ts`, reached from Apply template and "Fill from project") no longer call OpenAI. Each is one router run on Workers AI, held, guarded (D763) and charged to the founder who pressed (D762). The prompts and their token and temperature limits are unchanged.
2. **The page's matrix row picks the model.** The task is `rail_vision`, the routeTask of "Founder · Raise · Pitch deck" in D764's matrix (`services/ai/railMatrix.json`: kind vision, Gemma 4 26B by default, Llama 4 Scout as the fallback). A test holds both call sites to the row. *Why not `dd_synthesis`, the deck reviewer's task:* #2136 shipped it while the matrix was not on main; the issue names the row, so a follow-up (`Part of #2096`) moved both calls to `rail_vision` once D764's matrix landed.
3. **The usage row says who and where.** `surface` and `rail_page` are `/raise/pitch` (a new `AI_SURFACE.raisePitch`, listed in D552); `rail_option` is `deck_draft` (the draft, and Apply template's fill) or `fill_from_project`; `record_ref` is `project:<id>`.
4. **Nothing to charge, nothing run.** A refused or failed run falls back exactly as a missing key did: `/generate` returns the heuristic deck, and a fill leaves the AI-only fields as placeholders. `autofillDeck` without a founder makes no run.
5. **Not covered:** `/positioning` (`routes/decks.ts`) still calls OpenAI; it is the deck page's third call, outside #2096's scope.

**Tests (PR 2).**

- `cloudflare-worker/test/decks.autofill.test.ts` moved from an OpenAI `fetch` stub to a Workers AI stub over a real ledger, its assertions unchanged; `ai_surface_d552.test.ts` lists the two call sites.
- Mutations: 6 of 8 caught; the two survivors are equivalent (dropping the `!who` check throws inside the `try` and still returns `{}`; dropping `!res.ok` changes nothing, as a refused run carries no output).

**Rollback.** Revert the PR; the calls go back to OpenAI where a key is set, and to the heuristic where none is.
