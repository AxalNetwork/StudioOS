## D780 — The admin's and Super Admin's options fill, draft and place through the run path, and their runs leave proposals in `ai_rail_proposals`, never in a record

- **Status:** decided by S1, 2026-10-19 (#2105; task `X3` of D720's plan, #1874 §9). Built in parts of at most 30 option rows. **Part 1** creates the store (§1), the router change that lets a proposal name its run (§2), and the two options that run a model (§3, §4). **Part 2** (§7, the owner's B on #2105, 2026-10-20) makes `/admin/x`'s generated alt text a proposal.
- **Basis:** `origin/main` at `48dc7d7`. Worker paths are relative to `cloudflare-worker/src/`, SPA paths to `frontend/src/`.
- **Stacks on:** nothing. D777 part 1 (#2139), D765 (#2132, #2145) and D770 are on `main`.

### 1. The store: `ai_rail_proposals` (migration 506)

D720 §7 reserved migration 482 for this table under D765. D765 closed without creating it, so S1 moved it here (#2105, 2026-10-19), at the next free number, 503.

- **Columns.** D720 §7's list: `uid`, `user_id`, `rail_page`, `rail_option`, `record_ref`, `kind`, `payload_json`, `model`, `usage_log_id` and `status`, plus `decided_payload_json`, `decided_at`, `created_at` and `updated_at`.
  - The page, option and record are named as `ai_usage_logs` names them (migration 493).
  - `usage_log_id` points at the run's `ai_usage_logs` row.
- **Kinds:** `draft`, `proposal` and `note`.
- **Statuses:** `proposed`, `accepted`, `edited`, `discarded` and `withdrawn`. An edit keeps Eadwyn's payload and stores the member's version beside it.
- **The service is `services/railProposals.ts`.**
  - `proposeRail` stores a run's output, and refuses a payload whose `field` is in D777's never-fill registry.
  - `decideRail` records the member's press. It decides a row once (`WHERE status = 'proposed'`), and only the member's own row.
  - `listRail` and `getRail` are owner-scoped reads. `withdrawRail` takes back the member's open proposals on a record.
- **The routes are `routes/ai_rail_proposals.ts`,** with the caller's own rows only:
  - `GET /api/ai/rail/proposals?option=&record=&status=`;
  - `POST /api/ai/rail/proposals/:uid/decide` with `accept`, `edit` or `discard`.

  The SPA reaches them through `lib/api/railProposals.js`.
- **Deciding writes no record.** The page's own Save does that, through the record's own route.
- **Who writes here:** every rail option outside Validate (`validate_proposals`) and the zone drafts (`research_zone_drafts`). That includes D778 (#2103) and D779 (#2104) as their options land.

### 2. A run names its usage row

`run()` now returns `usageLogId` on a run that answered, live or from the cache: the `ai_usage_logs` row `recordUsage` wrote. It is null when that row could not be written.

A proposal stores it, so a member can see which run wrote a proposal and what it cost. This is the provenance D777 asks for (§ "Provenance" of #2102).

### 3. H20 `draft:publication-summary` (Super Admin · Content · Publications)

- **The run.** `POST /api/admin/publications/draft` runs under the inventory's key, `draft:publication-summary` (it was `draft:publication`), with the request's rail context (`railFor`).
- **The proposal.** When the model answers, its summary is a `draft` proposal on `publication:<id>`, and the publication's `summary_text` starts empty.
  - The response and `GET /:id` carry the admin's open proposal as `summary_proposal`.
  - When the model cannot be reached, the aggregate fallback (no model) fills the blank as before, and nothing is proposed.
- **The page.** `PublicationDetail.jsx` draws the proposal above the editor, as "Eadwyn's draft · not saved".
  - "Put it in the summary" fills the open editor, and writes nothing.
  - Discard decides the proposal, and writes nothing else.
- **Save is the only write.** `PUT /:id` carries `summary_proposal_uid` when the text began as the proposal.
  - The Worker writes the summary, then keeps the proposal as `accepted` (unchanged) or `edited`.
  - Only an edit marks the summary human-edited.
  - A proposal that is not the admin's open one for this publication is refused with 409.
- **Owner-scoped.** A proposal is the drafting admin's own, so another Super Admin opening the publication sees the summary, not the proposal.

### 7. Part 2: `/admin/x` alt text as a proposal (`draft:x/alt-text`)

The inventories leave no option after part 1: `ADMIN_OPTIONS` is empty (D774), and H20 is the Super Admin's only one (D775). Two admin-side model calls sit outside them, both D765 system calls (`rail_run_path_d765.test.ts`).
- **Monitoring's "Summarise with AI"** shows a summary and writes nothing. It stays a system call.
- **`/admin/x`'s "Alt"** wrote Eadwyn's caption straight into `x_posts.alt_texts`.

The owner chose B: make the alt text a proposal, and leave Monitoring alone.

- **The run is unchanged.** `POST /api/admin/x/posts/:id/alt-text` still runs `image_alt_text` as D765's system call (user 0, at cost).
- **The caption is a proposal.** It is the pressing Super Admin's `draft` on `x_post:<id>:<index>`, under `draft:x/alt-text` on page `x`, with the run's model and usage row.
  - It writes nothing to the post.
  - An earlier open proposal for the same image is withdrawn, so one waits at a time.
  - The response carries `proposal: { uid, text }`. The audit action is `x_post_alt_proposed`.
  - `/admin/x` is not a canvas board, so the option has no inventory row.
- **The list carries it.** `GET /api/admin/x/posts` adds `alt_proposals`, the caller's open proposals by image index, so the composer offers them after a reload.
- **Save is the only write.** `PUT /api/admin/x/posts/:id/alt-text` with `{ index, alt_text, proposal_uid? }` writes that image's alt text, on a post not sent or sending.
  - When `proposal_uid` names the caller's open proposal for that image, the proposal is kept as `accepted` (unchanged) or `edited`.
  - Any other uid is refused with 409.
  - The audit action is `x_post_alt_saved`.
- **The page.** `AdminX.jsx` draws the proposal beside its image as "Eadwyn: "…" · not saved".
  - "Use it" is the Save (`adminX.saveAltText`, with the proposal's uid).
  - Discard decides the proposal through `/api/ai/rail/proposals` and writes nothing else.
- **Tests.**
  - `ai_system_calls_d766.test.ts`: case 5 is updated, and case 5b is new (6 mutations, all caught).
  - `frontend/test/rail_proposals_d780.test.mjs`: the fourth case is new (4 mutations, all caught).

### 8. Part 3: Approve keeps the offered alt-text captions

Part 2 (#2222) remains the generation and Save implementation. Its per-image record (`x_post:<id>:<index>`), list projection, dedicated `PUT /posts/:id/alt-text` endpoint and `withdrawRail` are unchanged. No additional withdrawal helper is needed.

- `POST /posts/:id/approve` accepts `alt_text_proposal_uids`, the captions still offered by the composer.
- Each must be the pressing Super Admin's open `draft:x/alt-text` proposal for an image on this post. A stale, foreign or mismatched proposal refuses the entire approval before any write.
- A transactional D1 batch rechecks the open set, writes the captions and approval, and accepts the proposals together. Duplicate uids are deduplicated. Naming none leaves stored captions untouched.
- The batch also compares the loaded captions and media list with the current post. A concurrent Save or media change refuses approval, preserving the human's edits and leaving proposals open. A proposal cannot replace an already saved caption through Approve.
- The composer passes the proposals it displays beside images without saved alt text. Save and Discard retain part 2's existing paths.
- `rail_x_alt_text_d780.test.ts` retains the approval regression cases from #2225: stale refusal without partial writes, successful acceptance and preserving captions when none are named. `rail_proposals_d780.test.mjs` preserves part 2's tests and checks the Approve request.
