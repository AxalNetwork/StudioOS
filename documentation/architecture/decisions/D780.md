## D780 — The admin's and Super Admin's options fill, draft and place through the run path, and their runs leave proposals in `ai_rail_proposals`, never in a record

- **Status:** decided by S1, 2026-10-19 (#2105; task `X3` of D720's plan, #1874 §9). Built in parts of at most 30 option rows. **Part 1** creates the store (§1), the router change that lets a proposal name its run (§2), and the two options that run a model (§3, §4). **Part 2** (the owner's choice B, 2026-10-20) moves `/admin/x`'s alt text onto the store and records the two rulings on the admin-side system calls (§7).
- **Basis:** `origin/main` at `48dc7d7`. Worker paths are relative to `cloudflare-worker/src/`, SPA paths to `frontend/src/`.
- **Stacks on:** nothing. D777 part 1 (#2139), D765 (#2132, #2145) and D770 are on `main`.

### 1. The store: `ai_rail_proposals` (migration 506)

D720 §7 reserved migration 482 for this table under D765. D765 closed without creating it, so S1 moved it here (#2105, 2026-10-19), at the next free number, 503.

- **Columns.** D720 §7's list: `uid`, `user_id`, `rail_page`, `rail_option`, `record_ref`, `kind`, `payload_json`, `model`, `usage_log_id` and `status`, plus `decided_payload_json`, `decided_at`, `created_at` and `updated_at`.
  - The page, option and record are named as `ai_usage_logs` names them (migration 493).
  - `usage_log_id` points at the run's `ai_usage_logs` row.
- **Kinds:** `draft`, `proposal` and `note`.
- **Statuses:** `proposed`, `accepted`, `edited`, `discarded` and `withdrawn`. An edit keeps Eadwyn's payload and stores the member's version beside it.
- **The service is `services/railProposals.ts`.**
  - `proposeRail` stores a run's output, and refuses a payload whose `field` is in D777's never-fill registry.
  - `decideRail` records the member's press. It decides a row once (`WHERE status = 'proposed'`), and only the member's own row.
  - `listRail` and `getRail` are owner-scoped reads. `withdrawRail` takes back the member's open proposals on a record, and `withdrawRailUid` (part 2) takes back one of them.
- **The routes are `routes/ai_rail_proposals.ts`,** with the caller's own rows only:
  - `GET /api/ai/rail/proposals?option=&record=&status=`;
  - `POST /api/ai/rail/proposals/:uid/decide` with `accept`, `edit` or `discard`.

  The SPA reaches them through `lib/api/railProposals.js`.
- **Deciding writes no record.** The page's own Save does that, through the record's own route.
- **Who writes here:** every rail option outside Validate (`validate_proposals`) and the zone drafts (`research_zone_drafts`). That includes D778 (#2103) and D779 (#2104) as their options land.

### 2. A run names its usage row

`run()` now returns `usageLogId` on a run that answered, live or from the cache: the `ai_usage_logs` row `recordUsage` wrote. It is null when that row could not be written.

A proposal stores it, so a member can see which run wrote a proposal and what it cost. This is the provenance D777 asks for (§ "Provenance" of #2102).

### 3. H20 `draft:publication-summary` (Super Admin · Content · Publications)

- **The run.** `POST /api/admin/publications/draft` runs under the inventory's key, `draft:publication-summary` (it was `draft:publication`), with the request's rail context (`railFor`).
- **The proposal.** When the model answers, its summary is a `draft` proposal on `publication:<id>`, and the publication's `summary_text` starts empty.
  - The response and `GET /:id` carry the admin's open proposal as `summary_proposal`.
  - When the model cannot be reached, the aggregate fallback (no model) fills the blank as before, and nothing is proposed.
- **The page.** `PublicationDetail.jsx` draws the proposal above the editor, as "Eadwyn's draft · not saved".
  - "Put it in the summary" fills the open editor, and writes nothing.
  - Discard decides the proposal, and writes nothing else.
- **Save is the only write.** `PUT /:id` carries `summary_proposal_uid` when the text began as the proposal.
  - The Worker writes the summary, then keeps the proposal as `accepted` (unchanged) or `edited`.
  - Only an edit marks the summary human-edited.
  - A proposal that is not the admin's open one for this publication is refused with 409.
- **Owner-scoped.** A proposal is the drafting admin's own, so another Super Admin opening the publication sees the summary, not the proposal.

### 7. Part 2: `/admin/x` alt text, and the two admin-side system calls

**The question (2026-10-20).** After part 1, both inventories were covered: `ADMIN_OPTIONS` is empty, and the Super Admin's only option is H20's. Two admin-side model calls sat outside them. Both are system calls in D765's list (`rail_run_path_d765.test.ts`).
- `/admin/x` "Generate alt text" wrote Eadwyn's caption straight into `x_posts.alt_texts`, with no press to keep it. That is what D720 §9 rules out.
- Monitoring's "Summarise with AI" (H33) shows a summary and stores nothing.

The owner chose **B**: the alt text becomes a proposal, and Monitoring stays as it is.

**The rulings.**
1. **The X caption is a proposal.**
   - `POST /api/admin/x/posts/:id/alt-text` no longer writes the post. It stores a `draft` proposal (`proposeRail`) with:
     - option `draft:x/alt-text`;
     - record `x_post:<id>`, with the image index in the payload (`{ index, text }`);
     - the pressing Super Admin as `user_id`.
   - The page is the request's rail page, else `admin/x`. `/admin/x` is not a canvas board, so the page map has no key for it.
   - The response carries `proposal: { uid, index, text }`.
2. **The run is unchanged.** It stays the `image_alt_text` system call (D766: user 0, logged at cost, charged to no one), so D765's billing entry stands. Its list entry now says where the caption goes. The proposal names the run's usage row.
3. **One open caption per image.** A newer caption for an image withdraws the admin's older open one for that image (`withdrawRailUid`). Captions on the post's other images stay open.
4. **Save or Approve keeps it, nothing else.**
   - `PUT /posts/:id` takes `alt_text: { index, text, proposal_uid? }`.
     - It writes `alt_texts[index]`.
     - With a `proposal_uid`, it keeps the proposal as `accepted` (unchanged) or `edited` (with `{ index, text }`).
     - A proposal that is not the admin's open one for this post and image is refused with 409, and nothing is written.
     - A typed caption with no proposal is the admin's own, and decides nothing.
   - `POST /posts/:id/approve` takes `alt_text_proposal_uids`: the captions the composer still offers.
     - It writes each one and approves the post in one statement, then keeps each proposal as `accepted`.
     - Any uid that is not open refuses the whole Approve with 409, so nothing is kept by half.
     - An Approve that names none leaves `alt_texts` as it was.
5. **Monitoring "Summarise with AI" (H33) stays a system call** (D765's `ops_summary`). It stores nothing, so there is nothing to keep, and making it an option would charge the pressing admin's allowance. A rail option there would be a new task.

**The composer.** `pages/admin/AdminX.jsx`'s drafts list:
- reads the admin's open captions (`railProposalsApi.list`);
- offers each one beside its image as "Eadwyn's caption", editable, with Save and Discard;
- passes the offered ones to Approve.

"Alt" writes nothing and reloads nothing. `/admin/x` is paused (its default export says so), and this is the retained composer it re-enables.
