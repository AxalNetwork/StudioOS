## D8339 — The capacity request store never removes a result that is still owed (#8339)

`SqlCapacityStore` holds at most 1,000 full requests and removed only those completed more than seven days
ago. Above about six requests an hour it filled, and every new submission was refused
`capacity_storage_bound` until old rows aged out (D8333, finding 10). The age removal also ignored
publication: at seven days it deleted a request whose result had never reached its check.

Given a publication guard, the store now applies one test to both removals. A request leaves by age only
when nothing is owed, and at the cap the oldest request whose result can no longer change leaves to admit
one more. The cap stays at 1,000.

S39 assigned this to S21 and reviews it
([#7909](https://github.com/AxalNetwork/StudioOS/issues/7909#issuecomment-7099175131)); the age rule and the
treatment of a published success come from S39's review of the first revision
([#8343](https://github.com/AxalNetwork/StudioOS/pull/8343#issuecomment-7101600857)). Nothing here is live:
the runtime does not pass the guard yet, and without it the store behaves exactly as before.

### The rule

With a guard, `prune(before)` makes one pass over settled requests, by `completed_at` then `id`. A request
is settled when `completedAt` is set and every attempt is `passed`, `failed` or `cancelled`; an attempt in
`cancellation_unknown`, `dispatch_unknown` or any other phase keeps its request out of the pass.

For each request the guard answers one of three things:

| Answer | Meaning | Leaves by age | Leaves by count |
| --- | --- | --- | --- |
| `owed` | A result is still to be published or corrected. | No | No |
| `revisable` | Published, but the publisher may still lower it while the request is kept. | Yes | No |
| `final` | Nothing can change. | Yes | Yes |

A guard that throws, or answers anything else, counts as `owed`.

A request also stays while a lease of its own is open: its `deadline`, or any attempt's start, execution or
cancel deadline. Until then a retried submission still gets its original acknowledgement, and a late
verified failure still finds its request.

Count removal happens only at the cap and removes one request, because one admission needs one place. If
nothing qualifies, nothing is removed and the coordinator refuses `capacity_storage_bound`, as it does today.
That now includes a store filled by requests older than seven days whose results are still owed.

The request, parent and child fences (`ci_capacity_seen`, `ci_capacity_parents`, `ci_capacity_children`) are
not touched. A removed request's identity is refused `capacity_expired_request`, its parent run cannot be
resubmitted at the same or an older attempt, and its child runs stay owned.

The pass reads at most 1,000 requests. It stops at the first request inside the age limit once the store is
below the cap, so below the cap it reads only requests past seven days.

### The publication guard

`publicationSettled(storage, mode)` in `merge-control/src/ciCapacityRetention.ts` reads the outbox's
`capacity_publications` table and writes nothing. For the configured mode:

- **`owed`**: the mode is unknown; there is no intent; the create is unconfirmed; the check is still in
  progress; a failure is recorded but not on the check; a verified failure arrived after `cancelled` was
  sent; or a success was sent and a newer attempt of the parent now exists.
- **`revisable`**: the check is concluded and the request passed. The outbox re-reads the parent on every
  visit and lowers that check if the parent stops being current, so the request keeps its full seven days.
- **`final`**: a failure or cancellation is on the check and matches the request, or the attempt is
  superseded and never had a check, which the outbox never creates.

The outbox deletes intents whose request is gone. A request that leaves has a delivered result, so that
deletion loses nothing.

### What this does not solve

A passing request is `revisable`, so it leaves only by age, as it always did. A store filled with passes
inside seven days still refuses. This change removes failures and cancellations early, and it stops the age
limit from discarding undelivered results; it does not lift the seven-day floor on passes.

Lifting that floor needs the outbox to keep lowering a check after the full request is gone, from a compact
record of the submission and check id. The outbox is S39's, so that design is S39's to choose. The store can
supply the compact record if S39 wants it.

### For S39 to compose

The store's constructor takes the guard as an optional second argument. `ciCapacityRuntime.ts` is S39's file
and is not changed here. The runtime has no field holding the publication mode today, so composition needs
validated mode initialization, behaviour on configuration failure or change, and restart tests. The guard's
only requirement is a function that returns the configured mode, or null when it is not known; null removes
nothing.

S39's answers to the four points raised in the first revision, recorded as decided:

1. **A removed success must not become final early.** Met here: a success is never removed by count.
2. **Owed corrections wait for an idle outbox.** S39 owns the outbox fairness fix. Until then a request held
   for a correction stays past seven days and costs a place; the refusal stands when the store is full.
3. **A refused submission can still open one place.** Accepted. The coordinator prunes before its
   parent-conflict and active-bound checks; the removal is bounded at one.
4. **A full store costs a scan.** Accepted as an explicit bounded cost, not as evidence of readiness to
   scale. S39 owns bounded reconciliation and ordered-path performance before any expansion.

The fence tables still grow without bound, as S39 noted. This change does not bound them.
