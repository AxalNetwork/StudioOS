## D8339 — The capacity request store retains by count as well as age (#8339)

`SqlCapacityStore` holds at most 1,000 full requests and removed only those completed more than seven days
ago. Above about six requests an hour it filled, and every new submission was refused
`capacity_storage_bound` until old rows aged out (D8333, finding 10). At the cap, the store now makes room
for one admission by removing the oldest settled request whose result is already on its check. The cap stays
at 1,000 and the seven-day limit is unchanged.

S39 assigned this to S21 and reviews it
([#7909](https://github.com/AxalNetwork/StudioOS/issues/7909#issuecomment-7099175131)). Nothing here is
live: the runtime does not pass the guard yet, and without it the store behaves exactly as before.

### The rule

`prune(before)` runs the age removal first, as before. Then, only when the store is at the cap and a guard
was supplied, it walks settled requests by `completed_at`, then `id`, and removes the first one that passes
all three tests:

1. **Settled.** `completedAt` is set and every attempt is `passed`, `failed` or `cancelled`. A request with
   an attempt in any other phase, `cancellation_unknown` and `dispatch_unknown` included, is never a candidate.
2. **Its leases have run out.** The clock is past the request's own `deadline` and past every attempt's
   start, execution and cancel deadline. Until then a retried submission still gets its original
   acknowledgement, and a late verified failure still finds its request.
3. **Its result is published.** The guard says so. A guard that throws counts as no.

It removes one request, because one admission needs one place. If none passes, nothing is removed and the
coordinator refuses `capacity_storage_bound`, as it does today.

The request, parent and child fences (`ci_capacity_seen`, `ci_capacity_parents`, `ci_capacity_children`) are
not touched. A removed request's identity is refused `capacity_expired_request`, its parent run cannot be
resubmitted at the same or an older attempt, and its child runs stay owned.

### The publication guard

`publicationSettled(storage, mode)` in `merge-control/src/ciCapacityRetention.ts` reads the outbox's
`capacity_publications` table and writes nothing. For the configured mode it returns true only when:

- the intent is `known` with a confirmed check id and its last sent result is success, failure or cancelled; and
- that sent result is the one the request now owes. A failure recorded but not yet sent, a verified failure
  that arrived after `cancelled` was sent, and a success whose parent has since been run again all keep
  the request until the outbox has corrected the check.

A request with no intent is kept, unless a newer attempt of its parent exists: the outbox never creates a
check for a superseded attempt, so that request is owed none. An unknown mode, an intent for the other mode
only, an unconfirmed create and a check still in progress all keep the request.

The outbox deletes intents whose request is gone. The requests this rule removes have a final, correct
check, so that deletion loses nothing.

### What changes for S39 to compose

The store's constructor takes the guard as an optional second argument. Wiring it is one line in
`ciCapacityRuntime.ts`, which is S39's file and is not changed here:

```ts
this.store = new SqlCapacityStore(ctx.storage, publicationSettled(ctx.storage, () => this.publication));
```

`this.publication` is the configured mode, or null before configuration is read. No coordinator or outbox
line changes.

Three behaviours to review:

1. **A removed request's check is final.** Today a published success is lowered to cancelled if its parent
   stops being current at any time in seven days. After removal that no longer happens. The request is held
   when the newer attempt was submitted before the removal; when the removal comes first, the old success
   stays on the commit and the newer attempt's own check supersedes it.
2. **Owed corrections wait for an idle outbox.** The outbox visits already-final checks only when no request
   is active or unsent. Under steady load a request held for a correction stays until the seven-day limit.
   That is safe and costs places; it is the outbox's existing order, not a change made here.
3. **A refused submission can still open one place.** The coordinator prunes before its parent-conflict and
   active-bound checks, so a submission refused there has already removed one request. The store is then
   below the cap and later refusals remove nothing.

The fence tables still grow without bound, as S39 noted. This change does not bound them.

### Capacity after the change

A request stays at least until its leases end, about 90 minutes after acceptance under the current budgets, and until its check is
final. The planning cases in D8333 complete 20, 40 and 80 requests per 25 minutes; the largest, 80 active
requests, puts about 290 requests inside a 90-minute window. The store reaches the cap only when unpublished
or unresolved work fills it, and then it refuses.
