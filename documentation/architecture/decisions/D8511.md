## D8511 — The dev commerce client runs on a test-mode Stripe key or not at all (#8511)

**Context.** `backend/app/services/stripe_commerce.py`, the Replit-dev Stripe client behind the Products page cart and checkout, called itself test-mode but fell back to `STRIPE_SECRET_KEY` when `STRIPE_TEST_SECRET_KEY` was missing, and to `STRIPE_PUBLISHABLE_KEY` for the publishable key. A developer's or an agent's environment that held the live key would then create real Stripe objects from a dev checkout, and a warning in a log would be the only sign. `backend/` is never deployed (CLAUDE.md, fact 3), so the risk is entirely in development environments.

**Decision.**

- The client reads `STRIPE_TEST_SECRET_KEY` and `STRIPE_TEST_PUBLISHABLE_KEY` only. Both fallbacks are gone.
- The secret key must start with `sk_test_` or `rk_test_`, and the publishable key with `pk_test_`. A missing key answers `no_key`, a key of any other shape `not_test_mode`. Both are raised before the HTTP client is built, so no request leaves the process. The message names the variable and the expected prefix, never the value.
- `GET /payments/config` returns that refusal as its usual Stripe error response instead of an empty publishable key.
- `backend/scripts/seed_stripe_test_catalog.py` reads the live key for GETs only (it mirrors the live catalogue). It now exits before any request unless `STRIPE_TEST_SECRET_KEY`, the key every write uses, is a test-mode key.

**Tests.** `backend/tests/test_stripe_test_mode_d8511.py`, run in the ordinary frontend suite by `frontend/test/stripe_test_mode_d8511.test.mjs` (the `dev backend (import smoke)` job is pinned unchanged by D7909's job digests, so it gains no step; where `httpx` is not installed the test puts a stand-in in its place, since every case patches `httpx.Client`): a missing key, a live key, a live restricted key and `STRIPE_SECRET_KEY` alone are each refused with `httpx.Client` never called; the publishable key's three refusals; a test key reaching the client; and a source check that the module never reads either live variable. Restoring either fallback, dropping or widening the prefix check, putting the value in the message, or bypassing the check in `_request` each fails it.

**Not changed.** `backend/app/services/stripe_connect.py` (the Connect adapter, not the commerce path) still reads `STRIPE_SECRET_KEY`; it is out of this decision's scope. The Worker's Stripe client is untouched.
