## D7673 — Role-neutral introduction requests, requester readiness and the Axal operator workflow (#7673)

**Status:** implemented for review, 2026-11-22. Additive schema, service and API only. No UI, no outreach
transport, no production data. Builds on D7672's directory identities. #7674 owns directory reads, private
overlays and publication. The member and operator screens follow the approved Network canvases in a later change.

### What it is

Any signed-in member, whatever their role (founder, investor, advisor, partner or a Lab member), can ask Axal for
an introduction to a person. The person is either a published person in the shared Network directory (#7672) or
someone the requester names who is not in it yet (a *provisional target*). A request can also name only an
organisation; an operator then has to identify the right person before any outreach. A target needs no platform
account.

Submission only queues the request. An Axal operator (an HQ admin) assigns it to themselves, reviews it, asks the
requester for more if needed, and performs any outreach as a person. Each contact is recorded as an attempt and its
delivery reconciled. Nothing in this change sends a message: `recordContactAttempt` takes an optional transport, no
route passes one, and the tests use a fake one.

### Schema

Migration `202611220337_7673_network_introduction_requests.sql` adds:

| Table | Meaning |
| --- | --- |
| `network_intro_policies` | Versioned readiness policies; at most one active. Seeded with version 1: `professional_profile` and `capacity`. `validity_days` NULL means an approval does not expire. |
| `network_intro_readiness` | One row per member and requirement: shareable value, an optional *reference* to private evidence (never the evidence), reviewer, review time, validity. A change returns it to `submitted`. |
| `network_intro_provisional_targets` | A named person not in the directory, scoped to its creator, until an operator resolves it to a directory person or rejects it. |
| `network_intro_requests` | The request: requester, idempotency key, target (directory person, provisional, and/or organisation context), purpose, shareable brief, the requester's private notes, state, next actor, operator, policy snapshot, consent, outcome and a revision. `service_type` is `directory_introduction`. |
| `network_intro_events` | Append-only history (triggers refuse update and delete). Each event is `requester`-visible or `operator`-only. |
| `network_intro_contact_attempts` | Each contact: operator, channel, idempotency key, delivery state. Never deleted; only an unsettled attempt's delivery outcome may change. |

Triggers refuse a request whose target is not a directory person, or whose organisation context is not a directory
organisation.

### Readiness

The policy's requirements are configurable keys. The base policy asks for a shareable professional profile (a
headline and an optional https profile link) and the capacity the requester asks in (with an optional represented
organisation). No legal classification, accreditation, identity-document check, price or service-level promise is
part of it, and investor KYC is not used as the gate. A requirement is met only when a reviewer approved it and it
is not past its validity. A reviewer cannot review their own readiness. Submission reads the stored rows on every
call, so nothing a client sends can mark a requirement met. The request keeps a snapshot of the policy it was
submitted under.

### States

`draft → readiness_needed | submitted → in_review → needs_information | outreach_ready → contacted →
awaiting_target → declined | unavailable | agreed → introduction_made → closed`, plus `withdrawn` from any state
before a result. Who acts next is fixed per state (`NEXT_ACTOR`). Submission, review, assignment, contact, target
consent (`agreed` / `declined`), delivery reconciliation and the completed introduction are separate events.

- **Idempotency.** A new request carries the requester's idempotency key; the same key returns the first request
  and never rewrites it. A contact attempt carries its own key; a replay returns the recorded attempt and sends
  nothing again.
- **Concurrency.** Every state-changing write sends the revision it changes. The update and its event are one
  batch; the event is written only if the guarded update landed. A stale revision is refused with
  `revision_conflict` and writes nothing. Only the assigned operator moves a request or settles its attempts.
- **Delivery.** A transport failure leaves an attempt `uncertain`, never `failed`. A new attempt is refused while one
  is pending or uncertain, so a lost response is reconciled, never resent blind.
- **Withdrawal** after contact keeps every attempt and event.
- **Quotas.** This service spends no credit and debits nothing. The quarterly investor ask (#6261), curated-credit
  propositions (#7064), teammate requests (#7066) and Offer one (#6637) are untouched and keep their own quotas.

### Visibility

Three projections, all built in the service:

- **Requester:** their own request, their private notes, and requester-visible events. No contact attempts, no
  operator-only events, no requester id.
- **Operator:** everything except the requester's private notes.
- **Target brief:** the purpose, the shareable brief and the requester's shareable readiness fields only.

A requester can name only a *published* directory person or organisation. Anything staged, suppressed, withdrawn or
missing reads `target_not_found`, so a member never learns that an unpublished record exists. Directory contact
points and raw source records (#7672's operator-only table) are never read. A support session reads but cannot
write. Drafts never appear in the operator queue. Lists return a true total from the same WHERE as the page, with a
cursor over (created_at, uid).

`notificationFor` builds the payload each audience may receive for an event. No route sends one; a requester never
receives an operator-only event.

### Not built here

- The member and operator screens. They follow the approved Network canvases.
- Publication of directory people (#7674). Until it lands, only rows an operator has published can be targets.
- A reviewed merge or redirect of directory entries (#7674). A provisional target's reference stays stable when it
  is resolved; a merged entry's redirect is #7674's to add.
- An outreach transport. Outreach is the operator's recorded act.
- Sending notifications.

### Rollback

Revert the Worker change. The additive tables can stay; nothing else reads them.
