### 1. One queue (migration 595)

`data_room_access_requests` holds one row per request: `uid`, the venture, the investor, `source` (`round_call` or `deal_page`), `round_call_id`, `message`, `state` (`open`, `accepted`, `declined`), `decided_by`, `decided_at`, `decline_reason` and `created_at`.

- **One open request per investor and venture.** A partial unique index holds it, and both writers use `INSERT OR IGNORE`. A second ask, from another call or from the deal page, is the same row.
- **No request from someone who already has the room.** An investor with a live grant gets no row, so the founder is never asked a question already answered.
- **A decided request stays** as the record of the answer. A later ask opens a new row.

### 2. Where requests come from

- **The round call.** "Request the data room" (`respond`, action `data_room`) still sets `round_call_recipients.data_room_requested_at`, and now also writes the request.
  - It is written in the response's own batch, guarded by the response's claim, as the call's question insert is. A refused response leaves no request behind.
  - The response's update stays statement 0, so the claim check that reads `result[0]` is unchanged.
- **The deal page.** `dealPageRequestStatement()` is ready for DEAL #2421's DL9 to run from its own route. It carries the investor's message, trimmed, at most 2,000 characters.
- **The backfill.** Migration 595 writes one row per investor and venture from every round-call request recorded so far, dated by the earliest.
  - An investor who already held a live grant was answered before the queue existed. That row is `accepted`, with `decided_by` and `decided_at` null: who decided, and when, were never recorded. The read returns them as null; it does not invent them.
  - Every other backfilled row is `open`. Re-running the backfill adds nothing.

### 3. The routes (`/api/data-room`)

| Route | Who | What |
|---|---|---|
| `GET /:projectUid/requests` | owner, co-founder | The queue, open first and then newest. Each request carries its investor, source, round call, message, state, decision, the reason, the NDA between the venture's founder and that investor (`active`, `pending` or `none`) and whether they have the room now. Also `open` (the count) and `can_answer` (only the owner). A store that cannot be read is **503** `requests_unreadable` with a sentence, never an empty queue. |
| `POST …/requests/:uid/accept` | owner | `{ expires_at?, folders? }`, checked by part 2's `grantFields` before anything moves. See the accept steps below. |
| `POST …/requests/:uid/decline` | owner | `{ reason }`, 1 to 500 characters, required. See the decline rules below. |
| `POST /:projectUid/grants/:uid/nda` | the venture's founder | The platform's three-way NDA. See §4. |

**Accept** works in three steps:
1. The request is claimed: open becomes accepted, by this owner, at this instant. A request that is no longer open answers **409** `request_decided`, so two presses, or a decline in between, can never both win.
2. The grant is written exactly as `POST /grants` writes it: reactivated on conflict, with the folders and end date when given.
3. If the grant cannot be written, the claim is put back (open, no decider), so nothing is granted and the request can be answered again.

The accept is logged with `logCycleWrite` (`access_request_accepted`), and the investor's inbox is told, with a link to `/research/diligence`.

**Decline:**
- The update moves only an open request; a decided one answers **409**.
- The reason is kept on the request and sent to the investor's inbox.
- It is never logged: the `logCycleWrite` summary (`access_request_declined`) carries no words of it.

**Who answers.** Only the owner answers, as only the owner shares (D1103). A co-founder reads the queue and gets **403** `owner_only` on a decision. Anyone else, or another venture's request, gets **404**.

### 4. The founder's NDA (owner question 4, answer A)

Until now only the investor could start the platform's three-way NDA (`POST /api/trust/intro/request`). Now the founder can send it, for a grant:

- **Only the venture's founder.** They sign as party A, which `pairwise_ndas` fixes as the founder (migration 025).
  - A co-founder gets **403** `owner_only`.
  - An admin is not the room's owner since D1102 (#3045), so the route answers **404** to an admin, as every owner route does. An NDA is never sent in someone else's name. The route still checks that the caller is the venture's founder account (`founder_only`, 403) as a second guard on party A.
- **Only for a live grant of this venture.** A revoked, ended or other venture's grant gets **404**.
- **Refused when the NDA is in force** (**409** `nda_active`), whether read the room's way (`projectNdaActive`) or the pair's (`ndaActive`).
- **Refused when it is already out for signature** (**409** `nda_pending`). A second envelope would replace the first's record in `pairwise_ndas` while it is being signed.
- **It reuses the trust services:** `createThreeWayNdaEnvelope`, then `upsertPairwiseNda` (pending until all three sign; the eSign completion hook activates it, as before).
  - The founder gets only their own signing link back. The investor's and Axal's are emailed by the envelope service.
  - The investor gets a `contract_sign_request` inbox line pointing at the Trust Center.
  - The send is logged as `nda_sent`, with no names.
- **Refusals:** a library NDA with fields Axal has not filled is **409** `template_fields_unfilled`. An envelope that cannot be made is **502** `envelope_creation_failed`. Each comes with a sentence; the envelope service's own error text never reaches the response or the log (only the error's name is logged).

### 5. Not in this part

- **The Requests tab and the NDA button on Access.** They are drawn by a later part, against these routes and `dataRoomApi.requests`, `acceptRequest`, `declineRequest` and `sendNda`.
- **A stale envelope.** An NDA left pending is not resent here: `nda_pending` holds until it is signed or expires. Resending a stale envelope is a question for the owner if it comes up.
