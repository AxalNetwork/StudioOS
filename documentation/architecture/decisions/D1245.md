### 1. A partner-deal case seeds its checklist

The partner-deal opener inserted sections by hand and seeded no checklist, no
template version and no blocking from a template. It now calls
`seedNewCase(env, caseId, 'partner', 'standard', { notApplicable })`, the same
seed `POST /cases` uses:

- the depth's latest HQ template, or the built-in catalog (version 0) when none is saved;
- `dd_cases.template_id` set when a template exists;
- the checklist items at that depth;
- `stampNewCase`, so the opener leads it and its blocking sections are marked.

The depth is Standard, the column's default; a partner deal has no form that
picks one. A non-capital deal still seeds KYC (individual) and Accreditation
completed with the verdict `n_a`, as before, and those two sections seed no
items: nobody works them.

### 2. Notice links by role

`/admin/due-diligence` admits admins only, so a reviewer, lead or investor
sent there met a refusal. Every notice and email that links a case now reads
the recipient's role: an admin gets `/admin/due-diligence/<uid>`, every other
role `/due-diligence/<uid>`. A failed role read takes the member base, which
admits an admin too.

| Notice | Recipient |
|---|---|
| `dd_case_lead` (new case, lead change) | the new lead |
| `dd_high_severity_finding` (scan) | the case opener |
| `dd_section_assigned` (the invitation's magic link, `?section=…&inv=…`) | the assignee |
| `dd_section_completed` (verdict) | the case opener |
| `dd_request_responded` | the case opener |
| `dd_case_decided` | each reviewer |
| `dd_conflict_declared` (`/<uid>/team`) | the lead |

The `/due-diligence/requests` links go to the subject, who is never an admin, and are unchanged.

### 3. `allowed` in the case read

`GET /api/dd/cases/:uid` returns `allowed`, computed by `caseAllowed` from the
same rules each route applies:

| Flag | True when | Route |
|---|---|---|
| `scan` | a case writer (admin, lead, opener, or a reviewer on the case) who is an Admin or a partner | `POST /cases/:uid/scan` |
| `assign` | the same | `POST /cases/:uid/sections/:id/assign` |
| `verdict` | per visible section id: an Admin or the lead; otherwise that section's reviewer, never an observer | `POST /cases/:uid/sections/:id/verdict` |
| `requests` | an Admin, the lead or the opener | `POST /cases/:uid/requests` |
| `report` | the same as `scan` | `POST /cases/:uid/report` |
| `notify_founder` | an Admin, on a project or founder case | `POST /cases/:uid/report/share` |
| `audit` | an Admin, the lead or opener, or any reviewer | `GET /cases/:uid/audit` |

A flag says who may ask, not that the call succeeds: `report` still needs a
recent TOTP step-up, and a reviewer's verdict other than `n_a` still needs
their signed NDA. The tests call every route as admin, lead, opener, partner
reviewer, observer, investor reviewer and advisor reviewer and hold each flag
to the route's answer, so a gate that moves without `caseAllowed` fails the
build. Drawing only these controls is the page's work (#2385's frontend part).

### 4. Contracts' "Open in DD": dropped

The contract detail read looked up `dd_findings.esign_envelope_uuid` to offer
"Open in DD", and a voided contract wrote a row into that case's
`dd_audit_log`. Nothing writes the column: no connector or route makes a
finding from an envelope, so the lookup always found nothing and no page drew
the link. Both are removed rather than inventing an envelope-to-finding path
nobody asked for. The column stays; a later part that makes findings from
envelopes can write it and restore the link.
