## D7124 part 2 — A time budget for the changed-tests future-clock step (#7124)

**Date:** 2026-11-26. **Status:** Built. Owner answer A on #7124.

### Why

The acceptance read of `scripts/future-clock-changed.mjs` on natural PR runs (#7124 STATUS, 2026-11-25) found 12 runs with 10 or fewer changed test files that took 202–987 s, against a 3-minute target. Changed Worker test files caused it: under libfaketime one Worker file took 535 s across the two offsets (job 138106210809). The median run took 19 s.

### What changes

- **One file per run.** The step runs each changed test file as its own command, using its suite's command. Every file runs at the first offset (`+7d`) before any file runs at the second (`+9d 11h`).
- **A 150 s budget** (`BUDGET_MS`). Before starting each file, and before each offset's clock proof, the step checks a monotonic clock (`performance.now()`), which libfaketime leaves alone here (`FAKETIME_DONT_FAKE_MONOTONIC`). Once 150 s have passed, nothing new starts.
- **What still runs.** A run already started finishes. If it failed with the clock ahead, it is then run on today's clock, because that run decides whether the test is date-bound.
- **What gets reported.** The step names each file and offset it did not start, says the nightly future-clock run covers them, and exits by what it found: 1 if a date-bound test was found inside the budget, otherwise 0.

### What it does not do

A single file can still run past 150 s, because a started run is never cut short. Dropping the second offset is not the answer: a test bound to a weekday is caught only there. The step's place in `ci.yml`, the 40-file cap and the two offsets are unchanged.
