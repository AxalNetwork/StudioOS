## D6413 — Share recommendation audience reads and window saved-event visibility (#6413)

Recommendation candidates already have a 200-event SQL cap. Evaluate their
audience rules together: validate every stored rule, read the union of segment
keys once, and lazily reuse one caller role/licence read, one persona read and
one invitation query. All memoized promises belong to that call; the next
request re-reads grants and revocations. The shared evaluator retains the
single-event helper's role, retained licence, allowed persona overlap, guest
and non-revoked user/email invitation rules. Malformed or unreadable audience
stores fail closed. Single-event callers retain their existing lazy reads.

Read saved events with a 100-row keyset window over `(created_at, event_id)`.
Join each window's event records directly and batch registration/invitation
grants only for rows the ordinary host/admin/published gate cannot admit.
Both single and batch paths use `canViewEvent`. A holder may still see a
private, cancelled or withdrawn event; an outsider cannot. Revoked or foreign
invitations confer no access. Preserve the complete ordered `saved` array;
there is no silent cap or new frontend pagination contract.

The window uses bound cursor parameters and JSON-bound ID sets, keeping the
number of SQL parameters constant. No schema, billing, ranking weights or
public response shape changes. No caller state is cached across requests.
The independent stored-array repair is #6414; this PR does not carry it.

Real SQLite regressions exercise 200 recommendation candidates and 260 saved
rows, query/row bounds, equal-date cursor ties, caller changes and revoked
licences/invitations, private/draft/unapproved access, retained registrations,
admin/host access, guests and persona overlap. Related event routes retain
their existing regression coverage. Validation and mutations are recorded
against the exact candidate in the PR.
