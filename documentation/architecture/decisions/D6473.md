## D6473 — The landing bot's model runner: Claude, then Codex, then Gemini, and the key never meets the code (#6473)

- **Status:** built. The live smoke waits on the owner's `repair` environment and its secrets. Part of #5600
  (plan key C2).
- **Why:** the conflict resolver, main repair and red-PR repair each need a model that edits files.
  `claude-code.yml` cannot serve: it runs only on an `@claude` mention, and it held a key and write access in
  one job. This repository is public and its tests are code from the PR branch, so a key must never be in a
  process that runs them. One shared runner keeps the provider order and the caps in one place.
- **Owner's answers (2026-11-16, on #6473):**
  - provider order: Claude, Codex, Gemini;
  - secret names as filed: `ANTHROPIC_API_KEY` or the federation variables, `OPENAI_API_KEY`, `GEMINI_API_KEY`;
  - a `repair` environment limited to `main`.
- **Design:**
  - `.github/workflows/landing-bot-model.yml` (`workflow_call`, plus `workflow_dispatch` for the smoke test)
    does four things:
    - validates the task with main's `prepare.mjs`;
    - resolves the branch to a commit of this repository;
    - runs up to three rounds of `landing-bot-model-round.yml`;
    - publishes the first passing round's patch as `landing-bot-model-patch`.
  - **Each round is two jobs.**
    - `edit` is in the `repair` environment:
      - permissions `contents: read` and `id-token: write`, and no App token;
      - it runs only main's runner, and installs its pinned SDKs with `--ignore-scripts`;
      - it reads the commit as data;
      - the model has read, list, search, read-data and edit-an-allowed-file tools, and nothing that runs code.
    - `verify` has no environment, no secret and `contents: read`:
      - it re-checks the patch with main's code, against hashes of the files it was made from;
      - it applies the patch and runs the task's verify commands, which may only be `node`, `npm` or `npx`,
        started with no shell and an allowlisted process environment.
  - **Feedback.** A failed verify's output goes to the next round as a data file.
  - **The patch format.** Whole-file replacements in JSON, with a manifest of before and after hashes, not a
    git diff. The keyed job therefore never runs git over the checkout, and a changed base or a tampered
    content is caught by the hash.
  - **Provider order.** It comes from `LANDING_BOT_PROVIDERS`. The runner moves on only for authentication,
    permission, billing or quota, rate-limit, overload, 5xx, federation or a missing credential. A wrong fix,
    or no fix, ends the round.
  - **No patch is emitted** when the edits touch a file outside the allowed list, delete a file, add conflict
    markers, or fail verification. Every allowed file must also clear `pathGuard`: no protected path, no T2
    path, no existing test.
- **Caps.** `HARD` in `task.mjs`, which callers can lower but not raise:

  | Cap | Limit |
  | --- | --- |
  | Model calls per round | 30 |
  | Minutes per edit round | 20 |
  | Rounds | 3 |
  | Allowed files | 40 |
  | Verify commands | 6 |
  | Data | 200 KB |
  | Verify minutes | 20 |

- **Short-lived credentials.**
  - **Claude** uses workload identity federation when the four `ANTHROPIC_*_ID` variables are set *on the
    `repair` environment*. A job there carries the subject `repo:AxalNetwork/StudioOS:environment:repair`,
    so it needs its own rule; the review's pull-request rule refuses it.
  - **Codex** uses `OPENAI_API_KEY` directly through the pinned SDK. The issue preferred the Codex action's
    proxied key mode, but that action would bring a shell and its own tools into the keyed job, which this
    design rules out.
- **Guard:** `frontend/test/landing_bot_model_6473.test.mjs` covers each acceptance item with stub providers:
  - a quota error falls through; a wrong fix does not;
  - a forbidden file or conflict markers yield no patch; a failed verify yields none;
  - the caps stop the run;
  - a test that prints its environment shows no key in any artifact;
  - `edit` has no write permission and runs no repository script; `verify` has no secret;
  - no other workflow names `repair`.

  Mutation-checked: leaking the environment, falling through on any error, editing any file and removing the
  turn cap each fail it.
- **Not in scope:** pushing, commenting, labelling, deciding when to run, and the daily spend check (the
  caller's `budget()`).
