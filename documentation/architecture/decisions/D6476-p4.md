## D6476 part 4 — A retryable wait is not a hand-back (#6476)

- **Status:** built by S21 on 2026-11-21 for the defect the owner's coordination comment on #6476 reported (S1), as part of #6481's conflict-recovery request. Local only: activation stays behind #5719, #5500 and the reviewed rollout gate.
- **Builds on:** D6476, D6476-p2, D6476-p3.

**The defect.** After a conflict ejection, the keeper's merge starts new checks on the repaired head. `decide()` saw them pending and returned `label`, and the sweep wrote `ejected`. `candidates()` drops any removal with an `ejected` label event at or after it, so when the same head went green nothing looked again. The first-entry feeder skips PRs with queue history, so the PR stayed out of the queue for good. Removing the visible label did not help, because the label *event* was read.

| Case | Before | Now |
|---|---|---|
| Checks pending, checks missing on a fresh head, evidence unreadable, head moved between reads | `ejected` | **wait**: no label; looked at again each sweep |
| A breaker, `[alert] merge queue stalled`, a per-PR or repo-wide daily budget, the queue-failure share | `ejected` | **wait** |
| Still waiting 24 hours (`RECOVERY_WINDOW_HOURS`) after the ejection | — | `ejected`: the owner re-queues |
| No consent, a failed required check, `bot:off`, a `repair/` branch, a fork, a `.gitattributes` change, a never-re-queued class | `ejected` | `ejected` (unchanged) |
| Conflict, first 20 minutes (`KEEPER_DISPATCH_MINUTES`) | keeper, every sweep | keeper |
| Conflict after that, no keeper merge yet | keeper, every sweep | **wait** for the keeper's own schedule |
| Conflict after the App's keeper merge of main | keeper, every sweep | `ejected`: a person resolves it |

**What is read again on each look:** the same evidence as first admission (`readHeadEvidence`: every configured required check by its source, and the trusted full-suite run on this head), consent, `eligible()`, breakers and budgets. Evidence is one of `green`, `pending`, `failed`, `unknown` or `changed`, and only `green` admits. The enqueue still carries `expectedHeadOid` from the head read in that sweep.

**Retryable eligibility:** `eligible()`'s "could not be read", "a breaker is open" and "does not allow this trigger". Any other reason is the owner's. A test pins each real `eligible()` reason to its side, so a reworded reason cannot silently change sides.

**Stranded PRs.** An `ejected` label event the App itself wrote before `RETRY_CUTOVER` (2026-11-21T00:00Z), on a removal under `STRANDED_DAYS` (7) old, makes the PR a candidate again. If it is restored, the App removes only its own label, and only after the entry is back. A label a person added, a hand-back written after the cutover, and a removal over 7 days old are left alone.

**A stranded PR's hand-back is final, and add-only (review on #8054, two rounds of P2).** A stranded PR already carries the App's pre-cutover `ejected` label, so adding that label again writes no event, and the next sweep would treat the PR as stranded again.
- **Round 1** removed and re-added the label. Round 2 showed that two separate writes can be interrupted between them, losing the visible hand-back, and could delete a label a person had just added.
- **Now:** the hand-back is recorded with an add-only App label, `bot:handed-back`. `candidates()` treats an App `bot:handed-back` event at or after the removal as final. Nothing is deleted on a hand-back, and an interrupted run is finished by the next sweep, which adds the label again.
- **On a restore,** the App removes its stranded `ejected` only after a fresh `issues/{n}/events` read shows the newest `ejected` event is still its own pre-cutover one. A person's newer label stays.

Two-sweep regressions cover:
- expired window → green;
- failed check → green;
- an interrupted hand-back finished on the next sweep;
- a person's label replacement before the restore.

**Only a positive mergeable admits (owner addition on #6476, 2026-11-21).** The sweep passes GitHub's fresh `mergeable` (`true`, `false` or `null`) to `decide()`:
- `true` is required for every class to be re-queued;
- an explicit `false` goes to the keeper flow, whatever the ejection's class, provided consent holds;
- `null` (not yet computed, or unread) waits.

The rest of that addition (the PR-list `conflict` indicator, and separating it from the keeper's hand-back label events) is a follow-up on #6476.

**Writes.** A wait writes no label. The sticky comment is written only when its text changes, so repeated sweeps are silent. A concurrent second sweep finds the entry already queued: its newest queue event is no longer a removal.

**Not changed:** consent (a person's or the landing App's own entry, D6476-p3), the T2 / model-resolved owner lane, the per-PR and repo-wide caps, `LANDING_BOT_ENABLED=dispatch` (no scheduled recovery), and the classes the owner allowed on 2026-11-16.

**Tests:** `frontend/test/landing_bot_ejection_recovery_6476.test.mjs` runs the real `sweep()` against an in-memory GitHub. It covers:
- conflict → keeper merge → pending → green, with exactly one native re-queue;
- duplicate sweeps that write nothing;
- one keeper ask, and a hand-back after an unresolved keeper merge;
- failed checks, a non-keeper commit and a manual removal, each handed back at once;
- unreadable evidence and a red main that recover;
- the 24-hour bound;
- a head that moved between reads;
- stranded labels, against a person's label and an old removal.

`landing_bot_ejection_6476.test.mjs` now separates the hand-back cases from the waiting cases. Three mutations are caught: pending treated as the owner's, the unchanged-sticky check removed, and the cutover ignored.
