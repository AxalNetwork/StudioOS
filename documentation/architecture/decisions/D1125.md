### 1. A linked card is its member's deck card (Worker)

The people and drawer reads (`GET /api/admin/network/people`, `/people/:ref`) now read the roster's `linked_user_id`.

- **Folding.** A card linked to an account in the network is that member's deck card. It no longer appears as a second, deck-only person, and the member's `deck` block is the card's: `{ roster_id, shown, reach, position, has_photo }`.
  - When two cards link the same account, the first in the deck's order wins and the rest stay deck-only.
  - A card linked to an account outside the network (a founder, say) also stays deck-only.
- **No card.** A member the roster holds no card for reads `deck: ok(null)`, not "Not recorded": the roster was read and holds none. #3014's table reads it "No deck card".
- **Failed roster.** If the roster read fails, every member's `deck` is that failure.
- **Archived cards.** An archived card (`archived_at` set) is out of the people list, as D974 takes it out of the roster's working list.
- **References.** A linked card's own reference, `roster:N`, opens its member in the drawer.
- **On the deck.** "On the deck" (`on_deck=true`) now finds a member whose card is on the slide. Overview's "missing deck photos" counts members' cards too.

### 2. Each member's stage, and the stage filter (Worker; "check first", built)

Part 1 (#2759, D973) closed without the stage S1 asked for: every row read "Not recorded". Now:

- **Source.** The snapshot reads D976's standing rows once, as the block `network_stages`, and Overview's C1 uses the same block instead of a second query.
- **Each person's stage** is D976's `stageOf`: onboarding, active, paused or ended.
  - A deck-only name has no account, so its stage is "Not recorded" with that reason.
  - A failed standing read makes the stage Unreadable, while the rest of the row stays.
- **The filter.** `stage=onboarding|active|paused|ended` filters the list. Any other value is 400. A stage filter on a failed standing read is 503, never an empty list. The read's `filters.stage` lists the four stages.

### 3. The person's History (Worker)

The drawer read's `history` block (it read "not recorded yet") now comes from HQ's audit log, `admin_audit_log`, which `logAdminAction` writes. One fixed statement, bound, at most 50 rows, newest first, with `truncated` when there are more.

- **A member's rows** are those whose target is their account: `network.paused`, `network.resumed`, `network.directory_hidden` and `network.directory_shown` (D976); `advisor_cohort.assigned` and `advisor_cohort.ended` (D960); and the deck-card writes D974 logs while the card is linked. The card's own writes, by card id, are included too, so a write from before the link still shows.
- **A deck-only name's rows** are its card's writes.
- **Each item** is `{ id, action, at, by: { id, name }, reason, cohort_cycle_id }`.
  - `reason` is set only for a pause or a resume, which D976 already shows.
  - `cohort_cycle_id` is set only for a cohort row.
  - No email, hashed actor, assignment id or other detail leaves the log.
- **Limits.** Nothing from before these writers existed is recorded. If the log cannot be read, `history` is Unreadable and the drawer still answers.

Drawing History in the drawer belongs to #3014's `PersonDrawer.jsx`, which is not on main yet. It renders the block as a whole (`Whole`), so a list of items follows once both are on main (§5).

### 4. The header tabs' counts (Worker and page)

- **`GET /api/admin/network/tabs`** answers four blocks:
  - `overview`: the number of items Overview's Needs you lists. These are computed by the same `needsOf` that Overview uses. One unread list makes the count Unreadable, never short.
  - `people`: the people list's length.
  - `firms`: the firms on record.
  - `deck`: the shown cards, not the hidden or archived ones.
- **On the page:**
  - One read per mount, beside the tab's own reads, reloaded by Refresh.
  - Each tab draws its count through `HeaderTab`'s `count`: a number, a dash whose tip says why, or the reading bar. A failed count is never a zero.
  - The People tab joins these counts when #3014 merges. Its `people` count is already in the read.

### 5. AP8b — a linked card's account fields (Worker and dialog)

- **The roster read.** Each linked card's `linked_user` in `GET /api/admin/network-profiles` now carries `account: { name, headline, company, has_photo }`:
  - the account's display name (or name), headline, firm name and whether it has a headshot;
  - a value the account does not hold is null;
  - never the headshot's key or an email.
- **The card dialog** draws these under the link chip, "From the account · read only". A value the account does not hold reads "Not recorded on the account".
- **The deck is unchanged.** It still prints the card's own fields; the dialog says so. **For the owner:** whether a linked card's deck fields should follow the account is a change to the deck, so it is left to you rather than built.

### 6. AP12b — a paused studio (page)

- **Why the canvas line is not used.** The canvas draws "HQ has paused this studio's admin access. Contact HQ. No data is drawn while access is paused." Reads are never paused on this platform (D107, D142). The Worker answers every read on a suspended branch, and refuses only writes, with a 423 carrying `branch_suspended`, or `admin_frozen` for a frozen admin. So "No data is drawn" would be false.
- **What is drawn.** When a write on the page is refused that way, `lib/api.js` announces it. The page then draws AP12b's card: "HQ has paused this studio's admin access. You can still read everything here. Changes wait until HQ lifts the pause." Its Contact HQ button opens `/admin/my-licence`, the appeal door the suspension bar uses. The page keeps its data.
- **UNVERIFIED:** whether the owner wants the canvas's blank page instead. That needs reads gated on the Worker, which is a platform decision, not this part's.

### 7. HQ Content's roster panel (Worker and page)

- **The defect.** The panel (`GET /api/admin/content/summary` → C4) labelled every inactive row "Archived". Since 551 that is two states.
- **The summary** now reads `archived_at` and gives:
  - each row a `state` of active, hidden or archived;
  - the counts `active`, `hidden` and `archived`, overall and by kind.
- **Order.** Hidden rows sort after shown rows and before archived ones.
- **The panel's pill** reads Active, Hidden or Archived, and its counts line names all three.
