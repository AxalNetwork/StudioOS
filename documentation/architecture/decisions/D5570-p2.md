## D5570 part 2 — Persist admission policy in Durable Object transactions (#5570)

DurableWorkspaceAdmissionStore implements the existing AdmissionStore using one Durable Object storage transaction for each synchronous policy transition. Queue sequence, generation, reservations and settlement identity commit atomically. Policy callbacks must be synchronous and provider/billing I/O remains outside transactions. A callback throw rolls back; no process-local Map is authority.

A real SQLite Durable Object fixture tests concurrent enqueue/admit, runtime disposal/restart using persisted storage, rollback, rejected asynchronous callbacks, stale fencing, replayed settlement and expired/unknown-provider reconciliation. A released lease returns its original charge on replay; this is settlement identity, not an independent payment ledger.

This is an unmounted storage component, not completion of part 2 integration. A future binding must route all tenants sharing a provider/region quota to the same coordinator; per-tenant objects would oversubscribe global quota. No binding, route, namespace, provider call or resource is enabled here. Existing engine admission must precede lease creation on the same run uid; compute reservation must join laneBudget and existing reserve/settle holds. Unknown provider cleanup retains the lease.

Remaining: preview-only host/binding integration, authenticated engine run ownership, existing holds/outbox and replay recovery, #5567 security-capability gate composition, metrics/thresholds, bounded state retention and the owner-approved quota UI canvas. Production changes require explicit authorization. Revert this component to roll back; there is no deployed storage to migrate or delete.
