## D681 — Configure StudioOS MCP enablement with the owner's OAuth namespace

Issue: #1555. Part of #1495. This extends D666/D669 without changing the MCP implementation, scopes, consent, proposal review or authorization rules.

### Configuration

The owner created `OAUTH_KV` on 2026-10-13. S1 confirmed its non-secret namespace id, `a536c75e7461447a89b1967d367c13ad`, in the latest #1555 comment.

- Replace all three `OAUTH_KV-PENDING` blocks in `wrangler.toml` with live bindings using that id: top-level, production and preview. Production explicitly redeclares the binding.
- Set `MCP_SERVER_ENABLED = "true"` at the top level and in production. Preview remains `"false"`, as the issue requests enablement only for the first two.
- Keep both OAuth discovery paths in `run_worker_first`; do not add an apex route or change the Worker entry.
- Branch configs remain disabled for MCP and omit HQ's `OAUTH_KV`. Adding a live HQ binding otherwise breaks the branch generator's KV rename map. This explicit exception preserves the current branch registries and never shares HQ grants with a branch. Unknown KV bindings still fail; branch-local MCP storage/enablement is separate work.

### Rollback

Set `MCP_SERVER_ENABLED = "false"` at the top level and in production, then use the normal `npm run deploy` flow. All MCP/OAuth/discovery/consent/grant routes return 404 while the flag is off or the binding is absent. Keep the binding and namespace intact; flipping the flag does not revoke or delete stored grants/tokens. Existing signed-in grant revocation remains available when MCP is enabled.

Branch renderer tests and mutation/restoration probes keep MCP off, omit HQ's OAuth binding, reject re-enablement and reject a copied namespace. The generic binding-parity and branch-config guards remain required. Full validation builds the root SPA before `npm run test:drift`; no build output, new secret or D1 migration is committed.
