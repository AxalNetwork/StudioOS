## D8416 — The credential guard names the workflow it cannot parse, and the queue checks it first (#8416)

### What happened

On 2026-11-24 the merge queue lost two rounds, at 06:05Z and 11:07Z. Each time
the candidate for #8015 failed `suite (rest)` and every candidate built on it
failed with it: seven the first time, nine the second. The log said:

```
YAMLParseError: Map keys must be unique at line 119, column 5
[guard] check-production-credentials: failed; exit=1
```

It named no file. The files were `.github/workflows/codeql.yml` (job
`analyze`) and `.github/workflows/semgrep.yml` (job `scan`), each with
`permissions:` twice in one job. Neither `main` nor #8015's head had that. #8093
had moved `security-events: write` from the workflow to the job, below
`runs-on:`. #8015, last pushed before #8093 landed, made the same move at the
top of the job. The two hunks do not touch, so git merged them without a
conflict.

### Decision

1. `scripts/check-production-credentials.mjs` reads each workflow with
   `parseDocument` and reports every parse error as
   `.github/workflows/<file>:<line>:<column>: <CODE>: <message>`. It goes on
   to the other workflows and exits 1. A file that parses but has no `on` or no
   `jobs` mapping is reported the same way instead of throwing. A workflow that
   could not be read drops its inventory rows from the "no longer reads a listed
   secret" check, because its jobs were not read.
2. In the merge queue, every suite part runs that guard before its own
   commands. `scripts/test-drift-parts.mjs` holds the list (`QUEUE_PREFLIGHT`)
   and runs it through `runPart`, so a failure leaves the same evidence file
   and `ci-failure-id` annotation as any other command. The queue's matrix is
   `fail-fast`, so the first part to get there stops the others. On
   2026-11-24 the guard reported 5 min 50 s into `rest`, at the end of
   `test:guards`, with the other eight parts running throughout. Run locally
   as a queue candidate with the two broken files, a Worker part now exits in
   under a second.
3. Every command in `QUEUE_PREFLIGHT` is also in `scripts/guard-commands.json`,
   so `test:guards` and the full-suite verdict still include it. On a pull
   request and on `main` the early check does not run: those runs report every
   part.
4. The check lives in the part runner, not in a new `ci.yml` step. The
   capacity pilot pins a digest of every ordinary CI job
   (`frontend/test/ci_capacity_pilot_7909.test.mjs`), so the `suite` job is
   unchanged.

### What this does not do

It does not stop a PR like #8015 from being queued. Its own CI is green,
because that ran before `main` changed. A check at queue time, that the PR's
merge with current `main` still parses, would have prevented both rounds. That
belongs with the landing tooling and is a separate decision.
