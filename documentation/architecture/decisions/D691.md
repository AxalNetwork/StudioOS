## D691 — Grow and Raise records: Grow writes production's compliance_events, and every record has a one-record read, a stable id, its activity and a store behind each canvas field

The Grow section (#1696, #1697, #1698) and the Raise section (#1699, #1700) are added under this heading by their own PRs. This file was started by #1705, the share-link signup guards below, because that PR reached `main` first. Whichever of these PRs merges after another merges `main` and keeps every section.

### Deck share signup guards

Issue #1705, found while checking #1699. `POST /api/decks/share/:token/signup` (`routes/deck_share_actions.ts`) creates a user account for anyone holding a live share token. It inserts a `users` row, an `activity_logs` row and an `onboarding_progress` row, then mints a session. It had neither guard that `POST /api/auth/register` has. Its comment said Turnstile was bypassed because "the share-token-gated flow already proves intent". It does not: a token proves access to one deck, and a link with no expiry and no view cap reaches whoever it is forwarded to. Its only ceiling was the generic 200/min/IP bucket, so one IP could mint about 200 accounts a minute from a leaked link.

**Turnstile, as register does it.** The body must carry `turnstileToken`, verified with `verifyTurnstile(env, token, clientIp)`. A missing or failed token answers 403 "Bot verification failed. Please try again." It also writes a `turnstile_failed` activity row, as register does. That row holds only a hashed email (`hashEmail`), a /24 (IPv4) or /48 (IPv6) bucket from `ipPrefix`, and the deck id, never the raw email or the full IP. The check runs after the token and the input are validated and before any other read or write. That includes the existing-email lookup, so a script cannot use its 409 to learn which addresses have accounts. With no `TURNSTILE_SECRET_KEY`, `verifyTurnstile` fails closed in production and open in development, as it does for register.

**A rate-limit bucket.** `deck_share_signup` in `middleware/rateLimit.ts`, beside `register`, allows 6 requests per 60 seconds per IP, `failClosed: true`, matching POST on `DECK_SHARE_SIGNUP` (`^/api/decks/share/[^/]+/signup$`). The pattern is anchored, so the share family's other routes (`nda`, `feedback`, `context`, `deal-pack`) stay on the generic bucket. If KV is down, the account-creating write answers 503 instead of running uncapped.

**The modal.** `ShareViewerSignupModal.jsx` loads Turnstile with `loadTurnstile` and the same site key as `RegisterPage`. It renders the widget on the signup step, sends `turnstileToken`, keeps Continue disabled until a token arrives, and resets the widget after a refused submit, because a token is single-use. When the widget cannot load (a bounded poll of about 10 seconds), it shows register's fail-visible line: "Human verification couldn't load — usually an ad blocker or strict network."

**Departure: the second sentence of that line.** Register's notice goes on "You can still continue with an emailed sign-in link below." That is true there and not here, because the modal has no other way to create an account. So the modal says instead "Allow challenges.cloudflare.com or try another network, then reload to create your account" (D-s). `api.deckShareSignup` is unchanged: it already sends its payload as given.

**Unchanged.** The existing-email refusal (409 `requires_login`), the role whitelist, the conversion log and the session mint.

### Raise writes (#1700), part 1: holders, links and data-room access

The first of #1700's two PRs. It builds the three things its writes stand on, each on its own owner-checked path, so the closing PR's cycle routes only call them:

- `addHolder()` and `updateHolder()` (decision 4);
- the share-link rules (decision 5);
- the data room's per-file access (decision 6).

The closing PR adds the cycle write routes, the record actions in `services/records/raise.ts`, form-options and each write's log row (decision 12), which needs D690 S18-A's `logCycleWrite` (#1690). No migration: #1699's 463 holds every column used here.

**Holders (decision 4, `services/capTableWrites.ts`).**
- Both functions begin with `ensureTier(actor, 'studio')`. A caller below `studio` gets its 402 and nothing is written.
- **Founders · Common** writes a `cap_table_holders` row:
  - on the venture owner's account (the user whose `founder_id` is the project's);
  - with `security_type 'common'`, `kind 'founder'`, the role, and the shares or `ownership_pct`.
  - With only a percentage, shares are set so the founder holds that share of the founding table.
  - It writes a `cap_table_vesting` row on the same `user_id` and `holder_id` when `vesting` is given, and a `founders[]` entry carrying `holder_id`, then returns `h-<id>`.
  - If the save fails, the register and vesting rows are deleted again.
- **Investors · SAFE or Convertible note** adds a `safes[]` entry (amount and cap from cents, discount from a percentage, `instrument: 'note'` for a note) and returns its `e-<n>`.
- Every other group or instrument answers 400.
- **What is checked before anything is written:**
  - a `prospect_id` must be one of this venture's prospects (else 404 "Prospect not found");
  - an `h-` id must be a register row of this venture (else 404 "Holder not found");
  - the inputs pass the tool's own `validateInputs`.
- Both recompute through `saveScenario()`'s POST path, which logs nothing; the caller logs.
- The tool's own save keeps a posted founder's `holder_id` only when it is a register row of this venture (`keepOwnHolders`), and a founder matched by name keeps the stored one.

**Links (decision 5, `routes/decks.ts`).**
- `createShareLink()` is extracted from `POST /:id/share`, which keeps its caps and its `ensureTier`.
  - A link with no `ttlSeconds` never ends: `expires_at` is `9999-12-31 23:59:59`.
  - A link with no `viewLimit` has none.
  - It stores the prospect or a label, `allow_download` and `allow_forwarding`.
  - The raw link is returned once; only its hash is stored.
- **One live-link predicate, `shareLinkLive()`:** not revoked, not past `expires_at`, and, with forwarding off, opened from the bound browser. The share read's claim, the heartbeat and every share action (`verifyShareToken` in `deck_share_actions.ts`) ask it.
  - So a revoked link stops everywhere at once.
  - A second browser on a forwarding-off link gets the same `invalid_token` as a bad signature.
- **With forwarding off, the first open binds that browser.**
  - The bound browser gets a random `HttpOnly; Secure; SameSite=Lax` cookie on `/api/decks/share`, and the link stores the cookie's hash.
  - The bind is one `UPDATE … WHERE bound_viewer_hash IS NULL`, so of two first opens only one wins.
  - Another browser gets 403 "This link was sent to someone else." and uses no view.
- The share read returns `allow_download`. The viewer (`PitchDeckPrintPage.jsx`, `canSavePdf`) hides Save as PDF when it is false. That stops neither a screenshot nor the browser's print, and the page claims neither.
  - An older link sends no field and keeps the button.
  - The refusal hint no longer says links are single-use or last 72 hours.
- The withdrawal is extracted as `revokeShareLink()`. It keeps the views.

**Data-room access (decision 6, `services/dataRoomAccess.ts`).**
- `tierAdmits()` is the one predicate:
  - `invited` (or no tier, as every file before 463) admits any active grant;
  - `committed` admits a grant whose investor is a committed prospect of this venture, matched by email, case aside;
  - `nobody` admits no one;
  - `access_expires_at` hides the file from midnight UTC of that date.
- The NDA gate still applies to what the tier admits.
- **Who asks it:** the investor room (`/shared`, `/shared/:projectUid`, the download), the `research.ts` room reads (`/diligence`, `/diligence/:grantUid`, its one-file read and the drafting material) and the advisor brief. The brief is counted as an invited investor who has not committed.
- **So a hidden file:**
  - is never listed;
  - is never counted, in `file_count`, `file_total`, `file_open` or `withheld_behind_nda`;
  - and its download or file read answers as a file that is not there.
- **Writes:**
  - the upload and the file PATCH take `access_tier`, `access_expires_at` (a date), `dd_request_id` and `checklist_item`;
  - a `dd_request_id` must be a request of this venture's own `dd_cases` (else 404);
  - the upload's `folder_name` creates that top-level folder on first use.
- The founder read returns each file's `access_tier` and `access_expires_at`, and each grant's `committed`.
- **The file tool (`dataRoomRead.js`, `DataRoomPage.jsx`):**
  - `accessNow` and `noAccessReason` apply the same rules, each with its own reason;
  - the panel marks the selected file's tier ("This file") and says a folder has none;
  - each tier's note says it is set from Raise › Data room's Upload and Edit file;
  - nothing on the page says the tiers are not built.

**Fail closed (D-s).** These three cases hide a file rather than show it:
- an expiry that cannot be read;
- a tier value the code does not know;
- a pipeline read that fails while deciding "committed".

A folder has no tier: access is set per file, and a folder is shown as before.

**Not in this part.**
- The Upload and Edit file forms that set a tier are D695's (S03-B, #1657). Until they land, a tier is set through the API.
- The Data room record's Access section and the `ROUTE_MAP.md` rewrite come with the closing PR.
