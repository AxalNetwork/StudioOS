## D691 — Grow and Raise records: Grow writes production's compliance_events, and every record has a one-record read, a stable id, its activity and a store behind each canvas field

The Grow section (#1696, #1697, #1698) and the Raise section (#1699, #1700) are added under this heading by their own PRs. This file was started by #1705, the share-link signup guards below, because that PR reached `main` first. Whichever of these PRs merges after another merges `main` and keeps every section.

### Deck share signup guards

Issue #1705, found while checking #1699. `POST /api/decks/share/:token/signup` (`routes/deck_share_actions.ts`) creates a user account for anyone holding a live share token. It inserts a `users` row, an `activity_logs` row and an `onboarding_progress` row, then mints a session. It had neither guard that `POST /api/auth/register` has. Its comment said Turnstile was bypassed because "the share-token-gated flow already proves intent". It does not: a token proves access to one deck, and a link with no expiry and no view cap reaches whoever it is forwarded to. Its only ceiling was the generic 200/min/IP bucket, so one IP could mint about 200 accounts a minute from a leaked link.

**Turnstile, as register does it.** The body must carry `turnstileToken`, verified with `verifyTurnstile(env, token, clientIp)`. A missing or failed token answers 403 "Bot verification failed. Please try again." It also writes a `turnstile_failed` activity row, as register does. That row holds only a hashed email (`hashEmail`), a /24 (IPv4) or /48 (IPv6) bucket from `ipPrefix`, and the deck id, never the raw email or the full IP. The check runs after the token and the input are validated and before any other read or write. That includes the existing-email lookup, so a script cannot use its 409 to learn which addresses have accounts. With no `TURNSTILE_SECRET_KEY`, `verifyTurnstile` fails closed in production and open in development, as it does for register.

**A rate-limit bucket.** `deck_share_signup` in `middleware/rateLimit.ts`, beside `register`, allows 6 requests per 60 seconds per IP, `failClosed: true`, matching POST on `DECK_SHARE_SIGNUP` (`^/api/decks/share/[^/]+/signup$`). The pattern is anchored, so the share family's other routes (`nda`, `feedback`, `context`, `deal-pack`) stay on the generic bucket. If KV is down, the account-creating write answers 503 instead of running uncapped.

**The modal.** `ShareViewerSignupModal.jsx` loads Turnstile with `loadTurnstile` and the same site key as `RegisterPage`. It renders the widget on the signup step, sends `turnstileToken`, keeps Continue disabled until a token arrives, and resets the widget after a refused submit, because a token is single-use. When the widget cannot load (a bounded poll of about 10 seconds), it shows register's fail-visible line: "Human verification couldn't load — usually an ad blocker or strict network."

**Departure: the second sentence of that line.** Register's notice goes on "You can still continue with an emailed sign-in link below." That is true there and not here, because the modal has no other way to create an account. So the modal says instead "Allow challenges.cloudflare.com or try another network, then reload to create your account" (D-s). `api.deckShareSignup` is unchanged: it already sends its payload as given.

**Unchanged.** The existing-email refusal (409 `requires_login`), the role whitelist, the conversion log and the session mint.

#### Verified

- `cloudflare-worker/test/deck_share_signup_guards_d691.test.ts` runs the real router over a baseline-sliced node:sqlite database, with a real signed share token and a recorder standing in for Cloudflare's siteverify. It also runs the real `rateLimitMiddleware` over an in-memory KV. Its seven tests check that:
  - a missing token, and an unsolved one, each answer 403 and insert no user;
  - the refusal row has the email's hash and `198.51.100.0/24`, and neither the raw email nor the full IP;
  - an existing email behind a failed challenge gets 403, not 409;
  - a solved token creates the user as before, and a second signup with the same email still answers 409;
  - the seventh signup in a minute from one IP answers 429, a second token from that IP is still limited, and another IP is not;
  - a KV outage answers 503;
  - the pattern matches the signup route and none of its siblings.
- `frontend/test/deck_share_signup_guards_d691.test.mjs` pins the modal's source (it reads `import.meta.env` at load, which has no value under `node --test`). It checks the loader and site key, `turnstileToken` in the body, the gated Continue and the reset, and the bounded poll that shows the fail-visible notice with its dark-mode classes.
- On `main`'s code, five of the seven Worker tests and all four frontend tests fail. The two that pass pin unchanged behaviour (the successful signup and its 409) and the new pattern's own shape.
- Twelve mutations each fail at least one test:
  - Turnstile ignored, or moved after the email lookup;
  - the raw email or the full IP logged;
  - the bucket failing open, at a limit of 60, or scoped per user;
  - the pattern unanchored;
  - the token not sent;
  - a poll that never gives up;
  - no widget reset;
  - Continue not gated.
