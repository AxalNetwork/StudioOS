## D6267 — Diligence reads: the investor's own access requests and each room's NDA status (#6267)

An investor's room requests (`data_room_access_requests`, migration 595) are written from a round-call response and from the deal page (`services/dataRoomRequests.ts`). Until now the only investor read of them was per deal (`GET /api/deals/:id/room-access`, D1153). `/research/diligence` listed only granted rooms, and a room said nothing about where its NDA stood.

### What the reads return now

**`GET /api/research/diligence`** gains two fields.

- **`requests`.** The caller's own requests, `[{ uid, project_name, state, created_at, decided_at, decline_reason, source }]`, newest first, capped at 100.
  - Only rows naming the caller (`investor_user_id`).
  - Only `open` and `declined` rows.
  - Only where no live grant answers the request, so an accepted request appears as a room in `items`, not as a request. An accepted request whose grant was later revoked appears in neither.
  - A declined request carries the founder's `decline_reason` and `decided_at`.
- **`requests_unreadable`.** When the request store cannot be read, the response is `requests: null` with `requests_unreadable: true`, never an empty list. The rooms still answer.

Each room row also carries **`nda: { status: none | out_for_signature | on_file, valid_until }`**. **`GET /api/research/diligence/:grantUid`** carries the same `nda` object.

### The venture's name on a request

`project_name` is returned only where the investor could already see the name on whatever produced the request:

| Source | Named when |
|---|---|
| A round call | The caller is that call's recipient (`round_call_recipients`). The call page names its company (D1226). |
| The deal page | The caller may open a deal on that venture (`investorHasProjectDeal`): invited to it, or committed on it. This is the deal page's own rule. |

Otherwise `project_name` is null, and the request is still listed. A deleted venture is never named. The query lives in `services/dataRoomRequests.ts` (`investorRoomRequests`), beside the two writers. That keeps `research.ts`'s rule that a room-table statement outside the diligence handler is bound to an owned project (`research_stores_scoping.test.ts`).

### One NDA status read

The deal page's room door read the NDA's status with its own query. That query moved, unchanged, to `services/dealAccess.ts` as **`ventureNdaStatus(env, projectId, readerId)`**, beside `hasActiveVentureNda`. It reads the venture founder's NDA (party A) with the reader (party B), newest first:

| NDA | Status |
|---|---|
| Active, not past its `valid_until` | `on_file` |
| Pending, or partially signed | `out_for_signature` |
| None of these | `null` |

Who reads it:
- The room door (`deal_workroom.ts`) returns it as `nda`, **with the same shape as before**, `null` included, so #5907's reader of that route is unaffected.
- The diligence reads show `null` as `{ status: 'none', valid_until: null }`.

`hasActiveVentureNda` and `projectNdaActive` stay the gate: what opens NDA files, and `nda_signed`. The gate also requires the founder's account to be active. The status read is what the investor is shown. There is still one gate and one status, not three copies.

### Not in this PR

- No frontend change. `frontend/src/lib/api.js` documents the new fields on `research.diligence` and `research.diligenceRoom`.
- No migration.
