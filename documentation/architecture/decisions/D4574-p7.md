## D4574 part 7 — H3: the skill library's entries out of the Worker script, and why `landingTemplates.ts` stays (#4574)

This part continues `D4574.md`'s H3 (the Worker script's size, #4573's
baseline). It is a part file (D5615), so `D4574.md` is not edited. Measured on
`origin/main` 1498e75708 with `scripts/perf/worker-bundle-baseline.mjs` over
the `wrangler deploy --dry-run` metafile, before and after on the same tree.

### `landingTemplates.ts` was measured and left in the script

H3's open list named `landingTemplates.ts` (215.4 KiB of the script) as the
next cut. Minifying the file's sections on their own with esbuild says what
those bytes are:

| Section | Minified |
| --- | ---: |
| 23 page renderers (`renderMinimal` … `renderCustomerAudience`) | 159.3 KiB |
| `LANDING_CONTENT_SCHEMA` (each template's editable fields and defaults) | 39.5 KiB |
| Content accessor, form, waitlist script, palettes | 7.2 KiB |
| Registry, provenance maps, helpers, dispatch | 11.8 KiB |

Three quarters of it is **code**: template literals that interpolate the
brand kit, map the founder's lists and branch on options. It is not a data
blob that can become a static file. Moving it out would need a template
language and an interpreter for 23 layouts, which is a rewrite, not a cut.

The schema is data, but it is read **synchronously on the public page**.
`/landing/:slug` and `/p/:site/:page` render every visit through
`renderLandingTemplate`. That path takes each blank field's default from the
schema, and the save, autofill and AI-fill paths clamp to it. If the schema
were an asset, a failed read would leave a founder's public page without its
defaults. Unlike an admin panel, a visitor's page cannot honestly say "could
not be read". Saving at most 39.5 KiB is not worth that new failure mode.

So the file stays as it is, and the next candidate on the list was taken.

### The cut: the skill library's entries

`skillLibrary.generated.ts` had grown to **421.9 KiB**, the script's largest
single input (it was 363.6 KiB when H3 was last measured). It embedded every
SKILL.md and every case. Only three Super Admin routes read the entries:

- `GET /api/admin/ai-agents/skills/library`
- `POST …/library/seed`
- `GET …/library/reconcile`

The only other runtime reader, the HQ list's coverage, needs only the slugs.

`scripts/build-skill-library.mjs` now writes two outputs. Both are
gitignored and built by `scripts/build-generated.mjs` (D5612).

- **`services/agents/skillLibrary.generated.ts`** is the index: the entry types,
  `SKILL_LIBRARY_SLUGS`, `SKILL_LIBRARY_DIGEST` (the SHA-256 of
  `JSON.stringify(entries)`) and `SKILL_LIBRARY_ASSET`. It is 5.2 KiB of the
  script.
- **`frontend/public/skill-library/library-<digest16>.json`** holds
  `{ digest, entries }`, a static asset built into `docs/`. The digest in its
  name means one deploy's script never reads another's library. A write
  removes any stale `library-*.json` beside it.

`services/agents/skillLibraryAsset.ts` reads the asset through the Worker's
assets binding. It follows the pattern of the article covers and the icon
geometry in `D4574.md`:

- It reads once per isolate and remembers the result. A failed read is not
  remembered, so the next request tries again.
- It refuses the SPA shell, a wrong digest, a slug list that differs from the
  index, and an entry of the wrong shape.
- It recomputes the digest from what it read, so a body that only *claims*
  the digest is refused too.

`checkLibrary` and `seedLibrary` now take the entries as an argument. Neither
has a default that would import them.

**Nothing reads as empty.** Where the asset cannot be read, each library route
answers **503 `library_unreadable`** ("The skill library could not be read.
Nothing was changed; try again."). It writes nothing and audits nothing. The
gates still answer first, as before:

- the Super Admin gate (403);
- the seed's 400 `reason_required`.

HQ's From Axal panel already shows a failed library read as "unreadable",
never as an empty list.

**Who can read it.** On `axal.vc`, the entries were only ever readable through
the Super Admin routes. A file under `docs/` would be served to anyone. So
`/skill-library/*` is added to both `run_worker_first` lists in
`wrangler.toml`. A browser's request reaches the Worker, which has no such
route and answers 404. The Worker's own binding fetch still reads the file.

The pull-request preview Worker (`wrangler.pr-preview.toml`) serves its
`docs/` build as-is. On a preview host the file is readable, as the same
files are in this public repository. Not changed here.

**The data is unchanged.** The asset's entries are exactly what the module
embedded: `JSON.stringify(entries, null, 2)` equals the old literal's bytes.
The slugs, the order (golden case first, then scenarios) and the 182 skills
are unchanged. The tests and `scripts/check-skill-library.mjs` read the same
asset from disk, through `test/_skill_library.ts` and `generatedEntries()`.
`generatedSound` now also checks that the asset is the generator's build and
that git does not track it.

That is −415.5 KiB raw, −77.9 KiB gzip and −60.0 KiB brotli (Total Upload:
−415.5 KiB raw, −78.2 KiB gzip; two dry runs of the same tree differed by
0.06 KiB gzip, so the last digit is not significant). The "before" build is
the same tree with `origin/main`'s `admin_hq_skills.ts`,
`skillLibrarySeed.ts` and generator put back, which makes every bundled input
`origin/main`'s. As with the icon
set, the compressed gain is smaller because the text is repetitive and gzip
already folded most of it; the raw figure is what the isolate parses.
`src/services` falls from 8,449.2 to 8,033.5 KiB. The largest single input is
now `landingTemplates.ts` (215.4 KiB), then `routes/research.ts` (138.2 KiB).

**Not measured:** isolate start time and CPU time. They need production
metrics, which this session cannot read. The asset read costs one
`env.ASSETS.fetch` and one SHA-256 of about 440 KiB per isolate, and only on
the three Super Admin routes.

**Still open on #4574, each its own PR:** a split of `services/` and
`routes/`, which still wants #4573's production CPU figures, and the Research
router extraction #4613 points to. That extraction is for maintainability:
`research.ts` would still be bundled, so it would not shrink the script.

**Tests.** `cloudflare-worker/test/skill_library_asset_4574.test.ts` (7) checks:

1. The asset is where the index says, and only that one asset is there. The
   index is the generator's build and carries no entry text.
2. The index and the asset agree: digest, recomputed digest, name and slugs.
3. The entries are byte for byte the old module's, and the asset is
   `renderAsset()`'s output.
4. The loader refuses the shell, a wrong digest, a tampered entry under the
   right digest, a reordered library, a wrong shape and a short library. It
   does not remember a failed read, and it remembers a good read.
5. Each route answers 503 and writes nothing; 403 and 400 still answer
   first; with the asset readable, every route answers as before.
6. Both `run_worker_first` lists carry `/skill-library/*`, and the Worker
   answers 404 there without relaying the file.
7. No source file imports anything but the index from the generated module,
   and the esbuild bundle of `index.ts` carries under 16 KiB of it and none of
   the entries' text.

Eight existing suites read the entries through `test/_skill_library.ts`:

- five that only read entries;
- the seed and reconcile route suites, which gained an `ASSETS` binding;
- `skill_case_identity_5336`, which passes the entries to `seedLibrary` and
  whose fixture build now writes the asset.

Mutation-checked: 13 mutants, each applied alone and the suite run against
it; 12 caught, 1 equivalent. The suite passes on the real code. Caught: the
index embedding the entries again (1), a route importing them again (1, 7), the
generator hashing pretty JSON (2, 4, 5), the asset dropping the scenarios
(2, 3), the loader trusting a claimed digest (4), the loader reading the SPA
shell as JSON (4, 5), the loader remembering a refused body (4), `GET /library`
answering an empty library (5), the seed reading the library before its reason
check (5), reconcile reading it before the Super Admin gate (5), the production
`run_worker_first` list losing `/skill-library/*` (6) and the generator keeping
a stale asset (1). The equivalent one drops the loader's slug-order check: the
digest is recomputed over the entries, so a reordered body can never pass, and
that check only refuses it before hashing. The "remembers a refused body"
mutant survived the first run; test 4 now reads each refused body twice on one
binding.
