## D9032 — HQ · Platform's cron, webhook and dead-letter incidents notify through the capacity episodes (#9032)

- **Status:** built by S23, 2026-11-27 (#9032).
- **Migration:** none. One KV key (`platform-capacity:dlq:mark`) in the existing `RATE_LIMITS` namespace.
- **Why:** `platformHealth.ts` detects a scheduled-job failure streak, a Stripe webhook refusal streak and waiting dead letters, but only on a page read (`PLATFORM_OBSERVABILITY.md` §7: "derived on every read … not stored"). Nobody heard about them unless someone opened HQ · Platform. `agents/alerts.ts` pushed dead letters only for `agent_run`.

### 1. The existing episodes, three more metrics

`sweepPlatformCapacity` (`services/platformCapacityHistory.ts`, every 15 minutes on HQ) now evaluates `readIncidentSignals` (`services/platformCapacitySignals.ts`) beside the capacity read. No new channel: the D4559 episodes open once per (scope, metric), change severity in place, clear on a measured recovery, can be muted, and notify active HQ Super Admins in-app once per episode and stage (dedupe key `platform-capacity:<scope>:<metric>:<episode>:<stage>`). Running the sweep again on the same reading touches the episode and sends nothing.

| Metric | Reads | Warning | Critical |
| --- | --- | --- | --- |
| `incidents.cron.failure_streak` | `readCronStreaks`: the longest streak of any declared trigger | `CRON_FAILURE_STREAK` | none |
| `incidents.webhook.refusal_streak` | `readWebhookHealth` | `WEBHOOK_FAILURE_STREAK` | `WEBHOOK_FAILURE_CRITICAL` |
| `incidents.dlq.new_waiting` | both dead-letter tables above the watch mark | 1 | `DLQ_HIGH` |

Every number is the one `platformHealth.ts` already uses; none is new. The page's `high` maps to warning and its `critical` to critical, except the dead letters, whose `DLQ_HIGH` (the page's `high`) is critical, as #9032 asks.

### 2. Sweep only, never snapshotted

The three metrics are not in the capacity read the page draws (the page already shows them as incidents) and not in `SNAPSHOT_KEY` (a streak or an arrival has no daily trend). With no measured history, an unreadable source can never open a freshness `unavailable` episode: it holds an open episode and opens none, as §5's existing rows do for an outage.

### 3. New dead letters: a mark that moves only when nothing new waits

"New since the last sweep" taken literally would open an episode on one sweep and clear it on the next, two notices for every arrival. Instead the watch keeps the highest id of each table already accounted for, in KV:

- the first sweep sets the mark and reports `unavailable`; the backlog already waiting stays the page's figure;
- the value is the count of letters above the mark that are still in their table;
- the mark moves up to each table's highest id only on a sweep that counts none, so an episode stays open while its letters wait and clears when they are replayed or discarded (`POST /api/infra/dlq/:id/retry`, `DELETE /api/infra/dlq/:id`, or `dead_letter_queue`'s 30-day prune);
- each table is read in one statement (its `MAX(id)` and the count above the mark together), so a letter arriving during the read is either counted or above the mark, never skipped;
- an unreadable KV mark or table is `unavailable`, never 0.

**`agent_run` is excluded**, from `cf_dlq_mirror`, which is where `agents/alerts.ts` (`dlqAlerts`) counts and reports them to HQ once per batch. Reporting them here too would send two notices for one letter. `dead_letter_queue` is counted whole: `agents/alerts.ts` does not read it.

### 4. Not routed to Slack

The sweep also drains section incidents to Slack (`sectionIncidentOutbox.ts`) and, when configured, delivers capacity episodes (`sectionCapacityDelivery.ts`). Neither picks up these episodes: the outbox drains section incidents, not `platform_capacity_alerts`, and the capacity delivery selects `metric_key = 'd1.size_bytes'` only. The new episodes reach the HQ inbox and nothing else.

### 5. Branches

`sweepPlatformCapacity` returns `{ skipped: 'branch' }` before any read when `branchOf(env)` is set, so a branch deploy notifies no one and writes no mark.
