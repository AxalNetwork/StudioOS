## D4658 — Spin-Out Lab: lifecycle transitions are atomic and recoverable (#4658)

- **Status:** built by S15 on `agent/claude-s15/4658-lab-lifecycle`, stacked on D4657 (#4657). Not merged.
- **Audit:** Spin-Out Lab audit 2 of 5 (findings 3–5), revision `d85951c`.
- **Migration:** `202611071730_cohort_notification_delivery.sql`. It is additive: six nullable or defaulted columns on `cohort_app_notification_ledger`, and one partial index.

### Decision

1. **A transition's prerequisite is in its own write.** Each guard is part of the statement that does the write, not a separate read before it:
   - **The week only moves forward.** `spinout_lab_week = MAX(current, computed)`, written only while the Lab is on. A request that read a stale week cannot write a lower one over a competing request's higher one.
   - **The week-4 close** writes only while the Lab is on.
   - **`/start` refuses a graduate inside its own UPDATE** (`RETURNING`), so an exit landing after the start's probe cannot be undone.
   - **A moderation reinstatement never reopens a sprint that ended** (`is_incorporated = 1`).
   - **The cycle activation never reopens one either.**
2. **The cycle activation is one batch per applicant.** Each batch (one D1 transaction) writes, in order:
   - the enrollment (D4657);
   - the admission flag;
   - the workspace;
   - the accepted application;
   - last, the applicant's own `activated`.

   An interruption leaves the applicant `approved` with none of the effects, and the next run does it whole. A resumed run also re-applies the effects of applicants already `activated`, so a row left by an older Worker, flipped before its effects, converges. The job completes, and the cycle goes `active`, only when every applicant is done. A failure is recorded as a cycle event, and the job resumes on the next tick.
3. **Approval and withdrawal have one winner.**
   - **The withdrawal** is one batch: the application, the pool row and the interview. It withdraws only while no admin decision is on the pool row.
   - **The approval** refuses a withdrawn application.
   - **The loser** is a 409: `decision_conflict` for the admin, `not_withdrawable` for the founder.
   - **What follows the winner.** The answers are deleted, and the interview cancelled, only by a withdrawal that won.
4. **A notification is durable delivery work.** The claim stores the message as `pending`; delivery marks it `sent` (with `attempts` and `delivered_at`), and a thrown failure marks it `failed`. The tick's `retryCohortNotifications` sends `failed` rows, and `pending` rows older than ten minutes (a send cut off mid-way). Each is first re-claimed by a conditional update, so two sweeps never send one notification twice. After five attempts a row is `abandoned`. The per-(user, cycle, type) idempotency is unchanged.

### Why

The audit found:
- two decisions that could both succeed;
- an activation that recorded "done" before doing it;
- progress writes that applied whatever the request had read.

Each repair puts the check inside the write it guards, or makes the write all-or-nothing. In a resumable step it is idempotent and runs until every effect has landed.

### Limits

- **`notify()` reports its own failures as `null`,** the same value it returns when the user's preferences send nothing. The retry therefore covers a cut-off send and a thrown failure, not one `notify()` swallowed. Telling these apart is a change to `notify()` for every caller, and is left out here.
- **Rows written before the migration** have no stored message, and are left as they are.
