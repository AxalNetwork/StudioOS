## D612 — Identity reads are audit-logged, and the KYC queue no longer carries the record

**An admin who reads a member's KYC record, the KYC queue, or a partner profile is written to `activity_logs`, the same way opening the ID document already is.** Issue #1312. No migration.

**What is logged.** Each successful read writes one row. `actor` is `hashEmail` of the admin. `user_id` is the admin. `details` names the action and, for a single member, that member's id. It never contains a name, email, date of birth, address, phone, ID number, EIN, or transcript.

- `kyc_record_access` — `GET /api/kyc/admin/:userId`.
- `kyc_queue_access` — `GET /api/kyc/admin/queue`. One row for the read, with the count of rows returned, not one row per member.
- `partner_profile_access` — `GET /api/profiling/admin/:email`. If the address has no user account, the details say so and do not include the address.

A 404 writes nothing. Opening the ID document stays `kyc_document_access`.

**The queue.** Its rows were carrying full `kyc_data` only so the review window could fill itself without another read. The list the table draws (name, email, role, provider, submitted) does not need those fields. The queue no longer selects or returns `kyc_data`. Review calls `GET /api/kyc/admin/:userId`, which is the logged record read, and the window draws that response. Masking inside the window is not this change (#1165, area 7, item 6).
