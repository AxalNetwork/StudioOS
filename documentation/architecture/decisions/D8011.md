The existing flow orders supported requests, checks enablement, consumes a
durable minute counter, authenticates against the fixed GitHub issuer, reads
a bounded body, and invokes the submission or receipt transport. Authentication
fetches bounded JWKS, imports the selected key and verifies each signature.
Claims bind issuer, audience, repository, subject, token times, run and attempt,
and workflow/source formats. Transport then checks the configured repository ID,
pinned planner or direct executor workflow, source, event and attempt. The
submission plan digest and the receipt's current generation/profile/ownership
checks remain separate authority boundaries. The helper replaces none of those
checks. The cleared canonical endpoint warning is not reopened.

### Proposed bounds

These are conservative policy constants, not measured capacity. Key cache and
native-work concurrency are scoped to one authority instance. Rate reservations
must use the injected atomic durable store scoped to the repository authority.

| Work or state | Ceiling and behavior |
| --- | --- |
| Key origin | Only `https://token.actions.githubusercontent.com/.well-known/jwks`, GET, redirects refused |
| Provider document | 65,536 decoded bytes, 128 chunks including empty chunks, 20 RSA/RS256 signing keys |
| Key fields | Unique 1–200 character key ID, modulus at most 1,024 base64url characters, exponent at most 16, allowlisted public fields only |
| Key lifetime | Five minutes from a complete valid response, no expired-key fallback |
| Refresh | One fetch at a time, at least 30 seconds between attempts, including failures and unknown IDs |
| Key waiters | 16 maximum, no unbounded per-key miss table or waiting queue |
| Provider deadline | Five seconds for headers and body together, abort and reader cancellation on timeout |
| Non-cooperative operation | Timed-out raw fetch/read retains its single slot until actual settlement, late data cannot enter the cache |
| Ordinary authentication | 128 attempts per UTC minute, six concurrent, failed attempts are charged |
| Proven receipt authentication | Separate 96 attempts per UTC minute and two concurrent slots, signature and claims still checked every time |
| Authentication deadline | Five seconds including durable reservation, a timed-out raw operation retains its local slot until settlement |
| Receipt continuation proof | SHA256 fingerprint of the exact already verified bearer token, at most one per caller and 32 total, at most 30 seconds and never beyond verified token expiry, no raw token stored |
| Receipt work | 96 attempts per minute, four concurrent, 12 per repository/run/attempt, at most 32 caller entries |
| Submission work | 24 attempts per minute, two concurrent, four per repository/run/attempt, at most eight caller entries |
| Stored budget state | One bounded current-window record with separate authentication and work counters, at most 40 caller tuples, canonical fields only |
| Reset and failure | No refund for failed work, no eviction of a caller to reopen its quota, restart uses durable counters, backwards clock movement cannot reopen a window |

At most eight signature-verification operations and six authenticated work
callbacks can be active in one instance. There is no admission waiting queue.
Fixed windows permit a bounded burst across a minute boundary. Key misses do
not allocate state by arbitrary key ID. Ordinary requests cannot spend the
protected authentication pool or either authenticated work pool without proof.
A caller that already possesses a receipt bearer token is still constrained by
verification, durable per-caller quotas and the receipt's owned generation.

### s39 integration proposal

1. Construct one `CapacityIssuerKeys` and one `CapacityRequestBudget` per
   `CapacityControl` instance. Never construct a key cache per request. Supply
   the budget with an atomic durable `CapacityBudgetStore.update` implementation.
   It loads the current window, calls the decision function, persists its
   returned state and only then resolves `accepted`. Durable Object storage
   transactions can store this bounded record under a dedicated key. No new
   schema or binding is part of this child. Store errors must refuse work.
2. In `ciCapacityAuth.ts`, inject the key provider after the existing bounded
   bearer/header parse. Pass that header's `kid` to `keys.get(kid)`. Use the
   returned public JWK for the existing import and verify calls. Retain the
   fixed issuer, canonical endpoint, RS256 restriction and every existing
   audience/repository/subject/time/run/attempt/source check. Do not cache
   identities or successful signature results. Include the already validated
   numeric `exp` in the typed identity passed to the budget.
3. In `ciCapacityRuntime.ts`, perform synchronous method/path, environment-flag
   and bounded bearer checks before expensive work. A false environment flag
   can refuse immediately. Keep asynchronous durable kill-switch reads inside
   admitted verification/work, rather than allowing unlimited storage reads
   ahead of admission. Call `budget.run(verify, authorize,
   work, progress)` **before** adding a task to `ordered`. The verification
   callback checks the durable kill switch and performs the original
   authentication on this exact request. Recheck enablement when admitted work
   runs. The trusted authorization callback checks the pinned planner or direct executor
   identity, including configured repository ID, workflow revision, event,
   source and attempt. Request paths and body fields alone cannot select a
   protected lane. Unrecognized identities return null.
4. Only inside the admitted work callback read the bounded body and enqueue
   the existing ordered transport call. Preserve all exact plan digest,
   parent/source, receipt generation/profile/ownership, kill-switch and current
   provenance checks there. Reservations include time spent waiting for the
   ordered callback, bounding that queue to the admitted work count. Preserve
   independently authenticated owner controls and alarm/publication progress.
   Do not put unbounded authentication waits ahead of alarms in `ordered`.
5. For receipt continuation, pass the exact bearer token the verifier consumes
   as `progress.token`, extracted by trusted server code from Authorization.
   `progress.ownedReceipt` is a trusted callback that returns true only when
   the original receipt transport returns an active, current, owned receipt.
   Only that successful result promotes the token fingerprint for subsequent
   admissions. A false result, exception, unverified token, or path grants no
   priority. Continue to verify the token and current receipt on every use.
6. Do not stack the old shared 120/minute gate ahead of the new protected
   lanes, because that would consume their admission capacity first. Replace
   that gate only in s39's reviewed composition with the durable separate
   counters. Do not replace it with an in-memory global counter. The child
   helper has no default ephemeral budget store.

The first receipt, a new token, a restarted instance or an expired continuation
proof must bootstrap through ordinary authentication capacity. Reusing a still
valid exact token for short receipt progress windows is an integration choice
s39 must review with the reader owner. This does not bypass verification or
extend token expiry. The helper cannot promise admission of every new valid
token under unrestricted traffic. Trusted ingress controls, upstream capacity
and operation/body deadlines remain composition and pre-activation gates,
including coordination with #8009. No universal denial-of-service resistance,
live throughput, global fleet capacity or production fairness is claimed.

### Local follow-through

The integration report now makes the synchronous environment check and admitted
durable kill-switch reads explicit. A storage-integrity regression found that
false-like non-null native-store values could be interpreted as a missing
window. The helper now refuses all non-null malformed values before verification
or work. Null remains the typed absence sentinel. The SQL integration adapter
must separately refuse an existing row whose decoded value is null or malformed,
so only a genuinely absent row can initialize a window. s39 retains that adapter.

The updated helper suite has 19 passing tests on Node 22 and 26. The new guard
mutation is caught in addition to the original 21. These are local fixture and
SQLite review results, not evidence of a writable live row or an activation
approval. The exact composed revision and its independent verification are
recorded with the follow-through delivery. Publication remains held under #5719.
