- **Status:** built by S07, 2026-11-22, from fixtures (the session cannot reach Google). Part 2 of #5840; part 1 is `D5840.md` (#6588). #5839's picker and token (#6586, `D5839.md`) are on main.
- **Code:** `services/searchConsoleTrigger.ts` (new: the token adapter and the one start path), `routes/search_console.ts` (two handlers), `services/searchConsoleSync.ts` (two error codes, a 503 refusal status, the venture gate exported). No migration, no new table, no cron entry, no client module.
- **Test:** `cloudflare-worker/test/search_console_sync_trigger_5840.test.ts`, through the routes against a fake Google.

### What is decided

- **One selection, one token.** The sync reads the venture's row in `search_console_selections`, which D5839's `PUT /api/search-console/property` writes. Its token is `searchConsoleAccessTokenForUser(env, selection.user_id)`, the binding member's own connection, refreshed behind D5839's lease. No other store or grant is read.
- **The token's refusals are translated, not guessed.** `searchConsoleSyncAccessToken` maps D5839's codes onto the sync's:

  | D5839 code | Sync code | Selection |
  | --- | --- | --- |
  | `search_console_grant_revoked`, `_grant_changed`, `_not_connected`, `_connection_unreadable` | `grant_revoked` | marked `revoked` |
  | `search_console_refresh_busy` | `token_busy` | unchanged |
  | `search_console_token_failed` (Google's token endpoint) | `google_unavailable` | unchanged |
  | `search_console_token_invalid` | `malformed_response` | unchanged |
  | anything else | `token_unavailable` | unchanged |

  Without this, part 1's `call` read any foreign error as `grant_revoked`, so a busy lease would have unbound the property.
- **One start path.** `triggerSearchConsoleSync(env, user, project, trigger)` is the only way a sync starts. In order, before any Google request:
  1. `GOOGLE_SEARCH_CONSOLE_APPROVED` is `1` (D5839's flag), else 503 `search_console_unavailable`;
  2. the caller can write the venture (`canAccessProject` with write), else 400 `project_required`, 404 `project_not_found` or 403 `forbidden`;
  3. the venture has a selection, else 409 `no_property_selected`;
  4. the caller is the member whose connection serves it, else 403 `not_your_binding`;
  5. that connection is active and switched on for the venture's company (`projectEnabled`), else 409 `not_connected` or `company_not_enabled`;
  6. part 1's own refusals: 409 `property_malformed`, `property_denied`, `property_revoked`.

  A later scheduled or on-connect caller loads the binding member and calls the same function with `trigger` `cron` or `connect`, so it passes the same checks, the write gate included. That caller, and any `[triggers] crons` entry, is not built and not authorised here.
- **The narrowest gate for a start is the binding member.** A sync spends that member's Google grant and quota, as `POST /property/check` does, so a teammate is refused (`not_your_binding`) even when they can write the venture. Reading the results needs only read access to the venture.
- **Dark until approval.** Both routes answer 503 `search_console_unavailable` until the owner sets the flag. The results read checks it too, so nothing about Search Console is served before the owner has approved the client.
- **No search query anywhere.** The sync never requests the `query` dimension (part 1). The routes log only the run's status and its error code, never the property, a page, a figure or a token.

### The contract #5841 calls

`POST /api/search-console/sync` with `{ "project": <id> }`, signed in, not a support session.

- A refusal is `{ error, detail }` with the status and codes listed above. Every code has a sentence in `SEARCH_CONSOLE_REFUSALS`.
- A run that started answers 200 `{ ok: true, sync }`. `sync` carries these fields:
  - `status`: `ok`, `partial`, `failed`, `denied`, `revoked` or `busy`;
  - `run_id`, `site_url`, `range_from`, `range_to`, `fetched_through`;
  - `days_written`, `weeks_written`, `corrections`, `requests`, `retries`;
  - `error_code`, and `detail`, its sentence from `SEARCH_CONSOLE_SYNC_OUTCOMES`, or null.

  `busy` means a run of the same property is in progress (`sync_in_progress`). `partial` kept the whole chunks before the failure.
- The run is synchronous: at most 60 Google requests with bounded backoff (part 1's `LIMITS`).

`GET /api/search-console/results?project=<id>`, signed in, a reader of the venture, not a support session. It answers 200 with `searchConsoleWeekly`'s answer (`D5840.md`, "Weekly figures") plus `last_error_detail`:

- with no selection, `{ property: null, reason: 'Not recorded: …', weeks: [] }`;
- before a first good sync, `weeks: []` with `Not recorded: no sync yet` or `Unreadable: the last sync failed (<code>)`;
- otherwise these fields:
  - `property` (`site_url`, `property_kind`, `access_state`), `search_type` `web`, `data_state` `final`, `timezone` `America/Los_Angeles`;
  - `units`, `top_rows_note`, `initial_from`, `fetched_through`;
  - `last_status`, `last_error_code`, `last_error_detail`, `last_success_at`;
  - `weeks[]`: each week's clicks, impressions and weighted CTR (null with a reason when nothing was reported or no impressions), `complete` or why not, and `top_pages`, labelled `top_rows_only`, with `truncated`.

The screen shows a null figure as its reason, never as 0. It never adds top pages into a total.
