## D5567 part 3 — a real authorization revision for the workspace broker (#5567)

**Status:** S14, 2026-11-16. The owner chose option A on #5567 (2026-11-16): close the constant revision with per-member revision triggers. This builds it.

### The gap it closes

Part 2's first open item:

- `authorizeCompute` answered `revision: 1` for every sponsor, so the grant service's revision fence (D5567) never tripped.
- Authority was still re-read from D1 at every redemption, so a revoked sponsor was refused.
- But a sponsor revoked and re-granted within one grant's life (60 s at most) kept that grant, and kept the run registered under the old authority.

### What it does

**Table.** Migration `202611161330_5567_agent_authz_revisions.sql` adds `agent_authz_revisions (member_id, revision, updated_at)`.

- A member with no row is at revision 1.
- The first change inserts revision 2, and each later change adds one.
- Rows are written only by triggers.

**Triggers.** Each fires on a change that can take access away, and bumps the member whose access it is:

| Table | Fires on |
| --- | --- |
| `user_company_links` | a row deleted, or its user or company changed |
| `project_members` | a row deleted, or its status, role, user or project changed |
| `account_licences` | `revoked_at` set or changed, or the row deleted |
| `users` | `is_active`, `role` or `founder_id` changed (a write of the same value does not fire) |
| `team_agents` | `status` or `sponsor_user_id` changed (both the old and the new sponsor are bumped), or the agent deleted |

Granting access (a new link, membership or licence) does not bump: it cannot widen a grant issued before it.

**Bridge.** `authorizeCompute` returns the sponsor's current revision, read by `authorizationRevision`. If the revision cannot be read, it refuses (`allowed: false`); it never assumes 1.

**What changes for a running job.** The grant service compares a grant's revision, and the revision its run was registered at, with the current one. So after any revocation-type change to the sponsor, every earlier grant for that sponsor's runs is refused, and so is any new grant for a run registered before the change, even once the same access is back. That is fail-closed by design. A compute job is short; a job cut off this way ends as the compute host already ends a refused one. A new run registers at the new revision.

### Over-counting, accepted

The revision is per member, not per company or project. A change to a member's access anywhere, for example leaving an unrelated company, also ends their in-flight compute grants. That only refuses early, never late, and keeps one row per member.

### Tests

- `cloudflare-worker/test/agent_authz_revisions_5567.test.ts`: 7 tests on the migrated schema.
  - Each trigger fires on what it should.
  - Each stays quiet on grants, renames and same-value writes.
  - An unreadable table reads as refused, not as 1.
- `workspace_security_matrix_5567.test.ts` case 2b, on the real bridge:
  - an unrelated member's change leaves the run alone;
  - the sponsor deactivated and re-activated: the grant from before is refused, and so is a new grant for the run;
  - the revision reads 3 after the two changes;
  - an unreadable revision refuses.
- Mutation check: 14 mutations, 14 caught. Each trigger's event, column list and `WHEN` was weakened in turn, the new-sponsor bump was removed, the bridge read was set back to the constant, the unreadable read was turned into 1, and the refusal was dropped.

**Rollback.** Reverting the Worker leaves the table and its triggers, which only write their own table and are harmless; the old Worker ignores them. Dropping them is a later migration if ever wanted.
