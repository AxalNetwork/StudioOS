- **Status:** built 2026-11-10 (S12). Work package 1 of 5 of the Offers UI/UX audit (#4841–#4845).
- **Canvas:** Offers V2 (#4872), approved as is by the owner on 2026-11-10: boards **OF-01** (A populated, B new firm) and **OF-09a** (phone overview). The export was not yet in `design/incoming/` when this was built (S1 lands it under D4872), so the build reads the canvas page `Offers v2 Page.dc.html` on the linked canvas directly.
- **Builds on:** D403 (board anchors, crumbs back to `/offers#of-…`), #4696 (the root and the zones read the same records), #4697 (per-source states and retry), D575 (phone lenses).

### What the root shows, top to bottom

1. **A first step, for a new firm only** (OF-01 B): when the catalogue was read and holds nothing, "Start with what you sell" with one primary action, Add your first service (to `/offers/catalog`).
2. **Five readiness figures** (OF-01 A, in its order), each a link to the zone that prints the same number:

   | Figure | Value · note | Read, and the zone rule it is held equal to |
   | --- | --- | --- |
   | Services live | live · of total, drafts, unlisted | `GET /services/offerings?mine=1`; Live = priced and listed, the Catalog zone's `catalogState` |
   | Perks | live · in review, submitted | `GET /perks/partner`; `perkListingCounts`, the Perk deals zone's own function (Live = approved and not ended) |
   | Client-approved proof | count · of items | `GET /offers/proof`; the worker's `published_count`, which the Proof zone's Published tile prints |
   | Audience fit | rules in use · missing a reply | `GET /offers/fit-rules`; active rules, and the worker's `unstated_count` |
   | Testing programmes | live · waiting for HQ, drafts | `GET /partner/testing/programmes`; live = approved, open or testing, the Testing zone's Live chip |

3. **What needs attention**, at most three items. Each comes from a recorded state, names one zone and carries one direct action to it. In priority order:
   - Proof: no proof recorded (Add proof), or some proof has no client approval (`self_stated_count`, Request approval).
   - Audience fit: no rule in use (Add a fit rule), or rules in use with no reply (`unstated_count`, Review audience fit).
   - Testing: a programme HQ sent back (`rejected`), else a firm draft to submit (Review programme).
   - Catalog: services with no price, so not live (Open catalog).
   - Perk deals: perks rejected in review (Review perk deals).
   - Visibility: engagements with no source (`unattributed_count`, Review attribution).

   The list waits until every read has settled, so items do not reorder or slip past the cap as reads arrive. The count line says "3 of N" when more are found than shown. A failed read adds no item. When nothing qualifies the section says so in words. A new firm gets no Proof, Fit or Catalog gaps: its one step is the catalogue.
4. **Grouped previews**, Sell (Catalog, Perk deals) · Prove (Proof, Visibility) · Target (Audience fit) · Test (Product testing). Each zone shows its board summary line, up to three of its own rows and a link to the zone. The zone notes (how a figure is counted, the views and lead-ratio refusals, the attribution gap) stay, behind a "How this is counted" disclosure rather than as permanent prose. Each preview keeps its board anchor (`of-catalog` …), so a zone crumb still lands on it (D403).

### Honesty

- A loading read shows a skeleton. A failed read reads **Unreadable**, never zero, and one Try again re-reads only the failed reads.
- A field the read did not carry reads **Not recorded**.
- A zero is shown only when a read succeeded and counted nothing (the canvas's "zeros as measured zeros").

### How it is built

- **`frontend/src/workspaces/boards/offerReadiness.js`** holds the derivation as pure functions: `readinessMetrics`, `attentionItems` (cap `ATTENTION_CAP = 3`), `isNewFirm` and `zonePreview`. They read over the states `useBucketSources` returns for `partnerOffers.js`'s own `sources`. There is no new Worker route, no new API method and no aggregate read; the canvas's OF-10 names a summary endpoint optional (#4696).
- Three zone rules are **mirrored, not imported**, because each lives in a page the router loads lazily: `catalogState`, the Testing zone's `VIEW_STATUSES.live`, and the Proof tile's `published_count`. `frontend/test/offer_readiness_4841.test.mjs` imports the real page functions and holds each mirror equal to them.
- **Opt-in.** The Offers board sets `overview: 'readiness'`, and `PartnerBucketRoutes` renders `OfferReadiness` for that board alone. Every other root still renders `BucketBoard` or `BucketOverview`, unchanged.
- **Zone row.** The Offers bucket in `shellConfig.js` declares `groups` (`OFFER_GROUPS`). `ZoneNav` draws the same pills under the group labels on the same single row, with an Overview pill first that is current on the root. The routes are the same, and so is the zone order in the bucket. No other bucket declares groups, so every other zone row renders as before.
- **Intro line:** the canvas's "Package what your firm sells, prove it works, and tell Axal which opportunities fit."

### Desktop and phone

- **Desktop (≥1024px):** the five figures in one hairline strip, three attention cards in a row, and the group previews in two columns.
- **Phone (<1024px):** the figures in two columns (the fifth spans both), attention cards stacked with full-width 44px actions (the first one amber, OF-09a's single primary), and the previews in one column.

### Where the build departs from or reads the canvas

- **Five figures on the phone, not four.** OF-09a shows four (it slices the strip). All five are kept, so the phone does not hide the testing figure that the desktop shows.
- **Zone switcher on the phone.** OF-09a draws a dropdown ("Offers · Overview ▾"). The build keeps the existing pill row, grouped and wrapping, which on a phone already switches lenses in place (D575). Adding a second, phone-only control is left to #4845's responsive QA.
- **Labels and order in Prove.** The canvas lists Proof before Visibility. The zone row and previews follow that within the group. The bucket's zone order (and so the zone URLs, the board and the route map) is unchanged.
- **Attention copy is fitted to what is recorded.**
  - The canvas's "3 testers to review / Review applicants" needs a count of unreviewed applications. The programme list serves only `applicant_count`, which includes picked and declined applications, so no applicant item is drawn. The testing item is a sent-back programme or a draft.
  - The canvas's "Request approval" item uses `self_stated_count` (no live client consent), which counts awaiting, withdrawn and never-asked items together. Its body says "no client approval yet" rather than "self-stated".
- **Heading:** "What needs attention", as on the canvas. The issue's "recommended actions" is not used as copy (Eadwyn voice rule).
- **Group previews link every zone.** The canvas puts one link in each group header (Catalog →, Proof →). Each zone in a group gets its own link here, so all six zones stay one click from the root.
- **Not built here:** a Visibility trend and a Superseded consent state need backend support (#4872, OF-10). Proof and Audience-fit flows are #4842. Catalog, Visibility and Testing clarity is #4843. Typography and the shared form system are #4844.
