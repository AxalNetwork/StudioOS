### The trigger

The binding owner with readable access (the same condition that shows **Import responses**) sees **Check for deleted responses**. Nothing runs on mount, on sign-in return or after an import: each run is one explicit click and one `typeformApi.reconcile(projectId)` call, which makes one bounded pass step (D5828 part 4: at most 8 lookups of 25 ids). While `status.reconcile_in_progress` is true the button reads **Continue deleted-response check**. Under the counts the status shows **Last deleted-response check:** `status.last_reconciled_at`, or "Not recorded" when no pass has finished. It also says that a response deleted in Typeform is withdrawn only after two checks an hour apart both miss it.

### The states

The answer's `outcome` picks the sentence (`reconcileNotice`). Counts come from `result`. A missing or malformed count reads 0, never a guess.

- `ok`: "Deleted-response check finished." with checked, confirmed deleted (answers and evidence withdrawn), missing for the first time and back again.
- `partly`: "Deleted-response check is part way." with the same counts and an instruction to continue. It never says finished.
- `busy`: an import or check already holds the form; try again.
- anything else (a stored failure such as `rate_limited`, or an admission outcome such as `not_selected`): stopped before it finished; nothing unread was marked deleted; read the status first.
- a refusal (HTTP error): `typeformFailure`'s house sentence, never the server's `detail`. `not_bound` gains its own sentence; `not_your_binding`, `binding_lost`, `typeform_unavailable` and the rest keep theirs. The counts already on screen stay.

After any run the journey reads the status again, so the completed count and the last-check time are the server's.
