## D8520 — Skill evaluation cases that need no model, run in pull-request CI (#8520)

- **Status:** built by S10, 2026-11-25 (#8520, row B4 of #8509).
- **Migration:** none.
- **Why:** the skill library's evaluation (`skillEval.ts`, `skillAssertions.ts`, `skillCaseIdentity.ts`, `skillEvalCompare.ts`) runs from the HQ console, with a model. Nothing evaluated a pull request that edits a skill's text, reads or assertions before it merged.

### 1. Which cases need no model

A case's result needs no model when it carries **known outputs**: a #4588 scenario's known-correct output and its targeted incorrect outputs (`skills/scenarios/<slug>.json`). Those cases are **deterministic**. A golden case (`skills/cases/<slug>.json`) carries no output. Its judgement needs a model run on the board, so it is not deterministic here. Its shape and reads are still checked.

`skillEval.runCaseWithoutModel(skill, case)` is the model-free run mode. It is pure, and each check fails with its own code and a sentence:

| Check | Fails when |
|---|---|
| `case_invalid` | `checkCase` refuses the case: the assertion shape |
| `output_kind_mismatch` | the case expects another output kind than the skill proposes |
| `read_not_granted` | the case feeds a read whose source the skill's tools do not grant: the skill has lost an input its case needs |
| `correct_output_fails` | the known-correct output does not pass `judge()` |
| `incorrect_output_not_caught` | an incorrect output passes, or fails on another assertion than its target: the skill has lost or weakened an assertion |
| `incorrect_output_invalid` | an incorrect output's edit text is not in the correct output exactly once |

The required inputs checked are the reads a skill's cases feed. #4667's input matrix (`skillInputs.ts`) is not used: some of its required inputs are granted outside the skill's tools. `fund.performance` is granted by a rule book (D4667-p4), and `manual:` inputs are supplied by hand. Holding the matrix to the tools would fail `lp-quarterly-letter-draft` and `contract-risk-issue-spotting` for no fault.

### 2. The step

`scripts/check-skill-eval-cases.mjs` is a guard in `scripts/guard-commands.json`, after `check-skill-library`, so `npm run test:guards` runs it in the `rest` part of every pull request's suite. That includes the draft fast tier. `.github/workflows/ci.yml` is not edited. No model is called.

- **Which skills run.** It diffs from `--base`, or else from `SKILL_EVAL_BASE` or `CI_FAILURE_BASE`. It runs the skills whose definition, golden case or scenario pack the diff changes. It runs every skill when the diff touches the evaluation code (`EVAL_CODE`: `skillEval.ts`, `skillAssertions.ts`, `skillCaseIdentity.ts`, `skillEvalCompare.ts`, `skillLifecycle.ts`, `skillScenarios.ts`, `skillLibrarySeed.ts`, the script and its allowlist). It also runs every skill when git cannot diff the base. The suite job checks out one commit, so in CI today that is every skill, every time: 182 skills and 251 cases, judged in about a second.
- **The report.** Each finding is one line on stdout: skill, case, check and reason. It is also one row of a table in the job summary (`GITHUB_STEP_SUMMARY`), under what ran and why.
- **Every skill needs a deterministic case.** A skill without one fails `no_deterministic_case`, unless `scripts/skill-eval-allowlist.json` names it with its reason. The allowlist rule reads every skill, whichever ran.

### 3. The allowlist, and its count

It starts with every skill that has no deterministic case today, so the step lands green:

- **169 skills** are on the allowlist, each with the reason "No scenario pack with known outputs yet; its golden case is judged only by a model run on the HQ board."
- **13 skills** have a deterministic case: `board-meeting-brief`, `cash-runway-snapshot`, `contract-clause-extraction`, `contract-risk-issue-spotting`, `customer-interview-summary`, `legal-due-diligence-coordination`, `lp-quarterly-letter-draft`, `market-entry-brief`, `monthly-investor-update`, `pipeline-health-diagnostics`, `roadmap-review-brief`, `safe-convertible-instrument-review` and `unit-economics-summary`.

The list only shrinks:

- A skill that gains a scenario pack while still listed fails `allowlist_stale`. So does a listed slug with no skill.
- A listed skill with an empty reason fails `allowlist_reason_missing`.
- Adding a skill to the list is a change to a reviewed file, and it needs the owner's review.

`skill_eval_cases_8520.test.ts` holds the counts above to the file.

### 4. Proof

`cloudflare-worker/test/fixtures/skill_eval_8520/` is a pull request that removes a required input from one synthetic skill:

- `after/` is `before/` with `stripe.read` dropped from the skill's tools, while a scenario still feeds `stripe.revenue`.
- The step passes on `before/`.
- On `after/` it exits 1, and stdout and the summary name `fixture-kpi-brief`, the case `fixture-kpi-brief-revenue` and the reason.

On a copy of the real library, the same test shows two more failures:

- Dropping `compliance.read` from `board-meeting-brief` fails `read_not_granted`.
- Removing an assertion from one of its scenarios fails `incorrect_output_not_caught`.
