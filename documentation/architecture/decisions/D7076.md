## D7076 — An agent run builds its role context once (#7076)

Issue #7076. No migration, no route, no new binding.

**What was found.** In `cloudflare-worker/src/agents/loop.ts` the `context` Workflow step called `buildContext` only to write what was read on its timeline line, and threw the prompt away. The `run` step then called `buildContext` again to get the prompt. Each call checked the scope and the sponsor, loaded the rule book, ran every reader one after another, and read the notes, the goal, the handoff and the session. Every run did the full build twice.

**What was decided: the preflight (the issue's option 2).** The issue's option 1 would keep one build and pass what it read to the `run` step by revision, so the run could check nothing moved in between. Readers cannot name the revision of what they return yet: that is #4667's unfinished work (D4667 gave reads coverage and stable row references, not revisions). Without revisions the run step would either trust data read a step earlier or read it all again, so option 1 is left until readers can name revisions.

- **The `context` step is a preflight.** It runs only the checks that can refuse a run: the scope (gone or archived), the sponsor's access, a project moved to another company, a company agent's project no longer the company's, and every `reads` key having a function in `reads.ts` (`read_unavailable` otherwise). It also counts the agent's live memory notes (at most `NOTES_MAX`). It calls no reader and makes no prompt. It answers `{ go: true, reads: <the book's keys>, notes: <count> }`, plus `compute: true` for a compute run, as before. Its timeline line says `Cleared to read <keys> and <n> notes.` Refusals keep their codes, pauses and lines: the checks are the same function (`preflight`), and the step ends through the existing `end`/`pauseAgent` helpers.
- **The `run` step does the one full build.** `buildContext` runs the same preflight again first, so access is checked at the `run` step as before, and a sponsor who lost access between the steps ends the run with nothing read. The run step then writes what it read and left out on its own `run` timeline line, in the line format the context step used: `Read <keys> and <n> notes; left out <names>.` A retried run step keeps the line its first attempt wrote. `runActivity.sourcesOf` reads that line, and still reads the `context` line of a run from before this change. The rest of the run step, including its refusal handling, is unchanged.
- **The prompt is never stored.** It is not a Workflow step's output, a timeline line, a log or an event. The step outputs hold the book's key names and a count only.
- **Reads that do not depend on each other run together.** The book's reads go through `readAll` (`services/agents/reads.ts`), a pool of `READ_CONCURRENCY = 4` that keeps the book's order in the prompt. The notes, goal, handoff roles, handoff block and session block run alongside it in one `Promise.all`. A run therefore has at most nine D1 reads in flight, whatever the length of the book. A reader that throws rejects the build, as a throw in the old loop did, so the Workflow retries the step.

**Reads per run, before and after.** These are counts from the test fixture (`agent_context_once_7076.test.ts`: a ceo's default book of five reads, a project scope, no notes, no goal, no handoff, no session). They are not a production measurement.

| | Reader calls | D1 `prepare` calls (context + run steps) |
| --- | --- | --- |
| Before | 10 (5 in `context`, 5 in `run`) | 34 (17 + 17) |
| After | 5 (0 in `context`, 5 in `run`) | 28 (10 + 18) |

The run step's extra `prepare` is its own read line. The p95 time of the context build cannot be measured here and has not been measured in production. That measurement is still to do, on the runs' step timestamps after this ships.

**Verified.** `cloudflare-worker/test/agent_context_once_7076.test.ts` checks five things. The context step calls no reader. The run step calls each book read once. A whole loop calls each reader once, and the prompt is in no step output, timeline line or captured log. Access is refused at the run step when the sponsor goes after the preflight. A retried run step writes one read line. `readAll` keeps order, never has more than `READ_CONCURRENCY` reads in flight, and rejects on a throw. `agent_engine_d1528`'s timeline assertion now expects the run step's two lines. The existing agent engine, transfer, handoff, session, compute, runtime-contract and run-activity suites pass unchanged.
