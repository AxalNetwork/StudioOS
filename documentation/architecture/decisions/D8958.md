## D8958 — A partner's directory profile is Members only, enforced in the Worker (#8958)

- **Status:** built by S03 on #8958, 2026-11-27. Part of #6981 (the Network and Articles canvas, WS-02).
- **Chosen by:** the owner (2026-11-27, on #6981): a profile marked Members only must be refused by the public read as well, not only hidden on the page.
- **Builds on:** D702 (person profiles already apply the member's effective visibility in `publicPersonCard`), D1439 (link cards read behind the page's own public gate).

### The problem

The canvas shows a Directory card opened by a signed-out visitor as **Members only**. `GET /api/public/p/:partner_slug` (`cloudflare-worker/src/routes/public.ts`) answered every caller, signed in or not, with the partner's uid, name, company and specialization, for any partner with `status = 'active'`. It did not check that the directory lists the partner (`directory_listed`) or that the caller was signed in. A page that hid the profile still left it readable through the API.

### What was decided

`publicPartnerCard(env, slug, viewer)` in `routes/public.ts` is the one read, and the route and the link card both use it:

1. **One gate for every caller.** The key is the partner's uid or referral code, case-insensitive, read only from rows that `DIRECTORY_LISTED_WHERE` admits (`status = 'active' AND directory_listed = 1`), the same predicate as `GET /api/public/partners` and the home page's verified-member count. A uid match wins over a code match. A missing, inactive or unlisted partner is the same `404 {"detail":"Not found"}`, signed in or out, so the answer says nothing about which.
2. **Signed in** (`getCurrentUser` resolves an active account): the profile, `{ uid, handle, name, company, specialization }`, as before.
3. **Signed out** (no token, a token that does not verify, or one naming an inactive account): `{ name, members_only: true }`. The display name is all a shared or referral link needs to say whose page it is; the uid, company and specialization are not sent, so a referral code never maps back to the uid for a signed-out caller.
4. **Never cached.** Both answers carry `Cache-Control: private, no-store`, because the body depends on the caller.
5. **The link card.** `services/socialCards.ts` reads `/partners/<slug>` through `publicPartnerCard` with no viewer, the way the person and startup cards read theirs. A crawler is always signed out, so the card carries the partner's display name and the fixed line "Members only: sign in to Axal VC to see this partner's profile." Until now it carried the company and specialization.

The authorization ledger (`scripts/baselines/auth-inventory/%2Fapi%2Fpublic.json`) records the route as `optional_auth`, `verified` by the test below.

### Referral links

Only `frontend/src/pages/PublicPartnerProfilePage.jsx` (`/partners/:slug`, through `api.publicGetPartner`) calls this route. No referral landing reads it: a referral is captured on entry from `?ref=` (`lib/referralRef.js`, `keepFirstTouch`), which reads no partner profile. So the signed-out answer carries the display name only, and nothing beyond it had to be asked on #6981. A code for a listed partner still resolves while signed out, to that name.

### Other reads of the same profile

- `GET /api/public/partners` (the directory list) still answers signed-out callers with each listed partner's slug, name, company and headline. The canvas draws the directory's cards for a visitor and makes only the opened card Members only, so this is unchanged here and left as an open question for the owner.
- Search (`/api/search`), `/api/partners/*`, `/api/needs/providers` and `/api/network/directory/*` require sign-in. The static sitemap lists no partner page.
- `/api/public/u/:handle` shows a partner *person's* firm and specialization under `services`, governed by that member's own visibility (D702), not by this gate.

### Not built

- The page itself: `PublicPartnerProfilePage` still renders whatever the read returns, so a signed-out visitor sees the name with empty fields until #6981's build (#7011) draws the Members only panel from `members_only`. No frontend change here (the issue's limit).
- No migration.

### Verified

`cloudflare-worker/test/partner_card_members_only_8958.test.ts` (7 tests, synthetic data): signed out, signed in, unlisted, inactive and missing as one 404 for both, a referral code resolving signed out to the name only, an unverifiable or inactive-account token read as signed out, the link card, and the ledger entry. Seven mutations, each caught: the signed-out branch removed; the cache header removed; the gate as `status = 'active'` alone; the gate as the listed flag alone; the referral-code match removed; the card's description restored to company and specialization; the uid added to the signed-out answer.
