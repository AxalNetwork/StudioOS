### The canonical venture context

`useVenture()` (`frontend/src/pages/cycles/VentureContext.jsx`) answers one shape for every tool on a cycle page:

```
{ projectId, projectUid, project, company: { id, founderId, name }, status, projectStatus, retry }
```

- `projectId` is the venture `useProject` resolved from the address. `CycleRoute` puts a `VentureProvider` around its page with it.
- `projectUid`, `project` (the record) and `company` come from `GET /api/projects`, read once a tool asks for them, so a page whose tools need only the id makes no extra read. `company.id` is the project's `company_id`, `founderId` its `founder_id`, `name` the venture's name.
- `status` is the record's: `loading`, `ready`, `missing` (the venture is not in the caller's list; a tool answers it as a refusal), `unreadable` (the list failed; never an empty venture) or `none`. `retry()` reads the list again.
- Mounted outside a provider, `useVenture(projectId)` resolves the same way itself, so a tool has one way to ask.

The pure rules are `frontend/src/pages/cycles/ventureQuery.js`: `ventureRef`, `ventureSearch`, `canonicalVentureSearch`, `legacyVentureRedirect`, `resolveVenture`, `ventureOf`.

### The canonical URL form

- A generated link names its venture as **`?project_id=<number>`** and nothing else (`ventureSearch`; the Data room's `tabSearch` is built on it).
- **Legacy input, accepted and redirected:** `?project=<number>` (the Worker's `next.href` links), and a project UID in either key (`?project=<uid>`, `?project_id=<uid>`). `useProject` reads each, and once the venture is known replaces the address with the canonical one: the same path, every other query key in order, `?project=` dropped, the **hash kept**, and the history state kept (`legacyVentureRedirect`). A UID nobody has falls back to the first venture, as an unreadable id always did.
- Route helpers own this. A feature component never parses the query for its venture and never looks the UID up in the projects list.

### The capability contract (the Data room)

`cloudflare-worker/src/services/dataRoomCapabilities.ts` computes the caller's capabilities once:

| Capability | Owner | Co-founder | Support read | Admin summary | The write it governs |
| --- | --- | --- | --- | --- | --- |
| `upload` | yes | yes | no | no | `POST /files` |
| `edit` | yes | yes | no | no | `POST`/`PATCH /folders`, `PATCH /files` (rename, move, match) |
| `delete_folder` | yes | yes | no | no | `DELETE /folders/:uid` |
| `set_gate` | yes | no | no | no | a gate field on any folder or file write; an upload's default gate |
| `delete` | yes | no | no | no | `DELETE /files/:uid` |
| `share` | yes | no | no | no | `POST`/`PATCH`/`DELETE /grants`, `GET /share-candidates` |
| `answer_requests` | yes | no | no | no | `POST /requests/:uid/accept` and `/decline`; the requests read's `can_answer` |
| `send_nda` | yes, as the founder account | no | no | no | `POST /grants/:uid/nda` |
| `deck_source` | yes | no | no | no | `PUT /files/:uid/deck-source` |
| `download` | yes | yes | no | no | `POST /files/:uid/download`, `…/versions/:n/download` |
| `make_current` | yes | yes | no | no | `POST /files/:uid/versions/:n/current` |
| `export` | yes | yes | no | no | `GET /activity.csv` |
| `search_index` | yes | yes | no | no | `POST /search/index` |
| `admin_reason_required` | no | no | no | yes | the room opens only through `POST /support-read` with a reason |

- **The read carries it.** `GET /api/data-room/:projectUid` returns `capabilities` (the whole map, every key a boolean) beside `role`, for the owner and the co-founder; the admin summary returns the summary map; the support read returns the all-false map with `read_only: true`. An advisor member, an investor or another founder reads no room and gets no map (404, as before).
- **The writes ask the same function.** Every founder-side write calls `roomCan(room.role, '<capability>', user)` before it acts, refusing 403 `owner_only` (or `founder_only` for an owner who is not the founder account sending the NDA). The Worker stays the enforcement boundary; the map is what it enforces, so the page cannot be told one thing and refused another.
- **The page renders from it.** `roomCan(room, capability)` (`dataRoomModel.js`) is true only for a `true` in the read's map: no map, an unknown key or any other value allows nothing. Access (Share, Change, Revoke, advisor grants, Send the NDA), Files (Upload, New folder, Move, Match, Set gate, Set end date, Remove, search indexing), a folder (Delete, Rename, its NDA switch), a file (Download, Move, Rename, Remove, the gate, Make current), the deck-source toggle, Activity's Export and Upload's gate fields all read it. `accessModel.isOwner` and every `role === 'owner'` / `role !== 'cofounder'` test are gone. Before this, `role !== 'cofounder'` read a support read's `role: 'support'` as the owner.
- **Replace** on a file is the Raise record's action (`cycle_records.ts`) and keeps its own rules; it is not part of this map.

### Slice 2: the Cap table record (#5543)

`cloudflare-worker/src/services/capTableCapabilities.ts` computes the record's capabilities once, from who the caller is on the venture (`recordStanding` in `routes/captable.ts`: the read and write gates, admin, Super Admin, owner, the Studio plan):

| Capability | Owner | Co-founder | Ordinary admin | Super Admin | Reader (advisor, investor grant) | The write it governs |
| --- | --- | --- | --- | --- | --- | --- |
| `propose`, `import` | yes | yes | yes, with a reason | no | no | every record write: propose, import |
| `record` | yes | no | yes, with a reason | no | no | record, accept, dismiss, void, classes, currency (`owner_records` otherwise) |
| `correct` | no | no | yes | no | no | a studio correction of a recorded row |
| `export` | yes | yes | through the support read | through the support read | when it may read | the record export |
| `admin_reason_required` | no | no | yes | no | no | the write carries a support reason the founder reads (400 `reason_required` without one) |

- **`plan` is its own key.** Every write also needs the Studio plan. The map says `plan` apart from who the caller is, so the page can tell "not yours to do" from "your plan does not include it". The Worker answers a write without the plan with the plan's 402, before it looks at the capability.
- **The read carries it; the writes ask the same function.** `GET /api/captable/record/:projectId` returns `capabilities` beside the record. `recordWriter` builds the same standing and refuses from `recordCan(caps, …)`, so the page cannot be told one thing and refused another. A refused read carries no map.
- **The page renders from it.** `recordStanding(record)` (`capTableModel.js`) reads only the record read's map: `true` allows, and anything else (no map, an unknown key, another value) allows nothing. It gives `role` (owner, co-founder or reader), `admin`, `plan` and `writes`. Overview (Record an issuance, the holder drawer's Void and Correct, the record dialog's mode) and History (Void, Correct) use it. The account's `role`, `hasTier(user, 'studio')` and the grants read's `can_change` no longer decide a record control. History stops reading the grants. The one exception is the refused read's "support read" door. It reads the account, because a refused read has no map, and it opens only the reason-gated read, never a write.
- **The venture comes from the route helpers.** `tabSearch` is `ventureSearch(ventureRef(search))`: a tab link names its venture as `?project_id=` only. `CapTableMovedRedirect` stays the input-compatibility redirect for the old addresses (`?project=` read as `?project_id=`, query and hash kept).
- **Tests.** `cloudflare-worker/test/cap_table_capabilities_5074.test.ts` checks, for the founder owner, a member owner, an accepted co-founder, an advisor, a co-founder without the plan, an investor-licence member, a non-member, an ordinary admin and a Super Admin, that each capability's write is never refused for who the caller is when the map allows it, is refused 403 when it does not, and answers 402 without the plan. It also pins the frontend mirror (`frontend/test/_cap_table_capabilities.mjs`) to the Worker's function. `frontend/test/captable_capabilities_5074.test.mjs` checks that each role reads as its map says, that nothing is drawn without a map, and that no record control is decided from the account, the plan helper or the grants read. The mounted suites (D1022, D1025, D1023, D1028, D5079) serve the map the Worker sends each viewer.

### Slice 3: the Investor narrative

`cloudflare-worker/src/services/narrative/capabilities.ts` computes the narrative's capabilities once, from who the caller is on the venture (`narrativeStanding`: admin, and the venture's founder as the Evidence read decides it):

| Capability | Founder | Other writer | Admin with a reason (and the Super Admin on HQ) | The write it governs |
| --- | --- | --- | --- | --- |
| `edit` | yes | yes | no (`admin_read_only`) | every narrative write: a version, a section, positioning, an objection's answer, Eadwyn's drafts, the narrative's records |
| `check` | yes | no | no | the writes that state the records' figures: run the check, use a record's figure for a claim, answer the deck's likely questions (`founder_only` otherwise); the claims and check reads' `can_check` |
| `note` | yes | yes | yes | post a note |
| `end_read` | no | no | yes | `DELETE /narrative/reads/mine` (`admins_only` otherwise) |
| `admin_reason_required` | no | no | yes | the narrative opens only after a reason the founder sees (D914, D1463) |

"Other writer" is anyone else the shared Raise gate (`canWrite`) admits whom the Evidence read does not count as the venture's founder. A support session is one: it edits as the member, as before, and never runs the check.

- **The read carries it.** The versions read (`GET /api/cycles/raise/modules/investor-narrative/form-options`) returns `capabilities` beside `versions`. An admin reads it only with a live reason; without one, and for another founder or an investor, the read is refused as before and carries no map.
- **The writes ask the same function.** `narrativeAdminGate` refuses a write when the map's `edit` is false. The check, use-record, likely-questions and claims routes use `narrativeChecks` (the map's `check`), which replaces the route's own `narrativeFounder`. The end-read route uses `end_read`.
- **The page renders from it.** `narrativeStanding(capabilities)` (`narrativeModel.js`) reads only the versions read's map: `true` allows, and anything else allows nothing. `NarrativeTabPage` takes `admin` (notes, no reads list), `readOnly` (Story's editor, Positioning, Versions' Duplicate and "start from", New version) and the Check tab's fix offers from it. The account's `admin` flag from `CycleRoute` now only words a refused read, which carries no map. A page mounted with the account's admin flag but the founder's map draws the founder's controls.
- **The venture comes from the route helpers.** `tabSearch`, `versionHref` and `acceptFixHref` build their query from `ventureSearch(ventureRef(search))`, so a link names its venture as `?project_id=` only. `PitchPositioningRedirect` stays an input-compatibility redirect.
- **Not moved in this slice.** The Raise overview's narrative card (`defs/raise.jsx`, `NarrativeHome`'s `admin`) and the cycle's New version dialog (`narrativeFormAccess`) still read the account, because neither has a narrative read with a map before it draws. Each opens only reads the Worker gates.
- **Tests.** `cloudflare-worker/test/narrative_capabilities_5074.test.ts` checks the pure map for each standing and that no map, an unknown key or a non-true value allows nothing. Over HTTP, on the full schema, it checks the founder's map with every allowed write landing, and an admin's and the Super Admin's map (with a reason) with `edit` and `check` refused, `note` and `end_read` allowed, and the map gone once the read ends. An admin without a reason, another founder and an investor read no map. A source scan pins every narrative write route to the write gate, and the frontend mirror (`frontend/test/_narrative_capabilities.mjs`) to the Worker's function. `frontend/test/narrative_capabilities_5074.test.mjs` checks that Story's editor, notes and reads list, and Versions' writes are each drawn exactly when the map allows, for the founder, a writer, an admin and no map. It also checks that the map wins over the account, that links name the venture in the one form, and that no narrative file parses `project_id || project`. The mounted narrative suites (D906, D909, D910, D911, D913, D914, D1114) serve the map the Worker sends each viewer.
