### The trigger contract (for #5830's caller)

Both routes are on the existing `/api/typeform` router. Both answer `Cache-Control: no-store`.

| | `GET /api/typeform/sync?project=<id>` | `POST /api/typeform/sync` `{ project, backfill? }` |
|---|---|---|
| Does | Reads the bound form's import status. Writes nothing. | Follows the binding, optionally requests a backfill, runs one import of the bound form, answers its outcome and status. |
| 200 | `{ ok, project_id, binding: { form_id, access_state, lost_reason, checked_at }, status }`, where `status` is `null` until an import has followed the binding (never a zero) | `{ ok, project_id, outcome, result, status }` |

`status` is `typeformFormStatus`. It holds:

- `state` (`never`, `ok`, `partly`, `rate_limited`, `access_revoked`, `form_unavailable`, `region_unknown`, `unreadable` or `not_stored`);
- `active`, `last_synced_at`, `checkpoint` (the data-through time) and `link` (the region's responses page, or `null` without a recorded region);
- `completed`, `partial`, `qualifying`, `withdrawn` and `provider_deleted`;
- `needs_remap`, each with `field_id`, `title` and `status`.

`result` is the run's `SyncResult`. `outcome` is one of `ok`, `partly` (the page cap was reached, so call again), `busy` (another run or refresh holds it: nothing stored, try again), `stopped`, `not_selected`, `not_stored`, or a stored failure state from the list above. A run that happened answers 200 whatever its outcome. Only the refusals below are 4xx/5xx.

**Who may call it.** The narrowest gate that serves the data: the connection owner, through the checks #5827's writer routes already use (`writerConnection`). In order:

| Check | Refusal |
|---|---|
| `TYPEFORM_APP_APPROVED=1` (the existing D5827 flag). Until the owner sets it, both routes are dark. | 503 `typeform_unavailable` |
| Signed in (`requireAuth`) | 401 |
| Not a support session | 403 `support_session_refused` |
| A venture id | 400 `project_required` |
| The venture exists | 404 `project_not_found` |
| Can read it | 403 `forbidden` |
| Can write it (an advisor cannot) | 403 `read_only` |
| Has their own active `typeform` connection | 409 `not_connected` |
| That connection is switched on for the venture's company | 409 `company_not_enabled` |
| The venture has a binding | 409 `not_bound` |
| The binding is held by *their* connection (a teammate writer is refused) | 403 `not_your_binding` |
| POST only: the binding's access is `ok` (re-check it with `POST /form/check` first) | 409 `binding_lost` |
| POST only: `backfill` is absent or a boolean | 400 `sync_request_invalid` |

Each code has its sentence in `TYPEFORM_REFUSALS`, and no refusal sends a request to Typeform. The role contract is #5827's and #5829's: the member who bound the form with their own grant is the one who imports it and reviews it. No HQ or admin path is added.

**Backfill.** `backfill: true` clears the checkpoint (`requestTypeformBackfill`) before the run, so the history is read again from the start. It is recorded on the activity log as `typeform_backfill_requested`. Withdrawn and provider-deleted items stay so (part 1). A history longer than one run's ten pages answers `partly`. The caller repeats the POST without `backfill` to continue.

**Not in this contract.** The background poll schedule and the provider-deletion reconciliation run (`reconcileTypeformDeletions`) have no trigger yet, and neither does the mapping write (`setTypeformMappings`, whose route is #5830's). A schedule needs the owner's authorisation, which this release does not give. Each of these goes through `followTypeformBinding` and `typeformImportDeps` exactly as the POST does.

### The binding is the only selection

`typeform_form_bindings` (#5827, one row per venture) holds the choice and its access check. `typeform_form_syncs` (part 1) holds checkpoints, leases and outcomes. The two stores stay separate, and nothing in the importer picks a form.

- `followTypeformBinding(env, projectId)` makes the bound connection/venture/form's sync row `active`. It creates the row if it is new, or reactivates it with its checkpoint if the same form is chosen again. Every other sync row of the venture becomes `stopped`. Both statements read the binding themselves, in one D1 batch.
- It runs after every `PUT /form` write (bind, change, unbind) and again at the start of every import. A failure after `PUT` is only logged by name, because the binding is already committed and the next import catches it up.
- The importer checks the selection again at admission. A sync row the binding does not name is `not_selected`, with nothing read and nothing stored, even if it is still `active`.
- A stopped row keeps its responses, answers, ledger rows and counts, per form (D5829 `form-counts`). D5829's `prepare` and its confirmation guard already require `s.status = 'active'`, so a form that is no longer bound proposes and confirms nothing. Choosing it again makes its answers reviewable again, under the mapping versions D5829 recorded. Nothing is re-imported twice.
- Deleting a connection still cascades its sync rows (part 1). Disconnect deletes the bindings (D5827), and any sync row left is then `not_selected`.

### The grant and the region

- `ImportDeps.accessToken` is replaced by `ImportDeps.session(integrationId) → { accessToken, region }`.
- `typeformImportDeps(env, connection)` (`live.ts`) is the production implementation. It calls #5827's `typeformSession`, which decrypts the grant and refreshes it behind #5827's lease when it is near expiry. It serves only its own connection id.
- Requests refuse redirects, so the bearer token never follows one.
- The region is `recordedRegion`: the `us` or `eu` stored with the grant at sign-in. It is never `typeformSession`'s US default. A grant without one is `region_unknown`, and no request is built.
- Part 1's `integrations.config_json.region` is no longer read.
- Each run copies the validated region (never a token) onto `typeform_form_syncs.region`. That way `status.link` needs no decryption.

How a grant failure reads:

| Failure | Read as |
|---|---|
| `typeform_refresh_busy` | `busy`. Nothing is stored and the lease is released. |
| `typeform_token_failed` or `typeform_token_invalid` | `unreadable` |
| Revoked or changed grant, unreadable credentials, missing connection, or any other throw | `access_revoked`, as in part 1 |

None of these deletes anything, and none changes the binding's `access_state`. That stays #5827's `POST /form/check`.

### Unchanged from part 1 and D5829

Dedupe keys, checkpoints, the overlap, the lease, 429 handling, mapping versions and signatures, and withdrawal, provider-deletion and remap retraction (`retractTypeformReviews` in the same batch) are untouched.

What never reaches storage, an answer or a log: the token, respondent identity, hidden fields, metadata, variables, attachments and unmapped answers. Logs name outcomes only: `[typeform] import stopped { outcome }` and `[typeform] sync follow failed { outcome: <error name> }`.

### Tests

The new file is `cloudflare-worker/test/typeform_sync_5828.test.ts`. It runs on the migrated schema with real encrypted credentials and a fake Typeform serving both data centers. Its four tests cover:

1. Every refusal above, each before any Typeform request and without creating a sync row.
2. The owner's EU grant on the EU origin only, with a once-only count, a read-only GET and no marker or token in answers, tables or logs.
3. Following through change, re-choice, a stray row and unbind, with history kept per form and a stopped form proposing no D5829 review. The backfill is exercised and logged.
4. A lost binding, a revoked grant, a grant with no recorded region, the failure mapping, a deps object for another connection, and a refresh in progress.

Mutation check (`typeform_sync_5828` with `typeform_import_5828`): 17 mutations, 17 caught, 0 equivalent. They covered the recorded region, the selection check, the stop and reactivate statements, each gate, `PUT` following, the region copy, the busy mapping, the connection-id check, the backfill and a GET that writes.

`typeform_import_5828` and `typeform_review_5829` now give each sync row its binding and a `session`. Their expectations are otherwise unchanged.
