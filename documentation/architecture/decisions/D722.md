## D722 — Continue with Google opens Google's own window on /login; the redirect stays as the fallback

Issue: none; the owner's request of 2026-10-18 (about 08:10Z): "for axal.vc/login, do the same gmail option when logging like https://mail.axal.vc, a gmail popup comes, I think it will resolve that browser error once and for all." Built by S1 on `s1/google-signin`. No migration: `user_google_links` already holds the Google subject.

### What it fixes, and what it does not

- **It fixes the failures after you pick your Google account:** "Sign-in link expired" (`bad_state`), or landing back on /login. Those come from the redirect's round trip between axal.vc and app.axal.vc, which Google's window does not make.
- **It does not fix Safari's "A problem repeatedly occurred" while /login loads (#1460).** That happens before anyone clicks, and a window opened on a click cannot affect it. It is tracked separately.
- If the error you saw is not one of these, the exact message and browser say which one it was (owner action 7).

### Why

- **mail.axal.vc opens Google's window; StudioOS left the page.** mail loads Google Identity Services (`accounts.google.com/gsi/client`) and opens Google's account chooser in a popup. StudioOS's "Continue with Google" called `GET /api/auth/google/start` and sent the whole tab to Google, which returned it to `https://app.axal.vc/api/auth/google/callback`.
- **That round trip crosses hosts, and its state did not survive it.** `/start` ran on axal.vc and set `studioos_google_state` as a host-only cookie there. The callback runs on app.axal.vc, where that cookie never arrives. So the only check left was the KV record, read under a 2-second deadline. A slow or missed KV read turned a good Google sign-in into "Sign-in link expired".
- **And that KV record bound nothing to a browser.** It proved that `/start` minted the state and that the state was unused, not that this browser minted it. An attacker could run `/start` in their own browser, finish Google with their own account, and open the callback URL in the victim's browser within ten minutes: the victim was signed in to the attacker's account, and anything they then entered went to the attacker (login CSRF). The review's probe confirmed it on this branch before the fix. It was on main too; this change closes it (below).
- **The landing was fragile too.** The callback sets the session cookie and redirects. The SPA then boots from the cookie alone (`useAuthSync.jsx`), which is the path that has sent people back to /login before (`google_oauth_landing.spec.js`).

### What was decided

#### Which flow

- The GIS **authorization-code client in popup mode**: `google.accounts.oauth2.initCodeClient({ ux_mode: 'popup' }).requestCode()`. It is the same library and the same window mail uses. mail uses this exact client where its server needs the result (`requestOfflineCode`).
- The page gets a **code**, never a token. Only the Worker can exchange it, with `redirect_uri: 'postmessage'`, Google's documented value for a popup code. It needs no new registered redirect URI.
- **Not** mail's token client: that sends a Google access token as the bearer on every call, which conflicts with StudioOS's D1 session.
- **Not** the rendered ID-token button or One Tap: both run through FedCM and third-party iframes, which is the fragile part this change removes.
- **StudioOS's own sign-in client**, `GOOGLE_AUTH_CLIENT_ID` and `GOOGLE_AUTH_CLIENT_SECRET`, not mail's. `types.ts` keeps the sign-in client apart on purpose: mail's asks for Gmail scopes and may be Workspace-internal, which would refuse gmail.com founders.

#### Worker, production first (`cloudflare-worker/src/routes/auth_google.ts`)

- **`GET /api/auth/google/config`** answers `{ configured, popup, client_id }` with `Cache-Control: no-store`.
  - `configured` needs both the ID and the secret. `popup` is `configured` and either `GOOGLE_SIGNIN_POPUP === 'on'`, or `'canary'` with the request asking `?canary=1`. `client_id` is the env's ID only when `popup` is true, and null otherwise.
  - It touches no D1 or KV, sets no cookie and needs no session. It is in `RATE_LIMIT_EXEMPT` and in `ROLE_SCHEMA_SAFE_ANONYMOUS_READS`, so neither the limiter nor a cold isolate's users-table repair can hold it up. That answers D185's third objection to a request on mount: this one is a pure read.
- **`POST /api/auth/google/popup`** takes `{ code, state, expected_email?, lane? }` and checks, in this order:
  1. the client is configured (503 `not_configured`);
  2. the switch is `on` or `canary` (503 `popup_off`). With it off nothing below runs, no call to Google and no row, so "off" rolls back the route and not only the page;
  3. `Origin` is this request's own origin, and in production a `Sec-Fetch-Site`, when sent, is `same-origin`; outside production the dev servers and `EXTRA_DEV_ORIGINS` are admitted (403 `bad_origin`);
  4. `X-Requested-With: XmlHttpRequest`. It is not in the CORS `allowHeaders`, so no page on another origin can send it (403 `bad_origin`);
  5. the body is JSON with a printable `code` of at most 1024 characters and a 43-character base64url `state` (400 `bad_request`);
  6. the `studioos_google_popup` cookie equals `state`, compared in constant time (403 `bad_state`). From here the cookie is cleared on every answer;
  7. the exchange with Google's token endpoint, under the existing 10 s timeout (502 `exchange_failed`);
  8. `verifyGoogleIdToken` (502 `token_invalid`, or 403 `email_unverified_at_google`);
  9. `resolveGoogleSignin` (409 `link_blocked_unverified`, 409 `link_requires_email_proof`, 409 `different_account` with `google_email`, 403 `account_inactive`);
  10. `mintGoogleSession`. The answer is `{ token, csrf_token, user: {id, email, name, role}, expires_in: 86400, new_signup }`, the shape of passkey's `/auth-verify`.
- Every refusal is `{ error, code }` (D278), and none is a 401, so the SPA's `request()` never reads a refused sign-in as an expired session.
- **Recorded refusals (D200).** `exchange_failed`, `token_invalid`, `email_unverified`, `link_blocked_unverified`, `link_requires_email_proof` and `inactive` write a `security_events` row with factor `google`. `popup_off`, `bad_origin`, `bad_state` and `different_account` do not: none of them is a credential being refused. Neither does a JWKS outage, which is our fault and not the token's.
- **`services/googleIdToken.ts`** checks the RS256 signature by `kid` against Google's JWKS, `iss` (both spellings), `aud` and `azp`, `exp` with 300 s of skew, `iat` no more than 300 s ahead and no more than 900 s old, a non-empty `sub` of at most 255 characters, and a verified email. It returns `hd`, and `googleIsAuthoritative` applies Google's own rule for whether it vouches for an inbox. The keys are one `createRemoteJWKSet` per isolate (3 s timeout, 30 s cooldown, 6 h cache), refetched when a token names an unknown `kid`. `/callback` keeps its own `decodeIdToken` checks in this change.
- **One set of account rules for both ways in.** `resolveGoogleSignin` and `mintGoogleSession` were lifted out of `/callback`, which now calls them too:
  - rule 1: a known `sub` signs that user in;
  - rule 2: a verified row whose email matches case-insensitively is linked and signed in;
  - rule 3: an unverified row is refused (`link_blocked_unverified`). An email link proves the inbox; Google's verified flag for an address Google does not host is weaker proof;
  - rule 4: no row creates an account exactly as `/magic/verify` does (`exploring`, `email_verified` true, the `onboarding_progress` licence row, obligations, `embed_entity`), plus the link row, the suggested lane and `user_registered_google`. There is no "account not found" refusal, as there is none for the email link.
  - **Rules 2 and 4 run only where Google is authoritative for the address**: a gmail.com (or googlemail.com) address, or a Workspace account, which carries `hd`. That is Google's own rule ("Using email, email_verified and hd"): for any other address, `email_verified` only means the address was verified when the Google account was made, and whoever holds that inbox now may be someone else. Without it, a former holder of `ops@company.com` with a consumer Google account on it could be auto-linked into the Axal account that now uses the address, or pre-create one that its real owner later enters by email link with the stranger's Google still linked. Such an attempt is 409 `link_requires_email_proof` and writes nothing: "Use 'Email me a sign-in link' once, then press Link Google under Account → Security." The link then happens inside a session that proved the inbox (L1–L4). Rule 1, a `sub` already linked, is unchanged. The same helper applies it on `/callback`.
  - **Every refusal is decided before anything is written.** An inactive account is now refused before it is linked, on `/callback` as well.
  - `different_account`: when the person typed an email, and Google signed in an address that is neither Google's own for that account nor the matched account's, nothing is created. This is mail's "Different Google account" guard; it stops a wrong row in Google's chooser from opening a second application.
- **The session** is the same primitives in the same order as `/magic/verify`: the JWT, a `user_sessions` row with factor `google` and NULL `assurance_level` and `step_up_due_at` (as every Google session has had), `user_login_google` or `user_login_google_signup`, `revokeStaleCrossIdentitySession`, then `setAuthCookies` (Domain `.axal.vc` on HQ). `requireFactor('totp')` and `requireStepUp` still refuse it, and a Super Admin who signs in with Google must sign in with an authenticator code to write. This is the same credential the redirect has always minted; changing its assurance is a separate question.
- **Rate limits.** A new `google_popup` bucket: `POST /api/auth/google/popup` only, 60 a minute per IP, fail-open. Each accepted call is an outbound exchange with Google, so it gets a ceiling below the generic 200 a minute per IP, with room for an office or event network behind one address. It is fail-open like every other sign-in path: the redirect beside it creates accounts by the same rules with no fail-closed bucket, and each account it creates needs a real Google account and a single-use code, so a KV outage that refused it would close the main way in and protect nothing. The page answers a 429 by continuing through the redirect. `/start` stays limited (D74).
- **The redirect fallback's state cookie is now its binding, and the only one.** It carries the session's Domain (`authCookieDomainAttr`, exported from `auth.ts`), so on HQ `/callback` on app.axal.vc reads the cookie `/start` set on axal.vc. `/callback` refuses (`bad_state`) unless one of the values the browser sends under `studioos_google_state` equals the state's nonce, in constant time; a stale host-only cookie beside the new one does not get in the way. `/start` writes no KV record and `/callback` reads none, so a state minted in another browser can no longer sign this one in. A browser that finishes Google in another cookie jar (an in-app browser handing off to Safari) is refused the same way, because it cannot be told apart from that attack; Google refuses most in-app webviews anyway (`disallowed_useragent`). `/callback` clears the cookie with and without the Domain, so a host-only cookie from before the change goes too. Branches, localhost and previews stay host-only.

#### The page (`frontend/src/pages/LoginPage.jsx`, `lib/googlePopup.js`, `lib/api/googleSignIn.js`)

- After first paint, at idle (`requestIdleCallback`, 1.5 s timeout; a 200 ms timer on Safari), the page asks `/config`, with `?canary=1` when its own address has `?google_window=1`. If the window is offered, it loads Google's script at idle, and again on pointerenter, focus or touchstart of the button.
- **The click awaits nothing before `requestCode()`.** A browser opens a window only inside the click that asked for it. The page writes a fresh 32-byte state into `studioos_google_popup` (`Secure; SameSite=Strict; Path=/api/auth/google; Max-Age=600`), builds the code client with `openid email profile`, `select_account` and the typed email as `login_hint`, and calls `requestCode()` in the same turn. The button reads "Waiting for Google…" and stays enabled: a second press starts a fresh attempt, and an answer carrying an older state is ignored. Google reports a blocked window inside `requestCode()` itself, before it returns (checked in the live `gsi/client`), so "Waiting for Google…" is set only while the attempt is still live; otherwise it would overwrite the fallback's "Redirecting…" and unlock the button while `/start` is in flight.
- **On success** the page clears `token`, `viewMode`, `realUser` and `realToken` (Task #4), stores `token` and `user` as passkey sign-in does, records `login_success` with method `google`, and goes to `safeNextPath()`, else `/onboarding` for a new account, else `/studio`. The body, the purge, the store and the landing are pure functions in `lib/googlePopup.js` (`popupRequestBody`, `applyGoogleSession`), so node tests pin them.
- **`safeNextPath()` parses `?next=` against this origin** (`pendingNext.sameOriginNextPath`) and keeps it only if it stays here; a backslash or a control character is refused, because `/\evil.com` and `/%09/evil.com` both resolve to evil.com in a browser. This sink is the window's landing, so it is fixed here.
- **Every click the window cannot take is the redirect.** The config failed or says off, the script is not loaded yet, the library refused to build a client, or Google reports `popup_failed_to_open`: the click runs `continueWithGoogle({ forceRedirect: true })`, which is today's `/start` code. It is still the only `api.googleStartUrl` call site. So is every `/popup` refusal the redirect can still get past (`popupShouldRedirect`): a 429, the limiter's `rate_limit_unavailable`, and `popup_off` for a tab that loaded before the switch was turned off.
- **The button stays visible (D185).** Without a client ID the window is never used, and the click goes through `/start`, whose 503 the page already words as "Google sign-in is not enabled on this environment." This departs from the computed design on purpose: D185 and `login_offers_what_it_names.test.mjs` make the button unconditional.
- **The copy.** `GOOGLE_ERROR_COPY` serves both ways in: a blocked window ("…so Google is opening in this tab"), a closed one ("…cancelled. Nothing was changed."), Google's refusal, `exchange_failed`, `token_invalid`, `bad_state`, `bad_request` and `bad_origin`, the unconfirmed account (now "Use 'Email me a sign-in link' once to confirm it; after that, Continue with Google works", since rule 2 links on its own), `different_account` with both addresses, `account_inactive`, `link_requires_email_proof`, a 429 that names no bucket, "A security check stopped this sign-in…" for a 403 with no code (a Cloudflare challenge, or the CSRF check on a stale session cookie: the request arrived), and "We couldn't reach Axal VC" only when there was no answer at all.
- **No client ID is committed.** The page reads it from `/config` at runtime. There is no `VITE_` variable, and a test fails if `apps.googleusercontent.com` appears under `frontend/src`.

#### Headers

`frontend/public/_headers` is unchanged: it sends no CSP and no COOP. Google's window answers by postMessage, which COOP `same-origin` cuts. `same-origin-allow-popups` is not added either: when a page on another origin opens axal.vc in a window of its own (an AI client's MCP OAuth window that lands on /login), that policy cuts the link to the opener, and that sign-in breaks instead. The Worker's COOP `same-origin` on `/api/*` JSON is harmless, because COOP acts only on documents.

### The switch, and what the owner does

`GOOGLE_SIGNIN_POPUP` is a Worker var with three values, `"off"` in both `[vars]` and `[env.production.vars]` when this ships:

- `"off"` (or unset): every click takes the redirect, and `POST /popup` answers `popup_off`.
- `"canary"`: only `/login?google_window=1` is offered the window; every other visitor keeps the redirect. `/popup` accepts.
- `"on"`: everyone gets the window.

A JavaScript origin missing from the Google client makes Google show its own error inside the window ("Error 400: origin_mismatch"), which the page cannot see. So the window goes on in steps:

1. **Google Cloud Console → Credentials.** Open the Web client that "Continue with Google" uses today: the one whose Authorized redirect URIs include `https://app.axal.vc/api/auth/google/callback`. (Cloudflare never shows a secret's value, so match the client this way, or by the `client_id=` in the accounts.google.com address that Continue with Google on axal.vc/login opens today. Not mail's client and not the Calendar client.) Add the Authorized JavaScript origins `https://axal.vc` and `https://app.axal.vc`. Keep the redirect URI for the fallback.
2. **Wait.** Google says a new origin can take from 5 minutes to a few hours to take effect.
3. **Consent screen.** Confirm it is External and "In production", so gmail.com founders can sign in.
4. **Cloudflare.** Confirm that no WAF or Bot Fight rule challenges `POST /api/auth/google/popup` for real browsers (#1008 item 10 saw a managed challenge on `/api/auth/magic/start`).
5. **Canary.** A PR sets `GOOGLE_SIGNIN_POPUP = "canary"` on both lines, in `[vars]` and `[env.production.vars]` (the wrangler-blocks test fails if they differ). After it deploys, open `https://axal.vc/login?google_window=1` and `https://app.axal.vc/login?google_window=1` on Mac Safari, iPhone Safari and Chrome: Google's window appears and signs you in; with pop-ups blocked, it continues in the same tab. Everyone else still gets the redirect.
6. **The flip.** A PR sets `"on"` on both lines. No secret changes.
7. **The error you saw.** Say which browser and the exact message, so we can confirm this is what fixes it (see "What it fixes, and what it does not").

**Rollback:** set `GOOGLE_SIGNIN_POPUP = "off"` on both lines and deploy. Every click then takes the redirect, `/popup` refuses before it calls Google, and a tab opened before the rollback continues through the redirect when it gets `popup_off`. Nothing is stored that needs undoing.

### What this does not fix

- **Safari's "A problem repeatedly occurred" on /login (#1460).** It happens on page load, which a window opened on click cannot affect.
- **A redirect sign-in finished in a different browser** (an in-app browser handing Google off to Safari). It is refused as `bad_state` now, deliberately: it cannot be told apart from login CSRF.
- **The email-link landing.** `?magic=ok` is not one of `useAuthSync`'s markers. It is a one-line fix and its own issue.
- **Google's refusal inside in-app webviews (`disallowed_useragent`).** Both flows are affected the same way.

### Not in this change

- `useAuthSync.jsx`: add `params.has('magic')` to the post-OAuth marker, with an e2e twin of `google_oauth_landing`.
- Move `/callback` to `verifyGoogleIdToken` after a week of the window running in production.
- Use the window on RegisterPage (`/popup` already takes `lane`) and on Settings → link.
- Fix `cloudflare-worker/OAUTH-PROVIDER-SETUP.md` (Calendar only, wrong host).
- Re-test #1460 on production.
