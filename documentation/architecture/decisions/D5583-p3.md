## D5583 part 3 — Checksummed, resumable multipart media upload through the existing blob store (#5583)

Preview-only internal service, Part of #5583, following part 2 (D5583-p2). No route is mounted and no production
upload, rendition provider, signed delivery link or new binding is activated. Synthetic bytes and the existing test
stores only; no migration was run against `studioos-db`.

### What it adds

`cloudflare-worker/src/services/workGraphMediaMultipart.ts`: begin, part, finish, abandon and an expiry sweep for one
media object larger than the 8 MiB buffered path. The buffered cap is not raised: every part is held in memory alone
and is at most `MEDIA_BUFFER_MAX_BYTES` (the default part size, above R2's 5 MiB part minimum). Objects at or below
the cap take part 2's buffered path (`use_buffered`), where `admitMedia` reads the whole file.

### One identity, one ledger, one admission

- **Key and ledger.** The object is written to its part 2 typed key,
  `wg/v1/t<tenant>/c<company>/media/p<project-or-0>/<class>/sha256/<digest>`, and recorded by
  `recordFinishedBlob` in `workGraphBlobs.ts`: the same `work_graph_blobs` row statement `putVerified` writes (now one
  shared `blobRowStatement`), under the same per-tenant byte limit and with the same `blob_put` / `blob_reused` audit
  event. There is no second blob ledger.
- **Session tables.** Migration `202611252327_5583_media_multipart_uploads.sql` adds `work_graph_media_uploads` and
  `work_graph_media_upload_parts`. They hold transfer progress only: the declared object, the R2 upload id, the next
  part, eight SHA-256 state words, a small admission state and each acknowledged part's digest and etag. No content,
  prompt or provenance text is stored; the declared context (asset, expected head, class, type, size, digest,
  provenance, use, pins, residency) is kept as a digest, and finish must present the same context. The storage meter
  never reads these tables. Triggers keep a session's identity fixed and a closed session closed, and a part's digest
  fixed (a retry may refresh its etag only).
- **Admission.** `checkMediaContext` is now the one function both paths use for everything but the bytes: author
  revocation, rights on the current clock, pins, asset scope, kind, expected head, a derivation's source and each
  pin's head. Begin runs it and finish runs it again, so a head that moved, a licence that expired or an author
  revoked while the parts were sent fails the finish. `beginStreamAdmission` / `admitStreamPart` in `workGraphMedia.ts`
  apply part 1's format rules part by part: the declared type names the format and the first part must sniff as it;
  the header checks `admitMedia` makes (PNG IHDR, WebP RIFF size and glb header length against the declared size,
  AVIF's ftyp box, JPEG location metadata); PNG's chunk walk for `eXIf` carried across parts, including a header
  that straddles a boundary; and the trailer on the last part. Text formats (SVG, glTF JSON) never take this path;
  they are parsed whole. The one place the streamed rule is stricter: JPEG metadata segments that run past the first
  part are refused as `unsafe_metadata` rather than half-read. A test checks the streamed and whole-file verdicts
  agree on every other case.
- **Quota.** `mediaStorageRoom` is part 2's D1170 guard sequence moved into one exported function, used unchanged by
  `storeMediaUpload` and by begin and finish. It is asked for the declared size at begin and again at finish. It stays
  pass/fail, not a reservation: a finish refused for room keeps the upload open with nothing landed and can finish
  once there is room. Bytes already live in the exact namespace are charged nothing; the landing notice is sent once.

### Integrity

Each part carries its own SHA-256 and is refused (`digest_mismatch`, the upload stays open) when its bytes do not
match. Parts are accepted in order; each is chained into the running hash of the whole object (`Sha256` in
`sha256Incremental.ts`, whose state is carried between requests at a 64-byte boundary) before R2 sees it. When the
last part's chained digest is not the declared digest, the upload fails closed and is aborted before that part is
sent, so nothing ever lands at a content-addressed key under the wrong bytes. A duplicate of an acknowledged part
with the same bytes is accepted and re-sent (R2 then holds exactly what the hash covered); different bytes are
`part_conflict`; a gap is `out_of_order`; a wrong size is `part_size`.

The R2 writes live in `recordStore.ts` (`createContentAddressedMultipart`, `uploadContentAddressedPart`,
`completeContentAddressedMultipart`, `abortContentAddressedMultipart`), the one writer of `record` prefixes (D6651),
and refuse a key that does not end in its digest. Completion also refuses unless the chained digest is the key's.
R2 checks every part's etag at completion, so a body that replaced an acknowledged part in a lost race makes the
commit fail (`part_conflict`, nothing lands, the session stays open) until that part is re-sent.

R2 records no SHA-256 for a multipart object. `verifyBlob` therefore re-hashes a **media-class** object that has no
R2 checksum and is above `deepVerifyMaxBytes` as a stream (native `crypto.DigestStream` in Workers, the incremental
implementation elsewhere), up to `streamVerifyMaxBytes` (2 GiB, the largest media class). `recordFinishedBlob` runs
that verification before it records, and the revision store's head swap runs it again. Generic objects keep D5581
part 3's rule unchanged: above 8 MiB with no checksum they are `unverifiable`.

When bytes are already intact at the key (with R2's checksum), finish keeps that object, aborts this upload and
records a reuse. Dedup stays within the exact tenant/company/project/class namespace, and only after the uploader
sent every byte: a declared digest never short-cuts to someone else's bytes.

### Lifecycle

A session expires after 24 hours (reconciliation's grace period). Parts and finish on an expired session are
`upload_expired`; `sweepMediaMultiparts`, for a company-wide caller only, aborts expired sessions in bounded pages and
closes them as `abandoned` / `expired`. The uploader can abandon an open session. Open sessions are bounded per company
(16). Parts of an aborted upload never entered the ledger or the meter, so nothing is uncharged. A completed object
that is never recorded (a refused tenant limit or a failed verification after commit) is a record and is not deleted
here; with no ledger row and no revision naming it, reconciliation collects it as an orphan after the grace period.
Begin, close and abandonment are recorded on the session row (author, run, times, close code); refusals are
`blob_refused` integrity events with the phase and upload id, like part 2's.

Every call returns its cost: D1 statements and batches, R2 Class A (create, each part, complete, abort) and Class B.
Chaining a part costs one SHA-256 pass over at most 8 MiB in the Worker.

### Rollback

Leave the service unmounted. The tables are additive and read by nothing else; keep them and any recorded objects.
Objects written by this path are ordinary typed blobs to every reader. Do not deploy an older `verifyBlob` against
recorded multipart revisions above 8 MiB: it would answer `unverifiable` for them and refuse their head swaps.
