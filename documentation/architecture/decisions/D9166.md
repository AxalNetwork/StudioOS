## D9166 — The SPA shell carries a hash-based Content-Security-Policy, Report-Only first (#9166)

- **Status:** built by S05, 2026-11-27 (#9166, part 1: Report-Only). Enforcing is the follow-up below, so the PR says `Part of #9166`.
- **Revises:** D36 point 2 (`DECISIONS.md:1609-1610`, "and, deliberately, no CSP (nonce-based on the Worker; an inline boot watchdog in the shell)") and the note that stood at `frontend/public/_headers` lines 57-64. Both said the shell could not carry a static CSP until its inline scripts were enumerated and hashed. They now are.
- **Migration:** none.
- **Severity:** defense in depth. `SECURITY.md` classes security headers as Low.

### Why

The API paths send the Worker's nonce CSP (`middleware/securityHeaders.ts`); the SPA HTML on both hosts sent none. The shell keeps the session token in `localStorage` (36 `getItem('token')` reads under `frontend/src`), so one injected script there can read it. A CSP that allows only known inline code and known origins narrows that.

A nonce is per request and a static `_headers` file cannot mint one. Hashes can be static: the shell's inline code changes only with `index.html`, and the build can hash it.

### 1. What is hashed

The built `docs/index.html` (and each of the prerendered shells, which carry the same scripts) has:

- **4 executable inline `<script>` blocks**, all `data-cfasync="false"`: theme init, the `__axalIsDev` flag, the dev service-worker killer and the boot watchdog. Each is allowed by its sha256.
- **1 inline event handler** the issue's count missed: the font stylesheet's `onload="this.media='all'"`. CSP3 allows a handler by hash only with `'unsafe-hashes'`, which admits exactly the listed hashes and nothing else. Without it the fonts would stay on `media="print"` once the policy enforces.
- **1 `application/ld+json` block**, which is data, not script, and needs no hash.

`'unsafe-inline'`, `'unsafe-eval'` and `'strict-dynamic'` are not in `script-src`. `'strict-dynamic'` is left out on purpose: it would make browsers ignore `'self'`, and the entry module is an external `/assets/*.js` with no hash.

### 2. Where the line lives, and why it is committed

`scripts/lib/spaCsp.mjs` holds the scanner and the policy. The Vite plugin `spa-csp` in `frontend/vite.config.js` runs after Vite writes `docs/`, hashes the built `index.html` and writes the policy into `docs/_headers`.

The same line is also committed in `frontend/public/_headers`, and the build fails when that copy is stale, naming the line to commit (`SPA_CSP_WRITE=1` writes it). Two consumers need the committed copy:

- **The PR preview.** The trusted deploy (`pr-preview-deploy.yml`) and the local preview in `pr-preview.yml` both copy `frontend/public/_headers` as-is and never take `_headers` from the build artifact. A policy only in `docs/_headers` would never reach a preview, and the preview is where the policy is checked before it enforces.
- **The Worker's record cards.** `/events/*`, `/jobs/*`, `/articles/*` and the other card paths are shells that the Worker sends, and `_headers` is not applied to them. `SHELL_HEADERS` in `services/socialCards.ts` sends them the same value. The published-deck embed (`serveDeckEmbed`) leaves it out, because it already sends its own enforcing `frame-ancestors` CSP and the shell's `frame-ancestors 'none'` would report every allowed embed.

The two standalone pages are not the shell, so the policy is detached from them (`! Content-Security-Policy-Report-Only` on `/verify-email`, `/offline` and their `.html` forms, after the `/*` rule): `verify-email.html` loads a CDN script and its own inline code, and `offline.html` is the service worker's fallback. Giving them their own policy is a separate change.

### 4. The checks

- `frontend/test/spa_csp_9166.test.mjs` reads the built `docs/`. Every shell's executable inline scripts and handlers must have their hash in `docs/_headers`, with no hash that no shell needs. One `/*` rule sets the header, and no rule enforces yet. The standalone pages detach it. The committed line, the build's line and `SHELL_HEADERS` must be one value. `script-src` must not allow inline code beyond the hashes.
- `scripts/check-spa-live.mjs` checks every shell route on both hosts (the Worker's record cards included). The header must be present, keep `'self'` with no `'unsafe-inline'`, and hash each inline script and handler in the body that came with it.
- `interview_channels_ui_d684.test.mjs` (Meta's SDK) and `google_popup_headers_d722.test.mjs` (GIS) now check the real policy, not an absent one.
- The build itself fails on a stale committed line (`spa-csp` in `vite.config.js`).
- Mutation check (`spa_csp_9166`, `spaChunks`, `deck_publish_d1564`, `interview_channels_ui_d684`, `google_popup_headers_d722`, and the build): 19 mutations, 19 caught, 0 equivalent. Eleven ran through `scripts/mutation-check.mjs`. The seven on built `docs/` files, which the helper refuses, and the one on the build's stale-line check were run by hand.

### Follow-ups for the owner

1. **Enforce.** Open a PR preview and the production consoles on `/`, `/login`, a checkout, a Turnstile form, Google sign-in, the Picker, the WhatsApp connector and a lesson video, and read the Report-Only violations. Nothing has been checked against a deployed host yet: this session could not reach `axal.vc`. Anything Cloudflare injects into the shell (for example a Web Analytics beacon from `static.cloudflareinsights.com`) appears there. Then rename the header to `Content-Security-Policy` in `scripts/lib/spaCsp.mjs` (`SPA_CSP_HEADER`), `_headers`, `SHELL_HEADERS` and the test's "does not enforce yet" assertion.
2. **A report endpoint.** The policy has no `report-uri`/`report-to`, because the Worker has no route that collects reports. Violations show only in the browser console until one exists.
3. **The session token stays in `localStorage`. This is out of scope here, and the decision is the owner's.** Moving it to an `HttpOnly` cookie would take it out of reach of script entirely. That touches every `getItem('token')` read, the Worker's auth and CSRF handling, and the WebSocket subprotocol carrier. A CSP narrows the risk of a script reaching the token, and a cookie would remove it.
