## D6475 — The conflict resolver: a model resolves only the conflicted files, both sides must survive, a separate job pushes (#6475)

- **Status:** built 2026-11-17. Part of #5600 (plan key C4). Claimed from S06 for S21 on the owner's instruction.
  The branch is stacked on #6474's (#7089) with #6473's (#7088) merged in; it lands after both.
- **Owner's answers (2026-11-16, on #6475):** the model accounts and secret names are #6473's. **The owner lands
  every model-resolved PR, as T2**; the feeder never queues one.
- **Why:** after README rows, decision files and route-map rows stopped being conflict sources, about half of the
  latent conflicting pairs (20 of 42) and two thirds of the landing knock-outs (18 of 27) remained: sibling parts
  of one feature editing the same component, model or test. "Tests pass" is not proof of a resolution: one that
  drops a side's change together with its test also passes.

### Three jobs

| Job | Environment and token | Runs a model | Runs PR code | Writes |
| --- | --- | --- | --- | --- |
| `plan` | `landing-bot`; `GITHUB_TOKEN` read; an App token with `metadata: read`, only for the bot's login | no | no | artifacts only |
| `resolve` | the model runner (#6473): `edit` in `repair`, `verify` with no secret | yes | in `verify` only | nothing on GitHub |
| `apply` | `landing-bot`; the App token; no model key | no | no | the PR branch, labels, one comment |

`plan` refuses before any model call when:
- `eligible()`, `attempts()` or `budget()` say no. Attempts are at most 2 per PR, counted from the run names
  `Conflict resolver for #<n>` and the bot's `Landing-Bot-Kind: conflict` commits, neither of which a session can
  rewrite.
- One side deleted or renamed a conflicted file.
- A conflicted file fails `pathGuard()`. This covers existing tests, fixtures, baselines, allowlists, auth and money
  paths, which `merge-policy.mjs` rates T2.
- The conflict is over `LANDING_BOT_MAX_CONFLICT_FILES` or `LANDING_BOT_MAX_CONFLICT_LINES`. Unset is 0, so the
  resolver is closed until the owner sets both.

A bot that is off, a PR labelled `bot:off` and an open breaker stop quietly. Every other refusal is `giveUp()`:
`needs-session` and one comment for the owning slot.

### The resolution check, with main's code

`resolve-rules.mjs`'s `checkResolution()`, against the three versions git kept for each file (base, the PR's,
main's):
- **every line either side added is in the result**, compared trimmed, with blank and marker lines aside;
- no conflict marker is left;
- the count of `test(` and `it(` calls is at least the two sides' together (ours + theirs − base), so a test both
  sides added, or one side's test, cannot be dropped;
- no `skip`, `only` or `todo` beyond what the two sides had;
- exactly the conflicted files: a patch touching another file, or leaving one unresolved, is refused.

`apply` also re-reads the PR before staging and again just before pushing. A head that moved means no push, and
nothing is posted. The commit must be a merge of exactly the planned head and main.

### Merge mode in the model runner (#6473)

The runner edited a branch's commit. A resolution has to be edited, and verified, on the merged tree, or main's
side would not compile. So a task may now carry `merge_sha` and `head_sha`:
- **A step of its own stages the merge**, in `edit` and in `verify`: `model/stage.mjs`, in a separate process,
  with the branch keeper's git settings and main's merge rules only, and the conflict style pinned so all three jobs
  see byte-identical markers.
- **The edit job's modules still start no process.** `edit.mjs` reads the stage report and refuses unless it is the
  task's merge with exactly the allowed files. The staging step holds no model credential: the keys are set only on
  the `Edit` step. The #6473 rule test still passes, and the #6475 test checks that `edit.mjs` does not import
  `stage.mjs`.
- In merge mode, a patch must resolve every allowed file and may leave no marker.

This is recorded here and not in D6473, under D6466's rule that a decision file takes no appended section.

### Deviations from the issue

- **Named `landing-bot-conflict.yml`**, not `conflict-resolve.yml`. #6467's shared rules name each kind's workflow
  `landing-bot-<kind>.yml`, and the keeper already dispatches that name.
- **Dispatched with the PR number only.** `plan` reads the head and main itself; `apply` pins both SHAs from the
  plan, so a later main or head is never pushed.
- **Verify runs the installs, a typecheck or build, and selected tests**, at most six commands (#6473's cap). The
  `suite (rest)` guard chain is not in verify: it needs a built `docs/`. CI runs every guard on the pushed merge,
  and the owner lands it.
- **Today's budget is counted from reservation artifacts**, one per run cleared to call a model, as the keeper
  counts its pushes. Each is counted as one model run and one push.

### Known limits

- The markers name main's SHA, so the before-hash re-check assumes all three jobs run the same git. A difference
  refuses the resolution (it never pushes the wrong thing); the hosted proof will show whether it ever happens.
- "Every added line survives" compares lines, not meaning. A resolution that keeps both sides' lines but in an
  order that breaks the code fails verify or CI, and the owner reviews the diff before landing.

### Tests

`frontend/test/landing_bot_conflict_6475.test.mjs`, 12 cases on real git fixtures and stub providers:
- a one-line both-sides-add conflict is staged and resolved;
- keeping one side, leaving markers, dropping an assertion or a test, and adding a skip are each refused;
- a patch touching a non-conflicted file is refused;
- a conflicted test or protected file, or an oversized conflict, is refused before any model call;
- the third attempt and an exhausted budget hand back once;
- merge mode refuses without the stage report, refuses one that leaves markers, and verifies a good patch on a
  fresh staging;
- `apply` pushes one merge commit of the planned head and main, labelled and described;
- a head moved before staging, or just before the push, means no push and no comment;
- the workflow: `resolve` has no write, `apply` no model secret, no PR trigger, `assertWorkflow` passes.

Fourteen mutations were run against it; each fails at least one case.
