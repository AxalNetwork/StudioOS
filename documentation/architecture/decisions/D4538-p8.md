## D4538 part 8 — Discovery's input gate, run gate and quality and operational evidence in ranking (#4538)

Part 4 (`D4538-p4.md`, #5966) built the gate and ranking stages 1 to 3 as a pure service, and part 6 (`D4538-p6.md`, #5967) served it. Both left placeholders: the `input_unavailable` and `not_runnable` codes were seams nobody passed, and every candidate's `evaluation` and `operational` read `{ available: false }`. This part fills them from sources already on main. Issue #5968 is slice 3 of #4538 Part A.

### What is built

- `cloudflare-worker/src/services/agents/skillDiscovery.ts` stays pure. A catalogue skill can now carry four facts: `inputs`, `runnable`, `quality` and `operations`. If a fact is absent, the service says "Not recorded" and leaves the score alone. Four new exports:
  - `inputGapsOf` turns #4667's preflight into the gate;
  - `evaluationOf` builds stage 4's block;
  - `operationalOf` builds stage 5's block;
  - `gateOf` returns `input_unavailable` with the unmet inputs, and `not_runnable` with the run path's code.
- `cloudflare-worker/src/services/agents/skillDiscoveryEvidence.ts` is new. `withDiscoveryEvidence` reads those facts for the skills that pass the cheap gate (readable, published, not retired or suspended, the role, the grants, the asked-for output). A blocked skill costs no read. A read that fails is said on the skill, never served as zeros.
- `POST /api/teams/skills/discover` (`routes/team_skills.ts`) calls it with the agent row, its scope and the rule book in force (`effectiveBook`). The response gains `candidates[].inputs`, `blocked[].inputs` (for `input_unavailable`) and `blocked[].run` (for `not_runnable`). The evidence blocks are filled when their facts exist.

### Stage 3: inputs (#4667)

For a skill of the first ten, matched by slug as the run path matches it (`skillEvidenceForRun`), the route calls `preflight` through the real readers, as the agent's sponsor. The binding is the rule book's reads. The call is the readiness route's own (`GET /agents/:uid/skills/:slug/readiness`): the agent's own venture (a project agent's; none for a company agent) and no selected document or fund. `inputGapsOf` sorts each required input:

| Preflight says | Discovery |
|---|---|
| `unavailable_reader`, `not_granted`, `withheld`, `unreadable`, or `partial` with `wrong_shape` | **unmet**: the skill is `input_unavailable`, in `blocked` with those inputs. Never a candidate. |
| `missing` or `empty`, on a read that named the agent's venture | **unmet**, as above: nothing is recorded where the run would read it |
| `missing` because no document or fund is selected (`not_selected`), or a person supplies it (`manual:`) | **deferred**: a run supplies it when it starts. The candidate's `inputs.deferred` names it. |
| `missing` or `empty` for a company agent, whose read named no venture | **deferred**: "Read for the venture a run names" |
| `partial`, `stale`, `absent_optional`, `available` | not a gate; reported in `inputs.inputs` and `limits` |

A skill outside the first ten has no binding reported. Its `inputs` is `{ available: false, reason: "Not recorded: …" }`, and stage 3 says so. It is never assumed available because its read keys are in the catalogue. A preflight that throws makes every required input `unreadable`, so the skill is gated. `pathsFor`'s answer is carried in the facts. Where it says unsupported, preflight already reports the same input as `unavailable_reader` or `wrong_shape`.

### The run gate (#4534)

The issue names `skillRunRefusal` and `skillForRun`. Their checks that apply before a skill is attached are already gate codes:
- the suspension is `skill_suspended`;
- the ungranted tool is `tool_not_approved`;
- an unreadable version is `version_not_published`.

What the run path refuses beyond them is the agent itself: `agentRun` answers a paused agent `agent_paused` and an outside assistant's agent `outside_assistant`. Those are `not_runnable`, with `run` naming the code. The run manifest's `read_not_in_rules` and `skill_malformed` were considered and not used. The default (legacy) runtime runs a skill that the manifest leaves out (`skillTextForRun` falls back to `skill_not_in_manifest`), so gating on them would refuse skills that run.

### Stage 4: quality evidence (D4533)

This stage covers HQ skills only. A company skill has no golden cases and no manifest, and its block says so. Two reads cover every skill asked:
- the current version's row with its `evidence_json` manifest and the live cases;
- the latest row per case key and model on the **current** version in `agent_skill_version_evals`, over the cases a run takes (`goldenCasesFrom`) and the required models (the manifest's, else the declared or default set), as the HQ library counts them (D4536-p2).

The block names exactly what it used:
- `version`;
- `suite` (case count, models and their source);
- `results`: units, recorded, missing, pass, fail and not run; `meets_bar` on 9 of 10 of every unit, or null while a unit has no result; results by model; the evaluator versions against the current one; and the oldest and newest run;
- `release`: the manifest's evidence hash, suite revision, case count, evaluator, models, bar and approval date. It is **stale**, with reasons, when the evaluator, the live suite or the required models changed after the release;
- `freshness`: `fresh`, `stale`, `incomplete` or `not_recorded`, and `stale_reasons`.

Results are stale when the oldest counted result is more than 90 days old (`QUALITY_FRESH_DAYS`, a quarter, chosen here), when any result was judged by another evaluator or one not recorded, or when a run time does not parse. Only fresh, complete results on the current evaluator move the score:
- at the bar, ×1.1 (`QUALITY_BOOST`);
- below it, ×0.75 (`QUALITY_PENALTY`).

Stale, incomplete or absent evidence moves nothing, and `rank.reason` says why. The release manifest is reported and never scored, because every manifest met the bar to publish and so cannot tell skills apart. No case text, output or judge detail is read into the response.

### Stage 5: operational evidence (#4536)

The block reports #4536's served measures for the skill's current version, over the last 30 UTC days (#4536's default window):
- the attributed outcomes: `run` and `refused` events marked `outcome_v = 1`, classified with `FAILED_CODES` and `isRetryable`. Events that name another version are left out, and events that name none are counted as `version_not_recorded`;
- the rates over `ended`. Each is `{ available: false }` when nothing ended, never 0;
- the model-call latency, p50 and p95 by nearest rank.

`cost_per_completed_run`, `run_latency` and `workflows` are `{ available: false, reason }`. Cost is served on the HQ library read only, and discovery does not rank on it. The other two are not served by #4536.

Only the failure rate moves the score, and only down: ×(1 − 0.5 × failure), from 10 ended runs (`OPS_MIN_ENDED`). A clean record moves nothing. How many runs completed is reported and never read by the score.

**Scoped access.** Both reads count only **this company's agents**: a company agent of the company, or a project agent on one of its projects. An HQ skill's runs at another company never enter a figure, so member discovery never shows another company's evidence, whatever HQ's aggregate library read serves. The route test checks this for the company's editor and for HQ's admin asking about the same agent. A company skill can be read here only by its own company, because the catalogue query, the company gate and `mayRead` already keep out every other company's skill.

### Popularity never raises a rank

`use_count` is still never read. Two skills that differ only in use count, and in completed-run count (3 against 90,000), score the same, and the order between them is name then uid. That is tested. An unavailable measure is never scored as zero. These all leave the score exactly as no evidence leaves it, which is tested:
- an unreadable quality read;
- a version with no results;
- stale failing results;
- an unreadable run history;
- nine failures under the 10-run floor.

### Measured

Re-run with `cloudflare-worker/test/skill_discovery_evidence_5968.test.ts`, which pins these numbers:

- **queries.v1.json, sources wired.** The 182 library skills, published at v1, plus the set's fixtures. Each first-ten skill carries #4667's real preflight on a company agent's scope.
  - **`wired_readable`**: every reader answers. The numbers equal part 4's: precision@1 1.0, the relevant skill first in 10 of 10, outcomes 15 of 15. No skill is input-gated: the contract and fund skills' document and fund are deferred to the run.
  - **`wired_unreadable`**: every first-ten reader throws. The four first-ten skills the set labels relevant go to `blocked` with `input_unavailable`, and no ineligible skill is recommended. The labels assume those skills can run, so:
    - `investor-update-ir` abstains;
    - `runway-cfo` recommends `budget-vs-actual`, and `board-prep-ceo` recommends `pipeline-review-brief`. Both are eligible, and neither is labelled. That gives precision@1 0.778 and 14 of 15 outcomes.

    This shows a known limit. When the right skill is gated, discovery offers the next eligible match instead of abstaining, at the confidence its coverage earns. Naming the blocked skill beside a weaker candidate is follow-up work.
  - **`worst_case_evidence`**: every labelled relevant skill has fresh failing results and a 50% failure rate, and every other skill has fresh passing results. That is the most stages 4 and 5 can move an order. Nothing moves: relevant-first 10 of 10 and outcomes 15 of 15. On this set, stage 2's margin is larger than the evidence factors.
- **#4588's first-ten qualification set.** Two parts:
  - **The packs as discovery probes.** Each of the 52 scenarios is asked as a task, using its name without the skill prefix (for example "no burn recorded", "two versions disagree on the liability cap"). The agent has a role the skill lists and the skill's tools. The skill is first in 31 of 52, in the top 3 in 37, and missed in 15. 11 scenarios abstain. These names describe evidence conditions, not tasks, so this measures lexical reach on short phrases. It is not a relevance label.
  - **The gate against #4667.** For each of the ten skills: the ready state, then every required native input as no reader, withheld, unreadable and not granted. That is 62 cases. In all 62, the skill is a candidate exactly when preflight leaves nothing unmet, and `input_unavailable` otherwise.

  The ineligible-recommendation rate is zero throughout: no candidate fails its own gate.

**What these numbers do not claim:**
- **No full-catalogue qualification.** The first-ten set covers ten skills. The library's other 172 have no input binding and no qualification pack.
- **No live evidence.** Stage 4 and 5 numbers here come from fixtures. How many production skills have fresh complete results, or ten ended runs in a company, was not read: no production data was read.
- **No workflow measures.** Workflow executions wait on #4535, and the block says so.
- **The constants were chosen with this set in view:** QUALITY_FRESH_DAYS, QUALITY_BOOST, QUALITY_PENALTY, OPS_MIN_ENDED and OPS_PENALTY.
