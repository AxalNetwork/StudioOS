## D6694 — Formation filings and the registration record: the registry's date, number, certificate and address reach the company (#6694)

- **Status:** built by S11 for #6694, 2026-11-17. Part of #6680 (plan key E9, Phase 3). Extends D1415.
- **Depends on:** #6686 (E6), #6687 (E7) and #6690 (C2), all merged.
- **Migration:** `cloudflare-worker/sql/migrations/202611172331_6694_formation_filings.sql`. It adds three tables and changes no existing table.
- **Service:** `cloudflare-worker/src/services/formationFilings.ts`, the only writer of the new tables.
- **Test:** `cloudflare-worker/test/formation_filings_6694.test.ts`, 13 tests.

### 1. Why

Until now one hand-typed date stood for "filed" (D601). It is the day the filing was *submitted*. No registration number was ever captured, and the company's `incorporation_date` was that submission day.

A case needs several filings, each with its own evidence. Registration must write the registry's facts to the company.

### 2. The tables

**`formation_filings`**

| Columns | Meaning |
|---|---|
| `case_id`, `kind` | The filing. `kind` is one of `name_reservation`, `incorporation`, `tax_registration`, `vat`, `payroll`, `beneficial_owner_register`, `foreign_investment_notice` or `other`. |
| `authority_name`, `submitted_by_party`, `reference` | Who it was filed with, by whom, and the authority's reference. |
| `submitted_on` | The submission day. |
| `state` | `prepared`, `submitted`, `queried`, `accepted`, `rejected` or `withdrawn`. |
| `decided_on` | The registry's date. |
| `rejection_reason` | Required on a rejection. |
| `registration_number`, `certificate_document_id` | The registry's number and certificate. |
| `pack_document_id`, `pack_sha256` | The filing pack and its hash. |
| `founder_approved_at`, `founder_approved_sha256`, `founder_approval_request_id` | The founder's approval, and the pack hash it was given for. |
| `attempt`, `supersedes_filing_id` | Which attempt this is, and the attempt it follows. |
| `recorded_after_the_fact` | 1 only on a legacy correction (§6). |
| `revision` | Counts changes, so two calls from one read change the row once. |

The store holds the issue's two rules as `CHECK`s, so no writer can skip them:
- **Approval.** An incorporation filing past `prepared` has `founder_approved_sha256 = pack_sha256`. A legacy correction is exempt.
- **Acceptance.** An accepted incorporation filing has a `registration_number`, a `decided_on` and a `certificate_document_id`.

There is one live filing of a kind per case: a partial unique index over the states other than `rejected` and `withdrawn`. `(case_id, kind, attempt)` is unique. A trigger refuses a `DELETE`: a correction is a new row.

**`formation_filing_events`.** Append-only (triggers refuse `UPDATE` and `DELETE`). Each event holds `from_state`, `to_state`, `to_revision`, `occurred_on`, `recorded_by`, `evidence_document_id` and `detail_json`. `(filing_id, to_revision)` is unique.

**`formation_case_documents`.** The documents a case holds:
- `class`: `filing_pack`, `certificate`, `registry_receipt`, `registry_query`, `rejection_notice`, `evidence` or `other`;
- `visible_to`: `all`, `hq_partner` or `hq_only`.

`(case_id, document_id, class)` is unique.

### 3. How a filing changes

Each change is one batch of two statements, the same shape as D6686's case transition:
1. **The event**, written only while the filing is at the state and revision that were read.
2. **The filing update**, written only while it is still as read and that event exists.

Two calls from one read change it once; the second answers 409 `filing_moved`.

| Function | Change | Refused when |
|---|---|---|
| `createFiling` | A new filing at `prepared` (attempt `n + 1` after a rejected or withdrawn one). | A filing of that kind is still live (`filing_live`). |
| `setPack` | A new pack and hash on a prepared filing. **It clears the approval:** an approval is of one pack. | The filing is not prepared. |
| `approvePack` | The case's founder approves the pack by its hash. The hash they send must be the current `pack_sha256`. | Anyone else (`founder_only`); another hash (`pack_changed`). |
| `submitFiling` | → `submitted`, with the submission day. | An incorporation filing without the approval of its current pack (`founder_approval_required`). The consent-to-act check is #6706's. |
| `queryFiling`, `answerQuery` | `submitted` ↔ `queried`. | — |
| `rejectFiling` | → `rejected`, with the registry's date and a reason. The case stays at its stage. | No reason. |
| `withdrawFiling` | → `withdrawn`, with a reason. | The filing is already decided. |
| `acceptFiling` | → `accepted`. | An incorporation filing without a registration number, a registry date (a calendar day, not in the future, not before submission) or a certificate document. |

Every date is one a person typed (D4677).

### 4. V2 cases: the incorporation filing drives the case

On a `v2` case, the incorporation filing's changes run inside the case's `transition` (`formationCase.ts`), in the same batch:

| Filing change | Case moves | Also written |
|---|---|---|
| `markReadyToFile` | `preparing` → `ready_to_file` | `incorporations.packet_ready_at`; the pack as the order's `packet_document_id`. |
| `submitFiling` | `ready_to_file` → `submitted` | A later attempt, with the case already at `submitted`, moves only the filing. |
| `queryFiling`, `answerQuery` | `submitted` ↔ `registry_query` | — |
| `acceptFiling` | → `registered` | The order is `filed` with **`filed_on` = the registry's date**. The company write of §5 runs. |

**The submission date lives only on the filing.**

`transition` gains two options for this. Neither changes any existing caller:
- **`filingAsRead`.** The case event *and* the order update require the filing still at the state that was read. So a filing rejected between the read and the batch moves neither the case nor the order, and no company is written.
- **`expectRevision`.** `transition` refuses with 409 if the case is no longer at the revision the caller built its statements on.

### 5. The company write (D1415, extended)

`filingCompanyStatements` takes an optional `registration` (number, certificate document, structured address). It writes four facts:

| Fact | Written as |
|---|---|
| `incorporation_date` | The registry's date. |
| `registration_number` | Filled with `COALESCE`, like the other legal fields. |
| The certificate | A copy of the filing's certificate `documents` row, as the company's `certificate_of_incorporation` document (D1592's slot). The case keeps its own row. Written only while the slot is empty. |
| The registered address | The registry's structured address (line 1 and 2, city, region, postcode, country) as the open `registered` location, only when none is open. Without one, the agent's address line, as before. |

**A company that already has facts keeps them:**
- each field is written only while it is NULL;
- a certificate already in the slot stays;
- an open registered address stays.

**The mapping reads the catalogue.** `legalFor` reads the current catalogue form's `legal_form_family`, and its jurisdiction's country and subdivision. Each field falls back to `JURISDICTION_MAP`:
- when there is no current version;
- when the version has no such form;
- when the form has no value.

Version 1 holds exactly the array (D6690), so every answer is unchanged until a later version differs.

### 6. Legacy cases

`markFiled` (D601) is unchanged. It writes no filing.

`recordLegacyRegistration` is a logged correction (HQ only, `logAdminAction`). It can add the number, the registry's date and the certificate later:
- **The filing.** An accepted incorporation filing, marked `recorded_after_the_fact = 1`, with `submitted_on` set to the order's `filed_on`.
- **The company.** It fills only empty fields: the `registration_number`, and the certificate slot when it is empty.
- **What stays.** The `incorporation_date` written from the submission date at filing stays. Changing it is an edit of the company's legal facts, not this correction.
- **The order and the case** do not change.

### 7. What `packet_ready_at` and `filed_on` hold for v2

| Column | V2 meaning |
|---|---|
| `packet_ready_at` | When the case entered `ready_to_file` with its incorporation filing's pack. |
| `filed_on` | The registry's date of the accepted incorporation filing, not the submission day, which is on the filing. |

A note on #6038 says the same.

### 8. Not here

- HQ and partner routes that call this service: #6698 (H2) and #6711 (P3). Nothing here mounts a route.
- The consent-to-act check before submission: #6706 (E14).
- Storing files. Documents are `documents` rows named by id. Until #6651's write-once helper merges, no real file path is enabled; the tests use synthetic rows.
- Cap table writes.

### 9. Tests

`formation_filings_6694.test.ts`, over the full migrated schema with catalogue version 1 seeded:

1. Submitting without the founder's approval of that pack hash is refused, by the service and by the store. A new pack clears an approval. A submission moves the v2 case.
2. Accepting without a certificate is refused, by the service and by the store.
3. Accepting without a registration number is refused, by the service and by the store.
4. Accepting without a registry date is refused, also for a future date or one before submission; the store refuses it too.
5. A v2 registration files the order on the registry date and writes the four company facts.
6. A company that already has facts keeps them.
7. A rejected filing keeps the case at its stage and allows a new attempt. There is one live filing per kind.
8. A registry query moves the case to `registry_query` and back.
9. Two acceptances from one read change the filing and the case once. Events are append-only, and filings are kept.
10. A filing changed between the read and the batch moves neither the case nor the order.
11. The mapping reads the catalogue, with the array as fallback.
12. Legacy: `markFiled` is unchanged, and the logged correction fills only empty fields.
13. Case documents are recorded once, by class and visibility.

Every existing formation, incorporation and company test passes unchanged, the D601 test (`incorporation_filing_d601`) among them.

**Mutation check:** each rule was broken in the source, one change at a time, and this file was run. Of 21 mutants, 20 were caught and 1 is equivalent.

- **The equivalent one:** dropping `createFiling`'s live-filing check. The live-filing index refuses the same insert, and the service answers `filing_live` all the same.
- **Among those caught:**
  - the approval check dropped, kept across a new pack, or given for any hash;
  - each of the three acceptance checks dropped;
  - `filed_on` bound to the submission date;
  - the number, the certificate or the structured address not written;
  - `COALESCE` dropped on `legal_name` or on `registration_number`;
  - a rejection that moves the case;
  - the event's as-read guard dropped;
  - `filingAsRead` not passed, or not guarding the order update;
  - `legalFor` ignoring the catalogue, or without its fallback;
  - the legacy correction overwriting facts, or open to non-HQ callers.
