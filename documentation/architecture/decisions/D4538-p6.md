## D4538 part 6 — Discovery served from the Worker, for an agent the caller manages (#4538, #5967)

Part 4 (`D4538-p4.md`, #5966) built the gate and ranking as a pure service, `cloudflare-worker/src/services/agents/skillDiscovery.ts`. This part serves it. Issue #5967 is slice 2 of #4538 Part A; inputs and evidence stay #5968.

### The route

`POST /api/teams/skills/discover`, in `cloudflare-worker/src/routes/team_skills.ts`, behind the same `TEAM_AGENTS_ENABLED` switch as the rest of the skill library. The body is the contract's request (`../SKILL_DISCOVERY_CONTRACT.md`), with the agent named in it as `agent_uid` rather than in the path, so the request matches the contract word for word. The answer is `discoverSkills`'s result as it returns it, `stages` and each candidate's `score` and `coverage` included, so a reader can inspect the order.

The client method is `teamAgentsApi.discoverSkills(body)` (`frontend/src/lib/api/teamAgents.js`). No screen calls it: no canvas draws task-based discovery yet.

### Who may ask

Only someone who can read the agent's team and can manage it (`canRead` and `canManage`, as `PUT /agents/:uid/skills` checks them). Anyone else gets `404 not_found` with the same body an unknown uid gets, so the route does not tell a non-manager that the agent exists. `PUT /agents/:uid/skills` answers a reader `403 not_manager`; discovery does not, because the issue asks for the 404. A removed agent is `409 agent_removed`, as on the PUT.

### What the server reads, and what the body may not carry

The agent's role (`role_key`), its company (`agentCompanyId`: the company, or the project's company) and its granted tools (`grantsOf(tool_grants_json)`) come from the agent row. The body may carry only `task`, `output_kind`, `agent_uid`, `taxonomy_focus`, `workflow_context` and `limit`. Any other key, such as a role, a tool list, a company id, records or a connector payload, is refused `400 field_not_accepted` with `{ field }`, rather than ignored, so a client that believes it is narrowing the agent's grants learns that it is not.

### Field codes

Checked before the agent is looked up, so a refusal says nothing about the agent: `body_invalid` (not a JSON object), `field_not_accepted`, `agent_uid_invalid` (not 32 lower-case hex), `workflow_context_invalid` (anything but null or absent, until #4535 defines it), then `checkDiscoveryRequest`'s `task_invalid` (1 to 500 characters after trimming), `output_kind_invalid`, `taxonomy_focus_invalid` (not a list of at most 3 slugs) and `limit_invalid` (an integer 1 to 10; absent is 5). A `taxonomy_focus` slug that is not an active `/studio` taxonomy slug is also `taxonomy_focus_invalid`.

### The catalogue

Every HQ skill and every skill of the agent's company, read in one query, each described by its current published version (`agent_skill_versions` at `current_version`). A skill never published is described by its draft with no roles or tags; the gate stops it at `version_not_published`, so it can only be listed in `blocked`, never as a candidate. `readable` is the caller's own read gate (`mayRead`, called, not copied), so a draft the caller may not read is `not_found` and listed nowhere. `suspended` is `skillRunRefusal` at the current version, asked only of the skills HQ ever suspended (one query finds them), so a library of published skills costs two queries, not one per skill. Another company's skill is held out three times over: the catalogue query, the service's company gate and `mayRead`.

### Writes nothing

The route only reads. No `agent_skill_links` row, no `team_agent_events` row and no skill or moderation row is written; attaching stays `PUT /agents/:uid/skills`. `no_suitable_skill` and `ambiguous` are 200, as the contract says.

### No rate limit

The route runs no model and calls nothing outside the Worker: BM25 over the caller's catalogue in memory. No other route in `team_skills.ts` carries a rate-limit bucket, and this one adds none.

### Tests

`cloudflare-worker/test/skill_discovery_route_5967.test.ts`, on real SQLite: a manager's answer and an unchanged snapshot of the tables a write would touch; the same 404 for a reader, another company's editor, a stranger, an unknown uid and another company's agent; grants from the row (a CFO without HubSpot sees the CRM digest blocked with `tool_not_approved`, the IR agent with it gets it first) and every refused body key; each field code and the bounds' edges; `no_suitable_skill` and `ambiguous` at 200; another company's skill absent even for HQ's admin; HQ's suspension blocking a skill. Each case names the mutations it was checked against.
