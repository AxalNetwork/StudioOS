## D6678 — Scorecard: the queue clock from the first entry, ready and green to merged, candidate start wait, merges per hour (#6678)

- **Status:** built 2026-11-15 by S25 for #6678 (plan key F3, under #5600).
- **Code:** `scripts/lib/ciScorecard.mjs` (the rows), `scripts/ci-scorecard.mjs`
  (the collector). D5603 is the scorecard; this adds rows and corrects one.
- **Tests:** `frontend/test/ci_scorecard_6678.test.mjs`, and
  `frontend/test/ci_scorecard_5603.test.mjs` for the rows already there.

### 1. The new rows

- **Queue to merge, from the first entry:** from the PR's first
  `added_to_merge_queue` to merged. Every entry on the timeline counts, even
  one that ended before the window opened. The last-entry row (D5603) stays
  beside it, and both are labelled. A PR that was ejected and re-queued loses
  nothing before its last entry.
- **Entries per merged PR:** p50, p90, and the share that merged on the first
  entry.
- **Ready and green to merged:**
  - The clock starts at the later of two times. The first is ready: the PR's
    last `ready_for_review` before the merge, or its creation if it was never
    a draft.
  - The second is green. It is when the last of the required workflows
    (`REQUIRED_WORKFLOWS`) completed on the merged head SHA. Each one's latest
    `pull_request` run must have succeeded.
  - A PR without both times is counted as not measurable, never as zero.
    Examples: a required workflow did not run or did not pass on the head, or
    a draft has no `ready_for_review`.
  - The green time is the completion of the run, not of the check inside it.
    A run ends at or after its required job, so this row can only under-state
    the wait.
  - Reading check runs would need the `checks` scope, which the workflow does
    not hold. The required checks are main's ruleset's six contexts:
    - `test:drift (full suite)`, `worker (typecheck)`, `frontend (build)` and
      `api ↔ worker drift` run in `ci.yml`.
    - `applied migrations unchanged` runs in `migration-immutability.yml`.
    - `scan` runs in `gitleaks.yml`.
- **Candidate start wait:** for the `merge_group` runs of `ci.yml`, the time
  from run creation to the first job that got a runner. A job has a runner
  only when the jobs API gives it a `runner_id` above 0. A queued job already
  carries a `started_at` equal to its creation, with `runner_id` 0, so the
  start time alone would read as no wait at all. A sampled run with no job on
  a runner yet is counted as "no runner yet", not as a wait.
- **Merges per hour:** merged PRs in each whole UTC hour of the window, with
  the peak hour and the median hour. Empty hours are included.

### 2. Why "Runs per queued PR" read 0.0

The collector lists the window's workflow runs from `actions/runs`, ten pages
of 100. A busy day has several thousand runs, and the listing returns the
newest first. On 2026-11-15 the 1,000 runs covered about the last three and a
half hours of the 24, so the scorecard said "Run listing reached the page
limit." The queue entries it measured mostly started before that, so their
runs were not in the listing.

The row now counts from a full listing of its own:
`actions/workflows/ci.yml/runs?event=merge_group`, up to five pages, which is
read-only and needs no new scope. It counts only PRs whose every entry started
inside the window, so no entry's runs fall before the listing. The row is
renamed "Queue CI runs per PR (entries inside the window)". The candidate
start wait samples its jobs from the same listing. The other rows that read
the all-workflow listing are unchanged and still cover only its span.

### 3. Requests

The collector makes one more read per merged PR: the `pull_request` runs on
its head SHA, for the green time. Timelines may now take three pages instead
of one, so a PR with a long history is not dropped. The request cap rises
from 150 to 320, with sequential requests. The GITHUB_TOKEN limit is 1,000 an
hour. The budgets are:

- jobs stop at 120 requests;
- PR timelines and head listings stop at 280;
- the tracker comment keeps up to 11.

The scorecard's coverage line reports the GET count for every run, and says
when timelines stop at the budget. Permissions are unchanged.
