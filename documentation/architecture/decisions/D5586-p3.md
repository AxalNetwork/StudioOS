### 1. The class

`WorkspaceAdmission` hosts #5570's `createAdmissionControl` and part 2's `createAuditedSwarmAdmission` over **one**
`DurableWorkspaceAdmissionStore`, so a swarm ticket and its compute lease change in the same storage, as part 1
designed (the swarm's tickets live under the `swarm` key of #5570's state). It answers `POST /op` with
`{ op, caller, args }`. Each policy change is one storage transaction (D5570 part 2), and nothing is kept in memory
between calls. After each swarm change, the audit is copied to D1's `swarm_admission_events` through `env.DB` (part 2).
A failed copy is retried by the next call and never changes the answer.

- **The limits.** No broker record holds the coordinator's caps yet. `COORDINATOR_LIMITS` gives no provider a cap, so
  a compute lease waits (bounded: 10 per tenant, 100 in all) and is never admitted. Inline swarm tickets are admitted by
  the venture policy the caller read. The provider reader is "unread" too: a reconciling lease keeps its slot. Both
  are protected methods (`limits()`, `observe()`), which the Miniflare test overrides in a subclass of the real class.
- **The export.** `index.ts` re-exports the class, because the Workers runtime finds a Durable Object class only among
  the entry's module exports. That is one new name in a frozen hub (D5615), and `HUBS.md` gives a new class no other
  home, so `scripts/hub-freeze.json` gains exactly `import ./durable-objects/workspace-admission`, as D5581 part 2 §6
  did for `WorkGraphLease`.

### 2. The naming key: one object for every tenant that shares a quota

Every venture's call goes to `idFromName('workspace-admission:shared-quota:v1')` (`WORKSPACE_ADMISSION_OBJECT`).

- **The caps are shared.** The caps are per provider and per `provider:region`, and every tenant draws on the same
  ones. D5570 part 2: per-tenant objects would each hand out the whole quota.
- **Fairness needs one view.** Fair scheduling (fewest held slots first) and the per-tenant caps compare tenants, so one
  object has to see them all.
- **The audit's key.** The audit's `seq` is unique only within one coordinator (D5586-p2 §2). A second object would
  write colliding keys into `swarm_admission_events`.

Today there is one pool, so there is one name. `coordinatorName(venture)` is the one place a second pool (say, per
region) would be chosen. That would first need a coordinator column on the audit table, as an expand migration.
The object refuses any other name (`wrong_coordinator`). This object serializes every admission call. That is the
cost of a global quota, and the same trade `AI_GOVERNOR` makes per account.

### 3. The client (`workspaceAdmissionClient(env, caller)`)

| Method | Object op | Answers (`value`) |
| --- | --- | --- |
| `admission.request(req)` | #5570 `enqueue`, then one `admit` pass | the caller's slot: `{ state, generation, lease_expires_at, compute_reserve_microusd, duplicate }` |
| `admission.settle(run_uid, generation, measured)` | #5570 `release` | `{ charged_microusd, measured, first }` |
| `admission.withdraw(run_uid, generation)` | #5570 `cancel` | `{ state }` |
| `swarm.request(req, policy, facts)` | swarm `request` | the ticket view, as part 1 |
| `swarm.promote(ventures)` | swarm `promote` | the caller's admitted ticket uids |
| `swarm.settle(ticket_uid, measured, generation?)` | swarm `settle` | `{ charged_microusd, measured, first }` |
| `swarm.withdraw(ticket_uid, venture)` | swarm `withdraw` | `{ state }` |
| `swarm.revoke(venture, agent_id)` | swarm `revokeAgent` | `{ withdrawn, still_running }` |
| `swarm.snapshotFor(venture)` | `snapshotFor` | the venture's `SwarmState` |

Every answer is `{ ok: true, value } | { ok: false, status, code, message, reasons }`, the swarm's result shape.

- **Scope.** `caller` is the authenticated `Scope` (a route's, never a request body's). Any argument that names
  another venture is refused `wrong_tenant` (403) **before any stub call**. That covers a request, a policy, a
  withdraw or revoke venture, a promote map key or policy, and a snapshot venture. The object runs the same check
  again (`scopeRefusal`, shared). A call keyed only by a uid (the two settles, `admission.withdraw`) is checked inside
  the object against the stored owner. Another venture's lease or ticket answers `lease_not_found` /
  `ticket_not_found`, exactly as if it did not exist.
- **One bill per lease.** A #5570 call on a lease that a swarm ticket holds is refused `swarm_ticket`: that lease
  settles through the swarm, so its one bill is the ticket's.
- **Never throws.** With no binding, the answer is `admission_unbound` (503). A stub that throws, answers non-200 or
  answers something that is not a result is `admission_unavailable` (503). Nothing is assumed admitted.

### 4. For #5585 part 13

`RELEASE_ADMIN_DEPS.renderAdmissions(env, scope)` calls

```ts
import { swarmSnapshotFor } from './agents/workspaceAdmissionClient';
renderAdmissions: async (env, scope) => { const r = await swarmSnapshotFor(env, scope); return r.ok ? r.value : null; }
```

- **The signature.** `swarmSnapshotFor(env: Pick<Env, 'WORKSPACE_ADMISSION'>, scope: Scope): Promise<{ ok: true;
  value: SwarmState } | { ok: false; status; code: 'admission_unbound' | 'admission_unavailable' | 'wrong_tenant' |
  'invalid_admission_call' | …; message; reasons }>`.
- **The answer.** `value` holds only `scope`'s tenant and company: its `tickets` and its `audit` entries, refusals
  included. The counters (`audit_seq`, `audit_dropped`, `audit_flushed_seq`) are the coordinator's.
- **When it cannot read.** A refusal becomes null, which `renderAdmissions` already reads as `admission_unverified`.
- **The deps.** `RELEASE_ADMIN_DEPS` takes `Pick<Env, 'DB'>` today. Part 13 widens that to include
  `WORKSPACE_ADMISSION`.

### 5. Not in this part

- **Callers.** No route, cron or flag calls the client. Each caller (the engine's lease path, the release render
  check) is its own change.
- **Caps from a record.** The coordinator's caps and the provider reader need a broker-owned record and a provider
  observation. Until then, no compute lease is admitted.
- **Scheduled `admit`/`reconcile`/`promote`.** An alarm or cron that runs `admit`, `reconcile` and `promote` for every
  venture. Today the client runs them only for the caller.
- **Part 2's remainder.** The authenticated read route, the dashboard UI (it needs a canvas), recorders for the
  `not_recorded` signals, bounded state retention and the hosted stages are all still open.

### Deploy and rollback

The `v9-workspace-admission` tag creates the class's namespace on the next deploy of each environment. Nothing reaches
the object until a caller is added. Rollback has two steps. First, revert the client and the class, but keep the
binding and the tag: a Durable Object migration tag is append-only, and removing a class whose namespace exists needs a
`deleted_classes` migration. Second, if the namespace must go, add `[[migrations]] tag = "v10-…" deleted_classes =
["WorkspaceAdmission"]` in all three tables. It holds only preview state, which the D1 audit copy outlives.
