## D7142 — The backup manifest and the drill split read the D1 export as a stream (#7142)

### What changed

`scripts/d1-backup-manifest.mjs` (`buildManifest`) and `scripts/dr-drill-split.mjs` (the command line) no longer read the export into one JavaScript string.

1. **One statement splitter, fed in pieces.** `splitStatements` is now `StatementSplitter` in `dr-drill-split.mjs`. `push(text)` takes any piece of the export and hands each statement on as soon as its `;` is read. The rules are the ones D523 wrote: `''` escapes, `""`/`` ` ``/`[]` identifiers, `--` and block comments dropped, and `BEGIN … END` trigger bodies with nested `CASE`. They are not new rules. A piece may end anywhere: inside a string, a comment or a word, or between the two characters of `--`, `/*`, `*/` or a doubled quote. The one character that needs the next piece to decide is held back until that piece arrives, as is the first half of a surrogate pair so that byte offsets stay right. `splitStatements(sql)` is the same class fed one piece, so the string path and the stream path share every rule. An error reports the same character offset as before, and the byte offset the command line prints.
2. **Manifest.** `describe()` is now `createDescriber()` (`add(statement)`, `result()`), so it is fed one statement at a time. `describeFile(path)` streams the file once with `createReadStream` and a streaming `TextDecoder` (`ignoreBOM: true`, so the decode matches `readFileSync(path, 'utf8')`, invalid bytes included). The same pass hashes the bytes. `buildManifest` uses it. `MANIFEST_VERSION` (1) and every field are unchanged: version, key, database, exported_at, time_travel_bookmark, size_bytes, sha256, statements, tables (name, rows, references), and migrations (ledger, count, last). `restore-d1.sh`, `dr-drill.sh` and backup-status read the file as before. `describe(sql)`, `verify`, `compare` and `chunk-tables` keep their signatures.
3. **Split.** Planning is now `createRestorePlanner({ store })`, made of `add(statement)` and `finish({ chunkBytes, onChunk })`. It does the same classification, cycle breaking, parents-first order and packing as before. `planRestore(sql)` runs it with rows held in memory, so its output is unchanged. The command line runs `planFile`. That decodes the export as a stream and spools each table's rows to a temporary directory (`spoolStore`: a 4-byte length plus UTF-8 bytes per row, one 64 KiB write buffer per table). It writes each chunk file when the next chunk opens and removes the spool when it finishes. Chunk names, their contents, their order, `manifest.tsv` and the counts line are the same as before. Nothing is written when the export fails to parse or holds no `CREATE TABLE`, as before. The spool needs free disk about the size of the export, beside the chunk files, which are also about that size.

### Why

Node refuses a string longer than 536,870,888 characters (`ERR_STRING_TOO_LONG`), about 512 MiB. Both scripts called `readFileSync(path, 'utf8')` on the whole export. The nightly exports were 298 MiB on 2026-11-15, 302 MiB on 2026-11-16 and 306 MiB on 2026-11-17 (runs 43698134142, 43840201920 and 44066154804). That is growth of about 4 MiB a day, which reaches 512 MiB around **2027-01-07**: (512 − 306) / 4 ≈ 51 days after 2026-11-17. Multi-byte UTF-8 brings that date earlier, never later, because the limit counts characters and a multi-byte character is one character but two to four bytes. After that date, Daily D1 Backup would fail before upload (the manifest is built first), and the Monthly DR Drill could not split the backup. That is the same kind of outage as #7127: our own tooling hits a size limit after D1 has done its part. #7128 lifts Wrangler's 300 MiB upload cap and does not touch these reads.

### Evidence

- `frontend/test/d1_backup_stream_d7142.test.mjs`. **Golden:** the streamed manifest (API and CLI) and the split's chunk files, `manifest.tsv` and counts line are byte-identical to the frozen pre-D7142 code (`frontend/test/fixtures/d7142_old_d1_backup_manifest.mjs` and `d7142_old_dr_drill_split.mjs`, copies of `main` at cf2810ad). This holds on D4558's manifest fixture, D523's drill fixture, the FK-cycle fixture and a fixture holding every boundary the splitter knows (BOM, multi-byte table name, multi-line `INSERT … VALUES`, `;` and newlines in strings, TEMP triggers with nested `CASE`). It holds at read sizes of 1, 2, 3, 7, 64 and 65,536 bytes, and at chunk budgets of 1,024 and 1,000,000 bytes. Errors give the same offsets in characters and bytes. Bytes that are not UTF-8 decode as `readFileSync` decoded them. 3,000 seeded random inputs, fed in random pieces, split exactly as the old splitter split them. **Boundaries:** a statement split across reads, and a `;` inside a string literal (also a doubled quote, `--`, `/*`, `*/` and a keyword split between reads) are each counted once. **Memory:** a 96 MiB export is described and split under `--max-old-space-size=48`, where the old manifest dies. The counts match the generator and peak RSS stays under 160 MiB. With `D7142_LARGE=1`, a 630,194,575-byte (601 MiB) export runs under `--max-old-space-size=512` and matches the generator's counts. Peak RSS was 80 MiB for the manifest and 142 MiB for the split. That test writes the file to the temp directory and deletes it.
- Measured by hand on a 630,194,473-byte synthetic export (901,563 statements, 450,778 rows in each of two tables), on a 4-core container: the manifest took 3.1–3.3 s and the split (619 chunks) took 7.8–9.9 s, under both `--max-old-space-size=512` and `=64`. The pre-D7142 manifest exits with "Cannot create a string longer than 0x1fffffe8 characters", and so does the pre-D7142 split, even with a 4 GiB heap. On a 314,573,078-byte export, the old and new splits wrote identical chunk files (by SHA-256), an identical `manifest.tsv` and an identical counts line, and the old and new manifests were byte-identical.
- Every new assertion was mutation-checked: 17 mutations, 16 caught. The equivalent one is stripping the BOM in the manifest's decoder, which changes nothing the manifest records, because `trim()` drops a leading BOM from the first statement. The same mutation in the split's decoder is caught, because it shifts the byte offset an error reports.

### Not done

- Hosted proof: the first nightly backup after merge has to publish a verified heartbeat, and a DR drill against that backup has to pass. Those runs happen after merge, not in this PR.
- `chunk-tables` still reads one chunk file whole. A chunk is at most `chunkBytes` (1 MB by default) unless a single statement is larger, so it is far from the string limit.
- Reducing the database size, the R2 upload path (#7128) and restore chunk sizing are out of scope (#7142).
