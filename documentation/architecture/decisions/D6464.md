## D6464 — Flaky tests in the merge queue: a derived list, one retry, one issue per test (#6464)

- **Status:** built 2026-11-15 by S25 for #6464 (plan key A5, under #5600).
- **Code:** `scripts/flaky-tests.mjs` (the collector), `scripts/lib/flakyTests.mjs`
  (the rules), `scripts/lib/failedTestsReporter.mjs` (a node:test reporter),
  `scripts/test-drift-parts.mjs` (the suite runner's retry),
  `scripts/flaky-tests.json` (the list).
- **Tests:** `scripts/lib/flakyTests.test.mjs`, run by `npm run test:retention`.

### 1. Which tests are flaky

`flaky-tests.mjs` reads `ci.yml` runs from the last `--days` (7 by default):

- **Failed merge-queue runs:** the logs of their failed `suite (<part>)` jobs,
  and the files the run's PR changed.
- **Successful runs:** merge-queue runs, and pushes to `main`.

A failed test counts as one observation only when two things hold:

- Its file is not one the PR changed.
- The same code passed afterwards: the same commit in a later run, or `main`
  within 24 hours of the failure.

A test is flaky only when it is intermittent: either the same commit failed
and then passed it, or it failed on two different days with a successful run
between. A one-day burst is not a flake, however many runs it failed. Two
kinds of episode produce one. A red `main` (D5398) fails every entry until the
repair. An entry ahead in the queue can also break a test for the entries
behind it. On 2026-11-14 `workflow_channel_inventory` failed five times that
way: a new workflow had no Slack catalog row. The same code fails the same way
every time, so a retry could never help.

A flaky test enters the list after two runs and stays while it keeps failing.
An entry leaves after 14 clean days (`expiryDays`), or as soon as its name no
longer appears in its file's source. A test renamed or rewritten since it
failed can never match a failure, and its fix may be why it changed.

The failing test's name and file come from the TAP log. The file is the
`location:` of the `not ok` line, TAP's `\#` and `\\` escapes are undone so
the name matches what the reporter sees at run time, and a failed `describe` is
skipped in favour of the tests inside it. When the per-test artifact (#5502) and the per-entry
record (#5973) exist, they can replace the log reading; the rules stay the
same.

### 2. The one retry

Each node:test command in a suite part runs through `test-drift-parts.mjs`.
Under `merge_group` only, that command also writes its failed tests through
`failedTestsReporter.mjs`. TAP stays on stdout, so the log is unchanged.

When the command fails, the runner retries only if every failed test meets all
of these:

- It is on `flaky-tests.json`, matched by both file and test name. Another test
  in a listed file is not covered.
- Its file is not one the queue entry changed, read from `merge_group.base_sha`.
  If those changed files cannot be read, nothing is retried.

The retry runs those files once. If it passes, the part passes and the job
summary gets a "Flaky, retried" section naming each test. If it fails, the
part fails as before, with a "Flaky retry failed" section. Everything else
fails exactly as before:

- an unlisted failure;
- a `pull_request` or `push` run;
- a non-node:test step, such as `rest`'s guards.

### 3. Who changes the list

Only a PR that commits `flaky-tests.mjs --write` output changes the list. The
runner reads `flaky-tests.json` and never writes it, and a test checks that.
A missing or malformed list retries nothing.

### 4. One issue per test

`flaky-tests.mjs --open-issues` opens a `ci` issue titled
`Flaky test: <file> › <test>` for each listed test that has no issue with that
title yet, open or closed. The issue asks for the test to be fixed and its
entry removed in the same PR.

### 5. The first list (2026-11-15)

The window was the last 7 days: 175 failed merge-queue runs, 174 with a failed
suite part. Most of those failed in a guard step, an install or the runner,
not in a named test. The list is **empty**, so the retry would have turned 0
of the 175 green. The four tests #6464 named, in this window:

- `program_grant_revisions_d4805` › "7b. the push is durable…": one run.
- `data_room_d696` › "11. for a founder the bare address is the module page":
  9 runs on 11 and 12 November, which would qualify, but the test has since
  been rewritten and that name no longer exists.
- The retainer tests (`partner_delivery_measurements_4690`,
  `partner_pipeline_stores`): one run each.
- "A custom program: create → open → edit → publish → revisit": no run with a
  failed suite part in this window.

No queue commit was ever re-run to success, because the queue rebuilds an
entry as a new commit. So the same-commit signal is empty, and the two-day
rule is the one that can list a test.
