### 1. Migration 610

- **The feed token's scope.** `calendar_feed_tokens` allows `my_events` and `calendar`.
  - SQLite cannot widen a CHECK, so the table is rebuilt, as 562 rebuilt `program_grants`. Every row is copied with its id and hash, so no subscribed URL stops.
  - The test makes a my-events token before 610 and reads it back unchanged after.
  - It is a second scope, not a second table: one token per member per scope, as 603 designed for "a later feed".
- **The error state.** `last_sync_error` and `last_sync_error_at` on `google_oauth_tokens` and on `microsoft_oauth_tokens`. They are nullable and not backfilled: no earlier failure was recorded.
- **`calendar_sync_retained`.** One row per member per provider: an HMAC of the provider's account id (never the id), and when it was kept (§4).

### 2. The whole-calendar feed (item 3)

- **The routes:**
  - `GET`, `POST` and `DELETE /api/calendar/subscription` read, make and remove the token, signed in;
  - `POST` makes the token or replaces it (`replaced: true`): that is "rotate", and the old URL stops at once;
  - `GET /api/calendar/feed/calendar.ics?token=…` is the feed, with no session.
- **Mine only.** Every calendar reader is keyed on the member's own id, and `gather` ignores the role. So an admin's feed holds what the admin organises or attends, never a studio's calendar or every studio's.
  - The feed names `KNOWN_KINDS`, so a new kind joins it on purpose.
  - The test seeds an IC meeting with the member and one without, an expert session of theirs and one of the admin's, and a ticket. The member's feed holds their three. The admin's feed holds only the admin's own two.
  - Nothing a Studio or All studios scope reads can reach the feed, because no such read exists on the Worker.
- **The token is in the query, not the path.** The issue writes `GET /api/calendar/feed/:token.ics`. D1033 put the token in the query for a reason that holds here: the observability middleware writes the pathname into `api_metrics`, Analytics Engine and the activity log, and a token in the path would land in all three. So the path is fixed and the token rides in `?token=`.
- **One credential per feed.** A my-events token is refused by the whole-calendar feed, and this token by the my-events feed. Removing one leaves the other.
- **The window** is 30 days back and 180 ahead. My events keeps seven back.
- **Outside the session gate, not outside the plan rule.** `INVESTOR_PRO_EXEMPT` lets the GET past the session gate on `/api/calendar`, as for D1033. The route then gives an investor below Professional the same 402, so a lapsed plan stops a token made while it was active. The signed-in `/subscription` routes stay behind the gate.
- **Everything else is D1033's:**
  - only the SHA-256 is stored;
  - every refusal is the same 404;
  - "sign out everywhere" ends the token;
  - the response is `private, no-store`, since it carries join links;
  - `last_used_at` is written at most once a minute.

### 3. The sync error state (item 7)

- **Three codes, each with one sentence** (`SYNC_ERRORS`):
  - `connection_refused`: the provider refused the saved connection, so the member must reconnect;
  - `copy_refused`: some sessions were not copied, so sync again;
  - `sync_failed`: any other failure.

  Only the code is stored. A provider's own error text can carry an address or a title, and it never reaches the store, the response or the log.
- **Who writes it:**
  - **A full sync:** a refused refresh writes `connection_refused`; any other throw writes `sync_failed`. A run with a refused copy writes `copy_refused`, and a clean run clears the state. `not_connected` writes nothing.
  - **The create hooks** (`onAxalSessionCreated`, and so `pushOneEventForUser`): a refused refresh writes `connection_refused`, and a refused copy writes `copy_refused`. A refresh that works clears only `connection_refused`. It proves the connection, not that every copy exists, so only a full sync clears `copy_refused`.
  - **The cancel hook:** a refused delete writes `copy_refused`.
- **The status reads** (`/google/status` and `/microsoft/status`) return two fields:
  - `sync_error` is `{ code, message, at }`, or null;
  - `sync_error_read` is false when the state could not be read, for example before migration 610. The page then says "Unreadable", never a clean sync.

  A code this build does not know reads as `sync_failed`.

### 4. A disconnect keeps the copies (items 8 and 13)

- **One handler per provider:**
  - for Google, `DELETE /google` and `POST /google/disconnect`;
  - for Microsoft, `DELETE /microsoft` and `POST /microsoft/disconnect`.

  On `main` the two Google verbs already did the same thing, but each carried its own copy of the code. Now there is one.
- **Default: keep.** The copies on Google or Outlook stay, and so do their `calendar_sync_records`, so reconnecting the same account updates them instead of copying every session again. The response is `{ ok: true, copies: 'kept' }`.
- **"Remove the copies first"** is `?remove_copies=1`, or `{ "remove_copies": true }` on POST.
  - Every copy is deleted at the provider before anything else. A copy whose delete is confirmed, or already gone, loses its mapping.
  - A refused copy keeps its mapping and stops the disconnect: 502 `copies_not_removed`, with no figure in it. Nothing is revoked, and the member can retry or disconnect keeping the copies.
- **Google is revoked first, as #2413 does.** A refused revocation still keeps everything for a retry. `POST /google/force-disconnect` (local only, after a refused revocation) keeps the copies too.
- **Microsoft** has no grant revocation the Worker can call. Only its saved token goes, as before.
- **The next connect.** The disconnect writes `calendar_sync_retained` with the account's HMAC. The next callback takes the row, which decides one connect only:
  - **Google:** when there is no Gmail-removal marker and no live connection, the row feeds `shouldResetGoogleSyncMappings`. The same account keeps the mappings, and another account drops them.
  - **Microsoft:** another account's mappings are dropped. Their copies stay on that account's calendar.
  - **No row:** each callback behaves as before.
