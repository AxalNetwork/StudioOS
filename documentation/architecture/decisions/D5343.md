## D5343 — Runtime ADD COLUMN moves onto runSchemaBootstrap, hot paths first (#5343)

Follow-up to #4568 R2-04 (PR #4794). `scripts/runtime-ddl-baseline.json` listed 59 files with 338 blind `ALTER TABLE … ADD COLUMN`. Each is for a column a migration already declares. Against an up-to-date database each one can only fail, with `duplicate column name` (on `users`, which is at D1's 100-column limit, `too many columns`). It fails once per fresh isolate, and the error is swallowed. This decision moves them onto `runSchemaBootstrap` (`util/schemaBootstrap.ts`) in batches of related files, one PR each, "Part of #5343".

### The rule for each file

- Route its statements through `runSchemaBootstrap`. That reads the table's columns once per binding and skips an ALTER whose column exists, so production issues none.
- A genuine failure, such as a missing table, is never a quiet success. It throws a named readiness error, or answers `false` where the callers already fail closed on `false`. Either way it is not marked ready, so the next call tries again. The log carries a code, never a value or the driver's text.
- Every caller that used to carry on after a swallowed failure is checked. Each either handles the throw or answers a controlled error.
- The bootstrap stays for local and branch databases that have not run migrations. No applied migration is edited. Where no migration declares a column, the fix is a new migration named by its UTC minute, not the ALTER.
- Lower or remove the file's baseline entry. The ratchet fails a stale entry.

### Order

The order is by how often the code runs, ranked from the code. Production query insights are not available to agents, so this ranking is not measured.

1. **Request-path middleware and per-call services** (this batch): `middleware/lastActive.ts`, which runs after every authenticated `/api/*` request; `services/notifications.ts` and `services/notify.ts`, on every notification write and the digest flush; and `services/aiRouter.ts`'s usage-row columns, written on every AI call.
2. Cron and sweep services, then routes by traffic, then the rest.

`index.ts` (the investor bootstrap, on every fetch until ready) is deferred to a later batch. Its probe already reads `users`' columns first, so it never ALTERs blind in production. Its function is private to the Worker's entry module, and testing it properly means extracting it into its own module first. That is its own change.

### Batch 1 (this PR): 338 → 329 blind ALTERs, 59 → 55 files

| File | Before | After | On a genuine failure |
| --- | --- | --- | --- |
| `middleware/lastActive.ts` | 1 | 0 | throws `last_active_schema_not_ready`. The middleware logs it and skips the stamp, as it did for any failed update. HQ's Team read (`routes/admin_hq.ts`) answers `503 schema_not_ready`, not a 500 from a missing column. |
| `services/notifications.ts` | 1 | 0 | `false`, logged as `schema_not_ready`. Callers already fail closed on `false`. |
| `services/notify.ts` | 4 | 0 | `false`, logged as `schema_not_ready`. Callers already fail closed on `false` (no inbox row, no digest flush). The per-ALTER `try {} catch {}` loop is gone, so a failed ALTER no longer counts as ready. |
| `services/aiRouter.ts` | 3 | 0 | the error reaches `recordUsage`'s catch, which logs it and returns `null`, as before. It already read the table's columns first; it now goes through the shared bootstrap. |

`ensureNotificationsSchema` and `ensureInbox` are exported so the test can reach them. Their behaviour is otherwise unchanged.

**Tests.** `cloudflare-worker/test/runtime_ddl_5343_batch1.test.ts`:
- on the migrated schema, three fresh isolates and repeated calls issue no ALTER and no duplicate-column or too-many-columns error;
- with the columns missing, each bootstrap adds them once and the next isolate issues none;
- with no `users` table, lastActive throws its readiness error, retries, and recovers once the table exists;
- a failing notification ALTER answers `false`, is retried, and recovers;
- two isolates starting together both succeed and add each column once.

Restoring each file's blind loop fails the test.

### Batch 2: 329 → 323 blind ALTERs, 55 → 49 files

Six single-column bootstraps. Three ALTERed blind. Three already read the columns but did it by hand, so they now share `runSchemaBootstrap`.

| File | Runs on | Before | On a genuine failure |
| --- | --- | --- | --- |
| `services/market_intel/extractor_schema.ts` | the MI queue consumer | blind ALTER on `users` | `users` is at D1's 100-column limit. The blind ALTER of the existing `mi_contribution_optout` failed "too many columns" on every fresh isolate (not "duplicate column", which it ignored), logged a warning, and marked the binding ready anyway. Now it issues no ALTER; a failed statement leaves the binding unready and the next call retries. |
| `services/captableSchema.ts` | every cap-table read and write, the Demo Day deck, the SAFE basis repair | blind, every error swallowed | Throws `captable_schema_not_ready`, unready. Production always has `cap_table_scenarios`. Two test fixtures that built a cap-table database without it (`closing_guards_d1214`, `lab_honesty_zeros_d366`) now create it: the old bootstrap hid the gap by passing on a missing table. |
| `services/exploringSchema.ts` | the fetch-path exploring bootstrap | blind, swallowed | Reaches the bootstrap's existing catch, which logs it and leaves the schema unready. |
| `services/decks/cardBlobs.ts` | the card-blob prune cron and deck reads | read first by hand | `false`, unready, as before. |
| `services/eventsSchema.ts` | events outside production (production skips it) | read first by hand | `false`, unready, as before. |
| `services/xSchema.ts` | X posts | read first by hand; a failed column was logged and marked ready | Reaches the bootstrap's catch, unready. `schema_readiness.test.ts`'s D1 stub now answers `prepare()` the way D1 does (records the statement, returns no rows), since the column now goes through it. |

**Tests.** `cloudflare-worker/test/runtime_ddl_5343_batch2.test.ts`:
- on the migrated schema, three fresh isolates issue no ALTER and no duplicate-column or too-many-columns error;
- each missing column is added once, and the next isolate issues none;
- the cap table with no table throws, retries and recovers;
- a failing ALTER leaves the extractor, X and card-blob bootstraps unready, and the next call adds the column;

Mutation-checked: the extractor back on a blind exec, the cap table swallowing again, and the extractor latching after a failure each fail it.
