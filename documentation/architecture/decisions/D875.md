## D875 — Meeting Capture for Record a Session: the Zoom and Meet setup, and the calls that can be attached

- **Status:** filed by S1 as #2522, part of #2516. Built by S11.
- **Basis:** `origin/main` at `e19ff787bc`. Worker paths are relative to `cloudflare-worker/src/`.
- **Stacks on:**
  - D684 and D685 (the Zoom and Meet adapters, and attaching a call to a recording);
  - D757 (Meet transcripts behind `MEET_TRANSCRIPTS_ENABLED`, and the Zoom audience);
  - D863 (the Telegram setup read, whose shape this follows);
  - D872 (uploading a call recording).
- **Migration:** none.

### 1. The decision

A founder can see, without reading `documentation/operations/ZOOM_AND_MEET_TRANSCRIPTS.md`, two things:

- whether their Zoom and Google accounts are ready to have calls transcribed into an interview, and what is missing;
- which of their upcoming calendar calls can be attached to one.

There are two reads, both signed in as the member, and neither writes anything.

### 2. `GET /api/founder/validate/meetings/setup` (`services/channels/meetingSetup.ts`)

Each provider's steps are `done`, `todo` (the member's move, in one sentence) or `blocked` (Axal or an earlier step comes first, in one sentence), with a code. The read follows D863: `steps`, `next` (the first step not done), `ready`, and `prerequisites`.

| Provider | Step | Read from |
| --- | --- | --- |
| Zoom | `set_up` | the deployment's three Zoom secrets (`zoomConfigured`) |
| Zoom | `app_open` | `ZOOM_APP_AUDIENCE` (`zoomDistribution`): `own_account` is blocked, `beta` is the member's to check, `public` is done. A member who has connected is inside the distribution, whatever the var says. |
| Zoom | `connected` | the member's active `integrations` row for `zoom` (`zoomConnection`) |
| Google Meet | `set_up` | the Google Calendar OAuth client (`googleOAuthAvailable`) |
| Google Meet | `connected` | the member's `google_oauth_tokens` row (`googleConnection`) |
| Google Meet | `transcripts` | `meet_transcripts`, the same reading `GET /api/calendar/google/status` gives (`meetTranscriptsState`). It is blocked while `MEET_TRANSCRIPTS_ENABLED` is off, a todo while the scope is missing, and done when granted. A row with no recorded scope at all says "allow it once", since Axal cannot tell. |

The response also carries `zoom.audience` and `google_meet.meet_transcripts`.

**No provider call.** Every step is answered by a stored row or a var, so the read never calls Zoom or Google.

**What Axal cannot see is a prerequisite with a null state**, said as a reminder:

- **Zoom:** a paid plan with cloud recording, and "Create audio transcript" turned on.
- **Meet:** a Workspace edition with transcription, turned on in the call.

### 3. `GET /api/founder/validate/meetings/upcoming`

**What it reads.** The next 14 days (`UPCOMING_DAYS`) of the member's own primary Google Calendar:

- with the member's own grant;
- `singleEvents`;
- a `fields` mask that never asks for attendees or the organizer's address.

**Which events are kept:**

- an event with a Meet conference (the video entry point, else `hangoutLink`);
- an event with a Zoom join link, found in the conference, else the location, else the description.

Cancelled and all-day events are skipped. A call already held in `interview_channel_refs` is not offered again. That table has one row per call (`UNIQUE(provider, external_ref)`), whoever holds it.

**What each call is:** `provider`, `title` (whitespace folded, at most 200 characters), `starts_at`, `ends_at` and `join_url`, then `attach` or `attach_blocked`.

**What it never returns:**

- an attendee or an organizer's address;
- a description;
- a location;
- a Zoom passcode.

The description and location are read only to find a Zoom link. The link is rebuilt from its host and meeting id, so a `?pwd=` never leaves the Worker. Attaching needs only the id.

**Attaching** uses the existing D685 route, so nothing new writes a ref:

```
POST /api/founder/validate/interviews/:interview_id/meetings
{ "attach": { "join_url": "…" }, "session_id": <the video recording> }
```

That route does the checks:

- it needs a video session that is recording, with consent given;
- for Meet, `verifyHostedMeet` (the member organizes the event on their own calendar);
- for Zoom, `verifyHostedMeeting` (the connected account hosts the meeting).

So `attach.needs` names `interview_id` and `session_id`. The read offers attach only where it can already tell it will pass:

- **A Meet call** the member does not organize (`organizer.self`) answers `attach_blocked`, in our words.
- **A Zoom call** is offered when Zoom is connected. Whether the member hosts it cannot be read from Google, so the attach route checks it.

**Errors.** A member with no Google connection gets `{ connected: false, calls: [] }`, and no call is made. When Google refuses the grant, the answer is 409 `meet_reconnect`. When Google cannot be reached, it is 503 `meet_unreachable`. Each carries `MEETING_ERRORS`' sentence.

### 4. The connector pages

The Zoom and Google Calendar pages (`integrations/connectorPages.ts`) now say once that a call which ends without a transcript can still reach Customer research. The founder uploads its recording file in Record a Session, and Workers AI transcribes it on their AI tokens (D872).

**The audio fallback (M1, #2517) is not said.** It is not on `main` yet, and a page states only what is built. Its sentence goes in with M1.

### 5. Where this departs from the issue

- **The path.** The issue names `/api/validate/meetings/*`. No `/api/validate` mount exists: Record a Session's routes are under `/api/founder/validate` (`routes/founder_validate_sessions.ts`, the file the issue gives). The reads sit there, beside `GET /sessions/active`.
- **"M2's route for Meet".** The issue expects M2 (#2518) to add an attach route for Meet. The D685 attach route already takes a Meet link the member organizes, alongside Zoom's paste. Upcoming uses it for both, so this does not wait on M2. If M2 adds a route for a Meet call the member does not organize, only `attach_blocked`'s `meet_not_organizer` case changes.

### 6. Tests

`cloudflare-worker/test/meeting_setup_upcoming_d875.test.ts` covers:

- **Setup:** every Zoom and Meet state from fixtures (nothing set up; each audience; connected; the transcript scope off, missing, unrecorded and granted). Another member's connections never answer, and no provider request is made.
- **Upcoming:**
  - only the member's own calendar, through their own token;
  - the 14-day window and the field mask;
  - the four kept calls and the four skipped ones (cancelled, all-day, no link, already held);
  - no address, description, location or passcode in the body;
  - Meet attach only for the organizer, and Zoom only when connected.
- **No connection, and a refused grant.**
- **Attach from the list:** for a Meet call the member organizes and a Zoom meeting they host, through the D685 route. Once attached, neither is listed again.
- **`zoomLinkOf`:** its order of sources, and that a look-alike host is refused.
