## D5888 — Referral partners runs in the generic program shell (#5888)

- **Status:** built 2026-11-15 (#5888). Frontend only: no migration, no new Worker route, no new client method.
- **Number:** D5888 is the issue's number (D4106).
- **Builds on:** D5313 (Perks in the shell, and the pattern for the other eight), D4873 part 4 (the generic shell, PG03, `MODULE_PATHS`), D963 (Referral partners' Overview, How it runs, Queue, Activity and its signed-terms dialogs), D953 (the page and its addresses).
- **Answers:** the owner's option A on #4873 (2026-11-09): the nine built-in program pages move into the generic shell, one task per page. This is Referral partners, PG03a on the Programs v2 canvas.

### What changed

`/admin/programs/referral-partners` now draws the shell's six core sections, with its own screens where it has them:

| Tab | Address | What it draws |
| --- | --- | --- |
| Overview | `/admin/programs/referral-partners` | the segment chips, four tiles, both charts, Standard rules, where partner deals live and the partners table (D963), then the shell's Capability modules |
| Playbook | `/how-it-runs` | the playbook editor (D963), unchanged |
| Availability & grants | `/availability` | the shell's section: the grant badge, whether it can be offered, Manage grants |
| Participation | `/participation` | Partners taking part and Introductions this quarter, from the summary Overview already reads; Partners who introduced someone: "Not recorded" |
| Referral queue (module) | `/queue` | the terms sent to HQ (D963), unchanged, at `MODULE_PATHS['referral-partners'].referral_queue`; the tab carries the count waiting for HQ |
| History | `/activity` | the activity read (D963), unchanged |
| Settings | `/settings` | the shell's member-access editor (Super Admin) or its value (Admin) |

- **Every address is kept.** The four D953 and D963 gave Referral partners keep their paths and their `App.jsx` lines, which this task leaves alone. The three new ones are literal routes in `frontend/src/routes/adminProgramsReferralPartners.jsx`, onto the same `ProgramPage`, which `App.jsx`'s glob picks up. Until now they fell through to `/admin/programs/:key/…` and drew the registry-backed page.
- **Every test id is kept.** Overview, the queue, the playbook and the activity sections draw the same components with the same ids; the tab ids (`programs-tab-overview`, `-how`, `-queue`, `-activity`) are unchanged, and the new tabs take the shell's (`-availability`, `-participation`, `-settings`).
- **The signed-terms dialogs still work.** `ReferralTermsDialogs.jsx` (Custom terms, Approve, Send contract, End terms, a rule's edit) still opens from the page's own desk, outside any registry section, so it opens from Overview's row menu and the queue as before, and also when the registry read fails.
- **The registry read is the frame's.** `useProgramDetail('referral-partners')` feeds the header, Capability modules, Availability and Settings. A failed read marks only those: Availability and Settings say "This program could not be read" with Try again (`OnRegistry`), Modules says "Could not be read", never "None yet". Overview's own reads, Participation, the queue and History still draw.
- **Participation is never a 0 that was not measured.** The summary (`admin_referral_partners.ts` `/summary`) counts active partners and this quarter's introductions, so those are shown, a measured zero as 0, and a figure it did not carry as "Not recorded". It does not say which partners made the introductions, so "Partners who introduced someone" is "Not recorded" with that reason (`partnerParticipationTiles`, `referralPartnersModel.js`). A failed summary reads "Could not be read".
- **The strip.** `PAGES['referral-partners'].tabs` and `ProgramTabs.jsx`'s `PartnersTabs` list the seven tabs in PG03's order and words, each a literal `<Tab to="…">`. The module tab carries `module: 'referral_queue'`; the test holds its path equal to `moduleRows('referral-partners', …)`'s and the strip equal to `PAGES`.

### Departures from PG03a

- **Overview keeps the program's own figures.** PG03a draws a queue preview and an Availability card on Overview. Overview keeps D963's tiles, charts, rules and table, and adds Capability modules. The queue is one tab away and carries its count; Availability is its own section, as D5313 did for Perks.
- **The header action stays Invite a partner.** No "Review referral queue" door is added: the tab already carries the count, and Invite a partner (to Partner invitations) is the program's primary action.
- **The queue card keeps its title "Queue".** Only the tab reads "Referral queue", so the card's words and ids stay as D963's tests pin them.
- **No "+ module" chip.** A module arrives with its screen, so nothing here switches one on (D4873 part 4).
