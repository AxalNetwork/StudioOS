## D1326 — Fill with Eadwyn part 3: the write — the form run, the record after Save, Accept all for rows, and undo

S17, 2026-10-27, for #3487 (part 3 of #2431). No migration: migration 643's columns (D1325)
carry the source and the value a fill replaced. Basis: `main` at `76a6081b82`.

### 1. `POST /api/ai/rail/run`, handler `form`

`routes/rail_run.ts`, mounted at `/api/ai/rail`. It is D720 §7's one run path, with its
first handler.

**The body:**

    { page, option: 'form:<form>', project, record?: { type, id }, model?, input?: { values, text, rows } }

**Before the run:**

- `page` and `form` must name a FILL_FIELDS form (D1325).
- The venture must be one the member may write, in their own session. An advisor and a
  support session are refused.
- `record`, when given, must be a row of the form's table on that venture.

**What it asks for:**

- Each field of the form that Eadwyn is offered (`offeredToEadwyn`) and that is blank, both
  in what the member sees (`input.values`) and in the record.
- On an Add form, `input.rows` asks for up to 10 whole rows instead.

  A typed field is never asked. A measured field is never asked, so a form with only
  measured fields answers `nothing_to_fill`.

**The gather** (`services/fills/formRun.ts`) reads only:

- the venture's own pain themes and unretired hypotheses: the choices the restatement fields
  pick from;
- the titles already on the table;
- the member's own words.

The guard checks only the member's words (`guardText`, D763).

**The parse:**

- **restatement:** keeps a value only when it is one of the venture's own records, by id.
  Anything else is dropped as `unmatched`.
- **sourced:** keeps a value only with a citation, otherwise `no_citation`.
- **composition:** a value aimed at a measured field is dropped as `measured`.
- **never-fill:** a field the registry names is refused as `never_fill`, even when the form
  does not have it.
- **Effort** is kept as the writer stores it (S, M or L), so the record step can compare it.

**`run()` does the rest, in D720's order:**

1. the switch (`assist_off`, D765);
2. the hold (D762);
3. the guard on input and output (D763);
4. the model;
5. settling.

`quoteRun` gives `meta` its model and hold before anything runs. A refusal at either step is
`done`'s `refusal`, in `refuseRun`'s words. `refuseRun` now builds its answer from the new
`runRefusalView`, so a streamed answer and a JSON answer say the same thing.

**The stream:**

- `meta`: `{ model, hold_microusd }`;
- `guard`: `{ input, output }`;
- `done`: `{ proposals, dropped, usage_log_id, charged_microusd, budget }`, or
  `{ refusal: { code, status, message } }`.

**What it writes:** one `ai_rail_proposals` row per kept field, or per row, each naming the
run's `usage_log_id` and its project. It never writes the record. In a form, nothing is
written until Save.

**A changed form drops the result.** The asked columns are read before the run and again
after it. If any changed meanwhile, nothing is proposed (`record_changed`).

### 2. `POST /api/fills/record`: after the form's own Save

It re-reads the row the Save wrote, on the venture, and decides each proposal uid on its own:

- **Kept:** the field still equals what was proposed.
  - The proposal becomes `accepted`.
  - One `fill_provenance` row is written through `recordFill`, which checks never-fill a
    third time.
  - The row names the proposal and its run.
  - It gets `source_kind = 'eadwyn'` and `prior_value`.
- **Changed before Save:** the member's value is theirs. The proposal is discarded and no
  Eadwyn row is filed.
- **Refused, each with its reason:**
  - another member's proposal (`not_found`);
  - another form;
  - another venture or record;
  - a never-fill or measured field;
  - an already decided proposal.

### 3. `POST /api/fills/rows/accept`: Accept all for row proposals

- It takes at most 50 (#2431 question 3, A). The rest come back untouched as `over_limit`.
- Each row goes through its form's own writer (`ROW_WRITERS`). Add feature's writer is
  `featureCreateStatements`, the statements `POST /features` runs, with the same rules:
  - a title is required;
  - a pain theme or hypothesis must be the venture's own and unretired;
  - Impact is the founder's, Medium until they set it.
- Each outcome is reported.
- A proposal is decided before its row is written, so two presses cannot both create it. When
  the writer refuses, the proposal is put back to `proposed`.
- Each written field gets its provenance row.

### 4. `POST /api/fills/:id/undo`

- It writes the prior value back through a literal statement on that column only
  (`UNDO_WRITES`, scoped to the venture).
- It acts only while the field still holds what the fill wrote. An edited field is the
  member's (409 `edited`).
- A column the writer never leaves blank cannot be put back to blank (409 `no_prior`).
- It records `undone_at` and `undone_by`, and a `fill_undone` log line with ids only.
- The row's write is guarded on the fill not already being undone, so two undos write it once.
- A fill on a venture the member cannot write reads as one that does not exist.

Eadwyn fills only blank fields, so an Eadwyn fill's prior value is blank today. The column
carries what a connector's "Use GitHub's instead" will replace (PIPE-BUILD, #2426).
