## D629 — Licence AI allowances and paid top-ups

Issue #1372 implements the owner's 7.A answer on #1138. Migration 419 is additive. Bounty and introduction credits remain separate currencies and ledgers.

### Caps and configuration

One `ai_licence_caps` table holds explicit daily/monthly integer USD-millionth overrides. Empty means use the deployment's existing environment cap, then the existing default. No differentiated paid allowance is invented. An explicitly recorded zero means zero. The Super Admin writes a recognised key through `PUT /api/ai-budget/caps/:licence`; the cap write and actor audit commit together. Effective founder/investor tiers use the existing entitlement helpers, including delinquency and grant expiry.

| Licence key | Daily fallback | Monthly fallback |
| --- | --- | --- |
| founder:free, founder:growth, founder:studio | `WORKERS_AI_BUDGET_USD_DAY`, otherwise $5 | `WORKERS_AI_BUDGET_USD_MONTH`, otherwise $50 |
| investor:free, investor:professional, investor:institutional | same | same |
| advisor, partner, admin, other | same | same |

The issue directs the slot to post options and build its pick. Picks: 1A retain these fallbacks until explicit overrides; 2A integer micro-USD to preserve sub-cent model prices, rather than rounding each call up to a cent; 3A one USD actually paid for the top-up before tax buys one USD of balance. The integer-money guard also recognises the explicit `_microusd` unit and rejects float/text storage. Checkout amounts remain integer cents; $1 is 100 cents or 1,000,000 micro-USD. This is an explicit precision extension to the cents convention, not a new price surcharge.

`STRIPE_PRICE_AI_TOPUP` is an owner-created, active, one-time USD catalog price. Absent means **Top-up not configured**, with no purchase button. Invalid/unreadable configuration means **Unreadable**. Creating the product and configuring the price and existing Stripe webhook secret are owner actions. No provider product is created by this implementation.

### Draw order and estimates

The caller's remaining included allowance is the smaller remaining daily/monthly allowance. Each call reserves the worst supported model/fallback estimate, with a UTF-8 input bound and chat overhead, before invoking the provider. D1 allocates the included portion first, then paid balance in one transaction; simultaneous calls cannot spend the same balance. Settlement uses the router's existing recorded estimate, refunds unused allowance/balance and records each actual paid draw with its account actor. Replay cannot repeat a settlement. Failed model chains refund the hold. Cache hits cost zero. Org monthly enforcement and its kill switch remain in place; top-ups never bypass them. System calls with user ID zero retain environment/org enforcement and have no invented paid account.

Current-period counters initialise once from recorded successful usage and any higher legacy enforcement counter. Later paid usage does not reseed an existing included counter. Reads distinguish actual included spend from pending reservations and from total logged usage. A failed read refuses the call and shows Unreadable, not zero. Pending holds expire after five minutes and are released on the account's next read/run, against their original UTC periods. Unexpected provider usage above its reservation preserves a review hold and makes the budget unreadable; it is not silently capped or refunded. An operator must investigate such a provider contract mismatch before reconciling that hold.

Costs remain estimates based on the existing model price table and returned token usage. The existing streaming path forwards the response without reading its completion tokens, so its receipt still estimates prompt usage only; this change does not claim to measure an unseen completion or a provider invoice.

### Checkout and confirmed payment

Add tokens opens the existing `/checkout?ai_topup=1` flow and adds the configured catalog line once, preserving other cart items. The Worker prices it from the catalog, allocates any mixed-cart promo discount proportionally with conservative integer rounding, and persists the credit quote alongside the payment intent before returning its client secret. VAT does not buy credits. A completely discounted top-up grants no paid balance.

Only the verified `payment_intent.succeeded` webhook credits the account. It checks the persisted intent ID, user, order reference, currency, succeeded state and exact amount received. A unique payment ledger record, balance increase, purchase confirmation and webhook actor audit commit together. Audit failure rolls back and retries. Changing the configured price later does not rewrite a historical purchase quote. Checkout confirmation and general order fulfilment never credit AI balance. A previously fulfilled order can still receive its once-only webhook credit. The legacy unsigned local-development webhook cannot mint paid AI credit.

Paid top-ups never expire. There is no transfer, bounty conversion or client-controlled balance write. The owner has not requested a refund-to-balance policy; existing payment refund governance remains separate and a refund policy needs an explicit owner decision before automatic AI-balance adjustments are added.

### Read surfaces and deployment

The existing Worker/Assist rails show licence allowance/spend, available top-up balance, labelled holds and Add tokens. Raw usage remains a separate estimate, because it includes paid runs. Loading hides stale figures; budget failure removes figures/action; product failure preserves the known budget but removes the action. The existing rail/canvas usage area and existing checkout supply the layout; no new purchase screen is invented.

Apply migration 419 before the Worker, build the frontend, and configure the owner's existing product price.
