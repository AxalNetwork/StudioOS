## D5153 — Meeting bot: a runtime startup failure keeps its code, its stage and its time (#5153)

- **Status:** built (this PR). The live check after deploy is the owner's: rollout step 6.
- **Builds on:** D886 (B1 run supervisor, B8 container host), D1368 (`failure_detail`), #3708 (the staged diagnostic, which already had the specific codes), #4857.
- **Why:** production session 54 (2026-11-09, Google Meet) failed in about 25 s with `failure_code = runtime_unavailable`, `failure_detail = null` and no events. Workers observability showed `/init` taking 25.7 s and 31.6 s, and no runtime callback. The run never reached Google Meet. The member was told the link may have changed or the platform may block outside participants, and HQ had nothing but an aggregate count of `runtime_unavailable`.

### What changed

1. **The container host answers `/start` with a startup fact.** Every reply is
   `{ok, code, stage, runtime_version}`. The run path stops at one of these
   boundaries (`meeting-bot/worker/container.ts`):

   | Code | Stage | When |
   |---|---|---|
   | `image_unavailable` | `image_resolved` | The container has no runtime image. |
   | `container_start_failed` | `container_starting` | `container.start()` threw, or the binding has no container. |
   | `runtime_no_answer` | `runtime_port_waiting` | Port 8080 never answered `/healthz` within `HOST_READY_MS`. |
   | `runtime_process_exited` | `runtime_port_waiting` (or `runtime_command_accepted`) | The process ended while booting (`monitor()` resolved). |
   | `runtime_health_failed` | `runtime_health_ready` | `/healthz` answered but was not ready, or reported a different build than the host. |
   | `runtime_refused` | `runtime_command_accepted` | The runtime answered the signed `/start` with a refusal. |
   | `runtime_command_timeout` | `runtime_command_accepted` | The runtime was healthy but did not answer the command in time. |

   On the site Worker, a missing `MEETING_BOT_CONTAINER` binding is `binding_missing`. A transport that never answers is `runtime_command_timeout`. A host that answers `runtime_lost` keeps that code. Both vocabularies are closed (`services/meetingBotStartup.ts`); nothing else crosses the boundary.

2. **Readiness preflight.** Before the signed command, the host polls the runtime's `GET /healthz` (unauthenticated, private port, never given the meeting link) until it answers `ready: true`. The runtime now echoes `MEETING_BOT_VERSION`, which the host passes into the container. A reported version that differs from the host's own is `runtime_health_failed`. An older image that reports no version still starts.

3. **`joining` means the runtime accepted the command.** `MeetingBotRun` keeps the run `queued` while the runtime starts, records `dispatch_accepted`, and moves to `joining` only after `runtime_command_accepted`. On a startup failure it records the exact code and stage. It **releases every held minute** (the blocks settle at their own start, 0 minutes) and fails the run with the member-facing `runtime_unavailable`, unchanged for compatibility.

4. **Operator facts on the row** (migration `202611090953_meeting_bot_runtime_startup.sql`): `runtime_stage`, `runtime_stage_at`, `runtime_version`, `runtime_error_code`, `runtime_callback_seen_at` (the first signed callback: event, Zoom or Meet credentials, recorded once) and `runtime_start_ms`. Codes and numbers only. A database before the migration keeps working: each write is best-effort on a missing column, as D1368's was.

5. **The member's copy.** The founder's bot read gains `failure_category: 'infrastructure'`. It is set when a failed run's runtime never called back and the code is `runtime_unavailable` or `heartbeat_timeout`, or a startup code is recorded. In that case the panel says the recording service did not start and the meeting was not contacted. The failure panel lists no provider cause ("link changed", "outside participants"). Operator codes, stages and versions are not in the founder's read.

6. **HQ · Meeting bots** lists the last 20 failed runs in 30 days (`recent_failures` on `GET /api/admin/platform/meeting-bots`). Each row shows the platform, stage, failure code, startup code, D1368 detail, whether the runtime reported, its version, the startup time, the elapsed time and a next step. It never shows the link, names, roster, transcript or provider text. The staged diagnostic's last-run row also carries `runtime_stage`, `runtime_error_code` and `runtime_callback`.

7. **Observability.** The host logs one `meeting_bot.runtime_stage` line per transition, with only `run_uid`, `platform`, `stage`, `runtime_version`, `elapsed_ms`, `result` and `error_code`.

### Time budgets

Session 54's run gave a cold image 20 s for port 8080 and 25 s in all. A cold `standard-2` instance with Chromium and the Zoom SDK needs longer. The budgets now nest, outermost last:

| Constant | Value |
|---|---|
| `HOST_READY_MS` (port and health) | 40 s |
| `HOST_COMMAND_MS` | 10 s |
| `TRANSPORT_START_MS` | 53 s |
| `RUN_START_MS` | 55 s |

Each layer outlasts the one inside it, so the inner layer answers with a code instead of being cut off. `runtime_start_ms` on every run is the measurement to tune these against. The trade-off: while a cold start runs, the run's object is busy for up to 55 s (it was 25 s), so a Stop pressed then is answered when the start ends. The container host's Stop tombstone is unchanged and still wins.

### Rollout

1. Apply the migration (the deploy's `predeploy` does).
2. Deploy the meeting-bot Worker (host and image) and the site Worker. The site reads both old and new host replies; an old reply maps to plain `runtime_unavailable`.
3. Keep `MEETING_BOT=canary`.
4. Run the HQ staged diagnostic.
5. **Owner:** run one Google Meet canary. HQ · Meeting bots then shows either a startup code and stage, or `runtime_command_accepted` with the runtime's version and first callback, followed by `recording → processing → done`.
6. Only then rerun the full recording and transcription check (#3588).

### Not done

- The live canary (rollout step 5) needs a deployed build and the owner's meeting.
- A run whose host crashes mid-reply still reads as plain `runtime_unavailable`, with `dispatch_accepted` as its last stage and no code. HQ says so and points at the staged diagnostic.
