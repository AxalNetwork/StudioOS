## D925 — Partner deal writes, paid-plan preservation and retryable activation

Issue #2721, part 2 of #2370. D923's canvas and dated code map identify the
misleading terminate/revoke replies and the lost activation after signing.
O-TIER and O-WIN are unchanged: this does not rename granted plans or change
rev-share windows. No canvas screens are added in this Worker task.

### Terminate and revoke

Terminate snapshots the grant, then claims the transition with one conditional
`UPDATE ... WHERE status = 'active'`. Zero changed rows answers 409, including
when two requests read the same active snapshot. Only the winner cascades and
records the admin action.

The reply replaces `tiers_revoked` and `redemptions_revoked` with:

- `members_revoked`: distinct redeemers with at least one changed tier row;
- `partner_tiers_reverted`: whether either guarded partner update changed a row;
- `failures`: safe operation names and, where useful, affected row IDs. These
  cover partner revokes, the redeemer read and individual grant updates. An
  update failure does not abandon later tiers or later members.

Revoke returns its cascade failures alongside actual void counts. Empty arrays
mean success, not a swallowed database failure. The primary invitation revoke
still blocks activation when a downstream void fails. Exception messages are
never returned. Both operations include their outcomes in the actor's audit.

### Activation and migration 548

`548_partner_deal_activation_error.sql` adds nullable `activation_error` and
`activation_failed_at` (ISO UTC), plus two default-zero preservation flags:
`activation_preserved_founder` and `activation_preserved_investor`.

Activation keeps a founder's growth/studio plan or investor's
professional/institutional plan whenever its source is not a partner grant,
referral, revoked grant or expired grant. This is deliberately conservative:
Stripe status, renewal timestamps, subscription IDs and quota remain intact,
including paid plans in a billing recovery state. A paid-tier name alone with
an unknown source is preserved rather than overwritten. Founder and investor
families are guarded separately, at the SQL write, not just by an earlier read.
The deal records which paid families were preserved; its contracted grant tier
names are not rewritten. Free accounts still receive the agreed grants.

The preservation record, tier grants, signed invitation and conditional active
transition execute in one D1 batch transaction. A failed grant rolls back the
whole batch. Retried or concurrent activations cannot renew an active deal or
repeat its activation notification/audit. User lookup/creation and referral-code
reservation before this batch are reusable on retry; existing roles are kept.
Post-activation optional DD, Trust, profile-link and notification work retains
its existing best-effort policy.

The activator and e-sign completion failure path persist the fixed safe marker
`activation_failed` and its time on the awaiting deal. A signature remains
completed when activation fails. Raw SQL/provider exception text is not stored.
A failure to persist the marker is logged without leaking that exception.

`POST /api/admin/partners/deals/:id/activate` is admin-only. It requires the deal
to await signature/activation and its own linked envelope to be completed;
otherwise it answers 409. A repeated request after success also answers 409 and
changes nothing. Failed retries answer 503, retain the marker and are audited;
success clears both error fields and audits the actor. The matching client is
`api.adminPartners.activateDeal`. No automatic retry or new UI is added here.

### Reads and licence freeze

The deal list includes the activation marker, its time, the preservation flags,
and `terminated_by_name`, left-joined on `terminated_by_user_id`. The redemption
read retains its 500-row page and `redemptions_count`, and separately returns
uncapped `redemptions_total` and `truncated`.

Every admin partner write (create, resend, revoke, terminate, activate, firm
link and directory decision) calls the existing branch suspension gate, just as
Events does. The existing `branchFreeze.js` registry also names these writes, so
the branch's Locked screen describes the enforced gate. A suspended branch gets 423 `branch_suspended`; reads remain open
to the same admins. No production data or applied migration is changed.
