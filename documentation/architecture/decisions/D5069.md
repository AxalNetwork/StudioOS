## D5069 — Atomic Investor Narrative saves and stale-write protection (#5069)

- **Status:** Built, 2026-11-08 (Worker, two migrations, frontend).
- **Migrations:** `202611082100_narrative_version_revision.sql` adds `narrative_version_meta.revision` and `.claim`; `202611082130_uof_scenario_revision.sql` adds `uof_scenarios.revision`.
- **Builds on:** D908 (the Narrative stores), D913 (objection answers), D1176 (Use of Funds scenarios), D1025 (cap table scenarios).

### What was wrong

Three places let the later save replace the earlier one without saying so.

1. **Save version** (Investor narrative › Story) was a loop of one write per section, then one write per accepted objection answer. A failure on the third section left the first two saved, and the answer metadata was a second phase that could fail on its own.
2. **Cap table scenarios.** `PUT /api/captable/scenarios/:uid` took no revision. Two tabs that read the same scenario ended with the second tab's inputs.
3. **Use of Funds.** The store was transactional, but a scenario, split or milestone write never compared the revision the person had read.

### What it does now

**One answer for a stale write.** `409` with `error: 'changed_since_open'`, a sentence ("This … was changed somewhere else after you opened it. Nothing of yours was saved. Review the latest, then make your change again."), and `current_revision`. A write that sends no revision is `400 expected_revision_required` on the Cap table and Use of Funds routes. Nothing is written in either case.

**Narrative.** `PUT /api/cycles/raise/narrative/:version` takes `{ sections: [{ section, …fields }], answers: [{ objection, section, how }], expected_revision }` and writes all of it in one batch, or none of it. The batch is:

1. make sure the version's meta row exists;
2. claim the next revision — `UPDATE … SET revision = revision + 1, claim = ? WHERE revision = expected` — where `claim` is a fresh UUID for this save;
3. every other statement (section rows, deck words, bindings, `why_now`, answers) carries `WHERE EXISTS (… revision = expected + 1 AND claim = ?)`.

A save that lost the claim matches nothing at step 3 and the route answers 409 from step 2's `changes = 0`. The claim token is needed because the revision number alone is not unique to one save: a competing writer who reaches `expected + 1` first would otherwise let this save's guarded statements through (found by the race test; the first version of the guard used the number alone). A statement that errors rolls the whole batch back, because D1 runs a batch as one transaction. `PUT /narrative/:version/sections/:section` takes the same `expected_revision` (optional there, so existing callers keep working) and spends a revision too. `GET /narrative/:version` returns `meta.revision`.

**Cap table.** The revision is the scenario's `updated_at`, which every write to the row already replaced (`saveScenario`, `safeBasisRepair`). `saveScenario` writes with `UPDATE … WHERE uid = ? AND updated_at = ?` and treats `changes = 0` as the conflict; a save in the same millisecond as the one it replaces takes the next millisecond, so a revision is never reused. The scenario response carries `revision`. No migration. The POST path and the Raise holder writers do not pass a revision and keep their behaviour.

**Use of Funds.** `uof_scenarios.revision` goes up by one on a scenario edit, a split save, a milestone write and a make-base. Each write's batch starts with two statements: one that aborts the batch (`abs()` of the smallest integer is an integer overflow, which D1 reports as an error and rolls back) when the scenario's revision is not the one read, and one that takes the next revision. Everything the batch writes after that is therefore all-or-nothing. A plain read before the batch gives the same refusal without the abort on the ordinary path. The scenario PATCH, the Base split `PUT /api/cycles/raise/use-of-funds`, and milestone POST/PATCH take `expected_revision` in the body; milestone DELETE takes it as `?expected_revision=` because a DELETE has no body. Milestone responses carry `scenario_revision`; the split response carries `revision`. The Raise writer path that calls `saveSplit` without a revision still took a revision (so a reader's editor goes stale) but checked none; D5375 closes it.

**Frontend.**

- Story's Save version is one `narrativeApi.saveVersion` call (`saveBody` builds it: the changed sections, the answers whose section is among them, `expected_revision`). On a 409 the dialog says why, the text stays in the editor, and the accepted "Answer it" drafts stay pending.
- The cap table scenario page sends `expected_revision` from every update (save, rename, attach read, Compare's attach). On a 409 the person's inputs stay on the page, with **Review latest** (reads the scenario again) and **Copy my inputs**.
- Use of Funds' Edit split, Add milestone, Choose the round size and Edit scenario dialogs send the revision; on a 409 the dialog stays open with the sentence and **Review latest**, which closes it and reads the plan again.

### Tests

- Narrative: whole-version save (sections and answers together, one revision), a failing statement leaves nothing (SQLite trigger), serial stale 409, stale single-section 409, a save that loses the race between its check and its batch (writes nothing — fails without the claim token), refusals.
- Cap table: two tabs read revision N; A saves; B's save with N gets 409 and changes and logs nothing; the lost-race case.
- Use of Funds: scenario, split and milestone (including DELETE) stale 409; a write between the read and the batch aborts the whole batch (no line, name or audit row stays).
- Frontend: the one request and its body, the conflict dialogs, and `saveBody`/`saveFailure` alone.

### The abort on D1 (checked under D5375, #5375)

PR #5100 tested the `SELECT abs(-9223372036854775807 - 1) WHERE NOT EXISTS (…)` abort on SQLite only. D5375 ran it once on the local D1 simulator.

- **What ran.** wrangler 4.156.1's `getPlatformProxy` (workerd's D1 implementation, an in-memory database, no remote binding, no production data) gave a real `D1Database` binding. One `db.batch([abort, UPDATE … SET revision = revision + 1 WHERE revision = ?, UPDATE …, INSERT audit])` ran twice against a table at revision 5.
- **Matching revision (5).** The batch committed: four statements, revision 6, the update and the audit row written.
- **Stale revision (5 again, the row now at 6).** The batch threw `D1_ERROR: integer overflow: SQLITE_ERROR`, and the table read back as it was before the batch: revision 6, the earlier name, one audit row (the first batch's). Nothing of the aborted batch remained. The statement alone also throws `integer overflow: SQLITE_ERROR`.
- **Consequence.** `planBatch` matches `/integer overflow/i` on the error message, and the message D1 raises contains exactly that. The abort works as D5069 assumed, on the simulator.
- **Not run: hosted D1.** Hosted D1 needs a Cloudflare account and credentials this work does not hold, and the issue allows neither production data nor a write to production. The simulator and hosted D1 share the SQLite engine and the batch-as-transaction contract, but the hosted run is still unobserved. Anyone with a rehearsal database can repeat it with the four statements above; if it does not abort there, the fallback is the one D5375 uses for hires: put `AND revision = ?` on every later statement, as the Narrative store does.
