## D9202 — Request telemetry writes to D1 only what a reader needs (#9202)

- **Status:** built by S26 on #9202, 2026-11-27.
- **Chosen by:** the issue's scope (S1, coordinator audit 2026-11-27), which left the `activity_logs` rule to the builder; the choice and why are below.

### The problem

Every metered `/api` request ran three D1 statements in `middleware/observability.ts` after the response went out: an `INSERT INTO system_metrics`, a `SELECT plan FROM mi_pro_subscriptions` for the Analytics Engine tier label (on every signed-in request, because `ANALYTICS` is bound in production), and an `INSERT INTO activity_logs`. D1 runs writes one at a time, so the two inserts queued behind the real writes on `studioos-db`.

### What changed

1. **`system_metrics` 'request' rows are sampled.** Analytics Engine already records every request. The D1 rows still have readers, though: the monitoring dashboard (`/api/monitoring/metrics`, the anomaly read, `/throughput`) and the analytics reports (`loadOverview`, plus the `loadTechnical` fallback when Analytics Engine cannot be read). So the insert is sampled, not removed:
   - **Rate: one in 10** (`REQUEST_METRIC_SAMPLE_EVERY`). A kept row stores `value = 10`, which is the number of requests it stands for.
   - **Every 5xx and every 429 is kept at `value = 1`.** These rows are rare, and they are what the health figure and the rate-limited count are built from.
   - **Readers count `SUM(value)`, not `COUNT(*)`.** They weight averages by `value`, and percentiles too (`weightedPercentile`). Rows written before this change have `value = 1`, so they read the same as before. With every weight at 1, the weighted percentile gives exactly the old `arr[floor(n × p)]`.
2. **The tier label comes from what auth already loaded.** `resolveCurrentUser` already sets `mi_subscription_plan` on the request's user from `mi_pro_subscriptions`, once per request. The middleware reads that field. It used to run the same `SELECT plan` again. There is no cache and no TTL, and the label has the same value as before: the plan, whatever its status, and `free` when there is none.
3. **`activity_logs`: at most one row per account per endpoint per UTC minute for a read (GET/HEAD). A write (any other method) is logged every time.** This is option (b) of the issue, applied to reads only. Option (a), logging non-GET requests only, was ruled out:
   - **Weekly actives would change their definition.** The branch's line (`loadBranchWeeklyActives`), the benchmark week (`activeAccountsInWeek`) and the admin insights (weekly, by country, retention) all count distinct accounts with any logged request. An account that only reads would drop out, and the branch figure would stop matching HQ's Analytics Engine predicate (`aeLoggedRequestPredicate`), which counts every method. `ACTIVE_ACCOUNT_BASIS` would then be false.
   - **The reports would lose read-only days.** `loadOverview`'s active users, DAU and session hours read every account with a row in the day or hour.

   Writes are kept whole because the Stripe webhook is a POST from no account. Its delivery count, refusal count, newest success and failure, and failure streak (`readWebhookDeliveries`, `platformHealth`) read one row per delivery. A minute key would merge several deliveries into one row.

   The minute buckets fit inside every bucket a reader uses: an hour, a day, a Monday-to-Sunday week, the first logged day, the newest request. So each of those readers still sees every account in every bucket it was active in.

   The key is held per isolate (`Map` of key → minute, cleared once it reaches 10,000 keys). Two isolates can each write a row for the same minute, and a cleared map can write one extra row per key. The guarantee is a bound on writes, not a uniqueness constraint. No reader needs uniqueness.

### What a reader now sees differently

- **`/api/activity` (your own feed and its totals)** lists fewer repeated `http_get` rows: at most one per endpoint per minute. That is the intended reduction.
- **Raw row counts of `system_metrics` 'request'** are no longer request counts. Every reader in the repo now uses `SUM(value)`, and a new reader must do the same.

### Out of scope

- The KV write in `middleware/rateLimit.ts` `bumpCounter` (PR-7's task). `rateLimit.ts` is also edited by #9169, so it is not touched here.
- How long the tables grow: PR #9140 (for #9033) prunes `system_metrics` and the other log tables.

### Tests

`cloudflare-worker/test/telemetry_writes_9202.test.ts` sends a signed-in GET twice through the middleware against a counting D1 fake and asserts:
- no `mi_pro_subscriptions` read;
- no `system_metrics` insert on an unsampled draw;
- one `activity_logs` row;
- an Analytics Engine data point that carries the tier for each request.

The same file holds each reader to the rows it needs:
- weekly actives, the week count and the first logged day, over rows the middleware wrote;
- the Stripe webhook delivery count;
- the `loadTechnical` D1 fallback;
- the `/metrics` and `/throughput` monitoring routes over sampled rows.

`ae_branch_dimension_d161.test.ts` now pins the draw so its "D1 still records the request" assertion holds.
