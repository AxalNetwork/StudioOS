### 1. The rule

A release whose manifest pins a **render** cannot be approved (a `publish` or a `render` decision of `approve`) or
published unless #5586's swarm admission admitted the run that wrote it, and that run settled at a measured cost
within the reserve admission held for it. That is the requirement `render_admitted`. A refusal is
`render_unadmitted`, with the pinned piece's asset, revision, reason and, where there is one, #5586's own code.

**What a render is.** A pinned revision that an agent run wrote (`actor_kind = 'agent'`, so `agent_run_id` is set by
#5581's check constraint), where:

| Asset kind | Media profile | Modality (#5586's vocabulary) |
|---|---|---|
| `video` | any | `video_render` |
| `image`, `brand` | `image/*` | `brand_image` |

Everything else is not a render and is untouched: a person's upload spent no swarm budget, and a `brand` revision with
a non-image profile is a brand-token record (D5583 `brandKitUnits`), not an image. #5586 has no 3D or audio modality,
so `model_3d` and `audio` are not renders here.

**How a render finds its admission.** A swarm ticket's uid is the agent run (D5586: a lease-lane ticket takes #5570's
lease under the ticket's uid, and `readApprovals` joins approvals to tickets by `agent_run_id`). So the pinned
revision's `agent_run_id` is the ticket uid. Only a ticket of the revision's own tenant and company counts.

### 2. Why it is a requirement in the evaluation, not a gate at publish only

Every existing condition a manifest must meet is computed by `evaluate` and shown on `releaseStatus`: staleness,
attestations (`missingAttestations`), approvals (`missingApprovals`), changes requested, takedowns. `publishRelease`
then refuses on the first one that fails, from that same evaluation. A render's admission is one more such condition,
so it follows the same shape: `evaluate` computes `ComponentState.render` per piece and `ReleaseState.renderGaps` per
manifest, and `publishRelease` refuses `render_unadmitted` from it (after `attestation_missing`, before
`changes_requested`). A reviewer and a Super Admin see why on the status read before anyone tries to publish, which a
publish-only gate would hide.

It is **not** a new entry in `REQUIREMENTS`. Those are attested by a person or a CI run through `attestComponent`,
with an evidence ref. A render's admission is not something anyone attests: it is read from #5586's record. Listing it
there would let a person with an authority attest `render_admitted` by hand and so bypass the budget.

**Approval.** "Cannot be approved" is enforced in `decideRelease` itself: an `approve` of either purpose is refused
`render_unadmitted` while a gap exists. `reject`, `request_changes` and `withdraw` are never blocked, since they
authorize nothing. Approvals recorded while the render was admitted still have to pass the publish check, which reads
the swarm state again, so a release whose admission can no longer be read does not go out.

### 3. The reasons

The first that applies, per pinned render:

| Reason | When | `admissionCode` |
|---|---|---|
| `admission_unverified` | the caller passed no swarm state, or a malformed one: nothing was read | null |
| `not_admitted` | this venture's swarm holds no ticket and no refusal for the run | null |
| `refused` | admission refused the run's request | #5586's code: `no_capacity`, `budget_exhausted`, `storage_quota_exhausted`, `wrong_tenant`… |
| `other_modality` | the run's ticket was for another modality | null |
| `other_revision` | the ticket was for another asset, or for another base than the revision's parent (a stale admission) | null |
| `waiting` | still queued | its `wait_reason`: `venture_capacity`, `modality_capacity`, `budget_exhausted`… |
| `withdrawn` | ended without running | its `end_code`: `withdrawn`, `agent_revoked` |
| `not_settled` | admitted, still running: its cost is not known | null |
| `cost_unknown` | settled without metrics, so charged its reserve (`costEntriesFromTickets` basis `reserve`) | null |
| `over_budget` | settled above the reserve admission held against the venture's render budget | null |

**Unknown cost is never approved.** A ticket settled without metrics is charged its reserve, which is an upper bound,
not a measured cost. The read model already counts it as `estimated_microusd`, never as measured. Here it is a gap.

**Within budget.** Admission checks that a ticket's reserve fits the venture's render budget (`budgetCommitted +
reserve ≤ render_budget_microusd`). A measured charge can exceed the reserve, because #5570 bills what the provider
measured. A charge at or below the reserve stayed inside the room admission granted, and a charge above it did not
(`over_budget`). This is a property of the ticket alone, so a later render elsewhere in the venture cannot make an
approved release unpublishable.

**Stale admission.** A ticket names the asset and the base revision it was admitted on (`asset_uid`,
`base_revision_uid`). The pinned revision must be of that asset and built on that base: its `parent_uids_json` holds
the base, or is empty when the base is null. A ticket admitted on a head that then moved is `other_revision`, and so is
one for another asset. Another run's settled ticket does not cover a revision this run wrote (`not_admitted`).

### 4. No second ledger, no migration

- **The record is #5586's.** The caller passes `SwarmAdmission.snapshot()` as `ReleaseContext.renderAdmissions`.
  `renderAdmissionOf` reads its `tickets` and `audit` (for a refused request, which leaves no ticket). Nothing is
  copied or stored.
- **The cost basis is the read model's.** `costEntriesFromTickets` decides measured against reserve, so this part and
  the capacity read model cannot disagree about what was measured.
- **No extra D1 read.** `readComponents` now selects four more columns of `work_graph_revisions` (`actor_kind`,
  `agent_run_id`, `parent_uids_json`, `media_profile`). `evaluate` already ran that statement. `decideRelease` reads it
  once more, only for an `approve` of a manifest that pins a `video`, `image` or `brand` piece. A manifest with none
  costs nothing more.
- **No migration.** Every fact needed is already a column, or #5586's state.

### 5. Cross-tenant

The swarm state holds every venture's tickets, since one coordinator serves them all. A ticket or a refusal counts
only when its `ventureKey` is the pinned revision's tenant and company. Another venture's record under the same run
uid is treated as absent (`not_admitted`): it never satisfies the requirement, and its charge is never shown. A caller
of another scope is refused `wrong_tenant` before anything is evaluated, as before.

### 6. Routes, preview-only

No route changed. The admin context (`releaseAdminContext`) and the reviewer context (`reviewerContext`) both ask
`RELEASE_ADMIN_DEPS.renderAdmissions(env, scope)`. No binding reaches the swarm's Durable Object yet (#5586 part 1 is
unmounted), so it answers `null`. Behind `WORK_GRAPH_RELEASE_ADMIN=on`, then:

- `GET …/manifests/:manifest` and `GET …/lines/:line` show `release.renderGaps` with `admission_unverified`;
- an approval and a publication of a manifest that pins a render are refused `render_unadmitted` (409, with its
  sentence in `RELEASE_REFUSAL_SENTENCES`).

That fails closed. A manifest that pins no render behaves exactly as before. Wiring the resolver to the swarm's store
is the step that needs a binding, and so the owner's approval (§8).

### 7. Tests

`work_graph_release_renders_5585.test.ts` runs the real release services over part 2's SQLite world, and #5586's real
swarm admission over #5570's real admission control.

1. Admitted and settled within its reserve: approvable (publish and render purposes) and publishable; the evaluation
   shows the charge and the reserve.
2. No swarm state: `admission_unverified`; approval refused for both purposes; `request_changes` still recorded;
   approvals recorded while admitted cannot publish without the state; the refusal is an audited `advance_refused` row,
   and no effect is queued.
3. Not admitted; refused by admission (`budget_exhausted`, `no_capacity`); waiting (`modality_capacity`); not settled;
   withdrawn.
4. Unknown cost (`cost_unknown`) and over budget (`over_budget`) are refused and record no decision; a charge exactly
   at the reserve is within it.
5. Cross-tenant: tenant 8's settled tickets and its refusal under the same run uids never satisfy tenant 7, and their
   charges are not shown; tenant 8 reading tenant 7's manifest is `wrong_tenant`.
6. Stale admission: another base, another asset, another modality, another run.
7. Regression: a person's video upload, a brand-token record, an agent image with a non-image profile and code are not
   renders, with or without swarm state, and publish as before.
8. The pure rule: what a render is, malformed swarm state, distinct reasons, the refusal sentence.
9. The admin context: `renderAdmissions` is null by default; a resolver feeds the same evaluation.

### 8. Left for later parts

- **Wire the swarm state.** A resolver for `RELEASE_ADMIN_DEPS.renderAdmissions` that reads the swarm coordinator's
  Durable Object needs a binding, which #5586 part 1 left for the owner. Until then every release that pins a render is
  refused in preview, which is the safe default.
- **Render approvals before rendering.** This part ties a `render` approval to a render that has already settled. An
  approval that authorizes the spend *before* the render (feeding #5586's admission) is a separate flow and is not
  built.

### 9. Rollback

Revert the commit. `readComponents` loses four columns no other caller reads. `ReleaseState` loses `renderGaps`, and
`ComponentState` loses `render`. No data was written by this part, so nothing needs cleaning up.
