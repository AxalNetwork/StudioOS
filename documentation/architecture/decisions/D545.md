## D545 — The community task list's API, for the Eadwyn chat's Tasks panel

**`GET /api/community-tasks` gives a signed-in user the approved community
tasks for their persona and for everyone, and their own suggestions with
their review state; a read that fails is a refusal, never an empty list.**
Issue #1108, slot S08, part of #1101. No migration: the store is D544's
`community_tasks` (migration 383). This entry covers the API; the Tasks panel
in `PersonalAdvisor.jsx` waits on its design (`needs-design`). **D606 builds the
panel** to the owner's Eadwyn Tickets canvas.

**What changed.**
- **`routes/community_tasks.ts`**, mounted at `/api/community-tasks`. It
  returns:
  - `tasks`: approved tasks whose audience is `all` or the caller's persona,
    newest first.
    - The persona follows D544's audiences: `founder`, `investor`, `advisor`
      and `partner` as themselves, and `exploring` as `explorer`.
    - Any other account (an `lp`, for one) sees only the tasks for `all`.
    - An admin, who reviews them, sees every approved task.
  - `my_suggestions`: the caller's own suggested tasks, with their state
    (`pending`, `approved` or `declined`). The decline reason is sent on a
    decline only.
  - `audience`: what the list was filtered by.

  "No tasks yet" is an empty list. A failed read is a 500
  `community_tasks_unreadable` with no list on it, so the panel can say
  "Unreadable".
- **`frontend/src/lib/api/communityTasks.js`** (D527) exports
  `communityTasksApi.list()`, re-exported by one line in `api.js`'s module
  block.

**Not built here.** The chat's Tasks panel, with its "No tasks yet" and
"Unreadable" states and the "Suggest a task" button that opens the ticket form
with Type = Task, waits on the canvas whose prompt is on #1107.

**Verified.**
- `cloudflare-worker/test/community_tasks_d545.test.ts` (5 tests) runs the
  real router over migration 383, its triggers writing the rows. It covers:
  - the persona filter, and the `all` audience;
  - `exploring` reading `explorer`;
  - the admin's whole list;
  - newest first;
  - only the caller's own suggestions, with the reason on a decline only;
  - empty against unreadable, for each of the two reads;
  - a signed-out refusal.
- `frontend/test/community_tasks_api_d545.test.mjs` checks that the client
  GETs `/api/community-tasks`.
- Mutations: 10 run, 10 caught. Each file was restored and checked by sha256.

**After review.** Codex found two problems.
- **The all-audience view belonged to a role, not to the reviewer.** Any
  `admin` read every persona's tasks. D544's review routes are
  `requireSuperAdmin`, so the bypass is now `isSuperAdmin(user)`. A plain
  admin reads only the tasks for `all`, and their `audience` is `all`.
- **Suggestion history stopped at 100 with no sign of more.** It is now a
  cursor:
  - the list is newest first by id, 100 a page;
  - one extra row is fetched to tell whether there is another page;
  - `my_suggestions_next` names the `suggestions_before` value for that
    page, or is null on the last page;
  - a cursor that is not a positive integer is a 400 `bad_cursor`.

  `communityTasksApi.list(suggestionsBefore)` passes it.

The route test now has 6 tests. The admin test is split into a Super Admin
and a plain admin, and a paging test walks 101 suggestions, an exact 100 and
four bad cursors. Both fail on the code before review. The client test checks
the cursor URL. 9 of 9 mutations were caught:
- the bypass on role;
- no bypass;
- a 100-row fetch;
- `<=`;
- no cursor filter;
- `>=` on the page check;
- no slice;
- a looser cursor check;
- the wrong cursor row.
