## D4664 — Email: each profile's People, Stop sharing, and an unknown share is unknown (#4664)

### Decision

Email audit package 5 of 6, findings 8 to 10, rechecked on `main` at
`0c5e2de666`. All three still held on `/email`. Finding 10 had already been
fixed in `RecordEmailSheet` by #4740. The Worker already had everything this
needed: `GET /api/mail/people` (D1348), `GET /api/mail/shares` and
`DELETE /api/mail/shares/:uid` (D1342). So this PR changes the frontend
only. No route, access rule, client method or migration changes.

1. **People is the profile's own read (finding 8).**
   - `EmailHome` calls `mailApi.people()`. It no longer calls the founder-only
     `founderPeople()`.
   - `peoplePane` in `emailModel.js` draws the member's recent drafts first,
     as their own section ("Your drafts"). The server's groups follow, in the
     order it returns them.
   - The drafts never stand in for the profile's read.
   - Each row shows what the Worker returned: the role, the source label,
     the last contact day and the derived marker ("Follow-up due"). Nothing
     is computed on the page.
2. **Each group keeps its own state.**
   - A group with rows is `ready`. A group with none says its own `empty`
     line. A group the Worker could not read says its own `error`, with
     Retry. It is never drawn as empty.
   - A failed group leaves the healthy groups as they were read.
   - The Worker answers all of a profile's groups in one response, so there
     is no separate loading state for one group. While the read is pending,
     the pane says "Reading the people you work with…".
   - If the whole read fails, the pane says it is Unreadable and offers
     Retry. The recent drafts stay.
3. **"No people yet" is true, and it belongs to the profile.**
   - It is shown only when the read answered, no group failed, and nobody
     (no draft, no group row) is there.
   - Its line and its door come from `noPeopleState(profile)`:
     - founder: Customer research, as before;
     - investor and partner: Network;
     - advisor: their clients;
     - admin: Spin-Out Lab applications;
     - explorer: no door, because `/network` does not admit them.
   - The profile note the Worker returns is drawn under the pane. So is the
     right pane's prompt when the Worker gives one (the explorer's).
4. **The shares read keeps its state apart from its data (finding 10).**
   - `EmailHome` holds `{ status: 'reading' | 'ready' | 'unreadable', items }`.
     A failed read is `unreadable`. It is never `{ items: [] }`.
   - `shareStatus` decides what the page may say about one match. Only a
     read that answered decides anything.
   - While the read is pending or after it failed, the thread says "Address
     not verified: sharing could not be read". The page shows no address and
     no composer, and the card offers Try again.
   - Try again re-reads the shares only. The selected person stays in the URL
     and their records are not read again.
   - A known match stays in People because that list comes from the People
     read, not the shares read.
   - A refresh after a write keeps what it read until the new answer arrives.
     If the refresh fails, it forgets that answer, so no unverified address
     stays on screen.
   - A real empty answer is still "Address not shared yet".
5. **Stop sharing (finding 9).**
   - The Network card is drawn in all four states: matched, waiting, ready,
     and could not be read.
   - In waiting and ready it offers Stop sharing. The steps are:
     - **Scope**: the card.
     - **Review**: a confirmation that says what is true now, what stops (they
       no longer see your address, and Email closes until you both share
       again) and what stays (emails already sent).
     - **Result**: a line, drawn only once `DELETE /api/mail/shares/:uid` has
       answered.
   - "Keep sharing" writes nothing.
   - Confirming calls the existing `unshare` once. A ref guard and the
     disabled button stop a second press while it is pending.
   - The share the Worker returns is drawn at once, and the list is read
     again. The address and the composer close with it.
   - A failed revoke says "Sharing did not stop… Nothing changed. Try again."
     It keeps the confirmation open and never draws the result line.
6. **`RecordEmailSheet`.**
   - Its Unreadable state, which #4740 also uses for a failed shares read,
     gains Try again. Try again reads the same person ref again.
   - The line now ends "Try again." and no longer says "Close and try again."

### Departures

- There is no loading state per group, because the Worker returns every group
  in one response (see 2). A per-group refetch would need a new Worker
  contract, and the issue says to add one only if truly missing.
- `RecordEmailSheet` keeps #4740's generic "this person's records could not
  be read" line for a failed shares read. It does not get a sharing-specific
  line, because `network_relationships_fixes_4740.test.mjs` pins that text,
  and the line is honest: it does not claim that the member has not shared.
- `founderPeople` stays exported for its existing test. It now reuses the new
  `recentDrafts`, and the page no longer calls it.

### Tests

- `frontend/test/email_people_sharing_4664.test.mjs` mounts `EmailPage` and
  `RecordEmailSheet` against a faked mail API with synthetic records. It
  covers:
  - each of the six profiles' groups, with source, last contact and marker;
  - one failed group beside healthy ones;
  - every profile's empty state and its door;
  - a failed People read, then recovery;
  - a failed shares read, then recovery on the same person;
  - a real empty shares read;
  - Stop sharing while waiting: cancel, then confirm;
  - Stop sharing once ready: a failed revoke, then a retried confirm that
    succeeds;
  - a double press;
  - the Sheet's Try again;
  - the pure rules (`peoplePane`, `shareStatus`).
- Each new assertion was mutation-checked by breaking the code it guards and
  seeing it fail. The broken code covered:
  - swallowing the shares failure;
  - dropping server groups;
  - hiding the marker and the last contact;
  - erasing a group's error;
  - the founder door for every profile;
  - `none` on a failed read;
  - Stop sharing only while waiting;
  - cancel calling revoke;
  - a failed revoke claiming success;
  - removing the double-press guard;
  - composing on an unknown share;
  - the Sheet's retry.
