## D7259 part 2 — Group Code Scanning remediation into opaque, claimable batches (#7259)

D7259 landed the owner's Q2 C choice (fresh STATUS and open-PR handoffs hold a
tracker). This part builds the rest of #7259: the batch layer, with the
owner's Q1 A format (2026-11-20).

### Grouping

`scripts/scan-remediation/batches.mjs` keys each open Code Scanning alert by
scanner, rule ID and owning subsystem. The subsystem is the first folder, or
the first two under `backend`, `cloudflare-worker`, `frontend` and
`meeting-bot` (so `cloudflare-worker/src` and `cloudflare-worker/test` differ).
`ROOT_CAUSE_OVERRIDES` maps several rules to one shared cause, optionally across
subsystems. An alert with no readable scanner, rule or path is not grouped.

Two or more unbatched S21 trackers with one key file a batch; a single tracker
keeps the individual flow unchanged. A later compatible alert joins the open
batch instead of filing another. Membership is stable: a listed tracker never
moves, the lowest-numbered batch listing a tracker owns it, and a claimed,
assigned or otherwise held tracker never joins. Members are ordered Critical >
High > Medium > Low > not recorded, with production paths ahead of test paths,
and new batches are filed in that order, five per run.

### Public shape (Q1 A)

A batch issue is titled `[Code Scanning] Remediation batch <8-hex>` and
labelled `scan:batch` and `slot:S21`. Its body
(`scripts/lib/scanBatchIssue.mjs`) lists only member tracker numbers and their
protected alert links, open and resolved. The id is an HMAC-SHA256 of the
grouping key under `SCAN_BATCH_KEY` when that is configured, and under a
random per-run key otherwise; the key and its parts are never written or
logged. The workflow finds a batch again through its members, not its id, so
no stored key is needed.

### Claims

`scripts/claim.mjs claim <batch>` acquires `claim/<batch>` first, then one
`claim/<tracker>` ref per open member, each carrying `batch`. Every ref stays
atomic: a member another session already holds, or wins in a race, stays with
it and is reported under `heldElsewhere`. A member claim is refused (exit 3)
while an open batch listing it is held by someone else, even before that
member has its own ref. Renew takes members that joined since; release
removes only member refs this batch claim wrote, then the batch ref. Only a
batch a bot filed counts.

### Reconciliation

One PR may name the batch (`Part of #B`) and its members (`Refs #T`). The batch
moves to `state:review` with one traceability comment per PR while an open
same-repository PR to `main` names it or a member, and back to `state:ready`
when none does. A claim ref, assignee, other slot or state label, or a fresh
STATUS on the batch holds it. Batched members leave the ready queue; their
PR links and review labels work as before. Trackers still close only when
`main`'s scan reports the alert and its `main` instance fixed. The batch then
lists them as resolved, keeps the rest open, and closes as completed only when
no member tracker is open. A batch closed by a merge keyword while members are
open is reopened; a reopened alert reopens its batch. A batch a person closes
as not planned is left closed, and its trackers return to individual work.
Nothing dismisses an alert, writes code, or opens a branch or PR.

Dependabot and secret-scanning trackers stay individual: their unit of work is
already one dependency or one credential.
