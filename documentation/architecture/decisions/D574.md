## D574 — Wellbeing backend: a failed read says Unreadable, the weekly check-in, cancelling a booking, and the missing fields

Issue #1185, from Session 1's Wellbeing screens (#1174, D570). Migration 395
is reserved for this decision's columns.

### Part 1 — a failed read is not an empty one

**What was true on main (`1c547378`).** Four reads caught every failure and
answered 200 with an empty shape:

| Route | What it answered on a failure |
| --- | --- |
| `GET /api/wellbeing/checkins` | `{ checkins: [], submitted_today: false }` |
| `GET /api/wellbeing/resources` | `{ resources: [] }` |
| `GET /api/wellbeing/experts` | `{ matches: [], total_active: 0 }` |
| `GET /api/wellbeing/aggregate` | the small-cohort shape: `cohort_size: 0`, `insufficient_data: true` |

So the screens said "nothing yet" when nothing had been read. The admin pulse
said "Fewer than 5" founders: a claim about the cohort, made about a read that
failed.

**Now each one answers 503** through the shared `refuse` helper, with its own
code:
- `checkins_unreadable`
- `resources_unreadable`
- `experts_unreadable`
- `aggregate_unreadable`

The message says the read failed and that this is not a claim that the thing
is empty. The raw error is logged, never returned.

The screens already turn any thrown error into their Unreadable state, so no
screen change was needed. Only a comment on the pulse that described the old
answer was corrected.

**Tests.** `cloudflare-worker/test/wellbeing_unreadable_d574.test.ts` runs the
real router on node:sqlite. Every Wellbeing statement throws, as a D1 outage
would. It checks four things:
- each read answers 503 with its code;
- no read answers the empty shape;
- the raw text never reaches the body;
- the reads that work still answer 200, including the small-cohort shape
  when the cohort really is small.

**Mutations: 6 run, 6 caught.** The 503 was turned to 200. Each of the four
routes was put back to its empty answer. The raw error was put into the body.

### Part 2 — the gaps that need no migration

**Services, shown to members.** `GET /api/wellbeing/experts` and
`GET /experts/:uid` now return each expert's **active** services: uid,
title, description, length, price and currency, in the expert's order. Row ids
stay on the server. Until now both routes sent `services: null`.

The booking flow's step 2 lists the services:
- a member picks one, or a plain 30-minute session;
- `POST /experts/:uid/book` is sent the service's uid, and takes the length
  and price from it;
- `null` (an older Worker) reads "Services not read", never "none".

**The service on a booking.** `GET /bookings/mine` and `GET /experts/me/bookings`
return `service_uid` and `service_title` (`LEFT JOIN expert_services`).
- Both booking lists name the service.
- A booking without one reads "No service chosen". That is a fact about the
  booking, not a gap in the data.

**Slots from the weekly grid.** The new `services/wellbeing/slots.ts` cuts
30-minute slots from `expert_availability` for the next 14 days.
- **Each window is read in its own timezone.** Monday 09:00–10:00 Europe/Paris
  is 07:00 UTC in October.
- **Daylight-saving gaps.** A wall time a clock skips is not offered.
- **No grid.** An expert who has not set a grid keeps the old default: weekday
  half-hours, 09:00–17:00 UTC. The route says which applies
  (`source: 'grid' | 'default_hours'`), and the booking step tells the member
  when they are seeing the default.
- **Booking outside the grid.** A booking at a time the grid does not offer is
  refused with 409 `slot_not_offered`. It is checked against the whole set,
  not the listed page.
- **Copy.** The practice page now tells the expert that members book from
  their grid.

**A member's own rating.** `GET /experts/:uid` returns `my_rating` (stars,
review, date) or null. `POST /experts/:uid/rate` returns the rating as
stored. Each of the member's bookings carries `my_stars` for that expert, so
"Rated n of 5" survives a reload. Neither shows another member's rating.

**A member cancels their own booking.** `POST /bookings/:uid/cancel` works only
for the booker, on a booking that is open, unpaid and not yet started.

| Refusal | Code |
| --- | --- |
| Not the booker's booking | 404 `booking_not_found` |
| Status is not open | 409 `booking_not_open` |
| Session has started | 409 `booking_started` |
| Booking is paid | 409 `paid_booking` |

A paid booking is refused because its refund is the expert's to make through
Stripe. Cancelling it here would leave the money taken and the session gone.
The page says so.

The update is conditioned on the status it read (409 `booking_changed`), and
the expert is notified as when they cancel. My bookings shows Cancel, with a
confirmation step, wherever the route would allow it.

**The encrypted save.** `POST /checkins` returns `stored_encrypted`. It is
false when any value fell back to the plain backstop (Task #33). The card says
"Saved encrypted" or "Saved, but not encrypted", and never claims encryption
the route did not report.

**Tests.**
- `cloudflare-worker/test/wellbeing_gaps_d574.test.ts`: 7 tests, real router,
  the baseline's expert tables.
- `frontend/test/wellbeing_d570.test.mjs`: the tests that pinned these gaps
  as gaps now pin them closed.

**Mutations: 27 run, 27 caught.**
- 16 on the Worker: services listed even when inactive, unordered, or left
  off the directory; the rating read without its user; the rating not read
  back; the grid check removed; the grid ignored; the window zone ignored; a
  skipped time offered; the service join broken; another member's booking
  cancelled; the paid, started and closed checks each removed;
  `stored_encrypted` forced true; `my_stars` without its user.
- 11 on the screens: the paid and started rules, the service uid, the stored
  stars, the cancel button, both bookings' service lines, the default-hours
  note, the picked service, the confirm line, and the not-encrypted line.
