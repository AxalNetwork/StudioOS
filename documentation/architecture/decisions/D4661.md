## D4661 — Spin-Out Lab: submission recovery, retained access and read states, part 1 (#4661)

### Decision

This is #4661 in parts. Part 1 is scope items 1 and 2: the submission. Part 2,
below, is the Startup page's read states. The public outcome reads, the
retained graduate access and the workspace guards are not in either.

1. **The POST is the commitment; the status read after it is separate.**
   - Before, `submit()` cleared the form and then read the status inside the
     same `try`. When that read failed, the member saw "Your application was
     not submitted. Your answers are still on this page", which was false on
     both counts: it was submitted, and the answers were gone.
   - Now the page adopts the successful POST's own answer (`committedApplicant`)
     first, shows the submitted status, and only then clears the form.
   - The status read that follows is best-effort. A failure shows its own
     notice, "Your application was received. Its latest status could not be
     read just now", with a retry. It never says "not submitted".
   - A read that comes back showing no application is not believed over a
     commit that just succeeded: the submitted page stays, with the same retry.
2. **An unclear outcome is settled before another press.** `submitFailureKind`:
   - `refused`: a definite 4xx other than 408 and 429. Nothing was recorded.
     The Worker's words show and every answer stays.
   - `recorded`: 409, "already in review" or admitted. The application exists.
   - `unknown`: no status, a timeout, a rate limit or a 5xx. The POST may or may
     not have committed.
   - For `recorded` and `unknown`, the page reads the status and compares it
     with the application the member held before submitting (`recordedSince`).
     A new one in review is adopted and the form cleared. None means it did not
     land: the form stays, with "Your application was not received" and the
     answers kept.
   - If that status read also fails, the page cannot tell. Submit is shut and
     it says so, with "Check whether it was received". The member is never
     invited to send it twice.

### Tests

- `frontend/test/spinout_apply_recovery_4661.test.mjs` mounts the real page
  with a stubbed network: success then a failed read, then retried; an empty
  read after a commit; a refused 4xx; no answer, both when the status shows
  nothing and when it cannot be read; a 409; and a 503.
- The original submit code fails four of these.
- Mutation-checked, each failing a test: believing an empty read, leaving
  Submit pressable while unsettled, treating a 5xx as refused, never finding a
  new application, treating a 409 as refused, and not adopting the commit.

### Part 2: the Startup page's read states

3. **Two reads, two outcomes.**
   - Before, the page did `spinoutLab.state().catch(() => null)` and
     `api.listProjects().catch(() => [])`. A failed projects read became an empty
     list, so a founder whose record could not be read was told "No startup
     record yet" and offered to create one. A failed state read threw away a
     projects read that had succeeded.
   - Now each source keeps its own outcome: loading, ready or unreadable.
4. **"No startup record yet" follows only a successful empty read.**
   - A failed projects read draws `Your startup record could not be read. This
     is not a statement that you have none.` with a Retry. The Create prompt is
     not offered, because the record may already exist.
   - The rest of the page still draws, because the Lab state is separate.
5. **Each source retries alone.**
   - The projects Retry re-reads only the projects, and a recovered read draws
     the record. The state error's Retry re-reads only the state, where it used
     to reload the whole page, and the projects read earlier stay on the page.
   - A late answer from an older read of the same source never overwrites a
     newer one (a sequence per source).

### Part 2 tests

`frontend/test/spinout_startup_read_states_4661.test.mjs` mounts the real page:
a failed projects read is unreadable with no Create prompt; a successful empty
read does offer it; each retry re-reads only its own source; a failed state read
keeps the projects already read; a good read is neither unreadable nor empty.
The original page fails three of these. Mutation-checked, each failing a test:
a failed projects read drawn as empty, the state retry reloading both sources,
the projects retry re-reading the state, and the unreadable branch removed. One
mutant, a failed state read marked ready with no data, behaves the same as the
original because the page's no-state guard still shows the error screen. The
sequence guard against a late answer is not exercised by the test, since the
page offers no retry while a read is in flight.

### Part 3: the public outcome reads (#4661)

#4657, #4658 and #4659 are on `main`, so the enrollment and graduation
contracts are settled. This part is the Worker half of read-state item 5 and the
public section that draws it. Retained certificate access and the workspace
guards (items 3 and 4) are not in this part.

6. **A public outcome read that could not be read says so.**
   - `GET /api/spinout-lab/graduates`, `/stats`, `/cohort` and the signed-in
     `/shipped` answered `[]` or zeros when D1 failed. A page draws that as proof:
     "No graduates yet.", "0 companies", "no one in the sprint".
   - A failed read is now `503 { error: 'lab_outcomes_unreadable', message }`
     with one sentence we wrote ("The Lab’s graduates could not be read just
     now. Try again in a moment."). The exception's text goes to the log and
     never into the body, as `refuse` does everywhere (D278).
   - A read that worked and found nothing still answers `[]`, or a measured zero
     (`{ companies: 0, total_raised: null }`). Those are a different fact.
7. **A failed read of a company's fallback name is not "no name".**
   - A graduate or member with no project name falls back to their application's
     company name. A failed fallback read used to drop that row, so the list read
     as complete and shorter. It is recorded and the handler answers unreadable.
   - A company that already has a name from its project never reads the
     application, so the fallback table being down does not touch it.
8. **`/cohort` is one read.** A failed read of the recent graduates used to leave
   the column empty beside a good active list. It is now the whole read that is
   unreadable, so the page never shows a column that is empty because it failed.
9. **The section that draws it offers a retry.** `GraduatesSection` already drew
   a rejected read as an error and not as an empty list; it now says "This is not
   a statement that there are none" and has Try again, which reads again. The
   other consumers (`useSpinoutStats` draws an em-dash, `useCohortDirectory` and
   `OutcomesZone` draw an error with the Worker's sentence) already treated a
   rejected read as unreadable; the Worker was the part that hid failures.

**Not done here (the rest of #4661):**
- Retained certificate access for graduates (Explorer included) and the workspace
  cards and guards for active, paused, exited and graduated. They live in
  `App.jsx` and `SpinoutLabWorkspace.jsx`, which #4473 and #4474 also edit.
- `/fund-metrics` already carries `available` per block and is unchanged.

### Part 3 tests

`cloudflare-worker/test/lab_outcome_reads_4661.test.ts` runs the real routes over
the migrated schema: a read that worked answers its data, an empty list or a
measured zero; each failed read is a 503 with the code and the sentence and no
exception text; a failed application-name read makes `/graduates` and `/cohort`
unreadable instead of shorter; a named company never reads the application.
`frontend/test/spinout_outcome_reads_4661.test.mjs` mounts `GraduatesSection`: a
503 and a rejected transport are unreadable, never "No graduates yet.", and Try
again reads again and draws the recovered list or the empty state.
Mutation-checked, 12 mutations, each failing a test: each of the five catches
back to `[]` or zeros; the name-failure check removed from `/graduates` and from
`/cohort`; the name failure swallowed; the exception text in the body; a named
company still reading the application; the section drawing a failure as empty;
the retry not reading again.

### Part 4: retained certificate access and cards that agree with their destinations (#4661)

Items 3 and 4 of the scope, for the two lifecycle states whose cards and
destinations disagreed. (Stacked on part 3, merged in so this file has one
history.)

10. **A graduate keeps their own certificate whatever their role.**
    - `/spinout-lab/certificate` was behind `labRoles(['admin', 'founder'])`, and
      `labRoles` admits another role only while `spinout_lab_active === 1`.
      Graduation clears that flag, so an Explorer graduate (role `exploring`) was
      bounced by the route guard, while the workspace card for the certificate
      stayed enabled (it is the one tool a graduate keeps, D511).
    - The route now admits any signed-in account. The page and
      `GET /certificates/mine` are the member's own (the API is owner-scoped), and
      the page decides from the Worker's graduation rule (`state.graduated`, D4659)
      or the member's own credential. A member who is not a graduate still meets
      the locked view.
11. **A failed read is not "not yet".** The page read `state` and the credential
    with `.catch(() => null)`, so either failing drew "Your certificate unlocks in
    Week 4". A failure of either is now recorded, and when nothing else opens the
    page it says "Your certificate status could not be read just now. This is not a
    statement that you have none." with Try again, which reads again.
12. **An exited founder's tool cards are closed.** Leaving the programme (`/exit`)
    clears `spinout_lab_active`, and every tool route is behind it, so each
    destination refuses an exited founder. The cards stayed enabled from
    `unlocked_features`, opening pages that bounce. They are closed now and read
    "Closed after leaving"; an exited founder did not graduate, so the certificate
    is not kept either. An active member and a graduate are unchanged (D511).

**An existing source pin was updated, not weakened:**
`spinout_certificate_registry.test.mjs` pinned the credential read's
`.catch(() => null)`. Its intent, "no credential yet still gives a working page",
is unchanged and now proved by mounting the page; the pin follows the new catch,
which records the failure.

**Not done (left for the owner):** a paused member. Their `spinout_lab_active`
stays 1, so cards and guards already agree; no change was needed.

### Part 4 tests

`frontend/test/spinout_retained_access_4661.test.mjs` mounts the real certificate
page: a graduate of another role opens it from the graduation rule alone, from
their own credential alone, and from both; a member who is not a graduate meets
the locked view; each read failing, alone or together, is "could not be read" and
never the locked view, and Try again reads again; the route is no longer role
gated; an exited founder's cards are closed and an active member's open.
Mutation-checked, 8 mutations, each failing a test: the route role-gated again;
the graduation rule ignored; the member's own credential ignored; a failed read
drawn as locked; the retry not reading again; a state failure not recorded; a
registry failure not recorded; exited cards left open.
