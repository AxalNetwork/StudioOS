## D999 — Persona segments part 2: the segments read

- **Status:** S03, 2026-10-24 (#2814; part 2 of #2378, D997 §6). No migration.
- **Basis:**
  - D997's page at `/admin/persona-segments` (#2809), which today counts from `GET /api/personas/admin/list`: the newest 500 accounts, admins included (Guard L).
  - D998's mapping (#2826): each segment's `profile` (founder, investor, advisor, partner, exploring) in `cloudflare-worker/src/personas.ts`.
  - The canvas, `design/incoming/Persona Segments Page.dc.html`: SEG1, SEG2's tiles, SEG7 and SEG10 to SEG12.

### 1. The read

`GET /api/personas/admin/segments`, in `routes/personas.ts` under `requireAdmin` (an Admin and a Super Admin read the same counts, D997 §4). The read is built in `services/personaSegments.ts`. The client is `personaSegmentsApi.read()` in `frontend/src/lib/api/personaSegments.js`, re-exported by one line in `api.js` (D527).

- **Counts only.** No row names, emails or ids a member. Nothing a member answered (`user_profile_extras`) is read.
- **Every account but admins.** Admin accounts are left out of every count. Deactivated accounts are left out too, and counted apart as `members.deactivated`, as Insights counts them. The read counts every account, not the newest 500, so Guard L does not apply to it.
- **One segment per member:** their primary `user_personas` row. Should an account ever hold two primaries, the newest row (highest id) is counted, so no account is counted twice.
- **Each block answers alone:** `{ available: true, … }` or `{ available: false, unreadable: true, reason }`.
  - One grouped pass over the accounts feeds `members`, `segments`, `by_profile`, `how_set` and `confidence`, so their totals are the same total.
  - The LP store, the tag dates and the move log are read separately. A missing LP store fails only `sub_accounts`; a missing activity log fails only `moves_30d`.
  - A failed block carries no figures, never zeros.

### 2. The blocks

| Block | What it counts |
|---|---|
| `members` | `total`, `in_segment`, `no_segment`, `new_30d` (segments given in the last 30 days), `deactivated` (apart), `profile_differs`, `not_in_taxonomy` |
| `segments.rows` | One row per segment, in the taxonomy's order, then any stored id the taxonomy does not know (`in_taxonomy: false`). Each row has: `members`; `new_30d`; `still_explorers` (members whose account is still an Explorer); `profile_differs` (members whose account profile is not the segment's profile; null for an unknown id, which has no profile) |
| `sub_accounts` | `lp`: members with an approved LP application (Insights' definition), by segment and with no segment, not added to any total. `product_tester`: Not recorded, with Insights' reason (`PRODUCT_TESTERS_REASON`): nothing on the database marks one yet |
| `by_profile` | Per account profile (founder, investor, advisor, partner, exploring): its members, its no-segment count, and its segments by count. `other` holds any other role; while `users.role` is CHECKed to the six roles it is empty |
| `how_set` | `router` (Suggested at sign-up), `self_select` (Chosen by the member), `admin_retag` (Set by an admin), and `not_recorded` for any other source |
| `confidence` | Over members suggested at sign-up (`router`): D997's four bands (under 50%, 50 to 69%, 70 to 89%, 90% and over). A confidence that is not a number is `not_recorded`, never 0% |
| `weekly` | New segment tags per week, eight weeks from Monday (UTC), the current week `to_date`. Counted by the day each member's current segment was first given (`user_personas.created_at`); a member moved since is counted in the week of their current segment. A week before any segment was dated is `null` (a break), never 0; a quiet week after that is a real 0. Undated rows are counted apart |
| `moves_30d` | D255's `persona_retagged` rows in the last 30 days whose target is a member, not an admin |

### 3. Small cells

The house rule suppresses a count from 1 to 4 for what members *answered* (`suppressGroup`, `SMALL_CELL_MIN`); part 4's answer aggregate does this. This read does not suppress. A segment is not an answer. The same admins already see each member's segment, one by one, in `/admin/list` and on Unclassified, so hiding a small segment count would protect nothing that page does not already show. Part 4 suppresses the answers and archetypes by segment.

### 4. What does not change

- The page still reads `/admin/list`. Part 7 (#2819) switches its tiles, charts and cards to this read and drops Guard L for them.
- `/admin/list` and the re-tag route are unchanged.

### 5. Tests

`cloudflare-worker/test/persona_segments_d999.test.ts` (11 tests) runs on `node:sqlite` with the baseline's tables. The fixture is counted by hand: twelve accounts, among them an admin, a deactivated account, a stored id not in the taxonomy, an account with two primaries, and LP applications approved, pending and duplicated.

- The read: each block's exact counts; the confidence band edges; the Monday weeks with a break and a real 0; and each block failing alone (no LP store, no activity log, no segment table).
- The route, mounted as `index.ts` mounts it: 200 for an admin, with no name, email or account id in the body; 401 without a session; 403 for a member.
- Every new assertion was mutation-checked.
