## D6162 — Investor /raise/data-room redirect keeps the venture, and the stale Deals-row match is removed (#6162)

- **Status:** Built for #6162, 2026-11-27 (slot S37). Filed from the 2026-11-14 coordinator audit under #5074.
- **Builds on:** D311 (an investor's rooms are read by grant under Research · Diligence), D1109 (`/raise/data-room` is the Data room tool's Home), D4473 (a member who also holds Founder is served the founder's room), D5074 (the canonical venture context and `ventureRef`), D6267 and D6269 (the rooms list and its page).
- **No migration.** One additive field on an existing Worker read.
- **Mutation check:** 20 mutations, 20 caught, 0 equivalent (19 through `scripts/mutation-check.mjs`, one by hand: a failed read drawing the venture line).

### What was decided

1. **The investor arm keeps the query and the hash.** `/raise/data-room` still answers an investor who does not hold Founder with a redirect to `/research/diligence`, and the condition is unchanged (`effectiveRole === 'investor' && !holds('founder')`). The redirect was a bare `<Navigate to="/research/diligence" replace />`, which dropped `?project_id=N` and the hash; it is now `{ pathname: '/research/diligence', search: location.search, hash: location.hash }`, as the retired-mode forwards on the same route already did. The founder and admin arms (the `?mode=` forwards, then the Data room tool) are unchanged. The redirect is written inline in `App.jsx` because App's import list is frozen (D5615).
2. **The rooms list reads the venture the address names.** `ventureRooms(data, search)` in `diligenceZoneRead.js` reads the venture with the shared rule, `ventureRef` (D5074), so `?project_id=N`, the legacy `?project=N` and a project UID in either key all work. A number is matched against each room's `project_id`, a UID against its `project_uid`.
   - **One live grant for it:** the page opens that room, `/research/diligence/<grant uid>`, with a replace, the query and the hash carried on.
   - **More than one:** the page stays on the list, says how many rooms are open for this venture, and marks each one with a "This venture" pill beside the company name (a word, not colour alone; the row's own layout is unchanged).
   - **None:** the page stays on the list and says, above it, "No room is open to you for this venture. Only its founder can open one; you can ask from the deal's Documents tab." The rooms that are open to you are still listed.
   - **A room that does not carry the key the address used** (an older read): a miss is `unknown` and the page says nothing about the venture. Not finding it is not a claim that there is no room.
   - **A failed or refused read** says Unavailable or Refused as before and nothing about the venture (D5129: a failed read is never "none").
3. **The grant read carries the venture id.** `GET /api/research/diligence` already returned each room's `project_uid`; each item now also carries `project_id` as a number. It is the id of a venture the caller holds a live grant to, so nothing new is disclosed; the generated links (`ventureSearch`) name a venture by this number.
4. **The investor Deals row no longer claims `/raise/data-room`.** An investor never stays on that address. The route sends them to `/research/diligence`, which lights Research. The row's other entries are unchanged.

### Departure from the canvas

The Rooms canvas (D6268, IRV-02) draws no line for a venture-named address. The one-line status above the tiles and the "This venture" mark on a row are the smallest addition that says what the issue asks for, in the page's existing tones and with dark-mode variants. No layout changed.

### Dependency risk

Research v2 (#3701) may move `/research/diligence`. If it does, the investor arm in `App.jsx`, `ROOMS_PATH` and `roomTarget` in `diligenceZoneRead.js` move with it. #5074 (the venture context) closed on 2026-11-17 and touched the same Route element; nothing of it is open.
