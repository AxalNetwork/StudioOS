### 1. What changed in D1

`promo_codes` gains nine columns, each nullable:

| Column | Meaning |
|---|---|
| `paused_at`, `paused_by` | when and by whom a code was paused; cleared on resume |
| `ended_at`, `ended_by` | when and by whom it was ended; never cleared |
| `reason` | the reason given for the last pause, resume or end |
| `name`, `note` | HQ's own words for the code; also on the Stripe promotion code's metadata |
| `duration_in_months` | the months a `repeating` coupon runs; NULL for once or forever, and for every code made before this |
| `replaced_by` | the promotion code id that replaced this one, when Replace ended it |

There is also an index on `created_at`, for the default sort.

Stripe stays the source of truth for the discount, the cap and the expiry. The mirror records only what Stripe does not keep: why, by whom, and whether "inactive" means paused or ended.

### 2. The list read: `GET /api/admin/promos`

The read takes `q`, `state`, `applies`, `sort`, `page` and `page_size`. It returns `{ promos, total, page, page_size, sort, counts }`.

- **Each code carries `state`.** The states are D1270's words, in this order: `ended`, then `paused`, `off` (inactive in Stripe and never recorded as either), `expired`, `at_cap`, `active`. `listState` (TypeScript) and `STATE_SQL` (SQL) state the same order.
- **Expiry compares as a time** (`julianday`), so an ISO stamp and a SQL stamp read alike.
- **`q`** searches the code (any case) or the name, from two characters, through `likeNeedle`. `%` and `_` are escaped.
- **`applies`:**
  - `all` keeps codes with no product list; `products` keeps codes with one.
  - `plans` is refused with 400 `applies_not_recorded`. Plan scope is part 3's (migration 630), and an empty list would claim no code applies to plans.
- **`sort`:** `newest` (the default), `oldest`, `code` or `redeemed`. Every order ends on the id, so a page never shifts between two reads of the same rows.
- **Paging:** `page_size` defaults to 25, at most 100.
- **`total` and `counts`:**
  - `total` counts what the filters keep.
  - `counts` has one figure per state under every other filter, so the chips add up. A measured 0 is a 0.
- **Refusals:** a bad value is 400 with its code: `invalid_page`, `invalid_page_size`, `invalid_state`, `invalid_applies`, `invalid_sort`, `invalid_q`.
- **A read that fails** is 503 `promos_unreadable`, "That is not the same as none". It is never an empty list.

**Bound SQL.** Every value is bound. The statement text is built from three module constants (`LIST_FROM`, `LIST_WHERE_STATE`, and the `LIST_ORDER` entry picked by an allow-listed `sort`). `scripts/sql-prepare-baseline.json` records those three sites. They carry no value, so none is an injection.

### 3. Pause, resume and end: `PATCH /api/admin/promos/:id`

- **The body:**
  - `action` is `pause`, `resume` or `end`, with an optional `reason` of at most 280 characters.
  - A reason is required for `end`. It is also required for `pause` when the body sends `action` (the canvas's Pause dialog asks for one).
  - `name` and `note` may come with an action or alone. An empty value clears one.
- **The legacy `active` boolean** maps to pause or resume, with no reason, so today's toggle keeps working.
- **Stripe first.** Stripe's `active` and the `metadata[name]` and `metadata[note]` change before D1. If Stripe refuses, nothing in D1 changes.
- **Guarded updates.** Each D1 update is guarded on the state it expects, so two writers cannot both win. A guard that matches no row is 409 `promo_changed`.
- **Refusals:**
  - `invalid_action`, `invalid_active`, `nothing_to_change`, `reason_required`, `invalid_reason`, `invalid_name`, `invalid_note`;
  - 409 `already_paused`;
  - 409 `promo_ended` for any action on an ended code. **An ended code never resumes.**
- **Audit:** each write is audited as `promo_pause`, `promo_resume`, `promo_end` or `promo_update` (report type `billing`), with the reason and a changed name. A changed note is recorded as `note_changed`, never its text. Console logs hold error codes and outcomes, never a promo code, name, note or reason.

### 4. Delete

`DELETE /api/admin/promos/:id` now records the end, with an optional reason. It still deactivates the promotion code and deletes the coupon in Stripe (the coupon delete is best effort).

It no longer leaves a code that reads like a paused one.

### 5. Replace: `POST /api/admin/promos/:id/replace`

Stripe fixes a code's discount, cap and expiry once made. So "Edit" (PRM5) is a new code that takes the old one's place.

- **The body** is the same as `POST /` (the new code's terms), plus a required `reason`.
- **The order:**
  1. Make the new code. Its promotion code carries `metadata[replaces]`.
  2. End the old code in Stripe (`active=false`, `metadata[replaced_by]`).
  3. Record the end in D1, with `replaced_by`.
- **If Stripe refuses to end the old code,** the answer is 502 with `old_ended: false` and both ids. The new code exists, the old one is still live, and the page must say so. It is never reported as a clean replace.
- **Refusals:** 404; 409 `promo_ended` (an ended code is not replaced twice); `reason_required`; 400 `same_code`.
- **Audit:** `promo_create` (with `replaces`) and `promo_end` (with `replaced_by`).
