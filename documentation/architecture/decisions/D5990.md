### What triggers a decision

| Delivery | Head | Base |
|---|---|---|
| `pull_request` `opened`, `synchronize`, `reopened` | `pull_request.head.sha` | `pull_request.base.sha` |
| `merge_group` `checks_requested` | `merge_group.head_sha` | `merge_group.base_sha` |

- **Validation:** the webhook refuses either kind (400) without full SHAs, and a pull request without a positive number. It queues only the SHAs and the number; no title, branch name, fork or author is queued.
- **Everything else** carries no SHAs and decides nothing: other `pull_request` actions (`labeled`, `edited`, …), `issue_comment`, `pull_request_review`, and `merge_group` `destroyed` (which keeps D5618's cancellation). `policyTarget` is the one place this is decided.

### The decision

`decide(result, target)` maps `evaluate`'s result to the check:
- **Success:** only a completed T0 or T1 classification.
- **Action required:** everything else, carrying the tier and the reasons. That includes every API error, exception and timeout, which `evaluate` already returns as T2.
- **A T2 merge-group head:** action required by its own rule, with the reason "owner sign-off is not built yet (#5620 items 4 and 5)". This rule is where sign-off will plug in. Until then nothing can pass a T2 queue entry.

### The check run

`POST check-runs` with:
- `name: merge-control/policy`, `head_sha`, `status: completed` and the conclusion;
- `external_id` `<policy_version>:<event>`;
- `details_url`: this file at the policy commit;
- `output`: the title, a summary with the tier, conclusion and `policy_version`, and a text listing the event, base, head and every reason.

### Once per SHA and policy version

`repoControl.ts` stores one decision under `policy:<head>:<policy_version>` and audits it once. A retry or a redelivery, under any delivery id and across a restart:
- posts the stored decision, without evaluating again;
- never posts once the check run exists.

So one SHA never gets two different conclusions under one policy. A new head, or a new deploy (a new `policy_version`), is a new decision.

### Fail closed

- **A client or posting error** throws before anything is marked posted. The Queue retries the delivery, and the retry posts the same stored conclusion.
- **Errors before the decision:** an error creating the client, or a timeout before it, posts nothing.
- **The kill switch:** with it on (the default), the policy path makes no GitHub call and posts no check. A Worker that is not running posts nothing either.

### Audit

Each decision writes one `audit` row of kind `policy`, carrying the SHA, base, event, PR number, tier, conclusion, `policy_version` and time.
- The table now has two SQLite triggers that abort any `UPDATE` or `DELETE`, so the audit is append-only in the store, not only by convention.
- No current code updates or deletes audit rows.
- Durable Object SQLite is SQLite; whether the deployed runtime accepts the triggers is checked at #5618's first deployment, because the constructor creates them.

### Token scope

The policy path asks GitHub for its own installation token, `{ checks: write, contents: read }` (`POLICY_PERMISSIONS`). Cancellation and reconciliation keep D5618's `{ actions: write, contents: read }`, so a missing `checks` grant cannot break them.
