## D8198 — Preserve existing SQL proposal output (#8198)

The offline register compiler creates its SQL proposal with exclusive creation.
If that pathname already exists, the compiler opens it read-only, without
following a final symlink or blocking on a FIFO, and checks the opened file's
type and exact bytes through the same descriptor. Only an identical regular
file is accepted. Existing content is never truncated or rewritten, including
an identical replay, and a competing creator's output is preserved.

The SQL creation or comparison completes before the report, audit and statement
JSON outputs are written. A conflicting or unsafe SQL destination therefore
leaves those outputs untouched. Existing input/output separation and primary
source-ledger protections remain in force.

Each descriptor closes on success and failure. Non-collision errors propagate.
If writing a newly created proposal fails, any partial file remains for explicit
inspection; cleanup must not delete a pathname another process may have replaced.

This is output integrity within an operator-controlled parent directory. It is
not an atomic publication transaction for all four artifacts, a filesystem
permission change, or a production database operation. A later JSON failure
can leave a complete SQL proposal and a partial set of JSON outputs; replay
accepts the identical proposal and can regenerate the companion outputs.

Focused filesystem regressions cover exclusive creation, unchanged identical
replay, conflicting bytes, a controlled competing creator, descriptor-bound
comparison, final symlinks, FIFOs and partial failures. The existing register
admission, immutable source proof, additive SQL and source-ledger checks remain
part of the same integration suite. Validation results and environment limits
are recorded with the pull request.
