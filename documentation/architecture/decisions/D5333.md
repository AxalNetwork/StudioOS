## D5333 — A sequence opt-out is recorded on POST, not when the link is opened (#5333)

- **Status:** Built, 2026-11-10 (Worker only).
- **Amends:** D4493's opt-out section (#4493, PR #4781). That section now describes the two-step opt-out; this file
  says why it changed.

### Why

D4493's `GET /api/grow/optout/:token` recorded the `opted_out` suppression and stopped the contact's enrolments.
Many corporate mail gateways open every link in a message before the person sees it, so a prefetch opted the
prospect out without them doing anything. D4493 had accepted that ("a scanner can only stop messages"), but an
opt-out the person never chose is a lost prospect and a wrong record of what they asked for. The newsletter's
confirm link (D813) had already moved off GET for the same reason.

### What changed

1. **GET writes nothing.** A valid token answers a small public page with one button, "Stop these emails", naming
   no person, address or venture. Its plain HTML form posts back to the same URL: no script, within the Worker's
   CSP (`form-action 'self'`). A JSON caller gets the ask sentence and `method: "POST"`. A forged token, or one
   whose contact is gone, is 404.
2. **POST records** exactly what the GET used to (hash-only suppression, active enrolments stopped, one fixed
   sentence). It answers HTML to the page's form and JSON to anything else, 200 either way, so RFC 8058's
   `List-Unsubscribe=One-Click` body is accepted. It needs no session and is CSRF-exempt: the path prefix
   `/api/grow/optout/` sits beside the newsletter's one-click exemption in `middleware/csrf.ts`, since the signed
   token is the authority. A forged token is 404.
3. **The send sets the RFC 8058 headers.** `sequenceSendGate` returns the step's signed opt-out URL, and
   `/api/mail/send` hands it to the adapter as `listUnsubscribe`. `buildMime` adds
   `List-Unsubscribe: <url>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` for an https URL that can sit
   in a header, so mail that is not a sequence step is unchanged.

### Adapters

| Adapter | Both headers |
| --- | --- |
| Gmail | Yes: it sends the message `buildMime` builds. |
| SMTP (`imap`) | Yes: same. |
| Outlook | **No.** Graph's JSON `sendMail` accepts only `x-` custom headers in `internetMessageHeaders`. Graph also takes a whole MIME message on `sendMail`, which would carry them; switching Outlook's send to MIME changes every Outlook send and is left as a follow-up. |
| Member's MCP server | **No.** Its send tool takes to, subject and body only. |

Where a header cannot be set, the body's opt-out line is the way out; the send gate still requires it. The line's
wording did not change, so neither did the gate's check.

### Not changed

- The token, its HMAC domain and the opt-out line.
- No rate-limit bucket of its own: a capped opt-out is an opt-out lost; the general per-IP cap covers both verbs.
- No auth-inventory ledger entry: `scripts/build-auth-inventory.mjs --check` passes with the new POST as it did
  with the GET.

### Verified

`cloudflare-worker/test/grow_sequences_4493.test.ts`: a GET with a valid token leaves the suppression, stopped
enrolment and opt-out log counts unchanged and serves the one-button form; a POST records once (a second press adds
no suppression) and stops the enrolment; a forged token is 404 on both verbs; no answer names an address; a
one-click POST carrying an auth cookie and no CSRF token passes the CSRF middleware while another POST path is still
refused; the sent message carries the URL and `buildMime` writes both headers; a URL with a line break is never set.
Each was mutation-checked: GET calling `recordOptout`, removing the CSRF exemption, dropping `listUnsubscribe` from
the adapter call, dropping the header from `buildMime`, and POST not recording each fail a test.
