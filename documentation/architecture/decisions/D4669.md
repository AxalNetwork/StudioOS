## D4669 — Session containment: an ended session ends everywhere, and emergency acts say what they reached (#4669)

- **Status:** Part 1 built, 2026-11-07. Part 2 built, 2026-11-10: the owner chose option B for cross-branch emergency acts (§ Part 2). Still waiting on the owner: review of the audit findings in the private advisory process (SECURITY.md). Production behaviour is **unverified**: nothing here was checked against the live deployment.
- **Builds on:** D481 (HQ · Security's session list and acts), D165 (sign one account out), D248 (support-session expiry and ceiling), D120 and D122 (branch support sessions), D104 (branch cookie names), T6 (request protection).
- **Stays out of:** what counts as an active session in lists and counts, security-event identity, partial reads and backup evidence (#4691); the data-subject request lifecycle (#4675); the per-route authorization matrix (#4570).

### What is built

1. **Ending a session ends it on every request path.**
   - A support-session token, HQ's or a branch's, names its support-session record. Every request re-reads that record, so ending the session refuses the token from its next request. Before, ending closed the record and the token lived on until its own expiry.
   - An HQ support session also stands only while the operator who opened it is an active administrator whose own sessions were not signed out after it was opened. Signing the operator out ends the support sessions they hold.
   - A support session whose record cannot be written is not opened, and no token is handed out. On a branch the same holds for the session row. This reverses D290's choice to grant the session and report its reason as missing: a token with no record would be one nobody could end.
   - The realtime upgrade now asks the same question the HTTP path asks (`sessionStanding` in `auth.ts`): the account's sign-out floor, the session row, the support-session record.
   - Every Worker mint path issues a token bound to a row that can end it. The one that did not (the deck-share sign-up) now writes its session row; the realtime probe presents the caller's own session instead of minting one.
   - Sign-out revokes every session the request presents, read the way authentication reads them, including a branch's own cookie, and its answer says whether a session was ended.
2. **Safe failure.** A session or support-session store that cannot be read is a refusal, never a pass. Ending a support session, and HQ's sign-out acts, report a failed write as a failure (503, nothing changed) instead of a success or a generic error.
3. **Request protection follows the authentication source.** The exemption for Bearer-authenticated requests applies only when the Bearer is the credential that authenticates the request, by the same precedence authentication uses.
4. **Emergency-action scope is stated.** Every session act on `/admin/security` writes this deployment's database. A branch is its own deployment, with its own accounts and sessions, and is not reached. Each act's answer now carries `scope` and, for sign-outs, `outcomes`: one row per deployment, this one with its result and each bound branch as `not_reached` (`services/emergencyScope.ts`). The page says so beside the acts and under each result, and the sign-everyone-out control reads "this deployment", not "all tenants".

It now carries one and is refused from its next request. ### Part 2 — reaching branches, on request (the owner's option B)

The owner answered the scope question on 2026-11-10: **option B**. HQ's emergency sign-out may reach branch deployments when the operator asks it to, each branch reports its own outcome, and partial success is shown as partial.

**A separate act.** `POST /api/admin/security/branch-sign-out`, drawn on the Access workspace as "Sign out on branch deployments". Every other session act is unchanged: it writes this deployment, says so, and lists each bound branch as `not_reached`. Reaching a branch is something an operator asks for, not a side effect of an act that used to stay local.

**What it signs out.** One person, named by email (their account on a branch is a different record, so HQ's id means nothing there), or every active account on each branch. One account can also be named by its id on one branch. The branch raises the account's sign-in floor, the same primitive part 1 uses here, so every token issued before it, including any support session opened as that account, is refused from its next request.

**The branch call** (`emergencySignOut` on `HqEntrypoint`, logic in `rpc/branchOps.ts`):
- carries HQ's secret, first, and is refused without it (`authenticateHq`), as `unbindAdmin` is;
- checks the reason (at least ten characters), the operator's name, the operation key and the target, and throws every refusal **before** writing, prefixed `rpc:`;
- writes the floor and its audit row in **one batch**, with the count the update changed, plus a row addressed to the person for a named account;
- answers a key it already holds with that record (`replayed: true`) and writes nothing.

**HQ's route** checks the write bar (TOTP, a recent step-up, the elevation), the reason, the key, the target and `HQ_RPC_SECRET` before asking any branch, then asks every branch named concurrently, under a ten-second deadline (`BRANCH_WRITE_DEADLINE_MS`; a read's two seconds would turn healthy branches into "not known" mid-incident).

**Each branch is its own row** (`services/emergencyScope.ts`):

| Outcome | Means |
|---|---|
| `done` | The branch answered that it acted, with how many accounts. `replayed` when the act was already on its record. A branch where nobody holds the email answers `done` with 0 and says so. |
| `failed` | The branch refused (an `rpc:` error, thrown before its batch): nothing changed there. |
| `unreachable` | Not bound, or no answer before the deadline, or a call that failed in transit. Whether it acted is **not known**. Never counted as done, and never as "nothing changed". |

The act is `done` only when every branch named answered done, `failed` when none did, and `partial` otherwise. HQ records the act with every branch's row in its admin audit log, whatever the outcome.

**A retry is safe.** The page makes one key when the card opens and Try again resends it, so a branch that acted but timed out answers from its record instead of signing anyone out twice. Changing the target or the reason makes a new act with a new key.

**Gates kept.** `HQ_RPC_SECRET` must be set (409 otherwise, and no branch is asked), the write bar is the one signing everyone out here carries, and the branch checks HQ's secret for itself.

**Not built: ending one support session on a branch by its record.** HQ holds no read of a branch's support-session records, so it cannot name one. Signing out the account a support session was opened as ends that session too (it is held to the account's floor), and that is the containment option B offers. A per-record remote end would need a branch read of open support sessions first.

### Residual, stated

- A token minted before this change carries no binding and is held to the account's sign-out floor and its own expiry: at most thirty minutes for a support session, a day for an ordinary one.
