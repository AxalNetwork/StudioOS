## D4706 — Deployment attempts, retry without duplication, and a shared mutation outcome (#4706)

### Decision

A licence's deployment is split into its **identity** and its **attempts**.

- `licence_deployments` (migration 258) stays the identity: one row per
  licence, holding the code, hostname and residency. Two new columns:
  `current_attempt`, and `do_jurisdiction`, which was dispatched before but
  never stored.
- `licence_deployment_attempts` (migration
  `202611062205_licence_deployment_attempts.sql`) records each try:
  - who asked and when;
  - how it ended: `dispatching`, `dispatched`, `failed` or `succeeded`;
  - the failure code and reason;
  - the Actions run's id, link, status and conclusion.

  The migration backfills one attempt for each existing deployment.

New Worker routes (`routes/admin_deployments.ts`), all Super Admin:

| Route | What it does |
| --- | --- |
| `GET /api/admin/licences/:uid/deployment` | Returns the identity, every attempt (newest first), `last_failure`, `last_success`, `phase`, `retryable` and `reconcilable`. |
| `POST /api/admin/licences/:uid/deploy/retry` | Starts a new attempt when the current one failed. The body must name `expected_attempt`. |
| `POST /api/admin/licences/:uid/deploy/reconcile` | Reads the runs GitHub started for the current attempt and records how they ended. It never dispatches. |

### Why a retry cannot duplicate

- **The retry is a compare-and-set.** The identity moves from attempt N to
  N+1 only if, in the same `UPDATE`, it is still `failed` and still at N.
  - A double click, two tabs, or a replay after a lost response all find the
    counter already moved. They get the current state back with
    `replayed: true`, and nothing is dispatched a second time.
  - A test lands a rival write between the route's read and its `UPDATE`,
    and shows the losing request does not dispatch.
- **A refusal that can be known in advance never moves the counter.** A
  missing GitHub credential, a missing territory, or a pre-D4706 row with no
  Durable Object jurisdiction (which is asked for, never guessed) is refused
  before the `UPDATE`.
- **The infrastructure side was already idempotent.** `branch-provision.yml`
  tolerates "already exists" at every create step and runs one job per code
  (`concurrency: branch-provision-<code>`). So a retry resumes the work
  rather than creating it twice. No D1 row is deleted to retry.

### An answer that never arrived is unknown, not failed

`workflow_dispatch` answers 204 with no run id. When the dispatch gets no
answer at all (a network error, a timeout, or a 5xx from GitHub), GitHub may
still have queued the run. So:

- `dispatchWorkflow` sends the request **once**. `ghFetch` no longer retries
  it, because that retry is itself a blind duplicate.
- The route answers **504 `outcome_unknown`**. The attempt stays
  `dispatching` and the identity stays `requested`, so neither Deploy nor
  Retry can send it again.
- The page offers **Check status** instead. Reconcile lists the workflow's
  dispatched runs created since the attempt (less a minute), then picks the
  one that:
  - has a job named `provision <code>`, which is the job name the workflow
    declares; and
  - no earlier attempt has already claimed.

  How the run's state settles the attempt:

  | Run state | Result |
  | --- | --- |
  | Still running | Recorded, and the attempt stays pending. |
  | Concluded `success` | The attempt is `succeeded` and the identity becomes `hostname_active`. |
  | Concluded anything else | The attempt is `failed` (`run_failed`), with the run's log link. |
  | No run within 15 minutes, and no unidentified run left | The attempt is `failed` (`run_not_found`), and can then be retried. |

- A run that succeeded still reads as **partial**. The run's last checks are
  the host's smoke test and the PR that gives HQ its service binding. So the
  branch answers, but HQ reaches it only once that PR merges and HQ
  redeploys. Full completion is `linked`.

### One outcome vocabulary for licence writes

`frontend/src/lib/mutationOutcome.js` defines five outcomes:

| Outcome | What it means |
| --- | --- |
| `pending` | Sent; no answer yet. |
| `committed` | The server said it is done. |
| `refused` | The server answered and said no. Its own sentence is shown. |
| `partial` | Part of it is done; the rest is still pending. |
| `unknown` | No answer came back, so it may or may not have been done. |

- **How an error is classified.** No HTTP status (a timeout or a dropped
  connection), a bare gateway 502/503/504, or the Worker's
  `outcome_unknown` is **unknown**. Any answer from the route itself is
  **refused**.
- **What an unknown outcome does.** It always tells the operator to check
  before trying again, and the page re-reads the state rather than offering
  the write again.
- **How it is shown.** `components/OutcomeNotice.jsx` renders the outcome:
  refusals and unknowns with `role="alert"`, the rest with `role="status"`.

On the licence page:

- The Deploy step shows the current attempt, the last failure (with its
  reason) and the last success (with run links).
- Retry appears only for a failed attempt. The principal's email is kept from
  the form.
- Check status appears while an attempt is open, and the page re-checks by
  itself every 30 seconds until the attempt settles.
- Seats, terms, and the lifecycle actions (activate, suspend, reinstate,
  renew, terminate) used to report a failure only to telemetry. They now show
  their outcome, and keep what was typed.
- An unknown lifecycle outcome re-reads the licence.

### Tests

- `cloudflare-worker/test/deployment_attempts_d4706.test.ts` covers:
  - the backfill;
  - retry and replay, including the race;
  - the not-failed and stale refusals;
  - the unknown outcome being sent exactly once;

  - the deployment read.

  Every test counts the dispatches GitHub received.
