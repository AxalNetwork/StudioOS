## D7909 part 6 — Retain the Run deadline through journal and delivery tails (#7909)

S09 verified actual receipt and interface compatibility of combined `1e8ea436`
on #8234, including 175 passing local cases. Its review identified that S39's
post-supervisor mapping/journal/delivery tail checked only the receipt deadline,
which can be later than the original Run-process deadline. That scoped receipt
and review do not automatically cover this correction.

The listener now persists the earlier of the receipt and the Run-process bound
with its result journal. A valid observed test success that reaches final mapping
past this bound becomes a timed-out execution outcome, with a nonzero supervisor
exit. A raw test failure remains a test failure with its original exit.

The bound is checked again before delivery and after acknowledgement durability.
If delivery or its acknowledgement crosses it, the journal retains an outstanding
timeout correction; the old ACK cannot acknowledge that changed result. Cleanup
uses the persisted Run bound rather than creating a new one from its own process
start. It delivers the correction through the same authenticated ownership path.
A result whose Run and delivery already completed and were acknowledged in budget
is not retroactively expired just because a later cleanup process starts past the
old Run bound. Unacknowledged results still retain that original deadline.
The coordinator also independently requires completed successful run/job evidence
before aggregate success; a callback alone never supplies that provider truth.

Paired fake-time regressions cover success/failure after supervisor return, during
journal durability and during actual authenticated RSA/SQLite delivery. They
assert the earlier bound while the receipt is still live, sticky failure, dirty
late ACK and correction after a simulated new cleanup process. These are source
classification/delivery tests, not native latency measurements.

Synchronous filesystem durability remains non-interruptible here. Network/native
whole-path fit and cleanup after host loss still require independent review and
qualification; no timeout or resource limit is increased. The precise create-intent
absence exception is named in the bridge comment. Unknown creation or an absent
ID/result record alone still supplies no removal proof. All activation/caller
controls stay off, ordinary hosted CI stays intact, and #8234 remains draft.
