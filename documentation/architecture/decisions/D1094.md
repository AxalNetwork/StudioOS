### 1. Pitch deck: a Slides deck as "Import as version N" (GW6)

**What is read.** For each Slides deck the member chose for Pitch deck, a sync reads `files.get`, then `presentations.get`.

**The mapping onto `pitch_decks.slides`** was UNVERIFIED in the plan. I read the editor (`routes/decks.ts` `sanitizeSlides`, `services/decks/slideModel.ts`) and chose the editor's legacy fielded shape, one card per Google slide:

- `title`: the text of the slide's `TITLE` or `CENTERED_TITLE` placeholder, wherever it sits on the slide. A slide with none is "Slide N".
- `body`: every other text shape on the slide, in order, one per line.
- `notes`: the speaker notes (the notes page's `speakerNotesObjectId` shape), at most 4,000 characters.
- **Not carried:** images, charts, tables, layouts and the theme. The founder adds them in the editor, so no image is fetched from Google.
- At most 60 slides, as the editor takes.

**The proposal.**
- One per Google version of the file: the source key is `slides:<file id>:<modifiedTime>`.
- A re-sync refreshes a pending one.
- A newer Google version withdraws the pending one it replaces.
- A decided one is never proposed or refreshed again.
- A deck with no slides proposes nothing.

**How the module shows it.** `parts.google` titles the proposal "Import “Seed deck v7” as version 8?". It lists the slide titles and says "Version 7 stays as it is. You can switch back to it at any time."

**Accept.**
- Accept writes the version through the editor's own writer (`insertVersion`, `sanitizeSlides`), titled "From Google Slides: <name>".
- The previous version stays in place; it is only no longer the current one.
- The ledger row is `<file id>:deck:<project>:<modifiedTime>` → `pitch_decks`.

**Dismiss** is once; nothing is written.

### 2. Data room: chosen Drive files copied (a fact)

**What is copied.** A sync copies each file chosen for Data room into R2.
- The key is `data-room/<project uid>/<uid>`, under the venture's own prefix.
- A Google file (Doc, Sheet, Slides) is exported to PDF (`files.export`) and named "<name>.pdf".
- A stored file (a PDF, an image) is downloaded as it is (`alt=media`) with its own type.

**How the copy is filed.** It is `data_room_files` with `source_kind 'connector'`, `source_ref 'google_drive'`, NDA and access `nobody`. So nobody sees it until the founder opens it, as Mercury's statements are (D840). The Storage guard (D1170) weighs each copy.

**Replaced only on a new `modifiedTime`.**
- The ledger row `<file id>:copy:<project>` links the copy.
- A re-sync whose `files.get` gives the same `modifiedTime` reads nothing more and changes nothing.
- A new `modifiedTime` replaces the copy in place: the same row, a new object, and the old object deleted.

**A deleted copy stays deleted.**
- Delete (`DELETE /google/facts/:id`) removes the row and its object and keeps the ledger row with no `local_id`.
- A copy deleted in the data room itself is treated the same: the next sync unlinks it first.
- A re-sync never copies either back, even after the file changes.
- Part 2's "Stop using" also unlinks a copy, but keeps it. Re-choosing that file later does not copy it again: the ledger reads it as deleted. This is recorded, not changed here.

**Shown as.** `parts.google.copies` lists each copy with `as_of`, the `modifiedTime` it was copied at: "From Google Drive, as of <date>". `deleted_kept` counts the copies the founder deleted of files still chosen.

**Limits.**
- A document read stays at 2 MB. A copy may be up to 20 MB (`MAX_COPY_BYTES`), and `workspaceRead` refuses a larger `maxBytes`.
- A file Google refuses is marked `unreadable` with its code, and the others still sync.
- A rate limit stops the sync where it is (`partly_synced`), as does a full store.

### 3. Capital relationships: Calendar "last met" (a proposal)

**The read.**
- It uses the member's Calendar grant held today (`calendar.readonly`, `calendar.events` or `calendar`). Without one it says `calendar_not_allowed` and reads nothing.
- It is one GET read, `GOOGLE_CALENDAR_READS['events.list']` on the primary calendar.
- It covers the last 180 days, single events, at most 4 pages of 250.
- `fields` limits it to `items(start,attendees(email,self)),nextPageToken`, so no title or description is fetched.

**What is matched.**
- Each event is reduced in memory to its day and the domains of its attendees other than the member.
- A prospect's firm domain is the domain of the prospect's own address or of their contact's.
- Webmail domains (`FREE_MAIL`) name no firm and are never matched. A passed prospect is left out.
- With no prospect firm to match, the calendar is not read at all.

**The proposal.**
- For each prospect, the latest matching day becomes "Last met <day>".
- It is proposed only when that day is later than the last meeting already logged on the prospect.
- A later day withdraws a pending earlier one.

**Accept** logs a meeting on that day through the pipeline's own writer (`logProspectEvent`, kind `meeting`, note "Met, from Google Calendar"). If the prospect is gone, it is refused in words and the claim is handed back.

**Nothing from an event is stored but its day.**
- The proposal's payload is `{ prospect_id, day }`.
- No address, domain, title or text is stored, returned or logged.
- The test scans every Google table for "@" and for the domains.

### 4. Routes, gates and the module read

| Route | What it does |
| --- | --- |
| `POST /api/cycles/raise/google/sync?project=` | → `{ counts }`. The counts are only `decks_proposed`, `copies_added`, `copies_replaced`, `copies_unchanged`, `copies_kept_deleted`, `files_unreadable`, `last_met_proposed`, `partly_synced`, and a `calendar` or `stopped` code. |
| `POST /api/cycles/raise/google/proposals/:id/accept` | Accept, as §1 and §3. |
| `POST /api/cycles/raise/google/proposals/:id/dismiss` | Dismiss, once. |
| `DELETE /api/cycles/raise/google/facts/:id` | Delete a copy, as §2. |

- **The gates.** Each route passes the module's `scope()`, then part 2's gates through `workspaceContext`:
  - no support session;
  - a member who may write the venture, never an admin;
  - the member's own Workspace connection, enabled for the venture's company.
- **What a route acts on.** Every statement is keyed by that connection and project, so another venture's proposal reads as not found.
- **The module read.** The Pitch deck, Data room and Capital relationships reads carry `parts.google` for that member: the files chosen, the pending proposals and (Data room) the copies.
- **Failures.** It fails on its own ("What Google fed this module could not be read"). A failed sync answers `google_sync_failed` and logs only a code.
