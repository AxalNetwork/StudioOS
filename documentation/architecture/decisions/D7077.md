## D7077 — Agent dispatch throughput: a batch starts together, a model admission budget, dispatch metrics (#7077)

Part of #7077. Once teams may run many agents (#7074), the agent queue's
dispatch, not admission, caps how many runs start. This decision builds the
parts that need no measurement and records what waits for one.

### 1. A queue batch starts together

`agentQueueConsumer` (`cloudflare-worker/src/agents/agentQueue.ts`) used to
start a batch's Workflow instances one after another. It now dispatches every
run in the batch at once (`Promise.allSettled`). Each message keeps exactly
the outcome it had before, on its own:

- not an agent run, a run that is gone or past `admitted`, or an agent that is
  gone: acknowledged;
- started: acknowledged;
- any throw while reading the run or starting it: `retry({ delaySeconds: 30 })`,
  that message only. One failed start never fails, delays or retries another.

Two messages naming the same run in one batch are dispatched once and share
the outcome (before, the second start was a no-op through the existing
instance; now it is not attempted). Acks and retries are applied in message
order after every start has settled.

### 2. A platform admission budget per model

`cloudflare-worker/src/agents/modelBudget.ts`, D1 table
`agent_model_admissions` (migration `202611170939_7077_agent_model_admissions.sql`).

- **The knob.** `AGENT_MODEL_RPM`, a JSON object of model id → agent runs the
  queue may start per UTC minute, `"*"` for any model not named, e.g.
  `{"*": 250, "@cf/meta/llama-3.3-70b-instruct-fp8-fast": 40}`. **Unset, empty
  or malformed means no limit**, which is today's behaviour; nothing in
  `wrangler.toml` sets it, so merging this changes no production behaviour. An
  operator sets it per environment once the figures are chosen.
- **What is counted.** One started run is one request: a run makes its one
  model call in the loop's `run` step. The figure is set from the provider's
  published requests a minute with a margin (Workers AI: 300 a minute for text
  generation by default; 20 or 50 a minute per account for some paid-plan
  models). The gateway lease (D5338, `upstreamLease.ts`) still governs each
  upstream call; this budget only decides when a run may start.
- **Fair share.** Buckets are keyed (model, minute, scope), the scope being the
  team (`company:<id>` / `project:<id>`). A start is admitted while the
  minute's total is under the limit AND the scope's count is under
  `ceil(limit / k)`, `k` being the scopes already started on that model this
  minute, the asker included, and at least `MODEL_BUDGET_MIN_SHARES` (2). A
  lone noisy team therefore takes at most half a model's minute, and once k
  teams are active none takes more than 1/k from then on. The check and the
  increment are one `INSERT … SELECT … WHERE … ON CONFLICT DO UPDATE`
  statement, so racing consumers cannot both take the last slot.
- **A throttled start** is not `retry()`'d — that would spend the queue's three
  retries and the DLQ would end the run `queue_exhausted`. The message is sent
  again with `delaySeconds` to the next minute and acknowledged; if that send
  fails it is retried with the same delay. The sweep's resend of runs still
  `admitted` after 5 minutes remains the backstop. A budget read or write that
  fails lets the start through and counts `agent_dispatch_budget_unavailable`:
  the budget is a throttle, never a reason to fail a run. A start that is
  admitted by the budget and then fails has spent its unit (conservative).
- **Housekeeping.** The five-minute sweep deletes buckets older than
  `MODEL_BUDGET_KEEP_MINUTES` (10).
- **Boundary with #5586.** This is a per-model platform quota protecting a
  provider limit, shared by team only so one team cannot take a whole minute.
  It is not fairness between ventures, admission order, or per-venture
  priority, which #5586 owns; nothing here reads or writes its state.

No route is added.

### 3. Dispatch metrics

Into `system_metrics`, as the sweep and the DLQ repair already write, one batch
at a time. Labels are only `model` (the model id as the knob names it, else
`*`, so its cardinality is bounded by the knob) and `reason` (`model_full`,
`scope_share`); never a run, task, agent, scope, user, prompt or output.

| metric | value |
| --- | --- |
| `agent_dispatch_started` | runs started in the batch |
| `agent_dispatch_admitted_to_started_seconds` | the batch's longest admission → start |
| `agent_dispatch_queue_age_seconds` | the batch's oldest message age |
| `agent_dispatch_start_failed` | starts retried |
| `agent_dispatch_throttled` `{model, reason}` | starts throttled |
| `agent_dispatch_budget_unavailable` | budget reads that failed open |
| `agent_oldest_ready_task_age_seconds` | sweep: oldest ready task (open, ready column, active agent, dependencies done) |
| `agent_oldest_pending_decision_age_seconds` | sweep: oldest run in `waiting_decision`, beside the one above |

The two sweep ages are read every sweep, not only after a discovery scan, so a
backlog of work and a backlog of people's decisions can be told apart. When
there is none, or the read fails, no row is written rather than a zero.

### 4. Deferred, and why

- **Queue sizing.** `max_concurrency = 10`, `max_batch_size = 5` and
  `max_retries = 3` on `studioos-agent-queue` (all three environments) are
  unchanged. New figures must come from #5573's benchmark, not a guess; a test
  in `agent_dispatch_7077.test.ts` holds today's values so the change is a
  deliberate edit with that evidence.
- **The sweep's bounds.** `SWEEP_MAX` (60), `DISCOVERY_SCAN_MAX` (120) and
  `DISCOVERY_PER_SCOPE_MAX` (4) in `sweep.ts` were already named constants and
  keep their values. The per-scope bound follows #7074's elastic per-team
  ceiling, which is not on main; the follow-up edits these constants only.
- **The budget's figures.** `AGENT_MODEL_RPM` stays unset until an operator
  chooses figures per environment from the provider's limits for the models
  actually offered.
