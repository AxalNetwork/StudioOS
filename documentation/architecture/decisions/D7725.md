## D7725 — Market sizing: a source or 'assumption' label on every input, low, base and high scenarios, sensitivity, and overrides with a reason (#7725)

- **Status:** built 2026-11-23 for #7725. Owner questions below were built as option A.
- **Migration:** `cloudflare-worker/sql/migrations/202611232031_7725_market_sizing_scenarios.sql`.
- **Builds on:** D7704 (the sizing version, formula version 2, the gate), D7716 (the observation query and its revision chain), D6011 (`resolveMarketProvenance`), the `market_input` fill and `fill_provenance` (migration 246).
- **Code:** `cloudflare-worker/src/services/marketSizing.ts`, `cloudflare-worker/src/routes/market_sizing.ts`, `frontend/src/lib/api/marketSizing.js`.
- **Test:** `cloudflare-worker/test/market_sizing_scenarios_7725.test.ts`, on the migrated schema. `market_sizing_7704.test.ts` still passes unchanged.

### Why

A sizing version said what the figures were but not where each input came from or how uncertain the result was. This adds both to the version, and stores them so the version can be rebuilt later. Nothing D7704 added is replaced.

### What changed

**The labelled shape.** A save that sends `scenarios` or `top_down` must label every input, in every scenario, with one of four kinds. Otherwise it is refused (`missing_input_source`, with `field` and `scenario`) and nothing is written.

- `observation`: a row of #7716's query, named by its id. The Worker reads it through `readObservation` and copies these fields at save time: value (times its published scale), unit, period, vintage, currency and source name. The id is kept in the indexed `observation_id` column. The value, currency and year come from the row, so a client value is refused (`value_comes_from_source`).
- `market_source`: one of the venture's own `market_sources` rows, checked as `resolveMarketProvenance` checks one. A row of another venture is refused (`invalid_input_market_source`).
- `eadwyn_fill`: the accepted, cited and not undone `market_input` fill that `fill_provenance` holds for this input on this venture. Only `population` and `acv` have one. The Worker copies the figure from the fill's written value, and the citation as it was stored.
- `assumption`: needs a note saying why it applies.

The client sends the value only for the last two kinds. Titles, links and copied values come from the stored rows, and the Worker never picks a kind.

A save in #7704's shape (neither `scenarios` nor `top_down`) is still accepted, and the sizing page still sends it. Its inputs read back with `source_kind: 'not_labelled'`, never `assumption`, and the version read gives their count in `unlabelled_inputs`. In the labelled shape, the sizing inputs and `input_labels` are not also accepted in `assumptions` (`inputs_sent_twice`). The drawer's row is written from base's used values.

**Units.** Every input keeps its formula unit. A money input (`acv`, `tamOverride`, the top-down total) needs a currency. A count or money input needs a reference year, and the version needs `targetYear`.

- An input in a currency other than USD needs a conversion: a rate, the rate's date, and the rate's own source (any kind but a fill). Both the original and the converted value are stored. Without a conversion the save is refused (`missing_currency_conversion`).
- An input whose year differs from the version's needs an adjustment factor with its own source, or `unadjusted: true` with a reason. Without one the save is refused (`missing_year_adjustment`).
- `revenue_basis` (`annual` or `cumulative`) is required in the labelled shape and optional in #7704's. It is stored on the version and returned.
- The formula reads `revenue_basis`. `cumulative` means revenue per account is the total over the time horizon, so the formula makes it annual: value × 12 ÷ horizon months. A 0-month horizon is then refused. The figures stay annual, so the version's `som ≤ sam ≤ tam` check holds.
- When `revenue_basis` is absent, the input reads as annual, as formula version 2 always read it.

**Scenarios.** A version holds base alone, or low, base and high (`invalid_scenarios` otherwise). Each scenario is a complete input set a person enters; none is generated, scaled or copied from base. Base stays the `market_sizing_versions` row and its `market_sizing_version_inputs` rows, and only base writes the project's figures and `market_figures`. Low and high are one row each in `market_sizing_scenarios`. Every estimate of every scenario is a row in `market_sizing_input_estimates`. All of it is one `DB.batch`, written together or not at all. A low figure above base, or a high figure below it, comes back in `order_flags` and is not refused.

**Sensitivity**, computed on read and never stored (`GET …/versions/:uid/sensitivity`, and `sensitivity` on the version read). Each base input is moved to its low value and then its high value, with the other inputs at base. Inputs are ranked by the absolute change in SOM. A base-only version answers `available: false` with the reason, never a list of zeros.

**Overrides.** The override is formula version 2's TAM override, now allowed in each scenario. It is a labelled input like any other, and its reason is `tam_override_reason` on the scenario. Without a reason it is refused (`missing_tam_override_reason`). It is stored beside the computed TAM, and the version returns both. When base carries one, the project's TAM is the override, and its figure rows record method `typed`, as D7704 already did.

**Conflicting estimates.** An input may hold up to five estimates, each with its own source. Exactly one is marked `used`, with `used_reason` (`missing_used_estimate` otherwise). The formula reads only the used one, and every estimate is stored.

**Top-down check.** `top_down` is optional. It is one total in millions, labelled by the same four kinds. It is stored as `top_down_tam` and `top_down_gap` (top-down minus bottom-up TAM) beside the bottom-up figure. It is never blended into the figures and never written to the project.

**Superseded evidence.** On read, each estimate whose observation (or whose conversion or adjustment observation) has a later vintage in #7716's revision chain is flagged with `superseded` and `superseded_by` (the newest id, vintage and period). The saved value does not change. `supersededSizingEvidence(env, projectId | null)` in `services/marketSizing.ts` is the exported read #7726 uses to list the versions affected. `GET /projects/:projectId/superseded` returns it for one venture.

**Limitation.** Every version read carries `limitation`. It says the formula does not handle overlapping segments or organisations with several locations.

**Schema (migration 202611232031).** Only tables and nullable columns are added.

- New columns on `market_sizing_versions`: `revenue_basis`, `top_down_tam` and `top_down_gap`, guarded by their own append-only trigger.
- New tables: `market_sizing_scenarios` and `market_sizing_input_estimates`. Each has an append-only trigger, a cascade from the version, and a partial unique index that allows one used estimate per input and scenario.
- The only reference that may go NULL is an estimate's `market_source_id`.

**Access.** The new routes and the labelled POSTs use #7704's gate, `canEditProjectData`, checked before anything is read. Each new refusal has its own code and sentence in `SCENARIO_REFUSALS`. No page test collects refusal codes from the route file.

**A version saved before this change** is never rewritten. It reads `revenue_basis: null`, `top_down: null`, base only and `not_labelled` inputs, and it recomputes to the same figures (tested on a row written exactly as #7704 wrote it).

### Open questions for the owner (built as A)

1. **Overrides.** **A (built):** the TAM override, per scenario. B: a typed override for SAM and SOM as well, stored beside each computed figure.
2. **Cumulative revenue.** **A (built):** `revenue_basis` says how revenue per account is entered, and a cumulative figure is made annual over the horizon. B: SOM itself is reported as revenue over the horizon. This needs its own check, because SOM could then exceed SAM.
3. **Reference years.** **A (built):** a count or money input states its year, and an observation's year comes from its period. B: an input without a year takes the version's.
