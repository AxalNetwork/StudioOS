### What the pass does

The seed adds one published HQ skill, with one version pinned at version 1 to the synthetic agent. It has the agent's
own role (`ceo`), no tools and synthetic text. Its uid carries the run's mark.

**The path.** After the Workflow path and the plain manual run, the sponsor runs that skill on the manual sponsor-run
route (`POST /agents/:uid/run` with `skill`), three times, and accepts each proposal:

1. On the deployed Worker, with the legacy loader (no variable).
2. After a redeploy that adds only `AGENT_SKILL_RUNTIME = "cloudflare_sdk"`.
3. After a redeploy that removes it again.

It uses the manual path because a Workflow-path run uses a skill only for a session-sourced task (`sessionSkill`,
D4534), and seeding a session would test the session machinery rather than the runtime choice.

**What each run must show (`skillRunVerdict`):**

- exactly one usage row;
- that row on skill version 1, the pinned version and never the current one;
- the runtime it asked for. The run event's `skill_runtime` must be absent for legacy and present for the SDK.

A recorded SDK fallback (`sdk_version_unsupported`, `sdk_error`, …) is a result. It is reported, not hidden. Anything
unreadable fails the run.

**The redeploy changes one line.** A test holds the flat config to differ only by
`AGENT_SKILL_RUNTIME = "cloudflare_sdk"`, so every identity the #4566 preflight passed stays the same. The variable is
set only on the throwaway Worker; production's var blocks never name it, and `skillEngineOf` answers legacy there
anyway.
