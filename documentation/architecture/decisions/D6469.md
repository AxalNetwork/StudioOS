## D6469 — One sorted landing list for the owner, and the measured tier share (#6469)

Part of #5600, plan key E1. D5605 row 6 decided that T0/T1 PRs land
automatically and the owner lands T2. Nobody had measured how many PRs fall
in each tier, and the owner found the green PRs among a hundred-odd open ones
by opening them one by one.

**What it is.** `scripts/landing-list.mjs` with its pure half
`scripts/lib/landingList.mjs`:

- **Default.** Open, non-draft PRs whose required checks all pass on the
  current head SHA. For each: tier, mergeable state, age, files changed and a
  direct link. A PR whose required check is pending, missing, failed or
  unreadable is not listed. Neither is one whose base has no readable required
  set, or a draft (on the list read or the detail read). Each is counted under
  its reason, so a missing PR never reads as green.
- **Tiering** is `merge-policy.mjs`'s `classify` (D5607), fed the REST files
  endpoint's rows: added, modified, removed, renamed and copied map to
  A/M/D/R/C, and any other status stays unknown, which `classify` makes T2.
  The REST rows carry no file mode, and a binary diff has no patch. So the
  link/submodule and binary rules cannot fire here, and the `landing policy`
  check on the PR stays authoritative; the list says so.
- **Mergeable** is `prRisk.mjs`'s `mergeStatus` (D5580). An uncomputed state
  reads `unknown`, never `clean`.
- **Order.** The owner-lands group comes first: T2 PRs, and PRs carrying
  `bot:resolved` or `main-repair`, marked "model-changed, owner lands" at any
  tier. T0/T1 PRs follow. Inside a group, PRs that overlap keep the overlap
  report's suggested sequence (`prOverlap.mjs` `clusters`, D5616). Clusters
  and single PRs sort by the same rule, `order()`: ready, fewer files, lower
  number.
- **`--history[=N]`** classifies the last N merged PRs (default 300, newest
  merge first; a closed unmerged PR never counts). It reports the T0/T1/T2
  share and the T2 rules matched most often, counting a PR once per rule
  (`protected path`, `existing test or fixture`, `unmatched path`,
  `Timeout changed`, ...).
- **`--sticky`** writes the list into one issue authored by
  `github-actions[bot]` whose body starts with
  `<!-- studioos-landing-list:v1 -->`. It edits that body in place, creates
  the issue once when none exists, and makes no write when the body is
  unchanged. A marker in someone else's issue is ignored.

**Where it runs.** One step in the hourly `pr-overlap.yml`, after the overlap
report. That job already holds `issues: write`, so no permission changes.
GitHub access is `pr-overlap.mjs`'s bounded `gh api` client (`makeApi`),
capped here at 1,500 requests and stopping when the remaining quota drops
below 100. A capped or failed read marks the list partial. The step never
fails the workflow.

**What it never does.** It never labels, reviews, merges, queues or enables
auto-merge (test: the CLI's only write is the sticky issue). D5616 stays true
for the overlap comments. Queueing is #6481 (E2). The tier rules do not
change here.

**After merge.** The tier share over 300 merged PRs and the top T2 rules go on
#5600, as input to the owner's decision on the T2 list. They are measured with
`node scripts/landing-list.mjs --history`, or by the same lib over the same
REST rows. The sticky issue exists after the first hourly run on `main`, and
the next run edits it in place.
