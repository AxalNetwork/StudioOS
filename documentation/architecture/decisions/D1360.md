## D1360 — Record a Session: Eadwyn AI joins a call by default

- **Status:** decided by the owner, 2026-10-28 ("Eadwyn joins by default"), and built by S21 for S1.
- **Migration:** none.
- **Builds on:**
  - D886: Eadwyn AI, the meeting bot;
  - D1346: Create the meeting for me;
  - D1358: a meeting is captured by the platform, never by the browser.

### 1. Why

The owner created a Zoom call in Record a Session, held it, and ended it, and nothing reached Axal. Production showed why:
- **No bot run had ever been made.** The dialog saved the call for import instead, because the site did not report Eadwyn AI as available for Zoom.
- **Zoom had never sent Axal an event.** `channel_events` held no Zoom row, so the call's end and its cloud transcript never arrived.

The import after the call depends on the host's plan and settings: Zoom cloud recording with audio transcripts, or Meet transcription on a Workspace edition. Teams has no import at all. Eadwyn AI is the one capture that works on every plan of all three platforms, and it needs nothing done when the call ends.

### 2. The rule

**When Eadwyn AI is deployed for the call's platform and enabled for the member, it joins every call saved or created in Record a Session.**
- **The dialog:** Start already sends Eadwyn AI when the bot read says it can join (D1358). It no longer falls back to "Save for import after the call" while that read is still out: a link the bot can join waits for it.
- **The Worker:** a call saved for import also sends the bot, so the default holds even when the dialog's read was stale or unreadable. This covers a hosted Zoom call (`attach` with no session) and a Meet call from Calendar. Scheduling already did this (`auto_send_bot`, D886 B7).
  - The member opts out per call with `auto_send_bot: false`.
  - A call already over gets no bot.
  - A call still to come is scheduled for its start; one under way is joined now.
- **The import stays as the second path.** The saved call keeps its import ref, so Zoom's or Meet's own transcript is still taken when it comes.
- **Never a refused save.** A bot that cannot be queued (budget, limits) is reported beside the saved call as `bot_error`, in the bot's own words. With no bot deployed, the reply carries `bot: null` and `bot_error: null`.

### 3. What the owner sets up

These are configuration steps, not code:
- **For Zoom,** the site needs `MEETING_BOT_ZOOM_CLIENT_ID` and `MEETING_BOT_ZOOM_CLIENT_SECRET`, which belong on the `studioos` Worker (PRODUCTION.md, "Owner-only first deployment", step 3). Without them, `GET /meetings/bot` reports Zoom as false.
- **For the import's Zoom events,** the Zoom app's Event Subscription must point at `https://axal.vc/api/channels/zoom/webhook`, with the meeting-ended and recording events. Its Secret Token must equal `ZOOM_WEBHOOK_SECRET_TOKEN`.

### 4. Tests

- **Worker:** `meeting_capture_d1358.test.ts`, three new D1360 tests:
  - a saved Zoom call queues the bot, and `auto_send_bot: false` keeps it out;
  - with no bot deployed, the call is saved only, with no error;
  - a Calendar Meet call under way queues the bot now, and one already over gets none.

  Turning the default off fails two of them.
- **Frontend:** `record_meeting_capture_d1358.test.mjs`: while the bot read is out, a connected call waits instead of saving for import.
