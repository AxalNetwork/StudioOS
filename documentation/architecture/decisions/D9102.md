### 1. The read: `GET /api/cycles/build/plan/fed?project=&scope=`

- **Who:** the venture's founder only. It goes through `scoped(true, …)`, the same gate as the link writes. A partner, an admin and another founder get `not_this_project` (404). A signed-out caller gets `unauthorized` (401). A bad project or scope gets `invalid_project` (400). A store failure gets `unreadable` (503). These are the router's own `{ code, detail }` bodies.
- **Which rows:** `connector_fed_items` for the venture where `kind` is `issue` or `pull_request` and `external_id` is a GitHub key (`issue:owner/repo#n`, `pull:owner/repo#n`; `FED` checks it again).
- **Left out:** every item that is the `source_ref` of a `link:build/plan` proposal that is `proposed` or `accepted`. These are exactly the items `linkByHand` refuses as `already_linked`. An item whose proposal was dismissed ("Not this one") is listed again, because it then lands as its own row.
- **One row per item:** the ledger is unique per integration, not per venture, so a GitHub reconnect can hold one item twice. The read keeps one row per `external_id`. It takes the ledger row that has a local row, else the newest, plus the newest `last_seen_at` and the first `first_seen_at`. `total` counts distinct items.
- **Titles:** `roadmap_okrs.objective` for an issue's row, `mvp_features.title` for a pull request's, each joined on this venture's `project_id`. A ledger row with no local row, or one naming another venture's row, returns `title: null`.
- **Order and size:** newest `last_seen_at` first, at most 200 (`UNMARKED_MAX`), with `total`.
- **Shape:** `{ items: [{ fed, fed_kind, title, local_table, local_id, first_seen_at, last_seen_at }], total }`.
- Logs nothing of its own. The router logs only the failure code.

### 2. The board (VB9's fourth row)

- **The fifth read** is `buildPlanApi.unmarked`, only for the founder (`actions`). It answers alone and never blanks Progress.
- **The door** opens for waiting proposals **or** unmarked items. Its count adds the two, and its sentence stays "Arrived from your tools · N. Nothing is linked until you press Link."
- **The rows:** one per unmarked item, after the proposals. Each has "Connector · GitHub", "Pull request #15 ‘[title]’ · no plan marker." (or "Issue #9 · no plan marker." with no title) and **Link to a plan item…**.
- **"Not this one" is not offered** on an unmarked row. The item already landed as its own row, and no route dismisses it.
- **The picker is inline,** a list under the row and not a second dialog. One picker is open at a time.
  - It holds the accepted, landed items from the plan read (the `sendable` rule: decided, landed, never a door), grouped by module, each with its kind and title. Nothing is chosen at first, and Link stays disabled until one is.
  - **Link** calls `linkByHand(itemUid, fed)`. **Cancel** closes the list.
  - With no accepted item, the list says "No accepted plan items yet. Accept one on the plan first." and offers no Link.
- **After Link:** the row says "Linked to [kind] [title]." and Progress reads again, so the item's In progress shows "GitHub · pull request linked [day]". The drawer keeps the linked row with its line after the new read leaves the item out.
- **A refusal** stays on its row in the Worker's own sentence (`already_linked`, `not_accepted`, `not_this_project`), and the picker stays open.
- **More than 200:** the drawer's foot adds "Showing the newest 200 of [total]."
- **Loading:** the drawer shows "Reading…" for the unmarked list while it loads. The page does not wait for it.
- **A failed read:** "GitHub items without a marker could not be read. This is not a claim that none arrived." with Retry. It shows inside the drawer when there is a door. With no proposals and no door, Progress shows the same line above the chart, as it does for its other failed reads, so the failure is never silent.
- Opening the drawer or the picker writes nothing.
