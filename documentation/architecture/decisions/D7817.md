## D7817 — Research Project: attach a saved analysis version as a frozen copy, and let a finding cite a source of it (#7817)

- **Status:** built 2026-11-21. Backend, client module and citation labels; the attach action and the finding picker are #7853.
- **Builds on:** D5157 part 2 (`D5157-p2.md`, the findings store) and D7176 (saved competitor-analysis versions). The four findings files were handed over from #5157 in https://github.com/AxalNetwork/StudioOS/issues/5157#issuecomment-7026662658.
- **Migration:** `cloudflare-worker/sql/migrations/202611211307_7817_research_project_attachments.sql`.

### Why a copy

A saved competitor analysis could not reach a Research Project. A finding could cite only a passage from one of the project's Ask answers, or a document in its evidence. Citing the live analysis would not hold either:

- only superseded versions are stored (`competitor_analysis_versions`);
- a refresh changes sources without a new version;
- deleting an analysis deletes its versions.

So attaching copies one version into the project, and the copy never changes afterwards.

### Built

1. **The store.**
   - `research_project_attachments` holds the project, owner, kind, the attached object's id and version, a title, the copy (`copy_json`) with its format number (`copy_format`, now 1) and when it was attached. It has no reference to `competitor_analyses`, so deleting the analysis keeps the copy. One row per project, kind, object and version. It is not `research_attachments` (migration 222).
   - The kind is checked against `ATTACHMENT_KINDS` in `services/researchProjectAttachments.ts`, which holds one kind, `competitor_analysis`. The table has no constraint on kind.
   - `research_project_finding_citations` gains nullable `attachment_id`, `source_key`, `source_url` and `retrieved_at`. `research_project_findings` gains nullable `attachment_id` and `attachment_finding_n`, with a partial unique index that keeps one decision per generated finding per attachment. Every change is additive.
2. **The copy** (`buildCopy`, format 1) holds the title, version, saved date, subject (its directory uid and name as read at attach time, or `not_found` / `unreadable`), the output sections, the generated findings with the source keys they name, the competitors, and each source's link, title, kind, fetch status, whether it was fetched (`sourceFetched`, the analysis's own rule) and retrieval date. The service reads the stored rows itself; `routes/competitors.ts` is not edited or imported.
3. **One access decision.** `mayReadAnalysis(owner, caller)` decides both a read of the stored analysis and a read of an attached copy: the owner is the caller. Attaching widens no one's access. Anything else reads as not found.
4. **Worker routes** (`routes/research_project_attachments.ts`, self-mounting at `/api/research/projects`). Every path is `/:uid/attachments…`. The router declares no static first segment and no `before`, so `/with-study`, `/with-comparison` and `/briefs/saved` keep answering from their own routers. The route test shows this for `/with-study` and `/briefs/saved`; the per-project count read of #7726 is not on main.
   - `POST /:uid/attachments { kind, object_id, version }` attaches a completed analysis the caller owns, at its current version or a kept earlier one (201, `created: true`). Anything else is 404 `analysis_not_found`. The same project, analysis and version again returns the attachment on record (200, `created: false`), including after the analysis is deleted.
   - Caps: at most 20 attachments per project (409 `attachment_limit`, checked inside the insert), and a copy of at most 256 KB (413 `copy_too_large`).
   - `GET /:uid/attachments` lists them without the copy's body. `GET /:uid/attachments/:attachmentUid` returns one with its copy. `DELETE /:uid/attachments/:attachmentUid` detaches one.
   - Owner-scoped through `checkProjectOwner`. An archived project refuses writes (409 `project_archived`) and a support session cannot write (403 `support_read_only`). It can still read.
   - Receipts `research_project_attachment_added` and `_removed` carry the project, attachment, kind, object id and version, and no research text.
5. **Citations** (`routes/research_project_findings.ts`; exported names and shapes as on main, the new fields additive).
   - `{ attachment_uid, source_key }` is accepted only for an attachment of this project and a source its copy records as fetched. Anything else is still 400 `citation_not_in_project`.
   - The citation is stored frozen: the copy's title for the source (or its link), its link and its retrieval date.
   - No passage is recorded for an analysis source yet (#7839), so `passage` stays NULL. A source fact citing only an attached source is still 400 `passage_required`. An attached source can back a conclusion or a taken-over finding.
   - The findings read gains, per citation, `kind` (`document` or `analysis_source`), `state`, `attachment_uid`, `source_key`, `url` and `retrieved_at`. For an attached source, `availability` and `state` are `attached`, or `attachment_removed` after a detach, never `not_recorded`.
   - Each item gains `attachment_uid` and `attachment_finding_n`. The read never selects the copy's body.
6. **A generated finding taken over from an attached version.** `POST /:uid/interpretations/attachments/:attachmentUid/:n { decision, text? }` decides on generated finding `n` of the copy. It is stored as `kind = 'interpretation'`, exactly as an Ask interpretation is:
   - the generated words are kept in `proposed_text` beside any edit, and the state is accepted, edited or discarded;
   - a new decision updates the one row, and a decision cannot be deleted or edited as text;
   - the fetched sources the generated finding names go with it as frozen citations;
   - a blank generated finding is 409 `nothing_to_interpret`.

   It is never stored as the member's own conclusion. So #7720's rule (a discarded interpretation cannot be linked) and #7727's label for an interpretation apply to it unchanged.
7. **Detach** keeps every finding and its frozen citation. It clears the links to the gone copy itself, in one batch, without leaning on the foreign keys. Detaching, or any change of a citation's state, never writes a finding's `updated_at`: #7726 lists a finding whose text changed since it was linked, and a detach is not a change of text.
8. **Client and labels.** `frontend/src/lib/api/researchProjectAttachments.js` holds attach, list, get, detach and decide. `researchFindings.js` gains the labels From an attached analysis and Attachment removed, a note for a detached copy, and the source's link and retrieval date on the citation panel. So no page calls an attached source "Source not recorded". `ProjectFindings.jsx` is not edited.

### Owner question

Q1, how is a taken-over generated finding carried?

- **A:** as an interpretation that keeps the generated text.
- **B:** it is not carried; only the member's own conclusions cite an attached source.

The owner answered **A** on 2026-11-20 (https://github.com/AxalNetwork/StudioOS/issues/7817#issuecomment-7049957114). A was built.

### Boundary with study references

A study's pointer to a competitor analysis is #7724's reference kind in `research_study_refs` (#7721): a live pointer, read under the analysis's own access rule. This decision stores the copy a finding cites. Attaching writes no study reference, a study reference creates no copy, and the attachment list reads only `research_project_attachments`. Both name the analysis by its id and its saved output version number, and this decision does not change what that number means.

A finding and its frozen citation (link, title, retrieval date) are project content and travel where findings travel. The copy's body never enters a report.
