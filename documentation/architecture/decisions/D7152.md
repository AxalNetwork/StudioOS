## D7152 — Automatic rollback after a failed post-deploy smoke, off by default, report before act (#7152)

**Decided.** A production release whose live smoke fails, and fails again on one retry, may be returned to the Worker version the release recorded before it wrote anything (D7151), but only when the D7151 classifier called it `auto` or `auto-additive` (owner decision E1 on #7144). One repository variable, `RELEASE_ROLLBACK_MODE`, governs it, and it is off by default: unset, or any value other than exactly `report` or `act`, skips the whole path. `report` does everything except the rollback and logs "would roll back to `<version>`"; `act` performs it. This pull request sets no variable. The owner moves to `report`, and then to `act` after reading the report-only decisions of at least ten releases.

**The decision** (`scripts/lib/releaseRollback.mjs`, pure apart from injected effects):

| Situation | Decision |
| --- | --- |
| mode off | nothing; no smoke, no Cloudflare or GitHub call |
| `spa-smoke` passed, or did not finish (cancelled, skipped) | nothing |
| it failed, and the one retry passed | nothing: flaky, a single failure never rolls back |
| failed twice, class `manual` or unreadable | alert with the class's reasons and the DEPLOY.md §3 fix-forward; never rolled back, in either mode |
| failed twice, this commit was already rolled back automatically | page: one automatic rollback per release |
| failed twice, whether it was rolled back before is unreadable | alert, no rollback |
| failed twice, no usable recorded version, or the published or live version unreadable | alert, no rollback |
| failed twice, the live version is not the one this release published | alert: a newer release or a person moved it, nothing to undo |
| failed twice, safe class, mode `report` | "would roll back to `<version>`" |
| failed twice, safe class, mode `act` | `wrangler rollback <version>`, then the smoke against the restored version; a failed rollback or verification pages and stops |

Every alert and summary names the commit, the class, the version published, the version restored (or that would be) and the smoke rows that failed on the retry, and says that the next `main` commit releases normally and carries the same change unless a revert or a fix has landed.

**Where it runs.** A new `rollback` job in `cloudflare-worker-deploy.yml`, after `spa-smoke` (`needs: [deploy, spa-smoke]`), skipped unless the variable is `report` or `act`. It takes the `production` environment's credentials (#7145) and the `studioos-production-release` lock, so it cannot interleave with a newer release. It reads the deploy's evidence artifact: `rollback-class.json` (class and target, D7151) and `outcome.md` (the published version's "Current Version ID"). Its decide step is `continue-on-error` unless the mode is `act`, so `report` can never turn a release red. The retry and the verification run `scripts/check-spa-live.mjs` with the same hosts and manifests as `spa-smoke`. The verification checks the previous build's manifest as the current build and, when D7151 recorded the restored version's commit, expects that sha.

**No loop.** An `act` rollback uploads the artifact `release-rolled-back-<sha>` (kept 90 days). In `act` mode only, the deploy job's step "Hold a commit automatic rollback took off production", after the last admission check and before the D1 migrations, refuses to publish that commit again unless a dispatch sets the new boolean input `republish_rolled_back`. If the marker list cannot be read, the gate publishes with a warning and the rollback job then refuses a second rollback.

**The retention ledger (DEPLOY.md §2.1).** After an `act` rollback the job restores the asset cache this release saved, makes the restored build generation 0 of the ledger with a fresh `deployedAt` (it ships again now), and saves the result as a newer `spa-assets-…-rolled-back` entry, which the next deploy restores. The rolled-back build stays in the ledger with its own `deployedAt`, so the 72-hour window keeps its chunks for tabs opened while it served. The restored build is found by the entry chunks `capture-spa-previous.mjs` recorded before the build. When it is already generation 0 (the release changed no asset), or is not in the ledger (retention restarted), the ledger is left alone and the log says why.

**Not built.** Reverting D1, reverting the commit on `main`, gradual rollouts, staging. The Slack release thread and the production-release failure issue (#6387) are not yet given the decision directly: a page fails the job, which the failure reporter already sees, and an alert is an error annotation beside the already-failed smoke. The ten-release report-only qualification remains open on #7152.

**Verified.** `scripts/lib/releaseRollback.test.mjs` runs the whole path against a faked deploy and smoke for each branch: safe class failing twice in `report` and `act`, `manual`, a flaky single failure, a failed verification, a failed rollback, a re-run of a rolled-back commit, a superseded release, the three modes, the re-run gate, the ledger rewrite through `planAssetRetention` and `entriesFromLedger`, the command, and the workflow wiring.
