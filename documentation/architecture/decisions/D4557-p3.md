## D4557 part 3 — Approved Durable Object scheduling for general compute (#4557)

The owner selected B on 15 November 2026 (issue comment 6893943352): use
`durable_object` in a reviewed follow-up configuration. This supersedes the
original default-policy selection for new applications. It does not authorize
preview application creation, deployment, image publication or production use.

Both disabled preview applications and the host policy variable now select that
policy. Their `runtime` named images replace the default-only `image`,
`image_build_context`, `instance_type` and `max_instances` application fields.
The host rejects the old or missing policy before native startup and continues
to require the exact admitted image digest and `enableInternet: false`.

The current runtime does not accept `basic` as a Durable Object startup alias.
Python preserves its prior resource ceiling with an explicit custom instance:
0.25 vCPU, 1024 MiB memory and 4000 MB disk. Documents retains `standard-1`.
Actual account entitlements, resource metering and native enforcement remain
preview acceptance gates. No larger instance or fleet is authorized here.
The policy has no application `max_instances`; existing broker scope/global
admission quotas remain essential, alongside the provider account limits.

The owner-only, independently protected preview workflow renders its configuration
with `render-agent-compute-preview.py`. The renderer refuses mixed policies,
enabled/public hosts, unexpected applications/bindings, legacy fields, wrong
accounts, floating or mismatched images and non-preview service names. It writes
local JSON only. The workflow still verifies signed GHCR source provenance for
the exact main candidate. The runtime's named image must instead be a pre-published
Cloudflare managed-registry copy, in the approved account with the identical
immutable manifest digest. Copy/publication and its verification belong to the
approved image pipeline/operator; this workflow does not perform that copy.

No migration is needed: the existing SQLite-backed classes are retained. No
production binding, routing, privilege, admission switch or live resource is
changed. Application scheduling cannot be mutated after creation; any existing
default-policy application must be separately inventoried and reviewed for
replacement, never silently repurposed. Disabling remains the immediate rollback;
do not deploy the old policy onto a newly created durable-object application.

Behavioral fixtures invoke the actual local renderer and native adapter with
synthetic data. Type generation, dry-run packaging and local tests establish
source/configuration compatibility, not hosted isolation or measured capacity.
Owner-run end-to-end preview acceptance and different-vendor review remain open.
