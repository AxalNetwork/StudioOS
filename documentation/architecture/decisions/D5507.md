## D5507 — One hand-written contract per catalogue: Build's connector parts and the storage areas (#5507)

- **Status:** built 2026-11-15 by S33. Part of #5398.
- **Why:** #5417 changed Build's task composition and two provider suites
  (Vercel's, Google's) held the same full provider list, so #5493 had to
  repair both after merge. The storage-area catalogue was read out of
  `services/storageUsage.ts`'s own source by a frontend test, so the
  catalogue checked itself: the Worker counted `grow_voice_notes` (D5332) and
  `agent_compute` (D4557) while the Usage card listed neither, and the
  Storage page had no place for `grow_voice_notes`. Nothing failed.

### The decision

Each catalogue has exactly one expected contract, written by hand and never
derived from the production registry, so a registry and a renderer that
agree on the same mistake still fail.

| Catalogue | Contract | Held by | Contractual |
|---|---|---|---|
| Build's connector parts (`pages/cycles/buildParts.jsx`) | `CONTRACT` in `frontend/test/build_parts_contract_5507.test.mjs` | that file: `BUILD_PARTS` and `buildPartsMap()` | modules; each module's complete list, **in order** (the canvases' order); every part built and drawn in its own boundary. Access is not this catalogue's: no part is role-gated in `buildParts.jsx`. |
| Storage areas (`GET /api/usage/storage`) | `frontend/test/_storageAreasContract.mjs` | `frontend/test/storage_areas_contract_5507.test.mjs` (Usage card, Storage page places and kinds, ROUTE_MAP) and `cloudflare-worker/test/usage_storage_d1169.test.ts` (the read) | membership; each area's kind; where its file opens; the six kinds' order; ROUTE_MAP names each key. The order of areas is **not** contractual. |

**Provider suites own only their provider.** A Build provider's suite asserts
the modules its key sits on, its position relative to the neighbours its own
canvas names (before/after, never adjacency or a full list), and what its
render function mounts, through `frontend/test/_buildParts.mjs` (the
registry's exports, not its source text). PostHog's suite keeps "last on each
module", because D1606 says so of PostHog itself.

**Who updates a contract:** the task that adds, removes or moves a part or an
area edits the contract in the same PR, once. A legitimate addition changes
no other test. Removing a required entry, reordering a contractual order or
breaking one provider's mount fails the contract or that provider's suite.
Each contract file's header records the replay that showed this.
