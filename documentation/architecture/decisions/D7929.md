statement and robot policy must be read and recorded before the source is enabled.

### Why the company-concept API

It returns one concept for one company, so a batch is a few small, bounded responses rather than a company's whole
`companyfacts` file or a bulk archive, and each response lists every filing that reported each fact, which is what
restatement provenance needs. It needs no key. `frames` was not used: it keeps only the last-filed fact per entity and
period, so it cannot say what an earlier filing reported.

### Identification and pacing

The User-Agent comes from one env binding, `SEC_EDGAR_USER_AGENT`, set by an operator: printable ASCII, a name and a
contact address. **No value is in code**, not even a default: until it is set, every batch is refused
`sec_edgar_identity_not_configured` (409) before any run is recorded or any request sent. The tests use an invented
`example.org` identity, and a test fails if the importer contains any other email address. The market-intelligence
contact default (`MI_CONTACT_EMAIL`, `market_intel/sources/_live.ts`) is deliberately not reused.

A batch sends one request per concept, at most four, one at a time and at least 125 ms apart (at most eight a second,
under the ten the SEC publishes). There is no schedule here; #7930 owns refresh.

### What a row says

| Field | Value |
| --- | --- |
| entity | `geography_type` `ecosystem`, `geography_code` `CIK##########`; the entity name and CIK in `metric_label` and `applicability_note` |
| fact identity | key `edgar:<cik>:<taxonomy>:<concept>:<unit>:<start>:<end>` (instants have an empty start) |
| taxonomy and concept | in the key, the series (`EDGAR.<cik>.<taxonomy>.<concept>.<unit>`) and the label; metric `edgar_<id>` |
| period | `period` is the year of the period's end; the exact start and end are in the key and the applicability note |
| unit and currency | the unit key as reported (`USD`, `EUR`, …), also `currency`; `scale` `units`, `price_basis` `current_prices`; never converted |
| accession and filing date | `vintage` is the accession that first filed the current value; `published_at` its filing date; the form in the note |
| retrieval date | `retrieved_at`, set by the writer |
| restatement | `limitations` ends with "Restated: this value replaces X first reported in accession A (form, filed D)" for up to three earlier values |
| `statistical_unit`, status | `enterprise` (the registrant as it reports, consolidated where it consolidates); `actual` |

Concepts: `revenues` (us-gaap:Revenues), `revenue_from_contracts`
(us-gaap:RevenueFromContractWithCustomerExcludingAssessedTax), `operating_income` (us-gaap:OperatingIncomeLoss),
`net_income` (us-gaap:NetIncomeLoss), `assets` (us-gaap:Assets, an instant) and `ifrs_revenue` (ifrs-full:Revenue).
Only annual forms (10-K, 10-KT, 20-F, 40-F and their amendments), annual durations (350 to 380 days) or period-end
instants, and currency units are read; quarters, 8-K and registration-statement figures, per-share units and a
duration under a balance concept are not.

**Never a market size.** A company's revenue is its own, for its own reporting scope. Rows are stored under the
registrant, not a country or region, so the country page, a geography filter and `coverageOf` never return one as a
national or market figure (a test asks coverage of `edgar_revenues` for `USA` and gets `no_observation`). Every row's
limitations and every catalogue definition say it is not a market size, share or industry total. The source is not
exportable until the owner says so.

**Not the other EDGAR code.** The filings-count index connector (`market_intel/sources/sec_edgar.ts`) and the ticker
directory (`scripts/import-sec-edgar.mjs`, `scripts/lib/secEdgarCompanies.mjs`, `services/listedCompanies.ts`) are
neither imported nor read; a test fails if the importer imports any of them.

### Editions and restatements

For each fact the reader takes every annual-form filing that reported it, in filing order (accession breaks ties). A
change of value starts a new edition; a later filing that repeats the value (next year's comparative column) does not.
The current edition is stored, with the accession that first filed it as its vintage. So:

- a replay inserts nothing (the writer finds the same key and vintage unchanged);
- a restatement filed after an import adds one row with the amendment's accession, which supersedes the stored one
  through the writer's revision chain; the original row stays;
- a first import made after a restatement stores the restated value and names the original in its limitations.

### Missing, zero and conflicts

A fact with no value, or a null one, stores no row (`missing_value`); a reported `0` is stored. A concept the company
never tagged (HTTP 404) stores nothing and counts `not_reported`; the batch continues. A unit that is not a currency
counts `unknown_unit`. One accession giving two values for one fact stores nothing for it (`conflicting`). A response
for another CIK, taxonomy or concept, a malformed fact (date, accession, form), a body that is not JSON, any other HTTP
error, a transport error, a response over 5 MB, or more distinct facts than the writer's 40 fails the **whole** batch:
nothing of it is written, the stored rows keep their last good values, and the run and source carry the classed
failure (`provider_http HTTP 500`, `provider_payload`, …) with the earlier `last_success_at` kept.

The report adds `skipped` (the four counts above), `restated` (rows carrying a restatement) and `requests` to the
writer's run receipt. A batch is at most four requests and 40 cells.
