## D5207 — Durable outbound Calendar copies (#5207)

Calendar write hooks persist one intent per member, provider and source before
attempting a copy. The intent contains a source reference, a UTC lookup day
and operational state. Event content and credentials stay in their existing
stores. A retry reads the source through the member's Calendar reader and
checks the copy preference again. An unreadable preference cannot authorize
a new external copy, and an existing mapping can still receive updates.

D1 claims each due intent with a lease. A generation fences completion of
work superseded by a reschedule or cancellation. Google receives a stable
event ID and reconciles a create conflict with a patch. Microsoft receives
a stable transaction ID on create. Both keep the provider event ID in
`calendar_sync_records` for subsequent updates and deletes.

The existing scheduled Worker sweeps due jobs in bounded batches. Temporary
failures back off and stop after six attempts. Credential refusals park until
the affected provider reconnects. Cancelling marks the job before deleting
mapped copies. A successful write that finishes during cancellation hands
its mapping to the same delete path, including the existing delete retries.

Google Calendar writes also back off for HTTP 403 responses carrying
`rateLimitExceeded` or `userRateLimitExceeded`. A copy preference that
excludes the provider stops retries with `refused / not_selected`. A later
authorized booking update can requeue that job, including legacy rows
recorded as `cancelled / not_selected`. Source cancellation keeps its
`cancelled / source_gone` marker.

This is part of #5207. The owner verifies a Google and Microsoft copy with
their connected calendars in production after deployment.
