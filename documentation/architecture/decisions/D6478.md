## D6478 — Serial refresh of inherited-red PRs after main recovers; amends D5398's no-bulk-refresh rule (#6478)

- **Status:** built. The live proof waits on the owner's landing bot App. Part of #5600 (plan key C7). Stacked
  on #6474's branch, whose GitHub client and runner merge it reuses.
- **Why:** in the last 30 red PR runs, 67 to 70% went red only because main was. Re-running their checks
  re-tests the old base, so each needs a merge of main. D5398 forbade doing that in bulk, because a hundred
  simultaneous full runs swamp the runners.
- **Owner's answer (2026-11-16): yes.** When main turns green, the bot may merge main into inherited-red PRs'
  branches one at a time, at the configured rate, stopping at once if main goes red or a breaker opens. **This
  amends D5398**: sessions still never refresh in bulk, and the bot's serial, rate-limited refresh is the stated
  exception.
- **Built:**
  - `scripts/landing-bot/refresh-rules.mjs`, pure: `inherited()`, `allowance()`, `refreshSerially()`,
    `recheckOne()`;
  - `scripts/landing-bot/refresh.mjs`;
  - `.github/workflows/landing-bot-refresh.yml`, named for #6467's shared rules rather than the issue's
    `main-recovery.yml`.
- **How a run behaves:**
  - **Polling, not `workflow_run`.** The #4571 guard (WF-4) forbids `workflow_run` repo-wide. A run acts only
    when main's newest completed push run is green and one of the last 20 was red. Every 10 minutes is the
    trigger's resolution.
  - **The selection** comes from runs, not labels: the latest CI run on the PR's current head failed, and
    `verdictFor()` against the red main run says `inherited_main_failure`. Drafts are skipped.
  - **The rate.** Each run uploads a reservation artifact before refreshing. The next run counts the
    reservations inside `LANDING_BOT_REFRESH_WINDOW_MIN`, against `LANDING_BOT_REFRESH_PER_WINDOW`.
  - **One PR at a time.** Before each, the run re-reads the mode, `bot:off`, the head and `breakers('refresh')`.
    A breaker stops the run.
  - **The update** is update-branch with `expected_head_sha` and the App token. If GitHub refuses an App token
    (its documentation contradicts itself), the run falls back to the branch keeper's runner merge, pushed
    normally. The summary records each status code and fallback, which answers the question with a run link.
  - **A conflict** is labelled `conflict` and not retried.
- **Guard:** `frontend/test/landing_bot_refresh_6478.test.mjs`, on fixture runs:
  - only inherited failures are selected;
  - the rate holds over 30 PRs and across runs;
  - a red main or a queued-runs breaker mid-list stops the run;
  - drafts, `bot:off`, changed heads and an unset mode are skipped;
  - a conflict is labelled once;
  - the workflow is gated to main of this repository.

  Mutation-checked: not stopping, selecting own failures, and ignoring the rate each fail it.
