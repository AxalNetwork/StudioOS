- <https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-stacked-pull-requests>

What they say:

- **GraphQL (read-only, unversioned, no preview header).** `PullRequest.stack: PullRequestStack` and
  `PullRequest.stackEntry: PullRequestStackEntry`, each "null if it is not part of a stack". `PullRequestStack` has
  `number`, `size`, `baseRefName`, `entries`. `PullRequestStackEntry` has `position` ("1 is the closest to the base
  branch"), `pullRequest` and `stack`. There are no stack mutations. `autoMergeRequest(includeStack:)` and
  `disablePullRequestAutoMerge(includeStack:)` can cover the whole stack.
- **REST.** The pull resource has a `stack` object (`id`, `number`, `size`, `position`, `base{ref,sha}`) "when a pull
  request belongs to a stack" in both API versions 2022-11-28 and 2026-03-10. Its schema is `object | null` and not
  required, so **a missing `stack` key proves nothing**. `/repos/{o}/{r}/stacks` lists, creates, extends and unstacks.
  Merging a stack needs `PUT …/merge-async` (2026-03-10). The synchronous merge endpoint and `mergePullRequest` do
  not support stacks.
- **Merge queue.** "All pull requests in the stack are added to the queue in the correct order. If a pull request is
  removed or ejected from the queue, all pull requests above it in the stack are also removed."
- **Status.** The feature (`pr-stacks`, github.com and GHEC) is in public preview: the docs' links carry the
  `stacked-prs-gtm-public-preview-2026` campaign. Fields may change, which is why everything not positively read is
  `unknown`.

### The adapter and guard (`scripts/landing-bot/stack-membership.mjs`)

One GraphQL read per call (`STACK_QUERY`) through the caller's read-only client (`keeper.mjs`'s `client().graph`,
`GH_TOKEN`), never the App token. `classify()` is pure and returns `{ status, repo, number, head, draft, queued,
autoMerge, layer, stack, evidence, reason }`:

- **`ordinary`** only when the answer names this repository (`nameWithOwner`, case-insensitive), this PR number, a
  40-hex head, serves both `stack` and `stackEntry` as keys, and both are `null`.
- **`member`** when both are objects that agree: a positive stack number and size, `1 ≤ position ≤ size`, the entry
  naming this PR and this stack. Position 1 is the `bottom` layer; any other is `upper`. A draft layer is a member.
- **`unknown`** for everything else: a failed or timed-out read, a GraphQL error, a field missing from the answer,
  one field null and the other set, another repository, another PR, an entry for another PR or stack, a position
  past the size, an unreadable head, an invalid caller identity. The reason is one line of at most 160 characters,
  with any `Bearer …` value masked. The read never throws.

`stackGuard()` proceeds only for `ordinary` at the expected head (when one is given). Its disposition is `proceed`,
`held-member`, `held-queued-member`, `held-unknown` or `held-head-moved`, with one summary line, for example:
`#12 held before the keeper merge and push: upper layer of native stack #4, layer 2 of 3; native stacks are not
maintained one PR at a time; in the merge queue: its entry, order and auto-merge are left as they are`.

Ordinary PRs take exactly the paths they took before. Breakers, budgets, attempts, T2, provenance and `bot:off` are
unchanged and still run where they ran. A moved head on an ordinary PR keeps its existing handling where one existed
(the keeper's re-read skip, the resolver's definitive hand-back); the guard's own head pin adds a refusal when the
GraphQL read sees another head than the REST read did.

**Queued members.** Nothing in this stage dequeues, reorders, replaces an entry or sets or clears auto-merge, for any
PR. A member found in the queue is held with `held-queued-member` and a summary line that says its entry, order and
auto-merge were left as they are. GitHub removes the layers above an ejected member itself; the ejection handler
holds each of them rather than re-queueing one alone.

### Refusals and limits of this stage

- **The feeder stops its apply sweep** when the enqueue boundary holds a candidate, because `applySweep` throws on any
  non-`queued` status. That is the safe direction; a member normally never gets there because boundary 8 already
  passes it over. Treating `held` as a skip belongs in `feeder-sweep.mjs` after #8892.
- **Resolver hand-backs for a PR that joins a stack after its plan.** If the model failed, `applyStage` still writes
  its hand-back label before `fresh()` runs. No push, model call or queue write follows.
- **Keeper plan cap.** A held member is dropped after `LANDING_BOT_KEEPER_PER_SWEEP` is applied, so it can take a
  sweep slot without using a push.
- **Conflict indicator and main repair** are not guarded: the indicator only labels, and main repair works on its own
  `repair/` branch from main, not on a PR's branch.
