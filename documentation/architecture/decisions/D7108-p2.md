## D7108 part 2 — Queue suite parts plan for themselves with equal weights: no `plan` hop on merge_group (#7108)

Part 1 (`D7108.md`) deferred "Remove the `plan` hop in the queue" because it changes D5609 and the logic of the required gate. This part does it. It amends D5609's second paragraph ("`plan` uses the suite's verified condition. Gate requires plan and suite success") and its timing-source paragraph, for `merge_group` only. Whoever signs off on the required gate reviews the gate change below.

The six required contexts in ruleset 25309597 — `test:drift (full suite)`, `worker (typecheck)`, `frontend (build)`, `api ↔ worker drift`, `applied migrations unchanged`, `scan` — keep their names, jobs, `if`, `needs` and `runs-on`, and each is still produced on `pull_request`, `merge_group` and `push`. Every test that ran on a merge candidate still runs there exactly once (D5609).

### Why

In a `merge_group` run, `plan` (ci.yml, "suite plan") ran on its own runner before the nine-part `suite` matrix could be created. During the #7108 stall, the measured `plan` runner wait was 3.0–16.4 min, and run start → matrix created was 3.5–16.9 min; then each shard waited for a runner again. In the queue the part list was never dynamic: `scripts/lib/prTier.mjs` `tierFor` always returns the full tier there, so the parts are the static nine from `SHARDS`. Only the file packing came from the newest main `test-deps-*` timing artifact.

### What changed

1. **`plan` skips in the queue.** Its `if` gains `&& github.event_name != 'merge_group'`. Its steps are unchanged, so `runner-benchmark.yml`'s planner still starts with them (D5611).
2. **`suite` lists the queue's parts literally.** The matrix is `fromJSON(github.event_name == 'merge_group' && '<the nine names, in partsOf order>' || needs.plan.outputs.parts)`. Off the queue it is `plan`'s output, as before, so the draft `["rest"]` tier and the ready full tier are unchanged. `needs: [verified, plan]` and `if: ${{ !cancelled() && needs.verified.outputs.run == '' }}` are unchanged; with `!cancelled()` a skipped `plan` does not block `suite`.
3. **Each queue part writes the plan itself.** The `suite-plan` download carries `if: github.event_name != 'merge_group'`. A new step, "Exact-once plan from this commit (merge queue)", runs only under `merge_group`, right after setup-node: `node scripts/test-drift-parts.mjs --plan --equal-weights`. It then fails the part unless the plan has `strategy.job-total` parts and `matrix.part` is one of them. The literal list has no repeated name (tested), so if every part passes, the matrix and the plan pair up one to one. A stale literal after a `SHARDS` change fails a part; it cannot silently drop one. The run line, `TEST_TRACE_DIR` and the trace upload are unchanged, so `test-deps` still gets nine traces per queue run and PR plans and selection-shadow keep their timings.
4. **`--plan --equal-weights`** in `scripts/test-drift-parts.mjs` plans with timings `{}` and reads no file, so the queue does not depend on a missing file (ENOENT) to mean equal weights.
5. **The gate.** `test:drift (full suite)` keeps its name, `if: always()`, `needs: [verified, plan, suite]` and exactly two `exit 0`. The second way to pass is now `{ PLAN = success and EVENT != merge_group } or { PLAN = skipped and EVENT = merge_group }`, and `SUITE = success`. The first (a push the queue already verified) is unchanged.
6. **`runner-benchmark.yml`'s `benchmark` job** carries the same suite steps byte for byte (D5611 parity). It never runs on `merge_group`, so the new step is always skipped there.

### Why equal weights, not a pinned timing artifact

On 2026-11-17, for all 21 `merge_group` runs checked, `test-deps-<base_sha>` was created 12–46 min after the run started (run 44186177415 started 22:03:23Z; `test-deps-881efb72e1` appeared 22:22:36Z). The queue is stacked, so pinning to the candidate's base artifact would always fall back to equal weights. A selector over "an ancestor's artifact created before the run, minus a margin" would need about 40 REST calls per candidate, `actions: read` on a job that runs PR code, and a proof resting on listing order, retention and upload finalization. Weighting also barely helped: in a 40-run sample, the two runs that had already fallen back to equal weights (44151598139, 44167292803) had a longest shard of 22.7 and 23.2 min; the 38 weighted runs had a median of 21.9 min (17.6–28.0).

### Exact-once, and why every part agrees

In a `merge_group` run every part and every re-run starts from the same checkout (`github.sha`, the immutable queue head), the same `test:drift` script and the constant timings `{}`. `suiteFiles` expands the same globs over the same tree and sorts by UTF-16 code units. With no timings, `planParts` weighs every file 1, orders them by path and gives each to the lightest part, lowest index on ties. The plan is a pure function of the tree: the same `suite-plan.json` bytes in all nine parts. No API, artifact or clock input is read. Each part's `--plan-file` validation still re-checks names against `partsOf` and that each sharded script's files appear exactly once.

### Expected saving

The matrix is created at run start in the queue, and one runner acquisition per candidate goes (ten suite-path jobs become nine). In the 40-run sample (2026-11-17, 18:24–22:03Z), run start → matrix created was 0.4–9.0 min; in the #7108 window it was 3.5–16.9 min. Each part adds a local plan step of 1–2 s in place of the artifact download. Equal-weight packing may cost 0–1 min on the longest shard (n=2, noise level). The parts' own runner waits are not reduced.

### Follow-up

Re-measure the longest queue shard over at least 20 queue runs after this lands. If it is worse by more than the hop saved, add a pinned-artifact selector that fails closed on `merge_group` (first-parent ancestors of the candidate, artifacts created before the run minus `test-deps`' timeout, `actions: read` on `suite`).
