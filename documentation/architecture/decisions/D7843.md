## D7843 — Research › Funds: a reviewed-manifest writer that fills the fund statement store for the lists already in the catalogue (#7843)

Part of #3701, from the owner's Research › Companies audit of 2026-11-19 (items 4B and 4C). Builds on D7743.

### Why

`research_fund_vehicle_facts` (D7167) holds no rows, because nothing writes it, and D7743 gives it no writer. D7743's statement store (`research_fund_observations` and `research_fund_observation_terms`) is filled from the four imported sources by #7751, and by nothing for the lists the catalogue already serves. This decision adds that writer. It is proven on a fixture; production holds no rows from it.

### The writer: `scripts/import-fund-facts.mjs`

It compiles a reviewed manifest (JSON: `name`, `imported_on`, `rows`) into SQL, deterministically. `--check` fails when the file on disk is not what the manifest compiles to now. It writes the two tables of D7743 and nothing else: no `research_fund_vehicle_facts` row, and no table, index or trigger.

It holds no vocabulary and no parser of its own:
- Stage terms come from `normaliseStage`.
- Country and region terms come from `normaliseGeography`.
- Money readings come from `readAmount(fact, wording, heading)`.
- The served-row predicate is `SERVED_FUNDS`.

All four are imported from the Worker modules, and the script re-runs itself under the Worker tests' TypeScript loader, as `build-formation-seed.mjs` does.

**Each row of the manifest** gives:
- the row key, which becomes `source_record_ref`;
- a directory `fund_uid`;
- a fact from D7743's thirteen;
- the source's wording;
- `source_name`, a list with a review row;
- `source_url`, the page that states it;
- `reported_on`;
- optionally the column `heading`, for a money fact's currency basis;
- optionally `replaces`, the earlier row key a changed value replaces.

The manifest's `imported_on` is every row's import date.

How a row is compiled:
- One row writes one statement for that uid only. A manager's statement is keyed to the manager's row and never copied to its vehicles.
- A thesis is written as `sector_focus` or `interests`, and lead or follow as `lead_preference`. The reviewer chooses; the writer refuses any other fact name.
- Investment geography comes from the statement's wording only, never from a headquarters.
- A cheque is never derived from a fund size. Nothing is converted, and a currency is present only when `readAmount` finds one stated.

**How a compiled row fills the columns D7743 leaves to the writer:**
- `promoted_by_user_id` is NULL. D7743: a migration-written row has no promoting user.
- `promoted_at` is NULL, which D7743's CHECK requires when there is no promoting user.
- `period_start` is NULL.
- `method` is `COMPILED_METHOD`. D7743 does not say which method a migration-written row carries, so the question is on #7743. The constant holds `'manual'` until it is answered: each row is a statement a person reviewed and keyed, not a rule's output. It is the one place the value lives.

### Refused at compile time, each with its own code

The writer refuses a manifest at its first bad row. The message names the row key and the field, never a value.

| Code | Reason |
| --- | --- |
| `source_link_missing` | No `https:` source link. |
| `dates_missing` | No `reported_on`. |
| `imported_on_missing` | The manifest has no `imported_on`. |
| `fact_unknown` | A fact outside D7743's list. |
| `fact_follow_on_cheque_not_written`, `fact_deployment_status_not_written`, `fact_submission_route_not_written` | The follow-ups below. |
| `source_unreviewed` | A `source_name` with no review row. Review rows are read from every `INSERT INTO research_fund_sources` in the committed migrations; `--reviews` points elsewhere only for a fixture. A new list needs its review row first, as #7752 does for the community sources. |
| `value_email`, `value_phone`, `value_profile_link` | A value shaped like an email address, a phone number or a person's page on a social or professional network. Wording, link, heading and uid are all checked. |
| `changed_value_same_key` | A row key an earlier compiled file, or an earlier row, already used, with a different value. |
| `duplicate_key` | The same row twice in one manifest. |
| `replaces_unknown`, `replaces_other_fact`, `replaces_itself` | A `replaces` that names no known key, a key for another fact, or its own key. |

**Earlier compiled files form the ledger.** Every compiled file opens with `-- import-fund-facts v1` and lists each row's key, fact and value hash. The hash is SHA-256 over the uid, fact, wording, list, link, reported date and heading. The next compile reads those lines from the committed migrations. The file being written is left out, so an unmerged manifest can still be revised.

### At apply time

Each statement is an `INSERT … SELECT … WHERE` that writes nothing:
- for a uid the directory does not serve (`SERVED_FUNDS`). A uid in `research_fund_directory_uid_moves` is followed one hop, and the statement is written under the new uid;
- under a list whose verdict is 'not allowed'.

A replay writes nothing: `ON CONFLICT … DO NOTHING` on D7743's UNIQUE key (`fund_uid`, `fact`, `source_name`, `source_record_ref`), and on the terms' primary key. Nothing uses `OR IGNORE`, which would also hide a failed CHECK.

A row that names `replaces` closes the earlier statement once the new one is in the store. It sets `period_end` to the new row's `reported_on`, so `readFundStatements` returns the earlier one as past.

### Sources: option A

Mandate statements come from the organisation's own published pages and regulator filings only (Q1 A). A list's terms review still decides whether a statement is served.

### First real input, and what production holds

No migration ships with #7843, and production holds no rows from this writer. The first real input is the stage text and the `cheque_range` text of the manifest in PR #7337, after that PR merges. Those notes are free text per manager. They become statements only through a reviewed manifest: a data task Session 1 files when PR #7337 merges. That run's output is a migration named by D4106 and D5398 under the data task's own issue number. The manifest in PR #7586 has no stage or cheque field.

### Follow-up, not written here

D7743 has no fact for:
- a follow-on cheque;
- a reported deployment status;
- a published submission route.

A manifest row that carries one is refused by name, not dropped. Adding them is D7743's two-table rebuild.

### Tests

`cloudflare-worker/test/research_fund_facts_7843.test.ts` builds real SQLite with foreign keys on, as D7743's test does, then the fixture's invented list reviews and a fresh compile of `fixtures/fund_facts_7843/manifest.json`. It checks that the fresh compile equals the committed `compiled.sql`, and covers:
- the served read;
- a manager's statement absent from its vehicle;
- the money shapes (range, typical, lower bound, symbol only, heading only), each equal to `readAmount`;
- the terms, equal to `normaliseStage` and `normaliseGeography`;
- the unserved uid, the moved uid and the not-allowed list;
- a replay;
- a replacement;
- no vehicle-facts row and no new table;
- each refusal;
- `--check` failing on a changed file.

Every name and wording is invented.
