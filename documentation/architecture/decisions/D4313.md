## D4313 — Rail presses run their option's job through textChoice (#4313)

- **Status:** parts 1 and 2, built by slot S22 on 2026-11-03, and part 3, built by slot S25 the same day, from S1's decision on #4313 (split off from #3937, D1478 task 3b). Part 3 closes #4313.
- **Migration:** none. No model is newly wired.

### What was decided

**Every rail option names its job.**
- `RAIL_OPTION_JOBS` in `services/ai/textJobs.ts`, beside `TASK_TEXT_JOBS`, maps each of the 118 option keys `railMatrix.json` registers to a job of the use-case plan (`modelUseCases.ts`).
- One key, `draft:renewal-risk`, does different work on two pages (numbers on Retainers, a summary on Health). `RAIL_OPTION_PAGE_JOBS` lets the page's own job win there.
- Most rows follow the plan's job for the press.
- The plan names no job for several partner and investor reads. Those rows take the job whose kind and Default match the press, and are marked "nearest" in the table:
  - `IN11`, `IN13` and `GR16` for the Operating Partner and advisor presses;
  - `CA1` for the Studio layout chip;
  - `BU1` and `RA1` for two Raise writing presses.
- `rail_option_jobs_4313.test.ts` fails when an option has no row, or when a row names a key that is not registered.

**A press runs its option's job.**
- A rail run whose option maps to a job with a text step now resolves its model through `textChoice`, not through its page's row (D764).
- `textChoice` applies:
  - the job's ladder;
  - the plan lock;
  - whether the input fits, refusing up front when the input is too long for every model, naming the longest-window one;
  - the member's stored pick for the option, when the job lists it (a stale one reads as none).
- A job the caller names (`RunOptions.textJob`) still wins.
- These keep their own path:
  - an option whose job writes no text (a recording, an image, an upload, a re-index);
  - a run whose caller names a model.

**An option lists its job's models.**
- `withModuleModels` builds an option row's selector from the option's own job rather than its kind's (`RAIL_KIND_JOBS`).
- The rail therefore offers exactly what the press runs: the Default first, then the rest of what `jobChoices` accepts. It never offers a model `textChoice` would pass over, so a pick is never swapped silently (D1478 A (c)).
- Page rows are unchanged.

**Three options change model.**
- `OPTION_MODEL_MOVES` names them, both ends:
  - **Build › Operating systems' retro** moves from the 70B to glm-4.7-flash (BU2: "Roadmap, this-week and retro drafts").
  - **Investor › Closing's cover note** moves from the 70B to gpt-oss-120b (IN1: "closing note").
  - **Research › Library's "Draft the gaps"**, on all three profiles, moves from the 70B to gpt-oss-120b (RE3: "Drafts").
- Both models already run on routes, so none is newly wired, and none waits on a spend approval.
- Every other option keeps the model its kind's list ran first.

### Part 2: the presses that send only a page, and the page pick (built 2026-11-03)

Built by slot S22 (the S21 session). Part of #4313.

**No rail text press takes its model from a page row.**
- **A press with no option of its own** runs its page's job through `textChoice`. That covers a press that sends no option, or one the page does not register. The page's job is its kind's job (`RAIL_KIND_JOBS`), the same job the page's model list is built from (`withModuleModels`).
- **Every page's kind names a job.** `rail_page_jobs_4313` fails when one does not.
- **A speech or vision page's job writes no text** (VA1, BU6). A press on such a page with no option keeps the page's list: the Data room's figure extraction (`extract:deck-source`, D1602) is one. That list is the page job's own selector (`withModuleModels`), not the matrix's stored row, so its model is unchanged.
- **`railTextJob(page, option)`** in `aiRouter.ts` answers the job and the option row whose pick applies. The `pageRowed` gate is gone.
- **A page the matrix does not list** (Validate's interview structuring sends `validate`) is not a rail page: the task's own job applies (`TASK_TEXT_JOBS`, VA5 there), as before part 2.

**A caller that names a model** is checked against the option's or page's list. That list is the job's own selector, built from the same job's step and kind. The list only checks; it never chooses a model.
- A named model is not passed to `textChoice`, which would also apply the plan lock and the input-fit refusal. That would refuse a member's All models choice and a persona module's connection (#3626), which run today.
- Moving named models onto those rules too changes who may run what, so it is S1's call.

**The page-level pick is gone** (S1's decision on #4313).
- `PUT /api/ai/rail/pick` needs an option the page registers. Without one it answers 400 `option_required`.
- `GET /api/ai/rail` no longer falls back to a page pick, and a run never reads one.
- A page pick stored before part 2 is left in `ai_rail_preferences`: it is not deleted and no longer read.
- The rail (`WorkerRail.jsx`, `railModels.js`) offers a pick only while an option is open. With none open, the page's models are drawn as a list and the note reads "The models this page's work runs on. Open one of its options to choose the model for it."

**Still open on #4313:**
- **The model lists on the page rows of `railMatrix.json`.** No run, pick or rail read uses them any more: every page's list is rebuilt from its job. They remain only as the canvas's record, which the generator (`scripts/build-rail-matrix.mjs`) writes and validates.
- **Why they are not dropped here.** Removing them changes the generator, the D764 matrix tests and `check-model-coverage`, which all read that file. That is a separate PR.
- **Named models under `textChoice`'s lock and fit rules,** if S1 wants that (above).

**Count:** of the plan's 80 scope jobs, **46 now run through `textChoice`**, up from 43. Part 2 adds the page jobs BU5, BU8 and RE6.

**Tests:**
- `rail_page_jobs_4313` (4): every page kind's job; `railTextJob`'s answers; the router and route rules.
- `rail_matrix_d764`: the six tests of the page pick now check part 2 instead:
  - a page press runs exactly what a run naming its job runs, its fallback included;
  - an old page pick is not read;
  - a pick without an option is refused.
- `airail_d698` and `worker_rail_inherited_d402`: with no option open, the rail's cards and chips are not buttons and nothing is stored; with an option open, they pick for it.
- **Mutations**, each caught:
  - a page press given no job;
  - the pick read from somewhere other than the option;
  - the page pick read again;
  - a page pick accepted.

### Part 3: the page rows' model lists removed (built 2026-11-03)

Built by slot S25. Closes #4313. S1's decision said to remove the page rows' lists in the same PR as the last caller moved; the last caller moved in part 2 (#4347), and part 2 left the removal to this PR.

**What was checked first.** Before removing anything, every reader of `railMatrix.json`'s page rows was read on main:
- `railMatrix.ts` builds each page's row through `withModuleModels`. Every page kind names a job (`RAIL_KIND_JOBS`, held by `rail_page_jobs_4313`), and that job's selector replaces the stored list. A probe that emptied every stored page list gave the same `models` and `more` on all 205 pages.
- Every runtime caller (`GET /api/ai/rail`, `/api/ai/modules`, `/api/ai/catalogue/hq`, `aiRouter.run`, `publicModels`, the agents' catalogue, the deck routes) reads those built rows, never the stored list.
- **One reader did use the stored list: `coverage.ts`,** the generator of `AI_MODEL_COVERAGE.md`. It is not in the Worker's runtime path (only `render-ai-coverage.mjs` and its test import it), but it counted the stored page lists as wired and offered. It now reads `railRows()`, the rows the rail builds, so the matrix shows what the pages list and run (below).

**What was removed.**
- A page row in `railMatrix.json` is now `{ pageKey, kind, routeTask }`. Its `models` and `more` are gone, from all 205 rows. The file went from 192 KB to 109 KB.
- `scripts/build-rail-matrix.mjs` no longer writes them. `railMatrix.json` was regenerated with it, not edited.
- `withModuleModels` accepts a row with no stored list; `types-md.d.ts` describes the new page row.

**What was kept, and why.**
- `pageKey`: `resolveRail` finds a page by it, and the preference section is its lower case.
- `kind`: `withModuleModels` reads the page's job from it (`RAIL_KIND_JOBS`).
- `routeTask`: `rail_matrix_d764` holds each page's task to a `ROUTE` key, and the router's `rail_<kind>` entries are checked against the canvas's kind lists. Nothing at runtime reads a page row's task, but removing it is not part of this issue.
- **The options' stored lists stay.** An option with handler `transcribe`, a no-model chip and an option whose job writes no text still read them.
- **The canvas kind lists are still checked.** The generator still resolves each canvas kind's list, because the options of that kind take it. It now holds D720 §5's rules once per kind (labelled `kind <name>`), where before it checked them on every page row. So a bad list on a kind no option takes (code, multi) is still refused. It hands the lists to the test as `kinds` and does not write them.

**`check-model-coverage`.**
- New rule **`unreachable`**: an id the model table offers, and does not hide (`MODEL_LOCKS` "hidden"), that no job lists (`jobChoices`) fails the build. Today all 58 offered, unhidden ids are reached. The two hidden ones (the 3.1 70B and glm-5.2) are excused.
- Its Draw and Listen selectors now read the rows the rail builds (`railRows()`, `railOptionRows()`), plus the options' stored lists. Before, they read the stored page lists.

**The coverage matrix changed.** `AI_MODEL_COVERAGE.md` was re-rendered. 172 lines changed, all because a page's cell now comes from its job's list instead of the canvas list stored on its row. For example:
- Deepgram Flux was "offered" on Validate and the workspaces only because the speech pages' stored list named it. The speech pages' job (VA1) does not list it, so those cells now read "gap".
- gpt-oss-120b is now "wired" on Build, Grow and Research, where a page's job runs it first.
- A page cell's citation reads `<job> on "<page>"`, not `railMatrix.json "<page>"`.

No model runs differently: the runtime already read the built rows.

**Not built: named models under `textChoice`'s rules.** S22's open question 1 on #4313 is unanswered: should a model the caller names (an All models choice, a persona module) also go under `textChoice`'s plan lock and input-fit refusal? This PR leaves named models as part 2 (#4347) shipped them: checked against the job's own list, and not passed to `textChoice`. It is S1's call.

**Count:** of the plan's 80 scope jobs, **46 run through `textChoice`**. That is unchanged from part 2, because this PR moves no caller. It was recounted the same way as parts 1 and 2:
- the plan §6 PR 3 list, as `text_jobs_part3_d1478` pins it (that list holds 78 ids);
- a job counts when it is named by `TASK_TEXT_JOBS`, `FORM_TEXT_JOBS`, an option's text job (`railOptionTextJob`) or a page's job (`railTextJob`).

The 46: ST1 ST2 ST3 ST4 ON1 VA5 VA6 VA11 VA12 VA13 VA15 BU1 BU2 BU3 BU4 BU5 BU8 DK1 DK2 DK8 DK12 RA1 RA2 RA6 RA8 RA10 RA12 IN1 IN3 IN5 IN6 IN11 IN13 GR1 GR2 GR16 NE2 RE3 RE6 CA1 CA2 CA4 EV1 EM1 AD1 MI1.

- `rail_matrix_d764`, new test: every page row's keys are exactly `pageKey`, `kind`, `routeTask`; the generator writes no list; each page lists its kind's job's Default first; a page kind with no canvas list is refused.
