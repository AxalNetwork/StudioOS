## D5352 — Every target-creating Validate/Grow accept is keyed to its proposal (#5352)

D4627 made the proposal id the retry key for ordinary hypotheses and PostHog
experiment evidence, but its shared claim/revert coordinator also serves four
writers that were still unsafe to repeat after their target landed.

The proposal id is now carried to each remaining target stage:

- PostHog survey signals store `demand_signals.source_proposal_id`, protected by
  a partial unique index. `writeDemandSignal` returns that row on a retry before
  writing a second signal or activity.
- PostHog survey feedback reuses `product_feedback.uid`, already unique, as
  `posthog-proposal-<id>`. `addFeedback` returns that row on a retry.
- Ordinary competitor accepts reuse `competitor_candidates.id`, already the
  table's primary key, as `fill-proposal-<id>`. The shared manual writer returns
  the stored candidate before allocating another position or dependent row.
- Ordinary feedback-theme accepts stamp
  `product_feedback.theme_source_proposal_id`. A retry of that same proposal and
  theme returns the already-themed row so `recordFill` can finish; a different
  proposal or a manual theme still cannot claim it.

The new nullable columns and partial indexes are migration
`202611101053_validate_grow_accept_idempotency.sql`. Rows created by hand keep
NULL and retain their existing behavior. Manual theme changes clear the proposal
stamp because the shared writer receives no proposal id.

The D4627 claim-first and revert-on-throw mechanism and every HTTP response stay
unchanged. A target-stage retry is a no-op lookup; the provenance or `target_ref`
stage then completes once. Fault-injection tests fail the statement immediately
after each real target write, retry the same proposal, and require exactly one
target and one completed provenance/reference.
