## D1345 — Retire Messages after Email ships

- **Issue:** #3553, S27, implemented by s30 · Codex; part 6 of #3547.
- **Basis:** main `98f039a245fe49b24afcb073ca13cb1ba71c3cd7`; #3552 shipped in #3586.
- **Decision:** owner option A, relayed by S1 on #3553: remove the old inbox and its stores. Canvas `design/incoming/Email Page.dc.html`, EM10; D1347 Q3 settles removal.
- **Migration:** 650, `650_retire_messages.sql`. No production write or deployment performed by this task.

### Route and entry points

`/messages` replaces its history entry with `/email`, discarding old thread/query/hash data. EM10 says “Messages is now Email”, gives the approved explanation, and offers Open Email and Dismiss. Either enters Email. Acknowledgment is kept once per authenticated account and browser in local storage; blocked storage cannot block navigation. Direct Email visits show no notice. Existing route roles are preserved.

The top bar, Explorer sidebar row, palette, phone tabs/account sheet and admin placement point to Email. The old off-canvas Messages rail row is removed; Email keeps its own board. Messages was off canvas, so no board alias is invented. Storage usage no longer queries or offers the retired attachment area.

`MessagesPage.jsx`, `messagesView.js`, all eight `message*` API helpers and `routes/messages.ts` are removed. Cached clients get a small tombstone from the real Worker entry for the root and every descendant: HTTP 410, `code: messages_retired`, `moved_to: /email`. The normal security, rate-limit, CSRF, CORS and observability middleware still apply. Browser CORS preflight remains the standard middleware response. No old table or R2 read occurs. External providers' message APIs are unaffected.

### Former thread starters

The LP's GP control opens the actual Email composer on `fund_gp:<fund id>`. Multiple own funds keep a selector; a missing linked GP account keeps the honest help state. The Worker uses the shared `lpSelfScope` predicate, including its legacy email arm only for an unlinked LP row. The recipient is the GP's linked account address, never the fiduciary document's GP address. Its source contains the own fund name, GP name and own LP status, with two fund-specific purposes. No other LP rows or totals are included.

Delivery's unopened-client control lists individual Email actions on `work_product:<deliverable id>`. Each opens one draft, reviewed and sent from the advisor's mailbox. No bulk messages or automatic sends occur. A recipient resolves only for the advisor profile's own deliverable and an engagement belonging to that same advisor, linked to a client account; a booking is not required. An unlinked client is stated before opening a draft. Admins retain D1348's case-only rule and cannot use either shortcut. Both refs reuse the mounted `/api/mail/context` and draft services; no new API domain is added.

### Removal evidence and safeguard

Read-only production verification on **2026-10-28** returned:

- `message_threads`: 0 rows.
- `messages`: 0 rows.
- `message_thread_participants`: 0 rows.
- `message_attachments`: 0 rows.
- FILES R2 prefix `messages/`: 0 objects, `is_truncated: false`, using a bounded prefix listing. No object contents were read.

Migration 650 checks the sum of all four counts through a transient CHECK-constrained assertion table before the first DROP. Any new row aborts before removal and leaves the source tables intact. On success it drops the helper and the four stores, children before parents. The migration ledger prevents replay; applied migrations and the historical schema baseline are unchanged. The four intentional retired declarations are recorded with their reason in `scripts/migration-declarations-baseline.json`; no live reader is exempted. R2 emptiness is the recorded deployment prerequisite; SQL cannot check R2. There is no data export or recovery copy because there is no data to move.
