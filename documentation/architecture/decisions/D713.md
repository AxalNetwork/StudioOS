### PR B: what it delivers

PR B adds everything but the screens (step 11), which wait for the F28 and
F29b–F29e canvas. It enables the personal connection.

- **Connect** (`integrations/providers/mercury.ts`). It registers `connect`
  only. `ConnectRefusal` (`integrations/registry.ts`) carries a status, a
  code and our sentence; the `/connect` catch answers it through `refuse`.
  The checks run in this order: support session, audience, webhook secret,
  token, Mercury's answer, the scope, then decision 3. On success the
  provider stores `{ api_key }`, the organization's id and name, and
  `config.read_only` as `reported` or `confirmed`. Decision 3's lists are
  bound as one JSON value (`IN (SELECT value FROM json_each(?))`), so no id
  reaches the query text.
- **The catalogue.** `personal_roles` is `['founder', 'partner']`.
  `publicDescriptor` gives a founder or partner the personal variant: its
  own description, its capabilities ("Revenue import", "Payment matching"),
  its permission sentence, and its feeds (`revenue_and_traction` for a
  founder, none for a partner). `has_implementation` is true only for that
  audience. `fed.ts` counts Mercury in `FED_LEDGER_PROVIDERS` and reads
  feeds by the owner's role.
- **The webhook.** `POST /webhook/mercury/:uid` answers 404
  `{ error: 'not_found' }` before the schema check, the row lookup or a log.
- **The reads** (`services/mercuryPersonal.ts`). On every read,
  `personalConnection` runs the use policy and loads the member's own row.
  It decrypts the token, re-reads the organization, and re-runs decisions 2
  and 3. A 401 or 403, a reported write scope, or an entity's organization
  marks the row `error`. Each read writes one `integration_logs` row, for
  example `use=venture_revenue lines=8 credits=6`.
- **New client and parse calls.** The client gains `getTransaction` (GET
  `/account/:id/transaction/:id`); `parse.ts` gains `parseTransaction` and
  `parseTokenPermission`. **UNVERIFIED** against Mercury: the one-line path,
  its body shape (the line itself or under `transaction`), and whether any
  response reports a token's permission. `parseTokenPermission` looks for
  `permission`, `permissions`, `scope` or `scopes`, on the body or under
  `organization` or `token`. When none is present the result is
  `not_reported`, and connect then needs `confirm_read_only`. A 404 on one
  account means "try the next".
- **The use keys**, as `GET /api/mercury/personal/status` names them, each
  with `available` and a `reason` (`purpose_not_allowed` or `hq_only`):

  | Key | Role | Routes |
  | --- | --- | --- |
  | `venture_revenue` | founder | `GET /api/revenue/projects/:id/mercury-credits`, `POST /api/revenue/projects/:id/entries/import-mercury` |
  | `practice_income` | partner | `/api/mercury/personal/matches?target=invoice` |
  | `partner_deals` | partner, HQ only | `/api/mercury/personal/matches?target=payout` and `target=settlement` |

  `/status` reads only the member's own `integrations` row, never the bank.
- **The revenue import** (`routes/revenue.ts`, `revenueLedger.ts`
  `mercuryCreditToEntry`).
  - `mercuryCreditToEntry` is pure and takes booleans only, so no name
    reaches it. A debit, or a cancelled or failed line, is `skip`: it is not
    listed at all.
  - Every other refusal is listed with its reason: `pending`,
    `internal_transfer`, `axal_entity`, `stripe_payout`, `already_imported`,
    `imported_elsewhere` (the line is a row on another project; one bank
    line is one row on the platform), and `invalid_amount`.
  - The list writes nothing. The import takes at most 200 items and checks
    every UUID, label and type before calling Mercury. It then re-reads each
    line by id and inserts with `ON CONFLICT (source_ref) WHERE source =
    'mercury' DO NOTHING`.
  - It upserts the `connector_fed_items` link, so after a delete the link
    follows the new row. It answers `{ inserted, already_imported, refused }`.
- **Matching** (`routes/mercury_personal.ts`). `GET /matches?target=` lists
  the member's own open targets, each with every line that fits. `POST
  /matches` confirms one, re-reading the line by id. `POST
  /matches/:uid/withdraw` takes a reason; it reads no bank but keeps the
  use's policy. Each target query binds its filters as `?1` to `?5`.
- **The checklist.** `ef.plaid` reads "Connect Mercury (verify revenue)" and
  counts an active `mercury` row.
- **Tests.**
  - `mercury_personal_connect_d713` (connect, every refusal, the webhook,
    `/status`, the re-check on read);
  - `revenue_mercury_import_d713` and `mercury_partner_matches_d713`
    (extended);
  - the guard (no Eadwyn reader, `connect` only, `mercury_accounts` the only
    474 table, and `entity_key`, `account_last4` and `status` the only 472
    columns);
  - `connectors_audience_d710` (founders and partners now see the card, on a
    branch too);
  - `onboarding_checklist_mercury_d713`.

  The fixtures stub every Mercury call. Accounts carry a masked `****` and
  a last four, never an account or routing number. The registry is 472's
  own table; its rows carry an entity, a last four and a status, and leave the
  number columns empty, with 472's CHECKs lifted for that insert only.

### PR C: the screens, from existing parts

PR C (`Part of #1778`) builds step 11's screens now, on S1's 2026-10-18 word,
from the parts each page already uses and with no new layout. The canvas PR
(`Closes #1778`) lays them out to boards F28 and F29b–F29e once the owner
approves them, so `needs-design` stays. Where the export differs, it wins on
layout and copy; this decision wins on data, routes and who may act.

- **F28, the revenue ledger.** "Import from Mercury" sits beside "Import
  charges from Stripe" and opens `components/spinout/MercuryCreditImport.jsx`
  in the ledger's own modal. Each credit shows a checkbox when the Worker says
  it is importable and the Worker's reason otherwise
  (`MERCURY_CREDIT_REASON_TEXT` in `lib/revenueLedger.js`). A picked credit
  takes the label and type the founder gives it; the request carries only the
  transaction id, label and type, never an amount or date.
- **F29b to F29d, the member's matches.** `components/MercuryMatch.jsx` reads
  nothing until the member presses "Match to my Mercury". It then reads
  `/mercury/personal/matches?target=` once, lists the lines that fit, and
  confirms one, or withdraws a confirmed match with a reason of ten characters.
  It sits on the invoice (`InvoiceDocument`, partner only; both sides read the
  matched day and only the partner the last four), on each payout that has not
  failed (Received comes from `bank_match`, beside the status and never instead
  of it), and on the member's own issued and matched settlements, a new list
  on Earnings.
- **F29e, the Admin's desk.** Contracts › Partner deals gains a Settlements
  button per deal that opens `pages/admin/contracts/SettlementsDesk.jsx`: an
  Admin drafts, edits and deletes drafts; Issue and Void are drawn only for
  the Super Admin, so a plain Admin never reaches a route that answers
  `super_admin_required` and is never shown a step-up prompt.
  Draft Edit and Issue are offered only while the deal is active. Draft deletion
  and issued-settlement voiding remain available after a deal ends. A failed
  action stays visible when an edit form is hidden by an inactive deal. Deleting
  or issuing the draft being edited clears its form after the action succeeds;
  changing a different draft preserves the current edit.

- **States.** Each place has its empty state. A malformed credits, matches, member settlement or admin settlement
  response is Unreadable rather than an empty list. Payouts show Received from
  their bank match; settlements show Matched for confirmed credits or debits. No Mercury connection reads Not
  recorded with a link to Connectors; a refusal the Worker explains is shown as
  it said it; any other failed read is Unreadable, never an empty list.
- **Tests.** `frontend/test/revenue_mercury_import_d713.test.mjs` and
  `frontend/test/mercury_match_screens_d713.test.mjs`.

### Migration execution and the cold-isolate window

`scripts/migrate-d1.mjs` applies each file through `wrangler d1 execute --file`;
it does not split the statements of migration 477. Wrangler's `executeRemotely`
file branch uploads the file to the D1 import endpoint and polls ingestion to
completion. It warns that the database is unavailable to queries during that
operation and that failure restores the original state. Thus an old isolate's
`ensureRevenueEntriesSchema` cannot interleave CREATE between DROP and RENAME.
The new table copies every named column, preserving ids and evidence, then
recreates both existing indexes and the global Mercury transaction index.
This is a remote-import guarantee; a local SQLite run proves data preservation,
not production concurrency. Deploy must continue using the whole-file runner.

References: [D1 file import](https://developers.cloudflare.com/d1/best-practices/import-export-data/)
and [Wrangler implementation](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/d1/execute.ts)
(`executeRemotely`, file import branch; also checked in the installed Wrangler).
No explicit transaction statements or production database commands were added.

## What S1 decided

1. **A personal connection is an ordinary `integrations` row, for founders and partners only.**
   - D713 sets #1775's `personal_roles` for `mercury` to `['founder', 'partner']`. Operating partners and service providers sign up as `partner` (personas `operator_advisor` and `service_provider` have `role_alignment: 'partner'`, `personas.ts`). The `operator` and `service_provider` roles a branch invitation can grant (`branch_invitations.ts:43-45`) get no card: no partner use reads them (`isPartner` is `role === 'partner'`, `routes/_t13t14t15_helpers.ts:22-24`).
   - Investors, advisors and mentors get no card: #1775's audience check answers 404. `exploring` is not in `ALLOWED_ROLES` (`integrations.ts:53`). Admins keep #1775's 409 `entity_connection_only`.
   - On a branch, #1775's audience check serves the personal row to `personal_roles`; the entity row stays HQ only.
   - A founder needs Growth, as for Stripe (`tier: 'growth'`, `registry.ts:335`, enforced at `integrations.ts:436-440`); partners skip tiers (`requireTier.ts:32`). If #1775's `mercury` row carries another tier, this PR sets `growth`.
   - One Mercury organization per member (`UNIQUE(user_id, provider_key)`, `registry.ts:475`).
   - *Why:* this use fits the per-member model unchanged (`D649.md:34`, `D650.md:35-36`), so unlike #1775 it records no departure.
   - *Amended by D752 (#1886):* investors hold a personal connection too, on HQ only (`personal_hq_only_roles: ['investor']`); off HQ they get no card and `POST /connect` answers 403 `purpose_not_allowed`, "Mercury is offered to your profile on HQ only." Advisors, mentors, `operator`, `service_provider` and `exploring` still get none.
2. **Read-only, through #1775's client.**
   - `integrations/providers/mercury.ts` implements `connect` only: no sync, push, webhook, preview or action. If #1775 already registered a `mercury` impl, extend that module rather than register a second: `registerProvider` keeps the last (`registry.ts:189-191`).
   - It reads through #1775's GET-only `services/mercury/client.ts` and `parse.ts`, which drops account and routing numbers. The organization read keeps its id and name only; anything else in that response, an EIN included, is dropped there too.
   - The credential is a Mercury **Read Only** API token, stored as `{ api_key }` by `encryptCredentials` (`secrets.ts:31`, KEK_PII). Only the four-character preview is ever shown (`secrets.ts:62`).
   - If the API reports a token's permission, anything above read-only is refused with 403 `write_scope_refused`, at connect and on every read. If it does not, connect needs `config.confirm_read_only: true`, or answers 400 `confirm_read_only_required`.
   - Connect refuses a `webhook_secret` with 400 `webhook_not_supported`.
   - `POST /webhook/mercury/:uid`, on both mounts (`/api/connectors` and `/api/integrations`, `index.ts:1133-1134`), answers 404 before the row lookup at `integrations.ts:975`. It reads no body, writes no log, and cannot tell a real uid from a made-up one.
   - **Each refusal keeps its own status and code.** This PR exports a `ConnectRefusal` (status, code, our sentence) that the catch at `integrations.ts:461-463` answers as it is, through `refuse`. Every other throw stays `connect_failed`. If #1775 already added such a class, use it.
3. **Never an Axal entity's organization.** The Worker answers 409 `mercury_entity_account`, writing nothing at connect and marking the row `error` on a later read, when:
   - the organization's name, normalised, equals the normalised `name` of one of `AXAL_ENTITIES` (`legalDocFormat.ts:53-82`). Normalised means: lower-cased, every run of characters that are not letters or digits made one space, trimmed, and a trailing `llc`, `l l c`, `lp` or `l p` dropped. "AXAL VC MANAGEMENT, LLC" becomes "axal vc management"; or
   - any of its Mercury account ids is in #1775's `mercury_accounts`; or
   - any of its checking or savings accounts' last four equals the `account_last4` of an active #1773 `entity_bank_accounts` row (reading only `entity_key`, `account_last4` and `status`, never decrypting).

   Those two checks are the only reads personal code makes of a #1775 or #1773 table. *Why:* a partner who is a user in Management's Mercury organization could otherwise create a token there and read Axal's books through a personal card.
4. **Each use is checked in the Worker, on every route.**

   | Use | Who | Reads | Writes |
   | --- | --- | --- | --- |
   | Venture revenue | A founder, for a project whose `founder_id` is theirs (as `revenue.ts:215`) | Own credits | The `revenue_entries` rows the founder picks |
   | Practice income | A partner, for their own engagement invoices (as `needs.ts:761`) | Own credits | A match; `issued` becomes `paid` |
   | Partner deals with Management | A partner, for their own payouts; the deal's own user, for its settlements | Own credits and debits | A match |

   - Any other pairing answers 403 `purpose_not_allowed`. A member whose role has left `personal_roles` gets 403 on every read but can still disconnect.
   - Payout and settlement matches are HQ only. On a branch (`branchOf`, `util/branch.ts:87`) they answer 403 `HQ only` (`HQ_ONLY`, `util/branch.ts:45`), because only Management's payments are matched. Revenue imports and invoice matches work on a branch.
   - A support session (`impersonated_by`, read with `selectJwt(c)` as at `mcp_consent.ts:79`) is refused with 403 at connect and on every personal read and write. Disconnect stays open to it: it only removes access, and the generic route logs it (`integrations.ts:576-598`). An admin never reads a member's bank by acting as the member.
   - No cron, admin route, #1775 or #1777 code, Eadwyn reader (`CONNECTOR_READERS`, `eadwynReaders.ts:132`) or MCP tool reads a personal connection or its matches. The admin profile drawer keeps listing a member's connections by provider and status only (`routes/admin.ts:285-295`); that is not a read of the bank. Management sees a match's facts only on the payout or settlement it matched (decision 7).
   - *Amended by D752 (#1886):* the table gains `capital_attestation` (an investor, HQ only, its routes in #1888), with the founder's `venture_spend` and `raise_receipts` to come (#1889, #1887). `HQ_ONLY_USES` (`partner_deals`, `capital_attestation`) replaces the single `partner_deals` test. "No admin route reads a personal connection" still holds.
5. **Read on demand; store almost nothing.**
   - No scheduled sync. A personal connection is read only inside a request its owner makes.
   - A read covers 90 days by default, at most 366, and at most 1,000 transactions, with a 10-second deadline per call (`withDeadline`, `util/deadline.ts:41`). A 401 or 403 marks the row `error`.
   - Request values are checked before anything reaches Mercury: a `transaction_id` must be a UUID, and `from` and `to` calendar dates. Otherwise the route answers 400 and calls nothing.
   - Candidate lists are built per request, never stored or cached. They show the member, and only the member, each line's date, amount, last four and counterparty name, so the lines can be told apart.
   - Stored: the encrypted token; the organization's id and name (`external_account_id`, `external_account_name`); the revenue rows a founder imports and their `connector_fed_items` links; and match rows (transaction id, last four, signed cents, posted date, target). No balance, memo, counterparty name or full account number.
   - Each read writes one `integration_logs` row with the use and counts in `response_summary`, never a payload (`D684.md:272`), so the member's own `/:uid/logs` lists every read.
   - *Amended by D752 (#1886):* what a proof-of-funds statement stores is set by D752 section 3: a floor, a date and the organization's name, never a balance.
6. **Revenue import: the founder picks, and the Worker re-reads.**
   - Candidates are posted USD credits; cancelled and failed lines are not listed. Each of these is listed with its reason and cannot be imported:
     - `pending`;
     - `internal_transfer`, for the kinds D710.md records as transfers;
     - `axal_entity`: the counterparty names an Axal entity, so it is capital or a partner deal, not customer revenue;
     - `stripe_payout`: the counterparty names Stripe while the project holds a `stripe` row or the founder has an active Stripe connection, since every Stripe sale would count twice;
     - `already_imported`.
   - Import re-reads each transaction by id from the founder's own connection. Amount and date are Mercury's, never the request's; the amount becomes integer cents through #1775's `parse.ts`, never a float multiply here. The row has `source = 'mercury'` and `source_ref` = the transaction id. One bank line is one row on the whole platform.
   - The customer is the label the founder types. The Worker never copies Mercury's counterparty name in, as D587 keeps names out (`integrations/providers/stripe.ts:630-632`, `revenueLedger.ts:254-256`).
   - **Verification is `supported`, never `verified`.** A bank credit proves money arrived, not that it was a sale. `verified` stays a Stripe sale record (`revenueLedger.ts:13-19`). Amount and date are locked, as a Stripe row's are (`revenue.ts:280-291`); type, label, notes and proof stay editable.
   - The row lands only in the project imported into, which must be the founder's own and in their active company (`loadProject`, `revenue.ts:67-75`).
   - Each row also gets a `connector_fed_items` link (`445_connector_fed_items.sql:14-26`) in module `revenue_and_traction`, upserted on `(integration_id, external_id)` so a re-import after a delete points the link at the new row. `mercury` joins `FED_LEDGER_PROVIDERS` (`fed.ts:13`).
7. **Payment matches: proposed from the member's own bank lines, confirmed by the member.**
   - **Engagement invoice:** a credit equal to `total_cents` (never a total of 0), on an invoice whose `currency` is `USD` (stored upper-case, `engagementInvoices.ts:130`), posted within 180 days of `issued_at`. Confirm turns `issued` into `paid`, `paid_at` = the posted date; an invoice already `paid` gains the evidence. The founder sees the date, never the last four.
   - **Payout:** a credit equal to `amount_cents` whose counterparty names Axal VC Management LLC, posted within 60 days of the request, on the account ending in `destination_last4` when set (`409_payout_destination_and_leaderboard.sql:4-11`). A `failed` payout is never proposed. Its status stays the Super Admin's (`network.ts:842-917`). The partner reads "Received"; `GET /admin/payouts` shows the date and last four.
   - **Settlement** (decision 8), once issued: a credit for `to_member` or a debit for `from_member`, equal to its amount, counterparty Management, posted from 30 days before the due date to 90 after. Confirm turns `issued` into `matched`.
   - A target is named by its integer `id`: a payout requested before migration 393 has no `uid` (`network.ts:909`).
   - When several lines fit, all are listed and the member picks one. One bank line has at most one match, and one target has at most one.
   - Withdraw takes a reason of at least 10 characters. A settlement returns to `issued`, a payout loses "Received", and an invoice stays `paid`, as the partner's own word today.
   - USD only. A non-USD payout or invoice is never matched.
8. **Partner-deal settlements: one amount a signed deal says moves between the member and Management.**
   - New `partner_deal_settlements`, with Management as the only possible counterparty (a CHECK). Kinds: `revenue_share`, `capital`, `equity_for_services`, `other`. Direction: `to_member` or `from_member`.
   - `capital` means money between the member and Management under a capital partnership. An LP contribution to the Fund is a capital-call line, which only #1775 matches, on the Fund's own account (`partnerDeals.ts:139`).
   - An Admin drafts, edits or deletes a draft: `requireAdmin` (`auth.ts:523`), then refused on a branch with `HQ_ONLY` as `requireSuperAdmin` does (`auth.ts:694`; 403 through `util/authErrors.ts:92`). Not `requireHqAuthoring`, whose refusal speaks of templates (`util/branch.ts:53`).
   - Only a Super Admin issues or voids, behind `requireSuperAdminWriteBar` (`auth.ts:1041-1045`), as #1774 and #1777 issue. That bar checks TOTP and the step-up before the elevation, so issue and void, after the same `requireAdmin` and branch refusal as drafts, refuse an admin without the elevation (`isSuperAdmin`, `auth.ts:669`) with 403 `{ code: 'super_admin_required', detail: 'Super admin required' }`, before any TOTP or step-up demand, and write nothing. A plain Admin is never asked for a code it cannot use. This is an inline check; if #1779's `assertAdminAct` is on `main` with a row for these acts when this PR opens, the routes call it instead. Void takes an `issued` row; a `matched` one is withdrawn first.
   - A trigger fixes an issued row's deal, kind, direction, amount and due date, and keeps a `void` row final. A correction is a void plus a new row. A memo with a run of eight or more digits is refused.
   - The member reads their own issued, matched and void rows, never drafts.
   - *Why:* nothing else records these payments. Computing an amount from a deal's rate or base is not here.
9. **No money moves.** Nothing sends, transfers or requests money. Payout methods and the Super Admin's complete step are unchanged. #1775's guard test scans every file this task adds.
10. **The dead doors and the key sheet.**
    - `frontend/src/lib/revenueLedger.js` gains `ledgerSourceLabel(source)`: "Manual", "CSV import", "Stripe", "Mercury", and "Unknown source" for anything else, never "Manual". `RevenueLedger.jsx:272` uses it. A `supported` row from `mercury` without a proof document reads "Matched to a credit in your Mercury account", not "Proof document attached".
    - The checklist keeps the key `ef.plaid`, so saved progress survives, reads "Connect Mercury (verify revenue)", and counts an active `mercury` row. It says revenue, not cash, because cash is not a permitted use.
    - For `mercury`, the key sheet shows a banner as HubSpot's does (`ConnectorSheet.jsx:667-671`): create a **Read Only** API token in your own Mercury organization, never Read and Write. A required checkbox, "This is a Read Only token", sends `config.confirm_read_only: true` from `submitKey` (`:503-513`). The Advanced webhook-secret field is not drawn for `mercury`.
11. **Not here:** cash and burn snapshots in `project_metrics` (not income or revenue); a founder's outgoing payments; advisor payouts (advisors get no card); Build's `bank` core system; completing a payout; structured deal terms.
    - *Amended by D752 (#1886):* cash, burn and a founder's outgoing payments come with D752 section 5 (`venture_spend`, #1889).
