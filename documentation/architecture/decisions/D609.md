## D609 — Reference checks: an investor reads and changes only the references on deals they can open

**Issue:** #1309, found by #1165's audit (area 8, References). **No migration.**

### What was decided

1. **Every reference check scoped to its deal.**
   - Reads (`GET /`, `GET /:id`): an admin, or an investor with access to the deal via `investorHasDealRelationship` (invited to the deal or holds a commitment on it, matching `loadDealForRead` in `routes/deals.ts`).
   - Writes (`POST /`, `PATCH /:id`, `DELETE /:id`, `POST /:id/consent`): the same access rule.
   - Founders and partners remain refused (403 Forbidden), preserving the route's original gate.
2. **`GET /` requires `deal_id`.** Calling `GET /api/references` without `deal_id` returns 400 `deal_id_required`. The previous cross-deal list of 200 items across all deals is removed. Analysis of `frontend/src` confirmed that `ReferenceChecksPanel.jsx` already passes `dealId` via `api.listReferences(dealId)`.
3. **No existence leak.** A reference on a deal an investor cannot open returns 404 `Reference not found`, matching the missing reference response so existence is never leaked.
4. **Deal existence check on create.** `POST /api/references` verifies the deal exists in the database and returns 404 when it does not or when the investor cannot open it.

### Verified

`cloudflare-worker/test/reference_checks_deal_access_d609.test.ts` covers:
- Admin access on any deal across all routes.
- An invited investor accessing references on their invited deal.
- A committed investor accessing references on their committed deal.
- An uninvited/uncommitted investor refused with 404 across reads and writes (list, get, post, patch, delete, consent), asserting database rows remain unchanged.
- Founders and partners refused with 403.
- `GET /` without `deal_id` returning 400 `deal_id_required`.
- Cross-deal reference reads, writes, and consent calls returning 404.
