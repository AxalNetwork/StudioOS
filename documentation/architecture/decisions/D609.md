## D609 — Reference checks: an investor reads and changes only the references on deals they can open

**Every reference-check route now checks the reference's deal with the
deal-room reader rule. An investor sees and changes only the references on a
deal they are invited to or committed on, and an admin those on any deal.**
Slot S10, issue #1309, 2026-10-07. Found by #1165's audit (area 8,
References). No migration.

### What was open

`routes/references.ts` (mounted at `/api/references`) checked only "admin or
investor":
- `GET /` without `deal_id` returned up to 200 reference checks from every
  deal, and with one, any deal's.
- `GET /:id` returned any reference, transcript included.
- `PATCH /:id`, `DELETE /:id` and `POST /:id/consent` changed, hard-deleted
  or wiped any reference.
- `POST /` created a reference on any existing deal.

A reference check holds a third person's name, email, role, consent and notes.
So any investor could read, edit or delete those records on deals they had no
part in.

### The rule

- **Who reaches the routes:** admins and investors, as before. Founders and
  partners stay out (`gate`, 403), as the route always intended.
- **Which deals:** the reader rule deal rooms already use.
  `userMayReadDeal(env, user, dealId)` is exported from `routes/deals.ts`. It
  reads the deal and its project's founder, then calls the same
  `canReadDeal` that `loadDealForRead` uses, unchanged:
  - admins (and partners) read any deal;
  - a founder reads their own project's deal;
  - an investor reads only a deal they are invited to (`deal_invitations`) or
    committed on (`commitments`).

  It answers false for a deal that does not exist. Founders and partners
  never get this far in this file.
- **Reads and writes alike.** Listing, reading one, creating, updating,
  deleting and recording or withdrawing consent each require that the caller
  may open the reference's deal.

### No cross-deal list

`GET /` now requires a `deal_id` that is a positive whole number. Without
one it answers `400 deal_id_required`. Nothing in `frontend/src` lists
references without a deal:
- the only caller of `api.listReferences` is `ReferenceChecksPanel.jsx`, which
  passes its `dealId` prop;
- that panel is not mounted anywhere. Its screen waits on the area 8 design
  on #1165, so it was not touched here.

### Not found, not forbidden

A reference on a deal the caller cannot open answers `404 Reference not
found`, the same body as a missing reference. A deal the caller cannot open
answers `404 Deal not found` on the list and on create, the same as a deal
that does not exist. So a reference's or a deal's existence does not leak to
someone outside it. The 403 is kept for the role gate only, which reveals
nothing about a particular deal.

### Create checks the deal

`POST /` checks the deal through the same rule. A deal that does not exist,
or one the caller cannot open, is a 404, and a `deal_id` that is not a
positive whole number is a 400.

### Guard

`cloudflare-worker/test/references_deal_scope_d609.test.ts` runs the real
router on `node:sqlite` with the baseline tables. It covers the list, one
reference, update, consent, delete and create. For each route it checks:
- an admin, on either deal;
- an investor who is invited, committed, or neither;
- a founder and a partner, refused;
- the list without (or with an unreadable) `deal_id`, refused;
- another deal's reference or deal answering exactly like a missing one;
- refused writes leaving the rows unchanged.

Seven mutants were each caught:
- the per-reference deal check;
- the `deal_id` requirement;
- the list's deal check;
- the create's deal check;
- the role gate;
- a missing deal read as allowed;
- every deal read as allowed.
