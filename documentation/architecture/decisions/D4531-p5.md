### 1. The rubric and the judge

`RUBRIC` is version 1. It scores an output from 1 to 5 on five criteria: grounded, missing data said as Not recorded,
calculations on assumed inputs kept conditional, instructions in the records treated as data, and useful. A score of
4 or more meets the rubric. `JUDGE` is one pinned model (`@cf/meta/llama-3.3-70b-instruct-fp8-fast`, offered to
agents and not an Anthropic model), at temperature 0 with 60 output tokens. It runs through `aiRouter.run()` with
`pinned: true`, so there is no fallback. The judge must answer `{"score": n}`; any other answer is recorded as
`not_run` with our own sentence, never as a score. The system prompt says the records and the output are data.

A new wording, scale, pass mark or judge model is a new `RUBRIC.version` or `JUDGE.model`. Results and agreement are
read per version and per judge model. Labels are kept per rubric version.

### 2. What is judged, and what is stored

| Kind | The output | Its key on the row |
| --- | --- | --- |
| `calibration` | a synthetic output committed in a scenario pack (#4588): each scenario's known-correct output and each targeted incorrect one (`calibrationItems`) | `item_key`: `<case_id>:r<revision>#correct` or `#incorrect.<i>` |
| `case` | a skill draft's output on one of its live golden cases, written fresh by `caseOutput` on a chosen model | `skill_id`, `draft_hash`, `case_uid`, `case_sha256`, `model_id` |

Both kinds come only from synthetic cases. A golden case's records are made up and checked on every write (D4160),
and a scenario pack is committed, made-up text. A row (`agent_skill_rubric_results`) holds the score, `rubric_version`,
`judge_model`, `scored` or `not_run`, our sentence for a run with no score, and the usage-log ids. It never holds the
output: a calibration item's text is already in the repository, and a generated output is judged and then dropped.
The item key carries the scenario's revision, so a changed scenario never inherits an old label or score.

### 3. The $25 monthly cap

- **What counts.** Every call a rubric run makes, generation included, is recorded by the router under the surface
  `/hq/ai-agents/rubric` (`RUBRIC_SURFACE`). The router's guard calls carry the same surface. This counts more than
  the judge alone, so the cap is the stricter reading of "paid judge runs".
- **How spend is read.** `monthSpend` reads the current UTC month's `SUM(est_cost_usd)` for that surface from
  `ai_usage_logs`. That is the provider cost the router recorded, not a member charge, because these runs are HQ's
  own. This is the shape the agents' monthly cap uses (`teams.monthSpend`, by `agent_id`), keyed by surface instead.
- **The check.** Before each call pair, `capRefusal` adds the most the pair can cost (`worstCaseMicro`) to the
  month's spend. That worst case counts each prompt character as a token, the full output allowance, and the
  router's own guard quote; a case run's judge counts the whole generation allowance at 16 characters a token.
  `402 rubric_cap_reached` is returned with `cap_microusd`, `spent_microusd` and `need_microusd`. A press that has
  already judged something stops instead and answers `stopped: { code: "rubric_cap_reached" }`.
- **Unreadable spend.** `503 rubric_spend_unreadable`: an unread month is never treated as a cheap one.
- **Concurrency.** Two presses at the same instant can each pass the check. The overshoot is at most one pair's worst
  case, the same tolerance as the router's own caps. No hold is taken.

### 4. Calibration, and the gate rule

- **Labels.** HQ labels items by hand with `POST /calibration/labels { item, score, note? }`. There is one label per
  item and rubric version, and a later label replaces the earlier one. Each label is audited with
  `agent_skill_rubric_labelled`, recording the score before and after. A label shows its author as `{ uid, name }`.
- **Judging.** `POST /calibration/run` judges labelled items that have no score yet under the current rubric and
  judge model, at most 10 a press.
- **Agreement** (`agreementOf`). Calibration agrees when at least 10 items are labelled (`CALIBRATION.min_items`),
  every one has a judge score, and at least 90% of the verdicts (meets or misses) match (`agree_at`). The exact-score
  matches are reported beside them. Otherwise it is pending, with the reason: `too_few_labels`, `not_all_judged` or
  `below_agreement`. A label whose item no longer exists (its scenario moved to a new revision, as part 4 moves
  two) is kept but neither counts nor blocks.
- **The rule.** Rubric results never count toward the 9-of-10 publish bar.
  `rubricGate(a).counts_toward_publish` is `RUBRIC_IN_PUBLISH_GATE && a.agrees`, and `RUBRIC_IN_PUBLISH_GATE` is
  `false`. Every rubric read and run answers the gate, so HQ sees that rule.
- **Where it would switch.** Two things change together, in one reviewed PR with its own decision, once calibration
  agrees and the owner says so: `RUBRIC_IN_PUBLISH_GATE` in `skillRubric.ts`, and
  `skillLifecycle.releaseDecision` / `evalSummary`, which today read only `agent_skill_eval_results`. Flipping the
  constant alone changes only the label on reads; nothing in the gate reads rubric rows. The test shows a skill's
  `freshness` is identical before and after a rubric run that scored every case 1.

### 5. Routes (Super Admin, as `admin_hq_skills.ts`)

| Route | Does |
| --- | --- |
| `GET /` | the rubric, the judge, this month's spend against the cap (`recorded` or `unreadable`), agreement, the gate |
| `GET /calibration?skill=<slug>` | one skill's calibration items: the synthetic text and records, HQ's label and the judge's latest score |
| `POST /calibration/labels` | `{ item, score, note? }`; 400 `item_unknown`, `score_invalid`, `note_too_long` |
| `POST /calibration/run` | up to 10 labelled items; 409 `nothing_to_judge`, `judge_model_unavailable`; 402; 503 |
| `POST /skills/:uid/run` | `{ model }`: each live case of the HQ draft; 404; 400 `models_invalid`; 409 `no_cases`, `judge_model_unavailable`; 402; 503 |
| `GET /skills/:uid` | the latest score per case and model for the current draft |

Each run is audited (`agent_skill_rubric_calibration_run`, `agent_skill_rubric_run`) with its counts, the rubric
version, the judge model and whether the cap stopped it. Item keys are checked against a fixed shape and then looked
up; every value reaching SQL is bound. No UI is built: the HQ authoring screens are #4537's.

  the judge model not checked; generation off the surface; a partial press refusing; a label or a skill run not
  audited; another model accepted; a label on a retired item counted.
