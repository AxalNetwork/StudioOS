## D9045 — Account data inventory: every store that names a person and what account erasure does to it, checked in CI (#9045)

- **Status:** built by S08, 2026-11-27 (#9045, part of #4675; related #5510). Every store is listed; answers nobody has decided are `unspecified` and put to the owner below.
- **Migration:** none. No erasure behaviour changes; this records and tests what the code does.
- **Why:** D8530 lists the stores of a venture, keyed by `project_id` or `company_id`. Nothing listed the stores of a *person*. `services/dsrRequests.ts` says the platform performs no erasure ("no DELETE FROM users, no `deleted_at` and no anonymisation"), `PROCESSING_AND_RETENTION_5510.md` says account data has "no proved automatic global erase", and #4675's drill asks to trace the primary records, files and processors of a person. There was no list to trace from.

### 1. The inventory is code

`cloudflare-worker/test/_account_data_inventory_9045.ts` (`ACCOUNT_STORES`) is the single source: 900 stores.

- **884 D1 tables.** 883 name a person: a column `user_id` or `*_user_id` (604 tables), a column `email` or `*_email` (59), or a foreign key to `users` under another name (`created_by`, `reviewer_id`, ...: 258 tables have only that), plus `users` itself, whose `id` is the user id. Each lists the columns that name the person (`keyed_by`). One more, `agent_task_runs`, has no such column but is listed because the erasure reaches it through the person's agents (`via team_agents.sponsor_user_id`). The issue's measurement (602, 59, 848) was taken before the latest migrations; the replayed schema of 2026-11-27 gives 604 tables with a user-id column and 850 foreign keys to `users`.
- **10 R2 key templates** in `studioos-files`: nine under a user id that Worker source builds (`brand-logos/`, `deck-reviews/`, `headshots/`, `imports/`, `kyc/`, `mercury-statements/`, `program-exports/`, `research/`, `validate-audio/`), and `agent-compute/`, whose objects the erasure reaches through `agent_compute_objects`.
- **2 KV namespaces**: `RATE_LIMITS` (counters and stamps under a user id or an email, such as `last_active:{user_id}`, each with a TTL) and `OAUTH_KV` (the person's MCP OAuth grants and tokens). `TOKENS` holds no key under a person.
- **4 other stores** the test cannot read: the agent runtime of the person's agents (`other:AGENT_SCOPE`), the search vectors of their public founder, partner, advisor and investor entries (`other:VECTORIZE`), job messages in flight (`other:JOB_QUEUE`), and the D1 and KV backups (`other:BACKUPS`).

Each store has one **account erasure** answer: **removed** (`by` names the code), **changed** (`by` names the code), **kept** (with the reason) or **unspecified** (with `today`, what the code does now, and the question below). The erasure is `eraseAccountAgents` (D1530), the only account erasure code there is; the rest of a data-subject erasure is manual (D168). #9046 is wiring it into HQ's close of a data-subject request; that changes when it runs, not what it does to a store.

What it does today: it **removes** 5 stores' rows or objects (`agent_memory_notes`, `agent_task_runs`, `agent_compute_requests`, `agent_compute_objects`, and the `agent-compute/` objects, through `eraseRecordObjects` with a suppression-ledger row), **changes** 2 and keeps them (`scope_tasks`: an open task assigned to the person's agent is cancelled; `agent_duties`: the agent's duties end), asks the agent runtime to erase each agent the person sponsors (best effort, unreadable here), and leaves the other 889 untouched. Nothing is **kept** with a recorded reason: no decision says what an account erasure keeps.

Each store also says whether `GET /api/settings/data-export` carries it (`data_export`). Six do: `users` (profile columns), `activity_logs` (the 500 most recent), and through `exportAgentData` the agents the member can see (`team_agents`), their rule books (`team_rulebooks`), memory notes (`agent_memory_notes`) and run history (`agent_task_runs`). The other 894 are not in the export; the export's own note says a full export is by request to support.

### 2. Choices made here

- **A foreign key to `users` names a person**, whatever the column is called. The issue's rule (a `*_user_id` or `*_email` column) misses 258 tables that hold who created, reviewed or approved a row under names such as `created_by`; an erasure has to find those too.
- **A store D8530 also lists gives the same answer**, compared without the question number (each file numbers its own questions). 276 D1 tables and 3 other stores are in both. D8530 has `agent_memory_notes` removed, `scope_tasks` unspecified and `changed`, and every other shared store unspecified; so does this file. The issue's example of `activity_logs` "kept as the audit trail" is not used: that is D8530's hard-delete answer, and for account erasure D8530 has it unspecified, which the consistency test enforces. Whether the audit trail is kept is Q4 below.
- **The group of a table is read from its name**, in this order: `access` (sign-in, sessions, tokens and `users`), `records` (financial, legal, identity, investment, licence, consent), `communications`, `audit` (audit, log, event and history tables), then `workspace` for a table that also has a `project_id` or `company_id`, else `personal`. The group picks the question. A misplaced table is moved in the module; nothing else depends on the group.
- **Triggers are lifted while the test world is written.** A table's own guard trigger (for example `fund_booklet_answers`: "the booklet is not open") refuses a generic row. The erasure test drops the triggers while it writes the synthetic rows and recreates them before the erasure runs, the way D8530 lifts CHECK constraints, so every write the erasure makes fires its triggers and is checked.

### 3. CI

- `cloudflare-worker/test/account_data_inventory_9045.test.ts` fails when a D1 table names a person and is not listed, when a listed table is gone or names the person by columns other than its `keyed_by`, when Worker source builds a key `` `<prefix>/${<user or email>}` `` under an unlisted prefix (`founder/` and `investor/` are customer chat's plan labels, `NOT_STORES`), when a KV write names a person in a namespace not listed, when an answer is malformed or a D1, R2 or KV store says `unknown`, when a store D8530 also lists answers erasure differently, when the data export reads a table not marked as exported (or a marked one is no longer read), and when an unspecified answer's question has no heading here.
- `cloudflare-worker/test/account_data_erasure_9045.test.ts` (with `_account_stores_9045.ts`, which reuses D8530's row builders) builds the real migrated schema once, writes a row for a synthetic person and one for a control person in every D1 store (every user-id column and every foreign key to `users` names that person, every email column their address), links each person's agent to its run, duty, open task and compute request with a stored object, puts an object under every R2 template, fills the two KV namespaces, runs `eraseAccountAgents` on the person in a rolled-back savepoint and reads every store. A **removed** row or object must be gone, a **changed** one changed, an **untouched** one byte-identical, every KV key still there, the runtime asked to erase only the person's agent, and every control row, object and key untouched. A **removed** or **changed** answer must name `eraseAccountAgents`, and the erasure's source must name the table.

Mutation check (both test files): 20 mutations, 20 caught, 0 equivalent. Among them, a migration that adds `CREATE TABLE synthetic_9045_probe (id INTEGER PRIMARY KEY, user_id INTEGER, body TEXT)` fails the coverage test, and so does the export reading one more table, an erasure that skips the person's own notes or runs, keeps the compute object, or deletes a control person's note.

### 4. Questions for the owner

Every `unspecified` answer carries one of these. The module lists the stores of each question; Q1 and Q7 are short enough to name here. Pick a letter per question; my pick is marked.

### Q1 — The account itself and how it signs in

29 stores: `users`, `user_sessions`, `impersonation_sessions`, `passkeys`, `webauthn_challenges`, `magic_link_tokens`, `member_api_keys`, `email_change_requests`, `support_handoff_codes`, `user_recovery_state`, `push_subscriptions`, `oauth_state_tokens`, `provider_oauth_keys`, `calendar_feed_tokens`, `mail_nonces`, `mail_accounts`, `user_apple_links`, `user_google_links`, `google_oauth_tokens`, `google_sheets_oauth_tokens`, `microsoft_oauth_tokens`, `auth_recovery_tickets`, `auth_sms`, `auth_totp`, `auth_trusted_contacts`, `rate_limit_logs`, `super_admins`, and the KV namespaces `kv:RATE_LIMITS` and `kv:OAUTH_KV`. Today the erasure leaves every one; the account can still sign in.
**A** (my pick): erasure ends every session and grant and removes every credential, token and connected-account link; the `users` row is anonymised (name, email and profile cleared, `id` and `uid` kept so records that must stay still resolve) rather than deleted.
**B**: delete the `users` row and let foreign keys decide; every table that refuses is decided under its own question.
**C**: keep erasure manual (D168).

### Q2 — Financial, legal, identity and investment records, which may carry a hold

200 stores: KYC and KYB cases and documents, sanctions screenings, tax forms and 83(b) trackers, cap tables, SAFEs, closings, e-signatures, fund ledgers, capital calls, LP and investor records, licences, invoices, payouts, credit ledgers, consents and legal acceptances (198 D1 tables), and `kyc/{user_id}/` and `mercury-statements/{user_id}/` in R2.
**A** (my pick): keep them under a legal hold with the reason recorded per class, and remove the person's name and email from them where the record stays valid without it; counsel names the classes and periods (#5510).
**B**: keep them all unchanged until counsel rules.
**C**: remove them with the account.

### Q3 — Messages, notifications, invitations, bookings and calendars

79 D1 tables: notifications, mail drafts and sent mail, chat and assistant conversations, comments and mentions, invitations, bookings, calendar copies, reminders, outreach, and the channel captures (Telegram, WhatsApp).
**A** (my pick): remove what only the person sent or received; in a thread others still use, keep the message and replace the author with "a former member".
**B**: remove every row that names the person.

### Q4 — Audit trails, event histories and security logs that name the person

68 D1 tables, among them `activity_logs`, `admin_audit_log`, `security_events`, `error_logs`, and the `*_events` and `*_log` histories.
**A** (my pick): keep them as the audit trail (the reason D8530 records for `activity_logs` on a hard delete) and replace the person's email and name in their text with the user id.
**B**: remove the person's entries after the audit retention period counsel sets.

### Q5 — What the person wrote or did inside a company or a venture

197 D1 tables that also carry a `project_id` or `company_id`: decks, data rooms, tasks, agents, rule books, research, reports and the rest of a workspace. Two are changed today (`scope_tasks`: an open task assigned to the person's agent is cancelled; `agent_duties`: its duties end); the rest are untouched. D8530 Q1 asks the same from the venture's side.
**A** (my pick): the content stays with the company or venture, which still owns it, and the person's id in it is kept as a reference to the anonymised account (Q1 A); a venture whose only owner is erased follows D8530 Q1.
**B**: remove every row the person created.

### Q6 — The person's own profile, preferences, content and activity

318 stores: 311 D1 tables (profiles, preferences, onboarding, learning, saved views, uploads and other rows that belong to the person alone) and seven R2 templates under their id: `brand-logos/`, `deck-reviews/`, `headshots/`, `imports/`, `program-exports/`, `research/`, `validate-audio/`.
**A** (my pick): remove them with the account, R2 objects through `eraseRecordObjects` (reason `erasure_request`).
**B**: decide table by table in a follow-up issue.

### Q7 — Stores the erasure test cannot read: what erasure should do to them

`other:AGENT_SCOPE` (the agent runtime of the person's agents; the erasure asks it to erase each one, best effort, and the test checks that it asked), `other:VECTORIZE` (search vectors of the person's public founder, partner, advisor and investor entries), `other:JOB_QUEUE` (job messages in flight) and `other:BACKUPS` (D1 exports and KV snapshots, 365 days; record files restored from backup already skip erased keys, D6650, but D1 and KV restores do not).
**A** (my pick): a follow-up issue gives each a fake binding in the test and an answer; the vectors are removed with the entry, the queue is not applicable (ids only, for its retry window), and the backups age out with a suppression list applied on restore.
**B**: leave all four open until #4675's drill.

### 5. Limits

- The coverage rule is the column rule above. A store reached only through a parent (a deck's comments through the deck) is covered by its parent's answer and is not listed, except where the erasure itself reaches it. A key template whose interpolation is not named after a user or an email is not found, and KV keys built in a variable before the write are not scanned; the two KV namespaces were found by reading their writers.
- External processors (Stripe, the email provider, Google, Microsoft, meeting providers) are outside this inventory; `PROCESSING_AND_RETENTION_5510.md` §3 lists them.
- The test runs on the canonical schema. The D1 drift guards own any difference from production.
