### What changed

`/admin/programs/spinout-lab` draws the shell's six core sections, the three module tabs the registry names, and the Lab's own three:

| Tab | Address | What it draws |
| --- | --- | --- |
| Overview | `/admin/programs/spinout-lab` | the Lab's tiles, calendar, charts, funnel and Needs you (D937, D947), then the shell's Capability modules |
| Playbook | `/how-it-runs` | the Lab's playbook (D971), unchanged |
| Availability & grants | `/availability` | the shell's section: the grant badge, whether it can be offered, Manage grants |
| Participation | `/participation` | founders taking part and this week's standing (D946's read), and founders by cohort (the calendar) |
| Applications (module) | `/applications`, `/applications/:id` | the queue and drawer (D948), unchanged |
| Cohorts (module) | `/cohorts`, `/cohorts/:ym` | the calendar and one cohort (D947), unchanged |
| Hosts (module) | `/hosts` | office-hours hosts (D970), unchanged |
| Participants | `/participants`, `/participants/:uid` | the participants table and drawer (D949), unchanged |
| Formation | `/formation` | 83(b) review and formation orders (D970), unchanged |
| Graduation | `/graduation` | certificates (D970), unchanged |
| History | `/activity` | the Lab's history (D971), unchanged |
| Settings | `/settings` | the Lab's own Settings (D971), with the shell's member-access editor added |

- **Every address is kept.** The thirteen `App.jsx` lines stay as they are, with `onImpersonate`. The two new addresses are literal routes in `frontend/src/routes/adminProgramsSpinoutLab.jsx`, onto the same `AdminLab`. Until now they fell through to `/admin/programs/:key/…` and drew the registry-backed page. A literal route ranks above `:key`, so every Lab address is one page with one strip. Settings was already the Lab's, so it stays in `App.jsx`.
- **`onImpersonate` on the two new routes.** A route module gets `routeTools` (`guard`, `hqOnly`, `authOnly`, `labRoles`, `effectiveRole`, `user`, `location`), not `App.jsx`'s `handleImpersonate`, and `routes_modules_d528` pins that object's shape. Neither Availability & grants nor Participation draws a door that opens a founder's workspace. So the two routes pass no prop, and nothing is lost. Participants, Cohorts and Applications, which do open a workspace, keep their `App.jsx` lines with the prop. A tab click from a new section to one of those lands on its own `App.jsx` route and gets the prop.
- **The strip.** `labModel.js`'s `TABS` and `AdminLab.jsx`'s literal `HeaderTab` doors list the twelve tabs in the order above. The new test holds the two equal, order and words. The tab keys are unchanged (`how-it-runs`, `activity`), so every test id stays (`lab-tab-how-it-runs` reads Playbook, and `lab-tab-activity` reads History). Each module tab carries `module`, and its path equals `moduleRows('spinout-lab', …)`'s. Applications, Cohorts and Participants are `end={false}`, so each stays lit on its deep link.
- **The registry read is the page's.** `useProgramDetail('spinout-lab')` feeds the header's status pill (the registry's word, so a paused Lab reads Paused; no pill until it answers), Capability modules on Overview, Availability & grants, and Settings' member access. A failed read marks only those. The Lab's own reads still draw, and so do the header's counts.
- **Participation is the Lab's own records** (D5313 step 4), never the shell's "No participation store" line:
  - D946's participants read gives everyone it lists, and how each founder stands this week by the Lab's clock (On track, At risk, In grace, Failed a week, Graduated, Not in a cohort).
  - A founder whose week could not be read is counted apart (`not_read`), never in a row.
  - A standing figure the read did not carry is "Not recorded".
  - The cohort calendar gives each of the twelve newest cohorts with its founder count. A count it did not carry is "Not recorded" with its reason, never 0.
  - Each part answers alone (`labParticipation`).
- **Settings.** `LabSettings.jsx` keeps the cohort size, the grant terms and the fixed rules, each on its own read, and gains the shell's member-access editor (`ProgramShellSections.jsx`'s `Settings`, inside `OnRegistry`). A Super Admin saves `member_access` on `spinout-lab` (`PATCH /api/admin/programs/spinout-lab`), and an Admin reads it.

### Departures from the canvas

- **The Lab's own tabs.** Participants, Formation and Graduation have no registry module key, so they are the Lab's own tabs. They sit after the three module tabs and before History.
- **Overview keeps the Lab's own figures.** It keeps D937 and D947's blocks and adds Capability modules below them, as D5313 did for Perks.
- **The header.** It is still D936's `AdminPageHeader`, with its crumb, facts, scope chip, moved notice and counts, not `ProgramFrame`. Only its status pill now comes from the registry. The HQ-held / Granted pill and Preview founder journey are unchanged.
- **No five-dimension strip.** The Lab never drew one, and this task does not add one.
