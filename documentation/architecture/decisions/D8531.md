## D8531 — The DR drill compares table sets before counting, keeps correctness, RPO and RTO apart, and counts recovery as proven only with the file restore (#8531)

**Decision date:** 2026-11-25. **Scope:** `scripts/d1-backup-manifest.mjs`, `scripts/dr-drill-split.mjs`,
`scripts/dr-restore-lib.sh`, `scripts/dr-drill.sh`, `scripts/restore-d1.sh`, `.github/workflows/dr-drill.yml`, their
tests and `documentation/operations/D1_RECOVERY.md`. No application, Worker, database or migration change. Builds on
D263 (the marker), D523 (the chunked import), D4558 (the manifest), D5337 (one restore path) and #7919 (scalar count
batches).

### Why run 7 failed

`dr-drill.yml` had run eight times and never passed. Run 7 (44774210223, attempt 2, 2026-11-20) imported all 460
chunks, passed the smoke checks, and stopped with `row_counts_unreadable`: "a row-count query failed (a table in the
manifest is missing from the restore)". The message was a guess. The code of that day joined 40 `COUNT(*)` terms per
query with `UNION ALL` and printed nothing of wrangler's answer.

The case was rebuilt offline from what the repository produces, reading no backup and no production data:

1. A fresh schema in wrangler 4.162's **local D1**: `schema_baseline.sql`, every later migration and the synthetic
   fixtures (`agentSyntheticFixtures.mjs`), 1,336 application tables, 10 views, 367 triggers, then `ANALYZE`.
2. `wrangler d1 export --local`, then `d1-backup-manifest.mjs build` (1,338 manifest tables).
3. The repository's own restore functions (`dr_verify`, `dr_import_chunks`, `dr_compare_counts`) against a second
   local D1, through a shim that turns `--remote` into `--local`.

What it showed:

- **The count query itself.** Local D1 refuses a compound SELECT of more than five terms ("too many terms in compound
  SELECT": five pass, six fail). Run 7's code, on an export whose table sets agree (statistics removed), imported all
  20 chunks and then failed with run 7's exact message. **No object kind caused run 7's failure; the 40-term
  `UNION ALL` did**, and #7919's scalar subqueries already avoid it (`main`'s code passes the same restore).
- **Two kinds the manifest lists as tables that the export never creates.** The manifest lists every table with a
  CREATE or an INSERT. `wrangler d1 export` writes `DELETE FROM sqlite_sequence;` and `ANALYZE sqlite_schema;` in
  place of a CREATE, then the rows:
  - `sqlite_sequence` (AUTOINCREMENT's counters). The restore creates it as a side effect of the AUTOINCREMENT
    tables, so its rows restore and count correctly; with no rows, the manifest omits it while the restore holds it.
  - `sqlite_stat1` (and `sqlite_stat2`..`4`), once the source has run `ANALYZE` or `PRAGMA optimize`. The split put
    its rows in the data phase and the `ANALYZE` in the post phase, so `main`'s code stopped at a data chunk on
    "no such table: sqlite_stat1"; run 7's code, given a manifest listing it, would have failed its count.
- **Not found:** virtual tables and their FTS shadow tables (no migration creates one, and `wrangler d1 export`
  refuses a database that has one), and D1's `_cf_*` tables (the export skips them; the remote `sqlite_master` lists
  `_cf_KV`, which local D1 does not have).

With the changes below, the same local run passes: 1,338 manifest tables (2 engine-owned), 1,336 created by the
export, 1,337 restored, table sets agree, row counts match in all 1,337 counted tables.

### What changes

- **The table sets are compared before any count** (`dr_compare_tables`, `d1-backup-manifest.mjs tables`): the
  manifest's tables, the tables the export creates (`d1-backup-manifest.mjs describe`) and the restored
  `sqlite_master` (type, name and whether virtual, never `sql` or a row). A **missing** table (in the manifest, not
  restored as a table) or an **extra** one (restored, not in the manifest) exits 3 with `table_set_differs`, each
  named with its kind: `table`, `virtual table`, `rows only` (the export inserts but never creates it), `restored as
  a view`; extra ones `created by the export, not in the manifest` or `in neither`. Names compare without case, as
  SQLite's do. The count step then reports **unreadable** (`row_counts_unreadable`, with wrangler's error codes) and
  **mismatched** (`row_counts_differ`) apart.
- **Engine-owned tables are never missing or extra.** `sqlite_*` and `_cf_*` are listed as engine-owned with what
  happens to them. `sqlite_sequence` is counted wherever the manifest lists it. The statistics are not restored
  (the split drops `ANALYZE` and the `sqlite_stat*` rows, counted in `dropped_internal`; D1 rebuilds them) and not
  counted. The rule is applied at compare time, so the manifests already in R2 work unchanged, and the manifest and
  the split stay byte-identical to D7142's golden files for every export without statistics.
- **Three results, not one.** `drill-d1.json` (still `schema_version: 1`; every earlier field kept) adds
  `correctness` (`passed`/`failed`, `code`, `step`, and `table_set`: missing, extra, unreadable, mismatched, names
  only), `recovery_point_age` (age, the 24 h target, met) and `recovery_time` (duration, the 4 h target, met;
  `null` when the restore failed, because a failed run has no recovery time). The job summary shows the same rows.
  A met timing target never turns a failed correctness check into a pass. Smoke failures that had no reason now
  carry one (`smoke_zero_users`, `smoke_required_table_missing`); any other failure's code is
  `exit_<n>_at_<step>`.
- **"Proven" needs the file restore.** The `drill` job now `needs: independent-file-drill` with
  `if: ${{ !cancelled() }}`, so it runs after the file drill, skipped or not, and reads its result
  (`FILE_DRILL_RESULT`). The marker records `file_drill` as `passed`, `failed` or `not run`, `recovery_proven` true
  only when the D1 restore and the file drill both passed in the same run, and a `verdict`: "proven: …", "not
  proven: the file drill failed", "not proven: the D1 restore failed (<code>)" or "D1 only: not proven".
