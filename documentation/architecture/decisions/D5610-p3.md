## D5610 part 3 — Make shadow records scorable (#5610)

Part of #5610. Part 1 (`D5610.md`) is the selector, the shadow job and the gate.
Part 2 (`D5610-p2.md`) found that none of 3,652 shadow records could be scored.
This part fixes the causes that sit in the shadow's own files, as the owner
chose on 2026-11-27 (answer A). The shadow still changes no check state:
`selection (shadow)` stays outside `gate`'s needs, keeps
`continue-on-error: true` and exits 0. The #5621 gate is unchanged: **zero
misses across at least 300 scored `pr_failure` runs and zero misses in the
complete backtest**, and the owner decides.

### What changed

1. **The trace lookup asks for the trace by name.** The old step read the
   newest 100 artifacts in the repository. That is one to two hours of
   history, so 877 runs after 2026-11-16 found no trace. The job now lists the
   PR base's first-parent line (`git rev-list --first-parent
   --max-count=21 $BASE_SHA`, which is `STALE_COMMITS + 1`). It then queries
   `actions/artifacts?name=test-deps-<sha>` one commit at a time and stops at
   the first hit. Each query is one call, and the base itself usually has a
   trace: the merge-queue run that tested a SHA publishes `test-deps-<sha>`,
   and that SHA is what lands on main.
2. **The trace is at or before the base, never newer.** The old step took the
   newest main trace, and in 842 runs that trace was 1 to 3 commits *ahead* of
   the base, so the ancestry check refused it. `traceAtOrBefore()` in
   `scripts/lib/selectTests.mjs` picks the newest unexpired artifact named for
   a commit on that line, base first. Only an artifact whose run's `head_sha`
   is that commit counts. The CLI's ancestry check stays as a second guard.
   Staleness is now counted as the trace's distance from the base
   (`<trace>..<base>`), not from the PR's merge commit. The diff is taken
   against the base, so the PR's own commits never made the trace older.
3. **The shadow waits for the verdict.** The job now needs `[suite, classify]`.
   `classify` (`why CI failed (D5398)`) runs only on failure. When it runs, its
   `ci-failures-classified-attempt-<n>` record exists before the shadow reads
   it; before this change the shadow read first in 31 of 46 runs. When
   `classify` is skipped, `always()` still runs the shadow, and the green run
   is unscored, as before. The download takes this attempt's classified record
   by its exact name. Before, a `ci-failures-*` pattern also downloaded the
   per-part records, which have no verdict, and other attempts' records.
4. **A guard failure neither misses nor unscores.** `test:guards` is in
   `ALWAYS`, so a guard can never be a selection miss. Before, one guard row in
   a `pr_failure` made the whole run unscored. Now guard rows are dropped, and
   the run's test failures decide. A run with only guard failures is still
   unscored.
5. **The backtest fixture is replaced** (see below).

### What this part cannot fix: the classifier's verdict

The shadow scores only when the classified record says `pr_failure`. On PR
runs, `scripts/lib/ciFailureCollector.mjs` (#5502, not a file this task owns)
almost always says `main_health_unknown`. It looks for base evidence only in a
**completed main `push` run** for the base SHA. Two things defeat that, both
checked on 2026-11-27:

- Main push runs wait in the Actions queue for hours (#8883). The push run for
  `5997929a55` was still queued, so the lookup gives "No completed main run
  exists for the tested base SHA". That was the warning on 8 of 11 records in
  part 2.
- When a push run does finish, its suite is skipped, because `verified` finds
  the merge-queue run of the same SHA. The push run therefore has no
  `ci-failures-<part>` artifacts, and every PR failure stays `unknown`.

The evidence the classifier needs does exist. The merge-queue run that tested
the base SHA uploads `ci-failures-<part>-attempt-1` for every part, on success
too (checked on run 46047227519 for `ee23155ff6`). A fix in the collector
would read base evidence from that `merge_group` run whenever no push run with
suite evidence exists. That needs a task owned by #5502's files. Until it
lands, records stay unscored even with the changes above, so the 300-run count
does not start.

### Backtest episodes after 2026-11-16

`scripts/lib/fixtures/red_main_episodes.json` (version 2) replaces the 27
episodes from 2026-11-04 to 2026-11-11. None of those 27 could ever be scored,
because no trace existed before 2026-11-16 22:21 UTC.

Method (read-only `gh api`, 2026-11-27):

- **Runs read.** All ci.yml `push` runs on main created from 2026-11-16 were
  read: 574 runs. Of these, 62 failed, and 8 failed a `suite` part. The other
  54 failed only `editor visual regression and axe`, `ci / fast` or
  `dev backend (import smoke)`.
- **Episodes.** An episode is either the first suite-red run after a run whose
  suite was not red, or a run inside a red interval that failed a test file no
  earlier run in that interval had failed. That gives **4 episodes**.
- **Failing files.** These come from the TAP `location:` fields in the failed
  jobs' logs, because the `ci-failures` artifacts had expired.
- **Trace.** Each episode names the trace the shadow rule would have read: the
  newest `test-deps-<sha>` on the first-parent line at or before the parent
  commit that existed when the episode's run started.
- **What is stored.** Only SHAs, run, job and artifact ids, and test paths are
  stored.

| First red | Failing files | Trace (commits before parent) |
| --- | --- | --- |
| `35c4094613` | `cloudflare-worker/test/deck_ensembles_load_d1551.test.ts` | `05f749ec3a` (0) |
| `7dd4beb1b7` | `frontend/test/dr_cleanup_7917.test.mjs` | `821510884e` (0) |

The first episode's file is a timing-threshold load test. A miss there may
come from a flake rather than from the change, and the owner should read it as
such. Four episodes are few. The backtest half of the gate is only as strong as
this set, and the set can be extended the same way while traces are still
retained (30 days).

**Running it.** `node scripts/select-tests.mjs --backtest-evidence <dir>`
downloads each episode's trace with `gh`. It writes replay inputs to
`<dir>/<firstRedCommit>.json`: the first red commit's own diff against its
parent, that trace, and the trace's tests plus any added test files. Then
`node scripts/select-tests.mjs --backtest --evidence <dir>` prints `PASS`,
`MISS` or `unscored` for each episode. A failing file that neither the trace
nor the diff knows can never be selected, so it counts as a miss and never as
a pass.

The session that wrote this part could not download any trace: the egress
proxy refused the artifact blob hosts (`productionresultssa3`, `sa7`, `sa8`).
So **the backtest has not been run on real traces yet.** Each episode prints
`unscored` until an operator runs the two commands somewhere those hosts are
reachable. A run against synthetic traces exercised the whole path,
download, unzip, diff, select and score, and printed a verdict for every
episode.

### Limits

- Drafts do not run the suite (#6460). Only ready-PR failures can score, so
  300 scored runs take longer to collect than 300 runs.
- A `pr_failure` record scores its `own` failures. Failures it leaves
  `unknown` in the same run are not counted, so a miss could hide there.
- A trace older than 24 hours or more than 20 commits from the base still
  falls back to `full`. A PR whose base is that old is never scored as
  selected.
