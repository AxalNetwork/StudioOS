## D5997 — Validate stores and edits the venture's validation objective, "Trying to learn" (#5997)

- **Status:** built 2026-11-15. Filed under #4837. Builds to V1 (the header line "Trying to learn:" under the Validate title) and V11 (after Pivot, restate the objective) of `design/incoming/Validate v2 · Boards.dc.html`; the words are the page canvas's own (`design/incoming/Validate v2 Page.dc.html`).
- **The D4837 gap.** V1 leads the overview with what the venture is trying to learn, but D4837's "Backend required" list named no field for it, and nothing stored one. This decision adds that store, its writer and its read.
- **Migration:** `cloudflare-worker/sql/migrations/202611151331_5997_validation_objective.sql`.
- **Code:** the writer `setValidationObjective` in `services/validateWriters.ts`; the read `services/validateObjective.ts`; the route `PUT /api/cycles/validate/objective?project=` in `routes/cycle_validate.ts`; the client `cycleValidateApi.setObjective` in `frontend/src/lib/api/cycleValidate.js`; the control `frontend/src/pages/cycles/ValidateObjective.jsx`, drawn by `ValidateLead`.

### Storage

A table of its own, `validation_objectives`, one row per venture (`project_id` is the key): `objective TEXT` (nullable), `updated_by`, `created_at`, `updated_at`. It is shaped like migration 440's small Validate stores (`market_readiness_marks`, the `metric_targets` keys): the value, the actor and the time beside it, keyed to the project. `projects` gains no column only Validate reads.

NULL is Not recorded. A clear keeps the row and sets `objective` NULL, so who cleared it and when stay recorded. No venture is backfilled.

The issue wrote the query as `?project_id=`; every Validate write takes `?project=` (the route's one `scope` helper), so this one does too.

### The write

- **Who:** `canWrite`, the gate every Validate write in `routes/cycle_validate.ts` passes to `scope` (the venture's own or an admin). A partner reads the line and is refused the PUT (403); another founder and an investor reach neither. The overview's `can_write` (#5999) is the same check, so the page draws the control only where a save lands.
- **Value:** `{ value: string | null }`. Whitespace collapses to single spaces, so the header stays one line; an empty string or `null` clears it. A missing or non-text value is refused (400), so a malformed body never clears it by accident.
- **Limit: 280 characters**, counted as characters, not UTF-16 units. V1 draws one header line, one question (the canvas's sample is about a hundred characters); 280 leaves room for a precise question and stops a brief from landing there. The writer holds the limit, as every Validate limit is held, and the client checks it first with the Worker's own sentence ("Keep what you are trying to learn to 280 characters").
- **Activity:** one `activity_logs` row per write, in the same `DB.batch`, through `logCycleWriteStatement`: `entity_type = 'validate.objective'`, `entity_id` NULL (a module-level write, S1's ruling on #1736), `objective_set` with "Trying to learn: …" or `objective_cleared`. `CycleModules['validate']` gains `objective` for it. Validate's "Recent changes" part (D5996) reads the six modules only and so does not list it; that is unchanged here.

### The read

`GET /overview` adds `objective`, additive like D5996's parts:

- `{ state: 'ok', text, updated_at, updated_by_name, restate }`, with `text` null for Not recorded;
- `{ state: 'unavailable', reason }` when its read fails (#5129), the rest of the overview unchanged.

### The interim edit control

No board draws an edit field, so the builder chose (per the owner's comment on #5997). Until the V2 header is built, the line leads Validate's desktop lead row (`ValidateLead`, above the next action and the meter), in a white lead-row card:

- recorded: "Trying to learn: <text>", and for a writer a "Change" link;
- empty: "Trying to learn:" with the Not recorded chip, and for a writer "Write it";
- unavailable: the Worker's reason, and no control.

"Write it" and "Change" open one textarea in place (labelled "Trying to learn", a characters-left count), with Save, Cancel and, over a saved objective, Clear. A save re-reads the overview. A Worker refusal shows in its own words. A reader sees the line and nothing to press. A read without `objective` (an older Worker) draws the lead row exactly as before. The phone root does not draw it yet; V2 phone (390) puts it in the V2 header too.

### V11: after Pivot, restate the objective

Built, because the Pivot is cheaply readable: the overview already reads the venture's current given decision through D693's one reader (`currentDecision`) for its Verdict index row. `restate` is true only for a viewer who may write and read decisions, when that decision is Pivot and the objective was not written at or after it (none, cleared, or older). A partner never reads decisions, so the flag is never computed for one. A decision that cannot be read leaves it false, since the prompt is an invitation and leaving it out claims nothing.

With `restate`, the objective card adds the canvas's section: "After Pivot", "Restate what you’re trying to learn", "Your decision changes the customer or offer. Update the objective and hypotheses before planning a build.", and "Update the objective", which opens the same field. Saving clears the prompt on the next read. V11's other two states (Proceed's Plan the build, Stop's review or reopen) are D4589's next action, unchanged.
