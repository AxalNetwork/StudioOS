## D850 — The MCP platform end to end: one flow test through the real Worker, and the owner's switch-on runbook

- **Status:** filed by S21 for S1 as #2473, part of #2463; built by S15. It closes the backend phase of the MCP platform plan (`documentation/architecture/MCP_API_PLATFORM.md`).
- **Basis:** `origin/main` at `87b87a48`. Worker paths are relative to `cloudflare-worker/src/`.
- **Depends on:** D841 (#2464, member API keys, on `main`), D842 (#2470, `/mcp` accepts keys), D843 (#2465, usage rows), D844 (#2466, metering) and D845 (#2471, reports, which merged into #2465's branch and reaches `main` with it).

### 1. The decision

The backend phase is done when one test walks a member's whole path through the real Worker and passes on `main`:
1. create a key;
2. `initialize` and `tools/list` on `/mcp` with it;
3. call a test-priced tool;
4. see the hold, the settle, and the `api_usage_events` row that names the key;
5. read the report;
6. revoke the key;
7. be refused, 401, on the next call;
8. find no secret in anything printed or stored on the way.

The test is `cloudflare-worker/test/mcp_platform_e2e_d850.test.ts`. It calls `worker.fetch` (`index.ts`'s default export) for every step a client or a member makes, over `node:sqlite` D1 and in-memory KV, as `mcp_server_d666.test.ts` does for OAuth. It never calls a route's handler or a service in place of the request, except to read a verdict the request would not show (`verifyKey` after the revoke).

The owner switches keys on from `documentation/operations/MCP_API_RUNBOOK.md`: the flags, the read-only production checks, the rollback, revoking a member's keys, and the usage reads, which select counts and sums only.

### 2. Built in stages

The test grows with its dependencies. Each step is written when the task that builds it is on `main`, and until then the test asserts what `main` does at that point of the flow, never a stand-in.

**Today, on `main`:**
- **The flow, steps 1, 6 and 8.** A key is created through `POST /api/developer/keys` and listed without its secret. It is revoked through its route, after which `verifyKey` answers `revoked_key`. No printed line, `activity_logs` row or `member_api_keys` row holds the secret or the whole key.
- **The rollback.** A key made with `API_KEYS_ENABLED` on is refused once the flag is off: the key routes answer 404 and `/mcp` answers 401 to the `axk_` bearer, without echoing it. This is the runbook's §4.

**When #2470 merges:** steps 2 and 7, through `/mcp` with the key as the bearer.

**When #2465 and #2466 merge:** steps 3 and 4.

**When #2465 merges (carrying #2471):** step 5.

### 3. An open question: how the test prices a tool

#2466 (D844) prices every registered tool at 0 in `METERING_POLICY` v1. A test passes a priced policy as `callTool`'s last parameter, which a request through `worker.fetch` cannot reach. Step 3 needs one of these:
- **A.** A test-only seam in `services/metering.ts` (for example a module-level override that only tests set), so the real `/mcp` path runs a priced test tool. This is S15's choice: the flow stays one path.
- **B.** The test runs steps 3 and 4 through `callTool` with the principal `verifyKey` gives, and every other step through the Worker.
- **C.** A real tool gets a price above 0 in the policy. That changes what members pay, so it is the owner's call and not this task's.

S1 answers on #2473.
