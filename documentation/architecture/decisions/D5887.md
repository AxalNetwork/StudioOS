### What changed

`/admin/programs/learning` now draws the shell's six core sections, with Learning's own screens where it has them:

| Tab | Address | What it draws |
| --- | --- | --- |
| Overview | `/admin/programs/learning` | Learning's tiles, Completion by program, Enrolments per week and the programs table (D962), then the shell's Capability modules |
| Playbook | `/how-it-runs` | the playbook editor (D962), unchanged |
| Availability & grants | `/availability` | the shell's section: the grant badge, whether it can be offered, Manage grants |
| Participation | `/participation` | Active enrolments (R9, published programs) and Enrolled this period (P4, 12 weeks), from the reads Overview already makes; People taking part: "Not recorded" |
| Learners (module) | `/people` | People (D962), unchanged, at `MODULE_PATHS.learning.learners` |
| History | `/activity` | the activity read (D962), unchanged |
| Settings | `/settings` | the shell's member-access editor (Super Admin) or its value (Admin) |

- **Every address is kept.** The four D953 and D962 gave Learning keep their paths and their `App.jsx` lines. The three new ones are literal routes in `frontend/src/routes/adminProgramsLearning.jsx`, onto the same `ProgramPage`. Until now they fell through to `/admin/programs/:key/…` and drew the registry-backed page.
- **The sections are the shell's.** Availability & grants and Settings come from `ProgramShellSections.jsx` inside `OnRegistry`; Capability modules on Overview from `shellModules('learning', detail.read)`. A failed registry read marks only those sections; Learning's own reads (Overview, Participation, Learners) still draw, and Modules say "Could not be read", never "None yet".
- **The header's status is the registry's** (`status={registryStatus(detail)}`), as on Perks, so a paused Learning reads Paused. Before, it was the frontend constant's.
- **Participation is never a 0 that was not measured** (`learningParticipationTiles` in `programPagesModel.js`). Learning counts enrolments, not people (`ENROLMENTS_NOTE`: a person in two programs is two enrolments), so the two enrolment tiles show what is recorded, a measured zero as 0, and "People taking part" is "Not recorded" with its reason whatever the enrolments say. A failed read is "Could not be read", never 0. `useLearningReads` now makes R9 and P4 on Participation too.
- **The strip.** `PAGES.learning.tabs` and `ProgramTabs.jsx`'s `LearningTabs` list the seven tabs in PG03's order and words, each a literal `<Tab to="…">`. The module tab carries `module: 'learners'`; its key stays `people`, so its test id stays `programs-tab-people`.

### Departures from PG03

- **Overview keeps Learning's own figures.** PG03a draws its preview cards; Overview keeps D962's tiles, charts and programs table, and adds Capability modules, as D5313 did for Perks.
- **The module tab's word.** `MODULE_LABEL.learners` is "Learners", and the tab reads "Learners"; People's card was already titled "Learners". Its key and address stay `people` and `/people`, so D953 and D962's People tests pass unchanged.
- **No count on the module tab.** Learning's People has no queue, so the tab carries no count (a strip never reads "[0]", D953).
- **No header action.** Perks gained "Review perk queue" because its module is a queue; Learning's Learners is not one, so the header gains no primary action, and Download (CSV) stays D1124's ⋯ menu.
- **No new module chip.** A module arrives with its screen, so nothing here switches one on (D4873 part 4).
- **Participation for a plain Admin** covers the programs assigned to them, as R9 and P4 do; the card says "assigned to you".
- **No five-dimension strip of its own.** The header already draws the five dimensions (D4807), from the registry read.
