- **Status:** built 2026-11-19 for #7714 (filed under #3701 from the owner's Research › Markets audit of the same day). No migration.
- **Code:**

- **Open, for the owner on #5013:** the repair of the one value without history and the import of the figures. Neither is a closing condition here.

### Why

The audit counted 49 profiles, population in 34 and PPP GDP per capita in 34, with 34 population history rows and 33 PPP history rows: one PPP value has no history row. The two tables (`country_market_profiles`, `country_market_observations`) belong to the licence-pricing catalogue (D5014, D5016). The supported writes change both in one batch, but the database does not tie them together and nothing compared them. No dataset, script or record of the earlier import is in the repository, so how the value lost its row is not known; this decision assumes neither a hand write nor a route fault.

### The decisions

1. **One read compares every profile field with its latest history row.** `GET /api/admin/licence-pricing/consistency`, `requireSuperAdmin` (HQ only, a plain admin and a branch refused), writes nothing and touches no snapshot. It sits outside `/countries/` and `/catalogue/`, where `/:code` would take the path. It needs no auth-ledger entry: it is gated.
2. **What is a finding**, per country and per field of `OBSERVED_FIELDS`:
   - `value_without_history`: the profile holds a value and the field has no row;
   - `differs_from_history`: the value, status, source, reference or as-of date differs from what the latest row says the profile should hold (`differences` names which);
   - `cleared_but_history_holds_value`: the field is not recorded, yet its latest row holds a value;
   - `history_ahead_of_profile`: the latest row names a revision above the profile's.
3. **What is not:** a seeded field with no rows and no value, and a profile revision above the latest row's. `updateDetails` raises the revision with no history row by design, so "a row at the profile's revision" is not the test.
4. **What the latest row says the profile should hold.** A value row: its value and provenance. A `not_recorded` status row: nothing. A `provisional` status row: the value it marked (it carries one, so "a value row exists" is not the test either), and the provenance of the last value row that no `not_recorded` row cleared since. A rank holds only its value on the profile (a rank write changes no status, source or date), so a rank is compared on its value only.
5. **Each finding carries both sides and what sits beside it:** the profile's side, the latest row, what that row expects, and the frozen pricing snapshots that hold the value at stake for that field (the profile's value, or the history's where the profile holds none): their count, up to 50 of them, and how many pricing decisions name them. Snapshots are never changed (D5014).
6. **The answer says how much it checked** (`checked.countries`, `checked.fields`), so an empty list cannot be read as an unread table. The latest rows come from one literal query over the history (window functions, no parameter); `observationsFor` is per country and capped. The snapshot lookups bind the country, the field and the value; the field picks its column with a bound `CASE`, never an interpolated name.
7. **Which figures are missing is not rebuilt.** The catalogue read already answers it (`GET /api/admin/licence-pricing/catalogue?incomplete=1`, D5020).
8. **The builder makes the import body and nothing else.** `scripts/build-country-import.mjs` reads a reviewed source file (CSV or JSON: country, field, value, status, source, reference, as-of date), a saved `GET /api/admin/licence-pricing/countries` read (the priced `/catalogue` list holds no figures, and is refused), optionally a saved consistency read and fields named again (`--again CODE:field`), and a reason. It writes `{ observations, expected_revisions, reason }`.
   - It leaves a row out only when its value, status, source, reference and as-of date all equal the profile's; a rank, which holds only a value on the profile, when its value does. A field the consistency read reports, or one named again, is never left out.
   - It refuses, naming the row: a missing source, date or status, a value that is not an integer (nothing is rounded), a country not in the read, an unknown field, a provisional rank, a field listed twice, a source or reference the route would cut, and more than 500 rows to send. It never supplies a status, source or date.
   - With nothing to import it writes no file and says so. It calls no API, holds no credential, and refuses to write the body inside the repository. The source file, the saved reads and the body are never committed.
9. **The repair of the one value follows answer B until the owner answers.** B: record the checked figure again with its source, reference and as-of date, one write, the reason saying why. A: first mark the field not recorded with a reason, then record it; two writes, and the market cannot be priced between them. Either is a Super Admin act the owner runs. The builder works under both: under B the consistency read keeps the field in the body even when it equals the profile.
10. **No migration and no trigger.** Nothing here inserts or enforces history; the read reports and the owner repairs through the routes.

### What the real-shape test found

One import of two fields (population and PPP) for every one of the 49 seeded countries, built by the builder and sent through the import route over real SQLite, applies whole (`200`, two rows per country, 98 history rows) and leaves no finding. On this evidence the supported route does not leave a value without history. The test runs on SQLite through the D1 test binding, not on D1 itself.
