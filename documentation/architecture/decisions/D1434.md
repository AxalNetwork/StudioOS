## D1434 — The owner-run Stripe mode cutover, and portal plan switches

Part 2 of #3703, taken by S21 at the owner's request; it was S08's. Part 1 is D1433 (migration 691), and part 3 is the member and HQ screens. This decision adds no migration: migration 691 already holds `stripe_mode_cutovers`.

### Why

Production ran on Stripe's sandbox (test) account (migration 654's header). Every stored customer, subscription, saved card and mirrored price is therefore a test-mode object. Live keys can neither charge nor read these objects, so after the keys change, "Manage billing", renewals and auto-reload would all fail against them. The cutover clears them once, after the live keys are set.

### The owner's answers (2026-11-02, on #3703)

- **Q1 = A.** Plans paid on the sandbox go back to free, the stored Stripe ids are cleared, and each affected member is told.
- **Q2 = B.** Plan changes inside the Stripe customer portal are on, as well as the in-app sheet.
- **Q3 = A.** Yearly prices are offered (part 3 and #3702).
- **Q4 = A.** Stripe Tax is on in live (an owner step on #1008).

### The route

`GET` and `POST /api/admin/stripe/cutover`, in `routes/admin_stripe.ts`, behind the `/api/admin/stripe` recovery cool-off. The rules live in `services/stripeCutover.ts`.

**Read.** `GET` is for the Super Admin. It returns:
- the keys' mode;
- `stored_mode`, the last cutover's target, or `test` when none ran;
- the last cutover row;
- the counts the move would clear.

Every count is bound SQL, and one that cannot be read is 503 `cutover_unreadable`, never 0.

**Order of refusals.** `POST` first takes the Super Admin write bar (`requireSuperAdminWriteBar`). It then checks, in this order:
1. a reason (`paymentChangeReason`, the D1009 rule);
2. a mode of `live` or `test`;
3. `confirm` typed as that mode;
4. a secret key that is set;
5. keys already in the target mode (**keys go first**);
6. stored records not already in it.

Each refusal leaves every row, the cache and Stripe untouched.

**The batch.** Plans are reset before the ids they are found by are cleared. Seat colleagues are reset before their primary.

| Store | What changes |
| --- | --- |
| `users` founder columns (migration 011) | `subscription_tier` free, status `cancelled`, renewal cleared, where a Stripe subscription id is held. Then `stripe_subscription_id` and `stripe_customer_id` are cleared on every row. |
| `users` investor columns (migration 027) | The same for `investor_tier` and its accepted seat colleagues (`investor_seat_primary_user_id`), with the free deal-room cap. Then the investor ids are cleared. |
| `account_subscriptions` (migration 134) | Held plans (`active`, `trialing`, `past_due`) with a subscription id become `free`. Then the ids are cleared. |
| `mi_pro_subscriptions` (migration 103) | The same. |
| `member_ai_auto_reload` (migration 511) | Saved cards are cleared and auto-reload is turned off, with `disabled_reason = 'stripe_mode_cutover'`. |
| `billing_alerts`, `member_subscription_amounts` | Open alerts are closed and amounts marked canceled. Both name sandbox objects. |
| `ai_token_packs` (migrations 486 and 654) | Every pack still on the shelf is archived (`on_sale = 0`, `archived_at` set). Its price is the old mode's and cannot be charged under the new keys. HQ › Token packs creates the packs again on the new account. |
| `stripe_products` | Emptied. The sync after the batch refills it in the new mode. |
| `stripe_mode_cutovers` | One row, with the actor, the reason and the counts. |

**What is kept.** A plan granted without a Stripe subscription (a complimentary grant) has no subscription id, so it is kept.

**Counts.** The row is inserted in the batch with the counts read just before. If a statement changed a different number of rows, the row is corrected to what was done.

**After the batch:**
- both mode-scoped catalogue caches are deleted and `syncCatalog` runs;
- a failed sync is 502 `cutover_sync_failed`, and the cutover stays recorded, because the next catalogue read heals the mirror (D1433);
- each member whose plan was reset gets one in-app notice (`billing_plan_reset`, category `billing`, link `/pricing`);
- one `logAdminAction` row records the counts, the notices sent and the sync result.

**Change log.** HQ's payments change log adds the kind `mode` ("Stripe mode") for `stripe_mode_cutover`.

**Known window.** Two cutovers started in the same second could both pass the "already done" check. The write bar, the typed confirmation and the single owner make this unlikely. The second run would also find nothing left to clear, and would write a second row.

### AI credit top-ups in live

The owner asked that top-ups work on the live account too. A read of the live account on 2026-11-03 found:
- five one-time prices, all for incorporation;
- no token pack price;
- no $1 unit price.

Until those exist, every top-up correctly reads "not available yet" under live keys (D1433's readiness rule). Three parts go live:

1. **Packs** are rows of `ai_token_packs`, each naming one Stripe price.
   - The four seeded by migration 654 ($10, $25, $50 and $100) are sandbox prices.
   - The cutover archives them (above).
   - After the cutover, HQ › Token packs › New pack creates each pack on the live account (the D755 path: one product per pack, `metadata.kind = token_pack`, a one-time USD price).
   - The webhook credits a pack on `payment_intent.succeeded` exactly as in test, through D1433's event ledger.
2. **The custom amount** ($5 to $500) is N of a $1 one-time USD price.
   - `aiTopupUnitRaw` (`services/aiTopups.ts`) now reads the price for the keys' mode: `STRIPE_PRICE_AI_TOPUP_UNIT_LIVE` under live keys, and `STRIPE_PRICE_AI_TOPUP_UNIT` under test keys.
   - A live key never quotes the sandbox price, and with no live price set the custom amount is not offered.
   - The owner creates a live $1 one-time USD price. Its public id is then set as `STRIPE_PRICE_AI_TOPUP_UNIT_LIVE` in `[env.production.vars]`, which is a price id, not a secret.
   - Because both ids sit side by side, the switch of keys needs no edit of the existing var.
3. **Auto-reload** saved sandbox cards, which the cutover clears and turns off. A member saves a live card again on `/account/usage`.

### Portal plan switches (Q2 = B)

A plan switched in Stripe's portal keeps the metadata stamped at checkout (`kind: tier`, `tier: growth`) while its item moves to the new price. The in-app swap re-stamps the metadata; the portal does not.

`subscriptionPlanEvent` (`services/planSubscription.ts`) now reads the plan from the subscription item's current price on every `customer.subscription.*` event. The item's plan wins only when it sells a plan of the **same family** as the stamped `kind`, so the event then grants through the webhook's existing path. A price of another family, a price the catalogue does not know, or a catalogue that cannot be read leaves the metadata as it came. The webhook's take-over rules are unchanged, because it is the same subscription.
