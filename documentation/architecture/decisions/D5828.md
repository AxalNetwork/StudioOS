- **Code:** `cloudflare-worker/src/services/typeform/` (`api.ts`, `mappings.ts`, `importer.ts`, README). No route, no frontend, no edit to `index.ts`.
- **Migration:** `202611150138_5828_typeform_responses.sql`, additive: four new tables.

### Stores

| Table | One row per | Holds |
|---|---|---|
| `typeform_form_syncs` | connection (`integrations.id`), venture (`projects.id`), form | checkpoint, run lease, last outcome, `retry_after`, backfill request |
| `typeform_field_mappings` | mapped field, by Typeform's stable field id | type, last-seen title, demand kind, qualifying rule, `keep_text`, `active` / `field_deleted` / `type_changed` |
| `typeform_responses` | response id | `completed` or `partial`, submitted/landed dates, `active` / `withdrawn` / `provider_deleted` |
| `typeform_answers` | response and mapping | the founder-selected field's qualifying text only |

Each answer also has a ledger row, `connector_fed_items` (`module = 'demand_signals'`, `kind = 'typeform_answer'`, `local_table = 'typeform_answers'`), keyed `typeform:<form>:<venture>:<response>:<field>` under the connection's `integration_id`: the dedupe key is connection, venture, form, response and mapping. The answer and its ledger row are written in one D1 batch, and the answer is inserted only while no ledger row holds the key.

Turning a qualifying answer into a `demand_signals` row at `to_confirm` and offering confirmed signals as evidence is #5829's; this part stops at the source records.

### What is read and kept

- **Reads:** `GET /forms/{id}` (field ids, types, titles, choice ids) and `GET /forms/{id}/responses` (`page_size`, `since`, `after`, `sort`, `response_type=completed,partial`, `fields=<mapped ids>`, `included_response_ids`). Any other path or query key is refused before a request is built.
- **Kept from a response:** `response_id`, `token` (for paging only, never stored), `response_type`, `submitted_at`, `landed_at`, and the answers to mapped field ids. `hidden`, `metadata`, `variables`, `calculated`, unmapped answers and attachments are never read.
- **Mappable types:** choice (multiple_choice, dropdown, picture_choice: qualifying choice ids), yes/no and legal (`equals`), number, opinion scale, rating and NPS (`min`), short and long text (any non-empty answer). Email, phone, contact info, address, website, file upload, signature, payment and scheduling fields can never be mapped.
- **Stored text:** the matched choice labels, Yes/No, the number, or the free text (1,000 characters) only when the founder turned `keep_text` on. Nothing for a non-qualifying answer.
- **Logs:** `[typeform import] write failed: <error name>` and nothing else. Provider bodies never become messages.

### Counts

`typeformFormStatus` returns `completed` (distinct completed response ids Typeform still holds, withdrawn ones included, so it reconciles to Typeform), `partial`, `qualifying` (distinct completed responses with at least one kept answer), `withdrawn`, `provider_deleted`, the mappings needing a remap, the sync state and the region's responses link. A form with no completed response is `state: 'ok'` and `completed: 0`, a true zero; a failed read is its own state (`access_revoked`, `form_unavailable`, `rate_limited`, `region_unknown`, `unreadable`, `not_stored`), never zero.

### Runs

- **Lease:** a run takes `lease_owner`/`lease_until` (5 minutes) or returns `busy`. A stale lease is taken over. Two runs at once land everything once regardless, because every write is keyed.
- **Paging:** oldest first (`sort=submitted_at,asc` on the first page, `after=<last token>` after it), up to 10 pages of 200 per run; a run cut short is `partly` and the next run resumes at the checkpoint without the overlap.
- **Checkpoint:** after every write of a page has resolved, `checkpoint_submitted_at` moves to that page's latest completed submission, forward only, and only while this run still holds the lease. A write that fails mid-page leaves it where the last whole page put it; the retry re-reads that page and lands only what is missing.
- **Late arrivals:** a finished run's successor reads from 24 hours before the checkpoint (`OVERLAP_MS`), so a response Typeform makes visible late still arrives and dedupe absorbs the re-read. A response delayed longer is recovered by an intentional backfill.
- **Throttling:** 429 stores `retry_after` from `Retry-After` (default 60 s, capped at an hour) and no read is made before it.
- **Revoked or moved:** 401/403 or a failing token lookup is `access_revoked`; 404/410 is `form_unavailable`; a disconnected connection is `access_revoked` with no read. None of them deletes anything.
- **Region:** the origin is `api.typeform.com` (`us`) or `api.eu.typeform.com` (`eu`), and the link is `admin.typeform.com` / `admin.eu.typeform.com` `/form/<id>/results#responses`. #5827 owns validating the data center; until it lands the importer reads `integrations.config_json.region`, and anything but `us` or `eu` is `region_unknown`, never a guessed host.

### Fields

A field is matched by its id on every run. A rename updates `field_title` and keeps the mapping. A mapped field that is gone becomes `field_deleted`, one whose type changed `type_changed`; both are listed in `needs_remap`, excluded from `fields=` and land nothing until the founder remaps (`setTypeformMappings`, all or nothing, checked against the form's current fields).

### Retention, withdrawal and deletion

- **While the form is selected,** response rows (ids, types, dates) and kept answers stay. Deleting the connection or the venture deletes the sync row and, by `ON DELETE CASCADE`, its mappings, responses and answers. A disconnect only stops the reads (`access_revoked`); what a disconnect deletes is #5827's disconnect cleanup, which should delete the sync row and unlink its ledger rows.
- **Withdrawing an answer** deletes its text and keeps its ledger row with `local_id` NULL. **Withdrawing a response** deletes its answers and keeps only the id as `withdrawn`. Neither returns on a resync or a backfill.
- **Removing a mapping** deletes its answers and unlinks their ledger rows.
- **Upstream deletion is never inferred from absence on a page.** `reconcileTypeformDeletions` asks for the held ids explicitly (`included_response_ids`, 25 at a time); an id missing from a well-formed answer is marked, and a second miss at least an hour later marks it `provider_deleted` and removes its answers. A malformed or failed lookup concludes nothing; an id that comes back is cleared.
- **Intentional backfill** (`requestTypeformBackfill`) clears the checkpoint so the next runs read the whole history again; withdrawn and provider-deleted items stay so.
