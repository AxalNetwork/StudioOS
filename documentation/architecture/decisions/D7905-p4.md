## D7905 part 4 — Trace export, boundary-only execution and outcome categories (#7905)

This part connects result capture and export to the D8010 contract and the
hosted path to the accepted #8007 port. It changes no timeout, cap or lease,
and enables nothing.

**Export.** `trace-exporter.mjs` is the supervisor's exporter for the Linux
container. Its sequence:
1. Pause the exact container. Stopping it would discard its tmpfs.
2. Stream `docker cp <id>:/work/traces -` through a bounded USTAR reader that
   never extracts.
3. Write admitted files with exclusive, no-follow creation as 0400 into a
   fresh private pending stage (0700, owned by the listener).
4. Write `COMPLETE.json` last, as compact JSON plus one LF in the
   `studioos.trace-export.v1` envelope, with `evidenceClass:
   native-unqualified`.
5. Publish pending as `ready`.

The reader admits only an optional single `traces/` directory and direct
regular trace files owned by the candidate identity (10000:10000, mode 0600 or
0644). It refuses links, devices, FIFOs, sparse files, GNU/PAX extensions,
prefixes, bad checksums or magic, compressed input, duplicates, truncation,
trailing data, and D8010's proposed ceilings. One offer per context: an
existing leaf refuses. Any failure leaves no `ready` offer. The workflow
uploads only `trace-export/*/ready`. Node has no rename-no-replace; the leaf
is private and created exclusively, so only this supervisor can race there.
S33's 17 synthetic archive vectors were cross-checked locally (17 of 17 agree).

**Boundary-only execution.** No profile runs candidate `npm ci` as a host
step. Run mode executes only through a verified boundary job and otherwise
refuses with `execution_boundary_unavailable`, so the direct-host
`executeShard` path is unreachable from the executor. The supervisor re-checks
the same boundary instance (`boundaryIdentity()`) through live isolation
before the test phase, as well as before install. A failed or changed recheck
runs no test.

**Hosted.** `hosted` and `github-8` admission uses S30's accepted
`createHostedVerification` port (#8007), loaded lazily, with trusted readers
composed only in `executor-isolation.mjs`. There are none yet:
- provenance needs a target-job token that candidate processes cannot reach;
- the boundary needs a real credential-denying execution boundary;
- included eligibility comes from the authority's receipt (s39).

Every hosted admission and run therefore still refuses.

**Outcome.** A pilot success needs an observed test success, verified
removal and a completed export; an absent exporter is `export_failure`. The
supervisor reports `category` (`success`, `test_failure`, `cancelled`,
`timed_out`, `infrastructure`, `incomplete_cleanup`), the detailed `result`,
`cleanupComplete`, the raw test exit, and the export and cleanup states, in
the `container_outcome` line and the Run step outputs. The coordinator reading
them is s39's change, still to be agreed.

Still unresolved, and not to be read as proven: pause/copy behaviour and the
engine's actual archive encoding on the pinned runtime, privileged staging,
measured resource fit, actual-node qualification, the outcome and revision
contracts with s39, and any positive hosted reader.
