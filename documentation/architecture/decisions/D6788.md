## D6788 — Board resolutions stay with their held meeting (#6788)

GR-22 / GR-22B's previously unrecorded resolutions now use an additive
`board_resolutions` store. It references the compliance event and held occurrence; the event and held
date are copied by the writer from the same meeting, never accepted from a
separate client-supplied identity. Each entry keeps its full text, passed date,
recording actor/time and optional citation to that occurrence's minutes. Calendar
and Grow edit the same compliance event in place; its next due date is not the
meeting identity. Old meetings are not backfilled with invented resolutions.

The mounted cycle record/action route supplies the same venture gates as other
Grow records: its writers mark held and an advisor reads only. Mark held accepts
`resolutions` as up to 20 newline-separated texts or JSON entries
`{ text, passed_on? }`; no text is truncated. `resolutions_passed_on` defaults to
Held on; an entry can explicitly name another real passed date. These are
member-recorded dates, not legal conclusions. `cite_minutes: yes` requires an
uploaded minutes file; default No creates no citation. The client cannot choose
an arbitrary file key or another meeting's minutes. Resolutions are refused for
an obligation whose stored event type is not board_meeting.

Occurrence, resolutions, schedule movement and the existing actor-attributed
activity entry share one D1 batch. A next-date clash rolls them all back; the
existing upload cleanup handles a file whose DB write fails. There is no new
R2 prefix or download path. No production schema or data is changed by this task.

The existing server-driven record UI renders the Resolutions section by held
meeting, newest first, including an explicit None recorded row for a meeting
without entries. Existing resolutions remain visible if a later edit changes
the obligation kind. Minutes links use the existing checked open-minutes action and
never return object keys. The Mark held form adds the existing textarea/date/
choice controls; no new layout or renderer is invented. The obsolete Documents
placeholder is removed. Record read failures retain Unavailable, never an empty
resolution list. #6122 / #6795 owns the wider Company page and remaining GR-22
layout; this slice changes its store and existing record/action contract only.

Validation uses synthetic SQLite fixtures through the mounted Worker route:
record persistence, per-entry passed dates, actor attribution, optional minutes,
writer/advisor/tenant gates, Calendar and Grow edits (including a kind change),
validation and all-or-nothing rollback, migration references, and failed-store
reads. Real frontend record/form components cover desktop and phone output and
multipart submission. Browser checks at 1440px and 390px dark saved through the
actual Worker route with no page errors or horizontal overflow. Twenty mutations
of storage, gates, fields, ordering, history and transaction boundaries were
caught; the restored suite passes. No live member data or object was accessed.

Help: `validate-grow/board-meeting-resolutions` explains this flow, limits,
optional citations and shared Calendar history. No guide verification date or
ownership is assigned by this change.
