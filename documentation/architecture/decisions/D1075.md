### 1. The store (migration 584)

| Table | What it holds |
|---|---|
| `trust_content_blocks` | The seven blocks from TRU14's list: `glance`, `security`, `data`, `subprocessors`, `certifications`, `documents` and `disclosure`. Each has a `draft` and a `published` row: `body_json`, `checked_at` (a day, or null for "Not recorded"), `published_at` and `published_by`, and the `change_note` with its `change_uid`. A published row without its note, date and change cannot be written: the CHECK refuses it. |
| `trust_content_changes` | The change log: one row per Publish, with its note, the blocks it changed, and the subprocessors it added or removed. It is append-only: triggers refuse UPDATE and DELETE, as `licence_events` does (D156). |
| `trust_certification_reports` | Each auditor's report on file: its R2 key in `FILES`, SHA-256, size and uploader. The PDF itself is never in D1. |
| `trust_subprocessors` | Name, purpose, data seen, location and `starts_at`, with a state: `draft`, `published`, `removing` (still listed until the next Publish) or `removed`. |
| `subprocessor_subscribers` | The email's HMAC (`email_hash`, one row per address) and the email itself, encrypted (`email_enc`). Also the confirm token's hash and expiry, `token_version`, and the confirmed, unsubscribed and last-email times. |
| `subprocessor_notice_deliveries` | One row per subprocessor and subscriber: `sending`, `sent` or `failed`. |
| `security_reports` | Help's Security category (§6): what is affected, plus what happened and how to reproduce it, both encrypted, with its status. |

**The issue listed four tables; this builds seven.**
- **The email is kept, encrypted.** The issue's subscriber row has an "email hash and token", but a notice has to reach the address. The address is stored as AES-GCM ciphertext bound to the row (`services/columnCipher.ts`, KEK_PII). The HMAC is the lookup.
- **The reports and the deliveries are their own tables.** "A certification cannot be saved without its report file" needs a file record to check against. "Send once" needs a record of each send.
- **Security reports are not ticket rows.** The reason is in §6.

### 2. The public reads (`routes/trust_public.ts`, no sign-in)

- **`GET /api/public/trust`** answers with three parts:
  - **`blocks`:** each key maps to its published block or `null`. A `null` block was never published, and the page keeps its own "Not recorded" line for it (D1072 §3).
  - **`subprocessors`:** those listed, each with `starts_at` and `active`, and the `last_change`.
  - **`changes`:** the latest 10.
- **No draft is ever served.** The read selects `state = 'published'` and nothing else.
- **One part failing leaves the rest.** Each part is read on its own. One that cannot be read is `{ unreadable: true, message }`, and the others still answer.
- **A certification shows `report_on_file: true`, never the report's uid.** The report is not served publicly: whether visitors may download it is part 5's question to the owner (§8).
- **`GET /api/public/trust/changes?limit=`** is the full change log, newest first, at most 200, with `complete`.
- **`GET /api/public/trust/matrix`** is "What we check, and for whom".
  - It is built from `obligationsForRole` (`services/trust.ts`), the obligations the Worker seeds.
  - It has five profiles: Founder, Investor, Advisor, Operating Partner and Explorer.
  - It has eight named requirements. Terms, Privacy, Role NDA, Advisor disclaimer, Identity check, Accreditation and Entity check each list their obligation keys. The eighth, Partner agreement, is asked of no profile today, so it is left out.
  - A cell is `null` when the profile is not asked. Otherwise it is `{ asked: 'always' | 'when_it_applies', renews_months }`.
  - **Explorer has no list of its own.** `obligationsForRole('exploring')` falls back to the partner list (Terms and Privacy). Part 2 (#2966) adds the Explorer row, and the matrix follows it with no change here.
- **The reads are safe on a cold isolate.** All three are in `ROLE_SCHEMA_SAFE_ANONYMOUS_READS`. They read only migration 584's tables, never `users`.
- **Rate limit:** the `public_trust` bucket, 60 a minute per IP, fail-open, as the other public reads are.

### 3. The Super Admin's writes (`routes/admin_trust_center.ts`)

The routes are mounted at `/api/admin/security/trust-center`, ahead of `admin_security.ts`.
- **The bars:**
  - `GET /` (every block, draft and published, every subprocessor, the reports, the log, subscriber counts) needs `requireSuperAdmin`.
  - **Every write needs `requireSuperAdminWriteBar`:** a TOTP session, a recent step-up and the Super Admin elevation.
- **The audit log:** every write is in the admin audit log through `logAdminAction`. The log holds block keys, uids and counts, never the page's words or the note, because a draft is not public yet.
- **Blocks:**
  - `PUT /blocks/:key { body, checked_at }` saves the draft.
  - `DELETE /blocks/:key/draft` discards it.
  - Six blocks hold `{ intro, groups: [{ title, lines: [{ text, recorded, why, checked_at }] }] }`. A line with `recorded: false` must say why.
  - Certifications holds `{ items: [{ name, auditor, issued_on, expires_on, report_uid }] }`. **An item without its report on file is refused.** An empty list means "None held".
  - Dates are real days, never in the future. Unknown fields are refused.
- **Subprocessors:**
  - `POST /subprocessors` adds a draft, and `PATCH /subprocessors/:uid` edits one.
  - `DELETE /subprocessors/:uid` deletes a draft, or marks a listed one as `removing`. `POST /subprocessors/:uid/keep` cancels a removal.
- **Reports:**
  - `POST /reports` takes the auditor's report as a PDF body, at most 20 MB, and checks that it starts `%PDF-`. It goes to R2 at `trust-center/reports/<uid>.pdf`.
  - `GET /reports/:uid` reads it back.
- **Publish:** `POST /publish { note }`.
  - It is refused without a note of 10 to 1000 characters, and when nothing has a draft.
  - It re-checks the certifications' reports.
  - One D1 batch then does all of it: every draft block goes live as it stands at commit (`INSERT … SELECT`, so a second Publish at the same moment copies nothing), every drafted subprocessor is listed, every removal is applied, and one change row is written.
  - **A new subprocessor starts no sooner than ten days after Publish** (`NOTICE_DAYS`), the draft DPA's notice (`templates/legal/dpa_v1.md`). A later date the draft chose is kept.

### 4. Subprocessor notices (`services/subprocessorNotices.ts`)

The newsletter's double opt-in (D810), smaller:
- **Subscribe:** `POST …/subprocessors/subscribe { email, turnstileToken, hp }`.
  - Turnstile, then a `pending` row, with the address encrypted and only the confirm token's SHA-256 kept.
  - The confirm link is good for 48 hours, and the answer is the same for every address.
  - A confirmed or suppressed address is sent nothing. Signup mail is paced to one every ten minutes per address.
- **Confirm:**
  - `GET …/confirm` changes nothing: it shows a page with a button, because mail scanners open every link.
  - `POST …/confirm` confirms, once.
- **Unsubscribe:**
  - The link is `<uid>.<version>.<hmac>`, signed with KEK_PII and never stored.
  - `POST …/unsubscribe` raises `token_version`, so each link works once. It is also the RFC 8058 one-click target.
- **The send:** `sendSubprocessorNotices` emails each **confirmed** subscriber once for each published subprocessor that has not started yet.
  - **Nothing goes to an address that has not confirmed.** The query selects `status = 'confirmed'`.
  - It claims a delivery row before each send, so two sweeps never send twice. A failed send is retried after an hour.
  - Without mail credentials nothing is claimed, so the notices go once credentials are set.
  - It runs after Publish, in the background, and every five minutes from the HQ cron (`index.ts`, minute 4 of 5).
- **Rate limits and CSRF:** subscribe and confirm share the `trust_subscribe` bucket (10 a minute per IP, fail-closed). Confirm and unsubscribe are CSRF-exempt, as the newsletter's are.
- **In production without KEK_PII,** every subscription route answers 503 `subscriptions_unconfigured`, rather than store an address unencrypted.
- **The two emails are placeholders** (`templates/email/trust/`). The canvas draws no email.

### 6. The security Help category (`routes/security_reports.ts`)

**Why it is not a ticket row.** "A `security` Help ticket category, visible to HQ only" could not be a row in `tickets`, for four reasons:
- A ticket is mirrored to a GitHub issue on a public repository at creation (`routes/tickets.ts`).
- A ticket is posted to Slack's review channel with its text.
- Every admin reads every ticket, across about fifteen queries.
- `tickets.category` has a CHECK naming the eight categories (migration 333), so a ninth is a table rebuild.

So the category is `SECURITY_CATEGORY` (`services/ticketCategories.ts`): Help offers it beside the eight, and sends it to its own store. **`parseTicketCategory('security')` is refused** with that route's address, so the ticket route cannot file one by mistake.

**The routes:**
- `POST /api/help/security-reports { affected, what_happened, how_to_reproduce? }` files a report (TRU6d).
  - What happened and how to reproduce it are encrypted, bound to the report's uid.
  - A member may file five a day.
  - **On a branch it is refused,** with the email and the advisory as the ways to report: a branch's own administrators would be its readers there.
  - Each HQ Super Admin gets a bell notice with no words from the report.
- `GET /api/help/security-reports/mine` returns the member's own reports.
- `GET /api/admin/security/reports[?status=]` lists every report, oldest open first, at most 500 (`requireSuperAdmin`).
- `PATCH /api/admin/security/reports/:uid { status }` moves a report to open, acknowledged, resolved or closed, behind the write bar. It is audited by uid and status only.
