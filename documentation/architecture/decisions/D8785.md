## D8785 — The account journey signs B in off the live sign-in page (#8785)

- **Status:** built by S01, 2026-11-27 (#8785).
- **Migration:** none.
- **Scope:** test only. `frontend/tests/visual/account_journey_8529.spec.mjs`. The app, the Worker and the harness are unchanged.

### 1. Two failures, two causes

The issue was opened for main at `ff385110ac52` (run 45791598754). That run failed at the revoked-seat step at 1440 px, `getByRole('alert')` at line 129. That is the cause #8691 found: the terms screen drawn over the page. `ff385110` was committed one minute before that fix (`9c646641c`, #8736), and the spec it ran does not have the fix's checks. Main has not failed at that step since.

The failure that recurs is a different one. It happened on PR #8804 (run 45940914072, attempt 1) and on `agent/claude/land-addenda-1127` (run 46014354936, attempt 1). Both runs include #8736.

- It happened at 390 px only, at step 3 (`account_journey_8529.spec.mjs:102`).
- `getByRole('button', { name: /Open project|…/ })` was not found within 60 s.
- In both runs the 1440 px journey before it passed in under 5 s.

### 2. The cause

Step 3 signed B in by writing B's session into `localStorage` while the `/login` page was live:

1. B presses "Sign in to accept", a client-side `<Link>` to `/login?next=…`.
2. React Router 7's `BrowserRouter` changes the address at once, but commits the new route inside a transition, which can come later.
3. The spec's `toHaveURL(/\/login\?/)` passed on the address alone, and the spec wrote the session.
4. If that write landed before the `/login` commit, the commit ran `useAuthSync`'s route-change `refresh()`. That read the cached user and called `GET /api/auth/me`, which answered with B.
5. `AuthScreen` then saw a signed-in visitor on `/login`. That is its "account switch" case (Task #49), and it ran `clearSession()`: it removed the token and the user, and sent `POST /api/auth/logout`.
6. When that happened before the spec's `goto(next)` replaced the document, B reached the invitation signed out. The page drew "Sign in to accept", and the spec waited 60 s for an Open button that never comes.

The app behaved as intended here. A person cannot write storage between a URL change and a commit. The defect was in the spec's simulated sign-in.

### 3. The reproduction

- **Unforced:** 22 fresh-server runs of the old spec, alone and three at a time on a loaded host, all passed. A probe loop that ran 80 accept round trips (40 at each width) also passed.
- **Forced:** a throwaway probe made the window certain. It clicked the link and wrote the session in the same browser task, so before the commit, then waited. It failed every time: 4 of 4, at both widths. The request log showed the sequence:
  1. `GET /api/auth/me` (200), sent from `/login`;
  2. `POST /api/auth/logout`;
  3. `localStorage.token` empty before `goto(next)`;
  4. the invitation page showing "Sign in to accept".

### 4. The fix

- **Where the session is written.** B's session is now written on `/__visual/manifest`, a same-origin JSON document of the harness where no app runs. The spec still reads the `next` the app wrote and follows it. Nothing that is live on `/login` can see the session or act on it.
- **How the step ends.** Step 3 waits for whichever of these the page settles on: Open, "Sign in to accept", or the refusal's "Go to dashboard". It then requires that neither of the last two is there. A signed-out or refused arrival now fails in seconds, with the reason in the message, not after a 60 s timeout.
- **Unchanged:** the timeout, the retries and the steps, and nothing is skipped.

### 5. Verification

- **Repeated runs.** 26 consecutive fresh-server runs of the fixed spec passed, which is 52 of 52 journeys. Most ran three at a time on a shared four-core host whose load average was above 10. Every journey took 7.3 to 20.8 s, well inside the 180 s test limit.
  - `--repeat-each` cannot be used here. A repeat on the same server is refused at step 1 with 409, because A already has a company of that name.
- **The fixed order under a slow commit.** The probe ran the fixed order: click, leave for the manifest at once, write the session, follow `next`. With the browser's CPU throttled eightfold it passed 40 of 40 times, 20 at each width.
- **Mutations.** Each mutation failed at both widths, and each failure named its cause:
  - Writing the session on the live page before `/login` commits failed with "B arrives at the invitation signed in".
  - Accepting the invitation before B's page does, so the page is refused, failed with "the invitation is accepted, not refused".
