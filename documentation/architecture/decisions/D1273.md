### 1. What a code now records (migration 630)

| Column | Meaning |
|---|---|
| `plan_keys_json` | The plans HQ chose: `tier:growth`, `investor:professional`, `plan:<group>` or `mi:mi_pro`. `[]` when none. |
| `intervals_json` | The billing intervals a subscription may use it on: `["month"]`, `["year"]` or both. **NULL for a code made before 630**: it applied to every interval when it was made, and it still does. |
| `once_per_member` | 1: one use per member. 0 for a code made before 630, which had no such limit. |
| `first_purchase_only` | 1: only a member who has never paid. |

- **No CHECK constraints.** `ensurePromoSchema` adds the same columns, as literal `ALTER`s, on a store that never ran 630. A constraint on one path and not the other would be a difference nobody sees (the `advisorStoresSchema.ts` rule). The writer stores only 0, 1 and arrays it built itself.
- **A new index,** `promo_redemptions(promo_id, user_id)`, serves the once-per-member check.
- **The admin list** (`rowToView`) carries `plan_keys`, `intervals` (null for a code from before 630), `once_per_member` and `first_purchase_only`. An interval list that cannot be read shows as no interval, because checkout refuses it.

### 2. Create (`POST /api/admin/promos`)

- **Plans resolve to products.** Each plan key resolves to the catalog's *live* products that sell it (`planKeyOf`, the same metadata `planMetaForProduct` reads), and they join the product list.
  - So Stripe's own `applies_to[products]` enforces the plan on a subscription, and checkout's product check enforces it everywhere.
  - An archived product of the same plan is not added. A plan no live product sells is refused, `unknown_plan`.
- **Intervals:** `intervals` takes `["month"]`, `["year"]` or both, and defaults to `["month"]`. Anything else is refused, `invalid_intervals`.
- **The limits:** `once_per_member` and `first_purchase_only` take `true` or `false`; anything else is refused. `first_purchase_only` also sets the Stripe promotion code's `restrictions[first_time_transaction]`, so Stripe enforces it on a subscription too.
- **Refused before Stripe is asked:** every product the code names, chosen or through a plan, must be in the catalog (`unknown_product`), live (`product_archived`), and not a token pack (`token_pack_not_discountable`; D755 §5).
- **Records:** the promotion code's metadata and the `promo_create` audit row (report type `billing`) carry the scope and the limits.

### 3. Checkout: `validatePromoForProduct`

Every path now passes the buyer: the member, and the interval for a recurring price (null for a one-time price). Those paths are `/api/payments/intent`, `/promo/validate` (the preview), `/alacarte/intent`, and `/api/orders/intent` through `resolveCartPromo`.

The checks run in this order, cheapest first, and Stripe is asked only once the code's own terms pass:
1. **The terms:** not found, inactive, expired, currency, product list, token pack, as before.
2. **Interval** (a subscription only): a price on an interval the code does not list is refused, `interval_not_eligible`. A list that cannot be read is refused too, never read as "all". A code from before 630 applies to every interval. A one-time price is not touched.
3. **Once per member:** any recorded use of this code by this member (`promo_redemptions`) refuses it, `already_used`. A member is never assumed: asked without one, the code is refused.
4. **The usage cap,** as before.
5. **First purchase:** a member who has paid is refused, `not_first_purchase`.
   - **Who has paid:** a paid order here with money taken (`total_cents > 0`; a 100%-off order took none) answers first, without Stripe. Otherwise Stripe's own reading applies: a succeeded PaymentIntent on either of the member's Stripe customers.
   - **When it cannot be known:** if Stripe cannot be read, or a hundred intents with more behind them hold none that succeeded, the code is refused with `first_purchase_unreadable`. It is never let through as a first purchase.

### 4. Where a member's use is recorded

| Path | The use |
|---|---|
| A paid one-time purchase or cart | The webhook's `promo_redemptions` row, as before. |
| A free unlock | Its own `promo:<code>:<member>` row, as before. |
| A free cart order | Its `order:<ref>` row at fulfilment, as before. |
| **A subscription (new)** | For a once-per-member code, `member:<code>:<member>`, **reserved before Stripe is asked**. The row is unique, so two checkouts at once cannot both take the use. If Stripe refuses the subscription, the reservation is released. It does not move `times_redeemed`, because Stripe's own counter already carries a subscription redemption. |

A subscription the member then abandons unpaid still counts as their use: Stripe applied the coupon and counted it when the subscription was made. This is consistent with Stripe, and is noted as a question for the owner (§6).

### 5. Member copy

`AxalCheckout.jsx`, `CartDrawer.jsx` and `CheckoutPage.jsx` (D222's test holds that every reason has a sentence in all three) say:

| Reason | Sentence |
|---|---|
| `interval_not_eligible` | This code doesn't apply to this billing period. |
| `already_used` | You've already used this code. |
| `not_first_purchase` | This code is for a first purchase only. |
| `first_purchase_unreadable` | We couldn't confirm this is your first purchase. Try again in a moment. |

### 6. Not built here, and why

- **The admin form and the list's columns** for the scope and limits are part 5 (#3301, D1275). This part gives the Worker and the read.
- **Two concurrent one-time intents** by one member with a once-per-member code can both pass validation. The webhook records each payment as it lands. Reserving a one-time use at the intent would block a member who abandons the card form. Only a subscription reserves, because Stripe applies the coupon there at creation.
- **A per-interval price amount** (for example, a code of 20% monthly and 10% yearly) is a different code. A code's terms stay fixed once made.

### 7. Verified

- **`cloudflare-worker/test/promo_scope_d1273.test.ts` (7 tests).** The production baseline plus migration 630, with Stripe stubbed:
  - **The pure rules:** the interval reading (NULL means every interval; a bad list is no interval), the plan keys, the monthly default, and the view.
  - **Create:**
    - a plan resolves to its live product and not to its archived one; monthly by default;
    - Stripe's `first_time_transaction` restriction is set; the mirror row and the audit row carry the scope;
    - yearly and monthly together are allowed.
  - **Create, refused before Stripe:** a token pack, an archived product, an unknown product, an unknown plan, a bad plan key, bad intervals, and limits that are not booleans. Nothing is written.
  - **A monthly-only code refused on a yearly price,** through the validator, the intent (no subscription started) and the preview. A one-time price is untouched, a code from before 630 keeps every interval, and the monthly price goes through.
  - **Once per member:**
    - a second use is refused, another member's is not, and asking without a member is refused;
    - a subscription reserves the use without moving `times_redeemed`, so a second subscription with the code is refused;
    - Stripe refusing the subscription releases the reservation;
    - a cart checks the member.
  - **First purchase:**
    - a member with no Stripe customer is a first purchase, and intents that never succeeded are not payments;
    - a succeeded intent is refused; a 100%-off order is not a payment, while a paid order answers without Stripe;
    - more intents behind the page, or Stripe down, are both `first_purchase_unreadable`.
  - **A code refused on its own terms never asks Stripe about the member.**
