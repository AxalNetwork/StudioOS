## D7820 — Research › Companies: admin routes to place and clear a review status, record a check and list current holds (#7820)

- **Status:** built 2026-11-22 (#7820, under #3701), on D7819's ledger (`202611200052_7819_research_company_review_ledger.sql`). Option A: only an admin places and clears a hold. No migration.
- **Files:** `cloudflare-worker/src/services/researchCompanyReview.ts`, `cloudflare-worker/src/routes/research_company_reviews.ts` (mounted at `/api/research/company-reviews` with no `before`: `research.ts` has no catch-all or middleware there, and `research_client_prep_4574` requires client prep to stay immediately ahead of `research.ts`), `frontend/src/lib/api/researchCompanyReviews.js` (`researchCompanyReviewsApi`; no screen), and one line on the read guard's maintenance list in `cloudflare-worker/test/research_company_read_guard_7819.test.ts`.

### Routes (admin only, each one)

| Route | What it does |
|---|---|
| `POST /` | Place, change or clear a status for 1 to 200 uids, all or nothing in one D1 batch. Body: `uids`, `status` (`admitted`, `held`, `excluded` or `withdrawn`), `reason_code` (one of D7819's six), `proof_url` (https, required), and optionally `admin_note`, `next_action`, `next_review_on`, `withdrawn_on` (withdrawn only; the review time when omitted) and `run_reference`. |
| `POST /checks` | Record a check: `uid`, `kind` (`website`, `registry_status` or `source_published`), `outcome` (`ok`, `failed` or `changed`), `proof_url`, and optionally `what_changed` and `checked_at`. The answer carries the last good check of that kind. |
| `GET /` | Current held, excluded and withdrawn records, paged (`page`, `page_size` up to 100, `status=` to narrow). Each has its decision, reason code and sentence, proof link, reviewer, dates, run reference, and identity: the uid with the stored name and source name, or both null with `directory_row: false` where the directory row is gone. |
| `GET /:uid/history` | Every change to one uid, oldest first, with its reviewer and date, plus its checks. |

**The cap.** 200 uids a call, so the 11,000-record cohort (audit 2C) takes 55 calls.

**Refusals.**
- An unknown uid answers 404 `unknown_uids` and names it in `unknown`, and nothing is written. A uid is unknown when it has neither a directory row nor a review row. A review row alone is enough, so a record whose directory row is gone can still be changed, cleared and checked.
- A bad field answers 400 with its own code: `invalid_status`, `invalid_reason_code`, `proof_url_required`, `too_many_uids`, `invalid_uids` or `invalid_field`.

### Decisions

- **Clearing is a review.** D7819's trigger refuses deleting a review row, and a row is kept forever. So clearing writes `admitted` with its own reason and proof. The record is then reachable and counted again, the history keeps both the hold and the clearing, and the list of current holds no longer returns it.
- **The audit trail.** Every write calls `logAdminAction` (`activity_logs`) with a count, the status or check kind, and a batch reference, never a uid list. The batch reference is the `run_reference` given, else `batch-<uuid>`.
- **A run is referenced, not registered.** `run_reference` is opaque text: a #7742 run id where one exists, else a free batch reference. No route here creates a run or attaches rows to one, and the only tables written are `research_company_reviews` and `research_company_checks`.
- **Checks only append.** `research_company_checks` is append-only (D7819), so a failed check sits beside the last good one and never replaces it. D7819's read gives `last_failed_check` and keeps the earlier `ok`.
- **One direct read of the company table.** D7819's by-uid read returns no values for an excluded or withdrawn record, and answers the same whether the directory row exists or not. So it cannot test existence or name a record on the admin list, and it is not edited.
  - `readDirectoryIdentityForAdmin` (`IDENTITY_SQL`) selects `uid, name, source_name` by uid, whatever the review status, and nothing else. It writes nothing to that table.
  - Its file is on the guard's maintenance list, noted as an admin-only read. The pending list is unchanged.
  - Only the review service calls the read, and only `routes/research_company_reviews.ts` imports the service; a test over `cloudflare-worker/src` fails otherwise. So the stored name and source name of an excluded or withdrawn record leave only through the admin list.
- **Directory rows only.** The list covers records that have, or had, a directory row. Holds on candidates that never entered the directory stay in the offline ledger.

### Operator steps

Each call needs an admin session; there is no screen.
1. Hold or exclude records: `POST /api/research/company-reviews` with up to 200 uids, the status, a reason code and an https proof link. Repeat per batch, and keep the same `run_reference` across a batch's calls so the audit rows group.
2. Clear a hold: the same call with `status: "admitted"` and the reason it is cleared (for example `verified`), with proof.
3. Record a check: `POST /api/research/company-reviews/checks`.
4. Read current holds: `GET /api/research/company-reviews?page=1&page_size=100`. #7316's compilers point at this read once their scripts are on main. No export format is built here.
5. Read one record's trail: `GET /api/research/company-reviews/<uid>/history`.

**Not here.** Marking the 11,000-record cohort in production waits for the owner's answer on #7739, on the supported way to apply a list that is never committed. The uid list is kept only under a name #7741's ignore block covers (`*.private.*` or `private-payloads/`). It is never committed or copied into a fixture, and no row is marked from a guess about source or date. Deleting the cohort stays the owner's decision, recorded with #7316.
