## D4614 — Settings' session revoke writes one audit row per revocation (#4614)

- **Status:** built 2026-11-13. An audit-trail accuracy fix; no change to who may revoke what, and no change to any
  response.
- **Number:** D4614 is this issue's number (D4106).
- **Code:** `cloudflare-worker/src/routes/settings.ts`, `POST /api/settings/sessions/:id/revoke`.
- **Test:** `cloudflare-worker/test/session_revoke_audit_4614.test.ts`.

### The defect

The route called the shared revoke (`revokeUserSession` in `cloudflare-worker/src/services/userSessions.ts`, D481)
and then wrote a `session_revoked` row to `activity_logs` on every call that was not `not_found`. The service
returns `already_revoked` both for a repeat revoke and for the loser of two concurrent revokes (its read saw the row
live, its `UPDATE … WHERE revoked_at IS NULL` changed nothing), and its own comment says the caller must not audit
that outcome. The route ignored it, so two clicks, or two tabs, left two audit rows for one revocation.

### The decision

The route writes the audit row only when the outcome is `revoked`, that is, when this call's `UPDATE` changed the
row. `already_revoked` writes nothing. The response is unchanged: `200 { ok: true }` for both outcomes (the
already-revoked caller is still told the session is ended, as `account_concurrency_4618` pins), and
`404 { error: 'Not found' }` for a session that is not the caller's.

### Other callers checked

- `admin_security.ts` `POST /sessions/:id/revoke` (HQ · Security): returns 409 `already_revoked` before its
  `logAdminAction`, so it audits only a `revoked` outcome. Correct; not changed.
- `admin_security.ts` `POST /sessions/revoke` (bulk): audits inside `if (out.outcome === 'revoked')`. Correct; not
  changed.
- Sign out everywhere (`POST /api/settings/sessions/revoke-all`, `POST /api/auth/sign-out-everywhere`): bumps
  `users.jwt_min_iat` and does not call `revokeUserSession`, so it does not have this pattern. Not changed.

### Tests and mutations

The new file runs the real settings router over real SQLite (every migration), with a token bound to a
`user_sessions` row. The concurrent case holds the service's owner-scoped read until both requests have made it, so
both pass the read before either writes and the `UPDATE`'s `revoked_at IS NULL` decides, as in
`account_concurrency_4618`.

| Mutation | Tests that fail |
| --- | --- |
| The route's `out.outcome === 'revoked'` guard replaced by `true` | second revoke, revoke of a session ended earlier, two revokes together |
| The service reports `revoked` whatever the `UPDATE` changed | two revokes together |
| The route's revoke called without `user.id` | another member's session |
