## D8435 — The suite waits for no job: every part writes the plan itself, on every event (#8435)

On a pull request the nine `suite` jobs were created only after the `suite plan` job had found a runner and
finished. Hosted CI runs at most 60 jobs at once (D8421), so under load a run waited twice.

Pull-request runs, 2026-11-23 00:07Z to 11-24 13:32Z:

| Wait from creation to start, minutes | p50 | p90 | p95 |
| --- | --- | --- | --- |
| `suite plan` | 0.9 | 15.4 | 19.8 |
| Worker shards, after the plan finished | 1.4 | 18.9 | 23.9 |

### Decision

1. `suite` needs `verified` only. Its matrix is a literal on every event: `rest` for a draft pull request, the
   full nine parts otherwise. That is the tier rule in `scripts/lib/prTier.mjs`, and a test holds the two together.
2. Each part writes the exact-once plan itself with `--plan --equal-weights`, as the merge queue has done since
   D7108 part 2. The step no longer has a condition, and the part no longer downloads the `suite-plan` artifact.
3. The step still fails the part, and never drops one, when the part is not in the plan or the matrix is not
   the plan's parts a whole number of times. A draft tier must be exactly one part.
4. `runner-benchmark.yml`'s `benchmark` job carries the same steps, because `runner_lanes_5611.test.mjs` holds
   the two step lists equal. Its matrix is every part once a lane, which is why the count rule is "a whole
   number of times" and not "equal": one in CI, up to three there. It no longer downloads its own plan artifact.
5. The `plan` job is unchanged. It still runs off the queue, uploads `suite-plan`, prepares the capacity pilot's
   submission on `push`, and is still required by the full-suite gate. Nothing in `suite` reads it.

### Why equal weights, and not a timing snapshot

The issue proposed a committed timing snapshot so that parts could keep weighted plans. The measurement did not
support it. Pull requests used the timing-weighted plan and the merge queue used equal weights, over the same
37 hours, on runs where all six Worker shards passed:

| | Pull requests, weighted (105 runs) | Merge queue, equal (169 runs) |
| --- | --- | --- |
| Slowest Worker shard, minutes (p50 / p95) | 40.0 / 48.2 | 40.4 / 49.3 |
| Median by shard, minutes | 25 to 29 | 25 to 31 |

The weights bought nothing measurable. An equal-weight plan is a pure function of the commit, so two parts
cannot disagree, and there is no snapshot to refresh. The slow shard is run-to-run variance in heavy test files,
which #8437 addresses.

### Exact-once

Every part of a run must write the same plan, or a test file runs twice or not at all. The plan depends on the
commit and on nothing else: no clock, no API, no artifact, no timings. `ci_pr_plan_8435.test.mjs` builds it in
another process, directory, time zone and locale and compares bytes, and checks that every planned file is in
exactly one part.

### What S39 should look at

- **The `suite` digest** in `ci_capacity_pilot_7909.test.mjs`: `27bb0fe24483da04` becomes `c7c40cb382c001d6`,
  under D8434. No other line of that file changes.
- **`push` with the pilot enabled.** `plan` still writes a timing-weighted `suite-plan` artifact, which the
  capacity planner and executor read. The hosted parts of that same run now use the equal-weight plan. The suite
  rarely runs on `push` (it is skipped when the queue already verified the commit), and the pilot is off, so
  nothing differs today. If the pilot's delegated shard must cover the same files as the hosted part of the same
  name, `plan` should write the equal-weight plan too. That is S39's choice and is not made here.
- **#5609** (pack parts by measured duration, one plan for both matrices). This removes the hop that issue
  would also have removed, and the measurement above bears on its premise.

### Not done here

`plan` still runs on pull requests, where nothing but the gate now reads it. Dropping it there changes the
required gate job, and belongs with #5606.
