### The table (migration 406)

`research_fund_sources` has one row per `research_fund_directory.source_name`:
- `title`, `publisher` and `published_url`;
- `terms_status`, which is `found` or `not found`, with `terms_quote` and
  `evidence_url`;
- `evidence`, which says what was read and what it said;
- `verdict`, with `verdict_reason`, the sentence the page prints;
- `reviewed_on`;
- `repo_copy` and `repo_copy_note`.

Three CHECKs hold the rules:
- `verdict` is one of `republish allowed`, `cite only` or `not allowed`, and
  nothing else.
- A list whose terms were not found is never `republish allowed`.
- Terms marked `found` carry their quote and the URL they were read at.

The rows go in with `INSERT OR IGNORE`, so a later migration's verdict is never
undone by a re-run.

**A takedown is one later migration:** `UPDATE research_fund_sources SET
verdict = 'not allowed', verdict_reason = '…', …` with the quoted terms. No fund
row is deleted, and the list comes back if the verdict changes.

### What the Worker does

- **`SERVED_FUNDS`** (`services/researchFundDirectory.ts`) is every row of
  `research_fund_directory` except those of a list whose verdict is `not
  allowed`. It is the only way fund rows are read in:
  - the directory, its count, facets, coverage and sources;
  - the fund profile;
  - `research_sectors.ts`, where a sector's funds and counts are listed;
  - `research_overview.ts`, for its totals, the lists and "Where the money is".

  It is a literal of the file, interpolated into the query text, so
  `scripts/sql-prepare-baseline.json` gains its three sites. If the sources
  table cannot be read, the query fails and the page says "Unreadable". It
  never falls back to serving every list.
- **Every row carries `source`:** the list's name, title and publisher, a link
  to where it is published (or to where the row was read, if that is unknown),
  the verdict, the terms status and the reason. A list with no review row is
  still served, with `verdict: null` and the reason "Not recorded: this list's
  terms have not been reviewed". So a source name that differs on production
  shows as unreviewed rather than vanishing.
- **`removed_sources`** names each list taken down: its publisher, link and
  reason, and how many funds it withholds. That figure is a count, never a row.
- **`GET /fund-directory/:uid`** answers 410 for a fund whose list was taken
  down, with `{ detail: 'Removed', reason, removed }`: the list and why, and
  none of the fund's own fields.

**Not changed here: `research_markets.ts`.** Its `funds()` still reads
`research_fund_directory` directly, because that file belongs to open PR #1243
(#1230, slot S09). No list is `not allowed` today, so it serves nothing it
should not. When both PRs are merged, its `FROM research_fund_directory` becomes
`FROM ${SERVED_FUNDS} AS f`, the change this PR made in `research_sectors.ts`.

### What the pages do

- **The directory row** (`FundDirectory.jsx`) gains a source line: "Source:" and
  the list's title, linked to where it is published, then its publisher and its
  verdict. A publisher or verdict the API does not give reads "publisher not
  recorded" or "terms not recorded".
- **The drawer and the profile** (`FundDetails` → `SourceCard`) show the list,
  "Published by …", "Terms: Cite only" with the reason, the as-of date and
  "View the list".
- **The footer's source list** adds each list's publisher and terms, and a
  "Removed (N)" block naming each list taken down, why, and how many funds it
  withheld.
- **The profile of a removed fund** (`FundCatalogProfile.jsx`) says "This fund's
  list was removed", gives the reason and links the list.
- `fundDirectoryRead.js` `citationOf(item)` derives all of this from the API's
  `source`, and prints only the three verdicts.

### What a takedown would not reach

The repo is public. If a list is ever ruled `not allowed`, three things still
publish it in full:
- the CSV copies in `attached_assets/`: two EuroTech, one Deep Tech;
- `frontend/src/data/fundDirectory.json`, through
  `scripts/build-fund-directory.py`;
- the git history.

Removing them is its own change, and only the owner can decide on the history.
None is needed while every verdict is cite only.

### The question on #1232

- **A (my pick).** Keep all three lists cite only, as they are now. Allow
  `docs.google.com` and `hello-tomorrow.org` in the agent environment's network
  policy, so a slot can read each sheet's notes tab, quote any terms it finds,
  and set the verdicts in a follow-up migration. A list whose notes forbid reuse
  then comes down by that migration.
- **B.** Keep them cite only, and ask the three curators for permission:
  @Euro_VC, Hello Tomorrow and Shai Goldman. Their replies become the evidence.
- **C.** Take all three down (`not allowed`) until terms are read. The directory
  would serve no fund.
