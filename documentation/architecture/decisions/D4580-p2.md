### What the spec covers now

The code, passkey, Apple and Google answers are `page.route` fixtures; when one succeeds the browser is given a real session of the local Worker, so the landing is the signed-in app. Every row runs at 1440 and 390 px.

### Two failures, reproduced in Chromium and fixed

1. **A fragment swallowed the provider's marker.** Both callbacks appended `google=ok` / `apple=ok` to the whole kept destination, so `/grow/talent?tab=open#roles` came back as `…#roles&google=ok`. The SPA reads the marker from the query only, did not probe `/api/auth/me` for the cookie-only session, and sent a person the Worker had just signed in back to `/login`. `withLandingMarker` (exported from `routes/auth_google.ts`, used by both callbacks and Apple's link return) puts the marker in the query and keeps the fragment last. Worker tests: `auth_google_popup_d722.test.ts` and `auth_apple_6957.test.ts`, `#4580` cases.
2. **The SPA did not know Apple's marker.** `useAuthSync`'s post-callback probe looked for `google`, `google_signup` and `magic=ok`, not `apple=ok` / `apple_signup`. A browser with no cached user returning from Apple was sent to `/login`, signed in on the server but not in the tab, wherever the destination was. The probe now includes Apple's marker; `pending_next_redirect_8537.test.mjs` holds it.

Neither changes what is accepted as a destination (`sanitizeRedirect`, `sameOriginNextPath` are unchanged).

### Noted, not changed

- Google's refusal return (`callbackError`) keeps no `next`, so a cancelled Google sign-in shows the generic chooser instead of "Sign in to continue to Grow". The destination is not lost: the tab's kept copy (`gvpn:next`) still returns the person to Grow after any method, as the spec checks. Apple's `backWithError` keeps it.
