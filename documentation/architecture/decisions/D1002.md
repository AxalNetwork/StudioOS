### 1. The routes

All live in `routes/persona_members.ts`, mounted at `/api/personas/admin` before `routes/personas.ts`, and all are `requireAdmin`. The client is `personaSegmentsApi` (`frontend/src/lib/api/personaSegments.js`): `members`, `moveMembers`, `askToFinish` and `activity`.

| Route | What it answers |
|---|---|
| `GET /members` | One segment's members, or the members with none, a page of 25 at a time, with the read's own total |
| `POST /members/move` | `{ user_ids (1–50), persona_id }` → one outcome per member |
| `POST /members/ask-to-finish` | `{ user_ids (1–50) }` → one outcome per member |
| `GET /activity` | Moves, sign-up choices, segment edits and asks, newest first |

### 2. The members read (SEG3, SEG5)

**Who is listed.** Every active account but admins, as D999 counts them. An admin's account and a deactivated account are on no list.

**Each row carries:**
- name, email and profile (the account role);
- the segment, with its name from HQ's store (D1000), and the second segment (the newest non-primary row);
- how it was set, the confidence and the day it was given;
- joined and last active (`last_active_at`, else the older `last_active`);
- sub-accounts: LP (an approved LP application, Insights' rule) and tester (an `active` row in 576's `product_testers`);
- whether the segment's profile differs from the account's;
- with no segment, why;
- when the member was last asked to finish.

**What a member answered is never returned.** "Answered" (any `user_profile_extras` row) is a filter only.

**Filters:**

| Filter | Values |
|---|---|
| `segment` | a key or `none` |
| `q` | name or email, from two characters |
| `profile` | the account role |
| `how_set` | `router`, `self_select`, `admin_retag`, `not_recorded` |
| `band` | D997's four bands, `not_recorded`; only a sign-up suggestion has a band |
| `sub` | `lp`, `tester`, `none` |
| `answered` | yes or no |
| `active` | `7d`, `30d`, `90d`, `never` |
| `differs` | yes or no |
| `why` | only with `segment=none` |

**Sort:** `joined` (the default, newest first), `last_active`, `name` or `given`, with `dir`. An unknown value sorts last either way, never as the smallest.

A value nothing records is null ("Not recorded"), never 0.

**Why a member has no segment**, as SEG5 draws it:

| `why` | Means | Rule |
|---|---|---|
| `not_offered` | "Their profile has no segment yet" | No Active segment carries the account's profile (or `any`) in HQ's store. This is checked first: they could not have finished. |
| `started` | "Started, did not finish" | The sign-up chat has written at least one answer row. |
| `not_started` | "Skipped the sign-up chat" | Neither of the above. |

`why_counts` adds the reasons up over the whole scope. Without the answers store, `started` and `not_started` are null and named in `unreadable`; `not_offered` is still known.

**Failures.** A store the read needs failing is 503 `members_unreadable`, never `[]`. A store only one column needs (the LP store, the tester store, the asks log) leaves that column null and names it in `unreadable`.

### 3. The move, one and many

**The single move's rules (D255, D1000) are now one function,** `moveOne` in `services/personaMembers.ts`. Both `POST /admin/:user_id/retag` and the bulk move use it. Its checks:
- the member must exist;
- an admin's account needs a Super Admin;
- the segment already held is a no-op;
- a Retired segment takes no one.

**Each move writes:**
1. one batch to demote the old row and set the new one;
2. the subject-naming `persona_retagged` row;
3. the admin audit row (`logAdminAction`, which writes its own `activity_logs` line, as the single retag always has).

**The single route keeps its order and its answers:**
- the Retired check runs after the no-op, as D1000 placed it;
- 404 `user_not_found`, 403 `super_admin_required`, `{ ok: true, unchanged: true }`, 409 `segment_retired`, and 503 when the statuses cannot be read;
- D255's tests pass unchanged.

**The bulk move:**
- takes 1 to 50 distinct ids; duplicates are folded;
- refuses a Retired segment whole, before any write;
- answers `moved`, `unchanged`, `user_not_found` or `super_admin_required` for each member, or `failed` when that member's write threw;
- writes one activity row and one audit row per member moved.

### 4. "Ask to finish their profile" (migration 571)

One in-app notice (`notify`, type `persona_finish_profile`, category `proactive_nudges`, link `/onboarding/persona`) to each member with no segment.

**At most once per member in 30 days, whoever asks.** The 571 row is written first, guarded by the 30-day rule in the same statement, so two admins asking at once send one notice. Each ask also writes one audit row (`persona_finish_asked`).

**Outcomes:** `asked`, `asked_recently`, `has_segment`, `not_a_member` (an admin or a deactivated account), `user_not_found`, or `failed`.

### 5. The Activity read (SEG8)

**Sources:**
- moves: the subject-naming `persona_retagged` rows;
- sign-up choices: `router` and `self_select` rows, primary and second, members' only;
- segment edits: D1000's `segment_profile_history`, `edited` only, with the fields and the reason;
- asks to finish: 571.

**How it reads:**
- newest first, 25 to a page, with the read's own total;
- filtered by `kind` and by a name or email (member or actor);
- each source answers in `sources`. One that cannot be read is named and left out, never an empty list in its place;
- suggestions are part 6's (#2818), not on `main`: `{ recorded: false, reason }`.

### 6. Small cells

These are admin lists of members, the same members the retag table already shows one by one, so no count here is suppressed. Nothing a member answered is counted or returned per person: the answers aggregate is part 4's (D1001), suppressed there.
