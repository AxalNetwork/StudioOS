### 1. Each account's Mercury account

`GET /api/admin/bank-accounts` gives each account a `mercury` block, joined by entity and last four. This is the join `checkAgainstRegistry` makes at connect (D710 decision 3). `services/mercury/registryJoin.ts` reads only the stored `mercury_accounts` rows and their connection's status. It never calls Mercury, decrypts a number or reads an account number.

| `state` | When | What it carries |
| --- | --- | --- |
| `matched` | one Mercury account of the same entity ends in the same four | `uid`, `kind`, `connected`, `current_cents`, `available_cents`, `as_of` (`balance_read_at`) |
| `not_matched` | none does | `reason`: "No Mercury account of Axal VC GP LLC ends in 8897.", or, when the entity has no Mercury account on record, "Axal VC GP LLC has no Mercury account on record, so no balance is shown." |
| `ambiguous` | two or more end alike | `reason`: how many, and that none is shown |
| `unreadable` | the read could not be recorded or the store could not be read | `reason`: `AUDIT_UNAVAILABLE`'s sentence, or "The Mercury accounts could not be read. Try again in a moment." |

- **Never a zero.** An unmatched account has no balance field at all. A matched account whose balance Mercury has not given carries `null`, with `reason`: "Mercury has not given this balance yet. It is read at the next sync."
- **An account of another entity with the same last four is not a match.**
- **The read is audited first.** The GET writes a `mercury_accounts_read` row (`auditRead`, D710 decision 7) before it reads the store, with `filters_json = { surface: 'bank_accounts', accounts: n }`.
  - If the row cannot be written, no Mercury figure is read, and each account's `mercury` block reads `unreadable`.
  - The rest of the page still answers, because one failed block never blanks it. This is the house rule's "or answers 503", applied to the block rather than to the whole page.
- **Words.** Current, Available and *as of*, as in Fund admin.

### 2. `notice_preview`

Each account carries what a notice prints for it, purpose by purpose (BNK2), from the resolver itself (`payInstructionsFor`). Coverage is computed once per purpose, so the preview copies nothing.

- **Printed.** For each purpose the account takes: `ok: true`, the resolver's masked instructions (`account_masked` reads "••••8897") and `PAY_WARNING`, verbatim.
- **Refused.** `ok: false` with the resolver's own code and sentence, such as `ambiguous_account` when two accounts carry one purpose, or `holder_not_payee` and `savings_account`.
- **Not printed.**
  - A retired account: "A retired account is never printed on a notice."
  - An account with no purpose: "This account takes no purpose, so no notice prints it."
- **`printed`** is true when at least one purpose prints this account.
- **No full number.** The resolver gives none, and the tests sweep the response for each account's number. "Never copied on screen" is the page's rule: no Copy on the preview. That belongs to the frontend part.

### 3. The last-four check on add

`POST /api/admin/bank-accounts` takes an optional `mercury_account_uid`, the Mercury account the add is made from. When it is given, the route checks it before the registry's own validation. It reads the stored Mercury account, after its `mercury_accounts_read` row.

| Refusal | Status | When |
| --- | --- | --- |
| `mercury_account_invalid` | 400 | the uid is not a Mercury account uid |
| `audit_unavailable` | 503 | the read could not be recorded |
| `mercury_account_unknown` | 404 | no stored Mercury account has that uid |
| `mercury_entity_mismatch` | 409 | the Mercury account is another entity's |
| `mercury_last4_mismatch` | 409 | the typed account number does not end in the Mercury account's last four. The sentence names those four and never the typed number. |

- Nothing is stored on a refusal.
- An add that names no Mercury account reads no Mercury and writes no read row.
- The uid is not stored: the registry has no column for it, and this part adds no migration.

### 4. What else changed

- **`entity_bank_accounts_d708.test.ts`.** Its audit-order assertion now filters to the `bank_account_*` actions, because the GET also writes its Mercury read row.

### 5. Read-only

Mercury stays read-only. Nothing here calls Mercury's API or MCP: the join reads only what D710's sync stored. `registryJoin.ts` lives in `services/mercury/`, and the route imports `access.ts` and `registryJoin.ts`, never `store.ts` (`mercury_read_only_d710.test.mjs`).

### UNVERIFIED until the owner's live check

- **That the stored last fours match the registry's on production data.** Production's Mercury accounts and registry rows were not read.
- **Freshness.** The balances are as fresh as the last sync (D710's cron and Sync now); `as_of` says when.

### Tests

- **A match.** The account carries its Mercury account by entity and last four, after its audit row. Another entity's account ending alike is not a match.
- **No match, never 0.** Each case says so in words:
  - an unmatched account;
  - an entity with no Mercury account on record;
  - a matched account whose balance Mercury has not given (null, with its reason);
  - two accounts ending alike (`ambiguous`).
- **The audit row fails.** The Mercury block alone reads `unreadable`, the accounts still list, and no figure is shown.
- **`notice_preview`.** The masked instructions with `PAY_WARNING`; `ambiguous_account` on both accounts when two carry one purpose; the no-purpose and retired reasons. No full number appears in the response.
- **The add check.** Each refusal in §3 is covered, nothing is stored on a refusal, and a matching add is stored. The 503 comes when the read cannot be recorded. An add without `mercury_account_uid` writes no read row.
