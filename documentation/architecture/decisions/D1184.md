## D1184 — Bank registry: Mercury facts, notice preview and source validation

2026-10-26 · S19 · s30 (Codex) · #3113 · Part of #2389. No migration.

`GET /api/admin/bank-accounts` remains an HQ Super Admin read. It now refuses
support sessions and writes `bank_accounts_mercury_read` to `admin_audit_log`
**before** reading bank data. A failed, unsuccessful or zero-row audit answers
503 with no bank data. Responses use `Cache-Control: no-store`.

Each account gains:

- `mercury`: `account_uid`, `current: { cents, reason }`,
  `available: { cents, reason }`, `read_at`, and `reason`. The association uses
  the stored Mercury account's entity and last four, with its connection's
  entity checked too. The cached `registered` flag is not a join key.
  Unmatched or ambiguous associations carry null figures and those reasons;
  there is no arbitrary first match. Measured zero and negative balances stay
  measured figures. Missing figures are `not_recorded` before any read, and
  `unreadable` after a read; unsafe integer cents are unreadable. A failed
  Mercury query marks only this block unreadable, preserving the registry and
  notice preview. Cached facts remain available after disconnection, with
  their original read time; no fresh read or connection is implied.
- `notice_preview`: one result per assigned purpose from `payInstructionsFor`,
  including its masked instructions and `PAY_WARNING`, or its refusal. The
  same resolver results supply the existing coverage block. No full account
  number is returned. Retired accounts and accounts with no notice purpose
  have an empty array and `notice_preview_reason` (`account_retired` or
  `no_notice_purpose`). A successful result for a different account is refused
  rather than presented as this account's instructions. A resolver read
  failure affects its preview and coverage result, not the Mercury block.

The existing add POST accepts optional `mercury_account_uid`. It must be a
canonical local Mercury UID. After normal input validation and before
insertion/encryption, `bank_accounts_mercury_source_read` must persist. The
stored account must exist and match the selected entity, the normalized full
number's last four, and its checking/savings kind. No submitted ending or
provider ID is trusted. Mismatch returns a constant 409 refusal; an unknown
source is 404, invalid UID 400, unreadable or unauditable source 503. No refusal
inserts a registry account or echoes its input. The existing Super Admin
write bar remains; support sessions and branches are refused. Manual adds
without a source remain available. `bankAccountsApi.addFromMercury(uid, body)`
sends this field through the existing mounted POST; `list()` exposes the new
fields unchanged. No new route, page, reveal path or provider write is added.

All new SQL binds its values. The Mercury helper selects no credentials,
provider account IDs, full numbers or transaction text, and calls no network.
The existing number encryption and reason/step-up/ledger-first reveal remain
the only full-number path. New read audits contain actor, fixed action and a
boolean selection type, with no request content or account figures.

Validation uses the real Hono router and SQLite migrations 472/474, stubbed
network, role/branch/support denials, audit failures, matched/missing/ambiguous
facts, resolver success/refusals, encryption, and source add refusals. New
behavior is mutation-checked by breaking each guard/projection and restoring
it. The client transport is tested against the mounted existing paths.

these fields. No production bank records were read or written. This part is
API-only, so no page route or `ROUTE_MAP.md` entry changes. Revert the PR to
roll back; no schema change or data rewrite is required.

### Reconciliation of the parallel PR #3167

The owner asked to preserve and reconcile #3167 after #3166 merged. The
existing `registry.ts` remains the single implementation. Matched Mercury facts
also carry the stored `kind` and `connected` (true only for an active stored
connection); absent, ambiguous and unreadable matches carry null metadata.
Disconnected/error connections retain their dated cached balances, without
claiming a fresh provider read.

The merged `account_uid`/`current`/`available`/`read_at` format, array-shaped
`notice_preview` and `notice_preview_reason`, strict audit-first 503 gate,
support/branch refusals, and entity/ending/kind source checks stay intact.
The parallel `registryJoin.ts` path is removed rather than maintaining two
versions of the same policy. #3167's regression scenarios exercise the shared
implementation and its current response format, plus the additive metadata.
There is no migration, new endpoint or provider call. Production association,
freshness and the later BNK1/BNK2 integration remain UNVERIFIED.
