## D810 — Newsletter lists: a website signup with double opt-in, members' choices, signed preferences and one-click unsubscribe, and a suppression list every sender checks

- **Status:** decided by S1 for the owner, 2026-10-20 (#2256; part of D809, #2255, items D-a and D-b). Built by S08. S1 security-reviews it before it merges: it is public, and it holds personal data.
- **Basis:** `origin/main` at `662042c33c`. Paths are relative to `cloudflare-worker/` unless they say otherwise.
- **The owner, in the session (2026-10-20):** the suppression list goes **by reason**. An unsubscribe stops newsletter and marketing mail only. A bounce or a complaint stops all mail except account security: sign-in links, email verification and password resets.

### What is built

1. **Migration 515** (`sql/migrations/515_newsletter_lists.sql`).
   - `newsletter_topics`, seeded: `brief` (The Axal VC Brief), `portfolio`, `founder_calls`, `events`, `insights`, `announcements`, `testing_calls`, all public, and `partner_letter`, for investors and LPs only (`audience = 'investors'`).
   - `newsletter_subscribers`: one row per address, lowercased, with the member's `user_id` when there is one, `status` (`pending`, `confirmed`, `unsubscribed`), `confirm_token_hash` and `confirm_expires_at`, `token_version`, `source` (`website`, `account`, `import`), `consent_text_version`, `consented_at`, `ip_hash`, `last_email_at`, and the three timestamps.
   - `newsletter_subscriber_topics`: each subscriber's choice per topic.
   - `email_suppressions`: one row per address and reason (`unsubscribe`, `bounce`, `complaint`).
   - **The backfill:** each member with the weekly insights toggle on becomes a confirmed `account` subscriber with the `insights` topic on.
2. **The public routes** (`routes/newsletter.ts`): subscribe, confirm, preferences (GET and PUT) and unsubscribe (GET and POST). `ROUTE_MAP.md` has the contract.
3. **The member's routes:** `GET` and `PUT /api/me/newsletters`, on the account email.
4. **The four emails** (`src/templates/email/newsletter/index.ts`), plus the "manage your topics" note a confirmed address gets when it signs up again.
5. **The suppression check in every sender:**
   - `send()` (`services/email/send.ts`) classes a template by `mailClassOf`: marketing if `marketing`, security if its category is `security`, else transactional. A blocked send returns `reason: 'suppressed'`.
   - `sendRawEmail` (`services/email/gmail.ts`) takes a `mailClass` option (default `transactional`); `deliverNow` passes it.
   - The ten legacy senders in `services/email.ts` each ask before they send. `sendVerificationEmail` asks as `security`; the rest ask as `transactional`.
6. **The client:** `frontend/src/lib/api/newsletter.js` (D527). There is no UI (D813).

### Tokens

- **The confirm token** is 32 random bytes in the confirmation email. Only its SHA-256 is stored, with a 48-hour expiry. The confirming request claims it first (`UPDATE … WHERE confirm_token_hash = ?`), so it works once even if two requests race. A used token reads as unknown: 410 `token_invalid`, "already been used or is not valid".
- **The preferences token** in every later email is `<uid>.<version>.<hmac>`: HMAC-SHA256 of `newsletter:<uid>.<version>`, keyed by `NEWSLETTER_TOKEN_KEY`, compared in constant time. It has no row of its own and lasts until `token_version` changes. A confirmation of a row that had been unsubscribed (`unsubscribed_at` set) raises the version, so every link sent before the unsubscribe stops working. A preferences save that turns an unsubscribed row back on does the same.
- **`NEWSLETTER_TOKEN_KEY`** is a Worker secret (`PRODUCTION.md` §4); setting it is the owner's step. In production, without it, every public route answers 503 `newsletter_unconfigured`. Dev and preview fall back to `JWT_SECRET`.

### Abuse and privacy

- **Turnstile** guards the signup, as it guards the contact form: it fails closed in production and open in dev.
- **Per IP:** the `newsletter_public` bucket in `middleware/rateLimit.ts`, 10 a minute across subscribe, confirm and preferences. It fails closed: if KV is down, the routes answer 503. **Unsubscribe is outside it** (S1's review): RFC 8058 one-click POSTs come from the mailbox provider's servers, many people's from a few addresses, so a per-IP cap would drop real unsubscribes, and its HMAC token cannot be guessed anyway.
- **Per address:** `last_email_at` paces every email a public route sends to one per address per ten minutes. It is silent: the answer does not change.
- **No probing.** The signup answers the same 200 for a new, pending, confirmed, paced, bounced or honeypot request. A confirmed address gets the manage note, never a new consent. Choices sent from the website stay on the row until the confirmation; nothing is sent to a pending row.
- **The IP is never stored.** `ip_hash` is SHA-256 of `newsletter-ip:<NEWSLETTER_TOKEN_KEY>:<ip>`.
- **The preferences answer masks the address** (`p***@example.com`), so a forwarded link does not hand out the full address.
- **One-click unsubscribe** (RFC 8058): welcome and preferences-saved carry `List-Unsubscribe: <…/api/newsletter/unsubscribe?token=…>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. The POST is CSRF-exempt, as `/api/notifications/unsubscribe` already was: a mailbox provider's POST carries no CSRF pair, and the signed token is the authority. The GET behind the email's link changes nothing; it draws a page with one button that POSTs, so a link scanner cannot unsubscribe anyone.
- **A link scanner cannot confirm a signup** (S1's review). Mail scanners such as Safe Links open every link in a message, so the confirm link's GET changes nothing: a browser gets a page with one button, and only `POST /api/newsletter/confirm` confirms. That POST is CSRF-exempt, like the one-click unsubscribe: the single-use token is the authorisation. D813's `/newsletter/confirm` page confirms on a press, through `newsletterApi.confirm` (POST); `newsletterApi.checkConfirm` is the GET. The confirmation email links that page (D813), and the POST answers `{ ok, status: 'confirmed', topics }` with the labels it turned on.

### Which mail each suppression stops

| Reason | newsletter | marketing | transactional | security |
| --- | --- | --- | --- | --- |
| `unsubscribe` | stopped | stopped | goes | goes |
| `bounce`, `complaint` | stopped | stopped | stopped | goes |

- If the suppression store cannot be read, newsletter mail is stopped and every other class goes, as the marketing opt-out fails open (D189).
- The four newsletter emails are sent as `transactional`. Each answers the person's own action, so an earlier unsubscribe does not stop a confirmation they just asked for, and a bounce does. A new signup lifts an `unsubscribe` suppression only when it is confirmed. A `bounce` or `complaint` is never lifted by a signup.
- Nothing writes `bounce` or `complaint` yet. The Gmail API reports neither, so they come from an import or a later webhook. The list and the check are in place for them.

### The insights fold

- The weekly insights toggle (`routes/insights.ts`) writes the `insights` topic as well as `insight_subscriptions`. `GET /api/insights/newsletter` reads the topic once the member has a subscriber row, and the old table until then.
- `PUT /api/me/newsletters` and an unsubscribe of `insights` (or of everything) write the old table back.
- The old routes keep answering until the UI moves (D813).

### Placeholders

All four emails are placeholders: `confirm-subscription`, `welcome`, `unsubscribed` and `preferences-saved` (`NEWSLETTER_PLACEHOLDERS`). The owner's "Newsletter templates · Axal VC" design is not exported yet. Each email sends its wording as plain text, and its HTML part is the same text in a minimal wrapper with the links made clickable. When the export lands, each `html` takes the designed markup and keeps the same variables.

- **The preferences link** points at `/newsletter/preferences?token=`, the page D813 builds. Until then that address is the SPA's, and the API under it answers.
- **The unsubscribe link** points at the Worker's own `GET /api/newsletter/unsubscribe`, so it works today.

### Tests

`test/newsletter_d810.test.ts` (new, 10). It runs the real routers against node:sqlite holding `users` and `insight_subscriptions` from the baseline plus migration 515. Gmail is a recorder that decodes every email, members sign in with real JWTs, and the rate limit runs the real middleware.

1. Subscribe answers identically for a new, a pending and a confirmed address. It also covers pacing and topic cleaning.
2. Opening the confirm link changes nothing; only the POST confirms. A confirm token works once and expires.
3. Preferences and unsubscribe refuse a forged token and an old one (a changed signature, a changed version, the wrong key, a link from before an unsubscribe).
4. One-click unsubscribe works as a form POST with no sign-in and no CSRF pair, and unsubscribing from all suppresses.
5. The raw IP is never stored, at signup or after confirming.
6. The rate limit refuses the eleventh request and fails closed.
7. A member's topics round-trip. The partner letter is refused to a founder.
8. `insights` mirrors the old toggle both ways, and the backfill carried it over.
9. Suppression goes by reason, through `send()`, the legacy senders and the signup.
10. Production refuses every public route until the key is set.

21 mutations were checked and all were caught. Each removed one guard: the manage-email branch, the single-use claim, the expiry, the HMAC check, the version check, the CSRF exemption, the suppression on unsubscribe-all, IP hashing, `failClosed`, the limit, the investor check, both mirrors, the security exemption, the unsubscribe scope, the bounced-signup check, pacing, the production key check, the legacy guard, `send()`'s guard, and `mailClassOf`'s marketing case.
