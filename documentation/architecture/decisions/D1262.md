### Existing behavior confirmed

D891 already honours `check_against_json` in `checkInputs`, `runCheck` and
version summaries. An absent legacy selection keeps its old default; an empty
or unparseable selection compares nothing, and unknown keys select no source.
A deck is not invented from project
columns while its narrative binding waits for PITCH. The saved and inherited
writer contract remains unchanged.

Data-room readiness already uses `readableRoomFiles`, including a live grant,
its folders, the file's tier/expiry, an active investor and any required NDA.
The new regression covers downloadable checklist coverage with private,
uncommitted, unsigned-NDA and expired files alongside an accessible one.
The activity card now counts `open_room` and `download`, as #2430 specifies;
`blocked`, `view` and another project's events do not count as opens.

### Traction and narrative sources

MRR and paying-customer reads keep each source's latest non-null snapshot,
with the stored snapshot date. Stripe takes precedence for the narrative's
metric side, while readiness retains typed and Connector inputs separately.
A missing source says source not recorded; it is not guessed to be manual.

Traction also reads last-complete-month USD `revenue_entries` grouped by source,
verification and proof availability. Stripe's verified receipts are measured.
Supported Mercury credits retain their Connector source and supported strength;
a document-backed manual entry is Document/pattern, and manual or CSV entries
remain Typed/stated. A typed MRR never becomes measured. A metric snapshot
must be inside the current 90-day window to support current traction; older
or future observations retain their value/date with an explicit window warning.
Recorded zero remains zero, with Partial rather than a met/green criterion.
Verified narrative revenue names its contributing sources. Receipt
credits are not relabelled as recurring MRR. Customer names, notes and bank
lines are not read by these aggregates.

### Team backing without a new scoring policy

`teamReadiness` reads Build's founder holders and matching vesting rows
(`holder_id` and `user_id` must both agree), plus active, project-related GitHub
connections' contributor snapshots. It returns aggregate counts only, never
names, logins or repository names. Repeated repository/login snapshots across
connections use the newest stored snapshot, rather than the largest count,
and count once. The sync timestamp only orders snapshots; it is never presented
as a commit date. Contributor activity dates are Not recorded: the
store holds a sync timestamp, which is not a commit's date.

These rows accompany the existing readiness card and are available from
`computeReadiness`. The existing person's Team assessment and its manual
history stay intact; the six automatic checks still exclude Team. Counts do
not create a competence score or a new grade. Each Team source handles its own
read failure as Unreadable, retaining the other source's facts.

### Capital and runway

The commitment figure has disjoint `received`, `wired`, `signed`, `soft` and
`unclassified` subtotals in `breakdown`, also described in its reason. Only a
confirmed `raise_prospect` receipt belonging to the venture's founder is
received. Its recorded cents must exactly match the prospect's positive,
whole-cent amount. The comparison stays in SQL; the projection uses the
already recorded prospect amount and returns no bank amount. Retained integration
metadata must agree with the match's owner and Mercury provider. Removing a
connection does not erase a previously confirmed receipt: disconnect deletes
the integration, while the stored match remains. An accepted project member's
personal match is not the founder's receipt. Withdrawn receipts and matches
for another target kind do not count. A receipt
supersedes the prospect's typed status, preventing double counting. Wired,
signed and soft remain the founder's figures. The target comparison includes
received, wired and signed only. A missing firm amount stays missing, rather
than completing a partial subtotal with zero.

Mercury's eligible stored runway fact within 90 days still takes precedence.
Otherwise the metrics read prefers a Mercury cash/net-burn snapshot within
90 days, then the newest recorded snapshot, and names it; a typed
fallback says which source supplied it. The date is the selected record's date
and its spark uses up to eight points from that same source, with the limit
applied after source selection. Future snapshots are excluded and
an old-only fallback is explicitly marked Stale. Missing or non-positive burn does
not turn into a recorded zero or a fallback to a less reliable figure.
