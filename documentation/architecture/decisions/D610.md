## D610 — Co-founder matching: the other person's email stays hidden until both have signed the NDA

**Issue:** #1310, found by #1165's audit (area 8). **No migration.**

### What was decided

1. **Email revealed only after both sign.** Counterparty email is only exposed once both NDA signatures exist (`nda_signed_at_a` and `nda_signed_at_b`). Until both sides have signed:
   - `counterparty.email` is `null`;
   - `counterparty.email_withheld` is set to `'until_both_sign'`.
2. **Closed connections remain protected.** If a connection is closed before both parties have signed, the counterparty email remains hidden (`null`).
3. **The name remains visible before signing.** The mutual NDA document explicitly names both parties (`renderNda` populates `{counterparty_name}` and `{signer_name}`). Hiding the counterparty's name would obscure who the user is signing an agreement with.
4. **Admin access is unchanged.** An admin reviewing connections sees the counterparty's email regardless of NDA signing state.
5. **UI disclosure.** The Connections tab in `CofounderPage.jsx` renders `"Shown once you have both signed the NDA"` when the counterparty's email is withheld.

### Verified

`cloudflare-worker/test/cofounder_nda_email_privacy_d610.test.ts` and `frontend/test/cofounder_nda_email_privacy_d610.test.mjs` test:
- No email is exposed for either party when neither side has signed.
- No email is exposed when only one party has signed.
- Counterparty email is revealed to both sides once both have signed (including closed connections if both had signed).
- A connection closed before both sides sign keeps the email withheld.
- Admin reads reveal the counterparty email at any status.
- Listing (`/connections`) and single-read (`/connections/:uid`) agree.
- The UI copy is tested rendered via `renderToStaticMarkup` on `ConnectionCard` for pending, active, and closed shapes.
