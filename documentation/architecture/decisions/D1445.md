## D1445 — SMS enrolment runs the provider's bot check in the browser

Issue #3707. SMS remains a backup factor for account recovery; it never becomes
a primary sign-in or satisfies a sensitive-action step-up. No schema change.

The existing code input could not appear because the number step sent no
reCAPTCHA token. The API key alone established availability, not readiness.
`GET /api/auth/sms/status` now returns Google's public `recaptchaSiteKey`, the
Worker's existing country policy, and `sms_ready`. The key read is bounded by
two seconds and cached in RATE_LIMITS for one hour. No API credential is sent
to the browser. A failed status read is unreadable, not an unconfigured claim.

The existing settings card loads Google's invisible v2 widget and gets a fresh
token for each send or resend. Send requires a normalized, allowed destination
and a ready check. Success shows the last four digits, a six-digit code input,
Verify, and a 60-second resend countdown. Refusals remain inline; expiry clears
the code and offers Resend. Successful verification refreshes Enrolled/Remove.
The SIM-swap warning is unchanged. Existing enrolled factors remain removable
when the bot-check read is unavailable; no new enrolment form appears then.

The enrolment routes retain authentication, encrypted phone storage, fixed
rate limits and server-held candidate sessions. Provider quota maps to 429,
expiry to 410, unavailable Phone auth to 503, and region refusal to 400. Public
bodies contain a code and a sentence, never upstream diagnostics or full phone
numbers. Recovery and login-challenge routes, disable, and `requireFactor` are
unchanged. The development token fallback is not a production setup method.

Owner setup is recorded on #1008: Phone provider, authorized domains, Identity
Toolkit API permissions, API-key restriction type, existing SMS region policy,
and no production fallback token. Agents do not open the Google Cloud console
or send real SMS. S1/S01 confirms the sanitized production refusal code and the
owner completes the real-device send/verify check after setup.

Tests use synthetic destinations and mocked Google/KV/D1 and widget bindings.
They cover readiness/caching, provider token forwarding and refusal mapping,
rate limits, confirmation and unchanged TOTP-only removal; the mounted card
covers validity, readiness, resend timing, persistent errors and enrolment.
Every new assertion is mutation-checked, plus the specified behavioral faults.
