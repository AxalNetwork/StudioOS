## D633 — HQ tools from the Ops canvas: document types, a member's credits, and trust obligations by role

**Issue #1391, slot S08, 2026-10-07.** Part of #1165's area 7. No migration:
every store this needs exists. Two Worker reads are added.

The screens are the Ops canvas's `hq-contracts` (Q1), `hq-credits` (Q2) and
`hq-obligations` (Q3), in `design/canvases/integrated/ops-data.js` (#1387).
Each one is checked against the routes it reads, and the Worker is changed
first where a route did not return what the screen draws.

### Q1 · Document types (`/admin/contracts`)

D622 already showed a published type's pending revision and published it.
This adds what the canvas draws and D622 did not.

- **Each type's registry state:**
  - **In code only**, with "No draft yet";
  - **Draft**, with "Drafted in the store, not live";
  - **Published**, with when, by whom and the reason.

  The hub (`admin_contract_doc_registry.ts`) now gives each published type
  `published: { at, by, by_name, reason }`, from the store's `published_at`,
  `published_by` and `publish_reason`. The names come from one read of
  `users`. If that read fails, the names are left out and the hub still
  answers. A published type with no recorded publish reads Not recorded.
- **Publish on a draft type** (one never published), for a Super Admin only.
  It needs a reason of at least 10 characters, then the fresh sign-in check
  the route demands (`requireSuperAdminWriteBar`). `lib/api.js` prompts for
  that check on `step_up_required` and retries once. While it waits, the
  control says "Waiting for your fresh sign-in" and that nothing is published
  until the Super Admin confirms. Refusals use D622's `publishRefusal`.
- **The overlap mark:** types that share a layer and a party role are marked.
  The hub computed this already, and the card draws it.
- **Departure from the canvas.** The canvas warns: "Saving its draft changes
  the live type at once." In this app that is false. Since D615, a save on a
  published type stays pending until a Super Admin reviews and publishes it
  (D622). The card states the real rule instead.

### Q2 · A member's credits (`/admin/accounts/credits/:userId`)

- **Where it lives.** The canvas labels it `/admin/team/[member]/credits`. In
  this app, `/admin/team` is the public team page editor, and HQ's Team row is
  `/admin/accounts`. So the view lives at `/admin/accounts/credits/:userId`.
  Its door is a "Credits" link in the member drawer of the Team directory
  (`AdminPage.jsx`'s `UserDetailModal`), for a Super Admin only. The member id
  is the path's last segment, which the reachability test can resolve from the
  link.
- **The new Worker read** is `GET /perks/admin/credits/:userId`
  (`routes/perks.ts`). It is the Super Admin's, and returns the member, the
  balance (the sum of the ledger) and the latest 500 ledger lines, each with
  whether it was later taken back. An unknown member is a 404 with a
  sentence, and a bad id is a 400.
- **The view** shows:
  - **the balance:** 1 credit = US$1 of perk value. A failed read says
    Unreadable, never 0;
  - **the ledger:** date, change, source and note, with search, a source
    filter (adjustment, reward, perk, taken back), a period filter, a count
    and pages of 25. A line with no note reads Not recorded;
  - **"Adjust credits":** an amount up or down, a reason of at least 10
    characters kept in the audit log, and a note the member sees. It goes
    through D608's `POST /perks/admin/credits`.
- **The same change sent twice.** The form draws a fresh `source_ref` each
  time it opens. A second send of the same submission is refused by D608 as
  `already_recorded`, instead of being paid twice.
- **The canvas's three refusals,** each a titled sentence:
  - "Balance would go below zero", with the member's balance;
  - "Unknown member";
  - "Same change sent twice".

### Q3 · Trust obligations by role (`/admin/security/obligations`)

- **Read-only.** For each of founder, investor, advisor, partner and admin,
  the page shows the obligations the role carries, whether each is required,
  and how long each stays valid. It reads `GET /trust/matrix?role=`
  (`services/trust.ts` `ROLE_MATRIX`), which no screen called before.
- **Validity.** Terms and privacy last until the document changes. A period
  reads in months. An obligation with no period reads Not recorded, because it
  does not expire.
- **Each role is read on its own.** A failed read says Unreadable with Try
  again, and the other roles stand.
- **A note** says these are the defaults a new account starts with, and that
  one member's list can differ.
- **No sanctions action.** Nothing writes a sanctions review, so the page
  offers none. Its door is HQ Security's header.
