## D8417 — Owner adoption refuses locally before any token or alarm (#8417)

S34's review of #8412 (F1) found that a stale `POST /capacity/reconcile` was refused with 409, but only after the Durable Object had requested an installation token and armed the recovery alarm.

- **Order.** After the owner, input, mode, kill-switch and App identity checks, the route runs `inspect(requestId)`. It requires `adoptable` and a fingerprint equal to the submitted one before it calls `capacityGithubClient` or `setAlarm`. Any other case, including an unreadable request identity, answers 409 `{adopted: false}` with no token request, no GitHub read, no alarm write and an unchanged publication intent.
- **Eligible requests are unchanged.** The recovery alarm is still armed before adoption is written. `adopt` still verifies the parent attempt and the unique matching check through GitHub, and repeats the inspection and fingerprint comparison inside its synchronous write transaction, so an intent that changes during discovery is still refused.
- **Naming (N1).** `ownerAdoption.observedAt` keeps its name, so existing audit records stay readable. D8376 step 4 now says it records when the transaction writes the adoption, after the GitHub reads.

Tests: `merge-control/test/ci_capacity_compose_compact_7909.test.ts`, the three `8417` cases, with the existing `8376` change-during-reads regression retained.
