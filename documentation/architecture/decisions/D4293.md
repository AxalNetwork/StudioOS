### 1. An offer is a code with an owner

- HQ makes the Stripe promotion code in Promos (D1270–D1275), then links it to an influencer: `POST /api/admin/influencers/:uid/offers` with `{ promo_id, budget_cents, currency, featured?, reason }`.
- **What the link adds.** The code keeps its own rules: plans, intervals, once per member, first purchase only, expiry, pause and end. The offer adds:
  - the owner (`influencer_user_id`);
  - a budget, in one currency;
  - a status: `active`, `paused` or `ended`. Ended is final.
  - a `featured` flag. At most one offer per influencer is featured, enforced by a partial unique index; featuring one unfeatures the other.
- **The link is refused when:**
  - the code is not in Promos, or has ended;
  - the code already has an owner (`promo_id` is UNIQUE);
  - an amount-off code's currency is not the budget's;
  - the influencer's live offer budgets would pass the terms' `offer_budget_cents`.
- **Changes.** `PATCH …/offers/:offerUid` pauses, resumes, ends, re-budgets or features an offer.
- **Who and how.** Super Admin only, with the write bar, as Promos is. Every link and change needs a reason of at least 10 characters and writes `logAdminAction` (`influencer_offer_linked`, `influencer_offer_changed`, with before and after).
- `:uid` is the influencer's account uid. An account counts as an influencer when it has a `referral_partners` row; P1 creates that row on admission, in the `influencers` segment.

### 2. At checkout

`autoOffer` runs in `POST /api/billing/checkout/quote` and `/start`, for a new subscriber who typed no code:

- **Attribution.** The member is attributed to an influencer: an active row in `referral_attributions` (§6) whose referrer is not the member.
- **Which offer.** The influencer's offers are tried featured first, then oldest. The first to pass every check below is applied:
  - the offer is active;
  - its budget is in the price's currency;
  - the code's plan scope takes this plan;
  - `validatePromoForProduct` accepts the code for this product, interval and member. This covers expiry, pause, once per member, first purchase only and usage limits.
  - the discount fits what the offer's budget has left;
  - the discount fits what the terms' `offer_budget_cents` has left across all of the influencer's offers, ended ones included.
- **Never two codes.** A typed code always wins; an offer is looked for only when there is none, and only one offer applies.
- **What the member sees.** The quote shows the discount with the offer's `uid` (`influencer_offer`). The start sends the code as the subscription's one discount, with `metadata[promo_code_id]` and `metadata[influencer_offer_uid]`. It reads the offer again at start, since the budget may have moved, and the idempotency key follows the code applied.
- **Safety.** An unreadable offer store applies no offer and never blocks a sale.
- **How the budget is spent.** The budget is read from `promo_redemptions.discount_cents` (D1274) in the budget's currency, never a running total. A repeating code's later months are not in that record, so the budget counts each member's first discounted invoice only. This is the same figure Promos' Usage tab shows.

### 3. The influencer's read

`GET /api/influencer/me/offers` returns the signed-in member's own offers. A member with none reads `{ offers: [] }`. Each offer, as IN3 draws it, carries:

- `plans`: the code's plan names, or "Every plan";
- `intervals`: "Monthly and yearly" when the code has no interval scope;
- `discount`: in words, for example "20% off for 3 months";
- `who_for`: "First purchase only", "Once per member", or every member who arrives through the handle;
- `uses`;
- `discount_given`: per currency, never summed across currencies;
- `uses_without_recorded_discount`;
- `budget`, and `remaining_budget` with `budget_used`;
- `ends_at`: the code's expiry, or "No end date";
- `status` (the offer's own), and `code_state`: live, paused, ended or expired in Promos.

A value nothing records reads **"Not recorded"**:
- the discount given when the only uses predate D1274's detail;
- every field of an offer whose code is gone from the mirror (`code_state: 'unreadable'`).

No member's name or email is in the read.

**"Ask HQ for an offer"** is `POST /api/influencer/me/offers/request` `{ message }`. It is stored in `influencer_offer_requests`, and each Super Admin is notified. A member who is not an influencer is refused (403 `not_influencer`).

**P2's featured offer.** `featuredOffer(env, influencerUserId)` returns the featured active offer whose code is live, for P2's public `@handle` read. P2 owns that route, so P2 makes the call.

### 4. `offer_budget_cents` on the terms

D-b makes a tier's offer budget part of its terms, so this migration adds `referral_partner_terms.offer_budget_cents`, where NULL means no cap beyond each offer's own budget. **P1 must not add the same column** (a second `ADD COLUMN` fails the migration). P1's admission draft can fill it from the tier defaults. S26 told S25 on #4290.

### 5. What it does not do

- It never creates a Stripe promotion code: Promos does, with its own checks and audit. P9's Offers tab can link to Promos with the owner preset.
- It never discounts a plan change, as before: a code applies to a new plan only (D1051).

### 6. Before P1 and P2 merge

- **Attribution** reads `referral_attributions`, the first-touch store that P2 extends with handle visits and the 90-day window. `attributedReferrer` is the one reader, so P2's rule (and its own store, if it moves) changes one function.
- **Who is an influencer** is a `referral_partners` row until P1's `influencers.status` exists. When P1 lands, the link and the request should also require `influencers.status = 'active'`, and a paused influencer's offers should stop applying. That is one join in `influencerByUid` and in `autoOffer`.
