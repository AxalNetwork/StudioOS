## D5532 — Profile the prepared Worker before release admission (#5532)

Cloudflare rejected `569d0207fbcc40b44fbe2d4a2605da2eccb212e4` with startup error 10021 on November 10. The release had reached the publish step after migrations. On November 11 it published `20fe162791ecf40676ef8a8f5a58814e96f88dac` and reported 319 ms startup. [Rejected publication](https://github.com/AxalNetwork/StudioOS/actions/runs/42869138657/job/130015369541) · [Successful publication](https://github.com/AxalNetwork/StudioOS/actions/runs/42994820185/job/130436155417)

### Reproduction and evidence

Each historical checkout used its own Worker lockfile, Wrangler 4.156.1, Node 22.23.4, the effective production config and its SHA in `WORKER_DEPLOY_VERSION`. A disposable one-file assets directory satisfied the asset packager for the historical runs. The entry module and imported modules came from the exact SHAs, including the shared frontend helpers and meeting-bot source. The current checkout used the built SPA. The local host was an Apple M3 Pro. Cloudflare documents a [one-second global-scope startup limit](https://developers.cloudflare.com/workers/platform/limits/#worker-startup-time).

The check opens a fresh local workerd process for each sample. It profiles loading the packaged modules and the first `/api/health` request with the package's compatibility settings and plain-text bindings, locally generated test credentials, and an outbound stub. It verifies a second health request in the same isolate. The active figure is the sum of non-idle inspector samples and includes garbage collection and the cold health handler. This includes local instrumentation and scheduling effects.

All cold and warm checks returned 200 and `status: ok`. The largest sampled frames on the historical candidates were anonymous bundle entry/evaluation frames (61.0/56.3 ms mean self time on the rejected/published SHA) and garbage collection (27.4/26.0 ms). Mapped frames included `aiCredits.ts:179` currency formatting (11.5/12.5 ms), Zod schema setup (4.7/3.4 ms), and Hono routing. A run concurrent with the full test suite measured substantially more active time on both artifacts. Wrangler's built-in profiler worked for the rejected SHA and timed out on the published SHA locally. Both completed with the same isolated Miniflare probe above.

The historical timings overlap and do not reproduce 10021. They establish neither a source-level cause nor validator variance as the cause. The local gate detected an intentionally CPU-heavy fixture and wrote `over_budget` diagnostics. That fixture verifies the gate's failure path. The historical Cloudflare regression still needs a validator profile captured from a subsequent rejected candidate.

### Admission contract

Prepare the trusted artifact in the same checkout and with the same configuration as publication:

```sh
(cd cloudflare-worker && node node_modules/wrangler/bin/wrangler.js deploy \
  --dry-run --config ../wrangler.toml --env production \
  --var "WORKER_DEPLOY_VERSION:$CANDIDATE_SHA" --outfile "$OUT/worker.bundle")
node scripts/check-worker-startup.mjs "$CANDIDATE_SHA" "$OUT/worker.bundle" "$OUT/startup"
```

The CLI requires three valid fresh measurements. It retains invalid captures and allows at most two replacements. A valid over-budget measurement always counts. A missing profile, failed health request, SHA mismatch, artifact change or any active sample above 800 ms fails closed. The 800 ms budget has a nominal 200 ms margin to the platform limit. Calibrate it with repeated runs on the chosen Linux release runner before making it blocking. Archive `startup.json`, the raw CPU profiles and probe logs on success and failure. The report records candidate, artifact SHA-256, tool and host versions, timings, hot frames and failure reason. Keep source maps with the trusted build for mapping the hot frames.

#5501 owns admission ordering, the release lock and publication. Bind the measured artifact digest to its promotion evidence and require the check before migrations. The local result is a regression signal. An authoritative pre-mutation 10021 check needs the platform validator on an isolated target from #4566 or a supported validation-only release mechanism. Keep the profile from future 10021 failures and record an ordinary successful rollout after the admission change. The production workflow and application entry point are outside this slice.
