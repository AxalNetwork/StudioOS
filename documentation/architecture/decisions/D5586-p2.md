### 1. There is no admission Durable Object binding to wire through

On main (`1cd5a5c353`) `wrangler.toml` binds no admission object in any of its three tables, `Env` names none, and no
class hosts `DurableWorkspaceAdmissionStore`. D5570 part 2 says so itself: "No binding, route, namespace, provider
call or resource is enabled here", and its remainder starts with "preview-only host/binding integration". A Worker can
reach a Durable Object only through a binding, so a typed client the rest of the Worker can call needs one.

So, as the owner asked, nothing that needs a binding is built here: no Durable Object class, no client, no
`wrangler.toml` line. Everything that does not need one is: the table, the writer, the composition a coordinator object
will host, and the venture-scoped reads. The question is §5.

### 2. The table (`swarm_admission_events`)

- **One row per in-state entry.** It holds `SwarmAudit`'s fields: tenant, company, `seq`, `at`, ticket, action,
  outcome, code and, for a settlement only, the bill (`charged_microusd`, `measured`).
- **The key is `(tenant_id, company_id, seq)`.** `seq` is the coordinator's `audit_seq`, so a replayed copy lands once.
- **Append-only.** UPDATE and DELETE are refused by triggers, as `work_graph_release_authority_events` does.
- **CHECKs on every code.** The action, outcome and code lists are `swarmAdmission.ts`'s vocabulary. A test reads the
  source's refusal and wait codes and the migration's lists and pins them together. A refusal must name its code, and
  a settlement, and only a settlement, carries a bill.
- **A gap is a row.** Entries that the bounded state (`SWARM_AUDIT_MAX`) dropped before they were copied become one
  `audit_gap` row: tenant and company 0, no ticket, `seq` the first dropped number and `gap_to_seq` the last, code
  `audit_dropped`. The missing range is recorded, never silent. Only a gap row has no venture.
- **One coordinator per database.** `seq` is unique within one coordinator's state. A second coordinator (a second
  quota pool) would need a coordinator column first, as an expand migration.

### 3. The writer (`flushSwarmAudit`)

The in-state audit stays the record of the transaction: it commits or rolls back with the change (D5586 §2). The
writer copies it afterwards.

1. In one store transaction it reads the entries above the state's watermark (`audit_flushed_seq`), at most 100, and a
   gap row if the first kept entry is not the next number.
2. It writes them in one D1 batch with `ON CONFLICT DO NOTHING RETURNING seq`.
3. A row that was already there is read back and compared with its entry. A mismatch stops the copy with
   `audit_conflict`, and the watermark stays below that entry, so it is never skipped.
4. In a second store transaction the watermark rises to the last row copied. It never falls, so two copies racing over
   the same entries land them once and the slower one does not step back.
5. It repeats until it has caught up.

A D1 failure returns `audit_store_unavailable` and moves no watermark. The entries stay in the object's storage, across
a restart, and the next call copies them. No admission decision reads D1, so a D1 failure can neither admit nor refuse
anything.

### 4. The composition and the reads

- **`createAuditedSwarmAdmission`** is part 1's swarm admission with a copy after each `request`, `promote`, `settle`,
  `withdraw` and `revokeAgent`. The answer is the admission's own whatever the copy did: a failed copy is reported
  through `onFlush` and retried by the next call. This is what a coordinator object will host, over
  `DurableWorkspaceAdmissionStore` and `env.DB`. The Miniflare test hosts it in a test-only object.
- **`snapshotFor(venture)` / `scopedSwarmState`.** One tenant and company's tickets and audit entries (refusals
  included), nothing of another venture's. The shape is `SwarmState`, so a reader written for the whole state takes
  it. #5585 part 12's `renderAdmissions` is one.
- **`readSwarmAdmissionEvents(env, ctx, scope)`.** The copied rows of one tenant and company, optionally for some
  tickets. It refuses `wrong_tenant` before any statement and binds every statement to the scope. Refusals stay
  readable here after the bounded state has dropped them.

### 5. Open question: the coordinator binding

**B. How should the swarm reach its Durable Object?**

- **B1 (my pick).** Add one binding and class for #5570's coordinator. For example `WORKSPACE_ADMISSION` →
  `WorkspaceAdmission`, a `new_sqlite_classes` migration in all three `wrangler.toml` tables, one object by name for
  every tenant that shares a provider quota (D5570 part 2), hosting `createAdmissionControl` and
  `createAuditedSwarmAdmission` over the same store. Then a typed client for request, promote, settle, withdraw,
  revoke and `snapshotFor`. This changes `wrangler.toml`, so it needs the owner's yes.
- **B2.** Host it in an existing object (for example `AI_GOVERNOR`, which already serializes admissions). This needs
  no new binding, but it mixes AI token holds with compute leases in one object and one storage key space.
- **B3.** Wait for #5570's own part 3 to add the binding, then wire the swarm onto it.

### 6. For #5585 part 13

The venture-scoped snapshot exists (`scopedSwarmState`, `snapshotFor`). It is not yet available through a binding.
Until B is answered, `RELEASE_ADMIN_DEPS.renderAdmissions` keeps answering null (`admission_unverified`). Once a binding
exists, it calls the client's `snapshotFor({ tenant_id, company_id })`.

### Rollback

Nothing imports `swarmAudit.ts` outside its tests, and nothing writes the table. Revert the commit. The table is
additive: dropping it loses only the copy, and the in-state audit is unchanged.
