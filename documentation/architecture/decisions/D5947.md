## D5947 — Revenue ledger 3/6: the branch report carries measured stream gross, currency, source and freshness (#5947)

- **Status:** built. Slice 3 of 6 of #5038.
- **Builds on:** D111 (`branchRevenueSummary`, migration 260), D266 (the 05:10 usage report), D456 (HQ's coverage read), D5299 (`financial_events`), D5946 (the subscription reader).
- **Migration:** `cloudflare-worker/sql/migrations/202611161359_5947_usage_report_source.sql`. It adds `state`, `reason`, `source` and `source_as_of` to `subsidiary_usage_reports`. It is additive, with no backfill: a row reported before it has NULL in all four.

### What was checked first: does a branch receive Stripe webhooks?

No. Every branch is the same Worker code over its own database, so it has the
`financial_events` table and the webhook route that writes it. But the route
refuses every event with 503 when `STRIPE_WEBHOOK_SECRET` is unset, and
`branch-provision.yml` never sets it: its `BRANCH_SECRET_BUNDLE` carries
`SCORING_HMAC_SECRET`, the KEKs, Turnstile and the mail credentials
(`documentation/operations/DEPLOY.md`, the branch secrets table), and no Stripe key. HQ's refund route, the ledger's
other writer, refuses on a branch (`requireSuperAdminWriteBar`, D224). So a branch's
ledger is **empty by design** today, and its Stripe coverage row only records
when the migration ran there.

The report therefore says so. A branch with no `STRIPE_WEBHOOK_SECRET` and no
ledger row for the period reports subscriptions as `not_recorded` with that
reason. No other source is substituted: HQ's own ledger is HQ's, and a
`licence_uid` stamped on an HQ row is not something a branch can read.

### What a branch reports

`branchRevenueSummary` (`rpc/branchOps.ts`) now gives every stream a `state`
(`complete`, `incomplete`, `not_recorded`, `not_available` or `unreadable`,
the vocabulary of D5950's read model), a `source`, and `source_as_of`, the
time the branch read it.

| Stream | Source | What is reported |
| --- | --- | --- |
| `subscriptions` | `financial_events`, through D5946's `subscriptionRevenue` | the gross of the period's `invoice` rows in their own currency (see below) |
| `licence_fees` | `none` | NULL, `not_available`: a branch bills no onward licence fee |
| `token_margin` | `ai_usage_logs` | NULL, `not_available`, with the cost in `estimate_basis` as before; `unreadable` when the log cannot be read |

For subscriptions:

- **One currency in the period.** Its gross in that currency, with the
  reader's state. A period that starts before the ledger's coverage start is
  `incomplete`, with the start named; a period wholly before it is
  `not_recorded`. Rows with no amount or no stream also make it `incomplete`.
- **No row at all.** NULL and `not_recorded`. An empty ledger has no currency
  to state a zero in. With no webhook secret the reason says the ledger is
  empty by design.
- **A failed read.** NULL and `unreadable`.
- **Gross only.** Refunds stay in the ledger. The report key holds one figure
  per stream, and gross is what statements are drawn from (D111).

### The key stays (licence_uid, period, stream)

The issue asked whether to widen the key for a branch that collects one stream
in two currencies. **It is not widened.** Instead:

- the licence's own currency (`branch_licence.currency`) is reported when the
  ledger has it, and the stream is `incomplete`;
- every other currency is named in the reason with its amount in minor units,
  and none is added in;
- when no ledger currency is the licence's, the figure is NULL and the stream is
  `incomplete`.

Why not widen it:

- A statement draw (`admin_statements.ts`) and HQ's licence page
  (`licenceAccount.ts`) both key one row per stream.
- A re-report replaces by that key. With currency added to the key, a quarter
  re-reported in a different currency would leave the old row standing beside
  the new one, which would be two figures for one stream.
- No branch measures anything yet, so a second currency is hypothetical. When a
  branch bills through Stripe, widening the key is its own migration, with a
  replace-the-set rule for re-reports.

### What HQ stores

`reportUsage` (`rpc/hqOps.ts`) stores the figure as sent, in its own currency,
plus the four new fields:

- `state` is kept only when it is one of the five words; otherwise it is NULL.
- A figure whose state is `not_recorded`, `not_available` or `unreadable` is
  stored as NULL, whatever number came with it.
- `source_as_of` is normalised to ISO, or NULL when it does not parse.
- `reported_at` stays HQ's stamp of the report.
- A re-report still upserts on (licence, period, stream) and replaces all of
  these fields.

`pushUsageReport` and `sendUsageReportNow` (`services/usageReport.ts`) send
`state`, `reason`, `source` and `source_as_of` for each figure. Before this
change the reason was sent and dropped.

### What HQ says

- `subsidiaryUsageCoverage` names, per licence, `measurable_streams` and each
  reported stream's state, currency, source and as-of time. It carries no
  amount.
- Its `revenue_reason`, and the `revenue_per_subsidiary_reason` HQ Home sends
  through `revenuePerSubsidiaryUnavailable` (`routes/licence.ts`), keep the
  D266 sentence, word for word, while no licence has reported a measured
  stream for the quarter. Once any licence has, they switch to a sentence that
  says which streams can be measured and that nothing is totalled.
- `revenueAbsenceReason` for a licence that measured a stream names the stream.
  For a licence that measured none, it keeps "every stream arrived unmeasured".

Nothing sums across currencies, streams or licences on either side.
