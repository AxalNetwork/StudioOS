### 1. Share an update: the `audience` fact

`periodFollowers` (`services/updateShare.ts`) reads `tiktok_account_facts` for the update's period. It reads three counts: the last count before the period, and the first and last counts in it. A snapshot with no follower count is skipped. `audienceFact` turns them into one fact:

- With an earlier count: "TikTok followers 1,240 → 1,610 this period".
- With one count only: "TikTok followers: 1,610".
- The source is always "TikTok · followers, as of <date of the last count>", with `ref: 'revenue_and_traction'`.

`periodFacts` takes it as its sixth argument, and `POST /portfolio-updates/share/draft-lines` passes it. With no count in the period there is no fact. A count before the period alone is not this period's. Never a 0.

**The founder still sends.** The fact is something Eadwyn drafts from, and it never becomes a line by itself. A drafted line carries the fact's source through `parseDraft`. It reaches the sheet as a draft, and the founder keeps, edits or drops it before sending. An `audience` fact alone is enough for Eadwyn to draft, as a metric or a shipped item is; a role or a contact count alone still is not.

**No frontend edit for Updates.** `ShareUpdateSheet.jsx` already draws every line's `source.label` and `source.as_of`. The fact list itself never leaves the Worker.

### 2. Overview: the reach line

`tiktokReach` (`services/growCycle.ts`) reads `tiktok_video_facts`. It sums the views of the public videos posted this month (UTC) whose views TikTok gave, and counts those videos. `distributionCard` returns the result as `series.tiktok`: `{ views, posts, as_of, source, text }`, or `null`.

- **A video with no view count is not counted.** It is not a post with 0 views.
- **No such video, no line.** The value is `null`, never 0.
- **It is a line beside the funnel, never a funnel step.** A view is not a visit (D5863). The funnel and its Visit step (PostHog, D6107) are unchanged. Part 2a's test now holds `posthog/visits.ts` to never reading TikTok, where it held all of `growCycle.ts`.

**Frontend edit:** `frontend/src/pages/cycles/adapters/grow.js`. Its `distribution` adapter adds a row: "TikTok reach this month" with "9,400 views across 2 posts · From TikTok, as of 2026-11-15". The adapter drew only the series it knew, so without this edit the line would not have shown. No new figure is added to the Overview.

### 3. The daily sync

`syncAllTiktokIntegrations` is in `services/tiktok/daily.ts`, beside part 2a's service. It is not in the provider, because the provider is imported by `client.ts`, and the sync needs `client.ts` and `grow.ts`. The cron in `index.ts` calls it hourly at :41, beside `syncAllHubspotIntegrations`.

| Rule | How |
|---|---|
| Only a connection that is `active` | `status = 'active'` in the read. A `revoked` or `error` connection is never listed. |
| Only one a founder already linked | It joins `tiktok_account_links`. The cron never picks a venture: the first link is made by a founder's own sync (decision F). |
| Only one with an enabled company | `scheduledConnectorEnabled`: its sync frequency (a `manual` one is skipped), and at least one company switched on. Then `projectEnabled` for the linked venture's own company. |
| At most one snapshot a day | A connection whose `last_synced_at` is today (UTC) is skipped, whether the cron or the founder synced it. The snapshot is keyed by the day (`UNIQUE (project_id, snapshot_date)`, the ledger's per-day external id), so even a second read the same day updates that day's row. A failed hour leaves no stamp, and the next hour retries. |
| A deleted fact stays deleted | It is landed by part 2a's `syncTikTok` through `connector_fed_items` (D655): a ledger row with no `local_id` is touched, never re-created. |
| Counts only in logs | `daily.ts` logs nothing. `index.ts` logs `scanned ok failed skipped snapshots videos kept_deleted`. |
| Failures stay apart | Each connection fails on its own. Its `last_error` is a code (`tiktok_unauthorized`, …), never TikTok's body, and its status is not changed. A refresh lease held by a founder's concurrent sync reads as `unauthorized` too, so flipping a connection to `error` here would be wrong. |
| No KPI | It writes the two fact tables, the ledger, the link's cursor and the connection's stamps. It never writes `project_metrics`, `custom_kpi_values` or `portfolio_updates`. |

`last_synced_at` is stamped from the pass's own instant, in `CURRENT_TIMESTAMP`'s shape, so "synced today" means the day the pass ran.
