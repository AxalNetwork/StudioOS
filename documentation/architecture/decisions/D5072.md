## D5072 — Data Room Home: no placeholder, no duplicate module read (#5072)

- **Status:** Built, 2026-11-09 (frontend only).
- **Builds on:** D5074 (#5172, merged), which put the venture's `projectUid` in one shared context (`useVenture`) and moved the Data room onto it, and D5070 (merged), whose error contract Data Room search and indexing already use.

### What the issue found, and what was already done

1. **Stale placeholder.** Home's "The last ninety days" block rendered `ACTIVITY_WAIT`: "The last ninety days need the activity read (part 4, D1105)…". Part 4 shipped. **Fixed here.**
2. **Project lookup in the tabs.** `useRoom` read the whole projects list and scanned it for the uid. **Already fixed on `main` by D5074**: the tab takes `projectUid` from `useVenture()`, which reads the list once per page and shares it.
3. **Search and index failures** use D5070's `userFacingRaiseError`. **Already on `main`.**

### What this changes

- **Placeholder:** the block says what Activity holds (daily opens, downloads and blocked requests, the last fifty events, this week's counts) and links to the Activity tab. A real 90-day figure on Home would be one more request on every open, against the point of the package, and Activity is one click away.
- **A duplicate read, found by measuring.** Opening any module page read its module twice: `CycleRoute` reset the table's query on mount with a fresh `{}`, and the module read depends on `query`, so its effect ran again. The reset now keeps the same object when the query already is the default, so the read runs once. This is in `CycleRoute`, so it removes a request from every module page's first open, not only the Data room's.
- **Measured on Home's cold open** (the test's fetch log, before D5074 and this change): 13 requests, of which the module read was sent twice and a projects read came first. With D5074 the projects read is shared; with this change nothing is repeated. The Home test now asserts no GET repeats.

### Considered, not built

- **Dropping the shared projects read entirely.** A `GET /api/data-room/by-project/:projectId` that finds the uid from the id (and answers with it) would remove the one remaining directory read per page. I built it, then dropped it when D5074 landed: the venture context is that package's design, and a second way to resolve the uid would fight it. It is the follow-up if the directory read should go.
- **Automatic search index after a file change.** The index step reads and embeds each file; doing it inline in an upload or move would slow and risk the write, and doing it properly needs a queue job keyed on the change. The manual Index control stays.
