## D4161 — HQ moderates a company's skills and never writes one (#4161)

- **Status:** built by Claude Code for slot S08, 2026-11-02. Not deployed and not checked live.
- **Part of:** #4137 (HQ › AI agents), task H3 (Worker). Boards SA5, SA5b and SA9g.
- **Migration:** `202611022055_agent_skill_moderation.sql` (D4106's stamped name).

### 1. The routes

`routes/admin_company_skills.ts` mounts itself at `/api/admin/ai-agents/company-skills`, and every route is Super Admin only (`requireSuperAdmin`):
- `GET /` is the queue. It lists every `scope = 'company'` skill across companies, 25 a page, filtered by `status` and `q`.
- `GET /:uid` returns the SKILL.md read-only, plus the open flag or suspension and its history.
- `POST /:uid/flag`, `/suspend` and `/clear` each take `{ reason }`.

### 2. Flag, suspend, clear

- **A flag** leaves the skill running. The company's editors are told why in their inbox.
- **A suspension** stops it at once: the run gate refuses it, and it cannot be pinned again. The editors are told why. A suspension replaces an open flag, and the flag closes with the suspension's reason.
- **A clear** lifts the open flag or suspension. The editors are told.

Every action needs a reason of 10 to 500 characters (400 `reason_required`). Without one, nothing is written: no row, no audit, no inbox item.

The editors are the members `canEdit` lets write: the primary admin, or a member whose role in the company is Owner, Admin or Founder. Others are not told. The inbox link opens the skill on the company's Team page.

### 3. The run gate

`services/agents/skillModeration.ts`'s `skillRunRefusal(env, skillId, pinnedVersion)` is the one gate. A pinned version may not run when either:
- the skill has an open suspension; or
- a suspension closed only because the company republished, and it covered the pinned version (its `version` and below).

A flag never stops a run.

No run path puts a skill into an agent's turn yet: that is D1612 part D (#3954), which must call this gate before using a skill. Until then, the gate holds in two places:
- `attachCheck` refuses to pin a suspended skill (409 `skill_suspended`). An agent that already has it keeps it pinned, so editing its other skills is not refused.
- An agent's skills read carries `suspended: true`.

### 4. HQ has no write path

- The HQ router writes only `agent_skill_moderation`, and a test reads its source to prove it.
- `routes/team_skills.ts` now writes a company skill only for that company's own editors, through `canEditAsMember`, which is `canEdit` without the platform-admin pass. A Super Admin is refused 403 `not_editor` on `POST /skills`, `PATCH /skills/:uid` and `POST /skills/:uid/publish` for a company skill. The library's `company.can_write` says false to them.
- Before this, `canEdit`'s admin pass let any HQ admin edit a company's skill.

### 5. Republishing clears it

When the company publishes a new version, the publish batch closes the open flag or suspension (`cleared_how = 'republished'`):
- the new version starts clean;
- the versions the suspension covered stay refused at the run gate, until the team moves to the new one or HQ clears the suspension outright.

Rows are never deleted (a trigger refuses it), so the history stays.

### 6. Audit

Each action writes `services/adminAudit.ts`'s `logAdminAction` row: `agent_skill_flagged`, `agent_skill_suspended` or `agent_skill_moderation_cleared`. Its details hold the skill, the company, the reason, and the status before and after.

When H5's admin audit table lands, these actions move to it with the same keys.

### 7. What the queue shows

- **People** are `{ uid, name }`, never an email.
- **Project** is null: migration 759 scopes a company skill to the whole company.
- **Area** is the radar axis of the skill's first taxonomy tag; null when it has none.
- **Version** is null before the first publish, never 0.
- **Status** is `suspended` or `flagged` while one is open, else the skill's own. `in_review` is HQ's review state (H2), so the filter accepts it but no company skill is ever in it.
- **Order:** suspended first, then flagged, then the most recently updated.
