## D6698 — HQ case actions and Formation cases waiting on HQ (#6698)

HQ records a partner’s registry actions until partner accounts are available. The Worker verifies the authenticated HQ admin, loads the case by UID and verifies the current HQ owner or Super Admin before using private evidence. An HQ admin may assign an unassigned case. The assigned owner must be an active admin. Confirmation additionally uses the existing recent strong-factor gate.

Each operation is a JSON POST under `/api/admin/formation/cases/:uid/`. A caller can send the case revision it read as `expected_revision`. Every transaction independently checks the case stage, revision, closure, owner, partner, hold and waiting party at commit. A stale case or filing returns 409 with the entire batch rolled back. A successful action appends its case event and sealed admin audit row together. `logAdminAction` also records the activity. The authenticated user supplies the actor identity. The stored assignment supplies the partner identity.

| Action | Input and effect |
| --- | --- |
| `assign` | `owner_user_id` assigns an active HQ admin and updates the shared Approvals assignment and history. Assignment on the HQ inbox also changes the case owner in its batch. |
| `requests` | `asked_of`, `kind`, `title`, and optional `body`, `due_on`, `filing_id`, `bound_sha256` use D6695’s request, waiting party, visibility and notice. Founder notices go to the case’s own founder. |
| `notes` | `text` and optional `visibility` append a D6695 timeline note. The default is HQ only. |
| `filing-events` | `filing_uid`, `event`, `recorded_for_partner_id` and a written `reason`. Submitted uses `submitted_on` and optional `reference`. Queried and answered use `occurred_on`. Rejected uses `registry_date` and a distinct `rejection_reason`. Withdrawn uses the reason. Accepted uses `registry_date`, `registration_number`, `certificate_document_id` and optional structured `address`. Evidence documents must belong to the case. |
| `confirm-registration` | `filing_uid`, `recorded_for_partner_id`, `reason`. Consumes the facts from that partner’s recorded acceptance. D6694 writes the registered stage, filed order, company, certificate and post-registration pack together. |
| `hold`, `release` | A manual hold takes a `reason` and `waiting_on`. Release restores the active request’s party or the prior wait. Screening holds retain their separate review gate. |
| `cancel` | A written `reason` closes the case as cancelled and preserves its orders and filings. |
| `refund-review` | A written `reason` records a handoff for a rejected incorporation filing with a paid order. The response supplies the existing Billing review endpoint and the order’s payment intent. Billing controls its own review, permissions and confirmation. |
| `legacy-correction` | Registry date, number, certificate and a written reason use D6694’s after-the-fact correction for a registered legacy case. Its original filed date is preserved. |

The HQ proxy path distinguishes the registry’s acceptance from HQ’s confirmation. An accepted v2 incorporation filing waits on HQ and appears in its lane. Confirmation uses the recorded evidence without taking replacement facts in the request. Existing direct D6694 callers retain their atomic registration behavior. This phase covers HQ-entered partner records. The later partner workspace owns direct partner writes and the selection of its registrations for sampling after its first five (#6682 Q19).

The existing HQ lane registry, inbox, shared assignment reader and Studio Glance expose the same open cases waiting on HQ as D6697. Age starts at the most recent recorded waiting-party change. An assignment grants the case owner the access already enforced and logged by D6697. Case decisions remain on the case timeline. There is no migration.

The migrated-SQLite route tests use synthetic users, registry facts and documents. They exercise refusal paths, transaction races and both ownership entry points.
