### What the canvas decides

- `/delivery` lands on **Board** (Attention and All views); zones Deliverables, Capacity (with overload detail), Status reports (list and composer), Health (risk board and engagement detail); one cross-zone engagement sheet reusing the zone reads.

### Backend required

- Client open tracking (nothing sets `opened_at`).
- One basis for capacity: limits are weekly hours, allocations are monthly (#4690).
- A Blocked field on status reports (today `shipped` and `next_up` only).
- Client review history (only the latest satisfaction and its source are stored).
- An expected-version check on writes, for the conflict state.

## Backend part 1 (#5314): client-open tracking

- **The client records the open.** `POST /api/client/deliverables/:uid/open` (`client_deliverables.ts`) is the founder-side surface `opened_at` was always waiting for (migration 208:160). Only the engagement's client founder (`users.founder_id = engagements.founder_id`, the `statusReportAccess` rule) reaches it; anyone else gets 404. It answers the shared link and records the FIRST open: `opened_at`, `opened_by`, and the `revision` (D4682) and `version` the client was shown. A later open changes nothing, and a trigger in migration `202611110731_5314_deliverable_client_opens.sql` refuses a rewrite. Nothing is sent to anyone.
- **The client sees it on the engagement.** The engagement dialog (`NeedsBoardPage.jsx`) lists, for the founder only, what the firm has sent, with Open. Drafts are never listed.
- **The shared version.** The open names the row's `revision`, the version #4710's acknowledgement is to name too. A firm edit after the open shows as "Opened an earlier version" (`opened_current: false`).
- **When "Never opened" is a finding.** `delivery_read_instrumentation` records when opens began. A sent deliverable reads Never opened only if it was sent from then on and has a link to open; one sent before, or with no link, reads "Not recorded" and says which. With no instrument the book keeps the #4690 rule: `unopened_count` is null, never 0.
- **Back on the page:** the Never opened tile counts the Worker's `is_unopened`, the chase draft gathers only those rows, and the median days to open is taken over recorded opens, stated as Not recorded below three.
- **File ownership with #4709 (S33):** this part changed only the deliverable read and its helpers in `partner_delivery.ts`; period filtering, pagination and immutable sent evidence stay #4709's.

## Backend part 2 (#5314): a written Blocked section, and client review history

The owner split the canvas's "Backend required" list into #5314 on 2026-11-09. Part 2 builds two of its items.

- **Blocked is now a written section.** A report stores `blocked`, words the firm writes like Shipped and Next, and `blocked_recorded_at` (migration `202611111140_5314_status_report_blocked_history.sql`).
  - The engagement's open blockers stay live evidence beneath the section and are never copied in, so their side cannot go stale.
  - A report saved before the section existed, or saved without stating it, has no `blocked_recorded_at` and reads **Not recorded**. It never reads "nothing blocked".
  - A recorded empty section is the firm stating that nothing is blocked.
  - An omitted `blocked` key leaves the section as it was. The composer always sends it.
  - A sent report's section is frozen by a trigger, like the rest of the report (D4682).
- **Client review history.** `engagement_client_reviews` takes one row each time the client's score, source or date changes, written in the same batch as the health row. A save that leaves the review alone (the owner only, say) appends nothing.
  - Two triggers refuse any update or delete, so the history is what was recorded, in order.
  - `GET /api/partner/delivery/engagements/:id/reviews` lists it, oldest first. A score saved before the history began reads "earlier reviews Not recorded". An unreadable history is `available: false`, never an empty list.
  - Health's engagement detail draws it as "Client review history".
- **Built with part 3:** the status-report save and the health save carry part 3's expected-version check. On the health save, the review row is appended in the same batch only when the guarded write changed the row (`changes() = 1`), so a stale save appends no review.
- **Still not built here:** one capacity basis (part 4).

## Backend part 3 (#5314): every Delivery edit states the version it read

- **Status:** built by S08, 2026-11-11 (#5314 part 3). Owner's call (2026-11-11): the check covers every Delivery edit; creates are unaffected.
- **Migration:** `202611111141_5314_delivery_write_versions.sql` gives `revision` to the four stores D4682 left without one: `partner_engagement_health`, `partner_capacity`, `partner_internal_hours` and `engagement_hours`.

### The rule

1. **A write states the revision it read**, as `expected_revision` in its body, or `?expected_revision=` on a DELETE. Every Delivery read returns the revision it must send back: milestones, blockers, deliverables, seats and reports carry `revision`; Health carries `health_revision`; Capacity carries `cap_revision` (the firm's, and each person's), `internal_revision` and, per month, `revisions` on the hours entries.
2. **A stale write changes nothing** and answers 409 `delivery_changed` with `current_version` (and D4682's `revision`, the same number). The check is a pre-read comparison and, again, the write's own `WHERE … AND revision = ?`, so a write that lands between the read and the write still wins.
3. **`null` means "I read no record"** on the four upserts: a first save inserts only while there is still none, so two people creating the same health row, cap or month of hours cannot both win. A number names the row's revision; a removal (`weekly_hours: null`, `hours: null`, a DELETE) names it too.
4. **A malformed `expected_revision` is refused** (400 `bad_expected_revision`), never read as silence.
5. **A write that states nothing keeps D4682's guard** (its own read's revision, and the one field-level retry). It is not refused with 428: the deploy keeps 72 hours of older bundles serving (D529), and a tab opened before this build would otherwise fail every edit. The page always states one, and `frontend/test/delivery_write_conflicts_5314.test.mjs` fails if any Delivery write in the four zones stops doing so. A later PR can make it required once no older bundle can reach the Worker.

### The conflict state

A refused write draws the canvas's conflict state where the write was made (`DeliveryNote`): it says nothing was saved, and offers **Reload** (read again and drop this edit) and **Keep my edits** (send the same write again at the version that is there now). A status report draft adopts the revision its save returned, so a second save is not a conflict with itself.
