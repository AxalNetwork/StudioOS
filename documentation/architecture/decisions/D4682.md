## D4682 — Delivery edits and invoicing hold under concurrent requests, retries and partial failure (#4682)

- **Status:** built by S13, 2026-11-07 (#4682, Delivery audit 2/6, P1).
- **Migration:** `202611072115_delivery_revisions.sql`.

### The defects

1. A PATCH read a row, merged the body over it and wrote every column back by id. A request that read before another request finished overwrote that request: a stale edit reopened a completed milestone, un-cleared a blocker, unsent a deliverable or rewrote a revoked seat.
2. A status report's edit, send and delete each checked `state` in a read and wrote by id. A send racing an edit sent text nobody checked; a send racing a send replaced the recorded sender and time; an edit or delete racing a send changed or removed a record the client had received.
3. `nextInvoiceNumber` bumped the counter and read it back in a second statement, so two requests could print the same number. `issueInvoice` read, then inserted, so the loser of a race for one engagement burned a number.
4. `POST /engagements/:id/invoice` issued the invoice and then wrote the engagement in a second statement. A failure between them left a document with an engagement that did not claim it; a retry then went through the same path with nothing to reconcile it.
5. The engagement transitions (`start`, `deliver`, `cancel`) wrote by id, so a cancel racing a deliver could overwrite the cancellation. Several writes on another party's record (an admin's transition, a milestone, a report) left no actor line.

### The rule

1. **A revision on every Delivery child record.** Milestones, blockers, deliverables, seats and status reports carry `revision`. Every edit and delete is `WHERE id = ? AND revision = ?` and bumps it, and the route checks the affected-row count: a request that lost changes nothing and answers 409 `delivery_changed`, with the current revision.
2. **Omitted fields come from the current row.** A PATCH that loses the revision check reads the row again and merges again, once, but only when the concurrent change did not touch a field this request sets. Otherwise it is a conflict, because the caller was about to overwrite something it never saw. A caller that sends `expected_revision` is never retried: a different revision is a conflict at once.
3. **Sealed records are sealed in the statement and in the database.** A seat edit repeats `revoked_at IS NULL`, a revoke repeats it too, a report edit and delete repeat `state = 'draft'`. Triggers refuse any change to a revoked seat, and any change to or deletion of a sent report, whatever code runs.
4. **Sending a report sends the revision that was checked.** The send names the draft revision it read (and the caller's `expected_revision`, if any) and records it as `sent_revision`. An edit that landed since makes the send change nothing.
5. **A duplicate send has one outcome.** The same person retrying gets the record that exists (200, `already_sent`), unchanged. Anyone else is 409 `already_sent`. The recorded sender and time are never replaced.
6. **Invoice numbers are reserved inside the insert.** `issueInvoice` is one batch of three statements: reserve the number for the year, insert the invoice with it, mark the engagement `invoiced` with that invoice's number. The first two run only if the engagement has no invoice yet and can be invoiced, so a request that loses reserves nothing and returns the invoice that exists. A failure rolls the batch back: no document without the engagement claiming it, no claim without a document, no number lost. `nextInvoiceNumber` is one `INSERT … RETURNING`.
7. **Recovery needs no second document.** An engagement still `delivered` whose invoice exists (the old two-step write) is reconciled by the same batch on the next request. A retry after success is a 200 (`already_invoiced`).
8. **Lifecycle moves name the state they were decided from.** `start`, `deliver` and `cancel` repeat `status = ?`; a move that lost is 409 `engagement_changed` and the completed transition stands.
9. **Actor lines.** Every transition, and every milestone, deliverable and report write, records its actor through `logActorAct` (ids and states only). A transition says whether an admin made it on a record that is not theirs (`acting_as_admin`).

### What it does not do

- Capacity, hours and the health row are not changed here; they are upserts keyed by their natural key and have no state to lose.
- A payment is not implied. An invoice is still a document, not a charge.
