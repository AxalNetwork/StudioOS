### 1. Corrections and choices where the spec left room

- **The per-event routes have their own module.** They live in `routes/event_syndication.ts`, mounted at `/api/events` before `events.ts`, not inside `events.ts`. Every path is `/:id/syndication…`, so nothing of `events.ts` is shadowed. The module imports `canManage` from `events.ts`, so the gate is the same function.
- **A channel ticked after the approval posts at once.** The approval it waits for has already happened, so the row starts `pending` and a `post` is queued. Before approval it starts `selected` and posts on Approve. Owner question B (a) holds: only an admin's Approve makes an event eligible.
- **Unticking deletes a row that is not posted.** The log keeps the `unselect` and the history. A posted row cannot be unticked: 409 `already_posted`, use withdraw.
- **Disconnect** turns the account's `selected` and `pending` rows to `skipped` ("Account expired"). Posted listings stay up on the channel, as the spec says.
- **Retry** works from `failed`: a failed post, or a posted listing whose update failed. A failed post is re-checked first: 409 `not_eligible` with its sentence.
- **Withdraw on a channel that cannot remove its post** (a link post) sets `sync_state = 'unsupported'` and logs `skipped` with "Remove it on the channel by hand". The screens draw that row as "Remove the post on Facebook by hand ↗".
- **Settings** default to `hosts: 'approved_events'` (S1's recommendation (a) for owner question A) and `host_accounts: false` (question C (a)).

### 2. The eligibility rule (`eligibility.ts`)

One pure function, which every route and the job ask. The job asks again at run time. An event may be listed on an account only when all of these hold:

1. the public feed's predicate: `visibility = 'public' AND status = 'published' AND admin_published = 1`;
2. `starts_at` is in the future;
3. the host passes `hosts` (`admins` means only an admin's events);
4. the account is `active`;
5. the account is HQ's, or the host's own (`owner_user_id = host_user_id`) while `host_accounts` is on.

The five skip sentences are fixed:
- "Private event": private and unlisted alike, since unlisted is link-only;
- "Not approved for the public calendar";
- "Event has started";
- "Account expired";
- "Host not allowed by HQ settings".

### 3. The triggers (`hooks.ts`)

Each is one bound UPDATE of the event's rows, then one `event_syndication` job per row that has work. The idempotency key is `uid:action:content_hash`.

| Trigger | Where | What it does |
| --- | --- | --- |
| Approve | `admin_events.ts` `POST /:id/approve`, after the event is published | `selected` → `pending`; `post` |
| Edit | `events.ts` `PATCH /:id`, by the host or an admin | a `posted` row whose `pushed_hash` differs → `sync_state` `pending` and `update`, or `unsupported` when its channel cannot edit |
| Cancel | `events.ts` and `admin_events.ts` `POST /:id/cancel` | `posted` → `cancel` (or `unsupported`); not yet posted → `cancelled` |
| Unpublish | `admin_events.ts` `POST /:id/unpublish` | `posted` → `withdraw` (or `unsupported`); not yet posted → `withdrawn` |

**The content hash** (`content.ts`) covers every field a listing sends:
- the slug, type, title, summary and description;
- the cover;
- both times and the time zone;
- the place (location kind, text and URL);
- the price.

D917's `changed_after_approval_at` covers host edits to a smaller list, so a description or cover change was invisible to it. It is not used here.

**A hook never fails the event write.** `runHook` catches everything, logs a code and writes one `failed` log row when it can.

### 4. The job (`jobs.ts`)

- **It re-reads the row, the account and the event.** A `post` runs only from `pending`; an `update`, `cancel` or `withdraw` only from `posted` with `sync_state = 'pending'`. So a repeated message, or two at once, calls the adapter once.
- **For a `post`, the run-time check comes first:**
  - an event cancelled while queued makes the row `cancelled`, with no adapter call;
  - an ineligible event makes it `skipped`, with its sentence.
- **The link back** is `https://axal.vc/events/<slug>?utm_source=<channel>&utm_medium=event_syndication`.
- **A refusal** stores the platform's sentence on the row and in the log:
  - trimmed to 500 characters;
  - every credential value replaced by `[redacted]`, with bearer, token and key strings caught too.
  - It then throws so the queue retries. The third failed run marks the row `failed` (or `sync_state = 'failed'`) and stops.
  - A 429 reads "Rate limited by <channel>; retry after <time>" when the platform names a time.
- **The dead-letter consumer** marks a row whose message ran out of retries `failed`, keeping the reason the last run stored.

### 5. The routes

**HQ** (`/api/admin/event-syndication`):
- **Gates:**
  - `requireSuperAdmin` for `GET /channels`;
  - `requireSuperAdminWriteBar` for every write;
  - `requireHqAdmin` for `GET /settings` and `GET /log`.
- **Refusals:** each gate's sentence becomes `refuse(…)`: 403 `super_admin_required`, 403 `hq_only` on a branch, 403 `totp_required` or `step_up_required`, and 401.
- **No read selects `credentials_enc`.** A test reads every `SELECT … FROM event_channel_accounts` in the module and checks the responses.
- **OAuth `state`** is an HMAC over the channel, a nonce and the Super Admin's id. The nonce is held in KV for ten minutes and deleted on first use, as `linkedin.ts` does.

**One event** (`/api/events/:id/syndication`):
- **Gate:** `canManage`. Anyone else, and an event that does not exist, gets the same 404.
- **Overrides:** title, description and ticket link only. They are held to the channel's limits (200 and 5,000 characters while it has no adapter), and the ticket link must be https; otherwise 400 `invalid_overrides`. Another host's account is 404.
- **`registrations`** is null with "Not recorded: this channel's registrations are not imported" until Part D. It is never 0.
