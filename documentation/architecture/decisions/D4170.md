## D4170 — Data room: Eadwyn's proposals as accept-or-dismiss actions (#4170)

- **Status:** built by S09, 2026-11-02 (#4170, split from #4046).
- **Code:** `cloudflare-worker/src/services/dataRoomProposals.ts`, `cloudflare-worker/src/routes/data_room_proposals.ts`, `frontend/src/pages/raise/dataroom/DataRoomChecklist.jsx` and `checklistModel.js`, and the client in `frontend/src/lib/api/dataRoom.js`.
- **Tests:** `cloudflare-worker/test/data_room_proposals_4170.test.ts` and `frontend/test/data_room_d1108.test.mjs`.

### 1. What a proposal is

There are three types. Each is an action on file **metadata**, never a form field, so none of them goes through the fill registry (D777).

| Type | Option | What Accept writes |
| --- | --- | --- |
| match | `dataroom:match` | the file's `checklist_item`, only while the file has none |
| folder | `dataroom:folder` | a top-level file's `folder_id`. The named top-level folder is used if it exists; otherwise it is created with the file's own gate. |
| gap | `dataroom:gap` | nothing. It is a note: Accept marks it noted, and no file is written. |

### 2. Where they are kept: the existing store

There is no new table and no migration. Each proposal is one `ai_rail_proposals` row (D780):

- page `Founder · Raise · Data room`;
- record `data-room:<projectUid>`;
- kind `proposal`;
- payload `{ type, file_uid?, item?, folder_name?, would_satisfy?, reason }`.

Rows are the proposer's own, like every rail proposal. A member sees and decides only the rows they asked for.

The generic decide route (`decideRailAs`) can only **discard** a `dataroom:` proposal, as it does for `derive:` (D1583). Accept is the room's own route, so a proposal can never be marked accepted without its one change, or outside the room's gate.

### 3. The run: quoted, held, and given names only

1. `POST …/proposals/quote` prices one `rail_reason` run. It returns a `confirm_quote`: a SHA-256 over the member, the room, the index the run will be shown, the model and the hold.
2. `POST …/proposals/run` recomputes the quote. If the request does not carry the same digest, the answer is 402 `quote_required` with the fresh quote, and the model is never called.
   - A renamed or added file changes the digest, so a quote is for the room as it was.
   - The digest is taken over the index itself, not the prompt. The prompt's untrusted block carries a random delimiter.
3. The run is shown the room's **index** and nothing else:
   - file names, the folder each file is in, and the item it already answers;
   - top-level folder names;
   - the twelve checklist labels.

   It is sent inside an untrusted block (D1506). No file is opened, so no content leaves the room's access gate. No storage key and no person is sent.
4. The output is checked against the room before anything is stored (`proposalsFrom`). A proposal is dropped when:
   - its file is unknown;
   - for a match, its file already answers an item;
   - for a folder, its file is already in a folder;
   - for a gap, the item is unknown or already answered;
   - it repeats a file or a gap item;
   - its reason or folder name carries an email address, or the words "advice" or "advisor".

   At most 20 proposals are kept.
5. A new run withdraws the member's earlier open proposals for the room.

### 4. Accept: one change, one batch, the actor recorded

Accept is one D1 batch keyed by a fresh nonce:

1. The proposal is marked accepted only while it is open and its file is as proposed.
2. The file is written only under that nonce.

If the file write does not land, the proposal is put back to open and the answer is 409 `proposal_stale`. Two presses cannot both apply, and a match the founder made by hand since is never overwritten.

Every press records its actor in two places: `decided_by_user_id` (migration 712) and one `activity_logs` row on the room (`proposal_accepted`, `proposal_dismissed` or `proposal_undone`).

### 5. Access never changes

- **A match** changes nothing about who can open a file. This was already true in D1108: `checklist_item` is not part of `tierAdmits`.
- **A folder move** can change access, because a grant scoped to folders admits a file only inside its folders (D1103). A top-level file is outside every scope. Accept is refused with 409 `would_change_access`, and nothing is written, when the target folder:
  - is named by an active grant scoped to folders, or
  - has a different gate (`visibility`) from the file.

  The check runs before the batch and again inside the file write. A folder Accept creates takes the file's own gate, and no grant names a new folder.
- **No proposal** deletes a file, or changes a gate, a tier, an expiry, an NDA or a grant.

### 6. Dismiss and Undo

**Dismiss** writes only the proposal (`discarded`, with its actor).

**Undo** applies to an accepted match or folder move:

- It puts the file back only while the file still holds what the accept wrote. A later hand change is left alone (409 `proposal_stale`).
- The proposal is then filed as `discarded`, with `undone` and the actor in its decided payload.
- Undo works once.
- A folder the accept created stays, because removing a folder is the founder's own choice. A gap has nothing to undo.

### 7. Who

The room's owner and its co-founders can ask and press. These are the people who may match, move and rename files in the room (`roomProject`, D1103; now exported from `data_room.ts`).

- Anyone else, an admin included, gets 404, as on every founder-side room route.
- A member who lost write access since asking cannot accept. The gate is read on every press.

### 8. The page

Checklist's "Eadwyn proposals" group (DR14) lists the member's own proposals:

- each with its reason, Accept and Dismiss, and Undo once a match or move is accepted;
- an empty list reads "No proposals";
- a failed read is "Proposals could not be read · Try again", never an empty list.

**Ask Eadwyn** reads the quote first ("Holds up to $… · you pay what it uses"). **Read the room** runs it, with that quote's confirmation. An accepted match and an undo read the checklist again. People appear by name only; no email is drawn.
