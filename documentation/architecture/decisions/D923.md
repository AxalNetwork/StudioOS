### 2. What is read, and from where

| Read | Used for |
|---|---|
| `GET /api/admin/partners/invitations` (R1), newest 200 by first send | every invitation's own fields, the Overview's invitation tiles, the stage words |
| `GET /api/admin/partners/deals?status=` (R2), once for each of the six states, newest 200 each | every deal's own fields, the deal tiles, the stage repair |
| `GET /api/admin/partners/deals/top?status=all&limit=5` (R3) | Top deals by redemptions |
| `GET /api/admin/partners/deals/:id/redemptions` (R4), at most 500 | one deal's redeemers, and the fan-out under Guard F |
| `GET /api/admin/contracts/partner-deals` (R5), no cap | the exact Deals total and all-time redemptions. A recovery cool-off can refuse it. |
| `GET /api/admin/partners/links` (R6), 500 accounts | the unattached-accounts row and the Firm links tab |
| `GET /api/legal/esign/:id` (R7) | one invitation's or one deal's envelope: sent date, status, signing-link expiry |
| `GET /api/legal/esign/templates/partner_services` (R8) | the agreement-ready rule |
| `GET /api/dd/cases?subject_type=partner` (R9), newest 200 | the Deals table's Due diligence column and one deal's case |
| `trustScoreBatch([user_id])` (R10) | one deal's outstanding obligations |
| `GET /api/admin/users?q=<email>` (R11) | New invitation's member check |
| `GET /api/profiling/admin/:email` (R12) | one invitation's answers, only when the admin asks (§3) |

The writes are create, resend, revoke, terminate and the firm link. Their clients all exist (`adminPartners.*`), so the drift test needs no change.

- **Every one of these reads is truthful:** a D1 error is a 5xx, or a coded 503 on R5. Two Contracts reads hide failures, so the page does not use them: the detail for `partner_deal:<id>` and the Agreements union.
- **A failed read says so.** Each block draws `Unreadable` with Try again and leaves the rest of the page standing. A failed list never says "No invitations yet". After a failed refresh, earlier rows stay only under a "Could not refresh" line.
  - A 423 `recovery_cool_off_active` on R5, R7, R8 or R9 says the read is paused after a recent account recovery. It never says "Not opened" or "Not sent".
- **Guard L — lists that stop without saying so.** A list that returns exactly its cap is incomplete.
  - The caps are R1 200, each R2 200, R4 500, R6 500, R9 200 and R11 100.
  - Every figure drawn from a list at its cap says what it covers: "200+", "within the newest 200", "of the first 500". It is never drawn as a total.
  - Below the cap, client-side search, filters, sort, pages and counts are exact. R1's `status` and `email` filters are applied before its cap.
  - R5 is uncapped. When it answers, its `total` and per-deal redemption counts are exact, so it is read first. The six R2 lists are the fallback.
- **Guard F — sums over a fan-out.** The Referrals tiles and table, and the Overview's 90-day redemptions tile, call R4 once for each deal that has redemptions.
  - The deal set comes from R5 (`redemption_count > 0`), or else from the six R2 lists.
  - A figure is exact only when all three hold:
    - the deal set is complete;
    - every R4 call succeeded;
    - each call's row count equals that deal's uncapped count.
  - If a call failed, the figure reads "Could not be read for [k] of [m] deals", never a smaller number. A deal whose redeemers stop at 500 reads "First 500 for this deal".
- **Guard I — the stage word.** R1's stored status maps to the canvas's words:

  | Stored | Word |
  |---|---|
  | `sent` | Sent |
  | `viewed` | Opened |
  | `profiled` | Profile done |
  | `proposed` | Offers shown |
  | `selected` | Offer chosen |
  | `finalized` | Agreement out |
  | `signed` | Signed |
  | `revoked` | Revoked |

  - **Lapsed** means the link's `expires_at` has passed and the invitation is not Signed or Revoked (R1's `is_expired`). The dots stay at the stage reached, as the canvas draws Mara.
  - **No sweep writes it.** #2370's "a daily sweep marks lapsed invitations expired" is dropped, because that would erase the stage the canvas keeps. Part 3's server filter computes Lapsed by the same rule.
  - **A stored `expired` keeps its one meaning:** the agreement was signed after the link lapsed, and the deal was voided. It reads "Signed after the link lapsed · deal voided", never "link expired before signing".
  - **After a resend,** today's Worker writes `sent` over every stage. The page repairs the stage until part 1 stops the overwrite:
    - **Agreement out:** a row with an `envelope_id` that is not Signed, Revoked or stored `expired` is at least Agreement out. R1 proves this with no cap.
    - **Offer chosen:** a deal in R2 `proposed` with this `invitation_id` lifts the row to Offer chosen. If that list is at its cap or failed, the row says "Stage may lag".
    - Profile done and Offers shown cannot be repaired until part 1.
  - **A row was resent** when `expires_at` minus 14 days is later than `created_at`. Such a row reads "Resent [date]" beside its first send.
- **Dates.** D1's zone-less stamps (`created_at`, `viewed_at`, `signed_at`, `revoked_at`, `activated_at`) are parsed as UTC. `expires_at` carries its Z. D915's `parseStamp` moves to `frontend/src/ui/` in its own commit, and both desks use it.
- **The words are the canvas's:**
  - **Deal states:** Offer chosen, not sent · Awaiting signature · Active · Term over · Terminated · Voided.
  - **Deal types:** Equity partnership · Services partnership · Deal-sourcing revenue share · Capital partnership · Custom. Raw words like `awaiting_signature` never show.
  - **"Ending soon"** means within 30 days on this page. The branch home's 60-day count is its own figure, and this is recorded, not reconciled.
  - **Tiers.** The stored founder grant, `founder_pro`, is on no founder ladder (`requireTier.ts`). An unknown tier ranks as free.
    - So "Founder Pro" is never drawn as a plan.
    - The page draws the stored investor tier and "Founder grant: no plan", until O-TIER (§5).
  - **Term.** The stored start and end dates are drawn, never an end computed from months, because the Worker counts a month as 30 days (O-MONTH, §5). An active deal past its end, before the daily sweep, reads "Term ended, not yet closed". It never shows negative days.
  - **Placeholders.** A missing value is "Not recorded". A value that is stored but not returned by any read yet is "Not read here yet". A failed read says what could not be read. In particular:
    - **Email delivery:** "Not read here yet". The result sits only in the audit rows. Once part 1 stores it, the words are "Sent" and "Not sent", never "Delivered".
    - **The Profile done and Offers shown dates:** "Not read here yet". They exist only as onboarding activity rows.
    - **Offer chosen:** "First chosen [date]", from the deal row's `created_at`.
    - **Agreement out:** the envelope's `created_at` from R7.
    - **The message to the invitee**, the history beyond the record's own dates, who terminated, a redeemer's role, the KYB section and each obligation's own state: all "Not read here yet".
- **The agreement-ready rule** (one rule, from the map's Part A §0.1, R5). The Partner Services agreement cannot be sent yet when either is true:
  - R8 refuses, because the template has no body or cannot be read;
  - it lists a field that finalize leaves empty. That is a sender field outside the five finalize fills, or any `counterparty.*` field, which this flow never fills.

  When R8 itself fails, nothing is said either way. Part 5's signal replaces this rule.
- **Where links go:**
  - **Agreements:** the envelope page `/legal/send?envelope=<id>`. Any admin can read it there, and the original inviter has Remind.
  - **The template:** `/admin/contracts?tab=templates`.
  - **Payouts:** `/admin/contracts?tab=partner-deals`.
  - **Due diligence:** `/admin/due-diligence/:uid`.
  - **Partner profiles:** `/admin?tab=profiles`.
  - **Firms:** the Firm links tab, until #2369.
  - **"Member record":** plain text until #2377 gives every admin an account address.
