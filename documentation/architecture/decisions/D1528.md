### Migration 728: the six tables

All new tables, so every statement is `IF NOT EXISTS` and the file re-runs cleanly. Nothing is altered, rebuilt or backfilled. Scope rows follow #3727's pattern (712, 727): `scope_kind`, with exactly one of `company_id` and `project_id`, both immutable ids.

| Table | For | What it holds |
|---|---|---|
| `agent_task_runs` | E3 | One row per run attempt: `uid` (also the Workflow instance id), `agent_id`, `task_id`, `attempt` (UNIQUE with the task), `status` (`admitted`, `running`, `waiting_decision`, `done`, `refused`, `failed`, `cancelled`, `halted`, `scope_moved`, `step_lost`), `step` (`load` … `after`), `steps_json` (the step timeline the page reads; summaries never hold a prompt), `workflow_instance_id`, `admitted_company_id`, `usage_log_id`, `proposal_uid`, `refusal` (a code), and timestamps. |
| `agent_duties` | E5 | An agent's recurring duty: `template_key`, `title`, `module`, `option`, `cadence` (`daily`, `weekly`, `monthly`), `weekday` (weekly only) or `day_of_month` (monthly only), `hour_utc`, `next_due_at`, `last_claimed_at`, `last_outcome` (a code), `status`. |
| `agent_handoffs` | E5 | One step of a chain: `chain_uid`, `depth` 1–3 (UNIQUE with the chain), from agent, to role and agent, the tasks it came from and created, `title`, `why` and `note` (≤ 1,000 characters each; the note is untrusted), `status` (`proposed`, `accepted`, `discarded`, `refused`), `refusal` (a code), who decided and when. |
| `agent_memory_notes` | E5 | A note an agent keeps in one scope: `kind` (`decision`, `fact`, `summary`), `body` (1–1,000 characters, never a raw prompt), the run that wrote it, `expires_at` (set when the agent is removed). |
| `agent_custom_roles` | E4 | A scope's own role, key `custom:<uid>`: `name` (≤ 60), `mission` (≤ 600), `works_in`, `reads`, `may_propose`, `hands_off_to` and `kpis` as JSON arrays, `tone`, `status` (`live`, `retired`). |
| `agent_scope_settings` | E3 | One row per scope: `engine_paused` (0 or 1), `max_parallel_runs` (1–5, default 2). A missing row means the defaults. |

**What the schema holds, and what it leaves to the services:**
- **The schema holds:**
  - one live run per agent: a partial unique index on `agent_task_runs (agent_id) WHERE status IN ('admitted', 'running')`;
  - one live duty per agent and template (`duty_exists`);
  - one settings row per scope;
  - every limit above.
- **The services hold:** five live custom roles per scope, the 20-runs-a-day limit, the 90-day note expiry, and handoff loops (`handoff_loop`). Each is a product rule with its own refusal, so it is not a schema CHECK.

**Erasure.** A deleted `team_agents` row takes its runs, duties, memory notes and its own handoffs with it (`ON DELETE CASCADE`). A handoff made to it keeps its row without the agent (`SET NULL`).

`team_agents.paused_reason` has no CHECK (712), so the runtime's added reasons (`spend_limit`, `ai_paused`, `daily_limit`, `scope_archived`) need no migration. The runtime part of this decision documents them.

## Part 2: the runtime

Owner answers it rests on (#3742): Q3 B (in-house runtime first) with the `agents` AI Gateway; Q1 B (`self_start` only after E3 and E5 merge, so this part keeps `manual`); Q2 A; Q5 A; Q6 A (Workflow state 7 days on success, 30 on error); the fallback plan (comment 6542894365) and the product amendment (comment 6543010158).

### Architecture

| Piece | Where | What it is |
| --- | --- | --- |
| The seam | `cloudflare-worker/src/agents/runtime.ts` | `AgentRuntime` and `agentRuntime(env)`. Nothing outside `src/agents/` reaches a binding. |
| The scope object | `doRuntime.ts`, class `AgentScope` | One plain SQLite Durable Object per scope, named `project:{id}` or `company:{id}` (immutable ids), binding `AGENT_SCOPE`, migration tag `v3-agent-scope`. Admission one at a time, duty timers on alarms (the `MeetingBotRun` pattern), a hibernatable status socket (the `PipelineRoom` pattern). It never calls a model. Its behaviour is `ScopeCore`, over a storage interface, so tests drive it. |
| The run | `taskWorkflow.ts`, class `AgentTaskWorkflow` | One Workflow instance per run, id = run uid, binding `AGENT_TASK`, name `studioos-agent-task`. The steps are `loop.ts`'s plain functions. |
| The queue | `agentQueue.ts` | `AGENT_QUEUE` → `studioos-agent-queue` (batch 5, 5 s, 3 retries 30 s apart, 10 consumers), DLQ `studioos-agent-queue-dlq`. A message names one admitted run. |
| The sweep | `sweep.ts` | In the every-minute dispatcher on `% 5 === 1`, under the existing lease, only while the engine is enabled, not gated on `hqCadences`. No new cron line. |
| The record | `engine.ts`, migration 728 | D1 holds every run, its timeline, its proposal and its cost. The object and the Workflow hold only what can be rebuilt from D1. |

Every binding is declared in all three of `wrangler.toml`'s tables (preview with `-preview` names) and rendered for a branch as `studioos-<code>-agent-queue`, `studioos-<code>-agent-queue-dlq` and `studioos-<code>-agent-task` (`scripts/lib/branchConfig.mjs`; `check-branch-config.mjs` fails a branch that keeps HQ's Workflow or sends `AGENT_QUEUE` to its job queue). `branch-provision.yml` creates a branch's two agent queues. The topology page (`services/topology.ts`) lists the three bindings. `main` is unchanged, the migration tags are append-only, and there is no `jurisdiction` in v1 (a branch's `BRANCH_DO_JURISDICTION` still applies through `doNamespace`).

### The seam

`admit(scope, trigger)`, `schedule(scope, duty)`, `cancelSchedule(scope, dutyId)`, `startRun(scope, runUid)`, `status(scope)`, `halt(scope | 'all', reason)`, `rebuild(scope)` and `erase(scope, agentId | null)`. `startRun` takes the run uid; the run key (`agent:<run uid>`) is derived from it, so a caller cannot pass a key that names another run. `rebuild` and `erase` are on the seam because the fallback plan and the amendment need them on every runtime. `AGENT_RUNTIME` is `do`; `sdk` is not built (E0 evaluates it) and falls back to `do` with a warning. Only an sdk runtime's own file may import the `agents` package (`agent_runtime_contract.test.ts`).

The contract suite (`agent_runtime_contract.test.ts`) is parameterised by runtime and runs on `do`: a duplicate admission is refused; schedules fire once, survive eviction and cancel; a crash at any step repeats no proposal, charge or note; halt stops admissions within one request; `rebuild` restores live runs, timers and the pause from D1 alone; a decision reaches a waiting run.

### Admission

The scope's object runs one admission at a time and calls `admitInScope`, which checks, in order: the engine (`off`, `paused`, the halt key, the circuit breaker, or `canary` without a platform admin starting: 403 `engine_paused`); the scope's pause (403 `scope_paused`); the agent active in this scope (409 `agent_not_live`); the task assigned to it, ready (open, every dependency done, on a project board only in Ready) and with a module and option (409 `not_ready`); single flight (409 `agent_busy`); at most `max_parallel_runs` live in the scope (409 `scope_busy`, a code the spec's table did not name); at most 5 proposals waiting (409 `queue_full`). The insert is the last check: 728's single-flight index refuses a second live run even if two objects raced. D1 decides duplicates, never the object's cache, so a live entry the object failed to clear cannot hold an agent. The task moves to `in_progress` (its board column with it), and the object sends one queue message.

### The loop

`load` → `context` → `run` → `propose` → `wait` → `after`, each a named `step.do` (3 retries, 30 s then exponential, on a throw only; a refusal is an answer and ends the run):
1. `load` ends the run on: the engine off or halted; the scope paused; the agent not active; the task not this agent's or not in progress; the project's `company_id` not the one admitted (`scope_moved`); 20 runs of the agent today (`daily_limit`; the agent is paused `daily_limit`).
2. `context` checks the sponsor still reads the scope (else the agent is paused `sponsor_left`) and, for a company agent's project, that the project is still the company's (`project_not_in_company`, every run). It calls only the rule book's `reads`, each through `services/agents/reads.ts`; a key with no function refuses the run `read_unavailable`. Built: `project.summary`, `company.profile`, `team.roster` and the four cycles' records (their activity lines). Not built yet, so a rule book naming them refuses: `cap_table.read`, `data_room.index`, `research.library`, `network.relationships`, `compliance.calendar`, `mercury.balances`, `stripe.revenue`, `github.repos`, `vercel.deployments`. Each read answers `{ untrusted: true, data }`, at most 8 KB, inside `<agent_data trust="data">` with JSON that cannot open or close a tag; the last 20 memory notes are wrapped the same way; the task, its goal and its One Next Thing (the task's `source_ref` when it came from one; the worker computes no other) are the request. Blocks that do not fit the run's 8,000-character prompt are named, never cut in half. The step's answer is a summary: the prompt is never a step output, so the Workflow's stored state never holds it, and `run` builds it again.
3. `run` calls #3727's `agentRun` with `taskId`, the run uid (run key `agent:<uid>`, hold key `agent:<uid>:run`, `executionId` the uid, hold `agent.<role_key>`). `spend_limit`, `ai_paused`, `agent_cap_reached` and `sponsor_lost_access` pause the agent (`spend_limit`, `ai_paused`, `cap`, `sponsor_left`); `gateway_limit` sets the circuit breaker; a 5xx or `step_in_flight` throws so the step retries.
4. `propose`: the run and the task wait (`waiting_decision`, board In review); the sponsor and the managers are told (in-app, `proactive_nudges`).
5. `wait`: `step.waitForEvent('decision', { type: 'decision', timeout: '7 days' })`. `decideRailAs`, the one decide every press uses, sends it through the proposal's `run_key` (never while the engine is off). On timeout the task is `blocked` / `decision_expired`, the run stays `waiting_decision` with that refusal, and the proposal stays decidable: a late decision is applied directly.
6. `after`: accept or edit → the task is done (board Done, `completed`), one `decision` memory note (`Decision: a person accepted the proposal for "<title>" (<option>).`, keyed by the run) and the cycle's activity line naming the agent; discard → attempts + 1 and the task open again, or `blocked` / `needs_person` at the third. Then, unless `AGENT_AUTONOMY` is `manual`, the scope's object is asked to admit the agent's next ready task.

### Idempotency

- A message is `{ job_type: 'agent_run', payload: { run_uid } }`. A redelivery finds the run past `admitted`, or an instance with that id already, and does nothing. The DLQ ends the run `failed` (`queue_exhausted`), opens the task, and mirrors the message into `cf_dlq_mirror`.
- The `run` step is E2's: a retry answers the same proposal (`replayed`) or ends `step_lost` with nothing more charged.
- Every other write is conditional on the state it moves from, or keyed by the run (the note's uid), so a replayed step repeats nothing.
- `queue()` routes a batch whose name contains `agent-queue` first (its `-dlq` to the agent DLQ consumer), then the job queue's `dlq` test, unchanged.

### Kill switch

- `AGENT_ENGINE = "off" | "paused" | "canary" | "on"` (default `off`; anything else reads `off`). `paused` stops admissions only.
- KV `agents:halt` (in `RATE_LIMITS`): every run ends `halted` at its next step; read at every step; a key that cannot be read counts as set.
- KV `agents:paused`: the platform circuit breaker. The `agents` AI Gateway's limit (an attempt answered 429 through the gateway, `gateway_limit`) sets it; the engine reads `paused` until a person clears it, and members see the degraded-mode line, never a silent failure.
- A scope's pause (`agent_scope_settings.engine_paused`, `PUT …/engine`); an agent's pause; the existing AI kill switch and D791 inside `run()`.
- The gateway id is `AGENT_AI_GATEWAY` (unset = none), passed only by `agentRun` (`gatewayId` on the router's options). A gatewayed agent call is never retried without its gateway.

### Pauses

`team_agents.paused_reason` extends #3727's vocabulary (`cap`, `sponsor_left`, `tool_disconnected`, and the routes' `manual`) with `spend_limit`, `ai_paused`, `daily_limit` and `scope_archived`. 712 holds no CHECK, so none needs a migration. `scope_archived` is set when a company agent's run finds its company archived (`context`). Every pause is told once per agent, reason and UTC day (a two-day KV key), in-app under `proactive_nudges`, to the sponsor and the scope's managers (a company's Owner, Admin and Founder links; a project's founder accounts).

### Transfers and erasure

A project that moves company after admission ends its run `scope_moved` at `load`; a company agent's read of a project is re-checked every run. The product amendment: removing an agent (`DELETE /api/teams/agents/:uid`), hard-deleting a project (`hardDeleteProject`, before its rows go) and erasing an account (`eraseAccountRuntime`, every agent the account sponsors) end the runs (their Workflow instances terminated, rows `cancelled` / `erased`) and empty the scope object. With the engine `off`, a deletion reaches the runtime only when D1 shows an open run or an active duty, so a deployment that never turned the engine on behaves as before. No code path hard-deletes a company or an account today (D168: erasure is manual), so `eraseScopeRuntime` and `eraseAccountRuntime` are there for that manual step and for E7.

### Observability

The run row is the record: `status`, `step`, `steps_json` (`[{ name, status, at, summary }]`, summaries short and never a prompt or an output), `refusal` (a code), `usage_log_id`, `proposal_uid` and timestamps. `GET /runs/:uid` reads it; cost is `chargedFor(usage_log_id)`, `{ available: false }` when unrecorded. Logs carry codes only (`[agents] enqueue_failed`, `[agent-queue] start_failed`, ...). The sweep's counts go into the cron run's summary. E7 adds the admin views.
