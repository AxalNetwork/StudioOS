### What is requested

Two Search Analytics queries against `https://searchconsole.googleapis.com/webmasters/v3/sites/{siteUrl}/searchAnalytics/query`, both `type: 'web'` and `dataState: 'final'`:

- **Property totals:** `dimensions: ['date']`, `aggregationType: 'byProperty'`, `rowLimit` 25,000, paged with `startRow` while a page comes back full.
- **Top landing pages:** a separate query per week, `dimensions: ['page']`, `aggregationType: 'byPage'`, `rowLimit` 25.

Before them, `sites.get` checks that the principal still holds a usable permission on the exact property (`siteUnverifiedUser` is denied). The `query` dimension is never requested, so no search query is read or stored; no table has a column that could hold one, and the test checks both.

The property identifier is kept byte for byte (`sc-domain:example.com` or `https://example.com/`) and percent-encoded whole into the path.

### Dates, windows and progress

- **Provider dates are Pacific Time.** "Today" is the Los Angeles date at the run's clock (`Intl`, so DST is Google's own); the request ends yesterday. Stored dates are never converted to UTC. Weeks run Monday to Sunday in provider dates.
- **Initial window:** sixteen whole weeks ending with yesterday's week (`LIMITS.initialWeeks`), stored as `initial_from`.
- **Incremental:** each later run re-reads from `fetched_through − 7 days` (`overlapDays`), so late corrections are seen.
- **Finality:** under `dataState: 'final'` Google returns no row for a date that is not final yet. A chunk's fetched-through date is the later of the latest date Google returned and today − 3 days (`finalLagDays`), capped at the chunk's end. Dates after it are not written and are re-read next time.
- **Atomic progress:** the window is cut into chunks of four whole weeks. A chunk is fetched in full (every totals page and each week's top pages) and then written in one D1 batch: its days, its weeks' pages, its revisions and the advanced `fetched_through`. A failure inside a chunk (an interrupted page included) writes nothing of it and keeps the chunks before it; the run is `partial`.
- **Stable keys:** a day is `(project_id, site_url, search_type, data_date)`; a page week is `(project_id, site_url, search_type, week_start)`.
- **One run at a time:** a run claims `search_console_sync_state.run_token` (taken over after 15 minutes, compared through `datetime()`); a second run while it is held records a `busy` run and calls nothing. Every write is guarded on that claim and on the selection still naming the same property with access, so a property changed mid-run receives nothing.
- **Retry:** 429 and 500/502/503/504 (and a network failure) retry up to four attempts, waiting `Retry-After` when given, else 1 s, 2 s, 4 s, capped at 30 s; a run makes at most 60 requests. 401 is `grant_revoked`, 403/404 `property_denied`, neither retried.

### Missing, failed and zero stay apart

| What happened | What is stored | What the weekly read says |
| --- | --- | --- |
| Google reported the date with 0 | `row_state 'reported'`, `clicks 0`, `impressions 0` | counted, a true zero |
| A final date Google returned no row for (missing or suppressed) | `row_state 'not_returned'`, every figure NULL | `days_not_returned`; adds nothing; never 0 |
| The fetch failed | no row for the date; the run and `sync_state.last_status` carry the error code | the week is incomplete with `Unreadable: the last sync failed (<code>)` |
| Not final yet, or before the window | no row | the week is incomplete with the reason |

A denied property sets the selection's `access_state` to `denied` (a revoked grant to `revoked`), stores nothing and refuses the next sync with 409 until the selection is made again.

### Corrections

Every stored day and page week carries a SHA-256 `fingerprint` of its values and a `source_revision`. A re-read with the same fingerprint writes nothing (a duplicate run is a no-op). A changed one updates the row, increments the revision and adds a `search_console_revisions` row with the previous fingerprint and values.

### Weekly figures

`searchConsoleWeekly(env, user, projectId)` (venture read gate: `canAccessProject` without write; the sync needs write):

- weekly clicks and impressions are the sums over the week's **reported** days only, from `search_console_daily_totals`;
- weekly CTR is total clicks ÷ total impressions; zero impressions gives `ctr: null` with `No impressions: CTR is undefined`, never 0; a week with no reported day has null figures and a `Not recorded` reason;
- each week says `complete` (all seven days fetched as final) or why not;
- each week's top landing pages come with `row_limit`, `rows_returned`, `truncated` (the list filled its limit), `complete`, `top_rows_only: true` and a note that they are never summed into property totals. No code path adds page rows into a total.

The answer also carries the exact property, search type, data state, the provider time zone, the units (`clicks` and `impressions` counts, `ctr` a ratio, `position` an average rank), `initial_from`, `fetched_through` and the last outcome.
