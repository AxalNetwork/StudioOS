## D1542 — Deck v2 B4: Diagrams — the grid_diagram job, structure only, numbers stripped, drawn and fitted in code (#3780)

- **Status:** built by S14, 2026-11-03 (#3780, part of #3716).
- **Spec:** the issue's "Final canvas revision (2026-11-01)", which is S1's comment on #3780. It wins over the original body.
- **Migration:** none. The job runs through #3764's tables (`deck_area_batches`, `deck_area_batch_steps`, `deck_area_proposals`).

### 1. The job runs through Generate into areas

A diagram is one more kind of area in D1512's flow, `diagram`, beside text, chart, image and records (`services/decks/areas.ts` `kindOf`). It gets the same quote, the same one parent hold (`admitDeckRun`), the same 1 to 3 seeded variants, and the same proposals, Accept and Discard. No second generation route was added. The step is a `rail_write` run whose input carries `job: 'grid_diagram'` and the rail option `grid:<element>`. The job itself is `services/decks/gridDiagram.ts`.

- **The model** is the rail's Diagrams group's: `elementModelFor` → `resolveElementModel` (D1503, #3754), with HQ's lock first (D1549). The ids come from `catalogue.ts` through the per-job plan's DK2 row (#3721). Nothing in the job names a model, and the client never sends one.
- **The model writes structure only:** `{ type, nodes: [{ id, label, detail? }], edges: [{ from, to }], axes? }`, from the card's own words. The prompt tells it never to write a number, figure, amount, percentage or date.

### 2. Code does the rest

1. **Strip.** Every token that names a number (`newDeck.numberIn`: digits, currency and percent signs, number words from two up) is dropped from every label, detail and axis, along with the punctuation it leaves behind. "$3M ARR" becomes "ARR". A node left with no words is dropped, together with its edges. A final check refuses any diagram in which `numberIn` still finds something.
2. **Order.** For a flow, the edges give the order when they form one chain; for a cycle, when they form one ring. Otherwise the nodes keep the order the model wrote them in. A matrix is exactly four quadrants with both axes named.
3. **Refuse rather than cut.** More than 8 nodes is refused (`too_many_nodes`). So are too few steps once the numbers are gone, and a matrix that is not four quadrants with two axes.
4. **Render.** The stored diagram (`diagramModel.ts`, D898 §8.4) is laid out in code (`diagramLayout.ts`, D903 §11), the one geometry every export draws from. The type is always the element's, never the model's.
5. **Fit.** `fitProblems` runs over the block on its card, and its existing steps-per-width rule (two columns per step) is unchanged. Each node's words are also measured against the node's own box at the deck's aspect: label 26 then 22 px bold, detail 20 px. Either problem refuses the variant (`does_not_fit`) with the fit's sentence. A broken block never reaches the founder; the founder is charged only for what ran, and the other variants stay acceptable.

### 3. The family of types

| Type | Draws today | Generates |
| --- | --- | --- |
| flow, cycle, matrix | yes | yes: the canvas draws them live |
| timeline | yes | no: the Data group's Timeline is placed from records (`deck:timeline`) |
| funnel, hierarchy, hub and spoke, positioning 2×2 | no layout yet | no: refused `coming_later` before any model is resolved or quoted, and greyed "Coming later" in the picker |

An area too narrow for a type's fewest steps is refused before it is quoted (`area_too_small`): a matrix needs 8 columns, a cycle 6 and a flow 4. The picker's row says the same on the client.

### 4. Proposals, the client and the canvas

- **Proposals.** A variant's payload is `{ kind: 'block', block: { kind: 'graphic', graphic, diagram, grid }, title, stripped }`. `AreaResults.jsx` draws it with `DiagramView`, and "Checked: every number removed" shows under it. Nothing is written to the deck before Accept, and Discard leaves the card as it was. Accept places the block in its area and Save writes the version, as for every element.
- **The picker.** Flow, Cycle and Matrix are keyed to `R('POST /api/decks/:id/areas')` with no rail option: the model is resolved on the server, and the chip reads "Model set in the AIRail". The rest stay on `A('diagrams', 3780)`.
- **The adapter.** `deckV2Adapter.diagrams` now answers through `deckDiagramsApi.check` (`POST /api/decks/:id/diagrams/check`, `routes/deck_diagrams.ts`, contract `deckDiagramCheck.schema.json`). The check is free and read-only. It returns the edited diagram as it would be saved, its fit problems, the numbers the founder's own labels name (shown, never removed, because they are the founder's words), and the steps the area holds.
- **Canvas.** When one diagram block is selected in the editor, `GridStage` puts a field over each of its nodes (`DiagramNodes.jsx`), including a matrix's two axes. Each edit goes through `onCard` as one undo step ("Edit diagram"). An empty label is refused. The check's line shows under the card, and a check that could not be read never says "fits". No new panel or picker was added.

### 5. The one-click path is untouched

`recordDiagrams` (`services/decks/visuals.ts`) and `routes/deck_new.ts` are unchanged and do not import the job. `deck_record_diagrams_pin_d1542.test.ts` pins `recordDiagrams`' whole output for one synthetic venture, the composer's diagram blocks drawn from it (a roadmap's quarters stay in its details), and that none of those files reaches `gridDiagram`.

### 6. Not done here

- Funnel, hierarchy, hub and spoke, and positioning 2×2 have no layout in `diagramLayout.ts` or the export writers yet, so they stay "(later)".
- The data-shape rules for choosing a diagram ("funnel stages → funnel diagram", dk-auto gap c) are not built.
