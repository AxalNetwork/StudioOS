## D4422 — Team models and MCP tools allowed (#4422)

Part of #3727, TM8a. A company can narrow the models and read tools its
agents may use. Company projects inherit this list; a standalone project
keeps its own. This is a restriction, never permission to exceed a sponsor's
plan, tool approval, connection, grant or project access.

### Store and authority

Migration `202611041438_team_allowlists.sql` adds `team_allowlists`, one row
per company or standalone project. Each dimension is independent: SQL NULL
means the existing default, an empty JSON array allows none. No row also means
the existing defaults. Model IDs and `{ integration_uid, tool }` grants are
validated, deduplicated and sorted. No credentials or tool arguments are stored.

`GET/PUT /api/teams/:scope/:id/allowlists` is mounted in `team_agents.ts`,
behind `TEAM_AGENTS_ENABLED`. A reader of the requested scope or its company
may read the effective list. Saving always checks `canManage` on the effective
scope: a project owner alone cannot override its company's policy. The PUT
accepts only currently offered chat models on the editor's plan and connected,
approved read tools belonging to that team's members. Those choices do not
approve anything for another sponsor. Lists and `activity_logs` audit rows
commit in one D1 batch, with actor ID, time, scope and the new lists; an audit
failure rolls back the save. `updated_by` and `updated_at` also mark the policy.

### Enforcement

The existing model offer is shared in `modelOffers.ts`; `team_agents.ts`
re-exports it for existing callers. Add checks the plan/model offer and sponsor's
approved grants, then the inherited lists. A denied model is 403
`model_not_allowed`, a denied tool 403 `tool_not_allowed`.

Quote and run re-read the policy. A removed model or any removed grant refuses
the run in words before tool reads, provider calls or charges. Company denial
is checked before HQ's existing model fallback, and the resulting model is
checked again: fallback cannot evade a company restriction. Plan and platform
gates still apply. No policy cache survives an edit or project move. Missing
policy tables on a pre-migration database retain defaults, matching the existing
platform-policy rollout behavior; a failed read or malformed row fails closed
with `allowlists_unreadable`. A save requires the migrated table and audit store.

Every agent custom-MCP read checks the current stored agent, active sponsor,
manage gate, paid plan, grant and inherited policy before calls, and again
between reads. The transport carries restrictive agent/connection context to
`/mcp`; that server binds it to the authenticated sponsor and re-checks policy
before executing a tool. This context grants no access: ordinary member MCP
calls retain their OAuth/API-key gates; agent calls also pass all those gates.
Malformed context and write tools refuse. Context comes from the engine, never tool arguments.

### Screen and checks

The existing TM8a card uses its established card/checkbox/button styles, through
`agentsAdapter` and `teamAgentsApi`. Models precede servers/tools. Independent
Plan default controls restore null lists; explicit empty lists explain that
nothing is allowed. Company projects name the inherited company, and the
Worker's effective manage gate controls editing. Failed reads say Unreadable;
failed saves retain edits and show the refusal. Previously saved unavailable
choices remain visible and removable.

`team_allowlists_4422.test.ts` uses real SQLite to exercise default/reset and
empty-list behavior, plan bounds, inheritance, permissions, tool approval,
audit atomicity, model/tool revocation and the MCP use-time gate.
`team_allowlists_4422.test.mjs` exercises actual read/save requests, defaults,
read-only inheritance and failed reads/saves. Validation and mutation evidence
are recorded in the PR. No deployment or production data writes are performed
by the task; the owner merges and verifies deployment.
