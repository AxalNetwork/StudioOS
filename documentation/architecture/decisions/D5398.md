## D5398 — CI reliability: one repair for a red main, migration names that cannot collide, stateful alerts (#5398)

- **Status:** slice 1 built (this PR). It changes code, workflows and docs only. No repository setting is changed: the ruleset bypass, the merge-queue build concurrency and runner capacity are the owner's (see "Owner actions").
- **Builds on:** D4106 (migration names), D4107 (the merge queue), D5237 (GitHub health alerts).
- **Why:** on 2026-11-09 and 2026-11-10, main went red several times. These merges each broke main:
  - D5039 and D5052, date-bound tests;
  - D4820, the clock;
  - the `202611092035` migration pair;
  - the `check-sql-prepare` baseline;
  - #4647's fixtures and D3959's clock.

  Every open PR inherited each failure, and slots then ported the same repair, merged main into their branches and re-ran full suites. The Actions queue reached 116 and later about 136 queued runs (#5240, #5251). The session that built this slice did the same at about 10:05Z on 2026-11-10: it ported #5396 into six PRs. That is the behaviour this decision stops.

### 1. The red-main and queue protocol (`AGENTS.md`)

While `[alert] main is red` is open:

- **One repair PR**, named on the alert issue.
- **No ports** of that repair into other branches.
- **No merging main** into open PRs, or rebasing them, only to chase the inherited failure.
- **No re-runs** for an inherited failure.
- **One STATUS line** that names the alert.

When main is green again, PRs revalidate as they merge. There is no bulk "Update branch".

While `[alert] the Actions queue is backed up` is open, the same backpressure applies:

- no branch updates;
- no bulk re-runs;
- at most one failed job re-run, and only for a PR-specific failure;
- no manually dispatched load jobs.

CLAUDE.md points to the section. The alert messages now say the rule instead of "please don't open duplicates".

### 2. The inherited-failure classifier

`scripts/lib/ciClassify.mjs` is the rule. `scripts/ci-classify.mjs` reads the API. The gate job (`test:drift (full suite)`) runs it only after a failure on a pull request. It has read-only permissions and `continue-on-error`, so it can never change the gate's result. It writes one verdict to the job summary:

| Verdict | When |
|---|---|
| `inherited_main_failure` | Every failed part of this run is also failed on main's latest completed CI run. |
| `pr_failure` | At least one failed part passed on main (named). Or no failed part was found. |
| `main_health_unknown` | Main's latest run is missing, cancelled or unreadable. |

It compares CI parts (job names). A part failing on both runs can still hide a PR-only failure inside it, and the summary says so. It never calls anything inherited that it cannot show, and it never turns a failure green. Test-level comparison, from each part's TAP, is a later refinement.

### 3. Migration names that cannot collide

The old rule, `YYYYMMDDHHMM_<slug>.sql`, let two agents writing in the same UTC minute pick the same identity. That happened at 202611072219 and at 202611092035, and each time it was recorded after both files had merged. From **`DISCRIMINATOR_FROM` = 202611110000** (2026-11-11 00:00 UTC), a stamped migration also names its issue: **`YYYYMMDDHHMM_<issue>_<slug>.sql`**.

- A file's identity is `stamp + issue`. Two PRs for two issues never collide; the same minute and the same issue twice still fail, naming both files.
- Ordering is unchanged and deterministic: the numeric stamp first, then the full name. The existing `/^\d+_.*\.sql$/` filters still read the new form. The issue is 1 to 7 digits with no leading zero. The slug starts with a letter, so the issue and the slug cannot be confused.
- **No rename.** Every file stamped before the cut-off keeps its name (D269), and every file on main passes unchanged.
- **The cut-off is in the future on purpose.** Open PRs already carry migrations stamped on 2026-11-10 in the old form. A rule taking effect at once would turn all of them red, which is the storm this decision prevents. The new form is accepted before the cut-off too.
- `scripts/check-sql-migrations.mjs`, `scripts/lib/migrationPlan.mjs` (`migrationIssue`, `migrationIdentity`), CLAUDE.md, AGENTS.md and SCHEMA_DRIFT.md change together.

### 4. Stateful future-clock alert, and queue hysteresis

- **future-clock** is now an `[alert] future-clock tests failing` issue like the others:
  - it opens on the first failing night, with the test names and the run;
  - it says nothing on later failing nights;
  - it closes on the first clean night;
  - a run with no log is unknown and never "recovered".

  Before, it posted to Slack every failing night and kept no state.
- **Queue hysteresis:** the alert opens at its thresholds (40 runs, or 45 minutes). Once open, it clears only when both figures are under half of them (`QUEUE_CLEAR_RATIO`). A queue that hovers at the line no longer opens and closes the alert every hour.
