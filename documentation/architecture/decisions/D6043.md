### 1. What the file is

The module page's own list, as a spreadsheet: the same columns, in the same order, with the page's
search (`q`), filters (`filter`) and sort (`sort`) applied, and every matching row rather than one
page. It works for all six Build modules (Solution design, Prototype / MVP, Product roadmap, Founding
team, Company creation, Operating systems), because they share the one module read.

- **Same read.** The export calls the page's reader with the page's options (its integration parts
  too: Prototype / MVP's Built column is drawn from GitHub and Vercel, so without them the export
  would have a column fewer than the page). It passes no query to the reader, so the reader returns
  every row. The rows are then filtered, sorted and cut by `pageBuildRows`, the in-memory path that
  D4603's SQL pages are held to agree with.
- **Same gate.** `context()` is the page read's gate (`canReadBoard`): no project is 400, a venture the
  viewer may not read is 403, an unknown module is 404.
- **Cell words.** A cell is written as the page writes it (its text, never its link target). An empty
  cell is **Not recorded**. Where the page has its own words for an absence ("Links to nothing",
  "Not expected yet", "Missing"), the file keeps them.
- **No proof files.** Company creation's Proof column is the state the page shows (Stored, Missing,
  Not expected yet, Unreadable). The export never reads R2.
- **Unreadable.** A module whose read fails is a 503 with the module's sentence, never an empty file.
- **Escaping.** `csvCell` from `services/capTableRegister.ts`, the cap table export's escaper (RFC 4180
  quoting, plus a leading `'` on a value that would start a spreadsheet formula), CRLF records, and
  `csvResponse` / `stamp` from `services/csv.ts` for the response and the
  `<slug>-<project>-<date>.csv` name. Nothing was extracted: both are already shared modules.

### 2. The row cap

`EXPORT_ROW_CAP = 5000`. #4603 bounds what a read pulls per page. An export is the one read that
wants every matching row, so it is bounded here instead. Past the cap, the export **refuses** with
413, the matching count and the cap. It never writes a file that silently stops at row 5,000. A
search or a filter narrows the list, and the page shows the Worker's sentence under the button.
5,000 is far past any venture's list today: the largest module list is a roadmap of a few hundred
items. The readers that answer this already read the whole list into memory for any query SQL cannot
page (D4603), so the cap bounds the file, not a new read.

### 3. Founding team and the cap table export

The Founders export is this list (Founder, Role, Equity, Vesting, Agreement), not a link to the cap
table's exports, and it does not replace them:

- `GET /api/captable/register/:projectId/export.csv` (D1020) is the recorded register: holders,
  securities and classes. It writes its own audit row, and it gates holders' email addresses.
- `GET /api/captable/record/:projectId/export.csv` (D1026) is the record and its history.

The founders list holds none of that. It is what the Founding team page shows, to the viewers who
can already read it there, so it widens no access and writes no audit row. The full register stays
one click away through the module's cap table tool link. Pointing Export at the register would hand a
founder a different table from the one they asked to export.

### 4. The control

**Export CSV** sits in the records header, beside Add (desktop), and under the list as a full-width
44px button (phone). It shows from the **few** stage on (D5076). At zero, the one first action stays
the page's only action. It is hidden while the list is unreadable or loading. While the file is being
made the button reads "Exporting…". A refusal (403, 413, 503) is its sentence under the button.
Only Build names an exporter: `exportRecords` in `defs/build.jsx`, which `CycleRoute.jsx` hands the page
with the table's query, adding no import to that frozen hub (D5615). The other cycles' tables are unchanged.
