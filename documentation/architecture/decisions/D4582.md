## D4582 — The sign-in and sign-up routes carry their own head, however the visitor arrives (#4582)

- **Status:** Built for #4582, 2026-11-07. Frontend and the prerender script only.
- **Builds on:**
  - #3705 (route metadata and social cards; its policy is unchanged: signed-in deep links keep the home card, token links keep "Sign in to view");
  - `frontend/src/lib/ogRegistry.js` and `scripts/prerender-og.mjs`.
- **No migration, no Worker change.**

### What was decided

1. **The cause.** A direct load of `/login` is the prerendered HTML, so its head was right. A protected route such as `/grow` is the homepage shell; following its redirect to `/login` is client-side navigation, and neither `LoginPage` nor `RegisterPage` applied a head, so the homepage title, description, canonical and `og:url` stayed. `usePageMeta` also never touched the canonical link.
2. **`applyHeadTags(doc, tags)`** (`lib/seo.js`) writes one route's head, including the canonical link and the robots meta, and returns the function that puts the previous head back. `usePageMeta` uses it, and `LoginPage` and `RegisterPage` call `usePageMeta({ analytics: false })`, so the pageview beacon is not added to those pages.
3. **The indexing policy is explicit.** `/login` and `/register` are listed in `sitemap.xml` and allowed by `robots.txt`, so they are `index, follow`. Every registry entry now states a `robots` value (default `index, follow`), `prerender-og.mjs` writes it into the top-level `<head>`, and `applyHeadTags` writes the same value on a client visit.
4. **Checked on the top-level head only.** The test reads the real prerendered HTML for `/login` and `/register`, compares it with the redirect case on the homepage head, and reads only tags inside `<head>`, never an embedded verification iframe's document. It also checks the policy against the sitemap and robots.txt.
