## D1074 — Trust center part 2: who reads a member's score, whose NDAs a member sees, and which document was accepted

- **Status:** built by S12 for #2966 (part 2 of #2425), 2026-10-25. S1 reviews the scoping before merge.
- **Basis:** owner question 5 on #2425, recommended answer A, and the trust map's findings 5, 6 and 7. The owner has not answered it yet. If the answer is B, this PR's score scoping is reverted and the rest stays.
- **Migration:** 583 (`583_legal_acceptance_version.sql`).
- **Builds on:** D1072 (the public `/trust` and `/trust/me`), D1073 (Start retired), and #2636's first narrowing of the score reads.

### 1. Who reads another member's score (`services/scoreAccess.ts`)

`GET /api/trust/score/:userId` and `POST /api/trust/score/batch` serve a score to three readers:

- **the member**, for their own score;
- **an admin of this territory.** Each branch is its own deployment over its own database (D104), so a territory's members are the users in this database. An admin reads a user id that exists here. An id that does not is refused like any other: a branch's admin never reads HQ's members, nor HQ's a branch's.
- **a counterparty, in an open intro or an open deal** (`counterpartiesOf`):
  - **an open intro** is a `pairwise_ndas` row between the two, `pending` or `active` and not past `valid_until`. A revoked or expired pair is closed.
  - **an open deal** is one that is neither `funded` nor `rejected` and was not passed, on a venture one of the two belongs to. Belonging means being its founder or being linked through `user_company_links`. The other one must be invited to the deal, hold a commitment that is not withdrawn, or be its lead partner.
  - Both directions count: the founder reads their investor's score, and the investor reads the founder's.

Everyone else is 403, whatever their role. That is a change for partners: before, any partner read the founder of any deal. A partner now reads a founder as the deal's lead partner, or through an open intro.

**The batch** uses the same rule for every id, and one id the caller may not read refuses the whole batch. The role gate is gone, so a member's own id, and their deal's counterparties, are theirs to batch. One bounded query decides a whole batch.

**What each reader gets.** The member and the admin get the missing items and the required total. A counterparty gets only the score and its `status`.

**`status: 'not_recorded'`**, with a reason, when the member has no obligation rows. The score is then null, never 100. The batch does not seed missing rows, so this is where it shows. The single read still seeds a member's rows for their role first, as before.

**The public profile** (`PublicProfilePage.jsx`) reads the single score. It draws nothing on a 403 and "Trust score not recorded" on a null score, so it shows only what the Worker serves. No frontend change was needed. The batch client's comment in `api.js` now states the rule.

### 2. Pairwise NDAs (`routes/trust.ts`, finding 5)

`GET /api/trust/pairwise-ndas` lists only the pairs the caller is party to, for every role. An admin no longer gets every pair on the platform here; the platform's pairs are read in Contracts (`/api/admin/contracts/pairwise-ndas`, which D1073 already links). Resend and Void stay admin-only.

**A signer who is neither party**, which is Axal's own countersigner, is listed by name with `email: null`. The two parties' own addresses are still served, because each party already knows the other.

`GET /api/trust/agreements` already read only the caller's own pairs; its comment said otherwise and now does not.

### 3. Which version was accepted (migration 583, finding 7)

**The column.** `legal_acceptances.document_version` is nullable. The table stays append-only, and old rows are never backfilled: a row from before the migration does not say which text was shown.

**The writer.** `recordTermsAcceptance` writes the version from `LEGAL_DOCUMENT_VERSIONS` (`services/trust.ts`). That is each page's own "Last updated" date, as `YYYY-MM-DD`:
- `tos_v1` = `TERMS_UPDATED` in `TermsPage.jsx`;
- `privacy_v1` = `PRIVACY_UPDATED` in `PrivacyPage.jsx`.

The Worker cannot read the pages, so the dates are copied. `trust_score_scope_d1074.test.ts` §5 fails when a page's date and the map disagree: change the page, then the map.

**`GET /api/trust/me`** adds `acceptances`, one entry per document, from the member's latest acceptance of it (`latestAcceptances`). Each entry holds `accepted_at`, `surface`, `document_version` and `current_version`, plus:
- `newer_document`: true when the page has changed since. It is null, with a reason, when the version was not recorded, or when nothing was accepted yet.
- `acceptances` itself is null when the table could not be read, so the page can say Unreadable rather than "nothing accepted".

Drawing `acceptances` on `/trust/me` is the frontend part's.

### 4. The Explorer's row in the obligations matrix

`ROLE_MATRIX` gains `exploring`: the Terms and the Privacy Policy, both required. An Explorer used to fall through to `partner`'s row. That held the same two keys today, but a partner change would have changed what an Explorer owes without anyone deciding it.

### 5. Tests

**`cloudflare-worker/test/trust_score_scope_d1074.test.ts`** has 6 cases, on the baseline's own tables:
1. **The score**, 18 reader and target pairs. They cover:
   - self, the admin and each kind of counterparty, in both directions, and the company link;
   - the stranger, the other partner, a withdrawn commitment, a revoked and an expired intro, another founder, and another deal's investor;
   - a funded, rejected or passed deal;
   - an id not in this database;
   - a branch's own database, where its admin reads its own member and not HQ's.
2. **The batch:** all or nothing, a founder's own counterparties, `not_recorded` with a null score, 50 once rows exist, and one query.
3. **Pairwise NDAs:** an investor's one pair, the countersigner without an address, no other pair's party, the founder's three pairs, and none for the admin or a stranger.
4. **Acceptances:**
   - the writer's versions;
   - `/me`'s entry;
   - an older version reported as a newer document, read from the latest act;
   - a pre-583 row reported as not recorded;
   - nothing accepted;
   - an unreadable table, null.
5. The versions equal the pages' dates.
6. The Explorer's own row.

**The pins that moved:**
- `cloudflare-worker/test/score_access_2439.test.ts`: the partner now reads as the deal's lead partner, a counterparty's answer adds `status`, a founder's own batch is 200, and the access check is one query.
- `cloudflare-worker/test/trust_center_d432.test.ts`: an admin party to no pair lists none, and the route has one SELECT.
- `cloudflare-worker/test/terms_acceptance.test.ts`: the table is built from migrations 245 and 583.

**Mutation check:** 26 mutations, each applied alone, across `scoreAccess.ts`, the score, batch and pairwise routes, the acceptance writer and reader, the version map and the matrix. All 26 are caught.

### 6. UNVERIFIED until the owner's live check

- **Partners:** no partner on production loses a score they rely on. Today a partner sees founders' scores on every deal, and after this only on deals they lead or through an open intro. The Partner's Pipeline badge then draws nothing for the rest, which is the intended change.
- **Branches:** each branch's database holds only its own members, so a branch admin's territory is exactly that database. That is D104's design, not checked here against a live branch.
- **The Terms page date:** the date the clickwrap shows is the document a member read. The interstitial and the signup checkbox both link `/terms` and `/privacy`.
