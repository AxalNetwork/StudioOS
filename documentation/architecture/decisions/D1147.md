## D1147 — Eadwyn explains PMF inputs; it never writes a score

Issue #3033, part 6 of #2433. S18 · Codex. No migration.

### Built

`raise/pmf-explain` is an input-only, metered surface on Fundraising readiness.
`GET|POST /api/cycles/raise/pmf/explain?project=` reads kept wording or previews
an explanation/interview questions. `POST .../keep?project=` saves a reading.
The new router is mounted before the existing Raise router. Its client lives
in `lib/api/pmfExplain.js`, re-exported once by `api.js` (D527).

The service reads D1144's latest signed input payload without collecting facts
or recomputing a score. Explain receives recorded input rows only. Questions
receive the three lowest-confidence applicable inputs, including explicit
missing states; Not expected inputs are excluded. Ties retain model order.
No aggregate score, Verdict, next-step gain, raw interview quote, buyer identity
or browser-supplied input enters the model. Existing AI metering, rail model
selection, Manual switch and output guard apply to both presses.

Output must cite every supplied input exactly once, with no invented key,
duplicates, extra fields, numeric claims or scores. The server supplies labels,
recorded figures, grades and stale flags in citations. A recorded zero remains
zero; missing evidence remains Not recorded. Questions offer Copy or Dismiss.

### Keep is the only reading write

Previews stay in the browser; only normal AI usage/budget bookkeeping is written
by the router. Explain receives an owner/project/input-hash-bound signed receipt
with a fifteen-minute lifetime; questions receive no persistence receipt.
Keep verifies the receipt and current signed snapshot. An atomic latest-hash
condition refuses a snapshot that changes between verification and insertion.
It writes one accepted `research_zone_drafts` row and an actor-attributed,
metadata-only activity line in one batch; retries do not duplicate either.
The row retains the actual router cost receipt, never a guessed free run.
Kept wording has its own domain-separated signature, so a generic draft edit
cannot silently replace cited Eadwyn text. A read failure or altered body says
Unreadable, and retry remains local to this band.

No scorecard, checklist score, source record or next step is written by a run,
Keep, Copy or Dismiss. Only the authenticated venture founder may use the
surface. Admins (including residual founder links), investors, partners, other
founders and support sessions are refused. SQL is bound throughout.

### UI and registry

RD11's violet proposal band and cited rows open in the existing in-page
Lightbox at desktop/phone widths. The band is composed separately below the
readiness part; #3031 owns `PmfPart` and is not edited here. Canvas departures:
figures appear in server-owned citation lines rather than model prose, and
questions use the same dialog with Copy/Dismiss. This keeps invented figures
out of model wording and leaves the pending PMF card integration independent.
Kept text is labelled as a reading of its captured inputs, not current facts.

Both rail presses have inventoried options and matrix entries. Unlike generic
research ZoneDraft bands, these slash-key previews use a dedicated route so
running and dismissing them stores no reading. Inventory guards retain this
explicit exception and the route/rail tests cover it.

`score_rating` (Scores and ratings) is in both never-fill registries. Score and
rating field tokens, readiness score rows and venture scorecards are refused at
the existing proposal/accept/provenance boundaries. The deterministic scorer
and human entry paths are unchanged.

### Verification boundary

Synthetic model/real-SQLite route tests cover citation bounds, missing/zero,
lowest-confidence ordering, access, signatures, expiry, stale inputs, atomic
Keep/retry/rollback, cost and actor attribution, and no score/source writes.
UI tests cover mount, preview, Keep, Dismiss, question controls, errors and rail
headers. New assertions are mutation-checked both ways; results are in the PR.
