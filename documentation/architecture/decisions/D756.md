## D756 — Telegram Business: switched on, and a way into Record a Session

**The request.** At about 14:05Z on 2026-10-18 the owner shared the Connectors card. It reads "Telegram Business — Not available yet — Axal has not switched this on yet. There is nothing for you to set up until it does. Needs Telegram Premium … It cannot make or receive calls." The owner asked: "Build Telegram Business, backend to wire to Record a Session in Validate. Distribute across session s07-s14".

**Sibling plans.** This decision is planned with D754 (WhatsApp Business) and D753 (a page per connector). It stacks on D754's shared consent and audio steps and adds no second ingestion path. D757 (the Validate engine) owns everything after `interview_process` and `structureSession`.

**Source.** All code was read on `origin/main` at `0ce63b34`, and re-checked on `8a863c6d7` when #1895 opened: every cited file is unchanged but `wrangler.toml`, whose `PUBLIC_BASE_URL` line moved (now `:537`). The citations describe `main` before #1895, which changes lines in `telegram.ts`, `routes/channels.ts`, `threads.ts`, `types.ts` and `voiceFailures.ts` (§1.3).

### 0. What main already does (D684)

The whole Telegram Business channel was built and merged under D684 (#1575, #1576, #1578, #1586, #1602, #1625). Production does not use it yet.

- **"Not available yet" is computed. No flag is stored.**
  - `providerAvailable(env, 'telegram')` is true only when all three secrets are set: `TELEGRAM_CHANNEL_BOT_TOKEN`, `TELEGRAM_CHANNEL_BOT_USERNAME` and `TELEGRAM_CHANNEL_WEBHOOK_SECRET` (`cloudflare-worker/src/services/channels/connections.ts:84-108`).
  - The card shows `UNAVAILABLE_WHY` whenever `available !== true` (`frontend/src/pages/account/channelsModel.js:207`, `:233`).
  - On 2026-10-17 production had no Telegram connection, no link code and no link attempt (#1008 item 4).
- **One Axal bot**, kept separate from the news bot `TELEGRAM_BOT_TOKEN` (`services/channels/telegram.ts:1-9`; `D684.md:196`).
- **The webhook secret is checked on every update, before the body is read** (`routes/channels.ts:669-673`; `telegram.ts:61-77`):
  - both sides are hashed and compared in constant time;
  - an unset secret answers 503, and a missing or wrong one answers 401;
  - the body is capped at 256 KB, counted as it streams (`services/channels/types.ts:36`; `events.ts:116-137`).
- **Updates are idempotent on `update_id`:**
  - the claim is `INSERT OR IGNORE` (`events.ts:33-40`);
  - a redelivery answers 200 and does nothing (`channels.ts:579-580`);
  - a failure before anything is stored releases the claim and answers 500 (`:653-666`);
  - a second key guards messages: UNIQUE `<chat>:<message_id>` (`telegram.ts:30-34`).
- **Linking takes two sides within ten minutes** (`telegram.ts:310-408`; `channels.ts:234-258`). Attempts are counted in D1 and fail closed.
- **The Business connection** is upserted with `is_enabled`, `can_reply` (read from `rights`, Bot API 9.0) and `rights_json` (`telegram.ts:149-167`, `:262-274`).
  - The member is found only from `business_connection_id`.
  - A disabled connection resolves to nobody (`connections.ts:62-69`).
- **Chat scoping:**
  - Telegram delivers only the chats the member chose.
  - Axal keeps every chat pending until the member assigns it. An ignored chat stays a tombstone.
  - Only private chats are read (`threads.ts:1-17`; `telegram.ts:192`).
- **Replies** go out only with the reply right, inside 24 hours, and once per `client_key` (`channels.ts:387-478`).
- **Voice notes (only `message.voice`):**
  - each waits as an encrypted placeholder;
  - once its chat is in an interview it is fetched with `getFile`, transcribed by a direct `aiRun`, and appended as text to the chat's text session;
  - **the audio is thrown away and nobody's consent is asked** (`channels.ts:45-51`, `:738-805`; `threads.ts:383-419`, `:619`).
- **Not read at all:** `audio`, `video_note` and documents (`telegram.ts:209-211`).

### 1. Decisions

#### 1.1 Switching on is owner work, in a set order

- **No code path is switched off.** The owner creates the bot, sets the three secrets and registers the webhook once through the existing Super Admin route. That route sends the secret and the update list, and the result is `https://axal.vc/api/channels/telegram/webhook` (`channels.ts:816-825`; `PUBLIC_BASE_URL` at `wrangler.toml:537`).
- **Order** (settled by S1 on #1895, 2026-10-18):
  1. D754 W2's consent store and gate merge first (#1893). It keeps `consentRequired('telegram') = false`.
  2. D756 S12-consent merges next. It adds Telegram's sender and turns that switch on, so no Telegram audio is fetched without the interviewee's consent.
  3. Only then does the owner switch Telegram on.

  Switching on earlier would transcribe assigned chats' voice notes without the interviewee's consent, which is D684's behaviour.
- **Nothing breaks while D756's own consent step is unmerged:**
  - Telegram is dark on production, so no member loses anything;
  - text chats flow;
  - voice notes wait, undownloaded, as placeholders.
- **There is no var-based kill switch.** Removing a secret turns the channel off, and connected members then read "Axal has switched this off for now" (`channelsModel.js:222`). If D754 W1 adds `WHATSAPP_CHANNEL`, S01 adds `TELEGRAM_CHANNEL` in the same edit, or neither is added.

#### 1.3 Bot API drift fixed before switch-on (S10)

Checked against Bot API 10.3:

- **The reply window.** Telegram's own rule is "incoming messages in the last 24 hours". The window is now counted from `last_inbound_at` for both providers, in `windowRefusal` (`channels.ts:381-385`) and in the thread view (`threads.ts:674-684`). Today it counts from either side's last message.
- **Event keys.** Each update is claimed on `update_id` plus a short hash of its connection, chat and message ids (`telegram.ts:122`). After a quiet week Telegram restarts ids at random, and claims are kept 90 days (`threads.ts:782`).
- **The "manage this chat" button.** It sends `/start bizChat<id>`. That now gets "To manage this chat, open Axal › Interviews." instead of "That link has expired" (`telegram.ts:133`, `:422`).
- **Rate limits.** `retry_after` on a 429 is kept for the retry (`telegram.ts:435-436`).
- **Disabled connections.** The voice job and the consent notice refuse when the member's business connection is disabled. Today the job checks only the integration row (`channels.ts:769-771`).

#### 1.4 Voice notes, audio files and round videos (S13)

- **What is carried with each note:**

  - `file_size`;

#### 1.5 Consent from the interviewee, in the chat, before anything is fetched (S12, on D754 W2)

**Storage.** Consent is stored in D754 W2's provider-neutral `channel_consents` record:

- method `chat_reply`;
- provider `telegram`;
- the notice version;
- the hashed reference of the notice and of the answer;
- the times it was asked, answered and withdrawn.

It is kept with the thread and its interview. When it is given, it is copied to the session: `consent_status = 'given'`, `consent_method = 'chat_reply'`, `consent_at`. That makes the recorder's own gate pass (`interviewProcessing.ts:321-325`).

**Until the interviewee says YES, no voice, audio or video file of that chat is downloaded or transcribed.** This applies to either side's notes.

**Asking.** There are two ways, and both record the request the same way:

- **(a) Ask for consent in Telegram.** The member presses it, and Axal sends the notice through W2's `POST /api/channels/threads/:uid/consent-request` (Telegram half: `sendMessage` with `business_connection_id`).
  - It goes through the outbound ledger, with `client_key = consent:<thread uid>:<version>`.
  - It needs the reply right, and the contact must have written within the last 24 hours.
  - It is refused on an ignored chat.
- **(b) Copy the notice.** The member pastes it into the chat themselves. This works with no reply right and outside the window.
  - Telegram delivers the owner's own messages too, as side `me` (`telegram.ts:199-200`).
  - A `me` message carrying the notice link with its version records the request, with that message as the notice.

**Answering.** The answer is read in `processEvent`, before `storeInbound` (`channels.ts:644`). It counts only when all of these hold:

- `side === 'contact'` **and** `from.id` is the chat's own user;
- it is not `sender_business_bot` and not `is_from_offline`;
- the text is exactly YES or NO (any case, trimmed, with one trailing `.` or `!`);
- it is a reply to the notice, or the contact's first message after the notice;
- it arrives within 7 days of the notice.

Edits never count. The message is still stored as ordinary chat text.

**What each answer does:**

- **YES**
  - queues the chat's waiting notes, including those already sent and still held (30 days at most); the notice says so;
  - covers later notes;
  - before assignment, it waits on the thread and is copied at assignment.
- **NO** keeps the notes undownloaded until the 30-day purge.
- **STOP**, at any time after a YES, stops all further downloads. Audio already stored stays until the member deletes it. That is the recorder's remedy: after recording, deletion is the answer (`founder_validate_sessions.ts:419-439`). The thread tells the member so.

**Member attestation is not offered for Telegram.** The copy path means an in-chat answer is always possible.

#### 1.7 What the bot says

All of it is in `TELEGRAM_COPY` (`telegram.ts:411-427`). The words are approved by the owner and counsel with the S11 notice page.

- **Notice v1.** It is sent on behalf of the business account, so it reads in the founder's voice:

  > "Hi {first name}. I'd like to record this chat for my customer research at {venture}. Your messages here, and the voice notes, audio files and round videos you have sent or send here, will be saved and transcribed in Axal VC, the platform I use, and kept until I delete them. How it works: https://axal.vc/privacy/interviews?n=1 — Reply YES to agree or NO to decline. You can reply STOP at any time."

  The fallbacks are "there" and "my venture".
- **The only automatic messages,** at most one per answer. Each is sent only with the reply right; the answer has just reopened the window.

  | Answer | The bot replies |
  | --- | --- |
  | YES | "Thank you. This chat is now recorded for {venture}'s research. Reply STOP at any time." |
  | NO | "Understood. Nothing from this chat will be recorded." |
  | STOP | "Understood. Recording has stopped for this chat. To have what was already recorded deleted, just ask me." |

  An unclear reply gets no answer.
- **In the member's private chat:** the existing link texts, plus the `bizChat` line in §1.3.

#### 1.8 Retention and deletion, as the recorder's

- **Stored audio** stays until the member deletes the session or the interview. `deleteSession` removes:
  - the R2 chunks under the prefix;
  - the segments, receipts, chunks and staged transcripts;
  - the pending proposals.

  It then writes one audit line (`interviewSessions.ts:239-275`), and `deleteInterview` calls it for each session (`interviewWriters.ts:52-77`).
- **No timer deletes recorded audio**, as with the recorder.
- **Other channel rows:**
  - pending chats and their placeholders are purged at 30 days;
  - event ids at 90 days;
  - counters at 2 days (`threads.ts:776-804`).
- **Consent rows:** on a pending chat, the row goes with the chat; on an assigned chat, it stays with the interview.
- **Changes at the source:**
  - a note deleted in Telegram **before** download is never fetched;
  - one deleted **after** import stays, because the transcript is the member's record (`threads.ts:27-28`);
  - Disconnect forgets pending chats and keeps what is in interviews (`channels.ts:275-305`).
- **A known gap that D756 widens:** no data-subject or account-deletion path removes `validate-audio/` objects. `services/dsrRequests.ts` does not mention them. It is filed separately and not fixed silently.

#### 1.9 Security

- The secret is checked on every update before the body is read, and fails closed.
- Event claims are composite (§1.3), backed by message-level UNIQUE.
- Tenancy comes only from `business_connection_id`, and a disabled connection resolves to nobody.
- Nothing reaches an interview before the member assigns the chat.
- Consent counts only from the chat's own user (§1.5).
- **The bot token and file URLs:**
  - the token is used only inside the Worker;
  - a file URL holds the token, so it is never logged, stored or returned;
  - downloaded bytes go straight to R2 under the audio prefix.
- **Rights.** Only `can_reply` is used. `can_delete_all_messages` and every profile, gift, Star and story right are never called.
- The admin read returns codes only.
- **Tests run on fixtures. No CI job calls Telegram.**

#### 1.10 Limits

- **Telegram Premium on the member's account.** The card keeps "Needs Telegram Premium" until the owner checks it on a non-Premium account; sources conflict on whether that changed in 2026.
- Private one-to-one chats only.
- No calls: the Bot API has none (`telegram.ts:28`).
- **Files:**
  - 5 MB per note, about 20 minutes of a voice note;
  - only the admitted formats;
  - no round videos yet;
  - no captions.
- 50 transcriptions per connection per day, within the member's AI budget.
- The notice from Axal needs the reply right and a contact message in the last 24 hours. Otherwise the member copies it.
