### 1. A3: "results reused from vK"

The owner's answer: a recovery onto an old version's evidence keeps that version's results (A1's behaviour, unchanged), the approval is still spent (§10.1), and the reviewer is told the results are reused.

**The field.** The release decision (`freshness`, §4) gains `evaluation.reused`:

```
evaluation: { pass, total, not_evaluated, meets_bar, pass_bar,
              reused: { version, results } | null }
```

- `version`: the latest published version whose manifest counted any of the results this decision counts.
- `results`: how many of the counted cells that version's manifest named. It is out of `evaluation.total`.
- `null`: no counted result was counted by any version. That covers fresh runs, a draft with no results, and every skill whose versions predate D4533 (no manifest names anything).

**How it is read (`reusedFrom`, `services/agents/skillLifecycle.ts`).** The decision already holds each counted cell's `result_id` (the latest result per case and model under the current evidence). One bound query reads the versions on this skill whose manifest `evidence_hash` is the current one, newest first. The first version whose manifest `results[].result_id` names any counted id answers. A result row is immutable and bound to one evidence hash (§3), so the same id is the same run, and a manifest on other evidence can never name it. The evidence filter only narrows the read.

**Where it shows.** It is one decision, so every place that answers `freshness` carries it with no further change:

- GET `/api/admin/ai-agents/skills/:uid`;
- the restore reply (`POST /:uid/restore`);
- each publish refusal, and the publish success reply. The success reply's decision is the one publish was let through on, before the new version existed.

**What it changes.** Nothing in the gate. `reused` is not a blocking reason, and `publishRefusalOf` does not read it. A restored draft still needs a new approval (§10.1), every required cell evaluated, and 9 of 10. A new run on a model supersedes those cells, so `results` falls and then reads null once every counted cell has been run again (tested).

**It is not only for a restore.** An unchanged draft after a publish also stands on the results the version was released on, and reads `{ version: N, results: total }`. That is the same fact, and the reviewer of a second press is told the same thing.

**The HQ UI.** `SkillLifecycle.jsx`'s Publish card (the card §12.3 added) draws the line under the publish state, in `skillLifecycleModel.js`'s words (`reusedLine`):

> Results reused from v1: 4 of 4 required runs were recorded for v1's release and were not run again.

No decision read, or nothing reused, draws no line. `ReleaseEvidence.jsx` (#4537's release-evidence card, where the reviewer reads `freshness`) is not changed here: it is #4537's file, which another slot is working on. That card can read `freshness.evaluation.reused` as is.

### 2. B1, the company side: a note on Team › Skills

§12 built the column and the route for HQ and company versions, and the HQ UI only. Two gaps on the company page:

- **The note could not be written.** The New skill sheet (`SkillSheets.jsx`) published with an empty body. It now has an optional **Release note** field, sent with **Publish** as `release_note` through `agentsAdapter.publishSkill(uid, { releaseNote })`. The note is trimmed, with `\r\n` turned into `\n`. A blank note is no note, so nothing is sent. Over 2000 characters (`RELEASE_NOTE_MAX`, the Worker's limit) is told in the sheet before anything is written, so a refused note leaves no draft behind. **Save draft** never sends a note, because a note belongs to a version. A Worker refusal (`release_note_too_long`, `release_note_invalid`) reads in the sheet's own words (`skillRefusalWords`).
- **A written note was never shown.** `fromWorkerSkillPage` read `versions[].note`, which the Worker never sends. It sends `release_note` (§12.3). So every company version's note read "—". It now reads `release_note`, and a version without a note reads "Not recorded" (`Unrecorded`), as on HQ.

The company page has no other publish control. A company draft that was saved first is published elsewhere: an editor publishes it with `POST /api/teams/skills/:uid/publish`, which takes a note. A **Publish** action on the skill page is not drawn on main, and this slice does not add one.
