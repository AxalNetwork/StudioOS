## D4531 — A golden case's missing-data check is per field, and a case may assert numbers (#4531, slice 1)

- **Status:** built by S13, 2026-11-07. First delivery slice of #4531 (Session 03 of #4528). No migration. The wider evaluator work (structure, evidence, refusal, model-judged rubric) stays open on the issue.

### The defect

`judge()` passed `must_say_not_recorded: ["runway"]` when "runway" appeared anywhere and "not recorded" appeared anywhere. On the committed `board-meeting-brief` case, "There are 37 paying customers. Delaware franchise tax is on the agenda. Runway is 12 months. Churn is Not recorded." passed. This is an evaluator reproduction, not an observed model response. A correct `DPI: 0.20x; RVPI: 0.90x; TVPI: 1.10x` also failed a case written as the phrase `DPI 0.20x`, because phrases are substrings.

### The rule (judge version 2, `services/agents/skillAssertions.ts`)

1. **Statements.** The output is cut into lines, and lines into sentences or clauses ended by `.`, `!`, `?` or `;` and a space. A decimal point never ends a statement. A sentence, a list item, a `Field: value` line and a table row are each one statement. A field on one line and its value on the next is not supported.
2. **Missing data.** Each `must_say_not_recorded` field must be named, as a whole word, in a statement that also says "Not recorded". It fails when no statement does, or when another statement gives the field a figure without "Not recorded" (it is called missing and given a value). A figure inside the not-recorded statement ("Runway is not recorded, since burn for 2026 is missing") is allowed.
3. **Numbers.** A case may give `numbers: [{ metric, value, unit, tolerance }]`; `unit` is required (`""` for none). A statement supports it when the label is followed by the number, optionally after `:`, `=`, `is`, `of`, `at`, `was` or a table cell boundary, with the unit against the number or after one space. It fails on a missing metric, a value outside the tolerance, another unit, or a second statement giving the metric another value. A conditional statement (`if`, `would`, `could`, `assume`, `suppose`, `hypothetical`) neither supports nor contradicts.
4. **One judge.** The draft evaluation (`POST /:uid/evals`) and the published one (`POST /evals/published`, campaigns) both go through `runCase()` → `judge()`.

### What does not change

- `pass | fail | not_run`, the draft-hash and version binding, the two evaluation histories, the second-admin approval and the 9-of-10 publish bar.
- A v1 case without `numbers` is stored exactly as before. Its `must_include` and `must_not_include` are still substrings.
- Existing results are not re-judged. A result recorded under version 1 stays as recorded; the next run of a case is judged under version 2. `JUDGE_VERSION` is exported for a later change that records it with each result.

### CI

`scripts/check-skill-library.mjs` (#4532, D4532) counts `numbers` among the `expect` keys the judge evaluates, so a library case that asserts numbers is not warned that it proves nothing. Its numbers are validated by `checkCase` like every other field.

## Slice 2 — structure, evidence, refusal, claims and typed output (judge version 3)

- **Status:** built by S25, 2026-11-08. Second slice of #4531. No migration. `JUDGE_VERSION` is 3.

Five more optional keys of a case's `expect`, each with a schema (its TypeScript type and the shape below), a checker that `checkCase` runs, a deterministic evaluator that `judge()` runs, and a failure message naming the exact expectation. They are judged after the phrase lists and numbers, in `ASSERTION_KEYS` order (`numbers`, `output_schema`, `structure`, `evidence`, `refusal`, `claims`); the first miss is the result's detail. Every checker refuses a key it does not define. No miss quotes the output, since a result's detail is stored and outputs are not.

### Accepted forms

1. **Structure** — `structure: { sections: [..up to 12], ordered?: true, form?: "list" | "table" }`. A heading is a whole line outside a ``` fence: `#` to `###### Summary` (closing `#`s allowed), `**Summary**`, `**Summary:**`, `**Summary**:`, `__Summary__`, or `Summary:` alone; optionally numbered (`1. `, `2) `). Its text must equal the section, ignoring case and spacing. A section fails when it is absent or empty (nothing but a rule or a fence before the next heading); `ordered` fails when a section's first heading comes before the one listed ahead of it. `form: "list"` needs a line starting `- `, `* `, `+ `, `• `, `1. ` or `1) `; `form: "table"` needs a `| … |` row, a `| --- | --- |` row and one more `| … |` row. **The output kind** (`draft`, `record_change`, `brief`) has no textual form a judge could check without a model; it stays validated against the skill, and a typed output is asserted with `output_schema`.
2. **Evidence** — `evidence: { cite: [1..20 paths] }`. A path is a read key, then keys and array indexes joined by dots (`grow.records.kpis.0.value`), matched ignoring case. A citation is `[path]`, `[path, path]`, `[source: path]`, `[sources: path, path]` or `(source: path)`. Brackets around anything else (`[1]`, `[TBD]`) and markdown links are not citations; with `source:`, every item is one. It fails when any citation, anywhere, names a path the case's records do not hold, or when a `cite` path is not cited (itself or a path inside it) outside a conditional statement. `checkCase` refuses a `cite` path the case's own records do not hold. `judge(expect, output, input)` takes the case's input for this; `runCase` passes it on both paths.
3. **Refusal** — `refusal: { mode, subject }`. `ask_for_input`: one non-hypothetical statement names the subject and one of `ASK_MARKS` ("please provide", "could you share", "is required", …). `decline`: the subject and one of `DECLINE_MARKS` ("cannot conclude", "cannot be determined", "not enough evidence", …; "can't" and "can not" read as "cannot"). `not_recorded`: the missing-data rule of slice 1. `none`: no statement names the subject with an ask, a decline or "Not recorded". Asking or declining and, in another statement, giving the subject a figure fails. A statement with `if`, `suppose`, `assume`, `assuming` or `hypothetical` never counts. **`refuse_when` is removed from the docs, not implemented**: its condition was on the case's own fixed records, so within a case it was a constant, and an assertion keyed on it would prove nothing `refusal` does not. The one fixture that carries it (`customer-interview-summary.json`) is left as it is; `checkCase` drops the key and CI still warns on it.
4. **Claims** — `claims: { required: [{ subject, object }], forbidden: [...] }`, up to 20 each, at least one. A statement states a claim when it is not conditional (slice 1's list) and names the subject, then the object, as whole words. A negation (not, no, never, none, nor, neither, without, cannot, a word ending in n't) anywhere before the object negates it. A required claim fails when no statement affirms it, or any statement negates it; a forbidden claim fails when any statement affirms it, reported speech included. The object before the subject, or the two in different statements, do not state it. A claim may not be both required and forbidden.
5. **Typed output** — `output_schema: { format: "json", schema }`, for a case whose output contract is a typed artifact; nothing is required of a case that does not declare it. The value is the whole output when it starts with `{` or `[` (nothing may follow), else the content of its one ``` or ```json fence. The schema is a closed subset of JSON Schema: `type` (object, array, string, number, integer, boolean, null), `enum` (scalars, up to 20), `required` and `properties` and `additionalProperties: false` (objects; a required name must be a property when properties are given), `items` and `minItems` (arrays); at most 100 nodes, 6 deep. A miss names the JSON path (`At $.changes[0].to: expected number, got string.`).

### What does not change

- A case without the new keys is stored and judged exactly as under version 2. The test rebuilds the slice-1 judge from its unchanged exported rules and compares every committed library case on a battery of outputs; none differs. Library case identities (D4532) are unchanged.
- `pass | fail | not_run`, the draft hash and the version binding, the two histories, the regression alert and its dedupe, the second-admin approval and the 9-of-10 bar. An assertion miss is a `fail` like any other; `judge()` checks each assertion's shape again, so one written to the store without `checkCase` fails the case instead of passing it.
- The evaluation prompt (`runCase`) is unchanged. A skill whose case asserts citations, headings or JSON must say that form in its own steps.

### For other work

- `ASSERTION_KEYS` and `JUDGE_VERSION` are exported from `skillAssertions.ts`, for #4533's release-evidence manifest. `draftHash()` and `publishRefusal()` are untouched.
- `skillCatalogue.ts` counts the new keys as evaluated, so `scripts/check-skill-library.mjs` accepts them and reports a malformed one as `case_invalid`.
- The HQ case editor keeps every assertion key as it was on save, in the Worker's order, so an unchanged case keeps its uid. It does not edit them.
