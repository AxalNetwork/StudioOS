## D1098 — Vercel part 3: deployments, the Live strip, Preview chips, the Deploys strip and the SHA marks

- **Status:** built by S12 for #2963 (part 3 of #2408), 2026-10-27. Not deployed or live-verified; §6 lists what stays UNVERIFIED.
- **Builds on:** D1096 (part 1, #2961: the connection, Choose projects, `vercel_projects`), D1097 (part 2, #2962), D782 and G1 (#2414: GitHub's `merge_commit_sha` and `commit_sha`), D1311 (#3431: the owner's canvas, VC2, VC3, VC5, VC7, and `buildParts.jsx`).
- **Migration:** 591 (`vercel_deployments`).

### 1. What is kept

`vercel_deployments`, one row per deployment of a chosen project, UNIQUE (`integration_id`, `deployment_id`), indexed on (`project_id`, `target`, `created_at`):

- the id, target (`production` or `preview`), state, created and ready times, build seconds (ready minus building);
- the commit SHA, only when it is a full 40-character one, lowercased; the branch, the pull request number and the repository (`owner/repo`), from the deployment's `meta`, falling back to the project's linked repository;
- its source, error code, a rollback flag, a promotion time and, for a preview only, its address.

**Never** its creator, its commit message, its author or a log line (a test passes them in and finds none).

### 2. The sync, the ledger and retention

- **The sync** (`syncVercel`) reads each chosen project's deployments after its facts: two pages of 100 (`DEPLOYMENT_PAGES`), newest first, following Vercel's `until`. A 429 is "Partly synced" as in part 1.
- **The deployment.\* webhook deliveries** are part 1's nudges: they re-run the same sync, and nothing is taken from the body.
- **The ledger.** Each row is a `connector_fed_items` row `deploy:<id>`, kind `deployment`, local table `vercel_deployments`. A production deploy's module is Product roadmap; a preview's is Prototype / MVP. `vercelFeeds.ts` sets both landings' store, so the connector page claims both modules and Now fed by counts them from the ledger.
- **Retention:** 180 days, or the newest 500 per venture, whichever keeps fewer (`retainDeployments`, after every sync, partial ones included).
- **A deleted row stays deleted.** A row the retention removed, or one removed by any other means, keeps its ledger row without a local row. The sync checks that before writing and never brings it back.
- **Unchoosing is not deleting.** A project no longer chosen, or a venture the connection no longer feeds, takes its deployments **and their ledger rows** with it (`pruneDeployments`, skipped on a partial sync). Choosing it again brings them back.
- **Disconnecting** deletes them (`clearVercelRows`); they also cascade with the connection.

### 3. Evidence only

- **A Preview chip** is matched to a must-have GitHub feeds by its pull request's repository **and** number, read from the must-have's ledger key `pull:<repo>#<n>`, case aside. Never by a branch name, never by a time. The newest preview of that pull request is the chip.
- **"In production since"** is drawn only when a READY production deployment's `commit_sha` equals the must-have's `merge_commit_sha`. It is the first such deploy's ready time. A failed deploy or a preview of the same SHA marks nothing. Without GitHub's SHA the part says "Needs the GitHub connection's commit links"; with it and no match, "No production deploy carries this pull request's merge commit yet."
- **"Live on"** follows the same rule against the release's `commit_sha`. A release reads `live`, `no_match` or `needs_github`.
- **Vercel writes nothing there.** No sync writes `mvp_features`, `roadmap_okrs`, `roadmap_releases` or `mvp_release_checks`. A test diffs all four around a sync.

### 4. The reads: `parts.vercel`

`services/vercel/buildReads.ts`, called by `routes/cycle_build.ts` beside `parts.github`, each in its own try (`fromVercel`). A failed read is `{ state: 'unreadable' }`, logs the module name only, and leaves the module readable.

- **Prototype / MVP** (`mvpVercel`):
  - `live`: per chosen project, its state and label, since when, and its newest production deploy's short commit, build seconds and (when failed) error code;
  - `must_haves`: per GitHub-fed must-have, its title, GitHub's `pr_state`, the preview (state, time, address) or its reason, and `in_production_since` or its reason.
- **Product roadmap** (`roadmapVercel`):
  - `weeks`: 12 Monday-to-Sunday (UTC) counts of production deploys. A week before the first deploy the connection read is `null`, never 0. A later week with none is a measured 0;
  - `failed_share`: the percentage of finished production deploys that failed, or `null` with "No production deploy finished in these 12 weeks.";
  - `median_build_seconds`: over READY production builds, or `null` with "Not recorded: no build finished in the last 12 weeks.";
  - `events`: each rollback and promotion;
  - `releases`: the same releases, in the same order and number as GitHub's strip (`RELEASES_SHOWN`), each with its tag, state and `live_on`.
- **Both** carry `connection`: `as_of` (the oldest last sync among the connections) and `reconnect` (when a connection's status is `error`: since when, and the project's name for members).
- **Empty:** "Vercel has not brought anything to this venture yet. Choose projects on Vercel's connector page."

**Who sees what (the Tools rule).** The venture's owner and its company's members see project names, domains and preview addresses. Anyone else who reads the board sees states, counts and dates, never a name, a domain or a link.

### 5. The page

- **`MvpFromVercel.jsx`** (VC2): the Live strip ("Live at [domain]", "Ready since 3 Oct, 14:20", "Failing since …", "Not deployed", "Last production deploy · commit … · build …"). Then each must-have with GitHub's state, a Preview pill (Ready, Building, Failed, Canceled; a link for members) or "Not recorded: no preview deploy for this pull request yet.", and "In production since …".
- **`RoadmapFromVercel.jsx`** (VC3): "Deploys to production, last 12 weeks" as 12 bars. A measured quiet week is a flat line; a week not measured is a dashed line. The strip scrolls inside its card on a phone (VC7). Under it: "Failed 6% · median build 2m 30s · 1 rollback", "↺ Rollback on 12 Oct.", "The week of 25 Aug had no deploys.". Then Releases, each "Live on 3 Oct" or a dashed "No matching deploy" (or "Needs GitHub's commit links").
- **`VercelPartFrame.jsx`** draws `#from-vercel` and VC5's states:
  - Empty with Choose projects;
  - Unreadable, "Vercel could not be read. The rest of this page is current." with Try again;
  - Reconnect, "Vercel's sign-in for [acme-web] expired on 20 Oct. Figures are as of 20 Oct." with Reconnect Vercel, the figures still drawn under it.

  Each link goes to `/account/connectors/vercel`. Nothing here changes data, so nothing opens a dialog.
- **`vercelDeploys.js`** holds the words, pure.
- **Mounting.** The parts mount by replacing their `null` lines in `buildParts.jsx` (D1311, #3431): `['vercel', (data, ctx) => <MvpFromVercel vercel={data?.parts?.vercel} reload={ctx.reload} />]` on Prototype / MVP, and the same with `RoadmapFromVercel` above GitHub's on Product roadmap. #3431 was not merged when this was built. Until it is, the parts are built and tested, but not drawn.

**Two words differ from the canvas, on purpose:**
- VC2's "no preview deploy for this branch yet" reads "for this pull request": the match is by pull request, never by branch.
- VC5's Unreadable button reads "Try again" (the shared `Unreadable` and the honesty rule): it re-reads the page. A sync is on the connector page.

### 7. The one Live line (D1083, D1311)

When a Lovable app address equals a Vercel production domain, the Live line is Vercel's, and From Lovable reads "Hosted on Vercel". The rule is D1083's `liveHost.ts` (#2948, merged first).

- **What part 3 adds:** `lovableAppLinks.ts`' `vercelProductionDomains()` now returns each chosen Vercel project's production domain from `vercel_projects`. A store that cannot be read gives none, so every line stays Lovable's.
- **The shared test** (`vercel_deploys.test.ts`, this PR landing second) reads Prototype / MVP and checks:
  - an exact host match is drawn once, by Vercel;
  - `www.` of the host, and a Lovable address, stay Lovable's;
  - an unchosen project's domain claims nothing.
