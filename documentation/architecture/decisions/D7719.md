## D7719 — Research studies: the market, segments and decision a Research Project serves, and Markets creating the project and study together (#7719)

- **Status:** built 2026-11-19 from the owner's Research → Markets audit of the same date (sections 3 and 4), under #3701. Owner question answered **A** (built as A): a study links to at most one venture, optional to start.
- **Builds on:** D5157 (`research_projects`, `checkProjectOwner`, `readField`, `defaultTitle`), D7177 (the all-or-nothing `/with-comparison` save with a request id and `readRequestId`), D7171 (the Markets filters `FRESH_BANDS` and `SOURCE_KINDS`), D533 (the market directory and `research_market_sectors`, read through `services/researchTaxonomy.ts`).
- **Files:** migration `cloudflare-worker/sql/migrations/202611191832_7719_research_studies.sql`, route `cloudflare-worker/src/routes/research_studies.ts` (self-mounting at `/api/research/projects`), client `frontend/src/lib/api/researchStudies.js`, test `cloudflare-worker/test/research_studies_7719.test.ts`. The sibling project route files are not edited; their exports are imported.

### Store

- `research_studies`, one per project (`project_id` is the key, CASCADE with the project): product, product boundary, business model, the decision, horizon months (1 to 120), the origin (market slug and name, tracked sector, the Markets filters as JSON), an optional venture (`projects.id`, `ON DELETE SET NULL`), `request_id` (partial unique index on `(owner_user_id, request_id)`), `version`, `created_by` and timestamps. `owner_user_id` is stored as well, so the request-id index is per member as D7177's is.
- `research_study_segments`, children of the study (`project_id` references `research_studies(project_id)`, CASCADE): uid, name, buyer, end user (`end_user`), budget holder, purchasing unit, statistical unit, industry scheme, industry codes (JSON array), size band, customer countries (JSON array of two-letter codes), exclusions, beachhead flag, optional Validate segment (`customer_segments.id`, `ON DELETE SET NULL`), sample note, sample limits, position, `version`, `archived_at`. A partial unique index holds one beachhead among a study's live segments.
- Every text column is bounded by a CHECK; NULL means not written, never `''`. The origin slug and name are set together or not at all. Statistical unit and industry scheme have a length CHECK only: their allowed values are exported lists the Worker checks, so a list can grow without a table rebuild (the rule #7716 states for the observation store).

### Routes

| Method and path (under `/api/research/projects`) | What it does |
|---|---|
| `GET /:uid/study` | `{ study, venture, segments, archived_segments }`; `study: null` (and empty lists) for a project with none, never an empty study |
| `PUT /:uid/study` | Create (version 0) or replace the study with the version read; a stale version is 409 `study_changed` and writes nothing |
| `POST /:uid/study/segments` | Add a segment (409 `study_required` before the study exists) |
| `GET /:uid/study/segments/:segmentUid` | One segment, archived ones included |
| `PUT /:uid/study/segments/:segmentUid` | Replace a live segment with its version; stale is 409 `segment_changed` |
| `POST /:uid/study/segments/:segmentUid/archive`, `/restore` | Archive or restore; a segment is never deleted |
| `POST /:uid/study/segments/reorder` | `{ uids }`: every live segment once, in the new order |
| `POST /with-study` | `{ project, study?, origin?, request_id? }`: the project and its study in one `env.DB.batch` |

- **A PUT replaces.** The body carries every field; a field not sent is written as not recorded. This is the brief route's shape (D5157 part 4), and its upsert (`INSERT … SELECT … ON CONFLICT DO UPDATE … WHERE version = ?`) is the pattern. A study with no field written is refused (`study_empty`); a study made from Markets has its origin, which counts.
- **Owner scope.** Every route reads the project through `checkProjectOwner`: another member's project is 404 `project_not_found`, the same body as a project that does not exist. An archived project refuses every write (409 `project_archived`); a support session cannot write (403 `support_read_only`), `/with-study` included. Refusals are built with `refuse()`.
- **Receipts.** Each write calls `logAdminAction`: `research_study_created`, `research_study_updated`, `research_study_segment_created`, `…_updated`, `…_archived`, `…_restored`, `research_study_segments_reordered`, and `research_project_created` from `/with-study`. A receipt names the project and segment uids and the changed field names (and how many Validate links a venture change cleared), never the text typed.
- **Limits** are exported: `STUDY_LIMITS`, `HORIZON_MONTHS_MAX`, `SEGMENT_LIMITS`, `SEGMENT_MAX` (12 live segments), `INDUSTRY_CODES_MAX` (20), `CUSTOMER_COUNTRIES_MAX` (60), `ORIGIN_QUERY_MAX` (120) and `ORIGIN_COUNTRIES_MAX` (20, as the Markets list). Over a limit is a refusal (`<field>_too_long`, `too_many_…`, `segment_limit`), never a truncation.

### The venture (owner answer A)

- At most one venture, optional. A `venture_id` is accepted only for a live `projects` row the caller passes `canAccessProject` for; any other id gets the same 404 `venture_not_found` as one that does not exist.
- The link gives nobody access to the study: every read is the owner's through `checkProjectOwner`.
- Every read runs `canAccessProject` again. When it fails, `venture` is `{ linked: true, state: 'no_access', message }` with no name or id, and each segment's Validate link is `{ state: 'no_access' }`. A read that throws is `state: 'unreadable'`, never `no_access`.
- Later issues require the venture before Validate, Grow or sizing records are attached or the study is shared; this issue does not.

### The Validate segment

- Accepted only when the `customer_segments` row belongs to the study's linked venture, is not archived, and the caller can still read the venture; otherwise 404 `validate_segment_not_found` (and always with no venture).
- Changing or clearing the venture clears every segment's Validate link in the same batch as the study write. The clearing `UPDATE` runs only when the study write before it changed a row (`changes() > 0`, read inside the batch as `adminAuditStatement`'s `onlyIfChanged` does), so a stale write clears nothing. The first build keyed this on the study's next version and the test caught it clearing on a stale write whose version matched a later one; that is why it reads `changes()`.

### The origin

- `/with-study` accepts `origin: { market_slug, q, country[], fresh, src }` and no other key (a `tracked_sector` sent by the client is refused as `invalid_origin`). The slug must be in `research_market_directory` (`unknown_market`); country codes must be on `research_countries` (`invalid_country`); `fresh` and `src` must be in `FRESH_BANDS` and `SOURCE_KINDS`.
- The tracked sector is read by the Worker from `research_market_sectors` (`marketSectorFor`) at that moment, and a market with none is `{ state: 'none' }`.
- It is written once and never edited (a PUT carries no origin and leaves it). It comes back as `origin: { market, tracked_sector, markets_company_location_filters: { label, q, country, fresh, src } }`, the key and label (`ORIGIN_FILTERS_KEY`, `ORIGIN_FILTERS_LABEL`) saying these were company-location filters in Markets, not the customers' geography.
- A segment's customer countries are set only by its own `customer_countries` field, start empty, and must be on the country list.

### `/with-study`

- One `env.DB.batch`: the project insert and the study insert (the study selects the project by its new uid and owner). A failed batch is answered `500 save_rolled_back` with `rolled_back: true` only after a read finds no project under the uid the save minted; when that read fails too it is `503 save_outcome_unknown` with `rolled_back: null`.
- A `request_id` per form: a repeat returns the first project (`200`, `repeat: true`) and writes nothing; a repeat that races the first loses on the unique index and is answered the same way.

`STATISTICAL_UNITS` (`enterprise`, `establishment`, `legal_unit`, `household`, `consumer_unit`, `person`) and `INDUSTRY_SCHEMES` (`isic_rev4`, `nace_rev2`, `naics_2022`) are defined in `routes/research_studies.ts`, because #7716's PR had not merged when this was built (checked 2026-11-19: no merged PR for #7716). **Whichever of #7716 and #7719 merges second imports the first one's constant** and deletes its own copy, reconciling the values: if #7719 merges first, #7716 imports these two lists from `routes/research_studies.ts` (or moves them into its service and this file imports them from there); if #7716 merges first, this file imports its lists instead.
