### 1. Why

On PR #3838's routes:
- **`dropped` held bare keys,** so SM8b could not name a module.
- **A saved key that became plan-locked stayed in `layout`,** flagged `locked_by_plan`. `PUT /layout` then refused, 402 `module_locked`, any layout still holding it, so the member's next Done failed with no way out but Reset.
- **`PUT` overwrote unconditionally.** `updated_at` is accurate only to the second, so it cannot serve as a version.

### 2. Migration 750

`ALTER TABLE studio_layouts ADD COLUMN revision INTEGER NOT NULL DEFAULT 1`, additive only.
- A row saved before 750 reads 1.
- A first save starts at 1, and each later save adds one.
- Reset deletes the row, so the next save starts again at 1.

### 3. Every layout read

```
{ profile, source: 'saved' | 'default',
  layout:   [{ key, size }],                       // only modules this member can place now
  revision: number | null,                         // null when there is no row
  updated_at: string | null,
  dropped:  [{ key, title: string | null, reason: 'not_offered' | 'plan', plan: { tier, name, plan_key } | null }] }
```

- **A saved key this profile no longer offers** goes to `dropped` with `reason: 'not_offered'`.
  - Its `title` is its last known title from `RETIRED_TITLES` when the key is fixed (Chat, Founder strip, Profile card), removed ("Do these next", "Activity across the platform") or renamed by D1418 ("Module map", "Firm standing").
  - Otherwise the title is `null`, and the page says "A module was removed…", never the key.
- **A saved key that `lockOf` now locks** goes to `dropped` with `reason: 'plan'`, its `title` and its `plan`. It is no longer in `layout`, so the next `PUT` of the read's layout succeeds.
- **A read never rewrites the stored row.** If the member upgrades, the module comes back on the next read, until they save without it.
- **`locked_by_plan` has left the layout entries:** a placed module is never locked.
- **A default read** has `dropped: []` and `revision: null`.

`RETIRED_TITLES` lives in `routes/studio_layout.ts`, a file this issue owns, rather than in `services/studioModules.ts`, which #3862 owns. Both issues are S24's, so no coordination was needed. It can move into the registry if S1 prefers.

### 4. `PUT /api/studio/layout`

- **Body:** `{ layout, expected_revision }`.
  - `expected_revision` is required. It is the revision the read gave, or `null` when the read had no row.
  - Missing, or anything but a positive integer or `null`, is 400 `invalid_layout`.
- **The checks run in this order:**
  1. the body's shape;
  2. `expected_revision`;
  3. the entries, in #3838's order.

  402 `module_locked` still applies to a key the member tries to add.
- **One bound write:**
  - `null`: `INSERT … ON CONFLICT (user_id, profile) DO NOTHING`.
  - Otherwise: `UPDATE … SET layout = ?, revision = revision + 1, updated_at = datetime('now') WHERE user_id = ? AND profile = ? AND revision = ?`.
- **No row changed** is 409 `stale_layout`: "Your layout changed in another tab. Reload it to see the latest.", with `extra.revision` (the current one, or null after a reset). Nothing is written.
- **Two saves from one copy at once:** one wins and the other gets 409.
- **The 200** is the new read, with its new `revision`.

`POST /layout/reset` is unchanged. A tab still holding the old revision then gets 409 on its next save: SM8c.

### 5. Client

`studioLayoutApi.saveLayout(layout, expectedRevision, profile)`. The body is `{ layout, expected_revision: expectedRevision ?? null }`.

### 6. Verified

**`cloudflare-worker/test/studio_layout_revision_d1594.test.ts`** (8 tests), on real SQLite from 687 plus 750. It covers:
- **the migration:** 750 applies on top of 687, a row saved before it reads 1, and the column refuses NULL;
- **saving, in sequence:**
  - `null` → 200 at revision 1; `null` again → 409, row unchanged;
  - 1 → 200 at revision 2; 1 again → 409 with `revision: 2`, row unchanged;
