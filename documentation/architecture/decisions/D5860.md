## D5860 — Link a Facebook Page to a Distribution channel (#5860)

A venture's linked Facebook Page offers one channel-link proposal in
Distribution's `parts.from_facebook.proposal`, even before any Page insights
have been recorded. Linking the Page or syncing raises it with an insert that
leaves every existing decision alone. The unique key is venture, kind and Page
id. Relinking the same Page preserves dismissal. The only kind is `channel_link`.
If another connection subsequently serves that same Page, the proposal moves
to the current connection while keeping its decision. An in-flight sync of
an unlinked Page cannot raise a proposal or take it back.

### Who decides

Follow Facebook's sync and Beehiiv's connection-owner precedent. The caller
must be allowed to write the venture, own its active Facebook connection and
have that connection enabled for its company. An accepted cofounder whose
connection serves the venture may decide. The founder using another member's
connection may read the proposal but cannot decide it. Support sessions are
refused before any read or write. Every id is scoped to the venture, current
connection and currently linked Page. No provider request or token is needed
to decide a local channel proposal.

### Accept and Dismiss

Accept reuses the venture's channel with `utm_source = 'facebook'`, or calls
`addChannel` with that source and `kind = 'organic'`. An optional
`growth_channel_uid` must identify that venture's Facebook channel. A channel
with another source is refused, preserving its existing attribution. A new
channel gets its normal writer validation and activity entry. Attributed
Facebook contacts then count through the existing Distribution reader.

Accept reserves a pending proposal by setting its state to `accepted`, leaving
`decided_at` null until the channel is linked. Dismiss can change only a pending
proposal, so it cannot succeed midway through Accept. If the writer or the
final update fails, Distribution still presents the incomplete proposal as
pending and Accept resumes it. The existing channel-source uniqueness prevents
duplicate channels, including concurrent requests. Only the request completing
the decision returns success and logs acceptance through `logGrowWrite`.
Completed decisions refuse subsequent Accept or Dismiss with 409.

Dismiss writes its actor and time and stays final through sync and relinking.
Disconnect and the signed Meta deletion callback remove the connection's
proposals through the shared Facebook purge. Channels already linked belong
to the venture and remain. Venture deletion cascades proposals. Deleting a
channel nulls its proposal reference and never reopens a completed decision.

### Delivery and verification

The production Worker needs migration
`202611182032_5860_facebook_proposals.sql`. The existing deployment workflow
applies it. The feed registry marks the channel proposal built. This part
backfills proposals for Page links created before the migration, so those
ventures get the question without another sync. It
supplies the Worker response and actions for the Facebook frontend whose
approved design is recorded by #5861.

Regression tests run real SQL and JWT-authenticated routes with synthetic
connections, a fixed clock and stubbed insights. They cover attribution,
connection ownership, support refusal, venture/Page isolation, final dismissal,
concurrent decisions, interrupted acceptance and disconnect/Meta cleanup.
