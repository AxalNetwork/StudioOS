## D7674 — Shared Network directory reads, private overlays and reviewed publication (#7674)

**Status:** implemented for review, 2026-11-22. Additive migration, one router and one service. No production
import, publication or apply has run through this change, and no member data is visible until an operator
publishes an organisation after this lands.

### Owner boundary

The owner's answer on #7739 (Q3 B) excludes contact columns and whole records about people before upload, and
the 2026-11-21 note on this issue says it does not authorise the Network people-record import. Q4 A holds any
real production apply until #5719 closes. So this change builds the organisation path and **holds the people
path**: `POST /admin/entries/:uid/publish` refuses a person with `people_publication_held`, and a person can only
be hidden (suppressed), never published, here. Member reads still apply one rule to both kinds, so a later
authorised decision changes the publish gate and nothing else.

### What a member reads

`GET /api/network/directory/entries` and `/entries/:uid` (signed in) return only entries with
`publication_status = 'published'` and `verification_status <> 'withdrawn'`, through one professional projection:
name, optional first and last name, profile and website URLs, geography, sector, stage and source-category
labels, the investing tri-state (`null` when the source did not say), previous investments as the source's own
text, the verification state, and the source's name with its observation date. Not in it: the verified account or
company link (so a search never reveals whether a person has an Axal account), the source row id, any review
item or duplicate candidate, and anything from `network_directory_private_sources`, which no route here reads.

Lists are ordered by name then uid with an opaque cursor; `total` comes from the same WHERE as the page. A search
term matches anywhere in the name with `%` and `_` matched as typed. An entry's associations list only the other
side's visible entries and only associations not withdrawn; an undated association reads `current: 'unknown'`,
never assumed current, and no employment is inferred from an email domain or a website.

### The private overlay

`network_directory_overlays` keeps one member's saved mark and note (at most 2,000 characters) on a canonical
directory person. Every statement keys it by the caller's id, so another member reads `null`. A support session
is refused, because the note is the member's own. Writing an overlay creates no relationship, book link, notice
or consent. An overlay is refused on an organisation and on an entry members cannot see. Existing member books,
project contacts, partner books and platform ties are untouched.

### Reviewed publication

`GET /admin/entries` and `/admin/reviews` are Super Admin reads; publish and suppress are behind
`requireSuperAdminWriteBar` (a TOTP session, a recent step-up, then the elevation), as the owner's supported
route on #7739 names.

Readiness is read from the **latest** observation of every source row behind the entry (the 14:27Z note on this
issue): finding an accepted snapshot is not enough. An entry is blocked by `latest_observation_not_accepted` (a
later held or skipped observation of the same row), `same_time_conflict` (two different observations at the same
time; review, never last-writer-wins), `open_review` (a pending review naming any observation of those rows), or
`no_source_record`. An older hold behind a newer acceptance does not block.

Each change is one `network_directory_publication_events` row with a unique idempotency key, the source snapshot it
was checked against, the reason and the actor, and is also in the admin audit. The event is inserted only while
the entry is still staged and the entry moves only when that event exists, in one batch, so two concurrent
publishes write one event; the answer is read back from the database. A retried key returns its first answer
(200, `replayed: true`); a key reused for another entry or action is refused. Suppression keeps the entry's
sources, overlays, associations and history and stops members reading it.

### Not built here, and why

- **The controlled apply of a #7672 import plan.** The planner emits SQL batches; a Worker route that executes
  submitted SQL would be unsafe, and a server-side re-plan needs the source records, whose people part the owner
  has not authorised. With Q4 A holding production apply until #5719 closes, this is the next part once the owner
  authorises an organisation-only upload: a write-barred route that re-plans from an uploaded organisation
  manifest, applies idempotent batches and reads back counts.
- **Cross-run dedupe, reviewed merge, redirects, alias and conflict resolution actions.** Review items are
  inspectable here; resolving them is a separate operator action with its own decision.
- **Restricted contact projections.** No visibility policy permits one, so none exists.
- **The member-facing Network UI**, which follows its own approved canvas.
- **Production counts.** None are recorded because nothing was imported or published.

### Rollback

Revert the PR. The two additive tables can remain; nothing else is changed. An entry an operator published can be
suppressed through the same route.

### Verification

`cloudflare-worker/test/network_directory_apis_7674.test.ts` runs the mounted router over the migrated schema with
synthetic people and organisations only: visibility and the true total across pages, the literal search, the
projection's absent fields (with a marker planted in every private source cell), associations and unknown
currentness, overlay ownership and support-session refusal, operator readiness and review reads, the write bar
(member, plain admin and a stale step-up refused), idempotent and concurrent publication, the people hold, each
readiness blocker, suppression, and that no account, relationship, notice, book link or company row is written.
