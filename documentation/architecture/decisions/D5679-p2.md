## D5679 part 2 — Send HQ database-capacity incidents and recoveries to the platform section (#5679)

The HQ capacity cron already measures D1 capacity every fifteen minutes and persists one episode across warning, critical, and recovered readings. This pilot reconciles the existing `hq` / `d1.size_bytes` episodes to `axalvc-superadmin-platform`. A fixed server-owned notification opens the Slack thread and measured recovery replies to its acknowledged timestamp. An unreadable measurement leaves the episode open. An active mute holds delivery. The message contains neither measured usage nor user, tenant or request data.

Apply the `202611121106_5679_section_capacity_slack.sql` migration and deploy the Worker normally. Verify the private channel and bot using the D5679 receipt test. Set `AXAL_SECTION_CAPACITY_SLACK_START_UTC` to the UTC activation time as an ISO 8601 timestamp ending in Z on the intended HQ deployment. With the binding unset, the scheduled source continues its existing HQ behavior and skips Slack. Historical episodes opened before the configured time stay outside the route. Remove the binding to pause. Reuse the original cutoff to resume any eligible outstanding work.

If delivery storage or configuration is unreadable, the capacity sweep still completes and records its normal HQ alerts. The Worker writes one fixed diagnostic for that scheduled pass and returns `section_delivery: unavailable`. A checked pass may still have pending or uncertain transitions.

The delivery ledger stores the episode ID, phase, claim, attempt count, next eligible time, safe failure classification and provider receipt. A transition is unique per episode and phase. Each sweep attempts at most two sends. Known rejections and pre-send failures take at most five attempts with exponential backoff and the provider’s Retry-After. A missing acknowledgement or a timed-out claim stays uncertain. There is no automatic repost after a possibly accepted write. A recovery waits for a confirmed opening receipt and the original destination.

An operator can inspect unresolved delivery states using a read-only D1 aggregate:

```sql
SELECT state, stage, last_reason, COUNT(*) AS transitions
FROM section_capacity_slack_deliveries
GROUP BY state, stage, last_reason;
```

For an uncertain delivery, compare the episode timestamps with the private channel history before choosing any manual replay. Fix the underlying token, membership or channel configuration for exhausted deliveries. The ledger keeps these cases visible pending an operator’s reconciliation. This slice does not alter Slack membership, customer notification preferences, CI routing, production deployments or GitHub issues.
