## D1316 — Builder part 1, the Worker: the assistants overview, the grants read grows, the grant in the call log, the admin panel retired

S17, 2026-10-27, for #3474 (part of #2418). No migration. Basis: `main` after D1315 (#3477).

### 1. The overview: `GET /api/developer/assistants/overview`

`routes/developer_assistants.ts`, mounted at `/api/developer/assistants`. It is signed in, and
it answers 404 with the MCP flag off, as every assistant route does. It returns:

- `server_url`: `publicOrigin` plus `/mcp`.
- `scopes`: each scope with the consent page's own label (`SCOPE_COPY`).
- `tools`: `registeredTools()`, with name, title, description, required scope and
  read only. Each tool appears under its listed name. An alias (`structure_with_studioos`)
  is never listed.
- `limits`: the constants the server enforces, read from where it reads them, so this read
  cannot drift from them:
  - 60 a minute per connection, and 120 across every connection and key;
  - the tool time limit;
  - the interview submissions and placements a day.
- `can_grant` and `grantable_count`: the consent page's own rule (`grantableCompanies`).

### 2. The grants read grows: `GET /api/connectors/assistants`

Each grant gains these fields:

- **`scopes`**: what the grant was given.
- **`verified_assistant` and `assistant_label`**: from `assistantIdentity` on the callback
  the grant was made for, never from the self-declared name.
- **`companies[].still_owned`**: false once the venture is deleted or the member no longer
  owns it (`ownsVenture`).
- **`last_call_at`**, with `last_call_source`:
  - `call_log` when the `mcp_tool_call` lines name the grant;
  - otherwise the 31-day KV key, `last_use`;
  - otherwise null, which the page reads as "No call recorded".
- **`calls_30d`**: `{ total, ok, refused, rate_limited, failed }` from those lines. It is
  null, never zero, when the log cannot be read.

`last_used_at` stays, with the same value as `last_call_at`, for today's readers.

The counts come from one bound statement over the caller's own lines (`user_id = ?`). Another
member's line that names the grant is never counted, and the test proves it.

`api_usage_events` (D843) also holds `grant_id`. The issue names `activity_logs`, and that is
what this reads. Moving the counts to the usage ledger, which has history from D843 onwards,
is a one-statement change if the owner wants it.

### 3. The call log keeps the grant and the reason

`logToolCall` adds two fields to the `mcp_tool_call` line:

- `grant`: the grant id, never a token, for an assistant connection's call. A key's call
  keeps `api_key_uid` and has no grant.
- `reason`, for a refusal, one of `REFUSAL_REASONS`:
  - `not_granted`: the company is not one the connection was approved for;
  - `not_owned`: the member lost the access the tool needs;
  - `scope`: the token lacks the tool's scope;
  - `daily_limit`: the interview tools' daily limit, `ToolError` code `daily_limit`.

  Any other refusal keeps no reason.

Lines written before carry neither field and read as "connection not recorded". No argument
or result is ever logged.
