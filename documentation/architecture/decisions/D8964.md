## D8964 — HubSpot and Salesforce scope a founder to its owner through `users.founder_id` (#8964)

- **Status:** built by S39 on #8964, 2026-11-27.
- **Chosen by:** the existing schema. No migration: the mapping already exists.

### The problem

The HubSpot and Salesforce providers scoped deals and projects to the integration owner with `founders.user_id = ?`. `founders` has no `user_id` column: not in `cloudflare-worker/sql/schema_baseline.sql`, not added by any migration (the only two `ALTER TABLE founders` add `sf_contact_id`, 019, and `company`, 078). Every one of these reads therefore failed with "no such column" on D1:

- HubSpot: the outbound sync, the inbound match and the webhook match;
- Salesforce: push by deal id, the account push's project check, the outbound sync and the inbound match.

Found while building #5454 (PR #8945), whose test fixture added the column to exercise the readers.

### The decision

A founder row belongs to a user through **`users.founder_id`**. It is the column `canAccessFounderResource` in `cloudflare-worker/src/auth.ts` compares (`user.founder_id === ownerFounderId`), and the join the codebase already uses to tie a connected integration to its projects (`integrations i JOIN users u ON u.id = i.user_id JOIN projects p ON p.founder_id = u.founder_id`, `services/records/grow.ts`; also `labEvidence.ts`, `agents/memory.ts`).

The seven statements now live in `cloudflare-worker/src/integrations/crmDealScope.ts`, with one owner predicate:

```sql
f.id = (SELECT u.founder_id FROM users u WHERE u.id = ? AND u.founder_id IS NOT NULL)
```

- **Bind order is unchanged**: the owner's user id is still one `?` in the same place, so no call site changed beyond the SQL text.
- **Fail closed**: an owner without a `founder_id` (an admin, an investor) gets NULL from the subquery and matches nothing.
- **The company scope stays**: the outbound and inbound reads still require the deal's company to be enabled for that integration (`integration_companies`); the owner predicate is applied on top of it, so a company enabled by mistake for another tenant's venture still yields nothing of theirs.
- Salesforce's `row.user_id` is typed as text; SQLite's integer affinity on `users.id` matches it, and the test binds it both ways.

### Not chosen

- **Add `founders.user_id`** — a second, unsynchronised copy of a relationship `users.founder_id` already holds; it would need a backfill and a writer on every founder link.
- **Match on email (`founders.email = users.email`)** — emails change and are not the link auth uses.
- **Replicate the licence check** (`holdsLicence(user, 'founder')`) in SQL — the owner is reading their own founder's deals into their own CRM, not reaching another founder's data; `users.founder_id` is what the other integration reads use. If a converted founder must lose CRM sync, that is a separate decision.

### Proof

`cloudflare-worker/test/crm_deal_scope_8964.test.ts` runs every statement on the migrated schema (`_storage_schema.ts`: baseline plus every migration, no fixture-added column) and asserts `founders` has no `user_id`. User ids and founder ids are crossed (user 1 holds founder 2) so a predicate comparing a founder id to a user id leaks; both tenants' deals carry the same CRM ids; and one tenant's integration is enabled for the other's company, so only the owner predicate keeps the other tenant out. It also holds the provider sources to the shared statements.

### Follow-up
