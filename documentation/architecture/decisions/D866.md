### 1. The channel in D858's analytics

1. **A session's channel** (`channelOf`, `services/conversationAnalytics.ts`) extends D873's `session.channel`, which named only calls and chats:
   - a call's channel as D873 names it (`zoom`, `meet`, `upload`);
   - the provider it came in on (`submitted_via`: `telegram`, `whatsapp`);
   - else the provider of the chat that points at it (`channel_threads.session_id`);
   - else `recorder` for a recording made in StudioOS (`in_person`, `video`, `phone`);
   - else the session's own channel (`text`, `manual`).

   A session with none of these is NULL, never a guess. In a venture's per-channel figures it is keyed `unknown`, with `channel: null`.
2. **Both reads take `channel`.** It is a lower-case name (`^[a-z][a-z0-9_]{0,31}$`); anything else is 400.
   - **A venture** named with a channel reads that channel's sessions, whatever their kind, recordings and typed notes included; it takes precedence over D873's `kind`. The filter is `channelOf` in literal, bound SQL (`ventureChatSessions`), applied before the 500-session limit. Without a channel, the read is D873's: the venture's chats (the default), calls or both, by `kind`.
   - **A session** of another channel answers 404, as a filtered list would leave it out. It never reveals more than D858's 404 does.
3. **Figures per channel.**
   - A venture's read carries `sessions_by_channel` and `by_channel`: for each channel in the read, its own session count and the same figures as the whole, from messages to competitor mentions.
   - Each channel is read as a venture of its own, so its figures add up to the whole. Quotes and their counts stay on the whole read only.
   - Each session read names its `session.channel`.
4. **The client** (`frontend/src/lib/api/conversationAnalytics.js`) passes `channel` to both reads. No new method.

### 2. Telegram end to end

The Telegram chat reaches Validate through code that already exists; this task proves it with a test and adds no path of its own.

1. **An assigned Telegram chat's text** enters the session at once (D684), queues the engine (`chat_text_added`), and is structured by `structureSession`. D859's extraction then runs on it, as on every messaging provider (`validateEngine.ts`). Each item is a `validate_proposals` row citing its segment's span (`cite_from`, `cite_to`) with the verbatim quote, for the founder to accept.
2. **A consented voice note** (the contact's own YES, D756 §1.5) is fetched, transcribed, appended as a line, queues the engine (`voice_note_added`), and gives a proposal citing that line.
3. **Source labels.** #2512 asked for `source_label='Recorded'` and a `source_ref`. Under the owner's ruling on #2504 (option A), proposals are interview-engine placements, which carry no label column. The segment reference is the cited span, and the label is what D858 derives: a chat's text is `Typed`, and a voice note or recording is `Recorded`.
4. **Notes held.**
   - **Without a YES:** the note is never fetched and never becomes a line, so the proposals come from the text alone.
   - **After a NO:** D757 is stricter than #2512's wording. A NO declines the session, the engine runs nothing more on it (`sessionDigestConsentBlocks`) and no model is called, so there are no proposals, not even from the text. The text itself is still kept (D756 §1.5).
   - **After a STOP:** no new note is queued or downloaded.
5. **Prototype asks** are D859's `prototype_ask` finding, with `build_candidate: true`. Nothing is written to Build; PIPE-BUILD (#2426) reads the flag.
6. **Re-running proposes nothing twice.** A new message re-reads the whole chat. D859's dedupe (`storePlacements`) keeps an item the interview already has, in any status, from coming back, so a discarded one stays discarded.

### 3. Data hygiene

- Every query is bound. The channel filter is a validated name, bound, never interpolated.
- The venture read and its per-channel figures carry aggregates only.
- Nothing here logs content, and the test's fixture people are synthetic.

### 4. Edits and deletions at the source: open, waiting on S1

`main` cannot tie an assigned Telegram message to its transcript segment:
- `appendSegments` stores no message id;
- the pending copy that held the id (`refKey`) is deleted when the text moves;
- migration 438's `interview_transcript_segments` has no column for it;
- `threads.ts` says: "Once a message is in an interview the transcript is the member's record."

So an `edited_business_message` or `deleted_business_messages` on an assigned chat finds nothing to change. The options are on #2512:
- **A.** A migration adding `source_ref` (the `refKey` hash) to segments (recommended).
- **B.** The hash in `speaker_raw`.
- **C.** Keep D684's rule and drop scope 3.

The rule #2512 states holds under A or B:
- **An edit** replaces the segment's undecided proposals and re-runs extraction under D859's key; a decided proposal is never changed.
- **A deletion** withdraws the segment's undecided proposals and keeps the decided ones.

This section is completed by the ruling.
