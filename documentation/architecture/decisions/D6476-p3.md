## D6476 part 3 — The owner's answers to the merge-queue audit's open P1s (#6476, #6467)

- **Status:** decided by the owner on 2026-11-17, in a Claude Code session, and built the same day on #7089.
- **Builds on:** D6476-p2, D6467 (the shared budget), D6481 (the feeder).

| Question | Answer | What changed |
|---|---|---|
| What does `LANDING_BOT_DAILY_MODEL_RUNS` count? | **Runs.** | One unit per model run, however many rounds or account fallbacks (primary Claude, Claude 2, Claude 3, Codex) it used. The runner's per-run caps bound what one run spends. `budget()` reads `modelRuns`; the resolver already reserved one per run. A cap of 1 refuses the second run of the day (test). |
| May the ejection handler re-queue an entry the landing App made? | **Yes.** | `consent()` counts an entry by the App's own login (`LANDING_BOT_LOGIN`) as consent (`app-queued`). Another bot's entry is not. Any commit after the entry other than a no-model merge of main still voids it. |
| Is the keeper's merge of main a model repair? | **No** (it carries no model edit). | The feeder's `repairStatus()` treats a two-parent commit with `Landing-Bot-Kind: keeper`, made by the App itself, as no-model. With `LANDING_BOT_LOGIN` unset the commit stays uncertain and the PR is refused, as before. `scan-fix` (D6935-p2) counts as a model repair. |

**Owner step:** set the repository variable `LANDING_BOT_LOGIN` to the landing App's `<slug>[bot]`. The feeder reads it before it mints the App token.

Model-edited PRs stay in the owner's lane throughout: the feeder never admits them, and the owner submits them to the queue.
