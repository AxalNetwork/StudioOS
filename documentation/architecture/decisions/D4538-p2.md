## D4538 part 2 — Company extensions: the lineage columns, the fork route and the base-update read (#4538)

Part 1 (`D4538.md`) chose **fork with provenance**: an extension is an ordinary `scope = 'company'` skill that records which HQ skill and which published version it was copied from. This part builds the backend of that model: one migration, two routes, one rule on an existing route, and their tests. It builds no screen and no ranker.

### What is built

**Migration `202611130253_4538_skill_extension_lineage.sql`** (additive; nothing is backfilled):
- `agent_skills.based_on_skill_uid TEXT` (32 characters), `agent_skills.based_on_version INTEGER` (≥ 1) and `agent_skills.fork_reason TEXT` (1 to 300 characters once trimmed).
- A CHECK on `fork_reason`, added last so it can name the other two: the three are all NULL, or all set and only on a `scope = 'company'` row. Every existing row reads NULL in all three and passes; it stays standalone.
- `agent_skill_versions.based_on_version INTEGER` (≥ 1): the HQ base each published company version was built from, written in the version's own INSERT and so as immutable as the row (759's trigger).
- A partial index `idx_agent_skills_based_on (based_on_skill_uid, company_id) WHERE based_on_skill_uid IS NOT NULL`.

**`POST /api/teams/skills/:uid/extend`** (`routes/team_skills.ts`). `:uid` is the HQ skill. The body is `{ company, reason, version?, name? }`.
- **Who:** the company's editors (`canEditAsMember`), the same rule as `POST /skills` for a company skill. A plain member gets 403 `not_editor`. HQ's Super Admin also gets 403 `not_editor`, because HQ moderates a company's skills and never writes one (D4161). Another company's editor gets 404 `not_found` (the company is not theirs to see).
- **Eligibility of the base:**
  - it must be readable (404 `not_found` otherwise, which covers a never-published HQ draft);
  - it must be an HQ skill (422 `base_not_hq`);
  - the version must be published (422 `version_not_published`; a non-integer or < 1 is 400 `version_invalid`);
  - it must not be retired (409 `base_retired`);
  - that version must not be refused by the run gate's suspension rule (409 `base_suspended`, `skillRunRefusal`).

  Role and tool fit are per agent, not per skill, so they stay where they are: `attachCheck` on the extension's own published version when it is pinned.
- **The copy:** the exact version's parts (purpose, steps, tools, output kind, taxonomy tags, roles), checked by `checkDraft` as every save is. Only `name` may differ, so one company can extend one HQ skill more than once; a clashing short name is 409 `slug_taken`.
- **Reply:** a new company **draft** (nothing is published for the company) with `based_on_skill_uid`, `based_on_version` and `fork_reason` set. `created_by` and `created_at` are the creator and the time. It answers 201 `{ skill, base: { uid, name, version, current_version } }`.
- **HQ is only read.** The test compares the HQ row, its draft tags and roles, and its versions byte for byte before and after.
- **Audit:** the existing company-skill write audit, `company_skill_draft_created` (D4533 F1), with `based_on: { skill_uid, version }` and `fork_reason` added to its details.

**`GET /api/teams/skills/:uid/base`**, read under the skill's own read gate (`mayRead`: the company's members, and HQ's admins as moderators; another company gets 404).
- A standalone skill, which is every HQ skill and every company skill not made by `/extend`, answers `{ lineage: null }`.
- An extension answers `lineage`:
  - `based_on { skill_uid, version }`, `reason`;
  - `versions[]`: each company version with its `based_on_version`;
  - `base`: the HQ skill's `uid`, `name`, `status`, `current_version`, `retired`, `suspended`, the exact base `version` with its parts, and `newest` (the HQ skill's newest published version and its parts, only when an update is available);
  - `base_update_available`: true when the HQ skill is not retired and its `current_version` is newer than `based_on_version`;
  - `company { side: 'version' | 'draft', version }`: which company definition was compared, its latest published version, else its draft;
  - `fields[]`: per part (`name`, `purpose`, `steps`, `tools`, `output_kind`, `tags`, `roles`), `company_changed`, `base_changed` and `conflict`. A conflict is a part both sides changed, differently. This is D4538's three-way comparison of the old base, the new base and the company's latest version.
- When the HQ row or its version cannot be read, `base`, `base_update_available` and `fields` are null (the screen's "Unreadable"), never a guess.
- Nothing is applied: the test publishes a new HQ version and checks that the extension's draft, its versions and an agent's pin are unchanged.

**`PATCH /api/teams/skills/:uid` on an extension:** its tools must stay within its base version's tools. A tool the base did not have is 422 `tool_not_in_base` `{ tool }`, and nothing is saved. A base that cannot be read refuses the save, 409 `base_unreadable`. A standalone company skill keeps today's rule.

**Publish (`services/agents/skillPublish.ts`):** an extension's version row records `based_on_version`. A standalone skill's INSERT is unchanged, so it names no column a database without this migration lacks.

**Every card** (list, detail, write replies) carries `based_on: { skill_uid, version } | null`.

### Tests

`cloudflare-worker/test/skill_extensions_4538.test.ts`, 8 tests on the node:sqlite D1 fixture, covering:
- creating an extension, with provenance recorded and audited;
- HQ untouched;
- an older base version copied exactly;
- refusals for another company, a plain member, the Super Admin, a missing or over-long reason, and a company skill as base;
- a retired, suspended or unpublished base refused;
- `base_update_available` false then true, with a conflict named, nothing applied and the pin kept, and a retired base offering no update;
- tools narrowed but never widened;
- existing and standalone company skills unaffected, including `POST /skills` ignoring lineage fields;
- the migration's CHECK.

Sixteen mutations of the route, the publish and the migration each fail the suite, and it passes unmutated.

### Departures from D4538 and the issue

- **Rebase and fork-again are not built.** The base read gives the three-way comparison a rebase screen needs; producing a rebased draft waits on the screen. Fork-again is `/extend` from the newer version, which works today.
- **Base update when retired.** `base_update_available` is false once HQ retires the base, even if the retired skill has a version newer than the base. It reads `retired: true` instead: D4538 says a retired base reads "base retired", and no update should be offered from it.
- **The company side of the comparison** is the extension's latest published version, else its draft (D4538: "their latest version"). A writer with unpublished draft edits sees them on the card's `draft`, not in `fields`.
- **No HQ lineage view.** HQ's moderation queue (`admin_company_skills.ts`) does not yet show `based_on`. HQ admins can read it through `GET /skills/:uid/base`, under the existing read gate.
- **Locked fields.** Every part `checkDraft` accepts may be customised. Tools are the only locked part: they narrow and never widen.
