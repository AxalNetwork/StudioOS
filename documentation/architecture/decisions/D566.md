## D566 — The Ops canvas lands in design/incoming: five areas of screens for data the platform already stores

**The canvas the owner approved on 2026-10-06 is now two files in the
repository, so the slot that builds the event organiser (#1173) can read it.**
Slot S01, for the epic #1165. No migration, no route, no `frontend/src`
change.

**Where it came from.** #1165 found 155 client methods that no screen calls,
grouped them into areas, and gave five Claude Design prompts. The owner drew
all five as one design, `https://claude.ai/artifact/AZQC6nqkCj4ewoaJUvTH7F`.
On 2026-10-06 they asked for the event organiser to be built first.

**What landed.**
- `design/incoming/Ops · Boards.dc.html`: the board, rows of artboards
  chosen by a `set` property (events, account, partner, wellbeing, advisor),
  decoded with `scripts/read-canvas.mjs`.
- `design/incoming/Ops Page.dc.html`: the component every artboard imports,
  holding each screen's markup as one `sc-if` block per screen id. It came
  out of the artifact's bundle already in the processed format: the shared
  runtime, no inlined fonts.

**What the export lacks.** `Ops Page` takes its sample text from a script the
published artifact did not include (it sets `window.OPS_DATA`). The structure
of every screen is in the markup; its words are in the #1165 prompts. The
README section says how a builder combines the two, and that no figure is
invented.

**Why the files stay in `design/incoming/`.** Only the event organiser is being
built. The four other areas are not yet triaged, so the shared files stay in
the intake queue until every area's route is live.
