### 1. The table: one append-only event table

`work_graph_release_authority_events` holds one row per grant or revocation of one authority to one person in one
tenant and company: `tenant_id`, `company_id`, `user_id`, `authority`, `seq`, `op` (`grant` | `revoke`), `reason`,
`actor_user_id`, `idempotency_key`, `request_hash`, `created_at`.

**Why one event table and not a current-state table beside it.** The WorkGraph release tables are append-only, and
where something can be withdrawn the withdrawal is a later row: `work_graph_release_decisions` keeps every decision and
the live one is each reviewer's latest row; a withdrawn approval is a `withdraw` row, never an edit. Grants follow the
same shape. A second, mutable current-state table would be the only `UPDATE`-able table among them and would need its
own triggers to stay in step with the events; reading the latest row per key costs one indexed statement instead.

- **Who holds what now** is the latest row of each key (tenant, company, user, authority). `seq` numbers a key's rows
  1, 2, 3…; grants and revocations alternate, so an odd `seq` is a grant (a `CHECK`), and a `BEFORE INSERT` trigger
  refuses a row that is not the next number of its key. `UNIQUE (tenant, company, user, authority, seq)` backs it.
- **Append-only:** triggers refuse every `UPDATE` and `DELETE`.
- **Vocabulary:** the `CHECK` admits only the release services' names — `maintainer`, `brand_owner`, `marketing_lead`,
  `founder`, `partner`, `counsel`, `authorized_signatory`, `security_officer` — the union of `POLICY_PROFILES` approvers,
  `REQUIREMENT_AUTHORITY` attesters and `TAKEDOWN_AUTHORITIES`. The service derives the same list
  (`RELEASE_AUTHORITIES`) from those constants, and a test pins the two lists together, so a new authority in a profile
  fails the test until a migration admits it. `user_company_links.authority` (the team ladder) is not read: it is a
  different vocabulary (D5585-p7 §3, option C, not chosen).
- **Idempotency:** `UNIQUE (tenant_id, company_id, idempotency_key)`, with the request's hash, as on the other tables.

### 2. The rules

| Rule | Where |
|---|---|
| An unknown authority name is refused `unknown_authority` (400) | the service, and the table's `CHECK` |
| A grant needs the person linked to the company (`user_company_links`), else `not_member` (409) | the service |
| A revocation does not need the link, so a departed person's grant can still be withdrawn | the service |
| A grant counts only while the person is still linked: both resolvers join `user_company_links`, so removing the link withdraws every authority they hold there at once | the resolvers |
| A write names the `seq` it saw (`expected_seq`, 0 for a key never written); another is `stale_revision` (409) with `current: { seq, held }` | the service, then a conditional `INSERT … SELECT … WHERE` on the same `seq`, then the trigger |
| A grant of what is held is `already_held`; a revocation of what is not, `not_held` (409) | the service |
| A grant never crosses tenants: reads and writes name an exact (tenant, company); a write naming a company whose grants or release lines live under another tenant is `wrong_tenant` (403) | the service |
| Being a Super Admin grants nothing: a Super Admin holds an authority only where one was granted to them, and must be linked to the company like anyone else | the resolver |

Two Super Admins writing the same key from the same view: one lands, the other's conditional insert writes nothing and
is answered `stale_revision` (tested). The same request again under its key is a replay (`replayed: true`); another
request under that key is `idempotency_conflict`.

### 3. The routes (on part 7's router, so off unless `WORK_GRAPH_RELEASE_ADMIN=on`)

| Route | Gate | What it does |
|---|---|---|
| `GET /authorities?tenant_id&company_id[&user_id][&history=1]` | `requireSuperAdmin` | the current holders (linked people only), the vocabulary, and with `history=1` every event, newest first |
| `POST /authorities/grant` | write bar | `{ tenant_id, company_id, user_id, authority, reason, expected_seq, idempotency_key }` |
| `POST /authorities/revoke` | write bar | the same body; takes effect on the next resolution, i.e. the next request |

Off, all three answer 404 `release_admin_off` before the session or D1 is read (part 7's middleware). Every write that
passes the gate is an admin audit row (`logAdminAction`: `work_graph_release_authority_grant` / `_revoke`) with its
outcome, refused or not; every change is also its own event row in the store. Every answer carries
`cost: { d1Statements, d1Batches }`.

### 4. Wiring into publish and takedown

`RELEASE_ADMIN_DEPS.authorities` now defaults to `releaseAuthoritiesForScope(env, scope)`: every person of the named
scope with a live grant (capped at 1000 holders). `releaseAdminContext` puts that map in `ReleaseContext.authorities`
for every route, so:

- **Publish** counts a reviewer's approval only while the reviewer holds, in the store, the authority the approval was
  given under (the part 1 rule: authority is re-read at publication time). Without that, `approval_required`; a
  revocation makes the next publication refuse again.
- **Takedown** needs the acting Super Admin to hold the authority they claim (`TAKEDOWN_AUTHORITIES` or a profile
  approver of the manifest); without it, `no_authority`, recorded in the takedown table as before.
- **Reads** evaluate with the same map, so a manifest's `missingApprovals` shows what the store resolves.

Every existing refusal stays: `stale_approval`, `stale_revision`, `wrong_tenant`, `approval_required`, `no_authority`.

### 5. Tests

`work_graph_release_authorities_5585.test.ts`:

1. The vocabulary: service list = migration `CHECK` list = the eight names; five unknown names refused by the route
   (and audited), the service and D1.
2. Flag off: the three routes refuse 404 with a D1 that fails on any touch; admin, member and anonymous callers are
   refused; a Super Admin without step-up reads and cannot write.
3. Grant and revoke: `not_member`, malformed bodies, a grant, its replay, `idempotency_conflict`, `stale_revision`,
   `already_held`; a revocation takes effect at once; `not_held`; re-grant; unlinking withdraws; a departed person's
   grant can be revoked; history; every attempt audited; a grant that lands between another writer's read and write
   leaves that writer `stale_revision` with nothing written; the triggers refuse an update, a
   delete, a skipped `seq` and a revocation at an odd `seq`.
4. Scope: other company, other tenant and a bad tenant resolve nothing; writes naming another tenant are
   `wrong_tenant` (by release line before any grant, and by grant after); the other scope lists nothing.
5. Publish through the route: `approval_required` with no grant, with one of two, and with the wrong authority; then
   published; after a revocation the next manifest is refused.
6. Takedown through the route: an unlinked Super Admin cannot be granted; `no_authority` without, and after a
   revocation; applied with `security_officer` granted.

Mutation check: recorded in §7.
