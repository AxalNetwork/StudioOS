## D542 — Bug bounties are read from the coordinator's labels, and only an allowlisted sender's label counts

**Issue #1105, slot S09, part of #1101.** This file covers the first PR. It
reads the labels and closes outcomes. The grant, the 30-day revoke and the
on-screen bounty state follow in a second PR once the credit grant service
(#1103, D540) has merged. No migration.

**The labels.** They are declared by D543 (#1106), and only Session 1 applies
them:

| Label | Meaning | What the platform does |
|---|---|---|
| `bounty:confirmed` | the bug is real, a fix is being made | nothing yet; the state reads "Confirmed: being fixed" |
| `bounty:verified-high` / `-medium` / `-low` | the fix is live and graded | grant `bug_high` / `bug_medium` / `bug_low`, with source ref `bounty:ticket:<id>` |
| `bounty:not-a-bug` | not a bug, with S1's reason comment | close the ticket |
| `bounty:duplicate` | a duplicate, with a link to the original | close the ticket |

**Only an allowlisted sender counts.** `routes/github.ts` acts on a bounty
label only when the delivery's `sender.login` is on `BOUNTY_GRANTERS`.

- Logins are compared case-insensitively and separated by commas or whitespace.
- An unset or empty allowlist means nobody.
- The setting is declared at the top of `wrangler.toml` and again under the
  production vars, because an env table does not inherit them. Session 1
  labels as the owner account, so that is the one login on it.
- A bounty label from anyone else is refused, logged and reported in the
  response. It grants nothing and closes nothing.
- The ordinary label snapshot still records every label, as before. The
  allowlist governs what the platform does about a label, not whether the
  snapshot holds it.

The allowlist sits behind the webhook's HMAC signature check, which is
unchanged.

**Closing outcomes.** `bounty:not-a-bug` or `bounty:duplicate` from an
allowlisted sender does two things:

- The ticket's local status becomes `closed`.
- If the GitHub issue is still open, the platform closes it as `not_planned`
  through `updateIssue`. Otherwise the next absolute write from an `issues`
  event would reopen the ticket locally.

The closing call's own `closed` webhook comes back from the sync bot and is
dropped as an echo, as before. S1's reason comment reaches the user through the
existing comment sync.

**Tiers.** A verified tier added by an allowlisted sender is reported with its
rule key and its source ref. The response says `credits: 'not_granted'`, with
the reason: the credit grant service is not built yet. Removing a tier is
reported the same way.

Nothing is lost by waiting:

- The tier stays in `tickets.github_labels`.
- The grant is keyed by source ref, one per ticket, so the second PR can grant
  every verified ticket from the snapshot exactly once.
- D543 has S1 applying these labels only from the day #1105 merges.

**Bounty state.** `bountyStateFromLabels` gives each ticket its state from the
label snapshot, with no migration needed. The most decisive label wins:

1. not a bug, or duplicate;
2. fixed, at its tier;
3. confirmed;
4. under review, for a bug ticket with none of the labels above.

Any other ticket has no bounty state. Where the state is shown is an open
question on #1105:

- **A:** the existing `TicketsPage.jsx` list.
- **B:** a new list in the chat, which would need `needs-design`.
- **C:** both.

The issue named the chat's ticket list, but the chat has only the "Open a
ticket" form.

**Not done here, and why.**

- **The grant and the revoke wait on #1103.** That PR provides
  `grantCredits`, its revoke, and the rule amounts behind "Fixed: N credits".
- **The revoke window** (`BOUNTY_REVOKE_WINDOW_DAYS = 30`) is declared here and
  enforced by the second PR. It needs the grant's date, which only the ledger
  holds.
- **Grant idempotency across redeliveries** is tested in the second PR, against
  the ledger's unique index. This PR's handling already runs once per
  delivery, because the webhook's delivery GUID dedupe drops a redelivery
  before the bounty step.

**Tests.** `cloudflare-worker/test/bug_bounty_labels_d542.test.ts` has 10
tests. They send signed deliveries through the real router against a
baseline `tickets` table, with outbound GitHub calls captured. They cover:

- a stranger's tier label grants nothing and changes nothing;
- S1's tier label names the rule and the source ref, and says nothing was
  granted;
- each tier maps to its rule;
- a redelivery is dropped;
- not-a-bug and duplicate close the ticket and the GitHub issue;
- a stranger's outcome label closes nothing and writes nothing to GitHub;
- unsigned and forged deliveries are refused;
- the allowlist parses as described, with empty meaning nobody;
- the state precedence;
- `BOUNTY_GRANTERS` is declared in both var tables.

Ten mutations were run, and each was caught:

- the allowlist check removed;
- an empty allowlist read as everybody;
- two tiers swapped;
- the local close removed;
- the GitHub close removed;
- a refused label acted on;
- a grant claimed;
- the production var removed;
- the state precedence broken;
- the signature check skipped.
