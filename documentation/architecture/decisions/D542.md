## D542 — Bug bounties are read from the coordinator's labels, and only an allowlisted sender's label counts

**Issue #1105, slot S09, part of #1101.** This file covers the first PR. It
reads the labels and closes outcomes. The grant, the 30-day revoke and the
on-screen bounty state follow in a second PR once the credit grant service
(#1103, D540) has merged. No migration.

**The labels.** They are declared by D543 (#1106), and only Session 1 applies
them:

| Label | Meaning | What the platform does |
|---|---|---|
| `bounty:confirmed` | the bug is real, a fix is being made | nothing yet; the state reads "Confirmed: being fixed" |
| `bounty:verified-high` / `-medium` / `-low` | the fix is live and graded | grant `bug_high` / `bug_medium` / `bug_low`, with source ref `bounty:ticket:<id>` |
| `bounty:not-a-bug` | not a bug, with S1's reason comment | close the ticket |
| `bounty:duplicate` | a duplicate, with a link to the original | close the ticket |

**Only an allowlisted sender counts.** `routes/github.ts` acts on a bounty
label only when the delivery's `sender.login` is on `BOUNTY_GRANTERS`.

- Logins are compared case-insensitively and separated by commas or whitespace.
- An unset or empty allowlist means nobody.
- The setting is declared at the top of `wrangler.toml` and again under the
  production vars, because an env table does not inherit them. Session 1
  labels as the owner account, so that is the one login on it.
- A bounty label from anyone else is refused, logged and reported in the
  response. It grants nothing and closes nothing.
- The ordinary label snapshot still records every label, as before. The
  allowlist governs what the platform does about a label, not whether the
  snapshot holds it.

The allowlist sits behind the webhook's HMAC signature check, which is
unchanged.

**Closing outcomes.** `bounty:not-a-bug` or `bounty:duplicate` from an
allowlisted sender does two things:

- The ticket's local status becomes `closed`.
- If the GitHub issue is still open, the platform closes it as `not_planned`
  through `updateIssue`. Otherwise the next absolute write from an `issues`
  event would reopen the ticket locally.

The closing call's own `closed` webhook comes back from the sync bot and is
dropped as an echo, as before. S1's reason comment reaches the user through the
existing comment sync.

**Tiers.** A verified tier added by an allowlisted sender is reported with its
rule key and its source ref. The response says `credits: 'not_granted'`, with
the reason: the credit grant service is not built yet. Removing a tier is
reported the same way.

Nothing is lost by waiting:

- The tier stays in `tickets.github_labels`.
- The grant is keyed by source ref, one per ticket, so the second PR can grant
  every verified ticket from the snapshot exactly once.
- D543 has S1 applying these labels only from the day #1105 merges.

**Bounty state.** `bountyStateFromLabels` gives each ticket its state from the
label snapshot, with no migration needed. The most decisive label wins:

1. not a bug, or duplicate;
2. fixed, at its tier;
3. confirmed;
4. under review, for a bug ticket with none of the labels above.

Any other ticket has no bounty state. Where the state is shown is an open
question on #1105:

- **A:** the existing `TicketsPage.jsx` list.
- **B:** a new list in the chat, which would need `needs-design`.
- **C:** both.

The issue named the chat's ticket list, but the chat has only the "Open a
ticket" form.

**Not done here, and why.**

- **The grant and the revoke wait on #1103.** That PR provides
  `grantCredits`, its revoke, and the rule amounts behind "Fixed: N credits".
- **The revoke window** (`BOUNTY_REVOKE_WINDOW_DAYS = 30`) is declared here and
  enforced by the second PR. It needs the grant's date, which only the ledger
  holds.
- **Grant idempotency across redeliveries** is tested in the second PR, against
  the ledger's unique index. This PR's handling already runs once per
  delivery, because the webhook's delivery GUID dedupe drops a redelivery
  before the bounty step.

**Follow-up (review findings).** A review of the first PR found three bugs in
`routes/github.ts`. Each is fixed, and each fix has a test that fails without
it.

- **The coordinator's labels were dropped as sync echoes.** The
  `GITHUB_SYNC_BOT_LOGIN` filter ran before the bounty step. When the sync
  bot and the granter are the same account, every bounty label was ignored as
  `sync_bot_actor`. Now a `labeled` bounty label from a sender on
  `BOUNTY_GRANTERS` passes the filter. Every other event from the bot is still
  dropped, including a bounty label removed and the close the platform's own
  PATCH causes. The outbound label PUT keeps bounty labels as they are and
  never adds one, so an added bounty label is never an echo. The signature
  check still runs first.
- **The issue number reached a GitHub URL unchecked.** It was checked only for
  truthiness. Now it must be a JSON number that is a positive safe integer.
  Anything else is refused with a 400 `invalid_issue_number` before the
  delivery is claimed, any row is read or any fetch is made. A missing number
  is still acknowledged as `no_issue_number`.
- **A failed GitHub close still closed the ticket.** On a 401, 403, rate limit
  or 5xx after the retry, the ticket was closed locally and the delivery
  claimed with a 200, and the next sync reopened it. Now the GitHub close
  runs first. If it fails, nothing is written locally, the delivery claim is
  released, and the response is a 502 `github_close_failed`. GitHub does not
  redeliver a failed delivery on its own; it is listed as failed in the
  webhook's log, and redelivering it from there runs the whole step again.

- **Who decided is recorded.** Every bounty decision the platform acts on (an
  outcome that closes a ticket, a tier added or removed) writes one
  `activity_logs` row, `github.bounty_label`. The actor is `github:<login>`,
  and the details hold the ticket, issue number, label, outcome or rule, the
  sender, whether it came through the sync-bot account, and the status before
  and after. The row is written before the delivery is acknowledged. If it
  cannot be written, the claim is released and the response is a 500, so the
  delivery can be redelivered. A refused or ordinary label writes nothing.

Five tests were added, for 15 in all. They cover the shared account, ten bad
issue numbers and a missing one, a close failing with 401, 403, 429 and 500
and then succeeding on redelivery, and an outcome on an issue already closed.
Nine mutations were run, and each was caught: the bot exception removed,
widened to removed labels, and widened to refused senders; the number check
reduced to truthiness, opened to zero and negatives, and opened to numeric
strings; the local close kept on failure, the claim not released, and a 2xx
returned on failure. The three new route tests also fail against the code
before this fix.

### The grant and the revoke (after #1103)

#1103's grant service (D540) is on main, so a verified tier now pays. Before
this, the webhook answered `credits: 'not_granted'`.

- **A tier added** calls `grantCredits` with `bug_<tier>` and
  `bounty:ticket:<id>`, for the ticket's owner, as the system actor
  `system:github_bounty`. The service decides the rest:
  - it reads the amount from `credit_reward_rules` (migration 381: High 150,
    Medium 60, Low 20, which are the owner's #1102 Q3 A amounts);
  - it refuses staff;
  - it holds the 500-a-month cap;
  - it pays a source once. A redelivery, which GitHub sends with a new
    delivery id, answers `already_granted`, and so does a second tier on the
    same ticket.
- **A tier removed** revokes the grant through `revokeGrant`, but only when
  both hold:
  - the removed tier is the one that was paid. Removing another takes nothing
    back (`paid_under_another_tier`);
  - the grant is at most 30 days old. After that the grant is kept
    (`revoke_window_passed`).

  The age is read in either stored date shape (D162). The reason recorded on
  the ledger line names the label.
- **`revokeGrant` takes a system actor.** It used to take only a Super
  Admin, logged through `logAdminAction`. Now it also takes a `GrantActor`, so
  the webhook's revoke is logged to `activity_logs` as `system:github_bounty`,
  the way a system grant is. The `github.bounty_label` row beside it still
  names the GitHub sender, and now also carries the credit outcome.
- **A tier put back after a revoke does not pay again.** There is one grant
  per ticket, ever, and the answer is `revoked_earlier`. Paying it again is a
  Super Admin's manual grant.
- **Refusals are answered, not retried.** These all return 200 with the
  reason, because a redelivery would be refused the same way:
  - a staff owner;
  - the cap;
  - credits already spent (`would_overdraw`);
  - a ticket with no owner.

  A thrown error is different. It reaches the route's catch, which releases
  the delivery claim, so the event can be redelivered.
- **A removal by the sync-bot account now counts.** The follow-up above
  processed only *added* bounty labels from the shared account, and a test
  pinned a removal from it as an echo. In production the coordinator labels
  as that account, so the 30-day revoke could never run, and this PR reverses
  that pin.
  - The outbound label PUT in `routes/tickets.ts` reads the issue's labels
    live and re-sends every label it does not manage, bounty labels included.
    So it never adds or removes one.
  - The one gap is a label added between that read and that PUT. The PUT
    would drop it, and the removal would now revoke. That window is the
    length of one GitHub round trip.

### Where the bounty state is shown (the owner's answer on #1105: C, both)

`GET /api/tickets` now carries a `bounty` on each ticket.

- **Where it comes from.** `bountySummaries` reads the state from the
  ticket's label snapshot through `bountyStateFromLabels`.
- **Credits on a fixed ticket.** These come from the ledger, not from the
  rule. The amount is the grant's own `delta` for that ticket's owner and
  source ref, with `revoked` set when it was taken back.
- **Unpaid or unreadable.** A fixed ticket the grant service has not paid
  carries `credits: null`, never a guessed amount. If the ledger cannot be
  read, the row says so (`credits_unreadable`).
- **Not a bounty candidate.** A feature request or question has `bounty: null`.

**Wording.** `components/tickets/BountyBadge.jsx` gives each state its
wording once:

| State | Shown as |
| --- | --- |
| Under review | "Under review" |
| Confirmed | "Confirmed: being fixed" |
| Fixed, paid | "Fixed: N credits" |
| Fixed, taken back | "Fixed: credits taken back" |
| Fixed, never paid | "Fixed: no credits granted" |
| Not a bug | "Not a bug", with a pointer to the reason in the ticket's comments |
| Duplicate | "Duplicate" |

Neither reason is stored as a field, because the comment sync carries
S1's comment.

**Where it appears.**
- **Help → Tickets.** The badge sits beside the status on every row, in both
  the virtual list and the table.
- **The chat.** `components/tickets/MyBugReports.jsx` sits under the chat's
  ticket form. It reads the same list and shows the member's five newest
  reports that have a bounty state, each linking to its ticket, with
  "All tickets" for the rest. A failed read is said as one.
- **Layout.** This adds no new screen. The list lives in the panel the chat
  already opens for tickets, so I built it without a `needs-design` pass and
  without waiting for one.
