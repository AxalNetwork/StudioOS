## D5847 — A failed portfolio read answers 503 Unreadable, never an empty list (#5847)

- **Status:** built on `agent/claude/5847-unavailable-portfolio-reads`, 2026-11-18. Found under #5311 while building PF-05 (#5845) and PF-06 (#5846).
- **Code:** `cloudflare-worker/src/routes/positions.ts` (`GET /api/positions/:projectUid`), `cloudflare-worker/src/routes/portfolio_support.ts` (`GET /api/portfolio-support`); tests `cloudflare-worker/test/portfolio_unreadable_reads_5847.test.ts` and case 7 of `portfolio_periods_pages_4647.test.ts`.
- **Migration:** none. No frontend change.

### What is decided

- **A failed sub-read is not an empty one.** `GET /api/positions/:projectUid` caught a failed marks or distributions query as `[]`, so the company page showed "None recorded" and a $0 rollup that nothing had read. `GET /api/portfolio-support` did the same with its entries query, so `/portfolio/value-add` and the Support tab showed an empty ledger.
- **Each now answers `503 { available: false, source, detail, reason }`.** `source` names the read (`marks`, `distributions` or `entries`); `detail` and `reason` are the same sentence, starting "Unreadable — …". The pages already read a refused request as Unreadable (`readOf` in `frontend/src/pages/portfolio/portfolioModel.js`), so no shape the frontend checks changes.
- **Success is unchanged.** A read that worked and found nothing is still `[]` with 200. In the support ledger, only the figures (the two `GROUP BY` reads) failing still answers 200 with the entries, `totals: null` and `page_state: 'unreadable'`, as #4647 decided: the entries were read, only their totals were not.

### Not changed

- The cap-table snapshot read on `/api/positions/:projectUid` still falls back to `[]`; it is outside this issue and no PF board relies on it.
- Rollback is a revert.
