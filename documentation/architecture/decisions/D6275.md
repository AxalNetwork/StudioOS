## D6275 — A benchmark is deleted from its own page, by name, after a confirm step (#6275)

**What was missing.** `DELETE /api/research/benchmarks/:uid` and
`api.research.benchmarkRemove` existed, and no screen called them, so an
investor could not remove a benchmark.

**What the Worker route does (checked, not assumed).** The issue said it had
not been checked that the DELETE removes constituents first. It does.
`research.ts` looks the row up by `uid AND owner_user_id`, answers 404 when
that misses, and then runs two owner-scoped statements in order: the
benchmark's rows in `research_benchmark_constituents`, then the benchmark.
`cloudflare-worker/test/research_benchmark_delete_6275.test.ts` pins this on
real SQLite: another owner's uid answers 404 and nothing of theirs is
removed; the owner's delete removes only that benchmark's constituents, and
the constituents statement runs before the row's. The Worker is unchanged.
Two things about it are left as they are. Its 404 body is
`{ detail: 'Not found' }`, not the `benchmark_not_found` code the other
benchmark routes send. And the two statements are not one batch, so a
failure between them would leave the row with no constituents, never
constituents with no row.

**What the page does.** `BenchmarkDetail.jsx` adds a "Delete this benchmark"
card. `Delete…` opens a confirm step that names the metric
(`Delete “TVPI”?`) and says how many named constituents go with it. `Keep it`
closes the step and sends nothing. `Delete benchmark` sends the loaded uid
(D4607's `target`). Only a delete the Worker confirmed returns the page to
`/research/benchmarking`, with the deleted metric in the navigation state. A
failure keeps the benchmark drawn and says `This benchmark was not deleted.`
with the reason. A 404 says `This benchmark is not on your list.`, the D278
sentence the page already uses for a uid that is not yours. The page branches
on `status`, because this route's 404 carries no code. The buttons are
`min-h-[44px]`, full width below `sm`, and side by side above it.

**What the list does.** `BenchmarkingZone.jsx` re-reads on each arrival,
keyed on `location.key` rather than on mount, so a deleted row is gone even
when the zone stayed mounted. It also says `Deleted “<metric>” and the
constituents named against it.`

**Verified by** `frontend/test/research_benchmark_delete_6275.test.mjs`. It
mounts both real screens under one router: confirm text, Keep it, a confirmed
delete with its return and re-read, a re-read with the zone still mounted, a
500 and a 404. All six tests fail on the code before this change. Each
assertion was mutation-checked against the source.
