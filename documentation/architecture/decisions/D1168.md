## D1168 — Recorded member-file sizes and a resumable backfill

Issue #3081, S29, s31. Part 2 of #2449. Based on main `269fd7d5c8`.
Migration 605 is additive; it does not add a column to `users`.

### Built

`size_bytes` accompanies the file key on `demand_signals`, `formation_steps`,
`entity_obligations`, `obligation_occurrences` and `data_imports`. Existing rows
remain NULL until measured. Each has `size_missing_at` to distinguish a missing
object from an unmeasured one, and `size_unmeasurable_at` for an invalid namespace
or a key outside the owning project/user. Neither marker invents bytes. Sizes are non-negative integers; a measured empty
object can be 0, while a missing object always keeps NULL bytes.

Every accepted evidence, Build proof, Grow minutes and raw CSV upload saves its
measured size with its key in the same statement/batch. CSV uses UTF-8 byte length,
not string length. Imports without a stored raw file keep both key and size NULL.
Editing a legacy proof pointer clears its measurement and both outcome markers;
other edits and an unchanged pointer retain them.

`member_files` holds unique R2 keys for headshots and brand logos, with a uid,
owner, kind, measured bytes, missing/unmeasurable markers and timestamps. Brand sizes describe
the sanitized bytes actually stored. Both manual and LinkedIn headshot paths
commit the user pointer and side-table size together. Existing replacement
cleanup retains its behavior. Replacements invalidate the old size and queue a
recheck atomically with the new pointer, before cleanup; after a confirmed
deletion its metadata is marked missing. Superseded and unattributed headshots
can be verified again in later passes, so a failed missing-mark write or a
verification racing cleanup cannot leave a permanent positive size. This metadata service never deletes an object.

### Backfill

`POST /api/admin/platform/storage/backfill-sizes` requires HQ Super Admin,
TOTP and recent step-up, and is private/no-store. Body: `{ "limit": 10 }` by
default, an integer from 1 to 20. No caller-supplied key, prefix or cursor.
The client is `adminStorageApi.backfillSizes(limit)` through the D527 export.

Each call first persists one actor-linked `activity_logs` run receipt; its final
details contain an outcome and counts only. A failed audit prevents object calls.
No key, file name, body, address or error text is logged or returned.

Migration 605 also creates `member_file_size_backfill_state`. Its durable
checkpoints cover legacy user headshot pointers, light/dark landing-page logo
pointers and R2 discovery under the two profile-file prefixes. Indexed keyset
scans and persisted R2 cursors bound discovery work. Candidate size/missing
updates are each independently durable, so a stopped request resumes without
starting over. Cursor advancement and discovered keys share one D1 batch;
compare-and-set predicates prevent concurrent calls from rewinding discovery.
All SQL is static and bound.

Only `FILES.head(key)` measures an object. The backfill never reads its body,
writes it or deletes it. A NULL HEAD marks missing and retains the original key;
a failed HEAD leaves its row retryable and makes the batch `unreadable`, never
complete. Discovery failures do not stop measuring already-known candidates.
Measurement watermarks advance even for unmeasurable rows, so persistent
HEAD/size failures cannot starve later stores. Exhausting a pass resets
its watermarks for retries; a generation protects a newer retry pass from late
checkpoints. Transient failures keep the job incomplete and their sizes NULL. Invalid keys
are marked unmeasurable, retain their authoritative pointer and NULL bytes, and
do not block completion forever. Each batch reports its unmeasurable count;
future consumers must surface these unknown sizes rather than report zero.
Replacement uploads and proof-pointer edits clear the terminal mark.

Before HEAD, evidence and formation keys must match the row's project prefix;
entity proofs must name a project of that entity, minutes must match their
compliance event's project, and imports must match their user. Profile keys
must match their kind and known owner. Unknown owners remain unattributed.
Foreign keys are classified without any storage lookup.

Late HEAD responses update only a row still holding that same key and still
without a size/missing/unmeasurable mark, preserving concurrent replacements and uploads.
The returned counts are per batch: checked, recorded, missing, failed, changed
unattributed and unmeasurable, with `complete` and `outcome`. There is no invented total.

A legacy profile-file owner comes from its stored user relationship or the
server-generated numeric owner namespace, checked against `users`. If the user
is absent or the namespace is unrecognised, the side-table owner stays NULL and
the batch reports an unattributed count. No owner is guessed. Duplicate keys
are represented once. Earlier unreferenced profile objects are discoverable;
no general inventory of other R2 namespaces is attempted. A failed profile-file
metadata write can leave an unreferenced object. Discovery records its actual
retained bytes; the no-deletion rule is preserved. This part introduces no quota
charge or upload enforcement; downstream policy must account for retained copies.

This part does not change allowances, the usage meter, upload quotas, pricing,
notices or any page. The later storage parts consume these metadata stores and
must distinguish NULL/missing values from measured zero and unknown owners.
