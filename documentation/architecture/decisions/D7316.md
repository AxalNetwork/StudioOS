## D7316 — Worldwide Research company discovery identities (#7316)

The company expansion is additive to `research_company_directory`. The import
compiler consumes a fixed Wikidata snapshot, a fresh read-only snapshot of the
existing identities and taxonomy, and an explicit primary-source review of each
admitted company. It performs no network requests, opens no database and never
changes existing company records.

### Why the importer changed

The first implementation wrote a nonexistent `country_code` column, scraped only
two old migrations for duplicates, required a mapped industry, inferred founding
years from timestamps without their precision, and produced a migration even
when its coverage gate failed. Live country queries also made the result depend
on the time and order of remote responses. These behaviors prevented a reliable,
reviewable import into the current schema.

`scripts/import-wikidata-worldwide.mjs` now compiles explicit input bytes. The
source snapshot, existing identity snapshot, required quality-exclusion ledger
and required company-review ledger are hashed in the coverage report. Country codes and regions are audit
metadata; the company table receives its actual identity/provenance columns.
The existing `research_countries` names and regions win, including Turkey in
Europe and Mexico in Latin America. Only missing countries and missing exact
country mappings are proposed. Existing manual mappings are never overwritten.

The subsequent bulk attempt demonstrated a separate admission failure:
Wikidata business/company classes and negative exclusion filters admitted
branches, public institutes, associations and service brands. For example,
[Bank Melli Iran's Baku operation identifies itself as a branch](https://en.bmibaku.az/bank-s-shareholder/),
and the [Czech Notarial Chamber identifies itself as a legal association](https://www.nkcr.cz/en).
Source integrity and coverage checks do not establish a distinct company identity.

At this revision, 110 individually researched companies have been added.
Another 11,000 bulk rows were inserted and passed import-integrity checks, but
remain under a quality hold; automatic approval review blocked the next batch.
An exact-UID rollback has been prepared, backed up and rehearsed. Automatic
approval review rejected its deletion step because explicit user approval to
delete these rows had not been provided. No bulk rows have been removed, and
deletion awaits that approval. The remaining candidates are held for individual
primary-source review; the 25,000-company acquisition requirement is not fulfilled.

### Source contract and quality limits

`--snapshot` accepts a JSON array of normalized source rows or an object with a
`rows` array. Each row identifies its Wikidata Q-id, source page, `CC0-1.0`
license, actual retrieval date/time, source instance-of classes, P17 country
with its ISO code, and P856 official-website values. The row includes source
native industries and inception evidence when available. The compiler rejects
missing or contradictory provenance, non-web URLs, credentials, ambiguous
website hosts, explicit dissolution, conflicting identities for one Q-id and
entries on the supplied quality-exclusion ledger.

`--existing` must contain `{existing, countries, overrides}`. `existing` contains
raw directory identities, including `uid`, `name`, `website` and `country`;
`countries` and `overrides` are the observed Research taxonomy tables. No
migration scraping or hard-coded production row count is used. Exact manual
crosswalk keys retain their case; normalized dictionaries are fallback rules.
ISO codes must be current ISO 3166-1 alpha-2 assignments. New country/source
mappings require review before this snapshot reaches the compiler.

Deduplication uses the existing source Q-id first, normalized hostname second,
and normalized Unicode name plus country third. It applies within the incoming
snapshot as well as against every existing row. Different countries keep
otherwise identical names distinct. Source Q-ids remain lowercase `q123` UIDs;
they are never replaced with website-derived identifiers. Conflicting source
identities are rejected rather than selected by input order.

A source label without a taxonomy mapping can remain a raw `sector`; an absent
sector remains SQL `NULL`. A bare Wikidata P571 date string does not establish
an exact founding year. `founded_year` stays `NULL` unless the source supplies
unambiguous, non-deprecated time statements with year-or-finer precision and no
uncertainty bounds. Inception evidence and all native industries remain in the
source audit, including values that are not promoted to directory fields.

P17 is a country association, not independently verified headquarters. P856 may
contain a former or unreachable official website. Absence of a dissolution date
does not establish current operation. P31 classes remain audit context and
provide no automatic admission. Every candidate must pass the positive review
gate below, including candidates labelled company or business by Wikidata.

`--company-reviews` is a required JSON array of per-Q-id decisions. Every entry
contains `qid`, `decision` (`include`, `hold` or `exclude`), `entity_kind`,
`primary_url`, `reviewed_at`, `notes`, `candidate_sha256`, and `reviewed_identity` with `name`,
`website`, `country` and ISO `country_code`. The four identity values pin the
exact raw snapshot values, before canonical country names or Unicode identity
normalization. `candidate_sha256` also pins the entire parsed candidate row:
object keys are sorted recursively, array order is preserved, and compact JSON
is hashed as UTF-8 SHA-256. Changing any candidate value, including industry,
sector, source evidence or retrieval time, invalidates that approval even when
the four readable identity fields are unchanged. A review of another website
path, name, country or country code does not authorize a changed row.
Repeated Q-ids and malformed reviews fail the
compile. The primary URL must be a usable HTTP(S) URL outside the blocked
aggregation/social hosts; the review date must be valid and no later than
`--as-of`. The compiler cannot determine whether a URL actually contains primary
evidence: the reviewer must read it and record the relevant factual reasoning.

Only an exact matching `include` review with `entity_kind: "company"` can enter
deduplication and coverage. Missing reviews, `hold`, `exclude`, non-company
reviews and identity mismatches are recorded as rejected rows before coverage
is calculated. An empty ledger admits no companies. An explicit exclusion wins
even when a matching positive review is present. No automatic review generation
from Wikidata class labels, company-sounding names or website availability is
allowed.

Review notes must explain the distinct company identity using an official
company legal notice, incorporation/registry evidence or equivalent primary
evidence. Review the full pinned candidate, including whether its sector and
industry values describe the company rather than a product or unrelated item;
do not approve a candidate solely because its identity is valid. Confirm that a country-specific entry is a separately constituted
company before including it as a subsidiary. A branch, product, training
service, trade association or government programme must not become a separate
company row merely because it has its own name or URL. Do not infer dissolution
from acquisition. Record uncertainty as `hold`; collecting enough reviewed
companies to meet coverage does not justify weakening the gate.

The report records both the ledger's original byte hash and semantic hash. The
source audit retains the entire supplied review ledger, including holds and
exclusions, plus the matching review and raw source identity for each accepted
row. Retain those artifacts with the run; do not replace the ledger with a
blanket approval or omit previous holds during a replay.

To start a review, compile with an explicit empty review array. No rows will be
admitted and no migration will be written. Each rejection in the report and
audit includes the candidate's computed hash; accepted audit rows also retain
it. Review the corresponding complete source row, record its primary evidence,
then copy the hash into its explicit decision. The compiler does not generate
include decisions. Use the exported `candidateSha256` helper if a separate
review tool needs the same canonicalization.

The gate also covers exported SQL helpers. `prepareSnapshot` privately records
a fingerprint of each complete normalized row that passed admission and
deduplication. `migrationStatements` and `migration` accept only those exact
objects with unchanged contents. Directly normalized rows, copied/serialized
audit rows, forged review properties and post-preparation identity or sector
edits cannot emit SQL. Re-run preparation against the pinned source and review
inputs when loading a saved audit; audit JSON is evidence, not an admission token.

Keep those holds in `qa_exclusions.json`, an array of
`{qid, reason, evidence_url}` objects. Pass the consolidated ledger on every
compile; `--exclusions` is required and its bytes are hashed in the report.
Review existing holds before replacing the ledger. An explicit empty array is
valid only when the reviewed source has no known exclusions; omission is an
error. The source audit retains the ledger so a later replay cannot silently
lose the recorded reasons.

The Wikidata structured metadata is covered by
[Wikidata's CC0 policy](https://www.wikidata.org/wiki/Wikidata:Licensing).
Referenced company websites retain their own terms. Field-level
`company_sources` rows use `source_type='open_dataset'`, `confidence='low'`, the
actual source retrieval value and `verified_at=NULL`. They do not imply an
independent verification of every imported Wikidata field. The primary review
controls admission and remains in the audit; it does not promote those fields
to verified facts or grant a CC0 license to the primary website. Status notes, source-native industry
IDs and other research context belong in the audit artifact, never in
`metrics_evidence_json`. Funding, revenue, employee, valuation and diligence
fields remain untouched.

### Reproducible generation

Use a fixed review date and the UTC minute when creating the proposed migration:

```sh
node --experimental-strip-types scripts/import-wikidata-worldwide.mjs \
  --snapshot /path/to/reviewed-wikidata-companies.json \
  --existing /path/to/current-company-identities.json \
  --exclusions /path/to/company-quality-exclusions.json \
  --company-reviews /path/to/primary-company-reviews.json \
  --as-of 2026-11-18 \
  --migration-stamp 202611181230 \
  --report /path/to/worldwide-coverage.json \
  --audit /path/to/worldwide-source-audit.json
```

The default migration path follows the repository convention:
`cloudflare-worker/sql/migrations/YYYYMMDDHHMM_7316_research_company_directory_worldwide.sql`.
An existing migration with different bytes cannot be overwritten. The compiler
requires at least 25,000 accepted new identities across 50 countries, no country
over 35%, and at least 1,000 rows each in North America, Europe and Asia and 250
each in Latin America, Africa, the Middle East and Oceania. A failed gate writes
the review report and source audit, exits 2 and writes no SQL migration. Its
report describes proposed records, not a completed database import.

SQL uses bounded statements below 90,000 UTF-8 bytes, leaving room under
[D1's 100,000-byte statement limit](https://developers.cloudflare.com/d1/platform/limits/).
UID, normalized-host and name/country equality probes are separate so SQLite
can use indexes instead of a correlated OR scan. Runtime guards protect
against exact source IDs, host collisions and exact case-insensitive
name/country collisions appearing after the existing snapshot. The offline
Unicode/punctuation dedupe remains the broader identity check, so refresh the
existing snapshot before deployment. The generated SQL adds source evidence
only when the matching directory identity and source provenance agree. Replay
preserves existing financial values and produces no duplicate sources.

### Validation and deployment

Run the focused test with the repository's standard Worker loader:

```sh
node --experimental-strip-types --no-warnings \
  --import ./cloudflare-worker/test/_ts-loader.mjs \
  --test cloudflare-worker/test/research_companies_worldwide_d7316.test.mjs
```

The test builds the real directory, evidence and taxonomy schema from migrations
228, 370, 375 and 376. It imports a synthetic 25,000-company fixture, checks all
coverage gates and statement sizes, replays the SQL, verifies financial/source
preservation, and calls the production `listCompanies` service for pagination,
country-code filtering, missing-sector filtering, founded sorting and facet
counts. Synthetic fixtures are test data only and never count toward source
coverage. Smaller cases exercise invalid provenance, coarse dates, Unicode
identity dedupe, exact manual overrides, explicit exclusions and failed-gate
output. Admission tests cover a missing ledger, unreviewed/held/excluded rows,
changed identity values or other candidate metadata, non-company reviews, a matching positive review,
primary-URL/date validation and review-ledger retention/hashes. The scale
fixture also retains the runtime duplicate guards. Separate emission tests
reject direct unreviewed normalization and post-preparation sector/identity
changes through both public SQL helpers. The scale
fixture supplies synthetic reviews only; those are never production evidence.
Measure the real source snapshot separately on a representative local
D1 copy; local SQLite timing does not establish production latency.

Review the real source audit, rejection reasons, coverage, hashes and SQL before
including a generated migration in the normal reviewed migration/deployment
path. Keep the source artifacts alongside the run record. Compare pre/post
identities and retain the exact UIDs actually added by the deployment. If a
rollback is required, review that exact inserted-UID manifest and remove its
linked `company_sources` rows before those new directory rows, with matching
source and date predicates. Never delete a whole source/date cohort or legacy
228/403 identities. A future 100k expansion requires a separate coverage and
performance review.

The final focused file passed all nine tests in 73.407 seconds, including the
25,000-row fixture through the admission gate and protected SQL emitters. The
synthetic import took 62.859 seconds, replay took 0.757 seconds, and six production
list/facet calls took 0.187 seconds together. The eight small tests also passed
independent review. The focused local tests do not replace the repository build, drift suite or
remote CI. At this revision those full checks have not been run in this partial
review checkout, and PR checks remain queued under Actions queue alert #5719.
No manual CI dispatch, rerun or merge is part of this data/compiler work.
