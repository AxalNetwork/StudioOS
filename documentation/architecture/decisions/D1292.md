### 1. Who decided, recorded

- **`approved_by`.** Approve stores the admin beside `approved_at`. There is no backfill: an article approved before migration 635 has `approved_at` and no recorded approver, and a reader says Not recorded.
- **One audit row per transition**, through `logAdminAction`, as schedule already wrote. So each row reaches both `activity_logs` and HQ's governance feed (`admin_audit_log`), with the author as the target.

  | Action | When |
  | --- | --- |
  | `article.start_review` | submitted → in review |
  | `article.approve` | submitted or in review → approved |
  | `article.request_changes` | → changes requested |
  | `article.reject` | → rejected |
  | `article.publish` | approved → published; `via` is `manual` or `schedule` |
  | `article.unpublish` | published → approved |
  | `article.returned_to_submitted` | an edit sent it back (§3) |

  - A row holds the article id, the two statuses, the author and, on an override, the override and its reason. It never holds the article's text, a comment, or the reason given for requesting changes or rejecting.
  - A row is written only when the update changed the article. Each transition's `UPDATE` is now conditional on the expected status, so two admins deciding at once change the row once and audit it once; the loser gets 409.
  - The scheduled publish is recorded as the admin who set the time (`publish_at_set_by`), as its revision already was (D484).

### 2. No admin approves or publishes their own article

Approve, publish and schedule check whether the decider is the article's author (`selfApprovalCheck`):

| Who | What happens |
| --- | --- |
| An Admin on their own article | 403 `self_approval`: "You wrote this article, so another admin must approve and publish it. Ask another admin. Nothing was changed." |
| A Super Admin on their own article, with no reason | 403 `self_approval_reason_required` |
| A Super Admin on their own article, with `override_reason` (at least 8 characters) | Allowed. The audit row carries `self_approval_override: true` and the reason. |
| Anyone on someone else's article | Unchanged |

- **Schedule is included** because a publish time is a publish carried out later. Clearing a time publishes nothing and stays open to the author.
- **The author page's chain** (`ArticleAuthorPage.jsx`, Publish now: submit → approve → publish) follows the rule through `publishChainFor`:
  - on an Admin's own article, the button is gone and the page says "You wrote this. Another admin approves and publishes it.";
  - on a Super Admin's own article, it opens an in-page dialog for the reason, then sends it with approve and publish;
  - on someone else's article, it runs as before.

### 3. An approved text cannot change under a schedule

`PUT /api/articles/:id` on a `submitted` or `approved` article:

- **A save that changes no stored value changes nothing**, and returns `returned_to_queue: null`. The editor, and the chain, save every field each time, so an unchanged save must not reset an approval.
- **A real change sends the article to Submitted.** From `approved` it also clears `approved_at` and `approved_by` (the approval was of a text that no longer exists). It always clears `publish_at` and `publish_at_set_by`, so the cron cannot publish it.
- **The response carries `returned_to_queue`:** `{ from, publish_at_cleared }`.
  - The author page says it ("Edited after submission: it is back in the review queue, and its publish time was cleared.").
  - From `approved`, the author is also notified in the app (`author_back_to_submitted`) and a revision is saved.
- **The update is conditional on the status it read.** An edit cannot land on an article an admin approved or published in the meantime; it gets 409 `status_changed` and saves nothing.
- `in_review` stays locked (`locked_for_review`), and drafts are unchanged.
