### 1. What was decided

**Three forms fill through the existing routes.** They use the sheet, run, record and undo routes (`GET /api/fills/sheet`, `POST /api/ai/rail/run` with `form:<form>`, `POST /api/fills/record`, `POST /api/fills/:id/undo`), as D1329's other profiles do.
- Each form fills one composition field, with source `eadwyn`.
- Each runs under its own route's write gate.
- There is no new route and no new client method.

| Page | Form | Field | Label | Writes |
|---|---|---|---|---|
| Investor · Portfolio · Value-add | `support` | `summary` | What happened | `portfolio_support_entries.summary` |
| Operating Partner · Offers · Catalog | `offering` | `summary` | Summary (what the founder gets) | `service_offerings.summary` |
| Operating Partner · Offers · Perk deals | `perk` | `blurb` | One line founders see on the card | `perks.blurb` |

The entries are in `services/fills/fields.ts` and its SPA copy, `frontend/src/lib/fillFields.js`. Each column has its own scoped undo in `services/fills/keep.ts` `UNDO_WRITES`.
- The undo stamps `updated_at` as an ISO string, as these three routes do.
- A support entry's summary is required, so an undo with nothing to put back is refused (`no_prior`).

### 2. Not listed, on purpose

- **Support's `outcome`.** An outcome is a result, and D1329 never fills a result.
- **Support's `hours`.** Hours are a measure.
- **The perk's `detail`.** Its own hint says it carries "any conditions", which are terms.
- **Every price, value, credit and cap:** `price_usd`, `price_cents`, `value_cents`, `credits`, `claim_cap`. These are money.
- **The offering's title and category, and the perk's offer.** Each is the member's own call about what they sell.
- **The perk's partner name.** It is an identity.

A model output that names any of these is dropped, either as `never_fill` or as `unknown_field`.

**The canvas's other "after Worker support" triggers get no entry.** S1 records this in D1424:
- **Add LP:** a name, an email and a commitment. That is identity and money.
- **New call:** its only text is Purpose, which is the reason for a money act.
- **Block a date range:** its only text is the block's reason, and the addendum allows no trigger on a reason.
- **New brief:** it is itself a question to Eadwyn.

### 3. Each gate, shared with its route

The three route gates now live in `services/profileWriteGates.ts`. They moved there unchanged in behaviour, and each route and its fill scope call the same function. Nothing re-derives a gate a second way.

- **`supportBookIds`** is `routes/portfolio_support.ts`'s `scopeFor`: the investor's accessible book (`investorProjectIds`). **`inSupportBook`** checks `empty` first, so an empty book never falls through to the operator branch.
- **`offeringOwned`** is `routes/services.ts`'s `ensureOwnerOr404`: the owner, then the active company. An admin passes.
- **`myPerk`** is `routes/perks.ts`'s own: the partner's listing, narrowed by the active company.

The routes keep thin wrappers with their old names.

**`services/fills/scopes.ts` adds three `RECORD_SCOPES` entries.** Each read is one literal statement that binds the id alone.

| Table | Parent of an Add form | Writes (gets the trigger) | Reads marks only | Everyone else |
|---|---|---|---|---|
| `portfolio_support_entries` | `project:<id>`, the project the entry is logged against | an investor whose book holds the project | an admin: no admin trigger (D1329, #2431 question 5) | answered as if the record did not exist |
| `service_offerings` | `owner:<id>`, the caller (`own`) | the owner, under `offeringOwned`'s company rule | an admin | the same; the public catalog's readers get no marks |
| `perks` | `owner:<id>`, the caller (`own`) | a partner, on a listing `myPerk` returns | an admin | the same; founders who browse perks get no marks |

`ParentKind` widens to include `'project' | 'owner'`, and `parentKey` files proposals as `project:<id>` and `owner:<id>`.

**Two additions to the scope contract:**
- **The active company.**
  - The three route gates each read the request's verified active company (`activeCompanyFor` / `investorActiveCompany`, both `resolveActiveCompany` on the `X-Company-Id` header).
  - So `RecordScope.access` takes an optional `ScopeContext` with `activeCompany()`. `routes/fills.ts` and `routes/rail_run.ts` both pass it.
  - Without a context, the three new scopes answer nothing. A caller that forgets the context fails closed, never wide.
  - D1329's scopes ignore the context.
- **Concealed.**
  - The three new scopes are `concealed`. A caller who may not read the record gets `404 record_not_found`, the same answer as for an id that does not exist. They never get `403 record_not_available`, which would confirm the record is someone else's.
  - A caller who may read but not write (an admin) still gets `403 record_not_available` from the run, and `can_fill: false` from the sheet.
  - D1329's scopes keep their 403.

### 4. What a run reads

`services/fills/formRun.ts` `gatherScoped` reads only the caller's own records, never a figure:
- **support:** the company's name, and the caller's own last 10 entry summaries for that project (`recorded_by = caller`). A colleague's entries on the same company are not read.
- **offering:** the caller's own offering titles, at most 40.
- **perk:** the caller's own perk offers, at most 40.

### 5. Rows mode stays off

None of the three forms offers "add several rows". `POST /api/ai/rail/run` now refuses `input.rows` for any table with no `ROW_REQUIRED` entry with `400 rows_not_offered`. The refusal comes after the scope check and before any quote, so nothing is held. `ROW_REQUIRED` is unchanged.

### 6. Metering

There is no new AI task. These are `form:` runs:
1. task `rail_write`;
2. `quoteRun` before the run (SSE `meta { model, hold_microusd }`);
3. `run()` holds, guards and settles.

Out of tokens, AI switched off and budget refusals all pass through `runRefusalView` unchanged. An Explorer (`no_profile`) and a support session (`support_session_refused`) are refused before any quote.
