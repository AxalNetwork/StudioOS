## D5366 — Company project writes pass the company-seat gate (#5366)

**Decision (2026-11-10).** A project inside a company is still governed by its existing project authority, and every mutation of that existing project first passes `companyWriteDenial`. A support session writes nothing. A platform admin using HQ access without a company seat writes nothing. An Admin, Owner or Founder seat (or the primary-admin seat) passes the company boundary and the route's existing project rule then decides the action. Standalone projects keep D889 unchanged.

This applies to project data, its roster and invitations, lifecycle operations, and company-scoped agent-team management. `GET /api/projects/:id/members` returns `can_edit`, `can_manage` and `write_reason`; Portfolio › Company settings › Projects follows that server answer, so a cached account role cannot re-enable a link or button.

**Boundary with #5329.** This decision owns only the company-scope branch of agent `canManage` and the company boundary around project writes. It does not widen project authority. Project-scope `isProjectManager`, its callers, and any future company-editor project authority remain #5329's work.

**Verification.** `company_project_write_gate_5366.test.ts` calls project data, roster and lifecycle endpoints as HQ without a seat, support, an Admin with a seat, an editing member and a non-editing member; refused calls assert that no row changes. `team_agents_d1496.test.ts` covers the company agent-team gate. `portfolio_d1413.test.mjs` mounts the Projects tab and proves the server capability wins over the cached role.

**Narrowed by D5525 (2026-11-11).** Creating a project in a company refuses only a support session and HQ access without a seat; a Member seat of any role may create one.
