### 1. Where the lifecycle lives (option A on #5058)

The issue named two stores, and option A was taken (S26 and S1 both picked it).

- Each Founder, Investor, Operating Partner or Advisor licence is a `licences` row: family `user`, holder `user`,
  holder id the account. Its status, dates and `revision` are that row's, under D5057's triggers: the identity is
  frozen, every change moves `revision` by one, and nothing is deleted.
- `account_licences` (D4472) stays what access reads. Every lifecycle write updates it in the same batch, so the
  union and every predicate built on it are unchanged.
- **The primary licence** is still `users.role`. The migration backfills a `licences` row for it as its identity
  and lifecycle record. When that row is not in an access status, `heldLicences` leaves the primary licence out.
  A database with no row (one migrated before D5058) holds it as before.
- **Types.** `account_licences.licence` says `partner` and `licences.licence_type` says `operating_partner`. They
  are the same licence, mapped one to one (`ACCESS_KEY`).
- **One row per licence per account** (a partial unique index). A renewal is the next term, never a second
  licence.

### 2. Holder rules

- An account may hold several user licences at once, and each has its own status and revision.
- A write names one licence. It changes that row and that licence's own access row, and nothing else the account
  holds: the access write is filtered by licence and guarded by the licence row reaching the new revision.
- **Admin is never a licence.** Nothing here writes `users.role`, no lifecycle action names Admin, and a test
  suspends all four licences of one account and reads its role back unchanged.
- **The account boundary is D4472's:** an Admin, and a Super Admin for another administrator's account.

### 3. Lifecycle

| From | To |
| --- | --- |
| proposed | active (`activate`), terminated |
| active | suspended, renewal_pending, expired, terminated |
| suspended | active (`resume`), expired, terminated |
| renewal_pending | active (renew), expired, terminated |
| expired | active (renew, with a new term), terminated |
| terminated | final, except that an Admin's D4472 re-grant re-opens an additional licence |

- Access is held while the licence is `active` or `renewal_pending`, because its current term is still in force.
- **Every write names `expected_revision`.** The licence row changes only when its revision and status are still
  the ones read; otherwise it is 409 `licence_changed` with the current row, and nothing is written.
  - The licence row, the event and the access row are written in one batch, each guarded by the one before.
  - Two writes from the same revision at once: one lands, the other is refused (tested).
- **Every change records:**
  - which licence;
  - from which status to which;
  - at which revision;
  - why, since a reason is required;
  - who.
  These go in `user_licence_events`, which is append-only. A backfilled row has one `backfill` event.

### 4. Renewal

- A renewal is an explicit act, `POST /api/admin/user-licences/:uid/renew`. It takes the next term's dates, its
  renewal terms and the agreement version it is signed under.
- It adds a `user_licence_terms` row, which is append-only. Earlier terms and their agreement versions stay as they
  were signed.
- A term that starts before the current one began is refused. A terminated licence is not renewed.
- **Nothing extends a term by itself.** There is no scheduled extension; expiring and renewing are both people's
  acts.
- Replacing an agreement is naming a new `agreement_version` on the new term. Signing that agreement is #5048–#5060's.

### 5. Owner answers, 2026-11-09 (#3704 C, D, G)

These were given on #3704 (closed) and relayed by S1 on #5058; this file is where they are recorded.

- **C = A.** Only an Admin grants a second licence. The member's Licences page keeps "Contact Axal VC"
  (`how: 'contact'`). There is no self-service add and no request-and-approve flow. No checkout is built.
- **D = A.** An appointed Admin keeps the paid licences and plans they already hold. The `retainPrimary`
  appointment path is unchanged, and it writes no lifecycle change to the licence the person holds.
- **G = A.** Each licence is billed separately, at its own list price, with no bundle price. A renewal or
  suspension of one licence never changes the price or term of another: each write touches one licence.

D4472's "deferred" wording for second-licence purchase now reads "Admin grant only (owner, 2026-11-09)".

### 6. Routes

All three are Admin routes under D4472's boundary:

- `GET /api/admin/accounts/:id/user-licences` returns the licences, each with its terms, and the account's history.
- `POST /api/admin/user-licences/:uid/status` takes `{ action, expected_revision, reason }`. It is audited as
  `user_licence_status_changed`.
- `POST /api/admin/user-licences/:uid/renew` takes `{ expected_revision, starts_on, ends_on?, agreement_version?,
  renewal_terms?, reason }`. It is audited as `user_licence_renewed`.

Granting and revoking an additional licence stay D4472's routes. `grantLicence` and `revokeLicence` append the
statements that keep the shared row in step, guarded by the grant or revoke having landed:

- a grant creates the licence or re-opens the one already there;
- a revoke terminates it;
- the event is recorded either way.

A database without D5058's tables (a test built from the baseline and D4472's migration alone) skips them.

### 7. Considered and not built

- **Entitlements derived from a licence** are #5059's. The access union is unchanged here.
- **The Licences and Contracts UI** is #5060's. No frontend change is in this decision, and no client method is added.
- **Option B** (status and terms on `account_licences`) would have needed a second migration of the same data once
