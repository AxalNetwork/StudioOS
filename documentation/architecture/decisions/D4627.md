## D4627 — Validate evidence accept: proposal identity is the idempotency key, not a status flag alone (#4627)

Parent #4584, phase 2 of #4584's sequence. Coordinates with #3731 (the shared PostHog coordinator) and the ordinary fill registry (#188, D690 decision 12).

### What was wrong

**PostHog `acceptProposal` (`services/posthog/metrics.ts`) called the acceptor before claiming the row.** It read the proposal as `pending`, ran the acceptor — which writes a real experiment and links it as evidence, through two separate writer calls with nothing wrapping both — and only THEN tried to flip the status to `accepted`, checking `WHERE status = 'pending'` but never checking the update's affected-row count. Two overlapping accepts both read `pending`, both ran the acceptor, and both got a 200: the conditional update's own `changes` were `[1, 0]`, but the second writer call had already happened by the time either update ran. `dismissProposal` had the same shape of gap the other way: it read the row as `pending`, then wrote `status = 'dismissed'` conditioned on `status = 'pending'` but never checked whether that write actually changed anything, so a dismiss that lost a race to a concurrent accept still answered `ok`.

**The ordinary accept route's compensating revert was real, but target creation under it was not idempotent.** `routes/founder_validate.ts`'s accept route already claims the proposal atomically (`UPDATE … WHERE status = 'pending'`, checked by `claim.meta.changes`) before writing, and already reverts the claim to `pending` when the write throws — this part matched the issue's own quoted source closely, line numbers aside. But the write it guards is `spec.apply()` (which, for the `hypothesis` kind, calls `insertHypothesis` — a plain `INSERT … SELECT` that allocates the next `Hn` from the highest code ever used) followed by `recordFill()`. A failure between the two — `apply` succeeds, `recordFill` throws — reverted the proposal to `pending` but left the just-created hypothesis in place, addressable by nothing. A retry called `apply` again and allocated a second `Hn`, so one proposal could end up having created two hypotheses, one of them permanently without provenance.

Both are the same root cause: a proposal's own identity was never the thing target creation checked against. Status alone cannot carry that — a status update changes a row that already exists; it says nothing about whether the creation of some OTHER row (the target) should be allowed to happen again.

### What changed

**The idempotency key is the proposal's own id**, carried to the one write that can duplicate a target, checked before that write runs again:

- **`hypotheses` gains `source_proposal_id`** (migration `202611081112_validate_accept_idempotent_targets.sql`), nullable, unique only where set (a partial index) — every hand-typed and Pivot-created row stays `NULL` and untouched. `routes/founder_validate.ts`'s accept route now passes `proposalId: row.id` into the `FillContext` it hands `spec.apply`; the `hypothesis` kind (`services/fills/registry.ts`) passes it through to `insertHypothesis`. That function CHECKS the column first — `SELECT … WHERE project_id = ? AND source_proposal_id = ?` — and only inserts when nothing is found; a hit updates the existing row's `claim` and returns its id and code unchanged. This is deliberately a check-then-act, not an `ON CONFLICT` upsert: a test fixture that rebuilds `hypotheses` from the baseline plus migrations' bare `ADD COLUMN` lines (several worker test files do this) never replays a migration's `CREATE INDEX`, so an upsert that targeted the new partial index would throw there while working in production. The check is still correct without a race, because the ONLY caller that passes `sourceProposalId` is the accept route, which has already claimed the proposal atomically before calling this — two requests can never reach the check for the same id at once. The unique index stays as the defensive invariant: a bug that somehow still produced two rows for one proposal is a 500 on the second INSERT, not a silently accepted duplicate.
- **`hypothesis_experiments` gets no schema change.** It is migration 460's alone to touch — `validate_writes_d690.test.ts`'s own guard fails the build if any other migration names that table at all, column or not — so D4627 reuses the column 460 already made unique: `uid TEXT NOT NULL UNIQUE`. The PostHog `experiment_evidence` acceptor (`services/posthog/validate.ts`) now calls `addExperiment` with `sourceProposalId: row.id`; `addExperiment` (`services/validateWriters.ts`) builds a deterministic `uid` (`posthog-proposal-<id>`) from it instead of `crypto.randomUUID()`, and `INSERT … ON CONFLICT(uid) DO UPDATE SET …` — safe to target with `ON CONFLICT` everywhere, because the constraint comes from the table's original `CREATE TABLE`, not from an `ADD COLUMN` a narrower fixture could have skipped. `addEvidence` (same file) already upserts on `(hypothesis_id, kind, ref_id)`, so a retry's second call is a no-op repeat, never a second link.
- **The PostHog coordinator claims BEFORE calling the acceptor**, mirroring the idiom `founder_validate.ts` and `routes/pipeline.ts`'s `decision_gates` already use: `UPDATE posthog_proposals SET status = 'accepted' … WHERE … status = 'pending'`, checked by `claim.meta.changes`, runs first; a losing caller never reaches `acceptor.accept` and answers `'decided'`. A throw after the claim (the acceptor refusing, or a writer failing) reverts the claim to `pending` — recoverable because the writes it may have already made (the experiment, by its deterministic uid; the evidence link, by its own upsert) are themselves safe to repeat. `dismissProposal` now checks its own write's `meta.changes` and answers `'decided'` rather than `'ok'` when it loses a race to a concurrent accept — the same lie the other way round.
- **Why not a D1 transaction or batch.** `env.DB.batch()` runs several PREPARED statements atomically, but the statement that records provenance (`recordFill`, and the PostHog evidence link) needs a value the FIRST write only produces at execution time — the newly allocated `hypotheses.id`/`code`, or `hypothesis_experiments.id` — and a batch cannot thread one statement's result into another's bind parameters. SQLite also has no writable-CTE form that would let one `INSERT … RETURNING` feed a second `INSERT` in a single statement. So this is the "explicit recoverable operation state with idempotent stages" the issue names as the alternative: claim first (atomic, checked), write with an idempotent key, recover by retry rather than by rollback.

### Why the issue's own line numbers moved, and what checking against current `main` found

The issue's audit (commit `d85951ca9`, 2026-11-06) is six commits old relative to `main` at the time of this PR. Reading each named file as it stands now:

- `services/posthog/metrics.ts`'s `acceptProposal`/`dismissProposal` matched the audit's description exactly — the race is real and current, just at slightly different line numbers.
- `routes/founder_validate.ts`'s accept route (around lines 860–987 now, not 939–977) already has the claim-before-write ordering and the revert-on-throw the audit's own evidence assumed was missing context for; what it still lacked is idempotent target creation under that revert, which is the actual bug the issue's "General proposal partial failure" section describes. The PR's fix is scoped to that gap, not to the claim/revert mechanism, which already existed and is already covered by `founder_validate_proposals.test.mjs`'s source-shape tests.
- `services/fills/registry.ts`'s `hypothesis.apply` and `routes/_founder_validate_writes.ts`'s `insertHypothesis`/`insertHypothesisStatement` matched the audit.
- `services/fills/provenance.ts`'s `recordFill` matched the audit; unchanged by this PR — it still throws before writing on a never-fill field, and the accept route still reverts on that throw.

### Acceptance criteria

- ✅ Two overlapping accepts resolve to one target and one evidence/provenance set; a losing request gets an explicit conflict (`'decided'` → 409), never a silent second write.
- ✅ Accept versus dismiss settle on one outcome; the loser sees `'decided'`, never both reporting success.
- ✅ A failure after target insertion, before evidence/provenance, is recoverable without a duplicate target (ordinary route: `insertHypothesis`'s check; PostHog: `addExperiment`'s deterministic uid).
- ✅ A failure before the proposal's own completion is recoverable without duplicating the target or the evidence link (PostHog: both writers are idempotent on retry; ordinary route: same).
- ✅ Retrying a failed ordinary hypothesis proposal yields one hypothesis and the correct provenance.
- ✅ Accepted target references, human edits (`editableField`) and source provenance remain attributable — untouched by this PR; `recordFill` still runs exactly once per successful accept.
- ✅ Behavioral tests use concurrent requests (`Promise.all`/`Promise.allSettled` against the real coordinator and the real route, not source-text ordering) and fault injection (a wrapper that fails one specific statement once, then lets the retry through) against real writers.
- ✅ Validate-specific changes do not regress other modules on the shared coordinator: the `acceptProposal`/`dismissProposal` fix is in `metrics.ts` itself, so `build.ts`'s and `grow.ts`'s acceptors (registered through the same functions) get the same claim-first ordering for free, with no module-specific code. `posthog_build_d1606.test.ts`, `posthog_grow_d1608.test.ts` and `posthog_raise_d1607.test.ts` still pass unchanged.
- ✅ D5352 closes the remaining target-creation retry gaps under that shared claim/revert mechanism: PostHog `survey_signal` and `survey_feedback`, plus ordinary `competitor` and `feedback_theme` accepts, all key their target stage to the proposal before a retry is allowed.
