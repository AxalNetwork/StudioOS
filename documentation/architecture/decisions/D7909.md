### Service and configuration

The existing dedicated Worker exports RepoControl and CapacityControl. Its new
CAPACITY_CONTROL binding and appended `v2-capacity-control` SQLite migration do
not alter the RepoControl namespace or v1 migration. Public capacity routes
forward to one repository-named object; this is the coordination atom for its
bounded requests, reservations and owned generations. There are no studioos
D1/KV/assets bindings or production imports.

Configuration defaults to CAPACITY_ENABLED=false, CAPACITY_PUBLICATION=pilot,
a fixed audience and an empty CAPACITY_CONFIG. The object also requires its
independent authenticated owner switch to be cleared. Status is authenticated;
missing bearer shape, unknown paths and disabled ingress refuse before object
lookup. The protected namespace owns authentication, admission, result storage,
reconciliation and durable publication. Alarms survive eviction and are armed
before accepted submission/result writes. Owner recovery remains separate.

The pilot runtime admits one active request globally, not merely two external
shards per request. Failed requests with uncertain cleanup still hold that
admission slot. It excludes Macs, refuses github-8 configuration and leaves
its included capacity at zero. Missing/unreadable inventory chooses hosted;
that is not evidence of two qualified Linux machines.

CAPACITY_CONFIG contains the exact repository ID, installed App ID, approved
main executor SHA, separately pinned reusable planner SHA, group 5, explicit
Linux-only profile selection, the exact prerequisite job names, at most two
external Worker shards, zero included shards, and publication=pilot. The
installed repository App token request is limited to actions/checks/contents;
organization inventory uses a separate bounded read-only credential and a fixed
group-5 API allowlist. Provisioning either credential is an operator action,
not part of this code or local tests. Config/binding types are regenerated by
the project's Wrangler command. Existing deployment controls stay untouched.

### CI caller and identities

The plan job can emit bounded metadata only when an explicit main-push pilot
flag is enabled. Its optional metadata step has no OIDC grant and cannot make
ordinary plan/test jobs depend on external execution. The separate reusable
planner job submits once and exits; it has no polling/waiter loop. The initial
caller is main-push only, so queue and pull-request execution stay unchanged.
Candidate package scripts and plan files are read, never imported or executed
by the trusted planner. A single open descriptor bounds actual file bytes,
rejects symlinks/special files and handles growth after fstat. Metadata and
network JSON have byte/chunk/deadline bounds.

The caller literally pins the reviewed planner package commit; executor and
planner revisions are independently configured and independently authenticated.
This avoids requiring a workflow to contain its own commit SHA. An unpublished
local pin is a prepared artifact, not an available live dependency: it must
undergo the existing publication/intake process before enablement. The actual
caller pin, final head/tree and dependency set accompany the delivery manifest.
S09's proposed additional child-workflow identity still requires its exact
source and review; this preparation keeps the existing exact child provenance.

The ordinary six hosted Worker matrix parts continue under their original
checks. The pilot allocator additionally accounts for its own two Linux and
four hosted children; its separate report is comparison evidence. It does not
skip two required matrix contexts or silently promote pilot results into them.
Any later optimization/reuse or cutover requires coordinated consumer changes.

### Result delivery and remaining S09 integration

A prepared OIDC-authenticated supervisor callback stores canonical, complete
receipt/job-bound outcomes in the authority. Job identity is corroborated by
current independent GitHub run/job reads; JWT check-run identity is not assumed
to equal an Actions job ID. No arbitrary request supplies a trusted reader, and
no raw log or bearer token is stored. Historical receipts can attribute late
negative results; stale generations cannot grant new positive authority.

Known failure fences the aggregate before acknowledgement and remains sticky,
including while cleanup is unknown. Cleanup and export truth remain separate.
The actual pilot reader requires authenticated result evidence: a green outer
Run step alone cannot fill in a missing result. Missing evidence, failed export,
unknown cleanup and typed infrastructure/timeout outcomes never become success.
Successful publication also needs the independently observed exact whole job
and Run step to complete inside the immutable lease. Persisted receipt ownership
and current provider observations are checked again after restart. Stored
execution facts keep their original server receipt time; a fresh authority read
is not a claim that a native inspection was rerun.

The callback helper is for reviewed supervisor code outside candidate execution.
S09's final result-envelope normalization and invocation must be agreed against
the actual cumulative source before this becomes a supported executor path.
No workflow permission expansion, native reader or real hosted boundary is
assumed. Hosted verification still defaults to refusal without its genuine
trusted provenance and credential-denying boundary readers. Source preparation
and simulated callback tests do not supply those readers.

### Recovery corrections

Check publication adopts an exactly matching App/external identity after a
lost response. A missing pre-POST intent can retry only after repeatedly
observed absence and a delay, with two total create attempts. Duplicate or
unreadable identities never authorize publication. GitHub has no check-run
idempotency key: a remote request with an indefinitely ambiguous outcome cannot
be proved absent by a local timer. Such exhausted/duplicate cases remain
unresolved and keep recovery scheduled; this is not an exactly-once claim.

Moving-main dispatch discovery now retains a uniquely owned unexpected child
for cancellation only. Its unreviewed revision can never acquire a receipt or
supply test truth. Its cancellation identity is persisted before the cancel
request. Only independent no-test/cleanup proof can settle that execution;
API acknowledgement alone cannot trigger fallback. Definitive preflight refusal
is distinguished from a possibly sent dispatch. Remaining cancellation and
latest-full-fallback constraints from D7973 part 2 are preserved.
