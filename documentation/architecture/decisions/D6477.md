## D6477 — Main repair: when main is red, the bot takes the existing repair issue and opens exactly one repair PR (#6477)

- **Status:** built 2026-11-18. Part of #5600 (plan key C6). Built on #6467 (C1) and #6473 (C2), both on main.
- **Why:** a red main turns every PR and queue entry red within minutes. On 2026-11-14 it was red for almost two
  hours on one guard, and 19 queue runs failed for it. D5398 says one repair. The alert workflow (D6387) already opens
  a repair issue that a session may take, so the bot must never open a second repair beside a session's.

### Four jobs

| Job | Environment and token | Runs a model | Runs repository code | Writes |
| --- | --- | --- | --- | --- |
| `plan` | `landing-bot`; `GITHUB_TOKEN` read; an App token with `metadata: read`, for the bot's login | no | no | artifacts only |
| `claim` | `landing-bot`; the App token (contents, for the claim ref; issues) | no | no | the claim ref, one comment, a label |
| `repair` | the model runner (#6473) on `main`: `edit` in `repair`, `verify` with no secret | yes | in `verify` only | nothing on GitHub |
| `apply` | `landing-bot`; the App token; no model key; scripts from main | no | no | its own `repair/main-*` branch, one PR, labels, one comment |

- **Who owns the repair.** A `claim/<n>` ref (expired or not: `claim.mjs` refuses a claim while one exists),
  `state:in-progress`, `needs-session`, a linked open PR, or any open PR labelled `main-repair` or on a `repair/main-`
  branch means one comment (the landing bot's sticky comment, edited in place) and nothing more. Otherwise the bot
  claims the issue with `scripts/claim.mjs` before any model call. A claim it loses means it steps aside.
- **Attempts are per failure fingerprint** (the job without its suite part, plus the test), whatever the commit, as
  `attempts()` counts them. They are recorded as an artifact named after the fingerprint's hash, uploaded before the
  model is called. After two, the bot proposes a plain revert instead of a third model run.
- **The patch is re-checked with main's code.** `checkPatch()`, `pathGuard()` and main's `merge-policy.mjs` run on the
  committed diff. Any change is refused to an existing test, the failing test, a guard script (`scripts/check-*`,
  `scripts/ci/`, the landing bot), a baseline, an allowlist, a migration or a protected path. The easy wrong fix for a
  red guard is to edit the guard.
- **The fallback is a plain revert of the first red commit:** the oldest red push since the last green one. It must
  have one parent, apply cleanly, and contain no migration and no protected path. Otherwise the bot comments, releases
  the claim and labels the issue `needs-session`.
- **One PR, owner-landed.** The PR says `Part of #<issue>`, names the suspected commit and carries `main-repair`. The
  bot then releases its claim and labels the issue `state:review`: the open PR now marks the repair as taken. Nothing
  queues or merges it.

### Deviations from the issue

- **No `workflow_run` trigger (option A, built).** WF-4 in `frontend/test/workflow_security_4571.test.mjs` admits
  `workflow_run` only in `TRUSTED_WORKFLOW_RUN`, and requires each entry to refuse every run that is not a
  `pull_request` run. A push to main is exactly what this needs. So the workflow sweeps every 10 minutes and on
  dispatch, as the ejection handler (#6476) does. `confirmRed()` applies the issue's gate to the run data: a
  completed `push` run, `head_branch == 'main'`, head repository equal to this one, and failed. The cost is up to 10
  minutes before the plan starts.
  - **Option B, not built:** a `workflow_run` trigger on CI, with WF-4 widened to admit push-to-main entries. That
    changes a security guard, so it is the owner's call.
- **Named `landing-bot-main-repair.yml`**, not `main-repair.yml`. #6467's `dispatchable` list names each kind's
  workflow `landing-bot-<kind>.yml`. The concurrency group is `main-repair`, as asked.
- **The daily cap on repair PRs is `LANDING_BOT_DAILY_PUSHES`** through `budget()`, counted from `repair/main-` PRs
  opened today. Each repair PR is one push. No new variable was added.
- **"#6468 (D1) migration"** is read as a Cloudflare D1 schema migration: anything under `cloudflare-worker/sql/`, a
  `migrations/` folder, or `backend/app/models/migrations.py`. #6468 (plan key D1) is the WIP report and defines no
  migration rule.
- **Breakers.** Only `[alert] the Actions queue is backed up` stops main repair. `[alert] main is red` is why it runs,
  and a stalled merge queue is what a red main causes.

### Known limits

- `apply` builds on main's head when it runs. A patch made from an older main is refused by the before-hash
  re-check if a patched file changed in between; it is never applied to a different file.
- The fingerprint comes from the logs of the first three failed jobs. A failure the triage rules do not recognise is
  fingerprinted by its job and step, and its repair needs a reproduce command, or it goes straight to a revert.

### Tests

`frontend/test/landing_bot_main_repair_6477.test.mjs`, on fixtures with no network:
- a session's claim, an `in-progress` label, a linked PR or a repair PR means a comment and no bot PR;
- a second red push with a repair PR open creates none, at plan and again at apply;
- an infrastructure verdict creates none, and neither does a green push after the red one;
- a patch that deletes or loosens the failing test, or edits a guard, baseline or allowlist, is refused;
- a revert containing a migration is refused and handed back;
- five red commits with one fingerprint allow at most 2 model runs;
- the plan, claim and apply jobs end to end, with stub reads and real git;
- the workflow passes `assertWorkflow()`, its model job has no write, and its apply job has no model secret.
