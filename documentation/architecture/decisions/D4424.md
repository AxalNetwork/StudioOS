## D4424 — Outside assistants as proposal-only team agents (#4424)

Owner decision, 2026-11-04; part of #3727. An outside assistant connected to
`https://axal.vc/mcp` is its own team agent. It can propose; a person decides.
It gets no direct write tool and does not change D665's member write rules.

### Identity and storage

An outside agent has `source = 'mcp_client'`, `model_id = 'external'`, no
persona, and the connected app's name. Existing agents default to `platform`.
It occupies the existing one-live-role-per-scope seat. The connecting person
is its sponsor. The existing positive cap column holds a sentinel of one
microusd for these rows, not a budget or a charge; the finished client must
show “Runs on your own assistant” instead of that column.

`team_agent_mcp_bindings` binds one agent to the sponsor, OAuth client and
provider grant. It stores no bearer or secret. A fresh opaque binding UID goes
in encrypted authorization props and in provider metadata. The provider's
`completeAuthorization` returns only a redirect; the trusted consent handler
must resolve the new grant by that metadata before completing the binding.
Uncompleted bindings are not callable and can be cancelled. Binding/revocation
and the corresponding agent/events/proposal changes use D1 batches.

`GrantProps.keyUid` is a member API-key identity, not an OAuth grant id. Do not
reuse it for OAuth. A token or client name supplied as a tool argument never
establishes agent identity. Each request must recheck the encrypted binding,
client, sponsor, actual provider grant id, active agent, current Team manage
gate and feature flag. A missing or revoked binding refuses, even while KV
revocation propagates. Removing the agent or revoking from Connected apps
first invalidates D1, then revokes the provider grant; a failed provider call
is retryable and cannot restore D1 access.

### Scope and action rules

Consent's current “companies” are `projects.id`. Team company scopes are
`company_profiles.id`; these identities must never be conflated. Choose a
real company through `loadScope` and `canManage`; project reads additionally
retain the original grant's project allow-list and sponsor's live access.

Only explicitly mapped read tools allowed by the role's current rule book
and TM8a's inherited company allow-list may run. Unmapped tools fail closed.
The shared MCP boundary must intercept calls before any tool runs or holds
model funds. Direct writes refuse. Supported proposal tools must leave only
`ai_rail_proposals` with `agent_id` and the sponsor's `user_id`, after existing
safety checks, and record an agent event. The existing Team decide route
records the human decider; it must never execute an arbitrary queued tool.
The assistant pays its own model costs, with no team-cap or sponsor-model
charge. No new direct write tool is added.

### Connection screens

Team Add agent offers “Connect an outside assistant”, with the server address
and consent steps. Consent says “Act as a team agent for <company>”, shows
the role and proposals-only boundary, and allows only manageable companies.
The connected card has the app's name, AI-agent mark and “Runs on your own
assistant”. Product copy says “outside assistant” and “connected app”.

The existing TM3b canvas draws a platform model and read-only tool grants,
not this connection flow. The new choice, role/consent states, card, expiry,
refusal and unreadable states need an approved canvas at 390px and in dark
mode before the frontend is built (AGENTS.md “Missing UI”).

### Integration boundaries and current delivery

This first delivery is the additive migration and isolated binding/lifecycle
service with real SQLite tests. It exposes no route and enables no outside
assistant. It deliberately does not modify S31's shared files while #4422 /
#4445 owns `mcp/server.ts` and `routes/team_agents.ts` (AGENTS.md file ownership).

Remaining work: land/agree S31's restrictive agent-context/allow-list seam;
integrate consent and per-request identity, role/read mapping and proposal-only
dispatch; connect both removal paths and revocation retries; build the approved
screens and mounted frontend tests; run end-to-end authorization/refusal tests.
Until then #4424 stays open. This migration alone is not a completed feature.
