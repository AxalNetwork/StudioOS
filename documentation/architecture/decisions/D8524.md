## D8524 — eSign signer journey in a browser: sign an envelope and download the signed PDF, on isolated fixtures (#8524)

- **Status:** built 2026-11-25. Row D5 of the #8509 audit tracker (Contracts and eSignature, P1).
- **Builds on:** D717 (the four signing steps), D711 (the signer's copy), D1216 (staged signing), D7517 and D4819 part 5933 (the browser-spec-on-fixtures pattern).
- **No migration, no Worker route, no client method, no new dependency, no workflow change.** The Worker and the signer page are not edited.

### The decision

The Worker's own tests cover `routes/esign.ts`, and `admin_contracts.spec.js` covers the admin register. Nothing drove the signer's own page. `frontend/tests/e2e/esign_signer_journey.spec.js` now does, against the real router.

**Fixtures.** The spec starts `cloudflare-worker/test/_esign_e2e_server.mjs` as a child process, with the Worker tests' TypeScript loader. It serves the built SPA (`docs/`) and passes every `/api/legal/esign/*` request to the real `esign` router on real SQLite (the schema the staged-signing test uses). R2 is a Map, there are no mail credentials and `globalThis.fetch` throws and counts, so no email is sent and nothing leaves the machine; each test asserts the count is 0. Accounts and names are synthetic. The browser aborts any other origin. The helper lives under `cloudflare-worker/test/` because the packages it imports (`hono`, `jose`) resolve from there; the leading underscore keeps it out of the test glob.

**Why a real router rather than `/api` fixtures** (the pattern of the Licences and Expertise specs): the issue asks that breaking the completion route or the download make the spec fail. A fixture that answers "signed" cannot.

**What the spec proves** (desktop 1280 and phone 390, except the staged test, which runs at 1280):

1. **One external signer** (no account; the link is the credential): read, consent, adopt a typed signature, confirm, Done ("You signed …", "Completed.", the envelope's id); no horizontal scroll; axe finds no violation under `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` and `wcag22aa` on the read step and on the Done screen.
2. **The download** by the same link: 200, `application/pdf`, a filename `axal-<envelope uuid>.pdf`, a `%PDF-` header and a real size.
3. **A second visit** shows "Already signed" with no way to sign, and a second POST of a signature answers 409.
4. **Staged** (company, then investor, each an account signing through its own session cookie): before the company signs there is no investor link, and a guessed link opens nothing; the company signs; the investor's link now exists; the company's account cannot sign the investor's link (the page shows the Worker's refusal); the investor signs; the company's own link reads signed.

**What is not scanned.** The legal document itself, shown in a sandboxed frame (`PaperFrame`), is excluded from axe: it cannot run a script, and axe's retry for a frame it cannot reach opens a second tab and stalls. The signing controls around it are scanned.

### Mutation check, by hand

Seven one-line breaks of `routes/esign.ts`, each run against the spec and then restored: the recipient not marked signed (caught by all three tests); a download that is not `application/pdf` (caught); a filename that does not name the envelope (caught); a body that is not the signed file (caught); the signer-identity check removed (caught, staged); the next stage not sent after a signature (caught, staged); the `already signed` guard removed (**survived, equivalent**: the atomic claim a few lines later, `UPDATE … WHERE status = 'pending'`, refuses with the same 409, so the response is unchanged). 6 of 7 caught, 1 equivalent.

### Not covered

Declining a signature, an expired or voided link, the draw mode of the pad, the Axal countersign, and the emailed copy are not driven here. S30's #8516 owns effects after a signature.
