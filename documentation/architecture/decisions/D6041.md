## D6041 — Remove a roadmap item, a filing or a founder added by mistake (#6041)

Build's modules can now undo three kinds of record added by mistake. Each
goes through the PATCH routes' write gate (`writeContext`) and its ownership
check: a record of another venture reads as missing (404). Each leaves a line
in the activity log.

**Roadmap item** (`DELETE /api/cycles/build/roadmap/:id`). `deleteRoadmapItem`
in `routes/progress.ts` removes the item and its `okr_dependencies` edges, in
either direction, in one batch. It logs `build_roadmap_deleted`.

**Filing** (`DELETE /api/cycles/build/formation-steps/:id`).
- Only the venture's own `formation_steps` row can be named; a Lab order's
  step and an entity obligation are not in that table.
- Its checklist rows go in the same batch.
- Its proof file is then removed from storage, best effort.
- It logs `build_formation_step_deleted`.

**Founder** (`DELETE /api/cycles/build/founders/:id`). Decided by the owner,
2026-11-15: option **A**. Only a holder with nothing attached is removed, and
otherwise the delete refuses with a sentence naming what is attached.
- **The cap table's own code.** `removeFounderHolder` in
  `services/capTableWrites.ts` does the removal, under its studio-tier gate.
  A Carta row is read only here (D1020).
- **What counts as attached** (`founderAttachments`):
  - a vesting schedule;
  - issued shares (`cap_table_issuances` naming the holder);
  - a co-founder agreement with a party of the same email or name;
  - an 83(b) filing, or any filing for them (its checklist steps belong to the filing);
  - logged contributions.

  A store or column missing from the database holds nothing. Any other
  failed read refuses with an error, and nothing is removed.
- **"No shares".** The register row's own founding split is what a
  mistakenly added founder consists of, so the delete removes it from the
  base scenario's founding table. It is not treated as an attachment;
  otherwise no founder could ever be removed. Issued shares are an
  attachment. **This reading is for the owner to confirm.**
- **The last founder.** The only founder on a saved cap table stays
  (`409`): the table needs at least one.
- **Order of the writes:**
  1. The register row is deleted, re-checking for vesting in the same
     statement.
  2. The base scenario is saved without the founder's entry.
  3. If that save fails, the row is put back.
- **Logs.** One cap table activity row (`cap_table_holder_removed`) and the
  Build line (`build_founder_deleted`).
- **The record.** The founder's record offers "Remove founder" (danger,
  confirmed), with the rule in its confirmation.

**Verified.** `cloudflare-worker/test/build_writes_d690.test.ts` covers the
roadmap and filing deletes. For the founder delete it covers:
- the register row and the founding entry both gone, with both log rows;
- a second delete is a 404;
- the only founder is refused;
- contributions, then vesting as well, are named in the refusal, and
  nothing is removed;
- another venture's founder is a 404.

Dropping the attachment check fails it.
