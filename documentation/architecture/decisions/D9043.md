## D9043 — One normalised users.email on every write and lookup (#9043)

- **Status:** built by S05, 2026-11-27 (#9043).
- **Migration:** none. Existing rows are not rewritten here; the production backfill and its duplicate report are a separate task.
- **Why:** `/register` stored the address as typed and looked it up with an exact match, while `/magic/verify` lowercased it and inserted a new user when nothing matched. `users.email` is `TEXT UNIQUE` without `COLLATE NOCASE`, so `Jane@Example.com` and `jane@example.com` became two accounts. Admin create, partner deal activation and the email-change confirm wrote the raw address too, and lookups disagreed (exact `email =` in 19 places, `LOWER(email)` in the rest).

### The rule

1. **One form.** An address on `users.email` is trimmed and lowercased by `normalizeEmail` in `cloudflare-worker/src/util/accountEmail.ts`. It is the function `services/projectAccess.ts` already had, moved, not a second one; `projectAccess` re-exports it for its callers. `routes/email.ts`'s private copy is gone.
2. **Every write passes through it.** Each `INSERT INTO users` (register, magic link, Google and Apple first sign-in, branch invitation, deck-share sign-up, partner deal activation) and each `UPDATE users SET email` (email-change confirm and revert) stores `normalizeEmail(…)` or a variable whose declaration is that call. An email-change request also stores the normalised address, so a case-only change is refused as "matches current email". D9041 retires the unused admin-create route; the combined tests require its refusal to write nothing, while every remaining email write still follows this rule.
3. **Every lookup matches the normalised value against `LOWER(email)`** and, where it picks one account, orders by id: `WHERE LOWER(email) = ${normalizeEmail(x)} ORDER BY id LIMIT 1`. Until the backfill lands, rows stored before this rule can differ only in case, so `LOWER(email)` is what makes old rows findable; a lookup that already used `lower(trim(email))` keeps it.
4. **A case pair stored before D9043 is never merged.** Every lookup above picks the lowest id, so sign-in, register, magic link, Google, Apple and the rest all land on the same one of the pair and none of them creates a third row. Lookups that refuse an ambiguous address (`agents/cohort.ts`, `lpClaim.ts`, `LIMIT 2`) still refuse it. The pair itself is left for the backfill task's report.
5. **The revert of an email change is the one exact write.** It restores the old address normalised, unless another account already holds that address in any case; then it restores this account's own stored bytes, so the revert neither fails on the UNIQUE index nor joins the two accounts. The line carries an `account-email-exact:` comment, the only exemption the guard accepts.

### The guard

`cloudflare-worker/test/account_email_9043.test.ts` reads every file under `cloudflare-worker/src/` and fails on:

- an `INSERT INTO users (…, email, …) VALUES (…)` whose email value is not `normalizeEmail(…)` or a name whose nearest declaration is one (a template `${…}` or the matching `.bind(…)` argument for a `?`);
- an `UPDATE users SET … email = …` with the same test on the value;
- a `FROM users [alias] WHERE … email = / IN` whose column is not wrapped in `LOWER(…)`.

`INSERT INTO users … SELECT` (the table rebuild in `util/usersRoleRebuild.ts`) copies stored rows and is not a write of an address.

### What is not covered

- Joins from another table's address to `users.email` (`profiling.ts`'s `partner_profiles`, `jobs.ts`, `eventAudience.ts`, `capRelTabs.ts`, `roundCalls.ts`, `email.ts`'s referral invites) compare two stored columns; they are unchanged.
- `LOWER(email) = ?` cannot use `idx_users_email`, so these lookups scan `users`. An expression index, or the backfill that lets the lookups go back to `email = ?`, belongs with the backfill task.
- `services/newsletter.ts` keeps its own `normalizeEmail`: it validates as well and returns null for a non-address, and it keys `newsletter_subscribers`, not `users`. Its value is the same trimmed, lowercased form.
