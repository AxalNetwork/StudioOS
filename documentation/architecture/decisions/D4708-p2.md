  production behaviour unverified.
- **Scope:** `/api/admin/security/*` (`routes/admin_security.ts`) and its reads in `services/adminSecurity/`, the
  Overview's security event counts (`services/securityEvents.ts`), and the Events workspace's Load older.
- **Builds on:** D4573 H1 (the caller resolved once per request), D4699 and D4803 (the ledger's cursor), D4717

### 1. Request-scoped authentication: measured, nothing removed

Every statement a request to the router makes was recorded for a read (`/overview`, `/governance`, `/sessions`)
and for a write behind the Super Admin write bar.

- **The caller is already resolved once per request.** The user row, its side tables, the elevation and the
  session standing are read once, however many gates ask (`getCurrentUser`'s per-request memo, D4573 H1). The
  write bar's three gates share that one resolution.
- **What repeats on a write is the write bar's own checks.** How the session was minted and the recent step-up
  each read the session store. Those are the fresh checks an act must make, so they are not cached or merged.
- **Nothing was changed for this item.** The remaining repeat is decoding the request's token once per gate on
  a write. Folding it would edit the shared auth module, which every route uses, and would change how often
  that module writes one of its own audit records. It is left as it is, and noted for the owner.
- **Pinned:** `cloudflare-worker/test/admin_security_request_auth_4708.test.ts` holds one caller resolution per
  read and per write, the fresh checks on every write, a second request resolving the caller again, and an aged
  step-up refused on the next write.

### 2. The evidence reads: bounded and indexed

**Bounds.** Every list statement `/governance` and `/overview` make against the five ledger stores carries a
LIMIT (the feed's 60 a store, Data access's 12, the Overview's 25 recent support sessions and 50 named admins).
Two lists are deliberately not capped, and the owner may want to decide otherwise:

- the open erasure requests (`users.deletion_requested_at`), because each is a statutory deadline the page must
  show; the list is as long as the number of open requests;
- the support-session counts in `services/userSessions.ts`, an aggregate over all sessions, which this part
  does not edit (session containment is under review in #4669).

**Indexes.** Migration `cloudflare-worker/sql/migrations/202611151527_4708_security_evidence_indexes.sql`:

| Index | Serves |
| --- | --- |
| `admin_audit_log (datetime(exported_at))` | the audit and export arms of the ledger |
| `admin_audit_log (exported_at)` | Data access: the newest exports |
| `licence_events (datetime(created_at))` | the licence arms |
| `security_events (datetime(occurred_at))` | the sign-in and step-up arm, and the Overview's last-day counts |
| `impersonation_sessions (datetime(started_at))` | the filtered support-session arm |
| `impersonation_sessions (started_at)` | the newest support sessions (Overview, Data access) |

Each ledger arm orders on `datetime(col) DESC, id DESC`. A plain index on the column cannot serve that order, so
before this file every arm read its whole store and sorted it for one page. An index on the same expression is
read backwards and stops at the page; the rowid, which is `id`, breaks ties inside it.

`activity_logs` gets no new index. Its arm filters on the admin-side action list first, and the plan already
reads only those actions through `idx_activity_action_created`; an index on the time expression went unused in
the plan and would add write cost to the busiest log table.

The Overview's security event counts now name the window they count in (`WHERE datetime(occurred_at) >=
datetime('now', '-1 day')`). Both figures fall inside it, since midnight UTC is never more than a day ago, so
the answer is the same and the read uses the time index instead of the whole ledger.

**Measured.** On `cloudflare-worker/test/_security_scale_fixture.ts`: 30,000 audit rows, 100,000 activity rows,
40,000 security events, 6,000 licence events and 4,000 support sessions over two years, a fifth of the audit

### 3. A page wholly inside one second

D4803 ended a page before its boundary second, and the next read took rows strictly older. When every row on
a page shared one second, that page came back whole with `page_split_second: true`, and the next page started
after the second. So a second holding more than one page lost the rest of its rows. D4699 left the fixture for
this to package 6. The fixture showed the loss, so this part fixes it:

- **The merge order is the stores' own.** Rows are ordered by whole second, newest first. Inside one second the
  order is by store (the key's prefix, highest first, as D4699 set) and then by `id`, highest first. That is
  each store's `ORDER BY datetime(...) DESC, id DESC`. The old order compared milliseconds and then the key as
  text. That differs from the stores' order inside a second, for example where ids cross a digit boundary.
- **The cursor carries `skip`.** When a page lies wholly inside one second, its cursor is `{ before, skip }`.
  `skip` counts that second's rows shown so far, including earlier pages of the same second.
- **The next read includes that second.** `parseFeedQuery` turns `before` + `skip` into an upper bound at the end
  of that second. Each store reads `FEED_LIMIT + skip` rows. After the merge, the first `skip` rows of that
  second are dropped. The exactness argument from D4803 still holds: the newest `N + skip` rows of the union
  cannot hold more than that many from any one store.
- **Bounded.** `skip` is at most `FEED_SKIP_MAX` (600, ten pages), so a store reads at most 660 rows. A second
  that holds more is paged after the cap as before, without `skip`. The page still shows its existing note
  that rows in that second may not be shown. A `skip` out of shape, or without `before`, is a 400 naming
  `skip`.
- **The page.** The Events workspace sends the cursor's `skip` back with `before`. It shows the one-second note
  only when the cursor has no `skip`.

The response gains `cursor.skip`, and `applied.skip` when it was sent. No other key, route, gate, status or audit
write changed.

**Pinned:** `cloudflare-worker/test/governance_same_second_4708.test.ts`, through the router. 150 rows share one
second across three stores, with both timestamp formats, sub-second times and ids crossing 9 → 10 and 99 → 100.
The pages are 5, 60, 60 and 50 rows. Every row arrives once, newest second first, and each store reads
`FEED_LIMIT + skip`. A 700-row second stays bounded and reports the cap. Mutation-checked: each of these breaks
the test:

- not dropping the shown rows;
- a cursor without `skip`;
- the old merge order;
- a store page not widened by `skip`.
