## D4570 — The Worker's authorization inventory, and "unknown is review required" (#4570)

#4570 (S1 of #4554), in two slices: the inventory that says where to look and the guard that keeps new routes from arriving unlooked-at (slice 1), then the negative suite that proves the gates on the running Worker (slice 2).

### What it is

`scripts/lib/authInventory.mjs` reads every route the production Worker serves from the same mounts the API drift guard resolves (index.ts's `app.route` lines and the self-mounting routes of `routes/_registry.ts`): 3,861 routes in 171 families at the time of writing. For each it records:

- the **gate** — the strongest identity check the handler reaches: `super_admin`, `hq_admin`, `admin`, `cf_access`, `authenticated`, `service` (a signature or shared secret), `optional_auth` (a signed-in caller is read, none required), `forwarded` (the request is handed to another router, whose gate this reader does not follow) or `public`;
- the **evidence** — the ownership checks it reaches (`canAccessProject`, `getProjectMembershipRole`, `canAccessFounderResource`, … or a query bound to the caller's own id);
- whether it writes, its file and line;
- **review** — why a person must look, or null: no gate found, a forward, an optional sign-in, or an authenticated route that names a record (`:id`, `:uid`) with no ownership evidence.

"Reaches" is static and bounded: the handler, the router middleware and path-scoped app middleware that cover it, and the functions it calls or hands on by name (`gate(c, requireSuperAdmin)`, `r.post('/x', handler)`, dynamic imports), three levels down. App middleware on every `/api/*` request (rate limits, observability, last-active, CSRF) is not a gate. **It errs towards review**: a gate it cannot see reads as weaker than it is, never stronger. Evidence found is evidence *reached*, not scoping *proven*: that is what slice 2's negative tests are for.

### The ledger

`scripts/auth-inventory-ledger.json` has an entry for every route that needs review, with its reason, a `kind` hint for the reviewer and a `state`: `unreviewed`, `public_by_design` (with a note saying why it answers without a sign-in) or `verified` (with the test that proves its gate). The first baseline is 184 entries, **all `unreviewed`**: no route is called safe here that a person has not looked at. `node scripts/build-auth-inventory.mjs --check`, in `test:guards`, fails on a route that needs review and has no entry, on an entry whose route is gone, gated now, or flagged for a different reason, and on a registered mount that resolves to no route.

### Why not commit the inventory

Like the route map's projections (D4103), the full inventory is build output: every routing change would rewrite it and parallel branches would conflict. `node scripts/build-auth-inventory.mjs` writes `documentation/architecture/AUTH_INVENTORY.json` (gitignored), and CI keeps it in the `routing-docs` artifact. The ledger is the committed record.

### Slice 2 — the negative suite

**The sweep** (`cloudflare-worker/test/authz_sweep_d4570.test.ts`) runs the real Worker on the fully migrated schema and asks every route the inventory places behind an identity gate, as callers that gate must refuse:
- no credentials, on every signed-in route (3,662 of them);
- a founder, on every admin, HQ and Super Admin route;
- an admin who is not a Super Admin, on every Super Admin route;
- a disabled account, on one signed-in GET route of every family.

A refusal is any status that is not 2xx or 3xx. A 3xx counts as a refusal only on an OAuth callback, whose refusal is a redirect to the app's error page. It runs in about 30 seconds. It is the inventory checked against the running Worker: a route the reader called gated that answers would be a reader error in the dangerous direction, or an open route. Neither may pass. Each of the four refusals was mutation-checked against `auth.ts` (`requireAuth`, `requireAdmin`, `requireSuperAdmin`, the `is_active` check).

Two lists are ratchets, so neither can grow unseen and each fix shows as a line to remove:
- `KNOWN_500`: refused with 500 where 401 belongs. It held seven sign-in routes, refused with 500 because a catch-all caught `requireAuth`'s refusal: `safe()` in `routes/auth.ts` (accept-terms, step-up, sign-out-everywhere) and `err()` in `routes/auth_passkey.ts` (the four passkey routes). Both now re-throw any error `util/authErrors.ts` maps, so `app.onError` answers it with its own status and body (401 here, and 403 or 423 for the gates that throw those). The list is empty, and the sweep asserts the seven answer 401.
- `GATE_NOT_REACHED`: routes whose feature answers 503 before its gate runs, so the sweep does not test that gate. Eighteen at first; four since slice 3 (below).

One route, `GET /api/fund-booklets`, is an admin-tier act behind a helper that asks for a Super Admin only for some acts. It is named in the test with its reason.

**What the sweep corrected in the reader.** Its first run found the reader overstating gates, the dangerous direction. Each cause is fixed and has its own unit test and mutation check:
- a `requireAuth` whose failure is swallowed (`try { … } catch {}`) is an optional sign-in, not a gate;
- method calls (`.get(`, `db.run(`) no longer resolve to same-named functions;
- only top-level declarations are indexed, so a local `const user = await requireAuth(c)` is not a reachable function;
- regex literals no longer derail the bracket scanner (one in `decks.ts` had pulled 207 KB of unrelated code into a route);
- domain helpers named for an access check (`requireCaseWriter`, `requireFundGp`, …) count as ownership evidence;
- **(added after merge)** the auth module's own queries are not ownership evidence: `getCurrentUser` reads the caller's row by `user_id = ?`, which the reader had counted as an owner-bound query for every route that reached it within two call levels. #4573 wrapped `getCurrentUser` in one more function, which pushed that query out of reach and un-vouched 91 routes at once (ledgered by #4847); removing the false evidence for good un-vouched 194 more. `scripts/lib/authInventory.test.mjs` holds it, with a mutation check.

The ledger was re-baselined: 189 entries, 186 `unreviewed` and 3 `verified`. **After the correction above it is 478 entries, 475 `unreviewed` and 3 `verified`:** the first baseline had understated the review work by 289 routes (91 seeded by #4847, 194 by the reader fix), every one an authenticated route that names a record and shows no ownership check the reader can see.

**Cross-tenant cases** (`cloudflare-worker/test/authz_cross_tenant_d4570.test.ts`) cover the routes that name a record and whose ownership check the reader cannot see, because it sits in a service reached through a namespace or a factory:
- the introduction-request drafts;
- the WhatsApp link confirm.

A member who is not a party is refused 404, nothing of the record is named, and nothing changes. These are the ledger's `verified` entries.

### Slice 3 — share links, and the gates behind a feature switch

**The family.** The links a member hands to someone else, where the token is the gate: signed, stored only as a hash, with an expiry, a view limit and a revocation. Chosen first among the ledger's high-risk kinds (signed URLs, exports, MCP and agent reads, admin) because a link answers without the reader's session and is forwarded outside the platform. Four entries move from `unreviewed` to `verified`, each with a note saying what holds it:

| Route | Who is let in | What the suite refuses |
| --- | --- | --- |
| `GET /api/captable/share/:token` | anyone holding a live scenario link | a broken signature, another key's token, a signed scope no link stored (a widened audience), a venture link, a non-token: 403; spent and revoked: 410 |
| `GET /api/captable/access/shared/:token` | anyone holding a live venture link | the same, plus a signed scope naming another venture or another level than the stored row: 403; spent and revoked: 410 |
| `GET /api/lab-report-shares/open/:token` | the one named account, signed in | the report's owner, another founder, an admin, an unstored or broken token: the one 404; no credentials, or the named account disabled: 401 |
| `POST /api/lab-report-shares/:id/revoke` | the report's owner | another founder, the named reader, an admin: 404; no credentials: 401 |

`cloudflare-worker/test/authz_share_links_d4570.test.ts` asks each through `worker.fetch` on the migrated schema, with every link minted by its owner through the same Worker. Every refusal names nothing of what the link shows, and changes nothing: the token rows (views, use, revocation), the view and access logs, the report's open count and every audit row are compared before and after (the app-wide request log's own `http_*` row, written for every request, is not the route's write). The revokes and mints beside the links are held the same way: another founder or an admin cannot revoke a cap table link (403) or mint a venture link (403), and the attempt changes nothing.

**Mutation checks**, each seen red, then restored:
- `claimShareToken` answering `ok` when no stored row matched: the unstored full-audience scenario scope reads, and the spent venture link reads;
- the venture link's stored-row agreement test (`tok.project_id`, `tok.level`) removed together with the claim above: the unstored scopes read the venture;
- `ownerOf`'s `a.owner` test removed: an admin revokes a venture link;
- each revoke made a no-op that answers `ok` (`DELETE /api/captable/shares/:id`, `DELETE /api/captable/access/:projectId/links/:id`): the revoked link still reads;
- `DELETE /api/captable/shares/:id`'s scenario write gate removed: another founder revokes the owner's link;
- the report open's `grantee_user_id = ?` removed: the owner, another founder and an admin open it;
- the report revoke's owner test removed: another founder revokes it;
- the report open's `revoked_at IS NULL` removed: a revoked link opens.

One mutation is not seen, by design: skipping `verifyShareToken`'s signature comparison alone. A token is refused unless its hash is a stored link's, so a token with a bad signature is refused by the claim whatever its signature says; the signature check is a second wall, not the only one.

**The gates behind a switch.** Round calls answer 503 from router middleware while `ROUND_CALLS_ENABLED` is not `'true'`, so the sweep never reached their gates. The sweep now switches a feature on for its own routes only (`FEATURE_ON`, a test environment's flag, never a deployment's) and names a venture (`project_id`) for the three routes that read it before the gate. The thirteen round-call routes come off `GATE_NOT_REACHED`, and the sweep asserts every route behind a switched-on feature answers an anonymous caller 401; the founder, non-Super admin and disabled-account passes now reach them too. Emptying `FEATURE_ON` turns all four sweep tests red. `GATE_NOT_REACHED` is four: SMS enrolment (start, confirm), Meet transcript consent and LinkedIn sign-in start, each switched by a provider's credentials rather than a flag, so reaching them needs a stub of that provider's configuration.

### What remains

The ledger is 479 entries: 472 `unreviewed`, 7 `verified`. Each `unreviewed` entry needs a person, to `public_by_design` with a note or to `verified` with a test. That is review work, not a finding. In the share-link kind (`link_token`), 36 entries remain, among them the deck share and print-export links, the publication and analytics download tokens and the partner onboarding links. The four `GATE_NOT_REACHED` routes remain.

### What this does not claim

No finding is reported here. Every mismatch the build and the sweep found was a reader gap (each fixed, each now a test in `scripts/lib/authInventory.test.mjs`) or a refusal with the wrong status (`KNOWN_500`, now fixed); none let a caller read or change what its gate should refuse. This says nothing about routes a slice did not test. Any exploitable gap found in any slice goes to a private security advisory first; issue comments describe the remediation class only.
