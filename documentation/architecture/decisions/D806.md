## D806 — One invoice list for Billing (token packs, auto-reloads and plan invoices, newest first, 25 to a page), and the card's billing address

- **Status:** filed by S1 for the owner (2026-10-20) as #2245, part of D785 (#2210). Filed for S20; the owner asked S23 to build it. **A money path: S1 reviews it for security before the owner merges.**
- **Source:** the "Usage & Billing console" canvas (`design/incoming/Usage Page.dc.html`), B1's "Recent invoices" (the newest three) and B3's "Invoices · 1–25 of N".
- **Stacks on:** D755 (token packs, their purchases and refunds), D794 (auto-reload, #2236), D792 (the Billing page, which draws this list in a later commit) and D527 (an API domain's own module).

### 1. The decision

Before this, the two halves of a member's invoices lived apart:
- token-pack and other orders in D1 (`GET /api/orders/mine`, unpaged, each PDF at `/api/orders/:ref/invoice`);
- plan invoices in Stripe, inside `GET /api/billing/overview?scope=`.

The card's billing address was not read at all.

1. **`GET /api/billing/invoices?page&per`** lists the signed-in member's own rows, newest first, then pages them, with `total`.
2. **`billing_address`** joins each payment method on `/api/billing/overview`.

### 2. As built

No migration. Worker: `services/billingInvoices.ts` (D1 and pure) and the route in `routes/billing.ts` (Stripe).

1. **Each row** is `{ kind: 'order'|'stripe', id, date, description, amount_cents, currency, status, pdf_url }`.
   - `status` is `paid`, `refunded`, `partly_refunded`, `open` or `void`.
   - `amount_cents` is what was charged, tax included.
2. **Orders** are the member's own orders whose status is `paid`. A pending or failed order is not an invoice.
   - **A token pack** is an order with an `ai_topup_purchases` row. It reads "AI tokens, $25 pack", the face from its pack.
   - **An auto-reload** reads "AI tokens, auto-reload $25". See §3.
   - **Any other order** reads its items' names ("Incorporation, Expert session × 2"), or "Order" if none can be read.
   - **Refunds.** D1 records a refund only for a token pack: each `charge.refunded` writes an `ai_credit_ledger` refund row whose `source_ref` ends in the charge's cumulative cents refunded (D755 §8). The largest of them, against the order's total, gives `partly_refunded` or `refunded`. Any other order reads `paid`, because no refund of it is recorded in D1.
   - **The PDF** is `/api/orders/:ref/invoice`, which checks the owner.
3. **Plan invoices** come from each Stripe customer the member has, founder and investor, read once when both are the same customer.
   - At most 100 per customer, from Stripe's `/invoices`.
   - A draft is left out.
   - `uncollectible` reads `open`.
   - A paid invoice with credit notes (`post_payment_credit_notes_amount`) reads `partly_refunded` or `refunded`.
   - The description is "[plan] · monthly": the plan's name from the mirrored catalogue for the first recurring line's price, and its interval. Otherwise Stripe's own line words, else "Plan invoice".
   - The PDF is Stripe's `invoice_pdf`, passed through only as an `https://` URL. The Worker never proxies its bytes.
4. **Stripe down.** If any customer's list fails, or a member with a customer is read with no Stripe key, the orders still list, with `degraded: ['stripe']`. The list is never an error as a whole, as `/overview` is not.
5. **Paging.** `page` and `per` are whole numbers from 1, and `per` is at most 100. Anything else reads as the default (page 1, 25).
6. **The address.** `billing_address` is `{ line1, line2, city, postal_code, country }` from the payment method's `billing_details.address`. It is `null` when Stripe holds none (no address, or every field empty). It is never filled in from anywhere else.
7. **The client.** `frontend/src/lib/api/billingInvoices.js` (`billingInvoicesApi.list({ page, per })`), re-exported by one line in `api.js` (D527). D789's Usage overview reads the newest three rows; D792's Billing page draws the full list in a later change.

### 3. The auto-reload origin

The issue expected D794 (#2236) to record which orders were auto-reloads. It merged recording that only in Stripe's PaymentIntent metadata (`auto_reload: '1'`), not in D1. Reading Stripe once per order to name a row is out of proportion. So the reload now marks its pending order's lines with `origin: 'auto_reload'`. That needs no migration, because `items_json` is JSON and nothing that reads it checks for extra fields.

Reloads placed before this change carry no mark and read "AI tokens, $25 pack". That is what the issue asked for until an origin existed.

### 4. Verified

- `cloudflare-worker/test/billing_invoices_d806.test.ts`: real SQLite, with packs recorded, credited and refunded through the D755 code. Stripe is stubbed, and every customer, card and address is a placeholder. It covers:
  - five rows newest first, two pages at `per=3`;
  - another member's orders and invoices never appear, and Stripe is asked only for the member's own customer;
  - an investor's customer is read too, once;
  - Stripe down, or no key, still lists the orders, with `degraded`;
  - the auto-reload and part-refund rows;
  - a Stripe invoice's status, credit notes, PDF and words;
  - the address passed through, and `null`.
- Eighteen mutations, each killed: the sort, the refund read, the page slice, the paid filter, the member filter, the origin, the refund compare, drafts, the https check, credit notes, the `per` cap, the investor customer, the de-duplication, both degraded paths, the address dropped, an empty address, and the reload's origin.
