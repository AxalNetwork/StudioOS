## D887 — Release versions count active commit months, weeks and days

- **Status:** owner decision, recorded by S1 for #2654; clarified by the owner after #2655 merged on 2026-10-23. The original implementation incorrectly used publication timestamps, collapsing historical activity into one day.
- **Migration:** none. Only Git history and GitHub release metadata are read; no production data is touched. Publishing remains manual.
- **Replaces:** the minor-bump rule from #2614 and the publication-date interpretation initially implemented in #2655.

### Rule and history

A version is `v<months>.<weeks>.<days>`, computed from complete first-parent
main history through that day. Use UTC committer dates, recording when
changes landed on main, rather than side-branch author dates or later
publication timestamps.

- Months count distinct active months since the beginning and do not reset.
- Weeks and days reset each month. Days count distinct active commit days,
  from 1 to 31. Multiple commits on one day add only one.
- Weeks use seven-day blocks within the month: 1–7, 8–14, 15–21, 22–28,
  29–31. Count only active blocks, starting the week counter at zero:
  `number of active blocks - 1`, giving 0–4. Multiple pushes in a block
  add no extra week; an inactive block adds nothing.
- No year or stage suffix.

The first active day is `v1.0.1`. The owner's explicit correction on
2026-10-23 is **v8.3.23**, not v8.28.138: eight active months since March,
four active October week blocks giving counter 3, and 23 active October
days. A full 31-day active month ends with week counter 4 and day counter
31. The lifetime 138 active days are historical coverage, not the day
component of the version. Publication timestamps must not collapse history.

### Daily drafts and fixed publication

Create one draft for each active day, targeting that day's final main
first-parent commit. The display title is the version alone (for example,
`v8.2.21`), with no date or description, as explicitly clarified by the owner. Notes link its exact comparison against the previous
active day's final commit. Refresh only matching drafts, identified by a
daily marker. Unchanged drafts are idempotent. Once a daily release is
published, its version, target, notes and tag remain fixed. Later commit
days get separate drafts. Legacy published releases are never retagged.

The workflow fetches complete history and the generator reads every release
page. A conflicting unrelated version is an error, never an overwrite.
Backfill writes are paced to GitHub's content-creation limit. Publishing is
manual; historical drafts do not deploy any code by themselves. The old
unpublished `v0.29.0-alpha` draft is reused for the latest daily draft during
the one-time backfill. Existing legacy tags remain readable in the badge.

### Verification

Focused tests cover active dates, duplicate days, gaps, month/year
boundaries, monthly seven-day blocks, UTC conversion, exact commit targets, complete
pagination, daily backfill, unrelated releases, immutable published daily
releases, idempotent drafts and dry runs. Build and full drift validation
are reported in the implementation PR.

### Owner-directed history publication and display cleanup

The owner explicitly authorized publication of all 138 daily releases and
then removal of the 28 superseded weekly `v0.*-alpha` release entries and
their 34 attached history files, while retaining their Git tags. The daily
release titles are the version alone, without dates or descriptions. This
one-time metadata cleanup does not authorize the generator to rewrite
