## D887 — Release versions count the months, weeks and days that had a release

- **Status:** decided by the owner, recorded by S1, 2026-10-23 (#2654). Built by S18 in #2655 (`fecc38a4f2`).
- **Basis:** `origin/main` after `fecc38a4f2`.
- **Migration:** none. No production data is read or written. Only GitHub releases are, and publishing stays the owner's.
- **Replaces:** the naming rule #2614 introduced (`v0.1.0-alpha` first, then a minor bump per release at the current stage).
- **Why:** the owner wanted the version to say how long Axal has been shipping, not how many times the publish button was pressed. A minor bump per release had reached `v0.28.0-alpha` in one afternoon.

### 1. The rule

A tag is `v<months>.<weeks>.<days>`, each a cumulative count of distinct periods that contain at least one published release:

| Part | Counts | Boundary |
|---|---|---|
| months | calendar months with a release | UTC, `YYYY-MM` |
| weeks | weeks with a release | UTC, Monday-start |
| days | days with a release | UTC date |

- **Plain tags:** no stage suffix (`-alpha`) and no year. Counts keep accumulating across years.
- **Empty periods add nothing.** A month with no release does not bump the month count.
- **Several releases on one day count once.**
- **The first release is `v1.1.1`:** one month, one week and one day.
- **Today counts as active** when the draft is named, because publishing it makes it so.

`nextReleaseTag(releases, now)` in `frontend/src/lib/release.js` computes it. `releaseDays` reads only published releases whose tag parses, and fails on a missing or invalid `published_at` rather than silently dropping history and resetting the counts.

### 2. One release a day, and it stays fixed

- **Before publication:** `scripts/release-draft.mjs` refreshes the single draft on every push to `main` (`.github/workflows/release-draft.yml`).
- **After publication:** once a release is published on a UTC day, later runs that day write nothing, so neither the published release nor its tag ever changes. Further merges wait for the next day's draft.
- **Full history:** the generator reads every page of releases (`readReleases`). Counting only the newest 100 would make versions go backwards.
- **Publishing stays manual,** and `release-published.yml` still redeploys so the badge shows the tag.

### 3. Legacy tags

The 28 tags published under the old rule on 2026-10-23 (`v0.1.0-alpha` to `v0.28.0-alpha`) still parse (`parseRelease`). They are history: their publication dates count as active periods, so 2026-10-23 is already day 1, week 1 and month 1. **The first tag under this rule is therefore `v1.1.2`** if the next release is published on 2026-10-24. Published on Monday 2026-10-26 it would be `v1.2.2`, and on 2026-11-02 `v2.2.2`.

`RELEASE_STAGE = 'alpha'` stays, only as the badge's fallback label for builds with no published release (local, CI and previews) and its tooltip. It no longer names tags.

**A stale draft:** the draft `v0.29.0-alpha` was written under the old rule before #2655 merged. Because 2026-10-23 already has published releases, today's runs skip writing, so that draft keeps its old name until the first push to `main` on 2026-10-24 renames it. Publishing it before then would add one more legacy-named tag. The rule still counts it correctly as a release on 2026-10-23, but the name would not follow this decision.
