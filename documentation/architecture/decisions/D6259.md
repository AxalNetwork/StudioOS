## D6259 — Investor Network reads a tie's touches and reminders back (#6259)

- **Status:** built on `frontend/src/pages/investor/InvestorNetworkWorkspace.jsx`
  and `frontend/src/lib/networkBook.js`. No Worker change: the three routes
  already existed (`GET /api/partnernet/relationships/:id/interactions`,
  `GET /api/partnernet/reminders?all=1`, `PATCH /api/partnernet/reminders/:uid`),
  and so did their client methods (`partnerInteractionLog`,
  `partnerReminders(all)`, `partnerReminderDone`).
- **Builds on:** D465 (migration 338, the interaction log and reminders), the
  #5129 state vocabulary (D5129), `ui/Honesty.jsx`'s `Unreadable`.

### What was decided

- **The touch panel lists the history.** Opening "Log a touch" reads the log
  and lists every recorded touch newest first (by when it happened, then by
  when it was recorded): the date, the note ("No note recorded" when none),
  who recorded it, and "Voided" on a voided one. "Void this touch" stays on the
  reader's own live touches only; the route refuses anyone else's anyway.
  After recording or voiding, the panel stays open and the history is read
  again.
- **Who recorded it is a name, because the route already joins it.** The open
  point on the issue: the interactions route selects
  `u.name AS recorded_by_name` (a LEFT JOIN on `users`), and only the two
  people on an accepted tie (or an audited admin) can read it — each already
  sees the other's name in the book. So no Worker change was needed. The page
  says "You" for the reader's own; otherwise the joined name; "The other
  person" only when the name is absent and the id is the tie's other party;
  and "Not recorded" for anything else, rather than guessing whose touch it was.
- **Three states, in #5129's words.** Loading is a skeleton with "Loading
  recorded touches…"; a successful empty read says "No touch recorded"; a
  failed read says "The touch log could not be read. This is not a claim that
  none exist." with Retry (the shared `Unreadable`). A failed read used to go
  to the page-wide action error and leave an empty panel — that is gone.
- **Reminders are read with `all=1`.** The due banner still filters to open,
  due ones. Each tie shows its open reminder's date ("Reminder Mar 1, 2099",
  the earliest open one). A **Reminders view** lists Upcoming (open, soonest
  first, marked Due or Upcoming) and Done (most recently done first), each
  naming its tie; an open reminder can be marked done there whether or not it
  is due. The view has its own loading, empty and could-not-be-read states.
- **"Set reminders" opens the Reminders view.** It used to open the reminder
  form on whichever row sorted first, without saying so. A new reminder is
  still set on its tie with "Remind me". The op is now always enabled: the
  view is useful with no row on screen.

### What stays

- This is the investor tie's store (`partner_interactions`,
  `partner_reminders`). #5310's Person Sheet is a different store and is not
  touched. If the addendum's proposal 0 merges ties and contacts, this view
  moves into the sheet.
- Notes are personal content: nothing added here logs them.
