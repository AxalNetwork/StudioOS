### 1. What was decided

One local, append-only ledger of financial events, so Revenue can answer from recorded data rather than walking
Stripe customers on page load. Slices 2 to 6 of #5038 read it; this slice only writes it.

| Column | Meaning |
| --- | --- |
| `source`, `source_event_id` | `stripe` + the event id (`evt_…`), or `hq` + the object HQ's action made (the refund `re_…`). UNIQUE together: the idempotency key. |
| `source_event_type` | `invoice.paid`, `charge.refunded`, …, or `hq.refund`. |
| `kind` | `invoice`, `charge`, `payment`, `refund`, `dispute`, `adjustment` (CHECK). |
| `livemode` | Stripe's mode for the event, or NULL when not known. |
| `object_ref`, `charge_ref`, `payment_intent_ref`, `invoice_ref`, `customer_ref` | The Stripe ids the event names, so later slices can link an invoice, its charge and its PaymentIntent. |
| `refund_key` | A refund's `<charge>:<cumulative refunded, Stripe units>`; UNIQUE where set (below). |
| `user_id`, `company_id`, `project_id`, `licence_uid`, `revenue_stream`, `product_ref` | Attribution, stamped once at write time. NULL = unattributed. |
| `actor_user_id` | The HQ admin behind an `hq` row. |
| `currency` | ISO 4217, upper case; the row's own. |
| `gross_cents`, `refund_cents`, `net_cents` | Integer minor units of `currency`: what this event moved in, out, and `gross - refund` (CHECK). |
| `occurred_at` | When it happened: the Stripe event's `created`, or the moment HQ's refund returned. |
| `recorded_at` | When the ledger wrote it. |
| `reconciliation_state` (+ `reconciled_at`, `reconciled_by_user_id`, `reconciliation_note`) | `pending` → `matched` / `discrepancy` / `excluded`; `discrepancy` → `matched` / `excluded`. |

### 2. What each event records

| Event | kind | gross | refund | net |
| --- | --- | --- | --- | --- |
| `invoice.paid` | invoice | `amount_paid` | 0 | gross |
| `charge.succeeded` | charge | captured amount | 0 | gross |
| `payment_intent.succeeded` | payment | `amount_received` | 0 | gross |
| `charge.refunded` | refund | 0 | `amount_refunded` − `previous_attributes.amount_refunded` | −refund |
| `charge.dispute.created` | dispute | 0 | the disputed amount (0 for an inquiry, `warning_*`) | −refund |
| `charge.dispute.closed` | dispute | won: the amount reinstated; lost / `warning_closed`: 0 | 0 | gross |
| HQ refund route | refund | 0 | the refund's amount | −refund |

- **The same money from three sides.** An invoice, the charge that paid it and its PaymentIntent are three rows of
  three kinds, linked by their refs. A reader sums **one kind per stream**, never several. Nothing here dedupes them,
  because each is a fact Stripe reported; choosing which side a metric reads is slice 2's.
- **Every other event type writes nothing** (`invoice.finalized`, subscription events, `account.updated`, …).
- **Amounts** are Stripe's, converted to the currency's own minor unit (ISK and UGX from Stripe's hundredths, D5029).

### 3. Rules, and how each is held

- **Idempotent.** A row is one `INSERT … ON CONFLICT DO NOTHING`: a replay meets `(source, source_event_id)` or
  `refund_key` and writes nothing new. Not `INSERT OR IGNORE`, which would also drop a row a CHECK refuses, silently.
- **One refund, one row.** HQ's refund route and Stripe's `charge.refunded` for the same refund compute the same
  `refund_key` (HQ from the refunded total its confirmed review checked plus the refund's amount; Stripe from the
  charge's `amount_refunded`). Whichever lands first is the row; the other is a no-op. A refund made anywhere else
  (the dashboard, an API call) arrives only by the webhook and is recorded there.
- **A failed write is not acknowledged.** The webhook writes the ledger row after its handlers and before it marks
  the receipt (`stripe_webhook_events.handled_at`) handled. A failure throws into the route's existing catch:
  the receipt's claim is released, the answer is `503 webhook_processing_failed`, and Stripe retries. Handlers that
  already ran are idempotent on retry, as they were before. One statement means no partial row.
- **HQ's refund route is best-effort**, like its audit row: the money has already moved, so a ledger failure is
  logged and the refund answer is unchanged; the webhook's `charge.refunded` records it.
- **A missing amount is NULL, never 0.** A `charge.refunded` without `previous_attributes.amount_refunded` records a
  refund of NULL (the `refund_key` still holds it once). A row with no readable currency carries no amount (CHECK).
- **Attribution is never guessed.** `user_id` is our checkout's `metadata.user_id`, else the one account whose
  `stripe_customer_id` or `investor_stripe_customer_id` is the event's customer; none or two is NULL. `company_id`,
  `project_id`, `licence_uid` come from metadata only (nothing stamps `licence_uid` yet: slice 4 does); the revenue
  stream is `metadata.kind`; the product is `metadata.product_id` or `price_id`. A lookup that fails throws (Stripe
  retries) rather than storing NULL for good. `unattributedFields(row)` names what a row leaves unresolved.
- **No cross-currency totals.** Nothing in this slice sums; every row carries its own currency.
- **Immutable and kept.** Triggers refuse any UPDATE that changes a column other than the four reconciliation
  columns, and every DELETE. No foreign keys, so no ON DELETE action can rewrite a row.
- **One guarded path for reconciliation:** `setReconciliationState(env, { uid, from, to, actorUserId, note })`. The
  move must be allowed (`RECONCILIATION_MOVES`) and is compare-and-set on `from`, so two reconcilers cannot both move
  a row. No route calls it yet; a later slice gives it one.

### 4. Coverage start, and no backfill

`financial_event_coverage(source, coverage_starts_at, note)` holds one row per source (`stripe`, `hq`), written by
the migration at the moment it applied in each database. Its rows are immutable and kept, and a ledger insert from a
source with no coverage row is refused (trigger), so every row's source has a known start. Nothing before
`coverage_starts_at` is backfilled: later slices show that period as a gap, never as zero (`coverageStarts(env)`).

- No Stripe live-mode step was taken. The webhook endpoint already subscribes to every event recorded here

- The runtime safety net (`ensureFinancialEventsSchema`, D235) runs the migration's own statements; the test holds
