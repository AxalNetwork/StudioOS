## D5580 — WorkGraph part 1: hunk risk classes, PR evidence and the advisory baseline (#5580)

Part 1 of #5580. It extends #5616's scanner (`scripts/lib/prOverlap.mjs`,
`scripts/pr-overlap.mjs`, `.github/workflows/pr-overlap.yml`, D5616) instead of
adding a second one. The pure rules live in `scripts/lib/prRisk.mjs`. Everything
is **advisory**: nothing blocks, labels, reviews or merges, and every GitHub
protection stays as it is.

### Risk classes per overlapping pair

Each shared path gets a class, and a pair takes the highest class among its paths.
From lowest to highest risk:

| Class | Meaning |
|---|---|
| `disjoint` | No shared path. This class is never reported. |
| `same-path-disjoint-hunks` | A shared path where the old-side changed ranges neither overlap nor touch. At least one unchanged base line lies between them. |
| `unknown-hunks` | The hunks cannot be compared. A patch is missing, binary, truncated or unparsable. The merge base is not measured. Or the two merge bases differ and that file changed between them, or the difference was not checked. This class is never read as disjoint. |
| `overlapping-hunks` | The old-side changed ranges overlap or touch. Git's merge also treats touching changes as a conflict. |
| `dependency` | The path is a hub, migration, contract, baseline or generated file (D5616's `classify()`), or one of three new classes: `manifest` (`package*.json`, `pyproject.toml`, `uv.lock`, `requirements*.txt`), `api` (`frontend/src/lib/api/`) or `schema` (`cloudflare-worker/sql/`). Two PRs that share a new migration stamp also get this class. |
| `critical` | A security or production path (the list below). Also a shared migration whose added lines `ALTER`, `DROP` or `RENAME` an existing table, or whose patch is unavailable, so that an alteration cannot be ruled out. |

**Critical list** (`CRITICAL` in `prRisk.mjs`):

- any `wrangler*.toml`
- `.github/workflows/**` and `.github/actions/**`
- `.github/CODEOWNERS`, `.github/codeql/**` and `.github/dependabot.yml`
- `cloudflare-worker/src/auth.ts`
- every `cloudflare-worker/src/middleware/*.ts`, since every request passes through it (auth, CSRF, rate limit, security headers)
- `cloudflare-worker/src/routes/auth*.ts`
- `cloudflare-worker/src/util/{webauthn,authErrors,oauthReturn}.ts`
- `frontend/public/_headers`
- `.gitleaks.toml`, `.gitleaksignore` and `.semgrepignore`

**How hunks are compared.** The hunks come from the GitHub files API's `patch`.
That patch is diffed against the PR's merge base. The parser walks each hunk body
and drops the context lines, so only changed old-side lines count. A pure
insertion before old line `L` is the empty span `{start: L, end: L-1}`. A hunk
whose line counts do not match its header, or whose file reports different
`additions`/`deletions`, is truncated and therefore unknown. Old-side line numbers
are compared only when both PRs have the same merge base, or the same blob for
that file at their two merge bases. The CLI reads the blob with
`git rev-parse <base>:<path>` from the checked-out main history. In any other
case the result is `unknown-hunks`. The proof is recorded with the class: the
overlapping ranges, the disjoint spans on each side, or the reason the hunks are
unknown. A class is never a merge verdict. The textual conflict verdict still
comes only from D5616's `git merge-tree`.

### Evidence per PR

The scanner records four separate evidence fields for each PR and never merges
them into one. Each field has its own named unknown state, and an unknown value
is `null`, never 0.

1. **Merge status against the base** comes from `GET pulls/{n}`.
   `mergeable: false` or `mergeable_state: dirty` gives `conflict`.
   `mergeable: true` gives `clean`. `null` gives `unknown`, because GitHub has
   not computed it yet.
2. **Required-check failure.** The required contexts come from
   `GET rules/branches/{base}`: the union of the `required_status_checks` rules,
   as D5666 does, so no check name is hard-coded. The checks themselves come from
   `GET commits/{head}/check-runs`, taking the latest run per name. The result is
   `failed`, `pending` (with any contexts not reported), `passing` or
   `none required`. When the rules cannot be read, the result is `unknown`, and
   it lists every failed check under `failedAny`. Classic branch protection and
   legacy commit statuses are not read.
3. **CI queue delay.** The scanner takes the head's latest
   `.github/workflows/ci.yml` run (`GET actions/runs?head_sha=`) and reads its
   jobs. For each job that was not skipped, the delay is `started_at` minus
   `created_at`, the same measure as D5603's `runnerWait`, and the median comes
   from D5603's `percentile`. The field reports the maximum, the median and the
   number of jobs. Jobs still queued are counted separately with their wait so
   far. With no CI run, or no job that has both timestamps, the field is
   `not measured`.
4. **Base age** comes from `GET compare/{base}...{head}`: `behind_by`, the
   merge-base SHA, and the merge base's commit date and age in hours. When the
   compare cannot be read, the field is `unknown`. Its merge base is also what
   makes hunks comparable.

The advisory comment shows one evidence line per PR. The #5600 summary shows one
line per PR in a pair. Check names, paths and reasons go through D5616's
`escape()`. The marker is still `<!-- studioos-pr-overlap:v1 -->`.

### Determinism

- **Duplicate PRs.** Rows repeated by list pagination are deduplicated by number,
  and the first row is kept.
- **Disappeared PRs.** A PR whose files or detail read returns 404 or 410, or
  whose detail shows it is no longer open, is dropped. The summary says so.
- **Stale heads.** If a PR's head SHA changed between the list read and the
  detail read, the PR is marked `stale`. It is kept in the snapshot without
  evidence and is not classified or paired.
- **Other read failures.** Any other read failure keeps every PR that was not yet
  read and marks the scan partial.

The request cap rises from 300 to 600, because evidence needs about four reads
per PR. The rate-limit floor of 100 and every other D5616 cap are unchanged. The
job gains `actions: read` and `checks: read`. It still has no write permission
except the comment.

### Advisory baseline

Every hourly run writes `pr-overlap-<UTC stamp>.json` with schema
`studioos-pr-overlap-snapshot/v1`. For every open PR it records:

- the number, draft and stale flags
- the head and base SHAs and the base ref
- the changed paths, including previous names
- the four evidence fields

For every pair it records the risk class, the textual verdict, and each path's
class and proof. The workflow uploads the file as the
`pr-overlap-snapshot-<stamp>` artifact (pinned `upload-artifact`, 30-day
retention). Snapshots are never committed. Two weeks of these artifacts are the
baseline that any later enforcement must be judged against.
