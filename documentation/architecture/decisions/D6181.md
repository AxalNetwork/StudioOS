## D6181 — Exact diligence-case lookup for a deal: `GET /api/dd/cases?subject_id=` (#6181)

- **Status:** built by S15 for #6181, 2026-11-14.
- **Basis:** `main` at `95210ad1ab`. No migration.
- **Code:**
  - `cloudflare-worker/src/routes/dd.ts`: `subject_id` in `CASE_FILTER_SQL` and `caseFilterBinds`; the 400 in `GET /cases`.
  - `frontend/src/pages/deal/DealWorkTabs.jsx` (`DealDiligence`) and `frontend/src/pages/deal/dealWorkModel.js` (`caseForDeal`).
  - Tests: `cloudflare-worker/test/dd_case_subject_filter_6181.test.ts`, `frontend/test/deal_work_d1153.test.mjs`.

### The problem

The deal's Diligence tab read the caller's newest 200 project cases (`dd.listCases({ subject_type: 'project' })`) and looked for this company's case in the browser. A caller with more than 200 cases could miss it: the tab then said none of the newest was on this company and still offered **Open a diligence case**, inviting a second case on the same company.

### The API addition

- **`GET /api/dd/cases` takes an optional `subject_id`**: the cases on exactly that subject (a project's id when `subject_type` is `project`). It is one more bound optional clause in the shared `CASE_FILTER_SQL` (`AND (? IS NULL OR c.subject_id = ?)`, right after `subject_type`), so the list, its `total` and the overview read the same predicate, with the bind in the same position in each. The SQL text never changes with the request and nothing is interpolated (D1249).
- **The reader scope is unchanged.** The filter only narrows: an Admin still reads every case (or their own with `owner_only=1`); anyone else reads only the cases they opened, lead or review. A case on the company the caller may not read is not returned and not counted.
- **A malformed value is refused.** Absent or empty is no filter. Anything but a positive whole number (`abc`, `0`, `-1`, `1.5`, `1e3`, beyond a safe integer) answers **400** `{ code: 'invalid_subject_id' }`. Other list filters ignore a value they cannot read (`lead`, `stage`), but for an exact lookup ignoring would widen the answer to every case the caller reads, which is the failure this decision removes.

### The Diligence tab

- `DealDiligence` reads `dd.listCases({ subject_type: 'project', subject_id: deal.project_id })`; `dd.listCases` already passes every non-empty parameter through.
- `caseForDeal` loses its `not_in_read` state ("Only your newest N cases were read…"): the read is this company's alone, so it is never cut short by the caller's other cases, and an answer with no live case is "no case". It still takes the newest case that is not archived, and still checks the subject as a guard.
- **Open a diligence case** shows only for `none`: never beside a live case the caller can read.

### Not changed

- No other caller of `GET /cases` sends `subject_id`, so the team list, the overview and the partner desk read as before.
- The FastAPI dev port (`backend/`) is not mirrored.
