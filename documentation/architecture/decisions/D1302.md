### 1. Why no migration 638

#3399 asks for a sub-account store holding:
- account, kind (`tester` or `lp`), status (`applied`, `active`, `paused`, `declined`, `removed`), dates, who decided, note or reason, and consent version;
- append-only events;
- approve, decline, pause and remove routes, each telling the member and audited, with an admin account refused;
- a pool read and the lane's pending count.

**For the Product tester, every one of these is already on `main`:**

| #3399 asks | Already there |
|---|---|
| The store, its five statuses, dates, decider, note, reason, consent version | `product_testers` (migration 576, D1042) |
| Append-only events | `product_tester_events` (576), one row per change, in the same batch |
| Approve, decline, pause, remove (and resume), `requireAdmin` | `routes/admin_product_testers.ts` (D1042) |
| Each tells the member | `messageFor`, by email and in the inbox |

| #2390's Product testers lane count | `approvalSources.ts` `product_testers` (`status = 'applied'`) |

**For LP,** #3399 itself says to read from approved `lp_applications` with no second store.

A `sub_accounts` table with kinds `tester` and `lp` would have duplicated 576 for testers, and held a copy of `lp_applications` for LPs. Two stores for one fact drift apart. `ACCOUNTS_MAP_2026-10-26.md` (D1299, #3395) lists Product testers as "no store (D1302)". That line is mistaken: D1042 built the store in #2890. The map should read "D1042's store; D1302 reads it" when it lands.

**What #2377's item 2 lacked was the account's side:** Admin › Accounts could not say what sub-accounts an account holds, and the Overview had no LP or tester figure. That is what this part builds.

### 2. `GET /api/admin/sub-accounts/counts` — the Overview's two widgets (ACC1)

```
{ testers: { available, by_status: { applied, active, paused, declined, removed }, active, pending, unknown_status },
  lps:     { available, active, pending } }
```

- **Testers:** every status is counted, and a status with no row is a counted 0. `pending` (applied) is #2390's Product testers lane. A status outside the five is counted apart as `unknown_status`, never folded into one.
- **LPs:** accounts with an approved application to any fund, each counted once, however many funds. `pending` is the applications still waiting.

### 3. `GET /api/admin/sub-accounts/accounts/:userId` — one account's sub-accounts (ACC5)

```
{ user_id,
  tester: { available, record: { id, status, applied_at, decided_at, decided_by: { id, name } | null, reason, note,
                                 availability, consent_email_at, consent_version, updated_at,
                                 events: [{ action, from, to, at, by: { id, name } | null }] } | null },
  lp:     { available, is_lp, funds: [fund_slug], applications: [{ id, fund_slug, status, applied_at, reviewed_at, reviewed_by }] } }
```

- **`record: null`** means the account never applied to test.
- **`is_lp`** is true once any application is approved. `funds` lists the funds it is an LP of; a pending, declined or withdrawn application is in `applications` and not in `funds`.
- **A decider or reviewer whose account is gone** keeps the date, with `name: null`.
- **Never returned:** an email, the target commitment, the applicant's own note, the investor type, or the tester's answers. `note` here is HQ's own note on the tester row, which admins already read on D1042's route.

### 4. Who may read

- **`requireAdmin`:** an Admin or a Super Admin. A member is refused.
- **Another administrator's record is the Super Admin's to open:** 403 `super_admin_required`, D133's rule as `admin.ts` applies it. An administrator is an `admin` role or a `super_admins` row, as D1042's `isAdminAccount` counts it.
- **Your own record** is not a cross-admin read.
- **An unknown or malformed id** is 404 `account_not_found`.

### 5. Every block on its own

Each block is `{ available: false, reason }` when it cannot be read: `not_set_up` when this database lacks the store, `unreadable` when the store fails. One block failing never blanks the other, and neither is ever a 0 or an empty list. The log line names no account, only that a read failed.
