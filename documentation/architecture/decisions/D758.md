## D758 — Every library document renders from a coded template

Issue: #1861. S1 decided every open point on 2026-10-18, under the owner's standing rule. This is the library half of the owner's Contracts request ("make sure also the documents in the current library uses the templates … hardcode the documents"); #1862 (the send paths) and #1863 (one text per document) are the other halves. The canvas is "Legal Documents · Templates", boards L8 and L9. This decision draws no screen: it changes which state each catalog row is in.

### Why

- **24 bodies lived only inside a migration.** The old FastAPI plain-text templates (`lpa`, `ppm`, `safe` and 21 more) were seeded by migration 085 and had no file, so the repo held no copy of the text a row printed.
- **25 production rows are stubs although each has a file** (D706, "The 25 stubs that have body files"). Every send of them skips the store and falls to `buildTemplateBody` in `routes/esign.ts`: an inline paragraph for the 15 spaced slugs, and a generic "Closing Binder" text titled with the raw slug for the other 10.
- **The canvas draws one document that has no row:** "Operating Partner Agreement (Spin-Out Lab)" (L8, row "Internal Management (GP Level) · 34").
- **The seed generator rewrote an applied migration.** `gen_refresh` always rewrote 113, and on main a run produced a different file, because `privacy_v1.md` gained the company address after 113 was written (#296). D705 recorded the hazard and left the map alone.

### What was decided

1. **"Hardcode the documents" means four things.** Every catalog row's text is a file under `cloudflare-worker/src/templates/legal/`. Each store row is filled from its file by a migration, never by hand. Every sender reads the row (#1862, #1863). No clause text is written: counsel stubs stay stubs (D706; D717 decision 4). D758 changes D706's "Nothing here changes which text any send produces" for D706's 25 rows only.
2. **The 24 seed-only bodies become files, byte for byte.** Each is `<slug>_v1.md` and holds the store text exactly as 085 left it (469 changed none of them), with no newline added at the end. They keep the four flat tokens the incorporation wizard fills (`company_name`, `incorporation_date`, `registered_agent_name`, `registered_agent_address`); changing a token would change the text. `services/legalTemplates.ts` does not import them, and none prints the Fund's old name. `LEGAL_REVIEW.md` lists them as "seed skeleton, counsel to expand".
3. **Migration 484 fills every row that has no text, and only those.**
   - **The gate** is `is_active = 1 AND length(trim(body_md)) = 0`. A row with any text is never touched, which protects an admin's edit and every body production already holds; a soft-deleted row is never touched. The editor sets `is_stub` from the body on every save, so "no text" and "stub" are the same rows for anything it wrote; the text gate is the stricter. A row an admin emptied on purpose is filled once, and its empty version stays in history.
   - **A new version, never an in-place edit,** as 469: the row is first copied into `legal_template_versions` (INSERT OR IGNORE on `(template_id, version)`, `created_by` = the row's `updated_by`, `doc_kind` and `axal_party` kept); then `body_md`, `merge_fields` (the body's tokens, sorted, as `extractMergeFields`), `is_stub = 0`, `version + 1` and `updated_at` change. The title, category, kind, party and `updated_by` do not: no person made this change.
   - **Re-runnable.** After one run no row matches the gate.
   - **Which file.** The generator's map: `all_md_bodies()` (FULL_BODY_V1, then NEW_BODY_V1, then ESIGN_MD, first wins), then `SEED_SKELETON_V1`. `investment_management_agreement` is not filled although its file exists: it is a counsel stub and the generator does not map it. Where the mapped file prints "Axal VC Fund I, LP", D705's successor fills the row; for the 25 that is `partner_capital_v2.md` and `investor_subscription_inst_v2.md`. The generator refuses to write a body that prints the old name.
   - In production that fills D706's 25; elsewhere it finds nothing to do. No production read was needed first. Data only, no `BEGIN` or `COMMIT`.
4. **The Operating Partner Agreement gets a catalog row, as a counsel stub:** slug `operating_partner_agreement_spin_out_lab`, title "Operating Partner Agreement (Spin-Out Lab)", category `gp`, `is_stub = 1`, `body_md = ''`, `merge_fields = '[]'`, version 1, active. It is inserted as 478 inserts `securities_legend` (`INSERT OR IGNORE … SELECT … WHERE NOT EXISTS`), so an admin's row under that slug is left alone. It joins `COUNSEL_DRAFT_SLUGS` (now 32), so its card reads "Stub — counsel to draft.". No kind or party is stored: the slug gives `agreement` and `management`, which is L8's "Axal VC Management LLC, as Managing Partner". Whether it is the same document as "MSA + Equity-for-Services (Operating Partner)" is for counsel (`LEGAL_REVIEW.md` asks).
5. **Kind and party: no override is stored.** On 20 rows L8's party line differs from the pair the slug gives:
   - eight agreements drawn "Axal VC GP LLC (for the Fund)" where the slug gives `gp`: `carried_interest`, `investor_nda_axal`, `lpa`, `mgmt_company`, `ppm`, `SPV Joinder Agreement`, `Strategic Side Letter / Focused SPV` and `Secondary Purchase Agreement`;
   - `lpac_charter` (drawn for the Fund, slug `gp`) and `clawback_guarantee` (drawn "the GP’s members, to the Fund", slug `fund`);
   - ten policies and filings drawn with a publisher or filer line where the slug gives `none`: `aml_kyc`, `form_adv`, `privacy_v1`, `tos_v1`, `compliance_manual_code_of_ethics`, `investor_privacy_notice_reg_sp`, `valuation_policy`, `conflicts_allocation_policy`, `certificate_of_limited_partnership_de` and `form_d_filing_kit`.

   That is the canvas folding D705's two parties into one and naming a publisher a policy does not sign for. D717 decision 1 says the issue and the repo win on data; #1852's editor lets the owner set any row's pair.
6. **The generator stops rewriting applied migrations and is the one slug-to-file map.** `gen_refresh` skips 113 when it exists, as `gen_085` and `gen_105` do. `SEED_SKELETON_V1` holds the 24 seed files and is not part of `all_md_bodies()`, so nothing emits a force-upsert for them. `gen_484()` writes 484 once and skips it when it exists. A run of the generator on main changes no file.
7. **What a send does once 484 is live.** The rows it fills send their file's text through `templateBodyFor`'s store step, not the inline paragraph or the Closing Binder. `buildTemplateBody` stays until #1862 deletes it, after 484 is live in production. The desk still sends only published rows; a filled row can now be published (#1852's "Publish v[N]").
8. **Not changed:** `privacy_v1`'s replay drift (the row has text, and production holds `privacy_v2.md`); the senders (#1862, #1863); the merge schema (its comment is corrected, and no token is added); branch and bootstrapped databases, which carry no seeded bodies (085, 105 and 113 are below the bootstrap cutoff and the baseline holds no rows).
