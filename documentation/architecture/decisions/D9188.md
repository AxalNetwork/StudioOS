## D9188 — Investor seat invites and revocations are conditional writes (#9188)

**Why.** `cloudflare-worker/src/routes/investor_seats.ts` counted an
account's active seats, compared the count with the Institutional cap, and
inserted in a later statement, then raised `users.investor_seat_count` in a
third. Parallel invites could exceed the plan's seat cap. A revoke checked
`revoked_at` in JS and then ran three separate writes, the last an
unconditional decrement, so parallel revokes could drive the stored count
below the true number (billing shows it as `quotas.seat_count`). And because
`investor_seats` keeps `UNIQUE(primary_user_id, seat_email)` and a revoke only
sets `revoked_at`, a revoked address could never be invited again: the invite
answered 409 `already_invited`, saying the address already had a seat.

**What changed.**

- **Invite** is one `DB.batch` of three statements. The first brings back a
  revoked row for the same address as a fresh invite (`revoked_at`,
  `accepted_at` and `seat_user_id` cleared, a new token, a new `invited_at`);
  the second inserts a new row when the address has none. Each writes only
  while the active count, read inside that statement, is below the cap. The
  third sets `investor_seat_count` from the rows. When neither row statement
  changed a row, the reply is 409 `already_invited` if the address holds an
  active seat or open invite, otherwise 409 `seat_cap_exceeded` with `cap` and
  `used`. The old link of a re-invited address no longer opens anything.
- **Revoke** is one `DB.batch`: the seat user's downgrade (only while the seat
  is still active inside the batch), `UPDATE … WHERE id = ? AND revoked_at IS
  NULL`, and `investor_seat_count` set from the rows. Only the request whose
  revoke changed a row logs `investor_seat_revoked`; the others answer
  `{ ok: true, already_revoked: true }`, as an already revoked seat did before.
- **The count.** `investor_seat_count` is kept, because
  `/api/billing/investor/status` reads it from the user row, but every seat
  write now sets it from the rows in the same transaction instead of adding or
  subtracting one, so it cannot drift from them. A count that drifted before
  this change is corrected at that account's next invite or revoke.
- No schema change.

**Tests.** `cloudflare-worker/test/investor_seats_concurrency_9188.test.ts`
(4 tests) fires requests with `Promise.all` over the real-SQL D1 shim, with a
turn of the event loop before each D1 call so the requests interleave. It
covers parallel invites stopping at the cap, parallel revokes of one seat
lowering the count by one, invite → revoke → invite answering 200 with a fresh
token and one active seat, and a re-invite at the cap being refused. Each case
asserts the rows and the stored count. Three of the four fail against the
previous route. `investor_seats_d611` and `investor_seats_d632` stay green.

**Mutation check** (`investor_seats_concurrency_9188.test.ts`): 10 mutations,
9 caught, 1 equivalent (running the invite statements one by one instead of
in a batch: each carries its own cap condition and D1 runs one statement
atomically, so the cap still holds; the batch keeps the count with the row
change).

**Rollback.** Revert the commit. No data migration to undo: rows written by
the new code have the same shape as before.
