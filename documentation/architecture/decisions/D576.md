## D576 — Spin-Out Lab: a founder's tech-transfer answer re-sequences their Week 1

**A Lab member's Week 1 steps are ordered by the tech-transfer answer on their
application, through a per-member plan store with one rule per status.** Slot
S10, issue #1189, 2026-10-06. This is the owner's answer B on #978, which
builds the canvas's promise that D384 had dropped from the apply panel.
Migration 396.

### Where the answer and the steps live

- **The answer** is `tto_status` in `spinout_applications.answers_json`
  (D383, migration 315), one of `not_disclosed`, `disclosed`, `negotiating`,
  `signed` or `not_applicable`. An independent build is asked no
  tech-transfer question. An application from before 315 has no answers.
- **The steps** are the catalog's Week 1 milestone keys
  (`services/spinoutLabCatalog.ts`), which is not edited. There are ten: the
  four the week gate requires (`project_created`, interviews 1 to 3) and the
  six optional deliverables (interviews 4 and 5, `market_sizing_completed`,
  `profiling_completed`, `icp_defined`, `market_research_shared`).

### The rules

`services/week1Plan.ts` holds the rule table, the one place the orderings
live. It has one rule for each stored status, plus `independent` and
`not_recorded`. Each rule has a label (what "Ordered for:" prints), a
one-sentence reason, and an order:

| Rule | Order (after `project_created`) |
| --- | --- |
| `not_disclosed` | ICP, market sizing, interviews 1–3, profiling, interviews 4–5, research shared |
| `disclosed` | interviews 1–3, ICP, market sizing, profiling, interviews 4–5, research shared |
| `negotiating` | market sizing, ICP, interviews 1–5, profiling, research shared |
| `signed` | interviews 1–5, ICP, market sizing, profiling, research shared |
| `not_applicable`, `independent`, `not_recorded` | the catalog's own order |

**A rule orders the steps; it never adds or drops one.** #1189 allowed a rule
to add or skip a step. None does:
- an added step has no milestone key, so it could never be marked done;
- every catalog key is either in the week gate or on the checklist.

A test holds every rule to the catalog's ten keys, each once.

**The reasons.**
- *Not disclosed:* until the office knows, the founder talks about the
  problem, not the invention. Customer and market come first, and research
  is shared last.
- *Disclosed:* interviews come first, so the licence talk starts from
  evidence.
- *Negotiating:* a licence is scoped by field of use, so the market is sized
  first.
- *Signed:* the company can hold the IP, so every interview comes first.

### When a plan is written

A member has one plan (`spinout_week1_plans`, keyed on `user_id`):
- **When the answer is saved.** `POST /spinout-lab/apply` computes it after
  the application is stored. A later application (after a withdrawal or a
  decline) is a changed answer, and it recomputes the plan.
- **When Week 1 starts.** `POST /spinout-lab/start` computes one only if none
  is stored, for a member who applied before this change. Starting again
  writes nothing.

A plan that cannot be written never refuses the application or the start. It
is logged, and the start computes one later if none is stored by then.

**Before and after Week 1 starts** (`planSteps`). Week 1 has started once
`users.spinout_lab_started_at` is set.
- **Before it starts,** a recompute takes the new rule's order whole.
- **After it starts,** the steps already done keep their places at the head
  of the plan, in the order the previous plan had them. Only the steps not
  yet done follow the new rule's order.

Today nothing changes an answer after a member is admitted (`/apply` refuses
an admitted account), so this branch is the rule for when something does.
The plan records `started` so the admin can see which branch wrote it.

**Every write records its actor.** `computed_by` on the plan is
`user:<id>`: the member writes their own plan by saving their answer or
starting Week 1. Each write also appends a row to
`spinout_week1_plan_history` with the actor, the reason (`applied` or
`started`), the rule and the steps. The plan row and its history row go in
one batch, so a replaced plan is never lost.

### Who reads it

- **The member,** on `GET /spinout-lab/state`, as `week1_plan` (rule, label,
  reason, steps, who wrote it and when) and `week1_plan_unreadable`. Only the
  caller's own plan is read; no path takes an id.
- **An admin,** on `GET /api/admin/cohort/applications`, which is already
  `requireAdmin`. Each applicant carries `week1_plan`, read from the cycle's
  applicants on its own query, so a database without 396 still lists them.
  There each says the plan could not be read, never that none exists.

### On the pages

- **The member's Week 1** (`SpinoutLabWorkspace`). The checklist rows are
  ordered by the plan: a row sits where its first key sits. One line above
  them reads "Ordered for: <status>." with the reason. With no plan stored,
  it reads "Ordered for: Not recorded" and says why the standard order is
  shown. A failed read is Unreadable.
- **The apply panel** says what the answer does again: "If you join the Lab,
  this answer orders your Week 1 steps, and your Week 1 names the status it
  is ordered for." It names no order, because the rules stay in the Worker
  and are not copied into the SPA. A test checks the SPA holds no rule.
- **The admin's applicant row** (`AdminApplicantDetail`) shows the plan: the
  status, the steps in order, who wrote it and when, and whether Week 1 had
  started. With no plan it says Not recorded, and on a failed read it says
  Unreadable.
