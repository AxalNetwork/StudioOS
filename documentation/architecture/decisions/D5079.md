## D5079 — a refused read ends the rendering of authoritative data (#5079)

Issue: [#5079](https://github.com/AxalNetwork/StudioOS/issues/5079). Parent: #4863.
Companion contracts: #5070 (the safe refusal copy), #5074 (the canonical capabilities).

### What was wrong

`/raise/cap-table?project_id=12` is not a page of its own. It is the Raise
module page, with the Cap table tool injected as that page's `subnav`. The two
read different routes, gated differently:

| Read | Gate | An admin |
|---|---|---|
| `GET /api/captable/record/:projectId` (the tool's) | `canReadProject` | **403** — a studio or HQ role never inherits a raw legacy read (D1130) |
| `GET /api/cycles/raise/modules/cap-table` (the page's) | `canWrite` | **allowed** |

So a Super-Admin-backed session previewing the Founder shell was correctly
refused the cap table, and the page behind that refusal was correctly answered
with an empty module read. The screen then showed, in this order:

> ⊘ This cap table belongs to another company. Switch company, or ask its
> founder for access.
>
> Cap table · at a glance — Planned round — No holders yet — Holders — No
> records yet — *(Eadwyn's two proposal bands)* — Evidence

The refusal is authoritative. Everything under it was not. StudioOS keeps
**Not recorded**, **Unavailable**, **Refused** and a measured zero apart on
purpose, and this collapsed all four: a member could read it as a venture with
nothing in it when the platform had simply declined the read.

The other sensitive Raise tools had the same shape, and two had worse copy:

- **Data room**: Home drew `null` for an admin's `summary` answer, so the
  module's empty card, checklist and Evidence stood in its place.
- **Capital relationships**: `CapRelOverview` had **no refused state at all**.
  Every failure, a 403 included, was drawn as `Unreadable` — "This is not a
  claim that nobody has committed" — which claims the store could not be read
  when in truth it was not shown.

### The decision

**A tool's authoritative read decides whether the page draws authoritative
data for it.** Each sensitive Raise tool reports a refusal to the page through
one `onRefused` callback; `CycleRoute` turns that into the module page's
`refused` status. The page's existing refused branch then withholds the card,
the records table, its Add and row actions, and the children — Eadwyn's bands,
the module's parts and the Evidence block — on both the desktop and the phone
page. `subnav` sits outside that branch, so the tool's own refusal and its tab
row (explicitly non-data documentation: what the tool includes) stay.

Three further rules fall out of it:

- **A refusal is not a failed read.** `raiseReadState` in
  `frontend/src/lib/raiseErrors.js` is now the one definition: 403 and 404 are
  refusals, everything else is a failed read. 404 is a refusal because a
  venture outside the caller's scope answers 404 so its existence is not
  confirmed — a decision about access, not a missing store. Six tools each
  carried their own copy of that test, and one of them had none.
- **Nothing that speaks for the record survives a refusal, and nothing that
  writes to it.** The Cap table's tool bar (As of, the 409A line, the Carta
  state) and Record an issuance go with the data, as does the Home note that
  promises "the Holders list and the Planned round card below".
- **The page says why there is nothing, in its own words.** `refusedNoData`
  gives one sentence — "Nothing of this cap table is drawn here, because the
  read was refused. That is not a claim that nothing is recorded." — rather
  than repeating the tool's sentence above it.

One block's refusal is that block's, not the tool's. A viewer may read the
pipeline and not the round, so the round's own refused line says the round is
not theirs to read rather than claiming the whole tool is, or that the read
failed. The page keeps drawing the module in that case, because the tool's
authoritative read succeeded.

Where a read-only support path exists, the refusal names its door: an admin
refused the cap table is offered the reason-gated read at
`/cap-tables/:projectId`, which they previously had no way to reach from this
page. A founder, who has no such path, is still offered Ask for access.

### What did not change

No gate moved. The Worker refuses exactly what it refused before, and the
module read still answers an admin: this decision is about what the page draws
under the actual backend permission result, not about who may read what. The
Founder shell preview remains chrome only (D914's rule: the authenticated role
decides access, and a shell preview is not a different principal); this fixes
the data-shaped empty states that preview exposed, not the preview itself.

The Calls tab's own state machine still takes `ready`, `loading` or
`unreadable` only, so `CapRelTool`'s module read keeps those two answers; the
refusal contract there is the Overview read's.

### Where it is held

`frontend/test/raise_refused_no_data_5079.test.mjs` mounts the real
`CycleRoute` on a stubbed Worker whose module read succeeds while the tool's
own read is refused, for all three tools, and checks the empty, failed and
`summary` cases beside the refused one. Every assertion is checked both ways.
