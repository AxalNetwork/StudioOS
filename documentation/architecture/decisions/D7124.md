### Why

On 2026-11-17 nothing merged from 09:00Z to 15:25Z: 263 of 294 `merge_group`
runs failed (#7108). `promo_issued_report_5949.test.ts` pushed a report stamped
with a fixed `NOW` while the HQ read it asserted on used the real clock against
a 48-hour threshold. `check-test-clock` passed it, correctly by its rule: the
test file never read the clock. The nightly +7-day run had counted it 46.6
hours earlier, in an alert that said "2 verified test failures" with a run
link whose names lived only in a 3-day artifact. Nobody acted on it.

### A. At PR time

`scripts/future-clock-changed.mjs` lists the test files a pull request adds or
edits (`git diff --diff-filter=AMR` against the PR base), keeps those a suite
runs (`test:frontend`, `test:worker`, `test:meeting-bot`, `test:retention`; no
`_*` helper), and runs them with each suite's own command from `package.json`,
under libfaketime with the nightly's environment
(`FAKETIME_DONT_FAKE_MONOTONIC=1`, `FAKETIME_DONT_RESET=1`,
`NODE_OPTIONS=--import scripts/future-clock.mjs`, so children get the clock and
workerd does not) after `scripts/future-clock-check.mjs` proves every clock
moved. No Date-only mode (817 false failures on 2026-11-10).

- **Two offsets.** `+7d`, and `+9d 11h`, which changes the weekday and the time
  of day (`+7d` keeps the weekday and cannot catch #4770, "fails every
  Saturday"). libfaketime reads `"+9d 11h"` as nine hours, so the script passes
  it `+227h`.
- **Verdict.** A file that fails ahead runs once more on the real clock. A test
  that fails ahead and passes now fails the step with an `::error file=…`
  annotation naming the file, the test, the offset and the fix, and a table in
  the job summary. A test that fails on both clocks exits 0: the suite reports
  it. A clock that did not move fails the step, so a silent no-op never reads
  as "nothing breaks".
- **Where it runs.** One step in the existing `suite` job, `rest` part only,
  on non-draft `pull_request` only. `rest` already has every install and the
  built SPA, and is in every PR tier. No new job, no new required check: the
  step fails a job the gate already reads. `merge_group` runs are unchanged.
  The step lists the files first and installs libfaketime only when one
  changed; with none it logs "no changed tests". Above 40 files it says the
  nightly covers them and exits 0.
- **Reproduce:** `node scripts/future-clock-changed.mjs --offset '+9d 11h' <file>`
  (needs `apt-get install faketime`).

### B. The nightly alert, inside D5663

- The trusted reporter (`future clock (report)`) already holds verified TAP.
  It now writes each failing test, with its file and part, plus a reproduce
  command per file, to **its own job log and `GITHUB_STEP_SUMMARY`**. Only parts
  with no D5663 discrepancy are listed; with incomplete evidence the summary
  says the list may be short.
- The issue and the Slack text gain two derived facts and no raw text: the
  **break date** (the run's start plus 7 days, `YYYY-MM-DD`, validated again in
  `safeHealthFacts`) and "the names are in the run summary". While the alert
  is open, each failing night replaces one `Latest failing run:` line on the
  issue, so its link reaches a run whose summary still exists.
- `future-clock-*` artifacts are kept 14 days instead of 3, past the 7-day fuse.
- **Routing.** AGENTS.md § Red main: an open `[alert] future-clock tests
  failing` is a main repair due before its break date, and Session 1 files the
  slot task from the run summary. The coordinator-audit skill checks it. No
  label is added to the alert issue.

### Owner decision left open

Whether D5663 should be amended so the alert issue may carry sanitised test
names or a `state:ready` label. This decision assumes **no**: names go only to
the reporter's job log and step summary.

### What this does not do

It does not catch a fuse longer than the offsets, or a source-only change that
makes an untouched test date-bound; the nightly covers both, and part B makes it
readable. It does not touch `scripts/lib/futureClockEvidence.mjs` (#5663).
