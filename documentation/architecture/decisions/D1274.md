### 1. Migration 631: what each redemption was for

`promo_redemptions` gains seven nullable columns:

| Column | What |
|---|---|
| `source` | `cart`, `payment`, `free_unlock` or `subscription` (CHECK) |
| `product_id`, `price_id` | the catalog product and price, when the redemption was for one product |
| `billing_interval` | `day`, `week`, `month` or `year` for a subscription; NULL for a one-time charge (CHECK) |
| `amount_before_cents` | what the member would have paid without the code (≥ 0) |
| `discount_cents` | what the code took off (≥ 0) |
| `currency` | the ISO code, lower case |

- **Nothing is backfilled.** A redemption made before 631 has no source, product or amount. Every read counts it as `not_recorded`; it is never read as 0 or given a guessed source.
- Two indexes: on `created_at`, and on `(promo_id, created_at)`.
- `ensurePromoSchema` creates the same columns on a fresh database.

### 2. Where each source is recorded

| Source | Where | The detail |
|---|---|---|
| `payment` | `payment_intent.succeeded` in the billing webhook, for any PaymentIntent carrying `promo_code_id` (the generic intent and à la carte) | Checkout now stamps `product_id`, `promo_amount_before` and `promo_discount` on the intent (`promoDetailMeta`), because the intent's own amount is already discounted. An intent made before this records the currency only |
| `cart` | `fulfilOrder` (`services/orders.ts`) | the order's subtotal, discount and currency; the product and price only when the cart holds one product |
| `free_unlock` | `fulfilFreeUnlock` | the product and price. **The whole price is the discount**, because nothing is charged |
| `subscription` | `invoice.paid` in the billing webhook (`recordInvoiceRedemption`) | the invoice's subtotal, its discount lines, currency, and the first line's price, product and interval |

- **The detail is written once.** It is stamped after the redemption itself, only where none is stored (`source IS NULL`), so a re-delivered webhook never rewrites it. A malformed field (a product id that is not `prod_…`, a negative or fractional amount, a currency that is not three letters) is stored as NULL.
- **The count is unchanged** for every one-time source: `times_redeemed` still rises once per redemption, as before.

### 3. A subscription's redemption

Stripe redeems a promotion code on a subscription natively. Until now, only Stripe counted it.

- **Recorded from the first paid invoice:** `billing_reason: subscription_create`, with a discount. A renewal is never a redemption.
- **Keyed `sub:<subscription id>`** in `payment_intent_id`, so a re-delivered invoice, or a later one, records nothing more.
- **The code is the subscription's `promo_code_id`**, which checkout stamps (`routes/payments.ts`). The invoice carries the subscription's metadata on current API versions. When it does not, the subscription is read from Stripe, only for a discounted first invoice.
- **It never bumps `promo_codes.times_redeemed`.** Checkout's cap adds Stripe's counter to the mirror's (`totalRedeemed`), so a bump would count the subscription twice.
- **The drawer's count stays Stripe's.** `GET /:id/redemptions` returns `stripe.times_redeemed` beside the list, and says `unreadable` or `stripe_not_configured` when Stripe cannot be read. Subscriptions redeemed before this are only in Stripe's count, so the list's length is never the count.
- **It never fails the webhook.** The invoice's alerts and receipts do not wait on a usage record, and Stripe still counts a redemption whose record is lost. The log line names no code, id or amount.
- A code the mirror does not hold, or a subscription with no member id, records nothing.

### 4. The reads (HQ Super Admin, `requireSuperAdmin`)

| Route | Answers |
|---|---|
| `GET /api/admin/promos/usage?from&to&promo` | the Usage tab's five blocks |
| `GET /api/admin/promos/:id/redemptions` | the code's recorded redemptions, newest first (at most 100), each with its member's name, and Stripe's own count |
| `GET /api/admin/promos/:id/history` | the code's `promo_create`, `promo_update` and `promo_delete` rows from `admin_audit_log`, oldest first |
| `GET /api/admin/promos/export.csv?from&to&promo` | the range's redemptions as a CSV, audited as `promo_export` |

- **The range** is whole UTC days, `YYYY-MM-DD`, both included. It defaults to the last twelve weeks (84 days) and may be at most 366 days. A bad, reversed or too-long range is refused with 400 `invalid_range`, never clamped. A `promo` that is not a promotion code id is 400 `invalid_promo`.
- **Every block is `{ available, reason, … }`.** `reason` is one of:
  - `unreadable`: its query failed. One failed block never blanks the others;
  - `no_redemptions`: the range has none, so there is nothing to divide or rank;
  - `not_recorded`: there are redemptions, but none carries the detail.
- **The blocks:**
  - `redemptions`: the total and the members (each counted once). Every week of the range, Monday first, is split by source plus `not_recorded`, and a week with none is a measured 0. `detail_recorded_from` is the first redemption that carries a source, which is when the page can say "counted from".
  - `discount`: per currency, never added across currencies: redemptions with a recorded discount, the sum, and the average over those redemptions only. `not_recorded` counts the rest.
  - `top_codes`: the ten codes most redeemed in the range, each with its cap. `mirror_redeemed` is the mirror's lifetime count, a lower bound.
  - `products`: the twenty most-redeemed product, price and interval rows, with the catalog name where `stripe_products` holds it. `not_recorded` counts carts of several products and every pre-631 redemption.
  - `near_end`: active codes that end within 14 days, or are at their cap by the mirror's count, cap first, then soonest. This is sound because a code the mirror calls exhausted is exhausted. A paused code is left out. This block is not limited to the range.
- **History shows only the payload fields a history needs:** code, type, percent and amount off, currency, products, cap, expiry and active. The coupon id and anything else logged stay in the log. Only rows with `report_type = 'billing'` count.
- **The export:**
  - columns: `redeemed_at, code, promo_id, member_id, source, product_id, price_id, interval, amount_before_cents, discount_cents, currency`, oldest first;
  - a blank cell is "not recorded";
  - it holds at most 20,000 rows. A cut export says so with `X-Export-Truncated: true` and in its audit row;
  - it carries no member name or email, only the id;
  - the audit row records the range, the code filter, the row count and whether it was cut.
- **Every statement is a bound literal**, so no new raw-interpolated SQL is added (`schema_guards`).

### 5. Decided here

- **The per-code redemptions read is in this part.** The issue's "redemption detail" is the drawer's Redemptions frame (PRM2b), and part 6 (D1276, #3302) needs a read to draw it. It costs one route and no new store.
- **`payments.ts` and `orders.ts` change too,** though #3300 names `admin_promos.ts` and `billing.ts`. The detail has to be stamped where the amount before the discount is known: at checkout for a PaymentIntent, in the order for a cart.
- **A free unlock's discount is the whole price.** The member was charged nothing, even when the code's own discount left a sub-minimum amount.
