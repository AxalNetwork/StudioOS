### 1. Template sets

A form's template set is its catalogue pack items of kind `document` with a `template_key`, in position order. No text is written here: a body is the template store's active, non-stub row, supplied by counsel.

- **The six legacy forms** (`legacy_gate = '1'`) keep the wizard's rule exactly: a contract type is `pending_esign`; no body is `pending_counsel` for `COUNSEL_REQUIRED_TEMPLATES` and `pending_body` otherwise; the five flat tokens are filled with the wizard's values, placeholders included; a venture document already made from the template is reused. The parity test runs the real wizard and this service over the same data for all six and compares the documents written and every list.
- **Every other form**: a template is used only when an `approved` counsel review of its current body names the form's country (`templateApprovedFor`, D6693). This applies to every template of the set, not only those marked `counsel_required`: the issue says a template is usable only when its review matches the country. A missing body is `pending_counsel` when the item is counsel-required, else `pending_body`.
- A body with a token the case does not hold is `pending_fields` with the missing tokens. It is never written with a hole or a placeholder (D411's rule for sends).
- One generated row per case, template and person (a unique index). A second run reuses it; it is never rewritten. A changed template or case after generation does not regenerate (see section 7).

### 2. The merge schema

`FORMATION_MERGE_FIELDS` lists the tokens: the five flat ones (`company_name`, `jurisdiction`, `incorporation_date`, `registered_agent_name`, `registered_agent_address`), `company.legal_name`, `form.*`, `country.*`, `people.<role>` and `people.all`, `ownership.summary`, `capital.*`, `registered_office.address`, and for a consent `person.name` and `person.roles`. The company name and agent come from the case's latest order; generation needs an order. The registered office is the registered agent's address on the order: nothing else records a registered office yet.

### 3. Consent to act

The appointee roles are `director`, `resident_director`, `managing_director`, `secretary` and `legal_representative` (`APPOINTEE_ROLES`). `president`, `deputy`, `contact_person` and the owner roles are not appointees. A pack item whose `item_key` starts `consent_to_act` is generated once per appointee. An appointee consents by signing that document (an envelope with `purpose = 'consent_to_act'`) or by an upload HQ, a partner or counsel records (`recordConsentUpload`, a document already stored through the classified upload). Either sets `formation_case_people.consent_to_act_at`. A consent envelope records the person's revision when sent; if the person was edited before it completed (an edit clears consent, D6705), the signed copy still lands but the consent is not recorded.

### 4. The gate

`submitFiling` refuses an incorporation filing with `founder_approval_required` unless the founder's approval matches the pack hash, then with `consent_to_act_required` while any appointee has no consent. `markReadyToFile` applies the same two checks, so a v2 case reaches `ready_to_file` only when both hold. The trigger `trg_formation_filing_consent_to_act` holds the consent rule in the store for any writer. D6694's test now approves the pack before `markReadyToFile`.

### 5. Signing and the owed effect

The founder sends a generated document (as rendered text, `renderedBody`) or a contract template of the set (filled from the case) through `createAndSendEnvelope`, whose rules are unchanged (restricted templates, unfilled tokens). The same batch writes `formation_case_envelopes` and an `esign_effects` record of kind `formation_case_signed`.

The completion batch in `routes/esign.ts` is not changed, so it never names a formation table (most e-sign tests build a schema without one). Instead the record is **owed at send**: `owedEffectStatement` writes it when the envelope is sent, and the claim and the tick's sweep now run a record only when its envelope is `completed`. A record written at completion (the staged kind) always meets that, so nothing changes for it. On completion `runEnvelopeEffects` runs it; a failure is a `failed` record the tick replays.

`onCaseEnvelopeCompleted` writes a `documents` row pointing at the signed copy e-sign already stored (no new file), puts it on the case as `evidence`, origin `signed_copy`, with the SHA-256 of that file from `legal_document_files`, and stamps the consent. Its documents uid is derived from the envelope, so a replay adds nothing.

### 6. Pack approval

`setPackForApproval` sets a filing's pack (`setPack`, which clears the earlier approval) and opens the founder's approval request bound to the new hash and the filing (D6695). An active approval request of the filing bound to another hash is cancelled; one bound to the same hash is kept. `setPack` and `createFiling` themselves are unchanged: the HQ and partner routes call the documents service to get the request.
