### 1. What is stored, and what is not

One row per segment key:

| Field | Rule |
|---|---|
| `name` | 1 to 80 characters |
| `profile` | founder, investor, advisor, partner, exploring, or `any` (the canvas's "Any profile") |
| `status` | `active`, `draft` or `retired` (§3) |
| `who` | Who they are, at most 280 characters, or none |
| `typical` | The typical member: at most 4 lines of up to 120 characters |
| `needs` | At most 6, in HQ's order. Each has an `id`, its `text` (1 to 200 characters) and up to 6 answers, each `{ kind, ref }`. |
| `offers` | `programs` (keys in `programs`, #2371's registry), `perks` (uids in `perks`) and `content` (slugs in `articles`), at most 20 of each |
| `version` | 1 for the seed, then one more for each write |

Three things the canvas shows are **not** stored here, because something else already decides them, and a stored copy would say what the product does not do:

- **Sidebar links** are the persona's `nav_extras` in code. That is what the sidebar draws, by D998's rule: a link shows only when the member's account role is the segment's profile in code. The profile returns them as `offers.sidebar_links`, read only.
- **Events** are each event's own audience rule (D567), read by the needs read (§4).
- **The sign-up questions** stay in code (D997 §5). The profile returns how many there are.

A need's answer is a `program`, `perk` or `content` that this segment offers, one of its code `sidebar_link`s (by address), or `events` (no ref). A write that names anything else is refused.

**The seed** is the twelve as code describes them on this date: the label as the name, D998's profile, the short description as who they are, and Active. No need, offer or typical member is invented; those start empty. Each segment gets one `seeded` history row. The migration can be applied again without adding a row.

### 2. The routes

| Route | Guard | Returns |
|---|---|---|
| `GET /api/personas/segments` | `requireAdmin` | Every profile, with code's sidebar links, code's profile and the number of sign-up questions |
| `GET /api/personas/segments/coverage` | `requireAdmin` | The needs read (§4) |
| `GET /api/personas/segments/:key` | `requireAdmin` | One profile and its last 50 history rows |
| `PATCH /api/personas/segments/:key` | `requireSuperAdmin` (HQ only) | `{ segment, changed }` |

- **A write names the version it read** (`expected_version`). The UPDATE carries it, so of two editors who read the same version, the second changes nothing and gets 409 `segment_changed`, "This segment changed since you opened it. Reload to see the latest."
- **Only the fields present change,** and a value equal to what is stored is not a change. A write that changes nothing makes no new version and no history row.
- **Each change writes one history row in the same batch:**
  - the version;
  - the fields changed, with their values before and after;
  - the optional reason (up to 280 characters);
  - the Super Admin.

  It is copied to the admin audit store (`segment_profile_edited`) for Security's feed. A failed copy does not undo the write.
- **Refusals** are a sentence and a code:
  - `unknown_program`, `unknown_perk` and `unknown_content` for an offer no store holds;
  - `answer_not_offered` for an answer the segment does not offer, including taking away an offer a need still names;
  - `read_only` for sidebar links, events or the sign-up questions;
  - `invalid_*` for a limit;
  - `expected_version_required` for a write with no version;
  - 404 for an unknown key.
- **A D1 error is a 503,** never an empty list.

### 3. The status rules

| Status | Sign-up offers it | An admin may place a member in it | Current members |
|---|---|---|---|
| Active | yes | yes | keep it |
| Draft | no | yes | keep it |
| Retired | no | no: 409 `segment_retired`, "[Name] is retired, so it takes no new members." | keep it until moved |

- **Sign-up** (`GET /api/personas/taxonomy`, public) lists only Active segments. Each is listed under HQ's name and words; the questions stay code's.
- **The suggestion** (`POST /classify`) never suggests a segment sign-up does not offer. Such a suggestion becomes "pick one", and the alternatives are filtered the same way.
- **Finalize** (`POST /finalize`) refuses a primary or secondary segment that is not Active, with 409 `segment_not_offered` and "That segment is not open for sign-up. Pick one of the segments shown." The one exception is a segment the member already holds.
- **A code persona with no row** reads Active, which is what sign-up offered before this store existed.
- **A store that cannot be read** answers 503 on all three. It never falls back to the full twelve.

### 4. The needs read (`GET /api/personas/segments/coverage`)

For each segment:

- **Members:** primary segment, admin accounts left out. A count from 1 to 4 is suppressed.
- **Needs:**
  - `{ recorded: false }` when HQ has written none, which reads "Not recorded", never 0 of 0;
  - otherwise the total, how many are met, the gaps, and each need's answers with whether each resolves.
- **What makes a need met:** one of its answers resolves, by kind:
  - a `program` whose status is `live`;
  - a `perk` whose status is `live`;
  - `content` that is `published`;
  - a `sidebar_link` that is one of the segment's code links;
  - `events`, when at least one upcoming event is open to the segment.

  A need is a gap when no answer resolves. An answer whose store could not be read is unknown, not a gap.
- **`gap_kinds`:** the kinds a need asks for where nothing of that kind resolves (SEG1's "Gap" cells).
- **Offers by kind:**
  - programs, perks and content: how many are offered and how many are live;
  - events: how many upcoming events are open to the segment;
  - sidebar links: how many, and how far they reach.
- **Which events count:** published, not private, starting after now. The event's own registration rule must admit the segment: `everyone`, `selected` naming the segment, or `selected` naming its code profile as a role. Invite-only events do not count.
- **How far a sidebar link reaches:** of the segment's members, those whose account role is the segment's code profile, since only they see its links (D998). The reached and not-reached counts are suppressed together by `suppressGroup`: when either is 1 to 4, a second cell is hidden so the total cannot give it away. `profile_differs` says when HQ's profile is not code's.
- **Each kind is read alone.** A store that fails leaves the rest answering, and says it could not be read. The members read failing is a 503 for the whole read.
