## D5373 — Money correctness 2: every variable-currency amount is shown and written through `lib/money.js` (#5373)

- **Status:** Built for #5373 (slot S29). Part 1 2026-11-10 (#5452); part 2 2026-11-11 (the Use of Funds source text, the sweep, the cap-table five). Follow-up to D5029 / PR #5055, which built the layer and moved Revenue, the licence page and the licence terms form onto it.
- **Builds on:** D5029 (`frontend/src/lib/money.js`: ISO 4217 exponent, `parseMinor`, `formatMinor`), D5037 (Stripe's units at the refund boundary), D332 (event prices).
- **No migration. No new route.** The column names (`*_cents`) are unchanged. They always meant "a count of the currency's own minor units".

### The rule

A `*_cents` value is a count of its currency's own minor unit (JPY 0 decimals, EUR 2, KWD 3). Showing it, or turning typed text into it, goes through `lib/money.js`. A currency that is missing or is not an ISO 4217 code is **named beside the stored count** ("123,456 minor units (currency "XYZ" is not one we can price in)"); it is never read as euros or dollars. Stripe's own amounts (a price's `unit_amount`, a charge, a dispute, a coupon's `amount_off`) follow Stripe's rules (D5037, D5029 point 3): ISK and UGX are counted in hundredths although ISO gives them no decimals, and a three-decimal currency is taken in steps of ten.

### What the layer gained (all in `frontend/src/lib/money.js`, typed in `money.d.ts`)

| Function | For |
| --- | --- |
| `formatMinorOrCount(minor, code, opts)` | `formatMinor`, or the stored count with the currency named when it is unusable. Null only for a non-number. |
| `plainAmount`, `codeAmount`, `suffixAmount` | The grouped number alone ("20.00"), code first ("EUR 12,000"), code after ("12,000 JPY"), each at the currency's decimals. |
| `fromStripeUnits`, `toStripeUnits`, `formatStripeAmount`, `plainStripeAmount`, `parseStripeAmount` | Stripe's count (ISK and UGX hundredths; three-decimal currencies in steps of ten). `refundReview.ts` now reads its ISK/UGX list from here. |
| `majorToMinor(major, code)` | A legacy REAL column of major units to minor units at the exponent, rounded once. |
| `eventCurrency`, `formatEventPrice` | An event's `currency` column is NOT NULL DEFAULT `'usd'`; a payload that names none is that default, an unlisted code is named with the count. |

### The audit (every `/ 100`, `* 100`, `% 100` on a money value in `frontend/src` and `cloudflare-worker/src`)

The audit is the scan in `frontend/test/_moneyConversionScan.mjs`, run over every `.js .jsx .ts .tsx .mjs` file under both roots. **The scan is a heuristic, not a proof.** It reads one line at a time and flags a line that divides, multiplies or takes a remainder by a bare `100`, names money (or builds two fixed decimals, or formats the quotient as a locale number) and does not read as a percentage. It errs towards flagging, so the allow-list holds false positives (the `not-money` kind). It also misses: a conversion split over several lines, a `Math.round(a * 100)` on a value that no word on the line says is money, and a helper that hides the factor (`dollarsToCents(x)`). Part 2's sweep found three of those by reading (the table below). A clean scan means "nothing the heuristic can see", not "no manual conversion left".

### Part 2 (2026-11-11)

#### The Use of Funds source text

`cloudflare-worker/src/services/useOfFunds/eadwyn.ts` formatted a `*_cents` count as `(value / 100).toLocaleString('en-US', {2 decimals})` beside the currency code, so Eadwyn's source passage for a JPY plan read "JPY 50.00" for 5,000 yen. It now uses `codeAmount(value, currency, { trimWhole: false })`: "USD 1,500,000.00" and "EUR 12,345.67" read exactly as before; "JPY 5,000" and "KWD 1.250" read at their own decimals; a code the layer does not list names the stored count. The scan did not see it (no money word on the line, no `toFixed(2)`).

#### The scan's new rule

A line that divides or multiplies by 100 **and formats the quotient as a locale number** (`toLocaleString(`, `Intl.NumberFormat`, `FractionDigits`) is now flagged whether or not a money word is on it. It is the shape of the eadwyn line, and found three more (below). It adds no false positive in either source tree (a percentage, a ratio and a factor of 1000 stay out; the guard's own positive and negative lines pin that). A bare `Math.round(a * 100)` on a value no word marks as money cannot be told from `Math.round(p * 100)` on a percentage without reading the code, so no rule was added for it: those were found by reading.

#### The sweep

Searched in `frontend/src` and `cloudflare-worker/src` for `/ 100`, `* 100`, `/100`, `1e2`, `10 ** 2`, `.toFixed(2)`, `100 *`, `centsToDollars`/`dollarsToCents`/`toCents`-style helpers and a factor on its own line, then read every hit that sits in a file that handles a currency (about 450 lines, most of them percentages, chart geometry or `$`-labelled micro-USD). Use of Funds (frontend, Worker services and `cycle_use_of_funds.ts`) holds no other conversion: its `(cents * pct) / 100` lines take a percentage of an amount (units preserved) and `read.ts`'s `round(net_burn*100)` is a SQL validity ordering for the legacy USD project metrics.

#### The cap table's currency symbol (second commit of part 2)

The cap-table frontend printed a hard-coded "$" before every amount, whatever the venture's currency (a euro venture read "$5,000", a yen one "$5,000", a dinar one "$1.25"), and the figures it sits on are already whole major units, so nothing was converted: only the symbol and the decimals were wrong. `dollars(v, currency = 'USD')`, `price(v, currency)` (instruments), `short(v, currency)` (the chart labels) and every sentence built from them now take the venture's currency: the Today read's `currency` (`{ code }`), a simulation's `currency`, or the instrument's own. **USD is byte-for-byte what it was** (the existing tests that pin USD output pass unchanged, and the new test pins the exact strings). Any other code prints `${code} ${amount}`, the option pool's convention, the amount grouped as before at the currency's own decimals (JPY none, KWD up to three, else up to two); a code the layer does not list prints the number as stored beside the code, with no decimals guessed.

The Scenarios and Compare pages take the currency from the Today read they already load (`codeOf(today.data.currency)`); the Instruments page's convert-form hints carry a "$" only for USD.
