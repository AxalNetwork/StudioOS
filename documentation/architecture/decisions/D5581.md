### 1. Schema

| Table | What a row is | Changes allowed |
|---|---|---|
| `work_graph_assets` | One WorkGraph asset: `tenant_id`, `company_id`, `project_id` (D5579 scope), `kind` (D5579 `ASSET_KINDS`), `access_class`, `approval_policy`, and the accepted head (`head_revision_uid`, `head_seq`), plus `version_count` | Only the head and the count. A trigger refuses a changed scope or kind, a head that names no live revision of the asset, and every delete |
| `work_graph_revisions` | One immutable revision: `seq` per asset, `parent_uids_json` (same-asset lineage), `digest` (64 lowercase hex, checked by a `CHECK`), `byte_length`, `media_profile`, the `SourceRef` into the canonical domain store (`source_store`, `source_locator`, `source_id`, `source_revision`), recipe, residency, licence, `expires_at`, the author (`actor_kind`, `actor_user_id`, `agent_run_id`, `charge_id`), the retry key and request hash | Only `legal_hold` (toggle) and the tombstone (set once, never under a hold). A trigger refuses everything else and every delete |
| `work_graph_edges` | One dependency of a revision: `edge_kind` (`read`, `write`, `derived`, `component`), the other asset, and the revision it was pinned at | Append-only (triggers) |
| `work_graph_events` | The audit trail: action, actor, agent run, charge, base revision, mutated or published revision, `head_seq`, approval ref, approved digest, approver, outcome, refusal code, retry key and request hash | Append-only (triggers) |

**No content.** No column holds bytes, a preview, a rendered excerpt or model text, so a `restricted` asset has
nothing to leak. A revision points at its canonical domain row (D5579 §2) and holds only the digest.

**Why a WorkGraph event table and not `admin_audit_log`.** `admin_audit_log` (D159) is HQ's governance feed of
privileged admin actions; it is keyed by an admin user, and HQ's feed reads it unfiltered. A WorkGraph write is
a tenant's person or agent run, and its record must commit in the same D1 batch as the head move. Putting it there
would fill the governance feed with tenant work and could not carry the run, charge and approval as columns. No
domain revision table is duplicated either: WorkGraph's revisions are D5579's index over them.

### 2. How it works

- **Compare-and-swap head.** `advanceHead` issues one conditional `UPDATE work_graph_assets SET head_revision_uid
  = ?, head_seq = head_seq + 1 WHERE asset_uid = ? AND head_revision_uid IS ? AND <revision is live> AND <no edge of
  the revision is pinned off its dependency's head>`. The audit row is the next statement of the same batch,
  `INSERT … SELECT … WHERE changes() > 0`, so the move and its record land together or not at all. A refused swap
  is classified from what is true afterwards (`stale_revision` with the current head and `head_seq`,
  `stale_dependency`, `composite_incompatible` or `tombstoned`) and recorded as an `advance_refused` event.
- **The head only walks forward.** A revision may replace head H only if H is among its parents
  (`not_descendant` otherwise). So a writer who built on an older head cannot overwrite the accepted head by
  naming it, and A→B→A cannot recur, so `head_revision_uid` alone is a safe swap key.
- **Idempotency.** Every write carries a key, unique per (tenant, company): on `work_graph_assets`, on
  `work_graph_revisions`, and on `work_graph_events` per action for head moves. A retry with the same key and the
  same request hash (canonical JSON, SHA-256) returns the first result and writes nothing. That covers a lost
  callback, a late callback after the head has moved on, and two deliveries at once: the second batch hits the
  unique key, rolls back, and replays. The same key with a different request is `idempotency_conflict`.
- **Version cap and sequence.** The revision `INSERT … SELECT` takes `version_count + 1` as its `seq` and
  inserts only while `version_count < maxVersionsPerAsset`; the count is raised in the same batch. The cap holds
  under concurrency, and `seq` is read back from the inserted row, never from the pre-read.
- **Dependency DAG.** A revision's dependencies are written with it, each pinned to a revision of another asset in
  the same company that is that asset's head at the time (`stale_dependency` otherwise, and `composite_incompatible`
  for a composite's components). A self-dependency, or a dependency asset whose head already depends on this asset
  through any chain (one `WITH RECURSIVE` walk over heads' edges, bounded at `maxWalkDepth`), is
  `cyclic_dependency`.
- **Staleness is read, never stored.** An edge is stale when its pinned revision is not its asset's head now
  (`staleDependencies`). The swap re-checks it atomically, so a dependency that moves between creation and
  acceptance still refuses the head move.
- **Impact.** When a head advances, the result's `impact` names every revision built on the old head, transitively
  (one recursive query; `depth`, and `isHead` for outputs that are their asset's head), plus the approvals that
  were recorded when those outputs became heads (`invalidatedApprovals`). `impactOf` answers the same for any
  revision. The approval inbox stays the record of approvals (D5579 §1); WorkGraph holds only the ref and the
  digest approved.
- **Composites.** A `composite` asset's revisions consist of `component` edges, and only composites have them. A
  composite is accepted only while every component it pins is that component's head, so it never mixes
  incompatible parents silently.
- **Approvals.** Under `human_publication` a head moves only with an approval. D5579's validator checks it on a
  ChangeSet/ReviewDecision slice: an agent reviewer is `agent_review`, other bytes are `stale_approval`, and a
  revoked reviewer or writer is `revoked_author`.
- **Retention.** Nothing is ever deleted. `tombstoneRevision` is a person's act, one-way, refused under a legal
  hold and for the current head. The `UPDATE` re-checks both, and a trigger refuses a tombstone under a hold from
  any writer. A tombstoned revision can never again be a parent or a head. `setLegalHold` places or releases a
  hold and is audited.
- **Scope.** Every operation first checks the caller's scope with D5579's validator (a company-wide caller covers
  its projects; a project caller only its own), and refuses `wrong_tenant`.
- **Cost telemetry.** Every result carries `cost: { d1Statements, d1Batches }`: the statements the call issued,
  counted as they go. For example, a first head move costs 6 statements in 1 batch, and its replay costs 2.

### 3. Routes: none, and why

The issue says preview-only until a separate owner approval. A route, even Super-Admin-only behind a D1509-style
flag that defaults off, would be a mounted surface with nothing to approve it yet. Part 1 is the service and its
tests. The route that exposes it must be Super-Admin-only (legal holds and tombstones included), sit behind a
flag that defaults off, mount itself through the registry, and resolve the caller's scope through
`tenancyScope.ts` / `projectAccess.ts` (D5579 §1).

### 4. Limits

`WORK_GRAPH_LIMITS`: 2 GiB per revision, 500 versions per asset, 8 parents, 64 dependencies, a walk depth of 32.
Every call takes an override. The size limit and the version cap refuse with `size_limit` and `max_versions`.
Per-tenant plan limits are read in a later part. There is no retention policy to apply yet (`dsrRequests.ts`;
D5579 §5 step 5): tombstones and holds are the mechanism, not a policy.

### 5. Left for parts 2 and 3

- **Part 2: leases.** The Durable Object lease, with a short renewable TTL, a fencing token and busy or refused
  answers, needs a new DO binding in `wrangler.toml`. **That binding needs the owner's sign-off before part 2
  starts.** Optimistic concurrency (this part) stays the default. A lease will only reduce wasted work; it will
  never authorize a write. Capability authorization stays independent of reservations.
- **Part 3: bytes.**
  - R2 content-addressed writes, with `verifyVersionBytes` read-back before a release.
  - Reconciling a half-uploaded R2 object, a crashed DO, an expired lease, a deleted asset and cross-region
    restrictions.
  - The bounded event queue, with exactly-once effects keyed on these idempotency keys.
  - Composite release manifests (with #5585).
- Domain adapters (#5582, #5583, #5584) write revisions through this service, never into these tables directly.

### 6. Rollback

Dropping the four `work_graph_*` tables, with their triggers, loses only WorkGraph's index. No domain table was
read or written.
