### 1. Send to… (VB6–VB8)

- **Where:** "Send to… · N" sits in the plan's tools for the venture's founder, while a plan exists, is not paused and is not under a Stop. N is the number of items that may be sent.
- **What may be sent:** accepted, landed items only, as D1068 §2 rules. A Connect door is opened, never sent.
- **The founder chooses the items.** Nothing is chosen for them, so "Prepare" stays disabled until they pick one.
- **The tabs:** Lovable, GitHub, Notion and Vercel. Each says what it opens before anything happens.
- **The press records the send.** D1068 builds the text, runs the privacy check and records the handoff in one call, so the sheet cannot preview a prompt without recording it.
  - The press is "Prepare for [tool]". Before it, the sheet says: "Preparing records that you sent these items to this tool, so it shows on Progress. Nothing opens until you press it."
  - This replaces the canvas's preview-first order, which no route serves.
- **Then every send opens from the founder's own press.** Each is a link in a new tab, a copy, or a download. Nothing is sent by StudioOS.
  - **Lovable:** the prompt, the Worker's own count ("521 / 4,000"; the canvas's 1,840 was a static sample), "Privacy check passed: no names, emails or quotes.", Copy prompt, and "Open in Lovable ↗" (the Worker's link, `target="_blank"`).
  - **GitHub:** one issue per item with its body and marker, "Open on GitHub ↗" per issue (the Worker's pre-filled link), and "Copy all as Markdown".
  - **Notion:** the pages as Markdown, "Download .md" and "Copy for Notion".
  - **Vercel:** "Deploy [repository] on Vercel ↗", Vercel's import page.
- **The repositories:** GitHub and Vercel use a repository the founder picked on their GitHub connection for this venture.
  - The sheet finds the connection in `GET /api/connectors` (connected, `config.project_id` this venture) and reads `GET /api/connectors/:uid/repositories`. Only `selected` is offered, never merely `available`.
  - **With none, the tab reads "Not connected".** GitHub still prepares the issues, to copy one by one or all as Markdown, and sends no repository. Vercel cannot prepare, because it imports a repository. Each says so, with "Connect GitHub".
  - A repository is sent only with GitHub and Vercel.
  - A connection that could not be read says so, never "Not connected".
- **A refusal stays in the sheet.**
  - The privacy check (`pii_found`) names the item it found something in: "The privacy check found a name, an email or a quote in “[title]”. Nothing was sent or recorded." It never repeats the matched words, which the Worker never returns.
  - Every other refusal shows the Worker's own sentence, such as `too_long` with its count, or `repository_not_picked`.

### 3. Progress (VB10, VB12, VB22)

**Three reads, each answering alone:** the plan (D1065), the sends (`GET /handoffs`) and the links (`GET /links`). Only the plan's read can blank the page. A failed sends or links read says so above the chart, and its stage reads "Not recorded" with the reason, never "Not yet".

**What each stage is read from:**

| Stage | Read from | Source line |
|---|---|---|
| Accepted | the plan read's `decided_at` | "Your accept" |
| Sent | the newest handoff naming the item: "Lovable · opened 13 Oct", "Notion · copied 14 Oct" | "Your press" |
| In progress | an accepted link to the item: "GitHub · pull request linked 20 Oct". A Notion copy with no link is "Not recorded: Notion reports nothing back". | "Connector · GitHub" |
| Built, Live, Tested | **no read carries a landed row's state or the day it changed** | "Not recorded" wherever the stage applies |

- **Built, Live and Tested are never "Not yet".** That would claim the item is not built. The canvas's rule: "Not recorded means no tool reports that stage, never that it is not done."
- **A stage that does not apply says so:**
  - a prototype test is never built or live;
  - a risk is never built, live or tested;
  - a formation step is never live or tested;
  - a Connect door is never sent, in progress, built or tested.
- **Plan items by stage:**
  - **The rows:** one stacked bar per module. Each item sits in its furthest recorded bucket: Accepted, Sent, In progress, Built or live, Not started (a Later roadmap item), or Not recorded (sent to Notion with nothing back).
  - **The colours:** Not recorded is a dashed outline, never a fill. Every other colour is the canvas's.
  - **The screen-reader text** names each module with items not recorded.
- **The lead never says "0 of N are built or live",** because nothing here can read "built". It says "6 accepted items, 3 sent to a tool. Built and live are not recorded here yet."
- **Built per week** is the dashed "Not recorded" line, with "Not recorded: no read here carries the day an item was built, so no week is drawn as 0." The canvas's eight weekly points need a built date no store records.
- **The table:**
  - search, Module, Stage, Tool, and Sort (Last change, Name A to Z, Module), with pages of 25;
  - each cell's dot in the stage's colour, a hollow ring for Not yet, a grey dot for Does not apply, and a dashed pill for Not recorded, each with its source line;
  - an item's name opens its trail;
  - the canvas's foot under it.
- **VB12, dark:** every class carries its dark colour, and every light `hover:` has its `dark:hover:` pair (a test holds the new files to it).
- **VB22, phone:** the chart full width with bare counts; no "As of" line, weekly chart or table. Instead, one card per item with its module, title, furthest stage and six dots, five at a time with "Show more", and 44px targets. A card opens the trail, which the Lightbox draws full screen on a phone.
