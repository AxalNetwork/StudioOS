## D5948 — AI holds and usage rows name their licence (#5948)

Part of #5038 (revenue ledger, slice 4 of 6). AI cost, billed amount and
margin can now be read per licence on the database that holds the runs. How
a branch's figures reach HQ is slice 3's report and slice 6's read model.

### What is stored

Migration `202611150131_5948_ai_licence_uid.sql` adds a nullable
`licence_uid` to `ai_budget_reservations` and `ai_usage_logs`, with an index
for each (`licence_uid, updated_at` on holds, `licence_uid, created_at` on
usage rows). It also adds the one-row table `ai_licence_attribution_start`,
which records when attribution started on that database. Nothing is
backfilled.

`ai_usage_logs`' runtime CREATE and its pre-493 heal list (`aiRouter.ts`)
carry the column too, so a dev database matches.

### Which licence

`services/aiLicenceAttribution.ts` `runLicenceUid`:

- **Branch Worker** (`BRANCH_CODE` set): `branch_licence` row `id = 1`, its
  `licence_uid`. This is resolved once per database binding and kept for the
  isolate. A lookup that names none is not kept, so a branch provisioned
  after the isolate started is read again on its next run.
- **HQ** (`BRANCH_CODE` unset): no licence. No account names its licence
  yet (`routes/licence.ts`, U1), so nothing is guessed, and HQ never reads
  `branch_licence`.

**A failed lookup** (no row, an empty or malformed uid, an unreadable
table) stores NULL and logs `[ai-licence] lookup failed` with the reason,
never a value. The AI call goes on. NULL reads as unattributed, exactly as
an HQ run does.

### Written once

The hold's licence is written right after the hold is taken, beside D1278's
hold context. The usage row's is written right after its insert (and after
the pre-493 heal, if that ran). Each is its own statement with
`licence_uid IS NULL` in the WHERE, so a second stamp changes nothing.

No other statement in the Worker writes the column, and a test scans
`cloudflare-worker/src` for one. A stamp that fails leaves NULL and never
fails the hold or the run. A replayed hold (D844) is the first hold,
unchanged.

The INSERT statements themselves are unchanged. HQ, and every existing test
that builds its own tables, issues exactly the statements it did before.

### The aggregate

`licenceAiPeriod(env, { start, end })` follows `tokenMargin`'s arithmetic in
`routes/admin_revenue.ts`:

- the same join of holds to usage rows;
- settled holds with `updated_at` in `[start, end)`;
- non-admin members only.

For each licence it returns runs, `runs_not_recorded` (no usage row: before
migration 493), the included-allowance share, billed (top-up spend) and cost
(the provider cost of that spend). Margin is billed minus cost. It is
**null** when every run of the licence in the period has no usage row to
cost it.

**One departure from `tokenMargin`:** bonus and adjustment tokens
(`ai_credit_ledger`) are not subtracted per licence. That ledger names no
licence, so they stay in HQ's whole-business margin.

Holds with NULL `licence_uid` are counted at the period level, never per
licence:

| Field | What it counts |
|---|---|
| `unattributed_runs` | Created at or after `ai_licence_attribution_start.started_at`. These ran where no licence could be named. |
| `pre_migration_runs` | Created before it: "Not recorded", never folded into a licence or into zero. |

If the start row cannot be read, every NULL hold counts as unattributed,
and `pre_migration_runs` and `attribution_started_at` are null.

### Not changed

What a member is charged: holds, settlements and `charged_microusd` are
identical on a branch and at HQ, and a test compares the two.
