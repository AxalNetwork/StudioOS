## D9033 — The monitoring log tables keep 30 days, pruned at 03:00 in bounded batches (#9033)

- **Status:** built by S25, 2026-11-27. Closes #9033.
- **Migration:** `cloudflare-worker/sql/migrations/202611272140_9033_rate_limit_logs_time_index.sql`.

### What was wrong

`system_metrics` gains a row for every metered `/api/*` request and every queued job, and `error_logs` and `rate_limit_logs` grow with traffic too. The only delete for them was `POST /api/monitoring/cleanup`, an admin button nobody presses, whose comment said a cron could call it. No cron did. `index.ts` said the 02:05 analytics snapshot exists so comparisons "survive the nightly system_metrics cleanup", which did not exist: `Jobs.cleanup` at 03:00 prunes `queue_jobs` and `dead_letter_queue` only. `cf_dlq_mirror` was never pruned, while `dead_letter_queue` keeps 30 days. D1 size is a tracked capacity limit (`PLATFORM_OBSERVABILITY.md` §6).

### What it does now

1. **One prune.** `services/logRetention.ts` `pruneLogTables` deletes rows older than `LOG_RETENTION_DAYS` (30) from `system_metrics` (`timestamp`), `error_logs` (`created_at`), `rate_limit_logs` (`created_at`) and `cf_dlq_mirror` (`received_at`). 30 days is the cutoff the cleanup route already used, and `dead_letter_queue`'s.
2. **Bounded.** Each statement deletes at most 500 rows by rowid from a LIMITed subquery. A table gets at most 40 statements a run (20,000 rows) and is then reported `capped`; the next night continues. Each table runs in its own `try`, so one failing table does not stop the others.
3. **Index-walked.** The test is `col < ? AND datetime(col) < datetime(?)`: the bare range lets SQLite use the table's time index, and the `datetime()` term is the exact comparison (D124). A row the bare term passes over (an ISO stamp on the cutoff's own date) is kept one more day, never deleted early. `rate_limit_logs` had no index leading with `created_at`, so the migration adds `idx_rl_ts`. The other three already have one (`idx_metrics_ts`, `idx_errlog_ts`, `idx_cf_dlq_time`).
4. **On the 03:00 cron, recorded.** The scheduled handler calls `runLogPrune` in its own 03:00 block right after `Jobs.cleanup`, not at a new minute. It is not gated on `hqCadences`, because every deployment writes its own tables. Each table is a sub-task `log prune <table>`, recorded `done` with `deleted=N batches=B[ capped]` or `failed` through `taskFailed`, in `cron_run_history.task_outcomes`.
5. **The button runs the same code.** `POST /api/monitoring/cleanup` calls `pruneLogTables` and answers `{ purged: { <table>: n }, failed, capped, cutoff }`. Nothing in the frontend calls it.
6. **Written down.** `documentation/operations/DATA_RETENTION.md` has one row per table, with its period, where it is pruned, and whether it holds personal data (`error_logs` and `rate_limit_logs` carry `user_id`, #5510). The `index.ts` analytics snapshot comment names the prune.

### Tests

`cloudflare-worker/test/log_prune_9033.test.ts`, on the migrated schema in real SQLite with synthetic rows:
- old rows go and newer ones stay in every table, including an ISO-stamped old row, a row one day inside the window, and an offset-stamped row inside the window that sorts before the cutoff as text;
- a cap smaller than the old rows deletes only the cap and reports `capped`, and the next run deletes the rest;
- a failing table is the one failed sub-task, and the other three are pruned and recorded done with their counts;
- each prune's query plan searches a time index;
- the 03:00 block calls `runLogPrune`, and the snapshot comment names it;
- the cleanup route prunes all four tables through the same function, and names a table that failed while still pruning the others.
