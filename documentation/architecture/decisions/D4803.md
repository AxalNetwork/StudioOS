## D4803 — HQ › Security v2: triage, investigation, action and explanation separated, evidence kept (#4803)

- **Status:** canvas landed 2026-11-07 (`design/incoming/Security v2 Page.dc.html`, `design/incoming/Security v2 · Boards.dc.html`, boards SE01 to SE12 and spec boards SEA to SEE). Covers #4800, #4801, #4802 and #4803. Not built. The build is a separate task.
- **Builds on:** `admin_security.ts`, `userSessions.ts` (`SESSION_BULK_LIMIT` 100), `dsrRequests.ts` (`DSR_CLOCK_DAYS` 30, outcomes fulfilled · denied), `backup.ts` (`readRestoreDrill`), `trustContent.ts`, `subprocessorNotices.ts`.
- **Migration:** none for the frontend-only parts; see Backend required.

### The question

`/admin/security` is one long page that mixes operational controls with implementation history. The failed restore drill sits below unrelated content, the emergency action says “all tenants” while it reaches the HQ database only, raw identifiers are the primary labels, and the ledger stops at 60 rows.

### What the canvas decides

- **Seven workspaces** under one header: Overview, Events, Access, Privacy, Trust, AI Safety, Resilience (`?tab=` deep links). Each is triage → table → detail drawer → action dialog → explanation behind a disclosure.
- **Overview** leads with Action required (restore drill failed; 0 of 2 admins with MFA), then a “Checked and clear” row of measured zeros, then status by area. No synthetic score. “5 of 5 sources read” stays visible; store names sit behind Source details.
- **One state vocabulary** for every workspace: Verified, Healthy, Action required, Failed, Pending, Stale, Unknown, Unavailable, Not instrumented, Unsupported, Not applicable, Measured zero, No data yet. Each has a word, a shape and a description. “Not recorded” is retired.
- **Events:** human label first, raw id beneath and in the drawer; the six existing quick categories; Load older.
- **Destructive actions** go Scope → Review → Result. Each states its exact scope, whether the current admin is affected, takes a reason, and shows the server’s per-item outcome. Emergency re-authentication is worded “every HQ-held account; branch databases are not touched; you will be signed out too”, with a typed confirmation.
- **Privacy:** received date, due date (received + 30 days, shown as a date), remaining time, state, next action. Closing records a decision and does not erase data; Withdrawn is not offered to HQ.
- **Trust:** sanctions and KYC separate; publish review is a per-block diff against the published revision; subprocessor delivery reads Not instrumented.
- **AI Safety:** content safety, delivery enforcement and usage anomalies as three blocks, always “x of n”, with a small-sample flag and an HQ-only note (AI records carry no branch).
- **Resilience:** the failed drill leads, with the script’s steps, the failed step, exit code, duration, backup key and the `drill-d1.json` record. Backup evidence is separate and says an export proves a backup, not a restore.
- **Eadwyn** opens on security prompts; model and usage fold under one disclosure.

### Backend required

- `/governance`: a cursor (`before`) and server-side search, date, actor and outcome filters.
- Trust publish pinned to a draft revision, so a stale preview is refused.
- Per-notice subprocessor delivery records.
- DSR history beyond open and closed.
- Restore drill history (the record keeps only the latest run) and an error message beside step and exit code.

Everything else is frontend-only; board SED maps it to `SecurityPage.jsx`.

### Built — Events (2026-11-08, #4803 slice 1)

The Events workspace (SE03a, SE03b, SE11b, the SE10 states) and the first backend item SED lists. Part of #4803 and #4802; the brief asked this build to record under D4811, which is the Contracts v2 decision, so it records here, under the canvas's own decision.

**Worker: `/governance` takes a cursor and server-side filters** (`routes/admin_security.ts`). No migration.
- `before` is the cursor: the next page holds everything strictly older than the last row kept. `from` and `to` are whole UTC days; `actor` is a user id (a gate or step-up event also matches the support operator acting for that account); `q` is a substring search over the action, the names and emails each row joins and the store's own text column, with LIKE's wildcards searched for literally; `outcome` is `ok`, `refused`, `live`, `ended` or `not_closed`; `source` is one of the five stores.
- Every condition is in each store's own complete-literal SQL, through bound `? IS NULL OR …` parameters, and every timestamp is compared through `datetime()` (D124), so `admin_audit_log`'s ISO rows and the other stores' SQLite rows compare alike. Each store still returns its own newest 60 matching rows, so the merge stays exact.
- An outcome a store cannot hold skips that store: only the security ledger stores a verdict, and only a support session has a state.
- A value out of shape is a 400 with `code: 'invalid_filter'` and the `field`, never a wider read.
- A page ends on a whole second: rows in the last row's second are held back to the next page, because the cursor compares at the second `datetime()` keeps. When every row on a page shares one second, the page is returned whole and `page_split_second` says so.
- The answer adds `cursor`, `applied`, `page_split_second`, `outcomes` and `stores`. The Data access zone keeps its own unfiltered read, so a ledger filter never makes it look as if nobody acted as anyone.
- **A pre-existing gap, fixed:** `more` was set only when one store returned a full page of its own. When two stores of forty rows each merged to eighty, the page showed sixty, `more` was false, and the other twenty were unreachable. `more` is now also set when the merge holds more than a page.

**Frontend: `pages/hq/security/EventsWorkspace.jsx` and `eventsModel.js`.**
- The filter bar: search, date range (Any time, Today, Last 7 days, Last 30 days, Custom), actor (the accounts and support operators the loaded rows name), outcome and source. Branch is drawn disabled with its reason, as SE03a draws it. The six quick categories stay as chips.
- The table: Time, Actor, Scope, Event, Outcome and Source, grouped by UTC day, newest first. The human label leads, and the stored action (`gate.totp detail=factor_required`) sits beneath it in monospace. An action with no label is drawn from its own id.
- Outcomes use the shared vocabulary: Refused is Action required; Allowed, Recorded and Ended are Healthy; Live is Pending; Not closed and anything unrecognised are Unknown.
- Load older sends the cursor with the same category and filters, appends once per key, and says when the list is complete for these filters.
- The event drawer (`ui/Sheet`, read-only) has: what happened, who and where, the stored action, "All events for this actor →" (which sets the actor filter), the raw row behind a disclosure, and Copy event ID and Copy raw JSON.
- States: reading; unreadable (Retry, "This is not a claim that nobody did anything."); partial (the failed source named, rows from it may be missing, never drawn as a zero); and measured empty ("Every source was read; this is a real zero.").
- On phone the rows are cards from the same data, the filters open from "Filters · n", and every control is at least 44 px.
- How the ledger is measured (the branch reason, the per-minute refusal rule, the branch-view sentence, what the ledger does not count, retention) moved behind "How this is measured".

**Departures from the canvas:**
- **Event type is the six chips, not a second dropdown.** SE03a draws both an "Event type ▾" control and the six quick categories. They are the same server filter, so one control is drawn.
- **No counts on the chips.** SE03a draws "60+", "3", "9" and so on. Nothing counts per category; six more reads on every load would be the cost, and a count from the loaded page would be wrong.
- **The drawer's "Related" list, session link and route are not drawn.** No store records the session or the route for these rows, and the related events would need a read keyed by session that does not exist. "All events for this actor →" narrows the list instead.
- **Scope reads "Not recorded" where a store records no branch.** SE03a draws "HQ" on every row. Only licence events and security events record one (the payload's `tenant_reason`).
- **"Recorded" is drawn with the Healthy shape.** SE03a draws it as its own pill, but it is not one of SE02's thirteen states.
- **The phone filters open in place**, not as a bottom sheet.
- **The test changes are re-aims.** H23's monospace five-column ledger is superseded by SE03. `hq_governance_h7`, `hq_security_h23` and `hq_security_v2_d4800` now read the six columns off the Security v2 canvas, keep the time and stored action monospace, and find the sources, empty and reason markers in the workspace. Retention and the branch-view note are behind the disclosure.

**Tests:** `cloudflare-worker/test/governance_cursor_4803.test.ts` (8), `frontend/test/security_events_4803.test.mjs` (9). Mutation-checked: six Worker mutants and seven frontend mutants, each caught.

**Left for later slices** (as of slice 1; slice 2 below builds Resilience and AI Safety): Privacy (SE06), Trust (SE07), Eadwyn's security prompts (SE12) and the remaining phone boards; and the backend items for revision-pinned Trust publish, subprocessor delivery records, DSR history and drill history.

### Built — Resilience and AI Safety (2026-11-09, #4803 slice 2)

SE08 (AI Safety), SE09 (Resilience) and the phone boards SE11e and SE11f, read-only. Each workspace leads with the canvas's layout; the zone it replaces stays whole behind "How this is measured", so nothing H23 showed is lost.

- **Worker.** `readRestoreDrill` now returns the drill marker's `reason` (one line, cut at 300 characters), `recovery_point`, `migration` and `tables`; a marker that carries any of them with the wrong kind is not valid evidence. A marker written before these fields reads as before. `/overview`'s `backup_dr` adds `kv`, the KV snapshot heartbeat, read on its own. `ai_safety` adds `recent_verdicts`, the newest ten guard verdicts in the same 7-day window with what reached the person (`loadRecentGuardVerdicts`, from `ai_usage_logs` joined to the run it guarded). No migration.
- **Resilience** (`ResilienceWorkspace.jsx`, `resilienceModel.js`). The drill leads, its state from the drill record only: Failed (named step, exit code, reason), Stale for a pass older than its window, Verified only for a fresh pass, Action required when no drill has run, Unavailable with "this is not a pass" when the record is unreadable or not valid. The six steps of `scripts/dr-drill.sh` draw as done, failed and not reached; a failure at a preview step marks the main steps it passed. The raw record sits behind a disclosure. The D1 export and the KV snapshot are separate cards.
- **AI Safety** (`AiSafetyWorkspace.jsx`, `aiSafetyModel.js`). Content safety, delivery enforcement and usage anomalies, each "x of n" with its own state and source; fewer than 20 evaluated outputs is named a small sample, not a rate. An unsafe verdict makes content safety Unknown, never Healthy. One unreadable source says "This is not a zero" and the other blocks still draw. The recent verdicts are a table on desktop and cards on phone, from the same rows.
- **Departures from the canvas:**
  - **Drill history is not built.** The drill record keeps only its latest run, and SE09 already draws history as Not instrumented. The card says so and links to the drill workflow's runs. Writing a history object from `dr-drill.sh` is still backend work (Backend required, above).
  - **KV namespaces written** reads Not instrumented. The snapshot heartbeat does not count namespaces. KV has no restore drill, so that row is Unsupported.
  - **Delivery enforcement has one denominator.** Both "blocked before the model" and "withheld from the user" are counted out of the router guard's checks (`guard.by_page`). The legacy chat audit is a different table, so it is reported apart and never added in.
  - **The page-wide Unreadable banner is off on these two tabs.** Each workspace says in its own words what could not be read, so the banner would say it twice.

### Built — Privacy (2026-11-09, #4803 slice 3)

SE06a (workspace), SE06b (request detail), SE06c (Record outcome), SE06d (changed underneath) and the phone board SE11d. The Worker side is the "DSR history beyond open and closed" item from Backend required.

- **Worker.** `/overview`'s `dsr` adds `recent`: the requests closed in the last 90 days, newest first, from `dsr_requests` (`loadRecentDsrClosures`). Each row has the subject, receipt, outcome, close time, who closed it and the reason. A withdrawal names no operator, because it is the requester's own act. The read returns at most 100 rows, and `truncated` says when there were more. If the ledger can't be read, the answer is `available: false` with a reason, never an empty history. The open list is still read from `users.deletion_requested_at`. No migration.
- **Workspace** (`PrivacyWorkspace.jsx`, `privacyModel.js`):
  - **Figures:** Open (with the next due date), Due within 7 days, Overdue, and Closed in the last 90 days ("x closed by HQ · y withdrawn"). A figure whose read did not answer is Unavailable, not 0. An open request whose receipt time can't be parsed has an unknown due date, is said to have one, and is counted in neither Due soon nor Overdue.
  - **Table:** Request, Subject, Received, Due (a date, from the server's received + 30 days), Remaining, State. Open requests come first, soonest due first, followed by the closed ones. On phone, cards are drawn from the same rows.
  - **Detail:** lifecycle; facts; next action; the warning "Closing records a decision. It does not erase data."; Record outcome; Copy request summary; history. On phone the detail replaces the list, with "‹ Privacy" to go back.
- **Record outcome** (`PrivacyActions.jsx`): Scope → Review → Result in the shared `ActionDialog`.
  - **Scope:** Fulfilled or Denied only (Withdrawn is not offered), what closing does, and the reason.
  - **Review:** the request, the outcome and the reason, exactly as sent.
  - **Result:** only what the server answered. The D4675 rules carry over: one key per close, resent on every retry, and a new key for a different outcome or reason; a 202 or no answer is "Not confirmed", with Try again.
  - **Changed underneath (SE06d):** a stale or already-closed request gives "Nothing was saved", You saw / Now (from the server's answer), Copy my reason and Reload request.
- **The previous zone** sits behind "How this is measured", now read-only. Its inline "Record as fulfilled / denied" form (`DsrClose`) is removed, so the dialog is the one way to close a request. The tests that pinned the form (`admin_ops_d4675`, `hq_security_dsr_d168`, `hq_security`, `hq_security_v2_d4800`) now assert the same rules against the dialog.
- **Departures from the canvas:**
  - **"Seen by" is not drawn in the history.** Nothing records who opened a request, so the history lists only what the stores hold: the receipt, earlier requests from the same subject, and the close. The detail says views are not recorded.
  - **The request number** is the ledger row (`DSR-0031`). A request the ledger does not hold yet reads "No number yet"; its close still names it by its receipt stamp.
  - **"Now" in the changed-underneath result** reads the server's answer. For a request closed first, that is its outcome and time ("Withdrawn by the requester at …", or "… by another admin"). For one withdrawn and asked again, it is "A newer request" with the new receipt date.
  - **Due soon** means 0 to 7 days and draws as Action required. Overdue also draws as Action required.
  - **Where the detail goes:** beside the table on wide screens and below it otherwise. On phone it replaces the list.

### Built — Trust (2026-11-09, #4803 slice 4)

SE07a (workspace), SE07b (publish review) and SE07c (stale preview refused). Two of Backend required's items turned out to be met by the code already, so this slice reads and draws them:

- **"Trust publish pinned to a draft revision" was met by D4675.** The editor's read carries a review token for the pending set. Publish sends it back, the batch re-checks it, and drafts that changed since the read publish nothing (`changed_since_review`). The workspace sends the same token, so a stale preview is refused exactly as SE07c draws it.
- **"Per-notice subprocessor delivery records" already existed.** The notice sweep claims a `subprocessor_notice_deliveries` row for each subscriber and notice, and records `sent` or `failed`. SE07a drew delivery as Not instrumented; it is now shown from those rows.

What was built:

- **Worker** (no migration):
  - **`noticeDeliveries`:** per published notice whose subprocessor started in the last 90 days or has not started yet. It gives sending, sent and failed counts, plus confirmed subscribers not attempted yet. It also says whether mail is configured, because the sweep sends nothing without credentials.
  - **`publishedRevision`:** the change log's count (the log is append-only, so the count is the revision number) and the newest publish.
  - **The admin Trust Center read** carries both, and `read_at`.
  - **`screeningSummary`** adds reviewed hits, the latest review, and whether the newest run matched a list.
  - Each read fails on its own with a reason.
- **Workspace** (`TrustWorkspace.jsx`, `trustModel.js`) — every block is its own read with its own unreadable state:
  - **Sanctions screening:** unreviewed hits lead; no run yet reads as no data; the last run says match or no match.
  - **KYC:** the review queue's counts, with a link to the queue.
  - **Trust Center publishing:** the published revision, how many blocks differ, Review changes…, and a link to the editor for drafts and history.
  - **Subprocessor notices:** subscribers, and per notice Queued, Sending, Sent, Failed, or "Not sent before start".
  - **Trust obligations:** a link to the obligations page.
- **Publish** (`TrustActions.jsx`), Scope → Review → Result in the shared `ActionDialog`:
  - **Scope:** what publishing does. The public page changes, the change log gains the note, subscribers are emailed about a new subprocessor, and a publish is undone only by a correcting one.
  - **Review:** each draft block compared line by line with the published revision, the subprocessor list's own additions and removals, where it publishes, when the draft was read, and the change note.
  - **Result:** only the server's answer. One key per Publish is resent on its retries, and a changed note gets a new key. No answer reads "Not confirmed"; a stale review reads "Not published", then "Reload and review".
- **The previous zones** sit behind "How this is measured".

**Departures from the canvas:**

- **KYC shows its counts** (pending, approved, rejected) rather than "Not summarised here". The overview already reads them, so hiding them would drop a fact the page had.
- **Delivery is shown, not Not instrumented**, for the reason above. "Delivered" is not recorded: Sent means the mail provider accepted the notice, and the block says so.
- **"by Guillaume L." is not drawn** beside the revision. The public change log names no operator; who published is in the admin audit log.
- **The stale result does not say when the draft was edited.** The refusal does not carry it. The result says when the review was read, and Reload shows the newer draft.
- **The last screening names its result, not its subject.** The reviewer's note on a hit ("false positive") is not drawn; its date is. Both stay on the screening history page.
- **The publish target reads "/trust — public"**, not a host name, because the same build serves both hosts.
