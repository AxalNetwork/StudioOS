## D781 — one guard that every canvas page draws the rail with its page key, matrix row and switch, built as a ratchet so it lands before the boards are done

- **Status:** decided by S1, 2026-10-19 (#2106; task `Z1` of D720's plan, #1874, where it is numbered D745). The ratchet is S1's ruling on #2106. Part 1 is this PR. Part 2 closes D720.
- **Basis:** `origin/main` at `4f7816e81c`.
  - On this base, the page map (D768, #2092), the matrix (D764, #2089) and the per-page switch (D769, #2088) are not merged.
  - Every board task (D771–D775, #2097–#2101) is open.

### 1. The pages

The canvas's own data is the list: `profiles` in `design/incoming/airail-every-page-data/canvas.json`.
- **The keys** are D720 §5's, `<Profile> · <Section>` and `<Profile> · <Section> · <Module>`.
- **204 keys:**
  - the 200 boards: F1–F42, I1–I27, A1–A28, P1–P27, S1–S39 and H1–H37;
  - the four homes the canvas lists as sections: Founder · Studio, and Home for Investor, Advisor and Operating Partner.

  Admin and Super Admin have no home in the canvas.
- **Off-canvas pages** are D768's. The guard checks that the canvas is covered, not that the app has nothing else.

### 2. When a page is done

All three parts must reach it:
1. **The page map** (`frontend/src/lib/railPages.js`) names its key. An alias row counts (D720 §11).
2. **The matrix** (`cloudflare-worker/src/services/ai/railMatrix.json`) has a row with that `pageKey`.
3. **The rail** draws "Turn off AI assistance on this page". D720 §6 puts the switch on every page, so it is one check for all of them.

A file that is not on the base reaches nothing. The page map is read through every string its module exports, plus its string literals, so a table or a function's keys both count. The matrix is read for `pageKey` wherever its rows sit.

### 3. The ratchet

- **`NOT_YET`** lists every page not yet done, under the board task that finishes it:
  - #2097 Founder;
  - #2098 Investor;
  - #2099 Advisor and Operating Partner;
  - #2100 Admin;
  - #2101 Super Admin.
- **The test fails on:**
  - a page that is not done and not listed;
  - a listed page that is done, so its line must go;
  - a key the canvas does not have;
  - a key listed twice or under another profile's task.
- **The list only shrinks.** On the day part 1 lands, all 204 pages are listed.
- **Emptied on 2026-10-19 (S1).** Part 1 and D768 (#2133, the page map) landed minutes apart. D768 names all 204 keys, and the matrix and the switch were already on main, so every page passed the three checks at once. Each listed page then failed as "done, so delete it", which turned `main` red. Every line went in one change; the five task keys stay, with empty lists. A page that loses a part fails again as "not in NOT_YET". Telling M1–M5's pages apart is now part 2's render check.
- **The rules are pure functions,** `pageKeys`, `pageStatus` and `ratchet`, also run on fixtures. So each failure is shown to fire before the real modules exist.

### 4. Part 2: the render check

S1 released part 2 on 2026-10-19 (#2106): it lands as a draft before every board is done, as a second ratchet, and switches to `Closes #2106` when the last board PR merges.

**What is rendered.** The real App, in a `MemoryRouter`, at every route in the page map (`RAIL_PAGES`, 396 routes across the six profiles), signed in as a member of the route's profile. The shell, the guard, the route's element and `RailPageProvider` mount as a browser mounts them. Effects run, every lazily loaded module is loaded first, and redirects are followed. The document is `frontend/test/_appDom.mjs`, a small DOM that keeps elements, attributes and text and answers the browser APIs App calls with inert values.

**What passes.** Exactly one `<aside class="fwr">` in the document, whose `data-page-key` is the page map's key for where the app landed (`pageKeyFor`). `WorkerRail` now writes that attribute from `useRailPage()`. A route that redirects is judged at its target.

**The Worker is not called.** The session and onboarding answer as a finished member's would. `FIXTURES` answers what a page needs before it draws anything; today that is the Studio dashboard. Every other request answers in one of two states, tried in order:
- `down`: 503, so the page cannot read its data;
- `empty`: 200 `{}`, so the page read nothing.

A route passes if a state draws its rail. A second rail, or a rail with another page's key, in any state tried fails it. A page whose rail waits for real data adds its smallest payload to `FIXTURES`, in the PR that wires it.

**The ratchet.**
- `RENDER_NOT_YET` (`frontend/test/_airailRender.mjs`) lists every route that does not pass, as `<Profile> <route>`:
  - each canvas route under the board task that wires it (#2097–#2101);
  - each page the canvas does not draw under `offCanvas`.
- The test fails on:
  - a route not listed that does not pass;
  - a listed route that passes ("draws its rail now, so delete it");
  - a name the page map lacks;
  - a name listed twice or under another owner.
- On the day it was written, 257 routes pass. 139 are listed: 14 under #2097, 8 under #2098, 10 under #2099, 12 under #2100, 10 under #2101, and 85 off-canvas. Every one is "no rail": no route drew two rails or a wrong key.

**Speed.** One file per profile (`airail_render_<profile>_d781.test.mjs`), so `node --test` runs the six side by side. About 75 seconds in all on one machine.

**What else part 2 adds.**
- The ROUTE_MAP rows for D720's routes.
- The pricing copy on `/plans-and-pricing`, in D762's words. The draw order ships now. The owner's price sentence waits for D762's billing PR (#2019): `billingMode` answers `cost` on this base whatever `AI_BILLING` says.
- `documentation/operations/AIRAIL.md`, rewritten to what is on `main`.

### 5. Tests

`frontend/test/airail_every_page_d781.test.mjs`: 12 cases, part 2's rules on fixtures among them.

Each mutation was applied, run and reverted.

Part 1:
- **A listed page dropped from `NOT_YET`:** fails.
- **One page made done for real while still listed** (a page-map entry, a matrix row and the switch line): fails with "done, so delete it". With its line deleted, it passes.
- **That page's rail then dropped from the page map:** fails.

Part 2:
- **`data-page-key` removed from `WorkerRail`:** every passing route fails, "a rail keyed null".
- **A listed route deleted from `RENDER_NOT_YET`:** fails, "not in RENDER_NOT_YET".
- **A passing route listed:** fails, "draws its rail now, so delete it".
- **One page's rail dropped** (Super Admin · Licences): fails, "no rail".
- **A second rail drawn on that page:** fails, "2 rails".

`frontend/test/plans_pricing_ai_d781.test.mjs` renders `/plans-and-pricing` and checks the draw-order line under "How AI is priced", above the token packs.
