## D7742 — Research imports: a private store that keeps every source record exactly as captured (#7742)

- **Status:** built 2026-11-22. Filed from the owner's Research → Funds audit of 2026-11-19, under #3701. P0.
- **What ships:** migration `202611220322_7742_research_source_records.sql` (seven empty tables and one trigger),
  `cloudflare-worker/src/services/researchSourceRecords.ts` (no route calls it), and
  `cloudflare-worker/test/research_source_records_7742.test.ts`. No route, no client method, no page.
- **One store.** This is the one staging store and run ledger for Research imports: fund-side, company and
  funding-round records alike. The Companies plan cites a record by (source key, provider record id, stated row
  hash) and builds no second store. The store never merges two records; identity is #7746's and the Companies
  plan's. The Network directory (#7672) keeps its own typed tables.

### The tables

| Table | Holds | Content? |
|---|---|---|
| `research_source_runs` | One run: idempotency key (unique), acting user (no foreign key, so the run outlives the account), `WORKER_DEPLOY_VERSION` (null when unbound), the payload's SHA-256 as declared, the hash recipe id, the manifest, status, counts, chunks of unknown outcome, started and verified times. | No |
| `research_source_records` | A record as captured. Unique (source key, provider record id, stated row hash). A trigger refuses every UPDATE. | Non-contact columns |
| `research_source_run_records` | What each run saw: id, stated hash, body hash, outcome (`new`, `unchanged`, `new_version`, `refused`), and per manifest column `s`, `w` or `b`. | No |
| `research_source_private_fields` | A record's held contact values, as column-cipher ciphertext (`encryptColumn`, bound to the table, the column and the row `[source, id, hash]`). Cascades from the record. | Ciphertext only |
| `research_source_flags` | Flags supplied with the package, kept as supplied. The store computes none (#7747). | Ids and column names |
| `research_source_column_rules` | Per source and column: class (`fact`, `prose`, `contact`), contact handling (`withheld` or `held`), role, destination and serve (default `none` and no; #7747 sets them). A CHECK makes a contact column unservable. | No |
| `research_source_removals` | Each removal: actor, time, scope, counts, and when it was lifted. | No |

No table is named `research_source_imports`, `_mappings`, `_rules` or `_promotions`; later route modules use those.

### The record as stored

- `body_json` is the record's **non-contact** cells as `[[column, value], …]` in the source's order, written by
  `JSON.stringify` with no other processing. Blank (`""`), `null` and an absent column stay apart. Original wording,
  ordered lists, checkbox values and dates as text are kept as they arrived. Nothing is trimmed or
  Unicode-normalised. Text with a lone surrogate is refused (`invalid_value`), because it would not survive
  SQLite's JSON functions byte for byte.
- `columns_json` is the record's column names in the order they arrived.
- **Body hash:** SHA-256 (hex) over the UTF-8 bytes of `body_json` exactly as stored. The store always computes it.

### Contact data (owner, #7739 Q3 = B)

Contact columns, personal profile links and whole records about people are **never uploaded**. A contact column is
**withheld**: a value that arrives for it is dropped in the planner, before any write, and only counted. The
stored-equals-package check covers the permitted projection; withheld cells and excluded-person counts stay
explicit in the run's counts. The **held** path (encrypted under `research_source_private_fields`) exists in the
schema for a later source. It needs `allowHeld` at run open, and no caller sets it for the four-source package.

### The package's hash recipe: not supplied

The owner has not posted the package's key-only schema or canonical hash recipe (#7739 asks for them on this issue).
`HASH_RECIPES` is therefore empty, and every stated row hash is **kept as declared and counted as not checked**
(`hash_checked = 0`). When the recipe is posted, it is registered there by id. A run naming that recipe then
recomputes the whole-record hash and refuses a mismatch, named by id. This happens only when the whole record,
contact columns included, is supplied; under Q3 = B it never is for this package.

### Runs

1. **Open.** The column classes arrive with the request. A source with no rules gets them written in the same batch
   as the run. A manifest column with no class refuses the run naming the column (`column_class_missing`). A request
   that disagrees with a source's fixed rules is refused naming the column (`column_rules_disagree`). An active
   source removal refuses the run (`source_removed`). The same idempotency key answers the first run
   (`replayed: true`); with a different payload hash it is refused (`idempotency_key_reused`).
2. **Plan.** `planChunk` is pure and takes its clock as an argument. Same (source, id, stated hash) is `unchanged`
   and stores nothing. A known id with a new stated hash is a `new_version` beside the old one; otherwise `new`.
   Refused, by id with a code: an unknown source or column, a duplicate in the chunk, an invalid value, a record
   over 256 KB, a hash mismatch, a removed record or source.
3. **Write.** One chunk is four reads (the run, the rules, the chunk's stored identities through one bound JSON
   value, the active removals) and one `DB.batch` of five set-based statements: records, run records, private
   fields, flags, and the run's counts. That is **nine statements whatever the chunk holds**. The counts are
   recomputed from the run's own rows, so a replayed chunk never counts twice. Per source and column they say cells
   stored, withheld and blank, and the three sum to the record count times the column count. A batch that throws
   has an unknown outcome: the run becomes `uncertain` and the chunk index is recorded.
4. **Reconcile.** `reconcileChunk` sends the same chunk again. Every write is idempotent; a written batch clears the
   chunk, and the run returns to `running` when none is left.
5. **Seal.** `sealRun` reads back the run's membership in pages. Each source must have:
   - every expected record present once under its stated hash;
   - the per-source **digest** equal to the manifest's: SHA-256 over the `id:stated_hash` lines of the run's
     non-refused members, sorted by code unit, joined by `\n` with no final newline;
   - every body hash recomputed from the stored bytes;
   - no refusal;
   - stored + withheld + blank equal to the manifest's expected cells.

   Only then is the run `complete`. A missing or altered record makes it `partial`. A chunk of unknown outcome keeps
   it `uncertain`. Neither is ever Complete.

### Limits (tested constants)

At most 100 bound parameters a statement (each binds three or fewer). Statement text under 100 KB (each is a
constant of a few hundred bytes). One bound value at most 700 KB, far under D1's 2 MB row limit. At most 100 records,
256 KB a record body and a 64 KB manifest. Nine statements a chunk. An oversized chunk is refused before any
statement and writes nothing. The test database does not enforce D1's limits, so the tests prove the constants. D1's
own acceptance is #7745's rehearsal and #7760's first preview.

### Removals

Each removal is recorded with its actor, time, scope and counts, never content:

- **A record's private fields:** the id and both hashes stay. A replay does not restore them while the removal stands.
- **One whole record, every version** (for a person who asks): the content goes, and its id and hash stay in the run
  records.
- **One source:** no record, private field or flag row is left. Run ids, hashes and counts stay.

An active record or source removal refuses later runs for it until the removal is lifted (`liftRemoval`), so a
replay cannot undo it.

**What a removal does not reach.** It clears the live tables only. D1 Time Travel (30 days) and the locked nightly
export (365 days) keep earlier copies. In those, held values are ciphertext and withheld values were never written.

### What personal data the store can hold, and how it leaves

Under Q3 = B, none by design: contact values are withheld and person records are not uploaded. A non-contact column
can still carry a name in free text (prose), which is why the store is private:

- Only files named `researchSource*` or `research_source_*` may name its tables, and the test holds every file
  under `cloudflare-worker/src` to that.
- No function returns a private field's value. #7746 adds the one gated read (Super Admins only, each read logged;
  #7739 Q2 = A).
- Data leaves through the removals above, and from backups when they age out.

#5510's personal-data map is told the store exists; its document is not edited here.

### Payload guard

The package format's content marker is not added to `PRIVATE_PAYLOAD_CONTENT_MARKERS` (D7741). The format has not
been posted, and an invented marker would match nothing real. Until it is, a renamed payload is caught only by its
name. This is the open owner question below.
