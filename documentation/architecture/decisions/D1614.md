### 1. The owner's rules

- **Only projects have Work:** the board, backlog, burn-up, activity feed and workload.
  - A company hosts projects and carries the legal and compliance duties.
  - It has no board, and nothing rolls up into it.
- **Agents propose; a named person accepts.** "In review" waits for that person.
- **A compliance obligation stays with the company.** Work done for it becomes an item on a project's board, linked back to the obligation.

### 7. W7, a task's comments, timeline, review, drafts, labels and milestones (#3993)

- **Built by:** S24 (Claude Code), 2026-11-01, at the owner's request (moved from slot S11). It follows S21's scope split of 19:30Z: W1 owns the common task columns, and W7 adds the rest.
- **Migration 763** (`763_task_comments_labels_milestones.sql`, the number S21 assigned at 22:00Z):
  - **`task_comments`:** a person's or an agent's Markdown comment on one task. An agent's comment names its run (`run_id`, the run's proposal uid, which is what the run path records on `main` today). Edits and deletes are timestamps; a deleted comment keeps no body.
  - **`task_labels` and `task_label_links`:** a project's labels, unique by name ignoring case. W1's `labels_json` stays, as the names' mirror the board reads. Every name already in it was back-filled into a label and a link, so nothing a task carried is lost.
  - **`task_milestones`:** title, description, due date, open or closed.
  - **On `scope_tasks`:** `milestone_id`, `drafted_by_agent_id` and `review_state` (approved or changes_requested).
  - **Events:** `scope_task_events` gains `labelled`, `milestone` and `reviewed`, by the same id-keeping rebuild 762 used.
  - **Participants** are derived from the task, its comments and its events. They are never stored.
- **Routes:** `routes/work_items.ts`, mounted beside W1's board (ROUTE_MAP, "Work W7"). Project scope only; every company path answers 404.
- **Reading the issue, for the owner to confirm:**
  - **Drafts.** The issue says both that a draft "lands in triage" and that "nothing is created without the proposal's Accept". W7 keeps both: the draft is the agent's `propose:create-task` proposal, drawn in Triage with `review_state: 'needs_review'`, and no task row exists until a manager accepts it. Accept creates the task in Backlog with `drafted_by_agent_id`, and its author is that agent. Discard needs a reason and creates nothing.
  - **`review_state`** on a task records the last review (approved or changes_requested). "Review needed" is the In review column, so the filter `review:needed` reads the column, not a stored flag.
  - **Mentions** are sent as a list beside the body (`mentions: [{ kind, uid }]`), not parsed from the text. A person must be on the project. An agent's mention notifies its sponsor. A mention of anyone else refuses the whole comment.
  - **Markdown.** The Worker renders no HTML, so the comment is cleaned when stored: raw HTML tags and comments are removed, a stray `<` is escaped, and a link whose target is not http(s), mailto or relative points at `#`. Encoded schemes (`&#…`, `%3a`) count as unsafe.
- **Agents:**
  - The run path calls `agentComment` (only the task's assigned active agent) and `proposeTaskDraft` (only a live project agent). Neither is an HTTP route.
  - An agent moves its work through W1's `updateWorkTask` between Ready, In progress and In review. It never closes a task (403 `agent_cannot_close`).
  - **Cost:** an agent's comment carries the cost of the run it names, and a linked proposal carries its own. An agent's event has no run, so it reads `{ available: false }`. E3's runtime fields (#3847) are left to E3.
- **Review:** only a manager reviews, and only work In review (409 `not_in_review`).
  - Approve closes the task as completed through W1's own write, so its unblock notices run.
  - Request changes needs a comment, moves the task back to In progress and notifies the assignee (or the assigned agent's sponsor).
- **Labels and milestones:** CRUD with the manage gate.
  - A rename or delete rewrites the mirror of every task carrying the label, and bumps the task's revision so a stale W1 write cannot restore an old name.
  - W1's own writes that name labels go through `workLabels.ts`, so every name becomes a label and a link in the same batch.
- **On W1's board:** each card gains `milestone`, `author`, `drafted_by` and `review_state`. The filter gains `author:`, `milestone:`, `drafted_by:agent` and `review:`, and the list gains `?sort=`.
- **Client methods:** none here. The Work screens (#3973 W5 and its follow-ups) wire them.
- **Checks:** `cloudflare-worker/test/work_items_3993.test.ts`, 8 cases, and 18 of 19 mutations caught. The survivor, removing the Accept route's own manager gate, is equivalent: `createWorkTask` refuses with the same 403. W1's `work_board_3969` (14/14) and E1's `scope_goals_tasks_d1529` (9/9) pass with 763 applied.

### 8. W2, the burn-up (#3970)

Built 2026-11-01 by the S12 session for slot S14. It needs no migration, because the series is derived from 762's `scope_task_events` on every read, and nothing is stored.

- **Route:** `GET /api/teams/project/:id/work/burnup?range=2w|1m|3m|max&from=&to=&filter=`.
  - **Projects only** (owner revision, 2026-11-01). The path names `project`, so a company has no route and nothing rolls up to it.
  - The route is declared on `agent_engine.ts`'s own router. `scripts/check-api-drift.mjs` follows a mount only to a router variable, not to a factory call such as `router.route('/', workBoardRoutes(...))`, so W1's routes are invisible to it today. That gap is W1's and is left for #3973.
- **What a day is:** a snapshot at the end of that day, in the member's time zone (`user_settings.timezone`, else UTC).
  - `completed`: items closed as completed.
  - `not_planned` and `duplicate`: items closed with that reason.
  - `open`: every other item.
  - `scope = completed + open`. An item closed as not planned or duplicate leaves the scope, and returns if it is reopened.
  - `completed_by`: completed items split by the assignee kind they had when they were completed (`person`, `agent` or `none`). A later reassignment does not move the credit.
- **No zeros for the unknown:** a day before the project's first item is `{ day, available: false }`, and a project with no item answers `{ available: false }`.
- **Which events say what:**
  - `created` means the item exists. W1's `created` carries its column, so an item created in Done is completed.
  - `status`, and W1's `moved` and `updated` events with `to_status` and `close_reason`, set the state.
  - A bare `status` event to cancelled keeps a close reason already known for that item. W1 writes the `moved` event (duplicate) and then the bare `status` event, and the second must not turn a duplicate into not planned.
  - `assigned` sets the assignee kind from then on. An item with no `assigned` event is credited to its current assignee kind.
  - An item with no `created` event exists from its own `created_at`.
- **Range:**
  - `2w`, `1m` and `3m` are 14, 30 and 90 days ending today; `max` starts at the first item.
  - `from` and `to` together make a custom range, at most 730 days.
  - The read is bounded: events are fetched only before two days past `to`, which covers every time zone's end of `to`. The events before the range start are read too, because they set each item's state on day one.
- **`filter=`** is the board's filter: the burn-up counts the items the board keeps.
- **Cost:** measured locally on a project at the 5,000-item cap with 20,000 events: about 180 ms for any range, after caching one date formatter per zone (it was about 1.5 s with one formatter per event). That needs no per-day cache, so there is none.
- **Client:** `lib/api/work.js` (`workApi.burnup`). `workAdapter.js`'s `burnup` goes through it, and an engine that is off draws the same off block as before. The other seam methods are unchanged.
- **Checks:** `cloudflare-worker/test/work_burnup_3970.test.ts`, eight cases:
  - the gates and flags, and project only;
  - the empty project, and days before the first item;
  - created, completed, reopened, not planned and duplicate, day by day;
  - the split by assignee kind;
  - the time-zone edge at 23:30 UTC (Tokyo against UTC), with the member's own zone;
  - the ranges and their bound;
  - `filter=`;
  - the events W1 really writes, through its routes.

  `frontend/test/work_d1614.test.mjs` pins the seam.

  Eleven mutation checks were each red when applied:
  - not planned kept in the scope;
  - reopening ignored;
  - the current assignee credited;
  - days bucketed in UTC;
  - the read gate removed;
  - an empty project answered with zeros;
  - the days before the first item counted as zeros;
  - a bare `status` overriding a duplicate;
  - the filter ignored;
  - the 730-day bound dropped;
  - the SQL upper bound widened.

### 9. W3, an agent run in full, its retry, and the project activity feed (#3971)

Worker routes in `routes/agent_engine.ts`, behind E3's flag and gates. The reads are in `services/agents/runActivity.ts`. There is no migration.

**The run.** `GET /api/teams/runs/:uid` keeps E3's `{ run, steps, cost }` and adds `detail`:
- **agent:** the persona's name, else the agent's own name, plus its role and model;
- **skill:** null until #3954 records skill runs;
- **work:** the task and its instruction (`detail`);
- **sources:** the reads it used, by name, from the run's own `context` line ("Read a, b and N notes");
- **tools:** the agent's granted tools, by name;
- **proposals:** each with its decision and who decided, by name;
- **outcome**, plus `started_at`, `finished_at` and `duration_ms`;
- **cost:**
  - `held` is the hold, from `ai_budget_reservations.execution_id`;
  - `charged` is the usage row's charge with its guard rows, which is E2's `chargedFor`;
  - the model and tokens come from the usage row.

  Each is `{ available: false }` when unrecorded, never 0.

No raw prompt and no output are ever returned.

**Outcomes.** Each run status reads as one of these:

| Outcome | Runs | Extra fields |
| --- | --- | --- |
| `in_progress` | admitted or running | — |
| `completed` | done, or waiting on a person's decision | `awaiting_decision` |
| `skipped` | paused: the team, the engine, the agent, AI or the sponsor's access, or every agent halted | `reason: paused` |
| `skipped` | over a spend limit, cap, daily limit or the platform's agent limit | `reason: out_of_tokens` |
| `skipped` | a disconnected tool | `reason: tool_disconnected` |
| `cancelled` | a person cancelled it, or the agent was removed | — |
| `failed` | anything else | `reason_code`; `reason_text`, the run's own last line (already plain words); `retryable` |

A failure is `retryable` only when it was transient (`failed`, `step_lost`) **and** the run is its task's latest attempt. A refusal a retry would only repeat is not retryable.

**Retry.** `POST /api/teams/runs/:uid/retry` is open to the scope's editors or the agent's sponsor, as starting a task is. It answers 409 `not_retryable` otherwise. The new attempt goes through the runtime's own `admit`, which is the start route's. So the hold, the cap, the daily limit, single flight and every start refusal apply unchanged.

**The feed.** `GET /api/teams/project/:id/activity` is project scope only (owner revision, 2026-11-01); a company path has no route, so it answers 404. It merges three kinds of item, newest first:
- task events by people and agents: created, assigned, moved, and completed (a move to done);
- agent runs, with their outcome and charge;
- proposal decisions, with who decided.

An `updated` or `deps_set` event is not activity. W1's board writes a column move as `moved` and, when the status changes with it, a `status` event with the same `change` uid: the pair reads as one item, from `moved` (`completed` when it reaches done).

Filters and paging:
- `who` takes people, agents or both; `person`, `agent` and `task` take a uid.
- It pages 50 at a time by `before`, an opaque `<at>|<kind><id>` cursor.
- With `person` or `agent`, it also answers `lists`: that one's open tasks ("Worked on"), done tasks ("Completed"), and `completed_last_7_days`.

People are `{ uid, name }`, never an email.

### 10. W4, workload on the Calendar (#3972, part)

S1 released the part with no agent sessions (2026-11-02). Agents' scheduled sessions from #3957 join later through a named seam.

**Migration** `202611022205_work_workload.sql`:
- `scope_tasks.scheduled_start` and `scheduled_end`: an optional UTC time block, both or neither, the end after the start;
- `work_capacity (project_id, user_id, weekly_capacity_points)`.

**The time block.** W1's `PATCH /api/teams/tasks/:uid` and the create take `scheduled_start` and `scheduled_end` (`YYYY-MM-DDTHH:MM[:SS]Z`):
- both or neither;
- the end after the start, within 7 days (400 `invalid_task`);
- a task's assignee may set their own block, as they move their own card.

**Reassignment** is the same PATCH's `assignee`. E1's agent checks are unchanged: the agent is live (409 `agent_not_live`) and works in the task's module and option (422 `module_not_allowed`, `option_not_allowed`).

**Workload.** `GET /api/teams/project/:id/work/workload?weeks=1..12` is project only (a company path has no route). It answers per person and per agent, per week:
- **weeks:** they start Monday 00:00 UTC, and the first is the current week;
- **which week:** an open task counts in the week of its block, else of its due date; one with neither is `unscheduled`; done and cancelled tasks never count;
- **sums:** `estimate_points` sums the estimates, and an item with none is counted in `unestimated`, never as 0;
- **capacity:** a person's is `{ available: false, reason: 'Not recorded' }` when unset, never 0, and an unset capacity is never over (`over_capacity: null`); agents' caps are money (D1496), so they have no points capacity (`null`);
- **#3957's seam:** `WORKLOAD_DEPS.agentSessions` answers nothing until #3957 merges, and the shape does not change when it does.

**Capacity.** `PUT /api/teams/project/:id/work/capacity/:personUid { weekly_capacity_points: 0–1000 | null }`:
- one's own, or any project editor's for anyone on the project;
- a person not on the project answers 404;
- null clears it.

**Calendar.** A new source, `work_item` (family `tasks`, "Work › Board", page only, never pushable), shows the open tasks of every project the member can read:
- who reads a project: its founder-owner, or an accepted member;
- a task with a block shows in its block, otherwise all day on its due date;
- it opens the project's Work board.
