## D8536 part 2 — signatures, billing and operational alerts under the delivery contract (#8536)

Part 1 is `D8536.md`: the contract (`services/email/deliveryContract.ts`), the ledger `email_send_refs`, sign-in and company invitations. This part moves the signature, billing and alert senders onto `deliverWithReference`. It adds no migration: every new subject kind is a row that already exists, or a row the flow now writes before it sends.

- **Status:** built. Signatures, billing and the flagged-score alert meet the contract. The registry-template alerts and the rest of sign-in and invitations are still to move (see **Remaining**).

### New subject kinds

| Kind | Flow | Recipient query reads | Attempt |
|---|---|---|---|

### Signatures

The signing email is sent under `signingRef(recipientId, token, occasion)` (`services/email.ts`). The attempt is `<issuance>.<occasion>`:

- **Issuance** is the first 16 hex characters of the signing token's SHA-256. A replaced link (a lapsed token, or a partner renewal) is a new issuance, so it is a new attempt. The ledger never holds the token.
- **Occasion** says which deliberate send this is, because the same link is mailed more than once on purpose:
  - `send`: the first email of a token. Used by `POST /send` (`createAndSendEnvelope`) and the three-way NDA (`services/trustEnvelope.ts`).
  - `renew`: a partner signing-link renewal, which always mints a token.
  - `remind-YYYYMMDD`: the sender's `/remind`, at most one a day (D411).
  - `resend-YYYYMMDDHH`: a re-send of the same link. This covers a signer's `/resend` (at most one an hour, D6197), the admin contract resend (`admin_contracts.ts`) and the three-way NDA resend (`routes/trust.ts`).

  A retry within one occasion carries the same reference, so a send that was accepted, or that left without an answer, is not mailed again.

**One try per call.** A signing email is tried once per call, while the other bound senders try a refused send once more in the same call. A signing link can be replaced by a concurrent resend while the first send is out (D924, `partner_invitation_fixes_d924`), so a second try would mail the superseded link. Every caller already answers a refused send: it restores the earlier link, or answers 502 for the person to retry. That retry carries the same reference.

**Booklet stages** (`services/bookletSigning.ts`). The ledger reads lengthen the time between creating an envelope and recording its stage. A second, concurrent booklet send that finds the envelope already pending could then record the stage first, and both requests answered 409 (`booklet_esign_d759`). When the stage row already holds this send's own envelope, the send has landed and answers 201.

`signingEmailFor` (`routes/esign.ts`) now takes the reference instead of an address. It answers `EmailSendResult` through `asEmailSendResult`, so `.ok` is true only for `accepted`.

**What changes for a person:**
- **Signer `/resend` and sender `/remind`:** a send that timed out answers 502, as a failed send does. A retry within the same occasion is answered from the ledger (`timed_out`) and does not mail again.
- **Admin contract resend:** a second click in the same hour after an accepted send answers `email_sent: true` from the ledger, without a second email.
- **Three-way NDA resend:** `sent` now counts accepted sends only. Before, it counted every call that did not throw, which the old sender never did.

**Signed PDF forward** (`POST /:id/forward`). Each recipient's `esign_forward_log` row is written first (`status = 'pending'`), and the send reads the address from it. The row is then updated to:
- `sent` when Gmail accepted it;
- `timed_out` (error `no_answer`) when the request left and no answer came;
- `failed` otherwise.

The PDF rides as a binary attachment: `EmailAttachment.bytes`, new in `email/gmail.ts`.

### Billing

**Stripe receipts** (`services/invoiceEmails.ts`, `invoice.paid` / `invoice.finalized` / `charge.succeeded`):
- The `invoice_email_log` row is written first, with `sent_at` empty, and names the recipient. `alreadySent` reads `sent_at`, so the row suppresses nothing.
- A Stripe retry of the same event finds the same row (unique `dedupe_key`), and with it the same reference.
- **Outcomes:**
  - `accepted` sets `sent_at`.
  - `refused` throws, so the webhook answers non-2xx and Stripe retries. Nothing left, so the retry is safe.
  - `timed_out` does not throw. The receipt may have arrived, and the ledger will never send it again, so a Stripe retry could only be answered from the ledger.
- The recipient is the one the first event named. A retried event that names another address does not redirect the receipt.

**Storefront order confirmation** (`services/orders.ts`, step 5). It is sent to the buyer the order row names, under `billing:order_receipt:<order_ref>:1`.

### Alerts

**The flagged-score alert** (`services/notifications.ts`):
- `insertNotificationOnce` now returns the new row's id instead of `true`. That id is the subject: `alert:admin_alert:<notification id>:1`.
- The existing per-admin dedupe still decides whether to page.
- The address is read from the `users` row while that user is an active admin.

### Tests

`cloudflare-worker/test/email_delivery_contract_8536_part2.test.ts`. It runs over the e-sign harness plus the ledger migration, with Gmail and Stripe's PDF host stubbed at fetch.

- **Signature:**
  - the link's host matches the sending environment, on the first send and on a re-send;
  - an expired link answers 410, and a replacement makes the old one 404;
  - refused, then accepted-but-timed-out: one email, one reference (`tries = 2`), and the retry is reconciled;
  - a reminder is its own send;
  - a signed recipient has no recipient;
  - no signing token is in a log line or in the ledger, audit or activity rows;
  - the forward goes to its row's address with the PDF bytes, and a retry is reconciled.
- **Billing:**
  - refused, then timed out: one receipt under one reference;
  - a refused receipt throws, the retry sends once, and a later delivery is a no-op;
  - a retried event naming another address still mails the row's address;
  - Stripe's PDF and hosted links never reach a log line or a row.

  Receipts carry Stripe's links only, none of ours, so the host and expiry checks do not apply to them.
- **Alert:**
  - the review link's host matches the sending environment;
  - refused, then timed out: one email under one reference;
  - a user who is no longer an admin has no recipient.

Mutations that fail the file:
- each flow sending through its unreferenced sender (no reference);
- claiming a `timed_out` row;
- the provider called with a passed or event address instead of the row's;
- `signingRef` ignoring the occasion;
- dropping `status = 'pending'` (e-sign) or `role = 'admin'` (alert) from a resolver;
- logging a signing link or Stripe's PDF link;
- a fixed host;
- `/resend` re-sending a lapsed token;
- a refused receipt not thrown;
- the forward's PDF bytes dropped.

The booklet fix is held by the existing `booklet_esign_d759` test ("two sends started together"). Without it, that test fails on every run of this branch.
