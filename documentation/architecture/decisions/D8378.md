## D8378 — A bounded read of failed compact records, store half (#8378)

A request held only as a compact record (D8348) can still receive a verified failure after its check
showed success. The store records that failure at once, but the outbox reaches the record only in rotation.
S21's review of the composed source measured the delay: two compact records per alarm, so about 68 hours at
the 32,768-record bound
([#8367 review, R1](https://github.com/AxalNetwork/StudioOS/pull/8367#issuecomment-7112968023)). S39 rejected
that delay, chose a correction-due lane in the outbox, and asked the store for one read to feed it
([#8367](https://github.com/AxalNetwork/StudioOS/pull/8367#issuecomment-7113968198)). This is that read.

**Nothing here is live.** Nothing calls the read until S39 composes it. The correction-due lane, its place
in the four-publication cap, fairness, restart behaviour and retry evidence are S39's, and no line of the
outbox, result layer, transport or runtime changes here. D8333 finding 10 stays open until the composed
behaviour is demonstrated.

### The port

```ts
export interface CapacityCompactFailedStore {
  compactFailedPage(after: string, limit: number): CompactView[];
}
```

`SqlCapacityStore` implements it. It is a separate interface, as S39 proposed, so `CapacityCompactStore`
is not widened and nothing that implements that contract has to change.

- **What it returns.** Compact records with `failed = 1`, in identity order, strictly after `after`. A
  cursor does not have to name a failed record, or any record.
- **Limit.** The same rule as `compactPage`: `limit` must be a positive safe integer and `after` a string,
  or the call throws `capacity_compact_page`; at most 100 records come back whatever is asked.
- **Every failure counts.** The read is over the stored column, so it finds a failure however it was
  recorded, including one written before the correction lane, or this index, existed.
- **A read only.** One `SELECT`. It changes no record, no failure, no expiry cursor and no expiry
  decision. What it returns is not permission to publish: the publisher still validates the record, its
  mode and its intent as it does for any compact record.

### Why an index, and why a partial one

Without an index the query has to read the table to find its few failed rows. The new index is

```sql
CREATE INDEX IF NOT EXISTS ci_capacity_compact_failed ON ci_capacity_compact(id) WHERE failed = 1
```

It holds one entry per failed record and none for a pass, so a handoff of a passing request writes nothing
extra and the read costs what the failed records number. The query spells `failed = 1` literally, which is
what lets SQLite match it to the partial index, and a test reads the query plan and fails if the index is
no longer used, if it stops being partial, or if a sort step appears. Creating the index on a store that
already holds failures indexes them; a test opens such a store and finds the earlier failure.

Measured on Node's SQLite, in memory, with 32,768 records of about 1 KB and one failure. These are not
Workers-runtime figures.

| Way to find the failed record | Time per call | Statements |
| --- | --- | --- |
| `compactFailedPage` | 0.03 ms | 1 |
| The same query with the index disabled | 2.5 ms | 1 |
| Walking every `compactPage` | 269 ms | 329 |

### What the caller should know

- **Pagination is by identity, not by time of failure.** A record that fails behind the caller's cursor is
  seen on the next walk from the start, not on the current one. A lane that must not miss a new failure
  starts each pass from `''`, or keeps its own due set and uses this read to rebuild it after a restart.
- **A failed record stays in the read until it leaves the store.** Failure is sticky (D8348), so the read
  does not shrink when a correction is published. The lane needs the intent's `sent` value, which is S39's,
  to tell a corrected record from a due one. At the bound, with every record failed, a full walk is 328
  calls of up to 100.
- **Expiry is unchanged.** A failed record that expires or is removed simply stops appearing.

### Tests and checks

`merge-control/test/ci_capacity_compact_failed_8378.test.ts`, six cases against real SQLite and the real
store: order and cursor; validation and clamp, compared with `compactPage`; query plan, statement count and
the partial index; a failure recorded before the index and one written straight to the table; no writes,
and records failing or leaving between pages; the separate port.

Twelve mutations, each run against that file and restored: eleven caught. The survivor removes `ORDER BY`,
which changes nothing while the read walks an index keyed by identity; the clause stays as the stated
guarantee, and the plan test fails if honouring it ever needs a sort. The existing compact tests pass
unchanged.

Not exercised: the Workers runtime and deployed SQLite. Partial indexes are standard SQLite and are
documented for D1, which runs on the same storage, but no Durable Object has created this one.
