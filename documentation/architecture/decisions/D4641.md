## D4641 — Help content ownership and release decision (#4641)

### Interim implementation

- `frontend/src/pages/docs/guideGovernance.js` records proposed accountable Axal VC functional owners, a last-verified date field and a review scope for nine priority guides **without** claiming that they have passed source/browser checks. `null` means verification is pending. Other guides have an explicit unassigned state and need to be brought into the review process.
- The existing HQ `GuideAnswersAdmin` view derives a content-review candidate count from actual negative feedback and displays the responsible owner and pending state. This is **not** a durable task tracker; someone must assign and close each content change in the existing GitHub issue/PR process.
- `.github/pull_request_template.md` requires a Help impact decision: links to updated guides, or a reason no change is needed, for product, route, permissions, billing or support-channel changes.
- No guide was given an invented `lastVerifiedAt` date. Release notes continue to use the existing `/CHANGELOG-user.md` source; there is no independent release-note store.

### Outstanding dependencies

- Source and authenticated browser verification of guides, with evidence links and actual review dates, must be performed by their owners. #4637–#4639 are still under review, so dating them as verified now would be false.
- No screenshot is added until a real, current capture exists with an alt description and maintenance owner. No screenshot placeholders are represented as actual product captures.
- #4640 is blocked by #4957's unapproved Help redesign. The old `frontend/tests/e2e/docs-admin-visibility.spec.ts` asserts obsolete /docs rail behavior and should be replaced only against the settled new journey. Do not weaken security checks to satisfy that old layout.
- Search-gap aggregation needs a real, privacy-safe data source and owned triage workflow; the present HQ feedback endpoint offers negatives and missing-text signals, not a durable search-gap queue. Do not manufacture observations or falsely report lower support volumes.

### Completion checks

Owners should verify direct article routes, internal anchors, roles, permissions, public/admin separation, mobile search and escalation after the final design merges. Record baseline before-and-after support volumes, review dates and unresolved blockers. Only then should the issue close as a completed maintenance system.
