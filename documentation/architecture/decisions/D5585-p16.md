### 1. Why a table, not a column

`work_graph_release_lines` is fixed: its BEFORE UPDATE trigger refuses every edit (D5585). A name set after the line
is registered cannot live on that row.

`work_graph_release_line_names` holds one row per name a Super Admin gave a line. The line's name is its latest row. A
rename is a later row, so every earlier name is kept with who gave it and when. The table follows the authority store
(D5585-p8):

- `seq` numbers one line's rows 1, 2, 3…, and a trigger requires each row to be the next.
- A writer names the `seq` it saw. The insert is conditional on the line still being at that `seq`, so two renames
  racing cannot both land.
- A trigger refuses a row whose tenant and company are not its line's.
- UPDATE and DELETE are refused.
- A CHECK keeps a stored name trimmed and 1 to 120 characters.

A name cannot be cleared, only replaced. Nothing asked for clearing, and "the line once had a name, now it has none"
would need a third state on every read.

### 2. What a name may be

`normaliseLineName`:

1. applies NFC;
2. makes every run of whitespace one space (so a pasted tab or line break becomes a space);
3. trims the result;
4. keeps it only if it is 1 to 120 characters and holds no other control character (C0, DEL, C1) and no bidirectional
   embedding, override or isolate character.

The last rule matters because those characters let a name display as something other than its text. Anything else is
`line_name_invalid` (400).

### 3. The route

`PUT /api/admin/work-graph/releases/lines/:line/name` takes `{ tenant_id, company_id, name, expected_seq,
idempotency_key }`. It is gated by `requireSuperAdminWriteBar`: a TOTP session, a recent step-up, then the elevation.
`expected_seq` is 0 for an unnamed line.

| Case | Answer |
|---|---|
| a body without a string `name`, a whole `expected_seq` of 0 or more, and a key | `malformed` (400) |
| no scope | `malformed` (400) |
| a name that is not one (§2) | `line_name_invalid` (400) |
| a missing line | `not_found` (404) |
| a line of another tenant or company | `wrong_tenant` (403) |
| a `seq` that is not the line's | `stale_line_name` (409), with `current: { name, seq, setByUserId, setAt }` |
| a key reused for another request | `idempotency_conflict` (409) |
| a replay of the same request | the first answer, `replayed: true`, nothing written |

Every attempt, refused or not, is a `work_graph_release_line_name` row in the admin audit log, with its outcome.

### 4. The reads

`GET /lines` and `GET /lines/:line` carry:

- `lineName`: the name, or null;
- `lineNameReason`: `not_recorded` while the line has no name, else null;
- `lineNameSeq`: what a rename names, 0 when never named.

`GET /lines/:line` also carries `lineNameSetBy` and `lineNameSetAt`, and names that person in `people`, by display
name and never by email (D5585-p11 §2). An unnamed line reads exactly as part 11 left it.

Names are read for the request's own scope only, in one statement per read. Another tenant's or company's name is
never read.
