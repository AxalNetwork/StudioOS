## D9040 — Partner office hours and PartnerNet: the 22 ledger routes, tested and verified (#9040)

A #4570 slice, run under this issue's own number so it does not take S25's next `D4570-p<k>` part. It covers every
`unreviewed` auth-inventory entry in two families: 12 under `/api/partner-office-hours` and 10 under
`/api/partnernet`. Each entry is now `verified` by
`cloudflare-worker/test/authz_partner_network_d4570.test.ts`. The ledger read 330 unreviewed and 133 verified before
this change, and reads 308 unreviewed and 155 verified after it.

### How the gates work

**Office hours: a slot is its firm's.** Deleting a slot reads the firm from the caller's own account
(`requirePartnerProfile`, `users.partner_id`). The slot must carry that firm.

- Another firm's partner gets 404.
- A founder or an investor gets 403.
- An admin with no firm gets 400.

**Office hours: a booking has two parties.** They are the founder who booked it and the partner whose firm it is on.

- **Transitions.** Confirm, complete and no-show are the partner's (or an admin's); cancel is either party's (or an
  admin's). Anyone else gets 403.
- **Follow-ups.** Action items and the rating answer every non-party, admin and Super Admin included, the same 404 as
  a booking that does not exist (D355). Only the author deletes an item, and only the founder rates.

**Office hours: slots are public to the signed in.** Any signed-in account reads a partner's slots. The meeting link
and the notes go only to the partner, an admin, and a founder holding a confirmed booking on that slot (#4715).

**PartnerNet: a relationship is its two parties'.** Its history, interactions, reminders and edit refuse anyone else
with 403.

- **Admin bypass.** An admin or Super Admin passes. Each bypass writes one `admin_audit_log` row,
  `partnernet_admin_bypass`, naming the route. A party's own call writes none.
- **Reminders.** A reminder is its creator's. The relationship's other party is refused it too.
- **Requests.** A request is withdrawn only by its author. Everyone else gets 404, admin included.

**PartnerNet: the firm book is its owner's.** Its rows are bound to the owner in SQL. Everyone else gets 404, admin
included.

Every refusal in the matrix leaves every table unchanged, apart from the one audit line an admin's bypass writes. Each
route's right caller then passes the same gate, which shows that each refusal comes from the gate and not from the
body. The suite asserts nothing about support sessions, so it holds with or without #9016 (which refuses their
writes).

### What the tests found

**`POST /api/partner-office-hours/:uid/book` answered every call 404.** The alias re-fetched its own router at the
mounted path `/api/partner-office-hours/slots/:id/book`. A sub-router's routes are unprefixed, so that path matched
nothing. No client calls the alias, which is why nobody noticed.

- **The fix.** The alias now forwards to `/slots/:id/book` and carries the partner uid with it.
- **The scope.** The handler books only a slot of the partner the address names. Another partner's slot, or an unknown
  uid, gets the same 404 as no slot.

This was not a cross-tenant hole. Any founder may book any open slot.

**No cross-tenant hole was found.** Every other gate already held.

### Left as it is

**Office-hours transitions by an admin are not audited.** An admin may confirm, cancel, complete or no-show anyone's
booking, and unlike PartnerNet's bypass this writes no `admin_audit_log` row. The tests pin the current behaviour, an
admin passes, and the owner question on #9040 asks whether it should be logged or refused.
