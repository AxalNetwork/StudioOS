## D4559 part 5 — #4591's schema parity is listed as not read, never measured (#4559)

- **Status:** built. One entry in the capacity read's `not_read_here`, its row in `PLATFORM_OBSERVABILITY.md` §5.1, and a test. No metric, no snapshot key, no alert, no migration.
- **Context:** D4559 item 16 left #4591 out of the read because it was still open. #4591 has since closed (2026-11-12). It shipped two parity checks:
  - the deploy workflow's job `repo can still rebuild production's schema` (`check-baseline-drift.mjs`), which compares production's schema with a fresh build of the committed baseline and migrations on every deploy;
  - the dispatch-only `schema-rehearsal.yml` (D4591), which provisions and restores two throwaway databases and compares them with the same functions.

  Both print their outcome in the GitHub Actions run. Neither writes to a Worker binding, KV, R2 or a D1 row. The capacity read makes no outbound call, the same rule that keeps #4571's probe outcome out (item 16).
- **Decision:**
  23. `d1.schema_parity` is listed in `SIGNALS_NOT_READ_HERE` with that reason. It is not a metric. Measuring it would mean either an outbound call to the GitHub API from the Worker, or the workflow writing its outcome somewhere the Worker reads. Each needs a credential or a write path this issue does not authorise. A missing parity result therefore never reads as healthy or as 0.
  24. #4594 is still open (`state:blocked`). Its signal (a measured halt-propagation bound) waits for it, as item 16 says for #4572.
- **Consequences:** the read now names all five closed issues whose signals it cannot measure. If the owner later wants schema parity as an alert, that is its own scoped change. For example, the deploy job could write its last result to a KV key the read already has a binding for, under an approved write.
