### 1. Owner and due date, null until someone sets them

`deal_closing_checklist_items` gains `owner_user_id`, `owner_label` and
`due_date`; `ic_conditions` gains `owner_user_id` and `owner_label`. All are
nullable with no default, so a row written before the migration reads null
and the screen shows Not recorded. A default would state an owner or a date
nobody gave.

An owner is a platform user (`owner_user_id`, refused unless the user
exists), a named party that is not one (`owner_label`, such as "Founder"),
both or neither. A due date is a calendar date written `YYYY-MM-DD`; any
other string is refused. On a PATCH a field that is absent is left as it is,
and a field sent as null is cleared.

### 2. Who may set them: the rule that already moves the round

Adding an item and changing one stay role partner plus `canMoveRound`
(D4631): the deal's lead partner, or an admin. That rule now covers owner,
due date and note as well as state. There is no second, narrower rule for
the new fields. A refused write records nothing, including no event.

A condition's owner is set when the condition is created, by whoever may
create it: anyone who may see the decision (D461). Resolving a condition is
unchanged and keeps its owner.

### 3. History: one append-only event per write, in the same batch

`deal_closing_checklist_events` holds one row per write to an item: the
item, the actor, the state before (null for the item's creation) and after,
the note sent with the write, when, and the item's `owner_user_id`,
`owner_label` and `due_date` as they stand after that write. The three are
nullable with no default. The event and the write are one D1
batch, so either both land or neither does. A PATCH inserts the event first
and guards both statements on the state it read, so a write that raced
another lands neither row and answers 409 `checklist_item_changed`.

Reverting an item (done, then pending) still clears `done_by` and `done_at`
on the item, as before. The earlier event is kept, so the Audit tab still
says who did it. Two triggers refuse UPDATE and DELETE on the events table.
Items written before the migration have no events, because their history
was never recorded, and none is invented.

An edit that changes only the owner, due date or note also writes an event,
with the same state before and after. Its owner and due date are the new
ones, and the event before it still holds the old ones. Comparing the two
events shows what changed.

### 4. Reading the history

`GET /api/deals/:id/closing-checklist/events` answers under the checklist's
own read rule (`loadDealForRead`, which asks `dealAudience`): whoever may
read the checklist reads its history, anyone else gets the same 403 as the
checklist, and a missing deal gets 404. Each event carries `owner_name`,
resolved from `owner_user_id` the same way the checklist read resolves it.
The client is
`dealClosingHistoryApi.events(dealId)` in its own module (D527).

### 5. Owner decisions (2026-11-14)

- **`ic_conditions.owner_label` stays.** DE07 shows "Founder" as an owner,
  and no platform user stands for that.
- **Any existing user may be an owner.** The owner is not limited to the
  deal's team.
- **Each checklist event carries the owner and due date** as they stand
  after its write (section 3), so the Audit tab can show an owner-only or
  due-only edit.

### Rollback

Revert the PR. The added columns and table are additive and unread by the
earlier code, so they can stay in D1. Dropping them is a separate migration
and loses whatever owners, due dates and history were recorded.
