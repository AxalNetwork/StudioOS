## D5535 — Verify production queues before release mutations (#5535)

Cloudflare can reject Worker publication for a missing queue after the D1 migration step succeeds. The admission check reads the pinned Wrangler version's effective `production` configuration and takes the exact union of producer queues, consumer queues and consumer dead-letter queues. It requires the full candidate SHA at HEAD and verifies the configuration against that commit. A missing production environment or redirected config fails closed.

`node scripts/check-production-queues.mjs "$CANDIDATE_SHA"` uses the same `CLOUDFLARE_ACCOUNT_ID` as publication, and rejects a conflicting account in the effective config. It uses Cloudflare's [read-only queue inventory](https://developers.cloudflare.com/api/resources/queues/methods/list/) with the release token. Exact names may be established as soon as they are all observed. A complete inventory is required to diagnose a missing queue. Failed authorization, an incomplete or failed response, and a confirmed missing queue have distinct results. The latter tells the account owner what to provision. The check creates no resources and emits no provider error bodies or credentials.

#5501 owns the trusted production release path. After resolving and checking out its immutable SHA, acquiring the release lock and rechecking eligibility, run this command in the same checkout and production account as publication, before any migration or publish step. Let any nonzero exit block both steps. Keep the JSON result with release evidence and test the same ordering in #5501's admission suite. This script checks the checkout and bindings; #5501 establishes the candidate's trust and handles all production entry points. The fixture in `scripts/lib/productionQueues.test.mjs` rehearses the sequence with disposable API responses. It does not invoke D1 or deploy a Worker.
