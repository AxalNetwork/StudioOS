## D6006 — Problem discovery v2, part 1: the Worker side of the ranked list and the theme record (#6006)

Part of #6006, and part of the Validate v2 Discovery and ICP canvas (D5995, boards V17 to V20). This part is the Worker. Part 2 (`D6006-p2.md`) builds the page against it.

### The ranked list (V17)

`GET /api/cycles/validate/modules/problem-discovery` (`problemRecords`, `services/cycleValidate.ts`) keeps every field it had. Each row adds:

- **`rank`.** The theme's place in the whole venture's default order: most interviews first, then by name. It is fixed before any search, filter or sort, so a narrowed list keeps each theme's number.
- **`rank_reason`.** Why it ranks there, built from counts only, never from a quote, so every reader reads the same text (`rankReason`). Examples:
  - "Most mentions · 2 from ICP · mostly Severe";
  - "2 mentions, both in the last 30 days";
  - when two themes have the same count, "… · tied on mentions, ordered by name";
  - "Named in no held interview".
- **`grouped`.** False for a phrase in no theme. It still ranks, as its own row, and its `id` is null, so it opens no record ("Not grouped").
- **`sources`.** Sources beside mentions: `{ interviews, people, organisations, people_unrecorded, organisations_unrecorded }`.
  - `interviews` is `mentions`.
  - `people` and `organisations` count the distinct interviewee names and companies among those interviews. Each is `null` when not one of them recorded a name (or a company).
  - The `_unrecorded` counts say how many of those interviews recorded none.
- **`phrases`.** Each wording that lands on the theme, once per interview and wording.
- **`supporting`, `contradicting` and `contradicts`.** How many open hypotheses the theme is linked to in each direction. `contradicts` lists the codes beside the existing `supports`; it is `null` when there are none.

The stats strip and the unthemed panel are unchanged.
- **The strip's `ungrouped`** counts the distinct phrases in no theme.
- **`unthemed_total`** counts each phrase once per interview.

### The theme record (V19)

`GET …/problem-discovery/records/:id` adds these `parts`:

- **`problem_statement`** is `{ who, cope, cost, updated_at, updated_by }`. These are the founder's own words, not quotes, so every reader of the record reads them. A field never written is `null`.
- **`sources`** is the same shape as on the list, plus `phrases`. **`supporting`** and **`contradicting`** are the link counts.
- **`used_on_slide`** is `{ state: 'unavailable', reason, slide: 'problem' }`. The deck store keeps the Problem slide's text, never which themes fed it, so the question cannot be answered. The reason reads "Not tracked per theme yet. The deck reads the themes as a whole.", as the canvas draws it.

A new first main section, **Problem statement** (`statement`), shows the three fields, each "Not recorded" until written. The record's new **Write the problem statement** action (`statement`) saves the three fields together through `updateThemeStatement` (`services/validateWriters.ts`):
- **Writers only.** It takes the record's write gate, so a partner and another venture's founder are refused.
- **Empty and omitted fields.** A field sent empty clears it to NULL; a field left out keeps its value.
- **Length.** A field holds at most 1,000 characters (`MAX_STATEMENT_FIELD`); anything longer is a 400.
- **Who and when.** It stamps `statement_updated_at` and `statement_updated_by`.
- **One batch.** The update and one activity row (`theme_statement_edited`) are written in a single batch.

Migration `202611152333_6006_theme_problem_statement.sql` adds the five nullable columns to `pain_groups`.

### Assign several at once (V17's selection bar)

`POST /api/progress/pain-groups/:projectId/assign-many` takes `{ phrases: string[], group_id }` or `{ phrases: string[], new_title }`. It is the selection bar's "Assign to theme" and "New theme from selected".
- **Gate.** The same as Assign: `loadProject` then `ensureCanEdit`.
- **Limit.** 1 to 100 phrases (`MAX_BULK_ASSIGN`). Two wordings of one phrase count once.
- **One batch.** Every alias is written through `upsertPainAliasStatement` in a single batch with one activity row, so either all land or none do. A theme created for the set is taken back if the batch fails.
- **Reply.** The pain-groups view, plus `assigned` and `group_id`.
- **Refusals** carry codes:
  - `phrases_required`, `too_many_phrases`, `invalid_phrase` and `target_required`: 400.
  - `theme_not_found`: 404.
  - `assign_failed`: 503.
- **Client.** `painThemesApi.assignMany` (`frontend/src/lib/api/painThemes.js`).

Eadwyn's grouping proposals accepted as a set will call this same write once the proposals exist. Producing them is a later part, because no suggestion kind proposes a grouping today.
