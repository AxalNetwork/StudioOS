## D714 — Fund administration: one act table, enforced in the Worker, for Super Admin and Admin

Issue: #1779 (S09). This file covers PR 1, the gates, and PR 2, #1774's fee acts (§ PR 2). PR 3a adds #1773's rows, PR 3b the overview, and the closing PR the console at `/admin/fund-admin`.

### Why

The owner's instruction of 2026-10-17 divides the work:

- **A Super Admin** connects entity accounts, enters or reveals bank details, issues capital calls and fee periods, and publishes reports.
- **An Admin** views, reconciles, prepares drafts and exports them for review.

Nothing in fund operations told the two apart. `requireFundGp` let any `role = 'admin'` account through on every fund write. So any admin could:

- issue a capital call;
- execute a distribution;
- change a fund's GP of record, which changes who passes every GP gate;
- change its carry rate, which the distribution job withholds;
- assign an investor account write access to the books.

### What was decided

**One act table.** `cloudflare-worker/src/services/fundAdminAccess.ts` exports `FUND_ACTS`. Each row holds an act's key, label, routes, tier and owning task. For a Super Admin act, the row also holds the sentence a plain Admin reads in place of the control. Reads carry no act.

| Act | Routes | Admin | Super Admin |
| --- | --- | --- | --- |
| `capital_call.preview` | `POST /api/funds/:id/capital-calls/preview` | Yes | Yes |
| `capital_call.issue` | `POST /api/funds/:id/capital-call`; `POST /api/funds/:id/lps` with `first_call_cents > 0`; `POST /api/capital/calls`; `POST /api/capital/capitalCall` | No | Write bar |
| `capital_call.receipt` | `POST /api/funds/:id/capital-calls/lines/:lineId/receipts` | Yes | Yes |
| `distribution.preview` | `POST /api/funds/:id/distributions/preview` (new) | Yes | Yes |
| `distribution.execute` | `POST /api/funds/distributions/execute` | No | Write bar |
| `distribution.mark_paid` | `POST /api/funds/distributions/:id/mark-paid` | Yes | Yes |
| `fund_report.draft` | `POST /api/funds/:id/report-periods` | Yes | Yes |
| `fund.gp_of_record` | a `PATCH /api/funds/:id` that changes `gp_user_id` (null included) | No | Write bar |
| `fund.economics` | a `PATCH` that changes `carried_interest` or `management_fee` | No | Write bar |
| `fund.write` | any other `PATCH`; an LP without a first call; LP type; the comms log; regenerate LPA | Yes | Yes |
| `fund_ledger.administrator` | `PUT /api/fund-ledger/:id/administrator` | No | Write bar |
| `fund_ledger.write` | every other ledger write | Yes | Yes |

**How the gate runs.** Each `funds.ts` handler keeps its own `requireFundGp`, then runs `assertFundAct(c, gp, act)`. Routes with no `requireFundGp` run `assertAdminAct(c, user, act)`. Those are the two legacy issue routes, and the ledger writes inside `access(c, true)`. Both functions apply these rules in order:

1. A support session (`impersonated_by`) gets `403 support_session_refused` on every act, whoever it acts as. This applies on HQ and on a branch.
2. During a recovery cool-off, a Super Admin act gets the cool-off's 423 body. That body comes from `recoveryCoolOffBody`, which the middleware now shares.
3. On a branch Worker, today's gate stands.
4. For an admin on an Admin act, `requireAdmin` runs, so a frozen admin gets the D135 423.
5. For an admin without the elevation on a Super Admin act, the gate answers `403 { code: 'super_admin_required' }` at once, before any TOTP or step-up demand. The Super Admin then passes `requireSuperAdminWriteBar`.
6. A non-admin GP of record keeps today's power over their own fund. The one exception is `fund.gp_of_record`, which only the Super Admin may change.

**The gate refuses by throwing a `Response`, never an `Error`.**

- The report-period handlers and the ledger router's `onError` map thrown auth sentences to `fund_access_refused`. A step-up or freeze thrown as an Error inside them reached the SPA as a refusal the admin could not answer.
- The gate catches the sentences that `requireAdmin` and the write bar throw. It rethrows each as the body `app.onError` would have sent, built from `stepUpRefusalBody` and `adminFrozenBody`.
- `requireFundGp` does not change.

**Prepare, then issue.** `POST /api/funds/:id/distributions/preview` returns:

- the basis returned, the profit, and the carry withheld;
- the carry rate used, and whether it is the job's 0.20 default;
- each LP's line, the LPs whose line rounded to zero, and the cents no line received.

The preview and the `returns_distribution` job both call `splitDistribution` (`services/fundDistributionSplit.ts`) over the same LPs, so they cannot disagree. The job's arithmetic is unchanged.

**Every admin act is audited.**

- An act an admin performs writes one `fund_admin.<act key>` row through `logAdminAction`, after the act. Its details hold the act, the fund and amounts in cents, and never bank text (no receipt reference). The domain rows (`capital_call_issued`, `distribution_triggered`, …) stay.
- Mark-paid now writes `distribution_marked_paid` for every caller.
- A `PATCH` writes `fund_updated` with the changed fields. For `gp_user_id`, `carried_interest` and `management_fee` it also records the old and new values.

**Recovery cool-off.** `COOL_OFF_ROUTES` gains three routes:

- `/api/funds/:id/capital-call`;
- `/api/funds/distributions/execute`;
- `/api/fund-ledger/:id/administrator`.

The acts that share a route with reads take rule 2 instead: a first call through `POST /:id/lps`, and a change of GP of record, carry or fee.

**The console reads the table.** `GET /api/fund-admin/access` answers `{ super_admin, acts: [{ act, label, tier, owner, sentence, allowed }] }`. It is `requireAdmin`, HQ only, and refused to a support session.

In the SPA, `lib/fundActs.js` draws three controls through `FundActControl`:

- `AdminFundsView`'s Capital call and Distribute;
- `InvestorFundCalls.jsx`'s Issue.

A plain Admin reads the act's sentence ("A Super Admin issues capital calls.") instead of a disabled button. A non-admin GP and a branch admin make no read. A failed read keeps the buttons, because the Worker still decides.

### Where the build departs from the issue

- **The two activity rows are written directly.** These are mark-paid's `distribution_marked_paid` and the PATCH's `fund_updated`. The issue said to write them through `logActivity`, as the receipt route does. But `logActivity` leaves `activity_logs.action` (NOT NULL) unset and swallows the failure, so on a database built from the migrations it records nothing. The LP-type route already says so and writes its row directly; these two do the same. The receipt route's own `logActivity` row has the same gap, and this PR leaves it as it is.
- **The in-gate cool-off applies to any caller of a Super Admin act.** That includes a GP of record and a plain Admin, as the route-level middleware does for everyone on its routes.
- **The ledger's audit row is written by a router middleware.** After a successful write, it uses the act that `access` asserted, rather than a line in each of the eight handlers.

### What is recorded here, not built

- **Branches.** A branch has no Super Admin (D106), and none is deployed (`infra/branches` holds only `_example.json` and its README). On a branch the admin rows do not apply and today's gate stands, apart from the support-session refusal. The first branch must decide who issues there.
- **The legacy and syndicate routes.**
  - `POST /api/capital/calls` and `POST /api/capital/capitalCall` are now Super Admin acts. Their `api.js` methods have no caller. Retiring them is S1's to file.
  - `POST /api/legalcap/capital/call` names a deal or syndicate, never a `vc_funds` row, and D370 says production's `capital_calls` lacks the columns it writes. It is not in the table, and S1 is to file it with the legacy routes.
- **Two fee-terms stores** (settled by PR 2). The ledger's `POST /api/fund-ledger/:id/fee-terms` writes D628's `fund_fee_terms`, which post journal entries and bill nobody. #1774's fee reads its own `fund_mgmt_fee_terms` (migration 473), never `fund_fee_terms`. So the ledger route stays a `fund_ledger.write` act, and the books and the fee engine hold two sets of terms. Nothing reconciles them; S1 files that if it is wanted.
- **The distribution job's gaps**, which the preview now shows rather than fixes:
  - there is no hurdle;
  - the carry withheld is recorded nowhere;
  - each LP's line is rounded on its own, so the lines can fall short of or exceed the distributable amount by a cent or more;
  - a line that rounds to zero is dropped.

  S1 files the waterfall separately.

### PR 2 — #1774's fee acts

S1's plan of 2026-10-17, on #1774's routes (#1799, merged).

- **Three acts**, owned by `#1774`:
  - `fee_terms.confirm` (`super_admin`): `POST /api/fund-fees/:fundId/terms/:termsUid/confirm`;
  - `fee_period.issue` (`super_admin`): `POST /api/fund-fees/:fundId/periods/:quarter/issue`;
  - `fee.write` (`admin`): terms, admission, net invested, offsets, a period's preview and its funding call.
- **`routes/fund_fees.ts`'s `writeGate(c, act)`** keeps the context `requireFundGp` returned and runs `assertFundAct(c, gp, act)`. It returns a thrown Response, as `gate()` does. That replaces:
  - its own support-session refusal (code `support_session`, now `support_session_refused`);
  - its inline `isSuperAdmin` / `requireSuperAdminWriteBar` block.
- **What the table adds to the fee routes:**
  - a frozen plain Admin's write gets the D135 423;
  - a Super Admin act during a recovery cool-off gets the cool-off's 423 (`/api/fund-fees` is already in `COOL_OFF_PREFIXES`, so no route entry is added);
  - an admin's act leaves one `fund_admin.<act>` row. A router middleware writes it once the handler answers with success, as the ledger's does.
- **The two stores of fee terms.** PR 2 settles this: see "What is recorded here, not built".
- **Frontend.**
  - `frontend/src/lib/api/fundFees.js` (`fundFeesApi`) has one method per #1799 route. Its line sits in `api.js`'s block after `fundAdmin.js`, and it is described in `lib/api/README.md`.
  - `fundAdminApi.distributionPreview(fundId, proceedsCents)` calls PR 1's preview route.
  - Nothing draws either yet: the console is the closing PR's.

**Where the build departs from the plan.** On a branch Worker, the two Super Admin fee acts are still refused to an admin caller. Rule 3 says today's gate stands on a branch, and #1799's gate refused them there, because `isSuperAdmin` is false on a branch. `assertFundAct`'s branch passthrough would have let them through. So `REFUSED_TO_BRANCH_ADMINS` names the two acts, and the passthrough refuses an admin on them. A GP of record passes on a branch, as on HQ.
