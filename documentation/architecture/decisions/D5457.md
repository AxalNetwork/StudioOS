### 1. Where the manifest lives

A manifest is two keys of a D5454 revision's content, so it is pinned by the revision's `content_sha256` and is immutable with it:

- `evidence_refs`: at most 100 items, each exactly `{ kind, ref, version, purpose }`. No free text: internal comments belong in `internal_notes`, which no audience projection carries.
- `audience_manifest`: `{ audience, recipients }`, with `audience` one of `invited`, `invited_nda`, `marketplace_teaser` and at most 25 recipient user ids. A teaser names no recipient. There is no public, mass or automatic audience.

`parseManifest` refuses the whole manifest on any unknown kind, purpose, audience or field, a forbidden kind (`bank_balance`, `mercury_fact`, `investor_private_note`, `other_firm_record`), a duplicate, a malformed ref or version, or a bound exceeded. A refused manifest is never read as empty. ADP-02 (#5456) writes revisions and may call the same parser to refuse a bad manifest at save time.

`purpose` records why an item is there (`claim_support`, `counterevidence`, `risk_assessment`, `control_test`, `valuation`, `publication_attachment`). Inclusion is not measurement: nothing here feeds a score.

### 2. Source kinds and what each resolves against

| Kind | Store | Scope | Pinned version | Status rules |
|---|---|---|---|---|
| `data_room_file` | `data_room_files` (+ folder, versions) | `project_id` = the issuer's project | `MAX(data_room_file_versions.version) + 1`, the convention of `services/agents/reads.ts` | Trash → `withdrawn`; tier `nobody`, unknown tier or unknown visibility → `restricted`; expiry passed or unreadable → `expired`; other version → `version_changed`. An NDA folder makes the file NDA. |
| `raise_evidence_item` | `raise_evidence_items` | same | `version` | not `pinned` → `withdrawn`; `private`, or any `private_reason` (bank, quote) → `restricted`; other version → `version_changed`. |
| `pitch_deck` | `pitch_decks` (one row per version) | same | `version` of that row | wrong version → `version_changed`; an older version stays `available` and is flagged `superseded` (advisory). |
| `venture_scorecard`, `deck_derivative`, `dd_summary`, `contract_reference` | named, not read | — | — | always `unavailable`: not integrated yet, never guessed. |

Every item also resolves to `not_found`, `out_of_scope` (another project, including another project of the same company) or `unreadable` (its kind's read failed). For `not_found`, `out_of_scope`, `unavailable` and `unreadable` the resolution carries no label, date, version, category or access: one studio's package can neither select nor reveal another's files or names. Source words are the platform's (`Connector`, `Document`, `Recorded`, `Signed`, `Typed`); a store with no word gives `null` (Not recorded), never a guess.

Reads are bounded: one statement per integrated kind present (`RESOLVE_QUERY_MAX` = 3), every ref bound through `json_each`. A failed kind marks only its own items `unreadable`.

### 3. Admission: release and retrieval

- **Release** (`admitsAudience`): only an `available` item is admitted. A teaser carries only Raise evidence shared as a summary, never a document or deck. An invited audience gets open, invited-tier items; an NDA audience also NDA items. A committed-only item is closing material and exceeds every release audience.
- **Retrieval** (`retrievalDecision`): ADP-04 calls it with a **fresh** resolution and fresh recipient facts every time an investor opens the package. It applies the data room's own predicate (`dataRoomAccess.tierAdmits`: Trash, tier, expiry, grant folder scope) and the NDA rule. A file or deck needs a live grant on the issuer's project; evidence needs a grant or a committed prospect row. A pinned version never preserves access after a revocation, because the snapshot is not consulted. Decks follow the data room's grant rule here (conservative; no per-deck share rule is assumed).
- **Recipients** (`readRecipientFacts`): one statement for all recipients (active account, newest live grant on this project, NDA with the venture's founder, committed prospect), one for every scoped grant's folder tree. A failed read makes every recipient `unreadable`; a scoped grant whose folders cannot be read opens no folder. The release grants nothing.
- **Investor view** (`investorManifestView`): only items this recipient may receive, each as kind, source word, date and purpose. No ref, name, version or internal label; withheld items are counted, never named.

### 4. The readiness contract

`evaluateReadiness` is one pure function over facts, so the queue, workspace, review and publish gate show the same checks for the same revision. The result carries `contract_version`, `policy_version` (`d5457.1`), the preparation and revision, `candidate_digest`, `sources_digest`, `evaluated_at`, `fresh_until` (five minutes), `dependency_versions`, per-check `{ id, dimension, level, state, code, explanation, repair, counts? }`, a state per dimension, `release_ready` and `closing_ready`. Explanations are fixed words with no name, title or amount; counts are by status only.

Four dimensions, answered separately:

| Dimension | Checks |
|---|---|
| `content_completeness` | `manifest_valid`, `brief_sections` (the keys the audience's projection shows), `instrument_supported`, `typed_terms` |
| `release_eligibility` | `issuer_pair` (live company-backed pair, unchanged since the revision), `sources_current`, `sources_latest` (advisory), `audience_selected`, `distribution_policy`, `audience_projection`, `candidate_review` |
| `investor_access` | `recipient_access` (blocking on an inactive or unreadable recipient; advisory when the stores withhold some items) |
| `closing_readiness` | `legal_prerequisites` (active and reviewed template), `issuer_authority`, `instrument_closing_rules` |

Check states: `pass`, `fail`, `unreadable`, `unavailable`, `review_required`, `not_applicable`. A dimension is `ready` only when every blocking check in it passed; `unreadable` outranks `blocked`, which outranks `review_required`. `release_ready` needs content, release and investor access ready; it never looks at closing. `closing_ready` is its own answer and a complete brief never implies it.

**Blocker matrix** (`BLOCKER_MATRIX`, `INSTRUMENT_FAMILIES`): by audience, `distribution_policy` blocks a teaser and does not apply to an invited release; `recipient_access` does not apply to a teaser; `sources_latest` is advisory everywhere; closing checks block `closing_readiness` in every column and never a release. By instrument: `safe`, `convertible_note`, `priced_equity` and `spv` are known (the SPV also needs its vehicle record, not integrated: `unavailable`); anything else is `review_required` in content and closing, never a guessed rule. A candidate with no audience is judged as an invited release.

**Dependencies other packages supply** are explicit inputs and are `unavailable` until wired (`UNINTEGRATED_DEPENDENCIES`): typed terms (#5456), review and approval of the exact candidate (#5458: an approval recorded for another `candidate_digest` fails), legal/template prerequisites (#4811), the marketplace distribution policy (owner), the issuer representative's authority (no store read yet). Today, therefore, nothing is release-ready: that is the intended state while preparation stays disabled.

### 5. Digests and freshness

- `candidate_digest`: SHA-256 of canonical JSON of the contract and policy versions, the preparation, the revision id and `content_sha256` (which covers terms and narrative), the pinned issuer pair, the items in a fixed order and the audience with sorted recipients. Editing the manifest, a pinned version, a purpose, the terms, the audience or the issuer changes it; reordering does not.
- `sources_digest`: SHA-256 over each item's resolved status, current version, date and access. A new document version, a revocation, an expiry or a scope move changes it.
- `preflightFreshness` answers `current` only for the same candidate, the same sources and the same policy within `fresh_until`; else `stale` or `expired`. It is advisory: the result is never a permission token, and ADP-04's release re-runs the evaluation in its own transaction.

### 6. The bounded read

`readPackageReadiness(env, user, preparationUid, ctx)` refuses before any read unless the caller holds D5454 `read` (platform admin, outside a support session); then reads the preparation on this deployment's `scope_code`, its working or submitted revision, the issuer pair, the sources and the recipients: at most `READINESS_QUERY_MAX` = 9 statements, all reads. Another deployment's row, an unknown uid or a non-admin is `not_found`; a failed preparation or revision read is `unreadable`. The returned sources list is the authoring/review view (labels inside the issuer's scope only). It never echoes `internal_notes`.

No route mounts it in this part: the admin deal routes belong to ADP-02/ADP-05 and the publish gate to ADP-04, which call it when they enable their states.

### 7. Finding for the D5454 owner

`PROJECTIONS.investor` in `dealPreparation.ts` copies the revision's raw `evidence_refs`. Under this manifest shape that would show an investor the refs and versions of every selected item, including ones the stores withhold from them. Before ADP-04 enables publication, the investor projection should carry `investorManifestView`'s output instead of the raw key. `dealPreparation.ts` belongs to #5454 (open PR #8890), so this part does not edit it.
