### What is built

- **`services/wellbeing/storageReview.ts`.**
  - `holdingOf(env, row, fields)` classifies one row's answers as `encrypted`, `not_encrypted`, `partly_unreadable` (ciphertext that no longer opens and has no plaintext copy) or `empty`. It decrypts only to test, and keeps nothing.
  - `reviewWellbeingStorage` counts each store with fixed SQL:
    - `wellbeing_reflections`;
    - `wellbeing_daily_pulses`;
    - `wellbeing_checkins`, the weekly rows from before Task #33.
  - A store that does not exist reads `present: false`, never zero rows.
- **`GET /api/wellbeing/storage-review`** (`routes/wellbeing_storage_review.ts`).
  - Super Admin at HQ only (`requireSuperAdmin`).
  - Each run is recorded in the admin audit as `wellbeing_storage_review`.
  - It returns totals per store: `rows`, `checked` (the newest rows, up to 5,000), the earliest and latest period, and `held`. It returns no member id, uid, value or per-member count.
  - A failure answers 503 `storage_review_unavailable`.
  - There is no screen. The runbook is `documentation/operations/WELLBEING_STORAGE_REVIEW.md`, which says what each answer means and what to do next.
- **Earlier check-ins carry `held`.** This applies to `GET /api/wellbeing/reflections/earlier` and the export.
  - On This week, a row held without encryption says "Stored without encryption: saved while encryption was unavailable. Delete it if you'd rather it were gone."
  - A partly unreadable row says "Part of this check-in can't be read any more. It is unchanged; you can delete it."
  - An encrypted row, or a Worker that sends no `held`, adds nothing.

### Not changed, and why

- **The legacy writer.** `POST /checkins` and `/daily` still fall back to plaintext. No screen calls them since part 2, and changing a still-mounted route's contract is a separate decision.
- **The pre-Task #33 weekly store.** `wellbeing_checkins` is not shown to the member. The review counts it, and the owner decides from the count. Both are recorded in the runbook's table.
