## D799 — The Administrator's requests to HQ: renewal, a term change, seats, a delegate, notice of non-renewal, answered in the bell

- **Status:** decided by S1 for the owner, 2026-10-20 (#2232). Part of D795 (#2228), decision D-d.
- **Basis:** `origin/main` at `a44b6524`. Worker paths are relative to `cloudflare-worker/src/`.
- **The owner's answer:** an Administrator **requests** and HQ decides. The requests are a renewal, a term change, more seats and a delegate admin. HQ answers each within its response time, and HQ writes every term.

### 1. Four new kinds

The requests are escalations (migration 259). `rpc/hqOps.ts` adds four kinds to `ESCALATION_KINDS`, each with its response time in `SLA_HOURS`:

| Kind | Response time |
| --- | --- |
| `renewal` | 72 h |
| `terms_change` | 120 h |
| `delegate` | 72 h |
| `non_renewal` | 72 h |

`seat_increase` was already a kind. No licence kind hides a new one: `escalationKindsFor` still hides only a white-label's `content` (D206), and HQ's ledger is still read only for that kind.

### 2. What each request carries

`services/escalationRequests.ts` holds one rule per kind and one sentence for each refusal. Every door that records a request reads it: the HQ-tier lane, the branch lane and HQ's `recordEscalation`, which checks again what a branch sends.

- **`renewal`:** optionally the term asked for, in whole years from 1 to 25.
- **`terms_change`:** the term, the value as it stands, and what is asked. The term is one of the licence's own: `territory`, `seats`, `fee` or `term`.
  - **D797's keys join later.** D797's terms schedule (`services/licenceTerms.ts`, S10) was not on `main` when this was written, and had no PR. Its keys join `REQUESTABLE_TERMS` in whichever of the two PRs merges second.
- **`seat_increase`:** the seat type (one of migration 187's four) and the number, from 1 to 10,000.
- **`delegate`:** the person's sign-in email, and optionally their name.
  - Accepting it does not grant the role. HQ grants it through `POST /api/admin/licences/:uid/admins`, as today.
- **`non_renewal`:** nothing from the person. The notice date is the day HQ records the notice, set by the door that writes the row (`withNoticeDate`). D797's `non_renewal_notice_days` is measured from it, and a date sent by the person is refused.

**A field a kind does not have is refused, not dropped**, because a field dropped in silence reads as stored (the D208 rule). A request on a kind that carries none is refused too.

### 3. The fields travel in `detail`, so no migration

Every path an escalation takes already carries `detail` verbatim:
- HQ's insert;
- the branch's local row;
- the RPC call between them;
- the branch's retry of an undelivered row.

A request is stored there as one JSON object, `{ v: 1, request, note }`.
- **`note`** is the person's own words, at most 2,000 characters, so the object fits the column's 4,000.
- **A row whose `detail` is not that object** is plain text, as every row before D799 is. It reads back as a note with no request, and is never parsed into one.
- **`v`** is the format's version, so a later change to a kind's fields can be told from this one.

**Considered and not taken:**
- **A column for the request** (migration 513). It would have needed the branch table too, so that a retry carried the fields. About seventeen test harnesses build these tables from a fixed list of migrations.
- **A side table.** It needs a batched write to stay atomic with the escalation.

The issue preferred no migration, and `detail` already goes everywhere the request must.

### 4. The HQ-tier lane

No branch is deployed (D286), so today's Administrators hold licences on HQ's own database and had no way to raise a request. `routes/licence_requests.ts` adds:
- `GET /api/licence/mine/requests`;
- `POST /api/licence/mine/requests`.

It sits in its own file, mounted under `/api/licence` beside `routes/licence.ts`, which D798 also edits.

- **Whose licence.** The one `licence_admins` binds the caller to (its UNIQUE index on user_id makes it one). A caller bound to none, such as a founder, gets `no_licence` (404), as `GET /mine` answers.
- **The row** (`recordLicenceRequest`):
  - `branch_code = 'hq'` (`HQ_TIER_CODE`), which is not a code a deployment can take;
  - `subject_ref` is the licence's uid, and a `subject_ref` sent by the person is refused;
  - the raiser's name, and their HQ user id in `raised_by_branch_user_id` (the column's name is migration 259's, from when only a branch raised).
- **The read** lists only that licence's rows, with each one's `request`, `note` and response-time band. It also returns:
  - the kinds the licence offers and hides;
  - each kind's response hours;
  - the requestable terms and the seat types.
- **Open while the licence is suspended,** for the branch lane's reason (D107, D112): a suspended licence's way out is a request to HQ.
- **On this lane every request kind needs its fields,** `seat_increase` included. There is no older caller here.
- **At most 20 open requests per licence.** A 21st is refused with 409 `too_many_open`, and it says so. The ceiling bounds what one account can put on HQ's queue.
- **On a branch, one path for the page.** The same two calls are handed to the branch's "To HQ" lane (`routes/branch_escalations.ts`), with the caller's own headers. The branch keeps its rules: its admin gate, its local row, its retry.

### 5. The branch lane

`POST /api/branch/escalations` also takes `request`:
- it is required for the four new kinds;
- it is checked when sent for `seat_increase`, which the branch drawer has raised as text since D112 and still may;
- it is refused on any other kind.

The request is checked before HQ is called. It is stored in `detail` and sent to HQ, which checks it again. The lane's `GET` reads each row's request out beside its `detail`. The branch drawer offers only the kinds it knows (`kindsOffered`), so the new kinds appear only on D800's page.

### 6. HQ's answer, in the bell

`services/escalationAnswerNotice.ts` writes one notice per decision with `notify()`:
- channels `in_app` and `email`;
- category `compliance`;
- type `licence_request_answered`;
- link `/admin/my-licence/requests`.

The `notifications_inbox` row is what the header bell lists.

- **On HQ's tier**, `PATCH /api/admin/escalations/:uid` on an `hq` row tells the raiser instead of pushing to a branch, and reports `notified`.
  - The raiser's id is read from the row, never from the caller, so nobody else is told.
  - `POST …/resend` on such a row sends the notice again.
- **A branch's raiser** is a user of the branch's database, which HQ cannot write. So the branch tells them when the decision lands (`applyEscalationAnswer`).
  - This holds for every kind: the bell is where HQ's decision reaches the person who asked.
  - The notice is best effort and never undoes the decision.
- **HQ's board** (`GET /api/admin/escalations`) carries each row's `request` and `note`. The answer screen is D801's.

### 7. What this does not do

- **No UI.** The page is D800's, and HQ's request answers on the licence console are D801's. The SPA's client is `frontend/src/lib/api/licenceRequests.js` (D527).
- **No term is changed by a request.** HQ writes every term, through the routes it already has.

### 8. The guard

`cloudflare-worker/test/licence_requests_d799.test.ts`, 15 tests:
- each new kind is raised on HQ's tier against the caller's own licence, with its due date and its stored request;
- the read lists only the caller's licence;
- a founder gets `no_licence` and writes nothing;
- a suspended licence can still raise;
- a hidden kind is refused with its reason and writes no row;
- each kind's rule refuses with its own sentence and writes no row;
- the open-request ceiling;
- HQ's answer writes exactly one bell notice for the raiser, and a declined one says so;
- resend notifies again;
- HQ checks again what a branch sends;
- on a branch the same call is the branch lane, and the branch tells its own raiser;
- the response-time bands for the new kinds.

Fourteen mutations each fail it:
- a term change's hours changed;
- the read not scoped to the licence;
- the hidden-kind gate dropped;
- the term rule dropped;
- the bell notice dropped;
- the notice sent to the wrong user;
- a suspension gate added;
- any licence returned for anyone;
- the notice date dropped on HQ's tier;
- HQ's re-check of a branch request dropped;
- the branch's notice dropped;
- the notice sent by email only;
- a client notice date accepted;
- the branch call not handed to the lane.

`escalation_kind_gate_d206.test.ts` and `branch_rpc_fanout.test.ts` now expect the larger vocabulary.

**Rollback:** revert the PR. The four kinds and the HQ-tier lane go. Rows already written stay readable as plain escalations, whose `detail` holds the request object as text.
