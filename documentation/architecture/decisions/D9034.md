## D9034 — The job dead-letter mirror holds each message once, loses none quietly, and a replay runs once and is audited (#9034)

- **Status:** built by S26, 2026-11-27. Closes #9034.
- **Migration:** `cloudflare-worker/sql/migrations/202611272117_9034_cf_dlq_mirror_once.sql`.
- **Forward fix:** `cloudflare-worker/sql/forward-fixes/202611272117_9034_cf_dlq_mirror_once.fix.sql`.
  The release-window rehearsal (D8532) rates the migration `manual` (a `DELETE`
  and a `UNIQUE` index on an existing table). After a Worker rollback, the
  previous consumer's plain `INSERT` of an already mirrored message would fail
  on the index and be retried; the fix adds a `BEFORE INSERT` trigger that
  skips that row with `RAISE(IGNORE)`, so it is acknowledged and the table
  still holds one row per message. Nothing applies it on deploy.

### What was wrong

- `dlqConsumer` (`cloudflare-worker/src/queue-consumer.ts`) inserted into
  `cf_dlq_mirror` with a plain `INSERT`, then marked the email or listing, then
  acked. A delivery that died after the insert was delivered again and inserted
  a second row: nothing held `message_id` unique.
- The job DLQ consumers had `max_retries = 3` and no `retry_delay`. Three quick
  failures during a short D1 outage and the platform deleted the message, with
  only a `console.error` behind it.
- `POST /api/infra/dlq/:id/retry` read the row, enqueued under a fresh random
  key, then deleted the row. Two clicks both read it and both enqueued. Neither
  the replay nor `DELETE /api/infra/dlq/:id` wrote an audit row.

### What it does now

1. **One row per message.** The migration removes duplicate `message_id` rows
   (keeping the lowest id), adds the unique index `idx_cf_dlq_message`, and adds
   a nullable `idempotency_key`. The consumer writes `INSERT OR IGNORE` and
   stores the message's key. `ensureInfraSchema` in `routes/infra.ts` declares
   the same column and index.
2. **Never quietly lost.** A failed mirror is retried with
   `delaySeconds: JOB_DLQ_RETRY_SECONDS` (60), and `retry_delay = 60` is set on
   the job DLQ consumer in all three environments of `wrangler.toml`. The final
   attempt is counted as the agent DLQ's is (`attempts >= 3`): it writes one
   `error_logs` row (`source = 'dlq-consumer'`, job type, message id, attempts,
   never the payload) and acks.
3. **A replay runs once.** The route reads the row, then claims it by deleting
   it; only the request whose delete changed one row enqueues. The other gets
   409 `dlq_item_already_claimed`. An enqueue that throws re-inserts the row
   with every column it had and answers 502 `dlq_replay_enqueue_failed`. The
   replay key is `<stem>:dlq-replay:<source>-<id>`, where the stem is the
   stored key (an earlier replay's suffix removed) or `dlq-<source>-<id>`.
4. **Audited.** A replay writes `dlq_replayed` and a discard `dlq_deleted`
   through `logAdminAction` (`activity_logs` and `admin_audit_log`): the admin,
   the source, the row id and the job type.

### Why the final attempt is the third

`studioos-job-queue-dlq` has no dead letter queue of its own. The agent DLQ
(`agents/agentQueue.ts`, `DLQ_FINAL_ATTEMPT = 3`) already treats the third
delivery as final under the same `max_retries = 3`, and `>=` also covers a
fourth delivery if the platform makes one. Giving up one delivery early costs
one retry; missing the final one would lose the record.

### Tests

`cloudflare-worker/test/job_dlq_once_9034.test.ts`, on the migrated schema in
real SQLite: a redelivery after the mirror row landed leaves one row with its
key; retries before the final attempt are delayed and log nothing; the final
attempt writes one `error_logs` row without the payload; the three
`wrangler.toml` blocks carry the delay and retry count; the migration keeps the
first row per message and then refuses a duplicate; two concurrent replays (cf
and d1) enqueue once and one answers 409; a failed enqueue restores the row and
audits nothing; replay and delete each write one audit row.
