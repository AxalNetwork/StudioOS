### 1. The policy, written down

#### Fund reads (`routes/funds.ts`)

The relationship decides what a caller is shown. It is evaluated on every request from the stored rows, so a changed relationship applies to the next read.

| Caller | `GET /api/funds` (list) | `GET /api/funds/analytics` (family rollup) | `GET /api/funds/:id`, `/:id/analytics` | `GET /api/funds/:id/page`, report periods |
| --- | --- | --- | --- | --- |
| Platform admin | every fund, whole row, `can_manage: true`, `relationship: 'admin'` | every fund | any fund | any fund, as manager |
| GP of record (`vc_funds.gp_user_id`) | their funds, whole row; `can_manage` is the operating gate's answer (institutional tier, active company) | the funds the operating gate lets them run: institutional tier and the active company (`manageScope`) | through `requireFundGp`: tier, then GP of record under the active company; otherwise 402/404 | as manager when `requireFundGp` passes |
| Limited partner (`lpMembershipScope`) | the funds they hold a position in, **LP projection**: `id, name, slug, vintage_year, status, company_id, created_at`, `can_manage: false`, `relationship: 'lp'` | none | 404 (their view is `/lp-portal` and the fund page) | as LP: issued periods only (D631) |
| Anyone else | none | none | 402 below the tier, else 404 | 404 |

Two changes make the code match the table:

- **The list's LP projection.** A row the caller does not run carries only the fields that name the fund. The GP's contact details, service providers, terms and capital figures stay with the GP's whole row; an LP reads their own figures on `/lp-portal` and the fund page. The fields the Portfolio screens read from the list (`companiesModel.js`'s `fundGroups`, `managedFund.jsx`, the LP workspace's fund picker) are all in the projection.
- **The family rollup uses the operating gate's scope.** `/funds/analytics` used the bare GP-of-record predicate, so a GP below the institutional tier, or one whose fund belongs to another company than the active one, was given a rollup of funds whose per-fund analytics answer 402/404. It now reads `manageScope`, the predicate `can_manage` already used, so the rollup and the per-fund read agree on every fund.

#### Company-update records (`routes/portfolio_updates.ts`)

| Caller | Read (list, detail, `/versions`) | Projection | Create | Change, submit, send, ask again |
| --- | --- | --- | --- | --- |
| Platform admin | every update | full record | yes | yes |
| The venture's founder (owner) | their ventures' updates, drafts included | full record; on `/page`, recipients with delivery state | yes (`canShareUpdate`) | only an update they authored, while they still hold write authority |
| Seated writer (cofounder, accepted) | through the founder list or the partner/investor reads below | as their role | yes (`canShareUpdate`) | only an update they authored, while their seat still grants write authority |
| Advisor seat | as partner below | as partner | no | no |
| Investor tied to the venture (D889) | submitted updates whose founder chose investors (`audience_json` or a recorded recipient) | the update; on `/page`, the investor payload (`payloadFor`) | no | no |
| Partner with an accepted seat (D889) | submitted updates whose founder chose the team | the update; on `/page`, the team payload | no | no |
| Network recipient | `/page` only, as a recorded recipient | the network payload (asks; metrics only if included) | no | no |

**Current authority on every operation.** `operateRefusal` runs on `PUT /:uid`, `PUT /:uid/share`, `POST /:uid/submit`, `POST /:uid/send` and `POST /asks/:askUid/ask-again`. An admin passes; otherwise the caller must be the author **and** `canShareUpdate` must hold now — the check that let them create the update. A seat removed or downgraded to advisor after the draft was written refuses the next operation with `403 share_not_allowed`, and nothing is written. Before this the existing-record routes asked only "is this the author".

### 2. Publication

- An update of kind `'update'` is a draft until it is **published**: by `POST /:uid/submit`, `POST /` with `status: 'submitted'`, or the first `POST /:uid/send`.
- Publishing writes **version 1** to `portfolio_update_versions` with the publisher and the time, and sets `status = 'submitted'`, `submitted_at` (once) and `published_version = 1`. The publication is conditional on the row still holding the content the publisher read, so an edit that lands between the read and the write is not silently published (`409 changed_since_open`).
- **Re-submission changes nothing.** A second submit returns the update as it stands: `submitted_at`, the version and its record are the original ones, and followers are told once.
- **A published update is never edited in place.** `PUT /:uid` on a published update is a **correction**: version N+1 with the new content, `published_by_user_id` (the actor) and an optional `correction_reason` (≤ 280 characters). It lands only while the row is still at version N, and an optional `expected_version` must equal N; otherwise `409 changed_since_open` and nothing is written. Of two corrections made from the same read, one lands. `PUT /:uid/share` on a published update answers `409 update_published`: the sheet edits drafts.
- A version row is written once; no route updates it. `content_sha256` distinguishes versions' content.
- An update published before this change has no version. Its next operation records version 1 from the row as it stood, attributed to its author at its original `submitted_at`; that is not a new publication and notifies no one.
- `GET /:uid/versions` lists the versions (number, title, digest, time, actor, reason) to the same readers as the detail. The detail and list carry `version` and `published_at`.

A report (`kind = 'report'`) keeps its own revision chain and its Reporting routes (D1059); these routes still refuse it with `409 report_row`.

### 3. Delivery

One logical delivery per recipient per version, in `update_recipients`:

- **Reservation.** `recipient_key` is `user:<id>` or `email:<address>`; `UNIQUE (version_id, recipient_key)`. A send reserves each recipient of the chosen audience with `INSERT … ON CONFLICT DO NOTHING`, so concurrent sends reserve each recipient once.
- **Attempt.** A send claims each reservation with a conditional update (`WHERE delivery_state = <as read> AND attempt_claim IS <as read>`, a fresh claim token) and records the outcome only where its own claim still stands. A claim that loses does nothing, so each delivery is attempted once across concurrent sends.
- **States.** `reserved`, `attempting`, `delivered` (with `provider_ref`, the notification inbox row), `declined` (the notification path refused it: the recipient's settings or inbox; not retried, because that path may already have used another channel), `undeliverable` (no Axal account), `failed` (the attempt stopped before anything was sent; retried), `ambiguous` (the provider was called and no outcome was recorded). An `attempting` claim older than 15 minutes is read as `ambiguous`.
- **Reconciliation, not exactly-once.** Each notification carries its delivery's `delivery_uid` in the payload. A later send looks an ambiguous delivery up in the inbox by that uid: found, it is `delivered` and nothing is sent; not found, it stays `ambiguous` (`not_delivered_reason` says delivery could not be confirmed) until the sender asks for a resend with `{ "resend_ambiguous": true }`.
- **Publication state stays apart from delivery progress.** The update's `status`, `submitted_at`, `published_version` and `sent_at` (the first send's time, never moved) say what was published and when; each delivery row says how far its delivery got.
- **Sending again is the retry.** `POST /:uid/send` on a sent update no longer answers 409: it reserves anyone new in the audience, attempts `reserved` and `failed` deliveries, reconciles `ambiguous` ones, and leaves the rest. After a correction it reserves the recipients for the new version; earlier deliveries stay with the version they carried. The response keeps `{ uid, sent_at, recipients, delivered, not_delivered }` and adds `version` and `states` (a count per state). `/page` shows the latest sent version's deliveries with `delivery_state`; a state that is not delivered keeps a sentence in `not_delivered_reason`, so the founder page needs no change.
- Rows recorded before this change become version 1's deliveries with their recorded outcome, so a send after the change never reaches someone an earlier send reached.
- **Nothing sends on its own.** A delivery is attempted only inside a send someone made; no schedule retries.
