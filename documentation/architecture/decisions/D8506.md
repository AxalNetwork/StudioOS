## D8506 — One controller revision for the landing bot's edit, verify and publish, and a hand-back when the PR head moved (#8506)

- **Status:** built; the workflows are protected paths, so the PR is T2 and the owner lands it. Part of #8509 (row A2).
- **Why:** a repair attempt runs `prepare`, then `edit` and `verify` in up to three rounds (D6473), then the caller's publish step. `prepare` resolved the target commit once, but the controller (`scripts/landing-bot`, the trusted code that drives the round) was checked out with `ref: main` separately in `prepare`, `edit` and `verify`. `main` moves many times an hour, so the job that edited and the job that verified could run different controller code, and a later round a third. The verification then did not vouch for the code that made the edit.

### The controller commit

- `prepare` resolves it once, before its own checkout: `github.sha` when the run is on `refs/heads/main` (every caller is: `landing-bot-conflict.yml` and `landing-bot-main-repair.yml` gate on it), otherwise `main`'s head read once with `git ls-remote`. It is written to the run summary.
- `landing-bot-model.yml` passes it to each round as the `controller` input and exposes it as the `controller` output, with the edited commit as `head`.
- `edit` and `verify` in `landing-bot-model-round.yml` check out `${{ inputs.controller }}`. No checkout in either file names a branch: `landing_bot_controller_8506` fails on a literal `ref:`.
- The callers' `apply` jobs already check out `${{ github.sha }}`. They now receive the runner's `controller` as `CONTROLLER_SHA` and refuse a patch unless the two are the same commit, so the publish step runs the controller that edited and verified.

### The patch's record

- `scripts/landing-bot/model/record.mjs`. The edit job writes `record.json` beside `patch.json` and `manifest.json`: repository, the parsed task's digest, the PR (a new optional `pr` field of the task; the resolver sets it), the target head, the controller commit, the run id and attempt, the round, and the SHA-256 of `patch.json`'s exact bytes.
- `verify` rebuilds every field from its own inputs (`--round`, `--base`, `--controller`, the task file, the Actions environment) and refuses any difference before anything is applied or run.
- The publish step does the same with the plan's task and head (resolver) or the runner's `head` output (main repair), and `round` taken from the record, since it reads whichever round passed.
- The edit job calls no model when the record cannot be written: an unknown repository, run or attempt, or a controller that is not a full commit SHA.
- What it is not: a signature. The edit job could write anything. What it buys is that every job compares the same fields against inputs it did not take from the edit job, so a mix-up of revisions, heads, attempts or artifacts stops the attempt instead of publishing. A re-run that reuses an earlier attempt's artifact is refused on `run_attempt`.

### Publishing

- **The resolver** (`resolve.mjs apply`) compares the PR's current head with the verified head before staging and again before pushing. A moved head was a quiet skip; it is now a definitive hand-back, labelled and commented as D8077 hands back an exhausted keeper: what was verified is not what a push would make, and nothing re-runs the model on its own. The other quiet stops (closed, `bot:off`, the bot off, a breaker) are unchanged.
- The resolver re-reads the paths the patch changes, as well as the plan's files, against `pathGuard` (the #8067 list and T2). Today `checkPatch` already confines a patch to the plan's files, so this is a second reading of the same rule, kept so a later change to either cannot widen the other.
- **Main repair** (`mainRepair.mjs apply`) checks the record too; a refused record falls back to the plain revert, as any refused patch does. It does not require main's head to be unchanged: main moves, and the manifest's before hashes, read against main's head at apply time, are what keep a moved file from being overwritten.

### Tests

- `frontend/test/landing_bot_controller_8506.test.mjs`: the checkout refs in both workflows, the callers' wiring, verify's refusals (another controller, head, attempt, run, round, PR, task, changed bytes, no record), the publish check, and the edit job's refusal to call a model without a record.
- `landing_bot_conflict_6475`: a head that moved after verification hands back and pushes nothing; a patch from another attempt, controller or head hands back.
- `landing_bot_main_repair_6477`: the same refusals fall back to the revert.
