## D5572 — Outbound-only customer runner control protocol, disabled foundation (#5572)

**Status:** foundation only, unmounted and disabled. Owner-approved scope: the
protocol decisions and their fail-closed contract tests. The real `axal-runner`,
its Helm chart and Terraform, and any live cluster test wait for an explicit
BYOC customer need (#5564). No route, binding, migration, flag, secret or
account resource is added. Builds on D5565 (WorkspaceSpec, ExecutorAdapter,
fenced pull runner) and D5567 (grants, provider eligibility, sealing). Neither
D5566 nor D5568 has a decision file on main yet. This record depends on #5568
only for the checkpoint object it names.

### Decision

A customer-owned Kubernetes cluster joins Axal as an **independent trust zone**
through an outbound-only control agent, `axal-runner`. The runner opens every
connection to the Worker. The cluster exposes no inbound management API, and
Axal never holds a kubeconfig for it. The Worker stays the only control plane:
D1 and the scoped Durable Object hold task state, and the Cloudflare account
stays authoritative for every run's generation, lease and outcome. The runner
is a D5565 executor with `provider: 'byoc'`. It is not a second task engine,
scheduler, billing path or grant system.

`cloudflare-worker/src/services/agents/byocRunner.ts` holds the Worker-side
decisions as one factory, `createByocRunnerControl`, plus pure functions.
Every step a runner can take is a function that returns a D5565
`WorkspaceResult`, and every refusal is typed. The module reuses rather than
re-implements:

| Concern | Reused primitive |
|---|---|
| Lease, generation fence, heartbeat sequence, missed-beat reap, cleanup fence, idempotent completion | D5565 `createRunnerControl` (the BYOC layer feeds its `authorize` hook) |
| Resource, region, workload, network-mode, untrusted-code and checkpoint capability gate | D5565 `executorEligibility` over `byocCapabilities(runner)` |
| Provider security evidence for grants | D5567 `WorkspaceProviderEvidence` via `byocProviderEvidence(runner)` |
| Egress destination preflight | D5567 `workspaceDestination` |
| Grants for artifact upload, read and publish; revocation on kill | D5567 `issue`/`redeem`/`revoke` (injected as `revokeGrants`) |
| Checkpoint ownership, restore regions and key | D5567 `WorkspaceObject` fields, sealed with D5567 AES-GCM |

### Identity and transport

The runner generates an ECDSA P-256 key pair inside the cluster. The Worker
stores only the public point and its RFC 7638 thumbprint, which is the key id.
Every runner request is a signed envelope: base64url JSON of
`{v, runner_id, key_id, iat, nonce, kind, body}`, signed over
`axal-runner-v1.` + payload. The Worker accepts a request only when all of
these hold:

- the runner is known, attested and not revoked;
- the key id is current, so a rotated key is refused as `credential_rotated`;
- the credential has not expired;
- `iat` is within the clock-skew window;
- the nonce has not been seen;
- the signature verifies;
- the envelope's `kind` matches the operation, so a lease request cannot be
  replayed as a report.

This signed token is the application-layer identity. mTLS (Cloudflare API
Shield client certificates, pinned per runner) may be added at the edge as a
second factor. It does not replace the envelope check, because the Worker must
bind each request to a runner record, a generation and a nonce whatever the
transport is. D5567 grants remain the Worker's capability tokens for artifact
and publish audiences. A runner request proves who is calling, and a grant
proves what that caller may touch. Both are required.

No privileged credential crosses the boundary in either direction. D1, the
Worker and the task sandbox hold no kubeconfig, cloud key or cluster token. The
runner's own service account is namespaced and created by the customer's
install. Workloads get none of the runner's key material.

### Enrollment

1. **One-time registration.** A customer admin of the venture (existing role
   checks, injected as `authorize`) opens a registration. It binds one venture
   scope (tenant, company and an optional project list), one cluster id and
   region, the namespace prefix, and the **delegated scheduling limits**:
   workload classes, concurrency, CPU, memory, disk, duration, permitted
   egress hosts, checkpoint restore and shell. The Worker returns a 256-bit
   code once and keeps only its SHA-256. The code expires within 1 to 60
   minutes, and a wrong code burns the registration.
2. **Enroll.** The runner redeems the code with its public key, proving
   possession by signing with it, and presents its enforcement manifest. It is
   `pending_attestation` and can do nothing.
3. **Admin attestation.** A customer admin, never an Axal operator, confirms
   the exact key id and manifest the runner presented. Any difference is
   `attestation_mismatch`. Only then is the runner `active`.
4. **Conformance (untrusted work only).** A trusted Axal verifier records a
   conformance probe's pass with a timestamp. Untrusted code needs a pass
   younger than `conformance_max_age_ms`. The probe pod itself, which attempts
   a host mount, a privileged pod, a metadata fetch and egress to a canary, is
   runner work that remains.
5. **Rotating, expiring credentials.** A credential lives 5 minutes to 24
   hours. Rotation is signed by the current key and carries a proof signed by
   the new one. The old key stops at once, with no overlap. An expired
   credential cannot rotate, so the runner must re-register.
6. **Remote revoke and kill.** `revoke` marks the runner revoked, drops its
   key, fences every run it holds through D5565 `requestCancel` (a generation
   bump) and revokes those runs' D5567 grants. `kill` does the same for one
   run. Both are open to a customer admin or an Axal operator, and both work
   while the feature flag is off, so switching admission off never strands a
   live workload.

**Ownership.** The customer owns the cluster, its network, its logs, its data
retention and its compute bill. Axal owns the task record, grants, sealed
artifacts, AI usage on the existing ledger and the decision to stop. The
consent wording below says this to the member.

### Work delivery

- **Pull-only.** The runner asks for a run with `lease`. The Worker reads the
  broker's own spec (`specOf`, never the runner's copy) and runs
  `placementDecision`. That decision checks, in order: attested and not
  revoked, online, inside the venture scope, enforcement gaps, egress, D5565
  eligibility, the delegated concurrency limit, and customer-managed consent.
  The Worker then reserves capacity and takes D5565's atomic lease. A second
  lease of the same run, from any runner, is `lease_unavailable`, and the
  holder's assignment is untouched.
- **Signed, fenced, monotonic status.** `report` must come from the
  assigned runner and name the run's own namespace (`runNamespace`: prefix,
  tenant and a SHA-256 of the scope and run). It must carry the live
  generation and a strictly higher sequence, which D5565 checks. Any refusal
  means stop.
- **Heartbeat and offline.** Every verified request updates the runner's
  `last_seen`. A cluster quiet for `offline_after_ms` is not placed
  (`cluster_offline`). The trusted `sweep` runs D5565 `reap`, which fences each
  lease past its missed beats, records the generation the cleanup must be
  acknowledged under, and revokes the run's grants.
- **Disconnected reconciliation.** On reconnect, the runner lists what it
  holds. The Worker answers `continue` only for a live lease at the current
  generation for this runner, and `stop` for everything else, including runs
  it never assigned. Runs the Worker assigned but the runner no longer
  reports are fenced and told to stop.
- **Cleanup before relaunch.** Capacity and the run stay held until the runner
  confirms the namespace is gone (`cleanup`). If the runner is revoked or
  gone, the customer admin of that venture confirms it (`confirmCleanup`).
  Only then does D5565 allow a new lease, because a missing heartbeat does not
  prove a pod stopped.

### Runner-side enforcement it must attest

`BASE_ENFORCEMENT` is required for every workload:

- signed-image verification and digest-pinned pulls;
- a namespace per run and resource quotas;
- run as non-root, drop all capabilities, `RuntimeDefault` seccomp and no
  privilege escalation;
- deny privileged pods, host paths, the host network, host PID and IPC, the
  container-runtime socket and cloud metadata;
- a default-deny NetworkPolicy and ephemeral scratch;
- `activeDeadlineSeconds` and cleanup on a terminal state.

Untrusted code (`coding_untrusted`) also needs `read_only_root_filesystem`, a
`sandboxed_runtime` with a gVisor or Kata runtime class, and a fresh
conformance pass. An allowlist network policy needs
`egress_allowlist_enforced` (FQDN-aware egress, such as Cilium). A runner
missing any required feature is refused with `enforcement_missing`, and the
missing feature is named. The same manifest maps to D5567 provider evidence,
so the grant gate refuses it too: a runc cluster is `hostile_workload_denied`.
**When the cluster cannot isolate, untrusted code is refused, never
downgraded.**

**Egress.** Each allowlisted destination must pass D5567's preflight, which
rejects metadata, local and internal names and URL tricks, and must be in the
customer's delegated `egress_hosts`. Anything else is `egress_forbidden`.

### Checkpoint and resume

`resumeDecision` allows a resume only when all of these hold:

1. The checkpoint belongs to the run's tenant and run, and it is the spec's
   checkpoint ref.
2. It is sealed, using D5567 AES-GCM with a key id. A plaintext checkpoint is
   refused everywhere (`plaintext_checkpoint`).
3. The target provider and region are in the spec's allowlists, and the
   execution mode matches the provider: `byoc` is customer-managed and names a
   cluster.
4. A region change is in the checkpoint's server-owned
   `approved_restore_regions`.
5. Both jurisdictions are known, and a jurisdiction change is allowed by the
   venture's data policy (`cross_border_denied` otherwise).

A runner may cache a checkpoint locally only if the customer's policy allows it
and it attests `encrypted_local_checkpoint`. The Worker's R2 copy stays the
authority.

### Consent

`consentStatement` returns different words for each mode, and each starts with
its label: "Axal-managed execution" (infrastructure Axal operates) or
"Customer-managed execution" (a named cluster your organization operates,
which is responsible for isolation, network, logs, retention and compute cost,
and is reached only over the runner's own connection). `consentCovers` accepts
a consent only for the same mode, scope, cluster and region and the current
version's exact words. An Axal-managed consent never covers customer-managed
work, and the reverse is also refused. The lease refuses with
`consent_missing` until a covering consent exists.

### Storage the host will need (not added here)

- **D1:** runner registrations (code hash, scope, cluster, limits, expiry,
  creator), runners (public key and thumbprint, retired key ids, manifest,
  status, attester, conformance time), consent records, and the `byoc`
  ExecutorAdapter row. Every write goes through `logAdminAction` or
  `activity_logs` and binds every value.
- **Durable Object (per venture or cluster):** the request-nonce window,
  `last_seen`, active-run reservations and assignments, in the same atomic
  transaction as D5565's lease record. The in-memory stores live only in the
  tests.
- A migration named `YYYYMMDDHHMM_5572_<slug>.sql`, added only with the first
  mounted route.

### Verification

`cloudflare-worker/test/byoc_runner_5572.test.ts` has one test per acceptance
case: rogue runner, rotated, expired or revoked identity, duplicate lease,
offline cluster, stale callback, namespace and tenant escalation, forbidden
egress, missing enforcement, cross-border resume and consent. A further test
checks that the protocol is off and unmounted, that revoke and kill still work
while it is off, and that audit events hold only `action`, `outcome`, `code`
and `count`. The final test applies 16 deliberate source mutations, one or more
per case, and requires each to fail its journey, with each journey also passing
on the real module. All keys are generated at runtime, identities are
synthetic and the clock is injected. These are local contract tests, not
evidence that any cluster isolates code.

### Open owner decisions

- **(a) Evidence for untrusted code on BYOC.** Today the code accepts a
  customer-admin attestation plus a fresh Axal conformance probe. The
  alternative is to keep BYOC to trusted workloads only. I would keep the
  probe requirement and, until a probe exists, treat BYOC as trusted-only, which
  is already the effective state.
- **(b) Offline cleanup.** Today a fenced run on an offline cluster waits for
  the runner or the customer admin to confirm cleanup. An alternative would
  treat an attested `activeDeadlineSeconds`, past its deadline plus a grace
  period, as proof the pod stopped. I would keep the explicit confirmation.

### Rollout and rollback

Nothing ships active. Activation needs the remaining work above, a security
review, an owner-authorized flag and a named customer. Rollback is deleting the
unmounted module. Once a host persists records, roll back by turning
admission off, revoking the runners (which fences and kills their runs),
confirming cleanup and keeping the records. Never rewrite task or usage rows.
