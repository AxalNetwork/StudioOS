## D5458 — Bind deal review, preview and release to the approved revision (#5458)

- **Status:** proposed integration contract and acceptance fixtures. The release policy is pending owner approval.
- **Dependencies:** #5454 owns private preparation and investor projection, #5456 owns revision identity and idempotency, and #5457 owns source manifests and readiness. D5459 maps the workspace boards. Coordinate the approval read with #4814 and #4716, and the signed-paper and commitment handoff with #4633 and #5355.

### Current integration points

- `routes/deals.ts` creates a legacy deal directly on `POST /api/deals/draft`. The existing record has no reviewed release pointer. The round stage in `services/dealTransitions.ts` also governs live operations. Neither the draft route nor a stage transition is publication.
- Investor detail uses `canReadDeal` and `serializeDeal`. Document and evidence routes have separate NDA, relationship and sharing checks. #5454 must supply the shared candidate and live projection for these surfaces before preview can assert parity.
- `services/approvalSources.ts` owns inbox projections and lane counts. Add a read of the canonical review record once the preparation schema exists. Inbox actions and workspace actions must call the same decision operation.
- `POST /api/deals/:id/commitments` currently checks the live deal stage and minimum. Integrate released terms identity at the handoff so accepted commitments and signed documents retain the original terms and legal-party snapshot.

### Revision-bound decisions

The proposed approval binds deal, revision, content digest, manifest digest and versions, audience, policy version, issuer company, project and authorized representative or mandate. Resolve the issuer through the canonical company and project pair. A project without a company remains research-only. The account's active company, an investor's firm and fund/SPV context do not supply the issuer.

Submitting and requesting changes records the actor, time and reason against the current revision. A separate authorized reviewer is the proposed policy. Missing policy blocks approval and publication while drafting remains available. Preview is authenticated and scope-bound. It takes an explicit synthetic audience scenario and uses the same server projection as a live release. It performs no invitation, access grant, notification or publication.

The final write must compare the expected revision and current review and revalidate authority, company/project binding, source permissions, audience and readiness. Compare the policy and source version guards in the same authoritative transaction. An unreadable guard aborts. Persist the release pointer, identity, audit event, operation result and any explicitly requested delivery intent together. Dispatch follows the commit, rechecking recipients and source permissions. Retry unresolved delivery intents without re-running publication. Provider acceptance and confirmed delivery are separate outcomes.

Withdrawal or archive requires a reason and current release identity. Remove discoverability and invalidate derivatives. Retain signed paper, commitments, bank evidence and prior audit history. A correction requires a new reviewed revision. Revalidate the issuer, project and representative at origination, sending and execution. Where they differ from the approved snapshot, stop the new action for reconciliation.

### Synthetic acceptance fixtures

| Fixture | Expected result |
| --- | --- |
| Admin A authors r1, Admin B requests changes, r2 changes only the audience | r1 remains historical. r2 requires a new decision. The live pointer does not change. |
| No configured policy, self-approval, reviewer authority revoked, or policy revision superseded | No approval can authorize publication. Preserve the private draft and its history. |
| Issuer absent, company/project mismatch, representative belongs to another entity, or project moves after approval | Refuse the affected action. Keep the released and signed legal-party snapshot intact. |
| Same candidate/live content and synthetic teaser, invite-without-NDA and authorized scenarios | Preview equals the live projection for that audience. Restricted filenames and notes are absent. Revocation is applied on subsequent retrieval. |
| Parallel publish calls, idempotent replay, or timeout after commit | One release and one durable delivery intent per logical action. Replay returns the persisted outcome. |
| Audit or intent write fails; provider fails after commit or outcome is unknown | The first failure leaves the live pointer unchanged. The latter cases retain the publication and expose a truthful, retryable delivery state. |
| r1 published, r2 private, existing commitment and signed paper | Investor reads and new transactions use the current released revision. Existing commitments and signatures keep their recorded terms. |
| Withdrawal or archive replay; inbox vs workspace read | Discoverability stays withdrawn. Historical records remain. Inbox, workspace and history show the same review decision. |

The code integration and fixture execution await the prerequisite contracts. Owner decisions still required are the reviewer and publisher matrix, permitted teaser audience, and notification authority. No production release or recipient outreach is part of this work.
