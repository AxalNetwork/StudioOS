## D5204 — An all-day event is a calendar date; coverage is the server's count (#5204)

Part 4 of 7 of the 2026-11-09 Calendar audit (of #3723). P1. No migration.

Three findings, one theme: the page was deciding things it had no standing to decide.

### 1. An all-day event could land on the wrong day

A provider's date-only event travelled as `"2026-11-09"` in `start_at`, and every grouping on the page read it
with `new Date(...)`. A bare ISO date parses at **UTC midnight**, and UTC midnight read in a zone west of UTC is
the evening before — so one row drew on the 8th in Los Angeles and the 9th in Tokyo.

An all-day event now says so and carries its own dates:

| field | meaning |
| --- | --- |
| `all_day: true` | this is a date, not an instant |
| `start_date` | the provider's own date, inclusive |
| `end_date` | the provider's own date, **exclusive** — a one-day event on the 9th ends on the 10th, as Google states it |

`start_at` and `end_at` keep whatever they held, so the `.ics` file, the subscription feeds, the provider push
and every existing reader are untouched. Google's `start.date` (with no `dateTime`) and Graph's `isAllDay` are
both read; `isAllDay` was added to the Graph `$select`, which had not asked for it.

On the page, `dayKeyOf(ev)` places an all-day row by the date as written and never builds a `Date` from it; a
timed row still follows the member's own clock, which was always right. `byDay` and the agenda's grouping both
use it, so the grids and the list agree. `allDayLastDate(ev)` turns the exclusive end inclusive for display
only: the exclusive value is what travels.

### 2. A partial provider read looked complete

The readers stop at 4 pages of 250 and mark the source `truncated`. Nothing read that flag, so a Google read
with a thousand events and more to give looked exactly like a complete one. The page now discloses it, in the
audit's words — "… is partially loaded. Narrow the date range to see everything." — as its own banner
(`cal-truncated`), and the rail's provider row shows "Partially loaded" (D5202's read health). A truncated
source also makes `coverage.complete` false even though every source answered, because answering in part is not
answering.

### 3. Coverage was a constant in the frontend

"26 of 28 sources answered" was built from `KINDS.length`, a list in `CalendarPage.jsx`. That denominator
counted sources the member had hidden, sources their role never had, providers they have not connected, and
nothing a later registry adds until the page is rebuilt — four ways to be wrong at once.

The Worker derives it from the set it actually attempted:

```
coverage: { attempted, answered, failed, hidden, complete, truncated_kinds? }
```

`attempted` is the sources this read asked for; hidden ones are not asked and are counted in `hidden` instead. A
provider with no connection is in none of them: it was never a source (`NoSource`) and it is not a failure.
`answered + failed === attempted` by construction.

The page renders that. It takes `attempted` and `hidden` from the server — only the server knows what it asked
for — and derives `answered`, `failed` and the truncated kinds from the source rows it holds, so D5202's scoped
re-read of one provider moves the count without a second full read and the rows and the sentence cannot
disagree. A worker that sends no `coverage` still reads as "source coverage not reported", never as complete.

### Tests

- `frontend/test/calendar_allday_coverage_5204.test.mjs` (8): the zone matrix the issue names — Istanbul,
  Lisbon, New York, Los Angeles, Tokyo, plus Kiritimati and Niue for the extremes — on the 9th, New Year's Day
  and New Year's Eve; three DST transitions; a timed row still following the local clock; `byDay` placing both
  kinds together and counting what it could not place; the exclusive end kept and shown inclusive, including
  across a month and a year boundary; and the page's coverage read from the server with `KINDS.length` gone
  from its code.
- `cloudflare-worker/test/calendar_allday_coverage_5204.test.ts` (7): Google date-only and Graph `isAllDay`
  parsed with their dates and exclusive ends, timed events untouched; coverage adding up; a hidden source not
  inflating the denominator; a disconnected provider neither attempted nor failed; a read capped at exactly
  `MAX_PAGES × PAGE_SIZE` marked truncated and making coverage incomplete while failing nothing; and a scoped
  read reporting only its own kind.
- `frontend/tests/visual/calendar_degraded_5202.spec.mjs` gains a third journey: the truncation disclosure
  rendered in a browser.

Mutations caught: the all-day branch removed, so dates parse as instants again (the audit's own bug: 4 of 8
cases fail); the exclusive end read as inclusive; the page counting `KINDS.length` again; the Worker hardcoding
the denominator; a capped read calling itself complete; Google's date-only flag dropped; Graph's `isAllDay`
ignored; the exclusive end collapsed to the start; hidden sources not reported.

One mutation did **not** fail at first: removing the truncation banner's condition left its text in the file, so
a source-text assertion still matched. That test now asserts the condition, and the browser journey renders it.

### Not in this slice

Multi-day all-day events are placed on their start date, as every item is; `end_date` and `allDayLastDate` carry
what a future change would need to span them across cells. The rest of #3723.
