## D8076 — Queue concurrency: one privileged PR at a time, at most three per slot, a group per shared state (#8076)

- **Status:** built by S17 on 2026-11-22 for #8076 (audit section 14), after #8054, #8057 and #8067/#8104.
- **Builds on:** D6481 (the first-entry feeder), D8067 (`pr:privileged`).

**The problem.** Nothing stopped agents from filling the merge queue from one slot, or from queueing two PRs that
change privileged paths side by side. Workflows that write shared state also relied on each file's own concurrency
key, with nothing checking that the key stayed.

**The holds** (`scripts/landing-bot/concurrency.mjs`, pure). The feeder holds back a candidate when either is true:
- `PRIVILEGED_IN_QUEUE` (1) `pr:privileged` PRs are already in the queue;
- its slot already has `PER_SLOT_IN_QUEUE` (3) PRs queued.

Both constants live in `scripts/landing-bot/rules.mjs`, and the owner may change them on #8076. A sweep counts its
own admissions against later candidates. A PR's slot is the `slot:S…` label of the issue its body names
(`owningSlot()`). A PR that names no such issue has no slot, and the per-slot cap does not count it. If the queue's
entries or a slot cannot be read, the candidate is held, never admitted.

**Where it runs.** `feeder-sweep.mjs` checks the holds in the plan and again before each write in the apply stage,
because a person may have queued a PR in between. `feeder-github.mjs` gains two read-only methods:
- `readQueueEntries()`: one GraphQL read of the queue's entries with labels and body. An incomplete page throws;
- `readOwningSlot()`: one REST issue read, cached per run.

**The hold line.** Each hold writes one line to the feeder's run summary, for example: "Held from the merge queue:
slot S07 already has 3 PRs queued (#1, #2, #3), and the most is 3. It is admitted once one leaves the queue."
- **Departure from the issue:** the feeder has no sticky comment and no write token in its plan stage. The line
  goes in the run summary rather than a PR comment. `holdLine()` is the single source of the text, so a later
  sticky write reuses it unchanged.
- **Privileged PRs and the feeder:** the feeder admits only T0 and T1. A privileged PR is usually T2 and queued by
  the owner, so the privileged hold mostly guards the bot against adding a privileged entry beside one the owner
  queued. GitHub's own queue limits stay #8060's.

**Shared-state workflows.** Each workflow below declares its own `concurrency` group with
`cancel-in-progress: false`, listed in `SHARED_STATE_GROUPS`:

| Workflow | Group | State it serialises |
| --- | --- | --- |
| labels sync | `labels-sync` | repository labels |
| conflict indicator | `studioos-landing-conflict-indicator` | the PR-list conflict label |
| branch keeper | `studioos-landing-bot-keeper` | keeper pushes |
| feeder | `studioos-landing-feeder` | queue entries and the daily feed ledger |
| deploy (job `deploy`) | `studioos-production-release` | the retention ledger and the release |

Every one of them already had its group on main, so no workflow file changes. The test fails if a workflow loses
its group, if the group starts cancelling a running write, or if two states share one key. The groups were not
merged, because merging would drop scheduled runs that are waiting.

**Rollback.** Revert the PR, and the feeder admits as before. No data, settings or workflow change.

**Tests.** `frontend/test/landing_concurrency_8076.test.mjs` covers:
- both holds and their release;
- the hold lines;
- unread facts holding, never admitting;
- the sweep's own admissions counting;
- the plan and the apply re-read against the feeder sweep with a fake reader;
- the reader's queries;
- every named workflow's group.

`landing_feeder_sweep_6481.test.mjs`'s fixture gains an empty queue and no slot. The mutation check caught 21 of 21
mutations.
