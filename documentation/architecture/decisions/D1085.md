### 2. No scope asked, none accepted

Notion's MCP documentation names no OAuth scope. So the record asks for none and accepts none: a grant that reports any scope is refused and revoked (`scope_refused`). That is the shared client's rule (`grantOverreaches`), and it fails closed.

**One shared-client change.** `authorizeMcpUrl` and the DCR registration now leave `scope` out when a record asks for none, rather than send `scope=` empty. Mercury is unchanged: it asks for `read offline_access`.

**This is the first thing the live sign-in checks** (§6). If Notion's grant reports a scope, `accepted_scopes` must name it before anyone can connect.

### 3. The provider (`integrations/providers/notion.ts`)

It is imported once from `index.ts`.

| Hook | What it does |
|---|---|
| `connect` | A support session is 403 `support_session_refused`. Anyone else is 410 `sign_in_only`: there is no token to paste. Nothing reaches Notion or is stored. |
| `disconnect` | `revokeMcpConnection`: the grant revoked at Notion, best effort, then the tokens deleted. The integrations route deletes the row after. A support session may disconnect. |
| `revokeGranted` | A grant the route refused, revoked at Notion, best effort. |
| `ready` | D751: `mcpReadiness`, which is true for a record that registers by CIMD or DCR. |

The sign-in itself is D1080's:
- the start's refusals (signed in, the descriptor's audience, a support session, an active company, the plan);
- the state, the cookie and `iss`;
- the exchange;
- one `oauth_mcp` row with its tokens encrypted.

**A refresh** is the shared client's (`mcpAccessFor`):
- a token about to expire is refreshed first, behind the lease;
- the rotated refresh token is stored before it is used;
- a refused refresh marks the row `error` / `token_rejected`.

### 4. The typed reads (`services/notion/reads.ts`)

This is the only file that opens a Notion session (`openNotionReads`, or `notionReadsFor` for a member's row). Every part reads through it.

| Read | Tool | Returns |
|---|---|---|
| `searchSources(q)` | `notion-search` | pages and data sources: id, kind, title, URL, last edit |
| `fetchPage(id)` | `notion-fetch` | the Markdown exactly as sent (capped at 200,000 characters), title, URL, last edit, and its fingerprint (SHA-256 of the Markdown) |
| `listChildren(id)` | `notion-fetch` | the pages and data sources directly under a page |
| `dataSourceSchema(id)` | `notion-fetch` | a data source's properties, by name and type |
| `queryRows(id, { cursor, view })` | `notion-query-data-sources` | rows a page at a time, each property as a string, number, boolean or null, and the next cursor |

**Read-only, three times over:**
- the record lists no write tool;
- the session refuses any name off the record, or one the server does not offer as the record allows, before a request;
- each read builds its own arguments. `queryRows` sends `mode: 'rows'`, or `mode: 'view'` with a view id. **Never SQL**: no SQL mode and no SQL argument can be passed through it.

**A Notion id is checked before it reaches a tool argument.** `notionId` takes 32 hex digits, with or without the UUID dashes. A URL, a path, a query string or any other shape is `bad_id`, and nothing is requested. Ids read back from an answer are checked the same way, and a result without a valid id is dropped.

**Page text is data.** It is returned as strings. Nothing in it is followed, fetched or logged, and a link is kept only when it is https on Notion's hosts. An error carries a code and a status, never a body.

Every test runs against the fake. The live connection records `verified_on` and these:
- **The scopes** a real Notion grant reports (§2). Today any reported scope is refused.
- **Registration:** whether Notion's server takes a client ID metadata document or DCR, and the issuer it names.

  - the Markdown under `text`, `markdown` or `content`;

  The parsers accept a structured answer or the text of one.
- **That `notion-fetch` of a data source answers its schema,** and that `listChildren` is read from the parent page's `children`.
