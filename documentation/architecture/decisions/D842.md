## D842 — /mcp accepts member API keys; every call gets an execution id, a time limit and a structured error

- **Status:** built by S07 for #2470, part of #2463. This is the second task of the MCP platform plan (`documentation/architecture/MCP_API_PLATFORM.md`).
- **Basis:** `origin/main` at `87b87a48`. Worker paths are relative to `cloudflare-worker/src/`.
- **Stacks on:** D841 (member API keys, #2464), D666 and D669 (the MCP server, its grants and its per-call checks), D846 (one tool registry, #2467).
- **Migration:** none.

### 1. The decision

A member API key is a second credential for the same principal (D841). So `/mcp` does not grow a second permission path. A key resolves to the `GrantProps` an OAuth grant carries, and the same `callTool` checks run on every call:
- the user is re-read (active, not deleting, `jwt_min_iat`);
- each company is re-checked against what its creator can still reach;
- the scope is the key's own.

The OAuth suites (`mcp_server_d666`, `mcp_authorization_d669`) run unchanged.

### 2. What was built

- **`mcp/oauth.ts`: the key branch.** `routeMcp` reads the bearer on `/mcp` and `/mcp/*`. An `axk_` bearer is served by `serveWithKey` and never sent to the OAuth provider. In order:
  1. With `API_KEYS_ENABLED` off, it answers `401 invalid_key`.
  2. If the IP has failed 10 key lookups this minute (`mcp_keyfail:<ip>:<minute>`), it answers `429 rate_limited` before the lookup. If that count cannot be read, it fails closed.
  3. `verifyKey` runs. A failure counts against the IP and answers 401 with `invalid_key`, `revoked_key` or `expired_key`. It never says whether the id exists: a wrong secret and an unknown id read alike.
  4. The key's own rate is checked (`mcp_rl:key:<uid>` at `rate_per_minute`, counted per HTTP request). Past it, `429 rate_limited` with `Retry-After: 60`.
  5. `touchLastUsed` writes `last_used_at`.
  6. The request is served with props `{ userId, clientId: 'apikey:<uid>', companies, clientName: <key name>, grantedAt: <created, epoch s>, keyUid }` and the key's scopes.
- **`mcp/server.ts`: execution.**
  - **Execution id.** `callTool` gives each call a UUID. The tool receives it as `ToolRun.executionId`, and every result, success or error, reports it in `_meta["vc.axal/execution_id"]`.
  - **Time limit.** Each tool runs under `tool.timeoutMs ?? TOOL_TIMEOUT_MS` (20 s). Past it, the call answers a `timeout` error and `ToolRun.signal` aborts, so #2466's hold can be released. The rejection lands before the abort, so a tool that answers on the abort cannot win the race (the test caught this).
  - **Shared server.** `serveMcp` builds the one stateless server both credentials use.
- **Structured errors.** Every tool error is `{ error: <sentence>, code, …extra }`:
  - `insufficient_scope`: the key wording says to create a key with the permission;
  - `insufficient_tokens`: the router's `budget_user_*`, with `status: 402`, `needed_microusd` and `available_microusd` as `null` (unknown until #2466 reports them, never 0), and `add_tokens_href`;
  - `spend_limit`, `ai_paused`, `budget_review`: passed through with their status;
  - `rate_limited`, `timeout`;
  - `unavailable`: our failure, `budget_org_month` or `kill_switch`;
  - `refused`: every other check.
- **`mcp/grants.ts`.**
  - `GrantProps.keyUid`;
  - `ToolRefused.code`;
  - `withinGrantLimit` takes a limit id and a rate;
  - the IP failure counter;
  - `logToolCall` adds `api_key_uid` for key calls only, so an OAuth call's activity line is unchanged.
- **`services/apiKeys.ts`.** `SCOPE_LABELS` gains D846's `build:read`, `raise:read` and `connectors:read`. Without them the key page offered them under their raw names, as write scopes. `member_api_keys_d841` had been red on main since #2467.

### 3. Why count a key per request and a grant per call

Plan §3 promises `429` with `Retry-After` for a key, and only the HTTP response can carry that header. A tool error inside a 200 cannot. So a key's requests are counted before the server is built, and `callTool` skips its grant count for keys. OAuth grants keep their per-call count of 60 a minute, so D666 is unchanged.

### 4. Not built here

- Usage rows per key and per execution id: #2465 (D843).
- The hold itself and its release on the abort, and the real `needed_microusd`/`available_microusd`: #2466 (D844).
- The per-user limit across keys (120/min): #2472.

### 5. Verified

`cloudflare-worker/test/mcp_api_keys_d842.test.ts` (12 tests on D666's fixture, with migration 523) covers:
- initialize, tools/list and tools/call with a key, one execution id per call, and `last_used_at`;
- the activity line, and no secret in logs, `activity_logs` or the response;
- revoked, expired, wrong-secret, unknown and malformed keys answering 401, and wrong secret and unknown id reading alike;
- the flag off, and an OAuth token still served;
- the IP throttle after 10 failures, and failing closed;
- the per-key rate;
- `validate:write` not listed or callable without the scope, and `insufficient_scope`;
- a company outside the list, and one the creator lost;
- sign out everywhere;
- a slow tool timing out with its signal aborted;
- `insufficient_tokens` with null amounts;
- the code map.

Each new check was mutation-tested: 18 mutations of the branch, the limits, the timeout and the codes, all caught. `mcp_server_d666` and `mcp_authorization_d669` are unchanged and green.
