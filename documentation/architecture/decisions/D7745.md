### Routes

| Route | Gate | Does |
|---|---|---|
| `POST /preview` | `requireSuperAdmin` | Manifest + pages (≤ 500 entries each, ≤ 5,000 a request) of `[source key, record id, row hash]`. Per source: sent, new, unchanged, changed, removed, private fields removed, and whether a whole list matches the manifest's digest. One statement per page through a bound JSON value. Writes nothing. |
| `POST /runs` | write bar | Opens a run: idempotency key, manifest, column classes and contact treatment, the declared list digests (in the manifest) and the declared file digest. Answers the chunk bound. |
| `GET /runs` | `requireSuperAdmin` | The 50 newest runs: status, counts, digests labelled by what proves them. |
| `GET /runs/:uid` | `requireSuperAdmin` | One run: counts, the list digests recomputed from the store, the chunks the Worker holds, and its members (ids, stated hashes, outcomes; never a body) in pages of 1,000 (`?offset=`). |
| `POST /runs/:uid/chunks` | write bar | One chunk: `chunk_index` and at most 50 records. |
| `POST /runs/:uid/seal` | write bar | Read-back against the expected list. |
| `POST /runs/:uid/reconcile` | write bar | `resume` a partial run, or `close` a partial or uncertain one. |
| `POST /removals` | write bar | `private_fields`, `record` or `source`. |

Every route first requires a sign-in and refuses a support session (`impersonated_by`) with 403
`support_session_refused`; then the gate. The gate is named in each handler (`gate(c, requireSuperAdmin)`), so the auth
inventory reads it and no ledger entry is needed. A signed-out caller gets 401 (the house status for no session), a
member, a plain admin and a branch deployment 403. The write bar is a TOTP session and a fresh step-up: a step-up that
lapses mid-run refuses the next chunk with 403 `step_up_required`, writes nothing, and the run resumes after a new
step-up. No rate-limit exemption is added.

### Decisions

1. **A chunk may mix sources.** 2,191 records are 44 chunks of at most 50. The store keys every record by its own
   source, so mixing costs nothing.
2. **One run open at a time.** `running`, `uncertain` and `partial` block a new run. The check is inside the run's own
   `INSERT … WHERE NOT EXISTS`, so two opens cannot race past it; the audit row is written only if that insert wrote
   (`onlyIfChanged`). The same key again answers the first run and writes nothing; with another file digest it is
   refused (`idempotency_key_reused`).
3. **Reconcile has two actions.** `resume` puts a partial run back to `running` so its missing chunks can be sent and
   it can be sealed again. `close` ends a partial or uncertain run as `failed` (the store's unused status): its stored
   records stay, it no longer blocks. An uncertain run is settled by sending its uncertain chunks again (the store's
   `reconcileChunk`), never by `resume`.
4. **A chunk is keyed by (run, chunk index).** The same records under a held index answer `replayed` with no batch at
   all. Other records under a held index are refused (`chunk_index_reused`), and so is a record the run already holds
   under another index (`record_in_other_chunk`). A chunk index the run lists as uncertain is always sent through
   to the store, which settles it.
5. **Refused before any write:** over 50 records or 600,000 bytes (`chunk_too_large`, measured on the raw body before
   it is parsed), a malformed record, a duplicate in the chunk, a cell under a contact column
   (`contact_column_refused`), and a body hash that does not match (`body_hash_mismatch`, by record id). Then the
   store's `writeChunk` writes the chunk in one `DB.batch` whose last statement is the run update.
6. **Q3 B at the door.** The client leaves contact columns, personal-profile links and whole person records out
   before upload. The route refuses a contact cell rather than letting the store drop it, and refuses a `held`
   column (`held_not_enabled`; `allowHeld` is never set, the dormant held path is not used). A profile-link column
   is classed `contact` by the client. A whole person record cannot be recognised by the Worker: its exclusion is the
   client's, and the manifest may state the count as `excluded_person_records`, kept and shown as declared.
7. **Seal names ids against the expected list.** The seal request carries the ordered
   `[source key, record id, row hash]` list. Its per-source digest must equal the manifest's (else
   `expected_list_mismatch`, nothing sealed). The Worker then reads the run back from the store and names, up to 100
   each with whole counts: missing, hash differs, unexpected, altered (stored body hash ≠ recomputed) and refused (with
   the store's code). Complete only when every source has every record present once under its expected hash, the
   recomputed list digest equals the declared one, every body hash recomputes, nothing is refused and stored + withheld
   + blank cells equal the manifest's. A pending uncertain chunk keeps it `uncertain`; otherwise it is `partial`.
   The store's own `sealRun` agrees on the status (tested).
8. **Audit rows.** One `admin_audit_log` row (`adminAuditStatement`) in the same batch as each run open, seal,
   reconcile and removal, with the run id, source keys, counts and digests (a removal also names its scope and record
   id). A chunk's record is the run's own receipt (`research_source_run_records`).
9. **Removals refuse while a run is open** (`run_open`), so a chunk planned before a removal cannot land after it.
   After a record or source removal preview reports it `removed`; after a private-fields removal it reports
   `private_fields_removed` (the non-contact body is still stored, unchanged). A replay restores nothing: the store
   refuses a removed record (`record_removed`) and a removed source refuses the run (`source_removed`).

### The digests and hashes, and what each proves

| Value | Who computes it | Checked |
|---|---|---|
| Body hash: SHA-256 of `bodyJson(cells)` (the permitted columns as sent) | client and Worker at the chunk; store at seal from the stored bytes | **Computed.** A mismatch refuses the chunk; an altered stored body fails the seal. |
| List digest: per source, SHA-256 of sorted `id:stated_hash` lines (the store's `membershipDigest`) | client in the manifest; Worker from the store at seal and on read | **Computed.** The one the seal checks. |
| Stated row hash (whole record) | client | **Declared, not checked.** `HASH_RECIPES` is empty: no package recipe exists. |
| File digest (SHA-256 of the file on the operator's device) | client | **Declared, not checked.** No request receives the file. |

No whole-package or whole-record verification is claimed. That needs the package's hash recipe on #7742 (D7742 Q1).

### Rehearsal (local; `research_source_imports_rehearsal_7745.test.ts`)

An invented package of the audited shape, generated in the test: four sources of 120, 134, 84 and 1,853 records with
5, 12, 11 and 12 fields (two sources carry a contact column the client leaves out), the largest record 9,047 bytes,
people only at synthetic.invalid. Preview, apply, read-back and a replay through the mounted router over the migrated
schema, with a metering binding that fails on a statement over 100 KB of text, over 100 bound parameters or a bound
value over 2 MB.

| Figure | Value |
|---|---|
| Requests, preview + apply + read-back | **50** (1 preview, 1 open, 44 chunks, 1 seal, 3 reads) — target under 100 |
| Requests including the replay | 96 |
| Statements, preview + apply + read-back | 1,054 (gate reads included) |
| Statements in the largest request | 24 |
| Largest statement text | 1,431 bytes |
| Most bound parameters in a statement | 8 |
| Largest bound value | 77,924 bytes |
| Largest chunk request | 57,685 bytes |
| Manifest as the store takes it | 1,201 bytes (the audit's ~41 KB manifest carries more than the store's manifest holds) |
| Wall time | 2.4 to 4.5 s over runs (2.4 and 2.9 s on the 2026-11-27 re-run, D7745-p3) — **local SQLite on the build machine, not a D1 timing** |

At the default limit of 60 requests a minute per user, 50 requests fit in one minute; the client paces itself at one
request a second, so an apply takes about a minute and a replay as long again. A 429 leaves the run open and the
resent chunk writes once (tested). D1 itself is first met by #7760's production preview, which writes nothing.
