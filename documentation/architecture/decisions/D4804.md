## D4804 — Financial decisions are atomic: a losing decision leaves every dependent record unchanged (#4804)

- **Status:** built by S27, 2026-11-07 (#4804, Programs audit 1/7).
- **Number:** D4804 is this issue's number (D4106). Migration: none.
- **The invariant (from the issue):** a rejected or losing decision leaves every decision-dependent financial record unchanged. The winning status transition and all its dependent financial writes commit together. Notifications and audit lines follow the commit.

### 1. Referral partner commission terms

**The defect.** `PATCH /terms/:uid` read a draft, then ran one batch: the parent `UPDATE ... WHERE status = 'draft'`, then a `DELETE` of the terms' triggers and an `INSERT` per new trigger. Only the first statement named the status. A draft edit that was stale (a submit or an approval had committed after its read) lost the `UPDATE` and returned 409, but its `DELETE` and `INSERT`s had already replaced the commission triggers of submitted or approved terms.

**The fix.** `replaceDraftTriggers` is used by the edit. Its `DELETE` and every `INSERT` carry `EXISTS (SELECT 1 FROM referral_partner_terms WHERE id = ? AND status = 'draft')`.
- The parent `UPDATE` leaves the status as it found it. While the terms are still a draft, each dependent statement therefore sees a draft and runs.
- Once the terms are anything else, the `UPDATE` changes no row and the dependents do nothing. The route then answers 409 `terms_not_draft`, and nothing was written.
- The statements stay literal SQL; no query is assembled from pieces (`check-sql-prepare`).
- A new row's triggers (`POST /terms`) keep `saveTriggers`: nothing can have decided a row that did not exist a moment ago.

### 2. Refer & Earn acceptance rewards

**The defect.** `reviewSubmission` paid the reward first (`payReferralReward` → `grantCredits`, which commits its own ledger row) and then ran the guarded status `UPDATE`. A competing rejection that won the `UPDATE` left the referral rejected and the acceptance credits in the ledger, with the audit line and the notice already sent.

**The fix.** The reward is planned before any write and committed in the same batch as the move.
- `planGrant` (`creditGrants.ts`) does every read and refusal that `grantCredits` did and returns the one ledger `INSERT` and a `settle` step. `grantCredits` is now `planGrant` followed by running that statement and `settle`, so every other caller is unchanged.
- With `afterWin`, the `INSERT` carries `AND changes() = 1`, so it runs only if the statement just before it in the batch changed a row.
- `reviewSubmission` batches, in order: the status `UPDATE` (guarded on the status it read); the history row (`WHERE changes() = 1`, so it is written only when the `UPDATE` won); the reward `INSERT` (`WHERE changes() = 1`, so it is written only when the history row was). A losing decision therefore writes neither a history row nor credits.
- After the commit, `settle` writes the audit line and sends the notice. A losing decision does neither.
- **Refusals before any write, unchanged:** a rule HQ switched off or a referrer who never earns credits lets the move through unpaid; any other refusal answers 409 `reward_not_paid`. A source already paid reads `already_granted`.
- **A reward the batch could not settle** reports `paid: false, code: 'not_paid'` after the move committed. It cannot happen for a referral rule (they have no cap and no pair), and the UI already reads an unknown code as "No credits paid."
- **A batch that fails** answers 503 `decision_not_saved`, "The decision could not be saved. Nothing was changed. Try again." No database text reaches the UI.

### 3. Idempotency

- A request that loses to an identical one (the same move) finds the referral already moved: its `UPDATE` changes no row, so it writes no history and no credits, and answers 409 `bad_transition`.
- The same move requested again after it landed is an annotation (the status already equals the target), so it writes no ledger line.
- The ledger's unique `(user_id, kind, source_ref)` index remains the last guard.

### 4. Tests

`cloudflare-worker/test/programs_decision_atomicity_d4804.test.ts` (7 tests). A competing write lands between the route's read and its batch (the batch hook), so only the statements' own guards can stop the loser.
- **Terms:** an edit that loses to submit, and one that loses to approve, return 409 and change neither the terms nor any trigger, and record nothing. An edit that wins replaces the terms and all its triggers together, in turn.
- **Refer & Earn:** a conversion that loses to a rejection issues no reward, history or audit line. A conversion that wins writes one reward, one history row and one audit line, and a retry changes nothing. A conversion that loses to an identical one pays nothing a second time. A failed batch leaves no reward and answers in a sentence.
- 8 mutations, each caught.
- `referral_rewards_d965` now also asserts a failed move leaves no credits.
