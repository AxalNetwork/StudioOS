## D5338 — One restart-safe admission lease for shared upstream capacity behind `deps.admit` (#5338)

- **Status:** built 2026-11-10 (#5338). It changes nothing while `AI_PROVIDER_GATEWAY_OPENAI` is off, which it is in every environment. No gateway, credential, switch, secret, deploy or `wrangler.toml` change.
- **Number:** D5338 is the issue's number (D4106).
- **Builds on:** D4556 §8 (the `deps.admit` seam and the table of what shares what), D4870 (the publications caller), D1502 part 2 (the `AiGovernor` Durable Object), D844 (the hold and settlement), D264 (the Durable Object jurisdiction).
- **Migration:** none. **Route:** none. **Binding:** none new. The lease lives in the existing `AI_GOVERNOR` object class, which is already SQLite-backed in all three `wrangler.toml` tables (`v4-deck-gen`).

### Why

D4556's R2-08 audit asked for an admission check on shared upstream capacity, one that survives a restart. D4556 §8 left the seam and said #4594 hosts the restart-safe lease strategy, but #4594's contract has no such item. The publications caller (D4870) passed no `deps.admit`, so nothing counted gateway calls across tenants. Cloudflare's own 429 was the only backstop.

### 1. The design

There is one lease per AI Gateway, held in one `AiGovernor` object named `upstream:gateway:<slug>` (`services/upstreamLease.ts`, `durable-objects/ai-governor.ts`, the `/upstream/*` paths). One object per gateway, because the published request limit is per gateway. Inside it:

| What | Bound | Scope |
|---|---|---|
| Executions running at once | `modelConcurrent` (8) | per model on the gateway, every tenant and product |
| Of those, one tenant's | `tenantConcurrent` (2) | per tenant (`user:<id>`), per model |
| Upstream requests in a sliding 60 s | `windowRequests` (150) | the whole gateway, every model |
| Of those, one tenant's | `tenantWindowRequests` (50) | per tenant |

A tenant's share sits below the total on both axes. So a noisy tenant takes at most its share, and every other tenant still finds room. The product (the task: `publication` today) is recorded on each lease. It is not a separate quota, because the upstream does not care which product asks.

**One execution, one lease.** Admission is keyed by the run's execution id, the same id the D844 hold uses. A second admission under an id that still holds a lease waits.

**Retries and fallbacks count against the same lease.** The first request is counted when the lease is admitted. Before each retry, `runGatewayTextModel` calls the lease's `attempt`. That counts one more request in the window and renews the lease. A refused or unreadable `attempt` ends the run with the failure it already had. There is no second admission and no retry outside the window. The gateway path has no fallback to another gateway model (D4556 §3). The publications caller's fallback goes to Workers AI, which is a different upstream that this lease does not count (see §5). It runs only after the lease is released.

**Bounded waiting.** `upstreamAdmission` polls the object for up to `ADMIT_MAX_WAIT_MS` (5 s). It waits the time the object returns: 500 ms while every slot is held, or until the oldest request leaves the window. Then it refuses with `capacity_unavailable` and a `retryAfterSec`. A refusal makes no hold and no call.

### 2. What makes it restart-safe

- **Durable state.** Every lease and every counted request is in the object's storage (`state.storage`, key `upstream`). Each call reads that state, applies one pure step and writes it back. Nothing that decides admission lives in an instance field. A restart, an eviction or a deploy is a new instance over the same storage, and it sees every outstanding lease. Calls are applied one at a time: the storage input gate does this, and so does a promise chain that orders the read-modify-writes but holds no state.
- **Release by token.** Each admission gets a fresh random token. Release and attempt name the token, never the execution or the tenant. A lease that expired and was reaped, or one already released, matches no live lease, so its token frees nothing. A late or duplicate release therefore cannot free a slot that a newer execution holds.
- **Expiry longer than the run.** A lease lives `LEASE_TTL_MS` (180 s) from its last admission or attempt. That is longer than the gateway run's own ceiling: `GATEWAY_MAX_ATTEMPTS × GATEWAY_ATTEMPT_TIMEOUT_MS + GATEWAY_RETRY_BUDGET_MS + 30 s` = 124 s, the metered run's timeout, and a test holds the inequality. So a lease can expire only under a run that has already given up or died. Expired leases are reaped on every access, so no alarm is needed.
- **Completion unknown keeps the slot.** The run tells `release` how it ended: `done`, `none` (refused before any provider ran, such as a hold refusal or the input guard) or `unknown` (a timeout or a thrown run, where the provider may still be working). With `unknown` the lease is marked and keeps its slot until its own expiry, instead of handing the slot to new work while the old call may still be running upstream. The run's row still says `completion: 'unknown'` with `reconcile: 'gateway_log'` (D4556), and nothing is charged.
- **A missing binding refuses.** Without `AI_GOVERNOR`, `upstreamAdmission` answers `{ ok: false, reason: 'no_binding' }`, and the run is `capacity_unavailable` with no call. An object that answers with an error, or throws, is no admission either: the seam reads a throw as a refusal. There is no in-memory fallback. `governorFor`'s in-isolate fallback for deck steps is untouched and is never consulted here.
- **Unreadable state.** A stored value that does not parse reads as an empty state rather than a crash. This can only free capacity, and only if the stored shape is broken. A future change to the shape must bump `v` and say what happens to leases in flight.

### 3. What stays separate

- **Spending authority** is D844's hold and settlement in D1, and only those. The lease is admitted before the hold, refuses before it, and never stands in for it. One execution holds and settles once (`exec:<executionId>:<component>`), whatever the retries.
- **Tenant fairness for deck steps** stays the per-account governor (`services/decks/aiGovernor.ts`, `account:<n>`). It is still in memory, as D1502 designed it. That is a throttle on one account's own steps, not on shared capacity, so this decision does not change it.
- **No second router, queue or ledger.** The lease is a counter and a set of leases inside the existing governor class. It routes nothing and queues nothing: a waiting caller polls with a bound.

### 4. The limits used, with their source and date read

| Limit | Value used | Source | Read |
|---|---|---|---|
| Unified Billing request rate | 200 requests per 60 seconds per gateway (429, code 2018); the lease admits 150 | https://developers.cloudflare.com/ai-gateway/reference/limits/ (through the Cloudflare docs connector; also `test/fixtures/ai_gateway_4556.json`, read 2026-11-06) | 2026-11-10 |
| `openai/gpt-5-mini` concurrency or rate | none published on the model's catalogue page (context 128,000 tokens, ZDR yes, rates only) | https://developers.cloudflare.com/ai/models/openai/gpt-5-mini/ | 2026-11-10 |
| Spend limits | eventually consistent, so a burst can briefly exceed them; not used as admission | https://developers.cloudflare.com/ai-gateway/features/spend-limits/ (updated 2026-11-04) | 2026-11-10 |

A published limit is not a capacity promise. The window keeps a 25% margin below Cloudflare's figure, and the 429 stays the backstop. The concurrency figures (8 per model, 2 per tenant) and the tenant window (50) are Axal's own policy, not a published or measured number. They are constants in `UPSTREAM_LIMITS`, to be revised from what #4573 and #4559 measure.

### 5. What it does not cover

- **The other inference paths in D4556 §8:** `aiRouter.run()` and its guard calls, the Advisor, deck runs and image tools, agent runs, live transcription and document conversion. They all share Workers AI account limits, and none of them calls this lease. Bringing them under it needs each path to pass through an admission check. That is not done here, and the D4556 §8 table still says what each one shares.
- **Other Workers on the same account.** A branch Worker has its own Durable Object namespace, so its lease is separate even if it pointed at the same gateway. The lease counts this Worker's calls only.
- **Token or cost throughput.** It counts requests and concurrency, not tokens per minute: no such limit is published for this path.
- **Cross-region exactness.** One object per gateway is one point of coordination. Its location and latency are Cloudflare's, and admission costs one round trip to it.
- **Reconciliation of unknown completions** from the gateway log is still not built (D4556 §9).

- `cloudflare-worker/src/services/upstreamLease.ts`: the pure lease steps, the limits and `upstreamAdmission`.
