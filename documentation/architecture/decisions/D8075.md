## D8075 — Advisory file-ownership check (#8075)

The hosted `ownership` PR check reads the pull request and its entire changed-file
list, then the open issues labelled `state:in-progress` or `state:review`. It reads
path-shaped tokens in their task-form `### Files owned` / `## Owned files`
sections and single-line `Files owned:` / `Owned files:` labels (optionally bold).
An inline label applies only to that line; it does not open a new section or
reset a surrounding exclusion list. Pull-request rows from the issues endpoint
are excluded before issue validation and counting. Issue and file reads are paginated, bounded and cached
in memory for this invocation only. A new run always reads fresh ownership.
The event's frozen head is checked before and after pagination; a changed head
or base makes the result unknown. The draft-workflow registry allows this bounded
read-only check to give coordination feedback on draft PRs as required by #8075.

The task number comes first from `agent/<agent-or-slot>/<issue>-...` or a tagged
`claude/<name>-<issue>` branch (an optional letter identifies a part). A closing
or part-of link naming a different task makes even a tagged branch unknown;
dependency references remain incidental. A numeric Claude suffix is treated as
an issue tag by this convention, not verified against a separate branch ledger.
Without
that branch identity, a single explicit closing/part-of body link disambiguates
incidental title references when the title includes that task or contains no
task reference. Conflicting title/link evidence, multiple closing links or
multiple fallback references are unknown. Otherwise a single title reference,
then a single body reference, supplies the task.
The branch's task alone is exempt: mentioning another issue as a dependency does
not release that issue's ownership. An unlinked PR skips with a note. This is
an advisory coordination aid, not a reservation or an authorization grant.

Changed paths are matched directly against the declared POSIX patterns, including
new and deleted files and both sides of renames. Directory paths cover descendants.
Supported glob syntax is `*`, `**`, `?`, character classes and bounded flat brace
alternatives. Paths are repository-relative; traversal, URLs, shell expressions,
extglobs, numeric brace ranges and nested brace expansion are rejected. Issue
placeholders `<issue>` and `<this issue>` are replaced with that issue's number.
Explicit `Not`, `Except` and `Excluding` clauses and fenced examples do not claim
files. A standalone exclusion marker or nested exclusion heading applies to the
following list until an explicit `Owned:` / `Also owned:` marker or another
ownership heading; its later bullets never create claims. Bare filenames/paths
and inline-code paths are accepted. Prose such as
“the migration” or “its tests” does not identify a path and is never inferred.
Path-shaped prose such as `README/generated` can still be tokenized; the parser
does not establish that every token names an actual file. Full backticked paths
are the preferred declaration format. This heuristic is an advisory boundary,
not a canonical ownership or permission parser.
Five full public task snapshots (#8070, #8071, #8072, #8074, #8075) pin that boundary.

A bare filename is a confirmed match only at the repository root. If it equals
the basename of a changed path elsewhere, the report shows an **unconfirmed
name-only match**, including rename sources. It never infers directory ownership
from that name and never counts it as a confirmed overlap. A concrete matching
path suppresses redundant name-only uncertainty for the same issue/file.
Patterns whose first directory segment consists only of wildcards, such as
`**/*`, `*/*` and `**/*.ts`, likewise produce **unscoped broad pattern** rows
rather than asserting ownership of every matching file. Other patterns still
need declaration-scope review; brace/class-led broad patterns and bare filename
globs are not reclassified by these literal-name/leading-wildcard rules. These
checks are not a general breadth validator.
Unconfirmed evidence cannot produce a clear result and must be coordinated.

The summary reports both issue numbers, each overlapping changed path and its
patterns, with duplicate issues/paths suppressed. Oversized inventories, malformed
responses, missing file-list coverage and failed reads are `unknown`, never
“no overlap”. Summary cells encode HTML delimiters, Markdown link/format markers,
mentions, pipes and control characters as literal text, using the existing
prOverlap cell-encoding convention without its runtime dependency graph. This is
literal Markdown output, not a general-purpose HTML sanitizer. Request errors and issue
bodies are not logged. API access is GET-only to the fixed GitHub repository
endpoint, with a per-request timeout and redirects refused.

`LANDING_OWNERSHIP_CHECK` unset, empty or `advisory` reports without failing.
Any other nonempty value enforces: overlap, unconfirmed and unknown exit 1; clear and an
explicit no-task skip exit 0. The owner controls activation and required-check
settings separately. This PR changes neither settings nor production resources.

The workflow has only contents/issues/pull-request read permissions, no secrets,
no identity token, no persisted checkout credential and no shared Actions cache.
Candidate parser tests always run in a separate candidate checkout. After
introduction the report executes the trusted base's checker. Its first
PR must exercise the new checker, so a base without the file uses that head checkout
with advisory mode forced. This bootstrap is not enforcement evidence. Changing
the workflow itself can still change an advisory result; protected trusted
workflow policy and the landing bot's consumption are outside this task.

Integration: #5580 retains WorkIntent, reservations and conflict-graph ownership;
no such files are modified. #6478 may consume the named check and its structured
status later; adding that policy is a separate change. S14 reviews the handoff.

The state scope deliberately follows #8075's two labels. WorkIntent also treats
`state:blocked` as claimed; this checker does not evaluate those claims. The
report always states that coverage limit. Simply adding every blocked issue
would let planned, unstarted work reserve files indefinitely. Before enforcement
or treating this result as claim clearance in #6478, the owner must review an
integration with #5580's derived active-claim predicate (claim ref/STATUS), not
create a second claim ledger. A required task-link check must also accompany
enforcement: the deliberate no-task skip is not permission to land an unlinked
PR. The owner must also settle a single-task convention for multi-issue PRs and
whether common-name uncertainty (for example README.md) should block or annotate
in the eventual policy; this advisory implementation currently exits 1 for it
when explicitly enforced. Neither decision nor activation is implemented here.

Rollback: leave the repository variable unset/advisory to stop enforcement, or
revert this workflow and checker. No migration, deployment, production D1 write,
reservation or permission mutation needs undoing. An owner verifies any later
activation; a successful advisory check alone does not authorize file edits.
