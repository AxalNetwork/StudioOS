## D1364 — Keep deployed asset generations for 72 hours, within a safe file cap

Issue #3591. S20, s31 Codex. No migration. This follows the stale-chunk incident
and reload recovery in #3589. The retention guarantee concerns the hashed assets
served by the Worker on axal.vc and app.axal.vc; the owner merges and deploys.

### Policy and deployment clock

The planner keeps every complete generation deployed in the previous 72 hours,
including the boundary, plus a floor of three builds including the current
candidate (the new build and two prior deployments). After a successful deploy
those are the latest three deployed builds. The window also keeps the build
that was serving immediately before the first in-window deployment. A
long-lived build may have first shipped days earlier; tabs opened just before
it was superseded still need its chunks for 72 hours. The next generation’s
deployment time bounds that last-served window.
Consecutive identical content updates its deployment time without taking another
slot; an unchanged rebuild preserves its existing deployment timestamp until
its next successful deploy. A build candidate is always protected in the plan.
Old local/failed candidates do not consume deployed-history slots. `ASSET_RETAIN_BUILDS` can raise the production
minimum but cannot reduce it below three.

The private, cached `.asset-retention.json` is version 2. `ts` remains build
time; `deployedAt` is recorded only by `scripts/record-asset-deploy.mjs` after
a successful upload. The timestamp step must precede caching the deployed tree.
Local `npm run deploy` uses the same stamp before its live-check postdeploy.
Neither building nor previewing is labelled a successful deployment. The
production restore flag identifies a tree cached only after a successful
publish. An unstamped v2 entry in that trusted cache receives the same explicit
unknown-time, one-time grace as a legacy entry; its deployedAt remains null.
This recovers the caches saved before the CI hook landed, without deleting
live chunks or blocking the deploy that will finally record its real time.
Local candidates remain unserved and never receive this cache-only recovery.

Legacy entries have unknown deployment times. They retain `deployedAt: null`
and get a one-time `firstSeenAt` grace period at upgrade; subsequent builds keep
that first observation rather than restarting it. This avoids mislabelling a
build timestamp as a deployment timestamp and avoids immediately dropping the
previously saved tree. The existing no-ledger and explicit previous-shell seed
safeguards remain; a fresh cache restarts retention with a visible warning.

### Capacity, checked 2026-10-28

[Cloudflare's current limits](https://developers.cloudflare.com/workers/platform/limits/)
allow 20,000 static files on Free and 100,000 on Paid per Worker version, with
Wrangler 4.34.0+ needed for the larger limit. The default asset cap is **18,000**,
conservatively below the smaller plan limit without assuming an account upgrade.
The wrapper separately counts the full output against **20,000**, including
non-asset output. It reserves space for the final stamp. No plan setting changes.

The cap counts unique files, including shared chunks once. It evicts the oldest
optional generation as a whole; it never leaves a generation partially retained.
The newest generation, minimum deployed floor and explicit previous shell are
protected. If those alone exceed the cap, the build fails before upload; it
does not silently sacrifice the current app. On any build/prerender/cap
failure the wrapper restores the full pre-build output and ledger from its
private temporary snapshot, so a local retry cannot forget the last deployment.
A cap warning explicitly says the 72-hour window was shortened. Very frequent unique builds can therefore shorten
the window; 72 hours is guaranteed only within the cap and with continuous cache
restoration. The cap makes this resource boundary explicit rather than promising
unbounded retention.

[GitHub's cache policy](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#usage-limits-and-eviction-policy)
states a default of 10 GB per repository, with seven-day unused-cache eviction
and LRU size eviction. Administrators can raise the limit at additional cost; this PR
changes no cache or billing setting.

Public [cache usage](https://api.github.com/repos/AxalNetwork/StudioOS/actions/cache/usage) and
[cache entry metadata](https://api.github.com/repos/AxalNetwork/StudioOS/actions/caches?per_page=100)
read on 2026-10-28 showed 10,718,911,611 cache bytes over 41
entries (about 9.98 GiB); 18 `spa-assets-` snapshots totalled 234,724,060 bytes.
The newest was 13,303,767 bytes. At the issue's roughly 2,034-file baseline,
a linear 18,000-file projection is roughly 118 MB per compressed snapshot,
not a measured compression guarantee. The latest snapshot carries the whole
rolling union; it does not need every old cache entry to survive. Existing
per-run keys and successful-deploy-only saves continue. Older snapshots and
other dependency caches compete under GitHub's LRU policy. A lost latest cache
cannot recreate unavailable assets and is still reported as retention restarted.

### Scope and verification

The optional `advancedChunks` experiment is not part of this change. The time
policy works with today's chunk graph, without changing bundle partitioning or
the Vite configuration also owned by the Safari task #3592.

Unit tests exercise inside/outside/boundary timestamps and quiet-site
supersession, the minimum on a quiet
site, deployment-time ordering, oldest-first whole-build eviction, shared chunk
reference counts, over-cap protected output, a one-time legacy grace, undeployed
candidates, actual deploy time versus earlier build time, identical redeployment,
invalid inputs and the real stamp CLI. Historical tests explicitly request a
count-only window to retain their old D183/D252/D529 regression coverage. New
assertions and representative implementation faults are mutation-checked.
The real wrapper’s cap-failure fixtures use copied policy constants of 16
assets / 32 total files to avoid tens of thousands of temp writes; a policy
assertion independently pins production’s 18,000 / 20,000 defaults.

The production deploy workflow records the successful deployment timestamp
before saving the served assets. Its ordering test rejects a missing, reordered
or softened hook. The separate smoke-check job from #3590 runs after the
cache save, so a failed probe cannot discard the tree already deployed.
Local and CI command outcomes are recorded in the PR. No production deployment,
D1 read/write, cache deletion or setting change was performed by this session.

**UNVERIFIED until the owner's deploy check:** restore continuity on a real
deploy, the recorded successful-deploy timestamp in its saved ledger, an older
open tab's lazy imports on both hosts, and cap-pressure warning visibility. The
owner checks deployment logs after merging. A missing or evicted pre-upgrade
chunk cannot be restored retroactively by this change.
