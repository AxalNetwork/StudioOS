## D1358 — Record a Session: a meeting is captured by the platform, never by the browser

- **Status:** decided and built by S21 for S1, 2026-10-28, at the owner's request ("Fix and Implement Meeting Session Creation, Recording, and Bot-Based Capture").
- **Migration:** none.
- **Builds on:**
  - D684 and D685: calls, attach;
  - D871: Meet from Calendar;
  - D886: Eadwyn AI, the meeting bot;
  - D1346: Create the meeting for me, bot availability.

### 1. The root cause

In Record a Session › Call, Zoom, Google Meet and Microsoft Teams were the `video` channel. `RecordLightbox.submit` handed every `video` Start to the in-browser recorder (`handsOver`) unless Eadwyn AI was sent:
- **On a computer,** Start asked the member to share the call's tab.
- **On a phone,** the device microphone recorded.
- **When the bot was available,** the footer still offered "Record this device".

The bot is not deployed. `MEETING_BOT_DEPLOY_ENABLED` is unset, so `GET /meetings/bot` is false on every platform. So **every** Zoom, Meet and Teams start was a browser recording. The member was told it "records the call's audio", which is not a platform capture at all.

### 2. The rule

**A meeting (Zoom, Google Meet, Teams) is captured by the platform or not at all.** One pure decision, `callCapture` in `recordSetup.js`, picks the path:

| Path | When | Start reads |
|---|---|---|
| `bot` | Eadwyn AI is deployed for the link's platform and enabled for the member (`GET /meetings/bot`) | Send Eadwyn AI |
| `import` | No bot; a valid Zoom or Meet link; that provider connected | Save for import after the call |
| `none` | Anything else: no link, Teams without the bot, not connected, connections unreadable | Start is off, with the reason |

- **Never the browser.** "Record this device" is gone for a meeting.
- **The browser recorder stays for its two honest uses:**
  - In person;
  - a call on this phone's speaker (WhatsApp, Telegram, Signal, "This phone, on speaker"). The device microphone hears the speaker there, which is what the member chose.
- **The mode note** says "This device's microphone is not used." It no longer changes with whether a tab can be shared.
- **The device options are hidden for a meeting.** The live and final transcript pickers, language and estimate are replaced by what the capture will do.

### 3. Import after the call (the `import` path)

- **Zoom.** `POST /founder/validate/interviews/:id/meetings` with `{ attach: { join_url }, consent }` and **no `session_id`** (new: `attachHostedZoom`). In order:
  1. consent;
  2. Zoom available here;
  3. the member's Zoom connection;
  4. `verifyHostedMeeting`: the connected account hosts this meeting.

  Then it opens its own `video` session (`submitted_via = 'zoom'`, draft) and stores the ref with `ends_at` NULL. Zoom's `recording.transcript_completed` or `recording.completed` webhook imports it, as for a scheduled call. `meeting.ended` now gives such a ref its end (`markEnded`), so the sweep finds it if the transcript event is lost. A link pasted beside a recording (D685) still waits for Stop. A refusal deletes the empty session.
- **Google Meet.** The existing D871 path (`attachCalendarMeet`): a call organised by the connected Google account, found in its Calendar, imported by the sweep after its end.
- **Interviews.** When the dialog was not opened on an interview, the Save creates one first, booked, as "Schedule the call for later" does. If the save is refused, that interview is removed.
- **Retries.** A retried Save (a double press, a lost reply) returns the first attach with `200` and `existing: true` and the same session. That holds only for the same member, interview and call. Another member or interview still gets `409 meeting_link_reused`.

### 4. `GET /founder/validate/meetings/capabilities`

Per provider, for this member: `available`, `connected`, `can_create_meeting`, `can_join_as_bot`, `can_capture_realtime_audio`, `can_retrieve_transcript`, `can_retrieve_recording`, `capture_modes` (`bot`, `post_meeting_import`), `reason` and `notes`. Every flag is read from configuration and the member's own connection; none is assumed:
- **Zoom** says Realtime Media Streams (RTMS) are not configured.
- **Meet without the transcript scope** cannot import.
- **Teams** has no import (no Microsoft Graph connection) and only the bot, where deployed.

No token, link or secret is in the reply. The client is `channelsApi.meetingCapabilities()`. The dialog keeps reading `/meetings/bot` and the connections it already reads, so the route is for any surface that needs the full table.

### 5. What is still not true, and is not claimed

- **Eadwyn AI has not joined a live call.** The bot code is on `main` (D886), but it is not deployed. The owner's first deployment (`PRODUCTION.md`, "Owner-only first deployment") and the live check on Zoom, Meet and Teams (#2581, #2582, #2583, #2587) come first.
- **No live Zoom or Meet import was run from this change.** Every provider request in the tests is a mocked `fetch`.
- **Teams:** no Graph app, no transcript import. After the call the member uploads the recording or pastes the transcript.
- **Zoom RTMS:** not built. It needs an RTMS-enabled Zoom app and a media consumer outside the Worker.
