## D587 — Stripe charges become verified revenue entries

**A founder imports their own connected Stripe account's succeeded charges
into the Spin-Out Lab revenue ledger, one entry per charge, and those are
the only entries the Worker marks `verified`.** Slot S08, issue #1214,
2026-10-06, from the owner's answer on #1009 ("Stripe charge-level sync";
D363 named it "the step past this line"). Migration 400.

### What was true

- Migration 311 reserved `source = 'stripe'`, `source_ref` and
  `verification = 'verified'` on `revenue_entries` for a charge sync, and
  `verificationFor` already mapped `stripe` to `verified`.
- Nothing wrote them. The existing Stripe import (`/api/progress/metrics/…/
  import-stripe`) records MRR and customer counts, not charges. So the
  Revenue page's Verified KPI and mix line read Not recorded.

### What changed

- **`integrations/providers/stripe.ts` `listLedgerChargesForUser`.**
  - It reads the caller's OWN active Stripe integration and lists
    `/v1/charges`, read-only. It goes through the existing paged `listAll`,
    capped at 1,000 charges, newest first.
  - It keeps only succeeded, paid charges.
  - It answers `not_connected` or `read_failed` rather than an empty list.
- **`POST /api/revenue/projects/:projectId/entries/import-stripe`.**
  - It sits behind the revenue router's write gate, and further, only the
    startup's own founder may run it. The charges come from the caller's
    account, so an admin's or a partner's account is never written into a
    founder's ledger.
  - It returns `charges`, `inserted`, `already_imported`, `refunded`,
    `rejected` (charge id, code and our sentence per row), `capped` and
    `import_batch`.
  - Not connected is a 400 `stripe_not_connected`. A failed read is a 502
    `stripe_read_failed` with our sentence. Neither is ever "0 imported".
- **`services/revenueLedger.ts` `chargeToEntry`** (pure):
  - The amount is net of refunds, and a fully refunded charge writes nothing.
  - The date is the charge's own UTC date.
  - A non-USD charge is refused with `currency_unsupported`, as the CSV
    import refuses one.
  - The type is `recurring` when the charge paid an invoice, else
    `one_time`. That is a reading of Stripe's record, not something Stripe
    states, so the type stays editable.
- **Migration 400 `uq_revenue_entries_stripe_charge`.** It is a partial
  unique index on `(project_id, source_ref) WHERE source = 'stripe'`. The
  insert is `ON CONFLICT … DO NOTHING`, so a second import, or two at once,
  writes each charge once. Manual and CSV rows are untouched by it.
  `ensureRevenueEntriesSchema` heals the same index (D235).
- **The PATCH lock.** A synced entry's amount, date and customer are what
  Stripe reported, which is what `verified` means. A PATCH that changes any
  of them is refused with 409 `synced_entry_locked`. The type, notes and
  proof may change, and attaching proof leaves it `verified`.
- **The ledger (`RevenueLedger.jsx`).**
  - "Import charges from Stripe" sits beside Import CSV. Its answer is shown
    as one sentence (`lib/revenueLedger.js` `stripeImportLine`), with each
    refused charge listed. A refusal is shown as said.
  - Verified now reads the real share, and the mix line names the verified
    amount, once a Stripe entry exists. Before that it reads Not recorded.
  - When the ledger cannot be read, the Verified KPI now says Unreadable. It
    used to say Not recorded.

### Personal data

A charge carries the founder's customers' names, emails, addresses and
cards. None of it is read into the provider's charge shape or stored. The
entry's `customer` is the Stripe customer id (`cus_…`), or "Stripe charge"
when the charge names none, and `notes` is empty. Storing a name would need
the owner.

### Not built

- **Paging past 1,000 charges.** Charges older than the newest thousand are
  not read. The answer's `capped` says so, and the ledger prints it.
- **A scheduled sync.** The import runs when the founder presses it.
- **Non-USD ledgers.**
