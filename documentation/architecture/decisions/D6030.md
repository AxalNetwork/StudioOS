## D6030 — Solution design's features: one evidence cell, named evidence filters, Link evidence (#6030)

Board BD7 of the Build v2 canvas (`design/incoming/Build v2 Page.dc.html`, frame BU07), from #4846's export. The aim: the features list shows why each feature exists, and a feature with no evidence can be fixed in one step.

### What the read sends

The read is `routes/cycle_build.ts`, through `solution()`, `featureRow` and `FEATURE_LIST`.

- **One evidence cell.** The table's columns are Feature, Evidence link, Impact and Effort, as the canvas draws them. Before, it had separate Pain theme and Hypothesis columns.
  - **A linked feature.** Its `evidence` cell is `{ text, links }`. There is one link per record the feature cites:
    - `Pain · <theme>` → `/validate/problem-discovery/<pain_group_id>?project=<id>`;
    - `Hypothesis · <claim>` → `/validate/experiments/<hypothesis_id>?project=<id>`.
  - **A feature with neither.** Its cell reads `{ text: 'No evidence link', tone: 'warn' }`.
- **The evidence filter names its link kind.** The filter is `evidence`, labelled Evidence link, and replaces the `linked` filter. Each option carries its `count` over the whole list.

  | Option | Selects |
  |---|---|
  | Pain linked | a feature linked to a pain theme, with or without a hypothesis |
  | Hypothesis linked | a feature whose only evidence is a hypothesis |
  | No evidence link | a feature linked to neither |

  **The three are exclusive, and their counts add up to the total, as the canvas's 4 + 1 + 1 = 6 does.** A row's filter key holds one value. So a feature linked to both a pain theme and a hypothesis is Pain linked, and its cell shows both links. A feature linked only to a hypothesis is never shown as unlinked: not in the cell, the filter or the counts.
- **`keys.linked` stays.** Old `?filter=linked:yes` deep links still answer, and the card's Linked and Unlinked chart is unchanged.
- **Plan marks per row**, in the row's `keys`:
  - `scope` is `core`, `out`, or null;
  - `must_have` is yes when the scope is `core`, the MVP's must-have set;
  - `on_roadmap` is yes when a `roadmap_okrs` row names the feature (`feature_id`, migration 461).

  BD7's four-column frame draws none of the three, so they are sent but not drawn.

### Read cost

The three counts are SUMs in the module's existing aggregate, so they add no statement. `on_roadmap` is one correlated `EXISTS` per row on the indexed `(project_id, feature_id)`, inside the page's own statement. This is the issue's allowance of one extra aggregate. The SQL page and the in-memory page still agree, and `build_bounded_reads_4603.test.ts` compares them, now including the three evidence filters.

### The frontend

- **`cellView` and `Cell`** draw a cell's `links` as separate links. On a row that is itself a link, they read as plain text, so there is never a link inside a link.
- **Filter options** print their count ("Pain linked · 4"), on the desktop and on a phone (`optionLabel`).
- **Link evidence.** A row whose `keys.evidence` is `none` offers "Link evidence" in place of Edit (`linkEvidenceAction`).
  - It opens the same Edit form, which saves through the existing `PATCH`. The route passes `editingFocus: 'pain_group_id'`, and `FormLightbox` moves focus to that field once its options are read. The hypothesis field follows it.
  - On a phone, the row's tap is the same action. The evidence reads as the row's description, and No evidence link is its pill.
