## D843 — One attributable `api_usage_events` row per MCP tool call and API-key request

- **Status:** decided by S1 for the owner, 2026-10-21 (#2465; part of #2463). Built by S08.
- **Basis:** `origin/main` at `56c2498983`. Paths are relative to `cloudflare-worker/` unless they say otherwise.
- **Migration:** 524.

### What is built

1. **Migration 524, `api_usage_events`.** One row per call. The columns:

   | Column | What it holds |
   | --- | --- |
   | `execution_id` | A random UUID, `UNIQUE`. The id the call's result hands back in `_meta.execution_id`. |
   | `user_id` | The user the call is attributed to: the grant's or the key's owner, even when the account check refuses the call. |
   | `api_key_uid` | The member's API key (#2464), when the call came with one. NULL until keys exist. |
   | `grant_id` | The OAuth grant, when the call came through one. A call has at most one of `api_key_uid` and `grant_id`. |
   | `client` | The OAuth client's display name. |
   | `company_id` | The company (`projects.id`) the call named, once checked. |
   | `surface` | `mcp`, or `api` for a key request outside `/mcp`. |
   | `operation` | The tool's name. |
   | `outcome` | `ok`, `refused`, `error` or `rate_limited`: the same four words as the `activity_logs` line. |
   | `error_category` | One of the fixed list below; NULL when the outcome is `ok`. |
   | `duration_ms` | Whole milliseconds from the call's start to its row. |
   | `reservation_uid`, `held_microusd`, `charged_microusd` | The hold and the charge on the AI token ledger, from metering (#2466). |
   | `model`, `provider`, `connector` | What the call ran on, from metering (#2466), the providers (#2474) or a connector (#2469). |
   | `created_at` | When the row was written. |

   **Indexes:** `(user_id, created_at)`, `(api_key_uid, created_at)`, `(grant_id, created_at)` and `(user_id, operation, created_at)`. `execution_id` is `UNIQUE`, which already indexes it, so the issue's `(execution_id)` index is that one.
2. **`src/services/apiUsage.ts`:**
   - `newExecutionId()` returns a random UUID.
   - `recordUsage(env, row)` writes one bound INSERT. It never throws: a failed write logs a warning naming the execution id and the error's message only, returns false, and the call still answers.
   - `USAGE_ERROR_CATEGORIES` is the fixed list, exported for the reports (#2471) and the UI (#2481).
3. **`callTool` (`src/mcp/server.ts`).**
   - It mints an `execution_id` per call and times it.
   - It writes one row for every outcome: ok, refused, error and rate_limited.
   - Every result, success or error, carries `_meta: { execution_id }`.
   - The `activity_logs` line is kept. The usage row is written first, so a failing activity line cannot skip it, and the `UNIQUE` execution id keeps a second row for the same call out.

### The error categories

The list is fixed: `auth`, `scope`, `company`, `rate_limited`, `insufficient_tokens`, `timeout`, `provider`, `invalid_input` and `internal`. A new reason is a new decision. `callTool` sets them as follows:

| Where the call stopped | Category |
| --- | --- |
| The account check (`grantUser`): ended account, deletion request, signed out everywhere | `auth` |
| The scope check | `scope` |
| The company check (`grantCompany`), or a refusal from inside a tool | `company` |
| The grant's per-minute limit | `rate_limited` |
| A tool's `ToolError`, by status: 401 | `auth` |
| 402 (the plan does not include it) | `scope` |
| 403 or 404 (the venture or project) | `company` |
| 408 or 504 | `timeout` |
| 429 | `rate_limited` |
| 500 and above | `internal` |
| any other 4xx | `invalid_input` |
| Any other exception | `internal` |

`insufficient_tokens` and `provider` are set by metering (#2466) and the providers (#2474); nothing on `/mcp` raises them yet. A row whose outcome is not `ok` and which names no category is written as `internal`; an `ok` row never has one.

### What a row never holds

- No argument, no result and no error text. `operation` is the tool's name and `client` the client's display name.
- No secret, key or token. `api_key_uid` is the key's public uid, never the key.

### Unknown is NULL

`reservation_uid`, `held_microusd`, `charged_microusd`, `model`, `provider` and `connector` are NULL until something supplies them. NULL means "not metered", and a report must not count it as nothing spent. `recordUsage` turns a missing, negative or non-finite amount into NULL, never 0, and rounds a real amount to whole micro-USD.

### Not built here

- **No read route.** The reports task (#2471) adds the reads, with tenant checks.
- **No metering.** #2466 passes `reservation_uid` and the amounts.
- **No key authentication.** #2470 lets `/mcp` accept member keys. Until then `api_key_uid` is read from the principal (`props.apiKeyUid`) when present, which no principal sets yet.
- **`schema_baseline.sql` is unchanged.** Its header says it is regenerated from production and not hand-edited, and no migration since 2026-09-08 has touched it. The table is in migration 524 alone.
- **The plan document.** `documentation/architecture/MCP_API_PLATFORM.md` lands with #2464's PR and was not on `main` when this was built. Its §3 should carry the column list and the category list above.

### Tests

`test/api_usage_events_d843.test.ts` (new, 6). It drives the real `callTool` with stub tools against node:sqlite holding `users`, `projects` and `activity_logs` from the baseline plus migration 524.

1. An `ok` call writes one row with the execution id, duration, operation and outcome, and `_meta` quotes the same id. The `activity_logs` line is kept.
2. The scope, company, account and tool refusals each write one row with their category. An ended account is still attributed to the grant's user.
3. An `error` and a `rate_limited` call each write one row with their own execution id.
4. No argument or result text is stored, and the money fields are NULL, never 0.
5. A failed usage write does not fail the call: it still answers, with its execution id, and warns.
6. An API key on the principal is recorded, and the category list matches the migration's `CHECK`.

16 mutations were tried, removing or changing one guard each. 15 were caught. The one that survived drops the explicit `'internal'` category on the error path, which behaves the same because `recordUsage` gives any non-`ok` row without a category `internal`.

### Rollback

Revert the PR. Migration 524 is additive; with the code reverted, nothing writes or reads the table.
