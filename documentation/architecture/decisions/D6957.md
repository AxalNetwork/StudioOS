## D6957 — Sign in with Apple for the web: start, form_post return, account resolution and configuration (#6957)

- **Status:** built 2026-11-16, switched off until configured. The Worker, its migration, the client wrapper and the Settings link are in this change. The `/login` button is #6958's. The staging run in Safari on iPhone waits on the Apple Developer steps below.
- **Builds on:** the Google sign-in (Task #51, D722): the same session primitives, the same destination rule (`sanitizeRedirect`, now exported from `routes/auth_google.ts`), the same "authoritative for the address" rule, and the same link-from-Settings path for an address the provider cannot vouch for.

### The flow

1. `/login` asks `GET /api/auth/apple/config`. It answers `{configured}` from env alone, and the page shows the Apple button only when it is true. A deployment without the four settings below never shows a button that cannot work.
2. The button navigates the tab to `GET /api/auth/apple/start?redirect=…&lane=…` (or asks for it with `Accept: application/json` and navigates to the `url` it returns). `/start`:
   - mints a random nonce;
   - sets it in `studioos_apple_state`: HttpOnly, Secure, `SameSite=None`, path `/api/auth/apple`, ten minutes;
   - sends Apple an HMAC-signed state (the nonce, the time, `signin` or `link`, the user id for a link, the sanitized destination, the lane);
   - sends Apple `nonce = base64url(SHA-256(nonce))`, `response_type=code id_token`, `response_mode=form_post` and `scope=name email`.
3. Apple POSTs to `POST /api/auth/apple/callback` with `code`, `id_token`, `state` and, the first time only, `user` (the name). Before anything is written, the callback checks:
   - the state's signature and age;
   - that the cookie's nonce equals the state's;
   - the posted id_token: RS256 against Apple's keys, issuer `https://appleid.apple.com`, audience the Services ID, the clock, and the hashed nonce;
   - the code exchange at Apple's token endpoint, with a client secret (an ES256 JWT, five minutes) signed with the private key;
   - that the token endpoint's id_token passes the same checks and names the same subject (and the same nonce when it carries one).
4. The answer is a 303:
   - to the original destination with `?apple=ok`;
   - to `/onboarding` for a new account with no explicit destination;
   - or to `/login?apple_error=<code>&next=<destination>` (Settings for a link), where the chooser shows our own sentence with Email and Google still available.

**Why `SameSite=None`.** Apple's return is a cross-site POST. A Lax cookie is not sent on it, which is how an Apple sign-in fails in Safari with a "bad state". The session cookie is not sent either, so a link carries its user id in the signed state, as Google's does. The callback is exempt from the cookie-CSRF check (`middleware/csrf.ts`), because the state signature, the cookie and the id_token nonce bind it instead.

**Replay.** Every callback clears the nonce cookie, so a replayed POST in the same browser has no nonce to match. A POST taken to another browser never had one. Apple's code is single-use as well.

### Which account

| Case | Result |
| --- | --- |
| The Apple subject is already linked | Sign in. A repeat return with no name and no email (Apple sends the name only once) works. |
| An Axal VC account has the address, it is verified here, and Apple hosts the address | Link the Apple ID, then sign in. |
| An Axal VC account has the address, unverified here | `link_blocked_unverified`. |
| The address is not one Apple hosts (with or without an account) | `link_requires_email_proof`. |
| No account, and Apple hosts the address | New account (`exploring`, email verified, onboarding gate seeded, lane and referral kept). |
| No link and no email from Apple | `email_missing`. |
| The matched account is inactive | `account_inactive`, decided before any link is written. |

**Owner answer (2026-11-16, option A):** Apple may create a new account only for an address Apple hosts. This settles the ⚑ on the Sign In v2 canvas (D6956), which had proposed refusing a relay address that matches no account.

Apple hosts Hide My Email relay addresses (`@privaterelay.appleid.com`) and iCloud mailboxes (`icloud.com`, `me.com`, `mac.com`). For any other address, Apple's `email_verified` says only that the address was checked when the Apple ID was made, as D722 found for Google. The **explicit proof-of-ownership path** for those addresses is this:

1. Sign in with an email link once.
2. Press **Link Apple** under Account → Security (`/start?action=link`, which needs the session).
3. The callback links the Apple ID to the signed-in account. It refuses an account that already has one (`already_linked`), an Apple ID linked elsewhere (`sub_owned_by_other`) and an unverified address (`caller_email_unverified`).

After that, Continue with Apple signs straight in. Unlinking is `POST /api/settings/connected-accounts/apple/unlink`, under Google's no-orphan guard.

The session is `user_sessions.factor = 'apple'`: one factor, so step-up still asks for an authenticator code or passkey.

### Configuration

| Name | Kind | Value |
| --- | --- | --- |
| `APPLE_SIGNIN_SERVICES_ID` | var or secret | The Services ID's identifier, e.g. `vc.axal.web`. It is the OAuth `client_id`. |
| `APPLE_SIGNIN_TEAM_ID` | var or secret | The 10-character Team ID. |
| `APPLE_SIGNIN_KEY_ID` | var or secret | The Sign in with Apple key's Key ID. |
| `APPLE_SIGNIN_PRIVATE_KEY` | **secret only** | The `.p8` file's contents (PEM). Literal `\n` is accepted. `wrangler secret put APPLE_SIGNIN_PRIVATE_KEY --env production`; never committed, never in `[vars]`. |
| `APPLE_SIGNIN_RETURN_BASE_URL` | var, optional | The host of the registered return URL. The default is `PUBLIC_BASE_URL`, so production's is `https://axal.vc/api/auth/apple/callback`. |

**Apple Developer, once per environment (owner steps):**

1. **Identifiers → App IDs.** Use the primary App ID (or make one) with *Sign in with Apple* enabled as the primary.
2. **Identifiers → Services IDs.** Make one for the web, e.g. `vc.axal.web`. Enable Sign in with Apple, choose the primary App ID, and set:
   - **Domains:** `axal.vc`. Staging adds its own host.
   - **Return URLs:** exactly `https://axal.vc/api/auth/apple/callback`. Staging uses `https://<staging host>/api/auth/apple/callback`. HTTPS only; Apple refuses localhost.
3. **Keys.** Make a key with Sign in with Apple, tied to the primary App ID. Download the `.p8` (only once) and note the Key ID.
4. Put the four values above on the Worker: secrets with `wrangler secret put … --env production`, and the same for staging. `/api/auth/apple/config` then answers `configured: true`, and the button appears.
5. **Hide My Email delivery.** Under *Sign in with Apple for Email Communication*, register the sending domain and the From address that `EMAIL_FROM` uses (with SPF passing and DKIM). Otherwise Apple's relay drops sign-in links, invitations and notices sent to `@privaterelay.appleid.com` addresses. Send one test message to a relay address and confirm it arrives before turning the button on in production.

**Rotating the key.** Make a new key in Apple Developer and replace `APPLE_SIGNIN_PRIVATE_KEY` and `APPLE_SIGNIN_KEY_ID` together; the next exchange signs with it, because the client secret is minted per exchange. Then revoke the old key. Nothing is cached, so no deploy is needed.

**Turning it off.** Removing any of the four settings makes `/config` answer `configured: false`, hides the button, and sends `/start` back to the chooser with `not_configured`. Linked Apple IDs stay linked and work again when it is back.

### Limits and follow-ups

- The staging acceptance run is an owner step once a Services ID exists: Safari on iPhone and a desktop browser, with the environment, destination and result recorded and no identifying details. It is not in this change.
- `revokeStaleCrossIdentitySession` reads the incoming session cookie, which a cross-site POST does not carry. A stale impersonation cookie in the same browser is therefore not revoked at Apple's return. The new session cookie still replaces it in this browser.
- Rate limits: `POST /api/auth/apple/callback` has its own 60/min/IP bucket (`apple_callback`, fail-open like every sign-in path), and `/config` is exempt.
