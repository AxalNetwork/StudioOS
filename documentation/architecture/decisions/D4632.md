## D4632 — Deals: one policy for how a deal is born and moves, and every move whole (#4632)

- **Status:** Built for #4632, 2026-11-07. Worker, plus one frontend call (StudioLens Advance sends `from`).
- **Builds on:** task #127 (one door into the pass, the stage history), D469 (the amount is an admin's), D1238 (an investor's own deal flow), D1242 (an Operating Partner moves only the rounds they lead), D1153 (a withdrawal needs its reason).
- **No migration.**
- **Package 2 of 5** of the Deals follow-up. #4631 (access policy) is not on `main` yet. This package changes no reader's access: it uses the authority checks the routes already had.

### What was decided

1. **Birth (`services/dealTransitions.ts` `initialStatus`).**
   - **A founder's deal is born `applied` and nothing else.**
     - Another stage is 403 `initial_status_not_allowed`.
     - A `partner_id` is 403 `partner_staff_only`, because the studio assigns the partner.
   - **An admin may create or draft a deal into any pipeline stage.**
   - **Nobody creates a deal straight into `rejected`.** A pass needs its reason, so it goes through `POST /:id/pass` (400 `pass_needs_reason`).
   - **An unknown stage is 400 `unknown_status` on both creation routes.** The draft route used to save it as `applied` without saying so.
   - **The deal and its first history row are one batch** (`createDeal`), so a deal is never born outside the funnel's first cohort.
   - **Intake and project creation already write `applied`,** and they are unchanged.
   - **The CRM syncs (HubSpot, Affinity) are out of scope.** They copy a stage from the connected CRM, so they are not a person's entry into a deal.
2. **A move is one conditional batch** (`moveStatements`). The routes check the mover's authority (`canMoveRound`) first, as before. Then:
   - the history row is inserted only while the deal still has the stage and `stage_changed_at` the route read (its version);
   - the deal's UPDATE carries the same condition, together with every field sent with the move: the note, the partner, the terms, and the pass reason.

   A move that lands in between leaves both statements with nothing to change. The route answers 409 `deal_moved` with nothing written. The version includes the time, so even a re-entry of the same stage invalidates it. Two passes in flight can no longer overwrite each other's reason.
3. **A request lands whole or not at all.** `PUT /:id` used to run one UPDATE per field. A failure part way through left the earlier fields written, and D469's audit recorded what was committed. It is now one statement:
   - a failure writes nothing;
   - the admin audit still records the request, with `complete: false` and `written: []`.
4. **A retry cannot repeat a move.**
   - A `PUT` that sends the current stage is not a move, so it writes no second history row.
   - `POST /:id/advance` takes `{ from }`, the stage the page shows, and StudioLens sends it. A retry of an advance that already landed finds another stage and answers 409.
   - A second pass is 409, as before.
5. **The investor's deal flow (`services/dealFlow.ts`) follows the same rule.**
   - **A move with an owner or note.** Every statement, including each history row, carries the row's version guard (stage and `stage_changed_at`). The stage UPDATE runs last, so all of them read the same version.
   - **A pass.** Its history row and its UPDATE are guarded the same way.
   - **An add, and a pass on a deal not yet in the flow.** The row is inserted only while the deal is not already in the flow. Its history rows name the new row's own `uid`, so they can never attach to the row a concurrent add wrote. The loser gets 409 and writes nothing.
6. **One withdrawal door.**
   - `POST /:id/commitments/:uid/withdrawal` writes the status, the reason and the audit row in one batch: all of them or none.
   - The older `POST /:id/commitments/:uid/withdraw` wrote no reason and logged after the write. It now answers 410 `route_retired` and changes nothing.
   - No page called it. Its `api.js` method (`dealCommitmentWithdraw`) is removed.

### Tests

**`deals_pass_gate.test.ts`.** Its source-pattern checks of the move routes are replaced by executable tests over the real router and SQLite, with a batch that runs as one transaction, as D1's does. It covers:
- each creation path;
- missing and blank reasons;
- a failed write;
- retries;
- a competing move landing between the route's read and its write, injected just before the batch.

**`deal_flow_d1238.test.ts`** gains the same race tests for the investor flow.

**`deal_workroom_d1153.test.ts`** shows that a withdrawal whose audit row fails is not withdrawn.

**Fixtures.** Three older fixtures had a `batch` that returned its statements unrun, and a `deal_stage_events` table without `days_in_from`. They passed only because the history write swallowed its own failure. Both are fixed.

**Mutation checks.** Fourteen mutants of the guards, the birth policy, the retry checks and the conflict answers were each killed.
