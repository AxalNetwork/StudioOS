## D852 — Remote MCP servers a member adds: configure, discover, approve tools one by one, health and revoke

- **Status:** filed by S1 as #2475 (part of #2463) at the owner's request, 2026-10-21. Built by S23.
- **Stacks on D847 (#2468, PR #2487):** the shared MCP client. This branch carries its commits until it merges.
- **Basis:** #2487's head `cc5670fdb8`. Worker paths are relative to `cloudflare-worker/src/`.
- **Behind a flag.** `CUSTOM_MCP_ENABLED` must be exactly `true` (case and surrounding spaces ignored); unset, every route but revoke answers 404 `custom_connectors_off`. **The owner's question is still open:** #2475's own question, and #2404's A, which recommends keeping custom connectors off (A1). Built off by default, so either answer holds: A turns the flag on in `wrangler.toml`; B, or #2404's A1, leaves it off and nothing changes for members.
- **No migration.** A connection is an `integrations` row.

### 1. The decision

A member can connect a compatible remote MCP server that is not in the catalogue. The server's tools are listed for the member to approve one by one. Approved read tools can be used by Eadwyn and flows the member sets going, never on their own. Write tools stay off in v1.

### 2. As built

| File | What |
| --- | --- |
| `integrations/customMcp.ts` | The rules: the URL and address guard, the guarded fetcher, a connection's record, configure and sign-in, listing, approval, calling, health and revoke. |
| `routes/connectors_custom.ts` | The member's routes at `/api/connectors/custom`, mounted ahead of the connectors router. |
| `test/custom_mcp_d852.test.ts` | Eight cases, against D847's fake server (`_mcp_fake.mjs`) and a stubbed resolver. |
| `test/mcp_client_d847.test.ts` | Case 2's import boundary lists `customMcp.ts` as the client's second caller. |

**Routes** (signed in, a founder on a paid plan or HQ's admin, never a support session; anyone else is answered 404):
- `GET /`: the member's servers, each with its host, status, approved tools and drift.
- `POST /start {url}`: configure, as below. Answers `{ ok, uid, authorize_url }` and sets the CSRF cookie `__Host-axal_custom_mcp`.
- `GET /oauth/callback`: the server's sign-in returns here. The state is consumed first, then the cookie is checked, then the code is exchanged. It redirects to `/account/connectors?custom=ok|error`.
- `GET /:uid/tools`: what the server lists, each tool marked approved, changed or read-only.
- `POST` and `DELETE /:uid/tools/:name/approve`: approve one tool, or withdraw it. A name that is not printable (`[A-Za-z0-9_.-/]`, at most 64) is refused before anything is stored or logged.
- `POST /:uid/health`: one session, recording whether the server is reachable, signed in and drifted.
- `DELETE /:uid`: revoke. This works with the flag off, so a member can always remove a server.

**Configure.**
1. The pasted URL passes the guard (§3).
2. Its host resolves to public addresses only.
3. Its RFC 9728 protected-resource metadata is read. It must name this exact resource, and it gives the issuer and `scopes_supported`.
4. The issuer passes the same guard.
5. D847's `discoverMcp` and `mcpClientFor` (DCR) then run on a record whose hosts are exactly those two hosts. D847 checks that every endpoint sits on them.

**Sign-in.**
- PKCE S256 and the resource (RFC 8707), through D847.
- The state is #1's signed, single-use token, bound to the member and `custom_mcp`. It carries the CSRF cookie's hash, the connection's uid, its checked configuration and its client key.
- **Scopes.** None is requested, because the server's scope names mean nothing to Axal. A grant reporting a scope outside the server's own `scopes_supported` plus `offline_access` is revoked and refused (D847). Axal's own limit is the approved tools, not the scope.

**A connection's record** (`customProvider`) is built per row, never added to `MCP_PROVIDERS`:
- `key = 'custom:<uid>'` and `resources = [url]`;
- `hosts` = the resource's and the issuer's hosts;
- `read_tools` = the approved tools, with `tool_pins` = the fingerprint of each approved schema;
- `write_tools = []`, `era: 'auto'` and a budget of 12;
- a lease, state provider and DCR key prefix of its own.

**Storage.** One `integrations` row per server:
- `provider_key = 'custom:<uid>'`, `auth_type = 'oauth_mcp'`, and the tokens encrypted as every connection's are;
- `config_json = { pattern: 'mcp', url, hosts, accepted_scopes, approved, era?, drift?, checked_at? }`. It holds no secret: a URL with a query string is refused, because a query could carry a key.

### 3. SSRF

- **The URL.** It must be https, port 443 or none, with no userinfo, query or fragment. It must be a name, not an IP literal (the URL parser's IPv4 normalisation catches `2130706433` and `0x7f.1`). The name must have a dot and sit off `localhost`, `.local`, `.internal`, `.intranet`, `.lan`, `.home.arpa`, `.corp`, `.invalid` and `.onion`, and off Axal's hosts (`axal.vc`) and the host the request came to.
- **The addresses.** A host must resolve, by DNS over HTTPS (Cloudflare's JSON API, A and AAAA, 5 s and 64 KiB per answer), to public unicast addresses only. One private address refuses the host. The refused ranges:
  - IPv4: this network, private, loopback, CGNAT, link-local (169.254/16, the cloud metadata address included), IETF assignments, the documentation nets, benchmarking, multicast, reserved and broadcast;
  - IPv6: `::`, `::1`, IPv4-compatible, unique local (the metadata address `fd00:ec2::254` included), link-local, multicast and documentation;
  - IPv4-mapped, NAT64 and 6to4 addresses are read as the IPv4 they carry.
- **Every fetch.** `guardedFetcher` is the only fetcher D847 is given for a custom server: discovery, registration, token, revocation and the MCP POSTs. Each URL must pass the URL guard and sit on exactly one of the connection's hosts (a subdomain is not the host), and the host is resolved again once per request, so a host that starts resolving privately is refused on its next use.
- **The known gap.** Workers cannot pin the address `fetch` connects to, so a DNS rebinding between the lookup and the connection is not excluded by this code. Workers' egress does not reach private networks, which is the second wall.
- **Caps.** D847's caps: 10 s per request and per body, a 25 s session, 2 MiB per MCP body, 64 KiB per OAuth body, no redirect followed, and 12 requests per session. This file adds 64 KiB per protected-resource document, 10 servers per member and 25 approved tools per server.

### 4. Approval, calls and drift

- **Listing.** `tools/list` is captured from the client's own requests and read again under the client's cap. Each tool is shown with its name, its input and output schemas, and the server's description, marked `untrusted`: control and bidirectional characters are removed and it is cut to 1,000 characters. A name that is not printable is dropped. At most 200 tools are shown.
- **Approval.** Only a tool the server annotates `readOnlyHint: true` and not `destructiveHint: true` can be approved in v1. Its fingerprint (D847's: SHA-256 of its schemas, not its description) is pinned.
- **Calls.** `callCustomTool` is for Eadwyn and the member's flows, never run on its own, and refused with the flag off. A tool that is not approved is refused before any request. D847's session refuses an approved tool whose schema changed (`changed`), one now annotated as writing, and every write tool. The result is returned as `{ untrusted: true, data }`. No description or result is ever placed in an AI prompt as an instruction; a caller quotes them as data.
- **Drift.** Health opens a session and records the approved tools it no longer offers, with D847's reason. The row then reads `error` / `mcp_tool_drift` until each is approved again, which re-pins its new schema; otherwise it reads `active`. An unreachable server, or one whose sign-in expired, marks the row `error` too.
- **No metering here.** A tool call is not a billable AI step. The Eadwyn run or flow that calls one reserves and settles its own AI tokens (#2466, #2477).

### 5. Revoke

The server's revocation endpoint is called when it has one (RFC 7009, best effort, through the guard). Then the row is deleted, approvals and tokens with it, and so is this connection's registered client (`custom_mcp_client:<uid>:…` in `platform_settings`). The member's other servers are untouched.

### 6. Verified

- **`custom_mcp_d852.test.ts`**, 8 cases:
  1. The URL and address tables.
  2. The guarded fetcher.
  3. The gate: flag values, roles, tier and support session.
  4. Configure and sign in on the two hosts, with the row's exact config and no token outside the ciphertext. Then refusals before any fetch: a private resource host, an IP literal, a private issuer, a missing cookie and a replayed state.
  5. Approval: the injected description shown as data, write and unannotated tools refused, an unapproved tool never sent, another member refused, the flag off.
  6. Drift: a changed schema never sent, health recording it, approving again restoring it, and a tool newly annotated as writing refused.
  7. Revoke: both tokens revoked, the row and client deleted, the member's other server untouched, and revoke working with the flag off.
- **`mcp_client_d847.test.ts`**: 12/12, with case 2's lists naming `customMcp.ts`.
- **Mutation-checked:** 46 mutations, each killed. Each guard, range, approval, drift, revoke, gate and tool-name line was removed or inverted in turn. The first run left four redundant layers uncaught: single-label names, the fetcher's host list, the metadata's resource and the approval before a session. Each now has a test of its own.
