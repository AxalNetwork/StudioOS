## D5300 — Approval writes are atomic and retry-safe (#5300)

### Decision

An Approvals response must describe the state that actually committed:

1. **Reviewer assignment is one transaction.** Every selected item contributes
   an assignment statement immediately followed by its `approval_events`
   statement in one `DB.batch`. The event uses `changes() > 0`, so assigning
   the same reviewer again is a successful no-op and writes no duplicate event.
   A failure anywhere rolls back every assignment and every event in the call.
2. **A decision and its durable event commit together.** Co-marketing now
   batches its conditional pitch transition with the corresponding
   `activity_logs` event. Wellbeing expert review already batches the expert
   transition with `expert_review_decisions`; that history remains its
   authoritative event. A failed event therefore leaves the domain record
   unchanged and the route answers 503.
3. **Delivery is after commit and independently retryable.** Co-marketing and
   Wellbeing expert notifications remain best effort. A notification failure
   cannot undo or fail a committed decision: the route answers 200 with
   `notified: false`. No new message or delivery mechanism is introduced.
4. **Unknown is not unchanged.** The Approvals client keeps “Nothing changed”
   for confirmed refusals. A network failure or 5xx says the outcome could not
   be confirmed and asks the operator to read the item before retrying. The
   existing `notified: false` state continues to draw “decision recorded, but
   notification could not be delivered.”

### Failure contract

- Validation, authorization and stale conditional-write refusals happen before
  a write and may say nothing changed.
- A failed atomic batch changes neither the domain row nor its durable event.
- A successful batch is a committed decision even when later delivery fails.
- A transport failure or generic 5xx does not prove either outcome; the client
  must re-read before retrying.

### Tests

- `cloudflare-worker/test/approval_assignments_d470.test.ts` injects a failure
  after the assignment/event statements and proves both tables roll back.
- `cloudflare-worker/test/approval_decisions_d1043.test.ts` injects durable-event
  failures for co-marketing and expert review, then notification failures for
  both. It proves rollback in the former cases and committed 200 responses with
  `notified: false` in the latter.
- `frontend/test/approval_atomicity_d5300.test.mjs` proves 5xx and network
  failures no longer claim “Nothing changed.”

Each fault-injection test is also a mutation guard: splitting a batch, dropping
the durable event, allowing delivery failure to escape, or restoring the old
blanket frontend copy makes its corresponding assertion fail.

### Migration

None. The change uses the existing assignment, event, activity-log,
expert-decision and notification stores. Production D1 is not modified by this
work.
