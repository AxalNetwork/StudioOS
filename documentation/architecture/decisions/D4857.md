## D4857 — Meeting-bot diagnostic: running a stage and reporting it are separate facts (#4857)

- **Status:** built in slot S25, 2026-11-07 (#4857, platform audit 4/7; part of #3588, the Meet and Zoom live check). Not deployed or live verified.
- **Scope:** the owner's staged diagnostic (#3708) for Meet and Zoom. Teams diagnostics belong to #3709.
- **Migration:** none. The record already lives in R2 as JSON and holds the new fields.

### The fault

`runDiagnosis` added a finished stage to a local `done` set before `deps.report` was known to have succeeded, and swallowed a failed report on the assumption that "the next report says it again". It did not: each report held one stage. A callback that failed after stage N left N out of the table for good, and the console later read the gap as "the container went quiet".

### The choice: a cumulative snapshot, retried with backoff

Of the three options in the issue (retry each report, a durable outbox, a cumulative snapshot) the snapshot is the simplest that meets all five points. The container is short-lived and holds six stages, so an outbox on disk would add a store that dies with the container. The snapshot needs no store, and retry sits on top of it.

**Bot (`meeting-bot/src/diagnose.ts`).**
- A ledger holds each stage's latest event: `{stage, result, code, facts, rev, at, attempts}`. `rev` is a per-run counter that orders events, `at` comes from the injected clock, and `attempts` counts sends of that event that failed first.
- Each ledger entry has its own `delivered` flag. "Ran" (the entry exists) and "delivered" (the Worker acknowledged a snapshot that held it) never imply each other.
- Every callback is the whole ledger: `{diagnosis_id, revision, events[]}`. A report that fails is carried by the next one.
- A failed send is retried `REPORT_TRIES` (2) times while the check runs, and `FINAL_REPORT_TRIES` (6) times after it ends, with backoff 0.5 s, 1 s, 2 s, 4 s, 8 s on the injected clock. Retrying only resends the snapshot; no stage action reruns.
- If stages are still unacknowledged at the end, the run logs `diagnose_delivery_failed` with a count only, and `runDiagnosis` returns `{undelivered}`.

**Worker (`services/meetingBotDiagnose.ts`).**
- `report` accepts the snapshot after validating all of it (the id must be the path's, stages must be the container's six, no repeats, `rev` no higher than `revision`, facts under the same rules as before). One bad part refuses the whole snapshot with 400.
- Per stage the row with the highest `rev` wins. The same `rev` again is a no-op (no write, still 200, so the bot's retry after a lost answer is safe), and the same `rev` with other content cannot overwrite the first. An older or out-of-order snapshot cannot move a stage back, for example from pass to running.
- The record keeps the highest `revision`. A row keeps `rev`, `ran_at` (clamped to receipt time) and `attempts`.
- The old single-stage body is still accepted, so an old image still reports; it never replaces a row that has a `rev`.

### What the console shows

- **A failed check** is `fail`, with its code and its fix, and "Stops at".
- **A report that did not arrive** (past the ten-minute window) is `unrecorded`, "Not recorded", with `delivery: not_recorded`. It is never a pass and never "Stops at". The panel says, in plain words, that the report did not arrive and that this is not a failed check, lists the steps, and offers **Try again**, which starts a new check with the same link. A run with a missing result never reads "Every stage passed".
- **A report that arrived only after resends** keeps its own result and adds "Report arrived late, after N failed sends". A stage the Worker stored before the answer was lost arrived on time; the resend is a duplicate and changes nothing.
- The view gains `delivery` and `attempts` per row and `unrecorded` (the stage list). `never_reported` stays as the code and its fix text now says it is a reporting gap.

### Departures from the issue

- The issue named the timestamp as a field; `at` is the container's injected clock reading, and the Worker's own `at` (receipt) is kept separately, because the two clocks differ.
- The screenshot and probe callbacks are not part of the snapshot: they carry a file, not a stage fact, and a lost probe is already the `audio` stage's `upload_failed` result.

### Tests

- `meeting-bot/test/diagnose.test.ts`: for each of two scenarios (admitted with frames; stopped at the sign-in wall) and each stage from `DIAGNOSE_STAGES`, a transient failure and a whole-budget failure after that stage completes. The Worker's held table equals an undisturbed run, the join ran once, the event kept its `rev`, and `attempts` is right. Also: cumulative snapshots with rising revisions, a dead callback (bounded calls, `undelivered` listing, log line), backoff on the injected clock with `Date.now` poisoned, and a resend after a lost answer.
- `cloudflare-worker/test/meeting_bot_diagnose_4857.test.ts`: the real bot wired to the real callback, a loss before and after the Worker at every stage; duplicate, older, out-of-order and contradictory snapshots; malformed snapshots refused whole; the old body; the two console states.
- `frontend/test/meeting_bot_diagnose_4857.test.mjs`: the two states in the table and in the panel, and Try again.
- Mutation check: 30 of 30 mutations caught (script run against the three suites).

### Unverified

Not deployed. The bot image and the Worker deploy separately; either order works (the Worker takes both bodies, and an old image's single-stage reports still land). No live Meet or Zoom call was run.
