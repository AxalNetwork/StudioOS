## D8536 — One delivery contract for critical transactional email (#8536)

**Status:** part 1. Sign-in and company invitations meet the contract. Billing, signatures, operational alerts and the other invitation senders are listed below and still to move.

### The contract

`cloudflare-worker/src/services/email/deliveryContract.ts`. Every critical-flow send:

1. **Carries a send reference**: `flow:subject_kind:subject_id:attempt`. The subject is the record the email is about. The attempt is one issuance of that record's link. A retry of the same issuance computes the same reference. A replacement link is a new attempt, so it gets a new reference.
   - Sign-in: subject `magic_link_token:<row id>`, attempt `1`. Each `/magic/start` writes a new token row, so one row is one issuance.
   - Company invitation: subject `company_invitation:<row id>`, attempt = the first 16 hex characters of the token's stored SHA-256. A resend mints a new token, so it is a new attempt.
2. **Answers a state**:
   - `queued`: handed to the job queue.
   - `accepted`: Gmail answered 2xx. Its message id is stored.
   - `refused`: nothing was accepted, so a retry is safe. The reason is `suppressed`, `not_configured`, `provider_auth` (the token call failed before the send left), `provider_refused` (a non-2xx answer) or `no_recipient`.
   - `timed_out`: the send request left and no answer came. Gmail may have accepted it.

   The ledger also admits `delivered` and `bounced`, but nothing writes them. Gmail's `messages.send` reports no per-message delivery or bounce, and this deployment has no provider webhook for them. The existing D810 suppression list stays the bounce record.
3. **Is bound to its recipient.** `SUBJECTS` in the contract holds one query per subject kind, and that query names the address. Neither the caller nor the queued payload supplies it. The queue consumer re-reads the address at delivery. A company invitation that is no longer `pending` (for example, revoked) has no recipient, so nothing is sent.

### The ledger

The migration `202611250054_8536_email_send_refs.sql` adds one row per reference, holding: flow, subject, attempt, state, tries, reason, provider message id and timestamps. It stores no address and no link.

A send claims its row with one conditional UPSERT, and only a `queued` or `refused` row can be claimed. Any other row is answered from the ledger (`reconciled: true`) without calling the provider. A row still `sending` is answered as `timed_out`, because its request may have left. Two concurrent retries cannot both claim a row.

**Provider assumption.** The code does not use Gmail's idempotency semantics, so the reference is implemented entirely on our side. A `timed_out` send is never sent again under the same reference. The recovery is a new attempt: a replacement link, which invalidates the old one. This trades a possible missing email (recoverable by resending) for never sending a working link twice.

**If the ledger cannot be read** (for example, the migration has not reached that database yet), the send still happens once, unreconciled, and the error is logged by name only. A sign-in link that never leaves would lock the person out, which is worse than a rare duplicate.

### Flow changes

- **Sign-in** (`routes/auth.ts`, `/magic/start`). `sendBound` takes the place of `send`, with the reference set to the new token row. The queued message carries `send_ref`. The consumer's `deliverNow` sends under the reference, so a Cloudflare Queues redelivery is reconciled:
  - `refused`: the consumer throws, and the queue retries.
  - `accepted` or `timed_out`: settled, so there is no retry.

  `email_send_log.status` gains `timed_out`. Once the new link is queued, earlier unused links for the same address are retired (`expires_at = datetime('now')`), and `/magic/verify` answers `expired` for them. This happens only after the send is accepted for delivery: a refused send leaves the person the link they already have.
- **Company invitations** (`routes/company.ts`). `issueInvitationEmail` sends through `sendCompanyInvitationEmailBound` (`services/email.ts`). A `refused` send for a transient reason is tried once more in the same call. `email_sent` is true only for `accepted`. Recipient, subject, text and HTML are unchanged: the content moved into the pure `companyInvitationEmailContent`. The message now goes through `gmail.ts`'s MIME builder, which omits `Reply-To` when empty.
- **Logs**: no line in these paths carries a link, a token or a token hash. Errors log their stage and error name only. The enqueue-failure line in `send.ts` used to print the whole error and now prints the name only.

### Tests

`cloudflare-worker/test/email_delivery_contract_8536.test.ts` runs over the migrated schema, with Gmail stubbed at fetch. For each covered flow it checks:
- the link's host matches the sending environment;
- an expired link is refused;
- a replacement link invalidates the old one;
- refused, then accepted-but-timed-out: one email, one reference, `tries = 2`, and a further retry is reconciled;
- the recipient is the subject record's address;
- no token appears in any captured console line or in any row of the send, ledger, token, invitation, activity or inbox tables.

Mutations that fail the file:
- dropping the reference in `deliverNow`;
- claiming a settled row;
- re-sending `timed_out`;
- trusting the payload's address;
- logging the link (in either flow);
- not retiring earlier links;
- a fixed host;
- a constant invitation attempt.
