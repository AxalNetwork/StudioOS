### 1. Field-level saves, checked against the revision read

Each preference group carries a revision that moves by one with every write to it:

- **Visibility and discovery:** `user_settings.privacy_revision`.
- **Notifications** (digest, category maps, quiet hours): `user_settings.notifications_revision`.

`upsertUserSettings` takes an optional guard. When the save names `expected_revision`, the deciding statement is the
revision bump itself, followed by D4805's decision guard and then the field write. A stale revision fails the guard and
the batch rolls back. The route answers `409 privacy_conflict` or `409 notifications_conflict`, with the current
values.

Only the keys a body names change, as before. A client that names no revision still writes field by field and still
moves the revision on.

**Category maps merge key by key** (`mergeCategoryPatch`). Previously a category save replaced the whole map, so two
tabs editing different categories lost each other's choice. Now only the categories named change, and `null` puts one
back to its default.

### 2. Public-profile switches

`PUT /api/settings/privacy/public-profile` takes `{ fields: { name: true }, expected_revision }`. Only those switches
change, and the save is a compare-and-swap on the revision read.

`users` is at D1's 100-column limit, so this revision is the `revision` key inside `users.privacy_prefs`, compared with
`json_extract`. The older whole-map `PATCH /api/settings { privacy_prefs }` stays for older clients, but it now moves
the same revision on, so a tab holding the old one is refused afterwards.

### 3. Stored choices and the public profile agree

`GET /api/settings` returns `public_profile_effective`: the role defaults under the member's own switches, computed
by `effectiveFlags`, the function `/api/public` serves the profile with. The card draws its switches from that map.

Settings used to keep its own copy of the role defaults, and it had drifted:

- partners' `reviews` and `pricing` appeared only in the UI;
- `background` appeared only on the Worker.

That copy is deleted. The Worker's partner defaults gain `reviews: true` and `pricing: false`, the values the UI
showed. The public card renders neither yet, so nothing served changes.

### 4. One notification rule (`notificationPolicy.ts`)

`notify()` applies `effectiveChannels` before it writes an inbox row, pushes or queues an email. In order:

1. **Mandatory.**
   - Email for a locked event type (`capital_call_issued`, `agreement_ready_to_sign`) is always sent (D333).
   - A mandatory category (security, billing, contract signing) ignores category-level opt-outs.
   - The event switches still apply to in-app and Slack, as before.
2. **An opt-out at either level wins.** A channel is delivered only when neither the event switch nor the category
   switch turns it off; nothing stored means on.
   - An event switch can narrow a category.
   - A category switch silences every event in it, including events a preset stored as on. Presets write every
     event, so with the opposite precedence a category switch would never have worked.
3. **Channel scope.** Category switches cover email and in-app. Slack follows the event switch only. Push follows
   in-app.
4. **Timing.** Quiet hours and the digest decide when, never whether. They apply afterwards, unchanged.

Before this change the category switches were saved but never read by delivery. The only exception was
`proactive_nudges`, whose comment said the assistant read it, and nothing does today.

**Settings reports the same rule.** `GET /api/settings/notifications` returns `effective_categories`: every category's
effective value, with unset as on, and the locked list, which is billing. The card used to draw an unset category as
off (`!!email[key]`) while delivery sent it, and it showed billing as optional. It now draws from the effective map,
locks billing on ("Always sent"), and saves one category at a time. A save that tries to turn a mandatory category off
is refused (400).

A settings read that fails leaves category switches at their default (on) and quiet hours off. A lookup failure
never silently drops a message, and it never blocks the notify.

### 5. The client keeps the member's latest choice (`lib/serialSave.js`)

Each of the three cards saves through a `SerialSaver`:

- **One request in flight.** Edits made meanwhile are queued, merged, and sent when it returns, with the revision it
  returned. Responses therefore cannot arrive reversed, and a delayed one cannot pull the view back.
- **What the card shows:** the confirmed values, then the edit in flight, then the queue.
- **A failed save** drops only its own edit and keeps the queue going.
- **A 409** from another tab or device adopts the server's values, drops this tab's stale unsent edits, and says so.
  Nothing is silently replaced in either direction.

The controls are no longer disabled while a save is out, because rapid edits are now safe.

### Not changed

- Delivery defaults.
- The layout, which belongs to the Account redesign (#4955).
- The event matrix and presets: they still write `notification_prefs`.
