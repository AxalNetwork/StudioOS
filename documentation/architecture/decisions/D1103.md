### 1. The founder's own download

`POST /api/data-room/:projectUid/files/:uid/download` and `…/versions/:n/download`.

- **The link:** the same one-time, 120-second link the investor download mints, under the audience `data_room_founder:<project uid>`.
- **Only this venture's files:** an object outside `data-room/<project uid>/` is never handed out. The route answers 404.
- **How it is logged:** on the file's record (`logCycleWrite`, action `file_downloaded`, with no file name), and never in `data_room_access_log`.
  - The founder's own download is therefore never counted as an investor's download: not per file, and not in the week's count.
- **Who may:** the owner and a co-founder. Anyone else gets 404, as the founder side always answered.

### 2. Versions

- **The list:** `GET …/files/:uid/versions` gives the current version (the file's own row), then each earlier `data_room_file_versions` row, newest first.
  - A size or an uploader nobody recorded is null, never 0.
  - No storage key leaves the Worker.
- **Make current:** `POST …/versions/:n/current` is a **swap**.
  - The file's row takes version n's object, type, size and uploader. Version n's row takes what was current.
  - Nothing is lost, and the count of versions does not change.
  - Both updates are one batch, each guarded on the key its row held when read. If another write moved either row in between, the swap writes nothing and answers 409 `version_conflict`.
  - It is logged on the record as `version_made_current`.
- **A refused version:** a version whose key is outside the venture's prefix is never made current or downloaded (404).

### 3. A grant's folders and end date (owner question 1, answer A)

- **The scope (migration 594):**
  - `data_room_grant_folders (grant_id, folder_id)` holds one row per folder a grant opens.
  - A named folder opens its subfolders. The tree walk is bounded by the grant's own project at each step.
  - A file at the room's top level is in no folder, so a scoped grant does not open it.
- **A flag, where the issue said "no rows":**
  - The issue said "No rows means every folder". Taken alone, that lets a scope widen: when a scoped grant's last named folder is deleted, its rows go with it, and the grant would then open the whole room.
  - So `data_room_grants.folders_scoped` says whether a grant is scoped.
  - 0, which every existing grant is, opens every folder. With 1, only the rows count, and no rows opens nothing.
  - The folder delete removes the folder's scope rows by hand, in the same batch, because D1 may run with foreign keys off.
- **One predicate:**
  - `tierAdmits(f, committed, now, folders)` takes the scope as its fourth argument. `grantFolderScope(env, grantId)` reads it, and a scope that cannot be read is an empty set, which opens nothing.
  - Every investor reader passes its grant's scope:
    - the room list's count (`/shared`), the room (`/shared/:projectUid`) and the download;
    - `research.ts`'s list counts, the room read, the room memo's facts and the file read;
    - the Raise record's "who can open it" (`records/raise.ts`);
    - the evidence count (`raiseEvidence.ts`).
  - The room read also lists only the folders in scope.
  - The advisor brief reads advisor grants, which have no folders, so it is unchanged.
- **The write:**
  - `POST /grants` takes `expires_at` and `folders`. The new `PATCH /grants/:uid` changes either one.
  - `expires_at` is a day (`YYYY-MM-DD`), today or later. It is stored as the end of that day UTC, so the grant is open through it. Null clears it.
  - `folders` is null for every folder, or a non-empty list of this venture's folder uids. An empty list is refused (400), so "no folders" can never be mistaken for "every folder". A folder that is not this venture's is 404.
  - Both fields are checked before the address is looked up, so a refusal never tells the owner whether an email has an account.
  - A re-grant that names no `folders` keeps the scope it had.
- **The founder read:** each grant carries `folders`: null for every folder, or the uids it opens.
  - A scope that cannot be read is `folders: null` with `folders_unreadable: true`, never drawn as every folder.
  - The read also returns `role`.
  - `granted_by` was already returned.

### 4. Co-founders (owner question 2, answer A)

The owner is the account the tenancy scope gives the venture to, or an admin. A co-founder is an accepted `project_members` row with role `cofounder`. An advisor member, or a removed or pending co-founder, gets 404, as before.

| | Owner | Co-founder |
| --- | --- | --- |
| Read the room, versions, preview | yes | yes |
| Upload | yes | yes, with no gate fields. The file takes its folder's visibility (an NDA folder makes an NDA file) and the default tier |
| Rename, move a file or folder; create a folder; delete a folder | yes | yes |
| Match a file to a request or checklist item | yes | yes |
| Download any version; make one current | yes | yes |
| Share, revoke, change a grant | yes | 403 `owner_only` |
| Change a gate (`visibility`, `access_tier`, `access_expires_at`, `apply_to_contents`) | yes | 403 `owner_only` |
| Delete a file | yes | 403 `owner_only` |

- **"Answer requests":** read here as matching a file to a request (`dd_request_id`) or a checklist item, which is this route's part of answering. The request records themselves are the Requests tab's.
- **Deleting a file:** kept for the owner. It takes every earlier version with it, which is not organising.

### 5. The preview

`GET /:projectUid/preview?grant=<uid>` shows the room exactly as that grant's investor sees it.

- **Same filter:** `/shared/:projectUid` and the preview call the same function, `investorView`, so they cannot drift apart.
- **No log:** the preview writes no row in `data_room_access_log`. A founder looking is not the investor opening the room.
- **What is hidden:** files the tier, the expiry or the grant's folders hide are counted (`hidden_from_grant`) and never named. The investor's own read never returns that count.
- **A grant that opens nothing:** a revoked or ended grant answers `open: false` with a reason, and no files.
- **Not found:** another venture's grant, or no grant, is 404.
