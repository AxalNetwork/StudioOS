## D8348 — A passing request can hand its authority to a compact record, store half (#8348)

D8339 kept a passing request in the capacity store for its full seven days, because the outbox may still
lower its check while the request exists. A store of 1,000 passes inside seven days therefore still refuses,
and D8333 finding 10 stayed partially open. This adds the store half of the fix. At the full cap, the oldest
published pass is replaced by a compact record that keeps exactly what is needed to correct its check, and
the full request leaves.

S39 agreed the scope and its three decisions on
[#7909](https://github.com/AxalNetwork/StudioOS/issues/7909#issuecomment-7103562100) and the contract, with
amendments, on [#8348](https://github.com/AxalNetwork/StudioOS/issues/8348#issuecomment-7104498093). This
record follows that contract.

**Nothing here is live, and finding 10 is not resolved by it.** Compaction happens only when a consumer is
passed to the store, and nothing passes one. The matching outbox, result retention, failure routing, fair
reconciliation and runtime composition are S39's, and no line of those files changes here. Until they
exist, turning compaction on would lose the check's intent (see "What S39's half must do").

### The record

```ts
type CompactRecord = {
  version: 1;
  publicationMode: 'pilot' | 'full-suite';  // the mode the request was published under, fixed at handoff
  submission: CiSubmission;                 // exactly as accepted
  acceptedAt: number; completedAt: number; deadline: number;
  attempts: CompactAttempt[];               // every attempt that owned a child run
};
type CompactAttempt = { logicalShard; generation; profile; childRunId; childAttempt; startDeadline; executionDeadline; current };
```

Parent observation reads only `submission`. Result validation compares a whole `ExecutionReceipt`, and every
receipt field is in `submission` or in a `CompactAttempt`, so `compactReceipt` rebuilds the exact receipt of
any preserved attempt. `current` records which generation was current at handoff; it grants no receipt,
admission or late success.

The record does not hold the job association. That stays in S39's `capacity_execution_results`.

### When a request is handed off

In the existing oldest-first pass, at the full cap, a request is handed off only if all of these hold:

1. A consumer was passed to the store and its `mode()` returns `pilot` or `full-suite`. A missing consumer,
   a null, any other value or a throw means no handoff.
2. The request guard answers `revisable` and the request's own leases have run out (both from D8339).
3. The request is a pass at its original completion, read under the parent fence as it stands now.
4. No attempt, current or historical, carries `rejectedWorkflowSha`.
5. It has at most 18 owned attempts, each with a distinct positive child run id and a distinct shard and
   generation, and exactly one current owned attempt for each expected shard.
6. Every owned attempt's receipt, rebuilt from the projection, matches the original under `receiptMatches`
   and carries the same child workflow revision, present or absent.
7. The stored state is at most 4,096 UTF-8 bytes.
8. The compact table holds fewer than 32,768 records and none with this request id.

Otherwise the request stays whole, the pass moves on, and the store refuses `capacity_storage_bound` when
nothing else can leave. The pass still frees one place per admission.

The compact record is inserted and the full request deleted inside the one transaction `prune` already
runs. A failure at any statement rolls back both. A restart finds the full request or the compact record,
never neither. If both exist for one id, that is inconsistent state: the handoff refuses, neither is
changed, and `get(id)` and `compact(id)` both answering is the signal.

Request, parent and child fences are untouched. A compacted identity is refused `capacity_expired_request`
like any removed one.

### The sticky failure

`compactFailure(receipt, jobId)` sets a failure once and never clears it.

- It returns false and changes nothing when no record has that request id, when no preserved attempt
  rebuilds to a receipt matching the one given, or when the job id is not a positive integer. It cannot
  create a record.
- A repeat for the same attempt and job changes nothing. A failure for another owned attempt of the same
  request is accepted and the first stored failure kept.
- The same attempt with a different job throws `capacity_compact_conflict`.

The store keeps one failure. It can therefore show a different job only for the attempt that failure
names. After attempt A is stored, a later attempt B is accepted without its detail being kept, so a second,
different job for B is not detected here. Refusing that is the result-association layer's work, before the
store is called.

### Expiry

A compact record leaves only at the original limit, seven days from the request's completion, and only when
the consumer's `evidence` is exactly `revisable` or `final`. Anything else, a throw, or no consumer keeps it.

Each `prune` reads at most 64 expired records in `(completed_at, id)` order after a durable cursor. A full
page moves the cursor; a short page clears it, so the next visit starts again and owed records are seen
again. Owed records at the front cannot hide later ones.

`publicationConsumer(storage, mode)` in `ciCapacityRetention.ts` is a reference consumer over the outbox's
intents. It answers `owed` when the current mode is unknown or differs from the record's, so a pilot record
is never read as full-suite authority. S39 may use it or replace it.

### Bounds and measurements

| Bound | Value |
| --- | --- |
| Compact records | 32,768, counting overdue records still owed |
| Read page | 100, clamped; a non-positive or non-integer limit is refused |
| Expired records read per `prune` | 64 |
| Owned attempts per record | 18 |
| Stored state per record | 4,096 UTF-8 bytes |

Work per admission is at most 1,000 full-request reads, as in D8339, plus 64 compact reads and one count of
the compact table when a handoff is first tried.

Measured with identifiers of production size (a merge-queue request, eleven-digit run ids, a pinned child
workflow, three prerequisites):

| Case | Bytes |
| --- | --- |
| Full request, eight attempts | 7,510 |
| Compact state, eight attempts | 1,371 |
| Compact state, eighteen attempts | 2,101 |

Attempts are stored as fixed-order rows; as keyed objects eight of them cost about 2.1 KB.

SQLite storage for the compact table and its index at 32,768 rows, in memory, 4 KiB pages: 67.6 MiB with
1,371-byte states and 147.5 MiB with states at the 4,096-byte bound. `COUNT(*)` over 32,768 rows took under
0.3 ms. These are the table alone. They are not total storage, which also includes the fences and S39's
retained intents and results, and they say nothing about throughput.

### What S39's half must do

1. `ciCapacityOutbox.ts` deletes every intent whose id is not in `ci_capacity_requests`. With that
   unchanged, one outbox pass after a handoff removes the compacted request's intent. The reference consumer
   then answers `owed` for good, and the record never expires. A test shows exactly this. It fails closed,
   and it is why compaction must not be enabled first.
2. `lib/ciCapacityResults.ts` deletes results the same way, and that table holds the job association.
3. `CiCapacity.status`, `ownsResult` and `recordExecutionFailure` answer null or throw once the full
   request is gone. Routing them to `compact`, `compactReceipt` and `compactFailure` is the coordinator half.
4. Validation is asynchronous and the store's transactions are not. After any awaited check the caller must
   look the request up again, because it may have been handed off meanwhile.
