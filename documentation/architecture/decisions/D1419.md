### 4. The rules of the grid (`studioLayoutModel.js`, `useStudioLayout.js`)

- **Edits are local; Done is the only save.** One `saveLayout(draft, revision, profile)` call, with exactly `{ key, size }` per entry and the revision the read gave (`null` with no row). Nothing saves per move. Done with nothing changed saves nothing. Leaving with unsaved edits asks first (`beforeunload`).
- **Add** appends at the module's `default_size`. At 12 every Add is off and the cap line says why. A plan-locked module is never added; its entry reads "Included in <plan>" (the Worker's plan name, `lockedPlanName`) and opens the locked sheet.
- **A failed save keeps the edits:** 409 `stale_layout` → "Your layout changed in another tab." with Reload layout (SM8c); 402 `module_locked` → "<Title> is not on your plan. Included in <plan>." with See plans; anything else → "Your layout could not be saved." with Try again.
- **Reset** asks first ("Replace your layout with the default?", Cancel / Replace layout), then resets at once and leaves edit mode.
- **A failed layout read draws the default** with "Your layout could not be read; showing the default." and Try again, and offers no Customise. A 500 `layout_unreadable` says "Your saved layout could not be read" and offers Reset. The default then comes from `studioFallback.js`, a copy of the Worker's `STUDIO_DEFAULTS` and titles that `studio_canvas_d1419.test.mjs` holds equal to `services/studioModules.ts`.
- **A saved `[]` stays empty** (SM8d) and never falls back to the default.
- **Dropped modules are named by title** with why (`droppedLines`); a title the Worker no longer knows is "A module". A key never reaches the page.
- **The five states:** loading ("Reading…"), could not be read ("<Title> could not be read · Try again", alone; the only red is the icon), Not recorded with its reason (never 0, never red), empty, ready.
- **Lab tools outside a cohort** reads Not recorded ("The Lab’s tools open week by week inside a cohort, and you are not in one.") rather than a list of Locked rows (`cohort_only`).
- **Strip and edit bar counts are never derived from each other:** "Modules active" counts Lab features; "n of 12" counts placed modules.

### 5. Behind the seam, keyed to its issue

`frontend/src/pages/studio/studioProposalsAdapter.js` is the one way to Eadwyn's layout proposals (SM9, SM10, SM13c). **#3864** (D1420) builds the `studio:layout` run on `POST /api/ai/rail/run`. Until it is on `main`, `propose()` answers `{ available: false, reason, issue: '#3864' }` and nothing is drawn in the chat: no client method exists for a route that does not. Accept is not behind the seam: `applyProposal` applies the rows to a copy, skipping what the Worker would refuse, and the save is `studioLayoutApi.saveLayout`. A tripwire in the test fails the day the Worker names `studio:layout` while `propose` still answers unavailable.
