## D4600 — Build: progress says only what it recorded, and a filing's proof is retried against the filing that exists (#4600)

- **Status:** Built for #4600, 2026-11-07. Frontend only.
- **Builds on:** D968 (the states read: Built, Live, Tested), D1070 (the progress page), D690 (a filing's proof), D695 (the one `FormLightbox`).
- **No migration. No Worker change.**
- **Depends on #4630 (D4630)** for the shape of `FormLightbox`'s `save`. Both change its catch block. Whichever merges second takes a one-block merge.

### What was decided

1. **The lead names the evidence it rests on (`stageLead`).**
   - Each item's Built and Live are read together (`builtLiveRead`):
     - `done`: either is done;
     - `no`: every stage that applies is reported "Not yet";
     - `unknown`: any stage that applies is not recorded, and none is done;
     - `na`: neither applies (a risk, a prototype test).
   - "None is built or live yet" is said only when no item is `unknown` and none is `done`. Before, one item reported "Not yet" was enough to say it for every item.
   - When some items are reported and some are not, the lead says both: "Built or live: 1 not yet, 5 not recorded."
   - When none is reported, or the read failed, it keeps "Built and live are not recorded here yet."
   - When some are built, the count stands and the items not recorded are said: "3 of 6 accepted items are built or live. Built or live: 2 not recorded."
   - Items to which neither stage applies add nothing. A plan of only risks and tests makes no statement about built or live.
2. **A completed test is Tested, not Built or live (`bucketOf`).**
   - There is a new bucket, Tested, between "Built or live" and "Not started". Built or live keeps its label.
   - A built or live item stays in "Built or live" even when it is also tested.
   - The lead adds "N tested, not built or live." from the same bucket, so the lead, the bars, the legend and the Stage filter count the same items. A test covers that by comparing each filter's rows with the bar.
3. **A filing's proof is retried against the filing that exists.**
   - `FormLightbox` gives `onSubmit(values, memory)`, a per-open-form object. Add filing keeps the created step there.
   - If the upload fails, the error carries `partial = { result, cta, only }`. The form then:
     - calls `onSaved` once with the saved filing, so the page behind it shows the filing;
     - relabels the button Retry proof upload;
     - freezes every field but the proof;
     - says: "The filing was added; its proof was not stored: <reason>. Press Retry proof upload to try the upload again. The filing is not added twice."
   - The next press uploads to the same step and creates nothing. A press with no file chosen creates and uploads nothing, and asks for the file or for the form to be closed.
   - Other forms ignore `memory`, and a refusal without `partial` behaves as before.
4. **Not done: creation idempotency for an ambiguous network retry.** If the create call's own answer is lost, the form cannot know the filing exists. That needs a Worker idempotency key on `POST …/formation-steps`. It is a separate change; this one fixes the case the app can know.
