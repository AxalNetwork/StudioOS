## D4537 — The From Axal catalogue filters, and a library file is never shown as a skill (#4537)

#4537 is Session 09 of #4528, taken by slot S17. On main, #4840 had already connected the lifecycle actions on the From Axal list, and the review, cases, diff and retire controls on the detail page. #5086 added publish on release evidence. S1 set the order for what was still missing:
1. the catalogue filters, and the source-definition / D1-draft / published distinction from `GET /library` (this step);
2. the definition editor;
3. the release-evidence display.

Every screen stays inside the HQ AI Agents canvas.

### What is decided

- **The list row carries what it filters on.** `GET /api/admin/ai-agents/skills` adds each row's `slug`, its `roles` as `{ key, label }` (the catalogue role's name) and its `tools`, all from the draft the row already reads. There is no new endpoint and no extra query.
- **Filters are client-side over the one list read.** They are status, area, role, evaluation state and source, plus a search over name and slug. Each filter is exact and they combine. The list is read once, without fetching any skill's detail.
- **Evaluation state comes from the list's `golden`.** A missing result is never a pass, so there are five states, each distinct:
  - `no_cases`: the skill has no golden cases;
  - `not_evaluated`: none of the required runs has a result;
  - `partial`: some of them have one;
  - `below_bar`;
  - `meets_bar`.

  Whether a skill meets the bar is the server's `meets_bar`, never recomputed in the browser. A row without `not_evaluated` reads as unknown, not as a pass.
- **Source is read from `GET /library`.**
  - A stored skill whose slug is a library file reads "From a library file". Any other stored skill reads "Authored in HQ".
  - Until the library answers, the source reads "Not recorded" and its filter is off.
  - An unreadable library shows its own notice and never hides the stored skills.
- **A library file not in the store is not a skill.** It is listed in its own table, with its area, level, case count, check result (with the refusal code when invalid) and "Not seeded". It has no status, version, agents or checkbox, so no lifecycle action can be pointed at it. Seeding stays the existing `POST /library/seed`, and this step adds no control for it.

### Step 2: the definition editor

- **Opened on demand, beside the read view.** A skill's detail keeps showing its saved definition; "Edit definition" opens a form below it. A retired skill has no form.
- **The existing route saves it.** The form sends name, purpose, steps, read-only tools, output kind, taxonomy tags (level names, as stored) and roles to `PATCH /api/teams/skills/:uid`, which runs `checkDraft` for a Super Admin on an Axal skill. No new route.
- **The slug is shown, never sent.** `GET /:uid` now carries `slug`; the PATCH keeps the stored one.
- **The server decides.** A refusal shows "Not saved", the page's sentence and the code, and marks the field `checkDraft`'s code is about (`definitionModel.js`). A code with no sentence here shows the Worker's own. Nothing is checked in the browser that the server does not.
- **Saving says what it costs first.** A draft under review: the open review and its evaluation no longer cover it. A published skill: the published version stays as it is until a new one is published. Published versions are never edited.
- **Reused, not redrawn.** The steps editor and taxonomy picker are Team › Skills' (`SkillSheets.jsx`); roles come from `GET /api/teams/roles`.

### Step 3: the release-evidence display

- **The server's decision, in words.** A skill's detail shows "Ready to publish" or "Not ready to publish", with each reason, from GET /:uid's `freshness`. That is the same release decision (D4533) the publish gate refuses on. Nothing is recomputed in the browser. A detail without `freshness` reads "Not recorded", never ready.
- **Every blocking code has its own sentence.** A test reads the `Blocking` union from `skillLifecycle.ts` and fails on a code with no words.
- **The evaluation line never counts a missing run as a pass.** For example: "2 of 4 pass · 2 not evaluated · bar 9 of 10". A skill with no required runs says so, not "0 of 0".
- **Since the last approval, part by part.** Definition, golden cases, evaluator and required models each read "Changed", "Unchanged" or "Not recorded" (an approval made before that part was recorded). A skill never approved says so. An approval already spent on a release names the version.
- **Each published version's manifest.** For each version: its evidence and definition hashes, runs passed, cases, evaluator, models and approver. A version published before manifests says so. A publish with no audit row is flagged, and an unread audit log is not a missing row.
- **Replaces the raw record.** This card replaces the raw "Published versions" record on the detail page.
