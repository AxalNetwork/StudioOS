## D9036 — Explorer promo: the code and the unlock in one batch, and redemption tested end to end (#9036)

`POST /api/products/redeem` grants a 30-day feature unlock for $0 against a one-time explorer promo code
(`services/explorerPromo.ts`). The Products page calls it, together with `GET /api/products/promo`
(`frontend/src/pages/ProductsPage.jsx`). Until this decision no test covered either route.

### The defect

`redeemExplorerPromo` spent the code first, setting `redeemed_at` with an atomic claim, and wrote the unlock after it
(`writeFeatureUnlock`). If the second write failed, the code stayed spent with no unlock behind it. Every retry then
answered `already_redeemed`, and the account never received the license it had earned.

### The decision

**The claim and the grant are one D1 batch.** D1 runs a batch as a single transaction, so either both writes land or
neither does.

- **The grant is built by `featureUnlockStatement`** (`services/featureUnlocks.ts`), the same idempotent `INSERT OR
  IGNORE` as `writeFeatureUnlock`, prepared but not run. `writeFeatureUnlock` now runs that same statement, so the two
  cannot drift.
- **The grant needs no condition on the claim.** It is keyed `explorer_promo:<code id>:<user>` under
  `UNIQUE(source_payment_intent_id)`. A request that loses the claim to a concurrent one therefore inserts nothing:
  the winner's row already holds that key. It still answers `already_redeemed`, read from the claim's change count.
- **A failed batch is a refusal.** The route answers `503 redeem_not_saved`, saying the code was not used. The
  store's error is reported privately and never reaches the caller.

The batch was chosen over checking the grant before burning the code because only the batch is atomic. A check
before the claim still leaves a gap between the two writes.

### What the tests pin

`cloudflare-worker/test/explorer_promo_redeem.test.ts` runs the real router on the migrated schema, with synthetic
accounts and codes generated at run time.

- **One redemption, one unlock.** The owner's code redeems once into exactly one unlock, $0, running 30 days. A second
  redeem gets `already_redeemed` and grants nothing more.
- **Codes do not probe accounts.** Another account's code answers exactly what a made-up code answers (`not_found`).
- **Bad codes.** An expired code gets `expired`, and an empty one `not_found`.
- **Matching.** A code matches with or without its dashes, in either case.
- **A failed grant spends nothing.** When the unlock insert fails (a trigger that aborts it), `redeemed_at` stays NULL
  and no unlock exists. Once the fault is removed, the same code redeems.
- **Sessions.** Neither route answers without one.
