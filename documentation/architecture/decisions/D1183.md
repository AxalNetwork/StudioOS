## D1183 — Bank accounts' stored balance and monthly flow reads (#3112)

- **Scope:** S30, s30 (Codex), 2026-10-25. Part 2 of #2389.
- **Basis:** main `30a8cdcbef`, the BNK3 Cash chart specification in #2389,
  migration 474's existing stores and D712's five-day intercompany rule.
- **Migration:** none. No production reads or writes were made by this task.

### Reads and boundaries

`GET /api/admin/mercury/balances?account=&range=30d|90d|12m` reads the stored
daily Current and Available snapshots. The default is 90d. A missing account
filter reads every stored entity account; a supplied filter is its public UID,
not its bank identifier. Thirty/ninety days include today and the preceding
29/89 UTC days. Twelve months is the trailing calendar year, inclusive of
today, with the previous year's anniversary clamped for leap day. Future
readings are excluded. Unknown accounts are 404; invalid bounded filters 400.

Each account has masked ending metadata and dated `points`, with the stored
`as_of` time and nullable `current`/`available` money objects. A missing day
has no point. A recorded zero stays zero; a null amount has `not_recorded`.
An account with no snapshots has an empty series and `not_recorded`. No
nickname, provider identifier, credential, full number or transaction text is
selected. The Accounts read remains separate; this task adds no page.

`GET /api/admin/mercury/monthly?entity=` reads six calendar months, from the
first day five months before the current month through today (UTC). The
current month's point has `to_date: true`. Each entity returns dated `points`
with positive integer `in_cents` and `out_cents`; the page can mirror outflows
below its axis. Only the USD store's posted-status rows with a posting date
count, in their posting month. A month with no recorded posted rows is absent,
not a made-up zero. A month whose recorded rows are all excluded transfers
has measured zero external flows. Missing series carry `not_recorded`.

Native `internalTransfer` rows are excluded. Cross-entity transfers use D712's
existing rule: equal opposite cents on two **registered** accounts of
different entities, within five days, earliest first, each line used once.
Five days before the first displayed month are read to find a counterpart
across its boundary. All entities are considered before the display filter;
filtering to GP cannot turn its intercompany receipt into external money in.
Six-day matches and unregistered lines do not form D712 pairs. Stored rows of
disconnected connections remain readable, as on the reporting page.

### Gate, audit and failure

Both mounted routes use `requireMercuryReader`: an HQ Admin (including the
Super Admin), never a member, support session or branch. They are GET only,
use only bound SQL, and neither calls Mercury nor reads credentials.

`mercury_balances_read` and `mercury_monthly_read` are distinct actions in
`READ_AUDIT_ACTIONS`. The actor and validated filters are written **before
any bank-data query**, including an empty or unknown-account lookup. A failed
audit returns 503 `audit_unavailable` without making that read. Audit failure
logs contain the allowlisted action and outcome, never the database's error.
A failed store read or unsafe integer total returns a constant Unreadable
503 with no figures; it never becomes an empty chart or zero.

The existing `adminMercury.js` client exposes both mounted reads. No new API
domain, screen, migration, binding, external bank call or money action is added.

### Verification and live boundary

Mounted tests run the actual SQL over migration 474 with real node:sqlite and
synthetic records. They cover range/leap boundaries, absent days/months,
null/zero/as-of values, posting dates/statuses, internal transfers, one-use
pairing at both month boundaries and under entity filters, masking, all role
refusals, audit-before-read and failure, read failure and unsafe totals. Bank
callers are stubbed to refuse every request. Client tests exercise the actual
transport. Production-code mutations must fail these tests, then restored
code must pass. Actual build, frontend, guards and drift results are in the PR.

Live Mercury fields/statuses and historical sync coverage remain
**UNVERIFIED**, as in D710/D712. The five-day amount heuristic is the existing
rule, not proof of a transfer's counterparty. The owner's post-deploy check
must confirm the two reads, masking, gaps and audit order against the live
sync. This task does not deploy, reveal an account number or read live bank
content. Canvas rendering belongs to the later Bank accounts page parts.
