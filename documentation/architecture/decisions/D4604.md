## D4604 — Relationship transitions, private notes and introduction delivery (#4604)

Package 1 of 5 of the Network audit (findings 1–3). Migration `202611090834_intro_delivery_attempt`.

### 1. A relationship transition writes only from the state it read

`routes/partnernet.ts` read a row, checked its status, then wrote with `WHERE id = ?`. A request answered, withdrawn or removed in between was overwritten, and the event and the notice were written for it anyway.

Each transition is now one conditional UPDATE on the state it read, and `meta.changes` decides the answer:

| Route | Writes only while | Lost race |
| --- | --- | --- |
| `POST /relationships/:id/respond` | `pending`, the same `requested_by`, the same `requested_at`, and the caller is not the requester | 409 |
| `POST /relationships/:id/withdraw` | `pending`, the caller's own request, the same `requested_at` | 409 |
| `POST /relationships/:id/remove` | `accepted` | 409 |
| `POST /relationships` (asking again on an ended row) | the ended status, requester and time just read | 409 `relationship_changed` |
| `PATCH /relationships/:id` | `accepted`, and the metadata it was built from | re-read and rebuilt up to three times, then 409 `relationship_changed`; 409 once it is no longer accepted |

The `relationship_events` row, the network-score recompute and the notice follow only a write that changed the row. So the stored state, the history, the notice and the reply agree.

### 2. A private note is kept whole and read by its writer only

A note lives at `metadata.private_notes[userId]`. Before this change, the note was cut at 2,000 characters, and the whole metadata JSON was then cut at 4,000. Two full notes, or one with escaped characters, produced JSON that would not parse. That row then read as `{}`, which blanked both notes and the shared details.

- A note over 2,000 characters (after trimming) is refused with `400 private_note_too_long`, and nothing is saved. A note that is not text is `400 private_note_invalid`. Nothing is ever cut.
- The stored JSON is never cut. The shared metadata a party writes is bounded on its own, at 4,000 characters (`400 metadata_too_large`). A party can never set `private_notes` or `created_by` through it.
- The metadata write is conditional on the metadata it was read from (section 1), so two parties saving at the same moment both keep their notes.
- Asking again on an ended row keeps both notes. Each comes back to its writer once the row is accepted again.
- Every reply carries the caller's own note only (`my_private_note`), including `POST /relationships`, which used to return the raw row. The PATCH reply confirms the note as stored.
- Someone who is not a party (an admin bypass) has no private note to write: `403 private_note_party_only`.

### 3. An introduction's delivery is one durable attempt

D4665 made each email send an operation with a recorded outcome. An introduction request had no record of its own delivery. While an intro's send was `uncertain`, or delivered but not yet recorded as made, the request still read `accepted`, so a new composition went to the provider and the intro could arrive twice.

`relationship_interactions.delivery_op_uid` names the `mail_send_ops` row that holds the right to deliver the intro.

- **Claim.** `POST /api/mail/send` with `intro_uid` claims the delivery after admission. This happens before the nonce is spent and before any provider I/O, in one conditional UPDATE: the request must be `accepted`, and no other operation in `pending`, `accepted` or `uncertain` may hold it. If the claim fails, the new operation is discarded and nothing is sent:
  - the holder was accepted: the intro is recorded as made from the holder, and the reply is `409 intro_already_sent`;
  - the holder is unconfirmed: `409 intro_delivery_unconfirmed`;
  - the request is already made: `409 intro_already_made`. A replay of the operation that made it still recovers it (`200 recovered`), as in D4665.
- **Release.** A `refused` operation, or one discarded on a wrong nonce, releases the claim. The intro can then be written again.
- **Proof of delivery.** `markMadeOnSend` accepts the sent-log row or the accepted operation (they share a uid). A sent-log write that failed on its own therefore does not hold the record back. Made is written only from the holder, and its event and notice follow only a write that changed the row.
- **Recovery.**
  - The member's word on an unconfirmed send (`POST /api/mail/send/operations/:uid/resolve`) settles the intro it was delivering. `arrived` records the intro as made, with no resend. `not_arrived` releases the claim.
  - `POST /api/relationships/intro-requests/:uid/delivery/reconcile` is for the teammate. It records a delivery the provider accepted as made and sends nothing. It answers 409 while the send is unconfirmed or did not go out.
- **The reply says what is stored.** The send's `intro` is `{ status: 'made' }`, or `{ status: 'accepted', recorded: false }` when the record still lags.

The teammate's view of a request carries `delivery: { state, operation_uid }`. The asker's carries `null`, because the asker never reads the introducer's mailbox. The states are:

| `delivery.state` | Meaning | The desk shows |
| --- | --- | --- |
| `sending` | admitted; no answer yet | a line; no Write button |
| `unconfirmed` | the provider may have it (or a pending row went stale) | the composer's "It arrived" / "It did not arrive"; no Write button |
| `record_pending` | delivered; the request is not yet made | "Sent" with **Update the record**, which sends nothing; no Write button |
| `not_sent` | refused, or never admitted | a line, and Write the intro again |

The desk is the existing Network › Introductions "Asked of you" card. No screen was added (#4799).

### Not changed

- The introduction lifecycle's other transitions (`decideIntro`, `withdrawIntro`) were already conditional with a `changes` check.
- No row is backfilled. A request sent before the migration has no recorded attempt, and none is made up for it.
