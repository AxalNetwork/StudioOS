### 1. `GET /api/ai-budget/prices`

`priceList()` in `services/metering.ts` reads `METERING_POLICY` itself, so the page never carries a copy. It returns `{ version, operations }`, every operation in the policy's order, each with:
- `operation`, `label` and `unit`;
- `source`: `axal`, `connector` or `remote_mcp`, for where the call reaches;
- `price_microusd`: integer micro-USD;
- `ai`: true when the tool's model run is charged at that run's own cost, on top of its price (D844's composite rule).

**What a price reads as:**
- **A free operation** is a known 0, never left out.
- **A price the policy cannot read** (negative, or not an integer) is `null`, never a 0.

**Labels and sources** sit in `OPERATION_INFO`, beside the policy. The test fails when the two list different operations, or when a registered MCP tool has no label.

**Values today.** Every v1 operation is free (`d844-1`):
- `summarize_meeting`, `extract_action_items` and `structure_with_studioos` are `ai: true`.
- D846's two connector reads are `connector`.
- No `remote_mcp` operation is priced yet: D852's member MCP servers hold nothing today.

**Who reads it:** any signed-in member (`requireAuth`). Signed out is 401.

### 2. Migration 632: what a hold is for

`ai_budget_reservations` gains four columns. Each is a short id or NULL, never a prompt or an answer.
- **`operation`:** the metering operation, or `ai.<task>` for an AI run.
- **`surface`:** `mcp`, `flow` or `ai`, enforced by a CHECK.
- **`api_key_uid`:** the member key the call came through.
- **`execution_id`:** the execution the hold belongs to.

**Who writes them.** `reserveAiBudget` takes an optional `context` and writes it once the hold is taken.
- **`meteredCall`** passes the operation, its execution, its key and a new `surface`: `mcp` from `mcp/server.ts`, `flow` from `services/flows.ts`.
- **`aiRouter`'s run** passes `ai.<task>` and `ai`.
- **Anything that is not a short id** (`[A-Za-z0-9._:-]{1,120}`) is written as NULL, so a prompt can never land there.

**A label never decides a hold.** The context is written in its own statement after the hold, not in the hold's batch.
- If it cannot be written, the hold stands, the log says "hold context not recorded" with no value, and the read says the hold's context is not recorded.
- **Why it is not in the batch:** thirty-two existing test fixtures build `ai_budget_reservations` without 632. Putting the write in the batch made every hold in them fail. A label that blocks a charge would be the worse failure in production too.

**Other callers name nothing yet,** so their holds keep NULL:
- `aiProviders`;
- live transcription;
- the meeting bot;
- the Validate session's hold.

### 3. `GET /api/ai-budget/holds`

`memberHolds()` returns `{ holds }`, the caller's own `pending` and `review` holds, oldest first, at most 200. Each has:
- `uid`, `created_at` and `status`;
- `expires_at`: the stored one, never computed for the page;
- `included_microusd` and `topup_microusd`;
- `surface`, `operation`, `api_key_uid` and `execution_id`.

**Expiry is the Worker's.** An expired pending hold is released first, as every budget read does (`releaseExpired`), so it is refunded and never listed. `HOLD_TTL_MS` (five minutes) is now the one constant `reserveAiBudget` writes with.

**Whose holds:** `requireAuth` only, with no id in the address. Another member's holds are never returned.
