## D1368 — A failed meeting bot run says where it stopped

- **Status:** asked for by the owner on 2026-10-29 ("yes" to "make the bot save its failure step"); built by S21.
- **Migration:** 655 (`meeting_bots.failure_detail`, additive).
- **Builds on:** D886, the meeting bot. Its `failure_code` (what the member sees) is unchanged.
- **Tracker:** #3588, the live check of the Meet bot.

### Why

Four live Google Meet runs, on 2026-10-28 and 2026-10-29, failed the same way. Each started, reported `joining`, sent two heartbeats, and then failed about 50 seconds later as `runtime_failed`, with no waiting room. The bot knew more than that:
- its own code: `platform_blocked`, `link_invalid` and `obf_unavailable` all map to `runtime_failed`;
- the last join step it logged (`meet_navigation_ready`, `meet_prejoin_result:unknown`, `meet_join_clicked`, and so on).

Both lived only in the container's log, which neither the owner nor an agent could read from the app. Without them, no fix could be checked against a cause.

### What is recorded

- **The bot** (`meeting-bot/`):
  - `MeetAdapter` remembers the last `meet_*` step it logged, with its page classification when it has one, and returns it from `diagnostic()`;
  - `runBot`'s failure report carries it as `detail`;
  - an adapter that cannot start reports `runtime_start`;
  - the callback sends `failure_detail` = `<code>` or `<code>@<step>[:<state>]`.
- **The Worker** (`MeetingBotRun`) stores `failure_detail` on the run, but only on a failed status and only in that shape (`BOT_FAILURE_DETAIL`). The write is best-effort: a database before migration 655 still records the failure.

Nothing is shown to the member. The field is for HQ and for agents reading the run, so the next attempt names its cause. For example, `platform_blocked@meet_prejoin_result:unknown` means Meet showed a screen the bot did not recognise before it could ask to join.

### Privacy

D886's rule is unchanged: no meeting link, name, page text or browser message is stored or logged.
- **The steps:** they come from `logLine`, which already keeps only the bot's own codes.
- **The shape check:** both ends allow lowercase code words only. Anything else falls back to the code alone on the bot's side, and is not stored on the Worker's side.

### Tests

- **`meeting-bot/test/meet_adapter.test.ts`** (real Chromium): after a refused or unrecognised pre-join, `diagnostic()` is `meet_prejoin_result:platform_blocked` or `meet_prejoin_result:unknown`.
- **`meeting-bot/test/callback_privacy.test.ts`:**
  - a failed status sends `platform_blocked@meet_prejoin_result:unknown`;
  - page text falls back to the code alone;
  - a failed join reaches the transport with its step through `runBot`.
- **`cloudflare-worker/test/meeting_bot_control_d886.test.ts`:** the shaped detail is stored and a sentence is not.

All three are mutation checked: dropping the step, the bot's shape check or the Worker's shape check each fails its test.
