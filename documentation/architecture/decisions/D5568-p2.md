### Pointer store

- **One transaction per change.** Each call is one `storage.transaction`. Each pointer row is its own key (`workspace-checkpoint-pointer-v1:<tenant>/<run>`) and each runner record is its own key (`workspace-runner-v1:<run>`). Only changed rows are written. A throw anywhere rolls back every row, as with `DurableWorkspaceAdmissionStore` (D5570 part 2). A change callback must be synchronous; a returned promise is refused (`transaction_must_be_synchronous`).
- **Fenced by the D5565 generation in the same storage.** Before the change runs, each pointer's generation is raised to its run's runner generation. So a `requestCancel` or `reap` already committed fences every older checkpoint writer, restore and GC plan, with no separate `fence()` call. This is D5568's "wire D5565's generation bump to `fence()` in the same transaction boundary". The test cancels the run through `createRunnerControl` and the next commit from generation 1 is refused `stale_generation`.
- **The store's own refusals**, independent of the service's checks. Each throws `CheckpointStoreRefusal` and rolls back:

| Refusal | When |
|---|---|
| `checkpoint_pointer_removed` | a row is deleted |
| `checkpoint_pointer_key_mismatch` | a row's key is not its `tenant/run` |
| `run_contract_changed` | a row's tenant, run or origin region changes |
| `stale_generation` | a generation goes down, falls below the runner's, or a head advances at a generation other than the row's |
| `checkpoint_deleted` | a tombstone is cleared |
| `checkpoint_conflict` | a head's sequence goes backwards |
| `tenant_mismatch` | a row's tenant is not its runner's tenant |

  `DurableRunnerStore` refuses a removed record, a changed run id or tenant, and a lowered generation.
- **Tenant quota** sums the rows in this object only. A per-run object therefore enforces the quota per run. A tenant-wide quota needs a tenant-level counter, which is listed below.

### R2 adapter

- **Scope.** Every key is `<namespace>/` plus D5568's layout, `tenants/<tenant>/workspace-checkpoints/<run>/g<generation>/<token>/{blobs/<sha256>|manifest.json}`. Anything else is refused (`checkpoint_key_out_of_scope`) before the bucket or the fence is called. The namespace is required, has no default, and must match `[a-z][a-z0-9-]{0,31}`.
- **Put.**
  1. The bytes must hash to the stated SHA-256, or the put is refused before any write (`checksum_mismatch`).
  2. The put passes `sha256`, so R2 itself rejects a body that does not match. The test shows Miniflare's R2 refusing one.
  3. The put records the checksum in `customMetadata`.
  4. The object is then read back and re-hashed. A put R2 answers with `null` is `checkpoint_upload_interrupted`. An object missing on read-back is `checkpoint_object_missing`. Bytes that differ are `checksum_mismatch`.
- **Get.** An absent object is `null`. A body that does not hash to its recorded checksum, or has none, is refused (`checksum_mismatch`). The service turns that into a typed `checksum_mismatch` refusal and releases the restore worktree.
- **List.** Only a `tenants/<tenant>/workspace-checkpoints/<run>/` prefix is accepted (`checkpoint_prefix_out_of_scope`). Listing pages through cursors, 1,000 keys a page, at most 100 pages (`checkpoint_list_too_large`). A truncated page with no cursor is refused (`checkpoint_list_incomplete`), and a returned key outside the prefix is refused. The namespace is stripped from every key listed.
- **Fenced delete.** Before every delete, the adapter asks `DurableCheckpointPointerStore.mayDelete(key)`. That is a pointer transaction that allows the key only when its run's row exists for the same tenant and the acknowledged head does not reference the key. A refused key is never deleted (`stale_gc`). Checking and then deleting is safe, because every commit writes under its own `g<generation>/<token>/` prefix, so a later head cannot reference an existing key. This adds to `executePlan`'s own generation and head fence; it does not replace it.
- **Two reads per put.** The service's `putVerified` also reads back, so each object is read twice. That cost is accepted while the adapter is unmounted and can be dropped when the service trusts the adapter.
- A real `R2Bucket` satisfies the adapter's `CheckpointBucket` interface, and this is checked at compile time.

### Consistency notes

- `executePlan` prunes the pointer history before it deletes, as in part 1. If a delete fails part-way, the plan returns `stale_gc` or `checkpoint_store_unavailable`. The undeleted objects stay as unreferenced orphans under their own prefix, and a later plan collects them once their generation is fenced. Nothing acknowledged is lost.
- A pointer transaction does no R2 or network I/O. Uploads happen between the snapshot transaction and the commit-point transaction, as in D5568.

### Tests and mutations

- `workspace_checkpoint_store_5568_p2.test.mjs` covers:
  - five commits racing one head: each one either commits a new sequence or is refused `checkpoint_conflict`;
  - a runtime restart;
  - a runner cancel fencing the old writer and restore, and the next generation restoring the last acknowledged checkpoint;
  - rollback on a throw;
  - each store refusal above;
  - the head refused by the delete fence;
  - retention GC deleting from R2 with the head still restorable;
  - R2's own sha256 refusal.
- `workspace_checkpoint_r2_5568_p2.test.ts` covers:
  - namespace, key and prefix scope;
  - the checksum checks on put;
  - each read-back failure;
  - an object corrupted at rest;
  - paging;
  - the fenced delete;
  - the service mapping a corrupted manifest or blob to `checksum_mismatch` and a fenced delete to `stale_gc`.
- Fourteen mutations are listed in the two test headers (S1 to S7, R1 to R7). Each one fails a test.

### Rollback

Nothing is mounted or bound, so rollback means reverting the PR. That removes the two new modules, the two test files and the service's port-refusal mapping, and part 1's behaviour is unchanged. No storage, object, binding or remote state exists to undo. After a rollout, use D5568's rollback order: stop admission, leave pointers and objects in place, fence the generation, and restore from the last acknowledged head. Never delete customer repository data.
