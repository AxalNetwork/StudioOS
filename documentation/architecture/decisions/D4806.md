## D4806 — An approval applies to the exact revision the reviewer saw (#4806)

- **Status:** built by S27, 2026-11-07 (#4806, Programs audit 3/7).
- **Number:** D4806 is this issue's number (D4106). Migration: none.
- **The invariant (from the issue):** an approval applies to the exact revision or state the reviewer saw. A conflict leaves all approval-dependent state unchanged.
- **Kept explicit:** proposal sending stays closed (`PROPOSALS_CLOSED`, D955), and the pause policy gates are unchanged. This issue makes the approval paths safe so that opening proposals later is a policy decision, not a bug.

### 1. Playbook publish

**The defect.** `publishDraft` read the draft, compared it to the published version, then ran a batch whose sections were `INSERT … SELECT … FROM program_playbook_sections WHERE version = 0`. That copies whatever the draft is when the batch runs, not what was read. An edit landing between the review and the write was published under the publisher's action.

**The fix.**
- **The revision.** `programDetail` returns `draft.hash`, the SHA-256 of what `contentOf` says the draft holds (section key, position, title, body, computed flag and template keys, in order). That is the draft's revision.
- **The request.** `POST /:key/playbook/publish` takes `{ expected_hash }`. A missing or malformed one is refused (400 `expected_hash_required`). A draft whose hash is not the one named is refused (409 `draft_changed`, "Nothing was published").
- **The write.** The version's sections are inserted from the rows that were read and hashed (`VALUES`), never copied from version 0 at write time. An edit that lands in between stays in the draft and out of the version, and the draft then reads as differing from what was published. The version row is still unique per program, so two publishes racing cannot both land.
- **The clients.** The Playbook editor and the Lab's How it runs page capture `draft.hash` when the publish dialog opens and send it back. Their Publish button is off without one.

### 2. Program proposal approval

**The defect.** `decide` put the decision's `UPDATE … WHERE status = 'sent'` LAST in the batch, after the registry row, the playbook sections and the draft grant with its history line. A decision that lost (to a decline, a send-back or another approval) changed no proposal row and answered 409 `not_waiting`, but the statements before it had already committed: the program, its playbook draft and a draft grant sat in the registry for a proposal that was never approved.

**The fix.**
- **The order.** The decision's `UPDATE` is the batch's first statement. Everything an approval writes comes after it, each gated on that decision having won: `WHERE EXISTS (SELECT 1 FROM program_proposals WHERE id = ? AND status = 'approved' AND decided_at = ? AND decided_by_user_id = ?)`.
- **The gate.** `decided_at` is a timestamp minted for this request, so only the decision that this request wrote satisfies the gate. A proposal decided by anyone else first has another status or another `decided_at`, so none of this request's registry row, sections, draft grant or history line is written.
- **The statements.** `insertProgramStatementsOnApproval` and `openDraftStatementsOnApproval` are the gated forms. `insertProgramStatements` and `openDraftStatements` are unchanged for New program and the migration backfill. The proposal's `program_key` is set by a second gated `UPDATE`, since the key is derived after the decision statement is built.
- **The answer.** A lost decision answers 409 `not_waiting` as before, now with nothing written. A taken key still rolls the whole batch back (409 `program_key_taken`).

### 3. Perks feature and stop-feature

**The defect.** The page sent `{ action: 'approve', featured }` for Feature and Stop featuring. The Worker treated an approve of a live listing as a feature-only edit, but an approve of a paused one as a republish. If the listing was paused, or edited by its partner and so returned to review, while the dialog was open, the "feature" request put it back on the shelf. The only staleness check was `updated_at` read inside the same request, which a stale dialog satisfied.

**The fix.**
- **The revision.** A listing's revision is its `updated_at`, as the admin list returns it. Every review action and the new feature operation name it as `expected_revision`. A missing one is 400 `expected_revision_required`; one that is not the listing's is 409 `listing_changed`, "Nothing was changed". The UPDATE repeats the check, so a change landing between the read and the write loses too.
- **The operation.** `POST /perks/admin/:uid/feature { featured, editorial_note?, expected_revision }` acts only on a `live` listing (409 `not_live` otherwise) and changes the feature and the editorial line only: not the status, the review note or the reviewer. A request that changes nothing is 409 `no_change`. It is audited as `perk.feature_updated`.
- **Approve.** `approve` of an already-live listing is refused (409 `already_live`), so no request shaped like an approve can republish or re-review a live listing. Approving a paused or in-review listing, with its optional "also feature it", stays one review action.
- **The page.** `listingBody` sends `expected_revision` (the row's `updated_at`) with every action, and Feature and Stop featuring call `api.perkFeature`.

### 4. Tests

- `cloudflare-worker/test/program_approvals_d4806.test.ts` (6 tests):
  - a changed draft is refused and a missing hash is a 400, with nothing published;
  - an edit landing between the read and the write stays out of the version;
  - an approval that loses to a decline, a send-back or another approval writes no registry row, sections, draft grant, history or audit line;
  - an approval that wins writes each once, and a repeat writes nothing.
- `cloudflare-worker/test/perks_listing_revisions_d4806.test.ts` (5 tests):
  - the revision is required and a stale one is refused with nothing written;
  - a feature switch cannot republish a listing paused or edited while the dialog was open;
  - an approve of a live listing is refused;
  - the UPDATE repeats the check;
  - a feature switch that wins changes the feature and the line only.
