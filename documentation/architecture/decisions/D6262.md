## D6262 — Spendable introduction credits beside Accept (#6262)

The existing introduction service's `credits.balance` is the spendable sum of
allowance, purchased and referral credits. The zone header shows that exact
balance and each pending card says Accepting uses 1 credit. No allowance cap
or purchase total is substituted. Recorded zero is zero; null, invalid or
failed reads say Could not be read, matching approved NW5. Loading/refresh
also prevents accepting against a stale balance. Decline remains available.

Both the control and handler gate Accept. The existing accept/decline routes
remain authoritative. A successful action uses its returned balance; a
missing balance or refused/uncertain acceptance invalidates the old one.
A failed refresh retains previously read propositions, clearly labeled, so
Decline still works while Accept is unavailable. A zero balance explains
Insufficient credits and the required one credit; unknown never prints zero.

Each proposition separately shows the recorded counterpart answer: Agreed,
Declined, Not answered, expired without answer, or Not recorded. This never
infers that an introduction happened from one side accepting. No new store,
API method, permission, message, payment or automated outreach is introduced.
The existing section/rail both use the same credit state. Tests exercise
valid, zero, unknown, refreshed and failed reads and actual action payloads.
