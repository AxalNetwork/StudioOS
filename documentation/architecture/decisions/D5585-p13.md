### 1. The rule

The default `RELEASE_ADMIN_DEPS.renderAdmissions(env, scope)` is:

```ts
const r = await swarmSnapshotFor(env, scope);
return r.ok ? r.value : null;
```

It reads the one `WorkspaceAdmission` coordinator (`workspace-admission:shared-quota:v1`) and asks for the scope's own
venture (`tenant_id`, `company_id`) only. The caller is the route's authenticated scope, never a request body. The
client refuses `wrong_tenant` for any other venture before it calls the stub, and the object checks again.

Every answer that is not a readable `SwarmState` becomes null. That covers:

- no binding (`admission_unbound`);
- an unreachable or unreadable object, or a stub that throws (`admission_unavailable`);
- a scope the client cannot name (`invalid_admission_call`);
- a `BRANCH_DO_JURISDICTION` this Worker cannot use.

Null means "not read", so a manifest that pins a render is still refused `render_unadmitted` (`admission_unverified`).
A failure is never read as an empty state, and never as admitted.

### 2. What changes on a deployment

The release routes are behind `WORK_GRAPH_RELEASE_ADMIN=on`, and no deployment sets it. Before this part, a manifest
that pins a render showed `admission_unverified` on every deployment. Once the coordinator is reachable, the evaluation
reads its real state.

Nothing calls `swarm.request` yet, because #5586 has not mounted a caller. So a reachable coordinator answers an empty
venture, and a pinned render shows `not_admitted` instead of `admission_unverified`. Both refuse. The new reason is the
more accurate one: admission was read and holds no ticket for that run.

The reviewer context (D5585-p10) reads the same resolver, so `/account/portfolio/:uid/releases` shows the same reason.

### 3. Cost

Each admin or reviewer context makes one extra Durable Object request, in parallel with the two D1 reads it already
makes. A context is built once per request, and no list or loop builds one per row.

### Rollback

Revert this commit. `renderAdmissions` then answers null again, as in part 12. No data or binding is involved.
