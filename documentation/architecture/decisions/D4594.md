### 1. What this is, and what it is not

**This is a LOCAL SIMULATION.** The orchestration and accounting are the production code:

- the engine routes and their authorization;
- admission and the scope object (`ScopeCore`);
- the queue consumer and `dispatchQueue`;
- the loop;
- `agentRun` and `aiRouter.run()`, so holds, settlement, usage rows and charges are real;
- `decideRail` and `deliverDecision`;
- the DLQ repair.

**Three things stand in for Cloudflare's runtime:**

- **Inference** is stubbed: `env.AI` answers deterministically, or times out, or answers 429, or throws.
- **The Workflow, queue and `AGENT_SCOPE` bindings** are faked.
- **A step runner** stands in for the Workflow engine.

Every test title carries the label `LOCAL SIMULATION · real orchestration and accounting code · STUBBED INFERENCE · fake
Workflow and queue bindings`.

It is **not**:

- the hosted Stage A, which needs isolated resources, owner approval, ceilings and a passed #4566 preflight;
- provider readiness (#4556);
- a capacity figure (Stage C).

Nothing hosted was provisioned or run, and nothing in production changed. `AGENT_ENGINE=off` and
`AGENT_AUTONOMY=manual` stay as they are.

### 2. Why the real `agentRun` and not the existing fake

The engine's own fixture (`_agent_engine_fixture.ts`) fakes `agentRun`. That is right for testing the loop's rules,
but it cannot show that a hold was taken and settled, or what was charged. The issue asks for "reconciled
usage/hold/charge" and for one charge per logical execution, so this harness keeps the real `agentRun` and router and
stubs only below them, at the Workers AI binding. Everything the router does (Llama Guard, holds, fallback, usage rows,
settlement) runs unchanged.

### 3. What the suite proves (13 tests)

**Stage A:**

- **A1, the Workflow path, end to end:**
  1. an authorized start;
  2. scoped admission and a queue message;
  3. dispatch;
  4. a Workflow instance named by the run;
  5. the loop;
  6. a proposal;
  7. the sponsor accepts through the queue route;
  8. the run and task are done.

  Provenance is checked exactly: one call on the agent's own model, the proposal tied to its usage row, the usage row
  under the sponsor with the agent and the option, and the hold named `agent:<run>:run` with its `execution_id`. The
  hold is settled at exactly the sum charged, never more than was held.
- **A2, the manual sponsor run path:** one proposal and one settled hold, with no engine run, Workflow or queue message.
- **A3, refusals with zero unauthorized effects:** wrong tenant, missing permission, engine off, a stranger's manual run,
  a duplicate start, and a revoked sponsor (refused at the run step, before any hold).

**Stage B:**

- **B1:** duplicated and late-redelivered messages.
- **B2:** a provider timeout or 429, with the router's fallback included; the hold is refunded and a fresh start
  recovers.
- **B3:** an ambiguous commit (charged, proposal write failed) ends `step_lost` with no second charge.
- **B4:** an interrupted Workflow replays once.
- **B5:** a lost decision wait, then a late decision.
- **B6:** a cancellation that a later decision does not undo.
- **B7:** a moved scope, and the halt key.
- **B8:** the DLQ repair before acknowledgement, and a replay after it.

After each case `assertClean` holds:

- no pending hold;
- at most one proposal and one settled hold per run key;
- settled equals charged;
- no live slot for an ended run.

**Effect deduplication, not exactly-once delivery.** The tests deliver the same message more than once. What stays
single is the effect: the run key, the hold's idempotency key, and the run-status guards.

**Mutation-checked.** Each of these makes a test fail:

- the consumer's past-admitted guard removed;
- the hold's idempotency key dropped;
- `deliverDecision`'s waiting guard removed;
- the DLQ acknowledging without repairing;
- the proposal not tied to its usage row;
- the engine flag ignored.

### 4. Finding, now fixed: the DLQ repair left a stale live slot

`repairExhaustedRun` (D4593) correctly moves the run to `failed queue_exhausted` and the task back to `open`, in D1. It
did not tell the scope object. So the object's live view, which the status socket shows, still listed the failed run
until a rebuild.

- **Impact was limited.** Admission is decided by D1, by design (`doRuntime.ts`: "a live entry the object failed to
  clear must not hold an agent forever"). The agent was not blocked, and a fresh start was admitted.
- **The fix.** The harness PR left this as a `test.todo` (B8b), because #4594 keeps runtime fixes out. The owner
  approved the fix on 2026-11-09. Once the repair reads the run back as `failed queue_exhausted`, it now calls
  `untrackEnded`, which runs `trackRun(env, scopeOfRow(agent), run)`.
  - It is best effort and never throws, so a missed track costs at most a stale row until the next rebuild, as before.
    It cannot fail the repair or hold the message.
  - It runs on every outcome that reads the run back as failed, a newer attempt included, because the stale entry is
    this run's either way.
- **Test.** B8 now asserts the live view is empty right after the repair. Mutation-checked: removing the call makes B8
  fail.
