## D6703 — Server-side founder intake cases and immutable answers (#6703)

The self-mounting `/api/formation/cases` router is HQ-only. An authenticated
project owner or company editor can create/resume an open v2 case, read it,
and save answers at the revision they read. Existing partial unique indexes
serialize creation through different doors. New-company clients create the
project through the existing project route first, retaining that id on a
later intake failure so the caller can resume it.

Each save appends a `formation_case_answers` row and its source snapshot;
updates are rejected by a database trigger. Answer insert, actor event and
case revision/hold update are one D1 batch with revision preconditions.
Prefill reads minimal project/member/company/officer/location/founder and
base cap-table fields. Every field names its store. Country names and ISO
codes normalize without city inference; unknown values remain questions.
Answers never update those source stores or `projects.incorporation_meta`.

Every save checks the current restricted-place list against all known
founders' residence/nationality and operating countries. Omitting founders
is rejected. A match holds the case for HQ, with no options and only the
generic founder message. An existing hold requires HQ review to release.
Rules/options and people workflows remain #6704 and #6705 respectively.

The batched formation status reads include unpaid open v2 cases as
`draft_case`; positive incorporated evidence and paid orders retain priority.
Missing reads still fail closed as `unreadable`. The additive answers-table
migration must precede the Worker rollout. There is no runtime schema DDL for
that table and no production migration is run by this change.

Tests use migrated SQLite, real Hono routes and signed synthetic identities:
concurrent create/save, access revocation, branch refusal, immutable snapshots,
source provenance, live restrictions, hold persistence and existing status
projections. Validation and mutation results are recorded in the PR.
