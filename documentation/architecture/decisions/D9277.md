## D9277 — An Eadwyn conversation belongs to exactly one company or one project, and every read, run and action stays in it (#9277)

- **Status:** built by S21 on #9277, 2026-11-28.
- **Chosen by:** the owner's rule on #9271, as filed on the issue, reconciled with the owner's supplemental audit (the advisor interview's space is #9285's).

### The problem

`eadwyn_conversations` (migration 444) kept the company active when a conversation started and a free `workspace` label, and no project. A project's conversation therefore read every project of its company, a sibling project's figures included, and nothing tied a pending action to the project it was proposed in.

### What was decided

- **The space.** Every conversation, and every action it proposes, is in exactly one company or one project: `scope_kind` with `company_id` XOR `project_id`, the shape `team_agents` (712) uses. Migration `202611281314_9277_eadwyn_space.sql` adds both columns to `eadwyn_conversations` and `eadwyn_pending_actions`, backfills every row with a company to company scope, and holds the shape with triggers (as D4962 does) so the Worker one version back, which writes `company_id` without `scope_kind`, still works; the route reads such a row as company scope. `project_id` references `projects(id) ON DELETE CASCADE`.
- **No inheritance.** A project under a company is not in the company's space, and the company is not in the project's, even for a member of both. Membership is the platform's own: a company is a `user_company_links` row for a company that is not archived; a project is one not in Trash that `canAccessProject` lets the member read.
- **`services/eadwynSpace.ts`** is the one helper, for `/api/eadwyn` and for #9285: `parseSpaceRef`, `spaceRefOfRow`, `spaceColumns`, `resolveSpace` (membership now, with the name), `recheckSpace`, `spaceChecker` (one lookup per space per request), `projectInSpace`, `publicSpace` and `SPACE_REFUSALS`.
- **Routes.** `POST /conversations` takes `{ scope, id, workspace? }` and refuses 403 `space_not_member` (400 `space_invalid` for a bad claim). `GET /conversations?scope=&id=` lists that space only. The older `{ workspace }` start is the active company (400 `space_required` with none); `?workspace=` keeps listing, without rows whose space the member lost. Reading a conversation, changing its switches, quote, ask and confirm re-check the space (403 `space_access_lost`); a company space still runs only while it is the active company (409 `company_changed`). `/conversations/mine` leaves out a lost space's rows. Delete and cancel need no space: both are the owner's own and neither reads or sends anything.
- **Actions.** A pending action stores the space it was proposed in. Confirm re-checks that stored space (`space_access_lost`), and the target must be inside it: the space's own project, or a project assigned to the company (an unassigned project is in no company's space; before, it passed).
- **Context.** `readForRun` and the connector readers take the space: a project space binds `(? IS NULL OR p.id = ?)` in every reader query, with the project's own company for the `integration_companies` gate (a project with no company reads nothing). The run's system message names the space by kind and id, not by its member-typed name. Each source under an answer carries `space: { scope, id }`.
- **The header.** Every conversation answers `space: { scope, id, name }`, and the composer prints "In <name>".
- **Out of scope.** `/api/advisor` (the profiling interview) stays personal and private; #9285 binds it.

### Rows with neither company nor project

Read on production D1 on 2026-11-28 as aggregates only (AGENTS.md): 1 conversation, 0 with no company, 0 owners with such a row; 0 pending actions, 0 with no company. So the list is empty today. Any row with neither that appears later (none can be written by this Worker; only a fixture or a hand write could) stays readable by its owner, appears in their lists with `space: null`, and is never run (409 `no_space`).

### Inventory

`ventureSpaceDataInventory.ts` now reads both tables as keyed by project and company: a hard delete removes a project's rows by the cascade, and a move leaves them following the venture, since a row never names both.

### Tests

`cloudflare-worker/test/eadwyn_space_d9277.test.ts` (15) and `frontend/test/eadwyn_space_client_9277.test.mjs` (2), with the D652, D701, D1442 and D6420 fixtures given the space: 35 mutations, 33 caught, 2 equivalent (a company space reads no unassigned project and no project-scope row by its XOR shape alone, so its extra null guards cannot change an answer).

The company membership test is written in `eadwynSpace.ts` rather than called through `resolveActiveCompany`: a space is the stored company, never the client's selection, so these reads stay out of the D8526 company-scope inventory.
