### Capacity model

`ceilingPerDay` is batch × parallel builds × 1440 / wall minutes. It excludes
failures, human approval, deployment and arrivals. With batch 1, five builds
and 44.5-minute wall it is 161.8 merges/day; at 12 minutes it is 600.

The table models 12-minute wall, a 3× arrival peak, 108 runner-minutes per
full-suite run, and a 3% independent **per-PR deterministic culprit rate**.
It is not a measured failure probability. Fractional builds describe required
capacity; actual settings would round up, subject to the owner rule. This
landing-only cost model differs from #5611's broader 40k 4-vCPU-minute model.

`runsPerPr` charges the initial run and both child runs whenever a failed
batch is split in half. Every possible internal node contributes its two
children weighted by the probability that the parent contains a culprit.
Divide expected runs by expected successfully merged PRs, batch × (1 − rate).
At batch 1 this is 1 / 0.97; 300 × 108 / 0.97 = 33,402 rounded runner-minutes.
At zero failures, batch 8 costs 1/8 run per merged PR. At high failure rates,
bisection can cost more than single-entry testing. No always-cheaper claim.

Assumptions: failures identify stable culprits, all-good batches pass, both
halves run after a failure, every run costs the same 108 minutes, and failing
PRs do not merge. Flakes, infra retries, interactions between otherwise-good
PRs, partial batches and changed heads are not modeled. Mergify's documented
split policy can be N-way; this binary model is not a vendor cost forecast.

### Reopen only on observed evidence

`triggerMet(days)` accepts normalized complete daily #5603 windows with:
`date` (UTC day key), `sourceIssue: 5603`, `afterWaves: true`, `complete: true`,
`merged`, `entryToMergeP90Min`, and `runnerMinPerMergedPr`.
`afterWaves` means the **whole window begins after** #5601, #5606, #5621, #5609
and #5611 have merged; it is not an inferred timestamp from this model.

Only the latest 14 distinct consecutive complete windows count. Every day
must have either entry-to-merge p90 **>30 minutes at ≥200 merges**, or
runner-minutes per merged PR **>250**. A day with neither observed condition, a partial window, an invalid or
missing date, a duplicate, a gap or an unmerged-wave flag refuse the trigger.
A stale historical 14-day run cannot override a newer failing day.
Dates are sorted without mutating the input; comparisons use UTC day keys.
The function neither fetches history nor changes a queue.

exists in this task; #5611 is still awaiting benchmarks and the actual cap.
An empty evidence input returns false, not fabricated zeros. Once real daily
history satisfies this rule, post a BLOCKED STATUS with `needs-decision`,
A/B/C and the updated recommendation. The current settled A answer stays in

### Options, costs, risks and rollback

**A — native (selected).** No incremental vendor subscription; standard public
GitHub runners are free, with actual concurrency capacity supplied by #5605
row 5 and measured by #5506. Risk: the queue retains per-entry testing and
repeated combined candidates; capacity and failure work in W0–W2 still matters.
Rollback: no new component was installed; retain the existing gate and settings.
Do not re-ask concurrency or infer an account cap from the capacity equation.

**B — vendor batches and bisection (not selected; not currently admissible).**
First-party sources checked on **12 November 2026**:

- [Mergify batching](https://docs.mergify.com/merge-queue/batches/) creates a
  batch PR, validates it and splits failures. It introduces temporary queue
  branches/PRs and a batch-size/wait-time policy.
  [App permissions](https://docs.mergify.com/security/) include read/write
  Actions, Checks, Contents, Deployments, Issues, Pages, Pull requests and
  Workflows; read-only Administration, Commit statuses, Metadata and Merge
  queues, plus organization Administration read. This is broader than #5618's
  intended app. [Pricing](https://mergify.com/pricing) advertises zero cost for
  open source and a separate Free plan for small private teams; paid Max is
  shown at $21/seat/month; the selected billing commitment is unverified. Batch entitlement and project
  eligibility must be confirmed before treating either free offer as a quote.
- Crucially, [Mergify's setup](https://docs.mergify.com/merge-queue/setup/)
  explicitly requires the app as an **Exempt bypass actor** on applicable
  rulesets. Vendor-side injection of equivalent conditions is not the owner's
  no-bypass policy. The verify-first answer is **no**, not assumed compatible.
- [Trunk batching](https://github.com/trunk-io/docs/blob/main/merge-queue/optimizations/batching.md)
  is disabled by default, has batch size/wait controls and automatically
  bisects failures. Its [branch setup](https://github.com/trunk-io/docs/blob/main/merge-queue/getting-started/configure-branch-protection.md)
  creates `trunk-temp/**/*` / `trunk-merge/**/*` branches and draft PRs (or
  push-triggered branches). Its recommended rulesets require an **Exempt
  update bypass** for the app, while a separate mergeability ruleset keeps
  review/status checks. Preserved checks do not make this a no-bypass design.
- [Trunk app permissions](https://github.com/trunk-io/docs/blob/main/setup-and-administration/github-app-permissions.md):
  read/write Actions, Checks, Contents, Issues, Pull requests and Workflows;
  read-only Administration, Commit statuses and Metadata, organization Events
  and Members. Optional Trunk Sudo is separate and is not proposed.
  [Billing](https://github.com/trunk-io/docs/blob/main/setup-and-administration/billing.md)
  says Merge Queue usage is unlimited and public-repo committers do not count
  toward the private-committer limit; [pricing](https://trunk.io/pricing)
  lists Free $0 and Team $18/committer/month; its selected billing commitment
  is unverified. Actual account eligibility,
  other product usage and a written scope still require owner verification.

A future compatible vendor could own queue candidate construction, bisection
and stale candidate cancellation, replacing that **queue-specific** portion of

Risk: broad app rights, overlapping controllers and changed candidate proof.
Rollback: pause vendor admission, finish/abandon its candidates, revoke its app
and temporary-ref permissions, and restore the native queue behind the same
required checks. No bypass or direct-main push is approved to make B work.

**C — own train (not selected; highest risk).** It would depend on #5618 and
need batch refs, full-suite proof and ordered PR merge-API calls, with no App
push to main and no bypass. Engineering/on-call cost and per-run compute are
unmeasured; use the arithmetic only as a scenario, not a budget.

[GitHub's merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)
supports App installation tokens with Contents write, a pinned PR `sha`, and
refuses a non-mergeable request (405) or mismatched head (409). It now explicitly
states that the synchronous endpoint does **not** support merge queues; the
asynchronous endpoint can enqueue into the native queue, which does not itself
provide this proposed batching. [Rulesets layer and enforce all applicable
rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets),
and Apps only get an exemption when granted bypass. Documentation supports
keeping checks enforced; an actual no-bypass App refusal/rehearsal has **not**
been performed because that App is not configured. It remains a verify-first
acceptance gate for C, not a claimed successful merge test.

`ci.yml`'s current `verified` job searches successful native `merge_group` runs
at the exact commit SHA. C cannot reuse that lookup. It would need an
independent, App-pinned attestation binding the full tested batch tree, base
SHA, ordered PR head SHAs and each landed prefix/result tree. A PR head check
alone or a different batch SHA is insufficient. Main/deploy proof must agree
with #5501; a changed base/head invalidates reuse and requires validation again.
This is a required design change, not built here. A future owner-approved
transition must also resolve native queue requirements, rather than silently
bypassing them through a merge API.

Risk: stale combined proof, bad prefix/tree mapping and a controller merging
outside the proven candidate. Rollback: kill switch, stop new batches, remove
train admission and restore native queue proof before landing more PRs. No
post-merge repair substitute is approved.
