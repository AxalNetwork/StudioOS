### 1. Migration 574

- **`project_id` on `cap_table_option_pools` and `cap_table_vesting`,** each with its index.
- **The backfill ties a row only where one venture is proven:**
  - A vesting row takes the venture of its holder, or else of its security, on the same account.
  - A holder or security with no venture proves nothing. Nor does one on another account.
  - An option pool links to nothing (Carta writes it from the account's issuer), so no pool is tied.
  - Nothing is guessed from "this founder has one venture".
- **A row left unset is account-level.** No venture read returns it. The account view still does.
- **Carta's rows are renamed** from `source = 'carta'` to `connector_carta` in all four tables.

### 2. The venture reads

| Read | Change |
|---|---|
| `GET /api/captable/equity-plan?project_id=` | Pools and grants of that venture only, behind the venture's read gate (`ensureProjectReadAccess`: the founder, an accepted co-founder or advisor, an admin; never an investor). |
| `GET /api/captable/live?project_id=` | Holders and securities of that venture only, behind the same gate. A reader who may not write gets no holder email. |

- **Without `project_id`, each read answers the account, as before.** That covers the Spin-Out Lab's card and the old Cap table page. Each answer now says which register it read: `scope: { kind: 'venture' | 'account', project_id }`.
- **Never a zero for a missing value** (`services/capTableRegister.ts`):
  - **Totals.** A total is `knownSum`: null with no rows, and null when any row lacks the figure, because a sum over a partly recorded column is not the total. `unvested_shares` is null unless both of its parts are known.
  - **Ownership.** A holder's ownership is its share of a known total. With any holder's count missing, nobody's share is known, and every percentage is null. `/live` used to write `0%` there.
  - **Old page.** The old page's live table now prints "Not recorded" for a missing count or percentage, instead of `0`.
- **A read that fails answers 5xx.** The equity plan already did (D366). `/live` now refuses with `cap_register_read_failed`.

### 3. Carta is the record while connected, read only here

Owner question 6 is read as A until the owner answers.

- **Venture binding.** `PUT /api/captable/carta/venture` with `{ project_id }` names the venture a founder's Carta connection is the record for.
  - It requires the venture's write gate.
  - It stores `project_id` in the connection's `config_json`, keeping the rest of the config.
  - It moves the connector's rows in all four tables to that venture, and writes one audit row (`cap_table_carta_venture_set`).
  - `{ project_id: null }` makes them account-level again. An investor Carta connection is refused.
- **The sync.**
  - Every row is written with `source = 'connector_carta'`, on the bound venture (`boundVenture`), but only while the founder's account still owns that venture and it is not deleted. Otherwise the row is account-level.
  - A count Carta does not report is null, never 0. Available pool shares are derived only when both parts are known.
- **Read only.**
  - `updateHolder()` refuses a `connector_carta` holder with 409: "This holder comes from Carta. Change it in Carta; the next sync brings it here."
  - `/live` says `carta_is_record` when the connection is active and bound to the venture read.
  - Disconnect still turns the rows into `manual`, which can then be edited.
- **Readers updated for the new source.** PITCH's deck sources (`services/decks/sources.ts`) and the old page's Carta badge now read the new source.

### 4. The exports

Each export writes one audit row in `activity_logs`, with the venture and the actor's hashed email. It is not best effort: no audit row, no export.

- **The recorded cap table as CSV:** `GET /api/captable/register/:projectId/export.csv`.
  - It is behind the venture's read gate.
  - It lists the venture's holders, with share of the recorded total and source, then its securities.
  - A missing figure is an empty cell.
  - A cell a spreadsheet would read as a formula is prefixed with an apostrophe, because holder names come from Carta and imports.
  - A reader who may not write gets no email column.
  - Audit action: `cap_table_register_exported`.
- **The PDF snapshot:** `POST /api/captable/register/:projectId/snapshot`.
  - It is behind the venture's write gate.
  - The paper reads "Cap table, as recorded: [venture]" and "As of [date]", then the holders, the securities and a line saying it is not a 409A valuation.
  - It is added to the venture's data room as `Cap table as of [date].pdf` with `visibility = 'nda'` and `access_tier = 'nobody'`, so nobody sees it until the founder shares it.
  - The file row and its audit row (`cap_table_snapshot_filed`) are one batch. If the batch fails, the stored object is deleted. With no storage bound, the answer is 503.

### 5. Not built here, and why

- **Imports as proposals.** The importer's cap-table rows (`routes/imports.ts`) still write the record directly, and still name no venture.
  - Part 2 (#2854, D1017, migration 573) builds the proposals table those rows must land in, and it is not on `main`.
  - Writing them anywhere else would put an import on the record, or invent a second proposals store.
  - Following the issue's instruction, this part builds the rest first. The import moves to part 2's `proposed` rows, with "Shares missing" reasons and changed-holder flags, once part 2 lands.
- **The spreadsheet with history.** History is part 2's read, so it waits for that read.
- **Account-level rows elsewhere.** PITCH's deck sources and the Team page still read some rows by account. They are D896's and D435's, and are left as they are.

- the venture gate skipped;
- a partial sum counted;
- a zero share for a missing count;
- the backfill ignoring the account, or dropping the security path;
- the source rename dropped;
- the Carta re-tag skipping pools;
- the binding's gate removed;
- a Carta row made editable;
- a deleted venture bound;
- Carta's missing count back to 0;
- the formula guard removed;
- emails for every reader, on the CSV and on `/live`;
- the export unaudited;
- the snapshot opened to all;
- its object kept after a failure;
- the snapshot filed by any reader;
- `carta_is_record` for any venture.

The first backfill mutation dropped the account check from the `EXISTS` clause only. That changed no answer, because the `SET` subquery still checked the account. It was replaced by dropping the check from both, which is caught.
