## D983 — Program grants part 2: three request kinds on both lanes, and HQ's answer (#2774)

- **Status:** built by S10, 2026-10-25 (#2774, part 2 of #2376, under D981). Items 1 to 3 are here. Item 4, a proposal HQ approves "for this studio only" on Programs, waits for Programs' proposals (#2788, draft PR #2871).
- **Basis:** `origin/main` at `44898068eb`, which carries D982's store (#2835, migration 553). Paths are relative to `cloudflare-worker/src/`.
- **Canvas:** "Program grants" (`design/incoming/Program Grants Page.dc.html`): GR5 and GR5d (HQ's Requests and its answer), GR9 (the studio's request sheet) and GR10 D (Decline).
- **Migration:** none. `hq_escalations.kind` has no CHECK (migration 259), and a request's fields travel in `detail` (D799).

### 1. The three kinds

| Kind | Asks HQ to | Fields | HQ's door checks |
|---|---|---|---|
| `program_grant` | grant a program | `program` | HQ offers it (D982's readiness and its "can be granted" switch); the studio does not hold it, granted or paused |
| `program_terms_change` | change one term of a program the studio holds | `program`, `term`, `asked` | the studio holds it; the term applies to the program |
| `program_end` | end a program the studio holds | `program` | the studio holds it |

- **The kinds join three lists:** `REQUEST_KINDS` and `NEW_REQUEST_KINDS` in `services/escalationRequests.ts`, and `ESCALATION_KINDS` in `rpc/hqOps.ts`. Each gets 72 hours in `SLA_HOURS`, which is GR9's "HQ answers within 3 days".
- **The programs are D982's nine keys.** `REQUESTABLE_PROGRAMS` repeats them, so the fields' rule needs no store, and the test holds the two lists equal.
- **The note is required** for these three kinds (GR9's "Why your studio needs it · required"). Every other kind keeps D799's optional note. `parseNoteFor` is the rule, on both lanes.
- **What the term stands at is never sent.** GR9 draws it as read-only. Where HQ records the request, it is read from the grant: the stored value, or "Not recorded" for a term nobody set (D797). A `current` the caller sends is refused (`program_current_not_accepted`).
- **One open request per question.** A second open request of the same kind, for the same program, is refused (`program_request_open`). For a terms change, it must also be for the same term. Another studio's request is its own.

### 2. Both lanes

- **HQ's lane:** `POST /api/licence/mine/requests` (`routes/licence_requests.ts` into `recordLicenceRequest`).
  - It checks the fields, then the program against the caller's own licence (`checkProgramRequest`).
  - It keeps D799's cap of 20 open requests per licence.
  - A refusal from the store is a 409 with its sentence; a field refusal is a 400.
- **A branch's lane:** the branch's "To HQ" lane (`routes/branch_escalations.ts`) checks the fields and the note before it calls HQ. HQ's `recordEscalation` then:
  - checks the fields again;
  - checks the program against the licence the branch's deployment runs under;
  - fills in what the term stands at.
  - It refuses a program request when the branch already has 20 program requests open, the same cap as HQ's lane.
  - A refusal comes back as `{ refused, reason }`, so the branch writes no row, as D206 has it.
- **Both lanes stay open while a licence is suspended** (D107, D112). The licence's status is HQ's to weigh when it answers.

### 3. HQ's list

`GET /api/admin/program-grants/requests[?status=]` (`routes/admin_program_requests.ts`, `requireSuperAdmin`) returns every program request, from both lanes, oldest first.
- **Each row:**
  - its kind and GR5's "Asks for" word (Grant, Change terms, End);
  - the program's key and name, the request and its note;
  - the lane;
  - the licence (uid, reference, brand, status), or `null` when the ledger has no such licence. A row is never given another licence;
  - its status, sent, due and SLA band;
  - HQ's answer, and the draft an approval left.
- **The cap:** at most 500 rows, with `complete` saying whether the list was cut.
- **A D1 failure** is a 5xx through `mapError`, never an empty list.

### 4. HQ's answer

`POST …/requests/:uid/approve { reason, terms? }` and `POST …/requests/:uid/decline { reason }` both use `requireSuperAdminWriteBar` with a reason of at least 10 characters, as part 1's writes do. The reason is the answer the studio reads.

- **The draft.** "Approving a grant request opens a draft grant" (#2774, item 3), but D982's store has no draft state: a grant is granted, paused or ended. Adding one is a CHECK rebuild of `program_grants`, which is a migration, and this part takes none. So the draft is the approved request's own record:
  - **Approving** writes the answer and appends one `program_changed` event (`action: 'request_approved'`, `request_uid`, `request_kind`, `draft`). D982 §5 chose one generic history kind so that later parts could add actions like this one with no rebuild.
    - A grant's draft is the program's defaults with HQ's terms over them, checked by part 1's `validateTerms`. This is how part 1 fills a new grant.
    - A terms change's draft is the term, what it stands at and what was asked.
    - An end's draft is the program.
  - **Nothing is granted, changed or ended here.** Grant stays part 1's write. The list carries `draft`, and part 6's "Finish grant" (GR5) opens part 1's grant with it.
- **Declining** writes the answer and appends `request_declined`.
- **Terms:** only a grant request's approval takes them. They are refused on a terms change or an end, and on a decline.
- **What held when the studio asked is checked again** on approval. If a grant was made, ended or switched off since, the approval is refused with that sentence.
- **One answer.** The answer is written only while the request is open (`WHERE … AND status = 'open'`). A second answer, or one that lost a race, is refused as `not_open`. The route also checks the status before it writes. The two guards cover each other, and the test removes both together.
- **The studio is told** as the escalation queue tells it: in the bell on HQ's tier (`noticeHqTier`), and through the branch's Worker on a branch (`deliverAnswer`). Both are now exported from `routes/admin_escalations.ts`.
- **The generic answer refuses these kinds.** `PATCH /api/admin/escalations/:uid` on a program request is a 409 (`answer_on_program_grants`), so neither the write bar nor the history row can be skipped. Every other kind is answered there as before.

### 5. The grid's two request figures

D982 left `tiles.requests_waiting` and `series.requests_by_month` as `null` with a reason naming this part. `readGrid` now reads them from `hq_escalations`:
- **requests waiting:** every open program request, on both lanes;
- **requests by month:** the current month, so far, and the five before it. Each month counts the requests sent in it, by where they stand now: waiting, approved, declined or withdrawn.
- **If that store cannot be read,** both are `null` with "Program requests could not be read. That is not the same as none." The grants still answer.
