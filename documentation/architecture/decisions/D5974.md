## D5974 — Warn on an active candidate near the merge-queue response deadline (#5974)

The new `queue-deadline` detector reuses the existing issue-backed health
episodes and durable notification intents. It opens one
`[alert] merge queue candidate nearing response deadline` issue while at least
one current native candidate is near its deadline. Slack receives only open
and recovery transitions. Repeated observations update the reporter log and
job summary; the issue/notification text is the opening snapshot with its run
link. This is a warning, not a new queue breaker or a retry/setting change.

### Source, clock and unknowns

The deadline comes from main's live merge-queue rule via the existing
`queueDeadline()` helper, not another copy of 90. The warning defaults to
`QUEUE_DEADLINE_DEFAULTS.warnShare` (80%); optional repository variable
`QUEUE_DEADLINE_WARN_SHARE` overrides it with a value greater than zero and at
most one. An open warning uses the configured share multiplied by the
source-defined clear/warn ratio (70/80 by default), so hovering around the
warning boundary does not flap. Required-check names and integration IDs also
come from the live rules. A completed required check is finished, whatever
its conclusion; failure detection remains with the existing detectors.

The injected-clock pure `queueDeadlineState` accepts merge-group runs, current
native queue head SHAs, required checks and per-head check runs. It names
pending checks. A near-deadline head whose checks cannot be read names each
required check as unknown/unreadable, never healthy. Missing membership,
missing request time, invalid configuration or globally incomplete evidence
cannot close an open episode. Cancelled runs, replaced/removed heads and
candidates whose required checks all finished do not warn.

`scripts/lib/queueDeadline.mjs` reads native `mergeQueue.entries.headCommit`
and PR numbers with cursor pagination, current CI merge-group runs and the
latest paginated check runs. It re-reads membership after check sampling,
drops removed heads and refuses a newly appeared, unsampled head. Each API
read is bounded; over-limit inventories are unknown, not truncated success.
See [GitHub's MergeQueueEntry reference](https://docs.github.com/en/enterprise-cloud%40latest/graphql/reference/pulls#mergequeueentry).

### Cadence, budget and shared integration

The job joins the existing five-minute `2-57/5 * * * *` schedule; manual
`check: queue-deadline` is also available from main only. No live dispatch is
performed by this issue. With five built candidates and single-page reads,
the evidence phase uses nine API requests per poll (rules, two membership
reads, one run listing and five check lists), about 108/hour. The source caps
are three membership pages per read, three run-list pages, ten candidate
heads, and two check pages per head: at most 30 evidence reads per poll,
360/hour. Existing issue lookup/persistence and transition delivery are
additional, paginated costs; this is not a whole-workflow API bound. Empty
queues use rules and one membership read. Scheduled Actions may be delayed,
so this is not a guarantee of notification before expiry. Activation and
required-check configuration stay with the owner. #5719 is closed at the publication check; no live notification rehearsal was dispatched.

The owner explicitly authorized the scoped #5663 handoff for
`health-alert-episodes.mjs`: one bounded sanitized `deadlineCandidates` field
survives persistence and notification retries. It contains public SHA, PR,
age and pending-check names only. No token, raw issue text or arbitrary URL
is retained. Existing detectors and their on-call meaning are unchanged.
Transport/persistence errors still fail visibly as the framework requires;
the presence of a warning does not fail the monitored candidate or alter CI.

### Validation and rollback

Synthetic tests cover no candidates, one pending named check, completed,
cancelled, removed and replaced candidates, unreadable jobs, required-check
source matching, hysteresis, incomplete pagination, native-membership recheck,
sanitization and durable open/repeat/unknown/recovery delivery. Removing the
pending-check name must fail the regression. No live GitHub/Slack write,
production access or workflow dispatch is used by tests. Roll back the new
mode/job and field to remove the detector; existing incident records and
acknowledged intents are retained. Runtime source is the repository's Node 22
and existing health framework; no additional credential or bypass is added.
