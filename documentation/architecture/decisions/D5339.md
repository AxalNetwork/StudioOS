## D5339 — Guard the production Advisor boundary, not provider vocabulary (#5339)

The old `no-anthropic-in-prod` script grepped every Worker TypeScript file for Anthropic tokens. It was neither invoked by CI nor compatible with D851's deliberately present, default-off provider adapter, so the documented security control failed on main and proved no production reachability property.

The production rule is now structural. Every Personal Advisor entry (`routes/advisor.ts`, its cohort/audit helpers, and all `services/advisor/` modules) is walked through relative TypeScript imports. Reaching `services/aiProviders.ts` or any module under `services/ai/providers/` is a failure. The Workers AI router remains allowed. Separately, Anthropic endpoints, model identifiers and key names may appear only in an explicit reviewed allowlist: the dev assistant and its exposure fields, plus D851's catalogue, execution service and adapter. There is no marker-based escape hatch, and a stale allowlist entry fails.

The guard also reads `src/index.ts` and requires the `/api/assistant/*` middleware to precede the assistant mount, refuse both production stage spellings, require `ENABLE_ANTHROPIC_DEV` to equal `1`, return 404 while closed, and advance only after those checks. `npm run test:guards` now invokes it, so every full drift run exercises the control.

This changes no provider switch, model eligibility, Advisor task, production route or stored record. Synthetic-tree tests prove the current shape passes and mutation-check both forbidden import families, the D851 allowlist, a new endpoint/key reference, and removal of the assistant flag check.
