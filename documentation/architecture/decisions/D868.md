### 1. One harness for both channels' readiness checks

`test/_channel_readiness.ts` is the shape #2529 (D861) wrote for WhatsApp, moved out so both checks use it:
- each gate is `(environment, api) => Promise<void>`;
- `runReadiness` runs every gate on an isolated D1 fixture for development, preview and production;
- each mutation rewrites one line of a `services/channels/` module, imports the rewritten copy (no tracked file changes), and must fail its gate, while the restored code passes it.

`whatsapp_readiness_d861.test.ts` now calls `runReadiness`. Its gates and its 14 mutations are unchanged.

### 2. Telegram's gates

`test/telegram_readiness_d868.test.ts`, 39 tests: 8 gates × 3 environments, 14 mutations, and the webhook-order check.

| Gate | What it asserts | Mutations that must fail it |
| --- | --- | --- |
| `secret` | `verifyTelegramSecret`: `ok`, `mismatch`, `missing`, and `unconfigured` when unset | a mismatch accepted; a missing header accepted; unset failing open |
| `notesConsent` | an assigned chat's text flows while consent is awaiting, declined or withdrawn (D684), but no note is queued until the contact's YES (D756 §1.5) | the YES check removed from `queueVoiceTranscriptions` |
| `voiceSize` | a note declared over 5 MB makes no Bot API call; one declared at 5 MB whose `getFile` says more is refused after `getFile`, before any download | either size check removed |
| `videoNotes` | `TELEGRAM_VIDEO_NOTES` is false, and a round video makes no call | the flag switched on |
| `voiceCap` | 50 notes a day per connection, the next day free again, and a counter that cannot be read refuses | bypassed; denying all |
| `purge` | a pending Telegram chat goes after 30 days, not 29 or 31 | too late; too early |
| `encryptedText` | message text is stored as `v1.` ciphertext and decrypts to itself | stored plain |
| `rollout` | `canary` (and anything unknown) admits Super Admins only, `off` nobody, `on` everyone | open to everyone; closed to everyone |

The caps are written as their published values (5 MB, 50, 30 days), never read from the implementation's constants, so a changed constant fails the check.

**The webhook order** is checked through the real router (`routes/channels.ts`):
- a missing or wrong secret answers 401, and an unset secret answers 503;
- in each case, a body stream that counts reads is never read.

That module sits outside `services/channels/`, so its mutations were run by hand on this branch, and each failed the test:
1. reading the body before the check;
2. dropping the 401;
3. dropping the 503.
