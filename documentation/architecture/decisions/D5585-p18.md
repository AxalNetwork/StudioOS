### 1. What an origin is

`normaliseSiteOrigin` accepts `https://` and a DNS host name of at least two labels, with an optional port. It refuses:

- a path, query, fragment or user information;
- a wildcard;
- an IP literal;
- port 443 (it is the default, so `https://host` already names it), port 0, a port with a leading zero, and any port
  above 65535;
- `http://`, because a record read over plain HTTP could be changed on the way.

Upper case is folded to lower case, and a trailing `/` is dropped. A CHECK in the table keeps a stored origin `https`,
lower case and path-free, so no other writer can store one the route would never match.

### 2. The list

`work_graph_release_site_origins` holds one row per change to one company's list: an `allow` or a `remove` of one
origin. The list is each origin whose latest row is an `allow`. Every change is kept, with who made it and when.

- `seq` numbers one company's rows. A trigger requires each row to be the next one, and the writer names the list
  `seq` it saw. The insert is conditional on it, so two Super Admins editing at once cannot both land.
- UPDATE and DELETE are refused.
- At most `SITE_ORIGIN_LIMITS.perCompany` (20) origins are listed at once.

`POST /api/admin/work-graph/releases/site-origins` takes `{ tenant_id, company_id, op, origin, expected_seq,
idempotency_key }`. It is gated by `requireSuperAdminWriteBar`.

| Case | Answer |
|---|---|
| bad op, bad seq, no key | `malformed` (400) |
| not an origin (§1) | `site_origin_invalid` (400) |
| the company's release records live under another tenant | `wrong_tenant` (403) |
| another `seq` | `stale_site_origins` (409), with `current: { seq, origins }` |
| allowing a listed origin | `already_allowed` (409) |
| removing an unlisted one | `not_allowed` (409) |
| allowing past the limit | `site_origin_limit` (409) |
| a reused key | `idempotency_conflict` (409) |
| a replay | the first answer |

Every attempt is an admin audit row. `GET /site-origins` returns:

- the list, oldest allowed first, with who allowed each origin and when;
- the list's `seq`;
- the last 100 changes, newest first;
- `people`, the names of who made them, never an email.

### 3. The public route

`GET /api/public/release-sites/:tenant/:company/:site` reads the list after the flag check, and only when the request
names an `Origin`. Then:

- `Vary: Origin` is set on the answer.
- When that exact origin is on the list of the tenant and company in the path, the answer also carries
  `Access-Control-Allow-Origin: <origin>`.
- This applies to every answer, a refusal included, so the site can tell `withdrawn` from `not_found`.

Anything else gets no CORS header, and a browser then refuses to give the page the answer. That covers:

- an origin that is not listed;
- a spelling a browser never sends (upper case, a trailing slash);
- another company's list;
- a list that cannot be read.

`Access-Control-Allow-Credentials` is never sent. The route sets no cookie and reads no session, so there is nothing a
credentialed read could add.

`OPTIONS` answers a preflight with 204. For a listed origin it adds `Access-Control-Allow-Origin`,
`Access-Control-Allow-Methods: GET` and `Access-Control-Max-Age: 600`; anything else gets no CORS headers. With the
flag off it is 404, before D1 is read, as the `GET` is.

The record stays `no-store`. Removing an origin takes effect on the next request.

### 4. Cost

The public route adds one indexed statement, only for a request that names an origin it could match. The admin read
uses three statements and the write a few, each bounded.

### Rollback

Revert the Worker. The table stays and nothing reads it; the public route then sends no CORS headers. The forward fix
re-creates the table's guards after a manual recovery. A rollback itself needs none.
