## D6027 — Build Overview V2, Worker read: next action, needs attention and plan preview (#6027)

**Source.** The approved Build v2 canvas landed in #5858
(`design/incoming/Build v2 Page.dc.html`, `Build v2 · Boards.dc.html`):
BD1 (desktop overview: one Next card, a status strip with sources, Needs
attention limited to material blockers, a Build Plan preview) and BD2 (phone:
the next action, then attention and the plan). The pattern is Grow's
(#5775, commit `870402c7ee`, D4862 part 2): stored evidence only, a failed
source named as unreadable, actions for writers only. No sample venture,
name, date or count is copied from the canvas.

**What `GET /api/cycles/build/overview` adds.** Three parts beside the
existing figures, cards, focus, meter and index:

- `figures[].module`: each figure's source module slug (Must-haves and Days
  to the MVP → `prototype-mvp`; Shipped → `product-roadmap`; Systems →
  `operating-systems`).
- `plan`: the venture-scope Build Plan (the one `/build/plan` opens): its
  status, accepted and waiting counts, and the first three waiting proposals
  (`uid`, `title`, `kind`, `module`, `module_label`) in the plan's own order
  (module, then item key). Read from `build_plans`, `build_plan_items` and
  `ai_rail_proposals`, the stores `buildPlanner.ts` and `buildPlanState.ts`
  keep. `state` is `ready`, `not_recorded` (no plan prepared), `restricted`
  (not the founders' or an admin's, as D1065's read gate decides; nothing
  about the plan is revealed) or `unreadable`.
- `attention`: material blockers only, each `{ key, tone, title, detail,
  module, href, action }`, in BD1's order: a failing (or no longer connected)
  core system or tool, blocked or overdue must-haves, a filing overdue or due
  within 30 days, the MVP date not recorded, Build Plan proposals waiting for a
  decision (not while the plan is paused: a paused plan takes no decision).
  `href` is always the record's page; `action` is the write that clears it
  and is null for anyone who is not a writer. A source that could not be read
  adds its own "could not be read" item and is listed in `unreadable`; `state`
  is `ready`, `partial` or `unreadable`. An empty list with `state: ready` is
  the only "nothing needs attention".

**The focus** (`services/cycleFocus.ts` `buildFocus`) replaces rule 2
(`connect_tools` for any venture short of five core systems) with the
canvas's order, for a writer: (0) nothing in Build recorded: Add the first
feature, unchanged; (1) `set_mvp_date`; (2) `unblock_must_haves`; (3)
`filing_due`; (4) `review_plan`; (5) `reconnect_tool`; (6) `connect_tools`
only when the current step (the first card with a next) is Operating systems
waiting on its first connection. A rule fires only on a recorded fact. When
none fires and a source a rule reads could not be read, the focus is
`unavailable` with no cta, never the card rule. Anyone else gets the card
rule, as before. Desktop and phone read the same `focus` object; there is no
second one.

**Where the facts come from, and the cost.** Focus and attention share one
pure step (`services/buildAttention.ts` `buildSignals`) over the module reads
the overview already holds. Blocked must-haves are D6031's `blocked` fact, a
group Prototype / MVP's grouped statement already returns. Overdue must-haves
(not Done, a due date before today, UTC) are a scalar subquery of that same
statement, a range over D6031's `idx_mvp_features_must_due`, so only
must-haves dated before today are read (`due_date < today` equals comparing
the first ten characters with today's). The next open filing and the failing
system or tool were already computed for their cards and are now also facts
(`next_filing`, `reconnect`). The plan preview is one new statement. No
migration.
