## D5247 — Each Security store records its last good read, and is Stale past its own age (#5247)

Date: 2026-11-10 · Slot S25 · Parent #4559 · Related #4800, #4803, #5129

### 1. The problem

The Security Overview (D4800) reads eight stores: `security_events`, `admin_audit_log`, `activity_logs`,
`impersonation_sessions` and `licence_events` (the ledger, on `/governance`), and the D1 backup heartbeat, the
restore-drill marker and the sanctions screenings (on `/overview`). None of them recorded when it was last read
successfully. "Observed" and every "Read HH:MM UTC" were the moment the browser received the answer, so the
vocabulary's **Stale** state could never apply (D4800 §5, first bullet; this decision replaces that bullet).

The owner answered #4800's questions B and C on 2026-11-09:

- **C1:** record a last-successful-read time per store.
- **B2:** a store is Stale past its own age, not one age shared by every store. The backup heartbeat's is about
  26 h. Sanctions screenings have none, because they run on request only. The rest are set here, from how often
  each store is written.

### 2. The record

A small table, `security_source_reads` (migration `202611101036_security_source_reads.sql`), one row per store:

| Column | Meaning |
|---|---|
| `source` | The store's key, as `sources[]` names it |
| `last_read_at` | The last time a Security read of the store answered. Written only on success, so a failed read never moves it |
| `evidence_at` | For a store aged from its own evidence (below), that evidence's stamp as of the last good read |

It is a table rather than a column on each store: the stores are ledgers, an R2 object and a marker, and none
should change shape to say when HQ last read it. It is not a `system_metrics` row either: those rows are pruned
and are time series, while this is one current value per store.

`services/securitySourceFreshness.ts` reads it, computes each store's freshness, and records the reads that answered
in one batch. Recording is best-effort. A failed write never fails the read it follows. If the table cannot be
read, every recorded time comes back as Not recorded, and nothing is invented in its place.

### 3. The ages

Each store's age runs from one of two clocks, named per store as `age_from`:

- **`last_read`**: the age runs from the last time a read of the store answered. A ledger written about once per age
  has probably gained rows since a last good read older than that age.
- **`evidence`**: the age runs from the store's own stamp. A successful read of an old heartbeat is not a recent
  backup, so the read time says nothing here.

| Store | Age | From | Why |
|---|---|---|---|
| `security_events` | 6 h | last read | Written at the auth boundary on every refused sign-in, step-up and gate refusal: several times a day |
| `admin_audit_log` | 24 h | last read | Every admin write logs a row through `logAdminAction` (several hundred call sites); HQ writes it every working day |
| `activity_logs` | 24 h | last read | The admin-side rows the ledger reads (role changes, account switches, KYC decisions, contract void and resend) land on most working days |
| `impersonation_sessions` | 7 days | last read | A row only when support opens a session on a member's account: a few times a week |
| `licence_events` | 7 days | last read | A licence's issue, re-term, renewal, suspension, reinstatement or termination: weekly, not daily |
| `backup_d1` | 26 h | evidence (recovery point) | The owner's ~26 h. It is `BACKUP_STALE_AFTER_HOURS`: the daily export's 24 h recovery point plus two hours to run |
| `backup_kv` | 26 h | evidence (recovery point) | The daily KV snapshot cron, on the same window |
| `restore_drill` | 32 days | evidence (marker) | `DRILL_STALE_AFTER_DAYS`: the longest gap between two monthly runs |
| `sanctions_screenings` | none | — | The owner's answer: screenings run on request, so no age makes the store out of date |

The two evidence ages are the constants `services/backup.ts` already applies to the heartbeat's and the drill's own
`fresh` flags, imported rather than copied, so the source row and the card cannot disagree. `SOURCE_AGES` is kept in
key order (D4134). A new store is one line, and the test fails a store with no reason.

### 4. What the reads return

Each store a read touched gains these fields:

- `answered`: whether this read of it succeeded;
- `last_read_at`: the last good read, this one if it answered;
- `evidence_at`: the evidence stamp, for an `evidence` store;
- `last_good_at`: the time the age runs from;
- `age_hours` and `age_from`;
- `basis`: the sentence in the table above;
- `freshness`: `current`, `stale`, `not_recorded` (no good time exists: never 0, never "now", never Stale) or
  `no_age` (sanctions: never Stale).

`/overview` adds a `sources[]` for the seven stores it reads: the evidence stores, plus `admin_audit_log`,
`impersonation_sessions` and `security_events` for its own counts. `/governance`'s existing `sources[]` rows gain the
same fields for the ledger's five stores, and keep their own `table` key. A store that a filter on Events did not
read is not in that reply and is not recorded. A heartbeat or marker counts as answered when R2 answered. A
heartbeat that was never written, or is no longer valid evidence, keeps the last valid evidence time. The page then
still says how old the last good backup is.

### 5. The Overview

`overviewModel.js` folds both replies into one row per store. When both reads touched a store, the later last good
read wins, which is the read that answered whenever one did.

- **Stale is said where the store is drawn.**
  - A store past its age that answered (an old heartbeat) is its own **Stale** finding, with its last good time,
    its age, the reason for that age, and "This is not a claim that nothing is open".
  - A store that did not answer already has its **Unavailable** finding, so Stale is added to that finding's
    detail. One store is never two items.
  - The restore drill's existing out-of-date finding stands for its own store.
- **Cards.** An area card fed by a Stale store says so. A card that would read Healthy, Verified or Measured zero
  becomes **Stale**. A card already in a worse state keeps it. Its freshness line names the Stale store either way.
- **Never "nothing open".** A Stale finding counts as open. "Nothing needs action" and "n of n sources read" are
  never drawn while any store is Stale.
- **Source details.** Each row shows its last good read or evidence and its age: "Last good read 2026-11-10 12:00 UTC
  · age 6 h", or "Stale · last good evidence …, 30 h ago; its age is 26 h". "Last good evidence: Not recorded" means
  no time exists. Sanctions read "no age: it runs on request". The evidence stores are listed under the ledger's
  five, and a Stale store is named in the summary line.
- `SEVERITY` gains `stale` (after Unavailable). The drill's `stale` finding had been sorting as `NaN`.

**Vocabulary.** The words are Security v2's existing `stale` state (`securityStates.js`, SE02: "Last good evidence
is older than its threshold"), not a new one. #5129, the one platform state vocabulary, is still at the canvas stage
(S1's brief, 2026-11-10). That brief draws Stale as a modifier that always shows its age and last good time, and
"Age not recorded" where no time exists. This build follows it: every Stale line carries both, and a store with no
time says Not recorded. When #5129's shared `StateChip` lands, the badge here moves to it, and the model's
`freshness` field already carries what the chip needs.

### 6. Tests

`cloudflare-worker/test/security_source_freshness_5247.test.ts`, 11 tests:
- **One store per age rule.**
  - Aged from the last read (`security_events`, 6 h): current, Stale and Not recorded.
  - Aged from evidence (`backup_d1`, 26 h): Stale even when the read answered, and with R2 down.
  - The restore drill's window.
  - No age (`sanctions_screenings`): never Stale after 400 days.
- **The table.** Every store has a rule and a reason, in key order, and only sanctions has no age.
- **The routes.**
  - `/overview` returns the seven stores and records the good reads.
  - A failed read never moves the last good read, and turns Stale only past its age.
  - An unreadable bucket keeps the last evidence.
  - `/governance`'s rows carry the fields, with licence events aged a week.
  - An unreadable record table costs the times, never the page.
  - An invalid heartbeat keeps the last valid evidence.

`frontend/test/security_source_freshness_5247.test.mjs`, 8 tests:
- the all-current baseline, which alone says "Nothing needs action";
- a failed ledger store past its age: Stale inside its Unavailable finding, one item, the events card keeps
  Unavailable and names the Stale store;
- an old heartbeat: its own Stale finding, the Recovery card Stale, the Resilience tab marked, and never "Nothing
  needs action";
- sanctions never Stale;
- Not recorded, never 0;
- the source details and the Stale summary line;
- a Stale row keeping "n of n sources read" out of Checked and clear;
- the merge of the two replies.

**Mutation check.** A script broke 17 guarded lines in turn and restored each. 15 were caught:
- Stale and current swapped;
- sanctions given an age;
- the evidence clock replaced by the read clock;
- a missing time read as current;
- a failed read taken as now;
- `sources[]` dropped from `/overview`;
- the freshness fields dropped from `/governance`;
- the Stale finding never pushed;
- Stale dropped from an Unavailable finding;
- the "n of n" guard removed;
- Verified left over a Stale store;
- `no_age` read as Stale;
- "Not recorded" written as 0;
- a second item for one store;
- the merge keeping the first row.

The two misses are equivalent mutations, kept in the code as stated intent:
- Recording a failed read writes back the recorded time unchanged.
- Dropping the `COALESCE` that keeps the last valid evidence changes nothing, because the evidence value written is
  already the recorded one when this read found none. The test still pins the outcome.

Existing suites that read `admin_security.ts`, `overviewModel.js` or `SourceAvailability.jsx` pass unchanged: 19
worker files (238 tests) and 19 frontend files (211 tests). The `/overview` reply is built as one object and then
extended, so every source-text pin on its fields (`hq_security`, `security_resilience_ai_4803`) still holds.

### 7. Not done, and unverified

- **A store's own write cadence is not measured.** The ages above come from reading the writers' code, not from
  production row rates (production D1 is read for schema and aggregates only, and this session cannot reach it). The
  owner can change any one of them by editing one line of `SOURCE_AGES`.
- **No browser pass.** Layout at phone width and dark mode are checked against class names only. #5249 and #4803's
  browser pass touch the same Overview files. This change is confined to the model, the source disclosure and one
  note in `SecurityPage.jsx`, so either can merge first and the other rebases.
- **"Observed" is unchanged.** It is still the browser's receive time, and it is labelled as that.
- **GET writes.** `/overview` and `/governance` now write one small batch per load to record the good reads. Both are
  Super Admin only, and recording a read is the decision (C1), so the write is the feature. It is best-effort and
  never fails the read.
