## D4685 — Pipeline drafts and writes stay dependable (#4685)

- **Status:** S14, 2026-11-07 (#4685; order 3 of 6 in the 6 November 2026 `/pipeline` audit series). Frontend only. No Worker route, no migration and no new API method: every call below already has its Worker route.
- **Basis:** the audit was pinned to `d85951ca9`. Each problem was re-read on `1ee5b2c41` (origin/main) before anything changed, and each was then reproduced by a mounted test run against the old code (the "mutation" column below puts the old code back and watches the test fail).

### 1. What reproduced on current main, and what changed

| # | Audit claim | On `1ee5b2c41` | Change |
|---|---|---|---|
| 1 | The studio board stage mover reads its prior stage from a value assigned inside a `setDeals` updater, so a deferred updater moves the card without sending the write | **Reproduced.** `moveDealToStage` set `fromStage` inside `setDeals(curr => …)` and returned when it was still null. Two drops in one event turn sent one request, and the second card moved on screen with no write behind it | `PipelinePage.jsx` keeps `dealsRef` beside `deals` (`writeDeals` sets both). The deal and its prior stage are read from the ref before any state changes; no updater assigns anything. The mover resolves `true` or `false` and never throws, so drag, the drawer and Try again all learn the outcome the same way |
| 2 | Several partner mutations swallow failures and the caller clears or closes the draft | **Reproduced** in all four Pipeline zones. Each `run` caught the error, printed a note and resolved normally. Leads closed and cleared the pass editor, Negotiations closed the term editor and the new-term form, Proposals cleared the version draft, all after a failed write | `usePipelineZone.js` (new): `run` resolves `true` only after the server accepted the write. Leads, Negotiations and Proposals clear or close only on `true` |
| 3 | A full loading-state refresh unmounts editors, so saving one record discards unsaved work in another | **Reproduced** in the four zones (`load` set `loading: true` on every call, and `ZoneBody` swaps the whole zone for a skeleton), in the board (`reload` did the same) and in the deal drawer (`load` replaced the tabs with a skeleton after every save). Also found: `RetainerForm` and `TermRow` reset their fields whenever their record was a new object, which every refresh makes | The skeleton shows only while there is nothing to show. A later load is a background refresh; a refresh that fails keeps the last good rows. `RetainerForm` and `TermRow` reset on the record's values, not its identity. The drawer keeps its tab and open forms while it refreshes |
| 4 | Proposal history inspection and version editing share target state, so a draft can be submitted to the wrong proposal | **Reproduced.** One `openTrail` was both the History panel and the version form's target, and one `draft` object served every proposal. Pressing History on row B retargeted a half-typed version for A to B | `ProposalsZone.jsx` has `historyId` and `editId`, independent, and drafts keyed by quote id. The submit reads its target and text at click time and, on success only, clears that one proposal's draft. The note is scoped `version:<id>` |

### 2. Found while fixing them

- **A stale read could undo a confirmed move.** A board reload that began before a move and landed after it overwrote the confirmed stage. A move now invalidates reads that began before it and during it.
- **A failed drag-drop was an unhandled rejection.** The mover threw and the drop handler did not catch.
- **Drawer writes swallowed failures.** Add Task, a task's status and Capture Snapshot had no `catch`; they now keep the form and say so.
- **Raw server text was rendered** in the board's move error, the drawer's error line and the four zones' notes. Each now reads one fixed sentence. A zone's load error keeps the one distinction a person can act on, "No partner profile", by name.
- **Stale drawer reads.** A detail response for a deal the drawer had left could overwrite the one on screen; reads are now numbered and the late one is dropped.
- The same swallow-and-clear pattern is in the Delivery, Offers, Research and Advisor zones (the `grep "setNote({ ok: false"` list). They are outside this issue's Pipeline scope and were not touched.

### 3. Behaviour

- **A move is optimistic, and only confirmed moves stay.** The card moves at once and shows its saving mark. If the write fails it goes back to the column it came from, and the page says `Could not move "<name>" to <stage>. It is back in <stage>.` with a Try again button (44px) and a dismiss. There is no browser alert, confirm or prompt.
- **One write per deal and per zone at a time.** A second call while one is in flight resolves `false` and sends nothing.
- **A write that succeeded but whose refresh failed** still says it saved, and adds that the list did not refresh.
- Anything new carries `dark:` classes. No new surface says "advisor", "advice" or "Fill".
