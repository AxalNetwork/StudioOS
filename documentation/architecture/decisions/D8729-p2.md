## D8729 part 2 — the founder Studio opens on the active venture and its next action (#8729)

Part 1 is `D8729.md`: the canvas (`design/incoming/Studio Home Founder Page.dc.html`, boards SFD00 to SFD16) and the three questions it left to the owner. On 2026-11-27 the owner took **option A on all three**: Q1 A, two ventures and none selected, Studio asks which; Q2 A, the Next card follows the layout order of the placed modules; Q3 A, on the phone Eadwyn is a collapsed row under the Next card. This part builds the canvas on that basis, at 1440 and at 390 × 844. It is frontend only: no Worker route, no migration, no new store.

- **Status:** built. Every acceptance point of #8729 is met by the code and pinned by `frontend/test/studio_founder_venture_8729.test.mjs`; the departures from the canvas are listed below.

### What was built

- **The venture is the first heading, on both widths** (SFD03, SFD12A, SFD14). `StudioVenture.jsx` `VentureHeader` draws the eyebrow "Studio · your venture", the h1 with the venture's name, Switch venture, the Lab phase badge and the founder line; on desktop Customise sits on its right. On the paths with no venture the h1 is "Studio" (first venture, the chooser, a failed projects read) or "Venture not available" (D4619). Inside the multi-licence Studio, whose page owns the h1, the same heading is an h2 (`level`). The phone's Eadwyn bar (`StudioPhone.jsx`) is no longer a heading.
- **The Next card** (SFD03, SFD11). `founderNextModel.js` `nextStepsOf` lists the placed modules' own `card.next` from their cycles' overview reads, in the member's layout order (Q2 A), then Eadwyn's waiting questions when Eadwyn's questions is placed. The first venture task is the page's one primary (`sm-btn-p`), named with its venture ("Add feature to Atlas Orchard"). States: loading while the layout or any placed cycle's read is out, holding the card's height so the primary does not jump; unreadable when no module named a step and a cycle's read failed ("This is not a sign that nothing is waiting", Try again, Open Build for the venture); none when every module was read and named nothing (Add modules opens the Artifact map).
- **Eadwyn comes after the venture work.** On desktop it is the section under the Next card (`aria-label="Eadwyn AI"`). On the phone it is a collapsed row (Q3 A: "Eadwyn AI · Today · <venture> · <n> questions waiting", Open) with the chat under it, mounted while hidden so its thread and availability read are kept; a `?tab=` or the ticket form opens it. The phone order is venture, Next, Eadwyn's row, strip, profile, modules, so the venture and its task are inside the first 390 × 844 screen.
- **Every link keeps the venture** (SFD07). A task link is the module's canonical address for the venture Studio shows (`studioTaskLink`: `?project=<id>` becomes `?project_id=<id>`, and `&add=1` becomes the module's `/new`), and a link naming another venture is not followed. `StudioTaskLink` pushes it with `state: { under, focus, ventureId, venture }` after stamping Studio's own history entry with `focus`, so CycleRoute's `closeAdd` (Cancel, Esc) and the browser's Back land on Studio in the same venture and `useReturnFocus` puts focus back on the control that left. The tile's own next step goes the same way (`CardBody`'s new optional `nextLink`), and the tile's Open link carries `?project_id=` (`spec.search`, `withVenture` in `StudioModuleTile.jsx`).
- **The venture is resolved, then written** (SFD04, SFD08). `founderStudioReads.js`: the address, else the switcher's pick on this device (`activeProject.js`) when it is one of the member's ventures, else the only venture, else a choice (Q1 A): the venture read settles as `chooseProject(n)` and nothing venture-scoped is read. An address naming no venture of theirs is still unavailable and never swapped (D4619). The home writes a venture it resolved itself to the address with replace, and that write does not start the reads again. A pick in the shell switcher while on `/studio` writes its venture to the address. A venture switch moves focus to the h1.
- **Separate paths** (SFD08 to SFD10, SFD12E, SFD12F). First venture: "Start your first venture" with Create your startup (`/build?new=1`) and Go to Eadwyn. Two ventures, none selected: "Which venture are you working on?" with each venture as a link into Studio. Projects read failed: "Your ventures could not be read. This is not a sign that you have none." with Try again. Unavailable: the notice now offers the member's own ventures by name; "Open your Studio" is kept only when that list is empty or unreadable.
- **The Add feature dialog is kept** (SFD05, SFD12C), its fields and its disabled submit unchanged; opened from Studio, its first line names the venture: `FormLightbox` takes `venture`, and CycleRoute passes the name from history state only when `state.under` is set and `state.ventureId` is the venture in the address.
- **Customise is kept** (SFD13): the grid's handle, Space, arrows, live announcement, size radiogroup, ⋯ and × are untouched. The venture header and the Next card are not tiles; the Next card dims with the fixed blocks while the grid is edited.

### Departures from the canvas

1. **Switch venture opens the shell switcher that is on screen** (the sidebar's, or the phone header's pill, by `data-company-switcher`, as `/company-settings`' Switch company does) rather than a copy of its list; only when none is on screen does it draw the member's ventures in place. Focus on closing the switcher is the switcher's own, not returned to Switch venture as SFD14 asks.
2. **The switcher does not follow the address** (SFD08 B). Studio writes no pick: the projects read carries `company_id`, not the company UID the switcher's store needs, and a wrong company would mislabel the sidebar. The address still wins on screen. The chooser's line drops "and your switcher remembers it on this device" for the same reason.
3. **While a venture is still to be chosen** the venture zones (strip, tiles) say Unreadable with "Choose a venture to see its records.", as the unavailable path does; SFD08 A draws only the chooser.
4. **The primary is the first venture task** in layout order: Eadwyn's questions row is never the primary, even when that module is placed first.
5. **The primary's label is the module's own `next.text`** ("Link 2 features to a pain theme or hypothesis"), where SFD03's second venture shortens it to "Link features".
6. **No date** in the venture header, and no "Read <date>" on the none-waiting state.
7. **The phone keeps `StudioPhone`'s sticky Eadwyn bar** (with its tab label and menu), no longer a heading, above the body; SFD12A draws only the shell's top bar.
8. **The dialog's venture line is its eyebrow** (above the title), not its `aria-describedby` description.
9. **The strip is a list labelled "Summary"**, not an h2; the profile keeps its h3.

### Left out

- The optional Worker change (#5074, card links with `?project_id=`): Studio rewrites the address itself, so nothing depends on it.
- A real-browser check at 390 × 844: the first-screen order is pinned by DOM order in the tests, not by a measured layout. No screen here has a visual baseline, so none was changed.
