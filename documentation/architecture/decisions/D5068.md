## D5068 — Build module links preserve the venture and stop generating legacy roadmap routes (#5068)

- **Status:** built under slot S04, 2026-11-09 (#5068, 5 of 5 of the Build modules audit, part of #4846).
- **Number:** D5068 is this issue's number (D4106). No migration.
- **Files:** `cloudflare-worker/src/routes/cycle_build.ts` (the Founding team and Product roadmap cards' `next`
  hrefs); `cloudflare-worker/src/services/records/build.ts` (the Founding team `edit-split` action and the
  Company creation `Incorporation` linked row); `cloudflare-worker/test/cycle_new_venture_d688.test.ts`,
  `cloudflare-worker/test/cycle_records_build_d690.test.ts`, `frontend/test/cycle_new_venture_d688.test.mjs`.

### 1. The bug

Three links generated by Build read no venture from the card or record that built them:

- The Founding team card's empty state ("Add founder") linked to the bare `/raise/cap-table`.
- The Founding team record's "Edit split" action linked to the bare `/raise/cap-table`.
- The Company creation record's Lab-linked "Incorporation" row linked to the bare
  `/raise/legal-engine/incorporation`.
- The Product roadmap card's empty state ("Add item") linked to `/build/roadmap?project_id=<id>` — the legacy
  alias `railPages.js` already annotates as "The legacy Roadmap zone of the same module", not the canonical
  `/build/product-roadmap`.

Each of the first three opened whichever venture `CycleRoute`'s `useProject` fell back to (the founder's own
venture, or whatever the page had kept from an earlier redirect) rather than the venture whose card or record
the member was looking at — wrong whenever they hold more than one venture.

### 2. The fix matches each destination's own existing param, not a new one

`cloudflare-worker/test/cycle_new_venture_d688.test.mjs` and `frontend/src/pages/cycles/CycleRoute.jsx`'s
`useProject` document the split already live in the codebase: *"The read's own links (`next.href`) say
`?project=`; the page's own say `?project_id=`. Either picks the venture."* Both are read, so there was no
ambiguity to raise to the owner — only which existing family a given href belongs to:

- **Founding team's `card.next` href** (cycle_build.ts) is exactly a read's own `next.href`, so it now reads
  `/raise/cap-table?project=${p.id}`, matching `next()`'s own output for this file's other cards and
  `raiseCycle.ts`'s equivalent `teamReadiness` next step to the same destination (already `?project=`, D1262
  test `raise_evidence_fixes_d1262.test.ts`).
- **Product roadmap's empty-state href** now goes through the file's own `next()` helper instead of a
  hand-written string, so it reads `/build/product-roadmap?project=${p.id}&add=1` — the canonical module, in the
  same shape every other Build card's "Add X" link already uses (`add=1` opens `CycleRoute`'s add flow directly,
  per `cycle_new_venture_d688.test.ts`'s existing `?add=1` coverage).
- **`Edit split`** (build.ts, a `RecordAction` of `kind: 'link'`) now reads `/raise/cap-table?project_id=${ctx.projectId}`,
  matching the one other cross-module `kind: 'link'` action in the records services, `raise.ts`'s
  `manage-access` (`${DATA_ROOM_ACCESS}?project_id=${rc.projectId}`).
- **The Incorporation linked row** (build.ts) now reads `/raise/legal-engine/incorporation?project_id=${ctx.projectId}`,
  matching `raise.ts`'s own `raiseHref` helper — "A module page or a record, addressed as D696's routes are, the
  venture kept" — which addresses every `/raise/...` destination with `?project_id=`.

No param name is invented; `CycleRoute`'s `useProject` already reads both `project_id` and `project` (the first
taking priority), so every fixed link is picked up by the destination page regardless of which family it reads
from.

### 3. Tests

- `cycle_records_build_d690.test.ts` test 12 (new): reads venture A's `edit-split` and `Incorporation` hrefs,
  then venture B's (a second seeded holder and a second `incorporations` row), right after — proving venture B's
  links name venture B and not a value left over from venture A's read just before it.
- `cycle_new_venture_d688.test.ts` (new test, worker) and its frontend mirror: read Build's overview for venture B
  (project 202) first, then venture A (project 101), and assert venture A's Founding team and Product roadmap
  `next.href` still name 101 — the multi-venture regression the issue calls for, simulating a venture previously
  selected elsewhere in the app. The same test asserts no card's href contains `/build/roadmap`.
- The two files' existing fixtures (`cycle_new_venture_d688.test.ts`'s `emptyBuild`, `cycle_records_build_d690.test.ts`'s
  `edit-split` and `Incorporation` assertions) are updated in place to the corrected hrefs.

### 4. Audit for other new links to `/build/roadmap`

Grepped `cycle_build.ts` and `services/records/build.ts` (the only files this issue owns) for `build/roadmap`:
no other occurrence. The legacy route itself (`frontend/src/App.jsx`'s `/build/roadmap` route and its alias
entry in `railPages.js`) is untouched and keeps answering as a compatibility redirect.
