## D8072 — The untrusted pool contract: pull-request jobs hold no credential (#8072)

- **Status:** built 2026-11-21. Tracker #8059; ChatGPT Pro audit of 2026-11-21, section 9, P0 row 6.
- **Scope:** CI only. `scripts/ci/pool-contract.mjs` (new), `frontend/test/pool_contract_8072.test.mjs` (new), and the `permissions:` lines of `codeql.yml` and `semgrep.yml`. No Worker route, migration or production resource changed.

### The contract

A job that a pull request can start runs code a branch wrote. A pull-request job is one started by `pull_request`, `pull_request_target` or `merge_group`, after its own `if:` and `needs:` are read. Every such job:

| Rule | What it means |
|---|---|
| Pool | `runs-on` is a GitHub-hosted label (`ubuntu-…`, `windows-…`, `macos-…`) or the `untrusted` runner group. It is never another self-hosted runner, never the `trusted` group, and never an expression the check cannot read. |
| Token | Permissions are declared, at the job or the top, with no `write` scope and no `write-all`. Read scopes (`actions: read`, `checks: read`…) are allowed: a read-only token. |
| OIDC | No `id-token`. |
| Secrets | No `secrets.NAME` (`GITHUB_TOKEN` is the token above), no `secrets[…]`, no `toJSON(secrets)`, no secret in the workflow's own `env`, and no `secrets:` or `secrets: inherit` on a reusable call. |
| Environment | No `environment:`. An environment carries its own secrets. |

A job that names a deploy environment (`production`, `pr-preview`, `agent-compute-preview`) has two rules of its own:
- **Trigger:** it runs only from a `push` to main or a `workflow_dispatch`. The push counts as main when it is restricted to `branches: [main]`, or when the job, or a job it waits for, is guarded by `github.ref == 'refs/heads/main'`.
- **Runner:** a GitHub-hosted label or the `trusted` group.

The other environments (`production-ops`, `landing-bot`, `repair`, `scan-remediation`) are #8069's. Here they are held only to "never from a pull request".

A local reusable workflow's jobs carry the pull-request events of the jobs that call it.

**The groups are named `untrusted` and `trusted`.** #8065 creates them. Today no pull-request job uses a self-hosted runner: every one runs on `ubuntu-latest`. The constants in the script are where a different recorded name goes.

### Which jobs a pull request starts

The check narrows a workflow's pull-request events by each job's `if:`. It removes only what the expression proves:
- `github.event_name == 'X'` keeps X.
- `github.event_name != 'X'` drops X.
- `github.ref == 'refs/heads/main'` drops `merge_group` only. A merged pull request's `closed` event runs with `refs/heads/main`: `pr-preview.yml`'s branch delete did, in runs 44928484671 and 44921781176.
- A disjunction counts only when every branch pins an event.
- A job without `always()`, `failure()` or `cancelled()` runs only when every job it `needs` ran.

Anything else keeps every event, so a job is never let off by an expression the check cannot read.

**Review events are not in the set.** `pull_request_review` and `pull_request_review_comment` are left out, as the issue scopes them. The one workflow they start, `claude-code.yml`, is held by WF-6 (`workflow_security_4571`) to the `author_association` gate. This is the follow-up to the contract: list them as pull-request events, and give that job a read-only token or an exception.

### Why "today" is the commit's date

An exception expires. The test reads "today" from the date of the commit under test (`git log -1 --format=%cs`), not the wall clock:
- the guard on real-clock test reads (D5614) holds;
- a past commit still checks the same way;
- an exception lapses the first time a commit dated after it is tested, on a pull request or in the queue.

The command takes `--today` for anything else.

### Exceptions

Each one is allowed by workflow, job and kind, until its date. An exception past its date fails the check, and so does one that matches nothing. Each has an owner issue that removes it.

|---|---|---|---|---|

| `ci.yml` › `digest` | `pull-requests: write` | D5502: it posts the CI failure digest comment on the failing pull request. It runs only after a failure and reads no secret. | 2027-01-31 | #8072 |

| `claude-review.yml` › `review` | secrets, `id-token` | The model reviewer needs provider keys. It runs only for a same-repository head and takes its reviewer code from the base commit (#6461). | 2027-01-31 | #8069 |

**What changed in the tree.** `codeql.yml` and `semgrep.yml` granted `security-events: write` at the top, so their `visibility` job held it on every pull request. The write now sits on the one uploading job. `visibility` takes `security-events: read`, so whatever repository metadata its API call can see is unchanged. No other workflow needed a change: every other pull-request job already holds a read-only token and no secret.

### What this does not do

- **It is a guard on main, not a sandbox.** A same-repository pull request's workflow file is the branch's own code: a branch can edit a job's `permissions:` in its own run. The contract fails that branch's CI and keeps the edit off main. What a run can reach before then is bounded by the repository's settings and the runner groups' workflow restrictions (#8065), and the token a fork's pull request gets is always read-only.
- Deploy and ops workflows are #8069's. The runner groups are #8065's. The executor and coordinator are #7886, #7887 and #7909's.

### Rollback

Revert the PR. The script and test are new files. The two workflow edits move a permission from the top of the file to the one job that uses it, so reverting them grants it back to every job.
