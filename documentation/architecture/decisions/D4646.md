## D4646 — Learning is recoverable: drafts, pending positions, the first lesson and the way back (#4646)

- **Status:** built 2026-11-07 (Learning audit, work package 2 of 5). No migration, no new Worker route.
- **Builds on:** D4478 (the offline position writer), D4180/D4476/D4481 (the Learning lists and lesson player), D562 (exercises and exams), #4577 (the shared sign-in labels).

### What changed

- **Unsent work is kept on the device.** `learningDrafts.js` keeps an exercise's text or ticks, and an exam's choices, in the browser's storage under a key naming the learner, the content and, for an exam, the exact attempt (`axal:learning:v1:<learner>:<kind>:<content>[:<attempt>]`). `useLearningDraft` restores it when the same learner reopens the same content, writes after 400 ms and again when the page is hidden or the panel goes, and removes it once the server has the work (a new submission, a submitted attempt). Another learner on the same device, another attempt, or an expired (30 days) or corrupt entry reads as none. A store that refuses (full, private mode) says "Not saved" and leaves the page working.
- **The words say where the work is.** "Saved on this device. It is not sent until you submit." and "Restored your unsent work from this device." Nothing says saved without saying where; the exam intro no longer says a resumed attempt starts with no choices.
- **Exam choices are restored only where they still fit the attempt** (`restoredAnswers`): a question in the attempt and an option of that question; anything else is dropped. Timing, submission and the allowance stay the server's: resuming reuses the open attempt and consumes none.
- **A pending video position survives the player.** `queuedPositionWriter` takes a `store`; a position that could not be written is kept on the device, written when the connection returns or the item opens again, and removed once the server has it. Disposing the player no longer throws it away.
- **The first lesson appears in Continue learning.** The first position of a lesson also records the lesson and its course as `started` (`recordLessonStarted`); Continue learning and the in-progress count read course rows. The route never moves a completed row back or a percent down.
- **Sign-in returns to the Learning page asked for.** The route guard sends a signed-out visitor to `/login?next=<path, query and fragment>` for an area on `RETURN_AFTER_LOGIN_PREFIXES` (`/learning`), and the sign-in page already honours `next` for the email link, Google, passkey and authenticator code. Anything unsafe or over 200 characters falls back to a bare `/login`. Other areas join the list when their deep links need it.

### Not done here

- **Server-held drafts and exam choices.** The copy is on one device. Another device, or a cleared browser, does not have it. Storing exam choices on the server belongs with the attempt and completion contract in #4643, which this does not change.
- **Reconciling a pending position for an item the learner never reopens** is by the learner opening it (or the connection returning while its player is open); there is no background sync.
- **Continue opens the course** as before; opening the exact lesson and second needs the in-progress row to name the lesson, which the Worker does not return yet.
- **Production acceptance:** no authenticated production Learning flow, two-tab or mobile-tab-restoration check could be run in this sandbox.
