## D1375 — A safety check that does not answer is asked once more before the run fails closed

- **Status:** a fix, from the owner's first complete Zoom capture (2026-10-29, session 28). Built by S21.
- **Builds on:** D763: Llama Guard checks every run's input and output, and fails closed.
- **Migration:** none.

### What happened

The Zoom bot joined, recorded and uploaded, and the audio was transcribed. "Find suggestions" then ran the interview structuring on the transcript, and its input check timed out. The Llama Guard call took exactly `TIMEOUT_MS.chat` (8,000 ms), where another check on the same session took 5.5 s.

The guard fails closed, so the run was refused as `guard_unavailable`: nothing was stored and nothing was charged. The member saw "The model could not be reached." One slow answer from Workers AI was enough to fail the step.

### What changed

`guardSlice` asks a slice once more when the call did not complete, through a timeout or an error. The rules around that one retry:

- **Only an incomplete call is retried.** An unsafe verdict or an unreadable answer is final, as before.
- **Two failures still fail closed,** with the same refusal, refund and copy.
- **The record is unchanged:** a slice is still one guard row, and its charge comes from the call that answered.

The worst-case added latency is one more timeout per slice batch.

### Verified

- **Guard tests:** `ai_guard_d763` passes 34 of 34. The new cases:
  - a failed first call followed by a good answer lets the run through;
  - two failures refuse with one guard row and exactly two asks;
  - an unsafe verdict is asked once.
- **Mutation check:** without the retry, both new tests fail.
- **Neighbouring tests:** every Worker test that names `guard_unavailable` or the guard stub passes, 1,159 of 1,159, and `tsc` passes.
