## D6370 — Dedicated Slack channels for GitHub Actions workflow attempts (#6370)

Each completed StudioOS workflow attempt gets a short Slack entry with its conclusion and a link to that attempt's GitHub logs. GitHub continues to enforce access to the underlying logs. The public inventory in `engineering-notifications/workflow-channels.json` maps workflow IDs to paths and channel hashtags, including GitHub-managed workflows. Display names, PR input and event URLs do not select a destination.

### Registration and rollout

1. Register the exact workflow path and hashtag in the inventory. If a new workflow has no GitHub ID yet, use a pending ID of `null`, then fill in the actual number from the GitHub Actions workflows API after registration.
2. Create its private internal Slack channel and invite the intended Slack bot. The bot needs `groups:read` and `chat:write`. Privately configure the existing engineering sender's `ROUTING_REGISTRY`. Under `channels`, add the role `workflow:<GitHub numeric workflow ID>` with the Slack `id`, `private: true`, `enabled`, the approved `retentionDays` and `publisher: "internal-bot"`. The trusted channel name comes from the public inventory. Keep Slack IDs, tokens and the filled-in registry out of GitHub.
3. Configure the independent capture Worker and check that the `EngineeringEvents` entrypoint has ledger history for this repository. Deploy the sender with its read-only `ENGINEERING_EVENTS` binding to that Worker. Its existing five-minute cron runs the workflow relay when both `WORKFLOW_LOGS_ENABLED` and `DELIVERY_ENABLED` are true. Enable a pilot destination first. Keep existing role channels and health producers at their intended settings.
4. Compare an actual GitHub attempt with the message in the private destination and the internal `SlackPublisher.receipt` for `workflow-attempt:AxalNetwork/StudioOS:<workflow ID>:<run ID>:<attempt>`. Verify the destination and the message timestamp before expanding. Only a Slack acknowledgement confirms delivery.

### Recovery

Each page of history commits its attempt intents and cursor atomically. Up to 1,200 history rows are read each tick. Ledger reconciliation can supply attempts missed by the webhook. Duplicate webhook and reconciliation records reuse the same outbox key. Separate attempts have separate messages. Absent routes retain minimal recovery records. After the ID enters the catalog and its private destination is configured, the next polls drain the available records. If a source record lacked its workflow ID, a later authoritative record for the same run and attempt resolves it. The relay reads the public StudioOS ledger partition only. Restricted or unrelated event families never supply message content.

Use the internal `SlackPublisher.summary` to inspect `workflowLogs.cursor`, `workflowLogs.unmapped` and per-role outbox states. Entries older than the destination's retention can expire without posting. To pause an individual channel, set its role's `enabled` to false. To stop ingesting new workflow entries, disable `WORKFLOW_LOGS_ENABLED`. Existing queued entries still honor each role's switch and the global delivery switch. A renamed, inaccessible, shared or mismatched channel refuses delivery. Reconcile ambiguous and dead receipts against the real channel before recovery under D5665. The sender does not create an Actions job or post raw console output. Provider activation evidence is tracked in #6370 and #5668.
