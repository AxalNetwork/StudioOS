## D661 — The cycle overviews and module pages in the SPA, from the shared cycle read

Issue #1474, 2026-10-09, part of #1469 (D656). No migration. S07.

### What this part builds

S1's order on #1474: build the components now and mount nothing. Each cycle is
wired as its read merges:
- Validate first: #1472 (D659);
- then Build: #1475 (D662);
- then Raise: #1476 (D663);
- then Grow: #1477 (D664).

The pieces, all in `frontend/src/pages/cycles/`:
- **`CycleOverview`** draws `Cycle Overview.dc.html`'s `variant=full`, `new`
  and `states`:
  - the cycle's question and outcome, and its primary action;
  - four headline figures with sparklines;
  - one chart card per module, in the read's order.

  D688 specifies how the three new-venture boards are derived from their Worker records, without a `new` mode.

  There is no module list, no status pill and no Pro strip. This answers the
  owner's question of why each overview showed its modules twice: the tabs
  are navigation, and the cards are the modules.
- **`CycleModulePage`** draws `module=0…6`:
  - the tabs (a module menu on a phone);
  - the module's chart at full size, with its caption and its one next action;
  - the records as a working table: search, filters, sort, pages and Add;
  - a link to the module's own tool where it has one, rather than a second
    copy of it;
  - then the module's further parts.
- **The five card states:**
  - `empty` shows its line and the action that starts it;
  - `too_little` draws no line;
  - `not_recorded` shows its reason;
  - `unreadable` names its source and offers a retry for that card only.

  A card still being read draws the canvas's grey bars. A state the page does
  not know, and an `ok` card with nothing it can draw, read as unreadable,
  never as fine.
- **The charts are SVG components,** one per helper in the canvas. They use
  no chart library and no HTML strings: the canvas injected its charts as raw
  HTML, and these are elements, so a label from a read is always text.

### The shape D656 left open

D656 names `Card.series` and `records.cols`/`rows` but does not give their
shape. The page consumes them, so this decision gives it. The four read tasks
build to it.

**`Card.series` is a list of chart specs, drawn top to bottom.** Each spec
names its `kind` and carries that kind's data. Any spec may also carry
`legend: [{ label, tone }]`.

| kind | data |
| --- | --- |
| `hbar` | `items: [{ label, value, tone? }]`, `more?` |
| `vbars` | `values: number[]`, `labels?: [{ at, label }]` |
| `vstack` | `rows: number[][]`, `tones: string[]`, `labels?` |
| `funnel` | `steps: [{ label, value }]` |
| `stack` | `rows: [{ label, parts: number[] }]`, `tones`, `bare?` (one unlabelled bar) |
| `line` | `values: (number\|null)[]`, `target?`, `target_label?`, `plan?: number[]`, `mark?` (an index), `mark_label?`, `labels?` |
| `timeline` | `steps: [{ label, date, done }]` |
| `tiles` | `items: [{ label, state: 'connected'\|'failing'\|'not_connected' }]` |
| `dots` | `values: boolean[]`, `label?` |
| `rows` | `items: [{ label, value, tone? }]` |
| `progress` | `items: [{ label, pct }]` |
| `big` | `value: string`, `label` |
| `heat` | `rows: [{ label, cells: number[] (0–1) }]`, `axis?` |
| `bands` | `items: [{ label, value, source? }]` (total, serviceable, obtainable) |

- **Tones are names, never colours:** `v1`, `v2`, `v3`, `grey`, `ok`, `warn`,
  `bad`, `muted`.
- **A null value is drawn as "Not recorded",** or left undrawn inside a chart.
  It is never drawn as 0.
- **A line breaks at a missing point.** A spec with fewer than three real
  points is not drawn, as D656's `too_little` rule requires.
- **A spec of an unknown kind is skipped.** If nothing in the series can be
  drawn, the card reads as unreadable.

**The records:**
- `cols: [{ key, label }]`;
- `rows: [{ id, cells: { [key]: Cell } }]`, where a Cell is a string, a
  number, null, or `{ text, tone?, href? }`. Null is "Not recorded".
- optional `filters: [{ key, label, options: [{ value, label }] }]`,
  `sorts: [{ key, label }]` and `add: { text, href }`.

The page sends the read's own query: `q`, `filter=key:value,…`, `sort` and
`page`. It filters nothing in the browser, so the count is always the store's
count. An unknown `total` is shown as "N shown · total not recorded".

**Links are in-app only.** Every `href` a read carries (a card's `next`, a
cell, Add, a module's tool) must be a path on this app. Anything else is drawn
as text (`safeHref`).

**The figures:**
- `unit` is `usd`, `pct`, `score`, `of` (a pair: `[11, 18]` is "11 of 18"),
  `count`, `days` or `months`.
- `delta_30d` is written as "▲ 4 in 30 days". The page does not colour it
  good or bad, because the read does not say which direction is good.

### Edit a row, and Prototype / MVP's must-haves (Part of #1474, 2026-10-10)

**Eight tables gain Edit.** A row the Worker can change draws an Edit
control at its end, and the side sheet opens on the row's current values.
Each form sends only the fields it holds, and the route changes only those.

| Module | Edit | Writes |
| --- | --- | --- |
| Grow · Product improvement | status, theme, roadmap item | `PATCH /feedback/:uid` |
| Grow · Distribution | name, state | `PATCH /channels/:uid` |
| Grow · Partner network | type, stage, terms | `PATCH /partners/:uid` |
| Grow · Market expansion | state, decision, each part's score and source | `PATCH /markets/:uid` |
| Grow · Durable company-building | state, owner, due date | `PATCH /obligations/:id` |
| Build · Company creation | a formation step's name, date and state | `PATCH /formation-steps/:id` |
| Build · Prototype / MVP | a must-have's date, or taking it off the list | `PATCH /features/:id` |
| Build · Solution design | marking a feature a must-have | `PATCH /features/:id` |

**What an Edit form needs from a row:**
- **`idOf(row)`:** the store's own id. A row without one draws no Edit.
- **`valuesOf(row)`:** the row's current values.
- **Grow's rows** carry both as `edit`, and only when the read named the id (`adapters/grow.js`).
- **Build's rows** pass through, so the form reads the read's own cells. On Company creation, only `step-<id>` rows are formation steps; the Lab's steps and the entity's filings share that table and draw no Edit.

**Emptying a field clears it.** On a market, an emptied score clears that part, and a score still needs its source.

**Prototype / MVP gains "Add a must-have."** Two writes:
1. MVP scope (`POST /progress/mvp-scope/:projectId`) adds the feature, with its value, effort and state.
2. D662's feature route marks it a must-have and sets its date.

Taking a must-have off the list leaves the feature in scope. Solution design marks it back.

**Tests.** `cycle_adapters_d661.test.ts` runs every Edit form through its real route on SQLite:
- it starts from the row the read gives;
- it checks the row's own values pass the form;
- it reads the change back, and checks the fields the form does not hold have not moved;
- a row the venture does not hold is refused (404).
