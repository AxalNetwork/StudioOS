## D651 — The Connectors page, its user-menu entry, the redirect from Integrations, and Build's "Connect a tool"

Issue #1463, 2026-10-09, part of #1461 (D649: Connectors replace Integrations).
No migration. Built by S07 on the existing `/api/integrations` routes. The
switch to `/api/connectors` and its new fields waits on #1462 (D650), as the
issue orders.

### What was decided

- **Connectors is a section of the Account center**, at `/account/connectors`,
  after Usage in the section list and in the phone menu. The user menu gains
  "Connectors" under "Usage". The "Integrations" section left the "More" group;
  `SettingsPage.jsx`'s `integrations` path segment resolves to `connectors`.
- **Both old addresses redirect.** `/integrations` and `/account/integrations`
  go to `/account/connectors` with their query string and hash
  (`connectorsRedirect` in `connectorsModel.js`). This is what keeps sign-ins
  working: every provider still returns to `/integrations?…`:
  - `routes/integrations.ts` returns `?oauth=ok|error|rolling_out&provider=…`;
  - `routes/calendar.ts` returns `?google=…` and `?microsoft=…`;
  - `routes/linkedin.ts` returns `?linkedin=…`.

  The section reads that query (`oauthReturn`), opens the connector's sheet on
  `connected`, `cancelled`, `refused` or `overreach`, and strips the keys it
  read, so a reload does not replay the return. The redirect carries
  `state.connectorsMoved`. The section shows "Integrations are now Connectors."
  once, and remembers in browser storage that it did.
- **One sheet, two doors.** The connector sheet and the connect flow
  (`ConnectorSheet.jsx`) are drawn to the `connector` action of
  `Cycle Action.dc.html`. Two surfaces open the same panel:
  - the Connectors page;
  - Build's "Connect a tool" (`ConnectToolSheet.jsx`, the `connect` action, in
    `FounderBuildDesk.jsx`'s header).

  A tool connected from Build is a connector on the page. The catalogue read is
  shared (`useConnectors`):
  - the registry;
  - the member's connections;
  - the waitlist;
  - the Google, Microsoft and LinkedIn status reads.
- **Google Calendar, Microsoft 365 and LinkedIn are connectors.** They connect
  through their own first-party routes. Their token stores stay the only ones,
  as D650 requires. A registry entry with the same key, once D650 adds one,
  replaces the built-in entry.
- **`IntegrationsPage.jsx` is retired.** Its provider tools moved, unchanged,
  into `pages/account/connectorTools.jsx`:
  - the LinkedIn connections import;
  - HubSpot's pipeline picker;
  - Salesforce's stage and field mapping.

  Its per-provider connect rules moved into the sheet:
  - HubSpot's Private App token first, with OAuth offered beside it;
  - Calendly's personal access token;
  - Salesforce's sandbox choice;
  - DocuSign's `demo=0|1`;
  - Crunchbase's user key;
  - the webhook secret and JSON settings, under "Advanced".

  The Telegram join request became a card in Discover. Links to
  `/integrations` and `/account/integrations` in the app now name
  `/account/connectors`.

### Departures from the canvas, each for a reason

- **A field the registry does not carry yet reads "Not recorded", with its
  reason.** Each one arrives with D650:
  - "does", "feeds" and companies on a row;
  - pulls and sends;
  - plain-word permissions;
  - the sync frequency;
  - "Now fed by";
  - the verified badge.

  Each reader takes D650's field first (`doesLabel`, `feedsLabel`,
  `companiesLabel`, `p.permissions`, `p.verified`). The sheet shows the
  registry's own capabilities under "What it does" meanwhile. The category is
  the one field derived in the meantime: the registry's `integration_type` in
  the canvas's words, with Stripe as Payments.
- **"Suggested for you" draws no suggestion.** Suggestions are D650's rules
  over empty modules. Until that route exists the chip says "Not recorded",
  rather than inventing reasons.
- **The request form sends nothing.** `POST /api/connectors/requests` is
  D650's. The drift test refuses a client method whose route is not on `main`,
  so the form is drawn with Send disabled and says why.
- **"Add a custom connector" is shown as Pro and Coming soon, and is
  disabled.** The Worker has no MCP client, and the epic leaves it out.
- **`teammate` is not reachable yet.** It needs D650's per-provider read
  (`GET /api/connectors/:key`). `overreach` is reached through the sign-in's
  return (`reason=overreach`), the event name #1462 gives the scope check.
  D650 should return that reason.
- **The `pro` state does not print "Free keeps every connector you already
  have."** The sync route calls `ensureTier` for a paid provider, so a member
  on Free cannot sync a paid connector they connected earlier. The sentence
  would be false today. Build's locked banner says the same: it names the
  plan, not what Free keeps.
- **"Disconnect" says what is true today:** "Data already in StudioOS stays.
  The stored credentials are deleted." The route deletes the row and calls the
  provider's own disconnect where one exists. It does not promise a revoke at
  every provider.
- **The `signin` view says the provider "is opening", not "a window is open".**
  The sign-in replaces the tab rather than opening a popup.
- **Build's "Connect a tool" returns to Connectors, not Build, after an OAuth
  sign-in.** The Worker's callbacks choose `/integrations`. A tool connected
  with a key stays in Build's sheet.
- **Logos are initials on the house lavender**, not the providers' brand
  colours.
- **The AI rail frames (`rail`, `railList`) are #1464 (D652).** Build's `sync`
  view (choosing GitHub repositories) is #1467 (D655).
