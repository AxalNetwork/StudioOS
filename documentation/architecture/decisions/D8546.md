## D8546 — Problem discovery grouping proposals: the Worker contract and atomic set acceptance (#8546)

Part of #6006. The V17 and V29 boards of the Validate v2 Discovery canvas (D5995) draw "Proposed grouping": a set of phrases, from several interviews, offered for one theme, with Edit, Discard and Accept. D6006 part 2 (`D6006-p2.md`) left the backend open. This is that backend. It is the Worker only: no producer, no model call, no billing, no card.

### What a proposal is

- One row of `pain_grouping_proposals` (migration `202611251920_8546_pain_grouping_proposals.sql`): one venture, **exactly one target** (an existing theme of that venture, or a proposed new title; a `CHECK` holds it), and a set of members.
- A member is one phrase, once by its normalized form, with every interview of this venture that said it. The set may span interviews; it is not coerced into one interview's `target_ref`.
- The original (`members_json`, `target_*`) is written once. A writer's edit lands in `edited_members_json` and `edited_title`, so what was proposed and what was accepted stay distinguishable.
- **A pending or edited proposal writes no alias and no theme.**

### The contract (`services/painGroupingProposals.ts`, `routes/pain_grouping_proposals.ts`)

| Piece | What it does |
| --- | --- |
| `proposeGrouping` | The typed ingress for the later producer. Checks members and target; an optional `source_key` makes a replay answer the proposal already stored. **No route stores a proposal.** |
| `GET /api/progress/pain-grouping-proposals/:projectId` | The venture's proposals (`pending` by default, `?status=all`), each member with its sources: interview, interviewee, and whether that interview agreed to be quoted |
| `PATCH …/:projectId/:id` | `{ members?, title? }`, the same checks as the original; a set going to an existing theme has no title of its own |
| `POST …/:id/discard` | Status only; no theme or alias is read or written |
| `POST …/:id/accept` | The whole set, one decision, one write |

Validation, at ingress, edit and again at accept: every source interview is this venture's and still holds the phrase; the target theme is this venture's; 1 to 100 distinct phrases (`MAX_BULK_ASSIGN`, held equal by a test), phrases cut and normalized as the manual route cuts them. At accept a premise that moved answers 409 `stale_source` or `stale_target`, and the proposal stays pending.

### Atomic acceptance

One `DB.batch`. Its first statement claims the row (`pending` to `accepted`, with a fresh `decision_token`) and holds the premises read just before it: the target theme still exists in this venture, and each source interview's `pains_json` is still what was read (the `PainsGuard` idiom). Every other statement (the new theme, the alias upserts, the one activity row) writes only where that token is the proposal's own. So:

- a second or concurrent accept changes no row at the claim and writes nothing, and answers 409 `already_decided`;
- a premise that moves between the read and the claim writes nothing (409 `stale_grouping`);
- a batch that throws rolls back whole: the proposal stays pending with no theme, no alias and no activity (503 `accept_failed`, the raw error never sent).

### The boundary with the manual route (recorded before any edit of `progress.ts`)

**`routes/progress.ts` is not edited.** `POST /pain-groups/:projectId/assign-many` keeps its own code and tests. Accept does not extract or call its handler; it writes the same rows with the same statement shape as `upsertPainAliasStatement` (`ON CONFLICT (project_id, phrase_norm) DO UPDATE` of group, wording and time), cuts phrases the same way, makes a new theme with the same next `sort_order` and `created_by`, and logs one `activity_logs` row of the same action (`pain_group_created` or `pain_group_assigned`) and wording. The only addition is the claim guard on each statement, which `upsertPainAliasStatement` cannot carry. A test runs the manual route on a second database with the same input and holds the alias rows and the activity row equal. If the manual statement changes, that test is what fails.

Not touched, as the 2026-11-25 handoff on #8546 requires: `cycleValidate.ts`, `cycle_validate.ts`, `interviewSuggestions.ts`, `interviewStructuring.ts`, `founder_validate_structure.ts`. The generic one-interview proposal contract is unchanged.

### Who reads what

Venture writers only (`canWrite`: an admin, the venture's founder, an admitted Lab member on their own venture). A partner, an investor or another venture's founder is refused with no payload; the service itself returns nothing for a non-writer. A member's wording is the writer's own pain phrase, as the writer's panel shows it; each source says whether its interview consented, so the card can mark the ones that did not. After acceptance the theme's phrases reach a reader only under the view's existing consent rule.

### Tests

`cloudflare-worker/test/pain_grouping_proposals.test.ts`, 14 tests on the migrated schema through the mounted router: a two-interview set stored and read; ingress replay; edit keeps the original; discard; accept equals the manual route's rows and activity; a new theme made once; refusal of cross-venture and missing members and targets, empty and oversized sets; writers only; stale source and target; a premise moving between the read and the claim; two accepts at once; a loser that read before the winner decided overwrites nothing; a write that fails part way; consent. Mutation-checked: 18 mutations of the service and route, 18 caught (the first run left four alive; three needed the lost-race test and one was an equivalent `ON CONFLICT` spelling, replaced by a real mutation).
