### 1. Job postings' publish date (migration 609)

**The store.** `job_postings.published_at`. `POST /api/admin/jobs/:id/approve` (`routes/admin_jobs.ts`) writes it each time an admin approves a posting. Unpublishing or closing a posting leaves it as it was. `services/jobBoardSchema.ts` mirrors the column for dev and preview.

**Nothing is backfilled.** A posting approved before 609 has no recorded day. It reads "Not recorded", never 0 days open.

**The reads:**
- the admin job list and the admin posting carry `published_at` (`shapeJobPosting`, private fields only);
- the overview's `jobs.top` rows carry `days_open`: whole days since the last approval for a published posting, `{ recorded: false, reason }` for one approved before 609, and null for a posting that is not published. The block-wide `days_open: { recorded: false }` is gone.

**What the page draws:**

| Where | What |
|---|---|
| The Jobs card, Most applications | "[d] days open" beside the company; "Days open not recorded" before 609; nothing when the posting is not open |
| CM4, Posted | The day it was last approved; "Not recorded" for a published or closed posting before 609; "Not published" for one that never went live |
| CM4, Days open | Whole days for a published posting; "Not open" otherwise; "Not recorded" before 609 |
| CM4, sort | "Days open", longest first; not open or not recorded sorts last |

Posted and Days open replace CM4's Created column, as the canvas draws it. The footnote says what the two mean.

**Choices to check:**
- **Each approve writes the day,** not only the first. Days open is how long the posting has been live this time: one unpublished and approved again starts from the new approval.
- **Only a published posting is open.** Nothing records when a posting was closed, so a closed posting's days open would be a guess.

### 2. CM3's Type filter

D918's list (`GET /api/admin/events`, `services/adminEventsReads.ts`) takes `type`, one of the stored event types; any other value is 400 `invalid_type`. CM3 draws it as "Type ▾", and it combines with the other filters. The client is `adminEvents.list({ type })`.

### 3. The Confirmed step
