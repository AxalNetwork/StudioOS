## D9046 — HQ's close as fulfilled runs the platform's own erasure, and stays open when it fails (#9046)

- **Status:** built by S10, 2026-11-27. Part of #4675.
- **Builds on:** D168 (the data-subject ledger), D4675 (the exact request, the close key), D1530 (`eraseAccountAgents`).
- **Migration:** none.

### The gap

- `eraseAccountAgents` (`agents/erasure.ts`) was documented as "what that manual erasure runs", and nothing called it.
- So HQ could record a request as `fulfilled` while the person's agent memory notes were still in `agent_memory_notes`.

### What is built

- **The erasure is a step of the close (`services/dsrRequests.ts`).** `closeDsrRequest` takes an optional `erase` step. It runs it only when all of these hold:
  - the outcome is `fulfilled`;
  - the close key is not already on record (a replay erases nothing again);
  - the reviewed request is still the open one (`reviewedRequestIsOpen`). That means the same conditions as the claim: the flag holds the reviewed stamp, the named ledger row is open with that stamp, and no other open row would make the claim miss.
- **Order: check, erase, record.** A stale or closed request goes straight to the batch, which records nothing and says why. So an erasure never runs on a review the close then refuses.
- **A failed step records nothing.**
  - `closeDsrRequest` returns `erasure_failed` before the batch: the ledger row stays open, `users.deletion_requested_at` is unchanged, and no audit row is written.
  - The route answers 503 `erasure_step_failed`, "Nothing was recorded…", following `ledger_unavailable`.
  - A retry is safe: the erasure is a set of DELETEs and cancels.
  - What can throw: `eraseAgentData`'s batch, and the compute host's `/forget` (`compute_cleanup_unconfirmed`). The runtime half (`eraseAccountRuntime`) is best effort and logs its own failures, as D1528 set.
- **The route (`routes/admin_security.ts`)** passes `erase: () => eraseAccountAgents(c.env, uid)`.
  - The fulfilled message now says the platform erased the account's agent data and nothing else: the rest is the manual act being recorded.
- **HQ › Security (`privacyModel.js`).** `erasure_step_failed` reads as a refusal in the Worker's words. It is not "unconfirmed" like other 5xx answers, because the server knows nothing was recorded.
- **`denied` erases nothing.**

### What this does not change

- The platform still erases nothing beyond the agent data: no `DELETE FROM users`, no anonymisation (D168). `fulfilled` remains a decision record for the rest.
- **A race is still possible.** If the subject withdraws and asks again between the check and the batch, the erasure has run and the batch then refuses as stale. The person asked for erasure in both requests, so the agent data being gone is not a wrong state.

### Proof

- `cloudflare-worker/test/dsr_close_erasure_9046.test.ts`: 4 tests.
  - A fulfilled close leaves no notes, run summaries or queued tasks for the account; another member's agent is untouched; the ledger reads fulfilled.
  - A thrown step leaves the ledger open, the flag unchanged and no audit row, and a retry closes it.
  - `denied` erases nothing.
  - Stale reviews erase nothing, both with a ledger row and before migration 272.
  - A replay erases nothing again.
