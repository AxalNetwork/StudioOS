## D5377 — Capital relationships: Match, Activity and Commitments filters, sort and page in the address (#5377)

- **Status:** Built, 2026-11-10 (frontend only; no Worker change, no migration).
- **Builds on:** D5073 (the pipeline's open investor and view in the address), D1193 (the tabs), D1192 (Pipeline).

### What was wrong

D5073 put the pipeline's open investor (`?investor=`) and view (`?view=list`) in the address and listed every other CRM filter under "Not covered". On main, Match (`q`, `hq_country`, `focus`, `size_band`, `fit`, `warm`, `sort`, `offset`), Activity (`q`, `kind`, `investor`, `page`), Commitments (`q`, `status`) and the board's Passed column lived in component state, so a refresh, Back or a shared link lost them.

### The rule

`frontend/src/pages/raise/caprel/capRelUrlFilters.js` holds one spec per tab (`MATCH_FILTERS`, `ACTIVITY_FILTERS`, `COMMITMENT_FILTERS`, `PIPELINE_FILTERS`): each key, its default, and the values it allows. `useTabFilters(spec, projectId)` reads and writes them through `useSearchParams`.

- **Allowed values are the Worker's own.** Size bands, sorts, country and focus shapes from `researchFundDirectory.ts`; activity kinds from `capRelTabs.ts`; commitment statuses from `capRelReads.ts`; Match's offset steps by its page of 25; Activity's page is 1–10,000; a search is cut to 100 characters. A value outside the set reads as the default and is never sent to the Worker; it is dropped from the address at the next change.
- **Defaults stay out of the address**, and every key the tab does not own (`project_id`, `view`, `investor` on Pipeline, `moved`) is kept as it is.
- **A filter change resets the page** (`offset` on Match, `page` on Activity); a page change keeps the filters.
- **History.** A filter, sort or page change pushes an entry, so Back restores the set before. Search replaces the entry: Match and Activity on submit, Commitments on every keystroke, so no keystroke pushes one. The Passed column replaces too, like D5073's view.
- **A venture switch clears them** (D5073's rule for the sheet). The frame that first sees the new venture already reads the defaults, and keeps reading them until the address is cleared, so no read for the new venture carries the old one's filters. The clear is re-checked on each address change, because Pipeline's own clear of its open investor in the same frame can be written over it; Pipeline's clear now drops `passed` as well.
- **Tab links are unchanged.** `tabHref` keeps only `project_id` (`tabSearch`), so one tab's filters never ride onto another tab's link.
- **The read is keyed by the canonical filter set**, so an equal set (after a clear, or a value that normalises to the same) is never re-sent.

Outreach holds no filter state on main and is left as it is.

### Tests

`frontend/test/caprel_url_filters_5377.test.mjs`: the allowed sets and defaults; defaults kept out and foreign keys kept; the page reset; tab links carry the venture only. Mounted: Match and Activity set filters, sort and page, reload from the address and make the one same read, and Back reads the set before; an invalid address value reads as the default and is never sent; a filter change resets the offset or page; a search replaces the entry; Commitments restores its rows from the address, typing replaces the entry, an unknown status is no filter; Pipeline's Passed column follows `?passed=1`; a venture switch clears each tab's keys and sends no read for the new venture with the old filters.

Nine mutations each fail a test: Match, Activity or Commitments reading from `useState` again; no defaults-while-switching window; no page reset; defaults written into the address; no allowed set; no venture clear; Commitments typing pushing an entry.

### Not covered

- **An action over the complete server-side set** (D5073 chose the loaded page and the UI says so).
- **Phone board's one-stage picker** stays component state: it is a phone layout choice, not a filter of the read.
