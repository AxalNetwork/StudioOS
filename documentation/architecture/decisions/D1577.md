### The question

Co-founders edit one deck at once. Each sees who else is on it and where. An edit is never lost because someone else saved a different part of the same card. One slide of an older version can come back without throwing away everything since.

### What was decided

**Areas, not cards, are the unit of a save** (`services/decks/coedit.ts`, `routes/deck_coedit.ts`).
- An area is one block of a card, by its id, or the card's title (`__title`).
- `PATCH /api/decks/:id/cards/:uid/areas/:area` takes `{ base, next }`: the area as the member read it, and what they wrote.
- The server reads the card as it holds it now. If that area still reads as `base` (stable JSON, so key order is not a change), it writes `next` there and keeps every other area as the server has it. The write is one conditional statement on the card's `rev`. If another save moved the rev between the read and the write, the server reads again and re-applies, up to `AREA_RETRIES` (4) times.
- Two members on different areas therefore both keep their edit. Two members on the same area: the second gets 409 `area_conflict` with the server's copy, and nothing is written.
- A9's whole-card `PATCH /cards/:uid` and its `If-Match` are unchanged.

**Soft locks are advisory; the save is the guarantee.**
- The area a member has selected is theirs while they edit it. Each change refreshes the lock, and it lapses `LOCK_TTL_MS` (30 s) after their last edit.
- Another member who selects it is told "[Name] is editing this area. Wait or ask [Name]." and holds no lock there.
- One member's own tabs never lock each other out.
- If two members do write the same area anyway, `area_conflict` stops the second.

**Presence** (`durable-objects/deck-presence.ts`):
- one `DeckPresence` room per venture's deck (`deck:<project id>`), so every version shares it;
- each editor is one hibernatable WebSocket. Its state lives in the socket's attachment: who, a colour, the card and area, the lock's clock and the cursor. So the room needs **no Durable Object storage**, and a closed socket takes its lock with it;
- frames: `area`, `edit`, `cursor` (dropped when faster than 5 a second), `ping`. The room answers `hello`, `presence` (everyone's `editorView`) and `locked`;
- an editor is shown by user id, name, colour, card, area and cursor, never an address or a role;
- at most 12 editors on a deck;
- the socket authenticates as `/api/pipeline/ws` does: the `bearer.<jwt>` subprotocol, the same upgrade rate limit, and then `projectOwned` with write access.

**Single-slide restore**, beside the whole-version `POST /:id/restore`:
- `POST /api/decks/:id/restore-card { card_uid }` takes that card from version `:id` and saves a new version: the current one with only that card replaced, matched by `uid`;
- a card the current version dropped goes back at its old place, clamped to the end;
- every other card, and their order, is left as it is. The version restored from is not changed;
- 404 `card_not_in_version`, 409 `card_unchanged`; audited `deck_card_restored`;
- the UI follows the Versions sheet. In `VersionCompare.jsx`, each changed card of the older version has "Restore card". It opens the same kind of dialog: "Restore card 02, “Traction” from v2?", then "v5 is saved with card 02 … as it was in v2", "Every other card stays as it is in v4, in the same order." and "Nothing is deleted."

**The frontend** extends S1's files and adds no screen:
- `presenceModel.js` and `useDeckPresence.js`;
- the toolbar's avatars and "[N] editing" (`DeckToolbar.jsx`);
- the stage's outlined areas with "[Name] is editing this area", their tooltip "Wait or ask [Name]", the cursors and the lock line (`GridStage.jsx`);
- the Studio home deck card's avatars (`StudioHome.jsx`).

While presence is off, `editors` is null and none of this is drawn: never "0 editing". `deckV2Adapter.presence` answers through `deckCoeditApi.presence`, and a 503 `*_off` reads as "Coming later" with the Worker's own sentence.

### Estimated monthly cost (for the owner, decision L)

Cloudflare's published Durable Objects pricing, read 2026-11-02, on Workers Paid:
- **requests:** 1M a month included, then $0.15 per million. A request is a WebSocket connection, or an incoming message counted at 20:1. Outgoing messages are free;
- **duration:** 400,000 GB-s a month included, then $12.50 per million GB-s, at 128 MB. A hibernatable socket is billed only while a handler runs;
- **storage:** none (above).

Both allowances are shared with the four Durable Object classes already bound.

| Assumption | Incoming frames | Billed requests | Duration (worst case: never hibernates mid-session) | Monthly |
|---|---|---|---|---|
| Now: 50 decks, 2 editors, 10 co-editing hours a month each | 18M (cursor-bound) | about 0.9M | 225,000 GB-s, within the allowance | **about $0 to $0.15** |
| Growth: 500 decks, same use | 180M | about 9M, so about $1.35 | about 2.25M GB-s, so about $28; about $0 when it hibernates between frames | **about $1.35 to $29** |

The cursor cap (`CURSOR_MIN_MS`, five a second) bounds the frame count. Halving it halves the request line.

### Suggest mode (waits on Q1)

A suggestion is one member's edit that the owner must see and accept. `ai_rail_proposals` cannot hold it, because every read and decision there is scoped to the proposer's `user_id`, so the owner's "Waiting for you" sheet would never list it. It needs its own table, and the number comes from S1. Until then the Suggest switch is not drawn.
