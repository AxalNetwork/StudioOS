## D8694 — The CI coverage matrix is generated from the repository and checked in test:guards (#8694)

- **Status:** built 2026-11-25 (#8694, from the CI architecture audit).
- **Migration:** none. **Workflow change:** none. **Test change:** none to an existing test.

**Context.** Nothing in the repository said, for the Worker, the frontend, D1,
billing, eSign, the meeting bot or the dev backend, which checks run and what
kind of evidence each gives. A green `test:drift` was read as proof of things
it does not test: unit and contract tests pass while no workflow signs an
envelope in a browser (#8524) and no monthly restore drill has passed (#8531).

**Decision.**

1. **A script writes the page.** `scripts/ci/coverage-matrix.mjs` reads the
   workflows under `.github/workflows/`, the steps of `test:drift` in the root
   `package.json`, the guards `test:guards` runs (`scripts/guard-commands.json`)
   and the required checks in `scripts/lib/requiredChecks.mjs`, never a copy of
   that list. It writes `documentation/operations/CI_COVERAGE.md`: one row per
   area with its checks, when each runs, whether it is required, the highest
   level reached and the open gap.
   - **Areas.** Every path in `CLAUDE.md`'s file map; every top-level folder
     that holds a Worker entry (a root `wrangler*.toml` `main`, or a wrangler
     config of its own); every top-level folder a `test:drift` step reads; and
     the six Worker services with their own release gate (accounts, AI,
     billing, disaster recovery, email, eSign). `infra/` has a row because
     the runner workflows that run test shards belong to it.
   - **When** comes from each workflow's events and the job's `if:`. Only
     `github.event_name` terms rule an event out; any other term may be true.
     `push` is "push to main" unless the branch filter excludes main, and a
     `paths` filter is shown.
   - **Required** is "yes" when the job reports a required check by name, or
     as a quoted literal in its name expression. A suite step or guard runs in
     `ci.yml` › `suite` and reports through `ci.yml` › `gate`.
   - **Levels**, lowest first: unit and contract, isolated browser, staging,
     provider-backed pilot, production monitoring. A suite step and a guard
     are unit and contract. Each workflow job's level is hand-kept.
2. **One hand-kept map, in key order (D4134).** `scripts/ci/coverage-matrix.json`
   holds what cannot be derived:
   - each row's checks (`file#job`, `suite:<step>` or `guard:<id>`);
   - each named job's level;
   - each service's test files, as globs;
   - each row's gap issues.

   Every map and every list is sorted. A new row, check or gap is one line at
   its place. The page renders a row's checks grouped (suite steps, guards,
   then jobs by level), whatever their order in the map.
3. **Issue references are checked offline.** The map's `issues` lists each
   gap issue as `#<n>` with a short title. A row's gap must be a key there,
   and every key must be cited by some row. `--check` makes no network call,
   so it cannot see an issue close. When a gap issue closes, the PR that closes
   it, or the next one to touch the map, removes it and regenerates the page.
   A row with no gap reads "none filed". The page states what exists and
   proposes nothing.
4. **`--check` runs in `npm run test:guards`**, as the guard `coverage-matrix`
   in `scripts/guard-commands.json`. No new workflow job. It fails on:
   - a top-level source folder with no row;
   - a workflow job that runs tests (node:test or a `*.test.*` file run by
     node, Playwright, unittest or pytest, a guard run or a suite part) that no
     row names;
   - a row naming a workflow, job, `test:drift` step, guard or level that
     does not exist, a glob that matches no file, or a gap not in `issues`;
   - a map or list out of key order;
   - a required check that names no job;
   - a committed page that differs from what the script writes.

   `frontend/test/ci_coverage_matrix_8694.test.mjs` shows each failure on a
   fixture repository, and that the real page is current. Mutation check
   (`ci_coverage_matrix_8694.test.mjs`): 23 mutations, 23 caught, 0 equivalent.

**Consequences.** A PR that adds a test-running job, a source folder, or a
required check (as #8641 will) must also update the map or the page, or
`test:guards` fails. That is the point: the page cannot go stale. The page
changes only when a named job's name, events or condition changes, or the map
or required list changes. Adding a test file never changes it: the map holds
globs and the page shows no counts.
