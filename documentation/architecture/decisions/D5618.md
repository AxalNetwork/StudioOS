## D5618 — Independent Merge Control Worker (#5618)

The control plane is an independently deployed Worker, not an Actions job or a
studioos route. One SQLite Durable Object per repository serializes delivery
processing and durable issue leases. A Queue decouples authenticated ingress
from GitHub calls; five failed deliveries go to its separate DLQ. Cron reconciles
every five minutes. There are no production Worker imports, D1 or KV bindings.

A bounded raw body is verified with HMAC SHA-256 and a constant-time comparison
before any enqueue. Missing/incorrect signatures return 401. Only minimal event
metadata enters the queue/audit: no user object or commit message. Repository
selection is fixed by config. Owner status, switch and claim routes require a
separate constant-time checked Bearer secret. SQL values are bound. Audit rows
are insert-only; a partial unique index deduplicates event delivery rows.

The kill switch is durable and defaults ON, including on first deploy. While on,
events are audited without GitHub calls and are acknowledged rather than replayed
later. The owner explicitly enables cancellation. Cancelled-run keys survive
restarts; partial deliveries resume without repeating known successful cancels.
GitHub cancellation cannot participate in a storage transaction: a crash between
the API response and recording success can repeat the idempotent cancel request.
An already terminal run's HTTP 409 is treated as complete. Intent and outcome
are both audited. In-flight requests may finish when the switch is flipped;
each API request checks the switch immediately before calling GitHub.

Cancellation requires all of: matching head SHA, merge_group event, nonterminal
run, gh-readonly-queue/main branch, and an explicitly allowed workflow path.
Initially the allowlist is ci.yml, migration-immutability.yml and gitleaks.yml;
#5606 PR 2 can later reduce it to ci.yml. No PR or main run is cancelled. Cron
requires a positively observed 404 for the queue ref; 403/network errors never
mean gone. GitHub reads are paginated with a ten-page bound and a 100-request
operation cap; failures retry instead of silently treating partial state as full.

Lease admission persists the counter and holder before responding. It refuses a
second active acquire; expiry/release retains the counter. Renew/release must
present the current holder and fence. Mirrors of claim refs are observation only
and cannot overwrite the server lease. They are not a second fencing authority.
If Merge Control is unavailable, sessions use #5617's cooperative claim ref and
record that fallback; it does not provide server fencing. Callers must choose one
claim authority during rollout; no cross-store atomic lease is claimed.

Verified first:

- [GitHub's webhook documentation](https://docs.github.com/en/webhooks/webhook-events-and-payloads#merge_group)
  requires **Merge queues: read** to subscribe to merge_group, in addition to
  the permissions listed in the issue. GitHub Actions supports checks_requested;
  destroyed is received through the App webhook.
- [Octokit's destroyed payload schema](https://github.com/octokit/webhooks/blob/main/payload-schemas/api.github.com/merge_group/destroyed.schema.json)
  places reason at the top level: dequeued, invalidated, merged. head_sha and
  full head_ref are inside merge_group. Only the first two reasons cancel.
- [Cancel a workflow run](https://docs.github.com/en/rest/actions/workflow-runs#cancel-a-workflow-run)
  requires **Actions: write**, not administration or workflows permission.
- App token exchange narrows tokens to this repository, contents read and
  actions write. Generated GitHub PKCS1 and PKCS8 keys are supported.
- [SQLite storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
  supports bound sql.exec queries; [Queue retries](https://developers.cloudflare.com/queues/configuration/batching-retries/)
  support per-message ack/retry and a dead-letter queue.

Validation:

- Eleven focused tests and independent typecheck pass, including real SQLite,
  controller restart, duplicate delivery, partial retries, auth, cron and a
  cryptographically verified GitHub App JWT with a PKCS1 key.
- Required mutations each exit 1: bypass signature comparison; drop the event
  filter; reuse the fencing number.
- Wrangler 4.151.1 deploy --dry-run with the dedicated config exits 0 and lists
  only RepoControl, EVENTS and REPOSITORY. Generated types come from that config.
- A real local workerd run verified unsigned 401, authenticated status, competing
  acquire 409, stale renew 409, release, rising fence, two webhook deliveries
  with one event audit row, and kill-switch-on processing without App credentials.
  Installed workerd supports dates only through 2026-10-19; local smoke uses that
  explicit CLI override. The committed new Worker's date remains 2026-11-11.
  Packaging checks the committed date but does not prove hosted runtime readiness.

Initial manual deployment (owner, after reviewing every merge-control change):

1. Create/install the GitHub App with contents read, pull requests write, checks
   read/write, actions write and **merge queues read**. Subscribe to merge_group;
   never grant workflows, administration, secrets or bypass permissions.
2. Use a dedicated Cloudflare token scoped for this independent Worker/DO and
   its Queues. Create studioos-merge-control-events and studioos-merge-control-dlq
   with the dedicated config. Do not use studioos deployment credentials.
3. With the dedicated config, install WEBHOOK_SECRET, OWNER_TOKEN, GITHUB_APP_ID,
   GITHUB_INSTALLATION_ID and GITHUB_APP_PRIVATE_KEY using wrangler secret put
   via protected input. Never put values in arguments, issues or logs.
4. Run wrangler deploy --dry-run --config wrangler.merge-control.toml; then the
   same command without --dry-run. The root production deploy command is unrelated.
5. Point the App's webhook at the new Worker's /webhook. Confirm /status while
   authenticated, inspect its local-only audit and keep the switch on for the
   first signed event. Then explicitly POST /switch with on=false when ready.
6. Set MERGE_CONTROL_CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID and
   MERGE_CONTROL_DEPLOY_ENABLED=true for the independent main-only deploy job.

No remote resources, App, secrets or manual production deployment were created
in this task; those are the issue's owner setup steps. There is no D1 migration.
