## D5877 — Admin Approvals 5/8 (b): the Inbox reads its lanes four at a time (#5877)

Part of #4716 (package 5, "parallelize independent lane reads with bounded concurrency"). It edits
the same service as D5874 and D5875. Migration: none.

**What was wrong.** `approvalBoard` and `countLanes` in `services/approvalSources.ts` awaited each
lane in turn. A branch board has 20 lanes and HQ's inbox adds its own, and the reads do not depend
on each other, so the page waited for the sum of them.

**What changed.**

- `mapBounded(list, limit, fn)` runs `fn` over the lanes with at most `limit` calls in flight and
  returns the answers in the lanes' order, whatever order they settle in. The Worker had no
  bounded-concurrency helper to reuse (`webpush.ts` bounds one send by time, not a fan-out by
  count), so it lives beside its two callers.
- `LANE_READ_CONCURRENCY = 4`. Twenty reads at once would put twenty D1 queries in flight for one
  page. Four cuts the wait to about a quarter and keeps one page to four open reads.
- `approvalBoard` reads the lanes through it, then folds them in source order. Items, lane counts,
  `unreadable` and `reason` come out as before. The oldest-first sort is unchanged and stable, so
  tied items keep lane order too.
- `countLanes` (and so `laneCounts`, `backlogOf` and HQ's pressure tiles) reads the same way. A
  lane's sub-count still follows its count inside that lane's own slot.

**What did not change.** A failing lane is still its own `null`, named in `unreadable`, never a 0,
and never fails the others. Each lane's read catches its own error, so nothing escapes
`mapBounded`.

**Test.** `cloudflare-worker/test/approval_lane_reads_5877.test.ts` compares the board and the
counts with a copy of the old one-at-a-time loop over the same data, with one lane failing. Its
fake D1 settles the lanes in reverse order, so folding answers in settle order would fail it. It
counts reads in flight and requires the peak to equal the limit: never above it, and actually
parallel.
