## D8523 — Stripe: every money-moving call sends an idempotency key, checked in CI (#8523)

- **Status:** S14, 2026-11-25 (#8523; tracker #8509 row C4). No migration, no shared helper changed. Coordinates with #8510 (S15), which changes `stripeCall()`'s API version: this change does not touch `stripeCall()` itself.
- **Basis:** `stripeCall()` (`routes/billing.ts`) takes an optional `idempotencyKey` and sends it as `Idempotency-Key`. It is optional, so each caller decides, and nobody had listed which do. Stripe replays the first answer for 24 hours when a key recurs, so a retry or a second press cannot run a charge, subscription, refund or credit twice.

### 1. The inventory

`node scripts/build-stripe-inventory.mjs` reads every `stripeCall()` in `cloudflare-worker/src` and writes `documentation/architecture/STRIPE_IDEMPOTENCY_INVENTORY.json` (generated, gitignored, D5612): file, line, method, Stripe path (`${…}` shown as `:x`), whether it moves money, and the key with its source. The reader is `scripts/lib/stripeInventory.mjs`; it makes no Stripe call. Other Stripe clients in the Worker (`integrations/providers/stripe.ts`, a read in `routes/wellbeing.ts`) are listed in `rawClients`: today they are OAuth token calls and GETs, none moves money.

- **Money-moving** is a POST that creates or confirms something that takes money (`checkout/sessions`, `subscriptions`, `invoices`, `invoiceitems`, `payment_intents` and their confirm/capture, `charges`, `payment_links`, `quotes`), a refund, transfer, payout, credit note or balance entry, or a change to a subscription (a proration can bill). `setup_intents` and `customers` are not.
- **Source of the key:** `stable` (built from the order, invoice, user, price or period), `random` (a `randomUUID`, `Math.random` or `Date.now` in the key text: a retry sends another key and protects nothing), `param` (a member the function was handed, which the reader cannot follow) or `none`. A client's per-press `nonce` is stable: it is the same on a retry of that press.

On `main` at the time of writing: 111 `stripeCall` sites, 24 money-moving; 11 sent no key and 1 took its key from its caller before this change.

### 2. The check

`node scripts/build-stripe-inventory.mjs --check`, a guard in `scripts/guard-commands.json` (so `npm run test:guards`), fails on:

- a money-moving POST with no key, a random key, or a key from its caller, that is not on the allowlist;
- a POST to a path held in a variable (the check cannot tell whether it moves money);
- an allowlist entry with no reason, no matching call, or a wrong count (the list only records what is still true);
- a raw Stripe client POST to a money-moving path;
- fewer than 100 calls or 15 money-moving calls found (a scan that finds nothing cannot pass).

### 3. What the inventory found and what changed

Eleven money-moving POSTs sent no key, and one more took its key from its caller:

| Call | Resolution |
|---|---|
| `POST /subscriptions` (plan checkout, `billing.ts`) | Fixed: `planSubscriptionKey(user.uid, priceId)`. |
| `POST /subscriptions/:id` (plan swap confirm, `billing.ts`) | Fixed: `planSwapKey(user, sub, fromPrice, toPrice)`. A swap is a real change that can be made again, so its key carries a ten-minute window: a double press repeats it, a deliberate swap back later does not. |
| `POST /invoices`, `/invoiceitems`, `/invoices/:id/finalize` (incorporation fee, `legal.ts`) | Fixed: `incorporationKey(incId, step)`; the pending order's id names the invoice. |
| `POST /checkout/sessions` ×4 (`billing.ts` ×3, `legal.ts`) | Allowlisted: an unpaid Checkout Session moves money only when the customer completes it. |
| `POST /subscriptions/:id` ×2 (cancel/resume, default card) | Allowlisted: each sets a value; repeating it leaves the same state. |
| `createPaymentIntent` in `payments.ts` | Allowlisted: its key comes from its three callers, each `pi:<user>:<price or pack>:<promo>:<nonce>`. |

Existing keys that name a per-press `nonce` (`billing_checkout.ts`, `orders.ts`, `payments.ts`, the auto-reload attempt) were already stable and are read as such.

### 4. Keys

`cloudflare-worker/src/util/stripeKey.ts` builds the new keys and `cloudflare-worker/test/stripe_keys_d8523.test.ts` sends two identical calls through `stripeCall` with `fetch` replaced and asserts the same `Idempotency-Key` header. The scan's own tests (`scripts/lib/stripeInventory.test.mjs`) include a fixture with an unkeyed charge that fails the check.

### 5. Not done

- The route-level behaviour of the plan checkout, swap and incorporation routes is not exercised end to end: those routes need a step-up session and a catalog fixture. The test covers the keys and that the call sites send them (source assertions), not a full HTTP run.
- A Checkout Session is not keyed. If a duplicate session ever matters, key it by user, price and window the way the swap is.
