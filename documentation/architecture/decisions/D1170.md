### 1. The guard

`assertStorageRoom(env, owner, incomingBytes, caller)` runs before the R2 write.

**Whose plan.** The owner is `{ userId }` for a personal file, or `{ projectId }` for a venture's file. A venture's file counts to the company's first primary admin, else the venture's founder: D1169 §1's rule, the same SQL its read uses.

**The refusal.** When the bytes the plan already holds, plus the file, would pass the allowance, the write is refused before anything is stored:

```
413 { error: 'storage_full', message, used_bytes, allowance_bytes, incoming_bytes, plan_key, counts_to }
```

- `counts_to` is `you` or `company_owner`, and the message says which. It names no person and no file.
- It is thrown as a Response. Every route's `mapError` and the app's `withThrownResponses` answer it as it is.
- Two callers catch errors broadly, so each turns it into its own error type with the same words:
  - the channel intake (`IntakeError`);
  - Mercury's statement accept (`AcceptError`).
- The headshot route passes it through instead of turning it into its 400.

**Who passes.** Each pass is logged by its reason only, with no name, key or figure:
- staff uploading;
- a file that counts to a staff account, which has no allowance (D1167);
- a negotiated plan, whose allowance is not a figure we hold;
- a venture whose files count to no member;
- a plan or stored bytes we cannot read. A read failure of ours never refuses a member's file.

**Never delete, hide or cut** (#2449 owner questions 4 and 5, A). The guard only refuses a new write. Every stored file stays readable and downloadable.

**What it weighs.** The bytes are D1169's `measured_bytes`, so with files of unknown size they are a floor. A file that replaces another is weighed whole. Data room Replace keeps the old version, which still counts. A replaced Build proof is deleted after the new one lands.

### 3. The notices

`noteStorageLanded(env, ticket)` runs after the write lands. It sends one in-app notice (`storage_threshold`, category `billing`, link `/account/usage/storage`) to the member the file counts to, for the highest threshold the file crossed:
- 80% and 95%: "You have used N% of your X of storage". It says nothing changes yet, and that stored files are never removed.
- 100%: "Your storage is full: X used". It says new uploads are paused, and every stored file stays readable and downloadable.

**No ledger: the crossing is the record.** A threshold is crossed when the bytes before the file were under it and the bytes after it reach it. This is why no migration is needed. Falling back under a threshold and rising again (after an upgrade) is a new crossing. A notice that cannot be sent never undoes a stored file, and is never thrown.

**Limits, stated:**
- A session's chunks send no notice, because they are never weighed.
- A plan change crosses nothing, because nothing was written.
- Two uploads at the same instant can each see the same "before". The worst case is a second notice. The bytes are still counted.

### 4. `GET /api/admin/platform/storage`

`requireSuperAdmin`, and `private, no-store`. It answers totals only: no name, email, id, uid or file name. A test walks the payload for keys and strings that would name anything.

**What it carries:**
- **`totals`:** members, files, measured bytes and files of unknown size.
- **`by_kind`:** the six kinds, in the canvas's order.
- **`by_plan`:** each catalogue plan, with its allowance or reason, its members and their measured bytes.
- **`by_state`:** members in each state (`ok`, `near_80`, `near_95`, `full`, `over`, `no_allowance`), and `not_measured` for a negotiated plan.

**One rule, not a second copy.**
- **Bytes:** each member's come from a per-owner statement beside each area's own query in `storageUsage.ts`. A test proves that, for every member, they equal that member's own Storage read: files, bytes, unknown sizes and kinds.
- **Plans:** come from `chooseStoragePlanKey`, the rule `storagePlanKey` applies, fed in batch. It reads users, subscriptions and fund admissions in three statements, so the read does not grow with the number of members.
- **One difference:** an LP admission counts here only once the LP row is linked to the account. The member's own read links a row matching their verified email the first time it runs (D1167). This read writes nothing.

**What cannot be read is said.**
- **An area that fails** is named in `unreadable_areas`. Every member's bytes are then a floor, so `by_state` and the bytes by plan are null, with the reason.
- **A failed plan read** blanks the plan and state blocks only.
- Nothing is guessed.

The page is part 6's (#3085, STG20). `api.hqPlatformStorage` is its client.
