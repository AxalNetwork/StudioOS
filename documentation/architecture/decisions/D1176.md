## D1176 — Use of funds reads, scenarios and audit

Issue #3103, part of #2455. S29 · Codex. Builds on D1175/migration 606;
no new migration, binding, AI surface or screen.

### Built

`cycle_use_of_funds.ts`, mounted by `cycle_raise.ts`, owns
`/api/cycles/raise/use-of-funds`. Every call takes `?project=<id>`, checks
`canWrite`, active company and a non-deleted venture. Foreign ids and outside
roles are refused. Support cannot write; admin activity says Studio admin.

- `GET /plan`: independent base, round, runway_today, forecast, ties and
  needs_you blocks. Failed blocks stay Unreadable; good blocks remain readable.
- `GET/POST /scenarios`, `GET/PATCH/DELETE /scenarios/:id`,
  `POST /scenarios/:id/make-base`, `GET /compare?ids=1,2,3,4`.
  Lists use `{ items }`. One scenario includes lines, milestones, venture-wide
  hires, D1175's model and its input snapshot. Compare preserves up to four
  distinct scoped ids in order, separating measured today from models.
- `GET/POST /milestones`, `GET/PATCH/DELETE /milestones/:id`: optional
  scenario_id selects Base when omitted. OKRs belong to this venture and
  appear once per scenario. Null cost is Not costed; zero is recorded.
- `GET /hires`, `PATCH/DELETE /hires/:id`. Existing Add hire remains, with
  an atomic admin-attributed audit.
- The module PUT and record-drawer Edit split share the dual writer. Base
  edits and promotion atomically project the five-section split, dollar raise,
  target, milestones and OKR costs to legacy project fields, preserving other
  metadata and invalidating deck sync. Alternatives do not change them. Base
  deletion is refused, including a promotion racing a deletion. Stale edits also check the Base flag inside
  their batch. Deleted promotion/copy targets leave the existing Base intact,
  make no partial changes or false audit, and answer 409 to read again.
  Legacy-only milestone/cost entries added by the existing projects writer
  after the one-time copy are retained; they are not silently imported into
  the scenario model. Only the prior Base's matching projection is replaced.
  A conflicting later edit of the same key refuses with 409
  `legacy_plan_changed`, preserving both stores and recording no false audit.
- Forecast keeps the strict `/api/financials/:projectId` store, drivers and
  source marks; saving and forecast_saved now commit together.

The client is `frontend/src/lib/api/useOfFunds.js`, exported by the API barrel.
UI integration remains #3104/#3105.

### Contract and sources

Scenario create/patch accepts name, amount_to_raise_cents,
target_runway_months (1–120), currency, start_month, raise_month, cash_cents
and lines. Creation may copy a scoped from_id. Lines are
`{ key, share_pct, sublabel? }`: five fixed keys, total 100 or all unknown.
Patch preserves omissions; null and zero stay distinct. Base is USD because
legacy amounts record dollars. Other currencies stay alternatives.

Milestones accept scenario_id, category_key, label, due_on (month/real date),
cost_cents and okr_id. Patches cannot transfer scenarios. Hire patches accept
category_key, role, start_month, annual_cents and currency. Unknown fields,
including supplied AI/connector provenance, are refused. Historical copies
retain Recorded origin; computed outputs stay Modelled.

The D1175 copy deliberately refuses malformed legacy input or stale OKR cost
keys rather than discarding them. Writes now expose 409
`legacy_plan_repair_required` and name the existing authenticated correction
route, `PUT /api/projects/:id`. Its `use_of_funds`, `funding_needed` and
`use_of_funds_meta` fields can be explicitly corrected after reading the
stored project; retrying the split then creates Base. No automatic lossy
fallback is used. The active-founder requirement remains D1175's ownership
boundary. A milestone can still be deleted after its former OKR disappears.

Round precedence is an approved sent/closed call with a current terms hash,
then the active round target, then plan raise. All amount/currency disagreements
are listed. Cap-table rounds are compared without overriding precedence.
Its tie reads the canonical cap-table scenario's actual inputs/result.
Migration 606 stores no explicit per-plan cap-table link: that link says
Not recorded; no link or dilution value is invented.

Runway today uses only the founder caller's own active cached Mercury fact
outside support, then connector metrics, then Typed metrics, each dated.
Other users' connections, even malformed legacy associations, are excluded.
Admin/support omit Mercury facts and Mercury-labelled metrics. No provider is
called. Failed Mercury can fall back to dated metrics while reporting failure.
The retained forecast is Modelled and never supplies runway today.

Scenario/milestone writes log uof_scenario_created|updated|made_base|deleted
and uof_milestone_created|updated|deleted; hire edits log uof_hire_updated|deleted.
forecast_saved and retained split_saved/hire_added are scoped and attributed.
Each write and audit is one bound D1 batch; failed audit rolls it back. New
audit summaries are fixed outcomes, without amounts, dates or business text.
Old audit rows remain. Generic errors ask the caller to reread before retrying,
without falsely claiming an uncertain write did not happen.
