### 1. The trigger (`routes/cycle_verdict.ts`, `services/buildPlanState.ts` `onDecision`)

After `recordDecision` commits, the route calls `onDecision` in `waitUntil`, or inline where there is no execution context. What happens depends on the decision:

| Decision | What happens to the plan |
|---|---|
| Withheld | Nothing is prepared. |
| A given Proceed or Pivot | D1065's `preparePlan` runs for the decision's scope, with trigger `decision`. |
| A given Stop | The plan pauses (§3). |

- **A Proceed on one hypothesis** plans scope `h-<id>`, so only that claim and its themes are read.
- **A Pivot** reads its new claim (D1065's `readEvidence`), so it plans a prototype test of that claim and no must-haves.
- **The trigger is rules only.** It runs no model and writes no usage-log row.
- **A failure never fails the decision.** The decision is already committed when the trigger runs. A failure is logged as an outcome (`[build-plan] decision trigger: <code>`) and the route still answers 201.
- **Only the venture's own founder's Proceed or Pivot prepares a plan.** An admin may record a decision (`canWrite`), but D1065 forbids an admin preparing a plan for a founder, so an admin's Proceed prepares nothing. An admin's Stop still pauses.

### 2. Withheld and "Plan anyway" (VB14)

A withheld decision prepares nothing. "Plan anyway" is D1065's own `POST /api/cycles/build/plan`, trigger `manual`, which still prepares on withheld evidence. As D1065 rules it, a withheld decision unlocks no must-have and no formation step. Raise's "resting on withheld evidence" line is part 6's to draw, from the decision's state.

### 3. Stop, pause and resume (owner question 9)

**A given Stop pauses the open plan.**
- A venture Stop pauses every draft or open plan of the venture.
- A hypothesis Stop pauses only that scope's plan.
- Accepted items keep their status.
- A paused plan prepares nothing: `preparePlan` refuses `plan_paused`.
- A paused plan sends nothing: D1068's handoffs read `status`.

**Routes** (`routes/build_plan_state.ts`, mounted at `/api/cycles/build/plan` before D1065's router):

| Route | What it does |
|---|---|
| `POST /pause` | The founder's "Pause the plan" (VB1's More menu). Pausing twice is not an error. |
| `POST /resume` | Reopens a plan the founder paused: `open` once any item was decided, else `draft`. |
| `GET /since` | §5. |

- **Resume is refused while a given Stop stands** for the venture or that scope: 409 `plan_stopped`, "Your verdict is Stop. Record a new decision to resume." This is VB14's line.
- **Who may call what.** Pause and resume use D1065's write gate (the venture's founder or an admitted Lab owner). An admin reads `/since`. A partner gets 404 on all three, because they describe the private plan.

### 4. A newer given decision

`preparePlan` supersedes the current plan when the decision differs from the plan's, and **a paused plan too**, but only for the `decision` trigger. A manual press on a paused plan is still refused.
- The plan's undecided proposals withdraw.
- Accepted, edited and discarded items stay as they are (D1065).
- The new plan becomes current.

So a Stop, then a new Proceed, gives a fresh plan; this is "Record a new decision to resume". Re-running the same decision prepares no second plan.

### 5. New evidence since the plan (VB13)

`GET /since` answers `{ plan, status, changed, new, contradicting }`:

- **`changed`** compares the plan's SHA-256 `evidence_hash` with today's projection, hashed the same way: `evidenceHash`, extracted from `preparePlan` unchanged.
- **`new` and `contradicting`** count the `evidenceFor` items in the plan's scope that the plan was not prepared on, and how many of those contradict.
  - At preparation, the plan keeps the ids and directions of those items inside `brief_json` under `_seen`.
  - `readPlan` strips `_seen`, so it is never served.
  - The items sit beside the projection, not in it, so the hash means what D1065 made it mean.
- **A plan prepared before D1067 kept no list.** Its counts are `null` ("Not recorded"), never 0; `changed` still answers.
- **A failed read is 503**, never "no new evidence".
- **"Update the plan"** is D1065's `POST` with trigger `update`. It takes the new evidence in and, as D1065 rules, never changes an accepted item.
