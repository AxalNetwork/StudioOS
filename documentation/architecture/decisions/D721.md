## D721 — CodeQL and Semgrep ask on every run whether code scanning takes an upload, and upload only when it does

Issue: none; S1 hotfix, 2026-10-18. It amends D718, which put the uploads back while the repository was public, and keeps D672's job-summary report.

### Why

- **The repository is private again.** On 2026-10-18 the repository API answers `visibility: private`, and `security_and_analysis.code_security.status` is `disabled`. A private repository needs GitHub Code Security for code scanning, so every upload is refused with "Code Security must be enabled for this repository to use code scanning".
- **Every PR went red.** `analyze (javascript-typescript)` failed on `main` at ca870de16 (job 117551505720, at its upload). Then, while no scan had failed:
  - CodeQL's `Perform CodeQL Analysis` failed on #1813, #1814 and #1817;
  - Semgrep's `Scan` failed at `Upload SARIF` on #1817.
- **It has happened twice.** D672 stopped the uploads for this reason on 2026-10-10, and D718 restored them when the repository went public on 2026-10-17. A fixed setting is wrong whenever the visibility changes. So the workflows now read it on each run.

### What was decided

#### The `visibility` job (`codeql.yml`, `semgrep.yml`)

- Both workflows start with the same job, `visibility` ("code scanning takes uploads?"). It runs `gh api repos/$GITHUB_REPOSITORY` with the workflow's token and reads two fields:
  - `private`;
  - `security_and_analysis.code_security.status`. It reads `unknown` when the token cannot see it.
- It outputs `upload=always` for a public repository, or for a private one with Code Security `enabled`.
- It outputs `upload=never` for a private one otherwise, with a notice that the findings are in the job summary only.
- Any other answer, or a failed API call, fails the job. A red check then still means that something could not run.

#### How each scanner uses the answer

- CodeQL's `analyze` job `needs: visibility` and passes `upload: ${{ needs.visibility.outputs.upload }}` to `github/codeql-action/analyze`. It still writes `codeql-results/`, and the report step still reads it.
- Semgrep's `scan` job `needs: visibility`. Its `Upload SARIF` step takes `if: needs.visibility.outputs.upload == 'always'`.
  - That condition holds no status function, so the default `success()` still applies. A failed, cancelled or timed-out scan never uploads, as D170 and D718 require: an upload replaces the alert set, and a crashed scan's resultless SARIF would close every open alert.
- Findings still never fail either job. The job summary lists them either way.

#### Tests

- `frontend/test/code_scanning_visibility_d721.test.mjs`:
  - the two `visibility` jobs are identical, and both scanning jobs need theirs;
  - the step runs with a stand-in `gh` and gives each answer its output, failing on anything else;
  - the step's `jq` expression turns the repository JSON into those answers.
- `code_scanning_upload_d718.test.mjs` pins `upload:` to the visibility output and the Semgrep upload's exact `if:`.
- `semgrep_workflow.test.mjs` reads the `scan` job's steps, not the first `steps:` in the file, and accepts that one `if:` on the upload.

#### Also in this PR: no `node_modules` is tracked (e4aa55694)

- **What happened.** A merge commit on #1824's branch (e5956580f) committed a symlink, `cloudflare-worker/node_modules -> /home/user/StudioOS/cloudflare-worker/node_modules`. In a checkout at `/home/user/StudioOS` it points at itself.
- **What it broke.** Git treats an ignored directory as expendable. Checking out a commit that tracks the symlink therefore deletes the real `cloudflare-worker/node_modules` and puts the symlink in its place, without a warning. After that, every Worker import fails, for example "Cannot find package 'jose' imported from cloudflare-worker/src/auth.ts". S1's checkout lost its Worker packages this way on 2026-10-18. Checking out this fix removes the symlink, so `npm ci --prefix cloudflare-worker` brings the packages back.
- **Why it slipped through.** `.gitignore` said `node_modules/`, and a trailing slash matches only a directory, never a symlink. Agent worktrees link `node_modules` to the main checkout's packages, and `git add -A` then commits the link. 645aab7c3 did the same before; 4914a121b removed it.
- **The fix.** The symlink is removed, and `.gitignore` says `node_modules` with no slash.
- **The guard.** `repo_layout.test.mjs` fails when `git ls-files` lists any path with a `node_modules` segment. It also fails when `git check-ignore --no-index` stops ignoring a `node_modules` that is not a directory.
- **The temp leak (2f9c07794).** `profile_pages_d702.test.ts` built a template database in a `mkdtemp` folder of about 0.5 GB and never removed it. A few full Worker suites in one container fill the disk, and the next suite fails with "database or disk is full". An `after()` now removes the folder.

No migration, no Worker change and no new dependency.

### If the repository goes public again

Nothing needs to change. The next run reads `private: false` and uploads. The alerts return to the Security tab, where Copilot Autofix can propose fixes again.
