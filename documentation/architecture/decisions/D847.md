## D847 — One MCP client for every MCP provider, with Mercury as its first user

- **Status:** filed by S1 as #2468 (part of #2463) at the owner's request, 2026-10-21. It is #2404's shared client: "How it connects" and "Backend", within the files #2468 owns.
- **Basis:** `origin/main` at `56c2498983`. Worker paths are relative to `cloudflare-worker/src/`.
- **Spec read:** the MCP specification's source, `github.com/modelcontextprotocol/modelcontextprotocol` at `80041ab` (2026-10-20), `docs/specification/2026-07-28/` and `schema/2026-07-28/schema.ts`, read through git on 2026-10-21 (the published site is refused by the container's network policy, as #2404 found).
- **Stacks on:** D840 (Mercury's MCP client and sign-in), #1903 (the refresh lease), D753 (the connector pages) and D710 (Mercury is read-only).
- **Separate from D784.** `src/mcp/` is StudioOS's own MCP server, which outside assistants call. This decision is the other direction, and the two never import each other (`mcp_client_d847.test.ts`, case 2).

### 2. Mercury moves without a behaviour change

- **Same requests.** Mercury's record is `legacy`, budget 24, 10 s per POST. The legacy session sends what D840 sent, byte for byte: `initialize` with `2025-06-18`, the server's `Mcp-Session-Id`, `notifications/initialized`, up to five pages of `tools/list`, and POST only. The D840, D713, D752 and D710 suites pass with no test edited.
- **Same error words.** The shared client's new words map onto D710's:
  - `too_large` becomes `http_error` 413;
  - `scope_insufficient` becomes `unauthorized` 403;
  - `unsupported_protocol` becomes `http_error`.
- **The legacy names stay:** lease and state provider `mercury_mcp`, DCR prefix `mercury_mcp_client:`, and the callback path registered with Mercury. So a live row, its stored `client_key` and a sign-in in flight across the deploy all keep working.
- **New checks only narrow.**
  - The 2 MB body cap is far above a 500-row page; the statement PDF keeps its own 15 MB path in `reads.ts`.
  - A read tool the server annotates as writing is refused; Mercury's fake lists none.
  - A drift line is written; nothing else is.
- **One test outside D840 changed.** `connector_pages_d753.test.ts` now lists `integrations/mcpClient.ts` among Mercury's sources, because the `jsonrpc: '2.0'` POST that names Mercury's MCP reads moved there. Every POST in the shared client still sits within D753's window of a fragment Mercury's page already names: `jsonrpc: '2.0'`, `server.registration_endpoint`, `server.token_endpoint` or `server.revocation_endpoint`.

### 3. Session: held or per request (#2468 scope 3)

- **Decision: per request, for every provider.**
  - A `legacy` server's `Mcp-Session-Id` lives in memory for one Worker request; the server expires it, as D840 does today.
  - A `modern` (`2026-07-28`) server has no session at all: the spec removed `initialize` and `Mcp-Session-Id`, and every request carries its version and capabilities in `_meta`.
- **So there is no session row in D1 and no Durable Object.**
  - The record's `session` field is the literal `'per_request'`.
  - A provider whose server needs a session across requests must widen that type and amend this decision first.
  - A Durable Object is warranted only for a stream that must outlive a request, such as `subscriptions/listen`. No provider issue reads one.
- **What is stored instead:** the era an `auto` probe found, in `config_json.era`. The caller passes it back as `era`, so later sessions skip the probe. The spec says the era is a property of the origin and may be cached.

### 4. Tool allowlist pinning (#2468 scope 4)

- **Every session compares** the server's `tools/list` with the record, on connect and on every later read or sync.
- **Never called, and logged:**
  - `unknown`: a listed tool on neither `read_tools` nor `write_tools`;
  - `annotated`: a read tool annotated `readOnlyHint: false` or `destructiveHint: true`. Annotations can only narrow the list;
  - `invalid`: a read tool whose `x-mcp-header` breaks the spec's rules, which the spec says to exclude;
  - `changed`: a pinned tool whose schema fingerprint differs from its pin.
- **The log line.** One `console.warn` per session: `{"event":"mcp_tool_drift","provider":…,"tools":[{tool, why}]}`.
  - Names only, and only printable ones (`(unprintable)` otherwise), at most 50 entries.
  - Never a description, a schema, an argument or a result.
- **The fingerprint** is SHA-256 of the tool's `inputSchema` and `outputSchema` in canonical JSON. A reworded description does not change it; a new parameter does.
- **Pins live in the frozen record** (`tool_pins`), so a schema change needs a reviewed code change.
- **Mercury's pins are `null` for now.** The tool schemas were never read from the live server: D840 lists them UNVERIFIED, and `mcp.mercury.com` is unreachable from the building container. Until the owner's first live sign-in records them, Mercury is checked for unknown and annotated tools, but not for changed schemas. That is exactly D840's behaviour today. Recording the pins is a follow-up for that sign-in.
- **Write tools are never callable from this client.** Each is refused before any request, even on a record whose `publish_issue` lists one, because #2400's confirm ticket does not exist. A test holds every record with `publish_issue: null` to an empty `write_tools`.

### 5. Discovery, registration, sign-in, refresh and revoke

- **Discovery** generalises D840's `oauth.ts`:
  - RFC 9728 metadata comes from a 401's `resource_metadata` first, when that URL is on the record's hosts, then from the path-form and host-form well-known URLs. Its `resource` must equal the one asked for.
  - RFC 8414 metadata comes next, then OpenID's. The `issuer` must be identical, S256 must be offered, and every endpoint must be https on the hosts, with no userinfo or port.
  - Every fetch uses `redirect: 'manual'`, a 10 s deadline and a 64 KB body cap.
- **Registration** follows the record's order:
  - **Pre-registered:** the provider issue supplies a loader, env first, then `provider_oauth_keys`.
  - **CIMD:** used when the server advertises `client_id_metadata_document_supported` and the record's `cimd_url` is https on `axal.vc`.
  - **DCR (RFC 7591):** a public `"Axal VC"` client with `application_type: "web"`, once per redirect URI, stored in `platform_settings` under the record's prefix. A stored client from another issuer is never used: the provider is registered again. The first stored registration wins a race (`INSERT OR IGNORE` and a read-back), and a test holds the slower caller to it.
- **Sign-in:**
  - The authorize URL carries the record's scopes, `resource` (RFC 8707) and S256.
  - `issuerAccepted` implements RFC 9207. `iss` is required when advertised and byte-equal when present. On `false` the callback acts on nothing, not even `error`.
  - The exchange sends `resource`. A grant beyond `accepted_scopes` has both of its tokens revoked and is refused (`scope_refused`).
- **Refresh** runs 60 s before expiry, or after a 401, behind `acquireRefreshLease(env, record.lease, uid)`:
  - The winner re-reads the row first.
  - A loser polls the row for the winner's tokens: #1903's six polls 500 ms apart, as HubSpot's refresh does.
  - D840's Mercury code re-reads only once, so a loser that reads before the winner has stored refreshes with a rotated refresh token and marks the row `token_rejected`. The shared client closes that gap. Mercury's own `oauth.ts` keeps its copy until Mercury's sign-in moves onto the shared OAuth.
  - A refused refresh, or one reporting a wider scope, marks the row `error` / `token_rejected`.
  - There is no step-up: a 403 `insufficient_scope` is its own word, and the client never asks for more.
- **Revoke** (`revokeMcpConnection`):
  - It calls RFC 7009 for the refresh token, then the access token, when the server has a revocation endpoint (best effort).
  - Then it deletes the stored tokens (`credentials_enc = NULL`, `status = 'disconnected'`), whatever the provider answered.
  - `provider_revoked: false` tells the page to send the member to the provider's own settings.
- **Credentials:** a v2 blob is D840's `McpCredentials` plus `v: 2` and `resource`. A blob without `v` reads as version 1 on the record's default resource. Today's `mcpCredentialsOf` in `services/mercury/oauth.ts` reads a v2 blob, because it checks only `access_token` and `client_key`. So a rollback is safe.

### 6. Limits and the era

- **Budget:** every POST counts, the `auto` probe and the legacy handshake included. A spent budget is `rate_limited` before the request. A caller may lower the record's budget, never raise it.
- **Deadlines:** 10 s per POST and per body read, inside a 25 s session wall (#2404's proposal).
- **Body cap:** 2 MB, counted as the body streams (#2404's proposal), and `too_large` above it.
- **No redirects:** any 3xx is `redirect_refused` and is not followed. The bearer goes only to one of the record's `resources`.
- **Modern requests** (`2026-07-28`, `streamable-http.mdx` "Request Metadata"):
  - Every request carries `MCP-Protocol-Version`, `Mcp-Method` and `_meta`'s three keys.
  - `tools/call` also carries `Mcp-Name` and one `Mcp-Param-<name>` per `x-mcp-header` parameter.
  - A value that is not safe ASCII is sent as `=?base64?…?=`, as the spec requires, not refused as #2404 had proposed.
  - A result whose `resultType` is not `complete` (it asks for input) is `http_error`.
- **`auto`** (spec `versioning.mdx`, "Backward Compatibility"):
  - It sends one modern `tools/list`.
  - A 400, 404 or 405 without a recognised modern error (-32020 HeaderMismatch, -32021 MissingRequiredClientCapability, -32022 UnsupportedProtocolVersion) means a legacy server, so it sends `initialize`.
  - An UnsupportedProtocolVersion that lists a legacy version also falls back. One that lists only newer versions is `unsupported_protocol`.
- **Headers:** the record's fixed headers and a connection's own must be tokens with safe values, and never a reserved name (`Authorization`, `Mcp-*`, `Content-Type`, `Accept`, `Host`, `Cookie`). Otherwise the session is refused before any request.

### 7. Security

- **Hosts are allowlisted per provider.** Every discovered endpoint, the token endpoint and the revocation endpoint are checked against the record's `hosts`, and a foreign `resource_metadata` is never fetched.
- **Remote text is data.**
  - A tool description is never read, kept, logged or shown.
  - A result goes only to the provider's typed reads.
  - Neither can add a tool, a scope or a host: the record is frozen, and the session reads nothing else.
- **Tokens are encrypted as today:** `encryptCredentials`, AES-GCM under `KEK_PII`, bound to the row uid. A DCR client secret is encrypted with `encryptColumn`, as D840 does.
- **Nothing credential-shaped** reaches a log, an error or the drift line (case 11). Errors are a code and a status.
- **SQL:** bound statements only, with no raw interpolation. The `schema_guards` count is unchanged.
- **No migration:** `integrations`, `platform_settings` and `RATE_LIMITS` already exist.
