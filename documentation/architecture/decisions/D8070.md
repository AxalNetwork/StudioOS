## D8070 — Agent capability RBAC: a named capability set per agent, checked in the Worker (#8070)

- **Status:** built 2026-11-21. The Worker, its migration, the client module and the tests are in this change. Enforcement is switched off until HQ turns it on; the five reserved names are refused from the first deploy. The HQ screen (boards SA10 to SA14) waits on the canvas (`needs-design`) and ships in a second PR on #8070.
- **Builds on:** D1528 (run admission), D4162 (HQ's AI policy row and its audited writes), D4163 (the admin audit), D5567 (per-member authz revisions), D5569 (the publisher broker). Tracker: #8059.

### Why

An agent's reach was set by its role, its sponsor's read-tool grants and the module of the task it was given. Nothing named what a given agent may do across the product, so a founder could not deploy, for example, a Market Research Agent with `research.*`, `company.read`, `fund.read` and `web.search` and know it could do nothing else.

### What

**Names.** A capability is `<domain>.<action>`. The catalogue (`capability_catalog`, seeded by the migration and copied in `CAPABILITY_CATALOGUE`) holds twenty grantable names and five that exist only so a refusal can name them: `code.merge`, `deploy.production`, `cloud.write`, `finance.execute` and `email.send` are done by a person and are never grantable to an agent.

**Grants.** `agent_capabilities` holds one row per grant (agent, name, who, when, reason). A revoke stamps the row; it is never deleted, so the matrix can say who granted and revoked what. A partial unique index keeps one live grant per agent and name. A wildcard (`research.*`) expands at grant time into one row per grantable name in that domain, never at check time, and never into a reserved name. Each grant and revoke bumps the sponsor's `agent_authz_revisions` row through two triggers (D5567's pattern), so a broker grant minted before the change is refused at its next use.

**The check.** `requireCapability(env, agent, name)` in `services/agentCapabilities.ts` answers ok or a refusal:

| Code | Status | When |
|---|---|---|
| `capability_ungrantable` | 403 | a reserved name, always |
| `capability_unknown` | 403 | a name the catalogue does not hold, always; an action that declares no capability, once enforced |
| `capability_not_offered` | 403 | outside the platform's ceiling this month, once enforced |
| `capability_missing` | 403 | no live grant on the agent, once enforced |
| `capability_unreadable` | 503 | the policy or the grants could not be read: refused, never assumed |

It is called once at each guarded site:

| Site | Capability |
|---|---|
| Run admission, `agents/engine.ts` `admitInScope` (both runtimes, every trigger: a person, the sweep, `after`, a duty) | the task's module as a domain action, `MODULE_CAPABILITY` (every module in the catalogue has one; a test walks `MODULES`) |
| Compute request, `services/agents/computeBridge.ts` `createComputeRequest` | `cloud.read` |
| Publication, `services/agents/agentPublisherBroker.ts` `executeAgentPublication` | `code.pr`, for the agent the provenance names (`agent:<id>` or its uid); any other reference holds nothing |
| A skill's tool, `services/agents/skillLinks.ts` `attachCheck` (attach, the available list, the add-agent route) | each tool's declared capability, by connector (`CONNECTOR_CAPABILITY`); a connector with none is refused once enforced |
| Preview deploy | `deploy.preview`. No preview trigger exists on main; the one that lands calls the check. |

The skills runner makes one model call with no tool loop (`skillRuntime.ts`), so a skill's tools are checked where they are granted to the agent, at attach.

**Rollout (owner question, option A built).** `ai_agent_policy.capabilities_enforced` starts at 0: only `capability_ungrantable` and a named unknown are refused, so the agents already working keep working while HQ grants their sets. A Super Admin turns enforcement on with a reason. A database whose schema predates the migration reads as not enforced (the deploy applies migrations before the Worker ships); any other read failure refuses. The ceiling (`capability_ceiling_json`) is null at the start, which offers every grantable name.

**Routes** (`routes/admin_ai_agents_policy.ts`, Super Admin only, every write takes a reason of 1 to 200 characters and writes the admin audit row, before and after, in the same batch):

- `GET /api/admin/ai-agents/policy/capabilities`: the catalogue, the policy, each live agent's cells (granted, by whom, when, why; or the last revoke).
- `POST …/capabilities/grant { agent_uid, capabilities, reason }`, `POST …/capabilities/revoke { agent_uid, capability, reason }`.
- `PUT …/capabilities/ceiling { capabilities | null, reason }`, `PUT …/capabilities/enforcement { enforced, reason }`.

A revoke takes effect at the agent's next run; a live run finishes (the issue's question 2, option A). The matrix is per agent (question 1, option A); "apply to role" is a screen action over the same grant route.

The client is `frontend/src/lib/api/aiAgentsPolicy.js` (`aiAgentsPolicyApi`). The panel's refusal sentences are in `frontend/src/pages/hq/aiAgents/refusals.js`.

### Questions for the owner

1. **Turning enforcement on.** A) a switch on the policy, off at deploy, flipped by a Super Admin once the live agents hold their sets (built). B) enforce from the deploy and seed every live agent with its modules' capabilities in the migration. C) enforce per agent once it has any grant. I pick A: B guesses each agent's set, and C leaves an agent with no grants unchecked for good.

### Rollback

Turn enforcement off (`PUT …/capabilities/enforcement { enforced: false }`): every check but the reserved names answers ok. The tables and columns are additive and can stay. Reverting the code removes the checks; the migration needs no reversal.

### Tests

`cloudflare-worker/test/agent_capabilities_8070.test.ts`: the seeded catalogue equals the service's and the five reserved names are its only ungrantable ones; a reserved name is refused at check time enforced or not, by the grant route, and by every wildcard; admission on both runtimes, the compute request, the publisher and a skill's tool each refuse with the capability's code once enforced and pass once granted; a revoke refuses the next run; the ceiling refuses outside it; the routes are Super Admin only, need a reason, audit before and after, and bump the sponsor's revision on grant and revoke; an older schema reads as not enforced and any other failure refuses.
