## D4717 — Community: one population per count, the roster from the server, one clock (#4717)

**Admin Community audit, slot S26 · 2026-11-06.** Packages 1 and the clock half of 3. No migration. The rest of #4717 follows in later PRs (see "Still to do").

### What was wrong

- **The check-in band counted everyone.** The band is labelled as founders, and its privacy floor is seven. It counted every distinct `user_id` in `wellbeing_daily_pulses`, so five founders and six investors showed a band that should have been withheld.
- **The roster was counted from a capped list.** The roster tile, the Circles card and the consoles strip all counted `GET /api/admin/network-profiles`, which answers 200 rows by default and says `truncated`.
- **Archived profiles were in the network totals.** The server's network aggregate (`blocks.network`) counted archived profiles (migration 551, `archived_at`) as inactive roster members.
- **The clock was frozen at mount.** The page's clock was `useState(() => Date.now())`, so Refresh fetched new rows but measured days open, waits and Overdue from the moment the page was first opened.

### What changed

- **Check-ins (`services/communityOverview.ts`).** The band counts distinct `user_id`s whose account's role is `founder`, joined to `users`. A pulse whose account is gone counts for nothing. Still no answer column is read.
- **Network block.** It is grouped by kind and state:
  - **active:** `is_active = 1`, not archived;
  - **hidden:** not active, not archived;
  - **archived:** `archived_at` set.

  Archived rows are reported only as `archived`, in no total. The new `by_kind_state` gives each kind's active and hidden counts. `by_kind`, `active` and `inactive` keep their meaning, without archived rows.
- **The page's roster (`communityModel.rosterOf`).** The roster comes from that block, over every row, and the page no longer calls `network-profiles`. A count that is missing, negative or not a whole number makes the roster unreadable, never 0.
- **The page's clock (`communityModel.clockOf`).** The clock is the Community read's `as_of`. Before that read answers, it is the time the page's reads last settled. Refresh brings a new `as_of`, so every time-relative figure moves with it.

### Package 4 — the Jobs and Circles lightboxes, paged on the server (2026-11-07)

**The problem.** CM4 read every page of `GET /api/admin/jobs`, and CM5 read all of `GET /api/admin/circles`. Both then searched, filtered, sorted and paged in the browser, so opening either one transferred the whole table. No lightbox search waited for the typing to stop, so every keystroke started a read.

**The new reads.** Two Community routes, beside the overview, with the SQL in `services/communityLists.ts`. Each returns one page (25 by default, 100 at most) and the total that matched:

- `GET /api/admin/community/jobs?q=&status=&place=&seniority=&sort=&limit=&offset=`
  - The search covers the role and the company, with LIKE's own characters escaped.
  - Sorts:
    - applications, most first;
    - newest;
    - days open: the longest-open published posting first; a posting that isn't open, or was approved before migration 609, last (D1121);
    - role.
- `GET /api/admin/community/circles?q=&type=&access=&published=&featured=&sort=&limit=&offset=`
  - Sorts: by name, or by members as an admin entered them.
- **Shared rules:**
  - The sort is a bound key inside `CASE`, and every sort ends on the id, so page boundaries are stable.
  - A value the read can't take is a 400 sent through `refuse()`.
  - The consoles' own lists, `GET /api/admin/jobs` and `GET /api/admin/circles`, are unchanged.
  - The rows carry what a lightbox row draws, and never a host, an applicant or a member.

**The lightboxes.**

- **Jobs and Circles** send one page's query (`jobsQuery`, `circlesQuery`) and draw the Worker's page (`listPage`).
- **An answer without a numeric `total`** is unreadable, never an empty list.
- **Search:** Events, Jobs and Circles wait 300 ms after the last keystroke (`useSettled`, `SEARCH_WAIT_MS`). An answer to an older query is dropped (`useBoxRead`'s `live` flag), so one search makes one read.
- **Removed:** the client-side `listView`, `pageOf`, and the per-row search, filter and sort functions.

**Tests.**

- **Worker** (`community_lists_4717.test.ts`, 260 postings and 130 circles):
  - every row appears exactly once across the pages, for every sort;
  - the totals match the filters, and LIKE characters are searched for;
  - an unknown value is a 400;
  - Days open order follows D1121;
  - the read is admin-only and carries no person.
  - Mutation caught: Days open sorted newest approval first.
- **Frontend** (`community_lightboxes_d934`):
  - the lightboxes read one page of the Community lists and never the whole lists;
  - three keystrokes then a pause make one read;
  - the query and page helpers are tested.
  - Mutation caught: the query built from the live text.
