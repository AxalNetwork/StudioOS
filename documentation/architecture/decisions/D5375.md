## D5375 — Stale-write protection for hires, the Raise writers' split path and Eadwyn-worded splits (#5375)

- **Status:** Built, 2026-11-10 (Worker, one migration, frontend).
- **Migration:** `202611100935_uof_hire_revision.sql` adds `use_of_funds_hires.revision` (starts at 0).
- **Builds on:** D5069 (the revision, the `409 changed_since_open` answer and the Review latest dialog), D1176 (Use of Funds scenarios and hires), D1179 (Eadwyn's milestone wording), D691 (the Raise record drawer).

### What was wrong

D5069 made a scenario, a split and a milestone refuse a write made from a stale read. Its "Not covered" list left three Use of Funds write paths that still saved last write wins.

1. **Hires.** Two tabs editing the same hire both saved. Only a concurrent removal was caught (`hire_changed`).
2. **The Raise writers' path.** `saveUseOfFunds` (`services/raiseWriters.ts`) called `saveSplit` with no revision and the revision check off, so the record drawer's Edit split replaced a newer split without saying so.
3. **Eadwyn-worded splits.** Eadwyn writes nothing in Use of Funds (D1179): its only applied output is a milestone name that Accept places in the unsaved Edit split form, and the person's Save split writes it. Two forms host that assistant. The page's Edit split sheet already sent the Base revision from D5069. The record drawer's Edit split did not, which is the same unchecked path as 2. There is no other Eadwyn write to guard.

### What it does now

**Hires.** A hire carries its own `revision`; it is read with the hire (`GET /hires`, the plan's hire list) and goes up by one on every edit. `PATCH /hires/:id` takes `expected_revision` in the body and `DELETE /hires/:id` takes `?expected_revision=` (a DELETE has no body). A request that names none is `400 expected_revision_required`. A revision that is not the stored one is `409 changed_since_open` with the sentence "This hire was changed somewhere else after you opened it. Nothing of yours was saved. Review the latest, then make your change again." and `current_revision`. A hire of another venture is still `404` first, whatever revision is named.

The check runs twice. A plain read before the batch gives the readable refusal. Inside the batch, the audit row and the update or delete each carry `AND revision = ?`, so a hire that moved after that read changes no row and leaves no audit row (the batch is one transaction, and the audit row is selected from the row the second statement then changes). When the second statement changes nothing, the writer reads the row again: gone is the existing `409 hire_changed`, still there is `changed_since_open` with the new revision. Hires use this guard-every-statement form, not the integer-overflow abort, so they do not depend on the D1 check below.

**The record drawer's Edit split (the Raise writers' path, and Eadwyn-worded splits).** The drawer cannot say what it opened at from the server's side, because the server reads the record again when the action runs. So the revision is read when the record is read and travels with the client: `RecordAction` has an optional `body` (the drawer already merges `action.body` into the posted values, `recordActionBody`), and Edit split serves `body: { expected_revision }`, the Base scenario's revision (0 when no Base exists yet, nothing when the store cannot be read). `splitBody` passes it on and `saveUseOfFunds` now calls `saveSplit` with the revision required. A save without one is `400 expected_revision_required`; a stale one is `409 changed_since_open` with `code`, `error` and `current_revision` (a `WriterError` can carry extra response fields for this). Either way nothing is written and no audit row is logged. A milestone name Eadwyn worded rides the same save, so it is refused with the rest when the plan moved after the drawer opened.

**Frontend.** `useOfFundsApi.updateHire` sends the body as given and `deleteHire(project, id, revision)` puts the revision in the query. The Milestones and hires tab's Hires table has an Edit button (founders and admins who can write) that opens Edit hire: role, section and from-month, with Save hire and Remove hire. Both send the hire's `revision`. On a 409 the dialog stays open with the sentence and **Review latest**, which closes it and reads the plan again (D5069's `ReviewLatest`). The dialog does not edit the cost a year or its currency, so nothing here converts money through a fixed factor (that belongs to #5373).

### The abort on D1

Run once on the local D1 simulator and recorded in D5069.md: a stale batch throws `D1_ERROR: integer overflow: SQLITE_ERROR` and leaves nothing; a matching one commits. Hosted D1 was not run (no credentials, and the issue allows no production data). The existing scenario batches keep the abort; the hire batch does not need it.

### Decisions inside the build

- **A per-hire revision, not `updated_at`.** `updated_at` has one-second resolution; two saves inside a second would share a revision. Cap table could use it because its writer takes the next millisecond.
- **Required, not optional, on the drawer path.** The issue allows either "send the revision the writer opened at" or "record why it stays unchecked". Checking is possible here because the drawer already carries `action.body`, so the exception is not taken. The cost is that a client of `POST …/actions/edit-split` that sends no revision now gets a 400; the drawer and the page both send it.
- **Edit hire is a small addition to a screen with a canvas.** No canvas under `design/` draws a hire edit. The dialog reuses D5069's dialog pattern, and the page change is one column and one button. If the owner wants a different layout for it, only `EditHireDialog` and that column move.
