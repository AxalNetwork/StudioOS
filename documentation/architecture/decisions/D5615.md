### 2. The freeze

`scripts/lib/hubFreeze.mjs` reads the names each hub holds and
`scripts/hub-freeze.json` lists, per hub, the sorted names it held on `main`
when the freeze landed (built last, from `main` with this change's
`CycleRoute.jsx`):

| Hub | Names | What a name is |
| --- | --- | --- |
| `api.js` | 1,560 | every export (`export <name>`, `export * from <spec>`) and every key of an exported object literal (`api.<key>`, `dd.<key>`, …), parsed with acorn |
| `App.jsx` | 406 | every import specifier, static or `lazy(() => import(…))`, parsed with acorn-jsx |
| `CycleRoute.jsx` | 94 | every import specifier, static or `lazyStep(() => import(…))` |
| `index.ts` | 872 | every static import or re-export (`import <spec>`) and every registration on `app`: `ROUTE <path> <router>`, `USE <path> <middleware>`, `GET <path>`, `ON <methods> <path>` |
| `advisors.ts` | 43 | every registration on its router, method plus path (`GET /me`, `ROUTE / advisorServicesRoutes`) |

Every name found in a hub must be on its list. **It is a set, not a count:**
a name that leaves a hub stays listed harmlessly, so removals edit nothing and
a removal never makes room for an addition. A `route` or `use` name carries
the router or middleware it mounts, so a second router on a path already
listed is a new name. The TypeScript files are read with a small lexer that
blanks comments, strings, template literals and regex literals before
matching, so `app.route(…)` quoted in a comment (`index.ts` has two) is not a
registration. **Dynamic imports stay unfrozen**: the cron jobs `scheduled()`
loads with `await import(…)` have no other home yet.

`frontend/test/hub_freeze_5615.test.mjs` runs it under `npm run
test:frontend` (no `package.json` edit; the `frontend/test/*.test.mjs` glob
picks it up). A failure reads `<hub>: "<name>" is a new entry in a frozen hub
(D5615). It goes where documentation/architecture/HUBS.md § <hub> says, not
here.`

### 3. CycleRoute split by cycle

`CYCLE_DEFS`' four entries, the four `*Mount` functions and the lazy steps
only one cycle draws moved to `frontend/src/pages/cycles/defs/validate.jsx`,
`build.jsx`, `raise.jsx` and `grow.jsx`, each `const <cycle> = { … }; export
default <cycle>;`. With them went the helpers only one cycle uses: Validate's
`ExportSummary` and `RecordMount` (the Record a session lightbox
`ValidateMount` draws), Raise's `mercuryPart`, Grow's `fromMercury`.
`CycleRoute.jsx` imports the four and builds `CYCLE_DEFS = { validate:
validateDef, raise: raiseDef, grow: growDef, build: buildDef }`, so every
lookup (`primaryForModule`, the component's `def`) is unchanged. It went from
1,527 lines to 1,039 (488 shorter), and drops the imports only the entries used.

**Behaviour does not change.** The entries are the same objects with the same
functions; only the files they are written in moved. The lazy steps stay
lazy: `InterviewRecord` and `VerdictRecordWithPlan` (Validate), `NarrativeHome`
(Raise), `CalendarWeek` and `UpdatesHistory` (Grow) are the same `lazyStep(()
=> import(…))` declarations, now in their cycle's file, with paths one folder
up. `RecordMount` is imported from `defs/validate.jsx`, where its one caller
is; nothing outside the tests imported it.

**Tests that read the moved text** now read it where it lives:
`frontend/test/_cycleBands.mjs` reads `CycleRoute.jsx` with the four entries
(`cycleRouteText()`, `cycleRouteSource()`), and `cycleDef` slices
`const <cycle> = {` from them; `_cycleSteps.mjs` and
`cycle_route_lazy_steps_d4574.test.mjs` collect the lazy steps from all five
files, each spec resolved against its own file; the test files that matched
`CycleRoute.jsx`'s text read `cycleRouteText()` or the one cycle file the
assertion is about; `cloudflare-worker/test/fills_registry.test.ts` reads the
`fills` entries from the four files. `frontend/src/lib/railOptions/founder.js`
names each cycle option's file as its `defs/<cycle>.jsx` (its `at` and `rail`
paths are what the rail-options tests check; `railOptionFor` is never called
with `CycleRoute.jsx`). Dropping one cycle from the table fails
`distribution_shell_4484` and `phone_cycle_roots_d703`, which mount Grow.

### 4. Decision files per part

Part `k` of issue `n` writes `decisions/D<n>-p<k>.md`, headed
`## D<n> part <k> — <title> (#<n>)`, beside the issue's `D<n>.md`; later parts
never edit `D<n>.md`. `scripts/check-decision-ids.mjs` reads the form
(`filePart`) and fails a part file whose parent `D<n>.md` is not in the
folder, whose heading names another decision or part or is not in the part
shape, whose heading does not cite `#<n>`, that holds two headings, or whose
`n` is below D4000 (parts are for decisions numbered by their issue). A name
that is neither form is still refused, and the refusal now names both shapes.
The rule is in `AGENTS.md`'s Decisions house rule. Existing files stay as they
are, and open part PRs that already write `D<n>.md` (#5523, #5553, #5555,
#5563) keep doing so: the rule binds new parts.
