### The rule

`GET /api/fund-performance` and `GET /api/fund-performance/:id` return a fund
when the caller is any of these:

- an admin (every fund, as before);
- an investor with an LP record in it (`lpMembershipScope`, as before);
- its GP of record, as `requireFundGp` decides it.

The GP arm is `managedFundIds`, the operating gate's own scope
(`fundManageScope`). It holds the same three checks as
`/:id/positions` and `/:id/history`:

- `vc_funds.gp_user_id` is the caller;
- the caller meets the institutional investor tier;
- the fund is under the caller's verified active company.

The two reads cannot disagree on who runs a fund, because one function answers
both. Below the tier, the GP arm reads nothing: a 402 upsell would be new on
this list, so no 402 is added.

A fund that is both the caller's LP fund and their GP fund appears once.
Figures do not change: the same `readFundPerformance` runs for every caller,
and a GP reads exactly what an admin reads for that fund.

A caller who is neither an investor nor the GP of any fund still gets the same
404 on both routes. So do other funds, absent funds and malformed ids.

### SQL

The GP funds are read by id with `json_each(?)` and one bound JSON array, so the
route adds no interpolated SQL. The reviewed `sql-prepare` baseline is
unchanged.
