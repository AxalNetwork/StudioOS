## D4860 part 5 — The shared Platform strip: grouped by domain, ownership said, live state from the overview's rule (#4860)

Part of #4860: finding 13, the shared Platform strip in `lib/hqStrips.js`, which part 1 left (`D4860.md`, "Not done: 13"). It also brings finding 12's grouping, built on the overview in part 1, to the strip.

**Finding 13 asked** Platform to decide whether it is the true parent of the consoles its overview summarises (Integration keys, Monitoring, Telegram), or to present the overview explicitly as cross-HQ. The answer, as built:
- **Monitoring and Telegram are Platform's.** They are in its strip and light its row, as before (D285). They keep their addresses (`/monitoring`, `/admin/telegram`): moving them would break every link to them, and D4860 part 1 already said they stay. The strip now says so. Each carries an **HQ** mark, read as "at /monitoring, outside Platform", by one rule, `outsidePlatform` in `hqStrips.js`.
- **Integration keys is not Platform's.** It stays an HQ row of its own (the owner's ruling of 2026-10-20, pinned by `hq_subnav_h36_d285`), so it is not in the strip. Putting it there would light Platform's row on its page.
- **The overview is cross-HQ, and says so.** Detailed consoles reads "grouped by domain, across HQ". Every link there whose address is outside `/admin/platform` (Monitoring, Licences, Credit rules, Integration keys, GitHub sync, Telegram, X, Security) carries the same HQ mark, by the same rule.

**Grouped by domain** (finding 12, PL-07). The strip uses the groups and order of the overview's Detailed consoles (`CONSOLE_GROUPS`), so Platform has one map, not two. The sequence is Overview, then:
- Infrastructure: Monitoring, Topology, Storage, Meeting bots;
- Payments: Payments, Bank accounts, Promo codes;
- AI: AI allowances, AI usage, Scoring;
- Integrations: Telegram;
- Controls: Switches;
- Product: Product testing, Decks.

These are the same fifteen consoles, regrouped. An item's group is the third field of its `HQ_STRIPS` entry. `HqSubNavStrip` draws a group's name before the group's first item (`stripGroupStart`), so the strip in `App.jsx` is still plain literal links (no import was added to the frozen hub, D5615), and the reachability guard still sees each one. Finding 12's own names (Operations, Infrastructure, AI, Commercial, Product) are not used: the canvas and the overview group by Infrastructure, Payments, AI, Integrations and Controls, and a second set of names would give Platform two maps.

**Live state on the strip** (PL-07: "each link carrying its live state where one applies"). It uses one rule, the overview's, and through it the Worker's.
- `stripStates` in `platformOverviewModel.js` runs `signals`, which folds in the Worker's detected incidents (D4860 part 4), then `platformHealth`. These run over the same three reads the overview makes: the summary, the deployments registry and traffic by branch. Nothing new judges a signal.
- **Overview** always carries the overall state: Healthy, Degraded, Unknown or Critical, or Reading while the reads are out. So the strip never leaves health unsaid.
- **A console** carries its state from the signal `CONSOLE_GROUPS` already names for it: Monitoring telemetry, Payments the webhook, Telegram broadcast, Switches the overrides. `consoleState` is shared by the strip and the overview's Detailed consoles, and draws nothing for Healthy, as on the canvas. A signal that is missing because the summary did not answer is **Unknown, never blank**. The overview had left those links blank (Telegram on an unread summary), and now draws Unknown there too.
- Each state is drawn as a symbol and a word from the overview's vocabulary (`STATUS`), with "Platform health:" read out on Overview. Unknown keeps its dashed, non-emerald look. Each strip link is `relative`, so its screen-reader text stays inside the strip's scroller. The browser check found that without it, the far items' text widened the page and it scrolled sideways at 1280 and 390.

**Where the reads come from** (`lib/platformStrip.js`).
- On the overview, PlatformPage hands its own reads to the strip once all three have settled. The strip makes no request there, and the strip and the page show one judgement of one reading.
- On another Platform console, the strip reads the three itself, at most once per five minutes (`STRIP_READ_TTL_MS`), shared across consoles.
- A read that fails is UNAVAILABLE, which the model turns into Unknown.
- The deployments read fans out to every branch. Re-reading it on every console visit would cost a branch fan-out per click; the five-minute window bounds that. A reading's time is in the Overview state's tooltip.
