## D5201 — An unreadable copy preference makes no external copy (#5201)

Part 1 of 7 of the 2026-11-09 Calendar audit (of #3723). P0. No migration, no route change.

**The problem.** "Copy new Axal sessions to…" (`calendar_settings.copy_target`, D1485) decides whether a booked
session is also written to the member's Google or Outlook calendar. `copyAllowed` in
`services/calendar/sync.ts` started from `'all'` and kept that value when `readCopyTarget` threw:

```ts
let target: CopyTarget = 'all';
try { target = await readCopyTarget(env, userId); } catch { /* no settings store yet: the default */ }
```

So a `calendar_settings` row or store that could not be read for a moment turned an explicit **None** into a
copy on every connected provider. That is the wrong direction to fail for a write to someone else's calendar:
the member had refused it, and a write to Google cannot be taken back by Axal.

**The rule now.** An unreadable preference is exactly the case of a provider the setting leaves out: **nothing
new is created**. The distinction D1485 drew is kept:

- the setting names the provider (or `all`) → the copy is made or updated;
- the setting leaves it out, and the session already has a copy there → that copy keeps being updated, because
  it was authorised when it was made and a stale copy of a moved session is its own kind of wrong;
- the setting leaves it out, with no copy to update → nothing;
- **the setting could not be read → nothing new**, and an existing copy still updates, as above;
- the copies themselves could not be read either → nothing new.

A missing row is unchanged: it is not a failure, and it still reads as the documented default, `all`.

**A missing store fails closed too**, without reading the error's text. The audit named the row *and* the store,
and the rule is simpler for it: any read that does not answer makes no new copy. `calendar_settings` has been in
production since migration 708 (D1484 part 2), so this changes nothing there. One test fixture
(`calendar_feed_sync_d1209`) applied a minimal migration set without 708, so its create hook now refused before
reaching the error state it is about: that fixture carries 708 now, which is what production has.

**The member's preference is never rewritten.** Neither the unreadable read nor a provider write that fails
stores anything in `calendar_settings`. The tests hold both.

**What is observable.** `copyDecision` and `pushOneUserOneProvider` return one fixed word each, and
`onAxalSessionCreated` returns the list (`SyncReport`): `copied`, `existing_copy`, `not_selected`,
`preference_unreadable`, `disconnected`, `connection_refused`, `write_refused`. So the four states the audit
asked to tell apart — provider not selected, preference unreadable, provider disconnected, provider write
refused — are each their own word, for a caller, a test or support.

A refusal for an unreadable preference also records `copy_preference_unreadable` (a new `SYNC_ERRORS` code,
`services/calendar/syncState.ts`), so the status read still shows it after a reload. The write is an `UPDATE` on
the member's own token row, so a provider they never connected records nothing. An older build that meets the
new code reads it as `sync_failed`, which `readSyncError` already does for any code it does not know.

**Nothing private is carried.** An outcome is a fixed word. The refusal logs `{ provider, outcome }` and no
title, address, join link, token or provider body; a test asserts that of every log line and of the stored row,
and fails when the title is added to the log.

**Tests** (`cloudflare-worker/test/calendar_copy_fail_closed_5201.test.ts`, 6 cases, on the migrated schema with
`fetch` stubbed so no provider is reached):

1. a readable preference still decides the providers (`none`, `google`, `microsoft`, `all`, and no row);
2. an unreadable preference creates nothing on either provider and records no mapping;
3. an unreadable preference keeps updating a copy already held, and creates no other;
4. the refusal is recorded on a connected provider and not on a disconnected one;
5. a failed provider write does not rewrite the stored preference, and nor does an unreadable read;
6. no log line or stored row carries the title, the address, the join link or the provider's body.

Mutations seen failing: the fallback put back to `'all'` (the mutation the issue asks for: 4 of 6 fail); the
outcome not recorded; an existing copy no longer updated; the title added to the refusal log.

**A note on the fixture.** The first version of this file rebuilt the baseline and every migration per case and
took 201 seconds. It uses D1169's `migratedDatabase()` template instead, which builds the schema once and copies
it per case: 44 seconds for the same six cases.
