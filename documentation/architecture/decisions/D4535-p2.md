### 2. The routes

All behind `TEAM_AGENTS_ENABLED` (404 `team_agents_off`), like the agent and skill routes.

- `GET /`, `POST /` (`{ definition }`, 201), `GET /:uid`, `PUT /:uid` (`{ definition }`), `GET /:uid/versions/:version`, `POST /validate` (`{ definition }`) and `POST /:uid/validate` (the saved draft).
- **Scope.** `?company=<uid>` selects a company's workflows; no `company` selects HQ's. The route resolves it from the caller's own links and passes the resolved owner to the store, which binds it in every statement. Nothing in the body or path chooses a scope: the server mints a new workflow's uid (a uid in the body is replaced), fills `owner` when the body leaves it out, refuses a different `owner` (403 `workflow_out_of_scope`) and refuses a uid that is not the path's (400 `uid_mismatch`).
- **Roles.** HQ's workflows: a Super Admin only (403 `not_super_admin`). A company's: its editors only (`canEditAsMember`). A member who is not an editor gets 403 `not_editor`. Anyone else gets 404 `not_found`, as for a company that does not exist. That includes another company's editor and a Super Admin with no editor's seat: HQ moderates company skills and never writes them (D4161), and the same rule holds here. A workflow of another scope is 404.
- **Provenance.** A company's draft may not claim `hq_reference` (422 `provenance_invalid`).
- **Audit.** A draft save writes the admin audit row, `skill_workflow_draft_created|saved` or `company_skill_workflow_draft_created|saved`, with the definition hash before and after. A save that changes nothing writes no row.
- **Body.** At most 64 KB (413 `body_too_large`).

### 3. Validation

`validateWorkflow` (slice 1) takes facts, not reads. `workflowContext(env, companyId, def, readable)` reads them for one run company:
- **Skills** through `skillByUid`. The caller's read gate is the route's `readable`, which is team_skills.ts's rule: a company skill only for that company's members, and an unpublished skill only for those who may write it. A skill that fails the gate is left out, so it answers `skill_not_found`, as a missing skill does.
- **Versions** from `agent_skill_versions`. Suspension uses `skillRunRefusal`, the run gate's own rule.
- **The agent of each role** in the company: one live agent per role (`idx_team_agents_live_role`). Its pins come from `agent_skill_links`. Its tools come from `grantsOf(tool_grants_json)` through `missingTools`, narrowed by `requireCapability` (D8070), as `attachCheck` does.

**The run company:**
- A company's workflow runs only in its own company. Naming another is 400 `run_company_not_allowed`, so an editor never reads another company's agents.
- An HQ workflow must name one (`?run_company=`, 400 `run_company_required`).

The reply is `{ ok, refusals, order, levels, resolved, run_company, not_checked }`. `not_checked` is `['qualified_version', 'skill_input_contract']`: the checks §8 needs and no fact supplies yet, so an `ok: true` never claims them. Validation writes nothing: no row, no plan, no run, no pin.

Only company-scoped agents are read. A project run scope waits for the run slice, which decides how a project's agents and its company's skills meet.

### 4. Departures

- **No run-detail read.** The brief allowed "read an existing run, if any". No route can create a run, and #8823's Q1 is deciding where that read lives and who may open it (S1 proposes HQ-only at `/api/admin/ai-agents/workflow-runs/:uid`). A read built now would set that contract before the owner answers.
- **Reads are writers' only.** Drafts are seen only by those who may write them, as with skills. Nothing is published yet, so there is no published version to show a wider audience. Who may read a published workflow is for the publish slice.
