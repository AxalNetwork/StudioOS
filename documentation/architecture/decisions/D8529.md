## D8529 — The whole account journey in one browser test (#8529)

- **Status:** built by S23, 2026-11-25 (#8529, row E5 of #8509).
- **Migration:** none.
- **Why:** each step of the account journey has its own tests, and no test joined them. A change that broke the hand-off between two steps would have been found by a user first.

### 1. The journey

`frontend/tests/visual/account_journey_8529.spec.mjs` runs at 1440 and 390 px on the visual suite's local Worker (`server.ts`: the built SPA and the real Worker on SQLite). It uses two accounts, each seeded per width by `_account_journey_seed.ts`.

1. A creates a company, a project in it and a standalone project, through the real routes with A's session. The test checks that the first sits in the company and the second in none.
2. A invites B to the standalone project by email. The Worker's mailer runs, and the harness **outbox** (`_outbox.ts`) records the message instead of sending it. The spec reads the invitation link from there.
3. B opens the link signed out and presses "Sign in to accept". The app carries the invitation into `/login?next=…`. The harness's controlled sign-in puts B's session in place and follows that `next`, which returns B to the invitation. The invitation is accepted on arrival:
   - A's roster shows **exactly one** seat for B;
   - "Open project" lands B on that project;
   - B's settings name it.
4. A reload keeps B on the same settings.
5. A changes the project's address (`PUT /api/projects/:id/slug`, which retires the old slug) and moves it into the company. The new address and B's **old** link both resolve (`PortfolioAddress`) to the same venture.
6. A removes B's seat. B's next read of the settings shows that it could not be read, and the settings are gone. Row E3 (D8527) covers this in depth.

### 2. The harness pieces

- **`_outbox.ts`** answers the mailer's two Gmail calls by exact hostname (`oauth2.googleapis.com`, `gmail.googleapis.com`), as `company_invitations.test.ts` does. It decodes each message, and `GET /__visual/outbox?to=` lists them.
  - The visual server sets made-up Gmail credentials and `PUBLIC_BASE_URL` to its own origin, so mail links point at the harness.
  - No message leaves 127.0.0.1.
- **The controlled sign-in.** The Worker's emailed sign-in link and code go through its job queue, which the harness does not run. So B's sign-in is the harness's own. The deep link it follows is still the one the app wrote.

### 3. Where it runs

- **On every pull request that is not a draft.** The spec is in the visual suite, which the `visual` job of `ci.yml` already runs in full whenever a pull request is not a draft. A path filter would only narrow that, so **`ci.yml` is not edited** and there is no new required check.
- **A release-candidate gate** for account and VentureSpace changes is the owner's decision (#8529). The spec runs unchanged in any job that builds `docs/` and starts the visual server.

### 4. Where it departs from the issue

- **A's setup** (company, projects, invitation, address change, move, revoke) goes through the real routes with A's session, not by clicking A's screens. The journey under test is the hand-off between the steps, which B walks in the browser.
- **After accepting,** the app offers "Open project", which goes to the project's page, not its settings. The spec follows it, then opens the settings.
- **The new address** is the venture's portfolio page: `/p/<slug>` and `/c/<company>/p/<slug>` resolve to it. So "the old link resolves to the new address" is checked as both links landing on the same venture.

### 5. Proof

- **The spec:** 2 pass, one at 1440 and one at 390, locally on the visual harness with the session's Chromium (not CI's pinned build).
- **Mutation check:** 2 Worker mutations, both caught.
  - Accepting writes no seat: B is never offered "Open project".
  - The address resolver forgets retired slugs (`account_portfolio.ts`): B's old link no longer reaches the venture.
  - While building the check, a third mutation of `services/slugs.ts`'s `slugHolder` was not caught: the address resolver has its own history lookup, and the slug write path does not use that function to resolve.
