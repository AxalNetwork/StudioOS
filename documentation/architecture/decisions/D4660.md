## D4660 — Email: record entry points and drafts, part 1 (#4660)

### Decision

This is #4660 in parts. Part 1 is finding 4, the record entry point. Part 2,
below, is the Worker half of finding 5, durable drafts. The composer half of
finding 5 is part 3 and is not in either.

1. **One person-reference contract.**
   - A person ref is the string `personOfRecord` returns: `kind:id`, such as
     `interviewee:11`.
   - `EmailAction`, `emailHref` and `RecordEmailSheet` all take that string.
     `isPersonRef` says whether a value is one.
   - `RecordEmailSheet` took `person.ref` and `person.name`. `CycleRoute` passed
     it the string, so the sheet asked the Worker for the context of
     `undefined` and drew "Unreadable". The new-tab link worked only because
     `emailHref` takes the string.
2. **The record's title is a separate prop.**
   - `RecordEmailSheet` takes `label`, the record's title, for its subtitle
     until the context read names the person. It never draws "undefined".
3. **A value that is not a ref asks nothing.**
   - The sheet reads `Unreadable` and makes no accounts, shares or context
     request.
4. **The deep link and modified clicks are unchanged.**
   - A plain click opens the sheet over the record, whose URL stays put.
   - A modified click or a middle click follows `/email?person=…&compose=1`.

### Part 2: the Worker half of finding 5 (durable edits)

5. **A member's edit is stored beside the generated text.**
   - Migration `202611071600_mail_draft_edits` adds `edited_to`,
     `edited_subject`, `edited_body`, `edit_revision` and `edited_at` to
     `mail_drafts`.
   - `subject` and `body` stay what Eadwyn generated for that version: the
     source snapshot, never rewritten. The member's text is kept apart, per
     version, so the two stay distinguishable.
   - A draft read carries `edit`: `null` while never edited, else
     `{ to, subject, body, revision, at }`.
6. **A save is a plain write.**
   - `PATCH /api/mail/drafts/:uid` with `{ to?, subject, body,
     expected_revision }` runs no model and no router, so it is never charged.
   - The text is stored exactly as typed. A half-written draft is fine: an
     empty body, or a recipient that is not yet an address. The address is
     checked at send, not here.
   - Limits: subject 200, body 8000, address 254. Over them is 400
     `edit_too_long`; not text is 400 `edit_invalid`; no integer revision is 400
     `revision_required`.
7. **A save names the revision it read.**
   - The update is `WHERE edit_revision = ?`. A second tab holding an older copy
     is 409 `stale_edit` with the current draft, and writes nothing, the same
     rule as a layout save (D1594).
   - Another member's draft and an unknown uid are 404 in the same words, as
     everywhere on `/api/mail/drafts`.
8. **A revision starts from the saved edit.**
   - Revising a version that has an edit starts from the member's text, not the
     older generated text it replaced. With no edit it starts from the
     generated text, as before.
   - The new version is its own row that keeps its parent. Its provenance is
     its `parent_uid` and its instruction; it has no edits until the member
     makes some.
   - #4666's `base` snapshot, the text in the open editor, still wins when
     the client sends one, because it can be newer than the last save.

**Not done in part 2** (the composer, part 3, which waits for #4665 and #4666
to land because they rewrite the same files):
- the composer saving through `PATCH`, showing a pending or failed save, and
  keeping the member's text through closing, navigation and reload;
- reopening a stored draft from the conversation;
- a pending generation keeping the purpose it was submitted with;
- the fund-GP question check taken from the selected draft's own intent.

### Part 3: the composer half of finding 5 (#4660)

Part 2 stored the member's edits on the Worker. This part makes the composers
use it. #4665 and #4666 (S26) are on `main`, so the composer files are free.

9. **The member's text is saved per version, through `PATCH`.**
   - `useDraftEdits` queues every change to To, Subject or Body and saves it
     after a short pause, naming the revision it read and taking the revision
     the answer returns. Two changes in a burst are one save, of the latest
     text. Saving runs no model and is never charged.
   - The text is per version (by uid): going back to an earlier version shows
     the text the member left in it, never the generated text.
   - The recipient is part of the saved text. A version the member has not
     edited falls back to the recipient last typed, then the record's.
10. **A save is drawn as what it is.**
    - `DraftSaveLine` says "Changes not saved yet…", "Saving…" or "Your edits
      are saved." and claims the last only after the Worker answered.
    - A failed save keeps the text on the page and says so, with Save again. A
      409 `stale_edit` (the version was saved from another window) keeps the
      member's text too: Save again names the revision the Worker reported, so
      the member chooses, and nothing is overwritten in silence.
11. **Closing never discards text in silence.** Closing the sheet with text not
    stored yet saves first. If that fails the sheet stays open and says "Your
    latest changes are not saved, so this is still open", with Try saving again
    and Close without saving. Leaving the page asks too (`beforeunload`) while
    anything is unsaved.
12. **A stored draft reopens.** The conversation's draft rows show the member's
    own text (marked "edited") and an Open draft action. `draftChain` finds the
    draft's ancestors by `parent_uid` and the latest revision after it, so the
    composer opens on that version with the versions around it, the saved text
    and the saved recipient. It sends with the stored draft's uid and no model
    run. Closing reads the list again.
13. **Shorter revises the text on screen.** It already sent `base` (#4666); the
    edited text of the version on screen, including a reopened one, is that
    `base`, so the estimate and the run name the same text.
14. **A generation keeps the purpose it was submitted with.**
    - The purpose, tone and length controls are shut while a draft is pending.
    - The returned version carries the Worker's own `intent`; if it were ever
      missing, the purpose the run was pressed with fills in, never the form's
      current value.
    - Accept on the record's Email sheet hands over the draft's own intent
      (`{ ...draft, intent: draft.intent ?? null }`); it used to replace it with
      the form's live intent.
15. **The fund-GP question check reads the version's own intent.** An opening
    Eadwyn wrote for a question (`ask_question`) stays blocked until the member
    adds their question: through a changed purpose, version changes and
    reopening. The comparison is the saved text against the generated text of
    that same version, so it holds after a reload.
16. **The record's Email sheet saves too.** Once Accept has placed a draft, the
    form's To, Subject and Body are saved to that draft the same way, with the
    same save line and close guard. A typed email with no draft has nothing to
    save, as before.

**Not done here (left for the owner):**
- The "Not saved" pill on a placed draft (`FillMark placed`) is unchanged: it
  means "Eadwyn placed this, nothing is sent". Next to "Your edits are saved." it
  can read as a contradiction; whether the pill should go once the draft is
  stored is a design call.
- #4662 (s36) owns durable conversation history and edits `EmailPage.jsx` and
  `RecordCompose.jsx` as well. No branch from it exists yet; this part's edits
  to those two files are small and local (the draft rows, the save line), so a
  merge should be mechanical.
