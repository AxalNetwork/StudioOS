## D4610 — A shared document opens, answerability is one field, and the Ask history is reachable whole (#4610)

#4610 (Research audit 3 of 5, slot S12, taken at the owner's request).

### Open resolves a share

`GET /documents` lists shared documents on purpose — that is what
`source: 'client'` and the "From Verwood" chip are for — and `LibraryZone` drew
an `Open` button on every row. `Open` called the download route, which resolved
through `ownDoc` (`WHERE owner_user_id = ?`), so for a shared row it **404'd**.
A reader was listed a document, told where it came from, given a button, and
refused. The page's own adjacent comment argues that a client's document offers
no Metadata, Re-index or Remove "because drawing either would be a control that
cannot act", and `Open` sat outside the guard that reasoning describes; the
phone cards drew no `Open` at all, so the two viewports disagreed about whether
the feature existed.

`readableDoc` resolves ownership **or** an active permitted share, through the
existing signed-download mechanism (`mintDownloadToken`, 120s, consumed in KV,
logged by `routes/files.ts`). It is deliberately a **separate function** from
`ownDoc` rather than a flag on it: read and write are different permissions, and
the only safe way to keep them different is for them to be different lookups —
`ownDoc(…, { orShared: true })` would leave every write path one argument away
from granting a recipient the owner's delete. `PATCH`, `DELETE` and the
re-index queue still call `ownDoc` and are unreachable through a share.

A revoke is `status = 'revoked'`, never a delete (migration 218), so
`status = 'active'` is the whole of it: the same predicate the list uses, so a
row that is listed is a row that opens and the reverse. A revoked share, a
reader with none and a document that does not exist are all 404 with the same
body.

Opening a client's document writes `open_document` to
`advisor_client_access_log` — one of the two actions migration 218 declares,
whose reader (`GET /:projectUid/access-log`) already LEFT JOINs the document to
name the file and was waiting for rows nothing wrote. Best-effort and after the
token is minted: an audit write must not deny a reader a file they may read.

**Indexing policy is unchanged.** A client's share is readable and is not indexed
into the recipient's Ask namespace, which is why `dto()` computes `in_ask` as
`source === 'own' && …`. This grants a download and says nothing about Ask.

### Answerability is `in_ask`, counted

`indexed` counted `ANSWERABLE_STATES.includes(index_state)` over every item
**including shares**, while each row's own `in_ask` is narrower. So an indexed
client share was counted in "N answerable" and then labelled, correctly,
"Indexed in their library, not yours" on its own row — the header pill and the
row contradicting each other about one document, and an account holding only
shares told it had answerable documents when Ask could use none. `answerable` /
`not_answerable` count rows whose `in_ask` is true, so a count and a row cannot
differ: one field, counted, not a second rule that resembles it. `indexed` stays
beside them, unchanged and still true of index state, which is the different
question the Index-state column answers.

The artboards' tile labels are untouched — #3701 owns those. What changed is
what they count; the note under "Indexed" has always read "answerable in Ask".

### The history is a page, and its totals are the scope's

`saved`, `all` and the session scope each read `LIMIT 200` with nothing after
it, and `askTotals` was computed over that slice — so `asked`, `saved` and
`cost_usd` plateaued at 200 and then never moved again, under tiles that present
them as the reader's whole history. The truncation also ran in both directions:
`saved` and `all` are `id DESC` and dropped the **oldest** answers, while the
session was `id ASC` and dropped the **newest** — a reader past 200 exchanges
stopped seeing the answer they had just been given. The audit reproduced exactly
that at 201.

Four scopes now, each a whole statement with a first-page and a
keyset-continuation form, and `totals` from its own aggregate so it does not move
when the page does (`page_totals` is the slice's own figures, under a name that
says which they are). **Every scope reads newest-first, the session included**:
paginating an ASC read would have handed a reader their oldest two hundred
questions first, so the SQL walks back and the session's page is reversed for
display, which is where a thread's oldest-first reading order belongs. The
newest answer is then on the first page by construction.

`discarded` became the fourth scope. As a client-side narrowing over `scope=all`
it searched only the rows that read returned, so an answer archived and then
followed by two hundred questions was unreachable from the one tab whose purpose
is finding archived answers.

### Unavailable, never an invented zero

`payload?.indexed ?? 0` turned a failed or absent library read into three
confident zeroes in the same tiles that print real figures when it works — and
it is the value Ask's "Nothing to ask yet" empty state is gated on, so a failed
read was presented as an empty library. The Ask-history read beside them had
this right already (D4612), so one strip held both conventions. All of them are
null until a read succeeds, and every tile reading `totals` goes through its
unreadable state first.

Existing history also survives the last answerable document: the empty state was
gated on `indexed === 0` and replaced the whole body — composer, thread and tabs
— so a reader who removed their last document lost the answers they had already
been given behind a card saying "Nothing to ask yet". It is now for a reader with
no answerable documents **and** no history. Per S1's 2026-11-07 note, the empty
state leads with **Add evidence** over Open Library, and the Export /
Clear-history row is hidden when there is nothing to manage.
