### 1. Migration 621

On `dd_findings`:

| Column | Meaning |
|---|---|
| `owner_user_id` | who works the flag |
| `state` | `open`, `in_progress`, `condition_to_close`, `accepted` or `closed`; `NOT NULL DEFAULT 'open'` with a CHECK |
| `resolution_enc` | what closed or accepted it, column-cipher ciphertext keyed to the finding, like `detail_enc` |
| `raised_by_user_id` | who raised it by hand; NULL for a connector's finding |
| `checklist_item_id` | the checklist item it was raised against |
| `updated_at` | the last change to owner, state or resolution |

- **The three references are `ON DELETE SET NULL`,** as the checklist's owner is. An account or an item going never blocks the delete and never takes the flag with it.
- **Every row starts `open`.** That is true of a connector finding nobody has worked yet, and a connector's insert, which names none of these columns, keeps working.
- **The backfill** reads a row that already has `resolved_at` as `closed`. Nothing wrote `resolved_at` before this, so on production every row reads `open`.
- **The resolution column is ciphertext**, not the plain `resolution` the issue named, because every free text on a case is.

### 2. Raise a flag: `POST /api/dd/cases/:uid/findings`

- **The body:** `section_id`, `severity` and `title` (at most 200 characters) are required. `detail` (4,000, encrypted), `owner_user_id` and `checklist_item_id` are optional.
- **Stored as:** `source_kind 'manual'`, `raised_by_user_id`, state `open`.
- **Who may raise** (`requireCaseWriter`, then the checklist's rule):
  - admin and the case lead raise in any section;
  - a section's reviewer raises only in the sections they review;
  - an observer reads only;
  - anyone else, an advisor included, is 403.
- **Refusals, each with its code:**
  - 400 `section_required`, `invalid_severity`, `invalid_title`, `invalid_detail`, `item_other_section`;
  - 404 `section_not_on_case`, `owner_not_found`, `item_not_on_case`.
- **After the write:** it writes `finding_raised` to `dd_audit_log`, recomputes the score, and answers 201 with the flag and the score.

### 3. Work a flag: `PATCH /api/dd/cases/:uid/findings/:id`

- **The body:** any of `owner_user_id` (null clears it), `state` and `resolution`.
- **Connector findings and hand-raised flags are worked alike.**
- **Who may work it:** the same rule as raising, by the flag's section. A flag with no section (case-wide) is the lead's and admin's alone.
- **A resolution is required to accept or to close** (`resolution_required`). An accepted flag keeps the resolution it already has.
- **Closing stamps the resolution:** `resolved_at` (a SQL stamp) and `resolved_by_user_id`. Leaving `closed` clears both.
- **The score:**
  - It is recomputed on every change.
  - **Only a closed flag leaves the score.** `recomputeAndStoreScore` and D1246's blocking rule already skip `resolved_at`.
  - An accepted flag stays scored: a risk taken on is still a risk.
- **Two writers never both win.** The update is guarded on the state it read. A guard that matches no row is 409 `finding_changed`.
- **The audit row:** each change writes `finding_closed`, `finding_reopened` or `finding_updated`. Its encrypted details hold `from_state`, `to_state`, `owner_from`, `owner_to` and `resolution_changed`. It never holds the resolution's text.
- **Refusals:** `nothing_to_change`, `invalid_state`, `invalid_owner`, `owner_not_found`, `invalid_resolution`, `finding_not_found` (another case's flag included).

### 4. History: `GET /api/dd/cases/:uid/findings/:id/history`

- **What it returns:** the flag's rows in `dd_audit_log` (`target_type 'dd_finding'`), oldest first. Each row is `{ id, action, at, actor_user_id, actor_name, details }`.
- **Who may read it:** admin, the lead, and anyone on the flag's section, an observer included.
- **No email address.** An actor whose account is gone keeps the row, with `actor_name` null.

### 5. The case read

- **Each finding** carries `state`, `owner_user_id`, `raised_by_user_id`, `checklist_item_id`, `resolution` (decrypted), `resolved_by_user_id`, `updated_at` and `source` (`raised` or `connector`).
- **A new `flags` list** holds every finding (`kind 'finding'`) and every checklist item marked flag or fail (`kind 'checklist'`, `source 'checklist'`, `item_status`, state `open`).
  - The score has counted those items since build queue #128.
  - An item with no severity of its own carries the score's default (fail → medium, flag → low), with `severity_recorded: false`, so the page can say so.
  - A section reviewer sees only their sections' flags, as with findings.

### 6. The report

The report keeps every finding, a closed one included. Under each, it draws `flagStateLine`: the state in words (`FLAG_STATE_WORD`), then the resolution ("Closed — …").

Both renderers draw it:
- the HTML, which the Browser binding prints when it is bound;
- the pdf-lib PDF otherwise.

A report built from rows that predate 621 draws no state line.

### 7. Not built here

- **Raising from a checklist item in one step.** `checklist_item_id` links a hand-raised flag to its item, but marking an item flag or fail does not create a finding. The `flags` list shows the item itself. A flag raised against it appears beside it, linked by `checklist_item_id`. The score counts both; its worst-severity floor is unchanged by counting the same section twice.
- **A flag's severity cannot be changed after it is raised.** The issue asked for owner, state and resolution only.
