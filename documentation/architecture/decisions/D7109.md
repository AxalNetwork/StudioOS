## D7109 — Manual "Fix conflicts" check: signed-event adapters and the conflict-only dispatch (#7109)

**Context.** #7109 asks for an App-owned, advisory **Merge queue conflict** check on a pull request that the merge
queue removed for a conflict on `main`, with a **Fix conflicts** button that asks for a conflict-only repair. PR #7111
landed the pure check and the click handler (`merge-control/src/lib/manualConflictCheck.ts`,
`merge-control/src/manualConflictActions.ts`). PR #7089 landed the branch keeper, the conflict resolver and the model
runner under `scripts/landing-bot/`. #7088's separate model runner closed unmerged as superseded by #7089, so nothing
here adds a runner. On 2026-11-27 the owner asked for the remaining code as a `Part of #7109` PR. The hosted proof
waits on the owner (below).

**Decision.**

1. **Ingress keeps only verified fields.** After the existing HMAC check, `conflictIngress` (in
   `merge-control/src/manualConflictIngress.ts`, called from `webhook.ts`) adds a `conflict` field to the queued
   delivery for three events, and only for those:
   - `pull_request.dequeued`: repository, installation, PR, head, head repository, base ref and SHA, and the reason;
   - `check_run.requested_action`: a reduced copy of the fields the click handler reads, without output text or
     sender e-mail. The sender's login is kept because the collaborator-permission check needs it, and the audit
     row records who asked;
   - a moved PR (`synchronize`, `enqueued`, `closed`, `converted_to_draft`, `edited`): the number only.

   A malformed conflict event gets a 400. Other `check_run` actions are acknowledged and never queued.
2. **The repository object does the work, behind two switches.** `RepoControl.process` calls `processConflict` only
   when the kill switch is off. That function does nothing unless the Worker variable `MANUAL_CONFLICT_ENABLED` is
   `true` and `GITHUB_REPOSITORY_ID`, `GITHUB_APP_ID` and `GITHUB_INSTALLATION_ID` are all set. Both default to off.
   Each outcome adds one `conflict` audit row.
3. **The ejection is correlated to the latest queue transition.** One GraphQL read gets the PR, `isInMergeQueue`,
   `mergeable` and the latest `ADDED_TO`/`REMOVED_FROM_MERGE_QUEUE_EVENT`:
   - The removal's node ID becomes the signed snapshot's `removalId`. The snapshot is stored before the check is
     published, so a later click is checked against the signed ejection and not only the live read.
   - An uncomputed `mergeable` throws, so the Queue retries it; it is never read as "no conflict".
   - `CONFLICTING` is GitHub's answer against the PR's base (`main`). A conflict with a PR ahead in the queue that
     does not reproduce on `main` therefore publishes nothing.
   - Reasons are normalised (`Merge conflict` becomes `MERGE_CONFLICT`).
4. **Durable state is on Durable Object storage, and each multi-key change is one `put(entries)`.**
   - The check is published once per key (repository, PR, head, base, removal). After an ambiguous POST, the App's
     check with that `external_id` on that head is adopted rather than posted again.
   - A click reserves its request and appends it to the outbox in the same write. The outbox holds at most 20; a
     full outbox refuses the request for the Queue to retry.
   - Each request is dispatched once, and redeliveries and repeated clicks only drain the outbox.
   - A click on a stale button (head, base, queue, mergeability or removal moved), or a push or re-queue, sets the
     check to `expired` so it no longer offers the button. An unauthorized click changes nothing.
5. **The repair reuses the conflict resolver.** It does not add a runner. The dispatch is
   `landing-bot-conflict.yml` on `main` with `pr`, `expected_head`, `expected_base` and a 16-hex `request` id
   (derived from the key), using the App's D5618 `actions: write` token, never the checks token.
   - Before any model call, `plan` checks the repository variable `LANDING_BOT_MANUAL_CONFLICT` (`true` only), both
     pins, the PR's queue state (GraphQL), GitHub still reporting the conflict, and that no earlier run carries the
     request id. A repeated dispatch therefore costs nothing.
   - `apply` checks the switch, base and queue again before it pushes.
   - When a request cannot run, a moved head, moved base, re-queue or vanished conflict gets one sticky line
     (`report`) and no label. A switch that is off writes nothing.
   - Everything else is unchanged: `eligible()`, `attempts()`, `budget()` and the breakers, conflicted files only,
     `checkResolution()`, a normal merge commit, never forced, to the PR's own branch, a fresh CI run on the new
     head, and the owner landing every model-resolved PR.
   - The model keys stay in the `repair` environment's edit job. Merge Control never sees one.
6. **No new permission on the existing token scopes.** The conflict path uses its own token with `checks: write`,
   `contents: read` and `pull_requests: read`, like D5990's separate policy scope. `github.ts` gains a single
   `POST graphql` path.

**Not done here (owner steps, and the hosted proof).**
- The maintenance App needs **Checks: write** and **Pull requests: read**, and the **Check run** and
  **Pull request** event subscriptions.
- The Worker needs the `MANUAL_CONFLICT_ENABLED` and `GITHUB_REPOSITORY_ID` variables, and the repository needs
  `LANDING_BOT_MANUAL_CONFLICT`.
- The disposable-PR verification (#7109's last criterion) runs after these steps; nothing here ran it.
- The resolver's `apply` does not update the Merge Control check with the final outcome. The check run belongs to
  the maintenance App, and GitHub lets only the creating App update it. The outcome is in the sticky comment and the
  run summary (run name `Conflict resolver for #<n> (request <id>)`).
