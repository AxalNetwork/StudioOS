## D8068 — The identity chain: four trailers on every agent commit, checked by `provenance` (#8068)

**Decision date:** 2026-11-21. **Scope:** commit messages, one advisory CI workflow and
AGENTS.md; no application, database or production change.

### What every agent commit carries

Each commit an agent writes ends with one trailer block naming its slot, task, run and
session, each key exactly once:

```text
Agent-Slot: S21
Agent-Task: #6476
Agent-Run: <CI run id, or manual>
Agent-Session: <https:// session URL>
```

AGENTS.md § "Identity trailers" is the contract an agent reads. The parser in
`scripts/ci/agent-provenance.mjs` is the one that applies it, and
`scripts/ci/agent-provenance.test.mjs` reads that section and fails when the two differ:
the trailer names and their order, each documented example, the value boundaries and the
cutover sentence. The trailers we had until now (`Claude-Session`, `Co-Authored-By`)
were informal. This makes them a contract any vendor's agent can meet.

Rules beyond the four values:

- The block is the message's last paragraph, never the subject, and every one of its
  lines is `Key: value`. Other trailers (`Co-Authored-By`) may share it.
- All commits a pull request adds name one slot and one task. On
  `agent/<agent>/<issue>-<slug>` that task is the branch's issue.
- A merge commit is exempt only when its combined diff (`git diff-tree --cc`) is empty,
  so it adds nothing neither parent had. That covers the landing bot's merge from main
  (#6474). A merge that resolves a conflict or adds content carries the chain like any
  other commit.
- At most 250 commits per range, the same bound the landing bot reads.

### Cutover for `Claude-Session`

Before **2026-12-01T00:00:00Z** (committer date), a commit may give `Claude-Session` in
place of `Agent-Session`. From that instant on, `Claude-Session` alone fails the check.
When both are given, `Agent-Session` is the one read. The committer date can be set by
whoever writes the commit. The cutover is a migration aid, not a security boundary.

### The check

`.github/workflows/agent-provenance.yml` (job `provenance`) runs on `pull_request`
(not on drafts; it runs again on `ready_for_review`) and on `merge_group`.

- **Which pull requests.** It checks only a pull request whose head branch matches
  `agent/**`. Any other branch is reported as `verdict=skipped` and passes. In the
  queue, the queued pull request is read from the `gh-readonly-queue/main/pr-<n>-…` ref.
  Its own commits are then checked, not the squash.
- **Which copy of the check.** The base commit's copy of `agent-provenance.mjs` judges
  the branch, so a branch cannot edit the check that judges it. Only the pull request
  that adds the file (this one) runs its own copy, and the log says `source=pr`.
- **What it leaves.** It writes `provenance.json`, kept as the `provenance` artifact for
  30 days. The file holds the verdict, the branch, the range, the slot, the task, every
  run and session, and each commit's sha with its problems. The last log line,
  `agent-provenance: verdict=<pass|fail|skipped> head=<sha> commits=<n> source=<base|pr>`,
  is what a reader of the job log uses.
- **Running it locally.** `node scripts/ci/agent-provenance.mjs --base origin/main --head HEAD`
  checks a range with no branch filter. Add `--branch <name>` to apply the `agent/**`
  filter and `--out <file>` to write the JSON.

### Advisory until the owner makes it required

The job is `continue-on-error: true`. It reports, but it blocks nothing until the owner
adds `provenance` to main's required checks in the ruleset. When that happens, the same
change:

- removes `continue-on-error`;
- adds the context to `scripts/lib/requiredChecks.mjs`;
- moves the workflow out of `ADVISORY_QUEUE_WORKFLOWS` in
  `frontend/test/merge_queue_ci_4107.test.mjs`. A required check must not carry a
  job-level `if:`, so the draft skip goes with it.

Until then, `merge_queue_ci_4107` lists the workflow as an advisory queue workflow.

### The landing bot

The landing bot reads the verdict as one more eligibility reason. The read belongs in
`scripts/landing-bot/feeder-github.mjs`, and S21 owns the bot, so the read is proposed as
a diff on #6478 rather than edited here. The proposed read trusts a verdict only when all
of these hold:

- the `provenance` check run on the exact head is from GitHub Actions;
- its run is this workflow's `pull_request` run for that PR;
- the log's last line says `verdict=pass`, the same head and `source=base`;
- the PR touches neither the workflow nor the script.

A one-line retryable reason in `ejection-rules.mjs` stays S21's.

### Follow-ups, not in this decision

- **Signing.** Trailers are text that whoever writes the commit can forge. Sigstore
  (gitsign) signing of agent commits, verified in the same check, is a follow-up. The
  chain says who claims a commit. A signature would prove it.
- **App identities.** GitHub App identities per agent are #8061. Those Apps' commits carry
  the same trailers.
- The publisher stamping the trailers is #5569.

### Rollback

To roll back, delete `.github/workflows/agent-provenance.yml` and revert this PR's two
registry lines:

- the `merge_queue_ci_4107` entry;
- the `workflow-channels.json` entry.

Then regenerate `.github/workflows/README.md` with
`node scripts/workflow-inventory.mjs --write`. The check is advisory and nothing else
reads its artifact yet, so no landing or deploy depends on it. The AGENTS.md section can
stay as guidance or go in the same revert. Commits already written with the trailers need
no change, because git ignores trailers it does not know.
