## D5674 — Recording-stage source evidence and qualified recovery (#5674)

**Status:** local source implementation. No recording, production write, Slack send or observability setting was activated. Shared delivery/channel canary and a deployed affected-stage check remain prerequisites (#5665/#5671/#3588). The queue hold #5657 closed before draft publication.

The existing meeting_bots, interview processing/final receipts, runtime startup codes and cumulative diagnostic snapshots remain the authorities. The new HQ-only source read selects codes/times/status and final-receipt existence, never URLs, names, participant data, encrypted payloads or media. It does not create another recording ledger, change consent/billing, start a meeting or widen Teams. Reused sessions cannot prove one run's final receipt; ambiguity remains unknown.

The source separates idle fleet, disabled provider, expected cancellation/isolated admission denial, startup failure, never-arrived callback, capture stall, upload-stage failure and downstream processing. Existing startup/heartbeat/processing time budgets are reused; no new live paging threshold is approved. A failure without evidence of its stage is not relabelled as a specific upload or capture error. Missing/capped/unreadable evidence is unknown. Actual demand is considered against scheduled time, not an idle container count. Enabled flags do not suppress failures of already active work when new admission is off.

Only counts by provider, window, closed error category, version when known and owner enter the D5673 source contract. Existing HQ causes meeting_bot:start_failed and meeting_bot:unreported are attached as typed platform-episode references; site and host therefore feed the same subject instead of creating per-sensor incidents. Other stage causes use a service/provider/stage key. Recording keys are used internally to deduplicate retried/older observations, and are discarded before the source boundary. The shared sender #5665 owns the episode/thread and actual delivery, never this read.

Recovery requires a complete trusted open-episode inventory, fresh final success after the episode opened at the affected version, or explicit fresh verification of that stage. A deploy, process exit, missing callback, zero active fleet, old success or unreadable ledger cannot close an incident. Shared startup causes wait for all affected providers to recover. The default HQ read supplies no invented episode inventory and therefore cannot claim a recovery. Integration with the existing episode/delivery owner is still required before live routing.

The stage coverage response explicitly distinguishes demand/callback/processing/terminal ledger facts from dispatch, scheduling, container start/readiness, admission, notice, capture and upload boundaries that require verified cumulative snapshots. Existing one-off diagnostics have no index; this change does not pretend to query all of them. A complete production timeline/push adapter and actual stage-verification receipt remain acceptance work, not inferred data.

Both meeting host environments receive explicit source-controlled private logs and 1% trace sampling, with no archive tail consumer. Existing structured startup events remain private and are not copied to Slack. A planning estimate is about eight structured host stages per start plus native invocation metadata: at N starts/day, roughly 8N stage records before retries. This is not measured volume or a cost quote. Production and preview volumes/retention must be measured separately against the account plan before deployment; no account retention setting was changed.

The private preflight returns presence/capability checks only, not credential values or a successful-provider claim. Missing host/run bindings, signing context, callback origin and Zoom prerequisites have explicit boolean checks and an owner action in the rollout runbook. The canary must be provider-free and #3588 retains live Meet/Zoom acceptance; #3709 retains Teams rollout.

Tests exercise the requested outcome matrix, duplicate callbacks/revisions, no identifiers in receipts, provider gate awareness, existing shared causes, stale/wrong-version success, incomplete episode inventory and verified recovery. Four deliberate mutations break urgency, dedupe, final-receipt proof and freshness. These fixtures are not deployed recording evidence. Rollback removes the source route or mutes its shared sender route while preserving recording/episode history and existing B1 operations; revert host observability independently if its measured budget is exceeded.
