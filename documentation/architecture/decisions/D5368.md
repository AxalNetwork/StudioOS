## D5368 — A promo use is reserved atomically with its discount (#5368)

`max_redemptions` is enforced in the same conditional
`promo_ceiling_reservations` insert as the licence ceiling. The predicate uses
the greater of the mirrored redemption count and committed reservation count,
then adds unexpired reserved rows. With one use left, racing checkouts can
therefore create exactly one hold. This applies with or without a licence
ceiling and to subscription, one-time, cart, free-unlock, and automatic-offer
paths.

A live reservation is checked before the code is revalidated. A retry of the
same checkout owns the row it already made even when the cap has since filled.
Automatic offers use a stable `auto` checkout key; a retry looks up that key's
promo before choosing an offer again, so a later cap or licence-ceiling change
cannot silently remove the held discount. Released or expired reservations do
not consume a use and must pass the current atomic predicate to be retaken.

When a code has a cap, failure to read or write the cap fails closed with
`usage_limit_unreadable`. An uncapped code keeps D4855's no-ceiling trade-off:
a ledger write failure is counted but does not block the sale.

## Recurring invoices

The owner chose to hold exhausted renewals for review. For a draft
`subscription_cycle` invoice, the billing webhook matches the applied Stripe
discount to the promotion stamped at checkout and reserves that amount under
the invoice ID. Checkout reservations and renewal reservations share the code
cap and the branch currency and spend ceiling. Paid renewals count separately
from Stripe's native subscription-redemption counter.

If a reservation is refused, the Worker updates the draft with
`auto_advance=false` and the Stripe invoice metadata
`axal_promo_review=required`. Review the draft in Stripe. A reviewer must keep
it held until the discount is authorized or the invoice is voided. Do not
manually collect an unreserved discount. The Worker never removes a discount
or changes the invoice total to resolve a cap refusal.

An admitted invoice retains its reservation through payment retries. A paid
event commits it and inserts one usage row per invoice. A void event releases
an unpaid reservation.

Before enabling this flow, verify that each account-level Stripe destination
delivers `invoice.created`, `invoice.paid`, and `invoice.voided` to the billing
webhook and rehearse both draft outcomes with Stripe test clocks. Stripe
can finalize an invoice after 72 hours without a successful webhook response,
so a prolonged delivery outage can bypass webhook enforcement. Monitor failed
deliveries and inspect draft renewals during outages. This flow covers
automatically generated subscription-cycle invoices, not synchronous
subscription updates or manually finalized invoices.
