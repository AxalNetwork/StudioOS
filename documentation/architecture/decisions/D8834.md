### The route

`POST /signoff {pr, head_sha, actor}` is an owner route. `index.ts` reaches it only after the `ownerAuthorized(request, env.OWNER_TOKEN)` check that guards `/status`, `/switch` and `/claims`, and `signoffRequest` checks the token again itself. A call without the token, with another token or with no token configured gets 401. `pr` must be a positive integer, `head_sha` a full lowercase SHA and `actor` a GitHub login; anything else is a 400. The body is capped at 4 KB.

`RepoControl.signoff` runs in the object's serial order. It refuses with a 409 and stores nothing when:
- the kill switch is on (`kill_switch_on`);
- `head_sha` is not the head Merge Control last recorded for `pr` (`not_current_head`);
- that head has no pull-request policy decision under this `policy_version` (`no_decision`). A merge-group candidate cannot be signed: it is never a recorded pull request head, and its decision is a merge group's.

Otherwise it stores `{pr, head_sha, actor, policy_version, at}` under `signoff:<pr>:<head_sha>` and writes one `signoff` row to the D5990 `audit` table, whose triggers refuse `UPDATE` and `DELETE`. A repeat call for the same head stores and audits nothing new, and keeps the first actor. It then re-posts `merge-control/policy` on that SHA only, through D5990's `policy` path and its one `checks: write` client:
- conclusion `success`, title "T2: signed off by the owner";
- `external_id` `<policy_version>:signoff`, and this file as `details_url`;
- the actor, the pull request and the time in the text.

A pull request delivery for that head re-posts the sign-off once if the earlier post failed, and never after. Labels, comments and reviews still reach no policy code (`policyTarget` returns null for them), so they cannot create a sign-off.

**A sign-off counts only under the `policy_version` it was made under.** After a deploy the owner signs off again. That matches D5990's one decision per head and `policy_version`, and it fails closed.

### Which head a merge group is about

The `merge_group` event names the candidate, its base and the queue branch, but no pull request and no pull request head (D8692). Two parts make the binding:

1. **The pull request** is read from the queue branch: `refs/heads/gh-readonly-queue/main/pr-<n>-<sha>`. Any other form leaves `pr` null, and the group stays `action_required` ("the queue branch names no pull request"). The SHA in the branch name is not used.
2. **The enqueued head** is the head Merge Control last recorded for `<n>`. Each `opened`, `synchronize` and `reopened` delivery stores `pr-head:<n> = {sha, at}`, and the newer ingress time wins. The head is recorded while the kill switch is on too, because recording makes no GitHub call. GitHub removes an entry from the queue when its head moves, so at `checks_requested` this is the queued head. A late or missing delivery can still leave it stale. The binding below then fails, and the group fails closed.

The sign-off is then looked up at the exact key `signoff:<n>:<recorded head>`. The SHA in the key is what makes "a sign-off for A passes A, not B". Dropping it from the key is a mutation the tests catch.

### Binding the candidate to the signed head

A merge-group head is a squash candidate, not the pull request head (D8692). D8692 proves the binding with `git merge-tree`, which a Worker cannot run. `bindCandidate` does the same proof over the API, using the `contents: read` the policy token already has:
- `GET git/commits/<candidate>`: its only parent must be the group's `base_sha`;
- `GET compare/<base>...<head>`: the merge base;
- the recursive trees of the base, the head, the merge base and the candidate.

Each path is compared as mode, type and object SHA:
- if the head left the path as the merge base had it, or both sides agree, the candidate must hold the base's version;
- if only the head changed it, the candidate must hold the head's version;
- if both sides changed it differently, the content merge cannot be checked without git, so it is refused.

A truncated or malformed tree is an error. Every check passes only when the candidate's whole tree is exactly the trivial merge of the base and the signed head. So every path in it is either already on the base or is content the owner signed off.

This is stricter than D8692 in one place: a file both sides changed is refused, where `git merge-tree` could merge it cleanly. The owner rebases the pull request and signs off the new head. A rename that `merge-tree` would follow is also seen as changes on both sides, and refused.

### The decision

`decide(result, target, evidence)` changes only for a T2 `merge_group`:
- **`success`** (tier T2, title "T2: signed off by the owner"), only when the evidence is `ok` and the classification finished (`result.complete`). An evaluation error, such as a compare failure or a timeout, is never signed past.
- **`action_required`** otherwise. The reasons are the classifier's, then `SIGNOFF_PENDING` ("a T2 merge-group head passes only with an owner sign-off for its enqueued pull request head"), then why the evidence failed.

`mergeGroupSignoff` gathers the evidence only for a T2 merge group, so T0 and T1 heads make no extra read. It never throws. Each of these returns `ok: false` with its reason:
- no pull request number, no recorded head, or no sign-off;
- a sign-off under another `policy_version`;
- a candidate that does not bind;
- any API or storage error, and a timeout after 15 seconds.

The decision is stored once per candidate and `policy_version`, as D5990 does. A merge group decided before the sign-off keeps its `action_required`. Queueing the pull request again builds a new candidate.

`PolicyResult` gains `complete`, true only for a finished classification. `SIGNOFF_PENDING` keeps its name, because D5990's test imports it, and now states the rule that is built.

### Tests

`merge-control/test/signoff_8834.test.ts` (8 tests). It does not touch `policy_check_5620.test.ts` or `policy_check_run_5990.test.ts`, both of which still pass unchanged. The tests cover:
- a sign-off re-posts success on its head only, and a merge group built from that head passes;
- a sign-off for A passes A and not B, and a new push needs a new sign-off;
- a T2 merge group without a sign-off stays `action_required`, and `decide` passes only on `ok` evidence for a finished classification;
- a wrong tree, an extra path, two parents, another parent, a path changed on both sides and a dropped base change all fail, and a clean three-way merge binds;
- a commit, compare or tree error, a storage error and a sign-off under another `policy_version` never post success;
- a label, a comment or an approving review changes nothing;
- one audit row per sign-off, and refusals store nothing;
- 401 without the owner token, and 400 on a bad body.

Mutation check (`node scripts/mutation-check.mjs`, focused file): 23 mutations, 23 caught, 0 equivalent. They include:
- the SHA dropped from the sign-off key;
- the T2 merge-group branch skipped;
- the evidence or `complete` ignored;
- the `policy_version` check removed;
- the lookup's catch returning `ok`;
- the parent check, the tree comparison, the both-sides refusal and the merge base each removed;
- a truncated tree accepted;
- the route's own token check removed, and the route reached before `index.ts`'s check;
- the actor check removed;
- the current-head, kill-switch and merge-group-decision refusals removed;
- the audit row removed, or written on every call;
- the re-post skipped, or repeated on every call;
- the newer-head rule removed;
- the queue branch not parsed.
