### 1. The People read: `GET /api/mail/people`

`routes/mail_people.ts`, mounted at `/api/mail`, over `services/mail/people.ts`. It answers:

```
{ profile, groups: [{ key, label, people: [{ ref, name, role, source, last_contact, marker, marker_label }], empty, error }], note, empty }
```

The profile comes from `users.role`. `partner` is the operating partner and `exploring` the Explorer. The groups are the canvas's:

| Profile | Groups, in order | Person kinds |
|---|---|---|
| Investor | Founders · deal flow, Founders · portfolio, Co-investors, Network matches | `deal:<entry>`, `holding:<project>`, `coinvestor:<relationship>`, `member:<share>` |
| Advisor | Clients · sessions, Cohort founders, Network matches | `client:<user>`, `cohort:<cycle>-<user>`, `member:` |
| Operating partner | Clients · engagements, Leads, Network matches | `engagement:<id>`, `lead:<quote>`, `member:` |
| Admin | Spin-Out Lab applicants, Open support tickets, Partner firms | `application:<id>`, `ticket:<id>` |
| Explorer | Network matches | `member:` |
| Founder | Network matches | `member:` (the founder's module people are D1341's kinds, listed by each module's own page) |

Each person carries:
- a source label in the canvas's words: "From Deals", "From Portfolio", "From Deals · co-investing", "From Practice · sessions", "From Cohorts · 2026-11 cohort", "From Delivery · engagement", "From Pipeline · proposal sent", "From Programs · application", "From Support · ticket #4821", "Network · accepted ‹day›";
- the last contact day, which is the module's own last touch;
- a marker (§3).

A group whose module cannot be read says so ("‹Group› could not be read. Try again."). It is never shown as empty. An empty group has its own sentence. The admin's pane carries the canvas's note: "Admins email members only about a case they hold: an application, a ticket or a partner agreement. Eadwyn reads that case, never a member's own records." The Explorer's carries "Explorers see Network matches only…" and the empty line "Pick a Network match to write to them. Email opens once you have both shared an address."

### 2. Each group and source, under its module's own rule

`services/mail/profileRecords.ts` reads each kind when it is opened (`GET /api/mail/context?person=`, the drafts, and the MCP tools in D1343). The list and the record apply the same rule. A kind outside the member's profile, or a row the rule does not admit, is "Record not found.", the same as one that does not exist.

| Kind | Rule (the module's own) | What Eadwyn may quote, each with `as_of` |
|---|---|---|
| `deal` | the investor's own deal flow, `scope_key 'u:<id>'`, as `GET /api/deals/flow` | the deal note, stage and revisit; the portfolio KPIs the founder shared; co-investment status |
| `holding` | `investorHeldProjectIds`: a relationship and a confirmed commitment | the venture; the KPIs shared with investors; co-investment status |
| shared KPIs | `GET /api/portfolio-updates`' rule: a submitted update of a venture the investor relates to, naming them or with audience investors, read through `updateFigures` | an update shared with the team only is absent |
| co-investment | `GET /api/networkfx/syndicates`' rule: syndicates on the deal the member created or joined | the syndicate's status and members |
| `coinvestor` | an accepted `partner_relationships` row of type `co_investor` the member is in | the relationship and the member's own open reminder |
| `client` | the advisor's roster: a booking with them (`requireRosterClient`) | their sessions; the advisor's session notes (`advisor_client_notes`); the next session booked; their active Expertise services |
| `cohort` | an active `advisor_cohort_assignments` row for the cycle, not opted out (`optedOutFounderIds`), as `GET /api/advisors/me/cohort/:cycleId/founders` | the cohort week plan (each week's status, deliverables and deadline); their services |
| `engagement` | `engagements.partner_id` is the partner's (`actingPartner`) | the latest **sent** status report; the milestones; their active Offers (`service_offerings`) |
| `lead` | a `quotes` row of the partner's, on a founder need | the proposal (need, price, timeline, deliverables); their Offers |
| `application` | held (§4) | the application and its interview, nothing else |
| `ticket` | held (§4) | the ticket, nothing else |

`engagements.founder_id` and `founder_needs.founder_id` are `founders.id`. They are joined to `founders`, as `needs.ts` joins them, never to `users`. The partner delivery and pipeline routes join them to `users` (`partner_delivery.ts:149, 1550`, `partner_pipeline.ts:230, 440`). That is left for its own issue.

**An investor's firm scope.** The investor's pack and pane read the personal scope (`u:<id>`), as `GET /api/deals/flow` does without an active-company header. A firm's shared deal flow (`c:<company>`) is not read here yet.

### 3. The markers are derived, never stored

`markerOf({ lastFromThem, dueAt }, now)` in `people.ts`:
- **"Follow-up due"** is a module's own due date that has passed:
  - a deal's `revisit_at`;
  - a co-investor reminder's `remind_at`;
  - an advisor engagement's `term_ends_at`, not ended;
  - a cohort week past its `deadline_at` that is neither passed nor failed;
  - a milestone's `due_at`, not completed;
  - a Lab interview held (`scheduled_at` passed) still `scheduled`.
- **"Needs a reply"** is a thread whose last message is theirs, from a mailbox that shows replies. It wins over a due date.

No table stores a marker. **No person carries "Needs a reply" yet.** Nothing stores inbound mail. `listThread` exists on the Outlook adapter (D1340) but nothing calls it. A Gmail mailbox sends only (D1347 §1, Q1). Reading a thread per person needs the person's address, which D414 withholds for every kind but a ready Network match. The derivation is built and tested. Wiring it to a thread read is the owner's call (§5).

### 4. An admin reads the case only

- **Held applications.** The admin scheduled its interview (`spinout_application_interviews.scheduled_by`) or decided it (`cohort_applicants.decided_by = 'admin:<id>'`, bound whole). A withdrawn one is not held.
- **Held tickets.** `open` or `in_progress`, with `assigned_to` equal to the admin's address or name, ignoring case. `tickets.assigned_to` is free text, set only by an admin (`tickets.ts`). Two admins with the same name would both hold a ticket assigned by that name.
- **Partner firms.** No table records an Axal holder for a partner firm or agreement, so the group is empty with the sentence "No partner firm records an Axal holder yet, so none is listed." It is not guessed (§5).
- **The pack is the case.** `caseOnly(user)`:
  - `personRecord` refuses every other kind for an admin, including founder modules, advisor and partner engagements, and Network matches;
  - `companyItems` adds nothing, even with a `project` named;
  - `blocksNow` computes no block;
  - `POST /api/mail/blocks` is 403 `case_only`, "An admin's email quotes the case only."
  - D1341's blocks test now expects that 403 where it expected `{ block: null }`.

The relationships `founder`, `coinvestor` and `case` gain their own intents in `intents.ts`. For `case` they are "Ask for what is missing", "Share the next step" and "Answer their question".

### 5. For the owner

1. **"Needs a reply"** needs a thread read (§3). Option A: call Outlook's `listThread` for a person whose address the member has, which today means a ready Network match. Option B: leave it to a later part that stores inbound replies.
2. **An admin's partner firms** need a holder column (§4). For example, `partner_invitations.invited_by_user_id` could count as holding that firm's agreement.
3. **The founder's People groups** (Customers, Co-founders, Investors, Advisors, Operating partners) are not in #3555's list. Today the founder pane lists Network matches, and D1341's kinds open as before. #3552 can draw the founder's groups from the module lists, or a follow-up can add them to this read.

### 6. Verified

`cloudflare-worker/test/mail_people_d1348.test.ts` has 8 tests, on the real migrated schema with the drafts, shares and people routes mounted:
1. each profile's groups, exactly;
2. the markers, derived;
3. investor: their own deal flow only, holdings that are commitments, co-investors not mentors; the deal pack's note, the KPIs shared with investors (not the team-only update) and the syndicate, with dates; another investor's entry, a relationship that is not a holding, and a kind outside the profile are 404;
4. advisor: the roster and the cohort; notes, the next session, active services only; another advisor's client and an ended assignment are 404;
5. operating partner: engagements and proposals of their own; the sent report, not the draft; milestones; Offers; another partner's rows are 404;
6. admin: only held applications and open tickets assigned to them; partner firms empty with the sentence; the pack is the case only, even with a project named; every founder-module kind is 404; blocks are 403; an estimate carries no block;
7. Explorer: Network matches only, with the canvas's empty line; every other profile's kind is 404;
8. a group that cannot be read says so, and the others still read.

The tests also check that an opted-out cohort founder is neither listed nor readable, and that a completed milestone or an interview with an outcome carries no marker.

35 mutations were run and 33 were caught. The two survivors are the admin checks in `companyItems` and `blocksNow`. They are defence in depth: every block's own module gate already gives an admin nothing (D1341's test), so removing either check changes no result today. `POST /api/mail/blocks`' 403 and `personRecord`'s refusal are each caught.

The client method is `people()` in `frontend/src/lib/api/mail.js`.
