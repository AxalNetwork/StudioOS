## D9151 — Research › Funds: the Sheets Connect state is bound to the browser that started it, and the callback re-checks the account (#9151)

Under #4570. Closes the two Hardening items `D4570-p10.md` § Hardening recorded for the Google Sheets callback
(`GET /api/research/funds/sheet/callback`).

### What was wrong

- The state proved that Connect minted it, not where. Any browser bringing back the Super Admin's valid state landed a
  refresh token on the Super Admin's connection, linked to whichever Google account completed consent (login CSRF).
- The callback read the state's user without `is_active`, so a Super Admin disabled after Connect could still land a
  token for up to ten minutes.

Neither was exploitable without the Super Admin's own ten-minute Connect link.

### The binding is a cookie, not PKCE

The issue offered PKCE or an HttpOnly, Secure, SameSite=Lax cookie. The cookie is the one that binds the browser:

- **PKCE would not.** The callback carries no session, so the verifier would sit server-side beside the nonce and be
  sent on the exchange for whoever brought the state back. It protects a code in transit, not who finishes consent.
  Mercury's flow (`routes/mercury_oauth.ts`) uses PKCE for that and a cookie for the browser, the same split.
- **The cookie reuses D722's pattern** (`routes/auth_google.ts`, the Google sign-in state cookie): random value,
  `HttpOnly; Secure; SameSite=Lax`, ten minutes, the session cookie's Domain from `authCookieDomainAttr` (Connect
  answers on the SPA's host, Google returns to the callback host; `.axal.vc` on HQ, host-only on a branch, localhost
  and preview), every value under the name tried in constant time, cleared on every callback answer.
- **No migration.** `oauth_state_tokens.extra_json` already exists (schema baseline); the state row keeps only the
  binding's SHA-256 there, never the value.

### What changed

- `services/fundSheets.ts`: `makeSheetsState` returns `{ state, binding }` and stores `binding_sha256` on the row.
  `consumeSheetsState(env, raw, bindings)` deletes the row first, as before, so a state is spent on first use whatever
  follows, then returns the user only when the signature, the row, the expiry and the binding all hold.
  `sheetsBindingValues` reads the cookie values; `SHEETS_BINDING_COOKIE` (`studioos_sheets_state`) and
  `SHEETS_BINDING_PATH` (`/api/research/funds/sheet`) name it.
- `routes/research.ts`: Connect sets the cookie (and `Cache-Control: no-store`). The callback passes the browser's
  values to `consumeSheetsState`; a missing or wrong binding redirects to `?sheets=error&reason=invalid_state`, with
  no code exchange and no token. The user row is read with `is_active`; an inactive or missing account redirects with
  `reason=forbidden`, before the Super Admin check and before any exchange. Every answer clears the cookie, with the
  Domain Connect set and host-only.

Everything else holds: the state is signed, single-use and ten minutes long, only a Super Admin's state lands a token,
and every refusal redirects with a reason and no secret.

### Tests

`cloudflare-worker/test/authz_research_d4570.test.ts`:

- slice 10's refusals (no, unsigned, forged, never-issued or expired state; an admin's or a founder's state) still
  refuse, each now carrying its own state's binding so the gate it meets is the one it names;
- the Super Admin's valid state with no cookie, the session cookie only, an empty binding, another Connect's binding,
  a binding one character off, or the binding under another name redirects with `reason=invalid_state`, exchanges no
  code, stores no token and is spent;
- a Super Admin made inactive after Connect redirects with `reason=forbidden` and stores no token;
- Connect sets the cookie with `HttpOnly`, `Secure`, `SameSite=Lax`, its path and ten minutes, never in the body or
  the stored row; that browser lands one token after one exchange, the cookie is cleared, and a second use is refused.

Mutation check (`authz_research_d4570.test.ts`): 12 mutations, 12 caught, 0 equivalent.
