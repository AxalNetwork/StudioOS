## D1206 — Calendar read access, provider copying and source errors

2026-10-26 · #3172 · S29, transferred by the owner from S19 · Part of #2420.
No migration, new binding or production data access.

### Built

- Calendar reads and connection operations no longer inherit the broad Investor
  Professional prefix gate. Only `POST /api/calendar/ic-meetings` applies the
  existing Professional guard and its catalogue-backed plan sentence before any
  write. Existing role and deal-party checks remain. The token-authenticated
  my-events feed and D1209’s whole-calendar feed are available on every plan,
  as authenticated reads are. Both token scopes remain personal and distinct.
- Full Google/Outlook sync excludes Calendly before any event read. Totals
  cover copy-eligible items, and `excluded_kinds` names Calendly; an unreadable
  source that will not be copied cannot stop the other copies. Both provider push
  functions also refuse `calendly_event`, including updates of an existing copy.
  The one-event route already excludes that kind. Existing provider copies
  created by earlier syncs are not deleted automatically; a member removes an
  unwanted old duplicate in their provider calendar. No new deletion act is added. Personal `.ics` downloads
  retain Calendly entries; this change prevents copying back to a provider.
- The advisor reader verifies that a linked advisor belongs to the account,
  then falls back to `advisors.user_id`, matching the advisor router. A stale
  pointer cannot grant another advisor's bookings.
- `sources[].error` is only `unreadable`, `not_configured`, or null. Missing
  tables/columns are unavailable sources, not successful empty reads. A failed
  source retains other loaded sources. Strict feeds/downloads/push lookups
  reject a partial read with a fixed kind/code message. Source diagnostics hold
  kind and outcome only, never raw database text or member identifiers.

### Read-only Studio and All studios

The owner chose existing deployment boundaries in this chat on 2026-10-26.
`GET /api/calendar/events?scope=studio` requires Admin on a branch with a
readable current `branch_licence`. It reads each allowed source once with a bound membership CTE for active
local members; there is no per-member query loop or silent member cap. Shared
events appear once. Personal readers remain unchanged. It uses D1207’s item description and cancelled-page options,
with a Read only role and no source-page actions. Another administrator's private calendar stays Super Admin's.
An HQ Studio request says Not read here yet: HQ records no member-to-licence
association (U1); geography and role never substitute for membership.

`scope=all` requires the hydrated Super Admin elevation on HQ. It reads HQ
items and reports each known remote studio as Not read here yet, from the
licence/deployment register and service-binding inventory. Remote calendar
reading remains explicitly unavailable: there is no calendar RPC, and none is
invented. Failed register reads retain HQ items with Unreadable/Try again.
Remote or source gaps set coverage.complete=false; the API never calls HQ-only
items a complete All studios calendar. Combined register, source and result-cap
gaps retain every notice; Unreadable is never downgraded to Not configured.
Staff windows must be ordered and at most 180 days. Each source reads at most
1,001 rows to detect overflow and returns the earliest 1,000, ordered by time
and id. Overflow sets coverage.complete=false and truncated_kinds, with an
explicit Narrow the date window reason. Personal read windows are unchanged.

The owner also chose to exclude private Calendly and wellbeing items from
both staff scopes (2026-10-26). They are never queried there; `excluded_kinds`
names this policy separately from source availability. Personal calendars
retain both kinds. Scoped SQL selects no emails, notes, meeting URLs or private
addresses, rather than reading them and relying only on output redaction.

Every scoped item carries read_only=true and false RSVP/reschedule/cancel/copy
capabilities. Contact emails, private meeting links, notes and copied-provider
metadata are removed. Provider push functions and the ICS serializer also
refuse scoped projections. Scoped reads never replace a personal reader: sync,
one-event push, .ics downloads and token subscriptions still resolve only the
signed-in/token member's own events, ignoring scope query parameters. A failed
licence or membership read returns an unavailable scope rather than a fabricated
empty calendar. One failed calendar source retains the sources that loaded.

### Staff-view audit follow-up

The owner approved recording staff calendar views in this chat on 2026-10-26,
after the initial implementation merged in #3201. Each authorized Studio or
All studios response awaits the existing `logAdminAction` helper with action
`calendar_scope_read`. Its details contain only `scope`, `from` and `to`, with
the dates normalized to ISO instants. Actor identity and timestamps use the
existing audit stores; no target member, event title, attendee, meeting link,
query text or event payload is included. Repeated views each record an entry.
Personal reads and rejected/invalid requests do not create this audit action.
The helper retains its existing independent, best-effort writes to both stores;
this follow-up does not change its failure policy or any calendar source data.

### UPDATE (#4196, part of D4154): each scoped item's owner, company, studio and link

2026-11-02 · C1 of #4154, the Worker part. D4154's decision file arrives with
#4200, so this note is recorded here, on the decision that created the scopes.
No migration, route or binding.

Every Studio and All studios item now also carries:

- `owner: { uid, name }`, the person it belongs to: the IC meeting's organiser,
  the check-in's founder, the booking's booker, the ticket's registrant, the
  event's host, the prospect event's author, the deadline's owner (or its
  written owner's name, with no uid). Read in the source's own bound statement,
  from `users.uid` and `users.name`. Never an email: no scoped statement selects
  one, and a name that is itself an address is dropped, in `owner` and in the
  attendee names alike. Null when nothing records one.
- `company: { uid, name }`, the company its venture sits in
  (`projects.company_id` → `company_profiles`; an IC meeting through its deal).
  One batched statement per read. When it fails, every `company` and `where` is
  null and the read still answers; the log carries counts only.
- `where`, "<company> › <module>" from the source registry, for example
  "Northwind Labs › Build › Compliance"; null when the company is not known.
- `open_href`, the item's page inside its company: `/deals/:id` for an IC
  meeting, `/projects/:id` for a check-in, the company's compliance page
  (`/account/companies/:uid/settings/compliance`, else the venture) for a
  deadline, and `/events/:slug` for a published event. Null for bookings,
  investor meetings and drafts, whose only pages are someone's own. A link,
  never a write: `can` stays all false and `href` stays null.
- On `scope=all` only, `studio: { code, name }` on every row. That scope is
  HQ's alone and reads HQ's D1 alone; remote studios remain Not read here yet,
  so every row it returns is `{ code: 'hq', name: 'HQ-held' }`. A branch's rows
  would carry the branch's code and name, once a remote reader exists.

The guards and the audit are unchanged: a branch admin cannot read `scope=all`
(the route and the service both refuse it), and `logAdminAction` still records
only scope and window. Agent runs: #3957's scheduled agent runs are not a
calendar kind on main, so the staff scopes include none yet; they join, with
the agent's name as owner, once that kind exists.
`cloudflare-worker/test/calendar_scope_facts_d4154.test.ts` covers it.
