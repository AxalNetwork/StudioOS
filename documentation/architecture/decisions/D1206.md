## D1206 — Calendar read access, provider copying and source errors

2026-10-26 · #3172 · S29, transferred by the owner from S19 · Part of #2420.
No migration, new binding or production data access.

### Built

- Calendar reads and connection operations no longer inherit the broad Investor
  Professional prefix gate. Only `POST /api/calendar/ic-meetings` applies the
  existing Professional guard and its catalogue-backed plan sentence before any
  write. Existing role and deal-party checks remain. The token-authenticated
  my-events feed is available on every plan, as authenticated reads are.
- Full Google/Outlook sync counts Calendly items as skipped. Both provider push
  functions also refuse `calendly_event`, including updates of an existing copy.
  The one-event route already excludes that kind. Existing provider copies
  created by earlier syncs are not deleted automatically; a member removes an
  unwanted old duplicate in their provider calendar. No new deletion act is added. Personal `.ics` downloads
  retain Calendly entries; this change prevents copying back to a provider.
- The advisor reader verifies that a linked advisor belongs to the account,
  then falls back to `advisors.user_id`, matching the advisor router. A stale
  pointer cannot grant another advisor's bookings.
- `sources[].error` is only `unreadable`, `not_configured`, or null. Missing
  tables/columns are unavailable sources, not successful empty reads. A failed
  source retains other loaded sources. Strict feeds/downloads/push lookups
  reject a partial read with a fixed kind/code message. Source diagnostics hold
  kind and outcome only, never raw database text or member identifiers.

### Read-only Studio and All studios

The owner chose existing deployment boundaries in this chat on 2026-10-26.
`GET /api/calendar/events?scope=studio` requires Admin on a branch with a
readable current `branch_licence`. It reads each allowed source once with a bound membership CTE for active
local members; there is no per-member query loop or silent member cap. Shared
events appear once. Personal readers remain unchanged. It uses D1207’s item description and cancelled-page options,
with a Read only role and no source-page actions. Another administrator's private calendar stays Super Admin's.
An HQ Studio request says Not read here yet: HQ records no member-to-licence
association (U1); geography and role never substitute for membership.

`scope=all` requires the hydrated Super Admin elevation on HQ. It reads HQ
items and reports each known remote studio as Not read here yet, from the
licence/deployment register and service-binding inventory. Remote calendar
reading remains explicitly unavailable: there is no calendar RPC, and none is
invented. Failed register reads retain HQ items with Unreadable/Try again.
Remote or source gaps set coverage.complete=false; the API never calls HQ-only
items a complete All studios calendar.

The owner also chose to exclude private Calendly and wellbeing items from
both staff scopes (2026-10-26). They are never queried there; `excluded_kinds`
names this policy separately from source availability. Personal calendars
retain both kinds. Scoped SQL selects no emails, notes, meeting URLs or private
addresses, rather than reading them and relying only on output redaction.

Every scoped item carries read_only=true and false RSVP/reschedule/cancel/copy
capabilities. Contact emails, private meeting links, notes and copied-provider
metadata are removed. Provider push functions and the ICS serializer also
refuse scoped projections. Scoped reads never replace a personal reader: sync,
one-event push, .ics downloads and token subscriptions still resolve only the
signed-in/token member's own events, ignoring scope query parameters. A failed
licence or membership read returns an unavailable scope rather than a fabricated
empty calendar. One failed calendar source retains the sources that loaded.
