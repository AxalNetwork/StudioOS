## D5203 — Calendar reads its sources in bounded parallel and bounds the personal window (#5203)

- **Status:** built (this PR). Part of #3723 (Calendar audit 3/7).
- **Builds on:** D1206 (the staff scope's 180-day window), D1484 (the source registry and `kinds=`), D1485 (Google and Outlook read live, `NoSource`, `truncated`), #4620 / #4622 (the Studio homes' per-source coverage).
- **Why:** `gather()` in `cloudflare-worker/src/services/calendar.ts` awaited each of the 28 readers in turn, so a page read took as long as every source added together. Google and Outlook can each page four times at up to ten seconds a page, and every source #3723 adds made it slower. The personal `GET /api/calendar/events` had no window ceiling, and the Grow launch page asked every source for two years.

### What changed

1. **Bounded parallel reads** (`services/calendar/gatherPool.ts`, `runBounded`). The asked kinds run in two lanes started together:

   | Lane | Kinds | At once |
   |---|---|---|
   | local | every Axal (D1) reader | `CALENDAR_LOCAL_CONCURRENCY` = 6 |
   | network | `NETWORK_KINDS`: `external_google`, `external_microsoft` | `CALENDAR_NETWORK_CONCURRENCY` = 2 |

   At most 8 reads are in flight for one request, never one per source, and a slow provider never holds a D1 source's slot. Each read settles by itself (allSettled semantics; a synchronous throw is caught too). The per-source contract is unchanged: `{ kind, ok, error }` per asked source, partial results kept, `NoSource` omitted, `truncated` kept, provider codes (`reconnect`, `rate_limited`) kept, and the warning names the kind and outcome only. Outcomes are merged in the reader table's order, never in finish order, and the sort by `start_at` is stable, so the answer is the one the serial read gave. Only the kinds asked for are read (`kinds=`); an unknown kind is ignored, as before.

2. **Timing evidence.** Each gather writes one `console.info('[calendar] gather timing', { ms, sources: [{ kind, ms, ok, count }] })`: the whole read's time and each source's, with its outcome and how many items it returned. No title, address, id, email or error text.

3. **The personal window** (`personalWindowRefusal`, `PERSONAL_WINDOW_MAX_DAYS` = 180, the staff scope's own bound). `GET /calendar/events` without a staff scope refuses:
   - an empty, reversed or unparseable window with 400 `invalid_window`;
   - a window wider than 180 days with 400 `window_too_wide` ("Narrow the dates."). It is refused, not quietly narrowed, so a caller never takes a shortened answer for the whole range.

   The page's views fit: Month is at most 31 days, Week 7, Agenda 90 (`calendarViews.windowFor`), and the default window is a day back and 90 ahead. `GET /calendar/events.ics` also refuses an empty or reversed window (`invalid_window`); its default stays 7 days back and 180 ahead, and the subscription feeds are unchanged.

4. **Consumer audit.** Every `listCalendarEvents` call in `frontend/src`:

   | Consumer | Before | Now |
   |---|---|---|
   | `/calendar` (`CalendarPage.jsx`) | its view's window, every shown source | unchanged: it is the calendar |
   | Staff scope (`CalendarScopeView.jsx`) | ≤ 180 days, staff readers | unchanged |
   | Team › Advisors (`FounderTeamPage.jsx`) | 90 days, `advisor_booking,partner_office_hour` | unchanged |
   | Grow › Launch (`FounderGrowLaunch.jsx`) | **two years, every source** | 90 days either side, the launch kinds: `event_hosted`, `event_ticket` and Grow's six (`publish_send`, `content_planned`, `grow_campaign`, `ad_flight`, `newsletter_send`, `sequence_step`) |
   | Advisor Studio Today (`AdvisorStudioHome.jsx`) | default window, every source | `ADVISOR_AGENDA_KINDS` |
   | Investor Studio (`useInvestorSources.js`) | default window, every source | `INVESTOR_AGENDA_KINDS` |

   The two Studio homes already judged coverage by exactly those kinds (`studioAgenda.js`), so they now read what they draw. With an explicit `kinds`, a source the member hid on `/calendar` is still read for that tile, as D1484 part 2 defines for any explicit `kinds`. The Launch page no longer lists project-linked items of other kinds (an investor meeting, a deal closing); it is the launch calendar, and `/calendar` still shows them. Inside the Worker, `readItem` reads one kind over the item's own span and the push lookup one kind; both already passed narrow kinds.

### Tests

- `cloudflare-worker/test/calendar_parallel_gather_d5203.test.ts`: a slow source does not serialize the others; a slow connected calendar does not hold a D1 source; one rejection (async or synchronous) keeps the rest; ordering is the serial order after out-of-order finishes; concurrency is bounded per lane and at 8 over the production table; selected kinds run only their readers; `NoSource`, `truncated` and a provider code survive; the timing carries no payload; the window rules, and the route's 400s on in-memory SQLite.
- `frontend/test/calendar_consumers_d5203.test.mjs`: every `listCalendarEvents` call outside the calendar page and the staff scope passes `kinds`; the Launch window and kinds; the Studio homes' kinds.
- Every new assertion was mutation-checked both ways.
