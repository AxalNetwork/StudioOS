## D8013 — GET-only queue and current-attempt diagnostics (#8013)

The queue audit is an operator diagnostic, not a cancellation service or an
incident controller. It imports the existing D5618 workflow/event/ref eligibility
predicate from Merge Control and the existing queue cutoff/hysteresis functions.
It never invokes an operational reporter or changes alert state, thresholds,
workflows, concurrency, executor admission or provider configuration.

### Inputs and bounds

With Node 22, run:

```sh
node --experimental-strip-types --no-warnings scripts/ci/queue-capacity-audit.mjs --snapshot snapshot.json
node --experimental-strip-types --no-warnings scripts/ci/queue-capacity-audit.mjs --github --run-id 44816080223
```

The first command is offline. The second uses native fetch with only GET requests
to an allowlist on api.github.com, redirects refused. An existing GH_TOKEN or
GITHUB_TOKEN can supply read access; no administrative credential is needed or
requested. The transport projects responses to operational metadata and never
saves tokens, runner identities, actors or raw errors. Unknown CLI options fail;
there is no cancel, dispatch or write mode. Reports go to stdout.

`collectSnapshot` is the read-only API-input port; `auditSnapshot` accepts its
saved result. Each request is keyed by its exact API path and records status,
completeness, observedAt, projected data and pagination continuation. Defaults
are 80 GETs, three pages per list, 20 selected runs, ten seconds per request,
2 MB per response and 20 MB per saved input. Caller-supplied limits have hard
ceilings. Exhausted budgets and incomplete inventories prevent review entries.
Explicit run IDs support completed historical examples; the default selection is
a bounded sample of active runs, not a claim to enumerate every queue candidate.

### Evidence and classifications

Original creation age, current attempt start age and current-attempt job waiting
are separate fields. GitHub provides no authoritative attempt enqueue timestamp
here, so attempt queue wait stays null with a reason. Invalid/future timestamps
stay unknown. Attempt-scoped jobs must match run ID, attempt and candidate SHA;
a second current-run GET prevents an intervening retry from inheriting old proof.

Completed work, main pushes, current main SHA and current PR heads are excluded.
Live exact refs are active candidates; SHA mismatch is a superseded candidate,
not deletion proof. Only a complete, timestamped exact-ref 404 can support a
missing-ref finding, after readable repository/main provenance and D5618
eligibility. A 403, timeout, 5xx, missing page, inconsistent total, ambiguous PR
or contradictory ref inventory never becomes deletion evidence.

The review manifest names exact run ID, attempt, workflow, event, SHA, ref
observation, remaining consumers and the GET paths requiring fresh observation.
Matching live refs, PR heads and other active runs hold a candidate. Other fully
proven missing-ref runs may be reviewed together; their evidence paths are also
included. External/delegated execution authority is deliberately unverified:
root must check that separately against the capacity/executor contracts before
any operational action. Every entry says permissionToCancel=false. A snapshot
can become stale immediately, including when an exact ref reappears.

### Validation and delivery

The focused fixtures exercise reruns, new aggregate jobs, live/mismatched/missing
refs, merged and unreadable PRs, partial pages, attempt changes, consumer holds,
request bounds, credential projection and stale evidence. These fixtures are
synthetic, never live queue evidence. Related Merge Control capacity tests ensure
the imported eligibility policy remains intact. No production code is changed.
