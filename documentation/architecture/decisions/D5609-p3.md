## D5609 part 3 — Keep six Worker parts under equal weights (#5609)

On 27 November 2026, the owner chose option B for both questions in
[the decision on #5609](https://github.com/AxalNetwork/StudioOS/issues/5609#issuecomment-7224630757).
Acceptance measures the part count under equal weights and uses the elapsed
minutes of the slowest Worker part in place of the 15% spread between parts.
These answers supersede the pending acceptance criteria in D5609 and D5609
part 2.

Keep **six Worker parts and two frontend parts**, plus the existing rest part.
`SHARDS` in `scripts/test-drift-parts.mjs` controls those counts. The ordinary
CI suite uses `--plan --equal-weights` and the existing required context
`test:drift (full suite)`. Equal weighting keeps exact-once coverage for the
current file set. It avoids using the older per-file times as a forecast;
D5609 part 2 found that Worker durations moved considerably between snapshots.

**Timing target.** The median of the slowest Worker part per qualifying run
should be **21 minutes or less**. Measure the test-step elapsed time from start
to finish across the six Worker parts of each successful ordinary merge-group
run. Use the latest 12 runs with all six hosted Worker test steps executed and
successful. Record p90 and the sum of the six Worker jobs' elapsed time as
diagnostics. The target is the observed 20.52-minute median rounded up to a
whole minute. Queue time and setup are excluded from the test-step target;
the Worker job total includes setup. Check completion is a separate measure.
