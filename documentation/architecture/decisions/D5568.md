## D5568 — Git repository cache, per-task worktrees and portable checkpoints (#5568)

**Status:** local, host-independent contract over D5565's `WorkspaceSpec`. Unmounted and off: no route, binding, R2 bucket, D1 table, key, GitHub call or Container is added. Every store is an injected port with an in-process fake in tests. Depends on D5565 (spec, eligibility, generation) and D5567 (tenant-bound encryption, region approval). Part of #5568: cloud rollout remains (below).

No task engine, queue, usage ledger or Git server is introduced. `AgentTaskWorkflow`/`AGENT_QUEUE` and D5565's runner protocol stay the authority for runs and generations; this code is called by them.

### Cache and worktree model

- **Git's object model, not a server.** The real fetch is a verified partial/shallow fetch of one exact commit behind the `GitRemote` port. The port has `fetchCommit` only: no push, ref update, ref delete or history rewrite exists to call. GitHub stays canonical; publishing is #5569's trusted publisher.
- **ACL boundary.** The cache key is `git-cache/<provider>/<region>/t<tenant>/r<repo>`. Two tenants using the same repository get two entries and two fetches. The `have` set sent to the remote is the requesting tenant's own entry only. Sharing objects across tenants would need an explicit, verified ACL and encryption design, and none is proposed here.
- **Authorization on every checkout.** `RepoAccess.authorize(tenant, repo)` is asked before the cache is consulted. A revoked repository is refused even when its commit is already cached (mutation M2).
- **Exact base.** Only 40 lowercase hex characters are accepted (`isExactSha`). A branch, tag, `HEAD`, short or uppercase SHA is refused before any fetch.
- **No shared mutable worktree.** Each attempt (`tenant`, `run_id`, `execution_generation`) gets a `Worktree` with its own file map, index (staged set) and branch `workspace/<run>/g<generation>`. The base snapshot is read-only, and every read and write copies bytes. A second checkout of a live worktree id is refused. Writes are limited to the spec's `scope_paths` and D5565's `workspacePath`. Concurrent misses on one key and commit are coalesced into one fetch.
- **Separation.** The executor's transient scratch disk is not captured. A checkpoint carries only tracked changes against `base_sha` (written files and deletions). Large binary artifacts stay on D4557/D5567's artifact sink, and Git tracking stays with Git.

### Checkpoint manifest

The schema is closed and versioned (`CHECKPOINT_SCHEMA_VERSION = 1`, `workspace_version = WORKSPACE_VERSION`) and records `tenant/company/project/run/attempt/execution_generation/sequence/idempotency_token/repo_id`, `base_sha`, `tree_hash`, `artifact_hash`, `image_digest`, `created_at`, `regions { origin, allowed }`, `path_allowlist`, `encryption { AES-256-GCM, tenant key scope, key_id, AAD label }`, one entry per file (path, plaintext SHA-256, size, object key, ciphertext SHA-256), deletions and `previous_manifest_sha256`. That last field chains checkpoints without ever editing one. The validator refuses invalid SHAs, unsorted or duplicate entries, paths outside the allowlist, object keys outside the attempt's own prefix and a wrong `artifact_hash`.

`tree_hash` is a provider-neutral SHA-256 over sorted `path NUL sha256` lines of the whole tree. It is not Git's tree id, so it can be recomputed on any executor without Git.

Object layout: `tenants/<tenant>/workspace-checkpoints/<run>/g<generation>/<token>/{blobs/<ciphertext-sha256>, manifest.json}`. Blobs are sealed with the tenant's key. The AAD binds tenant, run, generation, path and plaintext hash, so a blob moved to another path, run or tenant does not open.

### Consistency model (atomic commit)

1. **Snapshot.** In one pointer transaction, check that the run exists, is not deleted, `spec.execution_generation` equals the pointer's generation, and the worktree is in the run's pinned origin region. Read the current head. A used token with the same tree hash returns the earlier result (`duplicate: true`, no upload). A used token with a different tree is refused (`idempotency_conflict`).
2. **Upload.** Each changed file is sealed, put, read back and hashed. A missing or mismatching read-back refuses the commit (`checksum_mismatch`). A store error refuses it (`checkpoint_upload_interrupted`). The tenant quota is checked as bytes accumulate. The manifest is validated, then put and verified the same way.
3. **Commit point.** One conditional transaction advances the pointer only if the generation is unchanged, the head is the one seen in step 1, and the token is still unused. It records the manifest key, the manifest's SHA-256, the object list and the bytes.

**Interrupted upload.** Anything before step 3 is invisible. Restore reads only the pointer's head and verifies the manifest bytes against the SHA-256 stored in the pointer. A crash during or after the uploads, a pointer-store outage at step 3, a corrupted write or a writer fenced mid-upload all leave the last acknowledged checkpoint in force. Their staged objects are orphans under their own `g<generation>/<token>/` prefix.

**Generation fencing.** `fence()` mirrors D5565's generation bump (reap, cancel, retry) and only ever increases. A writer whose generation was superseded during its upload is refused at step 3 (`stale_generation`, mutation M3). Restore requires the restoring attempt's generation to be current.

**GC fencing.** A plan records the generation and head sequence it saw. `executePlan` re-checks both, and that no key belongs to the head, in a transaction before deleting anything (`stale_gc`, mutation M7). A plan may only name keys under its own tenant/run prefix. Unreferenced staged objects are planned only from generations that are already fenced, so a live writer's staged objects are never collected.

Production must back `CheckpointPointerStore` with one atomic boundary: either the run's DO transaction, or a single D1 row updated with `UPDATE … WHERE tenant_id = ? AND run_id = ? AND generation = ? AND head_sequence = ?` using bound parameters, with zero changed rows read as a refusal. D1's own write ordering and the read-back verification above give the "content before pointer" property. R2 single-object PUTs are atomic, so a reader never sees half an object.

### Restore and portability

`restore()` requires D5565 eligibility (provider allowlist, region, capabilities) and `checkpoint_restore`. The target cache's provider and region must equal the executor and the requested region, which must be in the executor's enforced regions, the spec's allowed regions and the manifest's `regions.allowed`. The manifest's tenant, company, project and run must match, and so must its repository, exact `base_sha` and `image_digest`. The executor starts that image by digest.

The checkout is rebuilt from the exact SHA in the target executor's own tenant-scoped cache. Every blob's ciphertext hash is checked before it reaches the key provider, then decrypted, then its plaintext hash and size are checked. Deletions are applied, and the whole tree hash must match. Any failure releases the worktree and refuses the restore.

Only filesystem state moves. **Running processes, memory, open sockets and local PIDs are not migrated** (`NOT_MIGRATED`, returned on every restore). The task restarts in a fresh sandbox at the acknowledged state. The tests restore on the original fake executor (`cloudflare`) and on an alternate fake (`gcp`), which the acceptance text permits until #5566/#5571 supply real ones.

### Retention, quota, delete, export, region, eviction

| Policy | Rule in code |
|---|---|
| Quota | `tenant_quota_bytes` over all of a tenant's recorded checkpoints, and `max_file_bytes` per file; exceeding either refuses the commit before the pointer moves |
| Retention/TTL | A superseded checkpoint is planned for deletion only when it is beyond `keep_last` **and** older than `ttl_ms`. The head is never planned. Expiring the last checkpoint is an explicit delete, never automatic |
| Delete | `deleteRun` is an explicit tenant request with the expected generation. It fences writers (generation + 1), tombstones the pointer and plans every object under the run prefix. Restore and commit then refuse (`checkpoint_deleted`) |
| Export | The acknowledged head only, same tenant, origin region only. It returns keys, the manifest checksum and egress bytes, so the cost is visible before any transfer. Cross-region export needs D5567's explicit approval and is not offered here |
| Region pinning | The origin region is fixed at `register`. Writes from another region are refused. Restores are limited to the manifest's allowed regions |
| Cache eviction | Only derived mirror entries with no open worktree, by idle TTL and then by tenant byte budget (LRU). Nothing on GitHub is touched, and no customer repository object, ref or history is deleted or rewritten |

Plans are data. `executePlan` deletes only the Axal-owned checkpoint objects it names, after its fence.

### Metrics

`workspaceMetricsReport` reports GitHub push count, clone bytes, cache hits, misses and hit %, disk bytes, disk cost and checkpoint count, total and largest size. It carries counts and bytes only, with no paths, ids or content. The disk rate is an operator input, never a built-in price. `source` is `local_fake_adapter` until real executors report, so a local number is never presented as a hosted measurement. The test computes the report from the fakes. Four tasks and one alternate restore give 3 hits, 2 misses and a 60 % hit rate, with 0 pushes.

### Tests and mutations

The test file covers:

- 10 parallel tasks from one repository: one fetch, ten private worktrees, ten independent checkpoints, each restored correctly on the alternate executor, and the base left unchanged.
- An interrupted workspace (mid-upload crash, then a pointer-store outage) restores the last acknowledged checkpoint on both executors.
- Refusals for:
  - wrong tenant, including a forged pointer row;
  - wrong region, at each of the three region gates;
  - wrong image or base;
  - an invalid SHA;
  - a tampered blob or manifest, and a corrupted upload;
  - a stale generation, including a writer fenced mid-upload;
  - a revoked repository;
  - token reuse;
  - quota;
  - a stale or out-of-scope GC plan;
  - a deleted run.

Nine mutations (M1 to M9, listed in the test header) each fail at least one test.

### Rollback

The modules are unmounted and nothing imports them, so rollback is removing or ignoring the four files and their README rows. No migration, binding, object, key or remote state exists to undo.

After rollout, the rollback order is:

1. Stop admission.
2. Leave pointers and objects in place.
3. Fence the generation so in-flight writers cannot commit.
4. Restore from the last acknowledged head.

Never delete customer repository data and never rewrite history as part of a rollback.

### What remains for cloud rollout

1. **Pointer store.** Use the run's DO transaction, or an additive D1 migration `YYYYMMDDHHMM_5568_workspace_checkpoint_pointers.sql`, with bound-parameter conditional updates. Wire D5565's generation bump to `fence()` in the same transaction boundary.
2. **R2 adapter.** Use a preview bucket and namespace, put with a SHA-256 checksum, read-back verify, prefix list and fenced delete. The broker mediates all access and a runner never gets R2 credentials (D5567).
3. **Key provider.** Use D5567's tenant-scoped AES-GCM keys, with key rotation and retention tied to this retention policy.
4. **Real fetch.** A verified partial/shallow fetch through the GitHub App installation (D5569) on the executor (#5566), with object verification, byte caps and on-disk worktrees (`git worktree` or separate checkouts) that keep these guarantees.
5. **Alternate executor.** Wait for the first external adapter (#5571), which needs owner provider selection, before claiming a real cross-provider restore.
6. **Measured metrics.** Hosted runs report `source: measured`. Stage-gate numbers come from #5573/#4559, never from this local report.
7. **Authorization.** Production flags, buckets, migrations and secrets need separate owner authorization (#5564 stage gate 4).
