### 1. Units, on the stores that are already canonical

Each adapter takes content an existing reader already returned. It opens no second read path and keeps no copy
(D5579 §2).

| Asset kind | Canonical row (`SourceRef`) | Unit | Unit id |
|---|---|---|---|
| `pitch_deck` | `pitch_decks` version (`id`; revision `content_hash`, else `v<version>`), read by `getDeckRow` | one D1577 area of one card: a block by `id`, or the title; everything else on the card is one `__layout` unit | `<card uid>/<area>`, uid from D1500 |
| `legal_template` | `legal_template_versions` (`template_id:version`), read by `legalTemplateStore` | a clause: a heading to the next heading of the same or a higher level; the text before is `__preamble` | the clause number (`7.2`), else a slug; repeats get `-2` |
| `document` | the domain table the caller names (for example `documents`) | a section, cut as a clause | as a clause |
| `offer` | `quote_versions` (`id`; revision `version`) | a term: `price_cents`, `change_summary`, `note` | the column name |
| `legal_signed` | the e-sign envelope (`envelope_uuid`; revision `body_sha256`) | **none**: evidence is never edited | n/a |

A block with no `id` falls into its card's `__layout` unit. So an edit there overlaps any other edit to the card's
layout, and it is never merged field by field.

`unitsDigest(units)` is the SHA-256 of the units' ids and values, in order. It is what a ChangeSet proposes and
what a ReviewDecision approves. Any edit to a unit, or a reordering, changes it, so the old approval is stale
(D5579 `stale_approval`, `unapproved_release`).

### 2. The merge plan (`planMerge(kind, base, ours, theirs)`)

| Situation | Outcome |
|---|---|
| Only one side changed a unit | that side (`ours` / `theirs`, `added_*`, `deleted_*`). Separate slides or clauses never lose an edit |
| Both made the identical change | `same`, taken once |
| Both changed one unit differently | `conflict`. The unit keeps its **base** until a person picks; the plan carries base, ours and theirs |
| One deleted what the other changed | `conflict` (`delete_vs_change`) |
| Both added one id differently | `conflict` (`both_added`) |
| Both changed a text unit, in disjoint lines | `text_merged`, under every condition below |

Text merge is allowed only when **all** of these hold. Otherwise the outcome is a conflict, with the reason named.

- The kind is a deck, a document or a legal template. An offer is never text-merged, and signed evidence is refused
  outright (`immutable_record`).
- All three sides of the unit are `textMergeable`: deck `text` blocks and titles, clauses and sections. A deck
  layout, image, chart, metric or table never is, and neither is any offer term.
- No side is sensitive (§3).
- Each side's line edits, aligned on a longest common subsequence against the base, stay clear of the other's.
  Touching counts as overlap: adjacent lines, or two insertions at one point. The order or meaning of such edits is
  a person's call. A unit longer than 2,000 lines is a conflict (`too_long`).

The merged text needs no second sensitive check. Neither side is sensitive, and the two sides' edits are always
separated by an unchanged base line. Every pattern matches within a line, or across a single newline, so a merge
cannot assemble a sensitive phrase that neither side had.

`chooseVariant(plan, unit, 'base' | 'ours' | 'theirs', by)` resolves a conflict. It is a **person's** act; an
agent gets `not_a_person`. This is the explicit branch and variant selection for incompatible proposals.

`readyForReview(plan)` is true once no conflict is left. Being ready for review still publishes nothing.

### 3. Sensitive terms force a person

These categories force a person's review:

- `money`
- `equity`
- `signature`
- `liability`
- `legal_entity`
- `jurisdiction`
- `investor_claim`

A unit is sensitive by its words, or by its kind:

- a quote's price is always `money`;
- a deck metric, chart or table is always an `investor_claim`.

The patterns err toward review: a false positive costs one look, while a false negative lets a changed price,
party or claim through.

Every changed unit whose old or new text is sensitive is listed in `review`, whatever merged.
`requiresHumanConfirmation` is true when any of these holds:

- the candidate combines both sides;
- it touches a sensitive unit;
- it has a conflict;
- it is a legal template or an offer.

No path in this module auto-merges or auto-publishes a legal instrument. The combined revision is approved by a
person, against its exact digest, through D5579's ReviewDecision.

### 4. Frozen exports

A frozen export (PDF, DOCX, PPTX) is a D5579 ReleaseManifest. It pins the deck version's `unitsDigest` and each
included media version's digest, such as a `deck_images` R2 object. An edit to any unit or any media version
changes a digest, so the earlier approval no longer releases it, and the export needs a renewed approval. Part 2
stores the manifest through #5581, which invalidates dependent approvals on a new head (`impactOf`).
