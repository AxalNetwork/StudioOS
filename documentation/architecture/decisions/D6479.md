The question: does a green PR reach main without the owner touching it
again? The daily scorecard on #5600 gains a `### Landing` table under the CI
table, in the same sticky comment. A row with nothing to count prints
`no data`, never 0.

### 1. The rows and where each comes from

| Row | Source |
| --- | --- |
| Queue entries per merged PR | `entriesPerMergedPr` (D6678) over the PR timelines already read |
| Pushes to main with a green queue run | ci.yml `push` runs on main, against green ci.yml `merge_group` runs on the same SHA |
| How, and who merged, the rest | the PR whose `merged` event names the SHA, else `commits/{sha}/pulls` and its timeline: `queue` when its last entry ended in the merge, `outside the queue` when none did, `direct push` when the commit has no PR |
| Open PRs by mergeable state | `pulls?state=open`, then `pulls/{n}` for up to `mergeableReads` of them, evenly spaced |
| Non-draft PRs open over 24 hours | the open list |
| Owner touches per merged PR | timeline: `added_to_merge_queue` and `removed_from_merge_queue` by a `User` account up to the merge; re-additions are additions after the first entry |
| Conflicted to mergeable | timeline: the `conflict` label (rules.mjs `LABELS.conflict`) from `labeled` to `unlabeled` or the merge |
| Ejection to re-queue or label | timeline: each removal to the next queue addition or `ejected` / `needs-session` / `conflict` label |
| Landing bot runs by kind and outcome | each workflow in rules.mjs's `dispatchable` that exists on main: its runs' conclusions; for model kinds, the jobs (`model run`, `handed back before the model`, `stopped before acting`) |
| Landing bot actions | timelines read: bot commits with a `Landing-Bot-Kind` trailer, `needs-session` labelled by a Bot, queue entries by a Bot |
| Model runs per UTC day by provider | model-kind runs whose edit job ran; the provider from that job's log line (`model/edit.mjs`); the cap is `LANDING_BOT_DAILY_MODEL_RUNS`, passed in by the workflow and read with rules.mjs's `count()` |
| ci.yml jobs started per PR push, draft and ready | ci.yml `pull_request` runs' jobs with a runner; the tier from the `test:drift` job's name |
| Full-suite failures first seen after ready | `test:drift (full suite)` failures on PRs whose timeline shows `ready_for_review` before the run |
| Runner wait per job | every sampled job, pooled (`runnerWait`'s rule) |

### 2. Not visible to the API

- **A bypass of main's ruleset.** Rule-suite history needs administration
  read, which a workflow token cannot hold. Pushes without a green queue run
  are split by how the timeline shows they merged; whether a ruleset was
  bypassed is printed as not visible.
- **A breaker refusal.** The bots write it only to their job summary, which
  REST does not serve. A model-kind run that stopped before acting is counted
  as such, with no reason.
- **Who removed an entry.** REST gives the actor but no reason. A removal by a
  `User` account counts as manual; a session acting through the owner's
  account reads as the owner.

### 3. Cost

`LANDING_BUDGET` is the landing reads' own plan with its own cap (230 GETs,
worst case 217), counted apart from `BUDGET`, whose arithmetic (the comment
always fits) is unchanged. Each capped phase names its cap in the notes when
it stops. The workflow needs no new permission: `actions: read`,
`pull-requests: read`, `contents: read` and `issues: write` cover every
endpoint. It now checks out `merge-control/src/lib` too, because
`scripts/landing-bot/rules.mjs` reads its path rating, and its timeout is 15
minutes.
