## D8073 — Deploy provenance: the served version and one record per deploy (#8073)

**Decision.** A production deploy is traceable from the live site back to its
commit, its Actions run and its build attestation:

- `GET /api/public/version` (`routes/public.ts`) answers
  `{ sha, version_id, built_at, missing }`. Every field comes from the
  bundle's deploy-time bindings, and nothing is read from D1:
  - `sha` comes from `WORKER_DEPLOY_VERSION`, already stamped with
    `GITHUB_SHA`;
  - `version_id` comes from a `[version_metadata]` binding named
    `CF_VERSION_METADATA`;
  - `built_at` comes from `WORKER_BUILT_AT`.

  A field the deploy did not stamp is `null` and named in `missing`, never
  guessed.
- `POST /api/internal/deployments` (`routes/internal_deployments.ts`) writes
  one row to the new `deployments` table
  (`202611211825_8073_deployments.sql`). The row holds the sha, the run id,
  the Worker version id, the attestation URL, `built_at`, `deployed_at` and
  `rollback_of`.
  - No member session. The caller sends
    `Authorization: Bearer <DEPLOY_RECORD_TOKEN>`, compared in constant time.
  - Unset, the route refuses (503). A missing or wrong token gets 401.
  - It is idempotent on `(run_id, worker_version_id)`. A replay answers the
    existing row. A replay that disagrees with it is refused (409), so a run
    cannot rewrite the provenance it recorded.
  - The attestation URL must be one of this repository's
    (`https://github.com/AxalNetwork/StudioOS/attestations/<id>`).
  - `rollback_of` must name a recorded deploy.
- `scripts/deploy/record-deployment.mjs` builds the record from the run's
  environment and posts it once. It reads the Worker version id from
  `WORKER_VERSION_ID`, wrangler's ND-JSON output or the deploy log's
  `Current Version ID:` line. It appends the same line to the run summary.
  Its rules are `scripts/lib/deployProvenance.mjs`. It never prints the token
  or a malformed value, only the variable's name.
- `scripts/check-spa-live.mjs` reads the version on every host. It fails when
  no sha is served, or when the served sha is not `SMOKE_EXPECT_SHA` (set).

**Why a token and not an admin session.** The writer is a workflow, not a
person. The token's GitHub copy is meant for the `production` environment
alone (#8063), so a pull-request run cannot hold it. The deploy job sends no
session cookie, so the CSRF double-submit (`middleware/csrf.ts`) does not apply. The auth inventory
sees the constant-time check as a service gate.

**Not here.**
- The workflow file is #8069's. The attestation step
  (`actions/attest-build-provenance`, pinned), `WORKER_BUILT_AT`,
  `[version_metadata]`, the record step and `SMOKE_EXPECT_SHA` are proposed
  on #8069 as a diff.
- Sigstore for commits and rollback mechanics are out of scope.
- The secret's name is proposed here until #8063 records its environments.

**Rollback.** Revert the PR: the route, the script and the smoke assertion go,
and the `deployments` table stays unread (migrations are forward-only).
Unsetting `DEPLOY_RECORD_TOKEN` alone stops new records.

**Tests.**
- `cloudflare-worker/test/deployments_8073.test.ts` covers the refusals, the
  field validation, one row per deploy, the conflict, the rollback target, and
  the version route with a D1 that throws if touched.
- `scripts/lib/deployProvenance.test.mjs` drives the record, the script (a
  fake environment and a fake fetch: one post per run, the summary line, no
  token in output) and the smoke verdict.
