### 1. The model

- A **skill** is a named, versioned recipe for an AI agent:
  - a description and ordered steps;
  - taxonomy tags (a /studio `skills.slug` at a level: Aware, Working, Proficient, Advanced or Expert);
  - read-only tools (`*.read` only);
  - an output kind (a draft, a record change or a brief).
- **Roles:**
  - Each skill belongs to one or more **agent roles** from `services/agents/catalogue.ts`.
  - An agent can only be given skills of its own role.
  - What a skill produces is a proposal that a named person accepts, like every agent run.
- **Ownership:**
  - Axal curates skills ("From Axal"; written by a Super Admin).
  - A company's editors write or import their own ("[Company]'s skills"), readable only by that company's members.
- **Versions:**
  - Publishing writes an immutable version.
  - An agent pins a version, so editing a skill never changes a running agent. "Update to vN" moves the pin.
  - A retired Axal skill keeps working at its pin and says so.
- **SKILL.md** is the stored and exported format: YAML frontmatter (`name`, `description`, `roles`, `tools`, `output`, `taxonomy`, `version`) and a body of numbered steps.
  - A pasted SKILL.md is untrusted data. It lands as a draft, a write tool is refused, and nothing runs until an editor publishes it.
  - The frontend draws a SKILL.md as text, never as HTML.
- **The agent's radar** sits on the same 8 axes as a person's. Each axis is the highest tag level among the agent's skills, computed by the Worker (A2). With no skills it reads "Not recorded", never zeros.
- **Values** on the agent profile are the dimensions the company set in the role's rule book, on the /studio scale. Each is labelled "Set by [Company]" and never scored.
- **Team coverage** puts people and agents side by side on the 8 axes. An axis covered only by agents still reads as a people gap.

#### The question

An agent has a role, rule books and a cap, but there was no reusable unit of "how to do a job well" that could be given to several agents. There was also no way to read an agent's skills the way a person's are read.

#### What was decided

**The tables (migration 759)**
- **`agent_skills`** holds one row per skill: its `scope` (`hq`, with no company, or `company`), `slug`, `name`, `purpose`, `steps_json`, `allowed_tools_json`, `output_kind` (`draft`, `record_change` or `brief`), `status` (`draft`, `published` or `retired`) and `current_version` (0 until the first publish).
- **`agent_skill_versions`** keeps every published version. Each one stores its **SKILL.md** and its parsed parts. A trigger refuses any UPDATE, so a version an agent pins never changes under it.
- **`agent_skill_tags`** holds the draft's tags: a `skills.slug` of the /studio taxonomy and a seniority level (aware, working, proficient, advanced or expert).
- **`agent_skill_roles`** holds the draft's roles, from `services/agents/catalogue.ts`. An agent is only given skills of its own role.
- **`agent_skill_links`** records which agent uses which skill, and at which version.

**The gates**
- **Read:**
  - an HQ skill, by every member;
  - a company skill, by that company's members and HQ's admins;
  - a draft, only by those who may write it.
  - A reader sees the published version, never unpublished edits.
- **Write:**
  - an HQ skill, by a Super Admin only (`isSuperAdmin`; an admin without elevation is refused);
  - a company skill, by its editors (`canEdit`).
- **An agent's skills:** changed by its company's or project's managers (`services/agents/teams.ts`'s `canManage`, called, never copied).

**Attaching.** A skill may be given to an agent only when all of these hold:
- it is published;
- it is readable from the agent's company: HQ always, and a company skill only for that company's agents and its projects' agents;
- the version is of the agent's role;
- its tools are a subset of the agent's `tool_grants_json`.

Otherwise the request is refused with 409 `skill_not_attachable` and a sentence per skill (or per agent, for assign), and nothing is written. Example: "Needs the hubspot.read_deals tool, which this agent's sponsor hasn't approved." Assigning one skill to several agents is all or nothing. A retired skill stays at the version it is pinned to, but cannot be added again.

**SKILL.md**
- Each version is written as Markdown with YAML frontmatter (`name`, `description`, `version`, `output`, `roles`, `tools`, `taxonomy`), then the steps as an ordered list.
- A pasted SKILL.md (`POST /skills` with `skill_md`) is untrusted data. `parseSkillMd` is a strict reader of exactly those keys: double-quoted or plain scalars and flat lists, with no YAML tags, anchors or other features. Unknown keys are ignored.
- The result goes through the same `checkDraft` as a typed skill and lands as a draft. Nothing runs until an editor publishes it.

**The radar.** `skillsRadar` gives the agent's profile on the 8 /studio axes, on a person's 0–5 scale (aware = 1 … expert = 5).
- Each axis takes the highest level any attached skill tags in its category.
- An axis with no tag is `{ available: false, reason: 'Not recorded' }`, never 0.

**Not in part A**
- The run path (part D, #3954) puts a skill's instructions and its tool allow-list into the agent's turn, checks the tools again at run time, and records the skill and version on usage rows.
- The skill change itself is recorded on the link row (`linked_by`, `linked_at`). `team_agent_events.kind` has a CHECK without a skills value, and widening it means rebuilding that table, which is left to part D if it needs the event.

### Part A2 — an agent's skills, assigning, the radar and coverage (#3956)

Built 2026-11-01 by Claude Code for slot S29. No migration: `agent_skill_links` is migration 759's (A1). The tool grants are an agent's `tool_grants_json`, which #3844 (D1496 part 5) now fills with the sponsor's approved read tools.

**One gate.** `services/agents/skillLinks.ts`'s `attachCheck` is the only answer to "may this agent have this version". The agent routes, assign and the add-agent route all call it. In order:
1. `not_found` (404): the skill is another company's, or unreadable to the caller.
2. `version_not_published` (422): the version was never published. A draft has no version.
3. `skill_retired` (409): a retired skill is never added again. An agent that already has it keeps it at its pinned version, so a PUT that keeps it passes.
4. `role_mismatch` (422): the published version does not list the agent's role.
5. `tool_not_approved` (422, with `tool: { key, label }`): a tool the skill uses is not in the agent's grants.

Changing an agent's skills by anyone but the scope's managers is 403 `not_manager`.

**A2 replaces A1's agent shapes.** A1's `GET`/`PUT /agents/:uid/skills` and `assign` were rewritten to the shapes the Skills screens (part C, #3952) were built against. A1's tests 3 to 6 now follow them.
- **Fields renamed.** `version` and `latest_version` are now `pinned_version` and `current_version`.
- **The radar.** It is `{ axes: [{ slug, label, level }] } | null`: an axis no tag reaches is `null`, and an agent with no skills has `radar: null` (the screen says "Not recorded"), never zeros.
- **Refusal codes.** Refusals carry A2's codes instead of A1's 409 `skill_not_attachable`.
- **Assign is partial.** It answers `{ added, refused: [{ agent_uid, code }] }`, and one agent never refuses the whole call. It pins the current published version. An agent that already has the skill is left as it is.

**New reads.**
- `GET /agents/:uid/skills/available`: the agent's role's published skills from HQ and its company, most used first. Each is a library card with `assigned`, `pinned_version` and `blocked`. Only a missing tool is shown as blocked; other roles' skills are not offered.
- `GET /skills/:uid/agents`: the agents using a skill that the caller can read (never another company's), each with `{ kind, company_name, project_name }`.
- `GET /skills/:uid/assignable`: the agents of the current version's roles that the caller manages, each with `skill_count`, `assigned` and `blocked`. A company skill lists only agents inside its company. With a company chosen in the switcher (`X-Company-Id`, `activeCompanyFor`), only that company's agents and those on a project with no company are listed, as every founder-ownership read narrows (`projectInActiveCompany`).
- `GET /:scope/:id/coverage`: per axis, `people_level` and `agent_level`.
  - `people_level` is the highest `user_skills.self_level` among the team's people: a company's `user_company_links`, a project's founder and accepted `project_members`. A self-rating of 0 is no level.
  - `agent_level` is the highest level among the scope's own live agents' pinned versions.
  - The screen marks `people_level == null && agent_level != null` as a people gap.

**Add an agent with skills.** `POST /:scope/:id/agents` takes an optional `skills: [{ uid, version? }]`, checked with the same gate against the new agent's role and grants before anything is written. A refused skill adds no agent.

**Values: not set yet.** `values` is always `null`. Rule books (D1496) have no values section, and the /studio value spectrums run −2 to +2, not the 1 to 5 the spec names. Giving rule books a values section, and choosing its scale, is a rule-book change for the owner to decide (raised on #3956). Until then no value is invented or scored from behaviour.

**Client.** `teamAgentsApi.agentSkills`, `setAgentSkills`, `availableSkills`, `skillAgents`, `assignable`, `assignSkill` and `coverage` (`lib/api/teamAgents.js`). The adapter's seven A2 bodies now call them through `throughSkill`. A1's six library bodies stay unavailable: their adapter shapes (`/:scope/:id/skills`) differ from the merged A1 routes (`/skills?company=`), which is part C's to reconcile.
