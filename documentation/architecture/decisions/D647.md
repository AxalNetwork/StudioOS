of ten characters and fresh sign-in remain intact. The canvas's claim that a

### Reads and dates

The four-source union validates limit (1–500), offset (0–1,000,000), search
(200 characters), sorting, direction and filters. Sorting precedes paging;
missing values stay last and source/id/uid break ties. Viewed stays Awaiting
signature; rejected stays Voided. The desk requests 25 rows and preserves
filters in its URL. NDA/deal tabs return counted pages without a 500-row cut.
The template catalogue is read completely, then searched/paged locally.

`recorded=true` opts the new desk into actual send events: native `email_sent`,
successful resends, or the successful DocuSign creation audit. Missing send times stay missing.
Average days to sign uses those dates, not creation time. Synthetic NDA/deal
updated_at values are not asserted to be signature dates. Legacy callers retain
the creation-based metric unless they opt in. The union is still loaded in
memory; concurrent writes can change page totals between requests.

Failed reads show Unreadable with Try again; successful empty reads are empty;
missing fields show Not recorded with a reason. Strict catalogue usage refuses
to invent zero when a union source fails. Recipient/deal searches are counted,
paged and literal; plain admins cannot choose other admin accounts.

### Published template versions — migration 434

The new canvas explicitly says Publish chooses the versions New envelope
will offer. Reserved migration 434 records an approved template snapshot rather
than treating an active draft or published document type as a published template
(option A from the earlier issue question). No existing draft is backfilled as
published. This is an implementation choice from the supplied specification,
not a claim that the owner replied to the earlier lettered question.

A publication batch snapshots usable active templates and its actor audit
atomically. Archiving withdraws templates from new sends; existing envelopes
retain their copies. Editing leaves the approved body unchanged until Publish.
The existing branch-only publish route remains compatible; the new publication
route also fans out the recorded catalogue and reports each branch's outcome.
It never claims that an unanswered branch received the publication.

The guided panel uses only recorded snapshots, shows one input per actual body
token, resolves recipient identity on the server from email, and links a selected
deal. Recipient/effective-date fields and recorded recipient public IDs are automatic;
unrecorded required IDs refuse sending. Remaining tokens, including literal dotted
tokens, require input rather than invented identifiers. Provider
availability uses the canonical Studio gate (admins have its existing bypass)
and the sender's actual DocuSign connection.

Preview and send prepare the same approved snapshot. Send verifies both its
published version and preview body fingerprint before writing. Changing fields
or the effective date invalidates the preview. The snapshot approved at this
check is used even if another publication commits while the send finishes.
Signing URLs are omitted from the admin response. Send requests record the actor,
version and body fingerprint without recipient details. A committed envelope
whose invitation fails is reported as created with failed delivery; ambiguous
send failures instruct the admin to check Agreements before retrying.

### Detail and PDF

The detail panel projects named recipient/audit fields, never signing tokens
or legacy audit metadata containing signing links. Another admin's envelope
history/PDF requires Super Admin authority. Historical stores without envelope
parties/events say why those details are not recorded. Void keeps the existing
five-character reason floor and factor/step-up requirements.

Signed-PDF SHA-256 is calculated from the exact downloaded PDF bytes, after
DocuSign artifact decryption when required; it is not a document-body hash or
R2 ETag. Missing artifacts are Not recorded; failed reads/decryption are
Unreadable. Downloads use an authenticated, no-store response, with a 10 MiB
artifact ceiling. Neither migration nor production data is changed by this
implementation session; deployment must apply migration 434 first.
