## D4622 — Studio independent reads, layout half, part 1 (#4622)

### Decision

The Studio's two layout reads, the module catalogue (`GET /api/studio/modules`)
and the saved layout (`GET /api/studio/layout`), start together and settle
separately. Each has its own retry. This is the layout half of #4622. The role
homes, the founder's project reads, the shared progress and queue owner and
the lazy role loading are not part of this change.

1. **Each read commits when it settles.**
   - Before, `useStudioLayout` waited on `Promise.allSettled` for both, so the
     saved layout, which is all the grid needs, was held for the catalogue.
   - Now `layoutRead` is `ready` as soon as the layout answers. A tile whose
     module the catalogue has not named yet draws its fallback title.
   - The catalogue answering first does not wait for the layout either.
   - Customise stays unavailable until the catalogue is ready, because it
     needs the module list to add from.
2. **Each read retries alone.**
   - `reload` (the layout's Try again and Reload layout) re-reads the layout
     only. `reloadModules` re-reads the catalogue only.
   - A catalogue retry is not a layout reload, so it does not end a save or
     reset in flight (D4621's generation is bumped by the layout read only).
3. **A failed catalogue has its own notice.**
   - Before, it had none: Customise just disappeared.
   - `studio-notice-modules` says the module list could not be read and offers
     Try again. The layout above it stays as read.
4. **A late answer is dropped by each read**, whichever profile or retry it
   began under, as before.

### Measured

Both reads were already started together, so the request count is unchanged
(one each, per profile, per retry). What changes is when the first tile can
draw: before, at the later of the two answers; now, at the layout's answer. The
tests assert this order with deferred responses. No production timing was
taken, and none is claimed.

### Tests

`frontend/test/studio_independent_reads_4622.test.mjs`: one request each, the
layout drawing before the catalogue, the catalogue first, a failed catalogue
keeping the layout, each retry reading only its own source, a catalogue retry
leaving a save alone, late answers after a profile change, and the two
notices. Each guarded line was mutated, and each mutation fails a test.

### Part 2: the founder and investor reads, the shared advisor reads, and the role homes (#4622)

#4620's source-status contract (#5004) is on `main`, so the rest of #4622 could be built.
It covers scope items 1 to 3 and 5. Item 6 (admin overview de-duplication) needed no change.

1. **The founder Studio commits each read as it settles.**
   - `FounderStudioHome` read projects, the Lab, advisor progress and the advisor queue together, started the
     venture's lifecycle and scores only after all four, and committed nothing until the last. A slow advisor
     read held every zone on its loading state.
   - `founderStudioReads.js` starts the four together and hands each to the page the moment it settles. The
     venture is resolved from the projects read alone, and its lifecycle and scores start at once. A failure is
     that zone's own `failedRead`; no venture, or a failed projects read, settles the dependent zones as before.
   - A run a newer one has superseded (a project change, a retry) is dropped, as before.
2. **The investor Studio reads its two sources apart.**
   - Portfolio and calendar were committed only after both settled, and one retry asked for both.
     `useInvestorSources` reads, commits and retries each on its own, drops a read a newer one has superseded,
     and keeps the source that answered on the page when the other fails.
   - Retry asks again only for what failed, and for the calendar when it answered but a relevant source inside it
     did not (a partial answer has no entry in `failures`). An admin previewing reads nothing.
3. **One owner for the shared advisor reads.**
   - The founder home, its interview wrapper, the profile card and the chat each asked for `/advisor/progress`
     (and the queue) on their own. `api.advisor.progress` and `api.advisor.queue` now go through `sharedRead` in
     `api.js`, the request facility every page already uses: callers that ask while an identical read is in
     flight share it.
   - Nothing is kept once it settles, so a retry, or a read after the member answered a question, is never served
     a stale copy; a failure is never remembered. The key carries the identity the request is sent with (token,
     impersonation header, company) and, for the queue, its focus, so another member, another company or another
     queue never shares a read. That is the "explicit invalidation and retry": there is nothing to invalidate.
4. **A founder's own Studio does not wait for the dashboard.**
   - Nothing on the founder path uses the broad `/dashboard` payload, only the user. A founder on their own
     Studio now mounts the founder home at once, from the session's user, and the dashboard is not asked for.
   - Everyone else reads it as before: an investor, advisor or partner, an admin previewing a role, an admin
     impersonating, an exploring member admitted to the Lab. The condition is the session user being a founder
     while the Studio is the founder's (`ownFounder`); an admin previewing the founder Studio is not one.
5. **The five homes load lazily.** `Dashboard.jsx` imported all five homes statically. `StudioHomesLazy.jsx`
   wraps each in its own lazy boundary with a skeleton, with the same names and props, so a view fetches only the
   home it draws. A chunk that fails to load is recovered by the route's error boundary and `vite:preloadError`,
   as for the Product testing section (D4574). #4474 keeps the embedding seam: no props or default exports
   changed.

- **Requests.** One founder Studio mount asks for advisor progress from up to four places (the founder reads,

  (`studio_independent_reads_4622b.test.mjs` counts it).
- **When a zone can first draw**, with fixed delays (projects, Lab, lifecycle, scores 30 ms; advisor and queue
  400 ms), `frontend/test/baseline_studio_reads_4622.test.mjs`, run with

  | --- | ---: | ---: |
  | Lab, venture | 431 | 31 |
  | lifecycle, scores | 431 | 61 |
  | advisor, queue | 431 | 401 |

  Before, every zone drew when the slowest read ended. The test asserts the order, not the milliseconds.

  | file | before | after |

**Not done here:**
- Retry of the founder's cycle module reads and the advisor-progress consumers inside `PersonalAdvisor` are
  untouched; the latter shares the request through `api.advisor.progress` without any change to the chat.
- #4619's founder project-context scoping (stored result and in-flight key including the project) is still its
  own issue. The founder reads here keep their existing per-run guard.
