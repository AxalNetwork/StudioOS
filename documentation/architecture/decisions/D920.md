## D920 — The Events desk Overview

Issue #2703, part 5 of #2368. Frontend only; no migration. Dependencies D915,
D916 and D918 are merged. The source is the owner's Events Console canvas,
EV1/EV2, EV12, EV13a, EV14, EV15a/b and EV17a.

### Reads and period

The 4, 12 and 52 week radio group calls `adminEvents.overview(weeks)`. Each
D918 block keeps its own ready/loading/unreadable/unrecorded state. Changing
the period immediately hides the old period; a late response cannot replace
the selected period. Refresh preserves the current period's last successful
answer while re-reading. The header timestamp includes the overview.

The Overview no longer reads the capped analytics endpoint. D918 has no
Next-up rows, so that card uses the already paged, enriched events list,
sorted by start time, limited to five published/waiting events. Next 30 days,
queue and status counts retain D918's fixed/all-time meanings; the period
controls its period-based blocks. No new API route or client is added.

### What is shown

Eight tiles show the queue (including legacy creation-time fallback and
Overdue past 72 hours), upcoming events, registrations and their previous
period delta, show-up, waitlists, paid tickets, free seats and cancellations.
Paid currencies stay on separate lines. Unknown amounts remain unknown;
pending payments keep their own failure state. Cancellations say they are
counted by event start date. No previous-period delta is invented for blocks
whose read has none.

Weekly registrations/check-ins reuse the shared multi-series `WeekLines`,
which breaks at null values and draws only the API-marked current point hollow.
Missing type counts keep their Not recorded label without breaking neighboring
bars; missing ended-event rows are unreadable rather than an empty period. The table
keeps real zeros, missing values and “so far”. Its sentence comes from the
registration comparison and the independently read show-up block.

Needs attention draws at most six items with their event/calendar links and
the API's total. Overdue opens the Review queue (the existing review tab has
no event-selection URL); Browse all events opens the complete list rather
than D919's narrower attention filter. Recurring show-up titles use event
IDs as chart keys. Next up draws type, format, date, status and recorded seat
counts. Events by type uses the canonical twelve types and hides zero rows
until Show all. Show-up draws the last eight ended events against the
period's reference rate. `HBars` gains optional fixed scale/reference props;
its existing callers keep their existing behavior and palette.

Who comes uses D915's profile order; explorers, guests and admins form Other.
Unknown roles remain a separate recorded count and are excluded from the
recorded-profile bar. Seat sources stay signed-up, invitation and free-seat;
Added by an admin remains Not recorded. Page views and Feedback use D918's
explicit no-store reasons. Empty and failed reads never become zero values.

### Verification

`events_overview_d920.test.mjs` covers block states and failure isolation,
zero/missing distinctions, periods and racing reads, currencies, attention
limits, action targets, chart/table parity, type disclosure, missing-week
gaps and the reference scale. Existing desk assertions now use D918 for the
Overview while retaining Guard G checks on the other tabs. New assertions
are mutation-checked; results and full-suite status are recorded on the PR.

The shared charts were already moved to `ui/Charts.jsx` by D929; this change
reuses them and their one palette, without another chart library or tokens.
Only the frontend build ships. Revert this PR to restore the prior overview.
