## D4189 — Deck feature flags with a reason, an audit row, names not ids, and only the deck keys a route reads (#4189)

- **Status:** built by S10, 2026-11-02 (#4189, K2 of #4155).
- **Number:** D4189 is this issue's number (D4106). The HQ › Decks decision is D4155, which S21's PR carries. This file records K2 under it, so no file another open PR owns is edited.
- **Builds on:** D1509 (#3760, the Grid's feature flags: `feature_flags`, migration 723, `services/featureFlags.ts`, `routes/admin_feature_flags.ts`); D159 (`logAdminAction`).

### What was decided

- **A write says why.** `PUT /api/admin/feature-flags` takes a `reason` of 10 to 500 characters, else 400 `reason_required`. It is checked after the key, scope, scope id and value, so those keep their own codes, and nothing is written without it.
- **One audit row per write.** The route calls `logAdminAction` (`feature_flag_set`) with the key, the scope, the scope id, the value **before** (read before the write; `null` when no row existed) and **after** (`null` for back to the default), and the reason. That writes both `activity_logs` and `admin_audit_log`. A user-scope row names its member as the audit target (`target_user_id`), so HQ's governance feed shows whom it touched. The admin is recorded by id, as every admin audit row is, and the feed names them.
- **The read names people.** `GET` answers:
  - `updated_by: { uid, name } | null`, never the bare id it used to return and never an email;
  - `affected` for each row: the active members its scope reaches (everyone, the role, or the one member). It is `null` when it cannot be counted.
  - `labels`: the deck keys' plain-language label and description.
- **Only keys a route reads.** `DECK_FEATURES` in `services/featureFlags.ts` lists three keys, each gated in the same change:
  - `deck:rehearsal`: `POST /api/decks/:id/rehearsals/quote` and `POST …/rehearsals` (`deck_rehearsals.ts`);
  - `deck:pptx_import`: the deck upload in `imports.ts`, for a `.pptx` only, before any import row; a PDF is not affected;
  - `deck:logo_wall`: `POST /api/decks/:id/logos` (`deck_venture_elements.ts`). Logos already on slides stay.

  A switched-off key answers 404 `not_switched_on`, "Not switched on yet.", the D1509 shape. `keyShape` accepts `deck:<lowercase>`, and `knownKeys()` refuses any deck key not in the list.
- **Not listed yet.** The canvas also names `deck:compare` (multi-model compare), `deck:walkthrough` and `deck:stock_photos`. None has a route on main, so each joins `DECK_FEATURES` in the PR that builds its feature ("No flag that switches nothing").
- **The beta column** still answers for `grid_generate` and `element:*` only. Whether it answers for the deck keys is K3's (#4190).
- **The screens.** `frontend/src/pages/hq/decks/` (`BUILD.K2.live`) and `lib/api/adminFeatureFlags.js` arrive with S21's HQ › Decks PR. The write method and the switch-on follow there, or in a follow-up on this issue once that PR has merged. No client method is added here for a screen that is not on main.
