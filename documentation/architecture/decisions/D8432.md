## D8432 — The landing list holds back a green PR whose merge with its base would not be green (#8432)

On 2026-11-24 #8015 was queued twice and failed the merge queue twice, and every candidate built on it failed
with it (D8416). The PR was green and `main` was green. Their merge gave one job the key `permissions` twice,
and git reported no conflict. D8416 made that failure name its file and stop the queue run in its first minute.
This decision puts the warning where the queueing is decided.

### Decision

The owner's landing list (D6469) asks one more question of each green PR: what would merging its head into its
base break? `scripts/lib/queueSkew.mjs` answers from the tree `git merge-tree` writes, without checking anything
out:

| Answer | Meaning | In the list |
| --- | --- | --- |
| `clean` | It merges, and the merged tree has no problem the base does not already have. | As before. |
| `conflict` | It does not merge without a conflict. | Held. |
| `breaks` | It merges, and a workflow file in the merged tree gives a key twice. | Held, with `path:line:column` and the key. |
| `not checked` | git could not answer, or nobody asked. | As before. |

A held PR leaves both queue lists and appears under **Do not queue: merge the base in first**, with its reason.

- **Advisory.** The list still never labels, merges or queues. The credential guard in the queue is the
  authority; this only stops a PR being queued into it.
- **No new workflow, permission or dependency.** The list's job has no install step, so the duplicate-key check
  is a line scanner for block mappings, not a YAML parser. Its test compares it with the real parser on every
  workflow file in the repository and on each file with one line doubled.
- **Data only.** The PR head is fetched and read as objects. Nothing from it is checked out or run, and the
  answer is given only when the fetched commit is the head GitHub named. Text taken from the PR is escaped and
  bounded before it reaches the issue body.
- **Only new problems.** A key already given twice on the base is the base's to fix and would otherwise mark
  every PR. Only workflow files that differ between the base and the merged tree are read.
- **The check never holds up the list.** Any git failure, a moved head or a thrown error answers `not checked`.

### What it found on the day it was written

- #8015's head against `main`: `breaks`, at `.github/workflows/codeql.yml:119:5` and
  `.github/workflows/semgrep.yml:118:5`, the two places the queue failed on.
- The live list (31 green PRs): three held as conflicts, #7865, #8201 and #7970. GitHub's own answer for each is
  `mergeable: false`. The list had printed `mergeable: unknown` for all 31, because GitHub had not computed it
  when the list read it.
- Run time from a full local clone: 130 seconds with the check, 103 without.

### Not decided here

Two other things a clean merge can break are two migrations with one identity and two decisions with one
number (D5398, D4106). `mergeSkew` reads the merged tree, so each can be added as a further check on it.

### Verification

- `node --test scripts/lib/queueSkew.test.mjs scripts/lib/landingList.test.mjs`: 19 pass. The git cases run real
  git in a temporary repository with a local `origin`.
- The scanner and the real parser agree on all 9,581 one-line-doubled variants of the 71 workflow files (5,304
  with a duplicate key), and on 343 workflow files across five revisions.
- 25 mutations, 25 caught. Three more were equivalent; two of their lines were removed and one is an early exit.
- One defect found by the tests before publication: git exits 1 for a commit it cannot find, which is also its
  exit for a conflict. `mergeSkew` now requires the tree git wrote before it says `conflict`.
  `mergeTree` in `scripts/pr-overlap.mjs` reads the exit the same way and is not changed here.
