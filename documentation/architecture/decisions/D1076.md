## D1076 — Trust center part 4: on `/status`, days before records began are Not recorded, and an unmeasured figure is never called uptime

- **Status:** decided and built by S09, 2026-10-25 (#2968, part 4 of #2425, from S21's integration D1072 in #2925).
- **Owner question 7:** read as A (D1072 §5). No percentage of uptime is shown until measured checks exist.
- **Migration:** none.
- **Scope:** the Worker's status read and `/status`. The trust center's status tile (TRU1's strip in `pages/site/TrustCenter.jsx`) belongs to #2925, which has not merged. It reads the same fields when it lands, so this PR is `Part of #2425` and leaves that tile alone.

### 1. Why (the trust map's finding 11)

`GET /api/public/status` drew a 90-day history per service. It marked every day "operational" unless an incident named it, and turned that into `uptime_pct`. The page printed it as "99.98% uptime · 90 days".

Nothing measures uptime:
- the history is built from `status_incidents` alone;
- and nothing in the product enters an incident. `POST /api/public/status/incidents` has no caller (D202, `routes/admin_platform.ts`).

So every day read as a good day, including days before anyone could have recorded one. A 100% figure was arithmetic on an empty table.

### 2. The read (`routes/public.ts`)

- **`STATUS_RECORDS_SINCE`** is the day incident records began: `2026-10-25`. `recordsSinceOf(name)` gives a service's own date, and a service can override it. None does today.
- **Each history cell** is one of:

| Cell | When |
|---|---|
| `not_recorded` | a day before the service's records began |
| `no_incident` | a recorded day with no incident ("No incident reported", never "operational") |
| `degraded`, `down` | a day an incident covers, as before |
| `unknown` | every day of a row that is not monitored, as before |

  An incident paints its days even before records began, because an incident entered for a day is a record of that day.
- **`uptime_pct` is gone.** Each monitored row carries `records_since`, `days_recorded` (the window's days from then on) and `days_without_incident`. A row that is not monitored carries null for all three.
- **The live state is unchanged:** each row's `status`, and the overall roll-up (`lib/statusOverall.js`), still come from the probes.

### 3. The page (`StatusPage.jsx`)

- Each row reads "11 days of 11 days with no incident reported · records began on 2026-10-25".
- A service whose records have not begun reads "Not recorded yet: records begin on …". A row that is not monitored reads "Not monitored: no history is kept".
- The strip is the "90-day incident history". A Not recorded day is drawn as a dashed empty cell, never green. Each cell's title says the day's words.
- The services note says a day with no incident reported is not a measured check.
- The page, its meta description and the open-graph description (`lib/ogRegistry.js`) no longer say "uptime". No percentage is printed anywhere on the page.
- The words live in `lib/statusHistory.js` (`DAY_WORDS`, `recordLine`). A missing count is no line, never a zero.

### 4. UNVERIFIED until the owner's live check

- **The date.** `2026-10-25` is this decision's day, not a measured one. The clone is shallow, so git cannot date when `status_incidents` reached production. As of D202, the table held 0 rows and had no writer in the product.
  - If incidents were kept before this day, the owner moves `STATUS_RECORDS_SINCE` back (one line in `routes/public.ts`), and the window fills in.
  - Until someone enters incidents, "no incident reported" means none was entered, which is what the page now says.
- **The live page.** `/status` on `axal.vc` should show the dashed Not recorded days before 2026-10-25 and the count line, with no percentage.
