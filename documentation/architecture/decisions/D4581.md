## D4581 — /login no longer hangs on "Signing you out…": a /me sent before a sign-out is dropped (#4581)

- **Status:** built by S32, 2026-11-09 (#4581, Grow audit, verification task 2 of 3). Reproduced in a browser against a local build, not on production (this session cannot reach axal.vc). Not merged, deployed or live verified.
- **Code:** `frontend/src/hooks/useAuthSync.jsx` (`AuthProvider`: the session generation, checked by `refresh`).
- **Tests:** `frontend/test/auth_signout_race_4581.test.mjs`.

### What happened

`AuthScreen` (`App.jsx`, the wrapper for `/login` and `/register`) signs a still-signed-in visitor out, once, on arrival. It calls `clearSession()`, which does three things:
- sets the user to null at once;
- removes the cached user;
- revokes the server session in the background (up to 5 s).

While a user is present, `AuthScreen` draws "Signing you out of your previous session…".

`AuthProvider.refresh()` re-reads `GET /api/auth/me` on route changes. When a visitor arrived on a page (here `/grow`) and moved to `/login` before that `/me` answered, the answer came back with the session cookie still valid. `refresh()` then wrote the old account back, into state and into `localStorage`. `AuthScreen` saw a user again, but its teardown runs once, so it drew the message for good. A reload cleared it, because the server logout had landed by then.

### Reproduction

The built SPA was served locally, in Chromium (Playwright), with every `/api/*` intercepted and `/api/auth/me` held for 1.5 s. A signed-in user was cached.

| Scenario | `main` (d295bd8) | This change |
|---|---|---|
| direct `/login`, desktop 1280×900 | the form | the form |
| direct `/login`, resized to 390×844 | the form | the form |
| `/grow` → `/login` (client-side), desktop | **stuck on "Signing you out…"**; old user cached again | the form; nothing cached |
| `/grow` → `/login`, resized to 390×844 | **stuck**; old user cached again | the form; nothing cached |

**The viewport is incidental.** The trigger is the `/me` that the earlier page sent still being in flight. A direct `/login` sends none, since the teardown runs before the provider's effect. The audit's resize likely coincided with the slow `/me`.

### The fix

`AuthProvider` keeps a session generation.
- These move it on: `setUser(null)`, `setUser` with another account's id, the cross-tab `storage` event, and `refresh()`'s own identity change.
- `refresh()` records the generation when it sends `/me`, and drops the answer if the generation moved while it was in flight.
- A `/me` sent after the sign-out, or after a new sign-in, is unaffected.
- When nothing changed, a refresh of the cached user is unchanged.

No authentication safeguard changes: the teardown, the server logout and the 401 handling are as they were.

### Coordination

The file is shared with #4579 (S30) and #4580 (S31). The change is confined to `AuthProvider`'s `setUser`, `refresh` and `storage` handler. `App.jsx`'s `AuthScreen` and `clearSession` are untouched.
