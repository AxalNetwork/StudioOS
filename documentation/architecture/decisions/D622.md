## D622 — HQ · Contracts shows a pending revision, and publishes only the one the Super Admin reviewed

**Issue:** #1343. Follows D615 (#1313, PR #1335). **No migration.**

### The gap D615 left

D615 made a save on a published doc type go to the pending `draft_*`
columns, leaving the live values alone. Two things followed from that:

- **No screen showed the pending copy or published it.** An HQ admin who
  edited a published type saw the edit vanish, and nobody could make it
  live.
- **Publish applied whatever was pending when it ran.** A save that landed
  after the Super Admin had read the draft went live under a reason written
  for something else.

### What was decided

1. **Publish names the revision it reviewed.**
   `POST /api/admin/contracts/registry/:doc_type/publish` takes
   `reviewed_draft_at`, the pending revision's `draft_updated_at` as the
   reviewer read it.
   - A newer save gets a 409 `draft_changed` with a sentence, and nothing
     changes.
   - If a revision is pending and the publish names none, it gets a 400
     `reviewed_draft_required`.
   - With nothing pending, publish works as before.
   - The UPDATE is guarded with `AND draft_updated_at IS <the stamp read>`.
     A save that lands between the publish's read and its write therefore
     matches no row, and is refused the same way.
2. **The stamp has millisecond resolution.** `upsertDraft` writes
   `strftime('%Y-%m-%d %H:%M:%f', 'now')` instead of `CURRENT_TIMESTAMP`.
   That clause sits outside "publish only", but it is needed: with
   one-second resolution, two saves in the same second share a stamp, and
   the second would pass as reviewed. Two saves in the same millisecond
   could still collide; that window is accepted.
3. **The hub names who saved the pending revision.** `pending_draft` gains
   `updated_by` and `updated_by_name`, read from `users` by
   `draft_updated_by`.
4. **The ContractsPage card** of a published type with a pending revision:
   - says it is pending and not live, who saved it and when;
   - shows live against pending for title, layer, party roles and required
     fields, with changed fields marked;
   - gives a **Super Admin** (`isSuperAdminUser`, the route's own gate) a
     reason box with the route's 10-character floor and a publish button,
     which sends the `updated_at` shown on the card;
   - tells **any other admin** that the revision goes live only when a Super
     Admin reviews and publishes it.

   Each refusal reads as a sentence: a short reason, a newer save (and the
   card re-reads the hub to show the newer copy), a lapsed step-up, a missing
   reviewed stamp, a type that is gone.
5. **The publish audit records what went live.** `registry.type.publish`
   now carries `applied` (title, layer, party roles, required fields) and
   `reviewed_draft_at`, beside the reason. It used to record the code
   catalog's title, which was not necessarily the one that went live.

### Not changed

- A draft-only type (never published) still saves straight into its own
  columns, and its publish is not stamp-guarded: D615 gave it no pending
  copy to review.
- The step-up and TOTP gates (`requireSuperAdminWriteBar`) are unchanged.

### Verified

- **Worker test** (`cloudflare-worker/test/contract_doc_type_publish_d622.test.ts`,
  on node:sqlite over the baseline schema):
  - a publish with the reviewed stamp succeeds;
  - a publish after a newer save is refused, and nothing changes;
  - a save that lands between the publish's read and its write is refused;
  - a publish that names no revision is refused;
  - the hub names who saved the revision;
  - the audit records the applied values.

  14 mutations, all caught.
- **Frontend test** (`frontend/test/hq_contracts_pending_d622.test.mjs`):
  - the card, live against pending;
  - the control only for a Super Admin;
  - the publish carries the reviewed stamp;
  - each refusal's sentence.

  14 mutations, all caught.
- **D615's test** now names the reviewed revision and expects the applied
  values in the audit.
