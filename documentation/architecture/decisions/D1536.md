### 1. Which runtime drives a run

- `runtimeKind(env, lines)` (`services/decks/genRooms.ts`) answers `queue` only when all three hold:
  - `DECK_GEN_RUNTIME` is `"queue"`;
  - `JOB_QUEUE` is bound;
  - the plan has more than `QUEUE_ABOVE_VARIANTS` (18) variants.
- **A variant** is a plan line that writes a proposal: kind `text` or `image`. Guards, vision checks, critiques and retries are steps of a variant and are not counted.
- Every other run goes to the deck's `DeckGenRoom`, as before. `"do"` (and unset) is the switch that sends every run back to the room.
- `DECK_GEN_RUNTIME = "queue"` is set in `[vars]`, `[env.production.vars]` and `[env.preview.vars]`, because env tables do not inherit vars.
- **No new queue.** The queue reuses `JOB_QUEUE` (`studioos-job-queue`, and `-preview` in preview), which is bound in all three tables with its DLQ, under the job type `deck_gen_batch`. No binding, Durable Object or cron line was added, so decision L adds no monthly cost for this.

### 2. `QueueGenRuntime` (`services/decks/queueRuntime.ts`)

- **The same seam.** It implements `DeckGenRuntime` over the same `D1GenRuntime` core:
  - `admit` takes ONE parent hold for the quote, keyed by the Idempotency-Key, then sends one message for a new run. A replayed request sends nothing.
  - If the send fails, the run is stopped and the hold given back, and admission answers 503 `runtime_unavailable`. A run that nothing drives never holds a member's allowance.
  - `startBatch` is one driver, as the core's; `cancel`, `status` and `rebuild` are the core's.
- **The contract suite runs it.** `deck_gen_runtime_contract.test.ts` lists it in `IMPLEMENTATIONS` beside `D1GenRuntime` and `DeckGenRoom`, with every assertion unchanged: 31 tests, 10 per implementation, plus the router.
- **A delivery** (`deliver`) is one slice of the run:
  - It drives the run with six drivers at once for at most `SLICE_MS` (10 minutes), like the room's alarm.
  - If the run is still going at the end, it sends the next message as its last act.
  - On a retried message (`attempts > 1`, the last delivery died), it first `rebuild`s the run from D1: a step left `running` with a usage row is `done` at what it charged, and one without goes back to `waiting`. So the run is resumable and charged once.
- **The consumer.** The job queue consumer routes `deck_gen_batch` before its `job_idempotency` dedup, as it does connector flow steps (D853):
  - The run's step claims are the dedup, and a retried delivery must run again.
  - A failed delivery is retried after 30 s.
  - The DLQ consumer ends a run whose message ran out of retries (`endExhaustedRun`): rebuild, then stop. What ran is settled once and the rest of the hold is released, then the message is mirrored as usual.
- **The same events.** The core emits `area_started`, `step_done`, `variant_ready`, `area_failed` and `batch_done`, and the step executor emits `area_busy`.
  - In production each event is relayed to the deck's `DeckGenRoom` (`relayToRoom`, the room's new `POST /relay`).
  - The room streams it on the run's existing `GET /api/decks/areas/batches/:uid/events`, so the page (`BuildProgress.jsx`, `deckV2Adapter.batch`) needs no change.
  - `/relay` accepts only those six event types. A failed relay never stops the run.
- **The room never drives a queue run.** `/cancel` re-arms the room's alarm only for a run in the room's own active list. Otherwise the room's first alarm would `rebuild` the run and send a step the queue has in flight back to `waiting`. For a queue run, Stop marks it `cancelling` in D1, and the queue's delivery stops the waiting steps and settles.

### 3. The weekly AI catalogue drift job (`services/aiCatalogueDrift.ts`, `services/ai/catalogueDiff.ts`)

- **When.** Mondays 05:17 UTC, inside the every-minute tick, on HQ only (D106). The cron lists are pinned by `agent_engine_bindings_d1528`, and nothing in them changed.
- **What it reads.** `GET https://api.cloudflare.com/client/v4/accounts/:account/ai/models/search`, paged 100 at a time (at most 20 pages).
- **What it compares.** `diffCatalogue` names one finding per model and field:
  - `listed`: a live model with no catalogue row, or an offered (`ga`/`partner`) row the live list no longer has;
  - `kind`;
  - `context_window`, when both sides state one;
  - `beta`.
  - A retired row that is gone live is not drift.
  - Prices are not compared: the search answer carries no neurons, which is what the catalogue holds and Cloudflare bills.
- **What it writes.**
  - Each finding becomes a row of `ai_catalogue_drift(model_id, field, catalogue_value, live_value, seen_at)` (migration 731, additive, `IF NOT EXISTS`).
  - With any finding, one HQ alert goes to each active Super Admin. It uses D886 B10's mechanism: a `notifications` row keyed `ai-catalogue-drift:<day>` (so a retried run alerts no one twice), then its `notifications_inbox` item, type `ai_catalogue_drift`, category `operations`, linking to `/admin/platform/ai-usage`.
  - The alert carries counts only, and a Super Admin can switch it off in `notification_prefs.ai_catalogue_drift.in_app`.
  - The job never edits `catalogue.ts`. A person does that, with its fixture, in one commit (D760).
- **When the live answer is wrong.** An unreadable answer (not 2xx, `success` false, or thrown) is `failed: live_unreadable`, and an empty list is `failed: live_empty`. Neither writes a row or raises an alert: an empty list would otherwise read as every model gone.
- **The secret.** The job needs `CLOUDFLARE_AI_MODELS_API_TOKEN`, a Cloudflare API token with only `Account · Workers AI · Read`, and reuses `CLOUDFLARE_ACCOUNT_ID`.
  - The name follows `CLOUDFLARE_AE_API_TOKEN`'s pattern.
  - Creating the token is the owner's step under decision L. It is documented in `PRODUCTION.md` §4. No value is in the repository.
  - Until both are set, the job logs `[ai-drift] skipped reason=token_unset` (or `account_unset`), calls nothing, writes nothing and raises no alert.
  - The token goes only into the request's Authorization header. Logs hold the outcome and counts, never a token, an account id or a model id.

### 4. Not built

- **Eval runs through the queue** (the other half of decision Z): the runtime has no eval run class yet (`RunClass` is `areas | deck_build`). Once there is one, it routes through `runtimeKind`.
- **The deck-build batch class** itself is AUTO-6, not this task.
- **No HQ screen reads `ai_catalogue_drift`.** The alert links to the AI usage page, and the findings are read from D1.
- **Unverified live:**
  - the model search answer's exact shape: `result[].name`, `task.name` and `properties[]` with `context_window` and `beta`, written from Cloudflare's public API reference as remembered, not checked against the reference page or a live call in this build. The parser leaves out any row it cannot read, and an answer with no readable row fails (`live_empty`) rather than reading as drift;
  - the queue path on a deployed Worker.
- **A known narrow window:** a delivery that sends its continuation message and then dies before its own acknowledgement is retried. That retry's `rebuild` may then send a step the continuation already has in flight back to waiting. The step runs again once, and its first run's charge stands, so the cost is a repeated step. No driver lease prevents it yet; a lease on `deck_area_batches` (the driver's slice number, checked before each step) would close it.
