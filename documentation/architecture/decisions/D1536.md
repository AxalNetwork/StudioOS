### 1. A second implementation of the seam

`services/decks/queueRuntime.ts` adds `QueueGenRuntime`. It implements `DeckGenRuntime` over the same D1 core (`D1GenRuntime`) as the `DeckGenRoom` Durable Object. `deck_gen_runtime_contract.test.ts` lists it beside the core and the room, so all three are held to the same ten rules:
- one quote and one parent hold;
- one run per Idempotency-Key, and one active run per deck;
- Stop charges what started;
- a failed area never sinks the others;
- a crash repeats nothing;
- the hold stays alive on a long run;
- the event shapes match;
- the step records match.

What differs is who drives the run.

- **A queue message, not an alarm.** Admission sends one `deck_gen_slice` message on `JOB_QUEUE`, keyed `deckgen:<uid>:<slice>`. The consumer (`driveQueuedSlice`) handles a slice in three steps:
  1. it rebuilds the run from D1, so a slice that died mid-step repeats nothing;
  2. it drives the run with six drivers for one slice (`SLICE_MS`, five minutes, inside a consumer's wall time);
  3. while the run is still going, it sends the next slice's message.

  It sends a new message rather than retrying the current one, so a long run never spends a message's retries. A slice that throws is retried by the queue. A run stops sending at `MAX_SLICES` (500) and logs that it did.
- **A queue that refuses the first slice.** Nothing would drive the run, so admission stops it at once. The hold comes back, and the member gets `runtime_unavailable`.
- **Live progress read from D1.** No object holds a queue run between slices. So `eventsFromD1` sends a `snapshot`, then reads the run's rows each second. It sends what changed as the events a room sends (`area_started`, `step_done`, `variant_ready`, `area_failed`, `batch_done`) with the running charged-of-held, until `batch_done` or ten minutes. After ten minutes the client's EventSource reconnects and gets a fresh snapshot.
- **The run records its runtime.** The new `deck_area_batches.runtime` column is `'do'` or `'queue'`, defaulting to `'do'`, so every earlier run reads as the room's. Stop and the event stream go to whichever runtime drives the run: a queue run is stopped in D1 and its events come from D1, and it never reaches a room.

### 2. Which runtime takes a run (decision Z, answered A on #3716)

`runtimeFor`:
- **A run of more than 18 variant steps** goes to the queue (`QUEUE_ABOVE`). A variant is a `text` or `image` step; guards, checks and critiques ride along and do not count.
- **Every other run** goes to the room.
- **`DECK_GEN_RUNTIME = "queue"`** sends every run to the queue. It is set to `"do"` in `[vars]`, `[env.production.vars]` and `[env.preview.vars]`, so switching runtime is one variable and one deploy, with no code change.
- **With no room binding but the queue bound**, the queue takes the run.
- **With neither bound**, the answer is 503 `runtime_unavailable`, as before.

### 3. The weekly catalogue drift check

`services/ai/catalogueDrift.ts` runs on Mondays at 05:55 UTC, on HQ only (`hqCadences`). It reads Cloudflare's model search (`GET /accounts/{id}/ai/models/search`, 100 a page) and compares it with `services/ai/catalogue.ts`.

- **What counts as drift.** One row per model and field in `ai_catalogue_drift`:
  - `listed`: the catalogue has a model Cloudflare no longer lists, or Cloudflare lists one the catalogue lacks. A model the catalogue already holds as `not_found` is expected to be missing.
  - `kind`: the two task names differ.
- **Told once.** A row stays while the drift holds, with `seen_at` moved to the latest run, and is removed by the first run that no longer sees it. HQ (`tellHq`, type `ai_catalogue_drift`) gets one alert listing what is new or changed, and is not told again about the same drift. Nothing changes the catalogue: a person does that from the alert, in the catalogue and its fixture together (D760).
- **Only two fields are kept** from the live answer: the model's `name` and its task's name. Each is cut to 200 characters.
- **Nothing is assumed from a bad read.** Each of these writes nothing and raises no alert, so a bad week never reads as "every model is gone":
  - an error status, a network failure, a body that is not JSON, or `success` not true;
  - an empty list;
  - fewer rows than Cloudflare's own `total_count`;
  - more than 20 pages.

  An account id that is not 32 hex characters is refused before any request.
- **No token, no run.** Without `CF_AI_CATALOGUE_TOKEN` or `CLOUDFLARE_ACCOUNT_ID`, it logs which one is missing (by name), makes no request, writes nothing, and tells no one.

### 4. The queue's path keeps away from member bank data

Through the image pipeline and the slide model, that once reached `sources.ts` and the Mercury feeds behind it, only because `slideModel.ts` and `diagramModel.ts` imported one pure helper, `sanitizeBinding`, from there. The grades, the `Binding` type and `sanitizeBinding` now live in `services/decks/binding.ts`, which reads nothing. `sources.ts` re-exports them, so every other import is unchanged, and the consumer's reach no longer includes `sources.ts`.

### Not built here

- **A lease on a queue slice.** The queue delivers at least once. If one slice were delivered twice at the same moment, the second's `rebuild` could reset a step the first is still running, and that step could be called twice. The charge cannot exceed the run's one parent hold, which is the quote, and every step's charge is read from its usage rows. A duplicate delivery is rare, and a lease would add a row per slice, so the run's rows remain the only dedupe, as the consumer branch's comment says.
