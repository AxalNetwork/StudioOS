### 1. The return domain

A return was a number or `null`, and `null` meant six different things. A fund that had lost everything and a
fund with nothing recorded yet both read `irr: null`, and the page could not tell a reader which it was
looking at.

Every return metric now answers in one of three ways, and the state says which:

| State | Meaning |
| --- | --- |
| `computed` | A real figure. **Zero is computed**: capital back and no more is a return of 0%, and nothing distributed yet is a DPI of 0. |
| `total_loss` | Capital was deployed and nothing came back: no distribution and no carrying value. Reported as `-1`, that is -100%, the ILPA convention. |
| `unavailable` | The inputs do not define a return. A `reason` names the input to fix. |

The reasons, each pinned by a test:

| Reason | When |
| --- | --- |
| `no_flows` | Nothing is recorded yet. |
| `single_flow` | One usable dated flow; a rate needs two points. |
| `no_contribution` | Money came back with no capital in. |
| `no_paid_in` | A ratio whose denominator is zero, and the fund-level IRR when no capital was paid in. |
| `outside_bracket` | No root in [-99.99%, +1000%]: all outflows, or a rate past the range, which is noise rather than a return. |
| `not_a_number` | A flow's date or amount cannot be read. |

Two deliberate choices:

- **A total loss is decided where the NAV is known.** The solver cannot reach it: with no inflow at all the NPV
  never crosses zero inside its bracket, and the floor is -99.99%, so -100% is not a root it can find.
  `computeFundMetrics` therefore decides it before calling the solver.
- **The fund level names the missing input; the solver describes the series.** With no capital paid in, the IRR
  reason is `no_paid_in`, the same diagnosis the ratios give, not the solver's `single_flow`. A reader who is
  told `single_flow` goes looking for another date; the real fix is to record the capital.

**The unit does not change.** IRR stays a fraction and `frontend/src/lib/rate.js` formats it, exactly as D4619
settled: `formatRate(0.1)` is "10%", and a total loss, `-1`, reads as "-100%". The flat `irr`, `dpi`, `rvpi`,
`tvpi` and `moic` fields are untouched, so every existing caller behaves as it did; the states arrive beside
them under `returns`. That is the field contract agreed with #4619, which owns the formatting and left this
solver alone.

A recorded but **negative** carrying value is not a value. `rollUpPosition` now reports
`unsupported: 'negative_fmv'` instead of folding it into `unmarked`, so a page does not say "no valuation is
recorded" about a valuation that is recorded and wrong.

### 2. The as-of mark rule

Two stores hold marks, at two grains, and this decision does **not** merge them: they answer different
questions, and a migration that merged them would rewrite history that LP reports already cite.

| Store | Grain | Read by |
| --- | --- | --- |
| `portfolio_marks` | per project, `fmv` in dollars, optional `fund_id` (NULL = firm level) | the investor Portfolio |
| `fund_position_valuations` | per `portfolio_positions` row, `value_cents`, always inside one fund | the fund's own board |

One **rule** governs both, and it lives in `services/portfolioValuation.ts`:

1. **The reporting date is a ceiling.** Only marks effective on or before the requested date are eligible, so a
   quarter-end read never prices the book with a mark that did not exist yet. No date means no ceiling.
2. **The latest effective mark wins.**
3. **A correction beats what it corrects.** Among marks sharing an effective date, the one recorded later wins:
   `created_at` then `id`. `id` is an autoincrement, so the order is total and the answer is the same on every
   read.

**The defect this fixes.** The project-level read grouped `MAX(as_of_date)` and then selected bare columns. When
a mark was corrected for the same effective date, the join produced both rows and SQLite returned the value from
an arbitrary row of the group: the same request could price a position at either figure. Nothing recorded was
wrong — which record answered was undefined.

### 3. Scope

`portfolio_marks.fund_id` is nullable, so one project can carry a firm-level mark and a mark from each fund that
holds it. The old read ignored `fund_id` entirely, so one fund's mark could price another fund's position. A
reader now asks for the scope it means, and the scope contributes one key to the order, ahead of the correction
keys:

- **`{ kind: 'fund', fundId }`** — that fund's marks, with firm-level marks as a fallback. A sibling fund's mark
  is never read. On one effective date the fund's own mark wins, because it is the more specific record for it.
- **`{ kind: 'firm' }`** — the project-level aggregate, which is what the investor Portfolio reads. On one
  effective date a firm-level mark **wins outright**: it speaks for the whole book, and no single fund's view
  displaces it. Otherwise a single fund's mark is used.

**The unsupported combination.** When two different funds record different values for one company on the same
effective date, the aggregate has no basis for choosing, so the carrying value is **unavailable** with
`fund_marks_conflict`, and the position carries at cost like an unmarked one. `unusable_mark_count` counts these
apart from unmarked positions, so mark coverage never reports a disputed position as marked. Picking one fund's
figure silently is the behaviour this package exists to stop; the remedy is to record a firm-level mark, or to
read the fund on its own page.

### 4. Consumers

The rule is shared, not copied:

- `GET /api/positions` and `GET /api/positions/metrics` call `latestProjectMarks` under the `firm` scope.
- `readFundPerformance` and `readFundPositions` build their joins from `positionMarkIdSql`, so the fund's
  performance read and its board cannot drift.

`GET /api/positions` now honours `as_of` as the metrics read beside it already did. Before, the list used the
latest mark ever recorded while the metrics used the mark as of the requested date, so one page could show a
position and its totals priced on different days.

### 5. What the tests pin

20 tests in `portfolio_returns_valuation_4644.test.ts`: the three return states and all six reasons, the
unchanged IRR unit, the negative mark, and — over real SQLite — the date ceiling, correction precedence, the
total order under a same-instant tie, the fund scope, the firm-level override, the two-fund conflict, and the
shared position subquery.

**Mutation-checked.** Each of these makes a test fail:

- ordering marks by effective date alone (the original defect);
- dropping the scope's preference key;
- dropping the fund predicate, so a sibling fund's mark leaks;
- not detecting the two-fund conflict;
- removing the total-loss branch;
- letting the solver answer the zero-capital case;
- folding a negative mark back into `unmarked`;
- returning 0 for a ratio with a zero denominator.

### 6. What the reader sees

- A write-off reads "-100%" instead of "—".
- A company two funds mark differently on one date reads as unavailable, with a sentence saying so, instead of
  one of the two figures chosen at random.
- A quarter-end read prices its positions and its totals on the same day.
- No figure that was right before changes.

### Not in this slice

- **Portfolio presentation**, which waits on the #4817 canvas. The states and reasons are returned but no screen
  is restyled here.
- **#4645's** input-availability and health signals, and **#4647's** reporting presentation and history
  completeness, which read these fields.
- **Merging the two mark stores.** Out of scope on purpose, as §2 says.
- **A `corrected_at` column.** Correction precedence is carried by `created_at` and `id`, which both stores
