## D8081 — agents in a hierarchy: planner, worker and reviewer steps over `agent_handoffs`, shares from the parent's budget, and no self-review (#8081)

- **Status:** built by S24 on 2026-11-25, on #7074's capacity (PR #7104) and #8071's budgets (PR #8263, `agentBudgets.reserve` and `settle`). Tracker #8059, audit section 19.
- **Out of scope, as the issue says:** sub-agent lanes (#7074), recruits and outside executors (#7072), and any new screen.

### What a tree is

A task a person started is the **root**, and it plans. A run may still end with D1530's line `{"handoff":{…}}`. The line may now also say what the target is asked to be:

- `"role":"planner"`, `"role":"worker"` (the default), or `"role":"reviewer"`;
- for a reviewer, `"reviews":"<run uid>"`.

The step keeps it in `agent_handoffs.hierarchy_role` and `reviews_run_uid`. A step written before this change has no role and reads as a worker. Depth stays D1530's: at most 3 (`depth_exceeded`).

### The rules (`cloudflare-worker/src/services/agentHierarchy.ts`)

They are checked when the run asks (`proposeHandoff`) and again when a person accepts (`decideHandoff`), because Accept reads the target again. Each refusal is a `refused` step of its chain, as in D1530.

| Code | When |
| --- | --- |
| `planner_not_allowed` | A worker or a reviewer asks for a planner. Only the root or a planner may. |
| `too_many_workers` | A planner's task already has N worker steps proposed or accepted. N is `agent_scope_settings.planner_max_workers`, or 3 when that is NULL. |
| `review_target_missing` | A reviewer step names no run, or a run that does not exist. |
| `self_review` | The reviewer's target agent is the agent that made the reviewed run. The reviewer is never the author. |

### Budgets: the parent reserves each child's share

The rules use #8071's contract and keep no second ledger.

- **Where the share lives.** A child's share is its task's `budget_tokens_cap`. D8071's own `task_tokens` check halts a child that would pass it.
- **The parent's cap.** It is the parent task's token cap. If that is NULL, it is the parent agent's monthly token cap (D8071: "a task's NULL cap is the agent's"). If both are NULL there is no cap, and the child gets none.
- **The share.** What is left is the parent's cap less the parent task's tree. The tree is `taskTreeTokens`: the task's own settled tokens plus every child's hold. The share is an equal part of what is left, and the parent keeps one part:
  - left ÷ (worker slots left + 1) for a planner's worker;
  - left ÷ 2 for any other step.

  A share under 1,000 tokens refuses `share_exhausted`.
- **The reservation.** Before the child's task exists, `agentBudgets.reserve(parent run, share)` must pass, so every other cap of the parent still holds. Its refusal is the step's refusal (`budget_exhausted`, `budget_unreadable`).
- **A child's hold.** While the child's task is open, it holds its share, or what its own tree used if that is more. Once the task is done or cancelled, it holds only what it used, and the rest returns to the parent. Holds are derived from D8071's settlement rows and never written. A retried step or a second `settle` changes nothing: `agent_budget_settlements` already applies once per step. A second Accept finds the step no longer `proposed`.
- **The parent's own runs.** D8071's task total now counts the tree. A parent's own next call therefore sees what its children hold.
- **Two Accepts at once.** Both can read the same "left". After the child's task carries its share, the tree is read again. A step that no longer fits cancels its child task and is refused `share_exhausted`.
- **Units.** Shares are in tokens. Minutes stay per task and per agent, as in D8071.

### Schema (`202611250124_8081_agent_hierarchy.sql`)

The file is expand-only, with three nullable columns:

- `agent_handoffs.hierarchy_role`, with a CHECK on the three words;
- `agent_handoffs.reviews_run_uid`, with a CHECK that only a reviewer step carries one;
- `agent_scope_settings.planner_max_workers`, from 1 to 20.

The issue asked for one column and one check. A reviewer step must name its run, and N must come from `agent_scope_settings`, so this needs three.

### The read and the page

`GET /api/teams/:scope/:id/handoffs` carries `hierarchy_role` on each step, beside its `depth`. The route in `agent_engine.ts` is unchanged: the step shape comes from `chainsOf`. The Team engine page's handoff trail (`HandoffTrail.jsx`) adds the role word after the target: "as planner", "as worker" or "as reviewer". A step read without a role shows none. A new refusal code reads through the trail's existing fallback, for example "Stopped: self review."

### Where this departs from the issue's file list

- `services/agents/handoffs.ts`. The proposal and the Accept live there, not in `agent_engine.ts`, so that is where the rules are called.
- `services/agentBudgets.ts`. `taskTreeTokens` and `childHoldTokens` are new, and the task total counts the tree. Without that, a parent's own later runs could spend what its children hold.
- `agents/loop.ts`. One sentence in the prompt names the two new fields. Without it, no model would ask for a planner or a reviewer.
- `frontend/test/agent_engine_e8_d1531.test.mjs`. The trail's existing test asserts the role word.

### Rollback

Revert the PR. The columns are nullable, and nothing else reads them. A step proposed while this was live keeps its role, which the reverted code ignores. A child task keeps its `budget_tokens_cap`, which D8071 still honours as a task cap.
