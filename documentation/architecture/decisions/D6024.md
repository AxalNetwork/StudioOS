## D6024 — Remove Build features and unmark must-haves safely (#6024)

Build record writers get `Remove feature` on Solution design and `No longer a
must-have` on Prototype / MVP. Both declare the existing in-page confirmation
contract. The first permanently deletes the canonical `mvp_features` row; the
second runs the existing `patchFeature` with `is_must_have: false`, preserving
the feature and its linked work. The record route retains Build's existing
write/ownership checks and hides both actions from readers. This does not
change the legacy progress DELETE route's permissions or add another store.
Edit remains the final action so the existing fallback Next step never
promotes either removal action.

Feature deletion refuses linked roadmap items, risks or test sessions and
names their categories/counts. It checks every reference to the feature,
including an inconsistent reference from another project, without exposing
its title or changing that other project. A guarded DELETE rechecks references
inside the D1 batch. Its conditional actor-scoped activity row is in the same
transaction; a raced no-op writes no audit, and an audit failure rolls the
delete and foreign-key cascades back. The established FK semantics remove the
feature's design links and release checks; the confirmation names that loss.
D1's metadata counts cascaded child changes as well, so success is determined
by the single parent row from DELETE RETURNING, not `meta.changes === 1`.
The conditional audit uses SQL `changes()`, which counts the parent statement.

No generic record-page contract change is needed. A successful write re-reads
the record. A deleted feature or unmarked must-have then returns 404 under
its existing ownership predicate, and `useCycleRecord` returns to the module.
The module and overview reads run again on that route transition. Counts and
burn-up still derive from canonical feature rows, with no optimistic counters.

Build Plan keeps its acceptance, payload, evidence and landed identifiers.
Its existing read joins a feature under the same project and derives
`landed_state`: `present`, `removed`, or `not_must_have` for a Prototype / MVP
item whose feature remains outside the must-have list. The accepted row says
`Feature removed` or `No longer a must-have` and suppresses Open for either
absence. Readers also see the truthful history. A cross-project landed id
never becomes a link. This is a read projection, with no tombstone table or
historical proposal rewrite; existing progress stages already report a
missing landed row as not recorded.

Real migrated SQLite/D1 and mounted record regressions cover role/project
boundaries, confirmation/cancel/retry, protected/racing references, cascades,
rollback, canonical metrics and retained plan history. Mutation checks and
candidate build/validation outcomes are recorded in the PR. Other Build
record types and the separate Pitch phone slice #6063 remain outside this PR.
