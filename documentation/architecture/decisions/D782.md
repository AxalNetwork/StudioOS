## D782 — GitHub feeds every Build module, read-only, through the connector page

- **Status:** decided by the owner on 2026-10-19 and filed by S1 as #2110, the tracking issue. Its five parts run in slots S22 to S26. This file was written by S24's part (#2113), as #2110 asks, and each later part adds its own row to §3.
- **Basis:** `origin/main` at `48b77062`. Worker paths are relative to `cloudflare-worker/src/`.
- **Stacks on:** D655 (the GitHub connector and the `connector_fed_items` ledger, migration 445), D686 (Operating systems' Tools history), D751 (the connector's setup and the install slug) and D753 (GitHub's connector page).

### 1. The decision

The owner, 2026-10-19: "Build Github connection for connector, in "Connector" page, that will feed different modules across Build section of Founder profiles: Tools, Solution design, Prototype / MVP, Product roadmap, Founding team, Company creation, Operating systems."

**No new GitHub permission.** Each module is fed under the App's four Read permissions: Contents, Issues, Metadata and Pull requests. `hasScopeOverreach` stays as it is. Each part checks the endpoint it adds against those four in its own PR.

| Module | From GitHub | How it lands | Task |
| --- | --- | --- | --- |
| Product roadmap | issues (D655), milestones, releases | An issue is an item. A milestone gives its items their target and group. A release marks the items it closed as Shipped and adds a release row. | S22, #2111 |
| Prototype / MVP | pull requests (D655), their state, releases | A pull request is a must-have. Merged means built. A release records an MVP release check. | S23, #2112 |
| Operating systems, Tools, and the page | the connection and each sync | GitHub is the Code system on Operating systems, with its repositories, last sync and what it feeds. Each sync is a line in Tools. The connector page names every module fed. | S24, #2113 |
| Solution design | README, `docs/` and ADR files; languages and topics | Architecture notes and decisions arrive as proposals the founder accepts. The stack is facts. | S25, #2114 |
| Founding team, Company creation | contributors (commits in 90 days); the repository's owner and licence | The founder maps each GitHub login to a team member once; it is never guessed. A proposed formation step asks to move the code into the company's organisation (IP). | S26, #2115 |

### 2. Rules every part keeps

- **Every row goes through the `connector_fed_items` ledger.** A re-sync updates a row, and a row the founder deleted stays deleted (#1906).
- **Judgement is proposed, never written:** the solution design notes, the IP step and the team mapping. Facts are written.
- **A contributor's login is personal data.** Only the project's members see it. It never appears in a log, a comment or an error.
- **The page claims only what is built.** `integrations/githubFeeds.ts` lists what a sync lands (`GITHUB_LANDINGS`) and which modules read the connection itself (`GITHUB_READ_BY`). The registry's `pulls` and `feeds`, and the connector page's tools and description, are held to that list by `cloudflare-worker/test/github_code_system_d782.test.ts`. A part that adds a feed adds it to the list, then to the page.
- **GitHub is stubbed in every test.** The live check is the owner's, once the App is registered.

### 3. What each part built

**S24, #2113: Operating systems, Tools and the page.**

- **The Code system.** Operating systems' module read (`routes/cycle_build.ts`, `codeSystems`) returns `parts.tools.code`: one entry for each GitHub connection enabled for the project's company. Each entry has:
  - its chosen repositories;
  - its last sync and failure time;
  - what it fed in this project, from the ledger rows with this `project_id` (`fedCounts` gains a `projectId`);
  - its owner;
  - an Open link to Connect a tool.

  It is a read from the connection and is never written into `project_core_systems`. A hand-mapped core system stays in the systems table; this entry is labelled "From the GitHub connection".
- **Who sees what.** Repository names and the owner's name follow the Tools rule: the owner and the company's members see them, anyone else reads `null` and a count.
- **Each sync is a line.** The same read returns `parts.tools.syncs`: the last 20 GitHub syncs, newest first, from the sync's `integration_logs` row. Each line has its time, its state (done, partial or failed), the repositories it read and what arrived per module, for example "12 issues → Product roadmap, 3 pull requests → Prototype / MVP, 2 releases counted".
  - The sync route now keeps the repositories on that row (`syncLogPayload`, capped so the JSON stays whole under `logEvent`'s 4000-character cut).
  - A failed line shows the stored message without its code. Anything credential-shaped is replaced with `[hidden]` (`syncErrorWords`).
- **The page.**
  - `CONNECTOR_METADATA.github.pulls` no longer claims "Releases → Product roadmap", which makes no row. A release is still read and counted, and the tools list and the description say so.
  - `feeds` gains Operating systems. GitHub's "Now fed by" gives Operating systems `count: null` with its reason, never a ledger zero, because that module reads the connection.
- **The frontend.** `frontend/src/pages/cycles/ToolsHistory.jsx` draws the Code system above the Tools table and the sync lines below it. The words are in `codeSystem.js`.
- **Not built here: the install slug.** `GITHUB_APP_SLUG` is set once the owner registers the App and posts its URL slug on #2110 (`documentation/operations/GITHUB_CONNECTOR_APP.md` §2). Until then it stays `""` in both `[vars]` blocks, and the page has no install link.

**S22, #2111: Product roadmap — milestones, releases and Shipped.**

- **Where it lives.** `integrations/providers/github/roadmap.ts`, called from `github.ts`'s sync: the main loop hands it each page it reads (`roadmap.saw`), and after the loop `roadmap.finish` does the work per repository, within the first half of what is left of the subrequest budget (Solution design, #2114, takes the rest). Migration 499 adds `roadmap_okrs.milestone_title`, `milestone_due` and `shipped_release_id`, and the `roadmap_releases` table. `target_date` already existed (441).
- **Milestones** (`/milestones?state=all`, under Issues read). An item whose issue sits in a milestone takes the milestone's title as its group and its due date as its target. A milestone with no due date sets the group only. An issue taken out of its milestone loses the group, but its target stays, because it may be the founder's by then.
- **Releases.** Each published release is one `roadmap_releases` row through the ledger. A draft is not a release. A re-sync updates the row, and a row deleted here stays deleted: its ledger row keeps `local_table` with no `local_id`, so it reads as deleted rather than never landed. A release an earlier sync only counted (D655) lands as a row on the next sync.
- **Shipped, on evidence only.** An item is marked shipped by a release when its issue is closed and either:
  1. the release's notes name the issue (`#12`, `acme/app#12` or its issue URL), and then by the first such release; or
  2. a merged pull request in the same repository closes it with a closing keyword (close, fix, resolve and their forms), and the release is the first published at or after that merge.

  Nothing else marks an item. A mark once written is never moved by a later release. Deleting the release row clears it (foreign key `ON DELETE SET NULL`).
- **The module.** Product roadmap's read returns `parts.github`: the milestone groups (soonest target first), each item with its Shipped mark, and the Releases strip (the newest 12, each with the items it shipped). It is its own read, so a store it cannot read makes the part Unreadable and leaves the canvas's table as it is; the table keeps its five columns. `frontend/src/pages/cycles/RoadmapFromGithub.jsx` draws it at `#from-github`, with its words in `roadmapGithub.js`. A link out goes only to a release page on github.com. The item's record adds Milestone and Shipped rows to its GitHub panel.
- **The page and the counts.** `GITHUB_LANDINGS` gives releases their store and adds milestones (`ledger: false`: they write onto items rather than make rows). The registry's `pulls` add Milestones and Releases under Product roadmap, the page gains a `read_milestones` tool, and `read_releases` lands in Product roadmap. `fed.ts` counts releases as rows, so an unlinked ledger row now means a deleted row, and its reason says so.

**S25, #2114: Solution design.**

- **What is read.** Per chosen repository, `integrations/providers/github/solutionDesign.ts` reads `GET /repos/{o}/{r}` (its topics), `/languages`, `/readme`, and the Markdown listed under `docs/`, `doc/`, `adr/` and `docs/adr/` (`/contents/<dir>`, then each file's `/contents/<path>`). Contents and Metadata only, so no new permission.
  - **The caps:** at most 40 files and 200 KB of Markdown per repository. When the listing fits, every file is read. Otherwise each listed file (up to 100) is dated by its newest commit (`/commits?path=…&per_page=1`), and the newest are read while they fit. The 200 KB counts what is actually read, so a listing that understates a size cannot pass it.
  - **The budget:** `syncGithub` calls it once, after the issues, pull requests and releases and after Product roadmap's `finish` (#2111). What is left of the subrequest budget is shared: Product roadmap takes the first half and Solution design the rest, since neither reports what it spent. A run that runs out says `partial`.
  - **A repository GitHub no longer serves** (404 on `/repos/{o}/{r}`) feeds nothing here, and fails nothing.
- **The stack is facts.** Languages by bytes and topics are written to `solution_design_stack` (migration 500; 499 is #2111's), one row per repository and project. Its ledger row is `'solution_design', 'stack'`. Solution design reads it through the ledger as "Built with", each language with its share.
- **Architecture is proposed.** Each ADR file (under `adr/` or `docs/adr/`) is one proposal, and so is each README or docs section headed Architecture, Design or Decisions. A heading inside fenced code is not read. A proposal has its title, the section's own first paragraph as the extract, and the file's link. **No model reads the files.**
  - Proposals live in `solution_design_proposals`, keyed by connection, project and place (`owner/repo:path#anchor`). Each holds the SHA-256 of its section's text.
  - A re-sync of the same text leaves the row as it is, so a dismissed proposal stays dismissed. Changed text puts it back to pending, even when it had been accepted. The note an earlier Accept wrote stays.
  - A pending proposal whose section is gone is withdrawn, but only after a complete read of its repository.
- **Accept and Dismiss.** `POST /api/cycles/build/solution-design/proposals/:id/accept` and `…/dismiss`, under Build's write rule (`canWrite`).
  - Accept claims the pending row once. It then writes, in one batch, a `solution_design_notes` row citing the file, the note's id on the proposal, the note's ledger row (`'solution_design', 'design_note'`) and the activity line. A failed batch hands the claim back.
  - Dismiss writes no note. A proposal that has already been decided answers 409.
- **The fed count.** GitHub's "Now fed by" gains Solution design. It counts the ledger's accepted notes and stacks; a pending proposal is not in the ledger.
- **The page.** `GITHUB_LANDINGS` gains `design_note` and `stack`, so the sync lines say "3 architecture proposals → Solution design, 1 repository stack → Solution design".
  - The registry's `pulls` and `feeds` gain Solution design, and its Contents and Metadata permission lines name what they now read.
  - The connector page gains two read tools, `read_design_docs` and `read_stack`, and a sentence in its description.
  - `MODULE_LABELS` and `MODULE_HREFS` gain `solution_design`.
- **The frontend.** `frontend/src/pages/cycles/SolutionDesignFromCode.jsx` draws "From GitHub" under the features table: Built with, "Proposed from code" with Accept and Dismiss, and the accepted architecture notes. Repository text is drawn as text, and a link only when it is GitHub's own https page. The part is absent when GitHub has brought nothing to the venture. Its words are in `designFromCode.js`.
- **Not built here:** a summary of a design document by Eadwyn. That would be a rail option under D720.

**S26, #2115: Founding team and Company creation.**

- **What is read.** Per chosen repository, `integrations/providers/github/team.ts` reads `GET /repos/{o}/{r}/contributors` and `/commits?since=<90 days ago>` (at most 5 pages of 100), and `github/company.ts` reads `GET /repos/{o}/{r}` (its owner and licence). Metadata and Contents only, so no new permission. A repository GitHub no longer serves (404) feeds nothing and fails nothing; an empty one (409 or 204) has no contributors.
  - **The budget:** `syncGithub` calls each once, after the main loop. Before Product roadmap and Solution design share what is left, Founding team takes up to an eighth (8 a repository) and Company creation up to an eighth (2 a repository). A run that runs out says `partial`, and only a complete read of a repository drops a login it no longer sees.
- **Who builds is facts; who a login is, is the founder's.** Each login (lower-cased, bots and commits with no GitHub author left out, at most 100 a repository) is written with its commits in the last 90 days to `github_contributors` (migration 501). **A login is never matched by name or email.** The founder matches it once, on Founding team, to a founder on the venture's cap table (`github_login_map`, the project's, so it outlives a connection). Only a login a sync brought to this project can be matched, and only to a holder with a founder role on this venture.
  - `POST /api/cycles/build/founding-team/github-logins` `{ login, holder_id }` matches; `DELETE …/github-logins/:login` unmatches. Both are under Build's write rule (`canWrite`).
  - A matched login's ledger row is `'founding_team', 'contributor'`, linked to the founder's `cap_table_holders` row, one per connection that read it. A re-sync writes it for each mapped login it sees. Unmatching deletes it. The fed count counts mapped contributors only.
- **Where the code sits is facts; the IP step is proposed.** Each repository's owner kind (personal account or organisation), owner login and licence (SPDX id, or none) go to `github_repo_facts`.
  - **A personal account owns it:** one proposal per repository and connection in `company_creation_proposals`, "Move the code into the company's GitHub organisation", with its reason (the IP belongs to the company). A re-sync never brings back a decided one; a pending one is withdrawn when the repository moves to an organisation.
  - **An organisation owns it:** a `formation_step_checks` row `github_org:<owner>/<repo>` on each formation step whose title names IP (or intellectual property) assignment, as evidence. No step is made for it.
  - **No licence file** is drawn as the fact "No licence file", never as advice.
  - `POST /api/cycles/build/company-creation/proposals/:id/accept` claims the pending row once, then writes in one batch a `formation_steps` row (`todo`, kind `other`, last in order), the step's id on the proposal, its ledger row `'company_creation', 'ip_step'` and the activity line; a failed batch hands the claim back. `…/dismiss` writes nothing else. A decided proposal answers 409.
- **Personal data.** A login, a commit count and an owner's login are read only by the project's members: the venture's own founder or a member of its company (`user_company_links`). An admin or partner reads the board but gets how many, never which. They are never in a log, an error or an activity line: the sync's errors name a status and a path, the activity lines say "A GitHub login matched to a founder". Disconnecting deletes the connection's contributors and their ledger rows, its owner facts and its pending proposals (and the foreign keys cascade); the founder's own mapping stays with the project.
- **The page.** `GITHUB_LANDINGS` gains `contributor` (Founding team) and `ip_step` (Company creation). The registry's `pulls` and `feeds` gain both modules, and its permission lines name contributors, commits, owners and licences. The connector page gains `read_contributors` and `read_ownership` and a sentence in its description.
- **The frontend.** `FoundingTeamFromCode.jsx` draws "From GitHub" on Founding team: each matched founder with "Builds: N commits in the last 90 days" per repository and Unmatch, and "Not yet matched" with the founder's own control (choose a founder, Match). `CompanyFromCode.jsx` draws it on Company creation: where each repository's code sits and its licence, the proposal with Accept and Dismiss, and the evidence. A non-member's part says how many arrived. Their words are in `teamFromCode.js`.
