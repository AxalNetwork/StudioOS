### 2. Create

- **An explicit action only.** Nothing else creates a preparation: no read, preview or retry does. The body names `company_id`, `project_id`, an `operation_key`, optional initial `content` and optional `new_round`.
- **Issuer pair.** D5454's `resolveIssuerPair` on the server: a project without a company is refused (`project_has_no_company`, "Link the project's company before creating a deal"), and so are a mismatched pair, a deleted project and a missing or archived company. One company may hold drafts for several of its projects.
- **New round or resume.** While an unreleased `preparation` of the same pair exists, create answers 409 `open_preparation_exists` with that draft's uid. Opening a second one needs `new_round: true`. Nothing is matched by company name. The "no open draft" check runs again inside the insert, so two concurrent creates with different keys still open only one.
- **No deal row.** The row is `origin = 'preparation'`, `deal_id` NULL, `draft`/`unreleased`, `lock_version` 1, with revision 1 as its working revision (D5454 CHECK `dp_private_owns_no_deal`). Nothing here reads or writes `deals`.

### 3. Save: optimistic concurrency

- `lock_version` is the revision token. A save sends `expected_revision` (or `If-Match: "<n>"`; if both are sent they must agree), an `operation_key` and `changes`, the keys to set. A `null` change records "not recorded"; it never deletes the key or turns it into 0.
- The new content is the working revision's content with the changes applied, validated as a whole (cross-field rules read the merged draft). It is written as a **new** revision; earlier revisions are immutable (D5454 triggers), and the submitted, approved and released pointers do not move.
- The write runs only if the preparation still holds `expected_revision`, is `draft` or `changes_requested`, and still names the same company and project. A stale save is 409 `revision_conflict` with `current` (revision token, revision number, state, saved time, saver) and `fields`: for each key the save tried to change whose current value differs, `yours` and `current`. The caller holds `read`, so this is a comparison they may see. Nothing is merged; the editor reloads and reapplies. Financial terms are never auto-merged.
- **Issuer drift.** If the project has moved to another company, lost its company or been deleted, the save answers 409 `issuer_reconciliation_required` and writes nothing; the detail read reports `drift: moved` or `detached`. The pinned issuer is never rewritten.
- **In review or approved.** A save answers 409 `preparation_not_editable`. How an edit after submission opens a new working revision and invalidates approval is ADP-04's rule (#5458); until it exists, those drafts are not edited here.
- A save that changes nothing (same content digest) writes no revision and answers `unchanged: true`.

### 4. Operation keys

- `deal_preparation_operations` keeps one row per create or save that committed. Its key is the deployment, the admin, the action, the target (the preparation uid for a save, `''` for a create) and the client's key (8 to 128 of `A-Za-z0-9._:-`).
- The payload digest is SHA-256 of canonical JSON (sorted keys) of the action, the issuer pair, the expected revision (for a save), `new_round` (for a create) and the validated changes. The same key with the same digest returns the stored outcome (`replayed: true`). The same key with another digest is 409 `operation_key_reused`.
- The row stores the outcome: preparation, revision and revision token. A client whose response was lost retries with the same key and learns what happened. Concurrent retries of one key produce one preparation or revision: the unique key aborts the loser's whole batch, which then reads the winner's row.
- The table is append-only (triggers).

### 5. One batch: content, version, ledger and audit

Each write is one `DB.batch`, so one transaction. For a save: the revision insert (conditional on the token, the state and the pair), the pointer and token move (only if that revision exists), the operation row (only if the move changed a row), and the `admin_audit_log` row (`adminAuditStatement`, only if the operation row was written). A create has the same chain. A stale or refused write therefore leaves nothing behind. If the audit or ledger insert fails, the batch rolls back, so no revision exists without its audit row.

A batch that throws, or that commits nothing for a reason the follow-up reads do not explain, answers 503 `save_outcome_unknown` or `create_outcome_unknown`. Those say "retry with the same operation key"; they do not claim nothing changed. Before answering, the store reads back what committed: its own operation row, a concurrent winner's row, a moved token (a conflict) or a state change.

The audit rows are `deal_preparation_created` (preparation uid, revision 1, company, project, `new_round`) and `deal_preparation_saved` (preparation uid, revision number, the token saved from, the changed keys). They hold ids and key names only, never a value.

### 6. Validation

The server checks everything; the client's input attributes are only a convenience. The keys are D5454's `REVISION_CONTENT_KEYS`. Any other key is a field error (`unknown_field`). A refusal is 422 `invalid_fields` with `fields: { key: code }`, and nothing is written.

| Field | Rule | Codes |
|---|---|---|
| `title`, `summary`, `description`, `sector`, `spv_jurisdiction`, `internal_notes` | text, trimmed; at most 200 / 1000 / 20000 / 120 / 120 / 10000 | `not_text`, `too_long` |
| `target_raise`, `valuation_cap` | finite, ≥ 0, at most two decimals, ≤ 10¹³; a number or a plain decimal string (no separators) | `not_a_number`, `must_not_be_negative`, `too_many_decimals`, `too_large` |
| `minimum_check` | as above, and > 0 when supplied (no minimum is forced) | `must_be_positive` |
| `minimum_check` vs `target_raise` | when both are set, minimum ≤ target | `minimum_exceeds_target` |
| `carry_pct`, `management_fee_pct` | 0 to 100, at most two decimals | `percent_out_of_range`, … |
| `currency` | `USD` only (case-folded); new rounds stay USD-only until another currency is authorised | `unsupported_currency` |
| `instrument` | one of `SAFE`, `Convertible Note`, `Equity`, `SPV`: the vocabulary the existing Draft Deal and terms forms offer | `unsupported_instrument` |
| `closing_deadline` | a real calendar day, `YYYY-MM-DD` | `invalid_date` |
| `website` | `http`/`https` with a host and no credentials, at most 300 | `unsupported_url_scheme`, `invalid_url`, `too_long` |
| `evidence_refs` | at most 50 of `{ field, kind, source, url }`. `kind` is `typed` (an admin entered the value) or `quoted` (taken from a source, which must be named). `field` is an editorial key. `url` is http(s), at most 2048 | `quoted_reference_needs_source`, … |
| `audience_manifest` | not authored here (release, ADP-04) | `not_editable_here` |
| `brief_executive_summary`, `brief_investment_thesis`, `brief_problem_product`, `brief_market`, `brief_team`, `brief_traction`, `brief_use_of_funds`, `brief_risks_mitigations`, `brief_open_questions` | the nine brief sections (§9): text, trimmed, at most 5000 each; a source is an `evidence_refs` entry naming the section | `not_text`, `too_long` |
| `discount_pct` | #6196: a percentage, 0 to 100, at most two decimals | as the other percentages |
| `pro_rata` | #6196: `none`, `pro_rata` or `super_pro_rata` | `unsupported_value` |
| `information_rights` | #6196: `none`, `standard` or `major_investor` | `unsupported_value` |
| `information_rights_note` | #6196: text, at most 280 | `too_long` |
| `board_seat` | #6196: `none`, `observer` or `seat` | `unsupported_value` |
| `board_seat_count` | #6196: any positive whole number (no upper cap, owner 2026-11-27), and only when `board_seat` is `seat` (checked on the merged draft) | `not_a_whole_number`, `must_be_positive`, `board_seat_count_needs_seat` |

- **Blank is unknown.** `''`, whitespace and `null` are stored as null. No amount becomes 0, and no term gets a default: a blank `pro_rata`, `information_rights` or `board_seat` is never stored as `none`.
- **Who entered a term, and from where.** Each revision records its author and time (`created_by_user_id`, `created_at`), so the revision list shows who set each value and when. A term's source is an `evidence_refs` entry for that field, `typed` or `quoted` with its source.
- **Money** keeps the deal's existing semantics: whole currency units as a number, the shape `deals.target_raise` already has. Nothing is converted, and no ledger is added.
- **Incomplete drafts save.** Readiness warnings are separate from errors: `title_missing`, `instrument_missing`, `currency_missing`, `target_raise_missing`, `closing_deadline_missing`, `closing_deadline_passed`. ADP-03/04 decide which of them block release.
- **The deadline clock.** A deadline passes at the end of its day in UTC (23:59:59.999Z). The clock is injected (`deps.now`), and the tests pin the instant plus the day, month, year and leap-day boundaries. A past deadline saves, with a warning; it cannot reach release unnoticed.
- Instrument-specific required terms are not specified here. No commercial rule is invented; see §8.

### 7. Costs and indexes

The detail read issues four bound statements: the preparation, the working revision, the issuer names, and the capability check's freeze lookup. The revision list reads one indexed page (`idx_deal_preparation_revisions_prep`). A save issues the reads above, one `MAX(revision_no)`, and one batch. Operation lookups use the table's unique key. No DDL runs on a request beyond the existing `ensureAdminAuditLogTable` safety net, and nothing calls AI or an outside service.
