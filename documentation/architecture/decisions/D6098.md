## D6098 — Feedback: rename or merge a theme (#6098)

- **Status:** built 2026-11-14 by S15. Filed under #4861.
- **No migration.** No new table or column; the write touches `product_feedback.theme` and `roadmap_okrs.feedback_theme`.
- **Code:** `renameFeedbackTheme` and `feedbackThemes` in `cloudflare-worker/src/services/growWriters.ts`; `PATCH /api/cycles/grow/feedback/themes` in `routes/cycle_grow.ts`; `frontend/src/pages/cycles/FeedbackThemes.jsx`, drawn under Product improvement's table by `defs/grow.jsx`; `cyclesWrite.grow.feedbackTheme` in `frontend/src/lib/api/cycleWrites.js`.

### What a theme is

A theme is the exact text stored on a feedback row. Every writer stores it trimmed and cut to 80 characters (`str(v, 80)`); the module read's Theme filter, the roadmap form's "Answers" choices and `buildCreates.feedbackLink` all group and match by that exact text, case included. So this write matches the same way: `from` is trimmed and must equal a stored theme exactly. "Exprot" and "exprot" are two themes, and renaming one leaves the other alone; a founder who wants them together merges one into the other. Case-insensitive matching was rejected because no reader groups that way, so a rename would have reached rows the Theme filter shows as a different theme.

### Rename and merge are one write

`PATCH /feedback/themes { project, from, to, merge? }`, for whoever `canAccessProject` lets write (an advisor reads only, 403).

- `to` is trimmed and cut to 80 like every theme. Empty is a 400 on `to`; the same as `from` is a 400; `from` empty is a 400 on `from`; a `from` no feedback row of this venture holds is a 404.
- When `to` is not a theme of the venture's feedback, the write is a **rename**.
- When it is, the write is a **merge**, and it needs `merge: true`. Without it the answer is a 409 `{ detail, field: 'to', merge_needed: true, feedback, roadmap_items }`, and nothing moves. The 409 is the dry run: the page asks with its own counts first, and a stale list still gets the Worker's counts before anything moves.
- One `DB.batch`: every `product_feedback` row of the venture with theme `from` (its `updated_by` and `updated_at` set), every `roadmap_okrs` row of the venture whose `feedback_theme` is `from` (so an item that answers the theme keeps answering it), and one activity row. Every statement is bound to `project_id`, so another venture's rows are never touched.
- The route is registered before `PATCH /feedback/:uid`, so `themes` is never read as a uid.

### Logging

One `activity_logs` row, `grow.product-improvement`, `entity_id` NULL (a module-level write, D690), action `grow_feedback_theme_renamed` or `grow_feedback_theme_merged`. The summary holds the counts only, for example "Theme renamed on 2 feedback rows and 1 roadmap item": a theme is free text the venture typed, often a customer's words, and every reader reads activity (as `setFeedbackTheme` logs "Theme set" without the text).

### The counts the page shows

The Product improvement read gains `parts.themes`, `[{ theme, feedback, roadmap_items }]` sorted by theme, for writers only; a reader gets no part, so no Rename is drawn for them. A failed count read sends `themes: null` (no Rename drawn) and never blanks the feedback table. No canvas covers this control (the issue checked); it is drawn as a plain part in the style of the durability checklist: each theme with its counts and Rename, an inline name field, and for a merge a confirmation that names both themes and how many feedback rows and roadmap items move.
