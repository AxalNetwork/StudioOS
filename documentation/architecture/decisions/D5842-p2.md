### 1. The choice

The founder previews an aggregate (part 1) and pins it with the hash the preview showed and the claim it backs:

`POST /api/cycles/raise/evidence/search-console/selections` `{ site_url, week_start, metric, search_type, snapshot_hash, claim_id }`

The value is never taken from the request. Part 1's preview runs again; it must still be `selectable` and still hash
to `snapshot_hash`, otherwise the refusal names why:

| Check | Refusal |
| --- | --- |
| A founder of this venture, in its company, not a support session | 403 `forbidden` / `support_session_refused` |
| `GOOGLE_SEARCH_CONSOLE_APPROVED=1` | 503 `search_console_unavailable` |
| The claim is this venture's | 404 `not_found` |
| The claim is one organic search can back (`searchConsoleMayBack`) | 409 `claim_refused` |
| The property is the venture's selection, with access, through an active connection switched on for its company | 409 `not_selected` / `revoked` |
| The week is stored in full and the figure is defined | 409 `not_recorded` / `incomplete` / `undefined` |
| The figure still hashes to what the founder saw, and no day was revised in between | 409 `changed` |
| No other claim already holds this aggregate | 409 `already_selected` |

The same aggregate for the same claim again returns the existing selection with `repeated: true` and writes nothing.
To back a second organic claim with the same week, the founder links the item with the existing claim link.

### 2. What the pin writes, in one batch

As D5837 §2, on a side table of its own (`raise_search_console_selections`):

1. **The selection,** its own copy of the aggregate: exact property, week, metric, unit, value, numerator and
   denominator, coverage, the seven days' revisions and fingerprints, and part 1's keyed snapshot hash. A trigger
   refuses any edit of these. One selection per aggregate is current at a time (partial unique index).
2. **A `raise_evidence_items` row** of kind `search-console-aggregate`, source `connector`, provider
   `google_search_console`, strength measured, unit `count` or `ratio`, **pinned and Private**. Its `source_ref` is
   `<selection uid>:<metric>`: `raise_evidence_items` has no revision column and is unique on its reference, so a
   corrected week cannot reuse part 1's reference; the metric in the reference tells the claim check which figure the
   item measures. Its fingerprint is built by the same code that reads the selection back (`searchConsoleCandidate`).
3. **Provenance** (`fill_provenance`, task `raise:search-console-evidence`), the batch's NOT NULL guard.
4. **The founder's link to the claim** (`how = 'founder'`) and the claim reset to be checked again; an activity row.

The insert is guarded in SQL as well: the founder gate, the property still selected with access, and the week's
revisions still the ones read.

### 3. Which claims it may back

Organic search activity is not paying customers, revenue or attributed conversions. Part 1's `searchConsoleMayBack`
allows only the organic-search keys of the item's own metric. It is now enforced at three places:

- the pin (and re-review) refuses another claim kind;
- the generic claim link (`linkClaim`) refuses it for a Search Console item (`claim_refused`), whoever links it;
- the claim check (`claimMayBack` in `raiseClaims.ts`) never lets a Search Console item back a readiness claim such
  as Traction proof, even through a link made some other way.

No existing claim kind was one organic search may back, so a founder had nothing to attach to. The claim parser now
reads three figures, by their words only, as every other figure: `organic_search_clicks` ("4,200 organic search
clicks"), `organic_search_impressions` and `organic_search_ctr` ("6.9% organic search CTR"). Only a pinned Search
Console aggregate of the same metric measures them (CTR stored as a ratio, stated as a percentage). A bare "clicks"
states nothing. They are not in the readiness narrative check (`NARRATIVE_CHECK_FIGURES` is unchanged).

### 4. Every read checks again

The `searchConsole` source query admits a selection only while all of these hold:

- it is current;
- its property is still the venture's selection with `access_state = 'ok'`;
- an active OAuth connection of the binding member is switched on for the venture's company;
- the founder who chose it is still active and owns the venture.

It returns the week's current revisions and fingerprints beside the pinned ones, so a correction changes the item's
fingerprint. Every shared read is `currentShared`, so a revoked, unselected or switched-off source leaves every shared
view at once. That is "revoked access withdraws what was shared". The founder still reads the pinned figure, with
source `revoked`, and a restored grant restores the same unchanged item.

### 5. Sharing: the existing rules, the aggregate and its context

Sharing beyond Private is the existing `PATCH /api/cycles/raise/evidence/items/:id`. The investor view, staff view,
deal summary, pack link and PDF read `sharedView`, which adds `search_console` for this kind:

- the metric and its words, unit, the week and its time zone, search type, data state and aggregation;
- coverage (days reported, days with no row) and the sentence that it is not customers, revenue or conversions;
- the value, numerator and denominator, only when shared After NDA. A Summary share carries none of them.

Never the property URL, a top page, a query, a fingerprint or another property. An item with no current selection is
not shown.

Like a ledger fact, it is a founder's choice, so `FOUNDER_CHOSEN_KINDS` keeps it out of:

- the hourly builder (`buildCandidates`);
- "confirm current" (`setSharing`), so a corrected week is never re-shared in place;
- the scoring pack (`evidencePack`), Eadwyn's pack draft (`packFacts`) and the deal-summary draft (`dealSummarySources`);
- an admin's evidence read and the narrative claims an admin reads.

### 6. Corrections, withdrawal and staleness

**A correction.** D5840 bumps a day's `source_revision`. The item reads `changed`, leaves every shared view and cannot
be confirmed in place. `GET /selections` shows part 1's recheck: `corrected`, the original value (rebuilt from the
revision history and verified against the pinned hash) beside the revised one, the corrected days, and
`requires_review`.

**Re-review** (`POST /selections/:uid/review` `{ snapshot_hash, claim_id? }`). The founder confirms the revised week by
the hash its preview shows. It writes a new selection (`replaces_id`) and a new Private item; the old selection becomes
`replaced`, its item unpinned and Private, and its founder links move to the new item (only to claims it may back).
The founder shares the revised figure again explicitly. A week not corrected is `not_changed`; one no longer stored in
full is `missing`; lost access is `revoked`.

**Withdrawal** (`POST /selections/:uid/withdraw`). The selection becomes `withdrawn`, the item unpinned and Private, its
claim links removed and those claims reset. An investor opening the shared claim afterwards sees nothing of it, and it
cannot be shared again: its source no longer offers it.

**Stale.** A week older than 90 days is `stale`, on the item and on the recheck.

**Deletion.** A venture's hard delete cascades the selections (D8530 inventory: `raise_search_console_selections`,
`cascade`). Rollback is reverting the Worker; the table is additive and an older Worker never reads it.

### 7. Why the writes are not one helper with D5837's

D5837 §6 suggested lifting its batch into a shared helper when the second source lands. The statements differ in the
table they guard on, and a table name cannot be a bound parameter, so a shared helper would interpolate SQL
(`check-sql-prepare`). The pin, re-review and withdrawal follow D5837's statements one for one in their own file; the
shared paths (the rule adapter, `setSharing`, `linkClaim`, `currentShared`, `sharedView`, the claim check) are reused,
not copied.
