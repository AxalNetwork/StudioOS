### 1. The prompt (`cloudflare-worker/src/services/lovable/prompt.ts`)

- **Two deterministic templates.** The same record always gives the same prompt.
  - `landingTestPrompt` (an experiment): a one-page landing page that tests the claim. It names the venture and its description, the claim with its code, the experiment, how it is tested and what counts as a pass.
  - `prototypePrompt` (Prototype / MVP): a clickable prototype of the venture's must-haves (`is_must_have = 1`, not scoped out), with the ship date.
- **Capped at 4,000 characters** (`LOVABLE_PROMPT_MAX`, D1068's). A draft that would be longer leaves out whole lines from the end of the list, keeps the closing line, and says how many lines it left out. A launch over the cap is refused with its length (422 `too_long`).
- **Dates in words** ("1 December 2026"). The shared check reads `2026-12-01` as a phone number, so a drafted prompt carried a date the launch then refused. The test pins that a drafted prompt passes its own check.
- **What never goes in.** No interview, transcript, quote, contact, email or phone store is read to build a prompt (`NEVER_INCLUDE`, held by a source scan). The dialog says "Interview names, quotes and contacts are never included."
- **The link** is `https://lovable.dev/#prompt=` and the prompt through `encodeURIComponent`, nothing else. There is no `autosubmit`: Lovable waits for the founder's send. The prompt rides in the fragment, which the browser never sends to a server.

**The privacy check** runs in the dialog's check and again at launch. It is:
- the shared check for text that leaves StudioOS (`lintForSend`, `public`: emails, phones, tax and bank numbers, card-like numbers, members' names);
- and this venture's interviewees' names (`discovery_interviews.interviewee_name`), matched case-insensitively as whole words. That is the only read of an interview store, and it is for refusing.

A finding names its kind once and never the words, as in "This prompt contains an email address. Remove it to continue."

### 2. The routes

Each cycle mounts the same four (`lovableHandler` in `services/lovable/launch.ts`):

| Route | Gate | What |
|---|---|---|
| `POST /api/cycles/validate/lovable/draft`, `/api/cycles/build/lovable/draft` | `canWrite` | `{ project_id, record }` → the prompt, its length, the cap, the Left out line, `cut` when lines were left out, the check, `last_opened_at` |
| `POST …/lovable/check` | `canWrite` | `{ project_id, prompt }` → `{ prompt_chars, check: { ok, line, findings } }` |
| `POST …/lovable/launch` | `canWrite`; a support session is 403 `support_session_refused` | `{ project_id, record, prompt }` → `{ url, handoff: { uid, opened_at } }` |
| `GET …/lovable/launches?project=` | `canReadBoard` | `{ launches: [{ record, opened_at, times }] }` |

- **The record:**
  - Validate takes `{ kind: 'experiment', id }`, an experiment of this venture; another venture's is 404.
  - Build takes `{ kind: 'prototype', id }`, the venture's own id; any other id is 400.
- **The launch** re-runs the check. A finding is 422 `pii_found` with the kinds and the check, and nothing is written. Otherwise one batch writes:
  - one `build_handoffs` row: `provider 'lovable'`; `module` `experiments` or `prototype-mvp`; `record_table` `hypothesis_experiments` or `projects`; `record_id`; `prompt_text` (the venture's team's only, as D1068 keeps it); `prompt_chars`; `text_hash` (SHA-256); `target 'lovable.dev'`; no plan items and no marker;
  - and one activity line, `lovable_opened`, under `validate.experiments` (the hypothesis) or `build.prototype-mvp`.
- **Logs** keep the cycle and the length, never the prompt.
- **A failure** that is not a refusal is 503 `lovable_unavailable` ("Nothing was opened").

### 3. The pages

- **LV1 and LV4, an experiment:**
  - The hypothesis record's Experiments rows (`services/records/validate.ts`) carry `lovable: { cycle, project_id, record, can_launch, opened_at }`. `can_launch` is true for a writer on a Planned row only.

  - `RecordView.jsx` draws "Build in Lovable" in the row, and "Opened in Lovable on 2026-10-22" in mono once opened. On the phone, both go below the group.
- **LV7, Prototype / MVP:**
  - The module read's `parts.lovable` is `{ state, project_id, record, can_launch, opened_at }`; an unreadable read says so.
  - "Build in Lovable" sits beside Add must-have: an Add entry may now be its own control (`{ key, node }`, `CycleModulePage.jsx`). On the phone it follows the first Add.
- **LV2 and LV3, the dialog** (`pages/cycles/lovable/BuildInLovable.jsx`):
  - the title "Build in Lovable" and Close;
  - "Lovable opens in a new tab with this prompt. Nothing is sent until you press send there. Building uses your own Lovable credits.";
  - the editable prompt, with `n / 4,000` in mono, red over the cap;
  - the Left out line;
  - the PII row: "No personal data found", or the finding in the destructive tint;
  - Cancel, and **Open in Lovable ↗**.
- **How the dialog checks.**
  - Each edit is checked by the Worker after a pause. Open stays disabled until the text on screen has passed.
  - An edit not yet checked, a check that could not run, an empty prompt and one over the cap each keep it disabled.
- **What Open does.**
  - It opens the new tab on the press, before the request, so the browser keeps it, then records the launch. The tab goes to the Worker's link with no `opener`.
  - A refusal closes the tab and shows the Worker's sentence and its check.
  - A browser that blocks the tab gets a link "open Lovable ↗" (`noopener noreferrer`).
  - The row then reads "Opened in Lovable on [date]" without a reload.
- **LV8a:** on the phone the dialog is a full-height sheet.
- **LV4's "Add the app's address"** is part 3's (#2948) and is not drawn here.
- **The client:** `frontend/src/lib/api/lovable.js` (`lovableApi.validate.*`, `lovableApi.build.*`), one line in `api.js` (D527).
