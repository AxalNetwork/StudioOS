## D931 — Admin › Community: the counts read (#2715)

- **Status:** S14, 2026-10-24. Part 1 of the Community overview (#2367, D930 §6).
- **Basis:** `origin/main` at `6c48aa50`. Worker paths are relative to `cloudflare-worker/src/`.
- **Migration:** 550, `job_postings.submitted_at` (reserved on #2711).
- **Why:** the canvas's CM1 draws period figures and charts that no read sums. D930 drew each of them as "Not read here yet" and named this part.

### The read: `GET /api/admin/community/overview?weeks=4|12|52`

`routes/admin_community.ts` serves it beside D932's activity read (#2716), on the router `index.ts` already mounts, and `services/communityOverview.ts` computes it.

- **Who:** `requireAdmin`, any admin. There is no HQ gate.
- **Query:** `weeks` is 4, 12 or 52, and 4 when absent. Any other value is a 400 `bad_weeks`, never a different window.
- **The window** is that many Monday weeks in UTC, from `weekAxis` as Insights draws them, ending with the current week to date. **The period before** is the same number of weeks immediately before it (`previousAxis`).
- **Counts only.** No member's name, email or account id is in the answer. The strings that travel are statuses, types, kinds, role keys, weeks, and a posting's title and company. A test walks the whole answer for a person's details.
- **Each block answers alone,** in D893's shape:
  - `{ available: true, … }` when read;
  - `{ available: false, unreadable: true, reason }` when its store failed, which is not a claim of zero;
  - `{ recorded: false, reason }` when no store holds it.

  `queue`, `participation_by_role` and `wellbeing` are made of parts that read different stores, so each part is its own block.
- **Answer:** `{ weeks, week_starts, current_week, window, previous, as_of, blocks }`.

**Rules within the blocks:**

- **Migration 550's wait.** A posting submitted before 550 has no `submitted_at`. It counts as waiting with `wait_not_recorded`, and is never Overdue or a wait of 0 hours.
- **`jobs.top`** lists the five postings with the most applications in the window, then by id. Its entries are title, company, status and count.
- **`jobs.days_open`** is `recorded: false`, because no store records when a posting was published.
- **Roles.** `mentor` is an advisor and `partner` is an Operating Partner. An application with no account is a guest's, and every other role is `other`. Explorers and guests are split, as the issue asks.
- **`circles.members_entered`** is the number an admin typed on each circle, summed and tagged `typed: true` (D930 §5). It is not a count of anyone.
- **`network`** counts `mentor` as `advisor`.
- **Sample experts.** The real experts are those whose `uid` does not start with `SAMPLE_EXPERT_UID_PREFIX`. An expert is `hidden` when `hidden_by_admin` is set, whatever else is true, and `inactive` when it is not hidden and `is_active` is 0. The rest are verified or unverified. The same prefix keeps sample experts' bookings out.
- **The check-in band never reads an answer.** It selects `COUNT(DISTINCT user_id)` over `day` in the window, and no other column. Nothing is decrypted, and `GET /api/wellbeing/aggregate` is not called.
  - Under seven members (`MIN_CHECKIN_COHORT`, the aggregate's floor) the band is withheld.
  - Otherwise the count is shown as its multiple of five (`at_least`) and the next one (`under`).

### The events parts are D918's

Every events figure is D918's (#2701): registrations, show-up, by type, by role, and the events queue's age. Community calls D918's events overview (`readOverview` in `services/adminEventsReads.ts`) once per read, for the same weeks, so Community and the Events desk cannot disagree.

- **Nothing is recomputed.** Each part is one of D918's blocks with its own answer. A block D918 could not read is unreadable here too, and a part never reads as zero.
- **Only the keys are Community's.**
  - `weekly` names its weeks `week`, as Community's other weekly series do. The weeks are the same Monday weeks.
  - `by_role` maps D918's buckets: `partner` to `operating_partner`, `exploring` to `explorer`, `admin` to `other`. A registration D918 cannot place (an account that is gone) stays `not_recorded`, apart from `other`.
- **Counts only.** D918's `show_up.recent` lists events by title, so it stays on the Events desk.
- **Not in D918's overview, so not here:** a count of confirmed registrations on its own. D918 counts seats (registered, confirmed and attended together).
- **The jobs and events queues share one Overdue,** 72 hours (D915), so `queue.events.overdue_after_hours` equals `queue.overdue_hours`.
- **History.** Until #2701 merged (#2733), these parts answered unreadable with `EVENTS_PENDING_REASON`. That reason is gone.

### Migration 550

- **The column.** `ALTER TABLE job_postings ADD COLUMN submitted_at TEXT`. Nothing is backfilled.
- **The write.** `submitForReview` (`services/jobBoardCommon.ts`, called by `POST /api/jobs/:id/submit-review`) sets it to `datetime('now')` each time a posting enters `pending_review`.
- **Dev databases.** `ensureJobBoardSchema` carries the same column for development and preview databases, as it does for 443, 462 and 507.

### The client

`communityApi.overview({ weeks })` is in `frontend/src/lib/api/community.js`, re-exported by one line in `api.js` (D527). It draws nothing; part 3 (#2717) does.
