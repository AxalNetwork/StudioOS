### 1. Where a candidate's runs come from

D5973 classified candidates from the all-workflow run listing. D6678 showed that listing stops at 1,000 runs, about the last three and a half hours of a busy day, and gave `ci.yml`'s `merge_group` runs a listing of their own. A candidate also needs the `merge_group` runs of `gitleaks.yml` and `migration-immutability.yml` (`QUEUE_WORKFLOWS`: both run on `merge_group` and report a required check). The capped listing holds those only for its own span, so the earlier candidates of the day would all have read as missing evidence. The collector now lists each queue workflow's `merge_group` runs the way D6678 lists `ci.yml`'s, `BUDGET.queuePages` (5) pages each.

- Every listing's rows are one object per run id: a run both listings hold is the same object, so jobs read once show in both.
- `candidateRows` reads `unionRuns(runs, queue runs)`: one row per id, prior attempts left out, a row with jobs preferred. `report()`'s default rows do the same with `queueRuns`.
- `queueRuns` passed to `report()` stays `ci.yml`'s listing only, so D6678's rows (candidate start wait, queue CI runs per PR) count what they counted on main.
- Honesty is unchanged: a candidate is `sampled` only when every queue workflow's run is present with jobs and every required check is found. A listing that hits its page limit adds a note to the comment, and its earliest candidates read as `missing-evidence (required jobs not sampled)`, never a guessed class.

### 2. The job sample (`jobSample`)

D6678 sampled up to 74 `ci.yml` queue runs, those in the capped listing first. D5973 sampled 32 head SHAs with all three queue workflows of a SHA together. Taking 74 SHAs whole would cost 222 job reads; taking 32 SHAs only would cut D6678's start-wait sample. The combined rule, in the order the collector reads:

1. Up to `wholeShas` (32) head SHAs, all queue workflows of each together. SHAs whose `ci.yml` queue run the capped listing holds come first ("Queue stalled" needs a job sample for each of those, as in D6678), then SHAs evenly spaced over the rest of the day.
2. More `ci.yml` queue runs, listed ones first, then evenly spaced, until `queueCiRuns` (74) `ci.yml` runs are in. Their candidates read as missing evidence unless a run of theirs shows a failure, a cancellation or a merge.
3. `perEvent` (12) runs each of `pull_request`, `push` and other events; "other" leaves out every queue workflow's `merge_group` run, which steps 1 and 2 cover.

### 3. One request plan

`BUDGET` in `ciScorecard.mjs` is the only source of numbers; the collector states none (tested). Main's `cap = 320` and `budget = { jobs: 120, prs: 280 }` and D5973's cap of 200 are replaced by:

`{ cap: 385, runPages: 10, queuePages: 5, rules: 1, wholeShas: 32, queueCiRuns: 74, perEvent: 12, jobsUntil: 210, prPages: 2, timelinePages: 3, timelinesUntil: 370, commentPages: 10, writes: 1 }`

`requestPlan()` computes, and the test holds:

- **Listings:** 10 run pages + 3 queue workflows × 5 pages + 1 rules read = 26.
- **Job sample:** 32 × 3 + (74 − 32) + 3 × 12 = 174 job reads. Room before `jobsUntil`: 210 − 26 = 184, so the whole sample fits and 10 reads are left for prior attempts. A job step starts only below 210 and its prior-attempt read only below 210, so the phase ends at 210 at most.
- **Timelines:** 370 − 210 − 2 PR-list pages = 158 for timelines (up to 3 pages each) and one head-SHA listing per merged PR, D6678's room (280 − 120 − 2) kept.
- **Worst case:** a timeline step starts at 369 and takes 3 pages and 1 head listing (373), then the comment's 10 pages and 1 write: **384**, under the cap of 385.

At 384 sequential GETs once a day this is under two fifths of the documented 1,000 an hour for `GITHUB_TOKEN`.
