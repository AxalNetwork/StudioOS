- **Status:** built 2026-11-27 for #5343, batch 5. Part 5 of #5343 (`D5343.md` holds the rule and batches 1 to 3; batch 4, #7554, is recorded in `documentation/audits/RUNTIME_DDL_2026-11-07.md`). Worker only: no migration, no route change, no UI.

They move too, written out as literal statements so the schema guards read each one.
- **Test floor.** `runtime_ddl_4568.test.ts` asserted at least 300 blind ALTERs of declared columns, a floor this batch passes below. It now asserts that every blind ALTER left is of a declared column, which holds for every later batch.

### Why these ten

The rule is the one in `D5343.md`: route the statements through `runSchemaBootstrap`, never mark a binding ready after a genuine failure, and lower the baseline. The order there is by traffic. The request-path middleware and the investor bootstrap went first. What is left is mostly route files with large, mixed bootstraps (`wellbeing.ts` 42, `projects.ts` 16, `decks.ts` 13) whose callers each need checking. This batch takes the service bootstraps whose failure path is already settled: each one either has a catch that logs and leaves the binding unready, or already throws. So no caller changes behaviour except by being retried. These were ranked from the code, not from production query insights, which agents cannot read.

Two files on the cheap end were left for a later batch on purpose:
- `services/referralCommissions.ts`: a refund clawback that answered `no_commission` after a swallowed failure would answer `error` instead. That is an accounting outcome, outside a bootstrap-only change.
- `services/sanctions.ts`: making the pairwise-NDA bootstrap throw would also make `screenUser` throw on a database without `pairwise_ndas`, and the Trust Center routes would need a 503.
