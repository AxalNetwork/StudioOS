## D6695 — Formation case requests: asks tied to evidence, notes by visibility, and the founder's timeline (#6695)

- **Status:** built for #6695, 2026-11-22. Part of #6680 (plan key E10).
- **Depends on:** #6686 (E6, the case store), #6694 (E9, filings and case documents), both merged.
- **Migration:** `cloudflare-worker/sql/migrations/202611220347_6695_formation_case_requests.sql`. One new table; no existing table changes shape.
- **Service:** `cloudflare-worker/src/services/formationRequests.ts`, the only writer of `formation_case_requests`.
- **Route:** `cloudflare-worker/src/routes/formation_requests.ts` at `/api/formation/case-requests` (self-mounting). Client: `frontend/src/lib/api/formationRequests.js`.
- **Test:** `cloudflare-worker/test/formation_requests_6695.test.ts`, 6 tests, one per Done-when item.

### 1. Why

HQ or a partner had no way to ask a founder for a document or an approval and keep the answer on the case. Member messaging was retired. A request is not chat: each one asks for one thing, and its answer is evidence the case keeps.

### 2. The table

`formation_case_requests`: the case; who asked (`asked_by_party` hq, partner or counsel, and `asked_by_user_id`); who is asked (`asked_of_party` founder, hq, partner or counsel, and `asked_of_user_id`, the case's owner for the founder); `kind` document, answer, signature, identity, payment or approval; `title`, `body`, `due_on`; `state` open, answered, accepted, returned or cancelled; `answer_text`, `answer_document_id`, `partner_reference`, `bound_sha256`, `filing_id`, `return_reason`; and `prior_waiting_on` with `prior_case_revision` (section 4). Each change adds one to `revision` and is written only from the state and revision read.

The store holds three rules too: an identity request has no `answer_document_id`; only an approval has `bound_sha256` or `filing_id`, and an approval always has `bound_sha256`; a returned request has a reason.

### 3. Kinds

- **document, signature.** Answered with a `documents` row of the case's venture, company, or one the founder uploaded. The route takes no bytes: the file is uploaded through the classified file store first (`services/recordStore.ts`, for example `POST /api/company/:uid/documents`). The answer puts the document on the case (`formation_case_documents`, class `evidence`) in the same batch, and notifies the asker.
- **identity.** Takes no file and no document, from the route, the service or a raw write (owner decision 13, S1). It records that the partner asked; the partner accepts it with its own reference for the check. The founder's read does not return that reference.
- **approval.** Bound to a SHA-256 when opened. For a filing pack it names the filing and must equal the pack's hash at that moment. Answering it with the bound hash approves the pack through `approvePack` (D6694), which sets `formation_filings.founder_approved_at` and records the request id; the request goes straight to accepted. If the pack's hash changed since the request was opened, the answer is refused `pack_changed`.
- **answer, payment.** Text.

### 4. waiting_on

While a request is active (open, answered, returned) the case waits on the newest active one: the party asked while it is open or returned, the asker once it is answered. Every request in one window of active requests records the case's `waiting_on` from before the first of them. When the last one closes (accepted or cancelled) the case gets that value back. If the case changed stage in between (its revision moved), the case gets the new stage's own waiting_on (`stageWaitingOn`, exported from `formationCase.ts`), or the prior value when the stage names none. A request change does not bump the case revision, so it never races a stage transition's guard.

### 5. Notes and the timeline

A note is a `formation_case_events` row of kind `note`, visibility `all`, `hq_partner` or `hq_only`. HQ writes any; a partner or counsel `all` or `hq_partner`; the founder `all`. Request events carry `all` when asked of the founder, `hq_partner` when asked of a partner, else `hq_only`.

The timeline read filters by visibility in the SQL: the founder `all` only, a partner `all` and `hq_partner`, HQ every row. Only a note's text and what a request event names (uid, kind, title, reason) leave the store.

### 6. Logging and notices

Every write by HQ, a partner or counsel (open, accept, return, cancel, note) is recorded with `logAdminAction` and on the timeline. `notify.ts` gains the `formation` category (not critical) and `FORMATION_NOTIFY_TYPES`: request opened (to the person asked), request answered (to the asker), stage changed, registry question and registered (`notifyCaseStage`, to the founder).

HQ's and partners' write routes (#6698, #6711) call this service; until they merge the service is reached only from tests. `notifyCaseStage` has no caller yet: the stage writers that call it are those routes'. Checking that a partner actor is the case's partner is the partner route's (#6711).
