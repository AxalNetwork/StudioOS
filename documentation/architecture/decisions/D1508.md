## D1508 — Deck images leave R2 when nothing references them; the deck retention inventory (deck v2 A15)

- **Status:** built 2026-11-02 (#3759, deck v2 A15, part of #3716).
- **Basis:** `origin/main` at `d13839c4a3`.
- **Scope:** the issue as written; S1's final canvas revision changed nothing.
- **Migration:** 722 (`722_deck_r2_tombstones.sql`): the tombstone table, `deck_images.discarded_at` and the view `deck_images_named`.
- **Owner decision W** (retention periods for generated assets) is pending counsel. The periods here are S1's §5.9.5 pick until the owner rules.

### Why

Discard only flipped `deck_images.state`, and nothing ever removed a proposal nobody kept. Every discarded or unkept image stayed in R2 for good. The one-click path's whole-deck image passes multiply those objects. And nothing listed which deck stores exist or how their rows leave.

### 1. The daily cleanup

`services/decks/imageSweep.ts` `sweepDeckImages` runs once a day at 03:00 UTC, from the existing daily cleanup (`models/jobs.ts` `Jobs.cleanup`, which the cron calls at 03:00). Its own failure never stops the rest of that cleanup. Every tier runs it over its own images.

- **What goes:**
  - a **discarded** image 24 hours after Discard (`deck_images.discarded_at`, new in 722 and stamped by `POST /api/decks/images/:uid/discard`);
  - a **proposal** nobody kept, 14 days after it was made.
  - A kept image never goes here.
- **Nothing named goes.** The view `deck_images_named` (migration 722) holds the one copy of the reference rule. An image is named when its uid appears in any store of its venture that can hold a card:
  - every saved version (`pitch_decks.slides` and `theme_json`);
  - every card draft (`pitch_deck_cards.json`);
  - every proposed deck (`pitch_deck_proposals.slides`);
  - every derivative (`deck_derivatives.slides`).

  A slide names an image by its file URL or its `image_id`, and both hold the uid. If the check can't be read, the image stays.
- **The claim.** For each candidate, one D1 batch writes the tombstone and deletes the row. Both statements read `deck_images_named` again and check the state the run read. So a save that names the image after the first check keeps it, and a Keep pressed in between finds no row, never a row whose file is gone. Only when the delete took effect does the R2 object go.
- **Tombstones.** `deck_r2_tombstones(key, project_id, bytes, reason, deleted_at)`, with `reason` `discarded` or `unkept_proposal`, gone with its venture. An R2 delete that fails is counted, and its tombstone names the key for an operator.
- **Storage credit.** Deleting the row is the credit. Deck images are not yet an area of `storageUsage.ts`, so today no measured figure changes. When they are counted, they will be counted from these rows.
- **Limits.** At most 500 objects deleted per run, oldest first. A run scans at most 2,000 candidates, so images that stay referenced cannot starve the rest. Logs carry counts only.
- **Rows from before 722.** A row discarded before 722 has no discard time, so the migration gives it the migration's time, and it goes a day after deploy.

### 2. The retention inventory

`documentation/operations/DATA_RETENTION.md` has one row per deck store: what it holds, when its rows leave, and the R2 objects it names. It also lists the gaps it found:
- several stores have no cascade;
- a venture's deletion removes its image rows but not their R2 objects.

`scripts/check-deck-retention.mjs` runs in `npm run test:guards` and fails when:
- a table whose name starts `deck_` or `pitch_deck` is left by the migrations with no row;
- a row names a table that no longer exists;
- a deck table created from migration 722 on has no `ON DELETE CASCADE`.

The two made before this check (`deck_exports`, `deck_grants`) are on record. It replays the schema as a fresh build does: the baseline, then each migration after the cutoff, following renames and drops.
