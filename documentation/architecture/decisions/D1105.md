### 1. Migration 596: where each file came from

`data_room_files` gains two columns.

- **`source_kind`** is one of three words. It is NOT NULL, defaults to `document`, and a CHECK refuses any other word.
  - `document`: an upload, or a paper the platform made and filed there (the cap table snapshot).
  - `connector`: a file a connected service delivered (a Mercury statement).
  - `signed`: a signed copy filed from e-sign. No writer files one yet. The word is reserved so that writer needs no migration.
- **`source_ref`** names the source within its kind, never an account, key or token:
  - `mercury` for a Mercury statement;
  - `cap_table` for the snapshot;
  - NULL for an upload.
- **The backfill.** Every file a Mercury statement landed as (its proposal's `local_table` and `local_id`, migration 520) becomes `connector` / `mercury`. Every other existing file stays `document`.

The founder's room read (`GET /:projectUid`) returns both on each file, and so do the checklist's files.

### 2. The activity read: `GET /:projectUid/activity?from&to&investor&action&page`

The owner and an accepted co-founder may read it. Anyone else gets 404, as every founder route answers, and an admin uses the audited support read.

- **The period** is whole UTC days, `from` and `to` included, at most 366 days. With none named it is the 30 days to today.
- **The answer has four parts:**
  - **`daily`**: every day of the period, with `opened`, `downloaded` and `blocked`.
  - **`totals`** and **`previous`**: the period's figures, and those of the period before. That is the same number of days, ending the day before `from`.
  - **`investors`**: one row per reader, with their three figures and `last_at`, the busiest first.
  - **`log`**: fifty rows to a page, newest first, with `total` and `pages`. Each row has its action, its reader and its file.
- **A refusal is never counted as an open.** `blocked` (a download the NDA gate refused, D374) is its own figure everywhere: the days, the totals, the investors, the log and the CSV.
- **The filters:**
  - **`investor`** (a grant's uid) narrows everything to that reader. A uid that is not one of this venture's grants is 404 `unknown_investor`.
  - **`action`** (`open_room`, `download`, `blocked`) narrows the log and the CSV only, so the figures stay comparable.
- **Bad queries** answer 400, with `bad_from`, `bad_to`, `bad_period`, `bad_action` or `bad_page`.
- **Names and emails appear only for this venture's own grants.** `users` is joined only where the reader holds one of the venture's grants. A logged reader with no grant here keeps their row and their figures, with no name and no email. That covers a grant since deleted, or an advisor read logged by `research.ts`.
- **A day or a reader with no row reads 0.** That is a count of a table this route owns, as `week` already reads it (D374), not an unknown.

### 3. The CSV: `GET /:projectUid/activity.csv`

- **The rows:** the same filters and the same rows as the log, newest first, with no paging. Its columns are When (UTC), What, Investor, Email and File.
- **The words:** a refusal reads "Blocked: NDA not signed", never "Opened the room".
- **Names:** they follow the rule above.
- **Cells:** every cell goes through `capTableRegister.csvCell`, so a name a spreadsheet would run as a formula is prefixed with an apostrophe.
- **More than 10,000 rows** is 413 `too_many_rows`, asking for a shorter period, an investor or an action. The file is never cut short in silence.

### 4. The checklist: `GET /:projectUid/checklist`

The owner and a co-founder may read it. For each of `DILIGENCE_CHECKLIST`'s twelve items, in its order, it gives:
- **its files** (`checklist_item`): each with its visibility, tier, source, and `grants_that_open`, the number of grants in force that can open it;
- **its state:**
  - `open`: at least one file is openable;
  - `no_one_can_open`: files answer it, but no grant can open any of them;
  - `no_file`;
- **a reason** when it is not `open`:
  - no file;
  - only files private to the founder;
  - the room shared with no one;
  - or no grant admitted, by tier, end date, folders or NDA.

`grants_in_force` and `totals` (items, answered, openable) are counted beside the items.

**Whether a grant can open a file** is the investor read's own rule, so the checklist cannot promise what the room refuses:
- **In force:** a grant counts while it is active and its end date has not passed.
- **Tier, expiry and folders:** it is admitted by `tierAdmits`, with the grant's committed status and its folder scope (D691, D1103).
- **The NDA:** an `nda` file then needs the investor's NDA signed with the venture's founder.

This is the page's `accessNow` rule plus D1103's folder scope, which the investor read already applies. A file only a `nobody` tier answers is "no one can open it".
