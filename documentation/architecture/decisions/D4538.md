## D4538 — Company extensions are forks with provenance, and discovery is an eligibility gate before any ranking (#4538)

#4538 is Session 10 of #4528, taken by slot S17 at the owner's request. This is S1's first step: the documents only. There is no migration, no change to a production record, and nothing auto-attaches. Ranking that uses evidence waits on #4533 (rollback still open), #4536 (analytics), #4667 (inputs) and #4588 (first-ten qualification).

The two capabilities are kept apart:
- **discovery** ranks skills an agent can already run;
- **extension** creates a new company-owned skill from an HQ one, with its source recorded.

The recommendation contract is `documentation/architecture/SKILL_DISCOVERY_CONTRACT.md`. The labelled query set is `documentation/architecture/skill-discovery/queries.v1.json`.

### What exists today (read on main at `4c24f3d6bf`)

- **One table, two scopes.** `agent_skills` (migration 759) holds both scopes, keyed `(scope, IFNULL(company_id, 0), slug)`. A company skill is `scope = 'company'` with its `company_id`. It is a standalone record: no column names an HQ source.
- **Versions are immutable.** `agent_skill_versions` keeps each published version's `skill_md` and fields. An agent pins one exact version in `agent_skill_links (agent_id, skill_id, version)`.
- **A company can already copy an HQ skill, without provenance.** `POST /api/teams/skills` accepts `{ scope: 'company', company, skill_md }`, and a published version's `skill_md` is what export and copy give. The result is an ordinary company draft. Nothing records which HQ skill or version it came from, so "base update available" cannot be said about it.
- **Attach is gated.** `attachCheck` (`services/agents/skillLinks.ts`) refuses:
  - another company's skill (`not_found`);
  - an unpublished version (`version_not_published`);
  - a retired skill (`skill_retired`);
  - an HQ suspension (`skill_suspended`, D4161, D4534);
  - a role the version does not list (`role_mismatch`);
  - a tool outside the agent's `tool_grants_json` (`tool_not_approved`).

  The run gate applies the same rules.
- **Moderation, not authorship.** HQ moderates a company skill (D4161, `admin_company_skills.ts`) and never writes it. A company's editors (`canEditAsMember`) write their own skills.

### The decision: fork with provenance

| | Fork with provenance | Overlay / inheritance |
|---|---|---|
| What a company holds | A separate `scope = 'company'` skill, created from one HQ **immutable version**, with `based_on_skill_uid` and `based_on_version` recorded | A reference to the HQ base plus a stored set of overrides, merged when read |
| What an agent runs | The company skill's own published version: one `skill_md`, exactly as it is pinned today | A merge of the base version and the overlay, computed at run time |
| Schema change | Additive: three nullable columns on `agent_skills` and one on `agent_skill_versions` (below). Every existing row reads "not an extension" | A new overlay table; a merge rule for every field; pins that name two versions (base and overlay); release evidence, moderation and costs computed over the merge |
| Run path, pins, release evidence (D4533), moderation (D4161), costs (D4121) | Unchanged: the extension is an ordinary company skill | Each must learn to read a merge. A new HQ version would change what a pinned company agent runs unless the base is pinned too |
| Tool permissions | Checked as today, by `attachCheck` on the company skill's own tools. A fork can narrow them, and can never inherit beyond the agent's grants | Needs a rule that an overlay cannot widen the base's tools, enforced on every merge |
| HQ update | "Base update available" is a comparison between `based_on_version` and the HQ skill's `current_version`. Nothing is rewritten | Silent by construction unless the base is pinned. Pinning the base makes it a fork with extra steps |
| Conflict handling | Explicit: a three-way compare (old base, new base, company version) the company resolves into a new draft | Implicit at merge time; a conflict is hard to show and easy to get wrong |
| Existing company skills | Stay standalone; their provenance columns stay NULL | Same, but two kinds of company skill would run through two paths |

**Recommended: fork with provenance.** It is the smallest model that fits the current schema and authoring workflow:
- the copy already exists (`POST /skills` with `skill_md`), and the fork records where it came from;
- an executed skill stays one immutable `skill_md`, so the run gate, pins, release evidence, moderation and costs need no change;
- it never lets an HQ change reach a company agent silently.

Overlay is not built.

### The extension contract (for the implementing slice; no migration in this one)

**Lineage, proposed additive columns:**
- `agent_skills`:
  - `based_on_skill_uid TEXT` (the HQ skill's uid);
  - `based_on_version INTEGER` (that skill's immutable version);
  - `fork_reason TEXT` (1 to 300 characters, required when the other two are set).
- `agent_skill_versions.based_on_version INTEGER`: the base each published company version was built from, so history shows which base every version followed.

**Constraints:**
- The three lineage columns are all NULL or all set.
- When they are set, `scope = 'company'`.
- `based_on_version >= 1`, and the HQ version must exist when the fork is created.
- Existing rows stay NULL: they are standalone and are never converted.

**Identity:**
- A fork gets its own uid and a company-scoped slug (the existing unique index applies).
- A company may fork the same HQ skill more than once, with different slugs and reasons.

**Index:** `(based_on_skill_uid, company_id)` for "which of this company's skills are based on this HQ skill".

**Who:**
- A company's editors fork, edit and publish their extension, as for any company skill (`canEditAsMember`).
- HQ sees lineage metadata under the existing moderation policy and never edits company content.
- Another company never sees it.
- The creator and time are the existing `created_by` and `created_at`.

**Fields a company may change:** purpose, steps, examples, taxonomy tags, roles and output kind, all validated by `checkDraft` as for any company skill.

**Tools:**
- An extension's tools may only be the base version's tools or fewer.
- A tool the base did not have is refused at fork and at edit (`tool_not_in_base`).
- Agents' grants still decide attach and run (`attachCheck`, unchanged), so a fork can never widen what an agent runs.

**Base update:**
- When the HQ skill's `current_version` is newer than `based_on_version`, the company skill reads "base update available (v{n} → v{m})".
- Nothing changes until a company editor acts. They can either:
  - **rebase**: a new company draft built from a three-way compare of the old base, the new base and their latest version, with each conflicting field shown and resolved by them;
  - **fork again**: a new extension from the new base.
- Either way the company's earlier versions stay as they were, and pinned agents keep their pinned version.

**HQ retirement:**
- A base that HQ retires does not retire the extension; it reads "base retired".
- A base suspended by HQ does not suspend the extension. The extension is moderated on its own versions (D4161).

**Runs:** every run uses the extension's own pinned, immutable version and the agent's runtime grants, exactly as for any company skill.

### Discovery: the decision in brief

Discovery is a **hard eligibility gate**, then ranking. The gate reuses `attachCheck`'s codes and adds three of its own:
- `output_mismatch`: the request asks for an output kind the skill does not produce;
- `input_unavailable`: #4667 says the skill's inputs cannot be read for this scope;
- `not_runnable`: #4534's execution contract refuses it.

A skill that fails the gate is never returned as a candidate. It may be returned in `blocked`, with its code, so an operator can see why ("this skill needs `mercury.read`").

Ranking runs only over eligible skills, in the order the issue sets: role and taxonomy fit, task relevance, input/output compatibility, then quality and operational evidence. The evidence stages report "Not recorded" until #4533, #4536 and #4588 supply them, and never stand in for a measure.

Popularity is never quality. The response can be "no suitable skill", and nothing attaches without the existing attach action. The full contract is `SKILL_DISCOVERY_CONTRACT.md`.

### The labelled query set

`skill-discovery/queries.v1.json` has 15 scenarios on real library skills, covering:
- clear tasks;
- an ambiguous request;
- an output-kind constraint;
- a role mismatch and a missing tool;
- another company's skill and a retired skill (inline fixtures);
- tasks no skill should serve, including a write the read-only skills cannot do.

Each scenario names the agent (role, scope and granted tools) and labels:
- `relevant`: best first;
- `acceptable`;
- `must_not_return`, each with its gate code.

`cloudflare-worker/test/skill_discovery_queries_4538.test.ts` holds the set to the library and to the gate:
- every named skill exists;
- every `relevant` or `acceptable` skill passes the gate for its scenario's agent;
- every `must_not_return` skill fails it with exactly the stated code;
- an abstention names no relevant skill.

So a label can never ask the ranker to return a skill the agent cannot run. Precision@k, recall, rank quality, the ineligible-recommendation rate (must be zero) and abstention quality are measured against this set once a ranker exists. Human relevance judgements stay in the labels, apart from the deterministic gate.
