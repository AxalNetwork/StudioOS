### 1. What lands where (`services/notion/build.ts`)

| Module | Lands as | Store | From the founder's field map |
|---|---|---|---|
| Product roadmap | fact | `roadmap_okrs` | Objective → `objective`. Status → Now, Next, Later or Done (`kanban_status`). Quarter → `quarter`. - **A new row** gets defaults:
  - a roadmap item starts in **Next** when its status is unmapped or outside the map;
  - a must-have starts as **High** and **Backlog**, as Add must-have's does.

  Defaults are not guesses: a value outside the map is never forced onto one.
- **An update** writes only what the founder mapped. A field Notion leaves empty, or a value outside the map, keeps the row's own value (`COALESCE`). That includes a lane or status the founder set by hand.
- **Activity rows:**
  - `notion_roadmap_item_created` on `build.product-roadmap`;
  - `notion_must_have_created` on `build.prototype-mvp`;
  - `notion_design_note_accepted` on `build.solution-design`.

  None holds a title or page text.
- **Delete** goes through the writer's `remove`, scoped to the venture. The ledger keeps the item with no row, so it stays deleted (D1086).
- **Registration:** the writers and the acceptor register with `sync.ts` at import, from `index.ts`.
- **`NOTION_FEEDS`** gains `build_roadmap`, `build_must_haves` and `build_specs`. The registry's `pulls` and `feeds` read them. D1085's pin, which held the list empty, now holds `feeds` to the list's modules.

### 2. One owner per row

The engine (`sync.ts`, D1086) enforces it, and this part's writers rely on it:
- A fact is written new, or updated only while this connection's ledger row links it **and** `fedOwnership.ts` names this connection the owner.
- A row GitHub or Google feeds is `owned_elsewhere` and never written, even when a stale Notion ledger row points at it.
- A hand-entered row has no ledger row, so nothing of Notion's can name it.

### 3. The pages

`buildParts.jsx`'s three `notion` lines draw the shared `FromNotion` (`section="build"`, the module's key), last on Solution design, Prototype / MVP and Product roadmap, each inside its `PartBoundary`, anchored at `#from-notion`. `FromNotion` reads its own data (`GET /api/cycles/build/notion`) and draws the states D1086 built.

### 4. A look-alike waits as "Link to [existing]?" (migration 644)

This is #2405 § Module map, rule 4: a duplicate is a proposal to link, never a new row.

- **Migration 644** rebuilds `notion_proposals` with one more kind, `fact_link`. It copies every row as it is and keeps the unique key and the index. SQLite cannot widen a CHECK in place.
- **The engine** (`sync.ts`): a writer may offer `lookAlike`. When a new Notion row has one, the row is not written. It waits as a `fact_link` proposal keyed by the Notion row id, with the matched row in `payload_json` (`local_table`, `local_id`, `existing`, `fed_by`) and a fingerprint of the Notion title, the matched id and the owner. As every proposal does, a dismissed one stays dismissed until one of those changes.
- **Who is a look-alike:** the venture's item with the same title, ignoring case and outer or repeated spaces. Neither writer counts an item this connection already links (Notion's own rows). A must-have only matches a must-have, never a Solution design feature.
- **Fed by another connection:** when GitHub, Google or any other connection feeds the match, `fed_by` names it. The proposal reads "Already fed by GitHub" with Dismiss only, and Notion's row is not imported.
- **Accept** (`factLinkAcceptor`) gives the matched row this connection's ledger link as a `notion_fact`, so the next sync updates it as Notion's, and From Notion lists and deletes it like any fact. Nothing new is written.
  - A row gone since, or one another connection feeds (`fedOwnership.canLink`), is refused with 403 and nothing is decided.
  - The activity row is `notion_linked` on the item.
- **The read** (`GET /api/cycles/:section/notion`) gives a `fact_link` proposal its `link: { existing, fed_by }`.
- **The page:** From Notion draws `NotionLinks` on a fact module.
  - Linkable: "Link to “Checkout v2”?", then "“checkout v2” in Notion looks like “Checkout v2”, already in Product roadmap. Linking them lets Notion's changes update it; nothing new is added.", with Link and Dismiss.
  - Fed elsewhere: "Already fed by GitHub", with Dismiss only.
  - Dismissed: "1 look-alike stays out until it changes in Notion."
