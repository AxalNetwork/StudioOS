## D5815 — The Teams recorder's deployment matrix is checked offline, by presence, on every PR (#5815)

- **Status:** built 2026-11-14 by S19 for #5815, part of #3709. Partial: the
  positive path waits on #5812 (the Teams page driver) and #5675 (the isolated
  preview callback receipt).
- **Number:** D5815 is this issue's number (D4106).
- **Code:** `scripts/lib/meetingBotTeamsMatrix.mjs`, `scripts/check-meeting-bot-teams.mjs`
  (in `npm run test:guards`).
- **Tests:** `scripts/lib/meetingBotTeamsMatrix.test.mjs` (in `npm run test:retention`).
- **Runbook:** `documentation/operations/MEETING_BOT.md` §4b.

### 1. Teams adds no deployment of its own

Teams runs in the same `studioos-meeting-bot` and `studioos-meeting-bot-preview`
hosts, image and Container applications as Meet and Zoom. What it adds is the
`MEETING_BOT_TEAMS` switch (D1451) and, with #5812, a driver inside the one
image. So the matrix checks the shared deployment and the switch, and no new
binding, var or workflow step is introduced.

### 2. What the check reads, and what it never prints

It reads the two Wrangler configs, `meeting-bot-deploy.yml`, the Dockerfile,
the bot's `package.json` and `meeting-bot/worker/container.ts`, and reports one
row per capability and environment as `pass` or `FAIL`. It never prints an
origin, a bucket, a version or a script name, so its output may be pasted on a
public issue. It cannot read a secret, so secrets are checked by presence with
`wrangler secret list` (runbook §4b) and confirmed live by §4a row 1.

### 3. A switch value outside its exact set fails

The code reads anything but `on` as off. A typo (`On`, `true`) would therefore
pass every functional test while silently not doing what its author meant, so
the matrix requires `MEETING_BOT` to be `off`/`canary`/`on` and
`MEETING_BOT_TEAMS` to be `off`/`on`, and fails Teams `on` beside a bot `off`.
It does not pin which value either switch holds: turning Teams on is the
owner's separate rollout issue.

### 4. What stays UNVERIFIED

The Teams driver fixture in the packaged image, host → signed callback →
upload → assembly with a synthetic session, and live corrupted, replayed and
wrong-environment deliveries. They run against the deployed preview once #5812
and #5675 land; their results go in the runbook's stage table as states and
codes only.
