## D4117 — The 16 agent personas: a fixed identity on team agents, capability from skills (#4117)

- **Status:** built by S03, 2026-11-02 (#4117, Roster R1 of #4116).
- **Number:** D4117 is this issue's number (D4106's rule).
- **Builds on:**
  - D1496, the team agent registry (migration 712, `services/agents/catalogue.ts`);
  - D1612, the skill library and agent skills (`agent_skill_links`, `agent_skill_versions.roles_json`);
  - the Axal behavioral values of `services/axalFit.ts`.
- **Spec:** the issue body as revised by S1's owner notes on #4117 and #4116, all of 2026-11-02. Where they differ, the latest wins:
  - single sci-fi names;
  - values are `FIT_V2_VALUES`;
  - no philosophy and no trade-offs.

### The question

Picking an agent should show a named character with fixed values, not "CTO" or "CFO". What an agent can do should come from the skills it is given. How is that added to the registry without breaking the agents that already exist?

### What was decided

**A code catalogue** (`services/agents/personas.ts`), like `catalogue.ts`. There is no table, and personas are immutable: everything is frozen, and no route edits one. Each of the 16 has:
- `key` and a single `name`; there is no family name;
- `gender`;
- `tagline`, `story` (the futurist-medieval Hall of the Trefoil revision on #4116) and a plain business `goal`;
- `personality` (from #4116's body);
- `risk`, 1 to 5 (most cautious, cautious, balanced, bold, boldest);
- `values`, `natural_fit` and `avatar` (`/agents/<key>.webp`).

The names live only here, so a trademark swap is one line plus its image.

Solen's last sentence is the owner's rewrite: "…and he is happiest when the kind choice is also the sound one."

**Values are the platform's own.** They are the six `FIT_V2_VALUES` (`integrity`, `stewardship`, `curiosity`, `resilience`, `collaboration`, `ambition`), imported, never copied, so people and agents are described in one language. #4116 fixes each agent's top three:
- the top three score 0.92, 0.84 and 0.76, in that order;
- the other three score 0.58, 0.46 and 0.34, in `FIT_V2_VALUES` order (`valuesFromTop`).

The top three are always clearly highest. Because the 16 top-three sets differ, so do the 16 profiles. There is no Schwartz value, outlook or trade-off anywhere.

**Natural fit is derived, not written** (`naturalFitOf`, `FIT_RULE`). Each of the eight radar areas (`RADAR_AXES`, migration 089's slugs) scores the sum of two values:

| Area | Values |
| --- | --- |
| Finance / Ops, Legal / Compliance | Stewardship + Integrity |
| GTM / Sales, Capital / Network | Curiosity + Ambition |
| Engineering | Resilience + Integrity |
| Product, Marketing / Brand | Collaboration + Curiosity |
| Design | Stewardship + Collaboration |

The two highest areas are the fit. A tie goes to the area earlier in the radar's order. This is the owner's example rule on #4117. Natural fit is advisory and blocks nothing.

**An agent's persona** is `team_agents.persona_key` (migration `202611021728_team_agents_persona.sql`):
- **Additive:** one nullable column, plus a partial unique index allowing one live agent per persona per scope. A removed agent frees its persona.
- **Existing agents** have it NULL. They read as their role's default (`DEFAULT_PERSONA_BY_ROLE`, in `catalogue.ts`).

The eleven roles map to eleven distinct personas, picked by natural fit and goal, so a Team that holds one live agent per role never reads two agents as one persona:

**The routes** (`routes/team_agents.ts`):
- **`GET /api/teams/personas`** returns the catalogue, the six values with their labels and descriptions, and the eight areas.
- **Every agent read** carries `persona`.
- **`POST …/agents`** takes `persona_key`, with the role's default when it is absent:
  - 400 `invalid_persona` for a key that is not a persona;
  - 409 `role_taken`, checked first, as before;
  - 409 `persona_on_team` when that persona is already live on the Team, counting older agents' role defaults.
- **`PATCH`** never changes a persona.

**No job titles reach a client.** A role's `name` is now the work it covers ("Company direction", "Engineering", "Product", "Finance", "Marketing and growth", "Sales and partnerships", "Operations", "Legal (assistant)", "People and hiring", "Research", "Investor relations"). The keys are unchanged, so every stored row, rule book and skill keeps working.

The goal planner names each agent by its persona, with the role key its plan assigns by, for example "Seren (ceo: Company direction)".

**Capability comes from skills** (`agentBook` and `skillRoles`, in `services/agents/teams.ts`):
- **The union.** An agent's rule book is the union of the effective rule books of the roles its pinned skill versions serve (`roles_json`):
  - `works_in`, `reads`, `may_propose`, `escalates_when`, `kpis` and `always_asks_human` are unioned (for asks, the stricter book wins);
  - `may_do_automatically` is what every one of those books allows;
  - mission and tone stay its own role's.
- **The fallback.** An agent with no skills, or whose skills name no known role, works as its own role, as before. So does one whose skills cannot be read (a database before 757): never more.
- **Callers.** The run's gate, task fit, the profile's matrix and the list's `module=` filter all read it.

`role_key` stays on the agent for back-compat: its default persona, its mission, and D1612's skill gates.

### What was not changed, and why

- **D1612's `role_mismatch` gate stays.** Dropping it, so that any skill can go on any agent as #4116 describes, would reverse D1612's role-filtered "available" and "assignable" lists and their tests. That is the skill library's owner's change (R3/R5 of #4116).
  - Until then, an agent gains another role's modules through a skill that lists several roles.
  - This corrects the plan posted on #4117, which said the gate would be dropped.
- **`agentValues`** (D1612's agent-skills read) still answers `null`. The persona's values ride on the agent's `persona`, and that read's frontend card expects its own shape.
- **The queue's `Item.agent`** keeps `role_name`, now a work label, and gains no `persona` field yet. R3 adds what its cards need.

### Tests

`cloudflare-worker/test/team_personas_d4117.test.ts`, 11 cases:
- **the catalogue:** order, single names, eight women and eight men, Solen's line;
- **values:** exactly `FIT_V2_VALUES`, #4116's top three, 16 distinct sets and profiles, and the risk table;
- **natural fit:** derived by the rule, with four of the owner's examples;
- **immutability**, of the catalogue and at the route;
- **role defaults:** eleven distinct, and no title in a role name;
- **the routes:** `GET /personas`, add with and without `persona_key`, `persona_on_team` counting an older agent's default, `invalid_persona`, `role_taken` first, and a removed agent freeing its persona;
- **the database floor** (the partial index);
- **capability from skills:** the union, a skill for another role only, and the fallback without the skill tables;
- **no answer** carries a job title, a Schwartz value or a trade-off.

Mutations checked, each failing a case:
- the persona check removed;
- an older agent's role default not counted;
- `Object.freeze` dropped;
- the natural-fit tie order flipped;
- `agentBook` reading only the role;
- the no-skill fallback dropped;
- a role named "CFO" again;
- two roles sharing a default;
- `invalid_persona` not checked.

D1496's and D1530's suites now apply the new migration, and read "Finance" and the planner's persona line where they read "CFO" and "CEO / Chief of staff".
