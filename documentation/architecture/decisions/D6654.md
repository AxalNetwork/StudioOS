## D6654 — Erased record files stay erased after a restore: a suppression ledger, and only legally retained classes in the locked copy (#6654)

The owner's direction on #6428 (#6652 A): the seven-year locked copy holds only files a legal
duty requires for the full period; erasure removes the live object and writes a suppression entry;
every restore applies the suppression list before anything is put back; personal files with no
retention duty stay out of the locked copy. `PROCESSING_AND_RETENTION_5510.md` asks for proof that
erased data stays suppressed after a restore. This decision builds that on the pieces already on
main: the D6650 inventory, the D6428 snapshot/restore and the D6651 delete door.

**Legal basis per class.** The D6650 inventory (`documentation/operations/R2_INVENTORY.json`)
already carries `retention_basis` and `locked_copy` on every class. No basis is written down for
any class, so every record class reads `retention_basis: "not recorded"` and `locked_copy: "no"`.
None is invented here. Three classes carry the runbook's seven-year period without a basis
(`files-contracts-evidence`, `files-esign-signed`, `files-kyc`); they and the other 29 record
classes are listed for the owner and counsel with this change. A test fails if the committed inventory ever
marks a class `locked_copy: yes` without a recorded basis, and the copier refuses such a class
even when it is marked.

**Backup filter.** `scripts/file-recovery.py` already copied only `studioos-files` record
classes marked `locked_copy: yes` with a recorded basis and the approved 2557 days. A new test
uses a store that fails the moment an unmarked prefix is listed, read or copied, with the mark
absent, `no` or malformed, and proves the store itself catches a copied unmarked prefix.

**The ledger.** Migration `202611220347_6654_record_suppression_ledger.sql` adds
`record_suppression_ledger`: `bucket`, `key_hash` (lower-case hex SHA-256 of the object key),
`record_class` (the inventory class id, or `unclassified`), `reason` (D6651's closed list),
`request_id`, `actor` (`member`, `operator` or `system`) and `erased_at` (ISO time from the
Worker). It holds no file content and no key. Actor is a category, not a user id, so the row
carries no personal data beyond the request id. Triggers refuse UPDATE and DELETE: the ledger is
append-only.

**The erasure path.** `eraseRecordObjects(bucket, keys, reason, ledger)` in
`services/recordErasure.ts` is still the only delete of a record key (D6651's guard). It now
writes one ledger row per key in one D1 batch before it calls `bucket.delete`. If the batch
fails, nothing is deleted. The one exception is a rollback (`unreferenced`): D6651 says that
object is not a record, since the same request stored it a moment ago and no row names it. A
rollback usually runs because D1 just failed, and keeping the object then would leave personal
data that nothing can find, which D6651 exists to prevent. So a rollback whose ledger write fails
still deletes, and logs `record_rollback_unledgered` with a count. Its exposure is a snapshot
taken inside that window and later restored, which brings back an object no row names. If the delete fails after the rows landed, the rows stay: a suppressed
object that is still live is never lost by a restore, but an erased object with no row could come
back. The ledger argument is required, so TypeScript names every caller; all 33 call sites now pass the
`DB` binding. `requestId` is the erasure request's id where the caller has one; otherwise each
call records its own `op:<uuid>`, so the rows of one call share an id. No caller passes one yet:
none of the current erasure sites receives a DSR id. The class comes from a prefix list in the
module that a test holds equal to the inventory's `studioos-files` record classes. Every caller
passes `env.FILES` (the D6651 provenance entry), so the ledger records `studioos-files`.

**The restore.** `restore()` takes the ledger, read whole before any archive object is read
(`load_ledger`, page by page by id; any failed or malformed page refuses the restore). An entry
whose key hash is in the ledger is skipped and never fetched. Asking for a suppressed key by name
raises `SuppressedObjectRefused` before anything is fetched or written: refused, not warned.
`file-recovery.py restore --run-id … --target … --d1-database-id …` is the live entry point D6428
held back; it reads the ledger through the D1 HTTP API (`SELECT` only), then the manifest.

A deterministic key can be written again after its erasure (the key is absent, so the write-once
put succeeds). The snapshot now records each object's R2 write time. An archived copy written
more than five minutes after the latest erasure of its key is a later object and may be restored;
anything closer, or with no recorded write time, stays suppressed. Clock skew fails toward
suppression.

**The drill.** `scripts/file-recovery-drill.py` backs up two synthetic objects, erases one after
the backup by writing its ledger row, loses the source, reads the ledger and restores: the erased
object is absent, the other is byte-identical, and asking for the erased one is refused. Locally
the ledger is SQLite built from the migration file itself. `file-recovery.yml` gains a dispatch
mode, `suppression-drill`, gated on `FILE_RECOVERY_PREVIEW_DRILL_ENABLED`. It runs the same drill
against the preview D1 (`FILE_RECOVERY_PREVIEW_D1_ID`, a preview-only token in
`FILE_RECOVERY_PREVIEW_D1_TOKEN`), writes a synthetic ledger row there and reads it back through
the adapter a live restore uses. The objects stay in memory. The script refuses the production
database id. The hosted run has not been made: its link is outstanding on #6654.

**Tests.** `cloudflare-worker/test/record_erasure_6654.test.ts` runs the erasure path against
node:sqlite built from the migration; `scripts/file_recovery_6428_test.py` (through
`file_recovery_6428.test.mjs`) covers the restore, the ledger reader, the locked-copy filter and
the drill. Fixtures that assemble their own schema and erase a record file apply the migration
through `cloudflare-worker/test/_suppression_ledger.mjs`. Mutation check (those two test files):
22 mutations, 22 caught, 0 equivalent.

**Not done here.** No production object is deleted and the erasure path is not exercised on
production. The D1 and KV restores (D6428's other rows) do not yet read this ledger. Whether
#6654 should also sweep replaced record files (D6651's open question) is still the owner's call.
