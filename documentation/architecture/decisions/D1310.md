## D1310 — ROUTE_MAP.md merges with union: one row per canvas, and the corpus count read from the tables

- **Status:** decided and built by S21 for S1, 2026-10-27, at the owner's request ("ROUTE_MAP.md is posing always conflicts in PRs, resolve that", the same remedy as README.md).
- **Basis:** `origin/main` at `d0f47285d1`, then `9a89686827` (D1299 merged while this PR was open).
- **Migration:** none.

### 1. Why every pair of canvas PRs conflicted

Every canvas integration adds a row to ROUTE_MAP's last table, so two open integrations collided in four places at once:

- the end of ROUTE_MAP's last table, where both append a row;
- `PROFILE_ROUTING.md` and `PAGE_INVENTORY.md`, generated from it;
- the one line in `frontend/test/profile_routing_fresh.test.mjs` that pinned the row count (`assert.equal(recs.length, 179)`), with a ledger comment above it that every PR extended.

On 2026-10-26 and 27 that sent #3395, #3386 and #3407 back three times in one day, and each time the PR merged second had to be bumped again (179, then 180, then 181).

### 2. What changed

- **`.gitattributes`:** `ROUTE_MAP.md`, `PROFILE_ROUTING.md` and `PAGE_INVENTORY.md` get `merge=union`, beside `README.md` and `docs/.build-source`. `union` is git's built-in driver, so it also holds in GitHub's server-side merge, where no local config exists.
- **One row per canvas** (`parseRouteMap`, `scripts/build-profile-routing.mjs`). When two branches change the SAME row, union keeps both versions. Canvas names were unique across all 179 rows, so a second row for a canvas can only be a merge's leftover. The parser now refuses it, naming both lines; keep one. The generator and the freshness test both fail on it.
- **A conflict marker fails the parser.** Union never leaves one, but a hand merge can, and inside a table it used to end the table and drop the rows after it silently.
- **The count is read from the tables, not pinned.** The ledger stops at 180, the last row it recorded (D1299, which merged while this PR was open). The test now walks every table headed `| Canvas | Persona |`, a looser match than the parser's header, to the blank line or heading that ends it. It requires:
  - at least five such tables;
  - exactly as many records as body rows;
  - at least 107 rows, the P−1 audit's corpus.

  A parser that stops matching a header, or stops partway through a table (a row that lost its leading `|`), still fails. A branch adding a row no longer edits the test.
- **The projections' union is never trusted.** After a union merge they are stale, and the freshness test fails naming `node scripts/build-profile-routing.mjs`. That is a CI message instead of a conflict marker, as D113 chose for the build stamp.
- **`unionArtifacts`** (`scripts/lib/readmeUnion.mjs`, from the README change) runs on all three files: no marker, no row naming the same backticked file twice, no substantial line repeated within eight lines.

### 3. What it does not fix

- **PRs opened before this merges** still change the old count line. Each conflicts once more, in the test only: keep `main`'s side, then re-run the generator.
- **Prose rewritten two ways** at the top of ROUTE_MAP keeps both versions, as in a README. It is caught only when a whole line repeats. Keep feature prose in the decision file and add the row.

### 4. Verified

- `frontend/test/profile_routing_fresh.test.mjs`: 11 pass. Each new check was mutation-checked:
  - drop the duplicate check;
  - drop the marker check;
  - strip one row's leading `|`;
  - drop the `.gitattributes` line.
- **On the real case:** this branch with #3395 (Accounts) and then #3407 (Record a session) merged on top. ROUTE_MAP and both projections merged with no conflict, both rows present (181 records). The projections were stale until regenerated, and then all 11 tests passed. The only conflict was each PR's old count line.
