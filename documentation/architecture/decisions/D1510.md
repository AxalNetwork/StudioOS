### 1. The ceiling covers every generation route

`deckCeilingRefusal` (`services/decks/observability.ts`) is D1540's check for the Pitch deck page. Every deck run logs under that page, so the day's spend is one sum. It is called before any hold in these places:

| Where | What it covers |
|---|---|
| `admitDeckRun` (`genRooms.ts`) | Area runs (`POST /api/decks/:id/areas`), the whole-deck build (`deck_build`), a retry of failed areas and any autopilot run (AUTO-1). A run starts nowhere else. |
| `POST /api/decks/:id/images` and `/images/replace-all` | The one-click's images, and every other image draw |
| `POST /api/decks/:id/cards/:card/assist` | Card assist (priced only once a ceiling is set) |

**The refusal.** 429 `deck_ceiling_reached` with "Generation is paused for today. Manual editing still works.". It comes before the runtime is chosen, the balance is checked, storage is reserved or anything is held, so a paused run charges nothing and leaves no partial deck. `refusalOf` draws the message as-is.

**What it does not refuse:**
- **A replay.** The same Idempotency-Key as a run already admitted is answered as that run, because it holds nothing new.
- **The steps of an admitted run.** The check is at admission, never inside the shared run path. A whole-deck run that was admitted runs to its end, so the ceiling never leaves a partial deck.

The quote routes run nothing and are not refused.

**Departure (kept from D1540).** The ceiling counts settled charges. Runs admitted at the same moment can each pass the check, so the overshoot is at most those runs' holds.

### 2. HQ's 50% and 80% alerts

`noteCeilingAlerts` runs when a run is admitted (before the ceiling check) and when a run ends. The first time the day's settled spend reaches 50%, and then 80%, each active HQ admin (`role = 'admin' AND is_active = 1`) gets one in-app notice and one email: type `deck_ceiling_alert`, category `billing`, linking to `/admin/ai`. The notice names only the amounts and the ceiling.

**Once per day, without a migration.** Each threshold is claimed with `INSERT OR IGNORE` into `job_idempotency` under the key `deck-ceiling-alert:<UTC day>:<pct>`. That is the existing once-only table, and the key prefix keeps it apart from the queue's keys. So two runs ending together send one notice. A jump past both thresholds sends the 80% one and claims the 50% one unsent. A failed alert never fails a run.

**At the ceiling,** the refusal itself is the signal. There is no 100% alert, and the issue names none.

### 3. One Analytics Engine point per run, and the funnel

Points are written to the `ANALYTICS` binding (`studioos_metrics`), carrying ids and codes only. Without the binding nothing is written and nothing fails; a malformed branch code drops the point, never the request.

**The dataset's layout (D161, D209).** These points use the same layout as the request row and the branch-action mirror:
- **blob1 is the row's kind** (`deck:run`, `deck:funnel`). It is never a path, so the traffic readers (`blob1 LIKE '/%'`) never count these rows as requests.
- **blob6 is the branch:** `branchOf(env)`, or `hq`.
- **The index is the kind.**

`topology_d209.test.ts` pins the three writers and the sixth-blob rule.

**`deck:run`.** `D1GenRuntime.finish` writes it, only in the driver whose UPDATE closed the run, so a run writes one point whichever runtime drove it.
- Blobs: kind, class, end state, runtime, run uid, branch, deck id, venture id.
- Doubles: hold, charge, steps, done, failed, and seconds since admission.

**`deck:funnel`.** One point per event. Blobs: kind, event, deck id, venture id, proposal id, branch, and `one_click` when the build was the one press.

| Event | Where |
|---|---|
| `structure_change` | `PUT /api/decks/:id` when a card the deck already had changes structure. Matched by uid, else place; an added or removed card is not a change. |
| `share` | `createShareLink`, the one link writer (D691), whichever route made the link |
| `build` | `POST /api/decks/generate` |
| `accept_all` | `keep-slides` saving every card of the proposal |
| `accept_all_present` | The same save with `present: true`, which `OneClickBuild.jsx` now sends from Accept all and present |

**Reading the funnels.** The editor's funnel runs from structure change to share, and the one-click's from Build to Accept all and present. `deck:run` points join on venture id and deck id, never on a person.

### 4. The accept rate

`acceptRates(env, days)` reads `deck_area_proposals` (#3764) over the last `days` days (1 to 365).

**How a proposal is grouped:** by element and by the model its area ran on (from the run's steps; null for a records element, which runs no model).

**What each group answers:**
- `proposals` and `regenerated`;
- `decided`: Accept, Accept all, Discard, superseded and expired;
- `accepted` (Accept or Accept all) and `accepted_all`;
- `discarded`;
- `accept_rate`: accepted over decided, or null when nothing is decided (never 0);
- `first_result_seconds`: the mean time from the run's admission to the area's first finished step, or null when none is recorded.

"Insert rate" is renamed "accept rate" everywhere, as the revision asks.

### 5. HQ's read

`GET /api/admin/deck-generation?days=30` (`routes/admin_deck_generation.ts`, self-mounted) answers:
- the ceiling: `ceiling_microusd` (null: "Not set"), `spent_today_microusd`, `percent`, `paused`;
- the alert thresholds;
- the accept rates, with each model's label.

A figure that cannot be read is null, never 0. Only an HQ admin may read it, and a branch is refused. The page that draws it is B10's (#3786) and out of scope, so there is no client method yet.

### 6. Not built here

- **The HQ dashboard page** (B10, #3786).
- **The autopilot (AUTO-1).** It is not on main. When it lands it starts its runs through `admitDeckRun`, so the ceiling covers it with no further change.
- **A figure for the ceiling.** It is the owner's to set. Until `DECK_DAILY_CEILING_MICROUSD` is set, nothing pauses and no alert is sent.
