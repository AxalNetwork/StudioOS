## D992 — Partner profile verdicts and Exploring status

Issue #2803, part of #2380. S28. No migration.

### Verdict writes

`POST /api/profiling/admin/:email/verify` retains `requireAdmin`, including
Super Admin elevation and the existing compliance freeze. The route accepts
only `verified` and `rejected`. Unknown, missing and `pending` verdicts return
400 with a sentence before the profile or its audit rows change. Reopen belongs
to part 2; this route no longer treats arbitrary input as verification.

Omitting `admin_notes` or `agreement_type` preserves the stored field. An
explicit empty string or null clears it to SQL NULL. The response reports the
stored values. Omitting an agreement does not resend a previously stored one.
Successful writes retain both the admin audit row and, when the profile has a
member account, the member's private-feed row; they identify the member by id.
A failed profile read remains a 5xx, and an absent profile remains a 404.

### DocuSign preflight

The requested provider is normalised once, including the legacy `via_provider`
alias. For verification with an explicitly requested agreement, the existing
DocuSign plan check now runs before the verdict UPDATE or either audit INSERT.
The route retains the shared `userMeetsTier` policy, matching the eSign send
route. That policy currently exempts **all admins**, so its 402 cannot occur
under this route's present `requireAdmin` guard. S21 was asked on #2803 whether
a different plan policy is intended; this change does not silently introduce
one. Other send refusals keep D758's existing successful-verdict behavior.

### Exploring

The existing Profiling cell in `AdminExploring.jsx` draws the verdict as a linked
pill: pending → Waiting, verified → Verified, rejected → Rejected. Missing and
unknown values say Not recorded. The colours follow the Partner profiles canvas
in D989's dependency PR #2809, including dark colours. The address is always
`/admin/partner-profiles`, with no email or individual identifier.

**Dependency:** PR #2809 must supply that destination before this change ships.
The issue names #2742, but that merged PR supplies the shared header rather than
the D989 page; the page, canvas and D989 are in #2809. No read payload or API
address is changed here, so ROUTE_MAP's read inventory is unchanged.

### Verification

The verdict tests use the complete baseline plus all current migrations behind
real SQLite and the actual router/authentication. They cover invalid statuses,
field replacement/omission/clearing, audit recipients, authentication/admin
refusals, missing records and failed reads. The frontend checks render every
status and mount the actual Exploring row, including its person-free link.
Key regressions are mutation checked; final command results are recorded in
the PR. No email, DocuSign request or production database action is performed.
