## D5613 — Split busy guard ledgers by their review unit (#5613)

The authorization review ledger now has one JSON map per route family under
scripts/baselines/auth-inventory. SQL prepare has one map per Worker source file
under scripts/baselines/sql-prepare. Filenames are encodeURIComponent(group)
plus the JSON extension, so grouping cannot collide by replacing slashes with
dashes. Auth grouping calls the existing familyOf rule. SQL grouping uses the
source suffix after the last ` @ ` in its unchanged site key.

readSplit rejects duplicate keys, malformed maps and wrong-file keys, naming
both actual and expected paths. writeSplit validates before writing, sorts keys,
changes only different bytes and removes empty groups. Both consumers reject a
restored legacy file, including during seed/write operations. No fallback reads
an obsolete path. ledgerProblems keeps its existing checks; only its diagnostic
path changes. Counts and review meaning do not change.

### Migration evidence

Before deleting either original, the migration asserted deep equality of every
merged entry map against its original routes/sites map. A second write returned
an empty changed-file list. The SQL ledger's descriptive note is retained in its
README; no review entry, count, note, test reference or state was regenerated.

| Consumer | Before | After |

| SQL prepare | 273 current keys, 12 removed keys; 285 entries total | Identical; 157 source-file maps |
| Auth inventory | 4,075 routes in 171 families; 454 need review (435 unreviewed, 19 verified) | Identical; 89 family maps |

The issue's earlier 455-entry inventory was a snapshot; current main has 454.
SQL's prior behavior only fails on new keys, not increased counts or removed
sites; compare preserves that rule. Removing one split file makes its current
sites new, so there is no permissive missing-file fallback.

existing README files: deleting the README also removes the directory from the
set being checked, so the deletion passes. A replacement would need an
independent source of expected significant directories (for example a manifest
or a structural rule with explicit exemptions), plus deletion-mutation coverage.
This PR adds exactly the two significant leaf-directory rows required by the
issue; the container directory has its own README and is linked by scripts' README.
