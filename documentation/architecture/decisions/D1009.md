## D1009 — HQ Payments gates, step-up and recorded change reasons

Issue #2827, part of Payments #2386 and D1008/#2809. No migration.

The admin catalogue's products, mode and sync routes require Super Admin on HQ.
Stripe config/webhook reads and the fixed-event webhook update require the same
role. Reading and event repair do not demand a recent step-up. Webhook register
keeps its existing Super Admin write bar.

All six generic product/price mutations and PUT /admin/stripe/config require
`requireSuperAdminWriteBar`: a TOTP-minted session, a recent step-up, and HQ's
Super Admin elevation. These checks precede body validation, provider calls and
writes. Each of these seven requests must carry a `reason` string: trimmed,
nonblank, at most 500 characters. It is included with the existing actor and
action in the route's audit record. No reason is invented. The shared
`paymentChangeReason` validator supplies the same rule to both routers.

The existing audit mechanisms remain: generic catalogue writes use
`admin_audit_log`; the Stripe config write uses `logAdminAction`. Reasons are not
sent to Stripe. Publishable-key reads remain masked, signing/secret keys never
appear in response bodies, and a failed key persistence returns a 503 sentence.
The Stripe and D1 failure paths retain refusals rather than empty successful
lists. The catalogue's existing post-action audit behavior is unchanged.

`/api/admin/stripe` joins the recovery cool-off prefix list beside the catalogue.
The existing middleware therefore pauses every method under both prefixes,
including reads, for a recovering account until its cool-off ends.

A subscription may use `metadata.plan_group=advisor|partner`, matching the
existing `aiCredits.planOf` classifier for Advisor Pro and Operating Partner Pro.
Existing MI Pro, founder and investor plans remain valid. No Investor Plus plan
or unsupported group is introduced. Prices stay in their existing smallest-unit
representation. Checkout interval selection and AI allowances are outside this
part; token-pack routes keep their current gates and ownership.

The authenticated member catalogue remains available. No new endpoint, frontend,
secret, binding or schema change. The Payments route-map data sources and paths
are unchanged; only authorization and the generic-write request contract change.
The Payments dialogs must supply `reason` and complete the existing step-up flow
before these writes; older callers receive a refusal until updated.

### Verification

Mounted Hono/SQLite tests exercise all six HQ read/repair/sync routes and seven
write routes: anonymous, founder, plain admin, branch, stale and weak-factor
sessions, missing/invalid reasons, successful writes and stored actor/reason,
provider/mirror/KV failures, secret masking and the live recovery middleware.
The middleware fixture reads index.ts's actual prefix list. Existing D223
webhook tests now enforce the HQ-only event update; token-pack ownership tests
use a fresh holder for generic writes. Catalogue metadata is checked against
`planOf`. Key assertions are mutation-checked in isolation.

Keep the PR a draft for S1's security review before the owner merges. No
