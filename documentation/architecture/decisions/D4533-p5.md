### 1. Where it is answered

`GET /api/admin/ai-agents/skills/:uid` gains one field, `timeline`. It is additive, on the route #4537's screen already reads, so there is no parallel lifecycle API (the issue's part E rule), no new route, and no new client method: `frontend/src/lib/api/`'s existing read of this route carries it. The gate is that route's own `requireSuperAdmin`, the same as every HQ skill read. A company skill is not HQ's and answers 404, as before.

```
timeline: {
  rows: [Row],                 newest first, at most TIMELINE_MAX (200)
  truncated: boolean,          more rows were recorded than shown
  unreadable: ['draft_restore'] | []   a source that could not be read (its rows are left out, never read as "none")
}
```

`skillTimeline(env, skill)` in `services/agents/skillLifecycle.ts` builds it.

### 2. The rows

Every row has `id` (stable: the same source row gives the same id on every read), `kind`, `at` (the time as stored), `actor` (`{ uid, name }`, never an email; null when no row records who) and `version`.

| kind | Source rows | Fields | `actor` | `version` |
| --- | --- | --- | --- | --- |
| `publish` (`publish:v<N>`) | `agent_skill_versions` | `release_note` (null: "Not recorded") | `published_by` | the version |
| `review` (`review:<id>`) | `agent_skill_reviews` with a decision: `approved`, `changes_requested`, `withdrawn` | `decision`, `reviewer`, `requested_by`, `requested_at`, `decided_at` (= `at`), `comment` | the reviewer for a decision; null for a withdrawal | an approval named by a version's manifest (`$.review.review_id`, `D4533.md` §10.1); otherwise null |
| `draft_restore` (`draft_restore:<audit id>`) | the `agent_skill_restore_proposed` admin audit row, the restore's only record (`D4533.md` §10.2) | `source_version`, `reason`, `discarded_draft` (a boolean) | the audit row's admin | null |
| `retirement` (`retirement`) | `agent_skill_retirements` | `reason`, `replacement` (`{ uid, name }`), `pinned_agents` | `retired_by` | null |

**What is not a row.** An open review request is not a decision; GET `/:uid` answers it as `review.open`. Draft saves, case and model changes and eval runs are not part of S20's list, and their audit rows stay where they are.

**The comment.** A review row carries only the comment the reviewer wrote with the decision, the one the decide route sends to HQ. A withdrawal carries none (a later request, restore or retirement withdrew it, and wrote no comment). A restore row carries its reason, never the discarded draft's text, which stays in the audit row (`D4533.md` §10.2).

**A version is named only where a row proves it.** A publish is its version. An approval is the version whose manifest names its review id, and only an approval can be. A changes-requested or withdrawn review, an approval that released nothing, and every approval from before D4533 (no manifest) read null. A restore proposes a draft, and no row ties that draft to a later version, so it reads null; its `source_version` is the version it copied. A retirement row names no version, so it reads null.

**The release evidence stays where it is.** The manifest, `publish_audited` and the reused-results flag stay on `versions[]` and `freshness` (`D4533.md` §2, §10; `D4533-p4.md` §1), the release-evidence card's meaning. A timeline row neither repeats nor re-derives them; the screen joins a publish row to `versions[]` by `version`.

### 3. The order

- Newest first, by `datetime()` of the stored time, so the text format does not decide. A row whose time cannot be read goes last.
- Rows recorded in the same second (D1's `CURRENT_TIMESTAMP` has one-second steps) follow cause and effect, the effect first (`TIMELINE_RANK`): a retirement, then a publish, then a restore, then a review. So a publish sits above the approval it spent, and a retirement or a restore above the review it withdrew.
- Then the newer source row first (its id).

`orderTimeline` is pure and tested on its own.

**The cap.** Each source reads its newest 201 rows, so the merged first 200 are exact and `truncated` is true whenever a 201st exists, even when one source alone holds it. When the audit log cannot be read, the restores are left out and `unreadable` names them.

### 4. Tests and the mutation check

`cloudflare-worker/test/skill_version_timeline_d4533.test.ts`, 5 tests, on the real migrations (the node:sqlite D1 fixture) with synthetic rows at fixed times:

1. `orderTimeline`: newest first, the same-second rank, the source-row tie-break, an unreadable time last.
2. GET `/:uid`: every kind with its fields and its exact order, including two same-second ties; an approval named by a manifest reads its version, and one that released nothing reads null; a withdrawal has no actor and no comment; an open request is not listed; another skill's restore is not listed; no email, discarded draft text or evidence in the timeline; the ids are stable across reads.
3. Through the real routes: two publishes (one with a note), their gate approvals, a restore and a retirement read back as written.
4. Permission: a platform admin who is not a Super Admin and a company editor are refused 403; a company skill answers 404.
5. The cap and `truncated` (205 rows, and one source at exactly 201), and an unreadable audit log.

**Mutation check: 20 of 20 caught.** Each was scripted, the test file run, and the source restored. The list is at the foot of the test file. One first run survived: each source reading only 200 rows, because that test also had a restore row that kept the merged count above the cap. A case with one source at exactly 201 rows was added, and it catches it.
