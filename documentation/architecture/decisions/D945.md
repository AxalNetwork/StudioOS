### 1. One decision path, now shared (`services/labDecisions.ts`)

D943's decision moved out of `routes/admin_cohort.ts` into `decideApplicant`. Its behaviour is unchanged:
- the guarded update with the places count in the same statement;
- the cycle event and the legacy mirror in one batch;
- the decision email and notice (`tellDecision`);
- the activity row.

`decideCohortApplication` (both decide doors) now parses the request and calls it. The bulk decision calls it once per applicant. Admit without an application reuses its places count and its decision email. **Places are enforced in one place.**

### 2. The three writes (`routes/admin_lab_writes.ts`, mounted in `admin_cohort.ts` at `/api/admin/cohort`)

Every route:
- is an admin's;
- is frozen on a suspended branch (D107), after authentication;
- needs a reason of up to 500 characters;
- refuses through `{ error: code, message }`.

**"Open" means `cohort_cycles.app_status = 'open'`,** a cohort whose applications window has not closed, as SL4 D and G draw it ("Open cohorts only"). A cohort that is reviewing, postponed or active takes no one. Nothing here activates a founder: the scheduler starts approved founders on the cohort's 1st (D943).

| Route | Body | What it writes |
|---|---|---|
| `POST /applications/:applicant_id/move` | `{ cycle_id, reason, confirm_over_places? }` | SL4 D. A pending, waitlisted or approved applicant moves to another open cohort (§3). |
| `POST /applications/bulk-decide` | `{ applicant_ids, status, reason, confirm_over_places? }` | SL2's bulk bar. Approve or waitlist 1 to 25 applicants with one reason. Each goes through `decideApplicant` in the order given, with its own guarded update, cycle event and activity row. The answer lists each applicant's result (`ok`, or its refusal code). A bad request (another status, no reason, more than 25, a bad or repeated id) is refused whole. |
| `POST /applications/admit` | `{ user_id, cycle_id, reason, company_name?, confirm_over_places? }` | SL4 G. Creates the application on the founder's behalf and its approved place (§4). 201. |

### 3. Move to another cohort

One batch, or nothing:
1. **The new `cohort_applicants` row in the target.** It carries the applicant's status and its decision (`decided_at`, `decided_by`, `decision_reason`), with `rolled_from_cycle_id` set to the cohort it left. It is written only while all of these hold, checked in the same statement:
   - the target is still open;
   - the applicant's status is unchanged;
   - for an approved founder, a place is free there (D943's count, with `confirm_over_places: true` the only way past).
2. **The old row becomes `rolled_forward`,** the status the scheduler's rollover already uses. Its reason reads "Moved to <cohort>: <reason>". Every reader that knows a carried-forward application reads a move too:
   - D944's `carried_forward` and `carried_in`;
   - the legacy decide's newest-row lookup;
   - D943's terminal states.

   No new status is introduced.
3. **One cycle event, `applicant_moved`,** on the target cohort, naming both cohorts, the reason and `confirm_over_places`.
4. **One audit row, `cohort_applicant_moved`.**
5. **The legacy `spinout_applications.cohort` label** follows to the new cohort.

Then the founder is told, with one `moved_cohort` notice per founder and cohort. The answer carries `founder_told`.

**Refused:**

| Code | When |
|---|---|
| `cohort_not_open` | the target is not open |
| `same_cohort` | the target is the applicant's own cohort |
| `already_in_cohort` | the application already has a row in that cohort's history (`UNIQUE(application_id, cohort_cycle_id)`) |
| `not_movable` | the applicant is rejected, activated, withdrawn or already carried forward |
| `over_places` | an approved founder and a full target, without the confirmation |
| `decision_conflict` | the applicant changed during the move |
| 5xx | a failed audit write; nothing moves |

### 4. Admit without an application

One batch, or nothing:
1. **The `spinout_applications` row.** Status `pending`, D943's mirror of an approval that the scheduler accepts on the 1st. The cohort label is the cohort's month. The company is the name the admin gives, or empty. The idea is empty and the answers are null: nothing is made up for the founder. The statement checks, in itself:
   - the cohort is still open;
   - the founder holds no live application (pending, waitlisted, approved or activated);
   - a place is free, unless `confirm_over_places: true`.

   So two admissions of one founder cannot both land.
2. **Its `cohort_applicants` row,** status `approved`, decided by the admin with the reason.
3. **One cycle event, `applicant_admitted_without_application`.**
4. **One audit row, `cohort_applicant_admitted`.**

Then the decision email and the "You're in" notice, as an approval sends them, through the same ledger.

**Refused:**

| Code | When |
|---|---|
| `admin_not_admissible` | the account is an admin |
| `lab_alumnus` | the account has been through the Lab (`is_incorporated = 1`, as before) |
| `already_in_lab` | the founder is already in the Lab |
| `already_in_queue` | the founder already has a live application; the message names its cohort and status, so the admin decides or moves it there |
| `cohort_not_open` | the cohort is not open |
| `over_places` | the cohort is full, without the confirmation |

A rejected or carried-forward application is not live, so such a founder can be admitted.

### 5. Users' "Spin-Out admit": it calls the admit, and is not retired

`POST /api/admin/users/:user_id/spinout-admit` now calls the same write (`admitRoute`) with `{ cycle_id, reason, … }`:
- **it no longer writes a free-text cohort label into `user_spinout_flags`** with no application and no cycle row;
- a body that still sends `cohort` is refused 400 `cohort_label_unsupported`, as D943 refused it on the legacy decide.

**It is kept** because SL4 G is marked "OPENED FROM ACCOUNTS OR HERE": the canvas keeps a door from the account. Its client, `adminSpinoutAdmit(userId, { cycle_id, reason })`, still sends an old string as `{ cohort }`, so it is refused rather than silently ignored.

**For S21:**
- Users' button still opens a browser prompt for a label, so until SL4 G's dialog is drawn there, it answers that refusal.
- Over-capacity approvals worked the same way under D943 until its dialog.
- The part that draws SL4 G should open the same dialog from Users.
