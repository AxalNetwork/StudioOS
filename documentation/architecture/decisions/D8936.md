## D8936 — Reconcile duplicate additive D1 migrations one file at a time (#8936)

**Decision date:** 2026-11-27.

The production migration job stopped at D7707. The Worker can add the same six
columns through runtime schema setup while the migration remains pending.
D7708 and D8522 also have runtime paths that can create their columns. D7707
includes a source-run table and index that still need to be applied.

After Wrangler reports a duplicate column, table or index, the runner checks
that the diagnostic names an effect in the pending file. It accepts only
unqualified additive column and table/index creation statements. It verifies
the names of all added columns in the target catalog and the catalog SQL for
each unguarded table or index creation. Once those checks pass, it replays
guarded table and index creation statements individually in file order.

The runner lists the schema effects it found and records the original file
and checksum after all replays succeed. A refusal leaves the file pending and
stops later files. If a replay fails after an earlier guarded creation,
retrying can safely execute that guarded statement again. Column verification
checks presence by name, as required by the migration recovery contract.

The existing migration files and ledger format are preserved. The old
baseline procedure still applies to databases that predate the ledger.
Production deployment remains a separate owner action after source review.
