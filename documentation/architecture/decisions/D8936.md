## D8936 — The migration runner adopts columns the Worker already added, and nothing else (#8936)

- **Status:** built by S21 on #8936, 2026-11-27. T2: the owner lands it, then re-runs the production deploy.
- **Chosen by:** the owner (2026-11-27): one runner fix, one repair PR (D5398), no edit to any migration on main (D269).

### The problem

Every production deploy since 2026-11-21 03:30Z has failed at the D1 migration step. Run 45997731476 (main `1b841e77e`) planned 74 pending files, applied five (6960, 7075, 7077, 7585, 7672), then stopped:

```
✖ [migrate-d1] migration FAILED: 202611191833_7707_market_intel_row_dates_runs.sql
✘ [ERROR] duplicate column name: observed_period: SQLITE_ERROR
```

`services/market_intel/schema.ts` adds the same six `market_intel_rows` columns at runtime, so production already had them while the ledger did not record the file. Two more pending files have the same shape: `202611220337_7708_market_intel_index_window.sql` (`market_intel_indexes`, also from `schema.ts`) and `202611250054_8522_usage_contract_columns.sql` (`ai_usage_logs`, from `services/aiRouter.ts`).

The two existing tools do not fit:
- **editing the file** is refused by the immutability gate (D269);
- **`--baseline`** marks *every* non-idempotent pending file without running it, so it would skip the genuinely new migrations among the other 69.

### What was decided

`scripts/migrate-d1.mjs`, in apply mode, wraps its `--file` apply in `withPresentColumnAdoption` (`scripts/lib/migrationAdopt.mjs`). A file that applies is untouched; the wrapper only acts when the apply has already failed. It adopts the file only when all of these hold:

1. the error is `duplicate column name`. D1 rolled the whole `--file` batch back, so nothing of the file landed;
2. the column D1 named is one the file adds;
3. every `ALTER TABLE <t> ADD COLUMN <c>` in the file names a column already on `<t>`, read from the live `PRAGMA table_info(<t>)` through the same wrangler path. Each column must also have the same declared type and the same NOT NULL-ness;
4. no statement of the file other than a `CREATE` mentions one of those columns. An `UPDATE` backfill would overwrite values the Worker has already written.

When all four hold:
- the runner prints each present column with its live type;
- the file's other statements (`CREATE … IF NOT EXISTS`, triggers, inserts) run as **one** `--file` batch, so D1 applies them all or none, like the apply they replace;
- the file is recorded in the ledger exactly as an applied file: same `record`, same whole-file checksum.

If that batch fails, the run fails loudly, nothing of the batch lands and the file stays pending.

Anything else fails exactly as before, with the original error and one appended line, `not adopted (D8936): <reason>`. That covers a column that is absent (partial state), a different type, an `ADD` the parser cannot read, a backfill on an adopted column and every other error.

`--dry-run` in apply mode reads the same `PRAGMA`s. It prints `adopt <file> (will adopt present columns: …)`, or `apply <file> ⚠ will FAIL …` for partial state. It counts columns an earlier pending file adds as present for the files after it. If the schema cannot be read, it says so and makes no prediction.

### What was not adopted, and why

- **`table … already exists` / `index … already exists`.** A table or index of that name says nothing about its columns or what it indexes. It is not evidence of the same strength as a present column with the same declared type, so those errors fail as before (DEPLOY.md §4(b)/(c)).
- **Per-statement execution.** The rest of the file runs as one batch rather than one call per statement. A failure halfway through therefore leaves nothing behind, and a retry finds the same state.
- **Default values and CHECK clauses** are not compared. `PRAGMA table_info` reports no CHECK, and for the three files above the runtime DDL is the same text as the migration (`schema.ts` and `aiRouter.ts` declare it). The printed list of adopted columns, with their live types, is the record an operator checks.

### Evidence

- **Reproduced on a local D1** (wrangler `--local --persist-to`). The database was seeded to production's shape: the baseline plus every later migration, the runtime `ALTER`s standing in for 7707/7708/8522, and a ledger of 1018 rows without them.
  - The runner as on main (`1b841e77e`) exited 1 with `duplicate column name: observed_period: SQLITE_ERROR`.
  - The new runner's dry run printed `adopt` for all three.
  - Its live run adopted all three. It created `market_intel_source_runs` and its index, recorded the three ledger rows with the files' own SHA-256s, and left a Worker-written `ai_usage_logs` row intact.
  - A re-run was `Nothing to do`.
  - With `observed_period_end` dropped and 7707 un-ledgered, the dry run printed `will FAIL … partial state`, and the live run exited 1 with the original error and `not adopted (D8936): partial state: market_intel_rows.observed_period_end is absent …`. Nothing was created or recorded.
- `cloudflare-worker/test/migrate_d1_present_columns_8936.test.ts` runs the three real files through `planActions` → `applyPlan`, with an `exec` that is atomic per file as D1's is. It pins the reproduction, adoption, the no-op re-run, partial state for all three shapes, the untouched normal apply, the rethrown foreign error, the atomic rest-of-file batch, a trigger with semicolons, each refusal, the dry-run prediction, a parser check against every `ADD COLUMN` in the real migration set (which caught `ADD COLUMN IF NOT EXISTS` in 080), and the CLI wiring.
