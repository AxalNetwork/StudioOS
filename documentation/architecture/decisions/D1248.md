### 1. Migration 622

- **`dd_requests` gains:**
  - `due_date`, a calendar day CHECKed to `YYYY-MM-DD`;
  - `withdrawn_at` and `withdrawn_by_user_id`.
  - An older request keeps them NULL: no due date, not withdrawn.
- **`dd_item_evidence`:** what backs a checklist item. Each row is a file (a `dd_attachments` row on the item's section) or a link, with who added it and when. A CHECK holds that a file has an attachment and no link, and a link has a link and no attachment.

### 2. The case read's documents

`GET /api/dd/cases/:uid` gains one block of its own:
- **each request's `files`:** the data-room files the subject matched to it (`data_room_files.dd_request_id`);
- **each request's `reminders`:** a count and the last time;
- **`evidence`:** the case's item evidence, with who added it.

Who sees what is the case read's own rule:
- **request files and reminders** follow the requests: the owner's and an admin's only, so a section reviewer gets none;
- **evidence** follows its item's section, as the checklist does.

**A failed read of the block is its own.** `documents_unreadable: true`, `evidence: null` and each request's `files: null`, never "none"; the rest of the case still answers.

### 3. Requests: due dates, remind, withdraw

- **The due date** is set on `POST …/requests` and changed or cleared on `PATCH …/requests/:id` (`due_date`).
  - It must be a real day, today (UTC) or later; otherwise 400.
  - Changing it does not mark the request reviewed.
  - A withdrawn request takes no change (409 `withdrawn`).
- **`POST …/requests/:id/remind`** is for the owner or an admin, while the request waits.
  - **Refused:**
    - an answered request is 409 `answered`;
    - a withdrawn one is 409 `withdrawn`;
    - a second reminder inside a day is 429 `reminded_recently`;
    - a subject with no account is 409 `no_subject_account`.
  - **When sent:** each reminder is a `dd_request_reminders` row and an audit row. The subject's notice names the due date when there is one.
- **`POST …/requests/:id/withdraw`** is for the owner or an admin.
  - **What it changes:** the request leaves the subject's pages: `/requests/mine`, and the data room's diligence list (D1107). It takes no answer, no file and no reminder.
  - **Refused:** a reviewed request stays as it is (409 `reviewed`).
  - **The reason:** when given, it is kept only in the encrypted audit details, never on the request. The request is founder-visible, and migration 167's invariant holds.

### 4. The subject answers with a data-room file

- **Through the requests page:** `PATCH /api/dd/requests/:id/respond` takes `file_uid`.
  - The file must be one of the subject venture's own data-room files; another venture's is 404.
  - A subject that is not a venture has no data room (400 `no_data_room`).
  - A file alone keeps the note and link already given.
- **Through the data room:** matching a file to a request (`dd_request_id` on upload or `PATCH`) now answers it.
  - **`markRequestAnsweredByFile`** moves a waiting request to `received` and writes `request_answered_by_file` to the case's audit log.
  - **It never touches** a reviewed or a withdrawn request.
  - A withdrawn request cannot be matched (404, as a request the venture does not have).

### 5. Item evidence

`POST /api/dd/cases/:uid/items/:itemId/evidence` takes a link (`{ url, label }`, http(s) only) or a file (multipart `file`, up to 10 MB).
- **Who may add it:** the item's own writers, as `PATCH …/items/:itemId` decides: an admin, the case owner, or a reviewer of the item's section. Another section's reviewer is 403.
- **Where a file goes:** it is stored under `dd-evidence/<case>/<section>/`, as a `dd_attachments` row on the item's section, so the download rule below applies to it.
- **Without storage:** a file is refused (503 `storage_not_configured`). Nothing is recorded as stored.
- **Each one** writes `item_evidence_added`.

### 6. The document link: single use, logged, the caller's alone, two minutes

- **`POST /api/dd/cases/:uid/documents/download { kind, id }`** issues a link.
  - **`kind: 'attachment'`** is an NDA or item evidence. A section reviewer reaches only their own sections' attachments: another section's NDA answers 404, as a document that is not there.
  - **`kind: 'request_file'`** is a data-room file the subject gave a request. It is the owner's and an admin's only, as requests are; a reviewer is 403.
  - **Refused:**
    - an attachment whose file was never stored (`inline:`) is 409 `not_stored`;
    - a founder is refused, as on every DD route.
  - **The link** is a random 256-bit token, `/api/dd/documents/dl/<token>`, expiring two minutes later. Issuing it writes `document_link_issued`.
- **`GET /api/dd/documents/dl/:token`** answers once.
  - **One conditional `UPDATE`** sets `consumed_at` where the token's hash matches, the caller is the user it was issued to, it is unused, and it is in time.
  - **No row changed is a 403**, the same sentence for another user, a second open and a late one.
  - **Then** the file streams with `private, no-store`, and `document_downloaded` is written.
- **Why not `services/signedDownload.ts`.** Its single use is KV's best effort, as its own header says: no KV means no single use, and its token is not bound to the caller. A D1 row gives both, in one statement.
