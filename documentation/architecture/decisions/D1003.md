### 1. A suggestion

`POST /api/personas/segments/suggestions` (`requireAdmin`) takes `{ segment_key, kind, text }`:
- `kind` is `who` (who they are), `need`, `offer`, `new_segment` or `other`;
- `text` is 1 to 500 characters;
- `segment_key` names a segment in HQ's store, or one of the twelve in code. It may be left out only for a new segment.

A refusal is a code and a sentence: `invalid_body`, `invalid_kind`, `text_required`, `invalid_text`, `segment_required`, or 404 `not_found`. A refused suggestion stores nothing.

**On HQ** the suggestion is HQ's row (`origin_code` 'hq'). Every Super Admin is told in the bell (`segment_suggestion_new`, linking to the page). The answer says how many were told, or why none were.

**On a subsidiary** the Admin's database and HQ's are different Workers, so the suggestion travels as an escalation does:
- **HQ first.** The subsidiary calls `HQ.segmentSuggestion(code, { uid, segment_key, kind, text, suggested_by_name })`.
- **HQ checks the caller.** The code must be a provisioned subsidiary in `licence_deployments`. HQ then checks the suggestion again, stores its row with `origin_code` = the code and `origin_ref` = the subsidiary's uid, and tells its Super Admins.
- **A retry is stored once.** A retry after a lost response finds the same row through the unique `(origin_code, origin_ref)` and tells nobody twice.
- **What HQ holds of the Admin.** HQ keeps the Admin's name and studio, never the subsidiary's account id.
- **The subsidiary's copy.** The copy is written either way:
  - `delivered` with HQ's uid;
  - `undelivered` with the reason, when there is no HQ binding or the call failed.
- **A refusal is not retried.** HQ's refusal is returned, not thrown; the subsidiary answers it as a 400 and stores nothing.

### 2. HQ's decision

`POST /api/personas/segments/suggestions/:uid/decide` (`requireSuperAdmin`, so HQ only) takes `{ decision: 'accept' | 'decline', reason? }`:
- **A decline needs one line,** at most 200 characters; a line break is folded into a space. The table's CHECK refuses a decline without it too.
- **A decision is final.** The UPDATE is guarded on `open`, so a second decision is 409 `already_decided` and changes nothing.
- **Accept answers with what part 3's edit opens on:** `{ segment_key, expected_version, field, text }`, where `field` is `who`, `needs` or `offers` by kind, or null for "other". A new segment answers `new_segment: true`; New segment itself is not built yet.
  - Accepting changes no profile. The change is HQ's write through `PATCH /api/personas/segments/:key`, with its own version check and history row (D1000).
- **The Admin is told.**
  - On HQ, directly (`segment_suggestion_decided`, with the line on a decline).
  - For a subsidiary, HQ pushes `applySegmentSuggestionAnswer({ hq_uid, status, decline_reason, decided_by_name, decided_at })` to its `BRANCH_*` binding. The subsidiary updates its copy and tells its Admin, whose account is on its database. It invents no row for an HQ uid it never sent.
  - HQ records whether the push landed (`push_ok`, `push_reason`, shown as `pushed`). A decision whose push failed still stands, and the answer says why nobody was told.
- **Each decision is copied to the admin audit store** (`segment_suggestion_decided`).

### 3. Reading them

`GET /api/personas/segments/suggestions?status=` (`requireAdmin`), newest first, at most 200:
- HQ's Super Admin reads every suggestion HQ holds (`scope: 'all'`), from HQ's Admins and every subsidiary's.
- Any other Admin reads their own (`scope: 'mine'`), on the deployment where they made them. On a subsidiary that includes HQ's decision once it is pushed.
- **No account id leaves the store.** Each row carries the Admin's name and studio.
- A store that cannot be read is a 503, never an empty list.

### 4. The RPC surface

Two methods, each listed in `services/topology.ts` (`RPC_SURFACE`) and checked by `topology_d209`:
- `BranchEntrypoint.segmentSuggestion(code, input)`;
- `HqEntrypoint.applySegmentSuggestionAnswer(answer)`.

Neither takes a secret, by the escalation's rule. A forged call can only file a suggestion HQ reads and declines, or decide a copy whose HQ uid it would have to know. The behaviour lives in `rpc/segmentSuggestionOps.ts` and `services/segmentSuggestions.ts`, so it is tested; `rpc/index.ts` only delegates.
