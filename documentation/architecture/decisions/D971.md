## D971 — Spin-Out Lab: How it runs, Settings and Activity

Issue #2756, part of #2374. Canvas: Spin-Out Lab Admin Page, SL12, SL12s,
SL13, SL13d, SL14, SL14s, SL21 and SL21c. No migration.

### Playbook

Three literal header tabs and routes sit under the existing Lab header, without
an Eadwyn rail. How it runs reads D954's published playbook. An Admin reads
“HQ writes the playbook.” A Super Admin can switch to the draft, edit a section
in a dialog, then separately confirm publishing a new version. A failed save
keeps the entered text and refusal in that dialog. Successful dialog completion
refreshes the read. Every write retains D954's Super Admin gate and audit.

Migration 560 seeds no Lab sections. The existing section edit path therefore
accepts the canvas's ten fixed Lab section keys and creates a missing draft
section only after validating the requested edit, in the same batch. Unknown
keys and other programs retain their existing behavior. The read supplies a
heading catalogue but writes nothing; missing text says Not recorded with its
reason. No canvas sample is saved as factual program content. Editing calendar
wording does not change the Lab clock. The calendar section links to the live
cohort calendar instead of reproducing the canvas's sample-dated chart.

The monthly checklist and admin tools use the canvas's copy and link to their
live desks. They remain available when the independent playbook read fails.

### Settings

GET /api/admin/cohort/settings reads the existing operative settings and their
established defaults, without a bootstrap. Minimum and Places edit one field
at a time through the existing audited POST /applications/settings. Each dialog
explains its effect, refuses blank/fractional/out-of-range input, preserves a
recorded zero, and retains a server refusal. The fixed calendar, time zone,
eligible account types and message kinds are read-only.

A Super Admin can explicitly select a licensed studio from D982's grant read.
No studio is silently selected, HQ-held accounts are not assigned a subsidiary
grant, and unset terms are Not recorded. Terms cannot be edited here. Following
S1's release comment, an Admin's grant block says “Not read here yet” and names
#2775; it never calls the Super Admin grant API. This is the intentionally
remaining dependency, not an empty grant or a zero term.

### Activity

GET /api/admin/cohort/activity is Admin gated and read-only. One SQLite statement
unions existing cohort events, notification ledger, week transition log,
latest interview records, selected host/certificate/playbook audit actions and
Lab formation actions. Type, cohort, actor category and literal search are
bound filters; search includes the displayed event names and runs on explicit
submission rather than each keystroke. Sorting is allowlisted, pages are bounded and the count survives
an empty/out-of-range page. No per-source cap is silently merged in the browser.

The log never returns staff identities, emails, raw actor identifiers or
free-form reasons/audit payloads. Actor categories are the Lab's clock or an
admin. An admin subject is labelled Admin account. A missing cohort/subject is
Not recorded; an interview linked to multiple cohorts is not assigned one by
guesswork. Formation uses the current shared Lab-participant rule and states
that its historical cohort is not recorded. Interview rows are labelled latest
records, not a complete historical event stream. Coverage is stated on the page.
Any unavailable required source produces 503 rather than an empty successful log.

Support sessions independently reuse D946's Super Admin client. Search, sort
and pages cover the explicitly stated newest 100 sessions; target email is not
rendered. An Admin sees the canvas's Super Admin callout and makes no session
request. One failed block does not erase the other.

All Lab timestamps use parseStamp for zone-less D1 UTC and display
America/New_York, including interview schedules and support-session times.
Incomplete successful responses are treated as unreadable. These three tabs
say Unreadable with Try again; refresh failures retain clearly labelled stale
data and disable writes until a fresh successful read.
