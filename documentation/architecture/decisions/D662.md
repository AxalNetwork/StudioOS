## D662 — Build cycle stores and project-scoped reads

Issue #1475, 2026-10-09, part of #1469 (D656). Migration 441. S18.

### Decision

`GET /api/cycles/build/overview?project=:id` returns the four Build figures and
six cards. `GET /api/cycles/build/modules/:slug` returns one card and its
working records table. The response follows D656 and D661. The six card reads
are isolated: if one table is unreadable, only the dependent card reports
`unreadable`, with its source named and no raw database error. The two headline
figures derived from the failed card also report `unreadable`.

### Reuse and new stores

| Module | Existing source | Migration 441 |
| --- | --- | --- |
| Solution design | `mvp_features`, `pain_groups`, `hypotheses` | feature links; founder-owned `venture_risks` |
| Prototype / MVP | `mvp_features` and its delivery writer | must-have flag, completion transition date, owner, due date; `projects.mvp_target_date` |
| Product roadmap | `roadmap_okrs`, `okr_column_moves` | owner, target date, KPI key |
| Founding team | `cap_table_holders`, `cap_table_vesting` | founder role on the project holder |
| Company creation | `projects.incorporation_meta`, `projects.entity_id`, `entity_obligations` | project `formation_steps`, obligation proof key, project IP copy |
| Operating systems | `integrations`, `integration_companies`, `ritual_runs` | `project_core_systems` maps each of the core five to a chosen connector |

`venture_risk_overrides` from migration 114 is the deal team's analyst rating.
It is not a founder risk register and is not exposed by these reads. A Lab
venture is the same `projects` row used by the founder's Build cycle. The
accepted Lab application's IP and tech-transfer fields can be copied to
`projects.spinout_ip_meta` with an explicit application id; the source must
belong to the caller. No answer is inferred from the current user merely
because that user owns more than one project.

The existing MVP-scope writer still owns `delivery_status`. Migration 441's
triggers record the date of future transitions into `Done` and clear it when a
feature is reopened. An already-Done row with no date stays undated; its done
count is real, but no historical point is invented. The MVP target date is
`not_recorded` until the founder enters it.

Vesting joins on both `holder_id` and `user_id`, after constraining holders to
the requested project. Another project's founder or a different user's
schedule cannot enter this table. The vesting chart labels the recorded cliff.
The Agreement cell reads the latest document status only when a project-level
co-founder agreement names that holder's user as a party. It does not claim
that a particular party signed. The project has a single entity pointer;
its obligations supply the next three open filings. A project without that
pointer has no inferred filings.

The five system kinds are bank, accounting, payroll, CRM and product
analytics. A mapping may use only a connector owned by the actor and enabled
for this project's company. Reads join `integration_companies.enabled = 1`
again, so withdrawing company access immediately hides the mapping. They
expose provider, status and last successful sync, never credentials or personal
connector data. A connector in error reads `Failing` and keeps its last good
sync; a personal connector not enabled for the company never counts.

### Writes and access

Founders owning the venture and admins may write D662 fields. Partners may
read but cannot write. Every write is bound to a project and records the actor
in `activity_logs`. Feature links are checked against the same project. Owner
ids must be members of the project's company. The routes accept dates only as
real `YYYY-MM-DD` values. Credentials and application answers remain private
to their original user. Existing feature, roadmap, cap table and obligation
endpoints keep writing their pre-D662 fields.

### Limits and rollout

The module's Test cell is the linked hypothesis; no separate test result store
exists. Individual agreement signing status is not recorded. No completion history
is fabricated for existing Done features. The card's `next` action is derived
from records. The SPA cycle components are D661; mounting them is a separate
frontend step as its reads land.

Migration 441 is additive. Rolling back the Worker leaves the columns and
tables unused; no existing row is deleted. No credential, personal connector
record or production data is migrated. The route is authenticated and scoped
before any module query.
