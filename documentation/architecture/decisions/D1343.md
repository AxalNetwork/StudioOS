## D1343 — Email part 4: Eadwyn on MCP (`mail_context`, `mail_draft`) and a member's own MCP mail server as a mailbox

- **Status:** built by S17, 2026-10-28 (#3551, part 4 of Email, #3547).
- **Basis:** `origin/main` at `daed664fd1`. Paths are relative to `cloudflare-worker/src/`.
- **Map:** D1347. D1340 (mailboxes and send) and D1341 (drafts) are the parts this builds on.
- **Migration:** none. A mailbox on an MCP server is a `mail_accounts` row (migration 647) with provider `mcp`.

### 1. Two tools on Axal's MCP server, neither sends

`mcp/tools/mail.ts`, registered by `mcp/server.ts`:

| Tool | Scope | What it does |
|---|---|---|
| `mail_context` | `mail:read` | D1341's context pack for one person (`kind:id`), read-only: the person's record and the company's one-liner and KPI board, each through its module's own read, with its date and link. |
| `mail_draft` | `mail:write` | One draft, run and stored exactly as `POST /api/mail/drafts` runs it: `runDraft` (`services/mail/drafts.ts`), now shared by the route and the tool. Charged once to the member's AI tokens by the router, on rail `{ page: 'Email', option: 'draft:email' }`, and kept in `mail_drafts`. Answers `{ draft, sent: false, open_in: '/email' }`. |

**There is no `mail_send` tool.** A send stays a press in Axal VC, behind the composer's one-use confirmation nonce (D1340). An assistant can read and draft; the member sends.

**The grant bounds the pack.** A `project`, or a person whose record belongs to a company, outside the companies the connection was approved for is `404 not_found`, "Record not found.", the same as a record that does not exist. A person with no company (an advisor engagement, a Network match from D1342) is the member's own, under the scope.

**Scopes.** `mail:read` ("Read the records Eadwyn may quote in an email to someone, with their dates. Never sends.") and `mail:write` ("Draft emails with Eadwyn, charged to your AI tokens. Drafts are kept in Axal VC; nothing is sent."). They are added to `mcp/oauth.ts`'s `SCOPES`, the API key labels (`services/apiKeys.ts`, where `mail:write` is a write), the consent copy (`routes/mcp_consent.ts`) and the SPA's `assistantConsentModel.js`. Both tools are in `METERING_POLICY` at 0: the draft's AI tokens are charged by the router, not per call. A short balance or a pause answers in the ledger's own words (`refusalFor`).

**The tools import no mail service.** `mcp/server.ts` is reached from `auth.ts` (through `mcp/grants.ts` and `mcp/oauth.ts`). The context pack reaches every module's record read, and from there Stripe and Mercury code that D707's and D714's import guards keep out of that graph. So `mcp/tools/mail.ts` imports only the import-free `intents.ts`. The Worker's entry hands the services in with `bindMailTools()` (`services/mail/mcpTools.ts`), and a tool called before that answers 503, "Email is not available right now." `runDraft` names its page at the router call (`surface: AI_SURFACE.mailDraft`), where D552's scan reads it. D552's table now lists `services/mail/drafts.ts` for `mailDraft`.

### 2. A member's own MCP mail server as a mailbox

D852 lets a member add a remote MCP server and approve its **read** tools. The D847 client refuses every write tool except a connector's one D856 setup tool, which it calls only with a one-use in-process ticket. Sending mail is a write, so it uses that path:

1. **Designate the send tool.** `POST /api/connectors/custom/:uid/tools/:name/mail-send` (`routes/connectors_custom.ts` → `approveMailSendTool` in `integrations/customMcp.ts`). The tool must be listed now, must not be marked destructive (409 `tool_destructive`), must take `{ to, subject, body }` as strings, and must not be one of the member's approved read tools (409 `tool_shape`). It is pinned to the schema shown, as a read tool is. `DELETE` withdraws it. Each writes an activity row.
2. **Save the connector as a mailbox.** `POST /api/mail/accounts/mcp` takes `{ connection_uid, address, display_name? }`. It is 404 `provider_unknown` while custom connectors are off, 404 `connector_not_found` for none or another member's, and 409 `send_tool_not_approved` before a tool is designated. It verifies (the tool still listed against its pin; nothing is sent) and saves provider `mcp`. The sealed credentials name only the connection and its owner; the server's tokens stay the connector's. `GET /api/mail/accounts`' `providers` gains `mcp`.
3. **Send.** Unchanged in `routes/mail_accounts.ts`: the composer's nonce is spent first. Then `services/mail/adapters/memberMcp.ts` calls `sendThroughCustom`, which mints the ticket and calls the pinned tool once, keeping a short message id. A changed schema or an expired sign-in turns the mailbox `expired` with a sentence; nothing the server says is shown.

`sendThroughCustom` is the second minter of a D856 setup ticket after `routes/channels.ts`, and like it, mints only after a person's confirmation: here, the composer's spent send nonce. D847's test names both. `customProvider` lists the designated tool as the connector's only setup tool, so nothing on Axal's MCP server, and no other caller, can reach it. `sendThroughCustom` also checks the tool is on the session's offered setup list before calling. The client refuses such a call anyway, so this check is defence in depth; it is the one mutation the tests do not catch (§3).

### 3. Verified

- `cloudflare-worker/test/mail_mcp_tools_d1343.test.ts` (5 tests, the real migrated schema, the MCP server with an in-memory rate-limit KV):
  1. the two tools, their scopes and their price; no registered tool sends;
  2. before the entry hands the services in, a tool answers 503 and runs nothing, and `mail.ts` imports no mail service;
  3. each tool refuses without its scope, and is not listed without it;
  4. `mail_context` returns the pack with the person's record selected; a person outside the grant's companies, or a `project` outside it, is "Record not found.";
  5. `mail_draft` charges once through the router, stores one draft carrying that charge, sends nothing and answers `sent: false`, `open_in: '/email'`; a short balance refuses in the ledger's words and stores nothing.
- `cloudflare-worker/test/mail_mcp_mailbox_d1343.test.ts` (5 tests, D852's custom-connector harness with a fake server listing `send_email` and a read-only `preview_email` of the same shape):
  1. the send shape is `{ to, subject, body }`, each a string;
  2. designation refuses an unlisted tool, a destructive one, the wrong shape and an approved read tool, and pins the one it takes; another member's connector is 404;
  3. a mailbox needs a designated tool (409 `send_tool_not_approved`); choosing it sends nothing and returns no credential; a send without the nonce is 403 and calls nothing; with it the tool is called once; another member's connector is 404;
  4. a tool changed since it was designated, or withdrawn, turns the mailbox `expired` (409 `mailbox_expired`) and is never called;
  5. the designated tool is never callable as a read tool, nor through the session without the ticket.
- 12 mutations were run and 11 were caught. The survivor is the redundant offered-list check in `sendThroughCustom` (§2).
- The client method is `connectMcp` in `frontend/src/lib/api/mail.js`. The scope lists in `member_api_keys_d841` and `developer_assistants_d1316` gain the two scopes.
