### 1. Registering a webhook

A Super Admin registers a company's named webhooks with
`POST /api/admin/work-graph/releases/webhooks { tenant_id, company_id, op, name, url, audiences, expected_seq,
idempotency_key }`. It is gated by `requireSuperAdminWriteBar`.

- **`register`** names an https URL on a public host and the audiences the webhook may carry. A URL with
  credentials, a fragment, an IP literal or a bare host is refused. Registering again with a new URL or new audiences
  is the next `seq`.
- **`disable`** stops a webhook. Rows are append-only, so the history is kept.
- **Refusals:** `webhook_invalid`, `wrong_tenant`, `stale_webhook` (with the current webhook), `not_registered`,
  `webhook_limit` (10 active per company) and `idempotency_conflict`. A replay answers the first request. Every
  attempt is an admin audit row.
- **`GET /webhooks`** lists them, each with its `ref`, `webhook:t<tenant>.c<company>.<name>`, which a publish names as
  its `external_distribution` target. It also returns `signing`, which says whether the Worker holds the key:
  without it nothing is sent.

### 2. What is sent

For a publish, one `POST` to the URL:

- **The body:** part 6's `releaseRecord` (ids and digests only, never content or a source locator), plus the event,
  the channel's id for it, and the tenant and company.
- **`X-StudioOS-Event`:** `release.published`, or `release.withdrawn` for a takedown's withdrawal.
- **`X-StudioOS-Release-Key`:** the effect's idempotency key. **A receiver must treat a repeat of a key as the same
  delivery.**
- **`X-StudioOS-Signature`:** `t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<body>">` under the signing key. The
  timestamp is signed, so a receiver can refuse a replay.

Before the request:

- the URL and every address it resolves to must be public (`publicHostRefusal`);
- the webhook must be active and carry the release's audience.

A redirect is never followed: a signed request is not re-sent somewhere else, and a 3xx is a refusal. A request waits
at most 10 seconds.

How the outcomes map, through part 6's adapter:

| Outcome | Result |
|---|---|
| 2xx | accepted |
| 5xx, 429, unreachable | `provider_unavailable`, retried with backoff |
| 401 or 403 | `provider_unauthorized` |
| any other refusal (3xx, other 4xx, a refused host, a disabled or unknown webhook, an audience the webhook does not carry) | `provider_rejected` |

### 3. The ledger, and why it makes lookup honest

A receiver has no read API, so `work_graph_release_webhook_sends` records each request the receiver accepted, as
`published` or `withdrawn`, under the release key. The channel's `find` reads it, and the read is always complete:

- A lookup after an accepted publish confirms it with the same external id and sends nothing.
- A request whose answer was lost is not recorded, so the next attempt sends it again under the same key. The key is
  what makes that safe at the receiver.

A withdrawal is sent for each accepted, not yet withdrawn publication of the manifest, and recorded once. After it
there is nothing to retract.

### 4. The secret

One HMAC key, the Worker secret `RELEASE_WEBHOOK_SIGNING_KEY`, which the owner sets with `wrangler secret put`. It is
never stored in D1, logged, or returned by any route. The owner gives it to each receiver out of band. Keys per
webhook would need a stored secret per row, and are left for a later part if a second receiver needs its own key.

### Rollback

Revert the Worker. The tables stay and nothing reads them; the channel is no longer offered, and an effect naming it
refuses `target_not_configured` as before. Removing the secret has the same effect without a deploy.
