## D639 — One access rule for every document handler, and co-founder NDAs record uids

**Issue:** #1396, moved from S10 to S07 at the owner's request. **Built by:** S07.
**Migration:** 428 (`428_cofounder_nda_uids.sql`), which rewrites NDAs written
before this change.

### One access rule for documents

`GET /api/legal/documents/:id` already decided through
`canAccessFounderResource` (`auth.ts`). Two other handlers in `routes/legal.ts`
had their own role list, and that list included investors:

| Handler | Before | Now |
|---|---|---|
| `POST /templates/:key/generate` | admin, partner and **investor** could generate an unattached document | the rule: a project's document for an admin, a partner or that project's founder; an unattached one for an admin or a partner only |
| `GET /documents` | admin, partner and **investor** listed **every** document | every row passes the rule, so the list holds exactly what the single read opens |
| `GET /documents/:id` | the rule | unchanged |

- **Admins and partners keep what they had.**
- **A founder sees their own projects' documents,** as before.
- **An investor lists none and generates none.**
  - The rule gives investors no unmasked founder data (its own comment says
    why).
  - The list used to give them every document's metadata, project and title,
    across founders.
- **The list's SQL reads; the predicate decides each row,** so the list and the
  read cannot disagree.
- **The owner column used for the rule is not returned.** `safeDoc` drops it,
  along with the content.
- **A refused generate is a sentence:**
  - "You can only generate documents for your own project."
  - "Only an admin or a partner can generate a document that belongs to no
    project."

### Co-founder NDAs

- **Uids, not emails.** Each NDA's title is "Co-founder Mutual Non-Disclosure
  Agreement — <uid>". When it is signed, `documents.signed_by` holds the
  signer's uid; it used to hold the email.
- **Only the two members sign.**
  - `loadConnectionOr403` admits an admin, so an admin can read any connection.
    It also let an admin sign, and an admin who is not a member was recorded
    as party B.
  - Signing is now refused to anyone but the two members: 403 `not_a_party`,
    "Only the two people in this connection can sign its NDA. Nothing was
    signed."
  - An admin still reads the connection.
- **A neutral label in place of an email.**
  - `renderNda` printed `name || email`, so a member with an empty name, or a
    name defaulted from their email, had their address written into the
    counterparty's NDA before both had signed. That is what D610 withholds.
  - `ndaName` treats an empty name, the whole address and the part before the
    @ as no name.
  - The counterparty then reads "your co-founder", and the signer reads "the
    signing party".
  - The signer's own email still appears on their own NDA's signature line.

### Migration 428

- **What it rewrites.** It matches each NDA to its signer through
  `cofounder_connections` (side A's document to user A, side B's to user B),
  then rewrites the title and `signed_by` of rows that still hold an "@".
- **A signer whose account is gone** gets "a former member" in the title (the
  column is NOT NULL) and a NULL `signed_by`.
- **An NDA that no connection points at is left as written.** Connections are
  closed, never deleted, so there should be none, and there is no signer to
  read a uid from.
- **Only `nda_cofounder` documents are touched,** and the migration is
  re-runnable.

### Verified

**`cloudflare-worker/test/legal_docs_nda_d639.test.ts`**, on the real routers
and node:sqlite:
- **Every role agrees across the three handlers.** For an admin, a partner, an
  investor, the project's founder and another project's founder, the list
  equals what the single read opens. Generate is admitted for the same
  projects, and an unattached document is for staff only.
- **The project filter** narrows the same way.
- **A new NDA** holds no email in its title or `signed_by`.
- **Signing:** an admin and a non-member are refused, and nothing is written.
- **The neutral label** appears for an empty name, the whole email and its local
  part, both directly and through the route.
- **Migration 428** rewrites by connection side, handles a deleted signer,
  leaves other documents alone, and re-runs cleanly.

Every assertion is mutation-checked. Four mutants survived the first pass:
- Three were the list's own SQL restating the rule, so the list now leaves
  that decision to the predicate alone.
- One was an NDA no connection points at; the migration test now has one.
