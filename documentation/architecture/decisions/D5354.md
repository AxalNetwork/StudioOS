## D5354 — CRM-driven deal moves use the transition policy (#5354)

- **Status:** Built for #5354, 2026-11-10.
- **Builds on:** D4632's version-guarded deal transition batch.
- **Migration:** `202611101052_deal_stage_event_source.sql` adds the closed CRM source to stage history.

### Decision

1. HubSpot pull, webhook and import, Salesforce pull, and Affinity pull call
   `runSystemMove`. The helper re-reads the deal's status and
   `stage_changed_at`, then uses D4632's one batch for the history row and
   update. A lost race changes neither; a repeated mapped stage is a no-op.
2. A system history row has no `actor_user_id`. Its `source` is one of
   `hubspot`, `salesforce` or `affinity`, so readers can distinguish a CRM
   sync from an unexplained anonymous move. Existing tenant and enabled-company
   scoping remains at each provider before it calls the helper.
3. A CRM mapping to `rejected` is recorded as a pass. The existing checked
   reason category is `thesis`; `pass_note` is fixed application text naming
   the CRM. Provider text is never trusted as a pass reason. Moving back out
   of `rejected` clears the old pass fields.
4. The `pipeline_advance` queue case is retired. Current `main` has no
   `Jobs.enqueue` caller for it; only its dead handler and type remained. The
   similarly named Partner Network activity kind is historical telemetry, not
   a queue job, and remains readable.

### Verification contract

Executable SQLite tests cover each CRM source, a rejected mapping, a repeat,
and a race injected between the version read and the batch. A source scan
keeps direct `UPDATE deals SET status` statements inside
`services/dealTransitions.ts` only.
