## D1217 — Company receiving instructions and sender-only Closing reports

**Task:** #3214, part of #2424. **Slot:** S17. **Migration:** 613.

### Built in this draft

Migration 613 creates company-owned, versioned receiving instructions and a
separate reveal ledger. It also adds sender-only `sent_*` metadata to existing
commitments, the fallback expressly permitted by #3214 while #3212 builds the
Closing line store. It does not change pending/confirmed/withdrawn status.
New reported amounts use integer cents and an explicit currency.

`companyReceivingAccounts.ts` prepares masked reads, founder writes, logged
investor reveals and account-change notices. Instructions use the existing
column cipher with an immutable version identity. Ordinary responses contain
only the account's last four digits. The primary company administrator must
also own the project's founder record; an admin or support session has no
bypass. A conditional version change and its actor record commit together.
Stale saves return a conflict; unchanged normalized instructions are a no-op.
The owner can replace instructions that are unreadable after a key change.

An account replacement sends the existing notification service's in-app and
email notice to each distinct investor with a pending commitment across that
company's projects. Sent but unconfirmed lines remain pending. Confirmed,
withdrawn and other companies' lines are excluded. The notice carries CP9's
warning to call the company on a number already held. It contains no account
number and introduces no payment pause or hold. Delivery follows existing
notification preferences and best-effort transport; this draft does not
promise email delivery or add a delivery queue.

The prepared investor reveal writes its number-free audit entry before any
unmasked response. Audit failure refuses the reveal. The response specifies a
30-second display period and carries no-store headers. A client must enforce
that display period when a later task connects CP9; an API response cannot
retract a number already disclosed. A mismatched account/line currency refuses
unmasked instructions.

Accepting the investor's own Mercury Closing proposal conditionally accepts
the proposal, records the sender metadata and writes its actor log in one D1
batch. Stale, foreign, withdrawn, received and already-sent lines cannot be
accepted. The line remains pending: `sent_at` means **Sent, not yet confirmed**,
never Received. Confirmed totals and receiving-side evidence are untouched.
Only currently unsent pending USD commitments enter the existing USD matcher.
No bank request or money movement is introduced. Other Mercury proposal kinds
keep their existing behavior.

### Integration pending S01

The module's intended mount is
`/api/closings/company-receiving-accounts`: `GET /:projectId` (masked),
`PUT /:projectId` (founder save), and `POST /:projectId/reveal` (investor reveal).
**It is not mounted in this draft.** No frontend client or shared export has
been added. Shared router ownership requires S01's answer on #3214.

The present commitment store has no explicit signed-envelope link. The testable
legacy bridge requires an own non-withdrawn commitment, a SAFE issuance for the
same venture and amount, a completed SAFE envelope for the same deal, and that
investor's signed recipient. An unrelated signed document does not qualify.
This bridge is prepared pending S01's A/B answer on #3214; it must not be enabled
before that answer. Alternatively #3212 can supply its explicit line/signature
contract. Non-SAFE paper remains unavailable through this bridge.

#3210's Closing UI and #3212's line store were not on this draft's base commit.
The UI's Sent label, CP9 dialog, timed hide, client calls and route registration
are therefore not claimed as shipped here. #3214 remains open until integration
and the signed-line contract are settled.

the PR; built `docs/` output is never committed.

availability and recovery, live notification delivery, signed-paper mapping,
CP9's 30-second UI behavior, the mounted route/client, and the deployed Closing

retain migration 613's data rather than dropping receiving instructions or
reveal history.
