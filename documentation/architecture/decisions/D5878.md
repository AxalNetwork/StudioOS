## D5878 — The Inbox keeps per-lane reads and moves its search, filters, sort, paging and tiles into each lane's SQL; no approval projection table (#5878)

- **Status:** evaluated 2026-11-14 by S09. Filed under #4716, package 5 ("Reduce read amplification"), last bullet.
- **Evaluation only.** This file changes no code under `cloudflare-worker/src` or `frontend/src`.
- **Schema change: none.** The recommendation adds no table, column, index, view or trigger. It reads the lanes' own stores and the existing `approval_assignments` table, joining on that table's existing `UNIQUE (lane, item_id)` (`cloudflare-worker/sql/migrations/341_approval_assignments.sql:19`). So it is **not** an owner question on #4716. The build tasks in §6 go to the coordinator to file.
- Every citation is `path:line` on `origin/main` at `911e4ce2`.

### 1. What the Inbox does today

`GET /api/admin/approvals` picks the reader's lanes and hands them to `hqInbox` (`cloudflare-worker/src/routes/admin_approvals.ts:43-47`, `:57-61`). A Super Admin gets every studio lane plus HQ's lanes (`cloudflare-worker/src/services/hqApprovalSources.ts:222-224`, `cloudflare-worker/src/services/approvalSources.ts:696-698`). That is 20 studio lanes (`approvalSources.ts:163-508`) and 9 HQ lanes (`hqApprovalSources.ts:26-213`), 29 in all. A plain admin gets the 20.

Each Inbox request does the following, whatever page, filter or sort it asks for:

1. **Every lane is read to 1,000 rows.** `hqInbox` calls `approvalBoard(env, INBOX_LANE_CAP, …)` (`cloudflare-worker/src/services/approvalAssignments.ts:451`), and `INBOX_LANE_CAP = 1000` (`approvalAssignments.ts:381`).
   - `approvalBoard` runs each lane's `rowsSql` one after another in a `for … await` loop, binding the cap as its `LIMIT ?` (`approvalSources.ts:639-643`).
   - It computes each row's age and band in the Worker (`approvalSources.ts:646-655`), then sorts every row oldest first (`approvalSources.ts:670-674`).
2. **A capped lane gets a second read.** A lane that hit the cap is counted again with `laneCounts` (`approvalAssignments.ts:452-458`).
3. **The whole assignment record is read.** `readAssignmentState` sends two probe statements (`approvalAssignments.ts:70-79`). It then reads `approval_assignments` joined to `users` up to `READ_CAP = 5000` rows (`approvalAssignments.ts:28`, `:87-92`). It reads every active admin too (`approvalAssignments.ts:114-116`). If the record reaches 5,000 rows it is reported unreadable (`approvalAssignments.ts:94-101`).
4. **The tiles are computed in the Worker.** `over_72h`, `assigned_to_me`, `per_admin`, `unassigned`, `overdue_unassigned` and `oldest` are all worked out from every row read (`approvalAssignments.ts:467-495`). Any lane that is unreadable or capped sets them to null (`approvalAssignments.ts:465`).
5. **Search, filters and sort run in memory.** `filterInbox` does all three (`approvalAssignments.ts:503-504`). The file's own header says so: "ALL OF IT RUNS ON THE ROWS THE BOARD ALREADY READ … applied in memory" (`cloudflare-worker/src/services/approvalInbox.ts:7-10`).
   - Search is a lower-case substring match on `who`, `what` and `lane_label` (`approvalInbox.ts:101`).
   - The `who` and `lane` sorts use `localeCompare('en', { sensitivity: 'base' })` (`approvalInbox.ts:109-110`).
   - The `oldest` sort keeps the board's own order (`approvalInbox.ts:102`).
6. **A page is sliced out of the result.** 25 rows are cut from the filtered array (`approvalAssignments.ts:375`, `:509-511`).
   - A filtered total is withheld when any lane is capped (`approvalAssignments.ts:507`).
   - A lane's age-band split is withheld at the cap (`approvalInbox.ts:133`).

At least two other readers depend on the same capped board:

- **The one-item page** reads its lane to the cap and searches the result (`approvalAssignments.ts:398-403`). That is #5874.
- **The assignment write** checks its targets the same way (`approvalAssignments.ts:208-225`). That is #5874 as well.
- **The weekly Decided series** takes the board at 1,000 rows for waiting arrivals (`cloudflare-worker/src/services/approvalDecisions.ts:678`, `:730-734`).

**How many statements that is.** For a Super Admin, one request is 29 lane statements, run one at a time, plus 4 statements for the assignment state. Capped lanes add their counts on top. Moving to page 2, changing a filter or typing a search character re-runs all of it. Search is not debounced yet; that is #5881.

### 2. The options

#### Option A: keep per-lane reads, and move the filters into each lane's SQL

Each lane keeps its own store and its own predicate, as now.

- **Split each lane's SQL.** Today each lane has one `rowsSql` ending in `ORDER BY … LIMIT ?` (`approvalSources.ts:83-92`). It becomes two literal constants:
  - `openSql`: `SELECT id, who, what, created_at FROM … WHERE <the lane's predicate>`, with no order and no limit;
  - the lane's `ORDER BY`.
- **Build every statement from constants.** `rowsSql` is then `openSql + order + ' LIMIT ?'`. The Inbox wraps `openSql` in constant heads and tails, the same way the Decided log already wraps each lane (`approvalDecisions.ts:490-505`). Nothing a caller sends reaches the query text, which `check-sql-prepare` requires (`approvalDecisions.ts:18-21`).
- **Push each part of the query into SQL:**

| Part of the query | Where it goes |
|---|---|
| Lane and group filters | They choose which sources are read for rows (`LANE_GROUP`, `approvalInbox.ts:24-32`). Every lane is still read for its summary, because the tiles cover every lane today whatever the filter (`approvalAssignments.ts:467-495`). |
| Age band | Bound cut-off stamps compared against `datetime(created_at)`. `unknown` is `datetime(created_at) IS NULL`. This replaces `slaFor` (`approvalSources.ts:575-580`) on the read path. |
| Search | `who LIKE ? ESCAPE '\'` or `what LIKE ? ESCAPE '\'`, using the shared needle builder (`cloudflare-worker/src/util/likeSearch.ts:38-42`). A query that matches the lane's label is decided in the Worker and bound as a flag, because `lane_label` is not a column. |
| Assigned filter and tiles | `LEFT JOIN approval_assignments a ON a.lane = ? AND a.item_id = b.id`, using the existing unique index (`341_approval_assignments.sql:19`). |
| Sort and page | Each lane returns at most `page × 25` rows in the requested order. The Worker merges the lanes and slices the page, which is how `decidedLog` pages across lanes (`approvalDecisions.ts:583-611`). The depth is capped like `DECIDED_MAX_PAGE` (`approvalDecisions.ts:557-559`). |
| Lane summary (count, each band, unassigned, assigned to the caller, oldest) | Aggregates over the same `openSql`. These replace `laneCounts`, `laneBands` and the tile filters, and they have no cap. |

- **Failure handling stays as it is.** A lane that throws is named in `unreadable`, and its count is `null`, never 0 (`approvalSources.ts:659-662`).

#### Option B: a projection table

One table per D1 database, for example `approval_inbox_items`, holding the fields #4716 lists:

- `lane`, `item_id`, `status`;
- `submitted_at`, `who`, `what`;
- `assignee_id`, `decided_at`, `decided_by`, `outcome`;
- routing metadata: `scope`, `group` and the KYB studio code bound at `approvalSources.ts:367`.

It would be indexed on `(status, submitted_at)`, `(lane, status, submitted_at)` and `(assignee_id, status)`, beside a per-lane state table, `approval_inbox_builds (lane, built_at, ok, error)`. The Inbox would then be a single `SELECT … WHERE status = 'open' AND <filters> ORDER BY … LIMIT 25 OFFSET ?` plus a `COUNT(*)`.

**What would write it.** Dual writes from the decide routes cannot keep it correct on their own, because whether an item is in a queue often depends on rows in other tables that the lane's own route never touches:

| Lane | Its membership changes when… |
|---|---|
| Exploring | an e-sign envelope completes (`approvalSources.ts:141-144`) |
| KYB | a linked user's admin role changes (`approvalSources.ts:359`) |
| Wellbeing experts | the profile's completion percentage passes 70 on an edit (`approvalSources.ts:394-402`) |
| Features and tasks (HQ) | a `feature_request_reviews` row appears (`hqApprovalSources.ts:74-80`) |

- **The decide routes are many.** A grep of `cloudflare-worker/src` for `UPDATE <table>` over the 20 studio-lane tables finds 36 files, and 14 more files touch `kyc_status = `. HQ's nine lanes are on top of that. Each would need a second write, and any one that was missed would leave the projection silently wrong.
- **`who` and `what` would go stale.** They are copied from `users`, `partners` and `projects` (for example `approvalSources.ts:170`, `:377`, `:466`), so a rename would not reach the projection.
- **A trigger is not allowed.** The house rules say "never create a trigger by hand" (`AGENTS.md:341-342`).

**What would rebuild it.** The projection could only stay correct through a rebuild that re-runs every lane's predicate:

- per lane, `DELETE` the lane's open rows and `INSERT … SELECT` from that lane's `openSql`, in one `DB.batch`;
- then upsert the lane's `approval_inbox_builds` row with `ok = 1`;
- on a failure, write `ok = 0` with the error and keep the last good rows.

It would run from the per-minute cron (`wrangler.toml:646-654`) on HQ and on every branch database. Decide routes could also mark their lane dirty to trigger an early rebuild. Assignment columns would be written by `assignReviewers` (`approvalAssignments.ts:233-245`).

**How a stale or failed projection would be shown.** It would never be shown as an empty queue:

- Every lane would carry `built_at` from `approval_inbox_builds`.
- **Never built.** A lane with no build row, which is every lane on the day the migration lands, would be reported as `unreadable` with its count `null`, exactly as a failed lane is today (`approvalSources.ts:659-662`). An empty table would never be read as "nothing is waiting".
- **Failed, or older than its bound.** A lane whose last build failed, or is older than its bound (say 5 minutes), would keep its last good rows and be marked `stale: { built_at, reason }`. The tiles that include it would answer `null` with the reason, as capped or unreadable lanes make them do today (`approvalAssignments.ts:465`, `:482-495`). The response would carry `as_of` so the page can say "as of 14:02".
- **Just decided.** An item decided in the last minutes would still appear until the next build. The page would have to say so: "Decided items can take up to N minutes to leave the Inbox."

### 3. Cost in D1 reads for a typical Inbox page

**How D1 counts.** D1 bills rows read, which is the rows a statement scans, index entries and joined rows included. The platform does not record rows read per Inbox request today (task T1 below adds that), so the figures below are **illustrative, not measured**.

**Symbols:**

| Symbol | Meaning |
|---|---|
| `S_l` | rows that lane `l`'s predicate scans (the whole table where no index matches) |
| `O` | open items across all lanes |
| `A` | rows in `approval_assignments` |
| `U` | rows in `users` |
| `p` | the page number |

Several predicates have no matching index. No migration under `cloudflare-worker/sql/` indexes `users(kyc_status)` or `users(role)`, so the KYC lane (`approvalSources.ts:239-243`), the Exploring lane (`approvalSources.ts:274-282`, with correlated subqueries per row at `:141-144`) and the reviewer read (`approvalAssignments.ts:114-116`) each scan `users` in full.

**Assumed sizes** for the illustration: an HQ database with `U = 5,000`, `A = 2,000`, `O = 300`, and 20,000 rows across the other lane tables.

| | Statements per request | Rows read per request | Grows with |
|---|---|---|---|
| **Today** | 33 for a Super Admin, sequential (29 lanes and 4 for assignment), plus 1 for each capped lane | Σ`S_l` + `O` (user joins) + 2`A` + `U` ≈ 30,000 + 300 + 4,000 + 5,000 ≈ **39,000** | the size of the lane tables and the assignment record, for every page, filter and keystroke |
| **A** | 29 summaries and up to 29 page reads (one statement per lane once T4 merges them), in parallel under #5877, plus the page-scoped assignment and workload reads of #5875 | Σ`S_l` + `O` (user joins and assignment index lookups) + ~`A` (#5875's workload `GROUP BY`) ≈ **35,000**. Rows returned to the Worker drop from up to 29,000 to at most `29 × 25p` (725 on page 1). | the size of the lane tables. The rows returned scale with the page. |
| **B, page read** | 2 or 3 (list, count, the build-state rows) | about `O + 25p + 29` ≈ **350** | open items and page depth |
| **B, rebuild** | 29 batches per run | about Σ`S_l` + `O` ≈ 30,000 **per run, per database**: 43 million a day at one run a minute, 2.9 million a day at one run every 15 minutes | lane tables × rebuild frequency |

**What the table shows.**

- **Option B is cheap per page but costs more overall.** With five admins making 100 Inbox requests a day each, today's Inbox reads about 19.5 million rows a day, while the minutely rebuild B would need to stay fresh reads about 43 million. B reads less only when it is allowed to go stale for many minutes, and an approvals inbox showing items already decided is the failure this programme keeps refusing.
- **Option A barely changes rows scanned.** Its D1 saving is the 5,000-row assignment read (#5875) and the repeat reads of capped lanes.
- **Option A's real gains** are that every count and tile becomes exact with no cap, the Worker stops holding and sorting up to 29,000 rows, and each response is bounded by the page.
- **Scans fall only with indexes on the unindexed predicates.** That would be a separate schema change, outside this recommendation (§5).

### 4. Recommendation

**Option A.** Keep each lane's own read from its own store, and move search, filters, sort, paging and the tiles into each lane's SQL, merging the lanes in the Worker the way the Decided log already does.

Do not build the projection. Queue membership depends on writes to tables the lanes' decide routes never touch (§2, Option B). That means only a full rebuild keeps a projection correct, and a rebuild costs more D1 reads than the Inbox it serves unless it is allowed to go stale. The gains Option A cannot give, scans proportional to the page, come more cheaply from indexes on the few unindexed predicates than from a second copy of 29 queues.

### 5. What this leaves open

- **Indexes.** If T1's measurement shows full scans dominate, an index-only migration on the unindexed predicates (`users(kyc_status)`, `users(role)` and any others T1 names) is the lever. That is a schema change, so it would be its own task and, if the coordinator thinks it needs one, its own owner question. It is not part of this recommendation and nothing below depends on it.
- **Sort and search outside ASCII.** SQL `LIKE` and `COLLATE NOCASE` fold case for ASCII only, while today's in-memory match uses `toLowerCase()` and `localeCompare` (`approvalInbox.ts:101`, `:109-110`).
  - A search for "é" would stop matching "É".
  - The `who` sort would order accented names by byte value.
  - T4 states this in its PR and adds a fixture for it. If it is not acceptable, T4 keeps the `who` sort's merge in the Worker over each lane's rows.
- **Open draft PR #6324 (#5879).** It moves each lane's label, group, scope, notice and destination into `services/approvalLaneRegistry.ts`, and edits `approvalInbox.ts`, `approvalSources.ts`, `hqApprovalSources.ts` and `approvalDecisions.ts`. It leaves each lane's SQL in its source file. T2 rewrites those same source entries, so **T2 starts after #6324 merges**. With the registry in place, group membership for the lane and group filters comes from the registry, not from `LANE_GROUP`.

### 6. Build tasks, each one PR, in order

None of them needs a migration. The response of `GET /api/admin/approvals` keeps its keys; the `capped` key and the cap reasons stop appearing once nothing is capped, and `frontend/src/pages/admin/approvals/AdminApprovals.jsx:758` already treats an absent `capped` as none.

1. **T1: measure.** `hqInbox` logs one line per request with the statement count and the sum of D1's `meta.rows_read` across its statements, using a console log only. No response change. This gives the real figure for §3's illustration and for the index question in §5.
2. **T2: split each lane's SQL into `openSql` and its order** (after #6324). Every source in `APPROVAL_SOURCES` and `HQ_APPROVAL_SOURCES` gets a literal `openSql` and order, and `rowsSql` is derived from them by concatenating constants. A test holds each derived `rowsSql` byte-equal to today's text, so nothing that reads `rowsSql` changes.
3. **T3: lane summaries and tiles in SQL.**
   - One aggregate statement per lane over `openSql` joined to `approval_assignments` gives the count, each age band, unassigned, assigned to the caller, overdue unassigned and the oldest arrival.
   - `hqInbox`'s tiles and `laneBands` come from those statements. `per_admin` comes from #5875's workload `GROUP BY`.
   - Tiles and bands are no longer nulled by a cap. An unreadable lane still nulls them.
   - Depends on T2, and on #5875 for `per_admin`.
4. **T4: the page read in SQL.**
   - Each lane in scope returns at most `page × 25` filtered rows in the requested order, with age, search and assigned bound as parameters. Lane and group choose the sources.
   - The Worker merges the lanes and slices the page. The depth is capped and a deeper page is refused with 400.
   - The filtered total is exact, from each lane's filtered count, and is no longer withheld for a capped lane.
   - `filterInbox` remains only as the test oracle.
   - Where T1 shows it helps, the lane's summary and page are folded into one statement (a `MATERIALIZED` CTE feeding a summary row and the page rows), so each lane table is scanned once.
   - Depends on T3.
5. **T5: weekly arrivals from `openSql`.** `decidedWeekly` stops reading the whole board at 1,000 rows for waiting arrivals (`approvalDecisions.ts:678`, `:730-734`) and reads each lane's `openSql` arrivals since the window start. Depends on T2.

Already filed, so not repeated here: #5874 (the one-item read and assignment checks by lane and id; under T2 that is `openSql` plus `AND id = ?`), #5875 (page-scoped assignment state and workload in SQL) and #5877 (parallel lane reads with bounded concurrency).
