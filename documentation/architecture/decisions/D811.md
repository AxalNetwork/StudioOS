## D811 — Signed Axal VC Mail link, consented audiences and atomic feedback

Issue #2257, part of D809. Stacked on D810 PR #2273 (migration 515,
newsletter consent/suppression stores and signed preferences tokens). D812's
programme store is already on main.

Mail authenticates independently of sessions and admin roles with a shared
Worker secret, `MAIL_LINK_SECRET`, set by the owner in both Workers. Nothing is
exposed until it is set: every route answers 404 first. HMAC-SHA256 signs the
method, exact path **including query**, Unix-second timestamp and hex SHA256 of
the UTF-8 body, separated by newlines. The timestamp has a five-minute window in
either direction. KV nonces expire in ten minutes; an atomic D1 unique claim
closes the race that KV's eventually consistent get/put alone cannot close.
Replay stores fail closed. The router mounts before browser CORS/session middleware and bypasses unrelated role-schema bootstrap,
with its own fail-closed 120/minute/IP rate bucket and a 256 KiB body bound.

Newsletter topics, members by role and Partner Letter use confirmed D810
subscribers with explicit consent and an enabled topic. Partner Letter also
checks current investor/LP role. Registration alone does not consent to event
marketing: event guests need the confirmed events topic. Suppressions, pending
subscriptions, disabled topics, inactive accounts and stale account-email links
are excluded both in counts and pages. Recipient pages contain at most 500 rows,
with an audience-bound subscriber-ID keyset cursor. Merge fields are recorded
member name and profile organization, or null. D810 signs preferences and
one-click topic-unsubscribe URLs. No address is stored in read or feedback logs.

Migration 517 is the next free after 516, allocated under #2257's explicit
permission. It adds required `mail_link_reads`, ten-minute nonce claims and
feedback receipts. Receipt IDs digest (type, normalized email, message ID);
missing message ID is an empty value. A batch inserts only unseen receipts,
then changes preferences/suppressions only for that batch's random claim marker.
Receipts, topic opt-outs, unsubscribe-all, legacy insights mirror, suppression
and address-free `service:axal-mail` activity rows commit together. Duplicate
reports cannot undo a later resubscription; within one batch the first tuple
wins even if later duplicates disagree about the audience. Validation precedes any batch write;
one failure rolls everything back. Up to 500 events require only eight statements, including programme opt-outs and their testing audit.

### Owner decision: independent programme consent

The owner chose **A** on 2026-10-20: picked testers need only their recorded
programme consent, never a separate newsletter opt-in. `testers:<programme uid>`
uses D812 applications and excludes unpicked, unconsented, withdrawn, inactive,
programme-opted-out and suppressed people. Newsletter unsubscribe-all also stops
programme delivery. Count and page predicates match, with 500-row application-ID
keyset pages. Closed programmes remain sendable for the final thank-you.

Migration 517 adds `mail_enabled` and `mail_token_version` to applications.
Opt-out preserves the consent history. Public programme links reuse D810's token
format and cryptographic helpers, with a separate HMAC domain bound to the
programme and current account email. A newsletter token cannot authorize a
programme and a former-address/programme link stops working. The signed bearer
is the only authority; cookies and browser roles grant nothing. The existing
D810 lightweight HTML confirmation/form pattern handles browser links; JSON
reads/writes serve API callers and RFC 8058 POSTs work without sign-in or CSRF.
Public links have their own fail-closed 30/minute/IP bucket; token-authorized
POST/PUT unsubscribe writes bypass IP limits to survive mailbox bursts and KV
outages. Audience counts use four grouped queries, read audits use one bulk
insert, and event receipt claims have an index. Public links use no-store and
no-referrer headers, and bypass unrelated role-schema bootstrap.

A programme opt-out leaves other programmes and newsletters unchanged. Turning
it back on requires a still-picked application with recorded consent, records
the current D812 consent wording/version and advances the token version. The
mutation and both `testing_events` and `activity_logs` audits are one batch;
unchanged writes record no fictitious change. The actor is the signed-link
holder, never falsely attributed to the member. Concurrent revocation,
eligibility and account-email changes are checked inside the write; stale
requests cannot refresh retired credentials. Mail-reported opt-outs share the
same scope and idempotency guarantees.

### Verification

Real signed Hono requests against canonical baseline tables plus migrations 515
and 517 test signature binding, replay including concurrent KV lag, unset-secret
404s, rate limiting, live suppression-aware counts, consent/role/event gates,
500-row cursor paging, working D810 URLs, topic/all opt-outs, idempotency across
resubscription and concurrent feedback, 500-event batches, rollback, privacy,
unreadable stores body bounds, independent programme consent and signed public preference links. New assertions are mutation-checked with the
restored scenarios run before and after each mutation. Full drift/build results
are recorded in the PR.

The focused integration suite has 28 passing scenarios, including mailbox
bursts/KV outages, a 1,100-event catalogue with bounded queries, and an indexed
receipt lookup. Twelve additional assertion controls fail as expected and
pass when restored. All 98 earlier controlled
mutations were caught, with restored scenarios passing before and after each
mutation; the event guest identity regression also fails against the earlier
query and passes after the registration-account join. Root build exits 0. The
PR records the final full drift exit code.
