## D5828 part 4 — Typeform: a bounded deletion-reconcile trigger over the existing binding gate (#5828)

- **Status:** built 2026-11-25 by S07, part of #5828 (track #5825, program #5823). Fixtures only: no live Typeform request, credential, flag, schedule or deployment. Parts 1 to 3 are `D5828.md`, `D5828-p2.md` and `D5828-p3.md`, which this file does not edit. Where they disagree, this file is later.
- **Scope:** S1's 2026-11-25 note. Part 2 left the provider-deletion reconciliation run (`reconcileTypeformDeletions`) with no trigger. This part adds the trigger and bounds each run. It schedules nothing, and it enables neither the provider nor the flag.
- **Code:** `services/typeform/importer.ts` (`reconcileTypeformDeletions` and `typeformFormStatus`), `routes/typeform.ts` (one handler), `frontend/src/lib/api/typeform.js` (`typeformApi.reconcile`, for #5830's caller).
- **Migration:** `202611252324_5828_typeform_reconcile_cursor.sql`. It adds one nullable column, `typeform_form_syncs.reconcile_after_id`.

### The trigger

`POST /api/typeform/sync/reconcile` takes `{ project }`. It answers `{ ok, project_id, outcome, result, status }` with `Cache-Control: no-store`. The answer has the same shape as `POST /api/typeform/sync`, but `result` is the run's `ReconcileResult`:

- `outcome`;
- `lookups`, `checked`, `missing_once`, `provider_deleted` and `reappeared`.

`outcome` is one of:

- `ok`: the pass reached the end of the held ids;
- `partly`: the run's bound was reached, so call again to continue the pass;
- `busy`;
- a stored failure state;
- one of the importer's admission outcomes.

A run that happened answers 200 whatever its outcome.

**Gate: unchanged and not widened.** The handler uses part 2's `syncOwner`, then the same `binding_lost` check and `followTypeformBinding` that `POST /sync` uses. The refusals are the same, in the same order:

- 503 `typeform_unavailable` until `TYPEFORM_APP_APPROVED=1`;
- 401 when not signed in;
- 403 `support_session_refused`;
- 400 `project_required`;
- 404 `project_not_found`;
- 403 `forbidden`;
- 403 `read_only`;
- 409 `not_connected`;
- 409 `company_not_enabled`;
- 409 `not_bound`;
- 403 `not_your_binding`;
- 409 `binding_lost`.

Only the member whose own connection holds the venture's binding may start a run. A teammate who can write the venture is refused. No HQ, admin or service path is added, and no refusal sends a request to Typeform. `TYPEFORM_REFUSALS` gains no code.

**Activity log.** When a run concludes at least one deletion, it writes `typeform_provider_deletions_reconciled` with the provider key only. The entry carries no response id.

### Bounded and resumable

Before this part, one call read at most the *first* 1,000 held ids in row order, in up to 40 lookups. On a longer history the later ids were never checked. From this part:

- One run makes at most `SYNC_LIMITS.reconcileLookupsPerRun` (8) lookups of `reconcileBatch` (25) ids, so it checks at most 200 ids and sends 8 Typeform requests. `ImportDeps.limits` can lower both bounds for fixtures but never raise them.
- The ids are taken in local row order after `typeform_form_syncs.reconcile_after_id`. After each lookup's writes have resolved, the cursor moves to that lookup's last row id. It moves only while the run holds the sync row's lease, the same lease the import uses, so an import and a reconcile never run at once.
- A run that reaches the end clears the cursor and sets `last_reconciled_at`, and the next run starts a new pass. Over one pass, every held active id is asked about exactly once.
- A run that fails mid-pass keeps the cursor where the last whole lookup put it, so the retry asks only what that run did not conclude. As in part 1, a failed or malformed lookup concludes nothing. 429 stores `retry_after`, and the next run waits for it.
- Withdrawn and provider-deleted rows are not asked about again.

The deletion rule is part 1's and is unchanged. A response is marked deleted only after two explicit misses at least `RECONCILE_CONFIRM_MS` (one hour) apart. Concluding a deletion removes the response's answers, unlinks their ledger rows and retracts their D5829 evidence in the same batch. A response that comes back is cleared. Absence from an import page still means nothing.

### Status

`typeformFormStatus` adds two fields, and the other fields are unchanged:

- `last_reconciled_at`: when the last whole pass finished, or `null` when none has;
- `reconcile_in_progress`: `true` while a pass is part way through.

### Not done here

- No schedule or background poll; it needs the owner's authorisation.
- No rate limit on the POST routes beyond each run's own bound and the lease.
- No live check against a real account (#5831).
- #5830's screen is not wired to `typeformApi.reconcile`.

### Tests

- `typeform_import_5828.test.ts` adds one test. With a bound of two lookups of two ids, eleven held ids take three runs (`partly`, `partly`, `ok`). The next run continues after the cursor and does not re-ask the first ids. A failure on the second lookup keeps the first lookup's place, and its retry asks only the rest. A finished pass clears the cursor and records the time. A run whose lease is taken over mid-pass does not move the cursor. A second pass asks every held id once and concludes the deletion that has missed twice. A requested bound above `SYNC_LIMITS` is clamped to 25 ids per lookup.
- `typeform_sync_5828.test.ts` adds test 5. It checks every refusal above, the teammate included, each with no Typeform request and no sync row. The owner's run sends one lookup by id on the EU origin, with no `since` or `after`. A first miss deletes nothing, and a second miss within the hour concludes nothing. A second miss an hour on marks the response `provider_deleted`: completed drops from 3 to 2, the activity log has the entry, and a resync does not bring the response back. No token or respondent marker reaches an answer or a log.
