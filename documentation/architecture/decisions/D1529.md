## D1529 — The agent engine's goals, tasks and dependencies (E1 of #3742)

- **Status:** built by the S12 session for slot S02 (#3845, 2026-11-01). It is behind `AGENT_ENGINE` (`"off"` in both `wrangler.toml` blocks) and `TEAM_AGENTS_ENABLED`. Not deployed.
- **Builds on:**
  - D1496 (`team_agents`, the rule books, and the read and manage gates, now in `services/agents/teams.ts`);
  - D1137 (moving a project in and out of a company);
  - the lifecycle stages (`routes/progress.ts`);
  - `roadmap_okrs` (migration 001).
- **Migration:** 727 (`727_scope_goals_and_tasks.sql`, reserved for this task). It is additive. It has `ALTER`s, so it is applied through the ledger runner, as 493 and 712 are.
- **Owner answers it rests on (#3742):** Q1 B, Q2 A, Q3 B plus the `agents` AI Gateway, Q4 B, Q5 A, Q6 A. The runtime is built in-house first, with the SDK behind the seam. None of them is exercised yet: E1 stores the work, and nothing here runs a model.

### Why

No store spanned a company and its projects. OKRs are project-only (`roadmap_okrs`). Build plan items link proposals, not people. No task could be given to an agent. E2 (the run), E3 (the budget), E4 (duties and hand-offs) and the canvas's TM6b, TM6c and TM10–TM11 all need one place where a goal, its tasks, who does each and what each waits on are written once.

### What was decided

1. **Goals and tasks live on one scope**, with #3727's `scope_kind`, `company_id` and `project_id` and their CHECK.
   - `workflow_tasks` (177) and `project_rituals` (250) are untouched, and nothing is migrated into the new tables.
2. **A project goal may roll up** to a goal of the company the project is in (`parent_goal_id`). A project in no company, a goal of another company, and a project goal as parent are each 422 `parent_not_in_company`.
   - The column survives a move out of the company (D1137). The read answers `parent: null` until the project is back in that company, so the roll-up is never a false claim.
   - `okr_id` links one of the project's own OKRs, else 422 `okr_not_in_project`.
   - `stage` is one of the six lifecycle stages, on project goals only (CHECKed).
3. **A task is assigned to exactly one of** a person, an agent or no one. A CHECK keeps exactly the matching id set.
   - **Agent:**
     - it must be live in the task's own scope, else 409 `agent_not_live` (a paused or removed agent, or another scope's, is not this team's);
     - the task's module must be in its effective `works_in`, else 422 `module_not_allowed`;
     - its option, when there is one, must be in `may_propose`, else 422 `option_not_allowed`.
     - Both are checked on the task as it will be, so moving an agent's task to another module is refused too.
   - **Person:** they must pass the scope's read gate, else 422 `assignee_not_member`. Assigning never invites anyone: `invite_person` stays on D1496's floor.
   - **About a project:** a company task may name one of its own projects (`context_project_id`, CHECKed to company tasks), else 422 `project_not_in_company`.
4. **Ready is derived, never stored:** an open task whose every dependency is done. A stored flag would go stale the moment a dependency moved.
5. **Dependencies:**
   - They stay within one scope (422 `cross_scope`; an unknown uid reads the same).
   - They never loop: a depth-first walk from each new dependency looks for the task. A direct cycle, a three-hop cycle and a task on itself are each 422 `dependency_cycle`.
   - The walk is bounded at 200 tasks. A larger graph is refused (422 `too_many_dependencies`) rather than half-checked, and a `PUT` takes at most 50.
   - `PUT` replaces the list.
6. **Cost** is per task, from E3's `agent_task_runs.usage_log_id`, and per goal it is the sum of its tasks' costs.
   - Until E3 nothing records a task's run, so every cost is `{ available: false }`, and a goal's is too. A read that throws answers the same.
   - An unknown is never summed as 0 (`sumCosts`).
   - `taskCosts(env, ids, read)` is the seam E3 fills.
7. **Gates** are D1496's, called and not rewritten. Reading is read; writing is manage. A person assignee who cannot manage may change `status` and `blocked_reason` and nothing else (403 `not_manager`). When #3697 part 2 adds the company branch for projects under a company to `isProjectManager`, it reaches these routes unchanged.
8. **The flag.** Every route answers 404 `agent_engine_off` unless `AGENT_ENGINE` is set and not `"off"` and `TEAM_AGENTS_ENABLED` is `"true"`. A missing `AGENT_ENGINE` counts as off. The check is in each handler, not a `*` middleware: the router is mounted before `team_agents.ts`, so a middleware would answer for team agents' paths too.
9. **`ai_rail_proposals` gains `task_id` and `run_key`**, with a partial UNIQUE index on `run_key`, for E2's idempotent runs. E1 writes neither.
10. **Every task change is in `scope_task_events`:** created, assigned, status, updated (the field names only) and deps_set. No text is copied there.

### Routes

The routes are in `routes/agent_engine.ts`, mounted at `/api/teams`; the table is in `ROUTE_MAP.md` under "Agent engine E1". The client is `frontend/src/lib/api/agentEngine.js` (`agentEngineApi`), with one line in `api.js`'s block (D527):

- `goals`, `createGoal`, `updateGoal`;
- `tasks` (`{ goal, assignee, status, module }`), `createTask`, `updateTask`;
- `setTaskDeps`.

A person is `{ uid, name }` and an agent `{ uid, role_key, first_name, last_name }`; no email and no numeric user id appear in any answer.

### Not decided here

- Running a task (E2), its budget and `agent_task_runs` (E3), duties and hand-offs (E4), and the boards (E8).
- Which tasks a `plan`, `build_plan_item`, `lifecycle_check` or `one_next_thing` source creates. The source kinds are stored, but nothing creates them yet.
