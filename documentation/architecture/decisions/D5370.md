## D5370 — Platform health detects meeting-bot start failures and stored branch health; `not_detected` says only what is true (#5370)

- **Status:** built (this PR).
- **Builds on:** D4854 (detected incidents), D4857 (a failed check is not a missing report), D4858/D4859 (bounded readers with `reads` meta), D5153 (startup facts on `meeting_bots`), D452 (stored branch health), D110 (no fan-out in the summary).
- **Why:** #4854 named six signals and built four. `NOT_DETECTED` still said the meeting bot "is not deployed yet (D886)". That has been false since #3588 deployed the bot hosts, and a production session failed with `runtime_unavailable` on 2026-11-09. Failed starts did not lower Platform health.

### Meeting bot

`services/meetingBotHealth.ts` reads the newest runs created in the last seven days, newest first. It keeps the first `BOT_START_READ` (10) that reached a start outcome. It reads codes, stages and times only, from columns D5153 already writes. It adds no store.

| Outcome | When |
|---|---|
| `check_failed` | `status = failed` and a startup code from D5153's closed list. |
| `unreported` | `status = failed`, `failure_code` is `runtime_unavailable` or `heartbeat_timeout`, no code, and no runtime callback. |
| `started` | Any other run that got past `queued`, including a failure after the runtime reported. That is a provider-side failure: the start itself worked. |
| none | `queued`, or `stopped` before the command was accepted. |

Each kind has its own incident key, so a failed check and a missing report never merge (D4857):

- **`meeting_bot:start_failed`**: **medium** when the latest start failed. **High** when `BOT_START_FAILURE_STREAK` (3) failed in a row, or when the code is a readiness-preflight code (`runtime_no_answer`, `runtime_process_exited`, `runtime_health_failed`).
- **`meeting_bot:unreported`**: medium, and high at the same streak.

Both kinds count toward one streak, and the newest run's kind names the incident. A start that works clears both. Each incident links to HQ › Platform › Meeting bots and to `PLATFORM_OBSERVABILITY.md` §7.5.

**There is no separate preflight store.** D5153's readiness preflight is the host's `/healthz` wait inside each start. Its result is the run's code, so a failed preflight is read from the run.

**Staged diagnostics are not read.** A diagnostic is a check the owner starts, kept per run in R2 under a random id with no index. Finding the latest one would mean listing every diagnostic. It stays in `not_detected` with that reason. Its Not recorded stages already show on Meeting bots.

**Missing data and "not applicable".** These answer `available: false`, which is **unknown** and never healthy:

- no `meeting_bots` table;
- no D5153 columns (before migration `202611090953`);
- a reader that throws or times out.

`MEETING_BOT` off and a branch (the bot runs on HQ only) answer `applies: false`. That is **not detected**, with its own reason. It is not unknown, because there is nothing to judge.

### Branch health: the stored result, not the fan-out

Deployments stores each branch's last answer on `licence_deployments` (`last_health_at`, `last_health_ok`, D452) whenever it fans out. The summary reads only those columns, for branches in a live state (`worker_live`, `hostname_active`, `linked`). It never asks a branch (D110). A test proxies the fan-out binding and checks it is never touched.

- **`branch:<code>`, medium:** the last stored check answered and said not ok.
- **`branch:<code>`, low:** no stored check in `BRANCH_CHECK_STALE_HOURS` (24), or never. Deployments stores only an answer, so a branch that is down looks the same as one nobody checked. A low note does not lower the state, because otherwise the state would drop every day nobody opened Deployments. Opening Deployments refreshes it.

An unreadable registry is unknown. On a branch, branch health is not detected.

### Not detected, and the stale sentence

`not_detected` is now computed from what this read found:

- the fixed diagnostics entry;
- the meeting bot, only when it does not apply here;
- branch health, only when it does not apply here.

The "not deployed yet" sentence is gone from `platformHealth.ts` and from the runbook. CLAUDE.md's file-map line for `meeting-bot/` and `meeting-bot/README.md` said "not deployed yet" too. #3588 records the hosts as deployed (Meeting bot deploy run 40668914717) with `MEETING_BOT=canary`, so both now say that. The live Meet and Zoom check stays open on #3588.
