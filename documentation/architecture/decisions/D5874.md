## D5874 — Approvals: one item read, and assignment targets checked, by lane and id (#5874)

- **Status:** built. Package 4 of 8 of the Admin Approvals audit tracker #4716, first half (4/8 (a)).
- **Builds on:** D130 (the lanes' literal queries), D470 (assignment), D1040 (HQ's inbox), D1132 (the one-item read).
- **Migration:** none.

### What was wrong

`inboxItem` (the read behind `GET /api/admin/approvals/items/:lane/:id`) read the lane with
`approvalBoard(env, INBOX_LANE_CAP)` and looked for the item in those rows. The cap is 1,000 and
the rows come oldest first, so an open item at position 1,001 or later answered `null`. The page
then said "This item is not waiting any more" about an item that was waiting.

Assignment had the same flaw. `assignReviewers` checked each target against a board read to
`boardLimit`, which was 1,000 on HQ and 100 on a branch board. An item past either cap was
refused as `not_on_board`. A lane whose read failed was refused the same way, because a failed
lane is missing from the board rather than thrown.

### What changed

**One row, by lane and id, from the lane's own query.** `itemSqlOf(src)` in `approvalSources.ts`
builds the one-row read from the lane's existing `rowsSql`:

```
SELECT * FROM (<rowsSql without its trailing LIMIT ?>) WHERE id = ? LIMIT 1
```

The columns, joins and waiting condition therefore come from the board's query by construction.
The alternative was 30 hand-written queries, one per lane, each a second definition of "waiting"
that could drift from the board's. Every lane's `rowsSql` ends ` LIMIT ?`; one that does not is
refused with an error, never sent with a stray placeholder. The id is bound. The only text in the
query is the lane's own literal, so `check-sql-prepare` has nothing new to record. HQ's lanes
(`hqApprovalSources.ts`) are `ApprovalSource`s, so they get the same read and need no change of
their own.

SQLite flattens the subquery and pushes `id = ?` into it. On the full schema, 28 of the 30 lanes
plan as a primary-key `SEARCH`. The two compound lanes, KYB (a union of two business sources) and
tickets, still use the key inside their branches.

`approvalItem(env, src, id)` maps the row exactly as the board does (`itemOf`, now shared). It
answers `null` for a row that is not waiting and **throws** when the read fails, so a caller can
tell the two apart.

**The routes.**

- `inboxItem` uses `approvalItem`:
  - an item that is not waiting is still a 404 `item_not_waiting`;
  - a failed read is still a 503 `lane_unreadable`.
- `assignReviewers` reads each target the same way, among the caller's own sources, and drops
  `boardLimit`:
  - a lane the caller does not see, or a row that is not waiting, is a 400 `not_on_board`, as
    before;
  - a lane whose read fails is now a 503 `lane_unreadable` that names the lane, rather than
    "not on the board";
  - nothing is written unless every target is waiting.
- `POST /api/admin/approvals/assignments` and the branch board's
  `POST /api/branch/approvals/assignments` both stop passing a board limit.

**Visibility is unchanged.** Lane visibility is still decided before any read: `readHistoryQuery`
for the item read, and `isVisibleLane` in `assignFromBody` for assignment. So a plain admin, or a
branch, naming an HQ lane is refused as before (404 `item_not_found`, 400 `bad_item`), and the
service refuses a lane outside the sources it is given.

### Not in this change

The 5,000-row assignment-state read (`READ_CAP`) and reviewer workload counts are the 4/8 (b)
task. The inbox list itself still reads each lane to 1,000 rows and counts past that, as D1040
set out.

### Tests

`cloudflare-worker/test/approval_item_reads_5874.test.ts` uses 1,005 open job postings in one lane
on the full schema. It covers:

- every lane's one-row read prepares, and keeps the lane's query whole;
- items 1,001 and 1,005 are read and assigned;
- an item no longer waiting is not found and is not assigned (all or nothing);
- a dropped table is unreadable on both routes;
- an HQ lane is refused to a plain admin and to the branch sources;
- the branch board assigns item 150.

Mutation-checked: restoring the capped board read on either path, collapsing unreadable into not
found or not on the board, ignoring the caller's sources, and dropping the `LIMIT ?` guard each fail
a test.

### 4/8 (b): assignment state scoped to the page, workload counted in SQL (#5875)

**What was wrong.** `readAssignmentState` read the whole `approval_assignments` table, to
`READ_CAP = 5000` rows. When the table reached that cap, every row on every page lost its assignee
and every workload tile was withheld. Rows are never deleted when an item is decided, so the table
only grows. `hqInbox` then derived `assigned_to_me` and `per_admin` by filtering the board's rows in
memory against that map.

**What changed** (`services/approvalAssignments.ts`):

- **The items a read concerns are passed as one JSON parameter.** Each item is a `[lane, id, past]`
  entry, unpacked with `json_each`. Any number of items is a single bound value, and D1 allows at
  most 100 bound values per statement. The text of the statement never grows. The join uses the
  table's `UNIQUE (lane, item_id)` key, so the cost of a read follows the number of items asked
  about, not the size of the table.
- **`readAssignmentState(env, items)` takes the items it reads.** `READ_CAP` and its
  "larger than this read" answer are gone.
  - `hqInbox` with no assigned filter reads the assignees of the page's rows only.
  - With an assigned filter (`me`, `none`, `any`, or an id), it reads the assignees of the rows the
    board read, because the filter needs them. This is still scoped to those items.
  - `inboxItem` reads its one item.
  - The branch board reads the rows it shows.
- **`readWorkload(env, items)` counts held items per reviewer in SQL.** The query is a
  `GROUP BY assignee_user_id` over the waiting items the board read, and it also returns how many of
  those are past the SLA. The tiles come from it:
  - `assigned_to_me` and `per_admin`;
  - `unassigned`, which is items read minus items held;
  - `overdue_unassigned`, which is items past the SLA minus held items past the SLA.

  A row left by an item since decided is not workload: only the waiting items passed in are
  counted, as before.
- **A failed count is not zero.** When the aggregate fails:
  - those four tiles answer `null`;
  - `tiles.reason` is `WORKLOAD_UNREADABLE`;
  - the rows still show their assignees, because the page read is a separate read;
  - `over_72h`, which does not need the record, is still shown.
- **A real read failure is unchanged.** These still answer `ASSIGNMENTS_UNREADABLE`, with
  `assignments.available: false`:
  - a missing table;
  - a failed assignee read for the page or the item.

  The rows then carry no `assignee` field, which means not read, never nobody. An assigned filter
  on an unreadable record is still refused with `assigned_unreadable`.

The response fields are unchanged:

- `items[].assignee`;
- `tiles.{assigned_to_me, per_admin, unassigned, overdue_unassigned, at_least, reason}`;
- `assignments`;
- `reviewers` and `reviewers_reason`.

`frontend/src/pages/admin/approvals/inboxModel.js` needs no edit.

**Tests.** `cloudflare-worker/test/approval_assignment_scope_5875.test.ts` builds a full-schema
fixture with 30 open postings and 5,206 assignment rows; 5,200 of them belong to decided postings.
It covers:

- the assignees on pages 1 and 2;
- exact SQL workload tiles that ignore the stale rows;
- assigned filters;
- a failed aggregate, which gives null tiles with their reason while the rows keep their
  assignees;
- a failed page read and a dropped table, which give `ASSIGNMENTS_UNREADABLE` and refuse
  `assigned_unreadable`;
- the service reading only the keys it is given.

Mutation check: 10 mutations, 9 caught, 1 equivalent. The equivalent one drops the
`assignee_user_id > 0` guard; the write path never stores a non-positive id, and the column is
`NOT NULL`.
