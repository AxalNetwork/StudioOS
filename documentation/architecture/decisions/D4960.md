## D4960 — HQ and support read a company; its seats write it (#4960)

#4960 (slot S11, taken at the owner's request, P0). D4360 drew the read-only frame for an admin or HQ viewer with no seat, but only in the page: hiding **Company settings** was not an authorization boundary. The settings URLs stayed routable and the Worker's write gate (`canEdit`) passed any platform admin.

### The rule, in one place (`cloudflare-worker/src/services/companyAccess.ts`)

`companyWriteDenial(env, company, user, support)` decides every company settings write:

1. **A support session writes nothing** (`support_session_refused`, reason `support_session`). It acts as the member it impersonates; the platform's rule everywhere else (Mercury, Carta, Linear, PostHog, fund admin) is that support reads. This **reverses** what `company_logo_4201.test.ts` documented ("support sessions included" in the edit rule). It was a decision to make once, and the issue asked for the consistent answer; the test now pins the refusal.
2. **A platform admin writes only through a seat they hold in the company** (an Owner, Admin or Founder seat, or primary admin). With none, `company_read_only`, reason `hq_access`. An admin who legitimately holds a qualifying seat keeps member behaviour.
3. **Anyone else needs a qualifying seat**; a plain member or an outsider gets the route's own `not_an_editor` answer, unchanged.

`canEdit` is kept for what an HQ admin may READ (a company's economics, the team's salaries, the invitation list). It no longer decides a write.

### Where it applies

`company.ts` (General PATCH, logo POST/DELETE, member role and removal, invitations create/resend/cancel, the team record's people, coverage and plan), `company_legal.ts` (legal record, tax id, officers, locations, slug) and `company_documents.ts` (uploads). Legal's and Documents' `can_edit` / `can_upload` now follow the same rule, so the page cannot offer what the server will refuse. `POST /company/:uid/leave` is the member's own act and is unchanged.

### The capability the page reads

`GET /company/:uid` (and every response that returns the company detail) carries

```json
{ "viewer": { "member": false, "can_edit": false, "read_only": true, "read_only_reason": "hq_access" } }
```

with `read_only_reason` one of `hq_access`, `support_session`, `not_an_editor`, or null. `member` is a seat, not "admin or member" (`viewer_is_member` keeps its old meaning). The General form draws from `viewer.can_edit` and says the reason; it no longer reads the role cached in localStorage. A read with no `viewer` (an older Worker) falls back to the seat rule with no admin pass.

### Completed follow-up

D5366 applies this same company-seat boundary to existing company-project mutations and the company-scope agent-team gate. It deliberately leaves project-scope authority to #5329.
