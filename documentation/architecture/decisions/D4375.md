### 1. The route

`POST /api/admin/deck-images/:uid/takedown` takes `{ reason }`.

**Who.** `requireHqAdmin`: an HQ admin or Super Admin, never on a branch deployment. Anyone else is 403, and no session is 401.

**The reason.** It is required: 10 to 1,000 characters, trimmed. The founder reads it.

**In order:**
1. **Mark the row once.** `taken_down_at`, `taken_down_by` and `taken_down_reason` are set while `taken_down_at` is null. A second takedown is 409 `already_taken_down`, so the first one stands. An unknown uid is 404.
2. **Delete the R2 object.** A delete that fails is reported as `r2_deleted: false`. The bytes still never serve, because the file route reads the mark before R2.
3. **Tell the venture's founders** in their inbox, with the reason. The notification type is `deck_image_taken_down`.
4. **Write the admin audit row** `deck_image_taken_down` with the image, the venture, the reason, `r2_deleted` and the admin's uid and name. It never carries an email.

### 2. One placeholder, drawn everywhere the image is

A slide names an image by its file URL (`/api/decks/images/<uid>/file`) or its `image_id`. That holds in saved versions, card drafts, proposed decks, derivatives and brand kits (migration 722's `deck_images_named`). Every renderer draws the image from that URL:
- the editor and Present, as an `<img>` in `BlockGrid`;
- the PDF, through the print page's same `<img>`;
- the PowerPoint, .odp and HTML files, where `fetchImages` reads the URL and embeds what it gets.

So the takedown changes **what the URL answers**, not the decks. For a taken-down image, `GET /api/decks/images/:uid/file` answers a neutral PNG with `no-store` and `x-axal-image-state: taken-down`, and never the removed bytes.
- **The PNG** is 1600 × 900, "Image removed by Axal HQ" in Inter Medium, zinc-600 on zinc-200, about 5.7 KB (`takedownPlaceholder.ts`).
- **No version, draft or proposal is rewritten.** The decks keep their history, and a version's content hash still matches what it was.

**What it cannot reach:**
- **Cached copies.** A kept image was served `public, max-age=31536000, immutable`. An edge copy cached before the takedown is purged by hand (`DECK_GRID.md` §4, step 3), and a browser's own copy lasts until its cache clears.
- **Earlier exports.** Files a founder downloaded before the takedown are theirs.
- **Alt text.** A PowerPoint exported later carries the placeholder picture with the block's own alt text.

### 3. What changes for the founder

- **Founder routes refuse the image.** Keep, discard, edit, cut out or upscale (`imageOf` in both image route files) answer 410 `image_taken_down`, in the sentence `TAKEN_DOWN_SENTENCE`.
- **The art direction drops it.** It is no longer read as the reference image.
- **It leaves the library.** The image library (`GET /api/decks/:id/images`) no longer lists it.
- **The same bytes can't come back.** Uploading them again is 409 `image_taken_down`, never "already uploaded".
- **The record stays.** The daily sweep never removes a taken-down row: the row is the record, and the placeholder is served from it.

Images derived from a taken-down image, such as an edit or a cutout made earlier, are separate images. HQ takes each one down on its own.

### 4. The reports queue links to it

`GET /api/admin/deck-reports` gives each report `images: [{ uid, url, taken_down }]`, at most `REPORT_IMAGES_MAX` (6).
- **What it lists:** the deck images the result's payload names, then those on its card in the version.
- **Unreadable state:** `taken_down` is null when it cannot be read.

HQ › Decks › Reports shows those images on the report's sheet, each with Take down image. The button arms only on a reason of 10 to 1,000 characters, and the reason is sent trimmed. An image already taken down says so and offers nothing more.
