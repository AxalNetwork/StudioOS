## D6685 — The server says whether a company is incorporated (#6685)

Issue #6685, plan key E5, phase 1. There was no incorporated flag: a company with only a name read `Active`, and the three Incorporate doors could not tell an incorporated company from one that never filed. `cloudflare-worker/src/services/formationState.ts` now decides it once, and three reads carry the answer so no screen works it out. The frontend change is #6688; the case store and `draft_case` (#6703) are out of scope. No migration, no new route, no gate changed.

### The schema it reads

| Fact | Where it lives |
| --- | --- |
| Legal identity | `company_profiles.incorporation_date` (`YYYY-MM-DD`) and `company_profiles.registration_number`, both added by migration 685 |
| Formation order | `incorporations`, one row per order, keyed by `project_id`; `company_id` (685) is set when a filed order links or creates a company |
| Order status | `pending_payment` → `paid` → `packet_processing` → `packet_ready` → `filed` (411); `failed` appears in 086's comment and is never written today |

The issue's names match the schema. An order belongs to a company the way `account_companies.ts`'s `formation` block already attributes it: `COALESCE(incorporations.company_id, projects.company_id)`.

### The rule

| `formation_state` | When |
| --- | --- |
| `incorporated` | The legal record holds a non-blank `incorporation_date` or `registration_number`, or a bearing order is `filed` |
| `in_formation` | Otherwise, a bearing order is `paid`, `packet_processing` or `packet_ready` |
| `not_incorporated` | Otherwise, with both reads answered |
| `unreadable` | Otherwise: a read failed |

Precedence: incorporated beats in formation. A filed order with a newer paid order (a second order) reads `incorporated`. Positive evidence wins on its own: a recorded identity is `incorporated` even when the orders read failed, and a filed order is `incorporated` even when the legal read failed. Anything weaker needs both reads, so a failed read never becomes `not_incorporated` and a paid order with a failed legal read is `unreadable`, not `in_formation`. `pending_payment` and `failed` orders count for nothing.

Several orders: they are read latest first by `COALESCE(paid_at, created_at) DESC, id DESC`, the order the `formation` block uses. `formation_order_id` names the first in-flight order in that order, which is the latest.

Which orders bear on a row:

- **A company**: every order attributed to it.
- **A venture**: its own orders at any counted status, plus any `filed` order attributed to its company, and its company's legal identity. Another venture's in-flight order does not make this venture `in_formation`. A venture with no company has no legal record, so that read cannot make it `unreadable`.

### The shape

Each row gains two flat fields; nothing else changes.

```
formation_state:    'incorporated' | 'in_formation' | 'not_incorporated' | 'unreadable'
formation_order_id: number | null   // the order id when in_formation, else null
```

| Read | Rows that gain the fields |
| --- | --- |
| `GET /api/account/companies` | each company |
| `GET /api/account/projects` | each venture |
| `GET /api/account/switcher` | each company (its nested, standalone and elsewhere projects do not) |

The existing `status` block (D1412) stays as it was, including `in_formation` for a company that has a filed order and a newer paid one; `formation_state` is the field that answers "incorporated".

### Reads

Batched: at most one legal-identity statement and one orders statement per request, over every row on the page, never one per row. Each fails alone: a failed read sets the rows it touches to `unreadable` and the endpoint still answers 200. The registration number is only tested for presence in SQL (`COMPANY_IDENTITY_SQL` returns company ids); its value is never read into the Worker here and never returned.

Tests: `cloudflare-worker/test/formation_state_6685.test.ts` — the rule, each state on each read, the failed reads, the statement counts, and a snapshot of each read's keys.
