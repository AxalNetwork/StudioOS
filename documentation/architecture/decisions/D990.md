## D990 — Partner profiles part 1: the list read, a reference per profile, the derived source, the Draft state and the counts read

- **Status:** filed by S21 as #2801, part 1 of Partner profiles (#2380), from S21's integration in #2742 (D989). Built by S07. Migration 556.
- **Canvas:** `design/incoming/Partner Profiles Page.dc.html`, boards PRF1, PRF2, PRF7 and PRF9.
- **Worker only.** The page (D989) draws these reads. This PR adds no screen.

### 1. The decision

HQ's Partner profiles page reads its own list and counts from a new router, `routes/admin_partner_profiles.ts`, mounted at `/api/admin/partner-profiles`:
- a profile is named by a stable reference, never by its email;
- where it came from is derived from what each writer leaves behind;
- a row with no chat and no answers is a Draft, not waiting.

The rules live in `services/partnerProfiles.ts`. Approvals lane 7 reads the same waiting rule, so the queue and the lane agree.

`/api/profiling/admin/*` is unchanged: the Partners desk and the existing admin pages still read it.

### 2. As built

1. **Migration 556: `partner_profiles.ref`.**
   - The format is `pp_` plus ten random lowercase hex characters, such as `pp_7f3a21c04e`. It is never derived from the email: a hash of an address would let anyone holding a guess confirm it.
   - Every existing row gets its reference in the migration.
   - An `AFTER INSERT` trigger fills it on every insert that names none, so none of the three writers (the onboarding chat, a partner invitation, Eadwyn's partner questions) has to change.
   - A unique index refuses a duplicate. At 40 bits, one is about one in fifty million at ten thousand rows.
2. **The derived source** (`sources`, one or more):
   - **invitation** when `invitation_id` is set.
   - **chat** when `chat_history` holds a transcript.
   - **eadwyn** when one of three columns only Eadwyn's partner questions write is set (`services_offered`, `dealflow_channels`, `conflicts_text`). It also applies on a row with no invitation when one it shares with the invitation form (`organization`, `role_title`, `motivation`) is set. On an invited row the form wrote those, so they say nothing about Eadwyn.
   - "Set" means not null, not blank, and not an empty JSON value (`[]`, `{}`, `null`).
3. **Draft.**
   - A Draft is a pending row with no chat and no answers. "Answers" means every column a partner's words fill (`ANSWER_COLUMNS`). `full_name`, the keys and HQ's own columns do not count.
   - Its `status` reads `draft` while `admin_status` stays `pending`.
   - Eadwyn's name-only row (`ensurePartnerProfile`) is the case it exists for. It has no source by the rule.
   - The queue's waiting sort, the waiting tile and Approvals lane 7's count and rows (`IS_WAITING_SQL`) all leave Drafts out.
4. **`GET /api/admin/partner-profiles`.** `requireAdmin`. It returns:
   - `rows`: the page;
   - `totals` over the filtered set (`total`, `draft`, `pending`, `verified`, `rejected`, `not_recorded`);
   - `page`, `page_size` (default 25, at most 100) and `sort`;
   - `options`: the distinct categories, founder tracks, entity types and agreements, for the filters.

   **Search** (`q`) covers name (the profile's and the account's), email, entity and organization. It is case-blind, and `%` and `_` are literals.

   **Filters:**
   - `status`: `draft`, `pending`, `verified`, `rejected` or `not_recorded`;
   - `source`: `invitation`, `chat`, `eadwyn` or `none`;
   - `category` (the onboarding persona), `founder_track`, `entity_type` and `agreement`, exact match or `not_recorded`;
   - `has_account`: `yes` or `no`;
   - `identity`: `not_started`, `pending`, `approved`, `rejected` or `no_account`;
   - `captured_from` and `captured_to`, inclusive dates.

   **Sorts:** `waiting` (the default: pending first, oldest first), `newest` and `name`.

   **Each row** carries:
   - `ref`, `email`, `created_at`, `user_id`, `invitation_id`, `full_name` and `organization`;
   - the chat's fields;
   - `status` and `sources`;
   - `account`: the profile's `user_id`, else the account holding its email, with its role, `exploring`, and the Exploring review's suggested and assigned role;
   - `identity_check`: `{ state, label }` in KYC & KYB's words (Not started, Pending, Approved, Rejected), or null with no account.

   The tax ID is never on a row.

   **The log:** the read logs the D625 line `partner_profile_list_access` (`count=… total=… page=…`).
5. **`GET /api/admin/partner-profiles/counts`.** `requireAdmin`. Each block has `available` and `reason`:
   - `waiting`: `count`, `over_24h`, `over_72h`, `oldest_at` and the `drafts` it leaves out;
   - `verified_30d`: unavailable until part 2 records review dates;
   - `envelopes_out`: unavailable until part 4;
   - `weekly`: twelve weeks, Monday to Sunday UTC. `captured` counts profiles created that week, Drafts left out. `verified` and `rejected` are null, with `verified_available: false` and its reason.

   One block failing to read costs that block only, and never reads as zero.
6. **`GET /api/admin/partner-profiles/:ref`.** `requireAdmin`. It returns one profile, `ein` masked (D634), with the list's derived fields on `listed`.
   - It logs the D612 line `partner_profile_access` by reference (`ref=pp_… user_id=…`, or `; no user account`).
   - Anything that is not a reference is a 404, an email included.
7. **Refusals:**
   - no session is a 401 and a member is a 403;
   - a bad filter or sort is a 400 (`bad_filter`, `bad_sort`);
   - a D1 error on the list or a profile is a 503 (`partner_profiles_unreadable`), never an empty list.
8. **The client:** `frontend/src/lib/api/partnerProfiles.js` (`partnerProfilesApi.list`, `.counts`, `.get`), re-exported from `api.js`.

### 3. Departures, for review

- **A new router rather than `profiling.ts`.** The issue allows either. The new reads share nothing with the onboarding chat's file, and `/api/profiling/admin/*` keeps its callers.
- **A by-reference read (`GET /:ref`).** The issue's address `/admin/partner-profiles/[ref]` needs a read by reference, and its log line has to name the reference. It mirrors `/profiling/admin/:email` and does nothing more.
- **Ten hex characters, not six.** The issue's `pp_7f3a21` is an example. Six characters (24 bits) give about a 3% chance of a refused insert at a thousand rows.
- **What waits for part 2 is refused, not faked.** The `reviewed_by` filter and the `reviewed` sort answer 400 `not_recorded` with the reason, rather than ignore the filter or sort on another date.
- **Lane 7's rows also leave Drafts out**, not only its count, so the board and its count agree.
- **The weekly `captured` count leaves Drafts out.** A Draft has nothing captured.
- **ROUTE_MAP.md is unchanged.** Main has no Partner profiles row yet. D989 (#2742) adds it with the page.
- **`profiling.ts`'s runtime bootstrap matches migration 556.** `ref` joins `NEW_COLUMNS`, and `ensureProfileTable` writes the same backfill, unique index and trigger. A database built by that bootstrap alone then names its profiles too, and the D191 schema-pair guard stays silent on `partner_profiles` (its column count rises from 24 to 25).
- **Four approval fixtures widened.** `_approval_s16_stores.mjs`, `branch_approvals_s16_d215.test.ts` and `studio_glance_hq_d555.test.ts` now carry the baseline's and migration 275's answer columns, which the Draft rule reads.

- each row's fields;
- every filter;
- the sorts, the pages and the part 2 refusals;

- the counts and their unavailable blocks;
