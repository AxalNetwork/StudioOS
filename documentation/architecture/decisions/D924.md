## D924 — Partner invitation sends keep progress and report their outcome

Issue #2720, part 1 of #2370. Migration 547.

Resending an invitation renews its fourteen-day window without changing its
stored stage. At Agreement out, an authorized resending admin renews only the
invitation recipient's pending signing token, emails the signing link using
the existing agreement sender, and aligns its expiry with the new invitation
window. The admin need not be the original inviter. Expiry renewal is guarded against
terminal invitations, and a concurrent revoke is rechecked before fallback mail. Signing links stay out of
responses and audit metadata. Failed mail restores the prior token and expiry
only while the fresh token still matches; a newer concurrent renewal cannot be
undone. With no pending partner signature, resend uses the onboarding email
instead. Renewal's audit actions are separate from Remind's throttle. Finalize's repeat-call path is unchanged.

Create and resend record last_sent_at, send_count, last_send_ok and
last_send_reason. Gmail accepting a send means **Sent**, never Delivered.
Failure reasons are suppressed, not_configured, refused and failed. Existing
boolean email callers retain their contract; detailed result functions serve
the invitation routes. Migration 547 backfills recorded boolean outcomes from
audit rows, deduplicating the two audit stores, and leaves unknown historical
results and causes null. Every invitation counts its initial attempt, plus all
audited resends even when their outcome was not recorded. Renewal audit metadata
records success and whether a failed renewal restored the prior link.

Creation deduplicates allowed types before enforcing at most three distinct
valid types. The proposal builder's existing three-type backstop is unchanged.
The email filter binds its pattern and escapes percent, underscore and
backslash with an explicit SQL escape character.

Activation persists invitation_revoked or link_lapsed when it voids a deal;
admin revocation persists admin_revoked. Existing void reasons are retained.
Deal listing returns the reason. The signing completion notice tells the sender
that the agreement was signed but the deal was voided and why, instead of
claiming it was executed with partner benefits.

There is no lapse sweep. Lapsed means expires_at has passed while the
invitation is neither signed nor revoked; its stored stage remains. The stored
expired stage retains its sole meaning: signing after the invitation lapsed,
with the deal voided. No new path writes expired.

No frontend, founder-plan grant policy, server search/paging expansion or
applied migration changes are part of this decision. Tests use real migrated
SQLite and synthetic mail transport; no production content or provider is used.
