### 1. Per prospect

`GET /api/decks/:id/qa?prospect=<raise_prospects.id>` (the existing route in `routes/deck_qa.ts`; no new mount).

- With `prospect`, the objections THAT investor raised rank first, the ones it raised most first; then the venture's other objections in D913's order (most heard first); then the critic's findings, as D1559 orders them. The sort is stable, so each part keeps D1559's order.
- Each objection then carries `heard.from_prospect`: how many of its feedback rows that investor gave (0 for none). `objections.ts`'s `groupObjections`/`readObjections` count it from the `prospect_id` they already read; the order they return is unchanged.
- Without `prospect`, the reply's questions, order and keys are D1559's. No `from_prospect` is written.
- A prospect re-orders; it never re-words or re-keys a question, so a kept answer (D1559 §4) is found under the same key.

The reply adds:
- `prospect`: `{ id, name, firm }` of the one asked for, or null;
- `prospects`: the venture's own prospects for the picker, `{ id, name, firm, objections }`, those with the most feedback rows first, at most 200. Name and firm only, as Capital relationships shows the founder; never an email;
- `reads.prospects`: `ok` or `unreadable`, so a failed read is never "no investors".

### 2. The prospect must be the venture's

- `prospect` must be a positive whole number: otherwise 400 `invalid_prospect`.
- It is read with `WHERE id = ? AND project_id = ?` against the deck's venture. Any other id, another venture's prospect included, answers 404 `prospect_not_found` with the same body, so the read never says whether another venture's prospect exists. This is the scope `deck_investor_links.ts` already uses for a variant's prospect.
- The check runs after D1559's founder gate. An admin, a support session or another member gets 403 `founder_only` whatever the id, so no one else can probe prospect ids.

### 3. The drill: "Practise answers"

`frontend/src/pages/raise/pitch/LikelyQuestions.jsx`, drawn in the Rehearsal report (`RehearsePanel.jsx`) in place of "Likely questions are coming later."

- The block lists the questions with their rank, who raised them ("Raised by <investor>" for the picked prospect, "heard n times from m investors") or the deck check's severity, and a "Practise answers" button on each. A "For" picker reads the order for one investor.
- **One question at a time, never a chat thread.** "Practise answers" opens the drill at that question: "Question k of N", the question, a box for the founder's answer, "Check against the records", "← Previous", "Next question →" and "End practice". There is no message list, no reply and no model.
- "Check against the records" shows what D1559 bound: the answer's own words (or why there is none: not recorded with where to fill it, unchecked, no record), the founder's kept answer and their answer from Capital relationships when D1559 returned them. It then names each figure the founder typed that no binding carries ("Not carried by any record: 40. Say only what a record holds."), read as the Worker reads a figure (`rehearseModel.js` `figuresIn`, the same digits rule as `deckQa.ts`). The drill shows no figure that a binding did not carry.
- **Nothing is persisted.** The typed answers live in the page while the drill runs; nothing is sent. Keeping an answer stays D1559's write (`PUT …/questions/:question/answer`), which this drill does not call (§5).

### 4. Behind the `rehearse` row

The read goes through `through(() => deckQaApi.questions(…), SURFACES.rehearse.issue)`, so a Worker without the route draws "Likely questions are coming later." and nothing else; a refusal (such as `founder_only`) draws its sentence, never "coming later"; an empty list says there are no likely questions yet. No adapter method is added, so `deckV2Adapter.js` and D1511's contracts are unchanged: `rehearse` stays `deckRehearsalsApi.list` with `deckRehearsals.schema.json`. The client is `frontend/src/lib/api/deckQa.js` (`deckQaApi.questions(deckId, { prospect, stage, investorType })`), in the generated API index.

### 5. Later

- Keeping a practised answer from the drill through D1559's write. It needs the founder to pick the bindings, and D1559's write finds the question only in the venture-wide top 20, so a prospect's objection ranked past 20 would answer `question_not_found`; a `prospect` on that write would fix it.
- `qa_voice`: speaking the answer instead of typing it (decision P).
- The rehearsal report's own `questions` key stays null (D1580); the block reads the live questions, not a copy taken when the report was made.
