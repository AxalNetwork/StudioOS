## D1456 — Interview record actions and recorded processing failures

Issue #4014 completes the Worker reads for #3710's D1454 record and D1455
session screens. It changes no layout or permission policy.

### Record read

The first pill names the latest session's recorded channel: In person, Zoom,
Google Meet, Teams, WhatsApp, Telegram or Pasted. A meeting-bot session reads
its latest bot's platform with a bound session id; an absent session or unknown
platform supplies no channel pill. An upload records its capture source but
has no inferred meeting platform. Captured names Eadwyn AI for meeting bots
and an uploaded recording for uploads, without depending on a submitter name.

Only writers receive null-fact actions: Judge fit is a one-select form calling
the existing ICP writer, and Judge need links to the existing interview tools.
Consent has no repair action. Recorded facts retain their value and have no
null-fact action. The record route retains its project ownership check and
the same writer gate as the evidence PATCH: foreign ids return 404 and a
partner's write returns 403. Only strong, partial and none are accepted fits.

Pending placements in the latest session produce Review findings (n), linked
to the record's review anchor and given primary tone. Open recording has the
default tone while this action exists, and regains primary tone otherwise.
Counts do not include accepted/discarded placements or an older session.

### Failed processing step

Migration 760 adds nullable processing_failed_stage, constrained to uploading,
transcribing, summarising or placing. Historical rows remain null. It is an
additive ALTER, applied once by the existing checksum ledger; a second runner
pass skips it. It must apply before the new Worker is deployed.

failProcessing binds the step it read in the same UPDATE that marks failure.
The exception path passes the freshly read persisted step, falling back to
its prior snapshot if that diagnostic read fails. The upload sweeper's
conditional failure UPDATE also records uploading. Neither path infers a step
from the error sentence. A successful recovery claim clears the step atomically
with its other retry state. processingOf carries failed_stage through the
session, process response and active-session read, with null for unrecorded data.

### Bot failure details

The existing creator-only session bot read retains its scoping and supervisor
status read. It adds failure_detail from the selected run's D1 uid and accepts
only the existing BOT_FAILURE_DETAIL code pattern, including for legacy stored
values. An absent or invalid value is null. Meeting links, names and provider
sentences are not added. The existing callback storage filter is unchanged.

### Verification and rollback

Tests exercise real SQLite-backed routes with synthetic data: channel and
capture labels, writer-only null facts and fit writes, pending placement counts
and action tones, failed-step persistence and retry clearing across all reads,
creator-only bot details with malformed-value rejection, and two ledger-backed
migration passes. Behavioral mutation checks remove each boundary and confirm
the tests reject the changed behavior, then restore and rerun the baseline.
The PR records exact test and CI results.

Rollback the Worker change to stop writing or reading these fields. The nullable
column can remain; no destructive migration or historical backfill is needed.
