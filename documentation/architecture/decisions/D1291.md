### 1. Stages

An article's stage is its status, except that `approved` splits in two:

| Stage | Means |
|---|---|
| `submitted`, `in_review`, `changes_requested`, `published`, `rejected` | the status |
| `ready` | approved, with no `publish_at` |
| `scheduled` | approved, with a `publish_at` the per-minute cron publishes at (D484) |

- `stage` takes one stage, or one of three views:
  - `open` (the default): submitted, in review, changes requested, ready and scheduled. These are the same rows the queue always showed;
  - `calendar`: scheduled and published;
  - `all`: every stage, drafts included.
- **`status` keeps its old meaning,** one raw status. Today's page passes it, so it reads exactly what it did. Each row carries its `stage`.

### 2. Search, filters, sort and paging

- **Search (`q`)** matches the title or the author's name. `%` and `_` match themselves, never as wildcards.
- **Filters:**
  - `author` and `reviewer` (user ids);
  - `profile` (the author's role);
  - `sector`;
  - `submitted_from` and `submitted_to` (whole days, both included);
  - `open_comments` (`1`: at least one unresolved review comment; `0`: none).
- **Sort:**
  - `waiting` (the default): oldest submission first;
  - `newest`;
  - `goes_out`: the day it goes out, unscheduled last;
  - `rounds`: most first;
  - `title`: case-insensitive.

  Every sort breaks ties by the wait, then the id.
- **Paging:** `limit` (50, at most 100) and `offset`, with **`total`**, the whole match and not the page. A page past the end still says the total.
- **A bad value is refused by name** (400 with `invalid_stage`, `invalid_sort`, `invalid_status`, `invalid_filter` or `invalid_range`), never ignored or guessed.

### 3. Each row

The old fields stay. Each row adds:

- `stage`, `publish_at`, `published_at`, `sector`, `read_minutes`, `views`, `author_role` and `reviewer_user_id`;
- `open_comments`: unresolved `article_review_comments`;
- `rounds`: one per submission in `article_submission_log`. Every submit and resubmit writes one;
- `goes_out`: `publish_at` while scheduled, `published_at` once published. An article that went out late sits on the day it went out.

### 4. Counts per stage

`counts` is over the whole table, whatever the filters, for each of the seven stages:

- **`count`**: a stage with none is a measured `0`;
- **`oldest_since`** and **`oldest_hours`**: when the longest wait in that stage began. Submitted counts from `submitted_at`, in review from `reviewed_at`, and ready and scheduled from `approved_at`;
- **`oldest_reason`** where there is no age:
  - "Nothing in this stage";
  - "No column records when changes were requested": nothing stamps that moment, so the age is never guessed from `updated_at`, which every author edit moves;
  - "A published / rejected article is not waiting".

A draft is in no stage, so `total` counts the seven.

### 5. The calendar's range

- **`from` and `to`:** whole UTC days, both included, at most 92 days apart. They go together, and either alone is refused.
- **They filter on `goes_out`.** Without a `stage`, the view is `calendar`.
- **`publications`:** with a range, the response adds Publications' chips, each published `admin_publications` row whose `published_at` falls in it. A draft is never a chip.

### 6. Every statement bound, each block alone

- **One literal statement.** Every filter is a `(? IS NULL OR …)` predicate and the sort a bound `CASE` key, so nothing is spliced into the SQL. The old handler built its WHERE by interpolation, so `schema_guards`' skip count falls by one.
- **Each block fails alone.** The rows, the counts and the chips are separate:
  - a failed rows read is 503 `queue_unreadable`;
  - a failed counts or chips read is `{ available: false, reason: 'unreadable' }` beside the rows.

  The log line names no title, name or email.
