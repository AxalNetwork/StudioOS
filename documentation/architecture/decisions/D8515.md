## D8515 — A DocuSign delivery is seen only once its work is durable, and a failure is retried (#8515)

**Status:** decided 2026-11-25 (S09), from the Contracts and eSignature CI audit of 2026-11-25.

**What was wrong.** `webhook()` in `cloudflare-worker/src/integrations/providers/docusign.ts`
wrote its 24-hour replay marker before any work, then caught every reconciliation
error and returned a summary, so the shared receiver logged `ok` and answered 200.
`reconcileEnvelope` also returned `updated: false` when DocuSign's envelope read was
not OK, and when the signed PDF could not be pulled. A delivery that arrived while
DocuSign's API or R2 was briefly unavailable was acknowledged, and its redelivery was
rejected as a replay; the envelope stayed `sent` until the poller happened to visit it.

**Decided.**

1. **The marker follows the work.** Before reconciling, the marker says `pending` for
   60 seconds (KV's minimum TTL). An identical delivery that finds `pending` is told to
   retry: the handler throws `docusign_delivery_in_progress`, and it does not reconcile.
   On success the marker becomes `done` for 24 hours, and a later identical body is a
   replay, answered 200 as before. On failure the marker is deleted. A delivery that
   crashes mid-way blocks its own retry for 60 seconds at most. A marker written before
   this change (`1`) still reads as a replay. When KV cannot be read or written, the
   delivery reconciles anyway, as before (reconciliation is idempotent).
2. **A failure is a failure to the sender.** The handler throws on any reconciliation
   failure. The shared receiver in `routes/integrations.ts` already maps a thrown
   handler to an `error` log row and a 500 with `webhook_failed`, so it is unchanged,
   and so is every other provider's answer. The log keeps only the error class
   (`reconcile failed: docusign_envelope_read_failed`), never DocuSign's error body,
   which can carry recipient details.
3. **"Could not read" is not "nothing to do".** `reconcileEnvelope` throws
   `docusign_envelope_read_failed` on a non-OK envelope read and
   `docusign_pdf_pull_failed` when a completed envelope's signed copy could not be
   pulled and stored (it still records `last_error` on the envelope first). An unknown
   envelope and an unchanged status still return `updated: false`. The poller already
   wrapped each envelope in a `try`, so it now counts these as `errors` in its summary
   instead of as envelopes with no change.
4. **One transition, written once.** Each status write is conditional on the status the
   call read (`WHERE id = ? AND status = ?`). When a delivery and the poller race on one
   envelope, the loser's write changes no row and it returns "no change" before the
   audit event and the completion steps, so both are recorded once. The signed-file
   registry row was already single (`ON CONFLICT … DO NOTHING`, D711) and R2 write-once
   (D6651).

**Verified.** `cloudflare-worker/test/docusign_webhook_retry_8515.test.ts` runs the real
receiver and provider against the full schema, with stubbed `fetch`, KV and R2:
a transient provider failure then the same body (500 and `error`, then reconciled);
an R2 failure after the provider read (same); a signed PDF DocuSign will not return
(same); two identical deliveries at once (one envelope read, one registry row, the
second told to retry, its retry a replay); a delivery racing the poller (one registry
row, one audit event); a true replay after success (rejected, no provider read); and the
poller counting a non-OK read as an error. Mutation check: 9 mutations, 9 caught.

**Not built.** The partner-deal activation and `contract_signed` notification gap
the poller's comment records is unchanged. No migration; no provider call in tests.
