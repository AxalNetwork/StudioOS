## D905 — Pitch deck studio part 11: admins read and leave notes; the roles the studio is not for see a boundary

- **Status:** built by S12 for #2684 (part 11 of #2434), 2026-10-24. The owner moved the task from S06 to S12. Migration 538.
- **Basis:** `origin/main` at `b0422fef39` (D894's studio shell, #2685). Worker paths are relative to `cloudflare-worker/src/`; frontend paths to `frontend/src/`.
- **Owner question 6 (#2434), answered A:**
  - founders write;
  - Admin and Super Admin read and leave notes;
  - investors and partners see a deck only through a link.
- **Beside:** part 1 (#2674, PR #2689) makes the Worker refuse an admin's deck writes. This part adds what an admin may write, a note, and the boundary the other roles read.

### 1. The store: `deck_notes` (migration 538)

- **Columns:** `project_id`, `deck_id` (the version's `pitch_decks` row), `deck_version`, `card_index` (0-based; NULL is the whole deck), `author_user_id`, `author_kind`, `body`, `created_at`.
- **One thread per venture.** A venture has one deck whose saves are new `pitch_decks` rows, so the thread spans every version, and each note keeps the version it was written on ("v4").
- **`author_kind`** (`admin`, `super_admin`, `founder`) records what the author was when they wrote. A later role change does not rewrite the thread. The issue's column list did not name it; the thread's "who" needs it.
- **No `deleted_at`.** Notes are not withdrawn in this part.

### 2. The routes: `routes/deck_notes.ts`

Mounted at `/api/decks`, after `deck_share_actions` and before `decks`. Its paths are two segments, so they never shadow `GET /api/decks/:id`.

| Route | Who | What |
| --- | --- | --- |
| `GET /:id/notes` | an Admin; the Super Admin on HQ; the venture's founders | `{ notes: [{ id, deck_id, deck_version, card_index, body, author: { name, kind }, created_at }], viewer }`, oldest first, at most 500 |
| `POST /:id/notes` | the same | `{ body, card_index? }` → 201 `{ note }` |

**Who:**
- **An Admin** by role, on this deployment. On a branch that is the branch's own studio, because a branch's data is its own deployment (D106).
- **The Super Admin:** `hydrateSuperAdmin`, so on a branch nobody is one.
- **A founder:** the deck's write access (`projectOwned` with `write`), which is the owner or an accepted owner or cofounder member. A non-owner's post records `project_content_write_authorized` first, as every non-owner write does.
- **Everyone else** is `404 deck_not_found`, the same answer as a deck that does not exist: an advisor member (who can read the deck itself), an investor, an Explorer, another venture's founder.

**Checks:**
- **The body:** trimmed, 1 to 2,000 characters (`note_required`, `note_too_long`).
- **The card:** an integer inside that version's slides (`invalid_card`).

**The audit:** one `raise.pitch-deck` activity row per note (D691 decision 12), in the same `DB.batch` as the insert. Its entity is the version's deck row, and it names the card and version ("Note posted on card 2, v1"), never the note's words.

**Never in a share or an export.** Only `routes/deck_notes.ts` reads `deck_notes`: not the deck's own reads, not the share routes, not the exports. The test holds that, file by file.

### 3. The Super Admin's default template by sector and stage

`PUT` and `DELETE /api/decks/admin/recommend-overrides` now need the Super Admin on HQ (`super_admin_required`). The canvas draws the control in the Super Admin's frame only, and the setting applies to every studio. `GET` still answers any admin, so a branch admin reads which template a new deck starts from.

### 4. PD21 in the studio

- **The banner** reads "Read only. Notes are visible to the founder."
- **The Notes tab:** `/raise/pitch/notes` (`PitchNotes.jsx`). It holds:
  - the thread, with the author, date, version and a card pill;
  - the composer, with a card picker. Posting opens a dialog that says what it changes.
  - Who may post is the Worker's `viewer`, never a guess from the role.
- **The Super Admin's card** "Default template by sector and stage" sits beside the thread when `viewer` is `super_admin`. Changing a row opens a dialog. Template names come from `GET /api/decks/methods`, which is unreachable on `main` until part 1 moves it; until then each row names its template by id.
- **The scope badge.** The admin shell already draws the branch's "… · BRANCH" badge and the "HQ" chip (`App.jsx`), so the studio adds none.
- **Not here.** PD21's editor frame has no AI bar, no Share, no Export and no Check run, and the Design and Sources tabs have no editing controls. Those belong to the editor, #2434 part 4. Today's builder at `/raise/pitch/edit` is refused for admins' writes by part 1.

### 5. PD22: the boundary

- **Who:** an Advisor (`advisor`), an Operating Partner (`partner`) or an Explorer (`exploring`) opening `/raise/pitch`. A member of an active Spin-Out Lab cohort uses the studio as a founder does.
- **What it says:** "The Pitch deck studio is for the venture's founders. Ask them to share a link." The Advisor's adds "A shared deck opens in the viewer, with the NDA if they ask for one."
- **How:** `PitchBoundary.jsx`, drawn inside their own shell, as `hqOnly`'s notice is, instead of `RoleGuard`'s bounce. Nothing from a deck is read.
- **What moved with it:** the guard admits the three roles, and `HELP_SURFACES['/raise/pitch']` moves with it. The other studio addresses keep their guard.
- **Investors:** an investor opening `/raise/pitch` is still bounced. PD22's investor frame is an expired share link, which is the share part's (#2681).
