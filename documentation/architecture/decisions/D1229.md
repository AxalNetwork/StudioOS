### 1. The store (migration 614)

The status stays on `users.kyc_status`, a TEXT column with no CHECK, so the two new words needed no column change. The six statuses are the canvas's (`frontend/src/pages/admin/kyc/kycModel.js` `STATUS_WORD`):

| Stored | Canvas word |
| --- | --- |
| `not_started` | Not started |
| `pending` | Waiting |
| `needs_info` | Needs information |
| `approved` | Approved |
| `rejected` | Rejected |
| `expired` | Expired |

Only `approved` opens full access, as before: every gate in the Worker tests for it alone.

Migration 614 adds:
- **`kyc_case_assignments`:** who on HQ holds the case, and since when, one row per person keyed by `user_id`. It is a side table because `users` is at D1's 100-column cap (GOTCHAS; `migration_column_shapes` fails any migration that adds a column to `users`). Nothing is added to `users`.
- **`kyc_case_events`:** the case's history. Each row is one thing that happened:
  - a submission;
  - a decision: approved, rejected or needs information;
  - a re-check, an expiry or an assignment.

  A decision copies the submission it answers into `submitted_at`, so the time to a decision needs no join.
- **`kyc_notes`:** HQ's notes on a case. The member never reads them.
- **`kyc_documents`:** several documents per case, each with a kind: `id_front`, `id_back`, `proof_of_address`, `selfie` or `other`. Only the R2 key is stored, under the `kyc/` prefix that `services/r2.ts` guards.

Events and notes refuse an UPDATE. A document allows only `removed_at`, set once. None of them refuses a DELETE, and the user ids carry no REFERENCES, so an account erasure can still remove a member's rows.

There is **no backfill**. A case decided before 614 has no events, and the figures read only what is recorded.

### 2. The queue (KYC1, KYC2): `GET /admin/people`

The query takes these parameters. A value outside the lists falls back to the default; it never reaches SQL.

- **`status`:** `all` (the default) is every case someone has opened; `not_started` is read only when asked for.
- **`q`:** searches the name or the email. `%`, `_` and the escape character are escaped, so the search is text, never a pattern.
- **`id_type`** and **`country`:** the country is compared in upper case.
- **`flag`:**
  - `pep`: the member disclosed being politically exposed;
  - `auto_failed`: the automated check failed;
  - `no_document`: no document is on file.
- **`assignee`:** `me`, `none` or an admin's id.
- **`sort`:** `submitted`, `name`, `status` or `reviewed`. The default is submitted, oldest first, with an unsubmitted case last. `reviewed` defaults to the newest first.
- **`dir`**, **`page`** and **`page_size`** (25 by default, at most 100).

The reply is `{ rows, total, page, page_size, counts }`.
- **`total`** counts the rows under every filter.
- **`counts`** gives the count per status under every filter but `status`. With `status=all`, the counts other than `not_started` add up to `total`.

Each row carries:
- the person's id, name, email and role;
- the status, the submitted and reviewed times;
- the wait in whole days, for a waiting or Needs information case only;
- the ID type, the country and the flags;
- the assignee, with their name and when they took the case;
- the reviewer, by name. `kyc_reviewed_by` was stored and never read until now.

No identity value is on the list: no date of birth, ID number or address.

Every statement in `services/kycCase.ts` is static. A filter is a bound value read by a fixed `(? IS NULL OR …)` clause, and the sort is a bound key read by fixed `CASE` clauses. A malformed `kyc_data` reads as `{}`, never as an error. No raw-interpolated SQL is added.

Each read writes one `kyc_queue_access` row, with counts only. `GET /admin/queue` stays as it was for D648's console.

### 3. One case (KYC5)

- **`GET /admin/:userId/case`:** the assignee, the history (the newest 100), the notes and the documents. A document shows its kind, type, size and dates, never its key. Logged as `kyc_case_access`.
- **`PATCH /admin/:userId/assign { assignee_id | null }`:** only an admin can hold a case. It writes an `assigned` or `unassigned` event and a `kyc_case_assigned` log row. It is not a decision, so it needs no step-up.
- **`POST /admin/:userId/notes { body }`:** a note of 1 to 2,000 characters. The `kyc_note_added` log row names the case, never the note.
- **`GET /admin/:userId/documents/:docId`:** streams one document of that person's case, logged as `kyc_document_access` with its kind and id. The content type is re-checked against the allowlist on the way out.

### 4. Decisions

Each decision keeps the TOTP step-up and the branch-not-suspended gate. Each writes its history row and an activity line, and sends its member notice.

- **Needs information (`PATCH /admin/:userId/needs-info { message }`):** a waiting case goes back to the member with a question of 5 to 2,000 characters. Any other status is a 409, `not_waiting`. The member's `GET /status` now carries `info_request`, the latest question.
- **Re-check (`PATCH /admin/:userId/recheck { message }`):** an approved or expired person is asked to verify again. Their status becomes `needs_info`, so full access waits for the new check; the dialog must say so. Any other status is a 409, `not_checked`.
- **Approve (`PATCH /admin/:userId/approve { note? }`):** takes an optional approval note of at most 2,000 characters. The note is kept on the history and is HQ's: the member's notice does not carry it.
- **Reject:** also purges the case's listed documents. The bytes go from R2, and each row keeps `removed_at`, as the single legacy document did.
- **Submit (`POST /submit`)** accepts a resubmission from `needs_info` and `expired`, as well as from `not_started` and `rejected`, and records a `submitted` event.
  - An automated fail also records a `rejected` event.
  - `documents: [{ kind, data_uri }]`, at most five, stores each document to R2 and writes one `kyc_documents` row each. With no bucket bound they are refused with a 503 rather than inlined.
  - The single legacy `id_document_base64` works as before.

### 5. The member's notices

Each notice is sent in-app and by email through `services/notify.ts` with category `security`, so quiet hours and the digest do not hold it. Each links to `/kyc`. The words are in `kycCase.ts` `noticeFor`:

| Decision | Notice |
| --- | --- |
| Approved | Your identity is verified |
| Rejected | Your identity check was not approved, with the reason |
| Needs information | Axal compliance needs more information, with the question |
| Re-check | Verify your identity again, with the reason |
| Expired | Your identity check has expired |

A missing reason reads "Not recorded", never blank. A notice that fails never fails the decision.

### 6. Expired

`services/trust.ts` `expireDueArtifacts` marks a lapsed `kyc_v1` obligation as expired, as before. It then calls `expireKycFromObligations`, which:
- moves each person from approved to expired, unless they also hold a satisfied `kyc_v1`;
- records the event and the `kyc_expired` activity line, and tells the member;
- re-opens the obligation as pending, so the nightly `resyncKycKyb` satisfies it again once a new check is approved.

It is idempotent: a second night moves nobody. A failure here never stops the rest of the night's housekeeping. The return value carries `kyc_expired`.

### 7. The figures (KYC3): `GET /admin/figures`

The read returns:
- **Decisions per week** for the last eight weeks: approved, rejected and needs information.
- **The median hours from a submission to its decision**, over the last 90 days. With nothing recorded it is null, with the reason "No decision in the last 90 days has its submission time recorded".
- **The wait bands** of the people still waiting: under 1 day, 1 to 3 days, 3 to 7 days, over 7 days, and not recorded.

It is logged as `kyc_figures_access`.

### 9. Tests

`cloudflare-worker/test/kyc_people_queue_d1229.test.ts` runs on `buildFresh`: the baseline plus every later migration. It covers:
- **The queue:** oldest first, the wait, the ID type, the country, the flags and the reviewer, with no identity value.
- **Paging and counts agree:** the pages put together make the total, and the counts add up to it.
- **Search and filters:** search, each filter, assignee `me`, `none` and an id, and each sort. A wildcard in the search matches nothing.
- **Every read still logs:** one row per read, with no identity value; a member is refused.
- **Step-up:** a decision without step-up is refused (403 `step_up_required`) and writes nothing.
- **Decisions:**
  - Needs information: recorded, told, and read back by the member;
  - re-check;
  - approve with a note, which is not in the member's notice;
  - reject, which purges the listed documents.
- **Resubmission** from Needs information and from Expired; never while waiting.
- **Several documents:** refused without a bucket, refused with an unknown kind, and with a bucket stored under `kyc/`, read and streamed (logged); another person's document is a 404.
- **Expiry:** an expired `kyc_v1` moves its person to Expired, re-opens the obligation and tells them. A second night moves nobody, and the person can then resubmit.
- **Assignment and notes:** only an admin holds a case; a note never reaches a log; the history and the notes refuse an UPDATE.
- **The figures:** the eight weeks, the median, null over nothing, and the bands.
- **The query parser:** it falls back on anything unknown.

`frontend/test/kyc_people_client_d1229.test.mjs` pins the client: its query string, its routes and its line in `api.js`.

**Mutation checks, each caught:**
- submit refusing `expired`;
- Needs information without step-up;
- `all` counting `not_started`;
- wildcards left unescaped;
- no expiry hand-off;
- the queue read not logged;
- the Needs information notice not sent;
- oldest first lost;
- the obligation not re-opened.
