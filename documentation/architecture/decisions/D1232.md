### 1. Renewal periods (KYC17c)

- **Migration 617** holds one row per check whose period HQ has set. No row means the code's default (`DEFAULT_PERIOD_MONTHS`), so nothing is seeded, and an unset period never reads as someone's choice.
- **Months, not days:** a month is 365/12 days, so the defaults are exactly ROLE_MATRIX's 730 and 365 days. A test holds the two together.
- **A new period never moves a date.** Each approval is stamped with the period in force at that moment:
  - KYC: `resyncKycKyb`, when it satisfies `kyc_v1`.
  - KYB: D1231's case approval (`kyb_admin.ts` `PATCH /:id/approve`), which wrote a fixed two years. `resyncKycKyb` copies the case's date onto `kyb_v1` as D1231 built it.
  - No code reads the table to recompute a stored `expires_at`.
  - If the table is missing (migration 617 not applied yet), the defaults are used. Any other failure throws, so no date is stamped from a period that could not be read.
- **Accreditation's period is kept but not used yet:** no route satisfies `accreditation_v1` today. The read says so (`applied: false` with its reason).
- **Sanctions screening's period** (the canvas's fourth row) is part 2's (D1230) and is not stored here.

| Route | Gate | What |
|---|---|---|
| `GET /api/kyc/admin/periods` | any admin | each period, its default, whether HQ set it, when and by whom, whether it is applied; `can_change` |
| `PUT /api/kyc/admin/periods` `{ periods: { kyc_v1?, kyb_v1?, accreditation_v1? } }` | Super Admin at HQ, recent TOTP step-up | whole months, 1 to 120; only changed values are written; `kyc_periods_changed` names each change as `key from->to months` |

A branch deployment uses its own database (D106). HQ's setting does not reach a branch yet, and every branch keeps the defaults until that is built.

### 2. Renewals (KYC9)

`GET /api/kyc/admin/renewals?filter=all|soon|expired&q=&page=` (any admin; logged `kyc_renewals_access` with the row count).

- **What it lists:** every satisfied or expired `kyc_v1` and `kyb_v1` row that expired, or expires within 12 months. Expired rows come first, then the soonest.
  - Excluded: a check never satisfied, a pending row (one rejected on a re-check keeps its old date), and accreditation.
- **Each row:**
  - who, and whether it is a person (KYC) or a business (KYB);
  - the check, its date and days left;
  - which of the 30-, 14- and 7-day warnings went out (`renewal_notices`). A warning counts only when it was sent for the row's current date, so a renewed check shows none until the sweep warns again;
  - the obligation's status, and for KYC the person's `kyc_status`.
- **Counts:** expiring within 30 days (with the next date), expired, and all. The month chart covers the next 12 months, by people and businesses.
- **Screened over 12 months ago:** approved people whose latest `sanctions_screenings` run is over a year old, with those never screened counted apart. A failed run writes no row, so "never screened" is never folded into "screened". An unreadable table says so, never 0.
- **Re-checks asked, not done** (D1229's `kyc_case_events`, merged from main while this was built): each person's latest `recheck`, open until a submission comes after it. The tile gives the count and the oldest ask, and a KYC row carries `recheck_asked_at`. Unreadable events say so, never 0.
- **A failed read** is 503 Unreadable, never an empty list.

### 3. Audit (KYC10)

`GET /api/kyc/admin/audit?from=&to=&action=&admin=&case=&q=&page=` (any admin; logged `kyc_audit_access`).

- **Window:** from and to are dates, at most a year apart. The default is the last 30 days, ending with the current second: stored times are whole seconds, so a row written this second is included.
- **What it returns:** the window's admin-side KYC actions, newest first. Each row is the canvas word, the admin, the case and a detail. It also returns per-day looks and decisions, and the admins and actions to filter by.
- **Which actions:** `KYC_AUDIT_ACTIONS`:
  - the four reads (list, case, value shown, document);
  - the renewals and audit reads;
  - approve, grant without a check, reject;
  - period changes;
  - D1230's Send to HQ and HQ's decision, and D1229's case read, figures, ask for information, re-check, assignment and note (both merged from main while this was built);
  - D1231's eleven KYB case actions: the business list, a business case and its documents (looks); approve, reject, ask for documents and dismiss an import (decisions); link an import, update the owners, add a document and record a studio (changes).
  - Assignments and notes are a third kind, `change`: in the list, counted as neither a look nor a decision.
  - `kyc_expired` is the expiry sweep's own row, with the member in `user_id`, so it is left out with the members' rows.
  - The member's own rows (`kyc_approved`, `kyc_rejected`, `kyc_submitted`) are left out, so a member is never named as an admin.
  - A later part adds its actions to the map as it writes them.
- **A KYB row names its business**, never an account. `kyb_admin.ts` writes `{ case: <uid>, outcome, field? }`, so the row carries `business: { uid, name }` from `kyb_businesses`. Its shown-value row names the field (registered address, registration number, an owner's date of birth), never the value.
- **Names and actions only.** A row never carries the `details` sentence as written:
  - A rejection's reason is free text, so it is not shown; only whether a document was deleted.
  - "Showed a value" names the field, never the value.
  - The case's account id is taken from the last `user_id=<n>` that `kyc.ts` writes into the sentence. It is the last because an assignment names the assignee first; the assignee is shown as "Assigned to …". A row without one (the queue read) has no case.

### 4. The export (KYC17d)

`POST /api/kyc/admin/audit/export` `{ from, to, reason }` (Super Admin at HQ).

- **The reason** is required, 10 to 500 characters.
- **The record comes first.** One `admin_audit_log` row (`kyc_audit_export`, report type `kyc_audit`, CSV, with the dates, reason and row count) is written before the file is made. If it cannot be written, no file is made (503).
- **The file:** the same rows as the audit read, as CSV: when, admin, action, case (the person, or for KYB the business), detail. A cell that starts with a formula character is neutralised.
- **Size:** over 20,000 rows is refused with a request for a shorter window, never cut short.
- **Not built:**
  - "Every studio / One studio": this deployment's record only.
  - The step-up: the canvas shows none on this dialog.
