## D918 — The Events desk's reads: the overview, the paged list, one event's summary and history, the free-seat preview

Issue #2701; part 3 of #2368. Worker reads and their clients only; the pages
are parts 4 to 7. No migration.

Code: `cloudflare-worker/src/services/adminEventsReads.ts`, mounted in
`routes/admin_events.ts`. Every route is `requireAdmin`, with no HQ gate.
Tests: `cloudflare-worker/test/events_desk_reads_d918.test.ts`.

### 1. The rules

The words and rules are D915 §2's, so the overview, the calendar and the
review queue agree:

- **Seats taken** are registered + confirmed + attended.
- **An event has ended** once its `ends_at` has passed. With no `ends_at`, it
  has ended a day after its start. Offset-free timestamps are UTC (D916).
- **Show-up** is attended ÷ seats taken, for ended events that are not
  cancelled. Before that it is `null`, never 0.
- **Overdue** is waiting more than 72 hours (`SLA_PAST_HOURS`).
  - The wait counts from `submitted_at`.
  - An event queued before part 2 has no `submitted_at`, so its wait counts
    from `created_at`. That is the Approvals lane's rule (D917,
    `approvalSources.ts`), so the two counts match.
- **Two events clash** when neither is cancelled and their times overlap. An
  event with no `ends_at` lasts one hour for this rule.
- **Low sign-ups** is an event with a cap that starts within 7 days with fewer
  than a quarter of its seats taken.
- **How a seat was got**, in this order:
  - with an `invitation_id`, it is `invitation`;
  - otherwise a comp seat is `free_seat`;
  - otherwise it is `signed_up`.
  - "Added by an admin" is `{ recorded: false }`, because nothing writes it.
- **Who registered** uses `users.role`: founder, partner, exploring, advisor,
  investor or admin. With no account it is `guest`. An account that is gone,
  or a role with no bucket, is `not_recorded`.
- **Format** comes from `location_kind`:
  - `virtual` is `online`;
  - `physical`, and the legacy `in_person`, are `in_person`;
  - `hybrid` is `hybrid`.
- **Live** events are the ones published or waiting for review (D915 §3). Next
  30 days, the waitlists, type, format, Full and Low sign-ups count only these.

### 2. Every block answers alone

Blocks follow D893's shape:

- a block read is `{ available: true, ... }`;
- a failed block is `{ available: false, unreadable: true, reason }`, where the
  reason is a sentence and never the database's text;
- a block with no store is `{ recorded: false, reason }`.

A failed block never reads as zero. Blocks that share one read fail together,
because they share a store; the others still answer. Only the host line
carries a name, because the canvas draws it. No member's name, email or ID
appears in any read.

### 3. `GET /api/admin/events/overview?weeks=4|12|52`

`weeks` defaults to 12. Any other value is 400 `invalid_weeks`.

- **The period** is `weeks` Monday weeks (UTC), ending with the current week.
  The current week is still running, so it carries `to_date: true`.
- **The response** is
  `{ weeks, period: { start, end, current_week_to_date }, ...blocks }`.

| Block | Returns |
|---|---|
| `queue` | `count`, `oldest_since`, `oldest_hours`, `overdue`, `overdue_after_hours` (72), and `waiting_from_created_at` (queued events with no `submitted_at`) |
| `upcoming_30d` | Live events starting in the next 30 days: `events`, `seats_taken`, `full` |
| `waitlisted` | On live events still to start: `registrations` waitlisted, and `events` with a waitlist |
| `weekly` | `weeks[]` of `{ week_start, registrations, checkins, to_date? }`, plus `registrations: { this_period, previous_period }`. Registrations are counted by `registered_at` and check-ins by `event_checkins.checked_in_at`. |
| `show_up` | Events that ended in the period and are not cancelled: `events`, `seats_taken`, `attended`, `rate`, and `recent`, the last 8 with their own rate |
| `by_status` | All events: `draft`, `pending_review`, `published`, `rejected` (its own bucket), `cancelled`, `other` |
| `by_type` | Live events starting in the period, for the 12 types, plus `other` |
| `by_format` | The same events: `online`, `in_person`, `hybrid`, `not_recorded` |
| `by_role` | Seats registered in the period, by role, with `guest` and `not_recorded` |
| `by_source` | The same seats: `invitation`, `free_seat`, `signed_up`, plus `added_by_admin: { recorded: false }` |
| `paid` | Paid registrations from the period: `count`, and `by_currency[]` of `{ currency, count, amount_cents, amount_not_recorded }`. A paid row on a cancelled registration still counts, because the money was taken. |
| `payment_pending` | Pending payments from the period, leaving out cancelled and declined registrations: `count` |
| `free_seats` | Comp seats registered in the period: `count` |
| `cancelled` | Cancelled events that start in the period: `events` and `with_paid_tickets`. No cancellation time is stored, so the period is read by start, and `counted_by: 'starts_at'` says so. |
| `needs_attention` | `counts` per kind, `total`, and `items[]` of `{ kind, event_id, title, starts_at, ... }`. The kinds are below. |
| `views` | `{ recorded: false }` — "No store counts views of an event page, so the funnel starts at registration." |
| `feedback` | `{ recorded: false }` — "Events have no feedback form yet." |

The `needs_attention` kinds:

- `overdue`, with `waiting_hours`;
- `full`: a live event that has not ended and whose seats meet its cap;
- `low_signups`;
- `clash`, with `with[]`: the events it overlaps that have not ended yet;
- `changed_after_approval`: a published event that has not ended;
- `paid_on_cancelled`, with `paid_tickets`.

### 4. `GET /api/admin/events` — the paged list

Today's response stays valid: `events[]` still carries every field
`shapeEvent(..., { includePrivate: true })` gives. With no sort, the order is
still newest created first.

**Filters.** An unknown value is 400 `invalid_<name>`.

- `status`: one value or several, comma-separated or repeated;
- `visibility`: `public`, `unlisted` or `private`;
- `when`:
  - `upcoming` and `ended`, by the ended rule;
  - `this_week`: starts in the current Monday week;
  - `next_30d`;
- `price`: `free` or `paid`;
- `featured`: `1`/`true` or `0`/`false`;
- `q`: a case-insensitive match on the title, the host's name or the venture's
  name.

**Sorts.**

- `sort`: `starts`, `created`, `seats_taken`, `fill`, `show_up` or `waiting`.
- `dir`: `asc` or `desc`. `starts` defaults to ascending; the others default
  to descending.
- A missing value sorts last either way.

**Paging.** `limit` is 1 to 200, and defaults to 50. `offset` defaults to 0.

**Each row adds:**

- `seats_taken`, `attended`, `waitlisted`;
- `fill`: `null` with no cap;
- `ended`;
- `show_up`: `null` until ended;
- `waiting_hours`: only while waiting for review;
- `host: { name, role }`: the host's display name, else their name;
- `venture: { name }`: `null` with no project;
- `clash`.

**The response also carries** `total` (after the filters), `limit` and
`offset`.

The filters, the sorts and the clash flag need every event's counts and times,
so the event rows are read once and cut in the Worker. This is the same scale
as `/analytics`, and it retires D915's Guard G.

### 5. `GET /api/admin/events/:id/summary`

Counts only. Each of these is a block:

- `host`: `{ host: { name, role } | null, venture: { name } | null }`;
- `registrations`: `by_status` (registered, confirmed, attended, waitlisted,
  declined, cancelled, other), `seats_taken`, `capacity`, `ended` and
  `show_up`;
- `by_source` and `by_role`: the seated registrations, by §1's rules;
- `payments`:
  - `price_cents` and `currency`;
  - `by_payment_status`: none, free, pending, paid, refunded, not_recorded,
    other;
  - `paid` (`count` and `by_currency`) and `payment_pending`;
  - `refunds: { recorded: false }`. HQ refunds by hand in Revenue › Billing
    (O-REF).
- `free_seats`: `count`;
- `checkins`: `count`;
- `invitations`: `total`, `free_seat`, `by_status` (pending, accepted,
  declined, revoked) and `by_source` (manual, auto_partner, auto_lp);
- `reminders`: `sent` and `by_kind` (`reminder_24h`, `reminder_1h`), from
  `event_notifications`;
- `seats_by_day`: `days[]` of `{ day, seats, total }`, by the day each current
  seat holder registered.
  - Cancellation and promotion dates are not stored, so the series is
    `counted_by: 'registered_at'`.
  - Registrations with no date are counted in `registered_at_not_recorded`.

### 6. `GET /api/admin/events/:id/history`

`{ event_id, history }`. `history` is one block:

- `created_at`, `submitted_at`, `approved_at` and `changed_after_approval_at`;
- `items[]` of `{ at, action, actor }`, oldest first.

Where the items come from:

- the desk's own `admin_audit_log` rows (`report_type = 'events'`): approved,
  rejected, unpublished, featured, cancelled and capacity changed;
- the `event_submitted` and `event_updated` rows that `logAdminAction` writes.

How each item reads:

- **`actor`** is `admin` or `host`, never a name.
  - A desk action is always `admin`, even when the admin is also the host.
  - A submission or an edit is `host` when the host made it, and `admin`
    otherwise.
- A send-back carries `reason`.
- A feature carries `featured`.
- A capacity change carries `capacity`.
- An edit carries the names of the `fields` it changed, never their values.

### 7. `GET /api/admin/events/:id/comp-preview`

This is a dry run of what approve would invite. It covers only the two
sources approve mints (`mintCompInvitations`): official partners and invested
LPs. It mints nothing, and returns `minted: 0`.

- **`sources`** is one block, with `official_partners` and `invested_lps`.
  - A source whose flag is on gives
    `{ on: true, eligible, already_invited, would_invite }`.
  - "Already invited" uses `mintCompInvitations`' own match: an invitation for
    the same user, or for the same email.
  - A source whose flag is off gives `{ on: false }`, with `null` counts.
- **`seat_at_sign_up`** lists the other flags that are on. These are
  investors, project founders and host connections. They give a seat at sign-up
  and send no invitation.

`evaluateCompEligibility` takes `{ strict: true }` here, so that a failed
source makes the block unreadable instead of reading as nobody. Its other
callers keep their skip-the-rule behaviour.
