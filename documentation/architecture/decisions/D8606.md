## D8606 — A pull request merged into a stacked branch is exempt from the identity chain (#8606)

**Context.** D8068's `provenance` check reads every commit a pull request adds. Since
2026-11-25 the owner has been combining pull requests by merging one into another's branch.
GitHub writes that squash commit itself and puts a `Co-authored-by:` paragraph after the
merged pull request's trailers, so the parser finds no trailer block. A branch that holds
several merged pull requests also names several slots and tasks, which the check refuses. So
`provenance` could never pass on a combined pull request.

**Decision.** A commit is exempt when GitHub says it is a merged pull request's
`merge_commit_sha`. That pull request's own commits were checked on its own branch.

- The workflow asks the API (`GET /repos/{repo}/commits/{sha}/pulls`) about each commit in the
  range that GitHub committed. It writes the matching shas to a file.
- The script exempts exactly those shas (`--pr-merges <file>`). It never infers a merge from
  the author, the committer or the message.
- The branch's own commits still need the full chain, and still name one slot and one task:
  the branch's issue.
- A merge someone writes by hand that adds content is still an authored change, and still
  needs trailers. A clean merge is still exempt, as before.

**Rollout.** The workflow passes the list only to a base copy of the script that accepts
`--pr-merges`. A pull request whose base predates this change is judged as before, until its
base carries it.
