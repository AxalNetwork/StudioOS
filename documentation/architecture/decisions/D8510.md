## D8510 — The Worker's Stripe client names its API version, and the renewal webhooks read both invoice shapes (#8510)

**Context.** `stripeCall()` sent no `Stripe-Version` header, so every platform call ran on the Stripe account's default version, which a dashboard upgrade changes with no pull request. The renewal webhooks read `invoice.subscription`, the pre-Basil invoice shape. From `2025-03-31.basil` an invoice carries its subscription at `parent.subscription_details.subscription` instead. Neither the account's version nor the webhook destination's version is recorded (STRIPE_RENEWAL_GRACE.md).

**Decision.**

1. `routes/billing.ts` exports `STRIPE_API_VERSION` and `stripeVersionHeaders()`, and `stripeCall()` sends the header from them. The constant is `null` until the owner reads the account's version in Stripe Workbench and posts it on #8510. While it is null no header is sent, which is the behaviour before this decision. It is never set to a guess.
2. `services/stripeInvoiceShape.ts` reads an invoice's subscription from both locations, as an id or an expanded object. The alert writer, the renewal notice, the incomplete-row repair on `invoice.paid`, the refund and dispute lookup, and the renewal recovery read it there. Before this, a Basil `invoice.payment_failed` or `invoice.payment_action_required` opened no alert and told no member, and a Basil `invoice.paid` repaired no row left at `incomplete`.
3. `test/stripe_api_version_8510.test.ts` runs `invoice.paid`, `invoice.payment_failed` and `invoice.payment_action_required` in both shapes through the real webhook route to the alert, the notice and the entitlement. Its fixtures are sanitised.
4. A guard in the same test fails when a Worker file calls the Stripe API (`https://api.stripe.com/v1…`, or the host as a string a path is appended to) outside `stripeCall()` without its own `Stripe-Version`. The Wellbeing Connect status read now goes through `stripeCall()`, so `routes/wellbeing.ts` leaves the list of files that name `api.stripe.com` in D707 (its test, `stripe_money_kind_sites_d707.test.ts`, now pins five files). The allowlist has two entries, each with its reason: the credential probe in `providerOauthTest.ts` (a pasted key, not the platform key; status code only) and the endpoint displayed on the connector page. The connector client pins its own version and passes.

**Not done here.** The owner's step 1 (both version strings). The **Pay** and **Confirm** renewal actions still read `invoice.payment_intent` from an API response, which Basil removed: setting the constant to a Basil version must move those reads in the same change.

**Consequence.** A version upgrade is a reviewed change: the constant, the fixtures and the webhook destination move together.
