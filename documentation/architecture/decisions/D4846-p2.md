### The six states, one rendering each

BD14's audit finding was "all missing states carry the same visual weight". `pages/cycles/buildSystemStates.js` (pure) names the states and maps the Worker's words to them; `pages/cycles/BuildStates.jsx` draws them.

| State | Worker words | Drawn as |
| --- | --- | --- |
| Not recorded | null or empty cell, "Not recorded" | D5129 `StateChip` `not_recorded` (dotted, —) |
| Not expected yet | "Not expected yet", "Not required" | D5129 `StateChip` `not_applicable`, labelled "Not expected yet" (no border, lightest) |
| Unavailable | "Unavailable", "Could not be read", "Unreadable" | D5129 `StateChip` `unavailable` (dashed, "!"); always says "Unavailable" |
| Waiting | "Processing", "Waiting", "Pending", "Waiting for …" | Build chip, violet, clock glyph |
| Needs attention | "Needs attention", "Missing", "Blocked" | Build chip, amber, ▲ |
| Read only | "Read only" | Build chip, grey, padlock |

Any other word stays as the Worker wrote it. A missing value is Not recorded, never Needs attention; a failed read is Unavailable, never Not recorded, None or 0. The label is BD14's word for Not recorded and Unavailable, and the Worker's own word ("Blocked", "Missing") for the others.

Where each page uses it:

- **Module page** (`CycleModulePage.jsx` `Cell`): a state cell draws its chip, so "Not expected yet" (was plain text), "Unavailable" (was an amber pill) and Not recorded (was a dashed pill) no longer look alike.
- **Phone module page** (`PhoneModulePage.jsx`): a row whose pill is a state draws the same chip as its value (`phoneStateRow`), not a `ui/Pill`; Prototype / MVP's Blocked pill was red and is now Needs attention.
- **Overview** (`CycleOverview.jsx`): a Not recorded card draws D5129's chip; an unreadable card is D5129's Unavailable block with its own "Try again" (no red box, and `role="alert"` only after a Retry, ST-09); an unreadable figure is the Unavailable chip and "<source> could not be read" in muted ink. These three changes are in the shared overview and module card, so Validate's and Raise's overviews draw them too: one shape for these states on every cycle, as D5129 asks.
- **Parts** (`buildParts.jsx` `PartBoundary`): `DataState` Unavailable with Retry, announced only after a Retry.
- **Read only** on Build's overview (`data.read_only`) is the Read only chip and a sentence on a plain card. Raise's amber bar (RO14, its own canvas) is unchanged. Build's reads do not send `read_only` today, so this draws only once one does.

### One notice for failed module reads

BD14 A's "Partial read failure": `BuildPartialNotice` draws D5129's `PartialBanner` once over Build's module cards when at least one card could not be read: **"5 of 6 modules read"** and "Operating systems could not be read." Its Retry re-reads only the failed cards (`onRetryCard` per slug); each card keeps its own Retry. Hidden when every module was read. A card still loading counts neither way; empty, Not recorded and plan-locked cards were read; a card in a state the page does not know counts as not read (`cardView`'s rule). `PartialBanner` gained one optional prop, `lead`, for the bold words, because its own lead counts "sources".

### The tablet tier (BD14 B)

- `ui/phone/tabletTier.js` (pure): phone below 768px, tablet 768px to 1023px (`TABLET_QUERY`), desktop from 1024px. `useTabletWidth(enabled)` in `ui/phone/usePhoneWidth.js` reads it.
- `CycleRoute.jsx`: `const tablet = useTabletWidth(def?.tabletPages === true); const phone = usePhoneWidth() && !tablet;`. Only `defs/build.jsx` names `tabletPages`, so Build draws its desktop overview and module pages from 768px and its phone pages below; every other cycle is unchanged (phone page below 1024px). No new import in the frozen hub: `useTabletWidth` comes from the module it already imports (D5615).
- The tablet tier needs the tablet query to match **and** the below-768px query not to. In a browser the first implies the second; an environment that answers every query alike (a test's stub) keeps the page it drew before.
- At 768px Build's overview draws two module columns (`md:grid-cols-2`, the last card of an odd count spanning the row) and its four figures in one row (`md:grid-cols-4`, which also holds from 1024px, as BD1 draws), instead of the phone page's single column or the desktop's one-column grid below `lg`. The header keeps its module select below 1024px. The module page at 768px is the desktop page; its records table lays rows out as at any width below `lg`.
