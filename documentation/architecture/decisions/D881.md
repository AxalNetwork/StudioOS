## D881 — Mercury for members: Sign in with Mercury only; new API-token connections retired, existing ones keep working

- **Status:** filed by S1 for the owner on 2026-10-22 as #2554 (C3 of #2551). Built for slot S10.
- **Basis:** `origin/main` at `784a1bed8d`. Worker paths are relative to `cloudflare-worker/src/`; frontend paths to `frontend/src/`.
- **Stacks on:** D713 (a member's own Mercury), D752 (investors, HQ only), D840 (Sign in with Mercury through its MCP server).
- **Beside:** C1 (#2552, D879, merged as #2560 before this) removed the entity variant from the member connector, and C2 (#2553, D880) moves the entity UI under HQ. This decision changes only the member's way in, and leaves HQ's files as they are. C1's tests that named the old sign-in kind (`oauth_or_key`) or the old token answer (`api_key_required`) now read `mcp` and `token_connect_retired`.
- **Migration:** none. No row is changed or deleted.

### 1. The decision

The owner ruled on 2026-10-22: members connect Mercury only by Sign in with Mercury, through Mercury's MCP server, read-only.
- Pasting an API token is not offered to a new connection, and is refused if sent.
- A member already connected by token keeps their connection.
- When they disconnect or reconnect, the sign-in is what they are offered.

HQ's entity token connections (`/api/admin/mercury`, D710) are untouched.

### 2. As built

**The Worker:**
- **`integrations/providers/mercury.ts` `connect`.** This is what `POST /api/integrations/connect` (and `/api/connectors/connect`) calls for a member.
  - It keeps its first refusals: a support session (403 `support_session_refused`), and a role with no personal connection or an investor off HQ (403 `purpose_not_allowed`).
  - Then it refuses every token with 410 `token_connect_retired`: "Connect Mercury with Sign in with Mercury." (`TOKEN_CONNECT_RETIRED`). That covers a new connection, and a replace of a stored one, which is the same route's upsert.
  - Nothing reaches Mercury, and nothing is stored or logged. The stored row of a replace is left exactly as it was.
  - The token-checking code it no longer runs is removed. Decision 3's `entityAccountRefusal` and `readOnlyRefusal` stay, because the sign-in and every read call them.
- **`routes/mercury_personal.ts` `GET /status`.** The connection gains two fields:
  - `via` (`oauth_mcp` or `api_key`);
  - `notice`: "Connected with an API token. Sign in with Mercury to keep it connected after you reconnect." (`LEGACY_TOKEN_NOTICE`) on a token row, null on a sign-in.
- **`routes/mercury_oauth.ts`** is unchanged in behaviour. Signing in over a token row turns that same row into a sign-in, as it did; its comment no longer says a token can switch it back.
- **`integrations/connectorPages.ts`.** The member pages' `sign_in` is `{ kind: 'mcp', label: 'Sign in with Mercury', key_help_href: null }`.
  - `MERCURY_SIGN_IN` stays, without "A Read Only API token works too."
  - There is no entity page (C1, D879).

**The frontend:**
- **`connectorPageModel.js`:**
  - A member's Mercury has no other way in (`pageChoices`) and no Replace (`manageItems`).
  - A token row's Manage offers "Sign in with Mercury"; a sign-in's says "Sign in again".
  - `signInLabel` is "Sign in with Mercury".
  - The `mcp` kind draws its Sign-in URL.
- **`useConnectFlow.js`:** the member's read-only confirmation and Mercury's token-refusal branch are gone.
- **`ConnectorSheet.jsx`:**
  - The key form's Read Only banner and checkbox are gone, and so is "Use a Read Only API token instead".
  - The member's token row has no Replace.
  - "How it reads" gets the connection, so a token row shows the notice.
- **`mercuryModel.js`:**
  - `TOKEN_ALT` is removed.
  - `MEMBER_REPLACE` is "Sign in with Mercury again."
  - `VIA_ROWS.api_key` is the Worker's notice.
  - The sign-in failure words and Build's banner name no token.
- **Kept for HQ:** `TOKEN_HELP` and `confirmReadOnlyLabel` are used only by the entity `ConnectForm` (`MercurySheet.jsx`), which is HQ's form and C2's to move, so they stay.
- **`discoverModel.js`:** `SIGN_IN_LABEL.mcp` is "Sign in through the service’s MCP server".

### 3. The connections that exist today

- **The count.** The number of member token connections at D881 is a read-only D1 count, read by S1 or the owner and recorded on #2554, not in this PR:

  `SELECT COUNT(*) FROM integrations WHERE provider_key = 'mercury' AND auth_type = 'api_key'`

  Until it is recorded there, this file holds no figure.
- **The plan: no forced disconnect.**
  - Each such row keeps reading through D710's GET-only client (`services/mercury/connection.ts`) for what it read before: the venture revenue import and spending, receipt matching, practice income, partner deals and proof of funds.
  - Its page says the notice.
  - When the member disconnects, the row is gone and only the sign-in is offered. When they sign in, the same row becomes a sign-in.
  - A token Mercury later rejects marks the row `error`, as before. Its fix is the sign-in.

### 4. Grow and Raise

The issue's acceptance criterion "An existing token connection still syncs Grow and Raise" needs one precision.
- **On `main` before D881,** the D840 feeds already refuse a token row with 409 `mercury_sign_in_required`:
  - the Grow sync (`POST /api/cycles/grow/mercury/sync`);
  - the Raise modules (`services/mercury/raiseAccess.ts`).

  Their reads (invoices, treasury, cashflow, statements, SAFEs) exist only on Mercury's MCP server.
- **What D881 changes there:** nothing.
- **What a token row still feeds,** and keeps feeding:
  - D713/D752's reads: the revenue credits that become Revenue and traction rows, spending, burn and runway;
  - the raise receipt matches.

Anything more for Grow and Raise is C4's (#2555, D882).
