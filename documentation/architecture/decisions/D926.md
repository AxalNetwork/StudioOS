## D926 — Partner invitations: server-side search, filters, sort, pages and totals on invitations and deals; the create lookup

- **Status:** decided by S1, 2026-10-24 (#2722; part 3 of #2370). Built by the S08 agent in slot S04, at the owner's request.
- **Basis:** `origin/main` at `6daf1a3173`, which carries part 1 (D924, #2735) and part 2 (D925). Paths are under `cloudflare-worker/src/` unless they say otherwise.
- **Migration:** none. The filters read columns that are already stored.
- **Builds on:** D923 §2 (the stage words, Lapsed, Guard L) and §3 (the PI2 and PI5 toolbars); D924 (resend keeps the stage, so a stored stage is the stage reached).

### 1. What changed

All three reads are in `routes/admin_partners.ts`; the clients are `adminPartners.*` in `frontend/src/lib/api.js`.

| Read | New parameters | Answers |
|---|---|---|
| `GET /api/admin/partners/invitations` | `q`, `stage`, `deal_type`, `invited_by`, `sent_within`, `sort`, `limit`, `offset` | `{ items, total, limit, offset, sort }`; each row also carries `invited_by_user_id` |
| `GET /api/admin/partners/deals` | `status` (several, or `all`), `deal_type`, `ends_within`, `q`, `has_redemptions`, `sort`, `limit`, `offset` | `{ items, total, limit, offset, sort }` |
| `GET /api/admin/partners/invitations/lookup?email=` (new) | — | `{ open_invitation: { id, created_at } \| null, member: { role } \| null }` |

**Today's calls answer as they did.** With no new parameter:
- the invitation list is the newest 200 by first send, with today's fields and today's `status` and `email` filters;
- the deal list is Active, newest first, at most 200.

The three new keys (`total`, `limit`, `offset`) and `sort` are added beside `items`. The one change of meaning is `status=all` on the deal list, which matched nothing (it was bound as a state named "all") and now matches every state.

### 2. The invitation list

- **`q`** searches the name or the email, case-insensitively. `%`, `_` and `\` are literals: the backslash is escaped first, then `likeNeedleLower` escapes the wildcards, under `ESCAPE '\'`. A blank `q` is no search.
- **`stage`** takes one or more of `sent`, `viewed`, `profiled`, `proposed`, `selected`, `finalized`, `signed`, `revoked`, `expired` and `lapsed`, repeated (`?stage=sent&stage=lapsed`) or comma-separated. An unknown word is a 400 naming the valid ones.
  - **Lapsed is computed on each read, by D923's rule:** `expires_at` has passed and the invitation is not Signed, Revoked or a stored `expired`. Nothing writes it.
  - A lapsed row answers to `lapsed`, not to its stored stage, as the page's stage chips do (`STAGE_CHIPS`). Its stored stage is unchanged.
- **`deal_type`** matches an invitation that offered that type among its first three, the types the invitee was shown. A later one reads "Not offered to the invitee" on the page, so it does not match here.
- **`invited_by`** is a user id. **`sent_within`** is days since the first send (`created_at`), 1 to 3650.
- **`sort`:**
  - `newest` (the default): by first send, newest first;
  - `oldest_open`: open rows first (Lapsed is open), oldest first; then the closed, oldest first;
  - `expires_soonest`: open rows first, soonest expiry first; then the closed;
  - `name`: A–Z, ignoring case, then by email; an invitation with no name sorts last;
  - `stage`: Sent through Agreement out, then Signed, then Lapsed, then Revoked and a stored `expired` — the page's `stageRank`.

  Every sort ends on first send, newest first, then id, so pages never overlap.

### 3. The deal list

- **`status`** takes one or more of `proposed`, `awaiting_signature`, `active`, `terminated`, `expired` and `voided`, or `all`. With none, it is `active`, as today. An unknown state is a 400.
- **Before signing, the partner is the invitation's.** A deal with no `user_id` takes `partner_name` and `partner_email` from the invitation it was offered under, joined on `invitation_id`. After signing they are the account's, as today. `q` searches these and the referral code.
- **`ends_within`** is days. Only an active deal with an end date answers; a past end still counts, as the page's "Term ended, not yet closed".
- **`has_redemptions`** is `true` or `false`; `false` is no filter.
- **`sort`:**
  - `newest` (the default);
  - `ends_soonest`: active deals with an end date, soonest first, then the rest, newest first;
  - `most_redemptions`;
  - `partner`: A–Z on the partner's name, or their address when there is none.

### 4. Pages and totals

- **`limit`** is at most 100 when asked for. With no `limit` the cap stays today's 200, so a caller that has not moved to pages loses nothing.
- **`offset`** is any whole number; past the end the page is empty.
- **`total` is exact.** It is a second `COUNT(*)` over the same filters, not the page's length, so it is right on every page, including one past the end.

### 5. The create lookup

PI4's two warnings read it: "Open it instead?" (O-DUP, a warning, never a refusal) and "belongs to a member".

- The match is exact and lower-cased.
- `open_invitation` is the newest invitation to the address that is not Signed, Revoked or a stored `expired`. **A lapsed invitation is open** here, because a resend reopens it (D923 §3).
- `member` is the role of the account with that email, and nothing else about it.
- A malformed address is a 400. The route is admin-only, like every route in the file.

### 6. Static SQL

The two lists are static statements. Every filter is a bound value that is NULL when it was not asked for, and the sort is a bound `CASE`, as in `services/apiUsageReport.ts`. The SQL is built from constant strings only, with no `${}`. A guard test reads the source and fails if any `${}` appears in those strings.

### 7. Not in this part

- The page still filters client-side under Guard L. Part 7 (Invitations, #2726) and part 8 (Deals, #2727) switch it to these reads, together with the paged exports.
- `deals/top` is unchanged.

`frontend/test/admin_partners_client_d926.test.mjs` (new, 3) checks that today's client calls are unchanged and that each new option reaches its parameter.

**Mutation check.** 26 mutations were tried, and all 26 were caught. They covered:
- each filter's predicate;
- Lapsed's rule, both ways;
- the backslash escape;
- the first-three rule;
- each sort's grouping or direction;
- `total` counted from the page;
- both caps;
- `status=all`;
- the pre-signing partner;
- the lookup's lapsed, newest, case and account fields;
- an unknown stage;
- an interpolation in the SQL.

The first lookup mutation, selecting more columns, changed no answer, because the route builds `{ role }` itself. It was replaced by spreading the account row, which is caught.

### Rollback

Revert the PR. The lists return to their unfiltered first 200, and the lookup's route goes. Nothing is stored.
