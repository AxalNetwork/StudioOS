### What was wrong

### What is built

`cloudflare-worker/src/services/platformHealth.ts` reads three signals. Each is its own summary reader, with a deadline, a fallback and a `reads` meta.

**Telemetry (`readTelemetryHealth`)** probes Analytics Engine through the existing `aeSql`, using the new `probeTelemetry` beside it, so the credentials and the "null is a failure" rule stay in one place.
- It reports one of four statuses:
  - `not_configured`: the two secrets are not set;
  - `unavailable`: no answer;
  - `stale`: it answered, but has no HTTP row for 60 minutes;
  - `healthy`.
- It also reports:
  - the write binding;
  - the last event;
  - the request count over 24 hours;
  - its coverage, which is HQ reading the shared dataset; branches never read it.
- A good read is remembered in KV under `health:telemetry:last_ok`, so an outage says when telemetry last worked. A count it cannot parse is null, never zero.

**Cron streaks (`readCronStreaks`)** read the latest five runs per declared trigger, on the `(trigger_name, started_at)` index. They count how many failed in a row, and since when.

**Webhook (`readWebhookHealth`)** reads the latest 25 deliveries. It reports the refusal streak, when the streak began, the last delivery, and the last success and failure ever logged. A delivery with no recorded status is not a refusal.

**Detection.** `detectIncidents` is pure. It works from those signals plus the existing `jobs` and `dlq` blocks:

| Signal | Severity |
|---|---|
| A job's latest run failed | medium |
| A job failed 3 runs in a row, or its expected run never came | high |
| 3 refused webhook deliveries in a row | high |
| 10 refused webhook deliveries in a row | critical |
| No webhook delivery for 72 hours while Stripe is configured | low (a quiet store can be legitimate) |
| Dead letters waiting | medium; high from 100 |
| Telemetry not configured or not answering | high |
| Telemetry stale | medium |

How incidents behave:

- **Keys.** Each incident has a key, one per signal: `cron:<trigger>`, `webhook:failures`, `webhook:silence`, `dlq:backlog`, `telemetry:unavailable` or `telemetry:stale`. Duplicates keep the more severe one.
- **Not stored.** Incidents are derived on every read, so a reload is the same incident, and recovery clears it on the next read.
- **Times.** `since` comes from the signal's own rows. `observed_at` is this read.
- **Remediation.** Every incident carries a console link where one exists, and always a runbook section. The runbook is sent as a repo-relative path; the page adds the repository prefix, as the integration-key guides already do.

**State.** `healthStateOf` uses the order critical > degraded > unknown > healthy.

- Low-severity notes do not degrade the state.
- A signal whose source could not be read is listed under `unknown`. The state is never `healthy` while one is listed.

**Published incidents** ride in `health.published`, labelled manual. They never raise or clear the state.

**The page.** A new first zone, **Health**, shows:

- the state, as a symbol and a word;
- each detected incident, with its severity, since, observed time, console and runbook;
- the signals that could not be judged;
- the telemetry line, with the existing `Unreadable` retry when telemetry is not readable;
- published incidents, apart from the detected ones;
- what is not detected here.

The Monitoring zone's published count now says it is entered by hand, and that detected incidents are under Health.

**Runbook.** `documentation/operations/PLATFORM_OBSERVABILITY.md` §7 has one section per incident kind. A test holds every incident's runbook anchor to a heading that exists there, and every console link to a mounted route.

### Tests

`cloudflare-worker/test/platform_health_4854.test.ts` covers the following, against the real schema:

- missing and not-configured telemetry, which is degraded and never zero;
- a probe that is healthy, stale, empty (the epoch is not an event), down (it remembers the last good read) or returns a 200 with no data;
- a webhook streak that is below the threshold, high, critical, a null status, and recovered;
- webhook silence, with and without Stripe configured;
- cron streaks: medium, high, missed and recovered;
- dead-letter thresholds, and an unreadable backlog being unknown;
- unknown versus degraded;
- deduplication and determinism;
- published incidents apart from the state;
- the runbook anchors and routes;
- the summary end to end.

`frontend/test/platform_health_4854.test.mjs` covers each state's rendering, the incident links, the telemetry and retry lines, unknowns, an unreadable summary, and where the zone is mounted.

Twelve mutants were each killed. One survived the first run (keep-last deduplication); the test now puts the more severe entry first, and kills it.
