## D5353 — An unfinished session is visible and resumable, but never usable (#5353)

- **Status:** Built for #5353, 2026-11-10.
- **Builds on:** D4628 (`setup_complete_at` and resumable setup), D685 (one setup call and stable `client_key`), D872 (recording uploads).
- **Migration:** None. D4628 already backfilled `setup_complete_at` for every historical session.

### Decision

1. A setup response with `{ detail: 'setup_incomplete' }` is not a successful session. Record a session stays open, preserves every entered value, labels its action **Try again**, and resubmits the same `client_key`. It does not start the browser recorder or send a meeting bot. An initial 5xx setup failure has the same retry presentation because its persisted outcome is unknown.
2. The upload path makes the same distinction before reading session state or sending a chunk. A 202 incomplete response sends no audio and no finish request; selecting Try again for the same file derives the same upload key.
3. The Worker is the enforcement boundary. Bot dispatch, recording transitions, chunk upload, and finish all return `409 { detail: 'setup_incomplete' }` while `setup_complete_at` is `NULL`, before capture, storage, consent, or processing work. Retrying either setup endpoint with its original body/key remains the only way to finish setup.
4. Session lists and the session page expose the unfinished state. They offer **Finish setup**, which reopens Record a session with the persisted `client_key`, and **Delete**. Normal recording and bot controls are not rendered for that session.
5. When the one-call new-person path created the interview before setup failed, deleting the unfinished session deliberately leaves that booked interview in Customer research. The session row does not carry a safe fact that proves the interview exists only for it; deleting a person by inference could destroy a separately useful recruiting record. The founder may finish the same setup, delete only the unfinished session and start again on that interview, or delete the interview through its existing explicit action.

### Mutation checks

- Removing the frontend `detail === 'setup_incomplete'` check makes the mounted lightbox test observe `recorder.begin`/`onStarted`, and makes the upload test send bytes.
- Replacing the stable setup/upload key on retry fails the key-equality assertions.
- Moving or removing the Worker guard makes the route test start capture or write R2 data while `setup_complete_at` is `NULL`.
- Treating `undefined` as incomplete in the UI is intentionally avoided: only the Worker's explicit `NULL` state marks an unfinished setup, preserving compatibility with older test seams and non-session DTOs.

### Tests

- `frontend/test/record_lightbox_d685.test.mjs`: mounted 202 response, preserved inputs, Try again, same key, and no capture/start callback before completion.
- `frontend/test/recordingUpload.test.mjs`: 202 response sends no chunks/finish and retry uses the same file key.
- `cloudflare-worker/test/interview_sessions_d657.test.ts`: all four capture surfaces refuse a fault-injected incomplete row, write no audio, and become available after replaying the original setup request.
