## D1150 — Deal context: derived investor progress, visits and firm-private notes (#3055)

S29, 2026-10-25. Part of #2421, based on main at 114d347f. API-only part 2;
D1148's deal-page design on the integration branch supplies DL2 and DL14.
The issue assigns migration 600. No production query or deployment was made.

### Routes and contract

`deal_context.ts` is mounted before `deals.ts` at `/api/deals`. Every route
requires an authenticated investor and an invitation or commitment on this
deal. A verified selected company narrows the relationship. The caller's own
legacy relationship without a company is readable, without attributing it to
a firm. A single company is unambiguous; multiple companies require selection.
A forged explicit company is refused. Admins, including Super Admins, and their support impersonation sessions have no
bypass. The guards are registered only on the four new paths; they do not wrap the
existing sibling router. Responses are private and `Cache-Control: no-store`.

- `GET /:id/stage` returns `my_stage`, one `next_action` (label, working href and kind; respond_interest also
  carries the caller’s invitation_uid), and `ic.state`. Progress is recomputed from accessible facts every
  time: invitation; interested response or membership; owned/reviewed project
  DD case; the firm's scoped IC record; IC terms or a closing envelope;
  pending/confirmed own commitment; completed own closing paper or own signed
  recipient; confirmed receiving-side Mercury match for that commitment.
  A signed NDA is not closing paper. Only SAFE, SPA and subscription envelopes
  count. The receiving founder owns the Mercury match; no bank fields are
  returned. Later facts take precedence, then the studio's rejection, then
  the caller/firm's pass. Missing earlier steps or dates are never backfilled.
  If a withdrawn commitment grants access but no current progress fact exists,
  the stage is null with a reason. IC says Not used when this firm has no
  recorded IC decision, with that reason; there is no firm IC-enable setting.
- `GET /:id/whats-new` returns `since`, `seen_at`, `first_visit`, `changes`
  (type and timestamp only; a missing timestamp is null, never guessed), and an explicit coverage description. The first
  visit establishes a baseline and returns no historical changes. Later
  visits compare accessible source metadata to the previous snapshot. This
  catches new records even when source timestamps are rounded to seconds. Sources include document catalog additions, firm notes,
  anonymous commitments, owned/reviewed DD answers and the latest progress
  facts. This is current stored change metadata, not a reconstructed event
  history; intermediate edits/deletions without history cannot be recovered.
  An authenticated read advances only that user's marker in that company.
  Read-current/upsert-new is a D1 batch with a compare-and-swap on the
  expected snapshot and a monotonic clock; stale reads cannot overwrite a
  newer snapshot or consume its previous changes again. A failed source leaves the marker unchanged.
- `GET /:id/notes?limit=25&offset=0` returns `items` and `total`, max 100 per
  page. Items have uid, author_user_id, company_id, tag, body and timestamps.
  Other firm members may read; only the author in that same scope may edit
  or delete. A caller without a firm has an author-only scope, never a shared
  NULL-company pool.
- `POST /:id/notes`, `PUT /:id/notes/:uid`, `DELETE /:id/notes/:uid` take no
  caller-supplied author/company authority. Add/edit accept a nonblank body
  up to 10,000 characters and a tag up to 80. Writes and actor audit rows are
  atomic batches. The audit records only note reference and company, never
  note text, tag, names or bank data. Audit INSERTs are conditional on the
  preceding write affecting a row; a raced edit/delete returns 404 without
  recording success.

Migration `600_deal_seen_and_notes.sql` adds `deal_seen` and `deal_notes`,
including uid/timestamps, a metadata-only source snapshot and scoped indexes. NULL-company visits have an
expression unique index so repeat visits still have one marker. No historical
visit or note is inferred. `dealContext.js` exposes all six methods for part 4;
its one alphabetical barrel export is in `api.js`. This part adds no screen.

### Reviewed source boundaries

The document source mirrors the existing deal Documents catalog: project rows’
ids and creation dates, without body/title data. The existing catalog exposes
these to an invited/committed investor; it is separate from data-room files.
Deck versions are excluded: `decks.ts` uses the project-content owner guard
and its external viewer needs a live share token. A deal invitation does not
prove that token grant. The response names deck updates in `unavailable` with
this reason; it never queries private deck versions or infers a share.
