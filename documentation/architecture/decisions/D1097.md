### 2. Migration 590: `vercel_health_events`

**The columns:**
- `kind`, held by CHECK: `production_failed`, `rollback`, `domain_misconfigured`, `domain_unverified`, `certificate_failed`, `domain_expiring`;
- `subject`, a deployment id or a domain;
- `opened_at` and `closed_at`;
- `source`: `sync` or `webhook`;
- `vercel_project_id`;
- `dismissed_at` and `dismissed_by`, both set or neither.

**The keys:** `UNIQUE(integration_id, project_id, kind, subject, opened_at)`, as the issue gives it. A partial unique index allows **at most one open row per kind and subject**. `closed_at` is never before `opened_at`.

**Nothing personal:** no log, commit message, creator or person is stored. Nothing is backfilled.

### 3. Open and close on evidence (`health.ts`)

`healthFindings(evidence, now)` reads only what the API returned. It never reads a webhook body; part 1's webhook is a nudge that re-reads.

| Kind | Opens when |
|---|---|
| `production_failed` | the newest production deployment is `ERROR` |
| `rollback` | production points at a deployment older than the newest `READY` one |
| `domain_unverified` | a project domain reads `verified: false` |
| `domain_misconfigured` | a project domain's configuration reads `misconfigured: true` |
| `certificate_failed` | a read names a failed certificate. Part 1's client has no certificate read yet, so this opens only when one is passed. |
| `domain_expiring` | a Vercel-registered domain (Vercel knows its `expiresAt`) that one of this project's domains is, or sits under, expires within 30 days, or within 14 with auto-renew off (§7) |

- **What it returns:** each event, and **which kinds it could check**. A source that was not read checks nothing.
- **`applyHealth`:**
  - opens what is newly true, each with its `connector_fed_items` row `health:<kind>:<subject>:<opened_at>` (module `operating_systems`), in one batch;
  - keeps an event that still holds, and touches its ledger row;
  - closes an open event only among the kinds the evidence checked, so **a partial read never closes what it could not see**.
- **When trouble returns:** evidence that clears and later comes back is a new event, with its own `opened_at`.

### 4. The sync and the webhook open and close events (`providers/vercel.ts`)

**For each chosen project,** after recording its facts, `syncVercel` reads the health evidence:
- one page of deployments, keeping only production ones (a preview that failed is no production failure);
- each of the project's domains' configuration, at most 20;
- the account's registered domains, read once per sync, at most three pages.

It then calls `healthFindings` and `applyHealth`, with `source` set to `sync`, or to `webhook` when `routes/vercel_webhook.ts` re-reads after a delivery.

**When a read fails:**
- **Any read but a 429 or an expired sign-in** leaves its source null, so it checks nothing and closes nothing. The sync still succeeds.
- **A 429** stops the sync "Partly synced", as part 1 does, before that project's health is applied.

**The counts:** the sync's log row counts `deployments` (the production ones read) and `health_events` (those open afterwards, new or still open). They make the sync line.

**Several projects on one venture.** `applyHealth` scoped "what is open" to the venture, so one project's evidence closed another's events. The first multi-project test caught it.
- Now one project's evidence closes only the events that project opened.
- A subject two projects share (an account domain) stays one event.

**Leaving:**
- A project no longer chosen takes its events and their ledger rows with it at the next full sync.
- `clearVercelRows` deletes the connection's events and ledger rows. That covers Removed in Vercel, which keeps the connection's row so nothing cascades, and disconnect.

### 5. The reads (`services/vercel/hosting.ts`)

**`parts.tools.hosting` (VC1)** reads each Vercel connection enabled for the company:
- **its state:** Connected, Failing, Not connected, or Reconnect when the stored error is `vercel_reconnect_required` or `vercel_removed`;
- **its last sync, and its owner** by the Tools rule;
- **`sync_uid`** for the owner alone. The connector sync route takes only the owner's connection, so Sync again is the owner's;
- **each chosen project's facts** from `vercel_projects`:
  - project, domain, framework, runtime ("Node 20.x" from `20.x`), branch, repository and plan;
  - its live state and since when.

  A fact Vercel did not give is null, never a guess;
- **the Hobby line:** "Production runs on a personal Vercel account, Hobby plan." (or "a Vercel team"), linking to `/build/company-creation?project_id=…#from-vercel`, where D1099's proposal is;
- **`reconnect`** for an expired sign-in: the project, when it expired, and the date its figures are from;
- **the health events,** as #3438 built them.

It is Unreadable on its own. With no Vercel connection it reads "Vercel has not brought anything to this venture yet."; with one but no project chosen, "No Vercel project is chosen for this venture yet."

**`syncs`** are the connections' `sync` and `webhook` log rows, newest first, at most 10:
- "Synced: 1 project, 14 deployments, 2 health events", from the row's own counts;
- "Partly synced: …" for a partial run;
- a failure in our words ("Vercel's sign-in expired. Reconnect Vercel.", "Vercel asked Axal VC to slow down.", "The sync did not complete."), never the stored message.

**`parts.vercel_runtime` (VC4a)** is on Solution design. It is its own read, Unreadable on its own while the module stays readable. For each chosen project it gives framework, runtime, hosting ("Vercel"), domain, branch and repository, beside GitHub's `from_code`. It is never merged into `solution_design_stack`.

**The Tools rule:** the owner and the company's members read projects, domains, the plan, the Hobby line, the reconnect's project and each event's subject. Anyone else reads `projects: null` with `projects_total`, and the health counts.

**The connector page** (`vercelFeeds.ts`):
- Production health lands in `vercel_health_events` on Operating systems.
- Runs on reads `vercel_projects` on Solution design.
- Both modules read the connection, so "Now fed by" gives each its own sentence, never a ledger zero.
- The page says the sync now reads deployments, domain configuration and the account's domains.

### 7. Owner question: the expiry window

#2408 and #2962 both say "expiring within 30 days, or 14 with auto-renew off". Read literally:
- a domain that auto-renews is flagged 30 days out;
- one that does not is flagged 14 days out.

That warns later about the domain more likely to lapse. Both figures live only in `EXPIRY_WINDOW_DAYS`. The options are:
- **A.** As written: 30 days with auto-renew on, 14 with it off. **Built.**
- **B.** Reversed: 30 days with auto-renew off, 14 with it on. **Recommended.**
- **C.** One window, 30 days, whatever auto-renew says.
