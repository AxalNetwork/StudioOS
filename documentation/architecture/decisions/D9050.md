## D9050 — Alert when production has not shipped: `release_stale` in the scheduled-operations check (#9050)

- **Status:** built by S13, 2026-11-27 (#9050, under #8797).
- **Migration:** none. **Workflows:** unchanged.
- **Why:** a run of `cloudflare-worker-deploy.yml` whose `build and deploy studioos Worker` job was skipped still ends `success`. In the last 100 completed runs read on 2026-11-27, the job was cancelled in 59, skipped in 39 and failed in 2, and it succeeded in none. Production did not ship from 2026-11-21 to 2026-11-27 (#8932). That was found from the red post-deploy smoke, not from an alert.

### 1. What counts as published

`runPublished` (`scripts/lib/releaseHealth.mjs`) reads one run's jobs (`filter=all`, so every attempt counts). A run published when a `build and deploy studioos Worker` job's `Deploy to Cloudflare Worker` step concluded `success`. A job that lists no steps falls back to the job's own conclusion. A job that failed at `Apply pending D1 migrations` did not publish. A job that failed at a step after the publish did. Jobs that could not be read are `null`, never "not published".

### 2. The rule

`releaseHealth({ runs, jobsByRun, main, now })` is pure. It returns `{ active, ageHours, lastPublishedSha, waitingApproval, reasons }`:

- **`release_stale`.** The newest run that published started more than `RELEASE_MAX_AGE_MS` (24 h) ago, and the `main` tip is not the commit it published.
- **Nothing to ship is healthy.** If the tip is the published commit, the release is healthy however old it is.
- **The tip is compared by SHA, not by commit time.** Every push to `main` starts a run of this workflow, so a tip other than the published commit is newer than it. The merge queue builds a candidate before the run ahead of it starts, so a newer commit can carry an earlier time. The tip's time is read and reported, not compared.
- **No listed run published.** The listing is one page of 30 runs. The last publish is then older than every listed run, so it is stale once the oldest listed run is past the bound. A listing that spans less than the bound cannot say how old the release is, and returns `null`.
- **`approval_pending`.** The deploy job has waited on the production environment for longer than `APPROVAL_GRACE_MS` (1 h). The wait is measured from the waiting job's creation, not the run's, because admission alone can take up to 100 minutes. This reuses the reason already in `OPS_REASONS`, and only `release_stale` is added.
- **Unreadable evidence is `active: null`.** This covers the listing, a needed run's jobs, or the tip when the publish is old. As in `opsScheduleHealth`, the result never reads as a recovery: an open alert stays open and the job fails visibly.

### 3. Wiring

`readReleaseEvidence` takes an injected `gh(path)`, so it is testable and needs no network in tests. It makes three reads:

1. `GET /actions/workflows/cloudflare-worker-deploy.yml/runs?branch=main&per_page=30`.
2. Each run's jobs, newest first, stopping at the first run that published or could not be read (at most 30 calls an hour).
3. `GET /commits/main`.

The `ops-schedules` branch of `scripts/github-alerts.mjs` adds the result as one more entry beside the three watched workflows (`releaseWorkflowResult`). The one existing episode, `[alert] scheduled production operations not running`, therefore carries the reason and the workflow file.

The facts gain `releaseSha` (40 hex) and `releaseAgeHours` (a whole number), which `safeHealthFacts` allows. `safeHealthFacts` now filters `opsReasons` against `OPS_REASONS` itself rather than a copy of the list. `message('ops-schedules')` names the last published commit (12 characters) and its age.

**Permissions.** The `ops-schedules` job (`.github/workflows/github-alerts.yml`) already holds `contents: read` (enough for `/commits/main`), `actions: read` (runs and jobs) and `issues: write`. Its sparse checkout includes `scripts`. Nothing in `.github/workflows/` changes.

- what counts as a publish;
- a recent publish (healthy);
- only skipped and cancelled deploy jobs for more than 24 h with newer `main` commits (`release_stale`);

- a deploy waiting on approval for more than an hour (`approval_pending`);
- an unreadable listing (`null`, the open alert stays open);
- the safe facts and the message;
- that the evidence read stops at the newest publish.
