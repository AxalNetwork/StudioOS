### Policy and persistence boundary

The pure planner proposes at most the explicitly approved stage ceiling (1, 5,
10 or 50), never over 50. Reservations, pending boots, unknown instances and
terminating resources retain capacity and worst-case spending headroom. Creation
requires complete fresh inventory, an approved compatible image, enabled policy,
verified private budget/meter/rate/expiry, per-profile bounds, a burst allowance
and cooldown. Unverified or expired configuration refuses admission. Lowering
the global approval or per-profile maximum immediately drains excess eligibility;
it never kills active work to reach the smaller number.

Persist the entire proposal by compare-and-swap before any effect. Its revision,
reservation, generation and deterministic operation key fence stale/concurrent
effects. Pending effects survive serialization/restart. An uncertain create is
inspected, not blindly assigned a second reservation. The provider must support
and prove idempotent operations before any live adapter uses this journal. The
in-memory CAS function is a testable boundary, not a deployed durable store;
integration belongs to the reviewed asynchronous router stage.

Demand and allocation rounds are bounded by the current six-shard plan and
distributed by run/profile, with explicit per-run and
profile limits. Standard hosted execution retains at least one of the existing
six Worker shards, and initial external admission allows no more than two per
run. There is no paid larger-runner label, shard fan-out change or per-host YAML.
The eventual scheduler still owns concrete shard selection and hosted fallback.

Remove scheduling eligibility before waiting. Preserve owned, unrelated and
unknown active assignments. Confirm unregistration before proposing provider
deletion; a late assignment invalidates a proposed stop and returns to draining.
A finished job drains its one-job machine and retains its runner identity until
that exact registration is confirmed removed. Recovery from uncertainty requires
both provider and old-registration verification, increments the generation fence
and demands fresh boot/image proof before eligibility.

Only verified provider deletion is terminal, and billing holds remain until
the verified meter has settled beyond its configured lag. Lifetime/job deadlines
raise drain conditions; they do not authorize killing arbitrary active jobs.

### Provider, image and supervisor boundaries

The supplied Jelastic provider is deliberately unavailable: every live method
refuses. The account's supported API, operations, idempotency and permissions
have not been verified. No guessed console endpoints or account configuration
are shipped. The inventory collector uses a single request ceiling of at most
100, at most 20 pages/1,000 records, private staged cursors, duplicate detection
and checkpoint persistence. Partial or failed pages never advertise capacity.

The unapproved image template under `infra/runners/` has null unknown version
and digest pins. It cannot pass eligibility. #7889 explicitly requests image
preparation in this new namespace; it is an exception to the parent README's
branch registry convention, not a claim that a resource already exists. No
deployment or branch generator consumes this namespace. Actual image, runner
archive, Node 22 and Python pins, native dependencies, group enrollment and boot
proof must be reviewed against the completed #7885 profile before approval.

The supervisor is a pure next-action/environment policy, not a launched daemon.
It requests short-lived enrollment for one-job ephemeral registration; broad
GitHub/provider/issuer credentials are excluded from job environment inheritance.
It stops re-enrollment while draining, waits for safe assignment state, then
unregisters before teardown. Verified issuer/process callbacks, filesystem and
network credential isolation, and real lifecycle execution remain upstream work.
Environment filtering alone is not a security sandbox.

### Measurements and rollout still required

Routine proposal status separates healthy, busy, draining, offline, booting and
unregistered counts; inventory failure produces null capacity. It includes pending
demand, oldest wait, missed deadlines, bounded retries and approval state. Scale
events count reserved proposals, not measured running machines. No account IDs,
addresses, credentials or private monetary balances are returned in public status.

The reserve estimate in private meter units is:

`ceil((maximum machine lifetime + max finishing job + safe termination + billing lag) / one minute) × verified per-node-minute rate`.

Machine lifetime includes boot and idle time. Before live admission, the owned-job
hard deadline and termination bounds must be independently enforceable; a model
deadline alone cannot guarantee a cloud spending limit during an outage.

Actual provider rates, App budget, controller request/storage charges, boot and
job duration, availability, metered cost and throughput are **Not recorded**:
there is no approved live adapter or completed small-pool exercise. This formula
is a conservative admission input, not a claim about actual provider charges.
Fixed provider/control-plane costs require a separate private envelope as well.

### Independent review corrections (S37)

An independent Claude static review of public head `7a01b5ec0a` identified
receipt, recovery, inventory and supervisor contract gaps (F1–F15). S37 verified
the findings against the code and added regression coverage; no live operation,
runtime consumer, approved image or deployment is introduced by these fixes.

- Eligibility removal requires an explicit positive receipt. Terminal deletion
  matches the exact provider identity; verified absence also matches the recorded
  registration identity. Absence is a separate proof from an unavailable read,
  retains the billing hold, and only releases the slot after meter settlement.
- Unknown create outcomes are inspected by reservation rather than blindly
  deleted. Inspection distinguishes present, absent and unavailable results.
  Recovery starts a new `bootStartedAt` window while retaining `createdAt` for
  the absolute lifetime and reserve calculation. Future durable integrations
  must persist both fields; this inactive preparation has no deployed state.
- Job-start evidence cannot claim an idle assignment or authorize teardown.
  Registered, online, identity-matched heartbeats refresh liveness without
  resetting idle age, job age or lifetime. Successful lifecycle progress resets
  the retry episode; an uncertain observation, heartbeat or CAS commit alone
  does not replenish an exhausted retry budget.
- Inventory validates record shapes and identity uniqueness, and duplicate or
  mismatched reservation tags require reconciliation. Resume requires the full
  checkpoint snapshot, not only a cursor or records: `cursor`, `instances`,
  `complete`, `requestsUsed`, `pages` and `seen`. Attempts are persisted before
  provider reads; the 100-request/20-page/1,000-record bounds and cursor-cycle
  checks survive restarts and failed reads.
- Supervisor state must persist `jobsCompleted`; a completed one-job machine
  drains instead of enrolling again. Registration and eligibility observations
  must be explicit booleans before they can authorize cleanup. Environment
  filtering remains only one boundary, not proof of a sandbox.
