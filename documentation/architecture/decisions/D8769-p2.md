Not built. Landed at the owner's request before the questions below were answered.

### Built (2026-11-27, slot S10)

Built against `main` at `d26a93a25`, to option A of each owner question as the canvas draws it, except where noted.

- **Roster (TMM01, TMM07, TMM11).** `AgentsCard.jsx` columns are Agent, What it does (area of work and model), Can it run now, Sponsor, This month (with last activity under it). The name is a button named "{name}, AI agent, {work}: open profile"; ⋯ is "More actions for {name}" and opens `ActionMenu` (role `menu`): Open {name}'s profile, plus a paused row's one fix for a manager only. No control is named by the persona's motto. "Can it run now" is one pill from `agentChoiceModel.agentReadiness`: Paused (with its reason and fix, "· also no skills" when both apply), then No skills yet ("Can't run until a skill is added"), then Not recorded when the count was not read, then Active with "N skills". Q1 = A.
- **Engine.** The team's engine (`agentEngineApi.engine`, read by `TeamAgentsPage`) is one status line above the table (`engineNote`), never a row's pill. This departs from TMM07 C's priority 1 on purpose: the engine runs goals and plans (D1531), while a person's own run (`POST /agents/:uid/run`) does not check it, and `AGENT_ENGINE` is `"off"` in production, so an engine-first pill would have read "Off for this team" on every row while the agents still run. See ⚑ Q5.
- **Profile (TMM02).** `AgentProfile` runs readiness, "What {name} does" (area of work, `reads_line`, model), Skills (`AgentSkillsCard`), "Sponsor and cap", Permissions, Proposals, Activity, then "About {name}: story and values" (a `details` holding D4119's full card, Story and goal, Values and risk). The sheet's accessible name adds ", AI agent, {work}" instead of the motto.
- **Who (TMM03).** Search is "Search by name or work" (`gallery` also reads `personaWork`: the persona's own area and its natural fit); "Good for" is the first filter; each card leads with "Good for {work}" before the values. The "0 skills · cost per run Not recorded" line is gone: no per-persona skill count was read.
- **Model and cap (TMM05, TMM06, TMM08, TMM10E).** New `ModelChoice.jsx`. `GET /api/teams/roles` models now carry `jobs` (the agent kinds of `USE_KINDS` each is listed for, `modelOffers.AGENT_JOBS` order), `capabilities` and `context_window` from the catalogue. The step groups them: "Suited to {job}" first (`ROLE_JOB`, below), then "Other models this team allows" by the first job each is listed for. A plan-locked model reads "Not on your plan" and one outside the team's allowlist (`readAllowlists`, D4422) "Not allowed on this team", both disabled; an allowlist that could not be read marks nothing and says so; none allowed says so. Each model that can be chosen in a group on screen is estimated once with D4121's `GET /:scope/:id/cost-estimate` (model, area, persona, skills); its dearest run × 100 is "≈ $0.20 per 100 runs" (Q3 = A; "< $0.01 per 100 runs" below half a cent); `{ available: false }` or a failed read is "Estimate unavailable" with "Try the estimate for {model} again", which re-reads that model only. The cap's line is "A $25 cap pays for about N runs" (cap ÷ the dearest run, as `estimate` works out `monthly_at_cap`). "How the estimate is worked out" prints the Worker's new `basis` (`request_tokens`, `output_tokens`, `priced_at`, from `RUN_COST_CONFIG`). Token prices are behind "Show token prices" (`aria-expanded`). Sponsor and cap now follow the model; below `md` a bar at the foot of the step keeps the chosen model, its estimate and the cap, with a button to the cap field. A model the allowlist refuses cannot be added even if chosen before the allowlist was read.
- **Coverage (TMM09).** `coverageSentence`: eight empty rows read "No category is mapped yet." with the reason; "Every category with an agent on it also has a person on it." only when agents are mapped and none is a people gap; people with no agent read "No agent covers a category yet."; gaps keep today's sentence. While it reads, the card says "Reading team coverage…" over skeleton rows.
- **Worker.** `agentDto` carries `skill_count` (null, never 0, when unreadable; null for an outside assistant). `costAnswer` carries `basis`. No migration, no new route, no mount.

**Judgement call: `ROLE_JOB`** (`agentChoiceModel.js`) maps an area of work to the `USE_KINDS` job whose models suit it: research_analyst → research, cfo → numbers, general_counsel → legal, cto → code, ceo/coo/cpo → plan, cmo/sales/people/investor_relations → write. Only research, numbers and legal are named jobs in `USE_KINDS`; the rest are the nearest kind. A role whose job lists no offered model has no suited group, and every model is shown under its own job.

**Left out.**

- Q2's skills gate (Next off until a skill is chosen): it is the wizard's `SkillsStep` ready rule, which D8768 (#8768) is rebuilding with "Next: model and cap, with no skills" (TMS08); building either answer here would collide with it before the owner settles Q2.
- Per-skill readiness in the roster and "Runs with limits", the readiness summary on the agents list, readiness for an agent not yet added and for company skills: the backend item stays open (◇ above). The roster says "N skills", not "Ready".
- Skill counts on the Who cards ("how many published skills fit it"): that is the library read with eligibility, D8768's.
- Q4's last accepted output on the profile: no route serves an agent's last accepted output with its skill.
- Filtering `/roles` by the team on the Worker: the step reads the allowlist itself and shows the refused models disabled, as TMM05 draws one.
