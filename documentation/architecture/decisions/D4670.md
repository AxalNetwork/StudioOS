## D4670 — Expertise › Proof: the person named confirms, and only an Advisor keeps a profile (#4670)

- **Status:** Built for #4670, 2026-11-06. It covers the Worker, the Proof zone and the attester's page.
- **Builds on:**
  - migration 204 (proof items and consents; attested is derived, never stored);
  - D4472 (`account_licences`, an additional licence) and #4473 (the held-licence sidebar, which this does not touch).
- **Migration:** `202611062216_advisor_proof_attestation.sql`. It is additive: two columns on `advisor_proof_consents`, and two new tables. `services/advisorStoresSchema.ts` heals a database baselined past it.
- **Owner's calls on #4670:**
  - (1) the attester proves they read the named address with an emailed code;
  - (2) confirmations recorded before this decision need reconfirming.

### What was decided

1. **The link is an invitation, not a credential.** The advisor still hands the person a link (`/attest/:token`). Every read of the advisor's list now carries the link (`invite_token`) while the ask is pending, so a refresh no longer loses it. Holding the link lets someone read the claim; it does not let them answer.
2. **A code answers.**
   - Every answer needs a six-digit code: confirm, decline, withdraw or reconfirm.
   - Axal emails the code to the address the advisor named, only when the attester presses "Email me a code" on the page. The page shows that address masked (`s***@example.com`).
   - Only a SHA-256 of each code is kept, bound to its request. A code:
     - lasts 15 minutes;
     - allows five wrong tries;
     - is used once.
   - A request may send five codes an hour.
3. **The requester is never the respondent.**
   - The address is required, and it cannot be the advisor's account or profile address (422 `attester_is_requester`).
   - A signed-in caller who is the advisor is refused even with a code (403 `requester_cannot_attest`).
   - The only mail is the attester's code. Recording an ask still sends nothing.
4. **The claim is pinned.**
   - A request records the claim as it read (kind, title, organization, period, detail) and its SHA-256. The attester is shown that text.
   - An answer about another reading of the claim is refused (409 `claim_changed`).
   - A confirmation counts only while the claim still reads that way. An edit makes it "needs reconfirmation".
5. **Before D4670 is not verified.** A confirmation recorded through the old flow has no pinned claim, and the advisor held its link. It is kept and shown as "needs reconfirmation", and no longer counts as confirmed. The advisor asks again.
6. **Every answer is history.**
   - `advisor_proof_consent_events` is append-only (two triggers). It records `asked`, `confirmed`, `declined`, `withdrawn` and `reconfirmed`, with the claim's hash and the time.
   - The attester's page shows that history.
   - A withdrawal can be reversed only by the attester with a fresh code, and the reversal is recorded as `reconfirmed`.
7. **Only an Advisor keeps a profile.**
   - Who may call `POST /api/advisors/me`, which creates or changes a profile:
     - an Advisor, by primary or additional licence (D4472);
     - an admin;
     - nobody else, who gets 403 `advisor_licence_required`.
   - `GET /api/advisors/me` answers the same refusal to a caller with no Advisor licence, so "you may not" never reads as "no profile yet" (`null`).
   - Before, a founder's POST created an active profile.
   - The frontend's held-licence access (the sidebar union) is #4473's, and is not duplicated here.
8. **Fixed sentences.** The Proof zone, the Profile zone and the attester's page print a fixed sentence keyed on the refusal code (`ASK_REFUSALS` in the Expertise kit, `ATTEST_REFUSALS` on the page), never the raw error text.

### Not in this decision

- The Operating Partner's Offers › Proof (`/attest/partner/:token`). It is outside #4670's scope.
- An advisor can still name an address they control other than their own account's. The code proves the attester reads the named inbox, not who owns it; the page shows the masked address so the attester can tell.
