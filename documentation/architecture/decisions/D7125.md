## D7125 — The merge-queue stall alert opens on one failure shared by two queue chains, and names where it starts (#7125)

- **Status:** built 2026-11-19 for #7125 (part of #5600; follow-up to the
  2026-11-17 audit on #7108). **Amends D5604.** Hosted proof is still open:
  it needs a real failed `merge_group` run after merge (see "Not yet proven").
- **Code:** `scripts/test-drift-parts.mjs` (the annotation),
  `scripts/lib/githubAlerts.mjs` (`queueStallState`, `queueChains`,
  `stallIdentities`, `stallEvidence`, the alert text),
  `scripts/github-alerts.mjs` mode `queue-stalled` (the reads),
  `scripts/health-alert-episodes.mjs` (`safeHealthFacts` keeps the
  identities), `.github/workflows/github-alerts.yml` (`checks: read`,
  `pull-requests: read` on the `queue-stalled` job).
- **Tests:** `frontend/test/queue_stall_chains_7125.test.mjs`, with
  `frontend/test/fixtures/queue_stall_7125.json`. D5604's own tests
  (`ci_infra_breaker_5604`, `landing_gate_classifier_5606`) are unchanged.

### Why

On 2026-11-17, 294 `merge_group` runs failed between 09:00Z and 14:30Z and no
`[alert] merge queue stalled` opened. D5604 opens only when the two newest
failed runs share a setup-step fingerprint; a failed test gave `active: null`.
Shard names are no signature (four assertions spread over nine shard names in
one rebuild). The identity existed only in a 44,000-line job log.

### What D5604 now says

D5604's rule stays as it was: two different heads failing at the same setup
step open the alert, and only a green queue run clears it. A second rule is
added beside it.

1. **The identity leaves the runner.** Under `merge_group` only,
   `test-drift-parts.mjs` prints `::error title=ci-failure-id::<file> › <test>`
   for each failed test of a node:test command the flaky retry (D6464) did not
   rescue, at most 5, and `guard › <command, 120 characters>` for any other
   failed command. `%`, CR and LF are escaped (and `:` `,` in the title). The
   exit status is unchanged. The loop moved into an exported `runPart` so the
   tests drive it with a fake shell.
2. **The check reads it.** Mode `queue-stalled` lists the newest 100
   `merge_group` runs of every status (it listed 30 completed ones), reads the
   jobs of the completed failed runs created after the newest green one, at
   most 15, and for each failed job outside the two summaries reads
   `GET /check-runs/{job}/annotations`, keeping those titled `ci-failure-id`.
   Every status is listed because a chain links through candidates that are
   still running or green; only failed runs are read.
3. **Identities.** A job's annotations, else `<job without its N-of-M shard> ›
   <failed step>`. A setup step gives none (D5604's rule covers it), nor does
   `Check merge queue ref still exists`: that step fails when GitHub has
   already ejected the candidate, and on 2026-11-17 it failed in candidates of
   both 09:21Z chains, so it would have opened the alert falsely. A job whose
   annotations cannot be read makes its run unknown: it counts for nothing.
4. **Chains.** A run's branch is `gh-readonly-queue/main/pr-<N>-<parent>`;
   the parent is the head of the candidate ahead, or main for the root. A
   chain is one connected set; two are different when their roots differ in
   PR or base sha.
5. **The rule.** Active when one identity is in failed runs of at least two
   chains and on at least three heads, all created after the newest green
   queue run. One chain alone, however long, is `null`: its candidates are
   cumulative, so one bad PR fails every candidate behind it until GitHub
   ejects it.
6. **Where it starts.**
   - On the root of two chains whose root PRs differ: it fails on the base.
   - #N is the earliest candidate failing it in one chain, sits at or ahead of
     the earliest failing candidate of every other chain, and a candidate
     ahead of #N completed without it: it starts at #N. The issue's wording
     was "the earliest failing candidate is the same #N in both chains"; it is
     read this way because the queue stops a candidate at its first failed job
     (D5601), so a candidate can fail first on a different identity and never
     reach this one. On 2026-11-17 #6531 failed first on the promo-clock test
     in the 09:21Z chain, and the route-table test showed one candidate later.
   - Otherwise the PRs are listed and the start is "not determined".
   At open only, open PRs that change the failing test file and pass every
   required check of main are listed as possible repairs (best effort, at most
   30 PRs read; a failed read lists none).
7. **The alert.** The issue body and the Slack text carry, per identity (at
   most 5), the failure, how many candidates and chains failed it, where it
   starts, and one job link. Test names come from code a PR can change, so
   `safeStallIdentities` drops backticks, angle brackets, `&`, backslashes,
   control characters and `@`.
8. **The rule for people.** AGENTS.md § "Red main and a backed-up queue" and
   the `land-pr` skill: while the alert is open, add no queue entries and do
   not re-queue an ejected PR; the one repair linked on the alert is the
   exception, and the owner moves it to the front.

### Verified

The fixture holds the 31 `ci.yml` runs created 2026-11-17 09:21Z to 09:22Z
and the 30 created 12:21Z to 12:22Z, read through the REST API: each failed
job, and each failed suite job's identity taken from its log
(`No retry: not on the flaky list: <file> › <test>`, or the guard command
that exited). There were three chain roots: pr-6898 on `d172408` (one
candidate, ejected), pr-7055 on `5d14c9b`, and pr-6778 on `5d14c9b`. The
replay opens the alert with the promo-clock test failing on the base, main at
`5d14c9b`, the route-table test starting at #6531, the formation-gates fixture
starting at #6964, and `npm run test:guards` not determined (it failed on
#6773 in one chain and #6538 in the other, as one identity). Either window
alone stays `null`. The CLI is replayed against the same runs with the
annotation endpoint answering from the fixture.

### Not yet proven

- Hosted: on one real failed `merge_group` run after merge,
  `gh api repos/AxalNetwork/StudioOS/check-runs/<job id>/annotations` shows
  the annotation, and a `workflow_dispatch` of `github-alerts.yml` with
  `check: queue-stalled` logs the identities and chains it read.
- The metric: minutes from the first failing run of the second chain to the
  alert's `created_at` (target at most 30), and how many opens in 7 days
  closed within one rebuild with no repair merged (target 0).
- Runs from before the merge carry no annotation, so for the first hours their
  suite jobs fall back to `suite › Run node scripts/test-drift-parts.mjs
  <part> …`, which matches only the same part failing in two chains.

### Not built

Removing, re-queueing or reordering PRs (owner action; #6476), opening the
repair (#6477), the `ci-failures-*` artifact (#5502), queue settings or
runner capacity, and `classify`/`digest` on `merge_group`.
