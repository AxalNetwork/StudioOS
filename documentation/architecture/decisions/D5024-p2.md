## D5024 part 2 — Immutable commercial offers and atomic package acceptance (#5024)

This completes the Worker offer/acceptance foundation on top of the catalogue
(#5022), immutable country-adjusted recommendation (#5023), existing Program
Grants (#5018) and legal-policy freeze (#5052). The catalogue-name work in
`D5024.md` remains unchanged. Package operator screens and franchisee reads
belong to #5026; renewal, upgrades, downgrades and proration belong to #5025.

### Offer record and decisions

`licence_package_offers` freezes the exact published catalogue identity,
composition, operational terms, country pricing snapshot and recommendation.
Only an active catalogue version can create a new offer. A package term has
explicit real UTC calendar dates and cannot start before that version takes
effect. A draft can be offered or superseded; an offered draft can be accepted,
declined, expired or superseded. Editing a commercial proposal means creating
a new offer, never rewriting the original. Accepted commercial records have
no mutation endpoint. History has a monotonic ID so simultaneous timestamps
cannot reorder decisions.

The recommended and accepted package prices are integer native-currency minor
units. A different accepted price needs its own 10–500 character override
reason. No FX conversion, invoice change or automatic proration occurs.
The package price does not overwrite the territory licence's annual fee.
There is no per-program allocation model: new bundled grants have a NULL fee
and item allocation, not an invented zero. A retained grant keeps its recorded
economics; the accepted item freezes those terms and its grant revision.

### Review, atomicity and existing grants

Super Admin reads the offered package's consequences before accepting. The
review hash binds the frozen offer, accepted price, current grant revisions
and terms, licence revision, current legal policies/holdings and agreements.
Every write uses the existing recent-authentication write bar and a reason.
Creation and acceptance have actor-scoped idempotency keys; exact retries
return the recorded result, including a simultaneous retry after another
request won. Changed requests cannot reuse a key.

Acceptance uses `runDecision` and its transaction guard. One D1 batch commits
the revision-guarded accepted offer, immutable included items, normal grant
writes or unchanged grant links, grant history, package policy freeze,
replacement-required events, a package decision event and the normal durable
licence-push intent. Guards also check the licence, latest policy versions,
existing holdings, executed agreements, existing grant states/revisions and
current new-grant enablement. A competing accepted term cannot overlap. A
failed guard, duplicate grant or late item failure rolls the whole batch back.

An existing granted program is retained only if it records coverage for the
package term and its operational/economic terms are compatible. Different
dates, state, terms or currency are surfaced for explicit resolution through
Program Grants; acceptance does not regrant, resume, reprice or silently
rewrite it. Programs outside the package remain standalone and unchanged.
The existing single-program route and package orchestration share the grant
insertion service. Default enablement, registry readiness and schedule rules
remain enforced.

A new future-dated package can create future-dated grants. It cannot change
the legal policy of an already current included program early: that case is
an explicit conflict for the scheduled lifecycle workflow in #5025. Accepted
terms are not silently superseded to make an overlapping acceptance fit.
A held package policy also cannot be replaced early by a future term, or
removed from a still-granted program outside the incoming package. Those
moves require explicit standalone legal terms through #5025 first.

### Legal policy and contract provenance

Acceptance freezes the current package strategy and legal gate using
`freezeHoldingStatements` in the same batch, with the real offer UID and
package version. Its immutable legal event also identifies the holding. New
program policy holdings are frozen where needed; existing program holdings
retain their own frozen versions. A later policy publication does not reach
the licence. The package policy must name exactly the offered programs, so
it cannot silently change the legal gate of standalone extras.

`required_before_grant` requires executed documents before the batch can
grant. `required_before_in_force` keeps the grant out of force until its
documents are executed. A real package master/addendum must match the
accepted offer UID and package version; an executed document for an older
offer cannot satisfy the new gate. Legacy holdings preserve their existing
read behavior. `syncLegalGate` runs after acceptance, followed by the normal
licence copy, which carries Program Grants and their existing legal/schedule
gates. Failed delivery stays explicitly failed with the durable normal retry;
there is no second branch entitlement model.

The old legal-only `package-acceptances` endpoint now refuses with
`package_offer_required`. It cannot freeze a legal acceptance without the
commercial offer and grants. Earlier D5052 regression scenarios seed legacy
holdings through the same core freeze statements; real acceptance, access,
atomicity and retirement are covered by `package_offers_5024.test.ts`.

New agreement drafts use the explicitly named offer, or the accepted current
term, for the package name/version. The accepted offer supplies
`package.offer_uid`, `package.annual_fee`, `package.accepted_annual_fee_cents`,
`package.recommended_annual_fee_cents`, `package.currency`, `package.starts_on`,
`package.ends_on`, `package.programs`, `package.pricing_snapshot_uid` and
`package.pricing_model_version`. A recorded zero stays zero; absent commercial
terms remain unresolved. Explicitly offered, not yet accepted, records may
bind a draft's identity, but supply no invented accepted price. Existing
issued bodies, merge values and hashes never change with the catalogue or
country data.

### API

At `/api/admin/licences/:uid/package-offers`:

- GET lists the licence's offers; POST creates an immutable draft with
  `package_key`, optional `package_version`, `starts_on`, `ends_on`, optional
  `expires_on`, optional `country_pricing_snapshot_uid`/`snapshot_reason`,
  optional operational `program_terms`, `reason` and `idempotency_key`.
- GET `/:offer` returns the frozen offer and actual accepted item rows;
  GET `/:offer/history` returns its attributable decisions.
- POST `/:offer/review` reads consequences, conflicts and `review_hash`, with
  optional `accepted_annual_fee_cents`/`override_reason`; it writes nothing.
- POST `/:offer/offer`, `/decline`, `/expire` and `/supersede` require the
  `expected_revision` and `reason`.
- POST `/:offer/accept` requires `expected_revision`, `review_hash`, `reason`
  and `idempotency_key`, with the same reviewed price/override inputs.

### Catalogue compatibility decision

The seeded Core Network v1 includes HQ-only Influencers; other seeded bundles
also include unready programs. The safe implementation refuses an
incompatible bundle as a whole. It never bypasses Program Grants to make a
commercial catalogue appear fulfilled. A test-only published, grantable v2
exercises successful acceptance; production catalogue rows are unchanged.
The owner has been asked whether to retain this block pending an appropriate
catalogue version, or explicitly model HQ-run commercial items without branch
grants. That decision remains separate from silently granting HQ-only access.

Validation commands, real SQLite race/rollback regressions, mutation evidence
and the independent review requirement are recorded in the PR. No production
data, package publication, branch configuration or deployment is performed.
