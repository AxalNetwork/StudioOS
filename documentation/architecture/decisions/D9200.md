## D9200 — Terms accepted before obligations are seeded count (#9200)

**Decision.** `seedObligations` (`cloudflare-worker/src/services/trust.ts`)
reads the person's own `legal_acceptances` rows for the current
`LEGAL_DOCUMENT_VERSIONS` version of `tos_v1` and `privacy_v1`. A new
obligation row for a key with such a row is created `satisfied`, with the same
`evidence_meta` shape `recordTermsAcceptance` writes (`source`, `surface`,
`accepted_at` of the first current-version acceptance). An existing `pending`
or `in_review` row moves to `satisfied` on the same evidence, the guard
`recordTermsAcceptance` already uses, so accounts the bug already left pending
are healed on their next seed.

**Why.** An account created without seeding (admin- or script-created, older
paths) could accept through `POST /api/auth/accept-terms` with no obligation
rows. The acceptance was recorded, `satisfied` was 0, the next seed (for
example `GET /api/trust/me`) created both rows `pending`, and `/api/auth/me`
reported `terms_acceptance_pending` again. The fix sits in the seeder rather
than in the accept route, so every seeding path counts the acceptance and
`routes/auth.ts` is unchanged.

**Limits.**

- Only the person's own rows are read (`WHERE user_id = ?`). Nothing is
  written to `legal_acceptances`: no acceptance is made on anyone's behalf,
  there is no admin variant and no backfill (the rule above `/accept-terms`).
- An acceptance of an older version, or one with no recorded version (before
  migration 583), does not count; the row is seeded `pending` and the person
  is asked.
- A `satisfied` row is never downgraded and its evidence is not rewritten. A
  `waived` or `expired` row is re-armed to `pending` as before; a later seed
  then applies the rule above.
- An unreadable `legal_acceptances` (before migration 245) reads as "nothing
  accepted", which is the old behaviour.
- No schema change.

**Tests.** `cloudflare-worker/test/terms_before_seed_9200.test.ts` runs the
real `/api/auth/accept-terms`, `/api/trust/me` and `/api/auth/me` routes over
SQLite: the accept-then-seed sequence, the old-version case, healing a stuck
row, scope to the caller, and no downgrade. All three cases fail on main.
`obligation_satisfiable.test.ts` counts the new satisfied-write site (6).
Mutation check: 9 mutations, 9 caught, 0 equivalent.
