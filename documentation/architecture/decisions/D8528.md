## D8528 — Company invitations and ownership under concurrency: race tests and guarded writes (#8528)

- **Status:** built by S19, 2026-11-25 (#8528, row E4 of #8509).
- **Migration:** none. The fixes use the existing decision guard (`services/decisionBatch.ts`, D4805; migration 202611071200).
- **Why:** each invitation and lifecycle operation was tested on its own, and none ran two at once. Production has no invitation records yet, so the first real ones would have been the first test.

### 1. The barrier

`cloudflare-worker/test/_d1_barrier.ts` wraps a test D1 binding:

- It holds each tagged request at its first write (an INSERT, UPDATE, DELETE or REPLACE, or a batch) until every tagged request has finished its reads.
- It then lets those first writes through one at a time, in a chosen order.
- A request that ends without writing counts as arrived.

S03's move-and-rename task (row E1) can reuse it.

### 2. The rule each case is held to

Each case runs its two requests twice in each order:

- **Serial:** one after the other, on a fresh fixture.
- **Raced:** under the barrier, on another fresh fixture.

The raced run must end exactly as the serial run in the same order. That means the same answers, seats, primary admins, invitation states (status, who accepted, whether the token is the original), venture owners, venture seats and membership events. So no interleaving produces a state that running the requests in turn could not. Each case also states the issue's outcome in plain assertions.

### 3. What the barrier found, and the fixes

Before this change, six of the ten orders ended in a state no serial order gives:

| Case | Order | What happened before | Fix |
|---|---|---|---|
| Accept against revoke | revoke, then accept | The accept, having read "pending", wrote a seat **from a revoked invitation** and overwrote `revoked` with `accepted` | The accept claims the invitation first: `UPDATE … WHERE id = ? AND status = 'pending' AND token_hash = ?`, then `decisionGuard`, then the seat and its `join` event, in one batch (`runDecision`). A lost claim writes nothing. It answers 410 with the current status, or 404 when the token was replaced. |
| Accept against resend | resend, then accept with the old token | The old token, read before the resend, still seated the member | The same claim. It is guarded on the token it was opened with, so the old token stops working. |
| Accept against resend | accept, then resend | The resend gave an accepted invitation a new token, and would have mailed it | The resend's update is guarded `AND status = 'pending'`. It answers 409 with the current status when it changed nothing. |
| Two accepts (two tabs) | either | The second tab failed on the unique seat (400 `already_exists`) instead of reading as answered | The same claim. The second tab gets 410 `accepted`: one seat, one `join` event. |
| Primary-admin transfer against removing the new owner | remove, then transfer | The grant matched no row, but the demote and the `transfer` event still ran. **The company was left with no primary admin.** | The grant is the decision: `UPDATE … WHERE id = ? AND company_id = ? AND user_id = ?`, then `decisionGuard`. A lost grant writes nothing and answers 404. |
| Venture owner transfer against the recipient leaving the company | remove, then transfer | The venture went to an owner who no longer belongs to its company. That breaks D1137's rule that a venture only sits in a company its owner belongs to. | The owner change is the decision: guarded on the owner and company it read, and on the recipient still belonging to that company. A lost change answers 409 `owner_not_in_company`, or `venture_changed` when something else moved. |

The other four orders already ended as their serial order does:

- accept, then revoke;
- transfer, then remove (the remove refuses the only primary admin);
- venture transfer, then remove;
- and the barrier's own test.

The account page's accept by invitation id (`routes/account_companies.ts`, `POST /company/invitations/:uid/accept`) already wrote its seat only while the invitation was pending, in one batch. It is not changed here. It writes no `join` event, which is a separate gap and is not in this issue's scope.

`company_invitations.test.ts` builds its own schema. It now creates the `decision_guard` table production has, because accepting is a guarded decision.

### 4. Proof

`cloudflare-worker/test/company_races_8528.test.ts` has 10 tests:

- the four cases, each in both orders (the issue's five cases, with the two accepts in one test);
- the barrier's own test.

Mutation check: 8 mutations, all caught.

- On the accept: dropping its pending guard, dropping its token guard, or taking away its decision guard.
- On the resend: dropping its pending guard.
- On the primary-admin transfer: taking away the grant's decision guard.
- On the venture transfer: dropping its company check.
- On the barrier: not holding at all, or releasing in arrival order.
