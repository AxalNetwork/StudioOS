### 1. How each is turned on, and by whom

| What | Variable | On-value | Anything else, or unset |
|---|---|---|---|
| The Super-Admin routes | `WORK_GRAPH_RELEASE_ADMIN` | `on` | every route answers 404 `release_admin_off`, before it reads the session or anything in D1 |
| The drain, scheduled and manual | `WORK_GRAPH_RELEASE_DELIVERY` (part 3) | `preview` | the scheduled hook returns before any D1 read; the manual drain answers 409 `release_delivery_off` |

Neither variable is in `wrangler.toml`, so both are off on every deployment. **The owner turns them on**: set the
variable on a branch environment first, then in `[env.production.vars]` (or as a dashboard variable). No agent sets
either. Turning `WORK_GRAPH_RELEASE_DELIVERY` off stops delivery at the next tick; queued effects wait, pending.

The two are separate on purpose: the routes can be opened to read releases and their outbox while nothing is
delivered.

### 2. The routes

Mounted at `/api/admin/work-graph/releases`. Every route names the scope it acts in, `tenant_id` and `company_id`
(query on reads, body on writes), and the services refuse a line or manifest of another scope `wrong_tenant`.

| Route | Gate | What it does |
|---|---|---|
| `GET /lines` | `requireSuperAdmin` | the scope's lines, each with the manifest its pointer names and how many manifests it has |
| `GET /lines/:line` | `requireSuperAdmin` | `publishedRelease` (evaluated), `servedRelease` (or what is withheld and why), the line's manifests |
| `GET /manifests/:manifest` | `requireSuperAdmin` | `releaseStatus`: every pinned piece, its status and reasons, missing attestations and approvals, takedowns |
| `GET /deliveries` | `requireSuperAdmin` | the release effects of the scope (optionally by `state` or `manifest`), with part 2's delivery row once applied |
| `POST /manifests/:manifest/publish` | write bar | `publishRelease`, with the digest the Super Admin reviewed and the manifest they expect the pointer to name |
| `POST /manifests/:manifest/takedown` | write bar | `takedownRelease`, with the reviewed digest, a reason code, evidence and the authority claimed |
| `POST /lines/:line/repin` | write bar | `repinRelease`, from the head the Super Admin saw |
| `POST /drain` | write bar | one `drainReleaseEffects` of at most 25 effects (`limit` may ask for fewer) |

- **Gates.** Reads take `requireSuperAdmin` (HQ only). Writes and the drain take `requireSuperAdminWriteBar`: a TOTP
  session, a step-up, then the elevation. A drain delivers to outside providers, so it is a write.
- **Stale writes.** A publish whose digest is not the manifest's is `stale_approval`, before the service runs. Its
  `expected_manifest_uid` goes to the CAS, which refuses a moved pointer as `stale_revision`. A re-pin whose
  `expected_manifest_uid` is not the head is `stale_revision`, with `current_head`. A takedown's digest is checked by
  the service (`stale_approval`) and the refusal is recorded in the takedown table.
- **Audit.** Every write that passes the gate is an admin audit row (`logAdminAction`: `activity_logs` and
  `admin_audit_log`) with its outcome, refused or not: `work_graph_release_publish`, `_takedown`, `_repin`, `_drain`.
  The services keep their own rows beside it: `advance_head` and `advance_refused` events, the takedown table (a
  cross-tenant takedown is recorded against the line's own tenant), and the outbox's integrity events.
- **Refusals.** Each code the services send has a sentence of ours (`SENTENCES`); `error` is the code, `ids` and
  `cost` travel beside it. `malformed` is 400, `not_found` 404, `wrong_tenant` 403, `queue_full` 503, the rest 409.
- **Cost.** Every answer carries `cost: { d1Statements, d1Batches }`; a drain also carries its provider requests by
  target.
- **No client module, no page.** Nothing in the SPA calls these routes yet, so there is no module under
  `frontend/src/lib/api/` (the drift check needs a mounted route for a client method, not the reverse).

### 3. Release authorities: none on main (an open question)

`ReleaseContext.authorities` says which release authorities each person holds (`maintainer`, `brand_owner`,
`founder`, `counsel`, `authorized_signatory`, `security_officer`…). D5585 left the route to "resolve them from real
roles". No table records them: `user_company_links.authority` is the team ladder (`VIEW`…`VOTE`, `teamAuthority.ts`),
which is a different vocabulary and, by its own rule, not an access check yet.

So the route resolves **none** (`RELEASE_ADMIN_DEPS.authorities`). Being a Super Admin grants no release authority.
On main that means: an approval counts for nobody, so a publish is refused `approval_required` (and recorded); a
takedown is refused `no_authority` (and recorded); a re-pin, the reads and the drain work. Tests replace the
resolver to prove the full paths.

The owner decides how authorities are resolved before release publishing is used for real:

- **A.** A release-authority store per company (who holds `counsel`, `security_officer`… in which company), written by
  a Super Admin with an audit row. A migration and its own part. *(Recommended.)*
- **B.** A Super Admin acting on these routes holds the takedown authorities (`counsel`, `security_officer`) for
  takedowns only, so disallowed content can be withdrawn before A exists; approvals still need A.
- **C.** Map the team ladder (`user_company_links.authority`) to release authorities.

### 4. The schedule

`scheduled()` in `index.ts` already runs every minute (`* * * * *`) under its KV queue lease. On minutes where
`% 5 === 2` it now calls `scheduledReleaseDrain(env)` through a dynamic import (HUBS.md: cron's one home), inside
its own `try`, which names `work graph release drain` in the cron row if it fails. No cron trigger was added.

- **Off,** it returns null before any D1 read or provider call.
- **On,** it runs one `drainReleaseEffects(env, { limit: 25 })` through the real adapters: `website_cdn` writes the site
  record to `FILES` when it is bound; `external_distribution` has no channel on main, so it refuses
  `target_not_configured` with no request and dead-letters after its attempts; the others use their existing bindings
  or refuse `target_not_configured`.
- **Never twice at once.** Ticks normally run one at a time under the cron's queue lease, but that is a KV lease, not
  a strict lock. Where two drains overlap (a tick that outlives the lease, or a manual drain beside the scheduled one), the outbox's own claim decides: each delivery takes
  a conditional claim on its effect before it runs, so the drains split the due effects and no effect is delivered
  twice. No second lock is added.
- **Telemetry.** A drain that did anything adds one line to the cron row (`work graph release drain deliveries=…
  <status>=… d1=… provider=…`). Each delivery row keeps its own D1 statements and provider calls (part 2).
- **Not gated on `hqCadences`.** Each deployment's outbox is its own rows, like the agent sweep.

### 5. Tests

`work_graph_release_admin_5585.test.ts`:

1. Flag off (absent, empty, `true`, `ON`, `preview`, `off`): all eight routes, signed in or not, answer 404
   `release_admin_off` with a D1 that fails on any touch; the scheduled drain returns null with that D1 for every value
   but `preview`; the hook sits in the `% 5 === 2` block of `scheduled()`, behind a dynamic import.
2. Gates: an admin, a member and an anonymous caller are refused every route; a Super Admin without a TOTP session
   and step-up reads and is refused every write; a bad scope is 400.
3. Cross-tenant: reads, publish, takedown and re-pin naming another scope are `wrong_tenant`; no event, effect or
   manifest is written; the takedown refusal is recorded against the line's tenant with the Super Admin as actor; the
   other scope's lists are empty.
4. Publish: `stale_approval`, malformed bodies, `approval_required` with the default resolver, then one publication,
   its replay, `stale_revision` against a moved pointer, and the next publication; six audit rows; the reads.
5. Drains: delivery off refuses; `limit: 1` delivers one; `limit: 1000` is capped at 25; a second drain sends nothing;
   the outbox list shows each effect and its delivery row; every manual drain is an audit row with its cost.
   5b: the scheduled drain takes 25 of 30 due effects, then 5; two drains at once apply one effect once and write once.
6. Re-pin from a stale head is refused with the current head, then cuts the Super Admin's manifest; a takedown with a
   stale digest or without authority is refused and recorded; with the authority it queues the retraction, and the
   next drain deletes the site record while the line serves nothing.
