## D6476 part 5 — The PR-list conflict indicator, and the keeper's own hand-back (#6476)

- **Status:** built by S21 on 2026-11-21 for the owner's addition on #6476 (comment 7064822922), as a follow-up to #8054.
- **Builds on:** D6474 (the branch keeper), D6476-p4 (#8054: re-queue only on `mergeable: true`).

**What the owner asked.** Show a confirmed merge conflict in the PR list even when checks are green, including after a queue removal. Clear it only on positive mergeability for the current head and base. Re-evaluate after main moves. Keep this metadata separate from repair authority. Reuse the existing `conflict` label, and add no second merge or repair bot.

**The indicator.** `scripts/landing-bot/conflict-indicator.mjs`, run by `.github/workflows/landing-conflict-indicator.yml`:
- **When it runs:** on each push to main and every 15 minutes, with `GITHUB_TOKEN`, behind its own switch, `LANDING_CONFLICT_LABELS`.
- **What it reads:** every open PR into main.
- **What it does:**

| GitHub reports | Indicator |
|---|---|
| `CONFLICTING` | add `conflict` (idempotent; other labels kept) |
| `MERGEABLE`, labelled | re-read; remove only if the fresh read says `mergeable: true`, on the same head, with the PR's base at the current main head |
| `UNKNOWN`, `null`, unread, head moved, base behind main | no change |

It writes labels and nothing else. It never merges main, calls a model, enqueues, re-runs CI or uses the landing App. No bot reads the label to decide an action: GitHub's own mergeability and each bot's own records decide.

**The keeper's own hand-back.** The keeper used to treat any `conflict` label as "handed back; waiting for a push". The indicator, and the serial refresh's "conflict, for the keeper" label, would therefore have stopped a keeper run that was otherwise allowed. Now:
- when the keeper's merge leaves conflicts, it labels both `conflict` (the indicator) and `bot:keeper-tried` (its record);
- `keeper.mjs` and `keeper-plan.mjs` count only `bot:keeper-tried` and `needs-session` events as a hand-back;
- `conflict` alone never suppresses the keeper.

PRs the keeper labelled `conflict` before this change get at most one more keeper try, which ends in `bot:keeper-tried` if the conflict is real.

**Unchanged:** `needs-session` and `bot:off` as hand-backs; the resolver removing `conflict` when it resolves; the T2 / model-resolved owner lane; #5719 and the rollout gates. The indicator stays off until the owner sets `LANDING_CONFLICT_LABELS=true`.

**Already in #8054 (D6476-p4):** the ejection handler re-queues only on GitHub's fresh `mergeable: true`, for every class. An explicit `false` goes to the keeper flow; `null` waits.

**Tests.**

  - resolved is cleared only on fresh true;
  - unknown makes no false clear;
  - a moved head or a base behind main keeps the label;
  - a repeat sweep writes nothing;
  - the workflow's own switch, with no App or secrets and label writes only.
- `landing_bot_keeper_6474.test.mjs` covers `conflict` alone versus `bot:keeper-tried`.
- Mutations caught: the keeper reading `conflict` again, and clearing without fresh confirmation.
