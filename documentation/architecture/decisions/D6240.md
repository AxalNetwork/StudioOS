## D6240 — Delivery of an issued reporting period, recorded per LP (#6240)

**Store.** Migration `202611270442_6240_fund_report_lp_delivery.sql` adds
`fund_report_lp_delivery`: one row per (issued `fund_report_periods` row, LP
row), keyed `(period_id, lp_id)`. It records delivery for reporting periods
only. A pack issued through the reporting queue (D712) issues its linked
period through the same `sendFundReportNotices`, so the period's rows cover it;
the admin report packs carry no delivery rows of their own. It extends D6255
and does not replace it: the D6255 receipt stays the one-per-period record of
the notice transaction, and these rows are written in that same transaction.

**States.** The row's `state` is one of:

- `not_sent`: the LP row has no active linked account. The surfaces say
  **No account**, and it is not counted as delivered.
- `made_available`: the in-app notice reached the linked account.
- `opened`: that account read the issued report.
- `failed`: the notice transaction failed for this LP.

Acknowledged is not a state. An LP has no acknowledge step anywhere, so the
LP side cannot tell it; opening the report is the last state recorded. The
row's `user_id` is the account the notice went to (NULL exactly when
`not_sent`), and `made_available_at` and `opened_at` are set exactly when the
state says so (table `CHECK`s). `recorded_at` is when the issue wrote the row.

**Writes.** `sendFundReportNotices` inserts the rows in its batch, after the
inbox insert and before the D6255 receipt, under the same "no complete
receipt" guard: committed and active LP rows, an active linked account →
`made_available`, otherwise `not_sent`. Two LP rows on one account each get a
row; the account gets one notice. When the batch fails, the failure path
writes `failed` for each LP the notice would have reached and `not_sent` for
the rest. A later successful send rewrites only `failed` and `not_sent` rows,
so a retry never resets an opening. An LP's read of the issued period
(`GET /api/funds/:id/report-periods/:periodId` with `can_manage` false) moves
that account's `made_available` rows to `opened`, after the report is
served and once only: the first opening is the one kept. A failed write never
blocks the report. A manager's read records nothing.

**Reads.** Both are behind `requireFundGp`.

- `GET /api/funds/:id/report-periods` adds `lp_delivery` to each issued
  period: `{state: 'recorded', delivered, total, opened, failed, no_account}`,
  where `delivered` counts `made_available` and `opened` and `total` counts
  every row.
- The period read adds the same counts, plus `lp_deliveries` (LP id, name,
  state, both times, and whether the LP row was since removed) only when
  `fundPageAccess` admitted the caller through `requireFundGp`. An LP's read
  carries neither.

`lp_id` has no foreign key, so removing an LP row keeps its delivery history
and the period's `m`.

**Legacy periods.** A period with no rows was issued before this change. It
reads `{state: 'not_recorded'}`, and the per-LP read says *Not recorded: this
period was issued before delivery was recorded for each LP.* It never reads
0 of m. The one exception is a complete D6255 receipt that counted no LP and
no unlinked LP: the fund had no LP at issue, so 0 of 0 is true. A failed read
of the rows, or of the receipt for an empty period, is `unreadable`.

**Surfaces.** On `/funds/reporting`, the archive's Delivered column (FV10)
shows **n of m**, with opened, no-account and failed counts beneath. A legacy
period reads *Not recorded · issued before delivery was recorded*. The
Delivered tile shows the latest issued period. The Delivery chip is live as
*Not all delivered*: issued periods whose recorded `delivered < total`.
Delivery log stays unbuilt, because no read joins the per-period lists. On
the period page (FV11), the issued header's Delivered row and a
*Delivery to LPs* card list each LP for the manager. A reply without
`lp_delivery` (a Worker from before this change) keeps the D6255 label. The
overview's *Delivery recorded* gap counts a period only when its per-LP
counts are recorded.
