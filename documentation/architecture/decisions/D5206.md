## D5206 — Calendar reads publish only from the latest request (#5206)

## Decision

Personal and staff-scope Calendar views use one read controller. Every whole-window read and provider-only retry receives a monotonically increasing request identity plus a key made from scope, start and end. A result or error may publish only while both belong to the latest request.

Navigation starts a new window in `loading` and invalidates the old request. Retry and Refresh for the same key preserve a successfully rendered Calendar, set `refreshing`, and replace it only when the new answer arrives. A failed refresh leaves the prior answer visible and attaches the error to that refresh. Component cleanup cancels publication without aborting a promise that the request client cannot currently cancel.

## State

The controller owns `loading | ready | partial | unreadable`, items, source rows, coverage, current window, request identity, `refreshing`, and the current error. A response is `partial` when coverage says it is incomplete, a source failed, or a source was truncated.

Provider-only retries use the same identity stream. Therefore a late Google or Outlook retry from November cannot merge into a newer December, Week, Agenda, Studio or Platform view.

## Compatibility

No API or storage changes. Existing Calendar response fields and source-health copy remain intact. The controller wraps the existing reads and preserves D5202 provider retries and D5204 coverage semantics.
