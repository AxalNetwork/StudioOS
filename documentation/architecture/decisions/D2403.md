### What part 2 builds

1. **The provider** `cloudflare-worker/src/integrations/providers/x.ts`, key `x`, through the generic OAuth start and callback (`oauth_state_tokens`, PKCE S256, the D751 `ready` gate). It is registered by `routes/admin_integration_keys.ts`, which imports its `redirectUri`, as TikTok's is; `index.ts` is untouched.
2. **The founders app** (decision 2B) is a managed key, `x` → `X_FOUNDERS_CLIENT_ID` / `X_FOUNDERS_CLIENT_SECRET`, set from the Integration keys console or as Worker secrets. HQ's own posting app (`X_CLIENT_ID`) never serves a founder, and does not make the connector ready.
3. **Read first.** Connect asks for `tweet.read users.read offline.access` (`integrations/xScopes.ts`). The start's `publish=1` is "Turn on publishing": the start writes it into the signed state, and the provider reads it from the state, never from the callback's query, then asks for the read set plus `tweet.write media.write`. The registry lists the union, so the generic overreach check accepts either grant.
4. **What X granted is what is recorded.** `config_json` holds `x_user_id`, `handle`, `granted_scopes` and `publish_on`. A read sign-in that comes back with a write scope, or without the read set, is revoked (both tokens) and refused, and no row is saved. `assertPublishGranted(row)` refuses `x_publish_not_granted` without `tweet.write`; part 4's publish path calls it first.
5. **Tokens** sit in `integrations.credentials_enc` (row-uid AAD), never `x_accounts`. `xFounderAccessToken` refreshes 60 seconds before expiry behind its own lease, `x_founder:refresh:<uid>` (apart from HQ's `x:refresh:<id>`), and writes both rotated tokens in one statement. A refused refresh marks the row `error` with `last_error = 'x_refresh_refused'`. A held lease calls nothing.
6. **Disconnect** revokes the access and the refresh token at `/2/oauth2/revoke`, best effort; the route then deletes the row and its company rows whether or not X answered.
7. **Who may connect:** `audience_rule: 'venture'`, `tier: 'growth'` (decision 4: paid founder plans; a free plan is answered 402 before any state). `writesProjectData('x')` is true, so a connection serves only the companies it is switched on for.
8. **A one-letter key.** X's key is `x`, the issue's own and the one PUBLISH's targets name. The connector key pattern (`CONNECTOR_KEY_RE` in `services/eadwynConnectors.ts`, mirrored by `PAGE_KEY_RE` in `connectorPages.ts`, held equal by a test) required two characters or more; it now allows one: still a lowercase letter first, lowercase letters, digits and `_` after, 40 at most. Nothing else it admits changes.
9. **The directory:** a `CONNECTOR_METADATA` row in the shared `Social` category and a `CONNECTOR_PAGES['x']` entry. `integrations/xFeeds.ts` lists the three Grow feeds with `built: false`; the registry's `pulls` and `feeds` and the page's tools read built feeds only, so nothing is claimed before part 3 lands it.

### Left for later parts, and why

- **Not revoked on re-consent.** Turning publishing off is a read-only sign-in again; the stored pair is replaced by the read-scoped one, so StudioOS can no longer post. The replaced pair is not revoked at X: whether X's revoke ends one token or the whole grant is **UNVERIFIED**, and if it ends the grant it would also end the new connection. The owner's first live connection settles it.
- **The per-founder monthly cap** (decision 2) sits in front of the first billed call, which is part 3's sync; part 2 calls only the token, revoke and `users/me` endpoints at sign-in.
- **`FED_LEDGER_PROVIDERS`** gains `x` with part 3, when a feed first writes the ledger. Until then the connector page's "Now fed by" says Not recorded, never 0.
- **The connector page's Publishing row and its "Turn on publishing" dialog** are drawn on the X1-X5 boards, which are not in `design/incoming/` yet; they land with part 4, Post to X. Until then the publish consent is reachable only by `?publish=1` on the start.
- **Every UNVERIFIED fact in #2403** (prices, owned reads, refresh-token rotation lifetime, revoke semantics) stays so until the owner's first live connection, which records `verified_on` on the page.
