### 1. The decision

One registry describes every tool Axal can expose or call: Axal's own tools, connector-backed reads and, from #2468 and #2475 on, remote MCP tools. `tools/list` shows a member only the tools their scopes, plan, connections and companies allow.

The owner's question on #2467 was built as **A**: an external AI client may read connector-fed module data once the member consents to `build:read` or `connectors:read`, as module records only and never a live provider call. If the owner chooses B, the two tools in §3 come out and nothing else changes.

### 2. The contract (`mcp/server.ts`)

**A tool (`McpTool`) carries:**

| Field | Meaning |
| --- | --- |
| `requiredScope` | One of `SCOPES` (`mcp/oauth.ts`) |
| `source` | `axal`, `connector` (StudioOS's records of a connection) or `remote_mcp` |
| `provider` | A key in the connector registry (`integrations/registry.ts`), for a connector or remote tool |
| `version` | Semver. It is reported in `_meta` under `vc.axal/version`, with `vc.axal/source`, on the listing and on every result |
| `entitlement` | The founder plan the tool needs (`userMeetsTier`). None means every plan |
| `requiresConnection` | Listed only while `provider` is connected (`integrations.status = 'active'`) and switched on (`integration_companies.enabled = 1`) for at least one granted company |

**Listing.** `createServer` is now async. It registers only the tools for which all of these hold:

1. the token's scope covers the tool;
2. the plan is met;
3. the connection holds, when the tool needs one.

The granted companies are those the user can still read (`grantCompany`).

**A hidden tool.** A call to a tool that is not listed answers `That tool is not available on this connection.`, word for word what an unknown name answers. The answer never names the tool. The server puts that answer in front of the SDK's own `tools/call` handler, so the SDK's "Tool X not found" never reaches the client. When the grant no longer stands (an ended account, a deletion request, a later "sign out everywhere"), nothing is listed and a call answers with that refusal's sentence.

**Listing is not authorization.** `callTool` asks again on every call:

1. the user;
2. the scope;
3. the plan;
4. the rate limit;
5. the company;
6. the connection: the provider must be on for some granted company, and for the company the call names when it takes one.

**Versioning.** A tool's name is stable. A breaking change registers `<name>_v2` beside it and keeps v1 until it is retired the way #2319 retires.

**Investor plans.** No tool needs an investor tier yet, and a grant reaches only ventures the member owns (`grantableCompanies`), so `entitlement` is the founder `Tier`. A tool that needs `effectiveInvestorTier` adds that field when it is built.

### 3. The scopes and the first connector-backed reads

**Three read scopes:**

- `build:read`;
- `raise:read`;
- `connectors:read`.

They are added to `SCOPES`. The consent page shows each one's wording, which the Worker sends as `scope_labels`, built from `SCOPE_COPY` in `routes/mcp_consent.ts`. The page's model (`frontend/src/pages/connect/assistantConsentModel.js`) shows the Worker's words. A scope it has no words for is shown by its name, never dropped as it was before, so no scope is approved unseen.

A scope is granted only by an explicit consent, and from #2464 on by a key's own scopes. `raise:read` has no tool yet.

| Tool | Scope | Reads |
| --- | --- | --- |
| `get_build_progress` (`mcp/tools/build.ts`) | `build:read` | One company's Product roadmap items by column and how many shipped (`roadmap_okrs`), published releases (`roadmap_releases`, prereleases left out), Prototype / MVP must-haves built and in progress (`mvp_features`), and what the member's GitHub connection fed that is still standing (`connector_fed_items` with a `local_id`) with its last sync. `source: 'connector'`, `provider: 'github'`, `requiresConnection` |
| `list_connections` (`mcp/tools/connections.ts`) | `connectors:read` | For each granted company, the member's own connections switched on for it: provider, name, status, last sync and last failure time |

**Neither tool calls a provider or reads a credential.** The test fails if `fetch` is reached. Unknown is null: with no rows, "shipped" and "built" are null, not 0. `list_connections` never returns:

- a token or a webhook secret;
- an external account id;
- a stored error's text, which can carry what a provider echoed back.

### 4. Tests

`cloudflare-worker/test/mcp_registry_d846.test.ts` drives the server through the SDK's own client over an in-memory transport. It covers:

- three principals, each listing a different set of tools: by plan and connection, and by scope;
- a hidden tool's call matching an unknown one exactly;
- the per-call re-check of scope, plan and connection;
- the consent page's words;
- both reads under a failing `fetch` stub;
- `_meta` versions.

Every assertion was mutation-checked: 26 of 26 mutations fail the test, and the restored code passes. `mcp_authorization_d669.test.ts`'s registry list gains the two tools. Its probes still find each line they mutate, because the listing's copies of the scope check and of `grantUser` are worded differently.
