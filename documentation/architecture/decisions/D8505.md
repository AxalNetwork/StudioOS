## D8505 — claude-code.yml: a read-only admission job decides who may start a run; the model job holds no write scope (#8505)

- **Status:** built by S16 on 2026-11-25. A protected path: the PR is T2 and the owner lands it. Source: the agent-CI audit of 2026-11-25 (P0), tracker #8509 row A1.
- **Done when, still open after landing:** the owner runs one real `@claude` mention and links the run on #8505.

### What was wrong

`.github/workflows/claude-code.yml` gave the whole workflow `contents: write`, `issues: write`, `pull-requests: write` and `id-token: write`, and decided who may start a run from the comment's `author_association` (#4571 SC-02). That field is GitHub's label for the commenter, not their permission on the repository. The job that held the write scopes also read the issue and comment text that anyone can write on a public repository. Nothing is known to have been misused. The decision to start a run and the authority to write sat in one job.

### What this changes

| Job | Token | What it does |
| --- | --- | --- |
| (workflow) | `permissions: {}` | No token unless a job asks for one. |
| `admit` | `contents: read`, `pull-requests: read` | Keeps the SC-02 `if:` as a cheap first filter, then runs `scripts/claude-code-admission.mjs`. The script reads each requester's real permission with the collaborator permission API and admits `write` or `admin` only (the API's `permission` field folds `maintain` into `write`). The requesters are the account that wrote the text and the account that caused the event, so an `issues: assigned` event needs both. When the owner sets the repository variable `CLAUDE_CODE_ALLOWED_ACTORS`, each requester must also be on that list: the list narrows and never widens. The script binds the run to this repository, the issue or pull request number, and a head SHA. For a pull request that is the head read now. A review written on an older head is refused. For an issue or a dispatch it is the commit the run started on. A dispatch from any ref but `main` is refused, which the federation rule would refuse anyway. A refusal writes one line to the job summary and the output `admitted=false`. Every failure is closed: an unreadable permission or head refuses, and an internal error exits 1 with `admitted=false`. |
| `claude` | `contents: read`, `pull-requests: read`, `id-token: write` | Runs only on `admitted == 'true'` for the same repository. The checkout keeps no credential (`persist-credentials: false`). The federation preflight (D5530) runs as before. The new step "Head still at the admitted commit" re-reads the pull request and stops the job if its head moved since admission. That happens before the action starts. Then the pinned action runs. |

A request from an account without write gets no model step and no token with write scope. The admit job has none. The `claude` job does not start. `frontend/test/claude_code_admission_8505.test.mjs` shows both: dry runs of the script with `--fixture` read nothing from the network.

### Why there is no separate mutation job

The issue asks for mutations in a third job, bound to the admitted pull request and SHA. The pinned `anthropics/claude-code-action` does not hand its writes to anyone. It posts its tracking comment, updates it and pushes its branch inside its own step. The workflow passes it no `github_token`. Its v1 documentation says that in that case it exchanges the job's OIDC token for the Claude GitHub App's installation token. That is why `id-token: write` serves two exchanges here, the App's and the Anthropic federation's (D5530). The action has no mode that emits a patch for a later job to apply, so a mutation job would mean replacing the action's tag mode with our own runner. That is out of this issue's scope.

What this means in practice:

- The `GITHUB_TOKEN` of the job that reads untrusted text has no write scope. Before this change it had three.
- The action's writes carry the Claude App installation's permissions. This workflow cannot narrow them. #8061 (one App per agent role) is the console-side control for that token. When it lands, the App that the action exchanges for is the one to scope.
- The admission job and the SHA binding stay, as the issue asks.

**To confirm on the owner's first real mention.** This session could not see the action's source or a recent run: the last 600 runs of this workflow were all skipped by the `if:`. If the action's comment or push then fails for lack of a `GITHUB_TOKEN` write scope, the action is using the job token after all. The fix is then to give the `claude` job `issues: write` and `pull-requests: write`, plus `contents: write` only if it must push, and to update the guard test to match. The admission job and the head check still come first.

### Unchanged

- The federation of D5530: its own rule, and the `workflow_ref` claim names this file on `main`. Splitting the work into jobs does not change the file. No API key returns (`scripts/lib/claudeCodeFederation.test.mjs`).
- The action stays pinned by SHA (WF-1).
- The SC-02 filter on all four comment and issue events (`workflow_security_4571`).

### Rollback

Revert the PR. That restores the single job with the workflow-level write scopes. Nothing else depends on the new script or the `CLAUDE_CODE_ALLOWED_ACTORS` variable, and an unset variable changes nothing.
