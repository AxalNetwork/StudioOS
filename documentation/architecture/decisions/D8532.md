## D8532 — The release window is rehearsed on the pull request: migrate, stop before publishing, run the previous Worker on the migrated schema, retry and converge (#8532)

**Decided.** Every pull request that changes a D1 migration, the Worker, `wrangler.toml` or the deploy workflow runs `scripts/release-window-rehearsal.mjs` in the `release-window` job of `release-rehearsal.yml`. It rehearses the window between the release's two writes (`cloudflare-worker-deploy.yml` applies the migrations, then publishes): the migrations succeed, the publish fails, the **base** commit's Worker keeps serving the **candidate's** schema, then a retry or a forward fix lands. The rollback classifier (D7151) reasons about that window; this runs it. Locally, over synthetic data: no Cloudflare account, no production database, no deploy.

**The five steps** (`scripts/lib/releaseWindow.mjs`):

1. **The base schema.** The base commit's tree is exported with `git archive` (no worktree, so the repository's git state is untouched; design, documentation and attachment trees are left out), its Worker dependencies installed from its own lockfile and its generated modules built. Its `schema_baseline.sql` plus its migrations above the cutoff are built into a SQLite file with every file in `schema_migrations`, as production holds it after the base release. The **base Worker** seeds it (`scripts/release-window-probe.mjs --mode seed`): an account on the paid plan with a TOTP sign-in (the secret encrypted by that Worker's own column cipher), a free account with an accepted `project_members` grant, an outsider, and their project. The base Worker's answers to the probes on that database must be the expected ones (sign-in 200, paid plan 200, free plan 402, member 200, outsider 403, hashed asset 200, missing asset 404), or nothing later can be compared.
2. **The pending migrations,** the candidate's files the base does not have, planned and recorded with `migrate-d1.mjs`'s own `planActions` and `applyPlan`, each file run as one transaction, as D1 runs a `--file` (DEPLOY.md §4c).
3. **Publish stopped.** The base Worker answers the same probes on the migrated database: `POST /api/auth/login` with a TOTP code and `GET /api/auth/me` (sign-in, a write), `GET /api/funds` as the paid and the free account (the Raise + Grow gate), `GET /api/projects/:id` as the grantee and the outsider (the grant), and `GET /assets/index-<hash>.js` for a hashed asset and a missing one. Each answer keeps only what must not change (status, ids, names, an asset digest) and must equal its answer before the migration; a difference means manual recovery.
4. **Retry.** The ledger-driven re-run must plan nothing. Each pending file is then replayed once on a copy, as if its ledger row had been lost (`migrate-d1.mjs` executes a file and records it in two calls, and a run killed between them replays it): the replay must refuse and roll back (the runner stops and names it) or change nothing, compared object by object over every table's rows and every object's SQL. Forward fixes run. Then the **candidate Worker** on that database must answer exactly as the candidate Worker answers on a clean build of the candidate schema seeded after the migration, and the two ledgers must hold the same files and checksums.
5. **Manual recovery has a rehearsed forward fix.** A pending file the classifier (`classifyMigrations`) calls `manual`, and every pending file when step 3 differed, must name its fix in the file: `-- forward-fix: <repo path>.sql`, a SQL file inside the candidate tree (run in step 4 on the migrated database and on the clean build) or another pending migration (already run in step 2). A script is not accepted: it cannot be run locally against this database.

**Bound to the candidate.** The report (`release-window.json` and `.md`, in the job's artifact and summary) names the base SHA, the candidate SHA and every pending file with its sha256, so a release's evidence can cite the rehearsal of the commit it ships. Durable Object migration tags the candidate adds over the base are listed as **not rehearsed**, with the reason, and do not fail the run.

**Why node:sqlite and the test harness, not `wrangler dev`.** The issue allows either. The probes run the Worker's own `fetch` (the default export of `src/index.ts`), loaded with that tree's TypeScript loader, on `cloudflare-worker/test/_d1_sqlite.mjs`, the D1 adapter every Worker test already trusts (D190, D370, D517), over a database built the way D4133's schema build is. SQLite is D1's engine. It needs no account, no network and no workerd boot: one probe is a child process of a few seconds, so a rehearsal is three to five minutes on a runner, and the base and candidate Workers are each exactly their own tree. What it does not model, recorded rather than hidden:

- foreign keys are off, as in the Worker tests (D1 enforces them);
- D1's limits (statement size, 100 columns per table) are not applied;
- the Worker runs without workerd: no Durable Objects (hence "not rehearsed"), queues, R2, AI or outbound fetch; the probes are chosen to need none of them;
- the hashed asset is served by a stub ASSETS binding with the SPA fallback, because the Worker answers `/assets/*` from that binding before any D1 work; it shows the Worker's asset path survives the migration, not the deploy's old-bundle retention (DEPLOY.md §2.1).

**Where it runs.** `release-rehearsal.yml` gains a `changes` job that diffs the merge commit against its first parent (the base it lands on) and runs D5501's existing `rehearse` job only for its own paths, and the new `release-window` job for migrations, the Worker, the toml, the deploy workflow and the rehearsal's own files. The job first runs `scripts/release-window-rehearsal.test.mjs` (the fixtures below), then the rehearsal against `HEAD^1`. It is advisory, like the rest of the workflow. The fixture test is not in `test:retention`: it builds the whole schema and boots the Worker about twenty times, so it runs only where its answer can change.

**Not built.** Gating the deploy on the rehearsal, or citing it from `release-rollback-class.mjs` (the report is shaped for it). Running Durable Object migrations. Forward-fix scripts other than SQL.

**Verified.** `scripts/release-window-rehearsal.test.mjs` runs fixture migrations on top of this tree's own schema and Worker: an additive column passes every step (its replay refuses with `duplicate column`); a dropped column the old Worker reads (`auth_totp.recovery_hashes`, read by `loadTotp`) is caught at step 3; a non-idempotent migration (a new table and an unguarded `INSERT`) passes steps 1 to 3 and is caught at step 4 by the replay; a classifier-`manual` rewrite fails step 5 without a forward fix and passes with one; a forward fix outside the tree is refused; a rewrite of rows the base already holds does not converge with a clean build at step 4; a new Durable Object tag is reported not rehearsed. Mutation check over that file: 7 mutations, 7 caught, 0 equivalent (step 3 off, replay outcome blind, ledger ignored, step 5 off, forward-fix containment off, step-4 convergence off, Durable Object tags hidden). A local run of the driver against a real range (base `7663595ec2`, the parent of #8209's merge, candidate `6f53183b93`, five pending migrations from #8209, #8168, #8276, #8420 and #8419) passed steps 1 to 4 and failed step 5: `202611220319_6007_segment_primary_profile.sql` line 19 is a `UNIQUE` index on an existing table, which the classifier calls `manual`, and it names no forward fix.
