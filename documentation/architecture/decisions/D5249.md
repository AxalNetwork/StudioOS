## D5249 — Require MFA for admins: an HQ setting and an enrol-first gate (#5249)

- **Status:** Worker part built in slot S13, 2026-11-11 (Part of #5249). Not deployed or live verified. The Overview control ("Require MFA for admins" on the MFA finding) waits on #5247, which changes the same Overview files, and is a follow-up PR.
- **Owner's call:** option B from S1's question on #5249 (enrol-first), not a grace period. No owner answer overrode it.
- **Basis:** `origin/main` at `b0ca15fa0f`.

### The setting

- One `platform_settings` row, key `require_admin_mfa`; value `'1'` is on, anything else or no row is off. **Off by default**, and no migration: `platform_settings` exists since migration 241.
- `GET /api/admin/security/mfa-policy` (Super Admin): `enabled`, `readable`, `updated_at`, `updated_by`, `admins_without_mfa` (null when unreadable, never 0) and a sentence saying what "on" does.
- `PUT /api/admin/security/mfa-policy` `{ enabled, reason }`: Super Admin behind the write bar (a TOTP session and a recent step-up, as every switch write, D4703). A reason of 3 to 500 characters is required. The setting and its `admin_audit_log` row (`require_admin_mfa_update`, `{from, to, reason}`) are written in one batch: if the audit cannot be written, nothing changes (503). Writing the state it already has changes nothing and records nothing (`changed: false`).
- HQ only: `requireSuperAdmin` refuses on a branch, and the gate does nothing there.

### The gate (enrol-first)

- `requireAdmin` (`cloudflare-worker/src/auth.ts`) gains one step, `refuseWithoutRequiredMfa`, before the compliance freeze. While the setting is on, an admin without MFA is refused **on every route behind `requireAdmin`, reads included**, and so on every route behind `requireSuperAdmin`, which is layered on it. The answer is 403 `{ code: 'admin_mfa_required', enrol_path: '/account/security' }`, from both `app.onError` and the shared `mapError`.
- **The way back stays open.** Enrolment (`/api/settings/totp/*`, passkeys) and `/api/auth/*` are `requireAuth`, never `requireAdmin`, so the refusal cannot close the route that lifts it.
- **"Has MFA" is the Overview's rule** (D4800): `tfa_methods` is not null and not `'[]'`. An admin the finding names is exactly an admin the gate refuses.
- **Cost.** Nothing for an admin with MFA (the user row already says so). One keyed `platform_settings` read per request, memoised on the request, for an admin without.
- **An unreadable setting reads as off**, logged, on D135's reasoning for the freeze: enforcement is a claim a Super Admin made, and inferring it from a failed read would refuse every admin without MFA during one table's outage. The read route says `readable: false` so the screen can say Unreadable, never "off".
- **Routes that check `role === 'admin'` by hand** without `requireAdmin` are not covered. The gate is where admin routes already funnel, as the freeze is (D135).

### Cannot lock out every Super Admin

- Turning the setting on is refused (409 `actor_without_mfa`) to a Super Admin without MFA. The write bar already demands a TOTP session; the explicit check states the rule in the setting's own terms, so a later change to the bar cannot undo it.
- So whoever turns it on has MFA and keeps access. A Super Admin without MFA afterwards is sent to enrol, like any admin, and the account's recovery flow is unchanged.

### The Overview control (frontend)

- **Where.** On the Overview's "Administrators without MFA" finding (D4800, #5165), under its detail. With no gap open it sits in its own small "Administrator MFA" section below "Checked and clear", so the setting stays reachable once everyone has enrolled.
- **Who.** Super Admin only. The read is Super Admin only, so `SecurityPage.jsx` asks for it only when `/me` says `is_super_admin`; a plain admin is shown no control and no empty section.
- **What it says.** On, Off or Unavailable, from the server's last answer (`mfaPolicyView`). A failed read, `readable: false` or a reply without a boolean is Unavailable with Retry — never Off, so the page never implies enforcement is in a state it did not read. Off says what it means: an administrator without MFA still reaches admin pages with a password alone.
- **How it changes.** Turn on… / Turn off… opens the Security `ActionDialog`: Scope (who it reaches, from the read's own `admins_without_mfa`, never 0 when unread; whether you are affected; the reason, at least `MIN_REASON` characters, as every Security act), Review, then Result. The write bar's step-up is the API client's own retry. The state moves only to the server's reply (`changeMfaPolicy`): no optimistic flip, a reply without a boolean re-reads, and a refusal leaves the badge where it was and says why — 409 `actor_without_mfa` ("enrol MFA on your own account first"), 503 ("nothing was changed"), step-up.
- **Words.** The vocabulary's badges with labels (On as Verified, Off as Not applicable, Unavailable as itself); no new state word.

`frontend/test/hq_security_mfa_policy_d5249.test.mjs`: the model's three states and refusals; server renders (Off by default with Turn on…, On with who changed it, Unavailable with Retry and no switch, no control and no section for a plain admin, the own section with no gap); the client's route and body; the page's wiring; and mounted journeys (reason required before Review and nothing sent, 409 said and the badge stays Off, 503 says nothing changed, a confirmed reply turns it On). Eight mutants (unreadable read as Off, the Super Admin gate, the reason check, the 409 sentence, an optimistic flip, the no-gap section, the page's read guard, drawing a reply without a boolean) each fail the file.
