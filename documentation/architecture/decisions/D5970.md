### What is decided

- **Which filter applies to which block.**

  | Filter | `coverage` | `published_evaluation` | `skills` |
  |---|---|---|---|
  | `scope` (`hq` only) | yes | yes | no |
  | `status`, `uid`, `version` | yes | yes | no |
  | `category`, `tag`, `role` | yes | yes | no |
  | `model` | no: coverage has no model | yes | no |
  | `from`, `to` | no: coverage is the catalogue now | yes | no |

  The response's `filters` repeats this for the filters given: each block's `applied` and `not_applicable`.
- **Checked, never defaulted.** Every name and value is checked before anything is served:
  - names against the filter list (plus `page`), each given once;
  - category against the radar axes, tag against the taxonomy's active skills, role against `ROLES`;
  - model against the catalogue's chat models, a deprecated one included because its history stays;
  - uid and version by format;
  - the window by date, order and length.

  Each failure is a 400 with its own code. Nothing falls back to "all".
- **The window bound is 366 days**, counting both ends, on evaluation `run_at` in UTC. It runs from `from` 00:00:00 inclusive to the day after `to` exclusive. It is bound into the history read before the ranking, so the latest row counted is the latest inside the window. A year, a leap year included, covers an annual review; the owner chose it on #5970.
- **Skill terms read the current published version**, as coverage does. Version is the skill's current version. A skill with no published version matches no role, tag or category.
- **A company skill never matches.** Its tags and roles are never read, so a filtered `by_scope.company` is `{ available: false }`, not 0. The `scope` parameter accepts `hq` only; a company administrator's own analytics stay out of this issue.
- **Matching nothing is observed, not missing.** Counts read over the matched skills give 0. Measures that need a row give `{ available: false }`. Measures a filter cannot narrow say so: the library files (`sources`), the drafts' evaluation, and the campaign, which is the whole catalogue's progress. Never the unfiltered figures.
- **No new read.** The same five reads run with or without filters. Matching is in memory over rows they already return, and model and window are bound parameters. To filter adoption, the pins read now returns one row per linked HQ skill instead of one total. `adoptionOf` sums those rows, and unfiltered it sums all of them.
- **An unfiltered read is unchanged.** It has no `filters` key. On a fixture, its JSON was byte-identical to main's before and after this change.
