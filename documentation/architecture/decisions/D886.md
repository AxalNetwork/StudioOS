### 2. Q1 — the host: Cloudflare Containers

**Verified, from Cloudflare's docs:**
- **Instance types:**
  - `standard-2` is 1 vCPU, 6 GiB, 12 GB disk;
  - `standard-4` is 4 vCPU, 12 GiB, 20 GB;
  - custom types up to the `standard-4` maximums, at least 1 vCPU and at least 3 GiB per vCPU [C1];
  - the image may be as large as the instance's disk [C2].
- **Running time.** There is no fixed maximum runtime. A host restart can stop a container at any time: the platform sends `SIGTERM`, waits up to 15 minutes, then sends `SIGKILL`. **Cloudflare does not guarantee any instance runs for a set period** [C3].
- **Lifetime control.** A Durable Object owns its container through `ctx.container`:
  - `start({ image, instance, enableInternet, env })`;
  - `setInactivityTimeout()` (at most 6 hours), which stops the container once its Durable Object has been idle that long;
  - `monitor()`, which settles when the container exits;
  - `signal()` and `destroy()`;
  - Durable Object alarms [C4], [C5].

  A request to the Durable Object keeps it active, and so keeps the container running [C4].
- **Price** (Workers Paid), billed per 10 ms of running time:
  - memory: $0.0000025 per GiB-second, on the provisioned size;
  - CPU: $0.000020 per vCPU-second, on active use only;
  - disk: $0.00000007 per GB-second, provisioned;
  - egress: $0.025 per GB in North America and Europe [C6], [C7].
- **Concurrency.** Live instances may total 1,500 vCPU and 6 TiB, which is over 1,000 `standard-2` at once [C8].

**Inference: Containers holds a 2-hour call, with one risk to design for.** Nothing stops a container at 2 hours, and the bot's own traffic keeps it alive. But a host restart mid-call is possible, so B2 must:
- on `SIGTERM`, flush the current part, post `interrupted`, and leave;
- have the Durable Object start one replacement, which rejoins (through the lobby again) and continues the part numbering.

The gap is recorded as a timeline event, never hidden. How often this happens is **UNVERIFIED**.

**Why not a VM.**
- A 2 vCPU / 4 GB VM costs about €8 a month (Hetzner CPX22 after its April 2026 increase, from third-party listings, **UNVERIFIED**) [V1]. Cheap, but:
  - it runs whether or not a bot does;
  - it holds one or two browser bots at a time, so bursts queue or need more VMs;
  - it adds an operating system to patch, a public endpoint and its secrets, outside Cloudflare's account and observability.
- The owner's pricing is "Cloudflare's measured cost × 1.25". A per-run container bill makes that cost exact; a VM's cost has to be apportioned.
- Containers bill only while a bot runs, scale to zero, and are started by the Worker that already owns the session.

**The size:** start on `standard-2`. Chromium in a meeting tab, or the Zoom SDK, with audio only and video off is expected to fit 1 vCPU and well under 6 GiB (**UNVERIFIED**; §7 measures peak memory and mean CPU). If peak memory stays under 3 GiB, move to a custom `{ vcpu: 1, memoryMib: 4096, diskMb: 8000 }`; that cuts the memory charge by a third.

### 3. Q2 — the runtime: our own, not Attendee

**Attendee (`attendee-labs/attendee`), verified from its repository:**
- **Licence.** The **Elastic License 2.0** [A1]: "You may not provide the software to third parties as a hosted or managed service, where the service provides users with access to any substantial set of the features or functionality of the software."
- **Footprint.** It "runs as a Django app in a single Docker image. The only external services needed are Postgres and Redis." Bots launch as Celery tasks by default, which the README says is not suitable for production: bots die on restart and share audio devices across meetings. Production runs each bot in its own Kubernetes pod (`LAUNCH_BOT_METHOD="kubernetes"`), with Kubernetes directions under its paid self-hosting plan [A2].
- **Dependencies:** Django, Celery, `psycopg2`, `redis`, `selenium`, `kubernetes`, `deepgram-sdk` and `zoom-meeting-sdk` [A3]. The image installs a pinned Google Chrome with ChromeDriver on Ubuntu 22.04 [A4].

**Inference:**
- Axal letting its members send a bot to their meetings is, on a plain reading, "access to a substantial set of the features" of a meeting-bot service. Building on Attendee therefore needs either a commercial licence from Attendee Labs or a legal opinion that it is allowed. This study is not legal advice: the ELv2 question is **UNVERIFIED** for counsel if the owner ever wants Attendee.
- Even with a licence, the bot part is wired to Django models, Celery and Postgres. The Worker already holds sessions, consent, metering and storage, so that would be a second application to run.
- **Attendee is not used, and its code is not copied.** Copying would make a derivative work under the same licence. Its README is read only as a list of platform quirks to expect.

**Our runtime (proposal), one image, Python 3.12:**
- **Meet and Teams:** Playwright for Python with Chromium (Apache-2.0 and BSD). The bot joins as a guest named "Eadwyn AI", camera and microphone off, then:
  - reads the roster and the speaking indicator from the page;
  - captures the tab's audio through a virtual sink (PulseAudio) into 16 kHz mono PCM.
- **Zoom:** Zoom's Meeting SDK for Linux through `zoom-meeting-sdk` (Python bindings; BSD per its PyPI classifiers) [A5]. Its raw-data API gives per-participant audio; Attendee's README notes per-participant audio is in the C++ SDKs, which the Linux SDK is [A2]. Use of the SDK itself is under Zoom's SDK terms, and B4 confirms those for this use (**UNVERIFIED**).
- **One adapter interface** (B2) and one adapter per platform (B3, B4, B5). §6 gives the interface.

### 4. Q5 — named speakers

**Verified:**
- Workers AI `@cf/deepgram/nova-3` takes `diarize` ("each word in the transcript will be assigned a speaker number starting at 0"), `channels`, `utterances` and `encoding` (including `linear16`). It costs $0.0052 per audio minute over HTTP and $0.0092 over WebSocket [N1], [N2].
- Axal's `services/sttFormats.ts` already sends `diarize: true` to Nova-3.
- A per-participant stream is billed per participant audio minute (D876 §6; Cloudflare's RealtimeKit transcription works the same way [N3]).
- Per-participant audio is available through Zoom's SDK. A browser bot on Meet or Teams captures the tab's mixed audio; per-participant capture there is a vendor feature-flagged product (Recall.ai), not a platform API [R1].

**Decision:**
- **Zoom: per-participant streams.** The adapter writes one stream per participant, each labelled with the SDK's participant id, which the roster maps to a display name. Only voiced audio is kept (a simple energy gate per stream), so the transcription minutes are about the speaking time, not participants × duration. A name comes from the stream itself, and diarization is not needed.
- **Meet and Teams: mixed audio, diarized, then mapped.** Each 120-second part is transcribed with `diarize: true`. For each diarized speaker, B6 sums its words' time overlap with each participant's "speaking" intervals in the timeline, and takes the participant with the largest share if it is at least 60% of that speaker's speech. Otherwise the speaker stays "Speaker N", never a guessed name. Overlapping talk and one-word turns are expected to stay unnamed sometimes. The threshold and the share are B6's fixtures, then §7's measurement (**UNVERIFIED**).
- **Batch, not streaming.** Parts are transcribed when they land, through `aiRouter`, as D872's parts are: $0.0052 a minute, not $0.0092. A live transcript is out of scope (D876).

### 6. The design B1–B7 build to (proposal)

**One run, end to end:**

1. **Dispatch (B1, B7).** `POST /api/founder/validate/sessions/:id/bot`, with `{ url }`.
   - Refused unless:
     - `MEETING_BOT` is on;
     - the session's consent is given (D872's attestation);
     - the URL parses as Zoom, Meet or Teams;
     - the founder's AI tokens cover one 2-minute block.
   - The run gets a uid, its platform and its limit: 30 minutes on a free plan, 120 on a paid one.
   - The URL is stored encrypted and never logged.
2. **The Durable Object `MeetingBot` (B1), one per run uid.**
   - It calls `ctx.container.start({ image, instance: 'standard-2', enableInternet: true, env: { RUN_UID, CALLBACK_URL, RUN_TOKEN } })`, then `setInactivityTimeout(120_000)`.
   - It sets an alarm at the limit plus 2 minutes, and watches `monitor()`.
   - `RUN_TOKEN` is a per-run HMAC that the Worker checks on every callback; the bot gets nothing else.
   - The meeting URL is sent once over that channel, never as an environment variable.
3. **The runtime (B2) calls back over HTTPS to `/api/meeting-bot/runs/:uid/…`, routed to the Durable Object:**
   - `state`: `joining | lobby | in_call | leaving | ended | failed`, with a reason code;
   - `heartbeat`: every 15 seconds. It keeps the Durable Object, and so the container, alive. Missing ones end the run through the inactivity timeout.
   - `roster`: `{ participant_key, display_name, joined_at_ms | left_at_ms }`. Names are stored encrypted and never logged;
   - `speaking`: `{ participant_key, from_ms, to_ms }`;
   - `part`: one 120-second, 16 kHz mono WAV (D872's format), with its `seq`. On Zoom it also carries `participant_key` and is voiced audio only.
4. **Metering (B1).** Each `part` takes a 2-minute bot-fee hold and settles it (the `liveTranscription.ts` block precedent), then queues its transcription through `aiRouter`. A refused hold (out of tokens, limit or pause) sends `leave` with reason `tokens`.
   - The ledger's holds expire after 5 minutes, so the run is never held up front.
5. **Leaving.** The bot leaves on any of:
   - the meeting ending;
   - being the only participant left for 2 minutes;
   - the founder's Stop (`POST …/bot/stop`, sending `leave`);
   - the alarm at the limit;
   - `SIGTERM`.

   It flushes its last part, posts `ended`, and exits.
6. **Assembly (B6).** Once the last part is transcribed, B6 builds the named transcript (§4), stores the roster as the session's participants, and hands the session to the existing engine: translation, summary and suggestions, with the founder accepting.
7. **Notices (B9).** On entering, the bot posts in the meeting chat: "Eadwyn AI is recording this call for <founder's first name>'s notes. Ask them to stop it at any time." Its display name says what it is.

**The adapter interface (B2, implemented by B3, B4 and B5):**

```text
join(url, display_name) -> lobby | in_call | refused(reason)
post_chat(text)
on_roster(cb), on_speaking(cb), on_audio(cb(participant_key | None, pcm_16k_mono))
leave()
```

**Codes** a run ends with: `ended`, `left_alone`, `stopped`, `limit`, `tokens`, `not_admitted`, `interrupted`, `join_failed`, `platform_refused`.

### 9. Zoom (B4, #2582)

**Status of the facts.** Everything below is from Zoom's published documentation, read on 2026-10-22. **Nothing was measured.** This environment has no Zoom account and cannot run the Linux Meeting SDK. B4 still measures M3, M4 and M6 on a free account and corrects this section where the results differ.

#### 9.1. Joining (Q3)

- **The OBF rule.** Since 2026-03-02, a Meeting SDK app that joins a meeting outside its own Zoom account needs a JWT plus an **OBF ("on behalf of") token**. A meeting inside Axal's own account needs only the JWT.
- **Whose token.** The OBF token is minted for a user who authorized the app by OAuth: here, the founder's existing Zoom connection (D757). **That user must already be in the meeting**, or Zoom refuses. Until the founder joins, the notetaker waits and the UI says **"Join the call first; the notetaker follows."**
- **The scope.** `user:read:token`.
- **The endpoint.** `GET /v2/users/me/token?type=onbehalf&meeting_id=<id>`, with the founder's access token. Zoom's pages also show `/users/{userId}/token`, and whether `meeting_id` is required is unclear (UNVERIFIED).
- **SDK version (Q4).** 5.17.5 or later is required for OBF. With 6.6.10 or later, a join refused for this reason names it: `MEETING_FAIL_AUTHORIZED_USER_NOT_INMEETING`.

#### 9.2. What this part builds (`services/channels/zoom.ts`)

`mintObfToken(env, conn, meetingId)` mints one OBF token with the founder's own grant, through the same `zoomApi` as every other Zoom call (refreshed under the D684 lease).

- **The token is the caller's for one run.** It is returned and nothing else: never stored, never logged, never in an error. A test holds this: the integrations row is unchanged and no console line carries the token.
- **Its refusals (`MEETING_ERRORS`):**

  | Zoom answers | Code | Retry? | The member reads |
  | --- | --- | --- | --- |
  | 401 | `zoom_reconnect` | no | Reconnect Zoom |
  | 403 (a grant from before the scope) | `zoom_obf_scope_missing` | no | Reconnect Zoom so the notetaker may join |
  | 429 or 5xx, or no token | `zoom_unreachable` | yes | Zoom did not answer |
  | any other refusal | `zoom_waiting_for_host` | yes | Join the call first; the notetaker follows |
  | a meeting id that is not 6 to 20 digits | `zoom_meeting_invalid` | no | no request is made |

  Reading every other refusal as "not in the call yet" is UNVERIFIED: Zoom does not document the status for it. B0's check confirms or narrows it.

#### 9.3. The registry and the order of the owner's steps

- **The ninth scope.** `user:read:token` joins Zoom's `oauth_scopes`, with one sentence on the connector page: "Let Axal's notetaker join a call on your behalf, only while you are in it." The page's tool list gains `notetaker_join_token`.
- **The order matters.** Zoom sets scopes on the app, not on the authorize URL. The callback refuses a grant **wider** than the registry (`scope_overreach`) and accepts a narrower one. So:
  - the registry lists the scope **first** (this PR), and a grant without it still connects;
  - the owner adds the scope and the **Meeting SDK** feature to Axal's Zoom app **after** this deploys. Adding it before would refuse every founder's Zoom connection;
  - founders reconnect once. Until then the mint answers `zoom_obf_scope_missing`.
- **The SDK credentials.** Whether Zoom gives the SDK its own key and secret, or the app's Client ID and Secret sign the SDK's JWT, is UNVERIFIED. If separate, they are `ZOOM_SDK_KEY` and `ZOOM_SDK_SECRET`, stored with B2's runtime (#2580). The steps are in `documentation/operations/ZOOM_AND_MEET_TRANSCRIPTS.md` §1.

#### 9.4. Audio, roster and speakers (for the adapter, after B2)

- **No license.** The legacy raw-data licence is not needed.
- **Roster and active speaker.** From the SDK's participant and active-speaker callbacks.
- **Not evaluated.** Zoom suggests Real Time Media Streams (RTMS) for continuous media access.

### 12. B6 — Transcript assembly: named speakers and the participant list (#2584)

- **Status:** PR 1 of 2, by S12 (#2594). PR 1 is the mapping and the participant list, on fixtures (`services/channels/botTranscript.ts`). PR 2 wires them to B1's store (#2579) and B2's events (#2580), once the three contract points raised on #2577 are settled: speaker silence, one roster shape, and a column for the participant list.
- **Basis:** `origin/main` at `8ec211a9da`. Worker paths are relative to `cloudflare-worker/src/`.

#### 1. What goes in

- **Nova-3's diarized passages** (`sttFormats.ts`), one transcribed chunk at a time. Each passage carries:
  - its chunk's `seq`;
  - times from the recording's start (the chunk's offset added, as D870's `transcribeStoredChunks` does);
  - the model's speaker number.
- **The runtime's events (B2),** on the same clock:
  - `join`, `leave` and `rename`: the roster, by the platform's participant id, with `is_bot` on the bot's own entry. B2's roster (#2598) reports `join` and `leave` by `key` only and never the bot, so a second `join` under a key already in the call is read as a rename;
  - `active_speaker`: the platform's indicator. From `at_ms`, the named participant is speaking, until the next mark. `null` is silence. This is B2's `speaker` event.
- **B2's `at_ms`** is the time since recording started, the origin of the chunks' `start_ms`, so the indicator and the audio share a clock.
- **On Zoom,** each passage carries its stream's `participant_key` (D886 §4: per-participant streams). Such a passage takes that participant's name directly; an unknown key is one "Speaker N" across the call.

#### 2. The rule

**Per chunk.** Nova-3 numbers speakers within one request: its speaker 0 in one chunk need not be speaker 0 in the next. A speaker is therefore a (chunk, speaker) pair. Each pair is matched against the indicator inside its own chunk, and the indicator is what carries a person across the call.

**A pair is named** after the participant whose indicator time overlaps its passages most, when that overlap covers at least `MIN_SHARE` of the pair's own speaking time. `MIN_SHARE` is 60%, as D886 §4 sets it.
- A passage that merely brushes someone's turn is not theirs.
- The platform shows one speaker at a time, so above half no two participants can tie: a tie names no one.
- §7's measurement may move the 60%.

**Otherwise** the pair is "Speaker N", numbered across the call in order of first speech, never a guess. Also:
- A passage Nova gave no speaker number is never named.
- Two unnamed pairs in different chunks may be the same person. They are numbered apart, because nothing says they are one person.

#### 3. Names and the participant list

- **Last name wins.** A participant's last display name labels all their passages: a rename mid-call renames them all.
- **The founder** is "Me" when a participant's display name matches the founder's display name, ignoring case and spacing.
- **No email addresses.** A display name that is an email address, or one that is blank, reads "Participant N".
- **The bot** ("Eadwyn AI", or any entry with `is_bot`) is never a speaker or a participant. Its own indicator spans are gaps.
- **The participant list** is display names with the first join and the last leave. `left_at_ms` is null for anyone still in the call at the end. No email and no platform id is returned.
- **`stats`** are counts only (speakers, named, unnamed, participants), for a log line or a receipt.

#### 4. What PR 2 does (waits on B1 and B2)

1. **Transcribe** the run's chunks with Nova-3 and diarization through the recorder's path (`interviewProcessing.ts` `transcribeChunk`, metered as D870 and D872).
   - Today `labelSegments` turns the model's speaker number into "Me" or "Speaker ?" before a chunk is staged.
   - For a bot session, the raw number has to be kept in the staged segments, so the mapping can run once every chunk is in.
2. **Assemble** with `assembleBotTranscript` and store the named passages as the session's final segments.
3. **Store the participant list** on the session, in B1's migration 531, and show it on the session.
4. **Hand off** to the engine (D857 translation, the summary, Validate proposals) exactly as an uploaded recording (D872) does.
5. **Retention:** D877 applies to the bot's audio.

#### 5. Tests

`test/bot_transcript_d886.test.ts`, 11 cases:

2. a tie, silence, and an overlap either side of 60%;
3. a renamed participant;
4. no overlap, and a passage with no speaker;

### B1 — Worker control plane (#2579, S07)

Implemented against `BotRuntime.start/stop`; real runtime wiring, adapter measurements,
transcription/assembly and the release switch remain B2–B10's work. This section is
the concrete Worker contract, superseding §6's provisional route/state names.
S1's ruling on #2579 (2026-10-22) also replaces the original full-limit hold:

- Dispatch checks the caller's **entire plan limit** at bot plus Nova HTTP price,
  without holding that amount. Free is 30 minutes; paid is 120, fixed at dispatch.
- The supervisor takes an idempotent **two-minute bot-fee hold before starting**,
  renews at each boundary, settles actual whole minutes once per block, and
  refunds unused amounts. The key is `meeting-bot:<uid>:<block index>` on the
  existing AI ledger. A refused renewal stops with `tokens`. No second STT
  charge is made here: B6 uses `aiRouter` for actual transcription.
- `MEETING_BOT=canary` requires a freshly hydrated Super Admin. It uses the
  ceiling bot cost 2,232 µUSD/min (2,790 with the existing ×1.25 multiplier).
  `MEETING_BOT=on` requires `MEETING_BOT_COST_MICROUSD_PER_MINUTE` to contain the
  measured **bot-only** cost. Missing/invalid cost refuses dispatch. Existing
  `chargeMultiplier` applies, including cost billing and the admin licence.
  The markup constant is the existing `AI_MARKUP=1.25`; this is 20% gross margin.

**Member API:** POST/GET `/api/founder/validate/sessions/:id/bot`, POST
`…/bot/stop`. POST accepts `{meeting_url, scheduled_at?: ISO8601}` up to seven
days ahead. Only the session creator with current project write access and
recorded consent can control it. Audio must be a fresh draft. Refusals use
`code`, `detail`, `message`. The response is `{bot}` with only `uid`, `platform`,
`status`, `failure_code`, `scheduled_at`, `started_at`, `ended_at`, `minutes`,
`participant_count`, `limit_minutes`, `rate_per_minute_microusd`. Times are epoch
milliseconds. No link, passcode, names or ledger identifiers are returned.

**States:** `queued → joining → waiting_room → recording → processing → done`,
with permitted shortcuts (joining directly to recording) and terminal
`failed`/`stopped`. `MeetingBotRun` is the sole status writer and serializes
all controls, callbacks, uploads and alarms. GET/duplicate dispatch recovers
an interrupted queued initialization; a schedule missed by over a minute fails
without joining. Repeated callbacks are idempotent and out-of-order ones fail.

**Runtime:** B8 provides `MEETING_BOT_RUNTIME` with
`start({uid, platform, meeting_url, limit_minutes, deadline_at, budget_deadline_at})`
and `stop({uid})`. Both are idempotent by uid, acknowledge promptly, never log
input, and **must not wait for callbacks** to the serialized supervisor. Runtime
must leave/flush at the budget lease deadline even during a network/Worker
outage. Heartbeat/status responses carry renewed `budget_deadline_at`; heartbeat
every 15–60 seconds. At two missed minutes the supervisor stops the run.

**Callback:** POST `/api/meeting-bots/:uid/events`, HMAC-SHA256 lowercase hex with
`MEETING_BOT_SECRET` (32+ characters) over
`v1:<epoch-ms>:POST:<pathname>:<raw JSON>`. Headers are
`x-meeting-bot-timestamp`, `x-meeting-bot-signature`; freshness is five minutes.
Every event has monotonic `seq` and `type`:

- `status`: `status`, optional allowlisted `failure_code`;
- `heartbeat`;
- `roster`: `participants:[{id,name,joined_ms,left_ms|null}]`;
- `speaker`: `participant_id`, `at_ms`;
- `chunk`: `chunk_seq`, `size_bytes`, `start_ms`, optional `participant_id`.

Roster, speaker and chunk manifests are encrypted in `meeting_bot_events`, AAD
`<run uid>:<event seq>`. B6 can decrypt the manifest to map a Zoom part to its
participant. A chunk request returns `{upload_path,expires_at}` for a one-use PUT
of canonical 16 kHz mono PCM WAV. It reuses D872's chunk store and R2 prefix.
Manifest retry uses the original metadata, never the retried payload. Requests
and bodies are bounded before storage; upload tokens bind run, sequence and
expiry. Total PCM bytes cannot exceed the plan's audio minutes; Zoom's voiced
parts must respect that aggregate cap. B4/B6 must not multiply it by the roster.

**Leaving and recovery:** Stop during recording enters `processing`, closes the
billing clock immediately, signals runtime stop, and allows at most 30 seconds
to flush audio captured **before** that boundary. A final status or alarm ends
it as `stopped`. Normal runtime `processing` ends billing after it has uploaded
all parts; B6 later sends `done`, after assembly. Runtime stop must therefore
signal leave asynchronously. Withdrawal, access loss and deletion stop hard,
with no drain. Consent is rechecked after an in-flight R2 write; revocation
removes that write. Stop retries and ledger settlement retain alarms until both
succeed. Runtime command failures never expose their raw errors. Terminal cleanup
wipes the encrypted link and outstanding upload tickets. D877 retention includes
meeting-bot chunks; session deletion explicitly purges the run/event rows too.

**Release gates:** this PR does not enable the switch, set a price, call a live
meeting or wire a container. B8 measures §7 and enforces runtime leases; B6 wires
transcription and terminal assembly; B9 owns notices and public rollout. Production
and preview both need migration 531, the `v2-meeting-bot` DO migration and runtime
binding before enabling a canary. No production credentials or meeting content
belong in fixtures, comments or diagnostic output.

### B7 — Record a Session integration (#2585, S15)

The UI uses Record a Session's existing layout, as S1 ruled on #2585; no new
canvas is required. Supported Zoom, Meet and Teams links offer **Send Eadwyn AI**
first and **Record this device** second. Consent and B9's disclosure precede the
send. The setup call excludes the plain URL for a bot; dispatch stores it through
B1's cipher. Bot/device setup have distinct idempotency keys. A refusal offers
the saved session for a status check, never automatic retry/device capture.

`MeetingBotPanel` mounts on the session and scheduled-call rows. It polls the
actual B1 status/stop routes, displays each state, an approximate run timer,
participant count and authored failure/refusal sentences, and disposes pending
reads on unmount. Stop returning `processing` is followed through the drain.
Queued dispatch atomically marks `submitted_via=meeting_bot`, so no device Start
or recovery is offered while its alarm waits.

Scheduling POST `/api/founder/validate/interviews/:id/meetings` accepts
`auto_send_bot:false` to opt out; omitted/true queues B1 after the call and its
consented session are stored. The response adds `bot` and `bot_error`. A bot
refusal leaves the scheduled call intact and is shown as a separate failure.
GET meetings includes the latest content-free `bot` DTO. A scheduled row's choice
uses dispatch/stop on that session; cancellation stops the bot before contacting
the provider. The queued run is the persisted choice. B1's seven-day scheduling
window remains visible; calls further ahead can enable the bot closer to start.

runtime snapshot, not B6's final assembled roster. Named transcript labels are
rendered from existing `segments[].speaker_label`; B6 remains responsible for
writing the final transcript. No participant identity is inferred from counts.
