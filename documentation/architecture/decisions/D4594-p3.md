### 1. The throwaway Worker's config is derived, never hand-written

`stageASections` reads `[env.preview]`'s tables from `wrangler.toml`, with `branchConfig.mjs`'s `parseToml`, and
replaces every identity with the run's own (`-s4594-<run>`):

- the D1 database;
- the three KV namespaces;
- every queue and DLQ;
- the Workflow;
- the three R2 buckets.

The database is a #4591 rehearsal side, `studioos-rehearsal-<run>-src`, so `migrate-d1.mjs --rehearsal` provisions it
with no change to the migration runner.

**The Worker's vars** are `[env.preview.vars]` plus `STAGE_A_VARS`:

- `ENVIRONMENT = "preview"`;
- `AGENT_ENGINE = "on"`, with `TEAM_AGENTS_ENABLED = "true"`;
- `AGENT_AUTONOMY = "manual"`;
- `AGENT_INFERENCE_STUB = "deterministic"`;
- the meeting bot off.

**One rendering, printed two ways:**

- **Flat (`renderFlat`): the file the deploy uses.** It is flat because the top-level table holds `axal.vc`'s
  custom-domain routes, and an `[env.*]` inherits `routes` unless it overrides them. A flat file with no route cannot
  move the apex.
- **As `[env.s4594]` appended to the real `wrangler.toml` (`envView`): the text the #4566 `preflight()` reads.** Its
  production comparison is then against the real production tables, not a copy.

**Left out on purpose:**

- routes and custom domains;
- `[[services]]` and tail consumers;
- the meeting bot's Durable Object, which lives in another Worker;
- `[browser]`;
- the shared analytics dataset and vectorize indexes;
- crons;
- `[assets]`.

**`checkFlat` runs before every deploy.** It refuses the config if it has:

- a route;
- a custom domain;
- an `axal.vc` host;
- an `[env.*]` table;
- a shared or outbound binding;
- a cron;
- anything but `workers_dev = true`;
- any production identity. These are read from `wrangler.toml` using the preflight's own `KINDS` identity fields, so
  the two checks never disagree.

### 2. The run (`scripts/agent-stage-a.mjs`)

The steps follow `schema-rehearsal.mjs`'s ledger, and each is timed in the summary:

1. **create:** the D1 database (EU), KV, the queues and DLQs, and R2.
2. **provision:** bootstrap, apply, then a dry run that must report 0 pending.
3. **seed:** the #4566 fixtures (one tenant, one agent, two tasks, `synthetic.invalid` only), plus `extraSeed` (the
   sponsor's plan and the licence cap row, as the local harness sets).
4. **deploy:** `checkFlat`, then `wrangler deploy` of the flat file. A per-run random `JWT_SECRET` is its only secret.
5. **preflight:** the observation comes from read-only list commands (`d1 info`, `kv namespace list`, `queues list`,
   `workflows list`, `r2 bucket list`, `secret list`). Anything but `isolated` stops the run **before any agent step**.
   - **The Worker is deployed before the preflight,** because there is nothing to observe until it exists. With no
     route, no cron and an unpublished `workers.dev` address, nothing calls it until the driver does.
   - **Inference is the one thing the observation cannot see directly.** It is declared from the config, then proven
     afterwards by `verify_stub`.
6. **workflow_path:**
   1. `POST /api/teams/tasks/:uid/start` answers 202;
   2. poll `GET /runs/:uid` until `waiting_decision`;
   3. the sponsor posts `POST /queue/:proposal/decide` with `accept`;
   4. poll until `done`.
7. **manual_path:** `POST /agents/:uid/run` answers 200 with a proposal, then the sponsor accepts it.
8. **reconcile:** the local harness's own ledger reads (`RECONCILE`). The run fails on any of:
   - a pending hold;
   - a duplicate proposal or settlement;
   - settled not equal to charged;
   - a live run;
   - no proposal;
   - a failed read.
9. **verify_stub:** every agent proposal carries `STUB_ANSWER`. Otherwise inference was not the stub, and the run fails.
10. **ceilings:** see §3.
11. **teardown, in `finally`:**
    1. the Worker;
    2. the Workflow;
    3. the queues;
    4. KV;
    5. R2;
    6. D1.

    A delete that fails fails the job and is named.

**Authorization is the Worker's own.** The driver signs the synthetic sponsor's bearer token with the run's
`JWT_SECRET`. It is the HS256 `{ user_id, iat, exp }` token `auth.ts` verifies. No endpoint was added, and no check is
bypassed.

**The log and the artifact hold names, counts, states and timings only.** Wrangler output that could quote SQL or a
secret is withheld, and only its error codes are kept.

### 3. Ceilings (owner decision 2 = A)

| Ceiling | How it is held |
|---|---|
| One lifecycle per path | The driver runs one Workflow-path lifecycle and one manual run |
| $0 model spend | Inference is the stub, and `verify_stub` proves it |
| 60 minutes | Checked before every step; the job's own timeout is 90 minutes, for teardown |
| At most 1,000 D1 writes | Rows added by the agent phase (the sum of every table's count, after the phase minus before) |

**The D1 ceiling is a lower bound, and it says so.** Rows added does not count updates. D1's `rows_written` analytics
lag, so the summary reports `rows_written` as "Not recorded" rather than a stale figure. The agent phase's real writes
are a few dozen; the 1,000 ceiling exists to stop a runaway.
