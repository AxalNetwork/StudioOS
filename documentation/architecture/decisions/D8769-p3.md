### Built

- **The skills gate (TMM04B, Q2 = A).** `agentChoiceModel.skillsGate(block, picked, name)` decides whether the wizard's Skills step can go on, from the step's own read of the skills an agent not yet added could take (`eligibleSkills`, D8768), which `SkillsStep` now hands up (`onBlock`). With the read answered and nothing picked, Next stays off. It stays focusable (`aria-disabled`, not `disabled`) and is described (`aria-describedby`) by a status line, "{name} can’t run without a skill. Choose at least one to continue." A press does nothing. While the read is in flight Next is off too. A read that failed is an alert with Try again, which reads it again (`tries`), and Next stays off, as TMM04B's note asks: nothing is added that could never run. Its old line "You can add skills from the agent’s profile later" is gone from that state.
- **When skills are not open at all** (`team_agents_off`, or any other answer that is neither available nor unreadable), the gate is open and Next keeps D8768's "Next: model and cap, with no skills". No skill could be chosen anywhere, so a gate there would block every add. This is a judgement call; see the left-out list. While the gate holds, Next reads "Next: model and cap", never "… with no skills". `wizardSkillsNext` (D8768) is unchanged.
- **The whole ⋯ menu (TMM07 B).** `actionItems` gives a manager the canvas's list: Open {name}’s profile, Add skills for {name}, Edit {name}’s cap, Change {name}’s sponsor, then Pause {name}, or Resume {name} when Resume is that pause's fix (`pauseWords`). A paused row's fix comes second when it opens a dialog ("Raise the cap", "Choose a new sponsor"), and the item it stands for is not repeated. A reader still sees only the profile. An outside assistant (`mcp_client`) is offered the profile and its pause only, since it holds no Axal skills, cap or sponsor. Each item opens the profile on its action: `TeamAgentsPage` passes `editPause` and `addSkills` beside D4387's `editCap` and `editSponsor`; `AgentProfileSheet` opens the Pause or Resume confirm; `AgentSkillsCard` takes `openAdd` and opens Add skills once its skills are read, for a manager only.
- **The no-skills row's fix (TMM07 A).** A manager's no-skills row carries "Add skills for {name}" under "Can’t run until a skill is added". It opens the profile on Add skills. A reader's row keeps the words without the button.
- **What each skill makes (Q4 = A, first half).** `GET /api/teams/agents/:uid/skills` now carries each pinned version's `output_kind` and `output_label` (`OUTPUT_LABELS`), and the profile's skill rows say "Makes a brief" (`makesLine`; `SkillRow`'s new optional `makes`). With no label, the row says nothing, so no output is guessed.
- **Worker.** One DTO change (`agentSkillsDto`). No migration, no new route, no mount, no hub file.

### Left out, and why

- **Q4's second half, the agent's own last accepted output.** `ai_rail_proposals` holds an agent's accepted proposals (`agent_id`, `status`, `decided_at`), but its rows are the member's own: migration 506 scopes every read to `user_id`. A profile any team reader can open would show one person's accepted work to the whole team. The owner should decide whether that is wanted, and what may be shown (only the kind and date, or the text), before a route serves it. ⚑ Q6 below.
- **Per-agent readiness in the roster ("Ready", "Runs with limits") and readiness for an agent not yet added or for company skills (◇ in `D8769.md`).** The only readiness Axal computes is D4667's per-skill preflight (`GET /agents/:uid/skills/:slug/readiness`). It takes a venture and a period, covers only the first ten skills, and reads that skill's data, so a roster summary would run one preflight per skill per agent on every list read, against a venture and period the roster does not have. This needs its own design: what period, which venture, and whether to cache. The roster keeps "N skills", never "Ready".
- **How many published skills fit each persona, on the Who cards (TMM03).** "Fit" is D8768's `fitOf` on the Worker: the roles a version was written for, or the persona's natural-fit areas. Counting it per persona on the client would be a second copy of that rule. It needs the Worker to answer the count per persona, which belongs with #8768's eligibility work.
- **A gate when skills are not open at all.** See Built. If the owner wants no agent added while skills are off, the not-open branch of `skillsGate` changes and nothing else does.
