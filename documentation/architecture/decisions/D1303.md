### 1. Full access without an identity check needs a reason (ACC7 D)

- `PATCH /api/kyc/admin/:userId/approve` on an account with **no submission on file** now needs `{ reason }`, 10 to 500 characters. Without one it is 400 `reason_required`, and nothing changes.
- **Where the reason is kept:** on the approval's case event (`kyc_case_events.note`, D1229), with who granted it and when. The `kyc_bypass_granted` activity row says "reason recorded on the case" and never copies the words.
- **A reviewed submission's approval is unchanged:** it still takes an optional note.
- **The gates are as before:** an admin, a recent step-up, the branch not suspended, and a case with HQ decided by HQ alone.
- **The console:** until D1306's dialog (ACC7 D) replaces it, All accounts' Grant full access asks for the reason in a prompt, in place of the confirm it had. Without that, the button would only ever be refused.

### 2. The bulk resend of verification (ACC7 J)

`POST /api/admin/accounts/resend-verification` `{ user_ids, dry_run? }`, any admin.

- **Capped:** at most 50 accounts at a time (`RESEND_CAP`). Over that is 400 `too_many_accounts`, and nothing is sent.
- **Skipped and counted:**
  - a verified account;
  - a deactivated one;
  - an id that is no account;
  - for a plain Admin, another administrator's account. That record is the Super Admin's (D133), and a Super Admin reaches it.
- **The dry run** answers the dialog's counts ("1 is already verified and is skipped. Send 2 emails") and sends nothing.
- **Every send is the single resend's.** `services/verificationResend.ts` now holds what `POST /api/admin/users/:user_id/resend-verification` did, and both routes call it:
  - a fresh hashed token with a 24-hour lifetime;
  - the email, best-effort;
  - the `admin_resent_verification` row, which names the account by id and email hash.
  - One difference: a failed send logs the error's name, not the error, so no address reaches a log.
- **The audit:** each account's own row, plus one `admin_bulk_resent_verification` row with the counts. Nothing logged holds a name or an address.
- If nothing is left to send, the answer is 409 `nothing_to_send`, with the counts.

- **Not a branch freeze.** None of `/api/admin/accounts` is refused on a suspended branch (`lib/branchFreeze.js` lists every write that is):
  - the single resend never was, so the bulk resend is not;
  - the export is a read, and the freeze never gates a read;
  - a saved view is an admin's own setting.

### 3. Saved views (ACC3, migration 639 `account_saved_views`)

| Route | What |
|---|---|
| `GET /api/admin/accounts/views` | The caller's own views and the studio's, each with who saved it and whether the caller may change it |
| `POST /api/admin/accounts/views` | `{ name, scope: 'admin' \| 'studio', query }` |
| `PUT /api/admin/accounts/views/:uid` | `{ name?, query? }` |
| `DELETE /api/admin/accounts/views/:uid` | The view |

- **Who sees a view is stated by its creator:**
  - `admin` is only them;
  - `studio` is every admin of this studio. A studio is its own database (D106), so it is every admin on this deployment and never another studio's.
- **Who changes it:** the admin who saved it. A studio view may also be changed by a Super Admin. Another admin's own view is the same 404 as none.
- **The query** holds only the list's own filter, sort and column keys (`VIEW_KEYS`, D1300's list), each a short string or a short list of them. It is stored as JSON and never as a SQL fragment, and any other key is refused.
- **Names are unique per reader:** an admin's own views by name, and the studio's by name, without regard to case.
- At most 30 views per admin.

### 4. The accounts export (ACC7 K)

`POST /api/admin/accounts/export` `{ reason, user_ids? | q?, columns? }`, any admin.

- **The reason** is required, 10 to 500 characters.
- **Which accounts:**
  - the selected ones (at most 500);
  - or the list's search, on name or email as `GET /api/admin/users` reads it today;
  - or every account.
  - Over 10,000 rows is refused with a request to narrow it, never cut short.
- **The columns** are the list's own fields only, in the list's words: name, email, account ID, profile ("Operating Partner", "Explorer"), status, email verified, identity check ("Waiting", "Needs information"), limited access, and joined. Any other column is refused.
- **The record comes first.** One `admin_audit_log` row is written before the file is made: `accounts_export`, report type `accounts`, CSV, with the reason, the mode, the search, the row count and the columns. If it cannot be written, there is no file (503 `unrecorded`).
  - HQ's feed lists it under Exports, whose filter reads every `%export%` action.
- **The file:** a cell that starts with a formula character is neutralised.
- **Not built:** D1300's filters. The export reads today's search. When D1300's list read lands, its filter builder is what the export should take, so both answer the same set.

### 5. Who saved an account's notes (ACC6, migration 639 `account_note_saves`)

- **Why a sidecar:** `users` is at D1's column limit (migration 154), so the metadata is a table of its own: one row per account, with who saved, when and the length. It never holds the text, which stays in `users.admin_notes`.
- **The save:** `POST /api/admin/users/:user_id/notes` writes the notes and the metadata in one batch, and answers `notes_saved`.
- **Another administrator's notes are now the Super Admin's**, as their record is (D133): 403 `super_admin_required` for a plain Admin. The route had no such check.
- **The read:** `GET /api/admin/users/:user_id/profile` returns `notes_saved`:
  - who saved and when;
  - or "Not recorded: these notes were saved before who saved them was kept." for notes saved before migration 639;
  - or "No notes saved yet.";
  - or "could not be read" with Try again.
  - No saver is ever guessed, and nothing is backfilled.
