## D753 — Every connector has its own page

**Status:** proposed by S1 on 2026-10-18 for slots S07–S14. Code read on `origin/main` at `0ce63b344`. Since `aba147141`, only #1847 merged: it moved lines in `MercurySheet.jsx` and `mercuryModel.js` and nowhere else this decision cites. D753 is the foundation that D751 (GitHub) and D752 (Mercury for every member) stack on.

### Why

The owner, 2026-10-18 at about 13:30Z: "I want all connectors to have a page with a description, not a right sidebar, then once they're on the connector page, the connection option redirects to the service to connect the service to Axal VC platform like in the example image."

**Today a connector has no address of its own.**
- `/account/connectors` is one section of the Account center (`frontend/src/App.jsx:2480`, `frontend/src/pages/SettingsPage.jsx:507`).
- Every card, Yours row, phone row and Channels button opens a 480px right sheet (`frontend/src/pages/account/ConnectorSheet.jsx:133-142`).
- A view name held in React state chooses what the sheet shows (`AccountConnectors.jsx:340`, `:370`).

**Where the design comes from.**
- **Layout:** the owner's three screenshots of Claude's connector directory: (A) the Discover grid, (B) the filter menu, (C) the connector page.
- **Copy and states only:** the D649 canvases in `design/incoming/` (`Connectors Page.dc.html`, `Connectors · Boards.dc.html`, and `Cycle Action.dc.html` in page mode, `:137-141`). They stay in `incoming/` as content references.
- No new canvas is needed.

### What this supersedes

- **D651, "One sheet, two doors"** (`D651.md:27-34`), for the Connectors page only. Build's "Connect a tool" keeps its lightbox (D686).
- **D686**, the sentence "The Connectors page (`/account/connectors`) keeps its side sheet" (`D686.md:21`).
- **D700 A3m**, "A row opens its sheet" (`D700.md:97`). A row now opens its page.
- **D715's sheet rules** (`D715.md:14`, `:16`, `:75`) now read "page":
  - the Worker's row picks what the page body shows;
  - there is no entity read until `/account/connectors/mercury` mounts;
  - a sign-in return never routes to the Mercury page.
- **D687's sizes, for the page header only:** the tile is 56px, or 48px on a phone. Cards keep 34px.
- **D650's `verified`**, which never had a meaning. Decision 7 gives it one.

### Decisions

#### 1. The address

**The route.**
- The page lives at `/account/connectors/:key`, inside the Account center, with the same left section list and rail.
- It is routed beside `/account/:section` (`App.jsx:2480`), for the same six roles.

**What `:key` can be.**
- It is the hub's catalogue key:
  - a registry key;
  - one of the first-party keys: `google`, `microsoft`, `linkedin`;
  - after task C1, one of the channel keys: `whatsapp`, `telegram`.
- `google_calendar` redirects (replace) to `google`, and `microsoft_365` to `microsoft` (`REGISTRY_ALIAS`, `connectorsModel.js:49`).
- A key is drawn only if the catalogue holds it, as D651 requires for crafted links.

**The key survives canonicalisation.** `accountPathFor` (`accountPhone.js:150-154`) gains a `key` and returns `/account/connectors/<key>`. The canonicalising effect (`SettingsPage.jsx:285-290`) therefore no longer drops the key. `ConnectorsTab` (`SettingsPage.jsx:507`, `:4521-4544`) renders the page when a key is present.

**Page states.**
- An unknown key reads `No connector called "<key>".`, with Request it and a link back.
- A key withheld by audience (Mercury for a role that has none) reads `notOfferedSentence`.
- A 403 on `/available` (for example an `exploring` viewer) draws the hub's forbidden state with the Worker's sentence.
- A failed read draws Unreadable, with Retry.

**The hub's tab is in the address.** The hub uses `/account/connectors?tab=yours|discover`, so "← Connectors" returns to the tab the reader came from.

**Old links.** The sheet never had an address, so only these doors move:
- `/integrations?…` and `/account/integrations?…` go through `connectorsRedirect` (`connectorsModel.js:428-430`):
  - when `oauthReturn(search)` names a key, the reader goes to `/account/connectors/<key>?<the same query>`;
  - **Mercury is the exception**: it stays on the hub and the query is stripped (D715 decision 3);
  - anything else goes to the hub, as today.
- A bookmarked `/account/connectors?oauth=…`: the hub navigates (replace) to the page, with the same Mercury exception (`AccountConnectors.jsx:345-353`).
- Worker links go through one helper, `connectorPagePath(key)`:
  - `routes/crunchbase.ts:47` and `:76`, `connect_path` → `/account/connectors/crunchbase`;
  - `services/onboardingChecklist.ts:88`, `:91` and `:109` → `/stripe`, `/mercury` and `/hubspot`.
- Frontend links:
  - `ProjectDetail.jsx:615` → crunchbase;
  - `CapTablePage.jsx:947` and `:992` → carta;
  - `SettingsPage.jsx:3158` → slack;
  - `PartnerProfilesConsole.jsx:475` → docusign;
  - `EadwynComposer.jsx:27` and `:67-68`: Browse → `?tab=discover`.
- Unchanged:
  - Build's `?tool=<key>` (`connectorsModel.js:539-560`);
  - the `#interview-channels` and `#ai-assistants` anchors (`channelsModel.js:30`, `assistantSession.js:19`);
  - the user-menu link (`App.jsx:768`).

**The Worker's sign-in return does not change.**
- `returnBase` (`routes/integrations.ts:1315-1317`), the calendar return and the LinkedIn return still land on `/integrations?…`. The SPA's redirect carries the reader on to the page.
- So the source mutants in `build_connectors_d686.test.ts:102-196` stand, and so does `connectors_page_d651.test.mjs:204-219`.
- D751's `reason=not_configured` passes through unchanged.

#### 4. The data contract

It is agreed here so that W1, F1 and F6 can start at once. There are two reads.

**(a) `GET /api/connectors/available`** (the same router answers `/api/integrations/available`, `index.ts:1188-1189`).
- **Only additive fields.** Every existing field is unchanged, because D686's lightbox also reads it.
- **Each item gains:**

```
tagline: string                   // at most 120 characters: the card line and the header tagline
made_by: { name: 'Axal VC' }
service: { name: string, href: string | null }   // the company that runs the service
sign_in: { kind: 'oauth' | 'oauth_or_token' | 'key' | 'first_party' | 'entity' | 'channel',
           label: string, key_help_href: string | null }
added: 'YYYY-MM' | null           // the month it became connectable
verified_on: 'YYYY-MM-DD' | null  // and `verified` is sent as verified_on !== null
read_only: boolean                // true when it has no tool with access 'write'
page_key: string                  // the address key: 'google' for google_calendar
page_href: string                 // '/account/connectors/<page_key>'
configured: boolean | null        // D751's field: D753 fixes the name and type only, D751 computes it
```

- **The answer gains, at the top level:**
  - `category_order: string[]`;
  - `first_party: [ LinkedIn's card fields ]`.

**(b) A new read, `GET /api/connectors/directory/:key`** (alias `/api/integrations/directory/:key`).

Rules:
- It is registered beside `/suggestions` (`integrations.ts:305`), above `/:key` (`:365`). It has two segments, so it collides with no `/:uid/<literal>` route.
- It checks `requireAuth` and `ensureRole`, as `/available` does (`:193-194`).
- It needs no active company.
- It answers 404 `unknown_provider` for an unknown key or a `none` audience, the same rule as `:372-373`.
- It takes page keys and registry keys. `google_calendar` answers with `page_key: 'google'`.
- **It is descriptive only.** The viewer's connection stays on the reads that exist (`useConnectors()`, `ConnectorSheet.jsx:52-93`), so the hub and the page can never disagree about what is connected.

The answer:

```
{ ok: true, connector: {
  key, page_key, display_name, tagline, long_description: string[],
  category, status, tier, auth_type, supports_pat, locked_for_user,
  made_by, service, sign_in, added, verified, verified_on, read_only,
  tools: [{ name, label, access: 'read'|'write'|'account'|'inbound', what, lands_in: string|null }],
  prompts: [{ name, ask, proposes: string|null }], prompts_reason: string|null,
  permissions, pulls, sends, feeds, feed_modules,
  endpoints: { sign_in: string|null, api: string|null },
  links: { help, developer_docs, support, privacy },   // each https: or null
  trust: { built_by: 'Axal VC', reads: string[], writes: string[], moves_money: boolean, sentence: string },
  configured /* D751 */ } }
```

**The frontend method** is `connectorsApi.page(key)`, in `frontend/src/lib/api/connectors.js` (D527). It lands in the same PR as its route (W2), so `npm run test:drift` holds.

**Where the data lives: a new module, `cloudflare-worker/src/integrations/connectorPages.ts`.**
- It holds:
  - `CONNECTOR_PAGES`, keyed by registry key;
  - `FIRST_PARTY_PAGES.linkedin`;
  - `CHANNEL_PAGES` (C1);
  - Mercury's variants, `{ entity, personal: { founder, partner } }`;
  - `CATEGORY_ORDER`, `trustFor`, `pageDescriptor` and `connectorPagePath`.
- Each tool also carries an internal `calls` fragment, used only by the guard test and never sent.
- `registry.ts` re-exports it in one line. It imports no provider module, because providers import the registry.
- **It never edits `PERSONAL_MERCURY`** (`registry.ts:486-497`), which D752 owns. Mercury's card words (description, permissions, feeds) stay there. Mercury's page-only fields live in `connectorPages.ts`.

**LinkedIn stays out of `REGISTRY`.** A `linkedin` row would replace the first-party row at `buildCatalogue` (`connectorsModel.js:160-161`) and read as unavailable.

**After F7, the frontend holds no descriptive copy.**
- `FIRST_PARTY` (`connectorsModel.js:70-89`) keeps only `key`, `display_name`, `first_party`, `auth_type`, `status` and `tier`.
- `by: p.by || p.display_name` (`:152`) becomes `made_by.name`.
- `CATEGORY_ORDER` (`:35`) becomes the Worker's `category_order`. Build's `BUILD_CATEGORY_ORDER` stays.
- `ALIAS_FIELDS` (`:50`) gains the new fields.

**No migration, no new table.** The page data is static registry data.

#### 5. Tools and Prompts, as Axal VC means them

**Tools** are what Axal VC reads or does through the connector, read off each implementation: its scopes, and the calls it makes.
- Each tool has a `name` (snake_case, a stable id that is not drawn), a `label` (plain words, drawn), and an access value: read, write, account or inbound.
- **Read-only**, writing nothing to the member's account:
  - GitHub (`providers/github.ts:99-119`, `:227`, `:284-299`);
  - Mercury (`services/mercury/client.ts:100-128`; GET only);
  - Stripe (`providers/stripe.ts:152-213`, `:680`);
  - Carta (`providers/carta.ts:330-521`);
  - Crunchbase (`providers/crunchbase.ts:166-204`);
  - Calendly (`providers/calendly.ts:240-621`); its only writes are its own webhook subscription, which is plumbing (account);
  - LinkedIn (`routes/linkedin.ts:37`; identity only).
- **Writes:**
  - HubSpot: deals, companies and contacts (`providers/hubspot.ts:404-502`);
  - Salesforce (coming soon);
  - DocuSign: `send_envelope` (`providers/docusign.ts:375`, `:469`);
  - Slack: `post_message`, with no read (`services/notify.ts:225`);
  - Zoom: meetings (`services/channels/zoom.ts:407-434`);
  - Google Calendar (`services/calendar.ts:952-991`; `googleMeet.ts:154`);
  - Microsoft 365 (`calendar.ts:1021-1060`).
- **Figma and Affinity have no tools**, because no implementation is registered.
- **`capabilities` is never drawn as Tools.** The registry calls them "human-readable chips" (`registry.ts:43`), and some claim more than the code does. DocuSign's "Template library" (`registry.ts:334`) is Axal's own templates (`docusign.ts:338-339`).
- **The guard** is `cloudflare-worker/test/connector_pages_d753.test.ts`:
  - every tool's `calls` fragment occurs in its provider's source;
  - a provider with no outbound write declares no `write` tool;
  - a provider that writes declares at least one;
  - `read_only` equals "no write tool".

**Prompts** are example asks for Eadwyn that the code can answer.
- Only keys in `CONNECTOR_READERS` can have them (`services/eadwynReaders.ts:132`).
- `proposes` is allowed only for `SEND_TARGETS` (`services/eadwynConnectors.ts:121-130`).
- **v1 has prompts for three connectors:**
  - GitHub: `fed_by_github`, `roadmap_from_issues`;
  - HubSpot: `deal_stages`, `deal_amounts`, plus the proposals `send_company` and `update_deal` ("Nothing is sent until you press Send");
  - Stripe: `mrr_arr`, `churn_customers`.
- Salesforce is coming soon, so it gets `prompts: []`. Every other page draws no Prompts section.
- **Prompts are labels.** Turning a chip into a filled-in ask in the rail is AIRail's work (D720–D748). D753 draws no "Try in Eadwyn" door: `EadwynComposer.jsx` is mounted nowhere (`documentation/architecture/ROUTE_MAP.md:196`).

**Google's Gmail sentence is untrue, so it changes.**
- The permission sentence "Read Gmail messages linked to invitations." (`registry.ts:475`) does not match the code. No code reads Gmail with a member's token: every `gmail/v1` call is `messages/send`, on the house token (`services/email.ts:330`).
- W1 rewords it to "Gmail (read-only) is asked for at sign-in; Axal VC does not read your Gmail." The permission count is unchanged, so `connectors_d650.test.ts:82-84` holds. No Gmail tool is drawn.
- Dropping the scope (`services/calendar.ts:81-87`) forces every member to consent again, so it is a separate decision, not D753's.

#### 6. Connect

A pure `pageAction(p, flow)` in `connectorPageModel.js` picks the header's one action.

**Connectors with a sign-in.**
- The button reads "Connect to Axal VC". Its accessible name is "Connect <Name> to Axal VC".
- It calls `GET /api/connectors/oauth/:provider/start` (`integrations.ts:1240-1306`), then `window.location.assign(authorize_url)`. That sends the browser to the service's own sign-in.
- First-party connectors use their own start routes:
  - `/api/calendar/google/start` (`calendar.ts:808-810`);
  - `/api/calendar/microsoft/start` (`:1125-1126`);
  - `POST /api/linkedin/oauth/start` (`linkedin.ts:147`).

**Connectors that take a key or token.** These are Mercury's Read Only token, Crunchbase's key, HubSpot's private-app token and Calendly's personal token.
- There is no sign-in to redirect to. Connect opens the key form inline, under the band.
- The form carries a link, "Get one at <Service> ↗" (`sign_in.key_help_href`), that opens the service's own token page.
- The form posts to `POST /api/connectors/connect` (`integrations.ts:428-596`). Mercury's read-only confirmation (D715) is kept.

**Options on the split chevron.**
- Salesforce: Production or Sandbox.
- DocuSign: Production or Demo; `demo=0|1` is always sent.
- "Use a personal access token", when `supports_pat` is set.
- HubSpot: "Sign in with HubSpot instead".

**While starting**, the button reads "Opening <Name>…", is disabled, and sets `aria-busy`.

**The return.**
1. The service sends the browser to `/integrations?oauth=…&provider=<key>`, or `?google=`, `?microsoft=`, `?linkedin=`.
2. The SPA redirects to `/account/connectors/<key>?…`.
3. The page reads `oauthReturn` only when the return's key is the page's own. It shows the notice and strips the query (replace).
4. The fresh catalogue read draws the connected state.

GitHub's `oauth=ok` scrolls to and focuses `#repositories`.

**When connected.**
- The header shows a status pill (Connected, Needs attention or Paused) and "Manage ▾", which holds:
  - Sync now;
  - Replace key or token;
  - Reconnect;
  - Disconnect, which confirms with `disconnectNote` (`connectorsModel.js:640-648`), or Mercury's own notes.
- The primary action is "Reconnect" while the connection needs attention.

**The other states.**
- **Coming soon:** "Notify me", then "We'll tell you".
- **Locked by the plan:** a tier pill and "See plans", to `/account/billing`.
- **Not available here:** a disabled button with D751's words.
- **Entity Mercury:** no header action. Each entity has Connect, Replace and Disconnect in the body (D710, D715).

#### 7. Made by, Service, Verified, and the trust notice

**MADE BY is "Axal VC" on every page and every card.** Axal VC built and runs every connector. Today's card says "by HubSpot" (`connectorsModel.js:152`), which is untrue. **SERVICE** is the company that runs the service, linked ↗.

**Verified** means that an Axal VC live connect on production passed, and was recorded with its date in `verified_on`.
- No such check is recorded today. `PRODUCTION.md` lists secrets, not checks, and D650 gave the flag no meaning.
- So W1 gives the six rows marked `verified: true` today (`registry.ts:464-477`) a null date, and **their badges disappear until the owner records a check.**
- **The owner can override this:** post the date of a live connect on the D753 issue, and any later PR records it.
- The badge's accessible name says what it means.

**The trust notice is the Worker's `trust.sentence`, built from the tools. Its parts:**
1. "Axal VC built and runs this connector. It reads <reads> from <Service>."
2. Then one of:
   - "It never writes to <Service>.";
   - "It writes <writes>, only when you confirm.";
   - "It writes <writes> automatically."
3. Where it is true: "Nothing it does can move money."
4. "It asks <Service> only for the access listed under What Axal VC can access."

**`moves_money` is false on every row today.** Stripe's grant is `read_only` (`registry.ts:368`), and Mercury's client is GET only (`providers/mercury.ts:1-14`). The guard allows "never writes" only when there is no write tool.

#### 10. Accessibility

**Structure.**
- One h1, the connector's name. Each section is an h2.
- `document.title` is "<Name> · Connectors · Axal VC".
- The back link is a real link, labelled "Back to Connectors".

**The badge** is `role="img"`, with `aria-label` "Verified" and a `<title>` that gives its meaning and date.

**The split chevron.**
- It is its own button, with `aria-haspopup="menu"`, `aria-expanded`, and the label "More ways to connect <Name>".
- Its items are `menuitemradio`. Arrow keys, Home and End move between them. Escape closes the menu and returns focus.
- On a phone it is a `fieldset` of radios with a `legend`.

**Notices.**
- A success or neutral notice is `role="status"`; a failure is `role="alert"`.
- After a sign-in return, focus moves once to the notice heading (`tabIndex=-1`).

**The key form.**
- Inputs are labelled and use `autocomplete="off"`.
- `aria-describedby` points at the help text.
- An error sets `aria-invalid` and is tied to its message.

**Tools and prompts.**
- Each is a `<ul>` of static chips.
- A tool's `what` is its accessible description.

**The trust notice** is `role="note"`; its icon is `aria-hidden`.

**Details** are a `<dl>`. Each external link opens in a new tab with `rel="noopener noreferrer"`, and a visually hidden "(opens in a new tab)".
