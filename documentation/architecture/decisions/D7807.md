## D7807 — Needs reconfirmation is a whole-list count from the Worker (#7807)

- **Status:** built 2026-11-25. Found while building #7516 (PR #7568, D7516); filed on the owner's answer (A) of 2026-11-20.
- **Builds on:** D4689 (every Expertise figure is over the whole list), D4670 (`consentState` and `needs_reconfirmation`), D4825 (`proofCardState`, the card's one state), D7516 (the overview's Verification dimension), D5129 (Unavailable, never a zero).
- **No migration, no new route, no client method.** `GET /api/advisors/me/proof` (and its `/api/mentors` mount) gains one field; `frontend/src/lib/api/advisorProof.js` is unchanged.

### The problem

The Proof zone's Needs reconfirmation tile and the Expertise overview's Verification line counted the rows they held, so they showed a figure only while the whole proof list fit on one page (the `whole` guard in `ProofZone.jsx`, `wholePage` in `overviewModel.js`). With more claims than one page the tile read Not recorded and the overview left the figure out, because a count of one page would understate it.

### What changed

1. **The Worker counts it** (`cloudflare-worker/src/routes/advisors_proof.ts`). `counts.needs_reconfirmation` is the number of the advisor's claims whose card reads Needs reconfirmation, over the whole list: no live confirmation, no ask awaiting an answer, and at least one consent that was given and not withdrawn or cancelled but is not about the claim as it now reads (confirmed before D4670, or the claim changed since). That is `proofCardState`'s rule (`proofModel.js`), so the tile agrees with the cards. It is one more `SUM` in the same aggregate read as `total`, `attested` and `awaiting`: the read now computes three per-claim flags in a subquery and sums them, and the "about the claim as it now reads" test is the same `json_extract` comparison the `attested` flag already used.
2. **Never 0 for unread.** The `SUM` is wrapped in `COALESCE(…, 0)`, so an advisor with no claims reads a real `0`. A count that did not come back is `null` (`countOrNull`), never `0`. A failed aggregate read still fails the route (500), as #4689 decided for every Expertise list: no page of zeros.
3. **The tile reads it** (`frontend/src/pages/advisor/expertise/ProofZone.jsx`). The tile shows `counts.needs_reconfirmation` on any page size, and Unavailable (#5129's `StateChip`) when it is null or absent. It no longer counts the page.
4. **The overview reads it** (`frontend/src/pages/advisor/expertise/overviewModel.js`). The Verification line says "N need reconfirmation" from the same count, on any page size, and leaves it out when the count is null, as the file does for every figure it cannot state. `ExpertiseOverview.jsx` draws the model and counts nothing itself.

### Departures

- **One rule for both surfaces.** Before, the overview counted a claim with a stale consent even when a new ask was out, while the tile (by card state) did not. Both now use the card's rule: a claim already asked again reads Awaiting, and is not counted here.
- **The Next step stays a page fact.** The overview's "Ask {attester} to reconfirm …" step names one claim from the rows it holds (`reconfirmations`), which is a choice of a row, not a count. It is unchanged.
