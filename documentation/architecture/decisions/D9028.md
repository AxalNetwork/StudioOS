## D9028 — Microsoft calendar: store the rotated refresh token, refuse a grant without Calendars.ReadWrite (#9028)

- **Status:** built by S12 on #9028, 2026-11-27. Findings 2 and 3 of `documentation/operations/TEAMS_ENTRA_5809.md` (#5809).
- **Chosen by:** the issue's scope, filed from the S1 coordinator audit of 2026-11-27. The owner was told on 2026-11-15 that each finding "can become a small code change".

### The problem

1. `refreshMicrosoftAccessToken` returned only `access_token`. Microsoft may return a new `refresh_token` on any refresh, and the Worker threw it away, so every refresh kept spending the token saved at connect. Once that token lapsed, the member saw `teams_reconnect` (or `connection_refused` on the calendar) and had to connect again.
2. The Microsoft callback stored whatever `scope` the grant carried. A consent without `Calendars.ReadWrite` counted as connected, and only failed later, when a copy or a Teams meeting needed the permission.

### What was decided

- **One refresh, and it stores.** `services/calendar.ts` keeps the token-endpoint call private (`refreshMicrosoftTokens`, which returns the access token and the rotated refresh token or null). The only exported refresh is `refreshMicrosoftAccessTokenFor(env, userId, tok)`:
  - a refresh token in the answer that differs from the one spent is encrypted with `encryptString` and written to that member's `microsoft_oauth_tokens.refresh_token`, with `updated_at`;
  - no refresh token (or the same one) leaves the row as it was, except that a legacy plaintext row is rolled forward to ciphertext, as each caller used to do itself;
  - a refused refresh still throws `refresh_failed:<status>`, so every caller's refusal mapping (`teams_reconnect`, `connection_refused`, `reconnect`) is unchanged.
  The old export is gone, so no caller can refresh without storing. The six call sites now use the helper: `syncUserToMicrosoft`, the push, cancellation and disconnect paths in `services/calendar/sync.ts`, the external reader in `services/calendar/externalReaders.ts`, and the Teams meeting call in `services/channels/teamsMeet.ts`. Their own plaintext roll-forward is now Google-only, because writing the old token back after a rotation would undo the rotation.
- **Storing a rotation never fails the member's action.** An encryption or write error is logged by name and swallowed: the access token in hand still works, and the stored token stays the last one stored.
- **The callback refuses a grant without the permission.** `microsoftGrantHasCalendarScope` reads `Calendars.ReadWrite` bare or under `https://graph.microsoft.com/`, case-insensitively, as a whole scope (`Calendars.ReadWrite.Shared` alone is not it). Without it, the callback redirects through `failureRedirect` with `calendar_scope_missing`, named after Google's `meet_scope_missing`, and writes nothing; an existing connection is left as it was. The Calendar page has a sentence for the code.
- **Google is unchanged.**

### Not decided here

- Two refreshes for the same member at the same moment can each receive a rotation; the last write wins. Microsoft does not revoke an earlier refresh token when it issues a new one, so either stored token keeps working until its own lifetime ends.
- A member connected before this change keeps the token saved at connect until Microsoft next rotates it. The owner's live Entra proof on #5809 stays separate.
