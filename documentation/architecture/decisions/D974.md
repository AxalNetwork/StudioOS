### 1. Three states, not two

Until now `DELETE /api/admin/network-profiles/:id` set `is_active = 0`, the same act as hiding. A row is now in exactly one of three states:

| State | Columns | The deck | The public photo proxy | The working list |
| --- | --- | --- | --- | --- |
| shown | `is_active = 1`, `archived_at` NULL | reads it | serves it | listed |
| hidden | `is_active = 0`, `archived_at` NULL | drops it | refuses it | listed |
| archived | `archived_at` set, `is_active = 0` | drops it | refuses it | listed only with `?state=archived` |

**Archiving keeps `is_active = 0`.** So `loadNetworkProfiles` (the deck) and `network_public.ts`, which both read `is_active = 1`, needed no change and drop an archived row exactly as before.

**Migration 551 sets no `archived_at`**, so every row hidden before it stays hidden. The test proves that on a roster with two hidden rows.

**The acts:**

| Act | Request | What happens |
| --- | --- | --- |
| Hide | `PUT /:id { is_active: false }` | the row is hidden |
| Show | `PUT /:id { is_active: true }` | the row is shown |
| Archive | `POST /:id/archive` | the row is archived. `DELETE /:id`, which the current console calls, now archives too |
| Restore | `POST /:id/restore` | the row comes back **hidden**; reaching the deck again is the separate act of showing it |

**What is refused:**
- archiving a row that is already archived: 409;
- restoring a row that is not archived: 409;
- showing or hiding an archived row: 409, "Restore this profile before you show or hide it". A stray `is_active` can never put an archived row back on the deck.

### 2. The columns (migration 551)

| Column | Holds |
| --- | --- |
| `linked_user_id` | the member account the person signs in with. A write names only an active `users` row; anything else is 400 `invalid_linked_user`. NULL is a roster row with no account. |
| `created_by` | the admin who added the row. NULL for every row from before 551, and read as null, never guessed. |
| `archived_at` | when it was archived, as D1's UTC stamp. |

An index covers `linked_user_id`. `ensureNetworkProfilesSchema` adds the three columns where 551 has not run, as it already did for `company`. That also keeps `check-schema-pair-drift` green.

### 3. The list, `GET /api/admin/network-profiles`

**Parameters:**
- `state`: `shown`, `hidden` or `archived`. With no state, the list holds shown and hidden rows. Anything else is 400.
- `q`: up to 100 characters, matched against name, role and company. LIKE's own `%` and `_` are escaped, so "50%" finds "50%".
- `limit`: 1–500, default 200. The response says `truncated` when more rows matched.

The query is written out once; each state is switched on by a bound flag, never spliced in.

**Each row carries:**
- `state` and `archived_at`;
- `linked_user` and `created_by`, each `{ id, name }` or null;
- `deck_reach`.

**Counts.** `counts` gives the whole roster's shown, hidden and archived totals, whatever the filter.

**Deck reach** is one of `on_slide`, `name_only`, `counted` or `not_on_deck`. It is `deckRosterReach`, D214's one rule, over the rows the deck itself reads: `is_active = 1` in the deck's own order (`display_order`, `name`, `id`).
- It is read over the whole roster, so a filter or a limit never moves a row's reach.
- The test holds the six `on_slide` rows equal to the first six `loadNetworkProfiles` returns.

**`photo_r2_key` is gone from the payload.** The R2 key stays in the Worker. Each row gives:
- `has_photo`;
- `photo_url`, the admin read below;
- `public_photo_url`, the public proxy, only while the row is shown.

The photo upload's answer gives `photo_url` instead of the key.

### 4. The photo read for hidden and archived rows

`GET /api/admin/network-profiles/:id/photo` serves the photo of a row in any state, to an admin only.
- It answers with `Cache-Control: private, no-store` and `nosniff`.
- It answers 404 for no row or no photo, and 503 without the R2 binding.
- The HQ console reads it through its signed-in cookie, as an `<img>` does.

The public proxy is unchanged and still serves shown rows only.

### 5. The audit log

Every write goes through `logAdminAction` (D159), so it lands in `admin_audit_log`, which HQ's governance feed reads, as well as in `activity_logs`. Each act has its own name:
- `network_profile_created`
- `network_profile_updated`
- `network_profile_hidden`
- `network_profile_shown`
- `network_profile_archived`
- `network_profile_restored`
- `network_profile_photo_uploaded`
- `network_profiles_reordered`

**What a row records:**
- a hide or show is logged only when the state changes;
- an edit that only toggles `is_active` writes no `updated` row;
- the linked member, when there is one, is the row's `target_user_id`, which the feed shows as its Target;
- no email and no R2 key is written into the details.

### 6. The client

`adminNetworkProfiles` in `frontend/src/lib/api.js`:
- `list()` takes `{ state, q, limit }`; with no argument it behaves as before;
- `archive(id)` and `restore(id)` are new.

**What the current console does now:**
- its hide and show toggle (`PUT is_active`) works as before;
- its Archive button (`DELETE`) now archives, so the row leaves the default list;
- restoring from the page belongs to the page part of #2369, which draws AP7–AP9.
