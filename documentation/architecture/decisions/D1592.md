## D1592 — A company's own documents: read, upload and download

- **Status:** built by S09 from S1's specification on #3860 (Portfolio canvas #3696: PF2 Documents and PF7c).
- **Builds on:**
  - D639, the one document access rule (`canAccessFounderResource`);
  - D1136 and D1137, the member-editable company record and its archive;
  - the 83(b) receipt upload (`routes/legal_83b.ts`), whose checks and order this copies.
- **Migration:** `748_company_documents.sql`.

### The question

The company page draws a Documents card with four rows (Certificate of incorporation, Bylaws, Tax ID letter, Registered agent agreement), with the company's ventures' documents below them. There was no store for it. Every `documents` row hung off a project, `GET /api/legal/documents` answered only a project's founder, and nothing accepted an upload for a company.

### What was decided

**A company document is a `documents` row with `company_id` set and `project_id` NULL.**
- Migration 748 adds `company_id`, `uploaded_by` and a partial index on `(company_id, doc_type, created_at)`.
- The row has no project, so it has no founder. `canAccessFounderResource` refuses a null founder to everyone but an admin, so the old `GET /api/legal/documents` read never shows a company document to a non-admin. That is kept on purpose, and a test holds it.

**The kinds** (`doc_type`) are `certificate_of_incorporation`, `bylaws`, `tax_id_letter`, `registered_agent_agreement` and `other`.

**The routes** (`routes/company_documents.ts`, mounted at `/api` before `companyRoutes`):

| Method, path | Gate | Answer |
|---|---|---|
| `GET /api/company/:uid/documents` | member | `{ slots, other, ventures, can_upload }` |
| `POST /api/company/:uid/documents` | editor | multipart `file`, `kind`, optional `title` → the new document (201) |
| `GET /api/company/:uid/documents/:docUid/file` | member | the stored bytes, with the stored type, as an attachment |

- **The gates** are `viewerIsMember` and `canEdit`. They moved from `company.ts` to `services/companyAccess.ts` unchanged, and both route files import them.
- A non-member and an unknown uid get the same 404.
- Upload refusals: 400 `file_required`, `file_empty`, `file_type_invalid` and `kind_invalid`; 413 `file_too_large` (over 10 MB); 403 `not_editor`; 409 `archived`; 503 `storage_unconfigured`; 502 `storage_failed`.
- `can_upload` is true for an editor of a company that is not archived.

**A document as a reader sees it:** `{ uid, kind, title, status, created_at, uploaded_by: { name } | null, has_file }`. No answer carries `content`, the R2 key, the sha256 or an email.

**The slots.**
- There is one slot per named kind, holding the newest company row of that kind.
- `earlier` counts the older rows of that kind.
- Nothing is deleted: a new upload becomes the slot's document and the older ones stay.
- `other` lists every company document that is not a named kind, newest first.

**The ventures.**
- They are the company's projects with `deleted_at IS NULL`.
- Each lists only the documents the caller's existing read allows: `canAccessFounderResource`, D639, unchanged. A venture with none is left out.
- This does not widen who reads a venture's documents. **Owner call, open:** whether company editors should read their ventures' documents under #3697's authority rule (2026-10-31) is a separate decision.

**Each block fails alone.**
- `other` and `ventures` are `{ available: true, value }` or `{ available: false, reason }`, and a failed read never blanks the others.
- `slots` is the card itself and is a plain list, as the specification's shape has it. If its own read fails, the route answers 503 `documents_unreadable` rather than drawing four empty rows as "none".

**Storage.**
- The bytes go to R2 `FILES` under `company-documents/<company uid>/<random uuid>`, before the row is written. A failed put writes no row.
- The type is decided by the file's first bytes (PDF, JPEG or PNG). A declared type outside those three is refused as well.
- The row holds `{ kind: 'company_document', r2_key, content_type, size, sha256 }` in `content`, with `status` `generated`, `template_name` `company_upload` and `uploaded_by` set to the caller.
- A download answers `Content-Disposition: attachment`, `nosniff` and `no-store`.

**The client** is `frontend/src/lib/api/companyDocuments.js` (`companyDocumentsApi.list`, `.upload` and `.download`), re-exported by one line in `api.js` (D527). S1's `CompanyPage.jsx` Documents card reads it.

### Verified

- `cloudflare-worker/test/company_documents_d1592.test.ts`, on real SQLite with migrations 597 and 748 applied, covers:
  - the gates;
  - the upload order and every refusal;
  - the slots and `earlier`;
  - the ventures' rule and a trashed venture;
  - a failed ventures read leaving the slots readable;
  - nothing stored leaving the Worker, and the legal list unchanged;
  - downloads.
- `frontend/test/company_documents_api_d1592.test.mjs` covers the client's paths, methods and `FormData`.
- The mutation checks are listed in the PR.

### CI follow-up: shared company gate assertions

The existing carry and company-settings frontend tests now inspect
`services/companyAccess.ts` for the edit-role and primary-admin rules, and
assert that `routes/company.ts` imports the shared gate. The previous tests
looked for the moved helper's body inside the route. Role parity with the UI
and the route's use of `canEdit` remain checked; this repair changes no
application authorization behavior.

The R2 writer inventory names company legal-record uploads explicitly: the
existing `documents` store is not among D1169's measured storage areas. This
classification adds no quota exemption to a counted store and changes no
quota behavior. The writer remains covered by the file-type, size, editor,
archival and R2-before-row regression tests.
