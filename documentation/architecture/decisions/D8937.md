## D8937 — The migration runner checks a pending file's added columns before it replays them (#8937)

**Decided.** In apply mode, `scripts/migrate-d1.mjs` checks each pending file that is not safe to re-run, before it executes the file. It reads the file's `ALTER TABLE … ADD COLUMN` statements and asks the target, fresh for each file, whether those columns already exist (`presentAddColumns` in `scripts/lib/migrationPlan.mjs`).

| What the target holds | What the runner does |
|---|---|
| None of the added columns | Applies the file as written, as before. |
| All of them, and the rest of the file is safe to re-run (`IF NOT EXISTS`, `INSERT OR IGNORE` and the like) | Runs the file without those `ALTER`s, records it in the ledger and says so in the log. |
| Some but not all, or all of them but the rest is not safe to re-run | Stops with an error that names the columns present and the columns missing. A person resolves it (DEPLOY.md §4). |

A file that drops or renames a table is always applied as written. A rebuild replaces the table whose columns it adds, so their presence proves nothing.

**Why.** Runtime DDL (`runSchemaBootstrap`; #5343 is moving it off the request path) can add a migration's columns before the migration reaches a target. On 2026-11-27, production's Worker had been bootstrapping `market_intel_rows`' six D7707 columns while every deploy failed for other reasons. When a deploy finally reached the migration step, it stopped on `202611191833_7707_market_intel_row_dates_runs.sql` with `duplicate column name: observed_period` (run 45997731476, #8317). It would have stopped there on every later deploy too, although the file's columns, table and index were all present. A read-only check found it the only pending file in that state; the other 22 pending `ADD COLUMN` files add columns production lacks.

**Rejected.**
- **A one-off ledger row inserted by hand:** it is a manual production write, and the next file in the same state fails the same way.
- **`--baseline`:** it marks *every* pending file that is not safe to re-run without executing it, including the 22 whose columns are genuinely missing. `--verify-marked` would have to un-mark them afterwards.

**Not changed.** Baseline and bootstrap keep their own rules. A file whose added columns are all new runs exactly as before. The ledger row is the ordinary applied row: the runner verified the columns rather than assuming them, which is the difference from a baseline mark.
