## D5316 — The three Practice v2 facts the Worker did not store: end reason, Ready, Included (#5316)

- **Status:** built for #5316, 2026-11-11.
- **Builds on:** D4874 ("Backend required": the three fields the Practice v2
  canvas draws), D4695 / D4692 (the engagement graph and the booking
  lifecycle), D4713 (frozen financial terms), D4704 (one money aggregate).
- **Used by:** #4831 (end reason), #4833 and #4829 (Ready), #4832 and #4834
  (Included). S1's notes on #4829 to #4834 told those builds to leave these
  controls out until a backend field existed; it exists now.
- **Migrations:** `202611110734_5316_advisor_engagement_end_reason.sql`,
  `202611110740_5316_advisor_deliverable_ready.sql`,
  `202611110746_5316_advisor_booking_included.sql`. Each is an `ALTER`, so
  each column is also in `services/advisorStoresSchema.ts`'s lazy bootstrap
  (GOTCHAS: a baselined database records an `ALTER` without running it).

Nothing is inferred for an old row in any of the three. An ended engagement
with no stored reason reads "Not recorded"; a version nobody marked is not
ready; a booking nobody marked is not included, whatever its offer said.

### 1. Why an engagement ended

`advisor_engagements.end_reason`: `'did_not_renew'` ("Did not renew") or
`'other'` ("Ended for another reason"), NULL otherwise. The migration's ALTER
carries a CHECK on the two values.

- `POST /me/engagements/:id/renewal` with `decision: "ended"` now requires
  `end_reason`; without one of the two values it answers **400
  `end_reason_required`** with `allowed`, and writes nothing. It is written in
  the same guarded UPDATE that sets `outcome = 'ended'`.
- **It composes with D4695/D4692's graph rather than adding a path.** The
  reason is asked *after* the replay, conflict, lane and term checks, so a
  retry of a recorded ending (replay, 200), an ending that clashes with a
  recorded renewal (409 `term_decided`), an unsigned row (409) and a moved
  term (409 `cycles_changed`) answer exactly as before. A signed engagement
  still ends only through `/renewal`: signed → renewal_due → ended is still
  refused by `/advance` and still records an outcome. A renewal records no
  reason.
- An unsigned row abandoned through `/advance` has no renewal to lose, so it
  keeps NULL, as its outcome does. The one legacy case D4695 kept — an unsigned
  row that somehow holds an outcome, ended through `/advance` and read as
  `ended` — also gets no reason, and reads "Not recorded".
- Reads: each engagement carries `end_reason` (null unless the outcome is
  `ended`), and `totals.ended_by_reason` is `{ did_not_renew, other,
  not_recorded }`.
- Frontend: the board's ending form asks "Why it ended" and will not send an
  ending without it (the Worker would refuse it); the renewal history shows the
  reason, or "Not recorded". `engagementBoard.js` exports `END_REASON_LABEL`
  and `endReasonLabel`. The rest of the Practice v2 surface is #4831's.

### 2. A deliverable version marked ready to send

`advisor_deliverable_versions.ready_at` and `ready_by_user_id`.

- `POST /me/deliverables/:id/versions/:version/ready` marks it; the first mark
  stands (marking again answers the version with its original stamp and
  account). `DELETE` on the same path takes the mark off. **Neither sends
  anything**: no recipient, no `sent_at`, no message.
- `POST .../send` clears both in the same UPDATE that stamps `sent_at`, so a
  sent version is never also waiting to be sent.
- A sent version cannot be marked or unmarked (409 `already_sent`); one with no
  content cannot be marked (422 `empty_version`, the send's own rule — ready
  means it could be sent as it stands). Another advisor's version is 404.
- Reads: the advisor's list carries `ready_at`, `ready_by_user_id` and
  `ready_by_name` on each version, `ready_version` on each work product (the
  highest unsent version marked ready, beside `state`, not in it — a work
  product can be opened at v1 and ready at v2) and `totals.ready`. The
  client's read (`/received/deliverables`) never carries the mark.
- `api.js`: `markMyAdvisorDeliverableVersionReady(id, version)` and
  `clearMyAdvisorDeliverableVersionReady(id, version)`. No control calls them
  yet; the Ready filter and row are #4833's and #4829's.

### 3. A session included in an engagement

`advisor_bookings.included_at`, `included_by_user_id`, `included_engagement_id`.

- **Why not a fifth `billing_state` value.** Migration 205 put a CHECK on
  `billing_state` in its ALTER, and SQLite cannot change a CHECK without
  rebuilding `advisor_bookings`. The state is recorded beside the column, and
  every advisor read (`advisorMoney`, the ledger lines, the aggregate) reports
  a booking with `included_at` set as `billing_state: 'included'`.
- `PATCH /me/bookings/:id/billing` accepts `billing_state: "included"`, with an
  optional `engagement_id` (the advisor's own engagement, else 404; omitted
  means none was named). The first record stands; naming an engagement later
  changes only the link.
  - With a price in the body: 400 `included_has_no_price`.
  - On a priced line (Free, a recorded $0, included): **409 `priced_line`.**
    Including a priced line would restate its stamped amount, rate and cut, so
    #4713's frozen terms are never touched by this: the advisor clears the
    price first, which a settled line refuses (`settled_price`).
  - On an included line, a write that does not name `billing_state` is 409
    `included_line`; one that does clears the inclusion in the same
    compare-and-set UPDATE (whose WHERE now includes `included_at`).
- **Totals.** `ledgerAggregate` classifies a line `included` before anything
  else. An included line has no amount, so it is in no gross, billed,
  collected, written-off or outstanding figure; it is no longer counted as
  unpriced (or as priced: `priced = sessions − unpriced − included`).
  `GET /me/ledger` adds `totals.included_sessions` and `states.included`;
  `GET /me/earnings` adds `included_count`, an `included` row in `by_state`
  (total 0) and `population.included_sessions`; `GET /me/tax-summary` adds
  `included_sessions` and names them in its note.
- **The Earnings provenance line.** `pricedBasis` (the "From 12 priced
  sessions · …" line under Recorded billed) names them: "· 2 sessions included
  in an engagement, not billed". The ledger shows the state as "Included" and
  Sessions no longer counts an included session as unpriced.
- No control records a session as included yet; that is #4832's. A booking
  made on a session type whose offer says "included" is not marked by the
  booking: the offer is what was advertised, not how the session was settled.

### Not done here

- The Practice v2 controls themselves (#4829, #4831–#4834).
- The Sessions slot grid's "Booked" note (`sessionGrid.js`) still reads a
  booked hour with no price as unpriced when the booking is included; it reads
  `booked_pricing`, which knows priced, free and unpriced only.
- The engagement history (`/events`) does not carry the end reason; it is on
  the engagement, which is terminal once ended, so there is one per row.
