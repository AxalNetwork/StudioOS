### Why

Every edit lived in the browser's memory until Save version. A closed tab lost paid generations, and there was no way back from a bad edit except Versions. Plan §5.9.1 and §5.9.2 asked for four things on top of D1501's working copy:

- an undo model with a 100-step history;
- an autosave client;
- rich-text editing;
- find and replace that never touches a bound figure.

### 1. The undo model (`gridOps.js`)

**Reducers.** `apply(doc, op) → { doc, inverse }` is a pure reducer over the working deck `{ cards, theme, audience }`. It never mutates its input, reads no clock and sends nothing over the network. Applying `inverse` to the result gives back `doc` exactly. An op that the slide model refuses answers its sentence and changes nothing. Examples are a structure that is not one of the seventeen, and a divider that would take a chart below 4 × 3.

**The ops.** There are 26:

- the ops of plan §5.9.2:
  - `setStructure` and `moveDivider` (#3765's ops);
  - `addBlock`, `updateBlock`, `removeBlock` and `moveArea`;
  - `insertProposal` and `insertBatch`;
  - `setTheme` and `applyBrand`;
  - `reorderCards`, `duplicateCard` and `hideCard`;
  - `moveOverflowToNotes`, `findReplace` and `decorOp`;
- the plain ops that the editor's other edits use:
  - `setCard`, `setCards` and `setDoc`;
  - `setAudience`, `moveCard`, `insertCard`, `removeCard`, `insertBlock`, `setFlag` and `noop`.

Where an op has a natural inverse, its inverse is that op:

- `reorderCards` is inverted by the inverse permutation;
- `removeBlock` by `insertBlock` at the same place in the list;
- `updateBlock` puts each field back, and takes away a field it added;
- `duplicateCard` and `insertCard` are inverted by `removeCard`.

Otherwise the inverse puts the card or the deck back whole.

**The history** keeps 100 steps (`perform`, `record`, `undo`, `redo`, `HISTORY_STEPS`). A step is a list of ops, undone from last to first.

- Typing in one field is one step while each edit comes within 800 ms of the last. The same holds for one nudge burst on one block.
- Placements that share a `group` are one step, however many there are.
- A step that placed a charged run keeps `charged`.
- A new edit clears redo, and the 101st step drops the oldest.

**The editor.** `PitchEditor.jsx` now keeps the working deck in one reducer, `editReducer`, with its history. Every edit is an op. The editor's old `setCards`, `setTheme` and `setAudience` are thin wrappers that make one. History lasts as long as the version stays open: Save version remounts the editor on the new version, so the history starts again.

**Where Undo and Redo are:**

- **The header.** `DeckToolbar.jsx` draws Undo and Redo before the save state, with "100 steps". Each button is named with how many steps it can take, for example "Undo, 3 steps".
- **⋯ › This deck.** Undo and Redo are repeated there, greyed with "Nothing to undo." or "Nothing to redo." when they have nothing to do.
- **The keyboard.** Cmd/Ctrl+Z undoes, and Shift+Cmd/Ctrl+Z (or Ctrl+Y) redoes (`editKey`). Inside a text field, Z is the field's own native undo, as plan §5.9.2 says.
- **Who gets them.** A reader gets neither. On a phone they are only in ⋯.

**The seam.** `deckV2Adapter.history` answers `gridOps.js` at once. It is listed in `SWAPPED`, so its ⋯ items are live. It does not use `through()`: no route stores the history, so it has no contract. The contract test still matches only `through(` (`deck_contracts_d1511`, test 3) and passes.

### 2. "One undo step" is real

Each of these is one op, or one group, so one Undo takes it back whole:

- **Apply theme:** each change of theme (`setTheme`), and Apply to all cards (`applyBrand`).
- **Apply structure:** `setStructure`. Apply layout is one `setCard`.
- **A divider move and Move overflow to notes:** `GridStage.jsx` names each one in a second argument to `onCard`.
- **Slide size:** the cards and the theme change together in one `setDoc`. The size sheet's Undo is now the history's.
- **Accept all in "Generate into N areas"** (`AreaResults.jsx`) and in the header Ask (`DeckAsk.jsx`): each press places its proposals in one group.
- **Find and replace:** Replace all.
- **Restore unsaved changes.** It is one `setDoc`, so Undo takes it back too.

**Reorder for stage.** Its op, `reorderCards`, is built and covered by the property test. The menu item ⋯ › Reorder for stage stays greyed on the `deckActions` adapter, because its sheet belongs to #3808.

### 3. "Still charged"

Three kinds of Accept pass `charged` with their placement:

- the instruction box;
- "Generate into N areas", when the area ran a model;
- the header Ask.

When Undo takes back a step that placed a charged run, a line shows above the stage: "Still charged: undo takes the accepted run off the card, but what it cost stays spent." It goes away on the next edit or redo, or on OK.

The interim confirm line beside the instruction box's Accept, "Charged $x. The run was charged…", is removed. The proposal's eyebrow still shows what the run cost.

### 4. Rich text (`richText.js`, `TextWords.jsx`)

**The model.** A text block is edited as characters, each carrying its marks. Runs are rebuilt from them by joining neighbours with the same marks. `text` and `paras` always come from the same characters, because the Worker rebuilds `text` from `paras` (`parasOf`). A block with no mark left loses `paras`, and every v1 reader sees it as plain text again.

**The controls.** In `BlockTools.jsx`, the words of a selected text block get B, I, Accent and Link above them.

- **B and I** toggle on the selected words. With nothing selected, they apply to the whole block.
- **Accent** uses the theme's accent colour.
- **Link** opens an in-page line for an https address, with Apply link and Remove link.
- **`aria-pressed`** shows what the selection carries.

**Typing** keeps each run's marks (`retext`). New words take the marks of the words they replace, or else of the word before them.

**The Worker's limits are checked first.** A mark that would break one is refused with the Worker's own sentence, and nothing changes. The limits are:

- 40 paragraphs, and 40 runs in each;
- 3 accent runs;
- an accent with contrast of at least 4.5 : 1 on the card's ground (`groundOf`);
- a link that is https.

**`spellcheck`** is on the block's words, the speaker notes, the phone's notes, Add a block's text and Replace with. The Find field has it off.

**The scope of the change in `BlockTools.jsx`** is one import, one prop (`accent`) and the swap of the words' textarea for `TextWords`. This keeps it clear of #3777's edits to the same file.

### 5. Find and replace

**Where.** ⋯ › This deck › Find and replace… (⌘F). It is never a header control. Cmd/Ctrl+F opens it from anywhere in the editor, inside a text field too.

**The sheet** (`FindReplaceSheet`) has these parts:

- Find, Replace with and Match case;
- the count, for example "5 matches on 2 cards · 1 in bound figures, left as they are";
- Replace all;
- the line "Bound figures are never replaced.".

**What it searches:** card titles, the words of text blocks (keeping their runs' marks) and speaker notes.

**What it skips** (`isBound`):

- a metric;
- any block that carries a `binding`;
- a chart.

Matches inside those are counted as skipped and never rewritten.

### 6. The autosave client (`deckAutosave.js`)

It runs on D1501's routes, reached through the adapter's `saveCard`, `draft` and `discardDraft`.

**When it saves.** Every change of the working deck is written to IndexedDB at once (`idbStore`). The record is the whole deck, together with the card revisions it was made on. Each changed card is then sent as a PATCH:

- 1.5 s after the last edit;
- and never more than 10 s after the first unsent edit, while typing goes on.

Each PATCH carries `If-Match`, the revision this tab last saw (0 for a card the draft does not hold yet), and the card's place (`ord`). A reorder sends each card that moved. When the Worker holds every card, the device copy is cleared.

**The save state** in the header (`saveChip` with `sync`):

- "Saving…";
- "✓ All changes saved", titled "Saved to your draft at 14:32. Save version makes them a version.";
- "Offline · 3 changes saved on this device";
- "● Card changed elsewhere".

Save version still shows while the deck differs from its version. Versions stay explicit (owner question G).

**`beforeunload`.** While edits are unsent, the browser asks before the tab closes. The device copy keeps the edits either way.

**Offline (pd9p).** A PATCH with no status never reached the Worker. The edits stay on the device, and the line reads "Offline · [n] changes saved on this device. They'll sync when you're back." with "Typing still works.". The `online` event, or the next edit, sends them again with the same `If-Match`. Once they are sent, the line reads "Synced".

`through()` now keeps the Worker's `status` and body on an unreadable answer. That is how the autosave tells offline apart from a refusal, and how it reads the 409.

**The 409 (pd9q).** `card_rev_conflict` stops sending. The editor shows "Your version" next to "Their version" (the reply's `server`), with three choices:

- **Keep mine** sends my card with `If-Match` set to their revision.
- **Keep theirs** places their card.
- **Copy mine to a new card** places theirs, and inserts mine after it with a new uid, in one step.

**Restore.** On open, the editor reads the device copy and the Worker's draft (`restoreOffer`):

- The device copy comes first when it differs from the version.
- Otherwise the Worker's draft comes first when, laid over the version, it changes it (`mergeDraft`: by uid, at the draft's places).

The banner then reads "Restore unsaved changes from [14:32]?", with Discard and Restore. A time that cannot be read is left out, never drawn as 00:00. While the banner waits, nothing is sent and the device copy is not written over.

- **Restore** is one undoable step. The replay sends each card with the revision it was edited from, so a card that another tab changed in the meantime comes back as a 409, not as a silent overwrite.
- **Discard** calls `DELETE …/draft` and clears the device copy.

**After Save version,** that version's device copy and draft are cleared.

### Departures

- **"At most every 10 s"** is read as a maximum wait: a save always comes within 10 s while typing goes on. It is not read as a throttle. The plan's "1.5 s after typing stops and at most every 10 s" allows either reading, and only this one bounds the work a crash can lose.
- **Undoing an Insert does not return the proposal to "proposed"** (plan §5.9.2). Main has no route that reopens a decided rail proposal. The card goes back, and the "Still charged" line says the cost stays.
- **The Worker does not validate each op** (plan §5.9.2). It validates each card on PATCH (`modelProblems`) and on save. There is no op log on the Worker.
- **The Worker's draft cannot drop a card.** D1501 has no per-card delete, and it holds neither the theme nor the audience. So a restore from the draft alone brings back a card removed in the editor, and it keeps the version's theme. A restore from the device copy is exact, because that copy holds the whole deck. This is a follow-up for D1501: a delete route, or a deck-level field.
- **Generation is not turned off while offline** (plan §5.9.1). S1's revision does not ask for it.
- **The conflict line does not name who changed the card.** The 409 reply carries no editor name, so the line reads "in another tab or by another member".
- **Undo and Redo sit in the header,** although D1604's rule keeps the header to the save state, ⋯, Present, Share and Ask. The issue puts them in `DeckToolbar.jsx` by name.
- **A card with no uid is not autosaved.** The Worker gives every stored card a uid on read (D1500), so this happens only with a hand-made card. Such a card stays "Unsaved changes" until Save version.
- **Hide card:** the `hideCard` op is built, but the menu item stays on the `media` adapter (#3788), as S1's revision says.

### UNVERIFIED

None of this has run in a real browser. In particular:

- real IndexedDB (only a fake was used), including in Safari's private mode;
- the `beforeunload` prompt;
- the `online` event;
- where focus sits when Cmd/Ctrl+Z and Cmd/Ctrl+F are pressed;
- a textarea's selection feeding B, I, Accent and Link.

The 409 body the client reads is the shape of D1501's `refuse` reply, which `deck_draft_d1501` pins. The client test uses a synthetic body of that shape, not a live Worker.
