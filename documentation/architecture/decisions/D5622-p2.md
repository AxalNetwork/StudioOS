### Two workflows, because WF-4 allows nothing else

The re-scope asks for a `workflow_run` trigger. #4571 WF-4 admits `workflow_run` only for a reviewed
`TRUSTED_WORKFLOW_RUN` entry. Such an entry may only be triggered by `workflow_run`, may not check out any `ref:`, and
may not use `actions/download-artifact`. A model round and an apply job need all three. So the work is split in two:

| Workflow | Trigger | Token | Model | PR code | Writes |
| --- | --- | --- | --- | --- | --- |
| `pr-repair.yml` (WF-4 entry `'pr-repair.yml': 'D5622-p2'`) | `workflow_run` of `CI`, completed | `GITHUB_TOKEN`: `actions: write`, `contents: read`, `pull-requests: read`; no environment, no secret | no | no | one `workflow_dispatch` |
| `landing-bot-red-pr.yml` | `workflow_dispatch` (`pr`, optional `head_sha`, `run`) | `plan`: read-only plus an App token for metadata; `apply`: the App token in `landing-bot` | in `repair` only (#6473) | in the runner's keyless `verify` only | one commit on the PR's own branch, labels, one comment |

`landing-bot-red-pr.yml` is the name `rules.mjs` `dispatchable` already gives the `red-pr` kind. The ejection
handler's existing dispatch (`landing-bot-ejection.yml`, own failures) finds it with no edit, as D6475 and D6477
named theirs.

### The trigger's filters

Every filter is applied in `redPr.mjs`, never trusted from the event payload. The `if:` holds the cheap ones (pull
request event, this repository, conclusion failure, the switch and both limits). `triggerGate()` holds all of these:
- the run is CI's own `pull_request` run (`path` is `.github/workflows/ci.yml`), from this repository, red, on the
  PR's current head;
- exactly one open, non-draft PR has that head;
- its branch starts with `agent/` or `claude/` (AGENTS.md's prefix, and Claude Code's own), and is never `repair/`
  or `main`;
- its author is not a bot;
- it is not labelled `bot:off` or `needs-session`;
- nothing was pushed for 30 minutes;
- main's `ciClassify` (`verdictFor()`) reads the failure as `pr_failure`.

**The trusted verdict.** Main's code recomputes the verdict from the run's jobs and from main's completed push run
before the PR run started (`mainRunBefore`), both read from the API. The PR's artifact and the digest comment are
never read: a branch can write either.

### The plan trusts nothing it was handed

`plan` reads the PR and the CI run again. It refuses when:
- the head moved since the trigger;
- `eligible()` refuses (mode, open and same-repository, `bot:off`, `repair/`, `.gitattributes`, breakers, 30 minutes
  quiet);
- the PR is a draft, off an agent branch, or bot-authored;
- the verdict is not `pr_failure`;
- this head was tried before;
- `attempts()` and `budget()` refuse.

**Attempts (#6467).** Two per PR for its whole life. They are counted from the artifacts each run uploads before it
calls the model (one per PR, one per head, one per UTC day) and from the bot's `Landing-Bot-Kind: red-pr` commits. A
session's commits never reset the count. The re-scope asks for two per PR per fingerprint; #6467's per-PR count is
stricter, so it is used as written and nothing restates it. The plan records the fingerprint.

**Data, not instructions.** Log tails, the failure list, and the PR title and body reach the model only as data
files. No `run:` line expands an expression, and the trigger reads no `workflow_run.head_branch` or `display_title`.

### The apply job: main's guards, then one commit

`apply` checks out `github.sha` (main). It runs `redPr.mjs apply` and nothing else: no install and no PR script. The
patch must pass four checks:
1. `checkPatch()` and the #8506 record: the controller, the run, the task and the head.
2. #6467's `pathGuard()`: protected and T2 paths. An existing test is T2 when there is no diff.
3. `merge-control/src/lib/patchGuard.mjs` `validate()`, new and pure. It refuses any of these:
   - a privileged path;
   - an existing test;
   - a test helper or fixture, a baseline, ledger or snapshot, an allowlist or ignore list, a guard or check script,
     a shard list;
   - a deletion or a rename;
   - an added `skip`, `only` or `todo`;
   - fewer `test(`/`it(` calls or assertions;
   - any changed line that names a timeout;
   - binary content, a mode change, an emptied file, a file over 200 kB;
   - more files or changed lines than the owner's limits.
4. Main's `merge-policy.mjs` on the committed diff: T2 is refused.

It is plain JavaScript, like `classify.mjs`, so the Actions job loads it with no build step. A refusal labels the PR
`needs-session` with one comment (`giveUp()`). Then:
- The commit is ONE normal commit whose only parent is the planned head.
- `apply` reads the PR again right before a normal push. GitHub refuses a non-fast-forward push, so this is the
  compare-and-swap. A moved head pushes nothing and labels nothing: the session pushed.
- It never pushes to main or a `repair/` branch (`branchAllowed()` is checked again), and never forces. It never
  queues or merges.

**Sign-off.** The commit carries `Landing-Bot-Kind: red-pr`. The feeder's `repairStatus()` then keeps the PR in the
owner's lane, with no expiry, and the sticky comment says a person signs off this head.

### Closed by default

Nothing runs until the owner sets all of these:
- `LANDING_BOT_RED_PR_MAX_FILES` and `LANDING_BOT_RED_PR_MAX_LINES` (Actions repository variables, whole numbers).
  Unset, empty or 0 refuses everything: in the trigger's `if:`, in `triggerGate()`, in `plan` before any read
  beyond the switch, in `patchGuard.validate()`, and again in `apply` before the push.
- `LANDING_BOT_ENABLED`. Only `true` lets a CI run start anything. `dispatch` admits a manual run on one PR only.
- The shared `LANDING_BOT_DAILY_MODEL_RUNS` and `LANDING_BOT_DAILY_PUSHES` (unset is 0).

### Not done here, and why

- **The hosted proof** (a deliberately failing PR gets one repair commit, then needs sign-off) waits for the owner
  to set the limits. #8883 (the Actions queue backed up) also forbids dispatching now.
- **A quiet-period gap.** CI often finishes within 30 minutes of the push (8 to 70 minutes on 2026-11-26/27). Such a
  run is refused by the quiet rule, and nothing re-asks later unless the session pushes again or the queue ejects
  the PR. A sweep would close the gap; it is not in the re-scope, so it is left to the owner.
- **No `bot:repaired` label.** The commit trailer is the mark the feeder already reads. A label would be one more
  thing a person could remove.
