## D6884 — Case-scoped Eadwyn diligence proposals (#6884)

Issue #6884 implements the Worker runs specified by D6294 and the owner's
settled answers in that issue. The diligence rail UI is #6885; this change
adds no screen, navigation item or automatic case write. It does not change
the design decision owned by #6886.

### Contract and mount

`routes/dd_rail_run.ts` self-registers before the existing `rail_run.ts`
router at `POST /api/ai/rail/run`. Other options pass through with the cached
JSON body intact. No new client API is necessary.

The body has `page: "Due diligence"`, `case_uid`, and one of these options:

| Option | Additional input | Proposal |
| --- | --- | --- |
| `dd:summary` | `section_id` for a scoped selection | One cited line per draft: worked, open and blocking evidence |
| `dd:request_drafts` | Optional `section_id` | One founder-facing request per pending/flagged/failed checklist item |
| `dd:memo_draft` | Optional `section_id` | Four parts: `summary`, `verified`, `on_trust`, `conditions` |
| `dd:section_summary` | `section_id`; optional `mode: "verdict_note"` | Section summary or neutral evidence note, with no proposed verdict |
| `dd:answer_from_room` | `request_id`; optional `text` (the founder's proposed answer) | Answer with matched own-room passages and file UIDs |

`model` is optional and subject to the existing metered router's model policy.
The server selects the user and `dd_case:<uid>` record reference; client-sent
actor, budget and record fields cannot change them. IDs have closed formats,
SQL values are bound, and source lists are bounded. Oversized evidence is
refused rather than silently presented as the complete case.

Summary sources carry `blocks_proceed` from the same
`blockingSectionsWithOpenSevereFlags` helper used by the decision route. The
model reports that recorded gate; it does not choose which findings block.

The response uses the rail's SSE `meta`, `guard` and `done` events. A successful
`done` contains private proposal UIDs, closed payloads with `text` and
server-validated `citations`, and the member's usage-log ID, charged amount
and budget. Memo parts also carry character count, `max_characters: 8000`
and the existing memo revision. File citations include the matched passage.
No model-selected field, action, verdict, flag update or recipient is saved.
Invalid or changed evidence drops the proposals and retains the receipt for
the work actually performed. Pre-model refusals are one authored sentence
and a stable code; exception/provider text is never returned.

### Access and privacy

The four case-member options first use the exported `requireDdReader`, then
`caseAllowed` and the existing lead/opener/reviewer relationships. An Admin,
lead or opener can read the case; other members must select their assigned
section (a single assignment is resolved automatically). An observer has
`dd:summary` only. Reviewers never query the memo, cannot draft requests for
the subject and cannot select another section. A verdict-note draft uses
the verdict route's real NDA attachment gate, including its Admin/lead
exception; a client boolean is not evidence. The draft contains no verdict.

The founder option deliberately uses the existing request-recipient rule
(`resolveSubjectUserId`), rather than admitting founder-only accounts to the
case reader. The request must be unwithdrawn, unreviewed and on that case.
The subject must own that project's room through `roomProject`, including
the verified active-company scope. Other founders, cofounders and admins
gain no owner bypass. This path reads no section, flag or memo evidence.

The server decrypts flag detail for allowed case-member runs. It decrypts the
subject identity only to remove it: neither the subject email nor legal name
goes into guard/model input. Unicode-normalised literal redaction also
removes identity aliases from text, and the output is scrubbed before
storage. Request drafting receives just eligible item titles, never internal
flag details or reviewer notes. All evidence and founder answers are in
`untrustedBlock` with `UNTRUSTED_RULE` in the static system message.

Founder retrieval reuses `searchRoom` and its fixed embedding/ranking models.
Its query and ranking contexts are scrubbed before those models too. Hits
must still match a passage belonging to a file on the owned project. Before
storing any output, the Worker rechecks case access, source content, request
state and matched passages without another paid search. Revocation or a
changed source drops the result. Missing search or failed/decryption reads
are Unavailable, not empty evidence. An untouched case returns exactly
“Nothing to summarise yet” and risk “Not recorded”, without a model or hold.

### Billing and persistence

The five drafting runs use `aiRouter.run` with task `rail_write` as the member
who pressed. That router owns holds, guards, settlement and release; this
route does not implement a second billing path. Retrieval uses its existing
member-metered data-room search runs. The case page's assistance switch is
checked before retrieval too, so switching it off cannot incur search spend.
Usage is attributed to the actor, not
the case lead, and remains visible in Settings through the existing logs.

Only `proposeRail` writes the output. The existing proposal store binds every
read and keep decision to the keeper's `user_id`, so keeping a summary is
private and never creates a shared case note. Sharing or sending still needs
an explicit human action through the appropriate record route. No new table,
migration, credential, external provider or production-data operation is
introduced. The frontend remains responsible for the DDL20–29 presentation.

### Verification

The authenticated Hono tests run against SQLite built from the canonical
schema. They cover each option's outside-case refusal, observer/reviewer
scope, no reviewer memo query, identity canaries, private keeps, no DD writes,
real metered success/refusal, NDA evidence, strict citations, memo limits,
founder room ownership and changes during a run. Assertions and deliberately
bad source variants are mutation-checked before publication. The ordinary
build, decision-ID guard and full drift suite remain publication gates.
