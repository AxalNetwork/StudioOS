## D4807 — one entitlement predicate for "is this account a mentor today?" (#4807)

**Status:** part 1 of #4807. The remaining items on the issue (five-dimension status, KPI reconciliation, historical participation episodes, read-state fixes) follow in later parts.

## Decision

An account is an eligible mentor when `users.is_active = 1` (D960) AND it holds the Advisor licence, as the primary role or as an additional `account_licences` row that is not revoked (D4472). That rule is written once, in `cloudflare-worker/src/services/mentorEligibility.ts`, and every SQL read that needs it writes `{ELIGIBLE}` and passes the statement through `withMentorEligible`.

## Why

Three answers existed. The assignable list and the access gate honoured an additional licence; the catalogue's mentor count, cohort coverage, the "no longer an Advisor" warning and the opt-out total tested the primary role only. A valid secondary Advisor could be assigned and read a cohort's founders, yet was not counted, left the cohort reading "no mentor", and was flagged as having lost the role.

## Consequences

- The assignment list carries `advisor_eligible`; the Programs pages read it and fall back to the primary role for an older read.
- A revoked licence, a changed role and a deactivated account each remove eligibility at once, because the rule reads the live rows.
- A database without `account_licences` falls back to the primary role.
- Tests: `cloudflare-worker/test/mentor_eligibility_4807.test.ts`, `frontend/test/mentor_eligible_rows_4807.test.mjs`.

## Part 3 — historical participation reads episodes that later changes cannot rewrite

`peopleIn` (People taking part) read the mutable rows: a mentor assignment's `assigned_at` / `unassigned_at` / `is_active` and a Learning enrolment's `enrolled_at` / `status` / `updated_at`. A re-assign overwrites the first and clears the second; a re-enrolment overwrites the third. So a reassignment or re-enrolment made after a period closed changed that closed period's count.

- 565's `advisor_cohort_assignment_events` and 560's `learning_enrolment_events` already hold one immutable row per grant, end, enrolment and removal. Migration `202611072215_programs_participation_episodes_4807.sql` adds two **views** over them: `advisor_cohort_episodes` and `learning_enrolment_episodes`. An episode is a start and the first later event of the same assignment (or learner and program) that bounds it. A view stores nothing, so there is no second copy to drift.
- The migration is named by timestamp with the issue number in its slug: D4106 stops numbered migrations at 799, so a literal `4807_…` file would fail `check-sql-migrations`.
- An earlier episode whose end was never stored (565's backfill cannot recover one) is bounded by the next assignment's start, never left open to today. That is an upper bound, not an invented end.
- Fixtures that insert assignment rows directly now also insert the events the routes always write beside them.
- Tests: `cloudflare-worker/test/programs_participation_episodes_4807.test.ts` overwrites the mutable rows the way the routes do and checks the closed period's count does not move. Against the old query, three of its five tests fail.
- Not changed: the current-state figures (mentor total, coverage, active enrolments) still read the live rows; they are meant to.
