## D706 — The template catalog lists the 28 documents Axal VC Spin-Out Lab Fund I LP is missing

Issue #1718. The owner asked on 2026-10-17 for every document the Fund is missing to be in the template library at `/admin/contracts?tab=templates`. This adds each one as a catalog entry with no body. Counsel writes the bodies, and nothing here is legal text. S1 decided every point (the issue's decisions 1 to 5); this file records what was built and what was found.

### Migration 468

`cloudflare-worker/sql/migrations/468_legal_catalog_fund_i.sql` inserts one row per document into `legal_templates` (084): `is_stub = 1`, `body_md = ''`, `merge_fields = '[]'`, `version = 1`, `is_active = 1`. ### Kinds and parties

`services/legalDocFormat.ts` and its mirror `frontend/src/lib/legalDocFormat.js` list every new slug by name: the policies in `POLICY_SLUGS`, the filings in `UNILATERAL_SLUGS`, the resolutions in `RESOLUTION_SLUGS`. Agreements are the default kind. `axalEntityKeyForDoc` checks two new sets first: `FUND_PARTY_SLUGS_D706` returns `fund`, and `GP_PARTY_SLUGS_D706` returns `gp`. The regex fallback cannot catch these slugs, because `_` is a word character, so `\blpa\b` does not match `lpa_initial`.

- **"none" documents are not routed.** A unilateral filing's block carries only the filer, and a policy has no block. Neither has a preamble (`pdf.ts` and `PaperPreview.jsx` draw the preamble only for an agreement, and skip the block for a policy). Whatever `axalEntityKeyForDoc` returns for them is never printed.
- **The `fund` key** already exists in `AXAL_ENTITIES`. #1716 (D705) gives it the legal name and the "through its general partner" signature line. These routes pick that up when it lands, with no change here.

### No behaviour change for existing documents

- **No send can pick a stub up as text.** `getActiveTemplateBody` requires `is_stub = 0` and a non-empty body (`legalTemplateStore.ts:169-178`), and contract publication (D647) snapshots only rows with a body (`contractPublication.ts:97-102`).
- **No existing row changes.** The migration only inserts.
- **No existing slug's kind or party changes.** The new set members are all new slugs.

### The 25 stubs that have body files (decision 4)

Production has 25 active rows with `is_stub = 1` and an empty body. Each has a body file under `templates/legal/` (`scripts/gen-legal-templates-seed.py:73-119` maps slug to file). Nothing here changes which text any send produces.

**How a send resolves a body.** Every `createAndSendEnvelope` caller goes through `templateBodyFor` (`routes/esign.ts:254-261`):
1. The store body, which is null for a stub.
2. The bundled `.md`, through `templateKeyForDocType`.
3. The inline `buildTemplateBody` (`esign.ts:207-245`, used at `:469-470`).

Only nine `.md` files are loaded at runtime (`services/legalTemplates.ts:19-27`), and none of the 25 slugs is in `legalDocTypes.ts:118-134`. So **the body file is never what a stub sends**. Every send of these 25 uses an inline body: 15 spaced slugs have their own (`esign.ts:225-239`), and the other 10 get the generic "Closing Binder" text (`:241-244`), titled with the raw slug.

**The send surfaces**, all admin or super-admin:
- E1: `POST /api/legal/esign/send` (`esign.ts:721`).
- E2: profiling verify (`routes/profiling.ts:545`, send at `:611-620`). Its picker offers the 15 spaced slugs (`PartnerProfilesConsole.jsx:27-53`).
- E3: the exploring binding (`routes/admin_exploring.ts:144-171`).
- E4: the licence contract send (`routes/admin_licences.ts:1982-2049`), which sends by slug, not the stored contract body.

**Refusals:**
- Published-contract preview and send: `template_not_published` (`contractPublication.ts:22-23`).
- `GET /api/legal/esign/templates/:doc_type`: `template_not_offered` (`esign.ts:894-900`).
- Store fields: 404 (`admin_contracts.ts:827-833`).
- Template generate: 404 (`routes/legal.ts:879-883`).
- The store `preview.pdf` renders the empty store body (`admin_contracts.ts:1747-1775`).
- `NO_BODY` (`esignOriginators.ts:184`) is display text on a partner's not-offered list, not an error; a partner who posts the type anyway gets 403 (`esign.ts:767-769`).

Found while tracing, recorded for the owner and not changed:
- **Production and the repo disagree on these 25 rows.** Migration 085 seeds them as stubs, and migration 113 (an unconditional `ON CONFLICT … DO UPDATE`) would fill all 25 from the files above. Production still has them as stubs, so 113's upserts did not take effect there for these rows. Why is not established.
  - **Filled by D758.** Migration 484 (D758, #1861) fills these 25 from their files, each at a new version with its stub version in history. From then on a send of any of them uses its file's text, which changes this decision's "Nothing here changes which text any send produces" for these 25 rows only.
- **Partner deals never use the `partner_*` rows.** Partner onboarding always sends `partner_msa_v1` (`routes/partner_onboarding.ts:329-337`). The contracts list labels each deal `partner_${deal_type}`, which matches no key, so every deal counts as `partner_custom` (`admin_contracts.ts:570-571`).
- **The 15 spaced slugs always show 0 uses.** Usage is keyed by the `admin_contracts.ts` `TEMPLATES` keys (`:896`, `contractTemplateUsage.ts:21-22`).
  - *Since D758 (#1863):* partner deals count under `partner_services`, and the spaced slugs under their own rows.
