### 1. The route

`POST /api/ai/rail/run` gains a third handler, `studio:layout`. It is matched as `/^studio:layout$/` beside `sessions:block` (D1596), before the `form:` path.

```
POST /api/ai/rail/run
  { page: <the member's /studio rail key>, option: 'studio:layout', model? }
  → text/event-stream:
      meta  { model, hold_microusd }                                   before the run
      guard { input, output }                                          after it
      done  { proposals[{ uid, op, key, title, size?, index?, source, base_revision }],
              dropped[{ op, title | null, why }], usage_log_id, charged_microusd, budget }
         or { proposals: [], dropped[], reason: 'nothing_to_change', … }
         or { refusal: { code, status, message }, proposals: [], dropped: [] }
```

The rail key for each profile's /studio (`STUDIO_RAIL_PAGES`, matching `frontend/src/lib/railPages.js`):

| Profile | Page key |
|---|---|
| Founder (and a Spin-Out Lab member) | `Founder · Studio` |
| Investor | `Investor · Home` |
| Operating Partner | `Operating Partner · Home` |
| Advisor | none: Advisor /studio has no rail, by owner request |

**Refused before any quote, hold or run** (the stubs in the test are never called):

| Case | Answer |
|---|---|
| An Explorer with no Studio of their own | `403 no_profile` |
| A support session | `403 support_session_refused` |
| An admin | `403 read_only_preview` ("Eadwyn is off while you preview a member's Studio", SM11) |
| `studioProfile`'s own refusals (#3838) | as `GET /api/studio/layout` answers them |
| A page that is not the profile's key above | `404 unknown_page` |

**One change from the issue's wording.** The issue says an Explorer gets `no_profile` (`isExplorer`, role `exploring`). A Spin-Out Lab member also has role `exploring`, and `studioProfile` gives them the founder Studio: their Lab week is what this run reads first. So only an Explorer who is **not** in the Lab is refused. A Lab member arranges their founder Studio here as they can on `PUT /api/studio/layout`.

### 2. What the model reads

`services/studioLayoutRun.ts`, `studioLayoutMessages`:

- the member's current layout (`layoutView`, `routes/studio_layout.ts`), with its `revision`;
- the profile's catalogue (`catalogueOf`): each module's key, title, purpose, group, default size, whether the plan locks it, and whether it is placed;
- for a founder, `founderContext`:
  - the Lab week, from the columns `/api/spinout-lab/state` reads;
  - the readiness tier: the newest official score snapshot of the founder's own latest venture that `/api/scoring/scores/:projectId` would show them (signed, hash verified, not flagged or rejected).

  Each part fails alone and reads "Not recorded".

No other member's data, no email and no table name is in the prompt (the test pins this).

### 3. The task and its price

- **A new AI task, `studio_layout`** (`services/aiRouter.ts`), labelled "Arrange your Studio" (`services/aiCatalog.ts`).
  - Like `mail_draft`, it is a mid model with the same priced alternates.
  - Its router entry is what lists it in `GET /api/ai/pricing`, so `assistCost.js` prices it before the click.
- **The hold:** `meta` carries the hold from the same arithmetic as the hold, before the run. The panel writes it as "Holds up to $[x] · you pay what it uses".
- **The option**, "Arrange my Studio for this stage", is registered on the three page keys:
  - It is registered as an Ask chip (`FOUNDER_ASK_CHIPS`, `INVESTOR_ASK_CHIPS`, `PARTNER_ASK_CHIPS` in `frontend/src/lib/railOptions/`), kind `plan`, handler `form`.
  - `scripts/build-rail-matrix.mjs` lists it with the `plan` kind's models. So `GET /api/ai/rail?page=` offers it with its own `models` and `pick`, and a pick resolves through `resolveRailChain` as for every rail run.
  - It is not a rail action: the AIRail holds only model choice and consumption (the owner, 2026-10-31). So it stays out of the rail-option lists and their wiring tests.
  - Its matrix row's `routeTask` reads `rail_plan`, as every option of a page kind does. The run itself is the `studio_layout` task.

### 4. What may be proposed

The model answers `{"ops":[…]}`. `validateOps` checks each op against the catalogue and against the layout as the earlier kept ops left it:

| Op | Kept when |
|---|---|
| `{ op: 'add', key, size }` | offered, not fixed, not locked, not placed, size `1/3` / `1/2` / `full`, and the layout stays at most 12 |
| `{ op: 'remove', key }` | offered and placed |
| `{ op: 'resize', key, size }` | offered, not locked, placed, valid size |
| `{ op: 'move', key, index }` | offered, not locked, placed, `0 ≤ index < length` |

Every dropped op is `{ op, title | null, why }`:
- `why` is one of `unknown_op`, `fixed`, `not_offered`, `locked`, `already_placed`, `not_placed`, `invalid_size`, `invalid_index` or `over_limit`.
- `title` is the module's title, or its last known title (`RETIRED_TITLES`), or null. Never its key.

### 5. What is written

- One `ai_rail_proposals` row per kept op, through `proposeRail`, with:
  - `kind: 'proposal'`, `rail_option: 'studio:layout'`, `record_ref: null`;
  - the run's `usage_log_id`;
  - `payload: { op, key, title, size?, index?, source, base_revision }`. `source` is a short sentence naming what the run read; `base_revision` is the read's `revision` (null when there was no saved row).
- **Never `studio_layouts`.** Nothing kept is `done { proposals: [], reason: 'nothing_to_change' }` (SM10b) and no row.

### 6. Accepting (client, existing routes)

1. Apply the op(s) to the current layout.
2. `PUT /api/studio/layout` with `expected_revision: base_revision`. A 409 `stale_layout` shows SM8c.
3. `POST /api/ai/rail/proposals/:uid/decide` with `accept` for each row.

"Accept all (n)" is one `PUT`, then n decides. Edit changes the size or the position before saving and decides `edit` with the edited payload. Discard decides `discard`.

`decide` checks only a proposal's `field` against the never-fill list, and these payloads have none, so it needed no change; the test decides all three.
