### 1. What moved

| Reader | Before | Now |
| --- | --- | --- |
| `GET /api/legal/jurisdictions` | `JURISDICTIONS` | Each legacy form of the catalogue version, in order: `{ id, label, …legacy_display_json, templates }`, the templates being the form's `document` pack items in order |
| The admin wizard's `handoff.next_steps` (`POST /api/legal/incorporate/wizard`) | `HANDOFF_NEXT_STEPS[id]` | The form's `after_filing` `step` pack items, in order |
| The name check's register adapter (`services/nameCheck.ts`) | `JURISDICTION_REGISTRY[id]` | The adapter of the form's place in the catalogue (`PLACE_REGISTRY`: `US-DE`, `US-WY`, `GB`, `SG`, `EE`) |

Version 1 is the arrays (D6690), so every response is unchanged. Nothing else in `legal.ts` moved: the wizard's entity and documents, the quote, the order and the checkout still read the arrays (the quote is #6707; the arrays go in #6716).

### 2. Which version, which forms

- **HQ** reads the current published version.
- **A branch studio** reads version 1 only, and only when it is published (owner decision 8: after version 1, versions are written in HQ's database only).
- **Legacy forms only.** A form is listed when it has a `legacy_gate`, a `legacy_display_json` and a key among the frozen ids. A form a later version adds beyond those is not listed, because the order path cannot take it yet.
- **`offer_mode` is not read.** `uk_ltd`, `sg_pte` and `ee_oy` keep today's behaviour. Owner decision 11 (answered A) is applied by #8836, which waits on the production report on #6684.
- **The US order rule is unchanged.** An order still needs a catalogue price, and the Wyoming charter still needs a counsel-approved body (D586). An order with no price is refused before any write, as today.

### 3. The fallback

For one release the frozen arrays stay as the fallback. A reader falls back when:

- the read throws (`read_failed`), for example when the tables are missing;
- there is no version to serve (`no_version`);
- the version lists no legacy form (`no_forms`), or has no such form (`no_form`);
- a form's display fields cannot be read (`unreadable_form`); the whole list then falls back, never a part of it.

Each hit is logged with `console.warn` as one JSON line, `{"event":"formation_catalogue_fallback","reader":…,"reason":…,"form_key"?:…}`. A reader never throws.

### 4. Tests

**`incorporation_catalogue_readers_6691.test.ts` (6 cases),** on the full migrated schema with the real legal router:

- **Parity.** The jurisdictions response, the handoff for each of the six forms (through the service and through the wizard route) and the name check's outcome for each form (its adapter shows in its "verify manually" reason) equal the fixtures recorded from main `d26a93a252` before the change. No fallback is logged.
- **Empty tables.** On the schema before the seed, each reader answers the same fixtures from the arrays and logs `no_version`, one line per hit.
- **No tables.** Each reader answers the fixtures and logs `read_failed`.
- **The catalogue really drives.** A version 2 relabels Wyoming, rewords a UK step, moves `us_de_llc` to `US-WY`, drops `ee_oy`'s legacy gate and adds an unknown form. HQ serves every change. A branch studio still serves version 1, equal to the fixtures.
- **A branch whose version 1 is a draft** falls back, logged.

**D586 and D601 run with catalogue fixtures.** `wyoming_formation_d586.test.ts` and `incorporation_filing_d601.test.ts` now load the catalogue migration and the version 1 seed into their databases. D586 adds one case: the list read from the catalogue equals the list read from the array.
