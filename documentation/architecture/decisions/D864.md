## D864 — The Telegram MCP connector: Axal's own chat tools, and no MTProto user session

- **Status:** decided by S1 for the owner, 2026-10-22 (#2510; part of #2508). Built by S08.
- **Basis:** `origin/main` at `c5ab8a0a4a`. Paths are relative to `cloudflare-worker/` unless they say otherwise.
- **Migration:** none.
- **Owner ruling (#2510, relayed by S1 on 2026-10-22 at 09:55Z): Q1 B; Q2 A.**
  - Full stored transcripts may leave through an explicit `validate:read` option only for consented, assigned sessions. Speaker labels and available D857 translations accompany the original. Pending, ignored or unconsented chats return no transcript; notes still awaiting YES are never fetched.
  - Phone numbers, provider identifiers, credentials and media links never leave. Text is result data, never a description or instruction.
  - No third-party MTProto user-session server is connected.

### 1. The study: Telegram and MCP

Read on 2026-10-22. A claim that cites no page I read is marked UNVERIFIED.

1. **Telegram publishes no MCP server that I could find.**
   - The official MCP registry's search for "telegram" ([registry.modelcontextprotocol.io/v0/servers?search=telegram](https://registry.modelcontextprotocol.io/v0/servers?search=telegram), first page, 30 entries) lists no server under a Telegram-owned namespace. Every entry is a third party's (`io.github.<user>/…`, `com.<vendor>/…`).
   - UNVERIFIED: that no official server exists anywhere. `core.telegram.org` and `telegram.org` did not resolve from the build container, so Telegram's own pages were not read.
2. **The community servers log in as the user, over MTProto.** Each needs an `api_id` and `api_hash` from my.telegram.org, and a login that leaves a session behind.
   - **[chigwell/telegram-mcp](https://github.com/chigwell/telegram-mcp):**
     - built on Telethon;
     - takes `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` and a `TELEGRAM_SESSION_STRING` (or a session file), made by QR or phone-code login;
     - its README says: "A Telegram session string grants access to the account it belongs to", and that its read-only mode "is an MCP tool-surface restriction, not a Telegram session sandbox or reduced Telegram account permission";
     - by default it is unrestricted across chats;
     - its tools read and send messages and manage contacts and groups.
   - **[sparfenyuk/mcp-telegram](https://github.com/sparfenyuk/mcp-telegram):**
     - "MCP server to work with Telegram through MTProto";
     - its sign-in takes the API id and hash and a phone number, then "the code you received from Telegram", plus the 2FA password when one is set;
     - it warns: "Any misuse of the Telegram API may result in the suspension of your account."
   - **[kfastov/telegram-mcp-server](https://github.com/kfastov/telegram-mcp-server):**
     - it is "for your personal account (MTProto, not bot API)";
     - it uses `api_id` and `api_hash`;
     - sessions are stored locally, next to a synced `messages.db`.
3. **What such a session reaches.** It reaches everything the account does: every chat, every contact, and the history.
   - That follows from the first two READMEs' own words above.
   - UNVERIFIED: that it also reaches calls. No README I read mentions calls.
4. **What Axal's channel already uses.** Axal's channel is the Bot API's Telegram Business connection (D684, D756). It sees only the chats the founder put under the Axal bot in Telegram › Settings › Telegram Business › Chatbots. It has no call methods and no access to the rest of the account.
   - These Bot API facts are the ones the code already relies on (`services/channels/telegram.ts` header: no call methods; `getFile` up to 20 MB).
   - They were not re-read here: `core.telegram.org` was unreachable. UNVERIFIED in this study.

**The ruling.**

- Axal never asks a founder for a Telegram login code, an `api_id`, an `api_hash` or a session string. It stores or accepts none, and connects no MTProto user-session server, its own or a third party's.
- The Telegram MCP connector is Axal's own tools over the Bot API Business connection, which sees only the chats the founder chose.
- The owner's Q2 A answer confirms this ruling: the custom-server path does not provide an exception for MTProto user sessions.

### 2. What is built

`src/mcp/tools/channels.ts`, registered in D846's registry (`src/mcp/server.ts`). The tools take a `provider` filter (`telegram`, `whatsapp`), so WhatsApp gets the same tools.

1. **`list_channel_chats`** (`validate:read`, read-only). The member's chats, newest first.
   - Each chat gives:
     - its Axal uid as `id`, its provider and its state (`pending`, `assigned`, `ignored`);
     - its consent where the provider asks for one (`not_asked`, `awaiting`, `given`, `declined`, `withdrawn`), else `null`;
     - `language`;
     - the message count and the count of voice notes still waiting;
     - its last activity;
     - for an assigned chat, its company, interview and session.
   - Filters: `provider`, `state` and `limit` (1–200).
2. **`get_session_insights` 1.1.0** (`validate:read`, read-only), for `{ company, session_id, include_transcript?, transcript_limit?, transcript_after_id? }`.
   - It returns the session's state, consent and digest state, and its suggestions (`validate_proposals` on that session): id, kind, state, payload (the member's edit when there is one), created and decided times.
   - A session whose consent was declined returns its state and no suggestions. D858 analytics are read through the shared service without citation quotes.
   - Explicit `include_transcript: true` returns only stored final segments while both the session and its assigned thread have current consent on an active integration belonging to the member. The SQL segment read repeats the gate to catch a withdrawal during the read. Any other state returns `transcript: null`.
   - Pages contain up to 200 segments (100 by default), in stored transcript order, with `next_after_id` and `complete`; the cursor must be a final segment of this session. Each segment projects only its Axal id, speaker label, text, offsets, source language and optional translation.
   - D857’s nullable columns are read when present. A translation is decrypted with the shared per-column cipher, bound to its segment id; absent or unreadable values are null. No translation model is run by this read.
3. **`assign_chat_to_interview`** (`validate:write`), for `{ company, chat, interview_id }`. It calls the inbox route's own service function, `assignThread`, so its rules and refusals are the route's:
   - `thread_not_found` for a chat that is not the member's;
   - `interview_not_found` for an interview the member cannot write;
   - `consent_other_venture` and `thread_busy`, as the route has them.
   - Before that, an interview outside the checked company is refused with the same `interview_not_found`.
   - It asks for no consent and records none, and it never sets `quote_consent`. A WhatsApp chat is linked and keeps waiting for its contact's consent (D754). A Telegram chat's notes still wait for the contact's YES (D756 §1.5).

**Who sees what.**

- A chat is the member's own (`channel_threads.user_id`, on an active connection).
- An assigned chat is listed only while its venture is one the grant still reaches. That is the server's `companies`: granted, and readable now (`canReadBoard`). The filter runs in SQL, so `limit` counts only what the call may see.
- A pending or ignored chat belongs to no venture yet. It is listed as the member's, with `company` null.
- Insights are read only for a chat session (`submitted_via` telegram or whatsapp) the member made, on an interview in the checked company. Anything else is `404 session_not_found`.

**Export boundary.** The default structured read returns no transcript, digest or citation quote. The opted-in transcript preserves stored labels and original segments, with privacy redaction of phone numbers, the thread/connection's provider identifiers, credential-shaped values and links. Links are redacted conservatively because a transcript URL may point to media. Pending messages, held note references, raw speaker ids and other internal segment fields are never projected.

The three descriptions remain fixed strings. Conversation content is data in the tool result; it never enters a description or an instruction field. This adds no new consent action and changes no quote consent.

**Metering and usage.** The tools run through `callTool`:

- each call writes one D843 usage row;
- D844's policy lists all three at price 0, so no hold is taken and no unpriced-tool warning fires;
- reads cost no AI tokens.

### 3. Not built here

- **Chat language.** D857 (#2502) is not yet on this base, so the chat list’s `language` remains null. The transcript reader supports its declared nullable segment fields when present. D858 analytics are now on `main` and reused. D859 proposals continue to come from the existing `validate_proposals` rows and retain their state.
- **Creating an interview from a chat.** The route's `create` target is not offered. The tool assigns to an existing interview only.
- **The consent actions.** Asking for consent, and recording the member's word, stay in the inbox.
- **Provider calls and held notes.** The MCP read calls no provider or model and never admits pending messages or downloads audio.

### 4. Tests

`test/channel_mcp_tools_d864.test.ts` (12 cases: the initial six and six owner-follow-up cases). It drives the real `callTool` on D684's channel world (`_channels_fixture.ts`) plus migration 524. Real Telegram webhooks make the chats and the inbox route assigns two of them.

1. Only the member's own chats are listed. An assigned chat drops out when its venture leaves the grant, or stays in the grant but stops being readable. Another member sees only their own.
2. The provider and state filters work, and the limit counts only what the call may see.
3. By default, no output of the three tools carries:
   - message text, a contact's name, a phone number, a chat or user id, a citation quote or a secret;
   - chat text in the tool listing.
4. Insights return kind, state and payload (the edit when there is one), never the citation. They refuse:
   - a session in another company;
   - another member's chat session;
   - a session that is not a chat session;
   - another user at the company check.

   A declined session shows no suggestions.
5. Assignment without `validate:write` is refused before any work. The route's refusals match code for code: another member's chat, an interview in another venture, and an interview the member cannot write. The assignment moves the waiting text into the session and leaves consent and quote consent alone.
6. Each call writes one usage row with its operation and outcome, and no AI tokens are held.

The pinned tool lists in `mcp_server_d666`, `mcp_authorization_d669` and `mcp_registry_d846` gain the three tools.

**Mutation check.** 14 mutations were tried, removing or changing one guard each. All 14 were caught:

- the venture filter, the owner filter, and the provider and state filters;
- the assignment's company check and the `IntakeError` mapping;
- the insights' company, owner and chat-session checks;
- the declined rule and the edited payload;
- a leaked citation, a leaked provider chat id and a wrong notes count.

### Rollback

Revert the owner-follow-up PR to restore the structured-only read. Nothing is migrated; the three original tools remain registered.
