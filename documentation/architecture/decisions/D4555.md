## D4555 — Cloudflare Agent Skills SDK as a loading adapter behind D1-authorized skills (#4555)

Cloudflare's Agent Skills SDK (`agents@0.32.0`, `agents/skills`) is used only to load and disclose skills progressively. It is not an authority. D1 decides which skills, at which versions and with which reads, before the SDK sees anything, and again at every activation and resource read. The current Axal loader stays behind the same local interface as the tested fallback. Nothing selects the SDK in production: `AGENT_ENGINE`, `AGENT_AUTONOMY`, the bindings and the run path in `agentRun.ts` are unchanged.

**The seam.** `services/agents/skillRunManifest.ts` defines `SkillRuntime` (`catalogue`, `cataloguePrompt`, `activate`, `readResource`, `readsFor`), the run-scoped manifest and the legacy loader. `skillsSdk.ts` is the SDK adapter and the only file that imports `agents/skills`, and only `manifest`, `loadSkillCatalog` and their types. `skillRuntime.ts` chooses between the two. The legacy loader is the default. The SDK is used only when a caller asks for it, the package is the pinned version with the expected functions, and the catalogue it loads matches the manifest exactly. Otherwise the legacy loader is used, and the reason is returned: `sdk_version_unsupported`, `sdk_surface_changed`, `sdk_error` or `sdk_catalog_mismatch`. If an SDK call throws or answers in an unknown shape mid-run, the legacy loader answers that call.

**The manifest.** It is built from D1 for one agent. The agent is read again and must be active and not an outside assistant. Every link is checked at its pinned version. It must pass `skillForRun()` (link, readable version, suspension, tool grants) and then `attachCheck()` without the pin exemption (company scope, published version, retired, suspended, role, tool grants). The skill must also be `published`. Each tool the version lists must be granted by the sponsor and belong to a source the rule book in force reads (`READ_KEYS` ∩ `reads`). Malformed parts (an unsafe slug, a missing description, steps that are not 1–20 strings) leave the skill out with `skill_malformed`. No skill is ever loaded at its latest version.

**Disclosure.** The catalogue shows names (slugs) and descriptions only. Activation loads the pinned version's purpose, output and steps: the SDK renders them for the adapter, and the legacy loader uses today's `skillPrompt()`. Resources come from a provider called only after the gates pass. By default the provider returns the pinned version's stored SKILL.md from D1, so no bucket is created. Paths that are absolute, escape the skill, name `SKILL.md` or sit under `scripts/` are dropped, and nothing executes a script (`run_skill_script` is refused). Each file is named by an opaque id: an HMAC under a key drawn for that manifest, over tenant, agent, skill uid, exact version and path. A guessed id, another tenant's id, an id from another run, a path and a missing file all get the same `resource_not_found` answer.

**Loading grants nothing.** Activation and read results put skill content in an untrusted-data block (`untrustedBlock('record_text', …)`), alongside Axal's own sentence that loading grants no tool and changes no rule. The reads a skill may use are the D1 intersection, whatever its text says. Nothing in the three files writes to D1 or calls a model. A run still reaches a model only through aiRouter's `run()` in `agentRun.ts`.

**Duplicate names.** HQ skills are listed first, then the company's, each by id, and the first skill to take a name keeps it. That is also the SDK's first-source rule (sources `axal-hq`, then `axal-company`), so both runtimes give the same answer: a company skill never shadows an HQ starter, and the shadowed skill's files get no id.

**Judgement calls.** The `createSkillTools` AI SDK adapter (`agents/skills/tools/ai-sdk`) is not used. It imports `ai`, which is not installed, and its tools would answer the model outside Axal's run path. Axal's `callSkillTool` handles `activate_skill` and `read_skill_resource` instead. The SDK catalogue excludes retired skills even where a legacy pin of one still runs. The existing import guards (`agent_runtime_contract.test.ts`, `agents_sdk_rules_3852.test.ts`) admit exactly one more file and one subpath. `skills_sdk_adapter_4555.test.ts` asserts the exports and declared signatures used here, so an SDK upgrade that changes them fails CI.

**Not done in #4751.** Wiring the adapter into `agentRun.ts`, a preview end-to-end run and the rollback demonstration. The addendum below covers all three.

### Addendum, 2026-11-07: the seam on the run path, behind a preview-only switch

This supersedes the first paragraph's "the run path in `agentRun.ts` [is] unchanged". `AGENT_ENGINE`, `AGENT_AUTONOMY`, `wrangler.toml`, the bindings, published skills and assignments are still unchanged.

**The wiring.** `agentRun` still gates a named skill with `skillForRun()` first, exactly as before. The skill's text then comes from `skillTextForRun` (`skillRuntime.ts`) instead of a direct `skillPrompt()` call. With the switch off, it returns `skillPrompt()` of the pinned version and reads nothing else, so the system prompt is the same text, byte for byte. With the switch on, it builds the run-scoped manifest and picks the runtime with `skillRuntimeFor`. Through the SDK it then loads the catalogue (authorized, exact-pin skills only), activates the named skill and reads each of that skill's files, and each activation and each read re-checks D1. All of this goes into the system prompt of the run's one `run()` call. The run path has no tool loop. Progressive disclosure, where the model chooses what to activate, would need a multi-call loop through the router, and this change does not add one. Files are capped at 16 KB of text per run (`RUN_FILES_MAX_CHARS`). Files past the cap are left out whole, never cut. `sessions.ts` and `src/agents/loop.ts` reach skills only through `agentRun`, so they get the same switch.

**Failure, by kind.**
- A D1 re-check that refuses fails closed: 409 `skill_unavailable` before any hold or model call. This covers an activation refused, and a file read refused while a fresh `recheck` also refuses.
- A file the store no longer has, while D1 still allows the skill, is left out.
- An SDK that cannot be used (`sdk_version_unsupported`, `sdk_surface_changed`, `sdk_error`, `sdk_catalog_mismatch`) uses today's text unchanged. So does a pinned skill that the stricter manifest leaves out (`skill_not_in_manifest`, such as a retired skill that is still pinned and still runs today).

The `run` event names the runtime and reason (`skill_runtime`) only when the switch is on. A legacy run's event is unchanged.

**The switch, and why this one.** `skillEngineOf` returns `cloudflare_sdk` only when all three hold:
- `ENVIRONMENT` is exactly `preview`;
- `STUDIOOS_ENV` does not say production;
- `AGENT_SKILL_RUNTIME` is exactly `cloudflare_sdk`.

It is a positive check for the preview Worker, not "anything but production". A local `wrangler dev`, or a Worker with `ENVIRONMENT` unset or mistyped, also runs the legacy loader. Production cannot select the adapter. Both var blocks a production deploy reads (`[vars]` and `[env.production.vars]`) set `ENVIRONMENT = "production"`, so no value of `AGENT_SKILL_RUNTIME` is even consulted there. The variable is declared nowhere in `wrangler.toml`, so even the preview Worker runs the legacy loader until someone sets it there by hand. The switch is never a D1 row or member setting: nothing a member or an agent can write reaches it, and it reads no binding but the two env strings. Rejected: a D1 or HQ flag (a member- or admin-writable store could flip production), `AGENT_ENGINE`/`AGENT_RUNTIME` values (shared with production and out of scope), and "not production" (wider than preview).

**Recorded run and rollback.** `skill_runtime_run_path_4555.test.ts` is the preview-only end-to-end run. It drives the real `agentRun` with the switch on, over a migrated test D1, through the real aiRouter `run()` with a stubbed model binding. It shows:
- the model sees only authorized exact-pin skills: not the draft, the other tenant's, the retired one or version 2;
- the real SDK's catalogue activates and reads;
- the content is framed as untrusted data;
- one model call, one usage row tagged with the pin, one settled hold;
- skill data does not change;
- mid-run D1 changes fail the run closed.

The rollback half runs the same step with the switch off in every way it can be off (production with the variable set, unset, development, a wrong value) and gets today's text, byte for byte, with no manifest read. Switching on and then off again returns the same text on the same data, and each unusable SDK falls back to it. **No live preview Worker was deployed for this.** The run is a Worker test, not a deploy.

**Parity, observed.** The SDK's activation renders the pinned version's purpose, output and steps, and Axal's frame states the allowed reads. It does not repeat `skillPrompt()`'s closing line ("Never invent a figure: write "Not recorded" …"). Settle that before any wider enablement. `agentQuote` and the D4121 cost estimate still count `skillPrompt()`'s text, so a switched-on preview run can cost more than its quote. Task-to-skill integration stays with #4535.

### Update, 2026-11-10: both parity gaps closed (#5340)

**The "Not recorded" rule.** `NO_INVENTED_FIGURE_RULE` in `skillEval.ts` is the one copy of the line. `skillPrompt()` ends with it, unchanged byte for byte. The switched-on text (`skillRuntime.ts`) now ends with it too: after the catalogue, the activation and the files, outside every untrusted-data block, so it is Axal's own instruction and not skill data. A change to the line changes both loaders.

**The quote.** The price now counts the text the selected runtime sends.
- *`agentQuote`.* When a quote names a skill and the switch is on, it runs the same `skillForRun` and `skillTextForRun` as the run and quotes that prompt: the catalogue, the activation, the files the run takes up to `RUN_FILES_MAX_CHARS`, and the rule. The test shows the quote equals the hold the run then takes, with files at the cap and with none. With the switch off, the quote reads no skill and is unchanged. Today it never counted the skill, and no caller passes one.
- *The per-run ceiling (D4162).* `agentRun` quotes the ceiling before the skill text is loaded. On the SDK path it now quotes again once the text is in, before any hold or tool read. A run whose activation and files take it over the ceiling is refused `402 run_ceiling`, with no hold and no model call. The hold itself was already sized from the prompt `run()` sends.
- *The D4121 estimate.* With the switch on, `pinTokens` counts `sdkEstimateText` for each pin. That function puts the real SDK adapter over a manifest built from the pins with no D1 read: every pin in the catalogue, each with its whole allow-list, and the version's stored SKILL.md as its file, capped as a run caps it. So the figure is an upper bound of what a run sends, and the test holds it to that. Where a run would fall back (unusable SDK, steps that cannot be used), the estimate counts today's text. With the switch off, `pinTokens` is the stored or legacy figure, as before. `skillRunChangeMicro` passes a single pin, so its catalogue lists that one skill only.

Not changed: the legacy path's ceiling quote still leaves the skill's text out, as before. The issue asks for the switched-off quote to stay byte for byte, so that is left as a separate call. Tests: four new cases in `skill_runtime_run_path_4555.test.ts`, each mutation-checked.
