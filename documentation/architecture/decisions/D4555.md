## D4555 — Cloudflare Agent Skills SDK as a loading adapter behind D1-authorized skills (#4555)

Cloudflare's Agent Skills SDK (`agents@0.32.0`, `agents/skills`) is used only to load and disclose skills progressively. It is not an authority. D1 decides which skills, at which versions and with which reads, before the SDK sees anything, and again at every activation and resource read. The current Axal loader stays behind the same local interface as the tested fallback. Nothing selects the SDK in production: `AGENT_ENGINE`, `AGENT_AUTONOMY`, the bindings and the run path in `agentRun.ts` are unchanged.

**The seam.** `services/agents/skillRunManifest.ts` defines `SkillRuntime` (`catalogue`, `cataloguePrompt`, `activate`, `readResource`, `readsFor`), the run-scoped manifest and the legacy loader. `skillsSdk.ts` is the SDK adapter and the only file that imports `agents/skills`, and only `manifest`, `loadSkillCatalog` and their types. `skillRuntime.ts` chooses between the two. The legacy loader is the default. The SDK is used only when a caller asks for it, the package is the pinned version with the expected functions, and the catalogue it loads matches the manifest exactly. Otherwise the legacy loader is used, and the reason is returned: `sdk_version_unsupported`, `sdk_surface_changed`, `sdk_error` or `sdk_catalog_mismatch`. If an SDK call throws or answers in an unknown shape mid-run, the legacy loader answers that call.

**The manifest.** It is built from D1 for one agent. The agent is read again and must be active and not an outside assistant. Every link is checked at its pinned version. It must pass `skillForRun()` (link, readable version, suspension, tool grants) and then `attachCheck()` without the pin exemption (company scope, published version, retired, suspended, role, tool grants). The skill must also be `published`. Each tool the version lists must be granted by the sponsor and belong to a source the rule book in force reads (`READ_KEYS` ∩ `reads`). Malformed parts (an unsafe slug, a missing description, steps that are not 1–20 strings) leave the skill out with `skill_malformed`. No skill is ever loaded at its latest version.

**Disclosure.** The catalogue shows names (slugs) and descriptions only. Activation loads the pinned version's purpose, output and steps: the SDK renders them for the adapter, and the legacy loader uses today's `skillPrompt()`. Resources come from a provider called only after the gates pass. By default the provider returns the pinned version's stored SKILL.md from D1, so no bucket is created. Paths that are absolute, escape the skill, name `SKILL.md` or sit under `scripts/` are dropped, and nothing executes a script (`run_skill_script` is refused). Each file is named by an opaque id: an HMAC under a key drawn for that manifest, over tenant, agent, skill uid, exact version and path. A guessed id, another tenant's id, an id from another run, a path and a missing file all get the same `resource_not_found` answer.

**Loading grants nothing.** Activation and read results put skill content in an untrusted-data block (`untrustedBlock('record_text', …)`), alongside Axal's own sentence that loading grants no tool and changes no rule. The reads a skill may use are the D1 intersection, whatever its text says. Nothing in the three files writes to D1 or calls a model. A run still reaches a model only through aiRouter's `run()` in `agentRun.ts`.

**Duplicate names.** HQ skills are listed first, then the company's, each by id, and the first skill to take a name keeps it. That is also the SDK's first-source rule (sources `axal-hq`, then `axal-company`), so both runtimes give the same answer: a company skill never shadows an HQ starter, and the shadowed skill's files get no id.

**Judgement calls.** The `createSkillTools` AI SDK adapter (`agents/skills/tools/ai-sdk`) is not used. It imports `ai`, which is not installed, and its tools would answer the model outside Axal's run path. Axal's `callSkillTool` handles `activate_skill` and `read_skill_resource` instead. The SDK catalogue excludes retired skills even where a legacy pin of one still runs. The existing import guards (`agent_runtime_contract.test.ts`, `agents_sdk_rules_3852.test.ts`) admit exactly one more file and one subpath. `skills_sdk_adapter_4555.test.ts` asserts the exports and declared signatures used here, so an SDK upgrade that changes them fails CI.

**Not done here.** Wiring the adapter into `agentRun.ts` waits until parity has been shown on a preview run and #4535's workflow design is in place. A preview end-to-end run has not yet been recorded.
