## D884 — Every investor has their own Mercury, on HQ or in a branch; Deals › Pipeline shows capacity beside intended cheques

- **Status:** decided by the owner on 2026-10-22, answer **A** to #2557's question 1. Filed by S1 as #2557, part of #2551. S13 builds it in two PRs: PR 1 (this file, the availability, the Pipeline section and the catalogue) and PR 2 (the investor page's rewrite on C3's `mcp` sign-in kind, the `used_by` links, the ProofOfFunds connect link and the Connectors-list wording), which waits on C1 #2552 and C3 #2554.
- **Basis:** `origin/main` at `784a1bed8d`. Worker paths are relative to `cloudflare-worker/src/`.
- **Stacks on:** D752 (the investor's proof of funds, HQ-only), D753 (the connector page), D840 part 4 (the investor's sections fed from their own Mercury).
- **Migration:** none.

### 1. The decision

The owner, 2026-10-22: investors have the Mercury connector as founders do, their own Mercury, read-only, used in **Deals and Pipeline**. Asked where investors get it, the owner picked **A: every investor, on HQ or in a branch. Proof of funds stays HQ-only.**

### 2. What changes

**Availability.** D752 hid the connector from an investor off HQ with `personal_hq_only_roles: ['investor']`, because proof of funds was the investor's only use and it is shared with Axal's admins on HQ alone. D840 part 4 gave investors their own sections, which concern nobody but the investor. So:
- the `mercury` row in `integrations/registry.ts` drops `personal_hq_only_roles`. `audienceFor` gives an investor `personal` on both hosts, and `/connect` takes an investor in a branch to the provider as on HQ;
- `routes/mercury_investor.ts` `policy()` no longer refuses a branch. It refuses a support session and any role but investor, as before;
- **proof of funds stays HQ-only by its use, not by the role.** `HQ_ONLY_USES` in `services/mercuryPersonal.ts` still holds `capital_attestation`, so `personalPolicy` answers `403 hq_only` off HQ, and `routes/mercury_attestations.ts` keeps its own branch gate. Every investor use in `PERSONAL_USES` is in `HQ_ONLY_USES`, and a test holds it.

**Deals › Pipeline (new).** `PipelineZone.jsx` draws `<FromMercury section="pipeline" />`, over `GET /api/mercury/investor/pipeline` (`pipelineFigures` in `services/mercury/investorFeeds.ts`):
- **capacity** is the fact Deals › Commit already wrote from Mercury (`mercury_investor_capacity`), dated as Mercury gave it. Pipeline opens no Mercury session: the figure has one source and one date, and the investor changes the accounts it counts in Deals › Commit;
- **intended cheques** are the investor's own `commitments`, not `withdrawn`, on deals still in the pipeline (`PIPELINE_DEAL_STATUSES`: `applied`, `scored`, `active`; not `funded` or `rejected`). A commitment whose amount is not a positive number is counted apart as "without an amount, not counted", never as 0;
- **headroom** is capacity minus intended cheques; a negative headroom reads "Over capacity by $N";
- **unknown is NULL.** With no capacity fact, `capacity` and `headroom_cents` are `null` and the page reads "Not recorded", never $0;
- **it writes nothing.** Its landing in `INVESTOR_LANDS` is the new `shown`: no fact, no proposal, no `connector_fed_items` row. A figure the investor wants to keep is the Commit fact they already accept;
- shown on the investor's own page only, never to an admin, a founder or a support session.

**The catalogue.** `MERCURY_FEEDS` (`integrations/mercuryFeeds.ts`) gains `investor_pipeline` (module `deals_pipeline`, labelled "Deals · Pipeline", `/deals/pipeline`). The investor variant's `feeds` in the registry is `mercuryFedModules('investor')`, so the declared investor feeds are the implemented ones by construction, and a test holds it.

**The page text (minimal in PR 1).** The investor variant's description, capabilities, tagline and long description say "on HQ or in a branch", lead with Deals › Pipeline and Commit, and keep proof of funds as an HQ-only statement for Axal's admins. The full rewrite is PR 2.

### 3. The MCP path

The investor's sections already read only through Sign in with Mercury (`openOwnInvestorMercury`, auth type `oauth_mcp`, D840 part 4). Pipeline reads no Mercury at all. Proof of funds reads through `personalConnection`, which takes a sign-in or a legacy pasted token (C3's rule that a token connection keeps working); `mercury_oauth_d840.test.ts` test 2 drives it on a sign-in. No feed works only on the token path, so none needed a fix.

### 4. Rules kept

- Read-only. No Mercury scope, tool or write is added.
- No migration. Stored entity connections and member token connections are kept.
- SQL is bound. `intendedCheques` binds the statuses as JSON through `json_each`.
- A balance stays on the investor's own page. Axal's admins see only the dated proof-of-funds statement (D752).
- No Axal entity data on an investor surface: the investor page names no entity, and a test holds it.
