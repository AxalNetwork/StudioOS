## D4621 — Studio layout: revisions across reset, one pending operation, a guarded exit (#4621)

### Decision

A Studio layout save names the revision it read. Three paths let a save land
on, or draw over, something it had not read. They are closed.

1. **Reset keeps the row.**
   - Before, reset deleted the row. The next first save was revision 1 again,
     so a draft read before the reset (revision 1) overwrote a layout saved
     after it (also revision 1).
   - Migration `202611070916_studio_layout_reset_tombstone` adds `reset_at`.
   - Reset sets `reset_at`, `layout = '[]'` and `revision = revision + 1`, only
     `WHERE reset_at IS NULL`, so a second reset changes nothing and a
     revision is never issued twice.
   - A reset with no row writes no row.
   - The read treats a reset row as the default (`source: 'default'`) and
     still reports its `revision`. A save at that revision clears `reset_at`.
   - The client's `expected_revision` is now null only when no row was ever
     made. A save from a copy older than the reset is 409 `stale_layout`.
2. **One operation at a time, in the client.**
   - While a save or reset is in flight the draft, Customise, Done and Reset do
     nothing, so the Saved line describes what was sent.
   - Each operation holds the generation it began in. A reload, a profile
     change or an unmount starts a new one, and an older response is dropped:
     it does not set the layout, a Saved line or an error on the newer read.
3. **Leaving with unsaved edits asks first.**
   - The router is a `BrowserRouter`, with no blocker, so `useLeaveGuard`
     catches the exits itself: `beforeunload`; a plain same-origin link click,
     caught before the router and re-sent once on Discard or Save; and Back,
     with a history entry pushed when edits begin.
   - The dialog is Stay, Discard changes, Save and leave. A failed save stays
     with its notice.
   - Nothing is installed while there is nothing unsaved.
