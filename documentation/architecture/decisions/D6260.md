## D6260 — Investor intro ask: show the quota, take a message, confirm before spending, and name the target (#6260)

- **Status:** built, 2026-11-15 (#6260). No migration, no new route.
- **Deciding records:** D550 (the ask, its duplicate-click lock and "pending asks disable repeats", all kept). D702 (who may see a person and a venture), reused for the names.
- **Code:** `cloudflare-worker/src/services/introAskTargets.ts` (new), `cloudflare-worker/src/routes/introductions.ts` (`GET /`); `frontend/src/lib/investorIntroRequest.js`, `frontend/src/pages/investor/InvestorIntroRequest.jsx`, `frontend/src/pages/investor/InvestorNetworkWorkspace.jsx` (Asked view), `frontend/src/lib/api.js` (`listIntroductions`).
- **Tests:** `cloudflare-worker/test/introductions_ask_targets_6260.test.ts` (the join, on the baseline schema); `frontend/test/investor_intro_ask_6260.test.mjs` (quota read, unreadable, exhausted, success). `investor_receipts_intros_d550.test.mjs` now passes a readable quota and otherwise runs as before.

### Why

"Request an intro" spent one of the quarter's asks (Free: 3) on one click. It showed no quota first and sent no message, though the route takes one. The Asked view printed "Founder #12", because `GET /api/introductions` joined no names.

### What changed

- **The quota comes first.** The control reads `GET /api/introductions/quota` (`tier`, `quarter`, `used`, `cap`, `remaining`) and says "N of M asks left this quarter". While it loads, or when it cannot be read, sending is disabled. A failed read says "Unreadable: your asks left this quarter could not be read, so an ask cannot be sent." It never shows zero. When no asks are left, the button is disabled and the line says so.
- **A confirm step.** "Request an intro" now only opens the step. It has an optional message (2,000 characters, the route's own limit) and the line "An ask is not consent…". It also says which quarter's ask it uses. Only "Send ask" posts. Cancel spends nothing.
- **A 402** shows the route's own `message`. Its body carries `message`, `used`, `cap`, `tier`, `upgrade_to` and `checkout_path`. `used` and `cap` update the quota line. `upgrade_to` names the plan in "Upgrade to Plus", which links to the investor pricing page. That page is where the checkout at `checkout_path` (`POST /api/billing/investor/checkout`) is started. Above Institutional, `upgrade_to` is null, and the line says no higher plan raises the cap.
- **D550 kept.** The synchronous lock in `createIntroRequests` still blocks a second post for a target that is already sending or pending. It still applies across a person row and an organization row. A recorded pending ask still disables a repeat, and asks that cannot be read still disable new ones. Success still says Request pending, never Introduced. After success, the recorded asks are read again, so the Asked view shows the new row and its message.
- **The Asked view** shows the target's name, the message ("No message was sent with this ask." when there is none) and the date ("Asked Nov 10, 2026 · 5d ago"). If the reader may no longer see the target, it reads "Not available". If the name lookup failed, it reads "Target name unreadable".
- **`listIntroductions` lost its trailing slash.** The Worker mounts `GET /` under `/api/introductions`, and Hono is strict about the trailing slash. `/api/introductions/` was a 404, so every investor's Asked view read as unavailable, and with it the button stayed disabled (D550's "unreadable asks disable new requests").

### The name rule (the join)

`GET /api/introductions` adds `target: { kind, name, available }` to each row, from `askTargets`. A name is sent only when the caller could already see it under D702's two rules. They are called, never restated:

- **A founder** (`founder_user_id`, or a `founder_id` record resolved to its lowest user id, as D702 resolves it) uses the person's effective profile visibility: `effectiveVisibilityFor` + `visibleToViewer` in `services/userSettings.ts`. The public profile read serves people by the same rule. The account must also be active and a founder (`role = 'founder'` or a founder record). An id that names another investor, a private profile, a deactivated account or nobody reads `available: false`.
- **A project** must be not deleted and not in `hiddenFromInvestor` (`services/investorFindable.ts`). Every investor read that lists or opens a venture applies that rule.

A row that fails its rule carries no name. A lookup that throws sets `targets_unreadable: true` and `target: null` on every row. It is said as unreadable, never as "not available". The query still reads only the caller's own rows (`investor_user_id = ?`). Another investor's ask is never listed.

### Asks to a target the investor cannot see are refused (owner's choice B)

`investorProjectIds` counts an investor's own `investor_introductions` row as reach. D702 does too, and `profile_pages_d702.test.ts` holds it there. Before this, `POST /request` did not check the target. So an investor who spent one ask on any project id could then find that venture, even one whose founder turned "Let investors find my venture" off.

The owner chose B over A (leave it) and C (D702 stops counting a pending ask as reach, which would change every investor venture read). `POST /request` now runs `askTargets` on each id the row would store (founder account, project, founder record), before the quota is read or spent:

- any id not available → 404 `target_not_available`, "This founder or venture is not available to you. No ask was sent and none was used." A hidden target and an unknown id get the same answer, so the refusal does not say whether one exists.
- the lookup fails → 503 `target_unreadable`. Nothing is spent and nothing is stored.

The page shows the route's own sentence, as it does for every refusal. D702's reach rule is unchanged: a refused ask stores no row, so it gives no reach.

Proposal 5's option C (asks stop charging quota) would change the quota line's words only. This work does not wait on it.
