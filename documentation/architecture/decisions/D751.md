## D751 — An OAuth connector Axal holds no client for says so in the catalogue, and its start is refused before any sign-in state is written

Issue #1880, slot S14. The plan and the decision are in #1868; S1's reconciliation (#1880, comment 6253546110, after #1899's ruling 2) set Zoom's readiness.

### What happened

On 2026-10-18 the owner pressed **+** on the Connectors card for GitHub and got: **"GitHub refused access. Ask your GitHub admin to allow Axal StudioOS, or try again. This integration is not yet configured on the server. Please contact your administrator."**

GitHub never refused anything, and the request never left Axal. Production holds no GitHub App client (`GITHUB_APP_CLIENT_ID` / `GITHUB_APP_CLIENT_SECRET`), so the Worker's start route answered 503, and the page labelled that 503 "refused". Three findings:

1. **The catalogue could not tell.** `GET /available`'s only readiness field was `has_implementation`, true from boot for every registered provider, so the card drew **+** for a connector that could not be connected.
2. **A state row was written first.** The start route wrote its `oauth_state_tokens` row, then called `buildAuthorizeUrl`, whose `_oauth_unconfigured` throw became the 503. Every press left a row nobody could consume, and an admin got the same sentence as a member.
3. **The callback passed the code through.** A client that went missing between start and callback reached the page as `reason=github_oauth_unconfigured`, which it read as "refused".

It was not GitHub-only: all nine OAuth connectors with an implementation (Calendly, Carta, DocuSign, GitHub, HubSpot, Salesforce, Slack, Stripe and Zoom) reached the same 503 when their client was unset.

### Decisions

1. **One readiness answer per provider: `true`, `false` or `null`.** It never carries a value, a preview or a name.
   - `true`: the env pair is set, or a `provider_oauth_keys` row decrypts.
   - `false`: no env pair, and the table answered with no usable row (a row that fails to decrypt is unusable).
   - `null`: no env pair, and the read failed (D227: unknown, never "unset").
   - Zoom is env only. Its readiness is the Channels card's own check (`providerAvailable(env, 'zoom')`): `ZOOM_CLIENT_ID`, `ZOOM_CLIENT_SECRET` and `ZOOM_WEBHOOK_SECRET_TOKEN`, each non-blank. Without the webhook token no transcript arrives (D757), so the Connectors card must not call Zoom set up when the Channels card does not. It is `true` or `false`, never `null`.
2. **Readiness and `ensureCreds` read the same cache entry.** The 60 s entry in `services/providerOauthKeys.ts` now records `readable` beside `value`. `loadOauthCreds` keeps its signature and answers; `oauthCredsReady(env, key)` returns `value ? true : readable ? false : null` from the same entry.
3. **`GET /available` adds `configured` only where it means something:** every `auth_type: 'oauth2'` provider whose impl implements `ready` (`readinessOf` in `integrations/registry.ts`; a throw reads `null`). No other row gets the field: `api_key` rows, Figma, Google Calendar, Microsoft 365, and an impl without `ready`. `has_implementation` and `publicDescriptor` are unchanged. `configured` describes Axal's OAuth client only: Calendly and HubSpot also take a personal token, so `false` does not mean they cannot be connected. Members get the field too; it is about Axal's setup, not anyone's account.
4. **The start route checks readiness before it writes anything** — after 404, 400, 402 and 503 `provider_rolling_out`, before `buildPkce` and `issueOauthState`.
   - `false` → **503 `oauth_unconfigured`** through `refuse()`, with `provider` and no state row: **"<Name> isn't set up on Axal yet, so it can't be connected. Nothing was sent to <Name>."** Only for `user.role === 'admin'` the body adds `env_vars` (the two names from `PROVIDER_ENV_VARS`, or Zoom's three from `ZOOM_CLIENT_ENV_VARS`) and, for a provider the Integration keys console can hold, `admin_href: '/admin?tab=integration-keys'`. Zoom gets no `admin_href`. No `Retry-After`: retrying cannot help.
   - `null` → **503 `oauth_setup_unreadable`** with `Retry-After: 60` and no state row: **"Axal couldn't check whether <Name> is set up, so it can't be connected right now. Nothing was sent to <Name>. Try again in a minute."** Falling through would have written a row and then printed "isn't set up", which nothing measured.
   - An impl with no `ready` (only test fakes, after decision 7) is not pre-checked.
   - **The backstop stays.** If `ready` said true and `ensureCreds` then threw, the `/_oauth_unconfigured/` catch answers with the same builder: the same sentence and admin fields. The thrown text goes only to the log (D278).
   - **`coming_soon` is refused here as `/connect` refuses it**, after `active_company_required` and before the plan gate: one `comingSoonBody(desc)` serves both routes (`error: 'coming_soon'`, the "isn't available yet" sentence, `notify_me_url`, `Retry-After: 86400`).
5. **The callback maps a missing client to `reason=not_configured`.** Every other reason keeps its first token, and the `activity_logs` row is still written.
6. **Who reads this.** #1879 maps 503 `oauth_unconfigured`, 503 `oauth_setup_unreadable` and `reason=not_configured` to true sentences; #1881 reads `configured`; #1882 lists the same states on Integration keys; task T9's live smoke reads `configured`; D753's connector pages and D757's Zoom source read this field and invent no other. Until #1879 merges, the page still prefixes the new sentence with its "refused" banner, which is no worse than before.
7. **A guard keeps it complete.** Every registry `oauth2` provider with a registered impl implements `ready`, and the list is exactly the nine; a new one fails `connector_readiness_d751.test.ts`.

What does not change: Build's `systemChoices`; the Channels card's Zoom `available`; `PRODUCTION.md` (#1885's).

### Files

- `services/providerOauthKeys.ts`: `readable` on the cache entry, `credsEntry`, `oauthCredsReady`.
- `services/channels/zoom.ts`: `readClientCreds`, `ZOOM_CLIENT_ENV_VARS`, `zoomConfigured`, and `ready` on its `registerProvider`.
- `integrations/registry.ts`: `ProviderImpl.ready?` and `readinessOf`.
- `providers/{calendly,carta,docusign,github,hubspot,salesforce,slack,stripe}.ts`: `ready` through the same dynamic import `ensureCreds` uses.
- `routes/integrations.ts`: `configured` on `/available`, `comingSoonBody`, `unconfiguredRefusal`, the start pre-check, the backstop and the callback mapping. Zoom's names are loaded by dynamic import, so the route registers nothing.

### Verified

`cloudflare-worker/test/connector_readiness_d751.test.ts`, 11 tests over real SQLite with `oauth_state_tokens` present: the catalogue with nothing set, with GitHub's pair, with a D1 row that decrypts and one that does not, and with the key table unreadable; GitHub's start refused with no state row, the founder's and the admin's bodies, and the control that writes its one row; the backstop's sentence without the thrown text; the callback's `not_configured` and its control (`github_token_exchange_failed`); Slack and Zoom (all three secrets, the pair alone, whitespace); Salesforce's `coming_soon` body equal to `/connect`'s; one cache read for `/available` and the start; no fixture secret or client field in any refusal or catalogue body; and the guard. `connectors_audience_d710`, `connectors_d650`, `build_connectors_d686`, `github_connector_d655` and `channels_meetings_d684` pass unchanged.

**Mutations: 13 run, 12 caught.** Caught: readiness returning `value !== null`; readiness reading the env only; the route sending `configured` on every row; the check moved after `issueOauthState`; the null branch falling through; the admin fields sent to every role; Zoom given an `admin_href`; the backstop removed; the callback mapping removed; the start's `coming_soon` check removed; Zoom's check without the trim; `ready` removed from one provider. The survivor drops `readinessOf`'s `auth_type` test, which is equivalent: no non-OAuth impl implements `ready`.

### The page's words (#1879, slot S15)

The Worker half above stops the false 503 and says why. This half makes the page say it. All the rules are pure functions in `frontend/src/pages/account/connectorsModel.js`, so D753's connector page reuses them; `ConnectorSheet.jsx` only draws. No Worker change, no `/api` method, no migration.

1. **"Refused" means the provider said no.** It stays for a provider's own `error` on the return, a token exchange the provider rejected, `rolling_out`, and every code not named below. The existing `refused` sentences are unchanged.
2. **`unconfigured`: Axal holds no client.** `isUnconfigured(code)` is true for `oauth_unconfigured`, any code ending in `_oauth_unconfigured`, the first-party starts' `oauth_config_missing`, and the `not_configured` return (this decision's callback, and LinkedIn's). The match is on the code, never the status: a 503 is also `provider_rolling_out`, which stays `refused`.
3. **`company`: no company to write into.** `active_company_required` from the start or from `POST /connect`, and the return's `company_not_linked`. `connectFailure` checks it before `badkey`, so HubSpot's token path no longer says "That key is not valid." about a key the Worker never checked.
4. **`setup_unreadable`: Axal could not read its own setup** (decision 4's 503 `oauth_setup_unreadable`). Its banner is the Worker's message, Axal's own sentence, with a fallback; **Try again** is offered, because a retry can work.
5. **The words.** None says "refused" or "Ask your <Name> admin", and none prints the code.
   - `unconfigured` from a press: "<Name> isn't set up on Axal yet, so it can't be connected. Nothing was sent to <Name>."
   - `unconfigured` from a return: "… Nothing was connected." The member did visit the provider, so "nothing was sent" would be false there.
   - `company`: "<Name> connects for one company. Choose a company in the sidebar, then connect again. Nothing was connected."
6. **The sheet.** `unconfigured` (neutral) and `company` (warn) have Back and Close and no Try again, and the Worker's message is not appended: it repeats the banner, and Google's names env vars. All three views are in `CONNECT_VIEWS`, so a blocked Build project still offers only Close.
7. **The way forward, for the one person who can take it.** On `unconfigured`, a Super Admin (`isSuperAdminUser`) also sees "Set up <Name> in Integration keys". Its target is the body's `admin_href` when it matches `/^\/admin\?tab=[a-z0-9-]+$/` (`adminKeysHref`), else `/admin?tab=integration-keys`; a crafted value never becomes a link (D651). A plain Admin can open that console but not save a key, so gets no link.

Tests: `connectors_page_d651.test.mjs` (the rules, the sheet as markup, a blocked project, and the view inside D753's page layout) and `connectors_api_d651.test.mjs` (both returns on the connector page, the press with the Worker's exact 503, the Super Admin's link with a kept, a fallback and a crafted `admin_href`, the plain Admin, `setup_unreadable`, and HubSpot's token without a company). Fifteen mutations, each made alone, all caught.

### The cards (#1881, slot S15)

#1879 makes the sheet tell the truth after a press; this removes the press. Frontend only, reading decision 3's `configured`. The rules are pure functions in `connectorsModel.js` (`oauthOff` on each row, `patOnly`, `keysHref`), so D753's pages read the same field through the same functions.

1. **The field is read as a strict `false`.** `oauthOff = auth_type === 'oauth2' && configured === false`. `true`, `null` (unreadable) and a missing field keep today's behaviour; an `api_key` connector is never `oauthOff`. `configured` is not an alias field: the first-party rows keep their own status.
2. **No token path: unavailable.** `available` also requires `!(oauthOff && !supports_pat)`, so the existing `unavailable` path draws "Not set up here" with no action on the Discover card, Build's row and the `?tool=` deep link. The card stays in Top connectors with its reason.
3. **A token path: the token is the only way in** (`patOnly`). Calendly's `pre` has "Continue" to the token form, the steps read "Key", and one line says "Sign-in with Calendly isn't set up on Axal yet, so Calendly connects with a personal access token." HubSpot's key view drops "Connect with OAuth instead". Both keep their +.
4. **The key form's refusal is `badkey`.** `submitKey` maps a failure as an `api_key` connector, so a mistyped Calendly token reads "That key is not valid…", never "refused". #1879's `company` check still runs first.
5. **No door opens a sign-in that can only fail.** `openingView` returns #1879's `unconfigured` for an unconnected `oauthOff` row with no token path, before the plan lock, so nothing sells a plan for what cannot connect. A connected row still opens its detail.
6. **The phone row says what the card says.** An `unavailable` row's pill is "Not set up here" (or "Status unreadable") ahead of "Beta". Since D753 F1 every row links its connector's page, which draws the same "Not set up here", so the row keeps that link rather than becoming a plain row, as the plan had it before D753.
7. **A Super Admin gets the way to the keys; nobody else does.** `keysHref(p, { superAdmin })` gives `/admin?tab=integration-keys`, a fixed path, only for a Super Admin, an `oauthOff` row, not coming soon, and not the entity row. The Discover card draws "Add its keys in Integration keys" under its description, Calendly's and HubSpot's included; the phone Suggested row goes there instead, with that sentence. Build's sheet draws no link. The first-party rows get none until #1882 decides whether their clients become console keys.

Tests: `connectors_page_d651.test.mjs` (the rules, the card for a member and a Super Admin, Build's row and deep link, `openingView`, Calendly's and HubSpot's sheets), `account_phone_d700.test.mjs` (5b: the phone row, a Super Admin's row, Microsoft's), and `connectors_api_d651.test.mjs` (the section inside `AuthProvider` for a Super Admin, a plain Admin and a founder; Calendly's Continue starting no sign-in; a rejected token as `badkey`). Fourteen mutations: thirteen caught. The survivor adds `configured` to the alias fields, which is equivalent: the first-party rows compute neither `oauthOff` nor `available` from it.

### Integration keys says what to register (#1882, slot S26)

On 2026-10-18 the owner's GitHub press failed because nobody had registered the StudioOS GitHub App, and Admin → Integration keys did not say what to register, under which names, or which card a missing key breaks. Worker first, the console in the same PR, no new `/api` method (`adminListIntegrationKeys`), nothing secret.

1. **Each managed row says what to register and what it serves.** `GET /api/admin/integration-keys` adds four fields to every `providers` row, in the route, not in `listProviderKeyStatus`, so HQ's Platform summary (D213) reads what it did: `env_vars` (`[id, secret]` from `PROVIDER_ENV_VARS`), `callback_url` (or `null` for crunchbase, affinity, telegram, gcip), `connector` (`{display_name, status, tier}` or `null`) and `guide_href` (or `null`). Every D227 field and the order stay.
2. **The callback URL is the provider's own.** `oauthCallbackUrl(env, key)` in `util/url.ts` (#1899 ruling 3) builds `<callbackBase>/api/integrations/oauth/<key>/callback`; each provider's `redirectUri` is exported and returns it, as does Zoom's; `linkedinRedirectUri` is exported. The route's `CALLBACK_URL` is exhaustive over `ManagedProviderKey`, so a new managed provider fails `tsc` until it is listed. An empty URL is sent as `null`.
3. **`connector`.** A key whose registry row is `oauth2` gets its three facts (github, slack, hubspot, salesforce, docusign, calendly, carta, stripe); LinkedIn gets its first-party card's constant; everything else `null`.
4. **`guide_href`** points only at a file in this repository: `github` and `zoom` at `documentation/architecture/PRODUCTION.md`, until #1885's runbook (`documentation/operations/GITHUB_CONNECTOR_APP.md`) lands; whichever merges second points `github` at it. A test holds every path to a real file.
5. **`other_oauth`**, read-only: `zoom`, `google_calendar`, `microsoft_365`, each `{key, configured, env_vars, fallback_env_vars, callback_url, connector, guide_href}`. `configured` is measured from env (`zoomConfigured`, `googleOAuthAvailable`, `microsoftOAuthAvailable`), never unknown. Zoom's names are #1880's `ZOOM_CLIENT_ENV_VARS`, three (the webhook token included, #1899 ruling 2), not the plan's two. Google and Microsoft name their `*_CAL_*` pair and their legacy fallback; `services/calendar.ts` exports both pairs, and `preflightOAuthSecrets` pushes the same constants, its output unchanged. These clients are not settable from the console.
6. **Nothing secret; access unchanged.** No value, preview or fragment of a client is added; `other_oauth` rows have no `client_id_preview`. `GET /` stays `requireAdmin`; no write is added; the read writes no audit row and makes no outbound call.
7. **`state` is unchanged.** D227's four states stay. Known gap kept: a database row that will not decrypt reads `db` here and `configured: false` in #1880's catalogue.
8. **What the console shows** (`lib/integrationKeys.js`, pure): the Worker's `env_vars` (`envNamesFor`, the page's map only as a fallback; GitHub joins both maps); GitHub's hint; "Callback URL to register with <Name>" with Copy ("Copied" for 1.6 s; "Copy failed. Select the address instead."), also above the Configure dialog's inputs; the members line (#1881 is on `main`: 'Members see "Not set up here" on the <Name> card.', or "<Name> is coming soon, so members can't connect it yet."; '' for held or unknown keys); "Setup guide" only through `safeGuideHref`; "Or set them as the Worker secrets <ID> and <SECRET>." on unset rows; and a "Set at deploy only" section with each client's `wrangler secret put` lines, its fallbacks, callback, members line and guide, and no Configure, Rotate, Remove or Test. An older Worker's answer draws no section and no callback line.

Tests: `cloudflare-worker/test/integration_keys_setup_d751.test.ts` (8 cases: names and order, the callback under three bases and per provider, `connector`, guides on disk, `other_oauth`, no value leaves, access, the calendar preflight) and `frontend/test/integration_keys_d751.test.mjs` (7 cases: the maps, `envNamesFor`, `membersSeeLine`, `wranglerPutLine`, `safeGuideHref`, the two components as markup, the panel's wiring).
