## D1312 — Lovable part 4: sign-ups from a Lovable page into Demand signals (migration 646)

S22, 2026-10-27, for #3432 (part 4 of #2398). The owner answered #2398 decision 3: A, yes. Built on
`main` at `2fb4a32a`, after Lovable part 2 (D1082, #3525) and part 3 (D1083, #3455). Canvas:

### 1. What is built

**Migration 646** (`646_lovable_signup_tokens.sql`; 640 and 645 were taken, per S21's notes on the issue):
- `lovable_signup_tokens`: `uid`, `project_id`, `experiment_id`, `token_hash`, `created_by`,
  `created_at`, `revoked_at`. Only the token's SHA-256 is stored.
- `lovable_signup_seen`: one row per accepted sign-up, holding a keyed hash of (address, email),
  `UNIQUE(token_id, email_hmac)`. It is both the duplicate check and the address's count. The issue
  named only the tokens table; this second table is how a repeat is caught without storing an email.

**The token** is 32 hex characters derived from the row's `uid` with the Worker's index secret
(`indexHmac`, `services/columnCipher.ts`). So the venture's writers are shown the address again
(the canvas draws it with Copy) while only its hash is stored. A rotated index secret changes every
address; the founder then makes a new one.

**Routes:**
- `POST /api/validate/lovable-signups/:token` (`routes/lovable_signups.ts`), public:
  - form-encoded (or JSON) `{ email, company_website? }`;
  - the brand route's honeypot (`HONEYPOT_FIELD`) answers as success and writes nothing;
  - a repeat of the same email on the same address answers as success and writes nothing;
  - an unknown, malformed or turned-off address is 404; a missing or bad email is 400;
  - each accepted sign-up writes one `waitlist_signups` row: `source = 'lovable'`, `audience = 'customer'`,
    an empty email, no name, no `landing_page_id`, and the first 16 bytes of the IP's SHA-256 as
    `ip_hash` (the brand route's form);
  - a browser's form post gets a short thank-you page; a fetch gets `{ ok: true }`.
  - **Not under the CORS allowlist and no CORS header:** a plain HTML form post needs none, and the
    Lovable app's origin is never added.
  - **Rate limit:** the `lovable_signup` bucket, 6 a minute per IP, failing closed, as the landing waitlist.
  - **CSRF:** exempt by path prefix; the token in the address is the authorisation.
- `POST` and `DELETE /api/cycles/validate/lovable/signup-token?project=` (`routes/lovable_app_links.ts`):
  make and turn off an experiment's address, behind the same scope as the app link (`canWrite`; a support
  session is refused; Validate only). Making one turns off the live one, so one address is live per
  experiment. Each write records a Validate activity line that names no token.

**Reads and counts:**
- `weeklySignups` (`services/cycleValidate.ts`, now exported for its test) already counts every
  customer `waitlist_signups` row, so the Lovable sign-ups count in Demand and urgency signals with no
  change to the query. The test holds it.
- `lovablePart` gives each Validate slot `signup` (`{ live, uid, address, count, since }` or `null`)
  and `signup_unreadable` when the read fails, and the part `signup_writer`. The address is drawn only
  for the venture's writers; every reader sees the count.
- The owner's waitlist list (`GET /api/brand/landing/by-project/:pid/waitlist`) leaves Lovable rows out:
  they are counts, not contacts.

**The prompt** (part 2's `landingTestPrompt`): with a live address, it adds "Make the sign-up form a
plain HTML form: method POST, action [address], one email field named "email". Do not store the email
anywhere else."

**The page** (`FromLovable.jsx`, LV5): under each experiment's app link, "With a sign-up address":
- no address: "No sign-up address yet…", and for a writer Make a sign-up address;
- live: "N sign-ups received", and for a writer the address in mono with Copy and Turn off…;
- the note "Point the app's form at this address. Only the count is kept, never the names or emails.";
- Make and Turn off each ask first, in place, saying what changes;
- unreadable: "not the same as none".

The client is `lovableAppLinksApi.makeSignup` and `turnOffSignup`.

### 2. Departures from the issue and the canvas

- **The address is an https URL**, not the canvas's mail-like `signups-h2-7k2q@in.axal.vc`: the issue's
  endpoint is an HTTP form post.
- **"target 40"** is not drawn: an experiment's target is free text (`hypothesis_experiments.target`),
  not a number, and the slot does not carry it. The count stands alone.
