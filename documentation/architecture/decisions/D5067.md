### 1. Prototype/MVP: a measured zero stays 0

`prototypeMvp.record()` built its "Tests run" fact as `Number(done?.n ?? 0) || null`. `COUNT(*)` only ever
returns 0 or a positive integer, never `null`, so the `?? 0` never fires — but `|| null` does, for every
feature with zero *done* sessions: `0 || null` is `null`, and the generic `fact()` helper then reads any
`null` as "Not recorded", with the reason "No test session is done yet." A feature that genuinely has no
session done read identically to one the platform could not check at all.

**Fix:** the count is read once, kept as a plain number, and only a *missing* count (the query itself failed)
falls back to `null`:

```ts
let testsRun: number | null;
let testsReason = 'No test session is done yet.';
try {
  const done = await ctx.env.DB.prepare(
    "SELECT COUNT(*) AS n FROM mvp_test_sessions WHERE feature_id = ? AND project_id = ? AND status = 'done'",
  ).bind(f.id, ctx.projectId).first<{ n: number }>();
  const n = Number(done?.n);
  testsRun = Number.isFinite(n) ? n : null;
} catch {
  testsRun = null;
  testsReason = 'Unreadable: the test session count could not be read.';
}
```

`fact('Tests run', testsRun, testsReason)` now reads `0` (a genuine, measured zero), distinct from a read
failure, which gets its own `Unreadable:` reason — the house rule's third state ("Where a read fails, it says
Unreadable, never zero") was previously unreachable for this fact; it is wired in now even though D1's
`COUNT(*)` essentially never throws, so a real regression here (a dropped column, a locked table) reads
honestly instead of as "no test session is done yet."

Boundary tests (`cycle_records_build_d690.test.ts`, test 13): 0 sessions → `{ value: 0 }`; 1 session →
`value: 1`; a query that throws (a `failingDB` helper matching the exact SQL by substring, as
`cycle_focus_d692.test.ts` already does) → `value: null, reason: /^Unreadable:/`, while the record's other
section (`Test sessions`, which queries the same table with a different statement) still reads — only the one
fact's own query was made to fail.

### 2. Solution design: `linked` now means "a pain theme OR a hypothesis", everywhere

The feature row's own display already treated a hypothesis as a link (`featureRow`'s comment: "A feature with
neither a pain theme nor a hypothesis links to nothing"; `cycle_records_build_d690.test.ts` already carried the
assertion "a hypothesis is a link: not 'Links to nothing'"). But the module's `linked` key — the list filter
(`FEATURE_KEY_SQL.linked`), the chart (`solution()`'s aggregate `counts.linked`) and the card's `facts.linked` —
only answered "yes" when a pain theme was stored, introduced in D4603 part 2a when the card's counts moved to
SQL aggregates and the hypothesis half of the row's own rule was not carried over. A feature linked only to a
hypothesis read as connected in its own row and as **Unlinked** everywhere else that used the word.

**Choice: any-evidence-linked** (pain theme OR hypothesis), not pain-only. The alternative the issue allowed —
tightening the row to agree with the narrower, pain-only `linked` — was rejected because it already has a
dedicated, deliberately-tested rule (the comment and test above) that a hypothesis is a meaningful link; making
the row *stop* treating a hypothesis as a link to match the SQL aggregate would have reversed that, documented
intent, not clarified it. Making the aggregate honour the rule the row already encodes is the smaller,
better-supported change, even though it revises D4603 part 2a's "linked is a stored pain theme" line.

**Fix**, all three kept in lockstep:
- `FEATURE_KEY_SQL.linked`: `CASE WHEN pg.title IS NOT NULL OR h.claim IS NOT NULL THEN 'yes' ELSE 'no' END`.
- `featureRow()`'s `keys.linked`: `(f.pain_theme != null || f.hypothesis != null) ? 'yes' : 'no'`.
- `solution()`'s aggregate `counts` query: joins `hypotheses` too, and counts `pg.title IS NOT NULL OR h.claim
  IS NOT NULL`.
- Wording that names the metric: the module description, the "Link N features…" next-step text
  (`cycle_build.ts`), and the Build index row's "N features linked to a pain…" (`cycleFocus.ts`, which reads
  the same `facts.linked`) all now say "a pain theme or hypothesis", so a reader of the index is told the same
  rule the filter and chart apply — a label that quietly meant something narrower than the number behind it is
  exactly the bug this item reports, one level up.
- The cell shown for the Pain theme column is unchanged (still blank when a hypothesis-only feature has no pain
  theme, "Links to nothing" only when it has neither) — only the *classification* changed, not the display text
  a pain-theme-specific column already carried correctly.

Tests updated to the new, correct counts: `cycle_records_build_d690.test.ts`'s `linked:no` filter (a
hypothesis-only feature moves from the "no" bucket to "yes"), and the two literal "N features linked to a
pain…" strings in `build_bounded_reads_4603.test.ts` and `cycle_focus_d692.test.ts` (their fixtures' counts
were unaffected, since neither used a hypothesis-only feature, but the wording changed). `keys.linked matches
the chart's linked count` (test 11) needed no change — it derives its expectation from the read itself, so it
proves the row, the filter and the chart agree without hard-coding a number.

### 3. Product roadmap: Feedback it answers says when it is incomplete

The section read `product_feedback … LIMIT 20` with nothing to say so. No sibling record service in
`cloudflare-worker/src/services/records/` already has a "latest N of TOTAL" or "View all" convention for a
*section* (every existing `LIMIT 20`/`LIMIT 200` there is a plain, silent cap); the closest established pattern
is the module list's own bounded pages (`#4603`'s `PAGE_SIZE`/`paged`), which does not apply here since a
record's section has no page parameter in its contract (`SectionSpec.read(ctx, id, record)` — see item 4 below
for why that was not widened for this PR).

**Fix:** a second, bound `COUNT(*)` alongside the existing `LIMIT 20` read; when the total exceeds what is
shown, a trailing row says so and links to the one place that already lists every one of this venture's
feedback records without a module boundary — Grow's own "Product improvement" module
(`/grow/product-improvement?project=<id>`), which `cycleFocus.ts` already links to as "Open Product
improvement" and whose list reads every `product_feedback` row for the project (`cycle_grow.ts`), not just one
roadmap item's. That list does not yet accept a per-item filter and the deep link does not pre-fill its search
box (the generic module page keeps no query state across navigations), so "View all" lands on a complete,
project-scoped list the member can search by hand rather than a pre-filtered one — a real gap for a follow-up,
not a silent cap.

```
{ a: 'View all feedback', b: 'Showing the latest 20 of 23', href: '/grow/product-improvement?project=7' }
```

Boundary test (`cycle_records_build_d690.test.ts`, test 14): exactly 20 feedback rows draws no trailing row;
21 draws it, with the exact count and href, and the 20 real rows are still the 20 most recent.

### 4. Product roadmap: the dependency picker's 200-item ceiling, without raising the number

`addDependency`'s own write path was never actually capped: `references()`'s `ownedRow` check, and
`addOkrDependency`'s own membership check (`here.has(okrId) && here.has(blocksOkrId)`, read fresh against every
roadmap item in the project), both validate against the *whole* project, not the 200 rows the picker happened
to offer. The bug was pure discoverability: an item past the first 200 (by `sort_order`, `id`) could not be
selected, only typed in as a raw id by a client that already knew it.

**Fix — a project-scoped typed fallback, not a bigger list.** The `LIMIT 200` preview is unchanged (so the
issue's 200/201 boundary stays meaningful), but once the project holds more roadmap items than the preview
shows, the "Add a dependency" form gains two things: a `note` on each choice field naming the total
(`Showing the first 200 of 219. Not listed? Type its exact title or number below.`) and a plain text fallback
field per side (`waits_on_other` / `blocks_on_other`). `addDependency` resolves whichever of the four fields was
filled — a numeric string is read as an id (as the picked `waits_on_id`/`blocks_id` already were); any other
text is matched against `roadmap_okrs.objective`, case-insensitively, **scoped to `ctx.projectId`** — through
a new `resolveRoadmapRef()`, then goes through the exact same `addOkrDependency` write every picked option did.
A title that matches nothing in this project (including one that belongs to another venture entirely) resolves
to nothing and is refused (400), the same as any other validation failure here — never a 404-shaped leak of
another project's data, since the lookup never leaves `project_id = ctx.projectId`.

This was picked over building a live-search field because the generic record-action form
(`FormLightbox.jsx`'s `kind: 'CH'`/`'T'` rendering) has no search wiring for an action's own fields today — only
the separate "Add new record" forms do (`onSearch`, wired in `CycleRoute.jsx` only for that flow, calling a
module's own `formOptions` search, as `raise.ts`'s `capitalOptions` already does for "Add investor"). Reaching
parity for a record *action*'s field would mean extending that wiring and the shared form renderer, which is a
frontend capability change outside this issue's two backend files, not a one-item bug fix; the typed fallback
needs none of that and already makes every valid dependency reachable today. A follow-up to give the Add
dependency form that same live search, once the generic wiring exists, is a natural next step but is not this
fix's job.

Boundary tests (`cycle_records_build_d690.test.ts`, test 15): exactly 200 other items → 200 options, no note,
no fallback field; 201 → still 200 options (the number is never raised), a note naming 200 of 201, and the
fallback field appears; typing the 201st item's exact title through `waits_on_other` creates the edge (proving
the write path was never the bottleneck); typing another project's item's exact title through `blocks_on_other`
is refused and writes nothing (project-scoped).
