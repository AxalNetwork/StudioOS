## D4855 — A promo code is redeemed only inside the licence's promotion ceiling, decided by one rule (#4855)

- **Status:** Built for #4855, 2026-11-07. Worker, plus the reason sentences in the four checkout screens.
- **Builds on:**
  - migration 256 (`branch_promo_ceiling`, the ceiling HQ pushes to a branch) and 260 (`licence_promo_ceilings`, HQ's copy);
  - D1273 (a code's scope and per-member limits) and D1274 (what each redemption was for);
  - D4293 (influencer offers).
- **One migration:** `202611071527_promo_ceiling_reservations.sql`.

### What was wrong

Platform › Promos said it plainly: "A promo ceiling is not checked against these codes: nothing enforces one at checkout". HQ could set a ceiling for a licence and a branch could hold it, and no checkout read it. `branch_promo_ceiling.issued_cents` was never written by anything. Seven code paths each called `validatePromoForProduct`, the terms-only check, and then charged.

Two further faults sat beside it. The plan quote validated with no member, so a once-per-member code read as "already used" in the quote and not at the start. A code's cap was read, then the checkout went ahead, with the redemption recorded later by the webhook.

### What was decided

1. **One rule, in `services/promoRedemption.ts`.**
   - `canRedeemPromo(env, { code, productId, amountCents, currency, buyer, reference? })` answers and writes nothing.
   - `reservePromo(...)` answers and, in the same step, takes the discount out of the ceiling.
   - The code's own terms are still decided by `validatePromoForProduct` (state, expiry, an amount-off code's currency, listed products and plans, billing interval, once per member, the code's cap, first purchase only). It stays the home of those; the new module calls it first.
   - No route or service outside `promos.ts` and `promoRedemption.ts` names `validatePromoForProduct`. A test reads the sources and fails if one does.
2. **The ceiling is the licence's, and a licence is a branch Worker.** A code names no licence (D1272), so the licence is the Worker the buyer is on. A branch holds one row, `branch_promo_ceiling`, for one period. HQ's own Worker has no licence, so no ceiling applies to it and it writes nothing to the new table.
   On a branch a discount above 0 is refused when:
   - HQ has pushed no ceiling for the current quarter, or one for another quarter: `ceiling_not_recorded`. A missing ceiling is not an unlimited one and is not 0, and no figure is invented;
   - the ceiling's currency is not the sale's: `currency_mismatch`, naming the ceiling's currency. Nothing is converted;
   - the discount is more than what is left: `ceiling_exceeded`, with `remaining_cents` and `currency`. Exactly what is left is allowed;
   - the ceiling cannot be read: `ceiling_unreadable`. An unreadable ceiling does not wave a discount through.
3. **The check and the write are one statement.** `reservePromo` runs one conditional `INSERT … SELECT … WHERE (live total + this discount) <= (the ceiling)`. The row exists only if it fitted when SQLite ran it; `meta.changes` says which. Two checkouts racing for the last of the ceiling cannot both win, and a stale "allowed" from an earlier read cannot overspend (a test hands a stale answer to both).
4. **Retry-safe.**
   - A reservation's key is the checkout's own reference plus the discount: the Stripe idempotency key of the plan and payment checkouts, the order id of a cart (`cart:<order id>`). The same checkout twice is the same row.
   - `canRedeemPromo` takes that reference and does not count the checkout's own hold against it, so a retry is asked the question the first press was, not "does it fit twice".
   - A row that was released, or whose hold lapsed, is taken again by the same conditional write.
5. **Released, committed, lapsed.**
   - `reserved`: counts until `expires_at` (one hour). An abandoned checkout stops holding the ceiling by itself; nothing sweeps it.
   - `committed`: the PaymentIntent succeeded (`payment_intent.succeeded` reads `promo_reservation_ref` from its metadata), the subscription's first invoice was paid (`invoice.paid`), the order was free, or a free unlock was granted. Counts for good.
   - `released`: Stripe made no subscription, no PaymentIntent, or the free grant lost the code's cap. Counts for nothing.
   - A payment that succeeds after its hold lapsed is committed anyway. Money taken is not undone, so that one case can pass the ceiling, and the ledger then shows it.
   - Releasing never undoes a committed row.
6. **`branch_promo_ceiling.issued_cents` now follows the ledger.** It is the branch's own running figure, which migration 256 said the branch owns and which nothing wrote. It is recomputed from the live rows in the same batch as every reserve, commit and release. An HQ ceiling push still leaves it alone. A lapsed hold leaves it only at the next write; the ledger, not this figure, is what the rule reads.
7. **A refusal is typed.** Every path returns `{ error: 'promo_invalid', reason, message, detail, remaining_cents?, currency? }` (`promoRefusalBody`). `reason` is the stable code the screens already read; `message` is a sentence we wrote saying what to do. The preview (`POST /api/payments/promo/validate`) returns `{ valid: false, reason, message, remaining_cents?, currency? }`. The four checkout screens and the plan quote gained sentences for the three new reasons.
8. **The Platform page says what is true.** The caveat now says a branch checkout refuses a discount above what the ceiling has left, and every discount until HQ sets one; that HQ's own Worker has no ceiling; and that only the first payment's discount is counted. It no longer says "no screen sets one yet": Revenue has set them since D228.

### Departures from the issue

- **No `licence` argument.** The licence is the Worker (branch or HQ), not a parameter. The issue's `canRedeemPromo({ licence, code, amount, customer })` became `{ code, productId, amountCents, currency, buyer }` plus `env`, which carries the branch.
- **The quote now judges the member.** It used to pass no member, so a once-per-member code was refused in the quote. This is a fix the issue's "UI validation and every checkout path use the same rule" asks for.
- **Refusal bodies grew `message` and `detail`.** Three existing assertions in `promo_scope_d1273.test.ts` compared whole bodies; they now compare the code and reason and check the sentence is there.

### Not modelled, so not enforced

- **A code names no licence.** A code is not tied to a subsidiary, so the licence ceiling applies by the Worker the member is on, not by the code. A code redeemed on HQ's Worker meets no ceiling.
- **A member's "customer" type or cohort.** There is no field for it on a code (D1272), so none is enforced.
- **Later invoices of a repeating or forever code.** Only the first payment's discount is reserved. Stripe applies the coupon to later invoices natively and this platform sees only the first paid invoice (D1274). The Platform page says so.
- **The code's cap is still read, then recorded later.** `max_redemptions` counts Stripe's counter plus the mirror's; both are read, and the one-time redemption is recorded by the webhook. Two checkouts at once can both pass a code with one use left. The ceiling does not have that gap; the code's cap does, and moving it into the same conditional write is a separate piece of work. The free-unlock path was already atomic for its cap.
- **A retry of an automatic offer.** The key of an automatic-offer checkout includes the offer's code, and the offer is chosen before the hold is looked up. A retry made when the ceiling has since filled drops the offer rather than reusing its hold.
- **HQ's `licence_promo_ceilings.issued_cents`.** It stays what the branch reports. This decision makes the branch's figure true; it does not add a new report.

### Decision for the owner

A branch with no ceiling pushed for the current quarter now gives **no discounts** (`ceiling_not_recorded`). The alternative is to let a branch with no ceiling redeem freely until HQ sets one. The first is chosen because the ceiling is HQ's funding statement and "not recorded" must not read as "unlimited"; the cost is that a branch HQ never pushed a ceiling to, or whose quarter just turned, cannot give a discount until HQ saves one on Revenue. The other choice is one condition in `canRedeemPromo`.

### UNVERIFIED

- **The deploy.** The migration has not been applied to D1 here; the deploy's `predeploy` hook applies it. A branch Worker that runs ahead of it fails closed (`ceiling_unreadable`) for a discount; HQ is unaffected.
- **Stripe's live behaviour.** Stripe is stubbed throughout. The webhook paths read `promo_reservation_ref` from the PaymentIntent's metadata and the subscription's metadata (or the invoice's copy); a live invoice event whose metadata omits it is handled as the existing redemption code handles it, by reading the subscription from Stripe.
- **A lost commit.** `recordInvoiceRedemption` swallows its errors (D1274, so the invoice's other work does not wait). If the commit fails there, the hold lapses after an hour and the discount stops counting. The redemption row is still written by the same function, so the usage reads are right.
