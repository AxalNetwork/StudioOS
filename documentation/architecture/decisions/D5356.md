## D5356 — Continue learning opens the lesson the learner left, at its saved position (#5356)

- **Status:** part 1 built (#5394). Part 2 built after the owner answered B on 2026-11-10: an open exam attempt's choices are held on the server, and exercise drafts stay on the device.
- **Builds on:** D4646, D4648 (per-kind bounds on `GET /me`), D4650 ("Next for you").
- **Why:** #4646's criterion "Continue opens the appropriate lesson and resume position" was left unmet. `GET /me` course rows named no lesson, so Continue opened the course page.

### The rule, in one place

`services/learningResume.ts` gives each in-progress course one resume lesson:

1. The learner's most recently updated lesson row in that course that is `started`, not completed.
2. Otherwise, the first required lesson, in outline order (module position, then lesson position), that the learner has not completed.
3. Otherwise, none: the row keeps its course link.

A lesson is a candidate only while all of these hold:

- it still exists in that course;
- the course is published;
- for a video or reading, the item it opens is published.

So a removed or unpublished lesson is never named, and the link is never dead. The next rule answers, or the course page does.

The saved position is the learner's own item row for the lesson's video or reading. D4646 writes the position there. When none is recorded, it is null.

**One rule for two surfaces.** `GET /me` and "Next for you" (`learningNext.ts`, rule `continue_course`) both call `resumeLessons`. They cannot point to different lessons for the same course.

Before this change, "Next for you" named the first required lesson not completed. It now names the last started lesson first. Its reason text, `<n> of <m> required lessons complete.`, is unchanged.

### Bounds and privacy

There are two fixed statements, each `LIMIT 2000` across every in-progress course of the caller. Every user id they bind is the session's own: the course rows, the lesson rows and the position. So another learner's rows are never read, and a test seeds a peer to check this. They sit beside D4648 part 2's per-kind bounds on `GET /me`, which are unchanged.

### Frontend

- **Lesson link.** `meRowHref` sends a course row that has a resume lesson to `/learning/courses/<slug>/<lesson>`. That is the same lesson page "Next for you" opens. A row without one keeps `/learning/courses/<slug>`.
- **Position.** The lesson page's own item read carries the saved position. The player's existing resume (`resumeAt` → "Resume from 04:12") starts there, so no position travels in the URL.
- **Wording.** Continue learning, on desktop and on the phone row, says "Resume <lesson> at 04:12". When no position is recorded, it says "Resume <lesson>" with no time.

### Changed fixture

`learning_next_4650.test.ts` seeded reading lessons that pointed at an item that did not exist. A lesson is now resumable only while its reading is published, so the fixture creates that reading. The test's assertions are unchanged.

### Part 2: exam choices held on the server (owner's answer B, 2026-11-10)

Before this, an exam's choices lived only in the browser (D4646). A learner who changed device, cleared the browser or used private mode mid-attempt lost them, while the server-held clock kept running. Exercise drafts have no clock, so they stay on the device, worded as before.

- **Store.** Migration `202611101028_5356_exam_attempt_drafts.sql`, named in the D5398 form, adds three columns to `learning_exam_attempts`:
  - `draft_answers_json`;
  - `draft_revision`;
  - `draft_saved_at`.

  They are kept apart from `answers_json`, which holds only what was submitted.
- **Save.** `PUT /api/learning/exams/:uid/attempts/:attempt/answers` with `{ answers, revision }`.
  - It accepts a save only for the caller's own attempt (another learner's is 404), only while the attempt is open (`already_submitted` otherwise) and inside its time limit (`time_limit_passed`).
  - It validates the choices against the attempt's own questions and options, with the same rule submit uses. A uid that is not in the attempt is dropped.
  - `revision` is a whole number from 1. One conditional `UPDATE` writes only while the stored revision is lower, so a delayed request cannot overwrite a newer save. The refusal is 409 `stale_revision` and carries the saved copy.
  - It never grades, never reveals and never uses an allowance.
  - A database before the migration answers 503 `drafts_not_recorded`. The choices are still kept on the device.
- **Resume.** The start route already resumes the open attempt rather than opening a new one. Its reply now carries `draft` (`answers`, `revision`, `saved_at`), re-validated against the questions, or null.
- **Frontend** (`examServerDraft.js`):
  - The device write happens first, as before. Then `useServerExamDraft` sends the choices after 1.2 s of quiet, one revision higher each time.
  - **Stale save.** A `stale_revision` means another tab or device saved later. This tab then takes the server's revision and sends its own choices once more, because they are the newer action here; it never loops.
  - **Offline.** A save that failed is sent again when the browser comes back online.
  - **Closed attempt.** `already_submitted` and `time_limit_passed` stop saving.
  - The page says, truthfully, saving / saved to your account / not saved to your account (still on this device) / closed.
  - **Which copy wins on resume.** A resume opens with the newer of the two copies, by the device write time (`initialAt`) against `saved_at`. So a second device gets the first device's choices, and a stale server copy never overwrites newer choices on this device.

### Not done here

- Exercise drafts are still kept on the device only, by the owner's answer B.
- An exercise, exam or webinar lesson is resumed by opening its lesson page, which links onward. It has no position.
