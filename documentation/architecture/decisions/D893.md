### The read: `GET /api/admin/insights` (#2660)

`routes/admin_insights.ts` mounts the read, and `services/adminInsights.ts` computes it. Any admin can call it.

**Counts only.** No name, email or account id leaves it, as the Studio glance does. A test walks every response and fails on a per-account key or a person's details.

**Scope.** It answers for this deployment's own accounts: `hq`, or the branch code. Another `scope` is refused before any read:
- a plain Admin gets 403 `hq_only`;
- a Super Admin gets 400 `scope_unavailable`, because reading another subsidiary is #2662's and does not exist yet.

**Query.** Every parameter is optional:
- `range`: `8w`, `quarter` or `year`, the Analytics ranges (`ANALYTICS_RANGES`, `weekAxis`); the default is `8w`;
- `profile`: a role key;
- `country`: as stored;
- `compare=1`;
- `group`: a role key, for the lightbox.

A value the read cannot use is a 400 (`bad_range`, `bad_profile`, `bad_group`, `bad_country`), never a quietly wider answer.

**Filters.**
- `profile` and `country` narrow every block that is about accounts. The SQL is fixed: `(? IS NULL OR u.role = ?) AND (? IS NULL OR u.country = ?)`.
- The country is matched as stored, with no case folding.
- `activationFunnel()` takes the same two filters and a wider axis. Its other callers pass nothing, and a NULL bind matches everyone.

**Each block answers alone.** A block is one of three things:
- `{ available: true, … }`: read;
- `{ available: false, unreadable: true, reason }`: its store failed, which is not a claim of zero;
- `{ recorded: false, reason }`: nothing on this database records it.

The reason is a sentence, never the database's error text.

| Key | What | Source |
| --- | --- | --- |
| `kpis.accounts` | live accounts, new in 30 days, deactivated | `users` |
| `kpis.new_this_week` | created this week to date, and last week | `users.created_at` |
| `kpis.active_last_week` | distinct accounts in the last complete week, and the week before | `activity_logs`, middleware rows (`ACTIVE_ACCOUNT_BASIS`) |
| `kpis.activated` | the share active in week two, over cohorts whose week two has ended | `activationFunnel()` |
| `blocks.who` | live accounts by profile; LPs (an approved `lp_applications` row); Product testers `recorded: false` until #2377 and #2318 | `users`, `lp_applications` |
| `blocks.plan` | live accounts by `subscription_tier`; paid is every tier but `free` | `users` |
| `blocks.growth` | every account created per week, deactivated included (the glance's count), by profile | `users` |
| `blocks.activity` | distinct active accounts per week; `previous` is the same number of weeks just before, with `compare=1` | `activity_logs` |
| `blocks.activation` | the funnel by creation week (`ActivationCohort`) | `activationFunnel()` |
| `blocks.retention` | per Monday creation week: sign-ups, and how many made a logged request in the last 30 days | `users`, `activity_logs` |
| `blocks.countries` | live accounts by country; blank ones are `not_stated` | `users.country` |
| `blocks.identity` | Not started · Waiting · Approved · Rejected; an unknown status is `other` | `users.kyc_status` |
| `blocks.completeness` | four bands; no figure is `not_recorded`, not 0% | `users.profile_completion_pct` |
| `blocks.dormant` | live accounts whose latest request is over 30 days old; never stamped is `never_seen`, not dormant; `last_month` is null | `users.last_active_at` |
| `blocks.tickets` | open (open, in progress) and by status | `tickets` |
| `blocks.spend` | this calendar month, UTC, by the spender's profile | `ai_usage_logs` |
| `group` | with `group=<role>`: the count, new in 30 days, active last week, activated, dormant, both weekly lines, and a table by country | as above |

`definitions` holds one sentence per block, for the page's "How is this counted?" dialog.

**Activity before the log began is blank, not zero.** A week before `activity_logs`' first middleware row is `null`. After that row, a week with nobody active is a measured 0.

**The glance's stale sentence is retired.** `ACTIVE_ACCOUNTS_REASON` said no store records activity, but `activity_logs` does. The Studio glance's `insights.active_accounts` now reads last week's count on the same rule.

**Performance.** The weekly distinct count is one grouped query. It was measured on node:sqlite with the baseline's indexes, 5,000 accounts and 1,000,000 `activity_logs` rows over 60 weeks. The whole read took (median of 3):

| Request | Time |
| --- | --- |
| `8w` | 401 ms |
| `quarter` | 562 ms |
| `year` | 2.6 s |
| `year` with `profile` | 903 ms |
| `8w` with `group` | 474 ms |

A year's distinct count is about 1.8 s of that. The same cost is paid by the branch Analytics line, which runs the same query today. If a year's read becomes too slow, the next step is the daily snapshot job (`analytics_snapshots`), which would need a migration for by-profile columns.
