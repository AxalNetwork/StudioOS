### The read: `GET /api/admin/insights` (#2660)

`routes/admin_insights.ts` mounts the read, and `services/adminInsights.ts` computes it. Any admin can call it.

**Counts only.** No name, email or account id leaves it, as the Studio glance does. A test walks every response and fails on a per-account key or a person's details.

**Scope.** It answers for this deployment's own accounts: `hq`, or the branch code. Another `scope`:
- from a plain Admin, or any admin on a branch, is refused before any read with 403 `hq_only`;
- from a Super Admin on HQ, reads that subsidiary's own database through the fan-out (S08, below). Until S08 it was 400 `scope_unavailable`.

**Query.** Every parameter is optional:
- `range`: `8w`, `quarter` or `year`, the Analytics ranges (`ANALYTICS_RANGES`, `weekAxis`); the default is `8w`;
- `profile`: a role key;
- `country`: as stored;
- `compare=1`;
- `group`: a role key, for the lightbox.

A value the read cannot use is a 400 (`bad_range`, `bad_profile`, `bad_group`, `bad_country`), never a quietly wider answer.

**Filters.**
- `profile` and `country` narrow every block that is about accounts. The SQL is fixed: `(? IS NULL OR u.role = ?) AND (? IS NULL OR u.country = ?)`.
- The country is matched as stored, with no case folding.
- `activationFunnel()` takes the same two filters and a wider axis. Its other callers pass nothing, and a NULL bind matches everyone.

**Each block answers alone.** A block is one of three things:
- `{ available: true, … }`: read;
- `{ available: false, unreadable: true, reason }`: its store failed, which is not a claim of zero;
- `{ recorded: false, reason }`: nothing on this database records it.

The reason is a sentence, never the database's error text.

| Key | What | Source |
| --- | --- | --- |
| `kpis.accounts` | live accounts, new in 30 days, deactivated | `users` |
| `kpis.new_this_week` | created this week to date, and last week | `users.created_at` |
| `kpis.active_last_week` | distinct accounts in the last complete week, and the week before | `activity_logs`, middleware rows (`ACTIVE_ACCOUNT_BASIS`) |
| `kpis.activated` | the share active in week two, over cohorts whose week two has ended | `activationFunnel()` |
| `blocks.who` | live accounts by profile; LPs (an approved `lp_applications` row); Product testers `recorded: false` until #2377 and #2318 | `users`, `lp_applications` |
| `blocks.plan` | live accounts by `subscription_tier`; paid is every tier but `free` | `users` |
| `blocks.growth` | every account created per week, deactivated included (the glance's count), by profile | `users` |
| `blocks.activity` | distinct active accounts per week; `previous` is the same number of weeks just before, with `compare=1` | `activity_logs` |
| `blocks.activation` | the funnel by creation week (`ActivationCohort`) | `activationFunnel()` |
| `blocks.retention` | per Monday creation week: sign-ups, and how many made a logged request in the last 30 days | `users`, `activity_logs` |
| `blocks.countries` | live accounts by country; blank ones are `not_stated` | `users.country` |
| `blocks.identity` | Not started · Waiting · Approved · Rejected; an unknown status is `other` | `users.kyc_status` |
| `blocks.completeness` | four bands; no figure is `not_recorded`, not 0% | `users.profile_completion_pct` |
| `blocks.dormant` | live accounts whose latest request is over 30 days old; never stamped is `never_seen`, not dormant; `last_month` is null | `users.last_active_at` |
| `blocks.tickets` | open (open, in progress) and by status | `tickets` |
| `blocks.spend` | this calendar month, UTC, by the spender's profile | `ai_usage_logs` |
| `group` | with `group=<role>`: the count, new in 30 days, active last week, activated, dormant, both weekly lines, and a table by country | as above |

`definitions` holds one sentence per block, for the page's "How is this counted?" dialog.

**Activity before the log began is blank, not zero.** A week before `activity_logs`' first middleware row is `null`. After that row, a week with nobody active is a measured 0.

**The glance's stale sentence is retired.** `ACTIVE_ACCOUNTS_REASON` said no store records activity, but `activity_logs` does. The Studio glance's `insights.active_accounts` now reads last week's count on the same rule.

**Performance.** The weekly distinct count is one grouped query. It was measured on node:sqlite with the baseline's indexes, 5,000 accounts and 1,000,000 `activity_logs` rows over 60 weeks. The whole read took (median of 3):

| Request | Time |
| --- | --- |
| `8w` | 401 ms |
| `quarter` | 562 ms |
| `year` | 2.6 s |
| `year` with `profile` | 903 ms |
| `8w` with `group` | 474 ms |

A year's distinct count is about 1.8 s of that. The same cost is paid by the branch Analytics line, which runs the same query today. If a year's read becomes too slow, the next step is the daily snapshot job (`analytics_snapshots`), which would need a migration for by-profile columns.

### The page on the read (#2660)

The page now makes one read, `GET /api/admin/insights`, for every admin. The glance, the analytics overview, the cohorts and HQ analytics are no longer read here.

- **The filters are live and live in the URL:** `range`, `profile`, `country` and `compare`.

  - The profile chips are role keys, and Explorers is `exploring`.
  - LPs and Product testers are drawn but cannot be chosen, and each says why. LPs are investors with an approved application, not a profile; Product testers are not defined yet (#2377).

  - Growth is stacked by profile; mentors are added to Advisors.
  - Activity leaves weeks before the request log began blank, and draws the period before as a dotted line when Compare is on.
  - Activation, retention, countries, identity (#2384's words), completeness, dormant and spend by profile are read for every admin.

- **The group lightbox (INS3)** makes the same read with `group=<role>`. It shows four tiles, sign-ups and actives per week, and a table by country with a search box. A rate the read cannot give is "Not recorded", never 0%.
- **Failures:** a block whose store failed shows the Worker's sentence and Try again; the whole page fails only when the read does. A read answered after a newer one was asked is dropped.
- **Export:** the CSV records the filters it was made under.
- **INS10:** makes no read.

The retired `HeldInsights.jsx` page stays deleted. `/admin/held/insights` continues to redirect to `/admin/insights`.

### S08 — the Super Admin scope: each deployed subsidiary's counts, from its own database (#2662)

- **Status:** decided by S1 for the owner, 2026-10-24 (#2662; canvas boards INS2 and INS10). Built by S08.
- **Basis:** `origin/main` at `db73a01cda`, with #2660 PR 1 (#2664) and S1's page (#2663) merged. Paths are relative to `cloudflare-worker/` unless they say otherwise.
- **Migration:** none.
- **This PR is the Worker half and the client.** The page half (the Scope select, the chip and `scopeState`) follows once #2660 PR 2 (#2669) has switched the page to the one read; before that the page draws HQ's own reads, so a picked subsidiary would sit over HQ's figures.

#### 1. What is built

1. **`scope=<code>` on `GET /api/admin/insights`** (`routes/admin_insights.ts`).
   - A plain Admin, or any admin on a branch, asking for another scope gets 403 `hq_only` with INS10's words, before any read. `isSuperAdmin` answers false on a branch (D106), so only HQ's Super Admin goes further.
   - The filters are parsed first, by the same `parseInsightsQuery` the route always used: a bad one is a 400 before any branch is asked.
   - A scope that is not a branch code is 400 `bad_scope`.
   - Otherwise HQ asks that branch (`branchScopedInsights`, `services/insightsScope.ts`) through `branchRead`, the fan-out's single-branch form, so the states are the fan-out's own.
2. **The branch's `insights()` RPC.** `branchInsights` (`rpc/branchOps.ts`), delegated from `HqEntrypoint.insights()` beside `activation()`.
   - It runs `loadInsightsForBranch` (`routes/admin_insights.ts`): `parseInsightsQuery` and `adminInsights`, the same read over the branch's own D1. A filter it cannot use throws.
   - Only `range`, `profile`, `country`, `compare` and `group` cross, as bounded strings.
   - The answer goes through `countsOnly`, which drops every key naming a person or a record (`id`, `uid`, `name`, `email`, `phone`, `*_id`, `*_uid`, `*_name`, `*_email`, `*_phone`) and any email-shaped string. A read, so no secret, on `rpc/index.ts`'s rule.
3. **What HQ returns.** The branch's read, stripped again by `countsOnly` (a branch on an older deploy is not this code), with HQ's `scope: { key, label, kind: 'branch', source: 'counts read from its own database' }`. The label is the licence's brand name from the registry, else the code. `branch: { status }` says how the branch answered.
   - A branch that does not answer, answers without a read, exposes no `insights()`, or is not bound gives every KPI (`accounts`, `new_this_week`, `active_last_week`, `activated`) and every block `{ available: false, unreadable: true, reason }`. The reason names the branch and what happened. Never a zero, and never HQ's own accounts.
4. **`GET /api/admin/insights/scopes`** (`routes/admin_insights_scopes.ts`; Super Admin on HQ, anyone else 403 `hq_only`).
   - HQ-held accounts first, then each deployed subsidiary by code: `licence_deployments` joined to `territory_licences`, as `registryForAnalytics` reads them.
   - "Deployed" is a deployment whose status is `worker_live`, `hostname_active` or `linked` (migration 258): there is a Worker and a database to ask. A `requested` or `failed` one is not listed.
   - Each line is `{ code, label, kind, bound }`; `bound` says whether this Worker holds the branch's binding yet.
   - An unreadable registry still answers the HQ-held line, with the reason no subsidiary is listed.
5. **The client.** `insightsApi.insightsScopes()` in `frontend/src/lib/api/insights.js`, beside `adminInsights`.
6. **The topology page** (`services/topology.ts`) lists `insights` among `HqEntrypoint`'s methods.

#### 2. Not built here

- **No figure is computed at HQ for a branch.** Every count is the branch's own read; HQ adds only the label.
- **No cross-branch total.** "Compare all subsidiaries" stays on HQ Analytics (H15), as the canvas has it.
- **The page half**, after #2669: `ScopeSelect` in `AdminInsights.jsx` lists `/scopes` and sets `?scope=<code>`; the chip reads "[label] · counts read from its own database"; `scopeState` in `insightsModel.js` accepts a listed code for a Super Admin.

#### 3. Tests

`test/insights_scope_d893.test.ts` (new, 10), on `node:sqlite` at HQ behind the real route, with the real `branchInsights` behind a stubbed binding:

1. The branch answers with the contract's parameters only, and strips every personal field.
2. HQ's tier refuses to answer as a branch. The branch runs #2660's read over its own (empty) database, every block failing alone, and refuses a filter it cannot use.
3. `countsOnly` keeps counts, profiles, countries and labels, and removes ids, names and emails at any depth.
4. A Super Admin reads one subsidiary's counts under HQ's label; HQ forwards only the filters. End to end through `loadInsightsForBranch`, the branch's own block reasons travel.
5. A bad filter is a 400 before any branch is asked.
6. HQ strips again an older branch's personal fields.
7. A branch that throws, one without `insights()`, and an unbound code each give every KPI and block unreadable with its reason, and no zero.
8. A plain Admin is refused another scope with 403 `hq_only` and INS10's words; their own scope reads; a bad scope is 400.
9. The scopes list: HQ-held first, then the deployed subsidiaries by code, with labels and `bound`.
10. The scopes list refuses a plain Admin and a branch admin; an unreadable registry still answers HQ-held.

Every response is walked: no key names a person or a record and no string is email-shaped. `test/admin_insights_d893.test.ts`'s scope case now expects a Super Admin's other scope to be a branch read (`not_deployed` for an unbound code), not 400.
