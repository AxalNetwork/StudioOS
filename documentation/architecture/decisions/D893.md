### S08 — the Super Admin scope: each deployed subsidiary's counts, from its own database (#2662)

- **Status:** decided by S1 for the owner, 2026-10-24 (#2662; canvas boards INS2 and INS10). Built by S08.
- **Basis:** `origin/main` at `edffa495e2`. Paths are relative to `cloudflare-worker/` unless they say otherwise.
- **Migration:** none.
- **Order.** #2660's branch and S1's page PR were not pushed when this was built. This PR is the Worker half against #2660's fixed contract; the two wiring lines and the page half wait on them (§3).

#### 1. What is built

1. **The branch's `insights()` RPC.** `branchInsights` in `src/rpc/branchOps.ts`, delegated from `HqEntrypoint` in `src/rpc/index.ts`, beside `activation()`.
   - The branch runs the same read HQ's `GET /api/admin/insights` makes, over its own D1. It is handed that read as a loader.
   - Only the contract's parameters cross: `range`, `profile`, `country`, `compare`, `group`, each a bounded string. The loader validates their values.
   - The answer is counts only. `countsOnly` (`src/services/insightsScope.ts`) drops every key that names a person or a record (`id`, `uid`, `name`, `email`, `phone`, and any `*_id`, `*_uid`, `*_name`, `*_email`, `*_phone`) and any email-shaped string.
   - A read, so no secret, on `rpc/index.ts`'s rule.
2. **HQ's read of one subsidiary.** `branchScopedInsights` (`src/services/insightsScope.ts`) asks one branch through `branchRead`, the fan-out's single-branch form, so the states are the fan-out's own.
   - An answer is stripped again by `countsOnly`, because a branch on an older deploy is not this code. Its `scope` is HQ's: `{ code, label, kind: 'branch', source: 'counts read from its own database' }`. The label is the licence's brand name from the registry, else the code.
   - A branch that does not answer, answers without a read, exposes no `insights()`, or is not bound gives every KPI (`accounts`, `new_this_week`, `active_last_week`, `activated`) and every block `{ available: false, unreadable: true, reason }`. The reason names the branch and what happened. `branch: { status }` says which of `unreadable` and `not_deployed` it was. Never a zero.
3. **The gate on `?scope=`.** `insightsScopeGate` (`src/routes/admin_insights_scopes.ts`), for #2660's route to call:
   - no scope, or `hq`, is the admin's own deployment and always passes;
   - any other scope needs a Super Admin on HQ. A plain Admin, or any admin on a branch, gets 403 `hq_only` with INS10's words: "This view is for HQ. You see the accounts you manage.";
   - a scope that is not a branch code is 400 `bad_scope`.
4. **`GET /api/admin/insights/scopes`** (Super Admin on HQ; anyone else 403 `hq_only`).
   - HQ-held accounts first, then each deployed subsidiary by code: `licence_deployments` joined to `territory_licences`, as `registryForAnalytics` reads them.
   - "Deployed" is a deployment whose status is `worker_live`, `hostname_active` or `linked` (migration 258): there is a Worker and a database to ask. A `requested` or `failed` one is not listed.
   - Each line is `{ code, label, kind, bound }`. `bound` says whether this Worker holds the branch's binding yet.
   - An unreadable registry still answers the HQ-held line, with the reason no subsidiary is listed.

#### 2. Not built here

- **No figure is computed at HQ for a branch.** Every count is the branch's own read; HQ adds only the label.
- **No cross-branch total.** "Compare all subsidiaries" stays on HQ Analytics (H15), as the canvas has it.
