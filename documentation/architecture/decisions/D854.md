## D854 — Eadwyn uses the MCP registry's tools inside the member's own access: reads through the server's checks, writes as proposals, results as data

- **Status:** decided by S1 for the owner, 2026-10-21 (#2477; part of #2463). Built by S27.
- **Basis:** `main` at `56c2498983`. Worker paths are relative to `cloudflare-worker/src/`.
- **Depends on:**
  - D846 (#2467), the per-member tool filter;
  - D844 (#2466), metering.

  Neither was on `main` when this was built. §4 says how each one plugs in without a change here beyond one function.

### 1. The principal is the member, and the companies are the page's

- `services/eadwynTools.ts` runs Eadwyn's tool calls under a synthetic grant (`eadwynGrant`):
  - the member's `userId`;
  - `clientId: 'eadwyn'` and `clientName: 'Eadwyn'`, so the activity log tells Eadwyn's calls apart from an assistant's;
  - `companies` holding only the company the page is about.
- **A page about no company gets no company tool.**
- **A page about a company the member cannot read gets none either:** the company is checked with `grantCompany` before any call runs.
- **The member's session scopes** default to every scope a session holds (`SCOPES`). A caller may pass fewer. Eadwyn never holds more than the member.

### 2. The model proposes; the server decides

`runEadwynToolCalls(env, ctx, calls)` takes the calls one model turn proposed, as untrusted names and arguments, and checks each again:

1. **The tool must be on the member's list** for this page (`eadwynToolAvailable`). Otherwise: "That tool is not available here", the same answer as an unknown name.
2. **The company is the page's.** A company argument outside the context is refused, never swapped for the right one. A missing one is set to the page's.
3. **The arguments must pass the tool's own schema** (its zod shape). Unknown keys are dropped.
4. **At most five calls run in one turn** (`MAX_TOOL_CALLS_PER_TURN`). More are refused, not queued.

A refusal is a result the model can read. It is never an exception.

### 3. Reads, writes and results

- **A read runs through `callTool`** (`mcp/server.ts`): the same path an external client's call takes, with every per-call check:
  - the user is re-read, so an ended or deleted account refuses;
  - the company is re-checked;
  - the scope is checked;
  - one activity line is written, which never holds the arguments or the result.

  Eadwyn's access is therefore an external grant's access, by construction. The test holds the two results equal.
- **A write is never executed.** It becomes an `ai_rail_proposals` row (`kind: 'proposal'`, D780) with `{ tool, args }`, and the member's press decides it. Writing a kept value is the record's own route, as for every rail proposal.
- **A write is refused when its arguments name a field Eadwyn never fills** (D777's registry), so it can never reach a member's Accept.
- **Tool output is data.** `toolResultsForModel` sends each result under `TOOL_DATA_NOTICE`, in a `<tool_result … trust="data">` block. `<` and `>` in the data are escaped, so a result cannot close its block or open a tag.
- **Nothing reads a result for a call.** The only calls run are the ones passed in. A result that says "call this tool" calls nothing.

### 4. How the dependencies plug in

- **D844 (#2466), metering.** D844 wraps `callTool` in `meteredCall` for any tool its policy prices above 0. Eadwyn's reads go through `callTool`, so they are held and settled on the one AI token ledger with no code here. v1 prices every tool at 0, so nothing is charged today.
- **D846 (#2467), the tool filter.** `eadwynToolAvailable` is the one filter Eadwyn uses: scope and the page's company today. When D846 lands its per-member filter (plan, entitlement, connection), that filter replaces this function's body, so Eadwyn and an external client always list the same tools.
- **Defense in depth.** D846's rule that "listing is not authorization" still holds: `callTool` re-checks on every call.

### 5. Not in this decision

- **The rail runner calling these functions.** The model turn that proposes calls and reads `toolResultsForModel` is the rail run's (D777, D778). This decision gives it the tools, the checks and the format.
- **Plan §3 and §8.** `MCP_API_PLATFORM.md` lands with #2464's PR. This decision changes no contract listed there.

### 6. Tests

`cloudflare-worker/test/eadwyn_tools_d854.test.ts` has eight tests, each mutation-checked:
- **Access parity:** Eadwyn's read equals an external grant's for the same member and company, and writes the same activity line, marked Eadwyn.
- **Company access:** a company the member cannot read gets no company tool, and a company the model names outside the page is refused.
- **The list:** it follows the member's scopes and the page's company, and an unlisted or unknown tool is refused.
- **Arguments and the cap:** arguments are re-validated, and calls past the cap are refused.
- **Write to proposal:** a write becomes a proposal and its handler never runs, with unknown arguments dropped.
- **Writes outside the member's access:** a write for a company the member cannot read proposes nothing, and a never-fill field is refused.
- **The injection guard:** a result carrying instructions runs nothing more, and reaches the model escaped, under the notice.
