## 2. What ran

- **The code.** The Worker's own `aiRouter.run`, `reserveAiBudget`/`settleAiReservation` (inside `run`), `loadAiBudget`, `memberHolds`, `agentRun`, `admitInScope`, `markRun`, `moveTask`, `decideRail`, `listRail`, and the loop's own `after` step, which receives the `decision` event as `runTaskLoop` does.
- **The database.** A throwaway node:sqlite 3.50.4 file built from the baseline plus every migration (`_storage_schema.ts`), with foreign keys on.
- **The fixtures.** Synthetic tenants come from #4566's fixtures: each has a founder, a user, a company, a project and 2 agents. Every fourth tenant has no included allowance, so its runs draw on the top-up balance and write `ai_credit_ledger` through migration 486's triggers.
- **The isolation.** Inference is a stub. There is no queue, no Workflow, no network and no hosted database. Node is v22.22.
- **The mixes:**
  - **A** user reads: the budget and the holds;
  - **B** an AI call: hold, model, settle, usage;
  - **C** an agent run end to end: admission → running → `agentRun` → waiting decision → accept → `after`;
  - **D** proposal reads;
  - **E** failures: a duplicate idempotency key raced, a provider failure, a replayed agent step, a cross-tenant attempt.
- **The default weights** are A 30 / B 25 / C 20 / D 15 / E 10.

## 4. Contention candidates (simulated; the SQL fingerprints are exact)

### 4.1 `chargedFor` scans `ai_usage_logs` on every charged result

```
SELECT SUM(charged_microusd) AS charged, SUM(CASE WHEN charged_microusd IS NULL THEN N ELSE N END) AS unrecorded
  FROM ai_usage_logs WHERE id = ? OR guard_for = ?          -- agentRun.ts:273
```

`EXPLAIN QUERY PLAN` gives `SCAN ai_usage_logs`, because no index covers `guard_for`. The same `WHERE id = ? OR guard_for = ?` is in `tagUsage` (`skillEval.ts:128`), as an UPDATE. The database-only control timed the statement as the table grew:

| `ai_usage_logs` rows | Today (scan) | With a candidate partial index on `guard_for` (throwaway database only) |
| ---: | ---: | ---: |
| 1,000 | 0.059 ms | 0.005 ms |
| 10,000 | 0.44 ms | 0.005 ms |
| 100,000 | 6.1 ms | 0.005 ms |

The cost is linear in the table's size, and the whole table keeps growing, because usage rows are never archived (#4568). D1 runs queries one at a time per database, so every millisecond of this scan delays every other request to the database. Production's row count is unknown (§1).

### 4.2 `agentAreas` aggregates every agent's skill links, once per agent run with a model

```
SELECT l.agent_id, s.category_slug AS area, COUNT(*) AS n
  FROM agent_skill_links l JOIN agent_skill_tags t ON t.skill_id = l.skill_id JOIN skills s ON s.slug = t.taxonomy_skill_slug
 GROUP BY l.agent_id, s.category_slug ORDER BY …           -- adminReads.ts:98, from agentRun's underPolicy
```

The plan is `SCAN l USING COVERING INDEX`. Its cost grows with the number of **registered** agents on the platform, not with this run's agent. Only one agent's area is needed. This matters for "1M registered agents" (§5) even when few of them run.

### 4.3 Platform switches read on every AI call

- **Which reads.** Each AI call reads `feature_flags` (a SCAN), `ai_model_policy` (an ordered scan), `ai_model_locks` and `ai_agent_policy`. The tables are small and identical for every caller.
- **Cost.** In B, policy reads are 4 of the 33 statements; in C they are 10 of the 86.
- **Plan reads repeat.** The plan reads (`member_subscription_amounts`, `mi_pro_subscriptions` and `account_subscriptions`) each appear twice in one AI call's statement list: model choice reads them once, and the hold's allowance reads them again.

### 4.4 Statements that could share a batch

These are all in one run's path, with no read between them that decides anything:
- the three `ai_usage_logs` inserts;
- the hold's context `UPDATE`;
- the four `markRun` updates and three `moveTask` updates;
- the task events.

### 4.5 What did not contend

- **Fairness.**
  - With 1,000 tenants, the median tenant's p95 was 45 ms against a worst of 659 ms, and that worst came from the C operations' own length.
  - With half of all operations on one tenant (`--hot 0.5`), that tenant took 212 operations and the median tenant took 2. The median tenant's p95 was 86 ms.
  - The only refusals were the engine's own per-agent `agent_busy`. No mix degraded another tenant beyond the local process's own serial queue.
- **Engine limits, not contention.** With **one** tenant at concurrency 8, 56 of 71 agent starts were refused `queue_full`, and 9 `agent_busy`. These are the engine's own limits per scope: `max_parallel_runs` 2 and `OPEN_PROPOSALS_MAX` 5. They do not come from D1.

## 5. Load steps (simulated) and the D1 model

**The ramp.** 100 tenants, the default mix, open loop. Each step is load at a rate, not a capacity promise.

| Started/s | Achieved/s | Error rate | p50 | p95 | p99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1.24 | 0 | 16.5 ms | 53 ms | 53 ms |
| 5 | 5.21 | 0 | 11.9 ms | 32 ms | 35 ms |
| 10 | 10.19 | 0 | 10.8 ms | 35 ms | 40 ms |
| 25 | 25.19 | 0 | 3.7 ms | 27 ms | 28 ms |
| 50 | 49.95 | 0 | 7.0 ms | 37 ms | 48 ms |
| 100 | 100.03 | 0 | 6.7 ms | 76 ms | 121 ms |
| 200 | 121.62 | 0 | 5.0 ms | 2,009 ms | 3,518 ms |

**Where it saturates.** The local process saturates at about 120 operations a second of this mix. In closed loops, SQL is 60–75% of wall time, and the rest is the services' own JavaScript. This saturation belongs to one Node process on one file. It says nothing about D1's limit.

**D1 is serial per database.** If `t` is D1's mean time per statement, measured by the owner (§1), the database's own time per agent run is about 86 × `t`. The ceiling is therefore about 1 / (86 × `t`) runs a second, *before* any other traffic.

| If `t` were | Agent runs a second, the whole database, nothing else running |
| ---: | ---: |
| 0.1 ms | about 116 |
| 0.5 ms | about 23 |
| 1 ms | about 12 |

These are a formula's outputs for assumed `t`, not measurements. The Worker's latency per run is a separate figure: about 79 sequential round trips.

**1M registered agents and 1M concurrent runs are different questions.**

| Question | What decides it |
| --- | --- |
| **Registered** agents | Storage: one `team_agents` row with its indexes. One read: `agentAreas` scans every agent's skill links on each run (§4.2). |
| **Concurrent** runs | Each agent has 1 live run; each scope has 2 live runs (`max_parallel_runs`) and 5 waiting (`OPEN_PROPOSALS_MAX`); each agent has 20 runs a day (`DAILY_LIMIT`). Every one of those runs is 86 statements on the one serial database. |

At any `t` above, 1M concurrent runs on one database is not reachable by orders of magnitude. 1M registered agents is reachable for storage once §4.2 is fixed.

## 6. Growth (simulated, local SQLite pages)

| Workload | Bytes per 1,000 executions | Rows per execution |
| --- | ---: | --- |
| Agent runs (C only) | about 4.8 MB | 3 usage, 1 reservation, 0.66 ledger, 1 run, 1 task, 1 proposal, 1 agent event, 2 task events |
| AI calls (B only) | about 1.7 MB | 3 usage, 1 reservation, 0.66 ledger |

- **A lower bound.** The synthetic answers are a few words, and real proposals carry real output. Production rows are larger, so production grows faster than this.
- **Headroom.** Today's 308.5 MiB and the 10 GiB cap leave about 9.7 GiB, which is about 2 million agent runs or 6 million AI calls at these local sizes, before any other table grows.
- **The trend that matters is unknown.** Nothing deletes or archives these rows today; that is #4568.

## 7. Invariants (simulated)

Every count was 0 in every run: 1, 10, 100 and 1,000 tenants; the hot tenant; the ramp to 200/s; and the two single-mix runs.

- double settlement;
- missing charge;
- an orphaned hold;
- negative balance, including CHECK refusals;
- a second live run;
- an orphaned run;
- a duplicate proposal;
- a duplicate hold;
- a cross-tenant read;
- unknown read as zero.

Each invariant's query was broken on purpose in `d1_benchmark_4567.test.ts` and caught.

## 8. Alternatives, in the order to consider them

**No migration is started by this work.** Any schema change is #4568's, with its own evidence and review.

1. **Index and query fixes (§4.1, §4.2).**
   - A partial index on `ai_usage_logs(guard_for) WHERE guard_for IS NOT NULL`, or rewriting `chargedFor` and `tagUsage` as `id = ?` UNION `guard_for = ?` over that index.
   - `agentAreas` reading one agent's links rather than everyone's.
2. **Read once per request (§4.3).** The platform switches and the plan rows, read once per request or per isolate for a bounded time.
3. **Bounded batching (§4.4).** The usage rows with their guard rows; and `markRun` with `moveTask` and the task event that goes with it. Each batch stays one transaction, as D1 runs it.
4. **Retention and archive** of settled usage, reservations and finished runs. This is #4568, with the ledger's append-only rule kept.
5. **Asynchronous analytics** for the admin reads that aggregate `ai_usage_logs`.
6. **A partitioning study**, only if the owner's production baseline shows the database is the bottleneck after 1–5.
