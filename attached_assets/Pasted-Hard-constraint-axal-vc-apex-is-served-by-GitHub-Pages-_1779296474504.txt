Hard constraint
  axal.vc (apex) is served by GitHub Pages (marketing site). Do NOT
  attach a Cloudflare custom domain to the apex. Do NOT route the
  Worker on the apex.

Target architecture
    axal.vc            → GitHub Pages — marketing — UNCHANGED
    app.axal.vc        → Cloudflare Pages — frontend SPA (signed-in app)
    app.axal.vc/api/*  → Cloudflare Worker — production API
                          (same-origin under the SPA — best for cookies,
                          CORS, CSP)
    cdn.axal.vc        → R2 public bucket (optional; truly public assets)
    status.axal.vc     → public status page (Worker)
    backup.app.axal.vc → GitHub Pages failover for the SPA (Prompt BF)
                          (not on axal.vc apex; reserved)
    *.workers.dev      → preview / dev only; never appears in any
                          provider callback or production link.

End-to-end migration checklist (commit at MIGRATE_TO_CUSTOM_DOMAIN.md)

  1. wrangler.toml
       routes = [
         { pattern = "app.axal.vc/api/*", custom_domain = true },
       ]
     Remove any reference to workers.dev in production. Add
     [env.preview] block that DOES use workers.dev:
       [env.preview]
       name = "studioos-preview"
       (no custom routes; workers.dev resolves the preview)

  2. Cloudflare Dashboard
       a. Workers > studioos > Triggers > Custom Domains:
          add app.axal.vc with pattern /api/* (custom_domain = true
          binds the subdomain; Pages handles everything else under
          app.axal.vc/*).
       b. Cloudflare Pages > axal-frontend > Custom domains:
          add app.axal.vc. Do NOT add axal.vc — that's GitHub Pages.
       c. DNS records (in Cloudflare DNS for axal.vc zone):
          A/AAAA: axal.vc                → GitHub Pages IPs (existing;
                                            DNS-only / unproxied — do
                                            not toggle to proxied or it
                                            breaks Pages)
          CNAME: app.axal.vc             → Cloudflare Pages target
                                            (proxied / orange-cloud ON)
          CNAME: cdn.axal.vc             → public.r2.dev or R2
                                            custom-domain target
          CNAME: status.axal.vc          → app.axal.vc (status served
                                            by the same Worker)
          CNAME: backup.app.axal.vc      → axalnetwork.github.io
                                            (DNS-only)
          TXT  : axal.vc                  → existing GitHub Pages
                                            verification records — DO
                                            NOT remove
       d. SSL/TLS: Full (strict) on the axal.vc zone overall.
          HSTS preload: only enable AFTER you're confident all
          subdomains are TLS-ready. Apex preload would lock GitHub
          Pages into the policy too.
       e. Cloudflare Access policies: re-apply admin/monitoring/infra
          gates to app.axal.vc/api/admin/*, etc.

  3. Worker code — replace every hard-coded URL
     grep -rn "workers.dev\|studioos.guillaumelauzier" cloudflare-worker/
     Replace constants with:
       env.PUBLIC_BASE_URL = 'https://app.axal.vc'      // app + API
       env.PUBLIC_MARKETING_URL = 'https://axal.vc'      // GitHub Pages
     Common locations to fix:
       - OAuth redirect_uri builders (Google, Outlook, LinkedIn,
         Stripe Connect, HubSpot, Salesforce, Carta, Calendly,
         Slack, DocuSign, Persona)
       - email templates with magic links / signing links / unsubscribe

       - share/embed links produced in API responses
       - Stripe checkout success_url / cancel_url
       - Stripe Connect refresh / return URLs
       - sitemap base (marketing sitemap = axal.vc; app sitemap, if
         any, = app.axal.vc)
       - robots.txt for the app (disallow indexing of /app/* if
         signed-in routes shouldn't be crawled)
       - openapi.json server entry — set to https://app.axal.vc/api

  4. Frontend code — API base
     frontend/src/lib/api.js BASE constant must be '/api'
     (same-origin relative — works because /api/* is on the same
     host as the SPA). Remove any absolute base.
     vite.config.js: dev proxy to local Worker is fine; do not put
     workers.dev in the production build.

  5. CORS allow-list (worker middleware)
     Because the API and SPA share the same host (app.axal.vc),
     most reads/writes are SAME-ORIGIN — no CORS needed for them.
     Cross-origin still applies to:
       - Marketing site (axal.vc) hitting any /api/* (e.g. /contact,
         /demo form submissions, /api/public/status from a status
         widget)
     CORS allow-list:
       https://axal.vc
       https://app.axal.vc
       https://status.axal.vc
       (no localhost in production; dev allow-list separate)

  6. CSP connect-src
     Worker middleware setting CSP on the SPA bundle:
       connect-src 'self' https://app.axal.vc https://api.stripe.com
                   https://*.cloudflareaccess.com;
     Marketing site (axal.vc) CSP is owned by Jekyll; keep its
     existing config — just ensure it allows https://app.axal.vc
     if any marketing widget calls back to the API (e.g. /contact).

  7. Cookie domain
     Session / auth cookies are issued by the Worker at app.axal.vc.
     Use:
       Domain=app.axal.vc      (single subdomain — tightest scope)
     OR
       Domain=.axal.vc; SameSite=Lax    (broader — shareable with
                                          status.axal.vc etc.)
     Recommended: Domain=app.axal.vc. The marketing site doesn't
     need the auth cookie.
     Flags: HttpOnly; Secure; SameSite=Lax; Path=/. Use __Host-
     prefix on tokens where possible.

  11. Email-from + DKIM/SPF/DMARC for axal.vc
       DNS in Cloudflare for the axal.vc zone:
         SPF (TXT @):
           "v=spf1 include:_spf.google.com -all"
            (replace include with your actual provider — Gmail
             Workspace, Postmark, SES, etc.)
         DKIM (TXT, selector per provider):
           per-provider published TXT record
         DMARC (TXT _dmarc.axal.vc):
           "v=DMARC1; p=reject; rua=mailto:dmarc@axal.vc;
            ruf=mailto:dmarc@axal.vc; fo=1; pct=100"
         MX records: pointed at your inbound mail provider; do
            NOT mix conflicting MX configurations.
       Reply-to addresses (noreply@, support@, security@,
       compliance@, billing@, legal@, privacy@, dpo@) all on
       axal.vc — these are mail-domain identifiers, NOT URL
       hosts. They don't conflict with Pages on axal.vc.
       Verify with mail-tester.com → score ≥ 9/10.

  14. Cross-origin form posts FROM the marketing site
       The marketing Jekyll site (axal.vc) submitting /contact and
       /demo forms must POST to https://app.axal.vc/api/forms/*.
       This is cross-origin: the Worker must:
         a. include CORS headers allowing https://axal.vc
         b. accept POST + OPTIONS preflight
         c. apply Turnstile validation server-side
       The marketing JS must include credentials: 'omit' on these
       requests — they don't carry auth.

Migration order
  a. Land the wrangler.toml + DNS change (CNAME app.axal.vc) so
     app.axal.vc/api/* responds.
  b. Keep workers.dev resolving in parallel for fallback.
  c. Update each provider callback ONE AT A TIME, verifying each
     round-trip end-to-end before moving on.
  d. Once every provider is on app.axal.vc, remove the workers.dev
     production binding from wrangler.toml so the URL serves only
     the preview environment.
  e. Final smoke test (in the next section).
