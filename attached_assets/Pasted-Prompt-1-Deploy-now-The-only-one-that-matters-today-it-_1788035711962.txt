Prompt 1 — Deploy now. The only one that matters today; it ships #348's routes. Structure: sync and verify 318 patterns → prove the tree deployable (test:drift + check-docs-fresh --strict, exit codes read directly, never grepped) → --dry-run the migrations before they run → capture a rollback deployment ID → npm run deploy → read the postdeploy table. It names the five migrations that may be pending (184–188) and says to stop if anything else shows up, and it forbids SKIP_LIVE_SMOKE=1 — that flag would throw away the only evidence the deploy worked.

Prompt 2 — Migration failure triage. Splits the failure into three cases and gives the one legitimate use of --baseline (prod carries ~124 hand-applied migrations with no ledger). Two hard rules: never delete a schema_migrations row to force a re-run, never edit a migration the ledger records as applied.

Prompt 3 — The full cutover. Leads with the thing that trips people: there's no Jekyll site to migrate. The cutover doc's headline finding is that the Jekyll-owned content inventory is empty — Pages serves the same docs/ bundle the Worker does. So "moving off Jekyll" is routing and DNS, not content. It keeps the 24-hour observation gate (the first apex-wide attempt was rolled back on 504s; the cause is fixed, which is a reason to retry, not to skip observing), and keeps OAUTH_CALLBACK_BASE_URL pinned until all eleven redirect URIs are registered — flipping it early breaks Google sign-in for everyone at once.

Prompt 4 — The Actions workflow. Answering your earlier question properly: worth it, but workflow_dispatch + a production environment approval, not auto-on-merge — merging and shipping to 23 live accounts aren't the same decision. The design detail that matters: it runs the decomposition of npm run deploy minus the rebuild, because npm run deploy builds first and CI would then ship a bundle it built rather than the reviewed bytes in docs/. That turns check-docs-fresh --strict into a real gate instead of something a fresh build silently papers over.
