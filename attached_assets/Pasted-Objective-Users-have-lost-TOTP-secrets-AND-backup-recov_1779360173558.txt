Objective
  Users have lost TOTP secrets AND backup recovery codes. We need
  a way to get them back into their account without opening the
  door to social-engineering takeovers.

Strategy — layered, with rising friction as path becomes less
controllable

  Layer 1 — Self-serve, low-friction (preferred)
    a. Backup recovery code (10 codes minted at TOTP enrollment).
       If user kept any, single use → bypass TOTP, force re-enrol.
    b. Verified passkey on another device (Prompt GI).
       If user enrolled a passkey, that's both factors. Re-enrol
       TOTP after sign-in.

  Layer 2 — Verified channel (medium friction)
    c. SMS to verified phone (if user enrolled SMS 2FA).
       OTP code → sign in. Country allow-list applies. Strict
       rate-limit: 3 tries / 15 min / phone, 10 / day / phone.
    d. Email magic link to registered email (Prompt GI).
       Requires email_verified=1. Single-use, 15-min TTL.
       This is allowed BUT marked "lower assurance" — the JWT
       issued carries `assurance_level: 'email_only'` and step-up
       is required for any sensitive action.

  Layer 3 — Identity-bound reset (high friction)
    e. KYC re-verification path via Persona / Sumsub.
       User submits a fresh KYC selfie + ID at /auth/recover.
       Vendor returns a verification_id matched against the user's
       original KYC record. On match, an admin recovery ticket is
       auto-created with `vendor_match: 'high'` and can be approved
       with no further human review by default.
       If match `low` / `medium` → human admin review required.
    f. Trusted-contact attestation.
       User nominated 2 trusted contacts at signup (cofounder, lawyer,
       partner). Trusted contacts each receive a signed attestation
       request; once both attest (signed by their authenticated
       Axal accounts), the recovery proceeds.

  Layer 4 — Manual admin recovery (last resort)
    g. /auth/recover ticket opens; admin reviews evidence (KYC
       artifacts, login history, communication history). Multi-
       sig required: TWO admins must sign off. Approval writes to
       admin_audit_log + notifies ALL channels the user ever
       enrolled (email, SMS, slack, any).

Cooling-off + tamper resistance
  - Every recovery action triggers a 24-hour cool-off before
    high-risk operations (billing changes, contract void, KYC
    re-submission for a different person, capital movement) can be
    performed.
  - User receives notification on every enrolled channel when a
    recovery is initiated and again when it completes.
  - During cool-off the account is in "recovery-pending" mode:
    can read; cannot move money, sign contracts, change billing,
    impersonate, or download DD reports.
  - Sessions issued through Layers 1c / 2c / 3e / 4g start with
    `assurance_level` < full and must be re-elevated by enrolling
    a fresh TOTP or passkey within 7 days, or the account locks
    again.

Worker routes
  POST /api/auth/recover/start              { email, channel: 'auto' }
       → returns next recovery options available for this user,
         ordered by layer.
  POST /api/auth/recover/backup-code        { code }
  POST /api/auth/recover/passkey-options
  POST /api/auth/recover/passkey-verify
  POST /api/auth/recover/sms-start
  POST /api/auth/recover/sms-verify         { code }
  POST /api/auth/recover/email-magic-start
  POST /api/auth/recover/email-magic-verify  { token }
  POST /api/auth/recover/kyc-start          (Persona/Sumsub inquiry)
  POST /api/auth/recover/kyc-callback        (vendor webhook)
  POST /api/auth/recover/trusted-contact-request
  POST /api/auth/recover/trusted-contact-attest  (signed by the
                                                   trusted contact's
                                                   own session)
  POST /api/admin/recovery/:ticket/approve
  POST /api/admin/recovery/:ticket/deny

Schema
  CREATE TABLE auth_recovery_tickets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    status TEXT NOT NULL,         -- 'open','vendor_pending',
                                  -- 'admin_pending','approved',
                                  -- 'denied','cancelled'
    paths_attempted TEXT,           -- json of layers tried
    evidence_json TEXT,             -- KYC match scores, attestation
                                    -- envelope ids, channel hashes
    cooling_off_until DATETIME,
    opened_ip TEXT,
    opened_ua TEXT,
    opened_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    closed_at DATETIME,
    closed_by_admin_id INTEGER,
    closed_by_admin2_id INTEGER     -- multi-sig
  );
  CREATE TABLE auth_trusted_contacts (
    user_id INTEGER NOT NULL,
    contact_user_id INTEGER NOT NULL,
    role TEXT,                       -- 'cofounder','lawyer','partner',
                                     -- 'family','colleague'
    added_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id, contact_user_id)
  );

UI
  /auth/recover landing page presents the available layers IN ORDER
  with one-paragraph honest explainers:
    "Have your backup recovery codes? Fastest."
    "Have a passkey enrolled on another device? Use it here."
    "Have access to your enrolled phone? Receive an SMS code."
    "Have access to the email on file? We'll email a verification
     link. (You'll need to re-verify your identity before doing
     anything sensitive.)"
    "Lost all of the above? Submit a fresh KYC. Persona/Sumsub
     will compare to your original verification."
    "Have trusted contacts on Axal? Two of them can attest for you."
    "Need a human? Open a recovery ticket. Our team will review
     within 1 business day."

Abuse defences
  - Lockout on too many failed verifications (Layer 1a/c).
  - Verified-phone country allow-list (toll fraud).
  - KYC vendor returns liveness score; reject below threshold.
  - Trusted-contact attestation requires the contact to be 2FA-
    authenticated themselves (no chain reactions).
  - Email magic link does NOT grant full assurance.
  - Multi-sig on admin approval prevents single rogue admin.
  - Every recovery generates a public audit-log row (admin view).
  - Notification to ALL enrolled channels on every state change
    (so an attacker who controls one channel cannot silently take
    over without alerting the user via another).

Frontend Settings > Security additions
  - "Set up trusted contacts" wizard
  - "Print your backup recovery codes (one more time)" — only
    available for re-issue if 2FA still enrolled
  - "View recent recovery activity"

Acceptance
  - A user with backup codes can recover in < 60s.
  - A user with only a passkey on a second device can recover.
  - A user who lost everything can complete the KYC-re-verify
    flow + cool-off and get back in within 48h.
  - Two admins required to approve a Layer-4 recovery.
  - All recovery actions notify every enrolled channel.
  - 24h cool-off enforced; sensitive routes blocked during cool-off.
