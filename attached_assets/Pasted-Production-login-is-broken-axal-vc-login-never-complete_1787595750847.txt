## Diagnosis (from code, not yet live-confirmed)

The committed build on main is internally consistent — docs/login/index.html's referenced hashes (api-*.js, index-*.js, react-vendor-*.js, etc.) all exist in the committed docs/assets/. Nothing in the repo itself is broken.

But your 504-mitigation deploy earlier (ce2a0195-...) was very likely run as a direct `wrangler deploy` rather than the root `npm run deploy` wrapper — nothing in that session touched or rebuilt docs/. If so, the LIVE assets binding may still be serving an older/mismatched docs/ snapshot than what main currently has, which means the HTML for /login references JS chunk hashes that don't resolve at /assets/* on the live edge.

This repo has TWO client-side auto-recovery mechanisms for exactly that failure (main.jsx's chunk-error handler, and an inline boot watchdog in docs/index.html) — both are deliberately one-shot (sessionStorage + a ?__reboot= URL guard), so they can't loop forever; they try once and then fail to a clean blank/broken state. A user manually mashing reload against that dead end reads exactly as "keeps refreshing, never logs in."

For each hash returned, confirm it 200s with the right content-type (not an HTML fallback):

If any of those 404, or return text/html instead of javascript — that confirms the asset-skew hypothesis. Also worth a quick look in a real browser: DevTools Network tab on /login/, any /assets/*.js request showing 404; or Console for "ChunkLoadError" / "vite:preloadError".

If assets DO resolve cleanly and the page still won't complete login, this isn't asset skew — check instead whether the auth cookie set on login has a Domain that doesn't match the page's origin, and whether localStorage.getItem('token') actually holds a value right after a login attempt (open DevTools Application tab).
