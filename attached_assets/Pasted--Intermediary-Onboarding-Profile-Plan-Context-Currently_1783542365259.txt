# Intermediary Onboarding Profile Plan

## Context

Currently, when users complete the onboarding wizard they're immediately assigned their designated role. However, there needs to be an intermediary holding period where:
1. Admin can review the user's onboarding conversation
2. Admin creates and sends a binding (partnership agreement)
3. User signs the binding
4. Only THEN does admin assign them their actual role

During this intermediary "exploring" period, users need access to the unified Studio dashboard (same as all other users) with core features: Personal Advisor (for profiling), Documents hub, and Trust Center.

This ensures no user bypasses admin review and prevents premature role assignment before legal agreements are signed.

## Recommendation

Create a new **"exploring"** role type as a temporary holding state. After users complete the initial onboarding wizard, they get assigned "exploring" role and see a unified Studio dashboard (same as all other users). 

Meanwhile:
- Admin reviews the onboarding conversation and user data
- Admin creates a binding (partnership agreement) and sends it to user via e-signature flow
- User signs binding
- Admin then assigns the actual role (founder/investor/partner/advisor)

During the exploring phase, users access: Personal Advisor (ongoing profiling), Documents, Trust Center.

### Key Design Principles
- **Admin-driven routing**: Not automatic—requires human review and legal agreement before role assignment
- **Unified dashboard**: All exploring users see the same sidebar + features, regardless of origin
- **Reuse existing infrastructure**: Partner binding flow (partner_invitations → binding → signature)
- **Minimal schema changes**: Just add "exploring" to role enum; most infrastructure already exists

### 4. Admin Review & Binding Flow

**Admin Dashboard** (existing partner portal extended):
- Admin can view list of exploring users with their onboarding conversation summaries
- Admin creates binding/agreement for user (reuse partner_deals infrastructure)
- Binding is sent to user via e-signature flow (existing: `/partner-onboarding/:token`)
- Once signed, admin assigns actual role via new admin endpoint

**New Endpoints:**
- `POST /api/admin/users/{id}/create-binding` → Creates binding for exploring user
  - Input: `{user_id, role: "founder"|"investor"|"partner"|"advisor"}`
  - Output: Generates binding token, sends e-signature invite
- `PATCH /api/admin/users/{id}/assign-role` → Assigns final role after binding signed
  - Input: `{user_id, role: "founder"|"investor"|"partner"|"advisor"}`
  - Output: Updates users.role, sets role_confirmed=true, triggers role-specific onboarding if needed

**User Experience During Exploring:**
1. User completes onboarding wizard → assigned "exploring" role → sees Studio dashboard
2. User optionally completes Personal Advisor profiling (Skills Radar, Values, Archetype, Fit)
3. Admin reviews user's conversation + profiling data
4. Admin sends binding via e-signature
5. User signs binding
6. Admin assigns actual role
7. User redirected to role-specific dashboard/onboarding

## Implementation Plan

### Phase 1: Database & API (Backend)
1. Create migration to add `exploring` role type to users.role enum
2. Add `role_confirmed BOOLEAN DEFAULT FALSE` to users table (tracks if admin assigned final role)
3. Create `POST /api/admin/users/{id}/create-binding` endpoint
   - Validates user is in exploring role
   - Creates partner_deals record with binding terms
   - Generates e-signature token and sends invite
4. Create `PATCH /api/admin/users/{id}/assign-role` endpoint
   - Validates binding is signed
   - Updates users.role to final role
   - Sets role_confirmed = true
   - Triggers post-role-assignment logic (onboarding wizard if needed)
5. Ensure `/api/advisor/progress` works for exploring users (already modular)

### Phase 2: Frontend Shell & Routing
1. Update `App.jsx` route logic to handle "exploring" role
2. Create route for exploring users: `/studio` (same dashboard as other roles)
3. Update `sidebarConfig.js` to include "exploring" role config
4. Ensure role-gating doesn't break for exploring users accessing Documents, Trust Center, Personal Advisor

### Phase 3: UI Components (Mostly Reuse)
1. Add "exploring" role to sidebarConfig with links to:
   - Personal Advisor (`/studio/advisor`)
   - Documents (`/studio/documents`)
   - Trust Center (`/studio/trust`)
2. Ensure `PersonalAdvisor.jsx` works with exploring role
3. Ensure `TrustCenterPage.jsx` and Documents work with exploring role (likely no changes needed)

### Phase 4: Admin Interface
1. Create admin page: `/admin/exploring-users` to list all exploring users
2. Show user's onboarding conversation summary
3. Add button to "Create & Send Binding" → triggers Phase 1 endpoint
4. Show binding status (pending signature, signed)
5. Add button to "Assign Final Role" → triggers Phase 1 endpoint

## Notes

- The "exploring" role is temporary—it's a holding state until admin assigns final role (role_confirmed = false until transition)
- Profiling (Skills Radar, Values, Archetype, Fit) is optional during exploring phase; users can start Personal Advisor conversations at any time
- Admin must review onboarding conversation before creating binding (governance gate)
- Binding reuses existing partner_deals infrastructure—same e-signature flow already tested
- All exploring users see unified `/studio` dashboard regardless of their original onboarding path
- Role assignment is admin-driven, not algorithmic, giving full control over placement
- After role transition, all profiling data (skills, values, archetype) carries over to user's new profile
