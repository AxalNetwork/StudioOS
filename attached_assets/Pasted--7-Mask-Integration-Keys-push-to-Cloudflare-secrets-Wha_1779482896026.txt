#7 - Mask Integration Keys & push to Cloudflare secrets
What & Why
Today the Integration Keys panel stores admin-entered Client ID / Secret in the encrypted provider_oauth_keys D1 table and displays the full Client ID in plaintext. Two changes:
1. Mask after save. Never show full Client ID in the admin UI — only first4••••last4. (Secret is already never returned, that stays.)
2. Promote to real Cloudflare Worker secrets on save. When an admin saves or rotates keys, the worker calls the Cloudflare API to set the matching pair of Worker secrets (e.g. SLACK_CLIENT_ID + SLACK_CLIENT_SECRET), then deletes the encrypted DB row. From that point on the credentials live only as Cloudflare secrets and loadOauthCreds()'s existing env-first lookup picks them up on the next isolate boot — the row becomes the single source of truth as a real secret.
Done looks like
* Admin enters Client ID + Secret in the Integration Keys panel and clicks Save.
* The worker writes both as Cloudflare Worker secrets via the Cloudflare API and deletes the encrypted DB row in the same request. On success the card flips to the existing ENV VARS badge (was previously ADMIN-MANAGED).
* The Client ID in the card is masked as 1104••••7987 — never the full value.
* "Rotate keys" works the same way: pushes a new secret via the API, no DB row left behind.
* "Remove" deletes the Cloudflare secrets via the API in addition to clearing any DB row, and cascades integrations.status='disconnected' exactly as today.
* If the Cloudflare API call fails (missing token, 4xx/5xx, network), the save is rejected with a clear error toast and nothing is partially written (no orphan DB row, no half-set secret pair). The admin sees an actionable message — e.g. cloudflare_api_token_missing, cf_api_forbidden, cf_api_failed.
* Existing rows already in provider_oauth_keys keep working until an admin re-saves them (lazy migration — no destructive backfill).
* All Cloudflare API calls are recorded in admin_audit_log with action integration_key_cf_secret_push / …_rotate / …_delete, capturing provider, the two env-var names touched, and outcome.
Out of scope
* Changing which env vars each provider reads (PROVIDER_ENV_VARS map stays as-is).
* Changing the cryptoBox at-rest encryption used while a row temporarily exists during the save flow.
* Provisioning the Cloudflare API token itself — that's an ops prerequisite (see below).
* Touching providers configured purely via [env] secrets today (HubSpot, LinkedIn, Calendly per screenshot) — they already show ENV VARS and the Configure button is disabled.
* Backfilling existing DB rows into Cloudflare secrets automatically — admin must re-save to promote.
Steps
1. Cloudflare secrets client. Add a small worker-side helper that wraps the Cloudflare API endpoints for managing Worker script secrets (PUT /accounts/{account_id}/workers/scripts/{script_name}/secrets and the corresponding DELETE). It reads CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID, and the worker script name from env. All calls return a typed {ok, status, error?} result; never logs token values. Includes a unit-testable setSecret(name, value) and deleteSecret(name).
2. Wire save / rotate / delete through the API. Update the admin save, rotate, and remove handlers for integration keys so that on success they: (a) push the secret pair (or delete both) via the helper from step 1, (b) only then delete (or skip writing) the encrypted DB row, (c) invalidate the in-isolate creds cache. If the API call fails, return a structured 502-ish error with a stable error code the frontend can translate to a friendly toast — and leave the DB row untouched so retry is safe.
3. Mask Client ID on the wire and in the UI. Change the admin-list endpoint so client_id_preview is already masked as first4••••last4 (and null when fewer than 8 chars). Update the Integration Keys card so it renders the masked value verbatim — no truncation logic in the frontend. The Edit/Rotate modal does not pre-fill the existing Client ID; admin must retype on rotate-with-id-change.
4. Audit log entries. Write admin_audit_log rows for each Cloudflare-secret push, rotate, and delete with provider key, the env-var names touched, the outcome, and the acting user. Match the shape already used by the Telegram PII override audit entry.
5. Docs + ops prerequisite note. Add a short note in replit.md "Backend / Worker" gotchas explaining that admin-saved integration keys are now promoted to real Cloudflare secrets and the DB row is deleted; calls require CLOUDFLARE_API_TOKEN (scoped to Workers Scripts: Edit) and CLOUDFLARE_ACCOUNT_ID Worker secrets. Add a one-line entry to CHANGELOG.md. Add a new ops item under "Ops items still owned by user" for provisioning the Cloudflare API token if it isn't already set.
